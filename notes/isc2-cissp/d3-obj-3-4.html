Overview

Objective 3.4

3.4 Understand security capabilities of information systems (e.g., memory protection, Trusted Platform Module (TPM), Hardware Security Module (HSM), encryption/decryption).

Roots of trust are on the 1.11 page; cryptographic algorithms and key management on the 3.6 page; security models that these mechanisms enforce on the 3.2 page. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. Its laptops, payment platform and cloud AI workloads each rely on different hardware security features.

Why system capabilities matter

Objective 3.4Understanding that application controls depend on the platform beneath them.

Every access control check, encryption call and audit record in an application depends on the operating system and hardware below it behaving correctly. If an attacker controls the kernel, the hypervisor or the firmware, they can bypass any control above. Security capabilities built into the platform provide the foundation: separating privileged from unprivileged code, keeping processes apart, protecting keys in hardware, measuring what boots, and isolating sensitive computation. Selecting controls (objective 3.3) therefore includes checking that the platform offers and enables these capabilities.

Processor privilege and execution modes

Objective 3.4Knowing how processors separate trusted code from everything else.

  • Privilege levels (often called protection rings): the processor runs the operating system kernel at the most privileged level and applications at the least. Only privileged code can execute sensitive instructions, change memory mappings or talk directly to hardware.
  • Kernel mode and user mode: applications run in user mode and request services through controlled system calls; a fault in user mode cannot directly corrupt the kernel.
  • Hardware virtualization support: processors add a level for hypervisors, so guest operating systems run their kernels without being able to reach the hypervisor or other guests (objective 3.5).
  • Firmware and management engines: code below the operating system (UEFI firmware, baseboard management controllers, embedded management processors) runs with very high privilege, so it must be protected by secure boot, signed updates and restricted management networks.

The boundary between these levels is a security perimeter: crossing it must always go through checked interfaces. Many serious vulnerabilities are privilege escalations that break this boundary, which is why kernel, hypervisor and firmware patches are high priority.

Trusted computing base and reference monitor

Objective 3.4Understanding the small core of hardware and software that every other security control depends on.

  • Trusted computing base (TCB): the "totality of protection mechanisms within a computer system, including hardware, firmware, and software", the combination of which enforces the security policy (CNSSI 4009). Everything outside the TCB is untrusted; a flaw inside it can break the whole policy, so it should be as small as possible.
  • Reference monitor: "a set of design requirements on a reference validation mechanism" that enforces an access control policy over all subjects and objects. SP 800-53 AC-25 requires it to be "tamperproof, always invoked, and small enough to be subject to analysis and testing."
  • Security kernel: the "hardware, firmware, and software elements of a trusted computing base implementing the reference monitor concept."

The three reference monitor properties match design principles from objective 3.1: always invoked is complete mediation, tamperproof protects the mechanism itself, and small enough to verify is economy of mechanism. The boundary between the TCB and the rest of the system is the security perimeter, enforced by the processor privilege levels above.

Memory protection and isolation

Objective 3.4Knowing how systems keep processes apart and stop attackers running code where only data should be.

  • Process isolation (SP 800-53 SC-39): "maintain a separate execution domain for each executing system process", with separate address spaces so one process cannot change another's code. Sandboxes, containers and virtual machines extend the same idea.
  • Virtual memory: the processor's memory management hardware maps each process's addresses to physical memory and blocks access outside its own space.
  • Memory protection (SI-16): controls to stop "unauthorized code execution" in memory, which NIST says include "data execution prevention and address space layout randomization". Data execution prevention (DEP, also called NX or no-execute) marks data areas such as the stack and heap as non-executable, ideally enforced by hardware. Address space layout randomization (ASLR) places code and data at unpredictable addresses, so exploits cannot rely on known locations.
  • Privilege separation: kernel and user mode, so applications cannot directly touch hardware or other processes' memory.

These protections defeat whole classes of attack, such as buffer overflows that inject and run code. Memory-safe programming languages remove many of the underlying bugs altogether, which is why CISA's Secure by Design work asks vendors for memory-safety roadmaps (objective 8.2). Sensitive data in memory (keys, passwords) should also be cleared after use, since memory can be read by debuggers, crash dumps or attacks on hardware.

TPMs, HSMs and trusted execution environments

Objective 3.4Choosing between hardware that protects one device's keys and integrity, hardware that protects an organization's keys at scale, and protected areas inside the processor.

A Trusted Platform Module (TPM) is a chip on a device's motherboard that protects keys and records the device's state. Its main functions:

  • Measured boot: each boot stage is measured and recorded, so changes to firmware or the boot loader can be detected.
  • Binding: keys are wrapped so only that TPM can unwrap them, under a storage root key kept inside the TPM.
  • Sealing: a key is tied to the platform's measured state and released only if the measurements match, so a tampered system cannot unlock the disk.
  • Attestation: the TPM signs a report of its measurements, so a remote service can check that the device is in a trusted state before trusting it.

A hardware security module (HSM) is a dedicated, tamper-resistant device, usually a network appliance, a plug-in card or a cloud service, that generates, stores and uses an organization's most important keys, such as certificate authority keys or payment encryption keys, and performs cryptographic operations at high speed without the keys ever leaving it. HSMs are typically FIPS 140-3 validated at Level 3. The usual distinction: a TPM protects one device and its integrity; an HSM protects many systems' keys centrally.

A trusted execution environment (TEE), or secure enclave, is "an area or enclave protected by a system processor": code and data inside it are isolated, even from the operating system and hypervisor, which makes it the basis of confidential computing for data in use (objective 2.6). Remote attestation lets a client verify which code is running in the enclave before sending it data.

Encryption and decryption capabilities

Objective 3.4Using the encryption features built into platforms, and keeping keys out of software where possible.

  • Processor acceleration: modern processors include instructions that speed up standard algorithms such as AES, so encryption everywhere costs little performance.
  • Full-disk encryption in operating systems, with keys sealed to the TPM so the disk unlocks only on the expected, untampered device, optionally with a PIN.
  • Self-encrypting drives: encryption in the drive hardware, which also allows near-instant cryptographic erase (objective 2.2).
  • Memory encryption: some processors encrypt memory contents, protecting against physical attacks and, combined with TEEs, against a compromised hypervisor.
  • Cloud key management services backed by HSMs, with options for customer-managed or externally held keys.
  • Hardware random number generators: good keys need good randomness; weak randomness has broken otherwise strong cryptography.

The design rule: use built-in, validated capabilities rather than custom cryptographic code, and hold keys in a TPM, HSM or TEE rather than in files or application memory where possible. At the retail group, laptops use full-disk encryption sealed to the TPM, payment keys never leave a pair of HSMs, and the fraud-scoring AI model runs in a TEE in the cloud.

Hardening the platform

Objective 3.4Turning built-in capabilities on and keeping them on.

Capabilities only help when they are enabled and maintained. Platform hardening typically includes:

  • Secure boot and measured boot enabled, with firmware passwords and signed firmware updates; boot measurements checked by device management or attestation.
  • Virtualization-based protections where available, which use the hypervisor to isolate credentials and security-critical processes from the main operating system.
  • Exploit mitigations (DEP, ASLR and control-flow protections) turned on system-wide, and applications built with compiler protections.
  • Least functionality: unused services, drivers, interfaces and debug ports disabled; baseboard management controllers on isolated management networks with changed default credentials.
  • Configuration baselines enforced and monitored for drift (objective 7.3), and firmware patched like software.

Procurement matters too: require these capabilities (TPM, secure boot, memory protection, supported firmware update process) in hardware purchases, since they cannot be added later.

Processor and memory fundamentals

Objective 3.4The hardware concepts behind isolation and privilege.

  • Protection rings: ring 0 is the kernel (most privileged), rings 1 and 2 historically held drivers and services, ring 3 runs user applications. Processors switch between a privileged supervisor (kernel) state and an unprivileged problem (user) state.
  • Processing terms: multitasking (one processor switching between tasks), multiprogramming (older batch interleaving), multiprocessing (several processors: symmetric SMP sharing memory, or massively parallel MPP with their own), and multithreading (several threads within one process).
  • Memory types: RAM is volatile (dynamic DRAM needs refreshing; static SRAM is faster, used for cache); ROM is non-volatile, with PROM (written once), EPROM (erased by ultraviolet light), EEPROM and flash (erased electrically); registers and cache sit closest to the CPU.
  • Virtual memory: disk space used as an extension of RAM (paging or swap); sensitive data in memory can be written to disk, which is why swap and hibernation files need encryption.
  • Firmware: code in non-volatile memory (BIOS, UEFI) that runs before the operating system; protected by secure boot and signed updates.

Security modes of operation

Objective 3.4How systems handling classified data are described by who may use them.

These modes describe systems that process data at more than one classification level, by what every user must have:

  • Dedicated: every user has clearance, formal access approval and need-to-know for all data on the system.
  • System high: every user has clearance and formal approval for all data, but need-to-know for only some of it.
  • Compartmented: every user has clearance for the highest level, but formal approval and need-to-know only for some compartments.
  • Multilevel: users have different clearances, and the system itself (with mandatory access control and a trusted computing base) enforces separation.

Related design concepts: layering (separating the system into layers that communicate only through defined interfaces), abstraction (hiding detail behind simpler interfaces), data hiding (preventing processes at one layer from seeing data at another), and a trusted path (a channel between the user and the trusted computing base that cannot be spoofed, such as a secure attention key sequence before sign-in).

Scenario check

PracticeMatching system capabilities to needs, as exam questions do.

Scenario 1: the stolen laptop
Situation
A laptop is stolen. Its disk is encrypted with a key sealed to the TPM. The thief removes the disk and tries it in another computer.
Best answer
The disk stays unreadable: the key is released only by that laptop's TPM, and only when its measured boot state matches.
Why
Sealing ties keys to the platform and its state; moving the disk or tampering with boot breaks the seal.
Scenario 2: the CA signing key
Situation
The internal certificate authority's root signing key is stored as a file on the CA server.
Best response
Move it into an HSM (FIPS 140-3 Level 3) with dual control for key operations, and keep the root CA offline.
Why
HSMs protect high-value keys so they never leave hardware; files can be copied by anyone who compromises the server.
Scenario 3: the buffer overflow
Situation
An old in-house service written in C has a stack buffer overflow. Rewriting it will take a year.
Best response
Enable DEP and ASLR, run it with least privilege in an isolated container, patch the specific flaw, and plan the rewrite in a memory-safe language.
Why
Memory protections make exploitation much harder and isolation limits damage, while the memory-safe rewrite removes the class of bug.
Scenario 4: processing on a shared cloud host
Situation
The data science team wants to score sensitive customer data in the cloud but worries about the provider's administrators or a compromised hypervisor seeing it.
Best answer
Use confidential computing: run the workload in a TEE with memory encryption, and verify it by remote attestation before releasing keys.
Why
TEEs protect data in use even from the operating system and hypervisor.

Key takeaways

  • Platform first: application controls depend on the kernel, hypervisor and firmware beneath them.
  • Privilege levels: kernel vs user mode, hypervisor level, protected firmware; the security perimeter is crossed only through checked interfaces.
  • TCB: all protection mechanisms enforcing policy; keep it small. Reference monitor: tamperproof, always invoked, verifiable (AC-25). Security kernel implements it.
  • Memory protection: process isolation (SC-39), virtual memory, DEP and ASLR (SI-16), kernel/user mode; memory-safe languages remove root causes; clear secrets from memory.
  • TPM: one device's keys and integrity (measured boot, binding, sealing, attestation). HSM: an organization's keys at scale, typically FIPS 140-3 Level 3. TEE: processor-protected enclave for data in use, with remote attestation.
  • Encryption capabilities: AES acceleration, full-disk encryption sealed to the TPM, self-encrypting drives, memory encryption, HSM-backed key services, hardware randomness; use built-in validated features.
