Overview

Objective 7.3

7.3 Perform Configuration Management (CM) (e.g., provisioning, baselining, automation).

Change management, which approves changes to baselines, is on the 7.8 page; secure configuration of cloud systems on the 3.4 page. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. Its 300 store servers, 9,000 tills and cloud estate are built from code and checked for drift every night.

Configuration management

Objective 7.3Provisioning systems from approved baselines, detecting drift, and automating both.

Security-focused configuration management (NIST SP 800-128) keeps systems in known, approved, secure states. The SP 800-53 CM family supplies the controls: CM-2 baseline configuration, CM-3 configuration change control, CM-6 configuration settings, CM-7 least functionality and CM-8 component inventory.

  1. BaselineDefine the approved configuration for each system type, starting from a recognized secure configuration guide or benchmark (NIST's National Checklist Program, SP 800-70, lists many), tailored and documented.
  2. ProvisionBuild every new system from the baseline: hardened golden images, templates, or infrastructure as code, so new systems are secure by default and identical.
  3. Control changesChanges to baselines go through change control, are tested, and update the baseline version.
  4. MonitorCompare running systems with the baseline continuously; drift (unapproved changes) is corrected or investigated as a possible incident.
  5. InventoryKeep a current inventory of components and their configurations, in a configuration management database (CMDB) or from automated discovery.

Automation makes this scale: configuration management tools enforce the desired state, infrastructure-as-code templates are reviewed and scanned before deployment, and immutable infrastructure replaces rather than patches running servers. The code repository then becomes a critical asset: protect it, require reviews for changes, and sign what is deployed.

Baseline vs change management. Configuration management defines and maintains the approved state of systems; change management is the process that approves changes to it. A question about an unapproved setting found on a server is about configuration monitoring; a question about approving a new setting is about change management.

Writing and tailoring baselines

Objective 7.3Turning a generic benchmark into an approved configuration for each kind of system.

  • Start from a recognized source: consensus benchmarks (such as CIS Benchmarks), government configuration guides (such as DISA STIGs), and vendor security guides, many listed in NIST's National Checklist Program.
  • Pick a level: benchmarks often offer a basic level that rarely breaks functionality and a stricter level for high-risk systems; choose by the system's classification.
  • Tailor and document: remove or change settings that break required functions, record each deviation with its reason and approver, and add organization-specific settings (logging targets, banners, agents).
  • One baseline per role: workstation, store server, database server, web server, network device and container host baselines differ; a single generic baseline is either too loose or breaks things.
  • Test before rollout: apply new baselines to a pilot group first, with a rollback plan.
  • Version and review: baselines have owners, version numbers and review dates, and are updated when the operating system, threats or benchmarks change.

Least functionality (CM-7) is part of every baseline: disable unneeded services, ports, protocols and software, and allow only approved applications where practical. Each removed service is one less thing to patch and monitor.

Detecting and handling drift

Objective 7.3Finding systems that no longer match their baseline, and deciding what to do.

Drift happens through emergency fixes, manual troubleshooting, software installs, failed deployments and attackers. Handling it well needs:

  • Regular comparison: configuration management agents, compliance scanners or cloud posture tools compare actual state with the baseline, continuously or on a schedule.
  • Decide per setting: low-risk drift can be corrected automatically (the tool restores the desired state); high-impact or unexplained changes raise an alert for investigation, because an attacker adding a service or account looks exactly like drift.
  • Link to change records: a change with an approved ticket updates the baseline or is a documented exception; a change without one is a finding.
  • Reconcile the inventory: discovery scans find systems missing from the CMDB, which usually also means they are missing from patching and monitoring.
  • Measure: the share of systems compliant with their baseline, the number of exceptions and their age, and the time to correct drift.

At the retail group, the nightly drift report flagged a store server with remote desktop enabled and a new local administrator. There was no change ticket, so it was treated as a possible incident; it turned out to be a support engineer's shortcut, and remote access now goes only through the PAM gateway.

Configuration management in cloud and containers

Objective 7.3Applying baselines and change control when infrastructure is code.

  • Infrastructure as code (IaC): templates define networks, servers, permissions and services. Review them like code, scan them for insecure settings before deployment, and deploy only through the pipeline so the template stays the source of truth.
  • Policy as code: rules (no public storage, encryption required, approved regions only) checked automatically in the pipeline and enforced at the organization level of the cloud account structure as guardrails no team can override.
  • Immutable images: hardened machine and container images built and signed by the pipeline; to change a server, build a new image and replace it rather than logging in to patch.
  • Containers and orchestration: minimal base images, no secrets in images, scanned for vulnerabilities, and admission controls that refuse images that are unsigned or break policy.
  • Tagging and inventory: owner, environment and data classification tags on every resource, so drift and findings reach the right team.
  • Console changes: manual changes in the cloud console bypass review and create drift; restrict them to break-glass use and detect them from control plane logs (objective 7.2).

Asset inventory and the CMDB

Objective 7.3Knowing what exists, because nothing else in configuration management works without it.

CM-8 asks for an inventory of system components that is accurate, at the right level of detail, and kept current. In practice:

  • Several sources: network discovery scans, endpoint and EDR agents, cloud provider APIs, virtualization managers, purchasing records and identity systems each see part of the estate; reconcile them into one view.
  • What to record: owner, location, function, data classification, baseline and version, installed software and versions, and relationships (which application runs on which servers, which depend on which databases).
  • Configuration items and relationships: a configuration management database (CMDB) stores configuration items and their dependencies, which change management uses for impact analysis and incident response uses to understand what an outage or compromise affects.
  • Software inventory: which versions of which software run where, including libraries and SBOMs for in-house applications, so a new critical vulnerability can be located within hours.
  • Unknown assets: anything found on the network that is not in the inventory is investigated and then either registered with an owner or removed.

The inventory is only as good as its update process: building systems through the pipeline and registering them automatically keeps it accurate far better than manual entry.

Network devices and operational technology

Objective 7.3Extending configuration management beyond servers and workstations.

  • Network devices: routers, switches, firewalls and wireless controllers have baselines too. Back up their configurations automatically after every change, keep them in version control, compare them with a golden configuration, and alert on unexpected differences.
  • Firmware: track firmware versions in the inventory and update them through change control, since many network device vulnerabilities are fixed only in firmware.
  • Management plane: device administration only from management networks, through named accounts with central authentication (TACACS+ or RADIUS), never with default or shared credentials.
  • Operational technology: industrial and building control systems often cannot be scanned aggressively or patched quickly. Record their configurations and logic, monitor passively for changes, and coordinate changes with the vendor and the operations engineers in planned windows.
  • Point-of-sale and kiosks: locked-down builds with application allowlisting and no local administrator access.

At the retail group, firewall configurations are pulled every hour into a repository; any change not matching a change ticket opens an incident ticket for the network team.

Endpoints and mobile devices

Objective 7.3Keeping laptops, phones and tablets in an approved configuration wherever they are.

  • Unified endpoint management: policies for encryption, screen lock, firewall, updates and allowed applications pushed to devices over the internet, not only on the office network.
  • Compliance checks: devices that fall out of compliance (encryption off, overdue updates, jailbroken) lose access to corporate data through conditional access.
  • Autopilot-style enrollment: new devices configure themselves from the baseline at first sign-in, so shipping a laptop to a remote worker does not bypass hardening.
  • Personal devices: managed work profiles or app-level controls separate company data from personal data.
  • Lost or retired devices: remote wipe and removal from the inventory.

Roles in configuration management

Objective 7.3Who owns baselines, changes and evidence.

  • Baseline owners (often platform teams) write and maintain baselines for their technologies.
  • Security sets minimum requirements, reviews baselines and deviations, and monitors compliance.
  • System owners approve deviations for their systems and accept the residual risk.
  • The change board approves baseline changes with significant impact.
  • Audit checks that baselines exist, are applied and are monitored.

Clear ownership prevents the common failure where a baseline was written once, never updated, and no longer matches any running system.

Scenario check

PracticeApplying the objective to situations like those in exam questions.

Scenario 1: the unexplained setting
Situation
A nightly scan finds that a payment server has a new listening service not in its baseline and no change ticket.
Best response
Treat it as a possible incident: investigate before simply reverting, then restore the baseline and check how the change was made.
Why
Unapproved drift can be an attacker; configuration monitoring feeds incident detection.
Scenario 2: the benchmark breaks the application
Situation
Applying the strict benchmark level breaks a warehouse application.
Best response
Tailor the baseline: document the deviation, its reason, compensating controls and the approver, and keep the rest of the benchmark.
Why
Baselines are tailored and deviations recorded, not abandoned.
Scenario 3: hand-built servers
Situation
Penetration test findings keep coming from servers built by hand.
Best response
Provision every server from hardened images or infrastructure as code through the pipeline.
Why
Building from an approved baseline makes systems secure and identical by default.
Scenario 4: the console fix
Situation
An engineer fixes a production outage by changing a firewall rule in the cloud console.
Best response
Record it as an emergency change, update the infrastructure-as-code template to match (or revert), and review it after the fact.
Why
The template must remain the source of truth; emergency changes still go through change control afterwards.
Scenario 5: the remote laptop
Situation
Laptops for remote staff are shipped straight from the vendor and configured by users at home.
Best response
Use zero-touch enrollment so devices apply the baseline at first sign-in, and block corporate access until compliant.
Why
Baselines must apply wherever devices are provisioned.

Key takeaways

  • Configuration management (SP 800-128; CM-2, -3, -6, -7, -8): baseline, provision from it, control changes, monitor drift, keep the inventory; automate and protect the code.
  • Baselines: from benchmarks and guides, a level by risk, tailored with documented deviations, one per role, tested, versioned; least functionality.
  • Drift: compare regularly, auto-correct low-risk drift, investigate unexplained changes as possible incidents, link to change records, reconcile the inventory.
  • Cloud and containers: IaC reviewed and scanned, policy as code and guardrails, immutable signed images, admission controls, tags, no unmanaged console changes.
