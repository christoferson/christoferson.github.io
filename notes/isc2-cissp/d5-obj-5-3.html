Overview

Objectives 5.3 and 5.4

5.3 Federated identity with a third-party service. 5.4 Implement and manage authorization mechanisms.

Access control models are introduced in CC 3.2 and SSO on the 5.1–5.2 page. This page covers how federation is built and attacked, and how to choose and enforce an authorization model. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. It runs an on-premises directory synchronized to a cloud identity provider, which federates to about 150 SaaS applications and to two logistics partners.

How federation works

Objective 5.3Understanding the parties, the assertion and the trust relationship that let one organization vouch for users at another.

  • Identity provider (IdP): "the party in a federation transaction that creates an assertion for the subscriber and transmits the assertion to the RP" (NIST SP 800-63-4). It authenticates the user.
  • Relying party (RP), or service provider: the application that "processes assertions from the IdP and provides the service that the subscriber is trying to access" (SP 800-63C-4). It never sees the password.
  • Assertion: "a verifiable statement about the subscriber account to the RP", signed by the IdP (and possibly encrypted), carrying the identity, attributes and details of the authentication event.
  • Trust: set up in advance by exchanging metadata and signing certificates, under an agreement on attributes, assurance and responsibilities.

An assertion reaches the RP through the front channel (redirects through the user's browser) or the back channel (the browser carries only a reference, and the RP fetches the assertion directly from the IdP, which keeps it away from the browser). NIST defines three federation assurance levels: FAL1 "a basic level of protection"; FAL2 "a high level of protection", which requires additional protections; and FAL3, where the RP must also verify that the user controls an authenticator, through a holder-of-key assertion or an authenticator bound to the RP, so a stolen assertion alone is useless.

Federation protocols

Objective 5.3Telling apart the protocols that authenticate users from the one that delegates authorization.

ProtocolPurposeTypical use
SAML 2.0 (OASIS)Authentication and attribute assertions in signed XMLEnterprise SSO to web applications and SaaS
OpenID Connect"A simple identity layer on top of the OAuth 2.0 protocol": ID tokens (JWTs) say who the user isModern web and mobile sign-in, consumer and workforce
OAuth 2.0 (RFC 6749)Delegated authorization: access tokens let an application call an API on the user's behalf; not authentication by itselfAPI access, "allow this app to read your calendar"
SCIM 2.0Provisioning: creating, updating and removing accounts across domainsKeeping SaaS accounts in step with the directory

OAuth's security best current practice (RFC 9700, 2025) drops the implicit and password grants and requires PKCE. Older options still seen: WS-Federation in some enterprise products, and Kerberos inside on-premises domains (covered on the 5.5–5.6 page).

OAuth is authorization, not authentication. An OAuth access token says what an application may do, not who the user is. If a question asks for user sign-in across organizations, the answer is SAML or OpenID Connect; if it asks for an application to access an API on a user's behalf, it is OAuth.

On-premises, cloud and hybrid

Objective 5.3Choosing where the identity provider runs, and protecting the signing keys that every federated service trusts.

  • On-premises: the organization runs its own directory and federation server. It keeps full control, but must patch, harden and make highly available the servers that every application depends on.
  • Cloud (identity as a service): a provider runs the IdP, with built-in MFA, conditional access and connectors to SaaS applications. Less to operate, but the organization depends on the provider's security and availability and must configure it well.
  • Hybrid: an on-premises directory synchronized with a cloud IdP, the most common enterprise case. Convenient, but it links the two: the synchronization servers and any on-premises federation server become tier-0 assets, because compromising them can mean compromising the cloud as well.

The signing key is the crown jewel. Anyone who holds an IdP's token-signing key can forge assertions for any user, bypassing passwords and MFA. CISA advisory AA21-008A (2021) described attackers forging tokens trusted by an on-premises identity provider, "often referred to as 'Golden Security Assertion Markup Language' attacks". In 2023, attackers "used a Microsoft account (MSA) consumer key to forge tokens to impersonate consumer and enterprise users" (CISA AA23-193A); the Cyber Safety Review Board found that intrusion "was preventable".

  • Keep signing keys in HSMs, rotate them, and restrict and monitor who can reach the federation and synchronization servers.
  • Treat identity infrastructure as tier 0: dedicated admin accounts and workstations, no internet browsing from them.
  • Correlate sign-ins at applications with authentication events at the IdP; tokens with no matching authentication suggest forgery.
  • With third parties, agree in the contract which attributes are shared, the assurance level, incident notification, and how access is removed when the relationship ends.

Authorization models

Objective 5.4Choosing the access control model that fits the data, the organization and the risk.

  • Discretionary access control (DAC): "leaves a certain amount of access control to the discretion of the object's owner" (NIST SP 800-192), usually through ACLs and owner, group and other permissions. Flexible but "inherently weak", because users can pass on copies.
  • Mandatory access control (MAC): "access control policy decisions are made by a central authority, not by the individual owner of an object", by comparing the object's sensitivity label with the subject's clearance (and need-to-know categories). Users cannot change it. Used for classified systems; Bell-LaPadula is its model (objective 3.2).
  • Role-based access control (RBAC): permissions attach to roles and users get roles. NIST levels: core, hierarchical (roles inherit), and static and dynamic separation of duties. The standard enterprise model, but ad hoc roles lead to "role explosion".
  • Rule-based access control (RuBAC): access decided by administrator-set rules that apply to everyone, such as firewall rules by address and port or "no logons outside business hours". NIST notes there is "no commonly understood definition or formally defined standard" for it.
  • Attribute-based access control (ABAC, SP 800-162): decisions from subject attributes, object attributes, environment conditions ("current time, day of the week, location of a user, or the current threat level") and policy. Very fine-grained and avoids role explosion, but attributes must be accurate and policies are harder to audit.
  • Risk-adaptable access control (RAdAC): "a form of access control that uses an authorization policy that takes into account operational need, risk, and heuristics" (CNSSI 4009). Access is decided at the moment from identity, need and current risk, measured by factors such as "the strength of the authentication method" and location. Modern conditional access and zero trust policy engines work this way.

Spotting the model in a question. Owner decides: DAC. Labels and clearances: MAC. Job function: RBAC. Same rule for everyone (time, address): RuBAC. Combination of attributes and context: ABAC. Real-time risk and mission need, possibly overriding the usual policy: RAdAC.

Access policy enforcement

Objective 5.4Separating where access decisions are made from where they are enforced.

NIST's ABAC and zero trust architectures split authorization into components:

  1. Policy enforcement point (PEP)Intercepts the request at the resource (a gateway, proxy, application or API) and "enforces policy decisions".
  2. Policy decision point (PDP)"Computes access decisions" by evaluating the policy against the request; in SP 800-207 it is the policy engine plus the policy administrator.
  3. Policy information point (PIP)Supplies attributes and context: directory data, device posture, threat intelligence, location.
  4. Policy administration point (PAP)Where policies are written and managed.

Centralizing decisions in a PDP makes policy consistent, auditable and easy to change; distributing PEPs puts enforcement close to every resource. SP 800-207 grants access "on a per-session basis" with the least privilege needed. Policies themselves should be managed like code, with review, testing and version control.

At the retail group, the cloud IdP's conditional access engine acts as the PDP for SaaS (it allows store managers into the HR system only from managed devices and blocks sign-ins from unexpected countries), while an API gateway acts as the PEP for internal APIs, asking a central policy service for each decision.

Key takeaways

  • Federation: the IdP authenticates and signs an assertion; the RP trusts it; trust is set up in advance. Front vs back channel; FAL1-3 (FAL3 adds proof of an authenticator, holder-of-key).
  • Protocols: SAML 2.0 and OpenID Connect for federated sign-in; OAuth 2.0 for delegated API authorization (not authentication); SCIM for provisioning.
  • Deployment: on-premises (control, operating burden), cloud (less to run, provider dependence), hybrid (sync and federation servers are tier 0). Protect token-signing keys: Golden SAML and forged tokens bypass MFA.
  • Models: DAC (owner), MAC (labels, central), RBAC (roles), RuBAC (global rules), ABAC (attributes and environment), RAdAC (real-time risk and need).
  • Enforcement: PEP enforces, PDP decides, PIP informs, PAP manages policy; per-session, least-privilege decisions (SP 800-207).
