Overview

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. It runs an on-premises directory synchronized to a cloud identity provider, which federates to about 150 SaaS applications and to two logistics partners.

How federation works

Objective 5.3Understanding the parties, the assertion and the trust relationship that let one organization vouch for users at another.

  • Identity provider (IdP): "the party in a federation transaction that creates an assertion for the subscriber and transmits the assertion to the RP" (NIST SP 800-63-4). It authenticates the user.
  • Relying party (RP), or service provider: the application that "processes assertions from the IdP and provides the service that the subscriber is trying to access" (SP 800-63C-4). It never sees the password.
  • Assertion: "a verifiable statement about the subscriber account to the RP", signed by the IdP (and possibly encrypted), carrying the identity, attributes and details of the authentication event.
  • Trust: set up in advance by exchanging metadata and signing certificates, under an agreement on attributes, assurance and responsibilities.

An assertion reaches the RP through the front channel (redirects through the user's browser) or the back channel (the browser carries only a reference, and the RP fetches the assertion directly from the IdP, which keeps it away from the browser). NIST defines three federation assurance levels: FAL1 "a basic level of protection"; FAL2 "a high level of protection", which requires additional protections; and FAL3, where the RP must also verify that the user controls an authenticator, through a holder-of-key assertion or an authenticator bound to the RP, so a stolen assertion alone is useless.

Federation protocols

Objective 5.3Telling apart the protocols that authenticate users from the one that delegates authorization.

ProtocolPurposeTypical use
SAML 2.0 (OASIS)Authentication and attribute assertions in signed XMLEnterprise SSO to web applications and SaaS
OpenID Connect"A simple identity layer on top of the OAuth 2.0 protocol": ID tokens (JWTs) say who the user isModern web and mobile sign-in, consumer and workforce
OAuth 2.0 (RFC 6749)Delegated authorization: access tokens let an application call an API on the user's behalf; not authentication by itselfAPI access, "allow this app to read your calendar"
SCIM 2.0Provisioning: creating, updating and removing accounts across domainsKeeping SaaS accounts in step with the directory

OAuth's security best current practice (RFC 9700, 2025) drops the implicit and password grants and requires PKCE. Older options still seen: WS-Federation in some enterprise products, and Kerberos inside on-premises domains (covered on the 5.6 page).

OAuth is authorization, not authentication. An OAuth access token says what an application may do, not who the user is. If a question asks for user sign-in across organizations, the answer is SAML or OpenID Connect; if it asks for an application to access an API on a user's behalf, it is OAuth.

On-premises, cloud and hybrid

Objective 5.3Choosing where the identity provider runs, and protecting the signing keys that every federated service trusts.

  • On-premises: the organization runs its own directory and federation server. It keeps full control, but must patch, harden and make highly available the servers that every application depends on.
  • Cloud (identity as a service): a provider runs the IdP, with built-in MFA, conditional access and connectors to SaaS applications. Less to operate, but the organization depends on the provider's security and availability and must configure it well.
  • Hybrid: an on-premises directory synchronized with a cloud IdP, the most common enterprise case. Convenient, but it links the two: the synchronization servers and any on-premises federation server become tier-0 assets, because compromising them can mean compromising the cloud as well.

The signing key is the crown jewel. Anyone who holds an IdP's token-signing key can forge assertions for any user, bypassing passwords and MFA. CISA advisory AA21-008A (2021) described attackers forging tokens trusted by an on-premises identity provider, "often referred to as 'Golden Security Assertion Markup Language' attacks". In 2023, attackers "used a Microsoft account (MSA) consumer key to forge tokens to impersonate consumer and enterprise users" (CISA AA23-193A); the Cyber Safety Review Board found that intrusion "was preventable".

  • Keep signing keys in HSMs, rotate them, and restrict and monitor who can reach the federation and synchronization servers.
  • Treat identity infrastructure as tier 0: dedicated admin accounts and workstations, no internet browsing from them.
  • Correlate sign-ins at applications with authentication events at the IdP; tokens with no matching authentication suggest forgery.
  • With third parties, agree in the contract which attributes are shared, the assurance level, incident notification, and how access is removed when the relationship ends.

Running federation with third parties

Objective 5.3Setting up, operating and ending federation relationships safely.

  1. Agree the trustA written agreement on which attributes are shared, assurance levels (IAL, AAL, FAL), incident notification, liability, and how users are removed.
  2. Exchange metadata securelySigning certificates and endpoints exchanged through a verified channel; watch for metadata updates.
  3. Minimize attributesRelease only the claims each relying party needs; avoid sending more personal data than required.
  4. Map and authorizeMap federated identities to local roles; federation proves who someone is, not what they may do.
  5. MonitorLog federated sign-ins, alert on unusual patterns, and correlate with the identity provider's authentication logs.
  6. Rotate and reviewRotate signing keys on schedule, renew certificates before expiry, and review partners' access periodically.
  7. End cleanlyWhen the relationship ends, remove the trust, revoke tokens and accounts, and delete shared data.

Just-in-time provisioning (creating a local account at first federated sign-in) is convenient but leaves accounts behind when people leave the partner; combine it with SCIM deprovisioning or periodic cleanup. For customers, social or consumer identity providers can be accepted for low-risk services, with step-up for sensitive actions.

Federation patterns

Objective 5.3Recognizing the common ways federation is used across organizations and clouds.

  • Workforce to SaaS: the organization's identity provider federates to cloud applications, so staff sign in once and leavers lose access everywhere when disabled.
  • Business-to-business: partners sign in with their own identity provider (or as guest accounts) to shared applications; the agreement defines assurance and offboarding.
  • Customer identity: customers sign in with a local account or a social or consumer identity provider; step-up for sensitive actions, strong recovery, and privacy rules on attributes.
  • Workload identity federation: build pipelines and workloads in one environment obtain short-lived credentials in another (for example a CI/CD system deploying to a cloud account) by presenting a signed token, instead of storing long-lived keys.
  • Cross-cloud and hybrid: one identity provider trusted by several clouds and on-premises applications, with directory synchronization where needed.

Each pattern concentrates trust in a token issuer and its signing keys, so protecting the identity provider, limiting token lifetimes and validating tokens strictly (issuer, audience, signature, expiry) are common to all of them.

Federation risks and attacks

Objective 5.3Knowing how attackers abuse trust between identity providers and applications.

  • Identity provider compromise: control of the IdP gives access to every federated application, so it gets the strongest protection (objective 5.6).
  • Signing key theft: an attacker with the token-signing key can forge assertions for any user ("golden SAML"); keep keys in HSMs, rotate them, and monitor for tokens that the IdP never issued.
  • Malicious trust changes: adding a new federated domain or identity provider lets an attacker sign in as anyone; alert on any change to federation trusts.
  • Token theft and replay: session cookies and tokens stolen from browsers or by adversary-in-the-middle phishing bypass MFA; short lifetimes, token binding to devices, and conditional access reduce the window.
  • Consent phishing: users are tricked into granting a malicious OAuth app access to mail or files; restrict user consent and review app permissions.
  • Weak validation: applications that do not check signature, issuer, audience and expiry accept forged or misdirected tokens.

Provisioning and attributes in federation

Objective 5.3Getting the right accounts and claims to applications that trust the identity provider.

  • Just-in-time provisioning: the application creates an account the first time a federated user signs in, using attributes from the assertion. Simple, but accounts are not removed automatically when the user leaves.
  • SCIM provisioning: the identity provider creates, updates and deactivates accounts in the application through a standard API, so leavers lose access even if the application keeps local sessions.
  • Attribute release: send only the attributes each application needs (data minimization); a travel booking tool does not need salary grade.
  • Authoritative sources: attributes used for authorization (department, role, clearance) come from HR or a governed directory, not from user-editable profiles.
  • Mapping and testing: attribute names and values are mapped consistently between IdP and application, and changes are tested, since a mapping error can grant broad access.

At the retail group, every new SaaS application must support SAML or OIDC for sign-in and SCIM for provisioning before purchase; the few that lack SCIM are reconciled monthly against HR leaver lists.

OAuth 2.0 and OpenID Connect in detail

Objective 5.3The roles, tokens and flows behind modern delegated access and sign-in.

OAuth 2.0 (RFC 6749) is an authorization framework: it lets an application get limited access to a resource on a user's behalf without seeing the user's password. Its four roles:

  • Resource owner: the user who owns the data.
  • Client: the application that wants access.
  • Authorization server: authenticates the user, records consent and issues tokens.
  • Resource server: the API holding the data, which accepts access tokens.

The authorization code flow with PKCE (RFC 7636), now recommended for almost every client:

  1. RedirectThe client sends the user's browser to the authorization server with the requested scopes and a code challenge derived from a secret it generated.
  2. Authenticate and consentThe user signs in at the authorization server and approves the scopes.
  3. CodeThe authorization server redirects back to the client with a short-lived authorization code.
  4. ExchangeThe client sends the code and the original secret (code verifier) to the token endpoint; PKCE stops a stolen code being used by anyone else.
  5. UseThe client calls the resource server with the access token; it uses a refresh token to get new access tokens when they expire.
  • Scopes limit what the access token allows; access tokens are short-lived, refresh tokens longer-lived and must be protected.
  • Client credentials grant: machine-to-machine access with no user involved.
  • OpenID Connect adds authentication on top of OAuth: an ID token, a signed JSON Web Token (JWT) with claims such as issuer (iss), subject (sub), audience (aud) and expiry (exp), plus a UserInfo endpoint for profile attributes.

OAuth is not authentication. An OAuth access token says what a client may do, not who the user is. Signing users in with plain OAuth is a known mistake; OpenID Connect is the authentication layer.

SAML flows and federation trust

Objective 5.3How SAML sign-in works, and how trust between organizations is structured.

SAML 2.0 has three parties: the principal (the user), the identity provider (IdP) and the service provider (SP). Assertions are XML documents signed by the IdP and carry three kinds of statements: authentication (who signed in, when and how), attribute (details such as email or role) and authorization decision (whether access is allowed, rarely used).

  • SP-initiated: the user goes to the application, which redirects them to the IdP with an authentication request; the IdP returns a signed assertion, usually through the browser (HTTP POST binding).
  • IdP-initiated: the user starts at the IdP portal and picks the application; there is no request to match, which makes it more exposed to injected or replayed assertions.
  • Validation: the SP must check the signature, issuer, audience, recipient and validity times, and reject reused assertions.

Trust models: in a direct (mesh) model each pair of organizations configures trust with each other; in a hub-and-spoke model a federation operator or broker connects many members, as in academic federations using Shibboleth. Trust is not transitive unless the agreement says so: trusting a partner does not mean trusting everyone that partner trusts. Identity as a service (IDaaS) providers often act as the hub for an organization's cloud applications.

Scenario check

PracticeApplying the objective to situations like those in exam questions.

Scenario 1: the partner's leavers
Situation
A logistics partner's employees sign in through federation. One left the partner months ago but still appears in the retailer's app.
Best response
Rely on the partner's identity provider for authentication (it should block the leaver), remove stale local accounts, and add SCIM or periodic reconciliation.
Why
Federation shifts authentication to the partner, but locally provisioned accounts still need lifecycle management.
Scenario 2: the expiring certificate
Situation
Federated sign-in to 150 SaaS apps fails one morning: the identity provider's signing certificate expired.
Best response
Restore with a new certificate, update relying parties, and add certificate expiry to monitoring with renewal well ahead of time.
Why
Federation creates a single dependency; key and certificate management keeps it available.
Scenario 3: OAuth for sign-in
Situation
Developers plan to "log users in" by accepting any valid OAuth access token sent to the API.
Best response
Use OpenID Connect ID tokens for authentication and validate audience, issuer and signature; use access tokens only for authorization to the API they were issued for.
Why
OAuth is authorization, not authentication; accepting arbitrary access tokens enables token misuse.
Scenario 4: the federation server breach
Situation
An attacker gains administrator access to the on-premises federation server.
Best response
Treat it as a tier-0 compromise: rotate token-signing keys and certificates, revoke sessions, investigate forged token use in cloud logs, and rebuild the server.
Why
Stolen signing keys let attackers forge tokens for any user (Golden SAML).
Scenario 5: the new federated domain
Situation
Alerts show that a new external identity provider was added as trusted for the company's cloud tenant late at night by an administrator account.
Best response
Treat it as a likely compromise: remove the trust, revoke sessions and tokens, investigate the administrator account, and review sign-ins made through the new trust.
Why
Changes to federation trust let attackers sign in as anyone; they must be monitored and treated as high risk.

Key takeaways

  • Federation: the IdP authenticates and signs an assertion; the RP trusts it; front vs back channel; FAL1-3 (FAL3 adds proof of an authenticator).
  • Protocols: SAML 2.0 and OpenID Connect for federated sign-in; OAuth 2.0 for delegated API authorization (not authentication); SCIM for provisioning.
  • Deployment: on-premises, cloud, hybrid (sync and federation servers are tier 0); protect token-signing keys against forgery.
  • Running federation: agreements, verified metadata, minimal attributes, local authorization, monitoring, key rotation, clean exit; clean up just-in-time accounts.
