8.1: Integrating security in the software development life cycle

Building security into how software is planned, built and run, whatever the methodology, and measuring how mature that practice is.

Overview

Objective 8.1

8.1 Understand and integrate security in the Software Development Life Cycle (SDLC). Sub-topics: development methodologies (Agile, Waterfall, DevOps, DevSecOps, Scaled Agile Framework); maturity models (CMM, SAMM); operation and maintenance; change management; integrated product team; SSDF and SBOM requirements; shift left.

The system life cycle is on the 3.10 page; SBOMs and supply chain risk on the 1.11 page; the development toolchain on the 8.2 page. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. Its 250 developers in 30 teams ship the e-commerce site and mobile app several times a day, while the till software is released quarterly.

Development methodologies

Objective 8.1Fitting security activities into the way each methodology plans, builds and releases software.

  • Waterfall: sequential phases (requirements, design, build, test, deploy) with sign-off between them. Security fits into phase gates (requirements review, design review, security testing before release), but late findings are expensive to fix. Suits stable requirements and regulated systems, like the till software.
  • Agile: short iterations (sprints) delivering working software, with changing requirements. Security becomes part of the backlog: security user stories and abuse cases, a definition of done that includes security checks, and threat modeling for significant changes rather than one big design review.
  • Scaled Agile Framework (SAFe): coordinates many Agile teams on shared planning increments and release trains; security requirements and architecture are set at the program level so teams do not each reinvent them.
  • DevOps: development and operations share responsibility for building, deploying and running software, with heavy automation and frequent releases.
  • DevSecOps: security is built into DevOps as automated pipeline checks and shared responsibility, rather than a separate gate at the end: security teams provide tools, guardrails and guidance; developers fix what the tools find.

Older models still appear in questions: the spiral model iterates with explicit risk analysis in each cycle; prototyping and rapid application development build quick versions to refine requirements, where the risk is a prototype going into production without security work.

Maturity models

Objective 8.1Measuring how mature an organization's development and software security practices are, and planning improvement.

  • Capability Maturity Model (CMM, now CMMI): maturity levels from Initial ("unpredictable and reactive") through Managed, Defined, Quantitatively Managed, to Optimizing (continuous improvement); the current CMMI also defines a level 0, Incomplete. Higher levels mean repeatable, measured, improving processes, which make security activities consistent.
  • Software Assurance Maturity Model (OWASP SAMM): an open model specifically for software security, organized into five business functions (Governance, Design, Implementation, Verification, Operations), each with security practices scored on maturity levels. Organizations assess where they are and set targets per practice.

The retail group assessed itself with SAMM: strong on implementation (pipeline scanning), weak on design (little threat modeling); it set a one-year target to bring design up one level.

SSDF, SBOM and shift left

Objective 8.1Using the NIST Secure Software Development Framework and SBOMs, and finding problems as early as possible.

The Secure Software Development Framework (SSDF, NIST SP 800-218 v1.1, 2022; a Rev. 1 draft, v1.2, was published in December 2025) is a set of practices that fit into any SDLC, in four groups:

  • Prepare the Organization (PO): roles, training, security requirements, toolchains and secure environments.
  • Protect the Software (PS): protect code from tampering, provide ways to verify releases, archive each release.
  • Produce Well-Secured Software (PW): secure design, threat modeling, reuse of secure components, secure coding, code review (PW.7) and testing executable code (PW.8), secure default settings.
  • Respond to Vulnerabilities (RV): identify, analyze and fix vulnerabilities, and find their root causes.

SBOM requirements: an SBOM lists the components in a piece of software. CISA's 2026 Minimum Elements (July 2026) updated and replaced the 2021 NTIA baseline, and a separate minimum elements guide for AI SBOMs followed. In the US federal space, OMB M-26-05 (January 2026) rescinded the earlier mandatory self-attestation memos (M-22-18, M-23-16) and made attestations and SBOMs part of a risk-based approach that agencies may choose to use, so contracts, regulators and customers now drive SBOM requirements.

Shift left means moving security earlier in the life cycle: security requirements and threat modeling at design, checks in the IDE and on every commit, rather than a penetration test just before release. Fixing a flaw in design costs far less than fixing it in production. It complements rather than replaces testing and monitoring later on ("shift everywhere").

Security belongs in every phase. When a question asks when security should be considered in development, the answer is from the beginning (requirements and design), and throughout, not at testing or deployment.

Teams, operations and change

Objective 8.1Organizing people and processes so security continues after release and through every change.

  • Integrated product team (IPT): a cross-functional team (developers, testers, operations, security, business owner, sometimes legal or privacy) responsible together for a product, so security decisions are made with the people who build and own it. Security champions inside teams play a similar role.
  • Operation and maintenance: most of a system's life is after release. Monitor it, patch it and its dependencies, respond to vulnerability reports, review security as threats change, and plan end of life.
  • Change management: every change to code, configuration or infrastructure is requested, reviewed, tested, approved and recorded (objective 7.9); in DevSecOps much of this is enforced by the pipeline (pull request reviews, automated gates), with separation of duties so no one can push unreviewed code to production alone.

Security activities in each phase

Objective 8.1Knowing what security work belongs where, whatever the methodology calls the phases.

  • Requirements: security and privacy requirements from risk assessment, data classification, laws and contracts (for example "card data never stored", "MFA for all admin functions"); abuse cases alongside use cases.
  • Design: threat modeling (such as STRIDE), secure architecture patterns, choice of frameworks and components, and a design review for significant features.
  • Build: secure coding standards, IDE checks, peer code review, SAST and dependency scanning on each change (objective 8.5).
  • Test: security test cases from requirements and abuse cases, DAST, fuzzing and penetration testing for high-risk features (objective 6.2).
  • Release: final security sign-off by risk, secure default configuration, signed artifacts and an SBOM, and release notes that cover security fixes.
  • Operate and maintain: monitoring, patching, vulnerability intake and response, periodic reassessment.
  • Retire: decommission securely, migrate or dispose of data, revoke credentials and remove integrations.

In Agile and DevOps, these activities happen continuously and in small pieces rather than once per phase, but none of them disappears. The system-level life cycle around software is on the 3.10 page.

Security champions and developer enablement

Objective 8.1Scaling security across many development teams without a security engineer in every one.

  • Security champions: developers in each team with extra training and time to act as the first point of contact for security, run threat modeling sessions and help triage findings.
  • Training: role-based secure coding training tied to the weaknesses actually found in the organization's code, rather than generic annual courses.
  • Paved roads: approved frameworks, templates, libraries and pipeline configurations that are secure by default, so the easy path is the secure path.
  • Clear guidance: short, practical standards and examples rather than long policy documents.
  • Feedback: findings delivered in the tools developers already use, with fix advice and low false positive rates, so they are trusted and acted on.

At the retail group, 30 champions (one per team) meet monthly with the application security team; after a year, the time to fix critical findings fell from 40 days to 9.

Writing good security requirements

Objective 8.1Turning risk and policy into requirements developers can build and testers can verify.

  • Specific and testable: "lock the account for 15 minutes after 10 failed attempts" rather than "protect against brute force".
  • From known sources: data classification, laws and contracts (PCI DSS for card data, privacy law for personal data), the threat model, and standards such as OWASP ASVS.
  • Functional and non-functional: features such as MFA and audit logs, and qualities such as encryption, availability and performance under attack.
  • Abuse cases: what an attacker or malicious insider might try, written as stories with acceptance criteria.
  • Traceable: each requirement links to tests, so release decisions can show which ones are met.

Security in AI development

Objective 8.1Extending the life cycle to models and the data they learn from.

  • Data: provenance, quality and permission to use training and fine-tuning data; protection against poisoning.
  • Design: threat modeling that covers prompt injection, data leakage, model misuse and the tools the model can call.
  • Evaluation: tests for accuracy, bias, safety and security before release and after every model or prompt change.
  • Release and operation: versioned models and prompts under change control, monitoring of behavior in production, and a way to roll back.

NIST has published a community profile of the SSDF for generative AI and dual-use foundation models (SP 800-218A), which adds AI-specific practices to the same four practice groups.

Scenario check

PracticeApplying the objective to situations like those in exam questions.

Scenario 1: security at the end
Situation
A project plans a penetration test two weeks before go-live as its only security activity.
Best response
Add security requirements and threat modeling at design, code review and automated testing during build, and keep the penetration test as a final check.
Why
Security belongs in every phase; late findings are expensive and often accepted rather than fixed.
Scenario 2: the prototype in production
Situation
A quick prototype built to show the business an idea is now being used by customers.
Best response
Treat it as a new system: assess it, add the missing security controls or rebuild it through the normal life cycle before wider use.
Why
Prototypes skip security work; they must not become production by default.
Scenario 3: maturity targets
Situation
Leadership asks how mature software security is and where to invest.
Best response
Assess against a maturity model such as OWASP SAMM, set target levels per practice by risk, and track progress.
Why
Maturity models give a structured baseline and improvement plan.
Scenario 4: the customer asks for an SBOM
Situation
A large customer requires an SBOM and evidence of secure development practices for the mobile app.
Best response
Generate SBOMs in the build pipeline for each release, and map development practices to the SSDF as evidence.
Why
SBOM and SSDF requirements are increasingly set by customers and contracts.
Scenario 5: the vague requirement
Situation
A requirement says "the app must be secure", and testers do not know what to test.
Best response
Replace it with specific, testable requirements derived from the data classification, regulations, threat model and ASVS.
Why
Requirements must be verifiable to be built and tested.

Key takeaways

  • Methodologies: Waterfall (security gates per phase), Agile (security stories, abuse cases, definition of done), SAFe (program-level security), DevOps and DevSecOps (automated checks, shared responsibility); spiral includes risk analysis.
  • Maturity: CMMI levels (Initial to Optimizing); OWASP SAMM for software security (Governance, Design, Implementation, Verification, Operations).
  • SSDF (SP 800-218; Rev. 1 draft Dec 2025): Prepare the Organization, Protect the Software, Produce Well-Secured Software, Respond to Vulnerabilities. SBOMs: CISA 2026 Minimum Elements; M-26-05 made federal attestation risk-based. Shift left: security from requirements onward.
  • People and process: integrated product teams, security champions, operations and maintenance, change management with separation of duties.
  • Phases: requirements and abuse cases, threat modeling, secure build, security testing, release sign-off with SBOM, operation, secure retirement. Enablement: champions, targeted training, paved roads, findings in developer tools.
