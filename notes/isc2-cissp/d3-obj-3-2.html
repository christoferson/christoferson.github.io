Overview

Objective 3.2

3.2 Understand the fundamental concepts of security models (e.g., Biba, Star, Bell-LaPadula).

The outline's "Star" is not a separate model: it refers to the star (*) properties of Bell-LaPadula and Biba (our reading; ISC2 does not define it). Access control models such as DAC, MAC and RBAC are on the 5.3–5.4 page; the reference monitor that enforces a model on the 3.3–3.4 page. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. Its finance systems, consultancy arm and payment platform each illustrate a different model.

What security models are

Objective 3.2Understanding why formal models exist and the general types they fall into.

A security model is a precise, often mathematical, statement of a security policy that a system can be built and checked against. Policy says what should happen ("staff may not read above their clearance"); the model makes it exact enough to prove that a design enforces it; the implementation (a reference monitor, an operating system, an application) makes it happen. Common types:

  • State machine models: the system is secure if it starts in a secure state and every allowed transition leads to another secure state. Bell-LaPadula is one.
  • Information flow models: control how information moves between security classes, so it cannot flow in forbidden directions. Bell-LaPadula and Biba are both.
  • Lattice models (Denning, 1976): security labels form a lattice with a least upper bound and greatest lower bound for any two labels; information may flow only upward in dominance.
  • Noninterference (Goguen and Meseguer, 1982): actions at a high level must have no visible effect on what a low-level user sees. Stricter than Bell-LaPadula, it addresses covert channels.
  • Access matrix models: subjects as rows, objects as columns, rights in cells (Graham-Denning, HRU, Take-Grant).

Confidentiality: Bell-LaPadula

Objective 3.2Knowing the rules that keep classified information from flowing down.

Bell-LaPadula (Bell and LaPadula, MITRE, 1973) formalized US military multilevel security. Subjects have clearances, objects have classifications, and the model has these properties:

  • Simple security property: "no read up". A subject may read an object only at or below its own level.
  • Star (*) property: "no write down". A subject may write only at or above its own level, so it cannot leak high information into a lower object (for example by copying secret text into an unclassified file). Trusted subjects may be exempted to perform authorized downgrading.
  • Strong star property: read and write only at the subject's own level.
  • Discretionary security property: an access matrix also applies, so need-to-know limits access within a level.
  • Tranquility: strong tranquility means security levels never change during operation; weak tranquility allows changes only when they do not violate the policy.

Bell-LaPadula protects confidentiality only. It says nothing about integrity: a low-level user may write up into a high-level file, possibly corrupting it, which is why integrity models exist.

Read the arrows carefully. Bell-LaPadula: no read up, no write down ("write up, read down" is allowed). Biba is the mirror image: no read down, no write up. A quick check: confidentiality models stop secrets flowing down; integrity models stop dirty data flowing up.

Integrity: Biba and Clark-Wilson

Objective 3.2Knowing how integrity models prevent untrusted data and users from corrupting trusted data.

Biba (Kenneth Biba, MITRE, commonly dated 1977) uses integrity levels instead of clearances:

  • Simple integrity property: "no read down". A subject should not read lower-integrity data, which could contaminate its decisions.
  • Star (*) integrity property: "no write up". A subject may not write to higher-integrity objects.
  • Invocation property: a subject may not invoke (call on) a subject at a higher integrity level.

Clark-Wilson (Clark and Wilson, 1987) was designed for commercial integrity, where the concern is fraud and error rather than classification:

  • Constrained data items (CDIs) are the protected data, such as account balances; unconstrained data items (UDIs) are inputs not yet validated.
  • Transformation procedures (TPs) are well-formed transactions, the only way to change CDIs, moving them from one valid state to another.
  • Integrity verification procedures (IVPs) check that CDIs are valid.
  • The access triple (user, TP, CDIs): users never access data directly, only through approved programs.
  • Separation of duties: the person who certifies a TP is not the one who runs it; the model has certification and enforcement rules.

At the retail group, staff never edit the ledger tables directly; they post journals through the finance application (TPs), nightly reconciliation checks the ledger (IVP), and the person who approves a new journal type cannot post with it: Clark-Wilson in practice.

Other models

Objective 3.2Recognizing the remaining classic models and the problem each addresses.

  • Brewer-Nash (Chinese wall, 1989): data is grouped into company data sets inside conflict-of-interest classes. Access is dynamic: once a consultant has read one bank's data, the model blocks access to other banks in the same class, but not to unrelated industries. Used for consultancies, auditors and investment banks.
  • Graham-Denning: eight protection rules over an access matrix: create object, create subject, delete object, delete subject, read access right, grant access right, delete access right, transfer access right; each object has an owner and each subject a controller. It addresses how rights are securely created and passed on.
  • Harrison-Ruzzo-Ullman (HRU, 1976): defines commands from primitive operations on an access matrix and studies the safety problem: can a right leak to an unauthorized subject? It showed the problem is undecidable in general, though decidable for simple (mono-operational) commands.
  • Take-Grant (Lipton and Snyder, 1977): represents subjects and objects as a graph with take, grant, create and remove rules; for this model, whether a right can be obtained is decidable efficiently.

Questions usually give a scenario and ask which model fits: conflicts of interest (Brewer-Nash), commercial transactions and separation of duties (Clark-Wilson), military classification (Bell-LaPadula), preventing contamination of trusted data (Biba), how rights are granted and transferred (Graham-Denning or Take-Grant).

Models in real systems

Objective 3.2Connecting abstract models to the mechanisms that enforce them.

  • Mandatory access control systems implement Bell-LaPadula-style labels and rules in the operating system or database, so users cannot override them (multilevel secure systems for government; label-based database security).
  • Integrity levels in operating systems: some operating systems mark processes and objects with integrity levels so that a low-integrity process, such as a browser handling untrusted content, cannot write to higher-integrity system areas, a Biba-like idea.
  • Business applications enforce Clark-Wilson ideas: data changes only through validated transactions, approval workflows and reconciliations.
  • Information barriers in financial and professional services implement Brewer-Nash with dynamic access rules and monitoring.
  • The reference monitor is the mechanism that enforces a model: tamperproof, always invoked and small enough to verify (objective 3.4).

Models also explain the limits of real systems: covert channels (timing or storage channels that leak information despite access rules) are what noninterference tries to rule out, and HRU shows that proving a general system can never leak a right is not always possible, which is why simple, analyzable designs are preferred.

Comparing models and common traps

Objective 3.2Telling similar models apart and avoiding the mistakes exam questions are built on.

  • Confidentiality or integrity? Bell-LaPadula and Brewer-Nash protect confidentiality (Brewer-Nash against conflicts of interest); Biba and Clark-Wilson protect integrity. If a question is about preventing leaks, think Bell-LaPadula; if about preventing corruption or fraud, Biba or Clark-Wilson.
  • Lattice or rules? Bell-LaPadula and Biba are lattice-based, using fixed levels; Clark-Wilson uses programs and separation of duties instead of levels; Brewer-Nash changes access based on history.
  • Military or commercial? Bell-LaPadula came from military classification; Clark-Wilson from commercial accounting practice; Brewer-Nash from financial services.
  • Analysis models: HRU and Take-Grant are about proving what can happen to rights, not about running a system day to day; Graham-Denning is about the operations for managing rights securely.
  • Star properties differ: Bell-LaPadula's star property stops writing down; Biba's star integrity property stops writing up. Both are called "star", which is why the outline lists "Star".
  • Neither BLP nor Biba covers availability, and neither stops covert channels on its own.

A useful habit is to restate the scenario as a flow: who is reading or writing, at which level, and which direction is forbidden. Most model questions answer themselves once the direction of the flow is clear.

Scenario check

PracticeMatching scenarios to models, as exam questions do.

Scenario 1: the consultancy
Situation
The retail group's consultancy arm advises two competing grocery chains. A consultant who worked on one chain's pricing must be prevented from accessing the other's files.
Best answer
Brewer-Nash (Chinese wall): access depends on what the consultant has already accessed within the conflict-of-interest class.
Why
The rule is dynamic and based on conflicts of interest, not fixed levels.
Scenario 2: the classified copy
Situation
In a multilevel system, a user cleared for Secret tries to save text from a Secret document into an Unclassified file.
Best answer
Blocked by the Bell-LaPadula star property: no write down.
Why
Writing to a lower level could leak classified information; the simple security property would separately stop reading up.
Scenario 3: the untrusted feed
Situation
A pricing engine that sets shelf prices reads competitor price feeds scraped from the web without validation.
Best answer
Biba's simple integrity property (no read down) warns against high-integrity processes consuming low-integrity data; validate and sanitize the feed before use.
Why
Integrity models stop untrusted data from contaminating trusted processes and decisions.
Scenario 4: the ledger edits
Situation
Finance analysts have direct write access to ledger database tables "for quick fixes".
Best response
Remove direct access; allow changes only through the finance application's validated transactions, with reconciliation and separation of duties.
Why
Clark-Wilson: users change constrained data only through well-formed transactions, never directly.

Key takeaways

  • Models state policy precisely: state machine, information flow, lattice, noninterference, access matrix.
  • Bell-LaPadula (confidentiality): no read up (simple security), no write down (star), strong star, discretionary property, tranquility. "Star" in the outline means these star properties.
  • Biba (integrity): no read down, no write up, invocation property. Clark-Wilson (commercial integrity): CDIs, UDIs, TPs, IVPs, access triple, separation of duties.
  • Brewer-Nash: dynamic conflict-of-interest walls. Graham-Denning: eight rules for rights. HRU: rights leakage undecidable in general. Take-Grant: graph rules, decidable.
  • In practice: MAC labels, OS integrity levels, transaction-only business apps, information barriers; enforced by a reference monitor; covert channels are the limit models try to close.
