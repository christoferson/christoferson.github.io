Overview

Objective 8.5

8.5 Define and apply secure coding guidelines and standards. Sub-topics: security weaknesses and vulnerabilities at the source-code level; security of APIs; secure coding practices.

Code testing techniques are on the 6.2 page; the pipeline that enforces standards on the 8.2 page. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. It exposes public APIs to delivery partners, and its developers follow an internal coding standard based on OWASP ASVS.

Source-code weaknesses

Objective 8.5Recognizing the common weakness types in code and how each is prevented.

The OWASP Top 10:2025 ranks the most critical web application risks: A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions. MITRE's CWE (Common Weakness Enumeration) catalogs weakness types in detail, with a yearly list of the most dangerous. Key weaknesses and their fixes:

  • Injection (SQL, command, LDAP): untrusted input treated as code. Fix: parameterized queries, safe APIs, input validation.
  • Cross-site scripting (XSS): untrusted data sent to the browser as script. Fix: context-aware output encoding, content security policy.
  • Broken access control: missing checks that the user may access this object or function (including insecure direct object references). Fix: deny by default, server-side checks on every request.
  • Memory safety errors (buffer overflows, use-after-free) in C and C++. Fix: memory-safe languages, bounds checking, compiler protections.
  • Race conditions (time-of-check to time-of-use): the state changes between a check and its use. Fix: atomic operations and locking.
  • Insecure deserialization, server-side request forgery (SSRF), cross-site request forgery (CSRF), hard-coded secrets, weak cryptography, and verbose error messages that reveal internals.
  • Backdoors and logic bombs: deliberately hidden code; code review, separation of duties and change auditing are the defenses.

Vulnerabilities in released products receive CVE identifiers; NIST's NVD changed its operations in April 2026 to prioritize enrichment for KEV-listed and federal software, so do not rely on every CVE having a NIST score.

API security

Objective 8.5Designing and running APIs so every call is authenticated, authorized, validated and limited.

APIs expose application logic directly, often without a user interface to slow attackers down. The OWASP API Security Top 10 is led by broken object-level authorization (a user changes an ID in the request to read someone else's record), broken authentication, broken object property-level authorization, unrestricted resource consumption and broken function-level authorization. Controls:

  • Authentication: OAuth 2.0 access tokens or mutual TLS for partners; never API keys alone for sensitive data; short-lived tokens, validated on every call.
  • Authorization on every object and function: check that this caller may access this specific record and operation, server side.
  • Input and output: validate requests against a schema; return only the fields the caller needs (no "return the whole object").
  • Rate limiting and quotas: protect against abuse, scraping and denial of service.
  • Inventory: know every API and version, including old and test versions; retire unused ones.
  • Gateway and monitoring: an API gateway to enforce authentication, rate limits and logging centrally; alerts on unusual call patterns.

The retail group's partner API issues each delivery partner a client certificate and short-lived tokens limited to its own deliveries, and the gateway blocks any request for an order that does not belong to the caller.

Secure coding practices and standards

Objective 8.5Setting coding standards and practices that make secure code the default.

  • Input validation: validate all input on the server, by allowlist (type, length, format, range), as close as possible to where it enters.
  • Output encoding for the context (HTML, JavaScript, SQL, shell).
  • Authentication and session management through proven frameworks, not custom code.
  • Least privilege for the application's own accounts and permissions.
  • Error handling and logging: fail securely, show generic errors to users, log details (but not secrets or personal data) for investigators; handle exceptional conditions explicitly.
  • Cryptography from vetted libraries with approved algorithms; no home-made crypto; secrets from a secrets manager, never in code.
  • Secure defaults and minimal attack surface: features off unless needed, no default passwords (a CISA Secure by Design principle).
  • Dependencies kept current and scanned.

Standards make this measurable: the OWASP Application Security Verification Standard (ASVS 5.0, May 2025) defines verification requirements at three levels; language-specific secure coding standards set rules for each language; and an organization's own coding standard picks the rules, frameworks and tools developers must use. Enforce them through training, code review checklists, linters and SAST rules in the pipeline.

Frameworks over willpower. Safe defaults in frameworks (parameterized queries, auto-escaping templates, built-in CSRF protection) prevent more flaws than asking every developer to remember every rule. Standardize on them and block unsafe patterns automatically.

Secure code review

Objective 8.5Reviewing code so that people catch what tools miss.

  • Focus on risk: authentication, authorization, input handling, cryptography, payment and personal data paths, and changes to security controls deserve the closest review.
  • Checklists: short, language-specific checklists drawn from the coding standard and past findings.
  • Tools first: SAST, linters and secret scanners run before human review, so reviewers spend time on logic and design flaws, which tools find poorly.
  • Business logic: reviewers ask whether the code enforces rules correctly (who may refund, what prices are allowed), the kind of flaw no scanner understands.
  • Independence: the author does not approve their own change; high-risk code gets a second reviewer with security knowledge.
  • Feedback: recurring review comments become new linter rules, framework defaults or training topics.

Handling errors and exceptional conditions

Objective 8.5Writing code that stays secure when things go wrong.

Mishandling of exceptional conditions is new in the OWASP Top 10:2025 (A10). Code is often secure on the expected path and insecure when something unexpected happens:

  • Fail closed: if an authorization check, signature check or external service fails, deny the action rather than allow it.
  • Catch and handle errors deliberately, at the right level; do not swallow exceptions silently or let them crash services in ways attackers can trigger repeatedly.
  • Consistent state: transactions that fail halfway are rolled back, so partial updates cannot be exploited (for example, an order marked paid when the payment failed).
  • Resource limits: timeouts, size limits and rate limits stop unusual inputs from exhausting memory or connections.
  • Safe messages: users see generic errors; detailed errors go to logs without secrets or personal data.
  • Test the unhappy paths: fuzzing, negative tests and fault injection exercise error handling as deliberately as normal behavior.

Building and maintaining a coding standard

Objective 8.5Turning guidance into rules that developers can follow and tools can check.

  1. Start from a recognized sourceOWASP ASVS for web applications and APIs, language-specific secure coding standards, and vendor guidance for platforms.
  2. Choose a level by riskASVS levels let the organization require more verification for applications handling payments or sensitive data.
  3. Make it specificName approved frameworks, libraries and patterns (for authentication, queries, templates, cryptography), and list banned functions and patterns.
  4. Automate checksTurn rules into linter and SAST rules, pipeline gates and code review checklists.
  5. Train and supportShort training on the standard, examples, and security champions to answer questions.
  6. Review regularlyUpdate the standard when frameworks, threats or findings change, with a version history and an exceptions process.

A standard nobody reads does not change code; one that is built into templates, tools and reviews changes it every day.

Secure coding for AI features

Objective 8.5Handling the new weaknesses that come with building on large language models.

OWASP also maintains a Top 10 for LLM applications. Key coding practices:

  • Prompt injection: treat all content the model reads (user input, documents, web pages, tool results) as untrusted; never let model output alone authorize sensitive actions.
  • Output handling: validate and encode model output before using it in queries, commands, HTML or code, exactly as with any untrusted input.
  • Least privilege for tools: give the model access only to the functions and data the feature needs, with the user's own permissions.
  • Sensitive data: keep secrets and unnecessary personal data out of prompts and system instructions; filter outputs for leakage.
  • Limits: rate limits, size limits and cost controls against abuse and denial of service.
  • Logging and evaluation: log prompts and actions for investigation (respecting privacy), and test with adversarial inputs before release.

Memory safety in practice

Objective 8.5Reducing memory safety bugs in existing and new code.

  • New code in memory-safe languages wherever practical, especially for components that parse untrusted input.
  • Hardening existing C and C++: compiler and linker protections, safer library functions, bounds-checked containers, and sanitizers in testing.
  • Fuzzing: continuous fuzzing of parsers and network-facing code finds memory errors that review misses.
  • Roadmaps: CISA and partner agencies encourage manufacturers to publish memory safety roadmaps showing how they will reduce memory-unsafe code over time.

Scenario check

PracticeApplying the objective to situations like those in exam questions.

Scenario 1: the changed ID
Situation
A customer changes the order number in an API request and sees another customer's order.
Best response
Add server-side object-level authorization on every request, and add automated tests that try to access other users' records.
Why
Broken object-level authorization is the top API risk; checks must happen on the server for every object.
Scenario 2: the string-built query
Situation
A code review finds SQL queries built by joining user input into strings.
Best response
Rewrite them with parameterized queries, add a SAST rule to block the pattern, and check for similar code elsewhere.
Why
Parameterized queries prevent injection; tools stop the pattern returning.
Scenario 3: the stack trace
Situation
The online store shows full error messages with stack traces and database names when something fails.
Best response
Show generic errors to users, log details securely, and fail safely.
Why
Verbose errors reveal internals to attackers.
Scenario 4: the home-made encryption
Situation
A developer wrote a custom encryption routine to protect loyalty card numbers.
Best response
Replace it with a vetted library using approved algorithms, with keys from the key management system.
Why
Never write your own cryptography; use vetted libraries and managed keys.
Scenario 5: the assistant that ran a query
Situation
An AI feature turns user questions into database queries and runs them with an administrator account.
Best response
Run queries with the user's own permissions and a restricted read-only role, validate generated queries, and block dangerous operations.
Why
Model output is untrusted input, and AI tools need least privilege.

Key takeaways

  • Weaknesses: OWASP Top 10:2025 (A01 Broken Access Control to A10 Mishandling of Exceptional Conditions); CWE; injection, XSS, access control, memory safety, race conditions, SSRF, CSRF, deserialization, hard-coded secrets, backdoors.
  • APIs: object- and function-level authorization on every call, strong authentication, schema validation, minimal responses, rate limits, inventory, gateways and monitoring.
  • Practices and standards: validate input, encode output, proven frameworks, least privilege, fail securely, vetted crypto, secure defaults, current dependencies; ASVS 5.0 and coding standards enforced by review and tools.
  • Code review: focus on risky code, checklists, tools first, business logic, independent approval, feedback into rules and training.
  • Errors: fail closed, handle exceptions deliberately, roll back partial transactions, resource limits, generic messages, test unhappy paths.
