Overview

Objectives 3.3 and 3.4

3.3 Select controls based upon systems security requirements. 3.4 Understand security capabilities of information systems (e.g., memory protection, Trusted Platform Module (TPM), Hardware Security Module (HSM), encryption/decryption).

Control baselines and tailoring are on the 2.4–2.6 page, and roots of trust on the 1.11–1.12 page. This page covers how requirements become control and product choices, and the built-in capabilities of hardware and operating systems that those controls rely on. Cryptographic algorithms are covered under objective 3.6. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. It is buying hardware security modules and a new firewall for the payment platform.

Selecting controls from requirements

Objective 3.3Deriving controls from a system's security requirements and writing them into design and purchasing decisions.

Controls should trace back to requirements, so every control has a reason and every requirement is met. Requirements come from the system's security categorization and risk assessment, from laws, regulations and contracts (PCI DSS for the payment platform), from the organization's policies and standards, and from the threat model. The usual path:

  1. Define requirementsFunctional (what security features must do) and assurance (how much confidence is needed that they work).
  2. Start from a baselineSelect the baseline that matches the system's impact level and tailor it (objective 2.6).
  3. AllocateDecide which component, team or provider implements each control, including inherited and common controls.
  4. Choose productsPrefer products whose security has been independently evaluated, and write the requirements into the purchase.
  5. VerifyTest and assess that the controls meet the requirements before go-live (Domain 6).

For purchases, SP 800-53 control SA-4 Acquisition Process requires contracts to include, explicitly or by reference, security and privacy functional requirements, strength of mechanism, assurance requirements, the controls needed, documentation requirements and its protection, a description of the development and operating environment, allocation of responsibilities, and acceptance criteria. The retail group's tender for HSMs requires FIPS 140-3 validation at the security level its PCI requirements call for, vendor patch support for the life of the contract, and documentation of every administrative interface.

Product assurance: Common Criteria and FIPS 140-3

Objective 3.3Using independent evaluations to judge how much a product's security claims can be trusted.

Common Criteria (published as ISO/IEC 15408) is the international framework for evaluating IT products. The current version is CC:2022, which replaced CC 3.1 Release 5. Its vocabulary:

  • Target of evaluation (TOE): the product or system being evaluated.
  • Protection profile (PP): a set of security requirements for a class of products, such as firewalls or mobile devices, usually written by a user community.
  • Security target (ST): the vendor's statement of the TOE's security properties, which may claim conformance to a protection profile.
  • Evaluation assurance levels (EAL1 to EAL7): how deeply the product was evaluated, commonly listed as functionally tested, structurally tested, methodically tested and checked, methodically designed, tested and reviewed, semi-formally designed and tested, semi-formally verified design and tested, and formally verified design and tested.

Under the Common Criteria Recognition Arrangement (CCRA), 36 member nations accept certificates issued by the others, so a certified product can be bought without being re-evaluated. Recognition is generally limited to evaluations against collaborative protection profiles or the lower EALs, and the US scheme (NIAP) is described as accepting only protection-profile-based evaluations.

An EAL measures evaluation depth, not security. A product at EAL4 has been examined more thoroughly than one at EAL2, but only against its own security target: check that the evaluated configuration and claims match how you will use it.

FIPS 140-3 (effective September 2019, built on ISO/IEC 19790) is the US and Canadian standard for cryptographic modules, validated under NIST's Cryptographic Module Validation Program (CMVP). It has four security levels, which rise from correct algorithms and basic production-grade parts (Level 1), through tamper evidence and role-based authentication (Level 2), to tamper detection and response that erases secrets (Level 3) and protection against environmental attacks (Level 4).

FIPS 140-2 is now historical. After September 21, 2026, NIST moved the remaining FIPS 140-2 certificates to the Historical list, where they may be used "for existing systems only". New purchases for US federal use need FIPS 140-3 validation, and FIPS 140-3 certificates stay active for five years.

Trusted computing base and reference monitor

Objective 3.4Understanding the small core of hardware and software that every other security control depends on.

  • Trusted computing base (TCB): the "totality of protection mechanisms within a computer system, including hardware, firmware, and software", the combination of which enforces the security policy (CNSSI 4009). Everything outside the TCB is untrusted; a flaw inside it can break the whole policy, so it should be as small as possible.
  • Reference monitor: "a set of design requirements on a reference validation mechanism" that enforces an access control policy over all subjects and objects. SP 800-53 AC-25 requires it to be "tamperproof, always invoked, and small enough to be subject to analysis and testing."
  • Security kernel: the "hardware, firmware, and software elements of a trusted computing base implementing the reference monitor concept."

The three reference monitor properties match design principles from objective 3.1: always invoked is complete mediation, tamperproof protects the mechanism itself, and small enough to verify is economy of mechanism. The boundary between the TCB and the rest of the system is the security perimeter; hardware enforces it with processor privilege levels (often called protection rings), where the kernel runs at the most privileged level and applications at the least.

Memory protection and isolation

Objective 3.4Knowing how systems keep processes apart and stop attackers running code where only data should be.

  • Process isolation (SP 800-53 SC-39): "maintain a separate execution domain for each executing system process", with separate address spaces so one process cannot change another's code. Sandboxes, containers and virtual machines extend the same idea.
  • Virtual memory: the processor's memory management hardware maps each process's addresses to physical memory and blocks access outside its own space.
  • Memory protection (SI-16): controls to stop "unauthorized code execution" in memory, which NIST says include "data execution prevention and address space layout randomization". Data execution prevention (DEP, also called NX or no-execute) marks data areas such as the stack and heap as non-executable, ideally enforced by hardware. Address space layout randomization (ASLR) places code and data at unpredictable addresses, so exploits cannot rely on known locations.
  • Privilege separation: kernel and user mode, so applications cannot directly touch hardware or other processes' memory.

These protections defeat whole classes of attack, such as buffer overflows that inject and run code. Memory-safe programming languages remove many of the underlying bugs altogether, which is why CISA's Secure by Design program asks vendors for memory-safety roadmaps (objective 8.5).

TPMs, HSMs and trusted execution environments

Objective 3.4Choosing between hardware that protects one device's keys and integrity, hardware that protects an organization's keys at scale, and protected areas inside the processor.

A Trusted Platform Module (TPM) is a chip on a device's motherboard that protects keys and records the device's state. Its main functions:

  • Measured boot: each boot stage is measured and recorded, so changes to firmware or the boot loader can be detected.
  • Binding: keys are wrapped so only that TPM can unwrap them, under a storage root key kept inside the TPM.
  • Sealing: a key is tied to the platform's measured state and released only if the measurements match, so a tampered system cannot unlock the disk.
  • Attestation: the TPM signs a report of its measurements, so a remote service can check that the device is in a trusted state before trusting it.

A hardware security module (HSM) is a dedicated, tamper-resistant device, usually a network appliance, a plug-in card or a cloud service, that generates, stores and uses an organization's most important keys, such as certificate authority keys or payment encryption keys, and performs cryptographic operations at high speed without the keys ever leaving it. HSMs are typically FIPS 140-3 validated at Level 3. The usual distinction: a TPM protects one device and its integrity; an HSM protects many systems' keys centrally.

A trusted execution environment (TEE), or secure enclave, is "an area or enclave protected by a system processor": code and data inside it are isolated, even from the operating system and hypervisor, which makes it the basis of confidential computing for data in use (objective 2.6).

Encryption and decryption are themselves system capabilities: processors include instructions that accelerate standard algorithms, self-encrypting drives encrypt in hardware, and keys should be held in a TPM, HSM or TEE rather than in software where possible. At the retail group, laptops use full-disk encryption sealed to the TPM, payment keys never leave a pair of HSMs, and the fraud-scoring AI model runs in a TEE in the cloud.

Key takeaways

  • Controls trace to requirements: define functional and assurance requirements, start from a baseline and tailor, allocate, choose evaluated products, verify. SA-4 puts requirements, assurance, documentation and acceptance criteria into contracts.
  • Common Criteria (ISO/IEC 15408, CC:2022): TOE, protection profile, security target, EAL1-7 (evaluation depth, not security). CCRA: 36 nations recognize certificates.
  • FIPS 140-3 (four levels) validates crypto modules through the CMVP. FIPS 140-2 certificates became historical after September 21, 2026.
  • TCB: all protection mechanisms enforcing policy; keep it small. Reference monitor: tamperproof, always invoked, verifiable (AC-25). Security kernel implements it; rings separate privilege.
  • Memory protection: process isolation (SC-39), virtual memory, DEP and ASLR (SI-16), kernel/user mode; memory-safe languages remove root causes.
  • TPM: one device's keys and integrity (measured boot, binding, sealing, attestation). HSM: an organization's keys at scale, typically FIPS 140-3 Level 3. TEE: processor-protected enclave for data in use.
