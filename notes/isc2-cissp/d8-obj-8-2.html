8.2: Security controls in software development ecosystems

Protecting the languages, libraries, tools, pipelines and repositories that software is made with, since whoever controls them controls what reaches production.

Overview

Objective 8.2

8.2 Identify and apply security controls in software development ecosystems. Sub-topics: programming languages (memory safe, object-oriented); libraries; tool sets; integrated development environment; runtime; CI/CD; software configuration management; code repositories; application security testing (SAST, DAST).

Security in the development process is on the 8.1 page; supply chain risk on the 1.11 page; code testing techniques on the 6.2 page. The official outline is on isc2.org.

Running example. The retail group: about 4,000 staff, 300 stores in the US and the EU, its own card payment processing, a data center plus two cloud providers, an in-house development team and AI services. Its 250 developers in 30 teams use a shared code platform, cloud CI/CD pipelines and an internal package registry.

Languages, libraries, tools and runtimes

Objective 8.2Choosing and controlling the building blocks developers use, which each bring their own risks.

  • Programming languages: memory-safe languages (such as Rust, Go, Java, C#, Python) prevent whole classes of bugs such as buffer overflows and use-after-free that dominate vulnerabilities in C and C++; CISA's Secure by Design work asks manufacturers to publish memory-safety roadmaps. Object-oriented languages offer encapsulation (hiding internal data behind methods), inheritance and polymorphism, which help structure code but can spread a flaw through inheritance. Compiled languages need secure compiler options; interpreted ones depend on the security of the runtime.
  • Libraries: most code in an application is third-party. Use approved, maintained components, pin versions, scan them with software composition analysis, watch for typosquatted or hijacked packages, and keep an SBOM.
  • Tool sets: compilers, build tools, package managers, scanners and AI coding assistants are part of the supply chain. Get them from trusted sources, keep them updated, and review AI-generated code like any other code.
  • Integrated development environments (IDEs): plug-ins and extensions run with the developer's rights and may reach their credentials and code, so allow only approved extensions, keep secrets out of local files, and use IDE security plug-ins to catch issues as code is written.
  • Runtime: the environment that runs the code (virtual machines, interpreters, containers, serverless platforms). Patch it, run with least privilege, sandbox where possible, and use runtime protection and monitoring.

CI/CD, repositories and configuration management

Objective 8.2Protecting the pipeline and repositories, since whoever controls them controls what reaches production.

  • Code repositories: strong authentication (MFA, ideally phishing-resistant) for all developers, branch protection with required reviews, signed commits, no secrets in code (with secret scanning on every push), least-privilege access to repositories, and audit logs.
  • Software configuration management: version control for all code, configuration and infrastructure definitions, so every build is reproducible and every change is traceable to a person and a reason; release versions archived (SSDF PS.3).
  • CI/CD pipelines: pipelines hold powerful credentials and push to production, so harden the build systems, use short-lived credentials, isolate build jobs, review pipeline definitions like code, generate provenance and sign artifacts (frameworks such as SLSA define levels for this), and verify signatures before deployment.
  • Application security testing in the pipeline: SAST on each commit or pull request, software composition analysis for dependencies, secret scanning, infrastructure-as-code scanning, container image scanning, and DAST against test deployments, with thresholds that fail the build for serious findings (objective 6.2).
Pipeline controls (retail group e-commerce)
Repository
MFA with security keys; protected main branch; two reviewers for payment code; secret scanning blocks pushes
Build
Ephemeral build runners; short-lived cloud credentials; SAST, SCA and IaC scans; build fails on critical findings
Artifacts
Container images signed with provenance; SBOM generated per build
Deploy
Signature and policy check before deployment; DAST against staging; production deploy needs an approved change

AI coding assistants

Objective 8.2Using AI tools that write or suggest code without lowering the security bar.

  • Generated code is untrusted input: it can contain vulnerabilities, outdated patterns or insecure defaults, so it goes through the same review, SAST and testing as any other code.
  • Made-up dependencies: assistants sometimes suggest packages that do not exist; attackers can register those names with malicious code, so verify every new dependency.
  • Data exposure: prompts and code sent to an external service may leave the organization; use approved tools with agreed data handling terms, and keep secrets out of prompts.
  • Agents with permissions: tools that can run commands, change files or open pull requests need least privilege, sandboxed environments and human approval for consequential actions; content they read (issues, web pages, documentation) can contain prompt injection.
  • Licensing and provenance: track where code came from, and follow the organization's policy on AI-generated code.

The retail group allows one approved assistant under an enterprise agreement, tags pull requests that include generated code, and blocks new dependencies that are not in its package registry.

Secrets in development

Objective 8.2Keeping passwords, keys and tokens out of code and safe in pipelines.

  • Never in code: secrets in source code end up in every clone, fork, backup and log; once committed, assume they are exposed and rotate them, even after deleting the commit.
  • Secrets managers: applications and pipelines fetch secrets at runtime from a vault, with access control, audit logs and rotation.
  • Short-lived credentials: pipelines use workload identity federation to get temporary cloud credentials instead of stored keys.
  • Scanning: secret scanning on developer machines (pre-commit hooks), on every push, and across repository history.
  • Separate environments: development and test environments use their own secrets, never production ones.
  • Logs: pipelines mask secrets in output; debug logs are reviewed so they do not print tokens.

Containers and artifact repositories

Objective 8.2Protecting the packages and images that pipelines produce and consume.

  • Internal package registry: a proxy for public package sources, so builds use only approved and scanned packages, and an internal name cannot be hijacked by a public package of the same name (dependency confusion).
  • Base images: minimal, approved base images, rebuilt regularly to pick up patches.
  • Image scanning: images scanned for vulnerabilities and secrets in the pipeline and again in the registry, since new vulnerabilities are found after build.
  • Signing and provenance: images and packages are signed and carry build provenance; deployment checks signatures and policy before running them.
  • Registry access: least privilege for pushing images, immutable tags for releases, and audit logs.

These controls protect against the supply chain attacks described on the 1.11 page, where attackers poison a dependency or build system rather than attacking the application directly.

Developer workstations and access

Objective 8.2Treating developers as privileged users, because they are.

  • Managed devices: developer laptops are managed, encrypted and protected by EDR, even if developers need local administrator rights for some tools.
  • Phishing-resistant MFA for repositories, pipelines, cloud consoles and package registries; developer accounts are prime phishing targets.
  • Least privilege: developers have broad rights in development environments but limited or no standing access to production; production access is just-in-time and logged.
  • Cloud development environments: remote, standardized workspaces keep code and secrets off laptops and make offboarding simpler.
  • Offboarding: remove repository, pipeline and registry access promptly, and rotate any secrets the person could see.

Scenario check

PracticeApplying the objective to situations like those in exam questions.

Scenario 1: the committed key
Situation
A developer commits a cloud access key to a public repository and deletes the commit an hour later.
Best response
Revoke and rotate the key immediately, check logs for its use, and add secret scanning that blocks such pushes.
Why
Committed secrets must be treated as exposed; deleting the commit is not enough.
Scenario 2: the typo package
Situation
A build pulls a package whose name differs by one letter from a popular library and contains a credential stealer.
Best response
Use an internal registry with approved packages, pin versions with hashes, and scan dependencies with SCA.
Why
Library controls defend against typosquatting and hijacked packages.
Scenario 3: the over-privileged pipeline
Situation
The CI system uses a long-lived administrator key for the production cloud account in every job.
Best response
Use short-lived, least-privilege credentials per job through workload identity federation, separate build and deploy permissions, and require approval for production.
Why
Pipelines are privileged systems and an attack path to production.
Scenario 4: the assistant suggests a library
Situation
An AI coding assistant suggests a package that no one on the team has heard of.
Best response
Verify that the package exists, is maintained and is approved before adding it; review the generated code like any other.
Why
AI-generated code and suggested dependencies are untrusted until checked.

Key takeaways

  • Ecosystem: memory-safe languages, OO concepts, vetted and scanned libraries, trusted tools and reviewed AI code, approved IDE extensions, patched least-privilege runtimes.
  • Pipelines and repositories: MFA, branch protection, signed commits, secret scanning, version control for everything, hardened CI/CD with short-lived credentials, signed artifacts with provenance, SAST, SCA and DAST gates.
  • AI assistants: generated code is untrusted, verify suggested packages, approved tools only, least privilege and approval for agents, prompt injection risk.
  • Secrets: never in code, vaults, short-lived credentials, scanning before and after commit, separate environments, masked logs.
  • Artifacts and people: internal registry against dependency confusion, minimal rebuilt base images, scanning, signing and verification; developers as privileged users with managed devices, phishing-resistant MFA and JIT production access.
