Overview

Task 1.3

Configure subagent invocation, context passing, and spawning.

The exam guide asks you to know the tool that spawns subagents and how a coordinator is allowed to use it, that a subagent's context has to be provided in its prompt, how an AgentDefinition describes each subagent type, and how forking a session lets you explore different approaches from one shared analysis. In practice it asks you to put complete earlier findings into the synthesis subagent's prompt, keep content and source metadata apart so attribution survives, start parallel subagents with several calls in one coordinator response, and write coordinator prompts as goals and quality criteria rather than step-by-step scripts. Why and when to use a coordinator at all is task 1.2.

Sources: the Claude Agent SDK documentation on subagents, permissions, sessions and the Python reference, and the Claude Code pages on subagents and tools, checked on 19 November 2026. The docs are copyrighted, so they're paraphrased here with short quotes. The code is my own and was tested with anthropic 2.10.0 and claude-agent-sdk 0.2.185 against a mocked API and a stand-in for the SDK's query(), not the live service.

Running example. The outdoor-gear shop's research coordinator from task 1.2: specialists for reviews, sales data and the web, and a synthesizer that writes the buying team's recommendation about an ultralight tent range.

The spawning tool

Task 1.3The Task tool, now called Agent, and what allowedTools has to do with it.

A coordinator spawns a subagent by calling a built-in tool. The guide calls it Task; since Claude Code 2.1.63 it appears as Agent in tool_use blocks (the session's start-up tool list still shows Task), so code that detects subagent calls should accept both names. Its input carries a short description, the prompt that becomes the subagent's brief, and an optional subagent_type naming one of your defined agents; with no type, Claude gets the built-in general-purpose subagent.

"allowedTools must include Task": the guide's rule and today's behaviour. The guide states that a coordinator can invoke subagents only if allowedTools includes "Task", so expect that as the answer to an exam question about it, and the docs' own examples still list "Agent" there. Current Agent SDK documentation adds a nuance: allowed_tools only pre-approves tools, and Agent is one of the tools that "don't ask before running", so in the default permission mode a coordinator can spawn subagents even when it isn't listed. To stop spawning, remove the tool with disallowed_tools=["Agent"]; to stop one subagent from spawning its own, leave Agent out of its tools list.

Other limits on spawning: subagents can nest up to three levels by default (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH), at most 20 run at once, and a subagent inherits the main session's permission mode when that mode is plan, acceptEdits, auto or bypassPermissions.

Defining subagents

Task 1.3AgentDefinition: description, system prompt and tool restrictions per subagent type.

  • description (required): when to use this subagent. The coordinator reads it to choose, so make it specific ("Reads exported customer reviews in data/reviews/") rather than generic ("Helps with research").
  • prompt (required): the subagent's system prompt, its role, method and standards.
  • tools: the tools it may use. Omit it to inherit every tool available to subagents; list tools to restrict it, such as read-only Read, Grep and Glob for an analyst that must never edit. disallowedTools removes specific tools instead.
  • model: an alias such as haiku, sonnet or opus, a full model ID, or inherit.
  • Also: maxTurns, effort, skills, mcpServers, memory, background and permissionMode. The Python SDK keeps these camelCase names.

Definitions can be passed in code through the agents option, which the SDK docs recommend, or written as Markdown files in .claude/agents/; a definition in code wins over a file with the same name. The 1.2 page's coordinator example defines four.

Context is passed, not inherited

Task 1.3What a subagent knows comes from its brief.

The SDK docs are explicit: unless the subagent is a fork, the only content passed from parent to subagent is the Agent tool's prompt string, so file paths, error messages and decisions it needs must be written into that prompt. A subagent doesn't see the coordinator's conversation, its tool results or its system prompt, and when a subagent finishes, the next one of the same type starts fresh: nothing carries over between invocations by default.

  • Persistent memory is opt-in. A subagent definition can set memory (user, project or local) to give it a directory it reads and writes across sessions, with a MEMORY.md loaded at start. Without it, there's no shared memory.
  • Resuming is a different thing. A finished subagent can be resumed by its agent ID within the same session, with its own history intact; that continues one subagent, it doesn't share context between different ones.

Handing over complete findings

Task 1.3Full results into the synthesis prompt, with content and metadata kept apart.

The synthesis subagent can only combine what it's given. If the coordinator passes "the market scout found a cheaper rival tent", the synthesizer can't check it, quote it or cite it. Pass the complete findings from the earlier subagents (search results, document analysis) directly in its prompt, and pass them as structured data: each finding's content in one field and its metadata (source URL, document name, page number) in another.

synthesis_handoff.py (Python, anthropic SDK)Optional 
"""Hand complete findings to a synthesis subagent as structured data, so every claim keeps its source."""
import json

import anthropic

client = anthropic.Anthropic()

# What the web and document subagents returned: content separate from metadata.
FINDINGS = [
    {"id": "F1", "claim": "Rival A sells a 1.1 kg two-person tent for 320 EUR.",
     "source": {"type": "web", "url": "https://rival-a.example/tents/feather-2"}},
    {"id": "F2", "claim": "14 of 120 tent reviews in 2026 complain about weight.",
     "source": {"type": "document", "name": "reviews-2026.csv", "rows": "R-101 to R-388"}},
    {"id": "F3", "claim": "Tents under 1.5 kg had a 9% return rate, against 4% for heavier ones.",
     "source": {"type": "document", "name": "returns-report-q3.pdf", "page": 7}},
]

SYSTEM = (
    "You write the buying team's recommendation from the findings provided. "
    "Use only those findings, and cite their ids in brackets, like [F2], after every claim. "
    "If the findings don't answer part of the question, say so instead of guessing."
)


def synthesise(question: str, findings: list[dict]) -> str:
    # The synthesizer starts with an empty context, so everything goes into its prompt:
    # the question and the complete findings, as JSON inside a tag.
    prompt = f"<question>{question}</question>\n<findings>\n{json.dumps(findings, indent=2)}\n</findings>"
    response = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=2000, system=SYSTEM,
        messages=[{"role": "user", "content": prompt}],
    )
    report = "".join(b.text for b in response.content if b.type == "text")
    cited = {part.split("]")[0] for part in report.split("[")[1:]}
    unknown = cited - {f["id"] for f in findings}
    if unknown:
        raise ValueError(f"report cites findings that don't exist: {sorted(unknown)}")
    return report


def sources(report: str, findings: list[dict]) -> list[str]:
    """Rebuild the attribution list from the ids the report actually cites."""
    by_id = {f["id"]: f["source"] for f in findings}
    lines = []
    for fid in sorted({p.split("]")[0] for p in report.split("[")[1:]}):
        s = by_id[fid]
        where = s.get("url") or f"{s['name']}" + (f", page {s['page']}" if "page" in s else "")
        lines.append(f"[{fid}] {where}")
    return lines


if __name__ == "__main__":
    report = synthesise("Should we stock an ultralight two-person tent range next spring?", FINDINGS)
    print(report)
    print("\n".join(sources(report, FINDINGS)))
  • Why structure: when sources are mixed into prose, attribution gets lost or reworded at each hop. With an ID per finding, the synthesizer cites [F3] and code rebuilds "returns-report-q3.pdf, page 7" exactly.
  • Checkable: because citations point at known IDs, the code can reject a report that cites a finding that doesn't exist, rather than shipping an invented source.
  • Large results: when findings are too big to pass whole, store them and pass references with their metadata, as in task 1.2.

Spawning in parallel

Task 1.3Several spawning calls in one coordinator response, not one per turn.

Independent subagents should start together. A coordinator does that the same way any agent runs tools in parallel: it emits several Agent calls in one response.

parallel_spawn.json (JSON, one assistant response) 
{
  "role": "assistant",
  "content": [
    {"type": "text", "text": "I'll check reviews and competitors at the same time."},
    {"type": "tool_use", "id": "toolu_01A", "name": "Agent",
     "input": {"subagent_type": "review-analyst", "description": "Weight complaints",
               "prompt": "Goal: how often 2026 tent reviews in data/reviews/ complain about weight. Return counts and review IDs."}},
    {"type": "tool_use", "id": "toolu_01B", "name": "Agent",
     "input": {"subagent_type": "market-scout", "description": "Rival ultralight tents",
               "prompt": "Goal: weight and price of three rival two-person tents under 1.5 kg. Cite a URL for each."}}
  ]
}

Emitting one call, waiting, and emitting the next in a later turn makes the work sequential, so the run takes the sum of the subagents' times instead of the longest one. In the Agent SDK, subagents now also start in the background by default and report in a later turn, which softens that cost, but the guide's rule still holds for any coordinator that waits for each result.

Goals, not procedures

Task 1.3Coordinator prompts that state the goal and the quality bar.

coordinator_prompts.txt (coordinator prompts) 
PROCEDURAL (brittle): every subagent follows a script, whatever it finds
  1. Ask market-scout to search "ultralight tent" on three named retailer sites.
  2. Ask review-analyst to count reviews containing the word "heavy".
  3. Ask sales-analyst to export last year's tent sales.
  4. Ask synthesizer to write five bullet points.

GOAL-BASED (adaptable): the goal, the standard, and room to choose how
  Goal: decide whether an ultralight two-person tent range is worth stocking next spring.
  A good answer: states expected demand and margin with figures; compares at least three
    competing products on weight and price; says how weight affects complaints and returns;
    cites a source for every figure; lists what could not be established.
  Constraints: use only our own data and public web sources; finish within five subagent runs.
  Delegate as you judge best, and tell each specialist the goal and standard that apply to its part.

The procedural prompt fixes the steps, so when a retailer site changes, "heavy" misses reviews that say "weighs a ton", or the sales export lacks returns, no one adapts. The goal-based prompt says what a good answer must contain and leaves the method to the agents, which lets the coordinator choose specialists and lets each specialist change approach when its first attempt comes up short. Constraints (sources, budget) still belong in it; it's the step-by-step method that comes out.

Forking from a shared baseline

Task 1.3One analysis, two directions, neither disturbing the other.

The Agent SDK saves each session's history and offers three ways back into it: continue (the most recent session), resume (a session by ID) and fork. A fork (resume=session_id plus fork_session=True) creates a new session that starts with a copy of the original's history and gets its own ID; the original is unchanged and can be resumed separately.

fork_baseline.py (Python, claude-agent-sdk)Optional 
import anyio
from claude_agent_sdk import ClaudeAgentOptions, ResultMessage, query

TOOLS = ["Read", "Grep", "Glob"]


async def run(prompt: str, **session) -> str:
    """Run one query and return its session ID (a fork gets a new one)."""
    session_id = None
    async for message in query(prompt=prompt, options=ClaudeAgentOptions(allowed_tools=TOOLS, max_turns=20, **session)):
        if isinstance(message, ResultMessage):
            session_id = message.session_id
            print(f"[{message.subtype}] {message.result}")
    return session_id


async def main() -> None:
    # 1. One shared baseline: read the data once.
    baseline = await run("Analyse data/sales/ and data/reviews/ for the two-person tent range. Summarise demand, "
                         "returns and complaints. Don't recommend anything yet.")
    # 2. Two forks start from a copy of that analysis and diverge; the baseline is untouched.
    ultralight = await run("Option A: design an ultralight range. Price it and list the risks.",
                           resume=baseline, fork_session=True)
    budget = await run("Option B: design a budget range instead. Price it and list the risks.",
                       resume=baseline, fork_session=True)
    # 3. Back on the baseline, compare the two options it never saw being worked out.
    print("forks:", ultralight, budget)
    await run(f"Two options were developed in sessions {ultralight} and {budget}. "
              "List the questions we'd need answered to choose between them.", resume=baseline)


if __name__ == "__main__":
    anyio.run(main)
  • Why fork: the expensive part (reading the data, building the analysis) happens once; each alternative starts from the same baseline instead of redoing it, and an approach that goes nowhere doesn't clutter the main thread.
  • Only the conversation branches. Files a forked agent edits are real and visible to every session in that directory; use file checkpointing or separate working directories to branch files too.
  • Same machine. Sessions are stored under ~/.claude/projects/; to continue elsewhere, use a session store adapter or pass captured results into a fresh session.
  • Subagent forks are the in-conversation version: a subagent started as a fork inherits the parent conversation instead of starting fresh.

Key takeaways

  • Subagents are spawned with the Task tool, named Agent since Claude Code 2.1.63; match both names. The guide requires it in allowedTools; today that pre-approves rather than enables it, and disallowed_tools is how you block it.
  • AgentDefinition: a specific description (for choosing), a prompt (system prompt), tools to restrict, model to size; code definitions override .claude/agents/ files.
  • Subagents don't inherit the coordinator's context or share memory between invocations; the brief is the only channel. Persistent memory is opt-in.
  • Give the synthesizer the complete findings, as structured data with content and source metadata separated, so attribution survives and citations can be checked.
  • Start independent subagents with several Agent calls in one coordinator response, not one per turn.
  • Coordinator prompts state goals and quality criteria (plus constraints), not step-by-step procedures.
  • Fork a session (resume plus fork_session=True) to explore alternatives from one baseline; the original is untouched, and files aren't branched.
