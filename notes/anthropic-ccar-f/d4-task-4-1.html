4.1: Explicit Criteria for Precision

Getting an automated reviewer to report what matters and stay quiet about what doesn't: categories it can apply rather than moods it should adopt, severity levels pinned to real code, and a plan for the category that keeps crying wolf.

Overview

Task 4.1

Design prompts with explicit criteria to improve precision and reduce false positives.

The exam guide asks you to know why explicit criteria beat vague instructions, why general instructions such as "be conservative" or "only report high-confidence findings" don't raise precision the way specific categorical criteria do, and how a category with many false positives drags down developers' trust in the categories that are accurate. In practice it asks you to write criteria that say which issues to report (bugs, security) and which to skip (minor style, local patterns), to switch off a noisy category temporarily while its prompt is fixed, and to define severity levels with a concrete code example for each. Few-shot examples in general are task 4.2; multi-pass reviews are task 4.6.

Sources: Claude's prompting best-practices guide and the Claude Code documentation on Code Review and its customisation, checked on 19 November 2026. The docs are copyrighted, so they're paraphrased here with short quotes. The criteria file and the precision script are my own; the script was tested on sample feedback.

Running example. The outdoor-gear shop runs an automated review on every pull request to its TypeScript repository. After a month, developers have started ignoring it: most of its comments are about naming and comment wording, and the two real bugs it found last week were dismissed with the rest.

Explicit criteria, not vague goals

Task 4.1Telling the reviewer exactly what counts.

"Check that comments are accurate" leaves Claude to decide what accurate means. It will flag outdated wording, missing details, a comment that could be clearer and a typo, and every one of those is defensible, which is the problem. "Flag a comment only when the behaviour it claims contradicts what the code does, and quote both" defines a narrow, checkable category: there's a claim, there's code, and they disagree.

Claude's prompting guide puts the principle generally: Claude responds well to clear, explicit instructions, and should be treated like a capable new colleague who doesn't know your norms. Its test is to show the prompt to someone with little context; if they'd be unsure what to flag, so is Claude. It also advises saying why a rule exists, because Claude generalises from the reason ("the linter already enforces style, so style comments are noise").

Why "be conservative" doesn't work

Task 4.1Confidence wording versus categorical criteria.

Faced with too many false positives, the tempting fix is an adjective: "be conservative", "only report high-confidence findings", "don't nitpick". These don't change which kinds of finding the reviewer considers in scope; they ask it to apply a stricter version of the same fuzzy judgement. A naming quibble the model is sure about is still a naming quibble, and it still gets reported. And the model's sense of its own confidence isn't a measure of whether a finding is useful to your team.

What does move precision is changing the categories: name what's in scope, name what's out, and set evidence rules. Claude Code's Code Review guidance does exactly this when reviews are noisy, asking teams to "require evidence before a class of finding is posted", for example that behaviour claims cite a file:line rather than being inferred from a function's name.

Confidence can still narrow a defined scope. The same guidance suggests a higher bar for some paths: in scripts/, report only if near-certain and severe. That works because it's attached to a category (a path, and "severe"), not used instead of one. On the exam, the answer that adds categorical criteria beats the one that only asks for more confidence.

What to report, what to skip

Task 4.1Writing the criteria down.

REVIEW.md (Markdown, review criteria) 
# Review instructions for the shop's TypeScript repository

## Report
- Bugs: logic that produces a wrong result, an unhandled error path, or a race on shared state.
- Security: SQL or shell built from request data, secrets in code or logs, a missing auth check on a route.
- Money: amounts handled as floating point, or currency mixed without conversion (packages/payments).
- Comments: flag a comment only when the behaviour it claims contradicts what the code does,
  and quote both the comment and the line that contradicts it.

## Do not report
- Style, naming and formatting (the linter enforces these).
- Patterns that match the surrounding file, even if you'd write them differently.
- Missing tests, unless the change adds a new API route.
- Generated files under src/gen/.

## Severity
- High: wrong money or data, or a security hole, in code that runs in production.
  Example: `const total = price * 1.2;` where price is a float of euros.
- Medium: a bug with a limited blast radius or an easy workaround.
  Example: an error swallowed by `catch {}` in a retry helper, so failures are logged nowhere.
- Low: a real defect with no user impact today.
  Example: a comment says "returns null when not found" but the function throws.

## Evidence
Every finding cites file:line for the problem. Don't infer behaviour from a function's name.
  • Report lists categories with a test for each: what makes something a bug, a security issue, a money error or a misleading comment.
  • Do not report removes what other tools already cover (style is the linter's job), what's a matter of local taste (patterns that match the surrounding file), and what isn't code you care about (generated files).
  • Evidence applies to every category: a file:line for the problem, no conclusions from names.

Skipping "local patterns" matters more than it looks: a reviewer that proposes its own preferred style for code that's consistent with the rest of the file produces comments nobody will act on.

Severity with concrete examples

Task 4.1Consistent classification from defined levels.

"High, medium, low" with no definitions gets applied differently in every review, and sometimes differently to the same issue twice in one review. Each level needs a definition in terms of impact (wrong money or data, limited blast radius, no user impact today) and a concrete code example that sits clearly inside it, as in the criteria above. Examples anchor the boundary in a way adjectives can't: price * 1.2 on a float of euros is high, a swallowed error in a retry helper is medium.

The prompting guide's advice on examples applies: make them relevant to your actual code, diverse enough to cover the edge cases, and clearly marked as examples. If two levels keep getting confused, add an example that sits right at the boundary between them.

False positives and trust

Task 4.1One noisy category can bury the accurate ones.

Developers don't judge each comment on its merits; they judge the reviewer. When most of its comments in one category are wrong or pointless, they start dismissing everything it says, including the security finding that was right. So a category's false-positive rate isn't only that category's problem.

The guide's remedy is to temporarily disable the high false-positive category, which restores trust in the rest straight away, and to fix its criteria offline before switching it back on. That needs a measurement per category, not just a general feeling that the reviewer is noisy:

category_precision.py (Python)Optional 
"""Measure each review category's precision from developers' reactions, and switch off the noisy ones."""
from collections import Counter

MIN_PRECISION = 0.6  # below this, a category costs more trust than it earns
MIN_SAMPLES = 20     # don't judge a category on a handful of findings


def precision_by_category(feedback: list[dict]) -> dict[str, tuple[float, int]]:
    """feedback rows: {"category": "comments", "outcome": "fixed" | "dismissed"}"""
    total, kept = Counter(), Counter()
    for row in feedback:
        total[row["category"]] += 1
        kept[row["category"]] += row["outcome"] == "fixed"
    return {c: (kept[c] / total[c], total[c]) for c in total}


def update_config(config: dict, feedback: list[dict]) -> list[str]:
    """Disable categories that fall below the bar; keep a reason so they can be fixed and re-enabled."""
    changes = []
    for category, (precision, n) in precision_by_category(feedback).items():
        if n >= MIN_SAMPLES and precision < MIN_PRECISION and config[category]["enabled"]:
            config[category].update(enabled=False, reason=f"precision {precision:.0%} over {n} findings")
            changes.append(f"disabled {category}: {precision:.0%} of {n} findings were fixed")
    return changes


def review_prompt(config: dict) -> str:
    """Only enabled categories reach the reviewer; disabled ones become explicit skips."""
    report = [f"- {c}: {v['rule']}" for c, v in config.items() if v["enabled"]]
    skip = [f"- {c} (temporarily off while its criteria are rewritten)" for c, v in config.items() if not v["enabled"]]
    return "Report only these categories:\n" + "\n".join(report) + "\n\nDo not report:\n" + "\n".join(skip or ["- (none)"])


if __name__ == "__main__":
    config = {
        "bugs": {"enabled": True, "rule": "wrong results, unhandled errors, races"},
        "security": {"enabled": True, "rule": "injection, secrets, missing auth checks"},
        "comments": {"enabled": True, "rule": "claimed behaviour contradicts the code"},
        "performance": {"enabled": True, "rule": "work repeated inside loops over large inputs"},
    }
    feedback = ([{"category": "bugs", "outcome": "fixed"}] * 40 + [{"category": "bugs", "outcome": "dismissed"}] * 6
                + [{"category": "performance", "outcome": "fixed"}] * 7 + [{"category": "performance", "outcome": "dismissed"}] * 23)
    print("\n".join(update_config(config, feedback)))
    print(review_prompt(config))
  • Precision per category comes from what developers did with the findings (fixed or dismissed); a minimum sample size stops one bad week from switching off a good category.
  • A disabled category doesn't just vanish: it becomes an explicit "do not report" line, so the reviewer doesn't drift back into it.
  • Re-enable it only after the rewritten criteria have been tested on past pull requests and its precision is back above the bar.

How Claude Code's Code Review does it

Task 4.1The same ideas in Anthropic's own reviewer.

  • Verification before posting: several agents look for issues in parallel, then a verification step checks candidate findings against the code and drops false positives before anything is posted.
  • Three severities: Important (a bug to fix before merging), Nit (minor, not blocking) and Pre-existing (a real bug the pull request didn't introduce). Reviews never approve or block a pull request.
  • REVIEW.md at the repository root holds review-only instructions: redefine what Important means for this repository, cap nits ("report at most five"), list what not to report (anything CI enforces, generated files, lockfiles), and list checks to always run. It's read from the base branch, never from the pull request being reviewed, so a pull request can't loosen its own review.

Each of those is a categorical lever: a definition, a cap, an exclusion list, an evidence rule. None of them is "be more careful".

Key takeaways

  • Explicit, checkable criteria ("flag a comment only when its claimed behaviour contradicts the code") beat vague goals ("check comments are accurate"). Say why each rule exists.
  • "Be conservative" and "only high-confidence findings" don't change what's in scope, so they don't fix precision; categorical criteria and evidence rules do.
  • List what to report (bugs, security, money errors) and what to skip (style the linter enforces, local patterns, generated files).
  • Define each severity level by impact and give a concrete code example for each, so classification is consistent.
  • A high false-positive category undermines trust in the accurate ones: measure precision per category, disable the noisy one temporarily, fix and test its criteria, then re-enable it.
  • Claude Code's Code Review applies the same levers: a verification step, Important / Nit / Pre-existing, and a REVIEW.md read from the base branch.
