4.4: Validation, Retry and Feedback Loops

Catching the extraction that's well-formed but wrong, sending it back with exactly what failed, knowing when no retry will ever succeed, and recording enough about each review finding to learn from the ones developers throw away.

Overview

Task 4.4

Implement validation, retry, and feedback loops for extraction quality.

The exam guide asks you to know how a retry that includes the specific validation errors guides the model to a correction, that retries are useless when the information simply isn't in the source (as opposed to format or structural errors), how tracking which code constructs trigger findings (a detected_pattern field) makes dismissals analysable, and the difference between semantic errors and the syntax errors that tool use already removes. In practice it asks you to send follow-ups containing the original document, the failed extraction and the specific errors, to recognise in advance which retries will and won't work, and to design self-checking output such as calculated_total beside stated_total and a conflict_detected flag. Schemas themselves are task 4.3.

Sources: the patterns come from the exam guide; the supporting API behaviour (what schemas guarantee, stop reasons) is from the Claude API documentation, checked on 19 November 2026. The code is my own and was tested with anthropic 2.10.0 against a mocked API.

Running example. The outdoor-gear shop's invoice pipeline from tasks 4.2 and 4.3, and its pull-request reviewer from task 4.1.

Syntax errors and semantic errors

Task 4.4What's left to validate once the schema is enforced.

  • Syntax errors (malformed JSON, missing required keys, wrong types) are eliminated by tool use with strict schemas or by JSON outputs. If you still ask for JSON in plain text, your validator has to catch them too.
  • Semantic errors survive any schema: line amounts that don't add up to the total, a delivery date in the invoice-date field, a dropped line, a value copied from the wrong part of the document. Only checks that know the business rules find them.

Validation is the code that runs these checks on every extraction, and its output (the list of what failed) is the input to the retry.

Retry with error feedback

Task 4.4The document, the failed answer and the exact errors.

retry_loop.py (Python, anthropic SDK) 
"""Validate an invoice extraction, retry with the specific errors, and stop when retrying can't help."""
import json

import anthropic

client = anthropic.Anthropic()

SYSTEM = ("Extract the invoice as JSON: supplier, invoice_number, po_number (or null), lines (description, amount), "
          "stated_total (the total printed on the invoice), calculated_total (the sum of the line amounts you extracted), "
          "conflict_detected (true if the document itself disagrees with itself, e.g. two different totals) and conflict_note.")


def ask(messages: list) -> str:
    response = client.messages.create(model="claude-sonnet-5-5", max_tokens=2000, system=SYSTEM, messages=messages)
    return "".join(b.text for b in response.content if b.type == "text")


def validate(data: dict) -> tuple[list[str], list[str]]:
    """Return (fixable errors, unfixable gaps). Retrying only helps with the first kind."""
    fixable, gaps = [], []
    calc = round(sum(line["amount"] for line in data["lines"]), 2)
    if abs(calc - data["calculated_total"]) > 0.01:
        fixable.append(f"calculated_total is {data['calculated_total']} but your lines sum to {calc}")
    if data["stated_total"] is not None and abs(calc - data["stated_total"]) > 0.01 and not data["conflict_detected"]:
        fixable.append(f"lines sum to {calc} but stated_total is {data['stated_total']}: re-check the lines, "
                       "or set conflict_detected if the document is inconsistent")
    if data["po_number"] is None:
        gaps.append("po_number not in this document (it may be on the purchase order, which we didn't send)")
    return fixable, gaps


def extract(document: str, max_retries: int = 2) -> dict:
    messages = [{"role": "user", "content": f"<document>\n{document}\n</document>"}]
    for attempt in range(max_retries + 1):
        raw = ask(messages)
        try:
            data = json.loads(raw)
        except ValueError as e:
            fixable, gaps = [f"output was not valid JSON ({e})"], []
            data = None
        else:
            fixable, gaps = validate(data)
        if not fixable:
            return {"data": data, "gaps": gaps, "attempts": attempt + 1}
        # Retry with the original document, the failed output and the exact errors, not just "try again".
        messages += [{"role": "assistant", "content": raw},
                     {"role": "user", "content": "Your extraction failed these checks:\n- " + "\n- ".join(fixable)
                      + "\nCorrect them using the document above. Change only what the errors concern."}]
    return {"data": data, "gaps": gaps, "errors": fixable, "attempts": max_retries + 1, "needs_review": True}
  • What the follow-up contains: the original document (still the first message), the failed extraction (as Claude's previous turn) and the specific errors in a new message: "lines sum to 300.0 but stated_total is 492.0". A bare "that's wrong, try again" gives the model nothing to fix and often produces the same answer.
  • Change only what failed: asking for a targeted correction keeps the fields that were right from drifting.
  • Bounded: a fixed number of retries, then the result is marked for human review with its errors attached, rather than looping forever or silently accepting a bad record.

When a retry can't help

Task 4.4Separating errors the model can fix from gaps in the source.

A retry gives the model another look at the same document. That fixes mistakes in reading it, and nothing else:

  • Retries succeed for format mismatches (a date in the wrong format, "1.234,50" not converted), structural errors (a line dropped or split, a value in the wrong field) and invalid JSON when no schema is enforced.
  • Retries fail when the information isn't there: the PO number exists only on the purchase order, which wasn't sent; the delivery address is in a separate shipping note. Asking again invites the model to invent a value to satisfy you.

So the validator returns two lists: fixable errors, which trigger a retry, and gaps, which are recorded (null plus a reason) and routed elsewhere, for example by fetching the purchase order. The example treats a missing PO number as a gap and never retries for it.

"Retry until every required field is filled" is the tempting wrong answer for missing information. It turns honest nulls into fabrications. The fix for an absent field is a nullable schema (task 4.3) and a route to the document that does contain it.

Fields that check themselves

Task 4.4Making discrepancies visible in the output itself.

  • stated_total and calculated_total: extract the total printed on the invoice and the sum of the extracted lines. If they differ, either a line was misread (a fixable error, so retry) or the invoice itself is wrong.
  • conflict_detected and conflict_note: let the model say the source disagrees with itself ("page 1 says 500, the summary says 492"). A flagged conflict isn't an extraction error, so it isn't retried; it goes to a person, with the note.

These fields turn a silent inconsistency into data your code can act on: retry when the extraction is the problem, escalate when the document is.

Feedback loops for findings

Task 4.4Learning from the findings developers dismiss.

Knowing that 40% of the reviewer's "bugs" findings are dismissed (task 4.1) says there's a problem, not where. Adding a detected_pattern field to every structured finding, naming the code construct that triggered it ("empty catch block", "float money arithmetic"), lets you group dismissals by cause:

dismissal_patterns.py (Python) 
"""Which code constructs make developers dismiss review findings? Group by the finding's detected_pattern."""
from collections import defaultdict


def dismissal_report(findings: list[dict], min_count: int = 10) -> list[str]:
    """findings: {"category", "detected_pattern", "outcome": "fixed" | "dismissed"}"""
    by_pattern = defaultdict(lambda: [0, 0])  # [dismissed, total]
    for f in findings:
        key = (f["category"], f["detected_pattern"])
        by_pattern[key][1] += 1
        by_pattern[key][0] += f["outcome"] == "dismissed"
    rows = []
    for (category, pattern), (dismissed, total) in sorted(by_pattern.items(), key=lambda kv: -kv[1][0] / kv[1][1]):
        if total >= min_count:
            rows.append(f"{category:<10} {pattern:<32} {dismissed}/{total} dismissed ({dismissed / total:.0%})")
    return rows


if __name__ == "__main__":
    sample = ([{"category": "bugs", "detected_pattern": "empty catch block", "outcome": "dismissed"}] * 18
              + [{"category": "bugs", "detected_pattern": "empty catch block", "outcome": "fixed"}] * 2
              + [{"category": "bugs", "detected_pattern": "float money arithmetic", "outcome": "fixed"}] * 14
              + [{"category": "bugs", "detected_pattern": "float money arithmetic", "outcome": "dismissed"}] * 1)
    print("\n".join(dismissal_report(sample)))

Here the "empty catch block" pattern accounts for nearly all the dismissals, while "float money arithmetic" findings are almost always fixed. The fix is then specific: an exclusion or an acceptable-pattern example (task 4.2) for logged-and-retried errors, leaving the useful pattern alone, rather than switching off the whole bugs category.

Key takeaways

  • Schemas remove syntax errors; semantic errors (sums, field placement, dropped lines) need validation in code.
  • Retry with the original document, the failed extraction and the specific errors; ask for a targeted correction; cap retries and send what's still failing to review.
  • Retries fix misreadings (format, structure); they can't supply information that isn't in the source. Record gaps as nulls with a reason and route them, never retry them.
  • Self-checking fields such as stated_total versus calculated_total and conflict_detected separate extraction errors from inconsistent documents.
  • A detected_pattern on each finding makes dismissals analysable by cause, so fixes target the noisy pattern instead of a whole category.
