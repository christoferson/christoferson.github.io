4.3: Structured Output with Tools and Schemas

Getting machine-readable data out of Claude every time: extraction tools whose input schema is the output format, the tool_choice settings that make a call happen (and the newest models that refuse them), what a schema can and can't guarantee, and schemas designed so Claude never has to invent a value.

Overview

Task 4.3

Enforce structured output using tool use and JSON schemas.

The exam guide asks you to know that tool use with a JSON schema is the most reliable way to get schema-compliant output without JSON syntax errors, how the three tool_choice settings differ, that a strict schema prevents syntax errors but not semantic ones (line items that don't add up, values in the wrong field), and how to design schemas (required versus optional fields, enums with "other" plus a detail field). In practice it asks you to define extraction tools and read their tool_use input, use "any" when several extraction tools exist and the document type is unknown, force one named tool so an extraction runs before enrichment, make fields nullable when documents may lack them, add "unclear" and "other" values, and pair strict schemas with normalisation rules in the prompt. Validation and retries are task 4.4; the API mechanics are covered in the developer notes (structured outputs).

Sources: the Claude API documentation on defining tools, strict tool use, structured outputs and errors, checked on 19 November 2026. The docs are copyrighted, so they're paraphrased here with short quotes. The code is my own and was tested with anthropic 2.10.0 against a mocked API.

Running example. The outdoor-gear shop's supplier-document pipeline receives invoices and delivery notes in one mailbox, with nothing to say which is which, and must turn each into a record for the accounting system.

Tools as an output format

Task 4.3The tool's input schema is the shape of the answer.

An extraction "tool" doesn't have to do anything. You define extract_invoice with an input schema describing the fields you want, Claude "calls" it with the extracted values as arguments, and your code reads the tool_use block's input: already-parsed JSON in your shape. Asking for JSON in plain text, by contrast, invites a stray sentence, a missing bracket or a trailing comma.

With "strict": true on the tool, Claude's tool names and inputs are guaranteed to match the schema: required fields present, types right, no extra keys, no syntax errors. The same guarantee for a plain reply is available as JSON outputs (output_config.format), which the API now offers as the other route to structured output.

tool_choice: auto, any, forced

Task 4.3Whether Claude must call a tool, and which.

  • {"type": "auto"} (the default when tools are given): Claude decides, so it may answer in text instead of calling a tool.
  • {"type": "any"}: Claude must call a tool but chooses which. Right when several extraction schemas exist and the document type isn't known in advance: Claude picks extract_invoice or extract_delivery_note, but it can't reply in prose.
  • {"type": "tool", "name": "extract_metadata"}: Claude must call that specific tool. Right when a step has to happen first, such as extracting metadata before enrichment calls that depend on it.
  • {"type": "none"}: no tool calls.

With any or a named tool, the response starts directly with the tool call (no text before it), and on the models that allow forcing, the forced call skips thinking.

The newest models reject forced tool choice. The guide's "any" and named-tool techniques work on models such as Claude Haiku 5.5 and Opus 5, and they're the expected exam answers. But Claude Fable 5.2, Mythos 5.2, Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 return a 400 error for both ("tool_choice: type "tool" and "any" are not supported for this model"). On those, the docs say to use auto with strict tools and a clear instruction to call one, or JSON outputs when you need the reply itself in a fixed shape, and to check in code that a tool was actually called.

An extraction pipeline

Task 4.3Two schemas, an unknown document, and a forced first step.

extract_tools.py (Python, anthropic SDK)Optional 
"""Structured extraction through tool use: schema-valid input every time, then semantic checks in code."""
import anthropic

client = anthropic.Anthropic()

# Models that reject forced tool_choice ("any" or a named tool) with a 400 error.
NO_FORCED_CHOICE = {"claude-fable-5-2", "claude-mythos-5-2", "claude-opus-5-5", "claude-sonnet-5-5",
                    "claude-fable-5-1", "claude-mythos-5-1"}

NULLABLE_STR = {"type": ["string", "null"]}
LINE = {"type": "object", "additionalProperties": False,
        "properties": {"description": {"type": "string"}, "quantity": {"type": "number"},
                       "unit_price": {"type": "number"}, "amount": {"type": "number"}},
        "required": ["description", "quantity", "unit_price", "amount"]}

EXTRACT_INVOICE = {
    "name": "extract_invoice", "strict": True,
    "description": "Record a supplier invoice: a document that asks for payment.",
    "input_schema": {"type": "object", "additionalProperties": False, "properties": {
        "supplier": {"type": "string"},
        "invoice_number": {"type": "string"},
        "po_number": NULLABLE_STR,                     # often absent: nullable, so nothing gets invented
        "invoice_date": NULLABLE_STR,                  # ISO 8601, per the normalisation rules
        "category": {"type": "string", "enum": ["fabric", "hardware", "packaging", "other", "unclear"]},
        "category_detail": NULLABLE_STR,               # filled when category is "other" or "unclear"
        "lines": {"type": "array", "items": LINE},
        "total": {"type": "number"},
    }, "required": ["supplier", "invoice_number", "po_number", "invoice_date", "category", "category_detail", "lines", "total"]},
}

EXTRACT_DELIVERY_NOTE = {
    "name": "extract_delivery_note", "strict": True,
    "description": "Record a delivery note: a document listing goods delivered, with no amount to pay.",
    "input_schema": {"type": "object", "additionalProperties": False, "properties": {
        "supplier": {"type": "string"}, "delivery_date": NULLABLE_STR, "po_number": NULLABLE_STR,
        "items": {"type": "array", "items": {"type": "string"}},
    }, "required": ["supplier", "delivery_date", "po_number", "items"]},
}

RULES = ("Normalise as you extract: dates to YYYY-MM-DD, amounts to plain numbers without currency symbols "
         "or thousands separators, supplier names as printed on the letterhead. Use null when a field is absent.")


def extract(document: str, model: str = "claude-haiku-5-5") -> tuple[str, dict]:
    tools = [EXTRACT_INVOICE, EXTRACT_DELIVERY_NOTE]
    params = dict(model=model, max_tokens=2000, tools=tools, system=RULES,
                  messages=[{"role": "user", "content": f"Record this document with one tool.\n<document>{document}</document>"}])
    if model not in NO_FORCED_CHOICE:
        params["tool_choice"] = {"type": "any"}  # must call a tool; Claude picks which, as the document type is unknown
    response = client.messages.create(**params)  # elsewhere: "auto" plus strict tools and a clear instruction
    calls = [b for b in response.content if b.type == "tool_use"]
    if not calls:
        raise RuntimeError("no extraction tool was called")
    return calls[0].name, calls[0].input


def semantic_problems(invoice: dict) -> list[str]:
    """The schema guarantees shape, not truth: check the arithmetic and the cross-field rules."""
    problems = []
    for line in invoice["lines"]:
        if abs(line["quantity"] * line["unit_price"] - line["amount"]) > 0.01:
            problems.append(f"line '{line['description']}': quantity x unit price != amount")
    if abs(sum(l["amount"] for l in invoice["lines"]) - invoice["total"]) > 0.01:
        problems.append("lines don't add up to the total")
    if invoice["category"] in ("other", "unclear") and not invoice["category_detail"]:
        problems.append("category needs a detail")
    return problems


def extract_metadata_first(document: str) -> dict:
    """Force one specific tool so this step always runs before enrichment (on a model that allows forcing)."""
    meta_tool = {"name": "extract_metadata", "strict": True, "description": "Record the document's metadata.",
                 "input_schema": {"type": "object", "additionalProperties": False,
                                  "properties": {"supplier": {"type": "string"}, "document_type": {"type": "string"},
                                                 "language": {"type": "string"}},
                                  "required": ["supplier", "document_type", "language"]}}
    response = client.messages.create(
        model="claude-haiku-5-5", max_tokens=500, tools=[meta_tool],
        tool_choice={"type": "tool", "name": "extract_metadata"},
        messages=[{"role": "user", "content": f"<document>{document}</document>"}],
    )
    return next(b.input for b in response.content if b.type == "tool_use")
  • Choosing the setting by model: "any" where it's accepted; on models that reject it, auto plus strict tools, and code that raises if no tool was called.
  • Normalisation rules in the prompt: the schema says a date is a string; only the prompt can say it must be YYYY-MM-DD, and that "1.234,50 EUR" becomes 1234.50. Strict schemas and format rules work together.
  • The forced first step: extract_metadata_first names its tool so metadata is always extracted before anything else uses it, on a model that allows forcing.

Syntax versus semantics

Task 4.3What a schema guarantees, and what it doesn't.

A strict schema guarantees the shape: total is a number, lines is a list of objects with the right keys. It can't guarantee the content is true: line amounts that don't sum to the total, a delivery date placed in the invoice-date field, a PO number copied into the invoice number. Those are semantic errors, and the semantic_problems function above is where they get caught: arithmetic checks, cross-field rules ("other" needs a detail), and anything else your business knows must hold. Schemas also can't express numeric ranges or string lengths, so those checks live in code too.

Two cases can break even the shape: a refusal and a reply cut off by max_tokens, so check the stop reason before trusting the result.

Designing the schema

Task 4.3Fields Claude can fill honestly.

  • Nullable when the source may not have it. A required, non-nullable po_number forces Claude to produce one, so on an invoice without a PO it will find something plausible. A type list such as ["string", "null"] lets it answer "not present". The example lists every field as required and uses nullability for "may be absent", so the output always has the same keys; leaving a field out of required also works, within the limit of 24 optional parameters per request.
  • Enums for closed sets, with escape hatches. fabric, hardware, packaging cover most invoices; other plus a category_detail string handles new kinds without a schema change; unclear lets Claude say the document doesn't make it obvious, instead of forcing a guess into a real category.
  • Clear descriptions on tools and fields tell Claude which tool fits ("a document that asks for payment") and what a field means.
  • Within strict limits: every object needs additionalProperties: false, and there are caps per request (for example 16 union-type parameters and 20 strict tools), so keep schemas flat and focused.

Key takeaways

  • An extraction tool's input schema is the output format; read the tool_use input. strict: true guarantees schema-valid names and inputs, with no syntax errors; JSON outputs do the same for plain replies.
  • auto: Claude may reply in text. any: must call some tool (use when the document type is unknown). Named tool: must call that one (use to run a step first).
  • Fable 5.2, Opus 5.5, Sonnet 5.5, Fable 5.1 and the Mythos 5.x models reject any and named-tool choice with a 400; use auto with strict tools (and check a tool was called), or JSON outputs.
  • Schemas prevent syntax errors, not semantic ones: check sums, field placement and ranges in code, and check the stop reason.
  • Make absent-able fields nullable to prevent fabrication; use enums with other plus a detail field and an unclear value; put format normalisation rules in the prompt.
