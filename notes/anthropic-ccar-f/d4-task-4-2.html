4.2: Few-Shot Examples

Showing instead of telling: a handful of well-chosen examples that fix the output format, settle the ambiguous cases, separate fine code from real problems, and stop an extraction pipeline from guessing or leaving fields empty.

Overview

Task 4.2

Apply few-shot prompting to improve output consistency and quality.

The exam guide asks you to know that few-shot examples are the most effective fix when detailed instructions still give inconsistent output, that they show how to handle ambiguous cases (which tool to pick for an unclear request, when a branch-level coverage gap matters), that they let the model generalise the judgement to new patterns rather than match only the listed ones, and that they reduce hallucination in extraction from messy documents. In practice it asks you to write 2 to 4 targeted examples for the ambiguous cases with the reasoning behind each choice, examples that fix the output format, examples that separate acceptable code from real issues, and examples for varied document layouts that stop required fields coming back empty. The criteria themselves are task 4.1; schemas are task 4.3.

Sources: Claude's prompting best-practices guide, checked on 19 November 2026 and paraphrased with short quotes. The examples are my own; the extraction prompt was tested with anthropic 2.10.0 against a mocked API.

Running example. Two of the outdoor-gear shop's systems: the automated pull-request reviewer from task 4.1, and the pipeline that extracts supplier invoices, which arrive as tables, emails and multi-page PDFs.

When examples beat instructions

Task 4.2The fix for output that's still inconsistent after careful instructions.

Instructions describe; examples demonstrate. A paragraph saying "give the location, the issue, a severity and a suggested fix" still leaves room for a dozen layouts, while two examples in exactly that layout leave almost none. Claude's prompting guide calls examples "one of the most reliable ways to steer Claude's output format, tone, and structure", and few-shot (multishot) prompting improves both accuracy and consistency.

Examples do more than fix format. They show judgement: an example of a finding that was not reported, with the reason, teaches the boundary in a way a rule struggles to. Because the model generalises from the reasoning, it can apply the same judgement to patterns none of the examples covered, which is the guide's point about generalisation rather than matching only pre-specified cases.

Choosing the examples

Task 4.2A few targeted examples, aimed at the hard cases.

  • How many: the exam guide says 2 to 4 targeted examples; Claude's prompting guide recommends 3 to 5 for best results. Both mean a handful, chosen deliberately, not dozens. A single example tends to be copied too literally: its length, its wording, even its labels.
  • Relevant: mirror the real inputs (your code, your suppliers' invoices), not a generic textbook case.
  • Diverse: cover the edge cases, and vary in ways that don't matter so Claude doesn't learn an accidental pattern (every example flagged, every example the same length).
  • Aimed at ambiguity: spend examples where the right answer is unclear, and show why one action beat the plausible alternative. Easy cases teach little.
  • Marked as examples: wrap each in <example> tags inside <examples>, so Claude doesn't confuse them with the real input or with instructions.

The same applies to agents choosing tools: for an ambiguous request such as "where's my money?", an example that picks get_refund_status over get_order because the customer mentioned a return, with that reason stated, settles the choice better than a longer tool description.

Examples for a code reviewer

Task 4.2One format, one acceptable pattern, one ambiguous case.

review_examples.txt (few-shot block for the review prompt) 
<examples>
<example>
<code file="packages/payments/charge.ts">
const total = items.reduce((sum, i) => sum + i.price * i.qty, 0) * 1.2;
</code>
<finding>
location: packages/payments/charge.ts:14
issue: VAT is applied with floating-point euros, so totals can be off by a cent.
severity: high
fix: keep amounts in integer cents and round once, e.g. Math.round(subtotalCents * 1.2).
</finding>
</example>

<example>
<code file="src/api/orders.ts">
try { await notifyWarehouse(order); } catch (err) { logger.warn("warehouse notify failed", { err }); }
</code>
<finding>none</finding>
<why>Not flagged: the error is logged and the warehouse sync job retries every 5 minutes,
so swallowing it here is the documented pattern in this service, not a bug.</why>
</example>

<example>
<code file="src/api/refunds.ts" coverage="tests cover amount > 0 only">
if (amount <= 0) { return reject("invalid amount"); }
</code>
<finding>
location: src/api/refunds.ts:31
issue: the rejection branch for zero or negative amounts has no test, and it guards money.
severity: medium
fix: add a test that a refund of 0 and of -5 is rejected without calling the payment API.
</finding>
<why>Flagged although overall coverage of the file is high: the gap is a whole branch, on a payment path.</why>
</example>
</examples>
  • The first example fixes the format: location, issue, severity, fix, the same four lines every time, so findings can be parsed and compared.
  • The second shows an acceptable pattern that a naive reviewer would flag (a caught and logged error), with the reason it's fine here. This is the guide's way of cutting false positives without banning a whole category.
  • The third settles an ambiguous case: a file with good overall coverage still has an untested branch, and on a payment path that's worth reporting. The <why> carries the reasoning the model should reuse.

Examples for extraction

Task 4.2Varied layouts, informal measurements, and honest nulls.

Extraction from real documents fails in two opposite ways: the model invents a value to fill a required field, or it returns nothing because the value was somewhere unexpected. Instructions ("use null if absent") help; examples that show where values hide, and when null really is the answer, help more.

invoice_fewshot.py (Python, anthropic SDK)Optional 
"""Few-shot extraction for supplier invoices that arrive in every layout."""
import json

import anthropic

client = anthropic.Anthropic()

INSTRUCTIONS = """Extract the invoice fields as JSON with keys supplier, invoice_number, po_number,
currency, lines (description, quantity, unit, unit_price) and total.
Use null for a field the document doesn't contain; never guess one.
Convert quantities to a number plus a unit (kg, m, pcs)."""

# Each example shows one way invoices differ, and what correct output looks like for it.
EXAMPLES = [
    ("Line table with a PO number in the header",
     "ALPINE TEXTILES Invoice INV-0412  PO: 7731\nRipstop nylon | 120 m | 4.10\nTotal EUR 492.00",
     {"supplier": "Alpine Textiles", "invoice_number": "INV-0412", "po_number": "7731", "currency": "EUR",
      "lines": [{"description": "Ripstop nylon", "quantity": 120, "unit": "m", "unit_price": 4.10}], "total": 492.00}),
    ("Prose invoice, informal measurement, no PO number",
     "Hi, as agreed: 2 x 1.5kg sacks of down at 95 quid each, so 190 all in. Invoice 88. Thanks, Peak Feathers",
     {"supplier": "Peak Feathers", "invoice_number": "88", "po_number": None, "currency": "GBP",
      "lines": [{"description": "Down, 1.5 kg sack", "quantity": 2, "unit": "pcs", "unit_price": 95.00}], "total": 190.00}),
    ("Totals only on a separate summary page",
     "Page 1: Buckles (black) 500 pcs @ 0.12\nPage 2: Summary - amount due USD 60.00, ref FastClip-2209",
     {"supplier": None, "invoice_number": "FastClip-2209", "po_number": None, "currency": "USD",
      "lines": [{"description": "Buckles (black)", "quantity": 500, "unit": "pcs", "unit_price": 0.12}], "total": 60.00}),
]


def system_prompt() -> str:
    shots = "\n".join(
        f'<example name="{name}">\n<document>\n{doc}\n</document>\n<output>{json.dumps(out)}</output>\n</example>'
        for name, doc, out in EXAMPLES)
    return f"{INSTRUCTIONS}\n\n<examples>\n{shots}\n</examples>"


def extract(document: str) -> dict:
    response = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=2000, system=system_prompt(),
        messages=[{"role": "user", "content": f"<document>\n{document}\n</document>"}],
    )
    return json.loads("".join(b.text for b in response.content if b.type == "text"))


if __name__ == "__main__":
    print(extract("TRAILWORKS LTD  inv no. TW/551  your order 7745\n3 rolls webbing (25mm) x 50 m @ 0.80/m\nTOTAL: 120.00 EUR"))
  • Varied structures: a line table, a chatty email and a two-page document with the total on a summary page. Each shows the same fields found in a different place, which is what fixes empty extractions from unusual layouts.
  • Informal measurements: "2 x 1.5kg sacks at 95 quid each" becomes quantity 2, unit pcs, price 95.00, currency GBP: the example shows the conversion instead of describing it.
  • Honest nulls: two examples have no PO number, and the third has no supplier name; the reference "FastClip-2209" isn't treated as one. That teaches null over a plausible guess.

The guide's other document example works the same way: for research papers, show one paper with inline citations and one with a bibliography, one with a methodology section and one with methods buried in the results, so Claude knows to look in both kinds of place.

Pitfalls

Task 4.2How examples go wrong.

  • Examples that disagree with the instructions (a total computed when the rules say not to guess): Claude tends to follow the example. Check every expected output against the rules.
  • Only easy cases: examples the model would have got right anyway add tokens and no information.
  • Accidental patterns: if every example is flagged, the reviewer learns to flag; if every invoice has a PO number, missing ones get invented.
  • Too many near-duplicates: they narrow the model to the listed cases instead of the judgement behind them.
  • Cost: examples are input tokens on every call; keep them in the stable part of the prompt so prompt caching covers them.

Key takeaways

  • Few-shot examples are the strongest fix when detailed instructions still give inconsistent format or quality; they show judgement as well as format, and Claude generalises from the reasoning to new cases.
  • Use a handful of targeted examples (the guide says 2 to 4; Claude's prompting guide 3 to 5): relevant, diverse, in <example> tags, aimed at the ambiguous cases, each with the reason for the choice.
  • In code review: one example per output format, at least one acceptable pattern that isn't flagged (with why), and the ambiguous cases such as branch-level coverage gaps.
  • In extraction: examples across varied layouts and informal formats, including real nulls, reduce both invented values and empty required fields.
  • Make sure examples agree with the instructions and don't all share an accidental trait.
