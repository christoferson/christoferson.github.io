2.3: Tools Across Agents and tool_choice

Which agent gets which tools, and how far you can steer whether Claude calls a tool at all: role-scoped tool sets for subagents, the Agent SDK options that make tools available or pre-approve them, and the tool_choice settings, which the newest models partly reject.

Overview

Task 2.3

Distribute tools appropriately across agents and configure tool choice.

The exam guide asks you to know that giving an agent too many tools makes its choices less reliable, that agents given tools outside their specialty tend to misuse them, that scoped access with a few limited cross-role tools works better, and what the tool_choice options do. In practice: restrict each subagent to the tools its role needs, replace generic tools with constrained ones, force a particular first tool where needed, and use any to guarantee some tool is called. That last point now needs care, because the newest models reject forced tool use.

Sources: the Claude API tool-use documentation (define tools, tool search, parallel tool use, strict tool use, errors, release notes), the Claude Agent SDK documentation (subagents, permissions, MCP, Python reference) and Anthropic's engineering posts on tools and on its multi-agent research system, checked on 8 November 2026, paraphrased. The SDK code was built and inspected with claude-agent-sdk 0.2.179, but not run as an agent.

Running example. The shop's support system has a coordinator that talks to the customer, an order-lookup subagent, and a refunds subagent. Order tools and refund tools come from two MCP servers.

Fewer tools per agent

Task 2.3Why role-specific tool sets help.

  • Selection degrades with numbers. The tool search docs say accuracy falls once more than about 30 to 50 tools are loaded. (The exam guide's own illustration is far smaller: 18 tools against 4 or 5.) Definitions also cost context: Anthropic's example five-server MCP setup took about 55,000 tokens.
  • Off-role tools get misused. Anthropic's tool-writing guide warns that too many or overlapping tools distract agents from efficient strategies, and its multi-agent research post gives each subagent "clear task boundaries" and guidance on which tools and sources to use.
  • Constrained beats generic. Rather than a general fetch_url, give an agent a narrow tool that does one job safely, such as one that only loads documents from approved locations. The tool-writing guide makes the same point: build a few tools shaped around real workflows instead of wrapping every endpoint.
  • Limited cross-role tools. If the refunds agent often needs to check an order, give it just the one read-only order tool it needs, not the whole order toolkit; anything more complex goes back through the coordinator. This is the exam guide's framing; the docs support it through per-subagent tool lists.

Scoping tools per subagent

Task 2.3Giving each subagent only its role's tools in the Agent SDK.

support_agents.py (Python, Agent SDK) 
from claude_agent_sdk import (
    AgentDefinition,
    ClaudeAgentOptions,
)


def server(name):
    # stdio MCP server for one domain
    return {name: {
        "type": "stdio",
        "command": "python",
        "args": [f"{name}_mcp.py"],
    }}


agents = {
    "order-lookup": AgentDefinition(
        description=(
            "Order status and tracking"
            " questions. Read-only."),
        prompt=(
            "Look up orders and report"
            " status. Never refund."),
        # inline server: subagent only
        mcpServers=[server("orders")],
        tools=["mcp__orders__*"],
        model="haiku",
    ),
    "refunds": AgentDefinition(
        description=(
            "Refund and return requests"
            " for gear orders."),
        prompt=(
            "Check the order, then refund"
            " within the 60-day policy."),
        mcpServers=[
            server("orders"),
            server("refunds"),
        ],
        tools=[
            # one cross-role tool only
            "mcp__orders__get_order",
            "mcp__refunds__issue_refund",
        ],
        model="sonnet",
    ),
}

options = ClaudeAgentOptions(
    agents=agents,
    # coordinator's built-ins: Agent
    tools=["Agent"],
    # pre-approval only, not a limit
    allowed_tools=[
        "mcp__orders__*",
        "mcp__refunds__issue_refund",
    ],
    # anything else that asks: denied
    permission_mode="dontAsk",
)
  • description is what the coordinator matches tasks against; prompt is the subagent's system prompt.
  • tools lists exactly what the subagent can use. Leave it out and the subagent inherits every available tool.
  • Inline mcpServers connect only for that subagent: per the docs, the subagent gets the tools and the parent doesn't, which also keeps their descriptions out of the coordinator's context.
  • MCP tool names are mcp__<server>__<tool>, where the server name is the key you gave it; mcp__orders__* means every tool from that server.
  • Note the naming: AgentDefinition fields stay camelCase in Python (mcpServers, disallowedTools), while ClaudeAgentOptions uses snake_case (allowed_tools).

Available or pre-approved

Task 2.3The three options that sound alike and do different things.

OptionControlsWatch out
tools (and AgentDefinition.tools)Which tools exist for the agentAt session level it covers built-in tools only, not MCP tools
disallowed_toolsDeny rules: a bare name removes the tool; a scoped rule such as Bash(rm *) blocks matching calls in every mode"mcp__*" removes every MCP tool
allowed_toolsWhich calls run without askingThe docs: it "does not restrict Claude to only these tools". Unlisted tools still exist and fall back to the permission mode

The docs' locked-down pattern is allowed_tools plus permission_mode="dontAsk": listed tools run, anything that would ask is refused. MCP tools always need approval; acceptEdits doesn't cover them. A wildcard in allowed_tools only works after a literal server prefix: mcp__orders__* works, a bare mcp__* is silently ignored.

"allowedTools must include Task." The exam guide says a coordinator needs "Task" in allowedTools to start subagents. The tool is now called Agent (renamed in Claude Code 2.1.63; Task still works as an alias), and since allowed_tools only pre-approves, and Agent doesn't ask before running, what really controls delegation is whether Agent is in the agent's tools. The docs' examples still list "Agent" in allowed_tools, so "include it" remains the expected exam answer.

tool_choice

Task 2.3The four settings in the Claude API.

SettingMeaning
{"type": "auto"}Claude decides whether to call a tool (the default when tools are provided)
{"type": "any"}Claude must call one of the tools, any of them
{"type": "tool", "name": "..."}Claude must call that tool
{"type": "none"}No tools (the default when none are provided)

With any or a named tool, the API prefills the response, so Claude writes no text and does no thinking before the tool call. disable_parallel_tool_use: true goes inside tool_choice: with auto it means at most one call per response; with forced use, exactly one. Changing tool_choice between requests invalidates cached message blocks, though cached tools and system prompt survive.

Request with auto and a strict tool (JSON) 
{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "tool_choice": {"type": "auto"},
  "tools": [{
    "name": "lookup_order",
    "description": "...",
    "strict": true,
    "input_schema": {
      "type": "object",
      "properties": {
        "order_id": {"type": "string"}
      },
      "required": ["order_id"],
      "additionalProperties": false
    }
  }],
  "messages": [{
    "role": "user",
    "content": "Where is ORD-104233?"
  }]
}

When forcing isn't allowed

Task 2.3Which models accept forced tool use, and what to do instead.

ModelsForcing a tool
Claude Opus 5.5, Sonnet 5.5, Fable 5.1, Mythos 5.1Rejected with a 400 error, whatever the thinking settings (released September 2026)
Claude Haiku 5.5, Opus 5 and earlier modelsAccepted (but a forced call skips thinking)
Any model with manual extended thinking enabledRejected

The docs' alternatives on models that reject forcing: use auto with strict: true tools, or structured outputs (output_config.format) when you need a fixed JSON response rather than a tool call (task 4.3). Prompting still steers auto: "Call extract_metadata first" in the user message. For the guide's pattern of forcing a first step and then letting Claude continue, force the first tool and switch to auto afterwards on models that allow it; elsewhere, instruct it and offer only that tool on the first request.

strict doesn't force a call. Strict tool use guarantees that if Claude calls the tool, the input matches the schema and the tool name is valid. With auto, Claude may still answer in plain text. Only any or a named tool guarantees a call, on the models that support them. The exam guide predates the September 2026 releases and presents forcing as always available.

Large tool catalogs

Task 2.3Keeping hundreds of tools available without loading them all.

When an agent really does need a large catalog (many MCP servers, say), the tool search tool avoids loading every definition. Mark tools with defer_loading: true; Claude searches by name and description and only the matching definitions (five by default) are loaded. The docs report context savings of typically over 85%. Rules: you still send every definition with each request, at least one tool must stay non-deferred, and the three to five most-used tools should stay loaded. In Claude Code and the Agent SDK, tool search is on by default for MCP tools.

Choosing the right fix. Too many tools for one role: split the work across subagents with scoped tool lists. A genuinely large catalog in one agent: tool search. The wrong tool chosen between two similar ones: better names and descriptions (task 2.1), not forcing.

Key takeaways

  • Fewer, role-specific tools per agent improve selection (the docs' threshold is about 30 to 50 tools); give cross-role access as one narrow tool and route complex cases through the coordinator.
  • AgentDefinition.tools sets a subagent's tools (omit it and it inherits everything); inline mcpServers keep a server's tools out of the coordinator.
  • tools = available (built-ins at session level), disallowed_tools = removed or denied, allowed_tools = pre-approved, not restricted. MCP names are mcp__server__tool.
  • tool_choice: auto, any, a named tool, none. Forced use skips text and thinking; disable_parallel_tool_use sits inside tool_choice.
  • Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 reject any and named tools: use auto plus strict, prompting, or structured outputs. strict validates inputs but doesn't force a call.
  • The subagent tool is now Agent (formerly Task). Large catalogs: tool search with defer_loading.
