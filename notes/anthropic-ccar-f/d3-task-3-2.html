3.2: Slash Commands and Skills

Packaging a team's repeatable tasks as skills that anyone can run with a slash command, or that Claude picks up when they're relevant: where they live, how their frontmatter controls who can run them and with which tools, and when to run one in its own subagent.

Overview

Task 3.2

Create and configure custom slash commands and skills.

The exam guide asks you to know project versus personal locations for commands and skills, the SKILL.md frontmatter options context: fork, allowed-tools and argument-hint, how to keep personal variants from affecting teammates, and when a skill (on demand) beats CLAUDE.md (always loaded). Several of the guide's descriptions are now out of date, as noted below.

Sources: the Claude Code documentation (skills, commands, subagents, permissions), the Claude Code changelog, and Anthropic's Agent Skills documentation and engineering post, checked on 8 November 2026 against Claude Code 2.1.303, paraphrased.

Running example. The shop's team writes release notes for every deployment and reviews every pull request against the same checklist. They want both as commands anyone on the team can run.

Commands became skills

Task 3.2The relationship between .claude/commands and .claude/skills.

The docs say custom commands "have been merged into skills". Since Claude Code 2.1.3, a file .claude/commands/deploy.md and a folder .claude/skills/deploy/SKILL.md both create /deploy and work the same way. Command files keep working, but they're the older format; a skill can also hold supporting files (templates, references, scripts) in its folder.

Where skills live

Task 3.2Project, personal and other scopes, and which wins.

ScopePathReaches
Project.claude/skills/<name>/SKILL.mdThe team, once committed
Personal~/.claude/skills/<name>/SKILL.mdOnly you, in all your projects
EnterpriseThe managed settings folderEveryone in the organization
Plugin<plugin>/skills/<name>/SKILL.mdAnyone who installs it; run as /plugin:skill

When two skills share a name, enterprise beats personal, and personal beats project. A plugin's skills are namespaced, so they never collide.

Personal variants get their own name. If a developer copies the team's release-notes into ~/.claude/skills/release-notes/ to tweak it, their copy silently replaces the team version, for them only. Naming it my-release-notes keeps both available and leaves no confusion about which one ran.

A project skill

Task 3.2A complete SKILL.md with arguments, shell context and frontmatter.

.claude/skills/release-notes/SKILL.md 
---
name: release-notes
description: Draft release notes for the
  shop from merged PRs. Use when asked
  for a changelog or release summary.
argument-hint: "[from-tag] [to-tag]"
disable-model-invocation: true
context: fork
allowed-tools:
  - Bash(git log *)
  - Bash(git tag *)
  - Read
  - Edit(docs/releases/**)
---

# Release notes: $0 to $1

Recent tags:
!`git tag --sort=-v:refname | head -5`

1. List commits between $0 and $1
   with `git log --oneline $0..$1`.
2. Group them: Features, Fixes,
   Checkout, Payments, Other.
3. Follow [template.md](template.md).
4. Write docs/releases/$1.md and
   return a five-line summary.

Run it as /release-notes v2.3.0 v2.4.0. The pieces:

  • Arguments. $ARGUMENTS is everything typed after the command; $0, $1 and so on are single arguments, counting from zero.
  • Shell injection. A line like !`git tag ...` runs before Claude sees the skill, and its output replaces the line. A command that fails, or isn't allowed, stops the skill; that's why the git commands are listed in allowed-tools.
  • Supporting files. template.md sits in the skill's folder; Claude reads it only when the instructions point to it.
.claude/commands/review-pr.md (older format) 
---
description: Review a pull request
  against the shop's checklist
argument-hint: "[pr-number]"
allowed-tools: Bash(gh pr *)
---

Review PR #$ARGUMENTS. Read its diff
with `gh pr diff $ARGUMENTS`, then
check it against
@docs/review-checklist.md.
Report bugs, missing tests and risky
changes to payments code.

Frontmatter

Task 3.2The fields that control discovery, invocation and tools.

FieldEffect
descriptionWhat the skill does and when to use it. Claude matches requests against it, so it decides whether the skill is ever picked
argument-hintA hint shown in autocomplete after the command name, such as [pr-number]
allowed-toolsTools that may run without a permission prompt during the turn that invokes the skill
disallowed-toolsTools removed from Claude while the skill is active (since 2.1.152)
disable-model-invocation: trueOnly a person can run it with /name; Claude can't, and its description isn't loaded at all
user-invocable: falseHidden from the / menu; only Claude uses it, as background knowledge
context: fork and agentRun the skill in a separate subagent of the given type (below)
model, effortModel and effort level for that turn
pathsGlobs limiting when Claude may load the skill automatically (task 3.3)

allowed-tools grants; it doesn't restrict. The exam guide describes allowed-tools as restricting tool access during a skill. The current docs say the opposite: it pre-approves the listed tools so they run without asking, and "does not restrict which tools are available". To take tools away, use disallowed-tools, a subagent's tools list, or deny rules in settings. In an exam question, the guide's intended answer is allowed-tools as the scoping mechanism; in practice, know the difference.

Other differences from the guide. The guide says argument-hint prompts developers for missing parameters; the docs describe only an autocomplete hint. Positional arguments now count from zero ($0 is the first), so don't assume $1 is the first argument. And skills built with Claude Code-only fields such as argument-hint or context are rejected if uploaded to claude.ai or the Skills API, which accept only the core fields.

Running in a fork

Task 3.2Isolating a skill's verbose or exploratory work from the main conversation.

With context: fork, invoking the skill starts a new subagent (general-purpose unless agent names another, such as Explore), and the skill's text becomes its prompt. The subagent's tool calls and output stay in its own context; only its result comes back. That keeps long git logs, searches or test output out of the main conversation.

  • The subagent doesn't see your conversation, so the skill must be a self-contained task. A skill that only lists guidelines gives a fork nothing to do.
  • Since 2.1.218 forked skills run in the background by default; background: false makes the turn wait for the result.
  • Edits made by a background fork aren't covered by /rewind, so rely on Git for those.

How skills load

Task 3.2Progressive disclosure, and choosing between a skill and CLAUDE.md.

  1. AlwaysEach skill's name and description, about 100 tokens per skill, so Claude knows what's available.
  2. When invokedThe SKILL.md body, which then stays in the conversation.
  3. When neededSupporting files the instructions point to; scripts run, and only their output enters context.

That's the reason to prefer a skill over CLAUDE.md for task-specific procedures: CLAUDE.md is loaded in full every session, while a skill costs almost nothing until it's used. Universal standards ("money is integer cents") go in CLAUDE.md; the release-notes procedure goes in a skill.

Built-in commandPurpose
/skills, /reload-skillsList skills and their cost; rescan the skill folders
/memory, /initEdit memory files; generate a CLAUDE.md (task 3.1)
/compact, /clear, /contextSummarize, reset or inspect the context
/planEnter plan mode (task 3.4)
/hooks, /mcp, /permissionsView hooks, manage MCP servers, edit permission rules

Key takeaways

  • Commands and skills are one system: .claude/commands/x.md and .claude/skills/x/SKILL.md both make /x; skills are the current format and win on a name clash.
  • Project skills (.claude/skills/, committed) reach the team; personal ones (~/.claude/skills/) reach only you. Personal beats project on the same name, so give variants a different name.
  • description drives discovery; argument-hint is an autocomplete hint; $ARGUMENTS and zero-based $0, $1 insert arguments; !`cmd` injects command output first.
  • allowed-tools pre-approves tools for the turn (the guide calls it restricting); disallowed-tools actually removes tools.
  • disable-model-invocation: true means user-only; user-invocable: false means Claude-only.
  • context: fork runs the skill in a subagent without your conversation history, keeping verbose output out of the main context; background by default since 2.1.218.
  • Only names and descriptions are always loaded, so put on-demand procedures in skills and universal standards in CLAUDE.md.
