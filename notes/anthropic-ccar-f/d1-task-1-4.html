1.4: Enforced Workflows and Handoffs

Making a multi-step process happen in the right order when it has to: instructions for what can bend, code gates for what can't, splitting a message with several problems into separate investigations, and handing a case to a person with everything they need.

Overview

Task 1.4

Implement multi-step workflows with enforcement and handoff patterns.

The exam guide asks you to know the difference between enforcing a workflow's order in code (hooks, prerequisite gates) and guiding it with the prompt, that prompt instructions alone have a non-zero failure rate when compliance must be deterministic (identity checks before money moves), and what a structured handoff to a person contains. In practice it asks you to block a downstream tool until its prerequisite has succeeded, split a customer message with several concerns into items investigated in parallel and answered together, and write handoff summaries for human agents who can't see the conversation. Hooks for normalising tool data are task 1.5; escalation design in general is task 5.2.

Use the prompt for order that can bend, and code for rules that must always hold

Task 1.4When an instruction is enough, and when only code will do.

A system prompt line such as "always verify the customer before refunding" is followed almost every time. Almost is the problem: an instruction is a strong influence on the model, not a guarantee, so across thousands of conversations some will skip the step, through an unusual phrasing, a long context, or a customer who says "I'm already verified". That non-zero failure rate is acceptable for preferences and dangerous for obligations.

  • Prompt guidance suits ordering that can bend: greet first, summarise at the end, suggest accessories after a sale. A miss is a style problem.
  • Programmatic enforcement suits rules that must hold every time: identity verification before refunds or account changes, approval above a limit, no deletion without a backup. Code checks the condition before the action runs and refuses it otherwise, whatever the model decided.

Use both together: the prompt tells Claude the intended order so it usually gets it right first time, and the gate catches the rare case where it doesn't. A gate without the instruction works but wastes turns on refused calls; an instruction without the gate is the exam's classic wrong answer for a compliance requirement.

Block a step in code until its prerequisite has really happened

Task 1.4Blocking process_refund until get_customer has returned a verified customer ID.

Take a support agent with three tools, get_customer, process_refund and escalate_to_human, and a rule that no money moves until the customer has been verified, with refunds over $200 going to a person.

refund_gate.py (Python, claude-agent-sdk)Optional 
"""Support agent with a code-enforced prerequisite: no refund until get_customer has verified the customer."""
import json

import anyio
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher, ResultMessage, create_sdk_mcp_server, query, tool

CUSTOMERS = {"sam@example.com": {"customer_id": "C-2041", "verified": True, "orders": ["A1042"]}}
REFUND_LIMIT = 200.00          # above this, a person decides
verified_ids: set[str] = set()  # filled only by get_customer, never by the model
handoffs: list[dict] = []


@tool("get_customer", "Look up and verify a customer by email. Call this before any refund.", {"email": str})
async def get_customer(args):
    customer = CUSTOMERS.get(args["email"].lower())
    if customer is None:
        return {"content": [{"type": "text", "text": "No customer with that email."}], "is_error": True}
    if customer["verified"]:
        verified_ids.add(customer["customer_id"])  # the gate opens here, in code
    return {"content": [{"type": "text", "text": json.dumps(customer)}]}


@tool("process_refund", "Refund an order for a verified customer.",
      {"customer_id": str, "order_id": str, "amount": float, "reason": str})
async def process_refund(args):
    return {"content": [{"type": "text", "text": f"Refunded {args['amount']:.2f} on {args['order_id']}."}]}


@tool("escalate_to_human", "Hand the case to a human agent, who cannot see this conversation.",
      {"type": "object",
       "properties": {"customer_id": {"type": "string"}, "order_id": {"type": "string"},
                      "issue_summary": {"type": "string"}, "root_cause": {"type": "string"},
                      "refund_amount": {"type": "number"}, "steps_taken": {"type": "array", "items": {"type": "string"}},
                      "recommended_action": {"type": "string"}},
       "required": ["customer_id", "issue_summary", "root_cause", "refund_amount", "recommended_action"]})
async def escalate_to_human(args):
    handoffs.append(args)  # goes to the human queue as a self-contained case
    return {"content": [{"type": "text", "text": "Escalated. Tell the customer a person will reply within one business day."}]}


def deny(reason: str) -> dict:
    return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny",
                                   "permissionDecisionReason": reason}}


async def refund_gate(input_data, tool_use_id, context):
    args = input_data["tool_input"]
    if args.get("customer_id") not in verified_ids:
        # The reason goes back to Claude, so it can recover by calling get_customer.
        return deny("Blocked: call get_customer and get a verified customer_id before refunding.")
    if args.get("amount", 0) > REFUND_LIMIT:
        return deny(f"Blocked: refunds over {REFUND_LIMIT:.2f} need a person. Use escalate_to_human.")
    return {}


SHOP = create_sdk_mcp_server(name="shop", tools=[get_customer, process_refund, escalate_to_human])

OPTIONS = ClaudeAgentOptions(
    system_prompt="You handle refunds for an outdoor-gear shop. Verify the customer before any refund.",
    mcp_servers={"shop": SHOP},
    allowed_tools=["mcp__shop__get_customer", "mcp__shop__process_refund", "mcp__shop__escalate_to_human"],
    # The prompt asks for the right order; this hook makes it impossible to skip. A crash blocks, not allows.
    hooks={"PreToolUse": [HookMatcher(matcher="mcp__shop__process_refund", hooks=[refund_gate], on_failure="block")]},
)


async def main(request: str) -> None:
    async for message in query(prompt=request, options=OPTIONS):
        if isinstance(message, ResultMessage):
            print(message.result)


if __name__ == "__main__":
    anyio.run(main, "I'm sam@example.com. Please refund the 89.00 tent footprint on order A1042, it arrived torn.")
  • The state comes from code. Only the get_customer tool, running your code, adds an ID to verified_ids. A customer ID the model invents or copies from the customer's message fails the gate because it was never verified.
  • The hook runs before the tool. A PreToolUse hook matched to mcp__shop__process_refund (the naming pattern for tools on an MCP server) returns permissionDecision: "deny" when the prerequisite isn't met.
  • The refusal is useful. permissionDecisionReason goes back to Claude, so it can recover by calling get_customer, or route a large refund to escalate_to_human.
  • Per conversation in production. The example keeps one set for the process; a real service keys verified IDs by session or conversation so one customer's verification can't open the gate for another.

On the Messages API without the SDK, the same gate goes in your own tool dispatcher: before running process_refund, check the verified set and return an error tool_result explaining what's missing (task 1.1's loop).

Configure the gate so it fails closed

Task 1.4The details that make a hook a reliable control.

  • Failures: by default, a hook callback that raises an error lets the tool call carry on to the normal permission checks. For a control, set on_failure="block" on the matcher (Python SDK 0.2.177 and later) so a crashing guard blocks instead; a callback that returns nothing also counts as failing.
  • Timeouts: a PreToolUse callback that runs past its timeout (600 seconds by default) blocks the call.
  • Several hooks: matching hooks run in parallel and the most restrictive decision wins (deny over defer, ask and allow), so independent checks can't undo each other.
  • Order in the permission flow: hooks run first; a hook's deny holds even in bypassPermissions mode, while a hook's allow doesn't skip deny rules.
  • Matchers match tool names only. To gate on an argument (an amount, a file path), check tool_input inside the callback, as the example does with amount.

Telling the model isn't enforcing. Answer choices that add "IMPORTANT: never refund unverified customers" to the prompt, add a few-shot example, or ask Claude to confirm verification in its reply all reduce the failure rate but leave it above zero. Only an answer where code blocks the call satisfies "must always".

Split a request with several problems, investigate in parallel, answer once

Task 1.4Decompose, investigate in parallel with shared context, answer once.

"My order arrived damaged, I was charged twice for another order, and can you change my delivery address?" is three problems. Handled as one blob, the agent tends to solve the first and skim the rest. Handled one per message, the customer gets three replies and repeats themselves. The guide's pattern:

multi_concern.py (Python, anthropic SDK)Optional 
"""Split a multi-concern message into items, investigate each in parallel with shared context, then answer once."""
import json
from concurrent.futures import ThreadPoolExecutor

import anthropic

client = anthropic.Anthropic()

SPLIT_SCHEMA = {
    "type": "object",
    "properties": {"items": {"type": "array", "items": {
        "type": "object",
        "properties": {"id": {"type": "string"}, "concern": {"type": "string"}, "order_id": {"type": ["string", "null"]}},
        "required": ["id", "concern", "order_id"], "additionalProperties": False}}},
    "required": ["items"], "additionalProperties": False,
}


def text_of(response) -> str:
    return "".join(b.text for b in response.content if b.type == "text")


def split(message: str) -> list[dict]:
    response = client.messages.create(
        model="claude-haiku-5-5", max_tokens=1000,
        system="List each separate thing the customer wants resolved, one item per concern.",
        messages=[{"role": "user", "content": message}],
        output_config={"format": {"type": "json_schema", "schema": SPLIT_SCHEMA}},
    )
    return json.loads(text_of(response))["items"]


def investigate(item: dict, shared: str) -> dict:
    # Every investigation gets the same shared context: the customer record and the original message.
    response = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=1500,
        system="Investigate one customer concern. State the finding and the action you'd take.",
        messages=[{"role": "user", "content": f"{shared}\n<concern id=\"{item['id']}\">{item['concern']}</concern>"}],
    )
    return {"id": item["id"], "finding": text_of(response)}


def resolve(message: str, customer: dict) -> str:
    items = split(message)
    shared = f"<customer>{json.dumps(customer)}</customer>\n<message>{message}</message>"
    with ThreadPoolExecutor(max_workers=4) as pool:
        findings = list(pool.map(lambda it: investigate(it, shared), items))
    # One reply that covers every concern, not one reply per concern.
    response = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=1500,
        system="Write one reply to the customer that resolves every concern below, in order.",
        messages=[{"role": "user", "content": f"{shared}\n<findings>{json.dumps(findings)}</findings>"}],
    )
    return text_of(response)


if __name__ == "__main__":
    print(resolve("My order A1042 arrived with a torn footprint, I was charged twice for A1050, "
                  "and can you change my delivery address for A1061?",
                  {"customer_id": "C-2041", "name": "Sam", "orders": ["A1042", "A1050", "A1061"]}))
  1. DecomposeSplit the message into distinct items; structured output keeps the list machine-readable.
  2. Investigate in parallelOne investigation per item, run at the same time, each given the same shared context (customer record, original message) so none has to fetch it again or works from a different picture.
  3. Synthesise one resolutionA single reply that addresses every item, so nothing is dropped and the customer reads one answer.

The investigations here are separate calls; in an agent they could equally be subagents (task 1.2) or parallel tool calls. The point is the shape: split, share context, investigate side by side, merge.

Hand over to a person with a structured summary

Task 1.4Escalating mid-process to a person who can't see the transcript.

A human agent who picks up an escalated case usually sees a ticket, not the conversation. "Customer is upset about a refund, please help" forces them to start over and ask the customer to repeat everything. A structured handoff makes the case self-contained, with fields the escalation tool's schema requires:

  • Customer details: the verified customer ID and the order involved.
  • Issue summary: what the customer wants, in a sentence.
  • Root cause: what the investigation found ("damaged in transit", "duplicate charge from a retried payment").
  • Refund amount or other value at stake.
  • Steps taken: what the agent already checked or did, so it isn't repeated.
  • Recommended action: what the agent would do if it were allowed to.

In the example, escalate_to_human takes exactly these fields and the gate sends refunds over the limit there. Making them required in the tool's schema is itself enforcement: the agent can't escalate without stating a root cause and a recommendation. After escalating, the agent tells the customer what happens next.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A system prompt says “always verify the customer before refunding”, and audits find a few refunds were issued without verification. What fixes it?
  1. A. Repeat the instruction in capitals
  2. B. A gate in code that blocks the refund tool until a verification tool has recorded the customer
  3. C. Add a few-shot example
  4. D. Ask Claude to confirm verification in its reply
Answer
B
Why
An instruction is followed almost every time, which isn’t enough for a rule that must always hold. Code that checks state the model can’t fake enforces it.
Question 2
Scenario
A PreToolUse hook enforcing a compliance rule raises an exception. With default settings, what happens to the tool call, and what should be set?
  1. A. The call is blocked automatically
  2. B. The call carries on to the normal permission checks; set on_failure="block" on the matcher
  3. C. The session ends
  4. D. The hook retries forever
Answer
B
Why
By default a failing hook callback doesn’t block. For a control, configure it to block on failure so a crash can’t open the gate.
Question 3
Scenario
A customer writes about three unrelated problems in one message. How should the agent handle it?
  1. A. Answer the first problem only
  2. B. Split the message into items, investigate them in parallel with the same shared context, and reply once covering all of them
  3. C. Ask the customer to send three messages
  4. D. Escalate every multi-part message
Answer
B
Why
Decomposing, investigating side by side and answering once keeps any item from being dropped and gives the customer one complete reply.
Question 4
Scenario
An agent escalates to a person with the note “customer needs help”. What should the handoff contain?
  1. A. Nothing more; the person can ask the customer
  2. B. A structured summary: who the customer is, the issue, what was checked and tried, and what is needed
  3. C. The full transcript only
  4. D. The model’s confidence score
Answer
B
Why
A structured handoff lets the person act without re-reading the conversation or asking the customer to repeat themselves.

Key takeaways

  • Prompt instructions guide order but fail occasionally; where compliance must be deterministic (verification before money moves), enforce it in code. Use the prompt and the gate together.
  • A prerequisite gate blocks the downstream tool until the prerequisite succeeded, using state your code set (a verified ID from get_customer), not anything the model asserts.
  • In the Agent SDK: a PreToolUse hook matched to the tool returns permissionDecision: "deny" with a reason Claude can act on; set on_failure="block"; hooks combine most-restrictive-wins and a deny holds in every mode.
  • Multi-concern requests: decompose into items, investigate in parallel with the same shared context, then write one unified resolution.
  • Handoffs to people must be self-contained: customer ID, issue, root cause, amount, steps taken, recommended action, enforced as required fields of the escalation tool.
