5.1: Preserving Context in Long Interactions

Keeping the details that matter through a long conversation: exact amounts and dates that a summary would blur, tool results cut down before they pile up, and inputs laid out so nothing important sits unnoticed in the middle.

Overview

Task 5.1

Manage conversation context to preserve critical information across long interactions.

The exam guide asks you to know four things. Progressive summarisation turns numbers, percentages, dates and what the customer said they expect into vague prose. Models handle the start and end of a long input reliably but can miss findings in the middle. Tool results pile up and use tokens far out of proportion to their relevance. And each request has to carry the complete conversation history. In practice it asks you to:

  • keep transactional facts in a persistent block outside the summarised history, with one entry per issue when a session covers several;
  • trim tool output to the relevant fields;
  • put a key-findings summary first in aggregated inputs, with section headers for the details;
  • make subagents and upstream agents return structured data with metadata rather than long prose.

Exploring a large codebase has its own context problems, covered in task 5.4; tracking where each claim came from is task 5.6.

Sources: the Claude API documentation on context windows, compaction, context editing and long-context prompting, checked on 19 November 2026 and paraphrased. The code is my own and was tested with anthropic 2.10.0 against a mocked API.

Running example. A customer of the outdoor-gear shop spends an hour with the support agent on two orders: a torn tent footprint they want refunded, and a stove that never arrived. Separately, a research agent combines reports from several subagents before the shop decides what to stock.

How context fills up

Task 5.1Full history every request, and everything counts.

The Messages API keeps no conversation state. Each request's input is all the previous turns plus the new message, and your application sends it. If you drop earlier turns, Claude no longer knows what was agreed, so the guide's rule is to send the complete history. Everything in the request counts against the context window: the system prompt, every message including tool results and documents, the tool definitions, and the output (thinking included). Cached prefixes count too; caching changes the price, not the size.

Current models have a 1M-token window, so running out is rarely the first problem. The docs describe context rot: as the token count grows, accuracy and recall degrade. What you put in the window matters as much as how big it is.

What summaries lose

Task 5.1Progressive summarisation and its blind spots.

The usual fix for a long history is to summarise older turns, often repeatedly. Each round makes the text shorter and vaguer. "Refund of 89.00 to the card by Friday 20 November for order A1042" becomes "customer wants a refund", and the next round may drop even that. The things that disappear are the ones the agent later needs to be exact about: amounts, percentages, dates, order numbers, statuses, and what the customer said they expect.

"Write a better summary prompt" isn't enough on its own. Asking the summariser to keep numbers helps, but every round is another chance to lose them. The guide's fix is structural: keep the exact values somewhere that never gets summarised.

A case facts block

Task 5.1Exact facts outside the summary, one entry per issue.

case_context.py (Python, anthropic SDK)Optional 
"""Long support conversations: exact case facts kept outside the summarised history, and lean tool results."""
import json

import anthropic

client = anthropic.Anthropic()

STATIC_SYSTEM = {"type": "text", "text": "You resolve returns and refunds for an outdoor-gear shop.",
                 "cache_control": {"type": "ephemeral"}}  # stable prefix: cached

RETURN_FIELDS = ("order_id", "status", "delivered_at", "items", "amount_paid", "payment_method", "return_window_days")


def trim_order(order: dict) -> dict:
    """The order API returns 40-odd fields; only these matter for a return."""
    return {k: order[k] for k in RETURN_FIELDS if k in order}


class Case:
    def __init__(self):
        self.facts: dict[str, dict] = {}   # one entry per issue, keyed by order ID: exact values, never summarised
        self.messages: list[dict] = []
        self.summary = ""                  # older turns, condensed

    def record_order(self, order: dict) -> str:
        lean = trim_order(order)
        self.facts.setdefault(lean["order_id"], {}).update(
            {k: lean[k] for k in ("status", "amount_paid", "delivered_at") if k in lean})
        return json.dumps(lean)            # what goes into the tool result, and so into history

    def record_expectation(self, order_id: str, expectation: str):
        self.facts.setdefault(order_id, {})["customer_expects"] = expectation   # in the customer's words

    def system(self) -> list[dict]:
        facts = "<case_facts>\n" + json.dumps(self.facts, indent=1) + "\n</case_facts>"
        summary = f"<earlier_conversation>{self.summary}</earlier_conversation>" if self.summary else ""
        return [STATIC_SYSTEM, {"type": "text", "text": facts + summary}]

    def compact(self, keep_last: int = 6):
        """Summarise older turns, but the facts block keeps every number and date verbatim."""
        if len(self.messages) <= keep_last:
            return
        old, self.messages = self.messages[:-keep_last], self.messages[-keep_last:]
        response = client.messages.create(
            model="claude-haiku-5-5", max_tokens=800,
            system="Summarise this support conversation in a few sentences. Numbers, dates and order IDs are "
                   "kept separately, so describe what was discussed and decided.",
            messages=[{"role": "user", "content": json.dumps(old, default=str)}],
        )
        self.summary = "".join(b.text for b in response.content if b.type == "text")

    def ask(self, text: str) -> str:
        self.messages.append({"role": "user", "content": text})
        response = client.messages.create(model="claude-sonnet-5-5", max_tokens=2000,
                                          system=self.system(), messages=self.messages)  # full recent history every time
        reply = "".join(b.text for b in response.content if b.type == "text")
        self.messages.append({"role": "assistant", "content": reply})
        return reply
  • Facts are extracted when they appear: when an order lookup returns, its status, amount and delivery date go into the facts store. When the customer states an expectation, it's recorded in their own words.
  • The block goes into every request, in the system prompt, next to the summary of older turns. Compacting the history never touches it.
  • One entry per issue: the store is keyed by order ID, so the footprint refund and the missing stove stay separate. Two orders' amounts and statuses can't be blended into one. That's the guide's structured issue layer for multi-issue sessions.
  • The rest stays intact: recent turns are sent word for word. The static instructions are a cached prefix, and the facts block, which changes, comes after them.

Trimming tool results

Task 5.1Keep only the fields the task needs, before they reach history.

An order lookup can return 40-odd fields: warehouse codes, internal flags, marketing attributes. For a return, perhaps seven matter. Every tool result stays in the history and is re-sent on every later turn, so ten lookups of 40 fields cost far more context than they're worth, and the relevant values get buried. In the example, trim_order keeps only the return-relevant fields before the result goes into the conversation. The trimming happens in your code, in the tool handler or a post-tool hook (task 1.5), before the result is added to history.

This is the tool-design advice from task 2.1 seen from the other side: tools should return high-signal information, and when you don't control the API behind a tool, you filter its output yourself.

Position effects

Task 5.1Key findings first, details under clear headers.

The guide calls it the "lost in the middle" effect: in a long input, material at the start and end is processed reliably, but findings in the middle can be missed. When a synthesis step receives a long stack of subagent reports, the one report that matters may be fourth of nine. Claude's long-context prompting advice points the same way. Put long material at the top and the question at the end (Anthropic measured up to 30% better answers that way), and wrap each document in its own tags.

synthesis_input.py (Python)Optional 
"""Build the input for a synthesis step from many subagent reports: key findings first, details in labelled sections."""
import json


def build_input(question: str, reports: list[dict]) -> str:
    """reports: structured subagent outputs, each with findings that carry their own metadata:
    {"agent": ..., "findings": [{"fact", "source", "date", "method", "relevance"}]}"""
    findings = [dict(f, agent=r["agent"]) for r in reports for f in r["findings"]]
    key = sorted(findings, key=lambda f: -f["relevance"])[:5]
    top = "\n".join(f"- {f['fact']} ({f['source']}, {f['date']})" for f in key)
    sections = "\n".join(
        f"<section agent=\"{r['agent']}\">\n" + json.dumps(r["findings"], indent=1) + "\n</section>" for r in reports)
    # Most important material at the start, everything else under explicit headers, and the question last.
    return f"<key_findings>\n{top}\n</key_findings>\n<details>\n{sections}\n</details>\n<question>{question}</question>"
  • Key findings first: the most relevant findings across all reports, each with its source and date, open the input.
  • Explicit sections: each agent's full results sit in a labelled <section>, so nothing is anonymous text in the middle.
  • Question last.

Lean outputs between agents

Task 5.1Structured results with metadata, not reasoning transcripts.

A subagent's final message is all its parent receives (task 1.3), and the parent's context is limited. If every subagent returns pages of narrative and its whole chain of reasoning, the coordinator spends its budget reading prose. The guide's fix is to change the upstream agents:

  • Return structured data: key facts, citations and a relevance score per finding, as in the reports the synthesis example takes.
  • Include metadata: the date of each fact, where it came from, and how it was obtained (a keyword count of reviews, a web page, a database query). Without that, the synthesis step can't tell a current figure from a stale one or weigh a survey against an anecdote.
  • Leave out the working: the reasoning that led to a finding stays in the subagent's own context.

How the synthesis step then keeps sources attached and handles conflicting claims is task 5.6.

Built-in context management

Task 5.1What the API can do for you, and what it can't.

  • Compaction (beta, Claude 4.6 and later) replaces older turns with a summary Claude writes on the server. It can run on demand or automatically at a token threshold, and it can keep the most recent turns word for word. The docs suggest your own summarisation prompt when the default summary drops something a later turn needs. Even so, it's still a summary, so a case facts block remains the reliable place for exact values.
  • Context editing (beta) clears the oldest tool results once input passes a trigger (100,000 tokens by default). By default it keeps the last three, and each cleared result is replaced with a placeholder so Claude knows something was removed. Named tools can be excluded, and old thinking blocks can be cleared too. Combined with the memory tool, Claude is warned before clearing so it can save what it needs.

Both help with size. Neither decides which facts are critical; that remains your design.

Key takeaways

  • Send the complete history each turn; everything in the request counts, and accuracy degrades as context grows (context rot).
  • Progressive summarisation blurs amounts, dates, statuses and customer expectations. Keep them in a case facts block that goes into every prompt and is never summarised, with one entry per issue.
  • Trim tool results to the relevant fields before they enter history; otherwise they accumulate and bury what matters.
  • Against the lost-in-the-middle effect: key findings first, details under explicit section headers, question last.
  • Upstream agents should return structured findings with dates, sources, methods and relevance, not verbose reasoning. Compaction and context editing manage size, not what's critical.
