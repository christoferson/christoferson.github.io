1.6: Task Decomposition Strategies

Breaking a big job into pieces Claude can do well: a fixed chain of steps when the work is predictable, a plan that grows from what each step finds when it isn't, and the two shapes the exam keeps returning to, the split code review and the legacy test campaign.

Overview

Task 1.6

Design task decomposition strategies for complex workflows.

The exam guide asks you to know when a fixed sequential pipeline (prompt chaining) beats dynamic decomposition that adapts to intermediate findings, how chaining breaks a review into steps (each file on its own, then a cross-file integration pass), and why an investigation plan that generates subtasks from what it finds is valuable. In practice it asks you to pick chaining for predictable, multi-aspect reviews and dynamic decomposition for open-ended investigations, to split a large code review so attention isn't spread thin, and to tackle a task such as "add comprehensive tests to a legacy codebase" by mapping it, ranking it and keeping the plan flexible. Who carries out the pieces (a coordinator and subagents) is task 1.2.

A chain fixes the steps in advance; dynamic decomposition picks them as it goes

Task 1.6Steps decided in advance, or steps decided along the way.

  • Prompt chaining is a workflow in the sense of "Building effective agents": the task is split into a fixed sequence of calls, each working on the previous one's output, along predefined code paths. Code can check each intermediate result (a gate) before the next step runs. Each call has an easier job, so accuracy goes up at the cost of some latency. The essay's examples: write marketing copy, then translate it; or write an outline, check it against criteria, then write the document.
  • Dynamic decomposition lets the model decide the next subtasks from what it has found so far. In the essay's orchestrator-workers pattern, a central model breaks the task down at run time because the subtasks "aren't pre-defined"; its example is a coding change where the number of files and the change in each depend on the task.

Claude's prompting guide adds a current note: with adaptive thinking and subagents, Claude handles most multi-step reasoning itself, and explicit chains are worth building when you need to inspect intermediate outputs or enforce a pipeline's structure. Its most common chain is self-correction: draft, review against criteria, refine, each as a separate call you can log and evaluate.

Chain predictable work; decompose dynamically when findings decide the next step

Task 1.6Predictable multi-aspect work, or open-ended investigation.

  • Chain when the steps are known in advance: every pull request gets the same per-file checks and an integration check; every invoice goes through extract, validate, post. Signals: the same shape every time, a need for consistent coverage, a need to audit each stage.
  • Decompose dynamically when the next step depends on the last one's findings: debugging an intermittent failure, investigating why returns rose, adding tests to code nobody fully understands. Signals: "investigate", "find out why", "comprehensive", an unknown amount of work.
  • Mix them: a fixed outer pipeline can contain an adaptive step, and an adaptive plan can run each item through a fixed chain.
  • Start simple. The essay's advice is to use the simplest arrangement that works and add structure only when it measurably helps; for a small change, one well-prompted call may be enough.

Review each file on its own, then check how the files fit together

Task 1.6Per-file local passes plus a separate cross-file integration pass.

Reviewing a twenty-file pull request in one call spreads the model's attention across everything at once: it skims, reports the obvious, and misses the bug on line 140 of the fourth file. The guide calls this attention dilution. The chained version gives each file its own focused pass, then a second step that looks only at how the files fit together.

review_chain.py (Python, anthropic SDK)Optional 
"""Prompt chain for a pull-request review: one focused pass per file, then one cross-file integration pass."""
import json
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path

import anthropic

client = anthropic.Anthropic()

LOCAL_SCHEMA = {
    "type": "object",
    "properties": {
        "file": {"type": "string"},
        "exports": {"type": "array", "items": {"type": "string"}},  # what other files may depend on
        "issues": {"type": "array", "items": {
            "type": "object",
            "properties": {"line": {"type": "integer"}, "severity": {"type": "string", "enum": ["high", "medium", "low"]},
                           "problem": {"type": "string"}},
            "required": ["line", "severity", "problem"], "additionalProperties": False}},
    },
    "required": ["file", "exports", "issues"], "additionalProperties": False,
}


def text_of(response) -> str:
    return "".join(b.text for b in response.content if b.type == "text")


def review_file(path: str) -> dict:
    # Step 1: one file per call, so attention stays on that file's details.
    response = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=4000,
        system="Review one TypeScript file for bugs and unsafe code. List its exported functions and types.",
        messages=[{"role": "user", "content": f"<file path=\"{path}\">\n{Path(path).read_text(encoding='utf-8')}\n</file>"}],
        output_config={"format": {"type": "json_schema", "schema": LOCAL_SCHEMA}},
    )
    return json.loads(text_of(response))


def integration_pass(local: list[dict], diff: str) -> str:
    # Step 2: the whole change at once, with each file's exports and issues, looking only for cross-file problems.
    response = client.messages.create(
        model="claude-opus-5-5", max_tokens=6000,
        system=("You check how changed files fit together: callers and callees that disagree, renamed exports, "
                "changed types, duplicated logic. Don't repeat the per-file issues you're given."),
        messages=[{"role": "user", "content": f"<per_file>{json.dumps(local)}</per_file>\n<diff>{diff}</diff>"}],
    )
    return text_of(response)


def review(paths: list[str], diff: str) -> dict:
    with ThreadPoolExecutor(max_workers=6) as pool:
        local = list(pool.map(review_file, paths))
    # A programmatic gate between steps: every file must have come back before integration runs.
    missing = set(paths) - {r["file"] for r in local}
    if missing:
        raise RuntimeError(f"no local review for {sorted(missing)}")
    return {"per_file": local, "cross_file": integration_pass(local, diff)}


if __name__ == "__main__":
    files = ["src/api/refunds.ts", "packages/payments/charge.ts", "packages/payments/types.ts"]
    print(json.dumps(review(files, Path("change.diff").read_text(encoding="utf-8")), indent=2))
  • Local passes see one file and report its issues plus what it exports. They're independent, so they run in parallel.
  • The integration pass sees the per-file results and the diff, and looks for what no single file shows: a caller that still passes dollars after the callee switched to cents, a renamed export, duplicated logic. It's told not to repeat the local findings.
  • The gate between the steps is code: integration doesn't run until every file has a local review, so a silent failure can't produce a report that looks complete.
  • Structured handoff (a JSON schema for the local results) makes the second step's input predictable, the same idea as task 1.3's findings.

For open-ended work, map, rank and let discoveries change the plan

Task 1.6Map, rank, plan, and let discoveries change the plan.

"Add comprehensive tests to the legacy order service" has no fixed list of steps: nobody knows yet which modules are fragile or what they depend on. A fixed pipeline would either test everything in alphabetical order or miss what matters. The adaptive approach:

  1. Map the structureModules, what imports what, what's already tested.
  2. Identify high-impact areasRefunds and payments before formatting helpers; heavily imported modules early.
  3. Make a prioritised planA queue ordered by impact, not a fixed script.
  4. Adapt as you learnWhen testing refunds reveals that the untested currency module underpins it, currency moves to the front; finished work isn't redone.
adaptive_plan.py (Python, anthropic SDK)Optional 
"""Adaptive decomposition for "add comprehensive tests to the legacy order service":
map first, rank by impact, then let each step's discoveries reshape the plan."""
import heapq
import json

import anthropic

client = anthropic.Anthropic()


def ask_json(system: str, prompt: str) -> dict:
    response = client.messages.create(
        model="claude-opus-5-5", max_tokens=4000, system=system + " Reply with JSON only.",
        messages=[{"role": "user", "content": prompt}],
    )
    return json.loads("".join(b.text for b in response.content if b.type == "text"))


def plan_and_test(repo_map: str, max_steps: int = 20) -> list[str]:
    # 1. Map the structure: modules, what they import, what's already tested.
    modules = ask_json("List the modules in this repository map with their imports and existing tests.",
                       repo_map)["modules"]
    # 2. Rank by impact: money and data paths first, then the most-imported modules.
    ranked = ask_json("Score each module 1-10 for the damage a bug would do (payments and refunds score highest).",
                      json.dumps(modules))["scores"]
    queue = [(-score, name) for name, score in ranked.items()]
    heapq.heapify(queue)

    done, log = set(), []
    while queue and len(done) < max_steps:
        _, module = heapq.heappop(queue)
        if module in done:
            continue
        # 3. Work one item; the result reports what it discovered.
        result = ask_json("Write characterization tests for this module. Report untested dependencies you had to "
                          "stub, and anything that makes the module hard to test.",
                          f"<module>{module}</module>\n<done>{sorted(done)}</done>")
        done.add(module)
        log.append(f"tested {module}")
        # 4. Adapt: a dependency the tests rely on jumps ahead of everything else.
        for dep in result.get("untested_dependencies", []):
            if dep not in done:
                heapq.heappush(queue, (-11, dep))
                log.append(f"  discovered {dep}: queued first")
    return log


if __name__ == "__main__":
    print("\n".join(plan_and_test(open("repo-map.txt", encoding="utf-8").read())))

For work that outlasts one context window, the prompting guide recommends keeping the plan and progress outside the conversation: a structured file such as tests.json, setup scripts, and Git commits as checkpoints, with a first session that sets up the framework and later sessions that work through the list.

The mistakes that make decomposition answers wrong

Task 1.6How decomposition questions are usually made wrong.

  • One giant pass over a large review or codebase, hoping a bigger model or a longer prompt will keep track of everything: attention dilution.
  • Only local passes, which miss interface breaks between files; or an integration pass that re-reviews every file and duplicates the local findings.
  • A fixed pipeline for an open-ended investigation, which can't follow a lead it didn't anticipate.
  • Fully dynamic handling of a predictable review, which makes coverage vary from run to run and is harder to audit.
  • Planning everything up front for legacy work, then sticking to the plan after a step reveals a dependency that should have come first.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Every pull request needs the same security, style and interface checks, and auditors want to see the output of each stage. Which approach fits?
  1. A. Let the model decide the steps for each pull request
  2. B. A fixed chain with a code gate between stages
  3. C. One large call with all checks in the prompt
  4. D. A new subagent for every line changed
Answer
B
Why
The steps are known in advance and each stage must be inspectable, which is what a chain gives. Dynamic decomposition makes coverage vary; one large call dilutes attention.
Question 2
Scenario
A twenty-file review in one call reports obvious issues and misses a bug deep in one file. What change fixes this?
  1. A. A longer system prompt
  2. B. Per-file passes, then a separate integration pass over their results
  3. C. Lower temperature
  4. D. Review only the largest file
Answer
B
Why
Focused per-file passes avoid attention dilution, and the integration pass catches what no single file shows.
Question 3
Scenario
Per-file reviews all pass, but a caller still sends dollars after the function it calls switched to cents. What was missing?
  1. A. A bigger model for the local passes
  2. B. An integration pass that looks across files at interfaces
  3. C. More few-shot examples
  4. D. Running the local passes in sequence
Answer
B
Why
Interface breaks between files are invisible to a pass that sees one file. The integration step exists for them.
Question 4
Scenario
While adding tests to untested code, the agent finds that the module it is testing depends on another untested module. What should a good plan do?
  1. A. Finish the original order regardless
  2. B. Move the dependency up the queue and keep finished work
  3. C. Restart planning from scratch
  4. D. Skip the dependency
Answer
B
Why
An adaptive plan reorders when discoveries change priorities, without redoing completed work.

Key takeaways

  • Prompt chaining is a fixed sequence of calls, each on the previous output, with code gates between them; it trades latency for accuracy. Dynamic decomposition decides subtasks at run time from what's been found.
  • Chain predictable, multi-aspect work that needs consistent coverage or auditable stages; decompose dynamically for open-ended investigations. Start with the simplest arrangement that works.
  • Current models handle much multi-step reasoning internally; build explicit chains when you need to inspect intermediate outputs or enforce a structure (for example draft, review, refine).
  • Large code reviews: per-file local passes (in parallel, structured output) plus one cross-file integration pass, so attention isn't diluted and interface problems still get caught.
  • Open-ended tasks: map the structure, rank by impact, make a prioritised plan, and reorder it as each step reveals dependencies; keep long-running state in files and Git.
