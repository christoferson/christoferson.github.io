1.7: Sessions, Resumption and Forking

Coming back to work that spans days: naming a session so you can resume it, branching it to try two approaches, telling it what changed while you were away, and knowing when a clean start with a summary beats picking up an old conversation.

Overview

Task 1.7

Manage session state, resumption, and forking.

The exam guide asks you to know how to resume a specific earlier conversation by name with --resume, how fork_session creates independent branches from one shared analysis, why a resumed session must be told about files that changed since it analysed them, and why a new session with a structured summary can be more reliable than resuming with stale tool results. In practice it asks you to continue named investigations across days, fork to compare two testing strategies or refactors, choose between resuming and starting fresh, and point a resumed session at specific changed files instead of making it explore everything again. Forking is introduced in task 1.3; this page adds the Claude Code side and the decisions around it.

Sources: the Claude Code documentation on sessions and the CLI reference, and the Claude Agent SDK documentation on sessions, checked on 19 November 2026. The docs are copyrighted, so they're paraphrased here with short quotes. The decision helper is my own and was tested with claude-agent-sdk 0.2.185; the shell commands were syntax-checked, not run against a live account.

Running example. A developer at the outdoor-gear shop spends three days with Claude Code tracing why refunds are sometimes a cent off, while teammates keep committing to the same repository.

What a session holds

Task 1.7The saved conversation, and what isn't in it.

A session is a saved conversation: your prompts, Claude's replies, every tool call and every tool result, stored locally as a transcript tied to the project directory (under ~/.claude/projects/). Resuming one gives Claude back everything it knew: the files it read, the analysis it did, the decisions it made.

  • Tool results are snapshots. A file read on Monday is in the transcript as it was on Monday. If someone changed it on Tuesday, the resumed session still "remembers" the old version until it reads the file again.
  • The filesystem isn't part of the session. Sessions persist the conversation; files are whatever is on disk now.
  • Some settings aren't restored. The model carries on, and a terminal resume restores the permission mode, but flags such as --add-dir, --mcp-config and --settings have to be passed again.
  • Same machine. Transcripts are local files; to continue elsewhere, move the transcript, use the SDK's session store, or start fresh with a summary.

Naming and resuming

Task 1.7Returning to a specific investigation by name.

sessions.sh (shell, Claude Code CLI) 
# Monday: start a named investigation (or name it later with /rename inside the session)
claude -n returns-investigation

# Tuesday: pick it up by name; the history, files read and conclusions are still there
claude --resume returns-investigation

# Try two refactoring approaches from the same analysis, each in its own session
claude --resume returns-investigation --fork-session   # branch A: new session ID
claude --resume returns-investigation --fork-session   # branch B: another new ID
# (inside a running session, /branch try-event-sourcing does the same and switches you into the copy)

# Ask a saved session for a structured summary without opening it, for a fresh start later
claude -p --resume returns-investigation --output-format json \
  "Summarise the findings, decisions and open questions as JSON" | jq -r '.result' > summary.json
  • Name it at the start with claude -n <name> (or --name), or during the session with /rename. Unnamed sessions get a default display name or a generated title.
  • Resume it with claude --resume <name> (or -r), which also accepts a session ID or a transcript path; with no argument it opens a picker. Inside a session, /resume switches to another one. If a name matches more than one session, the picker opens with it as a search.
  • --continue needs no name: it reopens the most recent session in the current directory. That's fine for one thread of work, but with several investigations running, a name says which one.
  • In the Agent SDK the same thing is resume=session_id (or continue_conversation=True); sessions started by the SDK or claude -p don't appear in Claude Code's picker but can be resumed by ID.

Forking

Task 1.7Independent branches from one shared baseline.

Forking copies the conversation so far into a new session with its own ID and leaves the original unchanged. Do the expensive analysis once, then fork to compare, say, two testing strategies or two refactors, each branch building on the same understanding without seeing the other's work.

  • In Claude Code: /branch [name] inside a session copies the transcript and switches you into the copy; from the shell, add --fork-session to --resume or --continue. A /branch keeps your "allow for this session" approvals; a separate --fork-session process starts without them.
  • In the Agent SDK: resume=session_id, fork_session=True; the result message carries the fork's new ID (example in task 1.3).
  • Only the conversation branches. Edits a branch makes to files are real and visible to every session in that directory; use separate worktrees or checkpoints to branch the code too.

Don't resume one session twice at once. Two terminals (or two claude -p runs) resuming the same session both write to one transcript, and messages can be lost when it's resumed later. To run two lines of work in parallel, fork each one.

Resuming after the code changed

Task 1.7Telling a resumed session exactly what's different.

On Wednesday the refund investigation resumes, but a teammate has merged changes to two files the session read on Monday. Left alone, Claude reasons from its Monday copies. The fix isn't to make it re-read the whole repository, which wastes time and context, but to tell it which files changed, so it re-reads those and trusts the rest. Version control gives you the list: everything that changed between the commit the session last saw and now.

resume_or_fresh.py (Python, claude-agent-sdk)Optional 
"""Decide how to continue an investigation after the code has changed: resume with a targeted update,
or start fresh with a structured summary when too much of the old context is stale."""
import json
import subprocess
from dataclasses import dataclass

from claude_agent_sdk import ClaudeAgentOptions

TOOLS = ["Read", "Grep", "Glob"]


@dataclass
class Investigation:
    session_id: str
    commit: str             # HEAD when the session last ran
    analysed: list[str]     # files the session read
    summary: dict           # findings, decisions, open questions (saved at the end of each run)


def changed_since(commit: str) -> list[str]:
    out = subprocess.run(["git", "diff", "--name-only", f"{commit}..HEAD"], capture_output=True, text=True, check=True)
    return [line for line in out.stdout.splitlines() if line]


def next_step(inv: Investigation, changed: list[str], task: str, stale_limit: float = 0.25):
    touched = [f for f in changed if f in inv.analysed]
    if len(touched) <= stale_limit * len(inv.analysed):
        # Most earlier reads are still true: resume, and say exactly what to look at again.
        note = (f"Since your last run these files changed: {', '.join(touched) or 'none you read'}. "
                "Re-read only those before relying on them; everything else you analysed is unchanged.")
        return f"{note}\n\n{task}", ClaudeAgentOptions(resume=inv.session_id, allowed_tools=TOOLS)
    # Too much of the old context is stale: a new session seeded with the summary, not old tool results.
    prompt = (f"<summary_of_previous_work>\n{json.dumps(inv.summary, indent=2)}\n</summary_of_previous_work>\n"
              f"These files changed since that work and must be read fresh: {', '.join(touched)}.\n\n{task}")
    return prompt, ClaudeAgentOptions(allowed_tools=TOOLS)

The note is specific ("these files changed; re-read only those; everything else is unchanged"), which gives the session a targeted re-analysis instead of either trusting stale results or starting its exploration over.

Resume or start fresh

Task 1.7When old context helps, and when it misleads.

  • Resume when most of the earlier context is still valid: the code has barely moved, the conversation holds reasoning worth keeping, and a short note can cover what changed.
  • Start fresh with a structured summary when much of what the session read is out of date: a large merge, a refactor, a dependency upgrade. A transcript full of stale file contents and old test output can anchor Claude on things that are no longer true, and the stale material also takes up context. A new session that receives a summary (findings, decisions, open questions) plus the list of files to read fresh starts from what's still true.
  • Get the summary from the old session. claude -p --resume <session> --output-format json "..." asks a saved session for a summary without opening it; saving one at the end of each working day makes the fresh start cheap.

The helper above makes the choice explicit: if only a small share of the files the session analysed have changed, it resumes with a targeted note; otherwise it starts a new session seeded with the saved summary. Within one session, /compact (replace history with a summary) and /clear (start empty, keeping the old session resumable) are the in-session versions of the same trade-off.

Spotting the right answer. If a scenario says the code has changed a lot since the session ran, the answer is a fresh session with a summary, not "resume and ask Claude to double-check". If only a couple of files changed, it's resume and name those files, not "re-explore the codebase".

Key takeaways

  • A session is the saved conversation, including tool results as they were when read; it isn't the filesystem, and some flags aren't restored on resume.
  • Name sessions (claude -n, /rename) and resume them by name (claude --resume <name>); --continue reopens only the most recent one. The SDK uses resume= with a session ID.
  • Fork to explore alternatives from one baseline: /branch, --fork-session, or the SDK's fork_session=True. Each fork gets a new ID; the original is untouched; files aren't branched. Never resume one session in two places at once.
  • When resuming after code changes, tell the session which files changed so it re-reads just those.
  • Resume when prior context is mostly valid; start fresh with a structured summary (findings, decisions, open questions) when prior tool results are stale.
