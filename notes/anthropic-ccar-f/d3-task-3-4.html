3.4: Plan Mode or Direct Execution

When to have Claude investigate and propose a plan before touching any files, and when to let it make the change straight away, plus the read-only subagents that do the exploring.

Overview

Task 3.4

Determine when to use plan mode vs direct execution.

The exam guide asks you to recognize tasks that need a plan (large or multi-file changes, several valid approaches, architectural decisions) and tasks that don't (a simple, well-scoped change such as a single-file fix with a clear stack trace), to use the Explore subagent so verbose discovery doesn't fill the main conversation, and to combine the two: plan the investigation, then carry out the plan directly.

Sources: the Claude Code documentation (permission modes, common workflows, subagents, commands, model configuration, best practices) and the changelog, checked on 8 November 2026 against Claude Code 2.1.303, paraphrased.

Running example. Two tasks land on the shop team the same morning: replace the home-grown cart tax calculation with a tax service (many files, several possible designs), and fix a TypeError on an empty cart reported with a stack trace pointing to one line.

What plan mode does

Task 3.4Research first, no changes until you approve.

In plan mode Claude reads files, runs commands to explore, and writes a plan, but makes no edits to your source until you approve it. The docs recommend it "for changes you want to review before they touch disk".

  • Plan mode isn't "no commands": read-only commands run; with auto mode available, a classifier judges other commands; otherwise anything outside the read-only set asks first.
  • Research is handed to the built-in Plan subagent, so the exploration output stays out of the main conversation.
  • Plan mode keeps blocking edits in non-interactive runs (-p), the Agent SDK and the VS Code panel. The one exception: in an interactive terminal where bypass permissions is available, plan mode doesn't block edits.

Entering and approving

Task 3.4The ways into plan mode, and what happens to the plan.

Entering plan mode (shell and session) 
# start the whole session in plan mode
claude --permission-mode plan

# inside a session: plan one task
/plan add coupon codes to the cart

# or press Shift+Tab to cycle modes
# (Alt+M on some Windows terminals)
.claude/settings.json (project) 
{
  "permissions": {
    "defaultMode": "plan"
  }
}

Claude can also switch itself into plan mode when a task looks large. When the plan is ready, Claude presents it (the ExitPlanMode tool) and you choose:

  • approve and continue in auto mode (or auto-accepting edits, depending on setup);
  • approve but review each edit manually;
  • keep planning, with feedback.

Ctrl+G opens the plan in your editor to change it before approving. Plans are saved as files in ~/.claude/plans/ by default, so a long plan can be read again or handed to a later session.

Permission modes

Task 3.4Plan mode is one of six permission modes.

ModeWhat runs without asking
default (shown as Manual)Reads only; everything else prompts
acceptEditsReads, file edits and common file commands in the working folders
planReads and exploring; no source edits until the plan is approved
autoEverything, with a classifier model checking each action in the background
dontAskOnly pre-approved tools and reads; anything that would prompt is denied (for locked-down CI)
bypassPermissionsEverything, with no checks; only for isolated containers or VMs

Deny rules apply in every mode. Since 2.1.283, interactive terminal and VS Code sessions start in auto unless configured otherwise, while -p and the SDK start in default. Project settings can set plan as the default, but a project file can't make auto or bypassPermissions the default.

Plan or execute?

Task 3.4Matching the approach to the task's complexity.

SignalPlan firstExecute directly
ScopeMany files or modulesOne file or function
ApproachSeveral valid designs to choose betweenOne obvious fix
KnowledgeUnfamiliar code, unclear dependenciesCause already known, for example from a stack trace
Cost of a wrong startHigh: architectural decisions, migrationsLow: easy to check and undo

This split is the exam guide's framing; the docs say much the same more briefly, describing /plan as the way to switch "before a large change".

The shop's two tasks (prompts) 
# Plan first: many files, choices
/plan Replace our cart tax code with
the tax service. List every file you
would touch, the options and the
risks. No edits yet.

# Direct: one file, clear cause
Fix the TypeError in
src/cart/total.ts line 42: guard
against an empty items array and
add a unit test for it.

Don't start direct and hope. For a large change, answers like "start with direct execution and switch to planning if surprises appear" or "give very detailed instructions and execute directly" are the classic wrong choices. Plan first, then execute the approved plan. For a one-line fix, planning is wasted effort.

Large, mechanical migrations: /batch. The bundled /batch skill researches the code, splits a big change into 5 to 30 units and shows you the plan; once you approve, it runs one background subagent per unit, each in its own Git worktree, and each opens a pull request. It's plan-then-execute at scale.

Exploring with subagents

Task 3.4Keeping verbose discovery out of the main conversation.

Built-in subagentWhat it does
ExploreFast, read-only search and analysis of the codebase (Write and Edit denied), at a quick, medium or very thorough level; returns a summary. Claude sends broad searches to it automatically
PlanRead-only research used by plan mode before it presents a plan
General-purposeMulti-step work that needs both exploring and changes

Explore and Plan start without CLAUDE.md, and each runs once and returns; they can't be resumed. While the main conversation is in plan mode, any subagent it starts stays in plan mode too.

Changes since the guide's framing. Explore launched in 2.0.17 running on Haiku; since 2.1.198 it uses the session's model. The guide presents Explore mainly as protection against running out of context; the current best-practices page lists "protect your context window" as older advice, since 1M-token windows and automatic compaction make that rare, and stresses keeping noisy output out of the way and parallel or independent work instead. The guide also doesn't mention the Plan subagent, which is what plan mode actually uses. /ultraplan was removed in 2.1.222.

Thinking and effort

Task 3.4How much reasoning Claude applies to a plan.

Older guides tell you to write "think", "think hard" or "ultrathink" to get deeper reasoning. Today "think" and "think hard" are ordinary words with no special effect. The real control is the effort level, set with /effort (low, medium, high, xhigh, max; the Claude 5.5 models default to medium). ultrathink still works as a one-turn boost. The opusplan model setting uses Opus while planning and Sonnet while executing.

Key takeaways

  • Plan mode: Claude explores and proposes; no source edits until you approve. Enter with Shift+Tab, /plan, --permission-mode plan or "defaultMode": "plan".
  • Plan first for multi-file, multi-option, architectural or unfamiliar work; execute directly for single-file, well-understood fixes. Then execute the approved plan.
  • Modes: default (Manual), acceptEdits, plan, auto, dontAsk, bypassPermissions. Interactive sessions now start in auto; -p starts in default.
  • Explore (read-only search) and Plan (plan-mode research) keep verbose discovery out of the main context and return summaries.
  • /batch plans a large mechanical change and runs it in parallel worktrees after approval.
  • "Think hard" is no longer a keyword; use /effort (or ultrathink for one turn).
