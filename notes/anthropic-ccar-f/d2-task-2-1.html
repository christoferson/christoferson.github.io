2.1: Tool Interfaces

Claude picks a tool from its name and description, so a tool's interface is a prompt. This page covers writing descriptions that set similar tools apart, deciding how many tools to have, designing their inputs and outputs, and choosing between MCP tools and resources.

Overview

Task 2.1

Design effective tool interfaces with clear descriptions and boundaries.

The exam guide asks you to know that descriptions are the main thing Claude uses to choose a tool, that minimal or overlapping descriptions cause wrong choices between similar tools, and that keyword-heavy system prompt wording can pull requests toward the wrong tool. In practice: write descriptions that state purpose, inputs, outputs and when to use the tool instead of a similar one; rename tools that overlap; split a vague, catch-all tool into purpose-specific ones; and check the system prompt for wording that overrides good descriptions.

Sources: the Claude API tool-use documentation (define tools, strict tool use, tool search), Anthropic's "Building effective agents" (December 2024), "Writing effective tools for agents" (September 2025) and "advanced tool use" (November 2025) posts, the MCP specification (revision 2026-07-28) and the MCP Python SDK, checked on 8 November 2026; Anthropic's pages are paraphrased. The server code was run with MCP Python SDK 2.3.0.

Running example. The shop's support agent has tools to find an order and to issue a refund, and a returns policy it needs to know. Early on, Claude kept calling the refund tool for exchanges and guessing order numbers.

Descriptions decide selection

Task 2.1What a good tool description covers.

The Claude docs call detailed descriptions "by far the most important factor in tool performance" and suggest at least three or four sentences per tool. Anthropic's agents article puts it as writing each definition like a great docstring for a junior developer. A description should cover:

  • what the tool does, and what it returns;
  • when to use it, and when not to (naming the tool to use instead);
  • what each parameter means and its format;
  • limits and edge cases, including what it doesn't do.

The API builds a single tool-use system prompt from your tool definitions and your own system prompt, which is why the guide warns about system prompt wording: an instruction such as "always use the refund tool when a customer mentions a return" can override a careful description that says exchanges go elsewhere.

A weak and a strong definition

Task 2.1The same tool, described two ways.

Weak definition (JSON) 
{
  "name": "refund",
  "description": "Refunds an order.",
  "input_schema": {
    "type": "object",
    "properties": {
      "id": {"type": "string"},
      "amt": {"type": "number"}
    }
  }
}
Strong definition (Python, anthropic SDK) 
refund_tool = {
    "name": "shop_issue_refund",
    "description": (
        "Refunds part or all of one "
        "order to the customer's "
        "original payment method. Use "
        "it only after shop_find_order "
        "shows the order is inside the "
        "60-day return window. Not for "
        "store credit or exchanges: use "
        "shop_create_exchange. Refunds "
        "above 500 USD are rejected; "
        "hand the case to a person with "
        "shop_handoff instead. Returns "
        "the refund ID and amount. "
        "Repeating a call never "
        "refunds twice."),
    "strict": True,
    "input_schema": {
        "type": "object",
        "properties": {
            "order_number": {
                "type": "string",
                "description": (
                    "Order number like "
                    "ORD-104233, from "
                    "shop_find_order")},
            "amount_usd": {
                "type": "number",
                "description": (
                    "Amount to refund, "
                    "at most the order "
                    "total")},
            "reason": {
                "type": "string",
                "enum": [
                    "damaged",
                    "wrong_item",
                    "not_as_described",
                    "changed_mind"]},
        },
        "required": ["order_number",
                     "amount_usd",
                     "reason"],
        "additionalProperties": False,
    },
    "input_examples": [{
        "order_number": "ORD-104233",
        "amount_usd": 89.95,
        "reason": "damaged"}],
}

The weak version has a vague name, one sentence, cryptic parameter names without descriptions, no required fields and no boundaries. The strong one names its service, says when not to use it and which tool to use instead, states its limit and what it returns, describes each parameter, and constrains reason to fixed values.

Names and overlap

Task 2.1Naming tools so they can't be confused.

  • Distinct purposes. Anthropic's tool-writing guide says each tool needs a clear, distinct purpose; overlapping tools distract the agent. If two tools could plausibly handle the same request (analyze_content and analyze_document), rename and redescribe them so the boundary is obvious (for example extract_web_results).
  • Namespacing. Prefix by service or resource (shop_find_order, crm_find_customer) when tools come from several systems. The guide notes that prefix versus suffix can matter, so test it.
  • Unambiguous parameters. order_number, not id; customer_id, not user.
  • Name rules. Claude API tool names allow letters, digits, _ and - (up to 128 characters); MCP also allows dots, so a dotted MCP name needs converting.

Split or consolidate

Task 2.1How many tools to offer.

SituationDoExample
One vague tool hides several different jobsSplit it into purpose-specific tools, each with its own input and output contractanalyze_document becomes extract_data_points, summarize_content and verify_claim_against_source (the exam guide's example)
Thin wrappers the agent always chainsConsolidate into one tool that does the whole steplist_users, list_events and create_event become schedule_event (Anthropic's example)
Related operations on one objectOne tool with an action parameterCreate, review and merge a pull request (the Claude docs' example)

These look contradictory but aim at the same thing: one clear purpose per tool, no overlap, and fewer decisions for Claude. As the tool-writing guide puts it, more tools don't always mean better results; don't wrap every API endpoint as its own tool.

Inputs and outputs

Task 2.1Schemas that prevent mistakes, and responses worth reading.

FeatureWhat it does
enum, required, per-parameter descriptionsClose off invalid values and say what each field means
strict: trueGuarantees the input matches the schema (a number is never sent as a string). It controls the input's shape, not which tool Claude picks
input_examplesOne to five realistic example inputs; each must validate against the schema or the request fails. Most useful for nested or convention-heavy inputs

The agents article calls this "poka-yoke": change the arguments so mistakes are harder to make (Anthropic's coding agent stopped making path errors once its tools required absolute paths). For outputs, return high-signal fields with meaningful names rather than internal IDs, use pagination, filtering or truncation with sensible defaults, and consider a response_format option (concise or detailed). In Anthropic's example the concise response used about a third of the tokens.

Newer than the exam guide. Strict tool use, input_examples and tool search all launched as betas in late 2025 and are now stable without beta headers; the guide mentions none of them. Also, Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 reject forced tool_choice (any or a named tool) with an error, so "force the tool" is no longer a general fix for poor selection (task 2.3). Better descriptions and names come first.

MCP tools, resources and prompts

Task 2.1Exposing actions as tools and catalogs as resources.

MCP primitiveControlled byUse for
ToolThe model, which decides to call itActions and lookups: find an order, issue a refund
ResourceThe application, which attaches it as contextContent and catalogs: the returns policy, a product catalog, a database schema
PromptThe user, for example as a slash commandReusable prompt templates

Exposing a catalog as a resource lets the agent see what exists without a series of exploratory tool calls.

support_server.py (Python, MCP server) 
from typing import Annotated
from pydantic import Field
from mcp.server.mcpserver import (
    MCPServer)
from mcp.types import ToolAnnotations

mcp = MCPServer("shop-support")


# Resource: context the host attaches
@mcp.resource(
    "policy://returns",
    mime_type="text/markdown",
)
def returns_policy() -> str:
    """Return and refund rules."""
    return "# Returns\n60 days, unused."


# Tool: read-only lookup
@mcp.tool(
    annotations=ToolAnnotations(
        readOnlyHint=True,
        openWorldHint=False,
    ),
)
def shop_find_order(
    order_number: Annotated[str, Field(
        pattern=r"^ORD-\d{6}$",
        description="e.g. ORD-104233",
    )],
) -> dict:
    """Look up ONE order by its number
    (ORD- and 6 digits). Returns the
    status, items, total and whether
    it's inside the return window.
    Use before any refund. Can't search
    by customer name: ask for the
    order number instead."""
    return {"order": order_number,
            "status": "delivered"}

The SDK builds the tool's schema from the type hints and its description from the docstring, so the docstring is the description Claude reads. A parameter without a pydantic Field gets no description of its own.

Annotations are hints, not security. MCP tool annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) describe how a tool behaves, and the defaults are cautious (not read-only, possibly destructive). The spec says they aren't guaranteed to be accurate and clients should never make decisions based on annotations from untrusted servers. Real limits, such as the refund cap, belong in the server's code and the host's permissions.

Many tools, and testing them

Task 2.1Large tool sets, and measuring whether Claude picks the right tool.

The tool search docs note that selection accuracy drops once an agent has more than about 30 to 50 tools. With tool search, you mark tools with defer_loading: true and Claude finds the ones it needs by searching their names and descriptions, which is another reason to put the words customers actually use into descriptions. Keep the three to five most-used tools always loaded.

Anthropic's tool-writing guide describes an evaluation loop: write realistic, multi-step tasks with checkable outcomes, run them automatically, track accuracy, tool calls, tokens and tool errors, read the transcripts (including what the agent didn't do), improve the descriptions, and check on held-out tasks so you don't overfit. Include ambiguous requests, such as "I want to send these boots back", to test whether the refund and exchange tools are told apart.

Key takeaways

  • Descriptions are the main lever for tool selection: what it does and returns, when to use it and when not, parameters and formats, limits. Aim for at least three or four sentences.
  • Remove overlap with distinct names and boundaries, prefix by service, and use clear parameter names. Check the system prompt for wording that overrides descriptions.
  • Split vague catch-all tools; consolidate thin wrappers that are always chained. The goal is one clear purpose per tool.
  • Use enums, required fields and per-parameter descriptions; strict: true guarantees valid input, not the right tool; input_examples help with complex inputs.
  • MCP: tools for actions (model-controlled), resources for catalogs and context (application-controlled), prompts for templates (user-controlled). Annotations are untrusted hints.
  • Beyond 30 to 50 tools, use tool search with deferred loading. Evaluate selection with realistic and ambiguous tasks.
