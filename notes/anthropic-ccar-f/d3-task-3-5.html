3.5: Iterative Refinement

Overview

Task 3.5

Apply iterative refinement techniques for progressive improvement.

The exam guide asks for four techniques: concrete input/output examples when prose descriptions get interpreted inconsistently; test-driven iteration, writing the tests first and sharing the failures; the interview pattern, where Claude asks questions that surface things you hadn't considered; and knowing when to send interacting issues together and independent ones one at a time.

Sources: the Claude Code documentation (best practices, common workflows, checkpointing, worktrees, tools reference), Anthropic's prompting best-practices page and the changelog, checked on 8 November 2026, paraphrased. The test code below was run with Vitest 5.1.

Running example. The shop needs a formatPrice function that turns integer cents into a display string. A first attempt from the prompt "format prices nicely" got negative amounts and missing prices wrong.

Give Claude a check

Task 3.5Iterating against something that passes or fails.

The best-practices page's main point: Claude stops when the work looks done, and without something to run, "that makes you the test suite". Give it a check that returns pass or fail, and it can change, run, read the failure and fix on its own. Checks it lists include a test file, a build's exit code, a linter, a script that compares output with a fixture, and a browser screenshot next to the design.

How firmlyHow
AskIn the prompt: "run the pricing tests and keep going until they pass". Claude decides when it's satisfied
Goal/goal <condition>: a separate model checks the condition after every turn, and Claude continues until it's met
EnforceA Stop hook that runs the check and exits with code 2 sends Claude back to work until it passes

Ask for evidence, too: the command Claude ran and its output. "All tests pass" on its own tells you little. And put the command that runs the check in CLAUDE.md, so Claude never has to guess it.

Test-driven iteration

Task 3.5Tests first, then implement, feeding real failures back.

Prompt sequence 
1) Write tests only, in
   src/pricing.test.ts, for
   formatPrice(cents) using the
   examples below. No pricing.ts yet.
2) Run them and confirm they fail.
3) Implement src/pricing.ts. Don't
   edit the tests. Run pnpm vitest
   until everything passes.
4) Show me the command and output.
src/pricing.test.ts (TypeScript, Vitest) 
import {
  describe, expect, it,
} from "vitest";
import { formatPrice } from "./pricing";

describe("formatPrice", () => {
  it.each([
    [1999, "$19.99"], // normal
    [5, "$0.05"], // pad the cents
    [0, "$0.00"], // zero
    [123456, "$1,234.56"], // thousands
    [-250, "-$2.50"], // refund
  ])("%i -> %s", (cents, want) => {
    expect(formatPrice(cents)).toBe(want);
  });

  it("null price is N/A", () => {
    expect(formatPrice(null)).toBe("N/A");
  });

  it("rejects fractional cents", () => {
    expect(() => formatPrice(19.99))
      .toThrow(TypeError);
  });
});

Claude's first implementation passed six tests and failed one. The useful next prompt passes on the actual failure, not "it's still broken":

Feeding the failure back (prompt) 
"rejects fractional cents" fails:
expected function to throw an error,
but it didn't. Throw a TypeError when
cents isn't an integer. Keep the
other tests green.
src/pricing.ts (after the fix) 
export function formatPrice(
  cents: number | null,
): string {
  if (cents === null) return "N/A";
  if (!Number.isInteger(cents)) {
    throw new TypeError("not cents");
  }
  const sign = cents < 0 ? "-" : "";
  const abs = Math.abs(cents);
  const dollars = Math.floor(abs / 100)
    .toLocaleString("en-US");
  const c = String(abs % 100)
    .padStart(2, "0");
  return `${sign}$${dollars}.${c}`;
}

Tests define correctness, not the solution. Anthropic's prompting guide warns against code that only passes the tests: ask for a general solution, no hard-coding for test inputs, and a report if a test itself looks wrong rather than a workaround. Tell Claude not to edit the tests to make them pass.

Input/output examples

Task 3.5Showing the transformation instead of describing it.

"Format prices nicely" can be read many ways. A few concrete pairs, including the edge cases, pin it down:

Examples in the prompt 
<examples>
<example>1999 -> $19.99</example>
<example>5 -> $0.05</example>
<example>123456 -> $1,234.56</example>
<example>-250 -> -$2.50</example>
<example>null -> N/A</example>
</examples>

Anthropic's prompting guide calls examples "one of the most reliable ways" to steer output. Make them relevant, varied enough to cover the edge cases, and clearly marked with tags. The exam guide says two or three examples; the prompting guide suggests three to five. Either way the point is a few concrete cases rather than more adjectives. (Few-shot prompting in API applications is task 4.2.)

The interview pattern

Task 3.5Letting Claude ask the questions before it builds.

When you're not sure exactly what you want, the docs' advice is to "ask Claude to interview you instead". Claude asks multiple-choice questions (its AskUserQuestion tool) about the parts you haven't pinned down, keeps going until it could write a spec, and writes it to a file such as SPEC.md. Then start a fresh session to build from the spec: clean context, a written definition of done, and something to review the result against.

Starting an interview (prompt) 
I want discount codes at checkout
but haven't thought it through.
Interview me until you could write
the spec, then save it to SPEC.md.

The questions are where the value is: they surface things you hadn't considered, such as whether codes stack, whether they apply before or after tax, and what happens to a code when an order is refunded. This matters most in an unfamiliar domain.

Steering a session

Task 3.5Correcting early, rewinding, and starting over.

ActionUse it when
EscClaude starts going the wrong way: stop it straight away; the work so far is kept
/rewind (or Esc twice on an empty prompt)You want to go back to an earlier point: restore the code, the conversation or both, or summarize part of it
/clearBetween unrelated tasks, or after two corrections that didn't work: start fresh with one better prompt
/compactThe session is long but still on track; optionally say what to keep

Two failed corrections, then start over. The docs' advice: a third correction adds to a context already holding two failed attempts. /clear plus a single new prompt that folds in what you learned works better "almost every time".

One issue or all at once

Task 3.5Deciding how to hand over several problems.

The issuesHand them overShop example
Interact (fixing one changes another)Together, in one detailed messageRounding and currency formatting in the same price string
IndependentOne at a time, checking each fixA price bug and a typo in the order email
Independent and largeIn parallel, in separate Git worktreesTwo features worked on by two sessions

The together-or-separately split is the exam guide's framing; the docs support it indirectly (give everything Claude needs up front; refactor in "small, testable increments"). For parallel work, claude --worktree <name> (or -w) starts a session in its own worktree under .claude/worktrees/ on a new branch, so two sessions never edit the same checkout. A .worktreeinclude file copies gitignored files such as .env into new worktrees.

Checkpoints and their limits

Task 3.5What rewinding restores, and what it doesn't.

Claude Code takes a checkpoint before each prompt and keeps file snapshots for the last 100 checkpoints, saved with the conversation, so you can try a bolder approach knowing you can step back. Checkpoints arrived with Claude Code 2.0 in September 2025.

Checkpoints aren't Git. They track changes made by Claude's file-editing tools. They don't undo files changed only through Bash commands, edits you made yourself or another session made, most subagent edits, linked files, or anything outside the repository such as a database change or a deployment. Commit before risky work.

The old named workflows are gone. The 2025 engineering blog post on Claude Code best practices now redirects to a rewritten docs page. Recipes such as "write tests, commit; code, iterate, commit" are no longer there under those names; the ideas live on as "give Claude a check to run", "brainstorm with Claude first" and "steer the session". The page also drops older habits: no ALL-CAPS emphasis, no "think hard" phrases (effort is the control), and no "keep going, don't be lazy" lines, which cause over-work.

Key takeaways

  • Give Claude a pass/fail check (tests, build, linter, screenshot) and ask for evidence; make it stricter with /goal or a Stop hook.
  • Test-driven: write tests first, confirm they fail, implement without editing the tests, and feed back the actual failure output.
  • Use a few concrete input/output pairs, edge cases included, when prose gets read inconsistently (guide: 2 to 3; prompting docs: 3 to 5).
  • Interview pattern: Claude asks you multiple-choice questions, writes SPEC.md, and you build in a fresh session.
  • Interacting issues go in one message; independent ones one at a time; independent large work in parallel worktrees (claude -w).
  • Esc early, /rewind to step back, /clear after two failed corrections. Checkpoints don't cover Bash-only changes, outside edits or external effects.
