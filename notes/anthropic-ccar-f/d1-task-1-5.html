1.5: Hooks for Interception and Normalisation

Code that runs around every tool call: before it, to stop or redirect actions the business forbids, and after it, to turn each system's dates and status codes into one format before Claude reads the result.

Overview

Task 1.5

Apply Agent SDK hooks for tool call interception and data normalization.

The exam guide asks you to know the hook that intercepts tool results to transform them before the model processes them (PostToolUse), the hook that intercepts outgoing tool calls to enforce rules such as a refund threshold, and why hooks give deterministic guarantees where prompt instructions give probabilistic compliance. In practice it asks you to normalise mixed formats (Unix timestamps, ISO 8601, numeric status codes) coming from different MCP tools, block policy-violating calls (refunds over $500) and redirect them to another workflow such as human escalation, and choose hooks when a business rule must hold every time. Gates that depend on an earlier step's result are covered in task 1.4.

Sources: the Claude Agent SDK hooks guide and the Claude Code hooks reference, checked on 19 November 2026. The docs are copyrighted, so they're paraphrased here with short quotes. The hooks are my own and were tested by calling them with hook inputs, using claude-agent-sdk 0.2.185.

Running example. The outdoor-gear shop's support agent reads three systems through MCP servers: orders (numeric status codes, Unix seconds), warehouse (two-letter codes, Unix milliseconds) and carrier (upper-case words, ISO 8601 with local offsets). Refunds go through orders and must stay under $500 without a person's approval.

Two interception points

Task 1.5Before a tool runs, and after it returns.

  • PreToolUse runs after Claude has chosen a tool and its arguments but before the tool executes. It can deny the call (with a reason Claude reads), allow it, ask for a person's approval, defer it (the turn ends with stop reason tool_deferred so your application can resume the call later), or rewrite its arguments with updatedInput. This is where compliance rules go: once a refund has run, no later hook can undo it.
  • PostToolUse runs after a tool has finished successfully, with both its arguments (tool_input) and its result (tool_response). It can replace what Claude sees with updatedToolOutput, add a note with additionalContext, or attach a reason with decision: "block" (which leaves the original output visible). This is where normalisation goes. Failed calls go to PostToolUseFailure instead.

Both match on the tool name. MCP tools are named mcp__<server>__<tool>, so a regular-expression matcher such as ^mcp__orders__ covers every tool on one server.

Normalising tool results

Task 1.5One date format and one status vocabulary, whichever tool answered.

When each system speaks its own format, Claude has to translate every result, and it will sometimes get it wrong: 1763460000 and 2025-11-18T11:00:00+01:00 are the same moment, 3, DS and IN_TRANSIT all mean "shipped", and comparing "is the parcel later than the promised date" across them invites mistakes. A PostToolUse hook converts every result to one convention before the model reads it, so the agent reasons about data that's already consistent.

normalize_hook.py (Python, claude-agent-sdk hook)Optional 
"""PostToolUse hook that gives the agent one date format and one status vocabulary, whichever MCP tool answered."""
import json
from datetime import datetime, timezone

# Each back-end system reports status its own way.
STATUS = {
    "orders": {1: "placed", 2: "paid", 3: "shipped", 4: "delivered", 9: "cancelled"},       # numeric codes
    "warehouse": {"PK": "packed", "DS": "shipped", "RT": "returned"},                         # short codes
    "carrier": {"IN_TRANSIT": "shipped", "DELIVERED": "delivered", "EXCEPTION": "delayed"},   # upper-case words
}
TIME_FIELDS = {"created", "updated", "shipped_at", "eta", "delivered_at"}


def to_iso(value):
    """Unix seconds, Unix milliseconds or ISO 8601 in; ISO 8601 UTC out."""
    if isinstance(value, (int, float)):
        seconds = value / 1000 if value > 10**11 else value
        return datetime.fromtimestamp(seconds, tz=timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")
    if isinstance(value, str):
        parsed = datetime.fromisoformat(value.replace("Z", "+00:00"))
        if parsed.tzinfo is None:
            parsed = parsed.replace(tzinfo=timezone.utc)
        return parsed.astimezone(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")
    return value


def normalise(record: dict, server: str) -> dict:
    out = {}
    for key, value in record.items():
        if key in TIME_FIELDS:
            out[key] = to_iso(value)
        elif key in ("status", "state"):
            out["status"] = STATUS[server].get(value, f"unknown ({value})")  # never guess silently
        else:
            out[key] = value
    return out


def rewrite_text(text: str, server: str) -> str:
    try:
        data = json.loads(text)
    except ValueError:
        return text  # not JSON: leave it alone
    if isinstance(data, list):
        return json.dumps([normalise(r, server) for r in data])
    return json.dumps(normalise(data, server))


async def normalise_result(input_data, tool_use_id, context):
    server = input_data["tool_name"].split("__")[1]  # mcp__<server>__<tool>
    if server not in STATUS:
        return {}
    response = input_data["tool_response"]
    # MCP output isn't schema-checked, so return the same shape that came in.
    if isinstance(response, str):
        new = rewrite_text(response, server)
    else:
        blocks = response["content"] if isinstance(response, dict) else response
        new_blocks = [{**b, "text": rewrite_text(b["text"], server)} if b.get("type") == "text" else b for b in blocks]
        new = {**response, "content": new_blocks} if isinstance(response, dict) else new_blocks
    return {"hookSpecificOutput": {"hookEventName": "PostToolUse", "updatedToolOutput": new}}

Translation lives in a table in code, so adding a fourth system means adding its codes, not rewriting the system prompt, and every conversation gets exactly the same conversion.

Rules for rewriting results

Task 1.5What the docs warn about when replacing tool output.

  • It changes what Claude sees, nothing else. The tool has already run, so its side effects stand, and telemetry such as OpenTelemetry spans records the original output, not your rewrite.
  • Match the output shape. For built-in tools, a replacement that doesn't fit the tool's output schema is ignored and the original is used. MCP output isn't schema-checked, so the hook above returns the same shape it received: a string, a list of content blocks, or an object with content.
  • Don't hide what Claude needs. Stripping error details can make it carry on as if something succeeded. The hook passes unknown status codes through as unknown (7) rather than guessing, and leaves non-JSON text alone.
  • Prefer updatedToolOutput. The older updatedMCPToolOutput works for MCP tools only.
  • Adding beats replacing when both would do. If the original is fine and only needs a hint ("times are UTC"), additionalContext keeps the raw result intact.

Intercepting outgoing calls

Task 1.5Blocking a policy-violating action and pointing to the right workflow.

A PreToolUse hook on the refund tool checks the amount against the policy. Under the limit it returns nothing and the call proceeds; over it, it denies the call and uses the reason to redirect: it names the alternative workflow (escalating to a person) and what that workflow needs, so Claude's next step is the escalation rather than a retry with a slightly lower amount.

agent_hooks.py (Python, claude-agent-sdk)Optional 
"""Register both kinds of hook: normalise what comes back, intercept what goes out."""
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

from normalize_hook import normalise_result

REFUND_LIMIT = 500.00


async def refund_policy(input_data, tool_use_id, context):
    amount = input_data["tool_input"].get("amount", 0)
    if amount > REFUND_LIMIT:
        # Block the action and name the alternative workflow, so Claude redirects instead of retrying.
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": (f"Refunds over {REFUND_LIMIT:.0f} need approval. Call escalate_to_human "
                                         "with the customer ID, root cause, amount and your recommendation."),
        }}
    return {}


def build_options(shop_servers: dict) -> ClaudeAgentOptions:
    return ClaudeAgentOptions(
        mcp_servers=shop_servers,
        hooks={
            # Before the model reads a result: one format for every system.
            "PostToolUse": [HookMatcher(matcher="^mcp__(orders|warehouse|carrier)__", hooks=[normalise_result])],
            # Before a tool runs: business rules that must hold every time.
            "PreToolUse": [HookMatcher(matcher="mcp__orders__process_refund", hooks=[refund_policy], on_failure="block")],
        },
    )
  • Other ways to redirect. ask turns the call into an approval request for a person, and defer stops the turn so your application can hold the call for approval and resume it. updatedInput rewrites arguments (for example, capping a field), but silently changing a refund amount would mislead both the customer and Claude, so a deny with a clear reason is the cleaner fit here.
  • Check arguments inside the callback. Matchers only see tool names; the amount is read from tool_input.

Registering the hooks

Task 1.5Where each hook goes, and how they combine.

  • Hooks are passed in ClaudeAgentOptions(hooks={...}), keyed by event, each entry a HookMatcher with a matcher pattern and one or more async callbacks (input_data, tool_use_id, context). Shell-command hooks from .claude/settings.json also run when that setting source is loaded.
  • Several hooks on one event run in parallel; for permission decisions the most restrictive wins (deny, then defer, then ask, then allow), so write each check to stand on its own.
  • For a compliance hook, set on_failure="block" so a crash blocks the call instead of letting it through, and remember that a PreToolUse timeout blocks too (task 1.4 has the details).

Hooks or prompt instructions

Task 1.5Deterministic guarantees versus probabilistic compliance.

"Never refund more than $500 without approval" in the system prompt will be followed nearly always; a hook makes it always. "Treat 3 as shipped" in the prompt will usually be applied; a hook applies it to every result. Choose by the cost of the rare miss:

  • Hooks for rules that must hold every time (money, identity, data protection, irreversible actions) and for conversions that must be exact. They cost a little code and are tested like code.
  • Prompt instructions for judgement and preferences: tone, which question to ask first, when an apology is due. Hard-coding these makes the agent rigid.
  • Both for important rules: the prompt tells Claude the policy so it plans around it, and the hook is the guarantee.

Wrong answers that sound strong. Moving the rule to the top of the system prompt, writing it in capitals, repeating it in every turn, or adding examples of refused refunds all raise compliance without making it certain. When a scenario says the rule "must" hold or failures are unacceptable, pick the hook.

Key takeaways

  • PreToolUse runs before a tool executes: deny (reason to Claude), allow, ask, defer, or rewrite input. Compliance rules go here because executed actions can't be undone.
  • PostToolUse runs after a successful call: updatedToolOutput replaces what Claude sees, additionalContext adds a note, decision: "block" attaches a reason but keeps the original.
  • Normalise heterogeneous results (Unix seconds or milliseconds, ISO 8601 with offsets, numeric or coded statuses) to one format in a PostToolUse hook matched to the MCP servers, keeping the output's shape and flagging unknown values.
  • Rewriting output doesn't undo side effects and isn't what telemetry records; mismatched shapes are ignored for built-in tools; MCP output isn't validated.
  • Block a policy violation (refund over $500) with a deny whose reason redirects to the alternative workflow (human escalation).
  • Hooks give deterministic guarantees, prompts probabilistic compliance: use hooks when a rule must always hold, prompts for judgement, both for important rules.
