Overview

Task 4.5

Design efficient batch processing strategies.

The exam guide asks you to know what the Message Batches API offers (half the cost, up to 24 hours to process, no latency guarantee), which workloads it suits (overnight reports, weekly audits, nightly test generation) and which it doesn't (blocking checks such as pre-merge reviews), that a batch request can't run tools mid-request and continue, and how custom_id ties results back to requests. In practice it asks you to match the API to the workflow's latency needs, work out how often to submit to meet an SLA, resubmit only the failed documents (with fixes such as chunking an oversized one), and refine the prompt on a sample before processing thousands. The request mechanics are in the developer notes (batch or real time); batch economics in more depth are in their cost page (batches and budgets).

Batches cost half, finish within 24 hours, and return results in any order

Task 4.5The Message Batches API in brief.

  • Cost: half the normal price on every token, cached ones included.
  • Time: most batches finish within an hour, but there's no latency guarantee; requests not processed within 24 hours expire.
  • Size: up to 100,000 requests or 256 MB per batch.
  • Results: downloadable for 29 days, returned in any order, each tagged with the custom_id you gave its request (1 to 64 letters, digits, hyphens or underscores). Match by custom_id, never by position.
  • Billing of failures: errored, cancelled and expired requests aren't billed.
  • Not in batches: streaming and fast mode, and the server-side refusal fallback; a refusal comes back as a succeeded result with stop reason refusal. Batches also aren't available on every cloud platform and aren't covered by zero data retention.

Use batches only when nothing is blocked waiting for the result

Task 4.5Matching the API to the workflow's latency requirement.

  • Synchronous when someone or something is blocked waiting: a pre-merge review gates the merge, a support agent is answering a customer, a deploy pipeline waits for a check. Half price is no use if the result arrives tomorrow.
  • Batch when the work is non-blocking and latency-tolerant: a weekly contract audit, overnight reports, nightly test generation, re-classifying an archive, running evaluations.

"Use batches to halve the cost of pre-merge reviews" is the classic wrong answer: the developer would wait up to a day to merge. Cost savings never override a blocking latency requirement.

A batch request can't run tools and continue, so give it everything up front

Task 4.5One request, one response, no conversation.

Each item in a batch is a single Messages API call. If Claude's response ends with a tool_use block, nothing runs the tool and sends the result back within that request: the item simply finishes with the tool call. Agent loops that need several tool rounds (task 1.1) therefore don't fit in one batch request. The options are to give each request everything it needs up front (the full contract text, not a tool to fetch it), or to run tool rounds as successive batches or synchronous calls. Single-step jobs such as extraction, classification and auditing a provided document are the natural batch workload.

Submit often enough that the interval plus 24 hours fits the SLA

Task 4.5How often to submit so the slowest document still meets its deadline.

A document that arrives just after a submission waits for the next one, then up to 24 hours more for the batch. So the worst case is the submission interval plus the processing window, and that has to fit inside the SLA with some margin:

  • 30-hour SLA: 30 minus 24 hours of processing leaves 6 hours; keep 2 hours of margin and submit every 4 hours. That's the guide's example.
  • 48-hour SLA with a 4-hour margin: submit every 20 hours, so once a day is fine.
  • An SLA under 24 hours can't be guaranteed by batches alone, even though most batches finish within an hour: there's no latency guarantee.

The submit_interval_hours function in the pipeline below does this sum.

Match results by custom_id and resubmit only the failures, each with its fix

Task 4.5Submit, match by custom_id, resubmit only the failures.

Take a weekly audit of a few thousand contracts for long payment terms and missing liability caps, with results due within 30 hours of a contract arriving.

batch_pipeline.py (Python, anthropic SDK)Optional 
"""Weekly supplier-contract audit on the Message Batches API: pilot first, submit, match by custom_id,
and resubmit only what failed."""
import time

import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()
SYSTEM = "Audit this supplier contract for payment terms over 60 days and missing liability caps. Reply as JSON."


def submit_interval_hours(sla_hours: float, processing_hours: float = 24, margin_hours: float = 2) -> float:
    """How often to submit so the slowest document still meets the SLA: wait + processing + margin <= SLA."""
    return sla_hours - processing_hours - margin_hours   # a 30 h SLA gives a 4 h submission window


def params(text: str) -> MessageCreateParamsNonStreaming:
    return MessageCreateParamsNonStreaming(model="claude-sonnet-5-5", max_tokens=2000, system=SYSTEM,
                                           messages=[{"role": "user", "content": f"<contract>{text}</contract>"}])


def pilot(sample: dict[str, str], looks_right) -> float:
    """Refine the prompt on a few documents synchronously before paying for thousands."""
    passed = sum(looks_right(client.messages.create(**params(text))) for text in sample.values())
    return passed / len(sample)


def run_batch(docs: dict[str, str]) -> dict:
    # custom_id: 1-64 characters (letters, digits, - and _), so results can be matched whatever their order.
    batch = client.messages.batches.create(requests=[Request(custom_id=doc_id, params=params(text))
                                                     for doc_id, text in docs.items()])
    while client.messages.batches.retrieve(batch.id).processing_status != "ended":
        time.sleep(60)
    return {item.custom_id: item.result for item in client.messages.batches.results(batch.id)}


def chunk(text: str, size: int = 150_000) -> list[str]:
    return [text[i:i + size] for i in range(0, len(text), size)]


def audit(docs: dict[str, str]) -> tuple[dict, list[str]]:
    done, failed = {}, []
    results = run_batch(docs)
    retry = {}
    for doc_id, result in results.items():
        if result.type == "succeeded":
            done[doc_id] = result.message
        elif result.type == "errored" and "prompt is too long" in result.error.error.message:
            # Too big for one request: resubmit just this document, split into parts.
            for n, part in enumerate(chunk(docs[doc_id]), start=1):
                retry[f"{doc_id}-part{n}"] = part
        elif result.type in ("expired", "canceled"):
            retry[doc_id] = docs[doc_id]       # not billed; send again unchanged
        else:
            failed.append(doc_id)              # any other error: a person looks at it
    if retry:
        for doc_id, result in run_batch(retry).items():
            if result.type == "succeeded":
                done[doc_id] = result.message
            else:
                failed.append(doc_id)          # failed twice: stop resubmitting
    return done, failed
  • custom_id is the contract's ID, so each result maps straight back to its document.
  • Only failures are resubmitted, each with the fix its failure needs: a contract too long for the context window is split into parts with new IDs (c-peak-part1 and so on), expired or cancelled items go again unchanged, and anything else goes to a person rather than round again.
  • Resubmission is bounded: one retry batch; items that fail twice stop. Errors only show up once a batch has ended, which is another reason to try requests synchronously first.

Pilot the prompt on a sample before submitting thousands

Task 4.5Piloting on a sample before paying for thousands.

A prompt flaw in a batch of 5,000 contracts costs 5,000 requests, a day's wait, and another batch to redo them. Running the prompt synchronously on a representative sample of 20 to 50 first (the pilot function) shows the first-pass success rate in minutes; refine until it's high, then submit the full volume. The same logic suggests sending one request with a shared prompt prefix before the rest when relying on caching, since cache hits inside a batch are best-effort.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A team wants to halve the cost of pre-merge code reviews by moving them to the Message Batches API. What is the problem?
  1. A. Batches can’t review code
  2. B. Developers would wait up to 24 hours to merge, since batches have no latency guarantee
  3. C. Batches cost more
  4. D. Reviews need streaming
Answer
B
Why
Savings never override a blocking latency requirement; pre-merge checks stay synchronous.
Question 2
Scenario
Results must be ready within 30 hours of a document arriving, using batches. How often should they submit?
  1. A. Once a day
  2. B. About every 4 hours
  3. C. Every 24 hours
  4. D. Batches can’t meet any SLA
Answer
B
Why
Worst case is the submit interval plus 24 hours of processing; 30 − 24 leaves 6 hours, so about 4 with margin.
Question 3
Scenario
Batch results come back in a different order from the requests. How should the pipeline match them?
  1. A. By position
  2. B. By the custom_id set on each request
  3. C. By timestamp
  4. D. By response length
Answer
B
Why
Results are returned in any order; custom_id is what ties each result to its request.
Question 4
Scenario
A few requests in a batch fail because their documents exceed the context window. What should happen next?
  1. A. Resubmit the whole batch
  2. B. Resubmit only those documents, split into parts with new custom_ids
  3. C. Give up on them
  4. D. Switch every request to synchronous
Answer
B
Why
Resubmitting only the failures, each with the fix its failure needs, saves cost and time.

Key takeaways

  • Batches: 50% off, up to 24 hours with no latency guarantee, up to 100,000 requests per batch, results in any order for 29 days, failures not billed.
  • Synchronous for blocking work (pre-merge checks, live conversations); batch for non-blocking, latency-tolerant work (overnight reports, weekly audits, nightly test generation).
  • A batch request is a single call: it can't run tools mid-request and continue, so give it everything it needs or run tool rounds separately.
  • Submission interval plus 24 hours plus a margin must fit the SLA: every 4 hours for a 30-hour SLA.
  • Correlate by custom_id; resubmit only failed items, fixed for their failure (chunk oversized documents, resend expired ones); pilot the prompt on a sample first.
