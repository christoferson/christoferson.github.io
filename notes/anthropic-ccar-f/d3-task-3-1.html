Overview

Task 3.1

Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization.

The exam guide asks you to know the user, project and directory levels of CLAUDE.md, that user-level files aren't shared through version control, how imports keep the main file modular, that .claude/rules/ is an alternative to one large file, and how to work out why one developer gets instructions another doesn't. Path-scoped rules are covered in depth in task 3.3.

Sources: the Claude Code documentation (memory, best practices, features overview, commands) and the Claude Code changelog, checked on 8 November 2026 against Claude Code 2.1.303. The docs are copyrighted, so they're paraphrased here.

Running example. The outdoor-gear shop's web app lives in one Git repository: a TypeScript API in src/api/, a payments package in packages/payments/, and tests in tests/. Five developers use Claude Code on it, and CI runs it on pull requests (task 3.6).

The scopes

Task 3.1Every place a CLAUDE.md can live, and who it reaches.

ScopeLocationShared with
Managed policyA system path set by IT (for example /etc/claude-code/CLAUDE.md on Linux)Everyone on the machine; can't be excluded
User~/.claude/CLAUDE.mdOnly you, in every project
Project./CLAUDE.md or ./.claude/CLAUDE.mdThe team, through Git
Local./CLAUDE.local.md (add it to .gitignore)Only you, in this project
Subdirectorypackages/payments/CLAUDE.md and similarThe team; loads only when Claude works in that folder

"The new developer doesn't get our conventions." The classic cause: the instructions are in someone's ~/.claude/CLAUDE.md, which lives in their home folder and is never committed. The fix is to move them into the project's CLAUDE.md, .claude/CLAUDE.md or .claude/rules/ and commit them.

Beyond the exam guide's three levels. The guide names user, project and directory levels. The current docs also list the managed policy file and CLAUDE.local.md, plus user-level rules in ~/.claude/rules/. Since 2.1.277 Claude Code also reads an AGENTS.md, but only when no CLAUDE.md or CLAUDE.local.md exists in the folder or above it.

How files load and combine

Task 3.1Which files load at launch, which load later, and what happens when they disagree.

  • At launch, Claude Code walks from the folder you started in up to the filesystem root and loads every CLAUDE.md and CLAUDE.local.md it finds, plus the user and managed files and rules without path scoping.
  • Later, a CLAUDE.md in a subfolder below where you started loads only when Claude reads, writes or edits a file in that subfolder.
  • Combined, not overridden. Everything is concatenated. Nothing has formal precedence: if two files contradict each other, the docs say Claude may pick one arbitrarily. Content nearer your working folder comes later; in one folder, CLAUDE.local.md follows CLAUDE.md.
  • Delivered as context, not enforced. CLAUDE.md arrives as a user message after the system prompt. It's guidance Claude usually follows, not a guarantee.

Rules that must never be broken belong in settings (permissions.deny, sandboxing, managed settings) or hooks, not in CLAUDE.md. Writing "NEVER" in capitals isn't enforcement, and the current best-practices page advises against piling on emphasis, because it makes Claude over-apply the rule.

A project CLAUDE.md

Task 3.1What a lean, shared project file looks like.

CLAUDE.md (project, committed) 
# Shop web app

## Commands
- Install: `pnpm install`
- Test one file:
  `pnpm vitest run <file>`
- Typecheck: `pnpm tsc --noEmit`

## Conventions
- Money is integer cents, never floats
- Use errors from src/lib/errors.ts
- src/legacy/ is live; don't copy it

## Gotchas
- Integration tests need DATABASE_URL
  (see .env.example)

## Standards
- API style: @docs/api-conventions.md
- Git flow: @docs/git-workflow.md

Keep each file under about 200 lines: longer files cost context and get followed less reliably. Put in what Claude can't work out by reading the code (commands, conventions that differ from the defaults, misleading areas, decisions nobody wrote down) and leave out a description of the folder layout, which Claude can read for itself. /init generates a starter file from the codebase, or suggests improvements if one exists.

~/.claude/CLAUDE.md (user, personal) 
# My preferences (all projects)

- Explain the plan before big edits
- Prefer small commits, one topic each
- Personal snippets:
  @~/.claude/snippets.md

Imports

Task 3.1Splitting standards into files with @path references.

Write @path/to/file anywhere in a CLAUDE.md, and that file is pulled in with it. The details that matter:

  • Relative paths resolve from the importing file's folder, not your working folder; @~/... reaches your home folder.
  • Imports can nest up to four hops deep.
  • An @path inside backticks or a code block is just text, not an import.
  • A project file that imports something outside the project triggers a one-time approval prompt. If you decline, those imports stay off.

Imports organize; they don't save context. Imported files load at the same time as the file that imports them, so a 600-line standard split into three imports still costs 600 lines every session. To load guidance only when it's relevant, use path-scoped rules (task 3.3), a subdirectory CLAUDE.md, or a skill (task 3.2). Also, there's no @import keyword: the syntax is just @ and a path.

Rules and subdirectory files

Task 3.1Breaking one large file into topic files and per-package files.

Instead of one monolithic CLAUDE.md, put one-topic Markdown files in .claude/rules/ (subfolders are fine). A rule with no frontmatter loads at launch, just like the project CLAUDE.md; adding paths: frontmatter makes it load only for matching files.

.claude/rules/testing.md (always loaded) 
# Testing

- Vitest only; no Jest APIs
- One `describe` per module
- Use factories in tests/factories/
packages/payments/CLAUDE.md (on demand) 
# payments package

- Every charge call needs an
  idempotency key
- Never log card data or tokens
- Run `pnpm test --filter payments`

The payments file loads only once Claude opens a file in packages/payments/, so developers working elsewhere don't pay for it. The package owners can keep it next to their code.

Checking what loaded

Task 3.1Diagnosing inconsistent behaviour between developers.

CommandWhat it shows or does
/memoryLists the memory files for the user and project scopes (including ones not created yet), opens them for editing, and toggles auto memory
/context allThe "Memory files" list shows what actually loaded in this session
/initGenerates or improves the project CLAUDE.md
InstructionsLoaded hookLogs each CLAUDE.md or rule as it loads, and why: useful for files that load on demand

The exam guide names /memory for checking which memory files are loaded. Today's docs point to /context all for that, because /memory also lists files that don't exist yet. Subdirectory files won't appear at the start of a session in either, since they haven't loaded yet.

The # shortcut is gone, and "remember this" means auto memory. Older guides say to type # to add a line to CLAUDE.md; it was removed in 2.0.70. Ask Claude to add the line to CLAUDE.md, or edit it through /memory. Since 2.1.59, Claude Code has auto memory: notes Claude writes itself into ~/.claude/projects/<project>/memory/ (the first 200 lines or 25 KB of its MEMORY.md load each session). Auto memory is personal and machine-local, so it never replaces a committed CLAUDE.md for team conventions.

Key takeaways

  • Scopes: managed policy, user (~/.claude/CLAUDE.md, personal), project (./CLAUDE.md or .claude/CLAUDE.md, committed), local (CLAUDE.local.md, gitignored), subdirectory files.
  • Files from the working folder up load at launch; subfolder files load when Claude touches a file there. Everything is concatenated; contradictions are resolved arbitrarily.
  • A teammate missing conventions usually means they're in someone's user-level file. Move them to a committed project file or rule.
  • @path imports: relative to the importing file, up to four hops, ignored in code. They organize but don't reduce context.
  • Split large files into .claude/rules/ topics and per-package CLAUDE.md files; keep each under about 200 lines. Hard rules go in settings or hooks.
  • Check what loaded with /context all (the guide says /memory). The # shortcut is gone; auto memory holds Claude's own per-machine notes.
