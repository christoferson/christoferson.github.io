1.1: Agentic Loops

How an application lets Claude work through a task on its own: send a request, run the tools Claude asks for, return the results, and repeat until Claude is finished, deciding when to stop from the API's stop reason rather than from the text.

Overview

Task 1.1

Design and implement agentic loops for autonomous task execution.

The exam guide asks you to know the loop's lifecycle (request, inspect stop_reason, run tools, return results), how tool results build up the conversation history, and the difference between Claude choosing its next step and code following a fixed sequence. In practice it asks you to write a loop that continues on "tool_use" and ends on "end_turn", and to avoid three anti-patterns: parsing Claude's wording to decide when to stop, relying on an iteration cap as the main stopping rule, and treating the presence of text as a sign the task is done. Coordinators and subagents are task 1.2, and tool design task 2.1.

Sources: the Claude API documentation on tool use and stop reasons, the Claude Agent SDK documentation, and Anthropic's "Building effective agents" (December 2024), all checked on 8 November 2026. The docs are copyrighted, so they're paraphrased here with short quotes. The code is my own, following the docs' loop pattern, and was tested with anthropic 2.6.0 and claude-agent-sdk 0.2.179 against a mocked client, not the live API.

Running example. An online outdoor-gear shop builds a customer support agent. In this task it has one tool, get_order, and answers questions such as "Where is order A123?" Later tasks add refunds, escalation and more agents.

The loop

Task 1.1The agentic loop lifecycle, from request to final answer.

"Building effective agents" describes agents as "typically just LLMs using tools based on environmental feedback in a loop." With the Messages API, your code is that loop:

  1. Send a requestWith the conversation so far and the tool definitions.
  2. Check stop_reasonIf it's "tool_use", Claude wants one or more tools run. Anything else ends the loop.
  3. Run the requested toolsYour code executes each tool_use block; Claude never runs your tools itself.
  4. Return the resultsAppend Claude's whole turn, then one user message holding a tool_result for every call.
  5. RepeatThe next request carries the complete history, so Claude can reason about what it learned and choose the next step.

The docs put the rule simply: while stop_reason == "tool_use", run the tools and continue; the loop exits on any other stop reason, after which "your application should handle" whichever one it was. The API is stateless: the only memory between iterations is the messages list you send back.

Tools and tool_use blocks

Task 1.1What goes into a request, and what a tool call looks like coming back.

Each tool has a name (letters, digits, _ and -, up to 128 characters), a description and an input_schema (JSON Schema). The docs call the description "by far the most important factor in tool performance"; tool design is task 2.1.

When Claude decides to call a tool, the response contains a tool_use block with an id (like toolu_01A0...), the tool name and an input object matching the schema, and the response's stop_reason is "tool_use". The same response often starts with a text block ("I'll look that order up."), and can contain several tool_use blocks, because by default Claude may call more than one tool at once. So scan the whole content array; don't assume the tool call is the first or only block.

Tool kindWho runs itWhat your loop does
Client tools (your own, plus Anthropic-defined ones such as bash, text editor and memory)Your applicationExecutes the call and sends back a tool_result
Server tools (web search, web fetch, code execution, tool search)Anthropic, inside the APINothing per call: results arrive in the response. Handle pause_turn (below)

Stop reasons

Task 1.1Every value of stop_reason, and what the loop does with each.

The docs distinguish errors (HTTP 4xx and 5xx, a failed request) from stop_reason, which "tells you why Claude completed its response generation". There are seven values:

stop_reasonMeaningIn the loop
tool_useClaude is calling a tool you need to runRun every call, return the results, continue
end_turnClaude finished naturallyExit and use the answer
max_tokensYour max_tokens limit was reachedExit or continue the output; if the last block is an unfinished tool_use, retry with a higher limit rather than run a partial call
stop_sequenceOne of your stop sequences was generatedExit; stop_sequence says which one
pause_turnA server-tool loop hit its iteration limit (10 per request by default)Send the response back as it is to let Claude carry on, keeping any container ID
refusalClaude declined to respond (HTTP 200, not an error)Exit; stop_details gives the category
model_context_window_exceededThe response filled the model's context windowExit; treat the output as truncated but valid

"Stop on end_turn" isn't the whole rule. The exam guide frames the loop as continue on tool_use, stop on end_turn. That's the core, but a loop that only checks for end_turn can spin forever on a refusal or a token limit. Write it as: continue while the reason is tool_use; otherwise exit and branch on which reason it was. Only end_turn means the task finished normally.

pause_turn isn't "done". It only happens with server tools, and never while a client tool_use is waiting for you. A loop that uses web search or code execution needs a branch that sends the paused response straight back.

Returning results

Task 1.1How tool results are added to the conversation history.

The Claude API has no separate tool role: results go back in a user message as tool_result blocks, each pointing at its call with tool_use_id. content can be a string or a list of blocks, and is_error: true marks a failure so Claude can retry or work around it.

A tool result message (JSON) 
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_01A09q90...",
      "content": "A123: shipped, ETA 2d"
    }
  ]
}

The ordering rules are strict:

  • First append Claude's full assistant turn (its whole content, text and tool calls), then the user message with the results. Nothing may come between them.
  • In that user message, the tool_result blocks come first. Text before them is a 400 error.
  • Every tool_use needs a result, all in one user message. If you skip a call (because an earlier one failed, say), still return a result for it with is_error: true and a reason.

Two quiet mistakes. Sending parallel results in separate user messages works, but the docs say it "teaches" Claude to stop making parallel calls. And adding your own text after the results is a common cause of empty end_turn responses; send only the results. To limit Claude to one call per turn, set disable_parallel_tool_use: true, which goes inside tool_choice, not at the top level.

A complete loop

Task 1.1Loop control flow driven by stop_reason, with results fed back each iteration.

support_agent.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()

tools = [{
    "name": "get_order",
    "description": (
        "Look up an order by ID. "
        "Returns status and ETA."),
    "input_schema": {
        "type": "object",
        "properties": {
            "order_id": {
                "type": "string"},
        },
        "required": ["order_id"],
    },
}]


def run_tool(name, args):
    if name == "get_order":
        oid = args["order_id"]
        # Stand-in for a real lookup
        return f"{oid}: shipped, ETA 2d"
    raise ValueError(f"Unknown: {name}")


messages = [{
    "role": "user",
    "content": "Where is order A123?",
}]

while True:
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1024,
        tools=tools,
        messages=messages,
    )
    # Keep the whole assistant turn
    messages.append({
        "role": "assistant",
        "content": resp.content,
    })
    if resp.stop_reason != "tool_use":
        break  # handled below

    results = []
    for b in resp.content:
        if b.type != "tool_use":
            continue
        try:
            out = run_tool(b.name,
                           b.input)
            err = False
        except Exception as e:
            out, err = str(e), True
        results.append({
            "type": "tool_result",
            "tool_use_id": b.id,
            "content": out,
            "is_error": err,
        })
    # All results in ONE user message
    messages.append({
        "role": "user",
        "content": results,
    })

if resp.stop_reason == "end_turn":
    for b in resp.content:
        if b.type == "text":
            print(b.text)
else:
    print("Stopped:", resp.stop_reason)

Things to notice: the loop never looks at Claude's wording; a tool failure goes back as an error result instead of crashing the loop; and the number of iterations isn't known in advance. As the docs' tutorial says, the loop "might run once or several times depending on how Claude breaks down the task." This loop has no server tools, so it needs no pause_turn branch.

Model-driven or predefined

Task 1.1When Claude should choose the next step, and when code should.

"Building effective agents" separates two designs. Workflows are "systems where LLMs and tools are orchestrated through predefined code paths"; agents are "systems where LLMs dynamically direct their own processes and tool usage".

Predefined workflowModel-driven agent loop
Who picks the next stepYour code: a fixed sequence or decision treeClaude, from the conversation and tool results so far
Number of stepsKnown in advanceVaries with the task
StrengthPredictability and consistencyFlexibility for open-ended problems
FitsWell-defined tasks, such as "classify, then route to one of three handlers"Problems "where it's difficult or impossible to predict the required number of steps"

The article's advice is to start with the simplest design that works and add agency only when it pays off. The shop's order questions vary a lot (one lookup, or a lookup and then a returns check), so a loop where Claude decides fits better than a hard-coded sequence. Rules that must always hold, such as "verify the customer before a refund", belong in code rather than in Claude's choices; that's task 1.4.

Anti-patterns and safety nets

Task 1.1Three ways to decide "done" wrongly, and where an iteration cap fits.

Anti-patternWhy it failsInstead
Parsing Claude's words ("I'm done", "FINAL ANSWER") to end the loopPhrasing varies; the docs say not to rely on formatting conventions in generated textUse stop_reason. The docs: if you're writing a regex to pull a decision out of the output, "that decision should have been a tool call"
Treating any text in the response as completionTool-call responses often include text ("Let me check..."), and an end_turn can even be emptyOnly stop_reason says whether Claude is finished
An iteration cap as the main way to stopCuts off tasks that legitimately need more steps, and hides why the loop didn't finishLet the task end on end_turn; keep a cap only as a safety net that reports an error

Caps still have a place. "Building effective agents" notes it's "common to include stopping conditions (such as a maximum number of iterations) to maintain control." Anthropic's own tooling treats them that way: the caps are optional, unlimited by default, and hitting one is reported as an error, not a success.

Spotting the right answer. In a question about loop termination, the answer that checks stop_reason beats one that inspects the text, counts iterations or searches for keywords. A cap appears in a good answer only as an extra guard against runaway loops or cost.

Letting an SDK run the loop

Task 1.1The tool runner and the Claude Agent SDK, which implement the same loop for you.

OptionWhat it doesStopping
Your own loop (above)Full control; the docs recommend it when you need human approval, custom logging or conditional executionWhatever you write
Tool runner (beta), client.beta.messages.tool_runnerRuns your @beta_tool functions, manages the history and passes tool exceptions back as error resultsEnds when a response has no tool call; max_iterations is optional
Claude Agent SDK, query() or ClaudeSDKClientRuns "the same execution loop that powers Claude Code", with built-in tools (Read, Bash, Grep and more), hooks and sessionsEnds when Claude replies without tool calls; max_turns and max_budget_usd default to no limit
Agent SDK with a safety net (Python) 
import anyio
from claude_agent_sdk import (
    ClaudeAgentOptions,
    ResultMessage, query)

opts = ClaudeAgentOptions(
    max_turns=30,  # runaway guard
)


async def main():
    async for msg in query(
            prompt="List open tickets",
            options=opts):
        if isinstance(msg, ResultMessage):
            # success, error_max_turns..
            print(msg.subtype)

anyio.run(main)

When the Agent SDK stops, it emits a result message whose subtype says why: success (with the final result), or an error such as error_max_turns or error_max_budget_usd, which has no result field. Every result carries the cost, usage, turn count and session ID.

Renamed: Claude Code SDK. Key takeaways

  • The loop: request, check stop_reason, run every tool_use, return the results, repeat with the full history. The API is stateless; the messages list is the memory.
  • Continue only while stop_reason is tool_use. Exit on anything else and branch: end_turn (done), max_tokens, stop_sequence, pause_turn (send it back: server tools), refusal, model_context_window_exceeded.
  • Results go in a user message as tool_result blocks with tool_use_id: right after the assistant turn, results first, one result per call, all in one message, is_error: true for failures.
  • Agents let Claude choose the next step; workflows follow predefined code paths. Use an agent when the number of steps can't be predicted, and put must-always rules in code.
  • Don't end the loop by parsing text, by the presence of text, or by an iteration cap. Caps are a safety net that reports an error (Agent SDK error_max_turns).
  • The tool runner (beta) and the Claude Agent SDK (renamed from the Claude Code SDK in September 2025) run the same loop for you; both stop when Claude replies without tool calls.
