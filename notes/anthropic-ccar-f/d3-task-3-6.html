Overview

Task 3.6

Integrate Claude Code into CI/CD pipelines.

The exam guide asks you to know the -p (--print) flag for non-interactive runs, --output-format json with --json-schema for structured CI output, CLAUDE.md as the way to give CI runs project context (test standards, fixtures, review criteria), and why a fresh, independent session reviews code better than the one that wrote it. In practice: avoid runs that wait for input, turn findings into pull request comments, send previous findings on re-runs so only new issues are reported, and give Claude the existing tests so it doesn't duplicate them.

Sources: the Claude Code documentation (programmatic usage, CLI reference, permissions, permission modes, GitHub Actions, GitLab CI/CD, best practices), the claude-code-action repository (MIT licence) and the changelog, checked on 8 November 2026 against Claude Code 2.1.303, paraphrased. The JSON schema and the jq filters below were checked against sample output; the workflows weren't run.

Running example. The shop wants every pull request reviewed for bugs and security problems in the cart and checkout code, with comments on the PR, and a CI job that fails when a high-severity finding appears.

Non-interactive runs

Task 3.6The -p flag and the options that only work with it.

claude -p "prompt" runs the task without the interactive interface, prints the result and exits: 0 on success, non-zero when the run fails. Input can be piped in (up to 10 MB), so git diff main | claude -p "review this" hands Claude the diff without needing any Bash permission to read it.

FlagEffect
--output-formattext (default), json (one result object) or stream-json (one event per line)
--json-schemaReturns data matching your JSON Schema in the result's structured_output field
--max-turnsCaps the agent's turns; no limit by default
--max-budget-usdStops once the estimated cost reaches the amount
--allowedTools, --disallowedToolsTools that may run without asking, and tools that are denied
--permission-modeFor example dontAsk for locked-down CI (below)
--append-system-promptAdds instructions while keeping the default system prompt

The first four work only with -p. The JSON result includes result (the text), session_id, is_error, num_turns and total_cost_usd, and a subtype that is success or an error such as error_max_turns, error_max_budget_usd or error_max_structured_output_retries. Error results have no result field.

Structured results

Task 3.6Getting findings a pipeline can act on.

review.sh (shell, CI step) 
# findings schema: list of issues
SCHEMA='{"type":"object",
 "properties":{"findings":{
  "type":"array","items":{
   "type":"object","properties":{
    "file":{"type":"string"},
    "line":{"type":"integer"},
    "severity":{"enum":
     ["high","medium","low"]},
    "issue":{"type":"string"}},
   "required":["file","line",
    "severity","issue"]}}},
 "required":["findings"]}'

# diff via stdin: no Bash grant needed
git diff origin/main...HEAD \
 | claude -p \
  "Review this diff for bugs in the
cart and checkout code. Use CLAUDE.md
criteria. Skip style issues." \
  --output-format json \
  --json-schema "$SCHEMA" \
  --permission-mode dontAsk \
  --allowedTools "Read" \
  --max-turns 5 \
  > review.json

# no structured output = failed run
jq -e '.structured_output' \
  review.json > /dev/null || exit 1

# fail on any high-severity finding
HIGH=$(jq '[
  .structured_output.findings[]
  | select(.severity=="high")]
  | length' review.json)
[ "$HIGH" -eq 0 ] || exit 1

Look in structured_output, and check it's there. With --json-schema, the data is in structured_output, not result. The field is missing if the run failed or Claude declined, even on a result marked success, so test for it before using it. Schemas are checked as JSON Schema draft-07; since 2.1.205 an invalid schema is an error (before that it was silently ignored).

Each finding has a file, a line and a message, which is exactly what a script needs to post inline pull request comments through the GitHub API, or to raise annotations.

Permissions with nobody to ask

Task 3.6What happens to permission prompts in CI, and how to grant just enough.

The exam guide's reason for -p is to avoid jobs that hang waiting for input. In a -p run, a tool call that nothing approves is denied, not left waiting: the run carries on, and the denials are listed in permission_denials. Since 2.1.302, -p runs with no mode set start in default (Manual) mode.

  • --permission-mode dontAsk denies anything that would prompt; the docs call it useful for locked-down CI. Combine it with --allowedTools for exactly what the job needs.
  • Rule syntax: Bash(pnpm test *) allows any command starting pnpm test. The older form Bash(npm test:*) still works and means the same. An allow rule doesn't cover cmd && other: every part must be allowed.
  • Deny rules apply in every mode. bypassPermissions belongs only in isolated containers or VMs.

Untrusted folders and --bare. When -p runs in a folder nobody has trusted, the repository's .claude/settings.json allow rules are ignored, but its hooks still run and its .mcp.json servers still connect. The docs recommend --bare for scripted runs: it skips hooks, skills, plugins, MCP servers and auto memory, but also CLAUDE.md. So with --bare, pass context explicitly (for example with --append-system-prompt-file); without it, CLAUDE.md loads as usual.

The GitHub Action

Task 3.6anthropics/claude-code-action for mentions and automated reviews.

The action (v1, generally available since August 2025) runs Claude Code inside a GitHub Actions job. Run /install-github-app in Claude Code to set it up: it installs the Claude GitHub App, stores the API key as a repository secret and opens a pull request adding the workflow. It works in two ways, picked automatically:

  • Interactive: no prompt input, so it waits for @claude in an issue or PR comment and replies there.
  • Automation: a prompt input, so it runs on the event itself (a pull request, a schedule).
.github/workflows/claude-review.yml 
name: Claude PR review
on:
  pull_request:
    types: [opened, synchronize,
      ready_for_review, reopened]
concurrency:
  group: review-${{ github.ref }}
  cancel-in-progress: true
jobs:
  review:
    if: >-
      !github.event.pull_request.draft
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      contents: read
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v7
      - uses: >-
          anthropics/claude-code-action@v1
        with:
          anthropic_api_key: >-
            ${{secrets.ANTHROPIC_API_KEY}}
          prompt: |
            REPO: ${{ github.repository }}
            PR: ${{ github.event.number }}
            Review the cart and checkout
            changes against the review
            criteria in CLAUDE.md. Report
            only bugs and security issues;
            skip style. Post one summary
            with gh pr comment.
          claude_args: |
            --max-turns 8
            --allowedTools "Bash(gh pr *)"

Bash(gh pr *) lets Claude read the diff and comment; the job's read-only contents permission stops it from merging. For comments on specific lines, the action provides an inline-comment tool that must be named in --allowedTools (its full name, mcp__github_inline_comment__create_inline_comment, is too long for this layout). Pass --json-schema in claude_args, and the action exposes the result as a structured_output step output for later steps.

Beta inputs removed in v1. Older workflows use @beta with direct_prompt, mode, model, max_turns, allowed_tools and custom_instructions. In v1, mode is gone (detected automatically), direct_prompt became prompt, and the rest moved into claude_args as CLI flags (--model, --max-turns, --allowedTools, --append-system-prompt).

GitLab: the GitLab CI/CD integration is in beta and maintained by GitLab, not Anthropic. There's no packaged action: a job installs Claude Code and runs claude -p, with the API key in a masked CI/CD variable.

Context and review quality

Task 3.6Making automated reviews accurate, independent and not repetitive.

TechniqueWhy
Put review criteria, test standards and fixtures in CLAUDE.mdCI runs read it like any session, so every review uses the same rules (keep it short: it's read on every run)
Review in a fresh session, not the one that wrote the codeThe docs: a fresh reviewer helps "because it hasn't seen your reasoning", so it isn't swayed by it
Say what not to report ("skip style")A reviewer asked to find problems "will always find something"; narrow criteria cut false positives (task 4.1)
On re-runs, include the previous findings and ask only for new or unresolved onesAvoids posting the same comments on every push
When generating tests, give Claude the existing testsStops it proposing scenarios that are already covered

Anthropic also offers a managed Code Review service for Team and Enterprise plans, where several agents look for issues and a verification step filters out false positives before comments are posted.

Security and cost

Task 3.6Safe defaults for a job that reads untrusted pull requests.

RiskControl
Leaked keysKeys only in repository secrets or masked variables; prefer OIDC or workload identity federation over long-lived keys
Too much powerMinimal workflow permissions, narrow --allowedTools, dontAsk
Prompt injection in PR text or codeThe action strips hidden content such as HTML comments and invisible characters, but treat PR content as untrusted; filter by comment author where possible
Fork pull requestsPublic-repo forks get no secrets; with pull_request_target, never check out the untrusted head at the workspace root
Secrets in logsLeave show_full_output off, especially on public repositories
Runaway cost--max-turns, --max-budget-usd, job timeouts, concurrency groups; log total_cost_usd

Only users with write access can trigger the action, and bots are blocked unless listed. Commits pushed with the default GITHUB_TOKEN don't trigger other workflows, so CI won't run on Claude's commits unless you use a different token.

Key takeaways

  • claude -p runs non-interactively and exits 0 or non-zero; pipe input in. --output-format, --json-schema, --max-turns and --max-budget-usd are -p-only.
  • --json-schema results are in structured_output; check the field exists. Error results have no result.
  • In -p, unapproved tool calls are denied, not left hanging. Use dontAsk plus narrow --allowedTools; Bash(x:*) equals Bash(x *).
  • --bare is recommended for scripts but skips CLAUDE.md; an untrusted folder ignores the repo's allow rules but runs its hooks and MCP servers.
  • anthropics/claude-code-action@v1: prompt means automation, none means @claude mode; CLI options go in claude_args; set up with /install-github-app. Beta inputs such as direct_prompt and mode are gone.
  • Quality: CLAUDE.md for criteria, an independent reviewer session, "skip style", previous findings on re-runs, existing tests when generating tests.
  • Security: secrets or OIDC, minimal permissions, treat PR content as untrusted, care with forks, cost caps.
