4.6: Multi-Instance and Multi-Pass Review

Reviews that actually catch things: a second Claude instance that never saw how the code was written, passes that split a large review so nothing gets skimmed, and a verification step whose confidence decides which findings reach developers.

Overview

Task 4.6

Design multi-instance and multi-pass review architectures.

The exam guide asks you to know why self-review is limited (a model keeps the reasoning that produced its output and is less likely to question it in the same session), that independent review instances catch subtle issues better than self-review instructions or extended thinking, and that splitting large reviews into per-file and cross-file passes avoids attention dilution and contradictory findings. In practice it asks you to review generated code with a second, independent instance, to split multi-file reviews into local and integration passes, and to run verification passes in which the model reports its confidence per finding so findings can be routed. Splitting a review is worked through in task 1.6; writing the criteria is task 4.1.

Sources: the exam guide for the self-review argument; the Claude Code Code Review documentation and Claude's prompting best-practices guide for the supporting practice, checked on 19 November 2026 and paraphrased. The code is my own and was tested with anthropic 2.10.0 against a mocked API.

Running example. At the outdoor-gear shop, Claude writes a refund calculation from a short specification, and the pull-request reviewer then checks changes across src/api and packages/payments.

The limits of self-review

Task 4.6Why "now check your work" in the same session misses things.

When the instance that wrote the code is asked to review it in the same conversation, everything that led to the code is still in its context: the assumptions it made, the edge cases it decided not to handle, the reasons it found convincing. The guide's point is that this context makes it less likely to question those decisions. It tends to confirm the reasoning it already followed, so the same blind spot that produced a bug hides it in the review.

Asking harder ("review carefully", "be critical") or giving it more room to think doesn't remove that context; it reasons more about the same premises. The guide's claim is that an independent instance, one that sees only the requirement and the output, does better than either self-review instructions or extended thinking.

An independent reviewer

Task 4.6A second instance without the generator's reasoning context.

independent_review.py (Python, anthropic SDK)Optional 
"""Generate code in one instance, review it in another that never saw the generator's reasoning."""
import anthropic

client = anthropic.Anthropic()

SPEC = ("Write a TypeScript function refundAmount(order, items) for the shop: refund the listed items, "
        "never more than was paid, and keep amounts in integer cents.")


def text_of(response) -> str:
    return "".join(b.text for b in response.content if b.type == "text")


def generate(spec: str) -> str:
    response = client.messages.create(model="claude-sonnet-5-5", max_tokens=4000,
                                      messages=[{"role": "user", "content": spec}])
    return text_of(response)


def independent_review(spec: str, code: str) -> str:
    # A fresh conversation: the reviewer gets the requirement and the code, not the generator's
    # messages or reasoning, so it has no prior decisions to defend.
    response = client.messages.create(
        model="claude-opus-5-5", max_tokens=4000,
        system=("You review code written by someone else against its specification. "
                "List every way it can violate the spec, with the input that triggers it."),
        messages=[{"role": "user", "content": f"<spec>{spec}</spec>\n<code>{code}</code>"}],
    )
    return text_of(response)


if __name__ == "__main__":
    code = generate(SPEC)
    print(independent_review(SPEC, code))
  • Fresh conversation: the review request contains the specification and the code, and nothing from the generation turn. The reviewer has no prior decisions to defend, so "what if the same item is listed twice?" is a new question to it.
  • A reviewer's framing: its system prompt casts the code as someone else's and asks for violations with the inputs that trigger them, which makes findings testable.
  • A different model is optional: the example uses a stronger model to review, but the key property is the independent context, not the model.

In agent systems the same effect comes from a reviewer subagent: subagents start without the parent's history (task 1.2), so delegating review to one is an independent instance by construction. Claude's prompting guide makes a related point about chains: run draft, review and refine as separate calls, so each step can be logged and evaluated on its own.

Multi-pass review

Task 4.6Local passes per file, then integration passes across files.

One pass over a large multi-file change spreads attention thinly and can produce contradictory findings: the same pattern called fine in one file and a bug in another, because each judgement was made with a different slice of the change in view. The multi-pass design (built out in task 1.6) gives each file a focused pass for local issues, then runs a separate integration pass that sees all the per-file results and the diff together, and looks only at cross-file data flow: a caller and callee that disagree on units, a type changed on one side, a check moved out of one file and lost. Because the integration pass sees every local finding, it can also reconcile contradictions between them.

Verification and confidence routing

Task 4.6A pass that re-checks each finding and says how sure it is.

verify_and_route.py (Python, anthropic SDK)Optional 
"""Second pass over review findings: an independent verifier re-checks each one and reports its confidence,
and the result decides where the finding goes."""
import json
from concurrent.futures import ThreadPoolExecutor

import anthropic

client = anthropic.Anthropic()

VERIFY = ("You check one code-review finding against the code. Reply as JSON: "
          '{"verdict": "confirmed" | "rejected", "confidence": 0.0-1.0, "evidence": "file:line and why"}. '
          "Reject findings that rely on behaviour the code doesn't show.")


def verify(finding: dict, files: dict[str, str]) -> dict:
    path = finding["location"].split(":")[0]
    response = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=1000, system=VERIFY,
        messages=[{"role": "user", "content": f"<finding>{json.dumps(finding)}</finding>\n<file path=\"{path}\">{files[path]}</file>"}],
    )
    return {**finding, **json.loads("".join(b.text for b in response.content if b.type == "text"))}


def route(checked: dict) -> str:
    if checked["verdict"] == "rejected":
        return "drop"
    if checked["confidence"] >= 0.8:
        return "post"           # inline comment on the pull request
    return "triage"             # a person looks before it's posted


def review_pass(findings: list[dict], files: dict[str, str]) -> dict[str, list[dict]]:
    with ThreadPoolExecutor(max_workers=8) as pool:
        checked = list(pool.map(lambda f: verify(f, files), findings))
    routed = {"post": [], "triage": [], "drop": []}
    for c in checked:
        routed[route(c)].append(c)
    return routed
  • Each finding is re-checked independently: the verifier sees one finding and the file it's about, decides whether the code really shows the problem, and cites the evidence.
  • Confidence routes, it doesn't define scope: confirmed findings with high confidence are posted, uncertain ones go to a person for triage, rejected ones are dropped. That's different from task 4.1's warning about "only report high-confidence findings": the categories have already decided what's in scope; confidence only decides where an in-scope finding goes.
  • Calibrate the threshold: self-reported confidence is only useful if it tracks reality. Compare it with what developers did (fixed or dismissed, task 4.4) and move the threshold so "post" findings are nearly always acted on.

Anthropic's own reviewer

Task 4.6The same architecture in Claude Code's Code Review.

Claude Code's managed Code Review is built from these pieces. Several agents search the change in parallel; a verification step checks the candidate findings against the code and filters out false positives; the survivors are deduplicated and ranked by severity before being posted. A finding can carry a "Why this was flagged" section recording why it was raised and how it was verified. Multiple independent instances, a separate verification pass, and only verified findings reaching developers: the exam's architecture, in production.

Key takeaways

  • Self-review in the same session is weak: the reviewer keeps the reasoning that produced the output and tends to confirm it. More critical instructions or more thinking don't remove that context.
  • Review with an independent instance (a fresh call or a subagent) that sees only the requirement and the output.
  • For large multi-file changes, use per-file local passes plus integration passes for cross-file data flow, which avoids attention dilution and contradictory findings.
  • Add a verification pass that re-checks each finding against the code and reports confidence; route confirmed high-confidence findings to developers, uncertain ones to triage, and drop rejected ones. Calibrate the threshold against outcomes.
  • Claude Code's Code Review follows the same pattern: parallel agents, a verification step that removes false positives, then deduplication and severity ranking.
