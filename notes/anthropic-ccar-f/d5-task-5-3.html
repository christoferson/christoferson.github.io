5.3: Error Propagation Across Agents

What happens when one subagent's search fails: fixing what can be fixed where it happened, reporting the rest with enough detail for the coordinator to decide, and finishing the job with the gaps marked rather than hidden.

Overview

Task 5.3

Implement error propagation strategies across multi-agent systems.

The exam guide asks you to know four things:

  • structured error context (the failure type, the query that was tried, partial results and alternatives) lets a coordinator make sensible recovery decisions;
  • an access failure, such as a timeout that needs a retry decision, is different from a valid empty result;
  • generic statuses like "search unavailable" hide that context;
  • silently returning empty results as success and terminating the whole workflow on one failure are both anti-patterns.

In practice it asks you to return structured error context, keep access failures and empty results apart, have subagents retry transient failures themselves and pass up only what they can't fix, and annotate the final synthesis with which areas are well supported and which have gaps.

Error responses from a single MCP tool to Claude, including the isError flag and error categories, are task 2.2. This page is the layer above: subagent to coordinator to final output.

Sources: the exam guide for the error-handling principles; the Agent SDK agent-loop documentation and the Claude API error documentation for the supporting detail, checked on 19 November 2026 and paraphrased. The code is my own and was tested with anthropic 2.10.0 against mocked search backends and a mocked API.

Running example. The outdoor-gear shop's research coordinator sends subagents to look into reviews, returns, competitor pricing and stock before deciding whether to stock ultralight tents. The market-data service sometimes times out, and the shop's key for one pricing feed has expired.

Failed or found nothing

Task 5.3Access failures and valid empty results mean different things.

  • Valid empty result: the search ran and nothing matched. That's an answer: "no returns mention ultralight tents" is evidence about the product. Retrying won't change it.
  • Access failure: the search didn't run properly: a timeout, an expired key, a service outage. Nothing is known about the topic. Whether to retry, try another source or accept the gap is a decision someone has to make.

If both come back as an empty list, the coordinator can't tell "we looked and there's nothing" from "we couldn't look". The final report will then say there's no evidence about competitor pricing when in fact nobody could read the feed.

Two anti-patterns

Task 5.3Hiding the failure, or letting it stop everything.

  • Silent suppression: catching the error and returning an empty success. The workflow looks healthy, and the gap turns into a false negative in the final answer.
  • Terminating the whole workflow: one subagent's timeout aborts the run, throwing away the three topics that succeeded. One missing source rarely makes the rest worthless.
  • The milder version, a generic status: "search unavailable" admits the failure but nothing else. Was it a timeout worth retrying or a permission problem that never will be? Which query? Was anything found before it failed? The coordinator can only guess.

Recover locally, report the rest

Task 5.3A subagent fixes transient failures itself and propagates only what it can't.

subagent_errors.py (Python) 
"""A research subagent's search layer: recover from transient failures locally, report the rest with full context."""
import time


class SearchTimeout(Exception):
    pass


class SearchAccessDenied(Exception):
    pass


def search_with_recovery(search, query: str, attempts: int = 3, delay: float = 1.0, sleep=time.sleep) -> dict:
    for attempt in range(1, attempts + 1):
        try:
            hits = search(query)
            return {"status": "ok", "query": query, "hits": hits}       # [] is a valid answer: the search ran, nothing matched
        except SearchTimeout as e:                                        # transient: retry here, don't bother the coordinator
            if attempt == attempts:
                return {"status": "error", "failure_type": "timeout", "query": query, "attempts": attempt,
                        "retryable": True, "detail": str(e)}
            sleep(delay * 2 ** (attempt - 1))
        except SearchAccessDenied as e:                                   # permanent: retrying won't help
            return {"status": "error", "failure_type": "access_denied", "query": query, "attempts": attempt,
                    "retryable": False, "detail": str(e)}


def run_subagent(topic: str, queries: list[str], search, alternatives: list[str], **retry) -> dict:
    outcomes = [search_with_recovery(search, q, **retry) for q in queries]
    errors = [o for o in outcomes if o["status"] == "error"]
    report = {
        "topic": topic,
        "status": "complete" if not errors else "partial" if len(errors) < len(outcomes) else "failed",
        "findings": [h for o in outcomes if o["status"] == "ok" for h in o["hits"]],              # partial results kept
        "no_matches": [o["query"] for o in outcomes if o["status"] == "ok" and not o["hits"]],    # searched, found nothing
    }
    if errors:  # only what local recovery couldn't fix, with what was tried and where else to look
        report["errors"] = [{k: e[k] for k in ("failure_type", "query", "attempts", "retryable", "detail")} for e in errors]
        report["alternatives"] = alternatives
    return report
  • Transient failures are retried where they happen: a timeout gets up to three attempts with exponential backoff. If the second attempt works, the coordinator never hears about it and doesn't spend context on it. The Anthropic SDK does the same for the API's own transient errors: rate limits, overloads and server errors are retried twice by default.
  • Permanent failures are reported at once: an access-denied error won't fix itself, so retrying only wastes time.
  • Empty is not an error: a search that ran and matched nothing returns status: ok with no hits, and is listed under no_matches.
  • Partial results survive: a subagent with four queries where two failed returns the two that worked, with status partial.

What an error report carries

Task 5.3Enough for the coordinator to decide without guessing.

For each failure the report includes:

  • The failure type (timeout, access_denied), so the coordinator knows whether trying again could help.
  • What was attempted: the exact query and how many attempts were made. A timeout after three tries is different from one after one.
  • Whether it's retryable, and the raw detail ("403 from market-data") for logs and people.
  • Partial results collected before or alongside the failure.
  • Alternatives: other places the same information might be found, such as an archived price list.

The subagent knows these things because it was there; the coordinator only knows what it's told. This is task 5.1's point about structured outputs between agents, applied to failures.

The coordinator's decisions

Task 5.3Retry elsewhere, accept the gap, but keep going.

coordinator.py (Python, anthropic SDK) 
"""Coordinator: recover per report, never abort the run for one failure, and tell the synthesis step where the gaps are."""
import json

import anthropic

from subagent_errors import run_subagent

client = anthropic.Anthropic()


def recover(report: dict, backends: dict) -> dict:
    """Retry only the failed queries, on an alternative source the subagent suggested."""
    for alt in report.get("alternatives", []):
        if alt not in backends or report["status"] == "complete":
            continue
        failed = [e["query"] for e in report["errors"]]
        retry = run_subagent(report["topic"], failed, backends[alt], alternatives=[])
        report["findings"] += retry["findings"]
        report["no_matches"] += retry["no_matches"]
        report["errors"] = retry.get("errors", [])
        report["status"] = "complete" if not report["errors"] else "partial" if report["findings"] else "failed"
        report["recovered_via"] = alt
    return report


def coverage(report: dict) -> dict:
    if report["status"] != "complete":
        why = "; ".join(f"{e['failure_type']} on '{e['query']}'" for e in report["errors"])
        return {"topic": report["topic"], "coverage": "gap" if not report["findings"] else "partial", "reason": why}
    if not report["findings"]:
        return {"topic": report["topic"], "coverage": "no_evidence", "reason": "searched; nothing matched"}
    return {"topic": report["topic"], "coverage": "well_supported" if len(report["findings"]) >= 2 else "thin"}


def synthesize(question: str, reports: list[dict], backends: dict) -> str:
    reports = [recover(r, backends) for r in reports]
    table = [coverage(r) for r in reports]
    prompt = (f"<coverage>\n{json.dumps(table, indent=1)}\n</coverage>\n"
              f"<reports>\n{json.dumps(reports, indent=1)}\n</reports>\n"
              f"<question>{question}</question>\n"
              "Answer the question. Label each section with its coverage. For 'gap' topics say the source was "
              "unavailable, not that the evidence is absent; for 'no_evidence' say the search found nothing.")
    response = client.messages.create(model="claude-opus-5-5", max_tokens=3000,
                                      messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in response.content if b.type == "text")
  • Recovery per report: recover retries only the failed queries, on an alternative source the subagent suggested. Complete reports pass through untouched.
  • No abort: however many reports failed, the run continues to synthesis with what it has.
  • Escalation is still an option. If the missing topic is critical (the decision can't be made without pricing), the coordinator can stop and ask a person. That's a deliberate choice made with full information, not a crash.

Coverage in the synthesis

Task 5.3Saying which conclusions rest on solid ground and which have holes.

coverage gives each topic one of four labels, and the synthesis prompt asks Claude to carry the labels into its answer:

  • well_supported: complete, with several findings.
  • thin: complete but with little evidence; here, pricing recovered from the archive with a single finding.
  • no_evidence: searched successfully and nothing matched.
  • partial or gap: a source was unavailable, with the reason. The prompt tells Claude to say the source was unavailable, not that the evidence is absent.

The reader of the final report can then weigh the conclusion. "Reviews strongly favour lighter tents; we couldn't get current competitor prices" supports a different decision from a report that silently leaves pricing out. Attributing each claim to its source is task 5.6.

Agent SDK result types

Task 5.3How an SDK run reports the way it ended.

With the Agent SDK, every run ends with a ResultMessage whose subtype says how it ended:

  • success;
  • error_max_turns or error_max_budget_usd, when a limit was hit;
  • error_during_execution, for example after a cancelled request;
  • error_max_structured_output_retries, when no valid structured output was produced.

Only success carries the result text, so check the subtype first. Every subtype still carries the cost, turn count and session ID, so a run that hit its turn limit can be resumed with a higher one.

A single-shot query() raises an exception after yielding an error result; catch it if the caller should carry on. The budget cap covers subagents as well, and once it's reached, spawning another subagent fails.

Inside the loop, a tool call that's denied comes back to Claude as a rejection message in the tool result, and Claude typically tries another approach or reports that it couldn't continue. That's the same principle as the rest of this page: the failure is visible and described, so the agent can adapt.

Key takeaways

  • Keep access failures (timeouts, denied access) apart from valid empty results (searched, nothing matched); conflating them turns outages into false "no evidence" conclusions.
  • Both silent suppression and aborting the whole workflow on one failure are anti-patterns; a generic "unavailable" status hides what the coordinator needs.
  • Subagents retry transient failures locally with backoff, report permanent ones at once, and propagate only what they couldn't fix.
  • Error reports carry the failure type, the query attempted, attempts made, retryability, partial results and alternative sources.
  • The coordinator recovers per report and continues. The synthesis labels each topic's coverage (well supported, thin, no evidence, partial or gap) so readers can see where the holes are.
