Overview

Task 3.3

Apply path-specific rules for conditional convention loading.

The exam guide asks you to know .claude/rules/ files with paths frontmatter holding glob patterns, that such rules load only when Claude works with matching files (which saves context), and why a glob rule beats a subdirectory CLAUDE.md when the files it's about are spread across the codebase. The rules folder itself and the other CLAUDE.md locations are in task 3.1.

Sources: the Claude Code documentation (memory, features overview, large codebases, skills, hooks) and the changelog, checked on 8 November 2026 against Claude Code 2.1.303, paraphrased.

Running example. The shop's repository has API code in src/api/, a tests/ folder, and also test files next to the code they test (cart.test.ts beside cart.ts). The team wants API rules only when Claude touches API code, and test rules for every test file.

Scoping a rule

Task 3.3The paths frontmatter field.

A rule is a Markdown file in .claude/rules/. Add YAML frontmatter with a paths field, and the rule loads only for files matching one of its patterns. The value can be a YAML list (as here) or a comma-separated string.

.claude/rules/api.md (Markdown) 
---
paths:
  - "src/api/**/*.ts"
---
# API rules
- Validate every request body with zod.
- Return errors as { code, message }.
- Never log card numbers or tokens.
- Prices are integer cents, not floats.
.claude/rules/tests.md (Markdown) 
---
paths:
  - "tests/**"
  - "**/*.test.{ts,tsx}"
---
# Test rules
- Use Vitest; no real network calls.
- Build carts with makeCart() fixtures.
- One behaviour per test, clear names.
- Run: pnpm vitest run <file>

The first pattern covers the tests/ folder; the second catches test files sitting next to their code anywhere in the repository, which no single folder's CLAUDE.md could cover.

.claude/rules/style.md (no frontmatter) 
# Code style
- TypeScript strict mode, no any.
- Named exports only.
- Use pnpm, not npm or yarn.

A rule with no paths loads at launch in every session, with the same priority as .claude/CLAUDE.md. Rules in ~/.claude/rules/ apply to all your projects and load before project rules; neither overrides the other.

Glob patterns

Task 3.3What each kind of pattern matches.

Patterns are relative to the project root: the folder that contains .claude, not the rules subfolder the file sits in. (For user-level rules, they're relative to the session's working folder.)

PatternMatches
**/*.tsEvery .ts file at any depth
src/**/*Everything under src/
*.mdMarkdown files at any depth (a pattern with no slash isn't limited to the top level)
/*.mdMarkdown files directly in the project root only
src/components/*.tsxOnly files directly in that folder, not its subfolders
src/**/*.{ts,tsx}Brace expansion: .ts and .tsx under src/

When a rule loads

Task 3.3The trigger, and what happens afterwards.

  • A path-scoped rule loads when Claude reads, writes or edits a matching file with its Read, Write or Edit tools, or views one with a single-file Bash command such as cat.
  • Until then it costs no context at all. Once loaded, it stays in the conversation.
  • After /compact, path rules are dropped and come back only when a matching file is touched again. (The project-root CLAUDE.md, by contrast, is re-read after compaction.)
  • Everything is added together: rules and CLAUDE.md files never override one another, and when they conflict Claude may follow either.

"Only when editing" is out of date. The exam guide says path rules load when Claude edits matching files. Reading a matching file is enough, and that's how it has worked from the start; Write and Edit were added as triggers in 2.1.288 (October 2026), and single-file Bash reads in 2.1.293. The YAML list form the guide uses (paths: ["terraform/**/*"]) has been accepted since 2.1.84; before that, only a comma-separated string worked.

Rules, directory files or skills

Task 3.3Picking the right place for conditional guidance.

OptionLoadsBest for
Path-scoped ruleWhen a file matching its globs is read or changedConventions for file types spread across the repository (all test files, all migrations); keeping every convention in one central place
Subdirectory CLAUDE.mdWhen Claude works on a file in that folderOne folder's conventions, kept by the people who own that folder
Unscoped rule or project CLAUDE.mdEvery session, at launchWhat nearly every task needs
SkillIts description always; its body when invoked or judged relevantProcedures and reference material for particular tasks (task 3.2)

The exam's key distinction. A subdirectory CLAUDE.md is tied to one folder. If test files live in many folders, you'd need a copy in each; one rule with **/*.test.tsx covers them all. Skills can now take a paths field too, but that only decides when Claude may load the skill automatically; a matching rule's text is always added without Claude choosing it.

Traps

Task 3.3Mistakes that make a rule load always, never or at the wrong time.

MistakeWhat happens
Using another field name, such as globs: or description:paths is the only field read; others are silently ignored, so the rule loads every session
Invalid YAML in the frontmatterThe frontmatter is ignored and the rule becomes always-on; only claude --debug shows the error
Patterns written relative to the rules folderThey match nothing: patterns start from the project root
Expecting a rule to survive /compactIt's gone until a matching file is touched again
Path rules symlinked from outside the projectNeed a one-time approval, and even then only rules without paths load from that location
Writing a must-never rule as a path ruleIt's guidance, not enforcement: use permissions or hooks

To see what loaded and why, check /context all or a Loaded line in the terminal; the InstructionsLoaded hook reports the reason, including path_glob_match for path rules.

Key takeaways

  • A .claude/rules/*.md file with paths: frontmatter (a YAML list or comma string of globs) loads only when Claude reads, writes or edits a matching file.
  • No paths means always loaded, like .claude/CLAUDE.md. paths is the only field read; broken YAML makes the rule always-on.
  • Globs start from the project root. ** means any depth, {ts,tsx} expands, a leading / anchors to the root.
  • Path rules save context until needed, then stay; they're dropped by /compact until the next match. Nothing overrides anything.
  • Glob rules suit conventions for files spread across the repository (**/*.test.tsx); a subdirectory CLAUDE.md suits one folder owned by one team; skills suit occasional procedures.
  • The guide says "when editing"; reading is enough. Hard requirements still belong in permissions or hooks.
