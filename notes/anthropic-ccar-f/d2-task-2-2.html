2.2: Structured Error Responses

When a tool fails, the agent can only recover sensibly if the failure says what kind it was, whether trying again could help, and what to do next. This page covers how MCP reports tool errors and how to design error payloads an agent can act on.

Overview

Task 2.2

Implement structured error responses for MCP tools.

The exam guide asks you to know MCP's isError flag; the four kinds of failure (transient, validation, business-rule and permission); why a generic error stops the agent choosing the right recovery; and the difference between errors worth retrying and errors that aren't. In practice: return an error category, a retryable flag and a readable description; mark policy violations as not retryable and explain them in customer-friendly words; let subagents fix transient failures locally; and keep access failures distinct from valid empty results.

Sources: the MCP specification (revision 2026-07-28), the MCP Python SDK, the Claude API tool-use documentation and Anthropic's "Writing effective tools for agents" (September 2025), checked on 8 November 2026; Anthropic's pages are paraphrased. The server code below was run with the MCP Python SDK 2.3.0 through an in-memory client.

Running example. The shop's support agent can refund orders through an MCP tool, process_refund. Refunds over US$500 need a manager, and the payments API sometimes times out.

Two kinds of MCP error

Task 2.2Protocol errors versus tool execution errors.

KindUsed forShape
Protocol errorProblems with the request itself: an unknown tool, a malformed request, a server faultA JSON-RPC error, for example code -32602
Tool execution errorThe tool ran and failed: an API failure, invalid input values, a business ruleA normal result with isError: true and the details in content

The spec says clients should pass tool execution errors to the model so it can correct itself, while protocol errors may never reach the model at all. So failures the agent could recover from belong in the result, with isError: true. Since the 2025-11-25 revision, the spec says explicitly that input validation errors are execution errors, for this reason.

The category fields are yours, not MCP's. MCP gives you only the isError boolean and free-form content. Fields such as errorCategory and isRetryable are a convention you define (the exam guide uses those names, spelled a few different ways). Pick one shape and use it in every tool.

Why "Operation failed" fails

Task 2.2What a generic error costs the agent.

Given only "Operation failed", the agent has to guess. It may retry something that can never succeed (a refund over the limit), wasting calls and annoying the customer, or give up on something that would have worked a few seconds later (a timeout). The Claude API docs ask for instructive errors that say what went wrong and what to try next, and Anthropic's tool-writing guide says error responses should give specific, actionable fixes, not opaque codes or tracebacks.

An MCP tool with structured errors

Task 2.2One error shape for every failure, with a next step.

refund_server.py (Python, MCP server) 
import json
from mcp.server.mcpserver import (
    MCPServer)
from mcp.types import (
    CallToolResult, TextContent)

mcp = MCPServer("shop-support")
LIMIT = 500  # refund cap in USD


def fail(category, retryable, msg,
         **extra):
    # One error shape for every tool
    body = {"errorCategory": category,
            "isRetryable": retryable,
            "message": msg, **extra}
    return CallToolResult(
        content=[TextContent(
            type="text",
            text=json.dumps(body))],
        structured_content=body,
        is_error=True)


def charge_back(order_id, amount):
    # Stand-in for the payments API
    if order_id == "ORD-SLOW":
        raise TimeoutError
    return "RF-" + order_id[4:]


@mcp.tool()
def process_refund(order_id: str,
                   amount: float):
    """Refund part or all of an order."""
    if amount <= 0:
        return fail(
            "validation", False,
            "amount must be above 0")
    if amount > LIMIT:
        return fail(
            "business", False,
            f"Refunds over ${LIMIT} need "
            "a manager. Offer a handoff.",
            limit=LIMIT)
    try:
        ref = charge_back(
            order_id, amount)
    except TimeoutError:
        return fail(
            "transient", True,
            "Payments API timed out. "
            "Retry in 5 seconds.",
            retryAfterSeconds=5)
    return {"status": "refunded",
            "refundId": ref,
            "amount": amount}

Each failure returns isError: true with the same body: the category, whether a retry could help, a message that says what to do next (safe to show a customer), and extra details such as the limit or how long to wait. The body goes in the text content, which is what the model reads, and in structuredContent for programs.

FastMCP is now MCPServer. Version 2.0 of the MCP Python SDK (July 2026) renamed FastMCP to MCPServer (from mcp.server.mcpserver import MCPServer); the old import fails. It also changed error handling: a plain exception raised in a tool now reaches the model only as "Error executing tool name", with the details hidden (version 1 passed the exception text through). Raise ToolError("...") for a message the model should see, or return a CallToolResult with is_error=True as above. Raising MCPError now produces a protocol error, which most clients don't show the model.

What Claude receives

Task 2.2From MCP result to Claude tool result.

MCP result for a refund over the limit (JSON) 
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "content": [{
      "type": "text",
      "text": "{\"errorCategory\": ..."
    }],
    "structuredContent": {
      "errorCategory": "business",
      "isRetryable": false,
      "message": "Refunds over ...",
      "limit": 500
    },
    "isError": true
  }
}

The application or host running the agent loop turns this into a Claude API tool_result with is_error: true (task 1.1). Note the spelling: MCP uses camelCase isError, the Claude API uses snake_case is_error. Claude then works the error into its next step. For a missing or invalid parameter, the docs say Claude typically retries two or three times with corrections before apologizing; strict: true on the tool definition prevents invalid calls in the first place.

Keep the useful part in the text. A Claude API tool_result carries text, images and documents, not MCP's structuredContent. Hosts differ in what they forward, so make sure the category and the next step are in the text block.

Empty results and recovery

Task 2.2Telling "nothing found" from "couldn't look", and where to recover.

SituationReturnIf you get it wrong
The search worked and found nothingSuccess with an explicit empty result, such as {"orders": [], "count": 0}Reported as an error, the agent retries pointlessly
The search couldn't run (timeout, no access)isError: true with the categoryReported as empty, the agent tells the customer they have no orders

In a multi-agent system, a subagent should retry transient failures itself and pass up only what it can't resolve, together with the failure type, what it tried and any partial results, so the coordinator can decide what to do. Both silently swallowing an error and aborting the whole workflow over one failure are mistakes. Error propagation across agents is covered in depth in task 5.3.

Key takeaways

  • MCP protocol errors (JSON-RPC error) are for bad requests; tool failures go in the result with isError: true so the model can see and react to them. Input validation errors are execution errors.
  • Give every failure a category, a retryable flag and a message with the next step. These fields are your convention; MCP only has isError.
  • Transient: retry with a delay. Validation: fix the input. Business rule: don't retry; explain and offer a handoff. Permission: don't retry; escalate.
  • "Nothing found" is a success with an empty result; "couldn't look" is an error. Never confuse the two.
  • MCP isError becomes the Claude API's is_error; keep the important details in the text content.
  • MCP Python SDK 2.x: FastMCP is now MCPServer; plain exceptions are masked, so use ToolError or return an is_error result.
