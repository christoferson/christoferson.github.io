5.2: Understand security operations

The daily work of a security team: collecting and protecting logs, watching them for trouble, deciding which alerts matter, and using knowledge of attackers, threat intelligence and frameworks such as MITRE ATT&CK to tell a routine blocked attempt from a real intrusion.

Overview

Objective 5.2

Understand security operations. Sub-topics: logging and monitoring security events, security event triage (incident use cases, prioritization, correlation), threat actors, cyber threat intelligence and threat frameworks.

Preventive controls fail sometimes, so organizations also need to detect: notice that something is wrong, quickly enough to act. This is the work of security operations, often in a security operations center (SOC), and it is where many entry-level security jobs are. What happens once an incident is declared, the incident response plan, is objective 5.3.

The official exam outline is on isc2.org.

Running example. The mid-sized retailer: 800 staff, 60 US stores, an online shop with European customers, card payments, a cloud loyalty database and new AI tools. It has a three-person security team and a managed SOC provider that monitors its logs around the clock.

Events, alerts and incidents

Objective 5.2Using the right word for each stage, from an ordinary event to a declared incident, and knowing what false positives and negatives are.

NIST's incident response guide (SP 800-61 Rev. 3, 2025) builds the vocabulary in steps:

  • An event is "any observable occurrence that involves computing assets", such as a login, a software update or a web request. Most events are harmless.
  • An adverse event has "a negative consequence regardless of cause": a failed backup, a power cut or an attack. NIST notes that "additional analysis is often needed" to tell whether it is an incident.
  • An indicator of compromise (IoC) is a technical artifact or observable suggesting "that an attack is imminent or is currently underway ... or that a compromise may have already occurred", such as a known-bad IP address or file hash.
  • An incident, in the US federal definition NIST uses, is "an occurrence that actually or imminently jeopardizes, without lawful authority, the integrity, confidentiality, or availability of information or an information system; or constitutes a violation or imminent threat of violation of law, security policies, security procedures, or acceptable use policies."

An alert is a tool's notification that something may need attention. Detection tools make two kinds of mistake: a false positive is "an instance in which a security tool incorrectly classifies benign content as malicious", and a false negative is when a tool "intended to detect a particular threat fails to do so". Too many false positives waste analysts' time; false negatives let attacks through. Tuning trades one against the other.

Not every event is an incident, and the vocabulary changed. NIST CSF 2.0 makes declaring an incident a deliberate step: "Incidents are declared when adverse events meet the defined incident criteria" (DE.AE-08). The older term precursor (a sign an incident may happen in future) came from the 2012 Rev. 2 of SP 800-61, which was withdrawn in April 2025; Rev. 3 talks about adverse events and indicators of compromise instead.

Logging

Objective 5.2Deciding what to log, what each record must contain, and how to keep logs accurate, protected and available for long enough.

A log is "a record of the events occurring within an organization's systems and networks" (NIST SP 800-92). NIST's draft update of that guide stresses that "all logging is done for a purpose and not just for the sake of collecting log data." The SP 800-53 audit controls set out the essentials:

  • What to log (AU-2): event types "adequate to support after-the-fact investigations of incidents", such as logins, privilege changes, configuration changes, access to sensitive data and security tool detections.
  • What each record contains (AU-3): what type of event occurred, when, where, the source, the outcome, and the identity of any user or system involved.
  • Accurate time (AU-8 and SC-45): timestamps in UTC or with a known offset, and clocks synchronized to an authoritative time source, otherwise events from different systems cannot be lined up.
  • Protection (AU-9): "protect audit information and audit logging tools from unauthorized access, modification, and deletion", ideally by sending logs to a separate system that administrators of the source system cannot change.
  • Retention (AU-11): long enough for investigations and regulations.

CISA's Performance Goals 2.0 (goal 3.Q) ask for logs to be "stored in a central system, such as a security information and event management tool", accessible only to authorized users, and for teams to be notified "when a critical log function is disabled": attackers often turn logging off first. For US federal agencies, OMB memo M-26-14 (May 2026) replaced the 2021 logging memo with a "risk-based, prioritized logging approach": logs must stay "actively searchable for a minimum of 6 months" and "retrievable for a year", with accurate synchronized timestamps. Joint guidance from Australia's ACSC, CISA, the FBI, NSA and partners, "Best Practices for Event Logging and Threat Detection" (August 2024), sets a baseline for organizations of any size.

The retailer sends logs from its identity provider, firewalls, store tills, endpoint protection, cloud accounts and the online shop to one central platform, keeps them searchable for a year, and has an alert if any source goes silent for more than an hour.

Monitoring and the SOC

Objective 5.2Knowing the main monitoring tools, what each does, and how they are tuned so analysts see the alerts that matter.

Logs only help if someone, or something, reads them. NIST defines continuous monitoring as "maintaining ongoing awareness to support organizational risk decisions." The main tools:

  • SIEM (security information and event management): "a program that provides centralized logging capabilities for a variety of log types" (NIST SP 800-92), with search, correlation ("finding relationships between two or more log entries"), dashboards and alerts.
  • SOAR (security orchestration, automation and response): runs playbooks that carry out routine steps automatically, such as enriching an alert with threat intelligence, opening a ticket, or isolating a laptop.
  • EDR (endpoint detection and response): agents on laptops and servers that record activity, detect malicious behaviour and can contain a device.
  • IDS/IPS and network monitoring (objective 4.1), and UEBA (user and entity behaviour analytics), which learns normal behaviour and flags deviations.

Australia's ACSC and CISA published "Guidance for SIEM and SOAR Implementation" in May 2025, with separate parts for executives, practitioners and the priority logs to collect. NIST SP 800-61 Rev. 3 asks organizations to "tune the continuous monitoring technologies to reduce false positives and false negatives to acceptable levels", and lists what to watch: authentication attempts "to identify attacks against credentials", endpoints for malware and missing patches, and email, web and file sharing for phishing, data leaks and exfiltration.

A use case turns one of those concerns into a detection rule. A simplified correlation rule for password spraying against the retailer's staff accounts:

Correlation rule (generic pseudo-code) 
rule "Password spray then success"
  when  count(event=login_failed,
              distinct user) >= 20
        from same source_ip within 10m
  and   event=login_success
        from same source_ip within 30m
  then  alert severity=high
        enrich source_ip with threat_intel
        open ticket queue=SOC-tier1
# many accounts tried, then one works:
# likely a guessed password

Triage

Objective 5.2Sorting alerts by validating, enriching, correlating and prioritizing them, and knowing when to escalate.

Triage decides which alerts need human attention first. NIST SP 800-61 Rev. 3 states the problem plainly: the volume of possible adverse events "is generally quite high, so organizations should rely on technical solutions that filter large event datasets down to a subset that is suitable for human viewing and analysis." The steps, mapped to CSF 2.0:

  1. ValidateIs it real? "Incident reports are triaged and validated" (RS.MA-02); rule out known false positives.
  2. EnrichAdd context: "cyber threat intelligence and other contextual information are integrated into the analysis" (DE.AE-07), such as asset owner and criticality, user role and IP reputation.
  3. Correlate"Information is correlated from multiple sources" (DE.AE-03): the failed logins, the VPN connection and the EDR alert may be one attack.
  4. Scope and prioritizeEstimate "impact and scope" (DE.AE-04); "incidents are categorized and prioritized" (RS.MA-03).
  5. Declare and escalateDeclare an incident when the criteria are met (DE.AE-08) and escalate (more resources) or elevate (higher management) as needed (RS.MA-04).

NIST says "incidents should not be handled on a first-come, first-served basis". Priority depends on "asset criticality, functional impact of the incident, data impact of the incident, stage of observed activity, threat actor characterization, and recoverability." CISA's National Cyber Incident Scoring System uses six levels from Baseline (white or blue) through Low (green), Medium (yellow), High (orange) and Severe (red) to Emergency (black); CISA has said an updated methodology is coming.

The CC outline frames the key judgment as telling "a routine automated block" from "a high-priority event requiring human intervention". Two alerts from the same morning at the retailer:

Triage notes, Tuesday 09:00-09:30
Alert 1
Firewall blocked a scan of the online shop from an IP on a public blocklist
Assessment 1
Reconnaissance, blocked, no follow-up activity: routine; close with note
Alert 2
EDR: the finance manager's laptop ran an encoded PowerShell command, then connected to a new domain
Assessment 2
Execution and command-and-control on a high-value user, domain registered two days ago: high priority; isolate the laptop, escalate to incident handler

Threat actors

Objective 5.2Recognizing the main types of threat actor, what drives each, and how capable and persistent they tend to be.

A threat actor is "an individual or a group posing a threat" (NIST SP 800-150). NIST's risk assessment guide (SP 800-30) groups threat sources into four kinds: adversarial (people and groups acting deliberately), accidental (mistakes by users and administrators), structural (equipment and software failures) and environmental (natural disasters and infrastructure outages). Adversaries are assessed on their capability, intent and targeting. The Canadian Centre for Cyber Security summarizes the common types and their usual motivations:

  • Nation-states: "often geopolitically motivated" (espionage, pre-positioning for disruption) and frequently the most sophisticated.
  • Cybercriminals: "often financially motivated", from ransomware gangs to fraudsters. Many ransomware groups rent their tools to affiliates (ransomware as a service).
  • Hacktivists: "often ideologically motivated", usually less sophisticated: defacements, data leaks, denial of service.
  • Terrorist groups: motivated by ideological violence, generally with limited cyber capability.
  • Thrill-seekers: motivated by satisfaction or reputation, low skill.
  • Insiders: "often motivated by discontent", dangerous because they already have access. CISA also counts unintentional insiders, through negligence or accident, and collusive and third-party insiders.

An advanced persistent threat (APT) is "an adversary that possesses sophisticated levels of expertise and significant resources" and "pursues its objectives repeatedly over an extended period of time; adapts to defenders' efforts" (NIST SP 800-39). Most APTs are state-sponsored.

The US intelligence community's 2026 Annual Threat Assessment names China as "the most active and persistent cyber threat" to US government, private-sector and critical infrastructure networks, says China and Russia are continuing "pre-positioning efforts", describes North Korea's use of "IT workers with falsified credentials" and crypto theft of "at least $1 billion each year", and warns that "ransomware groups are shifting to faster, high-volume attacks." CISA advisories describe specific groups: Volt Typhoon pre-positioning in critical infrastructure while "living off the land" with built-in tools (2024), and Salt Typhoon targeting telecom backbone routers through known, unpatched vulnerabilities (2025).

Cyber threat intelligence

Objective 5.2Telling threat information from threat intelligence, knowing the kinds of intelligence, and how it is shared safely.

NIST SP 800-150 distinguishes raw threat information, "any information related to a threat that might help an organization protect itself", from threat intelligence: "threat information that has been aggregated, transformed, analyzed, interpreted, or enriched to provide the necessary context for decision-making processes." It lists five kinds of threat information:

  • Indicators: IP addresses, domains, URLs, file hashes, email subjects.
  • TTPs (tactics, techniques and procedures), which "describe the behavior of an actor".
  • Security alerts: advisories and bulletins about vulnerabilities and exploits.
  • Threat intelligence reports describing actors, their methods and targets.
  • Tool configurations: detection signatures, firewall rules and other settings that put the intelligence to use.

Intelligence is often described at three levels: strategic (trends and risks for leaders), operational (campaigns and actors, for security managers) and tactical (indicators and TTPs, for analysts and tools). Indicators are easy for attackers to change; behaviours (TTPs) are much harder, which is why detection increasingly targets behaviour.

Sharing

NIST's aim for sharing is that "one organization's detection" becomes "another's prevention." Organizations share through sector groups such as Information Sharing and Analysis Centers (ISACs) and through CISA's free Automated Indicator Sharing service. Machine-readable formats make this practical: STIX is "a language and serialization format used to exchange cyber threat intelligence", and TAXII is the protocol for exchanging it, both version 2.1. The Traffic Light Protocol (TLP 2.0, FIRST, 2022) labels how far shared information may go:

  • TLP:RED: "for the eyes and ears of individual recipients only, no further disclosure."
  • TLP:AMBER: within the recipient's organization and its clients, on a need-to-know basis; TLP:AMBER+STRICT: the organization only.
  • TLP:GREEN: within the recipient's community.
  • TLP:CLEAR: "no limit on disclosure" (it replaced TLP:WHITE).

The retailer belongs to its sector's ISAC; indicators from ISAC alerts flow into the SIEM automatically, and the security team reads the TLP label before forwarding anything to the managed SOC provider.

Threat frameworks

Objective 5.2Using MITRE ATT&CK, the Cyber Kill Chain and related models to describe attacks, spot gaps in detection and judge how far an intrusion has gone.

MITRE ATT&CK is a public knowledge base of adversary behaviour observed in real attacks, with matrices for Enterprise, Mobile and industrial control systems. CISA's mapping guide explains its levels: tactics are the "why" (the attacker's goal at that step), techniques the "how", sub-techniques a more specific how, and procedures a particular group's actual use of a technique. The Enterprise matrix has 15 tactics:

  1. ReconnaissanceGathering information to plan the attack.
  2. Resource DevelopmentAcquiring infrastructure, accounts and tools.
  3. Initial AccessGetting in, for example by phishing.
  4. ExecutionRunning malicious code.
  5. PersistenceKeeping access across restarts and password changes.
  6. Privilege EscalationGaining higher permissions.
  7. StealthAvoiding detection.
  8. Defense ImpairmentDisabling or weakening security tools.
  9. Credential AccessStealing passwords and tokens.
  10. DiscoveryLearning about the environment.
  11. Lateral MovementMoving to other systems.
  12. CollectionGathering the data of interest.
  13. Command and ControlCommunicating with compromised systems.
  14. ExfiltrationStealing the data.
  15. ImpactDisrupting, destroying or encrypting, as ransomware does.

"14 tactics" is out of date. In April 2026 (version 19) MITRE split the old Defense Evasion tactic into Stealth and Defense Impairment, so most older material, including CISA's mapping guide, still lists 14. In triage, the tactic tells you how far an attacker has got: a blocked Reconnaissance or Initial Access attempt is usually routine; Credential Access, Lateral Movement or Exfiltration inside the network needs urgent attention.

Other frameworks:

  • Cyber Kill Chain (Lockheed Martin, 2011): seven phases, reconnaissance, weaponization, delivery, exploitation, installation, command and control, and actions on objectives. Its key idea is that breaking any one link stops the attack.
  • Diamond Model: analyses each intrusion by four linked features: adversary, capability, infrastructure and victim.
  • MITRE D3FEND: the defensive counterpart, a catalogue of countermeasures (model, harden, detect, isolate, deceive, evict, restore) mapped to ATT&CK techniques.
  • MITRE ATLAS: an ATT&CK-style matrix for attacks on AI systems, including prompt injection, model theft and attacks through AI agents' tools.

CISA's Known Exploited Vulnerabilities catalog complements these for prioritizing: a vulnerability on the list is being exploited in real attacks, so an alert involving it ranks higher.

AI in security operations

Objective 5.2Understanding how AI helps analysts cope with alert volume, and how attackers are using AI against defenders.

The CC outline notes that SIEM tools use AI to correlate data and reduce alert fatigue: analysts who see too many low-value alerts start missing important ones. NIST's draft Cyber AI Profile (IR 8596, December 2025) says AI "can support cybersecurity teams by sifting through the significant volume of alerts, distinguishing actual threats from noise, distinguishing the most serious threats", and points to anomaly detection and behaviour analytics to reduce false positives and false negatives. The federal logging memo M-26-14 expects the most mature agencies to tune detections "using advanced techniques such as machine learning or artificial intelligence." AI suggestions still need human review: an AI summary can be wrong, and attackers can try to manipulate the data it reads.

Attackers use AI too. CISA's 2026 patching directive warns that attackers' "use of AI may further narrow the time defenders have to react." MITRE added ATT&CK techniques for querying public AI services and for prompt injection in 2026. AI providers have published reports on misuse: Google's threat intelligence group described malware that queries a large language model during live operations (November 2025), and Anthropic reported disrupting a campaign it attributed to a Chinese state-sponsored group in which AI performed most of the intrusion work (November 2025).

The retailer's SOC provider uses AI to summarize related alerts into one case with a suggested priority and next steps; an analyst confirms the priority before any containment action, and the summaries are checked against the raw logs.

Further reading

  • NIST SP 800-61 Rev. 3, Incident Response Recommendations and Considerations for Cybersecurity Risk Management (NIST, April 2025): detection, analysis, triage and prioritization mapped to CSF 2.0.
  • Best Practices for Event Logging and Threat Detection (Australia's ACSC, CISA and partners, August 2024).
  • NIST SP 800-150, Guide to Cyber Threat Information Sharing (NIST, 2016): threat information, intelligence and sharing.
  • ATT&CK v19 release notes (MITRE, April 2026): the split of Defense Evasion into Stealth and Defense Impairment.

Key takeaways

  • Event (any observable occurrence) → adverse event (negative consequence) → incident (jeopardizes CIA or violates policy), declared against criteria. IoCs suggest compromise. False positives waste time; false negatives miss attacks.
  • Logging: log events needed for investigations; each record has what, when, where, source, outcome and identity; synchronize clocks; protect logs on a separate system; retain them (federal: 6 months searchable, 1 year retrievable); alert if logging stops.
  • Tools: SIEM (central logging, correlation, alerts), SOAR (automated playbooks), EDR (endpoints), IDS/IPS, UEBA. Tune to keep false positives and negatives acceptable.
  • Triage: validate, enrich with CTI and context, correlate, scope and prioritize (not first come, first served), declare and escalate or elevate. Tell routine automated blocks from events needing human action.
  • Threat actors: nation-states (geopolitics), cybercriminals (money), hacktivists (ideology), terrorists, thrill-seekers, insiders (discontent, negligence, accident). APTs are skilled, well-resourced and persistent. Threat sources: adversarial, accidental, structural, environmental.
  • CTI: intelligence is information analysed for decisions. Types: indicators, TTPs, alerts, reports, tool configurations; levels strategic, operational, tactical. Share via ISACs and AIS, in STIX/TAXII, labeled with TLP (RED, AMBER, AMBER+STRICT, GREEN, CLEAR).
  • Frameworks: MITRE ATT&CK (15 Enterprise tactics since 2026; tactics = why, techniques = how, procedures = specific use), Cyber Kill Chain (7 phases), Diamond Model (adversary, capability, infrastructure, victim), D3FEND (defenses), ATLAS (AI attacks).
  • AI helps sort alerts and reduce noise but needs human review; attackers use AI to move faster.
