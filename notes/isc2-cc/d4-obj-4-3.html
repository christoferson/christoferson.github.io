4.3: Understand cloud security

What makes a service "cloud", the service and deployment models, and the question behind most cloud breaches: which security tasks belong to the provider and which stay with the customer, including when the service is an AI model.

Overview

Objective 4.3

Understand cloud security. Sub-topics: characteristics (broad network access, rapid elasticity, measured service, on-demand self-service, resource pooling), service models, deployment models, and the shared security model (roles and responsibilities).

Most organizations now run much of their IT on someone else's infrastructure. The network concepts from objectives 4.1 and 4.2 still apply, but who carries them out changes. This objective covers the standard vocabulary for cloud services and, most importantly, how security duties are divided between provider and customer.

The official exam outline is on isc2.org.

Running example. The mid-sized retailer: 800 staff, 60 US stores, an online shop with European customers, card payments, a cloud loyalty database and new AI tools. Email and office apps are a SaaS suite; the online shop runs on a cloud platform; the loyalty database runs on virtual servers in a public cloud; the customer chatbot uses a hosted AI model.

What cloud computing is

Objective 4.3Knowing the standard definition of cloud computing and the parties involved in a cloud service.

The definition used across the industry comes from NIST SP 800-145 (2011), still current:

NIST definition. "Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (e.g., networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction. This cloud model is composed of five essential characteristics, three service models, and four deployment models."

Remember the numbers: 5, 3, 4. NIST's reference architecture (SP 500-292) adds five roles in a cloud service:

  • Cloud consumer: the organization using the service (the retailer).
  • Cloud provider: the party "responsible for making a service available".
  • Cloud auditor: an independent assessor of the service's operations, performance and security.
  • Cloud broker: an intermediary that "manages the use, performance and delivery of cloud services, and negotiates relationships" between providers and consumers.
  • Cloud carrier: provides "connectivity and transport" between provider and consumer, such as a network operator.

Five essential characteristics

Objective 4.3Recognizing the five features that make a service cloud computing, and the security consequence of each.

  1. On-demand self-service"A consumer can unilaterally provision computing capabilities ... as needed automatically without requiring human interaction with each service provider." Security point: anyone with access can create servers and storage in minutes, so permissions and spending alerts matter.
  2. Broad network accessCapabilities are "available over the network" from many kinds of device, "mobile phones, tablets, laptops, and workstations." Security point: the management console is reachable from the Internet, so strong MFA is essential.
  3. Resource pooling"The provider's computing resources are pooled to serve multiple consumers using a multi-tenant model", with "a sense of location independence": the customer may choose a country or region but not the exact machine. Security point: tenants must be isolated from each other, and data location matters for laws such as GDPR.
  4. Rapid elasticityCapabilities "scale rapidly outward and inward commensurate with demand" and "often appear to be unlimited." Security point: capacity absorbs traffic spikes (useful against some denial-of-service), but an attacker with stolen keys can also scale up costs or crypto-mining.
  5. Measured serviceResource use is metered, "monitored, controlled, and reported, providing transparency for both the provider and consumer", typically pay-per-use. Security point: usage and billing data are an early warning of misuse.

For the retailer, elasticity is the main attraction: the online shop scales up for holiday traffic and back down in January, paying only for what it uses.

Service models

Objective 4.3Telling IaaS, PaaS and SaaS apart by what the customer controls in each.

SP 800-145 defines three service models by how much of the stack the consumer manages:

  • Infrastructure as a Service (IaaS): the consumer can "provision processing, storage, networks, and other fundamental computing resources" and run any software. The consumer controls "operating systems, storage, and deployed applications; and possibly limited control of select networking components (e.g., host firewalls)." Example: the retailer's virtual servers for the loyalty database.
  • Platform as a Service (PaaS): the consumer deploys its own applications onto the provider's platform and "has control over the deployed applications and possibly configuration settings for the application-hosting environment", but not the servers or operating systems. Example: the online shop's application platform and managed database.
  • Software as a Service (SaaS): the consumer uses "the provider's applications running on a cloud infrastructure", controlling at most "limited user-specific application configuration settings." Example: the email and office suite.

Newer terms such as serverless or function as a service (code runs only when triggered, with no servers to manage) and containers ("a method for packaging and securely running an application", NIST SP 800-190) fit within or between these models. They are not separate NIST models; for the exam, place them by what the customer still manages. Serverless behaves like PaaS: the customer manages the code and its permissions.

Deployment models

Objective 4.3Distinguishing private, community, public and hybrid clouds by who may use the infrastructure.

SP 800-145's four deployment models describe who the infrastructure is for:

  • Private cloud: "provisioned for exclusive use by a single organization." It "may be owned, managed, and operated by the organization, a third party, or some combination of them, and it may exist on or off premises."
  • Community cloud: for "a specific community of consumers from organizations that have shared concerns (e.g., mission, security requirements, policy, and compliance considerations)", such as government agencies or a group of hospitals.
  • Public cloud: "provisioned for open use by the general public"; it "exists on the premises of the cloud provider."
  • Hybrid cloud: "a composition of two or more distinct cloud infrastructures (private, community, or public) that remain unique entities, but are bound together" by technology that lets data and applications move between them, for example "cloud bursting" into a public cloud at peak times.

Multi-cloud means using services from more than one provider. It is not one of NIST's four models, but it is common, and a NIST draft from August 2026 (IR 8613) notes the challenge: each provider has its own security tools, configurations and shared responsibility framework, so keeping consistent controls across them is hard.

Private does not mean on-premises. A private cloud is defined by exclusive use, not location: it can be run by a third party in the third party's data centre. Only the public cloud is defined by location ("on the premises of the cloud provider").

The shared responsibility model

Objective 4.3Knowing which security tasks the provider and the customer each carry in IaaS, PaaS and SaaS, and that the customer remains accountable either way.

Moving to the cloud hands some security tasks to the provider, but not all of them. NIST's guide to public cloud security (SP 800-144) says each service model brings "different allocations of control and responsibility between the cloud consumer and the cloud provider", and that while tasks can be outsourced, accountability cannot: "Ultimately, the organization is accountable for the choice of public cloud and the security and privacy of the outsourced service."

The major providers describe the split in similar terms. One summarizes it as security "of" the cloud (the provider's infrastructure) versus security "in" the cloud (what the customer builds and configures); another says that "for all cloud deployment types, you own your data and identities"; a third calls its approach "shared fate", stressing an ongoing partnership. The pattern:

  • Always the provider: physical data centres, hardware, the physical network and the virtualization layer.
  • Always the customer: its data (classification, protection, encryption choices), identities and access (accounts, MFA, permissions), configuration settings, and the devices its users connect from.
  • Shifts with the model: in IaaS the customer also patches and secures the operating system, applications and network rules; in PaaS the provider runs the operating system and runtime and the customer secures its code and configuration; in SaaS the provider runs the application and the customer manages users, settings and data.

The customer's share shrinks from IaaS to SaaS but never reaches zero. The retailer records the split for each cloud service:

Responsibility record: loyalty database (IaaS)
Provider
Data centres, physical servers, storage hardware, hypervisor, physical network
Retailer
Operating system patching, database software, firewall rules (security groups), encryption keys, backups
Retailer (always)
Customer data and its classification, admin accounts and MFA, access permissions, logging and monitoring
Evidence from provider
Independent audit reports (for example SOC 2, ISO/IEC 27001) reviewed each year
Owner
Head of IT operations

Customers check the provider's half through independent assurance rather than visiting data centres: audit reports, the Cloud Security Alliance's STAR registry (self-assessments at Level 1, third-party audits at Level 2), and for US agencies FedRAMP, which provides "a standardized approach to security and risk assessment for cloud products and services." FedRAMP is mid-overhaul: its "20x" program, announced in March 2025, moves toward automated, continuous validation, and its 2026 rules call approved services "FedRAMP Certified".

When the split fails

Objective 4.3Learning from real breaches caused by gaps on the customer side and on the provider side, and the controls that close them.

Most cloud breaches happen on the customer's side of the line, through weak access controls and misconfiguration, but providers fail too.

Customer side: stolen passwords and no MFA. In 2024, attackers stole data from customers of the cloud data platform Snowflake, and CISA urged customers to hunt for malicious activity in their accounts. Mandiant's investigation found no evidence of a breach of Snowflake's own environment: "every incident ... was traced back to compromised customer credentials." The accounts had no MFA, used passwords stolen by malware that had never been changed, sometimes for years, and had no network allow lists. Around 165 organizations were notified.

Provider side: a stolen signing key. In 2023 a group assessed as linked to China used a Microsoft signing key created in 2016 to forge access to Exchange Online mailboxes of 22 organizations and over 500 individuals. The US Cyber Safety Review Board (report released April 2024) said "this intrusion should never have happened" and blamed "a cascade of security failures at Microsoft." The customer still mattered: the US State Department detected it with its own logging.

CISA and NSA's 2024 cloud guidance focuses on the customer's share: secure cloud identity and access management, secure key management, network segmentation and encryption, protecting data in the cloud, and managing the risks of managed service providers. CISA's SCuBA project publishes secure configuration baselines for major SaaS office suites, which US federal agencies must apply under BOD 25-01. The retailer's fixes are simple and close the Snowflake gap: MFA on every cloud account, no long-lived passwords for automated access, access only from known networks, and logs sent to its own monitoring.

Shared responsibility for AI services

Objective 4.3Applying the shared responsibility model when an AI solution is hosted in the cloud, from a ready-made AI app to a self-hosted model.

The CC outline expects you to apply the shared security model when hosting AI solutions. The same pattern holds, with new layers. Provider guidance published in 2026 splits AI services into the AI platform (infrastructure, model, weights, built-in safety filters), the AI application (grounding data, plugins, orchestration) and AI usage (identity, devices, data governance, user behaviour), and states for AI agents that the customer always keeps its data, identities, access management and human approval of high-impact actions: "Autonomy never reduces accountability."

  • Using an AI SaaS service (a chatbot or assistant): the provider runs the model and its safety filters. The customer still owns what goes into prompts, the contract terms on whether its data is used for training, who has access, which data sources the tool can reach, acceptable use, and checking outputs before relying on them.
  • Building on a hosted model (PaaS): the customer adds the application, its prompts and instructions, grounding data, and testing against attacks such as prompt injection.
  • Self-hosting a model (IaaS): the customer also owns the model weights, their protection, the safety filtering and patching the whole stack.

The Cloud Security Alliance's AI Controls Matrix (2025) spreads responsibility across five parties: cloud provider, model provider, orchestrated service provider, application provider and AI customer. US agencies have their own route: FedRAMP ran an AI prioritization initiative from August 2025 to April 2026 for conversational AI tools, requiring, among other things, single sign-on, role-based access and separation of each customer's data.

The retailer's chatbot uses a hosted model (PaaS). The provider secures the model and platform; the retailer owns the chatbot's instructions, its read-only connection to order data, opting out of training on customer conversations, logging, and the human approval step for refunds (objective 3.2).

Further reading

  • NIST SP 800-145, The NIST Definition of Cloud Computing (NIST, 2011): the five characteristics, three service models and four deployment models.
  • NIST SP 800-144, Guidelines on Security and Privacy in Public Cloud Computing (NIST, 2011): outsourcing, accountability and the division of responsibilities.
  • CISA and NSA Release Cybersecurity Information Sheets on Cloud Security Best Practices (CISA, March 2024): identity, keys, segmentation, data and managed service providers.
  • FedRAMP 20x (FedRAMP, 2025-2026): how US government cloud assurance is moving to automated validation.

Key takeaways

  • NIST SP 800-145: cloud is on-demand network access to a shared pool of configurable resources, with 5 characteristics, 3 service models, 4 deployment models. Roles: consumer, provider, auditor, broker, carrier.
  • Characteristics: on-demand self-service, broad network access, resource pooling (multi-tenant, location independence), rapid elasticity, measured service (metered, pay-per-use).
  • IaaS: customer manages OS, storage, apps and some networking. PaaS: customer manages its applications and their settings. SaaS: customer manages only user settings. Serverless and containers are not separate NIST models.
  • Deployment: private (one organization, on or off premises), community (shared concerns), public (open use, at the provider), hybrid (two or more bound together). Multi-cloud means several providers.
  • Shared responsibility: the provider always secures physical facilities, hardware and virtualization; the customer always owns data, identities and access, configuration and endpoints; the rest shifts from customer (IaaS) to provider (SaaS). Accountability stays with the customer (SP 800-144).
  • Failures: Snowflake 2024 customers (no MFA, stolen passwords) vs Microsoft Exchange Online 2023 (provider's key). Verify the provider through audits, CSA STAR or FedRAMP; secure your side with MFA, configuration baselines and your own logs.
  • For AI: SaaS AI leaves the customer prompts, data, access, configuration and output use; hosting or self-hosting adds the application, model, weights and safety filtering. Autonomy never reduces accountability.
