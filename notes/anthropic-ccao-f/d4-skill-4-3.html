4.3: Repeatable Workflow Design

Turning a task you redo every week by hand, or with a fresh prompt each time, into a set-up that gives the same quality every run, for anyone who runs it, and that a colleague can take over.

Overview

Skill 4.3

Repeatable Workflow Design: "Applying repeatable-workflow design to a recurring task currently done manually or with unstructured prompting, including Projects, Skills, connectors, code-executed steps, consistency across runs and users, and workflows handed off to a colleague who owns them afterward."

Exam items describe a recurring task that gives uneven results, or that only one person knows how to run, and ask what to build. Choosing capabilities for a one-off task is skill 3.1; the detail of configuring a Project, its knowledge and its instructions is Domain 5. This skill is about putting the parts together so the task repeats reliably.

Sources: the Claude Help Center articles on using Skills, Projects, connectors and creating files, and the Agent Skills overview, checked on 20 November 2026 and paraphrased. The Skill and the handover note are my own.

Running example. The weekly supplier report from skill 3.1. Today the operations coordinator, Sam, downloads two exports every Monday, pastes them into a new chat with a slightly different prompt each week, and fixes the layout by hand. Sam is moving to another role, and Priya will take the report over.

From ad hoc to repeatable

Skill 4.3Which part of the task goes where.

  • Project: the context that stays the same: instructions about readers and tone, and knowledge such as the supplier list with promised lead times and the last few reports for comparison. Shared on Team and Enterprise, so a colleague works from the same material.
  • Skill: the procedure and the output format: which figures to calculate, the thresholds to flag, the document layout, what to do when data is missing. Written once, used the same way every time.
  • Connector: where the inputs come from, such as a Drive folder of exports, so nobody downloads and re-uploads files. Each person signs in with their own account and permissions.
  • Code-executed steps: the calculations, so figures are computed from the files rather than written in prose, and the output file is built rather than pasted.
  • The person: the checks that need judgment, and sending the result.

Unstructured prompting fails a recurring task in predictable ways: wording changes each week, so the output does too; the method lives in one person's head; and nobody notices when the data changes shape.

Writing the Skill

Skill 4.3A custom Skill for the report.

supplier-report/SKILL.md (supplier-report/SKILL.md) 
---
name: supplier-report
description: Builds the weekly supplier performance report for the outdoor-gear shop from the deliveries and returns exports. Use when asked for the supplier report, supplier scorecard or weekly supplier summary.
---

# Weekly supplier performance report

## Inputs
- deliveries.csv and returns.csv for the week (exports from the stock system).
- If either file is missing or covers a different week, stop and say so.

## Steps
1. Using Python, calculate for each supplier: orders delivered, percent on time
   (delivered on or before the promised date), units returned as faulty, and
   faulty rate (returned units / delivered units).
2. Compare each figure with last week's report in the Project, if present.
3. Flag any supplier below 90 percent on time or above 3 percent faulty.

## Output
A Word document, "Supplier report - week of <Monday's date>":
1. Three-line summary: best supplier, worst supplier, biggest change.
2. Table: supplier, orders, on time %, faulty %, change vs last week.
3. Flagged suppliers, one line each with the figure that triggered the flag.
4. "Data notes": anything missing, odd or excluded, and why.

Never estimate a figure. If it can't be calculated from the files, write
"not available" and explain in Data notes.
  • The description decides when it's used: Claude chooses Skills from your request; the Help Center says a good description "tells Claude when to invoke your skill". Include the words people actually use ("supplier report", "scorecard").
  • Exact definitions: "on time" and "faulty rate" are defined, so two runs, or two people, calculate them the same way.
  • Stop rules: missing or wrong-week files stop the run instead of producing a confident report from bad inputs.
  • A fixed layout with a "Data notes" section, so the reviewer always knows where to look.

Using and sharing Skills in claude.ai

Skill 4.3Setting up, uploading and sharing.

  • Availability: Skills are on all plans, Free to Enterprise, and need code execution turned on. Anthropic's built-in Skills cover Excel, Word, PowerPoint and PDF.
  • Turning them on: individuals turn on code execution under Settings > Capabilities, then Skills under Customize > Skills. Team has Skills on by default; on Enterprise, owners enable them in Organization settings.
  • Uploading your own: zip the Skill folder and upload it under Customize > Skills. Common upload errors: the folder name doesn't match the Skill name, the SKILL.md file is missing, or the ZIP is too large.
  • Sharing (Team and Enterprise):
    • share with specific people (or groups, on Enterprise); shared Skills are view-only and update automatically for recipients;
    • publish to the organisation's library, possibly after review, where it can be Available, Installed by default or Required;
    • owners can provision a Skill to every user.
  • Security: Skills can run code and install packages, so the Help Center warns of prompt injection and data exfiltration. Install only from trusted sources, and read the files of a Skill a colleague shares before turning it on.

Consistency across runs and users

Skill 4.3Making "the same task" give the same result (my checklist).

  • One source of each thing: the method in the Skill, the context in the Project, the inputs from the connector. People don't keep private versions.
  • A short, fixed trigger: "Build this week's supplier report." The Skill carries the detail, so the prompt can't drift.
  • Test before you rely on it: run the new set-up on the last few weeks' files and compare with the reports you already trust.
  • Test with another person: have a colleague run it from their own account. Differences show up in permissions, connector access or an instruction only you knew.
  • Keep the human check: a repeatable workflow still needs a reviewer; the fixed layout makes that check quick (skill 2.3).

"Save the best prompt in a document and paste it each week" is better than nothing, but it still depends on everyone copying it correctly and supplying the same files. A Project plus a Skill carries the context and the procedure for every run and every user.

Handing it to a colleague

Skill 4.3So the new owner can run, check and change it.

handoff.txt (Handover note) 
Handover note: weekly supplier report (from Sam to Priya, from 1 December)

Where it lives
  Project "Supplier report" (shared with you, Can edit)
    instructions: who reads the report and the house tone
    knowledge:    supplier list with promised lead times; last 4 reports
  Skill "supplier-report": a shared copy is view-only, so Sam has sent you
    the ZIP; upload it as your own Skill and keep the ZIP in "Reports/Skill"
  Connector: Google Drive, folder "Stock exports" (sign in with your account)

Each Monday (about 15 minutes)
  1. In the Project, new chat: "Build this week's supplier report."
  2. Check the Data notes section, and recheck one supplier's on-time % against
     the export.
  3. Save the document to "Reports/Suppliers"; replace the oldest of the four
     reports in Project knowledge with this one.
  4. Send it to the buying team.

When something changes
  New supplier or lead time   update the supplier list in Project knowledge
  Different report layout     edit the Skill (Output section) and run it once
                              on last week's files to compare
  Export columns renamed      the Skill stops and says so: fix the Steps
                              section, then rerun

Who to ask: Sam (until 31 December); buying team lead for the thresholds.
  • Access first: the Project shared with edit rights, the Skill in the new owner's own account (a shared copy is view-only), and the connector signed in with their account.
  • Ownership, not just running: the note says how to change each part (the knowledge, the Skill, the thresholds), so the new owner can maintain the workflow, not only press go.
  • Overlap: the previous owner stays available for a few runs, and the new owner runs it once while they watch.

Key takeaways

  • Split a recurring task: the Project holds stable context, a Skill holds the procedure and format, connectors bring the inputs, code computes the figures, and a person checks and sends.
  • A good Skill has a description that says when to use it, exact definitions, stop rules for bad inputs, and a fixed layout with a data-notes section.
  • Skills are on all plans with code execution on; upload a ZIP with SKILL.md; share (view-only), publish to the organisation library, or have owners provision; install only trusted Skills.
  • Consistency comes from one source for each part, a short fixed trigger, testing on past data and with another user, and a quick human check.
  • Hand over access, the know-how to change each part, and a supervised first run, so the colleague owns the workflow afterwards.
