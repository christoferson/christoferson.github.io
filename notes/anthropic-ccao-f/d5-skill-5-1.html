5.1: Project Configuration

Setting up a Project for a job that keeps coming back: deciding what goes in the instructions, what goes in the knowledge, what belongs in a Skill, how memory is scoped, and how to keep one stream of work from bleeding into another.

Overview

Skill 5.1

Project Configuration: "Applying Project configuration to a defined recurring use case, including instructions, knowledge sources, Skills, and scoped memory, and choosing among instruction, knowledge source, and Skill for each requirement while keeping unrelated work streams isolated."

Exam items list the requirements of a recurring task and ask where each belongs, or why a Project's output has gone wrong. Building a whole repeatable workflow is skill 4.3; connectors and keeping knowledge current are skill 5.2; writing the instructions themselves is skill 5.3. This skill is the configuration choices.

A Project has instructions, knowledge, separate chats and its own memory

Skill 5.1What each part does, per the Help Center.

  • Name and description: for people. Claude doesn't see them, so nothing important should be only there.
  • Instructions: how Claude should behave and respond, applied to every chat in the Project. Keep them short: Claude's role, key rules and general context.
  • Knowledge: documents, text and code that Claude uses across all the Project's chats. On paid plans, retrieval kicks in as knowledge grows, so only relevant parts are loaded.
  • Chats: each chat is separate. Context isn't shared between chats in a Project unless it's added to the knowledge.
  • Memory: each Project has its own (below).
  • Limits: Projects are on all plans; Free accounts can have up to five.

Short rules go in instructions, reference material in knowledge, procedures in a Skill

Skill 5.1Rules of thumb for each requirement.

  • Instruction if it's a short rule about behaviour or tone that applies to every chat: the audience, a "never do", what to do when a fact is missing.
  • Knowledge if it's reference material Claude should look things up in: style guides, spec sheets, policies, past examples. Long material belongs here, not pasted into the instructions.
  • Skill if it's a procedure or output format that should run the same way each time, especially if it's also needed outside this Project, or includes steps like checks or scripts. Skills are turned on per person (or provisioned by owners), so everyone using the Project needs it enabled.
  • Personal memory, not the Project, for one person's preferences.

The exam guide treats Skills as part of a Project's configuration. The Help Center's Skills article doesn't describe attaching a Skill to a Project, so the safe reading is: the Project instructions say when to use the Skill, and each member has it enabled.

Keep instructions short and point to curated knowledge and a Skill

Skill 5.1Seven requirements, sorted.

Take an online team of three that writes about 40 new product pages a month and wants them to read the same whoever writes them.

Project instructions, as saved:

You write product pages for an outdoor-gear shop's online store. Readers are
keen beginners. Be friendly and plain; no hype words. Use the style guide in
this Project for wording and the spec sheets for every fact. If a fact isn't
in a spec sheet, write "[check with buyer]" instead of guessing. Use the
product-page Skill for the layout.

Isolation: separate Project from "Supplier report" and "Store openings";
"Use account memory" off, so other work doesn't leak into product pages.
  • The instructions stay short and point to the knowledge and the Skill rather than repeating them.
  • Knowledge is curated: only this season's spec sheets and the current style guide, so Claude can't draw on outdated versions (skill 5.2).
  • Examples go in knowledge: ten approved pages show the target better than a description of it.

"Put everything in the instructions" (the whole style guide, the spec sheets, the layout) makes them long, hard to maintain and easy to get out of date. "Put everything in knowledge" leaves the rules that must always apply buried in a document. Each requirement has a natural home.

Give each work stream its own Project so memory and knowledge stay apart

Skill 5.1Keeping unrelated work streams apart.

  • Per-Project memory: each Project has its own memory. Inside a Project, Claude uses that Project's memory plus your memory from chats outside Projects, but never another Project's memory.
  • Full isolation: turning off "Use account memory" on the Project page stops your general memory coming in too.
  • One chat without memory: switch off Memory in the "+" menu before the first message; that chat neither uses nor adds to the Project's memory.
  • One Project per work stream: separate Projects for product pages, the supplier report and store openings, and for different clients or teams, keep their knowledge, instructions and memory apart. Mixing streams in one Project lets one's documents and memories colour the other's output.

Give edit rights only to the people who own the configuration

Skill 5.1Team and Enterprise.

  • Visibility: private (only you and people you invite) or shared with the whole organisation, where admins allow it.
  • Roles: "Can view" members see the knowledge and instructions and can chat, but can't change them; "Can edit" members can change instructions and knowledge and member settings. Give edit rights to the people who own the configuration.
  • Housekeeping: only the creator can remove access. Archiving keeps members and sharing as they were; an archived Project must be unarchived before it can be deleted.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A team pastes its whole style guide into the Project instructions. What is better?
  1. A. Keep it there
  2. B. Put the style guide in knowledge and keep the instructions to short rules that point to it
  3. C. Put it in memory
  4. D. Repeat it in every prompt
Answer
B
Why
Long reference material belongs in knowledge.
Question 2
Scenario
Where should one person’s writing preferences go?
  1. A. Project instructions
  2. B. Their personal memory or account instructions
  3. C. Project knowledge
  4. D. A Skill
Answer
B
Why
Project instructions apply to everyone in the Project.
Question 3
Scenario
Product pages and a client’s supplier report share one Project, and terms leak between them. What fixes it?
  1. A. A longer instruction
  2. B. Separate Projects for each work stream
  3. C. Turning off code execution
  4. D. Deleting chats
Answer
B
Why
Separate Projects keep knowledge, instructions and memory apart.
Question 4
Scenario
A Project’s description says “always use British spelling”, but outputs ignore it. Why?
  1. A. The model is wrong
  2. B. Claude doesn’t see the name or description; put the rule in the instructions
  3. C. Spelling can’t be set
  4. D. Memory overrides it
Answer
B
Why
Nothing important should live only in the description.

Key takeaways

  • A Project has instructions (applied to every chat), knowledge (used across its chats, retrieved as needed), separate chats, and its own memory. Claude doesn't see the name or description.
  • Instruction for short always-on rules; knowledge for reference material and examples; Skill for repeatable procedures and formats; personal memory for one person's preferences.
  • Keep instructions short and point to knowledge and Skills; curate knowledge to current versions.
  • Use one Project per work stream; Projects never see each other's memory; turn off "Use account memory" for full isolation, or turn memory off for a single chat.
  • Share privately or org-wide; Can view versus Can edit; give edit rights to the configuration's owners.
