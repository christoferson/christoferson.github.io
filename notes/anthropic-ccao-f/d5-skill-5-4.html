5.4: Configuration Lifecycle and Degradation

When a set-up that used to work starts producing worse results: working out which layer changed (instructions, knowledge, a Skill, memory or the model), fixing that layer, and proving the fix worked.

Overview

Skill 5.4

Configuration Lifecycle and Degradation: "Evaluating an established Claude configuration whose output quality has shifted, including instructions, knowledge freshness, Skill versions, and accumulated memory, to attribute the degradation to the responsible layer and restore performance."

Exam items describe a Project or workflow that worked for months and then drifted, say what has and hasn't changed, and ask what to do first. The guide's own sample question for Domain 5 is of this kind; it isn't reproduced here. Diagnosing a single prompt is skill 1.3; this skill is about a configuration over time.

Sources: the Claude Help Center articles on using Skills, Projects, chat search and memory, model access, and adapting to model deprecations, checked on 20 November 2026 and paraphrased. The diagnosis log is my own.

Running example. The weekly supplier report from skill 4.3, now owned by Priya, ran well for ten weeks. This week's report looks different and has two odd details.

The layers and their symptoms

Skill 5.4What each layer tends to break (my mapping).

  • Instructions: behaviour changes across every output: tone, length, rules followed or ignored. Check whether anyone edited them, and whether account-level Instructions for Claude now conflict.
  • Knowledge freshness: specific facts are wrong or outdated (an old price, a retired policy, a superseded spec) while the format is fine. Uploaded files don't update themselves, and old and new versions side by side compete.
  • Skill versions: the procedure or format changes suddenly (sections missing, new columns, different checks). A Skill shared with you updates automatically when its owner edits it, and an organisation can publish a new library version.
  • Accumulated memory: outputs carry assumptions or terms from somewhere else: an old role, a finished project, another team's or client's vocabulary. A Project's memory builds up over time, and your general memory also comes in unless "Use account memory" is off.
  • Model and effort: style shifts everywhere, often after a model update or an admin change, while facts and format rules hold (below).
  • Inputs and connectors: the source data changed shape, or a connector lost access, so Claude worked from less or different material.

Diagnosing layer by layer

Skill 5.4Three symptoms, three different layers.

degradation_log.txt (Degradation log) 
Degradation log: weekly supplier report (owner: Priya), week of 16 November

Symptoms (first seen this week; last 10 weeks were fine)
  a. The flagged-suppliers section has disappeared; the table has new columns.
  b. One supplier's on-time % looks too low.
  c. The summary mentions "store openings", which has nothing to do with suppliers.

What changed recently?  (check the layers in this order; one at a time)

Layer          Check                                       Finding
-------------------------------------------------------------------------------------------
Inputs         same exports, same columns as last week?    yes, unchanged
Instructions   Project instructions edited?                no edits since September
Skill          version or source changed?                  YES: Priya uses the shared
                                                           "supplier-report" Skill from the
                                                           buying team; their lead updated
                                                           it on 14 Nov for a different
                                                           report. Shared Skills update
                                                           automatically.  -> explains (a)
Knowledge      files current?                              supplier list still has a lead
                                                           time from before a contract
                                                           change in October  -> explains (b)
Memory         topics that don't belong here?              "Use account memory" is on; a
                                                           memory about the store-openings
                                                           plan is coming in from Priya's
                                                           general chats  -> explains (c)
Model          model or effort changed?                    no

Fixes (each tested by rerunning last week's files and comparing with last week's report)
  (a) Upload the earlier Skill version as Priya's own copy, named
      "supplier-report v1 (2026-09)"; agree with buying team who owns which.
  (b) Replace the supplier list with the October version; date the file.
  (c) Turn off "Use account memory" for this Project; delete the stray memory.

Result: rerun matches the trusted report. Logged changes; next review 1 December.
  • Start from "what changed?": the instructions were untouched, so rewriting them would have fixed nothing. The cause is usually a layer that changed recently, possibly without the owner noticing.
  • Match symptom to layer: a format change points to the Skill, a wrong figure to knowledge, an out-of-place topic to memory.
  • More than one cause is normal: check every layer rather than stopping at the first finding.
  • Fix the responsible layer: for each symptom, the fix goes where the cause is.

Fixing a layer that didn't change is the usual mistake: adjusting the model or the instructions when neither has moved. It can't repair stale knowledge, a changed Skill or stray memories, and it adds a new variable that makes the real cause harder to find.

Model changes

Skill 5.4When the model itself is the layer that moved.

  • Models are retired: Anthropic calls deprecation a routine part of the model lifecycle and says it has deprecated most models around a year after release.
  • A newer model can feel different: the Help Center mentions it might be more or less talkative or have a different tone, alongside improvements such as better instruction following.
  • What to do: test the newer model early, side by side with your most important prompts, and tune the instructions where its behaviour differs. You can also ask Claude to look at chats you liked and draft instructions for itself.
  • Admin changes: on Enterprise, if a model is turned off, an open chat falls back to the member's default model, and lowered effort caps apply to the next message (skill 3.2).

Restoring and preventing

Skill 5.4Proving the fix, then keeping it fixed (my practice).

  • A trusted baseline: keep a past output you know is right, with its inputs. After a fix, rerun those inputs and compare.
  • One change at a time: so you know which fix worked.
  • Control your Skill version: if a workflow depends on a Skill, own a copy (or agree the owner and how changes are announced), and name versions.
  • Date knowledge and review it: an owner for each source and a review trigger (skill 5.2).
  • Review memory: look through the topics now and then, delete what doesn't belong, and isolate Projects that must stay separate (skill 3.3).
  • Keep a change log: what changed in the instructions, knowledge, Skill or settings, and when. The next diagnosis starts there.

Key takeaways

  • When an established configuration degrades, ask what changed, and check each layer: inputs, instructions, Skill, knowledge, memory, model.
  • Symptoms point to layers: everywhere-behaviour to instructions or model; wrong facts to stale knowledge; sudden format changes to a Skill version; out-of-place assumptions or terms to memory.
  • Shared Skills update automatically; uploaded knowledge doesn't; Project memory accumulates and account memory flows in unless turned off.
  • Fix the responsible layer; changing a layer that hasn't moved can't repair stale knowledge, a changed Skill or stray memories.
  • Prove fixes against a trusted baseline, one change at a time, and prevent repeats with Skill version control, dated knowledge, memory review and a change log.
