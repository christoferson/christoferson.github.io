Overview

Task 2.4

Automate and configure network infrastructure.

Networks change rarely but are hard to change safely: a subnet CIDR edit replaces the subnet, a hardcoded Availability Zone breaks in another account, and a console fix drifts from the template. Questions ask which CloudFormation feature, CDK setting or event-driven pattern meets a requirement such as "deploy the same VPC baseline to every new account", "react when a VPN BGP session drops", or "keep a security group in sync with AWS IP ranges".

The travel company keeps its network in code: a VPC baseline deployed by StackSets to every account, the Transit Gateway, endpoints and firewall in the network account's stacks, and EventBridge rules that page the network team and repair common misconfigurations.

Infrastructure as code

Knowledge 2.4.1Infrastructure as code (IaC) (for example, AWS Cloud Development Kit [AWS CDK], AWS CloudFormation, AWS CLI, AWS SDK, APIs)

CLI, SDK and APIs

Every network action is an API call (for example CreateTransitGatewayRoute), reachable from the AWS CLI, the SDKs (such as Boto3 in Lambda functions) or CloudFormation. Scripts suit one-off tasks and event handlers; declarative templates suit infrastructure that must be recreated, reviewed and kept in sync. Mind API throttling in bulk scripts, for example Route 53's change-based limits.

CloudFormation features that matter for networks

  • Parameters with AWS-specific types (AWS::EC2::VPC::Id, List<AWS::EC2::Subnet::Id>) validate values in the deploying account and Region; SSM parameter types (AWS::SSM::Parameter::Value<String>) read central values such as a shared CIDR or the latest AMI.
  • Pseudo parameters: AWS::Region, AWS::AccountId, AWS::Partition, AWS::StackName, and AWS::NoValue to drop a property conditionally.
  • Fn::GetAZs lists AZs for the Region; !Select [0, !GetAZs ""] picks one. It returns only AZs with a default subnet (if any exist), and the order can change when AZs are added.
  • Fn::Cidr [ipBlock, count, cidrBits] carves subnets; the third value is host bits, so 8 gives /24s and 5 gives /27s.
  • Cross-stack references: Outputs with Export and Fn::ImportValue work in one account and Region, and an export in use cannot be changed or deleted. Fn::GetStackOutput (May 2026) reads another stack's output across accounts and Regions without an export, but it is a weak reference resolved only at deploy time.
  • Dynamic references: {{resolve:ssm:...}}, {{resolve:secretsmanager:...}}. A VPN pre-shared key must come from Secrets Manager (ssm-secure is not supported on AWS::EC2::VPNConnection), and rotating the secret changes nothing until the resource is updated.
  • Update behavior: changing a VPC's CidrBlock replaces the VPC; changing a subnet's CIDR or AZ creates a new subnet and deletes the old. Add ranges with AWS::EC2::VPCCidrBlock instead.
  • DependsOn: routes to an internet gateway, Elastic IPs, public instances and load balancers must depend on the VPCGatewayAttachment; so does VGW route propagation.
  • DeletionPolicy and UpdateReplacePolicy (Retain) keep resources such as Elastic IPs or a Direct Connect gateway when a stack or replacement would delete them.
  • Custom resources (Lambda-backed) fill gaps, for example looking up a value or calling a vendor API; registry resource types (including third-party ones) also support drift detection.
  • Change sets preview changes, including replacements; drift detection finds console edits, and drift-aware change sets (--deployment-mode REVERT_DRIFT) can put them back; stack refactoring (February 2025) moves resources between stacks without recreating them (not Elastic IPs, customer gateways or Route 53 records); the IaC generator (2024) creates templates from existing resources.
  • Hooks and CloudFormation Guard check templates and resources against rules before deployment, for example "no security group open to 0.0.0.0/0 on port 22".

AWS CDK

The CDK writes CloudFormation from TypeScript, Python, Java, C# or Go. Constructs come in levels: L1 (CfnTransitGatewayRoute, one-to-one with CloudFormation), L2 (ec2.Vpc, with defaults and helper methods) and L3 patterns. cdk synth, cdk diff and cdk deploy generate, compare and deploy.

  • ec2.Vpc defaults to 10.0.0.0/16, public and private subnets in up to 3 AZs, and one NAT gateway per AZ; set natGateways lower to save cost. IpAddresses.awsIpamAllocation() takes the CIDR from an IPAM pool.
  • Subnet types: PUBLIC, PRIVATE_WITH_EGRESS (routes through NAT) and PRIVATE_ISOLATED.
  • Vpc.fromLookup() needs an explicit account and Region and caches results in cdk.context.json, which must be committed; environment-agnostic stacks use only 2 AZs.
  • VpcV2 (with Transit Gateway and peering constructs) is still experimental in @aws-cdk/aws-ec2-alpha.
A VPC for an application account: CIDR from IPAM, three subnet tiers, one NAT gateway to save cost (CDK, TypeScript) 
import { Stack, StackProps } from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class AppVpcStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    new ec2.Vpc(this, 'AppVpc', {
      // The /20 comes from the Regional IPAM pool, so it never overlaps
      ipAddresses: ec2.IpAddresses.awsIpamAllocation({
        ipv4IpamPoolId: 'ipam-pool-0use1prod12345',
        ipv4NetmaskLength: 20,
        defaultSubnetIpv4NetmaskLength: 24,
      }),
      maxAzs: 3,
      natGateways: 1, // non-production: one NAT gateway instead of three
      subnetConfiguration: [
        { name: 'public', subnetType: ec2.SubnetType.PUBLIC },
        { name: 'app', subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
        { name: 'data', subnetType: ec2.SubnetType.PRIVATE_ISOLATED },
      ],
    });
  }
}

Hardcoding problems

Knowledge 2.4.3Common problems of using hardcoded instructions in IaC templates when provisioning cloud networking resources

Availability Zone names

us-east-1a maps to a different physical AZ in each account, and not every account has every AZ. Use Fn::GetAZs or parameters, and AZ IDs (use1-az1, the subnet's AvailabilityZoneId property) when subnets must line up across accounts, for example for VPC sharing or PrivateLink.

CIDR blocks

The same hardcoded 10.0.0.0/16 in every stack produces overlapping VPCs that cannot be peered or routed. Pass CIDRs as parameters, derive subnets with Fn::Cidr, or allocate from IPAM pools.

Account IDs, Regions and ARNs

A template with 123456789012 or us-east-1 in ARNs works only there. Build ARNs with !Sub arn:${AWS::Partition}:...:${AWS::Region}:${AWS::AccountId}:...; AWS::Partition also makes templates work in GovCloud and China.

Resource IDs from other stacks

Pasting a vpc- or tgw- ID breaks when that resource is recreated. Use exports and imports, Fn::GetStackOutput, or SSM parameters that the owning stack updates.

Secrets

A pre-shared key or password in a template ends up in source control and stack history, and CloudFormation does not redact outputs. Use Secrets Manager dynamic references and NoEcho parameters.

Custom resource names

A fixed name (for example a security group name) prevents the same template being deployed twice in an account and blocks any update that needs replacement: "You can't perform an update that causes a custom-named resource to be replaced." Let CloudFormation generate names.

AMI IDs and service IP addresses

AMI IDs differ per Region and change; read them from public SSM parameters. AWS service IP ranges change too; use AWS-managed prefix lists (such as the CloudFront origin-facing list) or automate updates from the IP ranges topic (below).

Repeatable network configurations

Skill 2.4.1Creating and managing repeatable network configurations

A portable baseline: CIDR as a parameter, subnets from Fn::Cidr, AZs from Fn::GetAZs, the route waits for the gateway attachment, IDs exported (CloudFormation YAML, excerpt) 
Parameters:
  VpcCidr:
    Type: String
    Default: 10.64.0.0/20
    AllowedPattern: '^(\d{1,3}\.){3}\d{1,3}/\d{1,2}$'

Resources:
  Vpc:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: !Ref VpcCidr
      EnableDnsSupport: true
      EnableDnsHostnames: true   # needed for private zones and endpoints

  PublicSubnetA:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref Vpc
      AvailabilityZone: !Select [0, !GetAZs '']
      CidrBlock: !Select [0, !Cidr [!GetAtt Vpc.CidrBlock, 6, 8]]   # first /24

  PrivateSubnetA:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref Vpc
      AvailabilityZone: !Select [0, !GetAZs '']
      CidrBlock: !Select [3, !Cidr [!GetAtt Vpc.CidrBlock, 6, 8]]   # fourth /24

  Igw:
    Type: AWS::EC2::InternetGateway
  IgwAttachment:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties: {VpcId: !Ref Vpc, InternetGatewayId: !Ref Igw}

  PublicRouteTable:
    Type: AWS::EC2::RouteTable
    Properties: {VpcId: !Ref Vpc}
  DefaultRoute:
    Type: AWS::EC2::Route
    DependsOn: IgwAttachment    # the route fails if the gateway is not attached yet
    Properties:
      RouteTableId: !Ref PublicRouteTable
      DestinationCidrBlock: 0.0.0.0/0
      GatewayId: !Ref Igw

Outputs:
  VpcId:
    Value: !Ref Vpc
    Export: {Name: !Sub '${AWS::StackName}-VpcId'}

StackSets for every account

With service-managed permissions (Organizations), a StackSet deploys a template to OUs and Regions, and automatic deployment adds it to accounts that join the OU later. Operation preferences control how many accounts deploy at once and how many failures are tolerated. Service-managed StackSets never deploy to the management account and do not support nested stacks, macros or transforms.

Deploy the VPC baseline to every account in the Workloads OU, in two Regions, one account at a time (AWS CLI) 
aws cloudformation create-stack-set \
  --stack-set-name vpc-baseline \
  --template-body file://vpc-baseline.yaml \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation create-stack-instances \
  --stack-set-name vpc-baseline \
  --deployment-targets OrganizationalUnitIds=ou-trvl-workloads1 \
  --regions us-east-1 eu-central-1 \
  --operation-preferences MaxConcurrentCount=1,FailureToleranceCount=0
  • Split templates by lifecycle: a central network stack (Transit Gateway, endpoints, firewall) in the network account, and per-account baselines (VPC, attachment, rule and Profile associations).
  • Version templates in Git, deploy through a pipeline (CloudFormation Git sync or CDK Pipelines), and review change sets for replacements before applying.
  • Use IPAM pools and Cloud WAN attachment policies so new VPCs get addresses and segments without editing templates.

Event-driven automation

Knowledge 2.4.2Event-driven network automation

Event-driven automation reacts to a change instead of polling: a source emits an event, an EventBridge rule matches it, and a target acts (SNS, Lambda, Step Functions, Systems Manager Automation). Network event sources:

  • Network Manager (Transit Gateways registered in a global network, and Cloud WAN): source aws.networkmanager, detail types "Network Manager Topology Change", "Routing Update" and "Status Update" (for example VPN-CONNECTION-BGP-DOWN, TGW-ROUTE-INSTALLED). Delivered only in us-west-2, so rules must be there.
  • AWS Health: VPN tunnel endpoint replacements (AWS_VPN_TUNNEL_UPDATE_AVAILABLE with lifecycle control), single-tunnel notices, Direct Connect maintenance.
  • CloudWatch alarms on metrics such as TunnelState or VirtualInterfaceBgpStatus.
  • AWS Config rule compliance changes, CloudTrail API calls (for example someone calling AuthorizeSecurityGroupIngress), and GuardDuty or Security Hub findings.
  • The AmazonIpSpaceChanged SNS topic (arn:aws:sns:us-east-1:806199016981:AmazonIpSpaceChanged, subscribed from us-east-1) whenever ip-ranges.json changes.

Skill 2.4.2Integrating event-driven networking functions

Page the network team when any VPN in the global network loses BGP (AWS CLI; the rule must be in us-west-2) 
aws events put-rule --region us-west-2 \
  --name vpn-bgp-down \
  --event-pattern '{
    "source": ["aws.networkmanager"],
    "detail-type": ["Network Manager Status Update"],
    "detail": {"changeType": ["VPN-CONNECTION-BGP-DOWN"]}
  }'

aws events put-targets --region us-west-2 --rule vpn-bgp-down \
  --targets Id=oncall,Arn=arn:aws:sns:us-west-2:111111111111:network-oncall
Keep a managed prefix list in step with CloudFront's published ranges, triggered by the AmazonIpSpaceChanged topic (Lambda, Python) 
import json, urllib.request, boto3

PREFIX_LIST_ID = "pl-0cloudfrontranges1"   # customer-managed list used in security groups
ec2 = boto3.client("ec2")

def handler(event, context):
    url = json.loads(event["Records"][0]["Sns"]["Message"])["url"]
    data = json.load(urllib.request.urlopen(url))
    wanted = {p["ip_prefix"] for p in data["prefixes"]
              if p["service"] == "CLOUDFRONT" and p["region"] == "GLOBAL"}

    current = {e["Cidr"] for e in ec2.get_managed_prefix_list_entries(
        PrefixListId=PREFIX_LIST_ID)["Entries"]}
    version = ec2.describe_managed_prefix_lists(
        PrefixListIds=[PREFIX_LIST_ID])["PrefixLists"][0]["Version"]

    add = [{"Cidr": c} for c in wanted - current]
    remove = [{"Cidr": c} for c in current - wanted]
    if add or remove:
        # The list's max entries counts against every security group that uses it
        ec2.modify_managed_prefix_list(PrefixListId=PREFIX_LIST_ID,
            CurrentVersion=version, AddEntries=add, RemoveEntries=remove)

For CloudFront specifically, the AWS-managed prefix list com.amazonaws.global.cloudfront.origin-facing already does this; the pattern matters for other services or filtered subsets. Notifications can arrive out of order, so compare the synctoken or re-read the file.

Config rules with automatic remediation

Managed rules such as restricted-ssh, vpc-sg-open-only-to-authorized-ports, vpc-flow-logs-enabled, vpc-default-security-group-closed and vpc-vpn-2-tunnels-up flag problems; a remediation configuration runs a Systems Manager Automation runbook, such as AWS-DisablePublicAccessForSecurityGroup, AWSConfigRemediation-EnableVPCFlowLogsToCloudWatch, AWSConfigRemediation-RemoveVPCDefaultSecurityGroupRules or AWS-ReleaseElasticIP.

Close SSH from anywhere automatically whenever restricted-ssh finds it (AWS CLI) 
aws configservice put-remediation-configurations --remediation-configurations '[{
  "ConfigRuleName": "restricted-ssh",
  "TargetType": "SSM_DOCUMENT",
  "TargetId": "AWS-DisablePublicAccessForSecurityGroup",
  "Parameters": {
    "AutomationAssumeRole": {"StaticValue": {"Values": ["arn:aws:iam::111111111111:role/config-remediation"]}},
    "GroupId": {"ResourceValue": {"Value": "RESOURCE_ID"}}
  },
  "Automatic": true,
  "MaximumAutomaticAttempts": 3,
  "RetryAttemptSeconds": 60
}]'

Other patterns

  • VPN maintenance: with tunnel endpoint lifecycle control, the Health event goes through EventBridge to SNS, and a Systems Manager maintenance window runs a Lambda function that calls replace-vpn-tunnel --apply-pending-maintenance one tunnel at a time, inside the change window.
  • Threat blocking: a GuardDuty finding (through Security Hub and EventBridge) starts a Step Functions workflow that adds the attacker's IP to a Network Firewall rule group or a network ACL, and removes it later.
  • Troubleshooting runbooks: AWSSupport-ConnectivityTroubleshooter, AWSSupport-TroubleshootVPN and AWSSupport-EnableVPCFlowLogs can run from an alarm.

Hybrid automation

Skill 2.4.3Integrating hybrid network automation options with AWS native IaC

  • AWS side in CloudFormation: customer gateways, VPNs (with the pre-shared key from Secrets Manager), Direct Connect gateways, associations, VIFs and LAGs (all resource types since 2026), Transit Gateway Connect peers, Resolver rules. The cross connect and the on-premises router configuration stay outside.
  • Configuration hand-off: stack outputs (tunnel addresses, VIF peer IPs, BGP ASNs) feed the on-premises automation (Ansible, vendor APIs, an SD-WAN controller); a custom resource or pipeline step can call the vendor's API, or download the VPN sample configuration with get-vpn-connection-device-sample-configuration or the Direct Connect router configuration.
  • Modeling on-premises in AWS: Network Manager sites, devices, links and customer gateway associations (all CloudFormation resources) give one topology view and events for hybrid paths.
  • Third-party extensions: the CloudFormation registry includes vendor resource types, and Terraform's AWS provider covers the same APIs when the organization standardizes on it.
  • Landing zones: AWS Control Tower with Account Factory (or Account Factory for Terraform) and Customizations for Control Tower, or Landing Zone Accelerator on AWS (built on the CDK, with configuration files for VPCs, Transit Gateway and Network Firewall), apply the network baseline to every new account.

Reducing risk and cost

Skill 2.4.4Eliminating risk and achieving efficiency in a cloud networking environment while maintaining the lowest possible cost

Reducing risk

  • Review change sets for "Replacement: True" on VPCs, subnets and gateways before running them.
  • Block risky templates with Hooks or Guard rules (also used by Control Tower proactive controls).
  • Protect critical resources with stack policies, termination protection, and DeletionPolicy: Retain on Elastic IPs, Direct Connect gateways and hosted zones.
  • Roll out across accounts slowly with StackSet concurrency and failure tolerance, and use rollback triggers on CloudWatch alarms. CloudFormation express mode (2026) turns rollback off and is for development only.
  • Detect and correct console edits with drift detection and the Config rule cloudformation-stack-drift-detection-check.

Keeping cost down

  • Choose NAT gateway count per environment (one per AZ in production, one in development), or centralize egress where traffic is low.
  • Share interface endpoints and inspection centrally; use free gateway endpoints for S3 and DynamoDB in every VPC.
  • Prefer IPv6 or private addressing over public IPv4, which costs $0.005 per address per hour, in use or idle.
  • Keep same-AZ traffic in the same AZ, and tag everything for cost allocation, including Transit Gateway attachments.

Automating optimization

Skill 2.4.5Automating the process of optimizing cloud network resources with IaC

  • Trusted Advisor cost checks: Unassociated Elastic IP Addresses, Idle Load Balancers (Classic Load Balancers only), Idle NAT gateways and Inactive NAT Gateways (no traffic in 30 days), Inactive VPC interface endpoints, Inactive Gateway Load Balancer endpoints and Inactive AWS Network Firewall. Results can drive EventBridge rules and clean-up functions.
  • Config eip-attached with AWS-ReleaseElasticIP, and vpc-network-acl-unused-check or unused security group runbooks, remove waste automatically.
  • IPAM public IP insights show every public IPv4 address and which ones are unassociated.
  • Schedules: delete development network stacks (NAT gateways, endpoints, firewalls) at night with EventBridge Scheduler and recreate them from the same templates in the morning; change natGateways or endpoint lists through parameters, not by hand.
  • Right-size through code: when flow logs or Cost Explorer show a VPC pair exchanging heavy traffic over the Transit Gateway, add a peering in the template; when an endpoint is unused, remove it from the shared list.

"Apply a standard network to every new account automatically" points to service-managed StackSets with automatic deployment (or a landing zone tool built on them). "React to a Transit Gateway VPN BGP session going down" points to Network Manager events in EventBridge in us-west-2. "Keep firewall rules current with AWS IP ranges" points to the AmazonIpSpaceChanged topic or an AWS-managed prefix list.

Key takeaways

  • CloudFormation for networks: typed and SSM parameters, pseudo parameters, Fn::GetAZs (default-subnet AZs, order can change), Fn::Cidr (host bits), exports or Fn::GetStackOutput, Secrets Manager for VPN keys, DependsOn the gateway attachment, Retain policies, change sets, drift, refactoring, hooks and Guard.
  • Changing a VPC or subnet CIDR replaces it; add CIDRs with AWS::EC2::VPCCidrBlock.
  • CDK ec2.Vpc: one NAT gateway per AZ by default, IPAM allocation, PUBLIC / PRIVATE_WITH_EGRESS / PRIVATE_ISOLATED; fromLookup needs an environment and committed context; VpcV2 is still alpha.
  • Hardcoding breaks reuse: AZ names (use AZ IDs), CIDRs (use IPAM or parameters), account IDs and Regions (pseudo parameters, AWS::Partition), resource IDs, secrets and custom names.
  • StackSets with service-managed permissions and automatic deployment roll a baseline to every account in an OU (never the management account).
  • Events: Network Manager events only in us-west-2; Health events for VPN maintenance; Config rules with SSM runbook remediation; the AmazonIpSpaceChanged topic in us-east-1 for AWS IP range updates.
  • Hybrid: the AWS side in CloudFormation, outputs and sample configurations handed to on-premises automation, Network Manager for topology, landing zone tools for new accounts.
  • Risk and cost: review replacements, guard templates, roll out gradually, keep rollback on; automate clean-up of idle NAT gateways, endpoints and unattached Elastic IPs.
