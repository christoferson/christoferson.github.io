Overview

Task 3.3

Optimize AWS networks for performance, reliability, and cost-effectiveness.

Optimization questions give a working design and one pressure: too slow, too expensive, too fragile or out of addresses. The right answer changes the least while fixing that pressure, for example a peering for one heavy VPC pair rather than a new architecture, or prefix delegation rather than a new VPC.

The travel company is tuning its network: the bookings and pricing VPCs exchange terabytes a day, the fare engine on GPU instances needs low-latency interconnect, a market data feed must reach many instances, EKS clusters are running out of IP addresses, and partner traffic from around the world needs a faster entry point.

Peering, proxy or Transit Gateway

Knowledge 3.3.1Situations in which a VPC peer or a transit gateway are appropriate

  • VPC peering: few VPCs, highest throughput and lowest latency (no extra hop, 9001 MTU within a Region), no hourly or processing fee and free within an AZ. Not transitive, no shared gateways, no overlap.
  • Transit Gateway: many VPCs, transitive routing, shared hybrid links, central inspection and egress, segmentation. Adds $0.02 per GB, a hop, and 8500 MTU.
  • Both together: keep the Transit Gateway as the hub and add a peering for a heavy pair; the peering's more specific routes win and avoid processing charges.

Skill 3.3.3Choosing between VPC peering, proxy patterns, or a transit gateway connection based on analysis of the network requirements provided

A proxy pattern puts a service between networks instead of routing them together: an NLB with PrivateLink, a reverse proxy or a forward proxy fleet (or the AWS Network Firewall proxy, still in preview). Choose it when:

  • CIDRs overlap, so routing is impossible without NAT;
  • consumers need one service, not the whole network, or the provider must never reach back;
  • traffic must be inspected or authenticated at layer 7 on the way, for example outbound web traffic through a filtering proxy.

The cost is instances or endpoint charges, and an extra component to scale and keep available. When none of those needs apply, choose peering for a few VPCs and a Transit Gateway for many.

Skill 3.3.4Implementing a solution on an appropriate network connectivity service (for example, VPC peering, Transit Gateway, VPN connection) to meet network requirements

  • Bookings to pricing (terabytes a day, same Region): a VPC peering beside the Transit Gateway, with /16 routes in both VPCs to the peering.
  • All other VPCs: Transit Gateway attachments with segmented route tables.
  • A new small office needing access within a day: a Site-to-Site VPN to the Transit Gateway, BGP, two tunnels, later a VPN Concentrator connection with other small sites.
  • A partner consuming one API with overlapping addresses: PrivateLink.

Implementation steps are on Task 2.2 and Task 1.6.

Reducing bandwidth and transfer cost

Knowledge 3.3.2Different methods to reduce bandwidth utilization (for example, unicast compared with multicast, CloudFront)

  • CloudFront: caches content at the edge so the origin serves each object once per cache; request collapsing and Origin Shield cut origin load further. Data transfer from AWS origins to CloudFront is free, so delivering through CloudFront usually costs less than serving the internet directly. Flat-rate plans (Free, Pro, Business, Premium) are now an alternative to pay-as-you-go.
  • Multicast instead of unicast: a sender transmits each packet once and the network copies it to every receiver, instead of the sender sending one copy per receiver. It saves sender bandwidth and CPU, but Transit Gateway still charges processing per GB for each receiver.
  • Gateway endpoints keep S3 and DynamoDB traffic off NAT gateways; compression and caching in the application reduce bytes; keep traffic in the same AZ and Region where resilience allows.

Knowledge 3.3.3Cost-effective connectivity options for data transfer between a VPC and on-premises environments

  • Direct Connect: data transfer out is charged at Direct Connect rates (for example $0.02 per GB from a US Region to a US location), well below internet rates, and data in is free, plus port hours ($0.30 per hour for 1 Gbps, $2.25 for 10 Gbps). Steady, large volumes favor it; flat-rate pricing for 10 and 100 Gbps (2026) makes costs predictable.
  • Site-to-Site VPN: $0.05 per connection-hour plus internet data transfer out; cheapest for low or bursty volumes and as a backup.
  • Hosted connections (50 Mbps upward) when a full port is too much.
  • Reduce volume first: send only deltas, compress, and use S3 interface endpoints over Direct Connect rather than the internet for backups.
  • Transit Gateway adds $0.02 per GB on top; a private VIF straight to a VGW avoids it for a single VPC.

Multicast

Skill 3.3.5Implementing a multicast capability within a VPC and on-premises environments

Transit Gateway multicast

  • Multicast must be enabled when the Transit Gateway is created; it cannot be added later.
  • A multicast domain groups subnets (a subnet can be in only one domain). Groups are identified by group IP; members and sources are network interfaces.
  • Membership is static (register members and sources by API) or dynamic with IGMPv2 (hosts join and leave; the Transit Gateway queries every 2 minutes and removes a member after 3 missed queries). Only static membership supports IPv6.
  • Nitro instances are required to send; non-Nitro receivers need the source/destination check disabled.
  • Limits: 1 Gbps per flow, 20 Gbps per AZ, 100 members per group, 20 domains per Transit Gateway; fragmented packets are dropped. AWS warns it may not suit high-frequency trading.
  • Not supported over Direct Connect, VPN, Transit Gateway peering or Connect attachments.
Market data feed: a multicast-enabled Transit Gateway, an IGMP domain, the receivers' subnets, and one static member (AWS CLI) 
aws ec2 create-transit-gateway --description "market data" \
  --options MulticastSupport=enable

aws ec2 create-transit-gateway-multicast-domain \
  --transit-gateway-id tgw-0marketdata1 \
  --options Igmpv2Support=enable,StaticSourcesSupport=disable

aws ec2 associate-transit-gateway-multicast-domain \
  --transit-gateway-multicast-domain-id tgw-mcast-domain-0feed1 \
  --transit-gateway-attachment-id tgw-attach-0pricing1 \
  --subnet-ids subnet-pricing-az1 subnet-pricing-az2

# A receiver that cannot send IGMP joins
aws ec2 register-transit-gateway-multicast-group-members \
  --transit-gateway-multicast-domain-id tgw-mcast-domain-0feed1 \
  --group-ip-address 239.10.10.1 \
  --network-interface-ids eni-0legacyreceiver

Security groups and network ACLs on receivers must allow IGMP (protocol 2) inbound from 0.0.0.0/32 (the Transit Gateway's queries), IGMP outbound to 224.0.0.2/32 and the group address, and the UDP feed inbound from the sender's IP address (a security group reference does not work for multicast).

On-premises multicast

Because Direct Connect and VPN do not carry multicast, run a multicast-capable virtual router on EC2 in each AZ, build GRE tunnels to the on-premises routers over Direct Connect or VPN, run PIM on the tunnels, disable the source/destination check, and register the router's interface as a Transit Gateway multicast source (traffic from on premises) or member (traffic to on premises) with static joins.

Network interfaces and throughput

Knowledge 3.3.4Different types of network interfaces on AWS

Elastic network interface (ENI)

The virtual network card: private and public addresses, security groups, MAC address and source/destination check, in one subnet and AZ. Secondary ENIs can move between instances in the same AZ, taking their addresses with them (a failover pattern). The number of ENIs and addresses depends on instance type. Services create requester-managed ENIs (load balancers, endpoints, Lambda) that you cannot manage.

Elastic Network Adapter (ENA)

Enhanced networking (SR-IOV) on all Nitro instances, at no extra charge, up to 600 Gbps on the largest network-optimized types; queues per ENI can now be configured. The Intel 82599 VF (up to 10 Gbps) is the legacy option on old types. ENA Express adds AWS's SRD transport to ordinary TCP and UDP for up to 25 Gbps per flow and lower tail latency, with no application changes.

Elastic Fabric Adapter (EFA)

An ENA plus an OS-bypass device for HPC and machine learning through libfabric (MPI, NCCL), using SRD. Interface types are interface, efa (EFA with ENA) and efa-only (no IP addresses, never the primary interface). EFA traffic cannot cross AZs or VPCs and is not routable; its security group must allow all traffic to and from itself. One EFA per network card; large GPU instances have many cards (for example 32 on p5.48xlarge, 3,200 Gbps of EFA bandwidth).

Address and density features

Prefix delegation assigns /28 IPv4 (or /80 IPv6) prefixes to an ENI, each counting as one address slot, for container density. ECS ENI trunking (awsvpcTrunking) multiplies tasks per instance. Lambda shares Hyperplane ENIs per subnet and security group combination.

Skill 3.3.1Optimizing for network throughput

  • Pick instance types by network bandwidth, not only CPU (the "n" types, and multiple network cards for more than 100 Gbps).
  • Use several flows: one flow is capped at 5 Gbps (10 Gbps in a cluster placement group, 25 Gbps with ENA Express).
  • Use a cluster placement group for lowest latency and highest per-flow throughput between instances; jumbo frames inside it.
  • Watch the ENA allowance counters; when bandwidth or packets-per-second allowances are exceeded, scale up or out.
  • Avoid hairpins: same-AZ endpoints and load balancer AZ affinity, gateway endpoints instead of NAT, peering instead of Transit Gateway for heavy pairs.
  • For hybrid paths, ECMP across VPN tunnels or Large Bandwidth Tunnels, or Direct Connect with LAG.

Skill 3.3.2Selecting the right network interface for the best performance (for example, elastic network interface, Elastic Network Adapter [ENA], Elastic Fabric Adapter [EFA])

  • General web and database traffic: ENA (default on Nitro).
  • A single large TCP or UDP flow between instances in a Region: ENA Express.
  • Tightly coupled HPC or distributed training (MPI, NCCL): EFA, in a cluster placement group, one per network card.
  • Separate management and data networks, or a movable address for failover: additional ENIs.
Launch a training node with an EFA on card 0 and an EFA-only interface on card 1, both in the self-referencing security group (AWS CLI) 
aws ec2 run-instances --instance-type p5.48xlarge --count 1 \
  --image-id ami-0dlbase1234567890 \
  --placement GroupName=fare-training-cluster \
  --network-interfaces \
    "NetworkCardIndex=0,DeviceIndex=0,InterfaceType=efa,SubnetId=subnet-ml-az1,Groups=sg-efa-self" \
    "NetworkCardIndex=1,DeviceIndex=1,InterfaceType=efa-only,SubnetId=subnet-ml-az1,Groups=sg-efa-self"

# The EFA security group must allow all traffic to and from itself
aws ec2 authorize-security-group-ingress --group-id sg-efa-self \
  --ip-permissions IpProtocol=-1,UserIdGroupPairs=[{GroupId=sg-efa-self}]
aws ec2 authorize-security-group-egress --group-id sg-efa-self \
  --ip-permissions IpProtocol=-1,UserIdGroupPairs=[{GroupId=sg-efa-self}]

Frame size and jumbo frames

Knowledge 3.3.9Frame size optimization for bandwidth across different connection types

Larger frames carry more payload per packet, cutting per-packet overhead and CPU, which matters most at high throughput. The limits differ by path: 9001 within a VPC and same-Region peering; 8500 across Transit Gateway, inter-Region peering, NAT gateways and endpoints; 1500 to the internet; about 1400 through VPN tunnels (full table on Task 3.2). A jumbo frame on a 1500 path is dropped or fragmented, and where Path MTU Discovery fails, connections hang.

Skill 3.3.9Configuring jumbo frame support across connection types

  • Instances: current generation instances default to 9001; keep it for traffic within the VPC and cluster placement groups. For mixed paths, set MTU per route, or use a second interface with a different MTU for internal traffic.
  • Direct Connect: set MTU 9001 on private VIFs and 8500 on transit VIFs (the connection must be jumbo-frame capable; the change interrupts it briefly), and match it on every on-premises device. Jumbo frames apply only to propagated Direct Connect routes (and static Transit Gateway routes); if a VPN or another VIF with a different MTU advertises the same prefix, 1500 is used.
  • Transit Gateway: 8500, so instances behind it should not send 9001-byte packets to other VPCs; MSS clamping protects TCP.
  • VPN: no jumbo frames.
Raise the US data center's private VIF to jumbo frames during a maintenance window (AWS CLI) 
aws directconnect describe-connections --connection-id dxcon-us1a \
  --query "connections[0].jumboFrameCapable"

aws directconnect update-virtual-interface-attributes \
  --virtual-interface-id dxvif-us1priv --mtu 9001

Route 53 for availability

Knowledge 3.3.5High-availability features in Route 53 (for example, DNS load balancing using health checks with latency and weighted record sets)

Health checks on records let Route 53 stop answering with unhealthy endpoints: latency records send users to the closest healthy Region, and weighted records split traffic and drop unhealthy members. Combined trees (latency at the top, weighted per Region) fail over between Regions only when a whole Region is unhealthy. Use TTLs of 60 seconds or less (Task 2.3).

Knowledge 3.3.6Availability of options from Route 53 that provide reliability

  • A data plane in over 200 locations with a 100% availability SLA; rely on it (health checks, routing controls) rather than control plane edits during an outage.
  • Failover records with health checks; calculated health checks combining many checks; CloudWatch alarm health checks for private endpoints.
  • Application Recovery Controller routing controls (switched through five Regional cluster endpoints) and Region switch plans for controlled failover.
  • Accelerated recovery (November 2025) keeps public zone changes possible within about an hour if us-east-1 is impaired.
  • Resolver endpoints with IPs in several AZs for hybrid DNS.

Skill 3.3.6Creating Route 53 public hosted zones and private hosted zones and records to optimize application availability (for example, private zonal DNS entry to route traffic to multiple Availability Zones)

Load balancers and interface endpoints have zonal DNS names as well as Regional ones: us-east-1a.booking-nlb-0123456789abcdef.elb.us-east-1.amazonaws.com and vpce-0abc-us-east-1a.service.us-east-1.vpce.amazonaws.com. Records pointing at them keep clients in their own AZ (lower latency, no cross-AZ charges), with health checks or weights to spread or fail over between AZs.

Private records for the booking API: one weighted record per AZ pointing at the NLB's zonal names (change batch JSON) 
{"Changes": [
  {"Action": "UPSERT", "ResourceRecordSet": {
    "Name": "booking-api.aws.example.com", "Type": "CNAME", "TTL": 30,
    "SetIdentifier": "az1", "Weight": 50,
    "ResourceRecords": [{"Value": "us-east-1a.booking-nlb-0123456789abcdef.elb.us-east-1.amazonaws.com"}]}},
  {"Action": "UPSERT", "ResourceRecordSet": {
    "Name": "booking-api.aws.example.com", "Type": "CNAME", "TTL": 30,
    "SetIdentifier": "az2", "Weight": 50,
    "ResourceRecords": [{"Value": "us-east-1b.booking-nlb-0123456789abcdef.elb.us-east-1.amazonaws.com"}]}}
]}

Simpler for NLBs: set dns_record.client_routing_policy so the NLB's own DNS answers with the client's AZ first: availability_zone_affinity (100%), partial_availability_zone_affinity (85%) or any_availability_zone (the default). The NLB also removes a zone's address from DNS when that zone fails its health checks.

Keep 85% of resolver answers in the client's own AZ (AWS CLI) 
aws elbv2 modify-load-balancer-attributes \
  --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:444444444444:loadbalancer/net/booking-nlb/0123456789abcdef \
  --attributes Key=dns_record.client_routing_policy,Value=partial_availability_zone_affinity

Load balancing patterns

Knowledge 3.3.7Load balancing and traffic distribution patterns

  • Across Regions: Route 53 latency, geolocation or weighted records, or Global Accelerator endpoint groups with traffic dials.
  • Across AZs: load balancers in every AZ; cross-zone load balancing on for even spread (on by default for ALB, off for NLB, where it adds cross-AZ data charges), or AZ affinity to keep traffic local.
  • Across targets: ALB round robin, least outstanding requests or weighted random; NLB flow hash; weighted target groups for blue/green and canary releases.
  • Layer 3: Gateway Load Balancer for appliance fleets.
  • DNS only: multivalue answers for small fleets without a load balancer (up to 8 healthy answers).
  • Pre-warm with load balancer capacity reservations for known events; slow start for new ALB targets.

Feature details are on Task 1.3.

Subnets and IP addresses

Knowledge 3.3.8VPC subnet optimization

  • Size subnets for peak scale plus growth: every instance, container ENI, load balancer node, endpoint and Lambda ENI uses addresses, and 5 per subnet are reserved.
  • An ALB needs at least a /27 with 8 free addresses per AZ subnet to scale; without them it can return errors or fail. NLBs use one address per AZ (plus optional secondary addresses for port allocation).
  • Separate tiers (public, application, data, endpoints, Transit Gateway attachments) so route tables and ACLs stay simple; give Transit Gateway attachments small dedicated subnets.
  • Spread subnets across at least three AZs, and match AZ IDs across accounts.
  • Monitor with IPAM's SubnetIPUsage and VpcIPUsage metrics and each subnet's available address count.

Skill 3.3.7Updating and optimizing subnets for auto scaling configurations to support increased application load

  • Give the Auto Scaling group subnets in more AZs; it launches in the AZ with the fewest instances, and in that AZ chooses the subnet with the most free addresses.
  • Add a larger subnet (from a secondary CIDR if needed) to the group's subnet list rather than resizing; subnets cannot be resized.
  • AZ rebalancing may exceed maximum capacity by 10% or one instance while it moves instances; choose a capacity distribution strategy (balanced-best-effort, balanced-only or reservations-then-balanced).
  • Make sure load balancer subnets keep their free addresses as the group grows.
Spread the booking fleet over a new, larger subnet in each AZ (AWS CLI) 
aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name booking-web \
  --vpc-zone-identifier "subnet-app-az1,subnet-app-az2,subnet-app-az3,subnet-app2-az1,subnet-app2-az2,subnet-app2-az3"

Skill 3.3.8Updating and optimizing subnets to prevent the depletion of available IP addresses within a VPC (for example, secondary CIDR)

  1. Add a secondary CIDRAssociate another range with the VPC (up to 5 by default, 50 maximum). 100.64.0.0/10 can be added to any RFC 1918 VPC and suits non-routable workload subnets.
  2. Create new subnetsIn the new range, in every AZ, and add them to Auto Scaling groups, node groups and load balancers.
  3. ContainersFor EKS, use custom networking (pods in the 100.64 subnets through ENIConfig per AZ), prefix delegation (ENABLE_PREFIX_DELEGATION=true, /28 per slot; reserve contiguous space with subnet CIDR reservations), Enhanced Subnet Discovery (tag new subnets kubernetes.io/role/cni), or IPv6 pods.
  4. ReachabilityIf the new range is not routable on premises, add a private NAT gateway in a routable subnet (Task 1.6).
  5. Prevent recurrenceAllocate from IPAM with alarms on subnet usage.
Add 100.64.0.0/16 to the EKS VPC, create pod subnets, and turn on prefix delegation (AWS CLI and kubectl) 
aws ec2 associate-vpc-cidr-block --vpc-id vpc-bookings-eks --cidr-block 100.64.0.0/16

aws ec2 create-subnet --vpc-id vpc-bookings-eks --availability-zone-id use1-az1 \
  --cidr-block 100.64.0.0/19 \
  --tag-specifications 'ResourceType=subnet,Tags=[{Key=kubernetes.io/role/cni,Value=1}]'

kubectl set env daemonset aws-node -n kube-system ENABLE_PREFIX_DELEGATION=true

Prefix delegation needs contiguous free /28 blocks; a fragmented subnet fails with InsufficientCidrBlocks even when individual addresses remain. Create a subnet CIDR reservation of type prefix, or use a fresh subnet. Custom networking also reduces maximum pods per node, because the primary ENI is no longer used for pods.

Global Accelerator

Skill 3.3.10Optimizing network connectivity by using Global Accelerator to improve network performance and application availability

  • Performance: traffic enters AWS at the nearest edge location, where TCP is terminated, and crosses the AWS backbone to the endpoint, avoiding congested internet paths. The speed comparison tool measures the gain.
  • Availability: two static anycast IP addresses from independent network zones; unhealthy endpoints leave service in under a minute, without DNS caching delays; endpoint groups per Region with traffic dials, and endpoint weights (0–255).
  • Client affinity on source IP for stateful applications; client IP preservation to ALBs and suitable NLBs.
  • Fixed idle timeouts (TCP 340 seconds, UDP 30 seconds); TCP fragments are dropped at the edge; endpoint security groups must allow ICMP for Path MTU Discovery.
  • Cost: $0.025 per hour plus a data transfer premium on the dominant direction.
Shift 20% of partner traffic for us-east-1 to Frankfurt during a migration by lowering the us-east-1 traffic dial (AWS CLI, us-west-2) 
aws globalaccelerator update-endpoint-group --region us-west-2 \
  --endpoint-group-arn arn:aws:globalaccelerator::111111111111:accelerator/1234abcd-abcd-1234-abcd-1234abcdefgh/listener/0123vxyz/endpoint-group/098765zyxwvu \
  --traffic-dial-percentage 80

The dial lowers the share for that group; Global Accelerator sends the rest to the next closest healthy endpoint group. Use CloudFront instead for cacheable HTTP content, and Global Accelerator for TCP or UDP, static IP allow-listing, and fast deterministic failover.

Key takeaways

  • Peering for few VPCs and heavy pairs (fastest, no processing fee); Transit Gateway for scale, transit and inspection; proxy or PrivateLink patterns for overlapping CIDRs, single services and layer 7 control.
  • Cut bandwidth with CloudFront (free AWS origin fetch), multicast (still charged per receiver), gateway endpoints and compression; Direct Connect data out is far cheaper than internet for steady volumes, VPN for small or backup.
  • Transit Gateway multicast: enabled only at creation, domains of subnets, IGMPv2 or static members, Nitro senders, 1 Gbps per flow, no multicast over Direct Connect, VPN, peering or Connect (use GRE to EC2 routers).
  • Interfaces: ENI (movable, per subnet), ENA (up to 600 Gbps), ENA Express (25 Gbps per flow), EFA and efa-only (OS-bypass, not routable, self-referencing security group, one per network card).
  • Frames: 9001 in VPC, 8500 Transit Gateway and inter-Region peering, 1500 internet; Direct Connect 9001 private and 8500 transit VIFs with matching devices; no jumbo on VPN.
  • Route 53: health-checked latency and weighted trees, calculated and alarm checks, ARC routing controls; zonal DNS names and NLB AZ affinity keep traffic in-AZ.
  • Subnets: ALB /27 with 8 free addresses; Auto Scaling picks the subnet with most free addresses; fix depletion with secondary CIDRs, new subnets, prefix delegation, custom networking or IPv6; monitor with IPAM.
  • Global Accelerator: edge TCP termination, backbone transit, static anycast IPs, sub-minute failover, traffic dials and weights.
