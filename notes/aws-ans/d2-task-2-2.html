Overview

Task 2.2

Implement routing and connectivity across multiple AWS accounts, Regions, and VPCs to support different connectivity patterns.

Task 1.6 chose between peering, Transit Gateway, Cloud WAN, PrivateLink and VPC sharing; this task builds them. Expect questions on exact route table entries for centralized egress, where appliance mode goes, how to share interface endpoints, which authentication a Client VPN supports, and why a security group change did not cut a connection.

The travel company's network account now runs the shared Transit Gateway in each Region, an egress VPC with NAT gateways, AWS Network Firewall for inspection, shared interface endpoints, and Client VPN for staff, while application accounts only attach their VPCs.

Inter-VPC and multi-account options

Knowledge 2.2.1Inter-VPC and multi-account connectivity (for example, VPC peering, Transit Gateway, VPN, third-party vendors, SD-WAN, multi-protocol label switching [MPLS])

  • VPC peering, Transit Gateway and Cloud WAN: the rules and limits are on Task 1.6.
  • VPN between VPCs: Site-to-Site VPN from an appliance in one VPC to a VGW or Transit Gateway in another, used for encrypted overlays or the older transit VPC pattern (below).
  • Third-party vendors and SD-WAN: router, firewall and SD-WAN appliances from AWS Marketplace, joined with Transit Gateway Connect or Gateway Load Balancer (below).

MPLS and carrier WANs

AWS has no MPLS service. A carrier or Direct Connect Partner extends the existing MPLS WAN to a Direct Connect location and hands it over as a dedicated connection or a hosted connection (50 Mbps to 25 Gbps; no LAG or MACsec; you accept it and billing starts then). AWS then appears to the WAN as one more site, with BGP per VIF. Where the carrier manages the service, its router usually runs BGP with AWS and carries the routes into your VRF. SiteLink can link Direct Connect locations over the AWS backbone, replacing some carrier links between sites.

Other clouds: AWS Interconnect – multicloud

GA in April 2026 (Google Cloud first; Oracle Cloud GA July 2026; Microsoft Azure in preview from August 2026). A managed private link to another cloud, ordered with an activation key shared between the providers, with no routers or cross connects to run. It always attaches to a Direct Connect gateway, is built over at least two facilities with four connections, and is encrypted with MACsec. VGWs and Transit Gateways reach only interconnects local to their Region; Cloud WAN reaches them globally. A 500 Mbps local tier is free on the AWS side.

Hub and spoke

Skill 2.2.3Configuring a hub-and-spoke network architecture (for example, Transit Gateway, transit VPC)

Transit VPC (legacy)

A hub VPC runs EC2 router appliances that build BGP over IPsec VPNs to each spoke VPC's VGW, giving transitive routing before Transit Gateway existed. Its drawbacks: appliance cost, 1.25 Gbps per VPN tunnel, VPN encryption latency, and you run the appliances' high availability. The AWS Solutions implementation is no longer published. It still fits when every path must pass vendor routing or inspection features, for operational parity with on-premises kit, or for odd cases such as linking GovCloud and commercial Regions. Otherwise use Transit Gateway, with appliances in an inspection VPC.

Centralized egress

Instead of NAT gateways in every VPC and AZ, spokes send internet traffic over the Transit Gateway to an egress VPC in the network account. The routing:

  1. Spoke route table (RT1)Spoke attachments associate with it. Static 0.0.0.0/0 to the egress VPC attachment, and a blackhole for 10.0.0.0/8 so spokes cannot reach each other through it (remove or narrow it if they should).
  2. Egress route table (RT2)The egress VPC attachment associates with it; spoke attachments propagate into it, so return traffic finds each spoke.
  3. Egress VPC, Transit Gateway attachment subnets0.0.0.0/0 to the NAT gateway in the same AZ.
  4. Egress VPC, NAT gateway subnets0.0.0.0/0 to the internet gateway, plus a return route for the spoke ranges (10.0.0.0/8) to the Transit Gateway. Without it, replies never reach the spokes.
  5. Spoke VPCs0.0.0.0/0 in their subnet route tables to the Transit Gateway.
Centralized egress in us-east-1: Transit Gateway routes and the egress VPC's return route (AWS CLI) 
# RT1, used by all spokes: internet via the egress VPC, no spoke-to-spoke
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-spokes \
  --destination-cidr-block 0.0.0.0/0 \
  --transit-gateway-attachment-id tgw-attach-egress
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-spokes \
  --destination-cidr-block 10.0.0.0/8 --blackhole

# Egress VPC: NAT gateway subnets send replies for spokes back to the TGW
aws ec2 create-route --route-table-id rtb-egress-nat-az1 \
  --destination-cidr-block 10.0.0.0/8 --transit-gateway-id tgw-use1

Centralizing NAT adds Transit Gateway processing ($0.02 per GB) to every byte. It saves hourly NAT charges for many small VPCs, but a VPC sending large volumes to the internet can be cheaper with its own NAT gateway.

Centralized inspection

Route spoke-to-spoke, egress or hybrid traffic through an inspection VPC (firewall appliances, Gateway Load Balancer, or AWS Network Firewall endpoints) and turn on appliance mode on the inspection VPC's attachment, not on the spokes, so both directions of a flow use the same AZ. Two caveats: stickiness holds only for traffic that enters the inspection VPC from the Transit Gateway, and enabling appliance mode on an existing attachment can move existing flows. Simpler now: attach AWS Network Firewall directly to the Transit Gateway (below), which turns appliance mode on automatically.

Turn on appliance mode for the inspection VPC attachment (AWS CLI) 
aws ec2 modify-transit-gateway-vpc-attachment \
  --transit-gateway-attachment-id tgw-attach-inspection \
  --options ApplianceModeSupport=enable

Shared services

A shared services VPC (directory, DNS endpoints, shared interface endpoints, tooling) propagates into every spoke route table and receives every spoke's routes, while spokes stay isolated from each other.

Third-party vendor solutions

Skill 2.2.2Configuring hybrid connectivity with existing third-party vendor solutions

Router and firewall appliances on EC2

Launch the vendor image from AWS Marketplace, give it interfaces in the right subnets, and disable the source/destination check on every interface that forwards traffic; otherwise EC2 drops packets not addressed to the instance. Point route tables at the appliance's interface. Plan high availability yourself (two appliances in two AZs, with routing failover).

Let a Marketplace router forward traffic for other addresses (AWS CLI) 
aws ec2 modify-instance-attribute \
  --instance-id i-0vendorrouter1234 --no-source-dest-check

# For an extra interface on the same appliance
aws ec2 modify-network-interface-attribute \
  --network-interface-id eni-0vendorinside567 --no-source-dest-check

Firewalls behind Gateway Load Balancer

  1. In the security VPC, put the vendor appliances in a GENEVE target group (port 6081) behind a Gateway Load Balancer; the appliances must support GENEVE.
  2. Create an endpoint service from the Gateway Load Balancer, with allowed principals.
  3. In each consumer VPC (or the inspection VPC), create Gateway Load Balancer endpoints in their own subnets, one per AZ.
  4. Route through them, for example: internet gateway route table (edge association) sends the application subnet range to the endpoint; application subnets send 0.0.0.0/0 to the endpoint; endpoint subnets send 0.0.0.0/0 to the internet gateway.

Flow stickiness is 5-tuple by default (3- and 2-tuple are options, but not with Transit Gateway appliance mode). Target failover can rebalance flows on deregistration or failure. Prefix lists cannot be used as destinations for routes that target a Gateway Load Balancer endpoint.

SD-WAN and existing routers

Use Transit Gateway Connect (GRE with BGP, two sessions per peer, eBGP multihop TTL 2, no static routes or BFD) as set up on Task 2.1, or Site-to-Site VPN with BGP from the vendor device. The native Network Firewall attachment does not accept third-party firewalls; vendor firewalls still use an inspection VPC or Gateway Load Balancer.

Private application connectivity

Knowledge 2.2.2Private application connectivity (for example, PrivateLink)

Implementing an endpoint service (NLB, allowed principals, acceptance, private DNS name with TXT verification, supported Regions) and consumer endpoints is shown on Task 1.6. The other common build is shared interface endpoints for AWS services, so 300 VPCs do not each pay for their own:

  1. Endpoints in the shared services VPCCreate the interface endpoints (for example SSM, ECR, KMS) with private DNS disabled, because the AWS-managed private DNS only works inside the endpoint's own VPC.
  2. Private hosted zone per serviceNamed exactly like the service, for example ssm.us-east-1.amazonaws.com, with an alias A record at the zone apex pointing at the endpoint's Regional DNS name. Some services need a wildcard record, such as *.dkr.ecr.us-east-1.amazonaws.com.
  3. Associate the zonesWith every spoke VPC (cross-account authorization, or a Route 53 Profile). Spokes keep using the Amazon DNS server.
  4. RoutingSpokes reach the endpoint IPs over the Transit Gateway; on premises reaches them through the Resolver inbound endpoint.
Share the SSM endpoint: a private hosted zone named after the service, aliased to the central endpoint (AWS CLI) 
aws route53 create-hosted-zone \
  --name ssm.us-east-1.amazonaws.com \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services \
  --caller-reference ssm-use1-2026-11-15 \
  --hosted-zone-config PrivateZone=true

# Alias the apex to the endpoint's Regional DNS name
# (DnsName and its HostedZoneId come from describe-vpc-endpoints DnsEntries)
aws route53 change-resource-record-sets --hosted-zone-id Z0SSMSHARED123 \
  --change-batch '{"Changes":[{"Action":"CREATE","ResourceRecordSet":{
    "Name":"ssm.us-east-1.amazonaws.com","Type":"A",
    "AliasTarget":{"HostedZoneId":"Z7HUB4ULQPZ6S",
      "DNSName":"vpce-0ssm1234567890abc-a1b2c3d4.ssm.us-east-1.vpce.amazonaws.com",
      "EvaluateTargetHealth":true}}}]}'
  • Trade-offs: one endpoint policy for every spoke (20,480 characters maximum), a larger blast radius, and Transit Gateway processing on every byte.
  • Gateway endpoints for S3 and DynamoDB cannot be used through a Transit Gateway; each VPC needs its own (they are free).
  • An alternative is sharing endpoints as VPC Lattice resource configurations, which also works with overlapping CIDRs.

Expanding with Organizations and RAM

Knowledge 2.2.3Methods of expanding AWS networking connectivity (for example, Organizations, AWS RAM)

Enable RAM sharing with Organizations once from the management account; then share to the organization or OUs, and new accounts in those OUs get access automatically. Network resources commonly shared: Transit Gateways, subnets (VPC sharing), prefix lists, IPAM pools, security groups, Cloud WAN core networks, Resolver rules and query logging configurations, DNS Firewall rule groups, Route 53 Profiles, Network Firewall firewalls, policies and rule groups, and Gateway Load Balancer endpoint services (through allowed principals). What each sharing method allows is on Task 2.1. Use AZ IDs when matching subnets across accounts.

Organizations also carries guardrails: service control policies (for example, denying ec2:CreateInternetGateway outside the network account), declarative policies that enforce VPC Block Public Access, and Firewall Manager policies (below).

Name resolution across VPCs

Knowledge 2.2.4Host and service name resolution for applications and clients (for example, DNS)

  • Hosts: private hosted zones associated with every VPC that needs them; peering DNS resolution for public hostnames of peered instances.
  • Services: interface endpoint private DNS in their own VPC, or the shared zones above; PrivateLink endpoint services with verified private DNS names; Lattice service and resource domain names.
  • Clients outside AWS: Resolver inbound endpoints; remote users on Client VPN get DNS servers pushed by the endpoint.

The Route 53 documentation now calls Resolver "Route 53 VPC Resolver" (a separate, internet-reachable Route 53 Global Resolver also exists for branch and remote clients); exam material uses the older name.

Skill 2.2.4Configuring a DNS solution to make hybrid connectivity possible

Endpoints, forwarding rules and on-premises forwarders are configured on Task 2.1. In a multi-account network:

  • Share one set of forwarding rules (for corp.example.com and its reverse zones) and one Route 53 Profile (shared zones, endpoint zones, DNS Firewall rule groups) to all OUs, so new VPCs get hybrid DNS when they are associated.
  • Active Directory domains: forward the AD domain to the domain controllers through the outbound endpoint, so instances keep AmazonProvidedDNS in their DHCP options. For AWS Managed Microsoft AD trusts, add conditional forwarders both ways (on-premises DNS to the Managed AD DNS addresses, and Managed AD to on-premises DNS). The AD domain name must not clash with a private hosted zone name.
  • Remember the 1,024 packets per second per interface limit on the Amazon DNS server for chatty workloads.

Configuring single and multi-VPC networks

Skill 2.2.1Configuring network connectivity architectures by using AWS services in a single-VPC or multi-VPC design (for example, DHCP, routing, security groups)

DHCP

One option set per VPC, immutable, applied at lease renewal (Task 2.1). In a shared VPC the owner sets it for every participant.

Routing

  • Subnet route tables: local route, then the most specific route; static beats propagated for the same prefix.
  • Point spoke subnets at the Transit Gateway with a summary (10.0.0.0/8) or default route, rather than one route per VPC; route tables now hold 500 routes by default.
  • Use managed prefix lists for the data center and partner ranges in route tables and security groups, shared through RAM, so one edit updates every account (a reference counts as the list's maximum entries against quotas).
  • Gateway route tables (edge association with an internet gateway or VGW) send inbound traffic through a firewall or Gateway Load Balancer endpoint before it reaches the subnet.

Security groups across VPCs

  • Reference security groups across same-Region peering (account-id/sg-id), and in inbound rules across one Transit Gateway once security group referencing is enabled.
  • In shared VPCs, use shared security groups from the owner for common rules.
  • Otherwise use CIDRs or prefix lists, for example for traffic arriving from another Region or from on premises.

Authentication and authorization

Knowledge 2.2.6Authentication and authorization (for example, SAML, Active Directory)

AWS Client VPN

A managed OpenVPN-based remote access service (TLS on port 443 or 1194). An ACM server certificate is always required.

Authentication

  • Active Directory through AWS Directory Service: AWS Managed Microsoft AD, or AD Connector for on-premises AD. MFA if enabled on the directory.
  • SAML 2.0 federation (for example Okta, Microsoft Entra ID, IAM Identity Center): an IAM SAML provider, one identity provider per endpoint, the AWS-provided client, and a memberOf attribute for groups. The self-service portal (to download the client configuration) works with user-based methods, not with mutual authentication alone.
  • Mutual certificate authentication: client certificates from a CA you upload to ACM.
  • Mutual can be combined with Active Directory or with SAML (both must pass); AD and SAML cannot be combined with each other.

Authorization and networking

  • Authorization rules allow a destination CIDR to an AD or SAML group, or to all users. Access is denied by default, rules only allow, the longest prefix wins, and 0.0.0.0/0 is evaluated last: a specific rule for one group removes that range from everyone else's 0.0.0.0/0 access.
  • The client CIDR is /22 to /12, cannot overlap the VPC or routes, and cannot be changed later; size it at twice the expected concurrent users.
  • Subnet associations (one per AZ, all in one VPC) carry security groups and source-NAT client traffic. Split tunnel sends only the endpoint's routes through the VPN; any route change then resets every connection.
  • Endpoints can also attach directly to a Transit Gateway (2026): no source NAT (spokes need return routes for the client CIDR), no security groups, routes without a target subnet, same Region only.
  • Newer controls: a client connect handler (Lambda), connection logs to CloudWatch Logs, and device posture checks with a Cedar authorization policy (October 2026).
Staff Client VPN with SAML, split tunnel and logging, then let only the network team reach the data centers (AWS CLI) 
aws ec2 create-client-vpn-endpoint \
  --client-cidr-block 10.250.0.0/20 \
  --server-certificate-arn arn:aws:acm:us-east-1:111111111111:certificate/0f1e2d3c-4b5a-6978-8a9b-0c1d2e3f4a5b \
  --authentication-options 'Type=federated-authentication,FederatedAuthentication={SAMLProviderArn=arn:aws:iam::111111111111:saml-provider/travel-idp}' \
  --connection-log-options Enabled=true,CloudwatchLogGroup=/clientvpn/staff \
  --split-tunnel \
  --dns-servers 10.41.0.10 10.41.1.10

aws ec2 authorize-client-vpn-ingress \
  --client-vpn-endpoint-id cvpn-endpoint-0staff1234567890 \
  --target-network-cidr 10.100.0.0/16 \
  --access-group-id network-engineers

AWS Verified Access

VPN-less access: an identity-aware proxy that checks every request against Cedar policies using a user trust provider (IAM Identity Center or any OIDC provider; one per instance) and optional device trust providers (CrowdStrike, Jamf, JumpCloud). Endpoints are load balancers, network interfaces, network CIDRs or RDS databases. Non-HTTP (TCP) applications have been GA since February 2025 and need the Verified Access Connectivity Client.

Directory Service across accounts

  • AD Connector: a proxy to on-premises AD, holding no directory data. Two subnets in different AZs, VPN or Direct Connect to the data center, TCP and UDP 53, 88 and 389 open to the domain controllers, and a service account.
  • AWS Managed Microsoft AD: two domain controllers in two AZs. Share it with other accounts (through Organizations or a handshake) for seamless domain join; the consumer VPC needs peering, a Transit Gateway or VPN to the directory VPC, and the consumer account pays the sharing fee.
  • Trusts with on-premises AD need conditional forwarders both ways and the trust ports open in both directions, including an outbound rule on the security group AWS creates for the domain controllers.

Security between boundaries

Knowledge 2.2.7Security (for example, security groups, network ACLs, AWS Network Firewall)

Security groups and network ACLs

Security groups

  • Stateful, on network interfaces, allow rules only. The default group allows inbound from itself and all outbound.
  • 60 inbound and 60 outbound rules per group (counted separately for IPv4 and IPv6); 5 groups per interface, up to 16, with rules times groups no more than 1,000.
  • Connection tracking: removing a rule does not stop connections already tracked. A rule open to 0.0.0.0/0 in both directions makes the flow untracked, and those flows stop at once when the rule changes. Idle timeouts are configurable on Nitro instances (TCP established 60 to 432,000 seconds; newer Nitro v6 types default to 350 seconds).
  • Some traffic is always tracked, for example through NAT gateways, NLBs, interface endpoints and Network Firewall endpoints.

Network ACLs

  • Stateless, on subnets, allow and deny. Rules are evaluated from the lowest number; the first match wins, and a final * rule denies everything else. Put a deny at a lower number than the broad allow it carves out.
  • The default ACL allows all; a new custom ACL denies all until you add rules. 20 rules per direction by default, up to 40.
  • Return traffic needs ephemeral ports: 32768–61000 for Linux, 49152–65535 for modern Windows, 1024–65535 for NAT gateways, load balancers and Lambda. Opening 1024–65535 covers every client.
  • Adding a deny breaks existing connections immediately, which security groups do not do.
Block a known bad range on the egress VPC's public subnets ahead of the broad rules (AWS CLI) 
# Deny first (lower rule number), then allow return traffic on ephemeral ports
aws ec2 create-network-acl-entry --network-acl-id acl-egress-public \
  --ingress --rule-number 50 --protocol -1 \
  --cidr-block 198.51.100.0/24 --rule-action deny

aws ec2 create-network-acl-entry --network-acl-id acl-egress-public \
  --ingress --rule-number 100 --protocol tcp --port-range From=1024,To=65535 \
  --cidr-block 0.0.0.0/0 --rule-action allow

Neither security groups nor ACLs can filter traffic to the Amazon DNS server, DHCP, instance metadata or Time Sync; filter DNS with Route 53 Resolver DNS Firewall (which fails closed by default).

AWS Network Firewall

  • Firewall policy with stateless rule groups (priority order; aws:pass skips stateful inspection and logging, so forward to the stateful engine instead) and stateful rule groups (Suricata-compatible rules, 5-tuple rules or domain lists), plus optional TLS inspection.
  • Stateful rule order: STRICT_ORDER (recommended; rules in the order written, with a default action such as drop established) or default action order, where pass rules beat drop rules wherever they appear. Domain list rules need "drop established", not "drop all", because the domain is seen after the handshake. New policies since June 2026 default to "application drop established (server-directed only)".
  • Deployment: distributed (endpoints in each VPC), centralized (an inspection VPC with appliance mode, or the native Transit Gateway attachment, GA in all Regions since July 2025, which needs no inspection VPC, has appliance mode always on and is routed only in Transit Gateway route tables), or combined. Up to 50 extra VPC endpoints per firewall per AZ can serve other VPCs (May 2025).
  • Logs (flow, alert, TLS) go to S3, CloudWatch Logs or Firehose. Pricing: about $0.395 per endpoint-hour and $0.065 per GB, and NAT gateway charges are waived for traffic that passes through both.
  • Newer additions include URL category filtering (January 2026), a proxy mode (preview), and a Next Generation policy type (November 2026) with a drop-by-default firewall engine followed by an IPS engine.
An outbound allow list of partner and update domains, and a firewall attached directly to the Transit Gateway (AWS CLI) 
aws network-firewall create-rule-group \
  --rule-group-name egress-allowed-domains --type STATEFUL --capacity 100 \
  --rule-group '{
    "RulesSource": {"RulesSourceList": {
      "Targets": [".example.com", ".amazonaws.com", ".partner-airline.example"],
      "TargetTypes": ["TLS_SNI", "HTTP_HOST"],
      "GeneratedRulesType": "ALLOWLIST"}},
    "StatefulRuleOptions": {"RuleOrder": "STRICT_ORDER"}}'

aws network-firewall create-firewall \
  --firewall-name use1-central \
  --firewall-policy-arn arn:aws:network-firewall:us-east-1:111111111111:firewall-policy/central-strict \
  --transit-gateway-id tgw-use1 \
  --availability-zone-mappings AvailabilityZone=us-east-1a AvailabilityZone=us-east-1b

Organization-wide controls

  • AWS Firewall Manager: central policies for security groups (common, content audit, usage audit), network ACLs (first and last rules around account rules), Network Firewall (distributed, centralized or import), DNS Firewall, WAF and Shield. Needs Organizations, an administrator account and AWS Config in every account and Region. It creates firewall endpoints but does not change your route tables; it only monitors them.
  • VPC Block Public Access (November 2024): an account-level switch that blocks internet gateway traffic in both directions or inbound only, overriding routes and security groups, with VPC or subnet exclusions. It does not affect Transit Gateway, VPN or Cloud WAN traffic. Enforce it across the organization with a declarative policy.
  • VPC Encryption Controls (November 2025, paid from March 2026): monitor mode marks flow logs with encryption status; enforce mode blocks resources that allow unencrypted traffic. Gateway Load Balancer and Network Firewall cannot be used in an enforce-mode VPC.

Skill 2.2.5Implementing security between network boundaries

The travel company's layered setup:

  1. Account guardrailsBlock Public Access in ingress-only mode for application accounts, with exclusions only for the public load balancer subnets; an SCP stops internet gateways outside the network account.
  2. Between VPCsTransit Gateway route tables keep production and development apart; east-west and egress traffic passes the Transit Gateway-attached Network Firewall.
  3. EgressDomain allow list for outbound HTTPS; DNS Firewall blocks known bad domains for every VPC through the shared Profile.
  4. Subnets and workloadsNetwork ACLs for coarse deny lists; security groups referencing each other for application tiers.
  5. Hybrid edgeOn-premises firewalls filter the Direct Connect and VPN traffic; card-data VPCs use encrypted paths.
  6. GovernanceFirewall Manager audits security groups and keeps the firewall policy on every new VPC.

"Block traffic from a host immediately, including existing connections" points to a network ACL deny, not removing a security group rule. And remember the order: in a network ACL, a deny only works if its rule number is lower than the allow that would match first.

Automation

Knowledge 2.2.5Infrastructure automation

For many accounts, deploy network building blocks with CloudFormation StackSets to OUs (VPC attachments, route table entries, Resolver rule and Profile associations), keep central resources (Transit Gateway, firewalls, endpoints) in the network account's own stacks, and let Firewall Manager, IPAM allocation rules and the Cloud WAN policy apply standards automatically as accounts join. Resource types for the hybrid pieces are listed on Task 2.1; the tooling itself is Task 2.4.

Testing and monitoring

Knowledge 2.2.8Test connectivity (for example, Route Analyzer, Reachability Analyzer, tooling)

Reachability Analyzer works across accounts in the organization (through a delegated administrator) and through peering, Transit Gateways, NAT gateways, load balancers and Network Firewall (5-tuple rules only), but stops at Transit Gateway Connect attachments and ignores Transit Gateway policy tables. To analyze through a Gateway Load Balancer, use UDP 6081. Route Analyzer checks Transit Gateway routes across Regions. Details are on Task 2.1.

Skill 2.2.6Configuring network monitoring and logging by using AWS solutions

  • Transit Gateway flow logs per attachment, delivered to a central log account; Cloud WAN flow logs (November 2026) add segment and Region fields.
  • Network Firewall alert and flow logs, and its monitoring dashboard.
  • Client VPN connection logs; with a Transit Gateway association the client's own address appears in Transit Gateway flow logs.
  • Network Access Analyzer scopes such as "no path from development to production" checked regularly.
  • Centralize with CloudWatch cross-account observability (Task 1.4).

Key takeaways

  • MPLS reaches AWS through a carrier or Partner at a Direct Connect location (often a hosted connection); AWS Interconnect – multicloud links other clouds through a Direct Connect gateway.
  • Transit VPC (appliances with VPN overlays) is legacy; Transit Gateway replaces it. Centralized egress: spokes default-route to the egress VPC, blackhole spoke ranges in the spoke table, NAT per AZ, and a return route to the Transit Gateway in the NAT subnets; it adds $0.02 per GB.
  • Appliance mode goes on the inspection VPC attachment; the native Network Firewall attachment turns it on itself but does not take third-party firewalls.
  • Vendor appliances: source/destination check off, your own high availability, or Gateway Load Balancer with GENEVE 6081 and endpoints per AZ.
  • Shared interface endpoints: private DNS off, a private hosted zone named after each service with an alias record, associated with all spokes; gateway endpoints cannot be shared.
  • Client VPN: ACM server certificate always; AD, SAML or mutual certificates (mutual plus one user method); allow-only authorization rules with longest prefix; client CIDR /22 to /12, fixed. Verified Access checks every request with identity and device trust.
  • Security groups are stateful and keep tracked connections after rule changes; ACLs are stateless, ordered, and cut connections at once; ephemeral ports for return traffic.
  • Network Firewall: strict order, drop established for domain lists, distributed, centralized or Transit Gateway-attached; Firewall Manager, Block Public Access and Encryption Controls give organization-wide guardrails.
