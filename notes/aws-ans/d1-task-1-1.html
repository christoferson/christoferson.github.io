Task 1.1: Design a solution that incorporates edge network services to optimize user performance and traffic management for global architectures

Putting the AWS edge network between users and applications: Amazon CloudFront for caching and accelerating web traffic, AWS Global Accelerator for static anycast IPs and fast regional failover, and how both connect to load balancers, API Gateway, AWS WAF, AWS Shield and Route 53.

Overview

Task 1.1

Design a solution that incorporates edge network services to optimize user performance and traffic management for global architectures.

Users far from an AWS Region pay for distance: every TCP and TLS handshake crosses the public internet, and every lost packet is retransmitted over the same long path. Edge services move the first hop close to the user. Traffic enters the AWS global network at one of hundreds of points of presence (POPs) and rides AWS's own backbone to the Region. Questions in this task describe users, protocols and constraints (static IPs, caching, failover speed, private origins, security) and ask which edge service, or which combination, fits.

The running example for this guide is a global online travel company. Its booking website and mobile app serve customers worldwide from three Regions (us-east-1, eu-central-1 and ap-northeast-1). It has two on-premises data centers and many AWS accounts in AWS Organizations, with a central network account, 111111111111. On this page the company needs fast, secure global access to its website, booking API, image library and partner integrations.

Content distribution with CloudFront

Knowledge 1.1.1Design patterns for the usage of content distribution networks (for example, Amazon CloudFront)

How a request flows through CloudFront

A content distribution network (CDN) keeps copies of content close to users and terminates their connections nearby. CloudFront has three layers between a viewer and the origin:

  1. Point of presence (edge location)The viewer's DNS lookup returns a nearby POP. The TCP and TLS handshakes finish there, and the POP serves the object from its cache if it has a fresh copy.
  2. Regional edge cacheA larger cache shared by several POPs. On a miss at the POP, CloudFront checks the regional edge cache before going to the origin. Proxy methods (PUT, POST, PATCH, OPTIONS, DELETE), dynamic requests and S3 origins in the same Region bypass it.
  3. Origin Shield (optional)One more caching layer in a single Region you choose, close to the origin, so all regional edge caches funnel through one place. It raises the cache hit ratio and cuts origin load.
  4. OriginThe source of the content: an S3 bucket, a load balancer, an EC2 instance, a VPC origin, API Gateway or any HTTP server, including one on premises.

Even uncacheable, dynamic content gets faster: CloudFront keeps persistent connections to the origin (keep-alive, 5 seconds by default), starts forwarding the response as soon as the first byte arrives, and carries the request over the AWS network instead of the public internet.

Origins and protecting them

Amazon S3 with origin access control

An S3 bucket stays private and only CloudFront can read it. Origin access control (OAC) signs CloudFront's requests to S3 with SigV4; the bucket policy allows the CloudFront service principal, limited to one distribution with an AWS:SourceArn condition. OAC supports buckets in every Region, SSE-KMS encrypted objects and dynamic requests such as PUT and DELETE. The older origin access identity (OAI) is labeled legacy and not recommended: it does not support SSE-KMS or Regions launched after early 2023.

Bucket policy that lets only one distribution read the images bucket (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontOAC",
    "Effect": "Allow",
    "Principal": {"Service": "cloudfront.amazonaws.com"},
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::travel-images-111111111111/*",
    "Condition": {"StringEquals": {"AWS:SourceArn": "arn:aws:cloudfront::111111111111:distribution/DISTRIBUTION_ID"}}
  }]
}

With SSE-KMS, the KMS key policy also needs a statement letting the CloudFront service principal decrypt. An S3 website endpoint is different: it is configured as a custom origin over HTTP only, so OAC does not apply.

Custom origins

Any HTTP or HTTPS server: an internet-facing ALB, EC2 instances with public addresses, API Gateway, or a server in a data center. CloudFront can talk to IPv6 custom origins since September 2025. Connection settings control failover speed: up to 3 connection attempts (default 3), a connection timeout of 1 to 10 seconds (default 10) and a response timeout of 1 to 120 seconds (default 30). A response completion timeout (added July 2025) caps the total time for a response, including retries.

VPC origins

Since November 2024, CloudFront can reach an internal ALB, NLB or EC2 instance in a private subnet, so the origin has no public IP at all and CloudFront is the only way in. CloudFront creates a managed elastic network interface in the subnet and a security group named CloudFront-VPCOrigins-Service-SG; allowing that group in the origin's security group admits only your distributions. Requirements and limits worth knowing:

  • The VPC must still have an internet gateway attached, though it is not used for the traffic.
  • A Network Load Balancer origin needs a security group and cannot use a TLS listener; Gateway Load Balancers are not supported.
  • gRPC and Lambda@Edge origin-facing triggers are not supported.
  • Inbound network ACL rules are not evaluated, but outbound rules are, so allow return traffic on ephemeral ports.
  • No extra charge, and VPC origins can be shared across accounts through AWS RAM (since November 2025).

Cache behaviors, policies and TTLs

A distribution has a default cache behavior and up to 75 more, each matching a path pattern (for example /images/* or /api/*) and pointing to an origin or origin group. Each behavior sets the allowed HTTP methods, the viewer protocol policy (for example redirect HTTP to HTTPS) and three policies:

Cache policy

Decides the cache key: which headers, cookies and query strings make a request distinct, plus the minimum, default and maximum TTL and compression. Everything in the cache key is also sent to the origin. The fewer values in the key, the higher the hit ratio. The managed CachingOptimized policy uses no cookies or query strings (minimum TTL 1 second, default 1 day, maximum 1 year); CachingDisabled sets every TTL to 0 for APIs.

Origin request policy

Sends extra values to the origin without adding them to the cache key, for example the viewer's country header or all viewer headers (AllViewer). This lets the origin see what it needs while keeping the cache efficient.

Response headers policy

Adds or removes headers in responses to viewers: CORS, security headers such as HSTS, or Server-Timing.

How the TTL is decided:

  • With a minimum TTL of 0, CloudFront caches for the origin's Cache-Control: max-age (or s-maxage, which applies only to shared caches such as CloudFront), capped at the maximum TTL. Without those headers it uses the default TTL.
  • With a minimum TTL above 0, CloudFront caches for at least that long even if the origin sends no-store, no-cache or private.
  • stale-while-revalidate and stale-if-error let CloudFront serve a stale copy while it refreshes, or while the origin is failing.
  • Only responses to GET (and HEAD) requests are cached; the maximum cacheable object is 50 GB.

An API returning personalized data behind a cache policy with a minimum TTL of 1 second can serve one user's response to another, because the minimum TTL overrides the origin's no-store. Use CachingDisabled (TTLs 0) for dynamic API paths.

Origin failover

An origin group pairs a primary and a secondary origin. When the primary returns a status code you selected (any of 400, 403, 404, 416, 429, 500, 502, 503, 504), CloudFront retries the same request on the secondary. Connection failures count only if 503 is selected, and timeouts only if 504 is selected.

  • Failover happens only for GET, HEAD and OPTIONS. POST, PUT and other writes, and therefore gRPC, never fail over.
  • Every request tries the primary first; there is no sticky failover state.
  • With default settings a dead primary costs about 30 seconds (3 attempts of 10 seconds) before failover; lower the attempts and connection timeout for faster failover.

For the travel company, the image library is replicated between S3 buckets in us-east-1 and eu-central-1, and an origin group fails over between them. The booking API, which takes POST requests, needs regional failover by other means (see Global Accelerator or Route 53 failover routing in Task 1.2). Since 2025, a CloudFront Function can also choose the origin or origin group per request, which enables active-active routing across Regions by cookie, weight or geography.

Private content and geo restriction

Signed URLs and signed cookies

Both require a valid signature, created with a private key whose public key is in a trusted key group attached to the cache behavior (the recommended method, no root user needed). Use signed URLs for individual files, or for clients that do not support cookies. Use signed cookies for many files at once, such as all the documents in a customer's booking area or the segments of a video, without changing their URLs.

Geo restriction

An allow list or block list of countries for the whole distribution; blocked viewers get HTTP 403. To restrict only some paths, or to combine country with other conditions, use an AWS WAF geo match rule instead.

Field-level encryption, which encrypts specific POST form fields at the edge with a public key so only a specific application can decrypt them, is still documented without a deprecation notice.

Protocols

  • HTTP/2 needs TLS 1.2 or later and SNI; HTTP/3 (QUIC over UDP) needs TLS 1.3 and helps mobile users whose networks change mid-session.
  • WebSocket works automatically over HTTP/1.1, with a 10-minute idle timeout.
  • gRPC (since November 2024) needs HTTP/2, POST allowed and HTTPS end to end; it is never cached and does not support origin failover, Origin Shield, Lambda@Edge or VPC origins.
  • Viewer mutual TLS (since November 2025) lets CloudFront verify client certificates, for example from partner systems.

Edge functions

CloudFront Functions

Lightweight JavaScript that runs at every POP on viewer request and viewer response only, in under a millisecond and at millions of requests per second. No network access and no request body. Use it for cache key normalization, header changes, redirects and URL rewrites, simple token checks, and (since 2025) choosing the origin. A KeyValueStore holds data such as redirect maps or feature flags.

Lambda@Edge

Node.js or Python functions that can run on all four events: viewer request, origin request, origin response and viewer response. They have network access, can read the body and can run longer, so they fit authentication against an external service, image transformation or building responses at the edge. Functions are created in us-east-1 as a numbered version and replicated; they cannot use VPC access, environment variables or layers. Current documentation lists a timeout of up to 30 seconds; older material quotes 5 seconds for viewer events, so read questions on this carefully.

"Simple header rewrite or redirect for every request at the lowest cost and latency" points to CloudFront Functions. "Call an external service", "read the request body" or "origin request/response" points to Lambda@Edge.

Price classes, static IPs and pricing Extra

  • Price classes limit which edge locations serve the distribution: Price Class 100 (North America and Europe), 200 (adds most of Asia, the Middle East and Africa) or All. Viewers elsewhere are still served, from a location inside the class.
  • Anycast static IPs give a distribution a fixed list of 21 IP addresses (or 3 for apex domains) that network providers can allowlist, for example to zero-rate the app's data, or that customers can allow in outbound firewalls. They need Price Class All and approval from AWS.
  • Data transfer from AWS origins to CloudFront is free; you pay CloudFront's data transfer out and request prices instead of the Region's data transfer out. Flat-rate monthly plans (since November 2025) offer a fixed price per distribution with no overage charges.

Global traffic management with Global Accelerator

Knowledge 1.1.2Design patterns for global traffic management (for example, AWS Global Accelerator)

What Global Accelerator does

AWS Global Accelerator gives an application two static anycast IPv4 addresses (four with dual-stack, adding two IPv6 addresses), advertised from AWS edge locations worldwide. Users connect to the nearest edge; the connection then travels the AWS backbone to the healthiest, closest regional endpoint. It is a layer 4 proxy for TCP and UDP: it does not cache and does not look inside HTTP. The two addresses come from separate network zones, so if one is unreachable, clients can retry the other. They stay with the accelerator while it is disabled and are released only when it is deleted; you can also bring your own address range (BYOIP).

Building blocks

  1. AcceleratorStandard or custom routing, with its static IP addresses and DNS name.
  2. ListenerA port or port range and protocol (TCP, UDP or both), with client affinity set to none or source IP (to keep a client on the same endpoint).
  3. Endpoint groupOne per Region per listener, with a traffic dial and health check settings.
  4. EndpointsApplication Load Balancers (internet-facing or internal), Network Load Balancers, EC2 instances or Elastic IP addresses, each with a weight.
Add a Tokyo endpoint group with an NLB, sending listener port 443 to port 8443 (AWS CLI; the Global Accelerator API is called in us-west-2) 
aws globalaccelerator create-endpoint-group \
  --listener-arn "$LISTENER_ARN" \
  --endpoint-group-region ap-northeast-1 \
  --traffic-dial-percentage 100 \
  --health-check-protocol TCP \
  --port-overrides ListenerPort=443,EndpointPort=8443 \
  --endpoint-configurations EndpointId="$NLB_ARN",Weight=128,ClientIPPreservationEnabled=true \
  --region us-west-2

Traffic dials, weights and failover

Traffic dial (per Region)

A percentage from 0 to 100 (default 100) of the traffic that would normally go to this endpoint group; the rest goes to the next-closest groups. Turn a Region down to 0 for maintenance, or shift a share of traffic to a new Region for a blue/green deployment. Changes apply to new connections.

Endpoint weight (within a Region)

A number from 0 to 255 (default 128); traffic is shared in proportion to the weights. Weight 0 stops new traffic to an endpoint.

Health checks and failover

Load balancer endpoints use their own target group health checks (an ALB is healthy if every target group has a healthy target). EC2 and Elastic IP endpoints use Global Accelerator's health checks, which come from the Route 53 health checker address ranges; UDP listeners are checked with TCP, so the endpoint must also answer on TCP. When no endpoint in a Region is healthy, traffic moves to another Region within seconds, with no DNS caching involved. Failover ignores the traffic dial, so a Region dialed to 0 can still receive failover traffic. If every endpoint is unhealthy, Global Accelerator fails open and sends traffic to an endpoint anyway.

Client IP preservation

Without preservation, endpoints see Global Accelerator's addresses rather than the user's. Preservation is always on for EC2 endpoints and internal ALBs, on by default for internet-facing ALBs, and optional for Network Load Balancers that have security groups (not with TLS listeners). It is not available for Elastic IP endpoints or NLBs without security groups. With preservation, the endpoint's security groups must allow the real client addresses, and the traffic bypasses network ACLs, Gateway Load Balancer inspection and AWS Network Firewall in that VPC, which matters if those are part of the inspection design.

Custom routing accelerators

A custom routing accelerator maps each accelerator port deterministically to one private IP address and port of an EC2 instance in a VPC subnet. The application, for example a matchmaking service for online games or a voice and video conferencing system, tells each user exactly which accelerator port to use to reach a specific session server. All destinations are denied until allowed; there are no health checks and no failover, so the application must handle a failed server itself.

Pricing Extra

A fixed fee per accelerator per hour (0.025 USD), charged even while the accelerator is disabled, plus a data transfer premium per GB in the dominant direction, which depends on the source Region and the edge location, on top of normal data transfer out.

Global Accelerator addresses accept only connections that clients start. They cannot be used as the source address for outbound connections from your servers; outbound traffic still leaves through NAT gateways or Elastic IPs.

Integrating edge services with ELB, API Gateway and security

Knowledge 1.1.3Integration patterns for content distribution networks and global traffic management with other services (for example, Elastic Load Balancing [ELB], Amazon API Gateway)

CloudFront in front of an Application Load Balancer

If the ALB is internet-facing, users could bypass CloudFront (and its WAF rules and caching) by calling the ALB directly. Three ways to close that door, from weakest to strongest:

  1. Secret custom headerCloudFront adds a header such as X-Origin-Verify with a secret value; an ALB listener rule forwards only requests carrying it, and the default rule returns a fixed 403. Rotate the secret by allowing two values during the change.
  2. CloudFront managed prefix listAllow only com.amazonaws.global.cloudfront.origin-facing in the ALB's security group. It counts as 55 rules toward the default limit of 60 rules per security group, and it admits any CloudFront distribution, not just yours, so combine it with the header.
  3. VPC originMake the ALB internal in private subnets and add it as a VPC origin. It has no public address to bypass.

For HTTPS end to end, the certificate for the CloudFront alternate domain name must be in AWS Certificate Manager in us-east-1, while the ALB's certificate is in the ALB's own Region.

CloudFront with Amazon API Gateway

  • A REST API can be edge-optimized (the default): API Gateway puts a CloudFront distribution it manages in front, which you cannot configure.
  • A Regional endpoint plus your own CloudFront distribution gives control over caching, WAF at the edge, custom domains across APIs, edge functions and origin failover. AWS suggests this for global clients that need CloudFront features.
  • HTTP APIs are Regional only and cannot have AWS WAF attached; putting CloudFront with WAF in front of them is the way to protect them.
  • Private APIs are reachable only from VPCs through interface endpoints.

Global Accelerator with load balancers and instances

Global Accelerator usually fronts ALBs or NLBs in each Region, giving the application fixed addresses and multi-Region failover in front of regional load balancing. With an NLB endpoint, turn off cross-zone load balancing, and do not send users to the same endpoints directly as well, because direct and accelerated connections from the same client can collide. Since April 2026, the AWS Load Balancer Controller can manage accelerators from Kubernetes.

AWS WAF and AWS Shield Advanced

  • AWS WAF (whose web ACLs the console now calls protection packs) attaches to CloudFront, with the web ACL created in the global (us-east-1) scope, and to regional resources such as ALBs, API Gateway REST APIs, AWS AppSync, Amazon Cognito user pools and AWS Verified Access. It cannot attach to Global Accelerator, Network Load Balancers or API Gateway HTTP APIs.
  • AWS Shield Advanced protects CloudFront distributions, Route 53 hosted zones, Global Accelerator standard accelerators, ALBs, Classic Load Balancers and Elastic IP addresses. NLBs and EC2 instances are protected through their Elastic IP addresses.

Route 53 alias records

Point the company's domain at the edge with an alias record to the CloudFront distribution or the accelerator. Alias records work at the zone apex (the bare domain, such as example.com), resolve to the target's current addresses, and queries for them are free. Route 53 routing policies themselves are covered in Task 1.2.

"Prevent users from bypassing CloudFront to reach the ALB" points to an internal ALB as a VPC origin, or to a secret custom header with the CloudFront managed prefix list. "Add WAF to an HTTP API" or "WAF in front of an NLB application" points to putting CloudFront in front.

Evaluating global traffic requirements

Skill 1.1.1Evaluating requirements of global inbound and outbound traffic from the internet to design an appropriate content distribution solution

Questions that decide the design

  1. ProtocolHTTP(S), WebSocket or gRPC can use CloudFront; any TCP or UDP protocol needs Global Accelerator (or a regional NLB).
  2. CacheabilityStatic, media or slowly changing content benefits from CloudFront caching; personalized responses still gain from dynamic acceleration.
  3. Fixed addressesCustomers, carriers or firewalls that must allowlist IPs need Global Accelerator, or CloudFront Anycast static IPs for HTTP.
  4. FailoverFast multi-Region failover for any request type points to Global Accelerator; CloudFront origin groups fail over only reads; DNS failover depends on TTLs.
  5. Origin exposurePrivate origins fit CloudFront VPC origins or S3 with OAC; Global Accelerator can reach internal ALBs.
  6. Security at the edgeLayer 7 filtering means CloudFront with AWS WAF; DDoS protection with response team support means Shield Advanced on the edge resources.
  7. Cost and traffic directionCloudFront removes origin data transfer out for AWS origins; Global Accelerator adds a fixed fee and a premium per GB.

The travel company's design

Website and images

One CloudFront distribution for www.example.com. The default behavior points to the web application's internal ALBs as VPC origins; /static/* and /images/* point to S3 with OAC, using an origin group across two Regions and the CachingOptimized policy. AWS WAF (global scope) blocks common web attacks and bots.

Booking API

A /api/* behavior with CachingDisabled and an origin request policy forwarding the needed headers, in front of Regional API Gateway endpoints. A CloudFront Function picks the Region per request from a cookie set at sign-in, so a user's session stays in one Region.

Partner connections

Travel agencies and airline partners connect to a booking interface from locked-down networks and must allowlist addresses. A Global Accelerator standard accelerator gives them two fixed IPs in front of NLBs in all three Regions, with health-based failover in seconds and traffic dials for regional maintenance.

Outbound traffic

Servers calling airline and payment APIs leave through NAT gateways with Elastic IPs per Region, because the partners allowlist the company's outbound addresses and Global Accelerator addresses cannot be used for outbound connections.

Global Accelerator does not cache. If a scenario's main problem is slow downloads of the same large files by users worldwide, the answer is CloudFront, even if "global performance" makes Global Accelerator sound right.

Key takeaways

  • CloudFront terminates connections at POPs, caches in POPs, regional edge caches and optional Origin Shield, and accelerates dynamic content over the AWS network. Protect S3 with OAC (OAI is legacy) and private load balancers or instances with VPC origins.
  • The cache policy defines the cache key and TTLs; the origin request policy forwards extra values without fragmenting the cache. A minimum TTL above 0 overrides the origin's no-store. Origin groups fail over only GET, HEAD and OPTIONS.
  • Signed URLs for single files, signed cookies for many; geo restriction is per distribution; CloudFront Functions for light viewer-side logic, Lambda@Edge for origin events, network calls and bodies.
  • Global Accelerator: two static anycast IPs, layer 4 TCP/UDP, endpoint groups per Region with traffic dials and weighted endpoints, failover in seconds that ignores dials and fails open. Client IP preservation bypasses NACLs, GWLB and Network Firewall. Custom routing maps ports to specific instances without health checks.
  • Stop CloudFront bypass with VPC origins or a secret header plus the managed prefix list. Use a Regional API Gateway endpoint with your own distribution for full control. WAF attaches to CloudFront, ALB and REST APIs, not Global Accelerator, NLB or HTTP APIs.
  • Decide by protocol, cacheability, fixed addresses, failover needs, origin exposure, edge security and cost; outbound traffic needs NAT gateways or Elastic IPs, not Global Accelerator.
