Overview

Task 1.6

Design a routing strategy and connectivity architecture that include multiple AWS accounts, AWS Regions, and VPCs to support different connectivity patterns.

Questions here describe an estate (a few VPCs or hundreds, one Region or several, one organization or partners) plus constraints such as transitive routing, central inspection, lowest cost per GB, overlapping CIDRs or one-way service access. You pick the connectivity service and the routing that makes it work. Many wrong answers break a rule of one service, for example expecting VPC peering to be transitive or PrivateLink to let the provider start connections.

The travel company has about 300 VPCs in three Regions, owned by many accounts in AWS Organizations, with Transit Gateways in its network account, 111111111111. It sells a fare search API to airline and agency partners. It has just bought a hotel booking startup whose VPCs all use 10.0.0.0/16, which overlaps the company's own ranges.

Connectivity patterns

Knowledge 1.6.1Different connectivity patterns and use cases (for example, VPC peering, Transit Gateway, AWS PrivateLink)

There are two kinds of pattern. Network-level connections (peering, Transit Gateway, Cloud WAN) route IP traffic between whole VPCs in both directions and need unique address ranges. Service-level connections (PrivateLink, VPC Lattice) expose specific services or resources to consumers, work one way, and do not care if addresses overlap.

VPC peering

A one-to-one connection between two VPCs, in the same or different accounts and Regions. The requester asks, the accepter accepts within 7 days, and then each side adds its own routes to the peer's CIDR; nothing propagates. Only one peering can exist between the same two VPCs.

Rules that shape designs

  • Not transitive: if A peers with B and with C, B cannot reach C through A.
  • No edge-to-edge routing: B cannot use A's internet gateway, NAT gateway, VPN, Direct Connect or gateway endpoint to S3 or DynamoDB.
  • No overlap: if any IPv4 or IPv6 CIDR of one VPC overlaps any CIDR of the other, even a secondary one you never use, the request fails.
  • You cannot query the peer VPC's Amazon DNS server, and there is no reverse path check: return traffic follows your route table.

Same Region compared with inter-Region

  • MTU: 9001 within a Region; 8500 between Regions since March 2025 (it used to be 1500, which older material still says).
  • Security group references to the peer's groups work only within the same Region (format account-id/sg-id across accounts). Across Regions, use the peer's CIDR.
  • DNS: enable DNS resolution on the peering so the peer's public hostnames resolve to private IPs. Inter-Region peers always need it; same-Region peers need it only for CIDRs outside RFC 1918.
  • Inter-Region traffic is encrypted on the AWS network.

Scale and cost

50 active peerings per VPC by default, up to 125. A full mesh of n VPCs needs n(n−1)/2 peerings: 4,950 for 100 VPCs, each with routes on both sides. Route tables hold 500 routes by default (raised from 50 in June 2025, maximum 1,000). Peering has no hourly charge and no processing fee; traffic within one Availability Zone (matched by AZ ID) is free, cross-AZ costs $0.01 per GB each way, and inter-Region pays normal inter-Region transfer. It has the lowest latency, with no extra hop.

Peer the bookings VPC in us-east-1 with an analytics VPC in another account in eu-central-1, then turn on DNS resolution (AWS CLI) 
# Requester (bookings account), us-east-1
aws ec2 create-vpc-peering-connection --region us-east-1 \
  --vpc-id vpc-bookings \
  --peer-vpc-id vpc-analytics \
  --peer-owner-id 333333333333 \
  --peer-region eu-central-1

# Accepter (analytics account), in the accepter's Region
aws ec2 accept-vpc-peering-connection --region eu-central-1 \
  --vpc-peering-connection-id pcx-0abc1234def567890

# Each side enables DNS resolution for its own side, then adds routes
aws ec2 modify-vpc-peering-connection-options --region us-east-1 \
  --vpc-peering-connection-id pcx-0abc1234def567890 \
  --requester-peering-connection-options AllowDnsResolutionFromRemoteVpc=true
aws ec2 create-route --region us-east-1 --route-table-id rtb-bookings-app \
  --destination-cidr-block 10.44.8.0/21 \
  --vpc-peering-connection-id pcx-0abc1234def567890

Transit Gateway

A Regional router that VPCs, VPNs, Direct Connect gateways, Connect peers and other Transit Gateways attach to, so each VPC needs one attachment instead of a mesh. It is shared from a network account through AWS RAM (Task 1.5).

Route tables, associations and propagations

  • Each attachment is associated with exactly one route table, which decides where its traffic goes.
  • An attachment can propagate its routes (VPC CIDRs, or BGP routes from VPN and Direct Connect) into any number of route tables. You cannot filter what it propagates.
  • Static routes beat propagated routes for the same prefix. A blackhole route drops matching traffic. Prefix list references turn each entry of a managed prefix list into a route.
  • By default every attachment associates with and propagates to the default route table, giving full any-to-any routing. Turn both defaults off for segmented designs.
  • If a newly attached VPC overlaps one already attached, its CIDR is not propagated.

Segmentation patterns

  1. FlatEverything associates with and propagates to one table. Simple, but every VPC reaches every other.
  2. Isolated VPCsVPCs associate with a table that holds only the VPN or Direct Connect routes, so VPC-to-VPC packets find no route and are dropped, while all reach on premises.
  3. Isolated with shared servicesSpokes propagate only into the shared services table; the shared services VPC propagates into the spoke table. Spokes reach shared services but not each other.
  4. Environment tablesProduction, development and shared tables, each propagating only what that environment may reach.
  5. Centralized egress or inspectionA 0.0.0.0/0 static route to an egress or inspection VPC, with blackhole routes for RFC 1918 ranges so spokes cannot reach each other through it.
A production route table on the us-east-1 Transit Gateway: associate a spoke, propagate shared services and on premises, block development (AWS CLI) 
aws ec2 create-transit-gateway-route-table --transit-gateway-id tgw-use1 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=prod}]'

# The production spoke uses this table for its lookups
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-bookings-prod

# Production can reach shared services and the data centers
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-shared-services
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-dxgw

# Never route production traffic to the development range
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.42.0.0/16 --blackhole

Appliance mode

A Transit Gateway normally keeps traffic in the source Availability Zone, so the two directions of a flow between VPCs in different AZs can pass through firewalls in different AZs of an inspection VPC, and a stateful firewall drops them. Appliance mode on the inspection VPC's attachment pins each flow to one AZ for its lifetime. It is set per VPC attachment (ApplianceModeSupport=enable), and the AZ-aware choice needs route propagation in the appliance attachment's route table. Inspection itself is covered in Domain 4.

Inter-Region: Transit Gateway peering

Transit Gateways peer with each other within or across Regions and accounts, and inter-Region traffic is encrypted. Peering supports static routes only: add a static route in each Transit Gateway route table pointing at the peering attachment. AWS recommends unique ASNs per Transit Gateway for possible future route propagation. MTU is 8500 and Path MTU Discovery is not supported. Peering does not resolve private DNS names across Regions.

Security group referencing (September 2024)

VPCs attached to the same Transit Gateway can reference each other's security groups in inbound rules. Enable it on the Transit Gateway (off by default) and on the attachment (on by default). It does not work across Transit Gateway peering, through Gateway Load Balancer or Network Firewall inspection, or for PrivateLink endpoints. The 2024 multi-VPC whitepaper still says it is unsupported; it is now supported.

Policy-based routing (July 2026)

A policy table lets an attachment choose its route table by source and destination address, ports and protocol, not just destination: for example, send traffic from one subnet to the firewall route table and everything else to the default table. Rules are first-match, an attachment uses either a policy table or a route table, never both, and there is no extra charge. Associating a policy table with a VPN or Connect attachment stops the Transit Gateway advertising BGP routes to that peer.

Limits and pricing

5,000 attachments, 20 route tables and 10,000 routes per Transit Gateway; 50 peering attachments; up to 100 Gbps and 7.5 million packets per second per VPC attachment per AZ. A VPC can attach to up to 5 Transit Gateways. Pricing: about $0.05 per attachment-hour plus $0.02 per GB processed, charged on the sending attachment. A design with heavy traffic between two VPCs can be cheaper over a peering alongside the Transit Gateway, because the more specific peering route wins.

AWS Cloud WAN

A managed global network defined by a JSON core network policy. You list Regions as edge locations, and AWS runs a core network edge in each, peered with every other edge using BGP, so inter-Region routing is automatic.

  • Segments are global routing domains, like VRFs. Attachments reach only their own segment unless a share action joins segments. Sharing is not transitive: sharing a shared services segment with production and development does not join production to development.
  • isolate-attachments stops attachments in the same segment from reaching each other, useful for a segment of isolated workloads that may reach only shared services.
  • Attachment policies map attachments to segments by tag, account, Region or type, so a VPC owner tags an attachment and it lands in the right segment, optionally after acceptance.
  • Network function groups (service insertion, 2024) send traffic between segments, or to the internet, through inspection VPCs with send-via and send-to.
  • Routing policies (policy version 2025.11) filter, summarize and set BGP attributes on routes.
  • Attachments: VPC, Site-to-Site VPN, Connect, Direct Connect gateway, Transit Gateway route table, and Transit Gateway peering (same Region, BGP only) for gradual migration.
  • Pricing: $0.50 per edge per hour before any traffic, plus attachment-hours and $0.02 per GB processed. That fixed cost makes it poor value for one Region with a few VPCs.
Core network policy: two Regions, production and development segments that both reach shared services but not each other, segment chosen by attachment tag 
{
  "version": "2025.11",
  "core-network-configuration": {
    "asn-ranges": ["64520-64550"],
    "edge-locations": [
      {"location": "us-east-1"},
      {"location": "eu-central-1"}
    ]
  },
  "segments": [
    {"name": "prod", "require-attachment-acceptance": true},
    {"name": "dev", "isolate-attachments": true, "require-attachment-acceptance": false},
    {"name": "shared", "require-attachment-acceptance": true}
  ],
  "segment-actions": [
    {"action": "share", "mode": "attachment-route",
     "segment": "shared", "share-with": ["prod", "dev"]}
  ],
  "attachment-policies": [
    {"rule-number": 100,
     "condition-logic": "or",
     "conditions": [{"type": "tag-exists", "key": "segment"}],
     "action": {"association-method": "tag", "tag-value-of-key": "segment"}}
  ]
}

AWS PrivateLink

PrivateLink publishes a service from a provider VPC so consumers reach it through an interface endpoint: a network interface with an IP from the consumer's own subnet. No routes join the VPCs, so overlapping CIDRs do not matter. Consumers can also reach endpoints over Direct Connect, VPN, peering and Transit Gateway.

Endpoint services (provider side)

  • Fronted by a Network Load Balancer (or a Gateway Load Balancer for inspection appliances). There is no direct ALB option: put the ALB behind an NLB as an alb type target.
  • Access control: allowed principals (accounts, roles or users) and acceptance required. Allowing * with auto-accept exposes the service to any AWS account.
  • Available only in the NLB's Availability Zones; consumers can use only AZs they share with the provider, matched by AZ ID, since AZ names differ between accounts.
  • A private DNS name (for example fares.example.com) requires the provider to prove ownership with a TXT record in public DNS.
  • The provider sees NLB addresses, not consumer addresses. Turn on proxy protocol v2 on the target group to receive the client IP and the endpoint ID.

Consumer side and behavior

  • One endpoint network interface per chosen subnet (one per AZ), protected by security groups.
  • Regional and zonal DNS names; use zonal names to keep traffic in one AZ.
  • One way only: the consumer starts connections; the provider cannot connect back. Two-way needs a second endpoint service in the other direction.
  • 10 Gbps per AZ by default, scaling to 100 Gbps; MTU 8500, no Path MTU Discovery.
  • Pricing: about $0.01 per endpoint per AZ per hour plus $0.01 per GB (lower at high volumes), paid by the consumer.

Cross-Region PrivateLink

Since November 2024 a provider can list supported Regions on its endpoint service, and consumers in those Regions create endpoints with a service Region, with no peering needed. Since November 2025 some AWS services (such as S3, KMS, ECR and Lambda) can be reached cross-Region too. Both need the vpce:AllowMultiRegion permission. Failover is between AZs only, never between Regions.

The fare search API as an endpoint service for partners in two Regions, and a partner's endpoint (AWS CLI)

aws ec2 create-vpc-endpoint-service-configuration --region us-east-1 \

  --acceptance-required \
  --private-dns-name fares.example.com \
  --supported-regions us-east-1 eu-central-1

aws ec2 modify-vpc-endpoint-service-permissions --region us-east-1 \
  --service-id vpce-svc-0fares1234567890 \
  --add-allowed-principals arn:aws:iam::555555555555:root

# Consumer (an airline partner), in eu-central-1
aws ec2 create-vpc-endpoint --region eu-central-1 \
  --vpc-endpoint-type Interface \
  --vpc-id vpc-partner \
  --service-name com.amazonaws.vpce.us-east-1.vpce-svc-0fares1234567890 \

  --subnet-ids subnet-p1 subnet-p2 \

PrivateLink for VPC resources (December 2024)

Shares a database, IP address or DNS name with no load balancer. The provider creates a resource gateway (interfaces in its VPC) and a resource configuration for the target, shares it through RAM, and consumers reach it through a resource endpoint or a Lattice service network. TCP only; Amazon RDS is the only AWS resource type by ARN; the resource sees the gateway's addresses as the source.

Amazon VPC Lattice

An application networking service for many services across many VPCs and accounts. A service network groups services (HTTP, HTTPS or TLS listeners with rules sending to target groups of instances, IPs, Lambda functions or ALBs) and resource configurations, shared through RAM.

  • Consumers join through a VPC association (one service network per VPC; traffic uses link-local and AWS-owned non-routable addresses, so it cannot come from on premises, peering or Transit Gateway) or a service network endpoint (uses a /28 per AZ of the consumer VPC; reachable from on premises and other VPCs).
  • Auth policies: IAM resource policies on the service network and the service, checking SigV4-signed callers for vpc-lattice-svcs:Invoke. They do not apply to resource configurations.
  • Overlapping CIDRs are fine. Target security groups must allow the Lattice managed prefix list, not the client's security group.
  • Pricing: $0.025 per service per hour, $0.025 per GB and $0.10 per million requests after the first 300,000 each hour.

"Partners with overlapping CIDRs consume one API, and the provider must never reach into partner VPCs" points to PrivateLink. "Hundreds of microservices across accounts with IAM authorization and path-based routing" points to VPC Lattice. "Full two-way routing between hundreds of VPCs and on premises" points to Transit Gateway or Cloud WAN.

VPC sharing

Knowledge 1.6.2Capabilities and advantages of VPC sharing

With VPC sharing, an owner account shares subnets through AWS RAM with participant accounts in the same AWS Organization. Participants launch their own resources (EC2, RDS, Lambda, EKS, load balancers and more) into those subnets, but cannot see or change other accounts' resources. Billing and access stay per account while the network is shared.

Advantages

  • Fewer VPCs and attachments: one shared VPC per environment instead of one per account, so fewer peerings, Transit Gateway attachments and hourly charges.
  • Central control: the network team owns route tables, network ACLs, gateways, endpoints and Transit Gateway attachments; application teams cannot change them.
  • Simple, cheap traffic between teams: applications in different accounts talk over the VPC's local route, with no extra hop. Traffic within one AZ ID is free.
  • Better use of IP space: one larger VPC is carved into subnets instead of many half-empty VPCs.
  • Shared infrastructure: NAT gateways, interface endpoints and Resolver endpoints are deployed once and used by every participant.

Limits

  • Same organization only, with resource sharing enabled in RAM from the management account. Default VPC subnets cannot be shared.
  • Up to 100 participant accounts per VPC and 100 subnets shared with one account (both adjustable). Participants' resources count against their own quotas.
  • Everything shares one blast radius: route tables, network ACLs and quotas such as network interfaces per VPC. Use separate shared VPCs for production and non-production.

IP subnets and overlaps

Knowledge 1.6.3IP subnets and solutions accounting for IP address overlaps

VPC and subnet CIDR rules

  • IPv4 VPC and subnet CIDRs range from /16 to /28. RFC 1918 is recommended; public ranges are allowed but never advertised. You cannot use 0.0.0.0/8, 127.0.0.0/8, 169.254.0.0/16 or 224.0.0.0/4, and should avoid 172.17.0.0/16, which Docker uses.
  • Each subnet loses 5 addresses: network, VPC router (+1), DNS (+2), reserved (+3) and broadcast. A /28 leaves 11 usable.
  • A VPC holds up to 5 IPv4 CIDRs by default (adjustable to 50). CIDRs cannot be resized, and the primary cannot be removed.
  • A new secondary CIDR cannot overlap an existing one, and cannot be equal to or larger than an existing route destination in the VPC.

Secondary CIDR restrictions

You cannot mix RFC 1918 blocks: a VPC created in 10.0.0.0/8 cannot add 172.16.0.0/12 or 192.168.0.0/16 ranges, and vice versa. Any RFC 1918 VPC can add 100.64.0.0/10 (shared address space, often used as non-routable space) or public ranges. A VPC created with a public or 100.64 range cannot add RFC 1918 later, so create it with the RFC 1918 CIDR first. 198.19.0.0/16 is restricted.

IPv6

An Amazon-provided VPC block is a /56 (or bring your own); subnets are usually /64. Amazon IPv6 addresses are globally unique, so they never overlap, which removes the overlap problem for traffic that can use IPv6. Private IPv6 (ULA or private GUA) is available only through IPAM. IPv6-only subnets reach IPv4 services through NAT64 and DNS64.

Amazon VPC IP Address Manager (IPAM)

IPAM plans and tracks addresses across accounts and Regions. Scopes each represent one network (a default private and a default public scope); overlap is reported only within a scope. Pools form a hierarchy (for example top-level, then per Region, then production and development) with allocation rules such as minimum, maximum and default netmask and required tags. VPCs created from a pool get a non-overlapping CIDR automatically, and IPAM monitors compliance and overlap. For an organization, delegate a member account as IPAM administrator from IPAM itself, and share pools through RAM. Multi-account and private IPv4 management need the Advanced tier ($0.00027 per active IP per hour).

A us-east-1 pool under the company's top-level 10.32.0.0/11 pool: VPCs get /20 by default, never larger than /16, and must be tagged (AWS CLI) 
aws ec2 create-ipam-pool \
  --ipam-scope-id ipam-scope-0private1234567 \
  --address-family ipv4 \
  --source-ipam-pool-id ipam-pool-0toplevel123456 \
  --locale us-east-1 \
  --allocation-min-netmask-length 16 \
  --allocation-max-netmask-length 24 \
  --allocation-default-netmask-length 20 \
  --allocation-resource-tags "Key=env,Value=prod" \
  --auto-import

aws ec2 provision-ipam-pool-cidr \
  --ipam-pool-id ipam-pool-0use1prod12345 \
  --cidr 10.40.0.0/14

Why overlaps break routing

Overlapping networks cannot be joined at layer 3 as they are. Peering refuses the connection, a Transit Gateway will not propagate the second overlapping VPC, and a VPC always delivers addresses inside its own CIDR locally, so it can never send them out. The options are covered in Managing IP overlaps: translate addresses (private NAT gateway, Transit Gateway or Cloud WAN 1:1 NAT), connect at the service level (PrivateLink, Lattice), re-address, or use IPv6. Prevention is cheaper: allocate every VPC from IPAM.

Choosing how to connect VPCs

Skill 1.6.1Connecting multiple VPCs by using the most appropriate services based on requirements (for example, using VPC peering, Transit Gateway, PrivateLink)

VPC peering

A few VPCs (AWS suggests under about 10), no transitive routing needed, lowest latency and lowest cost per GB, or a very high-volume pair alongside a Transit Gateway. Not for hybrid sharing or central inspection, because there is no edge-to-edge routing.

Transit Gateway

Tens to thousands of VPCs in a Region, transitive routing, one shared Direct Connect or VPN path, route-table segmentation, and central egress or inspection. Usually one per Region, with peering between Regions using static routes. Pays $0.02 per GB processed and an extra hop.

Cloud WAN

Many Regions, global segments, policy-driven attachment by tags, and dynamic inter-Region routing without managing Transit Gateway peering routes. It can peer with existing Transit Gateways for a gradual move.

PrivateLink

Expose a specific service to many VPCs or accounts, including partners and SaaS consumers, one way, with overlapping CIDRs and without opening routes. It scales far beyond peering limits.

VPC Lattice

Many HTTP, gRPC or TCP services between application teams, with IAM authorization, layer 7 routing and no network plumbing.

VPC sharing

Teams in the same organization that trust each other and talk a lot: put them in one shared VPC instead of connecting many.

These combine. The travel company's design:

  1. Shared VPCs per environmentIn each Region the network account owns production, development and shared services VPCs and shares their subnets with application accounts, which cuts 300 VPCs to a few dozen.
  2. Transit Gateway per RegionRoute tables for production, development, shared services and on premises; development and production cannot reach each other.
  3. Inter-RegionTransit Gateway peering with static summary routes (10.40.0.0/14 for us-east-1, 10.44.0.0/14 for eu-central-1, 10.48.0.0/14 for ap-northeast-1). Moving to Cloud WAN is the planned next step.
  4. Peering for one heavy pairThe bookings and pricing VPCs exchange many terabytes a month; a direct peering avoids Transit Gateway processing charges, and its more specific routes win.
  5. PrivateLink for partnersThe fare search API is an endpoint service; airlines connect from their own accounts, with cross-Region access from Europe.
  6. IPAMEvery new VPC takes its CIDR from a Regional pool.

Peering is never transitive and never shares gateways. "VPC B must use VPC A's NAT gateway or VPN" cannot be solved with a peering; use a Transit Gateway with central egress, or VPC sharing so B's workloads sit in A's subnets.

Using VPC sharing

Skill 1.6.2Using VPC sharing in a multi-account setup

Who can do what

Owner (network account)

Creates and manages the VPC, subnets, route tables, network ACLs, internet and NAT gateways, VPC endpoints, Resolver endpoints, peering and Transit Gateway attachments. Can create flow logs for subnets and for participants' interfaces, and can describe participants' interfaces and security groups but not change or use them.

Participant (application account)

Creates its own instances, databases, load balancers and network interfaces in shared subnets, its own security groups, and flow logs for its own interfaces. It can describe the VPC, subnets, route tables and network ACLs, but cannot change them, cannot create gateways, peering or attachments, and cannot even describe NAT gateways. It cannot create interface endpoints in shared subnets.

Security groups

  • Participants can reference other accounts' security groups in rules (account-id/sg-id).
  • They cannot launch with the VPC's default security group, which belongs to the owner.
  • Since October 2024 the owner can share security groups through RAM, so participants attach centrally managed groups that update for everyone; participants cannot share their own.
  • Security group VPC associations let one group be used in several VPCs in the same Region.

Billing

Participants pay for their own resources and for their inter-AZ, peering, internet gateway and Direct Connect gateway data transfer. The owner pays for NAT gateways, VPN gateways, Transit Gateway attachments, PrivateLink and endpoints, and the public IPv4 addresses in the VPC. Plan cost allocation (tags, or Transit Gateway flexible cost allocation) if the network team charges back.

Other details

  • Tags are not shared with participants.
  • Match subnets across accounts by AZ ID.
  • If the owner unshares a subnet, participants' existing resources keep running but nothing new can be launched. The owner cannot delete the subnet or VPC while participants' resources remain in it.
Share the production application subnets in us-east-1 with the Bookings organizational unit (AWS CLI, network account) 
aws ram create-resource-share --region us-east-1 \
  --name prod-use1-app-subnets \
  --resource-arns \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-prod-app-az1 \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-prod-app-az2 \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-prod-app-az4 \
  --principals arn:aws:organizations::999999999999:ou/o-travel1234/ou-bkng-11112222 \
  --no-allow-external-principals

"Application teams must not change routing, but each account must keep its own bill and IAM boundary, with fewer Transit Gateway attachments" points to VPC sharing. "Share with a partner outside the organization" rules it out: use PrivateLink or a Transit Gateway share instead.

Managing IP overlaps

Skill 1.6.3Managing IP overlaps by using different available services and options (for example, NAT, PrivateLink, Transit Gateway routing)

The acquired hotel startup's VPCs all use 10.0.0.0/16, which also exists in two of the company's development VPCs. Several tools apply, depending on direction and scale.

PrivateLink or Lattice (service level)

If the company only needs to call a few of the startup's services (or the reverse), publish them as endpoint services, resource configurations or Lattice services. Consumers reach local addresses in their own VPC, so overlap is irrelevant. This is one way per service; the simplest fix when full network access is not needed.

Private NAT gateway

A NAT gateway with connectivity type private (no Elastic IP) translates outbound connections to its own private address, routing on to a Transit Gateway or VGW. The usual pattern:

  1. Two address ranges per VPCWorkloads stay in the overlapping, non-routable range; each VPC also gets a small unique, routable secondary CIDR.
  2. Private NAT in the routable subnetOutbound traffic from workloads goes to the private NAT gateway, which translates it to its routable address and sends it to the Transit Gateway.
  3. Inbound through a load balancerA private NAT gateway is outbound only, so the destination VPC exposes services through an internal ALB or NLB in its routable subnet, with targets in the non-routable range.
  4. Transit GatewayAttaches using the routable subnets, with static routes (or propagation) only for the routable ranges.

Each NAT address supports 55,000 simultaneous connections per unique destination, and a NAT gateway can have up to 8 addresses. Private NAT gateways are zonal; the regional NAT gateway (November 2025) does not support private mode. Traffic sent from a private NAT gateway to an internet gateway is dropped. Watch which range a question calls routable: AWS's own example uses 10.0.0.0/16 as the overlapping range and 100.64.x as routable, while many blogs do the reverse.

Private NAT gateway in the startup VPC's routable subnet, with two extra addresses for more connections (AWS CLI) 
aws ec2 create-nat-gateway \
  --subnet-id subnet-hotel-routable-az1 \
  --connectivity-type private \
  --secondary-private-ip-address-count 2

aws ec2 create-route --route-table-id rtb-hotel-workloads \
  --destination-cidr-block 10.32.0.0/11 \
  --nat-gateway-id nat-0hotel123456789a

aws ec2 create-route --route-table-id rtb-hotel-routable \

Transit Gateway and Cloud WAN 1:1 NAT (October 2026)

A newer option built into the Transit Gateway and Cloud WAN: static, stateless, two-way translation of a whole CIDR to another of the same prefix length on an attachment, keeping host bits (10.0.12.7 becomes 100.65.12.7). Connections can start from either side, so no load balancer is needed.

  • For identical CIDRs, translate both sides to different NAT CIDRs; a VPC cannot send traffic to an address inside its own CIDR.
  • NAT CIDRs must be RFC 1918 or 100.64.0.0/10. IPv4 only. Up to 50 rules per attachment.
  • Works on VPC, Direct Connect gateway, VPN, Connect and peering attachments. Not with appliance mode on the same attachment, Client VPN or network function attachments. Only the Transit Gateway owner can configure it.
  • When a rule exactly matches a VPC CIDR, the Transit Gateway replaces that VPC's propagated route with a system route for the NAT CIDR, so peers using the real addresses lose access. System routes rank below static and above propagated routes.
  • Billed at NAT gateway hourly and per-GB rates.
Translate the startup VPC (10.0.0.0/16) to 100.65.0.0/16 on its Transit Gateway attachment; the company's overlapping development VPC is translated to 100.66.0.0/16 on its own attachment the same way (AWS CLI) 
aws ec2 modify-transit-gateway-attachment-nat-configuration \
  --transit-gateway-attachment-id tgw-attach-hotel-app \
  --nat-gateway-support enable \
  --nat-gateway-rules '[{"RuleNumber":100,"MatchSourceCidr":"10.0.0.0/16","NatCidr":"100.65.0.0/16"}]'

aws ec2 get-transit-gateway-attachment-nat-configuration \
  --transit-gateway-attachment-id tgw-attach-hotel-app

Routing tricks with longest prefix

A hub VPC can peer with two spokes that overlap each other (but not the hub) and send traffic to each by more specific routes, for example a subnet or /32 route to one peering and the full CIDR to the other. Return traffic must also be routed carefully, because there is no reverse-path check. In a Transit Gateway, static and more specific routes can reach a non-overlapping part of an overlapping range. These give partial reachability only.

Longer-term fixes

Re-address the overlapping VPCs from IPAM pools (add a new secondary CIDR, move workloads, remove the old one), or move traffic to IPv6, where Amazon addresses are unique. For partners, a shared extranet VPC using public (BYOIP) or IPv6 addresses avoids everyone's private ranges.

A private NAT gateway only handles connections started from its own VPC. For two-way traffic between overlapping VPCs, add a load balancer on the other side or use Transit Gateway 1:1 NAT. And with 1:1 NAT on identical CIDRs, translating only one side does not work.

PrivateLink tunnel endpoints (November 2026) give one-way access to whole CIDR ranges in another VPC over GENEVE, across overlapping networks. They are too new to expect on the exam, but they extend the PrivateLink option beyond single services.

Key takeaways

  • Peering: one-to-one, not transitive, no edge-to-edge, no overlap of any CIDR; manual routes both sides; inter-Region MTU 8500 (since 2025), security group references same Region only; no hourly or processing fee, free within an AZ; 125 peers maximum.
  • Transit Gateway: association (one table) and propagation (many), static beats propagated, blackholes and prefix lists; segmentation by route tables; appliance mode for stateful inspection; inter-Region peering with static routes only; inbound security group referencing on one gateway; policy-based routing (2026); $0.02 per GB.
  • Cloud WAN: policy-defined global network, segments as VRFs, non-transitive share, isolate-attachments, tag-based attachment policies, network function groups, $0.50 per edge-hour.
  • PrivateLink: NLB (or GWLB) endpoint service, allowed principals and acceptance, AZ IDs, private DNS with TXT verification, proxy protocol v2 for client IPs, one way, overlap-proof, cross-Region since 2024; resource configurations need no NLB.
  • VPC Lattice: service networks, services and target groups with IAM auth policies; VPC association (one network, local traffic only) or service network endpoint (reachable from other networks).
  • VPC sharing: same organization only; owner controls network resources and pays for gateways and endpoints; participants run workloads and own security groups; shared security groups since 2024; fewer VPCs and attachments.
  • Addressing: /16 to /28, 5 reserved per subnet, no mixing RFC 1918 blocks, 100.64.0.0/10 always addable; IPAM pools, rules and overlap monitoring within a scope.
  • Overlaps: service-level access (PrivateLink, Lattice); private NAT gateway (outbound only, with a load balancer for inbound); Transit Gateway or Cloud WAN 1:1 NAT (stateless, both sides for identical CIDRs); longest prefix routing for partial access; re-address or IPv6 long term.
