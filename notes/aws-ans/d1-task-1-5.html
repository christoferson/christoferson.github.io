Overview

Task 1.5

Design a routing strategy and connectivity architecture between on-premises networks and the AWS Cloud.

This is the heaviest hybrid task in the exam. Questions give you bandwidth, latency, encryption, resilience and cost requirements and ask for the right mix of Direct Connect, Site-to-Site VPN and gateways. Others give a routing problem, such as traffic returning over the wrong link or a BGP session dropping, and ask which BGP attribute, community or limit explains it. The details matter: which virtual interface type takes jumbo frames, which gateway supports ECMP, and which route wins when Direct Connect and VPN advertise the same prefix.

The travel company runs two data centers, one in the US and one in Europe. Its network account, 111111111111, owns a Direct Connect gateway and Transit Gateways in us-east-1, eu-central-1 and ap-northeast-1. Card-data traffic must be encrypted on every link, the booking platform needs 10 Gbps or more to each data center, and 60 small sales offices around the world run an SD-WAN.

Routing fundamentals

Knowledge 1.5.1Routing fundamentals (for example, dynamic compared with static, BGP)

Static compared with dynamic routing

A static route is typed in and stays until someone removes it, even if the path behind it is dead. A dynamic route is learned from a routing protocol and withdrawn when the neighbor stops advertising it, which is what makes automatic failover work. On AWS the routing protocol for hybrid links is BGP:

  • Direct Connect virtual interfaces always use BGP.
  • Site-to-Site VPN offers static or dynamic (BGP). AWS recommends BGP for its liveness detection; ECMP, VPN Concentrators and Cloud WAN VPN attachments need it.
  • Transit Gateway Connect needs BGP and accepts no static routes.

BGP basics on AWS

BGP peers exchange prefixes with attributes, and every hybrid session on AWS is eBGP between two different autonomous systems (ASNs):

  • Customer ASN: a public ASN you own, or a private one (64512–65534, or 4-byte 4200000000–4294967294). It must differ from the AWS side. You can reuse it on many VIFs and VPNs.
  • Amazon-side ASN: set when you create a virtual private gateway (VGW), Transit Gateway or Direct Connect gateway, default 64512. A VGW's ASN cannot be changed after creation. Public VIFs peer with AWS ASN 7224.
  • Reserved customer ASNs for VPN: 7224 everywhere, plus 9059 (eu-west-1), 10124 (ap-northeast-1) and 17943 (ap-southeast-1).
  • Loop prevention: a route whose AS_PATH contains 7224 twice or more is dropped. Do not re-advertise routes learned from AWS back to AWS.

Which route wins

Hybrid designs fail most often because a route the designer expected to lose actually wins. Each AWS routing table has its own order.

VPC route table

The local route always wins, then the longest prefix. For an identical prefix, a static route (to an internet gateway, VGW, Transit Gateway, interface or peering) beats a prefix-list route, which beats a propagated route. Among propagated routes from a VGW: Direct Connect BGP, then VPN static, then VPN BGP.

Virtual private gateway

For identical prefixes, a healthy tunnel endpoint comes first, then: Direct Connect BGP routes, then VPN static routes, then VPN BGP routes. Between BGP VPNs, the shortest AS_PATH wins, then the lowest MED. The Direct Connect FAQ puts it plainly: the Direct Connect path is always preferred when established, regardless of AS path prepending.

Transit Gateway route table

Most specific route first. For the same prefix, by attachment type, in this order:

  1. Static routes (including static routes to a VPN)
  2. System routes (1:1 NAT)
  3. Prefix-list referenced routes
  4. VPC-propagated routes
  5. Direct Connect gateway-propagated routes
  6. Transit Gateway Connect-propagated routes
  7. VPN over private Direct Connect
  8. Site-to-Site VPN-propagated routes
  9. VPN Concentrator routes
  10. Client VPN routes
  11. Peering (Cloud WAN) routes

Within one attachment type: shorter AS_PATH, then lower MED, then eBGP over iBGP. Routes with no MED get 0 on Direct Connect and 100 on VPN and Connect. The route table shows only the winner, so a backup VPN route appears only after the Direct Connect route is withdrawn.

"Direct Connect primary, VPN backup" on a Transit Gateway works only if the VPN uses BGP. A static route to the VPN attachment beats every propagated route, so all traffic would go over the VPN. To make a VPN win over Direct Connect on purpose, advertise a more specific prefix over it; longest prefix is checked before anything else.

Timers and failure detection

  • BGP timers on Direct Connect default to hold 90 seconds and keepalive 30 seconds (minimums 3 and 1). You set them on your router; AWS negotiates to match. Transit Gateway Connect uses keepalive 10 and hold 30.
  • BFD on Direct Connect is enabled on the AWS side of every VIF, with a 300 ms interval and multiplier 3 (about 900 ms detection), but takes effect only when you configure it on your router. Transit Gateway Connect does not support BFD or graceful restart.
  • MD5 authentication is always on for Direct Connect BGP; you supply the key or AWS generates one.
  • Dead peer detection on VPN tunnels defaults to a 40-second timeout (minimum 30).

Physical interconnects

Knowledge 1.5.2Layer 1 and layer 2 concepts for physical interconnects (for example, VLAN, link aggregation group [LAG], optics, jumbo frames)

Dedicated and hosted connections

Dedicated connection

A physical port on an AWS device at a Direct Connect location, at 1, 10, 100 or 400 Gbps. The speed cannot be changed; order a new connection instead. Ordering:

  1. RequestIn the console (Connection wizard or Classic) or API. AWS provisions a port, which can take up to 72 business hours.
  2. LOA-CFADownload the Letter of Authorization and Connecting Facility Assignment, which names the patch panel and strands.
  3. Cross connectYour colocation provider or network partner uses the LOA-CFA to run fiber from your router to the AWS port. With no equipment at the location, use a Direct Connect Partner.
  4. BillingPort hours start when the port goes active or 90 days after the LOA is issued, whichever comes first, and are charged even with no traffic.

Hosted connection

A sub-rate connection provisioned by a Direct Connect Partner on its own port, at 50 Mbps up to 25 Gbps (1 Gbps and above only from qualifying partners; 25 Gbps only where 100G ports exist). You accept it in your account and billing starts then. It carries one VIF only, only the partner can change its speed, traffic above the rate is dropped, and it does not support MACsec or LAG.

Optics and layer 1

All dedicated ports use single-mode fiber: 1000BASE-LX (1310 nm) for 1 Gbps, 10GBASE-LR (1310 nm) for 10 Gbps, 100GBASE-LR4 for 100 Gbps and 400GBASE-LR4 for 400 Gbps. Your router must support 802.1Q VLANs, BGP and BGP MD5. Whether auto-negotiation must be on or off depends on the Direct Connect endpoint serving the port, so check it when a new link will not come up. Physical health shows in the CloudWatch metrics for connection state and optical light levels (Task 1.4).

VLANs and virtual interfaces

Each virtual interface (VIF) is an 802.1Q VLAN (1–4094, fixed after creation; on hosted connections the partner chooses it) with its own BGP session. Configure the BGP peer IP on the VLAN subinterface, not the physical interface. Each VIF runs one BGP session per address family: IPv4 (you choose or AWS assigns the /30 or /31 peer addresses) and IPv6 (AWS allocates a /125).

Private VIF

Reaches VPCs by private IP. It attaches either to one VGW (one VPC, same Region) or to a Direct Connect gateway (up to 20 VGWs in any account and any Region except China). Up to 50 private or public VIFs per dedicated connection.

Transit VIF

Attaches only to a Direct Connect gateway, which associates with Transit Gateways (up to 6) or a Cloud WAN core network. Up to 4 per dedicated connection (within a combined limit of 51), and available on hosted connections of any speed.

Public VIF

Reaches all AWS public endpoints in all public Regions (not China), such as S3, DynamoDB and public VPN endpoints. You must use public IP addresses you own and advertise 1 to 1,000 prefixes. AWS filters inbound traffic by source against those prefixes. It does not give internet access.

Hosted VIF

A VIF that a connection owner creates on their own connection for another account, which must accept it. Not to be confused with a hosted connection, which is a whole partner-provisioned connection.

MTU and jumbo frames

  • Private VIF: 1500 or 9001.
  • Transit VIF: 1500 or 8500, the Transit Gateway maximum.
  • Public VIF: 1500 only.
  • Site-to-Site VPN: 1446 maximum inside the tunnel, no jumbo frames.

Jumbo frames apply only to routes propagated over Direct Connect (and static routes through a Transit Gateway). If two private VIFs advertise the same route with different MTUs, or a VPN advertises it too, the path uses 1500. Changing a VIF's MTU can update the connection and interrupt all its VIFs for up to 30 seconds; check that the connection is "Jumbo Frame Capable" first. On hosted connections, jumbo frames work only if the partner's parent connection has them enabled. A Transit Gateway does not support Path MTU Discovery for traffic arriving over Direct Connect, so set the MTU on both ends rather than relying on it.

Create a jumbo-frame transit VIF on the US data center's 10 Gbps connection (AWS CLI; the router uses AS 65010) 
aws directconnect create-transit-virtual-interface \
  --connection-id dxcon-us1a \
  --new-transit-virtual-interface '{
    "virtualInterfaceName": "us-dc1-transit-a",
    "vlan": 101,
    "asn": 65010,
    "mtu": 8500,
    "authKey": "REPLACE_WITH_MD5_KEY",
    "addressFamily": "ipv4",
    "amazonAddress": "169.254.20.1/30",
    "customerAddress": "169.254.20.2/30",
    "directConnectGatewayId": "dxgw-travel-global"
  }'

Link aggregation groups (LAG)

A LAG bundles dedicated connections into one logical connection using LACP:

  • All members must be dedicated, the same speed, and terminate on the same AWS device at one location. No hosted connections, no static bundles, no multi-chassis LAG.
  • Up to 4 members below 100 Gbps; up to 2 at 100 or 400 Gbps. All members are active.
  • Minimum links (default 0): if fewer members are up, the whole LAG goes down, so BGP fails over to another LAG or location instead of squeezing all traffic onto the survivors.
  • There is no extra charge for a LAG.

A LAG adds bandwidth, not device resilience: every member is on the same AWS device. For resilience, use separate connections on separate devices and locations, as in Redundant hybrid design.

Encapsulation and encryption

Knowledge 1.5.3Encapsulation and encryption technologies (for example, Generic Routing Encapsulation [GRE], IPsec)

Direct Connect is private but not encrypted. Encryption on a hybrid link comes from one of three places: MACsec at layer 2, IPsec at layer 3, or the application (TLS).

Site-to-Site VPN (IPsec)

Each VPN connection has two tunnels to two AWS endpoints in different Availability Zones. AWS uses route-based VPNs only; the traffic selectors (default 0.0.0.0/0) are only sent in the IKE phase 2 proposal. The customer gateway device needs a static public IP (or the IP of the NAT in front of it) and must allow UDP 500 and, with NAT traversal, UDP 4500. It can authenticate with a pre-shared key or an AWS Private CA certificate; with certificates, the customer gateway does not need a fixed IP address.

Termination options

  • Virtual private gateway: one VPC, IPv4 only, no ECMP (one tunnel is used across all VPNs on the gateway), up to 100 routes from the customer gateway.
  • Transit Gateway: many VPCs, IPv4 or IPv6 inside and outside the tunnel, ECMP across tunnels with BGP, up to 1,000 routes in and 5,000 out.
  • Cloud WAN: create an unassociated VPN, then attach it to a core network edge. BGP only, and the attachment lives in the core network owner's account.

Tunnel options worth knowing

  • IKE versions: IKEv1 and IKEv2 by default; AWS recommends IKEv2.
  • Inside tunnel CIDR: a /30 from 169.254.0.0/16 (IPv6: a /126 from fd00::/8). It must be unique per VGW, but not per Transit Gateway. Some /30s are reserved, such as 169.254.0.0/30 through 169.254.5.0/30.
  • Phase 1 lifetime 28,800 seconds and phase 2 lifetime 3,600 seconds by default, with a rekey margin of 270 seconds.
  • Encryption AES128, AES256 and the GCM variants; integrity SHA1 or SHA2; DH groups 2 and 14–24 (group 5 in phase 2 only). Restrict the lists to the strong ones.
  • DPD timeout action: clear (default), none or restart. Startup action: add (default, your device starts IKE) or start (AWS starts it; IKEv2 only).
  • The pre-shared key can be stored in Secrets Manager.
  • Tunnel bandwidth: Standard (up to 1.25 Gbps, 140,000 packets per second per tunnel) or Large (up to 5 Gbps, 400,000 packets per second).
VPN from the European data center to the eu-central-1 Transit Gateway: BGP, IKEv2, AWS-initiated, restart on dead peer (AWS CLI) 
aws ec2 create-vpn-connection --region eu-central-1 \
  --type ipsec.1 \
  --customer-gateway-id cgw-eu-dc1 \
  --transit-gateway-id tgw-eu \
  --options '{
    "StaticRoutesOnly": false,
    "TunnelOptions": [
      { "TunnelInsideCidr": "169.254.30.0/30",
        "IKEVersions": [{"Value": "ikev2"}],
        "Phase1EncryptionAlgorithms": [{"Value": "AES256-GCM-16"}],
        "Phase2EncryptionAlgorithms": [{"Value": "AES256-GCM-16"}],
        "Phase1DHGroupNumbers": [{"Value": 20}],
        "Phase2DHGroupNumbers": [{"Value": 20}],
        "StartupAction": "start",
        "DPDTimeoutAction": "restart" },
      { "TunnelInsideCidr": "169.254.30.4/30",
        "IKEVersions": [{"Value": "ikev2"}],
        "StartupAction": "start",
        "DPDTimeoutAction": "restart" }
    ]
  }'

MTU and MSS inside IPsec

The tunnel supports at most 1446 bytes MTU and 1406 bytes MSS, with no jumbo frames and no Path MTU Discovery. The exact values depend on the algorithms: AES-GCM without NAT traversal allows the full 1446/1406; AES-CBC with SHA2-512 and NAT traversal drops to 1406/1366. AWS recommends clamping MSS, clearing the DF bit and fragmenting before encryption on the customer gateway.

Large Bandwidth Tunnels

Up to 5 Gbps per tunnel, on Transit Gateway and Cloud WAN only, priced at $0.60 per connection-hour against $0.05 for a standard VPN (US East, Ohio). Both tunnels must use the same setting, the customer gateway needs a fixed IP, acceleration is not supported, and a few Regions do not offer it. Since May 2026 the bandwidth of an existing VPN can be changed. For more than 5 Gbps, ECMP across several connections: two connections give four tunnels, about 20 Gbps.

Accelerated VPN

Tunnels enter AWS at the edge location nearest the customer gateway through two AWS-managed Global Accelerator accelerators, which helps distant sites on poor internet paths. Transit Gateway only (not VGW). It needs NAT traversal and requires the customer gateway to initiate IKE. Acceleration cannot be turned on or off on an existing VPN, and it cannot be used over a public VIF. Extra cost: two accelerator hourly fees plus premium data transfer.

Private IP VPN over Direct Connect

IPsec from your router over a transit VIF to a Transit Gateway, with private outside addresses on both ends. Give the Transit Gateway a CIDR block and include that block in the Direct Connect gateway's allowed prefixes. Compared with IPsec over a public VIF, it needs no public IPs, does not open all AWS public endpoints to the data center, and scales to more routes. The VPN and Direct Connect attachments can use different Transit Gateway route tables, so encrypted and unencrypted traffic can run side by side. It does not support acceleration or VPN Concentrators.

MACsec

IEEE 802.1AE encryption at layer 2 on the cross connect between your router and the AWS device. It runs at line rate, which IPsec cannot do at 100 Gbps.

  • Dedicated 10, 100 and 400 Gbps connections at supporting locations, and LAGs. Not 1 Gbps, not hosted connections.
  • 256-bit keys: GCM-AES-256 or GCM-AES-XPN-256 at 10 Gbps; XPN is required at 100 and 400 Gbps.
  • Static CAK mode: you associate a CKN/CAK pair (64 hex characters each), stored in Secrets Manager. Up to three pairs on a keychain allow rotation.
  • Encryption mode should_encrypt (default, falls back to unencrypted) or must_encrypt (no traffic without MACsec).
  • MACsec covers the link to the AWS device only, not end to end.

GRE

Generic Routing Encapsulation wraps one IP packet inside another with a 4-byte GRE header, so an appliance can run BGP and carry many routes over a single tunnel. On AWS, GRE is used by Transit Gateway Connect and Cloud WAN Connect attachments (SD-WAN integration). GRE adds 24 bytes (outer IP plus GRE header), so on a 1500-byte path the tunnel MTU is 1476. GRE is not encrypted: if confidentiality is needed, the appliances must add IPsec, or the transport underneath must already be encrypted.

"Encrypt 100 Gbps of Direct Connect traffic at line rate" points to MACsec. "Encrypt over a 1 Gbps or hosted connection" points to private IP VPN (or IPsec over a public VIF). "Encrypt with no public IP addresses" rules out public VIF IPsec.

Sharing across accounts

Knowledge 1.5.4Resource sharing across AWS accounts

Hybrid links are expensive, so one network account usually owns them and every workload account uses them. Each piece has its own sharing method.

Transit Gateway through AWS RAM

The network account shares the Transit Gateway with accounts or the whole organization (it can also go to accounts outside the organization). Participants attach their own VPCs. With auto accept shared attachments off, the owner approves each attachment. Only the owner can associate the Transit Gateway with a Direct Connect gateway, and VPN and Connect attachments are created in the owner's account, so the customer gateways and VPNs live with the network team.

Share the us-east-1 Transit Gateway with the whole organization (AWS CLI, from the network account) 
aws ram create-resource-share --region us-east-1 \
  --name tgw-us-east-1-shared \
  --resource-arns arn:aws:ec2:us-east-1:111111111111:transit-gateway/tgw-use1 \
  --principals arn:aws:organizations::999999999999:organization/o-travel1234 \
  --no-allow-external-principals

Direct Connect gateway association proposals

A Direct Connect gateway cannot be shared through RAM. Instead, the owner of the VGW or Transit Gateway sends an association proposal to the gateway's account, and the gateway owner accepts it, optionally overriding the allowed prefixes. The gateway owner stays in control of what reaches the data centers.

A workload account proposes its VGW; the network account accepts with its own allowed prefix (AWS CLI) 
# In workload account 222222222222
aws directconnect create-direct-connect-gateway-association-proposal \
  --direct-connect-gateway-id dxgw-travel-global \
  --direct-connect-gateway-owner-account 111111111111 \
  --gateway-id vgw-0a1b2c3d4e5f60789 \
  --add-allowed-prefixes-to-direct-connect-gateway cidr=10.60.0.0/16

# In network account 111111111111
aws directconnect accept-direct-connect-gateway-association-proposal \
  --direct-connect-gateway-id dxgw-travel-global \
  --proposal-id 5e1f7a2b-1111-2222-3333-444455556666 \
  --associated-gateway-owner-account 222222222222 \
  --override-allowed-prefixes-to-direct-connect-gateway cidr=10.60.0.0/16

Hosted VIFs and hosted connections

A connection owner can create a VIF on its connection for another account, which accepts it and owns the VIF. A Direct Connect Partner can provision a hosted connection into your account. Neither is a RAM share.

Cloud WAN core network

Shared through RAM from us-east-1. Participants can create VPC, Transit Gateway route table and Direct Connect gateway attachments, but VPN and Connect attachments must be created in the core network owner's account, and participants cannot change the core network policy.

VPC sharing, prefix lists and DNS

With VPC sharing (inside the organization only), workload accounts launch into the network account's subnets and use its existing gateways and Direct Connect path, with no extra attachments. Managed prefix lists for on-premises ranges can be shared so every account's security groups and route tables stay in step. Resolver forwarding rules for corp.example.com are shared the same way (Task 1.2).

Overlay networks

Knowledge 1.5.5Overlay networks

An overlay is a logical network built from tunnels on top of an underlay that only has to deliver packets between tunnel endpoints. The overlay can carry its own addressing, routing domains and encryption, independent of what the underlay knows. Hybrid examples:

  • IPsec VPN over the internet or over Direct Connect: the underlay is the public internet or a transit VIF; the overlay is the encrypted tunnel with BGP inside.
  • GRE with BGP from an SD-WAN or router appliance to Transit Gateway Connect. The underlay is a VPC attachment or Direct Connect.
  • SD-WAN fabrics: vendor tunnels (usually IPsec) between branches and a headend appliance in a VPC, often with one routing domain (VRF) per business unit.
  • Appliance-to-appliance overlays such as VXLAN between EC2 router instances. AWS has no managed VXLAN termination for hybrid traffic, so both ends are your appliances.

Design concerns

  • MTU: inner MTU = underlay MTU − overhead. GRE takes 24 bytes, IPsec 54 to 94 depending on algorithms and NAT traversal. Clamp TCP MSS on the tunnel, because Path MTU Discovery is often unavailable (not on Transit Gateway VPN, Direct Connect or peering attachments).
  • Routing: the tunnel endpoints themselves must stay reachable through the underlay. If a tunnel's own endpoint address is learned through the tunnel, the tunnel flaps (recursive routing).
  • Failover: overlay failover is only as fast as its keepalives. Tune BGP timers or BFD on the overlay and underlay so they do not fight each other.
  • Source/destination check: turn it off on EC2 appliances that forward traffic for other addresses.

Hybrid requirements

Skill 1.5.1Identifying the requirements for hybrid connectivity

Collect these before choosing anything; each one points toward certain designs.

Bandwidth and packet rate

A standard VPN tunnel gives 1.25 Gbps; a Large Bandwidth Tunnel 5 Gbps; ECMP across Transit Gateway VPNs multiplies that. Above that, or for steady high volume, use Direct Connect at 1 to 400 Gbps, with LAGs for more. Many small sites (under 100 Mbps each) suit a VPN Concentrator.

Latency and consistency

Direct Connect gives predictable latency over a private path; internet VPN varies. Accelerated VPN improves the internet leg for distant sites. SiteLink sends data center to data center traffic across the AWS backbone between Direct Connect locations without passing through a Region.

Encryption and compliance

Decide whether every hop must be encrypted and at what speed: MACsec (10 Gbps and above, dedicated), private IP VPN, or VPN over the internet. Card-data rules usually require it.

Time to deliver

A VPN is up in minutes. A dedicated connection takes weeks (port provisioning, cross connect, carrier circuits). A hosted connection from a partner or AWS Interconnect – last mile (GA April 2026; AWS-managed connection from your premises, attached to a Direct Connect gateway, with BGP and VLANs configured for you) can be faster. Bridge with a VPN while Direct Connect is ordered.

Availability target

The Direct Connect SLA (99.9% or 99.99%) depends on the number of connections and locations; see Redundant hybrid design.

Route scale and addressing

  • Count prefixes in each direction. Private and transit VIFs accept 100 on-premises prefixes per address family by default; since August 2026 prefix controls raise this to up to 1,000 per VIF, from a pool per connection and 10,000 per Direct Connect gateway. Exceeding the allocation puts the BGP session into idle, so summarize.
  • From AWS to on premises: 200 prefixes per Transit Gateway on a transit VIF.
  • A VGW VPN takes 100 routes and a Transit Gateway VPN 1,000.
  • Overlapping on-premises and VPC ranges need NAT (Task 1.6).

What must be reached

Private VPC resources (private or transit VIF, VPN), AWS public endpoints (public VIF, or interface endpoints over a private path), one VPC or hundreds (VGW, Direct Connect gateway, Transit Gateway, Cloud WAN), one Region or many.

Cost

Direct Connect charges port hours (for example $2.25 per hour for 10 Gbps dedicated) and data transfer out (for example $0.02 per GB within the US); data in is free. Flat-rate pricing (September 2026) bundles data transfer into a fixed hourly fee for 10 and 100 Gbps port pairs. VPN costs $0.05 per connection-hour plus internet data transfer out. Transit Gateway adds attachment-hours and per-GB processing.

"Connectivity needed tomorrow, Direct Connect in six weeks" points to VPN now, Direct Connect later, VPN kept as backup. "Hundreds of VPCs in several Regions over one connection" points to a transit VIF, Direct Connect gateway and Transit Gateways.

Redundant hybrid design

Skill 1.5.2Designing a redundant hybrid connectivity model with AWS services (for example, AWS Direct Connect, AWS Site-to-Site VPN)

Direct Connect resiliency models

The Direct Connect Resiliency Toolkit (Connection wizard) orders connections to a model. It enforces equal speeds and keeps connections off the same device.

Maximum resiliency (99.99% SLA)

Separate connections on separate devices in more than one location. It survives device, connection and whole-location failure. To qualify for the SLA you need at least 4 connections, at least 2 in each of at least 2 locations, each on its own AWS device. You also need Enterprise Support and a completed Well-Architected Review with an AWS solutions architect.

High resiliency (99.9% SLA)

One connection at each of two locations. It survives a fiber cut, device failure or a location outage, but you are down to one link during maintenance.

Development and test

Separate connections on separate devices at one location. No protection against losing the location.

A single connection (a LAG counts as one) has a 95% SLA. Hosted connections and hosted VIFs from partners are not covered by the SLA.

Building blocks for resilience

  • Use a single Direct Connect gateway. It is a global, distributed route reflector outside the data path, so it is not a single point of failure, and one gateway allows ECMP across transit VIFs.
  • Connect each data center to two locations, through diverse carriers and separate routers.
  • Configure BFD on your routers for sub-second failure detection.
  • Set LAG minimum links so a degraded LAG fails over completely.
  • Make backups carry the load: size each path for the full traffic, or accept degraded service during failover.

VPN as Direct Connect backup

A Site-to-Site VPN to the same VGW or Transit Gateway is a cheap backup. Because Direct Connect routes win, the VPN carries traffic only when the Direct Connect routes are withdrawn. Keep in mind:

  • Use BGP on the VPN (see the trap in Routing fundamentals).
  • The VPN's capacity (1.25 Gbps per tunnel, or 5 Gbps with Large Bandwidth Tunnels) is far below a 10 Gbps link.
  • The MTU drops from 8500 or 9001 to about 1400 during failover; MSS clamping must handle it.
  • Traffic to AWS public services over a public VIF falls back to the internet.
  • A VPN cannot back up Direct Connect for Local Zones; use two Direct Connect connections there.

For VPN-only designs, use two customer gateway devices with a VPN connection each, so four tunnels, with ECMP on a Transit Gateway.

The travel company's design

  1. US data centerTwo 10 Gbps dedicated connections, each at a different Direct Connect location near us-east-1, on separate routers, with MACsec.
  2. European data centerThe same pattern at two locations near eu-central-1. This is the high-resiliency model; the 99.99% SLA needs at least two connections at each of two locations on separate devices, as the resilient Direct Connect architecture builds.
  3. Transit VIFsOne per connection, all to one Direct Connect gateway, which is associated with the Transit Gateways in all three Regions.
  4. VPN backupBGP Site-to-Site VPNs from each data center to its nearest Transit Gateway, used only if all Direct Connect paths fail.
  5. SiteLinkEnabled on the transit VIFs so the two data centers talk across the AWS backbone, replacing a leased line between them.

Proving failover works

Run the Direct Connect BGP failover test, which brings selected BGP sessions down for up to 72 hours (default 180 minutes, and it can be stopped early) and is logged in CloudTrail. AWS Fault Injection Service can also disrupt Direct Connect BGP sessions in a resilience experiment (December 2025). Watch the CloudWatch BGP status and prefix count metrics during the test.

Take one transit VIF's BGP session down for an hour to test failover (AWS CLI) 
aws directconnect start-bgp-failover-test \
  --virtual-interface-id dxvif-us1a \
  --test-duration-in-minutes 60

# End early if traffic does not fail over as expected
aws directconnect stop-bgp-failover-test --virtual-interface-id dxvif-us1a

Two connections to the same location or on the same device are not "highly resilient", whatever the bandwidth. The exam distinguishes device failure from location failure: only connections in more than one location survive a whole location going down.

Steering traffic with BGP

Skill 1.5.3Designing BGP routing with BGP attributes to influence the traffic flows based on the desired traffic patterns (load sharing, active/passive)

There are two directions, and each is controlled from a different side. You control traffic from on premises to AWS with your own routers' policy on the routes AWS sends you, most commonly local preference. You control traffic from AWS to on premises through the attributes you attach to the routes you advertise to AWS.

AWS to on premises over private and transit VIFs

AWS chooses among your advertisements in this order:

  1. Longest prefix match.
  2. Local preference, which you set with BGP communities. By default AWS prefers Direct Connect locations associated with the same Region.
  3. Shortest AS_PATH (you lengthen it by prepending).
  4. Lowest MED (honored, but AWS does not recommend relying on it).
  5. If everything is equal, ECMP across up to 16 paths.

Local preference communities

Tag your advertisements with 7224:7100 (low), 7224:7200 (medium) or 7224:7300 (high). They must be standard communities, and they are checked before AS_PATH, so they override prepending. They work on private and transit VIFs only.

Active/active (load sharing)

Advertise the same prefixes with the same attributes (same community, same AS_PATH length) on all links. AWS uses ECMP across them; the ASNs in the path do not have to match on a Direct Connect gateway. Across locations associated with different Regions, tag both with the same community, or AWS keeps preferring the local one.

Active/passive

Tag the primary with 7224:7300 and the backup with 7224:7100 (or prepend on the backup, if communities are not an option). AWS also suggests advertising more specific prefixes on the primary. Do the same in the other direction with local preference on your routers, so traffic is symmetric. A stateful firewall in the data center drops traffic that returns on the other link.

Active/passive on the US data center routers: primary link preferred in both directions (Cisco IOS-style; AWS peer 169.254.20.1, Direct Connect gateway AS 64512) 
! Routes sent to AWS: primary gets high local preference at AWS
route-map TO-AWS-PRIMARY permit 10
 set community 7224:7300
route-map TO-AWS-BACKUP permit 10
 set community 7224:7100
!
! Routes received from AWS: prefer the primary for traffic going to AWS
route-map FROM-AWS-PRIMARY permit 10
 set local-preference 200
route-map FROM-AWS-BACKUP permit 10
 set local-preference 100
!
router bgp 65010
 neighbor 169.254.20.1 remote-as 64512
 neighbor 169.254.20.1 password REPLACE_WITH_MD5_KEY
 neighbor 169.254.20.1 fall-over bfd
 address-family ipv4
  network 10.100.0.0 mask 255.255.0.0
  neighbor 169.254.20.1 send-community
  neighbor 169.254.20.1 route-map TO-AWS-PRIMARY out
  neighbor 169.254.20.1 route-map FROM-AWS-PRIMARY in
! The backup router uses the BACKUP route-maps on its own peer

Public VIFs

Local preference communities do not apply. AWS picks by longest prefix and AS_PATH, so advertise more specific prefixes over Direct Connect than to the internet. Use AS_PATH prepending to make a link less preferred. This works only with a public ASN: AWS replaces a private ASN with 7224, which strips the prepends. Control how far your prefixes spread with scope communities:

  • 7224:9100: the local Region only.
  • 7224:9200: all Regions on the continent.
  • 7224:9300 or no tag: global.

In the other direction, AWS tags the prefixes it advertises with 7224:8100 (same Region as the Direct Connect location) and 7224:8200 (same continent), plus NO_EXPORT. Filter on them to accept only nearby AWS prefixes.

Inside AWS routing tables

  • On a Transit Gateway, ECMP across Direct Connect gateway attachments is automatic when prefix, length and AS_PATH match. VPN ECMP is a Transit Gateway option, and Connect ECMP is automatic.
  • There is no ECMP between attachment types (Direct Connect with VPN), across different ASNs (no multipath relax), on VGWs or on VPN Concentrators.
  • Between VPN tunnels on a VGW, AWS picks one; prepend on the tunnel you want as backup only if your device cannot handle asymmetric routing.

Allowed prefixes and summarization

What AWS advertises to your data center over a Direct Connect gateway is set by allowed prefixes:

  • For a VGW association they are a filter: the VPC CIDR is advertised only if an allowed prefix equals or contains it.
  • For a Transit Gateway association the allowed prefixes themselves are advertised, so you can send one summary (such as 10.40.0.0/14 for all us-east-1 VPCs) instead of hundreds of VPC routes. Allowed prefixes must not overlap between Transit Gateways on the same gateway.

On the inbound side, summarize data center routes to stay well under each VIF's prefix allocation. The VirtualInterfaceBgpPrefixesAccepted metric and the ListVirtualInterfaceRoutes API (July 2026) show what was learned.

AS_PATH prepending does not beat a local preference community, and on public VIFs with a private ASN it does nothing at all. A longer prefix beats both. Read the question for which VIF type and which ASN is in use.

SD-WAN integration

Skill 1.5.4Designing for integration of a software-defined wide area network (SD-WAN) with AWS (for example, Transit Gateway Connect, overlay networks)

An SD-WAN connects branches over internet links and builds encrypted overlays between them. To bring AWS into the SD-WAN, put the vendor's virtual appliance (from AWS Marketplace) in a VPC as a headend, or run the SD-WAN on premises over Direct Connect, and exchange routes with AWS dynamically.

Transit Gateway Connect

A Connect attachment rides on a transport attachment, either a VPC attachment (appliance in AWS) or a Direct Connect gateway attachment (appliance on premises). Each Connect peer is a GRE tunnel with two BGP sessions to AWS for redundancy.

  • Addressing: the Transit Gateway GRE address comes from a Transit Gateway CIDR block (up to 5 per gateway, not overlapping VPC or on-premises ranges). The BGP inside addresses are a /29 from 169.254.0.0/16 (optional /125 IPv6), unique on the gateway.
  • BGP: MP-BGP only, eBGP with multihop TTL 2. If you give no peer ASN, the gateway's own ASN is used and the session becomes iBGP. No static routes, BFD or graceful restart.
  • Scale: 4 peers per Connect attachment, up to 5 Gbps and 300,000 packets per second each, up to 20 Gbps per attachment. Appliances that advertise the same prefixes with the same AS_PATH get ECMP.
  • Routes: up to 1,000 from the appliance and 5,000 to it per peer.
  • MTU: 8500 on Connect attachments, with Path MTU Discovery supported for traffic entering on VPC and Connect attachments.
SD-WAN headend in a transport VPC in us-east-1: Connect attachment and one GRE peer (AWS CLI; appliance AS 65030) 
# Connect attachment on top of the transport VPC's attachment
aws ec2 create-transit-gateway-connect \
  --transport-transit-gateway-attachment-id tgw-attach-sdwan-vpc \
  --options Protocol=gre

# GRE peer to the appliance at 10.41.233.10; TGW side from its CIDR block 10.255.10.0/24
aws ec2 create-transit-gateway-connect-peer \
  --transit-gateway-attachment-id tgw-attach-sdwan-connect \
  --transit-gateway-address 10.255.10.100 \
  --peer-address 10.41.233.10 \
  --inside-cidr-blocks 169.254.6.0/29 \
  --bgp-options PeerAsn=65030

The transport VPC's subnet route table needs a route from the Transit Gateway CIDR block (10.255.10.0/24) to the Transit Gateway, and the appliance needs source/destination check off.

Design patterns

Headend in a VPC

Branches build vendor IPsec tunnels over the internet to appliances in a transport VPC, in two Availability Zones. The appliances peer with the Transit Gateway over Connect. Branch routes appear in Transit Gateway route tables, and VPC routes reach the branches without static routes or per-branch VPNs.

On-premises SD-WAN over Direct Connect

The Direct Connect gateway attachment is the transport. GRE runs from the on-premises appliance to a Transit Gateway CIDR address, which must be in the allowed prefixes. This keeps the SD-WAN's own route control across the private link, but GRE adds no encryption.

Cloud WAN

Cloud WAN Connect attachments offer GRE or Tunnel-less Connect (October 2023), where the appliance in a VPC peers BGP directly with the core network edge with no tunnel. That removes GRE overhead and the 5 Gbps per-peer limit: up to 100 Gbps per Availability Zone. Map each SD-WAN VRF to a Cloud WAN segment for end-to-end segmentation. For Tunnel-less, the transport VPC attachment must be in the same segment, so use one appliance interface per segment.

Branches without an SD-WAN appliance in AWS

A VPN Concentrator (November 2025) gives one Transit Gateway attachment for up to 100 low-bandwidth sites: 100 Mbps per site, 5 Gbps total, BGP only, no ECMP. It costs $1.95 per hour plus $0.01 per site-hour, less than 50 separate VPN attachments. Older designs used VPN CloudHub: one VGW where each site, with a unique ASN, learns the other sites' routes.

"SD-WAN appliance must exchange routes dynamically with the Transit Gateway at more than VPN throughput" points to Transit Gateway Connect. "Highest throughput and no tunnel overhead with Cloud WAN" points to Tunnel-less Connect. "Sixty small offices, under 50 Mbps each, fewest attachments" points to a VPN Concentrator.

Key takeaways

  • Routing: BGP everywhere for failover. VPC tables: local, longest prefix, static over propagated, then DX over VPN static over VPN BGP. Transit Gateway: static first, then VPC, DX gateway, Connect, private IP VPN, VPN, Concentrator. A static VPN route beats Direct Connect; a longer prefix beats everything.
  • Direct Connect: dedicated 1/10/100/400 Gbps over single-mode optics with LOA-CFA and cross connect; hosted 50 Mbps–25 Gbps with one VIF. VIFs are 802.1Q VLANs: private (VGW or DX gateway, MTU 9001), transit (DX gateway to Transit Gateways, 8500), public (owned public IPs, 1500).
  • LAG: LACP, same speed, same device, 4 members below 100G or 2 at 100/400G, minimum links for clean failover; bandwidth, not resilience.
  • Encryption: Direct Connect is unencrypted. MACsec for 10G+ dedicated at line rate; private IP VPN over a transit VIF; VPN tunnels 1.25 Gbps (Large 5 Gbps on Transit Gateway or Cloud WAN), MTU 1446; accelerated VPN on Transit Gateway only. GRE adds 24 bytes and no encryption.
  • Sharing: Transit Gateway and Cloud WAN through RAM (VPN and Connect attachments stay with the owner); Direct Connect gateway through association proposals, not RAM; hosted VIFs; VPC sharing inside the organization.
  • Resilience: 99.99% needs 4 connections in 2+ locations on separate devices, Enterprise Support and a Well-Architected Review; 99.9% needs 2 locations; BGP VPN as backup with less bandwidth and smaller MTU; test with the BGP failover test or FIS.
  • BGP steering: communities 7224:7100/7200/7300 set local preference at AWS and beat AS_PATH on private and transit VIFs; public VIFs use prepending (public ASN only) and scope communities 7224:9100/9200/9300; allowed prefixes summarize what AWS advertises; set local preference on your routers for the other direction.
  • SD-WAN: Transit Gateway Connect (GRE plus BGP over a VPC or DX transport, 4 peers of 5 Gbps each); Cloud WAN Tunnel-less Connect with segments per VRF; VPN Concentrator for many small sites.
