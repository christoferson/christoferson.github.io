Overview

Task 2.3

Implement complex hybrid and multi-account DNS architectures.

Task 1.2 explains how Route 53 and the VPC Resolver work; this task is about configuring them. Expect "which record or rule fixes this" questions: a name that returns NXDOMAIN inside the VPC, a failover that never happens for a private endpoint, a DNSSEC rollout that breaks resolution, or a shared rule that does nothing in another account.

The travel company uses example.com publicly (booking site, API, mail), aws.example.com as a private zone for AWS workloads, and corp.example.com in on-premises Active Directory. DNS endpoints live in the network account's shared services VPC in each Region.

Public and private hosted zones

Knowledge 2.3.1When to use private hosted zones and public hosted zones

  • Public hosted zone: answers anyone on the internet, through four Route 53 name servers you give the registrar. Use it for public names, and for records that must be resolvable from anywhere (for example certificate validation TXT records).
  • Private hosted zone: answers only VPCs associated with it (up to 300 per zone directly, more through Profiles), and on-premises clients through an inbound endpoint. Queries are free. It needs enableDnsSupport and enableDnsHostnames on in each VPC. It cannot be DNSSEC-signed, and IP-based routing and Traffic Flow policies are not supported in it.
  • Split-view: a public and a private zone with the same name give different answers inside and outside. Inside, the private zone is used whenever it matches; a missing record returns NXDOMAIN rather than falling back to the public zone, so copy every name internal clients need.
  • Between overlapping private zones (example.com and aws.example.com), the most specific zone wins.

Skill 2.3.1Configuring DNS zones and conditional forwarding

The private zone for AWS workloads, created in the network account and associated with the shared services VPC (AWS CLI) 
aws route53 create-hosted-zone \
  --name aws.example.com \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services \
  --hosted-zone-config PrivateZone=true,Comment="AWS workloads" \
  --caller-reference aws-example-com-2026-11-15

# Add the European shared services VPC to the same zone
aws route53 associate-vpc-with-hosted-zone \
  --hosted-zone-id Z0AWSEXAMPLE1234 \
  --vpc VPCRegion=eu-central-1,VPCId=vpc-shared-services-eu

Delegating a public subdomain to another account

  1. The bookings account creates a public zone bookings.example.com and its records.
  2. The network account adds an NS record named bookings.example.com in the example.com zone, listing the child zone's four name servers (TTL 172800 is typical).
  3. Remove any bookings.example.com records from the parent; duplicates give inconsistent answers.

This lets the bookings team change only its own zone through IAM, while the network team keeps the apex. A reusable delegation set (API or CLI only, chosen when a zone is created) gives many zones the same four name servers, and is the basis for white-label name servers.

Conditional forwarding in both directions is configured in the next section.

Delegation and forwarding

Knowledge 2.3.3DNS delegation and forwarding (for example, conditional forwarding)

Resolver rule types

  • FORWARD (conditional forwarding): queries for a domain and its subdomains go through an outbound endpoint to target resolvers (up to 6 IPs, with port and protocol each).
  • SYSTEM: carves a subdomain out of a forward rule so the VPC Resolver answers it, for example forward example.com but keep aws.example.com local.
  • RECURSIVE: the built-in internet resolver rule for everything else; it cannot be created or deleted.
  • DELEGATE (June 2025): follows NS referrals for a delegated subdomain, for example a private zone subdomain delegated to on-premises name servers. The private zone needs the NS records first.

Precedence

The most specific domain wins among rules. A rule beats a private hosted zone for the same name. A forward rule for an autodefined name (such as a reverse zone of the VPC) overrides the autodefined rule. A "." forward rule sends everything except autodefined AWS names to your network.

Inbound delegation

Instead of conditional forwarders, on-premises DNS can delegate a subdomain to the Resolver: create an inbound endpoint with direction INBOUND_DELEGATION (Do53 only) and use its IPs as the NS glue in the parent zone.

Forward the on-premises AD domain and its reverse zone to the data center DNS servers, but keep the AWS subdomain local (AWS CLI) 
aws route53resolver create-resolver-rule --creator-request-id corp-fwd-1 \
  --name corp-forward --rule-type FORWARD --domain-name corp.example.com \
  --resolver-endpoint-id rslvr-out-use1shared \
  --target-ips "Ip=10.100.0.53" "Ip=10.200.0.53"

aws route53resolver create-resolver-rule --creator-request-id corp-rev-1 \
  --name corp-reverse --rule-type FORWARD --domain-name 100.10.in-addr.arpa \
  --resolver-endpoint-id rslvr-out-use1shared \
  --target-ips "Ip=10.100.0.53" "Ip=10.200.0.53"

# example.com is forwarded for legacy names; aws.example.com stays in AWS
aws route53resolver create-resolver-rule --creator-request-id aws-sys-1 \
  --name aws-local --rule-type SYSTEM --domain-name aws.example.com

On premises, conditional forwarders for aws.example.com point at the inbound endpoint IPs (forwarder syntax on Task 2.1). Never forward to the VPC +2 address from outside the VPC.

Records

Knowledge 2.3.4Different DNS record types (for example, A, AAAA, TXT, pointer records, alias records)

  • A and AAAA: IPv4 and IPv6 addresses. Dual-stack names need both.
  • CNAME: points a name at another name; not allowed at the zone apex, and no other record can share its name.
  • Alias (Route 53 only): an A or AAAA (or other type) record that points at an AWS resource (CloudFront, ELB, API Gateway, Global Accelerator, S3 website, interface endpoint, VPC Lattice, and others) or another record in the same zone. Allowed at the apex, free to query for AWS targets, TTL taken from the target, and it follows the target's IP changes.
  • TXT: up to 255 characters per string, several strings per value; used for SPF, DKIM, domain verification (including PrivateLink private DNS names). Publish SPF as TXT, not the SPF type.
  • PTR: reverse lookups, in in-addr.arpa (or ip6.arpa) zones, often needed by AD and mail servers.
  • MX (priority and mail host; the host must be an A or AAAA name), SRV (priority, weight, port, target; used by AD and SIP), CAA (which certificate authorities may issue), NS, SOA, DS (DNSSEC chain), and the newer HTTPS, SVCB, TLSA and SSHFP (2024).

Skill 2.3.4Configuring appropriate DNS records

Apex alias to the CloudFront distribution, SPF and a CAA record for example.com (change batch JSON for change-resource-record-sets) 
{
  "Comment": "Booking site apex, mail policy and certificate policy",
  "Changes": [
    {"Action": "UPSERT", "ResourceRecordSet": {
      "Name": "example.com", "Type": "A",
      "AliasTarget": {"HostedZoneId": "Z2FDTNDATAQYW2",
        "DNSName": "d111111abcdef8.cloudfront.net",
        "EvaluateTargetHealth": false}}},
    {"Action": "UPSERT", "ResourceRecordSet": {
      "Name": "example.com", "Type": "TXT", "TTL": 3600,
      "ResourceRecords": [{"Value": "\"v=spf1 include:amazonses.com -all\""}]}},
    {"Action": "UPSERT", "ResourceRecordSet": {
      "Name": "example.com", "Type": "CAA", "TTL": 3600,
      "ResourceRecords": [{"Value": "0 issue \"amazon.com\""}]}}
  ]
}
  • Add an AAAA alias too if the distribution has IPv6 enabled. Z2FDTNDATAQYW2 is CloudFront's fixed zone ID; a CloudFront alias cannot be created in a private zone, and Evaluate Target Health must stay false for it.
  • For PTR records of AWS servers that on-premises tools look up, create a private zone such as 40.10.in-addr.arpa and associate it with the shared services VPC, or keep the autodefined reverse rules.
  • Change batches are all or nothing; a change reaches every Route 53 name server ("INSYNC") usually within 60 seconds. Record set protection (November 2026) can lock critical records against any change.
  • Automation must respect API throttling: since 2026 Route 53 limits both requests (10 per second) and changes (a bucket refilling at 100 changes per second; UPSERT costs two).

Traffic management

Knowledge 2.3.2Methods to alter traffic management (for example, based on latency, geography, weighting)

  • Weighted (0–255): canary releases and migrations. Weight 0 records serve only if every non-zero record is unhealthy; all zero means equal shares.
  • Latency: the Region with the lowest measured latency from the user to AWS; one record per Region.
  • Failover: primary and secondary; with both unhealthy, the primary is returned.
  • Geolocation: by continent, country or US state; the smallest match wins; add a default record or unmapped users get no answer.
  • Geoproximity: by distance to AWS Regions, Local Zone groups or coordinates, adjusted with a bias of −99 to +99; now available as normal records, without Traffic Flow.
  • IP-based: by the resolver's or client subnet's CIDR, using CIDR collections; public zones only.
  • Multivalue answer: up to 8 healthy values; not a load balancer, and not usable with alias.

Design and failover timing are on Task 1.2; use TTLs of 60 seconds or less on health-checked records.

Skill 2.3.2Configuring traffic management by using DNS solutions

Failover for a private endpoint

Route 53 health checkers are on the internet and cannot reach private IPs. For the private booking API in aws.example.com, alarm on a CloudWatch metric (for example the NLB's healthy host count) and base the health check on the alarm. The alarm must be in the same account, standard resolution, without metric math.

A health check that follows a CloudWatch alarm, used by the primary failover record in the private zone (AWS CLI and change batch JSON) 
aws route53 create-health-check --caller-reference api-use1-alarm-1 \
  --health-check-config 'Type=CLOUDWATCH_METRIC,AlarmIdentifier={Region=us-east-1,Name=booking-api-use1-unhealthy},InsufficientDataHealthStatus=LastKnownStatus'

{"Changes": [
  {"Action": "UPSERT", "ResourceRecordSet": {
    "Name": "api.aws.example.com", "Type": "A",
    "SetIdentifier": "use1-primary", "Failover": "PRIMARY",
    "HealthCheckId": "0f0e0d0c-1111-2222-3333-444455556666",
    "AliasTarget": {"HostedZoneId": "Z26RNL4JYFTOTI",
      "DNSName": "booking-api-use1-0123456789abcdef.elb.us-east-1.amazonaws.com",
      "EvaluateTargetHealth": true}}},
  {"Action": "UPSERT", "ResourceRecordSet": {
    "Name": "api.aws.example.com", "Type": "A",
    "SetIdentifier": "euc1-secondary", "Failover": "SECONDARY",
    "AliasTarget": {"HostedZoneId": "Z3F0SRJ5LGBH90",
      "DNSName": "booking-api-euc1-0123456789abcdef.elb.eu-central-1.amazonaws.com",
      "EvaluateTargetHealth": true}}}
]}

The load balancer zone IDs are per Region (shown on the load balancer as its canonical hosted zone ID). Failover alias records must set Evaluate Target Health to true.

Combining policies

Build trees bottom up with aliases in the same zone: weighted records per Region with health checks, then latency alias records pointing at each Region's weighted name with Evaluate Target Health on. If every record in a Region is unhealthy, Route 53 backs out to the next Region. A record without a health check is always considered healthy. Traffic Flow builds the same trees visually ($50 per policy record per month, public zones only).

DNSSEC

Knowledge 2.3.5DNSSEC

  • Signing (public zones only): you own the key-signing key, backed by a customer managed KMS key that is asymmetric, ECC_NIST_P256, sign and verify, in us-east-1, with a key policy allowing dnssec-route53.amazonaws.com. Route 53 manages the zone-signing key (algorithm 13, rotated every 7–30 days). Up to 2 KSKs per zone. Signed zones cap TTLs at one week.
  • The chain of trust needs a DS record in the parent: at the registrar (for a TLD) or in the parent zone.
  • Validation is separate: turn on DNSSEC validation per VPC for the VPC Resolver. It validates signed public names it resolves itself; forwarded queries are validated (or not) by the target resolver. The VPC Resolver does not return DNSSEC records to clients.
  • Route 53 charges nothing for signing; KMS charges for the key and signing calls.

Skill 2.3.5Configuring DNSSEC on Route 53

  1. PrepareTurn on query logging, lower the zone's maximum TTL to one hour and the SOA TTL and minimum, and wait for the old TTLs to expire.
  2. KMS keyCreate the ECC_NIST_P256 key in us-east-1 with the Route 53 DNSSEC key policy (or let the console create it).
  3. SignCreate an active KSK and enable signing; check the change is INSYNC, then monitor for problems such as devices that truncate DNS responses at 512 bytes.
  4. Chain of trustGet the DS value with get-dnssec and add it to the parent (start with a 300-second DS TTL), then wait for the parent's NS TTL.
  5. MonitorAlarm on DNSSECInternalFailure and DNSSECKeySigningKeysNeedingAction (us-east-1, reported every four hours).
Sign example.com with a new KSK and read back the DS record for the registrar (AWS CLI, us-east-1) 
aws kms create-key --region us-east-1 \
  --key-spec ECC_NIST_P256 --key-usage SIGN_VERIFY \
  --policy file://route53-dnssec-key-policy.json \
  --description "Route 53 DNSSEC KSK for example.com"

aws route53 create-key-signing-key --region us-east-1 \
  --hosted-zone-id Z0EXAMPLECOM1234 \
  --key-management-service-arn arn:aws:kms:us-east-1:111111111111:key/7a1b2c3d-1111-2222-3333-444455556666 \
  --name examplecomksk1 --status ACTIVE --caller-reference ksk-2026-11-15

aws route53 enable-hosted-zone-dnssec --region us-east-1 \
  --hosted-zone-id Z0EXAMPLECOM1234

aws route53 get-dnssec --region us-east-1 --hosted-zone-id Z0EXAMPLECOM1234 \
  --query "KeySigningKeys[0].DSRecord"
Validate DNSSEC for names resolved in the bookings VPC (AWS CLI) 
aws route53resolver update-resolver-dnssec-config \
  --resource-id vpc-bookings-prod --validation ENABLE

To turn signing off, remove the DS record from the parent first and wait for its TTL, then disable signing. Disabling first leaves validating resolvers with a DS record that matches nothing, and they return SERVFAIL. A broken KMS key policy puts the KSK into ACTION_NEEDED and resolution fails once the existing signatures expire.

Sharing DNS between accounts

Knowledge 2.3.6How to share DNS services between accounts (for example, AWS RAM)

  • Resolver rules through RAM: sharing a rule also lets the other accounts use its outbound endpoint. Each account associates the rule with its VPCs; it cannot edit the rule. Rule quotas count against the owner; associations against the consumer.
  • Query logging configurations and DNS Firewall rule groups through RAM: consumers associate their VPCs, and logs go to the owner's destination.
  • Route 53 Profiles through RAM: one association per VPC brings private zones, rules, firewall rule groups, interface endpoints and query logging, and updates reach every VPC. Up to 2 Profiles per VPC (November 2026), with priorities; local VPC settings win for the same name.
  • Private hosted zones are not RAM resources: use association authorization (CLI or API only) or a Profile.
  • Public zones: delegate subdomains to zones in other accounts (above).
Share the forwarding rules and the DNS Profile with the whole organization, and let a workload account's zone be associated with the shared services VPC (AWS CLI) 
aws ram create-resource-share --name dns-shared-use1 \
  --resource-arns \
    arn:aws:route53resolver:us-east-1:111111111111:resolver-rule/rslvr-rr-corpfwd01 \
    arn:aws:route53resolver:us-east-1:111111111111:resolver-rule/rslvr-rr-corprev01 \
    arn:aws:route53profiles:us-east-1:111111111111:profile/rp-travel-dns-01 \
  --principals arn:aws:organizations::999999999999:organization/o-travel1234

# Bookings account (zone owner) authorizes; network account associates
aws route53 create-vpc-association-authorization --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services
aws route53 associate-vpc-with-hosted-zone --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services
aws route53 delete-vpc-association-authorization --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services

Associating workload zones with the shared services VPC lets the inbound endpoint answer them for the data centers.

Inbound and outbound endpoints

Knowledge 2.3.7Requirements and implementation options for outbound and inbound endpoints

  • Both: at least 2 IP addresses (one interface each) in different AZs, up to 6 by default; IPv4, IPv6 or dual-stack; security group fixed at creation; Direct Connect or VPN to the data center (outbound can also use a NAT gateway for public targets). Not in dedicated-tenancy VPCs or in subnets shared with you. One of each per Region is usually enough; scale by adding IPs.
  • Inbound: security group allows TCP and UDP 53 in (443 for DoH); the VPC must be associated with the private zones it should answer; protocols Do53, DoH or DoH-FIPS; optional DNS64; or the delegation category.
  • Outbound: security group allows TCP and UDP out to the target DNS port; protocols Do53 or DoH (with SNI); each rule is tied to one outbound endpoint.
  • Capacity: about 10,000 UDP queries per second per IP, as low as 1,500 with tracked security group rules; add IPs when an interface passes 50% (the ResolverEndpointCapacityStatus metric warns).
  • Cost: $0.125 per IP per hour plus $0.40 per million queries.

Skill 2.3.3Configuring DNS for hybrid networks

Inbound and outbound endpoints in the us-east-1 shared services VPC, with DoH accepted from the data centers (AWS CLI) 
aws route53resolver create-resolver-endpoint --creator-request-id in-use1-1 \
  --name dns-inbound-use1 --direction INBOUND \
  --security-group-ids sg-dns-inbound \
  --ip-addresses SubnetId=subnet-shared-az1,Ip=10.41.0.10 SubnetId=subnet-shared-az2,Ip=10.41.1.10 \
  --protocols Do53 DoH

aws route53resolver create-resolver-endpoint --creator-request-id out-use1-1 \
  --name dns-outbound-use1 --direction OUTBOUND \
  --security-group-ids sg-dns-outbound \
  --ip-addresses SubnetId=subnet-shared-az1 SubnetId=subnet-shared-az2

Then forward rules (above), on-premises conditional forwarders to 10.41.0.10 and 10.41.1.10, and private zone associations with the shared services VPC. For interface endpoints used from on premises, forward their service names to the inbound endpoint as well.

Centralized or distributed DNS

Skill 2.3.6Configuring DNS within a centralized or distributed network architecture

Centralized

One inbound and one outbound endpoint per Region in the network account's shared services VPC, reached by spokes over the Transit Gateway. Rules shared through RAM or a Profile; workload zones associated with the shared services VPC for on-premises resolution. Fewer endpoints to pay for and one place to manage, at the cost of a shared dependency and Transit Gateway traffic.

Distributed

Each account or VPC runs its own endpoints and zones. Suits isolated business units or VPCs without Transit Gateway connectivity, but multiplies endpoint costs and rules.

Rules that keep the centralized design working

  • Do not associate a forwarding rule with the VPC that holds the inbound endpoint it might reach (directly or through on-premises servers): queries loop between the endpoints.
  • Spoke VPCs keep AmazonProvidedDNS in DHCP options; the shared rules forward only what must leave AWS.
  • Endpoints are Regional: repeat the design in each Region, with rules per Region.
  • Profiles avoid the 300 VPCs per private zone limit and the per-VPC authorization steps.

A shared Resolver rule does nothing until the receiving account associates it with its VPCs, and an account moved to an OU the rule is not shared with silently loses those associations.

Monitoring and logging

Skill 2.3.7Configuring DNS monitoring and logging on Route 53

Resolver query logging

Logs queries from associated VPCs, from inbound endpoints and through outbound endpoints, with the DNS Firewall action, to CloudWatch Logs, S3 or Firehose in the same Region. Cached answers are not logged. Share one configuration through RAM so every account logs to the central bucket.

Public query logging

Per public hosted zone, to CloudWatch Logs in us-east-1 only (with a resource policy for Route 53), one log stream per edge location. Only queries that reach Route 53 are logged.

Central Resolver query logs to S3, shared with the organization, and public query logs for example.com (AWS CLI) 
aws route53resolver create-resolver-query-log-config --creator-request-id qlog-use1-1 \
  --name dns-query-logs-use1 \
  --destination-arn arn:aws:s3:::travel-dns-query-logs-use1

aws route53resolver associate-resolver-query-log-config \
  --resolver-query-log-config-id rqlc-0use1central123 \
  --resource-id vpc-shared-services

aws route53 create-query-logging-config --hosted-zone-id Z0EXAMPLECOM1234 \
  --cloud-watch-logs-log-group-arn arn:aws:logs:us-east-1:111111111111:log-group:/aws/route53/example.com

Metrics

  • AWS/Route53 (us-east-1): DNSQueries per public zone, the DNSSEC metrics, and health check metrics such as HealthCheckStatus.
  • AWS/Route53Resolver (per Region): endpoint query volumes, healthy and unhealthy interface counts, ResolverEndpointCapacityStatus, detailed per-IP and per-target metrics (December 2025, opt-in), and DNS Firewall query volumes.
  • DNS Firewall blocks and alerts appear in Resolver query logs; Logs Insights and Contributor Insights find top queried or blocked names.

Key takeaways

  • Public zones answer the internet; private zones answer associated VPCs (both DNS attributes on) and the inbound endpoint. Split-view returns NXDOMAIN for names missing from the private zone; the most specific zone wins.
  • Delegate public subdomains to other accounts with NS records in the parent; reusable delegation sets give zones the same name servers.
  • Rules: FORWARD through an outbound endpoint, SYSTEM to keep a subdomain local, DELEGATE for referrals; most specific wins, and rules beat private zones. Inbound delegation uses endpoint IPs as glue.
  • Records: alias at the apex (free, target TTL, CloudFront zone Z2FDTNDATAQYW2, not in private zones); TXT for SPF and verification; PTR in reverse zones; CAA, SRV, MX.
  • Traffic: weighted, latency, failover, geolocation (with default), geoproximity with bias, IP-based with CIDR collections (public only), multivalue; private endpoints fail over with CloudWatch alarm health checks; nested alias trees with Evaluate Target Health.
  • DNSSEC: KSK on an ECC_NIST_P256 KMS key in us-east-1, DS at the parent, alarm on DNSSEC metrics; remove the DS before disabling; validation is a per-VPC Resolver setting.
  • Sharing: rules, query log configurations, firewall rule groups and Profiles through RAM; private zones by authorization or Profiles.
  • Endpoints: 2 or more IPs in 2 AZs, fixed security groups, about 10,000 queries per second per IP; centralize them in a shared services VPC and avoid rule loops.
  • Logging: Resolver query logs to CloudWatch Logs, S3 or Firehose in-Region; public query logs to CloudWatch Logs in us-east-1; metrics in AWS/Route53 and AWS/Route53Resolver.
