Reference architecture

Global edge: CloudFront and Global Accelerator across Regions

The booking platform now runs active in three Regions, and travellers in the Americas, Europe and Asia should reach the closest healthy one. CloudFront caches what can be cached and fails reads over between origins; a Global Accelerator standard accelerator gives the mobile and corporate API two static IP addresses and moves new connections away from a failed Region in under a minute, without waiting for DNS. This page builds both, compares them with Route 53 latency routing, and shows how to evacuate a Region on purpose.

Scenario and requirements

The travel company (example.com) has finished its multi-Region network, so the booking platform on Amazon EKS now runs in all three Regions: us-east-1 (booking VPC 10.40.8.0/21), eu-central-1 (10.44.8.0/21) and ap-northeast-1 (10.48.8.0/21). Each Region has an internal ALB in front of the pods: booking-alb-use1 from the inbound perimeter page, plus booking-alb-euc1 and booking-alb-apne1 built the same way in the booking account 222222222222.

The inbound page already covers the distribution's TLS, VPC origins, WAF, Shield Advanced and the partner-feed accelerator; this page adds how requests choose a Region, what happens when one fails, and what it costs.

RequirementDesign choice

Images and fare pages stay up if one origin failsOrigin groups with a primary and a secondary origin, failing over on 5xx and timeouts for GET, HEAD and OPTIONS
Mobile app and corporate booking tools need fixed IP addresses for firewall allow listsA Global Accelerator standard accelerator, booking-global, with two static anycast IPs

Operations can drain a Region deliberately for maintenance or a suspected faultTraffic dials, orchestrated by an ARC Region switch plan

Two public names reach the platform. www.example.com and api.example.com serve browsers through CloudFront, as on the inbound page. A new name, mobile-api.example.com, serves the mobile app and the corporate travel tools of large customers, whose security teams allow outbound traffic only to listed IP addresses.

How it works

Three requests show the two edges and a failure.

  1. A traveller in Madrid opens a fare page with images
  2. Nearest POPAWSAn alias for www.example.com resolves to a nearby edge location, where TCP and TLS finish.
  3. POP, then regional edge cacheAWSAn image misses at the POP and is looked up in the larger regional edge cache shared by several POPs.
  4. Origin ShieldAWSOn a second miss it goes to Origin Shield in us-east-1, which every regional edge cache funnels through, so the bucket sees one request instead of one per regional cache.
  5. Origin groupAWSOrigin Shield fetches from the primary bucket in us-east-1. If that returns a 500, 502, 503 or 504, or times out, CloudFront retries the same GET on the secondary bucket in eu-central-1.
  6. A traveller in Osaka books a hotel from the mobile app
  7. Anycast entryAWSmobile-api.example.com resolves to the accelerator's two static IPs. The nearest edge location terminates TCP and opens a second connection across the AWS backbone.
  8. Endpoint group choiceAWSGlobal Accelerator picks the closest healthy endpoint group, Tokyo, at its traffic dial of 100 percent, and the endpoint by weight within it: booking-alb-apne1.
  9. ALB with the client addressAWSThe internal ALB receives the request with the phone's real address preserved, terminates TLS and adds it in X-Forwarded-For. The POST goes to a booking pod.
  10. Tokyo fails
  11. Health turns redAWSThe ALB's target groups lose their healthy targets, so Global Accelerator marks the endpoint unhealthy. It uses the ALB's own target group health checks for this, not its own.
  12. New connections moveAWSIn under a minute, new connections go to the next closest group. The client still uses the same two IPs, so no DNS record changes.
  13. Existing flowsAWSOpen connections are not moved; the app retries on a new one.

Build it

Step 1

Cache policies per path, regional edge caches and Origin Shield

The distribution from the inbound page gets one cache behavior per kind of content. The cache policy sets the cache key and TTLs, and everything in the cache key is also forwarded to the origin, so a lean key means a higher hit ratio:

  • /images/* and /static/*: managed CachingOptimized (no cookies or query strings; TTLs 1 second, 1 day, 1 year).
  • /fares/* (public fare pages, GET only): a custom policy with the route and date query strings in the key and a minimum TTL of 0, so the origin's Cache-Control: s-maxage=60 decides how long a page lives.
  • /api/* (searches with personal prices, logins, bookings): the managed CachingDisabled policy, with all TTLs at 0, and an origin request policy that forwards the headers the API needs without adding them to the key.

With a minimum TTL above 0, CloudFront caches for at least that long even if the origin sends no-store, so one traveller's prices could reach another; CachingDisabled removes that risk.

Uncached does not mean unaccelerated: handshakes end at the POP, CloudFront keeps persistent origin connections, streams from the first byte and stays on the AWS network. Proxy methods (POST, PUT, PATCH, DELETE, OPTIONS) and requests CloudFront judges dynamic skip the regional edge cache and go from the POP straight to the origin.

Origin Shield is set per origin, in the Region with the lowest latency to that origin. The image bucket is in us-east-1, so its Origin Shield is in us-east-1. It is not enabled on the ALB origins, because dynamic requests through Origin Shield are always charged and never served from it.

Image origin with Origin Shield, and the three cache behaviors (CloudFormation YAML, excerpt of the distribution in the booking account) 
Origins:
  - Id: images-use1
    DomainName: travel-images-use1.s3.us-east-1.amazonaws.com
    S3OriginConfig:
      OriginAccessIdentity: ""
    OriginAccessControlId: !Ref ImagesOac
    # one shield layer in the origin's own Region; every regional edge cache funnels through it
    OriginShield:
      Enabled: true
      OriginShieldRegion: us-east-1
CacheBehaviors:
  - PathPattern: /images/*
    # origin group from Step 2
    TargetOriginId: images-og
    ViewerProtocolPolicy: redirect-to-https
    # managed CachingOptimized
    CachePolicyId: 658327ea-f89d-4fab-a63d-7e88639e58f6
  - PathPattern: /fares/*
    TargetOriginId: fares-og
    ViewerProtocolPolicy: redirect-to-https
    CachePolicyId: !Ref FaresCachePolicy
  - PathPattern: /api/*
    TargetOriginId: booking-alb-use1
    ViewerProtocolPolicy: redirect-to-https
    AllowedMethods: [GET, HEAD, OPTIONS, PUT, PATCH, POST, DELETE]
    # managed CachingDisabled: every TTL is 0
    CachePolicyId: 4135ea2d-6df8-44a3-9df3-4b5a84be39ad
    OriginRequestPolicyId: !Ref ApiOriginRequestPolicy

In standard logs, a hit at Origin Shield shows as OriginShieldHit in x-edge-detailed-result-type, which shows whether the layer earns its fee.

Step 2

Origin groups for read failover

An origin group has exactly two origins, a primary and a secondary, and a list of status codes that trigger failover. When the primary returns one of them, CloudFront retries the same request on the secondary. Two traps in the criteria: a failed connection counts only if 503 is selected, and a timeout only if 504 is selected. The company selects 500, 502, 503 and 504.

  • images-og: the image bucket in us-east-1 (primary) and its replica in eu-central-1 (secondary). Each origin uses its own Origin Shield; the secondary has none.
  • fares-og: the VPC origin for booking-alb-use1 (primary) and one for booking-alb-euc1 (secondary)

Speed is set on each origin. With defaults, a dead primary costs 3 connection attempts of 10 seconds, about 30 seconds, before the secondary is tried. The company sets 1 attempt with a 3-second connection timeout on the primaries, so a dead primary costs a viewer a few seconds; an origin that accepts connections but hangs is governed by the response timeout (default 30 seconds), which the fare origins lower too.

Origin groups with failover on 5xx (CloudFormation YAML, excerpt; the primary origins also set ConnectionAttempts: 1 and ConnectionTimeout: 3) 
OriginGroups:
  Quantity: 2
  Items:
    - Id: images-og
      FailoverCriteria:
        StatusCodes:
          # 503 also covers connection failures, 504 covers timeouts
          Quantity: 4
          Items: [500, 502, 503, 504]
      Members:
        Quantity: 2
        Items:
          - OriginId: images-use1
          - OriginId: images-euc1
    - Id: fares-og
      FailoverCriteria:
        StatusCodes:
          Quantity: 4
          Items: [500, 502, 503, 504]
      Members:
        Quantity: 2
        Items:
          - OriginId: booking-alb-use1
          - OriginId: booking-alb-euc1

The limits are why origin groups do not solve the booking problem:

  • Failover happens only for GET, HEAD and OPTIONS (OPTIONS only when it is a cached method). A POST that fails on the primary returns the error to the traveller.
  • There is no sticky state. Every request tries the primary first, so during an outage each request pays the failed attempt before the secondary answers.

For /api/*, the company therefore uses a viewer-request CloudFront Function with a KeyValueStore: it reads a Region cookie set at sign-in and selects the matching ALB origin, so a browser session stays in one Region. A per-Region flag in the KeyValueStore lets operations steer browsers away from a Region (Step 6). The 2026 active-active blog in the references builds this pattern.

"Fail over POST requests between Regions through CloudFront" cannot be done with an origin group. Answers that need write failover point to Global Accelerator, to Route 53 failover or latency records with health checks, or to origin selection in a CloudFront Function.

Step 3

The booking-global accelerator with three endpoint groups

A standard accelerator routes each new connection to the optimal endpoint by location, health and weights; custom routing accelerators map ports to specific EC2 addresses and have no health checks, so they do not fit. The accelerator gets two static anycast IPv4 addresses from two independent network zones; if one is unreachable from a client network, the client retries the other. They stay with the accelerator until it is deleted, so customers list them once.

The Global Accelerator control plane is called in us-west-2, whatever Region the endpoints are in. A listener takes TCP 443; a listener has one endpoint group per Region, and each group here holds that Region's internal ALB.

Accelerator, listener and the three endpoint groups (AWS CLI, booking account, control plane in us-west-2) 
aws globalaccelerator create-accelerator --name booking-global --ip-address-type IPV4 --region us-west-2

# source IP affinity keeps one phone on one Region's ALB for the whole booking
aws globalaccelerator create-listener --accelerator-arn ACCELERATOR_ARN \
  --protocol TCP --port-ranges FromPort=443,ToPort=443 --client-affinity SOURCE_IP --region us-west-2

# one group per Region; ALBs always have the client IP preserved when internal
aws globalaccelerator create-endpoint-group --listener-arn LISTENER_ARN \
  --endpoint-group-region us-east-1 --traffic-dial-percentage 100 \
  --endpoint-configurations EndpointId=arn:aws:elasticloadbalancing:us-east-1:222222222222:loadbalancer/app/booking-alb-use1/ALB_ID,Weight=128,ClientIPPreservationEnabled=true \
  --region us-west-2
aws globalaccelerator create-endpoint-group --listener-arn LISTENER_ARN \
  --endpoint-group-region eu-central-1 --traffic-dial-percentage 100 \
  --endpoint-configurations EndpointId=arn:aws:elasticloadbalancing:eu-central-1:222222222222:loadbalancer/app/booking-alb-euc1/ALB_ID,Weight=128,ClientIPPreservationEnabled=true \
  --region us-west-2
aws globalaccelerator create-endpoint-group --listener-arn LISTENER_ARN \
  --endpoint-group-region ap-northeast-1 --traffic-dial-percentage 100 \
  --endpoint-configurations EndpointId=arn:aws:elasticloadbalancing:ap-northeast-1:222222222222:loadbalancer/app/booking-alb-apne1/ALB_ID,Weight=128,ClientIPPreservationEnabled=true \
  --region us-west-2

Health checks. For ALB and NLB endpoints, Global Accelerator relies on the load balancer's own target group health checks; the endpoint group's --health-check-* and --threshold-count settings apply only to EC2 and Elastic IP endpoints. An ALB counts as healthy only if every target group has a healthy target, so the target group health check should test the real booking path (a /health that checks the database), and an empty spare target group marks the whole Region unhealthy.

Failover rules. When a group has no healthy endpoint with a weight above 0, Global Accelerator sends new connections to another group. If it tries the three closest groups and finds nothing healthy, it fails open and sends traffic to an endpoint in the closest group anyway. Traffic returns about 30 seconds after the endpoint recovers.

WAF. AWS WAF cannot be attached to an accelerator, so each booking ALB gets a Regional web ACL with the same managed rules as the global one on the inbound page. Shield Advanced can protect the accelerator itself, as it does partner-feed.

Step 4

Weights, client affinity and connection behavior

Endpoint weights (0 to 255, default 128) share traffic inside a Region in proportion to weight. For a blue/green release, a green ALB joins the us-east-1 group at a low weight; the update call lists both ALBs. Weight 0 stops new connections to an endpoint without removing it.

Send about 10 percent of us-east-1 connections to the green ALB (AWS CLI, us-west-2) 
# 230 / (230 + 25): roughly 90 percent blue, 10 percent green
aws globalaccelerator update-endpoint-group --region us-west-2 \
  --endpoint-group-arn ENDPOINT_GROUP_ARN_USE1 \
  --endpoint-configurations EndpointId=BLUE_ALB_ARN,Weight=230,ClientIPPreservationEnabled=true EndpointId=GREEN_ALB_ARN,Weight=25,ClientIPPreservationEnabled=true

Client affinity. With affinity NONE (the default), a phone's next connection can land on a different endpoint. SOURCE_IP keeps a client address on the same endpoint, which suits the app's multi-step booking.

Client IP preservation is always on for internal ALBs and on by default for internet-facing ALBs. Security groups see real client addresses, and the traffic bypasses network ACLs and GWLB or Network Firewall inspection in the booking VPC, which the PCI DSS review must accept.

Connection behavior the app team must design for:

  • Idle timeouts are fixed: 340 seconds for TCP, 30 seconds for UDP. TCP keepalives do not count; at least one byte of data must flow, so the app's long-polling connection sends a small heartbeat.
  • TCP fragments are dropped at the edge (UDP fragments are forwarded). Path MTU Discovery must therefore work, and ICMP cannot be blocked at the accelerator, so the endpoint security groups must allow the ICMP "fragmentation needed" message.
  • Pings are answered at the edge, so they say nothing about the path.
Allow ICMP type 3 code 4 (fragmentation needed) for Path MTU Discovery (AWS CLI, booking account, each Region) 
aws ec2 authorize-security-group-ingress --region us-east-1 --group-id sg-0bookingalb \
  --ip-permissions 'IpProtocol=icmp,FromPort=3,ToPort=4,IpRanges=[{CidrIp=0.0.0.0/0,Description=pmtud}]'

Performance comes from TCP termination at the edge: Global Accelerator ends the client's TCP connection at the edge and almost at once opens a new one to the endpoint, so the slow handshakes over a congested last mile are short, and the long haul runs on the backbone. Before launch, the company ran the Speed Comparison Tool (speedtest.globalaccelerator.aws) from test phones in the three continents to compare direct and accelerated downloads.

Step 5

DNS records for both edges

Both edges are reached with Route 53 alias records, which work at the zone apex, answer as normal A records, follow changes in the target's addresses, and are free to query. The fixed hosted zone IDs are Z2FDTNDATAQYW2 for CloudFront and Z2BJ6XQ5FK7U4H for Global Accelerator. CloudFront needs a separate AAAA alias for IPv6, and cannot be an alias target in a private zone.

Alias records for the browser site and the mobile API (Route 53 change batch JSON, public zone example.com) 
{
  "Comment": "Browsers to CloudFront, apps to Global Accelerator",
  "Changes": [
    {"Action": "UPSERT", "ResourceRecordSet": {
      "Name": "www.example.com", "Type": "A",
      "AliasTarget": {"HostedZoneId": "Z2FDTNDATAQYW2", "DNSName": "DISTRIBUTION_DOMAIN.cloudfront.net", "EvaluateTargetHealth": false}}},
    {"Action": "UPSERT", "ResourceRecordSet": {
      "Name": "www.example.com", "Type": "AAAA",
      "AliasTarget": {"HostedZoneId": "Z2FDTNDATAQYW2", "DNSName": "DISTRIBUTION_DOMAIN.cloudfront.net", "EvaluateTargetHealth": false}}},
    {"Action": "UPSERT", "ResourceRecordSet": {
      "Name": "mobile-api.example.com", "Type": "A",
      "AliasTarget": {"HostedZoneId": "Z2BJ6XQ5FK7U4H", "DNSName": "ACCELERATOR_DNS_NAME.awsglobalaccelerator.com", "EvaluateTargetHealth": false}}}
  ]
}
Apply the change batch (AWS CLI, account that owns the zone) 
aws route53 change-resource-record-sets --hosted-zone-id ZONE_ID --change-batch file://edge-aliases.json

EvaluateTargetHealth cannot be true for a CloudFront target,. For the accelerator, failover happens behind the same two IPs, so the record never changes and its TTL does not affect availability. That is the key difference from DNS-based failover, where the worst case is health check detection plus the record TTL plus any extra client caching (Alternatives).

Corporate customers get the two static IPs for their allow lists. The IPs accept only client-initiated connections; outbound calls leave through the centralized egress NAT gateways.

Step 6

Controlled Region evacuation

Health-based failover handles crashes; a degraded but "healthy" Region, maintenance or a drill needs a deliberate move. For the accelerator, the tool is the traffic dial on the endpoint group: 0 to 100 percent of the traffic that would normally go to that Region, default 100. The rest goes to the next closest groups. Dial changes apply to new connections only; existing ones finish naturally.

Evacuate Tokyo, then bring it back in stages (AWS CLI, us-west-2) 
# Tokyo's travellers now go to the next closest healthy group
aws globalaccelerator update-endpoint-group --region us-west-2 \
  --endpoint-group-arn ENDPOINT_GROUP_ARN_APNE1 --traffic-dial-percentage 0

# confirm the dial and the endpoint health
aws globalaccelerator describe-endpoint-group --region us-west-2 \
  --endpoint-group-arn ENDPOINT_GROUP_ARN_APNE1

# after the work: 25, 50, then 100 while watching error rates
aws globalaccelerator update-endpoint-group --region us-west-2 \
  --endpoint-group-arn ENDPOINT_GROUP_ARN_APNE1 --traffic-dial-percentage 25

A traffic dial of 0 is not an off switch for failover. Failover ignores the dial: if the other Regions' endpoints become unhealthy, a Region dialed to 0 can still receive traffic. To keep a Region completely out, set its endpoint weights to 0 or remove the endpoints, and remember the fail-open rule when nothing is healthy.

A real evacuation also touches the KeyValueStore flag for browsers, the database writer Region and EKS capacity elsewhere. The company orchestrates these with an ARC Region switch plan (launched August 2025). Plans run execution blocks in parallel or in sequence, including ARC routing controls, Route 53 health checks, Aurora Global Database, EC2 Auto Scaling, EKS, ECS, manual approval and custom Lambda actions. The dial and the KeyValueStore flag are custom Lambda blocks that run after EKS scales up in the receiving Regions. Region switch has a data plane in each Region, so the plan does not depend on the Region being deactivated. It costs $70 per plan per month.

Shift traffic away from Tokyo with the Region switch plan (AWS CLI) 
aws arc-region-switch start-plan-execution \
  --plan-arn PLAN_ARN \
  --target-region ap-northeast-1 \
  --action deactivate \
  --mode graceful \
  --comment "Tokyo database maintenance, change CHG-REF"

ARC readiness checks, the older way to confirm a Region could take traffic, have been closed to new customers since April 2026; Region switch plan evaluation is the recommended replacement.

Design decisions

Two edges with different jobs

CloudFront stays in front of browsers because it caches, runs WAF at the edge with larger body inspection, and accelerates the uncached API. Global Accelerator serves the app and corporate tools because they need fixed addresses and write failover in seconds. See Task 1.1.

Origin Shield in one Region only, on cacheable origins

One shield in the bucket's Region raises the hit ratio for global viewers. It is billed per 10,000 requests (for example $0.0075 in the US), except those from the regional edge cache in the same Region; on API origins it would only add charges.

Internal ALBs behind both edges

Global Accelerator accepts internal ALBs and CloudFront reaches them as VPC origins, so no booking ALB has a public address. The DNS alternative below would need public ALBs. See Task 1.3.

Cost

The accelerator costs $0.025 per hour (about $18 a month), charged even while disabled, plus a data transfer premium per GB on the dominant direction of each hour's traffic, on top of normal data transfer out. The premium depends on the Region and the edge location, for example $0.015 per GB for North American traffic and $0.035 per GB for some North America and Asia Pacific pairs. Booking traffic is small JSON, so the premium is modest; large downloads belong on CloudFront.

On CloudFront, data transfer from AWS origins (the ALBs and buckets) to CloudFront is free, so the Regions pay no internet data transfer out for this traffic. The company compared pay-as-you-go pricing with the flat-rate plans launched in November 2025 (Business $200 and Premium $1,000 per distribution per month, with no overage charges, and VPC origins included from Business upwards). Flat-rate plans buy predictable bills during sale peaks. See Task 3.3.

Alternatives

Route 53 latency records with health checks

The DNS-only design gives mobile-api.example.com one latency record per Region, each an alias to that Region's (public) ALB with evaluate target health on, so a Region whose ALB has no healthy targets drops out of the answers. Route 53 picks the Region with the lowest latency from AWS's measurements between user networks and Regions. It costs only queries and health checks.

Its weakness is time. Failover takes detection (about 90 seconds with the default 30-second interval and threshold 3, or less with fast 10-second checks) plus the TTL, plus resolvers and clients that cache longer than told. Alias records to an ALB use a fixed 60-second TTL; non-alias records should use 60 seconds or less. Health checks also cannot reach private IPs, so internal endpoints would need CloudWatch alarm-based checks. See Task 1.2.

ARC routing controls on the DNS design

With the DNS design, controlled evacuation uses ARC routing controls: on/off switches that drive Route 53 health checks attached to the records. They are flipped through the cluster's data plane endpoints in five Regions, not by editing records, because the Route 53 control plane runs in us-east-1 while its data plane has a 100 percent SLA. A cluster costs $2.50 per hour, so it fits when DNS failover is already the design.

CloudFront for everything, with Anycast static IPs

CloudFront Anycast static IPs give a distribution a fixed list of 21 addresses that customers can allow, but only for HTTP(S), only with Price Class All and only after AWS approves the request. Write failover still needs origin selection logic.

Testing it

  1. Region evacuation drillIn a quarterly game day, set the Tokyo traffic dial to 0. The Tokyo ALB's RequestCount should fall toward zero as connections close (allow the 340-second idle timeout) while the others rise and error rates stay flat. Return the dial in steps.
  2. Health-based failoverDeregister all staging targets in one Region. describe-endpoint-group should show the endpoint UNHEALTHY, and a client opening new connections should be served elsewhere in under a minute.
  3. Static IP allow listFrom a test network that allows only the two accelerator IPs, run a booking. Block one IP; the client should retry the other.
  4. CloudFront origin failoverMake the staging primary image bucket return 503 (deny CloudFront in its bucket policy) and request an uncached image: it should come from the secondary within the 3-second connection timeout. Send a POST to a failing primary and confirm it does not fail over.
  5. Cache behaviorRequest the same image twice from two continents and check x-edge-detailed-result-type for OriginShieldHit on the second continent.
  6. DNS failover (alternative)If the DNS design is used anywhere, fail its endpoint and read aws route53 get-health-check-status --health-check-id HEALTH_CHECK_ID for the checkers' view, then time how long clients take to follow, including TTL.
  7. Connection limitsOpen an idle TCP connection through the accelerator with keepalives only and confirm it closes after about 340 seconds; with a one-byte heartbeat it stays.
