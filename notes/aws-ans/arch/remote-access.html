Reference architecture

Remote workforce access: Client VPN and Verified Access

The travel company's call-center agents, staff and contractors work from home. Operations staff get full network access through AWS Client VPN, attached directly to the Transit Gateway so their own addresses reach every firewall and log. Everyone else gets per-application, VPN-less access through AWS Verified Access, which checks identity and device health on every request. AWS Network Firewall inspects both paths.

Scenario and requirements

About 2,000 call-center agents and back-office staff work from home, together with contractors from an outsourced support firm. They need four things in us-east-1: the booking console (a web app behind an internal Application Load Balancer in the production booking VPC vpc-bookings-prod, 10.40.8.0/21, bookings account 222222222222), the agent CRM (another web app behind the same ALB), SSH and RDP to servers in AWS and in the data centers (operations staff only), and a reporting database (Amazon RDS for PostgreSQL in the booking VPC). Card data stays in the payments VPC vpc-0payment01 (10.40.48.0/21), which is in PCI DSS scope; no remote user may reach it.

  • Network account 111111111111: endpoint cvpn-endpoint-0ops, attachment tgw-attach-clientvpn, new route table tgw-rtb-remote, and the attached firewall use1-central (tgw-attach-firewall) from Centralized egress.
  • Bookings account 222222222222: Verified Access resources; new subnets in vpc-bookings-prod: Verified Access 10.40.15.0/27 and 10.40.15.32/27, firewall 10.40.15.64/28 and 10.40.15.80/28.
  • Identity: SAML provider travel-idp for Client VPN; IAM Identity Center for Verified Access, with contractors in a contractors-support group. The support firm's laptops are enrolled in the company's CrowdStrike tenant as a contract condition.

How it works

Steps marked AWS happen automatically once configured; the others are actions of a user, a device or a server you run.

  1. An operations engineer opens an SSH session through Client VPN
  2. Connect and authenticateEngineer's laptopThe AWS client presents the device certificate, signs in to the IdP (SAML) and sends the CrowdStrike agent's signed device token. Both authentications must succeed.
  3. Cedar policyAWSThe endpoint verifies the token and evaluates its policy (an operations group and a CrowdStrike score above 70); no traffic flows until it permits. The client gets an address from 10.250.0.0/20 and, with split tunnel, only the endpoint's routes, which route enforcement protects.
  4. Authorization ruleAWSssh 10.40.10.25 is allowed because a rule grants 10.40.8.0/21 to ops-sre. The packet enters tgw-attach-clientvpn with its source 10.250.3.17 unchanged: no source NAT.
  5. Firewall and returnAWStgw-rtb-remote sends it to tgw-attach-firewall, which passes and logs SSH with the real client IP. The reply returns through the same firewall, because tgw-rtb-prod has a static 10.250.0.0/20 to it.
  6. An agent opens the booking console through Verified Access
  7. Browse to the appAgent's browserhttps://console.example.com is a public CNAME to the Verified Access endpoint. No VPN client.
  8. Policy on every requestAWSVerified Access signs the agent in through IAM Identity Center, collects CrowdStrike device claims, filters with AWS WAF and evaluates the group and endpoint policies for each request, logging each decision.
  9. Through the firewall to the ALBAWSThe Verified Access interface forwards the request from its own address (the agent's is in X-Forwarded-For); subnet routes steer it through the same-AZ firewall endpoint both ways.
  10. An analyst queries the reporting database
  11. Connectivity ClientAnalyst's laptopThe client signs the analyst in, tunnels the traffic and resolves the database name; psql connects on port 5432, and the RDS endpoint forwards through the firewall endpoint if the reporting policy permits.

Build it

Step 1

The Client VPN endpoint on the Transit Gateway

A VPC-associated endpoint source-NATs all client traffic to its interface addresses, so downstream firewalls and flow logs see a handful of IPs instead of users. Since April 2026 an endpoint can attach natively to a Transit Gateway: AWS creates an attachment of type client-vpn, there is no hosting VPC, and the client's own address is kept end to end. For an auditor asking "who ran this SSH session", that decides it. The rules:

  • Same Region; the Transit Gateway needs an IPv4 CIDR block (10.255.10.0/24). The client CIDR (/22 to /12, fixed) must not overlap attached VPCs or that block.
  • Up to 5 AZs (AWS picks 2 by default); subnet and Transit Gateway associations cannot be mixed on one endpoint.
  • No security groups (authorization rules only), no route propagation into the endpoint, no inter-Region peering; a RAM-shared Transit Gateway works across accounts.

Authentication combines a client certificate issued only to managed laptops with SAML to the IdP, so neither a stolen password nor a copied configuration file is enough. An ACM server certificate is always required.

Create the operations endpoint on tgw-use1 with mutual plus SAML authentication, split tunnel and route enforcement (AWS CLI, network account) 
# the Resolver inbound endpoint IPs become the clients' DNS servers
# configuration files go out through device management, so the self-service portal is off
aws ec2 create-client-vpn-endpoint \
  --description "Operations remote access" \
  --client-cidr-block 10.250.0.0/20 \
  --server-certificate-arn arn:aws:acm:us-east-1:111111111111:certificate/SERVER_CERT_ID \
  --authentication-options Type=certificate-authentication,MutualAuthentication={ClientRootCertificateChainArn=arn:aws:acm:us-east-1:111111111111:certificate/DEVICE_CA_ID} Type=federated-authentication,FederatedAuthentication={SAMLProviderArn=arn:aws:iam::111111111111:saml-provider/travel-idp} \
  --connection-log-options Enabled=true,CloudwatchLogGroup=/clientvpn/ops,IncludeAuthorizationPolicyContext=true \
  --transit-gateway-configuration TransitGatewayId=tgw-use1,AvailabilityZones=us-east-1a,us-east-1b \
  --split-tunnel \
  --dns-servers 10.41.0.10 10.41.1.10 \
  --client-route-enforcement-options Enforced=true \
  --session-timeout-hours 10 \
  --self-service-portal disabled \
  --transport-protocol udp --vpn-port 443

The AWS CLI reference lists --transit-gateway-configuration (with TransitGatewayId and AvailabilityZones or AvailabilityZoneIds), while the administrator guide's example uses --transit-gateway-id and --availability-zone-list; check your CLI version's help. Add an AZ later with associate-client-vpn-target-network --availability-zone.

Split tunnel keeps home browsing off the company's firewall and NAT bills. On a Transit Gateway endpoint it needs both routes and authorization rules, and any route-table change resets every session, so route changes go into a maintenance window.

Route enforcement makes the AWS client revert any routing-table change that conflicts with the VPN routes, which defeats TunnelVision-style DHCP option 121 injection on hostile Wi-Fi. It needs client 5.2.0 or later (5.3.0 for IPv6) on Windows, macOS or Ubuntu and applies after a reconnect. Its blog describes VPC-associated endpoints, so the company proved it on a test Transit Gateway endpoint first.

Step 2

Routes, authorization rules and Transit Gateway return paths

Three layers must agree: the endpoint route table (what goes into the tunnel), authorization rules (which group reaches which CIDR) and the Transit Gateway route table (where packets go). The payments range is in none of them.

Endpoint routes without a target subnet, and authorization rules per IdP group (AWS CLI, network account) 
# booking VPC, shared services (DNS, directory), both data centers
aws ec2 create-client-vpn-route --client-vpn-endpoint-id cvpn-endpoint-0ops --destination-cidr-block 10.40.8.0/21
aws ec2 create-client-vpn-route --client-vpn-endpoint-id cvpn-endpoint-0ops --destination-cidr-block 10.41.0.0/16
aws ec2 create-client-vpn-route --client-vpn-endpoint-id cvpn-endpoint-0ops --destination-cidr-block 10.100.0.0/16
aws ec2 create-client-vpn-route --client-vpn-endpoint-id cvpn-endpoint-0ops --destination-cidr-block 10.200.0.0/16

# access group IDs are the SAML memberOf values
aws ec2 authorize-client-vpn-ingress --client-vpn-endpoint-id cvpn-endpoint-0ops \
  --target-network-cidr 10.41.0.0/16 --authorize-all-groups
aws ec2 authorize-client-vpn-ingress --client-vpn-endpoint-id cvpn-endpoint-0ops \
  --target-network-cidr 10.40.8.0/21 --access-group-id ops-sre
aws ec2 authorize-client-vpn-ingress --client-vpn-endpoint-id cvpn-endpoint-0ops \
  --target-network-cidr 10.100.0.0/16 --access-group-id network-engineers
aws ec2 authorize-client-vpn-ingress --client-vpn-endpoint-id cvpn-endpoint-0ops \
  --target-network-cidr 10.200.0.0/16 --access-group-id network-engineers

Rules only allow, the longest prefix wins and 0.0.0.0/0 is evaluated last, so a narrower rule for one group removes that range from everyone relying on a broader rule.

The attachment gets its own Transit Gateway route table. Every destination points at the firewall, and returns are pinned to it as in the egress design: the client CIDR propagates only into the firewall table, and spoke and on-premises tables get a static route to the firewall.

The remote-user route table and the return routes (AWS CLI, network account) 
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-remote \
  --transit-gateway-attachment-id tgw-attach-clientvpn

# outbound: each permitted destination goes to the firewall first; no route for 10.40.48.0/21
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-remote \
  --destination-cidr-block 10.40.8.0/21 --transit-gateway-attachment-id tgw-attach-firewall
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-remote \
  --destination-cidr-block 10.100.0.0/16 --transit-gateway-attachment-id tgw-attach-firewall

# after inspection the firewall table must know how to reach the clients
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-firewall \
  --transit-gateway-attachment-id tgw-attach-clientvpn

# replies from production and the data centers are inspected too (repeat for tgw-rtb-shared)
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.250.0.0/20 --transit-gateway-attachment-id tgw-attach-firewall
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-onprem \
  --destination-cidr-block 10.250.0.0/20 --transit-gateway-attachment-id tgw-attach-firewall

The 10.41.0.0/16 and 10.200.0.0/16 routes follow the same pattern; tgw-rtb-pci gets no route to the client range. Without source NAT the range must be routable everywhere: spoke VPCs already send 10.0.0.0/8 to the Transit Gateway, and the data centers learn it as a Direct Connect gateway allowed prefix:

Advertise the client range to the data centers over Direct Connect (AWS CLI, network account) 
aws directconnect update-direct-connect-gateway-association \
  --association-id a1b2c3d4-0000-0000-0000-dxgwtgwuse1 \
  --add-allowed-prefixes-to-direct-connect-gateway cidr=10.250.0.0/20

Target security groups now see client addresses and cannot reference a Client VPN group: jump hosts allow TCP 22 and 3389 from 10.250.0.0/20, and the Resolver inbound endpoint's group gets a rule for port 53 from it.

Step 3

Device posture and the Cedar authorization policy

Since October 2026 an endpoint can register device trust providers (CrowdStrike, Jamf, JumpCloud). The AWS client reads a signed token from the provider's existing agent; Client VPN checks the signature against the public key URL and rejects other tenants' tokens.

Register the company's CrowdStrike tenant on the endpoint (AWS CLI, network account) 
aws ec2 modify-client-vpn-endpoint \
  --client-vpn-endpoint-id cvpn-endpoint-0ops \
  --device-posture-options 'TrustProviders=[{TrustProviderType=crowdstrike,TenantId=CROWDSTRIKE_TENANT_ID,PublicSigningKeyUrl=CROWDSTRIKE_KEY_URL}],Enabled=true'

Device claims and identity share one Cedar context, so one expression can require both. The endpoint's single policy is evaluated at connect time and for each refreshed token, about every five minutes; a deny disconnects the session. Stale claims are reused for up to 15 minutes, then a device-based policy denies.

ops-access.cedar: the operations groups on a healthy CrowdStrike-managed device 
permit(principal, action, resource)
when {
  (context.saml.memberOf.contains("ops-sre") || context.saml.memberOf.contains("network-engineers"))
  && context.crowdstrike.assessment.overall > 70
};
Attach the policy in shadow mode first, then enforce (AWS CLI, network account) 
# shadow mode evaluates and logs every connection but blocks nothing
aws ec2 modify-client-vpn-endpoint-authorization-policy \
  --client-vpn-endpoint-id cvpn-endpoint-0ops \
  --policy-document file://ops-access.cedar \
  --description "Ops groups with CrowdStrike score above 70" \
  --shadow-mode enabled

# after a week of clean logs
aws ec2 modify-client-vpn-endpoint-authorization-policy \
  --client-vpn-endpoint-id cvpn-endpoint-0ops \
  --shadow-mode disabled

The policy decides whether a connection carries traffic; authorization rules still decide where. Claims differ per provider (CrowdStrike 1–100 scores, Jamf a risk level, JumpCloud only "managed"). The blog does not mention Transit Gateway endpoints, so this too was proven on a test endpoint.

Step 4

Verified Access for the booking console and CRM

Agents need two web apps, not a network. Verified Access is an identity-aware reverse proxy that checks every request against Cedar policies, denies by default and logs each decision. An instance holds the trust providers, groups share a policy, and endpoints (load balancer, network interface, network CIDR or RDS) can add their own.

An instance takes one user trust provider plus device providers. IAM Identity Center must be the organization instance in the same Region; contractors are users there. The --policy-reference-name is the prefix used in policies.

The two trust providers; they are then attached to the Verified Access instance (AWS CLI, bookings account) 
aws ec2 create-verified-access-trust-provider \
  --trust-provider-type user --user-trust-provider-type iam-identity-center \
  --policy-reference-name idc

aws ec2 create-verified-access-trust-provider \
  --trust-provider-type device --device-trust-provider-type crowdstrike \
  --device-options TenantId=CROWDSTRIKE_TENANT_ID,PublicSigningKeyUrl=CROWDSTRIKE_KEY_URL \
  --policy-reference-name crwd

The company creates the instance, attaches both providers and an AWS WAF web ACL (16 KB body inspection by default), and creates the agent-apps group. AWS advises naming Identity Center groups by ID, so renames do not break policies.

agent-apps.cedar: agents or contractors, verified email, healthy device (group policy) 
permit(principal, action, resource)
when {
  (context.idc.groups has "AGENTS_GROUP_ID" || context.idc.groups has "CONTRACTORS_GROUP_ID")
  && context.idc.user.email.verified == true
  && context.crwd.assessment.overall > 70
};
One HTTPS endpoint per application on the internal ALB, in dedicated Verified Access subnets (AWS CLI, bookings account) 
# the ACM certificate must match the name users type
aws ec2 create-verified-access-endpoint \
  --verified-access-group-id vagr-0agentapps \
  --endpoint-type load-balancer --attachment-type vpc \
  --domain-certificate-arn arn:aws:acm:us-east-1:222222222222:certificate/CONSOLE_CERT_ID \
  --application-domain console.example.com --endpoint-domain-prefix console \
  --security-group-ids sg-ava-endpoints \
  --load-balancer-options Protocol=https,Port=443,LoadBalancerArn=BOOKING_ALB_ARN,SubnetIds=subnet-ava-az1,subnet-ava-az2

# the CRM endpoint is identical apart from its domain, certificate and an endpoint policy
aws ec2 create-verified-access-endpoint \
  --verified-access-group-id vagr-0agentapps \
  --endpoint-type load-balancer --attachment-type vpc \
  --domain-certificate-arn arn:aws:acm:us-east-1:222222222222:certificate/CRM_CERT_ID \
  --application-domain crm.example.com --endpoint-domain-prefix crm \
  --security-group-ids sg-ava-endpoints \
  --load-balancer-options Protocol=https,Port=443,LoadBalancerArn=BOOKING_ALB_ARN,SubnetIds=subnet-ava-az1,subnet-ava-az2 \
  --policy-document 'permit(principal, action, resource) when { context.idc.groups has "AGENTS_GROUP_ID" };'

The CRM endpoint policy narrows access to employees: a request needs both the group and the endpoint policy to allow it. console and crm become CNAMEs in the public example.com zone.

Step 5

Verified Access for the reporting database (TCP)

Since February 2025 Verified Access also fronts TCP resources (SSH, RDP, databases). Users need the Connectivity Client (Windows x64, macOS), which signs them in, tunnels traffic and handles DNS; TCP endpoint names have no public A record. Its configuration comes from export-verified-access-instance-client-configuration. Requirements include a local IPv6 stack, TPM and WebView2 on Windows, and no other VPN running, so engineers on Client VPN reach the database through Client VPN instead.

A separate group with a stricter policy, then an RDS endpoint for PostgreSQL (AWS CLI, bookings account) 
aws ec2 create-verified-access-group \
  --verified-access-instance-id vai-0travelagents \
  --description "Reporting database" \
  --policy-document 'permit(principal, action, resource) when { context.idc.groups has "ANALYSTS_GROUP_ID" && context.crwd.assessment.overall > 80 };'

aws ec2 create-verified-access-endpoint \
  --verified-access-group-id vagr-0reporting \
  --endpoint-type rds --attachment-type vpc \
  --security-group-ids sg-ava-endpoints \
  --rds-options Protocol=tcp,Port=5432,RdsDbInstanceArn=arn:aws:rds:us-east-1:222222222222:db:reporting-db,SubnetIds=subnet-ava-az1,subnet-ava-az2

Contractors are not analysts, so they never reach the reporting data. TCP policies can also test context.tcp_flow.client_ip. An OIDC provider used for TCP needs native application settings (redirect URI http://localhost:8000).

Step 6

Network Firewall on both paths

Client VPN path. Step 2 already sends remote traffic through use1-central. In AWS's 2024 pattern the firewall saw only the endpoint's NAT addresses; now rules and logs work per client address. A strict-order group drops card data, passes the ports operations need, and leaves the rest to the policy's drop_established default:

A remote-user rule group added to the firewall policy at a priority ahead of the egress rules (AWS CLI, network account) 
aws network-firewall create-rule-group \
  --rule-group-name remote-users --type STATEFUL --capacity 100 \
  --rule-group '{
    "RuleVariables": {"IPSets": {
      "REMOTE_USERS": {"Definition": ["10.250.0.0/20"]},
      "CARD_DATA": {"Definition": ["10.40.48.0/21"]},
      "OPS_TARGETS": {"Definition": ["10.40.8.0/21", "10.100.0.0/16", "10.200.0.0/16"]},
      "DNS_INBOUND": {"Definition": ["10.41.0.10/32", "10.41.1.10/32"]}}},
    "RulesSource": {"RulesString": "drop ip $REMOTE_USERS any -> $CARD_DATA any (msg:\"remote user to card data\"; sid:9100001; rev:1;)\npass tcp $REMOTE_USERS any -> $OPS_TARGETS [22,443,3389] (msg:\"ops admin\"; flow:to_server; sid:9100002; rev:1;)\npass udp $REMOTE_USERS any -> $DNS_INBOUND 53 (msg:\"remote dns\"; sid:9100003; rev:1;)\npass tcp $REMOTE_USERS any -> $DNS_INBOUND 53 (msg:\"remote dns tcp\"; flow:to_server; sid:9100004; rev:1;)"},
    "StatefulRuleOptions": {"RuleOrder": "STRICT_ORDER"}}'

Policy and rule groups must share one rule order. The drop rule is a backstop to the missing routes; PCI DSS assessors like controls at more than one layer.

Verified Access path. Verified Access to an ALB in the same VPC never touches the Transit Gateway. The June 2026 blog inserts firewall endpoints with VPC routing, which needs Verified Access endpoints in dedicated subnets:

  • Verified Access subnets: routes to the ALB and RDS subnets via the same-AZ firewall endpoint.
  • ALB and RDS subnets: routes to each Verified Access subnet via the firewall endpoint in that subnet's AZ, keeping flows symmetric across AZs.
  • Target security groups allow the Verified Access subnet CIDRs; group referencing does not work through a firewall.

This firewall sees Verified Access interface addresses and TLS to the ALB, so it enforces addresses, ports and threat signatures while Verified Access enforces identity and device. Network interface and network CIDR endpoints cannot have a firewall inserted, because they share the target's subnet.

A firewall can sit in front of Verified Access only for HTTP endpoints, which resolve through DNS. TCP endpoints are reached through the Connectivity Client tunnel, so for the database the firewall goes behind Verified Access, as here.

Step 7

Logs and evidence

PCI DSS asks who accessed what and when. Four sources answer it, delivered to the log archive account 777777777777:

  • Client VPN connection logs: user, client IP, times, and an authorization-policy-evaluation object (result, reason, device token status, shadow mode).
  • Transit Gateway flow logs on tgw-attach-clientvpn: flows with real client IPs; match IP and time against the connection log to name the user.
  • Network Firewall alert and flow logs, also keyed by client IP.
  • Verified Access logs (CloudWatch Logs, S3 or Firehose): each request with its identity and device context.
Flow logs on the Client VPN attachment to the central bucket (AWS CLI, network account) 
aws ec2 create-flow-logs --resource-type TransitGatewayAttachment \
  --resource-ids tgw-attach-clientvpn \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::central-flow-logs-111111111111/tgw-clientvpn/

AWS/ClientVPN publishes AuthorizationPolicyDeniedConnections and AuthorizationPolicyTerminatedConnections per endpoint. An alarm on a jump catches an attack or a broken CrowdStrike rollout.

Design decisions

Client VPN for a few hundred, Verified Access for everyone else

Client VPN gives a laptop a route into the network: right for engineers whose SSH, RDP, ping and tools cannot be listed in advance, but a compromised laptop can probe every authorized CIDR. Verified Access exposes one application at a time and checks every request, so a stolen agent session reaches the console and nothing else. Agents use only browsers, which made them easy to move off VPN; the migration and interoperability blog covers running both meanwhile.

Native Transit Gateway attachment rather than a VPN VPC

Benefits: no hosting VPC, real source IPs in every log, one place to route remote users through inspection. Costs: no endpoint security groups, hand-maintained routes, a client range that must be advertised to the data centers, and no Transit Gateway Encryption Support or 1:1 NAT for that attachment (both exclude Client VPN). Other Regions need their own endpoint, since Client VPN traffic does not cross Transit Gateway peering.

Two factors plus device posture

Certificates bind the connection to a managed laptop, SAML to a person and the IdP's MFA, and the Cedar policy adds device health rechecked about every five minutes. Mutual can be combined with SAML or Active Directory, never AD with SAML. Device claims are vendor-specific, so changing vendor means rewriting the policy.

Cost

Client VPN: $0.10 per endpoint association-hour plus $0.05 per connection-hour (how Transit Gateway AZ associations are counted is not stated in the sources used here). Four hundred engineers for 8 hours on 22 days is 70,400 connection-hours, about $3,520 a month; all 2,000 agents on Client VPN would add about $17,600 more. Verified Access bills per application-hour and per GB, not per user. The booking VPC firewall costs $0.395 per endpoint-hour (about $577 a month for two AZs) plus $0.065 per GB; a secondary endpoint of a RAM-shared VPC-based firewall would be $0.158 an hour. Transit Gateway processing ($0.02 per GB) applies to every remote byte through the hub (Task 4.1).

Quotas and limits to plan for

  • Client VPN: 5 endpoints per Region, 200 authorization rules, about 50 Mbps per user; one authorization policy per endpoint.
  • Verified Access: one user trust provider per instance; Connectivity Client on Windows x64 and macOS only.

Alternatives

Site-to-Site VPN from a call-center office

Site-to-Site VPN joins networks, not people: it would suit agents back in a call-center building, not laptops at home. The decision framework blog picks its form by sites and bandwidth: a virtual private gateway for one VPC and few sites, the Transit Gateway or Cloud WAN for many VPCs (1.25 Gbps per tunnel, ECMP to scale), Large Bandwidth Tunnels up to 5 Gbps, a VPN Concentrator for many small sites (Task 1.5).

Client VPN in a dedicated VPN VPC

The pre-2026 pattern, still common in exam questions: endpoint subnets with security groups, source NAT to the endpoint interfaces, then a Transit Gateway onward. Choose it when targets must reference a Client VPN security group; the price is logs that show the endpoint, not users.

Verified Access for SSH and RDP too

TCP network CIDR or network interface endpoints could replace Client VPN for operations, suiting a known host list but not ad hoc troubleshooting across data center ranges. A client connect handler (Lambda) is the older way to vet connections, at connect time only.

Testing it

  1. Prove card data is unreachableReachability Analyzer from tgw-attach-clientvpn to the payments database interface on TCP 5432 should report no path, blocked at tgw-rtb-remote. From a test laptop, 10.40.48.10 should time out with no firewall flow, because the client has no route.
  2. Check source IP preservationSSH to a jump host: its who output, the Transit Gateway flow log and the firewall log should show the same 10.250.x.x address as that user's connection log.
  3. Test group separationAn ops-sre user has the route to a data center host but no authorization rule, so the connection fails; a network-engineers user succeeds.
  4. Break the deviceIn shadow mode, stop the CrowdStrike sensor on a test laptop: the connection log records a deny with shadow mode on while the session stays up. Enforced, the session should drop within about 20 minutes (grace plus refresh) and AuthorizationPolicyTerminatedConnections rise.
  5. Try to leak routesAdd a host route for 10.40.10.25 via the home router; with route enforcement the client should remove it and traffic stay in the tunnel.
  6. Exercise Verified Access policiesA contractor test account should open the console, be refused by the CRM and by the reporting database, with each denial in the Verified Access log.

Troubleshooting checklist. Clients connect but reach nothing: a split-tunnel Transit Gateway endpoint needs a route and an authorization rule, and the spoke must route 10.250.0.0/20 back to the Transit Gateway. Replies vanish: the client CIDR propagated into a spoke table and the return skipped the firewall. One subnet disappears for everyone: a narrower authorization rule for one group. All sessions drop at once: a route change on a split-tunnel endpoint.

"Remote employees need access to a few internal web applications without a VPN, with access decided per request by user identity and device security posture" is AWS Verified Access with an identity trust provider, a device trust provider and Cedar policies. "Administrators need network-level access to many VPCs and on-premises servers, and security tools must see each user's own IP address" is Client VPN associated with the Transit Gateway. A Site-to-Site VPN answer for individual laptops, or security groups on a Transit Gateway-associated Client VPN endpoint, is wrong.
