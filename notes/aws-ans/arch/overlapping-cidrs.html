Reference architecture

Connecting overlapping networks

The travel company bought a hotel booking startup whose VPCs use 10.0.0.0/16, a range one of the company's own development VPCs already uses. No single tool covers every flow. Service-level links (PrivateLink and VPC Lattice) carry the application calls and don't care about addresses. Transit Gateway 1:1 NAT gives operations staff and the migration full two-way routing. Re-addressing from IPAM pools then removes the overlap for good.

Scenario and requirements

The startup's booking platform runs in vpc-hotel-app (10.0.0.0/16, its primary CIDR) in us-east-1. The startup's account has joined the travel company's organization. The company's network, described in Transit Gateway hub and spoke, uses 10.40.0.0/14 in this Region and doesn't overlap the startup. But one legacy development VPC, vpc-dev-legacy, was created long before IPAM and also uses 10.0.0.0/16. It is already attached to tgw-use1, so the Transit Gateway won't propagate the hotel VPC's CIDR, peering would be refused, and neither VPC can send to an address inside its own CIDR (Task 1.6).

The first step is listing the flows, because each overlap tool works in only some directions:

Flow neededPattern chosen
Company booking apps (EKS pods, data center batch jobs) call two hotel APIs, availability and rates, on TCP 443VPC Lattice resource configurations in a service network, reached through a service network endpoint in the shared services VPC
The hotel booking engine calls the company's payment APIA PrivateLink endpoint service in front of the payment API, with an interface endpoint in the hotel VPC
Operations staff in the US data center and the shared services VPC reach any hotel host (SSH, database clients, monitoring)Transit Gateway 1:1 NAT: the hotel VPC appears as 100.65.0.0/16
For the migration period, full two-way routing between the hotel VPC and the company, including integration tests against vpc-dev-legacy1:1 NAT on both overlapping attachments: the development VPC appears as 100.66.0.0/16

The first two flows are permanent; the last two end after re-addressing (Step 6). Values used on this page:

  • Accounts: network account 111111111111 owns tgw-use1 (AS 64521), the shared services VPC (10.41.0.0/16), the Route 53 Profile rp-travel-dns-01 and the service network. Hotel startup account 888888888888 owns vpc-hotel-app and its attachment tgw-attach-hotel-app. The development VPC's attachment is tgw-attach-dev-legacy.
  • Payment API: in the payments VPC vpc-0payment01 (10.40.48.0/21), published as payments-api.example.com.
  • Hotel APIs: availability.hotels.example.com and rates.hotels.example.com, names in the startup's private hosted zone for vpc-hotel-app.
  • NAT CIDRs: 100.65.0.0/16 for the hotel VPC and 100.66.0.0/16 for the development VPC. Both come from 100.64.0.0/10, outside the company's IPAM plan, and avoid the 100.64.0.0/16 that the EKS booking VPC reuses for pods (Task 3.3).

How it works

Steps marked AWS happen automatically once configured; the others are actions of a client or operator.

  1. A booking pod calls the hotel availability API (service level)
  2. Name lookupBooking podThe pod resolves availability.hotels.example.com. The company's copy of the hotels.example.com zone, carried by the Profile, returns a CNAME to the service network endpoint's DNS name for that resource, which answers with addresses in the shared services VPC.
  3. Ordinary routing to the endpointAWSThe connection crosses tgw-use1 to a company address in 10.41.0.0/16.
  4. Lattice to the resource gatewayAWSLattice carries the connection to the resource gateway in vpc-hotel-app. The gateway source-NATs it to its own address, so the hotel VPC replies locally and needs no route to the company.
  5. An operator in the US data center opens SSH to a hotel database host
  6. Translated nameOperatorData center DNS forwards hotels.example.com to the inbound endpoint (10.41.0.10, 10.41.1.10). The company zone returns pms-db.hotels.example.com as 100.65.20.15; the host's real address is 10.0.20.15.
  7. Direct Connect to the hubAWSThe data center learned 100.65.0.0/16 as an allowed prefix on the Direct Connect gateway association. The packet (source 10.100.20.5) enters tgw-use1 and hits the system route for 100.65.0.0/16 in the onprem table.
  8. DNAT on the hotel attachmentAWSThe packet leaves on tgw-attach-hotel-app, whose rule maps 10.0.0.0/16 to 100.65.0.0/16. The destination becomes 10.0.20.15; host bits are kept. The source stays 10.100.20.5, which doesn't overlap.
  9. Stateless returnAWSThe reply enters on the same attachment and the same rule rewrites its source to 100.65.20.15. No session table is involved, so connections can start from either side.
  10. A hotel test runner calls a service in the overlapping development VPC
  11. Both sides translatedAWSA host at 10.0.5.9 in vpc-dev-legacy appears as 100.66.5.9, and the hotel host 10.0.20.15 appears as 100.65.20.15. Each VPC routes the other side's NAT CIDR to the Transit Gateway, and neither ever sees a destination inside its own 10.0.0.0/16.

Build it

Step 1

The payment API to the hotel as a PrivateLink endpoint service

The hotel only ever calls the payment API, never the reverse: PrivateLink's one-way model. The payments team publishes an NLB in front of the API as an endpoint service and allows only the hotel account. The hotel's interface endpoint gets a 10.0.x.x address in its own subnets, and nothing is routed between the VPCs (Task 1.6, PrivateLink).

Publish the payment API and allow only the hotel startup account (AWS CLI, payments account; NLB ARN as a placeholder) 
# acceptance required: the payments team approves each new endpoint
aws ec2 create-vpc-endpoint-service-configuration --region us-east-1 \
  --network-load-balancer-arns PAYMENT_NLB_ARN \
  --acceptance-required \
  --private-dns-name payments-api.example.com

aws ec2 modify-vpc-endpoint-service-permissions --region us-east-1 \
  --service-id vpce-svc-0payments123456789 \
  --add-allowed-principals arn:aws:iam::888888888888:root

# fraud checks need the caller's address: turn on proxy protocol v2 on the target group
aws elbv2 modify-target-group-attributes --target-group-arn PAYMENT_TG_ARN \
  --attributes Key=proxy_protocol_v2.enabled,Value=true

The private DNS name (verified once with a public TXT record) lets hotel code call payments-api.example.com.

Without proxy protocol v2 the payment API sees only NLB node addresses. With it, each connection carries a header with the client address and the consumer's VPC endpoint ID, which targets must parse (health checks included). The client address, such as 10.0.31.7, also exists in the development VPC, so fraud and audit logs key on the endpoint ID.

The hotel's interface endpoint for the payment API (AWS CLI, hotel account) 
aws ec2 create-vpc-endpoint --vpc-endpoint-type Interface \
  --vpc-id vpc-hotel-app \
  --service-name com.amazonaws.vpce.us-east-1.vpce-svc-0payments123456789 \
  --subnet-ids subnet-hotel-app-az1 subnet-hotel-app-az2 \
  --security-group-ids sg-hotel-pay-clients \
  --private-dns-enabled

PrivateLink never lets the provider start connections. Company-to-hotel calls need their own mechanism (Step 2).

Step 2

The hotel APIs to the company through a Lattice service network

Booking pods in several VPCs and data center batch jobs call the two hotel APIs. The hotel shares them as resource configurations, which need no load balancer, behind a resource gateway whose security group controls traffic to the APIs. The API names live in the startup's private hosted zone, so the gateway uses IN_VPC DNS resolution (UDP only, fixed at creation).

Resource gateway and one resource configuration per API (AWS CLI, hotel account; repeat the second command for rates.hotels.example.com) 
aws vpc-lattice create-resource-gateway --name hotel-api-gw \
  --vpc-identifier vpc-hotel-app \
  --subnet-ids subnet-hotel-app-az1 subnet-hotel-app-az2 \
  --security-group-ids sg-hotel-rgw \
  --resource-config-dns-resolution IN_VPC

aws vpc-lattice create-resource-configuration --name hotel-availability \
  --type SINGLE \
  --resource-gateway-identifier rgw-0hotelapi1234567 \
  --resource-configuration-definition 'dnsResource={domainName=availability.hotels.example.com,ipAddressType=IPV4}' \
  --port-ranges 443

The hotel shares both configurations with the network account through AWS RAM. The network account adds them to its service network and creates one service network endpoint in the shared services VPC, because:

  • A VPC association allows only one service network per VPC.
  • An association can't serve traffic that arrives over the Transit Gateway, Direct Connect or VPN.
  • The endpoint takes ordinary addresses from 10.41.0.0/16, which every spoke and both data centers already route to.

The endpoint needs a free, contiguous /28 in each Availability Zone's subnet.

Service network, resource associations and the endpoint in the shared services VPC (AWS CLI, network account) 
aws vpc-lattice create-service-network --name hotel-apis

aws vpc-lattice create-service-network-resource-association \
  --service-network-identifier sn-0hotelapis123456 \
  --resource-configuration-identifier rcfg-0hotelavail12345

aws vpc-lattice create-service-network-resource-association \
  --service-network-identifier sn-0hotelapis123456 \
  --resource-configuration-identifier rcfg-0hotelrates12345

# sg-hotel-api-clients allows TCP 443 from 10.40.0.0/14 and 10.100.0.0/16
aws ec2 create-vpc-endpoint --vpc-endpoint-type ServiceNetwork \
  --vpc-id vpc-shared-services \
  --subnet-ids subnet-shared-az1 subnet-shared-az2 subnet-shared-az3 \
  --service-network-arn arn:aws:vpc-lattice:us-east-1:111111111111:servicenetwork/sn-0hotelapis123456 \
  --security-group-ids sg-hotel-api-clients

Resource configurations are TCP only and Lattice auth policies don't apply to them, so access control is the RAM share and the two security groups.

Step 3

Transit Gateway 1:1 NAT on both overlapping attachments

Operations and the migration need any host, any port, and connections from either side. Transit Gateway 1:1 NAT (October 2026) is a static, stateless, two-way CIDR-to-CIDR translation on an attachment, with no NAT resource or load balancer to deploy. Rules are configured only by the Transit Gateway owner (the network account, though the hotel owns the attachment):

  • MatchSourceCidr is the real range behind the attachment; NatCidr is its translated range.
  • Both must have the same prefix length, and host bits are kept.
  • NAT CIDRs must come from RFC 1918 or 100.64.0.0/10. IPv4 only, up to 50 rules per attachment.
  • NAT can't be enabled on an attachment that uses appliance mode.

Because the hotel VPC and vpc-dev-legacy are identical, both sides are translated. If only the hotel were translated, a development host would reply to 10.0.20.15, an address inside its own CIDR, and the VPC would deliver the reply locally.

One rule per attachment, each matching the full VPC CIDR (AWS CLI, network account) 
aws ec2 modify-transit-gateway-attachment-nat-configuration \
  --transit-gateway-attachment-id tgw-attach-dev-legacy \
  --nat-gateway-support enable \
  --nat-gateway-rules '[{"RuleNumber":100,"MatchSourceCidr":"10.0.0.0/16","NatCidr":"100.66.0.0/16"}]'

aws ec2 modify-transit-gateway-attachment-nat-configuration \
  --transit-gateway-attachment-id tgw-attach-hotel-app \
  --nat-gateway-support enable \
  --nat-gateway-rules '[{"RuleNumber":100,"MatchSourceCidr":"10.0.0.0/16","NatCidr":"100.65.0.0/16"}]'

# asynchronous: wait for NatGatewaySupport enabled and each rule activated
aws ec2 get-transit-gateway-attachment-nat-configuration \
  --transit-gateway-attachment-id tgw-attach-hotel-app

Each rule's MatchSourceCidr exactly equals the VPC CIDR, so the Transit Gateway replaces the VPC's propagated 10.0.0.0/16 route with a system route for the NAT CIDR. This happens in every route table the attachment propagates to. For the same prefix, system routes rank below static routes and above propagated ones. A rule for only part of a VPC translates but installs no route.

Order matters. The development VPC goes first, in a maintenance window: engineers reaching it by real addresses lose that route at once, so its DNS records and data center routes move to 100.66.0.0/16 in the same window. Then the hotel attachment can be propagated with nothing left to conflict with.

Associate the hotel attachment with its own table and propagate it where the NAT CIDR should appear (AWS CLI, network account; repeat the propagation for tgw-rtb-shared, tgw-rtb-onprem and tgw-rtb-dev) 
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-hotel \
  --transit-gateway-attachment-id tgw-attach-hotel-app

aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-hotel-app

tgw-rtb-hotel receives propagations from production, shared services, on premises and tgw-attach-dev-legacy, whose propagated route is now 100.66.0.0/16. Production and development still never meet: the hotel VPC doesn't forward between them.

Step 4

VPC routes, data center routes and filters for the NAT CIDRs

Translation happens only inside the Transit Gateway, so every VPC and router must send the translated ranges to it. Company spokes route 10.0.0.0/8 to the hub, which doesn't cover 100.65.0.0/16, so the VPC template adds the NAT CIDRs.

Routes in a company spoke and in the hotel VPC (AWS CLI; one command per route table) 
# company production spoke: the hotel's translated range goes to the hub
aws ec2 create-route --route-table-id rtb-bookings-app \
  --destination-cidr-block 100.65.0.0/16 --transit-gateway-id tgw-use1

# hotel workload subnets: company Regional summaries, the US data center and the development VPC's NAT CIDR
aws ec2 create-route --route-table-id rtb-hotel-workloads \
  --destination-cidr-block 10.32.0.0/11 --transit-gateway-id tgw-use1
aws ec2 create-route --route-table-id rtb-hotel-workloads \
  --destination-cidr-block 10.100.0.0/16 --transit-gateway-id tgw-use1
aws ec2 create-route --route-table-id rtb-hotel-workloads \
  --destination-cidr-block 100.66.0.0/16 --transit-gateway-id tgw-use1

For the data centers, the Transit Gateway's association with the Direct Connect gateway dxgw-travel-global gets 100.65.0.0/16 and 100.66.0.0/16 as extra allowed prefixes. On a Transit Gateway association, the allowed prefixes themselves are what is advertised to the data center (Task 1.5). The data center firewalls then need rules for the new ranges.

Security groups and network ACLs must allow the translated addresses, because that's what the other side sees:

  • Hotel hosts see company sources by their real addresses, which don't overlap, and see development hosts as 100.66.x.x.
  • Company production servers receiving migration traffic see hotel hosts as 100.65.x.x.

Security group references across the Transit Gateway weren't confirmed to work with translated traffic, so the rules use CIDRs.

Hotel database security group: operations SSH from the data center and the shared services VPC, test traffic from the translated development VPC (AWS CLI, hotel account) 
aws ec2 authorize-security-group-ingress --group-id sg-hotel-db \
  --ip-permissions 'IpProtocol=tcp,FromPort=22,ToPort=22,IpRanges=[{CidrIp=10.100.0.0/16,Description="ops from US data center"},{CidrIp=10.41.0.0/16,Description="ops from shared services"}]' \
  'IpProtocol=tcp,FromPort=5432,ToPort=5432,IpRanges=[{CidrIp=100.66.0.0/16,Description="vpc-dev-legacy via TGW 1:1 NAT"}]'

Network ACLs are stateless too. The Transit Gateway attachment subnets and the workload subnets need inbound and outbound entries for both NAT CIDRs, including the return ephemeral ports 1024–65535. A missing outbound entry looks exactly like a missing route.

Step 5

DNS that answers with the translated addresses

A host now has two correct addresses, depending on who asks. The startup's own hotels.example.com zone, associated with vpc-hotel-app, keeps the real 10.0.x.x answers for hotel clients. The network account creates a second private zone of the same name for the company side. It holds CNAMEs for the two APIs (pointing at the Lattice endpoint names from Step 2) and A records in 100.65.0.0/16 for the hosts operations staff use. The zone goes onto the Profile rp-travel-dns-01, so every company spoke gets it, and it is associated with the shared services VPC so that data center forwarders to the inbound endpoint get the same answers (Hybrid and multi-account DNS).

A translated host record in the company's copy of hotels.example.com (AWS CLI, network account) 
# real address 10.0.20.15; same host bits in the NAT CIDR
aws route53 change-resource-record-sets --hosted-zone-id Z0HOTELSNAT1234 \
  --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{
    "Name":"pms-db.hotels.example.com","Type":"A","TTL":300,
    "ResourceRecords":[{"Value":"100.65.20.15"}]}}]}'

Because host bits are kept, these records are generated from the startup's zone by replacing 10.0 with 100.65. In reverse, a small zone of development names with answers in 100.66.0.0/16 is associated with vpc-hotel-app through cross-account authorization.

Application-level addresses aren't rewritten. A protocol that embeds IP addresses in its payload, or a configuration file that lists 10.0.20.15, still carries the real address after translation. Names, not literal IPs, are what make 1:1 NAT workable.

Step 6

The exit: re-address from IPAM pools and remove the NAT

Translation is a bridge: it adds a per-GB charge, a second set of DNS records and logs where one address means two hosts. The real fix is unique addresses from the company's IPAM pools.

10.0.0.0/16 is the hotel VPC's primary CIDR, and a primary CIDR can't be disassociated. So the hotel platform moves into a new VPC created from the production pool, which gives it the next free block inside 10.40.0.0/16. A VPC whose overlapping range is only a secondary CIDR can instead add a new pool allocation, move its subnets and disassociate the old range.

The hotel's replacement VPC from the shared production pool, then retire the translation (AWS CLI; pool ID as a placeholder) 
# hotel account: IPAM picks a free, non-overlapping block
aws ec2 create-vpc --ipv4-ipam-pool-id PROD_POOL_ID \
  --ipv4-netmask-length 20 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=env,Value=prod},{Key=origin,Value=hotel}]'

# network account, after the old VPC is empty: clear the rules and disable NAT in one call
aws ec2 modify-transit-gateway-attachment-nat-configuration \
  --transit-gateway-attachment-id tgw-attach-hotel-app \
  --nat-gateway-support disable \
  --reset-nat-gateway-rules

Consumers of Steps 1 and 2 keep the same names; the hotel recreates its resource gateway and interface endpoint in the new VPC. vpc-dev-legacy gets the same treatment from the development pool, after which 100.66.0.0/16 and its DNS records are removed.

Design decisions

Service level first, network level only where it's needed

PrivateLink and Lattice are immune to overlap, expose only the named ports and outlive the migration, so every client-calls-service flow goes that way. Only flows needing arbitrary hosts or two-way initiation use translation, which keeps the translated estate small and easy to delete.

1:1 NAT rather than private NAT gateways for two-way traffic

A private NAT gateway covers only connections started from its own VPC, so operations SSH to arbitrary hotel hosts would need a load balancer per target. 1:1 NAT keeps host bits and lets either side start connections. Its constraints: IPv4 only, no appliance mode on the same attachment, and asynchronous changes that can drop traffic briefly.

Choosing NAT CIDRs

The NAT CIDRs must not overlap anything else the hub routes. The Transit Gateway checks overlap only between rules on one attachment, not against other attachments or connected networks, so that check is the network team's job. 100.64.0.0/10 sits outside the company's 10.0.0.0/8 plan. The /16s avoid the EKS pod range 100.64.0.0/16, reused in several VPCs. Recording the NAT CIDRs in IPAM keeps future VPCs off them.

Cost

Example rates from the facts used throughout this guide:

  • Lattice: the service network endpoint has no hourly charge. Each resource configuration associated with a service network costs about $0.10 per hour, so the two APIs come to about $146 a month, plus about $0.01 per GB for the consumer (lower at volume) and $0.006 per GB for the provider.
  • PrivateLink: the hotel's payment endpoint in two zones is about $14.60 a month plus $0.01 per GB, and the payments team pays for the NLB.
  • 1:1 NAT: billed at standard NAT gateway hourly and data processing rates, and the processing charge applies only to translated traffic. With the example NAT gateway rate of $0.045 per GB and Transit Gateway processing of $0.02 per GB, moving 50 TB of hotel data through the translation costs about 50,000 × $0.065 ≈ $3,250.

The Transit Gateway pricing page gives no dollar figure for the hourly part, so check it before budgeting.

Alternatives

Private NAT gateway with a routable secondary CIDR

This was the standard answer before 1:1 NAT, and it still appears on the exam. The setup:

  1. Routable rangeEach overlapping VPC keeps its workloads in the overlapping, non-routable range and adds a small, unique, routable secondary CIDR from IPAM.
  2. OutboundA private NAT gateway (--connectivity-type private, no Elastic IP) in a routable subnet translates outbound connections to its own routable address and sends them to the Transit Gateway.
  3. InboundTraffic into an overlapping VPC arrives at an internal ALB or NLB in its routable subnet, with targets in the non-routable range.
  4. HubThe Transit Gateway attaches through the routable subnets and carries static routes for the routable ranges only.

Each NAT address supports 55,000 simultaneous connections per unique destination, and a gateway can have up to 8 addresses. The gateways are zonal, one per Availability Zone; the regional NAT gateway doesn't support private mode. Traffic from a private NAT gateway to an internet gateway is dropped. The CLI is on Task 1.6 and the EKS variant on Task 3.3. It still fits where 1:1 NAT can't go: behind a virtual private gateway, or on an attachment that needs appliance mode.

PrivateLink endpoint services in both directions

The hotel could instead run an endpoint service per API, with an NLB in its VPC and interface endpoints on the company side. That costs an NLB per API and endpoints per consumer VPC and zone. Resource configurations need no load balancer and reach every consumer through one service network.

PrivateLink tunnel endpoints (November 2026)

A Tunnel endpoint reaches a CIDR resource configuration: up to 10 ranges in the provider VPC, including hosts created later, overlap allowed. It could give operations one-way access to the whole hotel VPC without NAT, but clients must wrap traffic in GENEVE (UDP 6081) and only consumers start connections. It's too new to expect on the exam.

Testing it

  1. NAT state and routesget-transit-gateway-attachment-nat-configuration must show NatGatewaySupport enabled and each rule activated on both attachments. Then aws ec2 search-transit-gateway-routes --transit-gateway-route-table-id tgw-rtb-onprem --filters "Name=route-search.subnet-of-match,Values=100.64.0.0/10" must list 100.65.0.0/16 and 100.66.0.0/16 as type system. No route table may still hold a propagated 10.0.0.0/16.
  2. The one-side trap, on purposeFrom a development host, a connection to the real 10.0.20.15 must fail (the address is local there) while 100.65.20.15 succeeds.
  3. Flow logs show the translated viewWith a custom flow log format that includes pkt-srcaddr and pkt-dstaddr on the hotel VPC, a session from the development VPC must appear with pkt-srcaddr 100.66.5.9, and an operator session with 10.100.20.5. On Transit Gateway interfaces srcaddr is the interface itself, so filter on pkt-srcaddr.
  4. Path analysis per legRun Reachability Analyzer (one Region, accounts in the organization) from the operations jump host's interface to the hotel attachment, and from the hotel database interface back. Whether it models 1:1 NAT wasn't confirmed, so the end-to-end proof is the flow logs.
  5. Service-level linksFrom a booking pod, curl https://availability.hotels.example.com must succeed and dig must return addresses in 10.41.0.0/16. From the hotel VPC, a payment test transaction must appear in the payment API's log with the hotel's VPC endpoint ID from the proxy protocol header.
  6. DNS viewsdig @10.41.0.10 pms-db.hotels.example.com must return 100.65.20.15. The same query from inside vpc-hotel-app must return 10.0.20.15.

Troubleshooting checklist. SYN out but no reply usually means a missing return route or ACL entry for a NAT CIDR. Broken development access right after Step 3 means clients still use real addresses. A hotel API timing out through Lattice points to the resource gateway's security group or name resolution, not routing.

"Two VPCs with the same CIDR must reach each other through a Transit Gateway, and connections start from both sides" is Transit Gateway 1:1 NAT with both attachments translated to different NAT CIDRs. On older questions it's private NAT gateways in routable subnets plus internal load balancers for inbound traffic. "Only one service must be consumed, one way, despite overlapping CIDRs" is PrivateLink (or a Lattice resource configuration). VPC peering and plain Transit Gateway routing are always wrong for identical ranges.
