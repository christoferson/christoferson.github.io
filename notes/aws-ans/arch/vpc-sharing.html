Reference architecture

VPC sharing or Transit Gateway for multi-account VPCs

A new analytics group wants about 40 small accounts that talk to each other all day. Instead of 40 more VPCs and Transit Gateway attachments, the network account owns one analytics VPC per environment and shares its subnets with the team accounts through AWS RAM. Teams keep their own accounts, bills and security groups; the network team keeps routing, gateways and the single attachment.

Scenario and requirements

The travel company (example.com) gives most workloads their own account and VPC on tgw-use1 (AS 64521), segmented by route tables as on Transit Gateway hub and spoke. A new analytics group wants about 40 small accounts in us-east-1, one per team (ingestion, machine learning, BI, data quality and so on), all reading the same MSK cluster, Aurora database and Redshift warehouse and calling each other constantly.

A VPC per account would mean 40 mostly empty VPCs, 40 more hourly attachments, and Transit Gateway data processing on all the east-west traffic. Instead the network account 111111111111 (the owner) owns one analytics VPC per environment and shares its subnets with the team accounts (the participants).

RequirementDesign choice
Each team keeps its own account, IAM boundary and billTeam accounts are participants in a shared VPC; they own their instances, clusters, ENIs and security groups
Heavy team-to-team traffic without per-GB hub chargesAll teams in one VPC, so east-west traffic uses the VPC's local route and never enters the Transit Gateway
Teams must not change routing or open the internetRoute tables, network ACLs, gateways, endpoints and the attachment exist only in the owner account
Production analytics separate from development, and outside PCI DSS scopeOne shared VPC per environment, its own Transit Gateway route table, blackholes for the payments and development ranges
Data stores reachable only by the teams that need themSubnet-level sharing in tiers, network ACLs between tiers, security group references between accounts
Charge-back and auditSubnet flow logs to the log archive account, CUR usage types, Transit Gateway metering policy where it helps

  • Team accounts in a new Analytics OU ou-anly-33334444: ingestion 121212121212, machine learning 131313131313, BI 141414141414, data quality 151515151515, and the data platform account 161616161616 that runs the shared data stores.

How it works

Steps marked AWS happen automatically once configured; the others are actions by the named account.

  1. A team joins
  2. Account lands in the Analytics OUPlatform teamThe data quality account 151515151515 is created in ou-anly-33334444. The subnet share names the OU, so the shared subnets appear at once, with no invitation.
  3. Team launches into shared subnetsTeam accountThe team creates its own security group in vpc-0anlyprod and launches EMR or EKS nodes into the shared subnets, without being able to change routing.
  4. East-west traffic inside the VPC
  5. Local routeAWSA Spark job in the ML account at 10.43.70.15 reads from the data platform's MSK broker at 10.43.17.20. The local route delivers it directly: no attachment, no hop, no Transit Gateway processing.
  6. Network ACL, then security groupAWSThe owner's ACL on the data tier allows the Kafka port from the application tier. The broker's security group, owned by 161616161616, allows the ML team's security group by reference (131313131313/sg-...).
  7. BillingAWSSame AZ ID: free, even across accounts. Different AZs: inter-AZ data transfer, billed to the participant that owns the resource.
  8. Traffic leaving the VPC
  9. To the hubAWSThe ingestion job pulls change data from the booking database at 10.40.10.25. The subnet route table sends 10.0.0.0/8 to the single Transit Gateway attachment, which belongs to the network account.
  10. Analytics route tableAWSThe analytics table holds shared services, on premises and the booking VPC, and blackholes payments and development. The packet leaves on the booking VPC attachment.
  11. Who paysAWSData processing goes by default to the source attachment's owner, the network account, unless a metering policy moves it.

Build it

Step 1

The analytics VPC from IPAM, with subnets in tiers

The network account, the delegated IPAM administrator, allocates a /17 per environment from a pool for the 10.43.0.0/16 growth block. One VPC carved into subnets wastes less space than 40 half-empty /21s, each with its own attachment subnets and headroom. The block sits inside the 10.40.0.0/14 summary already advertised to the data centers, so nothing changes on premises.

Production analytics VPC from the IPAM pool (AWS CLI, network account 111111111111) 
# the pool hands out the next free /17 inside 10.43.0.0/16, so it cannot overlap
aws ec2 create-vpc --ipv4-ipam-pool-id ipam-pool-0use1anly12345 \
  --ipv4-netmask-length 17 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=vpc-0anlyprod},{Key=env,Value=prod}]'

The subnet is the unit you share, so the plan has tiers, one subnet per AZ, created by AZ ID: us-east-1a can be a different zone in every team account, use1-az1 is the same everywhere.

  • Transit Gateway attachment: /28 per AZ in 10.43.0.0/24, owner only, never shared.
  • Endpoints: /24 per AZ in 10.43.4.0/22 for the owner's interface endpoints, never shared.
  • Ingestion: /24 per AZ in 10.43.8.0/21, shared only with 121212121212, so its addresses identify that team in rules and logs outside the VPC.
  • Data: /22 per AZ in 10.43.16.0/20, shared only with the data platform account 161616161616 (MSK, Aurora, Redshift).
  • Application: /20 per AZ in 10.43.64.0/18, shared with the whole Analytics OU.
One data-tier subnet, placed by AZ ID (AWS CLI, network account) 
aws ec2 create-subnet --vpc-id vpc-0anlyprod --availability-zone-id use1-az1 \
  --cidr-block 10.43.16.0/22 \
  --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=anly-data-az1},{Key=tier,Value=data}]'

Participants control their own security groups, so network ACLs are the owner's main lever between them. The data tier's ACL allows Kafka and PostgreSQL only from the application and ingestion tiers, plus outbound ephemeral ports because ACLs are stateless.

Data tier ACL: only the application and ingestion tiers reach the data stores (AWS CLI, network account) 
# Kafka (TLS listener) from the application tier
aws ec2 create-network-acl-entry --network-acl-id acl-anly-data \
  --ingress --rule-number 100 --protocol tcp --port-range From=9094,To=9094 \
  --cidr-block 10.43.64.0/18 --rule-action allow

# PostgreSQL from the ingestion tier
aws ec2 create-network-acl-entry --network-acl-id acl-anly-data \
  --ingress --rule-number 110 --protocol tcp --port-range From=5432,To=5432 \
  --cidr-block 10.43.8.0/21 --rule-action allow

# return traffic to clients (stateless ACL)
aws ec2 create-network-acl-entry --network-acl-id acl-anly-data \
  --egress --rule-number 100 --protocol tcp --port-range From=1024,To=65535 \
  --cidr-block 10.43.0.0/17 --rule-action allow
Step 2

Share the subnets with AWS RAM

VPC sharing works only inside one AWS Organization, and resource sharing with Organizations must be enabled once from the management account. Subnets of a default VPC cannot be shared. The network account creates one share per tier, so a principal sees only the subnets meant for it. Sharing to the OU means new team accounts get access automatically.

Application subnets to the Analytics OU, data subnets to the data platform account (AWS CLI, network account) 
aws ram create-resource-share --region us-east-1 \
  --name anly-prod-app-subnets \
  --resource-arns \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-anly-app-az1 \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-anly-app-az2 \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-anly-app-az4 \
  --principals arn:aws:organizations::999999999999:ou/o-travel1234/ou-anly-33334444 \
  --no-allow-external-principals

aws ram create-resource-share --region us-east-1 \
  --name anly-prod-data-subnets \
  --resource-arns \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-anly-data-az1 \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-anly-data-az2 \
    arn:aws:ec2:us-east-1:111111111111:subnet/subnet-anly-data-az4 \
  --principals 161616161616 \
  --no-allow-external-principals

The owner creates and manages the VPC, subnets, route tables, network ACLs, internet and NAT gateways, endpoints, Resolver endpoints, peering connections and Transit Gateway attachments. It can describe participants' ENIs and security groups, but cannot modify their ENIs, use their security groups or touch their resources.

A participant creates, modifies and deletes its own resources in the shared subnets (instances, EKS and EMR nodes, Aurora, Redshift, MSK, Lambda, load balancers and their ENIs) and its own security groups. It can describe the VPC, subnets, route tables, ACLs and internet gateways but change none of them, and cannot even describe NAT gateways. It cannot create peerings, gateways or attachments, or see other participants' resources. Tags on the VPC and its resources are not shared, so subnet IDs, not Name tags, are the contract.

Participants cannot launch with the VPC's default security group: it belongs to the owner. A team's first launch with no security group specified fails, which surprises everyone the first time. Each team creates its own groups, or uses one the owner has shared (Step 4).

Resources a participant creates count against the participant's quotas, but limits of the VPC itself are shared by everyone (see Design decisions).

Step 3

One Transit Gateway attachment and its own route table

Only the VPC owner can attach a shared VPC to a Transit Gateway, so the 40 teams share one attachment, paid for by the network account. Analytics needs a path to the booking database for change data capture, but production spokes do not propagate into the prod table, so production VPCs cannot reach each other. Rather than open prod, analytics gets its own analytics table.

The attachment, using only the owner's /28 subnets (AWS CLI, network account) 
aws ec2 create-transit-gateway-vpc-attachment \
  --transit-gateway-id tgw-use1 \
  --vpc-id vpc-0anlyprod \
  --subnet-ids subnet-anly-tgw-az1 subnet-anly-tgw-az2 subnet-anly-tgw-az4 \
  --options DnsSupport=enable,SecurityGroupReferencingSupport=enable \
  --tag-specifications 'ResourceType=transit-gateway-attachment,Tags=[{Key=segment,Value=analytics}]'

The attachment is in the Transit Gateway owner's own account, so there is no acceptance step. The analytics table receives propagation from shared services, the Direct Connect gateway and VPN attachments, and the booking VPC attachment. The analytics attachment propagates into shared and onprem, and into prod so that replies from the booking VPC can return.

Associate, propagate and blackhole (AWS CLI, network account) 
aws ec2 create-transit-gateway-route-table --transit-gateway-id tgw-use1 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=analytics}]'

aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-analytics \
  --transit-gateway-attachment-id tgw-attach-anly-prod

# the booking VPC becomes reachable from analytics only
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-analytics \
  --transit-gateway-attachment-id tgw-attach-bookings-prod

# return path: the booking VPC (in prod) learns 10.43.0.0/17
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-anly-prod

# card data stays out of reach, and so does analytics development
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-analytics \
  --destination-cidr-block 10.40.48.0/21 --blackhole
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-analytics \
  --destination-cidr-block 10.43.128.0/17 --blackhole

Propagating into prod gives every production spoke a route toward analytics, but the analytics table has no route back except to the booking VPC (and a blackhole for payments), so no other connection can complete. The development analytics VPC attaches to dev like any development spoke.

The growth block breaks the "one /16 per environment" assumption behind the hub's blackholes. The dev table's blackhole for 10.40.0.0/16 does not cover 10.43.0.0/17, so add a blackhole for it in dev, and for 10.43.128.0/17 in prod. IPAM pool rules keep the split clean; the route tables have to follow it.

Step 4

Security groups inside the VPC and across the hub

Inside the shared VPC, participants write rules that reference security groups owned by other participants or by the owner, in the form account-id/security-group-id. This is the main reason chatty teams fit a shared VPC well: the MSK brokers allow "the ML team's workers" rather than a list of addresses that changes every time an autoscaling group or EMR cluster replaces nodes.

The data platform allows Kafka from the ML team's security group (AWS CLI, data platform account 161616161616) 
aws ec2 authorize-security-group-ingress \
  --group-id sg-0mskbrokers \
  --ip-permissions 'IpProtocol=tcp,FromPort=9094,ToPort=9094,UserIdGroupPairs=[{GroupId=sg-0mlworkers,UserId=131313131313,Description=ml-spark-workers}]'

Since October 2024 the owner can also share security groups through RAM: a baseline group (for example, allowing monitoring from shared services) that participants attach and that updates for everyone when the owner changes it. Only the account owning both VPC and group can share it, default groups cannot be shared, and participants cannot share theirs. On an ENI mixing shared and own groups, the groups-per-ENI limit is the lower of the two accounts' quotas.

Across the hub the rules are tighter. Since September 2024, VPCs on one Transit Gateway can reference each other's groups in inbound rules only: same gateway (so same Region, not across peering), not through Gateway Load Balancer or Network Firewall inspection, not for PrivateLink endpoints, not in use1-az3; off by default on the gateway (on for tgw-use1), on by default per attachment. Cloud WAN added the same in June 2025, inbound only within one core network edge.

The documentation used here does not say whether a cross-VPC reference to a group owned by a participant in a shared VPC works, so the booking database does not depend on it. The ingestion tier has its own subnets, so its CIDR identifies the team:

Booking database allows PostgreSQL from the ingestion subnets only (AWS CLI, bookings account 222222222222) 
aws ec2 authorize-security-group-ingress \
  --group-id sg-0bookingdb \
  --ip-permissions 'IpProtocol=tcp,FromPort=5432,ToPort=5432,IpRanges=[{CidrIp=10.43.8.0/21,Description="analytics ingestion tier via TGW"}]'

Dedicated subnets for a team that talks outside the VPC are cheap insurance: the same CIDR works in remote security groups, network ACLs, on-premises firewalls and flow log queries. Teams that only talk inside the VPC can share the common application subnets.

Step 5

DNS and endpoints, owned once

One DHCP option set and one set of endpoints serve every participant. The owner sets the DHCP options and associates the shared Resolver rule rslvr-rr-corpfwd01, so corp.example.com queries reach the data centers.

Endpoints: participants cannot create interface endpoints in shared subnets, so the owner creates them (Glue, STS, Secrets Manager, ECR, CloudWatch Logs) in the endpoint subnets and pays for them. The S3 gateway endpoint sits in the owner's route tables with an owner-managed policy, so a team needing a new bucket asks the network team. Participants can create VPC Lattice resource gateways in shared subnets, with their own security groups.

Private hosted zones: the ML team owns ml.analytics.example.com in 131313131313. For a zone in another account, the zone's account authorizes the association and the account that created the VPC makes it; in a shared VPC that is the network account, not the team.

Cross-account private hosted zone association (AWS CLI, ML account, then network account) 
# in 131313131313: the zone owner authorizes the VPC
aws route53 create-vpc-association-authorization \
  --hosted-zone-id Z0ML1234567890 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-0anlyprod

# in 111111111111: the VPC owner makes the association
aws route53 associate-vpc-with-hosted-zone \
  --hosted-zone-id Z0ML1234567890 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-0anlyprod

AWS recommends deleting the authorization afterwards; the association stays. The console cannot do either step, so this belongs in the network team's automation. Other VPCs that need the zone get it through the central Resolver design, because the Transit Gateway does not resolve attached VPCs' private hosted zones.

Step 6

Flow logs, visibility and cost allocation

The owner can create flow logs for the VPC, subnets and participants' ENIs. A participant can manage flow logs only for its own ENIs, never a shared subnet, and the owner cannot describe or delete them. So the network team logs every shared subnet centrally, and teams log their own ENIs if they want a copy.

Central subnet flow logs for the shared tiers to the log archive bucket (AWS CLI, network account) 
aws ec2 create-flow-logs --resource-type Subnet \
  --resource-ids subnet-anly-app-az1 subnet-anly-app-az2 subnet-anly-app-az4 subnet-anly-data-az1 subnet-anly-data-az2 subnet-anly-data-az4 \
  --traffic-type ALL --max-aggregation-interval 60 \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::travel-log-archive/flow-logs/anly-prod/ \
  --destination-options FileFormat=parquet,HiveCompatiblePartitions=true,PerHourPartition=true
A team logs only its own interfaces, to its own log group (AWS CLI, BI account 141414141414) 
aws ec2 create-flow-logs --resource-type NetworkInterface \
  --resource-ids eni-0bidash01 eni-0bidash02 \
  --traffic-type REJECT \
  --log-group-name bi-rejects \
  --deliver-logs-permission-arn arn:aws:iam::141414141414:role/publishFlowLogs

Who pays what. Participants pay for their own resources and for their inter-AZ, peering, internet gateway and Direct Connect gateway data transfer. The owner pays the hourly and data charges of NAT gateways, virtual private gateways, Transit Gateway attachments, PrivateLink and VPC endpoints, and for the public IPv4 addresses in the VPC. Traffic between resources in the same AZ ID is free across accounts.

By default Transit Gateway data processing goes to the source attachment's owner, here the network account for all analytics traffic. Since November 2025 a metering policy (Flexible Cost Allocation) can charge matching traffic (by attachment type or ID, CIDR, port, protocol) to the source attachment owner, the destination attachment owner or the Transit Gateway owner. Here, analytics-to-booking traffic is billed to the bookings account as destination owner. It cannot bill a participant, which owns no attachment; it does not cover attachment hours; only the Transit Gateway owner manages it. The rest is charged back per team from flow log bytes by subnet or ENI.

Design decisions

Shared VPC for this group, Transit Gateway for the rest

AWS positions VPC sharing for workloads with heavy interconnectivity inside one trust boundary: fewer VPCs, while separate accounts still handle billing and access. The analytics teams fit. Bookings, payments and partner services keep a VPC per account, where a route table, not another team's security group, is the boundary. See Task 1.6.

Cost compared

Using the published us-east-2 example rates ($0.05 per VPC attachment-hour, $0.02 per GB of data processing), 40 team VPCs would cost about 40 × $0.05 × 730 ≈ $1,460 a month in attachment hours. If the teams exchange 150 TB a month across the hub, processing adds about 153,600 GB × $0.02 ≈ $3,070. The shared VPC needs one attachment (about $37 a month) and no east-west traffic enters the hub. Cross-AZ traffic inside the VPC still pays inter-AZ transfer ($0.01 per GB in and out in AWS's examples), billed to participants, so chatty consumers stay in their brokers' AZ ID where resilience allows. If the VPC is later peered, intra-Region peering charges appear since April 2025 under their own VpcPeering-In/Out-Bytes usage types in Cost Explorer and CUR. See Task 3.3.

Blast radius and isolation

One set of route tables, ACLs, endpoints and one attachment serve 40 teams, so one bad change hits all of them. The design limits that with one shared VPC per environment; tiered subnet sharing, so the data stores sit in subnets only the data platform account can use; owner resources in reviewed infrastructure as code; and card data kept out. The payments VPC stays separate and blackholed, and analytics receives tokenized data only, so the shared VPC stays out of PCI DSS scope. A card data workload inside it would put every participant in the cardholder data environment's network. See Task 4.1.

Quotas that become shared

  • Participant accounts per VPC: 100 (adjustable); subnets shared with one account: 100 (adjustable).
  • Network interfaces per Region (5,000) and security groups per Region (2,500) apply to shared VPCs too.
  • Network Address Usage: 64,000 units per VPC by default (up to 256,000), counting every participant's IPs. EKS pods and EMR clusters use it fast; turn on NAU metrics.
  • The one attachment carries up to 100 Gbps and 7.5 million packets per second per AZ for all teams combined.

When an account leaves or moves between organizations

Subnet sharing stays inside one organization. AWS's 2022 analysis: if the owner leaves, its subnets stop being shared but participants' existing resources stay active; Transit Gateway attachments keep working, but the organization principal is removed from the Transit Gateway share, so no new attachments until the owner re-shares, and billing moves to the new payer. If a participant leaves, it loses the share; by the documented unshare behaviour its resources keep running and can be modified or deleted, nothing new can be launched, and the owner cannot delete the subnet until they are gone.

So before a team account is divested or moved, its workloads move into a VPC of its own. A VPC per account moves with the account; a shared subnet does not. See Task 2.2.

Visibility for teams

Participants cannot change routing or log subnets, so the network team exposes central flow log tables filtered per team, Reachability Analyzer (which supports shared subnets) and a request path for ACL and endpoint changes.

Alternatives

A VPC per team account on the Transit Gateway

The company default. Each team owns its VPC and moves with its account, and the route table is a hard boundary. The cost is 40 attachments, per-GB processing on every byte between teams, and IP space spread over many small VPCs: expensive for an east-west-heavy group.

VPC peering between team VPCs

No hourly or processing charge, and security group references in both directions within a Region. But peering is not transitive, so 40 VPCs would need up to 780 connections for a full mesh, and in a shared VPC only the owner can create or accept peerings. Good for a few heavy pairs, not for a group.

PrivateLink or VPC Lattice between team VPCs

One-way, service-level access that tolerates overlapping CIDRs. It suits teams publishing a few APIs, not Spark clusters reading from every Kafka broker.

AWS Cloud WAN segments

An analytics segment gives route-table-style isolation as policy as code, but keeps per-attachment and per-GB charges between team VPCs. A shared VPC can join Cloud WAN later as one attachment.

Testing it

  1. Prove the participant boundaryFrom the BI account, try to add a route, replace a network ACL and create a NAT gateway: each must be denied. A launch with no security group must fail, because the default group belongs to the owner.
  2. Prove east-west paths with Reachability AnalyzerML worker ENI to MSK broker ENI on TCP 9094 should succeed; BI ENI to the Aurora ENI on 5432 should fail at the data tier ACL.
  3. Prove the hub segmentationIngestion ENI to the booking database on 5432 succeeds through the analytics table. Any analytics ENI to the payments VPC 10.40.48.0/21 fails at that table, and PacketDropCountBlackhole rises. Repeat from development analytics toward 10.43.0.0/17.
  4. Read the flow logsIn Athena, most ML-to-broker bytes should stay within one AZ ID; a large cross-AZ share is a cost finding.
  5. Check DNS from a participantResolve a name in ml.analytics.example.com, an interface endpoint (an address in 10.43.4.0/22) and a corp.example.com name.
  6. Rehearse an unshareIn development, remove a test account from the share: its instances keep working, a new launch fails, and subnet deletion is refused until they are gone.

"Many accounts in the same organization need high-volume communication with each other; application teams must keep separate billing and must not manage networking; minimize Transit Gateway attachments and data processing cost" is VPC sharing: the network account owns the VPC and shares subnets with AWS RAM. If the question adds "accounts outside the organization" or "the account will be divested next quarter", VPC sharing is out: use a VPC per account with a Transit Gateway share, or PrivateLink.
