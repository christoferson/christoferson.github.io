Reference architecture

Shared interface endpoints and a data perimeter

The travel company's 300 VPCs all call the same handful of AWS APIs. One set of interface endpoints per Region in the shared services VPC serves every spoke and both data centers through private hosted zones; free S3 gateway endpoints stay in every VPC; endpoint, bucket and key policies together keep the company's data inside its own organization and network.

Scenario and requirements

The travel company (example.com) runs about 300 VPCs across us-east-1, eu-central-1 and ap-northeast-1, attached to the Transit Gateways described in Transit Gateway hub and spoke. Most subnets have no internet route, yet every VPC needs the same APIs: Systems Manager for patching and Session Manager, ECR for the container images of the EKS booking platform, KMS and Secrets Manager for keys and database credentials, STS for IAM roles, CloudWatch Logs, and S3. The PCI DSS assessor wants evidence that card data is readable only from company networks by company identities.

RequirementDesign choice
Private access to AWS APIs from 300 VPCs without paying for 300 copies of each endpointOne interface endpoint per service per Region in the network account's shared services VPC, private DNS disabled
Applications keep the normal service names and SDK defaultsA private hosted zone named after each service, aliased to the endpoint, carried to every spoke by the Route 53 Profile
Data centers reach the same APIs privatelyConditional forwarders to the Resolver inbound endpoint, which sees the same zones
Cheap, high-volume S3 accessAn S3 gateway endpoint in every VPC; one S3 interface endpoint per Region for on premises only
Only company identities, only company resources, only company networksOrganization conditions in endpoint policies, network conditions in bucket and key policies, SCPs as the backstop

Values used on this page:

  • Accounts: network account 111111111111 owns the shared services VPCs, the endpoints and the zones; the bookings account 222222222222 owns the production booking VPC vpc-bookings-prod; the log archive account 777777777777 holds the trail bucket. The organization ID is o-travel1234.
  • us-east-1: shared services VPC vpc-shared-services (10.41.0.0/16), endpoint subnets subnet-shared-az1 to az3, Resolver inbound endpoint at 10.41.0.10 and 10.41.1.10, Route 53 Profile rp-travel-dns-01 from Hybrid and multi-account DNS. The other Regions repeat the pattern in 10.45.0.0/16 and 10.49.0.0/16.
  • Services per Region: ssm, ssmmessages and ec2messages (Session Manager and older agents), ecr.api, ecr.dkr, kms, secretsmanager, sts and logs: nine interface endpoints, plus the S3 interface endpoint for on premises.

How it works

Steps marked AWS happen automatically once configured; the others are actions of a client you run.

  1. A pod in a spoke reads a secret
  2. Name lookupBooking podA pod in vpc-bookings-prod calls Secrets Manager. The SDK resolves secretsmanager.us-east-1.amazonaws.com through the VPC +2 resolver; the VPC keeps AmazonProvidedDNS.
  3. Private zone from the ProfileAWSThe Profile rp-travel-dns-01 carries a private hosted zone named exactly secretsmanager.us-east-1.amazonaws.com. Its apex alias A record returns the private IPs of the central endpoint's interfaces in 10.41.0.0/16, not public addresses.
  4. Route to the hubAWSThe subnet route 10.0.0.0/8 sends the HTTPS connection to the Transit Gateway. The prod route table holds the shared services CIDR, so the packet reaches the endpoint subnet.
  5. Endpoint checksAWSThe endpoint security group allows TCP 443 from the company ranges. The endpoint policy allows the call because the caller is in o-travel1234 and the secret is too.
  6. Service and resource policyAWSSecrets Manager evaluates IAM, the secret's resource policy and the KMS key policy. The request context carries aws:SourceVpce of the central endpoint and aws:SourceVpc of the shared services VPC, which the key policy requires.
  7. The same pod pulls an image
  8. Registry calls through the hubAWSAuthentication and the manifest go to api.ecr and 222222222222.dkr.ecr.us-east-1.amazonaws.com, matching the dkr.ecr wildcard record.
  9. Layers through the local gateway endpointAWSThe image layers come from S3. S3 names are not overridden, so they resolve to public S3 addresses and the route table sends them to the VPC's own free gateway endpoint; the heavy bytes never cross the Transit Gateway.
  10. A data center job writes to S3 and reads a key
  11. Conditional forwarderUS data center DNSA batch server resolves s3.us-east-1.amazonaws.com and kms.us-east-1.amazonaws.com; data center DNS forwards both names to 10.41.0.10 and 10.41.1.10 over Direct Connect.
  12. Inbound endpoint answersAWSThe KMS zone is associated with the shared services VPC, so the answer is the KMS endpoint IPs. The S3 interface endpoint has "private DNS only for inbound endpoints", so queries arriving through the inbound endpoint get the S3 interface endpoint IPs, while queries from inside the VPC still get public S3 addresses.
  13. Private pathAWSThe traffic enters the shared services VPC through the Direct Connect gateway and Transit Gateway and reaches the interface endpoints. A gateway endpoint could not serve it.

Build it

Step 1

Interface endpoints in the shared services VPC, private DNS off

The network account creates each endpoint once per Region, with interfaces in three Availability Zones so that one zone's failure leaves two answers in the Regional DNS name. Private DNS must be disabled: the private zone that AWS manages for an endpoint is associated only with the endpoint's own VPC, so it would never reach the spokes, and it would block the company's own zone of the same name in the shared services VPC.

The security group is the network-layer gate for every spoke. It allows TCP 443 from the three Regional summaries and both data centers. It cannot reference spoke security groups: security group referencing across a Transit Gateway does not cover PrivateLink endpoints, so CIDRs (or a managed prefix list of them) are the tool.

Create the nine central endpoints in us-east-1 with private DNS off and the shared policy attached (AWS CLI, network account) 
# sg-shared-endpoints allows TCP 443 from 10.40.0.0/14, 10.44.0.0/14, 10.48.0.0/14, 10.100.0.0/16 and 10.200.0.0/16
for svc in ssm ssmmessages ec2messages ecr.api ecr.dkr kms secretsmanager sts logs; do
  aws ec2 create-vpc-endpoint --vpc-endpoint-type Interface \
    --vpc-id vpc-shared-services \
    --service-name com.amazonaws.us-east-1.$svc \
    --subnet-ids subnet-shared-az1 subnet-shared-az2 subnet-shared-az3 \
    --security-group-ids sg-shared-endpoints \
    --no-private-dns-enabled \
    --policy-document file://endpoint-policy-org.json \
    --tag-specifications "ResourceType=vpc-endpoint,Tags=[{Key=service,Value=$svc}]"
done

Nine interface endpoints plus the S3 interface endpoint of Step 4 is ten of the 50 interface endpoints per VPC quota (interface and Gateway Load Balancer endpoints together, adjustable). Check it before adding services; beyond it, raise the quota or add a second endpoint VPC.

Each endpoint scales from 10 Gbps per Availability Zone towards 100 Gbps, with an 8,500-byte MTU and no path MTU discovery: irrelevant for API calls, relevant if a bulk-data service is ever centralized.

Step 2

A private hosted zone per service, named after the service

For each endpoint the network team creates a private hosted zone whose name is the service's Regional hostname, associated first with vpc-shared-services, and an alias A record at the apex that points at the endpoint's Regional DNS name (the first entry in DnsEntries; the zonal names would pin clients to one Availability Zone). The shapes are on Task 2.2.

Read the Regional DNS name and its hosted zone ID for the Secrets Manager endpoint (AWS CLI, network account) 
aws ec2 describe-vpc-endpoints \
  --filters Name=vpc-id,Values=vpc-shared-services Name=service-name,Values=com.amazonaws.us-east-1.secretsmanager \
  --query "VpcEndpoints[0].DnsEntries[0]"

Zone names follow each service's hostname, which is not always the endpoint service name. com.amazonaws.us-east-1.ecr.api becomes the zone api.ecr.us-east-1.amazonaws.com, and the other seven are ssm., ssmmessages., ec2messages., kms., secretsmanager., sts. and logs.us-east-1.amazonaws.com. STS works only for clients using the Regional STS endpoint, so the account baseline sets the SDKs to Regional mode.

ECR's Docker endpoint is the exception. Image pulls use account-specific names such as 222222222222.dkr.ecr.us-east-1.amazonaws.com, so the dkr.ecr.us-east-1.amazonaws.com zone needs a wildcard record; an apex record alone would leave every pull resolving to public addresses and failing in subnets without internet access.

The dkr.ecr zone with a wildcard alias to the central endpoint (AWS CLI, network account; DNS name and zone ID from describe-vpc-endpoints) 
aws route53 create-hosted-zone \
  --name dkr.ecr.us-east-1.amazonaws.com \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services \
  --caller-reference dkr-ecr-use1-2026-11-15 \
  --hosted-zone-config PrivateZone=true

aws route53 change-resource-record-sets --hosted-zone-id Z0DKRSHARED456 \
  --change-batch '{"Changes":[{"Action":"CREATE","ResourceRecordSet":{
    "Name":"*.dkr.ecr.us-east-1.amazonaws.com","Type":"A",
    "AliasTarget":{"HostedZoneId":"Z7HUB4ULQPZ6S",
      "DNSName":"vpce-0ecrdkr1234567890-e5f6g7h8.dkr.ecr.us-east-1.vpce.amazonaws.com",
      "EvaluateTargetHealth":true}}}]}'

A zone named amazonaws.com or us-east-1.amazonaws.com would capture every AWS hostname in the Region, including S3 and services with no central endpoint, and return NXDOMAIN for them (a private zone has no fallback to public DNS). One narrowly named zone per service is the only safe shape.

Step 3

Deliver the zones to every spoke and to the data centers

The Profile rp-travel-dns-01 is already associated with every spoke VPC by the VPC template (Hybrid DNS, Step 4), so adding the nine zones to it reaches all 300 VPCs in the Region at once, with no per-VPC authorization and no 300-VPCs-per-zone ceiling. Without Profiles, nine zones in 300 VPCs means about 2,700 cross-account authorize-then-associate pairs.

Add the endpoint zones to the Regional Profile (AWS CLI, network account; one call per zone) 
aws route53profiles associate-resource-to-profile \
  --profile-id rp-travel-dns-01 --name vpce-secretsmanager \
  --resource-arn arn:aws:route53:::hostedzone/Z0SECRETSSHARED789

aws route53profiles associate-resource-to-profile \
  --profile-id rp-travel-dns-01 --name vpce-ecr-dkr \
  --resource-arn arn:aws:route53:::hostedzone/Z0DKRSHARED456

Endpoints are Regional, so Frankfurt has its own zones (kms.eu-central-1.amazonaws.com and so on) aliased to its endpoints and added to the Frankfurt Profile.

For the data centers, the zones are associated directly with the shared services VPC (they were created with it in Step 2), which is all the inbound endpoint needs. Data center DNS gets one conditional forwarder per service hostname, pointing at the inbound endpoint IPs, as the hybrid DNS page describes for aws.example.com.

US data center forwarders for two of the service names (Windows DNS PowerShell; repeat per service) 
Add-DnsServerConditionalForwarderZone -Name "kms.us-east-1.amazonaws.com" `
  -MasterServers 10.41.0.10,10.41.1.10 -ReplicationScope Forest
Add-DnsServerConditionalForwarderZone -Name "s3.us-east-1.amazonaws.com" `
  -MasterServers 10.41.0.10,10.41.1.10 -ReplicationScope Forest

These list only the us-east-1 inbound IPs: the Frankfurt inbound endpoint has no zone for a us-east-1 name.

Step 4

S3: a gateway endpoint in every VPC, one interface endpoint for the data centers

S3 is deliberately not centralized for VPC clients. A gateway endpoint is free but works only from inside its own VPC, never through a Transit Gateway, peering, VPN or Direct Connect (Task 3.1); centralizing S3 would add $0.03 per GB to traffic that is free today. So the VPC template adds a gateway endpoint to every route table, with the policy of Step 5.

The S3 gateway endpoint in the booking VPC, created by the VPC template (AWS CLI, bookings account) 
aws ec2 create-vpc-endpoint --vpc-endpoint-type Gateway \
  --vpc-id vpc-bookings-prod \
  --service-name com.amazonaws.us-east-1.s3 \
  --route-table-ids rtb-bookings-app rtb-bookings-data \
  --policy-document file://s3-gateway-policy-org.json

The data centers need an S3 interface endpoint. The shared services VPC gets one with private DNS on and PrivateDnsOnlyForInboundResolverEndpoint=true, exactly as on Task 3.1: on-premises queries arriving through the inbound endpoint get the interface endpoint IPs, and the shared services VPC's own clients keep using its gateway endpoint, which must exist first and must stay while the option is on. No custom zone is built for S3 and nothing S3-related goes into the Profile, so spokes are unaffected.

The option is available only for services with both gateway and interface endpoints (S3 and DynamoDB). Creating a gateway endpoint resets open connections to S3 in that VPC, so the template adds it before workloads start, not during peak hours.

Step 5

Endpoint policies that form one perimeter

A central endpoint has one policy for every spoke, capped at 20,480 characters including whitespace. Listing 300 account IDs or per-team rules would not fit and would change every week, so the policy states organization-level facts instead: the caller is in the organization (aws:PrincipalOrgID, trusted identities) and the resource is in the organization (aws:ResourceOrgID, trusted resources). The concepts and the S3 gateway version are on Task 4.1. Fine-grained permission stays in IAM and resource policies, because an endpoint policy only limits and never grants.

endpoint-policy-org.json, attached to the KMS, Secrets Manager, Logs, STS and ECR endpoints (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "OrgPrincipalsToOrgResources",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "*",
    "Resource": "*",
    "Condition": {
      "StringEquals": {
        "aws:PrincipalOrgID": "o-travel1234",
        "aws:ResourceOrgID": "o-travel1234"
      }
    }
  }]
}

The resource condition needs exceptions where AWS itself owns the resource. Systems Manager runs AWS-owned documents, so the three SSM endpoints get a principal-only version of the policy. ECR layers come from an AWS-owned S3 bucket, so the S3 gateway policy adds a statement allowing s3:GetObject on that Regional layer bucket.

The extra statement in s3-gateway-policy-org.json that keeps ECR image pulls working (JSON fragment) 
{
  "Sid": "EcrLayersInAwsOwnedBucket",
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::prod-us-east-1-starport-layer-bucket/*"
}

An endpoint policy does nothing for calls that do not pass through it. A spoke that sends a KMS call to another Region's hostname leaves through the NAT gateway (where one exists) and skips the policy; the egress firewall's domain allow list and the SCPs of Step 6 cover that path.

Step 6

Bucket and key policies that require the network, and SCP guardrails

The third perimeter question is the network: did the request come through the company's endpoints? Resource policies check it with aws:SourceVpce (an endpoint ID) or aws:SourceVpc (a VPC ID). Centralization simplifies this: every spoke's call to a us-east-1 key arrives through vpce-0kmsuse1shared in the shared services VPC, so the key policy names one endpoint, not 300 VPCs. S3 is the opposite, with a gateway endpoint per VPC, so the card-data bucket names only the payment VPC's gateway endpoint and the on-premises S3 interface endpoint (bucket form on Task 4.1).

A statement in the booking platform's KMS key policy: deny use of the key unless the call arrives through the central KMS endpoint, except for AWS services acting for the company (JSON) 
{
  "Sid": "DenyOutsideCentralKmsEndpoint",
  "Effect": "Deny",
  "Principal": "*",
  "Action": ["kms:Decrypt", "kms:GenerateDataKey", "kms:Encrypt"],
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {"aws:SourceVpce": "vpce-0kmsuse1shared"},
    "Bool": {"aws:ViaAWSService": "false"}
  }
}

The aws:ViaAWSService exception matters: for SSE-KMS objects, S3 calls KMS on the caller's behalf with no VPC endpoint in that hop. Add a break-glass role exception too.

SCPs set the outer fence for all member accounts. One statement denies data access to resources outside the organization (aws:ResourceOrgID), which covers the paths endpoint policies cannot see. Another stops anyone but the network account from using cross-Region PrivateLink to AWS services (Alternatives), because that permission, vpce:AllowMultiRegion, must be allowed by both IAM and the SCP.

SCP attached to the workload OUs (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "NoDataToForeignResources",
      "Effect": "Deny",
      "Action": ["s3:*", "kms:*", "secretsmanager:*"],
      "Resource": "*",
      "Condition": {"StringNotEqualsIfExists": {"aws:ResourceOrgID": "o-travel1234"}}
    },
    {
      "Sid": "CrossRegionEndpointsOnlyByNetworkTeam",
      "Effect": "Deny",
      "Action": "vpce:AllowMultiRegion",
      "Resource": "*",
      "Condition": {"StringNotEquals": {"aws:PrincipalAccount": "111111111111"}}
    }
  ]
}

SCPs do not apply to service-linked roles or service principals, so exceptions for AWS services go in endpoint policies, not here. Resource control policies (RCPs) can apply the identity and network checks to resources organization-wide.

Step 7

See what the perimeter denies

CloudTrail network activity events record API calls that pass through VPC endpoints, delivered to the endpoint owner, which here is the network account, so one team sees every spoke's traffic through the central endpoints. They are off by default and charged separately. Filtering on errorCode VpceAccessDenied (the only valid value) records only calls an endpoint policy refused: a misconfigured new service, or stolen credentials from another organization being used inside the network.

Record endpoint-policy denials for KMS and Secrets Manager on the organization trail, keeping management events (AWS CLI, management or delegated administrator account) 
# put-event-selectors replaces all selectors, so the management selector is repeated
aws cloudtrail put-event-selectors --trail-name org-trail \
  --advanced-event-selectors '[
    {"Name": "Management events",
     "FieldSelectors": [{"Field": "eventCategory", "Equals": ["Management"]}]},
    {"Name": "KMS denied through VPC endpoints",
     "FieldSelectors": [
       {"Field": "eventCategory", "Equals": ["NetworkActivity"]},
       {"Field": "eventSource", "Equals": ["kms.amazonaws.com"]},
       {"Field": "errorCode", "Equals": ["VpceAccessDenied"]}]},
    {"Name": "Secrets Manager denied through VPC endpoints",
     "FieldSelectors": [
       {"Field": "eventCategory", "Equals": ["NetworkActivity"]},
       {"Field": "eventSource", "Equals": ["secretsmanager.amazonaws.com"]},
       {"Field": "errorCode", "Equals": ["VpceAccessDenied"]}]}
  ]'

Each event source needs its own selector, and events carry the vpcEndpointId for per-endpoint alarms. Denials by bucket or key policies are ordinary AccessDenied errors, not network activity events. Flow logs on the endpoint subnets add source IPs and bytes per spoke (Task 4.2).

Design decisions

Centralized endpoints: the cost case

Interface endpoints cost $0.01 per hour for each Availability Zone interface plus $0.01 per GB processed (first petabyte), and partial hours count as full. Nine endpoints in 300 VPCs over two zones is 5,400 interfaces: 5,400 × $0.01 × 730 ≈ $39,420 a month before any data. Centrally, nine endpoints in three zones in three Regions is 81 interfaces, about $591 a month, plus about $66 for the three on-premises S3 interface endpoints.

The price of centralizing is Transit Gateway data processing, $0.02 per GB in the example rate, charged on traffic entering the Transit Gateway in each direction, on top of the same $0.01 per GB endpoint charge. The saving of roughly $38,700 a month would only be used up by about 1,900 TB a month of API traffic through the hub. API calls are small; the bulk bytes (S3 objects, ECR layers) stay on free gateway endpoints, which is why this split works. Detail: Task 3.3.

Blast radius

One endpoint, policy or zone now serves 300 VPCs: a bad policy or a deleted alias record stops patching, image pulls and secret retrieval across a Region at once. Mitigations: three zones, every change through infrastructure as code with a canary Region (ap-northeast-1 first), and per-Region resources so a mistake stays in one Region.

One policy for everyone

A shared endpoint cannot carry per-team least privilege, so it holds organization conditions and per-team rules live in IAM and resource policies. The PCI DSS payment VPCs are the exception worth paying for: their own KMS and Secrets Manager endpoints, a policy naming only the payment accounts, and zones for them in the higher-priority travel-dns-pci Profile, which wins for the same name.

Profile, not cross-account association

Cross-account association (the whitepaper's method) is one pair per zone per VPC and stops at 300 VPCs per zone. The Profile is already associated for hybrid DNS, so each new zone is one API call.

Quotas to plan for

  • 50 interface plus Gateway Load Balancer endpoints per VPC (adjustable); the central VPC uses ten.
  • Endpoint policy 20,480 characters, not adjustable.
  • Gateway endpoints: 20 per Region per account (adjustable); 300 VPCs spread over many accounts stay well inside it.
  • Profile limits (5,000 zones, 1,000 VPCs per Profile) leave ample room for nine zones per Region.

Alternatives

Endpoints in every VPC

Private DNS on, a policy per VPC, no Transit Gateway in the path and no shared blast radius. Right for a few or regulated VPCs; at 300 VPCs it is about 60 times the hourly cost and 2,700 endpoints.

VPC Lattice resource configurations and service network endpoints

The central endpoints can be exposed as resource configurations in a Lattice service network shared through RAM, reached from spokes through a service network endpoint. Traffic no longer depends on Transit Gateway routes, so it works when spoke CIDRs overlap (after an acquisition, say). The endpoint takes a contiguous /28 per zone from the spoke and, unlike a VPC association, is reachable from on premises. Pricing is per resource configuration hour plus per GB; the September 2026 blog below compares it with the Transit Gateway model. Resource configurations are TCP only, fine for HTTPS APIs.

Cross-Region PrivateLink to AWS services (November 2025)

An interface endpoint created with --service-region can reach some AWS services in another Region; the current list includes S3, IAM, ECR (api and dkr), KMS, ECS, Lambda, Data Firehose, Managed Service for Apache Flink and Route 53, but not SSM, Secrets Manager, STS or CloudWatch Logs. It supports Regional DNS names only, needs vpce:AllowMultiRegion in IAM and the SCP, fails over between zones but not Regions, and the endpoint owner pays inter-Region data transfer on every GB in both directions. AWS recommends staying in-Region where possible.

Associating the endpoints themselves with the Profile

Route 53 Profiles also list interface VPC endpoints as a supported resource type. Its exact behaviour was not confirmed here, so the design keeps the documented zone-per-service pattern.

Testing it

  1. Resolution from a spokeFrom a booking pod, dig +short kms.us-east-1.amazonaws.com and dig +short 222222222222.dkr.ecr.us-east-1.amazonaws.com must return addresses in 10.41.0.0/16. A public address means the VPC lacks the Profile, or the wildcard record is missing. dig +short s3.us-east-1.amazonaws.com must return public S3 addresses: S3 stays on the gateway endpoint.
  2. Resolution from the data centerdig @10.41.0.10 s3.us-east-1.amazonaws.com must return the S3 interface endpoint IPs, and the same name queried from an instance inside the shared services VPC must return public S3 addresses, proving "private DNS only for inbound endpoints".
  3. Path analysisReachability Analyzer from a booking instance to the Secrets Manager endpoint interface on TCP 443 shows the Transit Gateway hop and security group decision, or names the blocking component.
  4. Perimeter denialFrom a company test instance, use credentials of a test account outside o-travel1234 to call aws kms describe-key through the central endpoint. It must fail, and a VpceAccessDenied network activity event with the endpoint ID must appear in the trail. Then copy an object from a company bucket to a bucket outside the organization from a spoke: the gateway endpoint policy must refuse it.
  5. Gateway path for bytesPull a large image on a test node and check VPC flow logs: the layer download goes to S3 public addresses via the gateway endpoint, and Transit Gateway BytesIn for the attachment barely moves.
  6. Zone failureIn a game day, block one endpoint subnet with a network ACL and confirm calls continue through the other two zones.

Troubleshooting checklist. Timeouts to a service name usually mean it resolved publicly (no zone, no Profile, or private DNS still on in the shared services VPC hiding the custom zone). NXDOMAIN for an AWS hostname means an over-broad private zone. AccessDenied with a VpceAccessDenied event is the endpoint policy; plain AccessDenied without it is IAM, a bucket policy or a key policy. Pulls that stall on layers point to the S3 gateway endpoint or its policy.

"Hundreds of VPCs connected by a Transit Gateway need private access to AWS service APIs at the lowest cost, using the default service DNS names" is interface endpoints in a shared services VPC with private DNS disabled, a private hosted zone per service with an alias to the endpoint, associated with every VPC (through a Route 53 Profile), and S3 or DynamoDB gateway endpoints kept in each VPC. Options that leave private DNS enabled on the central endpoints, or route spoke S3 traffic to another VPC's gateway endpoint, are wrong.
