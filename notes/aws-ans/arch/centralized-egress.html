Reference architecture

Centralized egress with NAT gateways and Network Firewall

Instead of NAT gateways in every VPC and Availability Zone, the travel company sends all internet-bound traffic from its spokes over the Transit Gateway to one egress VPC per Region. There it passes AWS Network Firewall, which allows only approved domains, before a NAT gateway in the same AZ takes it to the internet.

Scenario and requirements

The travel company (example.com) already runs the Transit Gateway hub and spoke: one Transit Gateway per Region in the network account 111111111111, with prod, dev, shared and onprem route tables. That page explains associations, propagation and blackholes; this page adds internet egress on top. Today many of the 300 VPCs have their own NAT gateways, which costs an hourly charge per gateway and gives the security team no single place to control where traffic goes. The PCI DSS assessor also wants the card data environment's outbound connections limited to the payment processors it actually uses.

RequirementDesign choice
Fewer NAT gateways, one place to manage internet accessOne egress VPC per Region in the network account, reached from every spoke through the Transit Gateway
Egress must not become a path between segmentsDefault route to egress in the spoke tables, plus blackholes for every RFC 1918 range
Outbound HTTPS only to approved domainsAWS Network Firewall with a strict-order domain allow list on TLS SNI and HTTP Host, default drop established

Survive the loss of one Availability ZoneOne NAT gateway and one firewall endpoint per AZ, route tables per AZ
Evidence for auditors and troubleshootingFirewall alert and flow logs, Transit Gateway flow logs, NAT gateway metrics

The address plan from the hub page still applies: in us-east-1 production 10.40.0.0/16, shared services 10.41.0.0/16, development 10.42.0.0/16, all inside the Region summary 10.40.0.0/14; eu-central-1 uses 10.44.0.0/14 and ap-northeast-1 10.48.0.0/14. The egress VPC takes 10.41.240.0/22 from the shared services range, with three subnet tiers in each of us-east-1a, us-east-1b and us-east-1c: a /28 for the Transit Gateway attachment, a /28 for the firewall endpoint, and a public subnet for the NAT gateway. The same build is repeated in each Region, so European traffic leaves in Frankfurt and does not cross the Atlantic.

How it works

The path below is model A, firewall endpoints inside the egress VPC. Model B (the firewall attached to the Transit Gateway) changes only where the firewall sits; it is built in Step 5.

  1. A booking pod calls a payment processor
  2. Spoke VPC routeAWSA pod at 10.40.12.30 opens HTTPS to api.payments-partner.example. The subnet route table sends 0.0.0.0/0 (and 10.0.0.0/8) to the Transit Gateway ENI in its AZ. The spoke has no NAT gateway and no internet gateway.
  3. Spoke Transit Gateway tableAWSThe booking attachment is associated with prod. No more specific route matches, so the static 0.0.0.0/0 sends the packet to the egress VPC attachment.
  4. Appliance mode picks one AZAWSAppliance mode on the egress attachment hashes the flow and chooses one ENI in the egress VPC. Both directions of this flow use that AZ for its whole life.
  5. Attachment subnet to firewallAWSThe attachment subnet's route table in us-east-1b sends 0.0.0.0/0 to the firewall endpoint in us-east-1b.
  6. Firewall inspectsAWSThe stateless engine forwards to the stateful engine. In strict order, the domain allow list matches the SNI api.payments-partner.example and passes the flow. The firewall sees the pod's real source address, because NAT has not happened yet.
  7. Firewall subnet to NATAWSThe firewall subnet's route table sends 0.0.0.0/0 to the NAT gateway in the same AZ.
  8. NAT and internet gatewayAWSThe NAT gateway translates the source to its Elastic IP and sends the packet through the internet gateway. The payment processor allow-lists the three NAT addresses.
  9. The reply comes backAWSThe NAT gateway translates the reply back to 10.40.12.30. Its subnet route table sends 10.0.0.0/8 to the same-AZ firewall endpoint; the firewall subnet sends 10.0.0.0/8 to the Transit Gateway; the egress table holds the propagated booking VPC route.
  10. A pod tries an unapproved site
  11. Dropped after the handshakeAWSThe TCP handshake to files.unknown-share.example passes, because the SNI is only visible in the TLS Client Hello. That SNI is not on the list, so the default action drop established drops the flow and the firewall writes an alert log entry.
  12. A development host tries production through the egress VPC
  13. Blackholed at the hubAWSWithout the blackholes, a packet from development to 10.40.12.30 would follow 0.0.0.0/0 to the egress VPC, and the egress table (which knows every spoke) would deliver it. The dev table's 10.0.0.0/8 blackhole drops it before it leaves the spoke table.

Build it

Step 1

Transit Gateway routes: default to egress, blackholes for private ranges

Centralized egress uses two kinds of Transit Gateway route table. The spoke tables (here the existing prod, dev and shared) get a static 0.0.0.0/0 to the egress VPC attachment. A new egress table is associated with the egress VPC attachment, and every spoke propagates into it so replies find their way home.

The egress table knows every spoke in every segment. That makes the egress VPC a potential bridge: any private destination that a spoke table does not explicitly route would match 0.0.0.0/0, reach the egress VPC, and be routed back to the destination spoke by the egress table. The fix is a blackhole for each RFC 1918 range in every spoke table. Longest prefix still wins, so the real routes in each table (the propagated shared services /21s, the on-premises 10.100.0.0/16 and 10.200.0.0/16, the peer Region summaries) are more specific than 10.0.0.0/8 and keep working. Without these blackholes, production VPCs, which deliberately do not propagate into prod, could suddenly reach each other through the egress VPC.

The egress table and the default routes with RFC 1918 blackholes (AWS CLI, network account) 
# egress table: only the egress VPC attachment is associated with it
aws ec2 create-transit-gateway-route-table --transit-gateway-id tgw-use1 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=egress}]'
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-egress \
  --transit-gateway-attachment-id tgw-attach-egress

# every spoke propagates into egress so return traffic reaches it (repeat per spoke)
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-egress \
  --transit-gateway-attachment-id tgw-attach-booking-prod

# in prod, dev and shared: internet via the egress VPC
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 0.0.0.0/0 \
  --transit-gateway-attachment-id tgw-attach-egress

# and no private range may reach the egress VPC through that default route
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.0.0.0/8 --blackhole
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 172.16.0.0/12 --blackhole
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 192.168.0.0/16 --blackhole

The onprem table gets no default route, because the data centers have their own internet breakout. In each spoke, the default route now points at the Transit Gateway.

Spoke side: the default route now points at the Transit Gateway (AWS CLI, application account) 
# replaces the old 0.0.0.0/0 to the VPC's own NAT gateway
aws ec2 replace-route --route-table-id rtb-bookings-app \
  --destination-cidr-block 0.0.0.0/0 --transit-gateway-id tgw-use1

The blackhole belongs in the spoke Transit Gateway tables, not in the egress table and not in the egress VPC. The egress VPC needs the opposite: a return route for the spoke ranges back to the Transit Gateway (Step 2). Questions that describe "spokes can now reach each other after centralizing NAT" are missing the spoke-table blackhole.

Step 2

The egress VPC: attachment, NAT gateway per AZ, return routes

The egress VPC has an internet gateway, a NAT gateway with an Elastic IP in each AZ's public subnet, and a Transit Gateway attachment that uses the /28 attachment subnets. Each AZ gets its own route tables, so traffic stays in one AZ and avoids cross-AZ data charges. Before the firewall is added (Step 3), the routing is:

  1. Attachment subnet route table (one per AZ)0.0.0.0/0 to the NAT gateway in the same AZ.
  2. NAT gateway subnet route table (one per AZ)0.0.0.0/0 to the internet gateway, and 10.0.0.0/8 to the Transit Gateway. Without the return route, the NAT gateway translates the reply but has nowhere to send it.
One AZ of the egress VPC; repeat for us-east-1b and us-east-1c (AWS CLI, network account) 
# appliance mode is needed once a firewall is in the path (Step 3); set it from the start
aws ec2 create-transit-gateway-vpc-attachment \
  --transit-gateway-id tgw-use1 \
  --vpc-id vpc-0egressuse1 \
  --subnet-ids subnet-egress-tgw-1a subnet-egress-tgw-1b subnet-egress-tgw-1c \
  --options ApplianceModeSupport=enable,DnsSupport=enable

# a public NAT gateway with an Elastic IP in us-east-1a
aws ec2 create-nat-gateway --subnet-id subnet-egress-nat-1a \
  --allocation-id eipalloc-0natuse1a

# attachment subnet (1a): internet traffic to the same-AZ NAT gateway
aws ec2 create-route --route-table-id rtb-egress-tgw-1a \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id nat-0use1a

# NAT subnet (1a): out to the internet, and replies for spokes back to the hub
aws ec2 create-route --route-table-id rtb-egress-nat-1a \
  --destination-cidr-block 0.0.0.0/0 --gateway-id igw-0egressuse1
aws ec2 create-route --route-table-id rtb-egress-nat-1a \
  --destination-cidr-block 10.0.0.0/8 --transit-gateway-id tgw-use1

Each NAT gateway address supports 55,000 simultaneous connections per unique destination (IP, port and protocol), and a NAT gateway can hold up to 8 addresses; bandwidth starts at 5 Gbps and scales to 100 Gbps. Centralizing concentrates connections onto a few addresses, so watch ErrorPortAllocation.

IPv6 does not need NAT. AWS's guidance is an egress-only internet gateway in each dual-stack VPC (outbound-only and stateful, the IPv6 counterpart of NAT for direction control), or a centralized path through NAT or proxy instances. The booking VPCs are dual-stack, so each gets its own egress-only gateway; inspecting that IPv6 traffic would need a firewall in the VPC itself.

IPv6 egress stays in the spoke: an egress-only internet gateway (AWS CLI, application account) 
aws ec2 create-egress-only-internet-gateway --vpc-id vpc-0bookingprod

aws ec2 create-route --route-table-id rtb-bookings-app \
  --destination-ipv6-cidr-block ::/0 \
  --egress-only-internet-gateway-id eigw-0bookingprod
Step 3

Model A: Network Firewall endpoints inside the egress VPC

The first filtering model puts the firewall in the same VPC as the NAT gateways. Create the firewall with one subnet mapping per AZ; Network Firewall places an endpoint in each firewall subnet. Then insert the endpoint between the attachment subnet and the NAT gateway, and make sure the return path passes it too:

  1. Attachment subnet (per AZ)0.0.0.0/0 to the firewall endpoint in the same AZ.
  2. Firewall subnet (per AZ)0.0.0.0/0 to the NAT gateway in the same AZ, and 10.0.0.0/8 to the Transit Gateway.
  3. NAT gateway subnet (per AZ)0.0.0.0/0 to the internet gateway, and 10.0.0.0/8 now to the same-AZ firewall endpoint instead of the Transit Gateway.
Create the firewall in the egress VPC and re-point one AZ's routes (AWS CLI, network account) 
aws network-firewall create-firewall \
  --firewall-name use1-egress \
  --firewall-policy-arn arn:aws:network-firewall:us-east-1:111111111111:firewall-policy/egress-strict \
  --vpc-id vpc-0egressuse1 \
  --subnet-mappings SubnetId=subnet-egress-fw-1a SubnetId=subnet-egress-fw-1b SubnetId=subnet-egress-fw-1c

# the endpoint ID per AZ is in the firewall's sync states (describe-firewall)
aws ec2 replace-route --route-table-id rtb-egress-tgw-1a \
  --destination-cidr-block 0.0.0.0/0 --vpc-endpoint-id vpce-0fwuse1a

# firewall subnet (1a): on to the NAT gateway, and replies back to the hub
aws ec2 create-route --route-table-id rtb-egress-fw-1a \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id nat-0use1a
aws ec2 create-route --route-table-id rtb-egress-fw-1a \
  --destination-cidr-block 10.0.0.0/8 --transit-gateway-id tgw-use1

# NAT subnet (1a): replies now go back through the firewall
aws ec2 replace-route --route-table-id rtb-egress-nat-1a \
  --destination-cidr-block 10.0.0.0/8 --vpc-endpoint-id vpce-0fwuse1a

Appliance mode (set on the egress attachment in Step 2) makes the Transit Gateway pick one ENI per flow and keep it for both directions. Without it, the Transit Gateway keeps traffic in the source AZ, and once the same firewall also inspects east-west or hybrid flows, the two halves of a conversation can land on different endpoints and be dropped by the stateful engine. It goes on the inspection VPC's attachment, never on the spokes. Two caveats from the documentation: stickiness holds only for traffic that enters the inspection VPC from the Transit Gateway, and turning it on for a live attachment can move existing flows, so do it in a maintenance window.

Put the firewall before the NAT gateway. The firewall then logs and filters on the pod's real address (10.40.12.30), so rules can differ for the card data VPC and the logs show which workload made the call. After NAT, every flow would carry one of three Elastic IPs.

Step 4

The firewall policy: strict order, domain allow list, drop established

The policy forwards everything from the stateless engine to the stateful engine (aws:pass in the stateless engine would skip stateful inspection and logging). The stateful engine runs in strict order: rule groups by priority, rules in the order written, and a default action for whatever matches nothing. In the default action order, by contrast, pass rules win over drop rules wherever they appear, which makes an allow list harder to reason about.

Domain rules match the TLS SNI for HTTPS and the HTTP Host header for HTTP. Both arrive after the TCP handshake, so the default action must be drop established: the handshake is allowed, then any established flow that no rule passed is dropped. "Drop all" would drop the handshake before the domain can be seen, and nothing would ever match. Policies created since June 2026 default to "application drop established (server-directed only)", a variant that waits for application-layer data and avoids dropping keep-alives and resets.

The allow-list rule group; HOME_NET is set to the spoke ranges (AWS CLI, network account) 
aws network-firewall create-rule-group \
  --rule-group-name egress-allowed-domains --type STATEFUL --capacity 100 \
  --rule-group '{
    "RuleVariables": {"IPSets": {"HOME_NET": {"Definition": ["10.40.0.0/14"]}}},
    "RulesSource": {"RulesSourceList": {
      "Targets": [".example.com", ".amazonaws.com", ".payments-partner.example", ".partner-airline.example"],
      "TargetTypes": ["TLS_SNI", "HTTP_HOST"],
      "GeneratedRulesType": "ALLOWLIST"}},
    "StatefulRuleOptions": {"RuleOrder": "STRICT_ORDER"}}'

Domain list rules apply to traffic from HOME_NET. By default that variable is the CIDR of the firewall's own VPC, which in a central design is the egress VPC (10.41.240.0/22), not the spokes, so the rule would never match spoke traffic. Override it with the Region summary as above; for the Transit Gateway-attached firewall in Step 5 the override is mandatory, because the firewall has no VPC CIDR to infer. A leading dot (.example.com) matches the domain and all its subdomains.

The firewall policy that uses it (AWS CLI, network account) 
aws network-firewall create-firewall-policy \
  --firewall-policy-name egress-strict \
  --firewall-policy '{
    "StatelessDefaultActions": ["aws:forward_to_sfe"],
    "StatelessFragmentDefaultActions": ["aws:forward_to_sfe"],
    "StatefulEngineOptions": {"RuleOrder": "STRICT_ORDER"},
    "StatefulDefaultActions": ["aws:drop_established", "aws:alert_established"],
    "StatefulRuleGroupReferences": [
      {"ResourceArn": "arn:aws:network-firewall:us-east-1:111111111111:stateful-rulegroup/egress-allowed-domains", "Priority": 100}]}'

The policy and every stateful rule group in it must use the same rule order. The card data VPC can get a tighter list from a second rule group at a lower priority number, with source addresses limited to the payments CIDR, so the general list never applies to it. Analysis mode on TLS_SNI and HTTP_HOST reports the domains actually used over the last 30 days, a good starting point for the list.

Step 5

Model B: the firewall attached natively to the Transit Gateway

Since July 2025 in all Regions, Network Firewall can attach directly to a Transit Gateway. AWS owns a hidden VPC with the endpoints; the firewall appears on the Transit Gateway as a network function attachment. You build no inspection VPC, appliance mode is always on, and traffic reaches the firewall only through static routes in Transit Gateway route tables (no propagation from the firewall, no VPC route tables). The firewall's AZs must already be enabled on the Transit Gateway.

Because the managed VPC cannot hold a NAT gateway or an internet gateway, internet egress still needs a separate egress VPC, built exactly as in Step 2 without firewall subnets. The routing moves into the hub:

  1. Spoke tables (prod, dev, shared)0.0.0.0/0 to the firewall attachment, plus the RFC 1918 blackholes from Step 1.
  2. Firewall table (associated with the firewall attachment)0.0.0.0/0 to the egress VPC attachment, and the spoke routes (propagated from the spokes) for inspected return traffic.
  3. Egress table (associated with the egress VPC attachment)A static 10.0.0.0/8 to the firewall attachment, and no spoke propagations. A propagated /21 would beat the /8 and send replies straight to the spoke, bypassing the firewall on the way back, and the stateful engine would drop the half-seen flow.
  4. Egress VPCAttachment subnets to the same-AZ NAT gateway; NAT subnets to the internet gateway and 10.0.0.0/8 to the Transit Gateway.
Create the attached firewall and route through it (AWS CLI, network account) 
# no VPC or subnets: the Transit Gateway and its AZs, fixed at creation
aws network-firewall create-firewall \
  --firewall-name use1-central \
  --firewall-policy-arn arn:aws:network-firewall:us-east-1:111111111111:firewall-policy/egress-strict \
  --transit-gateway-id tgw-use1 \
  --availability-zone-mappings AvailabilityZone=us-east-1a AvailabilityZone=us-east-1b AvailabilityZone=us-east-1c

# spokes: internet traffic goes to the firewall first
aws ec2 replace-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 0.0.0.0/0 \
  --transit-gateway-attachment-id tgw-attach-firewall

# after inspection: on to the egress VPC
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-firewall \
  --destination-cidr-block 0.0.0.0/0 \
  --transit-gateway-attachment-id tgw-attach-egress

# replies from the egress VPC are inspected before reaching a spoke
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-egress \
  --destination-cidr-block 10.0.0.0/8 \
  --transit-gateway-attachment-id tgw-attach-firewall

The firewall can be owned by a separate security account: the network account shares the Transit Gateway through RAM, the security account creates the firewall, and the network account accepts the pending attachment (unless auto accept is on). The attached firewall itself cannot be shared through RAM; share the Transit Gateway instead. Either account can delete the firewall, and the Transit Gateway cannot be deleted while the attachment exists.

The 2021 blog that introduced the inspection-VPC pattern now carries an AWS note recommending the Transit Gateway-attached firewall for new designs. Model A is still valid and still common in exam questions, especially where a third-party firewall behind Gateway Load Balancer is needed, which the native attachment does not support.

Step 6

DNS Firewall against DNS exfiltration

A blocked HTTPS connection does not stop a compromised pod from encoding data into DNS lookups such as c2VjcmV0.tunnel.bad.example. Those queries go to the VPC Resolver (VPC base +2) in the spoke itself, never cross the Transit Gateway and cannot be filtered by security groups or network ACLs, so Network Firewall never sees them. Route 53 Resolver DNS Firewall filters queries that pass through the VPC Resolver: rule groups of domain lists (yours or AWS managed), evaluated by priority, with actions ALLOW, ALERT or BLOCK (responses NODATA, NXDOMAIN or a CNAME OVERRIDE). It works on names only: it does not inspect connections, and clients using their own DNS servers bypass it, which is why it is paired with Network Firewall.

Block a list of bad domains for the booking VPC (AWS CLI; repeat per Region, DNS Firewall is Regional) 
aws route53resolver create-firewall-domain-list \
  --creator-request-id dl-use1-1 --name blocked-domains
aws route53resolver update-firewall-domains \
  --firewall-domain-list-id DOMAIN_LIST_ID --operation ADD \
  --domains "*.tunnel.bad.example" "*.unknown-share.example"

aws route53resolver create-firewall-rule-group \
  --creator-request-id rg-use1-1 --name egress-dns
# test as ALERT first, then switch to BLOCK
aws route53resolver create-firewall-rule \
  --creator-request-id r-use1-1 --name block-bad \
  --firewall-rule-group-id RULE_GROUP_ID \
  --firewall-domain-list-id DOMAIN_LIST_ID \
  --priority 100 --action BLOCK --block-response NXDOMAIN

# association priority must be between 100 and 9900
aws route53resolver associate-firewall-rule-group \
  --name booking-dns-fw --firewall-rule-group-id RULE_GROUP_ID \
  --vpc-id vpc-0bookingprod --priority 101

Across 300 VPCs, nobody associates rule groups by hand: share the rule group through RAM and add it to the Route 53 Profile the spokes already use, or let Firewall Manager associate it with every in-scope VPC. DNS Firewall fails closed by default (unanswered queries get SERVFAIL); choose fail open only where availability matters more than filtering. DNS Firewall Advanced adds detection of DGA and tunneling patterns.

Step 7

Logging and monitoring

Network Firewall logs only traffic that reaches the stateful engine, which is why Step 4 forwards everything there. Alert logs record flows that hit a drop, alert or reject action (including the default drop established); flow logs record every flow the stateful engine saw; TLS logs need TLS inspection. Each type can go to S3, CloudWatch Logs or Firehose.

Alert logs to CloudWatch Logs for alarms, flow logs to the central bucket (CloudFormation, network account) 
EgressFirewallLogging:
  Type: AWS::NetworkFirewall::LoggingConfiguration
  Properties:
    FirewallArn: !GetAtt EgressFirewall.FirewallArn
    LoggingConfiguration:
      LogDestinationConfigs:
        # dropped and alerted flows: searched during incidents, alarmed on
        - LogType: ALERT
          LogDestinationType: CloudWatchLogs
          LogDestination:
            logGroup: /network-firewall/use1-egress/alert
        # every inspected flow: kept cheaply for audits and Athena
        - LogType: FLOW
          LogDestinationType: S3
          LogDestination:
            bucketName: central-flow-logs-111111111111
            prefix: nfw/use1-egress

The hub already has Transit Gateway flow logs (see the hub page, Step 6). For egress, per-attachment logs on the egress or firewall attachment show which spoke account sends the most internet traffic, which matters because that account's bytes drive the processing charges. For the Transit Gateway-attached firewall these logs, together with the firewall's own logs, are the main visibility: VPC flow logs and PrivateLink metrics are not available for its hidden endpoint ENIs.

Flow logs for the egress attachment only (AWS CLI, network account) 
aws ec2 create-flow-logs --resource-type TransitGatewayAttachment \
  --resource-ids tgw-attach-egress \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::central-flow-logs-111111111111/tgw-egress/

On the NAT gateways, alarm on ErrorPortAllocation above zero (port exhaustion to one destination) and on PacketsDropCount. Resolver query logs record DNS Firewall matches.

Design decisions

One egress VPC per Region, in the network account

Internet traffic leaves in the Region where it starts, so a Frankfurt booking call does not pay inter-Region transfer or latency to reach a US NAT gateway, and data stays in the Region for residency rules. The network team owns the internet gateways; an SCP keeps application accounts from creating their own, so the egress VPC really is the only way out. See Task 1.6 and Task 2.2.

Cost: hours saved, bytes added

Centralizing trades many hourly charges for per-GB charges. Using the published rates: a NAT gateway is $0.045 an hour and $0.045 per GB (the Ohio example on the pricing page), Transit Gateway data processing is $0.02 per GB on every byte a VPC sends into it, and a Network Firewall endpoint is $0.395 an hour plus $0.065 per GB in us-east-1. When a NAT gateway is service-chained with Network Firewall (same account, same Region, same network path), the NAT gateway's hourly and per-GB charges are waived one-to-one against firewall endpoint hours and gigabytes.

  • Before: 300 VPCs with NAT gateways in two AZs is 600 × $0.045 × 730 ≈ $19,700 a month in NAT hours alone, with no filtering.
  • Model A: three firewall endpoints are 3 × $0.395 × 730 ≈ $865 a month, and the three NAT gateways' hours are waived. If 50 TB (51,200 GB) a month crosses the hub, Transit Gateway processing adds about $1,024 and firewall processing about $3,330, while the NAT per-GB charge is waived.
  • Model B: egress traffic crosses the Transit Gateway twice (spoke to firewall, firewall to egress VPC), and each hop is processed, so the same 50 TB costs about $2,048 in Transit Gateway processing. The pricing page does not say whether a NAT gateway in a separate egress VPC qualifies for the service-chain waiver, so budget for NAT charges unless AWS confirms it for your setup.

The catch is volume. A VPC that downloads hundreds of terabytes (for example a data pipeline pulling partner fare files) pays $0.02 per GB extra through the hub; a local NAT gateway, or VPC endpoints for AWS services, can be cheaper for that one VPC. Gateway endpoints for S3 and DynamoDB are free but work only in their own VPC, so each spoke should keep its own rather than sending S3 traffic through egress. See Task 3.3.

Availability: one of everything per AZ

A NAT gateway and a firewall endpoint are zonal. With one of each per AZ and per-AZ route tables, losing us-east-1b takes out its Transit Gateway ENI, NAT gateway and endpoint together, and the Transit Gateway sends new flows through the remaining AZs; flows that were pinned to us-east-1b must reconnect. The weaker case is a single component failing while its AZ is healthy: VPC route tables do not fail over by themselves, so a broken NAT gateway in one AZ blackholes the flows hashed to it until routes are changed. Give the egress VPC an attachment subnet in every AZ the spokes use, and use AZ IDs (not names) when matching AZs across accounts. Resources in a spoke can only reach the Transit Gateway from AZs where that spoke has an attachment subnet.

Model A or model B

Model A keeps everything in one VPC that you can see and troubleshoot with VPC flow logs, and the NAT waiver clearly applies. Model B removes the inspection VPC, the per-AZ firewall route tables and the appliance-mode setting, lets a separate security account own the firewall, and supports Flexible Cost Allocation metering policies that charge firewall data processing back to spoke accounts. Its costs are the second Transit Gateway hop and less visibility into the managed endpoints. The travel company runs model B.

Filtering on names, not addresses

Partner APIs sit behind CDNs whose addresses change, so IP allow lists break; SNI and Host matching follows the name. SNI can be forged by a client that controls both ends, so where that is in the threat model add TLS inspection or Route 53 resolved IP validation (October 2026). See Task 4.1.

Alternatives

Distributed NAT gateways (and firewalls) per VPC

No Transit Gateway processing, no shared blast radius, and each team controls its own internet path. It costs an hourly charge per NAT gateway per AZ in every VPC, and filtering would need a firewall in every VPC. It fits a few high-volume VPCs, not 300.

Regional NAT gateway

Since November 2025 a NAT gateway can run in regional availability mode: no public subnet, its own route table with a route to the internet gateway (the Transit Gateway is a valid target there), automatic expansion to AZs where ENIs appear (which can take up to 60 minutes), billed per AZ-hour. It simplifies the egress VPC's NAT tier, but it does not support private NAT, and how it combines with firewall service chaining should be checked before relying on it.

Gateway Load Balancer with third-party firewalls

The same egress VPC, with Gateway Load Balancer endpoints in place of Network Firewall endpoints and a vendor firewall fleet behind GENEVE on port 6081. Use it when the security team needs a specific vendor's features. Appliance mode is still required on the egress attachment, and GWLB 2-tuple or 3-tuple stickiness cannot be combined with it.

Testing it

  1. An allowed domain worksFrom a booking pod, curl -sv https://api.payments-partner.example/health should succeed, and the payment processor should see one of the three NAT Elastic IPs as the source. The firewall flow log shows the pod's own 10.40.x address.
  2. An unapproved domain failscurl -sv https://files.unknown-share.example should complete the TCP handshake and then hang or reset after the Client Hello, with a matching alert log entry naming the SNI. If the handshake itself fails, the default action is drop all instead of drop established.
  3. Segments stay apartReachability Analyzer from a development instance to a production ENI should fail at the dev Transit Gateway route table. From a booking instance to the internet gateway, it should succeed through the NAT gateway and the firewall; it evaluates Network Firewall 5-tuple rules only, so domain rules are tested with real traffic.
  4. The return path is inspectedFor model B, temporarily remove the static 10.0.0.0/8 from the egress table in a test Region: replies bypass the firewall and connections fail, proving the route is what keeps the flow symmetric. Restore it and confirm traffic recovers.
  5. DNS exfiltration is blockeddig test.tunnel.bad.example from a spoke should return NXDOMAIN, and the Resolver query log should record the DNS Firewall rule.
  6. An AZ goes awayIn a staging copy, delete the attachment subnet path in one AZ (or the NAT gateway there) and run a synthetic check that opens many short connections. Watch which flows fail and how long recovery takes, and confirm the NAT gateway alarms fire.
