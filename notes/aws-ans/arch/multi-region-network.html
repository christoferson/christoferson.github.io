Multi-Region network: Transit Gateway peering or Cloud WAN

The travel company joins its three Regional hubs into one private network. Option A peers the Transit Gateways in a full mesh with static summary routes; option B replaces the mesh with an AWS Cloud WAN core network whose segments, attachments and inspection are defined in one policy document. This page builds both, then shows how to move from A to B without a flag day.

Scenario and requirements

The travel company (example.com) already runs the Transit Gateway hub and spoke in each of us-east-1, eu-central-1 and ap-northeast-1, owned by the network account 111111111111, with prod, dev, shared and onprem route tables, and centralized egress in every Region. That page set explains associations, propagation, blackholes and egress; this page connects the three hubs. Frankfurt bookings call shared fare services in Virginia, both data centers reach every Region, development in one Region must never reach production in another, and card data paths must stay inspectable for PCI DSS.

RequirementDesign choice

New VPCs land in the right segment without ticketsA: EventBridge automation per Region; B: tag-based attachment policies

Move from A to B with no outageTransit Gateway peering to the core network and route table attachments, segment by segment

The hub page's address plan keeps routing small: one /14 per Region, split the same way:

  • us-east-1 10.40.0.0/14: production 10.40.0.0/16, shared services 10.41.0.0/16, development 10.42.0.0/16; Transit Gateway tgw-use1, ASN 64521.
  • eu-central-1 10.44.0.0/14: production 10.44.0.0/16, shared 10.45.0.0/16, development 10.46.0.0/16; tgw-euc1, ASN 64522.
  • ap-northeast-1 10.48.0.0/14: production 10.48.0.0/16, shared 10.49.0.0/16, development 10.50.0.0/16; tgw-apne1, ASN 64523.
  • On premises: US data center 10.100.0.0/16 (AS 65010) and European data center 10.200.0.0/16 (AS 65020) on Direct Connect gateway dxgw-travel-global (AS 64512), associated with all three Transit Gateways.

How it works

The same request, a Frankfurt booking pod at 10.44.12.30 calling the fare service at 10.41.20.15 in Virginia, takes a different path in each option.

  1. Option A: across Transit Gateway peering
  2. Spoke routeAWSThe pod's subnet route table sends 10.0.0.0/8 to tgw-euc1 in its Availability Zone, as on the hub page.
  3. Sending tableAWSThe booking attachment is associated with the Frankfurt prod table. A static route 10.41.0.0/16 points to the peering attachment toward tgw-use1. Frankfurt charges $0.02 per GB processing, because the bytes entered from a VPC.
  4. Across the backboneAWSEncrypted on the AWS backbone, 8500-byte MTU, inter-Region data transfer billed.
  5. Receiving tableAWSIn Virginia the peering attachment is associated with a peer table that holds the propagated local VPC routes. Traffic arriving from a peering is not charged processing again.
  6. The replyAWSThe Virginia shared table has static routes for the Frankfurt summaries to the same peering.
  7. Option A: Tokyo development tries Frankfurt production
  8. No route at the sourceAWSThe Tokyo dev table holds static routes only for the other Regions' development and shared /16s. 10.44.0.0/16 hits only the RFC 1918 blackhole from the egress design, so the packet dies in Tokyo.
  9. Option B: across the Cloud WAN core network
  10. Spoke routeAWSThe subnet route table now points 10.0.0.0/8 at the core network. The attachment, tagged segment=prod, sits in the prod segment.
  11. Frankfurt edge lookupAWSThe Frankfurt edge looks up the prod segment, where the shared-to-prod share placed the Virginia shared services routes, learned over BGP.
  12. Edge to edgeAWSEdges peer automatically with each other: no peering to build, no static route. $0.02 per GB processing from the VPC, plus inter-Region data transfer.
  13. Delivered in VirginiaAWSThe Virginia edge forwards to the shared services attachment; the reply follows the shared segment's routes back.
  14. Option B: data center to production, inspected
  15. Through the network function groupAWSA packet from 10.100.20.5 enters through the Direct Connect gateway attachment in the onprem segment. A send-via action steers it through the inspection VPC in the inspection network function group before the booking VPC.

Build it

Steps 1 and 2 are option A; Steps 3 to 7 build option B and the migration toward it.

Step 1

Peer the three Transit Gateways

Three Regions need three peering attachments: Virginia to Frankfurt, Virginia to Tokyo and Frankfurt to Tokyo. Only one peering is allowed between two Transit Gateways, so the mesh is n(n−1)/2 peerings; a fourth Region adds three. The accepter's owner accepts, and each side pays its own attachment-hour.

Transit Gateway peering between Transit Gateways is static routing only. AWS still recommends unique ASNs per peered Transit Gateway for future route propagation, and option B needs them to differ from the Cloud WAN edges; the hubs use 64521 to 64523.

Request the Virginia to Frankfurt peering and accept it in Frankfurt (AWS CLI, network account) 
# requester side, us-east-1
aws ec2 create-transit-gateway-peering-attachment --region us-east-1 \
  --transit-gateway-id tgw-use1 \
  --peer-transit-gateway-id tgw-euc1 \
  --peer-account-id 111111111111 \
  --peer-region eu-central-1 \
  --tag-specifications 'ResourceType=transit-gateway-attachment,Tags=[{Key=Name,Value=peer-use1-euc1}]'

# accepter side, run in the peer Region
aws ec2 accept-transit-gateway-peering-attachment --region eu-central-1 \
  --transit-gateway-attachment-id tgw-attach-peer-use1-euc1

# repeat for use1-apne1 and euc1-apne1: three peerings for a full mesh
  • MTU: 8500 bytes over intra-Region, inter-Region and Cloud WAN peering attachments. No Path MTU Discovery on peering attachments, so larger do-not-fragment packets are silently dropped.
  • Encryption: inter-Region traffic is AES-256 encrypted at the virtual network layer, plus physical-layer encryption on links outside AWS control.
  • DNS: a Transit Gateway peering does not resolve public or private DNS hostnames to private IPs in another Region through Route 53 Resolver. Use Resolver endpoints and rules per Region, or associate private hosted zones with VPCs in every Region (Task 2.3).
Step 2

Static summaries in the right tables only

A peering attachment is associated with exactly one route table, so traffic arriving from Frankfurt is looked up in one table whatever its segment: the receiver cannot tell production from development. Segmentation across Regions is enforced at the sending side, with static routes only for the peer summaries each table may reach.

  • prod: peer production and shared services /16s (for Virginia: 10.44.0.0/16, 10.45.0.0/16, 10.48.0.0/16, 10.49.0.0/16).
  • dev: peer development and shared services /16s (10.45, 10.46, 10.49, 10.50).
  • shared: the peer Regions' whole /14s, so shared services reach everything.
  • onprem: nothing new; each data center already reaches every Region directly through the Direct Connect gateway associations, which is shorter than hairpinning through another Region.
  • A new peer table, associated with the peering attachments, holds the local VPC routes by propagation.
Virginia: the peer table, and production's static routes to Frankfurt (AWS CLI, network account) 
# one table for traffic arriving over the peerings
aws ec2 create-transit-gateway-route-table --transit-gateway-id tgw-use1 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=peer}]'
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-peer \
  --transit-gateway-attachment-id tgw-attach-peer-use1-euc1

# local spokes propagate into peer so returning traffic finds them (repeat per spoke)
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-peer \
  --transit-gateway-attachment-id tgw-attach-booking-prod

# prod may reach Frankfurt production and shared services, nothing else
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.44.0.0/16 --transit-gateway-attachment-id tgw-attach-peer-use1-euc1
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.45.0.0/16 --transit-gateway-attachment-id tgw-attach-peer-use1-euc1

That is about thirty static routes for the whole mesh, manageable only because IPAM keeps each environment in one /16 per Region; random CIDRs would mean a route per VPC in every peer Region. A managed prefix list per segment (hub page) keeps Regions identical.

Static routes never withdraw. If a production VPC is deleted, or a whole Region becomes unreachable, the summary in the peer Regions still points at the peering and the traffic is dropped there instead of failing over. Region failover belongs to the application and DNS layer (Route 53 or ARC), not to the peering mesh.

Step 3

The core network policy

Option B adds a core network to the existing global network. One JSON policy defines edges, ASNs, segments, sharing, inspection, attachment placement and, since version 2025.11, routing policies. Each Region in edge-locations gets a core network edge, peered with every other edge; a Region cannot be removed while it has attachments.

Design choices in this policy:

  • ASNs 64531 to 64533 avoid the Transit Gateways and Direct Connect gateways. An edge's ASN cannot change, and a Transit Gateway with the same ASN cannot peer with it.
  • Segments are global VRFs. prod uses isolate-attachments (production VPCs do not reach each other, as on the hub); dev needs no acceptance; onprem holds the Direct Connect gateway attachment.
  • Share is not transitive. Sharing shared with prod and dev gives both access to shared services but does not join production to development, and shared routes are not re-shared.
  • Inspection: the inspection network function group holds one inspection VPC per Region. send-via (single-hop) sends onprem-to-prod traffic through it, cross-Region flows through one Region chosen by priority or edge overrides; send-to covers north-south egress.
  • Attachment policies: rule 50 puts inspection-tagged attachments in the network function group; rule 100 maps others to the segment in their segment tag. Lowest rule first, first match wins; no match means no segment.
core-network-policy.json: three edges, four segments, hybrid inspection and tag-based placement (version 2025.11) 
{
  "version": "2025.11",
  "core-network-configuration": {
    "vpn-ecmp-support": true,
    "dns-support": true,
    "security-group-referencing-support": true,
    "asn-ranges": ["64530-64540"],
    "edge-locations": [
      {"location": "us-east-1", "asn": 64531},
      {"location": "eu-central-1", "asn": 64532},
      {"location": "ap-northeast-1", "asn": 64533}
    ]
  },
  "segments": [
    {"name": "prod", "isolate-attachments": true, "require-attachment-acceptance": true},
    {"name": "dev", "require-attachment-acceptance": false},
    {"name": "shared", "require-attachment-acceptance": true},
    {"name": "onprem", "require-attachment-acceptance": true, "deny-filter": ["dev"]}
  ],
  "network-function-groups": [
    {"name": "inspection", "require-attachment-acceptance": true}
  ],
  "segment-actions": [
    {"action": "share", "mode": "attachment-route", "segment": "shared", "share-with": ["prod", "dev"]},
    {"action": "share", "mode": "attachment-route", "segment": "onprem", "share-with": ["shared"]},
    {"action": "send-via", "segment": "onprem", "mode": "single-hop",
     "when-sent-to": {"segments": ["prod"]},
     "via": {"network-function-groups": ["inspection"]}}
  ],
  "attachment-policies": [
    {"rule-number": 50, "condition-logic": "and",
     "conditions": [{"type": "tag-exists", "key": "inspection"}],
     "action": {"add-to-network-function-group": "inspection"}},
    {"rule-number": 100, "condition-logic": "or",
     "conditions": [{"type": "tag-exists", "key": "segment"}],
     "action": {"association-method": "tag", "tag-value-of-key": "segment"}}
  ]
}

The deny-filter on onprem is a backstop like the blackholes: whatever shares are added later, no routes flow between the data centers and development.

Create the core network with the policy (AWS CLI, network account, Network Manager home Region) 
aws networkmanager create-core-network --region us-west-2 \
  --global-network-id global-network-0travel1234567 \
  --description "travel core network" \
  --policy-document file://core-network-policy.json

Every change is a new policy version with a change set you review before executing, so a wrong share is caught before it reaches the network (Task 2.4).

Step 4

VPC attachments placed by tag

The attachment policy reads the attachment's tags, not the VPC's. Production and shared segments require acceptance; development attachments go live at once, and without acceptance a changed tag also moves an attachment between segments, one reason production keeps it on. Security group referencing (June 2025) works only between VPCs on the same edge, so the same Region.

A Frankfurt production VPC joins the prod segment; the inspection VPC joins the network function group with appliance mode (AWS CLI) 
# booking account in eu-central-1: the tag value must match a segment name exactly
aws networkmanager create-vpc-attachment --region us-west-2 \
  --core-network-id core-network-0travel123456 \
  --vpc-arn arn:aws:ec2:eu-central-1:222222222222:vpc/vpc-0bookingeuc1 \
  --subnet-arns arn:aws:ec2:eu-central-1:222222222222:subnet/subnet-0cwan1a arn:aws:ec2:eu-central-1:222222222222:subnet/subnet-0cwan1b arn:aws:ec2:eu-central-1:222222222222:subnet/subnet-0cwan1c \
  --tags Key=segment,Value=prod

# network account: appliance mode keeps both directions of a flow on one firewall AZ
aws networkmanager create-vpc-attachment --region us-west-2 \
  --core-network-id core-network-0travel123456 \
  --vpc-arn arn:aws:ec2:eu-central-1:111111111111:vpc/vpc-0inspecteuc1 \
  --subnet-arns arn:aws:ec2:eu-central-1:111111111111:subnet/subnet-0insp1a arn:aws:ec2:eu-central-1:111111111111:subnet/subnet-0insp1b arn:aws:ec2:eu-central-1:111111111111:subnet/subnet-0insp1c \
  --options ApplianceModeSupport=true \
  --tags Key=inspection,Value=true

Appliance mode is still needed for stateful inspection behind service insertion, exactly as on the egress page; the network function group does not turn it on. A tag typo such as segment=Prod matches no segment, leaving an attachment with no routes.

Step 5

Migrate through Transit Gateway peering and route table attachments

Each Transit Gateway peers with the edge in its own Region, and a route table attachment maps one Transit Gateway route table to one segment, so prod, dev and shared stay separate end to end while VPCs remain on the Transit Gateways.

Unlike Transit Gateway to Transit Gateway peering, this peering uses dynamic BGP only; adding a static route to it returns an error. The Transit Gateway side uses a policy table on the peering attachment, filled in automatically. Route table attachments ignore isolate-attachments, so what the prod table propagates is the network team's responsibility.

Peer tgw-use1 with the us-east-1 edge and map its prod table to the prod segment (AWS CLI, network account) 
# the Transit Gateway ASN (64521) differs from the edge ASN (64531), so the peering can form
aws networkmanager create-transit-gateway-peering --region us-west-2 \
  --core-network-id core-network-0travel123456 \
  --transit-gateway-arn arn:aws:ec2:us-east-1:111111111111:transit-gateway/tgw-use1

# one route table attachment per table; the tag places it in the matching segment
aws networkmanager create-transit-gateway-route-table-attachment --region us-west-2 \
  --peering-id peering-0use1prod1234 \
  --transit-gateway-route-table-arn arn:aws:ec2:us-east-1:111111111111:transit-gateway-route-table/tgw-rtb-prod \
  --tags Key=segment,Value=prod

A migration sequence that keeps traffic flowing:

  1. Build the core networkEdges and segments, no attachments; edge-hours start.
  2. Peer every Transit GatewayThree peerings and route table attachments per table; cross-Region routes now also arrive dynamically.
  3. Remove the static routesDelete Step 2's summaries table by table; otherwise they keep winning, since static beats propagated for the same prefix.
  4. Delete the meshRemove the idle inter-Region peerings.
  5. Move VPCsRe-attach VPCs to the core network by tag, a few at a time.

During the overlap both networks are paid for: each Transit Gateway peering to an edge is $0.065 an hour on the Cloud WAN side plus $0.05 an hour on the Transit Gateway side, with no Cloud WAN processing charge across that peering.

Step 6

Direct Connect gateway attachments on Cloud WAN

Since November 2024 a Direct Connect gateway can attach to the core network directly (all Cloud WAN Regions since June 2025), with no Transit Gateway in between. Three rules shape the migration:

  • A Direct Connect gateway associated with a core network cannot be used for any other gateway type while associated: no Transit Gateways, no virtual private gateways, no private VIFs. So dxgw-travel-global keeps serving the Transit Gateways and a new dxgw-travel-cwan with its own transit VIFs serves Cloud WAN.
  • Its ASN must be outside the core network's asn-ranges, so 64512 and the new gateway's ASN are both fine with 64530 to 64540.
  • There are no allowed prefixes and no static routes toward the attachment. Routing is BGP both ways: each edge advertises its local routes, and data center routes are learned at every associated edge.
Attach the Cloud WAN Direct Connect gateway to all three edges in the onprem segment (AWS CLI, network account) 
aws networkmanager create-direct-connect-gateway-attachment --region us-west-2 \
  --core-network-id core-network-0travel123456 \
  --direct-connect-gateway-arn arn:aws:directconnect::111111111111:dx-gateway/DXGW_ID \
  --edge-locations us-east-1 eu-central-1 ap-northeast-1 \
  --routing-policy-label dxonprem \
  --tags Key=segment,Value=onprem

Because allowed prefixes are gone, route control moves into routing policies (policy version 2025.11, GA November 2025, no extra cost). The policy below, bound by the routing policy label (which only the core network owner can set), drops a leaked default route; outbound summarize and AS path prepending are other common uses.

Added to core-network-policy.json: drop a leaked default route from the data centers, accept their 10.0.0.0/8 routes 
"routing-policies": [
  {
    "routing-policy-name": "dxInboundFilter",
    "routing-policy-direction": "inbound",
    "routing-policy-number": 100,
    "routing-policy-rules": [
      {"rule-number": 10,
       "rule-definition": {
         "match-conditions": [{"type": "prefix-equals", "value": "0.0.0.0/0"}],
         "condition-logic": "and",
         "action": {"type": "drop"}}},
      {"rule-number": 20,
       "rule-definition": {
         "match-conditions": [{"type": "prefix-in-cidr", "value": "10.0.0.0/8"}],
         "condition-logic": "and",
         "action": {"type": "allow"}}}
    ]
  }
],
"attachment-routing-policy-rules": [
  {"rule-number": 10,
   "conditions": [{"type": "routing-policy-label", "value": "dxonprem"}],
   "action": {"associate-routing-policies": ["dxInboundFilter"]}}
]

Drop and allow are terminal, so non-terminal actions go first. During migration the data centers learn AWS prefixes from both Direct Connect gateways; prepend on the new path until cut-over (Task 2.1).

Step 7

Flow logs for the core network

Cloud WAN flow logs (November 2026) are scoped to the core network, an edge or an attachment, and go to CloudWatch Logs, S3 or Firehose with no Cloud WAN charge. Fields include src-segment-name, dst-segment-name, src-region, dst-region, the network function group attachments a flow passed, and drop reasons such as drop:no-route.

Flow logs for the whole core network, created in the home Region (AWS CLI, network account) 
aws ec2 create-flow-logs --region us-west-2 \
  --resource-type CoreNetwork \
  --resource-ids core-network-0travel123456 \
  --log-group-name /cloudwan/travel-core \
  --deliver-logs-permission-arn arn:aws:iam::111111111111:role/cwan-flow-logs

Grouping by Region pair gives the bytes that drive transfer cost; on option A, Transit Gateway flow logs on the peering attachments do the same (hub page).

Design decisions

Peering mesh or Cloud WAN

The Cloud WAN FAQ describes the Transit Gateway path as suited to "a few AWS Regions" where you want to manage your own peering and routing configuration. Three summarized Regions sit on that line, so the company started with A. Each added Region or segment favours Cloud WAN: more peerings, routes multiplied by segments times Regions, segmentation only at the sender. See Task 1.6.

Cost comparison

Take 100 VPC attachments across the three Regions and 10 TB (10,240 GB) a month crossing Regions.

  • Option A: VPC attachments 100 × $0.05 × 730 ≈ $3,650; peering attachments 3 peerings × 2 sides × $0.05 × 730 ≈ $219; processing 10,240 GB × $0.02 ≈ $205 on the sending gateways. Total about $4,074 plus inter-Region data transfer.
  • Option B: three edges 3 × $0.50 × 730 ≈ $1,095 before any traffic; VPC attachments 100 × $0.065 × 730 ≈ $4,745 at the us-east-1 rate (Frankfurt's published example is $0.080); the same $205 processing. Total about $6,045 plus the same inter-Region data transfer.

Inter-Region data transfer is identical in both and is often the largest line; the AWS example prices Virginia to Oregon at $0.02 per GB, and other Region pairs differ. Cloud WAN's premium is roughly $2,000 a month, bought back in fewer route changes and mistakes. Rates outside us-east-1 differ. See Task 3.3.

Failure behaviour

Both survive an AZ loss if attachments span every AZ used. Option A's static summaries stay installed when a peer Region or its VPCs fail, so traffic is blackholed rather than rerouted. Option B's routes are dynamic: when attachments go away their routes are withdrawn across all edges, and data center routes learned through the Direct Connect gateway at several edges remain reachable through the surviving edges. Neither design moves an application to another Region; that is the job of Route 53 health checks or ARC (Task 1.1).

Hybrid: Direct Connect gateway with Transit Gateways, or attached to Cloud WAN

With Transit Gateways, one Direct Connect gateway associates with every Regional Transit Gateway and advertises the allowed prefixes you choose, one summary per Region. With Cloud WAN, the Direct Connect gateway attaches to the core network once, routing is fully BGP with no allowed prefixes, and routing policies replace them. See Task 1.5.

Segment count and quotas

Cloud WAN allows 40 segments per core network (raised through your account team), 5,000 attachments and 10,000 routes across all segments. Segments are for routing domains, not teams; isolate-attachments handles "same segment, no talking". On option A, the 20 route tables per Transit Gateway and 50 peering attachments are the ceilings.

Alternatives

Inter-Region VPC peering

For one heavy cross-Region pair, such as the Tokyo booking database replicating to Virginia, a direct VPC peering has no hourly or processing charge, only inter-Region data transfer, also with 8500-byte MTU since March 2025. It is not transitive, so it complements a hub for a few pairs (hub page, Step 7).

Transit Gateways with Cloud WAN as the backbone only

Keep VPCs on the Regional Transit Gateways permanently and use Cloud WAN only between Regions, through peering and route table attachments. This keeps Transit Gateway-only features such as multicast, at the price of two services to pay for and configure.

SD-WAN overlay

A vendor SD-WAN fabric between Regions and branches can carry segments as VRFs. Connect attachments map each VRF to a route table or segment, at the cost of appliances to run.

Testing it

  1. Check the route tables firstOn option A, check each Region's gateway with Network Manager Route Analyzer or search-transit-gateway-routes: Frankfurt prod must hold the static 10.41.0.0/16 to the Virginia peering, and the Virginia peer table the propagated shared services route. On option B, the core network's route view per segment and edge should show the Virginia shared services routes in the Frankfurt prod segment, and no development routes there.
  2. Prove the boundaryFrom a Tokyo development instance, connect to 10.44.12.30. It must fail; on option A the Tokyo gateway's PacketDropCountBlackhole rises, on option B a Cloud WAN flow log record shows src-segment-name dev with a drop destination type such as drop:no-route.
  3. Test the MTUBetween Frankfurt and Virginia, send pings with the do-not-fragment bit at 8500 bytes and just above. Larger ones are dropped; keep application MTU below the limit.
  4. Test placementCreate an attachment tagged segment=Prod from a sandbox account and confirm it is not associated with any segment; one tagged segment=prod must wait for acceptance; one tagged segment=dev must go live without it.
  5. Fail a Region's hybrid pathIn a maintenance window, shut the BGP sessions on the US data center's transit VIF to the Cloud WAN Direct Connect gateway. Virginia should reach 10.100.0.0/16 only through another path (the European link or a backup VPN); watch synthetic checks and Network Manager routing events.
  6. Rehearse the migration on one segmentMove dev first and confirm with flow logs that its inter-Region traffic crosses the core network before touching prod.

"A company with VPCs in many Regions wants global segmentation, automatic routing between Regions and new VPCs placed in the correct segment by tag, with the least operational overhead" is AWS Cloud WAN with segments and tag-based attachment policies. "Existing Transit Gateways must keep working during the move" adds Transit Gateway peering to the core network edge in the same Region and route table attachments mapped to segments. If instead the question says "two or three Regions, the cheapest option, the team is happy to manage routes", the answer is inter-Region Transit Gateway peering with static routes, and "routes are not exchanged across the peering" is fixed by adding static routes, because Transit Gateway peering does not propagate.
