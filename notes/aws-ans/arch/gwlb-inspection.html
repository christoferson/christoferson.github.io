Reference architecture

Centralized inspection with Gateway Load Balancer

The travel company's security team has standardized on one vendor's next-generation firewall. In each Region, a security VPC runs a fleet of those firewalls behind a Gateway Load Balancer. Gateway Load Balancer endpoints put the fleet in the path of traffic between VPCs, traffic to the internet, and inbound partner traffic, without any VPC knowing that a firewall is there.

Scenario and requirements

The travel company (example.com) runs the Transit Gateway hub and spoke in the network account 111111111111, with tgw-use1 and the prod, dev, shared and onprem route tables, and the centralized egress design, in which internet traffic passes AWS Network Firewall before a NAT gateway in the egress VPC. The security team has now standardized on one vendor's next-generation firewall, with the same rules, threat feeds and console it runs in the data centers. Network Firewall cannot run that software, so the firewall layer moves to Gateway Load Balancer (GWLB); the egress VPC and its NAT gateways stay.

The hub's address plan stays (us-east-1 is 10.40.0.0/14; booking VPC 10.40.8.0/21; egress VPC 10.41.240.0/22). This page adds the security VPC 10.41.236.0/22, the payments VPC holding the card data environment 10.40.48.0/21, and the partner API VPC 10.40.56.0/22, which has its own internet gateway and an internet-facing NLB with Elastic IPs. The security VPC has three tiers in each of us-east-1a, 1b and 1c: a /28 for the Transit Gateway attachment, a /28 for the GWLB endpoint, and a /26 for the GWLB and firewall interfaces. The other two Regions get identical builds, so traffic never crosses a Region to find a firewall.

How it works

A GWLB is a layer 3 "bump in the wire": it takes all IP packets on all ports, wraps each in GENEVE (UDP 6081) for one appliance, and gets it back the same way. Traffic reaches it only through a GWLB endpoint, a PrivateLink endpoint used as a route table next hop, so route tables, not addresses, put the firewall in the path.

  1. A booking pod calls the payments API (east-west)
  2. Spoke to the hubAWSA pod at 10.40.12.30 opens HTTPS to the payments API at 10.40.50.20. The booking subnet sends 10.0.0.0/8 to the Transit Gateway.
  3. Prod table sends it to inspectionAWSIn the prod table, a static route for 10.40.48.0/21 points at the security VPC attachment. It is more specific than the 10.0.0.0/8 blackhole, so the packet goes to inspection.
  4. Appliance mode picks an AZAWSAppliance mode hashes the flow and picks one attachment ENI, for example in us-east-1b. Both directions of this flow will use that AZ.
  5. Attachment subnet to the endpointAWSThe attachment subnet route table in us-east-1b sends 0.0.0.0/0 to the GWLB endpoint in us-east-1b.
  6. GENEVE to a firewallAWSThe GWLB picks a healthy firewall by 5-tuple hash and sends the packet inside GENEVE. The firewall sees the real addresses, applies its "booking to payments, TCP 443 only" rule and returns the packet.
  7. Back to the hubAWSThe endpoint subnet sends 0.0.0.0/0 to the Transit Gateway, and the inspection table, which holds every spoke's propagated routes, delivers the packet to the payments VPC.
  8. The reply follows the same pathAWSThe payments VPC's pci table sends everything to the security VPC. Appliance mode returns the reply to us-east-1b, the GWLB's 5-tuple stickiness sends it to the same firewall, and the firewall matches it to the existing session.
  9. A pod calls a partner airline on the internet (egress)
  10. Inspect, then NATAWSThe prod table's 0.0.0.0/0 now points at the security VPC. After the firewall allows the URL category, the inspection table sends the packet to the egress VPC and its NAT gateway. The reply is inspected too, because the egress table holds only a static 10.0.0.0/8 to the security VPC.
  11. A partner calls the partner API (north-south inbound)
  12. Internet gateway edge routeAWSA partner connects to the NLB's Elastic IP. The internet gateway translates it to the NLB's private address in 10.40.56.0/26, and the gateway route table (associated with the internet gateway) sends that subnet range to the GWLB endpoint in the same AZ.
  13. Inspected, then localAWSThe same fleet inspects it, and the endpoint subnet's local route delivers it to the NLB. The NLB subnet sends 0.0.0.0/0 to the same endpoint, so responses are inspected on the way out.

Build it

Step 1

The security VPC, the Gateway Load Balancer and the GENEVE target group

The GWLB lives in the same VPC as its appliances, with one subnet per AZ (at least 8 free addresses each). Subnets cannot be removed later, so choose all three AZs at creation. Its single listener has no protocol or port and forwards everything to one target group, whose protocol must be GENEVE on port 6081, with instance or IP targets.

Create the GWLB, its target group and listener (AWS CLI, network account) 
# one appliance subnet per AZ; subnets cannot be removed later
aws elbv2 create-load-balancer --name gwlb-use1 --type gateway \
  --subnets subnet-sec-appl-1a subnet-sec-appl-1b subnet-sec-appl-1c

# GENEVE on 6081 is the only option; health checks go to the vendor's probe port
aws elbv2 create-target-group --name ngfw-use1 \
  --protocol GENEVE --port 6081 --vpc-id vpc-0secuse1 --target-type instance \
  --health-check-protocol HTTPS --health-check-port 443 --health-check-path /health \
  --health-check-interval-seconds 10 --healthy-threshold-count 3 --unhealthy-threshold-count 2

# the single listener: no protocol or port, just a forward to the target group
aws elbv2 create-listener --load-balancer-arn GWLB_ARN \
  --default-actions Type=forward,TargetGroupArn=TG_ARN

Health checks can use TCP (the default, port 80), HTTP or HTTPS. A TCP check only proves a port answers; a vendor HTTPS probe that fails when the data plane fails is a better signal (it must accept TLS 1.2, as TLS 1.3-only targets fail HTTPS checks). Checks come from several GWLB nodes, so each appliance sees several probes per interval.

The MTU rule is a classic trap. The GWLB accepts packets up to 8,500 bytes; GENEVE adds 68, so the appliance's data interface must accept at least 8,568 bytes. The GWLB does not fragment or send ICMP "fragmentation needed", so Path MTU Discovery fails: a 1,500-byte appliance silently drops large packets, and small requests work while large transfers hang.

The GWLB and its targets are in the security VPC; GWLB endpoints are in the VPCs being inspected. An endpoint and the workloads it protects must be in different subnets, because the workload subnet's route table points at the endpoint.

Step 2

The firewall fleet in an Auto Scaling group

The vendor's Marketplace image runs in an Auto Scaling group across the three AZs, with the target group attached so instances register and deregister automatically. With --health-check-type ELB, the group also replaces instances that fail the GWLB health check. Bootstrap user data points each new instance at the vendor console, which pushes the policy before the instance turns healthy.

Two firewalls per AZ, scaled on load (AWS CLI, network account) 
# the launch template holds the vendor AMI, instance type and bootstrap user data
aws autoscaling create-auto-scaling-group --auto-scaling-group-name ngfw-use1 \
  --launch-template LaunchTemplateName=ngfw-use1,Version='$Latest' \
  --min-size 6 --max-size 12 --desired-capacity 6 \
  --vpc-zone-identifier "subnet-sec-appl-1a,subnet-sec-appl-1b,subnet-sec-appl-1c" \
  --target-group-arns TG_ARN \
  --health-check-type ELB --health-check-grace-period 600

Scale on the appliance's bottleneck (CPU or a vendor session metric), and scale in slowly: a terminated firewall takes its sessions with it. Licences are part of the design: pay-as-you-go Marketplace images suit a group that grows and shrinks, while bring-your-own-licence is cheaper for the six that always run.

Step 3

Flow behaviour: stickiness, failover, idle timeout and TCP reset

Flow stickiness is a target group attribute: 5-tuple by default, or 3-tuple (source_ip_dest_ip_proto) or 2-tuple (source_ip_dest_ip) through stickiness.type, which keeps all flows between two hosts on one appliance. Here 5-tuple is the only choice: 2-tuple and 3-tuple are not supported with Transit Gateway appliance mode, and the idle timeout can only be changed with 5-tuple.

Target failover controls existing flows when an appliance fails or deregisters. With no_rebalance (the default) they stay on the same target, which allows draining but drops them if the target is gone; new flows go to healthy targets. With rebalance, they are rehashed to healthy targets after the deregistration delay or unhealthy detection, which can take minutes. target_failover.on_deregistration and target_failover.on_unhealthy must match. Rebalancing moves a mid-session flow to a firewall that never saw it, so it helps only with session synchronization.

TCP reset (September 2026) is what the company uses: with no_rebalance, the GWLB sends a TCP RST to the sender when a target turns unhealthy or finishes deregistering, so clients reconnect through a healthy firewall within seconds. It needs 5-tuple stickiness, excludes rebalance, and covers TCP only.

No rebalance with TCP reset, and a longer idle timeout (AWS CLI, network account) 
# target group: keep 5-tuple (stickiness off), no rebalance, reset on failure and deregistration
aws elbv2 modify-target-group-attributes --target-group-arn TG_ARN \
  --attributes Key=stickiness.enabled,Value=false \
    Key=target_failover.on_deregistration,Value=no_rebalance \
    Key=target_failover.on_unhealthy,Value=no_rebalance \
    Key=send_tcp_reset.on_unhealthy.enabled,Value=true \
    Key=send_tcp_reset.on_deregistration.enabled,Value=true

# listener: match the firewall's TCP session timeout, and reset idle flows
aws elbv2 modify-listener-attributes --listener-arn LISTENER_ARN \
  --attributes Key=tcp.idle_timeout.seconds,Value=1800 \
    Key=send_tcp_reset.on_idle_timeout.enabled,Value=true

The TCP idle timeout defaults to 350 seconds, configurable from 60 to 6,000 (UDP is fixed at 120). After it expires, data on the old connection is dropped. Booking pods hold long-lived connections, so the company sets 1,800 seconds to match the firewall's session timeout, and raises the appliances' ENI TcpEstablishedTimeout to match, since on Nitro v6 it also defaults to 350.

Cross-zone load balancing is off by default, so each GWLB node uses only its own AZ's appliances: no inter-AZ charges, but if all appliances in an AZ are unhealthy, the GWLB sends each flow to a random target and it is dropped. The company keeps it off, with two appliances per AZ and Auto Scaling replacement.

Step 4

The endpoint service and a GWLB endpoint per AZ

The network account creates a VPC endpoint service from the GWLB and lists the allowed principals that may create endpoints: itself and the partner API account. With acceptance required, the security team approves each endpoint.

Endpoint service with allowed principals (AWS CLI, network account) 
aws ec2 create-vpc-endpoint-service-configuration \
  --gateway-load-balancer-arns GWLB_ARN --acceptance-required

# who may create GWLB endpoints for this service
aws ec2 modify-vpc-endpoint-service-permissions --service-id vpce-svc-0ngfwuse1 \
  --add-allowed-principals arn:aws:iam::111111111111:root arn:aws:iam::PARTNER_ACCOUNT_ID:root

# approve a pending endpoint from the partner account
aws ec2 accept-vpc-endpoint-connections --service-id vpce-svc-0ngfwuse1 \
  --vpc-endpoint-ids vpce-0partner1a

A GWLB endpoint sits in one subnet, so each AZ gets its own and each AZ's routes use the local one. Across accounts, match AZ IDs (use1-az1), not names. GWLB endpoints have no private DNS names; they are only route targets.

The security VPC's own endpoint in us-east-1a; repeat for 1b and 1c (AWS CLI, network account) 
aws ec2 create-vpc-endpoint --vpc-endpoint-type GatewayLoadBalancer \
  --vpc-id vpc-0secuse1 \
  --service-name com.amazonaws.vpce.us-east-1.vpce-svc-0ngfwuse1 \
  --subnet-ids subnet-sec-gwlbe-1a
Step 5

Transit Gateway routing with appliance mode

The security VPC attaches to tgw-use1 with appliance mode. Without it, each direction stays in its source AZ: a request from 1a to a payments host in 1c is inspected in 1a and the reply in 1c, and the second firewall drops a reply for a session it never saw. Appliance mode uses one security VPC ENI for both directions. It goes on the security VPC's attachment only; enabling it on a live attachment can move flows.

Attach the security VPC and give it its own route table (AWS CLI, network account) 
aws ec2 create-transit-gateway-vpc-attachment --transit-gateway-id tgw-use1 \
  --vpc-id vpc-0secuse1 \
  --subnet-ids subnet-sec-tgw-1a subnet-sec-tgw-1b subnet-sec-tgw-1c \
  --options ApplianceModeSupport=enable,DnsSupport=enable

# inspection table: associated with the security VPC; every spoke propagates into it
aws ec2 associate-transit-gateway-route-table --transit-gateway-route-table-id tgw-rtb-inspection \
  --transit-gateway-attachment-id tgw-attach-inspection
aws ec2 enable-transit-gateway-route-table-propagation --transit-gateway-route-table-id tgw-rtb-inspection \
  --transit-gateway-attachment-id tgw-attach-payments-prod

# after inspection, internet traffic continues to the egress VPC
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-inspection \
  --destination-cidr-block 0.0.0.0/0 --transit-gateway-attachment-id tgw-attach-egress

The spoke side has three parts:

  1. Spoke tables (prod, dev, shared)0.0.0.0/0 now points at tgw-attach-inspection instead of the Network Firewall attachment; the RFC 1918 blackholes stay, so development still cannot reach production through the security VPC.
  2. Card data routesA new pci table for the payments attachment has one 0.0.0.0/0 to the security VPC. Payments propagates only into inspection. prod, shared and onprem get a static 10.40.48.0/21 to the security VPC, which beats their 10.0.0.0/8 blackholes; dev gets nothing.
  3. Egress tableA static 10.0.0.0/8 to the security VPC and no spoke propagations; a propagated /21 would win and let replies bypass the firewall.
The card data environment always goes through the firewalls (AWS CLI, network account) 
# prod (and shared, onprem): reach payments only via inspection
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.40.48.0/21 --transit-gateway-attachment-id tgw-attach-inspection

# pci: everything out of the card data VPC is inspected
aws ec2 create-transit-gateway-route --transit-gateway-route-table-id tgw-rtb-pci \
  --destination-cidr-block 0.0.0.0/0 --transit-gateway-attachment-id tgw-attach-inspection

Inside the security VPC, each AZ's attachment subnet table sends 0.0.0.0/0 to its same-AZ endpoint (so these are per AZ), and one endpoint subnet table sends 0.0.0.0/0 back to the Transit Gateway.

Security VPC routes for us-east-1a (AWS CLI, network account) 
# from the hub into the firewall, in the same AZ
aws ec2 create-route --route-table-id rtb-sec-tgw-1a \
  --destination-cidr-block 0.0.0.0/0 --vpc-endpoint-id vpce-0gwlbuse1a

# inspected traffic goes back to the hub (shared by all AZs)
aws ec2 create-route --route-table-id rtb-sec-gwlbe \
  --destination-cidr-block 0.0.0.0/0 --transit-gateway-id tgw-use1

A route whose target is a GWLB endpoint cannot use a prefix list as its destination. The ingress and spoke route tables that point at GWLB endpoints must list CIDRs, even though prefix lists work for routes to the Transit Gateway.

Step 6

North-south inbound with ingress routing

Traffic entering the partner VPC through its own internet gateway never touches the Transit Gateway, and appliance mode's stickiness only covers traffic arriving from the Transit Gateway. So the partner VPC gets its own GWLB endpoints from the same service, and ingress routing steers traffic to them: a gateway route table with an edge association to the internet gateway applies to inbound traffic.

  1. Gateway route table (edge association with the internet gateway)Each NLB subnet range, for example 10.40.56.0/26 in 1a, to the GWLB endpoint in the same AZ.
  2. NLB subnet route table (per AZ)0.0.0.0/0 to the same-AZ GWLB endpoint, replacing the old route to the internet gateway, so responses are inspected too.
  3. GWLB endpoint subnet route table0.0.0.0/0 to the internet gateway. Inspected inbound traffic needs no extra route: the local route delivers it to the NLB.
Edge association and routes for us-east-1a (AWS CLI, partner account) 
# a route table associated with the internet gateway itself
aws ec2 create-route-table --vpc-id vpc-0partnerapi
aws ec2 associate-route-table --route-table-id rtb-partner-edge --gateway-id igw-0partnerapi

# traffic for the NLB subnet in 1a goes to the endpoint in 1a first
aws ec2 create-route --route-table-id rtb-partner-edge \
  --destination-cidr-block 10.40.56.0/26 --vpc-endpoint-id vpce-0partner1a

# the NLB subnet's replies are inspected before reaching the internet gateway
aws ec2 replace-route --route-table-id rtb-partner-nlb-1a \
  --destination-cidr-block 0.0.0.0/0 --vpc-endpoint-id vpce-0partner1a

# after inspection, outbound traffic leaves through the internet gateway
aws ec2 create-route --route-table-id rtb-partner-gwlbe-1a \
  --destination-cidr-block 0.0.0.0/0 --gateway-id igw-0partnerapi

The gateway route table's destination is the subnet range, not the Elastic IP, because the internet gateway has already translated the public address. The firewall sees the partner's real public source address, so rules and logs can identify partners.

Design decisions

Gateway Load Balancer instead of AWS Network Firewall

The egress page's Transit Gateway-attached Network Firewall is managed and needs no instances. The company changes for operational reasons (one rule base, console and threat feed for data centers and AWS) and accepts running the firewalls itself: patching, licences, scaling and failure behaviour. The native attachment does not accept third-party firewalls, so a vendor product means an inspection VPC with GWLB. See Task 4.1 and Task 2.2.

One security VPC per Region, shared by east-west, egress and inbound

One fleet per Region keeps traffic in its Region for latency and European data residency, and one GWLB serves both the Transit Gateway path and the partner VPC, so there is one policy and one fleet to size. Separate inbound and outbound fleets would stop an inbound attack from exhausting egress capacity; the company will split them if partner traffic grows.

Failure behaviour: TCP reset rather than rebalance

The vendor's firewalls do not share session tables, so rebalancing a live flow would only move the drop. A reset makes the client open a new flow, which goes to a healthy firewall. Rebalance fits only with session synchronization or UDP-heavy traffic.

Cost: endpoints, GLCUs, double Transit Gateway processing, licences

GWLB endpoints are billed per AZ-hour and per GB (PrivateLink pricing); the GWLB per AZ-hour plus GLCUs (600 new flows per second, 60,000 active flows or 1 GB per hour); and at least six EC2 firewalls with licences run around the clock. Transit Gateway processing ($0.02 per GB on every byte a VPC sends into it) applies twice to each inspected packet: from the spoke, and from the security VPC after inspection. NAT gateways now pay full charges, because the service chaining waiver belongs to Network Firewall. So inspect only what the rules require (card data, egress, partner ingress); production to shared services stays on direct routes. See Task 3.3.

Encryption Controls, MTU and other compatibility limits

VPC Encryption Controls enforce mode is not compatible with Gateway Load Balancer, so the security VPC (and, to be safe, the partner VPC) stays in monitor mode, whose flow log fields still give encryption evidence. Security group referencing does not work through GWLB inspection, so the payments security groups allow the booking CIDR. Transit Gateway carries 8,500 bytes, matching the GWLB; the appliances need 8,568. See Task 4.3 and Task 3.2.

Alternatives

AWS Network Firewall (inspection VPC or Transit Gateway attachment)

The managed option, covered on the egress page: endpoints in an inspection VPC with appliance mode, or the native Transit Gateway attachment with appliance mode always on. No instances or licences, plus the NAT waiver. Choose it unless a vendor product is required.

Distributed GWLB endpoints in every VPC

Every internet-facing VPC gets endpoints and ingress routing, as the partner VPC does, served by the central fleet. No Transit Gateway charges, but endpoint hours multiply, and east-west traffic still needs the hub.

Appliances without GWLB

Routing to firewall ENIs (source/destination check off) with scripted route failover scales poorly. VPC Route Server can instead learn routes from appliances over BGP and steer to healthy ones (July 2026 blog).

Cloud WAN service insertion

On Cloud WAN, a network function group with send-via and send-to policies inserts the same security VPCs into paths across Regions; the GWLB fleet inside stays the same.

Testing it

  1. Reachability Analyzer, in two legsBooking to payments should pass the prod route and end at a GWLB endpoint; paths through an endpoint exclude the GWLB and its targets, so analyze the GWLB-to-appliance leg separately with UDP 6081 (other protocols or ports fail with GWLB restriction codes). Development to payments should stop at the dev blackhole.
  2. SymmetryRun long transfers between AZs and confirm in the firewall logs that each session shows both directions on one firewall. Turning appliance mode off in a staging hub should produce one-sided sessions.
  3. Large packetsSend don't-fragment pings of 8,500 bytes between jumbo-frame hosts across the hub. If they fail while 1,400-byte pings pass, an appliance MTU is below 8,568.
  4. Appliance failureStop one firewall's data plane under load. Within about 20 seconds (2 failures at 10 seconds) clients should get resets and reconnect, describe-target-health should show Target.FailedHealthChecks, and Auto Scaling should replace the instance. Alarm on UnHealthyHostCount (AWS/GatewayELB, Minimum statistic).
  5. Idle connectionsA database connection idle for 25 minutes should still work; after 30 minutes the client should get a reset, not a silent hang.
  6. Inbound inspectionCall the partner API from outside AWS and confirm the firewall logs the caller's public address. GWLB has no access logs, so VPC flow logs on the endpoint ENIs confirm the path.

"Inspect traffic between VPCs and to the internet with a third-party firewall, scalable and highly available, with both directions of each flow on the same appliance" is a security VPC with a Gateway Load Balancer, a GENEVE target group on UDP 6081 and appliances in an Auto Scaling group, GWLB endpoints per AZ as route targets, and Transit Gateway appliance mode on the security VPC attachment. If the question adds "inspect inbound internet traffic in a VPC with its own internet gateway", the answer is a gateway route table associated with the internet gateway that sends the application subnet range to a GWLB endpoint. If "large packets are dropped", it is the appliance MTU below 8,568 bytes.
