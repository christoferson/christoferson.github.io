Reference architecture

Network observability and troubleshooting

The travel company's network team builds one observability stack for its three-Region network: metrics and alarms, flow logs at every layer in a log archive account, Network Manager events, path analysis and on-demand packet capture. Then a change breaks part of the traffic from Frankfurt to Virginia, and each tool narrows the fault down until one attribute on one attachment explains it.

Scenario and requirements

The travel company (example.com) runs the Transit Gateway hub and spoke in us-east-1, eu-central-1 and ap-northeast-1, joined by inter-Region peering (option A on that page; segments are moving to Cloud WAN one by one). Egress and east-west traffic pass the central firewall and the Gateway Load Balancer security VPC, and the data centers connect over resilient Direct Connect with backup VPNs. Each page added its own logs and alarms. Nobody could answer a cross-Region question quickly, because the evidence sat in different accounts, Regions and formats.

The network team's goal: for any "A cannot reach B" ticket, answer three questions within minutes. Is it the network or the application? Is it routing (control plane) or forwarding (data plane)? Which change caused it?

Values used on this page:

  • The request in the incident (as on Multi-Region network): a Frankfurt booking pod 10.44.12.30 in vpc-0bookingeuc1 (bookings account 222222222222) calls the fare service 10.41.20.15 on TCP 443 in the Virginia shared services VPC (network account 111111111111), across tgw-euc1, tgw-attach-peer-use1-euc1 and tgw-use1.
  • New names: Frankfurt attachments tgw-attach-bookings-euc1 and tgw-attach-dev-euc1; the fare instance interface eni-0fare01 behind tgw-attach-shared-services; a capture host interface eni-0capture01; and tgw-attach-inspection-v2, the rebuilt security VPC attachment in the incident.
  • Log buckets in the log archive account: central-flow-logs-111111111111 (us-east-1, the bucket the hub and egress pages already use) and central-flow-logs-111111111111-euc1 (eu-central-1, so European flow records stay in Europe), plus travel-pcap-777777777777 for captures.

How it works

Steps marked AWS happen automatically once configured; the others are actions of a person or a host you run.

  1. Where each tool sees the Frankfurt to Virginia request
  2. Pod opens a connectionBooking pod10.44.12.30 sends a SYN to 10.41.20.15:443. VPC flow logs record it, with pkt-srcaddr showing the pod; Network Flow Monitor's agent on the node counts retransmissions.
  3. Frankfurt Transit GatewayAWSThe prod table sends 10.41.0.0/16 to the peering. Transit Gateway flow logs and CloudWatch drop counters see this hop.
  4. Virginia Transit GatewayAWSThe peer table sends shared services traffic through the security VPC. Network Manager records every route change here; Route Analyzer traces the route-table path.
  5. Firewall and fare serviceAWSFirewalls behind the Gateway Load Balancer inspect the flow. Flow logs show what arrived at eni-0fare01; a mirror session copies the packets.
  6. The incident
  7. The changeNetwork engineerAt 14:00 a pipeline replaces the Virginia security VPC attachment with tgw-attach-inspection-v2 and moves the routes. Its module leaves appliance mode off.
  8. First signalsAWSNetwork Manager events at 14:02 show the new attachment and routes. From 14:05 Network Flow Monitor shows retransmissions toward us-east-1 with its health indicator at 0 (not AWS), and a third of fare calls fail.
  9. Rule out routingOn-call engineerProduction drop alarms are quiet; the blackhole drops behind a gateway-wide alarm come from development. Route Analyzer and Reachability Analyzer report the path reachable.
  10. Find the data-plane faultOn-call engineerFlow logs show repeated SYNs with no reply; Virginia Transit Gateway flow logs show request and reply entering the security VPC in different AZs; mirroring proves the fare service answers.
  11. Fix and preventNetwork engineerAppliance mode goes on and errors stop. An EventBridge check and a Network Access Analyzer scope guard against a repeat.

Build it

Step 1

Flow logs into the log archive, partitioned for Athena

Flow logs are collected outside the traffic path, so they never affect throughput, but they are not real time (about 10 minutes to S3, best effort) and are billed as CloudWatch vended logs even when delivered to S3. The team chose:

  • S3 in the log archive account, one bucket per Region, written directly through the bucket policy (principal delivery.logs.amazonaws.com, conditioned on the organization). Network and workload accounts cannot delete the evidence.
  • Parquet with Hive-compatible prefixes and hourly partitions. AWS states Parquet queries run 10 to 100 times faster with about 20% less storage; hourly partitions let a query read only the incident hour, and Athena bills by data scanned.

Transit Gateway flow logs are created by the gateway owner, per gateway or per attachment. Their default format already includes every version 2 to 6 field (source and destination VPC, subnet, account, interface and AZ ID, the pair attachment and the four packets-lost-* counters), unlike VPC flow logs, whose default is version 2 only. The aggregation interval must be 60 seconds.

Flow logs for the Frankfurt Transit Gateway as hourly Parquet in the European log bucket (AWS CLI, network account; repeat for tgw-use1 and tgw-apne1 with their Regional buckets) 
aws ec2 create-flow-logs --region eu-central-1 \
  --resource-type TransitGateway \
  --resource-ids tgw-euc1 \
  --max-aggregation-interval 60 \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::central-flow-logs-111111111111-euc1/tgw/ \
  --destination-options FileFormat=parquet,HiveCompatiblePartitions=true,PerHourPartition=true

AWS's Athena integration templates create a Glue database, a partitioned table, a partition-loading Lambda function and named queries such as top talkers; the 2023 Transit Gateway walkthrough expects all fields, Parquet, Hive prefixes and daily partitions. With hourly partitions, the team defines its own tables with partition projection over year, month, day and hour. Columns are the field names with underscores (packets_lost_blackhole).

Segments already on Cloud WAN get Cloud WAN flow logs (November 2026), created in the home Region with segment and Region fields (Multi-Region network, Step 7), at no Cloud WAN charge beyond vended logs.

A flow log cannot be edited: a new format or destination means a new flow log, so settle the field list before rolling it out to hundreds of VPCs.

Step 2

VPC flow logs with the fields that answer questions

The default version 2 record cannot tell a pod from its node, a request from a reply, or which workload an interface belongs to. A custom format adds:

  • pkt-srcaddr and pkt-dstaddr: the original addresses behind NAT gateways, Transit Gateway interfaces and EKS pods.
  • tcp-flags: SYN 2, SYN-ACK 18, FIN 1, RST 4, OR-ed over the interval. Repeated 2s with no 18 back is a lost reply.
  • flow-direction, traffic-path (egress only) and az-id.
  • Version 11 fields (September 2026): instance-tag, interface-tag and asg-tag (each with a -2 partner) hold tag values chosen with --tag-field-specifications, at most two keys per resource type; the next-hop-* fields show the next interface, subnet, AZ and VPC. Tags need ec2:DescribeTags and a service-linked role (Auto Scaling group tags also a CloudTrail trail); next-hop is not filled for internet gateways, cross-Region traffic or ingress from a Transit Gateway.
The Frankfurt booking VPC's flow log: audit and troubleshooting fields, node tags, next hop, to the European log bucket (AWS CLI, bookings account) 
# the instance tags are the EKS node's Name and Application tags
aws ec2 create-flow-logs --region eu-central-1 \
  --resource-type VPC --resource-ids vpc-0bookingeuc1 \
  --traffic-type ALL --max-aggregation-interval 60 \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::central-flow-logs-111111111111-euc1/vpc/ \
  --destination-options FileFormat=parquet,HiveCompatiblePartitions=true,PerHourPartition=true \
  --log-format '${version} ${account-id} ${vpc-id} ${subnet-id} ${az-id} ${instance-id} ${interface-id} ${srcaddr} ${dstaddr} ${pkt-srcaddr} ${pkt-dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${tcp-flags} ${flow-direction} ${traffic-path} ${instance-tag} ${instance-tag-2} ${next-hop-interface-type} ${next-hop-az-id} ${log-status}' \
  --tag-field-specifications 'ResourceType=instance,TagKeys=Name,Application'

Flow logs never contain traffic to the Amazon DNS server, instance metadata, Time Sync, DHCP or ARP, so "no record" does not always mean "no packet". StackSets deploy the same format to every production VPC, so one table definition fits all.

Step 3

Metrics and alarms that point at a layer

AWS/TransitGateway publishes every 60 seconds, per gateway and per attachment; use Sum:

  • PacketDropCountBlackhole: matched a blackhole route, usually a deliberate block.
  • PacketDropCountNoRoute: matched no route, usually a missing propagation or static route. PacketDropCountTTLExpired points at a loop.
  • BytesIn, BytesOut, PacketsIn, PacketsOut, also per AZ for VPC attachments.

All attachment metrics go to the gateway owner's account. The team alarms per production attachment: development is blackholed from production by design, so a gateway-wide counter is never quiet.

Page the network team when production traffic in Frankfurt hits a blackhole or finds no route (AWS CLI, network account) 
# any blackholed packet from the booking attachment in five minutes is unexpected
aws cloudwatch put-metric-alarm --region eu-central-1 \
  --alarm-name tgw-euc1-bookings-blackhole \
  --namespace AWS/TransitGateway --metric-name PacketDropCountBlackhole \
  --dimensions Name=TransitGatewayAttachment,Value=tgw-attach-bookings-euc1 \
  --statistic Sum --period 300 --evaluation-periods 1 \
  --threshold 0 --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions arn:aws:sns:eu-central-1:111111111111:network-oncall

# no-route drops on the peering show a missing summary route between Regions
aws cloudwatch put-metric-alarm --region eu-central-1 \
  --alarm-name tgw-euc1-peer-use1-noroute \
  --namespace AWS/TransitGateway --metric-name PacketDropCountNoRoute \
  --dimensions Name=TransitGatewayAttachment,Value=tgw-attach-peer-use1-euc1 \
  --statistic Sum --period 300 --evaluation-periods 2 \
  --threshold 100 --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions arn:aws:sns:eu-central-1:111111111111:network-oncall

The dimension set must match the published metric exactly (aws cloudwatch list-metrics shows it). Alarms live in the metric's Region, so each Region has its own set.

The hybrid edge keeps its alarms from the Direct Connect page: VirtualInterfaceBgpStatus (March 2026; Minimum below 1 is BGP down, sampled every five minutes), VirtualInterfaceBgpPrefixesAccepted and ...Advertised (Maximum, below the prefix quota), and VPN TunnelState, where a connection-level value between 0 and 1 means one tunnel is down.

Network Flow Monitor shows TCP performance as the workloads see it. Its eBPF agent on EC2 instances and EKS nodes (here the Frankfurt booking nodes) publishes Retransmissions, Timeouts, RoundTripTime and a HealthIndicator in AWS/NetworkFlowMonitor. It measures flows only to the edge of another Region, so it can say "flows to us-east-1 are retransmitting" but not where.

Step 4

Network Manager: one topology, events and Route Analyzer

The three Transit Gateways are registered in the global network global-network-0travel1234567 (hub page, Step 6). The global network is free and its home Region is always us-west-2, so every Network Manager event arrives in EventBridge in us-west-2, whichever Region changed:

  • Topology Change: attachments, peerings, VPNs, Connect peers and firewall attachments created or deleted.
  • Routing Update: TGW-ROUTE-INSTALLED or TGW-ROUTE-UNINSTALLED, with per route the destinationCidrBlock, attachments, routeType and routeState (active or blackhole).
  • Status Update: VPN IPsec and BGP, and Connect peer BGP, down or up.
Send every route change and every VPC attachment change to the guardrail checker and the change log (AWS CLI, us-west-2) 
aws events put-rule --region us-west-2 \
  --name tgw-routing-and-attachments \
  --event-pattern '{
    "source": ["aws.networkmanager"],
    "detail-type": ["Network Manager Routing Update", "Network Manager Topology Change"],
    "detail": {"changeType": ["TGW-ROUTE-INSTALLED", "TGW-ROUTE-UNINSTALLED", "VPC-ATTACHMENT-CREATED", "VPC-ATTACHMENT-DELETED"]}
  }'

# a Lambda function checks the change; the log group keeps a searchable timeline
aws events put-targets --region us-west-2 --rule tgw-routing-and-attachments \
  --targets Id=checker,Arn=arn:aws:lambda:us-west-2:111111111111:function:network-guardrails Id=timeline,Arn=arn:aws:logs:us-west-2:111111111111:log-group:/network/change-timeline

The checker pages on a production route entering blackhole state and, since the incident below, on a new attachment from an inspection VPC with appliance mode off (read from the attachment's options).

Route Analyzer traces Transit Gateway route tables only, between attachments of registered gateways, optionally through a middlebox and back. It ignores VPC route tables, security groups, network ACLs and on-premises devices.

Trace Frankfurt booking to the Virginia fare service, and the return path (AWS CLI, us-west-2) 
aws networkmanager start-route-analysis --region us-west-2 \
  --global-network-id global-network-0travel1234567 \
  --source TransitGatewayAttachmentArn=arn:aws:ec2:eu-central-1:111111111111:transit-gateway-attachment/tgw-attach-bookings-euc1,IpAddress=10.44.12.30 \
  --destination TransitGatewayAttachmentArn=arn:aws:ec2:us-east-1:111111111111:transit-gateway-attachment/tgw-attach-shared-services,IpAddress=10.41.20.15 \
  --include-return-path

The console adds a topology tree and a geographic map, with the data centers as sites and devices tied to their customer gateways.

Step 5

Path analysis: Reachability Analyzer and Network Access Analyzer

Reachability Analyzer models the configuration (route tables, security groups, ACLs, Transit Gateway tables, load balancers, Network Firewall 5-tuple rules) and reports a hop-by-hop path or the blocking component, with codes such as TGW_RTB_NO_ROUTE_TO_TGW_ATTACHMENT. It sends no packets and costs $0.10 per analysis.

Source and destination must be in the same Region. AWS's January 2024 blog chains analyses: source to the peering attachment, then peering attachment to destination; a path exists only if both legs succeed. Cross-account paths use Organizations trusted access, with the network account as delegated administrator (any member account except the management account; other accounts' resources by ARN).

Two legs of the Frankfurt to Virginia path, from the delegated administrator (AWS CLI, network account) 
# leg 1, eu-central-1: the booking node's interface to the peering attachment
aws ec2 create-network-insights-path --region eu-central-1 \
  --source arn:aws:ec2:eu-central-1:222222222222:network-interface/eni-0bookingeuc1node \
  --destination tgw-attach-peer-use1-euc1 \
  --destination-ip 10.41.20.15 --protocol tcp --destination-port 443
aws ec2 start-network-insights-analysis --region eu-central-1 \
  --network-insights-path-id LEG1_PATH_ID

# leg 2, us-east-1: from the peering attachment to the fare instance
aws ec2 create-network-insights-path --region us-east-1 \
  --source tgw-attach-peer-use1-euc1 --source-ip 10.44.12.30 \
  --destination eni-0fare01 --protocol tcp --destination-port 443
aws ec2 start-network-insights-analysis --region us-east-1 \
  --network-insights-path-id LEG2_PATH_ID

Limits: IPv4 only; no Connect attachments or policy tables; for TCP through a Transit Gateway route table only the forward direction is analyzed; a GWLB endpoint path stops short of the appliances. A "reachable" answer proves configuration, not the return path through a firewall fleet.

Network Access Analyzer finds paths that should not exist. A scope lists match paths (violations) and exclude paths (exceptions). The team's scopes: no internet gateway reaches card-data interfaces, development reaches no production VPC, and peering-to-shared traffic passes the security VPC. An analysis covers one account and Region at $0.002 per interface.

For continuous compliance, the pattern from AWS's Security Hub blog runs: an EventBridge schedule (every 12 hours by default) starts a Step Functions state machine that runs every scope and sends findings to Security Hub. Scope syntax is on Task 3.2.

Step 6

Packet capture on demand with Traffic Mirroring and Mountpoint

Flow logs summarize; sometimes the team needs packets. Traffic Mirroring copies packets from a source interface, wrapped in VXLAN on UDP 4789, to an interface, a Network Load Balancer (UDP 4789 listener) or a Gateway Load Balancer endpoint. A filter decides what is copied (no rules, nothing mirrored). Inbound packets dropped by the source's security group or ACL are never mirrored.

A runbook creates sessions only during incidents, because each costs about $0.015 an hour until deleted. The target is one capture instance's interface, because NLB and GWLB targets can deliver packets out of order; AWS's January 2024 blog uses a GWLB endpoint and an Auto Scaling group when scale matters more.

Mirror TCP 443 on the fare instance to the capture host, first 256 bytes of each packet (AWS CLI, network account) 
aws ec2 create-traffic-mirror-target \
  --description "incident capture host" \
  --network-interface-id eni-0capture01

aws ec2 create-traffic-mirror-filter --description "fare-https"
aws ec2 create-traffic-mirror-filter-rule --traffic-mirror-filter-id tmf-0farehttps01 \
  --traffic-direction ingress --rule-number 100 --rule-action accept --protocol 6 \
  --destination-port-range FromPort=443,ToPort=443 \
  --source-cidr-block 10.44.0.0/16 --destination-cidr-block 10.41.20.15/32
aws ec2 create-traffic-mirror-filter-rule --traffic-mirror-filter-id tmf-0farehttps01 \
  --traffic-direction egress --rule-number 100 --rule-action accept --protocol 6 \
  --source-port-range FromPort=443,ToPort=443 \
  --source-cidr-block 10.41.20.15/32 --destination-cidr-block 10.44.0.0/16

# headers are enough to see SYN, SYN-ACK and retransmissions
aws ec2 create-traffic-mirror-session \
  --network-interface-id eni-0fare01 \
  --traffic-mirror-target-id tmt-0capture0001 \
  --traffic-mirror-filter-id tmf-0farehttps01 \
  --session-number 1 --packet-length 256 --virtual-network-id 4101

The capture host allows UDP 4789 from the fare subnets and writes rotating pcap files into S3 through Mountpoint for Amazon S3, so captures outlive the instance and open in Wireshark, which decodes VXLAN. Mountpoint does not implement full POSIX semantics, so each file is written once, start to finish, as with the blog's 900-second rotation.

On the capture host: mount the bucket, capture the VXLAN stream in 15-minute files (shell) 
mkdir -p /mnt/pcap
mount-s3 travel-pcap-777777777777 /mnt/pcap

# mirrored packets arrive as VXLAN on UDP 4789; one new file every 900 seconds
tcpdump -i ens5 -nn udp port 4789 -G 900 -w '/mnt/pcap/fare-%Y-%m-%d-%H-%M.pcap'

Only the capture host's role may write and only the network team read, because captures can hold sensitive data.

Step 7

The incident: query, fix and prevent

Rule out routing. An old gateway-wide blackhole alarm on tgw-euc1 fired at 14:10. One query splits the drops by attachment:

Which attachments lost packets to a blackhole or no route in the incident hour (Athena SQL, log archive account) 
-- year, month, day and hour are the partition columns of the team's table
SELECT tgw_attachment_id, tgw_src_vpc_id, srcaddr, dstaddr, dstport,
       SUM(packets_lost_blackhole) AS blackhole,
       SUM(packets_lost_no_route)  AS no_route
FROM tgw_flow_logs_euc1
WHERE (packets_lost_blackhole > 0 OR packets_lost_no_route > 0)
  AND year = '2026' AND month = '11' AND day = '17' AND hour = '14'
GROUP BY tgw_attachment_id, tgw_src_vpc_id, srcaddr, dstaddr, dstport
ORDER BY blackhole + no_route DESC
LIMIT 20;

Every row came from tgw-attach-dev-euc1: a development load test hitting the designed blackhole. Route Analyzer and both Reachability Analyzer legs reported the path reachable. Configuration was fine; forwarding was not.

Find the asymmetry. The booking VPC's flow logs showed repeated egress records with tcp-flags 2 and no ingress reply. The mirror session on eni-0fare01 showed every SYN answered, so the reply was lost on the way back. The Virginia Transit Gateway flow logs located it:

For flows between the pod and the fare service, which security VPC interface and AZ each direction used (Athena SQL, log archive account) 
SELECT srcaddr, srcport, dstaddr, dstport,
       tgw_dst_eni, tgw_dst_az_id, SUM(packets) AS packets
FROM tgw_flow_logs_use1
WHERE tgw_attachment_id = 'tgw-attach-inspection-v2'
  AND ((srcaddr = '10.44.12.30' AND dstaddr = '10.41.20.15')
    OR (srcaddr = '10.41.20.15' AND dstaddr = '10.44.12.30'))
  AND year = '2026' AND month = '11' AND day = '17' AND hour = '14'
GROUP BY srcaddr, srcport, dstaddr, dstport, tgw_dst_eni, tgw_dst_az_id
ORDER BY srcport, dstport;

For failing connections, the request entered the security VPC through the interface in one AZ and the reply through another. Without appliance mode the Transit Gateway picks the AZ for each direction separately, so the halves of a flow reached different firewalls, and the one that saw only the SYN-ACK dropped it as an unknown session. Flows whose directions shared an AZ worked: hence the partial failure.

The fix (AWS CLI, network account) 
aws ec2 modify-transit-gateway-vpc-attachment --region us-east-1 \
  --transit-gateway-attachment-id tgw-attach-inspection-v2 \
  --options ApplianceModeSupport=enable

Errors stopped within a minute and the mirror session was deleted. Prevention: the pipeline module now enables appliance mode by default, the Step 4 checker pages on any inspection attachment without it, and the gateway-wide blackhole alarm, which cost the first ten minutes, became per-attachment alarms.

Design decisions

S3 and Athena as the store, CloudWatch Logs only where alarms need it

S3 is cheap to keep and query by partition; CloudWatch Logs adds Logs Insights and metric filters at higher cost for this volume. Only firewall alert logs and the event timeline go to CloudWatch Logs; Firehose is the option when a SIEM needs a stream.

Where to enable flow logs

Transit Gateway flow logs on every gateway, where cross-account and cross-Region questions are answered; VPC flow logs on every production VPC, and REJECT-only in development. The Rivian blog shows a cheaper option for one question: a catch-all route to a "blackhole VPC" with flow logs on that attachment only.

Cost

Flow logs are vended logs, billed per GB even to S3, plus storage and Athena scans; Regional buckets avoid cross-Region delivery at the price of one table per Region. Network Manager is free; Reachability Analyzer is $0.10 per analysis; Network Access Analyzer $0.002 per interface, so one scope over 1,000 interfaces twice a day is about $120 a month; mirroring about $0.015 per session-hour plus data transfer.

Alternatives

CloudWatch Logs Insights instead of Athena

Simpler for one VPC or a short window, but at three Regions and a year of retention, ingestion cost and scattered log groups make it the wrong primary store.

Network Synthetic Monitor for the hybrid paths

Agentless probes to on-premises addresses give a latency and loss baseline over Direct Connect or VPN, with a health indicator for the AWS side. It complements Network Flow Monitor (workloads) and Internet Monitor (end users).

An always-on packet broker

A permanent mirror fleet feeding an IDS gives continuous packet visibility, at the price of session-hours on every source and more bandwidth on busy instances. The company inspects inline instead.

Testing it

  1. Trip each alarmIn staging, blackhole a test CIDR and send traffic: the attachment alarm fires within five minutes and a routing event with routeState blackhole reaches the checker.
  2. Check the logs end to endTen minutes after a test connection, Athena returns its records in both Regions, with pkt_srcaddr showing the pod and instance_tag the node.
  3. Run the chained path dailyA scheduled job runs both Reachability Analyzer legs per critical pair and alarms if either fails.
  4. Rehearse the asymmetryIn staging, attach an inspection VPC without appliance mode: the checker pages and the second query shows split interfaces.
  5. Rehearse a captureRun the mirroring runbook on a test instance: pcap files appear every 15 minutes and stop when the session is deleted.
  6. Verify the compliance loopAdd a route that bypasses inspection in staging: a Network Access Analyzer finding appears in Security Hub after the next run.

Troubleshooting checklist. Reachable but failing: look at the data plane (firewall symmetry, MTU, the application). Intermittent failures through an inspection VPC: appliance mode. Drop alarms always firing: alarm per production attachment. A known flow is missing: Amazon DNS, metadata, DHCP and ARP are never logged, and the default format has no pkt-srcaddr.

"Traffic through a centralized inspection VPC fails intermittently between VPCs in different Availability Zones" is enable appliance mode on the inspection VPC's Transit Gateway attachment. "Identify which configuration component blocks a path without sending traffic" is Reachability Analyzer; "verify that no unintended path exists" is Network Access Analyzer; "trace Transit Gateway route tables across Regions" is Network Manager Route Analyzer; "inspect packet contents" is Traffic Mirroring, never flow logs, which hold metadata only.
