Extra: VPC Lattice service network

The booking platform is splitting into services owned by different accounts: fare search on EKS, pricing on Lambda, loyalty on ECS, and a shared reporting database. Instead of Transit Gateway routes and per-service PrivateLink endpoints, the network account runs one VPC Lattice service network, shares it with AWS RAM, and lets IAM auth policies decide which caller may invoke which service.

Extra page. Amazon VPC Lattice is not on the ANS-C01 in-scope service list, so this page is background and comparison, not core exam content. The exam-relevant parts are how Lattice compares with PrivateLink, Transit Gateway and VPC peering, and its resource configurations (resource gateways and resource endpoints), which PrivateLink shares and which are covered in Task 1.6.

Scenario and requirements

The travel company (example.com) runs its booking platform in us-east-1 on tgw-use1 (AS 64521). The platform is splitting into services owned by separate accounts that call each other on every booking:

  • Fare search on EKS in the bookings account 222222222222, VPC vpc-bookings-prod (10.40.8.0/21), managed through the AWS Gateway API Controller.
  • Pricing on Lambda, plus a legacy bulk repricing engine on EC2.
  • Loyalty on ECS, migrating from a stack behind an internal ALB.
  • A shared reporting database (Aurora PostgreSQL, TCP 5432).

Callers sit in VPCs in several accounts, including the partner API VPC, where the company's partner gateway calls fare search and loyalty for airlines and hotels. Batch jobs in the US data center (10.100.0.0/16) call pricing.

RequirementDesign choice
No new Transit Gateway routes, no CIDR coordinationOne Lattice service network; VPCs join it, and no IP route exists between them
Authorization by caller identityIAM auth policies on the network and each service; SigV4-signed callers
Central control, team-owned servicesNetwork account owns and shares the network; teams own services and target groups
Data center callers and a shared databaseA service network endpoint in shared services; a resource configuration for the database

How it works

Steps marked AWS happen automatically once configured; the others are actions by the named account or caller.

  1. A fare search pod calls pricing
  2. Resolve and signFare search podThe pod resolves pricing.svc.example.com, an alias to the service's generated Lattice name, which returns link-local Lattice addresses (for example 169.254.171.x). Its IAM role signs the HTTPS request with SigV4; no route table entry is involved.
  3. Association security groupAWSThe booking VPC's association allows HTTPS only from the EKS security groups; other workloads in the VPC never enter the network.
  4. Two auth policiesAWSThe network policy requires an authenticated principal of o-travel1234 (unsigned requests get a 403). The pricing policy allows only the fare search role, only GET on /v1/quotes. Both must allow.
  5. Listener, rule, targetAWSThe HTTPS listener terminates TLS with the team's ACM certificate, forwards to the Lambda target group by default and sends /v1/bulk to the EC2 target group. DNS prefers the caller's AZ, and Lattice charges no inter-AZ transfer.
  6. Other callers
  7. Partner gateway to loyaltyAWSThe loyalty policy also requires the source VPC vpc-partner-api. The listener sends 90 percent of requests to the old ALB and 10 percent to the new ECS tasks.
  8. Data center to pricingBatch jobThe job resolves the endpoint-specific DNS name to the service network endpoint's addresses in 10.41.0.0/16 and crosses Direct Connect and tgw-use1. The same policies apply, and connections can only start from the endpoint side.
  9. Loyalty to the databaseAWSTasks connect to the cluster's own RDS hostname on 5432; private DNS returns a Lattice address. The resource gateway in vpc-reporting-prod source-NATs the connection to the cluster. No auth policy applies to resources.

Build it

Step 1

The service network in the network account, shared with RAM

Lattice has three owner roles: service network owner, service owner and resource owner. The network account owns the service network, the boundary that holds services and resource configurations; teams own their services. The network team decides who is connected, teams decide what they publish.

With AWS_IAM auth, requests are denied until an auth policy allows them. Sharing must be enabled to offer the network through RAM.

Create the service network and share it with the organization (AWS CLI, network account 111111111111) 
aws vpc-lattice create-service-network --name booking-services \
  --auth-type AWS_IAM \
  --sharing-config enabled=true

# every account in o-travel1234 can associate services and VPCs with it
aws ram create-resource-share --region us-east-1 \
  --name booking-services-sn \
  --resource-arns arn:aws:vpc-lattice:us-east-1:111111111111:servicenetwork/sn-0bookingsvcnet001 \
  --principals arn:aws:organizations::999999999999:organization/o-travel1234 \
  --no-allow-external-principals

Lattice is Regional. The documentation used here describes no cross-Region service network, so eu-central-1 would get its own, and cross-Region calls stay on Transit Gateway peering or cross-Region PrivateLink. Choose subnets by AZ ID: Lattice does not support use1-az3.

Step 2

Services, listeners, rules and target groups

A Lattice service is a small managed load balancer owned by the team: listeners (HTTP, HTTPS or TLS passthrough), rules matching path, method or headers, and target groups of type INSTANCE, IP, LAMBDA or ALB. Target groups live in the service's account; IP and instance targets must be in the target group's VPC. Defaults: two listeners per service, ten rules per listener (adjustable).

Pricing service and its two target groups (AWS CLI, pricing account 232323232323) 
aws vpc-lattice create-service --name pricing \
  --auth-type AWS_IAM \
  --custom-domain-name pricing.svc.example.com \
  --certificate-arn arn:aws:acm:us-east-1:232323232323:certificate/CERT_ID

# one Lambda function per LAMBDA target group
aws vpc-lattice create-target-group --name pricing-quotes --type LAMBDA
aws vpc-lattice register-targets --target-group-identifier tg-0pricinglambda001 \
  --targets id=arn:aws:lambda:us-east-1:232323232323:function:pricing-quotes

# the legacy engine on EC2, health-checked on /health
aws vpc-lattice create-target-group --name pricing-bulk --type INSTANCE \
  --config 'port=8443,protocol=HTTPS,protocolVersion=HTTP1,vpcIdentifier=vpc-pricing-prod,healthCheck={enabled=true,protocol=HTTPS,path=/health}'
aws vpc-lattice register-targets --target-group-identifier tg-0pricingbulkec201 \
  --targets id=i-0bulkpricing0001 id=i-0bulkpricing0002

The default action goes to Lambda; a rule catches /v1/bulk. Actions are forward (with weights) or a fixed 404 or 500.

Listener and the path rule (AWS CLI, pricing account) 
aws vpc-lattice create-listener --service-identifier svc-0pricing000000001 \
  --name https-443 --protocol HTTPS --port 443 \
  --default-action '{"forward":{"targetGroups":[{"targetGroupIdentifier":"tg-0pricinglambda001"}]}}'

aws vpc-lattice create-rule --service-identifier svc-0pricing000000001 \
  --listener-identifier LISTENER_ID --name bulk-to-ec2 --priority 10 \
  --match '{"httpMatch":{"pathMatch":{"match":{"prefix":"/v1/bulk"}}}}' \
  --action '{"forward":{"targetGroups":[{"targetGroupIdentifier":"tg-0pricingbulkec201"}]}}'

Loyalty migrates with weights: the old internal ALB is an ALB target group (an internal ALB can sit behind up to two Lattice services), and the new ECS tasks register in an IP target group.

Loyalty default action: 90 percent to the old ALB, 10 percent to the new tasks (AWS CLI, loyalty account 242424242424) 
aws vpc-lattice create-listener --service-identifier svc-0loyalty000000001 \
  --name https-443 --protocol HTTPS --port 443 \
  --default-action '{"forward":{"targetGroups":[{"targetGroupIdentifier":"tg-0loyaltyalb000001","weight":90},{"targetGroupIdentifier":"tg-0loyaltyecsip0001","weight":10}]}}'

# the owner of a service associates it with the shared network; across accounts use the network's ARN
aws vpc-lattice create-service-network-service-association \
  --service-identifier svc-0loyalty000000001 \
  --service-network-identifier arn:aws:vpc-lattice:us-east-1:111111111111:servicenetwork/sn-0bookingsvcnet001

Lattice does not validate target certificates (self-signed is fine), and if every target is unhealthy it fails open, so health checks are not a kill switch.

Target security groups must allow the managed prefix list com.amazonaws.us-east-1.vpc-lattice. Requests arrive from Lattice, so a rule referencing the caller's security group never matches.

Step 3

Fare search on EKS with the AWS Gateway API Controller

The fare search team works in Kubernetes. The AWS Gateway API Controller implements the Kubernetes Gateway API on Lattice. Its documentation maps the objects:

  • GatewayClass: identifies VPC Lattice as the implementation.
  • Gateway (cluster operator): a service network.
  • HTTPRoute (developer): a Lattice service with listeners, rules and target groups pointing at the pods behind a Kubernetes service; its target groups can span clusters and VPCs.

The controller's IAM role manages Lattice objects in 222222222222, so the service stays owned by the bookings account. Node and pod security groups must allow the Lattice prefix list. The controller covers east-west traffic only; public ingress stays on CloudFront and the ALB (Inbound perimeter).

App Mesh reaches end of support on September 30, 2026; AWS names ECS Service Connect as the path for ECS. For EKS, Lattice through this controller is one option.

Step 4

Auth policies at two levels, with SigV4 callers

Auth policies are IAM resource policies for vpc-lattice-svcs:Invoke. A request needs an allow from both the network and the service policy, and from the caller's IAM identity policy; an explicit deny wins. Callers sign with SigV4 (the AWS SDKs do this); unsigned requests count as anonymous. The network team writes a coarse guardrail, the teams the fine rules.

booking-services-auth.json: the network-level guardrail (applied by the network account) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "vpc-lattice-svcs:Invoke",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "aws:PrincipalOrgID": "o-travel1234" },
        "StringNotEqualsIgnoreCase": { "aws:PrincipalType": "anonymous" }
      }
    }
  ]
}
pricing-auth.json: only the fare search role, only GET on /v1/quotes (applied by the pricing account) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::222222222222:role/fare-search-pods" },
      "Action": "vpc-lattice-svcs:Invoke",
      "Resource": "arn:aws:vpc-lattice:us-east-1:232323232323:service/svc-0pricing000000001/*",
      "Condition": {
        "StringEquals": { "vpc-lattice-svcs:RequestMethod": "GET" },
        "StringLike": { "vpc-lattice-svcs:RequestPath": "/v1/quotes*" }
      }
    }
  ]
}
Attach both policies (AWS CLI, network account, then pricing account) 
aws vpc-lattice put-auth-policy --resource-identifier sn-0bookingsvcnet001 \
  --policy file://booking-services-auth.json

aws vpc-lattice put-auth-policy --resource-identifier svc-0pricing000000001 \
  --policy file://pricing-auth.json

The loyalty policy adds vpc-lattice-svcs:SourceVpc = vpc-partner-api for the partner gateway's role in 252525252525, so its credentials are useless from any other VPC. Other keys cover port, headers, query strings, service network ARN and source VPC owner. Policies are limited to 10 KB.

Auth policies are not evaluated for resource configurations such as the reporting database, even at network level. The RAM share and the security groups (association or endpoint, and resource gateway) control resources.

Step 5

Connect consumers: VPC associations and a service network endpoint

A VPC association connects the whole VPC through link-local and AWS-owned non-routable addresses: no CIDR space, no routes. Limits: one service network per VPC this way, and only clients inside the VPC; traffic arriving over peering, Transit Gateway, Direct Connect or VPN cannot use it. Up to five security groups decide which clients may enter; once added, at least one must stay.

Associate the booking VPC, with private DNS for resources (AWS CLI, bookings account 222222222222) 
# sg-0latticeclients allows HTTPS and 5432 only from the EKS node and pod security groups
aws vpc-lattice create-service-network-vpc-association \
  --service-network-identifier arn:aws:vpc-lattice:us-east-1:111111111111:servicenetwork/sn-0bookingsvcnet001 \
  --vpc-identifier vpc-bookings-prod \
  --security-group-ids sg-0latticeclients \
  --private-dns-enabled

A service network endpoint is the PrivateLink-based mode: a VPC endpoint of type ServiceNetwork with addresses from the consumer's subnets, so anything routed to them can use it, including the data centers. A VPC can have one per service network, at no hourly charge.

A second service network endpoint in the shared services VPC, for data center callers (AWS CLI, network account) 
# sg-booking-svc-onprem allows HTTPS from 10.100.0.0/16 (US data center) only
aws ec2 create-vpc-endpoint --vpc-endpoint-type ServiceNetwork \
  --vpc-id vpc-shared-services \
  --subnet-ids subnet-shared-az1 subnet-shared-az2 subnet-shared-az4 \
  --service-network-arn arn:aws:vpc-lattice:us-east-1:111111111111:servicenetwork/sn-0bookingsvcnet001 \
  --security-group-ids sg-booking-svc-onprem

The endpoint takes a contiguous /28 per AZ for services, allocated even while the network is empty, plus one IPv4 address per resource configuration per AZ. It sits beside the hotel API endpoint from Overlapping CIDRs. Its default DNS names are publicly resolvable and return its private addresses, so data center jobs can use them.

The 2023 "External connectivity" proxy pattern for on-premises and other-Region access has, per an AWS notice on that post, largely been replaced by service network endpoints. Endpoints also avoid the static route that Windows and macOS clients may need on an association.

Step 6

The reporting database as a resource configuration

The database joins as a resource configuration, the building block PrivateLink uses for VPC resources (Task 1.6). A resource gateway (interfaces across AZs in vpc-reporting-prod) is the entry point. It does not load balance, and the database sees gateway addresses, so its security group allows the gateway's. It keeps PUBLIC DNS resolution, because IN_VPC gateways cannot serve ARN configurations. IPv4 addresses per interface (1 to 62, default 16) cap concurrent connections.

Resource gateway and an ARN-type configuration for the Aurora cluster (AWS CLI, reporting account 262626262626) 
aws vpc-lattice create-resource-gateway --name reporting-db-gw \
  --vpc-identifier vpc-reporting-prod \
  --subnet-ids subnet-rpt-az1 subnet-rpt-az2 subnet-rpt-az4 \
  --security-group-ids sg-reporting-rgw \
  --ipv4-addresses-per-eni 32

# the network is shareable, so the configuration must allow association with a shareable network (default false)
aws vpc-lattice create-resource-configuration --name reporting-db \
  --type ARN \
  --resource-gateway-identifier rgw-0reportingdb00001 \
  --resource-configuration-definition 'arnResource={arn=arn:aws:rds:us-east-1:262626262626:cluster:reporting-prod}' \
  --allow-association-to-shareable-service-network

The reporting account shares the configuration with the network account through RAM, and the network account adds it to booking-services, as it did for the hotel APIs.

Add the shared database to the service network (AWS CLI, network account) 
aws vpc-lattice create-service-network-resource-association \
  --service-network-identifier sn-0bookingsvcnet001 \
  --resource-configuration-identifier rcfg-0reportingdb00001

RDS is the only ARN type (not publicly accessible clusters), and AWS manages the child configurations. With private DNS, clients keep the cluster's writer and reader hostnames, so certificate name checks pass. Resources are TCP only, and through an association each gets an address from the non-routable 129.224.0.0/17. The resource gateway patterns blog adds DNS-type configurations for reaching SaaS or public endpoints through one central VPC with NAT gateways.

Step 7

Custom domains with Route 53, access logs and metrics

Every service gets a generated name such as pricing-0pricing000000001.HASH.vpc-lattice-svcs.us-east-1.on.aws. The Lattice guide is explicit that the custom domain set in Step 2 only works once DNS maps it to that generated name, and you create that record. A service has one custom domain, it cannot be changed after creation, and it must be unique within the service network. HTTPS on a custom domain needs your own ACM certificate; there is no default certificate fallback.

Since June 2025, Route 53 has an alias to VPC Lattice service record type. The network account keeps svc.example.com as a private hosted zone on the Route 53 Profile rp-travel-dns-01, so every spoke resolves the same names. It creates A and AAAA alias records, with target health evaluation off, as the Route 53 guide shows.

pricing-alias.json: A record alias to the pricing service (apply with change-resource-record-sets in the network account) 
{
  "Comment": "pricing.svc.example.com to the Lattice service",
  "Changes": [
    {
      "Action": "CREATE",
      "ResourceRecordSet": {
        "Name": "pricing.svc.example.com",
        "Type": "A",
        "AliasTarget": {
          "HostedZoneId": "SERVICE_DNS_HOSTED_ZONE_ID",
          "DNSName": "pricing-0pricing000000001.HASH.vpc-lattice-svcs.us-east-1.on.aws",
          "EvaluateTargetHealth": false
        }
      }
    }
  ]
}

The alias target values come from the dnsEntry (domain name and hosted zone ID) that create-service returns. To keep records in step as teams add services, AWS publishes the Guidance for Amazon VPC Lattice Automated DNS Configuration, which creates the records automatically.

Access logs. Subscriptions attach to a network, service or resource configuration and deliver to CloudWatch Logs, S3 or Firehose. The network owner sees only traffic of its associated clients and services; it logs services and resources separately, and teams log their own services. Flow logs show Lattice addresses, so access logs identify callers.

Network-level access logs for services and for resources (AWS CLI, network account) 
aws vpc-lattice create-access-log-subscription \
  --resource-identifier sn-0bookingsvcnet001 \
  --service-network-log-type SERVICE \
  --destination-arn arn:aws:logs:us-east-1:111111111111:log-group:/lattice/booking-services

aws vpc-lattice create-access-log-subscription \
  --resource-identifier sn-0bookingsvcnet001 \
  --service-network-log-type RESOURCE \
  --destination-arn arn:aws:logs:us-east-1:111111111111:log-group:/lattice/booking-resources

Metrics appear in the AWS/VpcLattice namespace, per service and per target group, each also by AZ. Useful alarms: HTTPCode_5XX_Count and RequestTime (percentiles) per service, HTTPCode_VpcLattice_403_Count for requests Lattice itself rejected (auth denials after a policy change), RequestTimeoutCount, and ConnectionErrorCount per target group.

Design decisions

Who owns what

The network account owns the service network, its guardrail policy, network-level logs and the on-premises endpoint. Teams own services, target groups, certificates and fine policies; consumers own their associations and their security groups. The caller of an association must own one side of it. This mirrors the RAM-shared Transit Gateway on Task 2.2.

Identity at layer 7, security groups at layer 4

Any associated VPC can reach any listener; the real boundary is the pair of auth policies, which a route table cannot offer. Security groups still guard the association and the targets. For PCI DSS, the payments VPC (10.40.48.0/21) is not associated; card data stays on its segmented Transit Gateway path (Task 4.1).

Cost model

At the us-east-1 rates on Task 1.6, Lattice charges per service, not per consumer: $0.025 per service-hour, $0.025 per GB, and $0.10 per million requests after 300,000 each hour. Three services cost about 3 × $0.025 × 730 ≈ $55 a month before traffic. The database configuration costs about $0.10 per hour (about $73 a month) plus about $0.01 per GB for the consumer and $0.006 for the provider. Associations and endpoints are free.

The same three services through PrivateLink to six VPCs need 18 interface endpoints in three AZs: about 18 × 3 × $0.01 × 730 ≈ $394 a month, plus an NLB each. For bulk flows, $0.025 per GB exceeds Transit Gateway's $0.02, so replication stays on the hub (Task 3.3).

Limits that shape the design

  • One service network per VPC through associations: a VPC that needs a second network uses an endpoint for it.
  • 10 Gbps and 10,000 requests per second per service per AZ (raised through your AWS account team).
  • Service connections live at most 10 minutes, with an idle timeout of 60 to 600 seconds; there is no native WebSocket support. Long-lived streams use a TLS passthrough listener or a resource configuration (resources have a 350-second idle timeout and no lifetime limit).
  • Quotas: 500 services and 500 VPC associations per service network, 10 target groups per service, 1,000 targets per target group, five security groups per association (hard), MTU 8,500.

Partner traffic

The partner gateway is a company workload, so it joins like any VPC. The airlines still use the PrivateLink endpoint service vpce-svc-0fares1234567890 on Task 1.6: external accounts get one service, not the internal network.

Alternatives

PrivateLink endpoint services per service

Each team puts its service behind an NLB and publishes an endpoint service; each consumer VPC creates an interface endpoint per service. It is one-way, tolerates overlapping CIDRs and is on the exam. But it grows as services × consumers, has no layer 7 routing or IAM authorization (endpoint policies are not caller-level auth for custom services), and the provider sees NLB addresses unless proxy protocol v2 is used. Best for offering one service to external accounts or SaaS customers.

Transit Gateway with internal ALBs

The company's default network: every VPC on tgw-use1, services behind internal ALBs, authorization in application code. It gives full layer 3: any protocol, UDP, ICMP, connections in both directions, on-premises reach. It needs unique CIDRs, route table segmentation and security group rules by address (Transit Gateway security group referencing works for inbound rules only, within one gateway). Choose it when the need is "connect networks", not "publish services".

VPC peering

Cheapest for a few heavy pairs (no hourly or processing charge), with security group references in both directions within a Region. It is non-transitive, refuses overlapping CIDRs, and has no service-level authorization. Fine for two or three VPCs, not for a growing service estate.

Centralized interface endpoints through Lattice

The September 2026 centralization blog applies the same building blocks to AWS service endpoints: the shared services VPC keeps the interface endpoints, each exposed as a resource configuration behind a resource gateway, and consumers reach only what is associated. It suits overlapping CIDRs, tight access scope, or a hub built only for endpoints. If a Transit Gateway or Cloud WAN hub already exists for general connectivity, reusing it remains a valid choice.

When Lattice does not fit

  • Layer 3 needs: server-initiated connections, ICMP, routing to whole subnets. Use Transit Gateway, Cloud WAN or peering.
  • UDP and other protocols: services take HTTP, HTTPS or TLS passthrough; resource configurations take TCP. UDP appears only in the new CIDR configuration type, for DNS through tunnel endpoints.
  • Cross-Region: service networks are Regional; use cross-Region PrivateLink or the existing peered hubs.
  • Bulk data: per-GB processing above Transit Gateway's rate, and per-service throughput limits.
  • Client IP visibility: targets see Lattice addresses; identity comes from SigV4 and access logs instead.

Testing it

  1. Prove authorization, not reachabilityFrom a fare search pod, a signed GET /v1/quotes to pricing.svc.example.com succeeds. The same request unsigned, a POST, or a call to /v1/admin must return 403, and HTTPCode_VpcLattice_403_Count must rise.
  2. Prove the source VPC conditionRun the partner gateway's role from a test instance in the loyalty VPC: loyalty must deny it. From vpc-partner-api it succeeds.
  3. Prove the association security groupAn instance in the booking VPC that is not in the EKS security groups gets a timeout, not a 403: it never enters the service network.
  4. Check the weightsSend 1,000 requests to loyalty and count by target group in the service's access logs: about 900 to the ALB, about 100 to the IP target group.
  5. Test the database pathFrom a loyalty task, connect to the cluster's writer hostname on 5432 with certificate validation on. From a VPC whose association security group lacks 5432, the connection times out. In the reporting VPC, the database logs show resource gateway addresses as clients.
  6. Test the data center pathFrom a batch host in 10.100.0.0/16, resolve the endpoint's DNS name for pricing (it must return addresses in 10.41.0.0/16) and send a signed request.
  7. Test failure behaviourScale the new loyalty tasks to unhealthy and watch Lattice fail open; the runbook must set the weight to 0 instead of relying on health checks. Hold a connection open for more than 10 minutes and confirm clients reconnect cleanly.

Exam angles

Lattice itself is an extra; these rows point to the exam tasks where the comparison points and resource configurations are tested.

TaskWhat this architecture demonstrates

2.2 Implement multi-account, multi-Region connectivityRAM sharing to the organization, owner roles across accounts, an endpoint reachable over Direct Connect and the Transit Gateway

"Hundreds of microservices in many accounts call each other over HTTP or gRPC; authorize by IAM identity; teams must not manage routes or coordinate CIDRs" points to VPC Lattice. "Offer one service to customer or partner accounts, one way, with overlapping CIDRs" points to a PrivateLink endpoint service, and "share a database without a load balancer" to a resource configuration with a resource endpoint. "Full two-way routing between many VPCs and on premises, any protocol" points to Transit Gateway (or Cloud WAN); "two VPCs, heavy traffic, lowest cost" to VPC peering.
