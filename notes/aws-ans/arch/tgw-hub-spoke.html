Reference architecture

Transit Gateway hub and spoke with segmentation

The travel company connects hundreds of VPCs in many accounts, and both data centers, through one Transit Gateway per Region owned by the network account. Route tables keep production, development, shared services and on premises apart, so one router serves everyone without becoming a flat network.

Scenario and requirements

The travel company (example.com) has about 300 VPCs in us-east-1, eu-central-1 and ap-northeast-1, owned by many accounts in AWS Organizations. The booking platform runs on EKS, partners call a fare search API, and the payment services that handle card data are in scope for PCI DSS. The network team in account 111111111111 must give every team connectivity without letting a development workload reach production, and without building hundreds of peering connections.

RequirementDesign choice
Hundreds of VPCs, transitive routing to the data centersOne Transit Gateway per Region, owned by the network account and shared to the organization with AWS RAM
Production and development never talkSeparate Transit Gateway route tables per environment, no cross propagation, plus blackhole routes as a backstop
Everyone reaches shared services (DNS, directory, tooling) and on premisesShared services and on-premises attachments propagate into every environment table
Network team controls who joinsAuto accept shared attachments off; each attachment is accepted and associated by automation in the network account
No overlapping addresses, summarizable per RegionSpoke CIDRs allocated from VPC IPAM pools carved from one /14 per Region
Visibility and cost charge-backTransit Gateway flow logs to S3, CloudWatch drop metrics, Network Manager topology and events

The address plan used on this page:

  • us-east-1: 10.40.0.0/14 in IPAM, split into production 10.40.0.0/16, shared services 10.41.0.0/16, development 10.42.0.0/16 and 10.43.0.0/16 held for growth. The production booking VPC is 10.40.8.0/21.
  • eu-central-1: 10.44.0.0/14 (booking VPC 10.44.8.0/21); ap-northeast-1: 10.48.0.0/14, each split the same way.
  • On premises: US data center 10.100.0.0/16 (AS 65010), European data center 10.200.0.0/16 (AS 65020), reached through transit VIFs on one Direct Connect gateway (AS 64512), with BGP Site-to-Site VPNs as backup.
  • Transit Gateway ASNs: 64521, 64522 and 64523. They must differ from the Direct Connect gateway's 64512, and AWS recommends unique ASNs for peered Transit Gateways.

How it works

Steps marked AWS happen automatically once configured; steps marked Network team are actions in the network account.

  1. A new spoke joins
  2. Account creates a VPC from IPAMApp teamThe development account asks the shared IPAM pool for a /21 and gets the next free block in 10.42.0.0/16, so it cannot overlap anything else.
  3. Attachment requestApp teamIt creates a VPC attachment to the shared Transit Gateway with one small subnet per Availability Zone. The attachment waits in pendingAcceptance.
  4. Accept, associate, propagateNetwork teamAutomation checks the attachment's tags, accepts it, associates it with the dev route table and propagates its CIDR into the dev and shared tables only.
  5. A production packet to the data center
  6. VPC route tableAWSA booking pod at 10.40.12.30 sends to 10.100.20.5. The subnet route table matches 10.0.0.0/8 and sends the packet to the Transit Gateway ENI in the same Availability Zone.
  7. Lookup in the associated tableAWSThe booking attachment is associated with the prod table. It holds the shared services CIDR, the propagated on-premises routes from the Direct Connect gateway and VPN attachments, and blackholes for development.
  8. Best route chosenAWSLongest prefix wins; for an equal prefix, static routes beat propagated ones, and Direct Connect gateway routes beat VPN routes, so the VPN only carries traffic if Direct Connect fails.
  9. Out through the Direct Connect gatewayAWSThe packet leaves on a transit VIF. The data center learned the return path as the allowed prefix 10.40.0.0/14.
  10. Return trafficAWSThe on-premises attachment is associated with the onprem table, which holds production, development and shared services routes, so the reply reaches the booking VPC.
  11. A development packet to production
  12. Dropped at the hubAWSThe dev table has no production routes and a blackhole for 10.40.0.0/16. The Transit Gateway drops the packet, counts it in PacketDropCountBlackhole, and the flow log records it under packets-lost-blackhole.

Build it

Step 1

The Transit Gateway in the network account, shared through RAM

Create one Transit Gateway per Region with the default association and propagation turned off. With both defaults on, every new attachment would join the default table and see every other attachment, which is the flat design segmentation is meant to avoid. If both are disabled, no default route table is created. Leave AutoAcceptSharedAttachments disabled (its default) so the network team approves every spoke, and turn on security group referencing at the gateway level, where it is off by default.

network-us-east-1.yaml: the Transit Gateway and its organization share (CloudFormation, network account) 
TransitGateway:
  Type: AWS::EC2::TransitGateway
  Properties:
    Description: travel-hub-us-east-1
    # unique per Region; must differ from the Direct Connect gateway (64512)
    AmazonSideAsn: 64521
    # the network team accepts each shared attachment
    AutoAcceptSharedAttachments: disable
    # no default table: every attachment is placed deliberately
    DefaultRouteTableAssociation: disable
    DefaultRouteTablePropagation: disable
    DnsSupport: enable
    # ECMP across the BGP VPN tunnels
    VpnEcmpSupport: enable
    # off by default at the gateway; attachments default to enable
    SecurityGroupReferencingSupport: enable
    Tags:
      - { Key: Name, Value: tgw-use1 }

TgwShare:
  Type: AWS::RAM::ResourceShare
  Properties:
    Name: tgw-us-east-1-shared
    ResourceArns:
      - !Sub arn:aws:ec2:${AWS::Region}:${AWS::AccountId}:transit-gateway/${TransitGateway}
    Principals:
      - arn:aws:organizations::999999999999:organization/o-travel1234
    # keep the hub inside the organization
    AllowExternalPrincipals: false

Sharing to the organization (with RAM sharing enabled from the management account) means new accounts see the Transit Gateway automatically. Some things stay with the owner: only the Transit Gateway owner can associate it with a Direct Connect gateway, and VPN and Connect attachments are created in the owner's account, so customer gateways and VPNs live with the network team. Either side can delete a VPC attachment.

Turning AutoAcceptSharedAttachments on removes the approval step but not the segmentation, because with default association off a new attachment has no route table until someone associates it. In the exam, "the network team must approve each VPC that joins" points to auto accept off; "attachments should route automatically" points to default association or automation reacting to the attachment event.

Step 2

Route tables, associations, propagations and blackholes

Four route tables per Region carry the segmentation. Each attachment is associated with exactly one table, which decides where its packets can go. It propagates its routes into whichever tables should be able to reach it. Propagation cannot be filtered: a VPC attachment propagates its CIDRs, a VPN or Direct Connect gateway attachment propagates what it learned over BGP.

Route table (associated attachments)Routes in it (from propagation unless noted)
prod (production spokes)Shared services VPCs, Direct Connect gateway and VPN routes, peer Regions' production summaries (static); blackhole 10.42.0.0/16
dev (development spokes)Development VPCs, shared services VPCs, on-premises routes; blackhole 10.40.0.0/16
shared (shared services VPCs)Every production and development VPC, on-premises routes
onprem (Direct Connect gateway and VPN attachments)Every production, development and shared services VPC

Production spokes do not propagate into prod, so production VPCs cannot reach each other through the hub either. That is deliberate: PCI DSS scope stays small when the payment VPC is reachable only from the services that need it. Teams that must talk get an explicit route, a shared VPC, or a PrivateLink service. Development spokes do propagate into dev, because developers want any-to-any inside their own environment.

The development table: associate a spoke, propagate it, and block production (AWS CLI, network account) 
# one table per segment
aws ec2 create-transit-gateway-route-table --transit-gateway-id tgw-use1 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=dev}]'

# the spoke looks up its destinations in dev
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-dev \
  --transit-gateway-attachment-id tgw-attach-search-dev

# dev spokes see each other, shared services and on premises can reach it
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-dev \
  --transit-gateway-attachment-id tgw-attach-search-dev
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-shared \
  --transit-gateway-attachment-id tgw-attach-search-dev
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-onprem \
  --transit-gateway-attachment-id tgw-attach-search-dev

# backstop: even if someone propagates a production VPC here by mistake, drop it
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-dev \
  --destination-cidr-block 10.40.0.0/16 --blackhole

The blackhole works because of route priority: longest prefix first, and for the same prefix a static (or blackhole) route beats a propagated one. A propagated production /21 would still be more specific than the /16 blackhole, so the blackhole is a safety net, not a replacement for correct propagation. Blackholes are also how a centralized egress design stops spokes reaching each other through a 0.0.0.0/0 route.

Peer Regions are reached by static summary routes on the Transit Gateway peering attachment (AWS CLI) 
# Transit Gateway peering supports static routes only
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.44.0.0/16 \
  --transit-gateway-attachment-id tgw-attach-peer-euc1

Managed prefix lists keep long lists tidy: create-transit-gateway-prefix-list-reference turns every entry of a prefix list into a route (active or blackhole), and the same list can be shared through RAM and used in security groups. Each prefix list's maximum entries count toward the route quota.

Step 3

Spokes with IPAM-allocated CIDRs

The Transit Gateway will not route between overlapping VPCs: when a newly attached VPC overlaps one already attached, its CIDR is not propagated. IPAM prevents that up front. The network account (the delegated IPAM administrator) builds pools per Region and environment with allocation rules and shares them to the organization through RAM. Each spoke takes its CIDR from the pool, which also keeps every environment inside one summary that the blackholes and allowed prefixes can name.

A development spoke takes a /21 from the shared pool and attaches to the hub (AWS CLI, development account 444444444444) 
# the pool picks a free, non-overlapping /21 inside 10.42.0.0/16
aws ec2 create-vpc --ipv4-ipam-pool-id ipam-pool-0use1dev12345 \
  --ipv4-netmask-length 21 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=env,Value=dev}]'

# one /28 attachment subnet per AZ, used only by Transit Gateway ENIs
aws ec2 create-transit-gateway-vpc-attachment \
  --transit-gateway-id tgw-use1 \
  --vpc-id vpc-0searchdev \
  --subnet-ids subnet-tgw-az1 subnet-tgw-az2 subnet-tgw-az4 \
  --options DnsSupport=enable,SecurityGroupReferencingSupport=enable \
  --tag-specifications 'ResourceType=transit-gateway-attachment,Tags=[{Key=segment,Value=dev}]'

# send everything internal to the hub
aws ec2 create-route --route-table-id rtb-search-dev-app \
  --destination-cidr-block 10.0.0.0/8 --transit-gateway-id tgw-use1

The network account then accepts the attachment, and the association and propagation from Step 2 follow. In practice an EventBridge rule on the new attachment, or a StackSet deployed to the OU, runs those commands from the segment tag.

Accept the pending attachment (AWS CLI, network account) 
aws ec2 accept-transit-gateway-vpc-attachment \
  --transit-gateway-attachment-id tgw-attach-search-dev
  • Availability Zones: only resources in AZs that have an attachment subnet can reach the Transit Gateway, so give one subnet in every AZ the VPC uses. Use dedicated small subnets with their own route table and network ACL, so filtering on workload subnets never blocks transit traffic.
  • Limits per VPC: a Transit Gateway cannot have two attachments to the same VPC, and a VPC can attach to at most five Transit Gateways.
  • DNS: the Transit Gateway does not resolve Route 53 private hosted zones of attached VPCs. Name resolution uses Resolver endpoints and shared rules in the shared services VPC.
  • Shared VPCs cut attachments: where possible the network account owns per-environment VPCs and shares subnets to application accounts, so one attachment serves many accounts. The VPC owner pays for the attachment.
Step 4

Direct Connect gateway and VPN attachments

The data centers reach every Region over transit VIFs on one Direct Connect gateway, associated with the Transit Gateways in all three Regions. The allowed prefixes on each association are what AWS advertises to the data centers, so each Region sends one summary instead of hundreds of VPC routes. Allowed prefixes must not overlap between Transit Gateways on the same Direct Connect gateway, and the parameter is required for a Transit Gateway association.

Associate the us-east-1 Transit Gateway with the Direct Connect gateway and advertise one summary (AWS CLI, network account) 
aws directconnect create-direct-connect-gateway-association \
  --direct-connect-gateway-id dxgw-travel-global \
  --gateway-id tgw-use1 \
  --add-allowed-prefixes-to-direct-connect-gateway cidr=10.40.0.0/14

The association creates a Direct Connect gateway attachment on the Transit Gateway. Associate it with onprem and propagate it into prod, dev and shared, so the data center routes learned over BGP appear in every table. A development-only data center lab could instead be kept out of prod by a separate VIF and attachment.

Backup is a BGP Site-to-Site VPN from each data center to its nearest Transit Gateway. Two tunnels per connection, and ECMP across tunnels and connections because VpnEcmpSupport is on. The VPN attachment is associated with onprem and propagated like the Direct Connect gateway attachment.

The US data center's backup VPN, terminated on the Transit Gateway (AWS CLI, network account) 
# the customer gateway uses AS 65010; dynamic routing is the default when no static option is set
aws ec2 create-vpn-connection --type ipsec.1 \
  --transit-gateway-id tgw-use1 \
  --customer-gateway-id cgw-us-dc1-a

# after the attachment appears, place it like any other
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-onprem \
  --transit-gateway-attachment-id tgw-attach-us-dc1-vpn
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-us-dc1-vpn

When the same prefix arrives from Direct Connect and from VPN, the Transit Gateway prefers the Direct Connect gateway route, so the VPN is a backup with no extra configuration. Static routes beat both, so a forgotten static route to the VPN attachment silently moves all traffic onto the tunnels.

Step 5

Security group referencing across the hub

Route tables decide which networks can talk; security groups decide which workloads. Since September 2024, VPCs on the same Transit Gateway can reference each other's security groups in inbound rules, so the payment database can allow "the booking service's security group" instead of a list of CIDRs that changes whenever pods move. It must be enabled on the Transit Gateway (done in Step 1) and on the attachment (on by default), and costs nothing extra.

Payments database allows PostgreSQL only from the booking service's security group in another VPC (AWS CLI, payments account) 
aws ec2 authorize-security-group-ingress \
  --group-id sg-0paymentsdb \
  --ip-permissions 'IpProtocol=tcp,FromPort=5432,ToPort=5432,UserIdGroupPairs=[{GroupId=sg-0bookingsvc,UserId=222222222222,Description=booking-eks-pods}]'

Limits to remember: inbound rules only; both VPCs on the same Transit Gateway, so the same Region (not across Transit Gateway peering); not through Gateway Load Balancer or Network Firewall inspection; not for PrivateLink endpoints; not in the use1-az3 zone. Across Regions, rules fall back to CIDRs, which is where the IPAM summaries help again.

A security group reference does not create a route. If the route tables block the path (or the referenced VPC sits behind an inspection VPC), the rule is accepted but traffic never arrives. Check routing first, then the rule.

Step 6

Flow logs, metrics and Network Manager

Transit Gateway flow logs are created by the Transit Gateway owner, per gateway or per attachment, to S3, CloudWatch Logs or Firehose. The default format includes the version 2 to 6 fields: source and destination VPC, subnet, account and AZ ID, the attachment and its pair, plus counters of packets lost to no route, a blackhole, MTU exceeded and TTL expired. Multicast is not logged, and Connect traffic appears on its transport attachment.

Flow logs for the whole us-east-1 Transit Gateway to the central bucket (AWS CLI, network account) 
aws ec2 create-flow-logs --resource-type TransitGateway \
  --resource-ids tgw-use1 \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::central-flow-logs-111111111111/tgw/

From these logs, Athena queries grouped by tgw-src-vpc-account-id and bytes show which account sends the most data, which is the input for charge-back. Since November 2025, Flexible Cost Allocation metering policies can also bill data processing to the source, destination or owner account directly.

CloudWatch publishes BytesIn, BytesOut, PacketDropCountBlackhole and PacketDropCountNoRoute per gateway and attachment (use the Sum statistic). Alarm on blackhole drops from production: they mean someone is trying a path the design forbids.

Register all three Transit Gateways in one global network (AWS CLI, Network Manager home Region us-west-2) 
aws networkmanager register-transit-gateway --region us-west-2 \
  --global-network-id global-network-0travel1234567 \
  --transit-gateway-arn arn:aws:ec2:us-east-1:111111111111:transit-gateway/tgw-use1
# repeat for the eu-central-1 and ap-northeast-1 gateways

The global network is free. It gives a topology tree and map, events (attachments created, routes installed or uninstalled with their route_static or route_propagated type and active or blackhole state, VPN BGP down) delivered to EventBridge in us-west-2, and Route Analyzer for Transit Gateway route tables. Add the data centers as sites and devices with customer gateway associations to see the hybrid edge on the same map.

Step 7

A VPC peering for one heavy pair

Every byte a VPC sends into the Transit Gateway costs data processing ($0.02 per GB), billed to the sender's attachment owner. The booking VPC sends about 40 TB a month of search results to the fare cache VPC (10.40.32.0/20), both in production in us-east-1. Through the hub that is roughly 40,960 GB × $0.02 ≈ $820 a month in processing alone, plus an extra hop and a 100 Gbps per-AZ attachment ceiling. A VPC peering has no hourly or processing charge, is free within one AZ (matched by AZ ID) and costs $0.01 per GB each way across AZs.

Peer the two VPCs and add the more specific route (AWS CLI) 
# same Region, cross-account; the fare cache account accepts
aws ec2 create-vpc-peering-connection \
  --vpc-id vpc-0bookingprod \
  --peer-vpc-id vpc-0farecache \
  --peer-owner-id 555555555555

# /20 beats the 10.0.0.0/8 route to the Transit Gateway by longest prefix
aws ec2 create-route --route-table-id rtb-bookings-app \
  --destination-cidr-block 10.40.32.0/20 \
  --vpc-peering-connection-id pcx-0bookfare123456789

The fare cache VPC adds the mirror route to 10.40.8.0/21. Everything else still flows through the hub, so segmentation is unchanged. Peering is not transitive and has no edge-to-edge routing, so the cache cannot reach the data centers or other VPCs through the booking VPC. Same-Region peering also supports security group references in both directions.

Keep the peering for a small number of heavy, stable pairs. Ten such pairs are manageable; a mesh needs n(n−1)/2 connections and every new VPC multiplies the routes, which is what the Transit Gateway replaced.

Design decisions

One Transit Gateway per Region, in a network account

AWS guidance is typically one Transit Gateway per Region, using route tables for isolation; extra gateways are not needed for availability. A second gateway is valid only to limit blast radius or to separate control planes (for example after an acquisition). Keeping it in the network account means one team owns route tables, Direct Connect associations and VPNs, while application teams only create attachments. Detail: Task 1.6 and Task 1.5.

Route tables as the segmentation boundary

A packet with no route is dropped at the hub, before any security group sees it, and a single table change cannot be undone by an application team. The trade-off is operational: every new segment needs a table and propagation rules, and the 20 route tables per gateway (adjustable) and 10,000 total routes are real ceilings. Summaries from IPAM keep the route count small.

Auto accept off, with automation

Manual acceptance is a control point, but a human in the loop for 300 VPCs is slow. Accept, associate and propagate from an EventBridge-driven function or StackSet that reads the attachment's segment tag, and reject untagged requests. See Task 2.4.

Blackholes as a backstop, not the main control

The /16 blackholes catch a wrong propagation of a summary-sized route and make forbidden attempts visible in metrics and flow logs. They do not override a more specific propagated route, so propagation discipline is still the real control.

Costs

Attachments are billed per hour (for example $0.05 per VPC attachment-hour in the published us-east-2 example; partial hours count as full hours) and data processing at $0.02 per GB sent into the gateway from a VPC, Direct Connect or VPN attachment. One hundred VPC attachments cost about 100 × $0.05 × 730 ≈ $3,650 a month before data, which is why shared VPCs, which cut the number of attachments, matter. Peering attachments pay their hourly charge on each side but no processing for traffic arriving over the peering; inter-Region data transfer is added. The Direct Connect gateway itself is free. See Task 3.3.

Quotas to plan for

  • 5 Transit Gateways per account, 5,000 attachments per gateway, 50 peering attachments (adjustable).
  • 20 route tables per gateway (adjustable) and 10,000 routes across all of them (raised through your AWS account team).
  • Up to 100 Gbps and 7.5 million packets per second per VPC attachment per AZ; the same per AZ for Direct Connect gateway and peering attachments.
  • On the VPC side, propagated routes per VPC route table are limited to 100 (not adjustable), another reason to point a single 10.0.0.0/8 at the gateway.

Alternatives

Full VPC peering mesh

Lowest latency and cost per GB, no aggregate bandwidth limit, and security group references in both directions. But it is not transitive, gives no shared path to Direct Connect or VPN (hybrid connectivity per VPC), refuses any overlapping CIDR, and stops at 125 peers per VPC. AWS suggests it for fewer than about 10 VPCs; here it is kept only for heavy pairs (Step 7).

AWS Cloud WAN

Global segments defined in a JSON policy, attachments placed by tag, and dynamic routing between Regions instead of static peering routes. Cloud WAN costs $0.50 an hour per core network edge plus attachments, and suits many Regions and policy as code. The company plans to move later; Transit Gateways can peer with Cloud WAN and route table attachments map each table to a segment during migration. See Task 2.2.

Centralized inspection through the hub

Instead of trusting route tables alone for east-west traffic, send production-to-development or all inter-VPC traffic through AWS Network Firewall (natively attached to the Transit Gateway since June 2025, appliance mode on automatically) or a Gateway Load Balancer inspection VPC with appliance mode. Adds a processing charge and breaks security group referencing for inspected paths.

PrivateLink or VPC Lattice for service-to-service

When teams need only a service, not network reach, a PrivateLink endpoint service or a VPC Lattice service network gives one-way, application-level access and works with overlapping CIDRs, without any Transit Gateway route.

Transit VPC with appliances

The legacy hub of VPN overlays to EC2 routers. It needs you to run and scale the routers and has per-tunnel bandwidth limits; Transit Gateway replaces it.

Testing it

  1. Prove the allowed paths with Reachability AnalyzerFrom a booking instance to the US data center VPN attachment and 10.100.30.15 on TCP 1433, the analysis should succeed and list the prod route table. It models configuration and sends no packets.
  2. Prove the forbidden pathsFrom a development ENI to a production ENI, the analysis should fail with the dev Transit Gateway route table (the blackhole) as the blocking component. Network Access Analyzer scopes ("no path from development to production") turn this into a standing audit check.
  3. Check the hub's routes with Route AnalyzerIn Network Manager, analyze from the European data center VPN attachment to the Frankfurt booking attachment with the return path included. It checks Transit Gateway route tables only, not VPC routes or security groups.
  4. Read the flow logsAfter a test from development to production, the Transit Gateway flow log should show the flow with a non-zero packets-lost-blackhole, and PacketDropCountBlackhole should rise on the gateway.
  5. Fail Direct Connect over to VPNIn a maintenance window, shut the BGP sessions on the transit VIFs (or use the Direct Connect failover test). The prod table should switch to the VPN-propagated routes within the BGP timers, Network Manager should emit routing events, and synthetic checks from the data center should keep passing.
  6. Test attachment governanceCreate an untagged attachment from a sandbox account and confirm it stays in pendingAcceptance or is rejected, and that a correctly tagged one ends up in exactly one table.

"Hundreds of VPCs in many accounts must reach shared services and the data center, but development must never reach production, with the least operational overhead" is a Transit Gateway shared through RAM with separate route tables per environment (default association and propagation off) and no propagation between production and development. If the question adds "two VPCs exchange tens of terabytes and data processing cost must drop", the answer is a VPC peering between that pair with a more specific route, keeping the Transit Gateway for everything else.
