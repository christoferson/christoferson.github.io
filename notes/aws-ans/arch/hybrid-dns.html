Reference architecture

Hybrid and multi-account DNS

The travel company resolves names in both directions between its data centers and hundreds of VPCs in many accounts. One inbound and one outbound Resolver endpoint per Region, in the network account's shared services VPC, carry all hybrid DNS; a Route 53 Profile hands every VPC the same zones, rules, firewall and logging with a single association.

Scenario and requirements

The travel company (example.com) runs about 300 VPCs in us-east-1, eu-central-1 and ap-northeast-1, connected through the Transit Gateway hub described in Transit Gateway hub and spoke. Its names fall into three zones: example.com is public (booking site, partner API, mail); aws.example.com is a private hosted zone for AWS workloads, with team subzones such as bookings.aws.example.com owned by the workload accounts; corp.example.com is the on-premises Active Directory domain, served by the DNS servers 10.100.0.53 (US data center) and 10.200.0.53 (European data center).

RequirementDesign choice
Data center servers resolve aws.example.com and its subzonesInbound endpoint per Region in the shared services VPC; every private zone associated with that VPC; conditional forwarders on premises
Workloads resolve corp.example.com and on-premises reverse namesOutbound endpoint per Region with forward rules to both data center DNS servers
Hundreds of VPCs, many accounts, one configurationA Route 53 Profile per Region, shared to the organization through AWS RAM
Survive an Availability Zone or a whole RegionEndpoint IPs in two or more AZs; data center forwarders list two Regions
Block malicious domains, keep evidence for PCI DSSDNS Firewall rule groups in the Profile (fail closed); Resolver query logs to the log archive account

Values used on this page:

  • us-east-1: shared services VPC vpc-shared-services, inbound endpoint dns-inbound-use1 at 10.41.0.10 and 10.41.1.10, outbound endpoint dns-outbound-use1 (rslvr-out-use1shared). The protocol-level DNS background is on Task 1.2.
  • eu-central-1: vpc-shared-services-eu, inbound endpoint at 10.45.0.10 and 10.45.1.10; ap-northeast-1 the same pattern at 10.49.0.10 and 10.49.1.10.
  • Rules: rslvr-rr-corpfwd01 (forward corp.example.com), rslvr-rr-corprev01 (forward 100.10.in-addr.arpa), rslvr-rr-awssys01 (system rule for aws.example.com); Profile rp-travel-dns-01.
  • Private zones: aws.example.com (Z0AWSEXAMPLE1234, network account 111111111111) and bookings.aws.example.com (Z0BOOKINGS5678, bookings account).

How it works

Steps marked AWS happen automatically once configured; the others are actions of a client or a server you run.

  1. A data center server looks up an AWS name
  2. Conditional forwarderUS data center DNSA batch server asks 10.100.0.53 for search.bookings.aws.example.com. The server has a conditional forwarder for aws.example.com listing 10.41.0.10, 10.41.1.10 and then the Frankfurt IPs, so it forwards the query over Direct Connect.
  3. Inbound endpointAWSThe query arrives on the endpoint interface 10.41.0.10 in the shared services VPC. The security group allows TCP and UDP 53 (and 443 for DoH) from 10.100.0.0/16 and 10.200.0.0/16.
  4. VPC Resolver of the DNS VPCAWSThe Resolver answers as if the query came from inside vpc-shared-services. DNS Firewall checks the name, the most specific private zone associated with that VPC (bookings.aws.example.com) answers, and the query is logged.
  5. A workload looks up an on-premises name
  6. Query to the VPC ResolverBooking podA pod in the booking VPC asks the VPC +2 address for sql01.corp.example.com. The VPC keeps AmazonProvidedDNS in its DHCP options.
  7. Rule match from the ProfileAWSThe booking VPC is associated with rp-travel-dns-01, which carries the shared rule rslvr-rr-corpfwd01. The most specific matching domain wins, so corp.example.com is forwarded.
  8. Outbound endpointAWSThe Resolver sends the query from the outbound endpoint interfaces in the shared services VPC (in the network account, although the pod is in the bookings account) to 10.100.0.53 or 10.200.0.53 across the Transit Gateway and Direct Connect.
  9. Answer and cacheData center DNSActive Directory DNS answers; the Resolver returns the record to the pod and caches it for its TTL. Cached answers are not logged again.
  10. A public name
  11. Recursive resolutionAWSA query for a partner's public API name matches no forward or system rule, so the built-in recursive rule resolves it on the internet; no endpoint is involved, so there is no endpoint query charge.

Build it

Step 1

One inbound and one outbound endpoint in the DNS VPC

Only the VPC owner can create endpoints, and not in subnets shared from another account, so the DNS VPC belongs to the network account. Each endpoint gets at least two IPs in different Availability Zones; they stay fixed for the endpoint's life, so forwarders can hard-code them.

An endpoint's security group cannot be changed after creation. Inbound allows TCP and UDP 53, plus TCP 443 for DoH, from both data center ranges; outbound allows the same to 10.100.0.53 and 10.200.0.53. Rules that force connection tracking cut inbound capacity (Step 7; Task 2.1).

Inbound and outbound endpoints in the us-east-1 shared services VPC, both accepting DoH (AWS CLI, network account) 
# fixed IPs that the data center forwarders will point at
aws route53resolver create-resolver-endpoint --creator-request-id in-use1-1 \
  --name dns-inbound-use1 --direction INBOUND \
  --security-group-ids sg-dns-inbound \
  --ip-addresses SubnetId=subnet-shared-az1,Ip=10.41.0.10 SubnetId=subnet-shared-az2,Ip=10.41.1.10 \
  --protocols Do53 DoH

# outbound IPs can be picked by the service; Do53 plus DoH lets a rule use either per target
aws route53resolver create-resolver-endpoint --creator-request-id out-use1-1 \
  --name dns-outbound-use1 --direction OUTBOUND \
  --security-group-ids sg-dns-outbound \
  --ip-addresses SubnetId=subnet-shared-az1 SubnetId=subnet-shared-az2 \
  --protocols Do53 DoH

Repeat in eu-central-1 and ap-northeast-1: endpoints, rules and Profiles are all Regional. The Transit Gateway and Direct Connect gateway give each DNS VPC its path to the data centers.

You cannot switch an inbound endpoint straight from Do53 to DoH: enable both, move the forwarders, then remove Do53. DoH-FIPS is inbound only.

Step 2

Forward, reverse and system rules

Each rule is tied to one outbound endpoint and takes up to six target IPs, so each Region has its own copy. The us-east-1 set:

  • Forward corp.example.com to both data center servers, so a US outage still leaves the European one.
  • Forward the reverse zones 100.10.in-addr.arpa and 200.10.in-addr.arpa; a forward rule for a reverse domain overrides the autodefined reverse rule.
  • Forward example.com for legacy hosts that live only in data center DNS, with a system rule for aws.example.com so the VPC Resolver answers that subtree from the private zone. The most specific domain wins.
The rule set for us-east-1 (AWS CLI, network account); the European reverse zone and the example.com rule follow the same shape 
aws route53resolver create-resolver-rule --creator-request-id corp-fwd-1 \
  --name corp-forward --rule-type FORWARD --domain-name corp.example.com \
  --resolver-endpoint-id rslvr-out-use1shared \
  --target-ips "Ip=10.100.0.53" "Ip=10.200.0.53"

aws route53resolver create-resolver-rule --creator-request-id corp-rev-1 \
  --name corp-reverse --rule-type FORWARD --domain-name 100.10.in-addr.arpa \
  --resolver-endpoint-id rslvr-out-use1shared \
  --target-ips "Ip=10.100.0.53" "Ip=10.200.0.53"

# carve the AWS subtree out of the legacy example.com forward rule
aws route53resolver create-resolver-rule --creator-request-id aws-sys-1 \
  --name aws-local --rule-type SYSTEM --domain-name aws.example.com

When the data center servers support DoH, each target can carry its own port, protocol and Server Name Indication; the outbound endpoint must allow DoH (Step 1).

A DoH variant of the corp.example.com rule; the SNI names are this example's on-premises DoH servers (AWS CLI) 
aws route53resolver create-resolver-rule --creator-request-id corp-fwd-doh-1 \
  --name corp-forward-doh --rule-type FORWARD --domain-name corp.example.com \
  --resolver-endpoint-id rslvr-out-use1shared \
  --target-ips "Ip=10.100.0.53,Port=443,Protocol=DoH,ServerNameIndication=dns1.corp.example.com" "Ip=10.200.0.53,Port=443,Protocol=DoH,ServerNameIndication=dns2.corp.example.com"

Delegation instead of forwarding (June 2025): a DELEGATE rule (with --delegation-record and no target IPs) makes the Resolver follow NS referrals from a private zone to on-premises name servers, and an INBOUND_DELEGATION endpoint (Do53 only) can be the name server for a subdomain that on-premises DNS delegates. The company keeps forwarders, which its Active Directory team already manages (Task 2.3).

Step 3

Private zones the inbound endpoint can answer

An inbound endpoint answers only from private zones associated with the VPC that holds it. A zone associated only with the bookings VPC is invisible to the data centers, so every zone on premises needs is associated with the DNS VPC in each Region. Private zones are global, so one zone can serve all three.

The network account creates aws.example.com with the DNS VPCs (Task 2.3). The bookings account owns bookings.aws.example.com so it manages its own records; across accounts, the zone owner authorizes the VPC and the VPC owner associates it (CLI or API only).

Let the network account's DNS VPC see the bookings zone, in every Region with an inbound endpoint (AWS CLI) 
# bookings account (zone owner): authorize the DNS VPCs
aws route53 create-vpc-association-authorization --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services
aws route53 create-vpc-association-authorization --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=eu-central-1,VPCId=vpc-shared-services-eu

# network account (VPC owner): associate them
aws route53 associate-vpc-with-hosted-zone --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services
aws route53 associate-vpc-with-hosted-zone --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=eu-central-1,VPCId=vpc-shared-services-eu

# bookings account: tidy up; the associations stay
aws route53 delete-vpc-association-authorization --hosted-zone-id Z0BOOKINGS5678 \
  --vpc VPCRegion=us-east-1,VPCId=vpc-shared-services

enableDnsSupport and enableDnsHostnames must be true in every VPC that uses the zones. The account pipeline runs the authorization for each new team zone.

Overlapping zones are fine, and the most specific answers. But a name only in the parent aws.example.com zone, under bookings.aws.example.com, returns NXDOMAIN, not a fallback.

Step 4

A Route 53 Profile for every VPC

Without Profiles, every account associates every shared rule with every VPC and each zone needs a per-VPC authorization: over a thousand associations for 300 VPCs, and a zone stops at 300 VPCs. A Profile bundles private zones, rules, DNS Firewall rule groups, interface endpoints and query logging; it is shared through RAM within a Region and needs one association per VPC. Changes reach every VPC.

Build the us-east-1 Profile and put the zones and rules in it (AWS CLI, network account) 
aws route53profiles create-profile --name travel-dns-use1

# the private zone for AWS workloads
aws route53profiles associate-resource-to-profile \
  --profile-id rp-travel-dns-01 --name aws-example-com \
  --resource-arn arn:aws:route53:::hostedzone/Z0AWSEXAMPLE1234

# the forward and system rules from Step 2
aws route53profiles associate-resource-to-profile \
  --profile-id rp-travel-dns-01 --name corp-forward \
  --resource-arn arn:aws:route53resolver:us-east-1:111111111111:resolver-rule/rslvr-rr-corpfwd01
aws route53profiles associate-resource-to-profile \
  --profile-id rp-travel-dns-01 --name aws-local \
  --resource-arn arn:aws:route53resolver:us-east-1:111111111111:resolver-rule/rslvr-rr-awssys01

The RAM share on Task 2.3 shares rp-travel-dns-01 with the organization; the VPC template then associates it.

The bookings account attaches the shared Profile to its production VPC (AWS CLI) 
aws route53profiles associate-profile \
  --profile-id rp-travel-dns-01 \
  --resource-id vpc-bookings-prod \
  --name bookings-prod-dns

A VPC can carry up to two Profiles, each with a priority from 100 to 9900 (lower wins). Payment VPCs in PCI DSS scope add travel-dns-pci with a stricter firewall group at a lower number. For rules and zones the Resolver uses the first Profile with a match, ignoring later ones, then compares it with local VPC settings; for the same domain the local setting wins. Queries are logged to every associated Profile's configurations.

Profiles distribute rules; they do not create endpoints. Forwarded queries still use the outbound endpoint, so capacity and query charges are unchanged.

Step 5

Data center forwarders, loop avoidance and the second Region

Data center DNS servers forward aws.example.com to inbound endpoint IPs, never to the VPC +2 address (unsupported from outside the VPC), listing the nearest Region first and a second Region after it.

US data center forwarders: us-east-1 first, eu-central-1 as fallback (Windows DNS PowerShell and BIND) 
# Windows DNS, replicated to every domain controller in the forest
Add-DnsServerConditionalForwarderZone -Name "aws.example.com" `
  -MasterServers 10.41.0.10,10.41.1.10,10.45.0.10,10.45.1.10 -ReplicationScope Forest

# BIND named.conf on the non-Windows resolvers
zone "aws.example.com" {
  type forward;
  forward only;
  forwarders { 10.41.0.10; 10.41.1.10; 10.45.0.10; 10.45.1.10; };
};

The European data center lists Frankfurt first. Inbound load balancing is up to the client, so a forwarder that always uses the first IP makes a hot spot; watch per-IP InboundQueryVolume. How fast a forwarder moves to the next IP depends on the DNS software (see the high-availability blog below). Fallback only works because Step 3 associated every zone with each Region's DNS VPC; otherwise Frankfurt returns NXDOMAIN, which forwarders cache rather than retry.

Loop avoidance. AWS advises never associating a forward rule with the VPC holding the inbound endpoint that rule can reach, directly or through on-premises DNS. If vpc-shared-services had the example.com rule and data center DNS sent an example.com name back to the inbound endpoint, the query would bounce between the endpoints. So the DNS VPCs do not get the Profile: zones by direct association, no forward rules. Directory tooling that needs corp.example.com sits in vpc-shared-ad, which does.

To let on-premises clients use central interface endpoints by their normal names, also forward those service names (for example s3.us-east-1.amazonaws.com) to the inbound endpoint.

Step 6

DNS Firewall and query logging in the Profile

DNS Firewall matches query names against domain lists in rule groups. The baseline group blocks an AWS managed malware list and DNS tunneling (an exfiltration path for card data). New block rules run as ALERT first.

A rule group with a managed-list block and a tunneling detector, added to the Profile with priority 200 (AWS CLI, network account) 
aws route53resolver create-firewall-rule-group --creator-request-id frg-use1-1 \
  --name travel-dns-baseline

# the domain list ID is the AWS managed malware list in this Region
aws route53resolver create-firewall-rule --name block-malware \
  --firewall-rule-group-id rslvr-frg-0travelbase1 \
  --firewall-domain-list-id rslvr-fdl-0awsmalware1 \
  --priority 100 --action BLOCK --block-response NXDOMAIN

# DNS Firewall Advanced: ALLOW is not available, a confidence threshold is required
aws route53resolver create-firewall-rule --name block-tunneling \
  --firewall-rule-group-id rslvr-frg-0travelbase1 \
  --dns-threat-protection DNS_TUNNELING --confidence-threshold MEDIUM \
  --priority 200 --action BLOCK --block-response NXDOMAIN

aws route53profiles associate-resource-to-profile \
  --profile-id rp-travel-dns-01 --name dns-firewall-baseline \
  --resource-arn arn:aws:route53resolver:us-east-1:111111111111:firewall-rule-group/rslvr-frg-0travelbase1 \
  --resource-properties "{\"priority\": 200}"

DNS Firewall fails closed by default (SERVFAIL when it cannot evaluate a query). The company keeps that: a DNS outage is visible, exfiltration is silent. The fail mode can be set on the Profile, so it is one setting, not 300. Data center queries through the inbound endpoint are filtered by groups associated with the DNS VPC, so the baseline group is also associated directly there. Clients using their own DNS servers bypass DNS Firewall.

Resolver query logs cover VPC queries, inbound and outbound endpoint queries and firewall actions. A configuration serves VPCs in its own Region, so there is one per Region, each writing to a log archive account bucket (cross-account needs a bucket policy for delivery.logs.amazonaws.com); AWS recommends S3 for high query rates.

One logging configuration per Region, delivered to the log archive bucket and carried by the Profile (AWS CLI, network account) 
aws route53resolver create-resolver-query-log-config --creator-request-id qlog-use1-1 \
  --name dns-query-logs-use1 \
  --destination-arn arn:aws:s3:::travel-dns-query-logs-use1

# every VPC with the Profile logs here
aws route53profiles associate-resource-to-profile \
  --profile-id rp-travel-dns-01 --name dns-query-logs \
  --resource-arn arn:aws:route53resolver:us-east-1:111111111111:resolver-query-log-config/rqlc-0use1central123

# the DNS VPC has no Profile, so associate it directly to capture on-premises queries
aws route53resolver associate-resolver-query-log-config \
  --resolver-query-log-config-id rqlc-0use1central123 \
  --resource-id vpc-shared-services

Cached answers are not logged, DoH inbound queries show the wrong source IP (a known issue), and CloudWatch vended-log charges apply even for S3.

Step 7

Capacity, alarms and adding interfaces

Each endpoint IP handles about 10,000 UDP queries per second, but an inbound interface can drop to about 1,500 with connection tracking or behind an NLB. Add interfaces when any one passes 50%. ResolverEndpointCapacityStatus (June 2025) reports 0 OK, 1 above 50%, 2 above 75%, and accounts for latency, protocol, packet size and tracking, so it beats a raw query count.

Alarm when any inbound interface passes 50%, ignoring maintenance gaps (AWS CLI, us-east-1) 
# Maximum is the valid statistic; data arrives every 5 minutes
aws cloudwatch put-metric-alarm \
  --alarm-name dns-inbound-use1-capacity \
  --namespace AWS/Route53Resolver --metric-name ResolverEndpointCapacityStatus \
  --dimensions Name=EndpointId,Value=rslvr-in-use1shared \
  --statistic Maximum --period 300 --evaluation-periods 2 \
  --threshold 1 --comparison-operator GreaterThanOrEqualToThreshold \
  --treat-missing-data ignore \
  --alarm-actions arn:aws:sns:us-east-1:111111111111:network-oncall

Missing data is ignored because the metric has gaps during interface maintenance. On an inbound alarm, look for a hot spot first; on an outbound alarm, check the target servers, since slow ones fill interfaces that more interfaces will not fix. Real growth gets a new interface.

Add a third inbound IP in another AZ (AWS CLI); one call per address, then add it to the forwarders 
aws route53resolver associate-resolver-endpoint-ip-address \
  --resolver-endpoint-id rslvr-in-use1shared \
  --ip-address SubnetId=subnet-shared-az3,Ip=10.41.2.10

Also alarm on EndpointHealthyENICount below the IP count. Opt-in detailed metrics (December 2025) add per-interface P90 latency and error counts, and per-target latency outbound.

Design decisions

Centralized endpoints in the network account

Two endpoints per Region serve every account: 12 IPs instead of endpoints in 300 VPCs, and one team owns forwarders, rules and capacity. The cost is a shared dependency, and spoke queries cross the Transit Gateway. Distributed endpoints suit isolated units without Transit Gateway access (Task 2.3).

Profiles rather than per-VPC associations

One association per VPC replaces per-rule associations and per-zone authorizations and lifts the 300-VPCs-per-zone ceiling (a Profile serves 1,000 VPCs, 5,000 zones, 1,000 rules). RAM-shared rules remain the tool for a VPC needing an exception, since a local rule wins for the same domain. Three Regional Profiles are kept identical by infrastructure as code.

Zones associated directly with the DNS VPC

The DNS VPC holds zones by direct association, not through the Profile, so that it never inherits forward rules (the loop rule in Step 5). The cost is one authorization per team zone per Region, automated in the account pipeline.

Fail closed for DNS Firewall

Fail closed favours security, fail open availability. A unit without sensitive data could use a fail-open Profile; the highest-priority Profile that sets the value applies.

DNS over HTTPS on the hybrid path

AWS says encrypting DNS inside a VPC is not needed; DoH matters where DNS crosses Direct Connect. That path is already encrypted (Encrypted hybrid connectivity), so DoH is adopted as data center servers gain support, keeping Do53 until every forwarder has moved.

Cost

Endpoints cost $0.125 per IP address per hour plus $0.40 per million queries through them. Two endpoints with two IPs each in three Regions is 12 × $0.125 × 730 ≈ $1,095 a month; a third us-east-1 inbound IP adds about $91. If the endpoints carry 1.5 billion queries a month, that is 1,500 × $0.40 = $600. Queries to private zones from VPCs and recursive public lookups need no endpoint, which is why the design forwards only what must leave AWS. Detail: Task 3.3.

Quotas to plan for

  • 4 endpoints per Region per account (adjustable), 6 target IPs per rule, 1,000 rules and 2,000 rule-to-VPC associations per Region.
  • 5 Profiles per account per Region (adjustable), 2 Profiles per VPC, 5 DNS Firewall rule groups per Profile, 2 query logging configurations per Profile.
  • 5 DNS Firewall rule groups per VPC, 100 rules per group; 20 query logging configurations per Region.
  • Resolver API at 5 requests per second per account per Region, which matters when automation associates hundreds of VPCs: add retries with backoff.

Alternatives

RAM-shared rules and zone authorizations without Profiles

The pre-2024 pattern still works, but every account associates every rule with every VPC, an account moved to an OU outside the share silently loses its associations, and zones stop at 300 VPCs.

Self-managed DNS servers on EC2

BIND or Windows servers in the DNS VPC forwarding AWS zones to the VPC +2 address. You patch, scale and make them highly available, and instances using them through DHCP options bypass DNS Firewall and Resolver query logging.

Delegation instead of conditional forwarders

Inbound delegation endpoints let data center DNS delegate aws.example.com with NS records instead of maintaining forwarders on every server, and DELEGATE rules follow referrals the other way. Fewer forwarder entries to keep in sync, but Do53 only on the inbound side.

Route 53 Global Resolver (outside the exam guide)

An internet-reachable anycast resolver for sites, branches and remote clients, resolving private zone and public names over Do53, DoH or DoT with token or IP allowlist authentication. It is newer than the ANS-C01 outline, so treat it as background only.

Testing it

  1. Resolve AWS names from each data centerFrom a US server, dig @10.41.0.10 search.bookings.aws.example.com and the same against 10.41.1.10, 10.45.0.10 and 10.45.1.10 should return the same answer; any NXDOMAIN from Frankfurt means a zone is missing its association with vpc-shared-services-eu.
  2. Resolve on-premises names from a spokeFrom a booking instance, dig sql01.corp.example.com and a PTR lookup for 10.100.20.5 should succeed, and the query log should show the query leaving through rslvr-out-use1shared. A spoke that fails while the shared services VPC works usually has no Profile association.
  3. Fail over the forwardersIn a maintenance window, block 10.41.0.0/16 on port 53 for one test DNS server in the US data center. Lookups should continue through Frankfurt, and its InboundQueryVolume should rise.
  4. Prove there is no loopQuery a legacy example.com name at the inbound endpoint; the query log should show one query, not a chain between the endpoints.
  5. Test DNS FirewallAdd a test domain to a custom list with ALERT, check the log, switch to BLOCK and confirm NXDOMAIN from a spoke and through the inbound endpoint.
  6. Load test capacityReplay peak query rates from a test forwarder; the Step 7 alarm should fire before timeouts appear.

Troubleshooting checklist. NXDOMAIN inside the VPC for a name that resolves on the internet usually means a private zone with the same name or a parent (split-view) matches but lacks that record: there is no fallback to the public zone. A name forwarded when it should be local, or local when it should be forwarded, is rule precedence: the most specific rule wins, a rule beats a private zone for the same name, and a local VPC rule beats the Profile. Intermittent failures from one busy EKS node, with no endpoint involved, often mean the 1,024 packets per second per interface limit to link-local services (DNS, metadata and time sync together, not adjustable); the ENA counter linklocal_allowance_exceeded confirms it, and caching DNS on the node fixes it.

"On-premises servers cannot resolve records in a private hosted zone, and workloads in many accounts must resolve the on-premises Active Directory domain, with the least operational overhead" is Resolver inbound and outbound endpoints in a central VPC, the private zones associated with that VPC, on-premises conditional forwarders to the inbound endpoint IPs, and the forwarding rules distributed with a Route 53 Profile shared through RAM. If an option forwards on-premises queries to the VPC +2 address, or associates the forward rule with the VPC that holds the inbound endpoint, it is wrong.
