Reference architecture

Inbound perimeter: CloudFront, WAF, ALB and inspection

Travellers all over the world search fares and book trips on the travel company's site and API. Every one of those requests now enters through Amazon CloudFront, is filtered by AWS WAF at the edge, is covered by AWS Shield Advanced, and reaches a load balancer that the internet cannot reach directly. Partners that need raw TCP enter through Global Accelerator instead, and everything is logged where the security team can find it.

Scenario and requirements

The travel company (example.com) runs its booking platform on Amazon EKS in the booking account 222222222222, in the production booking VPC 10.40.8.0/21 in us-east-1 (with the same build in 10.44.8.0/21 in eu-central-1). An Application Load Balancer (ALB) fronts the pods. The site www.example.com and the API api.example.com serve travellers on every continent, and the login and checkout pages attract credential-stuffing bots and holiday-sale floods. Card data flows behind the platform, so the path is in PCI DSS scope.

The network account 111111111111 already runs the Transit Gateway hub and the GWLB inspection fleet; this page adds the edge.

The booking VPC gets three private subnets for the internal ALB, one per AZ: 10.40.9.0/26, 10.40.9.64/26 and 10.40.9.128/26. The partner API VPC 10.40.56.0/22 and its internet-facing NLB are the ones from the GWLB page.

How it works

A request passes three layers: the CloudFront edge (TLS, caching, WAF, Shield), the origin path, and the ALB. Each removes a class of attack.

  1. A traveller in Tokyo searches for flights
  2. DNS answerAWSThe resolver asks Route 53 for www.example.com. An alias record returns CloudFront addresses near the traveller.
  3. TLS at the edgeAWSThe browser connects to a Tokyo edge location over TCP 443. CloudFront presents the ACM certificate and negotiates TLS 1.2 or 1.3; Shield absorbs SYN floods and other layer 3 and 4 attacks here.
  4. WAF evaluates the requestAWSThe web ACL runs its rules in priority order (Step 3). A blocked request gets a 403 from the edge and never reaches the origin.
  5. Cache or originAWSStatic pages, images and scripts are served from cache. A fare search under /api/* is not cacheable, so CloudFront opens (or reuses) an HTTPS connection to the origin.
  6. VPC origin into the private subnetAWSCloudFront reaches the internal ALB through a service-managed ENI in the ALB's private subnet. There is no public address to attack.
  7. ALB to the podsAWSThe ALB terminates TLS and forwards to the EKS pod IP target group; the pod sees the traveller's address in X-Forwarded-For.
  8. A partner sends a booking feed over TCP
  9. Static anycast IPsAWSThe partner connects to a Global Accelerator static IP; the nearest edge carries the TCP connection over the AWS backbone to us-east-1.
  10. NLB with client IP preservedAWSThe NLB sees the partner's real source address, and its security group allows only partner ranges. TLS passes through to the targets.

Build it

Step 1

The distribution, its certificate and a VPC origin

CloudFront accepts viewer certificates only from ACM in us-east-1, whatever Region the origin is in. The ALB keeps its own certificate in its Region (an ELB origin's certificate can come from any Region). The viewer protocol policy is redirect-to-https and the security policy is TLSv1.2_2025, which allows TLS 1.2 and 1.3 and drops CHACHA20 and the SHA224 signature schemes.

A VPC origin (November 2024) lets CloudFront reach an ALB, an NLB or an EC2 instance in a private subnet. CloudFront creates a service-managed ENI in that subnet and a security group named CloudFront-VPCOrigins-Service-SG. There is no extra charge, and origin fetches from AWS origins are free. Prerequisites: the VPC must still have an internet gateway attached (it is not used for routing the traffic), the subnet needs a free IPv4 address (and an IPv6 one for dual-stack), and deployment takes up to 15 minutes. GWLBs, NLBs with TLS listeners and NLBs without a security group cannot be VPC origins.

VPC origin for the internal booking ALB (CloudFormation YAML, booking account) 
BookingVpcOrigin:
  Type: AWS::CloudFront::VpcOrigin
  Properties:
    VpcOriginEndpointConfig:
      Name: booking-alb-use1
      # the internal ALB in the three private /26 subnets of 10.40.8.0/21
      Arn: arn:aws:elasticloadbalancing:us-east-1:222222222222:loadbalancer/app/booking-alb-use1/ALB_ID
      HTTPSPort: 443
      # CloudFront to ALB is encrypted too, which PCI DSS expects across the whole path
      OriginProtocolPolicy: https-only
      OriginSSLProtocols:
        - TLSv1.2
The distribution's origin, default behavior and viewer certificate (CloudFormation YAML, created in us-east-1) 
BookingDistribution:
  Type: AWS::CloudFront::Distribution
  Properties:
    DistributionConfig:
      Enabled: true
      Aliases:
        - www.example.com
        - api.example.com
      # global web ACL from Step 3 (scope CLOUDFRONT, created in us-east-1)
      WebACLId: arn:aws:wafv2:us-east-1:222222222222:global/webacl/booking-edge/WEBACL_ID
      Origins:
        - Id: booking-alb-use1
          # the origin domain is the ALB's DNS name; the ALB certificate must cover it or the forwarded Host
          DomainName: internal-booking-alb-use1-ALB_DNS.us-east-1.elb.amazonaws.com
          VpcOriginConfig:
            VpcOriginId: !GetAtt BookingVpcOrigin.Id
      DefaultCacheBehavior:
        TargetOriginId: booking-alb-use1
        ViewerProtocolPolicy: redirect-to-https
        # AWS managed CachingOptimized policy for static content; /api/* gets a no-cache behavior
        CachePolicyId: 658327ea-f89d-4fab-a63d-7e88639e58f6
      ViewerCertificate:
        AcmCertificateArn: arn:aws:acm:us-east-1:222222222222:certificate/CERT_ID
        SslSupportMethod: sni-only
        MinimumProtocolVersion: TLSv1.2_2025

On the ALB side, the security group allows TCP 443 only from CloudFront-VPCOrigins-Service-SG. That is tighter than the CloudFront prefix list, which admits every customer's distributions. Inbound network ACL rules are not evaluated for this traffic, but outbound rules are, so the subnet NACL must allow responses to ephemeral ports 1024-65535; and Lambda@Edge origin request and response triggers and gRPC are not supported on a VPC origin.

"Origin protocol policy https-only" protects CloudFront to origin; "viewer protocol policy redirect-to-https" protects viewer to CloudFront. A question about end-to-end encryption needs both. And a certificate requested in eu-central-1 cannot be attached to the distribution, even if the origin is in Frankfurt.

Step 2

The alternative origin: a public ALB locked to CloudFront

Teams that still need a Lambda@Edge origin trigger keep a public ALB with two locks. The first: the ALB security group allows TCP 443 only from the AWS managed prefix list com.amazonaws.global.cloudfront.origin-facing (and com.amazonaws.global.ipv6.cloudfront.origin-facing for IPv6). That list has a weight of 55: one rule that references it counts as 55 of the default 60 rules per security group, leaving room for only five more.

The prefix list admits every customer's distributions, including an attacker's, so the second lock is that CloudFront adds a secret custom origin header that only the company's distribution knows, and the ALB forwards only requests that carry it. The default action becomes a fixed 403.

Security group limited to CloudFront, and an ALB rule that requires the secret header (AWS CLI, booking account) 
# find this Region's ID for the CloudFront origin-facing list
aws ec2 describe-managed-prefix-lists --region us-east-1 \
  --filters Name=prefix-list-name,Values=com.amazonaws.global.cloudfront.origin-facing

# one rule, weight 55 of the 60 rules a security group allows by default
aws ec2 authorize-security-group-ingress --group-id sg-0bookingalb \
  --ip-permissions 'IpProtocol=tcp,FromPort=443,ToPort=443,PrefixListIds=[{PrefixListId=PREFIX_LIST_ID,Description=cloudfront-origin-facing}]'

# forward only requests carrying the header CloudFront adds; the default action returns 403
aws elbv2 create-rule --listener-arn LISTENER_ARN --priority 1 \
  --conditions 'Field=http-header,HttpHeaderConfig={HttpHeaderName=X-Origin-Verify,Values=[HEADER_SECRET]}' \
  --actions Type=forward,TargetGroupArn=TG_ARN
aws elbv2 modify-listener --listener-arn LISTENER_ARN \
  --default-actions 'Type=fixed-response,FixedResponseConfig={StatusCode=403,ContentType=text/plain,MessageBody=Access denied}'

In the distribution, the header goes into the origin's OriginCustomHeaders (up to 30 per origin). Rotate it with an overlap of two accepted values.

A public ALB also collides with VPC Block Public Access. In bidirectional mode, internet-facing ALBs stop receiving traffic, so the ALB's public subnets need exclusions. Exclude all of the load balancer's subnets: AWS warns that excluding only one subnet still lets the ALB accept public traffic there and route it privately to targets in the others.

Exclude the public ALB subnets from Block Public Access; repeat for each AZ (AWS CLI, booking account) 
aws ec2 create-vpc-block-public-access-exclusion --region us-east-1 \
  --subnet-id subnet-0bookingpub1a --internet-gateway-exclusion-mode allow-bidirectional

# the exclusion should show as active before Block Public Access is enforced
aws ec2 describe-vpc-block-public-access-exclusions --region us-east-1

The VPC documentation lists CloudFront VPC origins among the traffic that Block Public Access blocks, alongside internet-facing ALBs and Global Accelerator. So the VPC origin design is not automatically exempt: if Block Public Access is enforced in the booking account, the ALB's private subnets need exclusions too. Create them before turning it on; the subnet still has no public address.

Step 3

The WAF web ACL on CloudFront

A web ACL for CloudFront has the global scope (--scope CLOUDFRONT) and must be created in us-east-1; its IP sets, regex sets and rule groups must be there too, and a CloudFront web ACL cannot also be associated with regional resources. At CloudFront the body inspection limit is 16 KB by default (configurable to 64 KB at extra cost) against a fixed 8 KB on an ALB.

The rule order:

  1. Anti-DDoS managed rule group (priority 0)AWSManagedRulesAntiDDoSRuleSet (June 2025, 50 WCU) baselines normal traffic within about 15 minutes, then detects HTTP floods in seconds and challenges or blocks suspicious requests. Since March 26, 2026 it is the default layer 7 flood protection, superseding Shield Advanced's automatic application layer mitigation. Run it first (the console adds it at the bottom); only GET requests can be challenged.
  2. Amazon IP reputation listAWSManagedRulesAmazonIpReputationList (25 WCU) blocks addresses Amazon threat intelligence has seen attacking or scanning.
  3. Core rule setAWSManagedRulesCommonRuleSet (700 WCU) covers XSS, file inclusion and metadata SSRF. Its SizeRestrictions_BODY rule blocks bodies larger than 8 KB, which breaks the passport scan upload on the booking page. The company overrides that rule to Count and adds its own size rule excluding the upload path.
  4. Known bad inputsAWSManagedRulesKnownBadInputsRuleSet (200 WCU) blocks Log4j and Java deserialization exploits.
  5. Account takeover prevention on the loginAWSManagedRulesATPRuleSet inspects POST requests to /api/login for stolen credentials and, on CloudFront only, login responses to count failures. Bot Control fits fare scraping instead; both are paid.
  6. Rate-based rulesA per-IP limit for the whole site and a much lower one for the login path.
Create the global web ACL (AWS CLI, booking account, us-east-1) 
aws wafv2 create-web-acl --region us-east-1 --scope CLOUDFRONT \
  --name booking-edge --default-action Allow={} \
  --visibility-config SampledRequestsEnabled=true,CloudWatchMetricsEnabled=true,MetricName=booking-edge \
  --rules file://booking-edge-rules.json
booking-edge-rules.json, abridged: Anti-DDoS, core rules with the body-size override, ATP on the login, and a login rate limit (the IP reputation, bad inputs and per-IP rules follow the same pattern) 
[
  {"Name": "anti-ddos", "Priority": 0,
   "Statement": {"ManagedRuleGroupStatement": {"VendorName": "AWS", "Name": "AWSManagedRulesAntiDDoSRuleSet"}},
   "OverrideAction": {"None": {}},
   "VisibilityConfig": {"SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "anti-ddos"}},
  {"Name": "core", "Priority": 2,
   "Statement": {"ManagedRuleGroupStatement": {"VendorName": "AWS", "Name": "AWSManagedRulesCommonRuleSet",
     "RuleActionOverrides": [{"Name": "SizeRestrictions_BODY", "ActionToUse": {"Count": {}}}]}},
   "OverrideAction": {"None": {}},
   "VisibilityConfig": {"SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "core"}},
  {"Name": "atp-login", "Priority": 4,
   "Statement": {"ManagedRuleGroupStatement": {"VendorName": "AWS", "Name": "AWSManagedRulesATPRuleSet",
     "ManagedRuleGroupConfigs": [{"AWSManagedRulesATPRuleSet": {"LoginPath": "/api/login",
       "RequestInspection": {"PayloadType": "JSON",
         "UsernameField": {"Identifier": "/email"}, "PasswordField": {"Identifier": "/password"}}}}]}},
   "OverrideAction": {"Count": {}},
   "VisibilityConfig": {"SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "atp-login"}},
  {"Name": "login-rate", "Priority": 6,
   "Statement": {"RateBasedStatement": {"Limit": 20, "EvaluationWindowSec": 60, "AggregateKeyType": "IP",
     "ScopeDownStatement": {"ByteMatchStatement": {"SearchString": "/api/login", "FieldToMatch": {"UriPath": {}},
       "TextTransformations": [{"Priority": 0, "Type": "LOWERCASE"}], "PositionalConstraint": "STARTS_WITH"}}}},
   "Action": {"Block": {}},
   "VisibilityConfig": {"SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "login-rate"}}
]

Rate-based rules take a limit from 10 to 2,000,000,000 requests per evaluation window of 60, 120, 300 (default) or 600 seconds. The aggregation key can be the source IP, a forwarded IP header, everything (with a scope-down), or up to five custom keys such as a header, cookie, query argument, URI path, JA3 or JA4 fingerprint, label namespace or ASN. An API rule keyed on the API key header plus IP stops one agency using up the limit for others behind its NAT. Rate-based rules can use any action except Allow, and a blocking rate-based rule is one of the prerequisites for Shield Advanced cost protection.

Count first, then Block. The ATP group above is deployed with the override set to Count. After a week of reading WAF logs and fixing false positives, the override changes to None so the group's Block actions apply.

Capacity and cost: the base price includes 1,500 WCU per web ACL (the core rule set alone is 700), up to 5,000 at extra cost. The web ACL is $5 per month plus $1 per rule and $0.60 per million requests; ATP and Bot Control cost extra.

Step 4

Shield Advanced protections, health checks and cost protection

Shield Standard protects CloudFront, Route 53 and Global Accelerator against layer 3 and 4 attacks at no charge. The company adds Shield Advanced ($3,000 per month for the organization's payer account, one-year commitment, plus data transfer usage fees) for the Shield Response Team, proactive engagement, attack metrics, health-based detection and cost protection; it also covers WAF fees for protected resources up to 1,500 WCU.

Protections are not automatic: each resource must be added, here or through a Firewall Manager policy. The company protects the CloudFront distribution, the example.com hosted zone and the partner accelerator. An ALB that only receives CloudFront traffic needs no separate protection.

Subscribe and protect the three edge resources (AWS CLI, booking account) 
aws shield create-subscription

aws shield create-protection --name booking-cloudfront \
  --resource-arn arn:aws:cloudfront::222222222222:distribution/DIST_ID
aws shield create-protection --name example-com-zone \
  --resource-arn arn:aws:route53:::hostedzone/ZONE_ID
aws shield create-protection --name partner-accelerator \
  --resource-arn arn:aws:globalaccelerator::222222222222:accelerator/ACCELERATOR_ID

With proactive engagement the Shield Response Team calls the company when a protected resource is attacked and its health check fails. It needs Business or Enterprise Support, WAF v2 web ACLs, one to ten emergency contacts and a Route 53 health check associated with each protected resource. It is not triggered by events the Anti-DDoS managed rule group detects.

A health check on the booking API, associated with the CloudFront protection, and proactive engagement (AWS CLI) 
# checks the real user path through CloudFront
aws route53 create-health-check --caller-reference booking-edge-1 \
  --health-check-config Type=HTTPS,FullyQualifiedDomainName=api.example.com,Port=443,ResourcePath=/health,RequestInterval=30,FailureThreshold=3

aws shield associate-health-check --protection-id PROTECTION_ID \
  --health-check-arn arn:aws:route53:::healthcheck/HEALTH_CHECK_ID

aws shield associate-proactive-engagement-details \
  --emergency-contact-list EmailAddress=soc@example.com,PhoneNumber=+15555550100
aws shield enable-proactive-engagement

Cost protection returns Shield Advanced service credits for charges an attack causes: CloudFront requests and data transfer, Route 53 queries, Global Accelerator data transfer, ALB LCUs, and EKS nodes that Auto Scaling added during the attack. The prerequisites are what the exam tests: the resource was protected before the attack; for CloudFront and ALB, its web ACL has a rate-based rule in Block mode (Count is not enough); the DDoS best practices were followed; and the request is made within 15 days after the billing month, in a billing case with "DDoS Concession" in the subject.

Step 5

Partner TCP traffic through Global Accelerator to an NLB

Some airline partners push feeds over TLS on TCP 443 that they terminate themselves, to fixed addresses. CloudFront is for HTTP, so this traffic goes through Global Accelerator: two static anycast IPs and failover in seconds without DNS caching. The full edge comparison is on the global edge architecture page.

Accelerator, TCP listener and endpoint group with the partner NLB (AWS CLI; the Global Accelerator API is in us-west-2) 
aws globalaccelerator create-accelerator --name partner-feed --ip-address-type IPV4 --region us-west-2

aws globalaccelerator create-listener --accelerator-arn ACCELERATOR_ARN \
  --protocol TCP --port-ranges FromPort=443,ToPort=443 --client-affinity SOURCE_IP --region us-west-2

# the NLB must have a security group for client IP preservation
aws globalaccelerator create-endpoint-group --listener-arn LISTENER_ARN \
  --endpoint-group-region us-east-1 \
  --endpoint-configurations EndpointId=NLB_ARN,Weight=128,ClientIPPreservationEnabled=true \
  --region us-west-2

Client IP preservation has a side effect: traffic with the client IP preserved bypasses GWLB inspection, Network Firewall and network ACLs, because it does not enter through the internet gateway that the ingress routing on the GWLB page depends on. Partners on the NLB's Elastic IPs are still inspected; accelerator partners rely on the security group and TLS client authentication. Partners who need IPS stay on the Elastic IP path.

Global Accelerator inbound traffic is also blocked by VPC Block Public Access, so the partner VPC's NLB subnets need exclusions if the partner account enforces it.

For optional IDS/IPS on inbound HTTP as well, the company can put a perimeter VPC with GWLB endpoints or Network Firewall endpoints between the internet gateway and a public ALB, using a gateway route table. That design is built on the GWLB inspection page; with Block Public Access, the workload (ALB) subnet is excluded, not the appliance subnet.

Step 6

Logging and alarms

The regional rules for global services are the trap. A CloudFront web ACL lives in us-east-1, so its log destination must too. The company streams WAF logs to an Amazon Data Firehose stream whose name starts with aws-waf-logs-, created in us-east-1 in the same account as the web ACL, with Direct PUT as its source (not a Kinesis data stream). One WAF log is one Firehose record, so size the stream for the request rate.

WAF logs to Firehose (AWS CLI, booking account, us-east-1) 
aws wafv2 put-logging-configuration --region us-east-1 --logging-configuration \
  ResourceArn=arn:aws:wafv2:us-east-1:222222222222:global/webacl/booking-edge/WEBACL_ID,LogDestinationConfigs=arn:aws:firehose:us-east-1:222222222222:deliverystream/aws-waf-logs-booking-edge

CloudFront standard logs v2 (November 2024) are vended logs delivered to CloudWatch Logs, Firehose or S3 (with Parquet output to S3 at extra CloudWatch cost) and configured in us-east-1; CloudFront does not charge for them. Real-time logs go only to a Kinesis data stream, within seconds, with a sampling rate of 1 to 100 percent and a configuration attached per cache behavior. The SOC samples 10 percent of /api/*.

Standard logs v2 to S3 as Parquet, and a sampled real-time log for the API (AWS CLI, us-east-1) 
aws logs put-delivery-source --region us-east-1 --name booking-cf \
  --resource-arn arn:aws:cloudfront::222222222222:distribution/DIST_ID --log-type ACCESS_LOGS
aws logs put-delivery-destination --region us-east-1 --name booking-cf-s3 --output-format parquet \
  --delivery-destination-configuration destinationResourceArn=arn:aws:s3:::example-edge-logs
aws logs create-delivery --region us-east-1 --delivery-source-name booking-cf \
  --delivery-destination-arn DELIVERY_DESTINATION_ARN

# then set RealtimeLogConfigArn on the /api/* cache behavior
aws cloudfront create-realtime-log-config --name booking-api-rt --sampling-rate 10 \
  --fields timestamp c-ip x-forwarded-for sc-status cs-uri-stem x-edge-request-id asn c-country \
  --end-points 'StreamType=Kinesis,KinesisStreamConfig={RoleARN=KINESIS_ROLE_ARN,StreamARN=KINESIS_STREAM_ARN}'

ALB access logs are off by default. They go to an S3 bucket in the same Region as the ALB, encrypted with SSE-S3 only (no SSE-KMS). The x-edge-request-id in CloudFront logs equals the X-Amz-Cf-Id header, which the application can log, so one booking can be traced from edge to pod.

ALB access logs, and an alarm on any DDoS event against the distribution (AWS CLI) 
aws elbv2 modify-load-balancer-attributes --region us-east-1 --load-balancer-arn ALB_ARN \
  --attributes Key=access_logs.s3.enabled,Value=true Key=access_logs.s3.bucket,Value=example-alb-logs-use1 Key=access_logs.s3.prefix,Value=booking

# Shield metrics for CloudFront, Route 53 and protection groups exist only in us-east-1
aws cloudwatch put-metric-alarm --region us-east-1 \
  --alarm-name booking-ddos-detected \
  --namespace AWS/DDoSProtection --metric-name DDoSDetected \
  --dimensions Name=ResourceArn,Value=arn:aws:cloudfront::222222222222:distribution/DIST_ID \
  --statistic Maximum --period 60 --evaluation-periods 1 \
  --threshold 0 --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:222222222222:security-oncall

The Anti-DDoS rule group reports DDoSAttackRequests in the AWS/WAFV2 namespace, and WAF's BlockedRequests per rule shows which layer is doing the work. Global Accelerator's own metrics are viewed in us-west-2.

Design decisions

VPC origins rather than a locked public ALB

With a VPC origin the ALB has no public address, so there is nothing to scan or flood directly, no header secret to rotate, and the security group can name CloudFront's service security group instead of a 55-weight prefix list. It costs nothing extra. The trade-offs are the feature limits (no Lambda@Edge origin triggers, no gRPC) and slow deployment. See Task 1.1 and Task 1.3.

WAF on CloudFront, not on the ALB

Filtering at the edge stops attacks near their source, inspects more of the body (16 KB against 8 KB) and lets ATP inspect login responses, which only works on CloudFront. A second web ACL on an ALB reachable only from CloudFront would double fees for little gain. See Task 4.1.

Shield Advanced for a business-critical, attack-prone site

$3,000 a month is easy to justify for a site whose holiday sales would be the target, because it brings the response team, proactive engagement and cost protection credits that can exceed the fee in one attack. A smaller site could stop at Shield Standard plus the Anti-DDoS rule group.

TLS policy and certificates

TLSv1.2_2025 keeps TLS 1.2 for older clients while removing weak ciphers; TLSv1.3_2025 is stricter. Both certificates come from ACM, so they renew automatically. See Task 4.3.

Alternatives

Regional ALB with WAF and no CloudFront

Cheaper for a single-Region audience, but attacks land in the Region, body inspection stops at 8 KB, there is no caching and the ALB is public.

Global Accelerator in front of the ALB

Static IPs and fast regional failover for HTTP too, with WAF on the regional ALB. It gives up caching and edge WAF. It suits customers who must allowlist IP addresses.

Perimeter VPC with IDS/IPS in front of a public ALB

When the security team needs signature-based inspection of inbound flows, ingress routing sends traffic through GWLB or Network Firewall endpoints before the ALB, as on the GWLB page. With CloudFront in front, the firewall sees CloudFront's addresses, not travellers'. See Task 4.1.

Central ingress VPC behind Transit Gateway

One shared ingress VPC holds the public load balancers and forwards to application VPCs over the hub. It adds Transit Gateway charges and a shared failure domain; VPC origins (shareable through RAM since November 2025) reduce the need.

Testing it

  1. Bypass attemptsFrom outside AWS, resolve the ALB's DNS name and connect directly. With a VPC origin it resolves to private addresses and cannot be reached. With the public pattern, a direct connection times out and a test distribution without the header gets the 403.
  2. TLS checksRequest http://www.example.com and expect a 301 to HTTPS. Force TLS 1.1 with a client such as openssl s_client -tls1_1 and expect a handshake failure; TLS 1.2 and 1.3 should succeed.
  3. WAF in CountSend a test SQL injection string, a Log4j pattern and a 20 KB upload. Confirm in the WAF logs which rule matched and that the upload only counted on SizeRestrictions_BODY.
  4. Rate limitsFrom one test address, send 30 login attempts in a minute: after about 20, requests should get 403. GetRateBasedStatementManagedKeys should list the address for a few minutes.
  5. Load test with warningIn staging, and only with an approved load-testing setup, a sustained GET flood from many sources should show the Anti-DDoS group labelling and challenging requests within seconds, and DDoSAttackRequests rising.
  6. Health check and alarm wiringFail the /health endpoint in staging and confirm the Route 53 health check turns unhealthy. Confirm the DDoSDetected alarm exists in us-east-1, not in the ALB's Region.
  7. Partner pathConnect from a partner test range to the accelerator's static IPs and from an unlisted address; only the first should succeed, and the NLB target should log the partner's real address. Run Reachability Analyzer from the internet gateway to the NLB to confirm Block Public Access exclusions and security groups.

"Ensure users can reach the ALB only through CloudFront, with the least operational overhead" is a CloudFront VPC origin with the ALB in private subnets (the VPC still needs an internet gateway attached). If the ALB must stay public, it is the com.amazonaws.global.cloudfront.origin-facing prefix list in the security group plus a secret custom header checked by an ALB listener rule. "Protect against HTTP floods and get credits for scaling costs" is Shield Advanced on the distribution before the attack, with a rate-based rule in Block mode in the web ACL, which must be created with global scope in us-east-1.
