Reference architecture

Dual-stack and IPv6 network

Mobile carriers and large partners are moving to IPv6, the EKS booking platform is running out of IPv4 addresses for its pods, and every public IPv4 address now costs money by the hour. The travel company adds IPv6 to the network it already has: IPAM pools, dual-stack VPCs, IPv6 routes on the Transit Gateways and over Direct Connect and VPN, egress-only internet gateways, NAT64 for IPv6-only workloads, and guardrails for addresses that are public by default.

Scenario and requirements

The travel company (example.com) runs the Transit Gateway hub and spoke in the network account 111111111111, with centralized IPv4 egress and resilient Direct Connect to its US and European data centers. Mobile carriers in Asia and Europe now give many customers IPv6-only addresses, and large partners publish IPv6-first APIs. The EKS booking platform in account 222222222222 uses one VPC IPv4 address per pod, and 10.40.0.0/16 is running short. And every public IPv4 address costs $0.005 an hour, in use or idle.

The address plan. All IPv6 values here come from the documentation range 2001:db8::/32. Real Amazon-provided addresses come from Amazon's own ranges and you cannot choose them, so these are stand-ins. Each Region gets a /44 pool: us-east-1 2001:db8:1000::/44, eu-central-1 2001:db8:1010::/44, ap-northeast-1 2001:db8:1020::/44. A /44 holds 4,096 /56 VPC blocks, and a /56 holds 256 /64 subnets. In us-east-1, production gets 2001:db8:1000::/56, shared services 2001:db8:1000:100::/56 and development 2001:db8:1000:200::/56, and the other Regions follow the same pattern. The US data center keeps 2001:db8:100::/48 (AS 65010) and the European data center 2001:db8:200::/48 (AS 65020). All IPv4 values stay as on the other pages.

How it works

Dual-stack is two independent networks in the same VPCs; these paths show where they meet.

  1. A customer on an IPv6-only mobile network opens the booking site
  2. CloudFront answers over IPv6AWSThe phone gets an AAAA record for the CloudFront distribution and connects over IPv6. CloudFront reaches IPv6 custom origins, here the booking ALB in account 444444444444.
  3. ALB without public IPv4AWSThe ALB runs in dualstack-without-public-ipv4 mode: public IPv6 addresses, private IPv4 only. It forwards to IPv6 pod targets in IP mode.
  4. A booking pod calls a partner airline's IPv6 API
  5. Spoke route to the egress-only gatewayAWSThe pod at 2001:db8:1000:10::a:1 sends to the partner's AAAA address. The node subnet sends ::/0 to the VPC's egress-only internet gateway; the pod's address is kept and the Transit Gateway is not involved.
  6. Replies onlyAWSThe gateway is stateful: replies return, connections opened from the internet are dropped.
  7. A booking pod calls an IPv4-only payment processor
  8. SNAT on the nodeAWSIPv6 pods also have a host-local IPv4 address that the VPC CNI translates to the node's primary IPv4 address. The packet leaves the node as IPv4 from 10.40.14.x.
  9. The existing IPv4 egress pathAWSFrom there it follows 0.0.0.0/0 through tgw-use1, the firewall and the central NAT gateway, as on the centralized egress page.
  10. An IPv6-only worker calls an IPv4-only hotel feed
  11. DNS64 synthesizes an addressAWSA content ingestion worker in the IPv6-only subnet 2001:db8:1000:20::/64 looks up feed.hotel-partner.example, which has only an A record, 203.0.113.5. The Resolver returns 64:ff9b::cb00:7105: the well-known prefix 64:ff9b::/96 plus the IPv4 address.
  12. Route to the hubAWSThe subnet route table sends 64:ff9b::/96 to tgw-use1, and the prod table sends it on to the egress path like 0.0.0.0/0.
  13. NAT64 on the NAT gatewayAWSIn the egress VPC, the attachment subnet sends 64:ff9b::/96 to the same-AZ NAT gateway. It strips the prefix to get 203.0.113.5, uses its own private IPv4 address as the source, and the internet gateway maps that to its Elastic IP.
  14. The replyAWSThe NAT gateway translates the reply back to IPv6. Its subnet route for 2001:db8:1000::/44 points at the Transit Gateway, and the egress table sends it back through the firewall.
  15. A US data center host reaches a booking service over IPv6
  16. Over the transit VIFAWSThe host 2001:db8:100::25 sends to 2001:db8:1000:1::40. Its router learned 2001:db8:1000::/44 over the IPv6 BGP session on dxvif-us1a, because that prefix is allowed on the tgw-use1 association. The onprem table holds the propagated production /56.

Build it

Step 1

IPAM IPv6 pools and the address plan

IPv6 comes in three kinds. Amazon-provided public IPv6 is globally unique and always advertised. BYOIPv6 is your own registered range in IPAM, where you control advertising. Private IPv6 (ULA under fd00::/8 outside Amazon's fd00::/16, or a GUA you own and never advertise) exists only through IPAM, is free, and is dropped at internet and egress-only gateways. The company owns no IPv6 range and needs partner reachability, so it uses Amazon-provided addresses.

The IPAM is already the Organization's delegated administrator in the network account (Task 1.6). Amazon-provided IPv6 needs a Regional pool in the public scope with a locale, service EC2 and source Amazon; you then provision a block of /40 to /52 (one per Regional pool by default). Allocation rules force /56 for VPCs.

The us-east-1 IPv6 pool: Amazon-provided, /56 per VPC, tagged VPCs only (AWS CLI, network account) 
# public scope, because Amazon-provided IPv6 is advertisable; locale is required for Amazon-provided blocks
aws ec2 create-ipam-pool \
  --ipam-scope-id ipam-scope-0public1234567 \
  --address-family ipv6 \
  --locale us-east-1 \
  --aws-service ec2 \
  --public-ip-source amazon \
  --allocation-min-netmask-length 56 \
  --allocation-max-netmask-length 56 \
  --allocation-default-netmask-length 56 \
  --allocation-resource-tags "Key=ipv6,Value=enabled"

# ask Amazon for a /44 (4,096 VPCs); Amazon picks the range, the page shows 2001:db8:1000::/44
aws ec2 provision-ipam-pool-cidr \
  --ipam-pool-id ipam-pool-0use1ipv6 \
  --netmask-length 44

Repeat per Region and share the pools with the organization through AWS RAM. The generous /44 buys clean summaries: one allowed prefix per Transit Gateway (Step 4) and one entry per Region in routes, prefix lists and firewall rules.

Real Amazon-provided blocks for different Regions come from unrelated Amazon ranges, so there is no global IPv6 summary like 10.0.0.0/8. The company keeps a customer-managed prefix list, internal-ipv6, with the three /44s and both data center /48s, for route tables and security groups.

Step 2

Dual-stack VPCs and subnets, plus one IPv6-only subnet

An existing VPC becomes dual-stack by associating an IPv6 block; IPv4 is untouched and always stays. AWS reserves the first four and the last address of each IPv6 subnet, and a VPC can hold five IPv6 blocks by default.

Give the production VPC its /56 from the IPAM pool (AWS CLI, account 222222222222) 
# IPAM picks the next free /56 in the us-east-1 pool: here 2001:db8:1000::/56
aws ec2 associate-vpc-cidr-block \
  --vpc-id vpc-0bookingprod \
  --ipv6-ipam-pool-id ipam-pool-0use1ipv6 \
  --ipv6-netmask-length 56

Existing subnets get a /64 through the console (Edit IPv6 CIDRs). New EKS node subnets are dual-stack and must auto-assign IPv6, or EKS cannot launch nodes. The ingestion workers get an IPv6-only subnet: no IPv4 CIDR, Nitro instances only, instance-ID hostnames, and DNS64 on.

A dual-stack node subnet and an IPv6-only worker subnet in us-east-1a (AWS CLI, account 222222222222) 
# dual-stack: an IPv4 /24 for the nodes themselves and a /64 for node and pod IPv6
aws ec2 create-subnet --vpc-id vpc-0bookingprod --availability-zone us-east-1a \
  --cidr-block 10.40.14.0/24 --ipv6-cidr-block 2001:db8:1000:10::/64
aws ec2 modify-subnet-attribute --subnet-id subnet-eks-node-1a \
  --assign-ipv6-address-on-creation

# IPv6-only: no --cidr-block; DNS64 and resource-name hostnames (one attribute per call)
aws ec2 create-subnet --vpc-id vpc-0bookingprod --availability-zone us-east-1a \
  --ipv6-native --ipv6-cidr-block 2001:db8:1000:20::/64
aws ec2 modify-subnet-attribute --subnet-id subnet-ingest-v6-1a --enable-dns64
aws ec2 modify-subnet-attribute --subnet-id subnet-ingest-v6-1a \
  --private-dns-hostname-type-on-launch resource-name

Leave DNS64 off on dual-stack subnets, where it would push IPv4-reachable traffic through NAT64.

Step 3

IPv6 on the Transit Gateways

The Ipv6Support attachment option (off by default) gives the Transit Gateway interface an IPv6 address and lets the VPC's IPv6 CIDRs propagate. It filters nothing, and static IPv6 routes work without it. Attachment subnets cannot be IPv6-only, so each /28 also gets a /64.

Turn on IPv6 for the booking attachment and add the IPv6 routes the spokes need (AWS CLI, network account) 
aws ec2 modify-transit-gateway-vpc-attachment \
  --transit-gateway-attachment-id tgw-attach-booking-prod \
  --options Ipv6Support=enable

# existing propagations now also carry 2001:db8:1000::/56 into the shared and onprem tables
# NAT64 traffic follows the same path as 0.0.0.0/0 (spoke tables prod, dev, shared)
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 64:ff9b::/96 \
  --transit-gateway-attachment-id tgw-attach-firewall

# the Frankfurt Region over the inter-Region peering (peering routes are always static)
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 2001:db8:1010::/44 \
  --transit-gateway-attachment-id tgw-attach-peer-use1-euc1

Segmentation carries over, because it depends on which routes exist: the dev table never receives production propagations. The spoke tables get no ::/0, since IPv6 internet traffic leaves each VPC through its own egress-only gateway, so the egress VPC cannot bridge segments over IPv6.

In the spokes, the internal-ipv6 prefix list and 64:ff9b::/96 go to the Transit Gateway and ::/0 to the egress-only gateway. Route quotas count IPv4 and IPv6 separately.

The NAT64 route in the IPv6-only subnet's route table (AWS CLI, account 222222222222) 
aws ec2 create-route --route-table-id rtb-ingest-v6 \
  --destination-ipv6-cidr-block 64:ff9b::/96 --transit-gateway-id tgw-use1
Step 4

IPv6 over Direct Connect and Site-to-Site VPN

A virtual interface runs one BGP session per address family, so each transit VIF gets a second, IPv6 session. AWS assigns the IPv6 peer addresses (a /125); omit them when creating the peer.

Add an IPv6 BGP peer to each transit VIF (AWS CLI, network account) 
# repeat for dxvif-us1b, us2a, us2b (AS 65010) and dxvif-eu1a ... eu2b (AS 65020)
aws directconnect create-bgp-peer \
  --virtual-interface-id dxvif-us1a \
  --new-bgp-peer asn=65010,addressFamily=ipv6

The routers advertise their /48 over the new sessions, and it propagates into the Transit Gateway tables. Toward the data centers, AWS advertises the allowed prefixes of each Direct Connect gateway association: exactly as written for a Transit Gateway, never overlapping between Transit Gateways, and /64 or shorter for IPv6.

Advertise each Region's IPv6 pool to the data centers (AWS CLI, network account) 
# the tgw-use1 association already allows 10.40.0.0/14 and 10.255.10.0/24
aws directconnect update-direct-connect-gateway-association \
  --association-id a1b2c3d4-0000-0000-0000-dxgwtgwuse1 \
  --add-allowed-prefixes-to-direct-connect-gateway cidr=2001:db8:1000::/44
# and cidr=2001:db8:1010::/44 on tgw-euc1, cidr=2001:db8:1020::/44 on tgw-apne1

A transit VIF carries at most 200 prefixes per Transit Gateway toward on premises, IPv4 and IPv6 combined. From on premises, VIFs accept 100 IPv6 prefixes by default (up to 1,000 with prefix pools since August 2026); exceeding the limit idles the session. Alarm on the BGP metrics with IpAddressFamily=ipv6.

A Site-to-Site VPN connection carries either IPv4 or IPv6 inside its tunnels, so IPv6 backup is a second VPN connection, with inside addresses from fd00::/8. Since July 2025 the outside addresses can be IPv6 too, on a Transit Gateway or Cloud WAN only.

The European data center's IPv6 backup VPN, IPv6 inside and outside, on tgw-euc1 (AWS CLI, network account) 
# the router's public IPv6 address at the European data center edge
aws ec2 create-customer-gateway --region eu-central-1 \
  --ipv6-address 2001:db8:200:ff::1 --bgp-asn 65020 --type ipsec.1

aws ec2 create-vpn-connection --region eu-central-1 --type ipsec.1 \
  --transit-gateway-id tgw-euc1 --customer-gateway-id cgw-eu-dc1-v6 \
  --options OutsideIPAddressType=IPv6,TunnelInsideIpVersion=ipv6,TunnelOptions=[{StartupAction=start},{StartupAction=start}]

It joins the onprem table like the IPv4 backup on the Direct Connect page, and Direct Connect stays preferred.

Step 5

Internet egress: egress-only gateways, NAT64 and DNS64

IPv6 needs no NAT, and the NAT gateway has no NAT66. Direction control comes from the egress-only internet gateway: outbound-only, stateful, highly available. Of the three patterns in the AWS dual-stack egress blog, the company uses IPv4 centralized, IPv6 distributed: IPv4 keeps the central egress VPC, and each dual-stack VPC gets its own egress-only gateway, which the blog notes has no data processing charge.

IPv6 egress stays in each spoke (AWS CLI, account 222222222222) 
aws ec2 create-egress-only-internet-gateway --vpc-id vpc-0bookingprod

# dual-stack and IPv6-only subnets alike: IPv6 internet through the egress-only gateway
aws ec2 create-route --route-table-id rtb-bookings-app \
  --destination-ipv6-cidr-block ::/0 \
  --egress-only-internet-gateway-id eigw-0bookingprod

NAT64 is built into every NAT gateway, with nothing to enable, and the NAT gateway's subnet need not be dual-stack. For spokes to use it, the egress VPC needs some IPv6:

  1. Egress VPCA /56 from the pool, /64s on the attachment subnets, Ipv6Support on its attachment.
  2. Attachment subnet route table (per AZ)64:ff9b::/96 to the NAT gateway in the same AZ, beside the existing 0.0.0.0/0.
  3. NAT gateway subnet route table (per AZ)The internal-ipv6 prefix list to the Transit Gateway, for replies.
  4. Transit Gateway64:ff9b::/96 to the egress VPC in the firewall table; the three /44s back to the firewall in the egress table, the twin of the static 10.0.0.0/8.
One AZ of the egress VPC: NAT64 in, replies out (AWS CLI, network account) 
aws ec2 create-route --route-table-id rtb-egress-tgw-1a \
  --destination-ipv6-cidr-block 64:ff9b::/96 --nat-gateway-id nat-0use1a

aws ec2 create-route --route-table-id rtb-egress-nat-1a \
  --destination-ipv6-cidr-block 2001:db8:1000::/44 --transit-gateway-id tgw-use1

DNS64 runs in the Route 53 Resolver, per subnet. A name with an AAAA record is returned unchanged; only names without one get a synthesized answer. It also covers IPv4-only systems on premises: answers forwarded through rslvr-rr-corpfwd01 are synthesized too, and that traffic must pass a NAT gateway on its way to the data center. Since April 2026, inbound Resolver endpoints can do DNS64 for IPv6-only clients on premises.

Security groups and network ACLs on the IPv6-only subnet must allow 64:ff9b::/96, and the firewall's HOME_NET must include the three /44s, or the domain rules never match.

NAT64 traffic crosses the Transit Gateway-attached firewall as IPv6, before translation. This page does not confirm the attached firewall's IPv6 behaviour in every setup; prove it in staging before moving production workers.

Step 6

The EKS booking cluster in the IPv6 family

This fixes the pod shortage. An EKS cluster chooses its IP family at creation and can never change it, so the company builds a new IPv6 cluster and shifts traffic with weighted DNS. In the IPv6 family:

  • Pods and services get only IPv6. EKS has no dual-stack pods. The VPC CNI gives each node /80 prefixes from its subnet's /64, so pods use no VPC IPv4 addresses.
  • Nodes are dual-stack, and the cluster's VPC and subnets need IPv4 and IPv6, so nodes go in dual-stack subnets, not IPv6-only ones.
  • Pods reach IPv4 through the node, not NAT64. A hidden host-local IPv4 address is translated to the node's primary IPv4 address; the EKS documentation says this removes the need for DNS64 and NAT64.
  • Pod IPv6 is not translated on the way out through the egress-only gateway.
  • Constraints: Nitro EC2 or Fargate only, no Windows pods, no custom networking, load balancers in IP mode (AWS Load Balancer Controller 2.3.1 or later), and the IPv6 IAM policy on the CNI role.

Security groups need IPv6 rules of their own: an IPv4 rule never matches an IPv6 packet, and the 60-rule quotas count each family separately. The node group uses the internal-ipv6 prefix list rather than one rule per range.

IPv6 routers never fragment, so path MTU discovery needs ICMPv6 "Packet Too Big". A network ACL that allows TCP 443 but drops ICMPv6 makes large responses hang (Task 3.3).

Step 7

Inbound IPv6 and the guardrails

Inbound. CloudFront has IPv6 enabled and www.example.com has A and AAAA alias records. The origin ALB moves to dualstack-without-public-ipv4: public IPv6, private IPv4, no public IPv4 charges. ALB authentication with an identity provider or Cognito still needs public IPv4 (HTTP 500 errors without it); the booking ALB uses none.

Remove the ALB's public IPv4 addresses (AWS CLI, account 444444444444) 
# the subnets must already have IPv6 CIDRs
aws elbv2 set-ip-address-type \
  --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:444444444444:loadbalancer/app/booking-web/0a1b2c3d4e5f6a7b \
  --ip-address-type dualstack-without-public-ipv4

Guardrails. With Amazon-provided IPv6 there is no NAT hiding anything: every address is public. One wrong ::/0 to an internet gateway leaves only security groups and network ACLs in the way. The 2026 Block Public Access blog recommends layers: Block Public Access, SCPs that stop teams attaching internet or egress-only gateways, then security groups and network ACLs.

Block Public Access (per account and Region) overrides routes, security groups and network ACLs. block-bidirectional blocks all internet and egress-only gateway traffic; block-ingress blocks inbound but allows outbound through NAT and egress-only gateways, which suits a dual-stack spoke. Exclusions are allow-bidirectional or allow-egress (bidirectional mode only).

Block inbound internet everywhere, except the ALB's public subnets (AWS CLI, run per account and Region) 
# workload account 222222222222: outbound through egress-only and NAT gateways still works
aws ec2 modify-vpc-block-public-access-options --internet-gateway-block-mode block-ingress

# account 444444444444: the same mode, plus one exclusion per ALB subnet
aws ec2 modify-vpc-block-public-access-options --internet-gateway-block-mode block-ingress
aws ec2 create-vpc-block-public-access-exclusion \
  --subnet-id subnet-alb-1a --internet-gateway-exclusion-mode allow-bidirectional

A declarative policy can enforce the mode organization-wide (Task 4.1). Private paths such as the Transit Gateway are unaffected.

Design decisions

A /44 per Region, a /56 per VPC, a /64 per subnet

A /56 per VPC is what Amazon hands out directly, and a /64 per subnet is the convention (EKS prefix delegation carves /80s from it). The /44 per Region trades unused space for one summary per Transit Gateway, peering route and prefix list entry. IPAM shows which VPCs are still IPv4-only. See Task 1.6.

Amazon-provided public IPv6, not BYOIPv6 or private IPv6

Amazon-provided addresses are globally unique, so IPv6 never repeats the company's IPv4 overlaps with partners (overlapping CIDRs page). BYOIPv6 would give partners one stable range to allow-list, at the cost of owning and registering it. Private IPv6 suits VPCs that must never reach the internet, but is hard to undo: getting out later needs a second, routable prefix or NPTv6 appliances.

IPv4 centralized, IPv6 distributed

Central IPv6 egress needs translation in the egress VPC, which no managed service offers: the NAT gateway has no NAT66, and the 2025 inspection blog states that Network Firewall supports neither NAT66 nor NPTv6. So IPv6 internet traffic is not inspected centrally. The company accepts this for general booking traffic, filtered by security groups, DNS Firewall and Block Public Access, and keeps the card data VPC IPv4-only so its outbound flows still pass the domain allow list. See Task 4.1.

EKS on dual-stack nodes, IPv6-only subnets for simple workers

The pod shortage is solved by the IPv6 family, not by IPv6-only subnets: EKS needs dual-stack subnets and covers IPv4 with node SNAT. IPv6-only subnets with NAT64 suit workloads that can live without IPv4, like the ingestion workers. Each NAT64 flow pays NAT gateway and Transit Gateway processing, so heavy IPv4 use argues for dual-stack.

Cost

Public IPv4 is $0.005 an hour per address, about $3.65 a month each, across ALBs, NAT gateways and instances in 300 VPCs; every dualstack-without-public-ipv4 ALB or IPv6-only subnet removes some. NAT64 and IPv4 egress still pay per-GB NAT and Transit Gateway charges; IPv6 through egress-only gateways pays only data transfer out. See Task 3.3.

Alternatives

Centralized IPv6 egress through NAT66 instances or proxies

The 2023 blog's other patterns: EC2 NAT66 instances in the egress VPC (which also let non-advertised BYOIP ranges reach the internet), or a proxy fleet behind an NLB for both families. Central control, but you run, scale and patch the instances, with routes per AZ.

Inspected IPv6 egress (2025 inspection blog)

Distributed: a firewall or Gateway Load Balancer endpoint in each VPC before the internet gateway, an edge route table for symmetric replies, and a policy that drops internet-originated flows. Centralized: Gateway Load Balancer endpoints in each spoke sending to central appliances (no Transit Gateway charges, but egress-only, and not in IPv6-only subnets), or Transit Gateway routing to appliances doing NAT66 or NPTv6. The blog favours distributed endpoints for fault isolation and scale.

Stay on IPv4 and fix the pods another way

A secondary 100.64.0.0/10 CIDR with EKS custom networking, or IPv4 prefix delegation, fixes pod density without touching routing (overlapping CIDRs page), but does nothing for IPv6-only customers or the IPv4 bill, and custom networking is unavailable in IPv6 clusters.

Testing it

  1. The address plan is cleanIPAM shows every production VPC with a compliant, non-overlapping /56 from its Region's pool.
  2. DNS64 and NAT64 workFrom an ingestion worker, dig AAAA feed.hotel-partner.example returns 64:ff9b::cb00:7105 and curl -6 https://feed.hotel-partner.example succeeds, arriving from a NAT gateway Elastic IP. A name with a real AAAA record comes back unchanged.
  3. Hub routing, both familiesReachability Analyzer is IPv4 only, a common exam trap. Route Analyzer in Network Manager accepts IPv6 addresses and checks Transit Gateway routes both ways: booking to 2001:db8:100::25 should use the Direct Connect gateway attachment, and development to 2001:db8:1000::/56 should fail.
  4. Hybrid IPv6 sessionsEach transit VIF shows two BGP peers up. A BGP failover test on dxvif-us1a should leave a Network Synthetic Monitor IPv6 probe to 2001:db8:100::25 healthy.
  5. No inbound exposureAn outside IPv6 host cannot connect to a pod. In staging, add a ::/0 route to an internet gateway: Block Public Access must still block inbound.
  6. Flow logs for IPv6Query VPC flow logs for 64:ff9b:: destinations (NAT64 dependants) and for IPv6 rejects by IPv4-only security groups.

"IPv6-only instances must reach an IPv4-only service on the internet" is DNS64 on the subnet plus a route for 64:ff9b::/96 to a NAT gateway (NAT64), not an egress-only gateway, which carries IPv6 only. "Instances must reach the internet over IPv6 without being reachable from it" is an egress-only internet gateway with ::/0, not a NAT gateway, which has no NAT66. "EKS is out of pod IPs and must not depend on IPv4 addressing" is a new cluster in the IPv6 family, because the family cannot be changed on an existing cluster.
