Reference architecture

SD-WAN integration with Transit Gateway Connect and Cloud WAN

The travel company's 60 sales offices already run on a vendor SD-WAN. Instead of 60 VPNs, headend appliances in a transport VPC join the fabric and exchange routes with the Transit Gateway over GRE and BGP, so offices and VPCs learn each other dynamically. A Cloud WAN variant and a VPN Concentrator for the smallest sites complete the picture.

Scenario and requirements

The travel company (example.com) sells holidays through 60 sales offices: 35 in North America and 25 in Europe. Each office has two internet links and a branch appliance from one SD-WAN vendor, which builds encrypted overlays and picks the best link per application. The network team in account 111111111111 wants offices to reach the Transit Gateway hub in us-east-1 and eu-central-1 directly, without a VPN per office and without static routes to maintain.

RequirementDesign choice
Offices join AWS through the SD-WAN they already runVendor headend appliances from AWS Marketplace in a transport VPC, two Availability Zones per Region
Dynamic routes, more than VPN throughputTransit Gateway Connect: GRE tunnels with BGP from each headend, ECMP across headends
Offices reach production and shared services, never developmentA new branch Transit Gateway route table and controlled propagation
Offices keep working if a Region's headends failThe US data center's SD-WAN appliance peers over Direct Connect as a backup path, with a longer AS path
Small sites with no SD-WAN applianceA VPN Concentrator on the Transit Gateway, or plain Site-to-Site VPN

Numbers used on this page, consistent with the other architecture pages:

  • Transit Gateways: tgw-use1 (ASN 64521) and tgw-euc1 (ASN 64522), route tables prod, dev, shared and onprem as on the hub page. tgw-use1 already has the Transit Gateway CIDR block 10.255.10.0/24 from the encrypted hybrid page, already in the allowed prefixes of dxgw-travel-global (AS 64512).
  • New on this page: the SD-WAN fabric uses private AS 65030, distinct from every other ASN in the company plan. Offices use 10.120.0.0/16, one /24 each: North America in 10.120.0.0/17, Europe in 10.120.128.0/17.
  • Transport VPC vpc-0sdwanuse1, 10.41.232.0/22 inside the shared services range. Headend sdwan-1a has its inside interface at 10.41.233.10 in us-east-1a, sdwan-1b at 10.41.233.74 in us-east-1b. Frankfurt mirrors it (10.45.232.0/22, block 10.255.20.0/24); only Virginia is shown.

How it works

A sales agent in the Chicago office (10.120.14.0/24) opens the booking console, served by the production booking VPC at 10.40.8.0/21.

  1. Office to AWS
  2. Branch appliance picks a pathSD-WANThe Chicago appliance has learned 10.40.0.0/14 from both Virginia headends through the vendor's controller. It encrypts the packet into its IPsec overlay and sends it over the better internet link to the public address of sdwan-1a or sdwan-1b.
  3. Headend decrypts and routesSD-WANThe headend ends the overlay, looks up 10.40.8.0/21 in its BGP table and finds it behind its Connect peer to tgw-use1.
  4. GRE inside the transport VPCSD-WANThe headend wraps the clear packet in GRE from 10.41.233.10 to the Transit Gateway address 10.255.10.100. The subnet route table sends 10.255.10.0/24 to the Transit Gateway, so the GRE packet enters through the transport VPC attachment.
  5. Connect recognises the tunnelAWSThe Transit Gateway matches the outer source and destination to a Connect peer, removes the GRE header and treats the inner packet as arriving on the Connect attachment.
  6. Lookup in the branch tableAWSThe Connect attachment is associated with the branch table, which holds the propagated production and shared services VPC routes. The packet leaves on the booking VPC attachment.
  7. AWS back to the office
  8. Production tableAWSThe booking VPC's attachment uses the prod table, where the Connect attachment propagated the office /24s learned over BGP. Both headends advertise them with the same AS path, so the Transit Gateway spreads flows over both peers (ECMP).
  9. GRE to the headendAWSThe Transit Gateway encapsulates the reply in GRE to the chosen headend's inside address. The headend re-encrypts it into the overlay toward Chicago.
  10. When both Virginia headends fail
  11. Backup over Direct ConnectAWSThe BGP sessions drop after the 30-second hold time and the office routes from the headends are withdrawn. The same /24s are still advertised, with a longer AS path, by the US data center's SD-WAN appliance through a second Connect attachment over Direct Connect. That path becomes active, and the offices reach AWS through the data center.

Build it

Step 1

The transport VPC, its attachment and the headends

The transport VPC lives in the network account, because Connect attachments are created in the Transit Gateway owner's account. It has three subnet tiers per Availability Zone: an outside subnet with a route to an internet gateway, where each headend's outside interface has an Elastic IP for the branch overlays; an inside subnet for the GRE side; and a small attachment subnet used only by the Transit Gateway. The headends come from the vendor's AWS Marketplace listing, one per Availability Zone.

Attach the transport VPC to tgw-use1, using the dedicated /28 attachment subnets (AWS CLI, network account) 
aws ec2 create-transit-gateway-vpc-attachment \
  --transit-gateway-id tgw-use1 \
  --vpc-id vpc-0sdwanuse1 \
  --subnet-ids subnet-0sdwtgw1a subnet-0sdwtgw1b \
  --options DnsSupport=enable \
  --tag-specifications 'ResourceType=transit-gateway-attachment,Tags=[{Key=Name,Value=sdwan-transport}]'

Two route details make or break the tunnels. The inside subnets need a route from the Transit Gateway CIDR block to the Transit Gateway, otherwise the headend's GRE packets for 10.255.10.100 have nowhere to go. And the headends forward packets that are neither from nor to their own addresses, so source/destination checking must be off on every interface that carries transit traffic.

Reach the Connect peer addresses and let the appliances forward (AWS CLI) 
# GRE from the headends to 10.255.10.0/24 goes to the Transit Gateway
aws ec2 create-route --route-table-id rtb-0sdwaninside \
  --destination-cidr-block 10.255.10.0/24 --transit-gateway-id tgw-use1

# repeat for sdwan-1b; extra interfaces use modify-network-interface-attribute
aws ec2 modify-instance-attribute \
  --instance-id i-0sdwan1a --no-source-dest-check
aws ec2 modify-network-interface-attribute \
  --network-interface-id eni-0sdwan1aout --no-source-dest-check

The transport VPC attachment is associated with the shared table. It carries GRE only, so it needs no propagation into the workload tables; the branch prefixes arrive through the Connect attachment instead. The internet gateway is a deliberate second internet edge, so the outside interfaces' security groups allow only the vendor's overlay ports.

Forgetting the route to the Transit Gateway CIDR block is the classic "Connect peer created, BGP never comes up" fault. The block is not part of any VPC, so nothing adds a route to it automatically.

Step 2

The Connect attachment and one GRE peer per headend

A Connect attachment rides on a transport attachment, here the VPC attachment from Step 1. Each Connect peer is one GRE tunnel with two BGP sessions to AWS-managed endpoints for redundancy, and AWS strongly recommends configuring both. The addressing has three parts:

  • Transit Gateway GRE address from a Transit Gateway CIDR block. Without a value, the first free address is taken; fixing 10.255.10.100 and .101 keeps them clear of the private IP VPN endpoints in the same block. Blocks are /24 or larger for IPv4, at most five per gateway, and must not overlap VPC or on-premises ranges.
  • Peer GRE address: the headend's inside interface, any address in the same IP family.
  • Inside CIDR: a /29 from 169.254.0.0/16, unique on the Transit Gateway, carrying the BGP sessions. The blocks 169.254.0.0/29 to 169.254.5.0/29 and 169.254.169.248/29 are reserved. The appliance uses the first address; the Transit Gateway uses the second and third.
One Connect attachment on the transport attachment, then a peer per headend (AWS CLI, network account) 
aws ec2 create-transit-gateway-connect \
  --transport-transit-gateway-attachment-id tgw-attach-sdwan-vpc \
  --options Protocol=gre

# sdwan-1a: appliance BGP address 169.254.100.1, AWS side .2 and .3
aws ec2 create-transit-gateway-connect-peer \
  --transit-gateway-attachment-id tgw-attach-sdwan-connect \
  --transit-gateway-address 10.255.10.100 \
  --peer-address 10.41.233.10 \
  --inside-cidr-blocks 169.254.100.0/29 \
  --bgp-options PeerAsn=65030 \
  --tag-specifications 'ResourceType=transit-gateway-connect-peer,Tags=[{Key=Name,Value=sdwan-1a}]'

# sdwan-1b: appliance BGP address 169.254.100.9, AWS side .10 and .11
aws ec2 create-transit-gateway-connect-peer \
  --transit-gateway-attachment-id tgw-attach-sdwan-connect \
  --transit-gateway-address 10.255.10.101 \
  --peer-address 10.41.233.74 \
  --inside-cidr-blocks 169.254.100.8/29 \
  --bgp-options PeerAsn=65030 \
  --tag-specifications 'ResourceType=transit-gateway-connect-peer,Tags=[{Key=Name,Value=sdwan-1b}]'

The output of each peer shows two BgpConfigurations entries, one per AWS-side address, each with BgpStatus down until the appliance is configured. If PeerAsn were left out, the Transit Gateway's own ASN would be used and the sessions would become iBGP.

Capacity: up to 5 Gbps and 300,000 packets per second per peer, four peers per Connect attachment (not adjustable), up to 20 Gbps per attachment if the transport allows it. Two peers give 10 Gbps, far more than 60 offices on broadband need. Two more peers raise it to 20 Gbps, and ECMP also works across Connect attachments on the same Transit Gateway.

Step 3

GRE and BGP on the headends

Every SD-WAN vendor has its own interface, but the settings Connect needs are the same everywhere:

  • MP-BGP only, over IPv4 peering; IPv6 prefixes would ride the same session. eBGP needs multihop with TTL 2.
  • Both sessions per peer: AWS side .2 and .3 of the /29.
  • No BFD, no graceful restart, no static routes. Failure detection relies on BGP timers: keepalive 10 seconds, hold 30 seconds.
  • Routes: at most 1,000 from the appliance to a peer and 5,000 from the peer to the appliance. Sixty office /24s are well inside that; summarize if the fabric grows.
  • MTU: the Transit Gateway supports 8500 bytes on Connect and VPC attachments. GRE adds 24 bytes (4 GRE plus 20 outer IP), so the tunnel MTU is the outer MTU minus 24.
sdwan-1a: GRE tunnel to tgw-use1 and eBGP to both AWS addresses (Cisco IOS-style; adapt to the vendor's syntax) 
interface Tunnel100
 description Connect peer to tgw-use1
 ip address 169.254.100.1 255.255.255.248
 ! 8500 on the transport attachment minus 24 bytes of GRE
 ip mtu 8476
 ! branch traffic arrives through 1500-byte internet overlays
 ip tcp adjust-mss 1360
 tunnel source 10.41.233.10
 tunnel destination 10.255.10.100
 tunnel mode gre ip
!
router bgp 65030
 neighbor 169.254.100.2 remote-as 64521
 neighbor 169.254.100.2 ebgp-multihop 2
 neighbor 169.254.100.3 remote-as 64521
 neighbor 169.254.100.3 ebgp-multihop 2
 address-family ipv4
  ! only the office ranges go to AWS
  neighbor 169.254.100.2 prefix-list OFFICES-OUT out
  neighbor 169.254.100.3 prefix-list OFFICES-OUT out
  neighbor 169.254.100.2 activate
  neighbor 169.254.100.3 activate

Office traffic arrives inside 1500-byte internet overlays, so the vendor's MSS clamping sets the real segment size; 1360 is an example. The Transit Gateway also clamps MSS and supports Path MTU Discovery for traffic entering on VPC and Connect attachments.

For ECMP, both headends must advertise the same prefixes with the same AS_PATH and ASN. Otherwise one peer carries everything. There is no ECMP between the two BGP sessions of one peer: they are redundancy, not extra bandwidth.

Step 4

A branch route table and controlled propagation

Connect routes propagate into a route table like VPN or Direct Connect gateway routes, but the hub runs with default association and propagation off, so the Connect attachment goes nowhere until it is placed. Sales offices need production (the booking console), shared services (DNS, directory) and the data centers, and must never reach development. Associating the Connect attachment with onprem would give them development routes too, so it gets its own branch table.

The branch table: associate the Connect attachment and choose who it can reach (AWS CLI, network account) 
aws ec2 create-transit-gateway-route-table --transit-gateway-id tgw-use1 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=branch}]'

# office traffic looks up its destinations in branch
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-branch \
  --transit-gateway-attachment-id tgw-attach-sdwan-connect

# production, shared services and the data centers can reach the offices
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-sdwan-connect
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-shared \
  --transit-gateway-attachment-id tgw-attach-sdwan-connect
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-onprem \
  --transit-gateway-attachment-id tgw-attach-sdwan-connect

# offices learn the data center routes; VPC attachments are added the same way
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-branch \
  --transit-gateway-attachment-id tgw-attach-dxgw

Production and shared services VPC attachments are propagated into branch by the same automation that places new spokes on the hub page, driven by the segment tag. branch also gets the 10.42.0.0/16 blackhole as a backstop.

Confirm the office routes arrived from Connect in the production table (AWS CLI) 
aws ec2 search-transit-gateway-routes \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --filters "Name=attachment.resource-type,Values=connect" "Name=route-search.subnet-of-match,Values=10.120.0.0/16"

Do not add static routes for 10.120.0.0/16 on the Transit Gateway peering toward Frankfurt. Static beats propagated for the same prefix, so a static summary would pull European offices' traffic across the Atlantic even though Frankfurt's own headends serve them.

Step 5

The data center's SD-WAN appliance over Direct Connect

The SD-WAN fabric also has a hub appliance in the US data center, us-dc1-sdwan, with loopback 10.100.255.10. It can join the Transit Gateway with no VPC at all: a Connect attachment whose transport is the Direct Connect gateway attachment tgw-attach-dxgw. GRE runs from the loopback across the transit VIFs to a Transit Gateway address. That needs the transit VIF, Direct Connect gateway and association in place, and the Transit Gateway CIDR block in the allowed prefixes. Both are in place from the resilient Direct Connect and encrypted hybrid pages.

A second Connect attachment over Direct Connect and its peer (AWS CLI, network account) 
aws ec2 create-transit-gateway-connect \
  --transport-transit-gateway-attachment-id tgw-attach-dxgw \
  --options Protocol=gre

# the data center loopback must be reachable over the transit VIFs, not through the tunnel itself
aws ec2 create-transit-gateway-connect-peer \
  --transit-gateway-attachment-id tgw-attach-dc-connect \
  --transit-gateway-address 10.255.10.200 \
  --peer-address 10.100.255.10 \
  --inside-cidr-blocks 169.254.100.16/29 \
  --bgp-options PeerAsn=65030

This attachment is placed exactly like the first one in Step 4. The data center appliance advertises the same office /24s, prepended twice. Both are Connect routes, and within one attachment type the Transit Gateway prefers the shorter AS_PATH, so the VPC headends carry traffic and the data center path is a hot standby. The 8500-byte transit VIFs allow the same 8476 tunnel MTU.

Two rules keep this stable. First, the tunnel's own endpoint (10.255.10.0/24) must stay reachable through the underlay; if the appliance learned it through the tunnel, the tunnel would flap. Second, Connect routes rank below Direct Connect gateway routes for the same prefix. The data center's own 10.100.0.0/16 stays on the transit VIFs, not in the tunnel.

GRE adds no encryption, and Direct Connect is private but not encrypted. Office traffic is encrypted only on the internet leg, inside the vendor's IPsec overlay, and travels in clear GRE from the headend to the Transit Gateway and from the data center over Direct Connect. Card data from phone bookings still needs TLS end to end, or the MACsec and private IP VPN layers of the encrypted hybrid design.

Step 6

The Cloud WAN variant: GRE or Tunnel-less Connect

When the company moves to the Cloud WAN core network, the headends attach to the core network edge instead. Cloud WAN Connect attachments are created in the core network owner's account, use a VPC attachment as transport (the documentation lists only VPC transport), and offer two protocols:

  • GRE: the same model as Transit Gateway Connect, with two BGP sessions per peer, 5 Gbps per peer, 4 peers per attachment and 1,000 routes in, 5,000 out per peer.
  • Tunnel-less Connect (October 2023, NO_ENCAP): the appliance peers BGP directly with the edge, with no GRE or IPsec. That removes the 24-byte overhead and the 5 Gbps per-peer limit: up to 100 Gbps per Availability Zone, 1,000 routes in and 10,000 out per peer, and 8500-byte MTU. There is no inside CIDR to choose and at most one Tunnel-less attachment per VPC.

Segmentation is the main reason to move. The SD-WAN carries two VRFs: sales for office users and cardpay for the phone-payment terminals in scope for PCI DSS. Each VRF maps one to one to a new Cloud WAN segment, branch and branchpci, so separation runs from the office to the VPC. With GRE, the transport VPC attachment sits in a transport segment and one Connect attachment per VRF sits in its own segment. With Tunnel-less, the Connect attachment and its transport VPC attachment must be in the same segment, so each segment needs its own transport VPC attachment and the headend needs one interface per segment (a multi-VPC ENI).

Tunnel-less Connect for the sales VRF in us-east-1 (AWS CLI, network account, Network Manager home Region) 
# the transport VPC attachment carries the tag segment=branch, so both land in branch
aws networkmanager create-connect-attachment --region us-west-2 \
  --core-network-id core-network-0travel123456 \
  --edge-location us-east-1 \
  --transport-attachment-id attachment-0sdwanbranch01 \
  --options Protocol=NO_ENCAP \
  --tags Key=segment,Value=branch

# the subnet is the one holding the headend's branch interface; BGP options apply only to GRE
aws networkmanager create-connect-peer --region us-west-2 \
  --connect-attachment-id attachment-0sdwanconnect1 \
  --peer-address 10.41.233.10 \
  --subnet-arn arn:aws:ec2:us-east-1:111111111111:subnet/subnet-0sdwin1a

For the GRE protocol, the same command takes --inside-cidr-blocks, an optional --core-network-address and --bgp-options PeerAsn=65030, mirroring Step 2.

Step 7

BGP monitoring through Network Manager

The Transit Gateways are already registered in the global network. Network Manager then emits Connect events to EventBridge in us-west-2: topology changes such as CONNECT_ATTACHMENT_CREATED and TGW-CONNECT-PEER-CREATED, and status updates CONNECT_PEER_BGP_DOWN and CONNECT_PEER_BGP_UP.

Page the network team when any Connect peer loses BGP (AWS CLI; the rule must be in us-west-2) 
aws events put-rule --region us-west-2 \
  --name connect-peer-bgp-down \
  --event-pattern '{
    "source": ["aws.networkmanager"],
    "detail-type": ["Network Manager Status Update"],
    "detail": {"changeType": ["CONNECT_PEER_BGP_DOWN"]}
  }'

aws events put-targets --region us-west-2 --rule connect-peer-bgp-down \
  --targets Id=oncall,Arn=arn:aws:sns:us-west-2:111111111111:network-oncall
Check both BGP sessions of every peer on the Connect attachment (AWS CLI) 
aws ec2 describe-transit-gateway-connect-peers \
  --filters Name=transit-gateway-attachment-id,Values=tgw-attach-sdwan-connect \
  --query "TransitGatewayConnectPeers[].ConnectPeerConfiguration.BgpConfigurations[].[PeerAddress,TransitGatewayAddress,BgpStatus]"

Transit Gateway flow logs record Connect traffic on the transport attachment, not the Connect attachment, so office flows appear under tgw-attach-sdwan-vpc or tgw-attach-dxgw. Alarm on a single session down: it silently removes redundancy.

Design decisions

Connect instead of a VPN per office or per headend

Sixty office VPNs would mean 120 tunnels and losing the SD-WAN's path selection; VPN from each headend gives 1.25 Gbps per standard tunnel. Connect gives 5 Gbps per peer, 1,000 routes in per peer and no IPsec to manage between two devices that are both inside AWS. See Task 1.5.

Two headends in two Availability Zones, one AS, no prepending

Identical prefixes and AS paths make the Transit Gateway load-share across both and fail over by withdrawal. Prepending on one gives active/standby at half the capacity. Without BFD, failover takes up to the 30-second hold time.

A separate branch route table

Offices are not data centers: they are many, less trusted and in public places. A branch table keeps them out of development and lets the network team change their reach without touching the data center paths. The cost is one more table out of the 20 per gateway (adjustable).

Small sites without an appliance

About 40 airport ticket desks have only a basic router and need under 50 Mbps each. A VPN Concentrator (November 2025) gives them one Transit Gateway attachment for up to 100 sites, at up to 100 Mbps and 10,000 packets per second per site and 5 Gbps in total. It is BGP only, has no ECMP, works only on Transit Gateways (not Cloud WAN or virtual private gateways), and its routes rank below normal VPN routes. The price is $1.95 an hour plus $0.01 per site-hour: for 40 desks about $1,423.50 + $292 = $1,715.50 a month plus its attachment, compared with about $2,920 for 40 separate VPNs: $1,460 for the connections at $0.05 an hour, plus $1,460 for their 40 Transit Gateway attachments at $0.05 an hour. For a few sites, or ECMP or static routing, plain Site-to-Site VPN stays the answer.

Costs

The headends are EC2 instances plus the vendor's Marketplace licence, usually the largest line item. The transport VPC attachment is billed like any VPC attachment ($0.05 an hour in the published example); check the Transit Gateway pricing page for the Connect attachment and data processing rates in each Region. Cloud WAN adds $0.50 an hour per core network edge. See Task 3.3.

Alternatives

Site-to-Site VPN from each office

Managed by AWS with no appliances, but it ignores the fabric the company pays for and adds two tunnels per office.

Connect over Direct Connect only

Backhaul every office to the data centers and enter AWS only through the data center appliance from Step 5. Fewer components in AWS, but every office then depends on the data centers.

Cloud WAN with Tunnel-less Connect

Best when the SD-WAN carries several VRFs that should stay separate end to end across Regions, or when throughput above 20 Gbps per attachment matters. It costs the core network edges and needs one interface and transport attachment per segment. See Task 2.2.

Testing it

  1. Both sessions on every peer are updescribe-transit-gateway-connect-peers should show four BgpConfigurations with BgpStatus up for the two headend peers, and two more for the data center peer.
  2. Routes and ECMP in the tablessearch-transit-gateway-routes on prod with attachment.resource-type=connect should list all 35 North American office /24s on tgw-attach-sdwan-connect, not on the data center attachment. On branch, the same search should show no development route.
  3. Reachability Analyzer up to the boundaryReachability Analyzer does not support Connect attachments, and analysis stops there. Test the AWS half instead: from a booking ENI to the inside interface of each headend, which proves the VPC routes, security groups and Transit Gateway tables up to the appliance. Prove the office leg with the vendor's own path tools and a synthetic test from an office.
  4. Fail one headendStop sdwan-1a in a maintenance window. Within the 30-second hold time, a CONNECT_PEER_BGP_DOWN event should reach the on-call topic, office routes should remain in prod through sdwan-1b only, and a continuous test from the Chicago office to the booking console should show a short pause, not an outage.
  5. Fail both headendsShut BGP on both Virginia peers. The office /24s should switch to tgw-attach-dc-connect (longer AS path, still Connect), and the transport attachment's flow logs should go quiet while flows appear on tgw-attach-dxgw.
  6. MTUFrom a booking pod, send large packets with the do-not-fragment bit to an office host. Check that MSS clamping keeps TCP sessions working and that no flow log entries count packets-lost-mtu-exceeded.

"SD-WAN appliances in a VPC must exchange routes dynamically with the Transit Gateway at higher throughput than VPN, without IPsec between them" is a Transit Gateway Connect attachment on the VPC attachment, with GRE Connect peers and BGP. "Highest throughput and no tunnel overhead with Cloud WAN, keeping SD-WAN VRFs separate" is Tunnel-less Connect with one segment per VRF. "BGP never establishes on a new Connect peer" usually means no route to the Transit Gateway CIDR block, a missing ebgp-multihop, or a reserved inside CIDR.
