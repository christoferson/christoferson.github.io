Overview

Task 3.2

Monitor and analyze network traffic to troubleshoot and optimize connectivity patterns.

Task 1.4 chose what to monitor; this task reads the results. Questions give you a flow log record, a metric, a Reachability Analyzer finding or a symptom ("SSH works but file copies hang") and ask what it means or which tool finds the cause. The packet size questions are especially common: know the MTU of every path and where Path MTU Discovery fails.

The travel company's network team investigates slow partner transfers, intermittent rejects in the booking VPCs, and a migration from VPC peering to the Transit Gateway that broke large responses.

Performance and reachability constraints

Knowledge 3.2.1Network performance metrics and reachability constraints (for example, routing, packet size)

MTU on each path

  • 9001: between instances in a VPC, and over same-Region VPC peering. Direct Connect private VIFs can be 9001.
  • 8500: inter-Region VPC peering; Transit Gateway VPC, Direct Connect, Connect and peering attachments (including Cloud WAN); transit VIFs; NAT gateways; VPC endpoints; Gateway Load Balancer; VPC Lattice.
  • 1500: the internet gateway, Site-to-Site VPN attachments, and traffic between Regions that does not use a Transit Gateway or peering.
  • 1446 (MSS 1406) inside a Site-to-Site VPN tunnel, lower with some algorithms and NAT traversal.

Larger packets are dropped or, where allowed, fragmented. Two private VIFs, or a VIF and a VPN, advertising the same prefix with different MTUs fall back to 1500.

Path MTU Discovery support

  • Sends "fragmentation needed" (ICMP type 3 code 4) or ICMPv6 Packet Too Big: NAT gateways, and Transit Gateways for traffic arriving on VPC and Connect attachments.
  • Does not: Transit Gateway on VPN, Direct Connect or peering attachments; Site-to-Site VPN; VPC endpoints; Gateway Load Balancer.
  • MSS clamping on Transit Gateway, NAT gateway and VPC endpoints rescues most TCP traffic; large UDP or ICMP packets with the DF bit set are the usual casualties.

Other constraints

  • Routing: missing propagation, a blackhole, an overlapping CIDR not propagated, a more specific route elsewhere, asymmetric paths through stateful appliances.
  • Throughput: single-flow and instance limits, VPN tunnel limits, NAT port exhaustion (Task 3.1).
  • Latency, jitter and loss: measured by Network Synthetic Monitor (hybrid), Network Flow Monitor (between workloads) and Internet Monitor (users).

Logs and metrics for loss

Knowledge 3.2.2Appropriate logs and metrics to assess network performance and reachability issues (for example, packet loss)

Where packets are lost, and what shows it:

  • The instance itself: ENA counters bw_in_allowance_exceeded, bw_out_allowance_exceeded, pps_allowance_exceeded, conntrack_allowance_exceeded, linklocal_allowance_exceeded (read with ethtool -S eth0 or the CloudWatch agent).
  • Transit Gateway: PacketDropCountNoRoute, PacketDropCountBlackhole; in Transit Gateway flow logs, packets-lost-no-route, packets-lost-blackhole, packets-lost-mtu-exceeded and packets-lost-ttl-expired.
  • NAT gateway: ErrorPortAllocation, PacketsDropCount, IdleTimeoutCount.
  • Security groups and network ACLs: REJECT records in VPC flow logs (with reject-reason for Block Public Access and Encryption Controls).
  • Hybrid links: Direct Connect ConnectionErrorCount, light levels and BGP status; VPN TunnelState and tunnel logs; Network Synthetic Monitor packet loss and round-trip time to data center addresses.
  • Load balancers: NLB TCP_Target_Reset_Count and ALB 5xx metrics split by load balancer or target.
  • Traffic Mirroring captures for retransmissions, duplicate ACKs and zero windows that prove loss or shaping at the packet level.

Collection and routing tools

Knowledge 3.2.3Tools to collect and analyze logs and metrics (for example, CloudWatch, VPC Flow Logs, VPC Traffic Mirroring)

  • CloudWatch: metrics, alarms, dashboards, Logs Insights queries, metric filters and Contributor Insights (which has built-in sample rules for VPC flow logs, for top talkers).
  • VPC, Transit Gateway and Cloud WAN flow logs to CloudWatch Logs, S3 (text or Parquet) or Firehose; query S3 copies with Athena.
  • Traffic Mirroring for full packets to an analysis appliance.

Field lists, limitations and delivery times are on Task 1.4.

Knowledge 3.2.4Tools to analyze routing patterns and issues (for example, Reachability Analyzer, Transit Gateway Network Manager)

  • Reachability Analyzer: configuration analysis from a source to a destination through routes, security groups, ACLs, gateways and Transit Gateway route tables, naming the blocking component. TCP or UDP, IPv4, $0.10 per analysis.
  • Network Access Analyzer: finds every path matching a scope you define (unintended access), $0.002 per interface analyzed.
  • Network Manager: topology and events for Transit Gateways and Cloud WAN, and Route Analyzer for Transit Gateway route tables only.

Analyzing flow logs

Skill 3.2.1Analyzing tool output to assess network performance and troubleshoot connectivity (for example, VPC Flow Logs, Amazon CloudWatch Logs)

Reading records

Two default-format records for one ping to a booking server: the request is accepted, the reply is rejected 
2 444444444444 eni-0booking01 10.100.20.5 10.40.12.30 0 0 1 4 336 1763200000 1763200060 ACCEPT OK
2 444444444444 eni-0booking01 10.40.12.30 10.100.20.5 0 0 1 4 336 1763200000 1763200060 REJECT OK
  • ACCEPT in, REJECT out for the same flow means a stateless network ACL blocked the reply (a security group would have let it out automatically). A single REJECT means the inbound rule (security group or ACL) denied the request.
  • tcp-flags (v3 and later): SYN 2, SYN-ACK 18, FIN 1, RST 4, OR-ed over the interval (19 = SYN-ACK plus FIN); ACK and PSH alone show 0. Many SYN records with no SYN-ACK point to a dropped reply or an unreachable server.
  • pkt-srcaddr and pkt-dstaddr show the original addresses: on a NAT gateway's interface, dstaddr is the NAT gateway and pkt-dstaddr the internet host; on a Transit Gateway interface, srcaddr is the Transit Gateway and pkt-srcaddr the client.
  • traffic-path (egress only): 1 same VPC, 2 internet or gateway endpoint, 3 VGW, 4 same-Region peering, 5 inter-Region peering, 6 Local Zone or Wavelength, 7 gateway endpoint, 8 internet gateway.
  • log-status NODATA (no traffic in the interval) or SKIPDATA (records skipped because of capacity or an error). Flow logs never show traffic to the Amazon DNS server, metadata, Time Sync, DHCP or ARP.

CloudWatch Logs Insights

Top talkers, and the sources rejected most often on a booking interface (CloudWatch Logs Insights) 
stats sum(bytes) as bytesTransferred by srcAddr, dstAddr
| sort bytesTransferred desc
| limit 15

filter interfaceId = "eni-0booking01" and action = "REJECT"
| stats count(*) as rejects by srcAddr, dstPort
| sort rejects desc
| limit 20

Athena

For flow logs in S3, the console's Generate Athena integration (or get-flow-logs-integration-template) builds a CloudFormation stack with a database, a partitioned table, a Lambda function that adds partitions on a schedule, and named queries such as top talkers, rejected TCP traffic and SSH/RDP traffic. Or create the table yourself with partition projection.

Rejected TCP traffic to the booking subnet over the last day (Athena SQL on a flow log table) 
SELECT srcaddr, dstaddr, dstport, SUM(packets) AS packets
FROM vpc_flow_logs
WHERE action = 'REJECT'
  AND protocol = 6
  AND dstaddr LIKE '10.40.12.%'
  AND day >= date_format(current_date - interval '1' day, '%Y/%m/%d')
GROUP BY srcaddr, dstaddr, dstport
ORDER BY packets DESC
LIMIT 20;

Column names are the field names with underscores (pkt_srcaddr); quote reserved words such as end. Parquet output with hourly partitions makes these queries faster and cheaper.

Mapping topology

Skill 3.2.2Mapping or understanding network topology (for example, Transit Gateway Network Manager)

Register each Region's Transit Gateway in a global network (home Region us-west-2, no extra charge), and add on-premises sites, devices and links with customer gateway associations. Network Manager then shows:

  • A topology tree (Transit Gateways, attachments, VPNs, Direct Connect gateways, Connect peers) and a geographic topology map.
  • Events: topology changes, route installs and withdrawals, and VPN and Connect BGP status, also sent to EventBridge in us-west-2.
  • Transit Gateway and VPN metrics on dashboards, across accounts in the organization once trusted access is enabled.
  • Route Analyzer paths between Transit Gateway attachments, including across Transit Gateway peering, with the return path.
Register the Frankfurt Transit Gateway and trace the route from the European data center's VPN to a booking VPC (AWS CLI, us-west-2) 
aws networkmanager register-transit-gateway --region us-west-2 \
  --global-network-id global-network-0travel1234567 \
  --transit-gateway-arn arn:aws:ec2:eu-central-1:111111111111:transit-gateway/tgw-eu

aws networkmanager start-route-analysis --region us-west-2 \
  --global-network-id global-network-0travel1234567 \
  --source TransitGatewayAttachmentArn=arn:aws:ec2:eu-central-1:111111111111:transit-gateway-attachment/tgw-attach-eu-dc1-vpn,IpAddress=10.200.5.10 \
  --destination TransitGatewayAttachmentArn=arn:aws:ec2:eu-central-1:111111111111:transit-gateway-attachment/tgw-attach-bookings-eu,IpAddress=10.44.8.20 \
  --include-return-path

Cloud WAN networks show segments and edges in the same console, and Cloud WAN flow logs (November 2026) add segment and Region fields for traffic analysis.

Analyzing packets

Skill 3.2.3Analyzing packets to identify issues in packet shaping (for example, VPC Traffic Mirroring)

Traffic Mirroring copies packets from a source interface, encapsulated in VXLAN on UDP 4789, to an interface, a Network Load Balancer (UDP 4789 listener) or a Gateway Load Balancer endpoint running a packet analyzer, IDS or capture tool.

  • Filters: up to 10 rules each for inbound and outbound, lowest number first, accept or reject by protocol, ports and CIDRs. No rules means nothing is mirrored; no outbound rules means no outbound traffic is mirrored.
  • Sessions: source, filter and target, with a session number 1–32,766 (lowest first; each packet is mirrored once, so several sessions can split traffic between tools), an optional VNI, and an optional packet length to keep only headers. Up to 3 sessions per source interface.
  • Overhead: VXLAN adds 54 bytes (IPv4), so mirrored jumbo packets may be truncated; production traffic has priority and skipped packets show in NetworkSkipMirrorIn and NetworkSkipMirrorOut.
  • What you see: inbound packets dropped by the source's security group or ACL are not mirrored; mirrored outbound traffic ignores the source's outbound rules. Identify sources by the outer source IP, not the VNI.
  • Sources are interfaces on a listed set of instance types; billing is per session-hour (about $0.015) until the session is deleted.
Mirror only HTTPS to and from a partner gateway instance, first 128 bytes of each packet, to the analysis NLB (AWS CLI) 
aws ec2 create-traffic-mirror-target \
  --network-load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:111111111111:loadbalancer/net/mirror-nlb/0a1b2c3d4e5f6a7b

aws ec2 create-traffic-mirror-filter --description "partner-https"
aws ec2 create-traffic-mirror-filter-rule --traffic-mirror-filter-id tmf-0partnerhttps1 \
  --traffic-direction ingress --rule-number 100 --rule-action accept --protocol 6 \
  --destination-port-range FromPort=443,ToPort=443 \
  --source-cidr-block 0.0.0.0/0 --destination-cidr-block 0.0.0.0/0
aws ec2 create-traffic-mirror-filter-rule --traffic-mirror-filter-id tmf-0partnerhttps1 \
  --traffic-direction egress --rule-number 100 --rule-action accept --protocol 6 \
  --source-port-range FromPort=443,ToPort=443 \
  --source-cidr-block 0.0.0.0/0 --destination-cidr-block 0.0.0.0/0

aws ec2 create-traffic-mirror-session \
  --network-interface-id eni-0partnergw01 \
  --traffic-mirror-target-id tmt-0mirrornlb001 \
  --traffic-mirror-filter-id tmf-0partnerhttps1 \
  --session-number 1 --packet-length 128 --virtual-network-id 4001

Recognizing shaping

When an instance exceeds its bandwidth, packets-per-second or connection-tracking allowance, EC2 queues and then drops packets. The ENA *_allowance_exceeded counters rising show the instance is being shaped; mirrored captures show the effect as retransmissions, duplicate ACKs and shrinking windows. The fix is a larger or network-optimized instance, more instances, ENA Express, or fewer tracked connections (for example untracked security group rules or longer-lived connections).

Troubleshooting and verifying design

Skill 3.2.4Troubleshooting connectivity issues that are caused by network misconfiguration (for example, Reachability Analyzer)

Create a path (source, destination or destination IP, protocol, port), run an analysis, and read the explanation codes. Common findings:

  • NO_ROUTE_TO_DESTINATION, MORE_SPECIFIC_ROUTE: a subnet route table is missing or overridden.
  • ENI_SG_RULES_MISMATCH, SUBNET_ACL_RESTRICTION: a security group or ACL blocks the port.
  • TGW_RTB_NO_ROUTE_TO_TGW_ATTACHMENT, TGW_ATTACH_MISSING_TGW_RTB_ASSOCIATION: Transit Gateway association or propagation missing.
  • TGW_ROUTE_AZ_RESTRICTION: the destination VPC's attachment has no subnet in the source AZ.
  • NGW_REQUIRES_SOURCE_IN_VPC: traffic from a VPN, Direct Connect or peering cannot use the NAT gateway.
  • ENI_SOURCE_DEST_CHECK_RESTRICTION: an appliance with the source/destination check on.
  • VPC_BLOCK_PUBLIC_ACCESS_ENABLED: blocked by account-level Block Public Access.

Reachability Analyzer never sends packets: when it says the path is reachable but traffic still fails, look at the data plane (flow logs, MTU, the appliance, the on-premises side).

Skill 3.2.5Verifying that a network configuration meets network design requirements (for example, Reachability Analyzer)

  • Reachability Analyzer proves required paths work: for example the booking app to the data center database on TCP 1433, and the internet to the public ALB on 443.
  • Network Access Analyzer proves forbidden paths do not exist: scopes with match paths (violations) and exclude paths (allowed exceptions), for example "no path from the internet to the card-data subnets" or "development cannot reach production". Amazon-created scopes cover internet gateway ingress and egress and VPC ingress and egress. It analyzes one account and Region at a time.
  • Use both, because one checks that required access exists and the other that nothing else does.
A Network Access Analyzer scope: any path from an internet gateway to an interface tagged data-class=card is a finding (AWS CLI) 
aws ec2 create-network-insights-access-scope --match-paths '[{
  "Source": {"ResourceStatement": {"ResourceTypes": ["AWS::EC2::InternetGateway"]}},
  "Destination": {"ResourceStatement": {
    "ResourceTypes": ["AWS::EC2::NetworkInterface"]}}
}]' --tag-specifications 'ResourceType=network-insights-access-scope,Tags=[{Key=Name,Value=no-internet-to-card}]'

aws ec2 start-network-insights-access-scope-analysis \
  --network-insights-access-scope-id nis-0nointernetcard1

aws ec2 get-network-insights-access-scope-analysis-findings \
  --network-insights-access-scope-analysis-id nisa-0a1b2c3d4e5f67890

Narrow the destination to the card-data interfaces with a resource or tag condition in the real scope; the shape above shows the structure.

Automating intent verification

Skill 3.2.6Automating the verification of connectivity intent as a network configuration changes (for example, Reachability Analyzer)

  1. On every changeAn EventBridge rule matches CloudTrail events for security group and route changes and runs a Lambda function that re-runs the saved Reachability Analyzer paths for the affected resources and alerts through SNS on failure.
  2. In the pipelineAfter deploying to a test environment, a Step Functions workflow runs the paths a template declares (AWS's "IaC Network Tester" sample) and fails the pipeline before production if any are unreachable.
  3. On a scheduleEventBridge Scheduler runs Network Access Analyzer scopes (for example every 12 hours) and sends findings to Security Hub.
Event pattern for configuration changes that should trigger re-analysis (EventBridge rule, JSON) 
{
  "source": ["aws.ec2"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["ec2.amazonaws.com"],
    "eventName": [
      "AuthorizeSecurityGroupIngress", "RevokeSecurityGroupIngress",
      "ModifySecurityGroupRules", "CreateRoute", "ReplaceRoute", "DeleteRoute",
      "ReplaceNetworkAclEntry", "CreateNetworkAclEntry"
    ]
  }
}
The Lambda function re-runs every saved path tagged critical=true and reports failures (Python) 
import time, boto3

ec2 = boto3.client("ec2")
sns = boto3.client("sns")
TOPIC = "arn:aws:sns:us-east-1:111111111111:network-intent"

def handler(event, context):
    paths = ec2.describe_network_insights_paths(
        Filters=[{"Name": "tag:critical", "Values": ["true"]}])["NetworkInsightsPaths"]
    runs = [ec2.start_network_insights_analysis(
                NetworkInsightsPathId=p["NetworkInsightsPathId"])
            ["NetworkInsightsAnalysis"]["NetworkInsightsAnalysisId"] for p in paths]

    while True:   # up to 100 analyses can run at once
        results = ec2.describe_network_insights_analyses(
            NetworkInsightsAnalysisIds=runs)["NetworkInsightsAnalyses"]
        if all(r["Status"] != "running" for r in results):
            break
        time.sleep(10)

    broken = [r["NetworkInsightsPathId"] for r in results if not r.get("NetworkPathFound")]
    if broken:
        sns.publish(TopicArn=TOPIC, Subject="Connectivity intent broken",
                    Message="Unreachable paths after %s: %s"
                            % (event["detail"]["eventName"], ", ".join(broken)))

Quotas allow 1,000 saved paths and 100 concurrent analyses; at $0.10 per analysis, run only the paths that the change can affect when volumes are high.

Packet size mismatches

Skill 3.2.7Troubleshooting packet size mismatches in a VPC to restore network connectivity

Symptoms

The TCP handshake and small requests work, but large transfers or responses hang; SSH connects but scp stalls; queries with large results time out; UDP applications lose large datagrams. Transit Gateway flow logs show packets-lost-mtu-exceeded.

Find the path MTU

Check the interface MTU, trace the path MTU to the partner, and set 1500 when the path needs it (Linux on EC2) 
ip link show eth0              # shows "mtu 9001" on most current instances
tracepath partner-api.example.net
#  1?: [LOCALHOST]   pmtu 9001
#  ...               pmtu 1500
#      Resume: pmtu 1500

sudo ip link set dev eth0 mtu 1500
# Persist on Amazon Linux 2023: MTUBytes=1500 in the [Link] section of a
# systemd-networkd file for the interface

If tracepath targets another instance, its security group must allow the inbound UDP probes.

Let Path MTU Discovery work

  • Network ACLs must allow ICMP type 3 code 4 ("destination unreachable, fragmentation needed") inbound and outbound (and type 11 code 0 for traceroute).
  • Security groups let the ICMP replies through when the connection is tracked (or untracked), or when inbound ICMP is allowed; an ACL deny still blocks them.
  • Global Accelerator endpoints must allow ICMP for Path MTU Discovery, and Global Accelerator drops TCP fragments at the edge.
Allow "fragmentation needed" through the booking subnets' network ACL in both directions (AWS CLI) 
aws ec2 create-network-acl-entry --network-acl-id acl-0booking01 \
  --ingress --rule-number 90 --protocol 1 --icmp-type-code Type=3,Code=4 \
  --cidr-block 0.0.0.0/0 --rule-action allow

aws ec2 create-network-acl-entry --network-acl-id acl-0booking01 \
  --egress --rule-number 90 --protocol 1 --icmp-type-code Type=3,Code=4 \
  --cidr-block 0.0.0.0/0 --rule-action allow

Fix by path

  • Internet: 1500 maximum; set 1500 on instances that talk mostly to the internet, or set MTU per route, or use separate interfaces for internal jumbo traffic.
  • VPN: no Path MTU Discovery; clamp TCP MSS (1406 or lower depending on algorithms) and fragment before encryption on the customer gateway; keep UDP payloads small.
  • VPC peering to Transit Gateway migration: 9001 becomes 8500; change both VPCs at the same time, or asymmetric jumbo packets are dropped. The travel company's broken large responses were this: one side still sent 9001-byte packets back through the old peering.
  • Endpoints, Gateway Load Balancer and Lattice: 8500 with no Path MTU Discovery; Gateway Load Balancer appliances need an MTU of at least 8568 for GENEVE.
  • Direct Connect: set the same MTU on every VIF and on-premises device on the path; mixed advertisements fall back to 1500. Changing a VIF's MTU interrupts the connection briefly.

"Small packets work, large ones fail, only through the VPN or endpoint" is MTU, not security groups. Look for a path without Path MTU Discovery (VPN, VPC endpoints, Gateway Load Balancer, Transit Gateway VPN or Direct Connect attachments) or an ACL blocking ICMP type 3 code 4.

Key takeaways

  • MTU: 9001 in a VPC and same-Region peering; 8500 inter-Region peering, Transit Gateway, NAT gateway, endpoints, Gateway Load Balancer, Lattice; 1500 internet and VPN attachment; 1446 inside a VPN tunnel.
  • Path MTU Discovery works through NAT gateways and Transit Gateway VPC and Connect attachments; not through VPN, endpoints, Gateway Load Balancer, or Transit Gateway VPN, Direct Connect and peering attachments. MSS clamping saves most TCP.
  • Loss shows in ENA allowance counters, Transit Gateway drop metrics and packets-lost fields, NAT port errors, flow log REJECTs, hybrid link metrics, and Synthetic Monitor loss.
  • Flow logs: ACCEPT in plus REJECT out means a network ACL; tcp-flags SYN 2, SYN-ACK 18, FIN 1, RST 4; pkt-srcaddr and pkt-dstaddr behind NAT and Transit Gateway; traffic-path egress only. Query with Logs Insights or Athena (generated integration, partitions).
  • Topology: register Transit Gateways in a global network (us-west-2); topology tree and map, events, Route Analyzer for Transit Gateway routes.
  • Traffic Mirroring: VXLAN 4789 to an interface, NLB or Gateway Load Balancer endpoint; ordered filters (empty means nothing); sessions 1–32,766, 3 per source, truncation; production traffic wins.
  • Reachability Analyzer for required paths and misconfiguration codes; Network Access Analyzer for forbidden paths; automate both on CloudTrail changes, in pipelines and on schedules.
  • Packet size fixes: tracepath, set MTU, allow ICMP 3/4 in ACLs both ways, clamp MSS on VPNs, change both sides when moving from peering to Transit Gateway.
