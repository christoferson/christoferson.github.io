Overview

Task 4.1

Implement and maintain network features to meet security and compliance needs and requirements.

Domain 4 is 24% of the exam. This task asks which control belongs on which flow: WAF and Shield at the edge, Network Firewall or a proxy for egress, security groups and endpoint policies between VPCs, and GuardDuty with EventBridge for detection. Many questions turn on a limit or default, such as WAF inspecting only the first 8 KB of an ALB request body, or Shield Advanced protecting nothing until you add resources.

The travel company processes card payments, so its booking platform falls under PCI DSS: public traffic enters through CloudFront and ALBs with WAF and Shield Advanced, card-data subnets are isolated, egress is filtered, and the security team wants alerts within minutes.

Threat models and threats

Knowledge 4.1.1Different threat models based on application architecture

A threat model depends on what the architecture exposes. A public web application faces DDoS, injection and bots at the edge; an internal microservice platform faces lateral movement and data exfiltration; a hybrid network adds the on-premises and partner networks as less trusted zones; a SaaS provider must isolate tenants. The AWS Well-Architected security pillar (SEC01-BP07) asks for a threat model for every workload and treats its absence as high risk.

Knowledge 4.1.2Common security threats

Threats and the matching control

  • DDoS: volumetric and reflection (UDP, DNS, NTP, SSDP, memcached), protocol (SYN and ACK floods), and application (HTTP request floods). Shield, CloudFront, Global Accelerator and Route 53 at the edge; WAF rate-based rules and the Anti-DDoS rule group; Auto Scaling behind load balancers.
  • Injection and web exploits (SQL injection, cross-site scripting, file inclusion, SSRF): WAF managed rule groups.
  • Bots, credential stuffing and fake accounts: WAF Bot Control, account takeover (ATP) and account creation fraud (ACFP) rule groups, CAPTCHA and Challenge.
  • Scanning and brute force: security groups, and GuardDuty findings such as Recon:EC2/Portscan and UnauthorizedAccess:EC2/SSHBruteForce.
  • Data exfiltration, including DNS tunneling: egress filtering, DNS Firewall, endpoint policies, GuardDuty Trojan:EC2/DNSDataExfiltration.
  • Lateral movement: segmentation with security groups, ACLs, Transit Gateway route tables and inspection.
  • Interception (man in the middle): TLS everywhere, IPsec or MACsec on hybrid links (Task 4.3).
  • Spoofing: EC2 checks that an instance is the source or destination of its traffic unless you turn the check off for an appliance.

Skill 4.1.5Developing a threat model and identifying appropriate mitigation strategies for a given network architecture

AWS's guidance follows four questions:

  1. What are we working on?Draw the data flows: users to CloudFront, CloudFront to the ALB, the ALB to the booking service, the service to the card-data database, the data centers over Direct Connect, partners through PrivateLink. Mark trust boundaries.
  2. What can go wrong?Walk each flow through STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege), plus the OWASP Top 10 for the web tier.
  3. What are we going to do about it?Pick a mitigation per threat, decide who owns it (AWS or you, under the shared responsibility model), and prioritize by risk.
  4. Did we do a good job?Test the mitigations (below) and revisit the model when the architecture changes.

Threat Composer, an open-source AWS tool, records threats in a standard grammar, links them to mitigations, and keeps the model as code next to the templates.

Secure architectures

Knowledge 4.1.3Mechanisms to secure different application flows

  • Internet to application: CloudFront and Shield at the edge, WAF on CloudFront or the ALB, the ALB in public subnets, instances in private subnets, origin access locked to CloudFront.
  • Application to internet: NAT gateways behind Network Firewall or a proxy, DNS Firewall, no public IPs on workloads.
  • East-west: security group references between tiers, ACLs as guardrails, Transit Gateway route tables and inspection between VPCs.
  • Workload to AWS services: VPC endpoints with endpoint policies; bucket and key policies that require them.
  • Hybrid: encrypted links, on-premises firewalls, inspection of traffic from the data centers.
  • Users: Client VPN or Verified Access with identity and device checks.

Knowledge 4.1.4AWS network architecture that meets security and compliance requirements

Compliance frameworks (PCI DSS, HIPAA, FedRAMP) ask for segmentation, restricted inbound and outbound access, encryption, logging and regular testing. On AWS that means: a small, isolated scope for regulated data (its own VPC or account), Network Access Analyzer proof that no unintended path reaches it, flow logs and WAF logs retained centrally, Encryption Controls and TLS for data in transit, and Firewall Manager and Config rules to keep it that way. Security Hub CSPM controls (for example VPC Block Public Access and Network Firewall settings) report drift.

Skill 4.1.4Implementing an AWS network architecture to meet security and compliance requirements (for example, untrusted network, perimeter VPC, three-tier architecture)

Three-tier

Web (public subnets with only load balancers), application (private subnets) and data (isolated subnets with no internet route) in each AZ. Security groups chain the tiers: the ALB group allows 443 from anywhere; the app group allows only the ALB group; the database group allows only the app group. ACLs add coarse subnet guardrails.

Perimeter (ingress) VPC

All internet traffic enters one VPC that holds the public load balancers, WAF and inspection (Network Firewall or Gateway Load Balancer appliances), then reaches application VPCs over the Transit Gateway; application VPCs have no internet gateways. AWS's centralized inbound inspection guidance pairs WAF for HTTP inspection with IDS/IPS through Gateway Load Balancer or Network Firewall. Note that WAF does not log request bodies.

Untrusted networks

Treat the internet, partner networks and often on premises as untrusted: terminate them in dedicated VPCs or Transit Gateway route tables, inspect traffic before it reaches workloads, and expose services to partners with PrivateLink rather than routing.

The travel company runs the card-data tier in its own account and VPC, reachable only from the payment service through the inspection firewall, with VPC Block Public Access on and a Network Access Analyzer scope proving no internet path exists.

Inbound traffic

Skill 4.1.1Securing inbound traffic flows into AWS (for example, AWS WAF, AWS Shield, Network Firewall)

AWS WAF

  • Where: CloudFront (web ACL created in us-east-1, global scope), ALB, API Gateway REST APIs, AppSync, Cognito user pools, App Runner, Verified Access, Amplify (global scope) and Bedrock AgentCore Gateway. Not NLBs, HTTP APIs or EC2 directly. One web ACL per resource; a CloudFront web ACL cannot also be used on regional resources. The new console calls a web ACL a "protection pack".
  • Rules: managed rule groups (Core rule set, Known bad inputs, SQL database, Linux, Windows, PHP, WordPress, Amazon IP reputation, Anonymous IP list), your own rules on IP sets, geography, headers, body, regex and labels, and rate-based rules.
  • Actions: Allow, Block (403 or a custom response), Count, CAPTCHA, Challenge, and (CloudFront only) Monetize, which returns HTTP 402 to AI bots. The web ACL's default action is Allow or Block.
  • Rate-based rules: a limit from 10 requests per window of 60, 120, 300 (default) or 600 seconds, keyed by IP, forwarded IP, or up to 5 custom keys (headers, cookies, URI, JA3/JA4, ASN and more); any action except Allow.
  • Capacity: 1,500 WCU included per web ACL, up to 5,000 at extra cost. The core rule set alone uses 700.
  • Body inspection: only the first 8 KB on ALB and AppSync; 16 KB by default (up to 64 KB, at extra cost) on CloudFront, API Gateway, Cognito, App Runner and Verified Access. The core rule set blocks bodies over 8 KB, which can break uploads; scope it down or override that rule.
  • Logs to CloudWatch Logs (log group must start with aws-waf-logs-), S3 or Firehose.
  • Price: $5 per web ACL and $1 per rule per month, plus $0.60 per million requests; Bot Control and fraud rule groups cost more. WAF Classic is being retired.
Web ACL for the booking ALB: core rules, known bad inputs, IP reputation, and a rate limit per client IP (AWS CLI with a rules file)

DDoS protection

Shield Standard

Free and automatic for every customer against common layer 3 and 4 attacks; strongest on CloudFront, Route 53 and Global Accelerator, which absorb attacks at the edge (SYN cookies, scale).

Shield Advanced

  • $3,000 per month per organization (payer account), one-year commitment, plus data transfer fees. You must add protections to resources (CloudFront, Route 53 zones, Global Accelerator, Elastic IPs, ALB and CLB; NLBs through Elastic IPs) yourself or with Firewall Manager.
  • Includes WAF for protected resources (up to 1,500 WCU), the Shield Response Team (with Business or Enterprise Support), proactive engagement (needs Route 53 health checks on the resources), health-based detection, protection groups, attack metrics in AWS/DDoSProtection (DDoSDetected), and cost protection credits for scaling caused by an attack (the resource must be protected beforehand, with a blocking rate-based rule on CloudFront or ALB, and the request made within 15 days after the billing month).

Layer 7 floods

The WAF Anti-DDoS managed rule group (AWSManagedRulesAntiDDoSRuleSet, June 2025, 50 WCU) baselines traffic, detects HTTP floods in seconds and challenges or blocks suspicious requests. Since March 2026 it is the default HTTP flood protection and supersedes Shield Advanced's automatic layer 7 mitigation, which existing customers can still use. Place it near the top of the web ACL.

Subscribe to Shield Advanced and protect the booking distribution (AWS CLI) 
aws shield create-subscription

aws shield create-protection --name booking-cloudfront \
  --resource-arn arn:aws:cloudfront::444444444444:distribution/E2BOOKING12345

# Required for proactive engagement: a health check for the protected resource
aws shield associate-health-check \
  --protection-id a1b2c3d4-5678-90ab-cdef-EXAMPLE11111 \
  --health-check-arn arn:aws:route53:::healthcheck/0f0e0d0c-aaaa-bbbb-cccc-444455556666

Network Firewall for inbound

For non-HTTP traffic or IPS signatures, route inbound internet traffic through firewall endpoints with an internet gateway edge route table, or inspect centrally in the perimeter VPC (Task 2.2).

Outbound traffic

Skill 4.1.2Securing outbound traffic flows from AWS (for example, Network Firewall, proxies, Gateway Load Balancers)

  • Network Firewall in the egress path (centralized egress VPC or Transit Gateway-attached firewall): domain allow lists on TLS SNI and HTTP Host, Suricata rules, URL category filtering, TLS inspection where policy allows, strict rule order with "drop established" as the default.
  • Forward proxies (a Squid fleet behind an NLB, or the Network Firewall proxy in preview) when applications can be configured with a proxy and you need URL-level control or user authentication.
  • Gateway Load Balancer with third-party next-generation firewalls when the organization standardizes on a vendor.
  • DNS Firewall blocks lookups of known bad or unapproved domains, stopping DNS tunneling that IP filtering misses; Network Firewall's Route 53 resolved IP validation (October 2026) checks that connections go to the IPs DNS actually returned.
  • No direct paths: no public IPs on workloads, VPC Block Public Access, and SCPs that stop teams creating internet gateways.

Configuration is on Task 2.2.

Inter-VPC traffic

Skill 4.1.3Securing inter-VPC traffic within an account or across multiple accounts (for example, security groups, network ACLs, VPC endpoint policies)

  • Security groups: reference groups across same-Region peering and (inbound) across one Transit Gateway; use shared security groups in shared VPCs; otherwise prefix lists of the other VPC's ranges.
  • Network ACLs: deny lists between environments and an immediate kill switch.
  • Routing: no route means no access; Transit Gateway route tables and blackholes separate environments.
  • Inspection: east-west through Network Firewall where the threat model requires it.

VPC endpoint policies and the data perimeter

An endpoint policy is a resource policy on the endpoint that limits what can be done through it; it never grants permissions that IAM or resource policies deny. Gateway endpoint policies must use "Principal": "*" (narrow with conditions), the size limit is 20,480 characters, and calls to services in another Region do not pass through the endpoint, so its policy does not apply to them. AWS's data perimeter guidance combines:

  • Trusted identities: only principals from your organization (aws:PrincipalOrgID) through your endpoints.
  • Trusted resources: only resources in your organization (aws:ResourceOrgID), so data cannot be copied to someone else's bucket.
  • Expected networks: resource policies that require your endpoints (aws:SourceVpce, aws:SourceVpc).
S3 gateway endpoint policy: only the travel company's principals, only the travel company's buckets (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "OrgPrincipalsToOrgBucketsOnly",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": "*",
    "Condition": {
      "StringEquals": {
        "aws:PrincipalOrgID": "o-travel1234",
        "aws:ResourceOrgID": "o-travel1234"
      }
    }
  }]
}
Card-data bucket policy: refuse any request that does not arrive through the payment VPC's endpoint (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "OnlyThroughPaymentEndpoint",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": ["arn:aws:s3:::travel-card-data", "arn:aws:s3:::travel-card-data/*"],
    "Condition": {"StringNotEquals": {"aws:SourceVpce": "vpce-0paymentss3gw01"}}
  }]
}

aws:SourceVpce takes the endpoint ID, not an ARN, and aws:SourceIp never matches traffic through an endpoint (use aws:VpcSourceIp). A deny like the one above also blocks console access to the bucket; keep a break-glass exception.

Testing compliance

Skill 4.1.6Testing compliance with the initial requirements (for example, failover test, resiliency)

  • Connectivity intent: Reachability Analyzer for paths that must work and Network Access Analyzer for paths that must not, run automatically (Task 3.2).
  • Hybrid failover: the Direct Connect BGP failover test, or Fault Injection Service aws:directconnect:virtual-interface-disconnect.
  • Fault Injection Service network actions:
    • aws:network:disrupt-connectivity: blocks traffic for subnets by swapping in a cloned ACL (scope all, AZ, S3, DynamoDB, prefix list or VPC), for up to 12 hours.
    • aws:network:route-table-disrupt-cross-region-connectivity and aws:network:transit-gateway-disrupt-cross-region-connectivity: simulate losing another Region.
    • aws:network:disrupt-vpc-endpoint: makes interface endpoints unreachable.
  • Security controls: WAF rules in Count mode before blocking, controlled DDoS tests within AWS's simulated event policy, penetration tests on permitted services, and Firewall Manager and Security Hub CSPM compliance reports.

Automated incident alerting

Skill 4.1.7Automating security incident reporting and alerting using AWS

Detection sources

  • GuardDuty analyzes VPC flow logs, DNS query logs and CloudTrail from its own independent copy, so you do not need to enable flow logs for it. It cannot see DNS sent to non-AWS resolvers (it raises DefenseEvasion:EC2/UnusualDNSResolver instead). Network findings include port scans, brute force (SSH on port 22 only), DoS from instances, crypto-mining, command and control, and DNS exfiltration. Extended Threat Detection (December 2024) adds critical attack-sequence findings.
  • Security Hub CSPM (the former Security Hub) runs standards and controls, including network controls such as Block Public Access and Network Firewall settings; the new AWS Security Hub (GA December 2025) correlates findings and shows attack paths.
  • Amazon Detective investigates a finding using a graph of flow logs and CloudTrail.
  • Metrics: Shield DDoSDetected, WAF blocked requests, Network Firewall alerts, Network Manager events.

Routing and response

GuardDuty findings arrive in EventBridge (source aws.guardduty, detail type GuardDuty Finding) in the administrator account for the whole organization. New findings arrive in near real time; updates to existing ones every 6 hours by default (15 minutes at the shortest). Findings archived by suppression rules are not sent. A rule sends high-severity network findings to SNS for paging and to a Lambda function or Step Functions workflow that blocks the attacker (an ACL deny entry, a WAF IP set, or a Network Firewall rule) and isolates the instance.

Page the security team and trigger containment for high-severity EC2 network findings (EventBridge event pattern, JSON) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{"numeric": [">=", 7]}],
    "type": [
      {"prefix": "UnauthorizedAccess:EC2/"},
      {"prefix": "Backdoor:EC2/"},
      {"prefix": "Trojan:EC2/"}
    ]
  }
}
Alarm on any DDoS event detected against the protected distribution (AWS CLI, us-east-1) 
aws cloudwatch put-metric-alarm --region us-east-1 \
  --alarm-name booking-ddos-detected \
  --namespace AWS/DDoSProtection --metric-name DDoSDetected \
  --dimensions Name=ResourceArn,Value=arn:aws:cloudfront::444444444444:distribution/E2BOOKING12345 \
  --statistic Maximum --period 60 --evaluation-periods 1 \
  --threshold 0 --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:444444444444:security-oncall

Shield metrics for CloudFront, Route 53 and protection groups exist only in us-east-1. Use suppression rules or trusted IP lists for expected activity such as a vulnerability scanner, so real findings stand out.

Key takeaways

  • Threat modeling: four questions (what are we building, what can go wrong, what will we do, did we do a good job), STRIDE per data flow, Threat Composer; a missing model is high risk in Well-Architected.
  • Architectures: three-tier subnets chained by security groups; a perimeter VPC with WAF and inspection in front of application VPCs; untrusted networks terminated and inspected; regulated data isolated and proven unreachable.
  • WAF: on CloudFront (us-east-1), ALB, API Gateway REST, AppSync, Cognito, App Runner, Verified Access, Amplify; 1,500 WCU included (5,000 max); rate rules from 10 requests per 60–600 seconds; ALB body inspection 8 KB; logs to aws-waf-logs- groups.
  • Shield Standard is free; Shield Advanced ($3,000 per month) protects only resources you add, with SRT, proactive engagement (Route 53 health checks), health-based detection and cost protection; the Anti-DDoS rule group is now the default layer 7 flood defense.
  • Outbound: Network Firewall domain filtering, proxies, Gateway Load Balancer vendor firewalls, DNS Firewall, no public IPs.
  • Inter-VPC: security group references, ACLs, route tables, inspection; endpoint policies with aws:PrincipalOrgID and aws:ResourceOrgID, and resource policies requiring aws:SourceVpce.
  • Testing: Reachability and Network Access Analyzer, Direct Connect failover tests, Fault Injection Service network actions with stop conditions.
  • Alerting: GuardDuty (no flow logs needed) to EventBridge to SNS and automated containment; Security Hub CSPM controls; Shield DDoSDetected alarms in us-east-1 for CloudFront.
