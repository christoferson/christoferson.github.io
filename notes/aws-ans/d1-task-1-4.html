Overview

Task 1.4

Define logging and monitoring requirements across AWS and hybrid networks.

A network you cannot see is a network you cannot troubleshoot, secure or size. This task asks which AWS tool answers which question: is a path configured correctly, did packets actually flow, which talker is using the bandwidth, is the Direct Connect link degrading, are users on one internet provider having trouble, and what does normal look like. Many questions hinge on a tool's limits, for example that Reachability Analyzer never sends packets, or that flow logs do not record queries to the Amazon DNS server.

The travel company needs to watch Direct Connect and VPN links to two data centers, Transit Gateways in three Regions, NAT gateways, load balancers and CloudFront, centralize logs from all accounts, and prove to auditors that card-data networks cannot reach the internet.

CloudWatch for network visibility

Knowledge 1.4.1Amazon CloudWatch metrics, agents, logs, alarms, dashboards, and insights in AWS architectures to provide visibility

Metrics

A metric is a namespace (such as AWS/NATGateway), a name and dimensions. AWS services publish at 1-minute resolution (EC2 basic monitoring at 5 minutes); custom metrics can be high resolution (1 second). Data is kept for 15 days at 1 minute, 63 days at 5 minutes and 15 months at 1 hour. Metrics are Regional, and some are published in one Region only: Route 53 health checks and CloudFront in us-east-1, Global Accelerator in us-west-2. Percentile statistics (p90, p99) describe latency better than averages.

The CloudWatch agent and ENA allowance metrics

Instances can drop packets because they exceed their own network allowances, which no AWS metric shows. The ENA driver counts these drops, and the CloudWatch agent's ethtool plugin publishes them (namespace CWAgent, prefixed ethtool_):

  • bw_in_allowance_exceeded and bw_out_allowance_exceeded: aggregate bandwidth over the instance maximum.
  • pps_allowance_exceeded: packets per second over the maximum.
  • conntrack_allowance_exceeded and conntrack_allowance_available: connection tracking limits.
  • linklocal_allowance_exceeded: the 1,024 packets-per-second limit to the Amazon DNS server, instance metadata and Time Sync.

The counters are cumulative, so alarm on RATE() metric math, not raw values.

CloudWatch agent configuration to publish ENA allowance counters (JSON) 
{
  "metrics": {
    "metrics_collected": {
      "ethtool": {
        "interface_include": ["eth0"],
        "metrics_include": [
          "bw_in_allowance_exceeded",
          "bw_out_allowance_exceeded",
          "pps_allowance_exceeded",
          "conntrack_allowance_exceeded",
          "linklocal_allowance_exceeded"
        ]
      }
    }
  }
}

Logs

CloudWatch Logs stores flow logs, Resolver query logs, VPN tunnel logs, WAF logs and others. Metric filters turn matching log lines into metrics you can alarm on; subscription filters (up to five per log group) stream logs in near real time to Kinesis, Firehose, Lambda or OpenSearch; Logs Insights queries logs interactively.

Top talkers through a NAT gateway from VPC flow logs (Logs Insights; replace the addresses) 
filter (dstAddr like 'NAT_PRIVATE_IP' and srcAddr like '10.20.')
| stats sum(bytes) as bytesTransferred by srcAddr, dstAddr
| sort bytesTransferred desc
| limit 10

Alarms

  • Static threshold alarms act when a metric stays past a value for a number of periods.
  • Anomaly detection alarms learn a band from up to two weeks of history, including hourly, daily and weekly patterns, and alarm when a metric leaves it; exclude maintenance windows from training.
  • Composite alarms combine alarm states with AND, OR and NOT, for example page only when the Direct Connect connection and the backup VPN are both down.
  • Alarms must be in the same Region as their metric.

Dashboards, insights and multiple accounts

  • Dashboards can show metrics from several Regions and, with cross-account sharing, several accounts.
  • CloudWatch cross-account observability (Observability Access Manager) links source accounts to a monitoring account per Region, sharing metrics, logs and traces with no extra charge; Organizations can link new accounts automatically.
  • Contributor Insights analyzes logs into top-N contributors, such as the source and destination pairs moving the most bytes in flow logs or the clients causing most NXDOMAIN answers in Resolver logs.

Transit Gateway Network Manager

Knowledge 1.4.2AWS Transit Gateway Network Manager in architectures to provide visibility

The feature the guide calls Transit Gateway Network Manager is now documented as AWS Global Networks for Transit Gateways in the Network Manager console, alongside Cloud WAN. It gives one view of a global network:

  • A global network holds registered transit gateways from many Regions and, with Organizations, many accounts.
  • On-premises sites, devices (routers, SD-WAN appliances), links (internet connections) and connections between devices can be recorded, so the topology includes the data centers.
  • Dashboards show a topology tree, a geographic map, events and CloudWatch metrics for transit gateways and VPNs.
  • Events go to EventBridge in us-west-2 (the fixed home Region): topology changes (attachments created or deleted), routing updates (routes installed or removed) and status updates (VPN IPsec or BGP up and down). A console option sends them to CloudWatch Logs for querying.
  • Route Analyzer checks the path through transit gateway route tables only, from a source attachment and IP to a destination, optionally including a middlebox and the return path. It does not check VPC route tables, security groups or network ACLs.

There is no extra charge for the global network itself.

"Be notified when a VPN tunnel's BGP session goes down anywhere in the global network" points to Network Manager events in EventBridge. "Check whether transit gateway routes allow traffic between two attachments" points to Route Analyzer.

Reachability Analyzer

Knowledge 1.4.3VPC Reachability Analyzer in architectures to provide visibility

Reachability Analyzer builds a model of your network configuration and works out whether a path exists between a source and a destination. It does not send packets. It considers route tables, security groups, network ACLs, internet and NAT gateways, load balancers, VPC peering, transit gateways, VPC endpoints, VPN gateways and AWS Network Firewall rules.

  • Sources and destinations: instances, network interfaces, internet gateways, transit gateways and attachments, virtual private gateways, VPC endpoints and endpoint services, peering connections, and IP addresses (as destinations). Both must be in the same Region, possibly in different accounts of one organization (management account or delegated administrator).
  • Results: the shortest reachable path hop by hop, or the component that blocks it with an explanation code such as ENI_SG_RULES_MISMATCH, SUBNET_ACL_RESTRICTION, NO_ROUTE_TO_DESTINATION or VPC_BLOCK_PUBLIC_ACCESS_ENABLED.
  • Limits: IPv4 only; target health is ignored; transit gateway Connect attachments and policy tables are not supported; a path through a Gateway Load Balancer endpoint does not include the appliances.
  • 0.10 USD per analysis.
Can the booking app reach the payments database on port 5432? (AWS CLI) 
aws ec2 create-network-insights-path --source eni-0bookingapp --destination eni-0paymentsdb \
  --protocol tcp --destination-port 5432

aws ec2 start-network-insights-analysis --network-insights-path-id "$PATH_ID"

Network Access Analyzer

The companion tool for posture rather than one path: you define a Network Access Scope of paths that should not exist (for example any path from an internet gateway to the card-data subnets, or from development to production), with exclusions for allowed paths, and it reports every matching path as a finding. It works within one account and Region and costs 0.002 USD per network interface analyzed. It is the tool for proving segmentation to auditors.

Reachability Analyzer says a path is configured; it cannot show that traffic actually flowed or was dropped by an appliance. For proof of traffic, use flow logs or traffic mirroring.

Flow logs and traffic mirroring

Knowledge 1.4.4Flow logs and traffic mirroring in architectures to provide visibility

VPC flow logs

Flow logs record metadata about IP flows (not packet contents) for a VPC, subnet or network interface, including interfaces of NAT gateways, load balancers and transit gateways. They are collected outside the traffic path, so they do not affect performance.

  • Traffic type: ACCEPT, REJECT or ALL. Destinations: CloudWatch Logs, Amazon S3 (text or Parquet, optionally Hive-style partitions) or Amazon Data Firehose.
  • Aggregation interval: 10 minutes (default) or 1 minute; on Nitro instances it is always 1 minute or less. Delivery takes roughly 5 to 10 minutes, so flow logs are not real time.
  • Format: the default contains the version 2 fields only (account, interface, addresses, ports, protocol, packets, bytes, start, end, action, log status). Other fields need a custom format, and a flow log cannot be edited after creation, only recreated.

Useful custom fields by version:

  • v3: vpc-id, subnet-id, instance-id, tcp-flags, type, and pkt-srcaddr/pkt-dstaddr, the original addresses behind NAT gateways, transit gateways and EKS pods.
  • v4: region, az-id, sublocation fields for Local Zones and Outposts.
  • v5: pkt-src-aws-service, flow-direction, traffic-path (how egress traffic left: same VPC, internet gateway, VPN gateway, peering and so on).
  • v7: Amazon ECS cluster, service and task fields.
  • v8 to v11 (2024 to 2026): reject-reason (BPA for VPC Block Public Access, EC for encryption controls), encryption-status, regional NAT gateway resource IDs, EC2 and Auto Scaling tag fields and next-hop fields.
VPC flow log to S3 with a custom format and 1-minute aggregation (AWS CLI) 
aws ec2 create-flow-logs --resource-type VPC --resource-ids vpc-0booking \
  --traffic-type ALL --max-aggregation-interval 60 \
  --log-destination-type s3 --log-destination arn:aws:s3:::central-flow-logs-111111111111 \
  --log-format '${version} ${account-id} ${interface-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${log-status} ${vpc-id} ${pkt-srcaddr} ${pkt-dstaddr} ${tcp-flags} ${flow-direction} ${traffic-path} ${reject-reason}'

Not captured: traffic to the Amazon DNS server (use Resolver query logs), DHCP, instance metadata (169.254.169.254), Time Sync (169.254.169.123), Windows license activation, ARP, and the source side of mirrored traffic.

Reading ACCEPT and REJECT: security groups are stateful, network ACLs stateless. An inbound ACCEPT followed by an outbound REJECT for the reply means a network ACL is blocking the return traffic, not the security group.

Transit Gateway and Cloud WAN flow logs

Transit gateway flow logs (created by the transit gateway owner, per gateway or attachment) include the version 6 fields by default: source and destination VPC, subnet, interface, account and Availability Zone, plus counters of packets lost to no route, blackhole routes, MTU exceeded and TTL expired. Multicast is not logged, and Connect attachment flows appear on their transport attachment. Cloud WAN gained flow logs in November 2026, at core network, edge or attachment level, with segment names and attachment types.

Traffic Mirroring

When you need the packets themselves (intrusion detection, forensics, application troubleshooting), Traffic Mirroring copies traffic from a source network interface on a supported (mostly Nitro) instance to a target:

  1. SourceA network interface; inbound packets dropped by its security group or network ACL are not mirrored.
  2. FilterInbound and outbound rules by protocol, ports and CIDRs, evaluated in number order; a filter with no rules mirrors nothing.
  3. TargetA network interface, a Network Load Balancer with a UDP 4789 listener, or a Gateway Load Balancer endpoint, in the same VPC or reachable through peering or a transit gateway, possibly in another account.
  4. SessionTies them together with a session number (priority) and optional packet truncation; mirrored packets are wrapped in VXLAN on UDP 4789, which the target's security group must allow.

Billing is 0.015 USD per session-hour until the session is deleted, plus data transfer and load balancer processing. Mirrored traffic shares the instance's bandwidth.

"Which IP addresses are talking, and was it allowed" points to flow logs. "Inspect packet payloads with an intrusion detection system" points to Traffic Mirroring. "Why can't these two resources connect" points to Reachability Analyzer.

Access logging

Knowledge 1.4.5Access logging (for example, load balancers, CloudFront)

Application Load Balancer

Access logs, off by default, go to an S3 bucket in the same Region (SSE-S3 encryption only) every 5 minutes per load balancer node. Each entry records client and target addresses, processing times, ELB and target status codes, bytes, request line, user agent, TLS cipher and protocol, target group, trace ID, rule priority, actions executed and error reasons. Connection logs (with mutual TLS) record one entry per TLS connection with client certificate details, joined to access logs by conn_trace_id. ALBs and NLBs can now also deliver logs (including ALB health check logs) through CloudWatch vended logs to CloudWatch Logs, Firehose or S3.

Network and Classic Load Balancers

NLB access logs exist only for TLS listeners and record TLS details (handshake time, cipher, certificate, ALPN); S3 buckets can use SSE-KMS. For TCP and UDP traffic through an NLB, use flow logs on its interfaces. Classic Load Balancers publish every 5 or 60 minutes.

CloudFront

Standard logs: the legacy option writes to S3; standard logging v2 (November 2024) delivers to CloudWatch Logs, Firehose or S3 (with Parquet and partitioning), with selectable fields. Real-time logs stream chosen fields to Kinesis Data Streams within seconds, with a sampling rate of 1 to 100%, configured per cache behavior.

Other network logs

  • AWS WAF: full request logs to CloudWatch Logs (log group names starting aws-waf-logs-), S3 or Firehose.
  • Site-to-Site VPN: tunnel activity logs (IKE, IPsec, dead peer detection) and BGP logs to CloudWatch Logs.
  • Global Accelerator: flow logs to S3 only, configured through us-west-2.
  • Route 53: public DNS query logs and Resolver query logs (Task 1.2).
  • AWS CloudTrail records API changes to network resources, such as route table or security group edits.

Identifying requirements

Skill 1.4.1Identifying the logging and monitoring requirements

Start from the questions the business and operations teams must be able to answer, then map each to a source:

  • Availability: are links, tunnels, gateways and targets up? CloudWatch state and health metrics, Network Manager events, Route 53 health checks.
  • Performance: is latency or loss rising? Synthetic probes, load balancer response times, Internet Monitor scores, Network Flow Monitor retransmissions.
  • Capacity: are we near limits? Throughput against port speed, NAT and ENA allowance counters, network address usage, load balancer capacity units.
  • Security and compliance: who connected to what, what was blocked, and could anything reach the internet? Flow logs, WAF and DNS Firewall logs, CloudTrail, Network Access Analyzer.
  • Troubleshooting: why does a path fail? Reachability Analyzer, Route Analyzer, flow logs, traffic mirroring.
  • Cost: who is driving data transfer and NAT processing? Flow log aggregation and Contributor Insights.

Then set retention (regulators often require a year or more, which favors S3 with lifecycle rules over CloudWatch Logs), centralize logs from all accounts (an S3 bucket in a log archive account and cross-account observability for metrics), and decide on near-real-time needs (subscription filters, CloudFront real-time logs) versus batch analysis (Athena on Parquet flow logs).

Metrics for network status

Skill 1.4.2Recommending appropriate metrics to provide visibility of the network status

AWS Direct Connect (AWS/DX)

ConnectionState (physical link up or down), ConnectionBpsEgress/Ingress against port speed, ConnectionErrorCount (MAC errors, replacing the retired CRC metric), ConnectionLightLevelTx/Rx (optical power in dBm), ConnectionEncryptionState (MACsec), ConnectionDiscardsPpsEgress, and per virtual interface throughput. Since March 2026, VirtualInterfaceBgpStatus, VirtualInterfaceBgpPrefixesAccepted and VirtualInterfaceBgpPrefixesAdvertised show BGP health and prefix counts; alarm before the prefix quota is reached, because exceeding it brings the session down.

Site-to-Site VPN (AWS/VPN)

TunnelState (1 up; a connection-level value between 0 and 1 means one tunnel is down), TunnelDataIn and TunnelDataOut.

Transit Gateway (AWS/TransitGateway)

BytesIn/Out and PacketsIn/Out per gateway and attachment, and drop counters PacketDropCountBlackhole, PacketDropCountNoRoute and PacketDropCountTTLExpired. Use the Sum statistic.

NAT gateway (AWS/NATGateway)

ErrorPortAllocation (above 0 means port exhaustion to one destination: add IP addresses or gateways), PacketsDropCount, ActiveConnectionCount, ConnectionAttemptCount vs ConnectionEstablishedCount (destinations not answering), IdleTimeoutCount (connections idle past 350 seconds) and bytes in each direction.

Load balancers and edge

ALB: HealthyHostCount and UnHealthyHostCount, HTTPCode_ELB_5XX_Count (the load balancer) vs HTTPCode_Target_5XX_Count (the application), TargetResponseTime, RejectedConnectionCount. NLB: TCP_ELB_Reset_Count, PortAllocationErrorCount, security group blocked flow counts. Global Accelerator: healthy endpoint counts and flows (us-west-2). CloudFront: requests, error rates, and optional cache hit rate and origin latency (us-east-1).

VPC and instances

Network address usage per VPC (enable it; reported daily) to avoid hitting address limits, and the ENA allowance counters from the agent for instance-level drops.

A Direct Connect ConnectionState of 1 means the physical link is up, not that BGP is established. Use the virtual interface BGP status metric for routing health.

Capturing a baseline

Skill 1.4.3Capturing baseline network performance

A baseline is a record of normal behavior to compare against when something changes. AWS's Direct Connect guidance is to measure at different times and under different load conditions and keep the history.

CloudWatch network monitoring features

Network Synthetic Monitor (formerly Network Monitor)

Agentless probes from a VPC subnet to on-premises IP addresses over Direct Connect or VPN, using ICMP or TCP, report round-trip time and packet loss every 30 or 60 seconds, giving a continuous baseline even when application traffic is quiet. A network health indicator tells you whether degradation is on the AWS-controlled part of the path. Probe traffic over TCP uses rotating source ports, so on-premises firewalls must allow them.

Network Flow Monitor (December 2024)

Lightweight agents on EC2 instances and EKS nodes report TCP performance between workloads, to AWS services and toward other Regions: data transferred, retransmissions, timeouts and round-trip time, with top contributors and a health indicator. Multi-account since May 2025.

Internet Monitor

Uses AWS's global connectivity data to compute performance and availability scores for traffic between your VPCs, NLBs or CloudFront distributions and your users, by city and internet provider (ASN). It raises health events to EventBridge when scores drop below thresholds and suggests changes such as other Regions or CloudFront.

Practical baseline steps

  1. Collect long enoughAt least a few weeks covering busy and quiet periods; 1-minute data expires after 15 days, so use 1-hour statistics or export for long trends.
  2. Use percentilesp50, p90 and p99 for latency and round-trip time.
  3. Let CloudWatch learnAnomaly detection bands capture daily and weekly patterns and alarm on deviations.
  4. Probe constantlySynthetic probes give steady latency and loss figures for hybrid paths.
  5. Profile trafficFlow log aggregation by source, destination and port shows the normal traffic mix and top talkers.
  6. Track utilizationCompare link throughput, NAT peaks and allowance counters against their limits to plan capacity.

AWS Health events (to EventBridge, free) announce planned maintenance, for example VPN tunnel endpoint replacements, so the baseline can exclude known events.

"Monitor latency and packet loss to the data center with no agents" points to Network Synthetic Monitor. "TCP retransmissions between microservices" points to Network Flow Monitor. "Users of one ISP in one city report slowness" points to Internet Monitor.

Key takeaways

  • CloudWatch: Regional metrics (Route 53 and CloudFront in us-east-1, Global Accelerator in us-west-2), retention 15 days at 1 minute; the agent's ethtool plugin exposes ENA allowance drops (use RATE()); metric and subscription filters, Logs Insights; static, anomaly detection and composite alarms; cross-account observability; Contributor Insights for top talkers.
  • Network Manager (Global Networks for Transit Gateways): global topology of transit gateways and on-premises sites, events to EventBridge in us-west-2, Route Analyzer for transit gateway route tables only.
  • Reachability Analyzer analyzes configuration without sending packets and names the blocking component; Network Access Analyzer finds unintended paths for compliance.
  • Flow logs: default v2 fields only, custom fields need recreation, 1 or 10 minute aggregation, not real time, no Amazon DNS or metadata traffic; ACCEPT then REJECT points to a network ACL. Transit Gateway and Cloud WAN flow logs add drop counters and segments. Traffic Mirroring copies packets over VXLAN UDP 4789 to an interface, NLB or GWLB endpoint.
  • Access logs: ALB to S3 every 5 minutes plus connection logs; NLB only for TLS listeners; CloudFront standard logs v2 or real-time logs to Kinesis; WAF, VPN, Global Accelerator and DNS logs.
  • Requirements: availability, performance, capacity, security, troubleshooting and cost questions mapped to sources; retention and central collection decided up front.
  • Key metrics: DX state, throughput, errors, light levels and BGP status; VPN tunnel state; Transit Gateway drops; NAT port allocation errors; load balancer health and 5xx sources.
  • Baselines: weeks of data, percentiles, anomaly detection, Network Synthetic Monitor probes, Network Flow Monitor, Internet Monitor, flow log traffic profiles, and AWS Health maintenance events.
