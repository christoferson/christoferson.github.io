Overview

Task 1.2

Design DNS solutions that meet public, private, and hybrid requirements.

Almost every network flow starts with a DNS lookup, so DNS design decides whether hybrid applications can find each other, whether internal names leak to the internet, and how fast users move to a healthy Region. Questions in this task give a mix of on-premises DNS servers, VPCs in many accounts and public users, and ask which hosted zone, Resolver endpoint, rule, sharing method or routing policy makes names resolve correctly, securely and resiliently.

The travel company from Task 1.1 owns example.com. Customers use www.example.com and api.example.com; AWS workloads use private names under aws.example.com; the two data centers run Active Directory DNS for corp.example.com. The central network account 111111111111 hosts the shared DNS infrastructure for dozens of workload accounts.

The Route 53 documentation now calls the VPC's built-in resolver Route 53 VPC Resolver; questions and older material say Route 53 Resolver, Amazon DNS server or AmazonProvidedDNS. Recent changes this page reflects: Route 53 Profiles (April 2024, with up to two Profiles per VPC since November 2026), outbound and inbound delegation (June 2025), accelerated recovery for public hosted zones (November 2025), record set protection (November 2026), and an API rate of 10 requests per second, up from 5 (July 2026).

The DNS protocol

Knowledge 1.2.1DNS protocol (for example, DNS records, TTL, DNSSEC, DNS delegation, zones)

Zones and delegation

DNS is a tree. The root delegates .com to its registry's name servers; .com delegates example.com to the name servers listed in NS records at the parent; those servers are authoritative for the zone. A zone is the part of the tree one set of name servers answers for; in Route 53 it is a hosted zone. Any subdomain can be delegated further by putting NS records for it in the parent zone. A recursive resolver (such as the VPC Resolver or an ISP's resolver) walks this chain on behalf of clients and caches what it learns.

Record types

  • A and AAAA: IPv4 and IPv6 addresses.
  • CNAME: an alias to another name. Not allowed at the zone apex (the bare domain, such as example.com), and no other record may share its name.
  • NS and SOA: the zone's name servers and its start of authority (primary server, admin contact, timers and the negative-caching TTL).
  • MX: mail servers with priorities (lowest wins); the target must be an A or AAAA name, not a CNAME.
  • TXT: text such as SPF, domain verification or DKIM; strings of up to 255 characters, joined for longer values. Publish SPF in TXT, not the deprecated SPF type.
  • SRV, PTR (reverse lookups), CAA (which certificate authorities may issue for the domain), NAPTR, DS (DNSSEC delegation), and since October 2024 HTTPS, SVCB, SSHFP and TLSA.

TTL and negative caching

The TTL tells resolvers how many seconds to cache an answer. Long TTLs mean fewer queries (lower cost, faster lookups) but slower changes; short TTLs (60 seconds or less) are recommended for records used with health checks and failover. Negative answers are cached too: NXDOMAIN (the name does not exist) and NODATA (the name exists without that record type) are cached for the lesser of the SOA's minimum TTL and the SOA record's own TTL. A record deleted by mistake can therefore stay missing in resolvers after you recreate it. In a new Route 53 zone the SOA record's TTL is 900 seconds, and NS records typically use 172,800 seconds (two days).

DNSSEC

DNSSEC lets resolvers verify that answers really come from the zone owner and were not changed, which defends against cache poisoning and spoofing. The zone owner signs records; each zone publishes its public keys (DNSKEY); the parent publishes a DS record with a hash of the child's key-signing key, forming a chain of trust up to the root. A validating resolver rejects answers whose signatures do not check out. In Route 53, signing applies to public hosted zones and validation is a per-VPC Resolver setting; both are covered in Using public hosted zones.

DNS logging and monitoring

Knowledge 1.2.2DNS logging and monitoring

Public DNS query logging

Logs the queries that reach Route 53's authoritative servers for a public hosted zone: name, type, response code, protocol, edge location, resolver IP and EDNS client subnet. Logs go only to CloudWatch Logs in us-east-1, one stream per edge location. Queries answered from resolvers' caches never reach Route 53, so the logs show only a fraction of real lookups.

Resolver query logging

Logs queries made inside VPCs through the VPC Resolver, queries arriving through inbound endpoints, queries forwarded through outbound endpoints, and DNS Firewall actions: VPC ID, source IP and instance ID, query name and type, response code and answer. Destinations are CloudWatch Logs, Amazon S3 or Amazon Data Firehose, in the same Region as the VPCs. A logging configuration can be shared with other accounts through AWS RAM, so every account's VPCs log to one central bucket. Cached answers are not logged.

CloudWatch metrics

In AWS/Route53: DNSQueries per public hosted zone (us-east-1 only), DNSSEC metrics such as DNSSECKeySigningKeysNeedingAction, and health check metrics such as HealthCheckStatus. In AWS/Route53Resolver (Regional): endpoint metrics such as InboundQueryVolume, OutboundQueryVolume, EndpointHealthyENICount and ResolverEndpointCapacityStatus (0 OK, 1 warning above 50% of an interface's capacity, 2 critical above 75%). Since December 2025, optional detailed metrics add per-interface P90 response time and SERVFAIL, NXDOMAIN and timeout counts, plus per-target name server metrics for outbound endpoints.

Route 53 Resolver DNS Firewall

Filters queries that go through the VPC Resolver against domain lists (your own or AWS managed lists of malicious domains) in rule groups associated with VPCs. Actions: ALLOW, ALERT (log only) or BLOCK, answering with NODATA, NXDOMAIN or an OVERRIDE CNAME pointing to a warning page. DNS Firewall Advanced (November 2024) detects DNS tunneling and domain generation algorithms with a confidence threshold. By default DNS Firewall fails closed (SERVFAIL if it cannot evaluate a query); switch to fail open where availability matters more. It sees only queries sent to the VPC Resolver, so instances using their own DNS servers bypass it; Network Firewall covers other protocols.

"Log DNS queries from EC2 instances" points to Resolver query logging. "Log queries from the internet for our public domain" points to public DNS query logging in us-east-1. "Block queries to known malicious domains from workloads" points to DNS Firewall.

Route 53 features

Knowledge 1.2.3Amazon Route 53 features (for example, alias records, traffic policies, resolvers, health checks)

Alias records

An alias record is a Route 53 extension that answers with the current addresses of an AWS resource: CloudFront distributions, Global Accelerator, Elastic Load Balancing, API Gateway, S3 website endpoints, VPC interface endpoints, App Runner, Elastic Beanstalk, AppSync, OpenSearch Service custom domains, VPC Lattice custom domains, or another record in the same hosted zone. Compared with a CNAME, an alias:

  • works at the zone apex;
  • is free to query when it points to an AWS resource (a CNAME pointing into Route 53 is billed as two queries);
  • has no TTL of its own: Route 53 uses the target's TTL, and follows changes such as new load balancer addresses automatically;
  • appears to clients as a normal A or AAAA answer;
  • can evaluate target health, inheriting the target's health (for an ALB or NLB, every target group with targets needs a healthy target). Not possible for CloudFront targets; no operational benefit for S3, API Gateway or interface endpoint targets.
Point the apex example.com at the CloudFront distribution (Route 53 ChangeBatch, JSON; Z2FDTNDATAQYW2 is CloudFront's fixed hosted zone ID) 
{
  "Comment": "Apex alias to CloudFront",
  "Changes": [{
    "Action": "UPSERT",
    "ResourceRecordSet": {
      "Name": "example.com",
      "Type": "A",
      "AliasTarget": {
        "HostedZoneId": "Z2FDTNDATAQYW2",
        "DNSName": "DISTRIBUTION_DOMAIN.cloudfront.net",
        "EvaluateTargetHealth": false
      }
    }
  }]
}

Health checks

Route 53 health checks decide which records are eligible in an answer. Types: endpoint checks (HTTP, HTTPS, TCP, optionally matching a string in the first 5,120 bytes of the body), calculated checks that combine other checks with AND, OR or "at least x of y", CloudWatch alarm checks, and routing control checks driven by Application Recovery Controller. Details and failover behavior are in Global traffic management.

Traffic policies (Traffic Flow)

Traffic Flow is a visual editor for routing trees, for example latency between Regions, then weighted between stacks, then failover to a static page. A traffic policy is the versioned definition (free); a policy record applies a version to a name in a public hosted zone (50 USD per month), and Route 53 creates the hidden records of the tree. Policy records are public hosted zones only. To save cost, point other names at one policy record with alias records.

Resolvers

The VPC Resolver answers DNS for every VPC, and Resolver endpoints and rules connect it to other networks. They are covered in Route 53 and Amazon VPC and Using Resolver endpoints.

Control plane, data plane and record protection

Route 53 answers queries from a highly available data plane in hundreds of locations, but changes to records and health checks go through a control plane in us-east-1. Fail over with data plane actions (health checks, routing controls) rather than by editing records during an incident. Accelerated recovery (November 2025, free, public zones only, enabled in advance) aims to let you change records again within 60 minutes if us-east-1 is impaired. Record set protection (November 2026) blocks creating, changing or deleting a protected name and type, even by administrators, until the protection is removed.

Route 53 and Amazon VPC

Knowledge 1.2.4Integration of Route 53 with other AWS networking services (for example, Amazon VPC)

The VPC Resolver

  • Built into every Availability Zone and reachable at 169.254.169.253, fd00:ec2::253 and the VPC CIDR base plus two (for example 10.20.0.2 in 10.20.0.0/16).
  • Answers private hosted zone names, Amazon-provided EC2 names, and public names by recursion.
  • Traffic to it cannot be filtered by security groups or network ACLs.
  • Each network interface may send 1,024 packets per second in total to link-local services (DNS, instance metadata, Time Sync); the limit cannot be raised, so DNS-heavy instances should cache answers locally.

VPC DNS attributes

enableDnsSupport

Whether the VPC Resolver answers at all. Default true.

enableDnsHostnames

Whether instances with public IP addresses get public DNS hostnames. Default false in new VPCs (true in the default VPC).

Private hosted zones and interface endpoint private DNS names need both attributes true. A common exam failure is a new VPC where a private hosted zone does not resolve because enableDnsHostnames was left false.

Other VPC integrations

  • DHCP option sets tell instances which DNS servers to use (AmazonProvidedDNS by default). Custom DNS servers on EC2 must forward private zone queries to the VPC +2 address to resolve them.
  • VPC peering can resolve the peer's public EC2 hostnames to private addresses when DNS resolution is enabled on the peering connection.
  • Interface VPC endpoints (AWS PrivateLink) create private DNS names that override the service's public name inside the VPC.
  • Alias records can target VPC interface endpoints and VPC Lattice services.

Hybrid, multi-account and multi-Region DNS

Knowledge 1.2.5Integration of Route 53 with hybrid, multi-account, and multi-Region options

Hybrid

Private hosted zones resolve only inside associated VPCs; on-premises servers cannot query the VPC +2 address across VPN or Direct Connect (AWS says this is unsupported). Inbound endpoints give on-premises DNS servers IP addresses in a VPC to forward queries to; outbound endpoints with forwarding rules send VPC queries for on-premises domains to on-premises DNS servers. Both are Regional.

Multi-account

  • Private hosted zones in another account: the zone owner authorizes each VPC, the VPC owner associates it (CLI or API only), up to 300 VPCs per zone.
  • Resolver rules are shared with accounts, OUs or the organization through AWS RAM; sharing a rule implicitly shares its outbound endpoint, and each account associates the rule with its VPCs.
  • Route 53 Profiles (April 2024) bundle private hosted zones, Resolver rules, DNS Firewall rule groups, interface endpoints and query logging settings, are shared through RAM, and apply to a VPC with one association.
  • Query logging configurations and DNS Firewall rule groups can also be shared through RAM, and AWS Firewall Manager can enforce DNS Firewall across an organization.

Multi-Region

Private hosted zones are global and can be associated with VPCs in any Region, but Resolver endpoints, rules, Profiles, DNS Firewall rule groups and query logging configurations are Regional and must be created in each Region. Public routing across Regions uses latency, geolocation, geoproximity and failover records (below).

Domain registration concepts

Knowledge 1.2.6Domain registration

  • A registry owns a top-level domain (TLD) and its authoritative database; a registrar accredited by ICANN sells and manages registrations in it. Route 53 Domains registers domains through Amazon Registrar (or its associate Gandi for some TLDs).
  • Registration and DNS hosting are separate: a domain registered with Route 53 can use another DNS provider, and a Route 53 hosted zone can serve a domain registered elsewhere. What links them is the name server list at the registrar.
  • When you register a domain, Route 53 creates a public hosted zone for it automatically (billed monthly; free if deleted within 12 hours).
  • The registration carries contacts (registrant, admin, technical, billing), privacy protection (on by default where the TLD allows), a transfer lock, auto-renew, and optionally DNSSEC public keys passed to the registry.
  • The Route 53 Domains API runs only in us-east-1.

Using public hosted zones

Skill 1.2.1Using Route 53 public hosted zones

What a new public zone contains

Route 53 assigns four name servers (one each under .com, .net, .org and .co.uk, for resilience across TLDs) and creates an NS record listing them and an SOA record. Give those four names to the registrar. You can create several zones with the same name, each with different name servers; only the one the registrar points to is used. Pricing: 0.50 USD per zone per month for the first 25 zones, per-million query charges by routing type, and free alias queries to AWS resources.

Delegating subdomains

The travel company lets each team run its own subdomain. The network account owns example.com; a workload account creates a hosted zone for flights.example.com; the network account adds an NS record for flights.example.com listing the child zone's four name servers. Do not leave records for the subdomain in the parent as well, or answers become inconsistent. Delegation also lets IAM limit who edits each zone.

Reusable delegation sets and white-label name servers

A reusable delegation set is one set of four name servers for many zones, created only through the API or CLI and attached only when a zone is created. It underlies white-label name servers such as ns1.example.com: you create A and AAAA records for the vanity names and glue records at the registrar.

Migrating DNS to Route 53

  1. Copy the recordsExport the zone file from the current provider and create the records in a new public hosted zone (imports create only simple records).
  2. Lower the NS TTLAt both the old provider and the parent, to 60 to 900 seconds, and remove the DS record if DNSSEC is on.
  3. Wait out the old TTLTypically two days.
  4. Switch name serversAt the registrar, to the four Route 53 servers; monitor, and roll back if needed.
  5. RestoreRaise the NS TTL to two days, then optionally transfer the registration and re-enable DNSSEC.

Signing a public zone with DNSSEC

Route 53 manages the zone-signing key and rotates it. You provide the key-signing key (KSK), backed by a customer managed KMS key that must be in us-east-1, asymmetric, with key spec ECC_NIST_P256, and a key policy allowing dnssec-route53.amazonaws.com to sign. Signing applies to public zones only and caps record TTLs at one week.

Create the KSK and enable signing (AWS CLI, us-east-1) 
aws route53 create-key-signing-key --region us-east-1 \
  --hosted-zone-id "$ZONE_ID" --key-management-service-arn "$KMS_KEY_ARN" \
  --name travel-ksk --status ACTIVE --caller-reference ksk-2026-11-14

aws route53 enable-hosted-zone-dnssec --region us-east-1 --hosted-zone-id "$ZONE_ID"

Then establish the chain of trust: add the DS record at the parent (in the parent hosted zone, or under Registered domains for a domain registered with Route 53), starting with a short DS TTL. Alarm on DNSSECInternalFailure and DNSSECKeySigningKeysNeedingAction: if the KMS key becomes unusable, signatures expire and validating resolvers fail. To disable DNSSEC, remove the DS record first and wait for its TTL, then disable signing; the reverse order makes the domain unresolvable for validating resolvers.

For VPC workloads, turn on DNSSEC validation per VPC in the Resolver; it applies when the Resolver itself recurses, and the Resolver does not pass DNSSEC records or the AD bit to clients.

A CNAME cannot be created at example.com. To point the apex at a load balancer, CloudFront or Global Accelerator, use an alias A or AAAA record.

Using private hosted zones

Skill 1.2.2Using Route 53 private hosted zones

How private zones answer

A private hosted zone answers only for VPCs associated with it (queries are free), using reserved name servers that public zones never use. Routing policies supported: simple, failover, weighted, latency, geolocation, geoproximity and multivalue answer; IP-based routing is not supported, and Traffic Flow policy records cannot be used. Health checks cannot reach private IP addresses, so private failover uses CloudWatch alarm-based health checks.

Which zone wins

  • Split-horizon DNS: a public and a private zone with the same name; associated VPCs get private answers, the internet gets public ones.
  • If a private zone matches the name (the same name or a parent) but has no record of the requested type, the VPC Resolver returns NXDOMAIN and does not fall back to the public zone. Every name VPC clients need must exist in the private zone.
  • With overlapping private zones (example.com and aws.example.com), the most specific zone answers.
  • A Resolver forwarding rule for the same domain as an associated private zone takes precedence and forwards the query.

Sharing a private zone across accounts

Associate a workload account's VPC with the central aws.example.com zone (AWS CLI; console not supported) 
# In the zone owner account (111111111111): authorize this VPC
aws route53 create-vpc-association-authorization --hosted-zone-id "$PHZ_ID" \
  --vpc VPCRegion=eu-central-1,VPCId=vpc-0workload

# In the workload account that owns the VPC: associate it
aws route53 associate-vpc-with-hosted-zone --hosted-zone-id "$PHZ_ID" \
  --vpc VPCRegion=eu-central-1,VPCId=vpc-0workload

# Back in the zone owner account: remove the authorization (the association stays)
aws route53 delete-vpc-association-authorization --hosted-zone-id "$PHZ_ID" \
  --vpc VPCRegion=eu-central-1,VPCId=vpc-0workload

At scale, a Route 53 Profile replaces this per-VPC dance and avoids the 300-VPCs-per-zone limit: associate the zone with a Profile, share the Profile, and associate it with each VPC once. A private zone can also delegate a subdomain to other name servers with NS records, used with the delegation feature described in Using Resolver endpoints.

"Instances in a new VPC can't resolve the private zone" points to enableDnsSupport and enableDnsHostnames or a missing VPC association. "Works in VPCs but not from on premises" points to an inbound endpoint and conditional forwarders.

Using Resolver endpoints

Skill 1.2.3Using Route 53 Resolver endpoints in hybrid and AWS architectures

Inbound and outbound endpoints

Inbound endpoint (on premises to AWS)

Elastic network interfaces in a VPC; on-premises DNS servers use conditional forwarders for aws.example.com pointing at the endpoint's IP addresses. Queries resolve against private zones associated with that VPC, so associate them there. The security group must allow TCP and UDP 53 (and 443 for DNS over HTTPS) from on premises.

Outbound endpoint (AWS to on premises)

Interfaces from which the VPC Resolver forwards queries that match forwarding rules, for example corp.example.com to the two data centers' DNS servers. The security group must allow outbound DNS to those servers, and the VPC needs a path to them (VPN, Direct Connect, or a NAT gateway for internet targets).

Design rules for both: at least two IP addresses, in at least two Availability Zones; IP addresses stay fixed for the endpoint's life; the security group cannot be changed after creation; each IP handles up to about 10,000 UDP queries per second, but as few as about 1,500 for inbound endpoints when connection tracking applies. Add interfaces when any one passes 50% (the ResolverEndpointCapacityStatus metric). Endpoints are charged per interface per hour plus per query. Endpoints can also speak DNS over HTTPS (since December 2023) to encrypt hybrid DNS.

Rules and precedence

  • Forward rules send a domain and its subdomains to target IP addresses through an outbound endpoint.
  • System rules make the Resolver answer a subdomain itself, carving it out of a forward rule (forward example.com, but resolve aws.example.com locally).
  • The built-in recursive rule resolves everything else.
  • Delegate rules (June 2025) follow NS delegations through an outbound endpoint; with inbound delegation, on-premises DNS delegates a subdomain to the inbound endpoint IPs as its name servers instead of forwarding.
  • When several rules match, the most specific domain wins.
Forward corp.example.com to the data centers and use the rule in a VPC (AWS CLI) 
aws route53resolver create-resolver-rule --creator-request-id corp-fwd-1 --name corp \
  --rule-type FORWARD --domain-name corp.example.com \
  --resolver-endpoint-id "$OUTBOUND_ENDPOINT_ID" \
  --target-ips "Ip=10.10.0.53" "Ip=10.30.0.53"

aws route53resolver associate-resolver-rule --resolver-rule-id "$RULE_ID" --vpc-id vpc-0shared

The centralized hybrid DNS design

  1. Hub VPCIn the network account, a shared-services VPC in each Region holds one inbound and one outbound endpoint, reachable from spoke VPCs over Transit Gateway and from the data centers over Direct Connect.
  2. Rules shared through RAMThe corp.example.com forward rule is shared with the organization; spoke VPCs use the shared outbound endpoint without endpoints of their own.
  3. Private zonesSpoke private zones are associated with the hub VPC so the inbound endpoint can answer for them, or distributed with a Route 53 Profile.
  4. On-premises forwardersConditional forwarders for aws.example.com point at the inbound endpoint IPs in the nearest Region.
  5. Firewall and loggingDNS Firewall rule groups and a query logging configuration are applied through the same Profile.

Do not associate a forwarding rule with the VPC that holds the inbound endpoint the rule ultimately points back to; queries can loop between the outbound and inbound endpoints. And forwarding from on premises to the VPC +2 address is unsupported: always use inbound endpoint IPs.

Route 53 Profiles in detail

A Profile is shared within a Region through RAM; a VPC can have up to two Profiles, each association with a priority from 100 to 9900 (lower wins). For the same domain, a setting made directly on the VPC wins over a Profile; across Profiles, the first Profile in priority order with a match is used. Profiles do not create endpoints: they distribute rules that point to existing outbound endpoints. Profiles can also set DNSSEC validation and the DNS Firewall fail mode for every VPC that uses them.

Global traffic management with Route 53

Skill 1.2.4Using Route 53 for global traffic management

Routing policies

Simple

One record, possibly with several values returned in random order; no health checks.

Weighted

Weights from 0 to 255; each record gets weight divided by the total. Records with weight 0 are used only if every non-zero record is unhealthy (or if all weights are 0, traffic is equal). Good for canary releases and gradual migrations.

Latency

One record per Region; Route 53 answers with the Region that has the lowest latency to the user, based on AWS's measurements between users and AWS Regions (not your own data centers).

Failover

A primary and a secondary record for active-passive designs. If the primary is unhealthy and the secondary healthy, Route 53 answers with the secondary; if both are unhealthy, it returns the primary. A typical secondary is an S3 static "temporarily unavailable" site.

Geolocation

By continent, country or US state; the most specific match wins. Create a default record, or users from unmapped locations get no answer. Good for language, legal or content-rights requirements.

Geoproximity

By distance between users and resources (an AWS Region, a Local Zone group or coordinates), adjusted with a bias from -99 to +99 that grows or shrinks each resource's area. Since January 2024 these are normal records and no longer need Traffic Flow.

Multivalue answer

Up to eight healthy records chosen at random; health-checked client-side load spreading, not a load balancer. Cannot be an alias.

IP-based

By the resolver's (or EDNS client subnet's) IP address, matched against CIDR collections you define, for example sending one internet provider's users to a specific endpoint. Public zones only.

Policies cannot be mixed for the same name and type; combine them by building a tree with alias records: for example, latency aliases for api.example.com pointing to weighted records per Region, each weighted record health-checked. With evaluate target health on the aliases, a Region whose records are all unhealthy drops out and the next-best Region answers.

Health checks in detail

  • HTTP and HTTPS checks need a TCP connection within 4 seconds and a 2xx or 3xx status within 2 seconds; TCP checks need a connection within 10 seconds. HTTPS checks do not validate certificates.
  • Interval 30 seconds (standard) or 10 seconds (fast, extra cost); failure threshold 1 to 10 checks (default 3). Detection takes roughly interval times threshold: about 90 seconds by default.
  • Checkers run from several Regions (at least three); the endpoint is healthy if more than 18% of checkers report it healthy. Firewalls must allow the Route 53 health checker address ranges.
  • Checkers are outside your VPCs and cannot test private IP addresses; for private or on-premises resources, publish a CloudWatch metric, alarm on it and use an alarm-based check (same account, standard-resolution metrics).
  • Records without health checks are always considered healthy, and if every record is unhealthy Route 53 treats them all as healthy (fails open), with exceptions for failover (returns primary), multivalue and geolocation.
  • Do not health-check instances behind a load balancer; use an alias with evaluate target health.

Failover speed and Application Recovery Controller

Worst-case failover is detection time plus the record's TTL plus any extra client caching, so use TTLs of 60 seconds or less with health-checked records. When failover must be deliberate and reliable, Amazon Application Recovery Controller (ARC) routing controls act as on/off switches behind Route 53 health checks; you flip them through a cluster's data plane endpoints in five Regions, not through the console. ARC Region switch (August 2025) orchestrates whole-Region recovery plans; ARC readiness checks have been closed to new customers since April 2026. For failover without any DNS caching, compare with Global Accelerator in Task 1.1.

"Users in Germany must be served from the EU for legal reasons" points to geolocation. "Lowest latency for global users" points to latency. "Shift more traffic toward a Region gradually by location" points to geoproximity bias. "Send 5% of traffic to the new version" points to weighted.

A geolocation design without a default record gives no answer to users whose location cannot be mapped, which looks like an outage for some of them.

Creating and managing domain registrations

Skill 1.2.5Creating and managing domain registrations

Registering

Choose the name, duration and auto-renew, enter contacts (some TLDs need extra fields), and verify the registrant email if the registry requires it, or the domain is suspended. New accounts can register 20 domains by default. Registrations are not refundable and cannot be renamed. Premium names can be registered since October 2026.

Protecting and renewing

  • Keep the transfer lock on (it shows as clientTransferProhibited); it is off after a domain is transferred in, so turn it back on.
  • Keep auto-renew on for production domains; since November 2026 expired or recently deleted domains can be restored self-service, at a higher price.
  • Register production domains in a central account, and do not use a domain registered in an account as that account's own root email domain: if the account is closed, the domain is suspended.

Transferring

To Route 53 from another registrar

The domain must be more than 60 days past registration or its last transfer; unlock it, get the authorization code, move DNS first if the old registrar provides it, and remove DS records first if DNSSEC is on. Most TLDs add a year on transfer.

Between AWS accounts

Not in the first 14 days after registration. The source account starts the transfer and receives a password; the destination accepts within 3 days. The hosted zone does not move with the domain, and DNS keeps working while they are in different accounts.

DNSSEC for a registered domain

Sign the zone first at the DNS provider, then add the public key under Registered domains so Route 53 sends the DS record to the registry. To disable, remove the key at the registrar first and wait before turning off signing.

Key takeaways

  • DNS is delegated through NS records; no CNAME at the apex (use alias); TTLs trade cost against change speed; negative answers are cached for the lesser of the SOA minimum and SOA TTL; DNSSEC chains trust through DS records.
  • Public query logs: CloudWatch Logs in us-east-1 only. Resolver query logs: CloudWatch, S3 or Firehose in-Region, shareable through RAM. DNS Firewall blocks malicious domains and fails closed by default.
  • Alias records are free for AWS targets, work at the apex and can evaluate target health (not for CloudFront). Traffic Flow policy records cost 50 USD a month and are public-zone only. Fail over with data plane actions; accelerated recovery and record set protection guard the control plane.
  • The VPC Resolver lives at +2 and 169.254.169.253, cannot be filtered, and is limited to 1,024 packets per second per interface. Private zones need enableDnsSupport and enableDnsHostnames.
  • Public zones: four name servers per zone; delegate subdomains with NS records in the parent; reusable delegation sets for white-label servers; DNSSEC KSK in a us-east-1 ECC_NIST_P256 KMS key; remove the DS before disabling.
  • Private zones: no IP-based routing; a matching zone without the record returns NXDOMAIN without public fallback; most specific zone wins; forwarding rules beat private zones; cross-account association needs authorize, associate, delete authorization, or a Profile.
  • Inbound endpoints for on premises to AWS, outbound endpoints plus forward rules for AWS to on premises, at least two IPs in two AZs, fixed security group; share rules or Profiles through RAM from a central hub; most specific rule wins; avoid loops.
  • Routing: weighted, latency, failover, geolocation (add a default), geoproximity (bias), multivalue (8 healthy), IP-based (public only); combine with alias trees and evaluate target health. Health checks: 18% rule, about 90 s detection, alarm-based for private resources, TTL 60 s or less; ARC routing controls for deliberate failover.
  • Domains: registrar vs registry, auto-created hosted zone, transfer lock, auto-renew, 60-day transfer rule, account transfers do not move the hosted zone.
