Overview

Task 3.2

Provision and configure resources for ML and AI workloads based on existing architecture and requirements.

This task is new in MLA-C02. Its questions start from an existing setup ("the company's VPC has no internet access", "the network team owns the VPC stack", "traffic triples every Monday") and ask for the configuration that fits: the capacity model, the cross-stack reference, the VPC endpoints, the scaling metric, the knowledge base storage, where agent conversations are kept. Task 3.1 chose the hosting options; this task configures them.

Running example. The online retailer (account 111111111111) has a shared network stack with private subnets and no internet route, runs the churn endpoint and a GPU endpoint for its open-weight model, and is adding a help-centre knowledge base and a support agent that remembers customers between conversations.

Status changes to know. ECR's old Clair-based basic image scanning was replaced by AWS-native basic scanning on 2 February 2026 (OS packages only; language packages need enhanced scanning with Amazon Inspector). The SageMaker inference toolkit GitHub repository was archived in November 2025. Enhanced endpoint metrics (per instance and per GPU, published as often as every 10 seconds) arrived in April 2026, and automatic container image caching in June 2026. On-demand or provisioned

Skill 3.2.1Optimize resource provisioning between on-demand and provisioned resources for performance and cost efficiency.

  • SageMaker AI endpoints bill per instance-hour on demand. A SageMaker Savings Plan (a one- or three-year dollars-per-hour commitment, up to 64% off, any instance family, size or Region) lowers the price but doesn't guarantee capacity. To guarantee scarce GPUs for an endpoint, reserve them with a training plan for inference and point the endpoint at it (CapacityReservationConfig); instance pools fall back to other instance types without a commitment.
  • Serverless inference pays only per request; provisioned concurrency removes cold starts but bills while idle, so use it only where cold-start latency matters.
  • Lambda: reserved concurrency caps a function at no charge; provisioned concurrency keeps instances initialized (billed), must target a version or alias rather than $LATEST, and can be autoscaled on LambdaProvisionedConcurrencyUtilization (a target of 0.7 is common).
  • Bedrock: on-demand per token by default; Flex for cheaper, delay-tolerant work, Priority for speed, the Reserved tier for committed tokens per minute, and Provisioned Throughput (hourly model units, no overflow) for steady high volume or custom models that need it.
Point an endpoint variant at reserved GPU capacity (JSON, part of CreateEndpointConfig) 
{
  "VariantName": "AllTraffic",
  "ModelName": "product-copy-lmi",
  "InstanceType": "ml.p5.48xlarge",
  "InitialInstanceCount": 2,
  "CapacityReservationConfig": {
    "CapacityReservationPreference": "capacity-reservations-only",
    "MlReservationArn": "arn:aws:sagemaker:us-east-1:111111111111:training-plan/genai-launch-plan"
  }
}

Steady, predictable usage means a commitment (Savings Plans, Provisioned Throughput, Reserved tier); spiky or unknown usage means on demand with autoscaling, serverless or Bedrock on-demand. When the reservation ends, invocations fail, and deleting the endpoint doesn't cancel the plan.

Automating provisioning

Skill 3.2.2Automate compute resource provisioning with integrated communication between stacks and orchestration services.

Infrastructure as code: AWS CloudFormation (or the AWS CDK, which generates it) has resource types for AWS::SageMaker::Model, EndpointConfig, Endpoint, InferenceComponent and Pipeline, AWS::Bedrock::KnowledgeBase, DataSource and Guardrail, and AWS::BedrockAgentCore::Runtime, Gateway and Memory. There is no training job resource; run training from a pipeline.

Ways for stacks to share values (VPC subnets, bucket names, role ARNs, the current model location):

  • Export and Fn::ImportValue: a strong link within one account and Region. Once imported, the exporting stack can't delete or change the value, which can block updates.
  • SSM Parameter Store with {{resolve:ssm:name}}: one stack (or a pipeline) writes a parameter, another reads it at deploy time; looser coupling, no export lock. Values are read only on stack create or update.
  • Fn::GetStackOutput: reads another stack's output without an export, across accounts and Regions, as a weak reference. In CDK, references between stacks in one app become exports automatically unless you choose weak references.
  • Nested stacks to keep sharing inside one stack group.
The serving stack reads the network stack's exports and the latest model from SSM (YAML, CloudFormation) 
Resources:
  ChurnModel:
    Type: AWS::SageMaker::Model
    Properties:
      ExecutionRoleArn: !ImportValue retail-ml-roles-SageMakerHostingRoleArn
      PrimaryContainer:
        Image: 683313688378.dkr.ecr.us-east-1.amazonaws.com/sagemaker-xgboost:3.2-0
        # The training pipeline writes the approved model location here
        ModelDataUrl: '{{resolve:ssm:/retail/churn/approved-model-uri}}'
      VpcConfig:
        Subnets:
          - !ImportValue retail-network-PrivateSubnetA
          - !ImportValue retail-network-PrivateSubnetB
        SecurityGroupIds:
          - !ImportValue retail-network-ModelSecurityGroup
  ChurnEndpointConfig:
    Type: AWS::SageMaker::EndpointConfig
    Properties:
      ProductionVariants:
        - VariantName: AllTraffic
          ModelName: !GetAtt ChurnModel.ModelName  # Ref would return the ARN
          InstanceType: ml.m5.xlarge
          InitialInstanceCount: 2
  • Update behaviour: almost every Model and EndpointConfig property forces a replacement, while changing an Endpoint's EndpointConfigName updates it in place with no interruption.
  • Orchestration hooks: EventBridge events such as "SageMaker Model Package State Change" (approval) can start a pipeline or a deployment; Step Functions can create models, configs and endpoints (endpoint creation has no .sync, so poll DescribeEndpoint), and calls StartPipelineExecution through its AWS SDK integration.

Ref on AWS::SageMaker::Model, EndpointConfig, Endpoint and InferenceComponent returns the ARN; use !GetAtt X.ModelName (or EndpointName) where a name is expected. Endpoint state change events report IN_SERVICE, while the API returns InService.

Containers

Skill 3.2.3Build and maintain containers for ML and AI workloads.

  • Start from AWS images (Deep Learning Containers, LMI, vLLM, framework containers) and extend them with a Dockerfile FROM the AWS image; build your own only when no image fits (the inference contract is in Task 3.1). Rebuild regularly: AWS images get security patches only for a limited time, and Amazon Linux 2023 based images are the ones AWS can keep patched.
  • Build in AWS CodeBuild (privilegedMode: true for Docker builds; ARM build images for Graviton), or in SageMaker Studio after a domain admin enables Docker access.
  • Store in Amazon ECR: turn on tag immutability so a tag always means the same image, and reference production images by digest (@sha256:...); AWS warns that :latest can pull a newer image than intended. Add lifecycle policies to expire or archive old and untagged images.
  • Scan: basic scanning checks OS packages on push; enhanced scanning (Amazon Inspector) also checks Python and other language packages and re-scans continuously as new vulnerabilities are published.
  • Access: the SageMaker execution role needs ecr:GetAuthorizationToken and the image pull actions; images in another account also need a repository policy granting ecr:BatchGetImage and ecr:GetDownloadUrlForLayer. Images can also come from a private Docker registry inside your VPC (RepositoryAccessMode Vpc).
An immutable, scanned repository and an extended LMI image (Bash, AWS CLI and Docker) 
aws ecr create-repository --repository-name retail/product-copy-lmi \
    --image-tag-mutability IMMUTABLE
aws ecr put-registry-scanning-configuration --scan-type ENHANCED \
    --rules '[{"repositoryFilters":[{"filter":"retail/*","filterType":"WILDCARD"}],"scanFrequency":"CONTINUOUS_SCAN"}]'

# Dockerfile: FROM 763104351884.dkr.ecr.us-east-1.amazonaws.com/djl-inference:0.38.0-lmi30.0.0-cu130
#             COPY serving.properties /opt/ml/model/
docker build -t 111111111111.dkr.ecr.us-east-1.amazonaws.com/retail/product-copy-lmi:2026-11-11 .
docker push 111111111111.dkr.ecr.us-east-1.amazonaws.com/retail/product-copy-lmi:2026-11-11

Image size drives scale-out time. SageMaker now caches images automatically on new instances for accelerator endpoints (AWS measured an LLM endpoint scaling out in 258 seconds instead of 525), but smaller images still start faster.

Endpoints in a VPC

Skill 3.2.4Configure SageMaker AI endpoints within VPC network environments.

  • Model VpcConfig (1 to 5 security groups, 1 to 16 subnets): SageMaker attaches network interfaces in your subnets so the container can reach resources in your VPC, with no internet access. Use subnets in at least two Availability Zones, even for one instance.
  • Without VpcConfig, containers have internet access by default but can't reach your private resources.
  • EnableNetworkIsolation blocks all outbound network calls from the container, even to AWS services. SageMaker still downloads the model artifacts and image for it, using the execution role.
  • Reaching AWS services privately: an S3 gateway endpoint for artifacts and data capture, and interface endpoints for anything else the code calls; otherwise a NAT gateway.
  • Calling the endpoint privately: interface endpoints for com.amazonaws.<region>.sagemaker.runtime (invocations) and sagemaker.api (management), and for Bedrock bedrock-runtime, bedrock-agent-runtime, bedrock and bedrock-agent. An endpoint policy can limit which endpoints may be invoked through it.
A churn model that runs only inside the private subnets (Python, boto3) 
import boto3

sm = boto3.client("sagemaker")
sm.create_model(
    ModelName="churn-xgb-2026-11",
    ExecutionRoleArn="arn:aws:iam::111111111111:role/SageMakerHostingRole",
    PrimaryContainer={
        "Image": "683313688378.dkr.ecr.us-east-1.amazonaws.com/sagemaker-xgboost:3.2-0",
        "ModelDataUrl": "s3://retail-ml-111111111111/churn/models/2026-11-01/model.tar.gz",
    },
    VpcConfig={
        "Subnets": ["subnet-0a1b2c3d4e5f60001", "subnet-0a1b2c3d4e5f60002"],  # two AZs
        "SecurityGroupIds": ["sg-0a1b2c3d4e5f60003"],
    },
    EnableNetworkIsolation=True,
)

Enforce it with IAM condition keys, so nobody can create a model outside the approved network:

Allow CreateModel only with the approved subnets and network isolation (JSON, IAM policy statement) 
{
  "Effect": "Allow",
  "Action": "sagemaker:CreateModel",
  "Resource": "*",
  "Condition": {
    "ForAllValues:StringEquals": {"sagemaker:VpcSubnets": ["subnet-0a1b2c3d4e5f60001", "subnet-0a1b2c3d4e5f60002"]},
    "Null": {"sagemaker:VpcSubnets": "false"},
    "StringEquals": {"sagemaker:NetworkIsolation": "true"}
  }
}

Without the Null condition, a request with no VPC settings passes the ForAllValues check. A policy that limits callers with aws:SourceVpce also blocks the SageMaker console. Serverless endpoints don't support VPC configuration.

Deploying programmatically

Skill 3.2.5Deploy and host models programmatically (for example, by using the SageMaker AI SDK for Python, AWS CLI, Boto3).

The same three objects in every tool: a model (image, artifacts, role, network), an endpoint configuration (variants, instance types and counts, data capture, async or serverless settings) and an endpoint. In the SDK, ModelBuilder builds and deploys them in one call; boto3 and the CLI create each explicitly.

Create, wait for and later update the churn endpoint (Bash, AWS CLI) 
aws sagemaker create-endpoint-config --endpoint-config-name churn-cfg-2026-11 \
    --production-variants '[{"VariantName":"AllTraffic","ModelName":"churn-xgb-2026-11","InstanceType":"ml.m5.xlarge","InitialInstanceCount":2}]'
aws sagemaker create-endpoint --endpoint-name churn-endpoint --endpoint-config-name churn-cfg-2026-11
# Polls every 30 seconds; gives up after 120 checks (about an hour)
aws sagemaker wait endpoint-in-service --endpoint-name churn-endpoint

# New model later: a new config, then update in place (new fleet first, no downtime)
aws sagemaker update-endpoint --endpoint-name churn-endpoint --endpoint-config-name churn-cfg-2026-12
  • boto3 has the waiters endpoint_in_service and endpoint_deleted; there is none for inference components, so poll describe_inference_component.
  • Every update needs a new endpoint configuration. Don't delete a configuration an endpoint is using. UpdateEndpointWeightsAndCapacities changes traffic weights and instance counts without a new configuration.
  • Autoscaled endpoints: an update that changes the instance type (or removes a variant) fails while autoscaling is registered; deregister the scalable target, update, then register again. Changing only the model is allowed.
  • Clean up in order: endpoint, endpoint configuration, model. Deleting the endpoint stops the charges but leaves the configuration, the model and the S3 artifacts.

Auto scaling metrics

Skill 3.2.6Select specific metrics for auto scaling implementations.

  • SageMakerVariantInvocationsPerInstance (requests per minute per instance) for classic short requests. Load test one instance to find its peak requests per second, then set the target to peak × 0.5 (AWS's suggested starting safety factor) × 60.
  • SageMakerVariantConcurrentRequestsPerModelHighResolution (and the per-copy version for inference components) for generative AI and streaming: it counts requests in flight, including queued ones and streams until the last token, and is published every 10 seconds, so scale-out reacts much faster.
  • SageMakerInferenceComponentInvocationsPerCopy for inference components (the scalable dimension is the copy count).
  • ApproximateBacklogSizePerInstance for asynchronous endpoints; SageMakerVariantProvisionedConcurrencyUtilization for serverless provisioned concurrency.
  • CPU or GPU utilization as a custom metric when compute is the bottleneck (Skill 3.2.10).
Scale the GPU endpoint on concurrent requests (Python, boto3) 
import boto3

aas = boto3.client("application-autoscaling")
resource = "endpoint/product-copy-endpoint/variant/AllTraffic"

aas.register_scalable_target(
    ServiceNamespace="sagemaker",
    ResourceId=resource,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    MinCapacity=1,
    MaxCapacity=6,
)
aas.put_scaling_policy(
    PolicyName="concurrency-target",
    ServiceNamespace="sagemaker",
    ResourceId=resource,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    PolicyType="TargetTrackingScaling",
    TargetTrackingScalingPolicyConfiguration={
        "TargetValue": 5.0,  # requests in flight per model copy
        "PredefinedMetricSpecification": {
            "PredefinedMetricType": "SageMakerVariantConcurrentRequestsPerModelHighResolution"},
        "ScaleOutCooldown": 180,
        "ScaleInCooldown": 600,
    },
)
  • Policy types: target tracking (AWS's recommendation in most cases), step scaling (needed to scale out from zero), and scheduled actions (CLI or API only) for known peaks such as Monday mornings.
  • Behaviour: default cooldowns are 300 seconds; target tracking adds capacity quickly and removes it cautiously (only when the metric is well below target). With several policies, any one can scale out but all must agree to scale in.
  • Custom metrics must change in proportion to capacity: adding instances should lower the value.

Knowledge bases

Skill 3.2.7Create and manage Amazon Bedrock knowledge bases with vector database configurations, document indexing, and retrieval optimization.

  • Managed knowledge base: Bedrock chooses and runs the embedding model, vector storage, hybrid search and reranking; you add connectors and permissions, and it can sync on a schedule.
  • Customer-managed knowledge base: you choose the embedding model (and its dimensions and data type) and the vector store: OpenSearch Serverless or managed clusters, S3 Vectors, Aurora PostgreSQL (RDS type), Neptune Analytics, MongoDB Atlas, Pinecone or Redis. The embedding model and store can't be changed after creation.
  • Data sources (S3 and connectors) carry the chunking strategy and parser; StartIngestionJob syncs changes incrementally (only added, changed or deleted files), and IngestKnowledgeBaseDocuments adds or updates single documents directly. Metadata files next to documents enable filtering.
  • Retrieval optimization (number of results, hybrid search, filters, reranking) is covered in Task 2.2 and Task 3.1.
A customer-managed knowledge base on S3 Vectors (Python, boto3) 
import boto3

agent = boto3.client("bedrock-agent", region_name="us-east-1")
kb = agent.create_knowledge_base(
    name="help-centre",
    roleArn="arn:aws:iam::111111111111:role/BedrockKbServiceRole",
    knowledgeBaseConfiguration={
        "type": "VECTOR",
        "vectorKnowledgeBaseConfiguration": {
            "embeddingModelArn": "arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-embed-text-v2:0",
            "embeddingModelConfiguration": {"bedrockEmbeddingModelConfiguration": {
                "dimensions": 1024, "embeddingDataType": "FLOAT32"}},
        },
    },
    storageConfiguration={
        "type": "S3_VECTORS",
        # indexArn alone, or vectorBucketArn plus indexName, never both forms
        "s3VectorsConfiguration": {
            "indexArn": "arn:aws:s3vectors:us-east-1:111111111111:bucket/help-vectors/index/articles"},
    },
)
print(kb["knowledgeBase"]["knowledgeBaseId"])

The vector index dimension must match the embedding model's (1,024 here). More detail in the customer-managed knowledge base notes.

Retrieval pipelines

Skill 3.2.8Implement retrieval pipelines to meet business needs.

  • Freshness: customer-managed knowledge bases don't sync themselves (managed ones can be scheduled since September 2026), and CloudFormation creates a data source without ingesting it. Trigger StartIngestionJob on a schedule (EventBridge Scheduler or Step Functions), or from S3 events through Lambda; ingestion jobs emit no EventBridge events, so poll GetIngestionJob for the result.
  • Multi-tenant isolation: AWS's suggested pattern is one shared knowledge base with a tenant attribute in each document's metadata and a mandatory filter on every query, injected on the server from the authenticated identity, never from the client. Separate knowledge bases per tenant isolate more strongly but multiply resources (a knowledge base allows 5 data sources).
  • Custom pipelines: Lambda or Step Functions calling Bedrock embeddings and your own store, when you need steps a knowledge base doesn't offer. Step Functions' optimized Bedrock integration covers InvokeModel and customization jobs; streaming and agentic APIs aren't supported there.
  • Cost and latency: prompt caching for the fixed instructions, and a semantic cache (for example Amazon ElastiCache) for repeated questions.
Re-sync the knowledge base when help articles change (Python, Lambda handler for S3 events) 
import boto3

agent = boto3.client("bedrock-agent")

def handler(event, context):
    # One ingestion job per knowledge base at a time; a running job raises ConflictException
    try:
        job = agent.start_ingestion_job(knowledgeBaseId="KB12345678", dataSourceId="DS12345678")
        return {"jobId": job["ingestionJob"]["ingestionJobId"]}
    except agent.exceptions.ConflictException:
        return {"skipped": "sync already running"}

Agent state

Skill 3.2.9Implement agent state management systems.

  • Session state is not durable: each AgentCore Runtime session runs in its own microVM, ended after 15 minutes idle or 8 hours by default; reusing the session ID afterwards gives a new, empty environment. Keep anything that must survive elsewhere.
  • AgentCore Memory, short-term: events (conversation turns or JSON) stored per actorId (the customer) and sessionId with CreateEvent, read back with ListEvents; they expire after the configured period.
  • AgentCore Memory, long-term: strategies extract records asynchronously from events: semantic (facts), user preference, summary (per session) and episodic (what happened and how it went), stored under namespaces such as /strategy/{memoryStrategyId}/actors/{actorId}/ and searched with RetrieveMemoryRecords. Use namespaces, not metadata alone, to separate customers.
  • Framework session managers: Strands Agents can persist the conversation and agent state to S3 or local files, and has an AgentCore Memory session manager; a custom repository can store sessions in DynamoDB.
  • Workflow state: Step Functions (Standard workflows) or Lambda durable functions keep the state of long, multi-step processes with retries and waits for approval.
Store a support conversation turn in AgentCore Memory (Python, boto3) 
from datetime import datetime, timezone

import boto3

memory = boto3.client("bedrock-agentcore", region_name="us-east-1")
memory.create_event(
    memoryId="support_memory-a1b2c3d4e5",
    actorId="customer-48213",
    sessionId="chat-2026-11-11-0915",
    eventTimestamp=datetime.now(timezone.utc),
    payload=[
        {"conversational": {"role": "USER", "content": {"text": "My jacket zip broke, order 12345."}}},
        {"conversational": {"role": "ASSISTANT", "content": {"text": "Sorry about that. I've started a repair claim."}}},
    ],
)
# Next visit: retrieve_memory_records() in this customer's namespace recalls the claim

Long-term records are extracted only from events stored after a strategy is active (no backfill), and extraction is asynchronous, so a fact said a moment ago may not be retrievable yet; keep the recent turns from short-term memory in the prompt. Strands session managers have no locking, so two sessions must not write the same session ID at once.

Scaling GPU workloads

Skill 3.2.10Implement AI-specific resource scaling for GPU workloads.

  • Scale on load, not only on GPU busy-ness: for LLMs, the high-resolution concurrency metrics track the real load (requests in flight); GPU utilization can read near 100% while capacity remains. AWS's EKS guidance likewise recommends scaling inference on requests or token throughput.
  • GPU metrics live in /aws/sagemaker/Endpoints: GPUUtilization and GPUMemoryUtilization are summed across GPUs (0 to 400% on a 4-GPU instance); inference component endpoints add normalized (0 to 100%) and reservation metrics. There's no predefined GPU scaling metric, so use a customized metric.
  • Inference components scale copies of a model, and managed instance scaling adds or removes instances to fit them, down to zero.
  • Slow scale-out: GPU instances take minutes (image pull, model download, loading), so scale out early, keep a minimum warm, and raise the startup timeouts.
  • Capacity: GPU instance quotas often start at 0 for P instances; request increases in Service Quotas before launch, and use training plans, instance pools or several instance types when capacity is scarce.
  • Kubernetes: Karpenter node pools for GPU instances (with the NVIDIA device plugin), KEDA for request-based scaling, and HyperPod's managed Karpenter.
A GPU memory scaling target for an inference component endpoint (JSON, TargetTrackingScalingPolicyConfiguration) 
{
  "TargetValue": 70.0,
  "CustomizedMetricSpecification": {
    "MetricName": "GPUMemoryUtilizationNormalized",
    "Namespace": "/aws/sagemaker/InferenceComponents",
    "Dimensions": [{"Name": "InferenceComponentName", "Value": "product-copy-ic"}],
    "Statistic": "Average",
    "Unit": "Percent"
  },
  "ScaleOutCooldown": 180,
  "ScaleInCooldown": 600
}

Agentic workflow infrastructure

Skill 3.2.11Deploy agentic workflow infrastructure.

  • The pieces: an AgentCore Runtime (the agent code) with a runtime endpoint, a Gateway and its targets (tools), a Memory resource, Identity credential providers for outbound OAuth or API keys, optional Policy for tool calls, and the models, knowledge bases and guardrails they use.
  • As code: CloudFormation types AWS::BedrockAgentCore::Runtime, RuntimeEndpoint, Gateway, GatewayTarget, Memory (which requires an event expiry of 3 to 365 days), WorkloadIdentity and the credential providers; or the stable CDK constructs; or the AgentCore CLI (agentcore deploy, which uses CDK).
  • Networking: Runtime runs in public mode or in VPC mode (your subnets and security groups) when tools live in private networks; add VPC endpoints for the AWS services the agent calls.
  • Access: callers need InvokeAgentRuntime or InvokeGateway, or sign in through a JWT authorizer; the Runtime execution role needs model, memory and tool permissions; the Gateway role needs permission to invoke its Lambda targets.
  • Observability: turn on CloudWatch Transaction Search so AgentCore traces and spans appear in the GenAI observability views.

Details in the AgentCore Runtime and Memory and tools notes.

Resource names differ: Runtime and Memory names can't contain hyphens (Gateway names can), and Ref returns different things per type (the memory's ARN, the gateway's ID). Changing a Memory's name or encryption key in CloudFormation replaces it, and its stored events with it.

Key takeaways

  • Capacity: on demand plus autoscaling for variable load; Savings Plans for price (not capacity); training plans to guarantee endpoint GPUs; provisioned concurrency and Provisioned Throughput only where steady use or cold starts justify them.
  • IaC: CloudFormation or CDK for SageMaker, Bedrock and AgentCore resources; exports for strong links, SSM parameters or Fn::GetStackOutput for loose ones; Ref returns ARNs for SageMaker hosting resources.
  • Containers: extend AWS images, build in CodeBuild, immutable tags and digests, enhanced scanning for language packages, lifecycle policies, cross-account repository policies.
  • VPC: two-AZ subnets and security groups on the model, network isolation, S3 gateway and interface endpoints, condition keys with a Null check; serverless has no VPC.
  • Deploying: model, endpoint config, endpoint; a new config for every update; deregister autoscaling before changing instance types; delete endpoints to stop charges.
  • Scaling metrics: invocations per instance (target = peak × 0.5 × 60), high-resolution concurrency for LLMs, per-copy metrics for inference components, backlog for async.
  • Knowledge bases: managed or customer-managed with a fixed embedding model and store; schedule or trigger ingestion yourself; one shared knowledge base with a server-side tenant filter.
  • Agent state: Runtime sessions are ephemeral; AgentCore Memory short-term events and long-term strategies by namespace; session managers to S3 or DynamoDB; Step Functions for workflow state.
  • GPUs and agents: scale on concurrency, GPU metrics are summed across GPUs, request GPU quotas early; deploy Runtime, Gateway, Memory and Identity together as code, in VPC mode when tools are private.
