Overview

Task 2.3

Analyze and evaluate the performance of ML and AI systems.

Questions in this task give a result and ask what it means or how to measure it properly: which metric fits an imbalanced problem, how to compare a new model with production without affecting users, why a loss curve looks wrong, how to show which features drove a prediction, which score suits translation versus summarization, and how to keep checking a RAG assistant after launch. Two habits: always compare against a baseline (the previous model, or a trivial one), and record everything needed to repeat a result.

Running example. The online retailer (account 111111111111) has a churn model in production, a candidate model to replace it, and a support assistant that answers from help articles and summarizes tickets.

Reproducible experiments

Skill 2.3.1Perform reproducible experiments (for example, by using MLflow on SageMaker AI, Amazon Bedrock evaluations, Amazon Bedrock Prompt Management).

An experiment is reproducible when someone else can rerun it and get the same result: same data version, same code and container, same hyperparameters, same random seeds, and the results recorded next to all of them.

  • MLflow on SageMaker AI records parameters, metrics, tags, artifacts and models per run, grouped into experiments. Two forms: MLflow Apps (serverless, no extra charge, upgraded automatically; AWS's recommended choice) and tracking servers (Small, Medium or Large, a chosen MLflow version, billed per hour). Both use the sagemaker-mlflow plugin with the app or server ARN as the tracking URI, and models logged with a registered name appear in the SageMaker Model Registry.
  • Bedrock evaluations are repeatable when the dataset, the model ID, the inference parameters and the judge model stay the same; keep the job configuration with the results.
  • Bedrock Prompt Management versions are immutable, so a test can name exactly which prompt version was used (see the Bedrock build tools notes).
Log a churn training run to an MLflow App (Python, MLflow) 
import mlflow
from mlflow.models import infer_signature
from sklearn.metrics import roc_auc_score
from sklearn.model_selection import train_test_split
from xgboost import XGBClassifier

mlflow.set_tracking_uri("arn:aws:sagemaker:us-east-1:111111111111:mlflow-app/app-a1b2c3d4e5f6")
mlflow.set_experiment("churn-xgboost")

# Fixed seeds so the split and the model repeat exactly
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.2, stratify=y, random_state=42)
params = {"max_depth": 5, "learning_rate": 0.1, "n_estimators": 300, "random_state": 42}

with mlflow.start_run():
    model = XGBClassifier(**params).fit(X_train, y_train)
    mlflow.log_params(params)
    mlflow.log_metric("test_auc", roc_auc_score(y_test, model.predict_proba(X_test)[:, 1]))
    mlflow.set_tag("data_version", "s3://retail-ml-111111111111/churn/2026-11-01/")
    mlflow.xgboost.log_model(
        model,
        name="churn_model",  # MLflow 3 renamed artifact_path to name
        signature=infer_signature(X_train, model.predict(X_train)),
        registered_model_name="churn-xgboost",
    )

Pin the container image version, not latest, and record the exact S3 location (or version) of the data, or the "same" run next month uses different code or data. "Compare dozens of training runs and their metrics side by side" points to MLflow; "compare prompt versions on the same dataset" points to Prompt Management versions plus a Bedrock evaluation job.

Baselines and drift

Skill 2.3.2Create model performance baselines and implement drift detection.

A baseline is the reference that later data and results are compared with: statistics of the training data (or a representative subset that did well in validation), and the model's metrics on a held-out set. Then watch for:

  • Data drift: the inputs change (new customer segments, a new product range).
  • Concept drift: the relationship between inputs and the label changes (a competitor's offer makes loyal customers leave).
  • Model quality drift: accuracy, F1 or AUC fall once ground truth arrives, often weeks later.
  • Bias drift: metrics diverge between groups; compare per-segment metrics against the baseline.

With Model Monitor closed to new customers, AWS's documented replacement uses the open-source Evidently library: DataDriftPreset computes the population stability index (PSI) and Kolmogorov-Smirnov (KS) statistics for each feature, with the training data as the reference and recent inference data as the current set; ClassificationPreset tracks model quality when ground truth arrives, matched by inference ID. Results go to an MLflow App, and alerts go through EventBridge, Lambda and SNS. AWS's samples (in the sample-aiops-on-amazon-sagemakerai GitHub repository) alert when more than 30% of features drift. For a simple numeric signal, publish your own metric and use a CloudWatch anomaly detection alarm, which learns the normal band from up to two weeks of history.

PSI for one feature, published as a CloudWatch metric (Python, boto3) 
import boto3
import numpy as np

def psi(reference, current, bins=10):
    edges = np.quantile(reference, np.linspace(0, 1, bins + 1))
    ref = np.histogram(reference, edges)[0] / len(reference)
    cur = np.histogram(current, edges)[0] / len(current)
    ref, cur = np.clip(ref, 1e-6, None), np.clip(cur, 1e-6, None)
    return float(np.sum((cur - ref) * np.log(cur / ref)))

score = psi(train_df["monthly_charges"], last_week_df["monthly_charges"])
boto3.client("cloudwatch").put_metric_data(
    Namespace="Retail/ChurnModel",
    MetricData=[{"MetricName": "PSI_monthly_charges", "Value": score,
                 "Dimensions": [{"Name": "Model", "Value": "churn-xgboost"}]}],
)
# A common rule of thumb: PSI above about 0.2 is a significant shift
  • Act on drift, not on a calendar: AWS's guidance is to trigger retraining (for example a SageMaker pipeline) when drift crosses a threshold, and to record each incident.
  • Generative AI: watch CloudWatch AWS/Bedrock metrics (latency, tokens, throttles), store prompts and responses with model invocation logging, and re-run evaluations on sampled traffic (Skill 2.3.10). More in the monitoring without Model Monitor notes.

Shadow variants

Skill 2.3.3Compare the performance of shadow variants to production variants.

A SageMaker AI shadow test sends a copy of live requests to a new model (the shadow variant) alongside the current one (the production variant). Only the production response goes back to the caller; the shadow's responses are captured for comparison, so users are never affected.

  • Created with CreateInferenceExperiment (type ShadowMode) on an existing endpoint, or in the console. One production and one shadow variant; the shadow receives a sampling percentage of traffic (up to 100%). Tests run for 7 days by default and up to 30.
  • The dashboard compares operational metrics: invocations, model latency, errors, CPU, memory and disk. To compare accuracy, capture the requests and responses to S3 (DataStorageConfig) and score both sets offline against ground truth.
  • At the end, promote the shadow (it replaces production; AWS recommends keeping the production instance settings), remove it, or retain it. Otherwise the endpoint returns to its earlier state.
  • Not available for serverless, asynchronous, multi-model or multi-container endpoints.
Shadow the candidate churn model at 50% of traffic (JSON, CreateInferenceExperiment)

Promote with StopInferenceExperiment and "ModelVariantActions": {"production": "Remove", "shadow": "Promote"}.

Shadow testing compares without user impact. A/B testing splits real traffic between production variants by weight, so some users get the new model's answers (use TargetVariant to force a variant and UpdateEndpointWeightsAndCapacities to shift traffic). Blue/green deployment with alarms is a safe rollout with automatic rollback, not a comparison (Domain 3).

Explaining outputs

Skill 2.3.4Explain model outputs.

  • Local explanations say why one prediction came out as it did: SHAP values give each feature's contribution, pushing the prediction up or down from the average (base value).
  • Global explanations say what drives the model overall: the mean absolute SHAP value per feature, and partial dependence or SHAP dependence plots showing how the prediction changes with one feature.
  • Which method: tree SHAP for tree models (fast and exact), integrated gradients for neural networks, Kernel SHAP for anything (slow with many features). Canvas shows column impact.

Clarify computed SHAP values; AWS's replacement guidance is to use the open-source shap library directly ("the same engine Clarify uses"), as AWS's own sample notebook does for an XGBoost model, logging the plots to MLflow:

Explain the churn model with SHAP (Python, shap) 
import mlflow
import shap

booster = model.get_booster()
# No background data needed with the tree path method
explainer = shap.TreeExplainer(booster, data=None, feature_perturbation="tree_path_dependent")
shap_values = explainer.shap_values(X_test)

# Global: average impact of each feature
shap.summary_plot(shap_values, X_test, plot_type="bar", show=False)
# Local: why one customer is predicted to churn (values are in log-odds)
shap.plots.waterfall(shap.Explanation(values=shap_values[0], base_values=explainer.expected_value,
                                      data=X_test.iloc[0], feature_names=list(X_test.columns)))

with mlflow.start_run(run_name="shap-analysis"):
    mlflow.log_dict(dict(zip(X_test.columns, abs(shap_values).mean(axis=0).tolist())),
                    "shap_feature_importance.json")

Generative AI outputs are explained differently:

  • Citations: knowledge base answers return the retrieved passages each part of the answer is based on (retrievedReferences); Converse can return citations for supplied documents.
  • Reasoning content: models with reasoning return a reasoningContent block (for newer Claude models, a summary of the thinking).
  • Traces: Guardrails traces show which policy blocked or masked content (and contain the unmasked values, so protect them); agent traces and AgentCore Observability show each step and tool call.
  • Automated Reasoning checks in Guardrails explain a verdict with the rules that support or contradict the answer.

Debugging convergence

Skill 2.3.5Debug model convergence issues.

  • Loss not decreasing (flat from the start): learning rate too low, features not scaled, a bug in labels or data loading, or weights initialized badly. Check that the model can overfit a tiny sample; if it can't, the problem is the code or data.
  • Loss exploding or NaN: learning rate too high (it "overshoots the minimum"), exploding gradients, unscaled inputs, or bad values in the data. Lower the learning rate, normalize inputs, clip gradients, check for infinities.
  • Loss oscillating: learning rate too high or batches too small and noisy; use a learning-rate schedule or a larger batch.
  • Vanishing gradients (early layers stop learning): saturating activations or too-small initialization; ReLU-family activations, normalization layers and proper initialization (such as Xavier) help.
  • Distributed jobs can fail to converge when each node reads files in a different order, or when the per-GPU batch becomes very small; sort input files in the script and adjust batch size and learning rate together.
  • Training fine, validation getting worse: overfitting, not a convergence problem (Task 2.2).

Tools now that SageMaker Debugger (whose rules such as LossNotDecreasing, VanishingGradient and ExplodingTensor detected these automatically) is closed to new customers:

  • TensorBoard in SageMaker AI reads training output from S3 to show loss curves, weights and gradients (PyTorch, TensorFlow, Hugging Face; the domain needs Amazon EFS, and it doesn't support tuning jobs out of the box).
  • MLflow metrics per step, CloudWatch metrics from metric definitions, and the job's logs in the /aws/sagemaker/TrainingJobs log group.
  • Bedrock fine-tuning writes step_wise_training_metrics.csv (training loss per step) and validation_metrics.csv to the output location.
Send TensorBoard logs from a PyTorch job to S3 (Python, SageMaker Python SDK v3)

Evaluating ML and GenAI models

Skill 2.3.6Apply comprehensive model evaluation techniques for traditional ML and GenAI models.

Classification (from the confusion matrix of true and false positives and negatives):

  • Precision TP / (TP + FP): matters when a false positive is costly (an expensive retention offer sent to someone who would stay).
  • Recall TP / (TP + FN): matters when a miss is costly (fraud, disease, a valuable customer leaving). Predicting everything positive gives perfect recall, so never use it alone.
  • F1: harmonic mean of precision and recall; balanced accuracy averages recall on each class; both suit imbalanced data, where plain accuracy misleads.
  • AUC-ROC: ranking quality across all thresholds (0.5 is random); AUC-PR is more informative when positives are rare; log loss punishes confident wrong probabilities.
  • Threshold: the default 0.5 is rarely right; choose it from the precision-recall trade-off the business needs (Linear Learner can pick it for a target precision or recall).

Regression: MAE (average error in the target's units, robust to outliers), MSE and RMSE (punish large errors; RMSE is in the target's units), R² (share of variance explained; below 0 means worse than predicting the mean), MAPE (percentage error; breaks near zero). Forecasting adds weighted quantile loss, WAPE and MASE (below 1 beats a naive forecast).

  • Validation: a holdout set never used in training or tuning; k-fold cross-validation for small datasets (Autopilot uses 5 folds up to 50,000 rows); time-based splits or backtests for anything sequential.
  • Baselines: always beat a trivial model (the majority class, the mean, last week's value) and the current production model.
  • Offline vs online: offline on historical holdout data first, then online with shadow tests or A/B tests on live traffic, because offline gains don't always survive real users.
  • Generative AI: combine automatic metrics, judge models and human review on a fixed evaluation set, plus safety checks; the next four skills cover each.
Compare the model with a trivial baseline (Python, scikit-learn) 
from sklearn.dummy import DummyClassifier
from sklearn.metrics import average_precision_score, balanced_accuracy_score, f1_score

baseline = DummyClassifier(strategy="most_frequent").fit(X_train, y_train)
for name, m in [("baseline", baseline), ("xgboost", model)]:
    pred = m.predict(X_test)
    prob = m.predict_proba(X_test)[:, 1]
    print(name, "F1", round(f1_score(y_test, pred), 3),
          "balanced acc", round(balanced_accuracy_score(y_test, pred), 3),
          "AUC-PR", round(average_precision_score(y_test, prob), 3))
# The baseline is 94% accurate on 6% churn, but its F1 is 0

Human evaluation

Skill 2.3.7Implement integrated human evaluation frameworks (for example, human-in-the-loop workflows, text generation quality assessment).

People are the reference for qualities metrics miss: helpfulness, correctness, tone, completeness. Amazon Bedrock human evaluation jobs send prompts and responses from up to two models (Bedrock models or your own precomputed responses) to your own work team, with instructions and your metrics. Rating methods:

  • ThumbsUpDown: acceptable or not.
  • IndividualLikertScale: a 5-point score for one response.
  • ComparisonLikertScale, ComparisonChoice and ComparisonRank: preference between two models' responses.
The human part of a Bedrock evaluation job (JSON, CreateEvaluationJob) 
{
  "human": {
    "humanWorkflowConfig": {
      "flowDefinitionArn": "arn:aws:sagemaker:us-east-1:111111111111:flow-definition/support-eval",
      "instructions": "Rate each answer for correctness against the policy and for the brand's friendly tone."
    },
    "customMetrics": [
      {"name": "Correctness", "ratingMethod": "IndividualLikertScale",
       "description": "1 = wrong or invented policy, 5 = fully correct"},
      {"name": "Preferred", "ratingMethod": "ComparisonChoice",
       "description": "Which answer would you rather send to the customer?"}
    ],
    "datasetMetricConfigs": [{"taskType": "Generation",
      "dataset": {"name": "support-prompts", "datasetLocation": {"s3Uri": "s3://retail-ml-111111111111/eval/prompts.jsonl"}},
      "metricNames": ["Correctness", "Preferred"]}]
  }
}
  • Design: clear criteria with examples of each score, several raters per item, a ground-truth answer as reference (raters don't score it), and a check on agreement between raters. Warn raters that they may see toxic content.
  • Human in the loop in production: with A2I closed to new customers, build review into the workflow yourself, for example a Step Functions task that waits for a reviewer with a task token (.waitForTaskToken, up to a year) before a low-confidence answer is sent.
  • Close the loop: store user feedback (thumbs up or down) with the request ID, and feed poorly rated conversations into evaluation sets.

NLP metrics

Skill 2.3.8Apply natural language processing (NLP) evaluation metrics (for example, bilingual evaluation understudy [BLEU], Recall-Oriented Understudy for Gisting Evaluation [ROUGE], BERTScore, semantic similarity).

  • BLEU: n-gram precision of the output against reference text, with a penalty for outputs that are too short; the classic metric for translation.
  • ROUGE: n-gram overlap oriented to recall of the reference; ROUGE-1 (words), ROUGE-2 (word pairs), ROUGE-L (longest common subsequence); the classic metric for summarization. AWS's open-source fmeval library defaults to ROUGE-2 and reports the F-measure.
  • METEOR: like ROUGE-1 but also matches stems and synonyms, so paraphrases score better.
  • BERTScore: compares contextual embeddings of output and reference words by cosine similarity, so it rewards the same meaning in different words (fmeval uses a DeBERTa model by default).
  • Semantic similarity: cosine similarity between embeddings of the output and the reference (for example with an embedding model on Bedrock).
  • QA metrics: exact match, quasi-exact match (ignoring case, punctuation and articles), and precision, recall and F1 over words.

Bedrock's automatic evaluation jobs use BERTScore for summarization accuracy, F1 for question answering, a real-world knowledge score for general text, word error rate for robustness, and a toxicity score; they don't compute BLEU or ROUGE. For those, use fmeval (ROUGE, METEOR, BERTScore) or the Amazon Nova evaluation recipes on SageMaker AI (which report BLEU and ROUGE).

Score one answer with fmeval's QA metrics (Python, fmeval) 
from fmeval.eval_algorithms.qa_accuracy import QAAccuracy, QAAccuracyConfig

# Several acceptable answers are separated by <OR>
scores = QAAccuracy(QAAccuracyConfig(target_output_delimiter="<OR>")).evaluate_sample(
    target_output="30 days<OR>thirty days",
    model_output="You can return items within 30 days of delivery.",
)
for s in scores:
    print(s.name, round(s.value, 2))  # exact match 0, but recall over words is high

Overlap metrics punish good paraphrases and reward fluent nonsense that reuses the reference's words. Use BLEU for translation and ROUGE for summarization when references exist, BERTScore or semantic similarity when wording can vary, and judge models or people for helpfulness and correctness.

AI evaluation and LLM judges

Skill 2.3.9Perform AI evaluation (for example, model output assessment, content quality validation, bias detection, LLM-as-a-judge frameworks).

LLM-as-a-judge uses a strong model to grade outputs against criteria, which scales like an automatic metric but judges meaning like a person. On Amazon Bedrock:

  • Built-in judge metrics: correctness, completeness, faithfulness, helpfulness, coherence, relevance, following instructions, professional style and tone, and the responsible AI metrics harmfulness, stereotyping and refusal (higher is worse for those three).
  • Custom metrics: your own judge instructions with {{prompt}}, {{prediction}} and {{ground_truth}} variables and a rating scale (up to 10 custom metrics per job).
  • Evaluate Bedrock models or your own precomputed responses, so models hosted anywhere can be compared. Keep the same judge model across runs.
A custom judge metric for policy accuracy (JSON, part of CreateEvaluationJob) 
{
  "customMetricConfig": {
    "customMetrics": [{"customMetricDefinition": {
      "name": "PolicyAccuracy",
      "instructions": "Does the response state the return policy correctly and only as written in the reference? Question: {{prompt}} Reference: {{ground_truth}} Response: {{prediction}}",
      "ratingScale": [
        {"definition": "Contradicts or invents policy", "value": {"floatValue": 0}},
        {"definition": "Partly correct", "value": {"floatValue": 0.5}},
        {"definition": "Fully correct", "value": {"floatValue": 1}}
      ]
    }}],
    "evaluatorModelConfig": {"bedrockEvaluatorModels": [{"modelIdentifier": "amazon.nova-pro-v1:0"}]}
  }
}
  • Other judges: Amazon Nova LLM-as-a-Judge on SageMaker AI compares two sets of responses pairwise and reports a win rate; AgentCore Evaluations scores live agent traces (goal success, tool selection, faithfulness and more), including sampled online evaluation.
  • Content quality and safety: screen outputs with Bedrock Guardrails and toxicity scores; check format and length rules in code.
  • Bias: the stereotyping judge metric, fmeval's prompt stereotyping (CrowS-Pairs) and toxicity evaluations, and comparing scores across groups of prompts (Task 1.3).
  • Judge pitfalls: judges can favour longer answers, the first of two answers, or their own model family; use clear rubrics, a reference answer, swap the order in pairwise tests, and check a sample against human ratings.

Monitoring RAG

Skill 2.3.10Configure RAG system monitoring, including retrieval accuracy assessment.

  • Retrieval accuracy: Bedrock RAG evaluation jobs score retrieval alone with context relevance (are the retrieved passages relevant?) and context coverage (do they contain what the reference answer needs?), and full answers with faithfulness (no claims beyond the passages), correctness, completeness and citation precision and coverage.
  • Operational metrics: CloudWatch metrics for knowledge base calls (invocations, errors, throttles) and for the model (latency, tokens).
  • Logs: knowledge base logging covers ingestion only (which files were indexed, skipped or failed to embed), not queries. Model invocation logging records prompts and responses for Converse and InvokeModel calls. Log each query, the retrieved chunk IDs and scores, and the answer from your application, or trace them with AgentCore Observability.
  • Quality over time: sample real queries, add reference answers for a golden subset, run a scheduled RAG evaluation job (EventBridge Scheduler and Lambda) with the same judge each time, publish the averages as CloudWatch metrics and alarm on drops; also re-run after re-ingesting documents or changing chunking or the embedding model.
Turn on model invocation logging for the assistant (Python, boto3) 
import boto3

boto3.client("bedrock").put_model_invocation_logging_configuration(loggingConfig={
    "cloudWatchConfig": {
        "logGroupName": "/retail/bedrock/invocations",
        "roleArn": "arn:aws:iam::111111111111:role/BedrockLoggingRole",
        # Bodies over 100 KB go to S3 only
        "largeDataDeliveryS3Config": {"bucketName": "retail-ml-logs-111111111111", "keyPrefix": "bedrock/large/"},
    },
    "textDataDeliveryEnabled": True,
    "imageDataDeliveryEnabled": False,
    "embeddingDataDeliveryEnabled": False,
})

Invocation logs contain customer prompts and answers: restrict access and set retention. Managed knowledge bases can't be evaluated directly by an evaluation job; evaluate their outputs as precomputed responses. Logging is per account and Region and is off by default.

Key takeaways

  • Reproducibility: MLflow (Apps preferred) for runs, parameters, metrics and models; fixed seeds, pinned images, recorded data versions; immutable prompt versions and fixed evaluation settings for GenAI.
  • Drift: baseline from training data and holdout metrics; data, concept, quality and bias drift; PSI and KS with Evidently and MLflow, CloudWatch anomaly alarms; retrain on drift.
  • Shadow tests: one shadow variant, users only see production, operational metrics on the dashboard, accuracy offline from captured data, then promote, remove or retain; A/B splits real users.
  • Explanations: SHAP (tree SHAP for trees) for local and global importance; citations, reasoning content and traces for GenAI.
  • Convergence: flat loss means low learning rate, scaling or data bugs; NaN or exploding means lower learning rate, normalize, clip; TensorBoard, MLflow and CloudWatch replace Debugger.
  • Metrics: precision for costly false positives, recall for costly misses, F1, balanced accuracy and AUC-PR for imbalance; MAE, RMSE and R² for regression; always beat a trivial baseline.
  • Human evaluation: Bedrock jobs with your own work team, thumbs, Likert, choice and ranking; build production review with Step Functions callbacks now that A2I is closed.
  • NLP metrics: BLEU for translation, ROUGE for summarization, METEOR adds synonyms, BERTScore and semantic similarity for meaning; Bedrock automatic jobs use BERTScore and F1.
  • Judges and RAG: built-in and custom judge metrics on Bedrock; context relevance and coverage for retrieval; log queries yourself because knowledge base logs cover ingestion only.
