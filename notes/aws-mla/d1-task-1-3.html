Overview

Task 1.3

Validate data quality and manage bias.

Questions in this task describe data that is incomplete, skewed, mislabeled or unsafe and ask for the check or fix: a rule that stops a pipeline when a column goes null, a split that keeps one customer out of both training and test sets, a metric that shows one group is under-represented, a way to stop a classifier ignoring a rare class, or the screening step that keeps toxic or malformed records out of a fine-tuning set. The habit behind the right answers is to measure first, then fix, then measure again, and to do it in the pipeline rather than once by hand.

Running example. The online retailer from Task 1.1 (account 111111111111): only 6% of customers churn, sign-ups from one region dominate the history, the nightly customer extract sometimes arrives half empty, and the support assistant's fine-tuning set is built from chat transcripts that contain the odd abusive message.

Data quality rules

Skill 1.3.1Validate data quality (for example, by using DataBrew, AWS Glue Data Quality).

AWS Glue Data Quality is serverless, built on the open-source Deequ library, and checks data against rules written in DQDL (Data Quality Definition Language). The result is a data quality score: the percentage of rules that passed. It runs in two places, and the exam likes the difference:

  • On Data Catalog tables ("data at rest"): for data stewards checking tables on a schedule. Only here can Glue recommend rules by profiling the table (StartDataQualityRuleRecommendationRun; an ADVANCED mode added in September 2026 uses Amazon Bedrock on a sample of rows and can suggest different rules each run). Billed at $0.44 per DPU-hour with at least 2 DPUs.
  • Inside a Glue ETL job ("data in transit"): the EvaluateDataQuality transform checks data before it lands. Only here do you get row-level results, so bad rows can be sent to a quarantine location, and the job can be set to fail before or after loading the target (the default is to carry on). The cost is the extra job time.
  • Both publish results to EventBridge (source aws.glue-dataquality, with the score and state) and CloudWatch, and both support ML anomaly detection: DetectAnomalies learns the normal range of a statistic such as row count and flags runs outside it. It needs at least three runs of history, and an anomaly doesn't lower the score.
A ruleset for the nightly customer extract (DQDL) 
Rules = [
    IsComplete "customer_id",
    IsUnique "customer_id",
    # At least 95% of rows must have a region
    Completeness "region" > 0.95,
    ColumnValues "plan" in ["basic", "plus", "premium"],
    ColumnValues "tenure_months" between -1 and 600,
    # Dynamic rule: no fewer rows than 80% of the last 7 runs' average
    RowCount > avg(last(7)) * 0.8,
    DataFreshness "signup_date" <= 24 hours,
    ReferentialIntegrity "region" "regions.code" = 1.0,
    DetectAnomalies "RowCount"
]
Check rows in an ETL job and quarantine the failures (Python, Glue PySpark) 
from awsglue.transforms import SelectFromCollection
from awsgluedq.transforms import EvaluateDataQuality

results = EvaluateDataQuality().process_rows(
    frame=customers_dyf,
    ruleset=customer_ruleset,
    publishing_options={
        "dataQualityEvaluationContext": "customer_extract",
        "enableDataQualityCloudWatchMetrics": True,
        "enableDataQualityResultsPublishing": True,
    },
)
rows = SelectFromCollection.apply(dfc=results, key="rowLevelOutcomes").toDF()

# Each row gets DataQualityRulesPass / Fail / Skip lists and a Passed or Failed result
good = rows.filter(rows.DataQualityEvaluationResult == "Passed")
bad = rows.filter(rows.DataQualityEvaluationResult == "Failed")
bad.write.mode("append").parquet("s3://retail-ml-111111111111/quarantine/customers/")
  • DQDL details that trip people up: IsComplete means 100% non-null while Completeness takes a ratio; between is exclusive; with threshold works only on ColumnValues, ColumnDataType and CustomSql; ColumnValues fails null values unless you allow NULL. Rules such as RowCount judge the whole dataset, so a row can pass even when the ruleset fails.
  • AWS Glue DataBrew checks quality in its own way: a ruleset (for example "no duplicate customer IDs", or "value A greater than value B in at least 95% of rows") is attached to a dataset and evaluated by a profile job, which also produces column statistics; a recipe job doesn't validate rules. Results go to EventBridge as DataBrew Ruleset Validation Result. DataBrew suits analysts working without code.
  • Data Wrangler in Canvas has a Data Quality and Insights report for a quick look at a sample or the whole dataset: missing and invalid values, outliers, duplicate rows, anomalous rows, class balance of the target, a quick XGBoost model, and per-feature prediction power, where a score near 1 usually means target leakage (see the Canvas and Data Wrangler notes).

"Stop bad records reaching the data lake and keep them for review" points to the EvaluateDataQuality transform in the ETL job with row-level outcomes; "suggest rules for an existing catalog table" points to Data Catalog rule recommendations; "alert when the score drops" points to an EventBridge rule on the data quality result event.

Labeling and annotation

Skill 1.3.2Label and annotate data.

Supervised models need labels, and label quality caps model quality. The ideas the exam tests are the same whichever tool you use:

  • Clear instructions and examples for labelers, several labelers per item where mistakes are costly, and a consolidation step (majority vote, or averaging boxes) that combines their answers.
  • Who labels: a private workforce (your employees or contractors, signed in through Amazon Cognito or your own identity provider) for confidential data, or a vendor workforce from AWS Marketplace. Older material also lists Amazon Mechanical Turk as a public workforce; never send it personal data.
  • Active learning cuts cost: people label a sample, a model learns from it and labels the items it is confident about, and only the hard ones go back to people. Ground Truth's automated data labeling worked this way for four task types (image classification, bounding boxes, semantic segmentation, text classification), needing at least 1,250 objects and ideally 5,000.
  • Task types to recognise: image classification, bounding boxes and segmentation; text classification and named entity recognition; video frame and 3D point cloud labeling.

Labels are usually stored as an augmented manifest: JSON Lines with a reference to each object, the label and a metadata object. Ground Truth wrote this format, and other services read it, such as Amazon Comprehend custom classification and SageMaker training channels with the AugmentedManifestFile type:

One labeled support message in an augmented manifest (JSON Lines) 
{"source": "Where is my refund? It has been two weeks.", "intent": 3, "intent-metadata": {"class-name": "refund_status", "confidence": 0.94, "type": "groundtruth/text-classification", "human-annotated": "yes", "job-name": "support-intents"}}
  • Simple formats also work: Comprehend custom classification accepts a two-column CSV with no header (CLASS,text).
  • For generative AI, "labeling" means writing or reviewing ideal responses and ranking pairs of answers. Amazon Bedrock model evaluation jobs can use human workers: a work team you create (managed by Cognito) rates or compares the responses of up to two models (see the Bedrock evaluation notes).

Ground Truth and A2I. Both have been closed to new customers since 30 July 2026, and AWS hasn't named a replacement for self-service labeling. New accounts build labeling with their own tool or a partner, or use Bedrock human evaluation for model outputs. Exam answers that say "use a private workforce for sensitive data" or "use active learning to reduce labeling cost" still hold (more in the Ground Truth and A2I notes).

Sources of bias

Skill 1.3.3Identify and mitigate sources of bias in data by using AWS tools and techniques (for example, dataset splitting, shuffling, augmentation).

Bias enters before any model is trained:

  • Sampling bias: the data doesn't represent the people or cases the model will see (most history comes from one region or one sales channel).
  • Historical bias: past decisions baked into the labels (who was offered a retention discount).
  • Measurement and label bias: a feature recorded differently for different groups, or labelers who disagree in a pattern.
  • Proxy features: a postcode or first name that stands in for a sensitive attribute even after that attribute is removed.
  • Leakage and ordering: the same customer in both training and test sets, or data sorted by date or class so that training batches aren't representative.

The techniques the skill names:

  • Splitting. Data Wrangler's Split data transform offers randomized, ordered (keep time order, for forecasting and anything where the future must not leak into the past), stratified (keep each class's share in every split; the column can have at most 100 distinct values) and split by key (one customer's rows never land in two splits). A random seed makes the split repeatable.
  • Shuffling. Shuffle before splitting unless order matters, and during training: a training channel's ShuffleConfig (a required Seed) reshuffles the input files every epoch in Pipe mode, and with ShardedByS3Key it also changes which node gets which files. Sharding splits by number of S3 objects, so a few huge files shard badly.
  • Augmentation and resampling. Add examples for under-represented groups: collect more, oversample, generate synthetic records, or augment images and text (Skill 1.3.5).
  • Removing or questioning features. Drop a sensitive attribute only after checking for proxies, and keep it aside for measuring bias even when the model doesn't use it.
A sharded, shuffled training channel (JSON, CreateTrainingJob) 
{
  "InputDataConfig": [{
    "ChannelName": "train",
    "DataSource": {"S3DataSource": {
      "S3DataType": "S3Prefix",
      "S3Uri": "s3://retail-ml-111111111111/churn/train/",
      "S3DataDistributionType": "ShardedByS3Key"
    }},
    "InputMode": "Pipe",
    "ShuffleConfig": {"Seed": 42}
  }]
}

A random split of customer events puts the same customer in training and test, so the test score measures memory, not generalisation. Split by key (customer ID) or by time; stratify when the label is rare so the test set still contains enough positives.

Bias metrics across data types

Skill 1.3.4Optimize multimodal data distributions by applying bias metrics across numeric, text, and image assets.

Pre-training bias metrics compare a facet (the attribute you check, such as region or age band) against the label, before any model exists. The favoured group is a and the disfavoured group is d. These are the metrics SageMaker Clarify computes, with their codes:

  • Class imbalance (CI): (na − nd) / (na + nd), from −1 to 1. It looks only at how many rows each group has, not at labels; 0 means equal numbers.
  • Difference in proportions of labels (DPL): the share of positive labels in group a minus that in group d, from −1 to 1. Positive means group a gets the good outcome more often in the training data.
  • Distribution distances: Kullback-Leibler (KL), Jensen-Shannon (JS), Lp-norm (LP) and total variation distance (TVD) compare the label distributions of the two groups (0 means identical); Kolmogorov-Smirnov (KS), from 0 to 1, is the largest gap between them.
  • Conditional demographic disparity (code CDDL): demographic disparity measured within subgroups of a group variable and averaged. It catches Simpson's paradox, where a gap overall disappears or reverses inside every subgroup.

Because Clarify is closed to new customers, AWS's guidance is to compute these with pandas, since they are simple arithmetic, and to track results in MLflow:

CI and DPL for the region facet (Python, pandas) 
import pandas as pd

df = pd.read_parquet("s3://retail-ml-111111111111/churn/train/")
# Facet: is the customer from the dominant region? Label: 1 = retained
a = df[df["region"] == "north"]
d = df[df["region"] != "north"]

ci = (len(a) - len(d)) / (len(a) + len(d))
dpl = a["retained"].mean() - d["retained"].mean()
print(f"CI={ci:.2f} DPL={dpl:.2f}")
# CI=0.64: about 82% of rows come from one region; collect or resample others

In Clarify's own analysis_config, the same check is "facet": [{"name_or_index": "region", "value_or_threshold": ["north"]}], "label_values_or_threshold": [1] and "methods": {"pre_training_bias": {"methods": ["CI", "DPL"]}}; Data Wrangler in Canvas also offers a Bias Report analysis with the same inputs.

The metrics work on table columns, so text and image data first need a column to measure:

  • Numeric and tabular: use the columns directly; turn numeric facets into groups with a threshold (age above 40).
  • Text: derive attributes with Amazon Comprehend, such as dominant language, sentiment or entities, then check how they are spread across labels (for example, that negative reviews aren't almost all in one language). Data Wrangler's text featurize adds length and character statistics.
  • Images: derive attributes with Amazon Rekognition (labels for scenes and objects; DetectFaces with Attributes=["ALL"] for age range and other face attributes, used only in aggregate, with AWS recommending a 99% confidence threshold for sensitive uses and never using predicted gender for decisions about a person).
  • Generative models: bias is measured on outputs: the open-source fmeval library's prompt stereotyping evaluation (CrowS-Pairs dataset) and Bedrock LLM-as-a-judge's Builtin.Stereotyping metric. Bedrock's automatic (programmatic) evaluation jobs have no stereotyping metric (more in Bedrock evaluation metrics).

"Before training, check whether one group is under-represented" means class imbalance (CI); "check whether one group already gets the positive label more often in the data" means DPL; "the gap disappears once you condition on department" means conditional demographic disparity. Post-training metrics (on predictions) belong to Domain 4.

Class imbalance

Skill 1.3.5Resolve class imbalance in numeric, text, and image datasets.

With 6% churners, a model that always predicts "stays" is 94% accurate and useless. The fixes, from data to algorithm to metric:

  • Resample (tabular): Data Wrangler's Balance data transform for binary classification offers random oversampling (repeat minority rows), random undersampling (drop majority rows, losing information) and SMOTE (create new minority rows by interpolating between neighbours, using numeric features for distance). It can't balance datasets with vector columns. Resample the training split only, never the test set.
  • Weight the loss: XGBoost scale_pos_weight (default 1; a typical value is negatives divided by positives); Linear Learner positive_example_weight_mult (default 1.0; set balanced or auto) and balance_multiclass_weights for multiclass; XGBoost csv_weights=1 to read per-row weights; Autopilot SampleWeightAttributeName (ensembling mode only).
  • Images: augment the rare class (flips, crops, colour shifts, rotation). The built-in image classification algorithm's augmentation_type (crop, crop_color, crop_color_transform) has no default, so augmentation is off unless set; use_weighted_loss applies only to multi-label jobs.
  • Text: generate or paraphrase extra examples for rare intents with an FM, back-translate, or collect more (Task 1.2 covers text augmentation).
  • Judge with the right metric: F1, precision and recall, AUC-PR or balanced accuracy instead of accuracy, and move the decision threshold. Autopilot's default objective for binary problems is F1; Linear Learner's default model selection criterion is accuracy, so change it (for example to f_beta or recall_at_target_precision).
Weight the rare churn class in XGBoost (Python, SageMaker Python SDK) 
negatives = (y_train == 0).sum()
positives = (y_train == 1).sum()

xgb.set_hyperparameters(
    objective="binary:logistic",
    # About 94 / 6, so each churner counts roughly 15 times
    scale_pos_weight=round(negatives / positives, 1),
    eval_metric="aucpr",
    num_round=300,
)

Oversampling or SMOTE before splitting copies minority rows, or near-copies, into the test set and inflates the score. Split first, resample the training data only, and evaluate on the untouched, naturally imbalanced test set.

Training data integrity for FMs

Skill 1.3.6Validate AI training data integrity (for example, prompt-response pair validation, content safety screening).

A fine-tuning job learns whatever is in the file, including mistakes and abuse. Amazon Bedrock doesn't document any screening of customization data for harmful content; that is your job, before the job starts. Three kinds of check:

  • Format and limits. Every line valid JSON in the model's format (Task 1.2 shows the shapes), roles in order (Amazon Nova: first turn user, last turn assistant), and counts and sizes within the model's limits: for Nova Micro, Lite and Pro 8 to 20,000 samples and a 32K context; for Nova 2 Lite fine-tuning 200 to 20,000 and no separate validation set. Nova jobs fail on reserved strings in prompts, such as User:, Assistant:, System:, Bot:, <image> and [EOS], which are common in exported chat logs. A bad file shows up as a Failed job with a failureMessage, after you have waited.
  • Pair quality. Each response actually answers its prompt, is correct and in the right tone; no duplicates; no test-set prompts in the training data (contamination); no personal data (Task 1.2). AWS's Nova guidance puts quality over quantity and says to deduplicate and review the data before training; an LLM judge can score pairs and drop weak ones.
  • Content safety. Screen every prompt and response for toxicity, hate, sexual content, violence and prompt attacks, and images for unsafe content.

AWS publishes a validator for Nova datasets in the amazon-nova-samples GitHub repository, which checks the format, roles, reserved strings, media rules and sample counts, then prints a pass rate and the first errors with line numbers:

Validate a Nova fine-tuning file before submitting it (Bash) 
python3 nova_ft_dataset_validator.py -i support-train.jsonl -m lite-2.0 -t sft -p bedrock
# Exit code 0 = PASS, 1 = errors (for example role_ordering_error on line 1834)

For content screening, the tools are:

  • Bedrock Guardrails ApplyGuardrail checks any text (and PNG or JPEG images) against a guardrail without calling a model. The response's top-level action is GUARDRAIL_INTERVENED or NONE, and assessments list each filter hit. Content filters cost $0.15 per 1,000 text units (1,000 characters each). The newer InvokeGuardrailChecks scores messages against chosen categories without creating a guardrail, at $0.07 per 1,000 text units for content filters (see ApplyGuardrail and InvokeGuardrailChecks).
  • Amazon Comprehend DetectToxicContent scores English text from 0 to 1 for PROFANITY, HATE_SPEECH, INSULT, GRAPHIC, HARASSMENT_OR_ABUSE, SEXUAL and VIOLENCE_OR_THREAT, plus an overall Toxicity score: up to 10 segments of 1 KB per call.
  • Amazon Rekognition DetectModerationLabels labels unsafe images with a three-level taxonomy (MinConfidence defaults to 50); StartMediaAnalysisJob handles batches of up to 10,000 images.
Screen fine-tuning pairs and keep only clean ones (Python, boto3) 
import json

import boto3

bedrock = boto3.client("bedrock-runtime")
kept, dropped = [], 0

with open("support-train-raw.jsonl") as f:
    for line in f:
        record = json.loads(line)
        texts = [c["text"] for m in record["messages"] for c in m["content"] if "text" in c]
        result = bedrock.apply_guardrail(
            guardrailIdentifier="training-data-screen",
            guardrailVersion="1",
            source="INPUT",
            content=[{"text": {"text": t}} for t in texts],
        )
        if result["action"] == "GUARDRAIL_INTERVENED":
            dropped += 1  # log the assessments for human review
        else:
            kept.append(line)

with open("support-train.jsonl", "w") as f:
    f.writelines(kept)
print(f"kept {len(kept)}, dropped {dropped}")
  • Integrity in storage: S3 adds a CRC64NVME checksum to new objects by default (since December 2024) when the client sends none, and rejects an upload whose checksum doesn't match; SageMaker ML Lineage Tracking records which dataset version produced which model.
  • Distillation from invocation logs: when you reuse logged prompt-response pairs, the teacher model in the job must match the model in the logs, otherwise the logs aren't used.

Comprehend's prompt safety classification (safe or unsafe prompt) closed to new customers on 30 April 2026; AWS points to the Guardrails prompt attack filter instead. DetectToxicContent is still available.

Cleaning data

Skill 1.3.7Clean data (for example, by detecting outliers, imputing missing data, deduplication).

  • Outliers. First ask whether the value is an error (age 230) or real but rare (one very large order). Data Wrangler in Canvas offers standard deviation, robust standard deviation (median based, less affected by the outliers themselves), quantile and min-max outlier transforms, each fixed by Clip, Remove or Invalidate, and Replace rare for rare categories. DataBrew's outlier steps use Z_SCORE, MODIFIED_Z_SCORE or IQR and can flag, remove, replace or rescale. For unusual whole records, the SageMaker Random Cut Forest algorithm scores anomalies; it isn't one of Canvas's outlier options.
  • Missing values. Drop rows only when few are missing at random. Otherwise impute: mean (skewed by outliers), median, most frequent value for categories, a constant, or forward fill and interpolation for time series. Add a missing indicator column when the absence itself carries meaning (no phone number on file). Fit imputation values on the training split only. Canvas offers Fill missing, Impute missing, Add indicator for missing and Drop missing; DataBrew has FILL_WITH_MEDIAN and similar steps.
  • Duplicates. Exact duplicates are removed with DataBrew DELETE_DUPLICATE_ROWS or Spark dropDuplicates, and detected with Glue Data Quality IsUnique or IsPrimaryKey. Fuzzy duplicates with no shared key ("Jon Smith, 1 High St" and "John Smith, 1 High Street") need the FindMatches ML transform (now documented as Lake Formation record matching), which you teach with labeled example pairs and which adds a match_id or removes the duplicates.
  • Other cleanup: fix types and units, trim whitespace and standardise case, and drop rows with an invalid label.
A DataBrew recipe: flag outliers, impute, deduplicate (JSON) 
[
  {"Action": {"Operation": "FLAG_OUTLIERS", "Parameters": {
    "sourceColumn": "order_total_90d", "targetColumn": "order_total_outlier",
    "outlierStrategy": "IQR", "threshold": "1.5",
    "trueString": "yes", "falseString": "no"}}},
  {"Action": {"Operation": "FILL_WITH_MEDIAN", "Parameters": {
    "sourceColumn": "tenure_months"}}},
  {"Action": {"Operation": "DELETE_DUPLICATE_ROWS"}}
]

Order matters: deduplicate before splitting (or identical rows end up on both sides), and compute imputation and outlier limits on the training data, then apply the same values to validation, test and inference data. Canvas computes a step's statistics when you define it and reuses them when the job runs.

Key takeaways

  • Glue Data Quality: DQDL rules and a score; catalog tables for scheduled checks and rule recommendations, the ETL transform for row-level quarantine and failing jobs; anomaly detection needs three runs; alerts through EventBridge.
  • DataBrew rulesets run in profile jobs; the Canvas insights report flags missing values, duplicates, outliers, imbalance and target leakage.
  • Labeling: clear instructions, several labelers and consolidation, private workforce for sensitive data, active learning to cut cost, augmented manifest output; Ground Truth and A2I are closed to new customers.
  • Bias sources: sampling, historical, measurement, proxies and leakage; split by key or time, stratify rare labels, shuffle with a seed, augment under-represented groups.
  • Pre-training metrics: CI (group sizes), DPL (positive-label rates), KL, JS, LP, TVD and KS (distribution gaps), CDDL (within subgroups); derive columns from text and images with Comprehend and Rekognition first; compute with pandas now that Clarify is closed.
  • Imbalance: oversample, undersample or SMOTE on the training split only; scale_pos_weight or positive_example_weight_mult; image augmentation; judge with F1, AUC-PR or balanced accuracy.
  • FM data: validate format and limits (Nova validator, reserved strings), check pair quality and duplicates, screen with ApplyGuardrail, Comprehend toxicity and Rekognition moderation; Bedrock doesn't screen it for you.
  • Cleaning: decide whether outliers are errors, clip or remove with standard deviation, robust or quantile rules; impute with training-set statistics and indicators; exact duplicates with drop duplicates, fuzzy ones with FindMatches.
