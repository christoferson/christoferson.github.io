Overview

Task 1.1

Collect and store data.

Questions in this task describe where data is today and what a training job, a feature pipeline or a RAG assistant needs, and ask for the extraction method, the storage service or the format that fits. Most answers come down to a few habits: land data in S3 as Parquet, extract with the source's own export feature rather than scanning a live database, stream with Kinesis or MSK into Firehose or Flink, and match the vector store to the scale, latency and filtering the application needs.

Running example. An online retailer (account 111111111111, Region us-east-1) builds two things. A churn model trained on customer profiles in Aurora PostgreSQL, orders in DynamoDB and clickstream events from the website. A product-support assistant that answers questions with RAG over help articles, manuals, product images and recorded support calls. Its data lake bucket is retail-ml-111111111111. Every task page in this guide reuses it.

Status changes to know. Amazon S3 Select is closed to new customers (since 25 July 2024); use Athena or filter after a GET. Kinesis Data Analytics for SQL is discontinued (no new applications since 15 October 2025, existing ones deleted from 27 January 2026), and Kinesis Data Analytics for Apache Flink is now Amazon Managed Service for Apache Flink. Kinesis Data Firehose is now Amazon Data Firehose. AWS Glue 0.9, 1.0 and 2.0 reached end of life on 1 April 2026.

Extracting from data sources

Skill 1.1.1Extract data from data sources (for example, Amazon S3, Amazon EBS, Amazon EFS, Amazon RDS, Amazon DynamoDB, Amazon OpenSearch Service).

The rule behind most right answers: use the source's export feature, which doesn't load the production system, and land the result in S3. Training jobs read from S3, EFS or FSx for Lustre.

Amazon S3

Querying a subset of the data lake

To pull a subset of a large dataset, run it through Athena. UNLOAD writes a query result straight to S3 in a chosen format without creating a table (CTAS does the same and registers a table). A SageMaker Processing job can also take an Athena or Redshift query directly as an input (DatasetDefinition), which writes the result and mounts it for the job.

Export the last year of orders for training as Parquet (SQL, Amazon Athena) 
UNLOAD (
  SELECT customer_id, order_total, items, channel, order_month
  FROM retail.orders
  WHERE order_date >= date '2025-11-01'
)
TO 's3://retail-ml-111111111111/churn/extracts/orders/'
WITH (format = 'PARQUET', compression = 'SNAPPY', partitioned_by = ARRAY['order_month'])
  • The target prefix must be empty unless you write partitions; UNLOAD never overwrites. Partition columns go last in the SELECT, and one statement can write at most 100 partitions.
  • Default compression is gzip for Parquet and zlib for ORC; JSON and text are always gzipped.

Amazon EBS, Amazon EFS and FSx for Lustre

What a training job can read

SageMaker training reads from S3 (including S3 Express One Zone), EFS or FSx for Lustre. EBS is not a training data source: data on an EBS volume (or a volume restored from a snapshot) is attached to an EC2 instance and copied to S3, EFS or FSx first. EFS and FSx channels need a VPC configuration, use File mode only, and FSx needs a subnet in the file system's Availability Zone. The data must already be on the file system before the job starts.

A training channel on FSx for Lustre (JSON, part of the CreateTrainingJob request) 
{
  "ChannelName": "train",
  "InputMode": "File",
  "DataSource": {
    "FileSystemDataSource": {
      "FileSystemId": "fs-0123456789abcdef0",
      "FileSystemType": "FSxLustre",
      "DirectoryPath": "/fsx/churn/train",
      "FileSystemAccessMode": "ro"
    }
  }
}

An FSx file system linked to S3 (a data repository association) loads files lazily on first read, so the first epoch is slower.

Amazon RDS and Aurora

Snapshot and cluster export to S3

Export to S3 writes a snapshot (manual, automated or AWS Backup) as compressed Parquet without touching the live database; Aurora can also export a live cluster by cloning it. It needs a bucket in the same Region, an IAM role trusted by export.rds.amazonaws.com and a KMS key, runs up to 5 exports per account at once, and the result can't be restored back into RDS. For continuous replication without an export pipeline, zero-ETL integrations replicate Aurora, RDS and DynamoDB into Amazon Redshift.

Export the customers schema from last night's snapshot (AWS CLI) 
aws rds start-export-task \
  --export-task-identifier churn-customers-2026-11-11 \
  --source-arn arn:aws:rds:us-east-1:111111111111:cluster-snapshot:rds:retail-prod-2026-11-11-03-00 \
  --s3-bucket-name retail-ml-111111111111 \
  --s3-prefix churn/extracts/customers \
  --iam-role-arn arn:aws:iam::111111111111:role/rds-s3-export \
  --kms-key-id arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab \
  --export-only retail.customers

Amazon DynamoDB

Export instead of Scan

Export to S3 needs point-in-time recovery, consumes no read capacity and can be full or incremental (15 minutes to 24 hours of changes). The output is DynamoDB JSON or Amazon Ion, not Parquet, so convert it with Glue or Athena afterwards. Since October 2026 an export can be filtered: a key condition reduces the data you're billed for, a filter expression doesn't. A full Scan for training data consumes capacity and can throttle the table.

Full export of the orders table (AWS CLI) 
aws dynamodb export-table-to-point-in-time \
  --table-arn arn:aws:dynamodb:us-east-1:111111111111:table/orders \
  --s3-bucket retail-ml-111111111111 \
  --s3-prefix churn/extracts/orders-ddb \
  --export-format DYNAMODB_JSON \
  --export-type FULL_EXPORT

Amazon OpenSearch Service

Snapshots and paging

Automated snapshots are for recovering the cluster only. To move indexes, take a manual snapshot to your own bucket (the caller needs iam:PassRole on the snapshot role, and the bucket must not have a Glacier lifecycle rule). To get the documents themselves, for example the support assistant's chunks for an evaluation set, page through them with point in time and search_after (OpenSearch 2.5 or later).

Exports differ by source: RDS and Aurora export Parquet, DynamoDB exports JSON or Ion, OpenSearch snapshots are segment files rather than rows. And S3 Select, which older material uses to "pull a few columns from a CSV in S3", isn't available to new accounts.

Storage decisions

Skill 1.1.2Make storage decisions and configure storage services based on cost, performance, data structure, and data compliance.

Where training data should sit

AWS's own guidance for SageMaker

  • S3 with File mode for small datasets (AWS suggests under 50 to 100 GB): the job copies the data to the instance before training. Pack many small files (under 50 MB) into larger files of about 150 MB (TFRecord, WebDataset, RecordIO).
  • S3 with FastFile mode for larger datasets of files over 50 MB: data streams on demand behind a normal file path, with no VPC or file system. Pipe mode still exists but AWS calls it "largely replaced" by FastFile.
  • FSx for Lustre for very large datasets, many small files that can't be combined, or random reads, and for distributed training that rereads data; EFS when the data already lives there.
  • S3 Express One Zone for the lowest latency next to the compute (one Availability Zone, single-digit milliseconds, higher request rates). Keep the master copy in S3 Standard, because data in a single zone can be lost with it.

Cost

Storage classes and tiers

S3 Standard costs about $0.023 per GB-month in us-east-1. S3 Intelligent-Tiering moves objects not accessed for 30 days to an infrequent tier and after 90 days to an archive instant tier, with no retrieval fees, which suits training data reread only when models are retrained; objects under 128 KB aren't tiered, and the monitoring fee per object matters for millions of tiny files. FSx for Lustre has its own Intelligent-Tiering (30 and 90 days) that AWS calls the best price and performance balance for most workloads. EFS throughput: Elastic is the console default and recommended; Bursting is the CLI and API default.

Structure and compliance

Matching the store to the data and the rules

  • Structure: tabular history in S3 (Parquet, Iceberg tables), key-value lookups in DynamoDB, relational data in Aurora or RDS, documents and media as S3 objects, features in Feature Store, embeddings in a vector store.
  • Encryption: S3 encrypts new objects with SSE-S3 by default; use SSE-KMS where key control or audit is required. Training and processing volumes take a VolumeKmsKeyId, except on instance types with local NVMe storage, which are encrypted by the hardware.
  • Retention: S3 Object Lock (with versioning) keeps an immutable copy of the exact training data behind an audited model.
  • Sensitive data: Amazon Macie finds personal data in S3 general purpose buckets, with findings in EventBridge and Security Hub CSPM.
  • Residency: a SageMaker job reads data only from its own Region, so data that must stay in a Region is trained there.

Capacity and scalability problems

Skill 1.1.3Troubleshoot and debug data ingestion and storage issues that involve capacity and scalability.

  • S3 503 Slow Down: S3 supports at least 3,500 writes and 5,500 reads per second per partitioned prefix, so spread keys across prefixes (for example by date) and retry with backoff. On a versioned bucket, objects with millions of versions also trigger throttling; AWS recommends fewer than 100,000 versions per object and a lifecycle rule to expire noncurrent versions. A job that rewrites features/latest.parquet every minute builds those up quickly.
  • DynamoDB throttling: exceptions now carry ThrottlingReasons. TableWriteKeyRangeThroughputExceeded means a hot partition key, which more capacity won't fix; change the key design or spread writes. ProvisionedThroughputExceeded means raise capacity or switch to on-demand (allowed 4 times per 24 hours since August 2025). Contributor Insights can show the throttled keys.
  • "No space left on device" in training: File mode needs the whole channel, the model and checkpoints to fit on the volume. Raise VolumeSizeInGB on EBS-backed instance types, switch to FastFile or FSx, or choose an instance type with more local NVMe storage (where VolumeSizeInGB adds nothing). Write large scratch files to /tmp, not small system directories.
  • Slow reads from EFS: in Bursting mode, a small file system runs out of BurstCreditBalance; when MeteredIOBytes reaches PermittedThroughput, change to Elastic throughput. SageMaker training volumes are gp2, so their IOPS scale with size.
  • RDS running out of storage: storage autoscaling grows the volume when free space is at 10% or less for 5 minutes, but at most 4 times in 24 hours, so it can't save a single huge bulk load; size for the load or set a higher maximum.
  • Kinesis throttling: a provisioned shard takes 1 MB or 1,000 records per second; a hot shard needs a higher-cardinality partition key, and rising GetRecords.IteratorAgeMilliseconds means consumers are falling behind (more shards or enhanced fan-out).

Streaming ingestion

Skill 1.1.4Use AWS streaming data sources to ingest data (for example, by using Amazon Kinesis, Apache Flink, Apache Kafka).

  1. CaptureThe website sends clickstream events to Kinesis Data Streams (or a Kafka topic on Amazon MSK).
  2. LandAmazon Data Firehose reads the stream, converts JSON to Parquet and writes it to S3 partitioned by date, for training and Athena.
  3. ComputeManaged Service for Apache Flink reads the same stream and computes rolling features, such as support-page visits in the last 30 minutes.
  4. ServeThe Flink application (or a Lambda consumer) writes those features to the Feature Store online store with PutRecord for real-time predictions.
  • Kinesis Data Streams: on-demand (two variants) or provisioned capacity; per shard 1 MB/s in and 2 MB/s out (shared, or 2 MB/s per consumer with enhanced fan-out); records up to 10 MiB; retention 24 hours by default, up to 365 days for replaying data into a new feature pipeline. Resharding works only in provisioned mode.
  • Amazon Data Firehose: sources are direct PUT, Kinesis Data Streams or MSK; destinations include S3, Apache Iceberg tables (including S3 Tables), Redshift and OpenSearch. Record format conversion turns JSON into Parquet or ORC using a Glue Data Catalog table schema (CSV needs a Lambda transform to JSON first, and fields missing from the schema are dropped). Buffering is 1 to 128 MiB or 0 to 900 seconds, and dynamic partitioning builds S3 prefixes from fields in the records.
  • Managed Service for Apache Flink: stateful, exactly-once stream processing; the current runtime is Flink 1.20 (1.13 and older reached end of support), billed per KPU (1 vCPU and 4 GB). Use it for windows, joins and aggregations that Firehose can't do.
  • Amazon MSK: managed Apache Kafka as provisioned clusters with Standard or Express brokers (since November 2024, faster scaling, no storage to provision) or MSK Serverless (IAM access control required). Choose it when producers already use Kafka.

Data formats

Skill 1.1.5Ingest from and write by using appropriate data formats (for example, Apache Parquet, JSON, CSV, ORC) based on data access patterns.

  • Parquet and ORC (columnar): compress each column, skip blocks with min and max statistics (predicate pushdown), split across readers and support schema evolution. Best for analytics and feature extraction that read a few columns of wide tables, and the default for Athena CTAS. ORC files are often smaller; Parquet is the common choice with Spark and Arrow.
  • JSON and JSON Lines: one record at a time, nested fields, easy to stream; what applications and Firehose receive. Convert to Parquet for repeated analytics.
  • CSV: simple interchange and the input many SageMaker built-in algorithms expect, with no header row and the label in the first column (unsupervised algorithms use text/csv;label_size=0).
  • Avro: row-based with its schema embedded, good for streaming and Kafka. RecordIO-protobuf: SageMaker's binary format for Linear Learner, k-means, PCA, Factorization Machines and other built-ins, efficient for sparse data and Pipe mode.
  • Apache Iceberg tables: Parquet files with table-level transactions, time travel and schema changes, used by S3 Tables, Firehose and the Feature Store offline store.

Match the format to the algorithm: XGBoost reads CSV, LibSVM and (for distributed GPU training with Dask) Parquet; BlazingText and DeepAR read JSON Lines; image algorithms read JPEG and PNG. Converting a whole data lake to the "best" format doesn't help if the training container can't read it.

Merging data

Skill 1.1.6Merge data from multiple sources (for example, by using programming techniques, AWS Glue, Apache Spark).

The churn training set joins customer profiles (from the Aurora export) with order history (from the DynamoDB export, converted). In an AWS Glue job:

Join customers and orders and write Parquet partitioned by month (Python, AWS Glue ETL job) 
import sys

from awsglue.context import GlueContext
from awsglue.job import Job
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext

args = getResolvedOptions(sys.argv, ["JOB_NAME"])
glueContext = GlueContext(SparkContext.getOrCreate())
job = Job(glueContext)
job.init(args["JOB_NAME"], args)

# transformation_ctx lets job bookmarks skip data already processed
customers = glueContext.create_dynamic_frame.from_catalog(
    database="retail", table_name="customers", transformation_ctx="customers")
orders = glueContext.create_dynamic_frame.from_catalog(
    database="retail", table_name="orders", transformation_ctx="orders")

# An inner equality join that keeps both key columns, so drop the duplicate
joined = customers.join(paths1=["customer_id"], paths2=["cust_id"], frame2=orders).drop_fields(["cust_id"])

glueContext.write_dynamic_frame.from_options(
    frame=joined, connection_type="s3",
    connection_options={"path": "s3://retail-ml-111111111111/churn/joined/", "partitionKeys": ["order_month"]},
    format="parquet", format_options={"useGlueParquetWriter": True},
    transformation_ctx="sink")
job.commit()
  • Other join types: DynamicFrame.join is inner only; for left, outer or anti joins convert with toDF(), use Spark's join(how=...), and convert back with DynamicFrame.fromDF. mergeDynamicFrame upserts a staging frame into a source by primary key.
  • Mixed types across sources become choice columns; fix them with resolveChoice before writing. relationalize flattens nested JSON.
  • Glue versions: 5.1 (Spark 3.5) is the default and 6.0 (Spark 4.1) shipped in August 2026. With Adaptive Query Execution (on by default from Glue 4.0) Spark broadcasts small tables in joins automatically.
  • Other tools: Athena SQL joins plus CTAS for SQL users; Spark on EMR or EMR Serverless, or a PySpark Processing job, for large custom joins; pandas in a Processing job for small data; AWS Glue DataBrew and SageMaker Canvas (Data Wrangler) for visual joins; zero-ETL integrations to avoid building the pipeline at all.

Joining features to labels by customer ID alone leaks the future: a feature computed after the churn date makes the model look better than it is. Join on the entity and a point in time (Feature Store's point-in-time queries do this, Skill 1.1.9). Job bookmarks also silently do nothing without transformation_ctx and job.commit().

Vector databases

Skill 1.1.7Configure scalable vector databases for AI applications (for example, OpenSearch Service, Amazon RDS with pgvector, Amazon S3) based on specifications.

The support assistant embeds help-article chunks with Titan Text Embeddings V2 (1,024 dimensions) and searches them by similarity, filtered by product category and language. Which store fits depends on the specification:

  • Amazon S3 Vectors: the lowest cost for large, infrequently queried collections, with no cluster. Up to 2 billion vectors per index, 1 to 4,096 dimensions, float32 only, cosine or Euclidean distance, sub-second queries (about 100 ms when frequent), up to 10,000 results per query. Indexes in buckets created since 30 September 2026 apply metadata filters before the search (ENHANCED mode). No keyword or hybrid search.
  • Amazon OpenSearch Service (managed domains or Serverless): millisecond latency, high query rates, hybrid keyword and vector search, aggregations and rich filters. Use the faiss engine with HNSW; compression or disk mode cuts memory, and GPU acceleration speeds up index builds.
  • Aurora PostgreSQL or RDS for PostgreSQL with pgvector (0.8.2): embeddings next to relational data, SQL filters and joins, moderate scale. Use an HNSW index; on filtered queries turn on iterative scan (0.8.0 and later) so results aren't cut short.
  • Others: DocumentDB (5.0 instance-based clusters, 2,000 indexed dimensions), MemoryDB and ElastiCache Serverless for Valkey (in-memory, microsecond latency, for real-time recommendations or semantic caching), Neptune Analytics for graph plus vector.
Create an S3 Vectors index, add a chunk and query it with a filter (Python, boto3) 
import json

import boto3
import numpy as np

s3v = boto3.client("s3vectors", region_name="us-east-1")
bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")


def embed(text):
    r = bedrock.invoke_model(modelId="amazon.titan-embed-text-v2:0",
                             body=json.dumps({"inputText": text, "dimensions": 1024}))
    return np.array(json.loads(r["body"].read())["embedding"], dtype=np.float32).tolist()


s3v.create_vector_bucket(vectorBucketName="retail-support-vectors")
s3v.create_index(
    vectorBucketName="retail-support-vectors", indexName="support-articles",
    dataType="float32", dimension=1024, distanceMetric="cosine",
    # Returned with results but never filtered on; this can't be changed later
    metadataConfiguration={"nonFilterableMetadataKeys": ["chunk_text"]},
)

text = "Items can be returned within 30 days of delivery..."
s3v.put_vectors(vectorBucketName="retail-support-vectors", indexName="support-articles", vectors=[{
    "key": "returns-policy#1",
    "data": {"float32": embed(text)},
    "metadata": {"category": "returns", "locale": "en-GB", "chunk_text": text},
}])

# A filter or returnMetadata also needs s3vectors:GetVectors permission
resp = s3v.query_vectors(
    vectorBucketName="retail-support-vectors", indexName="support-articles",
    queryVector={"float32": embed("How long do I have to send back a jacket?")},
    topK=5,
    filter={"$and": [{"category": "returns"}, {"locale": {"$in": ["en-GB", "en-US"]}}]},
    returnMetadata=True, returnDistance=True,
)
for v in resp["vectors"]:
    print(v["key"], v["distance"])
The same chunks in Aurora PostgreSQL with pgvector (SQL) 
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE support_chunks (id uuid PRIMARY KEY, embedding vector(1024), chunk text, category text);

-- HNSW needs no training step, so it can be built before the data is loaded
CREATE INDEX support_chunks_hnsw ON support_chunks
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 256);

SET hnsw.ef_search = 100;                 -- default 40; higher means better recall, slower queries
SET hnsw.iterative_scan = 'relaxed_order'; -- pgvector 0.8.0+: keep scanning when a filter removes rows

SELECT id, chunk FROM support_chunks
WHERE category = 'returns'
ORDER BY embedding <=> $1               -- cosine distance to the query embedding
LIMIT 5;

Vector store limits that decide questions: S3 Vectors is float32 with cosine or Euclidean only and its non-filterable keys are fixed at creation; an OpenSearch k-NN query without size returns k results per shard, and a post_filter can return fewer than k; IVFFlat indexes in pgvector must be built after loading data, HNSW indexes needn't; pgvector doesn't upgrade with the database engine (run ALTER EXTENSION vector UPDATE). Amazon Bedrock Knowledge Bases can manage any of these stores for you (see the Knowledge Bases notes).

Text, images and audio

Skill 1.1.8Ingest and store diverse data types (for example, text, images, audio) for AI and ML applications.

  • Store the originals in S3, organized by prefix, with descriptive information in user-defined metadata (2 KB, set at upload and changed only by copying), object tags (10 per object, usable in IAM and lifecycle rules) or the newer object annotations (up to 1,000 per object version, added after upload, for things such as labels or model outputs), and query it all through S3 Metadata tables.
  • Audio: Amazon Transcribe turns recorded support calls in S3 into text (StartTranscriptionJob with exactly one of LanguageCode, IdentifyLanguage or IdentifyMultipleLanguages), with speaker labels and PII redaction; OutputBucketName takes a bucket name, not an s3:// URI.
  • Documents: Amazon Textract extracts text, forms and tables from manuals. Synchronous calls take one page of a PDF; multipage PDFs (up to 3,000 pages) use the asynchronous APIs with an SNS notification, and results stay only 7 days unless written to your bucket.
  • Images and video: embed them directly with a multimodal model. Titan Multimodal Embeddings G1 averages text and image into one vector (up to 1,024 dimensions); Amazon Nova Multimodal Embeddings puts text, documents, images, video and audio in one space (up to 3,072 dimensions) and segments long video asynchronously. Amazon Bedrock Data Automation instead converts documents, images, audio and video into structured text.
  • Training jobs: a manifest file lists exactly which objects to train on; an augmented manifest (JSON Lines with data and labels, Pipe mode only) carries labels with each item, and the Converse data type carries conversations for fine-tuning.

Ingesting into Feature Store

Skill 1.1.9Ingest data into SageMaker Feature Store.

Feature Store keeps the latest features per customer in an online store for real-time inference and every version in an offline store in S3 for training (the concepts, tiers and point-in-time queries are in the SageMaker data preparation notes). PutRecord is the single ingestion API for both batch and streaming.

Write streaming features from Kinesis to the online store (Python, AWS Lambda) 
import base64
import json

import boto3

fs = boto3.client("sagemaker-featurestore-runtime")


def handler(event, context):
    for rec in event["Records"]:
        click = json.loads(base64.b64decode(rec["kinesis"]["data"]))
        # Every value is sent as a string; PutRecord replaces the whole record
        fs.put_record(
            FeatureGroupName="customer-activity",
            Record=[
                {"FeatureName": "customer_id", "ValueAsString": click["customer_id"]},
                {"FeatureName": "event_time", "ValueAsString": click["event_time"]},
                {"FeatureName": "support_visits_30m", "ValueAsString": str(click["support_visits_30m"])},
            ],
            TargetStores=["OnlineStore", "OfflineStore"],
        )
  • Streaming: your own consumer (Lambda, a Flink sink or a KCL application) calls PutRecord, or BatchWriteRecord for up to 25 records (July 2026); there's no managed Kinesis or Flink connector. Limits are 500 writes per second per record identifier and 350 KB per record.
  • Batch: ingest_dataframe in the SDK, the Feature Store Spark connector (FeatureStoreManager.ingest_data, with target_stores=["OfflineStore"] to backfill history straight to S3 without touching the online store), a feature processor pipeline, or a Canvas data flow export.
  • Write rules: a record with an older event time than the stored one goes only to the offline store; TargetStores limits a write to one store; a per-record TtlDuration expires online records. Offline data appears in S3 within about 15 minutes.

The Spark connector is documented for Spark 3.0 to 3.3, older than the Spark in current Glue and EMR releases, so check compatibility before choosing it. And an offline-only backfill doesn't update the online store: real-time predictions keep reading the old values until a PutRecord reaches the online store.

Key takeaways

  • Extract with export features: Athena UNLOAD (empty target, 100 partitions), RDS and Aurora export to S3 (Parquet, KMS key required, 5 at a time), DynamoDB export (needs PITR, no read capacity, JSON or Ion only), OpenSearch manual snapshots and point in time paging. S3 Select is closed to new customers.
  • Training reads S3, EFS or FSx for Lustre, not EBS. File mode for small data, FastFile for large files, FSx for huge, small-file or random-read data, Express One Zone for lowest latency with a master copy elsewhere.
  • Capacity: S3 503s mean spread prefixes and back off (or too many versions per object); DynamoDB KeyRangeThroughputExceeded means a hot key; out of disk means a bigger volume, FastFile or FSx; EFS Bursting runs out of credits; RDS autoscaling won't save one bulk load.
  • Streaming: Kinesis Data Streams or MSK in, Firehose to land Parquet in S3 (JSON input with a Glue schema), Managed Service for Apache Flink for stateful features, Feature Store online for serving.
  • Formats: Parquet or ORC for analytics, JSON for streaming and APIs, CSV without header and label first for built-ins, RecordIO-protobuf for sparse built-in input, Iceberg for tables with updates.
  • Merging: Glue join is inner and duplicates keys; use Spark for other joins; resolve choice types; join features to labels by point in time.
  • Vectors: S3 Vectors for cheap scale, OpenSearch for latency and hybrid search, pgvector for relational data with HNSW and iterative scan; check dimensions, distance metrics and filtering before choosing.
  • Feature Store: PutRecord (or BatchWriteRecord) for streaming, the SDK, Spark connector or feature processors for batch; older event times go offline only.
