Task 4.3: Secure ML and AI workloads and model endpoints

Protecting the whole ML and AI system: scanning code and images before they ship, giving every person and job only the access it needs, recording and checking what happens, fixing access errors, isolating workloads in private networks, defending against attacks specific to models and agents, choosing credentials for foundation models, and applying safeguards to model inputs and outputs.

Overview

Task 4.3

Secure ML and AI workloads and model endpoints.

Questions in this task describe a security requirement or a failure ("training data must never leave the VPC", "the job fails with AccessDenied", "only the support team may invoke this model", "users must not be able to bypass the guardrail") and ask for the control. The defaults behind the right answers: least privilege (narrow roles, scoped resources, conditions), encryption with your own keys, private networking, audit everything, and for generative AI, treat model input and output as untrusted.

Running example. The online retailer (account 111111111111) keeps customer data in encrypted S3 buckets, trains in private subnets, serves the churn model and the support assistant, and must prove to auditors who did what.

Status changes to know. Amazon CodeGuru Reviewer accepts no new repository associations, and CodeGuru Security is no longer documented; AWS points to Amazon Inspector code scanning (Inspector Code Security, June 2025) and Amazon Q Developer code reviews. SageMaker Role Manager has been closed to new customers since 30 July 2026, and AWS Audit Manager no longer accepts new customers. Bedrock API keys arrived in July 2025. GuardDuty AI Protection covers Bedrock, AgentCore and SageMaker AI activity. Bedrock now has data retention modes, so whether prompts are stored depends on the model and mode.

Securing CI/CD

Skill 4.3.1Secure continuous integration and continuous delivery (CI/CD) pipelines by checking for code and image vulnerabilities (for example, by using Amazon CodeGuru, Amazon Inspector).

  • Container images: Amazon ECR enhanced scanning with Inspector finds OS and language package vulnerabilities on push and re-scans when new CVEs appear (Task 3.2).
  • In the pipeline: the Inspector SBOM generator (inspector-sbomgen) lists an image's or directory's packages, and the Inspector Scan API (scan-sbom) returns vulnerabilities, so a CodeBuild step (or the CodePipeline InspectorScan action, with severity thresholds) fails the build before a vulnerable image is deployed. Plugins exist for GitHub Actions, GitLab and Jenkins.
  • Source code: Inspector Code Security runs static analysis, dependency checks and infrastructure-as-code checks on GitHub and GitLab repositories; Amazon Q Developer reviews code. Lambda functions get Inspector code scanning.
  • Also: pin dependency versions, keep secrets in Secrets Manager rather than notebooks or code, use AWS-maintained base images and rebuild them, and sign images.
Fail the build on vulnerabilities in the inference image (Bash, CodeBuild build phase) 
./inspector-sbomgen container --image "$IMAGE_URI" -o sbom.json
aws inspector-scan scan-sbom --sbom file://sbom.json --output-format INSPECTOR > findings.json

# Stop the pipeline if anything critical or high is found
python - <<'EOF'
import json, sys
vulns = json.load(open("findings.json"))["sbom"]["vulnerabilities"]
bad = [v for v in vulns if v.get("severity", "").upper() in ("CRITICAL", "HIGH")]
sys.exit(1 if bad else 0)
EOF

Older questions may expect CodeGuru as the code scanner; for new pipelines the AWS answer is Inspector (images, SBOMs, code) plus Amazon Q code reviews. Inspector Code Security doesn't re-scan repositories when a new CVE is published; ECR enhanced scanning of images does.

Least privilege to artifacts

Skill 4.3.2Configure least privilege access to ML and AI artifacts.

ML artifacts are training data, features, model files, container images, prompts, knowledge base sources and logs. Protect each with three layers:

  • Identity policies that name exact buckets, prefixes, repositories, model package groups and models, not *. AmazonSageMakerFullAccess is broad, and it only reaches S3 buckets with "sagemaker" in the name, a common source of surprise errors.
  • Resource policies: S3 bucket policies (deny anything but the expected roles and VPC endpoints), ECR repository policies, Model Registry group policies for cross-account sharing, KMS key policies.
  • Encryption with customer managed KMS keys for training volumes (VolumeKmsKeyId), job output (OutputDataConfig.KmsKeyId), endpoint storage, data capture, Feature Store (separate online and offline store keys), Bedrock custom models, guardrails and knowledge base data sources. The role needs kms:Decrypt for encrypted input, kms:Encrypt (or data key generation) for output, and kms:CreateGrant for a volume key.
  • Tags and conditions: tag resources by project and allow actions only where sagemaker:ResourceTag/Project matches the caller's project (and deny changing tags); condition keys such as sagemaker:VolumeKmsKeyArn, sagemaker:OutputKmsKeyArn, sagemaker:InstanceTypes and sagemaker:NetworkIsolation force secure settings at creation.
A training role limited to its data, output and key (JSON, IAM policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "ReadTrainingData", "Effect": "Allow", "Action": ["s3:GetObject", "s3:ListBucket"],
     "Resource": ["arn:aws:s3:::retail-ml-111111111111",
                  "arn:aws:s3:::retail-ml-111111111111/churn/train/*"]},
    {"Sid": "WriteModelArtifacts", "Effect": "Allow", "Action": "s3:PutObject",
     "Resource": "arn:aws:s3:::retail-ml-111111111111/churn/models/*"},
    {"Sid": "UseProjectKey", "Effect": "Allow",
     "Action": ["kms:Decrypt", "kms:Encrypt", "kms:GenerateDataKey", "kms:CreateGrant"],
     "Resource": "arn:aws:kms:us-east-1:111111111111:key/1a2b3c4d-5e6f-7a8b-9c0d-1e2f3a4b5c6d"},
    {"Sid": "PullTrainingImage", "Effect": "Allow",
     "Action": ["ecr:BatchGetImage", "ecr:GetDownloadUrlForLayer"],
     "Resource": "arn:aws:ecr:us-east-1:111111111111:repository/retail/churn-train"},
    {"Sid": "EcrAuth", "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*"}
  ]
}

To share a model across accounts through the Model Registry, the model package group needs a resource policy, the artifacts need a customer managed KMS key the other account can use, and the S3 bucket and ECR repository need matching policies; the default S3 key can't be shared across accounts.

IAM roles and policies

Skill 4.3.3Configure IAM policies and roles for users and applications in ML and AI systems.

  • People sign in through IAM Identity Center (or IAM); in SageMaker Studio each user profile has an execution role that notebooks and jobs use, so give different teams different roles.
  • Workloads use roles assumed by the service: SageMaker training, processing and endpoint roles (trusted by sagemaker.amazonaws.com), Bedrock knowledge base and customization service roles, AgentCore Runtime execution roles, Lambda roles. No long-term access keys in code.
  • iam:PassRole lets someone hand a role to a service; limit it to specific role ARNs and the right service with iam:PassedToService, or a user can pass an admin role to a job and act through it.
  • Bedrock model access is controlled with IAM on model and inference profile ARNs (a cross-Region profile needs both the profile and the foundation models it routes to), plus condition keys such as bedrock:GuardrailIdentifier (require a guardrail) and bedrock:ServiceTier. Model access is enabled by default since October 2025, so IAM and SCPs are the controls.
  • Confused deputy: add aws:SourceArn and aws:SourceAccount conditions to service role trust policies where supported.
Let data scientists pass only the training role, only to SageMaker (JSON, IAM policy statement) 
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111111111111:role/SageMakerChurnTrainingRole",
  "Condition": {"StringEquals": {"iam:PassedToService": "sagemaker.amazonaws.com"}}
}
Allow model calls only with the approved guardrail version (JSON, IAM policy statements) 
[
  {"Effect": "Allow",
   "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
   "Resource": "arn:aws:bedrock:us-east-1::foundation-model/*",
   "Condition": {"StringEquals": {"bedrock:GuardrailIdentifier": "arn:aws:bedrock:us-east-1:111111111111:guardrail/gr-support:3"}}},
  {"Effect": "Deny",
   "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
   "Resource": "arn:aws:bedrock:us-east-1::foundation-model/*",
   "Condition": {"StringNotEquals": {"bedrock:GuardrailIdentifier": "arn:aws:bedrock:us-east-1:111111111111:guardrail/gr-support:3"}}}
]

Guardrails can also be enforced for a whole account or organization, without relying on each policy (Skill 4.3.9).

Monitoring, auditing and compliance

Skill 4.3.4Configure comprehensive monitoring, auditing, compliance, and logging for ML and AI systems (for example, AWS CloudTrail, AWS Config).

  • AWS CloudTrail records API calls: who created, changed or deleted jobs, endpoints, models, guardrails and knowledge bases. Bedrock InvokeModel and Converse are management events (logged by default); SageMaker InvokeEndpoint is a data event that must be turned on, and is logged without the request body. CloudTrail never records prompts or payloads; that's what model invocation logging and data capture are for.
  • AWS Config records resource configurations and evaluates rules, for example sagemaker-endpoint-configuration-kms-key-configured, sagemaker-notebook-no-direct-internet-access, sagemaker-model-in-vpc, sagemaker-model-isolation-enabled and sagemaker-endpoint-config-prod-instance-count, and for Bedrock bedrock-data-source-encryption-enabled.
  • AWS Security Hub controls (SageMaker.1 to SageMaker.25, Bedrock.1) score posture across accounts.
  • Amazon GuardDuty AI Protection analyses Bedrock, AgentCore and SageMaker AI activity (no trail needed) for findings such as anomalous model invocation, cost harvesting and direct prompt injection; GuardDuty also flags guardrails being removed or invocation logging being turned off.
  • Logs: Bedrock model invocation logging, SageMaker data capture, CloudWatch Logs for jobs and endpoints, VPC Flow Logs; encrypt them, restrict access, and set retention.
  • Documentation: SageMaker Model Cards and lineage, Model Registry approvals, and AI Service Cards for AWS models.
Log invocations of the churn endpoint as CloudTrail data events (JSON, advanced event selectors) 
[{"FieldSelectors": [
  {"Field": "eventCategory", "Equals": ["Data"]},
  {"Field": "resources.type", "Equals": ["AWS::SageMaker::Endpoint"]},
  {"Field": "resources.ARN", "Equals": ["arn:aws:sagemaker:us-east-1:111111111111:endpoint/churn-endpoint"]}
]}]

Apply it with aws cloudtrail put-event-selectors --trail-name org-trail --advanced-event-selectors file://selectors.json.

Troubleshooting security issues

Skill 4.3.5Troubleshoot and debug security issues in ML and AI systems.

  • Job fails reading or writing S3: the execution role lacks s3:GetObject or s3:PutObject on that prefix, the bucket policy denies it, or the VPC endpoint policy blocks it.
  • Encrypted data: the role (or the key policy) lacks kms:Decrypt, kms:GenerateDataKey or kms:CreateGrant; check both the IAM policy and the key policy.
  • "is not authorized to perform: iam:PassRole": the caller can't pass the execution role; PassRole denials don't appear in CloudTrail.
  • Image pull fails: missing ECR permissions on the role, or a cross-account repository without a repository policy.
  • Bedrock AccessDeniedException: the IAM policy lacks the model or inference profile ARN, an SCP denies the model or Region, a guardrail condition isn't met, or Marketplace subscription permissions are missing for a third-party model.
  • Tools: decode the encoded message in an AccessDenied error with STS, test policies with the IAM policy simulator, look up the failed call's errorCode in CloudTrail, and use IAM Access Analyzer to validate policies and find unused access.
Read the reason behind an encoded authorization failure (Bash, AWS CLI) 
aws sts decode-authorization-message \
    --encoded-message "$ENCODED_MESSAGE" \
    --query DecodedMessage --output text | python -m json.tool
# Shows the action, the resource and which statement (or missing one) denied it

SageMaker notebook settings such as internet access, VPC and KMS key can't be changed after creation; the fix is a new notebook. A role can be correct while the key policy, bucket policy, VPC endpoint policy or an SCP still denies the call, so check every policy on the path.

Network isolation

Skill 4.3.6Create VPCs, subnets, and security groups to securely isolate ML and AI systems.

  • Private subnets without internet access in at least two Availability Zones, with VPC endpoints for the AWS services the workload calls (S3 gateway endpoint; interface endpoints for SageMaker API and runtime, Bedrock, CloudWatch, ECR, STS, KMS) and a NAT gateway only where something genuinely needs the internet (Task 3.2 shows endpoint configuration).
  • SageMaker Studio in VPC-only mode sends all traffic through your VPC; training, processing and endpoints take a VpcConfig.
  • Security groups: distributed training needs a self-referencing rule so instances in the same group can talk to each other (all traffic within the group with EFA); allow only HTTPS to interface endpoints.
  • Network isolation (EnableNetworkIsolation) blocks all outbound calls from the container, even inside the VPC, so a compromised or untrusted model (for example from a marketplace) can't send data out; SageMaker still moves the data for it. Inter-container traffic encryption encrypts traffic between training instances (slower).
  • Bedrock and agents: model customization and batch inference jobs can run with a VPC configuration; AgentCore Runtime has a VPC mode; interface endpoints keep Bedrock calls off the internet.
  • Audit the network with VPC Flow Logs (metadata only, not contents).
An isolated, encrypted distributed training job (JSON, part of CreateTrainingJob) 
{
  "VpcConfig": {
    "Subnets": ["subnet-0a1b2c3d4e5f60001", "subnet-0a1b2c3d4e5f60002"],
    "SecurityGroupIds": ["sg-0a1b2c3d4e5f60009"]
  },
  "EnableNetworkIsolation": true,
  "EnableInterContainerTrafficEncryption": true,
  "ResourceConfig": {
    "InstanceType": "ml.g5.12xlarge",
    "InstanceCount": 2,
    "VolumeSizeInGB": 100,
    "VolumeKmsKeyId": "arn:aws:kms:us-east-1:111111111111:key/1a2b3c4d-5e6f-7a8b-9c0d-1e2f3a4b5c6d"
  }
}

The security group needs an inbound rule allowing traffic from itself: aws ec2 authorize-security-group-ingress --group-id sg-0a1b2c3d4e5f60009 --protocol all --source-group sg-0a1b2c3d4e5f60009.

A VPC and network isolation do different jobs: the VPC lets the container reach private resources; network isolation stops it reaching anything. Field names differ by service: SageMaker VpcConfig {Subnets, SecurityGroupIds}, Bedrock vpcConfig {subnets, securityGroupIds}.

ML and GenAI risks

Skill 4.3.7Identify and mitigate security risks and vulnerabilities in ML and AI systems.

  • Prompt injection and jailbreaks (instructions hidden in user input or in retrieved documents): AWS treats this as the customer's responsibility, "similar to SQL injection". Mitigate with the Guardrails prompt attack filter, tagging user input so it is evaluated, keeping secrets out of system prompts (assume they leak), validating tool inputs, and limiting what the model can do.
  • Excessive agency (an agent doing more than intended): least-privilege tool roles, AgentCore Policy to allow or deny each tool call, human confirmation for consequential actions, caps on tool calls.
  • Data poisoning (bad training, fine-tuning, knowledge base or agent memory data): control who can write data, validate and check provenance (Task 1.3), version datasets, and validate memory writes.
  • Model extraction and inference attacks (rebuilding a model or recovering training data from its answers): authentication, rate limits, throttling and usage monitoring (GuardDuty), and returning only what callers need (labels rather than full probability scores).
  • Sensitive data leakage: redact before training or indexing, filter outputs with sensitive-information filters, find personal data in S3 with Amazon Macie.
  • Insecure output handling: treat model output as untrusted before running it, rendering it as HTML or passing it to another system.
  • Supply chain: scan images and dependencies, use models from trusted sources, and isolate untrusted ones with network isolation.

AWS frameworks for this: the Generative AI Security Scoping Matrix (five scopes, from using a consumer app to training your own model) and the Agentic AI Security Scoping Matrix (November 2025), and the security pillars of the Well-Architected Generative AI and ML Lenses.

"A support chatbot follows instructions hidden in a customer's uploaded document" means indirect prompt injection: guardrail input filtering on retrieved content, least-privilege tools and output checks, not a bigger model.

Credentials for FMs

Skill 4.3.8Select the appropriate credential type to access FMs (for example, Amazon Bedrock API keys, IAM credentials).

  • IAM role credentials (temporary, from STS) for applications on AWS: Lambda, ECS, EC2, SageMaker and AgentCore roles. The default, recommended choice.
  • IAM Identity Center for people using the console or CLI; web and mobile apps get temporary credentials through a backend (or an identity broker such as Amazon Cognito) rather than embedding keys.
  • Bedrock API keys (bearer tokens in the Authorization header or the AWS_BEARER_TOKEN_BEDROCK environment variable) suit tools and SDKs that expect an API key, such as OpenAI-compatible clients:
    • Short-term keys: generated from your current session, valid up to 12 hours (or the session's remaining time), in one Region, with the same permissions as the session.
    • Long-term keys: an IAM user's service-specific credential with an expiry you choose; AWS recommends them only for exploration. They can be deactivated or deleted, while short-term keys can only be stopped by revoking the session or denying bearer-token use.
  • API keys don't work for every Bedrock API (not for agents, Data Automation or bidirectional streaming).
Allow only short-term Bedrock API keys in the organization (JSON, SCP or IAM policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Deny", "Action": "bedrock:CallWithBearerToken", "Resource": "*",
     "Condition": {"StringEquals": {"bedrock:bearerTokenType": "LONG_TERM"}}},
    {"Effect": "Deny", "Action": "bedrock-mantle:CallWithBearerToken", "Resource": "*",
     "Condition": {"StringEquals": {"bedrock-mantle:bearerTokenType": "LONG_TERM"}}}
  ]
}

Denying only bedrock:CallWithBearerToken still lets keys work on the bedrock-mantle (OpenAI-compatible) endpoint; deny both. Limit long-term key creation with iam:ServiceSpecificCredentialAgeDays rather than denying iam:CreateServiceSpecificCredential outright, which also blocks credentials for other services.

Safeguards and data protection

Skill 4.3.9Implement safeguards and sensitive data protection to meet application requirements and responsible AI policies (for example, by using Amazon Bedrock Guardrails).

Amazon Bedrock Guardrails checks inputs and outputs against policies (details in the Guardrails notes):

  • Content filters: hate, insults, sexual, violence, misconduct and prompt attacks, for text and images, with adjustable strength.
  • Denied topics (for example investment advice), word filters and profanity.
  • Sensitive information filters that block or mask PII types and custom patterns.
  • Contextual grounding checks that answers are supported by the retrieved sources and relevant to the question; Automated Reasoning checks verify answers against formal policy rules.
  • A detect mode (log without blocking) to tune policies, Classic and Standard tiers, versions to deploy, and ApplyGuardrail for any model or text.
  • Enforcement: the bedrock:GuardrailIdentifier IAM condition (Skill 4.3.3), or account and organization-level enforced guardrails that apply without application changes.
Apply the support guardrail to every assistant call (Python, boto3) 
import boto3

runtime = boto3.client("bedrock-runtime", region_name="us-east-1")
resp = runtime.converse(
    modelId="global.amazon.nova-2-lite-v1:0",
    messages=[{"role": "user", "content": [{"text": customer_message}]}],
    guardrailConfig={"guardrailIdentifier": "gr-support", "guardrailVersion": "3", "trace": "enabled"},
)
if resp["stopReason"] == "guardrail_intervened":
    log_intervention(resp["trace"]["guardrail"])  # the trace can hold unmasked PII: protect it
  • Sensitive data beyond the model: Amazon Macie discovers personal data in S3 buckets (it finds, it doesn't redact); Comprehend and Glue redact before training or indexing (Task 1.2); encrypt at rest with KMS and in transit with TLS.
  • Data handling on Bedrock: AWS states prompts and outputs aren't used to train models and aren't shared with model providers. Storage now depends on the data retention mode (none, default, AWS review and others), and some models require a mode in which data is kept for up to 30 days for abuse review; enforce zero retention across an organization with the bedrock:DataRetentionMode condition key in an SCP.
  • Responsible AI policies: the AWS Responsible AI Policy (prohibited uses, human oversight for consequential decisions), AI Service Cards, Model Cards for your own models, and human review of high-impact outputs.

Guardrails don't evaluate tool results by default, and with InvokeModel only tagged input is checked for prompt attacks, so wrap untrusted content (user text, retrieved documents) in input tags. Guardrails aren't supported on embedding and rerank models or on the bedrock-mantle endpoint.

Key takeaways

  • CI/CD: Inspector for images (ECR enhanced scanning, SBOM scans in CodeBuild or the InspectorScan action) and code; Amazon Q code reviews; CodeGuru isn't the answer for new pipelines.
  • Artifacts: scoped identity policies, bucket, repository and key policies, customer managed KMS keys on every storage location, tag-based access, condition keys that force secure settings.
  • Roles: Identity Center for people, service roles for workloads, PassRole limited by role and service, Bedrock IAM on model and profile ARNs, guardrail condition keys.
  • Audit: CloudTrail (Bedrock invocations are management events, SageMaker InvokeEndpoint is a data event, no payloads), Config rules, Security Hub controls, GuardDuty AI Protection, invocation logging and data capture.
  • Troubleshooting: check role, key policy, bucket policy, endpoint policy and SCPs; decode authorization messages; policy simulator and Access Analyzer.
  • Network: private subnets in two Availability Zones, VPC endpoints, self-referencing security groups for distributed training, network isolation for untrusted code, inter-container encryption, Flow Logs.
  • Risks: prompt injection (customer's responsibility; prompt attack filter, input tags), excessive agency (least-privilege tools, Policy, confirmation), poisoning (write control, validation), extraction (rate limits), leakage (redaction, Macie).
  • Credentials: IAM roles first; Bedrock API keys for key-based clients, short-term preferred, block long-term keys on both endpoints.
  • Safeguards: Guardrails policies, detect mode, enforcement by IAM or organization; data retention modes; Responsible AI Policy and cards.
