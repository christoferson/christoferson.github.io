Overview

Task 3.1

Manage deployment infrastructure for ML and AI model types.

Questions in this task give a model and a traffic pattern and ask where to put it: a 2 GB request that takes 20 minutes, a model called a few times a day, 200 small per-customer models, a 70-billion-parameter open model, a model fine-tuned on premises, an agent that must call internal APIs. Match the traffic pattern (steady, spiky, rare, offline), the payload and latency, and the amount of control needed, and prefer the most managed option that fits. The SageMaker real-time and serverless notes and asynchronous and batch notes go deeper on hosting.

Running example. The online retailer (account 111111111111) serves the churn model to its CRM, scores all customers nightly, hosts an open-weight model for product descriptions, imports a model a partner fine-tuned, and deploys the support assistant as an agent that calls the order system.

Status changes to know. Amazon Bedrock Agents is now Agents Classic, in maintenance and closed to new customers since 30 July 2026; new agents use AgentCore. SageMaker Edge Manager reached end of life on 26 April 2024 (AWS points to ONNX and IoT Greengrass V2), and Elastic Inference is no longer available. The original SageMaker Operators for Kubernetes ended in February 2023; the ACK SageMaker controller replaces them. AWS's current LLM containers are LMI (with the vLLM engine), vLLM and SGLang; LMI-Dist and the older schedulers were removed in 2025. The new AgentCore CLI (npm @aws/agentcore, October 2026) replaces the pip starter toolkit.

Compute and deployment targets

Skill 3.1.1Select appropriate compute environments and deployment targets.

  • SageMaker AI endpoints: managed hosting with autoscaling, deployment guardrails, data capture and VPC support. The default answer for an ML model behind an API.
  • Amazon EKS: when the organisation already runs Kubernetes, or needs full control of the serving stack (vLLM or SGLang servers, GPU node pools from Karpenter that scale from zero). SageMaker HyperPod adds managed inference on its EKS clusters.
  • Amazon ECS: containers without Kubernetes; GPUs need EC2 container instances with the GPU AMI.
  • AWS Lambda: small CPU models with spiky traffic: up to 10,240 MB memory, a 10 GB container image, 15 minutes and a 6 MB synchronous payload, with no GPU.
  • EC2 with Deep Learning AMIs: the most control and the most operational work.
  • Edge devices: compile with SageMaker Neo or export to ONNX, and run on devices with AWS IoT Greengrass V2 (Edge Manager is retired).

Then choose the instance family:

  • CPU (M, C and Graviton families) for tree models, linear models and small networks.
  • GPU (G5, G6, G6e for most models; P4d, P5 for the largest) for deep learning and LLMs.
  • AWS Inferentia2 (Inf2) for lower cost per inference on supported models, after compiling them with the Neuron SDK.

"Least operational overhead" points to SageMaker AI endpoints (or Bedrock for foundation models); "the company standardised on Kubernetes" points to EKS; "inference on factory devices with poor connectivity" points to Neo or ONNX plus Greengrass. Use SageMaker Inference Recommender to compare instance types under load.

Orchestrators and multi-model hosting

Skill 3.1.2Select deployment orchestrators and multi-model or multi-container deployment strategies.

Orchestrators run the steps that train, register and deploy a model:

  • SageMaker Pipelines: ML-native steps (processing, training, tuning, model registration, endpoints, inference components), lineage and caching. The default for ML workflows on SageMaker.
  • AWS Step Functions: general workflows across many services, with optimized SageMaker integrations (training, processing, transform and endpoint calls that can wait for completion) and human approval steps.
  • Amazon MWAA (managed Apache Airflow): when data teams already schedule pipelines in Airflow.
  • Kubernetes: the ACK SageMaker controller manages endpoints, models and inference components as Kubernetes resources; Kubeflow pipeline components start training and hosting.

Packing several models onto shared infrastructure:

  • Inference components: each model gets its own CPU, accelerator and memory reservation and number of copies on a shared endpoint, scales independently (including to zero), and can serve LoRA adapters on a base model. The modern default for several foundation models.
  • Multi-model endpoints: many models with the same framework share one container and are loaded from S3 on demand (TargetModel); cheap for thousands of rarely used models, with cold starts. GPU multi-model endpoints need Triton.
  • Multi-container endpoints: up to 15 different containers on one endpoint, called directly (TargetContainerHostname) or in sequence.
  • Serial inference pipelines: 2 to 15 containers in sequence (preprocess, predict, postprocess) for real-time or batch, at no extra cost.

"A separate model per store, 500 stores, same algorithm, mostly idle" points to a multi-model endpoint. "Three models in different frameworks, low traffic each" points to a multi-container endpoint. "Several LLMs or fine-tuned variants sharing GPU instances, each scaling on its own" points to inference components.

Inference strategies

Skill 3.1.3Select model inference strategies (for example, real-time and batch processing).

  • Real-time endpoint: low latency, steady traffic; payloads up to 6 MB and 60 seconds per request (one SageMaker page now quotes 25 MB, but the API reference still says 6 MB). Stream tokens with InvokeEndpointWithResponseStream; bidirectional streaming over HTTP/2 suits speech.
  • Serverless inference: intermittent traffic, scales to zero, pay per use; up to 6 GB memory, 4 MB payloads and 60 seconds, no GPUs and no VPC; expect cold starts.
  • Asynchronous inference: queued requests with large inputs (up to 1 GB through S3) and long processing (up to an hour); results land in S3 with an SNS notification, and the endpoint can scale to zero when the queue is empty.
  • Batch transform: a whole dataset offline, no persistent endpoint, instances only while the job runs.
  • Foundation models on Bedrock: on-demand for interactive use, batch inference (about 50% cheaper, 100 to 100,000 records) for offline jobs.
Queue a large scoring request on an asynchronous endpoint (Python, boto3) 
import boto3

runtime = boto3.client("sagemaker-runtime")
resp = runtime.invoke_endpoint_async(
    EndpointName="product-image-tagger",
    # Input stays in S3; inline bodies are limited to 128,000 bytes
    InputLocation="s3://retail-ml-111111111111/async-in/batch-0412.json",
    ContentType="application/json",
)
print(resp["OutputLocation"])  # the result appears here; SNS can announce it

An endpoint created with an asynchronous configuration accepts only asynchronous calls, and serverless endpoints can't be converted back to real-time. To scale an asynchronous endpoint out from zero, add a scaling policy on HasBacklogWithoutCapacity; real-time endpoints scale to zero only with inference components.

FM deployment options

Skill 3.1.4Evaluate and select appropriate foundation model (FM) deployment options.

From most managed to most control:

  1. Bedrock serverless models: no infrastructure, pay per token, choose a service tier per request. For proprietary models (Claude, Nova) and catalog open-weight models.
  2. Bedrock custom model deployment: per-token serving of a model you fine-tuned on Bedrock, where supported (Nova and Llama 3.3 70B customized since July 2025).
  3. Bedrock Provisioned Throughput: hourly model units of guaranteed capacity, needed for custom models without on-demand deployment.
  4. Bedrock Custom Model Import: your own weights for a supported open architecture, served serverlessly (Skill 3.1.5).
  5. Bedrock Marketplace: over 100 specialised models deployed to SageMaker-managed instances that you size and pay for by the hour, but call through Bedrock APIs, so Guardrails and knowledge bases work with them.
  6. SageMaker AI endpoints: JumpStart models or any model in LMI, vLLM, SGLang or your own container, with full control of instances, scaling and networking.
  7. HyperPod inference or self-managed EKS and EC2: Kubernetes-native serving on reserved or existing clusters, with the most operational work.
Deploy a Bedrock Marketplace model on instances you choose (Python, boto3) 
import boto3

bedrock = boto3.client("bedrock", region_name="us-east-1")
endpoint = bedrock.create_marketplace_model_endpoint(
    endpointName="product-copy-model",
    # Hub content ARN from SageMaker list_hub_contents(HubName="SageMakerPublicHub")
    modelSourceIdentifier="arn:aws:sagemaker:us-east-1:aws:hub-content/SageMakerPublicHub/Model/example-model/1.0.0",
    endpointConfig={"sageMaker": {
        "initialInstanceCount": 1,
        "instanceType": "ml.g6.12xlarge",
        "executionRole": "arn:aws:iam::111111111111:role/MarketplaceEndpointRole",
    }},
    acceptEula=True,
)
# Then call bedrock-runtime converse() with the endpoint ARN as modelId

Bedrock Marketplace is not serverless: the instances bill until you delete the endpoint. "The model is already in Bedrock" means the serverless route; "a niche model from the Marketplace that should still use Guardrails" means Bedrock Marketplace; "an unsupported architecture or a custom serving stack" means a SageMaker AI endpoint.

Models built outside AWS

Skill 3.1.5Deploy models that were built outside of AWS into AWS environments (for example, Amazon SageMaker AI, Amazon Bedrock Custom Model Import).

Bedrock Custom Model Import serves open-weight models you trained or fine-tuned anywhere:

  • Supported architectures include Llama, Mistral and Mixtral, Qwen 2 to 3, Flan-T5, GPT-BigCode and GPT-OSS. Upload Hugging Face format files to S3 (safetensors weights, config.json, tokenizer files), under 200 GB for text models and 100 GB for multimodal, context under 128K. Embedding models aren't supported.
  • Serverless: billed per Custom Model Unit per minute in 5-minute windows while copies are active, and it scales to zero after 5 idle minutes, so the first call afterwards can return ModelNotReadyException; retry. Available in us-east-1, us-east-2, us-west-2 and eu-central-1; 3 imported models per account by default.
Import a partner's fine-tuned model into Bedrock (Python, boto3) 
import boto3

bedrock = boto3.client("bedrock", region_name="us-east-1")
bedrock.create_model_import_job(
    jobName="import-product-writer-01",
    importedModelName="product-writer-8b",
    roleArn="arn:aws:iam::111111111111:role/BedrockImportRole",
    modelDataSource={"s3DataSource": {"s3Uri": "s3://retail-ml-111111111111/imports/product-writer-8b/"}},
)
# Invoke with the imported model ARN as modelId; supply a chat template in the files

On SageMaker AI, the choices are:

  • A framework container (PyTorch, TensorFlow, scikit-learn, XGBoost): package the weights in model.tar.gz with code/inference.py, which defines model_fn (load) and optionally input_fn, predict_fn and output_fn.
  • Triton for ONNX, TorchScript and TensorRT models, with dynamic batching.
  • LMI, vLLM or SGLang containers for LLMs, pointed at Hugging Face files in S3.
  • ModelBuilder in the SDK, which picks a container, builds the serialization from sample input and output (SchemaBuilder), and can test locally first.
  • Your own container: respond to GET /ping and POST /invocations on port 8080, read artifacts from /opt/ml/model, and start within the health-check window.
The handlers in code/inference.py for a PyTorch model (Python) 
import json
import os

import torch

def model_fn(model_dir, context=None):
    # model.pth sits next to code/ inside model.tar.gz
    model = torch.load(os.path.join(model_dir, "model.pth"), weights_only=False)
    return model.eval()

def input_fn(request_body, content_type, context=None):
    return torch.tensor(json.loads(request_body)["features"])

def predict_fn(data, model, context=None):
    with torch.no_grad():
        return model(data)

def output_fn(prediction, accept, context=None):
    return json.dumps({"scores": prediction.tolist()})

ModelDataUrl must point to a single .tar.gz; to serve uncompressed Hugging Face files from S3, use ModelDataSource with CompressionType None. Custom Model Import doesn't support batch inference, and Converse isn't available for some imported architectures (Qwen 2.5 and 3, GPT-OSS), so use InvokeModel for those.

Deploying agents

Skill 3.1.6Deploy and configure agents for specific tasks, integration with other services and tools, and agent communication protocols.

Ways to build an agent on AWS:

  • AgentCore harness: declare the model, system prompt, tools and memory, and AWS runs the agent loop. AWS's guidance is to start here unless you need your own loop.
  • AgentCore Runtime: your own agent code in any framework (Strands Agents, LangGraph, CrewAI), packaged as a container or a zip, run in an isolated session per user. Needed for multi-agent graphs, swarms and custom routing.
  • Bedrock Flows: a fixed, visual sequence of prompts, knowledge bases and Lambda functions, when the path is known and no agent loop is wanted.
A support agent with one tool, ready for AgentCore Runtime (Python, Strands Agents) 
from bedrock_agentcore import BedrockAgentCoreApp
from strands import Agent, tool
from strands.models import BedrockModel

app = BedrockAgentCoreApp()

@tool
def get_order_status(order_id: str) -> str:
    """Look up the shipping status of an order.
    Args:
        order_id: The order number, for example 12345
    """
    return order_api.status(order_id)  # your internal API client

agent = Agent(
    model=BedrockModel(model_id="global.amazon.nova-2-lite-v1:0", temperature=0.2),
    tools=[get_order_status],
    system_prompt="You are the retailer's support agent. Use tools; never guess order data.",
)

@app.entrypoint
def invoke(payload, context):  # the second parameter must be named context
    return {"answer": str(agent(payload["prompt"]))}

if __name__ == "__main__":
    app.run()  # serves POST /invocations and GET /ping on port 8080

Deploy with the AgentCore CLI (agentcore deploy) or the CreateAgentRuntime API, then call InvokeAgentRuntime with a session ID. Integration and protocols:

  • AgentCore Gateway turns Lambda functions, OpenAPI and Smithy APIs, and existing MCP servers into tools behind one MCP endpoint, with outbound credentials (IAM, OAuth, API keys). AgentCore Identity handles inbound sign-in (IAM or a JWT authorizer) and stores outbound tokens; Policy can allow or deny each tool call.
  • Model Context Protocol (MCP): agent-to-tool. A Runtime hosting an MCP server listens on port 8000 at /mcp (streamable HTTP).
  • Agent2Agent (A2A): agent-to-agent across frameworks, on port 9000, with an agent card at /.well-known/agent-card.json.
  • AG-UI streams agent events to front ends; plain HTTP uses port 8080.
  • Multi-agent patterns (Strands): agents as tools (a supervisor calls specialists; start here), swarm (agents hand off to each other), graph (a defined flow with decisions at each node), workflow (a fixed DAG).

More in the AgentCore Runtime and Gateway, Identity and Policy notes.

Older questions may expect Bedrock Agents (action groups, knowledge bases attached to an agent); new accounts can't create them. A runtime protected by a JWT authorizer must be called over HTTPS with a bearer token, not with SigV4 through the AWS SDK.

FM hosting and resource allocation

Skill 3.1.7Configure FM deployment, model hosting, and resource allocation.

  • GPU memory for the weights: parameters × bytes per parameter: 2 bytes for fp16 or bf16, 1 for int8 or fp8, 4 for fp32. A 13B model in fp16 needs about 26 GB; a 70B model about 140 GB, more than any single GPU.
  • Plus the KV cache, which grows with context length and batch size; the memory left after the weights decides how many requests fit at once.
  • Fitting a large model: spread it over several GPUs with tensor parallelism (the degree must divide the GPU count), use a larger instance (G6e, P4d, P5), or quantize (fp8 or a pre-quantized AWQ or GPTQ checkpoint).
  • Throughput: continuous (rolling) batching packs requests together; speculative decoding with a small draft model speeds up generation. SageMaker AI's inference optimization jobs can apply quantization, compilation and speculative decoding for you.
  • Startup: large models take minutes to download and load, so raise ModelDataDownloadTimeoutInSeconds and ContainerStartupHealthCheckTimeoutInSeconds (up to 3,600 seconds).

The LMI container is configured with environment variables (OPTION_*) or a serving.properties file; then an inference component reserves the resources on a shared endpoint:

Host an open model with LMI as an inference component (Python, boto3) 
import boto3

sm = boto3.client("sagemaker")
sm.create_model(
    ModelName="product-copy-lmi",
    ExecutionRoleArn="arn:aws:iam::111111111111:role/SageMakerHostingRole",
    PrimaryContainer={
        "Image": "763104351884.dkr.ecr.us-east-1.amazonaws.com/djl-inference:0.38.0-lmi30.0.0-cu130",
        "Environment": {
            "HF_MODEL_ID": "s3://retail-ml-111111111111/models/product-copy-8b/",
            "OPTION_TENSOR_PARALLEL_DEGREE": "2",
            "OPTION_MAX_ROLLING_BATCH_SIZE": "32",
            "OPTION_MAX_MODEL_LEN": "8192",
        },
    },
)
sm.create_inference_component(
    InferenceComponentName="product-copy-ic",
    EndpointName="genai-shared-endpoint",
    VariantName="AllTraffic",
    Specification={
        "ModelName": "product-copy-lmi",
        "ComputeResourceRequirements": {
            "NumberOfAcceleratorDevicesRequired": 2,  # matches the tensor parallel degree
            "MinMemoryRequiredInMb": 32768,
        },
        "StartupParameters": {"ModelDataDownloadTimeoutInSeconds": 1800,
                              "ContainerStartupHealthCheckTimeoutInSeconds": 1800},
    },
    RuntimeConfig={"CopyCount": 1},
)

On a 4-GPU instance, a tensor parallel degree of 2 leaves room for two copies of the model. On Bedrock, resource allocation is a choice of service tier, Provisioned Throughput model units, or the number of Custom Model Import copies (more on the real-time inference page).

RAG configuration

Skill 3.1.8Apply Retrieval Augmented Generation (RAG) system configurations (for example, retrieval strategies, reranking).

The settings applied when a RAG application is deployed (the patterns themselves are in Task 2.1 and tuning in Task 2.2):

  • Number of results (1 to 100, default 5): more passages give the model more context but cost more tokens and add noise.
  • Search type: hybrid (keyword plus vector) or semantic on customer-managed knowledge bases; managed knowledge bases always use hybrid search.
  • Filters: explicit metadata filters (language, product line, region), or implicit filtering, where a model derives filters from the question.
  • Reranking: retrieve more (say 20), rerank, keep the best few (numberOfRerankedResults).
  • Query decomposition for multi-part questions; agentic retrieval on managed knowledge bases (AgenticRetrieveStream, whose iteration setting ranges from retrieval only through single-shot to multi-step).
  • Generation: a prompt template that includes $search_results$, a guardrail, and inference settings.
Answer from the help-centre knowledge base with citations (Python, boto3) 
import boto3

kb = boto3.client("bedrock-agent-runtime", region_name="us-east-1")
resp = kb.retrieve_and_generate(
    input={"text": "Can I return a sale item I bought online in a store?"},
    retrieveAndGenerateConfiguration={
        "type": "KNOWLEDGE_BASE",
        "knowledgeBaseConfiguration": {
            "knowledgeBaseId": "KB12345678",
            "modelArn": "arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-lite-v1:0",
            "retrievalConfiguration": {"vectorSearchConfiguration": {
                "numberOfResults": 8,
                "overrideSearchType": "HYBRID",
                "filter": {"equals": {"key": "language", "value": "en"}},
            }},
            "generationConfiguration": {
                "promptTemplate": {"textPromptTemplate": (
                    "Answer only from these help articles. If the answer isn't there, say so.\n"
                    "$search_results$\n$output_format_instructions$")},
                "guardrailConfiguration": {"guardrailId": "gr-support", "guardrailVersion": "3"},
            },
            "orchestrationConfiguration": {
                "queryTransformationConfiguration": {"type": "QUERY_DECOMPOSITION"}},
        },
    },
)
print(resp["output"]["text"], len(resp["citations"]))

Managed knowledge bases don't support RetrieveAndGenerate, a search-type override or a prompt template; use Retrieve with your own model call, or AgenticRetrieveStream. Removing $output_format_instructions$ from a custom template loses the citations.

Key takeaways

  • Targets: SageMaker AI endpoints by default; EKS for Kubernetes shops and full control; Lambda for small CPU models; Neo or ONNX with Greengrass at the edge; Inferentia2 for cheaper inference after Neuron compilation.
  • Orchestration: Pipelines for ML workflows, Step Functions across services, MWAA for Airflow teams, ACK for Kubernetes.
  • Packing: inference components for several FMs with their own resources; multi-model endpoints for many same-framework models; multi-container for different frameworks; serial pipelines for pre and post processing.
  • Inference: real-time (6 MB, 60 s), serverless (spiky, scales to zero, no GPU), asynchronous (1 GB, 1 hour, queue), batch transform (offline datasets); Bedrock batch for offline FM jobs.
  • FM options: Bedrock serverless, custom deployment, Provisioned Throughput, Custom Model Import, Marketplace (hourly instances), SageMaker endpoints, HyperPod or EKS.
  • Outside models: Custom Model Import for supported open architectures (serverless, cold starts); SageMaker framework containers with inference.py, Triton, LMI or your own container.
  • Agents: AgentCore harness or Runtime (Agents Classic is closed); Gateway for tools, Identity for auth; MCP for tools (port 8000), A2A between agents (port 9000).
  • Sizing: weights = parameters × bytes, plus KV cache; tensor parallelism, bigger instances or quantization for large models; raise startup timeouts.
  • RAG settings: number of results, hybrid search, filters, reranking, query decomposition, prompt template with $search_results$, a guardrail.
