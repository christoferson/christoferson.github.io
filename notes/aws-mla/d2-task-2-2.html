Overview

Task 2.2

Train, fine-tune, and customize models for ML and AI solutions.

Questions in this task are about the training job itself: the input format a built-in algorithm needs, where a script finds its data and saves its model, which tuning strategy to pick, why a model scores well in training and badly in testing, how to make a job finish sooner, and which settings change a fine-tuned foundation model. The SageMaker training notes go deeper on the training job API, Spot and warm pools; this page focuses on the choices the exam asks about.

Built-in algorithms and libraries

Skill 2.2.1Apply Amazon SageMaker AI built-in algorithms and common ML libraries.

A built-in algorithm is a container image you point a training job at, with no code of your own: you supply data in the format it expects and its hyperparameters. The details that come up most:

  • XGBoost: content types text/libsvm (the default), text/csv, Parquet and RecordIO-protobuf. For CSV, the label is the first column and there is no header; at inference the input has no label column. The only required hyperparameter is num_round (plus num_class for multiclass objectives); objective defaults to regression (reg:squarederror), so set binary:logistic for churn.
  • Linear Learner: RecordIO-protobuf (float32) or CSV with the label first; predictor_type is required (binary_classifier, multiclass_classifier or regressor).
  • K-Means: k and feature_dim are required.
  • Image classification: RecordIO files, or raw images with .lst index files (four channels), or an augmented manifest in Pipe mode; num_classes and num_training_samples are required.
  • Common libraries run in AWS's prebuilt framework containers: scikit-learn, XGBoost, PyTorch, TensorFlow and Hugging Face. Pin a framework version (built-in algorithm images, by contrast, are patched in place and AWS suggests the latest tag for them). Get image URIs with image_uris.retrieve.

Without "ContentType": "text/csv", XGBoost reads the files as libsvm and the job fails or learns nonsense. Hyperparameter values in the API are always strings. A CSV with a header row, or with the label anywhere but the first column, is a classic wrong answer.

Script mode

Skill 2.2.2Configure SageMaker AI script mode with supported frameworks for simplicity and performance.

Script mode runs your own training script inside AWS's framework container, so you write ordinary PyTorch, TensorFlow, scikit-learn or XGBoost code and don't build an image. The container contract:

  • Data in: each channel is at /opt/ml/input/data/<channel>, also given as SM_CHANNEL_<NAME>.
  • Model out: save to /opt/ml/model (SM_MODEL_DIR); SageMaker uploads it to S3 as model.tar.gz when the job ends.
  • Hyperparameters arrive as command-line arguments (and as JSON in SM_HPS). argparse actions such as store_true aren't supported; pass explicit values.
  • Cluster details: SM_NUM_GPUS, SM_HOSTS and SM_CURRENT_HOST for distributed jobs.
  • Metrics: print them and give the job metric definitions (a name and a regular expression) so they appear in CloudWatch and tuning can use them.
The skeleton of a script-mode training script (Python, train.py) 
import argparse
import os

import pandas as pd
import xgboost as xgb

parser = argparse.ArgumentParser()
parser.add_argument("--max_depth", type=int, default=6)
parser.add_argument("--eta", type=float, default=0.1)
args = parser.parse_args()

train = pd.read_csv(os.path.join(os.environ["SM_CHANNEL_TRAIN"], "train.csv"))
dtrain = xgb.DMatrix(train.drop(columns=["churned"]), label=train["churned"])
booster = xgb.train({"max_depth": args.max_depth, "eta": args.eta,
                     "objective": "binary:logistic"}, dtrain, num_boost_round=300)

# Anything in SM_MODEL_DIR becomes model.tar.gz in S3
booster.save_model(os.path.join(os.environ["SM_MODEL_DIR"], "xgboost-model"))
Run the script with ModelTrainer (Python, SageMaker Python SDK v3) 
from sagemaker.core import image_uris
from sagemaker.core.training.configs import Compute, InputData, SourceCode
from sagemaker.train import ModelTrainer

image = image_uris.retrieve("xgboost", "us-east-1", "3.2-0")
trainer = ModelTrainer(
    training_image=image,
    role="arn:aws:iam::111111111111:role/SageMakerTrainingRole",
    # requirements.txt inside source_dir is installed when the job starts
    source_code=SourceCode(source_dir="./src", entry_script="train.py",
                           requirements="requirements.txt"),
    compute=Compute(instance_type="ml.m5.2xlarge", instance_count=1),
    hyperparameters={"max_depth": 5, "eta": 0.1},
)
trainer.train(input_data_config=[
    InputData(channel_name="train", data_source="s3://retail-ml-111111111111/churn/train/"),
])
  • Simplicity ladder: a prebuilt container with your script; add a requirements.txt for extra packages (installed at every job start, and it needs a package repository, which breaks under network isolation); extend the AWS image with a Dockerfile FROM it to bake dependencies in; build your own container only when no framework image fits.
  • Test locally first: local mode runs the same container on your machine with Docker (Mode.LOCAL_CONTAINER in SDK v3), so mistakes cost seconds rather than a provisioned instance.
  • Performance: FastFile mode streams objects from S3 without waiting for a full download; FSx for Lustre suits large, repeatedly read datasets; warm pools reuse instances between runs.

Automatic model tuning

Skill 2.2.3Implement hyperparameter optimization (for example, SageMaker AI automatic model tuning [AMT]).

Automatic model tuning runs many training jobs with different hyperparameter values and keeps the best by an objective metric you choose (maximize validation AUC, minimize validation loss). The search strategies:

  • Bayesian (default): learns from finished jobs which values look promising. It gains from running jobs in sequence, so high parallelism makes it less effective.
  • Random: independent samples, so you can run as many jobs in parallel as you like without hurting the search.
  • Grid: every combination of categorical values only.
  • Hyperband: starts many jobs and stops weak ones early by resource level (epochs), so it suits iterative algorithms that report a metric each epoch and can be much faster. It has its own early stopping, so set the tuner's early stopping to Off.
  • Ranges: continuous, integer or categorical, with a scaling type (Auto, Linear, Logarithmic for values such as learning rates spanning several orders of magnitude, ReverseLogarithmic for values close to 1).
  • Early stopping (Auto) stops a job whose objective is worse than the median of earlier jobs at the same point.
  • Warm start reuses earlier tuning jobs: IdenticalDataAndAlgorithm (same data and algorithm, new ranges) or TransferLearning (changed data or algorithm).
  • Completion criteria end tuning when a target value is reached or the best result stops improving. Autotune lets AMT choose ranges and limits itself.
Tune the built-in XGBoost churn model (Python, SageMaker Python SDK v3) 
from sagemaker.core.parameter import ContinuousParameter, IntegerParameter
from sagemaker.core.training.configs import InputData
from sagemaker.train.tuner import HyperparameterTuner

tuner = HyperparameterTuner(
    model_trainer=xgb_trainer,  # a ModelTrainer for the built-in XGBoost image
    objective_metric_name="validation:auc",
    objective_type="Maximize",
    hyperparameter_ranges={
        "eta": ContinuousParameter(0.01, 0.5, scaling_type="Logarithmic"),
        "max_depth": IntegerParameter(3, 10),
        "subsample": ContinuousParameter(0.5, 1.0),
    },
    strategy="Bayesian",
    # max_jobs defaults to 1: always set it
    max_jobs=40,
    max_parallel_jobs=4,
    early_stopping_type="Auto",
)
tuner.tune(inputs=[
    InputData(channel_name="train", data_source="s3://retail-ml-111111111111/churn/train/"),
    InputData(channel_name="validation", data_source="s3://retail-ml-111111111111/churn/validation/"),
], wait=False)

Built-in algorithms publish their own metrics (such as validation:auc); script-mode jobs need metric definitions so the tuner can read the objective from the logs. "Tuning takes too long" points to Hyperband, early stopping, Random search with more parallel jobs, or warm start from an earlier tuning job.

Reducing training time

Skill 2.2.4Implement training time reduction techniques (for example, early stopping, distributed training).

  • Early stopping ends training when the validation metric stops improving: XGBoost early_stopping_rounds (no default; the best iteration is kept), Linear Learner early_stopping_patience (default 3 epochs) and early_stopping_tolerance, image classification early_stopping (off by default). In tuning, early_stopping_type="Auto".
  • Scale up before scaling out. AWS advises a larger instance (more or faster GPUs) before more instances, because one machine avoids network communication.
  • Data parallelism copies the model to every GPU and splits each batch; it is the first choice when the model fits on one GPU. Watch the per-GPU batch: 64 on 1 GPU becomes 2 per GPU on 32 GPUs, which can break convergence, so adjust the batch size and learning rate together.
  • Model parallelism splits the model itself when it doesn't fit, even with a batch of 1: sharded data parallelism (FSDP, sharding weights, gradients and optimizer state), tensor parallelism and pipeline parallelism. The SageMaker model parallelism library (SMP v2) builds on PyTorch FSDP.
  • Launching: in SDK v3, distributed=Torchrun(process_count_per_node=4) on ModelTrainer starts one process per GPU; HyperPod recipes package tested settings for large models.
  • Other levers: mixed precision (bf16 or fp16) for speed and memory; faster input (FastFile, FSx for Lustre, many medium-sized files with ShardedByS3Key); smart sifting, which skips low-loss samples in PyTorch; and a sample of the data while exploring.

SageMaker Debugger, whose built-in rules (overfit, loss not decreasing, vanishing gradient) could stop a job automatically, is closed to new customers. AWS points to MLflow, TensorBoard and CloudWatch for watching training; stop a run yourself or rely on early stopping.

Overfitting, underfitting and forgetting

Skill 2.2.5Prevent model overfitting, underfitting, and catastrophic forgetting.

  • Overfitting (high variance): good on training data, much worse on validation data, because the model memorised noise. Remedies AWS lists: more data, data augmentation, early stopping, fewer features, regularization (L1 penalises the absolute size of weights and can zero some out; L2 penalises their square), dropout in neural networks, and ensembles.
  • Underfitting (high bias): poor even on training data. Add informative features, use a more complex model, reduce regularization, or train for more epochs.
  • Detect it by comparing training and validation metrics over time, with a held-out test set and k-fold cross-validation when data is limited.

The knobs for the two most-tested algorithms:

  • XGBoost (all make the model more conservative as they grow, except where noted): alpha (L1, default 0), lambda (L2, default 1), gamma (minimum loss reduction to split, default 0), min_child_weight (default 1); lower max_depth (default 6; deeper overfits more), subsample and colsample_bytree below 1 (default 1), and a smaller eta (default 0.3) with more rounds.
  • Linear Learner: l1 and wd (weight decay, its L2 setting), both auto by default and 0 to turn off.

Catastrophic forgetting happens when fine-tuning or continued pre-training on narrow data overwrites what a model already knew: a model trained only on legal documents may lose its ability to code or do maths. AWS's Nova guidance prevents it by mixing general data with the new domain data and using a more conservative learning rate. Parameter-efficient fine-tuning (LoRA) also helps in practice because the base weights stay frozen, and so do fewer epochs and checking general benchmarks, not just the new task, after training.

"Training accuracy 99%, validation accuracy 70%" means overfitting: regularize, simplify, add data or stop earlier. "Both are 65%" means underfitting: more features, a more complex model or less regularization. "After fine-tuning, the assistant forgot how to follow general instructions" means catastrophic forgetting: mix in general data, lower the learning rate, use LoRA.

Combining models

Skill 2.2.6Combine multiple ML models to improve performance or reduce cost.

  • Bagging trains several models in parallel on resampled data and averages them (random forests); it mainly reduces variance.
  • Boosting trains weak models one after another, each correcting the last (XGBoost, LightGBM, CatBoost); it mainly reduces bias. Outliers can skew it.
  • Stacking trains a meta-model on the predictions of several base models. AutoGluon-Tabular stacks models in layers, and Autopilot's ensembling mode uses AutoGluon to train base models and combine them with a stacking ensemble.
  • Combining to cut cost or latency: route easy requests to a small model and hard ones to a large one (a cascade; Bedrock Intelligent Prompt Routing does this within a model family); distil a large model into a small one; host many models on shared instances with a multi-model endpoint, or up to 15 different containers on a multi-container endpoint; chain preprocessing, model and postprocessing on one endpoint with a serial inference pipeline (covered in Domain 3).

Ensembles usually improve accuracy at the cost of more inference compute and less interpretability. When a question asks for "the best accuracy on tabular data with little effort", an AutoML ensemble (Canvas, Autopilot, AutoGluon) is often the intended answer.

Fundamental hyperparameters

Skill 2.2.7Adjust fundamental hyperparameters (for example, epoch, steps, batch size).

  • Epoch: one full pass over the training data. Too few underfit; too many overfit (and in fine-tuning, cost more because more tokens are processed).
  • Batch size: examples processed before each weight update. Larger batches use more memory, run faster per epoch on GPUs and give smoother gradients, but very large batches can generalize worse; reduce the batch size when a job runs out of memory, and adjust the learning rate when you change it.
  • Step (iteration): one batch and one update. Steps per epoch = samples / batch size; total steps = epochs × steps per epoch. 50,000 examples with a batch of 100 for 3 epochs is 1,500 steps.
  • Learning rate: how far weights move each step. Too high diverges or bounces; too low trains slowly or stalls. Warmup steps raise it gradually at the start.

Names differ by algorithm: Linear Learner epochs (15) and mini_batch_size (1,000); K-Means mini_batch_size (5,000); image classification epochs (30) and mini_batch_size (32); XGBoost uses num_round and eta instead of epochs and learning rate.

Fine-tuning Amazon Nova Micro, Lite or Pro on Bedrock exposes just three: epochCount (1 to 5, default 2; larger datasets need fewer), learningRate (1e-6 to 1e-4, default 1e-5) and learningRateWarmupSteps (0 to 100, default 10). There's no batch size setting for Nova and no early stopping; AWS recommends starting from the defaults.

Prompting and fine-tuning FMs

Skill 2.2.8Apply customization techniques for AI solutions (for example, task-specific prompt engineering, fine-tuning).

Task-specific prompt engineering, from the Bedrock and Amazon Nova guides:

  • Give clear, complete instructions and a role in the system prompt; state the output format (one sentence, JSON with named keys); separate parts with delimiters or tags.
  • Few-shot examples: 3 to 5 examples similar to real inputs are often enough for classification.
  • Long documents first and the question last; tell the model to answer only from the supplied text and to say it doesn't know otherwise.
  • Step-by-step reasoning for multi-step problems; on Nova 2 use reasoning mode rather than "think in tags" prompts. For strict JSON with a complex schema, use tool use, which constrains the output.
  • Inference parameters: temperature low (0 to 0.2) for consistent extraction and classification, higher for creative text; topP limits choices to the most likely tokens; maxTokens and stopSequences bound the length.
  • Keep prompts as versioned templates with {{variables}} in Bedrock Prompt Management, test them against a held-out set, and try prompt optimization to rewrite a prompt for a target model.
A classification prompt with a role, examples and a fixed output (Python, boto3) 
import boto3

runtime = boto3.client("bedrock-runtime", region_name="us-east-1")
system = [{"text": (
    "You are a support triage assistant for an online retailer. "
    "Classify the message as one of: refund, delivery, product, account. "
    "Reply with the label only.\n"
    "Message: Where is my parcel? It was due Monday. -> delivery\n"
    "Message: I was charged twice for one order. -> refund\n"
    "Message: How do I change my email address? -> account"
)}]
resp = runtime.converse(
    modelId="amazon.nova-micro-v1:0",
    system=system,
    messages=[{"role": "user", "content": [{"text": "Message: The jacket zip broke after a week."}]}],
    inferenceConfig={"temperature": 0, "maxTokens": 5},
)
print(resp["output"]["message"]["content"][0]["text"])  # product

When prompting isn't enough (a consistent tone and template every time, or a narrow task a smaller model should handle), fine-tune. A Bedrock fine-tuning job takes the base model, a JSON Lines training file in S3 (Task 1.2), an optional validation file, an output location and hyperparameters as strings:

Fine-tune Nova Lite on approved support answers (Python, boto3) 
import boto3

bedrock = boto3.client("bedrock", region_name="us-east-1")
bedrock.create_model_customization_job(
    jobName="support-tone-ft-01",
    customModelName="support-tone-nova-lite",
    roleArn="arn:aws:iam::111111111111:role/BedrockCustomizationRole",
    baseModelIdentifier="amazon.nova-lite-v1:0:300k",
    customizationType="FINE_TUNING",
    trainingDataConfig={"s3Uri": "s3://retail-ml-111111111111/ft/support-train.jsonl"},
    validationDataConfig={"validators": [{"s3Uri": "s3://retail-ml-111111111111/ft/support-val.jsonl"}]},
    outputDataConfig={"s3Uri": "s3://retail-ml-111111111111/ft/output/"},
    # Strings only; for Nova these three are the only hyperparameters
    hyperParameters={"epochCount": "2", "learningRate": "0.00001", "learningRateWarmupSteps": "10"},
)
  • Watch the training and validation loss the job reports: validation loss rising while training loss falls means overfitting, so use fewer epochs or more data.
  • Fine-tuning on SageMaker AI (serverless customization, JumpStart, HyperPod recipes) adds LoRA or full fine-tuning, DPO and reinforcement techniques; see the SageMaker model customization notes and Bedrock supervised fine-tuning.

Retrieval and embedding models

Skill 2.2.9Optimize retrieval components and embedding models.

Measure first: Bedrock RAG evaluation jobs score retrieval with context relevance and context coverage (see the RAG evaluation notes). Then tune the components:

  • Chunking: chunks too small lose context, too large dilute the match; try fixed-size with overlap, hierarchical or semantic chunking (Task 1.2).
  • Search: hybrid search for exact terms, more results plus a reranker for relevance, and metadata filters to narrow the search space (Task 2.1).
  • Vector index: HNSW indexes trade recall against speed and memory. In OpenSearch, a larger graph (m, ef_construction) is more accurate but uses more memory and builds slower, and both are fixed when the index is created; a larger ef_search searches more accurately but more slowly. Faiss is the default engine (nmslib is deprecated). Quantization (fp16, byte, binary) and OpenSearch's disk-optimized mode compress vectors to cut memory cost at a small accuracy loss, with rescoring to recover it.
  • Store choice: S3 Vectors for large, infrequently queried indexes at low cost (sub-second, around 100 ms when warm, semantic only); OpenSearch for high query rates, hybrid search and rich filtering; Aurora pgvector when the data already lives in PostgreSQL.

The embedding model:

  • Dimensions: fewer dimensions mean cheaper storage and faster search at a small accuracy cost (Titan Text Embeddings V2: 256, 512 or 1,024; Cohere Embed v4: 256 to 1,536; Nova Multimodal Embeddings: 256 to 3,072, trained so that shorter vectors keep most of the accuracy).
  • Query versus document: models such as Cohere Embed take an input type (search_document when indexing, search_query when searching); mixing them up lowers relevance.
  • Domain fit: try another model on a sample of real questions, or fine-tune one. On Bedrock, only Titan Multimodal Embeddings G1 can be fine-tuned (image and caption pairs, no validation set). For text, fine-tune an open model such as BGE or a sentence-transformers model on SageMaker AI with question and passage pairs, and host it on an endpoint.
  • Changing the model means re-embedding everything: vectors from different models or dimensions can't be compared, and a Bedrock knowledge base's embedding model and vector store can't be changed after creation, so create a new knowledge base and re-ingest.
One training record for fine-tuning Titan Multimodal Embeddings G1 (JSON Lines) 
{"image-ref": "s3://retail-ml-111111111111/catalog/images/jacket-0412.png", "caption": "Women's waterproof hiking jacket, navy, taped seams"}

A better embedding model won't fix bad chunks, and a reranker can't find a passage that retrieval never returned. Tune in order: chunking, then retrieval (hybrid, number of results, filters), then reranking, then the embedding model, and re-run the same evaluation set after each change.

Key takeaways

  • Built-ins: XGBoost CSV has the label first, no header and needs text/csv (libsvm is the default); num_round is required; Linear Learner needs predictor_type, K-Means k and feature_dim; hyperparameters are strings.
  • Script mode: data in SM_CHANNEL_*, model to SM_MODEL_DIR, hyperparameters as arguments, metric definitions for CloudWatch and tuning; requirements.txt, then extend the image, then your own container; local mode to test.
  • AMT: Bayesian (default, modest parallelism), Random (parallel), Grid (categorical), Hyperband (fast, own early stopping); log scaling for learning rates; set max_jobs; warm start reuses earlier tuning.
  • Faster training: early stopping, a bigger instance before more instances, data parallel when the model fits, model parallel or FSDP when it doesn't, mixed precision, faster input.
  • Fit: overfitting means regularize, simplify, add data or stop early; underfitting means more features, complexity or epochs; forgetting means mix general data, lower the learning rate, use LoRA.
  • Combining: bagging reduces variance, boosting reduces bias, stacking learns from several models; cascades, distillation and multi-model endpoints cut cost.
  • Hyperparameters: steps = epochs × samples / batch size; adjust learning rate with batch size; Nova on Bedrock has only epochCount, learningRate and warmup steps.
  • FM customization: role, format, few-shot examples, low temperature for consistency, Prompt Management for versions; fine-tune with a Bedrock customization job when prompting can't deliver.
  • Retrieval: evaluate, then tune chunking, search, reranking and the index; fewer dimensions save cost; only Titan Multimodal Embeddings G1 fine-tunes on Bedrock; a new embedding model means a full re-index.
