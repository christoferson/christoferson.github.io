Overview

Task 4.2

Optimize and manage ML and AI infrastructure costs and performance.

Questions in this task give a cost or performance complaint ("the GPU endpoint is 20% utilised", "the Bedrock bill doubled", "nobody knows which team spends what", "latency spikes every evening") and ask for the tool or change that fixes it. The usual answer combines measurement (metrics, cost allocation, dashboards) with the cheapest change that keeps the service level: a smaller instance or model, packing models together, a commitment discount, caching or batching. Earlier tasks covered the levers themselves (Task 2.1 for training and inference trade-offs, Task 3.2 for capacity); this task is about managing them.

Running example. The online retailer (account 111111111111) runs the churn endpoint, a GPU endpoint for an open-weight model, the support assistant on Bedrock and an agent on AgentCore, and wants each team's share of the bill and an alert before it overspends.

Status changes to know. The AWS X-Ray SDKs and daemon have been in maintenance mode since 25 February 2026 (security fixes only); AWS recommends OpenTelemetry or the AWS Distro for OpenTelemetry, and X-Ray traces are viewed in the CloudWatch console (Trace Map, Transaction Search). Elastic Inference is retired. Cost Explorer can split Bedrock costs by model and provider (data from September 2026). AgentCore Runtime has a second pricing version (September 2026) that releases idle memory after 120 seconds. Prices below are us-east-1 list prices in November 2026; check the pricing pages before relying on them.

Inference instance families

Skill 4.2.1Select inference instance families to optimize performance and cost.

  • CPU (M, C, R and Graviton families) for tree models, linear models and small networks; Graviton gave up to 40% better performance at the same price on SageMaker (Graviton2 figure).
  • GPU: G6 (about twice G4dn for inference), G6e (AWS's "most cost-efficient GPU instances for generative AI", 2.5 times G5, LLMs up to about 13B parameters), G7 and G7e for larger models, P4d and P5 for the biggest models and highest throughput.
  • AWS Inferentia2 (Inf2): up to 40% better price performance than comparable EC2 instances for supported models, after compiling with the Neuron SDK.
  • Fit the model to the GPU (Task 3.1): an under-used GPU can be shared with inference components or Multi-Instance GPU partitions instead of paying for a second instance.

SageMaker Inference Recommender benchmarks a model on candidate instance types: a Default job (under 45 minutes) suggests instance types; an Advanced job (about 2 hours) load tests with your traffic pattern and stops on latency or invocation limits. Results include cost per hour, cost per inference, latency and maximum invocations. AWS's guidance: compare on cost per inference for throughput-bound work and cost per hour when there is no latency deadline.

Ask Inference Recommender which instances suit the churn model (Python, boto3) 
import boto3

sm = boto3.client("sagemaker")
sm.create_inference_recommendations_job(
    JobName="churn-instance-check",
    JobType="Default",  # "Advanced" adds a traffic pattern and stopping conditions
    RoleArn="arn:aws:iam::111111111111:role/SageMakerRecommenderRole",
    InputConfig={
        "ModelPackageVersionArn": "arn:aws:sagemaker:us-east-1:111111111111:model-package/churn-models/14"},
)
# describe_inference_recommendations_job(...)["InferenceRecommendations"] lists
# instance types with CostPerHour, CostPerInference, ModelLatency and MaxInvocations

Troubleshooting tools

Skill 4.2.2Configure and use tools to troubleshoot and analyze resources (for example, Amazon CloudWatch, Amazon Bedrock AgentCore Observability, AWS X-Ray).

  • CloudWatch metrics show where time and capacity go: ModelLatency versus OverheadLatency separates slow model code from SageMaker overhead; CPU, GPU and memory utilisation show over- or under-sized instances; Bedrock's time to first token and throttles show model-side limits (Task 4.1).
  • CloudWatch Logs Insights queries endpoint, job and invocation logs; Contributor Insights rules find the top contributors in logs (the callers sending most requests, the inputs causing most errors).
  • Tracing: AWS X-Ray (now viewed as Trace Map and Transaction Search in CloudWatch, fed by OpenTelemetry) follows a request through API Gateway, Lambda and other services. SageMaker endpoints don't emit traces themselves, so trace the client that calls them. Turn on Lambda active tracing and API Gateway stage tracing.
  • AgentCore Observability traces each agent step, model call and tool call (spans), with session, latency and error metrics, so a slow agent can be narrowed to one model call or one tool.
  • Container Insights on EKS reports GPU, Neuron and EFA metrics per pod and node; CloudWatch investigations (Amazon Q) can suggest causes for an alarm.

"Find which step of the request is slow across several services" points to tracing (X-Ray or OpenTelemetry traces in CloudWatch). "Find which customer sends most failing requests" points to Contributor Insights. "Is the delay in my model or in the platform?" points to ModelLatency versus OverheadLatency.

Dashboards

Skill 4.2.3Set up dashboards to monitor performance metrics.

  • CloudWatch dashboards combine metric graphs (with metric math), alarm status, log query results and text on a 24-column grid, up to 500 widgets. They can mix Regions without setup; across accounts, use CloudWatch cross-account observability.
  • Prebuilt views: the generative AI observability pages for Bedrock and agents, the SageMaker detailed metrics dashboard for self-hosted LLMs, and automatic service dashboards.
  • Sharing: with specific email addresses, publicly, or through single sign-on; viewers can see all metrics in the account, so share carefully.
  • Amazon Managed Grafana for teams that already use Grafana; the SageMaker Model Dashboard is a governance view (models, cards, monitors), not a performance dashboard.

Capacity for cost and reliability

Skill 4.2.4Optimize capacity for cost, performance, and reliability.

  • Reliability: AWS strongly recommends at least two instances per production endpoint, in subnets in at least two Availability Zones, so SageMaker can spread them; several smaller instances across zones survive a failure better than one large one. For inference components, more than two copies on at least two instances.
  • Cost: autoscaling instead of sizing for peak (Task 3.2), scale to zero for rarely used inference component endpoints (with cold starts), serverless or asynchronous inference for spiky or queued work, and packing models with inference components or multi-model endpoints.
  • Scarce GPUs: instance pools fall back to other instance types when one is unavailable; training plans reserve capacity outright; request GPU quotas early (several start at 0).
  • Bedrock: cross-Region inference profiles spread load across Regions for capacity, Provisioned Throughput or the Reserved tier guarantee throughput, and retries with backoff absorb throttling.

A single-instance endpoint has no redundancy, and the default quota is low (4 instances per endpoint), so reliability and scaling plans may need a quota increase first. Instance fallback improves the chance of capacity but doesn't reserve it.

Cost management tools and quotas

Skill 4.2.5Optimize costs and set cost quotas by using appropriate cost management tools.

  • Know who spends: activate cost allocation tags (SageMaker domains can propagate their tags to the apps they launch; tag endpoints, jobs and pipelines). For Bedrock, give each team or application its own application inference profile with tags, attribute by IAM principal, and use Cost Explorer's Bedrock model and provider attributes. requestMetadata on calls appears in logs but isn't a billing tag.
  • AWS Budgets: alerts on actual or forecast cost or usage (by service, tag or account), and budget actions that apply an IAM policy or SCP (for example denying new SageMaker endpoints or Bedrock calls) or stop EC2 and RDS instances. Budget actions can't stop SageMaker resources directly.
  • AWS Cost Anomaly Detection learns normal spend and alerts on unusual jumps (it also covers third-party Bedrock models billed through AWS Marketplace).
  • Cost Explorer and Data Exports (CUR 2.0) for analysis; AWS Compute Optimizer flags idle SageMaker endpoints (no invocations for 14 days).
  • Hard limits: Service Quotas (Bedrock tokens and requests per minute, SageMaker instance counts) cap how much can be consumed; IAM can restrict which models, tiers and instance types people may use.
  • Idle resources: SageMaker Studio idle shutdown for JupyterLab and Code Editor spaces, deleting unused endpoints, and lifecycle rules on S3 data.
A tagged inference profile per team, and a budget on that team's tag (Python, boto3) 
import boto3

bedrock = boto3.client("bedrock", region_name="us-east-1")
profile = bedrock.create_inference_profile(
    inferenceProfileName="support-assistant-prod",
    modelSource={"copyFrom": "arn:aws:bedrock:us-east-1:111111111111:inference-profile/global.amazon.nova-2-lite-v1:0"},
    tags=[{"key": "team", "value": "customer-support"}],
)
# The app calls Converse with profile["inferenceProfileArn"] as modelId

boto3.client("budgets").create_budget(
    AccountId="111111111111",
    Budget={
        "BudgetName": "customer-support-ai",
        "BudgetType": "COST",
        "BudgetLimit": {"Amount": "3000", "Unit": "USD"},
        "TimeUnit": "MONTHLY",
        "FilterExpression": {"Tags": {"Key": "team", "Values": ["customer-support"]}},
        "Metrics": ["NET_UNBLENDED_COST"],
    },
    NotificationsWithSubscribers=[{
        "Notification": {"NotificationType": "FORECASTED", "ComparisonOperator": "GREATER_THAN",
                         "Threshold": 90, "ThresholdType": "PERCENTAGE"},
        "Subscribers": [{"SubscriptionType": "EMAIL", "Address": "support-leads@example.com"}],
    }],
)

Tags must be activated as cost allocation tags in the Billing console before they appear in budgets and Cost Explorer.

Purchasing options

Skill 4.2.6Optimize infrastructure costs by selecting purchasing options.

  • On-Demand: the default for everything; pay for what runs.
  • SageMaker Savings Plans: up to 64% off for a one- or three-year dollars-per-hour commitment (no, partial or all upfront), covering SageMaker training, real-time inference, batch transform, processing and notebooks across instance families and Regions. Compute Savings Plans don't apply to SageMaker (they cover EC2, Lambda and Fargate). Savings Plans don't reserve capacity.
  • Managed Spot Training: up to 90% off for interruptible training with checkpoints. There's no Spot option for real-time endpoints.
  • Training plans: reserved GPU or Trainium capacity for training or inference, paid upfront and not cancellable.
  • Self-managed EC2 (EKS, ECS): EC2 Instance Savings Plans (up to 72%), Reserved Instances (only zonal ones reserve capacity), Spot (two-minute interruption warning), and Capacity Blocks for ML (prepaid P and Trainium instances for 1 to 182 days, no discounts on top).
  • Bedrock: on-demand tiers (Flex 50% cheaper, Priority 75% dearer), batch (50% cheaper), Reserved tier, Provisioned Throughput with no commitment, one month or six months (cheaper per hour with longer terms).

"Steady 24/7 SageMaker usage for the next year across several instance types" points to a SageMaker Savings Plan; "guaranteed P5 capacity for a launch in March" points to a training plan; "cheapest way to run nightly retraining that can restart" points to Managed Spot Training with checkpoints.

Cost of FMs in production

Skill 4.2.7Evaluate cost implications of using FMs for inference in production.

  • On-demand price = input tokens × input rate + output tokens × output rate, per million tokens. Output tokens cost several times more than input (8.3 times for Nova 2 Lite: $0.30 per million input and $2.50 output with a global profile), so long answers and reasoning dominate the bill.
  • Price varies by profile and tier: geographic and in-Region profiles cost about 10% more than global ones; Flex and batch halve the price; Priority adds 75%. Some models charge a higher long-context rate for the whole request above a size threshold.
  • Cached input is billed at a fraction of the normal input price (Nova 2 Lite cache reads $0.075 per million, and Nova cache writes are free; other providers charge for writes).
  • Provisioned Throughput bills every hour whether used or not (Nova: $60.50 per model unit per hour without commitment, $30.25 with six months, roughly $22,000 to $44,000 a month per unit), so it pays only for sustained, predictable volume or custom models that need it.
  • Self-hosting on SageMaker AI is a fixed hourly cost per instance: cheaper per token at high, steady utilisation, dearer when idle.
Estimate the support assistant's monthly model cost (Python) 
requests_per_day = 40_000
input_tokens, output_tokens = 1_800, 350   # per request, from CloudWatch token metrics
price_in, price_out = 0.30, 2.50           # USD per million tokens, Nova 2 Lite, global profile

monthly = requests_per_day * 30 * (input_tokens * price_in + output_tokens * price_out) / 1_000_000
print(f"${monthly:,.0f} per month")        # about $1,700; output is a third of the tokens but over 60% of the cost

cached_share = 0.8                          # 80% of the input is a fixed instruction block
with_cache = requests_per_day * 30 * (
    input_tokens * ((1 - cached_share) * price_in + cached_share * 0.075)
    + output_tokens * price_out) / 1_000_000
print(f"${with_cache:,.0f} per month with prompt caching")

Agent resource consumption

Skill 4.2.8Monitor agent resource consumption patterns.

  • AgentCore Runtime bills active consumption: vCPU-hours and GB-hours of memory. CPU isn't billed while the agent waits on I/O (model calls, tools), but memory is billed for the whole session: in AWS's own example memory is 68% of the Runtime cost. The newer pricing version releases idle memory after 120 seconds.
  • Watch CPUUsed-vCPUHours, MemoryUsed-GBHours and ActiveSessionCount in AWS/Bedrock-AgentCore (they can lag up to an hour), plus Gateway invocation counts and model token counts per agent.
  • Other agent costs: Gateway ($0.005 per 1,000 tool invocations, more for tool search), Memory (short-term storage by size, long-term records, $0.50 per 1,000 retrievals), evaluations, and above all the model tokens for every reasoning step and tool call.
  • Patterns to look for: sessions left open until the idle timeout, tool call loops (retries, agents handing work back and forth), many model calls per user turn, and context growing every turn. Gateway rate limits on requests, tokens and connection time can cap a runaway agent.

Shorten the idle timeout and end sessions explicitly when a conversation finishes, cap tool calls and handoffs (Task 4.1), and keep the agent's container small, because memory is billed for the whole session.

Optimizing FM usage

Skill 4.2.9Manage FM inference costs with usage optimization.

  • Smaller model first, route only hard requests to a larger one, or distil (Task 2.1).
  • Fewer input tokens: prompt caching for fixed instructions and documents, shorter prompts (Bedrock prompt optimization can shorten them), fewer and better-ranked retrieved chunks, and trimming or summarising conversation history.
  • Fewer output tokens: a realistic maxTokens, instructions for concise answers, structured output instead of prose, and turning reasoning down where it isn't needed.
  • Cheaper pricing: batch or Flex for anything not interactive, global profiles where data residency allows.
  • Meter every call: the Converse response's usage gives inputTokens, outputTokens, cacheReadInputTokens and cacheWriteInputTokens; log them per feature to see what each change saves.
Keep agent context bounded by summarising old turns (Python, Strands Agents) 
from strands import Agent
from strands.agent.conversation_manager import SummarizingConversationManager

agent = Agent(
    model=support_model,
    tools=support_tools,
    # Summarise the oldest 30% of history when the context fills; keep the last 10 messages
    conversation_manager=SummarizingConversationManager(summary_ratio=0.3, preserve_recent_messages=10),
)

Strands trims history with a sliding window by default; keeping the full history needs NullConversationManager, which grows cost every turn.

AI-specific cost patterns

Skill 4.2.10Monitor AI-specific cost patterns (for example, token usage optimization, embedding computation costs, vector database storage optimization).

  • Tokens: track input and output tokens per model, team and feature (CloudWatch token metrics, invocation logs by principal, tagged inference profiles); alarm on anomalies, which often mean a prompt change, a loop or abuse.
  • Embeddings: cheap per call (Titan Text Embeddings V2: $0.02 per million tokens, half that in batch) but repeated for every document, every re-ingestion and every query. Ingest incrementally, and remember that changing the embedding model means re-embedding everything.
  • Vector storage: fewer dimensions or binary embeddings cut storage and memory (Task 1.2).
    • S3 Vectors charges for storage ($0.06 per GB-month), writes, queries and data processed, with no minimum, so it suits large, rarely queried indexes.
    • OpenSearch Serverless charges per capacity unit hour ($0.24); classic collections keep a minimum number of units running (a vector collection costs a few hundred dollars a month even when idle), while newer collections can scale to zero.
    • Quantization and OpenSearch's disk-optimized mode lower memory needs.
  • Knowledge bases: a customer-managed knowledge base costs the embeddings, the vector store and the generation model; idle vector stores keep billing.
  • Logging: model invocation logs to CloudWatch Logs cost $0.50 per GB ingested (less for Infrequent Access), so set retention or send bulky logs to S3.

"The cheapest vector store" depends on query rate: S3 Vectors is cheapest at rest and for occasional queries, while OpenSearch is better value for high query rates, hybrid search and rich filtering. An unused OpenSearch Serverless classic collection still bills its minimum capacity.

Key takeaways

  • Instances: CPU and Graviton for small models, G6 and G6e for most GPU inference, Inf2 for price performance after Neuron compilation; Inference Recommender compares cost per inference and latency.
  • Troubleshooting: ModelLatency versus OverheadLatency, Logs Insights and Contributor Insights, traces through X-Ray or OpenTelemetry in CloudWatch, AgentCore spans for agents.
  • Dashboards: CloudWatch dashboards (JSON body, metric math, cross-Region and cross-account) plus the prebuilt GenAI and SageMaker views.
  • Capacity: two or more instances across Availability Zones, autoscaling, scale to zero where cold starts are acceptable, instance pools and training plans for GPUs.
  • Cost tools: tags and tagged inference profiles for attribution, Budgets with actions (IAM or SCP, not stopping SageMaker), Cost Anomaly Detection, Service Quotas as hard caps, idle shutdown.
  • Purchasing: SageMaker Savings Plans (not Compute Savings Plans), Spot for training only, training plans for reserved capacity, Bedrock tiers, batch and Provisioned Throughput.
  • FM costs: output tokens dominate; global profiles are cheaper; caching, batch and Flex cut the rate; Provisioned Throughput bills around the clock.
  • Agents and AI patterns: AgentCore memory bills for the whole session; watch tokens per feature, re-embedding costs and idle vector store minimums.
