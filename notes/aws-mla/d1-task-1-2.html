Overview

Task 1.2

Perform data transformation, feature engineering, and pre-processing.

Questions in this task give a dataset and a goal and ask which transformation, tool or setting gets the data ready: a scaler for a distance-based algorithm, an encoding for a high-cardinality column, a chunking strategy for long manuals, the service that redacts names before documents reach a knowledge base, or the file format a fine-tuning job expects. Two habits run through the right answers: fit every transformation on training data only and apply the same fitted transformation at inference, and clean and redact before data reaches a model or an index, because nothing downstream undoes it.

Running example. The online retailer from Task 1.1 (account 111111111111): the churn model needs scaled and encoded customer features plus real-time clickstream counts; the product-support assistant needs help articles chunked and embedded, support transcripts redacted, and a fine-tuning set of good answers in the company's tone.

Status changes to know. Data Wrangler now runs inside SageMaker Canvas; the classic interface isn't in the new Studio. Bedrock's own continued pre-training is no longer in its documentation; continued pre-training is done for Amazon Nova on SageMaker AI. Fine-tuning has ended on Bedrock for Claude 3 Haiku and Llama 3.2, and Llama 3.1 and 3.3 are Legacy. Some Amazon Comprehend features (topic modeling, event detection, prompt safety classification) are closed to new customers, but PII detection and redaction are not. S3 Object Lambda, once a way to redact on read, is closed to new customers since 7 November 2025.

Transformation tools

Skill 1.2.1Transform data by using AWS tools (for example, AWS Glue, AWS Glue DataBrew, Spark on Amazon EMR, SageMaker Data Wrangler).

AWS doesn't publish a single rule for choosing; the pattern exam questions follow is who does the work and how big it is.

  • SageMaker Data Wrangler (in Canvas): visual preparation for ML in Studio, with ML-specific transforms: encode categorical (ordinal, one-hot, similarity), scale values (standard, robust, min-max, max-absolute), handle missing values and outliers, featurize text and date/time, balance data (random over- or undersampling, SMOTE), split data, and a Data Quality and Insights report that flags target leakage. Results go to S3 or a Canvas dataset, run on EMR Serverless above 5 GB, and the flow can be exported as a notebook or a scheduled Processing job, so production repeats the same steps.
  • AWS Glue DataBrew: visual cleaning with 250+ transformations in reusable recipes, outside SageMaker, for analysts and data engineers. Its data science actions include BINARIZATION, BUCKETIZATION, CATEGORICAL_MAPPING, ONE_HOT_ENCODING (up to 10 distinct values), SCALE (min-max, mean normalization, z-score), SKEWNESS and TOKENIZATION, plus outlier and PII steps. Profile jobs describe a dataset; recipe jobs apply the steps ($0.48 per node-hour).
  • AWS Glue ETL: serverless Spark (Glue 5.1 by default, 6.0 since August 2026) for scheduled pipelines in code or Glue Studio, with transforms such as Detect PII, drop duplicates and fill missing values, and job bookmarks for incremental runs.
  • Spark on EMR or EMR Serverless: the most control for very large or custom work, including Spark MLlib feature transformers; SageMaker Processing runs scikit-learn or PySpark scripts on managed instances as a pipeline step.

"A data scientist wants to prepare and visualize data for a model without code, inside SageMaker" points to Data Wrangler in Canvas; "analysts clean data in a no-code tool and share recipes" points to DataBrew; "a nightly, large-scale, code-based job" points to Glue or EMR.

Managing features

Skill 1.2.2Create and manage features by using AWS tools (for example, SageMaker Feature Store).

Feature Store gives training and inference the same feature values: the online store holds the latest record per customer, and the offline store keeps every version for point-in-time training sets (creation, tiers and queries are in the SageMaker data preparation notes, ingestion in Task 1.1). Managing features means changing groups, documenting them and keeping pipelines that compute them.

Add a feature to an existing group and document it (Python, boto3) 
import boto3

sm = boto3.client("sagemaker")

# Features can be added (up to 100 per call) but never removed or changed
sm.update_feature_group(
    FeatureGroupName="customer-profile",
    FeatureAdditions=[{"FeatureName": "support_views_7d", "FeatureType": "Integral"}],
)

sm.update_feature_metadata(
    FeatureGroupName="customer-profile",
    FeatureName="support_views_7d",
    Description="Support page views in the last 7 days, from the clickstream pipeline",
    ParameterAdditions=[{"Key": "owner", "Value": "ml-platform"}, {"Key": "pii", "Value": "false"}],
)
  • Schema changes: a new feature is empty until records are rewritten, and changes take up to 5 minutes to appear. To remove or retype a feature, create a new feature group (for example customer-profile-v2) and backfill it.
  • Discovery: the Search API with Resource="FeatureMetadata" and the Feature Catalog in Studio find features by name, description or parameters, including groups shared from other accounts through AWS RAM.
  • Feature processors: a @feature_processor function reads sources (CSV, Parquet, another feature group's offline store), transforms with Spark and writes to a feature group; to_pipeline and schedule turn it into a scheduled SageMaker pipeline with lineage.
  • TTL and deletion: a group-level TTL expires online records counted from their event time, and applies only to records written after it's set. DeleteFeatureGroup removes the online store only; the offline data in S3 and its Glue table remain (and keep costing) until you delete them.

Transforming streams

Skill 1.2.3Transform streaming data (for example, by using AWS Lambda, Spark).

The churn model scores customers while they browse, using a feature that counts support-page views in the last five minutes. A Lambda function on the Kinesis stream with a tumbling window computes it without any other infrastructure:

Count support-page views per customer in 5-minute windows and write them to Feature Store (Python, AWS Lambda; event source mapping with --tumbling-window-in-seconds 300) 
import base64
import json

import boto3

fs = boto3.client("sagemaker-featurestore-runtime")


def lambda_handler(event, context):
    # State is carried between invocations in the same window (up to 1 MB per shard)
    state = event.get("state") or {}
    for record in event["Records"]:
        click = json.loads(base64.b64decode(record["kinesis"]["data"]))
        if click.get("page_type") == "support":
            state[click["customer_id"]] = state.get(click["customer_id"], 0) + 1

    if event["isFinalInvokeForWindow"]:
        for customer_id, views in state.items():
            fs.put_record(FeatureGroupName="customer-realtime-features", Record=[
                {"FeatureName": "customer_id", "ValueAsString": customer_id},
                {"FeatureName": "event_time", "ValueAsString": event["window"]["end"]},
                {"FeatureName": "support_views_5m", "ValueAsString": str(views)},
            ])
        return {"state": {}}
    # The function must always return state
    return {"state": state}
  • Lambda event source mappings for Kinesis and MSK batch records (batch size, batching window), can split a failing batch in two, report partial failures (ReportBatchItemFailures) and aggregate in tumbling windows of up to 15 minutes. Good for light, per-record or short-window transforms.
  • Spark Structured Streaming on Glue streaming jobs or EMR handles heavier transforms and joins in micro-batches: Glue's forEachBatch processes each window (100 seconds by default) with a checkpoint location instead of job bookmarks, and a Glue streaming job is billed for as long as it runs. Glue 6.0 adds a real-time mode for stateless streams with millisecond latency.
  • Firehose transforms records with a Lambda function before landing them, and Managed Service for Apache Flink handles long windows, stream joins and exactly-once state (Task 1.1).

Feature engineering

Skill 1.2.4Perform feature engineering (for example, scaling, standardization, feature splitting, binning, log transformation, normalization).

  • Standardization (z-score: subtract the mean, divide by the standard deviation) suits roughly normal features and linear and distance-based models. Min-max normalization rescales to 0 to 1, but one outlier squeezes everything else. Robust scaling uses the median and interquartile range, so outliers matter less. Tree models such as XGBoost don't need scaling; k-nearest neighbours, k-means, linear models and neural networks do. SageMaker's Linear Learner scales features itself (normalize_data, true by default, and normalize_label for regression).
  • Log transformation (often log1p to handle zeros) compresses long right tails such as order totals or session counts.
  • Binning turns a number into ranges: equal-width bins, or quantile bins with the same number of records in each, which helps when the relationship to the label isn't linear (age bands, tenure bands).
  • Encoding categories: one-hot for a few unordered values, ordinal for ordered ones (bronze, silver, gold), and for high-cardinality columns such as product IDs, hashing, target statistics or Data Wrangler's similarity encoding rather than thousands of one-hot columns. Decide what happens to categories that appear only after training.
  • Feature splitting and crosses: split a timestamp into hour, day of week and month (cyclical sine and cosine encoding for linear and deep models), split strings by a delimiter, and combine columns into a new feature (spend per visit, region by channel).
Split first, then fit the transformations on the training data only (Python, scikit-learn in a Processing job) 
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.model_selection import train_test_split
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import FunctionTransformer, KBinsDiscretizer, OneHotEncoder, StandardScaler

df = pd.read_parquet("/opt/ml/processing/input/customers.parquet")
X, y = df.drop(columns=["churned"]), df["churned"]
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.2, stratify=y, random_state=42)

features = ColumnTransformer([
    # Long-tailed spend: log first, then standardize
    ("spend", make_pipeline(FunctionTransformer(np.log1p), StandardScaler()), ["order_total_90d"]),
    ("scaled", StandardScaler(), ["tenure_months", "monthly_charges"]),
    ("age_band", KBinsDiscretizer(n_bins=5, encode="onehot-dense", strategy="quantile"), ["age"]),
    # Categories seen only at inference become all zeros instead of an error
    ("plan", OneHotEncoder(handle_unknown="ignore", sparse_output=False), ["plan", "channel"]),
])

X_train_t = features.fit_transform(X_train)  # learn means, bins and categories here only
X_test_t = features.transform(X_test)        # reuse them; never fit on test data

Fitting a scaler or encoder on the whole dataset before splitting leaks test information into training and overstates accuracy. Save the fitted transformer with the model (or put the same steps in a serial inference pipeline, or compute features once in Feature Store) so inference applies exactly the training-time transformation.

Embedding models

Skill 1.2.5Configure and use embedding models to transform text and image data into numerical representations.

  • Amazon Titan Text Embeddings V2 (amazon.titan-embed-text-v2:0): text to 1,024, 512 or 256 dimensions, a normalize flag for cosine similarity, and float or binary output (embeddingTypes). AWS measured 256 dimensions at about 97% of the accuracy of 1,024 for a quarter of the storage, and binary vectors at about 97 to 98.5%.
  • Cohere Embed: v3 (English and Multilingual; 96 texts of up to 512 tokens per call) and v4 (cohere.embed-v4:0; text and images, up to about 128K tokens, 256 to 1,536 dimensions). Both take an input_type: search_document when indexing and search_query when searching.
  • Multimodal: Titan Multimodal Embeddings G1 (text and images) and Amazon Nova Multimodal Embeddings (text, documents, images, video and audio in one space) for searching product photos or manuals by text (Task 1.1).
  • Self-hosted: open models such as BGE, E5 and GTE from SageMaker JumpStart on your own endpoint, when you need a specific model, a private network or fixed per-instance cost. Large backfills on Bedrock run as batch inference jobs (Titan and Nova embeddings support it).
Embed a help article for indexing with Cohere Embed v4 (Python, boto3) 
import json

import boto3

brt = boto3.client("bedrock-runtime", region_name="us-east-1")
resp = brt.invoke_model(
    modelId="cohere.embed-v4:0",
    body=json.dumps({
        "texts": ["Items can be returned within 30 days of delivery..."],
        # Queries later use "search_query"; documents use "search_document"
        "input_type": "search_document",
        "embedding_types": ["float"],
        "output_dimension": 1024,
    }),
)
body = json.loads(resp["body"].read())

Index and query with the same model, version and dimension: vectors from different models aren't comparable, and changing the embedding model means re-embedding the whole collection. The vector store's index dimension must match the model's output, and cosine search expects normalized vectors.

Text pre-processing

Skill 1.2.6Apply advanced text pre-processing techniques (for example, tokenization, domain-specific augmentation).

  • Tokenization splits text into the units a model reads. Large language models use subword tokenizers that belong to each model, so token counts differ between models; Bedrock's CountTokens API (free, permission bedrock:CountTokens) counts the tokens a request would use for a given model before you send it. A rough guide AWS gives for Titan is about 4.7 characters per token.
  • Classic NLP versus LLMs: lowercasing, stop-word removal and stemming help bag-of-words and TF-IDF models (Data Wrangler's vectorize transform tokenizes on white space, lowercases and computes TF-IDF), but they remove meaning an LLM or embedding model uses, so pass natural text to those. Always strip HTML and boilerplate and normalize whitespace.
  • Algorithm formats: BlazingText text classification wants one sentence per line, space-separated tokens and a __label__ prefix (__label__returns how do i send back a jacket); Amazon Comprehend custom classification takes a CSV of label then text, with at least 50 documents per class.
  • Domain-specific augmentation adds training examples for rare intents: paraphrases or synthetic questions generated with a Bedrock model, back-translation (translate to another language and back with Amazon Translate, using custom terminology to keep product names fixed), and synonym replacement with the company's own vocabulary. Review generated data before using it.

Documents for RAG

Skill 1.2.7Prepare documents for Retrieval Augmented Generation (RAG) applications (for example, chunking strategies, metadata extraction).

Retrieval quality depends on how documents are split and labelled. Amazon Bedrock Knowledge Bases offers these chunking strategies (details in the Knowledge Bases notes):

  • Default: about 300 tokens, keeping sentences whole.
  • Fixed-size: maxTokens (1 to 8,192) with overlapPercentage (1 to 99) so a fact cut at a boundary still appears whole in one chunk. Simple and predictable for uniform text.
  • Hierarchical: small child chunks for precise matching, returning their larger parent chunks for context. Good for long, structured manuals; can return fewer results than requested, and AWS doesn't recommend it with S3 Vectors.
  • Semantic: splits where the meaning changes (breakpointPercentileThreshold, bufferSize), using a model and so costing more. Good for documents without clear structure.
  • None: each file is one chunk, for content already split (FAQ entries); custom chunking is None plus a Lambda function after parsing.
Hierarchical chunking for the product manuals data source (JSON, part of CreateDataSource) 
{
  "vectorIngestionConfiguration": {
    "chunkingConfiguration": {
      "chunkingStrategy": "HIERARCHICAL",
      "hierarchicalChunkingConfiguration": {
        "levelConfigurations": [{"maxTokens": 1500}, {"maxTokens": 300}],
        "overlapTokens": 60
      }
    }
  }
}
  • The strategy can't be changed after the data source is created; changing it means a new data source and a full re-ingest.
  • Parsing: the default parser reads text; Bedrock Data Automation ($0.010 per page) or a foundation model parser extracts tables, figures and scanned pages, and can include a whole table or page with the chunk that matched it.
  • Metadata: a manual.pdf.metadata.json file next to each document (up to 10 KB), such as {"metadataAttributes": {"category": "returns", "product_line": "outdoor", "year": 2026}}, lets queries filter by category or product. Extract the values with Comprehend, a model call or the document's own fields during preparation.

Masking and redaction

Skill 1.2.8Mask, redact, and anonymize data.

Masking hides part of a value (card ending 4242); redaction removes or replaces it ([NAME]); hashing or deterministic encryption pseudonymizes an identifier so records still join; anonymization removes enough that a person can't be re-identified, even by combining fields. The support transcripts must be redacted before they reach the knowledge base or a fine-tuning set:

Redact personal data from support tickets before ingestion (Python, boto3, Amazon Comprehend) 
import boto3

comprehend = boto3.client("comprehend", region_name="us-east-1")
job = comprehend.start_pii_entities_detection_job(
    JobName="support-tickets-redact-2026-11",
    LanguageCode="en",
    # Redaction happens only in this asynchronous job; ONLY_OFFSETS just locates PII
    Mode="ONLY_REDACTION",
    RedactionConfig={
        "PiiEntityTypes": ["NAME", "EMAIL", "PHONE", "ADDRESS", "CREDIT_DEBIT_NUMBER"],
        "MaskMode": "REPLACE_WITH_PII_ENTITY_TYPE",
    },
    InputDataConfig={"S3Uri": "s3://retail-support-raw-111111111111/tickets/", "InputFormat": "ONE_DOC_PER_LINE"},
    OutputDataConfig={"S3Uri": "s3://retail-support-redacted-111111111111/tickets/"},
    DataAccessRoleArn="arn:aws:iam::111111111111:role/ComprehendPiiJobRole",
)
print(job["JobId"], job["JobStatus"])
  • Amazon Comprehend: DetectPiiEntities and ContainsPiiEntities are real-time (up to 100 KB) and find PII without changing the text; redaction is the asynchronous job above, with MASK (a mask character) or replacement by the entity type. PII detection is documented for English and Spanish.
  • AWS Glue Detect PII transform: detect, redact, partially redact or SHA-256 hash columns in an ETL job. Glue DataBrew has PII recipe steps such as MASK_CUSTOM, CRYPTOGRAPHIC_HASH (HMAC-SHA256 with a Secrets Manager key), ENCRYPT (KMS) and DETERMINISTIC_ENCRYPT (same input, same output, so joins still work).
  • Amazon Transcribe redacts PII in transcripts (not in the audio); Amazon Macie finds sensitive data in S3 but never changes it.
  • At query time, Bedrock Guardrails sensitive information filters block or mask PII in prompts and responses, but they don't clean the documents in a knowledge base or invocation logs, so redact before ingestion too.

Macie is discovery, not redaction; Comprehend's real-time PII APIs locate PII but don't redact it; hashing an email without a secret key can be reversed by hashing a list of known emails. The usual exam answer for "remove PII from documents before a RAG index" is a Comprehend redaction job (or Glue Detect PII for tables) before ingestion, plus Guardrails on the responses.

Data for fine-tuning and distillation

Skill 1.2.9Prepare data for FM fine-tuning, continuous pre-training, and model distillation.

AWS's guidance in one line: fine-tuning teaches a model how to respond, not what to know (use RAG for knowledge). Quality beats quantity: real user questions with reviewed, gold-standard answers, deduplicated, one skill per example, the same system prompt as production, and a held-out set for evaluation.

One training example per line (JSON Lines, for Amazon Bedrock and SageMaker AI customization) 
// Supervised fine-tuning, prompt and completion
{"prompt": "Can I return a jacket after 40 days?", "completion": "Our return window is 30 days from delivery, so ..."}
// Supervised fine-tuning, Converse format (Amazon Nova)
{"schemaVersion": "bedrock-conversation-2024", "system": [{"text": "You are the retailer's support assistant."}], "messages": [{"role": "user", "content": [{"text": "Can I return a jacket after 40 days?"}]}, {"role": "assistant", "content": [{"text": "Our return window is 30 days from delivery, so ..."}]}]}
// Continued pre-training of Nova on SageMaker AI: raw domain text
{"text": "Care guide: waterproof jackets should be washed at 30 degrees ..."}

The comment lines are for reading only; JSON Lines files can't contain comments.

  • Fine-tuning: labelled prompt and response pairs, typically hundreds to thousands (Amazon Nova 2 recommends 2,000 to 10,000, minimum 200; Nova allows up to 20,000 samples and a 32K context), plus a validation file. Some text patterns (role markers such as User:) make Nova jobs fail. SageMaker AI serverless customization adds DPO pairs (chosen and rejected) and RL formats (see the model customization notes).
  • Continued pre-training: large volumes of unlabelled domain text (tens of billions of tokens for Nova on SageMaker AI), packed into long samples, followed by instruction tuning so the model still follows prompts.
  • Distillation: only prompts are needed: a teacher model writes the responses that train a smaller student. On Bedrock, supply up to 15,000 prompts in Converse JSON Lines (2 GB file, 16 KB per line) or point at your model invocation logs; current teachers are Amazon Nova models.
  • Before training: redact PII (Skill 1.2.8), check sequence lengths against the model's limit, and keep a held-out test set the model never sees.

Key takeaways

  • Tools: Data Wrangler in Canvas for visual ML prep in SageMaker; DataBrew for no-code recipes outside it; Glue ETL for scheduled serverless Spark; EMR for large custom Spark; Processing for scripted steps in pipelines.
  • Feature Store: add features but never remove them (new group for breaking changes), document with feature metadata, schedule feature processors; deleting a group leaves the offline data behind.
  • Streams: Lambda tumbling windows (always return state) for short aggregations, Glue streaming forEachBatch or EMR for heavier transforms, Flink for long stateful windows.
  • Features: standardize for linear and distance models (trees don't care), log for skew, quantile bins for non-linear effects, one-hot for few categories and hashing or similarity encoding for many; fit on training data only.
  • Embeddings: Titan V2 (256 to 1,024 dimensions, normalize, binary), Cohere v3 and v4 (input_type document versus query), Nova and Titan multimodal; one model and dimension for index and query.
  • Text: model-specific tokenizers and CountTokens; classic cleanup for bag-of-words, natural text for LLMs; BlazingText __label__ format; augment rare intents with generated or back-translated examples.
  • RAG: fixed-size with overlap, hierarchical for long structured documents, semantic for unstructured; strategy fixed at creation; metadata files for filtering.
  • PII: Comprehend redaction jobs (real-time APIs only detect), Glue Detect PII, DataBrew hashing and deterministic encryption, Transcribe redaction; Macie only finds; redact before ingestion, Guardrails at query time.
  • FM data: fine-tuning needs reviewed prompt and response pairs in JSON Lines; continued pre-training needs lots of raw text; distillation needs only prompts.
