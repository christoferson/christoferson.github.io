Overview

Task 4.1

Monitor ML and AI model inference and performance.

Questions in this task ask which signal shows a problem and where to watch it: rising latency on one model, a pipeline that fails at night, a feature whose values have shifted, which variant of an A/B test is winning, an agent whose tool calls keep failing, answers that are being cut off. Task 2.3 covers how to measure quality (baselines, drift statistics, shadow tests, evaluation metrics); this task is about watching continuously and acting automatically, mostly with Amazon CloudWatch metrics, logs, traces and alarms.

Running example. The online retailer (account 111111111111) watches its churn endpoint and training pipeline, an A/B test of two churn models, the support assistant's Bedrock model calls, and the support agent on AgentCore with its order-lookup and refund tools.

Status changes to know. CloudWatch generative AI observability reached general availability on 13 October 2025 (preview from July 2025). SageMaker Model Monitor has been closed to new customers since 30 July 2026; drift is now watched with open-source Evidently and MLflow (Task 2.3). Don't confuse that library with CloudWatch Evidently, AWS's feature-flag service, discontinued in October 2025. CloudWatch Omni (September 2026) adds a separate console for agent investigation but doesn't replace the existing views or alarms.

Monitoring models in production

Skill 4.1.1Monitor model performance in production by using Amazon CloudWatch generative AI observability, Amazon Bedrock Model Evaluation, and drift detection pipelines.

CloudWatch generative AI observability is a section of the CloudWatch console with two views, at no extra charge beyond normal CloudWatch telemetry costs:

  • Model Invocations: invocation count, invocation latency, token counts by model and per day, requests grouped by input size, throttles and errors, filterable by model ID, with an alarm icon on each graph. The table of individual requests (inputs and outputs, opened in Logs Insights) needs Bedrock model invocation logging to CloudWatch Logs; S3-only logging doesn't feed it.
  • Bedrock AgentCore agents: sessions, traces and spans for agents on AgentCore Runtime or elsewhere (instrumented with OpenTelemetry through the AWS Distro for OpenTelemetry), which needs CloudWatch Transaction Search turned on.

Behind the views are the AWS/Bedrock metrics: Invocations, InvocationLatency, TimeToFirstToken (streaming only), InputTokenCount, OutputTokenCount, InvocationThrottles, InvocationClientErrors and InvocationServerErrors. Self-hosted models on SageMaker AI endpoints have their own metrics (ModelLatency, error counts, and for LLMs time to first token and tokens per second with the newer detailed metrics).

Alarm when more than 2% of Bedrock requests fail (Python, boto3) 
import boto3

def bedrock_metric(metric_id, name):
    return {"Id": metric_id, "ReturnData": False, "MetricStat": {
        # No ModelId dimension: errors before the model is resolved have none
        "Metric": {"Namespace": "AWS/Bedrock", "MetricName": name},
        "Period": 300, "Stat": "Sum"}}

boto3.client("cloudwatch").put_metric_alarm(
    AlarmName="support-assistant-bedrock-error-rate",
    Metrics=[
        bedrock_metric("srv", "InvocationServerErrors"),
        bedrock_metric("cli", "InvocationClientErrors"),
        bedrock_metric("thr", "InvocationThrottles"),
        bedrock_metric("inv", "Invocations"),
        # Throttles aren't counted in Invocations, so add them to both sides
        {"Id": "rate", "ReturnData": True,
         "Expression": "100 * (srv + cli + thr) / (inv + thr)", "Label": "Error and throttle rate %"},
    ],
    ComparisonOperator="GreaterThanThreshold",
    Threshold=2,
    EvaluationPeriods=3,
    TreatMissingData="notBreaching",
    AlarmActions=["arn:aws:sns:us-east-1:111111111111:ml-oncall"],
)
  • Bedrock model evaluation doesn't run continuously; schedule evaluation jobs on a sample of production prompts and responses (bring your own responses) and alarm when scores drop (Skill 4.1.6).
  • Drift detection pipelines compare captured inputs and predictions with the training baseline on a schedule and publish the scores as metrics (Task 2.3, and Skill 4.1.3 for the data).

Throttled requests appear in no other Bedrock metric (not Invocations, not the error counts), and requests rejected for exceeding a quota count as client errors, not throttles. CloudWatch publishes no recommended alarm set for Bedrock or SageMaker AI, so thresholds are your design.

Errors and anomalies in workflows

Skill 4.1.2Monitor workflows to detect anomalies or errors in data processing or model inference.

  • SageMaker Pipelines: EventBridge sends "SageMaker Model Building Pipeline Execution Status Change" (route Failed to SNS) and a per-step event that includes the failureReason; the execution event itself has no reason, so read it with ListPipelineExecutionSteps or DescribePipelineExecution. Training, processing and transform job events carry FailureReason too.
  • Job and endpoint logs are in CloudWatch Logs: /aws/sagemaker/TrainingJobs, /aws/sagemaker/ProcessingJobs, /aws/sagemaker/TransformJobs, and /aws/sagemaker/Endpoints/<endpoint-name> (one stream per variant and instance). Metric filters turn log patterns (for example "OutOfMemory") into metrics.
  • Endpoint metrics: Invocation4XXErrors, Invocation5XXErrors, InvocationModelErrors (the container returned an error, surfaced to callers as HTTP 424), ModelLatency and OverheadLatency (in microseconds), plus CPU, GPU, memory and disk in /aws/sagemaker/Endpoints.
  • Other services: Step Functions ExecutionsFailed and ExecutionsTimedOut; AWS Glue job run state events, job metrics and job run insights (which explain failed runs); Glue Data Quality results and score events (Task 1.3); Lambda Errors and Throttles.
  • Anomaly detection alarms learn a metric's normal band (with daily and weekly patterns, from up to two weeks of data) and alarm outside it: good for latency or traffic with no fixed threshold. Composite alarms combine several alarms (for example high latency AND high errors) to cut noise.

Alarm when endpoint latency leaves its normal band (Python, boto3) 
import boto3

boto3.client("cloudwatch").put_metric_alarm(
    AlarmName="churn-endpoint-latency-anomaly",
    Metrics=[
        {"Id": "m1", "ReturnData": True, "MetricStat": {
            "Metric": {"Namespace": "AWS/SageMaker", "MetricName": "ModelLatency",
                       "Dimensions": [{"Name": "EndpointName", "Value": "churn-endpoint"},
                                      {"Name": "VariantName", "Value": "AllTraffic"}]},
            "Period": 300, "Stat": "Average"}},
        {"Id": "band", "Expression": "ANOMALY_DETECTION_BAND(m1, 2)"},
    ],
    ThresholdMetricId="band",  # no fixed Threshold for anomaly alarms
    ComparisonOperator="GreaterThanUpperThreshold",
    EvaluationPeriods=3,
    AlarmActions=["arn:aws:sns:us-east-1:111111111111:ml-oncall"],
)

A pipeline that finishes with some failed steps ends as CompletedWithFailures, which never appears in EventBridge events; check the step events too. SageMaker may send more than one event per state change, so make handlers idempotent. Anomaly alarms can't drive Auto Scaling actions.

Changes in data distribution

Skill 4.1.3Detect changes in data distribution that can affect model performance.

To see what the model is receiving, capture it. Data capture on the endpoint configuration (DataCaptureConfig: on or off, sampling percentage, S3 location, input, output or both) writes JSON Lines files to s3://.../<endpoint>/<variant>/yyyy/mm/dd/hh/, each record holding the request, the response and an event ID. It works without Model Monitor.

  • Join with ground truth later: pass an InferenceId on each request; it is stored with the captured record, so labels that arrive weeks later can be matched to the prediction.
  • Compare distributions: on a schedule, compute PSI or KS statistics per feature between the training baseline and recent captured inputs (the Evidently and MLflow pattern in Task 2.3), publish them as CloudWatch metrics and alarm on them.
  • Watch predictions too: when labels are slow to arrive, a shift in the share of "will churn" predictions is the earliest warning that inputs or behaviour have changed.
  • Check data before it reaches the model: Glue Data Quality rules and anomaly detection on the incoming batch catch broken feeds (an empty column, a doubled row count) before predictions are made.
Tag each prediction so ground truth can be joined later (Python, boto3) 
import uuid

import boto3

runtime = boto3.client("sagemaker-runtime")
inference_id = str(uuid.uuid4())
resp = runtime.invoke_endpoint(
    EndpointName="churn-endpoint",
    ContentType="text/csv",
    Body="34,12,79.5,1,0,3",
    InferenceId=inference_id,  # stored in the captured record's eventMetadata
)
save_prediction(customer_id="48213", inference_id=inference_id,
                score=float(resp["Body"].read()))  # your own store, joined to outcomes later

Ground-truth files are organised by the date the label was collected, not the date of the prediction, so the join must use the inference ID, not the folder date. Sampling 100% of a busy endpoint gets expensive; capture a percentage that still gives enough data per day.

A/B test monitoring

Skill 4.1.4Monitor model performance in production by using A/B testing.

  • Split traffic between production variants by weight (50/50 to start), or force a variant with TargetVariant for chosen users.
  • Operational metrics per variant: every SageMaker endpoint metric has a VariantName dimension, so latency and errors can be compared side by side.
  • Model and business metrics per variant: each response names the variant that served it (InvokedProductionVariant, from the x-Amzn-Invoked-Production-Variant header). Store it with the prediction, join with outcomes (did the customer churn? did they accept the offer?), and compare precision, recall, F1 or revenue per variant.
  • Decide and shift: AWS's documented flow moves traffic gradually (50/50, then 25/75, then 0/100) with UpdateEndpointWeightsAndCapacities, without replacing the endpoint, then removes the losing variant.
  • Enough data: AWS gives no significance test for SageMaker variants, so run the test long enough to cover weekly patterns and collect enough outcomes before calling a winner. AgentCore's A/B testing for agents does report p-values and significance.
Record which variant answered, and shift traffic to the winner (Python, boto3) 
import boto3

runtime = boto3.client("sagemaker-runtime")
resp = runtime.invoke_endpoint(EndpointName="churn-ab-endpoint", ContentType="text/csv",
                               Body="34,12,79.5,1,0,3")
variant = resp["InvokedProductionVariant"]  # "churn-v1" or "churn-v2"; log it with the prediction

# Weeks later, v2 has better recall on joined outcomes: move 75% of traffic to it
boto3.client("sagemaker").update_endpoint_weights_and_capacities(
    EndpointName="churn-ab-endpoint",
    DesiredWeightsAndCapacities=[
        {"VariantName": "churn-v1", "DesiredWeight": 25},
        {"VariantName": "churn-v2", "DesiredWeight": 75},
    ],
)

A/B testing exposes real users to the new model; a shadow test (Task 2.3) doesn't. "Measure the effect on customers' behaviour" needs A/B; "check latency and errors without affecting anyone" needs shadow.

Agent performance and coordination

Skill 4.1.5Monitor and automate the management of agent performance and coordination (for example, coordination failure detection, truncated streaming, tool failures).

AgentCore Observability publishes metrics in AWS/Bedrock-AgentCore and traces to CloudWatch:

  • Runtime: invocations, latency, session counts, throttles, system errors and user errors.
  • Gateway (the tool layer): invocations, latency, duration, target execution time and errors per tool name. These are under All metrics, not on the GenAI observability page.
  • Memory and Identity: latency, errors, failed extractions, token fetch failures.
  • Traces: each agent step, model call and tool call is a span; a failed tool shows as an error on the span for that tool, so the "errors and latency by span" chart points to the failing tool.

The three failure modes the skill names:

  • Tool failures: a tool error comes back to the agent as a tool result with an error status, not an exception, so the agent may carry on with bad information. Alarm on Gateway errors per tool, and retry or stop in code.
  • Truncated streaming: an answer cut off by maxTokens ends with stopReason max_tokens on an otherwise successful call, so no error metric moves. Stream errors (such as modelStreamErrorException) arrive inside an HTTP 200 stream, and a stream with no final messageStop or metadata event is incomplete. AgentCore Runtime streams last at most 60 minutes.
  • Coordination failures: multi-agent runs can loop (agents handing the task back and forth), stall, or exceed limits. Strands Swarm and Graph have limits on handoffs, iterations and time (a Swarm defaults to 20 handoffs and 15 minutes), and report a failed status when one is hit; repetitive handoff detection is off unless configured.
Detect truncated or broken streamed answers (Python, boto3) 
import boto3

runtime = boto3.client("bedrock-runtime", region_name="us-east-1")
resp = runtime.converse_stream(
    modelId="global.amazon.nova-2-lite-v1:0",
    messages=[{"role": "user", "content": [{"text": "Explain our returns policy step by step."}]}],
    inferenceConfig={"maxTokens": 800},
)
text, stop_reason, finished = [], None, False
for event in resp["stream"]:
    if "contentBlockDelta" in event:
        text.append(event["contentBlockDelta"]["delta"].get("text", ""))
    elif "messageStop" in event:
        stop_reason = event["messageStop"]["stopReason"]
    elif "metadata" in event:
        finished = True
    elif "modelStreamErrorException" in event:
        raise RuntimeError("model failed mid-stream; retry the request")

if not finished or stop_reason == "max_tokens":
    publish_metric("TruncatedAnswers", 1)  # your own CloudWatch metric to alarm on
Retry a failing tool once and stop runaway tool loops (Python, Strands Agents hooks) 
from strands.hooks import AfterToolCallEvent, BeforeToolCallEvent, HookProvider, HookRegistry

class ToolGuard(HookProvider):
    def __init__(self, max_calls=15):
        self.calls, self.retried, self.max_calls = 0, set(), max_calls

    def register_hooks(self, registry: HookRegistry):
        registry.add_callback(BeforeToolCallEvent, self.before)
        registry.add_callback(AfterToolCallEvent, self.after)

    def before(self, event):
        self.calls += 1
        if self.calls > self.max_calls:
            event.cancel_tool = "Too many tool calls; ask a human for help"

    def after(self, event):
        tool_id = event.tool_use.get("toolUseId", "")
        if event.result.get("status") == "error" and tool_id not in self.retried:
            self.retried.add(tool_id)
            event.retry = True  # run the same tool call again once

# agent = Agent(..., hooks=[ToolGuard()])
  • Quality, continuously: AgentCore Evaluations online configurations score a sample of live sessions (goal success, tool selection and parameter accuracy, faithfulness) and publish the scores as CloudWatch metrics to alarm on.
  • Automate the response: alarms on error rate, throttles or evaluation scores trigger SNS and Lambda (page someone, switch traffic, disable a failing Gateway target); Strands retries model throttling automatically (up to 6 attempts with exponential backoff by default).

FM performance monitoring

Skill 4.1.6Configure AI-specific performance monitoring for foundation models (FMs), such as Amazon Bedrock evaluations.

  • Speed: TimeToFirstToken (what users feel when streaming), InvocationLatency (to the last token), and output tokens per second (computed from output tokens and latency with metric math); alarm on percentiles (p90) rather than averages.
  • Volume and cost signals: input and output token counts per model, with anomaly detection to catch a prompt change or abuse that suddenly multiplies tokens; group usage by caller with requestMetadata tags or by IAM principal in Logs Insights.
  • Safety signals: InvocationsIntervened and related metrics in AWS/Bedrock/Guardrails show how often guardrails block or mask content; a sudden rise suggests misuse or an over-strict policy.
  • Quality: scheduled Bedrock evaluation jobs on sampled production traffic (LLM-as-a-judge with the same judge model each time; RAG evaluations for retrieval), results published as metrics; human review of a small sample; user feedback stored with the request ID (Task 2.3).
Token use per caller from invocation logs (CloudWatch Logs Insights query) 
fields identity.arn as principal,
       input.inputTokenCount as inTokens,
       output.outputTokenCount as outTokens
| stats sum(inTokens) as totalInput, sum(outTokens) as totalOutput, count() as calls by principal
| sort totalInput desc

"Turn on online evaluation for a Bedrock model" is a distractor: Bedrock model evaluation runs as jobs, and continuous sampled scoring exists for agents in AgentCore. Invocation log records carry tokens and bodies but no latency or error code, so take those from metrics. Guardrail metrics are in their own namespace, not AWS/Bedrock.

Key takeaways

  • GenAI observability: Model Invocations view (metrics automatic, request table needs invocation logs in CloudWatch Logs) and the agent view (needs Transaction Search); no extra charge beyond CloudWatch.
  • Bedrock metrics: throttles aren't counted in Invocations or errors, quota rejections are client errors, don't filter error alarms by ModelId; build rates with metric math.
  • Workflows: EventBridge for pipeline and job failures (reasons are on step and job events), CloudWatch Logs groups per job type and endpoint, anomaly and composite alarms.
  • Data changes: data capture to S3 with an InferenceId for later ground truth, scheduled PSI or KS against the baseline, watch prediction shares when labels are slow, data quality checks upstream.
  • A/B tests: per-variant metrics by VariantName, log InvokedProductionVariant with predictions and join outcomes, shift weights gradually, collect enough data.
  • Agents: AgentCore Runtime, Gateway and Memory metrics and traces; tool errors come back as results; truncation is stopReason max_tokens; Swarm and Graph limits and hooks catch loops; online evaluations score live sessions.
  • FMs: time to first token, latency percentiles, tokens per second, token anomalies, guardrail interventions, scheduled evaluation jobs for quality.
