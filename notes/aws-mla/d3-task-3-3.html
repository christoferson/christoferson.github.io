Overview

Task 3.3

Implement automated orchestration and continuous integration and continuous delivery (CI/CD) pipelines for MLOps and AI workloads.

Questions in this task describe a manual, risky release and ask for the automated, reversible version: a canary that rolls back on an alarm, a pipeline that refuses a model worse than the current one, retraining that starts when drift is detected, an audit trail of who approved which model, and the same discipline for prompts, agents and knowledge bases. The pattern is always build, test, register, approve, deploy gradually, watch, roll back. The SageMaker Pipelines and MLOps notes go deeper on pipelines and projects.

Running example. The online retailer (account 111111111111) retrains the churn model monthly or when drift appears, deploys it through staging to production, versions the support assistant's prompts, ships agent updates through a pipeline, and refreshes the help-centre knowledge base nightly.

Deployment strategies and rollback

Skill 3.3.1Implement automated deployment strategies and rollback actions.

SageMaker AI deployment guardrails update an endpoint without downtime:

  • Blue/green (the default, all at once): a new fleet is built, traffic moves, and the old fleet waits for a baking period before being deleted.
  • Canary: a small share of capacity (up to 50%) gets traffic first; after the baking period the rest moves.
  • Linear: traffic moves in equal steps (10 to 50% each) with a wait between steps.
  • Rolling: instances are replaced in batches (5 to 50%) on the same fleet, which needs less spare capacity, for large GPU endpoints; not for serverless or multi-variant endpoints.
  • Automatic rollback: CloudWatch alarms (error rate, latency) watched during the rollout; if one fires, traffic returns to the old fleet.
Update the churn endpoint with a canary and alarm rollback (Python, boto3) 
import boto3

sm = boto3.client("sagemaker")
sm.update_endpoint(
    EndpointName="churn-endpoint",
    EndpointConfigName="churn-cfg-2026-12",  # same variant name as before
    DeploymentConfig={
        "BlueGreenUpdatePolicy": {
            "TrafficRoutingConfiguration": {
                "Type": "CANARY",
                "CanarySize": {"Type": "CAPACITY_PERCENT", "Value": 10},
                "WaitIntervalInSeconds": 600,  # bake the canary for 10 minutes
            },
            "TerminationWaitInSeconds": 600,
            "MaximumExecutionTimeoutInSeconds": 3600,
        },
        "AutoRollbackConfiguration": {
            "Alarms": [{"AlarmName": "churn-5xx-rate"}, {"AlarmName": "churn-p99-latency"}]},
    },
)
  • Inference components use rolling updates with batch sizes in copies (COPY_COUNT) or capacity percent.
  • Lambda and ECS model servers use CodeDeploy configurations such as LambdaCanary10Percent5Minutes or ECSLinear10PercentEvery1Minutes, with automatic rollback on alarms.
  • Generative AI resources roll back by moving a pointer: a Bedrock Flows alias to an earlier flow version, an AgentCore endpoint to an earlier runtime version, an application setting to an earlier prompt version. These aliases route to exactly one version, with no weighted traffic split.

CodePipeline has no SageMaker deploy action and CodeDeploy doesn't deploy SageMaker endpoints. Canary and linear rollouts of an endpoint come from the endpoint's own DeploymentConfig, triggered from CodeBuild, CloudFormation, Lambda or Step Functions.

AWS developer tools

Skill 3.3.2Configure and troubleshoot AWS CodeBuild, AWS CodeCommit, AWS CodeDeploy, AWS CodePipeline, and AWS CodeConnections.

  • AWS CodeConnections links GitHub, GitLab, Bitbucket, Azure DevOps and self-managed GitHub Enterprise or GitLab. A connection created from the CLI or CloudFormation stays PENDING until someone completes the handshake in the console: a classic "the pipeline never starts" cause.
  • AWS CodeCommit: managed Git repositories in your account, available to new customers again.
  • AWS CodePipeline V2 pipelines add triggers filtered by branch, file path or Git tag (connection sources only), pipeline-level variables, execution modes (SUPERSEDED by default, QUEUED, PARALLEL), stage conditions (before entry, on success, on failure) with rules such as a CloudWatch alarm, a Lambda check or a deployment window, and stage rollback to an earlier successful execution. Billing is per action-execution minute.
  • AWS CodeBuild runs tests and builds from a buildspec.yml (version 0.2, phases install, pre_build, build, post_build), with secrets from Parameter Store or Secrets Manager, test reports, caching, and GPU build environments.
  • AWS CodeDeploy shifts traffic for EC2, Lambda and ECS deployments, with canary, linear or all-at-once configurations and rollback on alarms.
A release pipeline triggered by release tags, with an alarm gate before production (JSON, part of the CodePipeline V2 definition) 
{
  "triggers": [{"providerType": "CodeStarSourceConnection",
    "gitConfiguration": {"sourceActionName": "Source",
      "push": [{"tags": {"includes": ["release-v*"]}}]}}],
  "stages": [{"name": "DeployProduction",
    "beforeEntry": {"conditions": [{"result": "FAIL", "rules": [{
      "name": "StagingHealthy",
      "ruleTypeId": {"category": "Rule", "owner": "AWS", "provider": "CloudWatchAlarm", "version": "1"},
      "configuration": {"AlarmName": "churn-staging-5xx", "WaitTime": "5"}}]}]},
    "onFailure": {"result": "ROLLBACK"},
    "actions": []}]
}

Common failures to troubleshoot:

  • "Cannot connect to the Docker daemon" means CodeBuild's privileged mode is off.
  • Access denied pulling a build image from another account means it needs SERVICE_ROLE image pull credentials and a repository policy.
  • A pipeline that never starts means a pending connection, or a trigger filter that excludes the change.
  • A stage rollback that isn't allowed means it was the Source stage, or the pipeline runs in PARALLEL mode.

Training and inference jobs in pipelines

Skill 3.3.3Configure training and inference jobs.

SageMaker Pipelines describes the workflow as steps whose outputs feed each other:

  • ProcessingStep (preparation, evaluation), TrainingStep, TuningStep, ModelStep (create or register a model), TransformStep (batch inference), ConditionStep and FailStep, plus Lambda, callback, EMR and endpoint steps.
  • Parameters (ParameterString, ParameterFloat and others, up to 200) let each run use new data, thresholds or instance types without editing the pipeline.
  • Step caching (CacheConfig with an expiry) skips a step whose inputs haven't changed; retry policies handle capacity errors; selective execution reruns only some steps.
  • Training and inference jobs themselves are configured as in Task 2.2 and Task 3.1: image, instance type, input channels, hyperparameters, stopping condition, Spot and checkpoints, VPC settings.
The quality gate at the end of the churn training pipeline (Python, SageMaker Python SDK v3) 
from sagemaker.core.workflow.conditions import ConditionGreaterThanOrEqualTo
from sagemaker.core.workflow.functions import JsonGet
from sagemaker.core.workflow.parameters import ParameterFloat
from sagemaker.mlops.workflow.condition_step import ConditionStep
from sagemaker.mlops.workflow.fail_step import FailStep

min_auc = ParameterFloat(name="MinAuc", default_value=0.80)

check_auc = ConditionStep(
    name="CheckAuc",
    conditions=[ConditionGreaterThanOrEqualTo(
        # evaluation.json written by the Evaluate ProcessingStep (a PropertyFile)
        left=JsonGet(step_name=step_eval.name, property_file=eval_report,
                     json_path="classification_metrics.auc.value"),
        right=min_auc)],
    if_steps=[step_register],  # ModelStep: register as PendingManualApproval
    else_steps=[FailStep(name="AucTooLow", error_message="AUC below the release threshold")],
)

Automated testing

Skill 3.3.4Configure automated testing strategies within CI/CD pipelines for traditional ML and AI workloads.

The Well-Architected ML Lens asks for automated tests of both code quality and model performance, with approval gates before production. The layers, from cheapest to most realistic:

  1. Unit tests of feature and preprocessing code in CodeBuild on every commit.
  2. Data validation: schema, ranges and missing values checked in a processing step (or with Glue Data Quality, Task 1.3); fail the pipeline on bad data.
  3. Model quality gate: a ConditionStep that compares the evaluation metrics with a threshold, or with the current approved model's metrics (look it up with list_model_packages filtered on Approved).
  4. Integration and smoke tests against a staging endpoint: it is InService, answers a known request correctly, captures data.
  5. Load tests with Inference Recommender's advanced (load test) jobs.
  6. Shadow tests with live traffic, then a canary with alarms in production.
Unit tests with a test report in CodeBuild (YAML, buildspec.yml) 
version: 0.2
phases:
  install:
    runtime-versions:
      python: 3.12
    commands:
      - pip install -r requirements-dev.txt
  build:
    commands:
      - pytest tests/unit --junitxml=reports/unit.xml
      - python tests/check_data_contract.py --sample s3://retail-ml-111111111111/churn/sample.csv
reports:
  churn-unit-tests:
    files:
      - unit.xml
    base-directory: reports
    file-format: JUNITXML

A failing command fails the build and stops the pipeline. Test reports are kept 30 days unless exported to S3. Generative AI tests are in Skill 3.3.9.

Retraining

Skill 3.3.5Build and integrate mechanisms to re-train models.

The ML Lens lists four triggers: a schedule, performance degradation, data drift and new training data. It calls retraining on a fixed schedule regardless of performance an anti-pattern, and its sustainability pillar says to retrain only when KPIs fall.

  • Schedule: an EventBridge Scheduler schedule (or PipelineSchedule in the SDK) starts the pipeline.
  • Drift or quality alarm: a CloudWatch alarm on your drift or accuracy metric (Task 2.3) emits "CloudWatch Alarm State Change"; an EventBridge rule on ALARM targets the pipeline.
  • New data: turn on S3 EventBridge notifications for the bucket, then match "Object Created" events under the data prefix.
Start the training pipeline with the new file's location (JSON, EventBridge rule target) 
{
  "Id": "retrain-churn",
  "Arn": "arn:aws:sagemaker:us-east-1:111111111111:pipeline/churn-train",
  "RoleArn": "arn:aws:iam::111111111111:role/EventBridgeStartPipelineRole",
  "SageMakerPipelineParameters": {"PipelineParameterList": [
    {"Name": "InputBucket", "Value": "$.detail.bucket.name"},
    {"Name": "InputKey", "Value": "$.detail.object.key"}
  ]}
}
  • Train on old and new data, validate against a holdout before deployment, and register each version with its data and metrics.
  • Warm starts: incremental training (a model input channel holding the previous artifact) works for only three built-in algorithms: image classification, object detection and semantic segmentation. Checkpoints (including XGBoost's) resume an interrupted job, which is different.

EventBridge pipeline parameter names allow only letters, digits and hyphens (no underscores), and a JSON path must be the whole value, so pass the bucket and key separately and join them inside the pipeline. Once S3 EventBridge notifications are on, every event type is sent; filter on "Object Created" and the prefix, or tag changes will start retraining.

Model versions

Skill 3.3.6Manage model versions for repeatability and audits (for example, SageMaker Model Registry, MLflow on SageMaker AI).

  • SageMaker Model Registry: a model package group per use case holds numbered model packages (versions), each with its image, artifacts, metrics, source commit, custom metadata, model card and approval status: PendingManualApproval, Approved or Rejected.
  • Lifecycle stages (Development, QA, PreProduction, Production, Archived, with statuses) describe where a version is; only Approved lets it deploy. IAM condition keys on the stage and approval status control who may promote.
  • Approval drives deployment: the "SageMaker Model Package State Change" event (filter on ModelApprovalStatus; it can repeat) starts the deploy pipeline. In the SageMaker Projects template, rejecting the current version redeploys the previous approved one.
  • MLflow on SageMaker AI tracks runs and registers models; with automatic registration turned on, MLflow versions are synced into the Model Registry with their lineage.
  • Audit trail: lineage tracking (data, job, model, endpoint), model cards (exportable as PDF), CreatedBy and LastModifiedBy on each package, and CloudTrail for every registry call. Share groups across accounts with AWS RAM.
Approve the new version, and find the version currently in production (Python, boto3) 
import boto3

sm = boto3.client("sagemaker")
sm.update_model_package(
    ModelPackageArn="arn:aws:sagemaker:us-east-1:111111111111:model-package/churn-models/14",
    ModelApprovalStatus="Approved",
    ApprovalDescription="AUC 0.86 vs 0.84 in production; shadow test passed",
)

latest = sm.list_model_packages(
    ModelPackageGroupName="churn-models",
    ModelApprovalStatus="Approved",
    SortBy="CreationTime",
    SortOrder="Descending",
    MaxResults=1,
)["ModelPackageSummaryList"][0]
print(latest["ModelPackageArn"])

Managing prompts

Skill 3.3.7Manage prompts (for example, Amazon Bedrock Prompt Management).

  • Prompts are code: store them in Bedrock Prompt Management with {{variables}}, model and inference settings; edit the draft, and snapshot an immutable version (prompt/ID:N) to release. A prompt keeps at most 10 versions, so delete old ones.
  • Applications pin a version ARN (from an SSM parameter or environment variable), so a prompt change is a deployment that can be tested and rolled back by changing that setting.
  • As code: AWS::Bedrock::Prompt and AWS::Bedrock::PromptVersion in CloudFormation; Ref on the prompt gives the unversioned ARN, on the version the :N ARN the application should use.
  • Flows use versions and aliases; AgentCore has versioned configuration bundles for an agent's prompt, model and settings.
Release a prompt version and call it (Python, boto3) 
import boto3

agent = boto3.client("bedrock-agent", region_name="us-east-1")
version = agent.create_prompt_version(
    promptIdentifier="PROMPT1234",
    description="Shorter refund answers; tested on golden set 2026-11-10",
)
version_arn = version["arn"]  # ...:prompt/PROMPT1234:7; store it in SSM for the app

runtime = boto3.client("bedrock-runtime", region_name="us-east-1")
resp = runtime.converse(
    modelId=version_arn,  # the prompt version supplies the model and settings
    promptVariables={"question": {"text": "Can I return a sale item?"}},
)

Agent deployment pipelines

Skill 3.3.8Implement automated agent deployment pipelines and agent version management.

AgentCore Runtime versions every change: each UpdateAgentRuntime (even an environment variable) creates a new immutable version. Endpoints point at versions: the DEFAULT endpoint always follows the latest version, while named endpoints (stage, prod) stay pinned until moved. A pipeline built from these pieces:

  1. Build the ARM64 container, scan it, push it to ECR with a commit-specific tag.
  2. UpdateAgentRuntime with the new image: version N appears on DEFAULT.
  3. Run agent tests (AgentCore Evaluations, trajectory checks) against DEFAULT.
  4. Move stage to version N, test again, approve, move prod.
  5. Roll back by moving prod to the previous version, with no downtime.
Deploy a new agent version and promote it (Python, boto3) 
import boto3

ctl = boto3.client("bedrock-agentcore-control", region_name="us-east-1")
updated = ctl.update_agent_runtime(
    agentRuntimeId="support_agent-a1b2c3d4e5",
    agentRuntimeArtifact={"containerConfiguration": {
        "containerUri": "111111111111.dkr.ecr.us-east-1.amazonaws.com/support-agent:9f3c2ab"}},
    roleArn="arn:aws:iam::111111111111:role/AgentRuntimeRole",
    networkConfiguration={"networkMode": "PUBLIC"},
)
new_version = updated["agentRuntimeVersion"]

# After tests on DEFAULT pass and the release is approved:
ctl.update_agent_runtime_endpoint(
    agentRuntimeId="support_agent-a1b2c3d4e5",
    endpointName="prod",
    agentRuntimeVersion=new_version,
)

Production traffic must call a named endpoint: anything calling DEFAULT gets every new version immediately, before it is tested. UpdateAgentRuntime needs the artifact and role on every call. Agents Classic (versions and aliases) is closed to new customers, so new pipelines target AgentCore.

AI and prompt testing

Skill 3.3.9Implement AI model testing frameworks, including prompt testing.

  • A golden dataset (the Generative AI Lens calls it ground truth): prompts with acceptable answers, grouped by variations of the same request, kept as a living artifact in S3. Every new prompt version, model or knowledge base is tested against it.
  • Baseline and compare: record the current version's scores, and fail the release if the new one scores lower. Bedrock evaluation jobs (automatic metrics or an LLM judge, same judge and temperature 0 each time) produce the scores; there is no built-in pass or fail, so a CI step reads the results and compares them with thresholds.
  • Agents: AgentCore Evaluations with expected responses, assertions and expected tool trajectories (trajectory matching is deterministic and uses no model tokens).
  • Libraries in CodeBuild: fmeval for QA accuracy, ROUGE and toxicity (Task 2.3).
  • Safety tests: run a list of attack and off-topic prompts through the guardrail version under test with ApplyGuardrail, in detect mode first to measure false positives; guardrail changes reach the application only when it uses the new guardrail version.
A release gate on evaluation scores (Python, CI step) 
import json
import sys

baseline = json.load(open("baseline_scores.json"))  # scores of the prompt version in production
candidate = json.load(open("candidate_scores.json"))  # parsed from the evaluation job output

failures = [m for m, base in baseline.items() if candidate[m] < base - 0.02]
if failures:
    print("Regression in:", ", ".join(failures))
    sys.exit(1)  # fails the CodeBuild step and stops the pipeline
print("Candidate meets the baseline")

Fine-tuned model deployment

Skill 3.3.10Configure FM deployment automation with fine-tuned model versioning.

  • Bedrock: each customization job produces a new custom model (its ARN is the version; tag it with the job and dataset). Serving then moves to it:
    • On-demand custom model deployment: UpdateCustomModelDeployment points an existing deployment at a new custom model, keeping the same deployment ARN for callers.
    • Provisioned Throughput: UpdateProvisionedModelThroughput with desiredModelId swaps to another custom model from the same base model while serving continues (some responses may still come from the old model during the switch).
  • SageMaker AI: register fine-tuned models in the Model Registry (packages record the base model they came from), then roll them out with endpoint deployment guardrails or UpdateInferenceComponent with a rolling policy. LoRA adapters can be separate inference components on a shared base model, so a new adapter version deploys without reloading the base.
  • Pipeline: customization job, evaluation against the golden set, registration or tagging, approval, then the pointer update; roll back by pointing back to the previous model.
Point the support model deployment at the newly approved fine-tune (Python, boto3) 
import boto3

bedrock = boto3.client("bedrock", region_name="us-east-1")
bedrock.update_custom_model_deployment(
    customModelDeploymentIdentifier="arn:aws:bedrock:us-east-1:111111111111:custom-model-deployment/support-tone",
    modelArn="arn:aws:bedrock:us-east-1:111111111111:custom-model/amazon.nova-lite-v1:0:300k/support-tone-v4",
)
# Callers keep using the deployment ARN; check get_custom_model_deployment for the update status

RAG and knowledge base refresh

Skill 3.3.11Configure AI-specific pipeline orchestration for RAG system updates and knowledge base refresh cycles.

  • Content refresh: schedule or trigger StartIngestionJob for customer-managed knowledge bases (managed ones have their own sync schedule); only one job runs per knowledge base at a time, and jobs emit no EventBridge events, so a Step Functions workflow polls GetIngestionJob. AWS's sync blog queues S3 changes (S3, EventBridge, SQS, Step Functions) to respect ingestion limits (Task 3.2 has a Lambda trigger).
  • After each refresh: run the RAG evaluation set (context relevance and coverage, faithfulness, citations) and alarm on drops.
  • Structural changes (a new embedding model, dimensions, chunking strategy or vector store) can't be applied to an existing knowledge base: build a new one alongside, ingest, evaluate both on the same set, then switch the application's knowledge base ID (a blue/green re-index), keeping the old one for rollback until the new one is proven.
  • Prompts and models used by the RAG application follow the prompt and model pipelines above.

Key takeaways

  • Rollouts: SageMaker blue/green (all at once, canary, linear) or rolling, with CloudWatch alarm rollback; CodeDeploy for Lambda and ECS; GenAI rollback by moving an alias, endpoint or version pointer.
  • Tools: CodeConnections (complete pending connections in the console), CodeCommit (GA again), CodePipeline V2 triggers, variables, conditions and stage rollback, CodeBuild buildspec and reports; no SageMaker action in CodePipeline.
  • Pipelines: processing, training, model, transform, condition and fail steps; parameters, caching and retries.
  • Testing: unit, data validation, quality gate against a threshold or the champion, staging smoke tests, load tests, shadow, canary.
  • Retraining: on drift, degradation or new data rather than blindly on a schedule; EventBridge targets the pipeline with parameters (no underscores); incremental training only for three image algorithms.
  • Versions: Model Registry groups, packages, approval status (only Approved deploys), lifecycle stages, lineage, model cards, CloudTrail; MLflow synced into the registry.
  • Prompts and agents: immutable prompt versions pinned by ARN (10 per prompt); AgentCore versions every update, DEFAULT follows the latest, named endpoints for promotion and rollback.
  • GenAI testing: golden dataset, baseline scores, evaluation jobs with a fixed judge, CI threshold checks, guardrail tests with ApplyGuardrail.
  • Fine-tunes and RAG: update custom model deployments or Provisioned Throughput in place; refresh knowledge bases on a schedule with evaluation after; rebuild alongside for embedding or chunking changes.
