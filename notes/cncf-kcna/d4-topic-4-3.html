How the CNCF is governed

Topic 4.3Telling apart the CNCF bodies that handle business, technical and end-user matters.

The CNCF's mission is "to make cloud native computing ubiquitous", through "an ecosystem of open source, vendor-neutral projects". As a Linux Foundation project, it has three main bodies:

BodyRoleMake-up
Governing Board (GB)"Marketing and other business oversight and budget decisions"; it "does not make technical decisions"Member representatives, plus the TOC chair, the End User TAB chair and two elected project committers
Technical Oversight Committee (TOC)"The technical governing body of the CNCF. It admits and oversees all projects"11 members on staggered two-year terms: 6 elected by the GB, 2 by end users, 1 by project maintainers, 2 by the TOC
End User Technical Advisory Board (TAB)"The voice of End Users in the CNCF community"; its recommendations are "advisory only"Seven or more representatives of end-user members

Members join as Platinum, Gold, Silver, End User, Academic or Non-Profit participants. End User members are companies that use cloud native technology internally but do not sell cloud native services.

Groups that do the technical work

  • Technical Advisory Groups (TAGs) "are the primary organizational units within the CNCF that oversee and coordinate interests across projects, working groups, and the broader cloud native community." Since the 2025 restructure there are five: Developer Experience, Infrastructure, Operational Resilience, Security and Compliance, and Workloads Foundation.
  • Technical Community Groups (TCGs) are "lightweight, topic or domain-focused groups that serve as rallying points": currently Artificial Intelligence, Environmental Sustainability, Platform Engineering and Software Supply Chain Security.
  • TOC subprojects, such as Contributor Strategy and Advocacy, and Mentoring.

The old TAGs are archived. Older material lists TAG Security, Storage, App Delivery, Network, Runtime, Observability, Contributor Strategy and Environmental Sustainability. All were replaced in 2025 by the five TAGs, the TCGs and TOC subprojects; for example, contributor strategy moved to a TOC subproject.

Vendor neutrality is built in: "No single vendor can control the direction of CNCF projects or groups". The TOC may have at most two members from one group of related companies, and its principles include "No kingmakers": competing projects are not excluded for overlapping.

How Kubernetes is governed

Topic 4.3Knowing which Kubernetes group owns what, and how decisions are made.

Kubernetes governance follows the principles of being open, welcoming, transparent ("Work and collaboration should be done in public") and merit-based.

GroupWhat it isExamples
Steering Committee"The governing body of the Kubernetes project", for bylaws, structure and finances; "all technical responsibilities should be delegated to SIGs". Seven elected members, at most one-third from one companyDecides escalations "in the case of extended debate or deadlock"
Special Interest Groups (SIGs)Members "from multiple companies and organizations, with a common purpose of advancing the project with respect to a specific topic"; every part of the project "is intended to be owned by some SIG"24 SIGs, such as Network, Node, Storage, CLI, Docs, Release, Security
Subprojects"Specific work efforts within SIGs"; "every part of the Kubernetes code and documentation must be owned by some subproject"kubeadm and minikube in SIG Cluster Lifecycle
Working Groups (WGs)For topics "that cross SIG lines"; temporary, own no code, and have "only influence"Batch, Device Management, AI Gateway
CommitteesFor topics needing discretion; "Committees do not have open membership"Steering, Code of Conduct, Security Response

Each SIG has a charter, chairs who organize it, and tech leads who resolve technical issues and approve its enhancement proposals. The kubectl bug from the running example belongs to SIG CLI.

Four governing bodies that are easy to confuse. The CNCF Governing Board handles business; the CNCF TOC oversees all CNCF projects technically; the Kubernetes Steering Committee governs only Kubernetes; and Kubernetes SIGs make its technical decisions. Similarly, a CNCF TAG spans many projects, while a Kubernetes SIG works inside one.

Contributing

Topic 4.3Making a first contribution and understanding how contributors earn more responsibility.

The Kubernetes community states five values: "Distribution is better than centralization", "Community over product or company", "Automation over process", "Inclusive is better than exclusive" and "Evolution is better than stagnation". "Individuals gain status through work."

A first pull request

  1. Find an issueIssues labelled good first issue are ones where "Kubernetes Members have committed to providing extra assistance for new contributors".
  2. Sign the CLA"All contributors must sign the CNCF CLA"; after the first pull request, the EasyCLA bot links to it.
  3. ReviewA reviewer listed in the code's OWNERS file comments /lgtm (looks good to me); the Prow bot adds the lgtm label.
  4. ApproveAn approver comments /approve to accept the change as a whole.
  5. Merge"Automation merges the PR": the Tide component merges it once labels and tests pass.

You do not need to be a member to contribute. Anyone can open issues and pull requests and review code; membership mainly gives conveniences such as automatic test runs. Also, Kubernetes requires a CLA, but the CNCF lets each project choose; many CNCF projects use only a DCO sign-off on each commit.

The contributor ladder

RoleResponsibilityRequirements (summarized)
Member"Active contributor in the community"Several contributions, including at least one merged PR; "sponsored by 2 reviewers" from different companies
Reviewer"Review contributions from other members"Member for 3 months; primary reviewer on 5 PRs; 20 substantial PRs reviewed or merged; listed as a reviewer in OWNERS
Approver"Contributions acceptance approval"Reviewer for 3 months; primary reviewer on 10 substantial PRs; 30 PRs reviewed or merged; listed as an approver in OWNERS
Subproject owner"Set direction and priorities for a subproject"Demonstrated responsibility and technical judgement

Members inactive for 12 months are removed, measured with the CNCF's DevStats. Contributions need not be code: the community lists documentation, translation (localized docs use ISO 639-1 language codes), issue triage, answering questions, events, design, blogging and release team roles.

Enhancements and releases

Topic 4.3Following a new feature from proposal through the release cycle to general availability.

"A Kubernetes Enhancement Proposal (KEP) is a way to propose, communicate and coordinate on new efforts for the Kubernetes project", inspired by "IETF RFCs, Python PEPs and Rust RFCs". KEPs "are required for most non-trivial changes": most new features, major changes and anything controversial. Small fixes like the kubectl bug need only a pull request.

KEP statusMeaning (KEP process)
provisional"Proposed and is actively being defined"
implementable"The approvers have approved this KEP for implementation"
implemented"Implemented and is no longer actively changed"
deferred, rejected, withdrawn, replacedPaused, declined, withdrawn by its authors, or superseded by a new KEP

A KEP also tracks the feature's stage, alpha → beta → stable, release by release (the feature gates of topic 1.2). Before a stage is accepted, a separate team carries out a Production Readiness Review, ensuring features "are observable, scalable and supportable, can be safely operated in production environments, and can be disabled or rolled back"; it has been blocking since v1.21.

The release cycle

"Kubernetes releases currently happen approximately three times per year", each cycle run by a Release Team "embedded within SIG Release". For v1.38:

  1. Week 1 (August 31, 2026)The cycle starts; SIGs opt their KEPs in.
  2. Weeks 4–5KEP Readiness Deadline (formerly "PRR Freeze"), then Enhancements Freeze: no new KEPs join the release.
  3. Week 12Code Freeze for about two weeks: only fixes for the release.
  4. Week 14Docs Freeze.
  5. Week 16 (December 16, 2026)v1.38.0 released. Patch releases then follow roughly monthly for about 14 months.

Release Team roles today are Release Team Lead, Enhancements, Release Signal, Docs and Communications (with a Branch Manager). Each lead takes on shadows, newcomers chosen through a questionnaire, and "successful Release Team Shadows should be prepared to assume a lead role in a subsequent release": one of the main ways new contributors get involved.

Conduct and communication

Topic 4.3Knowing the behaviour the community expects, how to report problems, and where conversations happen.

"Kubernetes follows the CNCF Code of Conduct", now version 1.3 and adapted from the Contributor Covenant 2.0. It states that "the CNCF Community is open, inclusive and respectful." Reports for Kubernetes go to the Code of Conduct Committee at conduct@kubernetes.io ("Please do not make reports via our public slack channel"); for other CNCF projects, to conduct@cncf.io. Security vulnerabilities go privately to the Security Response Committee (topic 2.2).

ChannelUsed for
Kubernetes Slack (slack.k8s.io)Day-to-day chat, "spread across 250+ channels", including one per SIG
dev@kubernetes.io mailing list"All upstream Kubernetes news and discussion"; joining is required for org membership
kubernetes-announce list"Major project announcements such as releases and security issues"
discuss.kubernetes.ioA forum "where Kubernetes users trade notes"
GitHubIssues, pull requests and KEPs: where decisions are recorded

Roles and personas

Topic 4.3Recognizing the main roles people play around cloud native systems.

There is no single official CNCF list of personas; this table combines the Kubernetes glossary's roles with the CNCF Glossary's disciplines.

RoleDefinition
Application developer"A person who writes an application that runs in a Kubernetes cluster" (Kubernetes glossary)
Cluster operator"A person who configures, controls, and monitors clusters"; not to be confused with the Operator pattern
Cluster architect"A person who designs infrastructure that involves one or more Kubernetes clusters"
Platform developer"A person who customizes the Kubernetes platform to fit the needs of their project", for example with custom resources
Platform engineerPractises platform engineering, "the art of building tools and processes that empower software developers" (CNCF Glossary)
Site reliability engineerSRE "combines operations and software engineering" and "ensures that code running in production works properly"
DevOpsA methodology "in which teams own the entire process from application development to production operations"
Contributor"Someone who donates code, documentation, or their time to help the Kubernetes project or community"

Security engineers and data or ML engineers are also common roles in cloud native teams, but neither glossary defines them.

Events, programs and certifications

Topic 4.3Knowing how the community meets, mentors newcomers and recognizes skills.

  • KubeCon + CloudNativeCon is the CNCF's flagship conference. In 2026 it ran in five regions: Europe (Amsterdam), India (Mumbai), Japan (Yokohama), China (Shanghai) and North America (Salt Lake City, November 9–12).
  • Kubernetes Community Days (KCDs) are regional, community-organized events supported by the CNCF.
  • CNCF Ambassadors are community leaders who promote cloud native through mentoring, speaking and content.
  • Mentoring: "Participation in the CNCF Mentoring Program is open to anyone", through LFX Mentorship, Google Summer of Code and Outreachy.

Certifications and Kubestronaut

The CNCF offers 15 certifications: the Kubernetes ones (KCNA, KCSA, CKA, CKAD, CKS) and project or practice ones such as PCA (Prometheus), ICA (Istio), CCA (Cilium), CAPA (Argo), CGOA (GitOps), CBA (Backstage), OTCA (OpenTelemetry), KCA (Kyverno), CNPA and CNPE (platform engineering).

TitleRequirement
KubestronautPass "every CNCF Kubernetes certification - currently CKA, CKAD, CKS, KCNA, KCSA"
Golden KubestronautPass every CNCF certification plus the Linux Foundation's LFCS; the title is "for life"

The certificates must be current. "All certifications must not have expired to be recognized as a Kubestronaut or a Golden Kubestronaut." KCNA is valid for two years, so passing it early in a plan to become a Kubestronaut means watching its expiry date.

Key takeaways

  • CNCF (a Linux Foundation project): Governing Board = business and budget, no technical decisions; TOC = 11-member technical body that admits and oversees projects; End User TAB = advisory voice of users. Five TAGs since 2025, plus TCGs and TOC subprojects. Vendor neutral.
  • Kubernetes: Steering Committee (7, governance, delegates technical work); SIGs (24, own the code through subprojects); WGs (temporary, cross-SIG, own no code); Committees (closed: Steering, Code of Conduct, Security Response).
  • Values: distribution, community over company, automation, inclusiveness, evolution. Anyone can contribute; sign the CNCF CLA; reviewers /lgtm, approvers /approve, Prow and Tide merge. Ladder: member (2 sponsors) → reviewer → approver → subproject owner.
  • KEPs for non-trivial changes (provisional → implementable → implemented); features go alpha → beta → stable with a Production Readiness Review. About three releases a year: Enhancements Freeze, Code Freeze, release around week 16; shadows train new release team members.
  • CNCF Code of Conduct v1.3; report Kubernetes issues to conduct@kubernetes.io. Talk on Slack, dev@kubernetes.io, GitHub and recorded Zoom meetings.
  • Roles: application developer, cluster operator, cluster architect, platform developer and engineer, SRE, DevOps, contributor.
  • KubeCon (five regions in 2026), KCDs, Ambassadors, mentoring. Kubestronaut = CKA, CKAD, CKS, KCNA and KCSA, all unexpired; Golden = all 15 CNCF certifications plus LFCS.
