Overview

Topic 2.2

Security.

This page takes the topic to cover the security model Kubernetes now teaches, the three gates every API request passes (authentication, authorization with RBAC, admission), Pod security, protecting Secrets and identities, and auditing and the supply chain. Earlier pages introduced pieces: the request stages in 1.2, container hardening in 1.4, and NetworkPolicy in 2.1.

Quotes are from the Kubernetes documentation (© The Kubernetes Authors) and the CNCF Glossary, both CC BY 4.0, for Kubernetes v1.37.

Running example. The web shop's shop namespace: the shop-web Pods run as a ServiceAccount named web that only needs to read Pods, the database password is a Secret, and the platform team wants every Pod in the namespace to meet the strictest Pod security level.

Security across the lifecycle

Topic 2.2Seeing security as a set of controls at every stage, from writing code to running it.

Kubernetes "draws on advice from the CNCF about good practices for cloud native information security". The CNCF's Cloud Native Security Whitepaper (version 2, 2022) describes "four continuous phases; Develop, Distribute, Deploy, and Runtime":

PhaseGoal (kubernetes.io)Examples
Develop"Ensure the integrity of development environments" and design securelyThreat modelling, zero trust design
Distribute"Ensure the security of the supply chain for container images"Image scanning, signing, private registries
Deploy"Ensure appropriate restrictions on what can be deployed, who can deploy it, and where"Admission policies, verifying signatures
RuntimeProtect three areas: "access, compute, and storage"TLS and RBAC for the API, Pod Security Standards, encryption at rest

The "4C's" page is gone. Many courses still teach the 4C's of cloud native security (Cloud, Clusters, Containers, Code). Kubernetes removed that page in 2024 and now organizes its security overview around the whitepaper's four lifecycle phases. The CNCF group behind the whitepaper is now called TAG Security and Compliance.

Three ideas recur. Shift left is "implementing tests, security, or other development practices early in the software development lifecycle rather than towards the end". Zero trust follows "never trust, always verify". And defense in depth layers independent controls, so that one failure does not expose everything.

Authentication

Topic 2.2Knowing how people and workloads prove who they are to the API server.

"All Kubernetes clusters have two categories of users: service accounts managed by Kubernetes, and normal users."

Normal usersServiceAccounts
ForPeopleWorkloads and automation
StoredOutside Kubernetes: "Kubernetes does not have objects which represent normal user accounts"As API objects, "bound to specific namespaces"
Proves identity withX.509 client certificates (the username is the certificate's CN), OIDC tokens from an external identity provider, or an authenticating proxyShort-lived tokens issued by the API server

A ServiceAccount authenticates as system:serviceaccount:<namespace>:<name>. "Every namespace gets a default ServiceAccount upon creation," and a Pod uses it unless it names another. Since v1.22 the Pod receives "a short-lived, automatically rotating token" (one hour by default) mounted as a projected volume. Requests with no credentials become system:anonymous; an invalid token gets "401 Unauthorized".

ServiceAccount settings in a Pod 
spec:
  serviceAccountName: web
  # don't mount a token the app
  # never uses
  automountServiceAccountToken: false

Tokens are mounted by default. "By default, Kubernetes provides the Pod with the credentials for an assigned ServiceAccount". An app that never calls the API should set automountServiceAccountToken: false. Long-lived Secret-based tokens are no longer created automatically (since v1.24), and unused legacy ones are invalidated after a year and later deleted.

Check identities 
# who am I to this cluster?
kubectl auth whoami

# issue a short-lived token for web
kubectl create token web -n shop

Authorization and RBAC

Topic 2.2Granting exactly the permissions each user and workload needs, using Roles and bindings.

"All parts of an API request must be allowed by some authorization mechanism in order to proceed. In other words: access is denied by default." A denied request gets HTTP 403. The API server can chain several authorizers (typically Node, for kubelets, then RBAC); Webhook and ABAC also exist, and AlwaysAllow "brings security risks".

Role-based access control uses four objects:

ObjectScopeContains
RoleOne namespaceRules: which verbs on which resources in which apiGroups
ClusterRoleCluster-wide ("a non-namespaced resource")The same rules, also for cluster-scoped resources such as nodes
RoleBindingOne namespaceSubjects (users, groups, ServiceAccounts) plus a reference to a Role or ClusterRole
ClusterRoleBindingWhole clusterSubjects plus a ClusterRole, granted everywhere
Let the web ServiceAccount read Pods in shop 
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: shop
rules:
- apiGroups: [""]   # core group
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: shop
subjects:
- kind: ServiceAccount
  name: web
  namespace: shop
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
The same with kubectl, then test it 
kubectl create role pod-reader \
  --verb=get,list,watch \
  --resource=pods -n shop
kubectl create rolebinding read-pods \
  --role=pod-reader \
  --serviceaccount=shop:web -n shop

# ask as the ServiceAccount
kubectl auth can-i list pods -n shop \
  --as=system:serviceaccount:shop:web

Four RBAC traps. First, "permissions are purely additive (there are no 'deny' rules)": you remove access by removing grants. Second, "a RoleBinding can reference a ClusterRole and bind that ClusterRole to the namespace of the RoleBinding", which is how a shared role is reused per namespace. Third, a binding's roleRef cannot be changed; delete and recreate it. Fourth, list and watch on Secrets "effectively allow for users to reveal the Secret contents", just like get.

Default roles and good practice

ClusterRoleAllows
cluster-admin"Super-user access to perform any action on any resource"
adminFull control within a namespace, including Roles and RoleBindings, but not quotas or the namespace itself
editRead and write most objects; cannot view Roles, but can access Secrets and run Pods as any ServiceAccount
viewRead-only for most objects; "does not allow viewing Secrets"
  • Give "minimal RBAC rights"; prefer RoleBindings to ClusterRoleBindings.
  • Avoid wildcards, which cover "all object types which are created in the future" too.
  • Avoid the system:masters group: its members bypass RBAC entirely, and that "cannot be revoked by removing RoleBindings". Use it only as break-glass access.
  • Remember that permission to create Pods in a namespace implicitly grants access to the Secrets and ServiceAccounts there.

Admission control

Topic 2.2Enforcing rules about what objects may look like, after a request is authorized but before it is stored.

"An admission controller is a piece of code that intercepts requests to the Kubernetes API server prior to persistence of the resource, but after the request is authenticated and authorized." It runs in two phases: mutating controllers may change the object (for example adding defaults), then validating controllers accept or reject it. If any rejects, "the entire request is rejected immediately".

  • Built-in plugins enabled by default include NamespaceLifecycle, LimitRanger, ServiceAccount, ResourceQuota, PodSecurity and DefaultStorageClass.
  • ValidatingAdmissionPolicy (stable since v1.30) and MutatingAdmissionPolicy (stable since v1.36) let you write rules in the Common Expression Language (CEL) as API objects, with no external service. For example, a ValidatingAdmissionPolicy with the expression object.spec.replicas <= 5, plus a binding that applies it, rejects Deployments with more than five replicas.
  • Admission webhooks call an external HTTP service to mutate or validate.

Admission never sees reads. Admission controllers "do not (and cannot) block requests to read (get, watch or list) objects". Controlling who may read is RBAC's job.

Policy engineApproachCNCF status
OPA GatekeeperAdmission webhook enforcing policies written in Rego, the Open Policy Agent languageOPA graduated (2021)
KyvernoKubernetes-native policies in YAML: validate, mutate, generate, and verify image signaturesGraduated (March 2026)
KubewardenAnother admission policy engine; listed by kubernetes.io, with the two above, as an alternative to the built-in Pod Security admissionSandbox

These are examples of policy as code: "storing the definition of policies as one or more files in machine-readable and processable form".

Pod Security Standards

Topic 2.2Choosing how strict Pod security should be in each namespace, and turning it on with labels.

"The Pod Security Standards define three different policies to broadly cover the security spectrum. These policies are cumulative and range from highly-permissive to highly-restrictive."

LevelMeaningIntended for
Privileged"Unrestricted policy ... This policy allows for known privilege escalations."System and infrastructure workloads run by trusted users
Baseline"Minimally restrictive policy which prevents known privilege escalations"; blocks host namespaces, privileged containers, hostPath volumes and moreCommon applications; easy to adopt
Restricted"Heavily restricted policy, following current Pod hardening best practices"Security-critical apps and lower-trust users

Restricted adds to Baseline: runAsNonRoot: true (and not user 0), allowPrivilegeEscalation: false, all capabilities dropped (only NET_BIND_SERVICE may be added back), a seccomp profile of RuntimeDefault or Localhost, and only safe volume types such as ConfigMap, Secret, emptyDir and PersistentVolumeClaim.

Pod Security Admission

The built-in PodSecurity admission controller (stable since v1.25) enforces the standards per namespace, using labels. Each label sets a mode and a level:

ModeEffect of a violation
enforce"Will cause the pod to be rejected"
auditRecorded in the audit log, but allowed
warnA warning shown to the user, but allowed
Enforce Restricted in the shop namespace
Label key
pod-security.kubernetes.io/enforce
Label value
restricted (or baseline, privileged)
Optional version pin
pod-security.kubernetes.io/enforce-version: latest
Command
kubectl label ns shop pod-security.kubernetes.io/enforce=restricted

Two PSA traps. A namespace with no labels is effectively privileged: nothing is enforced. And enforce applies only to Pods, while audit and warn also check workload templates; so a Deployment that violates the policy is created, but its Pods are rejected. Setting warn alongside enforce shows the problem when you apply the Deployment.

PodSecurityPolicy is gone. "PodSecurityPolicy was deprecated in Kubernetes v1.21, and removed from Kubernetes in v1.25." Pod Security Admission, or a policy engine such as Kyverno or Gatekeeper, replaces it.

securityContext

Topic 2.2Setting the user, privileges and kernel restrictions a container runs with.

"A security context defines privilege and access control settings for a Pod or Container." Pod-level settings apply to all containers; container-level settings "override settings made at the Pod level when there is overlap". This container meets the Restricted level:

Restricted-compliant container settings 
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true  # extra
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
  • runAsUser, runAsGroup and the Pod-level fsGroup set the user and group IDs; fsGroup also sets ownership of mounted volumes.
  • allowPrivilegeEscalation "controls whether a process can gain more privileges than its parent process"; if unset, it defaults to true.
  • seccompProfile restricts system calls; appArmorProfile (a field since v1.30, stable in v1.31; previously annotations) and seLinuxOptions apply Linux security modules.
  • readOnlyRootFilesystem is good practice, but Restricted does not require it.

Seccomp is off unless you ask. Without a profile, containers run Unconfined. The kubelet's --seccomp-default flag (stable since v1.27) makes RuntimeDefault the node default, but it must be turned on per node; the Restricted level requires setting a profile explicitly.

Secrets, certificates and identity

Topic 2.2Protecting sensitive data at rest and in transit, and giving workloads verifiable identities.

"By default, Secret objects are stored unencrypted in etcd." Encryption at rest is configured with an EncryptionConfiguration file passed to the API server with --encryption-provider-config. "The first provider in the list is used to encrypt resources written into the storage":

Encrypt Secrets at rest 
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: ["secrets"]
  providers:
  - secretbox:
      keys:
      - name: key1
        secret: <base64 32-byte key>
  - identity: {}   # read old data
ProviderNotes
identityThe default: "does not encrypt stored data"
kms (v2)Envelope encryption with an external key management service; stable since v1.29 and the recommended choice. KMS v1 is deprecated and off by default
secretbox, aesgcmLocal keys; aesgcm keys "must be rotated every 200,000 writes"
aescbc"Not recommended", vulnerable to padding oracle attacks

Beyond encryption: restrict list and watch on Secrets, remember that "a user who can create a Pod that uses a Secret can also see the value of that Secret", and consider external stores through the Secrets Store CSI Driver (a Kubernetes SIG project) or the External Secrets Operator (CNCF Sandbox).

TLS, certificates and workload identity

  • "Kubernetes expects you to configure and use TLS to provide data encryption in transit within the control plane, and between the control plane and its clients." The API server listens on port 6443 by default.
  • cert-manager (CNCF graduated 2024) "adds certificates and certificate issuers as resource types", obtaining and renewing them from sources such as Let's Encrypt.
  • SPIFFE defines standard workload identities, and SPIRE issues them after attesting nodes and workloads; both graduated in CNCF in 2022.
  • New in v1.37: Kubernetes can issue certificates to Pods itself (PodCertificateRequest and ClusterTrustBundle reached GA).
  • A service mesh adds mTLS between services, where "both sides are validated" (topic 2.1).

Auditing, runtime and supply chain

Topic 2.2Recording who did what, spotting attacks while they happen, and trusting only software you can verify.

Audit logging

"Kubernetes auditing provides a security-relevant, chronological set of records documenting the sequence of actions in a cluster", answering questions such as what happened, when, and who started it. Records come from the API server, governed by an audit policy in which "the first matching rule sets the audit level":

LevelLogs
NoneNothing for matching events
MetadataUser, time, resource and verb, but no request or response body
RequestMetadata and the request body
RequestResponseMetadata, request body and response body
audit-policy.yaml (log metadata for all) 
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
- level: Metadata

Auditing is off by default. The policy is passed with --audit-policy-file; "If the flag is omitted, no events are logged."

Runtime threat detection

Falco (CNCF graduated 2024) "is a cloud native runtime security tool for Linux operating systems. It is designed to detect and alert on abnormal behavior and potential security threats in real-time". At its core it watches kernel events "such as syscalls, based on custom rules".

Supply chain

Kubernetes' checklist asks that image references use "sha256 digests (rather than tags)" or that "the provenance of the image is validated by verifying the image's digital signature at deploy time via admission control". Kubernetes has no built-in signature check; admission tools such as Kyverno provide it.

ProjectPurposeHome
Sigstore (cosign)Signing and verifying images and binaries; Kubernetes signs its own releases with itOpenSSF
Notary ProjectSigning and verifying artifactsCNCF incubating
in-toto"A framework to protect supply chain integrity"CNCF graduated (2025)
TUFA secure root of trust for software updates, used by SigstoreCNCF graduated (2019)
SLSALevels of supply chain integrity "from source to service"OpenSSF

Kubernetes publishes SBOMs (software bills of materials, in SPDX format) for its releases. Vulnerabilities are reported privately to the Security Response Committee, which acknowledges reports "within 3 working days"; official CVEs are listed in a feed on kubernetes.io.

Key takeaways

  • Kubernetes follows the CNCF lifecycle: Develop, Distribute, Deploy, Runtime (the 4C's page was removed in 2024). Shift left, zero trust, defense in depth.
  • Every request: authentication (401 on failure) → authorization (403; denied by default) → admission (mutating then validating; never blocks reads).
  • No User object: people come from certificates, OIDC or proxies. ServiceAccounts are namespaced API objects with short-lived, auto-mounted tokens; disable with automountServiceAccountToken: false.
  • RBAC: Role and RoleBinding (namespace), ClusterRole and ClusterRoleBinding (cluster). Additive only, no deny. A RoleBinding can use a ClusterRole within its namespace. kubectl auth can-i ... --as= tests access. Avoid wildcards, cluster-admin and system:masters; list on Secrets reveals them.
  • ValidatingAdmissionPolicy (v1.30) and MutatingAdmissionPolicy (v1.36) use CEL; Gatekeeper (OPA, Rego) and Kyverno (YAML) are policy engines.
  • Pod Security Standards: Privileged, Baseline, Restricted, applied by namespace labels in enforce, audit or warn mode. Unlabelled = privileged. PSP removed in v1.25.
  • securityContext: non-root, no privilege escalation, drop ALL capabilities, RuntimeDefault seccomp (otherwise Unconfined), optional read-only root filesystem.
  • Secrets are unencrypted in etcd by default; use an EncryptionConfiguration, ideally KMS v2. cert-manager, SPIFFE and SPIRE handle certificates and identity.
  • Audit logging is off until --audit-policy-file is set (levels None, Metadata, Request, RequestResponse). Falco detects runtime threats. Sign and verify images (Sigstore is OpenSSF; Notary, in-toto, TUF are CNCF).
