Overview

Topic 2.4

Storage.

Files written inside a container are lost when it restarts: "After a crash, kubelet restarts the container with a clean state." This page takes the topic to cover volumes, the PersistentVolume system and StorageClasses, the CSI drivers that provide real storage, snapshots, ephemeral volumes, and storage for stateful apps.

Quotes are from the Kubernetes documentation (© The Kubernetes Authors) and the CNCF Glossary, both CC BY 4.0, and from the CSI specification, for Kubernetes v1.37.

Running example. The web shop's shop-db database needs 10 GiB of fast disk that survives restarts, shop-api needs a small in-memory cache, and the platform team wants nightly snapshots of the database volume.

Volumes

Topic 2.4Giving containers a directory that outlives a container restart, or the Pod itself, and picking the right volume type.

"At its core, a volume is a directory, possibly with some data in it, which is accessible to the containers in a pod." Volumes solve two problems: data lost when a container crashes, and containers in one Pod that need to share files. They come in two lifetimes: "When a Pod ceases to exist, Kubernetes destroys ephemeral volumes; however, Kubernetes does not destroy persistent volumes. For any kind of volume in a given Pod, data is preserved across container restarts."

A Pod lists its volumes in spec.volumes, and each container mounts the ones it needs in volumeMounts, at a mountPath, optionally readOnly or only a subPath of the volume.

TypeWhat it providesLifetime
emptyDirAn empty scratch directory shared by the Pod's containers; RAM-backed with medium: MemoryDeleted "when a Pod is removed from a node for any reason"
configMap, secret, downwardAPI, projectedConfiguration, secrets (on RAM-backed tmpfs) and Pod information as read-only filesEphemeral
persistentVolumeClaimDurable storage claimed through a PVC (below)Persistent
csiStorage from a CSI driverEither
nfsAn existing NFS share; "can be mounted by multiple writers simultaneously"Data kept; "merely unmounted"
localA disk on one node, as a static PersistentVolume with node affinityPersistent, but tied to that node
hostPathA file or directory from the node's filesystemStays on that node
imageAn OCI image or artifact, read-only (stable since v1.36)Ephemeral
An in-memory cache for shop-api 
  volumes:
  - name: cache
    emptyDir:
      medium: Memory
      sizeLimit: 256Mi
  containers:
  - name: api
    image: nginx:1.14.2
    volumeMounts:
    - name: cache
      mountPath: /cache

"A container crashing does not remove a Pod from a node. The data in an emptyDir volume is safe across container crashes." But with medium: Memory, "files you write count against the memory limit of the container that wrote them".

Avoid hostPath. "Using the hostPath volume type presents many security risks. If you can avoid using a hostPath volume, you should." Access to the node's files can expose kubelet credentials or the container runtime socket "that can be used for container escape". As a PersistentVolume it is "for single node testing only"; use a local volume instead.

The in-tree volume plugins are gone. Volume types built into Kubernetes for specific clouds and systems have been removed in favour of CSI drivers: awsElasticBlockStore and azureDisk (v1.27), gcePersistentDisk (v1.28), azureFile and vsphereVolume (v1.30), cephfs and rbd (v1.31), and Portworx (v1.36). The gitRepo volume is also gone: "The last version that provided a way to use this driver was Kubernetes v1.35"; use an init container that runs git clone into an emptyDir instead.

PersistentVolumes and claims

Topic 2.4Separating how storage is provided from how it is used, through PersistentVolumes and the claims that request them.

"The PersistentVolume subsystem provides an API for users and administrators that abstracts details of how storage is provided from how it is consumed."

  • A PersistentVolume (PV) "is a piece of storage in the cluster that has been provisioned by an administrator or dynamically provisioned using Storage Classes. It is a resource in the cluster just like a node". It is cluster-wide.
  • A PersistentVolumeClaim (PVC) "is a request for storage by a user. It is similar to a Pod. Pods consume node resources and PVCs consume PV resources." It is namespaced, and "claims must exist in the same namespace as the Pod using the claim."
  1. ProvisionStatic: an administrator creates PVs in advance. Dynamic: a StorageClass creates a PV for the claim on demand.
  2. BindA controller matches each claim to a PV, one to one. "The user will always get at least what they asked for". If nothing matches, the claim stays Pending.
  3. Use"Pods use claims as volumes." While in use, finalizers stop the PVC and its PV from being deleted, to avoid data loss.
  4. ReclaimWhen the claim is deleted, the PV's reclaim policy decides what happens to the data.
data-pvc.yaml (PersistentVolumeClaim) 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: fast
  resources:
    requests:
      storage: 10Gi
Using the claim in a Pod 
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data
  containers:
  - name: db
    image: postgres:16
    volumeMounts:
    - name: data
      mountPath: /var/lib/postgresql

Access modes

ModeShortMeaning
ReadWriteOnceRWORead-write "by a single node"
ReadOnlyManyROXRead-only "by many nodes"
ReadWriteManyRWXRead-write "by many nodes"
ReadWriteOncePodRWOPRead-write by a single Pod in the whole cluster; CSI volumes only; stable since v1.29

RWO is one node, not one Pod. "ReadWriteOnce access mode still can allow multiple pods to access (read from or write to) that volume when the pods are running on the same node. For single pod access, please see ReadWriteOncePod." Also, access modes "do not enforce write protection once the storage has been mounted", and a storage backend may support only some modes.

Reclaim policies and phases

PolicyWhen the claim is deletedDefault for
DeleteRemoves the PV "as well as the associated storage asset in the external infrastructure"Dynamically provisioned PVs
RetainThe PV is kept as Released, "not yet available for another claim because the previous claimant's data remains on the volume"; an administrator cleans upManually created PVs
RecycleDeprecated; a basic scrub, for NFS and hostPath only—

A PV's phase is Available, Bound, Released or Failed; a PVC's is Pending, Bound or Lost. Change a dynamically created PV to Retain with kubectl patch pv before deleting its claim if you need to keep the data.

Deleting a claim can delete the data. With the default Delete policy of dynamic provisioning, deleting the PVC deletes the actual disk.

Expanding a claim (stable since v1.24) works only if its StorageClass sets allowVolumeExpansion: true: edit the PVC to a larger size and the existing volume is resized. Volumes can only grow, never shrink.

StorageClasses

Topic 2.4Offering kinds of storage that are created automatically when a claim asks for them.

"A StorageClass provides a way for administrators to describe the classes of storage they offer", for example fast SSDs or cheaper disks. "Dynamic volume provisioning allows storage volumes to be created on-demand." Without it, administrators must create disks and PVs by hand.

fast.yaml (StorageClass) 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: csi.example.com
reclaimPolicy: Retain
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
parameters:
  type: ssd
  • provisioner names the volume plugin, usually a CSI driver; it "must be specified".
  • reclaimPolicy is Delete or Retain; if unset, "it will default to Delete".
  • parameters are passed to the provisioner and depend on the driver.

When the volume is created

volumeBindingModeBehaviour
Immediate (default)Provisioned as soon as the PVC is created, "without knowledge of the Pod's scheduling requirements. This may result in unschedulable Pods", for example a disk in a zone where the Pod cannot run
WaitForFirstConsumerDelays "binding and provisioning of a PersistentVolume until a Pod using the PersistentVolumeClaim is created", so the volume is created where the Pod is scheduled

The default StorageClass

A class marked with the annotation storageclass.kubernetes.io/is-default-class: "true" is used by claims that do not name a class, and kubectl get sc shows it as (default). There should be only one; if several are marked, the newest wins. Since v1.28, claims created before a default existed are updated when one appears.

Empty is not the same as missing. Leaving out storageClassName means "use the default class". Setting storageClassName: "" means "no class": such a claim "is always interpreted to be requesting a PV with no class" and disables dynamic provisioning.

For changing performance later, a VolumeAttributesClass (stable since v1.34) describes mutable settings such as IOPS or throughput; switching a claim to another class modifies the existing volume, if its CSI driver supports it.

CSI drivers

Topic 2.4Knowing how storage vendors plug into Kubernetes through the Container Storage Interface.

The Container Storage Interface aims "to define an industry standard ... that will enable storage vendors (SP) to develop a plugin once and have it work across a number of container orchestration (CO) systems". Kubernetes has supported it since v1.13 (GA, 2019); the specification's latest release is v1.13.0 (July 2026).

Why it matters: previously, "all volume plugins were 'in-tree'", so adding a storage system "required checking code into the core Kubernetes code repository". With CSI, "third-party storage providers can write and deploy plugins exposing new storage systems in Kubernetes without ever having to touch the core Kubernetes code."

PartRole
Controller plugin"A gRPC endpoint serving CSI RPCs that MAY be run anywhere": creates, deletes, attaches and snapshots volumes
Node pluginRuns on each node "whereupon an SP-provisioned volume will be published": mounts volumes for Pods
external-provisioner sidecarWatches PVCs and calls CreateVolume
external-attacher, external-resizer, external-snapshotterHandle attaching (via VolumeAttachment objects), expanding and snapshotting
node-driver-registrar sidecarRegisters the driver with the kubelet on each node

Kubernetes records installed drivers in CSIDriver objects and per-node driver information in CSINode objects.

You install the driver. CSI migration (stable since v1.25) transparently redirects old in-tree volume types to CSI drivers, but "you - or another cluster administrator - must have installed and configured the appropriate CSI driver for that storage. The core of Kubernetes does not install that software for you."

Snapshots and cloning

Topic 2.4Taking point-in-time copies of volumes and creating new volumes from existing data.

Snapshots mirror the PV and PVC pattern: "A VolumeSnapshot is a request for snapshot of a volume by a user. It is similar to a PersistentVolumeClaim", a VolumeSnapshotContent is the actual snapshot, like a PV, and a VolumeSnapshotClass sets the driver and deletion policy. Snapshots are stable since v1.20.

Snapshot the database volume 
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: data-snap
spec:
  volumeSnapshotClassName: csi-snap
  source:
    persistentVolumeClaimName: data

To restore, create a new PVC whose dataSource names the VolumeSnapshot. A clone is similar: a new PVC whose dataSource is an existing PVC in the same namespace (stable since v1.18). Volume populators (stable since v1.33) generalize this with dataSourceRef to fill a new volume from other sources.

Snapshots are an add-on. "VolumeSnapshot, VolumeSnapshotContent, and VolumeSnapshotClass are CRDs, not part of the core API", "support is only available for CSI drivers", and "the CRDs and snapshot controller installations are the responsibility of the Kubernetes distribution." VolumeGroupSnapshot, for crash-consistent snapshots of several volumes at once, reached GA in v1.36.

Ephemeral volumes

Topic 2.4Giving Pods storage that is created and deleted with them, so they can run anywhere.

Ephemeral volumes "follow the Pod's lifetime and get created and deleted along with the Pod", so Pods "can be stopped and restarted without being limited to where some persistent volume is available". They are specified inline in the Pod spec:

KindProvided by
emptyDir, configMap, downwardAPI, secretThe kubelet, as local ephemeral storage
imageThe container runtime (stable since v1.36)
CSI ephemeral volumesA CSI driver that supports them (stable since v1.25)
Generic ephemeral volumesAny dynamic provisioner (stable since v1.23)

A generic ephemeral volume embeds a claim template (ephemeral.volumeClaimTemplate): Kubernetes creates a real PVC for the Pod, named <pod>-<volume>, and "ensures that the PersistentVolumeClaim gets deleted when the Pod gets deleted". It is useful for large scratch space with features of real storage, such as a specific StorageClass.

Stateful apps

Topic 2.4Running applications that keep state, with storage that follows each replica, and knowing the CNCF projects that provide it.

The CNCF Glossary: in stateful apps, "state refers to any data the app needs to store to function as designed. Any kind of online shop that remembers your cart is a stateful app". "Stateless applications handle each request independently without remembering any previous interactions or user data."

A StatefulSet (topic 1.1) gives each replica its own storage: "For each VolumeClaimTemplate entry defined in a StatefulSet, each Pod receives one PersistentVolumeClaim", so shop-db-0 always gets back the same volume.

StatefulSet volumes are kept. "Deleting and/or scaling a StatefulSet down will not delete the volumes associated with the StatefulSet. This is done to ensure data safety". Since v1.32 (stable), persistentVolumeClaimRetentionPolicy can change that; both settings default to Retain.

Keep data on delete, clean up on scale-down 
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain
    whenScaled: Delete

Two scheduling aids help stateful Pods find storage: storage capacity tracking (stable since v1.24) lets the scheduler avoid nodes whose storage is full, when the class uses WaitForFirstConsumer, and node volume limits stop too many volumes being attached to one node.

Key takeaways

  • Volumes survive container restarts. Ephemeral volumes (emptyDir, configMap, secret, image...) die with the Pod; persistent volumes do not. emptyDir is erased when the Pod leaves the node but survives container crashes.
  • Avoid hostPath (container escape risk; single-node testing only). In-tree cloud plugins and gitRepo are removed: use CSI drivers.
  • PV = cluster-wide piece of storage; PVC = namespaced request, bound one-to-one. Provision (static or dynamic) → bind → use → reclaim.
  • Access modes: RWO (one node), ROX, RWX, RWOP (one Pod, CSI, stable v1.29).
  • Reclaim: Delete (default for dynamic; deletes the disk), Retain (PV becomes Released; manual cleanup), Recycle deprecated. Expansion needs allowVolumeExpansion; grow only.
  • StorageClass: provisioner, parameters, reclaimPolicy (default Delete). WaitForFirstConsumer avoids zone mismatches; Immediate is the default. Omitted class = default class; "" = no class.
  • CSI (GA v1.13): controller and node plugins plus sidecars; vendors ship drivers outside Kubernetes. You must install the driver.
  • Snapshots (VolumeSnapshot, stable v1.20) are CRDs plus a controller from your distribution; restore or clone with dataSource. Group snapshots GA v1.36.
  • StatefulSets give each replica its own PVC and keep PVCs on scale-down and delete unless the retention policy says otherwise. CNCF storage: Rook and CubeFS (graduated), Longhorn (incubating), OpenEBS and Velero (sandbox).
