1.3: Scheduling

How Kubernetes® decides which node runs each Pod: resource requests, rules that attract Pods to nodes or keep them away, priorities when the cluster is full, and what happens when a node runs short.

Overview

Topic 1.3

Scheduling.

"In Kubernetes, scheduling refers to making sure that Pods are matched to Nodes so that the kubelet can run them." This page takes the topic to cover how the scheduler chooses, the resource requests it relies on, the ways to steer Pods towards or away from nodes, priority and preemption, and eviction when nodes run short. Autoscaling gets a brief mention; it belongs mainly to topic 4.2.

Definitions are quoted from the Kubernetes documentation (© The Kubernetes Authors, CC BY 4.0) for Kubernetes v1.37.

Running example. The web shop runs on four nodes: three general nodes, two with fast SSDs, and one GPU node reserved for a recommendation model. shop-web must survive a node failure, shop-db needs SSD storage, and a log collector runs on every node.

How the scheduler decides

Topic 1.3Following how kube-scheduler picks a node for a new Pod, and recognizing what happens when no node fits.

"A scheduler watches for newly created Pods that have no Node assigned" and becomes "responsible for finding the best Node for that Pod to run on." kube-scheduler is "the default scheduler for Kubernetes and runs as part of the control plane." It works in two steps:

  1. FilteringFind the feasible nodes, those that meet all the Pod's requirements. For example, a resource check removes nodes without enough free CPU or memory for the Pod's requests.
  2. ScoringRank the feasible nodes using the active scoring rules, and pick the highest. Ties are broken "at random".
  3. BindingThe scheduler "notifies the API server about this decision in a process called binding". The kubelet on that node then starts the Pod.

If no node is feasible, "the Pod remains unscheduled until a place can be found", in the Pending phase, and the scheduler records an event each time it fails:

A Pod that cannot be placed 
kubectl describe pod shop-db-0
...
Events:
  Type     Reason
  Warning  FailedScheduling
  0/4 nodes are available:
  4 Insufficient memory.

Typical reasons in the message include Insufficient cpu, node(s) had untolerated taint(s) and node(s) didn't match Pod's node affinity/selector, each pointing to one of the sections below. Once placed, a Pod's node shows in the NODE column of kubectl get pods -o wide.

Other schedulers, and skipping the scheduler

  • The scheduler is built on a pluggable scheduling framework, and can run several profiles. A Pod picks one with spec.schedulerName; the default is default-scheduler. A Pod naming a scheduler that is not running "remains in 'Pending' state forever".
  • Setting spec.nodeName skips scheduling entirely: "the scheduler ignores the Pod and the kubelet on the named node tries to place the Pod on that node." If that node lacks resources, the Pod fails with a reason such as OutOfmemory or OutOfcpu. It is meant for custom schedulers, not everyday use.

Scheduling policies are gone. Older material describes configuring the scheduler with "predicates and priorities" policy files. That method "is not supported since Kubernetes v1.23"; scheduler configuration now uses profiles and plugins.

Requests, limits and QoS

Topic 1.3Telling the scheduler how much CPU and memory each container needs, and knowing what happens when a container uses more.

"When you specify the resource request for containers in a Pod, the kube-scheduler uses this information to decide which node to place the Pod on. When you specify a resource limit for a container, the kubelet enforces those limits".

Container resources in a Pod template 
containers:
- name: api
  image: nginx:1.14.2
  resources:
    requests:
      cpu: 250m       # 0.25 CPU
      memory: 64Mi
    limits:
      cpu: 500m
      memory: 128Mi
  • CPU is measured in cores: 1 is one physical or virtual core, and 100m ("one hundred millicpu") equals 0.1.
  • Memory is in bytes, with suffixes M, G (powers of ten) or Mi, Gi (powers of two).
  • The scheduler places a Pod only where the sum of requests fits the node's allocatable resources (capacity minus what system daemons reserve), shown by kubectl describe node. It does this "although actual memory or CPU resource usage on nodes is very low".
ExceedingWhat happens
The CPU limitThe container is throttled: "container runtimes don't terminate Pods or containers for excessive CPU usage"
The memory limitThe kernel may kill it: the container restarts with reason OOMKilled and exit code 137
The memory request, on a node short of memoryThe Pod is likely to be evicted (see eviction)

Two unit and default traps. "'M' means megabytes, while 'm' means millibytes. If you request 400m of memory, this is a request for 0.4 bytes." And if you set a limit with no request, Kubernetes "copies the limit you specified and uses it as the requested value".

Quality of Service classes

From its requests and limits, every Pod gets a QoS class:

ClassRuleWeb shop example
GuaranteedEvery container has CPU and memory requests and limits, and each limit equals its requestshop-db
BurstableNot Guaranteed, but at least one container has a CPU or memory request or limitshop-api (requests lower than limits)
BestEffortNo container has any CPU or memory request or limitA throwaway debug Pod

"The kubelet prefers to evict BestEffort Pods if the node comes under resource pressure." Requests can also be set for a whole Pod in spec.resources (beta and on by default since v1.34), and since v1.35 a running container's CPU and memory can be resized in place.

Choosing nodes

Topic 1.3Attracting Pods to nodes with the right labels, and spreading copies of an app across nodes and zones.

"Often, you do not need to set any such constraints; the scheduler will automatically do a reasonable placement". When you do, all these rules work on node labels. Kubernetes sets some on every node, such as kubernetes.io/hostname, kubernetes.io/os, kubernetes.io/arch and, in clouds, topology.kubernetes.io/zone.

nodeSelector

"nodeSelector is the simplest recommended form of node selection constraint": the Pod runs only on nodes "that have each of the labels you specify".

Label the SSD nodes, then select them 
kubectl label nodes node-2 disktype=ssd
kubectl get nodes --show-labels

# in the shop-db Pod template
spec:
  nodeSelector:
    disktype: ssd

Node affinity

Node affinity does the same with more expressive rules (operators In, NotIn, Exists, DoesNotExist, Gt, Lt), in two strengths:

  • requiredDuringSchedulingIgnoredDuringExecution: "The scheduler can't schedule the Pod unless the rule is met."
  • preferredDuringSchedulingIgnoredDuringExecution: the scheduler tries, but "if a matching node is not available, the scheduler still schedules the Pod". Each preference has a weight from 1 to 100.

affinity → nodeAffinity

The full YAML is in the kubernetes.io node affinity example. Several nodeSelectorTerms are ORed; expressions inside one term are ANDed.

"IgnoredDuringExecution" means running Pods stay put. It means "if the node labels change after Kubernetes schedules the Pod, the Pod continues to run." Affinity only affects scheduling decisions. If you set both nodeSelector and node affinity, both must be satisfied.

Pod affinity and anti-affinity

These rules look at the Pods already running rather than node labels: "this Pod should (or, in the case of anti-affinity, should not) run in an X if that X is already running one or more Pods that meet rule Y", where X is a topology domain named by a topologyKey, such as a node (kubernetes.io/hostname) or a zone. Anti-affinity on app: shop-web with topologyKey: kubernetes.io/hostname keeps two frontend replicas off the same node, so one node failure cannot take them all down. The docs warn these rules need "substantial amounts of processing" in large clusters.

Topology spread constraints

Stable since v1.19, these "control how Pods are spread across your cluster among failure-domains such as regions, zones, nodes".

Spread shop-web evenly across zones 
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: shop-web

maxSkew is how uneven the spread may be (here, zones may differ by at most one Pod). whenUnsatisfiable is DoNotSchedule (the default) or ScheduleAnyway. The constraint is checked only at scheduling time: "scaling down a Deployment may result in imbalanced Pods distribution."

Taints and tolerations

Topic 1.3Keeping Pods off nodes unless they are explicitly allowed there, and reserving special nodes for the workloads that need them.

"Node affinity is a property of Pods that attracts them to a set of nodes ... Taints are the opposite -- they allow a node to repel a set of pods." A taint is set on a node as key=value:effect (the value is optional). A toleration on a Pod lets it ignore a matching taint.

EffectNew Pods without a tolerationPods already running
NoScheduleNot scheduledStay ("not evicted")
PreferNoScheduleAvoided if possible; "not guaranteed"Stay
NoExecuteNot scheduled"Evicted immediately", or after tolerationSeconds if the toleration sets it
Reserve the GPU node 
# taint the node
kubectl taint nodes node-4 \
  gpu=true:NoSchedule

# remove the taint again (trailing -)
kubectl taint nodes node-4 \
  gpu=true:NoSchedule-
Toleration in the model's Pod template 
tolerations:
- key: gpu
  operator: Equal   # or Exists
  value: "true"
  effect: NoSchedule

A toleration allows, it does not attract. "Tolerations allow scheduling but don't guarantee scheduling": the recommendation Pods may still land on ordinary nodes. To reserve node-4 and make the model run only there, combine the taint with a node label and node affinity, as the documentation's "dedicated nodes" example does.

Built-in taints

  • The control plane taints nodes when conditions arise: node.kubernetes.io/not-ready, unreachable, memory-pressure, disk-pressure, pid-pressure and unschedulable (set by kubectl cordon). "The scheduler checks taints, not node conditions, when it makes scheduling decisions."
  • Pods automatically tolerate not-ready and unreachable for 300 seconds, so they "remain bound to Nodes for 5 minutes after one of these problems is detected" before being evicted.
  • DaemonSet Pods tolerate those two taints with no time limit, so they "are never evicted due to these problems".
  • kubeadm taints control plane nodes with node-role.kubernetes.io/control-plane:NoSchedule, which is why ordinary Pods do not run there. The older node-role.kubernetes.io/master taint is deprecated.

Priority and preemption

Topic 1.3Deciding which Pods matter most, so important Pods can displace less important ones when the cluster is full.

"Priority indicates the importance of a Pod relative to other Pods. If a Pod cannot be scheduled, the scheduler tries to preempt (evict) lower priority Pods to make scheduling of the pending Pod possible." Priorities come from a PriorityClass, a cluster-wide object mapping a name to a number: the higher the value, the higher the priority.

priority.yaml (PriorityClass) 
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: shop-critical
value: 1000000
globalDefault: false
description: "Checkout path"

A Pod uses it with spec.priorityClassName: shop-critical. Pods without a class get the globalDefault class if one exists, otherwise priority zero. Two built-in classes, system-cluster-critical and system-node-critical, protect essential components such as DNS. Pending Pods are also queued for scheduling in priority order.

Preemption is not polite. Respecting PodDisruptionBudgets during preemption "is best effort": if no other choice exists, "lower priority Pods will be removed despite their PDBs being violated." Preemption also "does not consider QoS": priority and QoS class are separate features. A class with preemptionPolicy: Never jumps the queue but never evicts other Pods.

Eviction under pressure

Topic 1.3Recognizing when a node removes Pods to protect itself, and how that differs from an eviction someone asks for.

"The kubelet monitors resources like memory, disk space, and filesystem inodes on your cluster's nodes. When one or more of these resources reach specific consumption levels, the kubelet can proactively fail one or more pods on the node to reclaim resources and prevent starvation." It first tries to free space itself, for example by deleting unused images.

Node-pressure evictionAPI-initiated eviction
Triggered byThe kubelet, when a signal such as memory.available or nodefs.available crosses a thresholdA request to the Eviction API, for example by kubectl drain
PodDisruptionBudgetsIgnoredRespected
Grace periodIgnored; hard thresholds kill with a 0 s grace periodRespected

Thresholds are hard (act immediately; defaults include memory.available<100Mi and nodefs.available<10% on Linux) or soft (act only after a grace period). Under pressure the node reports a condition, MemoryPressure, DiskPressure or PIDPressure, and is tainted so no new Pods arrive.

Who goes first. The kubelet ranks Pods by whether their usage exceeds their requests, then by Pod priority, then by how far usage exceeds requests. The documentation notes the kubelet "does not use the pod's QoS class" directly, but the effect is similar: BestEffort Pods (which request nothing) usually go first, Guaranteed Pods last. Setting realistic requests is the best protection.

Newer features and autoscaling

Topic 1.3Recognizing newer scheduling features by name, and how autoscalers change what there is to schedule.

Autoscaling in brief

  • The HorizontalPodAutoscaler (autoscaling/v2) adds or removes replicas to match demand, using metrics from metrics-server. It cannot scale a DaemonSet. Scaling to zero replicas on custom or external metrics became beta, on by default, in v1.37.
  • The VerticalPodAutoscaler adjusts requests; it is an add-on, not part of Kubernetes itself.
  • Node autoscalers add and remove nodes: "Cluster Autoscaler and Karpenter are the two Node autoscalers currently sponsored by SIG Autoscaling." Pending Pods that fit nowhere are what trigger them to add nodes.
  • KEDA, a CNCF graduated project, scales workloads on events such as queue length; it would suit shop-worker.

Autoscaling as a cloud native principle is covered in topic 4.2.

Key takeaways

  • kube-scheduler filters to feasible nodes, scores them, then binds the Pod. If nothing fits, the Pod stays Pending with a FailedScheduling event. nodeName bypasses the scheduler.
  • The scheduler uses requests, not limits or actual usage, against node allocatable. Over the CPU limit = throttled; over the memory limit = OOMKilled. A limit without a request sets the request. 400m memory means 0.4 bytes.
  • QoS: Guaranteed (limits equal requests for CPU and memory), Burstable (some requests or limits), BestEffort (none; evicted first in practice).
  • Attract with nodeSelector or node affinity (required or preferred; IgnoredDuringExecution). Place relative to other Pods with pod affinity and anti-affinity on a topologyKey; spread with topology spread constraints (maxSkew, default DoNotSchedule).
  • Taints repel, tolerations permit but do not attract. Effects: NoSchedule, PreferNoSchedule, NoExecute (evicts running Pods). Pods tolerate not-ready and unreachable nodes for 300 s; control plane nodes carry a NoSchedule taint.
  • PriorityClasses order Pods; higher priority can preempt lower, with PDBs respected only on a best-effort basis and QoS ignored.
  • Node-pressure eviction (kubelet) ignores PDBs and grace periods; API eviction (drain) respects both.
  • Newer: scheduling gates (stable 1.30), DRA (stable 1.34), gang scheduling (beta, off). Autoscalers: HPA, VPA (add-on), Cluster Autoscaler and Karpenter, KEDA.
