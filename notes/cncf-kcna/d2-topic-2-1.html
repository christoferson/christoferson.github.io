Overview

Topic 2.1

Networking.

This page takes the topic to cover the Kubernetes network model and the plugins that implement it, Services, kube-proxy and DNS for finding Pods, Ingress and the Gateway API for traffic from outside, NetworkPolicy for restricting traffic, and service meshes, which the old curriculum named separately. Using NetworkPolicy as part of a security design is revisited in topic 2.2; diagnosing network problems is topic 2.3.

Quotes are from the Kubernetes documentation (© The Kubernetes Authors) and the CNCF Glossary, both CC BY 4.0, and from the Gateway API project, for Kubernetes v1.37.

Running example. In the web shop, customers reach shop-web at shop.example.com; shop-web calls shop-api, which talks to shop-db. Only shop-web should be reachable from outside, and only shop-api should reach the database.

The network model

Topic 2.1Stating the rules every Kubernetes network follows, and which parts Kubernetes itself does not implement.

  • "Each pod in a cluster gets its own unique cluster-wide IP address."
  • Containers in the same Pod share one network namespace and "can communicate with each other over localhost."
  • "All pods can communicate with all other pods, whether they are on the same node or on different nodes. Pods can communicate with each other directly, without the use of proxies or address translation (NAT)."
  • "Agents on a node (such as system daemons, or kubelet) can communicate with all pods on that node."

The documentation names four problems and their solutions: container-to-container (Pods and localhost), Pod-to-Pod (the pod network), Pod-to-Service and external-to-Service (Services, plus Ingress or Gateway).

Kubernetes defines the APIs; plugins do much of the work. "Only a few parts of this model are implemented by Kubernetes itself." The pod network comes from a CNI plugin, Service routing from kube-proxy or a replacement, and NetworkPolicy from the network plugin. Clusters can be IPv4, IPv6 or dual-stack (stable since v1.23).

CNI plugins

Topic 2.1Knowing what a CNI plugin does and recognizing the common ones.

"CNI (Container Network Interface), a Cloud Native Computing Foundation project, consists of a specification and libraries for writing plugins to configure network interfaces in Linux containers". It "concerns itself only with network connectivity of containers". CNI is a CNCF incubating project; the specification is at version 1.1.0. "A CNI plugin is required to implement the Kubernetes network model": it gives each Pod an IP address and connects Pods across nodes.

PluginNotes
CiliumeBPF-based networking, observability and security; enforces policy at layers 3 to 7; "can act as a replacement for kube-proxy". CNCF graduated (2023)
Calico"A networking and network policy provider", with or without overlays and BGP
Flannel"An overlay network provider"; simple
AntreaBuilt on Open vSwitch; CNCF Sandbox
MultusAttaches several networks to one Pod

"You can install only one Pod network per cluster." The plugin is loaded by the container runtime, not the kubelet: kubelet's CNI flags "were removed in Kubernetes 1.24".

Services

Topic 2.1Giving a changing set of Pods one stable address, and choosing how widely that address is exposed.

Pods come and go, so their IPs change. A Service is "a method for exposing a network application that is running as one or more Pods in your cluster", with "a stable (long lived) IP address or hostname". It usually finds its Pods with a label selector, and the control plane keeps a list of matching Pods in EndpointSlices.

shop-api Service (ClusterIP) 
apiVersion: v1
kind: Service
metadata:
  name: shop-api
spec:
  type: ClusterIP   # default; may omit
  selector:
    app: shop-api   # matches Pod labels
  ports:
  - name: http
    protocol: TCP   # default
    port: 80        # the Service's port
    targetPort: 8080 # container port

A Service maps its port to the Pods' targetPort (by default the same number). Clients call http://shop-api on port 80 and reach a container listening on 8080.

Service types

"The type field in the Service API is designed as nested functionality - each level adds to the previous":

TypeReachable fromWeb shop use
ClusterIP (default)"Only reachable from within the cluster", through a virtual IPshop-api, shop-db
NodePortEvery node's IP at a fixed port from 30000–32767 by default, plus a cluster IPQuick testing without a load balancer
LoadBalancerAn external load balancer; "you must provide one, or you can integrate your Kubernetes cluster with a cloud provider"A simple way to expose shop-web
ExternalNameA DNS CNAME to an outside name; "No proxying of any kind is set up"Point payments at an external provider's hostname

Headless Services. Setting clusterIP: None creates a headless Service: "a cluster IP is not allocated, kube-proxy does not handle these Services, and there is no load balancing or proxying". DNS instead returns the individual Pod IPs, which is what a StatefulSet such as shop-db needs to give each Pod a stable name. None "is not the same as leaving the .spec.clusterIP field unset".

Other Service settings

  • Without a selector, no EndpointSlices are created automatically; you add them yourself, for example to point at a database outside the cluster.
  • sessionAffinity: ClientIP sends each client to the same Pod (default None; timeout three hours).
  • externalTrafficPolicy and internalTrafficPolicy are Cluster (default: any ready Pod) or Local (only Pods on the receiving node; traffic is dropped if there are none).
  • trafficDistribution: PreferSameZone or PreferSameNode (stable since v1.35) prefers nearby Pods; the older value PreferClose is a deprecated alias.

Two Service features are deprecated. The Endpoints API is deprecated since v1.33 in favour of EndpointSlices, and the Service field .spec.externalIPs since v1.36 because of a security problem: "All users should begin migrating away from externalIPs." The external IPs of LoadBalancer Services are not affected.

Expose and inspect 
# create a Service for a Deployment
kubectl expose deployment shop-api \
  --port=80 --target-port=8080

kubectl get svc,endpointslices
kubectl describe svc shop-api

# reach it from your laptop (one Pod)
kubectl port-forward svc/shop-web 8080:80

Note that port-forward picks a single Pod, so it does not load-balance.

kube-proxy

Topic 2.1Explaining how a Service's virtual IP actually reaches a Pod, and the modes kube-proxy can use.

"kube-proxy is a network proxy that runs on each node in your cluster, implementing part of the Kubernetes Service concept." It watches Services and EndpointSlices and programs the node's packet filtering so that traffic to a Service's virtual IP is rewritten to one of its Pods. The cluster IP is not assigned to any machine: "the Service IP is completely virtual, it never hits the wire."

ModeState in v1.37
iptablesThe default on Linux; "a future version of Kubernetes will change the default to nftables"
nftablesStable since v1.33; "the successor to the iptables API"; needs Linux kernel 5.13 or later
ipvsDeprecated since v1.35; to be disabled by default in v1.40 and removed in v1.43
kernelspaceThe only mode on Windows nodes

Some network plugins, such as Cilium, replace kube-proxy entirely with their own eBPF-based Service routing.

DNS

Topic 2.1Finding Services by name, across namespaces, and knowing what DNS returns for each kind of Service.

"Kubernetes creates DNS records for Services and Pods. You can contact Services with consistent DNS names instead of IP addresses." The cluster DNS server is CoreDNS, "the default implementation of Kubernetes cluster DNS" (a CNCF graduated project); for compatibility its Service is still called kube-dns.

Name used from a shop PodResolves to
shop-apiThe shop-api Service in the Pod's own namespace
shop-api.stagingThe shop-api Service in staging
shop-api.shop.svc.cluster.localThe full name: service, namespace, svc, cluster domain

This works because the kubelet writes the Pod's /etc/resolv.conf with search domains for its namespace, and "DNS queries that don't specify a namespace are limited to the Pod's namespace."

RecordReturned for
A / AAAAA normal Service: its cluster IP. A headless Service: "the set of IPs of all of the Pods selected"
SRVNamed ports, as _http._tcp.shop-api.shop.svc.cluster.local
CNAMEAn ExternalName Service

"Default" is not the default DNS policy. A Pod's dnsPolicy defaults to ClusterFirst (use cluster DNS). The value named Default makes the Pod inherit the node's DNS settings instead, and None means you supply everything in dnsConfig.

kube-dns is deprecated. CoreDNS has been the default since v1.13, and v1.37 deprecates the old kube-dns add-on; "no new packages will be built for kube-dns after v1.40."

Ingress and the Gateway API

Topic 2.1Routing outside HTTP traffic to the right Service, and knowing why new clusters use the Gateway API instead of Ingress.

Ingress

An Ingress is "an API object that manages external access to the services in a cluster, typically HTTP", with routing rules by host name and path, and optional TLS. Two things are needed: the Ingress resource and an Ingress controller: "Only creating an Ingress resource has no effect." It handles only HTTP and HTTPS; other protocols use NodePort or LoadBalancer Services.

The Ingress API is frozen, and Ingress NGINX is retired. "The Kubernetes project recommends using Gateway instead of Ingress. The Ingress API has been frozen." It stays generally available with "no plans to remove" it, but "is no longer being developed". Separately, the popular Ingress NGINX controller was retired on March 24, 2026, after an announcement in November 2025: no more releases or security fixes, though "existing deployments of Ingress NGINX will continue to function". The Ingress2Gateway 1.0 tool (March 2026) helps convert Ingress resources to Gateway API.

Gateway API

"Gateway API is an add-on containing API kinds that provide dynamic infrastructure provisioning and advanced traffic routing", described by its project as "the next generation of Kubernetes Ingress, Load Balancing, and Service Mesh APIs". Its design is:

  • Role-oriented: separate objects for the infrastructure provider, the cluster operator and the application developer.
  • Portable: "defined as custom resources and ... supported by many implementations".
  • Expressive: header matching, traffic weighting and more, "that were only possible in Ingress by using custom annotations".
ResourceOwned byDefines
GatewayClassInfrastructure providerA kind of gateway and the controller that implements it
GatewayCluster operator"An instance of traffic handling infrastructure, such as cloud load balancer", with listeners (ports, protocols)
HTTPRoute, GRPCRoute, TLSRoute, TCPRoute, UDPRouteApplication developerRules that map traffic from a Gateway listener to backend Services
Gateway and HTTPRoute for the shop 
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gw
spec:
  gatewayClassName: example-class
  listeners:
  - name: http
    protocol: HTTP
    port: 80
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop-route
spec:
  parentRefs:        # attach to Gateway
  - name: shop-gw
  hostnames:
  - "shop.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    backendRefs:     # target Service
    - name: shop-api
      port: 80

Gateway API is not built in. Its resources are custom resources you install (or a Gateway controller installs for you), and a controller must implement them, just as with Ingress. Gateway, GatewayClass and HTTPRoute reached GA in v1.0 (October 2023); the latest release is v1.7 (October 2026), and since v1.6 TCPRoute and UDPRoute are also standard.

NetworkPolicy

Topic 2.1Restricting which Pods may talk to which, starting from "everything is allowed".

A NetworkPolicy is "a specification of how groups of Pods are allowed to communicate with each other and with other network endpoints", at IP address and port level (OSI layer 3 or 4). It selects Pods by label and allows traffic from other Pods (podSelector), from namespaces (namespaceSelector) or from IP ranges (ipBlock).

  • Default open: "By default, a pod is non-isolated for ingress; all inbound connections are allowed." The same is true for egress.
  • Isolation: a Pod becomes isolated for ingress as soon as any policy selects it with Ingress in its policyTypes. Then only traffic from its node and traffic the policies allow can reach it.
  • Additive: "Network policies do not conflict; they are additive." The allowed traffic is the union of all policies, so order does not matter.
  • Both ends: a connection needs both the source's egress rules and the destination's ingress rules to allow it.
Deny all incoming traffic in the namespace 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}   # all Pods here
  policyTypes:
  - Ingress
Then allow only shop-web to reach shop-api 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow-web
spec:
  podSelector:       # pods protected
    matchLabels:
      app: shop-api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:   # same namespace
        matchLabels:
          app: shop-web
    ports:
    - protocol: TCP
      port: 8080

No plugin support, no effect. "Network policies are implemented by the network plugin ... Creating a NetworkPolicy resource without a controller that implements it will have no effect." Choose a CNI plugin that enforces policy. NetworkPolicy also cannot express explicit deny rules, cluster-wide defaults or anything TLS-related.

Cluster-wide rules that administrators set for every namespace come from a separate SIG Network project: ClusterNetworkPolicy, which replaced the earlier AdminNetworkPolicy design in 2026 and reached beta (v1beta1) in November 2026. Like Gateway API, it is installed as custom resources.

Service mesh

Topic 2.1Knowing what a service mesh adds between services, and the sidecar and sidecarless ways it is built.

The CNCF Glossary: "Service meshes add reliability, observability, and security features uniformly across all services across a cluster without requiring code changes." A mesh manages service-to-service traffic: retries and timeouts, traffic splitting, metrics and tracing, and mutual TLS (mTLS), in which "instead of validating the identity of just one connection, both sides are validated."

DesignHow it worksTrade-off
Sidecar"Pairs each pod with a proxy" (often Envoy) that intercepts its trafficFine control, but "uses more computing resources and becomes more complex to manage as your system grows"
SidecarlessMoves mesh functions to shared node-level proxies or the kernel, for example with eBPF"Drastically reduces resource usage and removes unnecessary network hops"
  • Istio (CNCF graduated 2023) supports both; its sidecarless ambient mode reached general availability in Istio 1.24 (November 2024).
  • Linkerd (CNCF graduated 2021) uses lightweight sidecar proxies.
  • Gateway API also configures meshes through the GAMMA initiative, standard since Gateway API v1.1: routes attach directly to Services.

Service Mesh Interface is archived. SMI, an earlier attempt at a common mesh API, was archived by CNCF in September 2023; Gateway API's GAMMA work is its successor in practice.

Key takeaways

  • Every Pod gets its own cluster-wide IP; all Pods can reach all Pods without NAT; containers in a Pod share localhost. A CNI plugin (Cilium, Calico, Flannel...) implements this; only one per cluster; CNI is a CNCF incubating project.
  • A Service gives Pods a stable virtual IP and name, found via a selector and EndpointSlices. Types nest: ClusterIP (default, internal) → NodePort (30000–32767) → LoadBalancer; ExternalName is a DNS CNAME. Headless (clusterIP: None) returns Pod IPs.
  • kube-proxy programs nodes to route Service traffic: iptables by default, nftables stable since v1.33, ipvs deprecated since v1.35. eBPF plugins can replace it. Endpoints (v1.33) and externalIPs (v1.36) are deprecated.
  • CoreDNS resolves <service>.<namespace>.svc.cluster.local; short names work within a namespace. Default dnsPolicy is ClusterFirst. kube-dns is deprecated.
  • Ingress needs a controller and handles HTTP(S) only; the API is frozen, and Ingress NGINX was retired in March 2026. The Gateway API (installed as CRDs; GatewayClass, Gateway, routes) is the role-oriented successor.
  • NetworkPolicy: open by default; selecting a Pod isolates it; policies are additive allow rules; enforcement requires a CNI plugin that supports it.
  • A service mesh adds mTLS, retries and observability without code changes, with sidecar or sidecarless proxies (Istio ambient, Linkerd). SMI is archived.
