Overview

Topic 1.2

Administration.

This topic is new in the November 2025 curriculum and is given as one word. This page takes it to mean the everyday work of running a cluster and the objects in it: connecting with kubectl, managing objects declaratively, sharing a cluster with quotas, creating and upgrading clusters within the version rules, maintaining nodes, backing up etcd, and extending Kubernetes with add-ons and operators. Security policy (RBAC) is topic 2.2, troubleshooting 2.3, and Helm and GitOps are topic 3.1.

Definitions are quoted from the Kubernetes documentation (© The Kubernetes Authors, CC BY 4.0) for Kubernetes v1.37.

Running example. The web shop from topic 1.1 (shop-web, shop-api, shop-db, shop-worker) now runs in a shop namespace on a three-node cluster that a small platform team administers, alongside a staging namespace used by developers.

kubectl and kubeconfig

Topic 1.2Connecting to the right cluster as the right user, and getting information out of it in a useful form.

"Kubernetes provides a command line tool for communicating with a Kubernetes cluster's control plane, using the Kubernetes API. This tool is named kubectl." It finds clusters through kubeconfig files, which "organize information about clusters, users, namespaces, and authentication mechanisms".

  • By default kubectl reads $HOME/.kube/config. The name "kubeconfig" is generic: "It does not mean that there is a file named kubeconfig."
  • The KUBECONFIG environment variable can list several files, which are merged; the --kubeconfig flag uses one file only.
  • A context groups three things under one name: a cluster, a user and a namespace. kubectl uses the current context unless told otherwise.
Switch between clusters and namespaces 
# list contexts; * marks the current one
kubectl config get-contexts
kubectl config current-context

# switch to the staging cluster
kubectl config use-context staging

# make "shop" the default namespace
kubectl config set-context --current \
  --namespace=shop

Treat kubeconfig files like passwords and scripts. They hold credentials, and the documentation warns: "Only use kubeconfig files from trusted sources. Using a specially-crafted kubeconfig file could result in malicious code execution or file exposure."

Useful output and generators

  • -o wide adds detail (for Pods, the node), -o yaml and -o json show the full object, -o name prints only names, -o jsonpath=... extracts fields, and -o kyaml prints KYAML (stable since v1.37).
  • --dry-run=client -o yaml prints the object a command would create without sending it: a quick way to start a manifest.
  • kubectl events --types=Warning lists recent warnings; kubectl top shows CPU and memory use once metrics-server is installed (see below).
Generate a manifest instead of typing it 
kubectl create deployment shop-api \
  --image=nginx:1.14.2 \
  --dry-run=client -o yaml > api.yaml

kubectl must be "within one minor version (older or newer)" of the API server: a v1.37 kubectl works with v1.36, v1.37 and v1.38 control planes. kubectl can also be extended with plugins, executables named kubectl-*, often installed with the Krew plugin manager (whose plugins "are not audited for security").

Ways to manage objects

Topic 1.2Choosing between imperative and declarative management, and sticking to one approach for each object.

kubectl supports three techniques:

TechniqueHow it worksExampleBest for
Imperative commandsOperate "directly on live objects", with the change given as argumentskubectl create deployment shop-api --image=...Learning and one-off tasks; no history
Imperative object configurationYou name the operation and a file with the full objectkubectl create -f api.yaml, kubectl replace -f api.yamlProduction, file by file
Declarative object configurationYou give files or directories; kubectl works out whether to create, update or delete each objectkubectl apply -f configs/Production, whole directories in Git

The documentation lists the drawbacks of imperative commands: they "do not integrate with change review processes", "do not provide an audit trail" and give no record "except for what is live". Files in version control fix all three, which is why declarative configuration is the basis of GitOps (topic 3.1).

Use one technique per object. "A Kubernetes object should be managed using only one technique. Mixing and matching techniques for the same object results in undefined behavior." In particular, create and replace do not keep the last-applied-configuration annotation that apply relies on. If you create something you later want to apply, use kubectl create --save-config. Deleting imperatively is fine.

create, replace and apply

  • kubectl create -f creates an object and fails if it already exists.
  • kubectl replace -f swaps in the whole spec, "dropping all changes to the object missing from the configuration file". Fields set by the cluster or by other tools are lost.
  • kubectl apply -f creates the object if needed, otherwise sends only the differences, so it "retains changes made by other writers". It works out the patch from your file, the live object and the last applied configuration (a three-way merge), and can be run again and again with the same result.
  • kubectl diff -f previews what apply would change.

Server-side apply (stable since v1.22, kubectl apply --server-side) moves this work to the API server. It records which field manager owns each field in metadata.managedFields, and reports a conflict if you try to change a field another manager owns. It is "meant both as a replacement for the original client-side implementation of the kubectl apply subcommand" and as a mechanism for controllers.

Kustomize

"Kustomize is a standalone tool to customize Kubernetes objects through a kustomization file", built into kubectl since v1.14. A base holds the common manifests; an overlay adapts them for an environment without copying them.

overlays/staging/kustomization.yaml 
resources:
- ../../base        # shared manifests
namespace: staging
namePrefix: stg-
labels:
- pairs:
    env: staging
Preview and apply the overlay 
kubectl kustomize overlays/staging
kubectl apply -k overlays/staging

Sharing a cluster

Topic 1.2Dividing a cluster between teams with namespaces, and stopping any one team from using more than its share.

Namespaces (topic 1.1) separate names; two more objects control resources within them:

ObjectLimitsStaging example
ResourceQuotaThe total for a namespace: "constraints that limit aggregate resource consumption per namespace", plus counts of objectsAt most 4 CPUs requested, 8 GiB of memory and 20 Pods across the whole namespace
LimitRangeEach Pod, container or PersistentVolumeClaim: minimums, maximums, and defaults injected into containers that set noneEvery container gets 250m CPU unless it asks for something else; none may exceed 1 CPU
quota.yaml (ResourceQuota) 
apiVersion: v1
kind: ResourceQuota
metadata:
  name: staging-quota
  namespace: staging
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.memory: 16Gi
    pods: "20"

Check usage with kubectl describe quota -n staging, which shows Used and Hard for each limit.

Three quota surprises. First, a request that would break a quota or LimitRange is rejected "with HTTP status code 403 Forbidden". Second, once a namespace has a CPU or memory quota, Pods "must specify requests or limits for those values", or they may be rejected; a LimitRange with defaults solves that. Third, a Deployment that exceeds the quota is still created: it is its Pods that fail to appear. Changes to quotas never affect objects that already exist.

Deleting a namespace deletes everything in it. The documentation's warning is blunt: "This deletes everything under the namespace!" The deletion is asynchronous, so the namespace shows as Terminating for a while.

Building and upgrading clusters

Topic 1.2Knowing the tools that create clusters, how often Kubernetes releases, and the rules for upgrading one version at a time.

Tools that create clusters

ToolWhat it isTypical use
kubeadmCreates "a minimum viable Kubernetes cluster that conforms to best practices" (kubeadm init on the control plane, kubeadm join on nodes) and handles upgradesSelf-managed clusters on your own machines
kind"Running local Kubernetes clusters using Docker container 'nodes'"; designed for testing Kubernetes itselfCI pipelines, local testing
minikube"Local Kubernetes, focusing on making it easy to learn and develop for Kubernetes"Learning on a laptop
k3sA lightweight, fully compliant Kubernetes distribution in a single binary; a CNCF Sandbox projectEdge devices, small servers
Managed KubernetesA cloud provider runs and upgrades the control plane; you manage nodes and workloadsMost production use in the cloud

After kubeadm init, you must install a CNI network plugin: "Cluster DNS (CoreDNS) will not start up before a network is installed", and "you can install only one Pod network per cluster."

Release cycle and support

Versions are x.y.z (major, minor, patch). New minor releases arrive "approximately three times per year", and the project maintains "the most recent three minor releases": in November 2026, 1.37, 1.36 and 1.35. Each gets roughly 14 months of patches (12 months standard, then 2 months of maintenance); v1.34 reached end of life on October 27, 2026.

Version skew rules

ComponentAllowed difference from kube-apiserver
Other kube-apiserver instances (HA)Within one minor version of each other
kube-controller-manager, kube-schedulerNever newer; at most one minor version older
kubelet, kube-proxyNever newer; up to three minor versions older
kubectlOne minor version older or newer

Upgrading

  1. Control plane firstUpgrade kube-apiserver (all instances), then the controller manager and scheduler. With kubeadm: kubeadm upgrade plan, then kubeadm upgrade apply v1.37.x on the first control plane node.
  2. Then each worker nodeDrain it, upgrade the kubelet (and kubeadm's node configuration with kubeadm upgrade node), restart the kubelet, then uncordon it. "In-place minor version kubelet upgrades are not supported": always drain first.
  3. One minor version at a time"Skipping MINOR versions when upgrading is unsupported": going from 1.35 to 1.37 means upgrading to 1.36 first.

The kubelet may lag, never lead. Because the kubelet may be up to three versions older but "must not be newer than kube-apiserver", upgrades always go control plane first, nodes second. Older material says the kubelet may only be two versions behind; that rule applies only to kubelets older than 1.25.

Node maintenance

Topic 1.2Taking a node out of service without breaking the applications running on it.

Patch a node safely 
# stop new Pods landing on node-2
kubectl cordon node-2

# evict its Pods (also cordons it)
kubectl drain node-2 --ignore-daemonsets

# ...maintenance... then allow Pods back
kubectl uncordon node-2

kubectl drain marks the node unschedulable and evicts its Pods, waiting for them to shut down gracefully. It stops if the node runs DaemonSet Pods unless you pass --ignore-daemonsets (they would be recreated immediately anyway), needs --delete-emptydir-data for Pods using temporary emptyDir storage, and --force for bare Pods that no controller would recreate. Remember to uncordon afterwards.

Disruptions and PodDisruptionBudgets

  • Involuntary disruptions are "unavoidable cases": hardware failure, a kernel panic, a VM deleted by mistake, a network partition, a node running out of resources.
  • Voluntary disruptions are caused by people: deleting or updating a Deployment, deleting a Pod, or an administrator draining a node.

A PodDisruptionBudget (PDB) "limits the number of Pods of a replicated application that are down simultaneously from voluntary disruptions". Drains respect it, so a drain waits rather than taking down too many copies at once.

api-pdb.yaml (PodDisruptionBudget) 
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: shop-api-pdb
spec:
  maxUnavailable: 1  # or minAvailable
  selector:
    matchLabels:
      app: shop-api

What a PDB does not cover. "Involuntary disruptions cannot be prevented by PDBs; however they do count against the budget." And "deleting deployments or pods bypasses Pod Disruption Budgets": they only apply to evictions, such as those made by kubectl drain. A PDB may set minAvailable or maxUnavailable, not both. The policy/v1 API has been stable since v1.21; policy/v1beta1 stopped being served in v1.25.

Protecting the control plane

Topic 1.2Backing up the cluster's data, keeping etcd available, and keeping the control plane's certificates valid.

"All Kubernetes objects are stored in etcd", so its backup is the cluster's backup. "Access to etcd is equivalent to root permission in the cluster", and by default the API server stores resources there "with no at-rest encryption" (encryption is covered in topic 2.2). Kubernetes v1.37 ships with etcd 3.7.

Back up and restore etcd 
# take a snapshot (etcdctl)
etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=ca.crt \
  --cert=server.crt --key=server.key \
  snapshot save snap.db

# check and restore it (etcdutl)
etcdutl snapshot status snap.db
etcdutl --data-dir /var/lib/etcd-new \
  snapshot restore snap.db

etcdctl snapshot restore is gone. Restoring and checking snapshots moved to etcdutl: the etcdctl versions were deprecated in etcd 3.5 and removed in 3.6. Older guides also set ETCDCTL_API=3, which has not been needed since etcd 3.4. Before restoring, stop all API servers.

etcd quorum

etcd runs as a cluster that needs a majority, or quorum, of "(n/2)+1" members to work. "You should run etcd as a cluster with an odd number of members", and five members are recommended for production:

MembersQuorumFailures tolerated
110
321
431 (no better than 3)
532

If most members fail, "Kubernetes cannot make any changes to its current state": running Pods may continue, but nothing new can be scheduled.

Certificates and access

Components talk over TLS using certificates. In kubeadm clusters, "client certificates generated by kubeadm expire after 1 year" (the CA lasts 10 years). kubeadm certs check-expiration shows what is due; every kubeadm upgrade renews them, and kubeadm certs renew all does it by hand. Kubelets rotate their own certificates.

Every API request passes three stages: authentication (who are you? failure gives HTTP 401), authorization (are you allowed? usually RBAC; failure gives 403), and admission control, modules that "can modify or reject requests", such as ResourceQuota and LimitRange. Workloads authenticate with a ServiceAccount, "a type of non-human account"; each namespace gets a default one. All of this is topic 2.2.

Extending the cluster

Topic 1.2Adding features to a cluster with add-ons, custom resources and operators, and knowing how new features mature.

  • Add-ons "extend the functionality of Kubernetes": a CNI network plugin (such as Calico, Cilium or Flannel), CoreDNS, and a web UI such as Headlamp. The classic Kubernetes Dashboard project is now archived.
  • metrics-server collects CPU and memory use from each kubelet and serves the Metrics API, used by kubectl top and autoscalers. In v1.37 the Metrics API became stable as metrics.k8s.io/v1. It offers "only ... the minimum CPU and memory metrics"; full monitoring is topic 4.1.
  • A custom resource is "an extension of the Kubernetes API that is not necessarily available in a default Kubernetes installation". A CustomResourceDefinition (CRD) adds one without programming; afterwards kubectl handles it like any built-in object.
  • Operators "are software extensions to Kubernetes that make use of custom resources to manage applications and their components", following "the control loop". An operator for shop-db could handle backups, upgrades and failover the way a human database administrator would.
  • Helm is "the package manager for Kubernetes"; Helm 4 was released in November 2025. Charts are covered in topic 3.1.

Feature gates and deprecation

StageDefaultWhat it means
AlphaOff"Might be buggy"; may be dropped "at any time without notice"; for short-lived test clusters
BetaUsually on (new beta APIs off since v1.24)"Well tested"; details may change but the feature will not be dropped
GA (stable)Always onCannot be disabled; the feature gate is no longer needed

Features are switched with --feature-gates=Name=true on each component. The deprecation policy promises that "GA API versions may be marked as deprecated, but must not be removed within a major version of Kubernetes", while beta APIs are removed within about three releases of being deprecated.

Key takeaways

  • kubeconfig (default ~/.kube/config, or a merged list in KUBECONFIG) holds clusters, users and contexts (cluster + user + namespace). kubectl must be within one minor version of the API server.
  • Three techniques: imperative commands, imperative object configuration (create, replace), declarative configuration (apply, diff). Never mix them on one object. replace drops fields not in your file; apply patches. Server-side apply tracks field owners; Kustomize (apply -k) layers overlays on a base.
  • ResourceQuota caps a namespace's total; LimitRange sets per-container limits and defaults. Violations get 403 Forbidden; a CPU or memory quota requires Pods to set requests or limits. Deleting a namespace deletes everything in it.
  • Tools: kubeadm (self-managed), kind and minikube (local), k3s (lightweight, CNCF Sandbox), managed services. About three releases a year; the latest three are supported for about 14 months each.
  • Skew: kubelet never newer than the API server, up to three versions older; controller manager and scheduler at most one older. Upgrade the control plane first, drain each node before its kubelet, and never skip a minor version.
  • cordon, drain --ignore-daemonsets, uncordon. PDBs limit voluntary evictions only; deleting Pods bypasses them.
  • etcd holds all cluster data: snapshot with etcdctl snapshot save, check and restore with etcdutl. Odd member counts; quorum (n/2)+1. kubeadm certificates last one year and are renewed by upgrades.
  • Extend with add-ons (CNI, CoreDNS, metrics-server), CRDs and operators. Feature stages: alpha off, beta usually on, GA always on.
