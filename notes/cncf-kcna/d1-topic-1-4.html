Overview

Topic 1.4

Containerization.

The CNCF Glossary defines containerization as "the process of packaging of application code including libraries and dependencies required to run the code into a single lightweight executable—called container image." This page takes the topic to cover what containers are, images and how they are built, the OCI standards, container runtimes and the CRI, and how Kubernetes pulls and runs images. Security policy for containers is topic 2.2; build pipelines are topic 3.1.

Quotes are from the Kubernetes documentation (© The Kubernetes Authors) and the CNCF Glossary, both CC BY 4.0, and from the Open Container Initiative and Docker documentation.

Running example. The web shop's shop-api is a small Go program. This page builds it into an image, pushes it to a private registry as ghcr.io/acme/shop-api:1.4.2 (an example name), and runs it in a Pod.

What a container is

Topic 1.4Explaining what makes a container different from a virtual machine, and the Linux features that make containers possible.

The CNCF Glossary: "A container is a running process with resource and capability constraints managed by a computer's operating system. The files available to the container process are packaged as a container image." Kubernetes adds: "Each container that you run is repeatable; the standardization from having dependencies included means that you get the same behavior wherever you run it."

The Kubernetes documentation tells the history in three eras:

EraHow apps ranProblem or benefit
TraditionalDirectly on physical servers"No way to define resource boundaries"; one app could starve the others, and one server per app was expensive
VirtualizedMany virtual machines on one serverIsolation and better use of hardware, but "each VM is a full machine running all the components, including its own operating system"
ContainerMany containers on one operating system"Relaxed isolation properties to share the Operating System (OS) among the applications. Therefore, containers are considered lightweight."

A container still has "its own filesystem, share of CPU, memory, process space, and more". This comes from features of the Linux kernel: namespaces give each container its own view of processes, network and files, and cgroups (control groups), a kernel feature that "limits, accounts for, and isolates the resource usage (CPU, memory, disk I/O, network) for a collection of processes". A layered (union) filesystem lets many containers share the same image files.

Containers share the host's kernel. That is what makes them light, and also their main weakness: the CNCF Glossary notes that "since containers share the same operating system, processes can be considered less secure than alternatives." A virtual machine has its own kernel. Sandboxed runtimes such as gVisor and Kata Containers (see below) sit between the two.

cgroup v1 is deprecated. Since v1.35 the kubelet will not start on a cgroup v1 node by default (failCgroupV1 defaults to true); cgroup v2, stable since v1.25, is now the norm. cgroup v1 is deprecated rather than removed: an override still exists in v1.37, but removal is planned.

Containers are also immutable: "you should not change the code of a container that is already running." To change an app, "build a new image that includes the change, then recreate the container". The CNCF Glossary calls containers "a good example of immutable infrastructure".

Container images

Topic 1.4Naming images precisely, and knowing why a digest is safer than a tag.

"A container image is a ready-to-run software package containing everything needed to run an application: the code and any runtime it requires, application and system libraries, and default values for any essential settings." Images are built from read-only layers, each a set of filesystem changes, and are stored in and pulled from a registry.

A full image reference is registry/repository:tag@digest. The parts you leave out get defaults:

You writeKubernetes uses
busyboxdocker.io/library/busybox:latest: the Docker public registry and the latest tag
busybox:1.32.0docker.io/library/busybox:1.32.0
registry.k8s.io/pause:3.5A specific registry and tag
registry.k8s.io/pause@sha256:...An exact image, identified by its content hash
A tag and a digest together"Only the digest will be used for pulling"

Tags move; digests do not. "Digests are hashes of the image's content, and are immutable. Tags can be moved to point to different images, but digests are fixed." If someone re-pushes a tag, you could end up with "a mix of Pods running the old and new code". The documentation advises avoiding :latest in production, since "it is harder to track which version of the image is running and more difficult to roll back".

One name can serve several CPU architectures: a registry can return an image index that points to an amd64, an arm64 and other versions, and each node pulls the one it needs.

Open standards: OCI

Topic 1.4Knowing which open specifications let images built by one tool run under another.

The Open Container Initiative (OCI) is "a lightweight, open governance structure (project), formed under the auspices of the Linux Foundation, for the express purpose of creating open industry standards around container formats and runtimes", launched in June 2015. It maintains three specifications:

SpecificationDefinesLatest version
Image specWhat an image is: "an image manifest, an image index (optional), a set of filesystem layers, and a configuration"v1.1.1 (March 2025)
Runtime spec"The configuration, execution environment, and lifecycle of a container", from an unpacked "filesystem bundle"v1.3.0 (November 2025)
Distribution spec"An API protocol to facilitate and standardize the distribution of content": how registries push and pullv1.1.1 (January 2025)

Docker donated its runtime, runc, to the OCI as the reference implementation of the runtime spec; it is "the underlying default runtime for both containerd and CRI-O." The image format can also carry non-image content, called OCI artifacts, such as signatures or configuration bundles.

Why it matters. "The image that Docker produces isn't really a Docker-specific image—it's an OCI (Open Container Initiative) image. Any OCI-compliant image, regardless of the tool you use to build it, will look the same to Kubernetes."

Building images

Topic 1.4Writing a small, cache-friendly Dockerfile and knowing the other tools that build OCI images.

"A Dockerfile is a text document that contains all the commands a user could call on the command line to assemble an image." This one uses a multi-stage build: the first stage has the full Go toolchain; the final image contains only the compiled program.

Dockerfile (shop-api) 
# build stage: full Go toolchain
FROM golang:1.25 AS build
WORKDIR /src
# dependencies first: cached until
# go.mod changes
COPY go.mod go.sum ./
RUN go mod download
# then the source, which changes often
COPY . .
RUN CGO_ENABLED=0 go build \
    -o /out/shop-api ./cmd/api

# runtime stage: tiny, no shell
FROM gcr.io/distroless/static-debian13
COPY --from=build /out/shop-api /shop-api
# run as a non-root user ID
USER 65532:65532
# documentation only: publishes nothing
EXPOSE 8080
ENTRYPOINT ["/shop-api"]
CMD ["--port=8080"]
InstructionPurpose (Docker reference)
FROM"Create a new build stage from a base image"; a Dockerfile must start with it
RUN"Execute build commands", creating a new layer
COPY"Copy files and directories"; --from copies from another stage
WORKDIR, ENV, USERSet the working directory, environment variables, and the user that runs the process
EXPOSE"Doesn't actually publish the port": documents which port the app listens on
ENTRYPOINT"Specify default executable"
CMD"Specify default commands": default arguments, easy to override
  • Layer caching: "Once a layer changes, then all downstream layers need to be rebuilt as well." Copying go.mod and downloading dependencies before copying the source means a code change does not re-download everything.
  • Small base images such as distroless or Alpine download faster and contain fewer vulnerabilities. Distroless images "do not contain package managers, shells or any other programs".
  • A .dockerignore file keeps files such as .git or .env out of the build.
  • Never pass secrets as build arguments or ENV: "they persist in the final image".
Build and push (Podman uses the same syntax) 
docker build -t \
  ghcr.io/acme/shop-api:1.4.2 .
docker push \
  ghcr.io/acme/shop-api:1.4.2

Other build tools

ToolNotes
BuildKit"The builder backend used by Docker", with parallel stages and better caching
Podman and BuildahBuild and run images "without requiring a daemon or root privileges"; CNCF Sandbox (as Podman Container Tools) since January 2025
Cloud Native BuildpacksTurn source code into images with no Dockerfile; graduated in CNCF in July 2026
kanikoBuilds inside a container without Docker; Google archived the original project in June 2025 (a community fork continues)

Container runtimes and the CRI

Topic 1.4Knowing how the kubelet talks to container runtimes, which runtimes exist, and why Kubernetes no longer needs Docker.

"You need a working container runtime on each Node in your cluster, so that the kubelet can launch Pods and their containers." The kubelet talks to it through the Container Runtime Interface: "The CRI is a plugin interface which enables the kubelet to use a wide variety of container runtimes, without having a need to recompile the cluster components." It is a gRPC API, stable since v1.23; since v1.26 runtimes must support CRI v1.

LayerExamplesRole
High-level (CRI) runtimecontainerd (CNCF graduated 2019), CRI-O (CNCF graduated 2023)Pull and store images, manage containers, answer the kubelet over CRI
Low-level (OCI) runtimerunc (the default), crunActually create the container from an OCI bundle
Sandboxed runtimegVisor (runsc), Kata ContainersExtra isolation: a user-space kernel, or lightweight VMs that "feel and perform like containers"

dockershim was removed in v1.24. Kubernetes once talked to Docker Engine through a built-in adapter called dockershim. It was deprecated in v1.20 and removed in v1.24, so clusters now use a CRI runtime such as containerd or CRI-O (Docker Engine needs the separate cri-dockerd adapter). This did not break images: "the images produced from docker build will work with all CRI implementations."

containerd 1.x is finished. Kubernetes v1.35 was "the last release to support the containerd v1.X series"; v1.36 and v1.37 need containerd 2.x, and containerd 1.7 reached end of life on September 30, 2026.

RuntimeClass

"RuntimeClass is a feature for selecting the container runtime configuration", stable since v1.20. It is useful when, for example, untrusted code should run in a sandboxed runtime while everything else uses runc. It is cluster-wide and has two main fields, a name and a handler that matches the runtime's configuration:

sandboxed.yaml (RuntimeClass) 
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: sandboxed
handler: runsc   # runtime config name

A Pod opts in with spec.runtimeClassName: sandboxed. If the class does not exist or the runtime cannot run its handler, "the pod will enter the Failed terminal phase".

Cgroup drivers must match. "It's critical that the kubelet and the container runtime use the same cgroup driver". "The systemd cgroup driver is recommended if you use cgroup v2", and since v1.34 the kubelet detects the driver from the runtime automatically.

crictl: looking at the runtime directly

"crictl is a command-line interface for CRI-compatible container runtimes. You can use it to inspect and debug container runtimes and applications on a Kubernetes node." It only sees the node you run it on.

On a node 
crictl pods            # Pod sandboxes
crictl ps -a           # all containers
crictl images          # images on node
crictl logs <container-id>

Running images in Pods

Topic 1.4Controlling when images are pulled, pulling from private registries, and overriding an image's entrypoint and arguments.

shop-api Pod 
apiVersion: v1
kind: Pod
metadata:
  name: shop-api
spec:
  imagePullSecrets:
  - name: regcred      # same namespace
  containers:
  - name: api
    image: ghcr.io/acme/shop-api:1.4.2
    imagePullPolicy: IfNotPresent
    args: ["--port=8080", "--log=json"]
    ports:
    - containerPort: 8080
    env:
    - name: SHOP_ENV
      value: prod

Pull policy

PolicyBehaviour
IfNotPresent"The image is pulled only if it is not already present locally"
AlwaysThe runtime checks the registry every time a container starts, downloading only layers it does not already have
NeverNever pulls; startup fails if the image is not already on the node

If you omit the field, it is set when the object is created: Always if the tag is :latest or there is no tag, otherwise IfNotPresent (including when you give a digest). It is "not updated if the image's tag or digest later changes".

Pull failures. A wrong image name or a missing credential first shows ErrImagePull, then ImagePullBackOff: "Kubernetes will keep trying to pull the image, with an increasing back-off delay", up to 300 seconds. "The most common cause of Waiting pods is a failure to pull the image." Diagnosing it is topic 3.2.

Private registries

imagePullSecrets is "the recommended approach to run containers based on images in private registries". The Secret must be "in the same namespace as the Pod" and of type kubernetes.io/dockerconfigjson:

Create the pull secret 
kubectl create secret docker-registry \
  regcred \
  --docker-server=ghcr.io \
  --docker-username=ci-bot \
  --docker-password='<token>'

Since v1.35 the kubelet also checks credentials for images already cached on a node (beta, on by default), so a Pod without the right secret cannot simply reuse a private image another Pod pulled.

command and args

"The command field corresponds to ENTRYPOINT, and the args field corresponds to CMD". What runs:

In the PodWhat runs
NeitherThe image's ENTRYPOINT plus its CMD
args onlyThe image's ENTRYPOINT with your args (the shop-api Pod above)
command onlyYour command alone; the image's CMD is dropped too
BothYour command with your args

Other container settings: env sets variables one by one and envFrom loads all keys of a ConfigMap or Secret; both "override any environment variables specified in the container image". Listing ports is informational: "Not specifying a port here DOES NOT prevent that port from being exposed." Lifecycle hooks run a command or HTTP call just after start (PostStart) or before stop (PreStop), and probes check health (topic 3.2).

Images as volumes. Since v1.36 (stable), an image volume can mount an OCI image or artifact read-only into a Pod, for example to ship data or a model separately from the application image.

Container security basics

Topic 1.4Building and running containers so that a compromised app does as little damage as possible.

Kubernetes' application security checklist starts with the container itself (policies to enforce these are topic 2.2):

  • "Set runAsNonRoot: true" and build images with a non-root USER.
  • "Configure the root filesystem to be read-only with readOnlyRootFilesystem: true."
  • "Disable privilege escalations using allowPrivilegeEscalation: false", avoid privileged containers, and drop Linux capabilities you do not need.
  • Scan images for known vulnerabilities, and "use container signing to validate the container image signature before deploying".

User namespaces became stable in v1.36: with spec.hostUsers: false, root inside the container maps to an unprivileged user on the host, so "even if a process escapes the container, it possesses no administrative power over the underlying node."

Who owns the signing tools. Sigstore and its cosign client are an OpenSSF project, not CNCF; Kubernetes itself signs its release artifacts with cosign. CNCF projects in this space include Notary Project (incubating), in-toto and Harbor (both graduated).

Key takeaways

  • A container is an isolated process sharing the host's kernel, built on Linux namespaces and cgroups; a VM runs its own operating system. cgroup v2 is required by default since v1.35. Containers are immutable: rebuild, don't patch.
  • An image is layers plus configuration, named registry/repository:tag@digest. No registry means Docker Hub; no tag means latest. Tags move, digests don't.
  • OCI specs: image, runtime and distribution; runc is the reference runtime. Any OCI image runs under any compliant runtime.
  • Dockerfiles: FROM, RUN, COPY, USER, ENTRYPOINT (executable), CMD (default arguments); EXPOSE only documents. Use multi-stage builds, small bases, cache-friendly order, no secrets in build args.
  • The kubelet uses the CRI to talk to containerd or CRI-O, which use runc. dockershim was removed in v1.24, yet Docker-built images still work. containerd 2.x is required from v1.36.
  • RuntimeClass (stable v1.20) selects a runtime handler, such as a sandbox. The kubelet and runtime must use the same cgroup driver. crictl inspects one node's runtime.
  • Pull policy defaults: Always for :latest or no tag, otherwise IfNotPresent. ErrImagePull then ImagePullBackOff. Private images need an imagePullSecrets Secret in the Pod's namespace.
  • command replaces ENTRYPOINT (and drops CMD); args replaces CMD. Run as non-root with a read-only filesystem; user namespaces are stable since v1.36.
