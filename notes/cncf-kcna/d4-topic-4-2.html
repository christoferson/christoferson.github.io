What cloud native means

Topic 4.2Stating the CNCF's current definition of cloud native, and what it does and does not require.

The CNCF Cloud Native Definition, version 1.1 (approved by the TOC and Governing Board in February 2024), begins: "Cloud native practices empower organizations to develop, build, and deploy workloads in computing environments (public, private, hybrid cloud) to meet their organizational needs at scale in a programmatic and repeatable manner." It is "characterized by loosely coupled systems that interoperate in a manner that is secure, resilient, manageable, sustainable, and observable."

Technologies typically include "some combination of containers, service meshes, multi-tenancy, microservices, immutable infrastructure, serverless, and declarative APIs — this list is non-exhaustive." The benefit: "Combined with robust automation, cloud native practices allow organizations to make high-impact changes frequently, predictably, with minimal toil".

Version 1.0 wording is still everywhere. Many courses, and even the CNCF Glossary entry "Cloud Native Technology", still quote the 2018 version 1.0: "technologies" that "build and run scalable applications in modern, dynamic environments" and "loosely coupled systems that are resilient, manageable, and observable". Version 1.1 says practices, adds secure and sustainable, and adds multi-tenancy and serverless to the list.

Cloud native is not "containers" or "public cloud". The definition covers "public, private, hybrid cloud", calls itself a set of practices, and says its technology list is non-exhaustive. Running a monolith in a container on a cloud VM does not make it cloud native; designing loosely coupled, automated, observable systems does.

Architecture principles

Topic 4.2Recognizing the design choices that make an application cloud native, and their trade-offs.

MonolithMicroservices
Definition (CNCF Glossary)"Contains all functionality in a single deployable program""Breaks applications into individual independent (micro)services, with each service focused on a specific functionality"
Strength"Often the simplest and easiest place to start""Easier to deploy, update, and scale independently"
WeaknessHard to maintain as it grows, with more conflicting changes"Operational overhead": many more things to deploy and track
  • Loose coupling: components "built independently from one another", so a change in one does not force changes in others. Tight coupling "can leave a system more vulnerable to cascading failures".
  • Stateless where possible: stateless apps "handle each request independently"; stateful ones need storage "accessible from anywhere" (topic 2.4).
  • Immutable infrastructure: infrastructure "that cannot be changed once deployed"; change means a new image, not a patch.
  • Declarative APIs and self-healing: a self-healing system has "a 'convergence' or 'control' loop that actively looks at the system's actual state and compares it to the state that the operators initially desired" (topic 1.1).
  • Automation: infrastructure as code, CI/CD and GitOps (topic 3.1) make change repeatable.

A popular way to say this is "pets versus cattle": servers used to be treated like pets, each unique, hand-built and nursed back to health; cloud native systems treat them like cattle, built by automation, interchangeable, and replaced rather than repaired when they fail.

The twelve-factor app

A set of principles for building services, written at Heroku and still widely cited:

FactorPrinciple
I. CodebaseOne codebase tracked in revision control, many deploys
II. DependenciesExplicitly declare and isolate dependencies
III. ConfigStore config in the environment
IV. Backing servicesTreat backing services as attached resources
V. Build, release, runStrictly separate build and run stages
VI. ProcessesExecute the app as one or more stateless processes
VII. Port bindingExport services via port binding
VIII. ConcurrencyScale out via the process model
IX. DisposabilityMaximize robustness with fast startup and graceful shutdown
X. Dev/prod parityKeep development, staging, and production as similar as possible
XI. LogsTreat logs as event streams
XII. Admin processesRun admin/management tasks as one-off processes

Many map directly onto Kubernetes: config in ConfigMaps and Secrets (III), stateless Pods behind Services (VI), scaling replicas (VIII), graceful termination and probes (IX), and logs to stdout (XI).

Autoscaling

Topic 4.2Matching capacity to demand automatically, by adding Pods, resizing them, or adding nodes.

"When you scale a workload, you can either increase or decrease the number of replicas managed by the workload, or adjust the resources available to the replicas in-place. The first approach is referred to as horizontal scaling, while the second is referred to as vertical scaling."

AutoscalerScalesNotes
HorizontalPodAutoscaler (HPA)Number of replicasBuilt in (autoscaling/v2); uses metrics-server for CPU and memory
VerticalPodAutoscaler (VPA)CPU and memory requestsAn add-on, "also known as rightsizing"
Cluster Autoscaler, KarpenterNumber of nodes"The two Node autoscalers currently sponsored by SIG Autoscaling"
KEDAReplicas, from eventsCNCF graduated; scales on queue length or schedules, "including to/from zero"

HorizontalPodAutoscaler

shop-web-hpa.yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: shop-web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: shop-web
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
The same with kubectl 
kubectl autoscale deploy shop-web \
  --min=2 --max=10 --cpu=70%

Every 15 seconds the HPA computes desiredReplicas = ceil[currentReplicas * (currentMetricValue / desiredMetricValue)], ignoring changes within a 10% tolerance and waiting 5 minutes before scaling down. Current kubectl uses --cpu (older guides show --cpu-percent).

HPA needs requests and metrics. "If some of the Pod's containers do not have the relevant resource request set, CPU utilization for the Pod will not be defined and the autoscaler will not take any action". CPU and memory metrics come from metrics-server, "which needs to be launched separately". The HPA "does not apply to objects that can't be scaled (for example: a DaemonSet.)" Scaling to zero replicas works only on object or external metrics (beta and on by default in v1.37).

VerticalPodAutoscaler

The VPA has a recommender, an updater and an admission webhook, and an updateMode: Off (recommend only), Initial (set requests when Pods are created), Recreate (evict Pods to apply new requests), or InPlaceOrRecreate (resize running Pods when possible, using in-place resize, stable in Kubernetes since v1.35). The older Auto mode is deprecated and now means Recreate.

Do not point VPA and HPA at the same metric. The VPA project warns it "should not be used with the Horizontal Pod Autoscaler (HPA) on the same resource metric (CPU or memory)". Using VPA on memory and HPA on CPU, or HPA on custom metrics, is fine.

For nodes, the Cluster Autoscaler "adds or removes Nodes to pre-configured Node groups", while Karpenter "auto-provisions Nodes based on NodePool configurations" and works with individual VMs. When consolidating, they consider "Pod resource requests and not real resource usage".

Serverless and events

Topic 4.2Explaining serverless and functions as a service, and the CNCF projects that bring them to Kubernetes.

  • Serverless "abstracts servers away from the user. Operational management falls to the service provider", charges "are based on a pay-per-use model", and scaling is automatic. Providers "can be public cloud entities or internal IT departments".
  • Function as a Service runs "event-triggered functions" that "operate on a short-term basis, and then shut down", with no cost while idle.
  • Event-driven architecture "promotes the creation, processing, and consumption of events", where "an event is any change to an application's state".

Serverless still runs on servers, run by someone else. And "although 'serverless' and 'FaaS' are often used as interchangeable terms, they embody distinct concepts": serverless spans services "from Platform-as-a-Service (PaaS) to Software-as-a-Service (SaaS)", while FaaS is specifically short-lived functions.

ProjectWhat it doesCNCF status
Knative"A Kubernetes-based platform ... for building, deploying, and managing modern serverless workloads": Serving (HTTP services that scale automatically, including to zero), Eventing (CloudEvents routing) and FunctionsGraduated (2025)
CloudEvents"A specification for describing event data in common formats"; every event has id, source, specversion and typeGraduated (2024)
KEDAEvent-driven autoscaling of ordinary DeploymentsGraduated (2023)
Dapr"A runtime for building distributed applications, workflows, and AI agents", with state, messaging and service-to-service APIsGraduated (2024)
wasmCloud, SpinKubeRunning WebAssembly applications, "a portable target for compiling high-level languages"Incubating; Sandbox

Older material lists only Serving and Eventing for Knative; its current documentation names three components. For the web shop, an order-confirmation function could run on Knative and scale to zero overnight.

Open standards

Topic 4.2Knowing the interfaces that let cloud native parts be swapped, and who maintains each.

Portability "helps to avoid 'lock-in' to certain operating environments, e.g. cloud providers, operating systems or vendors". Kubernetes achieves much of it through pluggable, standard interfaces:

StandardDefinesMaintained by
OCI specsContainer images, runtimes and registries (topic 1.4)Open Container Initiative, a Linux Foundation project (not CNCF)
CRIHow the kubelet talks to container runtimesKubernetes
CNIHow networks are attached to containers (topic 2.1)CNCF, still incubating
CSIHow storage systems plug in (topic 2.4)CSI community, SIG Storage

OTLPTelemetry data (topic 4.1)OpenTelemetry, CNCF graduated

Two earlier standards are archived: Service Mesh Interface (September 2023) and OpenMetrics (July 2024, merged into Prometheus).

How the CNCF ecosystem works

Topic 4.2Explaining how CNCF projects mature, how the Landscape maps the ecosystem, and what Certified Kubernetes means.

"CNCF is part of the nonprofit Linux Foundation", announced on July 21, 2015. Kubernetes was its first hosted project (March 2016) and became its first graduate (March 2018). Projects move through four stages decided by the Technical Oversight Committee (TOC):

StageMeaning (CNCF TOC)
Sandbox"Experimental or innovative projects early in their development"; "failure is a possibility", though some are used in production
Incubating"Projects gaining adoption, focusing on improving stability and maturity"
Graduated"Highly mature, robust projects whose adopters have demonstrated their production-readiness"
Archived"Inactive or low activity projects" no longer supported by the TOC

Projects can apply to Sandbox or directly for Incubation. Moving up involves adopter interviews, technical and governance reviews, a two-week public comment period and a two-thirds TOC vote. Graduation requires, among other things, maintainers "from at least 2 organizations", a "Third Party Security Review", the OpenSSF Best Practices passing badge (which replaced the older CII badge) and at least three adopters in production. An archived project "can not actively advertise being a CNCF project any more".

In November 2026 the CNCF hosts about 230 projects: roughly 40 graduated, 37 incubating and 150 sandbox, with 28 archived. Recent graduates include OpenTelemetry, Kubeflow, Karmada and KubeVirt (all 2026).

The CNCF Landscape

The CNCF Landscape "is intended as a map through the previously uncharted terrain of cloud native technologies", covering CNCF projects and many other open source and commercial products. Its main categories are Provisioning, Runtime, Orchestration & Management, App Definition and Development, Platform, Serverless and Observability and Analysis; newer ones cover WebAssembly and AI.

On the Landscape is not the same as a CNCF project. The Landscape lists products and projects from everywhere (open source projects generally need 300 GitHub stars); only those with a Sandbox, Incubating or Graduated status are hosted by the CNCF. Grafana and Zipkin appear on it, for example, but are not CNCF projects.

Certified Kubernetes

"Software conformance ensures that every vendor's version of Kubernetes supports the required APIs". The CNCF runs the Certified Kubernetes program, with "over 90" certified offerings, tested with Sonobuoy or Hydrophone and recertified at least yearly. It distinguishes a distribution ("installed by an end user ... and includes patches to the upstream codebase"), a hosted platform ("provided and managed by a vendor") and an installer (installs "vanilla upstream Kubernetes"). A newer Kubernetes AI Conformance program covers AI and ML workloads.

Certified is not graduated. Certified Kubernetes means a vendor's product passed the conformance tests; graduation is a TOC decision about an open source project's maturity.

Sustainability

Version 1.1 of the definition added sustainable to cloud native's qualities. In the CNCF, the former TAG Environmental Sustainability was archived in the 2025 TAG restructure; its work continues in a Technical Community Group and the Green Reviews subproject under TAG Operational Resilience. Kepler (CNCF Sandbox) measures energy use per container, Pod and node, and the separate Green Software Foundation, also under the Linux Foundation, promotes green software practices. Efficient scaling and right-sized requests (topic 4.1) are the everyday levers.

Key takeaways

  • Cloud Native Definition v1.1 (2024): practices to build and run workloads "at scale in a programmatic and repeatable manner" in public, private or hybrid cloud; loosely coupled systems that are secure, resilient, manageable, sustainable and observable; typical technologies include containers, service meshes, multi-tenancy, microservices, immutable infrastructure, serverless and declarative APIs. v1.0 (2018) wording is outdated.
  • Principles: microservices (independent deploy and scale, more overhead) vs monolith; loose coupling; stateless processes; immutable infrastructure; declarative APIs with self-healing control loops; automation; cattle, not pets; the twelve factors.
  • Autoscaling: HPA (replicas; needs requests and metrics-server; not for DaemonSets), VPA (requests; add-on; Off, Initial, Recreate, InPlaceOrRecreate; not on the same metric as HPA), Cluster Autoscaler and Karpenter (nodes), KEDA (events, to and from zero).
  • Serverless = provider-managed servers, pay per use, automatic scaling; FaaS = short-lived event-triggered functions. Knative (Serving, Eventing, Functions), CloudEvents, Dapr are graduated.
  • Open standards for portability: OCI (Linux Foundation), CRI, CNI (CNCF incubating), CSI, Gateway API, OTLP, CloudEvents. SMI and OpenMetrics are archived.
  • CNCF (Linux Foundation, 2015): Sandbox → Incubating → Graduated, or Archived, by TOC vote; graduation needs multi-organization maintainers, a third-party security review, the OpenSSF badge and production adopters. The Landscape maps everything, not only CNCF projects. Certified Kubernetes certifies products, not project maturity.
  • Extensions: Crossplane, Cluster API, Karmada, KubeEdge, KubeVirt, Kubeflow. Sustainability is now part of the definition.
