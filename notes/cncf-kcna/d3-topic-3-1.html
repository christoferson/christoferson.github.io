Topic 3.1

Application Delivery.

The earlier curriculum named GitOps and CI/CD separately; the November 2025 version folds them into this one bullet. This page takes it to cover CI/CD, release strategies, packaging with Helm and Kustomize, GitOps, and the tools and practices that support delivery. The basics of Deployments and rollbacks are in topic 1.1, and declarative management in topic 1.2; debugging a release that goes wrong is topic 3.2.

Quotes are from the CNCF Glossary, the Kubernetes documentation (© The Kubernetes Authors) and the Helm documentation, all CC BY 4.0, and from the OpenGitOps, Argo and Flux projects.

Running example. The web shop's manifests live in a Git repository. Each code change is built into an image, tested, and rolled out first to staging and then to production, where a new version of shop-web should reach a small share of customers before everyone.

CI, CD and DevOps

Topic 3.1Telling apart continuous integration, continuous delivery and continuous deployment, and the culture they come from.

TermCNCF Glossary
Continuous integration (CI)"The practice of integrating code changes as regularly as possible", ending "with a tested artifact ready to be consumed by a CD system"
Continuous delivery (CD)"Code changes are automatically deployed into an acceptance environment", with testing and "a way to rollback changes if deemed necessary"
Continuous deployment (CD)"Goes a step further than continuous delivery by deploying finished software directly to production"
DevOps"A methodology in which teams own the entire process from application development to production operations"; it "requires a complete shift in culture and processes"
Infrastructure as code"Storing the definition of infrastructure as one or more files"

Two meanings of "CD". Continuous delivery automates up to an acceptance environment, with a release to production that can still be a decision; continuous deployment pushes every passing change to production automatically. "CI is a prerequisite for continuous delivery."

  1. CommitA developer pushes a change to shop-web.
  2. CIThe pipeline runs tests, builds an image and pushes it, tagged 1.4.3, to the registry.
  3. CD to stagingThe manifests for staging are updated to the new image and deployed automatically.
  4. ProductionAfter approval (continuous delivery) or automatically (continuous deployment), production gets the same image, often through a canary first.

Release strategies

Topic 3.1Choosing how a new version replaces the old one, from simple rolling updates to traffic-controlled canaries.

StrategyHow it worksIn Kubernetes
Rolling update"Gradually scale down the old ReplicaSets and scale up the new one"The Deployment default
Recreate"All existing Pods are killed before new ones are created"strategy.type: Recreate
Blue-greenTwo full environments; traffic is "switched over (often via the use of a load balancer)" once the new one is testedTwo Deployments, then switch the Service or route to the new one
Canary"Traffic is gradually moved from the original version of the application to the updated version", for example 1%, then 10%, 25%Two Deployments behind one Service, or weighted routes

Only two strategies are built in. A Deployment's strategy.type "can be 'Recreate' or 'RollingUpdate'". Blue-green and canary are patterns built from several objects or extra tools. And a rollout starts only when .spec.template changes, as topic 1.1 explained.

A canary with plain Kubernetes

The Kubernetes documentation uses a track label: a stable Deployment with 3 replicas (track: stable) and a canary Deployment with 1 replica (track: canary) of the new image. "The frontend service would span both sets of replicas by selecting the common subset of their labels (i.e. omitting the track label)", so about a quarter of requests reach the canary. "Once you're confident, you can update the stable track to the new application release and remove the canary one."

Weighted traffic with the Gateway API

Replica ratios tie the traffic share to Pod counts. An HTTPRoute can split traffic by weight instead:

90/10 split between versions 
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
spec:
  parentRefs:
  - name: shop-gw
  rules:
  - backendRefs:
    - name: shop-web-v1   # stable
      port: 80
      weight: 90
    - name: shop-web-v2   # canary
      port: 80
      weight: 10

"weight indicates a proportional split of traffic (rather than percentage)", defaulting to 1. If the new version misbehaves, "the weights can be updated to quickly shift traffic back".

Progressive delivery tools

  • Argo Rollouts (part of the graduated Argo project) is "a Kubernetes controller and set of CRDs which provide advanced deployment capabilities such as blue-green, canary, canary analysis, experimentation, and progressive delivery". It addresses rolling updates' limits, such as having no "ability to query external metrics to verify an update".
  • Flagger (part of the graduated Flux project) "automates the release process ... by gradually shifting traffic to the new version while measuring metrics and running conformance tests", with canary, A/B testing and blue-green strategies.

Blue-green in cloud native terms. The CNCF Glossary notes that blue-green "usually means switching the entire environments", and that for cloud native systems its use "is normally a 'smell' that legacy software needs to be re-engineered so that components can be updated individually". For single services the preferred term is "zero-downtime deployment".

Packaging with Helm

Topic 3.1Packaging an application's manifests as a versioned chart that can be installed, upgraded and rolled back.

"Helm is the package manager for Kubernetes. It helps you define, install, and upgrade applications on a Kubernetes cluster". Helm is a CNCF graduated project (2020). Three components describe it:

ComponentHelm documentation
Chart"A Helm package. It contains all of the resource definitions needed to run an application", like "a Homebrew formula, an apt dpkg, or a yum RPM file"
Repository"The place where charts are collected and shared"; OCI container registries are recommended
Release"An instance of a chart running in a Kubernetes cluster"; each install creates a new release, and each change a new numbered revision

A chart is a directory with a required Chart.yaml (name, version, apiVersion: v2), default settings in values.yaml, and templates/ that, "combined with values, will generate valid Kubernetes manifest files".

Release the web shop chart 
# install, then upgrade with new values
helm install web ./webshop -n shop \
  -f prod-values.yaml
helm upgrade web ./webshop -n shop \
  --set image.tag=1.4.3

# revisions, and go back to revision 1
helm history web -n shop
helm rollback web 1 -n shop

# render locally without installing
helm template web ./webshop

# publish to an OCI registry
helm package ./webshop
helm push webshop-0.1.0.tgz \
  oci://reg.example.com/charts

Values can come from several -f files ("the rightmost file will take precedence") and --set, which has "higher precedence" still. "Helm stores release information in Kubernetes Secrets inside the cluster, so it does not need its own database."

Helm 4, and no more Tiller. Helm 4.0 was released on November 12, 2025, "the first new major version of Helm in 6 years". New releases use server-side apply by default, --atomic became --rollback-on-failure, plugins can run on WebAssembly, and "charts deployable with Helm 3 should be deployable by Helm 4". Helm 3 gets security fixes only until February 10, 2027. Material about Helm 2's in-cluster Tiller component is long out of date: Helm 3 chose "to completely remove Tiller".

GitOps

Topic 3.1Keeping the cluster in step with Git automatically, with an agent that pulls changes and corrects drift.

The CNCF Glossary: "GitOps is a set of practices for managing software applications and infrastructure by continuously evaluating and reconciling their desired states as defined in a version control system such as Git against their actual state." The CNCF Sandbox project OpenGitOps defines four principles (version 1.0.0, 2021). The desired state of a GitOps-managed system must be:

  1. Declarative"A system managed by GitOps must have its desired state expressed declaratively."
  2. Versioned and immutable"Desired state is stored in a way that enforces immutability, versioning and retains a complete version history."
  3. Pulled automatically"Software agents automatically pull the desired state declarations from the source."
  4. Continuously reconciled"Software agents continuously observe actual system state and attempt to apply the desired state."

GitOps pulls; classic CI/CD pushes. In a push model, the CI pipeline holds cluster credentials and runs kubectl or helm against the cluster. In GitOps, an agent inside the cluster pulls from Git; OpenGitOps explains the agents "must be able to access the desired state from the state store at any time". With Argo CD, "CI/CD pipelines no longer need direct access ... Instead, the pipeline makes a commit and push to the Git repository". Correcting a manual change is called fixing drift.

Argo CD

"Argo CD is a declarative, GitOps continuous delivery tool for Kubernetes", "implemented as a Kubernetes controller which continuously monitors running applications and compares the current, live state against the desired target state". An application whose live state differs is OutOfSync. Argo graduated in CNCF in December 2022.

webshop Application (Argo CD) 
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: webshop
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/shop
    targetRevision: main
    path: deploy/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true      # delete removed
      selfHeal: true   # undo drift

Automated sync is cautious by default. "By default (and as a safety mechanism), automated sync will not delete resources" removed from Git, and "changes that are made to the live cluster will not trigger automated sync". Set prune and selfHeal to get both.

Flux

"Flux is a tool for keeping Kubernetes clusters in sync with sources of configuration (like Git repositories), and automating updates to configuration when there is new code to deploy." It is built as a toolkit of controllers; Flux graduated in CNCF in November 2022 and remains actively developed (v2.10, October 2026).

Source and Kustomization (Flux) 
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: shop
  namespace: flux-system
spec:
  interval: 1m        # poll Git
  url: https://git.example.com/shop
  ref:
    branch: main
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: shop
  namespace: flux-system
spec:
  interval: 10m       # reconcile
  path: ./deploy/prod
  prune: true
  sourceRef:
    kind: GitRepository
    name: shop

Flux reconciles on its interval, and "if you make any changes to the cluster using kubectl edit/patch/delete, they will be promptly reverted". Sources can also be Helm repositories, buckets or OCI registries.

Some names have changed. Keptn was archived in September 2025. The CNCF's TAG App Delivery, which wrote the platforms white paper, was retired in the 2025 TAG restructure; delivery topics now sit mainly with TAG Workloads Foundation and TAG Developer Experience.

Platform engineering

"Platform engineering is the art of building tools and processes that empower software developers", like "a self-service station specifically designed to meet developers' needs". The CNCF platforms white paper (2023) describes a platform as "an integrated collection of capabilities defined and presented according to the needs of the platform's users", with "Web portals, project templates, and self-service APIs". For the web shop, that could mean a Backstage portal where a developer creates a new service from a template that already includes a Helm chart, a pipeline and an Argo CD Application.

Release practices

  • Version images and promote the same artifact. Avoid :latest in production; "specify a meaningful tag such as v1.42.0 and/or a digest". The image tested in staging is the one promoted to production, by changing its reference in Git.
  • Semantic versioning: MAJOR for incompatible changes, MINOR for backward-compatible features, PATCH for fixes.
  • Separate config from code. The twelve-factor app requires "strict separation of config from code"; in Kubernetes, config lives in ConfigMaps and Secrets per environment.
  • Immutable releases. Twelve-factor again: "a release cannot be mutated once it is created. Any change must create a new release."
  • Feature flags let code ship turned off and be enabled gradually, separating deployment from release.

Key takeaways

  • CI integrates and tests every change into an artifact; continuous delivery deploys automatically to an acceptance environment; continuous deployment goes all the way to production.
  • Built-in Deployment strategies: RollingUpdate (default) and Recreate (old Pods first). Blue-green and canary are patterns: two Deployments with a track label, or Gateway API weights. Argo Rollouts and Flagger automate progressive delivery with metrics.
  • Helm: charts, repositories, releases with numbered revisions; install, upgrade, rollback, template; rightmost -f wins, --set wins over files; OCI registries; Helm 4 (Nov 2025) uses server-side apply; no Tiller since Helm 3.
  • Kustomize: template-free overlays, built into kubectl. Helm templates; Kustomize patches.
  • GitOps (OpenGitOps): declarative, versioned and immutable, pulled automatically, continuously reconciled. Pull-based; agents fix drift.
  • Argo CD (Application CRD; enable prune and selfHeal) and Flux (GitRepository + Kustomization; reverts manual edits) are both CNCF graduated.
  • Tekton joined CNCF (incubating, 2026); Jenkins is CD Foundation; Backstage builds developer portals; Keptn is archived. Promote immutable, versioned images; keep config separate from code.
