Overview

Topic 2.3

Troubleshooting.

The curriculum lists both "Troubleshooting" here and "Debugging" in Domain 3. This page takes troubleshooting to mean problems with the cluster itself: nodes, control plane, networking, capacity and logs. It follows the Kubernetes documentation's own split, whose cluster guide "assume[s] you have already ruled out your application as the root cause". Application-level debugging (crashing containers, probes, debug containers) is topic 3.2.

Quotes are from the Kubernetes documentation (© The Kubernetes Authors, CC BY 4.0) for Kubernetes v1.37.

Running example. One morning the web shop is slow and the frontend cannot reach shop-api. Node node-2 shows NotReady, and some shop-api Pods are stuck. Each section below is one step in finding out why.

A layered approach

Topic 2.3Working through a cluster problem in a sensible order, from your own connection down to the network.

Each layer depends on the one before it, so checking them in order avoids chasing symptoms. This order is assembled from the Kubernetes troubleshooting guides:

  1. Your clientCan kubectl reach the cluster at all? kubectl version, the right context, valid certificates. "If you see Unable to connect to the server: dial tcp ... i/o timeout", the problem is connectivity, not the cluster.
  2. The API serverIs it live and ready? /livez and /readyz (below).
  3. The nodes"The first thing to debug in your cluster is if your nodes are all registered correctly" and Ready.
  4. Control plane and system PodsAre the Pods in kube-system running?
  5. The node agentOn a problem node: the kubelet, the container runtime and their logs.
  6. EventsRecent warnings across the cluster.
  7. The networkCNI Pods, DNS, then Service → EndpointSlice → Pods → kube-proxy, and NetworkPolicy.
  8. CapacityResource use, pressure conditions, stuck objects.

Cluster state and events

Topic 2.3Getting an overview of the cluster's health and reading the events that explain what changed.

First look 
kubectl get nodes
kubectl cluster-info
kubectl get pods -n kube-system

# everything, for a bug report
kubectl cluster-info dump \
  --output-directory=/tmp/state

Events record what controllers and the kubelet did and why: scheduling failures, image pulls, evictions, failed mounts. "Events are namespaced", so add -A to see all of them.

Read events 
# newest last
kubectl get events -A \
  --sort-by=.metadata.creationTimestamp

# only warnings
kubectl events -A --types=Warning

# one object, live
kubectl events --for pod/shop-api-0 \
  --watch

Events disappear after an hour. The API server keeps them for --event-ttl, "Default: 1h0m0s", and the documentation calls them "informative, best-effort, supplemental data". Look at events soon after a problem, and use a logging or monitoring system for history. kubectl events became a regular command (out of alpha) in v1.26.

Node problems

Topic 2.3Working out why a node is NotReady or under pressure, from its conditions, its kubelet and its runtime.

kubectl describe node node-2 shows the node's conditions, taints, capacity, allocated resources and events:

ConditionMeaning when not healthy
ReadyFalse: "not healthy and is not accepting pods"; Unknown: the node controller "has not heard from the node in the last node-monitor-grace-period (default is 50 seconds)"
MemoryPressure, DiskPressure, PIDPressureTrue when memory, disk or process IDs are running low (eviction, topic 1.3)
NetworkUnavailableTrue "if the network for the node is not correctly configured"; usually set by the network plugin
CauseWhat the node shows
kubelet stopped, or node unreachableReady is Unknown, "Kubelet stopped posting node status.", and an unreachable taint
Container runtime downReady is False, reason KubeletNotReady, "container runtime is down"
No CNI plugin installed or readyReady is False, "container runtime network not ready"; on a new kubeadm cluster CoreDNS stays Pending too

Timing matters: the kubelet renews its Lease in kube-node-lease every 10 seconds. After the 50-second grace period the node is tainted and marked Unknown; "the node controller waits 5 minutes" before evicting its Pods. If every zone looks unhealthy at once, it assumes a control-plane connectivity problem and "doesn't perform any evictions".

A missing CNI shows in Ready, not necessarily NetworkUnavailable. The kubelet reports the runtime's network as not ready through the Ready condition. And on a fresh kubeadm cluster, CoreDNS stuck in Pending "is expected": "You have to install a Pod Network before CoreDNS may be deployed fully." (Older material says the grace period is 40 seconds; it became 50 in v1.32.)

On the node

"On Linux nodes that use systemd, the kubelet and container runtime write to journald by default." When the API server or kubelet is down, kubectl cannot help, so you look on the machine itself:

Inspect node-2 directly 
systemctl status kubelet
journalctl -u kubelet --since "1 hour ago"
journalctl -u containerd

# containers the runtime knows about
crictl ps -a
crictl logs <container-id>

Without SSH access, kubectl debug node/node-2 -it --image=ubuntu starts a Pod on the node with its root filesystem mounted at /host. kubectl debug has been stable since v1.30, and since v1.36 its default profile is general instead of legacy. But it "won't work if the Node is down". In v1.36, reading node service logs through the API (node log query) also became stable, though it must be enabled on the kubelet.

Node Problem Detector is an add-on "daemon for monitoring and reporting about a node's health", which turns problems such as kernel errors into node conditions and events; the documentation recommends running it.

Control plane problems

Topic 2.3Checking whether the API server and other control plane components are healthy, and what fails when they are not.

The API server has health endpoints. "livez: Use this to determine if the API server should be restarted." "readyz: Use this to determine if the API server is ready to accept traffic", for example after waiting for etcd. Add ?verbose to see each check:

API server health 
kubectl get --raw='/readyz?verbose'
# [+]ping ok
# [+]etcd ok
# ...
# readyz check passed

Two old health checks are deprecated. The /healthz endpoint is "deprecated (since Kubernetes v1.16)", and kubectl get componentstatuses (kubectl get cs) uses an API "deprecated in v1.19+". Many older guides still use them; use /livez, /readyz and the kube-system Pods instead.

Static Pods

In kubeadm clusters, "kubeadm uses static Pods to run kube-apiserver, kube-controller-manager, kube-scheduler, and etcd". Their manifests are in /etc/kubernetes/manifests, and "the kubelet watches each static Pod and restarts it if it fails." You see them as mirror Pods in kube-system, named after the node, and read their logs with kubectl logs -n kube-system kube-apiserver-<node>, or with crictl if the API server itself is down.

Two static Pod surprises. Deleting a mirror Pod with kubectl does nothing: "the kubelet does not remove the static Pod". And the kubelet reads "all files not starting with a dot" in the manifest folder, so a backup copy such as kube-apiserver.yaml.bak left there is also started. Keep backups elsewhere.

Other control plane checks: certificate expiry shows up as x509 errors (check with kubeadm certs check-expiration, topic 1.2), and etcd health with etcdctl endpoint health.

FailureResult (kubernetes.io)Mitigation

Service and DNS problems

Topic 2.3Tracing a Service that does not work, step by step, from its name to the Pods behind it.

"An issue that comes up rather frequently for new installations of Kubernetes is that a Service is not working properly." The documentation's Debug Services guide checks, in order:

  1. Does the Service exist?"This is a step that sometimes gets forgotten, and is the first thing to check."
  2. Is a NetworkPolicy blocking it?Policies that select the target Pods may drop the traffic.
  3. Does it work by DNS name?Try shop-api, then shop-api.shop, then the full name; if only the longer names work, the client is in another namespace.
  4. Does it work by IP?If the cluster IP works but the name does not, the problem is DNS.
  5. Is it defined correctly?Is the port in spec.ports, is targetPort the Pods' port, is the protocol right?
  6. Does it have EndpointSlices?If not, the selector matches no Pods.
  7. Are the Pods working?Call each Pod on its own port.
  8. Is kube-proxy working?Is it running, and are its rules programmed?
Check the Service's endpoints 
kubectl get endpointslices -l \
  kubernetes.io/service-name=shop-api

# compare selector and Pod labels
kubectl describe svc shop-api
kubectl get pods --show-labels

No endpoints means a label mismatch. "If the ENDPOINTS column is <none>, you should check that the spec.selector field of your Service actually selects for metadata.labels values on your Pods. A common mistake is to have a typo".

DNS

Test DNS from inside the cluster 
U=https://k8s.io/examples/admin/dns
kubectl apply -f $U/dnsutils.yaml
kubectl exec -it dnsutils -- \
  nslookup kubernetes.default
kubectl exec -it dnsutils -- \
  cat /etc/resolv.conf

# is CoreDNS running and logging?
kubectl get pods -n kube-system \
  -l k8s-app=kube-dns
kubectl logs -n kube-system \
  -l k8s-app=kube-dns
  • "The value for label k8s-app for CoreDNS is kube-dns, for backward compatibility", and so is its Service name.
  • The nameserver in resolv.conf must be the cluster DNS Service, and ndots is 5 by default.
  • To see queries arriving, add the log plugin to the CoreDNS configuration (the coredns ConfigMap).
  • Known issue: on nodes using systemd-resolved, a stub resolv.conf can cause "a fatal forwarding loop"; kubeadm detects and handles this.

If CNI Pods in kube-system are crashing, everything networked fails; check them with kubectl get pods -n kube-system -o wide.

Guides still check iptables and IPVS. The Debug Services page shows iptables-save and ipvsadm checks, but IPVS mode is deprecated since v1.35, and nftables mode (stable since v1.33) is the future default. Adjust the kube-proxy check to the mode your cluster uses.

Capacity and stuck objects

Topic 2.3Seeing whether the cluster is out of resources, and freeing objects that will not finish deleting.

Resource use (needs metrics-server) 
kubectl top nodes
kubectl top pods -A --sort-by=cpu
kubectl describe node node-2

kubectl top uses the Metrics API, which "only offers the minimum CPU and memory metrics", and needs the metrics-server add-on; without it the command fails. The Metrics API became stable as metrics.k8s.io/v1 in v1.37. describe node shows Allocated resources, where "total limits may be over 100 percent", and the pressure conditions above.

Stuck in Terminating

  • A Pod stuck Terminating means "a deletion has been issued for the Pod, but the control plane is unable to delete the Pod object", typically because of a finalizer plus an admission webhook that blocks removing it. On a node that is down, deletion also takes much longer.
  • A namespace can stay Terminating if a finalizer on it is never removed; the documentation warns that a nonexistent finalizer leaves it "stuck in the Terminating state".
  • A PersistentVolumeClaim stuck Pending has no matching volume or StorageClass (topic 2.4).

Force deletion is a last resort. kubectl delete pod shop-api-0 --grace-period=0 --force removes the object from the API at once, but "does not wait for confirmation that the pod's processes have been terminated". For a StatefulSet this can leave two copies running and "may lead to data corruption". The documentation also advises: "avoid manually removing finalizers".

Where the logs are

Topic 2.3Knowing where each kind of log is kept, how long it lasts, and how to collect logs cluster-wide.

Logs ofWhereHow to read
Application containersFiles under /var/log/pods on the node, written by the runtimekubectl logs: "the kubelet on the node handles the request and reads directly from the log file"
kubelet, container runtimeThe systemd journal ("do not run in containers")journalctl -u kubelet on the node
API server, scheduler, controller manager, etcdUsually static Podskubectl logs -n kube-system ..., or crictl logs
kube-proxyUsually a DaemonSetkubectl logs -n kube-system ...

Node logs are short-lived. The kubelet rotates container logs at containerLogMaxSize (default 10Mi), keeping containerLogMaxFiles (default 5), and "only the contents of the latest log file are available through kubectl logs". "If a pod is evicted from the node, all corresponding containers are also evicted, along with their logs." Because kubectl logs goes through the kubelet, it fails if the node is down.

Cluster-level logging

"Kubernetes does not provide a native storage solution for log data", so logs must be shipped elsewhere. The documentation lists three patterns:

PatternNotes
Node-level agentOne agent per node, run as a DaemonSet; "doesn't require any changes to the applications"
Sidecar containerStreams an app's log files to stdout, or runs its own agent; can double storage or use "significant resource consumption"
Push from the appThe application sends logs to a backend itself; "outside the scope of Kubernetes"

More detail from kubectl

Adding -v=6 to any kubectl command shows the API requests it makes ("Display requested resources"); -v=8 shows request contents. Components also expose Prometheus metrics on /metrics; monitoring is topic 4.1.

Key takeaways

  • Troubleshoot in layers: client → API server → nodes → kube-system Pods → kubelet and runtime → events → network → capacity. Application debugging is topic 3.2.
  • Events are namespaced (-A for all) and kept only one hour by default. kubectl events --types=Warning.
  • Node Ready=Unknown after 50 s without heartbeats (kubelet down or unreachable); Ready=False for a runtime or CNI problem. Pods are evicted 5 minutes later. Without a CNI, CoreDNS stays Pending.
  • On the node: systemctl status kubelet, journalctl -u kubelet, crictl ps -a; or kubectl debug node/... (needs a working node). Node Problem Detector reports node issues.
  • API server health: /livez and /readyz?verbose. /healthz and componentstatuses are deprecated. kubeadm control plane = static Pods in /etc/kubernetes/manifests.
  • Broken Service: exists? NetworkPolicy? DNS? IP? ports? EndpointSlices empty = selector does not match Pod labels. Pods? kube-proxy? DNS: dnsutils, nslookup kubernetes.default, CoreDNS Pods labelled k8s-app=kube-dns.
  • kubectl top needs metrics-server. Stuck Terminating usually means finalizers; force delete only as a last resort.
  • Container logs live on the node, rotate at 10Mi × 5 files, and vanish on eviction; kubelet and runtime log to journald. Ship logs with a node-level agent DaemonSet.
