Running example. Customers complain that checkout is slow some evenings. The web shop's team wants to know which service is slow, why, and whether they are meeting their target that 99.9% of checkout requests succeed.

Observability and its signals

Topic 4.1Explaining what makes a system observable, the kinds of telemetry it emits, and how reliability targets are expressed.

The CNCF Glossary: "Observability is a system property that defines the degree to which the system can generate actionable insights. It allows users to understand a system's state from these external outputs and take (corrective) action." The CNCF's observability whitepaper puts the difference from monitoring this way: monitoring is sometimes described as detecting "known unknowns", while observability "emphasizes being able to find and reason about unknown unknowns as well".

"Telemetry refers to data emitted from a system and its behavior" (OpenTelemetry). Its main kinds, or signals:

SignalDefinition (OpenTelemetry)Answers
Logs"A timestamped message emitted by services or other components"; structured logs are recommendedWhat discrete events occurred?
Metrics"Aggregations over a period of time of numeric data", such as error rate, CPU use or request rateWhat is happening at the system level?
Traces"The path taken by a single request ... as it propagates through multiple services"; made of spans, each "a single unit of work"How does a request travel through the system?
ProfilesSamples showing "where applications consume resources during execution"; "emerging as the fourth essential signal"Which code is consuming resources?

Signals are correlated through context propagation: trace IDs travel between services in standard W3C Trace Context headers (traceparent), so a slow checkout's logs, metrics and trace can be linked. For the web shop, metrics show checkout latency rising, a trace shows the time is spent in shop-db calls, and logs show the slow query.

Reliability targets

  • An SLI (service level indicator) "represents a measurement of a service's behavior", ideally "from the perspective of your users", such as the share of successful checkouts.
  • An SLO (objective) is a target for an SLI: 99.9% successful checkouts over 30 days.
  • An SLA (agreement) is a contract with users that includes consequences of missing the SLOs (Google SRE book).
  • The error budget is how much unreliability the SLO allows (here 0.1%); when it is spent, releases are typically paused.

Site Reliability Engineering "combines operations and software engineering"; while DevOps "focuses on getting code to production, SRE ensures that code running in production works properly" (CNCF Glossary).

OpenTelemetry

Topic 4.1Collecting telemetry in a vendor-neutral way with OpenTelemetry's APIs, SDKs and Collector.

OpenTelemetry is "an observability framework and toolkit designed to facilitate the Generation, Export, Collection of telemetry data such as traces, metrics, and logs", "vendor- and tool-agnostic", so "you own the data that you generate. There's no vendor lock-in." It graduated in CNCF on May 11, 2026.

OpenTelemetry is not a backend. "OpenTelemetry is not an observability backend itself. The backend (storage) and the frontend (visualization) of telemetry data are intentionally left to other tools", such as Prometheus, Jaeger or a commercial service.

PartRole
API"Defines data types and operations for generating and correlating tracing, metrics, and logging data"
SDKsLanguage-specific implementations of the API
InstrumentationCode-based, or zero-code ("without touching your source code")
OTLPThe OpenTelemetry Protocol; ports 4317 (gRPC) and 4318 (HTTP)
Semantic conventionsCommon names for attributes, such as http.request.method
Collector"A vendor-agnostic proxy that can receive, process, and export telemetry data"

The Collector

A Collector pipeline has receivers ("collect telemetry from one or more sources"), optional processors (modify it, in order) and exporters ("send data to one or more backends"):

otel-collector.yaml 
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
exporters:
  otlp_grpc:
    endpoint: backend:4317
  debug: {}
service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [otlp_grpc]
    metrics:
      receivers: [otlp]
      exporters: [otlp_grpc, debug]

Defined is not enabled. "If a component is configured, but not defined within the service section, then it's not enabled." (Recent Collector versions renamed the otlp exporter to otlp_grpc; the old name still works.)

  • Agent pattern: a Collector "alongside the application or on the same host, such as a sidecar or DaemonSet"; easy to start, limited scalability.
  • Gateway pattern: Collectors run "as a standalone service, for example, in a Kubernetes deployment", with central credentials and policies.
  • The OpenTelemetry Operator manages Collectors and zero-code instrumentation in Kubernetes; a Pod opts in with an annotation such as instrumentation.opentelemetry.io/inject-java: "true".

OpenTracing and OpenCensus are gone. OpenTelemetry "is the result of a merger between two prior projects, OpenTracing and OpenCensus". OpenTracing was archived by CNCF in August 2021, and OpenCensus repositories were archived in July 2023. Traces, metrics and logs are stable in OpenTelemetry; profiles entered public alpha in March 2026.

Prometheus

Topic 4.1Collecting and querying metrics with Prometheus, and alerting on them.

Prometheus is "an open-source systems monitoring and alerting toolkit", created at SoundCloud, which joined CNCF in 2016 as its second hosted project and graduated in 2018, "its second project to graduate, following Kubernetes". In summary, from its documentation:

  • It stores metrics as time series: each identified by a metric name and labels, such as http_requests_total{method="POST"}.
  • It pulls ("scrapes") metrics over HTTP from targets' /metrics endpoints, found by static configuration or service discovery.
  • It is queried with PromQL, and each server is autonomous, without depending on distributed storage.
Metric typeBehaviourWeb shop example
CounterOnly increases, or resets to zero on restartTotal checkout requests
GaugeGoes up and downItems in the order queue
HistogramCounts observations in buckets, for percentilesCheckout latency
SummaryCalculates quantiles in the client over a sliding windowLatency quantiles in one service
PromQL for checkout 
# requests per second, per job
sum by (job) (
  rate(http_requests_total[5m])
)

# share of 5xx errors
sum(rate(
  http_requests_total{code=~"5.."}[5m]
))
/
sum(rate(
  http_requests_total[5m]
))

# 95th percentile latency
histogram_quantile(0.95,
  sum by (le) (rate(
  http_request_duration_seconds_bucket[5m]
  ))
)

Counters need rate(); labels need care. A counter's raw value just grows, so take a rate() first, then aggregate. And every unique label combination is a new time series: Prometheus advises against labels with unbounded values "such as user IDs, email addresses". High cardinality strains the memory and storage of the backend.

In Kubernetes

Scrape Pods found through the Kubernetes API 
scrape_configs:
  - job_name: k8s-pods
    kubernetes_sd_configs:
      - role: pod
  • Exporters expose metrics for systems that cannot be instrumented directly; node_exporter provides hardware and OS metrics.
  • Alertmanager receives alerts from Prometheus, deduplicates, groups and routes them to receivers such as email or PagerDuty, and handles silencing.
  • Storage: local storage is single-node and kept 15 days by default. For long-term or highly available storage, Prometheus remote write sends data to systems such as Thanos or Cortex (both CNCF incubating).

Prometheus pulls. Applications do not push metrics to it. The Pushgateway exists for jobs that cannot be scraped, but Prometheus recommends it only for limited cases, mainly "the outcome of a service-level batch job". Since Prometheus 3.0 it can also receive OTLP metrics, when enabled with --web.enable-otlp-receiver.

Prometheus 3 and OpenMetrics. Prometheus 3.0 (November 2024), its first major release in seven years, added a new UI, UTF-8 metric names and native OTLP ingestion; the current release is 3.16. The separate CNCF project OpenMetrics was archived in July 2024, and its specification now lives in the Prometheus documentation.

Kubernetes' own telemetry

Topic 4.1Knowing what metrics, state and traces Kubernetes itself provides, and which tool to use for each.

"Kubernetes components emit metrics in Prometheus format", usually on a /metrics endpoint; the kubelet also serves container metrics from its built-in cAdvisor on /metrics/cadvisor. Component metrics have stability levels: alpha metrics "can be modified or deleted at any time"; stable metrics "will not be deleted or renamed" and are hidden only after a deprecation of at least three releases or nine months.

ToolProvidesUse for
metrics-serverThe latest CPU and memory use of nodes and Pods, through the Metrics API (stable v1 since Kubernetes v1.37)Autoscaling and kubectl top only: it is "meant only for autoscaling purposes"
kube-state-metrics"Metrics generated from the state of individual objects", such as replicas wanted and available, or Pod phasesAlerting on object state, for example Pods not ready
PrometheusStored history of any metrics, with queries and alertsMonitoring and dashboards

Three tools that are easy to mix up. metrics-server keeps no history and is not a monitoring system. kube-state-metrics describes objects, not resource usage, and "is not focused on the health of the individual Kubernetes components". Prometheus scrapes both kinds of data and stores them. kube-state-metrics and metrics-server are Kubernetes SIG Instrumentation projects.

Query Kubernetes telemetry 
kubectl top pods -A --sort-by=cpu
kubectl get --raw /metrics | head

# PromQL: Pods that are not ready
count by (namespace, pod) (
  kube_pod_status_ready{
    condition="false"
  }
)

"System component traces record the latency of and relationships between operations in the cluster." The API server and kubelet send them with OTLP over gRPC (port 4317) to an OpenTelemetry Collector. Both became stable in v1.34, although the kubernetes.io page still labels the feature beta. Events and audit logs (topics 2.3 and 2.2) complete the picture, and Headlamp (CNCF Sandbox) replaces the archived Kubernetes Dashboard as a web UI.

Jaeger v1 has ended. Jaeger 1.x reached end of life on December 31, 2025. Older material describing separate jaeger-agent, collector and query binaries, or OpenTracing client libraries, describes v1; v2 is a single binary that receives data from OpenTelemetry SDKs.

Zipkin is another tracing system, but not a CNCF project. For traces, sampling controls volume: decided up front in the SDK (head sampling) or after the whole trace is seen, in a Collector gateway (tail sampling).

Cost and efficiency

Topic 4.1Using observability data to see what a cluster costs and where resources are wasted.

Cost management was named in the previous curriculum and still builds on the same data:

  • FinOps "is an operational framework and cultural practice which maximizes the business value of technology ... through collaboration between engineering, finance, and business teams". The FinOps Foundation is a Linux Foundation project.
  • OpenCost (CNCF incubating since October 2024) "provides visibility into current and historical Kubernetes spend and resource allocation", for showback and chargeback by namespace, team or application. It reads usage from Prometheus.
  • Requests drive cost. The scheduler reserves capacity by requests (topic 1.3), so requests far above actual use waste nodes. Comparing requests with measured usage guides rightsizing, and autoscalers (topic 4.2) match capacity to demand.
  • Kepler (CNCF Sandbox) is "a Prometheus exporter that measures energy consumption metrics at the container, pod, and node level".

eBPF-based observability

eBPF "allows small, sandboxed programs or scripts to run in the kernel space of a Linux system without having to change the kernel's source code". It lets tools observe without changing applications: Hubble (part of Cilium) shows network flows, Tetragon (also Cilium) provides "eBPF-based Security Observability", and Pixie (CNCF Sandbox) "uses eBPF to automatically collect telemetry data".

Key takeaways

  • Observability is a property: how well a system's outputs let you understand and act on its state, including "unknown unknowns". Signals: logs, metrics, traces (made of spans), and profiles (alpha). W3C Trace Context links them.
  • SLI = measurement, SLO = target, SLA = contract with consequences; error budget = allowed unreliability. SRE keeps production working.
  • OpenTelemetry (graduated May 2026): APIs, SDKs, instrumentation, OTLP (4317 gRPC, 4318 HTTP) and the Collector (receivers → processors → exporters; only components in service.pipelines run). It is not a backend. It replaced OpenTracing and OpenCensus.
  • Prometheus (graduated 2018) pulls metrics from /metrics; time series = name + labels; counter, gauge, histogram, summary; use rate() on counters; avoid high-cardinality labels; Pushgateway only for batch jobs; Alertmanager routes alerts; Thanos and Cortex for long-term storage. Prometheus 3 accepts OTLP.
  • Kubernetes: components expose Prometheus metrics; metrics-server only for autoscaling and kubectl top; kube-state-metrics for object state; API server and kubelet traces stable since v1.34.
  • Tools: Fluentd and Fluent Bit (logs), Jaeger v2 (traces; v1 ended), Grafana (not CNCF). OpenCost and FinOps for cost; Kepler for energy; eBPF tools (Hubble, Tetragon, Pixie).
