3.2: Debugging

Overview

Topic 3.2

Debugging.

This page takes the topic to mean debugging applications: the Kubernetes guide for it "is not a guide for people who want to debug their cluster." Cluster, node and network problems are topic 2.3. Here: triaging a failing Pod, reading container states, logs, inspecting Pods with exec and kubectl debug, probes, and debugging init containers, rollouts and Jobs.

Quotes are from the Kubernetes documentation (© The Kubernetes Authors, CC BY 4.0) for Kubernetes v1.37.

Running example. A new version of shop-api was just deployed. Some Pods restart over and over, others run but receive no traffic, and the rollout never finishes. Each section is one tool for finding out why.

Triage

Topic 3.2Working out what kind of problem a Pod has from its status, before reaching for deeper tools.

"The first step in troubleshooting is triage. What is the problem? Is it your Pods, your Replication Controller or your Service?" For a Pod, "the first step ... is taking a look at it": kubectl describe pod <name> shows the state of each container, restarts and recent events.

SymptomMeaningLook at
Stays Pending"It can not be scheduled onto a node", usually not enough resources, or a hostPort that limits where it can runScheduler events in describe (topic 1.3)
Stays WaitingScheduled, "but it can't run on that machine"; "the most common cause ... is a failure to pull the image"Image name, registry, pull secret (topic 1.4)
Crashing or unhealthyStarted but keeps failingLogs, exit code, probes (below)
Running, but not doing what you askedOften a typo or mis-nested key in the manifestCompare your file with kubectl get pod -o yaml
Running, but no trafficNot ready, or the Service does not select itReadiness probe; EndpointSlices (topic 2.3)

Typos are now caught. The Debug Pods guide still warns that a misspelled field such as commnd may be "silently ignored". Today kubectl's default is strict server-side field validation (stable since v1.27): the API server "rejects the request with a 400 Bad Request error when it detects any unknown or duplicate fields". Unknown fields are only dropped silently with --validate=false.

Container states and reasons

Topic 3.2Reading a container's state, reason and exit code to narrow down why it is not running.

"There are three possible container states: Waiting, Running, and Terminated." A Waiting container shows a reason; a Terminated one shows "a reason, an exit code, and the start and finish time". Common reasons, set by the kubelet and container runtime:

ReasonStateUsually means
ContainerCreatingWaitingStill starting: pulling the image, mounting volumes
ErrImagePull, ImagePullBackOffWaitingCannot pull the image
CreateContainerConfigErrorWaitingThe container's configuration cannot be built, typically a missing ConfigMap or Secret, or a missing key in one
RunContainerErrorWaitingThe runtime could not start it, for example a wrong command
CrashLoopBackOffWaitingIt keeps crashing, and the kubelet is waiting before the next restart
CompletedTerminatedExited with code 0
ErrorTerminatedExited with a non-zero code
OOMKilledTerminatedKilled for exceeding its memory limit (exit code 137)

CrashLoopBackOff

CrashLoopBackOff "indicates that the backoff delay mechanism is currently in effect for a given container that is in a crash loop, failing and restarting repeatedly". The kubelet waits "10s, 20s, 40s, …", "capped at 300 seconds (5 minutes)", and resets the timer once a container has run for 10 minutes without problems. Typical causes listed by the documentation: application errors, "configuration errors, such as incorrect environment variables or missing configuration files", too little memory or CPU, and failing liveness or startup probes.

Not a phase, and not the cause. CrashLoopBackOff is "a condition or event that might be seen as output from the kubectl command", not a Pod phase (topic 1.1). It tells you the container keeps failing, not why: check its logs and last exit code.

Exit codes

Kubernetes does not define exit codes; they follow the Linux shell convention that a process killed by signal N exits with 128 + N:

Exit codeMeaning
0Success
1 (or other small numbers)The application reported an error
137 (128 + 9, SIGKILL)Killed: by the out-of-memory killer, or after not stopping within the grace period
143 (128 + 15, SIGTERM)Stopped by the termination signal Kubernetes sends first
Last state and restart count 
kubectl get pod shop-api-0 -o jsonpath=\
'{.status.containerStatuses[0].lastState}'

Termination messages

An app can write why it failed to /dev/termination-log (the default terminationMessagePath); Kubernetes shows it under lastState.terminated.message, truncated at 4096 bytes. With terminationMessagePolicy: FallbackToLogsOnError, Kubernetes uses "the last chunk of container log output if the termination message file is empty and the container exited with an error", up to 2048 bytes or 80 lines.

Logs

Topic 3.2Reading what an application printed, including from a container that has already crashed.

kubectl logs 
# the current container
kubectl logs shop-api-0

# the crashed one before it
kubectl logs shop-api-0 --previous

# a named container, live, recent only
kubectl logs shop-api-0 -c api -f \
  --since=1h --tail=50

# every Pod with a label
kubectl logs -l app=shop-api \
  --all-containers

# a Job's first container
kubectl logs job/reindex

Use --previous after a crash. Without it you see the new, freshly restarted container, which may have printed nothing useful yet. "If your container has previously crashed, you can access the previous container's crash log with" --previous. The kubelet keeps only one terminated container's logs, and nothing survives eviction.

kubectl logs shows only what the container writes to stdout and stderr. An app that logs to a file inside the container needs a sidecar that streams the file, or a change to log to stdout.

Getting inside a Pod

Topic 3.2Running commands next to a misbehaving application, even when its image has no shell.

If the image has a shell and tools, kubectl exec runs commands in a container; "the double dash (--) separates the arguments you want to pass to the command from the kubectl arguments". kubectl cp copies files in and out, but needs tar in the image.

exec and cp 
kubectl exec -it shop-api-0 -c api \
  -- sh
kubectl cp shop-api-0:/tmp/dump.txt \
  ./dump.txt

Minimal images such as distroless have no shell, so exec fails with "executable file not found". That is what ephemeral containers are for: "a special type of container that runs temporarily in an existing Pod to accomplish user-initiated actions such as troubleshooting" (stable since v1.25). kubectl debug adds one:

Debug a running Pod in place 
# tools container sharing api's
# process namespace
kubectl debug -it shop-api-0 \
  --image=busybox:1.36 --target=api

Ephemeral containers are one-way. They "will never be automatically restarted", may not have ports, probes or resources, and "you may not change or remove an ephemeral container after you have added it to a Pod". They also need permission on the pods/ephemeralcontainers subresource, which the default admin and edit roles do not include.

Debugging a copy

When the app crashes at startup, attaching to it is not enough. kubectl debug can instead "create a copy of the Pod with configuration values changed to aid debugging", leaving the original untouched:

Copy the Pod and start a shell instead 
kubectl debug shop-api-0 -it \
  --copy-to=api-debug \
  --container=api -- sh

# or swap every image for ubuntu
kubectl debug shop-api-0 \
  --copy-to=api-debug --set-image=*=ubuntu

# clean up afterwards
kubectl delete pod api-debug

By default the copy drops the original's labels and probes, so it does not receive Service traffic or get restarted by a failing probe.

The default debug profile changed. Profiles set the debug container's privileges: general, baseline, restricted, netadmin and sysadmin. Since kubectl v1.36 the default is general; the old legacy profile "is deprecated and planned to be removed in v1.39". (The Debug Running Pods page still says legacy is the default.) Custom profiles with --custom are stable since v1.32.

Health probes

Topic 3.2Telling Kubernetes how to check an application's health, and avoiding probes that cause the failures they should detect.

"A probe is a diagnostic performed periodically by the kubelet on a container." "Based on the probe results, Kubernetes can restart unhealthy containers or stop sending traffic to containers that are not ready."

ProbeAnswersOn failure
StartupHas the app finished starting? Liveness and readiness probes wait until it succeeds"The kubelet kills the container", and the restart policy applies
LivenessIs the app still working, or is it stuck, "for example ... a deadlock"?"The kubelet restarts that container"
ReadinessCan it take traffic right now?No restart: the Pod's IP is removed "from the EndpointSlices of all Services that match the Pod", and Ready becomes false

Each probe uses exactly one mechanism: httpGet (success is a status from 200 to 399), tcpSocket (the port is open), exec (the command exits with 0) or grpc (stable since v1.27; the service reports SERVING). A container without a given probe always counts as passing it.

Probes for shop-api 
    # slow start: up to 30 x 10s
    startupProbe:
      httpGet:
        path: /healthz
        port: 8080
      failureThreshold: 30
      periodSeconds: 10
    # stuck process: restart it
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      failureThreshold: 3
    # not ready: stop sending traffic
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
FieldDefault
initialDelaySeconds0
periodSeconds10
timeoutSeconds1
successThreshold1 (must be 1 for liveness and startup)
failureThreshold3

Liveness probes can cause outages. They "must be configured carefully to ensure that they truly indicate unrecoverable application failure". A liveness probe that fails under heavy load restarts busy containers, putting more load on the rest: "cascading failures". For apps that start slowly, use a startup probe rather than a long initial delay; the documentation's example allows "a maximum of 5 minutes (30 * 10 = 300s)". And "the readiness and liveness probes do not depend on each other to succeed."

Failing probes show up as Unhealthy warning events in kubectl describe pod, and liveness failures increase the RESTARTS count.

Init containers, rollouts and Jobs

Topic 3.2Recognizing the statuses that init containers, stalled Deployments and failing Jobs report.

Init containers

Pod statusMeaning (kubernetes.io)
Init:N/M"The Pod has M Init Containers, and N have completed so far."
Init:Error"An Init Container has failed to execute."
Init:CrashLoopBackOff"An Init Container has failed repeatedly."
PodInitializing or RunningInit containers have finished

Read an init container's logs by name: kubectl logs shop-api-0 -c wait-for-db.

A rollout that never finishes

The documentation lists why a Deployment can fail: "Insufficient quota", "Readiness probe failures", "Image pull errors", "Insufficient permissions", "Limit ranges", "Application runtime misconfiguration". After progressDeadlineSeconds (default 600), its Progressing condition becomes False with reason ProgressDeadlineExceeded, and kubectl rollout status exits with an error.

Investigate, then roll back 
kubectl rollout status deploy/shop-api
kubectl describe deploy shop-api
kubectl get rs -l app=shop-api
kubectl rollout undo deploy/shop-api

Kubernetes does not roll back by itself. "Kubernetes takes no action on a stalled Deployment other than to report a status condition". You or a higher-level tool (such as Argo Rollouts, topic 3.1) must roll back. A quota problem shows as a ReplicaFailure condition with reason FailedCreate.

Jobs

A Job retries failed Pods up to backoffLimit (default 6) and then fails with reason BackoffLimitExceeded; activeDeadlineSeconds takes precedence and fails it with DeadlineExceeded. The documentation suggests "setting restartPolicy = "Never" when debugging the Job", because with OnFailure the Pod is terminated at the backoff limit, taking its logs with it.

Tools and observability

Topic 3.2Using local-development tools and observability data to debug beyond a single Pod.

  • kubectl port-forward pod/shop-api-0 8080:8080 reaches one Pod from your machine; "the forwarding session ends when the selected pod terminates".
  • Telepresence (CNCF Sandbox) supports "local development against a remote Kubernetes ... cluster"; DevSpace is also a CNCF Sandbox project, while Tilt, Skaffold and Okteto are independent tools for inner-loop development.
  • For problems across many services, logs alone are not enough. "Observability is a system property that defines the degree to which the system can generate actionable insights" (CNCF Glossary): logs, metrics and traces, collected with tools such as OpenTelemetry, which graduated in CNCF on May 11, 2026. Topic 4.1 covers this.

Key takeaways

  • Triage with kubectl describe pod: Pending = not scheduled; Waiting = cannot start (usually image); crashing = check logs and exit code; running but wrong = compare the manifest with get -o yaml. Strict field validation now rejects typos.
  • Container states: Waiting, Running, Terminated. Reasons: CreateContainerConfigError (missing ConfigMap or Secret), RunContainerError, CrashLoopBackOff (repeated crashes; 10 s to 300 s backoff), Completed, Error, OOMKilled (137).
  • Exit codes follow 128 + signal: 137 = SIGKILL, 143 = SIGTERM. Termination messages come from /dev/termination-log or, with FallbackToLogsOnError, the log tail.
  • kubectl logs --previous for a crashed container; -c, -f, -l, --since, --tail. Only stdout and stderr are captured.
  • kubectl exec needs a shell in the image; otherwise kubectl debug --target adds an ephemeral container (stable v1.25; cannot be removed). --copy-to debugs a copy. Default profile general since v1.36.
  • Probes: startup (gates the others), liveness (failure restarts), readiness (failure removes from Service endpoints, no restart). httpGet, tcpSocket, exec, grpc. Defaults: period 10 s, timeout 1 s, failure threshold 3. Careless liveness probes cause cascading failures.
  • Init:N/M, Init:Error, Init:CrashLoopBackOff. A stalled Deployment reports ProgressDeadlineExceeded after 600 s but is not rolled back automatically. Jobs fail at backoffLimit 6; debug with restartPolicy: Never.
