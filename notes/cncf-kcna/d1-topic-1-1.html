Overview

Topic 1.1

Kubernetes Core Concepts.

The curriculum gives this topic a single line. This page takes it to cover the ideas every other topic builds on: what Kubernetes is, the components of a cluster, how objects and controllers work, how objects are organized, and the main workload resources. Later topics go deeper into running clusters (1.2), scheduling (1.3), containers (1.4), networking (2.1), security (2.2) and storage (2.4).

Definitions are quoted from the Kubernetes documentation (© The Kubernetes Authors, CC BY 4.0) and the CNCF Glossary, and match Kubernetes v1.37 (August 2026).

Running example. These notes follow a small web shop deployed to one Kubernetes cluster: a shop-web frontend, a shop-api backend, a shop-db database and a shop-worker that processes orders in the background. Each concept is shown on one of those parts.

What Kubernetes is

Topic 1.1Explaining what Kubernetes does for containerized applications, and what it deliberately leaves to other tools.

The Kubernetes documentation defines it as "a portable, extensible, open source platform for managing containerized workloads and services that facilitate both declarative configuration and automation." The CNCF Glossary puts it more plainly: "an open source container orchestrator" that "automates the lifecycle of containerized applications", working as a "datacenter operating system".

The name "originates from Greek, meaning helmsman or pilot"; K8s counts "the eight letters between the 'K' and the 's'". Google open-sourced the project in 2014, building on its experience with an internal system called Borg. Kubernetes was accepted into the CNCF® in March 2016 and became CNCF's first graduated project on March 6, 2018.

What it provides

CapabilityWhat it means for the web shop
Service discovery and load balancingThe frontend finds the API by a DNS name, and traffic is spread across its copies
Self-healingKubernetes "restarts containers that fail, replaces containers, kills containers that don't respond to your user-defined health check"
Automated rollouts and rollbacksA new frontend version is rolled out gradually and can be undone
Horizontal scalingMore frontend copies for a sale, with "a simple command, with a UI, or automatically based on CPU usage"
Automatic bin packingContainers are placed on nodes to make good use of their CPU and memory
Storage orchestrationThe database gets a disk mounted automatically
Secret and configuration managementThe database password and settings are stored separately from the container image
Batch executionThe nightly sales report runs as a job

The documentation also lists IPv4/IPv6 dual-stack networking and being "designed for extensibility": features can be added "without changing upstream source code".

What it is not

Kubernetes "is not a traditional, all-inclusive PaaS (Platform as a Service) system". It "provides the building blocks for building developer platforms". In particular, it:

  • "does not deploy source code and does not build your application": CI/CD is left to other tools;
  • does not provide middleware, databases or caches "as built-in services";
  • "does not dictate logging, monitoring, or alerting solutions";
  • does not mandate a configuration language: it "provides a declarative API".

Orchestration, but not a script. The documentation makes a subtle point: classic orchestration means running "a defined workflow: first do A, then B, then C". Kubernetes instead "comprises a set of independent, composable control processes that continuously drive the current state towards the provided desired state." That idea, desired state plus control loops, is the heart of this topic.

Cluster architecture

Topic 1.1Naming the components of the control plane and of each node, and what each one is responsible for.

"A Kubernetes cluster consists of a control plane plus a set of worker machines, called nodes, that run containerized applications. Every cluster needs at least one worker node in order to run Pods." The control plane makes "global decisions about the cluster (for example, scheduling)" and responds to events, such as starting a new Pod when a Deployment has too few.

Control plane components

ComponentWhat it does (kubernetes.io)
kube-apiserver"The front end for the Kubernetes control plane": it exposes the Kubernetes HTTP API. It scales horizontally by running more instances
etcd"Consistent and highly-available key value store used as Kubernetes' backing store for all cluster data." The docs advise having "a back up plan for the data"
kube-scheduler"Watches for newly created Pods with no assigned node, and selects a node for them to run on" (topic 1.3)
kube-controller-manager"Runs controller processes", compiled into one binary: for example the Node, Job, EndpointSlice and ServiceAccount controllers
cloud-controller-manager (optional)"Embeds cloud-specific control logic", such as creating cloud load balancers. A cluster on your own premises or PC does not have one

Node components

ComponentWhat it does (kubernetes.io)
kubelet"An agent that runs on each node in the cluster. It makes sure that containers are running in a Pod." It "doesn't manage containers which were not created by Kubernetes"
kube-proxy (optional)"A network proxy that runs on each node", "implementing part of the Kubernetes Service concept"
Container runtimeRuns the containers: "containerd, CRI-O, and any other implementation of the Kubernetes CRI (Container Runtime Interface)" (topic 1.4)

Two components are optional. kube-proxy is not needed "if you use a network plugin that implements packet forwarding for Services by itself". The cloud-controller-manager only exists when Kubernetes runs on a cloud provider. The API server, etcd, scheduler, controller manager, kubelet and a container runtime are always there.

Add-ons

Add-ons are cluster features built from ordinary Kubernetes resources, kept in the kube-system namespace. The most important is cluster DNS: "all Kubernetes clusters should have cluster DNS, as many examples rely on it." Others include the web Dashboard, container resource monitoring, cluster-level logging, and network plugins that implement the Container Network Interface (CNI) and give Pods their IP addresses.

How the parts talk

Kubernetes uses a "hub-and-spoke" pattern: "All API usage from nodes (or the pods they run) terminates at the API server. None of the other control plane components are designed to expose remote services." The scheduler, the controllers and every kubelet read and write cluster state only through the API server, and only the API server talks to etcd.

Each node reports that it is alive in two ways: updates to its Node object's .status, and a small Lease object in the kube-node-lease namespace that the kubelet renews. The node controller checks nodes every 5 seconds; if a node stops reporting it is marked Unknown, and the controller waits 5 minutes before starting to evict its Pods.

Control plane components can run as ordinary system services, as static Pods managed directly by the kubelet (the approach kubeadm uses), or as a managed service run by a cloud provider.

Objects and desired state

Topic 1.1Describing what you want as an object, and understanding how controllers keep making the cluster match it.

"Kubernetes objects are persistent entities in the Kubernetes system", used "to represent the state of your cluster". Each one is "a 'record of intent'": once you create it, "the Kubernetes system will constantly work to ensure that the object exists." That intent is the cluster's desired state.

Almost every object has two nested fields: spec, the desired state you write, and status, "the current state of the object, supplied and updated by the Kubernetes system". Every manifest needs four top-level fields:

FieldMeaningExample
apiVersionWhich version of the Kubernetes API the object usesapps/v1
kindWhat kind of object it isDeployment
metadataIdentifying data: a name, a UID and an optional namespacename: shop-web
specThe state you wantreplicas: 3

ConfigMaps and Secrets are the exceptions: they carry data instead of a spec.

Controllers and the control loop

A controller is "a control loop that watches the shared state of the cluster through the apiserver and makes changes attempting to move the current state towards the desired state." The documentation's analogy is a thermostat: you set the temperature you want, and it keeps switching the heating on and off to reach it.

  1. You declareA Deployment for shop-web with replicas: 3.
  2. The controller comparesIt sees desired 3, current 0.
  3. It acts through the APIIt asks the API server to create Pods. A controller does not run containers itself: "the Job controller tells the API server to create or remove Pods", and the same is true of the others.
  4. It keeps watchingIf a node fails and a Pod disappears, current becomes 2, and the controller creates a replacement. This is self-healing.

API groups and versions

Every request goes through the API server's HTTP API. Resources are grouped:

  • The core (legacy) group is written without a group name: apiVersion: v1. Pods, Services, Namespaces, ConfigMaps, Secrets and Nodes live here.
  • Named groups use group/version: apps/v1 for Deployments, ReplicaSets, StatefulSets and DaemonSets; batch/v1 for Jobs and CronJobs.

Version names show maturity. Alpha (v1alpha1) APIs are disabled by default and may be dropped "at any time without notice". Beta (v1beta1) APIs are also disabled by default, except betas introduced before Kubernetes 1.22. Stable APIs are plain vX, such as v1.

Explore the API from the command line 
# every resource type the server offers
kubectl api-resources

# only cluster-wide (non-namespaced) types
kubectl api-resources --namespaced=false

# built-in documentation for any field
kubectl explain deployment.spec.replicas

New in v1.37: KYAML is stable. KYAML is "a safer and less ambiguous subset of YAML" designed for Kubernetes: it uses {} and [], and every string value is double-quoted, which avoids whitespace mistakes and implicit type conversion. kubectl get -o kyaml became stable in v1.37. Ordinary YAML still works and is what most examples use.

Organizing objects

Topic 1.1Naming objects, grouping them into namespaces, and tagging them with labels so they can be found and selected.

Names and UIDs

"Each object in your cluster has a Name that is unique for that type of resource. Every Kubernetes object also has a UID that is unique across your whole cluster." So there can be only one Pod called shop-web-1 in a namespace, but a Pod and a Deployment may share a name. Most names must be valid DNS subdomain names: at most 253 characters, lowercase letters, digits, - and ., starting and ending with a letter or digit.

Namespaces

"Namespaces provide a mechanism for isolating groups of resources within a single cluster. Names of resources need to be unique within a namespace, but not across namespaces." They cannot be nested. A cluster starts with four:

NamespaceUsed for
defaultObjects created without a namespace
kube-system"Objects created by the Kubernetes system", including add-ons
kube-publicReadable by all clients, even unauthenticated ones; "only a convention"
kube-node-leaseThe Lease objects nodes use as heartbeats

Not everything lives in a namespace: Namespaces themselves, Nodes, PersistentVolumes and StorageClasses are cluster-wide. The web shop could use a shop namespace for its parts and a separate monitoring namespace for observability tools. Avoid creating namespaces starting with kube-.

Labels and selectors

"Labels are key/value pairs that are attached to objects such as Pods", used for "identifying attributes of objects that are meaningful and relevant to users". Unlike names, they are not unique: many Pods share app: shop-web. A selector picks objects by their labels. There are two kinds:

  • Equality-based: =, ==, !=, for example tier=frontend.
  • Set-based: in, notin, and whether a key exists, for example env in (prod,staging).

Several requirements separated by commas must all match; "there is no logical OR". Services support only equality-based selectors, while Deployments, ReplicaSets, Jobs and DaemonSets also accept set-based matchExpressions.

Select objects by label 
# the frontend's Pods in production
kubectl get pods \
  -l app=shop-web,env=prod

# Pods of any web shop part
kubectl get pods \
  -l 'app in (shop-web,shop-api)'

Annotations, owners and finalizers

  • Annotations attach "arbitrary non-identifying metadata", such as a build number or a contact email. Unlike labels, "annotations are not used to identify and select objects", and they can be much larger (256 KiB in total per object).
  • Owners: "some objects are owners of other objects. For example, a ReplicaSet is the owner of a set of Pods", recorded in metadata.ownerReferences. Deleting an owner normally deletes what it owns.
  • Finalizers "tell Kubernetes to wait until specific conditions are met before it fully deletes resources", for example keeping a volume until nothing uses it.

Labels or annotations? If you need to select or group objects (a Service finding its Pods, kubectl get -l), use a label. If you only need to record information for people or tools, use an annotation.

Pods

Topic 1.1Understanding the Pod as the unit Kubernetes runs, and the states it passes through.

"Pods are the smallest deployable units of computing that you can create and manage in Kubernetes." A Pod (as in a pod of whales) "is a group of one or more containers, with shared storage and network resources, and a specification for how to run the containers." Each Pod gets its own IP address, and containers in the same Pod reach each other on localhost.

One container per Pod is "the most common Kubernetes use case": Kubernetes "manages Pods rather than managing the containers directly." Several containers belong in one Pod only when they are tightly coupled, such as an app and a helper that ships its logs.

You rarely create Pods yourself. Pods are "relatively ephemeral, disposable entities", and a Pod is "only scheduled once in their lifetime": if its node fails, the Pod is not moved but replaced by a new one. That is why you create a workload resource, such as a Deployment, that creates and replaces Pods for you.

Special containers

KindBehaviourWeb shop example
Init containerRuns to completion before the app starts; each must succeed before the next beginsWait until shop-db accepts connections
Sidecar containerStarts before the app and keeps running alongside it. Stable since v1.33; declared as an init container with restartPolicy: AlwaysA log shipper next to shop-api
Ephemeral containerAdded temporarily to a running Pod for troubleshooting with kubectl debug; no ports or probesAttach a shell with network tools to a misbehaving Pod

Pod phases

PhaseMeaning (kubernetes.io)
PendingAccepted, but containers are not yet ready to run: waiting to be scheduled or downloading images
RunningBound to a node, all containers created, at least one running or restarting
SucceededAll containers ended successfully and will not restart
FailedAll containers ended, at least one in failure
UnknownThe state could not be obtained, typically because the node cannot be reached

A Pod's restartPolicy is Always (the default), OnFailure or Never. Failing containers are restarted with a growing delay: 10 s, 20 s, 40 s and so on, "capped at 300 seconds (5 minutes)".

CrashLoopBackOff is not a phase. Words like CrashLoopBackOff and Terminating appear in the STATUS column of kubectl get pods, but the documentation warns not to confuse that display field "with the pod's phase". There are only five phases. Diagnosing these states is part of topics 2.3 and 3.2.

Changing resources without a restart. Since v1.35, in-place Pod resize is stable: a container's CPU and memory requests and limits can be changed "without recreating the Pod".

Workload resources

Topic 1.1Choosing the right workload resource for each kind of application, and managing a Deployment through its life.

"A workload is an application running on Kubernetes", always run "inside a set of pods". Workload resources create and manage those Pods from a Pod template:

ResourceUse it forWeb shop part
DeploymentStateless apps where "any Pod in the Deployment is interchangeable"; rolling updates and rollbacksshop-web, shop-api
ReplicaSetKeeps "a stable set of replica Pods running". Normally created by a Deployment, not by youCreated for each shop-web version
StatefulSetApps needing "stable, unique network identifiers", "stable, persistent storage" and ordered start-up and updatesshop-db, with Pods shop-db-0, shop-db-1
DaemonSetOne copy of a Pod on all (or some) nodes, added as nodes joinA log collector on every node
Job"One-off tasks that run to completion and then stop", retried on failure (6 retries by default)Rebuild the product search index once
CronJobJobs on a repeating schedule, written like "one line of a crontab"The nightly sales report

A StatefulSet needs a headless Service (clusterIP: None) to give each Pod its stable DNS name, and deleting or scaling it down does "not delete the volumes". Jobs only allow a restartPolicy of Never or OnFailure. A CronJob's schedule has five fields: minute, hour, day of month, month, day of week, so 0 2 * * * runs at 2 a.m. every day.

ReplicationController is legacy. The documentation calls it superseded: "A Deployment that configures a ReplicaSet is now the recommended way to set up replication." It still exists in the core API but should not be used for new work.

A Deployment, step by step

Adapted from the kubernetes.io Deployment example:

shop-web.yaml (Deployment) 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-web
  labels:
    app: shop-web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: shop-web   # must match
  template:           # the Pod template
    metadata:
      labels:
        app: shop-web
    spec:
      containers:
      - name: web
        image: nginx:1.14.2
        ports:
        - containerPort: 80

The selector must match the template's labels, and in apps/v1 it cannot be changed after creation.

Create, inspect, scale and update it 
# create or update from the file
kubectl apply -f shop-web.yaml

# the Deployment, its ReplicaSet, its Pods
kubectl get deploy,rs,pods -l app=shop-web

# which node each Pod runs on
kubectl get pods -o wide

# scale (no new rollout)
kubectl scale deploy/shop-web --replicas=5

# new image: starts a rolling update
kubectl set image deploy/shop-web \
  web=nginx:1.16.1
kubectl rollout status deploy/shop-web

# history, and go back one revision
kubectl rollout history deploy/shop-web
kubectl rollout undo deploy/shop-web

Behind the scenes, an update creates a new ReplicaSet for the new Pod template, scales it up and scales the old one down. The default strategy is RollingUpdate, which allows 25% extra Pods (maxSurge) and 25% unavailable Pods (maxUnavailable) during the change; the alternative, Recreate, stops all old Pods first. Ten old ReplicaSets are kept for rollbacks by default.

Two classic traps. First, a Deployment manages ReplicaSets, and the ReplicaSets manage the Pods; the documentation says "do not manage ReplicaSets owned by a Deployment." Second, a rollout happens "if and only if the Deployment's Pod template (that is, .spec.template) is changed": scaling does not create a new revision.

Configuration and Services

Topic 1.1Keeping configuration and secrets out of container images, and giving a group of Pods one stable address.

  • A ConfigMap is "an API object used to store non-confidential data in key-value pairs". Pods use it as environment variables, command-line arguments or files. It "does not provide secrecy or encryption".
  • A Secret "contains a small amount of sensitive data such as a password, a token, or a key." Values in its data field are base64-encoded. Both are limited to 1 MiB, and both can be made immutable.
  • A Service "is a method for exposing a network application that is running as one or more Pods". It usually finds its Pods with a label selector, so shop-api Pods can come and go while the frontend keeps one address. Service types and DNS are covered in topic 2.1.

Base64 is not encryption. The documentation warns: "Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd)", and anyone who can create a Pod in a namespace can read that namespace's Secrets. Protecting them (encryption at rest, RBAC, external secret stores) is part of topic 2.2.

Endpoints is deprecated. Since v1.33 the old Endpoints API is deprecated in favour of EndpointSlices, which the EndpointSlice controller fills in to link each Service to its Pods.

Key takeaways

  • Kubernetes is "a portable, extensible, open source platform for managing containerized workloads and services". It is not a PaaS: it does not build code, and leaves CI/CD, databases and monitoring to other tools. It became CNCF's first graduated project in 2018.
  • Control plane: kube-apiserver (the front end; everything goes through it), etcd (backing store for all cluster data), kube-scheduler, kube-controller-manager, and the optional cloud-controller-manager. Nodes: kubelet, the optional kube-proxy, and a CRI container runtime.
  • Objects record desired state in spec; the system reports status. Manifests need apiVersion, kind, metadata and spec. Controllers are control loops that keep moving current state towards desired state.
  • Core API objects use v1; others use group/version such as apps/v1 and batch/v1. Alpha and new beta APIs are off by default.
  • Namespaces isolate names; four exist at start (default, kube-system, kube-public, kube-node-lease). Labels identify and select; annotations only describe.
  • The Pod is the smallest deployable unit: one or more containers sharing an IP and storage. Five phases only; CrashLoopBackOff is a status, not a phase. Sidecars (stable in v1.33) are init containers with restartPolicy: Always.
  • Deployment for stateless apps (manages ReplicaSets; RollingUpdate with 25% surge and unavailable by default; only template changes create a rollout). StatefulSet for stable identity and storage, DaemonSet for one Pod per node, Job and CronJob for tasks that finish.
  • ConfigMaps hold settings; Secrets hold sensitive data but are only base64-encoded and unencrypted in etcd by default. A Service gives a set of Pods one address.
