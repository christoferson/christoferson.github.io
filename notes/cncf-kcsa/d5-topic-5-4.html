Overview

Topic 5.4

Admission Control.

This page is the admission control deep dive: the two phases, the built-in plugins, webhooks, the in-process CEL policies, and the policy engines built on them. Pod Security Admission has its own page (topic 3.1), image signature checks are in topic 5.1, and the request flow that leads to admission is in topic 2.1.

Quotes are from kubernetes.io (CC BY 4.0) and the Kyverno, Gatekeeper and Kubewarden documentation.

Running example. The platform team wants three rules for the shop: images only from registry.example.com/ and never :latest, no ServiceAccount token unless asked for, and a company webhook that checks Pods, without ever locking up the cluster.

How admission works

Topic 5.4What admission sees, in what order, and how it decides.

"An admission controller is a piece of code that intercepts requests to the Kubernetes API server prior to persistence of the resource, but after the request is authenticated and authorized."

  1. Mutating phaseMutating controllers (built-in plugins, mutating webhooks, MutatingAdmissionPolicies) may change the object.
  2. Schema validationThe API server validates the final object against its schema.
  3. Validating phaseValidating controllers (built-in plugins, validating webhooks, ValidatingAdmissionPolicies) accept or reject it. Webhooks in this phase run in parallel.
  4. Result"If any of the controllers in either phase reject the request, the entire request is rejected immediately". Otherwise the object is stored.

Admission sees four operations: CREATE, UPDATE, DELETE and CONNECT. Built-in plugins are compiled into kube-apiserver and turned on with --enable-admission-plugins or off with --disable-admission-plugins; the order you list them in "doesn't matter", because it's fixed in code. The old --admission-control flag is deprecated.

Reads skip admission; exec doesn't. Admission controllers "do not (and cannot) block requests to read (get, watch or list) objects". But kubectl exec, attach and port-forward are CONNECT requests, so an admission policy can block them. Paths that skip the API server entirely (etcd, the kubelet API, static Pods) skip admission too (topic 4.1).

Admission webhooks

Topic 5.4Calling out to your own service to accept, reject or change objects.

A ValidatingWebhookConfiguration or MutatingWebhookConfiguration (admissionregistration.k8s.io/v1, cluster-scoped) tells the API server to POST an AdmissionReview to a service over HTTPS. The reply carries allowed, an optional status message, warnings, and, for mutation, a base64-encoded JSON Patch.

The company Pod check, failing safely (ValidatingWebhookConfiguration) 
apiVersion: >-
  admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: policy.example.com
webhooks:
- name: pods.policy.example.com
  admissionReviewVersions: ["v1"]
  sideEffects: None
  timeoutSeconds: 5
  # reject if the webhook is unreachable
  failurePolicy: Fail
  matchPolicy: Equivalent
  clientConfig:
    service:
      namespace: policy-system
      name: policy-webhook
      path: /validate
    caBundle: <base64-PEM-CA>
  rules:
  - apiGroups: [""]
    apiVersions: ["v1"]
    operations: ["CREATE", "UPDATE"]
    resources: ["pods"]
    scope: Namespaced
  # skip kube-system and our namespace
  namespaceSelector:
    matchExpressions:
    - key: kubernetes.io/metadata.name
      operator: NotIn
      values: [kube-system, policy-system]
FieldDefault and rules
failurePolicyFail by default in v1, or Ignore; applies only to call errors: "An explicit rejection ... always denies the API request"
sideEffects, admissionReviewVersionsRequired; side effects None or NoneOnDryRun
timeoutSeconds10 by default, 1 to 30; a timeout follows the failure policy
rules.resources* means all resources but not subresources; use */* or pods/exec to include them
namespaceSelector, objectSelectorNarrow what's sent; an object selector can be skipped by anyone who controls the labels
matchConditionsUp to 64 CEL expressions (GA v1.30); all must be true to call the webhook
reinvocationPolicy (mutating)Never by default, or IfNeeded to run again after later mutations
  • Ordering: mutating webhooks run one after another, and "don't run in a consistent order", so "Don't rely on your webhook running at a specific point". Mutations must be idempotent. To check the final object, use a validating webhook or policy.
  • TLS and identity: HTTPS is required, and the server certificate must be valid for <service>.<namespace>.svc, verified with caBundle. The API server can authenticate to webhooks using a kubeconfig named in its AdmissionConfiguration. Since v1.37 (beta), webhooks are no longer called for TokenReview and SubjectAccessReview requests.

Webhook good practices and risks

Topic 5.4Keeping webhooks fast, safe and impossible to abuse.

kubernetes.io's admission webhook good practices start with a preference: "The Kubernetes project recommends that you use CEL-based admission control when possible." When a webhook is needed:

  • Avoid deadlocks: "Avoid matching objects in the kube-system namespace", and "Exclude the namespace where your webhook is running" with a namespace selector. Otherwise a fail-closed webhook can stop its own Pods from being recreated.
  • Keep it fast: set a small timeout, run several replicas, and avoid extra API calls. Validating webhooks run in parallel; mutating ones add up in sequence.
  • Fail open or closed: the page suggests letting mutating webhooks fail open (Ignore) while a validating control checks the final state; security-critical validation fails closed.
  • Roll out gradually: start with Ignore and a test namespace, then widen.
  • Protect the configuration: limit create, update, patch, delete and deletecollection on webhook configurations, and on the webhook server's namespace, to trusted administrators.

Admission can't protect itself. "Admission configuration resources (such as ValidatingWebhookConfiguration) are not themselves subject to webhook admission", and "you can't create a ValidatingAdmissionPolicy that prevents changes to ValidatingAdmissionPolicyBindings." So anyone who can write webhook configurations can intercept, or silently disable, enforcement for every object (topic 4.3). RBAC is the main defense. New in v1.37 (beta), manifest-based admission loads webhooks and policies from files on the API server host (staticManifestsDir); these can't be changed through the API and can protect the admission objects themselves.

Ignore is a bypass waiting to happen. With failurePolicy: Ignore, a policy simply isn't enforced while its webhook is down, slow or overloaded, and an attacker who can knock the webhook over gets everything through. Fail keeps the policy but risks availability: hence the namespace exclusions and replicas above.

CEL admission policies

Topic 5.4Built-in, in-process policies written in the Common Expression Language.

ValidatingAdmissionPolicy (VAP, GA v1.30) is "a declarative, in-process alternative to validating admission webhooks". It needs two objects: the policy (logic) and a binding (where it applies and what happens on failure). "At least a ValidatingAdmissionPolicy and a corresponding ValidatingAdmissionPolicyBinding must be defined for a policy to have an effect."

Trusted registry, no :latest (ValidatingAdmissionPolicy and binding) 
apiVersion: >-
  admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: trusted-images
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["pods"]
  validations:
  - expression: >-
      object.spec.containers.all(c,
      c.image.startsWith(
      'registry.example.com/'))
    message: untrusted image registry
  - expression: >-
      !object.spec.containers.exists(c,
      c.image.endsWith(':latest'))
    message: ":latest tag not allowed"
---
apiVersion: >-
  admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: trusted-images-shop
spec:
  policyName: trusted-images
  # block, and record in the audit log
  validationActions: [Deny, Audit]
  matchResources:
    namespaceSelector:
      matchLabels:
        env: prod
  • validationActions lives on the binding: Deny, Warn and/or Audit (not Deny with Warn). Audit writes to the validation.policy.admission.k8s.io/validation_failure audit annotation (topic 3.5).
  • A policy can take parameters (paramKind, with paramRef in the binding), define variables and matchConditions, and use messageExpression. Expressions can read object, oldObject, request, params, namespaceObject and authorizer.
  • A real policy should also check initContainers and ephemeralContainers. Because the rule matches Pods, a Deployment with a bad image is accepted and its ReplicaSet then fails to create Pods.

MutatingAdmissionPolicy (MAP, GA v1.36 in admissionregistration.k8s.io/v1) changes objects in CEL, either as an apply configuration merged like server-side apply, or as JSON Patch:

No ServiceAccount token for shop Pods (MutatingAdmissionPolicy and binding) 
apiVersion: >-
  admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicy
metadata:
  name: no-sa-token
spec:
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: ["v1"]
      operations: ["CREATE"]
      resources: ["pods"]
  failurePolicy: Fail
  reinvocationPolicy: Never
  mutations:
  - patchType: ApplyConfiguration
    applyConfiguration:
      expression: >-
        Object{spec: Object.spec{
        automountServiceAccountToken:
        false}}
---
apiVersion: >-
  admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicyBinding
metadata:
  name: no-sa-token
spec:
  policyName: no-sa-token

As written, this overrides Pods that explicitly ask for a token; a matchCondition can exempt them. A MAP binding has no validationActions and can't match DELETE.

Type checking only warns. When a VAP is created, type errors appear as warnings in status.typeChecking; they don't stop the policy from being stored or evaluated. Test policies with Warn or Audit before switching to Deny.

Policy engines

Topic 5.4Tools that add reporting, generation, external data and libraries on top of admission.

KyvernoCEL policy types in policies.kyverno.io/v1: ValidatingPolicy, MutatingPolicy, GeneratingPolicy, DeletingPolicy, ImageValidatingPolicyGenerate and clean up resources, verify images, background scans with Policy Reports, external data, CLI tests; can generate native VAPsCNCF graduated (March 2026)

Gatekeeper's model: a ConstraintTemplate defines a new kind (for example K8sRequiredLabels) and its Rego or CEL logic; a Constraint of that kind sets the parameters, what it matches and the enforcementAction (deny by default, or dryrun or warn). Its audit controller also reports violations by objects that already exist.

Kyverno's classic policies are deprecated. "ClusterPolicy, Policy, CleanupPolicy, and the legacy kyverno.io PolicyException are deprecated as of Kyverno v1.19 and will be removed in v1.20." The replacements are the CEL-based types above; kyverno migrate helps convert. Material written before 2026 shows the older kyverno.io/v1 style.

Policies worth enforcing

Choosing a mechanism. Built-in plugins for what they cover; CEL policies (VAP, MAP) for rules about the object in front of you; webhooks or engines when you need external data, lookups of other objects, signature checks, generation or reports. Whatever you use, protect its configuration with RBAC and roll out in warn or audit mode first.

Key takeaways

  • Admission runs after authentication and authorization: mutating, then schema validation, then validating; any rejection fails the request. It sees CREATE, UPDATE, DELETE and CONNECT (so it can block exec), never reads.
  • Built-ins: PodSecurity, ServiceAccount, LimitRanger, ResourceQuota, NamespaceLifecycle and the certificate plugins are on; NodeRestriction (kubeadm enables it), AlwaysPullImages, DenyServiceExternalIPs and ImagePolicyWebhook are off. PSP, SecurityContextDeny and DenyEscalatingExec are gone.
  • Webhooks: failurePolicy Fail by default (Ignore = bypass when down); sideEffects and admissionReviewVersions required; timeout 10 s (max 30); * excludes subresources; mutating webhooks serial, unordered, must be idempotent; HTTPS with caBundle.
  • Good practice: prefer CEL; exclude kube-system and the webhook's own namespace; small timeouts and replicas; protect webhook configs with RBAC, since admission can't protect itself (manifest-based admission, beta in 1.37, can).
  • VAP (GA 1.30): policy plus binding; validationActions Deny, Warn, Audit on the binding; params, variables, matchConditions; type checking only warns. MAP (GA 1.36): ApplyConfiguration or JSONPatch; no validationActions; no DELETE.
  • Engines: Kyverno (graduated; CEL types in policies.kyverno.io/v1; ClusterPolicy deprecated in 1.19), Gatekeeper (Rego ConstraintTemplates, audit, generates VAPs), Kubewarden (sandbox, WebAssembly). Use them for signatures, lookups, generation and reports.
