3.2: Authentication and Authorization

How Kubernetes® decides who is calling (users, ServiceAccounts, certificates, tokens, OIDC) and what they may do (the authorizer chain, RBAC roles and bindings, and the permissions that quietly lead to more).

Overview

Topic 3.2

Authentication. Authorization.

The curriculum PDF lists Authentication; the LF exam page also lists Authorization, so this page covers both. Authentication answers "who is this?" and authorization answers "may they do this?". Both happen in the API server before admission (topic 2.1, which also covers anonymous access and system:masters). The kubelet's own checks and the Node authorizer are in topic 2.2; kubeconfig files and client-side credentials in topic 2.3.

Quotes are from kubernetes.io (CC BY 4.0).

Running example. The shop's web ServiceAccount needs to read Pods and their logs, a developer called Ana needs read access in shop, and an external secret store needs to trust tokens from the cluster.

Identities

Topic 3.2The two kinds of user, and the identity attributes an authenticator produces.

"All Kubernetes clusters have two categories of users: service accounts managed by Kubernetes, and normal users." And: "Kubernetes does not have objects which represent normal user accounts. Normal users cannot be added to a cluster through an API call." People come from outside (certificates, an identity provider); workloads use ServiceAccounts, which are namespaced API objects.

An authenticator produces a username, a UID, groups and extra fields. "All values are opaque to the authentication system and only hold significance when interpreted by an authorizer."

IdentityWho has it
system:authenticatedEvery authenticated request (group)
system:anonymous in system:unauthenticatedRequests with no credentials, if anonymous access is on
system:serviceaccount:<ns>:<name>A ServiceAccount (username, singular)
system:serviceaccounts, system:serviceaccounts:<ns>All ServiceAccounts, and all in one namespace (groups, plural)
system:node:<name> in system:nodesKubelets
system:mastersSuperusers that bypass authorization (topic 2.1)

"The prefix system: is reserved for Kubernetes system use." Several authenticators can be on at once, and "the first module to successfully authenticate the request short-circuits evaluation." kubectl auth whoami (GA v1.28) shows what the API server concluded.

Authenticators have no fixed order. "The API server does not guarantee the order authenticators run in." Authorizers, by contrast, run in exactly the order configured (below).

Authentication methods

Topic 3.2The ways to prove an identity, and which ones suit people in production.

The kubernetes.io hardening guide Authentication Mechanisms advises: "enable as few authentication mechanisms as possible". "For production clusters with multiple users directly accessing the Kubernetes API, it is recommended to use external authentication sources such as OIDC."

MethodHow it worksVerdict and why
X.509 client certificatesA certificate signed by --client-ca-file; CN = username, each O = a groupFine for components; weak for people. Can't be revoked, keys can't be password-protected, groups are fixed for the certificate's life
Static token file--token-auth-file CSV: token, user, uid, groups"Not recommended for production servers": clear text on disk, restart to change, no rotation, no lockout
Bootstrap tokensShort tokens for joining nodes (topic 2.2)Node join only, "not recommended for user authentication"
ServiceAccount tokensSigned JWTs (below)For workloads, not people
OIDC / JWTThe identity provider's id_token as a bearer tokenRecommended for people; keep tokens short-lived, because an id_token "can't be revoked"
Webhook tokenThe API server sends a TokenReview to an external serviceFlexible; needs control plane access, so rarely available on managed services
Authenticating proxyA proxy authenticates the user and passes the identity in headers such as X-Remote-UserWorks if the proxy-to-API-server link is trusted (trap below)

OIDC with structured configuration

The --oidc-* flags support a single issuer. The structured AuthenticationConfiguration (GA v1.34, loaded with --authentication-config) supports several JWT issuers, CEL rules on claims and on the resulting user, and reloads when the file changes:

Trust the company IdP for people (AuthenticationConfiguration) 
apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
jwt:
- issuer:
    url: https://idp.example.com
    audiences:
    - kubernetes
  # reject tokens living over 1 hour
  claimValidationRules:
  - expression: >-
      claims.exp - claims.nbf <= 3600
    message: token lives max 1 hour
  claimMappings:
    username:
      claim: email
      # required when claim is set
      prefix: "oidc:"
    groups:
      claim: groups
      prefix: "oidc:"
  # nobody may become a system: user
  userValidationRules:
  - expression: >-
      !user.username.startsWith('system:')
    message: no system names

The prefix keeps IdP users from colliding with other identities, and the user rule stops a crafted token from claiming a system: name. A failed rule returns 401. Mixing a jwt section with any --oidc-* flag makes the API server exit at startup.

Authenticating proxy headers can be spoofed. The API server trusts X-Remote-User only from a client presenting a certificate signed by --requestheader-client-ca-file. If that CA also signs other certificates, and --requestheader-allowed-names is empty ("If empty, any CN is allowed"), any holder of such a certificate can claim to be anyone. kubernetes.io warns not to reuse a CA "used in another context" for this.

ServiceAccount tokens

Topic 3.2How workload identities get credentials, how long those last, and how to cut them off.

  • Every namespace has a default ServiceAccount, used by any Pod that doesn't set serviceAccountName. It gets "no permissions by default other than the default API discovery permissions", but anything granted to it goes to all those Pods. Give each workload its own ServiceAccount.
  • Pods get a bound token through a projected volume (default since v1.22), mounted at /var/run/secrets/kubernetes.io/serviceaccount. It's bound to the Pod, has an audience and an expiry, and the kubelet refreshes it.
  • The token is a JWT whose sub is system:serviceaccount:<ns>:<name>, plus private claims naming the Pod, node and ServiceAccount, and a unique jti (GA v1.32) that appears in audit logs.
Issue short-lived tokens by hand (shell) 
# 10 minutes, for one audience
kubectl create token web -n shop \
  --duration=10m \
  --audience=https://vault.example.com

# a token that dies with a Pod
kubectl create token web -n shop \
  --bound-object-kind=Pod \
  --bound-object-name=web-0

This needs create on serviceaccounts/token, a powerful permission in its own right. Nothing records issued tokens: "There is no central record of tokens issued".

The default token lasts a year, not an hour. The automatically mounted token shows expirationSeconds: 3607, but with --service-account-extend-token-expiration (default true) the API server extends it "up to 1 year" for older clients, adding a warnafter claim. A stolen default token can work for months unless its Pod is deleted. If an app doesn't call the API, set automountServiceAccountToken: false.

Revoking tokens

"There is no specific mechanism to invalidate a token issued via TokenRequest." A bound token stops working when its Pod, Secret or Node is deleted (within 60 seconds). To kill every token of an account, delete and recreate the ServiceAccount: its new UID invalidates them all. Services that accept ServiceAccount tokens should check them with a TokenReview, which notices deleted Pods at once, rather than validating the JWT offline until it expires.

Secret-based tokens are legacy. Before v1.24, each ServiceAccount automatically got a token Secret that never expired. Since v1.24 none are created, and since v1.30 auto-generated ones unused for a year are invalidated and later deleted. You can still create one by hand: a Secret of type kubernetes.io/service-account-token with the annotation kubernetes.io/service-account.name. kubernetes.io says "These tokens don't expire and don't rotate" and recommends avoiding them. Manually created ones are not cleaned up.

Trusting cluster tokens outside the cluster

ServiceAccount issuer discovery (GA v1.21) makes the API server publish /.well-known/openid-configuration and its signing keys at /openid/v1/jwks. Cloud IAM systems or a secret store can then verify the shop's tokens and exchange them for their own credentials, if the token's audience matches. That's workload identity federation, with no static keys. The design is "OIDC compatible, but not strictly OIDC compliant".

User certificates

Topic 3.2Issuing a client certificate through the API, and living with the fact it can't be revoked.

The CertificateSigningRequest API can issue a user certificate signed by the cluster CA. Ana creates a key and a CSR with /CN=ana/O=devs (username ana, group devs), and an admin submits it:

Request a 1-day certificate for Ana (CertificateSigningRequest) 
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: ana
spec:
  # base64 of ana.csr
  request: LS0tLS1CRUdJTi...
  signerName: >-
    kubernetes.io/kube-apiserver-client
  # 1 day; the minimum is 600
  expirationSeconds: 86400
  usages:
  - client auth
Approve and collect it (shell) 
kubectl get csr
kubectl certificate approve ana
kubectl get csr ana \
  -o jsonpath='{.status.certificate}' \
  | base64 -d > ana.crt

The kube-apiserver-client signer is "never auto-approved". The certificate's lifetime is the smaller of expirationSeconds and the controller manager's --cluster-signing-duration (one year by default). Approving needs the special verb approve on signers, and anyone who can both create and approve these CSRs can mint certificates for "arbitrary names including duplicates of Kubernetes system components".

Certificates can't be revoked. "Any certificate that is issued remains valid until it expires." Mitigations: issue short-lived certificates; grant access through RBAC bindings on the username or group, so removing the binding leaves the certificate authenticated but authorized for nothing; never put users in system:masters, where no binding can be removed; and keep a record yourself, since approved CSR objects are deleted after an hour. For people, prefer OIDC.

Authorization

Topic 3.2The authorizer chain, the attributes it sees, and how to test a permission.

"Access is denied by default." "When multiple authorization modules are configured, each is checked in sequence. If any authorizer approves or denies a request, that decision is immediately returned and no other authorizer is consulted. If all modules have no opinion on the request, then the request is denied" (HTTP 403).

ModeWhat it does
NodeAuthorizes kubelets for their own node's objects (topic 2.2)
RBACRoles and bindings stored as API objects (GA since v1.8); only allows or has no opinion, never denies
Webhook"Synchronous HTTP callout" sending a SubjectAccessReview; the only mode that can explicitly deny
ABACLegacy JSON policy file; "The apiserver will need to be restarted to pick up the new policy lines"
AlwaysAllow, AlwaysDenyTesting only

The default is AlwaysAllow. --authorization-mode "Defaults to AlwaysAllow if --authorization-config is not used". kubeadm sets Node,RBAC. And AlwaysAllow,RBAC "has the same effect as" AlwaysAllow alone, "because Kubernetes RBAC does not provide negative (deny) access rules": RBAC can never stop a request.

What an authorizer sees

Each request carries the user, groups and extra fields, the namespace, the API group, the resource and subresource (for example pods/log), or a non-resource path such as /healthz, and a verb:

HTTPVerb
GET, HEADget (one object), list (collection), watch
POSTcreate
PUT, PATCHupdate, patch
DELETEdelete, deletecollection
Special verbsimpersonate, bind, escalate, approve, sign, attest

list on Secrets is reading Secrets. "The get, list and watch verbs can all return the full details of a resource", so list on secrets "will reveal the data". There's no "list names only" permission. (The use verb belonged to PodSecurityPolicy, removed in v1.25.)

Test permissions (shell) 
# can I create Deployments in shop?
kubectl auth can-i create deployments \
  -n shop

# everything I may do in shop
kubectl auth can-i --list -n shop

# as the web ServiceAccount (needs
# impersonate permission)
kubectl auth can-i get pods/log -n shop \
  --as=system:serviceaccount:shop:web

can-i sends a SelfSubjectAccessReview; --list uses a SelfSubjectRulesReview and warns that the list may be incomplete when a webhook can't list its rules. Components and extension servers use SubjectAccessReview to ask about other users. Two newer refinements: the structured AuthorizationConfiguration (GA v1.32) chains several webhooks with CEL matchConditions and a failurePolicy, and authorization with label and field selectors (GA v1.34) lets a webhook allow, say, listing only Pods on one node.

RBAC objects

Topic 3.2Roles, bindings and their fields, with the shop's permissions as examples.

ObjectScopeHolds
RoleOne namespaceRules: apiGroups, resources, verbs, optional resourceNames
ClusterRoleClusterRules, plus cluster-scoped resources (nodes) and nonResourceURLs
RoleBindingOne namespacesubjects (User, Group, ServiceAccount) and a roleRef to a Role or ClusterRole
ClusterRoleBindingClusterSubjects and a ClusterRole, granted in every namespace

"Permissions are purely additive (there are no 'deny' rules)." A RoleBinding can refer to a ClusterRole: the rights then apply only in the binding's namespace, which is how the built-in view or edit roles are reused per namespace.

Let web read Pods and logs in shop (Role and RoleBinding) 
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-log-reader
  namespace: shop
rules:
# "" is the core API group
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: web-reads-pods
  namespace: shop
subjects:
- kind: ServiceAccount
  name: web
  namespace: shop
# immutable once created
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-log-reader
The same with kubectl, plus Ana's access (shell) 
kubectl create role pod-log-reader \
  --verb=get,list,watch \
  --resource=pods,pods/log -n shop

kubectl create rolebinding web-reads \
  --role=pod-log-reader \
  --serviceaccount=shop:web -n shop

# built-in view, in shop only
kubectl create rolebinding ana-view \
  --clusterrole=view \
  --user=ana@example.com -n shop
  • resourceNames limits a rule to named objects. "You cannot restrict deletecollection or top-level create requests by resource name." list and watch can be limited only if the client asks with a metadata.name field selector. An empty list means all names.
  • Wildcards (*) also cover resource types and verbs added later, so avoid them.
  • Aggregated ClusterRoles use aggregationRule.clusterRoleSelectors to combine other ClusterRoles by label. The built-in roles grow this way through labels such as rbac.authorization.k8s.io/aggregate-to-edit, so installing a CRD can widen edit.

roleRef can't be changed. Updating it gives a validation error: delete and recreate the binding, or use kubectl auth reconcile. Subjects can be changed, which is why update on a binding doesn't let anyone switch which role it grants.

Default roles and escalation

Topic 3.2The built-in roles, the guard against self-promotion, and permissions that lead to more.

RoleCanCan't
cluster-adminAnything, anywhere; bound by default to group system:mastersNothing is off limits
adminRead and write most namespace resources, including Roles and RoleBindings thereChange ResourceQuotas or the Namespace itself
editRead and write most objects, including Secrets, and run Pods as any ServiceAccountView or change Roles and RoleBindings
viewRead most objectsRead Secrets, or Roles and RoleBindings

edit means every ServiceAccount's rights. It "allows accessing Secrets and running Pods as any ServiceAccount in the namespace, so it can be used to gain the API access levels of any ServiceAccount in the namespace." view excludes Secrets because "reading the contents of Secrets enables access to ServiceAccount credentials".

Escalation prevention

"The RBAC API prevents users from escalating privileges by editing roles or role bindings", and this applies "even when the RBAC authorizer is not in use". You can create or update a role only if you already hold every permission in it, unless you have the escalate verb. You can create a binding only if you hold every permission in the referenced role, unless you have the bind verb on that role. So escalate and bind are themselves escalation permissions.

Permissions that lead to more

The RBAC good practices page lists the dangerous ones:

PermissionWhy it's dangerous
list or watch on SecretsReveals every Secret's contents
Creating workloadsMount any Secret, ConfigMap or volume in the namespace, run as any ServiceAccount; "boundaries within a namespace should be considered weak"
Creating PersistentVolumeshostPath volumes give host filesystem access (topic 2.3)
nodes/proxyExec into any container through the kubelet, bypassing audit and admission
escalate, bind, impersonateGrant yourself more, or act as someone with more
CSR create and approveMint certificates for any name
create on serviceaccounts/tokenIssue tokens for any ServiceAccount in scope
Admission webhook configurationsRead, and change, every object admitted
Modifying NamespacesLower the Pod Security level through its labels (topic 3.1)
  • Least privilege: namespace RoleBindings over ClusterRoleBindings, no wildcards, no day-to-day cluster-admin (use a low-privilege account plus impersonation when needed), and nobody in system:masters.
  • ServiceAccounts: from best to worst, a Role for an app-specific ServiceAccount, then the default account, then all accounts in a namespace, then all accounts cluster-wide. Avoid anything granted to all ServiceAccounts cluster-wide.
  • Review regularly: look for unused or overly broad bindings, and bindings to system:unauthenticated. "If an attacker is able to create a user account with the same name as a deleted user, they can automatically inherit all the rights of the deleted user."

Reviewing RBAC. Built in: kubectl auth can-i --list --as=... and kubectl get rolebindings,clusterrolebindings -A -o wide. Third-party tools (none of them CNCF projects) include kubectl-who-can, rbac-lookup, rakkess, rbac-tool and audit2rbac, which builds roles from audit logs.

Key takeaways

  • No User objects: people come from certificates or an IdP; workloads use namespaced ServiceAccounts (system:serviceaccount:<ns>:<name>, groups system:serviceaccounts[:<ns>]). Authenticators have no guaranteed order.
  • For people use OIDC (structured AuthenticationConfiguration, GA 1.34: multiple issuers, CEL rules, username prefix). Static tokens: not for production. Client certificates can't be revoked. Protect the request-header CA of an authenticating proxy.
  • ServiceAccount tokens: bound, projected, audience-scoped; kubectl create token --duration --audience. The default mounted token is extended to about a year. No auto token Secrets since 1.24; manual ones never expire or get cleaned up. Revoke by deleting the Pod or recreating the ServiceAccount; validate with TokenReview.
  • CSR API: signer kubernetes.io/kube-apiserver-client, never auto-approved, expirationSeconds at least 600; keep certificates short and grant through removable bindings.
  • Authorizers run in order; first allow or deny wins; all no-opinion = 403. Default --authorization-mode is AlwaysAllow (kubeadm: Node,RBAC). RBAC never denies; webhooks can.
  • RBAC: Role, ClusterRole, RoleBinding (can reuse a ClusterRole in one namespace), ClusterRoleBinding. roleRef is immutable. resourceNames can't limit create or deletecollection. list on Secrets reveals them.
  • edit = Secrets plus every ServiceAccount in the namespace; view = no Secrets; admin manages namespace RBAC. Escalation prevention is bypassed by escalate and bind; also watch impersonate, nodes/proxy, PV creation, CSR approval, token creation, webhook configs and namespace edits.
