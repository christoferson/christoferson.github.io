3.5: Audit Logging

The API server's record of who did what in a Kubernetes® cluster: how to turn it on, what to record at which level, where the records go, and how to use them to spot an attack.

Overview

Topic 3.5

Audit Logging.

This page covers Kubernetes API auditing: what it records, the policy that decides how much, the backends that store it, the fields in each event, and how teams use the records for detection and investigation. Auditing is a detective control (topic 1.2). Runtime detection inside containers, and observability more broadly, are in topic 5.2.

Quotes are from kubernetes.io (CC BY 4.0) and the Falco documentation (CC BY 4.0).

Running example. Someone read the shop's db-creds Secret last night, and someone else opened a shell in an API Pod. The platform team wants audit logging that answers who did both, without writing Secret values into the log.

What auditing records

Topic 3.5The questions audit answers, and the stages and levels of each record.

"Kubernetes auditing provides a security-relevant, chronological set of records documenting the sequence of actions in a cluster. The cluster audits the activities generated by users, by applications that use the Kubernetes API, and by the control plane itself." It answers: what happened, when, who initiated it, on what, where it was observed, from where it was initiated, and to where it was going.

Auditing happens in one place: "Audit records begin their lifecycle inside the kube-apiserver component." The kubelet, scheduler, controller manager and etcd have no audit log of their own; their API calls are audited because they go through the API server.

StageWhen it's generated
RequestReceived"As soon as the audit handler receives the request", before it's processed
ResponseStartedAfter the response headers, before the body; "only generated for long-running requests (e.g. watch)"
ResponseComplete"The response body has been completed"
PanicWhen the request handling panicked
LevelRecords
NoneNothing
Metadata"Requesting user, timestamp, resource, verb, etc." but no request or response body
RequestMetadata plus the request body
RequestResponseMetadata plus request and response bodies

Bodies are never recorded for non-resource requests such as /healthz. Auditing also costs something: it "increases the memory consumption of the API server", depending on the policy.

Auditing is off by default. "If the flag is omitted, no events are logged": without --audit-policy-file there's nothing. A policy also needs a backend, and leaving out --audit-log-path "disables log backend". A policy with no rules is invalid. kubeadm doesn't turn auditing on, so on a self-managed cluster you must configure it.

Audit policy

Topic 3.5Writing rules that record what matters, without recording secrets or noise.

A policy (audit.k8s.io/v1, kind Policy) is an ordered list of rules. "A request may match multiple rules, in which case the FIRST matching rule is used. The default audit level is None, but can be overridden by a catch-all rule at the end of the list." Within a rule, every field must match: users, userGroups, verbs, resources (group, resources, resourceNames), namespaces and nonResourceURLs. An empty field matches everything.

The shop cluster's audit policy (Policy) 
apiVersion: audit.k8s.io/v1
kind: Policy
# one event per request stage is enough
omitStages: ["RequestReceived"]
rules:
# 1. drop noisy, low-risk traffic
- level: None
  users: ["system:kube-proxy"]
  verbs: ["watch"]
  resources:
  - group: ""
    resources: ["endpoints", "services"]
- level: None
  nonResourceURLs:
  - "/healthz*"
  - "/livez*"
  - "/readyz*"
# 2. who touched secrets, never values
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets", "configmaps"]
  - group: authentication.k8s.io
    resources: ["tokenreviews"]
# 3. who exec'd or attached
- level: Metadata
  resources:
  - group: ""
    resources: ["pods/exec","pods/attach"]
# 4. full record of RBAC changes
- level: RequestResponse
  verbs: [create, update, patch, delete]
  resources:
  - group: rbac.authorization.k8s.io
# 5. catch-all, always last
- level: Metadata

Order decides, not specificity. If a broad Request rule came before rule 2, Secret reads would match it first and their values would be written to the log. Put specific rules first and the catch-all last. Also, resources: ["pods"] doesn't match subresources such as pods/exec or pods/log; list them, or use pods/*. The group is "" for core APIs and never includes a version.

The kubernetes.io example policy follows the same shape: RequestResponse for Pods, Metadata for Pod logs and status, None for kube-proxy watches and routine read-only URLs, Request for ConfigMaps in kube-system, Metadata for Secrets and ConfigMaps elsewhere, and a catch-all Metadata. Note that requestObject is recorded "prior to version conversion, defaulting, admission or merging": it shows what the client sent, not what was stored.

Backends

Topic 3.5Where events are written, with what defaults, and how to keep them safe.

BackendKey flags and defaults
Log file--audit-log-path (- means stdout), format json, mode blocking. Rotation: --audit-log-maxsize 100 MB, --audit-log-maxage 366 days and --audit-log-maxbackup 100 files (since v1.36); --audit-log-compress gzips old files
Webhook--audit-webhook-config-file (kubeconfig format: where to send and how to authenticate), mode batch (buffer 10,000 events, batches of up to 400), 10-second initial backoff

Both can run at once. In blocking mode the API server waits for each event to be written but ignores write errors. blocking-strict fails the whole request if logging at the RequestReceived stage fails. In batch mode, "if the rate of incoming events overflows the buffer, events are dropped."

Turn on auditing (kube-apiserver flags) 
P=/etc/kubernetes/audit
L=/var/log/kubernetes/audit
kube-apiserver \
  --audit-policy-file=$P/policy.yaml \
  --audit-log-path=$L/audit.log \
  --audit-log-maxage=30 \
  --audit-log-maxbackup=10 \
  --audit-log-compress

When the API server runs as a static Pod, "remember to mount the hostPath to the location of the policy file and log file, so that audit records are persisted":

Mounts in kube-apiserver.yaml (static Pod excerpt) 
# in the kube-apiserver container
volumeMounts:
- name: audit-policy
  mountPath: /etc/kubernetes/audit
  readOnly: true
- name: audit-log
  mountPath: /var/log/kubernetes/audit
# in the Pod spec
volumes:
- name: audit-policy
  hostPath:
    path: /etc/kubernetes/audit
    type: Directory
- name: audit-log
  hostPath:
    path: /var/log/kubernetes/audit
    type: DirectoryOrCreate

Retention defaults changed in v1.36. Before v1.36, --audit-log-maxage and --audit-log-maxbackup defaulted to 0, so old rotated files were never deleted and could fill the disk. Since v1.36 the defaults are 366 days and 100 files, and --audit-log-maxsize=0 now turns rotation off. Dynamic audit configuration (the AuditSink API, alpha from v1.13) was removed in v1.19: configuration is static flags only. And the "Securing a Cluster" page still calls the audit logger "a beta feature"; it has been GA since v1.12.

Protecting the logs

The Security Checklist has one item for this: "Audit logs, if enabled, are protected from general access." The API server creates the log file with mode 0600. Because an attacker who gets into the control plane would want to erase their tracks, forward events off the cluster, to a SIEM or other store that the cluster's own credentials can't modify. On managed services the provider writes the audit log and exports it to its logging service, often only if you turn that on.

Reading an audit event

Topic 3.5The fields of an audit record, and which ones can be trusted.

Each line of the log is one audit.k8s.io/v1 Event. "The configuration of an Audit Event configuration is different from the Event API object": these records are never stored in etcd. The Secret read from the running example:

Who read db-creds (audit Event, trimmed) 
{
  "kind": "Event",
  "apiVersion": "audit.k8s.io/v1",
  "level": "Metadata",
  "auditID": "7d0f2c1e-5b8a-4c11",
  "stage": "ResponseComplete",
  "verb": "get",
  "user": {
    "username": "ana@example.com",
    "groups": ["devs",
      "system:authenticated"]
  },
  "sourceIPs": ["10.0.4.17"],
  "userAgent": "kubectl/v1.37.2",
  "objectRef": {
    "resource": "secrets",
    "namespace": "shop",
    "name": "db-creds",
    "apiVersion": "v1"
  },
  "responseStatus": {"code": 200},
  "stageTimestamp":
    "2026-11-08T01:15:02.125901Z",
  "annotations": {
    "authorization.k8s.io/decision":
      "allow"
  }
}
FieldWhat it tells you
auditIDThe same ID on every stage of one request
user, impersonatedUserWho called. With impersonation, user is the real caller and impersonatedUser the identity they used
user.extraFor ServiceAccount tokens, authentication.kubernetes.io/credential-id holds JTI=..., the token's unique ID (GA v1.32); for client certificates, X509SHA256=...
verb, objectRefThe action and the object: resource, subresource, namespace, name, API group
responseStatus.codeThe result: 200, 401, 403 and so on
annotationsAdded by authorization (authorization.k8s.io/decision and reason), Pod Security (pod-security.kubernetes.io/audit-violations, topic 3.1) and admission policies; not the object's own annotations
sourceIPs, userAgentHints only: "All but the last IP can be arbitrarily set by the client", and the user agent "must not be trusted"

Detecting attacks

Topic 3.5Patterns to look for in audit events, and tools that watch for them.

ActivityWhat to filter on
Shells in PodsobjectRef.subresource is exec, attach or portforward (filter on the subresource; the verb varies by protocol)
Secret harvestingsecrets with get, list or watch; kubernetes.io suggests alerting on "concurrent reading of multiple Secrets by a single user"
Privilege changesWrites in rbac.authorization.k8s.io, especially bindings to cluster-admin
ImpersonationAny event with impersonatedUser
Anonymous accesssystem:anonymous or system:unauthenticated
Permission probingBursts of 403s (decision: forbid) from one user or ServiceAccount
Risky PodsPod Security audit-violations, or requestObject fields such as privileged (needs the Request level for Pods)
Who exec'd into which Pod (shell, using jq) 
L=/var/log/kubernetes/audit/audit.log
jq -c 'select(.objectRef.subresource
    == "exec")
  | [.stageTimestamp,
     .user.username,
     .objectRef.namespace,
     .objectRef.name]' "$L"
  • Falco (CNCF graduated) reads audit events through its k8saudit plugin, usually as the API server's webhook backend, and ships rules for privileged Pods, sensitive host mounts and broad grants. Its docs recommend running the receiver outside the audited cluster, "so that audit event collection does not depend on the integrity of the cluster being audited". There are variants for the main managed services.
  • SIEMs and log platforms correlate audit events with other sources over time.
  • audit2rbac works the other way round: it "takes a Kubernetes audit log and username as input, and generates RBAC role and binding objects" covering what that user actually did, which helps tighten roles to least privilege.

What auditing can't see

Topic 3.5The paths that bypass the API server, and what covers them instead.

BypassWhy it's invisibleCover it with
Kubelet API (10250)"Direct access to the kubelet API is not subject to admission control and is not logged by Kubernetes audit logging" (topic 2.2)Restrict nodes/proxy and the port; the kubelet's SubjectAccessReview calls do appear in the audit log
etcdDirect access "is not logged by Kubernetes audit logging"Network and certificate controls (topic 2.1)
Container runtime socketNever touches the API serverForbid hostPath mounts; runtime detection
Static Pod manifestsRun by the kubelet from files"Regularly audit and centrally report all access" to those directories
Inside a containerAudit records the exec, not the commands typed afterwardsRuntime security tools such as Falco watching system calls

Node components keep their own operational logs: "On machines with systemd, the kubelet and container runtime write to journald. Otherwise, they write to .log files in the /var/log directory." These aren't audit records, but correlating them with audit events by node, time and Pod helps reconstruct an incident.

Answering the running example. The db-creds read appears as a Metadata event with verb: get on secrets, showing the user, source and time but not the value. The shell appears as an event on pods/exec. What was typed in that shell is only visible to runtime detection.

Key takeaways

  • Only kube-apiserver audits. It's off by default: you need --audit-policy-file and a backend (--audit-log-path or a webhook). A policy with no rules is invalid; unmatched requests get None.
  • Stages: RequestReceived, ResponseStarted (long-running only), ResponseComplete, Panic. Levels: None, Metadata, Request, RequestResponse; bodies never for non-resource URLs.
  • First matching rule wins. Secrets, ConfigMaps and TokenReviews at Metadata only; drop noise with None; RequestResponse for RBAC writes; catch-all Metadata last. pods doesn't match pods/exec.
  • Log backend: JSON, blocking, rotation at 100 MB, keep 366 days and 100 files (defaults since 1.36). Webhook: batch, drops on overflow. Mount the policy and log directories into the static Pod. AuditSink was removed in 1.19.
  • Protect logs (file mode 0600, restricted access) and forward them off-cluster. Events have user and impersonatedUser, objectRef, responseStatus and annotations (authorization decision, Pod Security violations). The token's JTI is in user.extra. Don't trust sourceIPs or userAgent.
  • Watch for exec, attach and port-forward, Secret reads, RBAC changes, impersonation, anonymous access and 403 bursts; Falco's k8saudit plugin automates this. Auditing can't see kubelet API calls, etcd, the runtime socket, static Pods, or commands typed inside a container.
