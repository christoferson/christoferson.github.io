Overview

Topic 5.3

PKI. Connectivity.

The curriculum gives only the names. This page takes PKI to mean the cluster's own certificate infrastructure plus the ways workloads get certificates, and connectivity to mean securing connections into the cluster (Ingress, Gateway), to the control plane (API endpoints, Konnectivity), out of it (egress) and between clusters. Already covered: kubeadm certificate commands and lifetimes (topic 2.1), kubelet bootstrap and serving certificates (topic 2.2), user certificates through the CSR API (topic 3.2), TLS Secrets (topic 3.3) and mesh mTLS (topic 5.2).

Quotes are from kubernetes.io (CC BY 4.0), gateway-api.sigs.k8s.io, cert-manager.io and the Istio and Cilium documentation.

Running example. Customers reach the shop at shop.example.com through a Gateway; its certificate comes from cert-manager. The Gateway re-encrypts traffic to the web Service, and the platform team manages the cluster's own CAs.

The cluster's PKI

Topic 5.3The certificate authorities a cluster runs on, and what each one signs.

CA (kubeadm path)Signs
kubernetes-ca (ca.crt)The API server's serving certificate, its kubelet client certificate, kubelet client certificates, and the admin, controller manager and scheduler kubeconfigs; also the trust root for client certificates (--client-ca-file)
etcd-ca (etcd/ca.crt)etcd server, peer and health-check certificates, and the API server's etcd client certificate
kubernetes-front-proxy-caThe front-proxy client certificate, used only by the aggregation layer for extension API servers

The ServiceAccount key pair, sa.key and sa.pub, is separate: a bare key pair that signs and verifies tokens, not a CA. The API server's serving certificate must name every address clients use: its host name and IPs, the load balancer, and kubernetes, kubernetes.default through kubernetes.default.svc.cluster.local.

Check a certificate's names and expiry (shell) 
cd /etc/kubernetes/pki
openssl x509 -in apiserver.crt -noout \
  -subject -enddate -ext subjectAltName

# exit code 1 if it expires in 30 days
openssl x509 -in apiserver.crt -noout \
  -checkend 2592000

Protecting the CAs

  • The Security Checklist: "The root certificate is protected (either an offline CA, or a managed online CA with effective access controls)", "Intermediate and leaf certificates have an expiry date no more than 3 years in the future", and etcd's CA "should be unique to etcd".
  • The three cluster CAs can be intermediates under an organization root: "You can create a single root CA, controlled by an administrator. This root CA can then create multiple intermediate CAs".
  • kubeadm external CA mode: provide ca.crt without ca.key, and kubeadm leaves signing to you, keeping the CA private key off the cluster. "kubeadm cannot manage certificates signed by an external CA." The controller manager can then run as a standalone CSR signer with the key elsewhere.
  • Key algorithm: kubeadm's encryptionAlgorithm is RSA-2048 by default; RSA-3072, RSA-4096, ECDSA-P256 and ECDSA-P384 are allowed (the kubeadm certificate task page omits P384).

Two certificate details people miss. The generic certificates table gives the API server's kubelet client certificate the group system:masters; kubeadm uses the less privileged kubeadm:cluster-admins instead. And the CertificateSubjectRestriction admission plugin (on by default) rejects CSRs that ask for the system:masters group, but it can't stop someone who has the CA key itself.

Rotation and revocation

Topic 5.3Keeping certificates fresh, and why replacing a CA is hard.

  • Leaf certificates: kubeadm issues one-year certificates and renews them on every control plane upgrade, or with kubeadm certs renew. It never renews CAs.
  • Kubelets: client certificates rotate automatically (stable since v1.19), renewing "between 30% and 10% of the time remaining". Serving certificates rotate with serverTLSBootstrap, but those requests are never auto-approved (topic 2.2).
  • No revocation: Kubernetes doesn't check revocation lists, so a leaked client certificate works until it expires. Keep lifetimes short and grant access through RBAC bindings you can remove (topic 3.2).

Replacing a CA

"Kubeadm does not support rotation or replacement of CA certificates out of the box." The manual procedure runs a dual-trust phase so nothing breaks mid-way:

  1. Trust bothDistribute the new CA, then configure the controller manager, API servers, scheduler, kubelets, kubeconfigs, webhooks and aggregated API servers to trust old and new together.
  2. ReissueSign new certificates for the API server, kubelet client and front-proxy with the new CA, and restart each component in turn.
  3. Roll workloadsRestart every Pod that talks to the API server so it picks up the new CA bundle, using PodDisruptionBudgets to keep services up.
  4. Remove the old CAOnce nothing logs TLS errors, take the old CA out of every bundle and kubeconfig.

Why CA rotation is disruptive. Every component, kubeconfig, kubelet and in-cluster client trusts the CA, so all of them must change and restart. The procedure assumes a highly available control plane: "Configurations with a single API server will experience unavailability while the API server is being restarted." That's a reason to protect CA keys well enough never to need it in a hurry.

Certificates for workloads

Topic 5.3Signers, trust bundles and the new Pod Certificates.

The CertificateSigningRequest API (certificates.k8s.io/v1) routes each request to a signer named in spec.signerName:

SignerForAuto-approved?
kubernetes.io/kube-apiserver-clientClient certificates the API server acceptsNever
kubernetes.io/kube-apiserver-client-kubeletKubelet client certificates (system:node:<name>, no SANs)May be
kubernetes.io/kubelet-servingKubelet serving certificatesNever
kubernetes.io/kube-apiserver-servingAPI server serving certificates, CA published as a ClusterTrustBundleSigned outside the controller manager
kubernetes.io/legacy-unknownOld behaviourCan't be requested in the v1 API
Custom, such as example.com/servingYour own CA, through a controller that holds the sign verbYour approver decides

Approval decides who trusts whom: "The ability to approve CSRs should not be granted broadly or lightly." And for workload certificates, kubernetes.io warns that CSR-signed certificates use "a dedicated CA" and that relying on the cluster root for this is something "you should never rely on".

kube-root-ca.crt isn't a workload CA. The controller manager publishes the ConfigMap kube-root-ca.crt in every namespace, and Pods mount it to verify the API server. Use it "to verify internal Kubernetes endpoints" only, not to trust your own services' certificates.

ClusterTrustBundles (GA in v1.37)

A ClusterTrustBundle is a cluster-scoped object holding CA certificates for Pods to trust. A bundle linked to a signer must be named <domain>:<path>:<suffix>, and writing it needs the attest verb on that signer. Pods mount bundles through a projected volume, and the kubelet keeps the file current.

The shop's internal CA, as a trust bundle (ClusterTrustBundle) 
apiVersion: certificates.k8s.io/v1
kind: ClusterTrustBundle
metadata:
  # signer example.com/mtls as prefix
  name: example.com:mtls:roots-2026
  labels:
    trust: live
spec:
  signerName: example.com/mtls
  trustBundle: |
    -----BEGIN CERTIFICATE-----
    ...
    -----END CERTIFICATE-----

Trust bundles are world-readable. "ClusterTrustBundle objects should be considered world-readable within the cluster": every ServiceAccount can list them by default. Put only public CA certificates in them, never keys.

Pod Certificates (GA in v1.37)

A podCertificate projected volume asks for an X.509 certificate for the Pod. The kubelet generates the private key on the node, creates a PodCertificateRequest, and a signer issues it with no separate approval step. Unlike a ServiceAccount token, which is a bearer token, the key never leaves the workload.

An mTLS client certificate for a Pod (Pod volume excerpt) 
volumes:
- name: creds
  projected:
    sources:
    - podCertificate:
        signerName: example.com/mtls
        keyType: ECDSAP256
        maxExpirationSeconds: 86400
        # key and chain in one file
        credentialBundlePath: bundle.pem
    - clusterTrustBundle:
        signerName: example.com/mtls
        path: ca-roots.pem

Lifetimes run from 1 hour to 91 days (default 24 hours). credentialBundlePath is preferred over separate key and certificate files, because otherwise the kubelet "may rotate the credentials after your first read and before your second read". NodeRestriction ensures a node can request certificates only for Pods actually running on it.

No signer comes with Kubernetes. The v1.37 announcement: "Because the Kubernetes project does not yet ship any Pod Certificate signers in core, in order to try these features out, you will need to install a third-party signer." What goes in the certificate (a SPIFFE ID or not) depends on that signer. SPIRE remains the established way to issue SPIFFE identities.

cert-manager

Topic 5.3Automating certificates for Ingress, Gateways and Pods.

cert-manager (CNCF graduated) issues and renews certificates from Issuer (namespaced) or ClusterIssuer objects of type ACME (for example Let's Encrypt, with HTTP-01 or DNS-01 challenges), CA, Vault, CyberArk (formerly Venafi) or SelfSigned, plus external issuers for cloud CAs.

The shop's public certificate (cert-manager Certificate) 
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: web
  namespace: shop
spec:
  # kubernetes.io/tls Secret it writes
  secretName: web-tls
  dnsNames:
  - shop.example.com
  # 90 days, renew 15 days before
  duration: 2160h
  renewBefore: 360h
  privateKey:
    algorithm: ECDSA
    size: 256
    rotationPolicy: Always
  issuerRef:
    name: letsencrypt
    kind: ClusterIssuer
  • Since v1.18 (June 2025), rotationPolicy: Always is the default: "a new private key is generated each time a re-issuance is triggered" (it used to be Never). By default a certificate lasts 90 days and renews at two-thirds of its life.
  • The annotation cert-manager.io/cluster-issuer on an Ingress or Gateway makes cert-manager create the Certificate automatically. Prefer dnsNames to commonName: clients match the subject alternative names.
  • trust-manager distributes CA bundles to every namespace. Its v0.26.0 release removed two compromised roots from its default public CA bundle, a reminder that default trust stores need patching too.
  • The csi-driver mounts certificates straight into Pods without a Secret: "private keys never leave the node".

Check version support. cert-manager 1.21 (current at v1.21.3) is tested on Kubernetes 1.33 to 1.36. Support for 1.37 is expected with cert-manager 1.22, due around November 2026.

TLS at the edge

Topic 5.3Terminating, passing through and re-encrypting TLS at Ingress and Gateways.

An Ingress "assumes TLS termination at the ingress point (traffic to the Service and its Pods is in plaintext)". The Ingress API is frozen, and kubernetes.io recommends Gateway API, whose TLS model is richer:

HTTPS listener using a certificate in another namespace (Gateway and ReferenceGrant) 
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: edge
  namespace: infra
spec:
  gatewayClassName: example
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: shop.example.com
    tls:
      # the default mode
      mode: Terminate
      certificateRefs:
      - kind: Secret
        group: ""
        name: web-tls
        namespace: shop
---
# must live in the Secret's namespace
apiVersion: gateway.networking.k8s.io/v1
kind: ReferenceGrant
metadata:
  name: infra-gw-to-secrets
  namespace: shop
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: Gateway
    namespace: infra
  to:
  - group: ""
    kind: Secret
Re-encrypt from the Gateway to the web Service (BackendTLSPolicy) 
apiVersion: gateway.networking.k8s.io/v1
kind: BackendTLSPolicy
metadata:
  name: web-backend-tls
  namespace: shop
spec:
  targetRefs:
  - group: ""
    kind: Service
    name: web
  validation:
    # SNI; the backend cert must match
    hostname: web.shop.svc
    caCertificateRefs:
    - group: ""
      kind: ConfigMap
      name: shop-ca
Gateway API TLS featureWhat it doesStatus
Listener Terminate / PassthroughTerminate at the Gateway, or pass encrypted traffic to the backend by SNI ("TLS settings do not take effect")Core
ReferenceGrantAllows a cross-namespace reference; only valid in the target's namespacev1 since v1.5
BackendTLSPolicyTLS from the Gateway to a backend, verifying its certificate; the CA must be in the Service's namespaceStandard since v1.4 (October 2025)
Frontend client certificate validationmTLS from clients, set at Gateway level in spec.tls.frontendStandard since v1.5 (February 2026)
Backend client certificateThe Gateway presents its own certificate to backendsStandard since v1.5

Frontend mTLS is per Gateway, not per listener. It's configured once in spec.tls.frontend "to mitigate security risks associated with HTTP/2 and TLS connection coalescing", with optional per-port overrides. Its AllowInsecureFallback mode accepts clients without valid certificates and "should be used with caution". Material from before 2025 that calls BackendTLSPolicy v1alpha3 or experimental is out of date.

Control plane connectivity

Topic 5.3How users and the control plane reach the cluster safely.

  • The API endpoint: "External Internet access to the Kubernetes API server should be restricted to not expose the API publicly. Be careful, as many managed Kubernetes distributions are publicly exposing the API server by default." Options: an IP allow-list on a public endpoint (which doesn't apply to the private one), a private endpoint reachable only from the cloud network or VPN, or a bastion host.
  • Konnectivity (beta since v1.18) replaces the deprecated SSH tunnels for control-plane-to-node traffic. Agents on the nodes dial out to the Konnectivity server and authenticate with a ServiceAccount token (audience system:konnectivity-server), so nodes need no inbound port from the control plane. The API server is configured through an EgressSelectorConfiguration (apiserver.k8s.io/v1beta1) with cluster, etcd and controlplane routes, over a local socket or mutual TLS.
  • TLS settings for the API server, controller manager, scheduler and kubelet: --tls-min-version (VersionTLS12 or VersionTLS13), --tls-cipher-suites (the help text marks RC4, 3DES and plain TLS_RSA_* suites as "Insecure"; TLS 1.3 suites aren't configurable), and --tls-curve-preferences (new in v1.36) for key exchange.

Key takeaways

  • Three CAs: kubernetes-ca, etcd-ca (unique to etcd), front-proxy-ca; plus sa.key/sa.pub, a key pair, not a CA. Protect the root (offline, or a well-controlled managed CA); leaf and intermediate certificates under 3 years. External CA mode keeps the CA key off the cluster.
  • kubeadm renews leaf certificates (one year) but never CAs. CA rotation is manual: trust both, reissue, roll Pods, remove the old one; single API servers go down. No revocation: keep certificates short-lived.
  • Signers: kube-apiserver-client and kubelet-serving are never auto-approved; kube-apiserver-client-kubelet may be; legacy-unknown can't be requested; custom signers need sign. kube-root-ca.crt verifies only the API server.
  • ClusterTrustBundle and Pod Certificates are GA in 1.37 (certificates.k8s.io/v1): world-readable CA bundles; kubelet-generated keys and per-Pod certificates (1 hour to 91 days, use credentialBundlePath). No signer ships in core.
  • cert-manager: Issuers and ClusterIssuers (ACME, CA, Vault, CyberArk, SelfSigned); 90-day default, renew at two-thirds; rotationPolicy: Always default since 1.18; trust-manager for bundles; csi-driver for Secret-free certificates.
  • Edge: Ingress terminates at the edge (plaintext behind). Gateway: Terminate (default) or Passthrough; ReferenceGrant in the Secret's namespace; BackendTLSPolicy GA (v1.4) re-encrypts; frontend mTLS at Gateway level (v1.5).
  • Control plane: don't expose the API publicly (managed defaults often do); Konnectivity (beta) instead of SSH tunnels; set TLS 1.2+ and strong ciphers. Egress: NetworkPolicy plus egress gateways (a mesh gateway alone isn't enforcement). Multi-cluster: shared roots, mTLS, encrypted tunnels.
