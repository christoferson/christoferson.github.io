Overview

Topic 4.1

Kubernetes Trust Boundaries and Data Flow.

The curriculum gives only the name. This page takes it to mean the map behind every Kubernetes threat model: what a trust boundary is, which zones a cluster divides into, which data flows cross between them, and how each crossing is authenticated and encrypted by default. The other Domain 4 pages walk through what attackers do on that map (topics 4.2 and 4.3), and the formal methods such as STRIDE and MITRE ATT&CK® are in topic 6.2.

Sources: kubernetes.io (CC BY 4.0); the 2019 Kubernetes security audit by Trail of Bits and Atredis Partners and the CNCF® Financial User Group attack trees (both in Apache-2.0 repositories); the CNCF Cloud Native Security Whitepaper (CC BY 4.0); OWASP (CC BY-SA 4.0, quoted briefly). The 2022 NCC Group audit report forbids copying, so it's paraphrased.

Running example. The shop's security review starts by drawing its threat model: who and what talks to whom, through which component, and with what proof of identity. This page builds that map.

Trust boundaries and data flows

Topic 4.1The vocabulary of threat modeling, and why boundaries are where to look.

A trust boundary is a line where the level of trust changes. OWASP: trust boundaries "represent the change of trust levels as the data flows through the application", and "Boundaries show any location where the level of trust changes." Microsoft's Threat Modeling Tool gives examples: "Corporate networks, internet, machine, sandbox, user/kernel mode". Data crossing a boundary is where checks belong, and where attacks happen.

Threat models are usually drawn as data flow diagrams with five kinds of element:

ElementMeaningKubernetes example
External entitySomething outside the system that interacts with itAn administrator with kubectl, a CI pipeline, a shop customer
ProcessCode that handles datakube-apiserver, kubelet, a Pod
Data storeSomewhere data is kept; "Data stores do not modify the data, they only store data"etcd, a PersistentVolume, an image registry
Data flowData moving between elementsAn API request, an image pull, a database query
Trust boundaryWhere the trust level changesInternet to cluster, control plane to node, host to container

The CNCF whitepaper describes the method: start with "identifying all important processes, data stores, and security boundaries", then "model how these elements interact, with special attention paid to any interactions that cross security boundaries". Its "end-to-end architecture" view includes the source code and build pipeline too, not just the running cluster. kubernetes.io's Cloud Native Security page puts it as one step: "Build a threat model of your system or application that identifies trust boundaries."

The Kubernetes trust zones

Topic 4.1The zones Kubernetes' own audit divided a cluster into, and the attackers it considered.

The 2019 CNCF-funded security audit (Trail of Bits and Atredis Partners, on Kubernetes 1.13.4) produced a threat model that groups components "based on shared criticality, rather than physical placement". Zones "capture logical boundaries where controls should or could be enforced by the system".

ZoneDescription (2019 threat model)Components
Internet"The externally facing, wider internet zone."kubectl users, application clients
API Server"The central coordinator for the system, exposed only as much as needed for access from administrators"kube-apiserver
Master ComponentsInternal control plane parts that "work via callbacks and subscriptions to the API server"Controller managers, scheduler
Master DataThe data layer, "tantamount to 'root' or administrative access to the cluster when accessed in an uncontrolled fashion"etcd
Worker"All the components required to run and network containers"kubelet, kube-proxy
Container"The actual Linux containers"The container runtime and workloads

Today the "master" zones would be called the control plane. The model also named three attackers: a malicious internal user (an administrator or developer abusing their access, or someone with stolen credentials); an internal attacker "who had transited one or more trust boundaries, such as an attacker with container access"; and an external attacker, unauthenticated, who "will seek to transit network edges in order to become Internal Attackers".

  • The audit's broad findings: policies can be silently ineffective when the component that enforces them is missing; many channels carried credentials without the strongest TLS settings; and hosts "should be treated as a separate security domain from the cluster itself".
  • The 2022 audit, by NCC Group on Kubernetes 1.24, framed the cluster by actors (platform, node, cluster and namespace administrators, workloads, external users) and found that several 2019 issues were still open.
  • The CNCF Financial User Group ran STRIDE workshops "to identify potential security issues at the trust boundaries within the platform". Its attack trees are named for what attackers want: access sensitive data, attacker on the network, compromised container, denial of service, establish persistence, malicious code execution. Those are the threats on the next two pages.

The life of a Deployment

Topic 4.1Following one change through the cluster, boundary by boundary.

The attack-tree project mapped what happens when a user applies a Deployment. Condensed, with the shop's API as the example:

  1. Developer to API server (crosses: outside to control plane)kubectl sends the Deployment over TLS; the API server authenticates, authorizes and runs admission (topic 2.1).
  2. API server to etcd (crosses: into cluster data)The object is stored over mutual TLS.
  3. Controllers and scheduler (within the control plane)The Deployment controller creates a ReplicaSet and Pods; the scheduler binds each Pod to a node. Both talk to the API server, never to etcd.
  4. Kubelet to API server (crosses: node to control plane)The node's kubelet watches for Pods bound to it, using its node certificate; the Node authorizer limits what it sees.
  5. Runtime to registry (crosses: node to supply chain)The runtime pulls shop/api if it isn't cached (topic 1.3).
  6. Kubelet to runtime (crosses: host to container)Over the local CRI socket; the runtime creates the containers inside namespaces and cgroups (topic 2.2).
  7. kube-proxy (within the node)Watches Services and EndpointSlices and programs the rules that send api traffic to the new Pod.

Each step is a place to ask: who could pretend to be the sender, change the data, or read it on the way?

The weak crossings

Topic 4.1Directions and paths where default protection is thin or missing.

kubernetes.io's control plane and node communication page uses a "hub-and-spoke" pattern: "All API usage from nodes (or the pods they run) terminates at the API server." That direction "is secured by default and can run over untrusted and/or public networks." The reverse direction is not:

Control plane to node is the weak direction. "By default, the API server does not verify the kubelet's serving certificate, which makes the connection subject to man-in-the-middle attacks and unsafe to run over untrusted and/or public networks." The API server's proxy to nodes, Pods and Services uses plain HTTP by default, and even with https: it "will not validate the certificate". Fixes: --kubelet-certificate-authority with CA-signed kubelet certificates, kubelet authentication and authorization, and a private control plane network or the Konnectivity proxy (beta since v1.18), which replaces the deprecated SSH tunnels.

Flows that skip the API server

Some paths never cross the API server, so they skip authentication, admission and audit logging (topic 3.5):

  • The kubelet API: "Direct access to the kubelet API is not subject to admission control and is not logged by Kubernetes audit logging."
  • etcd: "Any certificate issued by a certificate authority that etcd trusts allows full access to the data stored inside etcd."
  • The runtime socket: "An attacker with access to this socket can launch new containers or interact with running containers."
  • Static Pods: "The API server doesn't manage these static Pods"; one that fails admission "still runs on the node".

In a threat model, mark each of these as a boundary crossing with weak or no checks, and decide how to compensate.

Where the boundaries sit

Topic 4.1The cluster's main trust boundaries, what crosses them and what guards them.

BoundaryWhat crosses itMain controls
Internet and clusterAdmin API calls, customer trafficPrivate or allow-listed API endpoint, TLS, authentication; Ingress or Gateway TLS; limits on LoadBalancer and NodePort

Containers in one PodShared network namespace and volumesBarely a boundary: treat the Pod as one unit

Cluster and cloud accountMetadata, node and controller cloud credentialsBlock metadata, least-privilege roles, workload identity
Cluster and supply chainImages, manifests, pipeline credentialsDigests, signatures, admission policy, pull-based GitOps (topic 5.1)

Within this map, the control plane and kubelets are trusted infrastructure, and workloads are untrusted. kubernetes.io's multi-tenancy page describes sandboxing for cases "where workloads are assumed to be malicious". So the most important boundary for a workload is the one between its container and the node, and the most important crossing for an attacker is the step from a compromised container into the Worker or control plane zones.

The shop's threat model, in one sentence per boundary. Customers reach only web through the Gateway. Developers reach the API server only through the company's identity provider. The api Pod reaches the database and nothing else, and has no token mount. Nodes block the metadata service. Images come only from the private registry, by digest. Each sentence names a crossing and the control that guards it.

Key takeaways

  • A trust boundary is where the level of trust changes; data flow diagrams show external entities, processes, data stores, data flows and boundaries. Focus on flows that cross boundaries, end to end (code and pipeline included).
  • The 2019 Kubernetes threat model had six zones: Internet, API Server, Master Components, Master Data (etcd: tantamount to root), Worker, Container. Attackers: malicious insider, internal attacker (already crossed a boundary, e.g. from a container), external attacker.
  • Node to control plane is secure by default. Control plane to node is weak: kubelet certificates aren't verified, and the API server proxy is plain HTTP. Use --kubelet-certificate-authority, kubelet authn and authz, and private networks or Konnectivity.
  • Flows that bypass the API server, and so admission and audit: the kubelet API, etcd (any trusted certificate = full access), the runtime socket, static Pods.
  • Default weak spots: Pod-to-Pod is allow-all and plaintext; Ingress TLS ends at the ingress; Pods reach cloud metadata; ServiceAccount tokens are mounted; webhooks see every object they match.
  • Boundaries: internet and cluster, API server and etcd, control plane and nodes, host and container (the kernel, the key one for workloads), Pod (weak), namespaces, cloud account, supply chain. Control plane and kubelets are trusted; workloads aren't.
