Overview

Topic 3.4

Isolation and Segmentation. Network Policy.

The curriculum gives only these names. This page takes isolation and segmentation to mean the Kubernetes-level ways to separate workloads and tenants: namespaces, RBAC scoping, quotas and the multi-tenancy patterns built from them. Network policy means the NetworkPolicy API in depth, plus the cluster-wide ClusterNetworkPolicy. Kernel and node isolation (sandboxes, dedicated nodes) are in topic 1.2; the Pod network, CNI and DNS in topic 2.3.

Quotes are from kubernetes.io (CC BY 4.0) and the Kubernetes network-policy-api project (Apache-2.0).

Running example. The shop runs in its own shop namespace: web calls api on port 8080, and api calls db on 5432. Nothing else should get in or out, apart from DNS.

Namespaces as a boundary

Topic 3.4What a namespace separates, and what it leaves shared.

"In Kubernetes, namespaces provide a mechanism for isolating groups of resources within a single cluster." Their scoping "is applicable only for namespaced objects (e.g. Deployments, Services, etc.) and not for cluster-wide objects (e.g. StorageClass, Nodes, PersistentVolumes, etc.)." Many security policies are scoped to a namespace: Roles and RoleBindings, NetworkPolicies, ResourceQuotas, LimitRanges and Pod Security labels.

Which Secrets and ConfigMaps a Pod can mountThe network: "all pods in a Kubernetes cluster are allowed to communicate with each other" by default
Service names (short names resolve within the namespace)DNS: "the Kubernetes DNS service allows lookups across all namespaces"

kubectl api-resources --namespaced=false lists the cluster-scoped kinds.

Namespace names can hijack DNS. A namespace named like a public top-level domain (say com) gives its Services short names that overlap with public DNS, so lookups "without a trailing dot will be redirected to those services". The fix: "limit privileges for creating namespaces to trusted users". Also avoid the reserved kube- prefix.

Sharing a cluster safely

Topic 3.4The patterns for putting several teams or customers on shared infrastructure.

"While Kubernetes does not have first-class concepts of end users or tenants, it provides several features to help manage different tenancy requirements." The most important is authorization: "If teams or their workloads can access or modify each others' API resources, they can change or disable all other types of policies thereby negating any protection those policies may offer." A common practice is "to isolate every workload in its own namespace, even if multiple workloads are operated by the same tenant."

PatternIsolatesCost and limits
Namespace per tenantNamespaced objects, with RBAC, quotas, NetworkPolicies and Pod Security"Negligible resource cost", but "difficult to configure" and doesn't cover CRDs, StorageClasses or webhooks
Virtual control plane per tenantEach tenant gets its own API server, controller manager and etcd on a shared host clusterIsolates non-namespaced objects, but "do[es] not solve isolation problems in the data plane"
Dedicated nodesThe machines (topic 1.2)The API server and network remain shared
Dedicated clusterEverythingStrongest, but cost and operations scale with the number of clusters

Tools come and go. The Hierarchical Namespace Controller (HNC) was archived in 2025, and in 2025 kubernetes.io removed its references to it and to other third-party multi-tenancy projects. Capsule, a namespace-based multi-tenancy operator, is a CNCF sandbox project; vCluster, a popular virtual-cluster tool, is not a CNCF project.

Quotas and limits

Topic 3.4Stopping one namespace from exhausting the cluster or its control plane.

A ResourceQuota "provides constraints that limit aggregate resource consumption per namespace" and can "limit the quantity of objects that can be created in a namespace by API kind". Object counts protect the control plane too: "Too many Secrets in a cluster can actually prevent servers and controllers from starting", and a misconfigured CronJob creating Jobs "can lead to a denial of service."

Cap the shop namespace (ResourceQuota) 
apiVersion: v1
kind: ResourceQuota
metadata:
  name: shop-quota
  namespace: shop
spec:
  hard:
    # sums across all Pods
    requests.cpu: "4"
    limits.memory: 8Gi
    # also protects the Pod IP pool
    pods: "20"
    # object count limit
    count/secrets: "30"
Defaults for Pods that set nothing (LimitRange) 
apiVersion: v1
kind: LimitRange
metadata:
  name: shop-defaults
  namespace: shop
spec:
  limits:
  - type: Container
    # request if none is set
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    # limit if none is set
    default:
      cpu: 500m
      memory: 256Mi
    max:
      cpu: "1"
      memory: 512Mi

Quotas change what Pods must declare. With a CPU or memory quota, every new Pod "must specify either requests or limits for that resource", or it can be rejected with 403. A LimitRange supplies defaults so users don't have to remember. Quotas don't affect objects that already exist, and "cannot protect against all kinds of resource sharing, such as network traffic". Restrict who can edit or delete the quota itself.

  • Priority: "In a cluster where not all users are trusted, a malicious user could create Pods at the highest possible priorities, causing other Pods to be evicted". A ResourceQuota scoped to PriorityClass prevents this.
  • API load: API Priority and Fairness can split requests into flows ByUser or ByNamespace, so one tenant "will not be able to starve requests for resources in other namespaces" (topic 2.1).

How NetworkPolicy works

Topic 3.4The rules that decide whether a connection is allowed.

NetworkPolicy (networking.k8s.io/v1, GA since v1.7) controls traffic "at the IP address or port level (OSI layer 3 or 4)". "Creating a NetworkPolicy resource without a controller that implements it will have no effect": the network plugin must support it.

  1. Isolation is per Pod and per direction"By default, a pod is non-isolated for egress; all outbound connections are allowed." A Pod becomes isolated for a direction once any policy that selects it lists that direction in policyTypes.
  2. Rules only allow"Network policies do not conflict; they are additive." What's allowed is the union of all applicable policies, so "order of evaluation does not affect the policy result". There's no deny rule.
  3. Both ends must agree"Both the egress policy on the source pod and the ingress policy on the destination pod need to allow the connection."
  4. Replies are automaticPolicies apply to connections: "Reply traffic for those allowed connections will also be implicitly allowed."

Leaving out policyTypes. "If no policyTypes are specified on a NetworkPolicy then by default Ingress will always be set and Egress will be set if the NetworkPolicy has any egress rules." A policy meant to block all egress must list Egress explicitly.

Choosing peers

  • podSelector in a rule picks Pods in the policy's own namespace. namespaceSelector picks every Pod in matching namespaces; an empty one ({}) means all namespaces. Namespaces can't be named directly, so select them by the automatic label kubernetes.io/metadata.name (GA v1.22).
  • ipBlock (cidr with optional except) is meant for "cluster-external IPs, since Pod IPs are ephemeral and unpredictable". NAT and load balancers may hide the real source address.
  • ports takes a protocol (TCP, the default, UDP or SCTP), a port number or name, and optionally endPort for a range (GA v1.25).

Combining selectors is the classic trap. Compare:

AND: Pods labelled role=client in namespaces labelled user=alice 
ingress:
- from:
  # one element: both must match
  - namespaceSelector:
      matchLabels:
        user: alice
    podSelector:
      matchLabels:
        role: client
OR: any Pod in user=alice namespaces, or role=client here 
ingress:
- from:
  # two elements: either may match
  - namespaceSelector:
      matchLabels:
        user: alice
  - podSelector:
      matchLabels:
        role: client

One dash opens a whole namespace. The only difference is the - before podSelector. kubernetes.io: "Be careful to use correct YAML syntax", and "When in doubt, use kubectl describe to see how Kubernetes has interpreted the policy." The multi-tenancy page also advises against an empty namespaceSelector when allowing traffic between namespaces.

Some traffic is always allowed. Traffic to and from the Pod's own node is allowed "regardless of the IP address of the Pod or the node", and "a pod cannot block access to itself". Only TCP, UDP and SCTP are guaranteed to be filtered; for ICMP or ARP "the behaviour is undefined".

Default deny for the shop

Topic 3.4Building an allow list: deny everything, then open only the flows the app needs.

The Security Checklist asks for "default network policies within each namespace, selecting all pods, denying everything", because "default network policies that block all egress and ingress ... can be useful to adopt an allow list approach to ensure that no workloads are missed."

1. Deny all traffic in shop (NetworkPolicy) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: shop
spec:
  # every Pod in shop
  podSelector: {}
  # isolated both ways, no rules
  policyTypes:
  - Ingress
  - Egress
2. Allow DNS to CoreDNS (NetworkPolicy) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: shop
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    # one element: namespace AND Pod
    - namespaceSelector:
        matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: In
          values: [kube-system]
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53

Default-deny egress breaks DNS. kubernetes.io added this caution in 2026: "A default deny-all egress policy also blocks DNS traffic." Allow UDP and TCP port 53 to the CoreDNS Pods (label k8s-app=kube-dns in kube-system).

3. The API accepts only web, on 8080 (NetworkPolicy) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-from-web
  namespace: shop
spec:
  # the Pods this protects
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  # from web AND on this port
  - from:
    - podSelector:
        matchLabels:
          app: web
    ports:
    - protocol: TCP
      port: 8080

Because egress is denied too, each flow needs both ends opened: an egress policy on web allowing app=api on 8080, then the same pair for api to db on 5432 (ingress on db, egress on api). The finished set:

FlowEgress sideIngress side
Any Pod to DNSallow-dns-egressNone needed, unless kube-system has its own policies
web to api :8080On app=web, to app=apiapi-from-web
api to db :5432On app=api, to app=dbOn app=db, from app=api
Internet to webNoneFrom the ingress controller's namespace and Pods

What NetworkPolicy can't do

Topic 3.4The documented gaps, and the extensions that fill some of them.

kubernetes.io lists what you can't do with network policies "(at least, not yet)":

  • Force traffic through a common gateway, or "anything TLS related" (use a service mesh or ingress controller).
  • Target nodes by identity, or Services by name (select Pods or namespaces by label instead).
  • Apply default policies to all namespaces, or explicitly deny ("the model for NetworkPolicies are deny by default, with only the ability to add allow rules").
  • Log network security events, or query reachability.
  • Block loopback or traffic from the Pod's own node.

There are also timing and scope gaps. A new Pod "may be started unprotected" if it's created before the network plugin has processed the policy. Whether a policy change affects existing connections is implementation-defined. And for hostNetwork Pods the behaviour "is undefined": most implementations treat their traffic as node traffic, so selectors don't see them.

CiliumNetworkPolicy and CiliumClusterwideNetworkPolicy (cilium.io/v2)Layer 7 HTTP rules, DNS name (toFQDNs) rules, and deny rules that "take precedence over allow policies", cluster-wide
Calico GlobalNetworkPolicy (projectcalico.org/v3)Cluster-wide, ordered policies with Allow, Deny, Log and Pass actions, tiers, and host endpoints

ClusterNetworkPolicy

Topic 3.4Cluster-wide rules that administrators set and namespace owners can't override.

ClusterNetworkPolicy comes from the Kubernetes network-policy-api project. It's a CRD in policy.networking.k8s.io, not a built-in API: you install it and need a supporting plugin (kube-network-policies, Calico v3.32+, Kube-OVN). It replaced AdminNetworkPolicy and BaselineAdminNetworkPolicy: "AdminNetworkPolicy becomes a ClusterNetworkPolicy with tier=Admin and BaselineAdminNetworkPolicy becomes a ClusterNetworkPolicy with tier=Baseline."

OrderLayerRole
1Admin tier"Takes precedence over all other policies": guardrails namespace owners can't override
2NetworkPolicyOrdinary policies; "always makes a final decision for selected pods"
3Baseline tierCluster-wide defaults that NetworkPolicy can override

Each rule has an action: Accept (allow, and stop evaluating), Deny ("Drops the selected traffic") or Pass (skip the rest of this tier and let the next tier decide). Within a tier, priority runs from 0 to 1000 and the lower number wins.

Keep sandbox namespaces out of prod (ClusterNetworkPolicy) 
apiVersion:
  policy.networking.k8s.io/v1beta1
kind: ClusterNetworkPolicy
metadata:
  # cluster-scoped, no namespace
  name: block-sandbox
spec:
  # namespace owners can't override
  tier: Admin
  priority: 10
  subject:
    namespaces:
      matchLabels:
        env: prod
  ingress:
  - name: deny-sandbox
    action: Deny
    from:
    - namespaces:
        matchLabels:
          env: sandbox

The API is new and still moving. ClusterNetworkPolicy was announced in October 2025, released as v1alpha2 in April 2026 (when the old Allow action was renamed Accept), and reached v1beta1 in release v0.3.0 on 6 November 2026; both versions are served. Older material uses AdminNetworkPolicy and BaselineAdminNetworkPolicy. Unlike NetworkPolicy, it has no implicit isolation: Pods it selects aren't denied anything unless a rule says so.

Testing policies

Topic 3.4Checking that policies do what you meant, and one lifecycle bug to know.

See and test the shop's policies (shell) 
kubectl get networkpolicy -n shop
kubectl describe networkpolicy \
  api-from-web -n shop

# from a Pod without app=web:
# this should time out
kubectl run t --rm -it -n shop \
  --image=busybox:1.36 -- \
  wget -T 2 -qO- http://api:8080

# the same with the web label works
kubectl run t --rm -it -n shop \
  --labels=app=web \
  --image=busybox:1.36 -- \
  wget -T 2 -qO- http://api:8080

NetworkPolicy itself has no logs. Plugin tools fill the gap: Cilium's Hubble shows flows and verdicts, Calico has flow logs, and visual editors help draft policies.

CVE-2024-7598: policies could vanish first. "The order in which objects are deleted during namespace termination is not defined, and it is possible for network policies to be deleted before the pods that they protect." That left a brief window where Pods ran without their restrictions (rated Low, 3.1). Ordered namespace deletion, which deletes Pods before other resources, fixed it: on by default from v1.33 and GA in v1.34. The GitHub issue still says "Fixed Versions - None".

Key takeaways

  • Namespaces scope names, RBAC, quotas, NetworkPolicies and Pod Security, but not Nodes, PVs, StorageClasses, CRDs, webhooks or ClusterRoles, and not the network or DNS. Don't use default in production; kube-public is readable by everyone; restrict namespace creation (TLD names hijack DNS).
  • Multi-tenancy: RBAC matters most. Namespace per tenant (cheap, can't isolate cluster-scoped objects), virtual control plane (isolates the API, not the data plane), dedicated nodes, dedicated clusters. HNC archived; Capsule is sandbox; vCluster isn't CNCF.
  • ResourceQuota limits totals and object counts (count/secrets, pods); a CPU or memory quota forces requests or limits on every Pod, so pair it with a LimitRange. Use PriorityClass-scoped quotas against priority abuse.
  • NetworkPolicy: needs a supporting CNI; isolation per Pod per direction; allow-only and additive; both ends must allow; replies automatic. Omitting policyTypes = Ingress, plus Egress only if egress rules exist.
  • One from element with namespaceSelector and podSelector = AND; two elements = OR. Select namespaces by kubernetes.io/metadata.name. ipBlock is for external IPs. Node traffic and a Pod's traffic to itself are always allowed.
  • Default deny all, then allow DNS (UDP and TCP 53 to k8s-app=kube-dns), then each flow at both ends. NetworkPolicy has no L7, TLS, logging, deny rules, cluster-wide defaults or Service-name targets: use Cilium or Calico CRDs, a mesh, or ClusterNetworkPolicy.
  • ClusterNetworkPolicy (CRD, v1beta1 since November 2026): tiers Admin, then NetworkPolicy, then Baseline; actions Accept, Deny, Pass; lower priority number wins. CVE-2024-7598 was fixed by ordered namespace deletion (GA 1.34).
