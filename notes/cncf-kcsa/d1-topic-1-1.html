Overview

Topic 1.1

The 4Cs of Cloud Native Security. Cloud Provider and Infrastructure Security.

The curriculum gives only these two topic names. This page takes the 4Cs to mean the layered model (Cloud, Cluster, Container, Code) from a kubernetes.io page that has since been retired, along with the lifecycle model that replaced it. It takes cloud provider and infrastructure security to mean the layer under Kubernetes: who is responsible for what, how the control plane and nodes are exposed on the network, what the cluster may do in the cloud account, the instance metadata API, etcd, and the node operating system.

Quotes are from kubernetes.io (including the retired page, at a pinned commit), the CNCF® Glossary and the CNCF TAG Security Cloud Native Security Whitepaper v2, all CC BY 4.0. Cloud providers are named only as examples.

Running example. A small web shop (frontend, API, database and a background worker) runs in the shop namespace of a Kubernetes cluster on a public cloud. This page looks at what protects it from below: the cloud account, the network, etcd and the nodes.

The 4Cs

Topic 1.1The layered model: what each C covers and how the layers depend on each other.

The old kubernetes.io page "Overview of Cloud Native Security" said: "You can think about security in layers. The 4C's of Cloud Native security are Cloud, Clusters, Containers, and Code." Its diagram drew them as nested boxes, with Cloud on the outside and Code in the middle.

LayerWhat it coversExamples from the old page
CloudThe cloud, co-located servers or corporate data center: "the trusted computing base of a Kubernetes cluster"API server not public, nodes reachable only from the control plane, least-privilege cloud API access, etcd limited to the control plane, disks encrypted at rest
ClusterThe configurable cluster components, and the applications that run in the clusterRBAC, authentication, Secrets encrypted at rest, Pod Security Standards, quality of service and resource management, network policies, TLS for Ingress
ContainerThe images and the runtimeScan images for known vulnerabilities, sign images and enforce signatures, don't run as privileged users, use a runtime with stronger isolation
CodeThe application itself: "one of the primary attack surfaces over which you have the most control"TLS for all traffic (mTLS between services), limit ports, scan third-party dependencies, static analysis, dynamic probing for SQL injection, CSRF and XSS

The key idea is dependency: "Each layer of the Cloud Native security model builds upon the next outermost layer." The page went on: "You cannot safeguard against poor security standards in the base layers by addressing security at the Code level." In other words, perfectly written code still falls if the node or the cloud account is compromised.

The page called this "layered approach" a way to augment defense in depth: several independent controls, so that when one fails another still stands. The CNCF Glossary has no entry for defense in depth, but the whitepaper uses the idea throughout, for example "least privilege must be applied at every layer of the stack".

Order matters. Outermost to innermost: Cloud, Cluster, Container, Code. A question that asks which layer the others depend on is asking about Cloud. A question about the layer you control most directly is asking about Code.

The 4Cs page was removed from kubernetes.io on 16 February 2024 (pull request #43176). The last versioned docs that include it are v1.28, and its URL now redirects to the Security section. The pull request said the page was "not really giving readers a good overview of how to secure a Kubernetes cluster", and set out to align the docs with the CNCF whitepaper. The issue behind it said its author was "not convinced" the 4Cs model was useful to learn. Only the cloud provider links table survived. The KCSA curriculum still lists the 4Cs, so learn the model, but know that current sources use lifecycle phases. The last version is preserved on GitHub.

The 4Cs come from kubernetes.io, not from the CNCF. The CNCF Cloud Native Security Whitepaper never uses the term "4C". It describes a foundational layer, the application lifecycle and the runtime environment. An answer that credits the 4Cs to the whitepaper is wrong.

Lifecycle phases

Topic 1.1The model kubernetes.io uses now: security controls for each phase of an application's life.

The page that replaced the 4Cs, Cloud Native Security and Kubernetes, starts from the whitepaper: it "defines security controls and practices that are appropriate to different lifecycle phases". The whitepaper says "the lifecycle is composed of four continuous phases; Develop, Distribute, Deploy, and Runtime."

PhaseGoalExample controls
DevelopKeep development environments trustworthy and design with security in mindZero trust design, security-aware code review, a threat model that names trust boundaries, fuzzing
DistributeSecure the supply chain for images and other componentsScan images and artifacts, sign them, keep dependencies updated, use a private registry that restricts pulls
Deploy"Ensure appropriate restrictions on what can be deployed, who can deploy it, and where it can be deployed."Verify image signatures at admission, use namespaces for isolation
RuntimeProtect the running system, in "three critical areas: access, compute, and storage"Access: API authentication and authorization, TLS. Compute: Pod Security Standards, a minimal node OS, AppArmor or seccomp. Storage: encryption at rest, tested backups

The two models fit together. The Cloud layer of the 4Cs is what the Deploy phase calls the foundation: "That infrastructure must provide the security guarantees that higher layers expect." The CNCF Glossary defines cloud native security as "an approach that builds security into cloud native applications", making sure "security is part of the entire application lifecycle from development to production". Its shift left entry describes moving tests and security "early in the software development lifecycle".

Matching a control to a phase. Scanning and signing are Distribute. Checking signatures before a Pod is admitted is Deploy. A seccomp profile on a running container is Runtime. Threat modeling and code review are Develop.

Shared responsibility

Topic 1.1Which security tasks the cloud provider takes on and which stay with you.

Cloud providers publish a shared responsibility model: they secure what they run, and you secure what you build and configure on top. kubernetes.io doesn't use the term, but its production environment page describes the split: with a managed control plane, the provider handles "the scale and availability of the cluster's control plane, as well as ... patches and upgrades". The whitepaper notes that provider offerings "reduce the overhead for enterprises as part of the shared responsibility model".

AreaSelf-managed clusterManaged Kubernetes service
Data center, hardware, hypervisorProvider if on IaaS; you if on premisesProvider
Control plane hosts and etcdYou: flags, certificates, etcd TLS, encryption, backupsProvider, with options you choose (for example encryption with a cloud key service)
Worker node OS and patchingYouUsually you, unless the nodes are provider-managed
Cloud permissions for nodes and PodsYouYou
Workloads, images, RBAC, network policies, SecretsYouYou

For provider-specific details, kubernetes.io keeps a table of each provider's security pages on its Security page: Alibaba Cloud, Amazon Web Services, Google Cloud, Huawei Cloud, IBM Cloud, Microsoft Azure, Oracle Cloud Infrastructure, Tencent Cloud and VMware vSphere.

Managed does not mean private or locked down. The Security Checklist warns that "many managed Kubernetes distributions are publicly exposing the API server by default." Your workloads, RBAC and network policies are always your job, whoever runs the control plane.

Network exposure and ports

Topic 1.1Keeping the API server, kubelets and etcd off the internet, and knowing which ports they use.

The Security Checklist sets the baseline: "The Kubernetes API, kubelet API and etcd are not exposed publicly on Internet." The old 4Cs page gave the same advice per component:

  • API server: not reachable from the internet, with network access control lists "restricted to the set of IP addresses needed to administer the cluster". The checklist suggests a bastion host for admin access. Providers also offer allow-lists of authorized networks or private endpoints (often called "private clusters").
  • Nodes: "only accept connections ... from the control plane on the specified ports", plus traffic for NodePort and LoadBalancer Services, and ideally not on the public internet at all.
  • etcd: reachable from the control plane only (see Protecting etcd).

Default ports

From the kubernetes.io Ports and Protocols reference. "All default port numbers can be overridden."

PortComponentWhere
6443 (TCP)Kubernetes API serverControl plane
2379-2380 (TCP)etcd (2379 client API, 2380 peer traffic)Control plane
10250 (TCP)Kubelet APIEvery node
10259 (TCP)kube-schedulerControl plane
10257 (TCP)kube-controller-managerControl plane
10256 (TCP)kube-proxy (health checks)Worker nodes
30000-32767 (TCP and UDP)NodePort ServicesWorker nodes

The quickest check from a laptop is which API endpoint your kubeconfig points at:

Where is the API server? (shell) 
# the control plane URL in use
kubectl cluster-info

# every server URL in kubeconfig
kubectl config view \
  -o jsonpath='{..server}'

For the web shop, a public IP in that URL with no allow-list means anyone on the internet can try to authenticate to the cluster.

The kubelet's built-in defaults are permissive. When the kubelet runs without a configuration file, --anonymous-auth defaults to true and --authorization-mode to AlwaysAllow. The checklist calls these settings "overly permissive". The old read-only port 10255 has no authentication at all. It isn't in the ports table, and in the kubelet configuration file readOnlyPort defaults to 0 (disabled), but the deprecated command-line flag still defaults to 10255. Production clusters should turn on kubelet authentication and authorization (topic 2.2).

Ports worth memorizing: 6443 API server, 2379 and 2380 etcd, 10250 kubelet, 10259 scheduler, 10257 controller manager, 30000-32767 NodePort. Older material may list 10251 and 10252 for the scheduler and controller manager. Those were the old insecure ports, and they are no longer in the table.

Cloud API and metadata

Topic 1.1Limiting what the cluster can do in the cloud account, and keeping Pods away from node credentials.

Least privilege for the cluster

The control plane and nodes call the cloud API to attach disks, create load balancers and so on. The old page advised giving the cluster "cloud provider access that follows the principle of least privilege for the resources it needs to administer". Give the control plane and nodes only the permissions they need. Give Pods their own workload identity instead of letting them borrow the node's.

The instance metadata API

Cloud VMs can query a local metadata service, usually at the link-local address 169.254.169.254. The kubernetes.io task Securing a Cluster explains the risk: "By default these APIs are accessible by pods running on an instance and can contain cloud credentials for that node, or provisioning data such as kubelet credentials. These credentials can be used to escalate within the cluster or to other cloud services under the same account."

Its mitigations are to "limit permissions given to instance credentials, use network policies to restrict pod access to the metadata API, and avoid using provisioning data to deliver secrets." The checklist puts it as one line: "Access from the workloads to the cloud metadata API is filtered."

Block the metadata API for the shop (NetworkPolicy) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: block-cloud-metadata
  namespace: shop
spec:
  # {} selects every Pod in shop
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - ipBlock:
        # allow all IPv4 ...
        cidr: 0.0.0.0/0
        # ... except the metadata IP
        except:
        - 169.254.169.254/32

Once a policy selects a Pod for Egress, only the traffic the policy lists is allowed. This rule allows everything except the metadata address, so DNS and calls to the database keep working. Network policies are covered in full in topic 3.4.

Apply and test it (shell) 
kubectl apply -f block-cloud-metadata.yaml
kubectl get networkpolicy -n shop

# should time out now
kubectl run t --rm -it -n shop \
  --image=busybox:1.36 -- \
  wget -T 3 -qO- http://169.254.169.254/

A NetworkPolicy has blind spots. It only works if the network plugin enforces policies, and kubernetes.io notes that most implementations don't apply them to Pods with hostNetwork: true. Such a Pod can still reach the metadata API. Some providers also offer an IPv6 metadata address, which an IPv4-only rule doesn't cover. Restrict hostNetwork Pods with Pod Security (topic 3.1) as well.

Provider-side controls work too. Some providers can require a session token for metadata requests and limit how many network hops the reply may travel. A hop limit of 1 keeps the reply from reaching containers that don't use host networking. Providers differ on whether to allow Pods any access (one AWS guide suggests a limit of 2 for container hosts, its Kubernetes guide suggests 1 to block Pods), so check the provider's own docs.

Protecting etcd

Topic 1.1Limiting access to the cluster's datastore, encrypting traffic to it and encrypting the data it stores.

etcd stores every object in the cluster, including Secrets. kubernetes.io is blunt about the risk: "Access to etcd is equivalent to root permission in the cluster so ideally only the API server should have access to it." Securing a Cluster adds that write access "is equivalent to gaining root on the entire cluster, and read access can be used to escalate fairly quickly."

TLS between the API server and etcd

The checklist asks for mutual TLS (mTLS), and says "The certificate authority for this should be unique to etcd." etcd requires client certificates signed by that CA, and the API server presents one. kubernetes.io notes that "etcd authentication is not planned for Kubernetes", so use certificates rather than etcd user accounts. The flags, with the file names kubeadm uses under /etc/kubernetes/pki/:

FlagSet onkubeadm file
--etcd-cafilekube-apiserveretcd/ca.crt
--etcd-certfilekube-apiserverapiserver-etcd-client.crt
--etcd-keyfilekube-apiserverapiserver-etcd-client.key
--client-cert-auth=trueetcd(turns on client certificate checks)
--trusted-ca-fileetcdetcd/ca.crt
--peer-cert-file, --peer-key-fileetcdetcd/peer.crt, etcd/peer.key

Also put etcd behind a firewall that only the API servers can get through, and encrypt its backups: a snapshot holds the same data.

Encryption at rest

TLS protects data in transit; the disk is a separate problem. kubernetes.io: "By default, the API server stores plain-text representations of resources into etcd, with no at-rest encryption." To turn encryption on, write an EncryptionConfiguration file and pass it to the API server with --encryption-provider-config.

Encrypt Secrets in etcd (EncryptionConfiguration) 
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      # first provider encrypts new writes
      - secretbox:
          keys:
            - name: key1
              secret: <BASE64-KEY>
      # still reads old plain-text data
      - identity: {}

The first provider in the list encrypts new writes. The others are tried in order when data is read. Existing Secrets stay in plain text until they are written again:

Rewrite every Secret with the new key (shell) 
kubectl get secrets -A -o json \
  | kubectl replace -f -
ProviderProtection
identityNone: "does not provide any confidentiality protection"
aescbcRated "Weak"; not recommended because of padding oracle attacks
aesgcmMust be rotated every 200,000 writes
secretboxStrong (XSalsa20 and Poly1305), but the key sits on the control plane host
kms v2Strongest: envelope encryption with keys in an external key service; stable since v1.29 (KMS v1 deprecated in v1.28)

Two common mistakes. If identity is first in the list, nothing is encrypted. And the kubernetes.io example uses aescbc, which the same page rates "Weak". For local keys use secretbox; in production prefer kms v2. The old 4Cs etcd row, by contrast, was about encrypting the disk itself. The checklist asks for both.

Hardening the nodes

Topic 1.1Reducing the attack surface of the machines that run containers.

For node operating systems, kubernetes.io recommends a specialized, typically read-only container OS that provides only the services needed to run containers. Such systems "present a reduced attack surface in case of a container escape." The CNCF Glossary's immutable infrastructure entry describes the same idea: infrastructure "that cannot be changed once deployed", which is replaced rather than patched in place.

  • Patch and replace nodes regularly, and rotate infrastructure credentials: Securing a Cluster advises short-lived certificates and revoking bootstrap tokens once a node has joined.
  • Isolate sensitive workloads on their own nodes or in sandboxed runtimes, so a container breakout on a shared node doesn't reach them (topic 1.2).
  • Check configuration against a benchmark. The CIS Kubernetes Benchmark is a consensus configuration guide for the control plane, etcd and nodes, with variants for managed services. kube-bench, an open-source tool from Aqua Security (not a CNCF project), checks a cluster against it.

CIS Benchmarks are guides, not proof. A clean kube-bench report shows that the configuration matches the benchmark's checks at that moment. It doesn't make a cluster secure on its own or certify compliance. Compliance frameworks are covered in topic 6.1.

Key takeaways

  • 4Cs, outermost to innermost: Cloud, Cluster, Container, Code. Each layer builds on the next outer one; good code can't make up for weak base layers. The model is from kubernetes.io, not the CNCF whitepaper, and was removed from kubernetes.io on 2024-02-16.
  • Lifecycle phases (current model, from the CNCF whitepaper): Develop, Distribute, Deploy, Runtime. Runtime covers access, compute and storage.
  • Shared responsibility: the provider secures what it runs (with a managed service, the control plane and etcd). You always own workloads, RBAC, network policies, Secrets and the cloud permissions you grant. Managed API servers are often public by default.
  • Keep the API server (6443), kubelet (10250) and etcd (2379-2380) off the internet. Kubelet defaults without a config file are anonymous and AlwaysAllow.
  • Give the cluster least-privilege cloud access. Block Pods from the metadata API at 169.254.169.254 with an egress NetworkPolicy, keeping in mind that hostNetwork Pods slip past it.
  • etcd access equals root on the cluster: mTLS with its own CA, API servers only. Encryption at rest is off by default; use EncryptionConfiguration with secretbox or KMS v2, never identity first.
  • Nodes: a minimal, immutable OS, regular replacement, and checks against the CIS Benchmark (kube-bench is an Aqua tool, not CNCF).
