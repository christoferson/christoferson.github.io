Overview

Topic 3.1

Pod Security Standards. Pod Security Admissions.

The Pod Security Standards (PSS) are a definition: three named levels listing which Pod settings are allowed. Pod Security Admission (PSA) is the built-in admission controller that enforces them, configured with namespace labels. This page covers both, as of Kubernetes v1.37. The kernel features the standards refer to (capabilities, seccomp, AppArmor, SELinux, user namespaces) are explained in topic 1.2, and admission control in general in topic 5.4.

Quotes are from kubernetes.io (CC BY 4.0).

Running example. The web shop's shop namespace should enforce Baseline now and move to Restricted. The platform team needs to test the change, roll it out, and exempt the one system workload that can't comply.

The three standards

Topic 3.1What each level is for, and who it's aimed at.

"The Pod Security Standards define three different policies to broadly cover the security spectrum. These policies are cumulative and range from highly-permissive to highly-restrictive."

LevelDefinitionAimed at
Privileged"Unrestricted policy, providing the widest possible level of permissions. This policy allows for known privilege escalations.""System- and infrastructure-level workloads managed by privileged, trusted users", such as CNI agents and storage drivers
Baseline"Minimally restrictive policy which prevents known privilege escalations. Allows the default (minimally specified) Pod configuration.""Application operators and developers of non-critical applications"
Restricted"Heavily restricted policy, following current Pod hardening best practices.""Operators and developers of security-critical applications, as well as lower-trust users"

The standards only define the levels: "The methods of enforcement of individual policies are not defined here." PSA is one way to enforce them; policy engines are another. The checks cover every container in the Pod, including init and ephemeral containers: "If any of the listed containers fails to meet the requirements, the entire pod will fail validation."

Profile vs security context. A security context configures a Pod or container "at runtime". A security profile (a PSS level) is a "control plane mechanism to enforce specific settings in the Security Context". There's no level between Privileged and Baseline, because "privileges required above the Baseline policy are typically very application specific".

Baseline controls

Topic 3.1Everything Baseline forbids: the known ways out of a Pod.

The safe sysctls are those "namespaced in the container or the Pod, and ... isolated from other Pods or processes on the same Node": kernel.shm_rmid_forced and twelve net.ipv4.* settings for ports, keepalives and TCP buffers. v1.37 added two, net.ipv4.tcp_slow_start_after_idle and net.ipv4.tcp_notsent_lowat, bringing the list to 14.

Baseline still allows a lot. A Baseline Pod may run as root, have no seccomp profile at all (only explicitly Unconfined is blocked) and keep the 13 default capabilities. NET_RAW isn't on that list, so it can't be added, but on containerd it's granted by default and Baseline doesn't drop it (topic 2.3).

Restricted controls

Topic 3.1What Restricted adds to Baseline, and how to write a Pod that passes.

Restricted includes "everything from the Baseline policy", plus:

ControlRequirement
Volume typesOnly configMap, csi, downwardAPI, emptyDir, ephemeral, persistentVolumeClaim, projected, secret
Privilege escalationallowPrivilegeEscalation: false, set explicitly
Running as non-rootrunAsNonRoot: true (Pod level, or on every container)
Non-root userrunAsUser must not be 0
SeccompRuntimeDefault or Localhost: "Both the Unconfined profile and the absence of a profile are prohibited."
Capabilities"Containers must drop ALL capabilities, and are only permitted to add back the NET_BIND_SERVICE capability."
A shop Pod that passes Restricted (Pod) 
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: shop
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: web
    image: shop/web:1.4.2
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]

Restricted needs explicit settings. Leaving allowPrivilegeEscalation, runAsNonRoot, capabilities.drop or the seccomp profile unset fails, because PSA checks the spec and never fills in defaults. Restricted does not require readOnlyRootFilesystem, runAsGroup, resource limits or hostUsers: false. And passing PSA with runAsNonRoot: true isn't the end: if the image's user is root and no runAsUser is set, the kubelet refuses to start the container.

Two relaxations

  • Windows Pods. Since v1.25, Restricted uses spec.os.name: the privilege escalation, seccomp and capabilities rules "are only required if .spec.os.name is not windows".
  • User namespaces. For Pods with hostUsers: false, "Kubernetes relaxes the application of Pod Security Standards in a controlled way". runAsNonRoot and runAsUser aren't checked, because root in the Pod "is never mapped to a privileged user on the host". Baseline also relaxes procMount, but Restricted doesn't. This is built into policy version v1.35 and later; it used to need a feature gate, now removed.

On sandboxed runtimes, the standards admit "there is no standard definition of what a sandboxed runtime is", so there's no special level. PSA's way to handle them is a RuntimeClass exemption (below).

Pod Security Admission

Topic 3.1The built-in controller: its modes, and what each mode acts on.

The PodSecurity admission plugin is a validating admission controller that "checks new Pods before they are admitted". It was alpha in v1.22, became beta and on by default in v1.23, and went GA in v1.25. Its feature gate was removed in v1.28, and it's in the API server's default plugin list. "Pod security restrictions are applied at the namespace level when pods are created."

ModeOn a violationApplies to
enforce"The pod to be rejected."Pods only
audit"The addition of an audit annotation to the event recorded in the audit log", otherwise allowedPods and workload resources
warn"A user-facing warning", otherwise allowedPods and workload resources

"A namespace can configure any or all modes, or even set a different level for different modes." Workload resources are those with a Pod template: Deployments, ReplicaSets, StatefulSets, DaemonSets, Jobs, CronJobs, ReplicationControllers and PodTemplates.

Enforce doesn't block Deployments. "Enforce mode is not applied to workload resources, only to the resulting pod objects." A Deployment that violates the enforced level is accepted. Its ReplicaSet then fails to create Pods, and the error shows in the ReplicaSet's events, not in the output of kubectl apply. That's why a warn label at the same level is useful: it warns at apply time.

Namespace labels

Topic 3.1Setting the level and version for each mode, and testing a change safely.

PSA namespace labels
Level
pod-security.kubernetes.io/<MODE>: <LEVEL>
Version
pod-security.kubernetes.io/<MODE>-version: <VERSION>
MODE
enforce, audit, warn
LEVEL
privileged, baseline, restricted
VERSION
latest (default) or v<major>.<minor>, such as v1.37

Pinning a version keeps a namespace on that release's rules when the cluster is upgraded. latest picks up new rules automatically. A common pattern is to enforce a pinned version and warn and audit on latest, so you see new violations before they're enforced.

Roll out Baseline on the shop namespace (shell) 
P=pod-security.kubernetes.io

# 1. test: nothing is saved
kubectl label --dry-run=server \
  --overwrite ns shop \
  $P/enforce=baseline

# 2. enforce Baseline, pinned;
#    warn and audit on Restricted
kubectl label --overwrite ns shop \
  $P/enforce=baseline \
  $P/enforce-version=v1.37 \
  $P/warn=restricted \
  $P/audit=restricted

# namespaces with no enforce label
kubectl get ns -l "!$P/enforce"

The server dry run tests existing Pods and prints warnings without changing anything, in the form Warning: existing pods in namespace "shop" violate the new PodSecurity enforce level "baseline:latest", followed by each Pod and its violations, such as host namespaces, hostPath volumes. Applying the label for real prints the same warnings: "Violations are returned to the user as warnings." Running Pods are never evicted.

Label details that trip people up. The version needs the v: v1.37, not 1.37. An invalid enforce level is treated as restricted, so it fails closed. An unlabelled namespace gets the cluster default, which out of the box is privileged: no restrictions at all. kubernetes.io: "Namespaces that lack any configuration at all should be considered significant gaps in your cluster security model."

Namespace editors control the level. "Anyone who can update (or patch or create) a namespace can also modify the Pod Security level for that namespace." Restrict update and patch on Namespaces with RBAC (topic 3.2).

Cluster defaults and exemptions

Topic 3.1Configuring the controller itself: levels for unlabelled namespaces, and who skips the checks.

The API server reads the plugin's configuration from the file named by --admission-control-config-file: an AdmissionConfiguration (apiserver.config.k8s.io/v1) containing a PodSecurityConfiguration.

PodSecurityConfiguration for the shop cluster
apiVersion
pod-security.admission.config.k8s.io/v1
defaults
enforce: baseline, audit: restricted, warn: restricted, each with a -version (default latest); applied "when a mode label is not set"
exemptions.usernames
Requests from these authenticated (or impersonated) users
exemptions.runtimeClasses
Pods using these RuntimeClasses, for example a sandbox such as gvisor
exemptions.namespaces
All Pods and workloads in these namespaces, for example the CNI agent's namespace

"Exemptions must be explicitly enumerated. Requests meeting exemption criteria are ignored by the Admission Controller (all enforce, audit and warn behaviors are skipped)." They exist only in this static file: there's no exemption label. Exempt requests get the audit annotation pod-security.kubernetes.io/exempt with the value user, namespace or runtimeClass.

Two exemption mistakes. First, exempting a person "will only exempt them from enforcement when creating pods directly, but not when creating a workload resource". Exempting a controller's ServiceAccount, such as system:serviceaccount:kube-system:replicaset-controller, "would implicitly exempt any user that can create the corresponding workload resource". Second, kube-system is not exempt by default; a server dry run of Baseline usually reports violations there (etcd, kube-proxy, CNI agents). Label it privileged deliberately, or exempt it.

What PSA does and doesn't check

Topic 3.1The edges of the built-in controller, and where its results show up.

  • It never changes Pods. "Pod Security Admission is a non-mutating admission controller, meaning it won't modify pods before validating them." Unlike the old PodSecurityPolicy, it won't add a seccomp profile or drop capabilities for you.
  • It checks updates selectively. Changing only metadata, activeDeadlineSeconds or tolerations isn't re-checked. Adding an ephemeral container is checked, so kubectl debug with a privileged profile fails in a Baseline namespace.
  • It doesn't cover exec, attach or port-forward. Those are RBAC's job (topic 2.2).
  • It knows only three levels. It has no custom rules, nothing per user inside a namespace, and nothing about images, registries, labels, resource limits or readOnlyRootFilesystem.
  • Static Pods are started by the kubelet from files and never pass through admission (topic 2.2).

Where results appear

OutputExample
Enforce rejectionpods "bad" is forbidden: violates PodSecurity "baseline:latest": host namespaces (hostNetwork=true), privileged (container "app" must not set securityContext.privileged=true)
WarningWarning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (...)

Audit mode needs auditing. The audit annotations are added to API server audit events, not to Pods (the labels reference page wrongly says "to the Pod"). If API auditing isn't configured, audit mode records nothing anyone can see (topic 3.5).

PodSecurityPolicy and alternatives

Topic 3.1What PSA replaced, and what to use when three levels aren't enough.

PodSecurityPolicy is gone. "PodSecurityPolicy was deprecated in Kubernetes v1.21, and removed from Kubernetes in v1.25" (April 2021 and August 2022). PSA went GA in the same release. PSP could mutate Pods and was granted through RBAC's use verb per ServiceAccount; the migration guide calls that model one with "many pitfalls". Migrating means mapping each PSP to the nearest level, testing with --dry-run=server and audit, then enforcing. Older material that mentions PSP, or says PSA mutates Pods, is out of date.

PSA "was designed to be complementary to other policy enforcement mechanisms". For custom rules, defaults or exceptions finer than a namespace, add one of these, often alongside PSA as a fallback:

OptionWhat it isStatus
ValidatingAdmissionPolicyBuilt-in rules written in CELGA v1.30
MutatingAdmissionPolicyBuilt-in CEL mutations, for example adding a seccomp profileGA v1.36
KyvernoPolicy engine with YAML policies: validate, mutate, generate, verify imagesCNCF graduated, March 2026
OPA GatekeeperAdmission webhook running Open Policy Agent policies written in RegoSub-project of OPA (CNCF graduated 2021)
KubewardenPolicies compiled to WebAssemblyCNCF sandbox

kubernetes.io's advice on choosing: "Ultimately, using any of the aforementioned approaches will be better than doing nothing." Admission policies are covered in topic 5.4.

Key takeaways

  • Three cumulative levels: Privileged (no restrictions), Baseline (blocks known escalations; allows the default Pod), Restricted (hardening best practice). PSS is a definition; PSA is one enforcer.
  • Baseline forbids host namespaces, privileged, extra capabilities beyond the default 13, hostPath, hostPort, probe and hook host (1.34), Unconfined AppArmor or seccomp, custom SELinux, Unmasked procMount and unsafe sysctls (14 safe in 1.37).
  • Restricted adds: allowed volume types only, explicit allowPrivilegeEscalation: false, runAsNonRoot: true, runAsUser not 0, seccomp RuntimeDefault or Localhost, drop ALL (add back only NET_BIND_SERVICE). It doesn't require readOnlyRootFilesystem. Windows Pods skip three rules; hostUsers: false Pods skip the non-root checks (policy v1.35+).
  • PSA: built-in validating plugin, GA 1.25. enforce rejects Pods only; audit (annotation on the audit event) and warn also cover workloads.
  • Labels pod-security.kubernetes.io/<mode> and <mode>-version (v1.37 or latest). Test with kubectl label --dry-run=server; label changes only warn about running Pods. Unlabelled = cluster default, privileged out of the box.
  • Defaults and exemptions (usernames, runtimeClasses, namespaces) live in the static PodSecurityConfiguration; exemptions skip all modes. Don't exempt controller ServiceAccounts; kube-system isn't exempt by default.
  • PSA never mutates, checks ephemeral containers, ignores exec and attach. PSP: deprecated 1.21, removed 1.25. For more: ValidatingAdmissionPolicy, MutatingAdmissionPolicy, Kyverno, Gatekeeper, Kubewarden.
