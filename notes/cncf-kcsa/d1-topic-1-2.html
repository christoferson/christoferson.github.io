Overview

Topic 1.2

Controls and Frameworks. Isolation Techniques.

The curriculum gives only these topic names. This page takes controls and frameworks to mean what a security control is, how controls are classified, the principles behind them (defense in depth, least privilege, zero trust) and the main documents cloud native teams use to pick and check controls. Compliance frameworks such as PCI DSS get their own page in topic 6.1, and threat matrices in topic 6.2. It takes isolation techniques to mean the layers that keep a workload from affecting the host and other workloads, from kernel features up to dedicated nodes and clusters. Pod Security Standards are in topic 3.1, and namespace and network segmentation in topic 3.4.

Quotes are from kubernetes.io, the CNCF® Glossary and the CNCF TAG Security Cloud Native Security Whitepaper v2 (CC BY 4.0), and from NIST publications (US government works, credited).

Running example. In the web shop, the API handles customer data, the database must not share nodes with anything else, and the worker resizes product images that customers upload. Those images are untrusted input, so the worker gets the strongest isolation.

Security controls

Topic 1.2What a control is, and classifying controls by what they do and how they are implemented.

NIST defines a security control as "the safeguards or countermeasures prescribed for an information system or an organization to protect the confidentiality, integrity, and availability of the system and its information."

By function

NIST IR 8286 Rev. 1 (December 2025) gives these examples of control types:

TypeNIST descriptionCloud native example
Preventative"Reduce or eliminate specific instances of a vulnerability"Admission policies, RBAC, network policies, seccomp, image signature checks
Deterrent"Reduce the likelihood of a threat event by dissuading a threat actor"Published acceptable-use policy, login banners (little is Kubernetes-specific)
Detective"Provide warning of a successful or attempted threat event"API server audit logs, Falco runtime alerts, image and configuration scanning
Corrective"Reduce exposure by offsetting the impact of consequences after a risk event"Controllers replacing failed Pods, kubectl rollout undo, patching and redeploying an image, restoring an etcd snapshot
Compensating"Apply one or more controls to adjust for a weakness in another control"Strict seccomp and AppArmor profiles plus extra monitoring when a workload can't be sandboxed

The examples in the last column are this page's own mapping. kubernetes.io uses these words only in passing. It says ecosystem tools "implement preventative or detective controls around Pods". Its multi-tenancy page suggests "compensating controls such as seccomp, AppArmor or SELinux" where node isolation is a concern.

By category

  • Technical (also called logical): carried out by hardware, software or firmware. RBAC, network policies and encryption are examples.
  • Administrative: policies and procedures, such as who may approve cluster-admin bindings, change review and incident runbooks.
  • Physical: locks, guards and data center access. In the cloud these sit on the provider's side of shared responsibility (topic 1.1).

Don't confuse the two classifications. "Detective" is a function; "technical" is a category. An audit log is both a detective and a technical control. Also, "recovery" and "directive" controls are common industry labels, but NIST IR 8286 doesn't list them. Older NIST documents grouped controls as management, operational and technical.

A detective control only works if it's on. Kubernetes audit logging is off by default: "If the flag is omitted, no events are logged" (the --audit-policy-file flag). Audit logging is covered in topic 3.5.

Principles

Topic 1.2The ideas that decide which controls to combine and where to put them.

PrincipleDefinitionIn a cluster
Defense in depth"The application of multiple countermeasures in a layered or stepwise manner to achieve security objectives" (NIST)RBAC and admission and seccomp and network policies, so no single failure exposes the workload
Least privilege"Each entity is granted the minimum system resources and authorizations that the entity needs to perform its function" (NIST)Narrow Roles, dropped Linux capabilities, non-root users, scoped cloud permissions. The whitepaper: "least privilege must be applied at every layer of the stack"
Zero trust"Trust is completely removed. The core principle being 'never trust, always verify'" (CNCF Glossary)Authenticate and authorize every request, encrypt service-to-service traffic, deny by default between Pods

NIST SP 800-207 (2020) is the standard reference for zero trust architecture. Several of its seven tenets map directly onto a cluster: "All communication is secured regardless of network location", "Access to individual enterprise resources is granted on a per-session basis", and "All resource authentication and authorization are dynamic and strictly enforced before access is allowed." The CNCF whitepaper names the cloud native pieces: "Orchestrator network policies as well as use of a service mesh are all components of a comprehensive zero trust solution." NIST SP 800-207A (2023) applies the model to cloud native applications with service meshes.

Zero trust doesn't mean "no internal network". It means being inside the network earns no trust by itself. A Pod in the same namespace is verified just like a request from the internet. A flat cluster network where every Pod can reach every other Pod is the opposite of zero trust.

Frameworks, guides and benchmarks

Topic 1.2The main documents for choosing and checking controls, and what each kind is for.

On benchmarks, the whitepaper warns that they "cannot consider data flows and custom usage of the platforms under testing. Security practitioners should implement them as a guide rather than a checklist."

NIST SP 800-53 Rev. 5

The US federal control catalogue (current release 5.2.0, August 2025) groups controls into 20 families, each with a two-letter ID. Families that come up most in a cluster include AC Access Control (AC-6 is Least Privilege), AU Audit and Accountability, CM Configuration Management, IA Identification and Authentication, SC System and Communications Protection (SC-39 is Process Isolation) and SR Supply Chain Risk Management.

NIST SP 800-190

The Application Container Security Guide (September 2017, still the current edition) organizes container risks, and the countermeasures for them, into five areas:

AreaExample risks
ImageVulnerabilities, configuration defects, embedded malware, clear-text secrets, untrusted images
RegistryInsecure connections, stale images, weak authentication and authorization
OrchestratorUnbounded admin access, unauthorized access, poorly separated network traffic, mixing workload sensitivity levels, node trust
ContainerRuntime vulnerabilities, unbounded network access, insecure runtime configuration, app vulnerabilities, rogue containers
Host OSLarge attack surface, shared kernel, component vulnerabilities, improper user access, file system tampering

The others in brief

  • CIS Kubernetes Benchmark: consensus-built configuration recommendations for the control plane, etcd, nodes and policies, with separate benchmarks for major managed services. kube-bench (from Aqua Security, not a CNCF project) checks a cluster against it. See topic 1.1.
  • NSA/CISA Kubernetes Hardening Guidance: a joint US government report, first released August 2021. The current version is 1.2 (August 2022), so parts of it predate Kubernetes 1.25.
  • MITRE ATT&CK Containers matrix: attacker tactics and techniques for containers. In April 2026 (version 19), MITRE split the "Defense Evasion" tactic into "Stealth" and "Defense Impairment". Covered in topic 6.2.
  • OWASP Kubernetes Top 10 (2025 edition): K01 Insecure Workload Configurations, K02 Overly Permissive Authorization Configurations, K03 Secrets Management Failures, K04 Lack Of Cluster Level Policy Enforcement, K05 Missing Network Segmentation Controls, K06 Overly Exposed Kubernetes Components, K07 Misconfigured And Vulnerable Cluster Components, K08 Cluster To Cloud Lateral Movement, K09 Broken Authentication Mechanisms, K10 Inadequate Logging And Monitoring.

CNCF Cloud Native Security Controls Catalog. In 2022, CNCF TAG Security published a spreadsheet mapping the recommendations in its whitepapers to NIST SP 800-53 Rev. 5. It was designed "to complement and leverage, but not replace, existing industry accepted frameworks". The working group behind it was archived in February 2025, and the whole cncf/tag-security repository in December 2025. The group continues as TAG Security and Compliance. Don't present the catalogue as an active standard.

The OWASP list changed in 2025. The 2022 edition had Supply Chain Vulnerabilities at K02. The 2025 edition drops it, merges the two "misconfigured" and "outdated components" items into K07, and adds K06 and K08. Older practice material uses the 2022 numbering.

Layers of isolation

Topic 1.2The range from a shared kernel to separate hardware, and when to move up it.

kubernetes.io puts the basic limit plainly: "Containers utilize OS-level virtualization and hence offer a weaker isolation boundary than virtual machines that utilize hardware-based virtualization." Every container on a node shares the node's kernel. NIST SP 800-190 notes that a shared kernel "invariably results in a larger inter-object attack surface than seen with hypervisors". Each step up the table below costs more but removes more of that sharing.

LevelWhat is separateWhat is still shared
Container, hardenedLinux namespaces, cgroups, capabilities, seccomp, AppArmor or SELinux, user namespacesHost kernel, node, kubelet
Sandboxed runtimeA user-space kernel (gVisor) or a lightweight VM with its own guest kernel (Kata Containers)Node hardware, kubelet
Dedicated nodesThe machines a tenant's Pods run onAPI server, control plane, cluster network
Dedicated clusterControl plane and nodes; possibly dedicated hardware "if VMs are not considered an adequate security boundary"Cloud account and tooling, unless those are separated too

Kernel isolation features

Topic 1.2The Linux features that make a container a container, and the Pod fields that tighten them.

The kubernetes.io page Linux kernel security constraints sums up the approach: "Kubernetes lets you configure and use Linux kernel features to improve isolation and harden your containerized workloads." Values in the Pod manifest take "precedence over similar values in the container image".

FeatureWhat it isolates or limitsPod field
Linux namespacesWhat a process can see: PID, network, mount, IPC, UTS (hostname), user, cgroup, time. Containers in a Pod share the network namespacehostNetwork, hostPID, hostIPC turn sharing with the host on (avoid)
cgroupsHow much CPU, memory and other resources a process may use, so one workload can't starve the noderesources.requests and limits
CapabilitiesSplits root's powers into units such as NET_ADMIN or SYS_ADMINsecurityContext.capabilities (container level)
seccomp"Filter which system calls a process can make"securityContext.seccompProfile
AppArmor"Restrict the access privileges of individual programs" with path-based profilessecurityContext.appArmorProfile
SELinux"Assign security labels to objects" and enforce policy on those labelssecurityContext.seLinuxOptions
User namespacesRoot inside the container maps to an unprivileged user on the hostspec.hostUsers: false

cgroup v1 is deprecated. It entered maintenance mode in v1.31 (August 2024) and was deprecated in v1.35 (December 2025). Since v1.35 the kubelet refuses to start on a cgroup v1 node by default (failCgroupV1 defaults to true). Removal of the fallback is planned for v1.38. cgroup v2 has been stable since v1.25.

Capabilities, privileged mode and privilege escalation

In a manifest, capability names drop the CAP_ prefix: NET_BIND_SERVICE, not CAP_NET_BIND_SERVICE. The usual hardening is to drop ALL and add back only what's needed. NET_BIND_SERVICE lets a non-root process listen on a port below 1024.

privileged: true undoes almost everything on this page: "Privileged containers override or undo many other hardening settings such as the applied seccomp profile, AppArmor profile, or SELinux constraints. Privileged containers are given all Linux capabilities". allowPrivilegeEscalation "directly controls whether the no_new_privs flag gets set", which stops a process from gaining more privileges than its parent, for example through a setuid binary.

allowPrivilegeEscalation defaults to true. You must set it to false explicitly; the Restricted Pod Security Standard requires that. It can't be false if the container is privileged or has SYS_ADMIN.

seccomp, AppArmor and SELinux

seccomp profiles have three types: RuntimeDefault (the container runtime's built-in filter), Localhost (a profile file on the node) and Unconfined (no filter). kubernetes.io recommends: "Use the default seccomp profile that's bundled with your container runtime. If you need a more isolated environment, consider using a sandbox, such as gVisor."

AppArmor and SELinux are both mandatory access control systems, and a node usually runs one or the other. "AppArmor uses profiles to define access to resources. SELinux uses policies that apply to specific labels." AppArmor identifies files by path; SELinux by inode. The Security Profiles Operator (a Kubernetes SIG project) helps manage profiles at scale.

No profile means no seccomp filter. Unless the kubelet's seccompDefault setting is turned on, a Pod with no seccomp profile runs Unconfined. The SeccompDefault feature has been GA since v1.27, but the setting still defaults to false, so it's opt-in per node.

AppArmor annotations are deprecated. AppArmor moved to the securityContext.appArmorProfile field (beta v1.30, GA v1.31). Old manifests and some kubernetes.io pages still show the container.apparmor.security.beta.kubernetes.io annotation. The seccomp field has been GA since v1.19, and its annotations are deprecated too.

User namespaces

With hostUsers: false, each Pod gets its own user namespace. The process "has full privileges for operations inside the user namespace, but is unprivileged for operations outside the namespace." The API reference calls this "useful for mitigating container breakout vulnerabilities even allowing users to run their containers as root without actually having root privileges on the host." The feature went GA in v1.36 (April 2026). It needs Linux 6.3 or later and a recent runtime (containerd 2.0+ or CRI-O 1.25+), and it can't be combined with hostNetwork, hostPID or hostIPC.

The shop API, hardened (Pod) 
apiVersion: v1
kind: Pod
metadata:
  name: api
  namespace: shop
spec:
  # own user namespace (GA 1.36)
  hostUsers: false
  # Pod-level settings
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: api
    image: shop/api:1.4.2
    # container-level settings
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
        add: ["NET_BIND_SERVICE"]
    volumeMounts:
    - name: tmp
      mountPath: /tmp
  volumes:
  - name: tmp
    emptyDir: {}

capabilities, privileged, allowPrivilegeEscalation and readOnlyRootFilesystem exist only at container level. hostUsers sits directly under spec, not in a securityContext. The read-only root filesystem means the app needs an emptyDir for temporary files.

Restricted doesn't require a read-only root filesystem. The Restricted Pod Security Standard requires dropping ALL capabilities, allowPrivilegeEscalation: false, non-root and a seccomp profile, but not readOnlyRootFilesystem. That is extra hardening (topic 3.1).

Setting AppArmor explicitly can block scheduling. If a container sets appArmorProfile.type: RuntimeDefault, "the Pod will not be admitted if AppArmor is not enabled on the Node." On a mixed fleet, or SELinux-based nodes, leave it unset: the runtime default then applies wherever AppArmor is available. In v1.37, SELinux volume relabeling through mount options became GA and on by default, so Pods with different SELinux labels sharing one volume on a node may fail to start. seLinuxChangePolicy: Recursive opts a Pod out.

Sandboxed runtimes

Topic 1.2Running a Pod behind a second kernel, and choosing the runtime per Pod with RuntimeClass.

kubernetes.io describes sandboxing as running "each pod in a separate execution environment such as a virtual machine or a userspace kernel", and says it "is often recommended when you are running untrusted code". The two common approaches:

RuntimeHow it isolatesWho runs it
gVisorA user-space "application kernel" written in Go. Its Sentry component intercepts the application's system calls and handles them itself, so they don't go straight to the host kernel. Runtime binary runscGoogle; not a CNCF project
Kata Containers"Lightweight Virtual Machines (VMs) that feel and perform like containers": each Pod gets its own guest kernel, on a hypervisor such as QEMU, Cloud Hypervisor or FirecrackerOpenInfra Foundation; not a CNCF project

Sandboxes "require more compute resources on your nodes and might have compatibility issues with GPUs and other specialized hardware." Confidential Containers, a CNCF incubating project since July 2026, builds on Kata to run Pods inside hardware trusted execution environments.

RuntimeClass

"RuntimeClass is a feature for selecting the container runtime configuration." It's a cluster-scoped object (node.k8s.io/v1, GA since v1.20). Its handler names a runtime configured in the node's CRI runtime, and a Pod picks it with runtimeClassName. The shop's image worker:

Sandbox the image worker (RuntimeClass and Pod) 
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  # cluster-scoped, no namespace
  name: gvisor
# runtime name in the CRI config
handler: runsc
---
apiVersion: v1
kind: Pod
metadata:
  name: image-worker
  namespace: shop
spec:
  runtimeClassName: gvisor
  containers:
  - name: worker
    image: shop/worker:2.0.1

A RuntimeClass can also carry scheduling (a nodeSelector and tolerations, so Pods land only on nodes that have the runtime installed) and overhead (extra CPU and memory the sandbox itself uses, counted by the scheduler).

Check it (shell) 
kubectl get runtimeclass
kubectl get pod image-worker -n shop \
  -o wide

Three RuntimeClass details. The handler field is immutable. If a Pod names a RuntimeClass that doesn't exist, or the node can't run its handler, the Pod goes to the Failed phase. And "there is currently no API standard that controls whether a Pod is considered sandboxed": Kubernetes has no "sandboxed" flag, only the runtime you choose.

Who wrote which sandbox. gVisor = Google, a user-space kernel. Kata Containers = OpenInfra Foundation, lightweight VMs. Neither is a CNCF project. Confidential Containers is.

Nodes and clusters

Topic 1.2Isolating tenants and sensitive workloads by machine and by cluster.

The CNCF Glossary defines multitenancy as "a single software installation that serves multiple tenants." The kubernetes.io multi-tenancy page distinguishes "'hard' multi-tenancy ... [which] implies strong isolation, and 'soft' multi-tenancy, which implies weaker isolation", and adds that the difference "is better understood as a broad spectrum". Hard multi-tenancy is for tenants that don't trust each other.

  • Control plane isolation "ensures that different tenants cannot access or affect each others' Kubernetes API resources": namespaces, RBAC and quotas.
  • Data plane isolation "ensures that pods and workloads for different tenants are sufficiently isolated": network and storage isolation, sandboxed containers, and node isolation.

With node isolation, "a set of nodes is dedicated to running pods from a particular tenant and co-mingling of tenant pods is prohibited." NIST SP 800-190 gives the same advice: orchestrators "should be configured to isolate deployments to specific sets of hosts by sensitivity levels." For the shop database, label and taint its nodes:

Dedicate nodes to the database (shell) 
# keep other Pods off
kubectl taint nodes node-db1 \
  dedicated=db:NoSchedule

# mark it for the database
kubectl label nodes node-db1 \
  dedicated=db
Database Pod spec, pinned to those nodes (excerpt) 
spec:
  nodeSelector:
    dedicated: db
  tolerations:
  - key: dedicated
    operator: Equal
    value: db
    effect: NoSchedule

The taint keeps other Pods away; the nodeSelector keeps the database on those nodes. You need both. Taints and node selection are covered in depth in the KCNA notes on scheduling.

Labels a node can change aren't a security boundary. A compromised kubelet could relabel its node to attract sensitive Pods. For isolation, kubernetes.io recommends label keys with the node-restriction.kubernetes.io/ prefix, which the NodeRestriction admission plugin stops kubelets from setting. Dedicated nodes still share the API server with everyone else; only separate clusters remove that.

Windows nodes are different. "Linux-specific pod security context mechanisms (such as SELinux, AppArmor, Seccomp, or custom POSIX capabilities) are not supported on Windows nodes", privileged containers aren't supported, and Kubernetes doesn't support Hyper-V isolated containers. HostProcess containers (GA v1.26) are the privileged equivalent, with no file system or process isolation from the host.

Key takeaways

  • Control functions (NIST IR 8286 Rev. 1): preventative, deterrent, detective, corrective, compensating. Categories: technical (logical), administrative, physical. A control has one of each, for example an audit log is detective and technical.
  • Defense in depth = layered countermeasures; least privilege = the minimum needed, at every layer; zero trust = never trust, always verify (NIST SP 800-207; network policies and service meshes in a cluster).
  • Framework (NIST SP 800-53, 20 families), guide (NIST SP 800-190 with five risk areas: image, registry, orchestrator, container, host OS; NSA/CISA v1.2), benchmark (CIS, checked with kube-bench), threat matrix (MITRE ATT&CK), risk list (OWASP Kubernetes Top 10, 2025 edition). The CNCF Controls Catalog was archived in 2025.
  • Containers share the host kernel. Harden them with namespaces, cgroups (v2; v1 deprecated in 1.35), dropped capabilities, seccomp RuntimeDefault, AppArmor or SELinux, non-root, allowPrivilegeEscalation: false and hostUsers: false (GA 1.36). Never privileged: true.
  • Traps: allowPrivilegeEscalation defaults to true; no seccomp profile = Unconfined unless the kubelet's seccompDefault is on; capabilities drop the CAP_ prefix; AppArmor uses a field since 1.31, not annotations.
  • Sandboxes for untrusted code: gVisor (Google, user-space kernel, runsc) or Kata Containers (OpenInfra, lightweight VMs), chosen with a RuntimeClass (node.k8s.io/v1, handler, Pod runtimeClassName).
  • Beyond that: dedicated nodes (taint plus nodeSelector, with NodeRestriction-protected labels), then dedicated clusters for hard multi-tenancy.
