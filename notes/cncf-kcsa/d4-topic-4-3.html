4.3: Attacker on the Network, Access to Sensitive Data, Privilege Escalation

What an attacker inside a Kubernetes® cluster tries next: move across the network, reach secrets and credentials, and turn a small foothold into control of a node, the cluster or the cloud account. Seen from the defender's side: what enables each step, and what detects and stops it.

Overview

Topic 4.3

Attacker on the Network. Access to Sensitive Data. Privilege Escalation.

The curriculum gives only these names. This page continues from topic 4.2: once an attacker has code running in a container, these are the three things they try next. Each is described the way public threat matrices do, then mapped to the misconfigurations that enable it and the controls covered on earlier pages. As the Microsoft matrix says of itself, the purpose "is to educate readers on the potential of Kubernetes-based tactics, techniques, and procedures (TTPs). It is not to teach how to weaponize or specifically abuse them."

Sources: kubernetes.io (CC BY 4.0), the Microsoft Threat Matrix for Kubernetes (CC BY 4.0), MITRE ATT&CK® (under MITRE's terms) and the Falco rules (Apache-2.0). Public incident reports are summarized in a line each.

Running example. Picking up from 4.2: an attacker is running code in one shop api Pod. For each step they might try, the review asks: would it work here, would we see it, and what stops it?

The Microsoft matrix pairs each technique with numbered mitigations, for example "Adhere to least-privilege principle", "Network Segmentation", "Restricting cloud metadata API access", "Disable Service Account Auto Mount" and "Use NodeRestriction Admission Controller". Those names are a good summary of this page's defences.

The two matrices don't line up exactly. Microsoft maps ARP and CoreDNS poisoning to MITRE T1557 (Adversary-in-the-Middle), and metadata theft to T1552.005, but neither technique is on ATT&CK's Containers matrix: they sit on its Linux and cloud (IaaS) matrices. The Microsoft matrix also still uses the tactic name "Defense Evasion", which MITRE split in 2026 (topic 4.2).

Attacker on the network

Topic 4.3What a compromised Pod can reach and intercept, and the controls that narrow it.

The starting point is kubernetes.io's own warning: "By default, all pods in a Kubernetes cluster are allowed to communicate with each other, and all network traffic is unencrypted. This can lead to security vulnerabilities where traffic is accidentally or maliciously sent to an unintended destination, or is intercepted by a workload on a compromised node."

RiskWhat enables itPrevent
Mapping and reaching every Pod and ServiceNo NetworkPolicy, or a CNI that ignores it; cluster DNS answers for every namespaceDefault deny per namespace plus allow lists; ClusterNetworkPolicy guardrails (topic 3.4)
Reaching the API server, kubelet or etcdControl plane and node ports reachable from the Pod network; anonymous kubelet; a public API endpointEgress policy to node and control plane addresses; kubelet Webhook authn and authz; etcd firewall and mTLS; private endpoint (topic 2.1, 2.2)
Spoofing neighbours on the nodeA bridge-based CNI plus a container with NET_RAW (granted by default on containerd); CVE-2020-10749Drop NET_RAW (Restricted drops all capabilities); a CNI that filters spoofed traffic; TLS with certificate checks
Intercepting a Service's trafficUsers who can set externalIPs or patch services/status (CVE-2020-8554, which has no patch)The DenyServiceExternalIPs admission plugin (off by default); never grant patch on services/status (topic 2.2)
Redirecting namesWrite access to the CoreDNS ConfigMap in kube-systemRestrict writes in kube-system; audit changes there
Cloud credentials from the metadata servicePod egress to 169.254.169.254; a broad node roleBlock metadata egress; workload identity; least-privilege node role (topic 1.1)

NetworkPolicy has two blind spots here. It doesn't cover Pods with hostNetwork: true, which can still reach the metadata service and node ports, and a CNI that doesn't implement it silently ignores it. Pair network policy with Pod Security, which forbids hostNetwork at Baseline.

The Security Checklist adds a preference: injecting secrets from third-party storage "should be done preferentially as compared to providing the pods service account RBAC access to secrets." And "Securing a Cluster" warns that integrations which ask to "view all secrets on your cluster" are "effectively making that component a cluster admin".

Encryption at rest doesn't stop API readers. It protects etcd and its backups. Anyone the API authorizes to read a Secret still gets the plaintext value, so RBAC and token hygiene matter just as much.

Privilege escalation

Topic 4.3The four ladders an attacker climbs, and what breaks each rung.

Container to node

The Microsoft matrix describes this tactic as "getting access to the node from a container, gaining higher privileges in the cluster, and even getting access to the cloud resources". What makes escaping to the node easy:

  • privileged: true, host namespaces (hostPID, hostNetwork, hostIPC), writable hostPath mounts, and powerful capabilities such as SYS_ADMIN;
  • running as root without user namespaces, with allowPrivilegeEscalation left at its default of true;
  • an unpatched runtime or kernel: for example runc's "Leaky Vessels" bug, CVE-2024-21626 (topic 2.2).

Defences: Pod Security, user namespaces (hostUsers: false, GA v1.36), seccomp and AppArmor or SELinux, sandboxed runtimes, and patching (topic 1.2). "Securing a Cluster" sums it up: administrators "who wish to prevent client applications from escaping their containers should apply the Baseline or Restricted Pod Security Standard."

Baseline vs Restricted on escalation. Baseline "prevents known privilege escalations": no privileged mode, host namespaces, hostPath or extra capabilities. But allowPrivilegeEscalation: false, dropping all capabilities (including NET_RAW), running as non-root and requiring seccomp are Restricted rules (topic 3.1).

Within the API

RBAC good practices: "Within Kubernetes RBAC there are a number of privileges which, if granted, can allow a user or a service account to escalate their privileges in the cluster or affect systems outside the cluster."

PermissionLeads to

impersonateActing as any user, group or ServiceAccount allowed
Create workloads"The API access levels of any service account in that namespace"; with privileged Pods allowed, node access

RBAC's built-in escalation check applies "even when the RBAC authorizer is not in use", and only escalate and bind get around it (topic 3.2).

Node to cluster, and cluster to cloud

  • Node to cluster: a stolen kubelet credential is limited by the Node authorizer (only its own Node and its Pods' objects) and by NodeRestriction (only its own Node and Pods; no protected labels). NodeRestriction isn't in the API server's default plugin list, but kubeadm enables it. CVE-2020-8559 was a "privilege escalation from compromised node to cluster" (topic 2.2).
  • Cluster to cloud: node roles and managed identities reachable through the metadata service, or cloud credential files on the node. "These credentials can be used to escalate within the cluster or to other cloud services under the same account." Block metadata access from Pods, give each workload its own cloud identity, and keep node roles minimal.

Detecting these steps

Topic 4.3Signals in the audit log and at runtime.

Audit log (topic 3.5): events with impersonatedUser; writes in rbac.authorization.k8s.io; list or watch on Secrets; bursts of 403s from one identity; externalIPs being set or services/status patched by a user; pods/exec, CSR approvals, serviceaccounts/token creation and webhook configuration changes. Direct kubelet API access won't appear.

Falco's separate k8saudit plugin reads the audit log instead of system calls, with rules such as "Create Privileged Pod", "Attach to cluster-admin Role", "Anonymous Request Allowed" and "K8s Secret Get Successfully".

Check which rules are on. A default Falco install loads only the stable rules. Detection of privileged Pod launches or metadata access needs the incubating or sandbox rulesets, or the k8saudit plugin.

Defender self-checks

Topic 4.3Quick checks that show how far an attacker in the shop could get.

What could the api ServiceAccount do? (shell) 
# needs impersonate rights yourself
kubectl auth can-i --list \
  --as=system:serviceaccount:shop:api \
  -n shop

# can it climb? each should say "no"
S=system:serviceaccount:shop:api
kubectl auth can-i escalate \
  clusterroles --as="$S"
kubectl auth can-i bind \
  clusterroles --as="$S"
kubectl auth can-i impersonate \
  serviceaccounts --as="$S"
Find privileged or hostPath Pods (shell, using jq) 
kubectl get pods -A -o json \
  | jq -r '
  .items[]
  | select(
      any((.spec.containers
        + (.spec.initContainers
           // []))[];
        .securityContext.privileged
          == true)
      or any(.spec.volumes[]?;
        .hostPath != null))
  | .metadata.namespace + "/"
    + .metadata.name'
Enforce Restricted on the shop namespace (shell) 
L=pod-security.kubernetes.io
kubectl label --overwrite ns shop \
  "$L/enforce=restricted" \
  "$L/warn=restricted" \
  "$L/audit=restricted"

Expect system namespaces such as kube-system to appear in the privileged and hostPath list: CNI agents and kube-proxy need host access. Anything else is a finding to review.

Two public incidents, one lesson. In 2018 researchers reported a car maker's Kubernetes console open without a password, with cloud credentials reachable from a Pod and the cluster used for crypto-mining. In a 2018 bug bounty report, a server-side request forgery flaw at an e-commerce company reached a cloud metadata service and, through the credentials it exposed, gave root on Kubernetes-hosted instances. In both, an exposed interface or the metadata service turned a small foothold into broad access: the boundaries in topic 4.1.

Key takeaways

  • Matrices: Microsoft (network mapping, cluster internal networking, kubelet and API server access, ARP and CoreDNS poisoning; list secrets, container service account, metadata; privileged container, cluster-admin binding, hostPath, cloud resources) and MITRE Containers (T1046, T1613, T1552.007, T1528, T1611, T1068, T1098.006). T1557 and T1552.005 aren't on the Containers matrix.
  • Network: the default is open and unencrypted. Default-deny policies, blocked control plane ports and metadata from Pods, no NET_RAW, DenyServiceExternalIPs (CVE-2020-8554 has no patch), locked-down CoreDNS config, mTLS or CNI encryption. NetworkPolicy misses hostNetwork Pods.
  • Sensitive data: the mounted token, list or watch on Secrets, Pod creation, etcd and backups, nodes, env vars, logs, images, ConfigMaps, exec and snapshots, Helm releases. Encryption at rest doesn't stop authorized API readers.
  • Container to node: privileged, host namespaces, hostPath, SYS_ADMIN, root, runtime CVEs. Baseline blocks the known escapes; allowPrivilegeEscalation: false, drop ALL, non-root and seccomp are Restricted. Add user namespaces and sandboxes.
  • Within the API: escalate, bind, impersonate, workload creation, nodes/proxy, CSR approval, token creation, webhook configs, namespace edits. Node to cluster: Node authorizer plus NodeRestriction (not default; kubeadm enables it). Cluster to cloud: metadata and node roles; use workload identity.
  • Detect with audit signals (impersonation, RBAC writes, Secret lists, 403 bursts) and Falco (only stable rules load by default; privileged-launch and metadata rules are incubating). Self-check with kubectl auth can-i --list --as=....
