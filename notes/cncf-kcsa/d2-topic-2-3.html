2.3: Container Networking, Client Security and Storage

Three more parts of a Kubernetes® cluster to secure: the Pod network and the plugins that build it, the clients and kubeconfig files people use to reach the API, and the volumes that hold the cluster's data.

Overview

Topic 2.3

Container Networking. Client Security. Storage.

The curriculum gives only the names. This page treats each as a part of the cluster to secure. Container networking: the Pod network, CNI plugins, DNS and how Services are exposed. Client security: kubectl and other API clients, and the kubeconfig files that hold their credentials. Storage: volumes, who can create and mount them, and how their data is protected.

NetworkPolicy in depth is in topic 3.4, service mesh encryption in topic 5.2, TLS for Ingress and Gateway in topic 5.3, and Secrets in topic 3.3. Quotes are from kubernetes.io (CC BY 4.0) and the projects named.

Running example. The web shop's developers reach the cluster with kubectl from their laptops and from CI. The shop's database keeps its data on a PersistentVolume, and the frontend is exposed to the internet.

The Pod network and CNI

Topic 2.3The default network model, and the plugins that implement it.

"Each pod in a cluster gets its own unique cluster-wide IP address", and "all pods can communicate with all other pods, whether they are on the same node or on different nodes", "without the use of proxies or address translation (NAT)". The multi-tenancy page spells out the security consequence:

Open and unencrypted by default. "By default, all pods in a Kubernetes cluster are allowed to communicate with each other, and all network traffic is unencrypted. This can lead to security vulnerabilities where traffic is accidentally or maliciously sent to an unintended destination, or is intercepted by a workload on a compromised node." NetworkPolicy fixes the first part, but only if the network plugin supports it: "Otherwise, NetworkPolicy resources will be ignored."

How CNI plugins run

Kubernetes doesn't build the Pod network itself. The container runtime calls a CNI (Container Network Interface) plugin for each Pod. CNI is "a specification and libraries for writing plugins to configure network interfaces in Linux containers" (spec version 1.1.0, a CNCF incubating project). Since v1.24 the kubelet no longer manages CNI.

  • Plugin binaries live in /opt/cni/bin and configuration in /etc/cni/net.d. The runtime, running as root, executes the binary named in the config for every new Pod.
  • The plugin's agent usually runs as a DaemonSet with hostNetwork and NET_ADMIN, often more (Calico's node agent is privileged), plus a cluster-wide ServiceAccount.

The CNI directories are root code execution. Write access to /opt/cni/bin or /etc/cni/net.d, for example through a hostPath volume, lets an attacker run code as root each time a Pod starts, and control its networking. A compromised CNI agent can read, redirect or drop Pod traffic and switch off policy enforcement. Keep CNI namespaces privileged-only and forbid hostPath elsewhere.

Encrypting traffic between nodes

Kubernetes doesn't encrypt Pod traffic. Some CNI plugins can: Cilium offers IPsec or WireGuard®, and Calico offers WireGuard, encrypting traffic as it travels between nodes. The Security Checklist notes: "Not all CNI plugins provide encryption in transit. If the chosen plugin lacks this feature, an alternative solution could be to use a service mesh". CNI encryption covers the wire between nodes only: not traffic between Pods on the same node, and it says nothing about which workload is talking. Service mesh mTLS adds workload identity (topic 5.2).

DNS and spoofing

Topic 2.3Cluster DNS settings that matter for security, and attacks from inside a node.

CoreDNS has been the default cluster DNS since v1.13. Every Pod can resolve the Services of every namespace (<svc>.<ns>.svc.cluster.local), so DNS gives an attacker a map of the cluster. A default-deny network policy must still allow DNS: the multi-tenancy page recommends a deny-all policy "with another rule that allows all pods to query the DNS server".

  • dnsPolicy: ClusterFirst, ClusterFirstWithHostNet, Default (use the node's resolver) or None (use only dnsConfig). With None, a Pod can point at any resolver and skip cluster DNS logging and filtering.
  • CoreDNS pods option: the plugin's default is disabled. insecure answers Pod-name queries "without checking k8s" and "is vulnerable to abuse if used maliciously in conjunction with wildcard SSL certs". kubeadm's CoreDNS configuration sets pods insecure, for compatibility with kube-dns.

"Default" isn't the default. "'Default' is not the default DNS policy. If dnsPolicy is not explicitly specified, then 'ClusterFirst' is used."

NET_RAW and spoofing on a node

The NET_RAW capability lets a container craft raw packets: forged ARP replies, DNS answers or IPv6 router advertisements on the node's network. CVE-2020-10749 showed the danger: "By sending 'rogue' router advertisements, a malicious container can reconfigure the host to redirect part or all of the IPv6 traffic of the host to the attacker-controlled container". The advisory said "Kubernetes itself is not vulnerable"; the affected party was the networking implementation. Its mitigations included "Disallow CAP_NET_RAW for untrusted workloads or users."

SettingNET_RAW?
containerd default capabilitiesIncluded
CRI-O default capabilitiesNot included
Baseline Pod Security StandardCan't be added, but isn't dropped either
Restricted Pod Security StandardRemoved: containers "must drop ALL capabilities"

So on containerd, a Baseline Pod still has NET_RAW. Drop it explicitly with capabilities: drop: ["ALL"].

kube-dns is deprecated. Kubernetes v1.37 deprecated the old kube-dns add-on, and no new packages are expected after v1.40. NodeLocal DNSCache moved to its own repository. Use CoreDNS.

Exposing Services

Topic 2.3How Service types and Ingress controllers widen the attack surface.

  • NodePort: "Every node in the cluster configures itself to listen on that assigned port" (30000-32767), even nodes that don't run the Pods.
  • LoadBalancer: a cloud load balancer, often public by default. Restrict it with spec.loadBalancerSourceRanges or the provider's internal load balancer option. The checklist: "Use of LoadBalancer and ExternalIPs is restricted."
  • Ingress and Gateway: the controller that implements them often holds read access to Secrets for TLS certificates, which makes it a high-value target.

ingress-nginx is retired; externalIPs is deprecated. The Kubernetes project announced on 11 November 2025 that ingress-nginx would get only best-effort maintenance until March 2026, then "no further releases, no bugfixes, and no updates to resolve any security vulnerabilities". Its repository is archived. The Ingress API itself is frozen, not removed, and kubernetes.io recommends Gateway API instead. Service externalIPs was deprecated in v1.36 because of CVE-2020-8554 (topic 2.2).

Why the retirement matters: CVE-2025-1974. Published 23 March 2025 with CVSS 9.8, it meant "an unauthenticated attacker with access to the pod network can achieve arbitrary code execution in the context of the ingress-nginx controller". In the default installation, "the controller can access all Secrets cluster-wide." The pattern behind it and related bugs: a user who can create an Ingress injects configuration through annotations, takes over the controller, then reads every Secret. Find remaining installs with kubectl get pods -A -l app.kubernetes.io/name=ingress-nginx.

kubeconfig files

Topic 2.3The files that hold every client's credentials, and how they can be abused.

"A file that is used to configure access to clusters is called a kubeconfig file." kubectl reads $HOME/.kube/config unless --kubeconfig or KUBECONFIG says otherwise. It holds cluster addresses, CA certificates and user credentials, so whoever can read it can act as you. Client tools write it with mode 0600.

Credential in the fileRisk
Client certificate and keyLong-lived; "cannot be individually revoked"; the key "cannot be password-protected"
Bearer tokenWorks for anyone who copies it until it expires or is revoked
exec credential plugin (GA v1.22)Fetches short-lived tokens at run time, so no secret sits in the file, but runs a program with your privileges
auth-provider (legacy)The gcp and azure providers were removed in v1.26; use their exec plugins

For people, the authentication hardening guide recommends "external authentication sources such as OIDC" with short-lived tokens. An exec entry for the shop's developers:

Short-lived credentials via a plugin (kubeconfig excerpt) 
users:
- name: dev
  user:
    exec:
      apiVersion: >-
        client.authentication.k8s.io/v1
      # runs with your privileges
      command: kubelogin
      args: ["get-token"]
      interactiveMode: IfAvailable

A kubeconfig can run code. kubernetes.io warns: "Only use kubeconfig files from trusted sources. Using a specially-crafted kubeconfig file could result in malicious code execution or file exposure. If you must use an untrusted kubeconfig file, inspect it carefully first, much as you would a shell script." The exec.command field can name any program. When several files are merged through KUBECONFIG, "the first file to set a particular value or map key wins", so a planted file earlier in the list can redirect a context or swap a user's credentials.

Allowlisting credential plugins with kuberc

kuberc is kubectl's preferences file (~/.kube/kuberc; beta and on by default since v1.34). Unlike a kubeconfig, it "does not contain cluster details, usernames or passwords". Since v1.35 it can limit which credential plugins kubectl will run:

Only run known plugins (kuberc) 
apiVersion: kubectl.config.k8s.io/v1beta1
kind: Preference
credentialPluginPolicy: Allowlist
credentialPluginAllowlist:
- command: /usr/local/bin/kubelogin

The policy can be AllowAll, DenyAll or Allowlist. If it's left unset, it's the same as AllowAll, so the protection is opt-in.

Check your own client (shell) 
# who the API server thinks you are
kubectl auth whoami

# current context only, secrets hidden
kubectl config view --minify

# the file should be 600 and yours
stat -c '%a %U' ~/.kube/config
chmod 600 ~/.kube/config

Safe client habits

Topic 2.3kubectl features that can leak your access, and keeping clients current.

FeatureRiskSafe use
--insecure-skip-tls-verifyThe server certificate isn't checked: "This will make your HTTPS connections insecure". A fake API server can collect your tokenNever; fix the CA instead
kubectl proxyAdds your credentials to every request, with no authentication on the proxy portKeep the default localhost address and host filter; never --disable-filter, which "can leave you vulnerable to XSRF attacks"
kubectl port-forward--address 0.0.0.0 exposes a Pod's port, such as a database, to your local network, bypassing network policiesKeep the default localhost
Impersonation (--as)The impersonate verb on users or groups can reach system:mastersGrant rarely; constrained impersonation (beta in v1.36) scopes it
kubectl cpRelies on tar in the container; a malicious container has repeatedly been able to write files on the user's machineCopy only from trusted containers; keep kubectl patched

kubectl cp path traversal bugs date from 2018 (CVE-2018-1002100) through several 2019 CVEs to CVE-2026-19444 (August 2026, Windows clients). kubectl "is supported within one minor version (older or newer) of kube-apiserver", so upgrade clients along with clusters. kubectl version --client shows yours.

  • CI systems hold some of the most valuable kubeconfigs. Prefer short-lived tokens through the CI provider's workload identity federation, namespace-scoped roles rather than cluster-admin, and never commit a kubeconfig.
  • Web UIs are clients too. The Kubernetes Dashboard "has been archived and is no longer actively maintained"; kubernetes.io suggests Headlamp, now part of SIG UI. In-cluster UIs act through a ServiceAccount, so give it least privilege and don't expose it publicly.

Volumes and who can use them

Topic 2.3Access modes, file ownership, and the permission to create storage.

Access modeMeaning
ReadWriteOnce (RWO)Read-write by a single node; several Pods on that node can still use it
ReadOnlyMany (ROX)Read-only by many nodes
ReadWriteMany (RWX)Read-write by many nodes
ReadWriteOncePod (RWOP)Read-write by a single Pod in the whole cluster; GA since v1.29, CSI volumes only

Access modes aren't write protection. "Volume access modes do not enforce write protection once the storage has been mounted." Even a ReadOnlyMany volume "is no guarantee that it will be read-only". Only ReadWriteOncePod actually constrains access. For read-only, set readOnly: true on the volume mount.

File ownership

The shop database's storage (Pod and PVC) 
apiVersion: v1
kind: Pod
metadata:
  name: db
  namespace: shop
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    # volume files get this group
    fsGroup: 2000
    fsGroupChangePolicy: OnRootMismatch
    # ignore the image's /etc/group
    supplementalGroupsPolicy: Strict
  containers:
  - name: db
    image: shop/db:1.0
    volumeMounts:
    - name: data
      mountPath: /var/lib/db
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: db-data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data
  namespace: shop
spec:
  # one Pod only, cluster-wide
  accessModes: ["ReadWriteOncePod"]
  storageClassName: retained-enc
  resources:
    requests:
      storage: 10Gi
  • fsGroup makes Kubernetes change the ownership of volume files to that group; OnRootMismatch does so only when the volume's top directory doesn't already match, which is faster on large volumes.
  • supplementalGroupsPolicy: Strict (GA in v1.35) attaches only the groups in the Pod spec. The default, Merge, also adds groups from the image's /etc/group, which could silently grant access to group-owned files. Strict needs containerd 2.0+ or CRI-O 1.31+.

The right to create storage

PersistentVolumes, StorageClasses and CSIDrivers are cluster-scoped; PVCs are namespaced. RBAC good practices: "If someone - or some application - is allowed to create arbitrary PersistentVolumes, that access includes the creation of hostPath volumes". So "trusted administrators should create PersistentVolumes, and constrained users should use PersistentVolumeClaims".

Pod Security can't see a hostPath behind a claim. A Pod that mounts a PVC bound to a hostPath PersistentVolume lists only persistentVolumeClaim in its spec, so the Baseline standard passes it. Control hostPath at PV creation. Similarly, generic ephemeral volumes let anyone who can create Pods "create PVCs indirectly ... even if they do not have permission to create PVCs directly".

Protecting stored data

Topic 2.3Encryption, deletion, snapshots and the storage drivers on each node.

Kubernetes' EncryptionConfiguration encrypts API data in etcd (topic 1.1), not what's on a PersistentVolume. Volume encryption is the storage backend's job, usually chosen through StorageClass parameters that differ by driver:

Encrypted, retained volumes (StorageClass, illustrative) 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: retained-enc
# example: the AWS EBS CSI driver
provisioner: ebs.csi.aws.com
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer
parameters:
  # driver-specific keys
  encrypted: "true"
  kmsKeyId: <kms-key-arn>
Reclaim policyWhen the claim is deletedSecurity angle
Delete (StorageClass default)The PV and the backing storage are deletedRelies on the backend to wipe the data
RetainThe PV stays "released"; "the previous claimant's data remains on the volume"Good for recovery; someone must clean up and track released volumes
Recycle (deprecated)"A basic scrub (rm -rf /thevolume/*)", then reuseNot secure erasure; data remnants can reach the next claimant
  • Snapshots (GA v1.20, installed as CRDs): anyone who can create a VolumeSnapshot and a PVC in a namespace can copy any volume there into a new one. Pre-provisioned VolumeSnapshotContents, which can point at any backend snapshot, should be admin-only.
  • CSI drivers: "containerized CSI node plugins are typically deployed as privileged containers", and the controller part holds storage-admin credentials. In 2026, the NFS and SMB CSI drivers had path traversal bugs through crafted volume identifiers. The mitigation: "Restricting PersistentVolume creation privileges to trusted administrators".
  • Secrets on disk: Secret volumes are tmpfs, "never written to non-volatile storage". For other sensitive scratch files, use emptyDir with medium: Memory and a sizeLimit.
CVEWhat happened
CVE-2017-1002101subPath mounts could follow symlinks "outside of the volume, including the host's filesystem"
CVE-2021-25741 (high)A symlink exchange gave "hostPath-like access without use of the hostPath feature", worst where hostPath was already banned

CVE-2024-10220The gitRepo volume allowed arbitrary command execution; the volume type is gone from v1.36

New in v1.37 (alpha): bindMountOptions on a volume mount can add noexec, nosuid and nodev, so a compromised process can't download and run binaries from a writable volume, and emptyDir.mode sets the directory's permissions (default still 0777).

Key takeaways

  • The Pod network is flat, allow-all and unencrypted by default; NetworkPolicy works only if the CNI plugin supports it. CNI encryption (WireGuard, IPsec) covers node-to-node traffic only.
  • CNI binaries in /opt/cni/bin run as root for every Pod; agents are host-network and highly privileged. Cilium and CoreDNS are CNCF graduated; CNI is incubating; Calico and Flannel aren't CNCF.
  • DNS: default dnsPolicy is ClusterFirst; kubeadm sets CoreDNS pods insecure; kube-dns deprecated (1.37). NET_RAW enables spoofing: containerd grants it, Baseline doesn't remove it, Restricted does.
  • NodePort opens every node; restrict LoadBalancers; externalIPs deprecated (1.36). ingress-nginx is retired (no fixes after March 2026); CVE-2025-1974 was 9.8 and exposed all Secrets.
  • kubeconfigs hold credentials (0600) and can run code through exec: only use trusted files. Prefer short-lived OIDC or exec tokens; kuberc credentialPluginPolicy: Allowlist (beta 1.35) limits plugins; unset = AllowAll.
  • Never --insecure-skip-tls-verify; keep kubectl proxy and port-forward on localhost; limit impersonate; kubectl within ±1 minor and patched (kubectl cp CVEs). Dashboard archived; Headlamp suggested.
  • Storage: access modes aren't write protection (only RWOP constrains); fsGroup and supplementalGroupsPolicy: Strict (GA 1.35); PV creation = hostPath, admin-only; volume encryption comes from the backend; Retain keeps data, Recycle is deprecated; CSI node plugins are privileged.
