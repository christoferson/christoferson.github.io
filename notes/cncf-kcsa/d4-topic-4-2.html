4.2: Persistence, Denial of Service, Malicious Code Execution and Compromised Applications

Three things attackers do in a Kubernetes® cluster: stay in, knock things over, and run their own code. For each, the main techniques as public threat matrices describe them, and the controls that detect and prevent them.

Overview

Topic 4.2

Persistence. Denial of Service. Malicious Code Execution and Compromised Applications in Containers.

The curriculum gives only these names. This page treats each as an attacker goal on the map from topic 4.1, describes the techniques at the level of public threat matrices, and focuses on detection and prevention. The other goals (attacker on the network, access to sensitive data, privilege escalation) are in topic 4.3, and the frameworks themselves in topic 6.2.

Sources: kubernetes.io (CC BY 4.0), the Microsoft Threat Matrix for Kubernetes (CC BY 4.0), MITRE ATT&CK® (used under MITRE's terms), the CNCF® Financial User Group attack trees (Apache-2.0) and the Falco rules (Apache-2.0). Incidents reported by security vendors are summarized in a line each.

Running example. A vulnerable library in the shop's api image lets an attacker run commands inside one api Pod. What could they do next, how would the team notice, and what limits the damage?

Escaping from a container to the node (MITRE T1611 Escape to Host) is privilege escalation, covered in topic 4.3. The CNCF Financial User Group's attack trees cover the same ground, with trees named Establish Persistence, Denial of Service, Malicious Code Execution and Compromised Container. They were modeled on Kubernetes 1.14, so some leaves mention ports and Docker integrations that no longer exist. The project's own summary of the main mitigations still holds: "Strict RBAC policies or disabling the automatic service token mounting are key mitigations".

ATT&CK renamed a tactic in 2026. Version 19 (April 2026) split "Defense Evasion" into Stealth and Defense Impairment. Older material, and the Microsoft matrix, still use the old name.

Persistence

Topic 4.2How attackers make a foothold survive restarts, and where to look for it.

A shell in a container is fragile: Kubernetes replaces containers and Pods all the time. The attack trees order footholds by how much they survive. Defenders can use the same ladder to decide where to look:

FootholdSurvivesWhere it shows up
A process in a running containerNothing: gone when the container restartsRuntime detection; audit events for pods/exec
A backdoored image in the registry (implant internal image)Pod restarts and redeployments that pull itRegistry pushes, image digests changing for the same tag (topic 1.3)
Workload objects: a CronJob, DaemonSet or DeploymentPod deletion; the controller recreates it. A DaemonSet runs on every nodeAudit events creating workloads, unfamiliar objects in any namespace
A mutating admission webhookEverything: it can inject a sidecar into every new Pod (sidecar injection)Changes to MutatingWebhookConfigurations
Credentials: a token Secret, a client certificate, a new RBAC bindingWorkload deletion; client certificates can't be revoked (topic 3.2)Audit events for CSRs, serviceaccounts/token, (Cluster)RoleBindings
Node level: a static Pod manifest, files written through a writable hostPathCluster-level cleanup; static Pods bypass the API serverFile integrity monitoring on nodes, mirror Pods that no one created
Hunt for persistence (shell) 
# scheduled and per-node workloads
kubectl get cronjobs,daemonsets -A

# webhooks that see every new object
kubectl get \
  mutatingwebhookconfigurations

# who holds cluster-admin
kubectl get clusterrolebindings \
  -o wide | grep cluster-admin

# certificate requests, recent first
kubectl get csr \
  --sort-by=.metadata.creationTimestamp

Static Pods show up in the API as mirror Pods, named after their node and carrying the kubernetes.io/config.mirror annotation. One that nobody put in /etc/kubernetes/manifests on purpose is a red flag (topic 2.2).

Prevention, in short. Restrict who can create workloads, webhook configurations, bindings, CSRs and tokens (topic 3.2); forbid hostPath and privileged Pods (topic 3.1); pin images by digest and allow only trusted registries; audit those object types at the RequestResponse level (topic 3.5); and protect node manifest directories.

Denial of service

Topic 4.2Exhausting nodes, the control plane or an application, and the limits that stop it.

TargetHow it's exhaustedControls

Cap processes per Pod on each node (KubeletConfiguration) 
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
# max processes per Pod (-1 = none)
podPidsLimit: 1024

Kubernetes has no per-Pod PID field; the limit is set per node. The API also caps object sizes: a Secret or ConfigMap at 1 MiB, an etcd request at 1.5 MiB and an API request body at 3 MiB.

  • Parser bugs: CVE-2019-11253 let a small YAML or JSON document with deeply nested references ("billion laughs") consume the API server's memory.
  • Protocol attacks: since v1.29 the API server limits HTTP/2 from unauthenticated clients (the UnauthenticatedHTTP2DOSMitigation gate, beta and on by default), a response to HTTP/2 attacks such as "Rapid Reset".

Resource hijacking

The most common "impact" in real incidents isn't an outage: it's cryptocurrency mining on someone else's CPUs, which Microsoft's matrix calls resource hijacking. Public cases include a 2018 report of a car maker's cloud account mined through an unprotected Kubernetes dashboard, Unit 42's 2021 "Hildegard" campaign, which entered through a misconfigured kubelet, and Microsoft's 2023 report on the Kinsing malware targeting vulnerable containers. The defences are the same as above (CPU limits, quotas) plus restricted access and detection of unexpected processes and outbound connections.

Limits are a security control. A Pod without resource limits, or a namespace without quotas, is a denial-of-service risk to everything sharing the node or the control plane. kubernetes.io's Application Security Checklist asks for memory limits on every workload (topic 1.3).

Once inside, an attacker's first moves are predictable: read the mounted ServiceAccount token and try the API, query the cloud metadata service, scan the flat Pod network, and look for a way onto the node through privileged settings, hostPath or a runtime bug. Those steps are the subject of topic 4.3. The attack trees call "default network exposure of the control plane to all running containers" a main vector.

Runtime detection

Audit logs show API calls, not what happens inside a container (topic 3.5). Runtime tools watch system calls and process activity instead:

  • Falco (CNCF graduated): its default rules include "Terminal shell in container" and "Contact K8S API Server From Container". Many more rules exist in its sandbox and incubating sets, which aren't loaded by default.
  • Tetragon (part of the Cilium project) and KubeArmor (CNCF sandbox) can also enforce policy, blocking an action rather than only alerting.

Responding to a compromised Pod

Topic 4.2Containing a compromised workload without destroying the evidence.

  1. Isolate, don't deleteDeleting the Pod destroys evidence, and the ReplicaSet just starts a fresh copy. Cut its network access and take it out of service first.
  2. Take it out of serviceRemoving the label that the Service and ReplicaSet select on (here app) stops traffic to it, and the ReplicaSet replaces it with a clean Pod.
  3. Contain the nodekubectl cordon stops new Pods landing on that node while you investigate.
  4. Collect evidenceLogs, audit events, runtime alerts. A container checkpoint (beta since v1.30, through the kubelet API only) captures its memory, but treat that file as highly sensitive.
  5. Rotate and rebuildRotate every credential the Pod could reach (its token, mounted Secrets, cloud credentials), fix the cause, and redeploy from a clean image.
Quarantine policy for the shop (NetworkPolicy) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: quarantine
  namespace: shop
spec:
  podSelector:
    matchLabels:
      quarantine: "true"
  # no rules: deny both directions
  policyTypes:
  - Ingress
  - Egress
Quarantine one Pod and its node (shell) 
# apply the policy above to it
kubectl label pod api-7d9f -n shop \
  quarantine=true
# out of the Service and ReplicaSet
kubectl label pod api-7d9f -n shop \
  app-
# no new Pods on its node
kubectl cordon node2

A quarantine policy doesn't override others. NetworkPolicies only add allows, so any other policy that still selects the Pod, such as an allow-DNS policy with podSelector: {}, keeps working. Removing the Pod's app labels drops the policies that select on them. For a true block regardless of other policies, use an Admin-tier ClusterNetworkPolicy with a Deny rule (topic 3.4), or the network plugin's own deny policies.

Key takeaways

  • Public catalogues: the Microsoft Threat Matrix (persistence, execution, impact techniques), MITRE ATT&CK Containers (T1609, T1610, T1053.007, T1525, T1496, T1499; Defense Evasion split in 2026), and the CNCF Financial User Group attack trees.
  • Persistence, by what survives: processes (nothing), backdoored images, workload objects (CronJobs, DaemonSets), mutating webhooks (sidecar injection), credentials (token Secrets, unrevocable client certificates, RBAC bindings), node-level (static Pods, hostPath writes). Hunt with kubectl and audit; prevent with RBAC, Pod Security, digests and audit.
  • DoS: node CPU, memory, PIDs (podPidsLimit, per node) and disk; API server (APF); etcd (object quotas, size limits); priority abuse. Limits and quotas are security controls. Resource hijacking (crypto-mining) is the most common real impact.
  • Code gets in through app exploits, bad images, misused exec or Pod creation, pipelines, or exposed management services. Then: token, metadata, network, escape (topic 4.3).
  • Shrink the blast radius: no token mount, Restricted Pod Security, read-only root, no shell, egress policy, metadata blocked, user namespaces or sandboxes, limits. Detect at runtime with Falco, Tetragon or KubeArmor.
  • Respond: isolate (quarantine label and policy), take it out of service (remove the app label), cordon the node, collect evidence (checkpoints are sensitive), rotate credentials, rebuild. Quarantine policies don't override other allows.
