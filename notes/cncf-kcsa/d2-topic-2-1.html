Overview

Topic 2.1

API Server. Controller Manager. Scheduler. Etcd.

The curriculum gives only the component names. This page asks three questions about each one: what it does, what an attacker gains by compromising it, and how it is secured (configuration, network exposure, credentials and file permissions). Flag examples follow kubeadm, the reference installer. On a managed service the provider sets these flags for you.

Page 1.1 already covered the ports, keeping the control plane off the internet, etcd mutual TLS and encryption at rest. Authentication and authorization in depth are in topic 3.2, audit logging in topic 3.5, certificates in topic 5.3 and admission control in topic 5.4. Quotes are from kubernetes.io (CC BY 4.0) and etcd.io.

Running example. The web shop runs on a self-managed cluster built with kubeadm: three control plane nodes, each running all four components as static Pods. The platform team is reviewing how each one is configured.

The control plane at a glance

Topic 2.1What each component holds, and what its compromise means.

Kubernetes uses a "hub-and-spoke" pattern: "All API usage from nodes (or the pods they run) terminates at the API server. None of the other control plane components are designed to expose remote services." The scheduler, the controller manager and every kubelet read and write cluster state through the API server. Only the API server, plus backup tooling, holds credentials for etcd.

ComponentWhat it holdsIf an attacker controls it
kube-apiserveretcd client certificate, kubelet client certificate, ServiceAccount signing keyEvery request to the cluster passes through it: full control
kube-controller-managerThe cluster CA private key and the ServiceAccount signing key (kubeadm), broad write permissionsMint certificates for any identity, forge tokens, create Pods anywhere
kube-schedulerPermission to bind and delete Pods; can't read SecretsPlace Pods on chosen nodes, evict workloads, leave Pods unscheduled
etcdAll cluster data, including Secrets"Equivalent to root permission in the cluster", with no admission control or audit logging

API server

Topic 2.1The front door: how requests are checked, and the flags that decide how strict it is.

"The API server is the front end for the Kubernetes control plane." By default it listens on port 6443, "protected by TLS". Every request then passes these stages (Controlling Access to the Kubernetes API):

  1. AuthenticationEach configured authenticator is "tried in sequence, until one of them succeeds". If none succeeds, the response is HTTP 401. Kubernetes "does not have a User object nor does it store usernames".
  2. Authorization"If any module authorizes the request, then the request can proceed. If all of the modules deny the request, then the request is denied (HTTP status code 403)."
  3. Admission controlMutating controllers first, then validating ones. "If any admission controller module rejects, then the request is immediately rejected." Admission doesn't act on reads.
  4. Validation and storageThe object is validated against its schema and written to etcd.

The "password" authenticator is gone. The Controlling Access page still lists "client certificates, password, and plain tokens", but password (basic) authentication with --basic-auth-file was removed in v1.19.

The kubeadm manifest for the shop's API server, trimmed to the security flags (P stands for /etc/kubernetes/pki):

kube-apiserver flags (static Pod excerpt) 
kube-apiserver
--secure-port=6443
--authorization-mode=Node,RBAC
--enable-admission-plugins=NodeRestriction
--client-ca-file=P/ca.crt
--tls-cert-file=P/apiserver.crt
--tls-private-key-file=P/apiserver.key
--service-account-key-file=P/sa.pub
--etcd-servers=https://127.0.0.1:2379
--etcd-cafile=P/etcd/ca.crt
# hardening kubeadm doesn't add
--profiling=false
--tls-min-version=VersionTLS12

kubeadm also sets --kubelet-client-certificate and --kubelet-client-key (the API server's client certificate for talking to kubelets), and the ServiceAccount token issuer and signing key (--service-account-issuer, --service-account-signing-key-file=P/sa.key).

The API server trusts any kubelet by default. "By default, the API server does not verify the kubelet's serving certificate, which makes the connection subject to man-in-the-middle attacks and unsafe to run over untrusted and/or public networks." kubeadm doesn't set --kubelet-certificate-authority. Kubelet certificates are covered in topic 2.2.

Limiting anonymous access

Turning anonymous authentication off entirely with --anonymous-auth=false breaks health probes that call /livez and /readyz without credentials, including kubeadm's own. The structured authentication configuration (GA in v1.34) can allow anonymous requests on named paths only:

Anonymous only for health checks (AuthenticationConfiguration) 
apiVersion: apiserver.config.k8s.io/v1
kind: AuthenticationConfiguration
anonymous:
  enabled: true
  # the only paths open to anonymous
  conditions:
  - path: /livez
  - path: /readyz
  - path: /healthz

Load it with --authentication-config. "Any other endpoints will not be reachable anonymously, even if your authorization configuration would allow it." That protects against a mistaken RBAC binding to system:anonymous. If the file has an anonymous block, you can't also set --anonymous-auth. The equivalent for authorizers, --authorization-config, has been GA since v1.32 (topic 3.2).

Who can reach which endpoint

EndpointWho can read it by default
/livez, /readyz, /healthz, /versionEveryone, including unauthenticated users, through the system:public-info-viewer ClusterRole (/healthz is deprecated since v1.16)
/metrics, /flagz, /statuszThe system:monitoring group and admins; "the metric endpoint may expose sensitive information." /flagz and /statusz are beta since v1.36

The system:masters group

RBAC good practices: "Any user who is a member of this group bypasses all RBAC rights checks and will always have unrestricted superuser access, which cannot be revoked by removing RoleBindings or ClusterRoleBindings." The API server checks this group before any other authorizer, so it also bypasses authorization webhooks, and it's exempt from API Priority and Fairness. The Security Checklist says it "should only be used as a break-glass mechanism".

admin.conf is no longer system:masters. Since kubeadm v1.29, admin.conf belongs to the group kubeadm:cluster-admins, which an RBAC binding gives cluster-admin rights, so the access can be revoked. A separate super-admin.conf, created only on the node where kubeadm init ran, carries system:masters. Keep it offline. Membership comes from the certificate's organization field, and Kubernetes can't revoke a client certificate: it stays valid until it expires.

API Priority and Fairness

API Priority and Fairness (APF, GA in v1.29) protects the API server from being overwhelmed. It "classifies and isolates requests in a more fine-grained way", so "a poorly-behaved controller need not starve others". FlowSchemas sort requests into PriorityLevelConfigurations, each with its own share of concurrency. Requests over the limit get HTTP 429. Inspect them with kubectl get flowschemas and kubectl get prioritylevelconfigurations.

No more insecure port. The API server could once serve plain HTTP with no authentication or authorization on a local port. That ability was removed in v1.20, and the --insecure-port and --insecure-bind-address flags in v1.24. The kubeadm "Implementation details" page on kubernetes.io still lists --insecure-port=0; ignore it.

Controller manager

Topic 2.1The component with the most powerful keys, and how to limit what each controller may do.

kube-controller-manager "runs controller processes", compiled "into a single binary and run in a single process". In a kubeadm cluster it holds two keys worth more than anything else on the node:

  • The cluster CA private key (--cluster-signing-key-file=P/ca.key), used to sign approved certificate requests. Whoever has it can mint a client certificate for any identity, including system:masters.
  • The ServiceAccount private key (--service-account-private-key-file=P/sa.key). The flag now only "Enables legacy secret-based tokens"; current tokens are signed by the API server. But kubeadm points both at the same sa.key, so either host's compromise lets an attacker forge tokens.
FlagUpstream defaultkubeadm
--use-service-account-credentialsfalse: all controllers share the manager's own credentialtrue
--bind-address0.0.0.0127.0.0.1
--secure-port10257 (HTTPS only)Default
--profilingtrueNot changed (set false to harden)
--authentication-kubeconfig, --authorization-kubeconfigEmpty: requests are anonymous, and anything not on the always-allowed paths is forbiddencontroller-manager.conf

With --use-service-account-credentials, "kube-controller-manager starts each controller using a separate service account", each bound to a narrow role such as system:controller:deployment-controller. That's least privilege inside the control plane, and the Security Checklist asks for it.

The cloud-controller-manager "embeds cloud-specific control logic": it creates cloud load balancers and routes and watches cloud VMs. It holds cloud credentials, so its compromise reaches the cloud account. Give it least-privilege cloud permissions (topic 1.1). The in-tree cloud providers were switched off by default in v1.29, and the last one was removed in v1.31, so every cluster now uses an external cloud controller manager.

Controllers act on your behalf. A controller does things users ask for indirectly, so bugs can turn it into a "confused deputy". In CVE-2026-2270 (September 2026, fixed in v1.37.1), write access to StatefulSets and ControllerRevisions let a user make the StatefulSet controller create Pods in other namespaces. Patch releases matter even on the newest minor version.

Scheduler

Topic 2.1Who decides where Pods run, and the ways around that decision.

kube-scheduler "watches for newly created Pods with no assigned node, and selects a node for them to run on." Its ClusterRole, system:kube-scheduler, lets it read nodes and workloads, bind Pods to nodes, and delete Pods (for preemption). It can't read Secrets.

A compromised scheduler could put an attacker's Pod on the same node as a victim, steer sensitive Pods to a node the attacker controls, evict workloads, or leave Pods pending. The kubernetes.io scheduler hardening guide warns that a misconfigured scheduler "can target specific nodes and evict the workloads or applications that are sharing the node".

  • --bind-address: "the kube-scheduler does not need to be externally accessible. Setting the bind address to localhost is a secure practice." kubeadm sets 127.0.0.1; it serves HTTPS on 10259.
  • Profiling: turn it off to avoid the "risk of denial of service or information leakage". The --profiling flag is deprecated in favour of the configuration file.
  • Its kubeconfig (scheduler.conf) "should be protected with strict file permissions."
Scheduler profiling off (KubeSchedulerConfiguration) 
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
enableProfiling: false

The scheduler isn't the only way onto a node. "If the nodeName field is not empty, the scheduler ignores the Pod and the kubelet on the named node tries to place the Pod on that node", skipping taints and affinity rules. Anyone with create on pods/binding can also place Pods, and any Pod creator can pick a custom schedulerName. Use admission policy if those need restricting (topic 5.4).

Ports 10251 and 10252 are gone. The scheduler (10251) and controller manager (10252) used to serve plain HTTP with no authentication. Insecure serving stopped around v1.22 and v1.23, and the flags were removed in v1.24 (May 2022). Today they serve only HTTPS, on 10259 and 10257.

etcd

Topic 2.1Protecting the datastore that holds every object and Secret.

etcd is the "consistent and highly-available key value store used as Kubernetes' backing store for all cluster data." kubernetes.io's API server bypass risks page explains why direct access is so dangerous: it "is not subject to Kubernetes admission control and is not logged by Kubernetes audit logging." And etcd itself "doesn't encrypt key/value data stored on disk drives", so Secrets are only protected if encryption at rest is on (topic 1.1).

Kubernetes authenticates to etcd with TLS client certificates only. etcd has its own users and roles, but "etcd authentication is not planned for Kubernetes", so Kubernetes doesn't use them.

etcd flagDefaultPurpose
--client-cert-authfalseRequire a client certificate signed by the trusted CA (setting --trusted-ca-file turns this on too)
--peer-client-cert-authfalseSame check for other etcd members (with --peer-trusted-ca-file)
--listen-client-urlshttp://localhost:2379Use https, on localhost or a private address
--auto-tls, --peer-auto-tlsfalseSelf-signed certificates: encryption without authentication. Keep them off
--tls-min-versionTLS1.2Minimum TLS version
--data-dir${name}.etcd (kubeadm: /var/lib/etcd)etcd expects mode 700 and warns otherwise

Any certificate etcd trusts is a master key. "Any certificate issued by a certificate authority that etcd trusts allows full access to the data stored inside etcd", and "etcd client certificates that are only used for health checking can also grant full read and write access." That's why the etcd CA should be used for nothing else; kubeadm gives etcd its own CA. Note also that kubeadm's etcd listens on the node's IP as well as localhost, because the members of a highly available cluster need to reach each other. Firewall ports 2379 and 2380.

--auto-tls isn't real TLS security. etcd's docs describe it as being for when "communication encryption, but not authentication, is needed": "Self-signed certificates do not authenticate identity." Anyone could connect, or join as a peer.

Backups

"The snapshot file contains all the Kubernetes state and critical information. In order to keep the sensitive Kubernetes data safe, encrypt the snapshot files." Restrict who can read the backup location as tightly as etcd itself.

Back up and check a snapshot (shell) 
E=/etc/kubernetes/pki/etcd
etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=$E/ca.crt \
  --cert=$E/server.crt \
  --key=$E/server.key \
  snapshot save /backup/etcd.db

# status and restore use etcdutl
etcdutl --write-out=table \
  snapshot status /backup/etcd.db

etcd 3.6 and 3.7 changed the tools and flags. From etcd 3.6, snapshots are restored only with etcdutl, not etcdctl. etcd 3.6.0 (May 2025) replaced the --experimental-* flags with normal flags or --feature-gates entries. etcd 3.7.0 (July 2026), the default in Kubernetes 1.37, removed them along with the old v2 store, so manifests copied from older guides fail to start. etcd 3.4 is out of support. etcd is a CNCF graduated project (since November 2020) and, since 2023, also a Kubernetes SIG.

Control plane files and hosts

Topic 2.1The files on a control plane node that are as sensitive as the components themselves.

/etc/kubernetes/manifests/Static Pod manifests for the four components (written 0600, directory 0700)Write access lets an attacker change any flag or add a Pod. A static Pod that fails admission "still runs on the node"
/etc/kubernetes/pki/CA key (ca.key), sa.key, API server, front-proxy and etcd certificates and keys (keys 0600)The CA key mints any identity; sa.key forges tokens

The CIS Kubernetes Benchmark has checks for the permissions and ownership of these files; tools such as kube-bench run them (topic 1.1). kubernetes.io advises: "Avoid sharing the super-admin.conf or admin.conf files. Instead, create least privileged access even for people who work as administrators".

Certificates

kubeadm client certificates "expire after 1 year"; its CA lasts 10 years. In kubeadm config v1beta4 these are the certificateValidityPeriod and caCertificateValidityPeriod fields. v1beta3 was removed in v1.37. kubeadm renews certificates during every control plane upgrade.

Check and renew certificates (shell) 
# expiry of certs and kubeconfigs
sudo kubeadm certs check-expiration

# renew all, on every control plane node
sudo kubeadm certs renew all

After renewing, restart the control plane Pods so they load the new certificates.

Checking how components are configured

Inspect control plane flags (shell) 
# the control plane static Pods
kubectl -n kube-system get pods \
  -l tier=control-plane

# full command line of one component
kubectl -n kube-system get pod \
  kube-apiserver-cp1 -o yaml

# the API server's own flags (beta)
kubectl get --raw /flagz

Control plane nodes carry the taint node-role.kubernetes.io/control-plane:NoSchedule, which keeps ordinary workloads off them. Older material uses master: that label stopped being added in v1.24 and the taint in v1.25.

On a managed service you can't edit manifests, read /etc/kubernetes/pki or take raw etcd snapshots. You usually can control API endpoint exposure, export control plane audit logs, turn on Secret encryption with the provider's key service, and manage RBAC and admission policies. Flag questions about --profiling or etcd TLS are about self-managed clusters.

Lessons from CVEs

Topic 2.1Past control plane vulnerabilities, and the pattern they share.

From the official Kubernetes CVE feed:

CVEComponentWhat happened
CVE-2018-1002105 (critical, 9.8)API serverProxied connections could be reused to send arbitrary requests to a backend "authenticated with the Kubernetes API server's TLS credentials", reaching aggregated APIs or the full kubelet API
CVE-2020-8559API serverFrom a compromised node, a redirect could make the API server's client follow it using the original request's credentials
CVE-2020-8555, CVE-2025-13281Controller managerHalf-blind SSRF: certain volume types or StorageClasses made it send requests into the control plane's network
CVE-2026-2270Controller managerThe StatefulSet controller could be made to create Pods across namespaces (fixed in 1.37.1)

The common thread. Control plane components act with strong credentials on behalf of less privileged users. Most serious bugs make them do so for the wrong request: proxying, redirects, SSRF and confused deputies. Defenses: patch promptly, limit network reach from the control plane, give each component least privilege, and turn off what you don't use.

Key takeaways

  • All traffic goes through the API server; only it (and backups) should reach etcd. Request flow: authentication (401) → authorization (403) → mutating, then validating admission → validation → etcd.
  • Permissive upstream defaults: anonymous auth on, authorization falls back to AlwaysAllow, profiling on, bind address 0.0.0.0, kubelet certificate not verified. kubeadm sets Node,RBAC and NodeRestriction, but leaves profiling on.
  • Limit anonymous access to /livez, /readyz and /healthz with AuthenticationConfiguration anonymous.conditions (GA 1.34). Unauthenticated users can read health and version only; /metrics needs system:monitoring.
  • system:masters bypasses RBAC, webhooks and APF and can't be revoked. Since kubeadm 1.29 only super-admin.conf has it. APF (GA 1.29) is the API server's DoS protection.
  • Controller manager: holds the CA key and sa.key; use --use-service-account-credentials, bind to 127.0.0.1, profiling off. Scheduler: bind to localhost, enableProfiling: false; nodeName and pods/binding bypass it. Ports 10251 and 10252 removed in 1.24.
  • etcd: access = root, with no admission or audit; client and peer certificate auth with a dedicated CA; no --auto-tls; data dir 700; encrypted, restricted backups. etcd 3.7 (default in 1.37) removed --experimental-* flags; restore with etcdutl.
  • Protect /etc/kubernetes/manifests, /etc/kubernetes/pki and the kubeconfigs. kubeadm certificates last 1 year, the CA 10 years: kubeadm certs check-expiration and renew.
