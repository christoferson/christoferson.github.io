Overview

Topic 2.2

Kubelet. Container Runtime. KubeProxy. Pod.

The curriculum gives only the names. As with topic 2.1, this page asks of each: what it does, what an attacker gains by compromising it, and how it is secured. Kernel-level hardening (securityContext, seccomp, user namespaces, sandboxes) is in topic 1.2; Pod Security Standards are in topic 3.1; the Node authorizer in depth is in topic 3.2.

Quotes are from kubernetes.io and the CNCF® Glossary (CC BY 4.0) and from project security advisories.

Running example. The web shop's worker nodes run the kubelet, containerd and kube-proxy, set up with kubeadm. A security review asks: if one shop Pod were compromised, how far could the attacker get?

Kubelet API and its defaults

Topic 2.2What the kubelet exposes, and why its defaults depend on how it's started.

The kubelet is "an agent that runs on each node in the cluster. It makes sure that containers are running in a Pod." Its HTTPS API, on port 10250 on all interfaces by default, allows "disclosure of information about the pods running on a node, the logs from those pods, and execution of commands in every container running on the node." And: "Direct access to the kubelet API is not subject to admission control and is not logged by Kubernetes audit logging."

EndpointWhat it gives
/pods, /runningpods/Full specs of every Pod on the node
/exec, /run, /attach, /portForwardCommands and shells in any container on the node
/containerLogs, /logs/Container logs and node log files
/configzThe kubelet's running configuration
/stats/, /metricsResource statistics and Prometheus metrics
/checkpointA container's full memory written to disk, which "includes all private data and possibly keys used for encryption" (beta, on since v1.30)
/debug/pprofGo profiling

Three different sets of defaults

kubernetes.io warns that "some default values differ between command-line flags and the kubelet config file":

How the kubelet startsAnonymous requestsAuthorizationRead-only port
Flags only, no --configAllowedAlwaysAllow10255 open
Config file, field left outRefused (401)Webhook0 (off)
kubeadm (writes a config file)RefusedWebhook0, and kubeadm warns if you change it

The kubelet's security flags are all deprecated in favour of the config file. Writing the settings out explicitly documents intent, and protects against a stray flag overriding them:

Hardened kubelet settings (KubeletConfiguration) 
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
authentication:
  # no credentials = 401
  anonymous:
    enabled: false
  # bearer tokens via TokenReview
  webhook:
    enabled: true
  # client certs from the cluster CA
  x509:
    clientCAFile: >-
      /etc/kubernetes/pki/ca.crt
authorization:
  # ask the API server (SAR)
  mode: Webhook
# no unauthenticated port 10255
readOnlyPort: 0
protectKernelDefaults: true
rotateCertificates: true
serverTLSBootstrap: true

Two kubelet traps. The kubernetes.io example of viewing a kubelet's configuration shows anonymous: enabled: true, AlwaysAllow and port 10255. That's output from a development cluster, not the defaults. Also, protectKernelDefaults: true doesn't set kernel parameters: the kubelet refuses to start unless the expected sysctls are already set on the host.

The read-only port has no authentication at all. It serves "with no authentication/authorization". CVE-2025-0426 (February 2025) let anyone fill a node's disk with checkpoint requests through it. Keep readOnlyPort: 0.

Check a node's kubelet settings (shell) 
# running config via the API server
# (needs get on nodes/proxy)
kubectl get --raw \
  "/api/v1/nodes/node1/proxy/configz" \
  | jq .kubeletconfig.authentication

# read-only port should refuse
curl -s http://<node-ip>:10255/pods

A direct call to https://<node-ip>:10250/pods without credentials should return 401. A 403 means anonymous access is on, with Webhook authorization. Pod JSON means anonymous access with AlwaysAllow, which is the worst case.

Kubelet authorization

Topic 2.2How kubelet API calls map to RBAC, and why nodes/proxy is so powerful.

In Webhook mode, the kubelet sends a SubjectAccessReview to the API server for each request. HTTP verbs become RBAC verbs (GET becomes get, POST becomes create), the resource is always nodes, and the path chooses the subresource:

Kubelet pathRBAC subresource
/stats/*nodes/stats
/metrics/*nodes/metrics
/logs/*nodes/log
/spec/*nodes/spec
/checkpoint/*nodes/checkpoint
/pods, /configz, /healthznodes/pods, nodes/configz, nodes/healthz first, then nodes/proxy
Everything else, including execnodes/proxy

The finer-grained subresources come from fine-grained kubelet authorization (alpha v1.32, beta v1.33, GA v1.36). A monitoring tool can now read /pods or /configz without the catch-all nodes/proxy.

get on nodes/proxy is not read-only. kubernetes.io, January 2026: some endpoints "support Websocket protocols via HTTP GET requests, which are authorized with the get verb. This means that get permission on nodes/proxy is not a read-only permission, and authorizes executing commands in any container running on the node." That access "bypasses audit logging and admission control". "Avoid granting the nodes/proxy catch-all permission, even with just the get verb."

Who may use the kubelet API? (shell) 
kubectl auth can-i get nodes/proxy
kubectl auth can-i get nodes/proxy \
  --as=system:serviceaccount:shop:web

Other mitigations from the bypass-risks page: allow port 10250 only from trusted address ranges, use webhook or certificate authentication, and make sure the read-only port is off.

Kubelet certificates and identity

Topic 2.2How a kubelet gets its credentials, and what a stolen kubelet credential allows.

  1. TLS bootstrapA new kubelet starts with a low-privilege bootstrap token (format abcdef.0123456789abcdef, valid 24 hours by default under kubeadm) and uses it to create a certificate signing request (CSR).
  2. Client certificateThe controller manager can auto-approve client CSRs. The kubelet gets a certificate with CN system:node:<node> and group system:nodes, valid one year.
  3. RotationWith rotateCertificates: true (default false; kubeadm forces it on), the kubelet renews its client certificate before expiry.
  4. Serving certificateBy default self-signed. With serverTLSBootstrap: true the kubelet requests one through the CSR API instead. Then the API server can verify it (topic 2.1).

Serving CSRs are never approved automatically. The kubernetes.io/kubelet-serving signer is "Never auto-approved by kube-controller-manager", "for security reasons": a serving certificate claims hostnames and IPs. A person or a custom approver must check each one: the requester is system:node:<name> in system:nodes, the usages are server auth only, and the IP and DNS names belong to that node.

Approve kubelet serving CSRs (shell) 
S=kubernetes.io/kubelet-serving
kubectl get csr \
  --field-selector spec.signerName=$S

# check requester, usages and SANs
kubectl describe csr csr-9wvgt
kubectl certificate approve csr-9wvgt

What a stolen kubelet credential can do

Two controls limit each kubelet to its own node. The Node authorizer lets a kubelet read only the Secrets, ConfigMaps and volumes of Pods bound to its node, and, since v1.34, only its own Node and Pods. The NodeRestriction admission plugin limits writes: kubelets "will only be allowed to modify their own Node API object, and only modify Pod API objects that are bound to their node", may not change their own taints, and may not set node-restriction.kubernetes.io/ labels.

NodeRestriction isn't on by default. It isn't in the API server's default admission plugin list; kubeadm adds it. Without it, a compromised node could relabel itself to attract sensitive Pods or edit other nodes. Even with it, patch promptly: CVE-2025-5187 (August 2025) let a node delete and recreate its own Node object with different taints.

Container runtime

Topic 2.2The software that actually starts containers, and its socket.

The kubelet talks to the runtime through the Container Runtime Interface (CRI), "the main protocol for the communication between the kubelet and Container Runtime", over a local socket. Kubernetes 1.37 requires CRI v1.

LayerExamplesProject
High-level runtime (CRI)containerd (socket /run/containerd/containerd.sock), CRI-O (/var/run/crio/crio.sock)Both CNCF graduated: containerd 2019, CRI-O 2023
Low-level OCI runtimerunc (containerd's default), crun (CRI-O's default)runc is an Open Container Initiative project, not CNCF
Sandboxed runtimesgVisor, Kata Containers (topic 1.2)Not CNCF

The runtime socket is root on the node

kubernetes.io: "An attacker with access to this socket can launch new containers or interact with running containers." The runtime doesn't apply RBAC, admission or Pod Security, and the Kubernetes audit log doesn't see the calls. So a client on the socket can start a privileged container with the host filesystem mounted, or open a shell in any container on the node and take its Secrets. The Docker socket (/var/run/docker.sock), where Docker Engine is still installed, is just as dangerous.

DANGER: what not to allow (Pod, teaching only) 
# Do not apply. Hands the Pod the
# node's containerd API.
apiVersion: v1
kind: Pod
metadata:
  name: sock-demo
spec:
  containers:
  - name: shell
    image: busybox:1.36
    command: ["sleep", "infinity"]
    volumeMounts:
    - name: cri
      mountPath: /cri.sock
  volumes:
  - name: cri
    hostPath:
      path: >-
        /run/containerd/containerd.sock
      type: Socket

The Baseline Pod Security Standard forbids hostPath, so enforcing it on the shop namespace blocks this Pod (topic 3.1). kubernetes.io's mitigations: restrict socket access to root; forbid hostPath mounts of the socket "either directly or by mounting a parent directory", and make allowed host mounts read-only; and restrict user access to nodes.

Runtime escapes

A runtime bug bypasses every Kubernetes control, so the runtime and runc need patching like the kernel:

CVEWhat it allowed
CVE-2019-5736A root process in a container could "overwrite the host runc binary (and consequently obtain host root access)"
CVE-2024-21626 ("Leaky Vessels", January 2024)A leaked file descriptor gave a new container process a working directory on the host filesystem, through a malicious image or runc exec. Fixed in runc 1.1.12
CVE-2025-31133, CVE-2025-52565, CVE-2025-52881 (November 2025)Container escapes by tricking runc into writing to host /proc files, including a way to bypass AppArmor and SELinux. Fixed in runc 1.2.8, 1.3.3 and 1.4.0-rc.3

The runc maintainers' own advice: "we strongly recommend all users use user namespaced containers", which blocks "most of the most serious aspects of these attacks". In Kubernetes that's hostUsers: false, GA since v1.36 (topic 1.2). Running node components themselves without root (the rootless kubelet) became beta in v1.37.

Runtime versions that are gone or going. dockershim, the kubelet's built-in Docker support, was removed in v1.24 (May 2022); Kubernetes has used only CRI v1 since v1.26. containerd 1.7 reached end of life on 30 September 2026, and kubernetes.io warns that from v1.38 "older versions of containerd will fail with newer kubelets". containerd 2.x also removed io_uring syscalls from its default seccomp profile.

kube-proxy

Topic 2.2The node agent that programs Service traffic, and the networking risks around it.

kube-proxy "maintains network rules on nodes" so that traffic to a Service's virtual IP reaches a backend Pod. In iptables and nftables modes the kernel forwards the packets; kube-proxy just writes the rules.

ModeStatus in v1.37
iptablesDefault on Linux; "a future version of Kubernetes will change the default to nftables"
nftablesGA since v1.33; by default exposes NodePorts only on the node's primary IPs
ipvsDeprecated since v1.35; off by default from v1.40, removed in v1.43
  • Privileges: under kubeadm, kube-proxy is a DaemonSet that runs privileged with hostNetwork on every node. Its RBAC role, system:node-proxier, is read-only (Services, EndpointSlices, nodes), so the danger is its host access, not its API rights.
  • Credentials: its kubeconfig, in the kube-proxy ConfigMap, points at the Pod's own projected ServiceAccount token, so there's no long-lived secret in the ConfigMap.
  • Ports: health checks on 10256 (all interfaces), metrics on 10249 (localhost only).

CVE-2020-8554 has no patch. "An attacker that is able to create a ClusterIP service and set the spec.externalIPs field can intercept traffic to that IP." It's "a design flaw that cannot be mitigated without user-facing changes", and all versions are affected. The fix is policy: the DenyServiceExternalIPs admission plugin (since v1.21, off by default) "rejects all net-new usage" of externalIPs, and nobody should be granted patch on services/status.

CVE-2020-8558 is a reminder that "localhost only" isn't a guarantee: a setting kube-proxy used for localhost NodePorts let neighbouring hosts and containers reach services bound to 127.0.0.1 on the node. Some network plugins replace kube-proxy entirely with eBPF; their agent is then just as privileged.

The Pod as a security boundary

Topic 2.2What containers in a Pod share, and the fields that break the wall between Pod and node.

The Pod is "the smallest and simplest Kubernetes object". Its containers share a network namespace (one IP, one localhost), can share volumes, and run on one node. So the boundary between workloads is the Pod, not the container: containers in one Pod trust each other. With shareProcessNamespace: true they also see each other's processes, "such as passwords that were passed as arguments or environment variables", and each other's filesystems through /proc/$pid/root.

Fields that reach the host

FieldWhat it exposes
hostNetworkThe node's interfaces and localhost-only services; skips most network policies
hostPIDEvery process on the node, including other workloads' environment variables
hostIPCShared memory of host processes
hostPath volumesThe node's filesystem: kubelet credentials, the runtime socket
hostPortA port on the node itself
privileged: trueAll capabilities and devices, no seccomp or AppArmor confinement

The Baseline Pod Security Standard forbids all of these, plus unsafe capabilities, host probes and unsafe sysctls (topic 3.1). On hostPath, kubernetes.io is direct: "Using the hostPath volume type presents many security risks. If you can avoid using a hostPath volume, you should." It "can expose privileged system credentials (such as for the kubelet) or privileged APIs (such as the container runtime socket)".

Allow-listing host directories only works read-only. A restriction on hostPath directories "is only effective when you additionally require that any mounts of that hostPath volume are read only." A read-write mount can be subverted to reach other paths. And type: Socket or Directory are existence checks, not security controls.

Static Pods

A static Pod is "managed directly by the kubelet daemon on a specific node, without the API server observing it"; kubeadm runs the control plane this way (topic 2.1). The kubelet publishes a read-only "mirror Pod" to the API. Static Pods "cannot refer to other API objects, such as ServiceAccount, ConfigMap, or Secret", and don't support ephemeral containers.

Static Pods dodge admission. "If a static Pod fails admission control, the kubelet won't register the Pod with the API server. However, the Pod still runs on the node." Anyone who can write to the manifest directory (staticPodPath) can run anything there. The kubelet loads every file in that directory that doesn't start with a dot, whatever its extension, so backup copies run too.

Ephemeral containers and kubectl debug

Ephemeral containers (GA v1.25) are added to a running Pod for troubleshooting, through the pods/ephemeralcontainers subresource. That subresource is not in the default edit or admin roles, so it must be granted on purpose. Pod Security Standards apply to ephemeral containers too.

  • kubectl debug -it web --image=busybox:1.36 --target=web adds a debugging container that shares the target's process namespace.
  • kubectl debug node/node1 -it --image=busybox:1.36 creates a Pod with host namespaces and the host's root filesystem at /host. That's root-level access to the node, so it's blocked wherever Baseline is enforced.

The kubectl debug default changed. Since kubectl v1.36 the default profile is general, not legacy; legacy is planned for removal in v1.39. The kubernetes.io "Debug Running Pods" page still says legacy is the default.

The Pod's API credential

Unless automountServiceAccountToken is false, each Pod gets a projected ServiceAccount token. It's bound to the Pod and has an audience and an expiry (an hour by default for explicitly projected tokens), and the kubelet refreshes it. A stolen token stops working when the Pod is deleted. Tokens and ServiceAccounts are covered in topic 3.2.

Key takeaways

  • The kubelet API (10250) can exec into every container on the node, and bypasses admission and audit. Defaults: flags only = anonymous + AlwaysAllow + read-only port 10255; config file (and kubeadm) = anonymous off, Webhook, readOnlyPort: 0.
  • Kubelet paths map to nodes/stats, /metrics, /log, /spec, /checkpoint; everything else to nodes/proxy. get nodes/proxy allows exec. Fine-grained subresources (nodes/pods, /configz, /healthz) are GA in 1.36.
  • Certificates: bootstrap token → client CSR (auto-approvable) → system:node:<name>; rotateCertificates defaults to false (kubeadm sets true); serving CSRs are never auto-approved. Node authorizer plus NodeRestriction (not on by default) confine a kubelet to its own node.
  • The runtime socket (and its parent directory) is root on the node and bypasses all Kubernetes controls. containerd and CRI-O are CNCF graduated; runc is OCI. Patch runc (Leaky Vessels 2024, three escapes November 2025) and use user namespaces. containerd 1.7 is end of life.
  • kube-proxy: iptables default, nftables GA (1.33), ipvs deprecated (1.35). Privileged and host-network, with read-only RBAC. CVE-2020-8554 (externalIPs) has no patch: use DenyServiceExternalIPs.
  • Pods: containers in a Pod trust each other. hostNetwork, hostPID, hostIPC, hostPath, hostPort and privileged break out to the node; Baseline forbids them. Static Pods run even if they fail admission. pods/ephemeralcontainers isn't in edit or admin; kubectl debug's default profile is now general.
