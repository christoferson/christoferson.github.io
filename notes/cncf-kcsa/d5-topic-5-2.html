5.2: Observability and Service Mesh

Two platform layers seen as security tools: the telemetry that lets you notice an attack in a Kubernetes® cluster (and must itself be protected), and the service mesh that gives every workload an identity, encrypts traffic between them and decides who may call whom.

Overview

Topic 5.2

Observability. Service Mesh.

The curriculum gives only the names. This page takes both from a security angle: observability as the signals for detecting and investigating attacks, the protection those signals need, and runtime security tools; service mesh as a layer that adds workload identity, encryption and authorization between services. Observability basics (metrics, logs, traces, OpenTelemetry, Prometheus) and mesh basics are in the KCNA notes on observability and networking; audit logging is in topic 3.5.

Quotes are from kubernetes.io and the CNCF® Cloud Native Security Whitepaper (CC BY 4.0), and from the Prometheus, OpenTelemetry, Falco, Tetragon, Istio and Linkerd documentation.

Running example. The shop's services run in a mesh. The goal: web may call api only with GET /api/*; all traffic between them is encrypted; and the security team can see, from outside the cluster, when a shell starts in a container or a Secret is read.

The CNCF whitepaper: "Through the use of behavioral and heuristic analysis, teams can detect and escalate outliers, suspicious events, and unexplained calls". On runtime: "The runtime environment of a container needs to be monitored and secured from a process, file, and network perspective", and some threats, such as "time or event delayed trojan horses", are "only detectable by comparing to baseline expected behavior".

kubernetes.io's Cloud Native Security page has an "Observability and runtime security" subsection. It asks you to review "the chain of components that populate data into that dashboard ... so that you can rely on it even during an incident", to consider "cryptographically measured boot or authenticated distribution of time (which helps ensure the fidelity of logs and audit records)", and, "for a high-assurance environment", to "ensure that logs are both tamper-proof and confidential."

Get evidence out fast. The whitepaper's key point on log handling: "Immediate forwarding of logs to a location inaccessible via cluster-level credentials also defeats an attacker's attempt to cover their tracks." It also warns that alerts must be "tuned for false positives to avoid alert flooding, fatigue, and false negatives".

Protecting the telemetry pipeline

Topic 5.2Logs, metrics and traces are data an attacker wants too: secure how they're collected and kept.

Logs

"In a cluster, logs should have a separate storage and lifecycle independent of nodes, pods, or containers", and "Kubernetes does not provide a native storage solution for log data." The usual pattern is a logging agent DaemonSet that reads every Pod's log files on its node. That makes it a high-value target: it sees all logs on the node and holds the backend's credentials, so keep its mounts and RBAC minimal. A logging sidecar in each Pod spreads those credentials into every Pod, and its logs aren't visible to kubectl logs.

Metrics

  • Kubernetes components serve /metrics, which needs authorization. The built-in system:monitoring role grants it, and kubernetes.io notes that "individual health check endpoints and the metric endpoint may expose sensitive information."
  • A scraper reading kubelet metrics needs nodes/metrics (and nodes/stats), never nodes/proxy, which allows exec into any container (topic 2.2).
  • Prometheus' own security model is blunt: "It is presumed that untrusted users have access to the Prometheus HTTP endpoint and logs", and "metrics are not considered secret." So never put secrets in labels, and keep Prometheus endpoints off public networks, since they're easy to overload. Server-side TLS and basic authentication arrived only in Prometheus 2.24 (2021), through --web.config.file, and are still marked experimental. The admin and lifecycle APIs are off by default.

OpenTelemetry Collector

The OpenTelemetry Collector (OpenTelemetry graduated in the CNCF in May 2026) gathers all three signals, so its configuration holds tokens and keys. Its security guidance:

  • Encrypt and authenticate receivers and exporters.
  • Bind to localhost or the Pod IP rather than 0.0.0.0; since v0.110.0, localhost is the default.
  • Ship only the components you use ("Minimizing the number of components you use minimizes the attack surface exposed"), and avoid running as root.
  • Scrub sensitive data before it leaves, using the redaction or attributes processor:
Strip auth headers and tokens from traces (Collector config excerpt) 
processors:
  attributes/scrub:
    actions:
    # http.request.header.authorization
    - pattern: header\.authorization$
      action: delete
  redaction:
    allow_all_keys: true
    # mask values of matching keys
    blocked_key_patterns:
    - ".*token.*"
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors:
      - attributes/scrub
      - redaction
      exporters: [otlp]

The redaction processor ships only in the contrib and Kubernetes Collector builds; attributes is also in the core build. OpenTelemetry's HTTP conventions warn that capturing request headers "can be a security risk".

Events aren't an audit trail. Kubernetes Events are ordinary API objects kept for an hour by default. They're useful hints (an admission denial in FailedCreate, a blocked image in ErrImagePull), but for evidence, ship them off-cluster and rely on the audit log for who did what.

A simple detection rule (Falco) 
- rule: Shell in container
  desc: A shell started in a container
  condition: >
    spawned_process and container
    and shell_procs
  output: >
    Shell in container
    (user=%user.name
    cmd=%proc.cmdline
    container=%container.id)
  priority: WARNING
  tags: [container, shell, T1059]

The rule uses Falco's built-in macros. The stock rule, "Terminal shell in container", adds conditions for an interactive terminal and the container's entrypoint. Falco's rule text suggests correlating such alerts with audit exec events to find the user or token behind them.

Blocking has edges. Tetragon notes that "sending a SIGKILL signal does not always stop the operation": a write() already under way may complete, so combine the signal with an Override action. Start any enforcing tool in an audit mode first. Also, Falco 0.44 (May 2026) removed the legacy eBPF probe and the gVisor engine, so older install guides may no longer work.

What a service mesh adds

Topic 5.2Identity, encryption and authorization between services.

The CNCF whitepaper: "organizations should implement a service mesh to eliminate implicit trust within and across workloads, achieved through data-in-motion encryption. Utilization of a service mesh also resolves identity issues where traditional static identities, like IP addresses, no longer cleanly map to workloads." A mesh puts a proxy in the path of every call (a sidecar per Pod, or per-node proxies) and adds:

  • Mutual TLS: both sides present certificates, so traffic is encrypted and each side knows who the other is.
  • Workload identity taken from the Pod's ServiceAccount, written as a SPIFFE ID such as spiffe://cluster.local/ns/shop/sa/web.
  • Authorization on that identity, and at layer 7 on methods, paths and JWT claims.
  • Telemetry on who called whom, plus traffic policy such as egress control.

SPIFFE and its reference implementation SPIRE (both CNCF graduated, 2022) standardize these identities. NIST SP 800-207A (2023) describes the same model: zero trust for cloud native apps moves from "security controls based on segmentation and isolation using network parameters ... to identities", using "sidecar proxies, and application identity infrastructures (e.g., SPIFFE)".

Istio security policies

Topic 5.2Requiring mTLS and authorizing calls by identity in Istio.

Istio (CNCF graduated, 2023) gives every workload an X.509 certificate signed by its control plane, istiod, and rotates it automatically. Its policies use security.istio.io/v1 (v1 since Istio 1.22).

Require mTLS into every shop Pod (PeerAuthentication) 
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: shop
spec:
  mtls:
    mode: STRICT

Istio starts in PERMISSIVE mode. "Mesh-wide peer authentication policies with an unset mode use the PERMISSIVE mode by default": each workload accepts both mTLS and plaintext, which "weakens the security stance". Apply STRICT per namespace, or mesh-wide in the root namespace (usually istio-system). And "Mutual TLS alone is not always enough ... it provides only authentication, not authorization. This means that anyone with a valid certificate can still access a service."

Deny everything in shop by default (AuthorizationPolicy) 
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-nothing
  namespace: shop
# ALLOW with no rules never matches
spec: {}
Only web may GET /api/* on the api Pods (AuthorizationPolicy) 
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: api-allow-web
  namespace: shop
spec:
  selector:
    matchLabels:
      app: api
  action: ALLOW
  rules:
  - from:
    - source:
        # no spiffe:// prefix here
        principals:
        - cluster.local/ns/shop/sa/web
    to:
    - operation:
        methods: ["GET"]
        paths: ["/api/*"]

How Istio decides, in its own words: "the CUSTOM action is evaluated first, then the DENY action, and finally the ALLOW action". If no ALLOW policies apply to a workload, the request is allowed; if any do, the request needs to match one. AUDIT policies never allow or deny anything. A RequestAuthentication validates end-user JWTs, but "When requests carry no token, they are accepted by default", so pair it with an AuthorizationPolicy that requires requestPrincipals.

Two Istio identity traps. principals are written as cluster.local/ns/<ns>/sa/<sa>, without the spiffe:// that appears in the certificate. And identity fields such as principals and namespaces "will never match when the traffic is plain text", so in PERMISSIVE mode a request might be "allowed unexpectedly". Istio strongly recommends using them only with STRICT mTLS.

Ambient mode, Linkerd and others

Topic 5.2Sidecarless Istio, Linkerd's defaults and policy objects, and other options.

Istio's ambient mode (GA in Istio 1.24, November 2024) replaces sidecars with a per-node proxy, ztunnel, for layer 4 mTLS and authorization, plus optional waypoint proxies for layer 7. Namespaces opt in with the label istio.io/dataplane-mode=ambient.

ztunnel ignores layer 7 rules. "A DENY policy whose rules contain only L7 attributes, such as notRequestPrincipals, paths or methods, is not enforced by ztunnel and does not block any traffic." (An ALLOW policy with L7 attributes fails closed instead: traffic is denied.) For layer 7 rules, deploy a waypoint and attach the policy to it with targetRefs; waypoints ignore selector policies.

Linkerd

Linkerd (CNCF graduated, 2021, the first mesh to graduate) "automatically enables mutually-authenticated Transport Layer Security (mTLS) for all TCP traffic between meshed pods". Proxy certificates are tied to the ServiceAccount and "expire after 24 hours and are automatically rotated". But encryption isn't authorization: the default inbound policy is all-unauthenticated, which allows all traffic. Policies use policy.linkerd.io: a Server defines a port, and once a Server exists, traffic to it "will be denied unless explicitly authorized".

Only the web ServiceAccount may call api (Linkerd) 
apiVersion: policy.linkerd.io/v1alpha1
kind: MeshTLSAuthentication
metadata:
  name: web-only
  namespace: shop
spec:
  identityRefs:
  - kind: ServiceAccount
    name: web
---
apiVersion: policy.linkerd.io/v1alpha1
kind: AuthorizationPolicy
metadata:
  name: api-from-web
  namespace: shop
spec:
  # a Server for the api port
  targetRef:
    group: policy.linkerd.io
    kind: Server
    name: api-http
  requiredAuthenticationRefs:
  - group: policy.linkerd.io
    kind: MeshTLSAuthentication
    name: web-only
  • Cilium offers a sidecarless mesh with per-node Envoy. Its mutual authentication (with SPIRE) is still beta and doesn't encrypt on its own, and its ztunnel-based encryption is beta too.
  • cert-manager's istio-csr lets an external CA, through cert-manager, sign mesh certificates instead of istiod.
  • Gateway API's GAMMA work lets mesh routes use the same Route objects as ingress; authorization still uses each mesh's own policy objects.

Mesh project changes. Since February 2024 the Linkerd open source project has published only edge releases ("the vendor community around Linkerd is responsible for creating stable release artifacts"); 2.20 corresponds to edge-26.6.3. Its AuthorizationPolicy and MeshTLSAuthentication are still v1alpha1, and ServerAuthorization is being phased out. Open Service Mesh and the Service Mesh Interface (SMI) were archived in 2023.

Limits of a mesh

Topic 5.2What a mesh doesn't protect, and how it complements NetworkPolicy.

  • Pods outside the mesh: Pods with hostNetwork are never injected, Pods can opt out with sidecar.istio.io/inject: "false", and Pods created before a namespace was labelled have no sidecar until they restart.
  • A sidecar can't protect its own Pod: Istio notes "there is minimal security boundary between an application and its sidecar proxy". A compromised app can remove the traffic redirection. Only TCP is captured.
  • Egress: Istio's default outbound policy is ALLOW_ANY. REGISTRY_ONLY "is not a strong security boundary ... should be considered best-effort". Use an egress gateway together with NetworkPolicy.
  • The control plane: istiod signs every workload certificate and pushes all configuration, so compromising it means minting any identity. Lock down its debug and plaintext ports, and keep it patched: Istio published eight security bulletins in 2026 alone.
  • Privileges: the sidecar's init container needs NET_ADMIN and NET_RAW in every Pod, which conflicts with Pod Security. The istio-cni (or Linkerd CNI) node agent moves that into one privileged DaemonSet per node; ambient mode requires it.

Use both: Istio says its policies "can be layered with Kubernetes Network Policies" for defense in depth, and the CNCF whitepaper lists "orchestrator network policies as well as use of a service mesh" as parts of "a comprehensive zero trust solution" (topic 3.4).

Key takeaways

  • Security signals: audit log, app and node logs, metrics, traces, Events (1 hour), runtime events, mesh telemetry. Forward them off-cluster to a store cluster credentials can't reach; protect their integrity (authenticated time, tamper-proof logs).
  • Protect the pipeline: logging agents are high-value; /metrics "may expose sensitive information"; scrapers need nodes/metrics, not nodes/proxy; Prometheus assumes untrusted readers (no secrets in labels; TLS and basic auth only since 2.24); OTel Collector on localhost (default since v0.110.0), minimal components, redaction and attributes processors.
  • Runtime tools: Falco detects (graduated; modern eBPF default); Tetragon (Cilium) and KubeArmor (sandbox) can block; Tracee isn't CNCF. Blocking has edges: pair SIGKILL with Override, audit first.
  • A mesh adds mTLS, SPIFFE workload identities from ServiceAccounts, L7 authorization and telemetry; it removes implicit trust (SP 800-207A).
  • Istio: PERMISSIVE by default, so apply PeerAuthentication STRICT. AuthorizationPolicy: spec: {} allows nothing; order CUSTOM, DENY, ALLOW; principals without spiffe://; identity fields never match plaintext. RequestAuthentication alone accepts token-less requests.
  • Ambient: ztunnel can't enforce L7, so an L7-only DENY blocks nothing; use waypoints. Linkerd: mTLS on by default but inbound policy allows all until a Server and AuthorizationPolicy exist; edge releases only since 2024. Cilium mutual auth is beta.
  • Mesh limits: unmeshed and hostNetwork Pods, a sidecar can't protect its own Pod, egress REGISTRY_ONLY is best-effort, istiod is a crown jewel, init containers need NET_ADMIN (use CNI agents). Layer the mesh with NetworkPolicy.
