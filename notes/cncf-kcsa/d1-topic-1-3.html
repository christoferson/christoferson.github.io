Overview

Topic 1.3

Artifact Repository and Image Security. Workload and Application Code Security.

The curriculum gives only these topic names. This page takes artifact repository and image security to mean how images are named, stored, pulled and kept trustworthy: digests and tags, pull policies and credentials, registry protection, image hygiene and vulnerability scanning. It takes workload and application code security to mean securing the code and dependencies inside the image (secure coding and security testing) and the workload settings an application team controls. Signing, SBOMs, provenance and SLSA belong to supply chain security and are covered in topic 5.1.

Quotes are from kubernetes.io and the CNCF® Glossary (CC BY 4.0), NIST SP 800-190 (credited), and the docs of the tools named.

Running example. The web shop's images (web, api, worker) are built in CI and pushed to the team's private registry. The cluster pulls them into the shop namespace.

Naming images: tags and digests

Topic 1.3Why a digest is safer than a tag, and how the image name decides the pull policy.

kubernetes.io: "Digests are hashes of the image's content, and are immutable. Tags can be moved to point to different images, but digests are fixed." The CNCF Glossary's image digest entry calls a tag "a nickname" you can reassign and a digest "a fingerprint", and spells out the risk: "a compromised tag could silently deliver a malicious image."

  • A name with no registry means Docker Hub, and no tag means latest. kubernetes.io advises avoiding :latest in production because "it is harder to track which version of the image is running and more difficult to roll back properly."
  • Pinning by digest means a change at the registry can't change what you run. A reference with both a tag and a digest (web:1.4.2@sha256:...) is allowed: "Only the digest will be used for pulling."

A real case of mutable tags: Trivy, March 2026. On 19 March 2026, attackers with stolen credentials published a malicious Trivy release, v0.69.4, and repointed 76 of the 77 version tags of its GitHub Action to credential-stealing code. More malicious images followed on Docker Hub on 22 March (advisory GHSA-69fq-xp46-6x23, CVE-2026-33634). The advisory lists images referenced by digest, and Actions pinned to a full commit SHA, as not affected. Even security tools are supply chain inputs.

imagePullPolicy

The pull policy decides when the kubelet asks the runtime to pull: Always (check the registry on every container start), IfNotPresent (pull only if the image isn't on the node) or Never. If you leave it out, it's defaulted from the image name:

Image referenceDefault policy
Has a digestIfNotPresent
Tag :latestAlways
No tagAlways
Any other tagIfNotPresent

The default is set once. "The value of imagePullPolicy of the container is always set when the object is first created, and is not updated if the image's tag or digest later changes." Changing a Deployment's image to :latest later doesn't switch it to Always. And Always isn't a full download: the runtime checks the digest and fetches only missing layers.

Pulling from private registries

Topic 1.3Giving Pods registry credentials without baking them into nodes or images.

kubernetes.io lists several ways to authenticate to a private registry. Pod-level imagePullSecrets are "the recommended approach to run containers based on images in private registries". With node-level configuration, by contrast, "All Pods can read any configured private registries." The shop's pull credential:

Create the registry Secret (shell) 
kubectl create secret docker-registry \
  regcred -n shop \
  --docker-server=registry.example.com \
  --docker-username=ci-puller \
  --docker-password="$REG_TOKEN"

This creates a Secret of type kubernetes.io/dockerconfigjson. kubernetes.io warns that typing secrets on the command line "may store them in your shell history", hence the environment variable here. Attaching the Secret to the workload's ServiceAccount means every Pod created with that account gets it automatically:

ServiceAccount for the web Pods (ServiceAccount) 
apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: shop
# web never calls the Kubernetes API
automountServiceAccountToken: false
# added to every Pod using this account
imagePullSecrets:
- name: regcred
The web Pod, pinned by digest (Pod) 
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: shop
spec:
  serviceAccountName: web
  containers:
  - name: web
    # only the digest is used to pull
    image: shop/web@sha256:<digest>

A real reference includes the registry host and the 64-character hex digest. A Pod can also list imagePullSecrets directly under spec.

Pull secrets are namespaced. The Secret must be in the same namespace as the Pod. One docker-registry Secret covers one registry. Adding a pull secret to a ServiceAccount affects only Pods created afterwards. And the Secret only base64-encodes the password: anyone who can read it can decode it.

Credential provider plugins

Kubelet credential provider plugins (GA since v1.26) let the kubelet fetch short-lived registry credentials on demand from an external program, "as opposed to storing static credentials on disk". They replaced the old built-in cloud credential providers, which have been removed. Since v1.34 (beta, on by default), a plugin can receive a token for the Pod's ServiceAccount, so each workload pulls with its own identity. Plugins also cover static Pods, which can't reference Secrets or ServiceAccounts.

Cached images and credentials

Topic 1.3Stopping Pods without credentials from using private images already on a node.

Once a private image is on a node, the old behaviour with IfNotPresent let any Pod on that node use it. kubernetes.io describes the problem on the AlwaysPullImages admission plugin: "once an image has been pulled to a node, any pod from any user can use it by knowing the image's name ... without any authorization check against the image."

ControlHow it worksDefault
AlwaysPullImages admission pluginRewrites every new Pod to imagePullPolicy: Always, so every start checks the Pod's credentials with the registryNot enabled; add it with --enable-admission-plugins
Credential re-verification (KubeletEnsureSecretPulledImages)The kubelet checks that a Pod's credentials have pulled an image before letting it use the cached copy; known-good credentials are checked locally, without calling the registryBeta, on by default since v1.35 (December 2025)

AlwaysPullImages' downside is that "the pull does put the registry in the critical path of starting a container": if the registry is down, Pods can't start. That's why kubernetes.io's multi-tenancy advice says to make sure it's active when tenants have their own registries, "Otherwise, all Pods of all tenants potentially have access to all images." The kubelet feature solves the same problem with less registry traffic. It's set in the kubelet configuration:

KubeletConfiguration: image credential checks
Field
imagePullCredentialsVerificationPolicy
NeverVerify
Old behaviour: anyone on the node can use any cached image
NeverVerifyPreloadedImages
Default. Images the kubelet didn't pull itself (pre-loaded) aren't re-checked
NeverVerifyAllowlistedImages
Only images listed in preloadedImagesVerificationAllowlist skip the check
AlwaysVerify
Every image needs its credentials re-verified

The first enablement trusts everything already on the node. When the feature is first turned on, every image already cached counts as pre-pulled, so under the default policy it's never checked. Clean the nodes first if that matters. (The kubernetes.io Images page spells one value NeverVerifyAllowListedImages; the API uses a lowercase "l".)

Admission can also restrict which images run at all. The ImagePolicyWebhook admission plugin (off by default) asks an external service to approve each image, and policy engines can require approved registries, digests or signatures. Admission control is covered in topic 5.4.

Securing the registry

Topic 1.3Protecting the artifact repository that every node trusts.

NIST SP 800-190 names three registry risks, each with countermeasures:

RiskCountermeasure (paraphrased)
Insecure connectionsConnect to registries only over encrypted channels; don't use "insecure registry" settings
Stale imagesPrune vulnerable images regularly; deploy by immutable, versioned names, since latest is "not a guarantee of freshness"
Weak authentication and authorizationAuthenticate all access to private registries and every write; grant push rights per repository; audit writes; allow pushes only after scans and checks pass

Common practices built on that:

  • Use a private registry or curated internal mirror for production, rather than pulling straight from public registries. A pull-through cache also protects against upstream outages and rate limits (Docker Hub allows 100 unauthenticated pulls per 6 hours per IP address).
  • Least-privilege accounts: only CI can push; nodes and Pods get pull-only credentials.
  • Tag immutability, so a released tag can't be overwritten, plus retention rules for stale images and scanning on push.

Harbor, a CNCF graduated registry, is one example: it can scan images on push, make tags immutable and block pulls of images above a chosen severity. It's covered with other supply chain tools in topic 5.1. Other CNCF projects in this space include Distribution and Zot (registries, sandbox) and Dragonfly (peer-to-peer image distribution, graduated 2025).

k8s.gcr.io is frozen. The Kubernetes project's images moved to registry.k8s.io. The old registry was redirected from 20 March 2023 and frozen after 3 April 2023, with no new images or security updates. Manifests that still reference it run outdated images.

Building secure images

Topic 1.3Small, non-root images that carry no secrets and are rebuilt often.

The kubernetes.io Security Checklist has four image items:

  • "Minimize unnecessary content in container images."
  • "Container images are configured to be run as unprivileged user."
  • "References to container images are made by sha256 digests (rather than tags) or the provenance of the image is validated by verifying the image's digital signature at deploy time via admission control."
  • "Container images are regularly scanned during creation and in deployment, and known vulnerable software is patched."

It adds that a production image "should not contain shells or debugging utilities, as an ephemeral debug container can be used for troubleshooting." A multi-stage build onto a minimal base does all of that for the shop's Go services:

Multi-stage build onto distroless (Dockerfile) 
# syntax=docker/dockerfile:1
ARG BASE=gcr.io/distroless/static-debian13

FROM golang:1.25 AS build
WORKDIR /src
COPY go.mod go.sum ./
# secret file exists for this RUN only
RUN --mount=type=secret,id=token \
    ./scripts/fetch-deps.sh
COPY . .
RUN CGO_ENABLED=0 go build \
    -o /out/web ./cmd/web

# no shell, no package manager
FROM ${BASE}:nonroot
COPY --from=build /out/web /web
# the nonroot user, UID 65532
USER 65532:65532
# exec form: there is no shell
ENTRYPOINT ["/web"]
Build with the secret (shell) 
docker build \
  --secret id=token,src=token.txt \
  -t registry.example.com/shop/web:1.4.2 .
  • Multi-stage: compilers and build tools stay in the first stage; the final image holds only the binary.
  • Minimal base: "Distroless" images "contain only your application and its runtime dependencies. They do not contain package managers, shells or any other programs", which also "improves the signal to noise of scanners". Alternatives include scratch (empty) and other minimal distributions that are rebuilt often. Distroless is a Google project, not a CNCF one, and its current images are based on Debian 13.
  • Non-root: set USER in the image. runAsUser can override it, but the checklist notes that file permissions in the image may then stop the process from starting.
  • Rebuild often to pick up base image fixes, and keep .env files, keys and .git out of the build context with .dockerignore.

Build arguments leak secrets. Docker's docs: build arguments and environment variables "are inappropriate for passing secrets to your build" because "they persist in the final image." Deleting a copied secret in a later step doesn't help either: it's still in the earlier layer. Use a secret mount (RUN --mount=type=secret), and give Pods their secrets at run time through Kubernetes Secrets (topic 3.3). NIST SP 800-190 makes the same point: keep secrets out of images and inject them at run time.

Scanning images

Topic 1.3What scanners find and miss, where to run them, and how to rank what they report.

An image scanner lists the OS packages and language dependencies in an image and matches them against vulnerability databases. Many also flag misconfigurations, secrets and licences. Their limits:

  • They find only known, published vulnerabilities, and only in software they can identify. Binaries copied in without package metadata may be missed.
  • They say nothing about flaws in your own code logic. That's what code testing is for (below).
  • A clean scan today isn't clean tomorrow: new CVEs appear for images already in the registry or running.
WhereWhyExample
CI pipelineEarliest and cheapest fix; fail the build on policy. The checklist says scanning "is usually done as part of the deployment process in a CI/CD pipeline"trivy image --exit-code 1
RegistryScan on push and re-scan on a schedule; block pulls above a severityHarbor with its built-in Trivy scanner
Running clusterCatches images that skipped CI and CVEs disclosed after deploymentTrivy Operator, Kubescape
AdmissionRefuses images that are unscanned, unsigned or from unapproved registriesPolicy engines (topic 5.4)
Scan the web image in CI (shell) 
# default scanners: vuln and secret
trivy image shop/web:1.4.2

# only HIGH and CRITICAL findings
trivy image --severity HIGH,CRITICAL \
  shop/web:1.4.2

# fail the build on a fixable CRITICAL
trivy image --exit-code 1 \
  --severity CRITICAL --ignore-unfixed \
  shop/web:1.4.2

# misconfigurations in the manifests
trivy config ./k8s

A scan doesn't fail a pipeline by default. "By default, Trivy exits with code 0 even when security issues are detected", so without --exit-code the build passes whatever it finds. --ignore-unfixed hides vulnerabilities that have no fix yet. That cuts noise, but those risks are still there.

ToolWhat it doesOwner
TrivyScans images, file systems, repositories and clusters for vulnerabilities, misconfigurations, secrets and licencesAqua Security; not CNCF
Grype and SyftVulnerability scanner, and SBOM generatorAnchore; not CNCF
ClairAPI-based static image analysisRed Hat (Quay); not CNCF
HarborRegistry with built-in scanning (Trivy by default)CNCF, graduated
KubescapeCluster and manifest scanning against NSA/CISA, MITRE and CIS controls, plus image CVEsCNCF, incubating since January 2025
CopaceticPatches OS-package vulnerabilities in an existing image without a full rebuildCNCF, sandbox

Ranking what a scan finds

  • CVSS (now version 4.0, from FIRST) scores how severe a vulnerability is, from 0 to 10. FIRST stresses that base scores "are not risk".
  • EPSS (FIRST, version 5 since June 2026) estimates "the probability that a published CVE will be exploited in the wild" in the next 30 days.
  • VEX (Vulnerability Exploitability eXchange) is a machine-readable statement from a supplier that a product is, or isn't, affected by a CVE. Scanners can use it to drop findings for code that's present but not exploitable.

Fix first: high severity, likely to be exploited (high EPSS or on a known-exploited list), a fix available, and actually reachable in your image.

Securing application code

Topic 1.3Finding flaws in the code and its dependencies before they ship.

The CNCF Glossary's shift left entry describes "implementing tests, security, or other development practices early in the software development lifecycle rather than towards the end", because late fixes are "more difficult and expensive". Its DevSecOps entry calls this "a cultural merger of the development, operational, and security responsibilities", where "the goal is not to be a blocker".

TechniqueWhat it doesStrengths and limits
SAST (static analysis)Analyzes source or compiled code for security flaws without running itScales, runs in CI, points to the line; many false positives, weak on access control and design flaws
DAST (dynamic testing)"Black-Box" testing of a running application by sending attack payloads such as SQL injection and XSSFinds what's really exploitable; needs a running app, can't see code paths it doesn't reach
SCA (dependency scanning)Lists third-party libraries and matches them to known vulnerabilities and licencesCovers most of the code you didn't write; only known issues
FuzzingFeeds automatically generated, malformed input to find crashes and unexpected behaviourFinds unknown bugs; needs setup and run time
Secret scanningDetects committed keys and tokens in repositories and imagesCheap, best as a pre-commit hook; anything found must be rotated

The OWASP Top 10:2025 lists the most critical web application risks: A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions.

Two OWASP lists, both 2025. The OWASP Top 10 (web applications) replaced its 2021 edition, adding Software Supply Chain Failures and Mishandling of Exceptional Conditions. The separate OWASP Kubernetes Top 10 is in topic 1.2. And a secret removed from git history must still be rotated: it may already have been copied.

The Open Source Security Foundation (OpenSSF), a Linux Foundation foundation separate from the CNCF, offers the free course LFD121 "Developing Secure Software", the OpenSSF Scorecard (automated checks that score an open source project's security practices, such as pinned dependencies, fuzzing, SAST and signed releases) and the OpenSSF Best Practices Badge. Secret scanners such as gitleaks and TruffleHog aren't CNCF projects either.

Workload settings

Topic 1.3The security settings an application team controls in its own manifests.

The kubernetes.io Application Security Checklist (2024) is written for application developers; the older Security Checklist is for cluster administrators. Its main items:

  • ServiceAccounts: "Avoid using the default ServiceAccount. Instead, create ServiceAccounts for each workload". "automountServiceAccountToken should be set to false unless the pod specifically requires access to the Kubernetes API".
  • Resources: set requests and limits for an appropriate QoS class; "Memory limit is set for the workloads with a limit equal to or greater than the request". Limits contain the damage of a runaway or abused process.
  • securityContext: runAsNonRoot: true, allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, no privileged containers, drop all capabilities (topic 1.2).
  • Images: scan before deploying, and "use container signing to validate the container image signature before deploying".
  • Network: "Configure NetworkPolicies to only allow expected ingress and egress traffic from the pods."

The shop's web ServiceAccount above already turns off token automounting. If both the ServiceAccount and the Pod set automountServiceAccountToken, the Pod spec wins.

Consuming Secrets safely

The Security Checklist prefers files: "Pods needing secrets should have these automatically mounted through volumes, preferably stored in memory". It explains that "the environment variable method might be more prone to leakage due to crash dumps in logs and the non-confidential nature of environment variable in Linux". The kubelet keeps Secret volumes in tmpfs "so that the confidential data is not written to durable storage". Mount Secrets only into the containers that need them, and make sure the app never logs them.

Immutable ConfigMaps and Secrets. Setting immutable: true (GA since v1.21) protects against accidental or unwanted changes and lowers API server load. It can't be undone: "You can only delete and recreate" the object.

Key takeaways

  • Tags are mutable, digests immutable; pin production images by digest (with a tag and a digest, only the digest is used). The March 2026 Trivy compromise spared digest-pinned users.
  • Default pull policy: digest or ordinary tag = IfNotPresent; :latest or no tag = Always; fixed when the object is created.
  • Private registries: docker-registry Secrets in the Pod's namespace, referenced by imagePullSecrets on the Pod or its ServiceAccount; or kubelet credential provider plugins (GA 1.26) for short-lived credentials.
  • Cached private images: AlwaysPullImages (off by default, puts the registry on the critical path) or kubelet credential re-verification (beta, on since 1.35; default NeverVerifyPreloadedImages).
  • Registries: TLS only, authenticated pulls and pushes, push from CI only, immutable tags, pruning, scan on push. k8s.gcr.io is frozen; use registry.k8s.io.
  • Images: multi-stage, minimal or distroless, non-root USER, no shell, no secrets in layers (use --mount=type=secret), rebuilt often.
  • Scan in CI, the registry and the cluster. Trivy exits 0 without --exit-code. CVSS = severity, EPSS = likelihood of exploitation, VEX = "not affected" statements. Trivy, Grype and Clair aren't CNCF; Harbor and Kubescape are.
  • Code: SAST, DAST, SCA, fuzzing and secret scanning; OWASP Top 10:2025. Workloads: own ServiceAccount, token automount off, limits, hardened securityContext, Secrets as in-memory files rather than environment variables.
