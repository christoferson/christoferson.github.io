Overview

Topic 3.3

Secrets.

This page covers the Secret object: its types and limits, who can read it, how Pods should consume it, how it leaks, encryption at rest with a key management service, and the external tools that keep secrets out of the cluster or out of Git. Related material elsewhere: the encryption providers table (topic 1.1), secrets in images (topic 1.3), Secret volumes on nodes (topic 2.3) and ServiceAccount token Secrets (topic 3.2).

Quotes are from kubernetes.io (CC BY 4.0) and the projects named.

Running example. The shop's API needs the database password. Today it sits in a Secret called db-creds, created by hand. The team wants it encrypted in etcd, readable by the API alone, and eventually fetched from the company's secret store.

What a Secret is

Topic 3.3The object, its limits and types, and the default risk.

"A Secret is an object that contains a small amount of sensitive data such as a password, a token, or a key." It's a namespaced core object, "similar to ConfigMaps but ... specifically intended to hold confidential data." The Secrets page opens with this caution:

The default is plaintext. "Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd). Anyone with API access can retrieve or modify a Secret, and so can anyone with access to etcd. Additionally, anyone who is authorized to create a Pod in a namespace can use that access to read any Secret in that namespace; this includes indirect access such as the ability to create a Deployment." Its four steps: enable encryption at rest, least-privilege RBAC, restrict Secret access to specific containers, and consider external Secret store providers.

  • data vs stringData: data values are base64; stringData takes plain strings, is merged into data and wins on a clash. Reading the Secret back always shows data.
  • base64 isn't protection: "Base64 encoding is not an encryption method, it provides no additional confidentiality over plain text."
  • Limits: "Individual Secrets are limited to 1MiB in size", to protect API server and kubelet memory. The type can't be changed after creation. Static Pods can't use Secrets.
  • Immutable: immutable: true (GA v1.21) blocks changes and stops the kubelet watching the Secret; it can't be undone.

The convenience types only help people and tools understand the contents; the API server doesn't treat their values more securely than Opaque.

Who can read a Secret

Topic 3.3The direct and indirect routes to a Secret's value, and how to narrow them.

RouteWhy it works
get, list or watch on secrets"Granting list access to Secrets implicitly lets the subject fetch the contents of the Secrets"
Creating Pods or workloads"A user who can create a Pod that uses a Secret can also see the value of that Secret", even without any Secret permission
A privileged container"Any containers that run with privileged: true on a node can access all Secrets used on that node"
etcd or its backupsEverything is readable if encryption at rest is off
Cluster-wide controllersIngress controllers, secret syncers and CD tools often read Secrets everywhere (CVE-2025-1974 in topic 2.3)

A Pod that needs one Secret should get exactly that one:

The API may read only db-creds (Role) 
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-db-creds
  namespace: shop
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["db-creds"]
  # no list or watch
  verbs: ["get"]

Most apps don't need this at all: mounting a Secret into a Pod requires no RBAC on secrets for the Pod's ServiceAccount, because the kubelet fetches it under the Node authorizer. Grant API access only to apps that read Secrets themselves.

Good practices

The kubernetes.io Good practices for Kubernetes Secrets page, by role:

  • Cluster administrators: configure encryption at rest; for components, "Restrict watch or list access to only the most privileged, system-level components"; for humans, "Restrict get, watch, or list access to Secrets. Only allow cluster administrators to access etcd." It also recommends "Use short-lived Secrets", audit rules that alert on unusual reads (such as one user reading many Secrets at once), wiping old etcd storage, and "separate namespaces to isolate access to mounted secrets".
  • Developers: restrict Secret access to the containers that need it; "your application must avoid logging the secret data in the clear or transmitting it to an untrusted party"; and avoid sharing Secret manifests, since a checked-in manifest "means the secret is available to everyone who can read the manifest."

Using Secrets in Pods

Topic 3.3Creating Secrets without leaving traces, and mounting them safely.

Create db-creds from files, not the command line (shell) 
# files keep values out of shell history
kubectl create secret generic db-creds \
  --namespace shop \
  --from-file=username=./user.txt \
  --from-file=password=./pass.txt
# then delete the files

--from-literal=password=... works too, but it puts the password in your shell history. kubernetes.io's own pull-secret page warns of this.

Mount one key, owner-read only (Pod) 
apiVersion: v1
kind: Pod
metadata:
  name: api
  namespace: shop
spec:
  containers:
  - name: api
    image: shop/api:1.4.2
    volumeMounts:
    - name: db
      mountPath: /etc/db
      readOnly: true
  volumes:
  - name: db
    secret:
      secretName: db-creds
      # default is 0644
      defaultMode: 0400
      # only this key is projected
      items:
      - key: password
        path: password

The kubelet keeps the files in tmpfs "so that the confidential data is not written to durable storage", and "a Secret is only sent to a node if a Pod on that node requires it". Only the api container mounts it, so a sidecar in the same Pod wouldn't see it.

Consumed asSees updates?Leak risk
VolumeYes, eventuallyLower: protected by file permissions
Volume with subPathNeverLower
Environment variableOnly after a restartHigher: "crash dumps in logs and the non-confidential nature of environment variable in Linux"; inherited by child processes
Immutable SecretNever: delete and recreateSame as how it's mounted

A missing Secret can block a Pod. By default, "None of a Pod's containers will start until all non-optional Secrets are available", and a missing key in an existing Secret makes the Pod fail. With optional: true, a missing Secret is ignored, which is safer for availability but means the app must handle having no credentials.

How Secrets leak

Topic 3.3The everyday paths by which secret values escape the cluster's controls.

PathWhat happensFix
kubectl outputdescribe shows only byte counts, but get -o yaml shows the base64 valuesLimit get; never paste the output
GitA Secret manifest in a repository is plaintext to every reader, forever in historySealed Secrets, SOPS, or references to an external store

The kubernetes.io audit policy example logs Secrets and ConfigMaps at Metadata level, recording who touched what, but not the contents:

Audit rule for Secrets (audit policy excerpt) 
# who and when, not the values
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets", "configmaps"]

Audit logging is covered in topic 3.5.

Encryption at rest with KMS

Topic 3.3Envelope encryption with an external key service, and checking that it works.

Page 1.1 introduced EncryptionConfiguration and its providers. Local-key providers keep the key in a file on the control plane host, which protects etcd and its backups but "fails to protect against a host compromise". The KMS provider keeps the master key outside:

  • "The data is encrypted using a data encryption key (DEK). The DEKs are encrypted with a key encryption key (KEK) that is stored and managed in a remote KMS." An attacker "would need to compromise etcd and the third-party KMS provider".
  • The API server talks to a KMS plugin over gRPC on a local Unix socket; the plugin holds the credentials for the remote KMS.
  • KMS v2 (GA v1.29) derives single-use DEKs from a seed, so it doesn't call the KMS on every write. KEK rotation needs no API server restart, and kubernetes.io "recommends rotating the KEK at least every 90 days."
Encrypt Secrets with a KMS v2 plugin (EncryptionConfiguration) 
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  # first provider encrypts writes
  - kms:
      apiVersion: v2
      # can't be changed once set
      name: cloud-kms
      endpoint: unix:///var/run/kms.sock
      timeout: 3s
  # reads old plaintext; remove later
  - identity: {}
Re-encrypt, then check etcd directly (shell) 
# rewrite every Secret with the new key
kubectl get secrets -A -o json \
  | kubectl replace -f -

P=/etc/kubernetes/pki/etcd
etcdctl \
  --cacert=$P/ca.crt \
  --cert=$P/server.crt \
  --key=$P/server.key \
  get /registry/secrets/shop/db-creds \
  | hexdump -C | head
# encrypted values start with
# k8s:enc:kms:v2:cloud-kms:

An encrypted value starts with k8s:enc:<provider>:; a readable value means encryption isn't working. With --encryption-provider-config-automatic-reload (since v1.26), the API server picks up config changes without a restart. On a managed service you can't edit this file; the provider offers envelope encryption with its cloud KMS instead, and you manage the key's access policy and rotation.

KMS v1 is off by default. KMS v1 was deprecated in v1.28 and disabled by default from v1.29; it can be re-enabled only with the KMSv1 feature gate. Use apiVersion: v2, which also has no cachesize field. (The kubernetes.io KMS page checks etcd at /kubernetes.io/secrets/...; the default prefix is /registry.)

Order and leftovers. The first provider encrypts, so identity first means nothing is encrypted. Keep identity last only while migrating, then remove it so plaintext is no longer accepted. And existing Secrets stay plaintext until rewritten.

External secret managers

Topic 3.3Tools that fetch secrets from a dedicated store, or keep them safe in Git.

ToolHow it worksStatus
External Secrets Operator (ESO)Reads from AWS, Azure, Google, Vault and others, and "automatically injects the values into a Kubernetes Secret"CNCF sandbox since 2022; API external-secrets.io/v1
Secrets Store CSI DriverA privileged DaemonSet mounts secrets from an external store straight into Pods as a tmpfs volume; sync to a Secret is optionalKubernetes SIG Auth subproject
Sealed Secretskubeseal encrypts with the controller's public key; only the controller can decrypt, into a normal SecretBitnami; not CNCF
SOPSEncrypts the values in YAML or JSON files with a KMS, age or PGP, leaving keys readable and diffableCNCF sandbox since 2023
HashiCorp Vault, OpenBaoDedicated secret stores with dynamic credentials and audit trailsVault under BSL 1.1 since August 2023 (IBM since 2025); OpenBao is the MPL-2.0 fork under OpenSSF
Pull the DB password from the company store (ExternalSecret) 
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: db-creds
  namespace: shop
spec:
  refreshInterval: 1h
  secretStoreRef:
    kind: ClusterSecretStore
    name: corp-vault
  target:
    # the Secret ESO writes
    name: db-creds
    creationPolicy: Owner
  data:
  - secretKey: password
    remoteRef:
      key: shop/db
      property: password

A ClusterSecretStore is "a central gateway to your secret backend" for every namespace. Without conditions limiting which namespaces may use it, any namespace's ExternalSecret can pull any path the store's identity can read.

ApproachGainRemaining risk
Sync into a Secret (ESO, CSI sync, Sealed Secrets)Apps unchanged; works for env vars, pull secrets, TLSThe value is again a normal Secret: still needs encryption at rest and RBAC
Mount only (CSI driver, sidecar agent, direct API calls)No copy in etcd or the APIDepends on the store at Pod start; privileged node plugin; rotation needs the app to reload
Encrypt in Git (Sealed Secrets, SOPS)Safe to commitSolves only "Git is plaintext"; the decryption key becomes the crown jewel

The "secret zero" problem. Whatever authenticates to the external store is itself a secret. The cloud native answer is workload identity: the Pod's short-lived, audience-bound ServiceAccount token (topic 3.2) or a SPIFFE identity (topic 5.3), not a static token stored in yet another Secret.

Recent project changes. ESO paused releases from August to September 2025 for lack of maintainers, then resumed. Its v1beta1 API stopped being served in v0.17.0 (May 2025). The Secrets Store CSI Driver's automatic rotation is still alpha and off by default. HashiCorp moved Vault to the Business Source License on 10 August 2023, and OpenBao, the open fork, moved from LF Edge to OpenSSF in June 2025. None of these are CNCF graduated projects.

TLS Secrets and CVEs

Topic 3.3Certificate Secrets, and what past bugs teach about protecting Secrets.

Ingress and Gateway listeners terminate TLS using kubernetes.io/tls Secrets. An Ingress must use a Secret in its own namespace; a Gateway can use one in another namespace only if a ReferenceGrant in the Secret's namespace allows it. cert-manager (CNCF graduated, announced November 2024) issues and renews certificates from Issuers and ClusterIssuers and writes them into these Secrets. Certificates are covered in topic 5.3.

CVEWhat happened
CVE-2023-2728The mountable-secrets policy could be bypassed with ephemeral containers
CVE-2024-3177The same policy could be bypassed with envFrom
CVE-2023-2878The Secrets Store CSI Driver logged ServiceAccount tokens at higher log levels
CVE-2025-7445secrets-store-sync-controller logged tokens that could be exchanged with cloud providers for secrets
CVE-2021-25742ingress-nginx snippets let users read the controller's token and Secrets in all namespaces

kubernetes.io/enforce-mountable-secrets is deprecated. This ServiceAccount annotation limited which Secrets its Pods could mount. It was bypassed twice (the first two CVEs above) and was deprecated in v1.32. The advice now: "Use separate namespaces to isolate access to mounted secrets."

Key takeaways

  • Secrets are plaintext in etcd by default and base64 is not encryption. Limits: 1 MiB, type fixed, stringData write-only. Types include Opaque, tls (tls.crt, tls.key), dockerconfigjson, basic-auth, ssh-auth, service-account-token and bootstrap token.
  • Readers: get, list or watch on secrets; anyone who can create Pods or workloads in the namespace; privileged containers on the node; etcd and backup access; cluster-wide controllers. Use a Role with resourceNames and get only, and namespaces as the boundary.
  • Mount as volumes (tmpfs, only on nodes that need them, defaultMode and items to narrow), only into the containers that need them. Env vars leak more and never update; subPath never updates; non-optional missing Secrets block the Pod.
  • Leaks: kubectl get -o yaml, --from-literal in shell history, Git, Helm release Secrets, audit logs above Metadata, verbose component logs, ConfigMaps.
  • KMS v2 (GA 1.29): envelope encryption, DEKs wrapped by a KEK in an external KMS via a local gRPC plugin; KMS v1 off by default since 1.29. First provider encrypts; drop identity after re-encrypting; verify with etcdctl (k8s:enc:kms:v2:).
  • External: ESO (sandbox, external-secrets.io/v1) and CSI sync create normal Secrets; mount-only CSI keeps values out of etcd; Sealed Secrets and SOPS make Git safe. Solve secret zero with workload identity. Vault is BSL; OpenBao is the open fork.
  • TLS Secrets for Ingress and Gateway (ReferenceGrant across namespaces), cert-manager graduated. enforce-mountable-secrets deprecated in 1.32 after two bypasses.
