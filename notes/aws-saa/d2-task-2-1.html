Overview

Task 2.1

Design scalable and loosely coupled architectures.

A scalable system adds capacity by adding more of something rather than by replacing it with something bigger. A loosely coupled system lets one component slow down, fail or be replaced without the others noticing, because they talk through queues, events, load balancers and APIs instead of direct calls to fixed servers. The two go together: you can only scale a tier out if any copy of it can handle any request, and you can only absorb a traffic spike if something holds the work until capacity catches up. Exam questions describe a tightly coupled or fixed-size design and ask which change makes it scale, survive a failing part, or need less management.

Running example. The company's web application takes orders from its website and mobile app. On this page it grows from one tier into a scalable system: CloudFront in front, an Application Load Balancer and Auto Scaling for the web tier, ECS services on Fargate for the order and catalog APIs, an SQS queue between ordering and payment processing, SNS and EventBridge to tell other systems an order was placed, Step Functions to run fulfilment, Aurora PostgreSQL with replicas, and DynamoDB for carts and sessions.

Event-driven, microservice and multi-tier designs

Skill 2.1.1Designing event-driven, microservice, and/or multi-tier architectures based on requirements

Multi-tier architectures

Separate tiers that scale separately

A multi-tier design splits presentation, application logic and data into tiers, each in its own subnets (Task 1.2) and each scaled on its own. The classic AWS form:

  1. EdgeCloudFront caches static content and forwards dynamic requests.
  2. Web tierAn internet-facing Application Load Balancer spreads requests over an Auto Scaling group or ECS service in private subnets across several AZs.
  3. Application tierAn internal load balancer (or service discovery) in front of the business logic, again scaled out.
  4. Data tierA managed database (Aurora, RDS, DynamoDB) with replicas, and a cache in front of hot reads.

The load balancer between tiers is what makes them loosely coupled: the web tier talks to one stable name, not to individual servers that come and go.

Microservices

Small services that own their data

A microservice architecture splits the application into small services, each owning one business capability and its own data store (orders, catalog, payments), deployed and scaled independently and talking through APIs or events. Each service can use the database that suits it, which AWS calls polyglot persistence.

The most important design principle is statelessness. A stateless service keeps nothing about a client in its own memory or disk between requests, so any copy can serve any request, copies can be added or removed at any time, and Spot capacity is safe to use. Session data goes to ElastiCache (Valkey or Redis OSS) or DynamoDB, and files go to S3 or EFS. Sticky sessions on a load balancer are the workaround for stateful servers, with costs: uneven load after scaling out, and lost sessions when a server fails. The components that must stay stateful (databases, caches, queues) should be managed services.

Finding and connecting services

Services find each other through AWS Cloud Map (a service registry), ECS Service Connect (Cloud Map plus a managed proxy in each task, so code calls short names such as http://orders:8080, at no extra charge), or Amazon VPC Lattice, which connects services across many VPCs and accounts with IAM-based auth policies and no peering or transit gateway routing. AWS App Mesh reached end of support on 30 September 2026; AWS points its users to Service Connect or VPC Lattice.

Breaking up a monolith: the strangler fig pattern

AWS Prescriptive Guidance recommends migrating a monolith gradually. A proxy layer (API Gateway, or ALB path-based rules) sits in front of the monolith; one feature at a time is rebuilt as a microservice and its route switched to the new service, until the monolith can be retired. Related patterns in the same guidance include the saga (a multi-step transaction with compensating actions, often run by Step Functions), publish-subscribe, retry with backoff and circuit breaker.

Event-driven architectures

Producers, routers and consumers

In an event-driven design a producer announces that something happened ("order placed") without knowing who cares; a router (EventBridge, SNS) delivers the event to every interested consumer; consumers react independently. Adding a new consumer, such as a loyalty-points service, needs no change to the producer. Events also come from AWS itself: S3 sends an event when an object is uploaded, DynamoDB Streams records every item change, and AWS services publish state changes to EventBridge.

Event-driven systems are asynchronous: the producer doesn't wait for consumers, so a slow consumer doesn't slow the website. The trade-off is that consumers must cope with duplicates and out-of-order events (be idempotent), and failures surface in dead-letter queues rather than error responses.

APIs with Amazon API Gateway

REST, HTTP and WebSocket APIs

API Gateway gives services a managed front door with authentication, throttling and monitoring, and integrates with Lambda, HTTP backends, AWS services, and private load balancers through VPC links. It offers three API types:

  • REST APIs have the most features: API keys and usage plans for per-client throttling, response caching, request validation, AWS WAF, resource policies, private endpoints, canary deployments and response streaming. Endpoints are edge-optimized (the default), Regional or private.
  • HTTP APIs are cheaper and simpler, with native JWT authorizers, Regional endpoints only, and none of the REST-only features above.
  • WebSocket APIs keep two-way connections open (up to 2 hours) for chat, live dashboards and notifications.

An account can make 10,000 requests per second per Region across all APIs (burst 5,000) by default, and returns HTTP 429 when throttled. REST integrations time out at 29 seconds by default; since June 2024 Regional and private REST APIs can request a longer timeout, while HTTP APIs stop at 30 seconds. Payloads are limited to 10 MB.

"Charge customers by API usage", "per-client throttling with API keys", "cache API responses" or "protect the API with AWS WAF" points to a REST API. "Lowest cost and latency, JWT authorization" points to an HTTP API. "Real-time two-way messages" points to a WebSocket API.

Scaling strategies

Skill 2.1.2Determining scaling strategies for components used in an architecture design

Horizontal and vertical scaling

Out, not up

Vertical scaling (scaling up) moves to a bigger instance or database class. It's simple, but usually needs a restart, has a ceiling, and leaves a single point of failure. Horizontal scaling (scaling out) adds more instances, tasks or nodes behind a load balancer or queue. It needs a stateless design, but has no practical ceiling, survives the loss of one copy, and can shrink again when demand falls. The exam's "scalable" answer is almost always horizontal; vertical scaling appears for components that can't be spread out, such as a single relational primary database.

Load balancing

Application, Network and Gateway Load Balancers

An Application Load Balancer works at layer 7 (HTTP, HTTPS, gRPC, WebSockets). Listener rules route by path, host, header, method, query string or source IP, so one ALB can front many microservices; targets can be instances, IP addresses (containers) or Lambda functions, and weighted target groups split traffic for blue/green or canary releases. A Network Load Balancer works at layer 4 (TCP, UDP, TLS): millions of requests per second at very low latency, one static IP per AZ (or an Elastic IP), source IP preserved, and it's what fronts PrivateLink endpoint services. A Gateway Load Balancer sends traffic through third-party appliances (Task 1.2). The Classic Load Balancer is the previous generation and AWS recommends migrating off it.

Behaviours worth knowing

  • Cross-zone load balancing spreads requests evenly over all targets in all AZs. On an ALB it is always on at the load balancer (it can be turned off per target group); on an NLB it is off by default, so each AZ's share goes only to that AZ's targets.
  • Health checks remove failing targets. If all targets are unhealthy, the load balancer fails open and sends traffic to all of them.
  • Deregistration delay (connection draining, 300 seconds by default) lets in-flight requests finish before a target is removed during scale-in or deployment.
  • Sticky sessions on an ALB bind a client to one target with a cookie; they need cross-zone load balancing on, and they weaken scaling as explained above.

EC2 Auto Scaling

Groups, templates and policies

An Auto Scaling group keeps a number of instances between a minimum and maximum, spread over AZs, replaces unhealthy ones, and registers them with the load balancer. It launches from a launch template, which supports versions, several instance types, and a mix of On-Demand and Spot. Launch configurations are deprecated: accounts created on or after 1 October 2024 can't create them at all. Scaling policies decide the desired capacity:

  • Target tracking (AWS's recommended default): keep a metric at a target, such as average CPU at 50% or ALBRequestCountPerTarget at 1,000. Auto Scaling creates the alarms, scales out quickly and in gradually.
  • Step scaling: different adjustments for different sizes of alarm breach.
  • Simple scaling: one adjustment, then a cooldown (300 seconds by default). AWS recommends not using it.
  • Scheduled scaling: change capacity at known times, such as before a weekday morning peak.
  • Predictive scaling: forecasts daily and weekly patterns from history and launches capacity ahead of demand; combine it with a dynamic policy.
Keep each web instance at about 1,000 requests per target (target tracking configuration JSON for aws autoscaling put-scaling-policy) 
{
  "TargetValue": 1000.0,
  "PredefinedMetricSpecification": {
    "PredefinedMetricType": "ALBRequestCountPerTarget",
    "ResourceLabel": "app/web-alb/0123456789abcdef/targetgroup/web-tg/fedcba9876543210"
  }
}

Turn on default instance warmup so a new instance's metrics aren't counted until it's ready (AWS suggests 300 seconds if unsure). Warm pools keep pre-initialized instances stopped or hibernated, so scale-out is fast for applications that take minutes to start; instance refresh replaces instances in rolling batches after a template change; lifecycle hooks run custom actions as instances launch or terminate.

Scaling queue workers

For workers that read from SQS, AWS's guidance is to scale on backlog per instance, not on the raw queue length: divide the visible messages by the number of running instances, and target the backlog each instance can clear within the acceptable delay. For example, if a message takes 0.1 seconds and the acceptable delay is 10 seconds, the target is 100 messages per instance; 1,500 messages on 10 instances (150 each) means scaling out to 15. Target tracking with metric math computes this without a custom metric.

Target tracking on ApproximateNumberOfMessagesVisible alone keeps adding instances while the queue drains, because it ignores how many instances are already working. Use backlog per instance.

Scaling everything else

Application Auto Scaling and database scaling

Application Auto Scaling applies the same target tracking, step and scheduled policies to other services: ECS service task counts, DynamoDB provisioned capacity, Aurora replicas, Lambda provisioned concurrency, ElastiCache shards and replicas, and more. For databases: DynamoDB on-demand capacity scales instantly per request with no planning, while provisioned capacity scales with Application Auto Scaling; Aurora Auto Scaling adds and removes Aurora Replicas (up to 15); Aurora Serverless (formerly Serverless v2) scales capacity in fine steps and can now pause at 0 ACUs when idle. RDS storage can grow automatically, but RDS read replicas don't scale automatically.

Scaling reads with read replicas

When a replica is the answer

When a relational database is busy with reads, read replicas take them off the primary. RDS read replicas use the engine's asynchronous replication (RDS for MySQL allows up to 15 per source), can be in another Region, and can be promoted to a standalone database. Aurora Replicas (up to 15) share the cluster's storage, so replica lag is usually well under 100 milliseconds, and the cluster's reader endpoint spreads connections over them. Use replicas for read-heavy applications and for reporting queries that shouldn't touch the primary; the application must send reads to the replica endpoint and accept slightly stale data. Replicas are not the high-availability standby; that's Multi-AZ, covered in Task 2.2.

"Reporting queries slow down the production database" points to a read replica for the reports. "The same few queries are repeated constantly" points to a cache. "Survive the loss of the primary" points to Multi-AZ (Task 2.2).

Caching strategies

Caches at every layer

A cache keeps frequently read data closer to the user and away from the database. AWS offers one at each layer: CloudFront at the edge, the API Gateway stage cache (REST APIs, 300-second default TTL, up to 3,600), ElastiCache in front of any database, and DynamoDB Accelerator (DAX), a DynamoDB-compatible cache with microsecond reads for eventually consistent reads that needs only a client change. ElastiCache runs Valkey, Redis OSS or Memcached, as node-based clusters or in a serverless form with no capacity planning; Valkey and Redis OSS add replication, failover and data structures such as sorted sets, while Memcached is simple, multithreaded and has no replication.

Lazy loading, write-through and TTL

  • Lazy loading (cache-aside): read the cache; on a miss, read the database and write the result into the cache. Only requested data is cached and a cache failure only adds latency, but a miss costs three trips and data can go stale.
  • Write-through: update the cache whenever the database is written. Cached data is never stale, but every write costs more and the cache fills with data that may never be read.
  • Time to live (TTL): expire entries after a set time to limit staleness and clutter.

AWS recommends combining them: lazy loading plus write-through for data that must be fresh, with a TTL on everything.

Edge accelerators

CloudFront and Global Accelerator

Amazon CloudFront is AWS's content delivery network, with more than 750 points of presence plus Regional edge caches. It caches static and dynamic HTTP(S) content close to users, absorbs traffic spikes and DDoS attacks (Task 1.2) and reduces load on the origin. For an S3 origin use origin access control (OAC), which replaced the legacy origin access identity; since November 2024 VPC origins let CloudFront reach ALBs, NLBs and instances in private subnets, so the load balancer needn't be public. Small edge logic runs in CloudFront Functions (viewer events only, sub-millisecond, header and URL rewrites) or Lambda@Edge (all four events, network access, up to 30 seconds).

AWS Global Accelerator gives an application two static anycast IP addresses; users enter the AWS network at the nearest edge and reach the closest healthy Regional endpoint (ALB, NLB, EC2, Elastic IP). It caches nothing, works for any TCP or UDP traffic, and fails over between Regions in seconds without waiting for DNS. Domain 3 covers both in depth.

"Cacheable website or video content for global users" points to CloudFront. "Static IP addresses for allow-listing", "UDP or non-HTTP protocols such as gaming" or "fast Regional failover" points to Global Accelerator.

Services for loose coupling

Skill 2.1.3Determining the AWS services required to achieve loose coupling based on requirements

Queues and pub/sub: the concepts

Point-to-point and publish/subscribe

A queue is point-to-point: a producer puts a message in, one consumer takes it out, processes it and deletes it. The queue absorbs bursts, so producers never wait for consumers and consumers work at their own pace. Publish/subscribe is one-to-many: a publisher sends a message to a topic and every subscriber receives its own copy. Combining them (a topic that delivers into several queues) gives each consumer a durable buffer of its own; that's the fan-out pattern.

Amazon SQS

Standard and FIFO queues

Standard queues handle a nearly unlimited number of requests per second, deliver each message at least once, and order messages only on a best-effort basis. FIFO queues (names end in .fifo) keep strict order within each message group and process each message exactly once using a deduplication ID. A FIFO queue handles 300 API calls per second per action, or 3,000 messages per second with batches of 10; high-throughput mode raises that to tens of thousands per second in the largest Regions.

The settings that decide behaviour

  • Visibility timeout (default 30 seconds, up to 12 hours): after a consumer receives a message, it's hidden from others for this long. If the consumer doesn't delete it in time, it reappears and is processed again, so set it longer than processing takes.
  • Retention: 4 days by default, from 1 minute to 14 days.
  • Long polling (ReceiveMessageWaitTimeSeconds up to 20): waits for messages instead of returning empty responses, which cuts cost and empty receives.
  • Delay queues: hold new messages invisible for up to 15 minutes.
  • Message size: up to 1 MiB since August 2025 (it was 256 KiB). For larger payloads, store the data in S3 and send a pointer; the SQS Extended Client Library does this for you, up to 2 GB.
  • Dead-letter queue (DLQ): after a message has been received maxReceiveCount times without being deleted, SQS moves it to the DLQ for inspection instead of retrying forever. A FIFO queue's DLQ must be FIFO. A redrive task can move messages back to the source queue after the bug is fixed.
Create the payment queue with long polling and a dead-letter queue after five failed attempts (AWS CLI) 
aws sqs create-queue --queue-name payments \
    --attributes '{
      "VisibilityTimeout": "120",
      "ReceiveMessageWaitTimeSeconds": "20",
      "RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:us-east-1:111111111111:payments-dlq\",\"maxReceiveCount\":\"5\"}"
    }'

"Orders are lost when the payment service is slow or down" points to an SQS queue between ordering and payment. "Must be processed in order, exactly once" points to a FIFO queue. "Messages are processed twice" points to a visibility timeout shorter than the processing time. "Poison messages block the queue" points to a dead-letter queue.

Amazon SNS

Push to many subscribers

SNS pushes each published message to every subscription: SQS queues, Lambda functions, HTTP/S endpoints, Data Firehose, and people through email, SMS and mobile push. It doesn't store messages for later reading; failed deliveries are retried (for SQS and Lambda, for days) and can go to a subscription DLQ. Filter policies on a subscription, matched against message attributes or the message body, let each subscriber receive only the messages it cares about. FIFO topics keep order and deduplicate, and deliver only to SQS queues (FIFO or, now, standard). Message size is 256 KiB by default, and a topic can be raised to 1 MiB for SQS, Lambda and Firehose subscribers.

Filter policy: the fraud-check subscription only receives orders of US$500 or more (JSON) 
{
  "event": ["order_placed"],
  "total_usd": [{ "numeric": [">=", 500] }]
}

"One event must be processed by several independent systems, each at its own pace" points to SNS fan-out to SQS queues. "Each subscriber only wants some of the messages" points to SNS filter policies.

Amazon EventBridge

An event router

EventBridge receives events from your applications, from AWS services (every service sends state changes to the default event bus) and from SaaS partners, and routes them by their content. On the familiar rules-based bus, a rule matches an event pattern and sends matching events to up to five targets, such as Lambda, Step Functions, SQS, another bus in another account or Region, or any HTTP API through an API destination. Events can be archived and replayed, and the schema registry documents event formats.

Event pattern: send a message whenever an EC2 instance is terminated (JSON) 
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": { "state": ["terminated"] }
}

Two related features: EventBridge Pipes connects one source (SQS, Kinesis, DynamoDB Streams, Kafka) to one target with optional filtering and enrichment, without glue code; EventBridge Scheduler runs millions of one-time or recurring schedules against hundreds of AWS APIs, and AWS recommends it over scheduled rules.

Two kinds of custom bus. The EventBridge documentation now offers a new Custom Event Bus (subscribers with one target each, built-in retention of 1 to 365 days, ordered delivery within an event group, replay) alongside the rules-based bus, now called Custom Event Bus – Classic, and recommends the new one for new applications. The exam guide predates this; questions describe the rules-and-targets model.

Amazon MQ

For existing message brokers

Amazon MQ is a managed Apache ActiveMQ or RabbitMQ broker. It speaks the industry protocols and APIs existing applications already use (JMS, AMQP, MQTT, STOMP, OpenWire), so an on-premises application can move without rewriting its messaging code. It runs on broker instances (active/standby across two AZs for ActiveMQ, a three-node cluster for RabbitMQ), so it doesn't scale like SQS and SNS.

"Migrate an application that uses JMS or AMQP with minimal code changes" points to Amazon MQ. "New cloud-native application, near-unlimited scale" points to SQS and SNS.

Workflow orchestration with Step Functions

A state machine instead of glue code

AWS Step Functions runs workflows defined as state machines: tasks, choices, parallel branches, waits and maps over items, calling Lambda and more than 200 AWS services directly. Retries, error handling and state are part of the definition rather than code you write, and each run's progress is visible. In the running example, fulfilment reserves stock, charges the card, books a courier, and on a failure refunds the payment, a saga with compensating steps.

Standard workflows run for up to a year, execute each step exactly once, are priced per state transition, and support waiting for a job to finish (.sync) and waiting for a callback with a task token (.waitForTaskToken, for example a human approval). Express workflows run for up to 5 minutes at very high rates, are priced by executions and duration, run at least once (asynchronous) or at most once (synchronous, which suits being called behind API Gateway), and support neither .sync nor callbacks. Inputs and outputs are limited to 256 KiB, so large data travels as S3 pointers.

One task in the fulfilment state machine: charge the card, retry throttling with backoff, and run the refund branch on any other error (Amazon States Language JSON fragment) 
"ChargeCard": {
  "Type": "Task",
  "QueryLanguage": "JSONata",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Arguments": { "FunctionName": "charge-card", "Payload": "{% $states.input %}" },
  "Retry": [
    { "ErrorEquals": ["Lambda.TooManyRequestsException"], "IntervalSeconds": 2, "BackoffRate": 2.0, "MaxAttempts": 3 }
  ],
  "Catch": [
    { "ErrorEquals": ["States.ALL"], "Next": "RefundPayment" }
  ],
  "Next": "BookCourier"
}

This state uses JSONata (added in November 2024) for its arguments; without the QueryLanguage field, the older JSONPath style is the default. For data pipelines written as Apache Airflow DAGs, Amazon MWAA (managed Airflow) is the alternative.

"Coordinate several steps with retries, branching and human approval", "long-running business process" points to Step Functions Standard. "High-volume, short event processing" points to Express.

Kinesis Data Streams is not a drop-in for SQS: it keeps an ordered stream per shard that several consumers can read and replay, while SQS deletes each message once it's processed. "Many applications must read the same real-time stream" points to Kinesis (Domain 3); "a work queue" points to SQS.

When to use containers

Skill 2.1.4Determining when to use containers

Why containers

Where they fit

A container packages an application with its dependencies into an image that runs the same way everywhere. Containers fit long-running services and APIs, applications already built as Docker images, jobs that run longer than Lambda's 15 minutes, workloads that need a specific runtime or sidecars, and teams that want portability between environments. They start in seconds and pack densely, so many microservices can share capacity.

Orchestration: Amazon ECS or Amazon EKS

Choosing the orchestrator

Amazon ECS is AWS's own orchestrator: simpler, deeply integrated with IAM, load balancers, CloudWatch and Service Connect, with no control plane to upgrade. Amazon EKS runs upstream Kubernetes: choose it when the team already uses Kubernetes, wants its tooling and ecosystem, or needs the same platform on premises and in other clouds, accepting regular Kubernetes version upgrades. EKS Auto Mode (December 2024) has AWS manage the nodes, scaling, load balancing, storage and networking add-ons. Both pull images from Amazon ECR, a managed registry with image scanning and cross-Region replication.

"Already running Kubernetes on premises" or "open-source portability" points to EKS. "Least operational overhead to run containers on AWS" points to ECS on Fargate.

Capacity: EC2, Fargate or Managed Instances

Who runs the servers

  • AWS Fargate runs each task (or EKS pod) in its own isolated environment with no servers to manage, billed per task for the vCPU and memory requested. Tasks range from 0.25 vCPU up to 32 vCPU and 244 GB of memory. No GPUs, no privileged containers, and every task gets its own network interface. Fargate Spot runs interruptible tasks at a discount.
  • EC2 capacity (an Auto Scaling group as a capacity provider) gives full control of the instances (AMI, instance type, GPUs, daemons) and bin-packs many tasks per instance, but you patch and scale the instances.
  • ECS Managed Instances (2025) is in between: AWS provisions, patches and replaces EC2 instances for you, with access to the full range of instance types including GPUs, and you pay for the instances plus a management fee.
Minimal Fargate task definition for the order API (JSON); the execution role pulls the image and writes logs, the task role is what the code may call

Migrating applications into containers

From servers to images

Containerizing an existing application means writing a Dockerfile for it, building the image into ECR, externalizing its configuration and state (environment variables, Secrets Manager, S3 or EFS instead of local disk), and defining an ECS service or Kubernetes deployment behind a load balancer. AWS App2Container automated this for Java and ASP.NET applications, analysing a running server and generating the image, task definitions and pipeline without the source code. It's the answer older questions expect, but it's no longer open to new customers (sign-up closed on 7 November 2025), and AWS points new users to AWS Transform.

Changed services. AWS App Runner, the fully managed "container to URL" service, is no longer open to new customers; AWS recommends ECS Express Mode, which creates a Fargate service with a load balancer, TLS and auto scaling from one call. App2Container and Migration Hub Refactor Spaces closed to new customers on 7 November 2025 (AWS Transform is the suggested path), and App Mesh support ended on 30 September 2026.

When to use serverless

Skill 2.1.5Determining when to use serverless technologies and patterns

What serverless means

No servers to manage, scale with demand

Serverless services have no instances to provision, patch or scale; they scale automatically (often to zero) and charge for use. The family includes AWS Lambda (functions), Fargate (containers), API Gateway, SQS, SNS, EventBridge, Step Functions, DynamoDB, Aurora Serverless, S3 and Cognito. Choose serverless for spiky or unpredictable traffic, event-driven processing, and teams that want the least operational work.

AWS Lambda

Limits that decide whether it fits

  • Runs for at most 15 minutes per invocation.
  • Memory from 128 MB to 10,240 MB, with CPU in proportion; /tmp storage up to 10 GB.
  • Payloads of 6 MB for synchronous calls (up to 200 MB streamed responses) and 1 MB for asynchronous calls.
  • 1,000 concurrent executions per Region by default (a soft quota), shared by all functions; each function can add 1,000 environments every 10 seconds.
  • Deployment as a .zip (250 MB unzipped with layers) or a container image up to 10 GB.

Reserved concurrency caps a function (and guarantees it that much of the pool), which protects a downstream database from being overwhelmed. Provisioned concurrency keeps environments initialized so there are no cold starts, at a cost, and can be scheduled with Application Auto Scaling. A function URL gives one function its own HTTPS endpoint without API Gateway.

How Lambda gets invoked

Lambda is invoked synchronously (API Gateway, ALB, function URLs, the SDK), asynchronously (S3 events, SNS, EventBridge; Lambda queues the event and retries, with an optional failure destination), or through an event source mapping that polls SQS, Kinesis, DynamoDB Streams or Kafka and invokes the function with batches. For SQS, turn on partial batch responses so one bad message doesn't send the whole batch back, and make the function idempotent because delivery is at least once.

Lambda isn't the answer for a job that runs longer than 15 minutes, needs a GPU, or holds long-lived connections. Use containers on Fargate or EC2, AWS Batch, or Step Functions to split the work into shorter steps.

New Lambda options. Since the guide was written, Lambda has added durable functions (multi-step code that can run for up to a year), Lambda Managed Instances (functions on EC2 capacity in your account), and documentation that now calls ordinary functions "Event Functions". The exam's "Lambda function" means the ordinary kind.

Serverless patterns

  • Serverless API: API Gateway, then Lambda, then DynamoDB, scaling from zero to thousands of requests per second.
  • Event processing: an S3 upload event invokes Lambda to resize the image or scan the file.
  • Buffer in front of a fragile backend: API Gateway or the web tier writes to SQS; Lambda reads with a maximum concurrency so the database is never flooded.
  • Fan-out: SNS or EventBridge sends one event to several queues or functions.
  • Orchestration: an EventBridge rule starts a Step Functions workflow that calls Lambda and other services.
  • Serverless containers: ECS on Fargate for services that don't fit Lambda's limits.

"Unpredictable traffic, pay only when used, no servers to manage" points to Lambda (with API Gateway and DynamoDB). "Database connections are exhausted by Lambda at peak" points to RDS Proxy or an SQS buffer with reserved concurrency. "Relational database that pauses when idle" points to Aurora Serverless.

Storage: object, file and block

Three ways to store data

Object storage (Amazon S3) stores whole objects with metadata, reached over HTTPS: unlimited capacity, designed for very high durability across AZs, objects up to 50 TB, ideal for uploads, static websites, backups, data lakes and anything shared over the web. File storage gives a shared, hierarchical file system that many servers mount at once. Block storage gives a raw disk to one server for a file system or database.

  • Amazon EFS: serverless NFS for Linux, shared by thousands of EC2 instances, containers and Lambda functions across AZs, growing and shrinking automatically. Not for Windows.
  • Amazon FSx: FSx for Windows File Server (SMB with Active Directory), FSx for Lustre (high-performance computing, linked to S3), FSx for NetApp ONTAP (NFS, SMB and iSCSI, for moving NetApp workloads) and FSx for OpenZFS.
  • Amazon EBS: network block volumes in one AZ, attached to one instance (io1 and io2 can Multi-Attach to up to 16 instances in the same AZ with a cluster-aware file system), kept when the instance stops, backed up by snapshots.
  • Instance store: disks physically attached to the host, very fast but lost when the instance stops or the hardware fails; for caches, scratch space and data that is replicated elsewhere.

The web tier in the running example keeps no files locally: uploads go to S3, and a few legacy jobs that need a shared POSIX directory use EFS. Since 2026, S3 Files also offers an NFS file system over an S3 bucket, built on EFS. Volume types and performance are in Domain 3.

"Shared file system for many Linux instances across AZs" points to EFS. "Windows file shares with Active Directory" points to FSx for Windows File Server. "HPC with data in S3" points to FSx for Lustre. "Lowest-latency temporary storage" points to instance store. "Store any amount of files for web access" points to S3.

Networking

Getting traffic in and between services

For HTTP(S) applications: CloudFront at the edge, an ALB for layer-7 routing. For TCP or UDP, static IPs, extreme throughput or PrivateLink: an NLB. For global static IPs and fast Regional failover: Global Accelerator. Between services: service discovery, ECS Service Connect or VPC Lattice, and PrivateLink (Task 1.2) to expose a service privately to other VPCs and accounts.

Databases

Relational or not

Choose relational (Amazon RDS for PostgreSQL, MySQL, MariaDB, SQL Server, Oracle or Db2; or Aurora, AWS's MySQL- and PostgreSQL-compatible engine with six-way replicated storage and up to 15 replicas) when data has relationships, needs joins, transactions across tables and flexible queries. Choose Amazon DynamoDB, a serverless key-value and document database with single-digit-millisecond performance at any scale, when access patterns are known in advance and the workload needs huge scale or unpredictable traffic, such as carts, sessions and user profiles. Other data shapes have purpose-built engines (Skill 2.1.7); engine performance is in Domain 3.

Purpose-built services

Skill 2.1.7Using purpose-built AWS services for workloads

Managed services instead of servers you run

Let AWS run the undifferentiated parts

Running your own message broker, FTP server or database cluster on EC2 means patching, scaling and failover work that doesn't make the product better. The exam's "least operational overhead" answer is usually the managed service that does the same job:

  • AWS Transfer Family: fully managed SFTP, FTPS, FTP and AS2 endpoints (and browser-based transfer web apps since December 2024) that store files directly in S3 or EFS. Partners keep their existing clients and host names; users can come from the service, a directory, or a custom identity provider.
  • Amazon SQS, SNS and Amazon MQ instead of self-managed queues and brokers.
  • AWS Secrets Manager instead of credentials in configuration files (Task 1.2), which also keeps compute replaceable.
  • Amazon OpenSearch Service for full-text search and log analytics, instead of a self-managed search cluster.
  • Amazon Cognito for customer sign-up and sign-in, instead of a home-grown user database.

"Partners upload files by SFTP and the data must land in S3, with no servers to manage" points to AWS Transfer Family.

Purpose-built databases

AWS's database decision guide matches each data model to an engine:

  • Relational: Aurora, RDS, and Aurora DSQL (serverless distributed SQL, active-active across Regions).
  • Key-value: DynamoDB.
  • Document: Amazon DocumentDB (MongoDB compatible).
  • Wide-column: Amazon Keyspaces (Apache Cassandra compatible).
  • Graph: Amazon Neptune (social networks, fraud detection, recommendations).
  • In-memory: ElastiCache (a cache) and Amazon MemoryDB (a durable in-memory primary database).
  • Time series: Amazon Timestream (IoT, metrics).
  • Search: OpenSearch Service. Analytics: Amazon Redshift (data warehouse).

Discontinued. Amazon QLDB, the ledger database, is no longer in AWS's database guide and its documentation has been withdrawn; AWS suggested Aurora PostgreSQL as the migration path. The AWS Snow Family is no longer available to new customers, and Snowball devices reach end of support in commercial Regions on 31 December 2026.

Key takeaways

  • Multi-tier: CloudFront, an internet-facing ALB, scaled web and app tiers in private subnets, managed data tier. Microservices own their data, stay stateless (sessions in ElastiCache or DynamoDB) and find each other through Cloud Map, Service Connect or VPC Lattice; migrate with the strangler fig pattern.
  • API Gateway: REST for API keys, usage plans, caching, WAF and private endpoints; HTTP for lower cost and JWT auth; WebSocket for two-way connections. 10,000 rps per account and Region by default; 29-second REST timeout, now raisable for Regional and private APIs.
  • Scale out, not up. ALB at layer 7 (path and host rules, weighted targets), NLB at layer 4 (static IPs, low latency). Auto Scaling with launch templates and target tracking; scheduled and predictive for known patterns; scale queue workers on backlog per instance.
  • Reads: read replicas for read-heavy and reporting load (RDS replicas don't auto scale; Aurora replicas do, up to 15); caches with lazy loading, write-through and TTL; CloudFront for cacheable content; Global Accelerator for static IPs, non-HTTP traffic and fast failover.
  • SQS buffers work (standard: at-least-once; FIFO: ordered, exactly once; visibility timeout, DLQ, 1 MiB messages, 14 days); SNS pushes to many (fan-out to SQS, filter policies); EventBridge routes AWS, SaaS and custom events by content; Amazon MQ for JMS or AMQP apps; Step Functions for workflows (Standard up to a year, Express up to 5 minutes).
  • Containers for long-running, portable services: ECS for AWS-native simplicity, EKS for Kubernetes; Fargate for no servers (up to 32 vCPU, no GPUs), EC2 or Managed Instances for control and GPUs. App Runner and App2Container are closed to new customers.
  • Serverless for spiky, event-driven work: Lambda up to 15 minutes, 10 GB memory, 1,000 concurrent executions per Region by default; reserved concurrency protects downstream systems; provisioned concurrency removes cold starts.
  • Storage: S3 for objects, EFS for shared Linux files, FSx for Windows, Lustre, ONTAP or OpenZFS, EBS for single-AZ block volumes, instance store for ephemeral speed. Use purpose-built databases and managed services such as Transfer Family over self-managed software.
