Task 4.3: Design cost-optimized database solutions

Running the data tier for less: knowing which settings drive a database bill, keeping backups only as long as they're needed, avoiding licence costs, choosing between DynamoDB, RDS, Aurora and serverless by price, using purpose-built types for time series and analytics, and migrating without paying for more than the move.

Overview

Task 4.3

Design cost-optimized database solutions.

Database costs come from more than instance hours: standby copies, storage and I/O, backups kept too long, licences, read replicas added where a cache would do, idle development databases, and old engine versions that quietly move into paid extended support. Task 3.3 chose databases for performance; this task chooses them, and their settings, for price, keeping the business's availability and recovery requirements intact.

Prices are us-east-1 on-demand rates checked in November 2026, from AWS's published price lists.

Running example. Orders in Aurora PostgreSQL; a catalog on RDS for MySQL with heavy reads; carts and sessions in DynamoDB; a legacy SQL Server database for the warehouse; development copies of each; a clickstream archive used for monthly analytics; and IoT sensor readings from the warehouses.

What drives a database bill

The knowledge list for this task includes capacity planning, replication, connections and proxies, caching, and the cost tools. Here is how each one affects the bill.

RDS: instances, copies and storage

Capacity choices

  • Instance class: a db.m7g.large costs US$0.168 per hour and a db.r7g.large US$0.239 (MySQL and PostgreSQL); Graviton classes are a few percent cheaper than their Intel equivalents; burstable db.t4g classes (from US$0.016 per hour) suit development.
  • Multi-AZ: a Multi-AZ DB instance costs about twice a Single-AZ one (US$0.337 for a db.m7g.large), and a Multi-AZ DB cluster with two readable standbys about 2.8 times. Storage is doubled too.
  • Storage: gp3 and gp2 cost the same per GB (US$0.115 per GB-month Single-AZ), and gp3 includes baseline performance, so gp3 is the default; io2 adds a charge per provisioned IOPS.
  • Read replicas are full-price instances. If the extra reads are the same queries again and again, a cache node is cheaper: a cache.r7g.large Valkey node costs US$0.1752 per hour against US$0.239 for a db.r7g.large replica, and answers in under a millisecond.
  • RDS Proxy costs US$0.015 per vCPU-hour of the database behind it (about US$22 a month for a 2-vCPU instance); pooling connections can let a smaller instance handle the same load.

Commitments

RDS Reserved Instances last 1 or 3 years: for a db.m7g.large, savings run from about 23% (1-year, no upfront) to about 47% (3-year, all upfront), and No Upfront exists only for 1-year terms. They're size-flexible within a class for MySQL, MariaDB, PostgreSQL, Db2, Oracle BYOL and Aurora, but not for SQL Server or Oracle License Included. Database Savings Plans (up to 35%, 1-year, no upfront only) cover RDS, Aurora, DynamoDB, ElastiCache for Valkey and other database services, but only generation 7 and newer instances and serverless usage, and they can't be combined with RIs on the same workload. Neither covers storage, backups or Extended Support.

Paying nothing for idle databases

An RDS instance can be stopped for up to 7 days, after which RDS starts it again automatically; while stopped you pay no instance hours but still pay for storage, backups and any public IPv4 address. Instances with read replicas (or that are replicas) can't be stopped. For development databases unused for longer, AWS's suggestion is to snapshot and delete, or schedule stop and start. Aurora Serverless can pause at 0 ACUs when idle (Skill 4.3.3).

Finding waste

Compute Optimizer right-sizes RDS and Aurora instances and storage (MySQL and PostgreSQL engines) and flags idle DynamoDB provisioned tables, ElastiCache and MemoryDB clusters and DocumentDB clusters. Cost Optimization Hub gathers these with RI and Savings Plans recommendations, and Trusted Advisor flags RDS instances with no connections for 7 days. Cost allocation tags on databases (Task 4.1) show which team owns each cost.

"Steady production database for 3 years, lowest cost" points to an RDS Reserved Instance (3-year). "Commitment that covers several database engines and services" points to a Database Savings Plan. "Repeated read queries overload the database; lowest cost" points to a cache rather than more replicas. "Development database used only in working hours" points to stopping it on a schedule (or Aurora Serverless).

A stopped RDS instance starts again by itself after 7 days, and storage keeps billing while it's stopped. For long idle periods, snapshot and delete instead.

Backup and retention policies

Skill 4.3.1Designing appropriate backup and retention policies (for example, snapshot frequency)

What backups cost

Free up to a point

RDS and Aurora give free backup storage equal to your total provisioned database storage in the Region. Beyond that, RDS backups cost US$0.095 per GB-month and Aurora backups US$0.021. Automated backups (retention 1 to 35 days, or 0 to turn them off; the console defaults to 7 days, the API to 1) are deleted with the database, while manual and final snapshots are kept until you delete them and keep billing, a common source of forgotten cost. Automated backups plus point-in-time recovery already give an RPO of about five minutes within the retention period, so frequent extra snapshots rarely improve recovery, only cost.

Keep 14 days of automated backups on the catalog database (AWS CLI) 
aws rds modify-db-instance --db-instance-identifier catalog-mysql \
    --backup-retention-period 14 --apply-immediately

Long-term retention for less

AWS Backup can't move RDS, Aurora, DocumentDB or Neptune backups to cold storage (it can for DynamoDB with advanced features, Aurora DSQL and Timestream). For data that must be kept for years, two cheaper patterns:

  • Export snapshots to S3 as Parquet (US$0.010 per GB of snapshot) and let S3 Lifecycle move them to Glacier classes (Task 4.1). The exported data can be queried with Athena or Redshift Spectrum, but it can't be restored as a database; reloading it takes Glue or DMS.
  • Keep fewer, sparser snapshots: daily for a few weeks, monthly for a year, with a backup plan that deletes the rest, rather than every snapshot forever.

DynamoDB retention

DynamoDB on-demand backups cost US$0.10 per GB-month and are kept until deleted; point-in-time recovery costs US$0.20 per GB-month with a recovery window of 1 to 35 days. Time to Live (TTL) deletes expired items within a few days at no charge, which keeps tables (and their backups) small; in global tables the replicated deletes are charged. Old data can be exported to S3 (US$0.10 per GB) before it expires.

Expire sessions automatically using the epoch-seconds attribute expires_at (AWS CLI) 
aws dynamodb update-time-to-live --table-name sessions \
    --time-to-live-specification Enabled=true,AttributeName=expires_at

"Keep database backups for 7 years for compliance, rarely accessed, lowest cost" points to exporting snapshots to S3 and archiving them to Glacier (accepting that restore means re-import), or keeping a few long-retention snapshots. "Delete old session data automatically at no cost" points to DynamoDB TTL.

Manual snapshots don't expire with the retention period and survive deletion of the database. Retention policies must cover them too, through AWS Backup lifecycles or scheduled clean-up.

Choosing an engine for cost

Skill 4.3.2Determining an appropriate database engine (for example, MySQL compared with PostgreSQL)

Licences dominate

Open-source versus commercial engines

MySQL, MariaDB and PostgreSQL carry no licence charge: a db.m6i.large runs at about US$0.17 per hour for MySQL. The same instance with SQL Server Standard Edition licence included costs about US$0.98 per hour, nearly six times as much (SQL Server Web Edition is about US$0.31). Oracle is offered licence-included only for Standard Edition 2; other editions use bring-your-own-licence (BYOL), priced like the open-source engines on AWS's side. Between MySQL and PostgreSQL, AWS's prices are the same or nearly so, so the choice is about features (Task 3.3), not cost.

Leaving commercial engines

  • Heterogeneous migration to Aurora PostgreSQL or MySQL with DMS Schema Conversion and DMS (Skill 4.3.5) removes the licence entirely.
  • Babelfish for Aurora PostgreSQL lets SQL Server applications run against Aurora PostgreSQL with few code changes.
  • For SQL Server that must stay, Web or Standard Edition instead of Enterprise, or BYOL where your licences allow, cuts the licence charge.

Aurora or RDS, and old versions

An Aurora instance costs about 15% more per hour than the same RDS class (db.r7g.large US$0.276 against US$0.239), in return for higher throughput, six-way storage and cheaper backups; it pays off when you use what it adds. Staying on an engine version past RDS standard support triggers RDS Extended Support automatically, at US$0.10 per vCPU-hour for the first two years and US$0.20 in the third, on every instance including standbys and replicas, and not discounted by RIs or Savings Plans. RDS for MySQL 8.0 entered Extended Support in August 2026, so upgrading to MySQL 8.4 avoids the charge.

"Reduce licensing costs of a SQL Server or Oracle database" points to migrating to Aurora PostgreSQL (or MySQL), or Babelfish for SQL Server applications. "Unexpected new charges on an old engine version" points to Extended Support; upgrade the major version.

Cost-effective database services

Skill 4.3.3Determining cost-effective AWS database services with appropriate use cases (for example, DynamoDB compared with Amazon RDS, serverless)

DynamoDB

On-demand or provisioned

On-demand mode costs US$0.625 per million write request units and US$0.125 per million read request units (after a 50% price cut in November 2024), with nothing to plan; AWS recommends it as the default for most workloads. Provisioned mode costs US$0.00065 per WCU-hour and US$0.00013 per RCU-hour. A WCU used fully for an hour handles 3,600 writes, which works out to about US$0.18 per million writes, so by my arithmetic provisioned capacity (with auto scaling) becomes cheaper once its average utilization is above roughly 29%; AWS publishes no official threshold. Reserved capacity on provisioned Standard-class tables in one Region saves up to 54% (1 year) or 77% (3 years). Storage costs US$0.25 per GB-month (the first 25 GB free).

Table classes

The Standard-Infrequent Access table class cuts storage to US$0.10 per GB-month but raises read and write prices by about 25%. AWS's rule: consider it when storage costs more than half of the table's throughput cost, such as an order history table read rarely. A table can change class at most twice in 30 days, and reserved capacity doesn't apply to Standard-IA tables.

Move the order history table to Standard-IA (AWS CLI) 
aws dynamodb update-table --table-name order-history \
    --table-class STANDARD_INFREQUENT_ACCESS

Aurora

Standard or I/O-Optimized

Aurora Standard charges US$0.10 per GB-month of storage and US$0.20 per million I/O requests. Aurora I/O-Optimized charges nothing for I/O, but instances cost about 30% more (db.r7g.large US$0.359 instead of US$0.276) and storage US$0.225 per GB-month. AWS's guidance is to choose I/O-Optimized when I/O makes up 25% or more of the Aurora bill (Task 3.3); Compute Optimizer recommends the switch when it pays off.

Aurora Serverless and DSQL

Aurora Serverless costs US$0.12 per ACU-hour (Standard), scaling in half-ACU steps, so a database that is busy for a few hours a day pays only for those hours. With a minimum capacity of 0 it auto-pauses after an idle period you set (5 minutes to 24 hours), paying only for storage while paused and resuming in about 15 seconds. Several things prevent pausing: an attached RDS Proxy, Global Database, binlog or logical replication, zero-ETL integrations, provisioned instances in the cluster, and any open connection. Aurora DSQL charges per million DPUs (US$8) plus US$0.33 per GB-month, with a small free tier, for serverless distributed SQL.

Let the development Aurora cluster pause after an hour without connections (AWS CLI) 
aws rds modify-db-cluster --db-cluster-identifier orders-dev \
    --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=16,SecondsUntilAutoPause=3600

Caching to shrink the database

A cache costs less than capacity

Offloading repeated reads to ElastiCache or DAX lets the database run on a smaller class or with fewer replicas. Valkey is the cheapest ElastiCache engine: nodes cost 20% less than Redis OSS or Memcached, and ElastiCache Serverless for Valkey costs 33% less (US$0.084 per GB-hour of data, with a 100 MB minimum, so it starts at a few dollars a month). Reserved nodes save up to 55%, and data tiering on r6gd nodes keeps less-used data on SSD for large datasets. Choose the caching strategy (Task 2.1) for cost too: lazy loading keeps the cache small, while write-through caches data that may never be read.

Cost-effective database types

Skill 4.3.4Determining cost-effective AWS database types (for example, time series format, columnar format)

Time series data

Data that's mostly appended and read by time

Sensor readings, metrics and events are written once, read by time range, and become less valuable as they age. Storing them in a general relational database means paying fast-storage prices for years of cold rows. Cheaper patterns:

  • Amazon Timestream for InfluxDB: a managed InfluxDB time series database, priced by instance (from US$0.12 per hour) and storage tier. Timestream for LiveAnalytics is closed to new customers.
  • Partition by time: one DynamoDB table per period, so older tables can be moved to Standard-IA or deleted cheaply, with TTL expiring individual items; or time-based partitions in PostgreSQL that can be dropped instead of deleting rows.
  • Tier history to S3: keep recent data in the database and move older data to S3 in Parquet, queried with Athena (Task 3.5).

Columnar formats for analytics

Warehouses and the lake

Analytical queries scan a few columns over many rows, which row-based transactional databases do slowly and expensively. Columnar storage reads only the needed columns, compressed:

  • Amazon Redshift Serverless: US$0.375 per RPU-hour, from a 4-RPU minimum, billed per second only while queries run; reservations save up to 45%.
  • Redshift provisioned: RA3 nodes with managed storage (US$0.024 per GB-month), and a newer Graviton-based RG node type that AWS now recommends. Clusters can be paused when unused (on-demand compute stops billing; reserved nodes don't), and include a daily free hour of concurrency scaling credit.
  • S3 plus Athena (US$5 per TB scanned) or Redshift Spectrum on Parquet files: no cluster at all for occasional queries, such as the monthly clickstream analysis.

Other purpose-built types

DocumentDB and Neptune offer serverless capacity and I/O-optimized storage options like Aurora's; Amazon Keyspaces prices like DynamoDB (but charges for TTL deletes); OpenSearch Service moves older indexes to UltraWarm and cold storage on S3-backed managed storage at a fraction of hot-storage cost.

"Store and query IoT sensor data by time, cost-effectively" points to a time series database (Timestream for InfluxDB) or time-partitioned tables with old data tiered to S3. "Occasional analytics on large historical data" points to Parquet on S3 with Athena; "frequent BI on structured data" points to Redshift (Serverless for intermittent use).

Migrating schemas and data

Skill 4.3.5Migrating database schemas and data to different locations and/or different database engines

What migration tools cost

AWS DMS options

  • Replication instances: priced per hour (dms.c5.large about US$0.12, doubled for Multi-AZ), with some storage included. Size them for the migration, and delete them afterwards.
  • DMS Serverless: about US$0.08 per DCU-hour, scaling with load, so you don't pay for an oversized instance.
  • Homogeneous data migrations (same engine, using native tools): US$0.09 per hour of migration, with no instance or storage to pay for.
  • DMS Schema Conversion is free apart from the S3 storage it uses, and the desktop AWS SCT is free to download.

Data moving into DMS is free and DMS-to-database traffic in the same AZ is free; cross-AZ, cross-Region and internet transfer are charged at normal rates, so place the replication instance in the target's AZ.

Cheaper native paths

Some moves need no DMS at all: RDS for MySQL to Aurora MySQL by migrating a snapshot, or with lower downtime by creating an Aurora read replica of the RDS instance and promoting it; engine-native replication or dump and restore for same-engine moves; and native backup and restore through S3 for SQL Server. Moving a database to another Region is cheapest as a snapshot copy or cross-Region read replica that you then promote, paying inter-Region transfer once.

"Move RDS for MySQL to Aurora MySQL with minimal downtime and cost" points to an Aurora read replica, then promote. "Oracle to Aurora PostgreSQL" points to DMS Schema Conversion plus DMS (Serverless avoids sizing an instance). "One-off copy to another Region" points to a snapshot copy or cross-Region replica.

Key takeaways

  • RDS bill drivers: instance class (Graviton slightly cheaper, db.t for development), Multi-AZ about 2x (Multi-AZ DB cluster about 2.8x), gp3 storage at gp2's price, replicas at full price (a Valkey cache node is cheaper for repeated reads), RDS Proxy US$0.015 per vCPU-hour.
  • Commitments: RDS RIs save about 23% to 47% (no 3-year No Upfront; size flexibility not for SQL Server or Oracle licence-included); Database Savings Plans up to 35%, 1 year, generation 7+ and serverless, no stacking with RIs. Neither covers storage, backups or Extended Support.
  • Idle: stop RDS up to 7 days (it restarts itself; storage still bills); snapshot and delete for longer; Aurora Serverless pauses at 0 ACU unless a proxy, replication, zero-ETL or open connections block it.
  • Backups: free up to provisioned storage; beyond, RDS US$0.095 and Aurora US$0.021 per GB-month; manual snapshots never expire; no AWS Backup cold storage for RDS or Aurora, so export snapshots to S3 Parquet (not restorable as a database) and archive; DynamoDB TTL deletes free.
  • Engines: licences dominate (SQL Server Standard licence-included costs about six times MySQL); migrate to Aurora PostgreSQL or use Babelfish to drop them; Aurora costs about 15% more per hour than RDS; upgrade before Extended Support charges start.
  • Services: DynamoDB on-demand by default (US$0.625 and US$0.125 per million writes and reads), provisioned plus reserved capacity for steady load, Standard-IA when storage exceeds half the throughput cost; Aurora I/O-Optimized at 25%+ I/O spend; Aurora Serverless US$0.12 per ACU-hour.
  • Types: time series in Timestream for InfluxDB or time-partitioned tables with history in S3; analytics in columnar Redshift (Serverless US$0.375 per RPU-hour, pause provisioned clusters) or Parquet with Athena.
  • Migration: DMS Serverless or right-sized instances deleted afterwards, homogeneous data migrations US$0.09 per hour, free Schema Conversion and SCT, Aurora read replica promotion for MySQL to Aurora, snapshot copies between Regions.
