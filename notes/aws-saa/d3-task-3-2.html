Task 3.2: Design high-performing and elastic compute solutions

Getting the compute right for speed and elasticity: separating tiers so each scales on its own, scaling on the metric that actually tracks load, choosing instance families, processors, networking and services such as AWS Batch and EMR, and sizing instances, containers and Lambda functions to the workload.

Overview

Task 3.2

Design high-performing and elastic compute solutions.

Task 2.1 introduced the compute services, queues and Auto Scaling policies. This task asks the performance questions about them: which metric should trigger scaling, which instance family and processor give the best performance for the money, what networking a tightly coupled cluster needs, which managed service runs batch or big-data jobs, and how much memory a Lambda function or container should get. Answers that are merely "bigger" are rarely right; the exam wants the option sized and shaped for the workload.

Running example. The company's web tier runs on an Auto Scaling group, the order and catalog APIs on ECS with Fargate, and image resizing on Lambda. New on this page: a nightly risk-scoring job that runs thousands of independent simulations, a clickstream pipeline processed with Spark, and an in-house physics simulation for packaging design that needs low-latency networking between nodes.

Decoupling so components scale independently

Skill 3.2.1Decoupling workloads so that components can scale independently

Each tier on its own metric

Why a buffer makes scaling work

When the web tier calls the order processor directly, both must be sized for the peak, and a slow processor makes the website slow. Put a buffer between them and each tier can follow its own load: the web tier scales on requests per target, the worker tier on the depth of its queue (backlog per instance, Task 2.1), and stream consumers on the number of shards or partitions. A burst of orders then lengthens the queue for a few minutes instead of overloading anything. The queuing concepts are the same as in Task 2.1: a queue gives point-to-point work distribution, and publish/subscribe (SNS, EventBridge) fans one event out to many independent consumers, each with its own queue and its own scaling.

Choosing the buffer

SQS, Kinesis or MSK

  • Amazon SQS for independent units of work. Standard queues accept a nearly unlimited request rate; FIFO queues handle 300 API calls per second per action (3,000 messages with batches), up to 70,000 per second in high-throughput mode in the largest Regions. Messages are up to 1 MiB.
  • Amazon Kinesis Data Streams for ordered, replayable streams that several consumers read. Each shard takes 1 MB/s or 1,000 records per second of writes and serves 2 MB/s of reads. On-demand mode scales shards automatically (up to double the previous 30-day peak, with throttling if traffic more than doubles within 15 minutes); a newer On-demand Advantage mode keeps warm throughput at a lower per-GB price for a minimum commitment; provisioned mode uses a shard count you set. Enhanced fan-out gives each consumer its own read throughput.
  • Amazon MSK for Apache Kafka applications; MSK Serverless scales without brokers to manage (200 MB/s in and 400 MB/s out per cluster).

"The order API must stay fast even when processing falls behind" points to an SQS queue with a separately scaled worker tier. "Several applications must process the same clickstream in order, and replay it" points to Kinesis Data Streams. "Existing Kafka producers and consumers" points to MSK.

Metrics and conditions for scaling

Skill 3.2.2Identifying metrics and conditions to perform scaling actions

Choosing the metric

A metric that moves with capacity

A good scaling metric rises with load and falls in proportion as capacity is added. EC2 Auto Scaling target tracking offers four predefined ones: ASGAverageCPUUtilization, ASGAverageNetworkIn, ASGAverageNetworkOut and ALBRequestCountPerTarget. Metrics that don't shrink as you add instances don't work: the load balancer's total RequestCount, its latency, and the raw SQS queue length (use backlog per instance instead, computed with metric math). Choose the metric that represents the real bottleneck: request count per target for a web tier, CPU for a compute-bound tier, queue backlog for workers.

Custom and faster metrics

  • EC2 doesn't report memory or disk usage by itself; install the CloudWatch agent to publish them and scale on them as custom metrics.
  • Basic monitoring sends EC2 metrics every 5 minutes for free; detailed monitoring sends them every minute (charged), and AWS strongly recommends it for scaling. Launch templates use basic monitoring unless you enable it.
  • Target tracking can use high-resolution custom metrics down to 10-second periods, and ECS has 20-second predefined CPU and memory metrics, for workloads that change within a minute.

Conditions around a scaling action

  • Instance warmup: a new instance's metrics are ignored until it's ready, so a scale-out doesn't trigger another one.
  • Health check grace period: how long Auto Scaling waits before trusting a new instance's health checks; 300 seconds by default in the console but 0 from the CLI and SDKs.
  • Scale in only when all agree: with several target tracking policies, the group scales out if any policy asks and scales in only if all do.
  • Predictive scaling pairs a load metric with a scaling metric (for example ALBRequestCount with CPU), needs at least 24 hours of history, can start in forecast-only mode, and launches capacity ahead of the forecast with a scheduling buffer.

Metrics for other services

Application Auto Scaling metrics

Application Auto Scaling has predefined metrics for each service it scales:

  • ECS services: ECSServiceAverageCPUUtilization, ECSServiceAverageMemoryUtilization, or ALBRequestCountPerTarget.
  • DynamoDB provisioned tables and indexes: read and write capacity utilization.
  • Aurora Replicas: average reader CPU or connections.
  • Lambda provisioned concurrency: LambdaProvisionedConcurrencyUtilization.
  • ElastiCache: engine CPU or memory used.
Keep the order API's ECS tasks at about 60% average CPU (target tracking configuration JSON for aws application-autoscaling put-scaling-policy) 
{
  "TargetValue": 60.0,
  "PredefinedMetricSpecification": {
    "PredefinedMetricType": "ECSServiceAverageCPUUtilization"
  },
  "ScaleOutCooldown": 60,
  "ScaleInCooldown": 300
}

Scaling the capacity under containers

On Fargate there are no instances to scale. On EC2 capacity, ECS cluster auto scaling uses a capacity provider's targetCapacity: 100% means no spare instances (new tasks wait in PENDING while instances launch), and a lower value keeps headroom for faster task starts. On EKS, the Cluster Autoscaler resizes node groups, while Karpenter launches right-sized instances directly from pending pods' requirements and consolidates them afterwards; EKS Auto Mode runs Karpenter for you.

AWS Auto Scaling and scaling plans

AWS Auto Scaling scaling plans configure scaling for several resources at once (Auto Scaling groups, ECS services, DynamoDB tables, Aurora replicas, Spot Fleets), discovered by tag or CloudFormation stack. They're still documented, but if you use them only for predictive scaling AWS strongly recommends predictive scaling policies set directly on each resource instead, and publishes a migration guide.

"Instances are added while the first ones are still starting, overshooting demand" points to setting an instance warmup (and a health check grace period), not to a longer cooldown on a simple scaling policy.

"Scale on memory usage" points to the CloudWatch agent and a custom metric. "Scale the web tier with traffic" points to ALBRequestCountPerTarget. "React within seconds to spikes" points to high-resolution metrics plus warm pools. "Traffic follows a daily pattern" points to predictive scaling.

Choosing compute options and features

Skill 3.2.3Selecting the appropriate compute options and features (for example, EC2 instance types) to meet business requirements

EC2 instance types

Reading an instance name

An instance type such as c7gn.xlarge is a series (c), a generation (7), options (gn) and a size (xlarge, or metal for bare metal). The series tells you the shape:

  • M general purpose (balanced CPU and memory): web servers, application servers, small databases.
  • C compute optimized: batch processing, media encoding, high-performance web servers, gaming servers, scientific modelling.
  • R, X, U, z memory optimized: in-memory databases and caches, real-time big-data analytics (U is high-memory up to tens of TiB; z has high CPU frequency).
  • I, D, Im, Is storage optimized: large local NVMe or HDD storage for NoSQL databases, data warehousing, distributed file systems.
  • P, G, Trn, Inf, F, VT accelerated computing: GPUs for training and graphics, Trainium for training, Inferentia for inference, FPGAs, video transcoding.
  • Hpc high-performance computing: many cores, very high network bandwidth with EFA.
  • T burstable, and Mac for macOS builds.

Option letters add attributes: g AWS Graviton, a AMD, i Intel, d local NVMe instance storage, n higher network and EBS bandwidth, b higher EBS performance, e extra memory or storage, z high frequency, and flex for flex instances. Newer generations give better performance per dollar; current ones include the eighth generation (M8g, C8g, R8g on Graviton4, M8i and C8i on Intel, M8a on AMD) and the Graviton5-based M9g, C9g and R9g.

Graviton

AWS Graviton processors are AWS's own Arm-based chips. AWS says Graviton instances cost up to 20% less than comparable x86 instances and use up to 60% less energy for the same performance; Graviton4 gives up to 30% more compute performance than Graviton3. They run Linux only, so the application and its libraries must support Arm (most interpreted languages, containers built for arm64, and managed services do). Graviton is also available for Lambda (arm64), Fargate, RDS, ElastiCache and other managed services.

Burstable and flex instances

T instances earn CPU credits while running below a baseline (for example 20% per vCPU for a small or medium, 30% for a large, 40% for xlarge and 2xlarge) and spend them to burst to full speed. T3, T3a, T4g and T8i start in unlimited mode: they can keep bursting, and if their 24-hour average exceeds the baseline you pay for surplus credits, so a T3 kept at 100% CPU costs roughly 1.5 times an equivalent M5. Watch CPUCreditBalance and CPUSurplusCreditsCharged. Flex instances (M7i-flex, C7i-flex, M8i-flex and others) are different: no credits, a 40% baseline per vCPU with the ability to run at full speed a majority of the time, at a lower price than the standard version, for workloads that don't use all their CPU all the time.

"A T3 instance is slow under constant load" or "the T3 bill keeps rising" means the workload isn't bursty. Move it to an M or C (or flex) instance; T instances suit low average use with occasional peaks.

Networking for performance

Enhanced networking, ENA Express and EFA

All current instances use enhanced networking through the Elastic Network Adapter (ENA), at no extra cost; the newest Nitro cards reach up to 400 Gbps per card, and the largest network-optimized instances 600 Gbps. Sizes with "up to" bandwidth (usually 4xlarge and smaller) have a baseline and burst for a limited time. A single network flow is limited to 5 Gbps by default, up to 10 Gbps inside a cluster placement group, and up to 25 Gbps with ENA Express (both ends enabled, same Region), which also reduces tail latency. Elastic Fabric Adapter (EFA) adds OS-bypass networking for tightly coupled HPC and machine learning (MPI and NCCL); EFA traffic stays inside one AZ and isn't routable.

Placement groups and MTU

A cluster placement group packs instances close together in one AZ for the lowest latency and highest per-flow throughput, which is what the packaging simulation needs (launch all instances at once, of one type, to avoid capacity errors). Spread and partition groups (Task 2.2) do the opposite, for resilience. Inside a VPC current instances support jumbo frames (MTU 9001), which raise throughput; traffic through an internet gateway or VPN uses 1500, and inter-Region VPC peering now allows 8500.

"Tightly coupled HPC with low-latency node-to-node communication" points to a cluster placement group with EFA on Hpc or network-optimized instances. "Highest throughput for one TCP connection between two instances" points to ENA Express (or a cluster placement group).

Spot and reserved capacity

Designing for Spot

Spot Instances use spare capacity at a large discount (pricing is in Domain 4) but can be interrupted with a two-minute notice, usually preceded by a rebalance recommendation. Design for it: workloads that can stop and resume, many instance types and AZs, and a mixed instances policy on the Auto Scaling group with an On-Demand base and the price-capacity-optimized allocation strategy (AWS's recommended default). Capacity Rebalancing launches a replacement when an instance is at risk, before it's interrupted. Attribute-based instance type selection lets the group pick any instance type that matches vCPU and memory ranges, including new generations as they appear.

Web tier: two On-Demand instances always, then 70% Spot across any instance with 2 to 8 vCPUs and 4 to 32 GiB (MixedInstancesPolicy JSON for create-auto-scaling-group) 
{
  "LaunchTemplate": {
    "LaunchTemplateSpecification": { "LaunchTemplateName": "web-prod", "Version": "$Latest" },
    "Overrides": [
      {
        "InstanceRequirements": {
          "VCpuCount": { "Min": 2, "Max": 8 },
          "MemoryMiB": { "Min": 4096, "Max": 32768 }
        }
      }
    ]
  },
  "InstancesDistribution": {
    "OnDemandBaseCapacity": 2,
    "OnDemandPercentageAboveBaseCapacity": 30,
    "SpotAllocationStrategy": "price-capacity-optimized"
  }
}

On-Demand Capacity Reservations guarantee capacity in an AZ (including inside a cluster placement group) for as long as needed, billed whether used or not; Capacity Blocks for ML reserve GPU or Trainium instances for a future period of days or weeks.

Compute services for specific jobs

AWS Batch

AWS Batch runs containerized batch jobs at any scale without a scheduler or cluster to manage: you submit jobs to a job queue, and Batch scales a compute environment of Fargate, EC2 or Spot capacity (or ECS Managed Instances, or EKS) to run them. Array jobs run up to 10,000 copies of one job with an index each, ideal for the nightly risk simulations; multi-node parallel jobs run one job across several instances for MPI-style work (not on Spot); fair-share scheduling divides capacity between teams. AWS recommends Fargate for most Batch jobs (they start in about 30 seconds); use EC2 for GPUs, more than 32 vCPUs or 244 GiB, or custom AMIs.

Submit the nightly risk simulation as 1,000 parallel child jobs (AWS CLI) 
aws batch submit-job --job-name risk-sim-2026-11-09 \
    --job-queue risk-spot-queue --job-definition risk-sim:7 \
    --array-properties size=1000

Amazon EMR

Amazon EMR runs open-source big-data frameworks such as Apache Spark, Hive, Flink, HBase, Presto and Trino. On EMR on EC2 a cluster has a primary node (three for high availability), core nodes that store HDFS data and run tasks, and task nodes that only compute, so task nodes are the safe place for Spot. Instance fleets mix up to 30 instance types and On-Demand and Spot targets per node type; managed scaling resizes the cluster for YARN applications such as Spark and Hive (not Presto or HBase). EMR Serverless runs Spark and Hive jobs with no cluster, scaling workers per job, with pre-initialized capacity for fast starts; EMR on EKS runs Spark on an existing EKS cluster. Glue (serverless Spark ETL) and Athena (serverless SQL on S3) are the lighter alternatives.

"Thousands of independent jobs, queued and scheduled, no cluster to manage" points to AWS Batch. "Run existing Spark or Hadoop jobs with control over the cluster" points to EMR, with Spot on task nodes; "Spark without managing clusters" points to EMR Serverless. "Short event-driven functions" points to Lambda.

Simpler and managed platforms

Amazon Lightsail offers virtual servers, containers, databases and load balancers at a low, predictable monthly price for simple applications. AWS Elastic Beanstalk deploys web applications onto EC2 (and, since September 2026, a shared EKS cluster in its new Cluster Mode) and manages capacity, load balancing and scaling for you; its remaining Amazon Linux 2 platforms were retired in August 2026. AWS ParallelCluster and AWS Parallel Computing Service (managed Slurm) build HPC clusters.

Choosing resource type and size

Skill 3.2.4Selecting the appropriate resource type and size (for example, the amount of Lambda memory) to meet business requirements

Lambda memory

Memory is the performance dial

A Lambda function's memory setting, from 128 MB (the default) to 10,240 MB in 1 MB steps, also sets its CPU and network share: at 1,769 MB a function gets the equivalent of one full vCPU, and more memory gives more. AWS calls memory "the principal lever" for performance. Because Lambda bills by duration times memory, raising memory often lowers cost for CPU-bound functions, since they finish much faster. Each execution environment also has about 625 Mbps of network bandwidth.

To find the best setting, run AWS Lambda Power Tuning (an open-source Step Functions tool that invokes the function at several memory sizes and charts speed against cost) or read Compute Optimizer's memory recommendations. Other levers: the arm64 (Graviton) architecture, which AWS says gives significantly better price and performance; up to 10 GB of /tmp storage; and a timeout matched to the real run time.

Give the image-resize function more memory (and so more CPU) and a 60-second timeout (AWS CLI) 
aws lambda update-function-configuration --function-name resize-image \
    --memory-size 2048 --timeout 60

The architecture is set with the code, for example aws lambda update-function-code --function-name resize-image --architectures arm64 --zip-file fileb://resize-arm64.zip, because native dependencies must be built for Arm.

Cold starts and steady load

A cold start happens when Lambda creates a new execution environment. SnapStart (Java 11+, Python 3.12+ and .NET 8+) restores a snapshot of an initialized environment to cut start-up time, on published versions; provisioned concurrency keeps environments initialized for consistent low latency, at a cost. For steady, high-volume traffic, Lambda Managed Instances (November 2025) run functions on EC2 instances in your account, several requests per environment and no cold starts, priced at the EC2 rate plus a 15% management fee; they don't scale to zero.

"A CPU-heavy Lambda function is slow" points to more memory (which adds CPU), not a longer timeout. "Find the most cost-effective memory size" points to Lambda Power Tuning or Compute Optimizer. "Java function with slow start-up" points to SnapStart.

Containers and instances

Fargate task sizes

Fargate tasks come in fixed CPU and memory combinations: 0.25 vCPU with 0.5 to 2 GB, 1 vCPU with 2 to 8 GB, 4 vCPU with 8 to 30 GB, 16 vCPU with 32 to 120 GB, and 32 vCPU with exactly 60, 120 or 244 GB. Pick the smallest combination that fits the container's measured use, scale out with more tasks rather than larger ones, and consider ARM64 tasks, which the Fargate FAQ says give up to 40% better price performance than comparable x86 tasks. Ephemeral storage is 20 GiB by default, up to 200 GiB.

Right-sizing with Compute Optimizer

AWS Compute Optimizer analyses utilization (14 days by default, up to 93 days with paid enhanced infrastructure metrics) and recommends instance types for EC2 and Auto Scaling groups, volume types for EBS, memory for Lambda, CPU and memory for ECS services on Fargate, and now also database and cache sizes, and it flags idle resources. It must be opted in, and memory-based EC2 recommendations need the CloudWatch agent.

Sizing for the peak with one large instance is the vertical-scaling trap: it costs money all day and still has a ceiling. Size each instance or task for typical load, and let Auto Scaling add copies for the peak.

Key takeaways

  • Decouple tiers with SQS (work queues, 1 MiB messages), Kinesis Data Streams (ordered, replayable; 1 MB/s writes per shard; on-demand or provisioned) or MSK (Kafka), and scale each tier on its own metric.
  • Scaling metrics must move with capacity: CPU, network, ALBRequestCountPerTarget, or backlog per instance; not total RequestCount, latency or raw queue length. Memory needs the CloudWatch agent; use detailed monitoring and, for fast changes, 10-second high-resolution metrics. Set instance warmup and a health check grace period (300 s console, 0 CLI).
  • Application Auto Scaling metrics: ECS CPU, memory or requests; DynamoDB capacity utilization; Aurora reader CPU or connections; Lambda provisioned concurrency utilization. ECS capacity provider targetCapacity below 100% keeps headroom; Karpenter right-sizes EKS nodes.
  • Instance names: series (M, C, R, X, I, D, P, G, Trn, Inf, Hpc, T) plus generation plus options (g Graviton, a AMD, i Intel, d local NVMe, n network, e extra, flex). Graviton costs up to 20% less (Linux only). T3 and T4g default to unlimited credits; flex instances have no credits.
  • Networking: ENA everywhere; one flow 5 Gbps (10 in a cluster placement group, 25 with ENA Express); EFA for MPI and NCCL inside one AZ; cluster placement groups and jumbo frames (MTU 9001) for tightly coupled jobs.
  • Spot: diversify instance types and AZs with a mixed instances policy, price-capacity-optimized allocation and Capacity Rebalancing. Capacity Reservations and Capacity Blocks guarantee capacity.
  • AWS Batch for queued jobs (array jobs up to 10,000, Fargate recommended); EMR for Spark and Hadoop (Spot on task nodes, managed scaling for YARN apps, EMR Serverless); Local Zones, Wavelength and Outposts for edge latency.
  • Lambda memory (128 MB to 10,240 MB) sets CPU too (1 vCPU at 1,769 MB); tune with Power Tuning or Compute Optimizer; arm64 for price performance; SnapStart and provisioned concurrency for cold starts. Size Fargate tasks to measured use and use Compute Optimizer for EC2, EBS, Lambda and Fargate.
