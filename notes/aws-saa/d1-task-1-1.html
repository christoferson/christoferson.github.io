Overview

Task 1.1

Design secure access to AWS resources.

Almost every SAA-C03 scenario starts with an access question, even when it looks like a storage or network question: which principal is calling, does it have long-term or temporary credentials, is the call crossing an account boundary, and is there an organization-wide rule that blocks it no matter what the local policy says. The exam rewards one habit above all: people sign in through federation, workloads use roles, and nobody uses long-term keys or the root user for daily work.

Running example. A company runs a customer-facing web application and a mobile API on AWS. It uses AWS Organizations with a management account, a security account, a shared-network account and separate prod, staging and dev workload accounts (the prod account is 111111111111). Engineers sign in with the company's existing workforce directory; the app runs on EC2 Auto Scaling and ECS behind an Application Load Balancer, stores uploads in S3 and data in Aurora PostgreSQL, and its primary Region is us-east-1 with disaster recovery in us-west-2. Every task page in this guide reuses it.

Foundations: shared responsibility and global infrastructure

The task's knowledge list includes two ideas that frame every access decision: what AWS secures for you, and where your resources and identities actually live.

The shared responsibility model

Security of the cloud versus security in the cloud

AWS is responsible for security of the cloud: the hardware, software, networking and facilities that run every AWS service. You are responsible for security in the cloud, and how much that covers depends on the service you choose. On Amazon EC2 you own the guest operating system (updates and security patches), everything you install, and the security group configuration. On more abstracted services such as Amazon S3 and Amazon DynamoDB, AWS runs the infrastructure, operating system and platform, and you manage your data, its classification, the encryption options and the IAM permissions.

Some controls are shared: AWS patches and configures its infrastructure while you patch and configure your guest OS, databases and applications, and each side trains its own staff. Physical and environmental controls are inherited from AWS. Access management is always yours: no service takes over deciding who may read your data.

"Who is responsible for patching the operating system" points to the customer on EC2, and to AWS on managed services where you never see the OS. "Who controls access to the data" is always the customer.

Regions, Availability Zones and partitions

Where resources and identities live

In November 2026 AWS lists 124 Availability Zones in 39 Regions, with more announced. A Region is a separate geographic area with several isolated Availability Zones; most resources are Regional or zonal, so an access design has to say which Regions are allowed.

Identity is different. IAM and AWS Organizations are global services (both are physically hosted in us-east-1), so a user, role or policy you create works in every enabled Region of the account. Regions launched before 20 March 2019 are enabled by default; later Regions are opt-in, and IAM data is only propagated to them when you enable them. Partitions (aws, aws-cn, aws-us-gov) are hard boundaries: each has its own IAM, and roles or resource policies never work across them. The AWS European Sovereign Cloud, launched in January 2026 with its first Region in Brandenburg, Germany, is likewise separate from the other AWS Regions, with its own sign-up and console.

A policy that denies every Region except us-east-1 and us-west-2 by checking aws:RequestedRegion also blocks global services unless they are exempted, because calls to IAM always evaluate as us-east-1. The Region-restriction pattern for multiple accounts is shown in Skill 1.1.4.

Root user and IAM user best practices

Skill 1.1.1Applying AWS security best practices to IAM users and root users (for example, multi-factor authentication [MFA])

The root user

What only root can do

The root user is the identity created with the account; it can do anything and IAM policies can't restrict it inside its own account. AWS keeps a short list of tasks that genuinely need it. For a standalone account these include changing the root email address or password, closing or reopening the account, restoring access when the only IAM administrator has locked themselves out, activating IAM access to the Billing console, registering as a seller in the EC2 Reserved Instance Marketplace, configuring MFA Delete on an S3 bucket, and fixing an S3 bucket policy or SQS queue policy that denies every principal. Account name, contacts and Regions don't need root.

Everything else should be done with a federated identity or a role. AWS's best practices say: protect the root user's credentials, never create root access keys, and use root only for those tasks.

MFA is now required

AWS now requires MFA on the root user of every account type (standalone, management and member accounts): if it isn't set up, the root user must register a device within 14 days of first trying to sign in to the console. Each root user and IAM user can have up to eight MFA devices of any mix, and only one is needed to sign in. AWS recommends phishing-resistant passkeys and security keys (FIDO2); authenticator apps and hardware TOTP tokens also work. Passkeys can only be registered in the console, and AWS no longer lets you enable SMS MFA for IAM users.

Centralized root access for member accounts

Since November 2024 an organization can remove root credentials from member accounts entirely. From the management account (or an IAM delegated administrator) you enable two features: root credentials management, which deletes member root passwords, access keys and signing certificates and deactivates their MFA, and privileged root actions, which open a short root session in a member account for a specific task. Accounts created through Organizations after this is enabled start with no root credentials at all, so there's nothing to steal and nothing to put MFA on.

Turn on centralized root access from the management account (AWS CLI) 
# Let IAM work with Organizations, then enable both root access features
aws organizations enable-aws-service-access --service-principal iam.amazonaws.com
aws iam enable-organizations-root-credentials-management
aws iam enable-organizations-root-sessions

# Run a privileged task in the prod account: a root session limited to one task policy
aws sts assume-root \
    --target-principal 111111111111 \
    --task-policy-arn arn=arn:aws:iam::aws:policy/root-task/S3UnlockBucketPolicy \
    --duration-seconds 900

A root session lasts at most 15 minutes, must be requested from a Regional STS endpoint, and is limited to one of five AWS managed task policies: auditing root credentials, creating a root password, deleting root credentials, unlocking an S3 bucket policy and unlocking an SQS queue policy. In the running example the security team uses it when a bucket policy in prod accidentally denies everyone.

"Remove long-term root credentials from all member accounts" or "fix a bucket policy that locks everyone out, without signing in as root" points to centralized root access and sts:AssumeRoot.

IAM users: the exception, not the rule

Temporary credentials everywhere

AWS's first two IAM best practices are "require human users to use federation with an identity provider to access AWS using temporary credentials" and "require workloads to use temporary credentials with IAM roles to access AWS". An IAM user with a password and access keys is a long-term credential that can leak and doesn't expire, so AWS keeps them for a narrow set of cases: workloads that can't use roles, third-party tools that don't support IAM Identity Center, and service-specific credentials such as CodeCommit Git credentials. Workloads running outside AWS should get temporary credentials with IAM Roles Anywhere (X.509 certificates) or OIDC federation rather than access keys.

If an IAM user does need keys, AWS's wording is to update access keys when needed (each user can have two, so you can rotate without downtime), and to remove unused users, keys and passwords. IAM Access Analyzer's unused-access findings show which ones to remove. For developers who want CLI credentials, the AWS CLI (version 2.32.0 or later) offers aws login, a browser sign-in that issues temporary credentials instead of keys.

Storing access keys on an EC2 instance, in a container image or in application code is always wrong on this exam. EC2 uses an instance profile (a role), ECS tasks use a task role, Lambda uses an execution role; the SDK picks up the temporary credentials automatically.

A flexible authorization model

Skill 1.1.2Designing a flexible authorization model that includes IAM users, groups, roles, and policies

The building blocks

Users, groups and roles

An IAM user is a long-term identity for one person or application. An IAM group is a set of users that share policies; it isn't a principal, so it can't sign in and can't be named in a resource-based policy, and groups can't contain other groups. A user can be in at most 10 groups, and a group can have at most 10 managed policies attached (neither is adjustable). An IAM role has no credentials of its own: a trusted principal assumes it and gets temporary credentials. Roles are what people, services and workloads should use.

Policy types

Identity-based policies attach to users, groups and roles and say what that identity can do. They come as AWS managed policies (maintained by AWS, broad, a good starting point), customer managed policies (yours, reusable, versioned, up to 6,144 characters) and inline policies (embedded in one identity and deleted with it). AWS's advice is to start with AWS managed policies and move toward least privilege with customer managed ones. A role can have 20 managed policies attached by default (adjustable to 25); a user 10 (adjustable to 20).

Resource-based policies attach to a resource and name who can use it (Skill 1.1.5). Permissions boundaries set the most an identity-based policy can grant a user or role. Session policies are passed when a role session is created and narrow that one session. SCPs and RCPs set the maximum for whole accounts (Skill 1.1.4). Only identity-based and resource-based policies grant anything; the rest only take away.

How AWS decides

  1. Start with denyEvery request is implicitly denied unless something allows it.
  2. Look for an explicit DenyAWS checks every applicable policy (SCPs, RCPs, resource-based, identity-based, permissions boundaries, session policies). One explicit Deny anywhere ends the evaluation with Deny.
  3. Check the organization limitsIf the account is in an organization, an RCP and an SCP must each allow the action.
  4. Check the grantsIn the same account, an Allow in either the identity-based policy or the resource-based policy is normally enough.
  5. Check the limits on the principalA permissions boundary (if set) and a session policy (for role sessions, if passed) must also allow it.

Two resource policies are exceptions to the "either one is enough" rule even inside one account: a role trust policy and a KMS key policy must explicitly allow the principal. Across accounts, the request needs an Allow on both sides: the caller's identity policy in its account and the resource policy in the resource's account.

Adding an Allow to an SCP grants nothing. If a user in a member account can't do something that their identity policy allows, look for a missing Allow or an explicit Deny at any level of the SCP hierarchy, or a permissions boundary.

Permissions boundaries for delegation

Let teams create roles without escalating

In the running example, application teams in the dev account need to create roles for their own Lambda functions. Giving them iam:CreateRole alone would let them create an administrator role. Instead, the platform team lets them create roles only if a specific boundary policy is attached, so no role they create can exceed it. They also deny editing or removing that boundary.

Allow role creation only with the team boundary attached (identity policy JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CreateRolesOnlyWithBoundary",
      "Effect": "Allow",
      "Action": ["iam:CreateRole", "iam:PutRolePermissionsBoundary", "iam:AttachRolePolicy", "iam:PutRolePolicy"],
      "Resource": "arn:aws:iam::111111111111:role/app/*",
      "Condition": {
        "StringEquals": {
          "iam:PermissionsBoundary": "arn:aws:iam::111111111111:policy/AppTeamBoundary"
        }
      }
    },
    {
      "Sid": "ProtectTheBoundaryPolicy",
      "Effect": "Deny",
      "Action": ["iam:CreatePolicyVersion", "iam:DeletePolicy", "iam:DeletePolicyVersion", "iam:SetDefaultPolicyVersion"],
      "Resource": "arn:aws:iam::111111111111:policy/AppTeamBoundary"
    },
    {
      "Sid": "NoRemovingBoundaries",
      "Effect": "Deny",
      "Action": "iam:DeleteRolePermissionsBoundary",
      "Resource": "*"
    }
  ]
}

Scaling with tags: ABAC

Attribute-based access control

Role-based access needs a new policy for every new project. Attribute-based access control (ABAC) writes one policy that compares tags: allow the action when the principal's project tag equals the resource's project tag. New projects then need tags, not policy changes. The condition keys are aws:PrincipalTag/key (tags on the role or user, or session tags passed by the identity provider), aws:ResourceTag/key and aws:RequestTag/key (tags in a create request).

One statement for every project team (identity policy JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ec2:StartInstances", "ec2:StopInstances", "ec2:RebootInstances"],
      "Resource": "arn:aws:ec2:*:111111111111:instance/*",
      "Condition": {
        "StringEquals": { "aws:ResourceTag/project": "${aws:PrincipalTag/project}" }
      }
    }
  ]
}

"Permissions should apply automatically to new projects without updating policies" or "many teams, each managing only its own resources" points to ABAC with matching principal and resource tags.

Checking the model with IAM Access Analyzer

Four jobs in one service

IAM Access Analyzer helps keep the model at least privilege. External access analyzers (free, one per Region) find resources shared outside your account or organization, such as S3 buckets, KMS keys, IAM role trust policies, Lambda functions, SQS queues and Secrets Manager secrets. Unused access analyzers (paid) find unused roles, access keys, passwords and permissions. Internal access analyzers (added in June 2025, paid per resource) show which principals inside your organization can reach critical resources such as S3 buckets, DynamoDB tables and RDS snapshots. Policy validation and generation check policies as you write them and build a least-privilege policy from CloudTrail activity.

Roles, STS and cross-account access

Skill 1.1.3Designing a role-based access control strategy (for example, AWS STS, role switching, cross-account access)

How a role works

Two policies on every role

A role has a trust policy, which says who may assume it, and one or more permissions policies, which say what the session can do. AWS Security Token Service (STS) checks the trust policy, then returns temporary credentials: an access key ID, secret key and session token that expire. The session gives up the caller's own permissions and has only the role's.

The STS operations

AssumeRole is used by IAM users and roles; sessions last 15 minutes to the role's maximum session duration (1 hour by default, configurable up to 12 hours), and the call can include MFA, session policies and session tags. AssumeRoleWithSAML and AssumeRoleWithWebIdentity exchange a SAML assertion or an OIDC token from a trusted identity provider for role credentials, with the same duration limits. GetSessionToken gives an IAM user temporary credentials for its own permissions, typically to prove MFA for the CLI (up to 36 hours for IAM users, 1 hour for root). GetFederationToken is an older way for a proxy application to issue credentials to federated users.

Using one role's credentials to assume another role is role chaining, and it caps the new session at 1 hour, whatever the role's maximum. STS accepts 600 requests per second per account per Region across its operations.

A role with a 12-hour maximum session still gives only 1 hour if it's reached by role chaining, and console role switching counts as chaining when you start from a role. If a scenario needs long sessions, the caller has to assume the target role directly.

Role switching in the console

Switch role

A signed-in user or federated role session can switch role in the console to work in another account; permissions are not combined, the user simply acts as the role. You can't switch roles while signed in as root, the console always checks the switch against the original identity, and the console can hold up to five identities at once. Roles that require an external ID can't be used from the console.

Cross-account access

The trusting and trusted accounts

In the running example, the deployment pipeline in a tooling account must update ECS services in prod (111111111111). Prod creates a role whose trust policy names the tooling account's pipeline role; the tooling account gives that pipeline role permission to call sts:AssumeRole on it. Both sides must allow it. MFA can be required for people by adding "Bool": {"aws:MultiFactorAuthPresent": "true"} to the trust policy.

Trust policy on the prod deploy role (JSON); the tooling account is 222222222222 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::222222222222:role/pipeline-deployer" },
      "Action": "sts:AssumeRole"
    }
  ]
}
Assume it from the tooling account (AWS CLI) 
# Returns temporary credentials for the prod deploy role, valid for one hour
aws sts assume-role \
    --role-arn arn:aws:iam::111111111111:role/ecs-deploy \
    --role-session-name pipeline-run-482 \
    --duration-seconds 3600

Third parties and the confused deputy

When a third-party service (a monitoring vendor, for example) assumes a role in your account, another customer of that vendor could try to trick it into using your role: the confused deputy problem. The fix is an external ID: the vendor generates a unique value for each customer, you put it in the trust policy as a condition on sts:ExternalId, and the vendor sends it with every AssumeRole call. The external ID is chosen by the vendor, not by you. When an AWS service acts on your behalf (S3 writing to an SNS topic, for example), the equivalent guard is the aws:SourceArn or aws:SourceAccount condition in the resource policy.

"Grant a third-party SaaS vendor access to our account securely" points to a cross-account role with an external ID, never to an IAM user with access keys.

Role or resource-based policy?

The difference that decides the answer

Cross-account access can also be granted with a resource-based policy on the resource itself. The difference: through a role, the caller gives up its own permissions while using the role; through a resource-based policy, the caller keeps its own permissions and works in its own account. So to copy objects from a bucket in one account to a bucket in another, a bucket policy lets one principal read the source and write the destination at the same time, which a role can't. Roles work for every service and for console access; resource-based policies only exist on services that support them (Skill 1.1.5).

Security across many accounts

Skill 1.1.4Designing a security strategy for multiple AWS accounts (for example, AWS Control Tower, service control policies [SCPs])

Why many accounts

The account is the strongest boundary

An AWS account is a hard boundary for permissions, quotas and billing: nothing in one account can reach another unless a policy explicitly allows it. Separating prod from dev, and security tooling from workloads, limits the blast radius of a mistake or a compromised credential far more reliably than policies inside one shared account. AWS Organizations groups the accounts into a tree of organizational units (OUs) under one root, gives consolidated billing, and, in "all features" mode, lets you apply organization policies.

AWS's multi-account guidance recommends a Security OU with a Log Archive account (central, protected CloudTrail, Config and VPC Flow Logs) and a Security Tooling account (also called Audit) that acts as delegated administrator for services such as GuardDuty, Security Hub CSPM, Macie, Inspector and IAM Access Analyzer; an Infrastructure OU for shared networking and identity; a Workloads OU split into prod and non-prod; and a Sandbox OU for experiments. Keep the management account nearly empty, and register member accounts as delegated administrators so people rarely need to sign in to it.

Service control policies

Guardrails for your own principals

An SCP sets the maximum permissions for IAM users and roles in member accounts, including the member account's root user. It never grants: a principal still needs an identity-based or resource-based Allow. An action is available only if it's allowed at every level from the root through each OU to the account, and an explicit Deny at any level wins. Every root, OU and account must have at least one SCP attached; by default that's FullAWSAccess, and removing it without a replacement blocks everything.

SCPs don't affect the management account, service-linked roles, or principals outside your organization calling your resources. Since September 2025 SCPs support the full IAM policy language (conditions and specific resources in Allow statements, NotResource, wildcards anywhere in action names), but still not Principal or NotPrincipal. An SCP can be up to 10,240 characters, and up to 10 can be attached directly to each root, OU or account.

Deny everything outside the two approved Regions, except global services and a break-glass role (SCP JSON, NotAction list abridged from AWS's example) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*", "organizations:*", "sts:*", "cloudfront:*", "route53:*",
        "support:*", "budgets:*", "kms:*", "waf:*", "wafv2:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["us-east-1", "us-west-2"] },
        "ArnNotLike": { "aws:PrincipalARN": "arn:aws:iam::*:role/BreakGlassAdmin" }
      }
    }
  ]
}
Attach it to the Workloads OU (AWS CLI) 
# SCPs must be enabled on the root once, then created and attached
aws organizations enable-policy-type --root-id r-abcd --policy-type SERVICE_CONTROL_POLICY
aws organizations create-policy --name DenyOtherRegions --type SERVICE_CONTROL_POLICY \
    --description "Only us-east-1 and us-west-2" --content file://deny-regions.json
aws organizations attach-policy --policy-id p-examplepolicyid --target-id ou-abcd-workloads

AWS recommends testing new SCPs on a test OU first and never attaching an untested SCP to the root.

"An SCP denies X but an administrator in the management account can still do X" isn't a bug: SCPs never apply to the management account. That's why workloads shouldn't run there.

Resource control policies and declarative policies

RCPs: guardrails for your resources

SCPs only limit your principals. A bucket policy in a member account could still grant access to someone outside the organization. Resource control policies (launched November 2024) close that gap: they set the maximum permissions on resources in member accounts, whoever is calling. Customer RCPs can only Deny, the Principal must be "*" (you narrow it with conditions), and they cover a growing list of about 60 services, including S3, KMS, SQS, Secrets Manager, STS, DynamoDB, ECR and CloudWatch Logs, but not, for example, Lambda or SNS. Up to 5 RCPs can be attached per entity, including the AWS-managed RCPFullAWSAccess that's attached automatically.

RCP: refuse any S3 request that doesn't use TLS, across every member account (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceSecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "*",
      "Condition": { "BoolIfExists": { "aws:SecureTransport": "false" } }
    }
  ]
}

Declarative policies: fix a configuration everywhere

Declarative policies (December 2024) don't evaluate API calls at all; they set a service configuration across the organization and keep it set, even when the service adds new APIs. EC2 declarative policies can enforce VPC Block Public Access, block public sharing of AMIs and EBS snapshots, limit which AMIs can be used, and set instance metadata (IMDS) defaults; an Organizations S3 policy enforces S3 Block Public Access for every account. Unlike SCPs and RCPs, they also apply to service-linked roles.

AWS Control Tower

A landing zone with controls built in

AWS Control Tower sets up and governs a multi-account environment (a landing zone) on top of Organizations: it creates the Log Archive and Audit accounts, centralizes CloudTrail and Config logging, configures IAM Identity Center, and provides Account Factory for vending new accounts with a standard baseline (Account Factory for Terraform does the same with Terraform). Its controls (formerly called guardrails) come in three behaviours:

  1. PreventiveStop an action before it happens. Implemented with SCPs, RCPs and declarative policies.
  2. DetectiveFind non-compliant resources after the fact. Implemented with AWS Config rules.
  3. ProactiveCheck resources before CloudFormation provisions them. Implemented with CloudFormation hooks.

Landing zone version 4.0 (November 2025) made the service integrations (Config, CloudTrail, security roles, AWS Backup) optional, no longer requires a Security OU, and no longer applies the mandatory controls by default. Like SCPs, Control Tower controls don't restrict the management account.

"Set up a new multi-account environment quickly with best-practice guardrails and automated account provisioning" points to AWS Control Tower. "Enforce a single rule across existing accounts" points to an SCP or RCP in Organizations.

Resource-based policies

Skill 1.1.5Determining the appropriate use of resource policies for AWS services

What they are and where they exist

A policy on the resource itself

A resource-based policy is attached to a resource and has a Principal element saying who may use it. Common examples are S3 bucket policies and access point policies, KMS key policies, SQS queue policies, SNS topic policies, Lambda function policies, Secrets Manager secret policies, ECR repository policies, API Gateway resource policies, EventBridge event bus policies, EFS file system policies and AWS Backup vault policies. An IAM role's trust policy is also a resource-based policy. The principal can be an account, a user, a role or role session, a federated user, an AWS service, or "*", but never an IAM group.

When a resource policy is the better tool

  • The caller must keep its own permissions, for example a process that reads a bucket in one account and writes to its own.
  • An AWS service needs access: S3 event notifications publishing to an SNS topic or SQS queue, or EventBridge invoking a Lambda function, are granted in the target's resource policy to a service principal.
  • Many accounts share one resource: one bucket policy or key policy that allows every account in the organization is simpler than a role in each account.
  • Role chaining limits would get in the way, because there is no role session to cap.

Use a role instead when the service has no resource-based policies, or when people need console access in the other account.

Limiting a resource to your organization

The organization condition keys

Instead of listing account IDs, a resource policy can allow every principal in the organization with aws:PrincipalOrgID (or a subtree with aws:PrincipalOrgPaths). The opposite direction, stopping your principals from writing to resources outside the organization, uses aws:ResourceOrgID in an identity policy or SCP. For requests made by AWS services on your behalf, aws:SourceOrgID, aws:SourceAccount and aws:SourceArn prevent the confused deputy problem.

Bucket policy: only principals in the company's organization can read the shared artifacts bucket (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOrgRead",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::example-shared-artifacts", "arn:aws:s3:::example-shared-artifacts/*"],
      "Condition": { "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" } }
    }
  ]
}

Each principal still needs an identity policy that allows s3:GetObject, because the access is cross-account. When an AWS service principal also needs the bucket, exempt it with the aws:PrincipalIsAWSService key, since service principals have no organization ID.

"Allow all current and future accounts in the organization to access a bucket without updating the policy" points to aws:PrincipalOrgID.

Two resource policies that behave differently

S3: Block Public Access and Object Ownership

New S3 buckets block public access by default, and the four Block Public Access settings (two for ACLs, two for policies) can be set on the organization, the account, the bucket and the access point; the most restrictive combination wins. New buckets also use the Bucket owner enforced setting for Object Ownership, which disables ACLs, so access is controlled by policies alone. AWS recommends keeping ACLs disabled.

KMS: the key policy comes first

Every KMS key must have a key policy, and unlike other resources, IAM policies have no effect on a key unless the key policy allows it. The default key policy does this with a statement that gives the account ("Principal": {"AWS": "arn:aws:iam::111111111111:root"}) full access, which lets IAM policies in the account grant key use. Remove that statement and IAM Allow policies stop working for the key. Cross-account use of a key needs both the key policy in the key's account and an IAM policy in the caller's account.

A resource-based policy that names a role ARN is still limited by that role's permissions boundary and session policy; one that names a specific role session or IAM user ARN is not. Most questions don't go this deep, but it explains "the bucket policy allows the role, so why is it denied?" scenarios.

Federating a directory

Skill 1.1.6Determining when to federate a directory service with IAM roles

Federation in one sentence

Sign in once, receive a role

With federation, people keep the accounts they already have in a corporate directory or identity provider (IdP). The IdP authenticates them and sends AWS a signed SAML assertion or OIDC token; STS exchanges it for temporary credentials for an IAM role. Nobody gets an IAM user, leavers lose access as soon as they're disabled in the directory, and MFA is enforced in one place. The design choice is where the federation happens.

IAM Identity Center for the workforce

The default answer for people across many accounts

AWS IAM Identity Center (the successor to AWS Single Sign-On) is AWS's recommended way to give the workforce access to many accounts. An organization instance, enabled in the management account and usually run from a delegated administrator account, has one identity source: its own directory, Active Directory (through AWS Managed Microsoft AD or AD Connector), or an external IdP such as Okta or Microsoft Entra ID using SAML 2.0 with SCIM to provision users and groups automatically. You define permission sets (for example ReadOnly, Developer, NetworkAdmin) and assign them to groups for specific accounts; Identity Center creates the matching IAM roles in each account. Users pick an account and role in the AWS access portal, and get CLI credentials with aws configure sso and aws sso login.

An account instance is tied to one account and is only for AWS managed applications; it can't manage access to AWS accounts. Identity Center can't use Simple AD as its identity source. When teams need custom roles that differ per account instead of uniform permission sets, IAM's account access manager can assign existing IAM roles to Identity Center users and groups.

"Employees already in Active Directory or an external IdP need single sign-on to many AWS accounts, managed centrally" points to IAM Identity Center with that directory as the identity source.

Federating straight to IAM roles

SAML 2.0 per account

You can also create an IAM SAML identity provider in each account and roles that trust it (sts:AssumeRoleWithSAML). The IdP then decides which role each user gets in each account. AWS describes this direct IAM federation as per-account, with the user-to-role mapping held in the external IdP, and as suited to workloads; it fits when only one or a few accounts are involved, when an existing IdP integration must be kept, or when Identity Center isn't an option.

OIDC for workloads and pipelines

CI/CD systems such as GitHub Actions federate with OIDC: the account trusts the IdP (for GitHub, token.actions.githubusercontent.com), and the job exchanges its token for role credentials with sts:AssumeRoleWithWebIdentity, so no access keys live in the pipeline. Since June 2025 IAM refuses to create or update a role trusting a shared OIDC provider like GitHub unless the trust policy checks the claim that identifies your repository or workflow.

Trust policy for the deploy role used by one GitHub repository's main branch (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Federated": "arn:aws:iam::111111111111:oidc-provider/token.actions.githubusercontent.com" },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:example-org/web-app:ref:refs/heads/main"
        }
      }
    }
  ]
}

Customers are not the workforce: Amazon Cognito

User pools and identity pools

The web app's customers should never be in the corporate directory or in IAM. Amazon Cognito user pools are a user directory and OIDC provider for app users: sign-up, sign-in, MFA, and federation with social, SAML and OIDC providers, issuing JWTs the app and API Gateway can check. Cognito identity pools exchange a trusted token (from a user pool or another IdP) for temporary AWS credentials for an IAM role, and can also give unauthenticated guests limited access. In the running example, the mobile app signs users in with a user pool and uses an identity pool so each user can upload photos straight to S3.

Which directory service?

AWS Directory Service options

When the identity source is Active Directory, AWS Managed Microsoft AD runs real Microsoft AD in AWS, can trust an on-premises domain, and works with services that need AD such as Amazon RDS for SQL Server and WorkSpaces. AD Connector is a proxy that sends authentication to your existing on-premises AD and stores nothing in AWS; it doesn't work with RDS for SQL Server. Simple AD is a low-cost Samba-based directory with no trusts and no MFA, and can't be an Identity Center identity source.

Key takeaways

  • Shared responsibility: AWS secures the cloud; you secure what's in it, and access control is always yours. IAM and Organizations are global; opt-in Regions and partitions are boundaries.
  • Root: MFA on every account type (up to 8 devices, passkeys preferred), no access keys, used only for root-only tasks; centralized root access removes member root credentials and allows 15-minute sts:AssumeRoot sessions.
  • People federate, workloads use roles; IAM users and access keys are the exception. Groups aren't principals and can't nest; roles allow 20 managed policies by default (25 max).
  • Evaluation: explicit Deny wins; SCPs, RCPs, permissions boundaries and session policies only limit; trust policies and KMS key policies must explicitly allow; cross-account needs both sides.
  • Roles: AssumeRole sessions up to 12 h, but role chaining caps at 1 h; third parties need an external ID that they generate; with a role you give up your own permissions, with a resource policy you keep them.
  • Many accounts: Security OU with Log Archive and Security Tooling; SCPs limit your principals (including member root, never the management account or service-linked roles; 10,240 characters, 10 per target); RCPs limit your resources (Deny only, about 60 services); declarative policies fix configurations; Control Tower builds the landing zone.
  • Resource policies: use them for service principals, shared resources and keep-your-permissions access; aws:PrincipalOrgID limits to the organization; new buckets block public access with ACLs disabled.
  • Federation: workforce through IAM Identity Center (organization instance, one identity source, permission sets), direct SAML per account when needed, OIDC for pipelines, Cognito for customers; AD Connector proxies, Managed Microsoft AD hosts.
