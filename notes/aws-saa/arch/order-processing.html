Reference architecture

Decoupled order processing

What happens after the mobile API accepts an order: a queue that absorbs bursts and parks bad messages, a workflow that charges, reserves and confirms with retries and a compensation path, and an event fan-out to email, analytics and the warehouse, with every consumer safe to run twice.

Scenario and requirements

The serverless API accepts an order in well under a second: order-api records the request in the DynamoDB table order-requests with a conditional write, sends one message to the SQS queue order-intake and returns 202 Accepted. This page is everything after that message. Payment, stock and confirmation are slow, call outside systems and sometimes fail, so they run behind the queue in the production account 111111111111 in us-east-1, at their own pace (Task 2.1).

The requirements:

  • No lost orders: an order accepted by the API is processed even if payment or stock services are slow or down for a while.
  • No double charges: delivery is at least once, so every step must be safe to repeat (Task 2.2).
  • Bad messages don't block good ones: a malformed order is set aside for inspection, then replayed once the bug is fixed.
  • A failed payment or stock check undoes what already happened, and the customer sees a clear status.
  • Other teams react without changing ordering code: email, the small Kinesis analytics feed (Task 3.5) and the warehouse each get completed orders.
  • Pay for work, not for idle servers: overnight there are almost no orders (Task 4.2).

Reused from the serverless API page: order-api, order-requests (keyed by request_id) and order-intake. Reused from Task 2.1: the charge-card task with its retry and RefundPayment catch. New on this page: the dead-letter queue order-intake-dlq; the consumer function order-worker; the Standard state machine order-fulfilment with functions reserve-stock, confirm-order, refund-payment and release-stock; the event source com.example.orders with detail type OrderCompleted on the default event bus; queues order-email, order-analytics and order-warehouse (each with a -dlq); the dedup table order-dedup; and the SNS topic oncall already used on Task 2.2.

Status changes to know. SQS messages can be up to 1 MiB since August 2025 (it was 256 KiB), and older posts still quote the old limit. EventBridge now offers a new Custom Event Bus alongside the rules-based bus (now called Custom Event Bus – Classic); the exam describes rules and targets, which is what this page uses. The X-Ray SDKs are in maintenance mode: trace new consumers with OpenTelemetry.

How it works

One order travels from the queue through the workflow to its subscribers. Steps marked AWS happen automatically.

  1. Buffer the order
  2. Enqueueorder-apiAfter the conditional write, order-api sends a small JSON message with the request ID to order-intake and returns 202.
  3. PollAWSThe Lambda event source mapping long-polls the queue and invokes order-worker with batches, capped by a maximum concurrency so a sale can't flood payment and stock.
  4. Claim and startorder-workerFor each message the worker claims the request ID in order-dedup with a conditional write, starts an order-fulfilment execution named after the request ID, and reports any failed messages back in a partial batch response.
  5. Run the workflow
  6. Charge, reserve, confirmAWSStep Functions runs charge-card, then reserve-stock, then confirm-order, retrying throttling and timeouts with exponential backoff.
  7. CompensateAWSIf stock is unavailable or confirmation fails after retries, a Catch sends the run to release-stock and refund-payment, and the order is marked failed.
  8. AnnounceAWSOn success, the last state puts an OrderCompleted event on the default event bus.
  9. Fan out and watch
  10. RouteAWSThree EventBridge rules match the event and deliver it to order-email, order-analytics and, for shipped orders only, order-warehouse; each team's consumer reads its own queue.
  11. Park and alarmAWSA message that fails five times moves to order-intake-dlq; CloudWatch alarms on the age of the oldest message and on DLQ depth notify oncall.

Build it

Step 1

The queue: order-intake and its DLQ

Standard, not FIFO. Standard queues take a nearly unlimited request rate, deliver at least once and order only on a best-effort basis. FIFO queues (names end in .fifo) keep strict order within a message group and use a deduplication ID for exactly-once processing, but handle 300 API calls per second per action, or 3,000 messages per second with batches of 10, more in high-throughput mode (Task 2.1). Orders are independent of one another, so order doesn't matter, and the dedup table in Step 5 handles duplicates at any rate.

The settings that matter. The visibility timeout (default 30 seconds, up to 12 hours) hides a received message from other consumers; if it isn't deleted in time it reappears and is processed again. For a Lambda consumer, the Lambda documentation says to set it to at least six times the function timeout, so order-worker's 30-second timeout gives 180 seconds. Long polling (ReceiveMessageWaitTimeSeconds up to 20) cuts empty receives and cost. Messages can be up to 1 MiB; anything larger goes to S3 with a pointer in the message. Retention is 4 days by default and up to 14 days.

A dead-letter queue. After a message has been received maxReceiveCount times without being deleted, SQS moves it to the DLQ instead of retrying forever. Lambda's guidance is at least 5, which gives a few retries before a message is parked. The DLQ keeps messages for the full 14 days so nobody loses evidence over a long weekend.

Create the dead-letter queue with 14-day retention, then order-intake pointing at it after five failed receives (AWS CLI; same form as the payments queue on Task 2.1) 
# The DLQ: keep parked messages for 14 days (1,209,600 seconds)
aws sqs create-queue --queue-name order-intake-dlq \
    --attributes '{"MessageRetentionPeriod": "1209600"}'

# The main queue: visibility 6 x the 30 s function timeout, long polling, redrive after 5 receives
aws sqs create-queue --queue-name order-intake \
    --attributes '{
      "VisibilityTimeout": "180",
      "ReceiveMessageWaitTimeSeconds": "20",
      "RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:us-east-1:111111111111:order-intake-dlq\",\"maxReceiveCount\":\"5\"}"
    }'

"Messages are processed twice" is a visibility timeout shorter than processing time. "Poison messages block the queue" is a dead-letter queue. "Must be processed in order, exactly once" is a FIFO queue, whose DLQ must also be FIFO.

Step 2

The consumer: batches, failures, concurrency

An event source mapping, not a polling loop. Lambda polls the queue for you and invokes order-worker with batches (default 10, up to 10,000 for a standard queue; a batch size above 10 needs a batching window of at least 1 second). The worker's role gets the AWSLambdaSQSQueueExecutionRole managed policy for the queue, plus states:StartExecution on order-fulfilment and item writes on order-dedup.

Partial batch responses. By default, one failed message sends the whole batch back to the queue, so nine good orders are retried with the bad one. With ReportBatchItemFailures the function returns the IDs of only the messages that failed, and only those return to the queue and count towards maxReceiveCount (Task 2.1).

Maximum concurrency as a valve. Lambda starts with five concurrent batches and adds up to 300 concurrent invocations a minute while messages remain. The mapping's MaximumConcurrency (2 to 1,000) caps how many copies run, so a promotion lengthens the queue instead of overloading the payment provider. Provisioned mode, which adds dedicated pollers for faster scaling, can't be combined with maximum concurrency.

Connect order-intake to order-worker: batches of 10, per-message failure reporting, at most 20 concurrent copies (AWS CLI; options checked on the create-event-source-mapping reference) 
aws lambda create-event-source-mapping \
    --function-name order-worker \
    --event-source-arn arn:aws:sqs:us-east-1:111111111111:order-intake \
    --batch-size 10 \
    --function-response-types ReportBatchItemFailures \
    --scaling-config MaximumConcurrency=20
What order-worker returns when one message in the batch failed (JSON; the identifier is the message ID) 
{
  "batchItemFailures": [
    { "itemIdentifier": "MESSAGE_ID_OF_THE_FAILED_ORDER" }
  ]
}

Containers or EC2 instead. If the consumers were ECS tasks or an Auto Scaling group, they would scale on backlog per instance, not raw queue length: visible messages divided by running instances, against the backlog one instance clears within the acceptable delay. At 0.1 seconds per message and a 10-second acceptable delay the target is 100 per instance, so 1,500 messages on 10 instances means scaling to 15 (Task 3.2).

Step 3

The workflow: Step Functions Standard

Orchestration instead of glue code. Payment, stock and confirmation are a saga: a multi-step transaction where each step has a compensating action if a later one fails (Task 2.1). Step Functions holds the state, the retries and the error paths in the definition, and shows each order's progress in the console, so nobody writes retry loops or status tables by hand.

Standard, not Express. Standard workflows run up to a year, execute each step exactly once and are priced per state transition. Express workflows run up to 5 minutes, are priced by executions and duration, run at least once when started asynchronously, and support only request-response integrations. Charging a card must not happen twice, and a stock check might wait on a supplier, so order-fulfilment is Standard. Inputs and outputs are limited to 256 KiB, so the workflow carries the request ID, not the whole order.

Retry with backoff, then Catch. Each task retries transient errors such as Lambda throttling with exponential backoff; any other error goes to the compensation branch. The fragment below follows Task 2.1's ChargeCard state for the next step.

The stock step of order-fulfilment: retry throttling with backoff, release stock and refund on any other error (Amazon States Language JSON fragment, JSONata as on Task 2.1) 
"ReserveStock": {
  "Type": "Task",
  "QueryLanguage": "JSONata",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Arguments": { "FunctionName": "reserve-stock", "Payload": "{% $states.input %}" },
  "Retry": [
    { "ErrorEquals": ["Lambda.TooManyRequestsException"], "IntervalSeconds": 2, "BackoffRate": 2.0, "MaxAttempts": 3 }
  ],
  "Catch": [
    { "ErrorEquals": ["States.ALL"], "Next": "ReleaseStock" }
  ],
  "Next": "ConfirmOrder"
}

Waiting for a person or a partner. If the warehouse had to approve large orders by hand, a Standard task could send a message with .waitForTaskToken and pause until the approver's system returns the token (Task 2.1 gives human approval as the example). Express workflows can't do this. The company doesn't need it today, so the workflow has no callback step.

Step 4

Fan-out: EventBridge rules to SQS

Announce once, let others subscribe. The last state of order-fulfilment puts an OrderCompleted event on the default event bus with the EventBridge service integration. The workflow doesn't know who listens: adding a loyalty-points consumer later is a new rule, not a change to ordering (Task 2.1).

The final state: publish OrderCompleted to EventBridge (Amazon States Language JSON fragment) 
"AnnounceCompleted": {
  "Type": "Task",
  "QueryLanguage": "JSONata",
  "Resource": "arn:aws:states:::events:putEvents",
  "Arguments": {
    "Entries": [
      { "Source": "com.example.orders", "DetailType": "OrderCompleted", "Detail": "{% $states.input %}" }
    ]
  },
  "End": true
}

One rule per consumer, each to its own queue. A rule matches an event pattern and sends matching events to up to five targets. Each consumer gets a queue rather than a direct function target, so a slow email provider or a warehouse system down for maintenance just lets its queue grow while the others carry on. The warehouse rule adds a content filter, because digital orders have nothing to ship.

Event patterns: all completed orders for email and analytics, shipped orders only for the warehouse (JSON) 
// order-completed-email and order-completed-analytics
{ "source": ["com.example.orders"], "detail-type": ["OrderCompleted"] }

// order-completed-warehouse: only orders with physical delivery
{
  "source": ["com.example.orders"],
  "detail-type": ["OrderCompleted"],
  "detail": { "delivery": ["ship"] }
}
The warehouse rule and its queue target with retries and a target DLQ (AWS CLI, same form as the SAP event-driven page) 
aws events put-rule \
    --name order-completed-warehouse \
    --event-pattern '{"source":["com.example.orders"],"detail-type":["OrderCompleted"],"detail":{"delivery":["ship"]}}' \
    --state ENABLED

# targets.json: [{"Id": "warehouse-queue",
#   "Arn": "arn:aws:sqs:us-east-1:111111111111:order-warehouse",
#   "RetryPolicy": {"MaximumRetryAttempts": 20, "MaximumEventAgeInSeconds": 7200},
#   "DeadLetterConfig": {"Arn": "arn:aws:sqs:us-east-1:111111111111:order-warehouse-dlq"}}]
aws events put-targets --rule order-completed-warehouse --targets file://targets.json

Each target queue needs a queue policy that lets events.amazonaws.com send messages, scoped to the rule's ARN. The analytics consumer reads order-analytics and writes a record to the Kinesis analytics feed, where the Flink and Firehose consumers already read (Task 3.5).

The SNS version. The same fan-out works as an SNS topic with three SQS subscriptions, using a subscription FilterPolicy (matched against message attributes by default, or the body with FilterPolicyScope set to MessageBody) in place of the event pattern, and RawMessageDelivery so the queues receive the plain message without the SNS envelope.

SNS alternative: subscribe the warehouse queue to a topic with a body filter (AWS CLI; replace ORDERS_TOPIC_ARN) 
aws sns subscribe \
    --topic-arn ORDERS_TOPIC_ARN \
    --protocol sqs \
    --notification-endpoint arn:aws:sqs:us-east-1:111111111111:order-warehouse \
    --attributes '{"FilterPolicyScope": "MessageBody", "FilterPolicy": "{\"delivery\": [\"ship\"]}", "RawMessageDelivery": "true"}'
Step 5

Idempotency, alarms and redrive

At least once means design for twice. A standard queue can deliver a message more than once, a consumer can crash after doing the work but before deleting the message, and EventBridge and SNS retry deliveries. Each consumer therefore records what it has done with a conditional write, the same technique order-api uses on order-requests (Task 2.2). The key combines the consumer and the order, so the email and warehouse consumers each process an order once without blocking each other.

Claim an order for one consumer; a duplicate delivery fails with ConditionalCheckFailedException and is deleted without redoing the work (AWS CLI; order-dedup is on-demand, keyed by dedup_id) 
aws dynamodb put-item --table-name order-dedup \
    --item '{"dedup_id": {"S": "order-worker#REQUEST_ID"}, "expires_at": {"N": "EPOCH_SECONDS_IN_7_DAYS"}}' \
    --condition-expression "attribute_not_exists(dedup_id)"

TTL on expires_at clears old claims at no charge. Powertools for AWS Lambda packages the same pattern as an idempotency utility backed by DynamoDB. Naming each execution after the request ID adds a second guard, because a Standard workflow won't run two executions with the same name.

Alarms on age, not just depth. ApproximateAgeOfOldestMessage rising means consumers aren't keeping up or one message keeps failing; it's the earliest warning that customers are waiting. A DLQ should be empty, so any visible message there is an alarm.

Page on-call when any message reaches the dead-letter queue (AWS CLI; same form as the alarms on the SOA and DVA guides; ONCALL_TOPIC_ARN is the oncall topic) 
aws cloudwatch put-metric-alarm \
    --alarm-name order-intake-dlq-not-empty \
    --namespace AWS/SQS \
    --metric-name ApproximateNumberOfMessagesVisible \
    --dimensions Name=QueueName,Value=order-intake-dlq \
    --statistic Maximum --period 60 \
    --evaluation-periods 1 \
    --threshold 0 \
    --comparison-operator GreaterThanThreshold \
    --treat-missing-data notBreaching \
    --alarm-actions ONCALL_TOPIC_ARN

A second alarm on ApproximateAgeOfOldestMessage for order-intake, with a threshold of a few minutes, catches a stalled workflow before customers start calling.

Redrive after the fix. Once the bug behind the parked messages is fixed and deployed, a message move task sends them back. Leaving out the destination returns them to their original source queue; a rate cap (up to 500 messages per second) keeps the replay gentle on payment.

Move parked orders back to order-intake at 50 messages per second (AWS CLI; options checked on the start-message-move-task reference) 
aws sqs start-message-move-task \
    --source-arn arn:aws:sqs:us-east-1:111111111111:order-intake-dlq \
    --max-number-of-messages-per-second 50

Redriving before the fix just cycles the same poison messages through five more failures and back into the DLQ. Only one move task can run per queue at a time.

Design decisions

EventBridge rules over SNS for the fan-out

EventBridge filters on any field of the event content, can archive and replay events, and can route to other accounts or Regions; SNS is the choice for very high-throughput fan-out and for notifying people by email, SMS or push (Task 2.1). Order events are moderate in volume and other teams will add rules, so content routing wins. Either way, each consumer reads its own SQS queue.

A Lambda worker instead of EventBridge Pipes

EventBridge Pipes could connect order-intake to the state machine with no code. The worker exists because it claims the request in the dedup table and reports per-message failures. A team with a simpler idempotency story could use a pipe and drop a function.

Per-request pricing over always-on consumers

Lambda, SQS, Step Functions and EventBridge charge for use, so an overnight lull costs close to nothing, and long polling keeps empty receives down. Task 4.2's comparison applies: at steady high volume, Fargate workers on a Compute Savings Plan can be cheaper than Lambda, and Standard workflows' per-transition price adds up for very short, high-rate work (Task 4.2). Recheck with Pricing Calculator if traffic becomes steady.

Alternatives

Amazon MQ for existing broker applications

If the warehouse system already spoke JMS or AMQP to an on-premises broker, Amazon MQ (managed ActiveMQ or RabbitMQ) would let it move without rewriting its messaging code. It runs on broker instances and doesn't scale like SQS and SNS, so it's for compatibility, not new designs (Task 2.1).

Kinesis Data Streams when order and replay matter

A stream keeps records in order per shard for 24 hours by default (up to 365 days), and several applications read and replay it independently; SQS deletes each message once processed. The analytics feed is a stream for that reason; order processing is a work queue (Task 3.2, Task 3.5).

Direct synchronous calls

If order-api called payment, stock and email in turn, the API would be as slow as its slowest dependency and fail whenever any of them did, and every tier would have to be sized for the peak. The API's 29-second timeout and the phone's patience would be the limit, and a failed call would lose the order. That breaks the first requirement, which is why the queue exists.

Testing it

  1. Duplicate deliverySend the same order-intake message twice: one execution of order-fulfilment, one charge, one email, and the second delivery deleted after a failed condition on order-dedup.
  2. Poison messageSend a malformed message in a batch of ten good ones: the nine complete, the bad one is retried five times and lands in order-intake-dlq, and the DLQ alarm fires.
  3. CompensationMake reserve-stock fail in staging: the execution history must show the Catch, release-stock and refund-payment, and the order status must read failed.
  4. Downstream outageStop the warehouse consumer for an hour: order-warehouse grows while email and analytics keep up, and nothing is lost when it restarts.
  5. BurstLoad-test ten times the normal order rate: concurrency stays at the cap of 20, the age of the oldest message rises and then falls, and payment sees no more than the agreed rate.
  6. RedriveFix the parser, start a move task from the DLQ and confirm every parked order completes exactly once.

"Orders are lost when the payment service is slow. Which solution meets these requirements with the LEAST operational overhead?" is an SQS queue with a Lambda consumer, not a bigger instance. "Coordinate payment, stock and shipping with retries and undo steps" is a Step Functions Standard workflow. "Several systems must each receive every completed order, at their own pace" is SNS or EventBridge fan-out to SQS queues. "One bad message makes the whole Lambda batch retry" is partial batch responses. "Migrate an application using JMS with minimal changes" is Amazon MQ.
