Reference architecture

Highly available web application

The company's customer-facing web application in us-east-1, built so that losing a whole Availability Zone costs users at most a few seconds of errors, and so that a sales peak adds capacity by itself: CloudFront and WAF at the edge, an Application Load Balancer and an Auto Scaling group across three AZs, Aurora PostgreSQL with replicas, and sessions in ElastiCache.

Scenario and requirements

The company's website and mobile app take orders from customers around the clock. The web tier runs on EC2 in the production account 111111111111 in us-east-1, and the order data lives in Aurora PostgreSQL. Task 2.2 states the target: survive the loss of an AZ with no manual action, and scale with demand without anyone resizing servers (Task 2.1, Task 3.2). Losing the whole Region is the DR on a budget page (not written yet) and, at Professional depth, the SAP multi-Region DR architecture.

The requirements:

  • AZ failure is a non-event: every tier spans three AZs, and the remaining two can carry the load.
  • Elastic web tier: capacity follows traffic, and failed instances are replaced automatically.
  • Stateless servers: any instance can serve any request, so instances can be added, removed or replaced at any time.
  • Database failover in about a minute or less, without code changes, and reads offloaded from the writer.
  • Protected at the edge: HTTPS everywhere, and SQL injection, cross-site scripting and floods filtered before they reach the servers (Task 1.2).
  • Cost-aware: pay for redundancy where the requirement needs it, and commit only to the steady baseline (Task 4.2).

Reused from the task pages: vpc-0prod11111111111 and its security groups (Task 1.2), web-alb and web-tg (Task 2.1), orders-proxy and the web-5xx-high alarm (Task 2.2), and the Valkey cache web-cache (Task 3.3). New on this page: the Auto Scaling group web-asg, the launch template web-lt, the third app subnet subnet-0appc111111111111, and the Aurora cluster orders-east with instances orders-east-1 (writer), orders-east-2 and orders-east-3.

Status changes to know. Launch configurations are deprecated, and accounts created on or after 1 October 2024 can't create them: use launch templates. Route 53 Application Recovery Controller is now Amazon Application Recovery Controller (ARC); its readiness check is closed to new customers, while zonal shift and zonal autoshift continue. A Regional NAT gateway (November 2025) is now an option next to one zonal NAT gateway per AZ. AWS WAF Classic has reached end of support, so new web ACLs are AWS WAF.

How it works

A customer's request, and what happens when an AZ fails. Steps marked AWS happen automatically.

  1. Normal request
  2. Resolve the nameAWSRoute 53 answers www.example.com with an alias record pointing at the CloudFront distribution; alias queries to AWS resources are free.
  3. EdgeAWSCloudFront terminates TLS with an ACM certificate, AWS WAF checks the request, and static paths such as /static/* are served from cache.
  4. Load balancerAWSDynamic requests go to the ALB, which sends each one to a healthy instance of web-asg in any of the three AZs (cross-zone is always on at an ALB).
  5. ApplicationWeb tierThe instance reads the customer's session from web-cache, reads catalog data from cache or the Aurora reader endpoint, and writes orders through orders-proxy to the writer.
  6. An AZ fails
  7. Stop sending trafficAWSALB health checks fail for targets in the impaired AZ and the ALB routes only to healthy targets; with zonal autoshift, or a zonal shift you start, ARC moves traffic away even when health checks still pass.
  8. Replace capacityAWSAuto Scaling launches replacements and new capacity in the healthy AZs, and rebalances when the AZ returns.
  9. Fail over the databaseAWSIf the writer was in that AZ, Aurora promotes the replica with the best promotion tier, typically in under 60 seconds; RDS Proxy keeps client connections open and reconnects them to the new writer.

Build it

Step 1

Network across three AZs

Three tiers of subnets in three AZs. Each AZ gets a public subnet (the ALB's nodes and, with zonal NAT, the NAT gateway), a private app subnet (the instances and the cache) and a private database subnet with no route to the internet at all (Task 1.2). Security groups chain the tiers by reference, not IP address, so the rules keep working as instances come and go.

Allow the app tier to receive traffic only from the load balancer (AWS CLI, from Task 1.2) 
aws ec2 authorize-security-group-ingress \
    --group-id sg-0app1111111111111 \
    --protocol tcp --port 8080 \
    --source-group sg-0alb1111111111111

Outbound internet without a single point of failure. A zonal NAT gateway is redundant only inside its own AZ: one serving all three AZs means losing its AZ cuts outbound access for the other two. The fix is either one zonal NAT gateway per AZ with each private route table pointing at the one in its own AZ, or a Regional NAT gateway, one ID that expands across AZs automatically and needs no public subnet.

Create a Regional NAT gateway for the prod VPC (AWS CLI, from Task 1.2) 
# Automatic mode manages the addresses and the AZ expansion for you
aws ec2 create-nat-gateway --vpc-id vpc-0prod11111111111 --availability-mode regional

"Instances in private subnets lost internet access when one AZ failed" means a single zonal NAT gateway. The highly available answer is one NAT gateway per AZ (with per-AZ route tables) or a Regional NAT gateway, not a second NAT gateway in the same AZ.

Step 2

Edge: Route 53, CloudFront, WAF and ACM

Route 53 alias to CloudFront. An alias record works at the zone apex too, needs no TTL management and costs nothing per query. Route 53 failover records belong to the Region-level design; inside one Region the ALB and ARC handle AZ failures.

CloudFront in front of the ALB, even for dynamic pages. CloudFront ends TLS close to the customer, caches what it can, and absorbs spikes and DDoS attacks (Task 2.1). One distribution has two cache behaviours:

  • /static/* (images, CSS, scripts): long TTLs, so most requests never reach the ALB.
  • Default (*): forwards to the ALB with caching off or very short, passing the cookies and headers the application needs for sessions.

AWS WAF on the distribution. A global web ACL (created in us-east-1) on CloudFront filters at the edge: the Core rule set for cross-site scripting, the SQL database rule group for SQL injection, and a rate-based rule for request floods from one address (Task 1.2). Shield Standard protects CloudFront and Route 53 automatically at no cost.

Certificates from ACM. Public ACM certificates are free and renew automatically. The certificate for CloudFront must be in us-east-1, and the ALB's certificate must be in the ALB's Region; here both are us-east-1.

Protecting the origin. If the ALB is internet-facing, anyone who finds its DNS name can skip CloudFront and its WAF rules. Since November 2024, CloudFront VPC origins can reach an ALB in private subnets, so the load balancer doesn't need to be public at all. The company starts with an internet-facing ALB and plans that move (Design decisions).

"Block SQL injection and cross-site scripting for a website behind CloudFront" is AWS WAF on the CloudFront distribution (or the ALB), never a security group or network ACL. "TLS certificate for CloudFront" means ACM in us-east-1, whatever Region the origin is in.

Step 3

Web tier: ALB and Auto Scaling

The ALB spans three AZs. It has nodes in every enabled AZ, so it isn't a single point of failure; web-tg health-checks each instance and sends traffic only to healthy targets, across zones. Deregistration delay (300 seconds by default) lets in-flight requests finish when an instance leaves during scale-in or a deployment.

An Auto Scaling group with a launch template. The launch template web-lt holds the AMI, instance type, IMDSv2 requirement and security group; each new AMI is a new version.

Create the web tier group across three AZs with ELB health checks (AWS CLI; new names web-asg, web-lt, subnet-0appc111111111111) 
aws autoscaling create-auto-scaling-group \
    --auto-scaling-group-name web-asg \
    --launch-template LaunchTemplateName=web-lt,Version='$Default' \
    --min-size 6 \
    --max-size 30 \
    --desired-capacity 6 \
    --vpc-zone-identifier "subnet-0appa111111111111,subnet-0appb111111111111,subnet-0appc111111111111" \
    --target-group-arns arn:aws:elasticloadbalancing:us-east-1:111111111111:targetgroup/web-tg/fedcba9876543210 \
    --health-check-type ELB \
    --health-check-grace-period 300 \
    --default-instance-warmup 300 \
    --availability-zone-impairment-policy ZonalShiftEnabled=true,ImpairedZoneHealthCheckBehavior=IgnoreUnhealthy

How it reads:

  • --health-check-type ELB: EC2 status checks notice a broken instance, not a broken application; the ELB check also replaces an instance whose web server has hung.
  • --health-check-grace-period 300: how long a new instance has to boot before its health checks count. It is 300 seconds by default in the console but 0 from the CLI and SDKs, so set it explicitly, or new instances are killed while they are still starting.
  • --default-instance-warmup 300: a new instance's metrics aren't counted in scaling decisions until it is ready (AWS suggests 300 seconds if unsure).
  • Minimum of six, two per AZ: static stability. If one AZ is lost, four instances keep serving while replacements launch; the minimum is sized so two AZs carry normal peak traffic.
  • --availability-zone-impairment-policy: registers the group for ARC zonal shift (Step 5); IgnoreUnhealthy means instances in a shifted-away AZ aren't replaced during the impairment, which AWS recommends when the group is prescaled.

Target tracking on requests per target. The group keeps about 1,000 requests per instance, the policy from Task 2.1. ALBRequestCountPerTarget suits a web tier because it rises with traffic and falls as instances are added; the load balancer's total RequestCount or its latency don't fall with added capacity and make poor targets (Task 3.2).

Attach the target tracking policy to web-asg (AWS CLI; config.json is the Task 2.1 configuration with TargetValue 1000.0 and ALBRequestCountPerTarget) 
aws autoscaling put-scaling-policy \
    --auto-scaling-group-name web-asg \
    --policy-name web-1000-requests-per-target \
    --policy-type TargetTrackingScaling \
    --target-tracking-configuration file://config.json

Stateless instances. Nothing about a customer lives on an instance: sessions are in ElastiCache and uploads in example-prod-uploads, so scale-in, instance refresh and AZ loss are harmless. Sticky sessions would lose the session with its instance, so the target group doesn't use them.

"Instances are terminated and replaced in a loop right after launch" is a health check grace period that is too short (often 0 because the group was created from the CLI), not a scaling policy problem. "The web server hangs but Auto Scaling never replaces the instance" is a group using only EC2 health checks; switch it to ELB.

Step 4

Data tier: Aurora, RDS Proxy and ElastiCache

Aurora PostgreSQL with replicas in the other AZs. Aurora's storage keeps six copies across three AZs, so data survives an AZ loss even with one instance; but with no replica Aurora must recreate the writer (typically under 10 minutes). With replicas in other AZs it promotes one, typically in under 60 seconds. orders-east has its writer orders-east-1 in one AZ and a replica in each of the others.

Add an Aurora Replica to orders-east in a second AZ, first in line for promotion (AWS CLI; new names; the cluster manages storage, security groups and backups) 
# Run once more with orders-east-3, us-east-1c and the same tier for the third AZ
aws rds create-db-instance \
    --db-instance-identifier orders-east-2 \
    --db-cluster-identifier orders-east \
    --engine aurora-postgresql \
    --db-instance-class db.r6g.large \
    --availability-zone us-east-1b \
    --promotion-tier 0

Promotion tiers run from 0 to 15, and Aurora promotes the replica with the lowest tier first. Keep replicas the same class as the writer.

Writer and reader endpoints. The cluster endpoint always points to the writer and follows it through a failover; the reader endpoint spreads connections (not individual queries) over the replicas. The application sends order writes to the writer and catalog and order-history reads to the reader endpoint, so the failover replicas also offload reads (Task 3.3). Keep client DNS caching short.

RDS Proxy for faster, quieter failovers. orders-proxy pools connections, protecting Aurora from connection storms when the web tier scales out quickly, and during a failover keeps the application's connections open and reconnects to the new writer itself, bypassing DNS caching. It is never publicly accessible.

The proxy in front of the orders database, from Task 2.2 (AWS CLI) 
aws rds create-db-proxy \
    --db-proxy-name orders-proxy \
    --engine-family POSTGRESQL \
    --auth AuthScheme=SECRETS,SecretArn=arn:aws:secretsmanager:us-east-1:111111111111:secret:orders-db,IAMAuth=REQUIRED \
    --role-arn arn:aws:iam::111111111111:role/rds-proxy-secrets \
    --vpc-subnet-ids subnet-0dba111111111111a subnet-0dbb111111111111b \
    --vpc-security-group-ids sg-0proxy1111111111 \
    --require-tls

ElastiCache for Valkey for sessions and read caching. web-cache is serverless Valkey: no node sizing, automatic scaling, replicated across AZs. Sessions carry a TTL matching the session timeout; catalog pages use lazy loading with a TTL, so a burst of product views doesn't reach the database (Task 2.1). Valkey is priced 33% lower than other engines on serverless.

The serverless Valkey cache in the app subnets, from Task 3.3 (AWS CLI) 
aws elasticache create-serverless-cache --serverless-cache-name web-cache \
    --engine valkey \
    --subnet-ids subnet-0appa111111111111 subnet-0appb111111111111 \
    --security-group-ids sg-0cache111111111111

"Survive an AZ failure with automatic database failover and also scale reads" is Aurora with replicas in other AZs (or an RDS Multi-AZ DB cluster). "Reduce failover time without changing the application" is RDS Proxy. "Session state must survive the loss of a web server" is ElastiCache (or DynamoDB), not sticky sessions.

Step 5

Deployments and AZ impairment

Instance refresh for new AMIs. Servers are never patched in place: EC2 Image Builder bakes a new AMI, it becomes a new web-lt version, and an instance refresh replaces the fleet in rolling batches (Task 2.2). Keeping 90% healthy (the default) limits the capacity dip, and automatic rollback returns the group to the previous template version if the refresh fails or the web-5xx-high alarm fires.

config.json for aws autoscaling start-instance-refresh --cli-input-json file://config.json: roll out the default web-lt version, roll back on failure or on the 5xx alarm 
{
  "AutoScalingGroupName": "web-asg",
  "DesiredConfiguration": {
    "LaunchTemplate": {
      "LaunchTemplateName": "web-lt",
      "Version": "$Default"
    }
  },
  "Preferences": {
    "MinHealthyPercentage": 90,
    "InstanceWarmup": 300,
    "AutoRollback": true,
    "AlarmSpecification": { "Alarms": ["web-5xx-high"] }
  }
}

Blue/green (weighted target groups or CodeDeploy) is the alternative when both versions must run before traffic moves.

Zonal shift for gray failures. Health checks catch instances that fail outright. Some AZ problems don't fail them: higher latency or intermittent errors in one AZ while checks still pass. ARC zonal shift moves traffic away from one AZ for a supported resource (ALB, NLB, Auto Scaling group, EKS) for up to three days, extendable, and back again; with zonal autoshift AWS starts the shift itself and runs practice shifts. Enable zonal shift on each load balancer first. During a shift on web-asg, the group launches all new capacity in the healthy AZs and blocks scaling policies from lowering desired capacity.

Move web-asg away from the impaired AZ for two hours (AWS CLI; replace <uuid> with the group's ID from its ARN; use the AZ ID, not the AZ name) 
aws arc-zonal-shift start-zonal-shift \
    --resource-identifier arn:aws:autoscaling:us-east-1:111111111111:autoScalingGroup:<uuid>:autoScalingGroupName/web-asg \
    --away-from use1-az1 \
    --expires-in 2h \
    --comment "Elevated 5xx in use1-az1, shifting web tier"

Shift the ALB too, so it stops sending requests into the AZ. AZ IDs such as use1-az1 name the same physical AZ in every account.

Design decisions

Three AZs, prescaled for the loss of one

With three AZs, losing one leaves two thirds of the capacity; with two, it leaves half, so a two-AZ design must overprovision to 200% of peak to stay statically stable, against 150% for three. The six-instance minimum costs money every hour but removes any dependence on launching capacity during the failure.

Aurora replicas instead of a larger single writer

Two replicas roughly triple the database instance cost, but turn a possible 10-minute writer recreation into a sub-minute failover and absorb reads. Aurora Standard charges per I/O; I/O-Optimized suits clusters where I/O is at least 25% of the Aurora bill (Task 3.3).

Regional NAT gateway instead of one per AZ

Both meet the requirement. A zonal NAT gateway costs US$0.045 per hour plus US$0.045 per GB processed (Task 4.4), so three of them cost three hourly charges; the Regional NAT gateway is billed per AZ it runs in, so its gain is simpler routing. A single zonal NAT gateway is what fails the requirement.

Origin protection: move to a CloudFront VPC origin

An internet-facing ALB can be reached around CloudFront, skipping its WAF rules and caching. A VPC origin makes the ALB internal, so CloudFront is the only way in. The ANS inbound perimeter architecture cover the edge in more depth.

Multi-AZ cost, cross-AZ traffic and commitments

Redundancy has running costs beyond extra instances: traffic between AZs costs US$0.01 per GB in each direction, so a web tier calling a cache or database in another AZ pays for every byte (Task 3.4). The steady baseline (the six-instance minimum around the clock) is covered by a Compute Savings Plan, up to 66% off and still valid if the team moves to Graviton or Fargate (Task 4.2); peaks above it stay On-Demand, and the Aurora instances can be covered by Reserved Instances or a Database Savings Plan (Task 4.3).

Alternatives

ECS on Fargate instead of EC2

The company's APIs already run as ECS services on Fargate (Task 2.1). The same design works with an ECS service across three AZs behind the ALB: no AMIs or patching, Application Auto Scaling for tasks, and built-in blue/green with rollback. Fargate is billed per second for the vCPU and memory each task requests, with no instances to keep busy, and it removes the server management, which is the usual answer to "least operational overhead". Compute Savings Plans cover Fargate too.

Elastic Beanstalk

Beanstalk creates the ALB, Auto Scaling group and health monitoring from an uploaded application, for a team that wants a multi-AZ web tier without designing it, at the cost of control. Its Amazon Linux 2 platforms are retired; use the AL2023 platforms (Task 3.2).

A single-AZ design

One AZ is cheaper (no cross-AZ traffic, one NAT gateway, no replicas) but fails the requirement: an AZ event takes down every tier at once. It suits only dev and test. An Auto Scaling group of one across several AZ subnets is the minimum self-healing pattern for an application that can't run more than one copy (Task 2.2), with downtime while the replacement starts.

Testing it

  1. Load test to the peakRamp synthetic traffic through CloudFront to the expected sales peak and beyond; web-asg must scale out on ALBRequestCountPerTarget without 5xx errors, and scale back in gradually afterwards.
  2. Kill instancesStop the web server on one instance: the ELB health check must mark it unhealthy and Auto Scaling must replace it, with no customer losing their session.
  3. Fail over AuroraRun aws rds failover-db-cluster --db-cluster-identifier orders-east --target-db-instance-identifier orders-east-2 in a quiet period; measure how long order writes fail through orders-proxy and confirm the cluster endpoint now points at orders-east-2.
  4. Rehearse an AZ lossStart a zonal shift on the ALB and web-asg for one AZ ID (or use an AWS FIS AZ scenario); two AZs must carry peak load, latency must stay within target, and new instances must launch only in the healthy AZs.
  5. Check the edgeSend a request with a SQL injection pattern: WAF must block it at CloudFront. After the VPC origin move, the ALB must not answer from the internet at all.
  6. Roll back a deploymentStart an instance refresh with a deliberately broken AMI on staging; the failing health checks or the 5xx alarm must stop the refresh and restore the previous template version.

"A web application must remain available if an Availability Zone fails. Which solution meets these requirements with the LEAST operational overhead?" is an ALB with an Auto Scaling group across multiple AZs and a Multi-AZ database (Aurora with replicas here), not scripts that relaunch instances or a larger single instance. "Users are logged out when Auto Scaling terminates instances" is sessions in ElastiCache (or DynamoDB). "Most cost-effective way to keep private instances' internet access through an AZ failure" is NAT per AZ or a Regional NAT gateway. "Unhealthy instances keep receiving traffic and aren't replaced" is ELB health checks on the group.
