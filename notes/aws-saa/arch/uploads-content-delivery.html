Uploads and content delivery

Customers upload photos and documents straight to S3 with short-lived presigned URLs, a queue-driven function scans them and makes thumbnails, and CloudFront serves product images and private documents worldwide from buckets nobody can reach directly, with encryption, replication and lifecycle rules keeping the data safe and cheap.

Scenario and requirements

Customers of the web application and the mobile API attach photos and documents to their accounts and orders: profile pictures, product reviews with photos, receipts and delivery paperwork. The company also serves its own product images, scripts and stylesheets to shoppers around the world. Everything lives in S3 in the production account 111111111111 in us-east-1, with a copy in the DR Region us-west-2 (Task 1.3, Task 3.1).

The requirements:

  • Uploads don't pass through the servers: a 200 MB file must not tie up the API, and the API's 10 MB payload limit rules that out anyway (Task 2.1).
  • Only signed-in customers upload, only into their own area, for a few minutes at a time.
  • Nothing reaches other customers unchecked: every file is scanned and resized before anyone sees it.
  • Fast worldwide reads of product images, and private documents visible only to their owner.
  • No public buckets, encryption with the company key for customer data, and a recoverable copy in us-west-2.
  • Storage costs fall as files age: most photos are read in the first weeks, some for years.

Reused from the SAA pages: the buckets example-prod-uploads (customer files), example-dr-uploads (its replica in us-west-2) and example-order-archive (seven-year order records with Object Lock), and the KMS key alias/prod-data. New on this page: the bucket example-prod-assets for product images and static files; the prefixes incoming/ and processed/ in the uploads bucket; the function upload-url behind the serverless API and its role upload-url-role; the queue upload-events with upload-events-dlq; the processing function upload-processor; and one CloudFront distribution, shown as E1EXAMPLE.

Status changes to know. Since April 2023 new buckets block public access and disable ACLs (Bucket owner enforced), and since January 2023 every new object is encrypted with SSE-S3 by default. CloudFront origin access control (OAC) replaced the legacy origin access identity (OAI). S3 objects can be up to 50 TB since December 2025. S3 Select and S3 Object Lambda are closed to new customers, and the original Glacier vault service is closed; the S3 Glacier storage classes are unaffected.

How it works

One photo travels from the phone to S3, through processing, and out through CloudFront. Steps marked AWS happen automatically.

  1. Upload
  2. Sign inCustomerThe app signs the customer in with the Cognito user pool and calls POST /uploads with the JWT, the file type and its size.
  3. Issue a URLupload-urlThe function checks the type and size, chooses the key incoming/USER_ID/UUID.jpg and returns a presigned PUT URL that expires in five minutes.
  4. PUT to S3CustomerThe app uploads straight to example-prod-uploads; large files use multipart upload. S3 encrypts the object with alias/prod-data.
  5. Process
  6. NotifyAWSAn event notification for objects created under incoming/ sends a message to upload-events.
  7. Scan and resizeupload-processorLambda polls the queue; the function checks the real file type, scans it, writes the clean file and a thumbnail under processed/ and records the result. Failures land in upload-events-dlq.
  8. Deliver and protect
  9. ServeAWSCloudFront serves product images from example-prod-assets and, with a signed URL, the customer's own files from processed/, signing every origin request with OAC.
  10. Replicate and tierAWSCross-Region Replication copies new uploads to example-dr-uploads; lifecycle rules expire raw uploads, old versions and abandoned multipart uploads.

Build it

Step 1

The upload path: presigned URLs

Signed by the API, used by the phone. A presigned URL carries the permissions of the principal that created it, for one bucket, one key, one HTTP method and a limited time. The phone needs no AWS credentials and the bucket policy needs no change. URLs made with the CLI or SDKs can last up to 7 days, but a URL signed with role credentials dies when the role session ends, so a Lambda function's URLs never outlive its credentials. Five minutes is plenty for an upload that starts at once; S3 checks expiry when the request starts, so a long upload already under way finishes.

Limits before the URL, checks after the upload. upload-url refuses unknown types and oversized files, chooses the key itself (the customer never names the object), and signs the content type into the URL. A presigned POST form can also carry a policy with a size range; the upload patterns blog compares both. The client can still lie, so upload-processor checks the real type and size afterwards. A bucket policy condition on s3:signatureAge can reject old signatures across the bucket.

upload-url: return a five-minute presigned PUT URL for a key the server chooses (Python, AWS SDK for Python; user_id comes from the validated Cognito JWT) 
import uuid, boto3

s3 = boto3.client("s3")
ALLOWED = {"image/jpeg": "jpg", "image/png": "png", "application/pdf": "pdf"}

def handler(event, context):
    user_id = event["requestContext"]["authorizer"]["jwt"]["claims"]["sub"]
    content_type = event["queryStringParameters"]["type"]
    if content_type not in ALLOWED:
        return {"statusCode": 400, "body": "file type not allowed"}
    # The server picks the key: incoming/ is the only prefix customers can write to
    key = f"incoming/{user_id}/{uuid.uuid4()}.{ALLOWED[content_type]}"
    url = s3.generate_presigned_url(
        "put_object",
        Params={"Bucket": "example-prod-uploads", "Key": key, "ContentType": content_type},
        ExpiresIn=300)                      # five minutes
    return {"statusCode": 200, "body": f'{{"url": "{url}", "key": "{key}"}}'}

Large files and distant customers. A single PUT takes at most 5 GB; AWS recommends multipart upload above 100 MB, with parts of 5 MiB to 5 GiB uploaded in parallel and only failed parts retried (Task 3.1). For multipart, the API presigns each part. Transfer Acceleration routes uploads through the nearest edge location and can be 50% to 500% faster for large objects over long distances, at US$0.04 per GB charged only when it is faster (Task 4.4). Most uploads here are phone photos of a few MB, so it stays off; a team that handled large video from overseas would turn it on for that bucket.

Locked buckets. Both buckets keep Block Public Access on and Object Ownership at Bucket owner enforced, so ACLs are disabled and only policies decide access (Task 1.1). upload-url-role may only s3:PutObject on example-prod-uploads/incoming/* and use the KMS key to encrypt.

Step 2

Processing: events, queue, function

Event notification to a queue. S3 publishes an event for each new object under incoming/ to upload-events, which needs a queue policy allowing s3.amazonaws.com to send messages for this bucket. The queue absorbs bursts, keeps failed messages for retry and parks poison files in the DLQ, exactly like order processing (Decoupled order processing).

Send an event to upload-events for every object created under incoming/ (notification.json for aws s3api put-bucket-notification-configuration; structure checked on the CLI reference) 
# aws s3api put-bucket-notification-configuration \
#     --bucket example-prod-uploads --notification-configuration file://notification.json
{
  "QueueConfigurations": [
    {
      "Id": "new-uploads",
      "QueueArn": "arn:aws:sqs:us-east-1:111111111111:upload-events",
      "Events": ["s3:ObjectCreated:*"],
      "Filter": { "Key": { "FilterRules": [ { "Name": "prefix", "Value": "incoming/" } ] } }
    }
  ]
}

The call replaces the bucket's whole notification configuration, so keep every destination in the one file.

No recursive triggers. upload-processor writes its output under processed/, which the prefix filter ignores. If the function wrote back into incoming/, each output would trigger another invocation and the bill would climb until someone noticed. A separate output bucket is the stricter version of the same rule.

Connect upload-events to upload-processor with per-message failure reporting and a concurrency cap (AWS CLI; same options as on the order processing page) 
aws lambda create-event-source-mapping \
    --function-name upload-processor \
    --event-source-arn arn:aws:sqs:us-east-1:111111111111:upload-events \
    --batch-size 10 \
    --function-response-types ReportBatchItemFailures \
    --scaling-config MaximumConcurrency=20

The queue's visibility timeout is six times the function timeout and its redrive policy moves a message to upload-events-dlq after five receives, as for order-intake. Files that fail the scan are left in incoming/ and expire there (Step 5); nothing under incoming/ is ever served.

Step 3

Delivery: CloudFront with OAC

One distribution, two private origins. The default behaviour reads example-prod-assets; a /files/* behaviour reads processed/ in example-prod-uploads. Both buckets stay private: CloudFront signs every origin request with origin access control (SigV4, signing behaviour always). AWS recommends OAC over OAI because OAC works in every Region, supports SSE-KMS and supports PUT and DELETE requests. OAC needs a regular bucket endpoint, not an S3 website endpoint, and Object Ownership at Bucket owner enforced (Task 2.1).

The origin access control (CloudFormation YAML, from the CloudFront developer guide) 
AssetsOAC:
  Type: AWS::CloudFront::OriginAccessControl
  Properties:
    OriginAccessControlConfig:
      Name: prod-s3-oac
      OriginAccessControlOriginType: s3
      SigningBehavior: always        # sign every request; CloudFront to S3 is always HTTPS
      SigningProtocol: sigv4

Only this distribution may read. The bucket policy allows the CloudFront service principal, but only on behalf of distribution E1EXAMPLE, so another customer's distribution can't point at the bucket.

example-prod-assets bucket policy: read-only access for one distribution (JSON, the AWS OAC example) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontServicePrincipalReadOnly",
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-prod-assets/*",
      "Condition": {
        "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::111111111111:distribution/E1EXAMPLE" }
      }
    }
  ]
}

The uploads bucket gets the same statement for processed/*. Its objects are encrypted with alias/prod-data, so the key policy also needs a statement letting cloudfront.amazonaws.com use the key under the same AWS:SourceArn condition; without it CloudFront gets an access error from S3.

Statement added to the prod-data key policy so the distribution can decrypt (JSON fragment, the AWS OAC example) 
{
  "Sid": "AllowCloudFrontServicePrincipalSSE-KMS",
  "Effect": "Allow",
  "Principal": { "Service": ["cloudfront.amazonaws.com"] },
  "Action": ["kms:Decrypt", "kms:Encrypt", "kms:GenerateDataKey*"],
  "Resource": "*",
  "Condition": {
    "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::111111111111:distribution/E1EXAMPLE" }
  }
}

AWS WAF attaches to the distribution with a global web ACL created in us-east-1, and Shield Standard protects every distribution at no charge (Task 1.2).

Step 4

Caching, private files and updates

Cache behaviours and TTLs. Each behaviour has a cache policy that sets the minimum, default and maximum TTL and the cache key. Product images and versioned scripts get long TTLs; the cache key includes only the headers, cookies and query strings that change the response, which raises the hit ratio and cuts origin requests (Task 4.4). If most shoppers are in North America and Europe, Price Class 100 lowers the CloudFront bill; Origin Shield adds a central cache layer when misses from many edges overload the origin.

Private documents with signed URLs. The /files/* behaviour requires signed URLs from a trusted key group. When a signed-in customer opens a receipt, the API checks ownership and returns a CloudFront signed URL valid for a few minutes. Signed URLs suit single files and clients without cookies; signed cookies suit many files at once, such as a whole gallery or video, without changing the URLs. If both are present, the signed URL wins. An S3 presigned GET URL would also work, but it bypasses the cache and the edge.

Versioned file names over invalidations. The build pipeline names files by content (app.3f9c2b.js, sku-1042-v7.jpg) and changes the reference in the HTML. AWS recommends versioning for files that change often: browsers and corporate proxies can't serve a stale copy, rolling back is changing a name, and there is no invalidation charge. Invalidation is for mistakes, such as a wrong price on a banner image.

Remove a wrong banner from every edge cache now (AWS CLI; options checked on the create-invalidation reference) 
aws cloudfront create-invalidation \
    --distribution-id E1EXAMPLE \
    --paths "/banners/sale.jpg"
Step 5

Encryption, replication and lifecycle

Two buckets, two encryption choices. Product images are public content, so example-prod-assets keeps the free SSE-S3 default. Customer files are personal data, so example-prod-uploads uses SSE-KMS with alias/prod-data: every use of the key is in CloudTrail and the key policy decides who may decrypt. S3 Bucket Keys cut KMS requests by up to 99%, which lowers cost and avoids KMS throttling during upload bursts (Task 1.3).

Default encryption for the uploads bucket: SSE-KMS with the company key and a Bucket Key (AWS CLI, as on Task 1.3) 
aws s3api put-bucket-encryption --bucket example-prod-uploads \
    --server-side-encryption-configuration '{
      "Rules": [{
        "ApplyServerSideEncryptionByDefault": {
          "SSEAlgorithm": "aws:kms",
          "KMSMasterKeyID": "arn:aws:kms:us-east-1:111111111111:alias/prod-data"
        },
        "BucketKeyEnabled": true
      }]
    }'

Versioning and replication. Versioning keeps every version, so an overwritten or deleted photo can be restored, and replication needs it on both buckets. Task 1.3's replication rule copies new uploads to example-dr-uploads in us-west-2: SSE-KMS objects only replicate when opted in with a key in the destination Region, objects that existed before the rule need S3 Batch Replication, and deletes of specific versions are never replicated. Replication Time Control adds a 15-minute target with metrics. Product images can be rebuilt from the catalogue, so example-prod-assets isn't replicated; the DR plan is on the Disaster recovery on a budget page.

Lifecycle. upload-processor writes processed files to S3 Intelligent-Tiering, because some photos are re-read for years and others never (Task 4.1). It moves objects by their own access history, with no retrieval fees and no minimum duration, but objects under 128 KB are never tiered, so thumbnails effectively stay at Standard rates. The lifecycle rules below clean up the rest.

Expire raw uploads after 7 days, old versions after 30, and abandoned multipart uploads after 7 (lifecycle JSON for aws s3api put-bucket-lifecycle-configuration) 
{
  "Rules": [
    {
      "ID": "expire-raw-uploads",
      "Filter": { "Prefix": "incoming/" },
      "Status": "Enabled",
      "Expiration": { "Days": 7 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 1 }
    },
    {
      "ID": "processed-versions-and-multipart",
      "Filter": { "Prefix": "" },
      "Status": "Enabled",
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}

Incomplete multipart uploads are billed until aborted, and S3 Storage Lens flags those older than 7 days. Where files have a known pattern, such as delivery paperwork read for a month and kept for years, a transition rule to Glacier Instant Retrieval or Deep Archive is cheaper than Intelligent-Tiering, but mind the 90- and 180-day minimum durations and the per-object transition charge on millions of small files.

Object Lock only where a rule demands it. Order records in example-order-archive use compliance mode for seven years because nobody may delete them. Customer photos must be deletable when a customer closes the account, so the uploads bucket has versioning but no Object Lock, which can't be turned off once enabled.

Design decisions

Presigned URLs over identity pool credentials

The serverless API mentions a Cognito identity pool for photo uploads: it trades the user's token for temporary AWS credentials scoped to their own prefix. That works, but puts AWS credentials on the device and leaves key names to the client. Presigned URLs from upload-url give one key, one method and five minutes, the same for web and mobile, so the identity pool is only needed where the app calls other AWS services directly.

A queue from the event notification, EventBridge when consumers multiply

A direct notification to SQS is the simplest path with a prefix filter and retries. Sending S3 events to EventBridge instead (EventBridgeConfiguration in the same call, events with source aws.s3 and detail type Object Created) allows content filtering and several targets per event, such as an analytics feed or a moderation queue. The company would switch when a second team needs upload events.

The endpoint-only bucket policy, narrowed

Task 1.2 and the secure VPC page deny requests to example-prod-uploads that don't arrive through the prod VPC's gateway endpoint. Applied to everyone, that Deny would also block the customers' presigned PUTs (they come from the internet) and CloudFront's reads. So the endpoint condition stays on the application roles, while upload-url-role is limited to PutObject on incoming/* and CloudFront to GetObject on processed/* for one distribution.

Two buckets by data class

Company content and customer data differ in encryption, replication, retention and deletion rules. Separate buckets keep each policy simple: SSE-S3, no replication and long caches for assets; SSE-KMS, versioning, replication and signed URLs for uploads. The cost is a second origin and bucket policy.

Alternatives

Uploading through the API or web servers

Sending files through API Gateway hits the 10 MB payload limit and the 29-second timeout, and through the ALB and EC2 fleet it ties up instances and pays to move every byte twice. Direct uploads into S3 are free and scale without the servers.

EFS or FSx for shared files

EFS gives Linux instances a shared POSIX file system and FSx for Windows File Server gives SMB shares; they suit applications that need file semantics. For files that customers upload and browsers download over HTTP, S3 is far cheaper (US$0.023 against US$0.30 per GB-month in the standard classes) and works with CloudFront (Task 3.1, Task 4.1).

S3 website hosting or Amplify Hosting

An S3 website endpoint serves HTTP only and needs a public bucket, and CloudFront must treat it as a custom origin without OAC. Amplify Hosting packages build, CDN and HTTPS for a front-end team and is the least effort for a single-page app. For a private bucket, signed URLs and fine cache control, CloudFront with OAC is the answer.

Testing it

  1. Direct access deniedRequest a product image and a processed file by their S3 URLs: both must return 403. The same image through CloudFront returns 200, and a /files/ request without a signed URL returns 403.
  2. URL limitsUse a presigned URL after six minutes, with a different content type, and for a key outside incoming/: all three must fail. A request for an unsupported file type must be refused by upload-url.
  3. Processing and poison filesUpload a photo and confirm exactly one clean file and one thumbnail under processed/, and no new event from them. Upload a corrupt file: it is retried five times, lands in upload-events-dlq and the DLQ alarm fires.
  4. Replication and recoveryOverwrite a test photo and restore the previous version; check that the new object reaches example-dr-uploads within 15 minutes and that the replication metrics show no failures.

"Users upload large files through the web servers, which slows the application. Which solution meets these requirements with the LEAST operational overhead?" is presigned URLs for direct upload to S3. "Serve S3 content worldwide; users must not access the bucket directly" is CloudFront with origin access control. "Paid subscribers only, for many files" is signed cookies.
