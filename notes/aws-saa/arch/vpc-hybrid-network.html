Secure VPC and hybrid connectivity

The network under every other architecture page: a production VPC split into public, private and isolated subnets across three AZs, private paths to AWS services, layered filtering between the tiers, and a hub in the shared-network account that connects the VPCs and the head office.

Scenario and requirements

The highly available web application, the serverless API and order processing all run in the production account 111111111111 in us-east-1. This page is the network they sit in: the production VPC vpc-0prod11111111111, the shared-network account that owns the connections between VPCs, and the link to the head office. Its job is to let the right traffic in, keep the rest out and keep AWS service traffic off the internet (Task 1.2).

The requirements:

  • Only the load balancer faces the internet: application servers, containers and Aurora have no inbound path from it.
  • Losing one AZ doesn't cut off the others, including their outbound internet access (Task 2.2).
  • Calls to S3, DynamoDB and other AWS services stay private and don't pay NAT processing where they don't have to.
  • Staff in the head office reach internal tools over an encrypted link now, with a steadier private link later.
  • Room to grow: new VPCs join without re-addressing (Task 3.4).
  • No surprise network bills: NAT, cross-AZ and connection charges are chosen on purpose (Task 4.4).

Reused: vpc-0prod11111111111 with its security groups, app route tables, public NACL and S3 endpoint (Task 1.2); the app and database subnets and sg-0proxy1111111111 (the web application page); the shared-services VPC vpc-0shared1111111111 (Task 4.4). New on this page: the prod VPC range 10.1.0.0/16, the office range 172.16.0.0/16, the shared-network account 444444444444, which owns the transit gateway and vpc-0shared1111111111, and the flow-log bucket example-network-logs.

Status changes to know. A Regional NAT gateway (November 2025) is now an option next to one zonal NAT gateway per AZ. Route 53 Resolver is now called Route 53 VPC Resolver in newer documentation; the endpoints work the same way. Large-bandwidth VPN tunnels now carry up to 5 Gbps; 1.25 Gbps is the standard tunnel.

How it works

Three paths cross this network: a customer request coming in, an application call going out, and an office user reaching an internal tool. Steps marked AWS happen automatically.

  1. Inbound from customers
  2. Reach the ALBCustomerAfter CloudFront and AWS WAF, the request reaches web-alb in the public subnets on 443, passing the NACL and sg-0alb1111111111111.
  3. Forward to a targetAWSThe ALB sends the request by private IP to an instance or task in a private app subnet, where sg-0app1111111111111 accepts 8080 only from the ALB's group.
  4. Query the data tierAWSThe application connects through orders-proxy to Aurora in the isolated database subnets, which have only the local VPC route.
  5. Outbound from the application
  6. AWS services privatelyAWSCalls to S3 and DynamoDB follow the prefix-list route to the free gateway endpoints; calls to Secrets Manager and other services resolve, through private DNS, to interface endpoints in the same AZ.
  7. Internet through NATAWSA call to the payment provider follows 0.0.0.0/0 to the NAT gateway and out through the internet gateway; nothing outside can start a connection in.
  8. From the office
  9. Resolve the nameOffice userThe office DNS server forwards queries for the company's private zone to the VPC Resolver inbound endpoint in the shared-services VPC and gets back a private IP.
  10. Cross the linkAWSTraffic for 10.1.0.0/16 takes one of two IPsec tunnels to the transit gateway, which routes it to the prod VPC attachment; the security groups on the target decide the rest.
  11. Record itAWSVPC Flow Logs record accepted and rejected flows to S3 for every hop inside the VPC.

Build it

Step 1

Address plan and subnet tiers

Plan addresses before the first VPC. A VPC's IPv4 range is between a /16 and a /28 and can't be resized, only extended with secondary blocks. Overlapping ranges block peering, Direct Connect gateways and clean routing (Task 3.4). The prod VPC uses 10.1.0.0/16, inside the us-east-1 prod block 10.0.0.0/12 from Task 3.4, and the office keeps 172.16.0.0/16, so the two never collide. New VPCs take ranges from IPAM pools.

How the next VPC gets a non-overlapping range: a /20 taken automatically from the us-east-1 prod IPAM pool (AWS CLI, from Task 3.4) 
aws ec2 create-vpc --ipv4-ipam-pool-id ipam-pool-0prodeast1111111111 \
    --ipv4-netmask-length 20 \
    --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=orders-prod}]'

Three tiers in each of three AZs. Public subnets route 0.0.0.0/0 to the internet gateway and hold only the ALB's nodes (and zonal NAT gateways, if used). Private app subnets hold EC2 and ECS tasks and route the default route to NAT. Isolated database subnets have only the local route. A small dedicated subnet per AZ holds the transit gateway attachment. The main route table keeps only local routes, and each subnet is explicitly associated with its own custom table. Every subnet loses five addresses (a /24 gives 251).

Public IPv4 costs money. Every public IPv4 address costs US$0.005 an hour, in use or idle (Task 3.4). Nothing in the private tiers has one, and administrators use Session Manager instead of bastion hosts.

A guardrail above the routes. VPC Block Public Access, in ingress-only mode, blocks inbound internet traffic for every VPC in the Region while still allowing outbound through NAT gateways; it overrides security groups, NACLs and route tables. The ALB's public subnets are excluded, and an EC2 declarative policy enforces it across the organization (Task 1.2, Task 1.1).

Step 2

Egress and private access to AWS

NAT that survives an AZ. A zonal NAT gateway is redundant only inside its AZ, so the classic design is one per AZ, with each app route table pointing at the one in its own AZ. The Regional NAT gateway is one ID that expands across AZs as workloads appear and needs no public subnet; it doesn't support private NAT and is billed per AZ it runs in (Task 1.2). Prod uses the Regional NAT gateway for simpler routing.

Create a Regional NAT gateway for the prod VPC (AWS CLI, from Task 1.2) 
# Automatic mode manages the addresses and the AZ expansion for you
aws ec2 create-nat-gateway --vpc-id vpc-0prod11111111111 --availability-mode regional

Gateway endpoints for S3 and DynamoDB. They're free, work through a prefix-list route, and take the app tier's largest traffic (uploads and DynamoDB order data) off NAT. They reach only the same Region and can't be used from the office, peered VPCs or a transit gateway.

Add an S3 gateway endpoint to the three private app route tables (AWS CLI, from Task 1.2; DynamoDB uses the same form with com.amazonaws.us-east-1.dynamodb) 
aws ec2 create-vpc-endpoint --vpc-id vpc-0prod11111111111 \
    --vpc-endpoint-type Gateway \
    --service-name com.amazonaws.us-east-1.s3 \
    --route-table-ids rtb-0appa111111111111 rtb-0appb111111111111 rtb-0appc111111111111

Policies on both ends. An endpoint policy limits what can be done through the endpoint and never grants more than IAM and bucket policies allow. Here it allows only the company's buckets, so a compromised instance can't copy data to someone else's bucket; the uploads bucket in turn denies requests not arriving through vpce-0s3a1111111111111 (Task 1.2).

Endpoint policy for the S3 gateway endpoint: object access to the company's own buckets only (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CompanyBucketsOnly",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::example-prod-uploads", "arn:aws:s3:::example-prod-uploads/*",
        "arn:aws:s3:::example-order-archive", "arn:aws:s3:::example-order-archive/*"
      ]
    }
  ]
}

Interface endpoints for everything else. Secrets Manager, KMS, ECR and CloudWatch Logs are reached through interface endpoints (AWS PrivateLink): an elastic network interface in each chosen subnet, private DNS so code doesn't change, and a security group that allows 443 from the app tier. At US$0.01 per AZ-hour plus US$0.01 per GB, against NAT's US$0.045 per GB, they pay off on busy paths such as ECR pulls (Task 4.4).

Step 3

Layered filtering and flow logs

Security groups chained by reference. Security groups are stateful, allow-only and attached to each network interface. The ALB's group allows 443 from the internet (or from CloudFront's managed prefix list); the app group allows 8080 only from the ALB's group; sg-0proxy1111111111 allows 5432 only from the app group, and the database allows 5432 only from the proxy. References keep working as Auto Scaling replaces instances (Task 1.2).

Allow the app tier to receive traffic only from the load balancer (AWS CLI, from Task 1.2) 
aws ec2 authorize-security-group-ingress \
    --group-id sg-0app1111111111111 \
    --protocol tcp --port 8080 \
    --source-group sg-0alb1111111111111

NACLs as a coarse subnet guard. Network ACLs are stateless, numbered, first match wins, and can deny. The public subnets' NACL is where the company blocks an abusive range, because security groups have no deny rules. Return traffic must be allowed explicitly on ephemeral ports: Amazon Linux uses 32768–61000 while ELB, NAT gateways and Lambda use 1024–65535, so AWS suggests allowing 1024–65535.

Block one abusive range before the allow rule on the public subnets' NACL (AWS CLI, from Task 1.2) 
aws ec2 create-network-acl-entry --network-acl-id acl-0pub111111111111 \
    --ingress --rule-number 90 --protocol tcp --port-range From=443,To=443 \
    --cidr-block 203.0.113.0/24 --rule-action deny
aws ec2 create-network-acl-entry --network-acl-id acl-0pub111111111111 \
    --ingress --rule-number 100 --protocol tcp --port-range From=443,To=443 \
    --cidr-block 0.0.0.0/0 --rule-action allow

Network Firewall only if needed. Filtering outbound traffic by domain or intrusion prevention would mean AWS Network Firewall, in a firewall subnet per AZ or attached to the transit gateway (since June 2025). The company has no such requirement yet; DNS Firewall covers DNS-based exfiltration.

Flow logs for evidence. VPC Flow Logs record metadata about accepted and rejected traffic without affecting performance; they show a rule that is too strict and who sends traffic through NAT.

Record all traffic in the prod VPC to S3 with one-minute aggregation (AWS CLI; options checked on the create-flow-logs reference) 
aws ec2 create-flow-logs \
    --resource-type VPC \
    --resource-ids vpc-0prod11111111111 \
    --traffic-type ALL \
    --log-destination-type s3 \
    --log-destination arn:aws:s3:::example-network-logs/prod/ \
    --max-aggregation-interval 60
Step 4

The hub: Transit Gateway shared with RAM

A hub, not a mesh. Prod, staging, dev and the shared-services VPC all need the office, and some need shared services. Peering is one non-transitive link per pair; a transit gateway needs one attachment per VPC (Task 3.4). It lives in the shared-network account 444444444444, so the network team owns routing and the workload teams only attach. With default association off, each attachment goes into the right route table on purpose, and blackhole routes keep dev from prod.

In the shared-network account: a transit gateway that doesn't auto-associate attachments (AWS CLI, from Task 3.4) 
aws ec2 create-transit-gateway --description "us-east-1 hub" \
    --options AmazonSideAsn=64512,AutoAcceptSharedAttachments=disable,DefaultRouteTableAssociation=disable,DefaultRouteTablePropagation=disable,VpnEcmpSupport=enable,DnsSupport=enable

Share it, then attach. AWS RAM shares the transit gateway with the organization. Each attachment uses one subnet per AZ (only those AZs reach the hub), and each app route table gets a route for 172.16.0.0/16 to the transit gateway.

Share the transit gateway with the organization only, then attach the prod VPC from account 111111111111 (AWS CLI; options checked on the create-resource-share and create-transit-gateway-vpc-attachment references; replace TGW_ID, MANAGEMENT_ACCOUNT_ID and the attachment subnet IDs) 
# In 444444444444: share with every account in the organization, nobody outside it
aws ram create-resource-share --name tgw-us-east-1 \
    --resource-arns arn:aws:ec2:us-east-1:444444444444:transit-gateway/TGW_ID \
    --principals arn:aws:organizations::MANAGEMENT_ACCOUNT_ID:organization/o-exampleorg \
    --no-allow-external-principals

# In 111111111111: one small attachment subnet per AZ
aws ec2 create-transit-gateway-vpc-attachment \
    --transit-gateway-id TGW_ID \
    --vpc-id vpc-0prod11111111111 \
    --subnet-ids TGW_SUBNET_A TGW_SUBNET_B TGW_SUBNET_C

Security group references across a transit gateway work since September 2024, but only in inbound rules and only when enabled on the transit gateway and the attachment (Task 1.2). The deeper design, with segmented route tables, is the ANS Transit Gateway hub and spoke page.

Step 5

The office: VPN now, Direct Connect next, hybrid DNS

Site-to-Site VPN first. A VPN can be set up in minutes, is encrypted with IPsec, and every connection has two tunnels to different AWS endpoints, so the office router should run both. Ending it on the transit gateway rather than a virtual private gateway means it reaches every attached VPC and can use ECMP across tunnels with BGP, which a virtual private gateway can't (Task 3.4). A standard tunnel carries up to 1.25 Gbps; large-bandwidth tunnels carry up to 5 Gbps.

Connect the office router to the transit gateway with dynamic (BGP) routing (AWS CLI; options checked on the create-vpn-connection reference; OFFICE_CGW_ID is the customer gateway for the office router) 
aws ec2 create-vpn-connection \
    --type ipsec.1 \
    --customer-gateway-id OFFICE_CGW_ID \
    --transit-gateway-id TGW_ID \
    --tag-specifications 'ResourceType=vpn-connection,Tags=[{Key=Name,Value=office-vpn}]'

Direct Connect when volume and consistency justify it. Direct Connect gives consistent bandwidth and latency over a private link, but ordering takes weeks and it isn't encrypted by default. The plan is a transit VIF through a Direct Connect gateway to the transit gateway, keeping the VPN as backup; the transit gateway prefers Direct Connect routes over VPN routes for the same prefix. For encryption, run the VPN over Direct Connect or MACsec on a dedicated 10 Gbps or faster port (Task 1.2). The ANS resilient Direct Connect and encrypted hybrid pages go further.

Hybrid DNS. The VPC's built-in resolver, Route 53 VPC Resolver, can't be reached from the office directly. An inbound endpoint in vpc-0shared1111111111 gives the office DNS servers IP addresses to forward the company's private hosted zone to; an outbound endpoint with forwarding rules sends queries for the office's own domain back to its DNS servers. Rules are shared through AWS RAM, so one pair of endpoints serves every VPC (ANS hybrid DNS page).

Remote staff. Client VPN gives home workers' devices a VPN into the VPC; Verified Access gives users specific internal applications without a VPN, checking identity and device state on every request (ANS remote access).

Design decisions

Regional NAT gateway, plus endpoints to keep traffic off it

A zonal NAT gateway costs US$0.045 an hour plus US$0.045 per GB, and the Regional NAT gateway is billed per AZ it runs in, so it costs about the same as three zonal ones: it saves management, not money (Task 4.4). The real saving is what never touches NAT: free gateway endpoints for S3 and DynamoDB and interface endpoints for heavy service traffic. One shared NAT gateway saves hours but adds cross-AZ charges and an AZ single point of failure: dev only.

Transit Gateway over peering

Peering has no hourly or processing charge and same-AZ traffic is free, so it's the cheaper choice for two VPCs exchanging a lot of data. A transit gateway costs US$0.05 per attachment-hour plus US$0.02 per GB processed, but gives transitive routing, one place to attach the VPN and Direct Connect, and route tables for segmentation (Task 4.4). With four VPCs today and more coming, plus the office, the hub wins.

VPN first, Direct Connect when the numbers say so

A VPN costs US$0.05 per connection-hour, about US$36 a month, plus internet egress rates. A 1 Gbps dedicated Direct Connect port costs about US$219 a month and saves US$0.07 per GB on outbound traffic, so it pays for its port at roughly 3.1 TB out a month, before the carrier circuit and colocation (Task 4.4). Inbound data is free either way, so uploads into AWS don't count, and an idle port still bills.

Watching inter-AZ and DNS charges

Traffic between AZs costs US$0.01 per GB in each direction, as is traffic to a public IP inside the VPC, so tiers use private IPs. Resolver endpoints cost about US$182 a month each, which is why there is one shared pair. Cost Explorer usage types and Flow Logs show where the money goes.

Alternatives

A single shared egress VPC

With many VPCs, one egress VPC in the shared-network account can hold the NAT gateways, and spokes send 0.0.0.0/0 to the transit gateway. It saves NAT hours in every VPC but adds US$0.02 per GB of transit gateway processing, so a busy VPC like prod can be cheaper with its own NAT (Task 3.4). The ANS centralized egress page has the full design.

AWS Cloud WAN for a larger network

Cloud WAN builds a global network from one core network policy, with segments such as prod and dev mapped to attachments by tag. It suits many Regions; with two, the company stays on Transit Gateway (ANS multi-Region network).

VPC Lattice or shared VPCs for service-to-service traffic

VPC Lattice connects services across VPCs and accounts at the application layer, priced per service-hour and US$0.025 per GB, without routing whole networks together (Task 4.4; ANS Lattice service network). Shared VPCs, subnets shared through RAM, reduce the number of VPCs to connect at all (ANS VPC sharing). Neither replaces the office link.

Testing it

  1. No path from the internetNetwork Access Analyzer must find no path from the internet gateway to the app or database subnets; Reachability Analyzer from an app instance to Aurora on 5432 must pass.
  2. AZ loss keeps egressDuring an AZ zonal shift or a FIS test that disrupts one AZ's subnets, instances in the other AZs must still reach the payment provider through NAT.
  3. Endpoints actually usedUpload a test object from an app instance and check the flow logs and the NAT gateway's bytes: S3 traffic must not appear on NAT. A request to the uploads bucket from outside the endpoint must be denied.
  4. NACL return trafficAfter any NACL change, load-test the ALB: rejected flows in the logs on ports 1024–65535 mean the ephemeral range is missing.
  5. Tunnel failoverTake one VPN tunnel down from the office router: traffic must continue on the second tunnel, and a CloudWatch alarm on tunnel state must fire. Once Direct Connect is live, disable its BGP session and confirm traffic moves to the VPN.
  6. Hybrid DNSFrom an office workstation, resolve an internal name in the private hosted zone; from an app instance, resolve an office server's name through the outbound rule.

"Private instances must reach S3 without internet access. Which solution meets these requirements MOST cost-effectively?" is an S3 gateway endpoint, not a NAT gateway or an interface endpoint. "Private instances lost internet access when one AZ failed" is a NAT gateway per AZ or a Regional NAT gateway. "Connect dozens of VPCs and the data center with the LEAST operational overhead" is a transit gateway. "An encrypted connection to the office that can be set up quickly" is Site-to-Site VPN; "consistent performance for large daily transfers" is Direct Connect, with a VPN as the low-cost backup. "On-premises servers must resolve private hosted zone names" is a VPC Resolver inbound endpoint.
