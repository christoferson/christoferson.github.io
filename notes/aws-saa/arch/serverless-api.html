Serverless API

The company's mobile API rebuilt in us-east-1 with no servers to run: an API Gateway REST API with Cognito sign-in and AWS WAF, Lambda functions that can each touch only their own DynamoDB table, throttling and caching at the front door, and slow work handed to a queue.

Scenario and requirements

The mobile app's API has been served by the web tier's ALB and EC2 fleet (the highly available web application). Its traffic is spiky: busy evenings and promotions, almost nothing overnight. The company rebuilds it as a serverless API in the production account 111111111111 in us-east-1, following the pattern Task 2.1 names: API Gateway, then Lambda, then DynamoDB. Customers already sign in with an Amazon Cognito user pool (Task 1.1).

The requirements:

  • No servers to manage: capacity follows requests, and idle hours cost close to nothing (Task 4.2).
  • Only signed-in customers reach their own cart and orders; customers never become IAM users.
  • Protected front door: HTTPS on the company's domain, SQL injection and floods filtered, and a runaway client unable to exhaust capacity for everyone else (Task 1.2).
  • Least privilege: each function can reach only the data it owns.
  • Safe retries: a phone on a flaky network that resends "place order" must not create two orders.
  • Fast reads, recoverable data: single-digit-millisecond reads, and tables restorable after a bad deployment (Task 3.3).

Reused from the task pages: the on-demand carts table keyed by customer_id and item_id (Task 3.3) and the rate-based WAF rule (Task 1.2). New on this page: the REST API mobile-api with stage prod on api.example.com; functions products-api, cart-api and order-api with roles named after them; tables mobile-products and order-requests; the queue order-intake; and the web ACL mobile-api-acl. Placeholders such as API_ID and USER_POOL_ID stand for generated IDs.

Status changes to know. The AWS X-Ray SDKs and daemon entered maintenance mode on 25 February 2026: instrument new code with OpenTelemetry (AWS Distro for OpenTelemetry or the CloudWatch agent). AWS App Runner is closed to new customers; Amazon ECS Express Mode is the suggested replacement. AWS WAF Classic has reached end of support, so web ACLs are AWS WAF.

How it works

A customer opens the app, views products, edits the cart and places an order. Steps marked AWS happen automatically.

  1. Sign in and call the API
  2. Sign inMobile appThe app signs the customer in to the Cognito user pool and receives JWTs; it sends the token in the Authorization header of every call to https://api.example.com.
  3. FilterAWSAWS WAF on the prod stage applies the managed rule groups and the per-IP rate rule before API Gateway does any work.
  4. Authorize and throttleAWSThe Cognito user pool authorizer validates the token; stage and method throttles and the account limit decide whether the request runs or gets HTTP 429.
  5. Cached readsAWSGET /products is answered from the stage cache when a fresh copy exists, without invoking Lambda.
  6. Run the request
  7. InvokeLambdaAPI Gateway invokes the matching function synchronously; cart-api reads and writes carts under a role that allows only that table.
  8. Place an orderLambdaorder-api writes the request to order-requests with a condition that the request ID is new, sends a message to order-intake, and returns 202 Accepted at once.
  9. Process laterAWSThe order processing consumers (the Decoupled order processing architecture) read order-intake at their own pace; the app polls GET /orders/{id} for the status.

Build it

Step 1

Sign-in: Cognito user pool authorizer

Customers live in a user pool, not in IAM. The user pool handles sign-up, sign-in, MFA and social or SAML federation, and issues JWTs that API Gateway can check (Task 1.1). An identity pool is only needed where the app calls AWS directly, such as photo uploads to S3; the API itself needs no AWS credentials on the phone.

A Cognito authorizer on the REST API. API Gateway validates the token itself, so no authorizer function runs and no code checks signatures. Each method then sets its authorization type to the authorizer.

Create the user pool authorizer on mobile-api (AWS CLI; replace API_ID and USER_POOL_ID) 
aws apigateway create-authorizer \
    --rest-api-id API_ID \
    --name mobile-customers \
    --type COGNITO_USER_POOLS \
    --provider-arns 'arn:aws:cognito-idp:us-east-1:111111111111:userpool/USER_POOL_ID' \
    --identity-source 'method.request.header.Authorization'

The function reads the customer's ID from the validated claims that API Gateway passes in the request context, never from the request body, so a customer can't ask for someone else's cart.

"Let app users sign up and sign in, and protect the API with their tokens" is a Cognito user pool with a user pool authorizer (REST) or a JWT authorizer (HTTP API). "Give app users temporary AWS credentials" is a Cognito identity pool. Creating IAM users for customers is always wrong.

Step 2

Front door: REST API, domain and WAF

REST API rather than HTTP API. REST APIs have the features this design needs: response caching, AWS WAF, request validation, usage plans and canary deployments. HTTP APIs are cheaper and simpler with native JWT authorizers, but have none of those (Task 2.1). The API uses a Regional endpoint; REST endpoints can also be edge-optimized (the default) or private.

Timeouts. REST integrations time out at 29 seconds by default; since June 2024 Regional and private REST APIs can request a longer timeout, while HTTP APIs stop at 30 seconds. Payloads are limited to 10 MB. Anything slower belongs on a queue (Step 5).

Custom domain with ACM. api.example.com uses a free public ACM certificate that renews automatically. It must be in the API's Region, and an edge-optimized endpoint (like CloudFront) needs it in us-east-1; here both mean us-east-1 (Task 1.2). A Route 53 alias points the name at the API's domain.

AWS WAF on the stage. A regional web ACL attaches to a REST API stage, but not to an HTTP API, and each resource has one web ACL. mobile-api-acl holds the Core rule set and the per-IP rate rule from Task 1.2 (2,000 requests per IP, blocked above that).

Attach the regional web ACL to the prod stage (AWS CLI; the resource ARN of a REST API stage has no account ID) 
aws wafv2 associate-web-acl \
    --web-acl-arn arn:aws:wafv2:us-east-1:111111111111:regional/webacl/mobile-api-acl/WEB_ACL_ID \
    --resource-arn arn:aws:apigateway:us-east-1::/restapis/API_ID/stages/prod

API keys and usage plans are not security or cost controls. API keys identify a client for metering; they don't authenticate anyone, and AWS calls usage plan throttles and quotas best effort, not hard limits (Task 4.4). Authenticate with Cognito, IAM or a Lambda authorizer, filter abuse with AWS WAF, and watch spend with AWS Budgets.

Step 3

Functions: roles, concurrency, arm64

One function per resource, one table per role. Each function has its own execution role allowing only the actions it uses on its own table, plus the AWS managed basic execution policy for logs. order-api also gets sqs:SendMessage on order-intake. If a function is compromised, the damage stops at its table.

cart-api-role: item actions on the carts table only (IAM policy JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CartsTableOnly",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem",
        "dynamodb:Query"
      ],
      "Resource": "arn:aws:dynamodb:us-east-1:111111111111:table/carts"
    }
  ]
}

Memory, architecture and timeout. Memory (128 MB to 10,240 MB) also sets CPU, so raising it often lowers cost for CPU-bound code; Lambda Power Tuning or Compute Optimizer finds the right size (Task 3.2). The functions run on arm64 (Graviton), which costs 20% less per GB-second. The timeout sits well below the API's 29 seconds, so a stuck call fails fast instead of holding concurrency.

Size cart-api and cap its run time far below the API timeout (AWS CLI, as on Task 3.2) 
aws lambda update-function-configuration --function-name cart-api \
    --memory-size 1024 --timeout 10

Concurrency. An account has 1,000 concurrent executions per Region by default (a soft quota shared by all functions), and each function can add 1,000 environments every 10 seconds (Task 2.1). Reserved concurrency caps a function and guarantees it that share, so a flood of order calls can't starve the cart; the account must keep at least 100 unreserved.

Reserve (and cap) 200 concurrent executions for order-api (AWS CLI) 
aws lambda put-function-concurrency \
    --function-name order-api \
    --reserved-concurrent-executions 200

Cold starts. A cold start happens when Lambda creates a new execution environment. Provisioned concurrency keeps environments initialized, at a cost, and can be scheduled with Application Auto Scaling for the evening peak. SnapStart (Java 11+, Python 3.12+ and .NET 8+, on published versions) restores a snapshot of an initialized environment instead (Task 3.2).

Observability. Powertools for AWS Lambda adds structured logging, metrics and an idempotency utility. For tracing, new code uses OpenTelemetry rather than the X-Ray SDKs, which are in maintenance mode. The DVA guide covers handler code, layers and tracing (DVA Task 1.2, DVA Task 4.2).

Step 4

Data: DynamoDB keys, idempotency, recovery

Keys from the access patterns. DynamoDB is designed around the queries it must answer. "Show my cart" is a Query on customer_id in carts. "Show product P" is a GetItem on product_id in mobile-products. "Status of order request R" is a GetItem on request_id in order-requests. All three keys have high cardinality, so no partition gets hot; each partition handles at most 3,000 read and 1,000 write units per second (Task 3.3).

On-demand capacity. On-demand is DynamoDB's default and recommended mode: pay per request, nothing to plan, and a table instantly handles up to double its previous peak. Spiky mobile traffic is the case it was made for.

The order request table: on-demand, keyed by the client's request ID (AWS CLI; same form as the carts table on Task 3.3) 
aws dynamodb create-table --table-name order-requests \
    --attribute-definitions AttributeName=request_id,AttributeType=S \
    --key-schema AttributeName=request_id,KeyType=HASH \
    --billing-mode PAY_PER_REQUEST

Conditional writes for idempotency. The app generates a request ID once per order and resends the same ID on every retry. order-api writes with a condition that no item with that key exists yet. A retry fails the condition, so the function returns the original order's status instead of queueing a second order (Task 2.2).

Record an order request only if the ID is new (AWS CLI; a duplicate returns ConditionalCheckFailedException) 
aws dynamodb put-item --table-name order-requests \
    --item '{"request_id": {"S": "REQUEST_ID"}, "customer_id": {"S": "CUSTOMER_ID"}, "status": {"S": "RECEIVED"}}' \
    --condition-expression "attribute_not_exists(request_id)"

TTL and point-in-time recovery. TTL deletes expired items within a few days at no charge, so old order requests and abandoned carts clean themselves up. Point-in-time recovery restores a table to any second in a window of 1 to 35 days, for US$0.20 per GB-month (Task 4.3); it protects against a bad deployment that corrupts data.

Turn on point-in-time recovery, then expire old order requests by their epoch-seconds attribute expires_at (AWS CLI) 
aws dynamodb update-continuous-backups --table-name order-requests \
    --point-in-time-recovery-specification PointInTimeRecoveryEnabled=true

aws dynamodb update-time-to-live --table-name order-requests \
    --time-to-live-specification Enabled=true,AttributeName=expires_at

No database secrets. DynamoDB is reached with the execution role's IAM permissions and needs no connections or passwords, so there is nothing to rotate. Secrets Manager is needed only for a third-party credential, such as a payment provider's key, read by the one function that uses it.

Step 5

Throttling, caching and async work

Throttling in layers. API Gateway uses a token bucket: the rate refills it, the burst is its size, and excess requests get HTTP 429. Limits apply in order: usage plan limits per client and method, then per-method stage limits, then the account's 10,000 requests per second per Region (burst 5,000) (Task 4.4). The stage limits keep mobile-api inside the share of the account and of Lambda concurrency it was sized for.

The stage cache. REST APIs can cache responses per stage, with a 300-second default TTL, up to 3,600 seconds (Task 2.1). Product summaries change rarely and are the same for every customer, so GET /products is cached; carts and orders are per customer and are not. The cache cluster is sized from 0.5 GB upwards and is an extra charge.

Stage throttles for all methods, a 0.5 GB stage cache, and caching for GET /products only (AWS CLI; ~1 encodes the slash in the resource path) 
aws apigateway update-stage --rest-api-id API_ID --stage-name prod \
    --patch-operations \
    'op=replace,path=/*/*/throttling/rateLimit,value=1000' \
    'op=replace,path=/*/*/throttling/burstLimit,value=2000' \
    'op=replace,path=/cacheClusterEnabled,value=true' \
    'op=replace,path=/cacheClusterSize,value=0.5' \
    'op=replace,path=/~1products/GET/caching/enabled,value=true' \
    'op=replace,path=/~1products/GET/caching/ttlInSeconds,value=300'

DAX or API caching. The stage cache saves the whole request: no Lambda invocation and no table read. DAX caches DynamoDB reads in microseconds, eventually consistent only, but the function still runs. Here API caching is enough; DAX would fit if many different keys were read repeatedly.

Hand slow work to SQS. Payment, stock and email take longer than a phone should wait and may fail and retry. order-api records the request, sends one message to order-intake, and returns 202. The consumers scale on queue depth with a capped concurrency, so a sale can't flood the downstream systems (Task 2.1); the queue design is the Decoupled order processing architecture. API Gateway can also send to SQS directly with no function, a pattern in AWS's serverless-patterns sample code.

"Clients get 429 Too Many Requests" is API Gateway throttling (stage, method, usage plan or account limit) or Lambda concurrency, not a WAF block (403). "A request takes 2 minutes and the API times out" is a design to move behind a queue, not a longer Lambda timeout: the API's 29 seconds is the limit the client sees.

Design decisions

Serverless instead of the ALB and EC2 fleet

Task 4.2's worked example shows the trade-off: an API at a steady 20 requests per second (200 ms, 512 MB) costs about US$97 a month on Lambda against US$36 for two Fargate tasks, but at 1 request per second with bursts Lambda costs about US$5. The mobile API is the second kind, and the ALB alone costs US$0.0225 per hour plus LCUs before any instance runs (Task 4.2). API Gateway's request charge adds to Lambda's, so recheck with Pricing Calculator if traffic becomes steady.

REST API features over HTTP API price

The company pays more per request for caching, WAF and request validation on the stage. If those were not needed, an HTTP API with a JWT authorizer would be the lower-cost, lower-latency answer.

Reserved concurrency as a bulkhead

Reserving 200 for order-api takes 200 out of the shared pool for everyone else, and throttles orders beyond it. That is the point: order bursts queue up as 429s and retries rather than starving the cart and product functions. Request a higher Regional quota before launch if the sum gets close to 1,000.

On-demand tables, with provisioned as the later option

On-demand costs US$0.625 per million writes and US$0.125 per million reads in us-east-1. Provisioned capacity with auto scaling becomes cheaper once its average utilization is high (Task 4.3 estimates about 29% by its own arithmetic), and Database Savings Plans also cover DynamoDB (Task 4.3). Switch only when months of metrics show steady traffic.

Alternatives

HTTP API with a JWT authorizer

Cheaper and simpler, with native JWT validation of the same user pool tokens, but no WAF, caching, usage plans or request validation, and Regional endpoints only (Task 2.1). A fit for internal or low-risk APIs.

JWT authorizer on an HTTP API that trusts the user pool (AWS CLI; replace HTTP_API_ID, APP_CLIENT_ID and USER_POOL_ID) 
aws apigatewayv2 create-authorizer \
    --name mobile-customers-jwt \
    --api-id HTTP_API_ID \
    --authorizer-type JWT \
    --identity-source '$request.header.Authorization' \
    --jwt-configuration Audience=APP_CLIENT_ID,Issuer=https://cognito-idp.us-east-1.amazonaws.com/USER_POOL_ID

ALB with Lambda targets

An ALB can route paths to Lambda functions, authenticate users with an authenticate-cognito action and carry AWS WAF (Task 1.2). It has no per-client throttling, usage plans or response caching, and it bills by the hour even when idle, so it suits an existing ALB gaining a few functions rather than a new API.

ECS on Fargate behind an ALB

The company's order and catalog APIs already run this way. Fargate removes servers too, suits long requests, held connections and steady load (cheaper with a Compute Savings Plan), but pays for tasks around the clock and scales in tasks rather than per request. App Runner, once the simplest container option, is closed to new customers.

Testing it

  1. AuthorizationCall each method with no token, an expired token and another customer's token: the first two must get 401 from API Gateway without invoking Lambda, and the third must return only the caller's own cart.
  2. Least privilegeFrom cart-api's role, try to read order-requests: it must be denied. Review IAM Access Analyzer's unused access findings for the three roles (Task 1.1).
  3. IdempotencySend the same POST /orders with the same request ID three times: one item in order-requests, one message on order-intake, the same response each time.
  4. Load and throttlingRamp a load test past the stage rate limit: the excess must get 429, cart latency must hold while orders are capped by reserved concurrency, and the Lambda Throttles metric must show where requests were refused.
  5. Edge protection and cachingSend a SQL injection pattern and a burst above 2,000 requests from one IP: WAF must block both with 403. Repeat GET /products: the CacheHitCount metric must rise while the function's invocations stay flat.
  6. RestoreRestore order-requests to a point in time as a new table in staging, and confirm the items and the time it takes.

"A mobile backend has unpredictable traffic and must scale automatically. Which solution meets these requirements with the LEAST operational overhead?" is API Gateway, Lambda and DynamoDB on-demand, not EC2 Auto Scaling or containers. "Protect the API from SQL injection and limit requests per IP" is AWS WAF with a rate-based rule on a REST API. "Lambda functions overwhelm a downstream system at peak" is reserved concurrency or an SQS buffer. "Most cost-effective authentication for app users of an HTTP API" is a Cognito user pool with a JWT authorizer.
