Reference architecture

Disaster recovery on a budget

The company must keep taking orders if the whole of us-east-1 is lost, without paying for a second production site. Each workload gets its own recovery target and the cheapest strategy that meets it: live replicas for order data, a small standby for the order path, and tested backups for everything else, all recoverable in us-west-2.

Scenario and requirements

Everything on the other architecture pages runs in the production account 111111111111 in us-east-1: the web application behind CloudFront, the serverless mobile API, order processing and customer uploads. Multi-AZ already handles the loss of one AZ. The board now asks what happens if the whole Region is unavailable, and wants an answer that doesn't double the AWS bill. us-west-2 is the DR Region (Task 2.2).

Targets first. RTO is the longest acceptable time until service is back; RPO is how much recent data the business can afford to lose. They are business decisions, set per workload, and they pick the strategy. AWS's four strategies, in order of rising cost and falling recovery time:

  • Backup and restore: only backups live in the DR Region; RPO since the last backup, recovery in hours. Lowest cost.
  • Pilot light: data replicates continuously; application servers are off or not deployed. Seconds to minutes of data lost, recovery in tens of minutes.
  • Warm standby: a scaled-down but working copy of production. Seconds of data, recovery in minutes, and it can take some traffic at once.
  • Multi-site active/active: full copies serving live traffic. Near-zero RPO and RTO for an outage, at the highest cost.

The company sets one tier per workload:

WorkloadTarget and strategy
Ordering: web-asg, mobile-api, carts, order-requests, Aurora orders-eastRTO 1 hour, RPO a few seconds (the Task 2.2 target): warm standby at minimum size, data replicating live
Order processing: order-intake, order-fulfilmentSame RTO; deployed but idle in us-west-2, which costs almost nothing because it is serverless
Customer uploads: example-prod-uploadsRPO 15 minutes: Cross-Region Replication to example-dr-uploads, already in place
Internal tools: the EC2 reporting server and its EBS volumesRTO 24 hours, RPO 24 hours: backup and restore

Reused from the SAA pages: web-asg, web-lt, orders-east, orders-proxy, web-cache and the CloudFront distribution (web application); mobile-api, carts, order-requests and order-intake (serverless API); order-fulfilment (order processing); the shared-network account 444444444444 and its transit gateway (VPC and hybrid network); the backup plan prod-daily, vaults prod-vault and dr-vault (Task 1.3); the global cluster orders-global, its secondary orders-west and the web-dr load balancer (Task 2.2). New on this page: the security account 333333333333 and its vault security-dr-vault in us-west-2; the DR VPC range 10.16.0.0/16; the CloudFormation stack web-dr; the origin name origin.example.com; and a customer managed key with the alias alias/prod-data in us-west-2 (aliases are Regional).

Status changes to know. CloudEndure Disaster Recovery was replaced by AWS Elastic Disaster Recovery. Route 53 ARC is now Amazon Application Recovery Controller (ARC); its readiness check closed to new customers on 30 April 2026, while routing controls, zonal shift and Region switch (August 2025) continue. Aurora Global Database's "managed planned failover" is now called switchover. Launch configurations are deprecated: use launch templates.

How it works

The recovery path when us-east-1 is lost. Steps marked AWS run all the time without anyone acting.

  1. Always on
  2. ReplicateAWSAurora Global Database copies orders-east to orders-west at the storage layer, DynamoDB global tables copy carts and order-requests, and S3 replicates uploads, each with lag of about a second (S3 within 15 minutes).
  3. Copy backupsAWSAWS Backup takes the nightly backups and copies them to dr-vault in us-west-2 and to the locked security-dr-vault in the security account.
  4. The event
  5. Detect and declareOn-call leadRoute 53 health checks and CloudWatch alarms show us-east-1 failing; the lead declares a Regional event and starts the runbook, rather than letting a false alarm move production.
  6. Promote the dataDBAAn unplanned failover makes orders-west the writer, accepting the replication lag as lost data. The DynamoDB replicas in us-west-2 already accept writes.
  7. Scale outPlatform teamUpdating stack web-dr raises the standby web fleet to production size and turns on the order queue consumers.
  8. Move trafficAWSRoute 53 failover records answer with the us-west-2 load balancer and API once the primary is unhealthy; CloudFront and the mobile app follow the names.
  9. Restore the restPlatform teamThe reporting server is rebuilt from its latest copy in dr-vault; later, a planned switchover brings production home.

Build it

Step 1

Backups copied out of the Region

Every workload needs backups, even the replicated ones. Replication copies a bad deployment's damage or a deleted table as faithfully as good data, so Aurora and DynamoDB get backups as well as replicas. For the reporting server, backups are the whole DR plan. AWS Backup assigns resources by tag, so tagging a resource backup=daily puts it in the plan (Task 1.3).

Two copies away from production. The prod-daily plan from Task 1.3 already copies to dr-vault in us-west-2 for the Region loss. A second copy action sends each recovery point to the security account, for the case where prod's account itself is compromised. Cross-account copies need the accounts in one organization with cross-account backup turned on in the management account, a destination vault policy allowing backup:CopyIntoBackupVault, and a customer managed source key shared with the destination. The destination vault can't be the default vault, and backups in cold storage can't be copied across accounts. The external vault's ARN carries its Region, so one copy action can land in another account and Region.

prod-daily with a second copy action to the security account's vault in us-west-2 (backup plan JSON for aws backup create-backup-plan; the first copy action is unchanged from Task 1.3) 
{
  "BackupPlan": {
    "BackupPlanName": "prod-daily",
    "Rules": [
      {
        "RuleName": "daily-0500-utc",
        "TargetBackupVaultName": "prod-vault",
        "ScheduleExpression": "cron(0 5 ? * * *)",
        "StartWindowMinutes": 60,
        "CompletionWindowMinutes": 480,
        "Lifecycle": { "DeleteAfterDays": 35 },
        "CopyActions": [
          {
            "DestinationBackupVaultArn": "arn:aws:backup:us-west-2:111111111111:backup-vault:dr-vault",
            "Lifecycle": { "DeleteAfterDays": 35 }
          },
          {
            "DestinationBackupVaultArn": "arn:aws:backup:us-west-2:333333333333:backup-vault:security-dr-vault",
            "Lifecycle": { "DeleteAfterDays": 35 }
          }
        ]
      }
    ]
  }
}

Lock the last copy. security-dr-vault uses Vault Lock in compliance mode: after a grace time of at least three days nobody, not the root user and not AWS, can delete recovery points early or remove the lock. A logically air-gapped vault is the stronger option, always in compliance mode and shareable through AWS RAM for restores. Restore time is part of RTO: volumes restored from EBS snapshots load lazily and large database restores can take hours, which is why the order data doesn't rely on backups for the Region loss.

Step 2

Live data: Aurora and DynamoDB

Aurora Global Database for orders. A cross-Region snapshot copy would cost less, but restoring it takes hours and loses everything since the snapshot, which misses a one-hour RTO and a seconds RPO. Aurora Global Database replicates at the storage layer with lag typically under a second, supports up to 10 secondary Regions, and gives a global writer endpoint that follows the primary (Task 2.2, Task 3.3). The existing orders-east becomes the primary of orders-global, and orders-west joins as a read-only secondary with one instance.

Turn orders-east into a global database, then add the secondary cluster in us-west-2 (AWS CLI; options checked on the create-global-cluster and create-db-cluster references) 
aws rds create-global-cluster \
    --global-cluster-identifier orders-global \
    --source-db-cluster-identifier arn:aws:rds:us-east-1:111111111111:cluster:orders-east

# Run in us-west-2: an encrypted secondary needs a KMS key in its own Region
aws rds create-db-cluster --region us-west-2 \
    --db-cluster-identifier orders-west \
    --engine aurora-postgresql \
    --global-cluster-identifier orders-global \
    --kms-key-id arn:aws:kms:us-west-2:111111111111:alias/prod-data \
    --db-subnet-group-name DB_SUBNET_GROUP \
    --vpc-security-group-ids DB_SG_ID

Like any Aurora cluster, orders-west starts empty of instances; one reader instance is added with create-db-instance. It serves product and order reads in us-west-2 all the time, so the standby web tier can show the catalogue even before promotion. An RDS Proxy like orders-proxy is created in us-west-2 too, because a proxy belongs to one Region.

DynamoDB global tables for carts and order requests. Adding a replica turns an existing table into a global table (multi-Region eventual consistency, the default), with no performance impact on the source. Every replica accepts writes, replication usually takes under a second, and conflicts resolve as last writer wins. The SLA is 99.999%.

Add a us-west-2 replica to carts (AWS CLI; the JSON form of --replica-updates from the update-table reference); repeat for order-requests 
aws dynamodb update-table --table-name carts \
    --replica-updates '[{"Create": {"RegionName": "us-west-2"}}]'

Two details matter here. Point-in-time recovery is not synchronized between replicas, so it is turned on again for each us-west-2 replica. Conditional writes are checked against the item in the local Region, so the idempotency check in order-requests only holds while all requests for one order go to one Region, which active-passive routing ensures. Uploads already replicate to example-dr-uploads with Replication Time Control (uploads page).

Step 3

Compute and network ready to go

Images in the DR Region. AMIs and container images are Regional. An EC2 Image Builder pipeline can bake the web AMI and copy each new version to us-west-2; a one-off copy looks like this. Amazon ECR replication copies container images for the ECS services the same way.

Copy the current web AMI to us-west-2, encrypted with the key there (AWS CLI, run in the destination Region; options from the copy-image reference) 
aws ec2 copy-image --region us-west-2 \
    --source-region us-east-1 \
    --source-image-id AMI_ID \
    --name web-ami-dr \
    --encrypted \
    --kms-key-id alias/prod-data
Replicate every repository in the registry to us-west-2 (replication.json for aws ecr put-replication-configuration --replication-configuration file://replication.json) 
{
  "rules": [
    {
      "destinations": [
        { "region": "us-west-2", "registryId": "111111111111" }
      ]
    }
  ]
}

The DR VPC as code. The us-west-2 network, the web tier and the order queue come from the same CloudFormation templates as production, deployed as stack web-dr. The VPC uses 10.16.0.0/16, a range chosen here outside the us-east-1 prod block 10.0.0.0/12 and the office range 172.16.0.0/16, so it can attach to a transit gateway in us-west-2 from the shared-network account and peer back to us-east-1 without overlapping (Task 3.4). The office VPN or Direct Connect also needs a path to us-west-2, or staff lose the internal tools along with the Region.

Fragment of the web-dr template: the DR VPC and a web fleet whose size is a parameter (CloudFormation YAML; subnets, route tables, NAT and endpoints omitted) 
Parameters:
  WebMinSize:
    Type: Number
    Default: 2          # warm standby; production size is 6
  WebAmiId:
    Type: AWS::EC2::Image::Id
Resources:
  DrVpc:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: 10.16.0.0/16
      EnableDnsSupport: true
      EnableDnsHostnames: true
  WebLaunchTemplate:
    Type: AWS::EC2::LaunchTemplate
    Properties:
      LaunchTemplateName: web-lt
      LaunchTemplateData:
        ImageId: !Ref WebAmiId
  WebAsg:
    Type: AWS::AutoScaling::AutoScalingGroup
    Properties:
      AutoScalingGroupName: web-asg
      MinSize: !Ref WebMinSize
      MaxSize: "30"
      LaunchTemplate:
        LaunchTemplateName: web-lt
        Version: !GetAtt WebLaunchTemplate.LatestVersionNumber
      VPCZoneIdentifier: [!Ref AppSubnetA, !Ref AppSubnetB, !Ref AppSubnetC]

Queues and functions. SQS queues are Regional and not replicated, so the same template creates order-intake, its DLQ and the order-fulfilment state machine in us-west-2. Messages still inside us-east-1's queue wait there until the Region returns, but every accepted order is also in the global table order-requests, so a reconciliation job can find and resubmit any that never completed. mobile-api, its Lambda functions, a Regional custom domain for api.example.com with an ACM certificate in us-west-2, and a regional web ACL are deployed too: idle API Gateway and Lambda cost nothing. Service quotas in us-west-2 are raised to production levels now, not during the event.

Step 4

Failover: database first, then traffic

Failover records. CloudFront is global, so it keeps serving; what moves is its origin. The distribution's origin is origin.example.com, a pair of Route 53 failover records: primary the us-east-1 load balancer, secondary web-dr in us-west-2, each alias evaluating target health (the Task 2.2 change batch, with this name). api.example.com gets the same pair for the two API custom domains. Each load balancer needs a certificate for the origin name in its own Region. Health checks and failover answers are data plane operations, which keep working when a Region's management APIs are impaired.

Database before traffic. Route 53 may move traffic before anyone has acted, but writes fail until orders-west is the writer. During that gap the us-west-2 tier serves reads from the secondary, and the order consumers in us-west-2 stay switched off so orders wait in the queue instead of failing into the DLQ. The runbook's first step is the unplanned failover, which promotes the secondary and accepts the replication lag as lost data.

Unplanned failover of orders-global to us-west-2, accepting the lag as data loss (AWS CLI, run in us-west-2; from the failover-global-cluster reference) 
aws rds failover-global-cluster --region us-west-2 \
    --global-cluster-identifier orders-global \
    --target-db-cluster-identifier arn:aws:rds:us-west-2:111111111111:cluster:orders-west \
    --allow-data-loss

Then the platform team updates stack web-dr with WebMinSize=6 and production capacity for the ECS services, enables the queue consumers, and confirms the health checks. Applications connected through the global writer endpoint need no connection-string change. ARC routing controls are the higher-assurance on/off switch for this decision and Region switch can run the whole plan across accounts; they are more to set up and run, so the company starts with Route 53 failover and a written runbook (Task 2.2).

Step 5

Failback

Coming home is planned, not rushed. When us-east-1 recovers, the old orders-east must be back in orders-global as a secondary and in sync before anything moves back. Once it is in sync, a switchover moves the primary with no data loss. The DynamoDB replicas resynchronize by themselves, and S3 replication from example-dr-uploads back to the primary bucket is needed only if customers uploaded during the event.

Planned switchover back to us-east-1 with no data loss (AWS CLI; the Task 2.2 command pointed the other way) 
aws rds switchover-global-cluster \
    --global-cluster-identifier orders-global \
    --target-db-cluster-identifier arn:aws:rds:us-east-1:111111111111:cluster:orders-east

Traffic returns when the us-east-1 load balancer passes its health checks again, and web-dr is scaled back to WebMinSize=2. The incident review records the measured RTO and RPO against the targets.

Design decisions

Warm standby at minimum size, not pilot light at zero

A pilot light with web-asg at zero is cheaper, but the first launch happens during the event, when launch templates, AMIs, quotas and user data have never run in that Region. Two small web instances that pass health checks every day prove the stack works and take some traffic at once, which keeps the one-hour RTO safe. Everything serverless is warm for free.

What runs all the time, by tier

Backup and restore pays for stored copies and cross-Region transfer only (Task 4.1). Pilot light adds the replicated data stores: Aurora secondary storage and one instance, global table replicated writes, S3 replica storage. Warm standby adds the two web instances, a load balancer and a NAT gateway. Copying only what DR needs to us-west-2 and keeping the copies' retention short keeps backup cost down; Aurora backups beyond the free allowance cost less than RDS backups (Task 4.3).

Elastic Disaster Recovery for the reporting server

Restoring the reporting server from AWS Backup meets its 24-hour target at the lowest cost. If that target tightened, AWS Elastic Disaster Recovery would replicate the server at block level into a low-cost staging area in us-west-2 and launch it full size on recovery, for RPOs of seconds and RTOs of minutes, with drills and failback and no code changes. It is a pilot light for whole servers.

A human declares the event

AWS notes that many teams start Regional failover manually, because automatic failover on a false alarm causes an outage of its own. Route 53 fails traffic over automatically, but the database promotion that makes it useful is a person's decision taken from the runbook.

Alternatives

Multi-site active/active

Both Regions serve customers all the time, with latency routing and a write strategy such as DynamoDB global tables or Aurora write forwarding. Recovery is near instant, but it pays for full capacity in both Regions and needs the application to handle conflicts. For a one-hour RTO, it buys more than the business asked for. The SAP multi-Region DR architecture covers this at Professional depth.

Multi-AZ in one Region only

Three AZs survive an AZ loss with no action, which is the right first step and what the other pages build. But every copy shares one Region's control plane and fate, so it can't meet a requirement to survive the loss of the Region, however many AZs are used.

Elastic Disaster Recovery for everything

DRS protects EC2 servers with no code changes, so it suits the reporting server or a lift-and-shift estate. It doesn't replicate Aurora, DynamoDB, S3, Lambda or API Gateway, which are most of this company's workload; their own replication features are cheaper and faster for them.

Testing it

  1. Restore testsAWS Backup restore testing restores the reporting server and a DynamoDB table from dr-vault on a schedule and records how long it took. The time must fit the 24-hour RTO, and Backup Audit Manager must show every tagged resource copied cross-Region.
  2. Database game daySwitch orders-global to us-west-2 and back during a quiet hour, and confirm that the application reconnects through the global writer endpoint. Watch replication lag and confirm the DynamoDB replicas have PITR on.
  3. Traffic failover drillForce the primary origin unhealthy in staging and time how long until origin.example.com and api.example.com answer from us-west-2. Fault Injection Service experiments can pause global table replication to test the application's behaviour.
  4. Scale-out rehearsalUpdate web-dr to production size and run a load test against us-west-2. Launch failures here usually mean a quota or missing AMI, both cheap to fix before a real event.

"Recover in another Region within hours at the LOWEST cost" is backup and restore with AWS Backup copies and infrastructure as code. "Data must be current, servers can start on demand" is pilot light. "Recover within minutes and take some traffic immediately" is warm standby. "Multi-Region relational database with an RPO of seconds" is Aurora Global Database. "Replicate on-premises or EC2 servers for DR with the LEAST operational overhead" is AWS Elastic Disaster Recovery.
