Task 3.1: Determine high-performing and/or scalable storage solutions

Matching storage to the speed and growth a workload needs: which EBS volume type delivers the IOPS and throughput, which file system serves a fleet or an HPC cluster, how to push S3 to very high request rates and long-distance uploads, how each service grows, and how on-premises systems reach cloud storage.

Overview

Task 3.1

Determine high-performing and/or scalable storage solutions.

Task 2.1 chose between object, file and block storage; Task 2.2 made it durable. This task is about numbers: how many IOPS, how much throughput, what latency, and how far each option grows. Performance questions give a requirement ("20,000 IOPS", "sub-millisecond latency", "thousands of uploads per second from around the world") and expect the cheapest storage that meets it. Two things changed in 2025 that make older answers wrong: gp3 volumes now reach 80,000 IOPS, and S3 objects can be 50 TB.

Running example. The company's Aurora database is managed, but a reporting server on EC2 runs a self-managed PostgreSQL copy that needs fast block storage; the web fleet shares product images; a data science team trains models on terabytes of clickstream data in S3; customers in Asia and Europe upload large videos to a bucket in us-east-1; and the head office still has a file server and tape backups.

Storage that meets performance demands

Skill 3.1.1Determining storage services and configurations that meet performance demands

Performance vocabulary

IOPS, throughput and latency

IOPS (input/output operations per second) measures how many small reads and writes a disk handles, which matters for databases with random access. Throughput (MiB/s) measures how much data moves per second, which matters for large sequential reads and writes such as logs, backups and analytics. Latency is how long each operation takes. A workload described as "transactional" needs IOPS and low latency; one described as "big data" or "streaming large files" needs throughput.

gp3: the default answer

Since September 2025 a gp3 volume reaches 64 TiB, 80,000 IOPS and 2,000 MiB/s (it was 16 TiB, 16,000 IOPS and 1,000 MiB/s). Every gp3 volume includes 3,000 IOPS and 125 MiB/s whatever its size, and you buy more of each separately: up to 500 IOPS per GiB (so 80,000 IOPS needs at least 160 GiB) and 0.25 MiB/s per provisioned IOPS (so 2,000 MiB/s needs at least 8,000 IOPS). It doesn't burst, so it sustains what you provision, and it costs about 20% less per GiB than gp2. AWS now says to choose io2 only when one volume needs more than 80,000 IOPS or 2,000 MiB/s, or sub-millisecond latency.

gp2, io1 and io2

gp2 ties performance to size: 3 IOPS per GiB (minimum 100, maximum 16,000), and volumes under 1 TiB burst to 3,000 IOPS from a credit balance, which runs out under sustained load (watch BurstBalance). To get IOPS from gp2 you buy capacity you may not need; that's the classic reason to move to gp3, which Elastic Volumes does with no downtime. Since April 2025 every io2 volume is io2 Block Express: up to 256,000 IOPS on Nitro instances (non-Nitro instances reach 32,000). io1 (up to 64,000 IOPS at 50 IOPS per GiB) is older, and AWS recommends io2 instead. Only io1 and io2 support Multi-Attach (up to 16 Nitro instances in one AZ, with a cluster-aware file system).

Answers that say "more than 16,000 IOPS, so io1 or io2" are out of date: gp3 now covers up to 80,000 IOPS and 2,000 MiB/s more cheaply. Choose io2 Block Express for more than that, for sub-millisecond latency, or for Multi-Attach.

The instance is part of the answer

Volume performance is capped by the instance's own EBS bandwidth: you get the lower of what the instance supports and what the volumes provide. Current instance types are EBS-optimized by default; smaller sizes can burst to their maximum EBS bandwidth for 30 minutes a day and then fall back to a baseline. To go beyond one volume, RAID 0 stripes several volumes and adds up their IOPS and throughput (losing any one volume loses the array; AWS doesn't recommend RAID 5, 6 or 1 on EBS), but with today's gp3 and io2 limits one larger volume is often enough.

Volumes restored from snapshots

A volume created from a snapshot loads each block from S3 the first time it's read, so it's slow until fully read. Three fixes: fast snapshot restore gives full performance at creation (per snapshot and AZ, at most five snapshots per Region, charged hourly); Provisioned Rate for Volume Initialization fills the volume at a set 100 to 300 MiB/s, so you know when it will finish; or read every block yourself with fio or dd.

Restore the reporting database volume from a snapshot and initialize it at 300 MiB/s (AWS CLI) 
aws ec2 create-volume --availability-zone us-east-1a \
    --snapshot-id snap-0report111111111 --volume-type gp3 \
    --iops 12000 --throughput 500 \
    --volume-initialization-rate 300

Instance store

The fastest disk, and the most temporary

Instance store volumes are NVMe disks physically attached to the host, included in the instance price. Storage-optimized instances deliver millions of random IOPS (the largest i7i and i8g sizes list over 7 million random reads per second), far beyond any EBS volume. The data survives a reboot but is lost when the instance stops, hibernates, terminates, changes type or loses its disk, so use it for caches, buffers, scratch data, and databases that replicate across nodes themselves.

"Millions of IOPS for temporary data" or "the database replicates across nodes, so local loss is acceptable" points to instance store. "Highest IOPS on persistent storage" points to io2 Block Express. "Cost-effective SSD with tunable IOPS" points to gp3. "Large sequential reads at low cost" points to st1.

Amazon EFS performance

Performance mode and throughput mode

An EFS file system has a performance mode, fixed at creation: General Purpose, which AWS recommends for every file system, or Max I/O, now labelled previous generation, with higher latency and no support for One Zone or Elastic throughput. It also has a throughput mode:

  • Elastic (recommended, the console default): scales automatically with demand and charges per GB transferred. Best for spiky or unpredictable workloads. In the largest Regions a file system reaches 60 GiB/s of reads, 5 GiB/s of writes and 2.5 million read IOPS; one client reaches 1,500 MiB/s with the current EFS mount helper.
  • Provisioned: a fixed throughput you choose, independent of storage size, for known sustained loads. After a change you must wait 24 hours to switch back or decrease it.
  • Bursting: throughput grows with the amount stored (50 MiB/s per TiB baseline, bursts to 100 MiB/s per TiB from credits). Small file systems run out of credits quickly.

Read latency is about 1 ms on the Standard storage class (tens of milliseconds on Infrequent Access and Archive). Watch the defaults: the console picks Elastic, but the API and CLI still default to Bursting.

Shared file system for the web fleet: General Purpose, Elastic throughput, encrypted (AWS CLI) 
aws efs create-file-system --creation-token web-shared-01 \
    --performance-mode generalPurpose --throughput-mode elastic \
    --encrypted --tags Key=Name,Value=web-shared

"EFS throughput drops after a busy period" on a small file system is the Bursting mode running out of credits. Switch to Elastic (or Provisioned); adding dummy data to raise the baseline is an old workaround.

Amazon FSx performance

FSx for Lustre

FSx for Lustre is a parallel file system for high-performance computing, machine learning and media processing: sub-millisecond latency, millions of IOPS, and up to terabytes per second across thousands of clients. A data repository association links it to an S3 bucket, loading objects as files on first access and exporting results back. Deployment types:

  • Scratch: temporary storage with no replication, for short jobs where data can be reloaded from S3.
  • Persistent: replicated within the AZ for long-running workloads; Persistent 2 offers 125 to 1,000 MB/s per TiB on SSD, or an Intelligent-Tiering storage class that grows and shrinks automatically, with throughput bought separately in 4,000 MB/s units.

GPU clusters reach up to 1,200 Gbps per client with Elastic Fabric Adapter and GPUDirect Storage.

FSx for Windows File Server, NetApp ONTAP and OpenZFS

FSx for Windows File Server serves SMB shares with Active Directory; you choose a throughput capacity (up to 12 GB/s and 400,000 IOPS in the largest Regions) and SSD (sub-millisecond, for databases and heavy workloads) or HDD (cheaper, single-digit milliseconds, for home directories). FSx for NetApp ONTAP serves NFS, SMB and iSCSI from an SSD tier with sub-millisecond latency and tiers cold data to an elastic capacity pool; second-generation Single-AZ file systems scale out to 12 HA pairs. FSx for OpenZFS serves NFS with a few hundred microseconds of latency from its read cache, up to 400,000 IOPS and 10 GB/s.

"HPC or ML training on data in S3, sub-millisecond, hundreds of GB/s" points to FSx for Lustre (Scratch for short jobs, Persistent for long-running). "Shared Linux file system for a web fleet" points to EFS with Elastic throughput. "Windows file shares for a high-I/O SQL Server" points to FSx for Windows on SSD.

Amazon S3 performance

Request rates scale with prefixes

S3 supports at least 3,500 PUT, COPY, POST or DELETE and 5,500 GET or HEAD requests per second per partitioned prefix, with no limit on the number of prefixes. Spreading objects over ten prefixes (for example clicks/2026-11-09/shard-0/ to shard-9/) supports about 55,000 reads per second. Scaling happens gradually, so during a sudden ramp S3 may return HTTP 503 Slow Down, which SDKs retry. Keep compute in the same Region as the bucket, open many connections in parallel, and remember that SSE-KMS adds KMS requests that count against KMS quotas (S3 Bucket Keys reduce them, Task 1.3).

Multipart upload and byte-range fetches

A single PUT uploads at most 5 GB; larger objects, up to the new 50 TB maximum (December 2025), need multipart upload, which AWS recommends for anything over 100 MB. Parts are 5 MiB to 5 GiB, up to 10,000 of them, uploaded in parallel, with only failed parts retried. Downloads parallelize the same way with byte-range fetches (the Range header). The AWS CLI switches to multipart at 8 MB by default; the CRT-based transfer client and S3 Transfer Manager in the SDKs do the parallelism for you. Incomplete multipart uploads are billed until aborted, so add a lifecycle rule to clean them up (Task 1.3).

Tune the AWS CLI for large uploads (AWS CLI configuration) 
aws configure set default.s3.preferred_transfer_client crt
aws configure set default.s3.multipart_threshold 64MB
aws configure set default.s3.multipart_chunksize 64MB

S3 Transfer Acceleration

For clients far from the bucket's Region, Transfer Acceleration sends uploads and downloads to the nearest CloudFront edge location and then over AWS's network to the bucket, which AWS says can be 50% to 500% faster for large objects over long distances. It's enabled per bucket, uses the endpoint bucket-name.s3-accelerate.amazonaws.com, needs virtual-hosted-style requests and a bucket name without periods, takes up to 20 minutes to start working, and charges only for transfers it actually speeds up. The documentation now lists 15 supported bucket Regions, including us-east-1.

Turn on Transfer Acceleration for the video upload bucket, then use it from the CLI 
aws s3api put-bucket-accelerate-configuration --bucket example-video-uploads \
    --accelerate-configuration Status=Enabled
aws configure set default.s3.use_accelerate_endpoint true

S3 Express One Zone

For the lowest latency, S3 Express One Zone stores objects in directory buckets in one AZ you choose, next to your compute, with consistent single-digit-millisecond access, up to 10 times faster than S3 Standard and request costs up to 80% lower. Each directory bucket handles 200,000 reads and 100,000 writes per second by default (up to 2 million reads with a support request), without prefix limits. Requests authenticate with short-lived session credentials from CreateSession, which the SDKs handle. Because data is in one AZ, it suits ML training, analytics and other data that can be re-created.

File access to S3 data

Mountpoint for Amazon S3 mounts a bucket as a Linux file system with high read throughput, good for data lakes and training data, but it can't modify existing files and isn't POSIX-complete. S3 Files (2026), built on EFS, gives a full shared NFS file system over a bucket with locking and POSIX permissions. For HPC, FSx for Lustre linked to the bucket is the classic answer.

"Users worldwide upload large files to one bucket slowly" points to Transfer Acceleration with multipart upload. "Uploads of multi-GB files fail and must restart" points to multipart upload. "503 Slow Down at high request rates" points to more prefixes. "Single-digit-millisecond object access for ML training" points to S3 Express One Zone.

Closed to new customers. S3 Select (SQL queries inside one object) is no longer available to new customers; use Athena or filter in the client. S3 Object Lambda has been limited to existing customers and selected partners since 7 November 2025.

Storage that scales for future needs

Skill 3.1.2Determining storage services that can scale to accommodate future needs

Elastic by design

S3 and EFS grow on their own

When growth is uncertain, the simplest answer is storage with nothing to provision. S3 stores unlimited objects and data, with request rates that scale per prefix. EFS grows and shrinks to petabytes as files are added and removed, and with Elastic throughput its performance grows with demand too. S3 Files and Mountpoint extend that elasticity to file access. The FSx for Lustre and FSx for OpenZFS Intelligent-Tiering storage classes and the FSx for ONTAP capacity pool are elastic as well.

Provisioned, but resizable

Amazon EBS with Elastic Volumes

An EBS volume has a fixed size (up to 64 TiB for gp3 and io2, 16 TiB for gp2, io1, st1 and sc1), but Elastic Volumes lets you increase the size, change the type, and change IOPS and throughput while the volume stays attached and in use. The old rule of waiting six hours between changes is gone: you can make up to four modifications per volume in a rolling 24 hours, each after the previous one completes. Two limits remain: a volume can't be made smaller (create a smaller one and copy the data), and after a size increase you must extend the partition and file system yourself. Beyond one volume's limits, add volumes (or RAID 0) within the instance's EBS bandwidth, or move to a larger instance.

Move the reporting volume from gp2 to gp3 with more IOPS and throughput, without detaching it (AWS CLI) 
aws ec2 modify-volume --volume-id vol-0report111111111 \
    --volume-type gp3 --iops 16000 --throughput 1000

Amazon FSx

  • FSx for Windows File Server: storage can only grow (by at least 10%, six hours apart, up to 64 TiB); throughput capacity can go up or down at any time.
  • FSx for Lustre: SSD and HDD storage can only grow (six hours apart); Intelligent-Tiering storage is elastic.
  • FSx for NetApp ONTAP: the capacity pool is elastic, second-generation file systems can now also shrink SSD capacity, and Single-AZ 2 scales out to 12 HA pairs.

"Reduce the size of an EBS volume" can't be done with Elastic Volumes; it needs a new, smaller volume and a data copy. The same is true of FSx for Windows storage. Plan EBS sizes with growth in mind, or choose EFS or S3 when shrinking matters.

"Storage needs will grow unpredictably and nobody should have to manage capacity" points to S3 or EFS. "The database volume needs more IOPS now, without downtime" points to Elastic Volumes (gp2 to gp3, or more IOPS on gp3 or io2).

Hybrid storage

The task's knowledge list includes hybrid storage: on-premises systems using cloud storage, and data moving between them.

AWS Storage Gateway

Cloud storage behind familiar protocols

Storage Gateway runs on premises (as a VMware, Hyper-V, KVM or Nutanix virtual machine, or a hardware appliance) or on EC2, and gives local applications standard storage protocols backed by AWS, with a local cache for low-latency access to recent data:

  • S3 File Gateway: NFS and SMB file shares whose files are stored as objects in S3, so cloud applications can use the same data and S3 features (lifecycle, versioning, replication) apply.
  • Volume Gateway: iSCSI block volumes. Cached volumes keep the primary data in S3 and only frequently used data locally (up to 32 TiB per volume); stored volumes keep all data locally and back it up asynchronously to S3 as EBS-compatible snapshots (up to 16 TiB per volume).
  • Tape Gateway: a virtual tape library for existing backup software, archiving virtual tapes to S3 Glacier Flexible Retrieval or Glacier Deep Archive, which replaces physical tapes without changing backup jobs.

Closed to new customers. Amazon FSx File Gateway (low-latency on-premises access to FSx for Windows File Server) is no longer available to new customers; access FSx for Windows directly over Direct Connect or VPN instead. The AWS Snow Family no longer accepts new customers either: for offline transfers AWS points to AWS Data Transfer Terminal, physical sites where you bring your own devices and upload over 100 Gbps links.

Moving data

AWS DataSync

DataSync copies data online between on-premises NFS, SMB, HDFS or object storage, other clouds, and S3, EFS or any FSx file system, with encryption, integrity checks and incremental transfers. On premises it uses an agent (a VM). A task moves up to 10 Gbps with an agent (5 Gbps without one), and more throughput comes from running tasks in parallel, over Direct Connect if the internet link is the bottleneck. Enhanced mode transfers in parallel with virtually unlimited file counts; Basic mode is limited to tens of millions of items per run, and a task's mode can't be changed later.

One Enhanced-mode task copying the office file share to S3 (AWS CLI) 
aws datasync create-task \
    --source-location-arn arn:aws:datasync:us-east-1:111111111111:location/loc-0smbshare1111111 \
    --destination-location-arn arn:aws:datasync:us-east-1:111111111111:location/loc-0s3archive111111 \
    --task-mode ENHANCED --name office-share-to-s3

Other hybrid options

AWS Transfer Family (Task 2.1) receives partner files over SFTP, FTPS, FTP or AS2 into S3 or EFS. EFS and every FSx file system can be mounted from on premises over Direct Connect or VPN, with throughput limited by the link's latency. S3 on Outposts provides the S3 API on an Outposts rack in your own data center for data that must stay on site, and Outposts also offers local EBS volumes. AWS's DataSync guidance sums up the usual pairing: DataSync to migrate data, then S3 File Gateway for ongoing low-latency on-premises access.

"On-premises applications need NFS or SMB access to data stored in S3" points to S3 File Gateway. "Replace physical backup tapes without changing backup software" points to Tape Gateway. "iSCSI storage with most data in AWS" points to Volume Gateway cached volumes. "Migrate hundreds of terabytes from NAS to EFS or S3 over the network" points to DataSync.

Key takeaways

  • gp3 is the default block volume: 3,000 IOPS and 125 MiB/s included, up to 80,000 IOPS, 2,000 MiB/s and 64 TiB since September 2025 (500 IOPS per GiB, 0.25 MiB/s per IOPS). gp2 ties IOPS to size and bursts on credits.
  • io2 Block Express (all io2 since April 2025): 256,000 IOPS, 4,000 MiB/s, under 500 microseconds, 99.999% durable, Multi-Attach. Choose it beyond gp3's limits or for sub-millisecond latency. st1 (500 MiB/s) and sc1 (250 MiB/s) are HDD for sequential data and can't boot.
  • Instance EBS bandwidth caps volume performance; RAID 0 adds volumes together. Snapshot-restored volumes are slow until initialized: fast snapshot restore (5 per Region) or Provisioned Rate for Volume Initialization (100 to 300 MiB/s). Instance store gives millions of IOPS but loses data on stop.
  • EFS: General Purpose mode (Max I/O is previous generation) with Elastic throughput (up to 60 GiB/s reads); the CLI still defaults to Bursting. FSx for Lustre for HPC and ML (Scratch or Persistent, S3-linked); FSx for Windows on SSD for heavy SMB; ONTAP and OpenZFS for NAS.
  • S3: 3,500 writes and 5,500 reads per second per prefix, so spread prefixes; multipart above 100 MB (required above 5 GB, objects up to 50 TB); byte-range fetches; Transfer Acceleration for distant clients; Express One Zone for single-digit milliseconds. S3 Select and Object Lambda are closed to new customers.
  • Growth: S3 and EFS are elastic; EBS grows online with Elastic Volumes (four changes per 24 hours, never smaller); FSx for Windows storage only grows; ONTAP second generation can now shrink SSD.
  • Hybrid: S3 File Gateway (NFS and SMB over S3), Volume Gateway (iSCSI, cached or stored), Tape Gateway (virtual tapes to Glacier); DataSync for online migration (10 Gbps per task); Data Transfer Terminal replaces Snowball for new customers; FSx File Gateway is closed to new customers.
