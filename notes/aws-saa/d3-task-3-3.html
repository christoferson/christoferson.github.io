Overview

Task 3.3

Determine high-performing database solutions.

Database questions describe an access pattern and a pain point: "reports slow down checkout", "writes are throttled at peak", "the same product pages are read millions of times", "an Oracle database must move to open source". Read replicas and caches answer read problems; a bigger writer, better keys or sharding answer write problems; the right engine and type answer most of the rest. Task 2.1 introduced replicas and caching strategies, and Task 2.2 covered Multi-AZ, global databases and RDS Proxy; this page goes deeper into configuration, capacity and choice.

Running example. Orders live in Aurora PostgreSQL in us-east-1; finance runs heavy month-end reports; the catalog is read far more than it's written; carts and sessions live in DynamoDB; product pages are cached; and a legacy warehouse system on Oracle is being moved to PostgreSQL.

Configuring read replicas

Skill 3.3.1Configuring read replicas to meet business requirements

RDS read replicas

How many, and how they replicate

RDS builds a replica from a snapshot of the source (which must have automated backups on) and then keeps it current with the engine's own asynchronous replication. A source can have up to 15 replicas for MySQL, MariaDB, PostgreSQL, Oracle and SQL Server (AWS recommends at most 5 for Oracle and SQL Server, to limit lag) and 3 for Db2. Replicas are billed as normal instances; replication traffic is free within a Region and charged across Regions. RDS doesn't add replicas automatically.

  • Instance class and storage can differ from the source (a gp3 replica of an io2 source, for example), but AWS recommends the same or larger compute, and scaling replicas when you scale the source, so they keep up.
  • Writable replicas: only MySQL and MariaDB replicas can be made writable; the others must be promoted.
  • Cascading replicas (a replica of a replica): MySQL, MariaDB and PostgreSQL 14.1+, up to three levels for MySQL. This offloads replication work from the source.
  • Multi-AZ replicas: a replica can have its own standby, so the replica itself survives an AZ failure.
  • Mounted replicas (Oracle) and standby replicas (Db2) don't accept reads; they exist for cross-Region DR.

Cross-Region replicas

A cross-Region replica serves reads close to users in another Region, provides DR, and helps migrate between Regions. You create it from the destination Region, naming the source by ARN and, for an encrypted source, a KMS key in the destination Region (Task 1.3). For MySQL and MariaDB, you can create one cross-Region replica and then further replicas from it in that Region, paying cross-Region transfer once. If the source is deleted, cross-Region replicas are promoted, except PostgreSQL ones, which stop.

Create a read replica of the catalog database (RDS for MySQL) in us-west-2, encrypted with a key there, as its own Multi-AZ deployment (AWS CLI, run in the destination Region) 
aws rds create-db-instance-read-replica --region us-west-2 \
    --db-instance-identifier catalog-replica-west \
    --source-db-instance-identifier arn:aws:rds:us-east-1:111111111111:db:catalog-mysql \
    --db-instance-class db.r8g.xlarge \
    --kms-key-id arn:aws:kms:us-west-2:111111111111:key/KEY_ID \
    --multi-az

Lag

Replication is asynchronous, so a replica can return slightly old data. Watch the ReplicaLag metric (seconds); heavy writes, an undersized replica or long queries on the replica increase it. Applications that must read their own write immediately should read from the primary.

Aurora replicas and endpoints

Reader, custom and instance endpoints

Aurora Replicas (up to 15) share the cluster volume, so lag is usually well under 100 ms. Applications connect through endpoints:

  • The cluster endpoint always points to the writer.
  • The reader endpoint spreads connections over the replicas, not individual queries: a long-lived connection pool sticks to the replicas it first connected to. With no replicas, it connects to the writer.
  • Custom endpoints (up to five per cluster) group chosen instances, for example two large replicas reserved for finance reports, so analytics never competes with the application's reads.
  • Instance endpoints reach one specific instance.

Aurora Auto Scaling adds and removes replicas (0 to 15) with target tracking on average reader CPU or connections, which suits read traffic that varies through the day. Monitor AuroraReplicaLag.

"Month-end reports slow down the application's reads" points to a custom endpoint on dedicated, larger Aurora replicas. "Read traffic varies, replicas should follow it" points to Aurora Auto Scaling. "Users in Europe need fast local reads of a US database" points to a cross-Region read replica or an Aurora Global Database secondary.

DynamoDB has no read replicas. Reads scale with capacity (and eventually consistent reads cost half as much as strongly consistent ones), with DAX for microsecond caching, and with global tables for other Regions.

Designing database architectures

Skill 3.3.2Designing database architectures

Start from the access pattern

Read-heavy, write-heavy, spiky or analytical

  • Read-intensive: read replicas or Aurora replicas behind reader or custom endpoints, a cache (ElastiCache) in front, DAX for DynamoDB, and eventually consistent reads where acceptable.
  • Write-intensive: replicas don't help, because every write still goes to one writer. Scale the writer up (larger instance, io2 Block Express storage, RDS Optimized Writes), shard with Aurora PostgreSQL Limitless Database, use DynamoDB with well-distributed partition keys, or buffer bursts in SQS or Kinesis (Task 3.2).
  • Spiky or unpredictable: Aurora Serverless, DynamoDB on-demand, ElastiCache Serverless, Aurora DSQL.
  • Analytical (large scans and aggregations): a replica or custom endpoint for reports, Aurora MySQL parallel query, or move analytics to a data warehouse (Redshift) or Athena, keeping the transactional database for transactions.

"Writes are slow, add read replicas" is the classic wrong answer. Replicas only add read capacity. Write bottlenecks need a bigger or faster writer, sharding, a different database type, or a queue to smooth bursts.

Capacity planning for RDS

Instance classes

RDS instance classes mirror EC2's: db.m general purpose, db.r, db.x and db.z memory optimized (databases benefit most from memory, which holds the working set), db.t burstable for development and test only, and Graviton versions (db.m8g, db.r8g, and the newer db.m9g) for better price performance. Classes with local NVMe (the d versions, such as db.r8gd) enable RDS Optimized Reads for MySQL, which puts temporary tables and sorts on the local disk for up to 2x faster complex queries. RDS Optimized Writes for MySQL doubles write throughput on supported classes by skipping the doublewrite buffer.

Storage

RDS storage is EBS-based: gp3 (recommended general purpose) and io2 Block Express (recommended Provisioned IOPS, up to 256,000 IOPS with sub-millisecond latency) are current; gp2 and io1 are previous generation; magnetic storage is gone. gp3 includes 3,000 IOPS and 125 MiB/s, rising to 12,000 IOPS and 500 MiB/s included once the volume is at least 400 GiB (200 GiB for Oracle), when RDS stripes it across volumes. The instance class's own EBS limit caps what you actually get, whatever you provision. Volumes reach 64 TiB (256 TiB for Oracle and SQL Server with extra storage volumes). Storage autoscaling, enabled by setting a maximum, adds storage when free space falls to 10%, up to four times in 24 hours; it never shrinks storage.

Aurora capacity choices

  • Storage grows automatically, now up to 256 TiB on recent engine versions (128 TiB on older ones), and you pay for what you use.
  • Aurora I/O-Optimized charges nothing for I/O in exchange for higher instance and storage prices; choose it when I/O is at least 25% of the Aurora bill. Aurora Standard charges per million I/O requests. You can switch to I/O-Optimized once every 30 days.
  • Aurora Serverless scales each instance in steps as small as 0.5 ACU (one ACU is about 2 GiB of memory), from 0 (paused) up to 256 ACUs for Aurora MySQL or 384 for Aurora PostgreSQL; provisioned and serverless instances can be mixed in one cluster.
  • Aurora PostgreSQL Limitless Database shards tables across many Aurora instances behind routers, for millions of write transactions per second in one database.
  • Fast cloning creates a copy-on-write copy of a cluster in minutes, for testing or analytics, without copying the data.

Monitoring performance

Performance Insights reached end of life on 31 July 2026; its users were moved to CloudWatch Database Insights, whose Standard mode shows database load and top SQL and whose Advanced mode adds per-query statistics, execution plans and lock analysis. Enhanced Monitoring adds operating-system metrics; key CloudWatch metrics include ReadIOPS, WriteLatency, DiskQueueDepth and DatabaseConnections.

Connections and proxies

Connections are a limited resource

Each database connection uses memory, so the default max_connections is derived from the instance's memory (roughly 630 for MySQL on an 8 GiB instance, about 60 on a db.t3.micro). Thousands of short-lived connections, typically from Lambda, exhaust it. The fixes: connection pooling in the application, RDS Proxy to pool and share connections and speed failover (Task 2.2), or the RDS Data API for Aurora, which runs SQL over HTTPS with no connection to manage at all. DynamoDB and Aurora DSQL are reached through signed HTTPS requests, so there's no connection pool to exhaust, which is one reason DynamoDB pairs so well with Lambda.

Placement

Near the application, spread for safety

Latency between AZs is single-digit milliseconds, and within one AZ lower still, so applications perform best when they talk to a database in the same Region and use Multi-AZ for safety rather than spreading one transaction across Regions. For users in other Regions, serve reads locally from cross-Region replicas, Aurora Global Database secondaries, DynamoDB global tables or ElastiCache Global Datastore (Task 2.2), and keep writes in one place unless the database is built for multi-Region writes (DynamoDB global tables, Aurora DSQL).

"Lambda functions cause too many database connections" points to RDS Proxy (or the Data API for Aurora). "Unpredictable workload, relational, scale to near zero" points to Aurora Serverless. "I/O charges are a large part of the Aurora bill" points to Aurora I/O-Optimized. "Write throughput beyond one Aurora writer" points to Limitless Database.

Choosing a database engine

Skill 3.3.3Determining an appropriate database engine (for example, MySQL compared with PostgreSQL)

The engines on RDS and Aurora

Open-source and commercial engines

RDS runs six engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server and Db2. Aurora offers MySQL- and PostgreSQL-compatible editions (AWS's guide credits Aurora MySQL with up to five times the throughput of standard MySQL) and Aurora DSQL. The commercial engines need a licence, either included in the hourly price or brought by you (BYOL), and are chosen when an application depends on them.

Special cases

  • RDS Custom (Oracle and SQL Server) gives operating-system and administrator access for legacy or packaged applications that need customization RDS doesn't allow, while AWS still automates backups and patching.
  • Babelfish for Aurora PostgreSQL accepts SQL Server's wire protocol and T-SQL on port 1433, so SQL Server applications can move to Aurora PostgreSQL with few code changes and no driver change.
  • Version lifecycle: when an engine version leaves RDS standard support, databases are automatically enrolled in paid RDS Extended Support for up to three years unless you upgrade or opt out. RDS for MySQL 8.0 left standard support on 31 July 2026, so MySQL 8.4 is now the current major version; RDS for PostgreSQL 13 left on 28 February 2026.

Migrating between engines

Homogeneous and heterogeneous migrations

A homogeneous migration keeps the engine (MySQL to RDS for MySQL or Aurora MySQL). Use the engine's native tools (dump and restore, native backups, replication, or an Aurora read replica of an RDS for MySQL or PostgreSQL database that you then promote), AWS DMS, or DMS homogeneous data migrations, which run those native tools serverlessly. A heterogeneous migration changes the engine (Oracle or SQL Server to PostgreSQL) and takes two steps:

  1. Convert the schemaDMS Schema Conversion (managed, in the console, built on the AWS SCT engine, now with generative AI for code it can't convert by rule) or the desktop AWS Schema Conversion Tool converts tables, views, stored procedures and functions, and reports what needs manual work.
  2. Move the dataAWS DMS copies the data with a full load, then keeps the target in sync with change data capture (CDC) until you cut over, so the source stays in use with minimal downtime.

DMS runs on a replication instance you size, or as DMS Serverless, which scales capacity units automatically. Its task types are full-load, cdc and full-load-and-cdc.

Full load plus ongoing replication from the Oracle warehouse to Aurora PostgreSQL (AWS CLI) 
aws dms create-replication-task \
    --replication-task-identifier warehouse-to-aurora \
    --source-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:ORACLE_SOURCE \
    --target-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:AURORA_TARGET \
    --replication-instance-arn arn:aws:dms:us-east-1:111111111111:rep:REPLICATION_INSTANCE \
    --migration-type full-load-and-cdc \
    --table-mappings file://table-mappings.json

End of support. DMS Fleet Advisor, which inventoried on-premises databases for migration planning, reached end of support on 20 May 2026.

"Migrate Oracle to Aurora PostgreSQL with minimal downtime" points to schema conversion (DMS Schema Conversion or SCT) plus DMS full load and CDC. "Move MySQL to Aurora MySQL" points to native tools or an Aurora read replica, or DMS. "Run SQL Server apps on Aurora PostgreSQL with few changes" points to Babelfish. "The application needs OS access to the database host" points to RDS Custom (or EC2).

Choosing a database type

Skill 3.3.4Determining an appropriate database type (for example, Amazon Aurora, Amazon DynamoDB)

Relational or non-relational

Matching the type to the data

Relational databases suit data with relationships, joins, flexible queries and multi-row transactions. Non-relational (NoSQL) databases trade those for scale and speed on known access patterns: key-value (DynamoDB), document (DocumentDB), wide-column (Keyspaces), graph (Neptune), in-memory (ElastiCache, MemoryDB) and time series (Timestream for InfluxDB). Serverless options include Aurora Serverless, Aurora DSQL, DynamoDB, ElastiCache Serverless, Keyspaces and Neptune Serverless. Analytics belong in a warehouse such as Redshift (OLAP), not in the transactional database (OLTP).

Designing with DynamoDB

Capacity modes and units

On-demand mode is now DynamoDB's default and recommended mode: you pay per request (50% cheaper since November 2024), and a table instantly handles up to double its previous peak. Provisioned mode sets read and write capacity units, usually with auto scaling (target 70% utilization), for steady, predictable traffic. The units:

  • 1 RCU = one strongly consistent read per second of an item up to 4 KB, or two eventually consistent reads. Transactional reads cost twice.
  • 1 WCU = one write per second of an item up to 1 KB. Transactional writes cost twice.
  • Sizes round up: reading a 6 KB item strongly consistently costs 2 RCUs; writing a 1.5 KB item costs 2 WCUs.

Worked example: 100 strongly consistent reads per second of 6 KB items need 200 RCUs (100 if eventually consistent); 50 writes per second of 1.5 KB items need 100 WCUs. Items are at most 400 KB.

Partitions and keys

DynamoDB stores data in partitions chosen by the partition key, and each partition handles at most 3,000 read units and 1,000 write units per second. A key with few distinct values (a status field, today's date) creates a hot partition that throttles even when the table has spare capacity. Choose high-cardinality keys (customer ID, order ID); for unavoidable hot keys, use write sharding by adding a random or calculated suffix. Adaptive capacity automatically gives hot partitions more throughput and can isolate hot items, but it doesn't fix a bad key. Throttling can also come from traffic that more than doubles within 30 minutes on-demand; warm throughput lets you pre-warm a table before a launch, and an on-demand maximum throughput caps runaway cost.

Queries, indexes and streams

A Query reads items with one partition key value (efficient); a Scan reads the whole table (slow and costly at scale). To query by another attribute, add an index:

  • Global secondary index (GSI): a different partition and sort key, added or removed at any time, with its own throughput; reads are eventually consistent only. Up to 20 per table.
  • Local secondary index (LSI): the same partition key with a different sort key, created only with the table, sharing its throughput, supporting strongly consistent reads, and limiting each partition key value to 10 GB. Up to 5 per table.

DynamoDB Streams records item changes for Lambda or Pipes to process, TTL deletes expired items for free, and the Standard-Infrequent Access table class lowers storage cost for rarely accessed tables.

Carts table: on-demand, keyed by customer, with streams for downstream processing (AWS CLI) 
aws dynamodb create-table --table-name carts \
    --attribute-definitions AttributeName=customer_id,AttributeType=S AttributeName=item_id,AttributeType=S \
    --key-schema AttributeName=customer_id,KeyType=HASH AttributeName=item_id,KeyType=RANGE \
    --billing-mode PAY_PER_REQUEST \
    --stream-specification StreamEnabled=true,StreamViewType=NEW_AND_OLD_IMAGES

"Throttling on one DynamoDB table although total capacity isn't used" means a hot partition: fix the partition key or shard writes; adding capacity alone doesn't help. "Need strongly consistent reads on an alternate key" can't be done with a GSI; it needs an LSI, which must be defined when the table is created.

"Unpredictable traffic, no capacity planning" points to on-demand. "Steady, predictable traffic, lowest cost" points to provisioned with auto scaling (and reserved capacity). "A big launch will spike traffic" points to warm throughput.

Integrating caching

Skill 3.3.5Integrating caching to meet business requirements

When a cache is the answer

Repeated reads, low latency, protecting the database

A cache pays off when the same data is read many times, the data tolerates being slightly stale, and latency or database load matters: product pages, session state, leaderboards, API responses, results of expensive queries. It doesn't help write-heavy workloads or data read once. Task 2.1 explained lazy loading, write-through and TTLs; here the question is which cache.

Amazon ElastiCache

Valkey and Redis OSS, or Memcached

Valkey and Redis OSS support rich data structures (sorted sets for leaderboards, hashes, lists, geospatial indexes), replication with automatic failover, pub/sub, backups and, in cluster mode, sharding across up to 500 shards with online resharding. Valkey is priced 20% lower than other engines on node-based clusters and 33% lower on serverless, and Valkey 9.0 adds an optional durable mode. Memcached is a simple, multithreaded key-value cache that scales by adding nodes, with no replication, failover or persistence, for caches that can be lost and rebuilt.

ElastiCache Serverless needs no node sizing: it charges for data stored and ElastiCache Processing Units (ECPUs), scales automatically, and returns a writer and a reader endpoint; minimums can pre-scale it for a known event. Node-based clusters suit steady loads, with reserved nodes for discounts.

A serverless Valkey cache for product pages and sessions in the prod VPC (AWS CLI) 
aws elasticache create-serverless-cache --serverless-cache-name web-cache \
    --engine valkey \
    --subnet-ids subnet-0appa111111111111 subnet-0appb111111111111 \
    --security-group-ids sg-0cache111111111111

DynamoDB Accelerator and MemoryDB

DAX for DynamoDB

DAX is an in-memory cache built for DynamoDB and compatible with its API, so the application only swaps in the DAX client. It returns eventually consistent reads in microseconds from an item cache (GetItem, BatchGetItem) and a query cache (Query, Scan), and writes through to DynamoDB. Strongly consistent reads pass straight to DynamoDB, and DAX doesn't help write-heavy tables. A cluster has a primary and up to 10 read replicas in a VPC.

MemoryDB

Amazon MemoryDB is not a cache but a durable in-memory primary database, compatible with Valkey and Redis OSS, storing every write in a Multi-AZ transaction log: microsecond reads, single-digit-millisecond writes, and no separate database behind it.

"Microsecond reads for a DynamoDB table with minimal code change" points to DAX. "Cache for an RDS database, leaderboard with sorted sets, or session store with failover" points to ElastiCache for Valkey or Redis OSS. "Simple cache, multithreaded, data loss acceptable" points to Memcached. "Durable, Redis-compatible primary database" points to MemoryDB.

A cache in front of the database doesn't help if the application reads with strong consistency or rarely repeats a read, and DAX never caches strongly consistent reads. Read replicas, not caches, fit "complex, ad hoc SQL queries on large datasets".

Key takeaways

  • RDS replicas: asynchronous, up to 15 per source (5 recommended for Oracle and SQL Server; 3 for Db2), any class, can be Multi-AZ and cross-Region (create in the destination with a destination KMS key); only MySQL and MariaDB replicas are writable; cascading for MySQL, MariaDB and PostgreSQL 14.1+. Watch ReplicaLag.
  • Aurora: up to 15 replicas, reader endpoint balances connections (not queries), custom endpoints isolate reporting, Aurora Auto Scaling adds replicas. DynamoDB has no read replicas.
  • Design for the pattern: replicas and caches for reads; bigger writers, io2 Block Express, Optimized Writes, Limitless sharding, good DynamoDB keys or queues for writes; serverless and on-demand for spikes; Redshift or replicas for analytics.
  • Capacity: memory-optimized classes for databases, db.t only for test; gp3 (12,000 IOPS included at 400 GiB and up) or io2 Block Express (256,000 IOPS); instance EBS limits cap IOPS; storage autoscaling only grows. Aurora: 256 TiB, I/O-Optimized at 25%+ I/O spend, serverless 0 to 256 or 384 ACUs. Performance Insights is retired; use Database Insights.
  • Connections scale with instance memory; use pooling, RDS Proxy or the Data API; DynamoDB needs no connections.
  • Engines: MySQL for ecosystem, PostgreSQL for features and the Aurora growth path, commercial engines when required (RDS Custom for OS access, Babelfish to leave SQL Server). Homogeneous migration: native tools or DMS; heterogeneous: DMS Schema Conversion or SCT, then DMS full load and CDC. MySQL 8.0 is now in paid Extended Support.
  • Types: RDS for engine choice, Aurora for performance, Aurora DSQL for multi-Region active-active SQL, DynamoDB for scale. DynamoDB: on-demand default; 1 RCU = 4 KB strong (or two eventual) reads, 1 WCU = 1 KB write, rounded up; 3,000 RCU and 1,000 WCU per partition; GSIs (any time, eventual) versus LSIs (at creation, strong, 10 GB). Timestream for LiveAnalytics is closed to new customers.
  • Caching: ElastiCache Valkey or Redis OSS (structures, failover, cluster mode, cheaper Valkey) or Memcached (simple, no replication); ElastiCache Serverless; DAX for DynamoDB eventually consistent reads; MemoryDB as a durable in-memory primary database.
