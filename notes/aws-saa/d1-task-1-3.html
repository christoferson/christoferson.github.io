Overview

Task 1.3

Determine appropriate data security controls.

Tasks 1.1 and 1.2 controlled who can reach a resource. This task assumes someone or something might still get to the data, by mistake, by attack or by deletion, and asks which controls keep it confidential and recoverable: encryption with keys you control, copies in another Region or account that can't be deleted, retention rules that satisfy an auditor, and evidence that it's all in place. Questions often hinge on one detail, such as which key type can be shared across accounts, or which lock mode even the root user can't undo.

Running example. The company's prod account (111111111111) keeps customer uploads in the S3 bucket example-prod-uploads, orders in Aurora PostgreSQL, and session data in DynamoDB, all in us-east-1, with disaster recovery in us-west-2. A security account manages the backup vaults, and the company must keep order records for seven years and show auditors that card data is handled to PCI DSS.

Meeting compliance requirements

Skill 1.3.1Aligning AWS technologies to meet compliance requirements

Two halves of compliance

Evidence about AWS, and evidence about you

Compliance follows the shared responsibility model from Task 1.1. AWS's half (physical security, the infrastructure) is audited by third parties, and you inherit those controls. AWS Artifact is the free self-service portal for that evidence: SOC, ISO and PCI reports about AWS, and agreements you accept, such as the HIPAA Business Associate Addendum (BAA), for one account or the whole organization. Your half (how you configure services, classify data and encrypt it) needs its own controls and its own evidence. For example, HIPAA has no AWS certification: you sign the BAA and then keep protected health information only in HIPAA eligible services, configured correctly.

Services that check and prove your half

Config, Security Hub CSPM and Control Tower

AWS Config records the configuration history of your resources and evaluates them against rules (for example, "S3 buckets must have default encryption", "EBS volumes must be encrypted"), with optional automatic remediation. Conformance packs bundle rules into templates for frameworks such as PCI DSS, HIPAA and NIST, and deploy them across an organization. Security Hub CSPM (the original Security Hub, renamed) runs continuous checks against standards including AWS Foundational Security Best Practices, CIS AWS Foundations Benchmark, NIST SP 800-53 and PCI DSS, using Config recording. AWS Control Tower controls (Task 1.1) apply preventive, detective and proactive rules per OU, including Region restrictions for data residency.

CloudTrail as the audit record

AWS CloudTrail records API activity. For audits, turn on log file integrity validation: CloudTrail writes an hourly digest file with SHA-256 hashes, signed and chained to the previous digest, so aws cloudtrail validate-logs can prove whether log files were changed or deleted. Store the trail in the Log Archive account's bucket with Object Lock (Skill 1.3.6).

Closed to new customers. AWS Audit Manager has been in maintenance mode since 30 April 2026: new accounts, Regions and organizations can't start using it, and AWS points to Config conformance packs, Control Tower controls and Security Hub CSPM instead. CloudTrail Lake closed to new customers on 31 May 2026, with CloudWatch as the suggested path; ordinary trails are unaffected.

Classification, residency and governance

Knowing what the data is and where it may live

Controls depend on classification: public marketing images need different handling from card data. Tag resources with a classification (for example data-class=confidential) so policies (ABAC, Task 1.1), backup plans and Config rules can act on it, and use Amazon Macie (Task 1.2) to find sensitive data in S3 that wasn't classified. For data residency, choose the Region and enforce it with an SCP or Control Tower Region-deny control; customers needing an EU-only cloud operated by EU residents can use the AWS European Sovereign Cloud, a separate partition launched in January 2026.

"Download AWS's SOC 2 or PCI report" or "accept the BAA" points to AWS Artifact. "Continuously check our resources against PCI DSS" points to Config conformance packs or Security Hub CSPM. "Prove the audit logs weren't tampered with" points to CloudTrail log file integrity validation.

Encryption at rest

Skill 1.3.2Encrypting data at rest (for example, AWS KMS)

How AWS KMS works

Keys that never leave KMS

AWS Key Management Service holds KMS keys in hardware security modules validated to FIPS 140-3 Level 3. The key material of a symmetric KMS key never leaves KMS unencrypted; you send data to KMS, or ask KMS for a data key. Every use is logged in CloudTrail and controlled by the key policy (Skill 1.3.4).

Envelope encryption

KMS's Encrypt call takes at most 4 KB, so services don't send your data to KMS. Instead they use envelope encryption:

  1. Ask for a data keyGenerateDataKey returns a fresh data key twice: in plaintext, and encrypted under the KMS key.
  2. Encrypt locallyThe service encrypts the data with the plaintext data key, then discards the plaintext key.
  3. Store the encrypted key with the dataOnly the encrypted data key is kept.
  4. Decrypt laterThe service sends the encrypted data key to KMS's Decrypt, gets the plaintext key back, and decrypts the data.

An optional encryption context, non-secret key-value pairs bound to the ciphertext, must match exactly on decrypt and appears in CloudTrail, so it also works as an audit and policy condition (S3, for example, uses the object's ARN).

Choosing a key type

Who owns and manages the key

  • AWS owned keys live in the service's own account and are free. You can't see, audit, control or share them. Many services use one by default (DynamoDB, SQS, Redshift).
  • AWS managed keys appear in your account with aliases such as aws/s3, aws/ebs and aws/rds. You can see them and their CloudTrail use, but you can't change their policy, and they can be used only by your account through that one service, so data encrypted with them can't be shared with another account. AWS calls them a legacy key type that new services stopped creating in 2021.
  • Customer managed keys are created and controlled by you: key policy, grants, rotation, enable, disable, delete. They cost US$1 per key per month plus requests, and they are the only choice when you need your own policy, cross-account use, or control over rotation and deletion.

Any scenario that shares encrypted data with another account (sharing an RDS or EBS snapshot, replicating SSE-KMS objects cross-account, copying backups to another account) fails with an AWS managed key. It needs a customer managed key whose policy allows the other account.

Multi-Region keys, imported keys and custom key stores

Multi-Region keys are related keys in different Regions with the same key ID (starting mrk-) and the same key material, so ciphertext from one Region decrypts in another without calling back. You replicate a primary key into chosen Regions; each replica has its own policy. They suit client-side encryption, active-active applications and DR, but most AWS services still treat them as single-Region keys (S3 replication, for example, still re-encrypts with the destination key), and an existing key can't be converted.

Imported key material (bring your own key) lets you supply the material and set an expiry; you remain responsible for keeping a copy. A custom key store keeps key material outside standard KMS: in your own AWS CloudHSM cluster, or in an external key manager outside AWS (if you cut off its proxy, AWS can no longer decrypt anything). Custom key stores support only symmetric keys, with no automatic rotation and no multi-Region keys.

AWS CloudHSM

CloudHSM gives you single-tenant HSMs in your VPC (the current hsm2m.medium type is FIPS 140-3 Level 3; the older hsm1.medium reached end of support on 31 March 2026). You manage the users and keys; AWS can't recover them if you lose the credentials. Run at least two HSMs in two AZs for production. Choose it when a regulation or contract demands dedicated HSMs under your sole control, or for uses such as SSL/TLS offload, Oracle TDE or document signing; put a KMS CloudHSM key store in front to use those keys with S3, EBS or RDS. FIPS validation alone isn't a reason, because KMS is validated too.

"Encrypt with keys the company fully controls, including rotation and who can use them" points to a customer managed KMS key. "Dedicated, single-tenant HSM" points to CloudHSM. "Decrypt in the DR Region without re-encrypting" points to a multi-Region key.

Encryption by service

Amazon S3

Since January 2023 every new object is encrypted by default with SSE-S3 (S3-managed keys, free). Other options are SSE-KMS (a KMS key, with CloudTrail records of every use and your key policy), DSSE-KMS (two layers of encryption, for rules that demand multi-layer encryption) and SSE-C (you send the key with each request). Since April 2026, SSE-C requests are blocked by default on new buckets unless you allow them again. With SSE-KMS, turn on S3 Bucket Keys: S3 uses a short-lived bucket-level key and cuts its KMS requests by up to 99%, which lowers cost and avoids KMS throttling. Objects uploaded before 2023 without encryption stay unencrypted until they're copied (S3 Batch Operations can do it in bulk).

Default encryption for the uploads bucket: SSE-KMS with a customer managed key and a Bucket Key (AWS CLI) 
aws s3api put-bucket-encryption --bucket example-prod-uploads \
    --server-side-encryption-configuration '{
      "Rules": [{
        "ApplyServerSideEncryptionByDefault": {
          "SSEAlgorithm": "aws:kms",
          "KMSMasterKeyID": "arn:aws:kms:us-east-1:111111111111:alias/prod-data"
        },
        "BucketKeyEnabled": true
      }]
    }'

Default encryption only applies when an upload sends no encryption headers. To guarantee SSE-KMS with your key, add a bucket policy that denies s3:PutObject when the s3:x-amz-server-side-encryption-aws-kms-key-id header names another key or is missing.

EBS, RDS, Aurora, EFS, DynamoDB and Redshift

Amazon EBS: turn on encryption by default per account and Region (optionally with your own key) and every new volume and snapshot copy is encrypted; it also encrypts data moving between the instance and the volume. An existing unencrypted volume can't be encrypted in place: snapshot it, copy or restore the snapshot with encryption, and swap volumes.

Amazon RDS and Aurora: encryption is chosen at creation and covers storage, logs, automated backups, snapshots and read replicas. You can't encrypt an existing unencrypted database or change its key in place; copy a snapshot with encryption and restore it (blue/green deployments are also documented for this). A cross-Region snapshot copy or read replica needs a key in the destination Region, and snapshots encrypted with aws/rds can't be shared.

Amazon EFS: encryption at rest is set at creation (the console turns it on, the API doesn't) and can't be changed later; enforce it with the elasticfilesystem:Encrypted condition key. DynamoDB always encrypts every table, index, stream and backup, and you can switch between an AWS owned, AWS managed or customer managed key at any time. Amazon Redshift is the exception to "encrypt only at creation": you can modify an unencrypted cluster to use KMS encryption.

SQS and SNS can encrypt message bodies with KMS (SQS also has free SQS-managed keys, the default for new queues); Secrets Manager always encrypts secrets with KMS; Lambda environment variables are always encrypted at rest.

Encrypt every new EBS volume in us-east-1 with the company's key (AWS CLI) 
aws ec2 enable-ebs-encryption-by-default --region us-east-1
aws ec2 modify-ebs-default-kms-key-id --kms-key-id alias/prod-data --region us-east-1

"Encrypt an existing unencrypted RDS database" is never "modify the instance and tick encryption". The answer is snapshot, copy the snapshot with encryption, restore (the same idea applies to EBS, and EFS needs a new file system). Redshift is the one service here that can be encrypted in place.

Encryption in transit

Skill 1.3.3Encrypting data in transit (for example, AWS Certificate Manager [ACM] using TLS)

TLS at every hop

Client to edge to load balancer to target

All AWS service API endpoints have required TLS 1.2 or later since February 2024. For your own traffic, encryption in transit means TLS on each hop, with certificates from ACM (Task 1.2 covers issuing them):

  1. Viewer to CloudFrontSet the viewer protocol policy to Redirect HTTP to HTTPS or HTTPS only.
  2. CloudFront to originSet the origin protocol policy to HTTPS only (S3 website endpoints can't do HTTPS to the origin; S3 REST origins can).
  3. Load balancer listenerAn HTTPS (ALB) or TLS (NLB) listener with an ACM certificate and a security policy that allows only modern TLS versions.
  4. Load balancer to targetsFor end-to-end encryption, an HTTPS target group (the ALB re-encrypts), or TCP passthrough on an NLB so the targets terminate TLS.

Watch the load balancer security policy. The console's default for new HTTPS listeners allows only TLS 1.3 and 1.2 with post-quantum key exchange (ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09), but a listener created through the CLI or CloudFormation without a policy still gets ELBSecurityPolicy-2016-08, which allows TLS 1.0 and 1.1.

Requiring TLS to S3 and databases

S3 accepts HTTP unless you forbid it. The standard control is a bucket policy that denies any request where aws:SecureTransport is false:

Bucket policy: refuse every request to the uploads bucket that isn't over TLS (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RestrictToTLSRequestsOnly",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::example-prod-uploads", "arn:aws:s3:::example-prod-uploads/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}

For a whole organization, the same condition can go in an RCP (Task 1.1). Databases are set through parameter groups: RDS for PostgreSQL forces SSL by default from version 15 (rds.force_ssl = 1), while RDS for MySQL leaves require_secure_transport off until you turn it on. Clients should verify the server certificate against the RDS certificate authority bundle. EFS encrypts NFS traffic when mounted with the mount helper's tls option.

Inside the AWS network

AWS encrypts traffic between its Regions and between Availability Zones at the physical layer, and Nitro-based instance types encrypt traffic between supported instances automatically. VPC Encryption Controls (November 2025) can monitor whether traffic inside and between VPCs is encrypted, and in enforce mode block resources that would allow cleartext.

"Ensure all connections to the bucket use HTTPS" points to a bucket policy denying aws:SecureTransport = false. "Encrypt traffic all the way to the instances" points to an HTTPS listener plus HTTPS target group or NLB TLS passthrough, not TLS termination at the load balancer alone.

Access policies for keys

Skill 1.3.4Implementing access policies for encryption keys

Three ways to grant key access

Key policy, IAM policies and grants

Every KMS key has exactly one key policy, and it is the primary control: IAM policies work only if the key policy allows the account to use them (the account-principal statement explained in Task 1.1). Grants add narrow, allow-only permissions for one key, usually created by AWS services on your behalf: when EBS attaches an encrypted volume or RDS starts an encrypted database, the service creates a grant and retires it later. A grant takes effect within about five minutes, or immediately if the grant token is used.

Separating administrators from users

The console's default key policy has separate statements for key administrators, who can manage the key (enable, disable, tag, change its policy, schedule deletion) but not encrypt or decrypt with it, and key users, who can use it for cryptography but not manage it. That's separation of duties: the security team runs the key; the application role uses it.

Key policy statements for the prod-data key: the app role may use it, and only to let AWS services create grants (JSON fragment) 
[
  {
    "Sid": "AllowUseOfTheKey",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111111111111:role/web-app" },
    "Action": ["kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*", "kms:GenerateDataKey*", "kms:DescribeKey"],
    "Resource": "*"
  },
  {
    "Sid": "AllowAttachmentOfPersistentResources",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111111111111:role/web-app" },
    "Action": ["kms:CreateGrant", "kms:ListGrants", "kms:RevokeGrant"],
    "Resource": "*",
    "Condition": { "Bool": { "kms:GrantIsForAWSResource": "true" } }
  }
]

The kms:GrantIsForAWSResource condition lets the role have EBS or RDS create grants for it, without being able to create grants directly. Key administrators can still edit the key policy and give themselves use, so true separation also restricts kms:PutKeyPolicy and kms:CreateGrant and monitors them.

Condition keys and cross-account use

kms:ViaService and kms:CallerAccount

kms:ViaService limits use of a key to requests that an AWS service makes for you, for example s3.us-east-1.amazonaws.com or rds.us-east-1.amazonaws.com (EBS uses ec2.region.amazonaws.com). A role can then decrypt S3 objects through S3 but can't call Decrypt directly. kms:CallerAccount allows every identity in one account, with "Principal": {"AWS": "*"}. AWS managed keys combine the two, which is exactly why they can't be used from another account.

Sharing a key with another account

In the running example, the security account's backup vault must decrypt copies of prod's backups. Two things are needed, and neither works alone: the key policy in prod allows the other account ("Principal": {"AWS": "arn:aws:iam::account:root"}) to use the key, and an IAM policy in that account gives specific roles the same actions on the key's ARN. Only cryptographic operations, grant operations and DescribeKey work across accounts; nobody outside the key's account can change its policy or delete it. The other account must refer to the key by its full ARN.

"The bucket policy allows the other account, but its users get AccessDenied on SSE-KMS objects" means the key policy (or the other account's IAM policy for the key) is missing, or the objects use the AWS managed aws/s3 key, which can't be shared.

Backups and replication

Skill 1.3.5Implementing data backups and replications

What data recovery needs

Copies that survive the failure you fear

A backup only helps if it survives the event: a deleted table needs a point-in-time copy, a lost Region needs a copy in another Region, and ransomware or a compromised administrator needs a copy in another account that nobody can delete. Replication gives a live second copy, which protects against outages but also faithfully copies mistakes, so most designs need both. Domain 2 covers recovery objectives and disaster recovery strategies; this skill is about the mechanisms.

AWS Backup

One policy for many services

AWS Backup centralizes backups for EC2, EBS, RDS, Aurora, DynamoDB, EFS, FSx, S3 and more. A backup plan has rules: a schedule, a start and completion window, a lifecycle (move to cold storage, delete after so many days), optional continuous backup for point-in-time restore, and copy actions to another Region or account. Resources are assigned by tag or ARN, so tagging a new database backup=daily is enough to protect it. Recovery points live in backup vaults, each encrypted with a KMS key and protected by a vault access policy.

Daily backup kept for 35 days, copied to the DR vault in us-west-2 (backup plan JSON for aws backup create-backup-plan) 
{
  "BackupPlan": {
    "BackupPlanName": "prod-daily",
    "Rules": [
      {
        "RuleName": "daily-0500-utc",
        "TargetBackupVaultName": "prod-vault",
        "ScheduleExpression": "cron(0 5 ? * * *)",
        "StartWindowMinutes": 60,
        "CompletionWindowMinutes": 480,
        "Lifecycle": { "DeleteAfterDays": 35 },
        "CopyActions": [
          {
            "DestinationBackupVaultArn": "arn:aws:backup:us-west-2:111111111111:backup-vault:dr-vault",
            "Lifecycle": { "DeleteAfterDays": 35 }
          }
        ]
      }
    ]
  }
}

Cross-account copies require the accounts to be in the same organization with cross-account backup turned on, a destination vault policy that allows backup:CopyIntoBackupVault, and (for most resource types) a customer managed source key shared with the destination. Restore testing runs scheduled test restores to prove backups work and measure how long restores take, and Backup Audit Manager reports whether resources meet controls such as "protected by a plan" or "copied cross-Region".

Vault Lock and logically air-gapped vaults

AWS Backup Vault Lock makes recovery points immutable and enforces minimum and maximum retention. In governance mode, users with the right IAM permissions can remove the lock. In compliance mode, after a grace time of at least three days, nobody, not the root user and not AWS, can delete the recovery points early or remove the lock. A logically air-gapped vault (generally available since August 2024) is always locked in compliance mode, is held by AWS Backup outside your account's normal reach, and can be shared through AWS RAM so another account can restore directly from it, for recovery after an account compromise.

"Backups must be immutable and protected even from administrators and the root user" points to Vault Lock in compliance mode or a logically air-gapped vault. "Centrally manage backups of RDS, EFS and EBS across accounts" points to AWS Backup with organization backup policies.

Amazon S3

Versioning and MFA Delete

Versioning keeps every version of every object; deleting without a version ID only adds a delete marker, so mistakes can be undone. Once enabled it can only be suspended, not removed, and replication and Object Lock both require it. MFA Delete additionally requires an MFA code to permanently delete a version or change the versioning state; only the bucket owner's root user can turn it on, only through the CLI or API, and a bucket that uses it can't have lifecycle rules.

Replication

S3 Replication copies new objects asynchronously to another bucket in a different Region (Cross-Region Replication) or the same Region (Same-Region Replication), in the same or another account. It needs versioning on both buckets and an IAM role that S3 assumes. Not replicated by default: objects that existed before the rule (use S3 Batch Replication), delete markers (opt in), and SSE-KMS objects (opt in and name a key in the destination Region). Deletes of specific versions are never replicated, which protects the replica from malicious deletion. S3 Replication Time Control adds an SLA: 99.9% of objects replicated within 15 minutes, with metrics and events for late objects.

Replicate SSE-KMS uploads to the DR bucket within 15 minutes (replication configuration JSON for aws s3api put-bucket-replication) 
{
  "Role": "arn:aws:iam::111111111111:role/s3-replication",
  "Rules": [
    {
      "Status": "Enabled",
      "Priority": 1,
      "Filter": {},
      "DeleteMarkerReplication": { "Status": "Disabled" },
      "SourceSelectionCriteria": { "SseKmsEncryptedObjects": { "Status": "Enabled" } },
      "Destination": {
        "Bucket": "arn:aws:s3:::example-dr-uploads",
        "EncryptionConfiguration": { "ReplicaKmsKeyID": "arn:aws:kms:us-west-2:111111111111:key/mrk-EXAMPLE" },
        "ReplicationTime": { "Status": "Enabled", "Time": { "Minutes": 15 } },
        "Metrics": { "Status": "Enabled", "EventThreshold": { "Minutes": 15 } }
      }
    }
  ]
}

Turning on replication doesn't copy the objects already in the bucket. "Replicate existing objects" needs S3 Batch Replication.

Databases and volumes

RDS, Aurora and DynamoDB

RDS automated backups keep daily snapshots plus transaction logs for 0 to 35 days (0 turns them off), allowing point-in-time recovery to any second in the window; manual snapshots stay until you delete them. Cross-Region automated backups replicate snapshots and logs to another Region so you can restore to a point in time there (encrypted databases need a key in that Region). Aurora Backtrack (Aurora MySQL only, up to 72 hours) rewinds a cluster in place in minutes without a restore; it's a fast undo, not a backup. DynamoDB point-in-time recovery keeps continuous backups for a recovery window you set between 1 and 35 days and restores to a new table; on-demand backups stay until deleted.

EBS snapshots

EBS snapshots are incremental and stored durably by AWS; snapshots of encrypted volumes are encrypted. EBS Snapshot Lock protects snapshots from deletion for a set period, in governance or compliance mode, and Recycle Bin keeps deleted snapshots, volumes and AMIs recoverable for a retention period you set. AWS Backup or Amazon Data Lifecycle Manager automates the schedule.

"Restore the database to its state five minutes before the bad deployment" points to point-in-time recovery (RDS, DynamoDB) or Aurora Backtrack for the fastest rewind of Aurora MySQL.

Access, lifecycle and protection policies

Skill 1.3.6Implementing policies for data access, lifecycle, and protection

Access policies on the data

The defaults on new buckets

New S3 buckets block public access and disable ACLs (Object Ownership set to Bucket owner enforced), so access is decided only by IAM and bucket policies (Task 1.1). Data access policies then combine the controls on this page: a bucket policy that requires TLS and your KMS key, a key policy that allows only the application roles, and endpoint conditions from Task 1.2. Data governance means writing these policies once and enforcing them everywhere, through SCPs, RCPs and Config rules.

Lifecycle and retention rules

S3 Lifecycle for retention

S3 Lifecycle rules act on objects by prefix, tag or size. Transition actions move objects to cheaper storage classes (Domain 4). Expiration deletes current versions after a number of days (in a versioned bucket it adds a delete marker), NoncurrentVersionExpiration permanently removes old versions after so many days (optionally keeping the newest few), and AbortIncompleteMultipartUpload cleans up failed uploads. In the running example, application logs are kept for one year and old versions for 30 days:

Lifecycle rule for the logs/ prefix (JSON for aws s3api put-bucket-lifecycle-configuration) 
{
  "Rules": [
    {
      "ID": "logs-retention",
      "Filter": { "Prefix": "logs/" },
      "Status": "Enabled",
      "Expiration": { "Days": 365 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30, "NewerNoncurrentVersions": 10 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}

CloudWatch Logs keeps log events forever unless a retention period is set on the log group; account-level retention policies can now set it for many log groups at once.

Immutability: S3 Object Lock

Write once, read many

S3 Object Lock stops object versions from being deleted or overwritten for a retention period or indefinitely. It requires versioning, can be enabled at bucket creation or later, and can't be turned off once enabled. A retention period protects a version until a date, in one of two modes:

  • Governance mode: users with s3:BypassGovernanceRetention can still delete or shorten the lock by sending a bypass header. Good for protecting against accidents while keeping an escape hatch.
  • Compliance mode: nobody, including the root user, can delete the version or shorten its retention until it expires. Used for regulations such as SEC 17a-4.

A legal hold is separate: it has no end date and stays until someone with s3:PutObjectLegalHold removes it. A plain DELETE on a locked object still succeeds by adding a delete marker; the protected version remains.

Keep every new order record in the archive bucket for seven years, in compliance mode (AWS CLI) 
aws s3api put-object-lock-configuration --bucket example-order-archive \
    --object-lock-configuration '{"ObjectLockEnabled": "Enabled", "Rule": {"DefaultRetention": {"Mode": "COMPLIANCE", "Years": 7}}}'

Glacier vaults. The original vault-based Amazon Glacier service, with its Glacier Vault Lock, is no longer accepting new customers; existing data stays accessible. New designs use the S3 Glacier storage classes with S3 Object Lock.

"Records must not be deleted or changed by anyone, including administrators, for seven years" points to S3 Object Lock in compliance mode. "Prevent accidental deletion but let a few admins override" points to governance mode. "Keep until the lawsuit ends" points to a legal hold.

Rotating keys and renewing certificates

Skill 1.3.7Rotating encryption keys and renewing certificates

KMS key rotation

Automatic and on-demand rotation

For a customer managed symmetric key with key material created by KMS, automatic rotation is off by default; when on, KMS creates new key material every 365 days by default, or any period from 90 to 2,560 days. On-demand rotation rotates immediately (up to 25 times per key) and also works for symmetric keys with imported material, which can't rotate automatically. AWS managed keys rotate every year and you can't change that.

Rotation keeps the same key ID, ARN, policy and aliases, and keeps all previous key material, so data encrypted before the rotation still decrypts and nothing has to be re-encrypted. It also doesn't re-encrypt existing data, which means rotation doesn't fix a leaked data key. The first two rotations each add US$1 a month to the key's price; later ones are free.

Rotate the prod-data key every 180 days, and check it (AWS CLI; these calls take the key ID or key ARN, not the alias) 
aws kms enable-key-rotation --key-id KEY_ID --rotation-period-in-days 180
aws kms get-key-rotation-status --key-id KEY_ID

Manual rotation

Asymmetric keys, HMAC keys and keys in custom key stores can't be rotated by KMS. Rotate them manually: create a new key, point the application's alias at it with UpdateAlias, and keep the old key enabled for as long as old data must be decrypted. This only works if applications use the alias rather than the key ID.

Disabling and deleting keys

Disabling a key is reversible and is the safe first step when retiring one. Deletion is scheduled with a waiting period of 7 to 30 days (30 by default) and can be cancelled until then; afterwards every ciphertext under the key is unrecoverable. Only customer managed keys can be deleted.

Certificate renewal

When ACM renews for you

ACM renews certificates it issued automatically, keeping the same ARN, if the certificate is in use by an integrated service (load balancer, CloudFront, API Gateway) and, for DNS validation, the validation CNAME record is still in DNS. With DNS validation that's fully automatic; with email validation someone must approve the renewal email, and ACM will phase out email validation during 2027. Exportable certificates are renewed too, but you must export and install the new copy. AWS Health and EventBridge send notices if a renewal is failing.

Imported and private certificates

Imported certificates are never renewed by ACM; you must import a new one before expiry. Catch them with the EventBridge event ACM Certificate Approaching Expiration or the AWS Config rule acm-certificate-expiration-check (14 days by default). For internal services, AWS Private CA runs your own private certificate authority (US$400 per CA per month, or US$50 in short-lived certificate mode for certificates valid up to seven days); private certificates requested through ACM can be renewed by ACM.

EventBridge rule pattern: alert when any ACM certificate approaches expiry (JSON) 
{
  "source": ["aws.acm"],
  "detail-type": ["ACM Certificate Approaching Expiration"]
}

"The certificate on the load balancer expired even though it came from ACM" usually means it was imported (never renewed), used email validation with nobody approving, or its DNS validation record was deleted. Secrets Manager rotation (Task 1.2) rotates secrets, not KMS keys or certificates.

Key takeaways

  • Compliance: Artifact gives AWS's reports and the BAA; Config rules and conformance packs and Security Hub CSPM check your side; CloudTrail log file integrity validation proves logs weren't altered. Audit Manager and CloudTrail Lake are closed to new customers.
  • KMS: envelope encryption with data keys (Encrypt takes 4 KB at most). AWS owned keys are free and invisible; AWS managed keys (aws/s3, aws/rds) are legacy and can't be shared across accounts; customer managed keys give you the policy, rotation and sharing. Multi-Region keys share material across Regions; CloudHSM gives single-tenant HSMs.
  • S3 encrypts with SSE-S3 by default; SSE-KMS plus Bucket Keys for control at scale; SSE-C is blocked by default on new buckets. EBS encryption by default per Region. RDS, EBS and EFS can't be encrypted in place (snapshot, copy, restore); Redshift can; DynamoDB always is.
  • In transit: HTTPS viewer and origin policies on CloudFront, HTTPS listener and target group for end to end, deny aws:SecureTransport = false on buckets, rds.force_ssl on PostgreSQL 15+ by default but MySQL's require_secure_transport off. CLI-created HTTPS listeners still default to an old TLS policy.
  • Key policies: the key policy is primary; separate administrators from users; kms:ViaService limits use to a service; cross-account needs the key policy and the other account's IAM policy; only crypto and grant operations cross accounts.
  • Backups: AWS Backup plans with lifecycle and cross-Region or cross-account copies; Vault Lock compliance mode and air-gapped vaults are immutable even to root. S3 replication needs versioning and doesn't copy existing objects (Batch Replication); RTC is 99.9% in 15 minutes. RDS PITR up to 35 days, DynamoDB PITR 1 to 35 days, Aurora Backtrack 72 hours.
  • Protection: lifecycle expiration rules enforce retention; Object Lock governance can be bypassed with permission, compliance can't by anyone; legal holds have no end date; MFA Delete is root-only and conflicts with lifecycle.
  • Rotation: automatic yearly by default (90 to 2,560 days) for KMS-generated symmetric keys, on-demand up to 25 times, manual by alias swap for asymmetric, HMAC and custom key store keys; old material is kept. ACM renews in-use certificates with DNS validation automatically; imported certificates never renew.
