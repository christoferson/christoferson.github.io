Overview

Task 3.5

Determine high-performing data ingestion and transformation solutions.

This task is a solutions architect's view of a data platform: which service brings each kind of data in, where it lands, who may read which columns, what processes it, and how it reaches a dashboard. Questions turn on a few words: "real time" versus "near real time", "no code", "existing Spark jobs", "only certain columns", "reduce query cost". This site's Data Engineer – Associate guide goes deeper into each service; this page stays at the level of design choices.

Running example. The company streams clickstream events from its website and app, receives nightly CSV files from suppliers over SFTP, replicates orders from Aurora, and pulls sales data from a SaaS CRM. Everything lands in an S3 data lake, is converted to Parquet and cataloged, is queried with Athena by analysts, and appears in dashboards for managers. Finance analysts may see order totals but not customers' personal data.

Building and securing data lakes

Skill 3.5.1Building and securing data lakes

Layout on Amazon S3

Raw, stage and analytics layers

A data lake keeps all data, structured or not, in S3 at any scale, and lets many engines query it in place. AWS Prescriptive Guidance recommends at least three layers, each in its own bucket:

  1. RawData exactly as it arrived, in its original format, with versioning on, kept long term on cheaper storage classes.
  2. StageValidated, cleaned data converted to an efficient format such as Parquet, with its schema in the Glue Data Catalog.
  3. AnalyticsAggregated, consumption-ready data for specific uses, such as daily sales by region.

For sensitive data, a separate landing bucket comes first, where personal data is masked before it reaches the raw layer. (Other common names for the layers are curated and consumption, or bronze, silver and gold.)

Cataloging

AWS Glue Data Catalog and crawlers

The Glue Data Catalog is the lake's metadata store: databases and tables that describe where data lives, its schema and its partitions, used by Athena, Redshift Spectrum, EMR, Glue and Amazon Quick alike. A crawler scans S3 (or JDBC, DynamoDB, Iceberg, Delta and Hudi sources) on a schedule or on S3 events, infers schemas and creates or updates tables; it can crawl only new folders to save time. Tables can also be created directly, by Glue jobs or Athena DDL.

Access control with AWS Lake Formation

Database-style grants on lake data

AWS Lake Formation adds database-style GRANT and REVOKE permissions on catalog databases, tables and columns, enforced by the engines that read the data (Athena, Redshift Spectrum, EMR, Glue), instead of managing many S3 bucket policies. A request must pass both IAM (which controls the Lake Formation and Glue APIs) and Lake Formation. You register S3 locations with Lake Formation, which then hands temporary credentials to the engines.

  • Named resources: grant SELECT on a table to a role.
  • LF-Tags (tag-based access control): tag databases, tables and columns (for example classification=pii) and grant by tag; AWS recommends it for large catalogs because grants grow with principals plus resources rather than principals times resources. LF-Tags are separate from IAM tags.
  • Data filters: column-level, row-level and cell-level security on a table, for SELECT only.
  • Cross-account sharing through AWS RAM, with resource links in the consuming account for Athena and Redshift Spectrum.
  • Hybrid access mode: chosen principals use Lake Formation permissions while others keep their IAM-only access, for a gradual migration.
Let finance analysts read the orders table, except the customer's email and phone columns (JSON for aws lakeformation grant-permissions --cli-input-json) 
{
  "Principal": { "DataLakePrincipalIdentifier": "arn:aws:iam::111111111111:role/finance-analyst" },
  "Resource": {
    "TableWithColumns": {
      "DatabaseName": "sales",
      "Name": "orders",
      "ColumnWildcard": { "ExcludedColumnNames": ["customer_email", "customer_phone"] }
    }
  },
  "Permissions": ["SELECT"]
}

"Analysts may see only some columns or rows of lake tables" points to Lake Formation column permissions or data filters. "Thousands of tables, permissions by data classification" points to LF-Tags. "Share catalog tables with another account" points to Lake Formation cross-account sharing (through AWS RAM).

Tables on S3: Apache Iceberg and S3 Tables

Transactions on lake data

Plain files in S3 can't be updated row by row safely. Apache Iceberg tables add ACID transactions, row-level updates and deletes, time travel and schema evolution on top of Parquet files, and Athena, Glue, EMR, Redshift and Firehose all read or write them. Amazon S3 Tables stores Iceberg tables in a new bucket type, table buckets, with higher transaction rates than self-managed tables and automatic compaction and snapshot cleanup. Its integration with the analytics services now uses IAM access control by default, with Lake Formation optional. The lakehouse architecture of Amazon SageMaker (launched as SageMaker Lakehouse) unifies S3 data lakes and Redshift warehouses behind an Iceberg-compatible catalog.

Securing the lake

The controls from Domain 1, applied

  • Encrypt every bucket with SSE-KMS (customer managed keys for cross-account use) and require TLS (Task 1.3).
  • Block public access, use bucket policies with aws:SourceVpce or organization conditions, and reach S3 through a gateway endpoint and Glue, Lake Formation and Kinesis through interface endpoints (Task 1.2).
  • Use Macie to find personal data that arrived where it shouldn't.
  • Give each layer its own bucket and access policy, and keep the raw layer read-only for most users.

Data streaming architectures

Skill 3.5.2Designing data streaming architectures

The streaming services

Kinesis Data Streams

Kinesis Data Streams stores an ordered, replayable stream that many consumers read independently: Lambda, applications using the Kinesis Client Library, Managed Service for Apache Flink, or Firehose. Records stay 24 hours by default and up to 365 days (extra charge beyond 24 hours), and can be up to 10 MiB. Shard limits, capacity modes and decoupling were covered in Task 3.2; two consumer details matter here. Standard consumers share each shard's 2 MB/s of reads (about 200 ms latency with one consumer), while enhanced fan-out gives each registered consumer its own 2 MB/s per shard pushed with about 70 ms latency. And in on-demand mode, a stream can now deliver directly to S3 or S3 Tables with exactly-once delivery per shard and 5 to 15 minute freshness.

Amazon Data Firehose

Amazon Data Firehose (renamed from Kinesis Data Firehose in February 2024) is the no-code way to load streams into storage and analytics: S3, Iceberg tables (including S3 Tables), Redshift, OpenSearch, Splunk, Snowflake, HTTP endpoints and partner tools. It buffers records and delivers in batches (near real time, from a few seconds to 15 minutes), can transform records with Lambda, convert JSON to Parquet or ORC (Skill 3.5.7), and partition output by keys in the data (dynamic partitioning). It doesn't store data for replay and has no custom consumers. Producers write to it directly (Direct PUT), or it reads from a Kinesis data stream or MSK topic.

Managed Service for Apache Flink and Amazon MSK

Amazon Managed Service for Apache Flink runs Apache Flink applications (Java, Scala, Python or SQL) for real-time analytics on streams: windowed aggregations, joins, anomaly detection, with checkpoints and automatic scaling; Flink Studio notebooks run interactive SQL. Kinesis Data Analytics for SQL applications was discontinued (no new applications from October 2025, deletion from January 2026), so Flink is the answer for SQL on streams. Amazon MSK runs Apache Kafka for applications that already use Kafka APIs, long retention and many consumer groups.

The clickstream pipeline

  1. ProducersThe website and app send events to a Kinesis data stream through the SDK.
  2. Real-time consumerA Managed Service for Apache Flink application computes live metrics, such as sessions per minute, for an operations dashboard.
  3. DeliveryFirehose reads the same stream, converts events to Parquet, partitions them by date and writes them to the stage layer in S3.
  4. Catalog and queryThe table is in the Glue Data Catalog; analysts query it with Athena and managers see it in Amazon Quick.

"Load streaming data into S3 or Redshift with the least effort" points to Data Firehose. "Real-time processing by several applications, with replay" points to Kinesis Data Streams. "SQL or windowed analytics on a stream in real time" points to Managed Service for Apache Flink. "Video from cameras" points to Kinesis Video Streams.

Firehose isn't real time: it delivers in buffered batches, and it can't replay data. When a question says milliseconds or "multiple consumers", Firehose alone is the wrong answer.

Data transfer solutions

Skill 3.5.3Designing data transfer solutions

Ingestion patterns by frequency

Batch, micro-batch, streaming and change data capture

  • Batch (hourly, nightly): scheduled Glue jobs and crawlers, EMR steps, DataSync tasks, DMS full loads, orchestrated by Step Functions or Amazon MWAA.
  • Micro-batch (seconds to minutes): Firehose buffering, Kinesis delivery to S3, Glue streaming jobs.
  • Streaming (milliseconds): Kinesis Data Streams or MSK with Lambda or Flink.
  • Change data capture (CDC) from databases: AWS DMS full load plus ongoing changes into S3, Kinesis or MSK (Task 3.3), or zero-ETL integrations, which replicate Aurora MySQL, Aurora PostgreSQL, RDS for MySQL, PostgreSQL and Oracle, DynamoDB and several SaaS applications into Redshift with no pipeline to build.

Choosing the transfer service

By source

  • On-premises file servers and object stores: AWS DataSync for one-time or scheduled online copies (up to 10 Gbps per task); Storage Gateway S3 File Gateway when on-premises applications keep writing files that should land in S3 (both in Task 3.1).
  • Partners sending files: AWS Transfer Family SFTP, FTPS, FTP or AS2 endpoints that write to S3, with workflows that process each upload. The suppliers' nightly CSVs arrive this way.
  • SaaS applications (Salesforce, ServiceNow, Zendesk, Slack and others): Amazon AppFlow runs managed flows on demand, on a schedule or on events into S3 or Redshift, privately over PrivateLink where supported; Glue connectors and zero-ETL integrations are alternatives.
  • Databases: DMS or zero-ETL, as above.
  • Very large one-off datasets: Direct Connect or many parallel DataSync tasks online; offline, Snow devices are closed to new customers, and AWS Data Transfer Terminal (bring your own devices to an AWS site) is currently only for Enterprise Support customers.

"Replicate Aurora data to Redshift for analytics without building ETL" points to a zero-ETL integration. "Bring Salesforce data into S3 on a schedule" points to AppFlow. "Partners upload by SFTP" points to Transfer Family. "Migrate an NFS share to S3 once" points to DataSync.

Removed. Firehose briefly offered databases as a source in preview, but it was removed in September 2025; use DMS or zero-ETL for change data capture. AWS Data Pipeline is in maintenance mode and closed to new customers; use Glue, Step Functions or MWAA.

Visualization strategies

Skill 3.5.4Implementing visualization strategies

Amazon Quick and Quick Sight

Business intelligence dashboards

In October 2025 Amazon QuickSight was renamed Amazon Quick; its BI capability continues as Amazon Quick Sight, with the same APIs. Quick Sight builds interactive dashboards and reports over Athena, Redshift, RDS, S3, SaaS sources and more; SPICE, its in-memory engine, imports data for fast dashboards without querying the source each time; dashboards can be embedded in applications, shared with many readers, and restricted with row-level security. Organization plans are priced per user (only the Enterprise plan can author dashboards) plus a monthly infrastructure fee per account. Amazon Quick also adds AI agents, research and automation features around the BI core.

Renamed. The exam guide says Amazon Quick; older questions and answers say Amazon QuickSight. They're the same BI service.

Other ways to see data

Athena, OpenSearch Dashboards and Managed Grafana

  • Amazon Athena: analysts query the lake with SQL directly, priced at about US$5 per TB scanned, with workgroups to separate teams, cap data scanned per query and track cost; it's also the usual data source for Quick Sight.
  • Amazon Redshift: the data warehouse for heavy, repeated BI queries on large structured data, provisioned (RA3) or Serverless, querying S3 through Spectrum.
  • Amazon OpenSearch Service with OpenSearch Dashboards: log and search analytics, near-real-time operational views, fed directly by Firehose.
  • Amazon Managed Grafana: dashboards for operational metrics, logs and traces from CloudWatch, Prometheus, OpenSearch and others.

"Interactive business dashboards for managers, embedded in an app" points to Amazon Quick Sight. "Ad hoc SQL on S3 without loading it anywhere" points to Athena. "Visualize logs in near real time" points to OpenSearch Dashboards. "Operational metrics dashboards" points to Managed Grafana.

Compute for data processing

Skill 3.5.5Selecting appropriate compute options for data processing (for example, Amazon EMR)

The processing options

AWS Glue

AWS Glue runs serverless Apache Spark (and Python shell) ETL jobs, priced per DPU-hour (one DPU is 4 vCPU and 16 GB), with worker types from G.1X up to G.16X and memory-optimized R types. Glue 5.1 is the default for new jobs and Glue 6.0 the latest; versions 2.0 and older reached end of life on 1 April 2026. Job bookmarks process only new data on each run; Flex execution runs time-insensitive jobs on spare capacity at a lower price; Glue Studio builds jobs visually; Glue streaming jobs process Kinesis or Kafka in micro-batches; Glue Data Quality checks rules on data. Glue DataBrew offers more than 250 no-code transformations for analysts. Glue for Ray closed to new customers on 30 April 2026.

Choosing between them

  • AWS Glue: serverless Spark ETL with the Data Catalog built in; the default for new pipelines.
  • Amazon EMR (Task 3.2): existing Spark, Hive, Presto, Trino, HBase or Flink workloads, full control over the cluster and its tuning, Spot task nodes for cost; EMR Serverless for Spark and Hive without clusters.
  • Amazon Athena: SQL transformations with CTAS and INSERT INTO, no infrastructure; Athena also runs Spark notebooks.
  • AWS Lambda: light, per-record or per-file transforms (up to 15 minutes), such as Firehose record transformation or reacting to S3 uploads.
  • Amazon Redshift: SQL ELT inside the warehouse.

"Serverless ETL with minimal management" points to Glue. "Migrate existing Hadoop or Spark jobs with the least change" or "need HBase or Presto" points to EMR. "Analysts want point-and-click data preparation" points to Glue DataBrew. "Process each uploaded file in seconds" points to Lambda.

Configuring ingestion

Skill 3.5.6Selecting appropriate configurations for ingestion

Sizes and speeds

Sizing Kinesis Data Streams

In provisioned mode, each shard accepts 1 MB/s or 1,000 records per second of writes and serves 2 MB/s of reads shared by standard consumers. Size by the largest of the three: incoming MB/s, incoming records per second divided by 1,000, and total read MB/s divided by 2. For the clickstream at 5 MB/s and 2,000 records per second, writes need 5 shards; with three standard consumers each reading everything (15 MB/s), reads need 8 shards, or keep 5 shards and give the consumers enhanced fan-out. Choose a high-cardinality partition key (such as session ID) so records spread evenly over shards. On-demand mode avoids the arithmetic, starting at 4 MB/s and scaling automatically.

Configuring Data Firehose

  • Buffering: Firehose delivers when either the buffer size (1 to 128 MiB for S3, default 5) or the interval (0 to 900 seconds, default 300) is reached. Larger buffers mean fewer, larger files and lower cost; shorter intervals mean fresher data. Zero buffering delivers within seconds to application destinations, but not to the S3 backup or with dynamic partitioning.
  • Throughput: Direct PUT accepts 5 MiB/s per stream in us-east-1, us-west-2 and eu-west-1, and only 1 MiB/s in most other Regions (quotas rise automatically under sustained throttling). With a Kinesis data stream as the source, that quota doesn't apply, so put Kinesis in front for high-volume producers.
  • Dynamic partitioning writes to S3 prefixes from fields in the data, up to 500 active partitions per stream by default.
  • Error output: failed records go to an error prefix, and an S3 backup can keep all source records.

Securing ingestion access points

Who can write, over which path, encrypted how

  • IAM: producers get a role allowing only kinesis:PutRecord/PutRecords (or firehose:PutRecordBatch) on their stream; consumers get read permissions. Kinesis streams also accept resource-based policies for cross-account producers and consumers without role assumption.
  • Network: interface VPC endpoints for Kinesis, Firehose and Glue, and a gateway endpoint for S3, keep ingestion off the internet; policies can require aws:SourceVpce.
  • Encryption: Kinesis server-side encryption with KMS (a customer managed key if the stream is shared across accounts), Firehose encryption with AWS-owned or customer managed keys, and SSE-KMS on the destination bucket. All traffic uses TLS.
  • File endpoints: Transfer Family users come from the service itself, AWS Managed Microsoft AD, or a custom identity provider through Lambda or API Gateway; VPC-hosted endpoints add security groups and Elastic IPs.
  • Kafka: MSK supports IAM access control, mutual TLS and SASL/SCRAM.

"Firehose throttles producers in a smaller Region" is the 1 MiB/s Direct PUT quota, not a buffering problem. Put a Kinesis data stream in front (its shards scale the input) or request a quota increase.

Transforming data between formats

Skill 3.5.7Transforming data between formats (for example, .csv to .parquet)

Why columnar formats

Parquet and ORC

CSV and JSON are row formats: to read one column, an engine reads every row in full. Apache Parquet and Apache ORC store each column together, compressed, with statistics, so engines read only the columns a query needs and skip blocks that can't match (predicate pushdown). AWS's Athena pricing example shows the effect: a query scanning 3 TB of raw text costs $15; compressed (about 3:1) it costs $5; converted to Parquet and reading only the needed columns, $1.25. Combine format conversion with partitioning (folders such as order_date=2026-11-09/) so queries filtered by date read only those partitions, and with compression (Snappy, GZIP or ZSTD).

Three ways to convert

Firehose record format conversion

Firehose converts JSON records to Parquet or ORC on the way to S3, using a Glue Data Catalog table as the schema. CSV or other input must first be turned into JSON with a Lambda transform, and fields missing from the Glue table are dropped. The Parquet serializer compresses with Snappy by default.

Clickstream Firehose stream: convert JSON to Parquet using the Glue table clicks.events (DataFormatConversionConfiguration inside the ExtendedS3DestinationConfiguration JSON) 
{
  "Enabled": true,
  "InputFormatConfiguration": { "Deserializer": { "OpenXJsonSerDe": {} } },
  "OutputFormatConfiguration": { "Serializer": { "ParquetSerDe": { "Compression": "SNAPPY" } } },
  "SchemaConfiguration": {
    "DatabaseName": "clicks",
    "TableName": "events",
    "Region": "us-east-1",
    "RoleARN": "arn:aws:iam::111111111111:role/firehose-glue-schema"
  }
}

Athena CTAS

For files already in S3, an Athena CREATE TABLE AS SELECT query reads the CSV table and writes a new Parquet table, partitioned, in one SQL statement; INSERT INTO adds later batches. CTAS writes Parquet by default (with GZIP compression unless you choose otherwise) and creates at most 100 partitions per query.

Convert the suppliers' CSV table to partitioned, Snappy-compressed Parquet in the stage layer (Athena SQL) 
CREATE TABLE stage.supplier_orders
WITH (
  format = 'PARQUET',
  write_compression = 'SNAPPY',
  external_location = 's3://example-lake-stage/supplier_orders/',
  partitioned_by = ARRAY['order_date']
) AS
SELECT order_id, supplier_id, sku, quantity, unit_price, order_date
FROM raw.supplier_orders_csv;

Glue ETL jobs

For recurring pipelines with validation and joins, a Glue job reads the raw layer, cleans and validates the data, writes Parquet (or an Iceberg table) to the stage layer, and updates the Data Catalog, with job bookmarks so each run processes only new files. That's AWS's own example for moving data from the raw to the stage layer. EMR does the same for existing Spark code at larger scale.

"Reduce Athena cost and speed up queries" points to converting to Parquet and partitioning. "Convert streaming JSON to Parquet with no code" points to Firehose format conversion. "One-time conversion of existing CSV in S3" points to Athena CTAS (or a Glue job). "Need updates, deletes and time travel on lake tables" points to Apache Iceberg or S3 Tables.

Key takeaways

  • Data lake: raw, stage and analytics buckets (plus a landing bucket to mask personal data); the Glue Data Catalog and crawlers describe it; Lake Formation grants databases, tables, columns and rows (IAM and Lake Formation must both allow; LF-Tags for scale; data filters; sharing through RAM). Iceberg and S3 Tables add transactions.
  • Streaming: Kinesis Data Streams for replayable, multi-consumer, real-time streams (24 hours to 365 days, enhanced fan-out 2 MB/s per consumer per shard); Data Firehose for no-code, buffered delivery to S3, Iceberg, Redshift and OpenSearch; Managed Service for Apache Flink for real-time SQL and analytics (KDA for SQL is gone); MSK for Kafka.
  • Transfer by source and frequency: DataSync and Storage Gateway for on-premises files, Transfer Family for partner SFTP, AppFlow for SaaS, DMS CDC or zero-ETL for databases, Direct Connect or Data Transfer Terminal (Enterprise Support only) for huge datasets.
  • Visualization: Amazon Quick Sight (formerly QuickSight) dashboards with SPICE and embedding; Athena for ad hoc SQL ($5 per TB scanned, workgroups); OpenSearch Dashboards for logs; Managed Grafana for operational metrics.
  • Processing: Glue for serverless Spark ETL (5.1 default, bookmarks, Flex); EMR for existing big-data frameworks; Athena CTAS for SQL transforms; Lambda for light per-record work; DataBrew for no-code preparation; Glue for Ray is closed to new customers.
  • Configuration: shards = max(MB/s in, records/s / 1,000, read MB/s / 2), or on-demand; Firehose buffers 1 to 128 MiB or 0 to 900 seconds; Direct PUT only 1 MiB/s in most Regions; secure with least-privilege IAM, resource policies, VPC endpoints and KMS.
  • Formats: Parquet or ORC plus partitioning plus compression cut scan cost (AWS's example: $15 to $1.25). Firehose converts JSON only (CSV needs Lambda first) using a Glue schema; Athena CTAS converts with SQL (100 partitions per query); Glue jobs convert on a schedule.
