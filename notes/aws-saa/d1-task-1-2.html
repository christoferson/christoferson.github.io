Task 1.2: Design secure workloads and applications

Building the network and application layers so that only the traffic you intend can reach a workload: filtering in the VPC, separating tiers, keeping calls to AWS services private, stopping attacks at the edge, protecting credentials and connecting other networks safely.

Overview

Task 1.2

Design secure workloads and applications.

Task 1.1 decided who can call AWS. This task decides what traffic can reach a workload and how the workload protects itself: which subnets can talk to the internet, which ports are open between tiers, how calls to AWS services avoid the internet, what stops a flood of requests or an injection attack, where database passwords live, and how an office network connects. Questions usually describe an architecture with one gap and ask for the most secure change with the least effort.

Running example. The company's web application runs in the prod account (111111111111) in us-east-1. An Application Load Balancer sits in public subnets; the application runs on EC2 Auto Scaling and ECS on Fargate in private subnets; Aurora PostgreSQL sits in isolated database subnets. Customer uploads go to S3, CloudFront serves the site, and the head office connects through Site-to-Site VPN today, with AWS Direct Connect planned.

VPC security components

Skill 1.2.1Designing VPC architectures with security components (for example, security groups, route tables, network ACLs, NAT gateways)

Security groups

A stateful firewall on every network interface

A security group (SG) is attached to an elastic network interface, so it filters traffic for an instance, a container task, a load balancer or a database. It has allow rules only; anything not allowed is dropped. It is stateful: if an inbound request is allowed, the response goes back out automatically, whatever the outbound rules say. All rules are evaluated together, and when several SGs are attached their rules are combined.

A new SG allows no inbound traffic and all outbound traffic. The VPC's default SG also allows all traffic between its own members; you can't delete it, and AWS recommends creating specific groups rather than using it. Each SG has 60 inbound and 60 outbound rules by default, an interface can have 5 SGs by default (up to 16), and rules per SG multiplied by SGs per interface can't exceed 1,000.

Reference groups, not addresses

A rule's source can be a CIDR range, a prefix list, or another security group. Referencing a group means "anything that has this SG attached", so the rule keeps working as Auto Scaling adds and removes instances. In the running example the tiers are chained:

  1. ALB security groupAllows 443 from 0.0.0.0/0 (the internet).
  2. App security groupAllows 8080 only from the ALB security group.
  3. Database security groupAllows 5432 (PostgreSQL) only from the app security group.
Allow the app tier to receive traffic only from the load balancer (AWS CLI) 
aws ec2 authorize-security-group-ingress \
    --group-id sg-0app1111111111111 \
    --protocol tcp --port 8080 \
    --source-group sg-0alb1111111111111

Group references work inside one VPC and across VPC peering. Since September 2024 they also work across a transit gateway, but only in inbound rules, only when it's enabled on the transit gateway and the attachment, and not across transit gateway peering or through an inspection appliance. Since October 2024 one SG can be associated with several VPCs in the same Region, and shared through AWS RAM with accounts in the same organization.

"Allow only the web tier to reach the database, even as instances scale" points to a database SG rule that references the web tier's security group, not a list of IP addresses.

Network ACLs

A stateless filter on every subnet

A network ACL (NACL) is attached to a subnet and checks traffic entering and leaving it. It has allow and deny rules, numbered from 1 to 32766 and evaluated lowest number first; the first match decides and the rest are skipped, and a final * rule denies anything unmatched. It is stateless: return traffic must be allowed explicitly, in the other direction, on the client's ephemeral ports. Each subnet has exactly one NACL.

The default NACL allows all traffic in both directions. A custom NACL starts with only the deny-all rules, so it blocks everything until you add rules. Ephemeral port ranges differ by client (Amazon Linux uses 32768–61000; ELB, NAT gateways and Lambda use 1024–65535), so AWS suggests allowing 1024–65535 for return traffic and putting any deny rules for bad ports in that range at lower numbers. A NACL has 20 rules per direction by default (up to 40), costs nothing, and can only use CIDR ranges, never security groups or prefix lists.

Block one abusive address range before the allow rules on the public subnets' NACL (AWS CLI) 
# Rule 90 is evaluated before rule 100, so the deny wins for this range
aws ec2 create-network-acl-entry --network-acl-id acl-0pub111111111111 \
    --ingress --rule-number 90 --protocol tcp --port-range From=443,To=443 \
    --cidr-block 203.0.113.0/24 --rule-action deny

aws ec2 create-network-acl-entry --network-acl-id acl-0pub111111111111 \
    --ingress --rule-number 100 --protocol tcp --port-range From=443,To=443 \
    --cidr-block 0.0.0.0/0 --rule-action allow

"Block traffic from a specific IP address" can't be done with a security group, which has no deny rules. The answer is a NACL deny rule with a lower number than the allow rules, or AWS WAF for HTTP traffic.

Neither security groups nor NACLs can filter DNS queries to the Amazon-provided resolver, and NACLs don't filter instance metadata, DHCP or Amazon Time Sync traffic. Blocking DNS-based data exfiltration needs Route 53 Resolver DNS Firewall (in newer docs the resolver is called Route 53 VPC Resolver).

Route tables, gateways and NAT

Routes decide what is reachable at all

A route table says where traffic from a subnet can go. An internet gateway (one per VPC, free, highly available) is what makes internet traffic possible; a subnet whose route table has a route to it is a public subnet by definition. An instance there also needs a public IPv4 address or an Elastic IP. An egress-only internet gateway is the IPv6 version of "outbound only": it lets instances start IPv6 connections out, but nothing from the internet can start one in.

AWS's guidance is to give each subnet route table only the routes it needs. In the running example, the database subnets have no route to the internet at all.

NAT gateways

Instances in private subnets often need to reach the internet outbound (to download patches, call a payment API) without being reachable from it. A public NAT gateway does this for IPv4: private subnets route 0.0.0.0/0 to it, and it sends the traffic out through the internet gateway with its Elastic IP. A private NAT gateway has no Elastic IP and translates traffic to other VPCs or on-premises networks. A NAT gateway scales from 5 to 100 Gbps, supports TCP, UDP and ICMP, and has no security group (only the subnet's NACL applies).

The classic zonal NAT gateway is redundant only inside its own Availability Zone, so AWS recommends one in each AZ, with each private subnet routing to the one in its AZ. Since November 2025 there is also a Regional NAT gateway: one NAT gateway ID that expands across AZs automatically as workloads appear, needs no public subnet, and supports more IP addresses per AZ. It doesn't support private NAT and is billed per AZ it runs in. NAT instances, EC2 instances you configure and patch yourself, are the legacy alternative.

Create a Regional NAT gateway for the prod VPC (AWS CLI) 
# Automatic mode manages the addresses and the AZ expansion for you
aws ec2 create-nat-gateway --vpc-id vpc-0prod11111111111 --availability-mode regional

"Private instances must download updates from the internet but must not be reachable from it" points to a NAT gateway (or an egress-only internet gateway for IPv6). "Highly available" with zonal NAT gateways means one per AZ.

Guardrails and visibility

VPC Block Public Access

VPC Block Public Access (November 2024) blocks internet traffic through internet gateways and egress-only internet gateways for every VPC in a Region, in two modes: bidirectional, or ingress-only (which still allows outbound through NAT gateways). It overrides security groups, NACLs and route tables. You exclude specific VPCs or subnets (up to 50) that really need internet access, and an EC2 declarative policy can enforce it across the organization. It doesn't block private connectivity such as Site-to-Site VPN, Transit Gateway, Client VPN or Verified Access.

Flow logs and analyzers

VPC Flow Logs record metadata about accepted and rejected IP traffic for a VPC, subnet or interface, sent to CloudWatch Logs, S3 or Data Firehose, without affecting performance; they're how you see that a rule is too strict. Reachability Analyzer tests whether one resource can reach another and names the security group, NACL, route table or load balancer that blocks it. Network Access Analyzer looks for unintended paths, such as a database reachable from the internet.

Common ports worth knowing for rule questions: 22 SSH, 3389 RDP, 80 HTTP, 443 HTTPS, 3306 MySQL and Aurora MySQL, 5432 PostgreSQL, 1433 SQL Server, 1521 Oracle, 6379 Redis and Valkey, 2049 NFS (Amazon EFS), 53 DNS (TCP and UDP).

Network segmentation

Skill 1.2.2Determining network segmentation strategies (for example, using public subnets and private subnets)

Tiers in separate subnets

Public, private and isolated

Segmentation puts each tier where it can only be reached the way it should be. A public subnet has a route to the internet gateway; only things that must accept connections from the internet go there, usually load balancers and NAT gateways. A private subnet has no route to the internet gateway; instances there "can't communicate with the internet, even if they have public IP addresses", and reach out only through NAT. An isolated subnet (a private subnet with no NAT route either) suits databases that never need the internet.

The running example uses three subnets in each of three AZs:

  1. Public subnetsThe internet-facing ALB, routing 0.0.0.0/0 to the internet gateway.
  2. Private app subnetsEC2 and ECS tasks, routing 0.0.0.0/0 to the NAT gateway and S3 traffic to a gateway endpoint.
  3. Isolated database subnetsAurora PostgreSQL, with only the local VPC route.

Subnets give the coarse separation; the chained security groups from Skill 1.2.1 give the fine-grained one. Administrators reach instances with Systems Manager Session Manager instead of opening SSH or RDP from the internet or running bastion hosts in public subnets.

Putting an application server in a public subnet "with a security group that only allows the load balancer" works, but it isn't the most secure design: the server still has a path to the internet if a rule is changed. Exam answers put application and database tiers in private subnets.

Keeping AWS service traffic private: VPC endpoints

Public endpoints and the alternative

Every AWS service has public endpoints such as https://s3.us-east-1.amazonaws.com. From a private subnet, reaching them means a route through a NAT gateway and the internet gateway; the traffic stays on the AWS network, but the subnet needs an internet path and you pay NAT processing charges. VPC endpoints remove both.

Gateway endpoints

Gateway endpoints exist only for Amazon S3 and DynamoDB, cost nothing, and work through the route table: AWS adds a route whose destination is the service's prefix list and whose target is the endpoint. They don't use PrivateLink, they only reach the service in the same Region (requests to an S3 bucket in another Region still need the internet path), and they can't be used from on-premises networks, peered VPCs or a transit gateway.

Add an S3 gateway endpoint to the private app route tables (AWS CLI) 
aws ec2 create-vpc-endpoint --vpc-id vpc-0prod11111111111 \
    --vpc-endpoint-type Gateway \
    --service-name com.amazonaws.us-east-1.s3 \
    --route-table-ids rtb-0appa111111111111 rtb-0appb111111111111 rtb-0appc111111111111

Interface endpoints (AWS PrivateLink)

Interface endpoints put an elastic network interface with a private IP into each chosen subnet for almost any AWS service (Secrets Manager, KMS, ECR, CloudWatch Logs, and S3 too). With private DNS on, the service's normal name resolves to those private IPs, so code doesn't change. They're billed per endpoint per AZ per hour plus per GB, have security groups, and can be reached from on-premises over VPN or Direct Connect, which is why S3 has both types. The same technology lets you publish your own service to other VPCs and accounts (an endpoint service behind a Network Load Balancer), and since late 2024 endpoints can reach services in another Region and shared resources such as an RDS database directly.

Policies on both ends

An endpoint policy limits what can be done through the endpoint (by default, everything); it never grants more than IAM and resource policies allow. On the other end, a bucket policy can require that requests come through your endpoint with aws:SourceVpce (one endpoint) or aws:SourceVpc (any endpoint in a VPC).

Bucket policy: the uploads bucket accepts requests only through the prod VPC's endpoint (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OnlyThroughProdEndpoint",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::example-prod-uploads", "arn:aws:s3:::example-prod-uploads/*"],
      "Condition": { "StringNotEquals": { "aws:SourceVpce": "vpce-0s3a1111111111111" } }
    }
  ]
}

This Deny grants nothing by itself, and it also blocks the S3 console, whose requests don't come through the endpoint.

"Private instances must reach S3 or DynamoDB without internet access, at the lowest cost" points to a gateway endpoint. "Reach another AWS service privately", or "reach S3 privately from on-premises", points to an interface endpoint.

Inspecting traffic between segments

Network Firewall, Gateway Load Balancer and DNS Firewall

When rules by port and address aren't enough, traffic is routed through an inspection layer. AWS Network Firewall is a managed stateful firewall and intrusion prevention service (it runs Suricata-compatible rules, domain lists and TLS inspection) deployed as endpoints in a dedicated firewall subnet in each AZ, with route tables sending traffic through them. It can inspect traffic to and from internet gateways, NAT gateways, VPN and Direct Connect, and since June 2025 it can attach directly to a transit gateway, so a central inspection VPC is no longer required. Gateway Load Balancer does the same job for third-party firewall appliances, passing all IP traffic to them with GENEVE on port 6081. Route 53 Resolver DNS Firewall filters outbound DNS queries against allow or deny domain lists.

"Filter outbound traffic by domain name" or "intrusion prevention for all traffic leaving the VPCs" points to AWS Network Firewall. "Use our existing third-party firewall appliances" points to Gateway Load Balancer.

Services that secure applications

Skill 1.2.3Integrating AWS services to secure applications (for example, AWS Shield, AWS WAF, IAM Identity Center, AWS Secrets Manager)

Threats from outside AWS

What the edge services defend against

A distributed denial of service (DDoS) attack tries to exhaust capacity. At the network and transport layers (layers 3 and 4) that means floods of SYN or UDP packets or reflection attacks; at the application layer (layer 7) it means floods of valid-looking HTTP requests. Other application attacks abuse input: SQL injection slips database commands into a form field or query string, cross-site scripting (XSS) injects script that runs in other users' browsers, bots scrape content, and credential stuffing tries stolen passwords against the login page. Each maps to a control:

  • Layer 3 and 4 DDoS: AWS Shield Standard, and edge services (CloudFront, Route 53, Global Accelerator) that absorb attacks before they reach the VPC.
  • Layer 7 floods: AWS WAF rate-based rules and the Anti-DDoS managed rule group, CloudFront caching, and Shield Advanced automatic application-layer mitigation.
  • SQL injection and XSS: AWS WAF managed rule groups (the Core rule set covers XSS; the SQL database rule group covers SQL injection) or your own match statements.
  • Bots, credential stuffing and fake sign-ups: AWS WAF Bot Control and the Fraud Control account takeover prevention (ATP) and account creation fraud prevention (ACFP) rule groups.

AWS Shield

Standard and Advanced

Shield Standard is automatic and free for every customer and protects against the most common network and transport layer attacks; CloudFront, Route 53 hosted zones and Global Accelerator get the most comprehensive protection. Shield Advanced costs US$3,000 a month with a one-year commitment (one fee covers an organization's consolidated billing family) and adds protection you assign to specific resources: CloudFront distributions, Route 53 hosted zones, Global Accelerator accelerators, Elastic IPs (and the EC2 instances behind them), Application Load Balancers and Classic Load Balancers. A Network Load Balancer is protected only through its Elastic IPs. Shield Advanced also includes AWS WAF fees for protected resources up to set limits, automatic application-layer DDoS mitigation, and access to the Shield Response Team, which needs Business or Enterprise Support.

"DDoS protection at no extra cost" is Shield Standard, which is already on. "24/7 access to AWS DDoS experts", "protection against DDoS-related cost spikes" or "advanced protection for an ALB and CloudFront" points to Shield Advanced.

AWS WAF

A web application firewall in front of HTTP endpoints

AWS WAF inspects HTTP and HTTPS requests against a web ACL (the new console calls it a protection pack; the API is unchanged) of rules and rule groups, then allows, blocks, counts, or challenges with a CAPTCHA. It attaches to CloudFront (a global web ACL created in us-east-1), and regionally to an Application Load Balancer, an API Gateway REST API, AppSync, Cognito user pools, App Runner, Verified Access and Amplify. It can't attach to a Network Load Balancer or an API Gateway HTTP API, and each resource has one web ACL. AWS WAF Classic, the original version, reached end of support on 30 September 2025.

Rules can match IP sets, countries (geo match), headers, body content and request rates. AWS Managed Rules give ready-made groups: the Core rule set (common web exploits, XSS, oversized bodies, requests aimed at EC2 instance metadata), Known bad inputs (Log4j-style exploits), the SQL database group, IP reputation and anonymous IP lists, plus paid Bot Control and Fraud Control groups. A rate-based rule blocks a source that exceeds a request limit in a time window.

Two rules for the web ACL in front of the ALB: AWS's Core rule set, then a rate limit per client IP (JSON fragment of the Rules list) 
[
  {
    "Name": "aws-common",
    "Priority": 0,

The standard edge pattern

  1. Route 53Resolves the site's name; protected by Shield.
  2. CloudFront with AWS WAFAbsorbs volumetric attacks, caches content and filters requests at the edge.
  3. ALB in public subnetsAccepts traffic only from CloudFront (for example through CloudFront's managed prefix list in its security group), with its own web ACL if needed.
  4. Application in private subnetsAccepts traffic only from the ALB's security group.

AWS Firewall Manager

With many accounts, AWS Firewall Manager applies AWS WAF rules, Shield Advanced protection, security group policies, NACLs, Network Firewall and DNS Firewall policies across an AWS Organizations organization from one administrator account, and applies them automatically to new accounts and resources.

"Block SQL injection and cross-site scripting" points to AWS WAF on CloudFront, the ALB or API Gateway, never to security groups. "Apply the same WAF rules to every account automatically" points to Firewall Manager.

Signing users in to the application

Let the load balancer authenticate

An Application Load Balancer can authenticate users before a request reaches the application, with an authenticate-cognito action (an Amazon Cognito user pool, which can federate social and corporate identity providers) or an authenticate-oidc action (any OpenID Connect provider). It works only on HTTPS listeners; the ALB passes the user's claims to the targets in a signed x-amzn-oidc-data header. For the workforce, IAM Identity Center can be the single sign-on point for AWS managed applications and for SAML applications, using the same directory it uses for AWS account access. For machine-to-machine traffic, an ALB can also check client certificates with mutual TLS, and since November 2025 validate JWT access tokens.

TLS certificates with ACM

AWS Certificate Manager issues public certificates for free (exportable ones cost extra) and renews them automatically. A certificate must be in the same Region as the load balancer or API that uses it, and certificates for CloudFront must be in us-east-1. Public certificates are now valid for 198 days, following the industry move to shorter lifetimes, which matters only if you install them yourself.

Credentials and configuration

Secrets Manager

Database passwords, API keys and tokens shouldn't be in code, AMIs, user data or plain environment variables. AWS Secrets Manager stores them encrypted with KMS, controls access with IAM and resource policies, and rotates them. RDS, Aurora, DocumentDB and Redshift credentials can use managed rotation with no code; other secrets rotate through a Lambda function. Rotation can run as often as every four hours, and a secret can be replicated to other Regions for disaster recovery. It costs US$0.40 per secret per month plus US$0.05 per 10,000 API calls. AWS recommends it over Lambda environment variables for database credentials.

Rotate the Aurora application secret on the 1st and 15th of each month (AWS CLI) 
aws secretsmanager rotate-secret --secret-id prod/web/aurora-app \
    --rotation-rules '{"ScheduleExpression": "cron(0 16 1,15 * ? *)", "Duration": "2h"}'

Parameter Store

Systems Manager Parameter Store holds configuration values and, as SecureString parameters, secrets. The standard tier is free (10,000 parameters of up to 4 KB per Region); the advanced tier (100,000 parameters, 8 KB, parameter policies such as expiry, cross-account sharing) is charged and can't be downgraded. It has no built-in rotation.

"Store database credentials and rotate them automatically" points to Secrets Manager. "Store configuration values and feature settings cheaply" points to Parameter Store.

Instance credentials and IMDSv2

An EC2 instance gets its role credentials from the instance metadata service. Version 2 (IMDSv2) requires a session token obtained with a PUT request, which blocks most server-side request forgery (SSRF) attacks that trick an application into fetching the credentials. By default instances accept both versions; Amazon Linux 2023 AMIs require IMDSv2, and an account can make IMDSv2 the default for new launches (or enforce it, so launches that allow IMDSv1 fail). For containers on EC2, set the hop limit to 2.

Make IMDSv2 the default for new instances in this Region of the account (AWS CLI) 
aws ec2 modify-instance-metadata-defaults --http-tokens required --http-put-response-hop-limit 2

External network connections

Skill 1.2.4Securing external network connections to and from the AWS Cloud (for example, VPN, AWS Direct Connect)

AWS Site-to-Site VPN

Encrypted tunnels over the internet

Site-to-Site VPN connects an on-premises network to AWS with IPsec-encrypted tunnels over the internet. On the AWS side it ends on a virtual private gateway (one VPC) or a transit gateway (many VPCs, and the option for IPv6); on-premises it ends on your router, represented by a customer gateway resource. Every connection has two tunnels to different AWS endpoints for redundancy. A standard tunnel carries up to 1.25 Gbps; since September 2025, large bandwidth tunnels carry up to 5 Gbps on a transit gateway or Cloud WAN, and on a transit gateway ECMP over several tunnels (with BGP) adds more. Accelerated VPN sends the tunnels through Global Accelerator's edge network for steadier performance. It can be set up in minutes, which makes it the usual first connection and the usual backup.

AWS Client VPN

Remote users, not sites

Client VPN is a managed VPN for individual users' devices. Users authenticate with Active Directory, mutual certificates, or SAML single sign-on (certificates can be combined with AD or SAML), and the endpoint always needs a server certificate in ACM. Use it when staff working from home must reach private resources in the VPC.

AWS Direct Connect

A private, dedicated link

Direct Connect links your network to AWS over a private connection at a Direct Connect location, for consistent bandwidth and latency and lower data transfer cost. Dedicated connections are 1, 10, 100 or 400 Gbps ports; hosted connections from partners range from 50 Mbps to 25 Gbps. Ordering takes weeks, not minutes. Traffic uses virtual interfaces: a private VIF reaches a VPC (through a virtual private gateway or a Direct Connect gateway), a public VIF reaches AWS public endpoints such as S3 (not the internet), and a transit VIF reaches transit gateways through a Direct Connect gateway.

Direct Connect is not encrypted

AWS states that Direct Connect does not encrypt traffic in transit by default. Two ways to add encryption:

  • MACsec (layer 2, between your router and the AWS device) on dedicated 10, 100 and 400 Gbps connections at supported locations. It isn't available on 1 Gbps or hosted connections.
  • Site-to-Site VPN over Direct Connect: IPsec tunnels running over the private link, which works at any speed.

Resilience

AWS's Direct Connect Resiliency Toolkit describes three models: maximum resiliency (separate connections on separate devices in more than one location, for the 99.99% SLA), high resiliency (one connection in each of two locations, 99.9%), and development and test (separate devices in one location). A cheaper common design pairs one Direct Connect connection with a Site-to-Site VPN as backup.

"Consistent network performance", "large daily data transfers" or "private connection that doesn't use the internet" points to Direct Connect. "Encrypted" plus "quickly" or "low cost" points to Site-to-Site VPN. "Direct Connect, and the traffic must be encrypted" points to MACsec or VPN over Direct Connect.

AWS Verified Access

Application access without a VPN

AWS Verified Access gives users access to internal applications without a VPN, following zero-trust principles: every request is checked against the user's identity and their device's security state from trusted providers. It started with HTTP(S) applications behind load balancers and network interfaces; since February 2025 it also supports non-HTTP protocols, CIDR ranges and RDS databases, and it can be protected with AWS WAF.

Key takeaways

  • Security groups: on interfaces, allow-only, stateful, reference other groups to chain tiers (inbound references now work across a transit gateway). NACLs: on subnets, allow and deny, numbered with first match winning, stateless, so open ephemeral ports 1024–65535 for return traffic.
  • Public subnet = route to an internet gateway. NAT gateways give private subnets outbound IPv4 only, have no security group, and zonal ones are needed in every AZ; the Regional NAT gateway (November 2025) spans AZs itself. VPC Block Public Access overrides everything else for internet paths.
  • Segment into public (load balancers), private (application) and isolated (database) subnets; use Session Manager instead of public bastions.
  • Gateway endpoints: S3 and DynamoDB only, free, route-table based, same Region, not from on-premises. Interface endpoints: almost any service, ENIs with private DNS, hourly cost, usable from on-premises. Lock buckets to an endpoint with aws:SourceVpce.
  • Inspection: Network Firewall (managed IPS, domain filtering, now attachable to a transit gateway), Gateway Load Balancer (third-party appliances), DNS Firewall (DNS exfiltration).
  • Shield Standard is free and automatic; Shield Advanced ($3,000/month, one-year term) adds the response team, WAF fees and protection for named resources (NLB only through Elastic IPs). AWS WAF on CloudFront, ALB, API Gateway REST and more (not NLB or HTTP APIs) stops SQL injection, XSS, bots and floods; Firewall Manager applies it everywhere.
  • Secrets Manager stores and rotates secrets (managed rotation for RDS and Aurora, every 4 hours at most); Parameter Store has no rotation. Require IMDSv2. ACM certificates for CloudFront live in us-east-1.
  • GuardDuty detects threats, Macie finds sensitive data in S3, Inspector finds vulnerabilities, Security Hub CSPM checks posture and the new Security Hub prioritizes across them.
  • Site-to-Site VPN: IPsec, two tunnels, minutes to set up. Direct Connect: private, consistent, weeks to order, not encrypted (add MACsec on dedicated 10/100/400 Gbps, or VPN over it). Client VPN for users; Verified Access for per-application access without a VPN.
