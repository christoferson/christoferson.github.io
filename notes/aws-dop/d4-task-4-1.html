Overview

Task statement 4.1

Configure the collection, aggregation, and storage of logs and metrics.

You can't operate what you can't see. This task covers the plumbing of observability: which telemetry exists, how it reaches CloudWatch (or a central store), how log lines become metrics, how long it's kept, who can read it and how it's encrypted. Typical scenarios: "memory usage isn't visible for EC2 instances", "count application errors and alarm on them", "stream all logs from 50 accounts to one place", or "logs must be encrypted with a customer managed key and kept for 7 years".

How to monitor applications and infrastructure

Knowledge

Monitor every layer, and start from what users experience. The four golden signals work for almost any service:

  • Latency: how long requests take (track percentiles such as p99, not just averages).
  • Traffic: how much demand there is (requests per second).
  • Errors: the rate of failed requests (5xx responses, exceptions).
  • Saturation: how full the system is (CPU, memory, queue depth, connections).
TelemetryAWS source
Service metricsCloudWatch, automatically, for almost every AWS service (EC2 CPU, ALB request count and 5xx, RDS connections, Lambda errors and duration)
Operating system metricsThe CloudWatch agent (memory, disk space, processes): EC2 doesn't report these by itself
Application logsCloudWatch Logs, through the agent, the Lambda runtime, ECS log drivers or Fluent Bit
AWS API activityAWS CloudTrail
Network flowsVPC Flow Logs, to CloudWatch Logs, S3 or Firehose
Traces and service mapsAWS X-Ray; CloudWatch Application Signals for application performance monitoring
User experienceCloudWatch Synthetics canaries (scripted checks) and CloudWatch RUM (real browser sessions)
Container and serverless detailContainer Insights (ECS, EKS), Lambda Insights
Open source stacksAmazon Managed Service for Prometheus, Amazon Managed Grafana, Amazon OpenSearch Service

Seeing many accounts in one place

CloudWatch cross-account observability links source accounts to a monitoring account. From the monitoring account you can search and graph metrics, query logs, view traces and alarm on data from every linked account, without copying it.

  • Sink: created in the monitoring account; defines what may be shared to it.
  • Link: created in each source account, connecting to the sink (Organizations or StackSets can do this for every account).

"The operations team needs one console to view metrics, logs and traces from all workload accounts" points to CloudWatch cross-account observability with a monitoring account. Copying logs around isn't needed just to view them.

  • Every unique combination of dimensions is a separate metric. OrdersPlaced with Service=checkout and OrdersPlaced with Service=checkout, Region=eu are different metrics, and CloudWatch doesn't aggregate one into the other.
  • EC2 basic monitoring sends metrics every 5 minutes; detailed monitoring every minute (charged).
  • High-resolution metrics allow alarms with 10-second or 30-second periods.

Older data is rolled up into coarser resolutions automatically. Metrics can't be deleted; they expire when no new data arrives. For longer retention, stream or export metrics to S3.

Publishing custom metrics

From code or scripts, with PutMetricData:

aws cloudwatch put-metric-data \
  --namespace Orders/App \
  --metric-name OrdersPlaced \
  --dimensions Service=checkout,Environment=prod \
  --value 1 --unit Count \
  --storage-resolution 1               # high resolution; omit for standard (60)

From Lambda functions and containers, the Embedded Metric Format (EMF) is cheaper and faster: write a structured JSON log line, and CloudWatch extracts the metric from it asynchronously, with no API call in the request path.

EMF log line 
{
  "_aws": {
    "Timestamp": 1767225600000,
    "CloudWatchMetrics": [{
      "Namespace": "Orders/App",
      "Dimensions": [["Service"]],
      "Metrics": [{ "Name": "CheckoutLatency", "Unit": "Milliseconds" }]
    }]
  },
  "Service": "checkout",
  "CheckoutLatency": 182,
  "orderId": "o-7781"                    // extra fields stay searchable in the log
}

Using a high-cardinality value (such as a user ID or order ID) as a dimension creates a separate metric for each value, which is costly and unhelpful. Keep IDs as log fields, and use dimensions for a small set of values such as service or environment.

Real-time log ingestion

Knowledge

CloudWatch Logs organizes data as log groups (one per application or source, holding settings such as retention and encryption), which contain log streams (one per instance, container or function environment), which contain log events.

SourceHow logs get in
EC2 and on-premises serversThe CloudWatch agent tails log files
LambdaAutomatically: anything written to stdout or stderr goes to /aws/lambda/<function>
ECS and FargateThe awslogs log driver, or FireLens (Fluent Bit) to route to CloudWatch, Firehose, OpenSearch or third parties
EKSFluent Bit as a DaemonSet (Container Insights), or the CloudWatch Observability add-on
AWS servicesVPC Flow Logs, API Gateway access logs, Route 53 Resolver query logs, RDS logs, CloudTrail: each can deliver to CloudWatch Logs
High-volume streamsProducers write to Kinesis Data Streams or directly to Amazon Data Firehose formerly Kinesis Data Firehose
  • Amazon Data Firehose: buffers incoming records (by size or time), optionally transforms them with Lambda or converts them to Parquet, and delivers them to S3, Redshift, OpenSearch, Splunk or HTTP endpoints. It's near real time (buffering adds seconds to minutes) and fully managed.
  • Kinesis Data Streams: real time with milliseconds of latency, ordered per shard, replayable, for custom consumers.
  • Live Tail: watch log events in CloudWatch Logs as they arrive, filtered, for interactive troubleshooting.
  • Log classes: Standard (all features) and Infrequent Access (lower ingestion cost with a reduced feature set, for logs you rarely query).

Encryption options for logs and metrics

Knowledge
StoreAt restIn transit
CloudWatch LogsAlways encrypted with service-managed keys; optionally a customer managed KMS key per log groupTLS
CloudWatch metricsEncrypted by the serviceTLS
Amazon S3SSE-S3 (default), SSE-KMS, DSSE-KMS (two layers), or client-side encryption before uploadTLS; a bucket policy can deny non-TLS requests
CloudTrail log filesSSE-S3 by default; SSE-KMS with a customer managed key as an optionTLS
Kinesis Data Streams, Data FirehoseServer-side encryption with KMSTLS
OpenSearch ServiceEncryption at rest with KMSNode-to-node encryption and HTTPS required
  • Server-side encryption: AWS encrypts data when it's stored.
  • Client-side encryption: you encrypt before sending, so AWS never sees plaintext (for example, with the AWS Encryption SDK), at the cost of managing keys and losing server-side search on the content.
  • Customer managed keys: give you control over who can decrypt (key policy), audit of every use (CloudTrail), rotation, and the ability to disable access by disabling the key.

Masking sensitive data

Encryption doesn't stop authorized readers from seeing a credit card number in a log line. CloudWatch Logs data protection policies detect and mask sensitive data (credentials, financial and personal data identifiers) as it's ingested; only principals with logs:Unmask can see the original. Findings can be sent to CloudWatch Logs, S3 or Firehose for audit.

Securely storing and managing logs

Skill

Logs are evidence. Store them where the people and systems being logged can't change or delete them.

  1. Collect in each accountApplication logs to CloudWatch Logs; CloudTrail as an organization trail; Config and VPC Flow Logs enabled everywhere.
  2. CentralizeDeliver to a dedicated Log Archive account: the organization trail writes there directly, and subscription filters stream application logs through Firehose to its S3 bucket.
  3. Protect the bucketBlock Public Access, SSE-KMS, versioning, Object Lock for retention, a bucket policy denying non-TLS access and deletion, and an SCP preventing changes to the bucket.
  4. Prove integrityCloudTrail log file validation writes signed digest files, so you can show logs weren't altered.
  5. Grant read access narrowlySecurity teams get read-only roles; nobody gets delete permissions on the archive.
  • Protecting log groups: restrict logs:DeleteLogGroup, logs:PutRetentionPolicy and logs:DisassociateKmsKey with IAM or SCPs, so operators can read logs but not destroy them.
  • Searching archived logs: query the S3 archive with Athena, or keep recent logs in OpenSearch or CloudWatch Logs for fast search.

"Logs must be immutable and kept for 7 years for auditors" points to a central S3 bucket with Object Lock (compliance mode) and lifecycle transitions to Glacier storage classes. CloudWatch Logs retention alone isn't tamper-proof.

Creating CloudWatch metrics from log events using metric filters

Skill

A metric filter watches a log group, matches events with a filter pattern, and publishes a number to a CloudWatch metric for each match. You can then graph and alarm on log content.

Example: count application errors from JSON logs

Assume the application writes JSON lines such as {"level":"ERROR","service":"checkout","msg":"payment declined"} to /app/orders.

error-metric-filter.yml 
OrdersErrorFilter:
  Type: AWS::Logs::MetricFilter
  Properties:
    LogGroupName: /app/orders
    FilterPattern: '{ $.level = "ERROR" }'          # JSON field match
    MetricTransformations:
      - MetricNamespace: Orders/App
        MetricName: ErrorCount
        MetricValue: "1"                            # add 1 per matching event
        Unit: Count
        Dimensions:
          - Key: Service   # dimension taken from the log field
            Value: $.service

OrdersErrorAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: Orders/App
    MetricName: ErrorCount
    Dimensions: [{ Name: Service, Value: checkout }]
    Statistic: Sum
    Period: 60
    EvaluationPeriods: 5
    Threshold: 10
    ComparisonOperator: GreaterThanThreshold
    TreatMissingData: notBreaching                 # no errors logged means no data, which is fine
    AlarmActions: [!Ref OpsTopic]
  • Metric value from the log: use a field (MetricValue: $.latencyMs) to publish numbers such as latency, not just counts.
  • Default value: setting DefaultValue: 0 publishes zero when nothing matches, so the metric has no gaps. (You can't combine it with dimensions.)
  • Security monitoring: metric filters on the CloudTrail log group are how CIS benchmarks alarm on root user activity, console sign-in failures or IAM policy changes.

Metric filters only apply to log events ingested after the filter is created. They don't backfill. To analyze history, query it with Logs Insights.

Creating CloudWatch metric streams

Skill

A metric stream continuously sends CloudWatch metrics, within a few minutes of collection, to an Amazon Data Firehose delivery stream. From there they go to S3 (for a long-term data lake) or to partner tools such as Datadog, Dynatrace, New Relic, Splunk or Sumo Logic. It replaces polling GetMetricData on a schedule.

metric-stream.yml 
AllMetricsToS3:
  Type: AWS::CloudWatch::MetricStream
  Properties:
    Name: metrics-to-data-lake
    FirehoseArn: !GetAtt MetricsFirehose.Arn          # Firehose delivers to S3
    RoleArn: !GetAtt MetricStreamRole.Arn            # allows firehose:PutRecord and PutRecordBatch
    OutputFormat: opentelemetry1.0                  # or json, opentelemetry0.7
    IncludeFilters:
      - { Namespace: AWS/EC2 }
      - { Namespace: AWS/ApplicationELB }
      - { Namespace: Orders/App }
    StatisticsConfigurations:                       # add percentiles to the default statistics
      - IncludeMetrics: [{ Namespace: AWS/ApplicationELB, MetricName: TargetResponseTime }]
        AdditionalStatistics: [p99]
  • Filters: include or exclude whole namespaces, or specific metric names.
  • Cross-account: a stream in a monitoring account can include metrics from linked source accounts.

"Send all CloudWatch metrics to a third-party monitoring tool in near real time" or "keep metrics longer than 15 months" points to a metric stream to Firehose.

Collecting custom metrics (CloudWatch agent)

Skill

The CloudWatch agent collects what the hypervisor can't see: memory, disk space, swap, processes and network details from inside the OS. It also tails log files, and can receive StatsD, collectd and OpenTelemetry data. It runs on EC2, on-premises servers, and as part of Container Insights.

Install and configure it at scale with Systems Manager

  1. Store the configurationPut the agent's JSON configuration in Parameter Store, for example AmazonCloudWatch-linux-web.
  2. Install the agentA State Manager association runs AWS-ConfigureAWSPackage with the package AmazonCloudWatchAgent on targeted instances.
  3. Apply the configurationRun AmazonCloudWatch-ManageAgent with the configuration source set to the Parameter Store parameter. A configuration change only needs this step again.
AmazonCloudWatch-linux-web (agent configuration) 
{
  "agent": { "metrics_collection_interval": 60 },
  "metrics": {
    "namespace": "CWAgent",
    "append_dimensions": {
      "InstanceId": "${aws:InstanceId}",
      "AutoScalingGroupName": "${aws:AutoScalingGroupName}"
    },
    "aggregation_dimensions": [["AutoScalingGroupName"]],
    "metrics_collected": {
      "mem": {
        "measurement": ["mem_used_percent"]
      },
      "disk": {
        "measurement": ["used_percent"],
        "resources": ["/"]
      }
    }
  },
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "file_path": "/var/log/nginx/access.log",
            "log_group_name": "/web/nginx/access",
            "log_stream_name": "{instance_id}",
            "retention_in_days": 30
          }
        ]
      }
    }
  }
}
  • append_dimensions: tags each metric with the instance ID and Auto Scaling group.
  • aggregation_dimensions: also publishes a rolled-up version per Auto Scaling group, so you can alarm on the group as a whole.
  • Retention: retention_in_days sets the retention when the agent creates the log group.

"Scale the Auto Scaling group on memory utilization" requires the CloudWatch agent publishing mem_used_percent with the AutoScalingGroupName aggregation dimension, then a target tracking policy on that custom metric.

Managing log storage lifecycles

Skill

By default, CloudWatch log groups never expire, so storage costs grow forever. Set retention on every log group (from 1 day up to 10 years), and move long-term logs to S3, which is far cheaper.

log-group.yml 
OrdersLogGroup:
  Type: AWS::Logs::LogGroup
  Properties:
    LogGroupName: /app/orders
    RetentionInDays: 30                            # searchable in CloudWatch for 30 days
    KmsKeyId: !GetAtt LogsKey.Arn                  # customer managed key
log-archive-bucket.yml (lifecycle) 
LifecycleConfiguration:
  Rules:
    - Id: archive-logs
      Status: Enabled
      Transitions:
        - StorageClass: STANDARD_IA
          TransitionInDays: 30
        - StorageClass: GLACIER
          TransitionInDays: 90
        - StorageClass: DEEP_ARCHIVE
          TransitionInDays: 365
      ExpirationInDays: 2555                         # about 7 years
Moving logs to S3Behavior
Export task (CreateExportTask)A one-off batch copy of a time range; can take hours, and only one export task per account can run at a time. Not real time
Subscription filter to FirehoseContinuous, near real-time delivery of new events to S3. The usual choice for ongoing archiving

To enforce retention across many accounts, use the AWS Config rule cw-loggroup-retention-period-check with an automatic remediation that sets retention on non-compliant log groups.

Processing log data with CloudWatch Logs subscriptions

Skill

A subscription filter sends matching log events from a log group, in near real time, to:

  • Kinesis Data Streams: custom real-time processing, or a cross-account hub.
  • Amazon Data Firehose: delivery to S3, OpenSearch, Splunk and other destinations.
  • Lambda: custom processing, alerting or enrichment.
  • Amazon OpenSearch Service: set up through a Lambda function that the console creates for you.

A log group can have up to two subscription filters. An account-level subscription filter applies to every log group in the account (with optional exclusions).

subscription-to-firehose.yml 
OrdersToFirehose:
  Type: AWS::Logs::SubscriptionFilter
  Properties:
    LogGroupName: /app/orders
    FilterPattern: ""                                # empty: every event
    DestinationArn: !GetAtt LogArchiveFirehose.Arn
    RoleArn: !GetAtt LogsToFirehoseRole.Arn           # assumed by logs.amazonaws.com, allows firehose:PutRecord*

Central log aggregation across accounts

Assume workload accounts must send application logs to the Log Archive account 444444444444:

  1. Create the receiving streamIn 444444444444, a Kinesis data stream (or Firehose delivery stream) that feeds S3 or OpenSearch.
  2. Create a CloudWatch Logs destinationA destination in 444444444444 that points at the stream, with an access policy allowing the workload accounts (or the whole organization) to subscribe.
  3. Subscribe in each workload accountSubscription filters (or an account-level policy) in each account target the destination's ARN.
  4. Deliver and storeFirehose batches the events into the protected archive bucket and, optionally, into OpenSearch for search.

Data delivered by a subscription filter is base64-encoded and gzip-compressed, with several log events in each record. A Lambda function or Firehose transformation must decode and decompress it before processing.

Searching log data with filter patterns and CloudWatch Logs Insights

Skill

Filter pattern syntax

Filter patterns are used by metric filters, subscription filters, filter-log-events and the console search:

PatternMatches
ERROREvents containing the term ERROR
ERROR ExceptionEvents containing both terms
?ERROR ?WARNEvents containing either term
"connection refused"The exact phrase
ERROR -HealthCheckERROR but not HealthCheck
{ $.statusCode >= 500 }JSON events with a numeric field at or above 500
{ $.level = "ERROR" && $.service = "checkout" }JSON events matching both conditions
[ip, user, timestamp, request, status = 5*, bytes]Space-delimited logs (such as web server access logs) whose 5th field starts with 5

CloudWatch Logs Insights

Logs Insights is an interactive query language for one or many log groups. It discovers JSON fields automatically and charges by the data scanned.

Errors per 5 minutes 
fields @timestamp, @message
| filter level = "ERROR"
| stats count(*) as errors by bin(5m)
| sort errors desc
The 10 slowest requests 
fields @timestamp, path, latencyMs
| filter ispresent(latencyMs)
| sort latencyMs desc
| limit 10
Lambda memory and duration from REPORT lines 
filter @type = "REPORT"
| stats max(@maxMemoryUsed / 1000 / 1000) as maxMemoryMB,
        avg(@duration) as avgDurationMs,
        count(*) as invocations
  by bin(1h)
Extracting a value from unstructured text 
parse @message /status=(?<status>\d{3})/
| stats count(*) by status
  • Commands: fields, filter, stats (with count, avg, pct, bin), sort, limit, parse, dedup.
  • Saving and sharing: save queries, add results to dashboards, and generate queries from plain-language descriptions.
  • "Find the cause of last night's errors across several log groups": Logs Insights.
  • "Alarm on errors from now on": a metric filter plus an alarm.
  • "Query years of archived logs in S3": Athena.

Configuring encryption of log data (AWS KMS)

Skill

To encrypt a log group with a customer managed key, the key policy must let the CloudWatch Logs service in that Region use it, limited to your log groups through the encryption context:

key policy statement (logs key) 
{
  "Sid": "AllowCloudWatchLogsToUseKey",
  "Effect": "Allow",
  "Principal": {
    "Service": "logs.eu-west-1.amazonaws.com"
  },
  "Action": ["kms:Encrypt*", "kms:Decrypt*", "kms:ReEncrypt*", "kms:GenerateDataKey*", "kms:Describe*"],
  "Resource": "*",
  "Condition": {
    "ArnLike": {
      "kms:EncryptionContext:aws:logs:arn": "arn:aws:logs:eu-west-1:111111111111:log-group:*"
    }
  }
}

Then associate the key with a new log group (KmsKeyId in CloudFormation), or with an existing one:

aws logs associate-kms-key \
  --log-group-name /app/orders \
  --kms-key-id arn:aws:kms:eu-west-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab
  • Existing data: after association, new events are encrypted with the key; data ingested earlier stays encrypted as before.
  • Losing access: if the key is disabled or scheduled for deletion, CloudWatch Logs can't read or write the log group.
  • Elsewhere: set SSE-KMS on the archive bucket, the Firehose delivery stream, Kinesis streams and the CloudTrail trail, so logs stay encrypted with your keys end to end.

"Associating a KMS key with the log group fails with an access error" means the key policy doesn't allow the logs.<region>.amazonaws.com principal. IAM permissions on the caller alone aren't enough.

Key takeaways

  • Monitor the golden signals (latency, traffic, errors, saturation) at every layer. Cross-account observability gives one monitoring account a view of all accounts.
  • Metrics: namespace, name, dimensions (each combination is a separate metric), statistics, period. Standard resolution is 1 minute, high resolution 1 second. Retention rolls up to 15 months.
  • EC2 memory and disk need the CloudWatch agent; Lambda and containers can publish metrics cheaply with the Embedded Metric Format.
  • Ingestion: the agent for servers, automatic for Lambda, awslogs or FireLens for ECS, Fluent Bit for EKS, Firehose and Kinesis for high-volume streams.
  • Encryption: CloudWatch Logs is always encrypted; use a customer managed key per log group with a key policy for logs.<region>.amazonaws.com. Data protection policies mask sensitive data.
  • Store logs securely in a Log Archive account: Object Lock, SSE-KMS, CloudTrail log file validation, no delete permissions.
  • Metric filters turn log events into metrics (no backfill). Metric streams send metrics through Firehose to S3 or partners.
  • Set retention on every log group (default is forever); archive continuously through subscription filters to Firehose, not export tasks.
  • Subscription filters feed Kinesis, Firehose, Lambda or OpenSearch, and cross-account destinations; the payload is base64 gzip.
  • Search with filter patterns (terms, JSON, space-delimited, regex) and Logs Insights (fields, filter, stats, parse).
