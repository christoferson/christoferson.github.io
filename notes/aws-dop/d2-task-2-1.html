Overview

Task statement 2.1

Define cloud infrastructure and reusable components to provision and manage systems throughout their lifecycle.

Infrastructure as code (IaC) means describing infrastructure in files that are version-controlled, reviewed and deployed by a pipeline, just like application code. This task covers the whole lifecycle: creating stacks, changing them without breaking production, keeping running systems in their desired configuration, and turning good patterns into building blocks that every team reuses. Typical scenarios: "a template update replaced the production database", "deploy the same baseline to 200 accounts", or "developers must launch only approved, compliant resources".

Change management processes for IaC-based platforms

Knowledge

Update behaviors: what a change does to a resource

Changing a property in a template has one of three effects. The CloudFormation documentation lists which effect each property has, under "Update requires".

BehaviorEffectExample
No interruptionUpdated in place, with no outageChanging an EC2 instance's tags
Some interruptionUpdated in place, but restarted or briefly unavailableChanging an EC2 instance's type (it stops and starts)
ReplacementA new resource is created with a new physical ID, and the old one is deletedChanging an RDS instance's DBInstanceIdentifier, or a DynamoDB table's key schema

Replacement of a stateful resource (database, table, bucket) means data loss unless something protects it. That's why the change set preview, DeletionPolicy, UpdateReplacePolicy and stack policies exist.

Protecting stateful resources

database.yml 
OrdersDatabase:
  Type: AWS::RDS::DBInstance
  DeletionPolicy: Snapshot           # if the stack or resource is deleted, keep a final snapshot
  UpdateReplacePolicy: Snapshot      # if an update replaces it, snapshot the old one first
  Properties:
    Engine: postgres
    DBInstanceClass: db.r6g.large
    AllocatedStorage: "100"
    MasterUsername: appadmin
    ManageMasterUserPassword: true   # password kept in Secrets Manager
  • DeletionPolicy: what happens when the resource is removed from the template or the stack is deleted. Values: Delete (default for most resources), Retain, Snapshot (for resources that support snapshots), RetainExceptOnCreate.
  • UpdateReplacePolicy: what happens to the old resource when an update replaces it. Same values.
  • Termination protection: prevents the whole stack from being deleted.
Knowledge

Change sets: preview before you apply

A change set shows exactly which resources will be added, modified or removed, and whether each modification needs replacement. Nothing changes until you execute it. A safe change process looks like this:

  1. Propose the change in a pull requestReviewers read the template diff. Linting (cfn-lint) and policy checks (CloudFormation Guard) run automatically.
  2. Merge to the main branchThe pipeline starts.
  3. Create a change setA CloudFormation action with CHANGE_SET_REPLACE creates the preview without applying it.
  4. ApproveA manual approval action, with a link to the change set, gates production. Reviewers look especially for Replacement: True.
  5. Execute the change setA CloudFormation action with CHANGE_SET_EXECUTE applies exactly what was reviewed.
  6. Watch and roll back if neededRollback triggers watch CloudWatch alarms during the update and undo it if they fire.

Stack policies: block updates to critical resources

A stack policy is a JSON document attached to a stack that denies updates to selected resources, even for users with full IAM permissions. To change a protected resource, you must deliberately supply a temporary overriding policy for that one update.

stack-policy.json 
{
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "Update:*",
      "Principal": "*",
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": ["Update:Replace", "Update:Delete"],
      "Principal": "*",
      "Resource": "LogicalResourceId/OrdersDatabase"
    }
  ]
}
  • Update actions: Update:Modify, Update:Replace, Update:Delete and Update:*.
  • Default: once any stack policy is set, everything not explicitly allowed is denied. That's why the policy above starts with "allow everything".

"Prevent anyone from accidentally replacing or deleting the production database through a stack update" points to a stack policy denying Update:Replace and Update:Delete on it, plus DeletionPolicy: Retain or Snapshot. IAM policies alone can't express this per resource.

Drift detection

Drift is any difference between the template and the real resources, usually caused by manual console changes. Drift detection compares each supported resource's actual properties with the expected ones and reports IN_SYNC, MODIFIED, DELETED or NOT_CHECKED.

  • Drift isn't fixed automatically: correct it by updating the template to match, or by updating the stack to overwrite the manual change.
  • Scheduling it: the AWS Config managed rule cloudformation-stack-drift-detection-check checks stacks regularly and can notify or trigger remediation.
  • Adopting existing resources: resource import brings manually created resources under a stack's management, and a stack refactor can move resources between stacks.

CloudFormation Hooks

Hooks run checks before CloudFormation creates, updates or deletes a resource, and can fail or warn on the operation. Use them for proactive controls across an account, for example "no S3 bucket without encryption", written as Guard rules or as a Lambda function.

Knowledge

Rollback and recovery

  • Automatic rollback: if a create or update fails, CloudFormation returns the stack to its last stable state.
  • Rollback triggers: list CloudWatch alarms and a monitoring period (up to 180 minutes). If an alarm fires during the update or the monitoring period, the stack rolls back.
  • Preserving successful resources: on failure, CloudFormation can keep resources that were created successfully, so you can fix the problem and retry faster (useful in development).
  • Custom resources: a Lambda-backed custom resource must send a response to the pre-signed S3 URL CloudFormation gives it. If it never does, the stack waits until the custom resource times out (one hour by default).

When a rollback itself fails

A stack in UPDATE_ROLLBACK_FAILED couldn't return to its old state, often because something was changed or deleted outside CloudFormation. To recover:

  1. Find the resource that failed to roll backThe stack events show which one and why.
  2. Fix the cause outside CloudFormationFor example, recreate a manually deleted resource, or raise a service quota.
  3. Continue the rollbackRun ContinueUpdateRollback. If a resource can't be fixed, tell CloudFormation to skip it (--resources-to-skip).

A stack in UPDATE_ROLLBACK_FAILED can't be updated or deleted normally. Answers that say "delete and recreate the stack" or "update it again" are wrong; the fix is ContinueUpdateRollback.

Configuration management services and strategies

Knowledge

IaC creates resources. Configuration management keeps what runs on and inside them correct over time: installed software, settings, patches and application configuration.

Strategies

  • Desired state: declare what a system should look like, then apply it repeatedly so drift is corrected (Systems Manager State Manager).
  • Push vs pull: push sends changes now (Run Command); pull has agents check in and converge on a schedule (State Manager associations).
  • Detect and remediate: continuously evaluate resource settings, then fix violations automatically (AWS Config rules with remediation).
  • Separate configuration from code: keep values and feature flags outside the artifact, so behaviour changes without a redeploy (AppConfig, Parameter Store).
  • Immutable configuration: bake configuration into images and replace instances instead of changing them.

Composing and deploying IaC templates

Skill

AWS CloudFormation

This template uses the sections and functions the exam expects you to read fluently. It creates a bucket whose settings depend on the environment:

bucket.yml 
AWSTemplateFormatVersion: "2010-09-09"
Description: Application bucket with environment-specific settings

Parameters:
  Environment:
    Type: String
    AllowedValues: [dev, prod]
  LatestAmiId:                                               # resolved from Parameter Store at deploy time
    Type: AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>
    Default: /golden-ami/latest

Mappings:
  EnvSettings:
    dev:  { RetentionDays: 7 }
    prod: { RetentionDays: 365 }

Conditions:
  IsProd: !Equals [!Ref Environment, prod]

Resources:
  AppBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    Properties:
      BucketName: !Sub "orders-${Environment}-${AWS::AccountId}"   # pseudo parameter
      VersioningConfiguration:
        Status: !If [IsProd, Enabled, Suspended]                    # condition in a property
      LifecycleConfiguration:
        Rules:
          - Status: Enabled
            ExpirationInDays: !FindInMap [EnvSettings, !Ref Environment, RetentionDays]

  ReplicaBucket:
    Type: AWS::S3::Bucket
    Condition: IsProd                                          # created only in prod

Outputs:
  BucketArn:
    Value: !GetAtt AppBucket.Arn
    Export:
      Name: !Sub "${AWS::StackName}-BucketArn"                   # other stacks: !ImportValue
FunctionReturns
!RefA parameter's value, or a resource's main identifier (often its name or ID)
!GetAttA specific attribute of a resource, such as .Arn
!SubA string with ${...} variables substituted
!FindInMapA value from the Mappings section
!If, !Equals, !And, !Or, !NotConditional values
!ImportValueAn output exported by another stack in the same account and Region
!Select, !Split, !Join, !GetAZsList and string handling

Nested stacks or cross-stack references?

Nested stacksCross-stack references

Configuring instances from the template

  • AWS::CloudFormation::Init metadata: declares packages, files, commands and services. cfn-init, called from user data, applies it.
  • cfn-signal: reports success or failure to a CreationPolicy or WaitCondition.
  • cfn-hup: a daemon that detects metadata changes after a stack update and reruns cfn-init, so configuration changes reach running instances without replacing them.
Skill

AWS SAM

A SAM template is a CloudFormation template with Transform: AWS::Serverless-2016-10-31. During deployment CloudFormation expands each SAM resource into the full set of underlying resources (functions, roles, permissions, API stages, event source mappings).

template.yml 
Transform: AWS::Serverless-2016-10-31

Globals:                                    # shared settings for every function
  Function:
    Runtime: python3.12
    Timeout: 10
    Tracing: Active                         # X-Ray

Resources:
  OrdersTable:
    Type: AWS::Serverless::SimpleTable

  CreateOrderFunction:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: src/create_order/
      Handler: app.handler
      Policies:
        - DynamoDBCrudPolicy:                 # SAM policy template, scoped to one table
            TableName: !Ref OrdersTable
      Environment:
        Variables: { TABLE_NAME: !Ref OrdersTable }
      Events:
        CreateOrder:
          Type: HttpApi                       # creates the API, route and permission
          Properties: { Path: /orders, Method: post }
CommandDoes
sam buildInstalls dependencies and prepares each function
sam local invoke, sam local start-apiRuns functions and APIs locally in containers
sam deployPackages, uploads to S3 and deploys the stack through a change set
sam sync --watchPushes code changes to a development stack in seconds, bypassing full deployments (not for production)
sam pipeline initGenerates a CI/CD pipeline for the application
Skill

AWS CDK

A CDK app contains stacks, which contain constructs. Constructs come in three levels:

  • L1: generated one-to-one from CloudFormation (CfnBucket), with every property and no defaults.
  • L2: hand-written with sensible defaults and helper methods (Bucket, bucket.grantRead(role)).
  • L3 (patterns): several resources wired together (ApplicationLoadBalancedFargateService creates a cluster, service, load balancer and roles).
lib/orders-stack.ts 
import { Stack, StackProps, RemovalPolicy, Duration } from "aws-cdk-lib";
import * as s3 from "aws-cdk-lib/aws-s3";
import * as lambda from "aws-cdk-lib/aws-lambda";
import { Construct } from "constructs";

export class OrdersStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const bucket = new s3.Bucket(this, "Invoices", {      // L2 construct
      encryption: s3.BucketEncryption.KMS_MANAGED,
      enforceSSL: true,
      versioned: true,
      removalPolicy: RemovalPolicy.RETAIN,                 // becomes DeletionPolicy: Retain
    });

    const fn = new lambda.Function(this, "Generate", {
      runtime: lambda.Runtime.PYTHON_3_12,
      handler: "app.handler",
      code: lambda.Code.fromAsset("src/generate"),         // uploaded as an asset
      timeout: Duration.seconds(30),
    });

    bucket.grantWrite(fn);                                 // least-privilege IAM policy generated for you
  }
}
CommandDoes
cdk bootstrapCreates the CDKToolkit stack in each account and Region: an S3 bucket and ECR repository for assets, and deployment roles. Required once before the first deploy
cdk synthGenerates the CloudFormation templates and assets (the cloud assembly)
cdk diffCompares the app with what's deployed
cdk deployUploads assets and deploys the stacks through CloudFormation

"cdk deploy fails in a new account or Region because the assets bucket or deployment role doesn't exist" means the environment was never bootstrapped. For cross-account deployment from a pipeline, bootstrap the target with --trust <tooling-account-id>.

Applying CloudFormation StackSets across multiple accounts and Regions

Skill

A stack set deploys one template as stack instances in many account and Region combinations, from a single administrator account. Updating the stack set updates every instance.

Two permission models

Self-managedService-managed
RequiresNo AWS OrganizationsAWS Organizations with trusted access for StackSets enabled
RolesYou create AWSCloudFormationStackSetAdministrationRole in the administrator account and AWSCloudFormationStackSetExecutionRole in every target accountStackSets creates the roles it needs for you
TargetsAccount IDsOrganizational units (OUs) or accounts
New accountsAdd them yourselfAutomatic deployment: accounts that join a target OU get the stack automatically, and optionally lose it when they leave
Who administersAny accountThe management account or a delegated administrator member account

Example: a security baseline for every account in two OUs

baseline-stackset.yml 
SecurityBaseline:
  Type: AWS::CloudFormation::StackSet
  Properties:
    StackSetName: security-baseline
    PermissionModel: SERVICE_MANAGED
    AutoDeployment:
      Enabled: true                            # new accounts in these OUs get it automatically
      RetainStacksOnAccountRemoval: false     # remove it when an account leaves
    Capabilities: [CAPABILITY_NAMED_IAM]
    OperationPreferences:
      RegionConcurrencyType: PARALLEL
      MaxConcurrentPercentage: 25            # deploy to 25% of accounts at a time
      FailureTolerancePercentage: 10         # stop if more than 10% fail
    StackInstancesGroup:
      - DeploymentTargets:
          OrganizationalUnitIds: [ou-ab12-workloads, ou-ab12-sandbox]
        Regions: [us-east-1, eu-west-1]
    TemplateURL: https://tooling-artifacts.s3.amazonaws.com/security-baseline.yml

Operation preferences

  • Maximum concurrent accounts (count or percentage): how many accounts are deployed at the same time, per Region.
  • Failure tolerance (count or percentage): how many accounts can fail, per Region, before StackSets stops the operation in that Region.
  • Region order and concurrency: deploy Regions one after another (SEQUENTIAL, the safer choice, with a chosen order) or at the same time (PARALLEL).

With service-managed permissions, StackSets doesn't deploy to the organization's management account, even if you target the root OU. Deploy to the management account separately, for example with a regular stack.

  • "Every new account must automatically get the baseline": service-managed StackSets with automatic deployment on the OU.
  • "Accounts aren't in AWS Organizations": self-managed StackSets with the two IAM roles.
  • "Roll out cautiously and stop on problems": low maximum concurrency, low failure tolerance, and sequential Regions.

State Manager association

This association keeps the CloudWatch agent installed on every instance tagged Environment=prod, and rechecks every 30 days:

state-manager.yml 
CloudWatchAgentAssociation:
  Type: AWS::SSM::Association
  Properties:
    Name: AWS-ConfigureAWSPackage                  # SSM document to run
    Parameters:
      action: [Install]
      name: [AmazonCloudWatchAgent]
    Targets:
      - { Key: tag:Environment, Values: [prod] }
    ScheduleExpression: rate(30 days)              # reapplied on this schedule
    ComplianceSeverity: HIGH

New instances that match the target tag get the association automatically when they register with Systems Manager.

AWS AppConfig

AppConfig deploys configuration the way CodeDeploy deploys code: validated, gradual and reversible.

  1. Store the configuration profileA feature flag profile, or freeform JSON or YAML in AppConfig, Parameter Store, Secrets Manager or S3.
  2. Validate itA JSON Schema or a Lambda validator rejects bad configuration before it's deployed.
  3. Deploy with a strategyFor example, AppConfig.Linear20PercentEvery6Minutes or AppConfig.Canary10Percent20Minutes, or AppConfig.AllAtOnce.
  4. Watch alarmsIf a CloudWatch alarm on the environment fires during deployment or the bake time, AppConfig rolls back to the previous version.
  5. The application reads itThrough the AppConfig Agent (a Lambda extension or a container sidecar) that caches and refreshes configuration locally.

"Turn on a new feature for a percentage of traffic without deploying code, and roll back automatically if errors rise" points to AppConfig feature flags with a gradual deployment strategy and an alarm. Parameter Store alone has no gradual rollout or rollback.

Implementing infrastructure patterns, governance controls and security standards into reusable IaC

Skill

The goal: platform teams write the standard once (encryption, logging, tags, network rules), and application teams get it automatically by reusing a component instead of copying and editing templates.

CloudFormation modules

A module is a reusable template fragment registered in the CloudFormation registry as a type ending in ::MODULE. Teams use it like any resource, and CloudFormation expands it into the resources it contains.

app-stack.yml 
Resources:
  InvoiceBucket:
    Type: ExampleCorp::S3::SecureBucket::MODULE     # registered by the platform team
    Properties:
      BucketPrefix: invoices                       # encryption, TLS-only policy, logging, block public access built in
  • Sharing: register the module in each account and Region that uses it (StackSets can do this).
  • Updates: stacks pick up a new module version on their next update.

CDK construct libraries and Aspects

  • Shared construct library: publish your own L3 constructs (for example, SecureBucket or StandardService) as a package in CodeArtifact. Every team installs it and gets the standards by default.
  • Aspects: visit every construct in an app before synthesis and can add tags, change properties or raise errors. They're useful for rules such as "every bucket is encrypted".
  • cdk-nag: an open source set of Aspects that checks apps against rule packs such as AWS Solutions or NIST 800-53 and fails synthesis on violations.

AWS Service Catalog

Service Catalog lets administrators publish approved products (CloudFormation templates, or Terraform configurations) that users launch themselves, without needing permissions to create the underlying resources.

ConceptMeaning
ProductA versioned template, such as "standard VPC" or "approved RDS database"
PortfolioA collection of products, granted to IAM users, groups or roles
Launch constraintAn IAM role that Service Catalog uses to launch the product, so end users need only Service Catalog permissions
Template constraintRestricts parameter values, for example only t3.small or t3.medium
Tag optionsRequired or allowed tags applied to provisioned products
SharingShare a portfolio with other accounts or a whole organization or OU from a hub account

"Developers must create databases themselves but only in an approved configuration, and must not have direct RDS permissions" points to Service Catalog with a launch constraint.

Policy as code before deployment

CloudFormation Guard rules check templates in the pipeline (or in a Hook) and fail the build on violations:

s3-rules.guard 
let buckets = Resources.*[ Type == 'AWS::S3::Bucket' ]

rule s3_buckets_encrypted when %buckets !empty {
    %buckets.Properties.BucketEncryption exists
        << Every S3 bucket must declare encryption >>
}

rule s3_buckets_versioned when %buckets !empty {
    %buckets.Properties.VersioningConfiguration.Status == 'Enabled'
}
cfn-guard validate --data template.yml --rules s3-rules.guard   # non-zero exit on failure
ControlWhen it acts
cfn-lint, CloudFormation Guard in CodeBuildIn the pipeline, before deployment
CloudFormation HooksDuring every stack operation in the account, before resources change
Service Catalog constraintsWhen a user launches a product
SCPsOn every API call, preventive, across accounts

Key takeaways

  • CloudFormation is the default IaC answer; SAM for serverless; CDK for code and reusable constructs. Both SAM and CDK deploy through CloudFormation.
  • Know update behaviors: no interruption, some interruption, replacement. Replacement of stateful resources loses data unless protected.
  • Protect resources with DeletionPolicy and UpdateReplacePolicy (Retain or Snapshot), stack policies denying Update:Replace and Update:Delete, and termination protection.
  • Safe changes: change set, approval, execute, with rollback triggers on CloudWatch alarms. UPDATE_ROLLBACK_FAILED is fixed with ContinueUpdateRollback.
  • Drift detection reports manual changes but doesn't fix them. Custom resources must respond to the pre-signed URL, or the stack hangs.
  • StackSets: self-managed (two IAM roles, account IDs) or service-managed (Organizations, OUs, automatic deployment, no management account).
  • Systems Manager configures what's on servers; AWS Config evaluates AWS resource settings; AppConfig deploys app configuration and feature flags gradually with rollback. OpsWorks is retired.
  • Reusable standards: CloudFormation modules, CDK construct libraries and Aspects, Service Catalog products with launch constraints, and Guard rules in the pipeline.
