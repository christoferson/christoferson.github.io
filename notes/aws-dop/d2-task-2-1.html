Overview

Task statement 2.1

Define cloud infrastructure and reusable components to provision and manage systems throughout their lifecycle.

Infrastructure as code (IaC) means describing infrastructure in files that are version-controlled, reviewed and deployed by a pipeline, just like application code. This task covers the whole lifecycle: creating stacks, changing them without breaking production, keeping running systems in their desired configuration, and turning good patterns into building blocks that every team reuses. Typical scenarios: "a template update replaced the production database", "deploy the same baseline to 200 accounts", or "developers must launch only approved, compliant resources".

Change management processes for IaC-based platforms

Knowledge

Update behaviors: what a change does to a resource

Changing a property in a template has one of three effects. The CloudFormation documentation lists which effect each property has, under "Update requires".

BehaviorEffectExample
No interruptionUpdated in place, with no outageChanging an EC2 instance's tags
Some interruptionUpdated in place, but restarted or briefly unavailableChanging an EC2 instance's type (it stops and starts)
ReplacementA new resource is created with a new physical ID, and the old one is deletedChanging an RDS instance's DBInstanceIdentifier, or a DynamoDB table's key schema

Replacement of a stateful resource (database, table, bucket) means data loss unless something protects it. That's why the change set preview, DeletionPolicy, UpdateReplacePolicy and stack policies exist.

Protecting stateful resources

database.yml 
OrdersDatabase:
  Type: AWS::RDS::DBInstance
  DeletionPolicy: Snapshot           # if the stack or resource is deleted, keep a final snapshot
  UpdateReplacePolicy: Snapshot      # if an update replaces it, snapshot the old one first
  Properties:
    Engine: postgres
    DBInstanceClass: db.r6g.large
    AllocatedStorage: "100"
    MasterUsername: appadmin
    ManageMasterUserPassword: true   # password kept in Secrets Manager
  • DeletionPolicy: what happens when the resource is removed from the template or the stack is deleted. Values: Delete (default for most resources), Retain, Snapshot (for resources that support snapshots), RetainExceptOnCreate.
  • UpdateReplacePolicy: what happens to the old resource when an update replaces it. Same values.
  • Termination protection: prevents the whole stack from being deleted.
Knowledge

Change sets: preview before you apply

A change set shows exactly which resources will be added, modified or removed, and whether each modification needs replacement. Nothing changes until you execute it. A safe change process looks like this:

  1. Propose the change in a pull requestReviewers read the template diff. Linting (cfn-lint) and policy checks (CloudFormation Guard) run automatically.
  2. Merge to the main branchThe pipeline starts.
  3. Create a change setA CloudFormation action with CHANGE_SET_REPLACE creates the preview without applying it.
  4. ApproveA manual approval action, with a link to the change set, gates production. Reviewers look especially for Replacement: True.
  5. Execute the change setA CloudFormation action with CHANGE_SET_EXECUTE applies exactly what was reviewed.
  6. Watch and roll back if neededRollback triggers watch CloudWatch alarms during the update and undo it if they fire.

Stack policies: block updates to critical resources

A stack policy is a JSON document attached to a stack that denies updates to selected resources, even for users with full IAM permissions. To change a protected resource, you must deliberately supply a temporary overriding policy for that one update.

stack-policy.json 
{
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "Update:*",
      "Principal": "*",
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": ["Update:Replace", "Update:Delete"],
      "Principal": "*",
      "Resource": "LogicalResourceId/OrdersDatabase"
    }
  ]
}
  • Update actions: Update:Modify, Update:Replace, Update:Delete and Update:*.
  • Default: once any stack policy is set, everything not explicitly allowed is denied. That's why the policy above starts with "allow everything".

"Prevent anyone from accidentally replacing or deleting the production database through a stack update" points to a stack policy denying Update:Replace and Update:Delete on it, plus DeletionPolicy: Retain or Snapshot. IAM policies alone can't express this per resource.

Drift detection

Drift is any difference between the template and the real resources, usually caused by manual console changes. Drift detection compares each supported resource's actual properties with the expected ones and reports IN_SYNC, MODIFIED, DELETED or NOT_CHECKED.

  • Drift isn't fixed automatically: correct it by updating the template to match, or by updating the stack to overwrite the manual change.
  • Scheduling it: the AWS Config managed rule cloudformation-stack-drift-detection-check checks stacks regularly and can notify or trigger remediation.
  • Adopting existing resources: resource import brings manually created resources under a stack's management, and a stack refactor can move resources between stacks.

CloudFormation Hooks

Hooks run checks before CloudFormation creates, updates or deletes a resource, and can fail or warn on the operation. Use them for proactive controls across an account, for example "no S3 bucket without encryption", written as Guard rules or as a Lambda function.

Knowledge

Rollback and recovery

  • Automatic rollback: if a create or update fails, CloudFormation returns the stack to its last stable state.
  • Rollback triggers: list CloudWatch alarms and a monitoring period (up to 180 minutes). If an alarm fires during the update or the monitoring period, the stack rolls back.
  • Preserving successful resources: on failure, CloudFormation can keep resources that were created successfully, so you can fix the problem and retry faster (useful in development).
  • Custom resources: a Lambda-backed custom resource must send a response to the pre-signed S3 URL CloudFormation gives it. If it never does, the stack waits until the custom resource times out (one hour by default).

When a rollback itself fails

A stack in UPDATE_ROLLBACK_FAILED couldn't return to its old state, often because something was changed or deleted outside CloudFormation. To recover:

  1. Find the resource that failed to roll backThe stack events show which one and why.
  2. Fix the cause outside CloudFormationFor example, recreate a manually deleted resource, or raise a service quota.
  3. Continue the rollbackRun ContinueUpdateRollback. If a resource can't be fixed, tell CloudFormation to skip it (--resources-to-skip).

A stack in UPDATE_ROLLBACK_FAILED can't be updated or deleted normally. Answers that say "delete and recreate the stack" or "update it again" are wrong; the fix is ContinueUpdateRollback.

Configuration management services and strategies

Knowledge

IaC creates resources. Configuration management keeps what runs on and inside them correct over time: installed software, settings, patches and application configuration.

Strategies

  • Desired state: declare what a system should look like, then apply it repeatedly so drift is corrected (Systems Manager State Manager).
  • Push vs pull: push sends changes now (Run Command); pull has agents check in and converge on a schedule (State Manager associations).
  • Detect and remediate: continuously evaluate resource settings, then fix violations automatically (AWS Config rules with remediation).
  • Separate configuration from code: keep values and feature flags outside the artifact, so behaviour changes without a redeploy (AppConfig, Parameter Store).
  • Immutable configuration: bake configuration into images and replace instances instead of changing them.

Composing and deploying IaC templates

Skill

AWS CloudFormation

This template uses the sections and functions the exam expects you to read fluently. It creates a bucket whose settings depend on the environment:

bucket.yml 
AWSTemplateFormatVersion: "2010-09-09"
Description: Application bucket with environment-specific settings

Parameters:
  Environment:
    Type: String
    AllowedValues: [dev, prod]
  LatestAmiId:                                               # resolved from Parameter Store at deploy time
    Type: AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>
    Default: /golden-ami/latest

Mappings:
  EnvSettings:
    dev:  { RetentionDays: 7 }
    prod: { RetentionDays: 365 }

Conditions:
  IsProd: !Equals [!Ref Environment, prod]

Resources:
  AppBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    Properties:
      BucketName: !Sub "orders-${Environment}-${AWS::AccountId}"   # pseudo parameter
      VersioningConfiguration:
        Status: !If [IsProd, Enabled, Suspended]                    # condition in a property
      LifecycleConfiguration:
        Rules:
          - Status: Enabled
            ExpirationInDays: !FindInMap [EnvSettings, !Ref Environment, RetentionDays]

  ReplicaBucket:
    Type: AWS::S3::Bucket
    Condition: IsProd                                          # created only in prod

Outputs:
  BucketArn:
    Value: !GetAtt AppBucket.Arn
    Export:
      Name: !Sub "${AWS::StackName}-BucketArn"                   # other stacks: !ImportValue

!GetAttA specific attribute of a resource, such as .Arn
!SubA string with ${...} variables substituted
!FindInMapA value from the Mappings section
!If, !Equals, !And, !Or, !NotConditional values
!ImportValueAn output exported by another stack in the same account and Region
!Select, !Split, !Join, !GetAZsList and string handling

Configuring instances from the template

  • AWS::CloudFormation::Init metadata: declares packages, files, commands and services. cfn-init, called from user data, applies it.
  • cfn-signal: reports success or failure to a CreationPolicy or WaitCondition.
  • cfn-hup: a daemon that detects metadata changes after a stack update and reruns cfn-init, so configuration changes reach running instances without replacing them.
Skill

AWS SAM

A SAM template is a CloudFormation template with Transform: AWS::Serverless-2016-10-31. During deployment CloudFormation expands each SAM resource into the full set of underlying resources (functions, roles, permissions, API stages, event source mappings).

template.yml 
Transform: AWS::Serverless-2016-10-31

Globals:                                    # shared settings for every function
  Function:
    Runtime: python3.12
    Timeout: 10
    Tracing: Active                         # X-Ray

Resources:
  OrdersTable:
    Type: AWS::Serverless::SimpleTable

  CreateOrderFunction:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: src/create_order/
      Handler: app.handler
      Policies:
        - DynamoDBCrudPolicy:                 # SAM policy template, scoped to one table
            TableName: !Ref OrdersTable
      Environment:
        Variables: { TABLE_NAME: !Ref OrdersTable }
      Events:
        CreateOrder:
          Type: HttpApi                       # creates the API, route and permission
          Properties:
            Path: /orders
            Method: post

Skill

AWS CDK

A CDK app contains stacks, which contain constructs. Constructs come in three levels:

  • L1: generated one-to-one from CloudFormation (CfnBucket), with every property and no defaults.
  • L2: hand-written with sensible defaults and helper methods (Bucket, bucket.grantRead(role)).
  • L3 (patterns): several resources wired together (ApplicationLoadBalancedFargateService creates a cluster, service, load balancer and roles).
lib/orders-stack.ts 
import { Stack, StackProps, RemovalPolicy, Duration } from "aws-cdk-lib";
import * as s3 from "aws-cdk-lib/aws-s3";
import * as lambda from "aws-cdk-lib/aws-lambda";
import { Construct } from "constructs";

export class OrdersStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const bucket = new s3.Bucket(this, "Invoices", {      // L2 construct
      encryption: s3.BucketEncryption.KMS_MANAGED,
      enforceSSL: true,
      versioned: true,
      removalPolicy: RemovalPolicy.RETAIN,                 // becomes DeletionPolicy: Retain
    });

    const fn = new lambda.Function(this, "Generate", {
      runtime: lambda.Runtime.PYTHON_3_12,
      handler: "app.handler",
      code: lambda.Code.fromAsset("src/generate"),         // uploaded as an asset
      timeout: Duration.seconds(30),
    });

    bucket.grantWrite(fn);                                 // least-privilege IAM policy generated for you
  }
}
CommandDoes
cdk bootstrapCreates the CDKToolkit stack in each account and Region: an S3 bucket and ECR repository for assets, and deployment roles. Required once before the first deploy
cdk synthGenerates the CloudFormation templates and assets (the cloud assembly)
cdk diffCompares the app with what's deployed
cdk deployUploads assets and deploys the stacks through CloudFormation

"cdk deploy fails in a new account or Region because the assets bucket or deployment role doesn't exist" means the environment was never bootstrapped. For cross-account deployment from a pipeline, bootstrap the target with --trust <tooling-account-id>.

Applying CloudFormation StackSets across multiple accounts and Regions

Skill

A stack set deploys one template as stack instances in many account and Region combinations, from a single administrator account. Updating the stack set updates every instance.

Two permission models

Self-managedService-managed
RequiresNo AWS OrganizationsAWS Organizations with trusted access for StackSets enabled
RolesYou create AWSCloudFormationStackSetAdministrationRole in the administrator account and AWSCloudFormationStackSetExecutionRole in every target accountStackSets creates the roles it needs for you
TargetsAccount IDsOrganizational units (OUs) or accounts
New accountsAdd them yourselfAutomatic deployment: accounts that join a target OU get the stack automatically, and optionally lose it when they leave
Who administersAny accountThe management account or a delegated administrator member account

Example: a security baseline for every account in two OUs

baseline-stackset.yml 
SecurityBaseline:
  Type: AWS::CloudFormation::StackSet
  Properties:
    StackSetName: security-baseline
    PermissionModel: SERVICE_MANAGED
    AutoDeployment:
      Enabled: true                            # new accounts in these OUs get it automatically
      RetainStacksOnAccountRemoval: false     # remove it when an account leaves
    Capabilities: [CAPABILITY_NAMED_IAM]
    OperationPreferences:
      RegionConcurrencyType: PARALLEL
      MaxConcurrentPercentage: 25            # deploy to 25% of accounts at a time
      FailureTolerancePercentage: 10         # stop if more than 10% fail
    StackInstancesGroup:
      - DeploymentTargets:
          OrganizationalUnitIds: [ou-ab12-workloads, ou-ab12-sandbox]
        Regions: [us-east-1, eu-west-1]
    TemplateURL: https://tooling-artifacts.s3.amazonaws.com/security-baseline.yml

Operation preferences

  • Maximum concurrent accounts (count or percentage): how many accounts are deployed at the same time, per Region.
  • Failure tolerance (count or percentage): how many accounts can fail, per Region, before StackSets stops the operation in that Region.
  • Region order and concurrency: deploy Regions one after another (SEQUENTIAL, the safer choice, with a chosen order) or at the same time (PARALLEL).

With service-managed permissions, StackSets doesn't deploy to the organization's management account, even if you target the root OU. Deploy to the management account separately, for example with a regular stack.

  • "Every new account must automatically get the baseline": service-managed StackSets with automatic deployment on the OU.
  • "Accounts aren't in AWS Organizations": self-managed StackSets with the two IAM roles.
  • "Roll out cautiously and stop on problems": low maximum concurrency, low failure tolerance, and sequential Regions.

State Manager association

This association keeps the CloudWatch agent installed on every instance tagged Environment=prod, and rechecks every 30 days:

state-manager.yml 
CloudWatchAgentAssociation:
  Type: AWS::SSM::Association
  Properties:
    Name: AWS-ConfigureAWSPackage                  # SSM document to run
    Parameters:
      action: [Install]
      name: [AmazonCloudWatchAgent]
    Targets:
      - { Key: tag:Environment, Values: [prod] }
    ScheduleExpression: rate(30 days)              # reapplied on this schedule
    ComplianceSeverity: HIGH

New instances that match the target tag get the association automatically when they register with Systems Manager.

AWS AppConfig

AppConfig deploys configuration the way CodeDeploy deploys code: validated, gradual and reversible.

  1. Store the configuration profileA feature flag profile, or freeform JSON or YAML in AppConfig, Parameter Store, Secrets Manager or S3.
  2. Validate itA JSON Schema or a Lambda validator rejects bad configuration before it's deployed.
  3. Deploy with a strategyFor example, AppConfig.Linear20PercentEvery6Minutes or AppConfig.Canary10Percent20Minutes, or AppConfig.AllAtOnce.
  4. Watch alarmsIf a CloudWatch alarm on the environment fires during deployment or the bake time, AppConfig rolls back to the previous version.
  5. The application reads itThrough the AppConfig Agent (a Lambda extension or a container sidecar) that caches and refreshes configuration locally.

"Turn on a new feature for a percentage of traffic without deploying code, and roll back automatically if errors rise" points to AppConfig feature flags with a gradual deployment strategy and an alarm. Parameter Store alone has no gradual rollout or rollback.

Implementing infrastructure patterns, governance controls and security standards into reusable IaC

Skill

The goal: platform teams write the standard once (encryption, logging, tags, network rules), and application teams get it automatically by reusing a component instead of copying and editing templates.

CloudFormation modules

A module is a block of template (parameters, resources, and optionally conditions and outputs) that a platform team registers once in the CloudFormation registry as a private extension. Application teams then use it in their templates as if it were a single resource type. When a stack is created or updated, CloudFormation expands the module into the resources it contains, so the standard (encryption, logging, policies) comes with it and can't be forgotten.

PropertyDetail
Type nameOrganization::Service::Name::MODULE, for example ExampleCorp::S3::SecureBucket::MODULE. The ::MODULE suffix is what marks it as a module.
ContentsParameters (the inputs users may set), resources, and optionally conditions and outputs. A module can include other modules.
ScopeRegistered per account and Region, like any private registry extension
VersionsEach registration creates a version; stacks always use the account's default version
CostNone; you pay only for the resources it expands into. Stack quotas count the expanded resources.

A module goes through three steps: write the template fragment, package it with its schema, and register it in the CloudFormation registry of every account and Region that uses it. The module's name is given at registration, not inside the fragment. The examples below assume the platform team owns the bucket standard and names the module ExampleCorp::S3::SecureBucket::MODULE.

The module project

A module project is a folder with three files:

  • fragments/secure-bucket.yaml: the template fragment. The fragments folder holds exactly one file, in JSON or YAML.
  • schema.json: the module schema, generated from the fragment. It lists the module's parameters and resources and is what users see in the registry.
  • .rpdk-config: project settings written by cfn init, including the module's type name.

The fragment is an ordinary template body: parameters for the choices users may make, and the resources with the standard built in.

fragments/secure-bucket.yaml 
Parameters:
  BucketPrefix:
    Type: String
    Description: Prefix for the bucket name
Resources:
  Bucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub ${BucketPrefix}-${AWS::AccountId}-${AWS::Region}
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: aws:kms
      PublicAccessBlockConfiguration:
        BlockPublicAcls: true
        BlockPublicPolicy: true
        IgnorePublicAcls: true
        RestrictPublicBuckets: true
      VersioningConfiguration:
        Status: Enabled
  TlsOnlyPolicy:
    Type: AWS::S3::BucketPolicy
    Properties:
      Bucket: !Ref Bucket
      PolicyDocument:
        Statement:
          - Effect: Deny
            Principal: "*"
            Action: s3:*
            Resource:
              - !GetAtt Bucket.Arn
              - !Sub ${Bucket.Arn}/*
            Condition:
              Bool:
                aws:SecureTransport: "false"

A fragment can't use Fn::ImportValue, Export on outputs (plain outputs are fine), macros or transforms (including AWS::Serverless and AWS::Include), nested stacks or StackSets. A fragment can include other modules, up to three levels deep.

Registering with the CloudFormation CLI

The CloudFormation CLI (cfn) creates the project, generates the schema and registers the module in one flow:

pip install cloudformation-cli
mkdir secure-bucket-module && cd secure-bucket-module

cfn init
# choose "m" (module), then enter ExampleCorp::S3::SecureBucket::MODULE
# replace fragments/sample.json with fragments/secure-bucket.yaml

cfn validate
# regenerates schema.json from the fragment

cfn submit --region us-east-1 --set-default
# packages the project, uploads it, registers a new version, makes it the default
  • cfn submit registers in one Region of the current account; run it once per account and Region, or use one of the methods below to roll out further.
  • The first version registered is the default automatically; --set-default matters for later versions.
  • cfn submit --dry-run builds the package zip in the project folder without registering it. That zip is what the next two methods upload to S3.

Registering with the AWS CLI

Without the CloudFormation CLI on the registering machine, upload a package built earlier and call the registry API directly:

# 1. Put the package in S3
aws s3 cp secure-bucket-v1.zip s3://examplecorp-modules/secure-bucket-v1.zip

# 2. Register it under the module's name
aws cloudformation register-type \
  --type MODULE \
  --type-name ExampleCorp::S3::SecureBucket::MODULE \
  --schema-handler-package s3://examplecorp-modules/secure-bucket-v1.zip \
  --region us-east-1
# returns a RegistrationToken

# 3. Wait until ProgressStatus is COMPLETE
aws cloudformation describe-type-registration \
  --registration-token f5525280-104e-4d35-bef5-8f1fexample

# 4. For later versions, choose which one stacks use
aws cloudformation set-type-default-version \
  --type MODULE \
  --type-name ExampleCorp::S3::SecureBucket::MODULE \
  --version-id 00000002

The caller needs s3:GetObject on the package. Registration is asynchronous, which is why step 3 polls for the result.

Registering with a CloudFormation template

The CloudFormation console has no page for registering a private module directly; the registry pages there list and activate extensions. The console route is to upload the package zip to S3 (the S3 console is fine), then create a stack from a template whose AWS::CloudFormation::ModuleVersion resource registers it. The same template works in a pipeline, and as a StackSet it registers the same version in every account and Region.

register-secure-bucket-module.yaml 
Resources:
  SecureBucketV1:
    Type: AWS::CloudFormation::ModuleVersion
    Properties:
      ModuleName: ExampleCorp::S3::SecureBucket::MODULE
      ModulePackage: s3://examplecorp-modules/secure-bucket-v1.zip

  SecureBucketDefault:
    Type: AWS::CloudFormation::ModuleDefaultVersion
    Properties:
      Arn: !Ref SecureBucketV1   # the version stacks use
  • Name: three parts of 2–64 letters or digits, then ::MODULE. The first part can't be Alexa, AMZN, Amazon, AWS, Custom or Dev.
  • New versions: a registered version can't be changed. Pointing ModulePackage at a new zip registers a new version; deleting the resource marks that version deprecated.
  • Policies: a DeletionPolicy or UpdateReplacePolicy set where the module is used applies to every resource in it. CreationPolicy and UpdatePolicy can't be set on a module.

Using the module in a stack

Application teams set only the module's parameters. To reference a resource inside the module, combine the module's logical ID and the inner resource's logical ID, with or without a dot: InvoiceBucket.Bucket or InvoiceBucketBucket.

app-stack.yml 
Resources:
  InvoiceBucket:
    Type: ExampleCorp::S3::SecureBucket::MODULE
    Properties:
      BucketPrefix: invoices

  InvoiceQueue:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: !Ref InvoiceBucket.Bucket   # Ref a resource inside the module

Outputs:
  BucketArn:
    Value: !GetAtt InvoiceBucket.Bucket.Arn
  • What gets deployed: the processed template contains InvoiceBucketBucket and InvoiceBucketTlsOnlyPolicy. A change set shows them before you deploy, and CloudFormation records which resources came from the module.
  • Tags and outputs: stack-level tags reach the module's resources. Any outputs a module defines become stack outputs named after the module plus the output; a module output BucketName would appear as InvoiceBucketBucketName.
  • Parameters: module parameters aren't stack parameters; pass a stack parameter into them with !Ref if users should choose the value at deploy time.

Changing a module's default version doesn't update existing stacks. Each stack picks up the new version on its next create or update (unless the update uses "use previous template"). And because the default version is per account and Region, the same template can expand differently in two accounts; keep versions aligned when deploying with StackSets.

Modules versus nested stacks: a module expands into resources inside your stack (one stack, governed versions in the registry). A nested stack is a separate stack created from a template URL in S3, with its own events, outputs and quotas. Pick modules for small standard building blocks, and nested stacks for large reusable parts or to stay under the per-stack resource limit.

CDK construct libraries

In the CDK, the reusable unit is a construct: a class that creates one or more resources. A platform team writes L3 constructs that wrap the company's defaults, publishes them as a package, and teams install that package instead of writing raw resources.

lib/secure-bucket.ts (platform team's package @examplecorp/constructs) 
import { Construct } from "constructs";
import { RemovalPolicy, Duration } from "aws-cdk-lib";
import * as s3 from "aws-cdk-lib/aws-s3";
import * as kms from "aws-cdk-lib/aws-kms";

export interface SecureBucketProps {
  readonly retentionDays?: number;   // the only choice teams get
}

export class SecureBucket extends Construct {
  public readonly bucket: s3.Bucket;

  constructor(scope: Construct, id: string, props: SecureBucketProps = {}) {
    super(scope, id);
    const key = new kms.Key(this, "Key", { enableKeyRotation: true });
    this.bucket = new s3.Bucket(this, "Bucket", {
      encryption: s3.BucketEncryption.KMS,
      encryptionKey: key,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      enforceSSL: true,        // adds the TLS-only bucket policy
      versioned: true,
      removalPolicy: RemovalPolicy.RETAIN,
      lifecycleRules: [{
        expiration: Duration.days(props.retentionDays ?? 365),
      }],
    });
  }
}
  1. PublishA pipeline builds the package and publishes it to a private CodeArtifact repository (npm, PyPI or Maven). Writing it with jsii lets one TypeScript library be published for Python, Java, .NET and Go too.
  2. ConsumeTeams install @examplecorp/constructs and write new SecureBucket(this, "Invoices"). They get encryption, TLS-only access and retention without knowing the details.
  3. UpgradeThe platform team releases a new package version; each team picks it up by upgrading the dependency and redeploying.

CDK Aspects

A construct library only helps when people use it. Aspects enforce rules across everything in an app, including resources teams created directly. An aspect is a class with a visit(node) method; Aspects.of(scope).add(...) attaches it, and during synthesis the CDK calls visit on that scope and every construct inside it, top down.

import { IAspect, Aspects, Annotations, Tags, Tokenization } from "aws-cdk-lib";
import { IConstruct } from "constructs";
import * as s3 from "aws-cdk-lib/aws-s3";

// Read-only aspect: fail synthesis if any bucket lacks versioning
class BucketVersioningChecker implements IAspect {
  public visit(node: IConstruct): void {
    if (node instanceof s3.CfnBucket) {
      const v = node.versioningConfiguration;
      if (!v || (!Tokenization.isResolvable(v) &&
                 (v as s3.CfnBucket.VersioningConfigurationProperty).status !== "Enabled")) {
        Annotations.of(node).addError("Bucket versioning is not enabled");
      }
    }
  }
}

// Mutating aspect: force a setting instead of just reporting it
class ForceBucketKeys implements IAspect {
  public visit(node: IConstruct): void {
    if (node instanceof s3.CfnBucket) {
      node.addPropertyOverride(
        "BucketEncryption.ServerSideEncryptionConfiguration.0.BucketKeyEnabled", true);
    }
  }
}

Aspects.of(app).add(new BucketVersioningChecker());
Aspects.of(app).add(new ForceBucketKeys());
Tags.of(app).add("CostCenter", "1234");   // tagging is itself built on aspects
  • Errors stop the deployment: Annotations.of(node).addError() makes cdk synth fail, so nothing reaches CloudFormation. addWarning() only reports.
  • Read-only vs mutating: read-only aspects check and report; mutating aspects change properties (as above, through escape hatches such as addPropertyOverride).
  • cdk-nag: an open-source library of rule packs (AWS Solutions, HIPAA, NIST 800-53, PCI DSS) implemented as aspects: Aspects.of(app).add(new AwsSolutionsChecks()). Accepted exceptions are recorded with NagSuppressions.addResourceSuppressions(resource, [{ id, reason }]), so every exception is in code review.

Aspects don't cross Stage boundaries. In a CDK Pipelines app, where each environment is a Stage, an aspect added to the app doesn't check the stacks inside the stages; add it to each Stage (or the stacks inside it).

"Ensure every CDK app in the company meets security standards before deployment" is Aspects (often cdk-nag) that fail synthesis, run in the pipeline's build step. "Give teams pre-approved building blocks" is a shared construct library in CodeArtifact. In plain CloudFormation, the same pair is modules for building blocks and CloudFormation Guard or hooks for enforcement.

AWS Service Catalog

Service Catalog turns approved templates into products that users launch themselves. The platform team decides what a product creates and which choices users may make; users launch it without having permission to create the underlying resources. A launch creates a CloudFormation stack (or a Terraform run) behind the scenes, so everything stays infrastructure as code.

The examples below assume a hub account 555555555555 where the platform team manages the catalog, and workload accounts in the Workloads OU where developers launch products.

Building blocks

ConceptWhat it is
ProductAn approved template with versions (called provisioning artifacts), for example "PostgreSQL database" v1 and v2. CloudFormation and Terraform product types exist.
PortfolioA collection of products, plus who may use them and under which constraints
Principal associationGrants IAM roles, users or groups access to a portfolio's products
Launch constraintThe IAM role Service Catalog assumes to create the product's resources
Template constraintRules that limit parameter values, such as allowed instance classes
Other constraintsNotification (stack events to SNS), StackSet (deploy the product to several accounts and Regions), tag update (whether users may change tags)
TagOptionsAllowed tag keys and values; a single-value TagOption is applied automatically
Service actionsSystems Manager documents users may run on a provisioned product, such as "restart" or "take snapshot"
Provisioned productOne launched instance of a product; it's a CloudFormation stack named SC-<account>-pp-<id>

Defining the catalog as code

The portfolio, product and constraints are themselves CloudFormation resources, so the catalog is reviewed and deployed like any other stack:

catalog.yaml (in 555555555555) 
Resources:
  DataPortfolio:
    Type: AWS::ServiceCatalog::Portfolio
    Properties:
      DisplayName: Approved data stores
      ProviderName: Platform team

  PostgresProduct:
    Type: AWS::ServiceCatalog::CloudFormationProduct
    Properties:
      Name: PostgreSQL database
      Owner: Platform team
      ProvisioningArtifactParameters:
        - Name: v1
          Info:
            LoadTemplateFromURL: https://examplecorp-catalog.s3.amazonaws.com/postgres-v1.yaml

  ProductInPortfolio:
    Type: AWS::ServiceCatalog::PortfolioProductAssociation
    Properties:
      PortfolioId: !Ref DataPortfolio
      ProductId: !Ref PostgresProduct

  DevelopersCanUse:
    Type: AWS::ServiceCatalog::PortfolioPrincipalAssociation
    Properties:
      PortfolioId: !Ref DataPortfolio
      PrincipalType: IAM_PATTERN   # matches by name in every shared account
      PrincipalARN: arn:aws:iam:::role/aws-reserved/sso.amazonaws.com/*AWSReservedSSO_Developer*

  LaunchAs:
    Type: AWS::ServiceCatalog::LaunchRoleConstraint
    DependsOn: ProductInPortfolio
    Properties:
      PortfolioId: !Ref DataPortfolio
      ProductId: !Ref PostgresProduct
      LocalRoleName: SCLaunchRole-Data   # resolved in the account that launches

  AllowedSizes:
    Type: AWS::ServiceCatalog::LaunchTemplateConstraint
    DependsOn: ProductInPortfolio
    Properties:
      PortfolioId: !Ref DataPortfolio
      ProductId: !Ref PostgresProduct
      Rules: |
        {
          "prodSize": {
            "RuleCondition": {
              "Fn::Equals": [ { "Ref": "Environment" }, "prod" ]
            },
            "Assertions": [ {
              "Assert": {
                "Fn::Contains": [ [ "db.r6g.large", "db.r6g.xlarge" ], { "Ref": "InstanceClass" } ]
              },
              "AssertDescription": "Production databases must be db.r6g.large or db.r6g.xlarge"
            } ]
          }
        }
  • Versions: adding a provisioning artifact (v2) publishes a new version. Existing provisioned products keep their version until users update them; old versions can be deprecated so nobody launches them again.
  • Template constraint rules use the CloudFormation rule functions (Fn::Contains, Fn::Equals, Fn::EachMemberIn and others) against the product template's parameters. A rule without RuleCondition always applies.

The launch role

The launch role holds the real permissions. Service Catalog assumes it when a user launches, updates or terminates the product, so the user needs only Service Catalog permissions. It needs three things: CloudFormation access, read access to the product template that Service Catalog stores, and permissions for the resources the template creates.

launch-role.yaml (deployed to every workload account) 
SCLaunchRoleData:
  Type: AWS::IAM::Role
  Properties:
    RoleName: SCLaunchRole-Data   # same name everywhere for LocalRoleName
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:
            Service: servicecatalog.amazonaws.com
          Action: sts:AssumeRole
          Condition:
            StringEquals:
              aws:SourceAccount: !Ref AWS::AccountId   # confused-deputy protection
    ManagedPolicyArns:
      - arn:aws:iam::aws:policy/AWSCloudFormationFullAccess
    Policies:
      - PolicyName: provision-postgres
        PolicyDocument:
          Version: "2012-10-17"
          Statement:
            - Effect: Allow   # read the template Service Catalog stores
              Action: s3:GetObject
              Resource: "*"
              Condition:
                StringEquals:
                  s3:ExistingObjectTag/servicecatalog:provisioning: "true"
            - Effect: Allow   # what the product template creates
              Action:
                - rds:*
                - ec2:Describe*
                - secretsmanager:CreateSecret
                - secretsmanager:TagResource
              Resource: "*"

With LocalRoleName, the constraint names the role instead of pointing at one account's ARN, so one shared portfolio works in every account. The role must exist under that name in each account that launches the product; deploy it with a StackSet to the same OU the portfolio is shared with.

Sharing the portfolio with the organization

# In the management account: allow Service Catalog to use Organizations,
# then let the hub account manage shares
aws servicecatalog enable-aws-organizations-access
aws organizations register-delegated-administrator \
  --account-id 555555555555 \
  --service-principal servicecatalog.amazonaws.com

# In 555555555555: share with the Workloads OU,
# including TagOptions and principal names
aws servicecatalog create-portfolio-share \
  --portfolio-id port-abcd1234efgh5 \
  --organization-node Type=ORGANIZATIONAL_UNIT,Value=ou-ab12-cdef3456 \
  --share-tag-options \
  --share-principals
  • No import step: accounts in the OU see the portfolio automatically. Account-to-account shares, by contrast, must be imported by the recipient.
  • Stays in sync: recipients get a reference, so new product versions and changed constraints appear everywhere. Recipients can't change products or constraints, but they can grant extra local IAM principals access.
  • Principal names: with --share-principals, the IAM_PATTERN association above grants access to matching roles in each account. Use PrincipalType: IAM instead if someone in a recipient account could create a role with a matching name to gain access.

What the end user does

A developer with only Service Catalog end-user permissions (for example, the AWSServiceCatalogEndUserFullAccess managed policy) opens the Service Catalog console, picks the product and fills in its parameters. The same from the CLI:

aws servicecatalog provision-product \
  --product-name "PostgreSQL database" \
  --provisioning-artifact-name v1 \
  --provisioned-product-name orders-db \
  --provisioning-parameters Key=Environment,Value=prod Key=InstanceClass,Value=db.r6g.large

# later: move to the new version the platform team published
aws servicecatalog update-provisioned-product \
  --provisioned-product-name orders-db \
  --product-name "PostgreSQL database" \
  --provisioning-artifact-name v2

Service Catalog checks the template constraint, assumes SCLaunchRole-Data in the developer's account, and creates the stack. A request for db.t3.micro in prod fails before any resource is created, with the rule's AssertDescription as the message.

"Developers must create databases themselves, only in an approved configuration, and must not have direct RDS permissions" points to Service Catalog with a launch constraint (the permissions) and a template constraint (the approved configuration).

A launch constraint applies to one product in one portfolio, not to the whole portfolio; each product needs its own. And without a launch constraint, Service Catalog launches with the user's own credentials, so the user would need CloudFormation and RDS permissions after all.

Policy as code before deployment

Policy as code means writing the rules (encryption on, no public buckets, approved instance types) as files that a machine checks, instead of a checklist someone reads. The same rules can run at several points, and the earlier a check runs, the cheaper the mistake is to fix:

  1. While writingcfn-lint in the editor or a pre-commit hook: syntax, invalid property values, resource-specific best practices.
  2. In the pipelineCloudFormation Guard (and cfn-lint) in a CodeBuild step: company rules; the build fails before anything is deployed.
  3. During every stack operationCloudFormation Hooks: the same Guard rules run inside CloudFormation for every stack in the account, including ones that never went through the pipeline.
  4. On every API callSCPs: deny actions outright, across accounts, regardless of tool.
  5. After deploymentAWS Config rules: detect drift or manual changes, with optional automatic remediation.

Writing Guard rules

A Guard rule selects parts of a template with a query, then states what must be true about them. Rules work on any JSON or YAML, so the same tool also checks Terraform plans (as JSON) and Kubernetes manifests.

rules/s3.guard 
# Select every S3 bucket in the template
let buckets = Resources.*[ Type == 'AWS::S3::Bucket' ]

# "when" skips the rule if there are no buckets
rule s3_encrypted when %buckets !empty {
    %buckets.Properties.BucketEncryption exists
        << Every S3 bucket must declare default encryption >>
}

rule s3_versioned when %buckets !empty {
    %buckets.Properties.VersioningConfiguration.Status == 'Enabled'
        << Every S3 bucket must have versioning enabled >>
}

rule s3_no_public_access when %buckets !empty {
    %buckets.Properties.PublicAccessBlockConfiguration {
        BlockPublicAcls == true
        BlockPublicPolicy == true
        IgnorePublicAcls == true
        RestrictPublicBuckets == true
    }
}

# A rule can depend on another rule
rule s3_logging when s3_encrypted {
    %buckets.Properties.LoggingConfiguration exists
}
  • Resources.*[ Type == '...' ] selects resources by type; let names the selection so rules can reuse it as %buckets.
  • Every clause in a block must hold (AND); some means at least one element must match; << ... >> is the message shown on failure.
  • A rule evaluates to PASS, FAIL, or SKIP when its when condition is false.

Testing the rules

Rules are code, so they get unit tests. A test file lists sample inputs and the result each rule should give:

rules/s3_tests.yaml 
- name: no buckets, rule is skipped
  input:
    Resources: {}
  expectations:
    rules:
      s3_encrypted: SKIP
- name: unencrypted bucket fails
  input:
    Resources:
      Logs:
        Type: AWS::S3::Bucket
  expectations:
    rules:
      s3_encrypted: FAIL
cfn-guard test --rules-file rules/s3.guard --test-data rules/s3_tests.yaml

Running the checks in the pipeline

A CodeBuild step lints and checks every template before the deploy stage. A failed check exits non-zero, which fails the build, and the JUnit output appears as a test report in CodeBuild:

buildspec-policy.yml 
version: 0.2
phases:
  install:
    commands:
      - pip install cfn-lint
      # install cfn-guard from its prebuilt release binary
  build:
    commands:
      - cfn-lint templates/*.yaml
      - cfn-guard test --rules-file rules/s3.guard --test-data rules/s3_tests.yaml
      - mkdir -p reports
      - cfn-guard validate --data templates/ --rules rules/ --structured --output-format junit > reports/guard.xml
reports:
  policy-checks:
    files: [ reports/guard.xml ]
    file-format: JUNITXML

For CDK apps, run the same checks on the synthesized templates in cdk.out/ after cdk synth, or use cdk-nag during synthesis.

Enforcing the rules in every stack operation

Pipeline checks only cover templates that go through the pipeline. A Guard hook runs the same rules inside CloudFormation for every stack operation in the account and Region, including stacks created from the console. The rules are read from S3:

guard-hook.yaml 
GuardHookRole:
  Type: AWS::IAM::Role
  Properties:
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:
            Service: hooks.cloudformation.amazonaws.com
          Action: sts:AssumeRole
    Policies:
      - PolicyName: read-rules
        PolicyDocument:
          Version: "2012-10-17"
          Statement:
            - Effect: Allow
              Action: [ s3:GetObject, s3:GetObjectVersion, s3:ListBucket ]
              Resource:
                - arn:aws:s3:::examplecorp-guard-rules
                - arn:aws:s3:::examplecorp-guard-rules/*

S3RulesHook:
  Type: AWS::CloudFormation::GuardHook
  Properties:
    Alias: ExampleCorp::Guard::S3Rules   # may not start with AWS
    ExecutionRole: !GetAtt GuardHookRole.Arn
    RuleLocation:
      Uri: s3://examplecorp-guard-rules/s3.guard
    TargetOperations: [ RESOURCE ]   # also STACK, CHANGE_SET, CLOUD_CONTROL
    TargetFilters:
      Actions: [ CREATE, UPDATE ]
    FailureMode: WARN   # start with WARN, switch to FAIL
    HookStatus: ENABLED
  • FailureMode: WARN lets the operation continue and records the finding; FAIL stops it. Rolling out in WARN first shows what would break.
  • Other hook types: a Lambda hook (AWS::CloudFormation::LambdaHook) runs your own function for checks Guard can't express, such as looking something up in another system.
  • At scale: deploy hooks to every account with StackSets. AWS Control Tower proactive controls are managed hooks of this kind.

"Block noncompliant resources even when someone deploys a template from the console" is a CloudFormation hook. "Catch problems before the change is merged" is cfn-lint and Guard in the pipeline. "Find resources that were changed by hand after deployment" is AWS Config. A strong answer often combines them.

Key takeaways

  • CloudFormation is the default IaC answer; SAM for serverless; CDK for code and reusable constructs. Both SAM and CDK deploy through CloudFormation.
  • Know update behaviors: no interruption, some interruption, replacement. Replacement of stateful resources loses data unless protected.
  • Protect resources with DeletionPolicy and UpdateReplacePolicy (Retain or Snapshot), stack policies denying Update:Replace and Update:Delete, and termination protection.
  • Safe changes: change set, approval, execute, with rollback triggers on CloudWatch alarms. UPDATE_ROLLBACK_FAILED is fixed with ContinueUpdateRollback.
  • Drift detection reports manual changes but doesn't fix them. Custom resources must respond to the pre-signed URL, or the stack hangs.
  • StackSets: self-managed (two IAM roles, account IDs) or service-managed (Organizations, OUs, automatic deployment, no management account).
  • Systems Manager configures what's on servers; AWS Config evaluates AWS resource settings; AppConfig deploys app configuration and feature flags gradually with rollback. OpsWorks is retired.
  • Reusable standards: CloudFormation modules, CDK construct libraries and Aspects, Service Catalog products with launch constraints, and Guard rules in the pipeline.
