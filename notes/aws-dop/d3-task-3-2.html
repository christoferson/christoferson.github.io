Overview

Task statement 3.2

Implement solutions that are scalable to meet business requirements.

Scalability is the ability to handle more (or less) load by adding (or removing) capacity, ideally automatically and without redesign. This task tests whether you can choose what to scale on, build architectures where each part scales on its own, and recognize the bottleneck in a struggling system. Typical scenarios: "the Auto Scaling group reacts too late to the morning peak", "Lambda functions are throttled", "the database runs out of connections", or "users in Asia see high latency".

Appropriate metrics for scaling services

Knowledge

A good scaling metric rises and falls with the load, and goes back to normal when capacity is added. A metric that stays high however many instances you add (for example, a downstream database's latency) makes scaling run away.

WorkloadGood metricWhy
Web tier behind an ALBALBRequestCountPerTargetTracks real demand directly; works for I/O-bound apps where CPU stays low
CPU-bound processingAverage CPU utilizationSimple, built in
Queue workersBacklog per instance: messages visible ÷ running instancesRaw queue length doesn't account for how many workers there are
ECS servicesECSServiceAverageCPUUtilization, memory, or request count per targetBuilt-in Application Auto Scaling metrics
DynamoDB (provisioned)Consumed vs provisioned read and write capacityBuilt into DynamoDB auto scaling
Aurora read replicasReader CPU or connectionsAdds replicas as read load grows
Lambda provisioned concurrencyProvisioned concurrency utilizationKeeps warm capacity ahead of demand
Kubernetes podsCPU or memory through the Horizontal Pod Autoscaler; custom or queue metrics through KEDAScales replicas; node autoscalers then add nodes

Example: scaling queue workers on backlog per instance

Assume each worker processes 10 messages per second and the business accepts messages waiting up to 30 seconds. An acceptable backlog is 10 × 30 = 300 messages per instance. A target tracking policy can calculate the metric with metric math:

worker-scaling.yml 
WorkerBacklogPolicy:
  Type: AWS::AutoScaling::ScalingPolicy
  Properties:
    AutoScalingGroupName: !Ref WorkerAsg
    PolicyType: TargetTrackingScaling
    TargetTrackingConfiguration:
      TargetValue: 300                                   # acceptable messages per instance
      CustomizedMetricSpecification:
        Metrics:
          - Id: visible
            ReturnData: false
            MetricStat:
              Metric:
                Namespace: AWS/SQS
                MetricName: ApproximateNumberOfMessagesVisible
                Dimensions: [{ Name: QueueName, Value: orders-queue }]
              Stat: Sum
          - Id: instances
            ReturnData: false
            MetricStat:
              Metric:
                Namespace: AWS/AutoScaling
                MetricName: GroupInServiceInstances
                Dimensions: [{ Name: AutoScalingGroupName, Value: worker-asg }]
              Stat: Average
          - Id: backlogPerInstance
            Expression: visible / instances                  # the metric being tracked
            ReturnData: true

"Scale workers so messages never wait more than N seconds" points to backlog per instance, not raw queue length or CPU.

Loosely coupled and distributed architectures

Knowledge

In a tightly coupled system every component must handle the peak at the same moment, and one slow part slows everything. Putting a queue or event bus between components lets each one scale, fail and deploy on its own.

ServiceModelUse it forKey details
Amazon SQSQueue: each message processed by one consumerBuffering spikes, work queuesStandard: nearly unlimited throughput, at-least-once, best-effort order. FIFO: exactly-once processing and strict order per message group, with lower throughput unless high-throughput mode is on
Amazon SNSPublish-subscribe: each message pushed to every subscriberFan-out to many queues, functions or endpointsSubscription filter policies; FIFO topics for ordered fan-out
Amazon EventBridgeEvent bus with content-based rulesRouting events between services and accounts, SaaS integrationRules filter on any event field; archive and replay; schema registry
Kinesis Data StreamsOrdered, replayable streamHigh-volume real-time data, several consumers reading the same dataOrder per shard, retention up to 365 days, on-demand or provisioned shards
AWS Step FunctionsOrchestrated workflowMulti-step processes with state, retries and branchingCentral control of the sequence

Patterns

  • Queue-based load leveling: producers write to SQS at any rate; consumers process at a steady rate and scale on backlog.
  • Fan-out: one SNS topic (or EventBridge rule) delivers each event to several SQS queues, so each downstream service has its own buffer.
  • Choreography vs orchestration: services react to each other's events (EventBridge), or a central workflow tells each service what to do (Step Functions).

SQS settings that matter at scale

  • Visibility timeout: how long a received message is hidden from other consumers. Set it longer than the processing time, or messages are processed twice.
  • Dead-letter queue: after maxReceiveCount failed attempts, the message moves aside instead of blocking or looping forever.
  • Long polling: ReceiveMessageWaitTimeSeconds up to 20 reduces empty responses and cost.
  • Batching: send, receive and delete up to 10 messages per call.

"Messages are processed more than once" with a Standard queue usually means the visibility timeout is shorter than the processing time, or the consumer isn't idempotent. Standard queues can always deliver a message more than once, so consumers must tolerate it.

Serverless architectures

Knowledge

Serverless services scale automatically and charge per use. You still need to know how fast they scale and where they stop.

ServiceHow it scalesLimits to know
AWS LambdaOne execution environment per concurrent request. Concurrency ≈ requests per second × average durationAccount concurrency quota per Region (1,000 by default, can be raised). Each function can add 1,000 concurrent executions every 10 seconds
Amazon API GatewayManagedAccount-level throttling per Region (10,000 requests per second, burst 5,000, by default); stage, route and usage plan limits
Amazon DynamoDBOn-demand: instant; provisioned: auto scaling on utilizationPer-partition throughput, so a "hot" key can throttle even when the table has spare capacity
Aurora Serverless v2Capacity in Aurora capacity units (ACUs), adjusted in small steps within secondsMinimum and maximum ACUs (up to 256; the minimum can be 0 to pause when idle)
AWS FargateTasks without servers; scaled by ECS or EKSTask launch rate and vCPU quotas per Region
Amazon S3ManagedAt least 3,500 writes and 5,500 reads per second per prefix; spread keys over prefixes for more
SQS, SNS, EventBridge, Step FunctionsManagedAPI rate quotas (EventBridge PutEvents, Step Functions state transitions) can need increases at very high volume

To estimate Lambda concurrency: 2,000 requests per second with a 500 ms average duration needs about 2,000 × 0.5 = 1,000 concurrent executions, already the default account quota.

Two levels of scaling

Containers scale on two levels, and both need configuring:

  • Tasks or pods: ECS Service Auto Scaling, or the Kubernetes Horizontal Pod Autoscaler.
  • Underlying capacity: ECS capacity providers with managed scaling, Karpenter or Cluster Autoscaler on EKS. Fargate removes this level entirely.

Check Service Quotas when scaling stops at a round number. Many "it won't scale past N" problems are quotas (Lambda concurrency, vCPUs per Region, API rates), and CloudWatch alarms on quota usage give early warning.

Identifying and implementing auto scaling, load balancing and caching solutions

Skill

EC2 Auto Scaling policies

PolicyHow it worksUse for
Target trackingKeeps a metric near a target value, like a thermostatThe default choice for most workloads
Step scalingAdds or removes different amounts depending on how far an alarm is breachedFine control over large jumps
Simple scalingOne adjustment per alarm, then a cooldownLegacy; prefer step or target tracking
Scheduled scalingChanges capacity at set timesKnown events (business hours, a sale starting)
Predictive scalingForecasts load from 14 days of history and adds capacity before it's neededRegular daily or weekly cycles
  • Warm pools: keep stopped or hibernated instances already initialized, so scale-out takes seconds instead of minutes.
  • Lifecycle hooks: pause an instance while launching (to finish setup) or terminating (to drain work or copy logs).
  • Mixed instances policy: combine On-Demand and Spot, across several instance types, with allocation strategies such as price-capacity-optimized.
web-scaling.yml 
RequestCountPolicy:
  Type: AWS::AutoScaling::ScalingPolicy
  Properties:
    AutoScalingGroupName: !Ref WebAsg
    PolicyType: TargetTrackingScaling
    EstimatedInstanceWarmup: 120
    TargetTrackingConfiguration:
      PredefinedMetricSpecification:
        PredefinedMetricType: ALBRequestCountPerTarget
        ResourceLabel: !Sub "${WebAlb.LoadBalancerFullName}/${WebTargetGroup.TargetGroupFullName}"
      TargetValue: 1000                       # requests per target per minute

PredictivePolicy:
  Type: AWS::AutoScaling::ScalingPolicy
  Properties:
    AutoScalingGroupName: !Ref WebAsg
    PolicyType: PredictiveScaling
    PredictiveScalingConfiguration:
      Mode: ForecastAndScale                 # ForecastOnly to evaluate first
      SchedulingBufferTime: 300              # launch 5 minutes ahead of the forecast
      MetricSpecifications:
        - TargetValue: 1000
          PredefinedMetricPairSpecification:
            PredefinedMetricType: ALBRequestCount
            ResourceLabel: !Sub "${WebAlb.LoadBalancerFullName}/${WebTargetGroup.TargetGroupFullName}"
Skill

Application Auto Scaling

Other services scale through Application Auto Scaling, with the same target tracking, step and scheduled policies. It covers ECS services, DynamoDB tables and indexes, Aurora replicas, Lambda provisioned concurrency, Spot Fleet, EMR, ElastiCache, SageMaker endpoints and more. Each one needs a scalable target (what to scale, minimum and maximum) and a policy.

ecs-service-scaling.yml 
OrdersScalableTarget:
  Type: AWS::ApplicationAutoScaling::ScalableTarget
  Properties:
    ServiceNamespace: ecs
    ResourceId: service/prod/orders                 # service/<cluster>/<service>
    ScalableDimension: ecs:service:DesiredCount
    MinCapacity: 3
    MaxCapacity: 40

OrdersCpuPolicy:
  Type: AWS::ApplicationAutoScaling::ScalingPolicy
  Properties:
    PolicyName: orders-cpu
    PolicyType: TargetTrackingScaling
    ScalingTargetId: !Ref OrdersScalableTarget
    TargetTrackingScalingPolicyConfiguration:
      PredefinedMetricSpecification:
        PredefinedMetricType: ECSServiceAverageCPUUtilization
      TargetValue: 60
      ScaleOutCooldown: 60
      ScaleInCooldown: 300                         # scale in more cautiously

Load balancing for scale

  • Application Load Balancer: scales automatically; route by path or host to separate services so each scales independently.
  • Network Load Balancer: millions of requests per second at very low latency, with static IPs.
  • Global Accelerator: spreads global users over Regional load balancers on the AWS network.
  • Very sudden spikes: load balancers scale quickly, but for a known extreme event (such as a product launch) ALB and NLB support load balancer capacity unit reservations to pre-provision capacity.
Skill

Caching

A cache serves repeated reads from a fast copy, so the expensive layer behind it handles less load. Cache as close to the user as the data allows:

LayerServiceBest for
EdgeAmazon CloudFrontStatic assets, media, cacheable API responses, close to users worldwide
APIAPI Gateway caching (REST APIs)Repeated identical API requests, cached per stage with a TTL
ApplicationAmazon ElastiCache (Valkey, Redis OSS, Memcached)Database query results, sessions, leaderboards, rate limiting
DatabaseDynamoDB Accelerator (DAX)Microsecond reads of DynamoDB items without changing the application's API calls
Read offloadRDS or Aurora read replicasRead-heavy SQL that can tolerate slight replication lag

Caching strategies

  • Lazy loading (cache-aside): read the cache; on a miss, read the database and store the result. Only requested data is cached, but the first read is slow and data can be stale.
  • Write-through: update the cache whenever the database is written. Data is fresh, but every write costs more and unread data fills the cache.
  • TTL: always set an expiry, so stale data ages out.
  • "DynamoDB read-heavy with microsecond latency needed, minimal code change": DAX.
  • "Relational database overloaded by repeated identical queries": ElastiCache with lazy loading.
  • "Global users downloading the same files": CloudFront.

Deploying container-based applications (ECS, EKS)

Skill

Amazon ECS on Fargate

orders-ecs.yml 
OrdersTaskDefinition:
  Type: AWS::ECS::TaskDefinition
  Properties:
    Family: orders
    RequiresCompatibilities: [FARGATE]
    NetworkMode: awsvpc                                 # required for Fargate: each task gets its own ENI
    Cpu: "512"                                           # 0.5 vCPU
    Memory: "1024"                                       # 1 GB
    RuntimePlatform: { CpuArchitecture: ARM64, OperatingSystemFamily: LINUX }   # Graviton
    ExecutionRoleArn: !GetAtt TaskExecutionRole.Arn     # pull image, write logs, read secrets
    TaskRoleArn: !GetAtt OrdersTaskRole.Arn             # the app's own AWS permissions
    ContainerDefinitions:
      - Name: web
        Image: 111111111111.dkr.ecr.eu-west-1.amazonaws.com/orders:v1.4.2
        PortMappings: [{ ContainerPort: 8080 }]
        Secrets:
          - { Name: DB_PASSWORD, ValueFrom: arn:aws:secretsmanager:eu-west-1:111111111111:secret:prod/orders/db }
        LogConfiguration:
          LogDriver: awslogs
          Options: { awslogs-group: /ecs/orders, awslogs-region: eu-west-1, awslogs-stream-prefix: web }

OrdersService:
  Type: AWS::ECS::Service
  Properties:
    Cluster: prod
    ServiceName: orders
    TaskDefinition: !Ref OrdersTaskDefinition
    DesiredCount: 3
    CapacityProviderStrategy:
      - { CapacityProvider: FARGATE, Base: 3, Weight: 1 }        # first 3 tasks always On-Demand
      - { CapacityProvider: FARGATE_SPOT, Weight: 3 }            # then 3 of every 4 extra tasks on Spot
    NetworkConfiguration:
      AwsvpcConfiguration:
        Subnets: [!Ref PrivateSubnetA, !Ref PrivateSubnetB, !Ref PrivateSubnetC]
        SecurityGroups: [!Ref OrdersSecurityGroup]
    LoadBalancers:
      - { ContainerName: web, ContainerPort: 8080, TargetGroupArn: !Ref OrdersTargetGroup }
  • Capacity provider strategy: Base is the minimum number of tasks on that provider; Weight splits the rest. Spot saves up to 70% but tasks can be interrupted with a 2-minute warning, so keep a reliable base on On-Demand.
  • ECS on EC2: a capacity provider linked to an Auto Scaling group with managed scaling adds instances when tasks can't be placed, and managed termination protection stops scale-in from removing instances that still run tasks.

Amazon EKS

Pods scale with the Horizontal Pod Autoscaler (HPA), which needs the Kubernetes Metrics Server:

orders-hpa.yml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: orders
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: orders }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 60 }   # percentage of the pod's CPU request

Nodes then scale to fit the pods:

Node scalerHow it works
Cluster AutoscalerChanges the desired size of existing node groups (Auto Scaling groups) when pods are pending or nodes are underused
KarpenterLaunches right-sized EC2 instances directly for pending pods, choosing from many instance types, On-Demand or Spot, and consolidates underused nodes. Faster and more flexible
EKS Auto ModeAWS runs Karpenter-based node management for you
Fargate profilesPods matching a profile run on Fargate, so there are no nodes to scale
karpenter-nodepool.yml 
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    spec:
      requirements:
        - { key: karpenter.sh/capacity-type, operator: In, values: [spot, on-demand] }
        - { key: kubernetes.io/arch, operator: In, values: [amd64, arm64] }
      nodeClassRef: { group: karpenter.k8s.aws, kind: EC2NodeClass, name: default }
  limits:
    cpu: "1000"                                         # cap on total vCPUs this pool may launch
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized       # repack pods to save cost

An HPA can't scale on CPU if the pods have no CPU requests: utilization is calculated as a percentage of the request. Missing requests also make node autoscalers pack nodes badly.

Deploying workloads in multiple Regions for global scalability

Skill

Serving users from the Region closest to them cuts latency and spreads load. Each layer needs a global answer:

LayerGlobal option
Entry pointRoute 53 latency or geolocation routing; Global Accelerator (anycast IPs, nearest healthy Region); CloudFront for cacheable content
ComputeThe same stack in each Region, deployed by StackSets or a pipeline with cross-Region actions
Data, writes everywhereDynamoDB global tables
Data, reads everywhereAurora Global Database secondaries (with write forwarding), ElastiCache Global Datastore
ObjectsS3 replication with a Multi-Region Access Point
Images and secretsECR replication, Secrets Manager replica secrets, KMS multi-Region keys

Adding a new Region

  1. Check quotas and servicesQuotas are per Region and start at defaults. Request increases in advance, and confirm every service you use is available there.
  2. Replicate data and artifactsAdd a DynamoDB replica or Aurora secondary; replicate ECR images, S3 data, secrets and keys.
  3. Deploy the stackAdd the Region to the StackSet or pipeline, so it's identical to the others.
  4. Test it in isolationRun synthetic canaries against the Region's own endpoint before it gets traffic.
  5. Send it traffic graduallyAdd its latency record or Global Accelerator endpoint, using weights or traffic dials to start small.

"The new Region fails under load although the stack is identical" usually means default service quotas in that Region (Lambda concurrency, vCPUs, API rates). Quotas don't copy across Regions.

Configuring serverless applications (API Gateway, Lambda, Fargate)

Skill

Amazon API Gateway

REST APIHTTP APIWebSocket API
FeaturesMost: caching, usage plans and API keys, request validation, AWS WAF, private endpointsFewer, but faster and cheaper; JWT authorizers built inTwo-way persistent connections
Use forPublic APIs needing quotas, caching or transformationMost Lambda and HTTP backendsChat, live dashboards, notifications
  • Throttling: set limits per stage and route (rate and burst). Usage plans with API keys give each client its own rate and quota (REST APIs).
  • Caching: per-stage cache for REST APIs (TTL default 300 seconds), reducing calls to the backend.
  • Integration timeout: 29 seconds by default. Regional and private REST APIs can raise it (at the cost of a lower throttle quota); for longer work, respond quickly and process asynchronously (SQS, Step Functions).

template.yml (SAM) 
ProcessOrderFunction:
  Type: AWS::Serverless::Function
  Properties:
    CodeUri: src/process_order/
    Handler: app.handler
    Runtime: python3.12
    Architectures: [arm64]
    MemorySize: 1024
    Timeout: 60
    ReservedConcurrentExecutions: 200          # never more than 200 at once
    Events:
      Orders:
        Type: SQS
        Properties:
          Queue: !GetAtt OrdersQueue.Arn
          BatchSize: 10
          MaximumBatchingWindowInSeconds: 5     # wait up to 5 s to fill a batch
          ScalingConfig:
            MaximumConcurrency: 50             # protect the database behind this function
          FunctionResponseTypes: [ReportBatchItemFailures]   # retry only failed messages

OrdersApi:
  Type: AWS::Serverless::HttpApi
  Properties:
    DefaultRouteSettings:
      ThrottlingRateLimit: 500                 # steady requests per second
      ThrottlingBurstLimit: 1000

The SQS queue's visibility timeout should be at least six times the function's timeout (AWS guidance), so messages aren't redelivered while a batch is still being processed or retried.

AWS Fargate

  • Task size: choose CPU and memory from the supported combinations (from 0.25 vCPU with 0.5 GB up to 16 vCPU with 120 GB).
  • Cost: ARM64 (Graviton) and Fargate Spot reduce cost; Spot suits interruptible or stateless work.
  • Storage: ephemeral storage defaults to 20 GiB, configurable up to 200 GiB; mount EFS for shared or persistent files.
  • Scaling: through ECS Service Auto Scaling (or EKS), with no servers to add.

Key takeaways

  • Scale on a metric that tracks load: request count per target for web tiers, backlog per instance for queue workers, CPU for CPU-bound work.
  • Decouple with SQS (buffer), SNS (fan-out), EventBridge (routing) and Kinesis (ordered streams). Set SQS visibility timeouts longer than processing, and use DLQs.
  • Serverless scales automatically within quotas: Lambda concurrency = requests per second × duration; API Gateway throttles; DynamoDB partitions can get hot.
  • Fix symptoms by cause: predictive scaling and warm pools for late scale-out, RDS Proxy for connection exhaustion, DAX or ElastiCache for read load, better keys for hot partitions, quota increases for hard ceilings.
  • EC2 Auto Scaling: target tracking by default, predictive and scheduled for known patterns, mixed instances for capacity. Application Auto Scaling for ECS, DynamoDB, Aurora and Lambda provisioned concurrency.
  • Caching: CloudFront at the edge, API Gateway cache, ElastiCache for the application, DAX for DynamoDB; lazy loading vs write-through, always with a TTL.
  • ECS: Fargate with capacity provider strategies (Base and Weight for Spot); EC2 capacity providers with managed scaling. EKS: HPA for pods, Karpenter or Cluster Autoscaler for nodes, pods need resource requests.
  • Going global: latency routing or Global Accelerator, identical stacks per Region, DynamoDB global tables, and quotas raised in every Region.
  • Lambda: memory sets CPU, reserved concurrency caps, provisioned concurrency and SnapStart for cold starts, SQS maximum concurrency to protect downstream systems.
