Task 5.2: Implement configuration changes in response to events

Changing systems and infrastructure automatically when something happens: pushing configuration to a fleet safely, reacting to launches, terminations and API calls, and bringing drifted resources back to their desired state.

Overview

Task statement 5.2

Implement configuration changes in response to events.

Task 5.1 was about receiving events. This task is about what you change when they arrive: instance settings, application configuration, scaling, security settings, or whole resources. The skill is doing it automatically, safely (in controlled batches, with approvals where needed) and without fighting your own infrastructure as code. Typical scenarios: "a parameter changes and every web server must reload it", "logs must be copied off instances before Auto Scaling terminates them", "new buckets must have encryption turned on automatically", or "instances drift from the approved configuration".

Rate control and error thresholds

Run Command, State Manager and Automation can all limit blast radius:

  • Maximum concurrency: how many targets run at once (a number such as 10, or a percentage such as 10%).
  • Maximum errors: how many failures are tolerated before Systems Manager stops sending the change to remaining targets.
Knowledge

Auto Scaling as fleet management

An Auto Scaling group manages a fleet's size and health, and it also controls configuration through its launch template:

  • Launch template versions: every new instance uses the configured version (AMI, instance type, user data, instance profile).
  • Instance refresh: replaces existing instances so they pick up a new launch template version, in batches with a minimum healthy percentage, optional checkpoints and automatic rollback.
  • Health replacement: unhealthy instances (by EC2 or ELB health checks) are terminated and replaced from the template.
  • Lifecycle hooks: pause an instance while it launches or terminates, so automation can configure it or clean up before it continues.
  • Scaling plans: AWS Auto Scaling (the service) lets one scaling plan manage scaling for several resource types together (Auto Scaling groups, ECS services, DynamoDB tables, Aurora replicas) from a single interface.
  • "Change the configuration of every instance in the group": update the launch template and run an instance refresh (immutable).
  • "Change a setting on running instances now, without replacing them": Run Command (mutable).

Configuration management services (AWS Config)

Knowledge

AWS Config doesn't change resources by itself. It tells you what the configuration is, how it changed, and whether it's allowed, and that information drives automated changes.

PartWhat it does
Configuration recorderRecords all supported resource types, or chosen ones. Recording is continuous (every change) or periodic (daily)
Configuration itemsA snapshot of a resource's configuration and relationships each time it changes; the timeline shows its history
Change notificationsConfiguration changes and compliance changes go to EventBridge (Config Configuration Item Change, Config Rules Compliance Change) and optionally SNS
Rules and remediationEvaluate compliance, then run SSM Automation documents to fix non-compliant resources

"What did this security group look like last Tuesday, and who changed it?" points to the AWS Config timeline for the configuration, linked to the CloudTrail event for who made the change.

Run Command with rate control

Assume the web tier needs a larger connection limit right away:

aws ssm send-command \
  --document-name AWS-RunShellScript \
  --targets Key=tag:Role,Values=web \
  --parameters 'commands=["sudo sed -i \"s/^worker_connections .*/worker_connections 4096;/\" /etc/nginx/nginx.conf","sudo nginx -t","sudo systemctl reload nginx"]' \
  --max-concurrency "10%" \
  --max-errors "2" \
  --output-s3-bucket-name ops-command-output \
  --cloud-watch-output-config CloudWatchOutputEnabled=true \
  --comment "Raise nginx worker_connections (CHG-1042)"
  • Batches: 10% of web instances change at a time, and the command stops after 2 failures.
  • Validation: nginx -t validates the configuration first, so a bad change fails before the reload.
  • Audit: output goes to S3 and CloudWatch Logs; CloudTrail records who sent the command.

Event-driven: reload configuration when a parameter changes

Parameter Store emits a Parameter Store Change event when a parameter is created, updated or deleted. An EventBridge rule can send a Run Command straight to the affected instances, without any Lambda function:

parameter-change-rule.yml 
ReloadOnParameterChange:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [aws.ssm]
      detail-type: [Parameter Store Change]
      detail:
        name: [/orders/prod/max-connections]
        operation: [Update]
    Targets:
      - Id: reload-web-tier
        Arn: !Sub arn:aws:ssm:${AWS::Region}::document/AWS-RunShellScript
        RoleArn: !GetAtt EventsRunCommandRole.Arn          # allows ssm:SendCommand
        RunCommandParameters:
          RunCommandTargets:
            - { Key: tag:Role, Values: [web] }
        Input: '{"commands": ["/opt/orders/bin/reload-config.sh"]}'

Pushing changes to every instance at once (no rate control), or outside the agreed window, turns a small mistake into an outage. On the exam, prefer answers with rate control and error thresholds, maintenance windows or Change Calendar, and a validation step.

Modifying infrastructure configurations in response to events

Skill

Auto Scaling lifecycle hooks

A lifecycle hook holds an instance in a wait state (Pending:Wait on launch, Terminating:Wait on termination) until your automation calls CompleteLifecycleAction, or the heartbeat timeout expires (1 hour by default, extendable with RecordLifecycleActionHeartbeat).

Assume application logs must be copied to S3 before any web instance is terminated by scale-in:

  1. Scale-in chooses an instanceThe terminate hook moves it to Terminating:Wait; it stays running.
  2. EventBridge receives the lifecycle eventEC2 Instance-terminate Lifecycle Action, with the instance ID, hook name and group name.
  3. An Automation runbook ships the logsIt runs a command on the instance to sync logs to S3.
  4. The runbook completes the hookIt calls CompleteLifecycleAction with CONTINUE, and the instance terminates.
terminate-hook.yml 
ShipLogsHook:
  Type: AWS::AutoScaling::LifecycleHook
  Properties:
    AutoScalingGroupName: !Ref WebAsg
    LifecycleHookName: ship-logs
    LifecycleTransition: autoscaling:EC2_INSTANCE_TERMINATING
    HeartbeatTimeout: 600                       # give up after 10 minutes
    DefaultResult: CONTINUE                      # terminate anyway if automation never answers

TerminateHookRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [aws.autoscaling]
      detail-type: [EC2 Instance-terminate Lifecycle Action]
      detail:
        AutoScalingGroupName: [web-asg]
    Targets:
      - Id: ship-logs-runbook
        Arn: !Sub arn:aws:ssm:${AWS::Region}:${AWS::AccountId}:automation-definition/ShipLogsBeforeTerminate:$DEFAULT
        RoleArn: !GetAtt EventsRunAutomationRole.Arn
        InputTransformer:
          InputPathsMap:
            instance: $.detail.EC2InstanceId
            asg: $.detail.AutoScalingGroupName
            hook: $.detail.LifecycleHookName
          InputTemplate: '{"InstanceId": ["<instance>"], "AsgName": ["<asg>"], "HookName": ["<hook>"]}'
ShipLogsBeforeTerminate (Automation runbook) 
schemaVersion: "0.3"
assumeRole: arn:aws:iam::111111111111:role/LifecycleAutomationRole
parameters:
  InstanceId: { type: String }
  AsgName: { type: String }
  HookName: { type: String }
mainSteps:
  - name: ShipLogs
    action: aws:runCommand
    onFailure: Continue                           # still release the instance if this fails
    inputs:
      DocumentName: AWS-RunShellScript
      InstanceIds: ["{{ InstanceId }}"]
      Parameters:
        commands: ["aws s3 sync /var/log/orders s3://example-app-logs/{{ InstanceId }}/"]
  - name: CompleteHook
    action: aws:executeAwsApi
    inputs:
      Service: autoscaling
      Api: CompleteLifecycleAction
      AutoScalingGroupName: "{{ AsgName }}"
      LifecycleHookName: "{{ HookName }}"
      InstanceId: "{{ InstanceId }}"
      LifecycleActionResult: CONTINUE

A launch hook works the same way in the other direction: hold a new instance in Pending:Wait while it's configured, registered or warmed up, then complete with CONTINUE (or ABANDON to discard it if setup failed).

If nothing ever calls CompleteLifecycleAction, every scale-in or scale-out waits for the full heartbeat timeout. "Scaling takes an hour" with lifecycle hooks configured means the automation isn't completing them.

secure_new_bucket.py (EventBridge rule on CreateBucket) 
import boto3

s3 = boto3.client("s3")

def handler(event, context):
    bucket = event["detail"]["requestParameters"]["bucketName"]
    s3.put_public_access_block(
        Bucket=bucket,
        PublicAccessBlockConfiguration={
            "BlockPublicAcls": True, "IgnorePublicAcls": True,
            "BlockPublicPolicy": True, "RestrictPublicBuckets": True,
        },
    )
    s3.put_bucket_encryption(
        Bucket=bucket,
        ServerSideEncryptionConfiguration={
            "Rules": [{"ApplyServerSideEncryptionByDefault": {"SSEAlgorithm": "aws:kms"}}]
        },
    )

Automation that edits resources owned by CloudFormation creates drift, and the next stack update may undo it, causing the two to fight. For stack-managed resources, prefer fixing the template or triggering the pipeline. Use direct API fixes for resources created outside IaC, or as an emergency stop-gap.

Custom remediation from compliance changes

When no SSM document fits, react to the compliance change event with your own code. Assume instances without an owner tag must be tagged from whoever launched them:

eventbridge-pattern.json 
{
  "source": ["aws.config"],
  "detail-type": ["Config Rules Compliance Change"],
  "detail": {
    "configRuleName": ["required-tags-owner"],
    "newEvaluationResult": { "complianceType": ["NON_COMPLIANT"] }
  }
}

The target Lambda function looks up the instance's RunInstances event in CloudTrail, adds the creator as the owner tag, and notifies them. Config re-evaluates the instance and marks it compliant.

A safe remediation process

  1. DetectA Config rule, association compliance, drift detection or a finding.
  2. DecideLow-risk, well-understood fixes run automatically. Risky ones open an OpsItem or a Change Manager request with an approval step.
  3. Act within limitsRate control, retries with limits, exceptions for resources that are allowed to differ, and change windows.
  4. VerifyRe-evaluate compliance and check the application still works.
  5. Record and tellAutomation executions, CloudTrail and notifications to the resource owner give an audit trail.
  • "Keep instances in the approved configuration and correct drift automatically": a State Manager association.
  • "Correct non-compliant AWS resource settings automatically": an AWS Config rule with automatic remediation.
  • "Operators should review issues and run the fix with one click": OpsCenter OpsItems with runbooks.

Two automations that disagree (for example, a Config remediation that enables a setting and a scheduled script that disables it) loop forever. Keep one source of truth for each setting, and watch for remediations that run repeatedly on the same resource.

Key takeaways

  • Systems Manager manages fleets by tag: Run Command (now), State Manager (keep it so), Automation (multi-step, including AWS APIs), Patch Manager, Change Manager and Change Calendar, OpsCenter.
  • Use maximum concurrency and maximum errors to limit blast radius; validate before applying; send output to S3 or CloudWatch Logs.
  • Auto Scaling manages fleet configuration through launch template versions and instance refresh, health replacement, and lifecycle hooks; AWS Auto Scaling scaling plans cover several resource types.
  • AWS Config records configuration history and compliance and emits change events; it fixes things only through remediation actions.
  • EventBridge can target Run Command and Automation directly, for example reloading configuration on a Parameter Store Change event.
  • Lifecycle hooks hold instances in Pending:Wait or Terminating:Wait until CompleteLifecycleAction (CONTINUE or ABANDON) or the heartbeat timeout.
  • React to API calls (new buckets, open security groups, untagged instances) with EventBridge plus Lambda or Automation, but change IaC-owned resources through IaC to avoid drift.
  • Remediate by type: State Manager for instance drift, Config remediation for resource settings, drift detection plus stack updates for IaC, health checks for unhealthy capacity, approvals for risky fixes.
