Task 6.1: Implement techniques for identity and access management at scale

Giving people and workloads exactly the access they need across many accounts: choosing the right IAM entity and policy type, federating human sign-in, delegating safely with permissions boundaries, setting guardrails with SCPs, and replacing long-lived secrets with rotated or temporary credentials.

Overview

Task statement 6.1

Implement techniques for identity and access management at scale.

"At scale" means dozens or hundreds of accounts, many teams and many workloads. You can't hand-write a policy per person, so the exam looks for patterns that scale: federated sign-in instead of IAM users, roles instead of access keys, guardrails set once at the organization level, and tags instead of one policy per project. Typical scenarios: "developers must be able to create roles without escalating their own privileges", "no account may disable CloudTrail", or "the database password must rotate every 30 days without downtime".

IAM entities for human and machine access

Knowledge

An identity (who is calling) gets permissions from policies (what they may do). The modern rule: people sign in through federation and receive a role; workloads run with a role. Long-lived IAM user access keys are the exception.

EntityWhat it isUse it for
IAM userA long-lived identity with a password and/or access keysBreak-glass access, or a third-party tool that can't use roles. Avoid for people and workloads.
IAM groupA set of users that share policiesManaging permissions for the few IAM users you still have. A group is not a principal: it can't be named in a policy.
IAM roleAn identity with no permanent credentials; whoever assumes it gets temporary credentials from STSWorkloads, cross-account access, federated people, AWS services acting for you
Identity providerAn IAM SAML or OIDC provider that IAM trusts to vouch for usersFederating a corporate IdP or a CI system (GitHub Actions, GitLab) into roles
Service-linked roleA role owned and managed by an AWS serviceLetting a service (Auto Scaling, Organizations, Config) act in your account. You can't edit its policies.

Resource-based and session policies

Assume a data account 333333333333 owns the bucket shared-reports, and an analytics role in account 222222222222 must read it. The bucket policy grants the other account's role; the role's own identity policy must also allow s3:GetObject on the bucket.

bucket-policy.json (in 333333333333) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::222222222222:role/AnalyticsRole"
    },
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::shared-reports/*"
  }]
}

A session policy narrows one session. Here a script assumes a broad role but only needs one prefix:

aws sts assume-role \
  --role-arn arn:aws:iam::222222222222:role/AnalyticsRole \
  --role-session-name nightly-export \
  --policy '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::shared-reports/2026/*"}]}'
# effective access = role permissions AND session policy

How a request is evaluated

For a request inside one account, AWS checks these in order. Any explicit deny ends the evaluation; otherwise every applicable layer must allow.

  1. Explicit deny anywhereA Deny in any applicable policy (SCP, RCP, resource, identity, boundary, session) wins over every allow.
  2. SCPs and RCPsEvery level from the organization root down to the account must allow the action. Not applied in the management account.
  3. Resource-based policyIn the same account, a resource policy that names the principal can allow the request on its own.
  4. Identity-based policyOtherwise the user's or role's policies must allow the action.
  5. Permissions boundaryIf set, the action must also be inside the boundary.
  6. Session policyIf passed, the action must also be inside the session policy.
  7. DefaultNothing allowed it: implicit deny.

Cross-account access needs both sides. The caller's account must allow the action in an identity-based policy, and the resource's account must allow it in a resource-based policy (or a role trust policy, if the caller assumes a role there). For KMS-encrypted objects, the key policy must allow the caller too.

A group can't be a principal. A policy with "Principal": {"AWS": "arn:aws:iam::...:group/Admins"} is invalid; grant the group's members access through the group's identity policy instead.

Identity federation

Knowledge

Federation lets an external identity provider (Okta, Microsoft Entra ID, Google Workspace, Active Directory, a CI system) authenticate users. AWS then issues temporary role credentials. Nobody gets an IAM user, and leavers lose access when they're disabled in the IdP.

OptionScopeUse it when
IAM Identity CenterWhole organizationPeople need access to many accounts. The default exam answer for workforce access.
IAM SAML 2.0 providerOne accountA single account federates directly with a corporate IdP (older pattern)
IAM OIDC providerOne accountWorkloads: GitHub Actions, GitLab CI, EKS IRSA
Amazon CognitoApplicationEnd users of your app sign in (customers, not employees)

IAM Identity Center

  • Identity source: the built-in directory, AWS Managed Microsoft AD (or AD Connector), or an external IdP over SAML 2.0. With an external IdP, SCIM provisions users and groups automatically.
  • Permission set: a template of policies (managed, inline, customer managed policy references, an optional permissions boundary) plus a session duration.
  • Assignment: group + permission set + account. Identity Center creates a role named AWSReservedSSO_<PermissionSet>_<id> in each assigned account and keeps it in sync.
  • Delegated administrator: run Identity Center from a member account instead of the management account.
  • Attributes for access control: pass IdP attributes (department, cost center) as session tags for ABAC.

When a developer signs in:

  1. Open the AWS access portalIdentity Center redirects to the corporate IdP, which authenticates the user and applies MFA.
  2. Choose an account and permission setThe portal lists only the accounts and permission sets assigned to the user's groups.
  3. Receive temporary credentialsIdentity Center assumes the matching AWSReservedSSO_* role in that account. The CLI does the same with aws sso login.

"Centrally manage access for hundreds of employees to many accounts using the existing corporate directory" is IAM Identity Center with the IdP as the identity source and SCIM. Changing a permission set updates the role in every assigned account.

OIDC federation for CI pipelines

Assume a GitHub Actions workflow in repo acme/orders deploys to account 222222222222. Instead of storing access keys as GitHub secrets, the account trusts GitHub's OIDC provider and the workflow exchanges its token for a role.

github-oidc.yaml 
GitHubOidcProvider:
  Type: AWS::IAM::OIDCProvider
  Properties:
    Url: https://token.actions.githubusercontent.com
    ClientIdList: [ sts.amazonaws.com ]

GitHubDeployRole:
  Type: AWS::IAM::Role
  Properties:
    RoleName: GitHubDeployRole
    MaxSessionDuration: 3600
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:
            Federated: !Ref GitHubOidcProvider
          Action: sts:AssumeRoleWithWebIdentity
          Condition:
            StringEquals:
              token.actions.githubusercontent.com:aud: sts.amazonaws.com
              token.actions.githubusercontent.com:sub: repo:acme/orders:ref:refs/heads/main   # only this repo and branch
    ManagedPolicyArns:
      - !Ref DeployPolicy

An OIDC trust policy without a sub condition lets any repository on GitHub assume the role. Always pin the repository, and usually the branch or environment.

Delegating permission management with permissions boundaries

Knowledge

A permissions boundary is a managed policy set as the maximum permissions for a user or role. Effective permissions are the intersection of the identity-based policies and the boundary. Its main use is delegation: letting developers create roles for their own workloads without being able to create a role more powerful than allowed.

Assume developers in account 222222222222 build Lambda functions and need to create execution roles. Security wants every role they create limited to the team's DynamoDB tables, S3 buckets and logs.

  1. Security writes the boundaryA managed policy DevWorkloadBoundary that lists the most any developer-created role may ever do.
  2. Developers may create roles only with that boundaryTheir policy allows iam:CreateRole only when the request attaches DevWorkloadBoundary.
  3. Developers can't remove or edit the boundaryExplicit denies on deleting the boundary, changing the boundary policy, or changing their own permissions.
  4. ResultWhatever policy a developer attaches to the new role, it can never exceed the boundary.
developer-policy.yaml 
DeveloperPolicy:
  Type: AWS::IAM::ManagedPolicy
  Properties:
    PolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Sid: CreateRolesOnlyWithBoundary
          Effect: Allow
          Action: [ iam:CreateRole, iam:PutRolePolicy, iam:AttachRolePolicy, iam:DetachRolePolicy, iam:DeleteRolePolicy ]
          Resource: arn:aws:iam::222222222222:role/app-*          # only roles with this prefix
          Condition:
            StringEquals:
              iam:PermissionsBoundary: arn:aws:iam::222222222222:policy/DevWorkloadBoundary
        - Sid: PassOnlyAppRoles
          Effect: Allow
          Action: iam:PassRole
          Resource: arn:aws:iam::222222222222:role/app-*
        - Sid: NoBoundaryTampering
          Effect: Deny
          Action: [ iam:DeleteRolePermissionsBoundary, iam:PutRolePermissionsBoundary ]
          Resource: "*"
        - Sid: NoEditingTheBoundaryPolicy
          Effect: Deny
          Action: [ iam:CreatePolicyVersion, iam:DeletePolicy, iam:DeletePolicyVersion, iam:SetDefaultPolicyVersion ]
          Resource: arn:aws:iam::222222222222:policy/DevWorkloadBoundary

The iam:PermissionsBoundary condition is what makes iam:CreateRole fail unless the boundary is attached. The app-* prefix stops developers from modifying security or admin roles.

"Allow developers to create IAM roles for their applications without allowing privilege escalation" is a permissions boundary plus a condition requiring it on iam:CreateRole. An SCP limits the whole account, so it can't tell developer-created roles apart from others.

A boundary grants nothing. A role with a boundary allowing s3:* but no identity policy can't read S3.

Organizational SCPs

Knowledge

Service control policies set the maximum permissions for every IAM user and role in the member accounts they apply to, including each account's root user. They are guardrails: they never grant access, so principals still need identity policies.

  • Inheritance: an action must be allowed at every level from the root to the account. A deny at any level applies to everything below it.
  • Default: the AWS managed FullAWSAccess SCP is attached everywhere. Most organizations keep it and add deny SCPs (a deny list), which is simpler than listing allowed services (an allow list).
  • Not affected: the management account, and service-linked roles.
  • Test first: attach new SCPs to a test OU, and use the "last accessed" data to check which services accounts really use.

A typical guardrail SCP attached to the Workloads OU:

scp-workload-guardrails.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectSecurityServices",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging", "cloudtrail:DeleteTrail", "cloudtrail:UpdateTrail",
        "guardduty:DeleteDetector", "guardduty:DisassociateFromMasterAccount",
        "config:StopConfigurationRecorder", "config:DeleteConfigurationRecorder"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/SecurityAdminRole"
        }
      }
    },
    {
      "Sid": "StayInTheOrganization",
      "Effect": "Deny",
      "Action": "organizations:LeaveOrganization",
      "Resource": "*"
    },
    {
      "Sid": "ApprovedRegionsOnly",
      "Effect": "Deny",
      "NotAction": [ "iam:*", "organizations:*", "sts:*", "support:*", "cloudfront:*", "route53:*", "budgets:*" ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": [ "us-east-1", "eu-west-1" ]
        }
      }
    }
  ]
}
  • ArnNotLike aws:PrincipalArn exempts the security team's role, so the guardrail doesn't block legitimate administration.
  • NotAction in the Region rule exempts global services, whose API calls go to us-east-1; without it, IAM and CloudFront would break in other Regions.

Other organization policies

PolicyControlsExample
SCPWhat your principals can doNobody in the account may stop CloudTrail
RCP (resource control policy)What can be done to your resources by anyone, including outside principalsS3 buckets and KMS keys may only be accessed by principals in the organization (aws:PrincipalOrgID)
Declarative policyThe configuration of a service across accounts, enforced even for new featuresBlock public access to EBS snapshots and AMIs; require IMDSv2

Backup policyAWS Backup plans applied to accountsDaily backups for every resource tagged backup=daily

An SCP has no effect on the management account. "Restrict every account including the management account" can't be done with SCPs; keep workloads out of the management account instead.

"Prevent anyone outside the organization from accessing our S3 buckets, even if a bucket policy is misconfigured" is an RCP (a data perimeter on resources). "Prevent our users from doing X" is an SCP.

Designing policies to enforce least privilege access

Skill

Least privilege means granting only the actions, on only the resources, under only the conditions a principal needs. In practice you start broad and tighten using evidence.

  1. Start from a scoped baselineAWS managed job-function policies, or a policy written for the known actions and resource ARNs.
  2. Generate from real activityIAM Access Analyzer generates a policy from the role's CloudTrail history over a chosen period.
  3. Remove what's unusedLast accessed information and Access Analyzer unused access findings show unused roles, keys, passwords, services and actions.
  4. Validate in the pipelineAccess Analyzer policy validation and custom policy checks fail the build if a change adds risky access.
  5. Monitor external accessAccess Analyzer external access findings flag resources shared outside the account or organization.

A scoped policy

An orders Lambda function needs to read and write one DynamoDB table and read one secret:

orders-function-policy.yaml 
PolicyDocument:
  Version: "2012-10-17"
  Statement:
    - Effect: Allow
      Action: [ dynamodb:GetItem, dynamodb:PutItem, dynamodb:UpdateItem, dynamodb:Query ]   # not dynamodb:*
      Resource: !GetAtt OrdersTable.Arn                                                 # not "*"
    - Effect: Allow
      Action: secretsmanager:GetSecretValue
      Resource: !Ref PaymentApiSecret

Conditions that tighten access

Condition keyRestricts to
aws:PrincipalOrgIDPrincipals in your organization (cross-account sharing without listing accounts)
aws:SourceVpce, aws:SourceVpcRequests through a specific VPC endpoint or VPC
aws:SourceArn, aws:SourceAccountA specific calling resource when a service acts for you (prevents the "confused deputy" problem)
aws:SecureTransportHTTPS only (deny when false)
aws:RequestedRegionApproved Regions
aws:MultiFactorAuthPresentSessions authenticated with MFA
aws:CalledVia, kms:ViaServiceRequests made through a specific service (for example, a KMS key usable only through S3)

Policy checks in a pipeline

In a CodeBuild stage that reviews IAM changes, compare the new policy with the approved one and block anything granting more:

aws accessanalyzer check-no-new-access \
  --policy-type IDENTITY_POLICY \
  --existing-policy-document file://approved-policy.json \
  --new-policy-document file://new-policy.json
# result FAIL = the new policy grants access the approved one didn't

aws accessanalyzer check-access-not-granted \
  --policy-type IDENTITY_POLICY \
  --policy-document file://new-policy.json \
  --access '[{"actions":["iam:CreateUser","s3:DeleteBucket"]}]'
# result FAIL = the policy grants one of the listed actions

"Reduce a role's permissions to what it actually uses" is IAM Access Analyzer policy generation (based on CloudTrail). "Find roles and keys nobody has used for 90 days across the organization" is Access Analyzer unused access findings.

ABAC example

Assume developers sign in through IAM Identity Center, and the IdP passes each user's project as the session tag project. One permission set lets every developer start, stop and connect to only their own project's instances:

abac-permission-set-policy.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OwnProjectInstancesOnly",
      "Effect": "Allow",
      "Action": [ "ec2:StartInstances", "ec2:StopInstances", "ssm:StartSession" ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/project": "${aws:PrincipalTag/project}"
        }
      }
    },
    {
      "Sid": "LaunchOnlyWithOwnProjectTag",
      "Effect": "Allow",
      "Action": [ "ec2:RunInstances", "ec2:CreateTags" ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:RequestTag/project": "${aws:PrincipalTag/project}"
        }
      }
    },
    {
      "Sid": "NoRetagging",
      "Effect": "Deny",
      "Action": [ "ec2:CreateTags", "ec2:DeleteTags" ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:ResourceTag/project": "${aws:PrincipalTag/project}"
        },
        "Null": {
          "aws:ResourceTag/project": "false"
        }
      }
    }
  ]
}
  • aws:PrincipalTag is the tag on the caller (from the role, or from session tags set by the IdP).
  • aws:ResourceTag is the tag already on the resource; aws:RequestTag is the tag in the request.
  • The deny stops users from retagging another project's resources to gain access to them. ABAC is only as safe as the control over who can change tags.

"Avoid updating policies every time a new project is added" or "permissions should follow the user's department in the corporate directory" points to ABAC, with Identity Center attributes for access control or SAML session tags.

Automating credential rotation for machine identities

Skill

The best machine credential is one you don't store: a role gives temporary credentials that AWS rotates automatically. Where a real secret is unavoidable (database passwords, third-party API keys), keep it in Secrets Manager and let it rotate on a schedule.

CredentialHow to rotate it
AWS credentials for code on AWSUse a role. Credentials expire and renew automatically.
AWS credentials for code outside AWSIAM Roles Anywhere or OIDC federation. If access keys are unavoidable, rotate them with automation and detect old ones with the AWS Config rule access-keys-rotated.
RDS or Aurora master passwordManaged rotation: ManageMasterUserPassword: true stores and rotates it in Secrets Manager (every 7 days by default).
Other database usersSecrets Manager rotation with an AWS-provided rotation function, or RDS IAM database authentication (15-minute tokens, no password)
Third-party API keysSecrets Manager rotation with a custom Lambda function that calls the provider's API
Parameter Store SecureStringNo built-in rotation. Use Secrets Manager when rotation is required.

Rotating a database secret

db-secret.yaml 
Transform: AWS::SecretsManager-2020-07-23        # needed for HostedRotationLambda
Resources:
  AppDbSecret:
    Type: AWS::SecretsManager::Secret
    Properties:
      Name: prod/orders/db-app-user
      KmsKeyId: !Ref SecretsKey                 # customer managed key if shared across accounts
      GenerateSecretString:
        SecretStringTemplate: '{"username":"orders_app"}'
        GenerateStringKey: password
        PasswordLength: 32
        ExcludeCharacters: '"@/\'

  AppDbSecretAttachment:                       # adds host, port and engine to the secret
    Type: AWS::SecretsManager::SecretTargetAttachment
    Properties:
      SecretId: !Ref AppDbSecret
      TargetId: !Ref OrdersDbCluster
      TargetType: AWS::RDS::DBCluster

  AppDbRotation:
    Type: AWS::SecretsManager::RotationSchedule
    DependsOn: AppDbSecretAttachment
    Properties:
      SecretId: !Ref AppDbSecret
      RotationRules:
        ScheduleExpression: rate(30 days)
      HostedRotationLambda:                     # AWS creates the rotation function
        RotationType: PostgreSQLSingleUser
        VpcSubnetIds: !Join [ ",", [ !Ref PrivateSubnetA, !Ref PrivateSubnetB ] ]
        VpcSecurityGroupIds: !Ref RotationLambdaSG

Each rotation runs the function four times, once per step:

  1. createSecretGenerates a new password and stores it as a new version labelled AWSPENDING.
  2. setSecretChanges the password in the database to the pending value.
  3. testSecretLogs in to the database with the pending value to prove it works.
  4. finishSecretMoves the AWSCURRENT label to the new version; the old one becomes AWSPREVIOUS.
StrategyHow it worksTrade-off
Single userChanges the password of the one userSimple; connections opened with the old password during the switch can fail briefly
Alternating usersTwo users (app and app_clone); each rotation updates the inactive one and switchesNo interruption; needs a separate admin secret to manage the users
  • Network: the rotation function runs in the VPC and must reach both the database and the Secrets Manager endpoint (a VPC interface endpoint or a NAT gateway).
  • Applications: read the secret at runtime (with the Secrets Manager caching client) rather than at build time, so they pick up new values. ECS injects secrets only when a task starts, so long-running tasks need a restart or must read the secret themselves.
  • Monitoring: failed rotations appear in CloudTrail and the function's logs; an EventBridge rule on RotationFailed can alert.

"Rotation fails with a timeout" usually means the rotation Lambda function is in a private subnet with no route to the Secrets Manager endpoint, or its security group can't reach the database.

"Rotate database credentials automatically" is Secrets Manager, not Parameter Store. "Eliminate database passwords for the application altogether" is RDS IAM authentication.

Managing permissions for human and machine identities

Skill

Multi-factor authentication

  • Federated users: enforce MFA in the IdP or in IAM Identity Center's MFA settings.
  • Root users: MFA on the management account's root user. For member accounts, centralized root access lets the management account remove member root credentials altogether and run privileged root tasks centrally when needed.
  • IAM users that remain: require MFA for sensitive actions with a condition:
{
  "Sid": "DenyDeleteWithoutMfa",
  "Effect": "Deny",
  "Action": [ "ec2:TerminateInstances", "s3:DeleteBucket" ],
  "Resource": "*",
  "Condition": {
    "BoolIfExists": {
      "aws:MultiFactorAuthPresent": "false"
    }
  }
}

Use BoolIfExists, not Bool, in a deny. Requests signed with long-term access keys don't include the key at all, so a plain Bool ... "false" doesn't match them and the deny is skipped.

AWS STS

APIUsed by
AssumeRoleRoles assumed by users, services and other accounts (cross-account access)
AssumeRoleWithSAMLSAML federation through an IAM SAML provider
AssumeRoleWithWebIdentityOIDC federation: CI systems, EKS IRSA, Cognito identity pools
GetSessionTokenAn IAM user getting temporary credentials, typically after entering an MFA code for the CLI
GetFederationTokenA proxy application issuing credentials for its users (rare)
  • Session duration: 1 hour by default; up to the role's MaxSessionDuration (1 to 12 hours). Role chaining (a role assuming another role) is limited to 1 hour.
  • External ID: a third party (a monitoring SaaS) that assumes a role in your account must pass the sts:ExternalId you agreed on. This prevents the confused deputy problem.
  • Source identity: sts:SourceIdentity records the original user through role chains, so CloudTrail shows who really acted.
  • Regional endpoints: use the STS endpoint in your Region for lower latency and resilience.
  • Revoking leaked session credentials: temporary credentials can't be deleted. Use "Revoke active sessions" on the role, which adds a deny for sessions issued before now (aws:TokenIssueTime), then fix the root cause.

AssumeRolePolicyDocument:
  Version: "2012-10-17"
  Statement:
    - Effect: Allow

Instance profiles

An EC2 instance gets its role through an instance profile. The console creates one automatically with the same name as the role; in CloudFormation you create it yourself.

AppInstanceProfile:
  Type: AWS::IAM::InstanceProfile
  Properties:
    Roles: [ !Ref AppInstanceRole ]                 # exactly one role

AppLaunchTemplate:
  Type: AWS::EC2::LaunchTemplate
  Properties:
    LaunchTemplateData:
      IamInstanceProfile:
        Arn: !GetAtt AppInstanceProfile.Arn
      MetadataOptions:
        HttpTokens: required                          # IMDSv2 only
        HttpPutResponseHopLimit: 1
  • IMDSv2 (session tokens) protects the instance's role credentials from server-side request forgery. Enforce it with HttpTokens: required, a declarative policy, or the condition ec2:MetadataHttpTokens.
  • To launch an instance with a profile, the caller needs iam:PassRole on the role. "Access denied when launching with a role" is usually a missing iam:PassRole.

CLI profiles

Named profiles in ~/.aws/config let people and scripts switch between accounts using temporary credentials:

~/.aws/config 
[sso-session acme]
sso_start_url = https://acme.awsapps.com/start
sso_region = us-east-1
sso_registration_scopes = sso:account:access

[profile prod-readonly]                      # IAM Identity Center: run aws sso login --profile prod-readonly
sso_session = acme
sso_account_id = 222222222222
sso_role_name = ReadOnly
region = us-east-1

[profile prod-deploy]                        # role assumption from another profile, with MFA
source_profile = tooling
role_arn = arn:aws:iam::222222222222:role/DeployRole
mfa_serial = arn:aws:iam::111111111111:mfa/alice
duration_seconds = 3600

"Engineers need CLI access to several accounts without long-term keys" is IAM Identity Center with aws sso login and named profiles.

Key takeaways

  • People: federate through IAM Identity Center (permission sets, assignments, SCIM). Workloads: roles through instance profiles, execution and task roles, EKS Pod Identity, IAM Roles Anywhere or OIDC. IAM users and access keys are the exception.
  • Evaluation: explicit deny wins; SCPs, RCPs, boundaries and session policies only cap; identity or resource policies grant. Cross-account access needs both sides (and the KMS key policy).
  • OIDC trust policies for CI must pin sub to the repository and branch.
  • Permissions boundary + iam:PermissionsBoundary condition on iam:CreateRole = safe delegation. Boundaries grant nothing.
  • SCPs: deny-list guardrails inherited down the OU tree; no effect on the management account or service-linked roles. Exempt admin roles with aws:PrincipalArn and global services with NotAction. RCPs protect resources from outside principals.
  • Least privilege: Access Analyzer policy generation, unused and external access findings, and policy checks in the pipeline; tighten with condition keys.
  • RBAC by job function; ABAC by matching aws:PrincipalTag to aws:ResourceTag, with tag changes locked down.
  • Secrets Manager rotation (createSecret, setSecret, testSecret, finishSecret); alternating users for no interruption; the function needs network access to the endpoint and database. Parameter Store doesn't rotate.
  • MFA with BoolIfExists; STS session limits (1–12 hours, 1 hour when chaining), external IDs for third parties, revoke sessions by token issue time; IMDSv2 and iam:PassRole for instance profiles.
