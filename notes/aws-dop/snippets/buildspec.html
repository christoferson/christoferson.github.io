buildspec patterns

CodeBuild build specifications for the jobs pipelines ask of them: building and pushing images, publishing test reports, caching, reading secrets, passing values to later stages, and running builds in parallel. Each snippet shows when to use it, the code with comments, and the detail that usually decides the exam answer.

A buildspec (buildspec.yml in the source root by default) tells CodeBuild which commands to run in each phase and what to keep afterwards. Phases always run in the order install, pre_build, build, post_build.

A minimal annotated buildspec

Use whenStarting a build project for an application, such as a Node.js service.

buildspec.yml 
version: 0.2                          # always 0.2: all commands share one shell

phases:
  install:
    runtime-versions:
      nodejs: 20                       # pin it; the default changes when versions retire
    commands:
      - npm ci
  pre_build:
    commands:
      - npm run lint
  build:
    commands:
      - npm test
      - npm run build
  post_build:
    commands:
      - echo "Build finished on $(date)"

artifacts:
  files:
    - '**/*'
  base-directory: dist                 # zip the contents of dist/, not the folder itself

Watch forIf a command fails in build, CodeBuild still runs post_build, so check $CODEBUILD_BUILD_SUCCEEDING (1 or 0) there before pushing or deploying anything.

Build and push a Docker image to ECR

Use whenA pipeline builds a container image and the next stage deploys it to ECS.

buildspec.yml 
version: 0.2

env:
  variables:
    REPO: 111111111111.dkr.ecr.us-east-1.amazonaws.com/orders

phases:
  pre_build:
    commands:
      - aws ecr get-login-password | docker login --username AWS --password-stdin ${REPO%%/*}
      - TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c1-7)   # commit ID, not "latest"
  build:
    commands:
      - docker build -t $REPO:$TAG .
  post_build:
    commands:
      - docker push $REPO:$TAG
      - printf '[{"name":"orders","imageUri":"%s"}]' $REPO:$TAG > imagedefinitions.json

artifacts:
  files:
    - imagedefinitions.json             # read by the CodePipeline ECS deploy action

Watch forThe project needs privileged mode to run the Docker daemon, and its service role needs ECR push permissions (ecr:GetAuthorizationToken plus the layer upload actions). The name in imagedefinitions.json must match the container name in the task definition. For CodeDeploy blue/green, write imageDetail.json instead.

Test and coverage reports

Use whenTest results and code coverage should appear in the CodeBuild console, with trends across builds.

phases:
  build:
    commands:
      - npx jest --ci --reporters=default --reporters=jest-junit --coverage

reports:
  unit-tests:                           # creates report group <project>-unit-tests
    files:
      - junit.xml
    file-format: JUNITXML                 # default; also CUCUMBERJSON, NUNITXML, TESTNGXML...
  coverage:
    files:
      - coverage/clover.xml
    file-format: CLOVERXML                # or COBERTURAXML, JACOCOXML, SIMPLECOV

Watch forReports are uploaded even if the tests fail, which is when you need them most. The service role needs codebuild:CreateReportGroup, CreateReport, UpdateReport and BatchPutTestCases (plus BatchPutCodeCoverages for coverage).

Caching dependencies

Use whenBuilds spend minutes downloading the same packages or Docker layers every time.

buildspec.yml 
cache:
  key: npm-$(codebuild-hash-files package-lock.json)   # exact match first (S3 cache)
  fallback-keys:
    - npm-                               # then prefix match on older caches
  paths:
    - '/root/.npm/**/*'
build project (CloudFormation) 
Cache:
  Type: S3                             # shared by every build, survives between hosts
  Location: tooling-build-cache/orders
# or a local cache on the build host:
# Cache:
#   Type: LOCAL
#   Modes: [ LOCAL_DOCKER_LAYER_CACHE, LOCAL_SOURCE_CACHE, LOCAL_CUSTOM_CACHE ]

Watch forLocal caches are best effort and only help builds that land on the same host shortly after. LOCAL_DOCKER_LAYER_CACHE requires privileged mode. LOCAL_CUSTOM_CACHE caches the buildspec paths.

Secrets and exported variables

Use whenThe build needs a token or password, or a later pipeline stage needs a value the build calculated.

env:
  parameter-store:
    SONAR_URL: /build/sonar/url            # parameter name
  secrets-manager:
    SONAR_TOKEN: prod/sonar:token          # secret-id:json-key[:version-stage:version-id]
    NPM_TOKEN: arn:aws:secretsmanager:us-east-1:333333333333:secret:npm-AbCdEf:token   # another account: use the ARN
  exported-variables:
    - IMAGE_TAG                          # available to later actions

phases:
  build:
    commands:
      - export IMAGE_TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c1-7)
# in CodePipeline, give the build action a namespace (BuildVariables)
# and reference the value in a later action as #{BuildVariables.IMAGE_TAG}

Watch forSecret and parameter values are masked in the logs. The service role needs ssm:GetParameters or secretsmanager:GetSecretValue (and kms:Decrypt for a customer managed key). Plain variables are visible in the console, so never put secrets there.

Primary and secondary artifacts

Use whenOne build produces several outputs, such as an application bundle and a CloudFormation template for different pipeline actions.

artifacts:
  files:                                 # primary artifact (always required)
    - '**/*'
  base-directory: dist
  exclude-paths:
    - '**/*.map'
  secondary-artifacts:
    TemplateArtifact:                     # must match an output artifact name in the action
      files:
        - infra/template.yaml
        - infra/prod-config.json
      discard-paths: yes                 # put both files at the root of the zip
    AppArtifact:
      files:
        - '**/*'
      base-directory: dist

Watch forWhen a CodePipeline build action has more than one output artifact, every identifier under secondary-artifacts must match one of the action's output artifact names.

Batch builds: build list and build matrix

Use whenOne trigger should run several builds in parallel, such as tests on several runtimes or images for several architectures.

batch:
  fast-fail: true                       # stop the others when one fails
  build-list:
    - identifier: amd64
      env:
        image: aws/codebuild/amazonlinux2-x86_64-standard:5.0
        variables: { ARCH: amd64 }
    - identifier: arm64
      env:
        type: ARM_CONTAINER
        image: aws/codebuild/amazonlinux2-aarch64-standard:3.0
        variables: { ARCH: arm64 }
    - identifier: integration
      buildspec: buildspec-integration.yml
      ignore-failure: true                # don't fail the batch

# or every combination of the listed values:
# batch:
#   build-matrix:
#     dynamic:
#       env:
#         variables:
#           NODE_VERSION: [ "18", "20", "22" ]

Watch forBatch builds must be enabled on the project, with a batch service role. Use build-graph with depend-on when some builds must wait for others, and build-fanout to split one test suite across parallel builds.

Cleanup and retries: finally and on-failure

Use whenTest resources must be cleaned up even when tests fail, or a flaky step should be retried.

phases:
  pre_build:
    on-failure: RETRY-2-.*connection timed out.*   # retry the build twice on this error only
    commands:
      - ./scripts/start-test-db.sh
  build:
    on-failure: ABORT                    # ABORT | CONTINUE | RETRY | RETRY-count | RETRY-regex
    commands:
      - npm run test:integration
    finally:                             # runs even if a command above failed
      - ./scripts/stop-test-db.sh

Watch forA failure in finally still fails the phase. on-failure works only on the EC2 compute images CodeBuild provides, not on Lambda compute or reserved capacity.
