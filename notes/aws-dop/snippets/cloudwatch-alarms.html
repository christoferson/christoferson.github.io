An alarm watches one metric (or one metric math expression) and changes between OK, ALARM and INSUFFICIENT_DATA. Actions run when the state changes, not continuously while it stays in ALARM.

Threshold alarm with M of N evaluation

Use whenA metric crossing a fixed value means trouble, but one noisy data point shouldn't page anyone.

cpu-alarm.yaml 
HighCpuAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: web-asg-high-cpu
    Namespace: AWS/EC2
    MetricName: CPUUtilization
    Dimensions:
      - Name: AutoScalingGroupName
        Value: !Ref WebAsg
    Statistic: Average
    Period: 60
    EvaluationPeriods: 5   # look at the last 5 periods (N)
    DatapointsToAlarm: 3   # 3 of them must breach (M)
    Threshold: 80
    ComparisonOperator: GreaterThanThreshold
    TreatMissingData: notBreaching
    AlarmActions:
      - !Ref OnCallTopic

Watch forTreatMissingData decides what gaps mean: missing (default), notBreaching, breaching or ignore. For "alert if the heartbeat metric stops arriving", use breaching.

Alarm on an error rate (metric math)

Use whenThe alarm should depend on a ratio, such as 5xx responses as a percentage of all requests, rather than a raw count.

error-rate-alarm.yaml 
ErrorRateAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: orders-alb-5xx-rate
    EvaluationPeriods: 3
    Threshold: 5   # percent
    ComparisonOperator: GreaterThanThreshold
    TreatMissingData: notBreaching
    Metrics:
      - Id: errors
        ReturnData: false   # input only
        MetricStat:
          Metric:
            Namespace: AWS/ApplicationELB
            MetricName: HTTPCode_Target_5XX_Count
            Dimensions:
              - Name: LoadBalancer
                Value: !GetAtt OrdersAlb.LoadBalancerFullName
          Period: 60
          Stat: Sum
      - Id: requests
        ReturnData: false
        MetricStat:
          Metric:
            Namespace: AWS/ApplicationELB
            MetricName: RequestCount
            Dimensions:
              - Name: LoadBalancer
                Value: !GetAtt OrdersAlb.LoadBalancerFullName
          Period: 60
          Stat: Sum
      - Id: rate
        Label: 5xx error rate (%)
        Expression: IF(requests > 0, 100 * errors / requests, 0)
        ReturnData: true   # the alarm evaluates this one

Watch forExactly one entry has ReturnData: true. With Metrics, don't also set MetricName, Statistic or Period at the top level; the period lives in each MetricStat.

Anomaly detection alarm

Use whenNormal values change by time of day or day of week, so no single fixed threshold works.

latency-anomaly-alarm.yaml 
LatencyAnomalyAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: orders-latency-anomaly
    EvaluationPeriods: 3
    ComparisonOperator: GreaterThanUpperThreshold
    ThresholdMetricId: band   # compare against the band, not a number
    Metrics:
      - Id: latency
        ReturnData: true
        MetricStat:
          Metric:
            Namespace: AWS/ApplicationELB
            MetricName: TargetResponseTime
            Dimensions:
              - Name: LoadBalancer
                Value: !GetAtt OrdersAlb.LoadBalancerFullName
          Period: 300
          Stat: p90
      - Id: band
        Expression: ANOMALY_DETECTION_BAND(latency, 2)   # 2 standard deviations
        ReturnData: true

Watch forNo Threshold property: ThresholdMetricId replaces it. The model needs some history before the band is useful, and a larger band width means fewer alarms.

Composite alarm

Use whenSeveral alarms fire together during one incident and on-call should get one notification, or only when symptoms combine.

composite-alarm.yaml 
OrdersUnhealthy:
  Type: AWS::CloudWatch::CompositeAlarm
  Properties:
    AlarmName: orders-unhealthy
    AlarmRule: >-
      ALARM("orders-alb-5xx-rate")
      AND (ALARM("orders-latency-anomaly") OR ALARM("orders-db-cpu"))
    AlarmActions:
      - !Ref OnCallTopic
    # optional: stay quiet while a deployment alarm is in ALARM
    ActionsSuppressor: orders-deployment-in-progress
    ActionsSuppressorWaitPeriod: 60
    ActionsSuppressorExtensionPeriod: 300

Watch forRemove the actions from the child alarms, or on-call still gets one page per child. Rules can use ALARM(), OK() and INSUFFICIENT_DATA() with AND, OR and NOT.

Metric filter on JSON logs

Use whenThe application logs JSON and you need a metric (and an alarm) for events such as failed payments.

payment-failures-filter.yaml 
PaymentFailuresFilter:
  Type: AWS::Logs::MetricFilter
  Properties:
    LogGroupName: /app/payments
    FilterPattern: '{ $.event = "payment" && $.result = "failed" }'
    MetricTransformations:
      - MetricNamespace: Payments/App
        MetricName: PaymentFailures
        MetricValue: "1"   # count each match
        Dimensions:
          - Key: Provider   # one metric per provider
            Value: $.provider

Watch forMetric filters only see events that arrive after the filter is created. A filter with dimensions can't also set DefaultValue, so the metric has gaps when nothing matches; set TreatMissingData: notBreaching on its alarm.

Metric filter on space-delimited logs

Use whenLogs are plain text with fields separated by spaces, such as web server access logs.

access-log-5xx-filter.yaml 
# matches: 203.0.113.9 - alice [29/Oct/2026:10:00:00] "GET /cart" 503 120
Server5xxFilter:
  Type: AWS::Logs::MetricFilter
  Properties:
    LogGroupName: /web/access
    FilterPattern: '[ip, ident, user, timestamp, request, status_code = 5*, bytes]'
    MetricTransformations:
      - MetricNamespace: Web/Access
        MetricName: Server5xx
        MetricValue: "1"
        DefaultValue: 0   # report 0 when nothing matches

Watch forFields in square brackets are named by position; text in brackets or quotes counts as one field. Use ... to skip fields you don't name, for example [..., status_code = 5*, bytes].

Embedded metric format

Use whenA Lambda function or container should publish custom metrics by writing a log line, without PutMetricData calls.

one log line (pretty-printed) 
{
  "_aws": {
    "Timestamp": 1761732000000,
    "CloudWatchMetrics": [
      {
        "Namespace": "Orders/App",
        "Dimensions": [["Service"]],
        "Metrics": [
          { "Name": "CheckoutLatency", "Unit": "Milliseconds" }
        ]
      }
    ]
  },
  "Service": "checkout",   // dimension value
  "CheckoutLatency": 182,   // metric value
  "orderId": "o-1234"   // extra field: searchable in Logs Insights, not a metric
}

Watch forCloudWatch extracts the metric asynchronously from the log, so there's no API throttling in the request path, and the full event stays queryable. Keep high-cardinality values (order IDs) out of Dimensions.

Alarm actions

Use whenAn alarm should do more than notify: recover an instance, scale, or open an OpsItem or incident.

alarm-actions.yaml 
AlarmActions:
  # notify
  - !Ref OnCallTopic
  # EC2 action: recover | reboot | stop | terminate (needs an InstanceId dimension)
  - !Sub arn:aws:automate:${AWS::Region}:ec2:recover
  # Auto Scaling: a step or simple scaling policy
  - !Ref ScaleOutPolicy
  # Systems Manager OpsCenter: OpsItem with severity 2 and a category
  - !Sub arn:aws:ssm:${AWS::Region}:${AWS::AccountId}:opsitem:2#CATEGORY=Availability
  # Systems Manager Incident Manager: start an incident from a response plan
  - !Sub arn:aws:ssm-incidents::${AWS::AccountId}:responseplan/orders-outage
  # Lambda: invoke a function directly
  - !GetAtt AutoRemediateFunction.Arn
OKActions:
  - !Ref OnCallTopic   # tell on-call when it recovers

Watch forThe recover action goes on an alarm for StatusCheckFailed_System with an InstanceId dimension; it moves the instance to new hardware and keeps its ID, IP addresses and EBS volumes. A Lambda target needs a resource policy allowing lambda.alarms.cloudwatch.amazonaws.com.

CloudWatch agent: memory and disk

Use whenYou need memory or disk usage from EC2, which basic EC2 metrics don't include.

amazon-cloudwatch-agent.json 
{
  "metrics": {
    "namespace": "CWAgent",
    "append_dimensions": {
      "AutoScalingGroupName": "${aws:AutoScalingGroupName}",
      "InstanceId": "${aws:InstanceId}"
    },
    "metrics_collected": {
      "mem": {
        "measurement": ["mem_used_percent"]
      },
      "disk": {
        "measurement": ["used_percent"],
        "resources": ["/"]
      }
    }
  },
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "file_path": "/var/log/app/app.log",
            "log_group_name": "/app/orders",
            "log_stream_name": "{instance_id}"
          }
        ]
      }
    }
  }
}

Watch forStore the file in Parameter Store and push it to every instance with Systems Manager (the AmazonCloudWatch-ManageAgent document or State Manager). The instance role needs CloudWatchAgentServerPolicy.
