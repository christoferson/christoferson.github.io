Permissions boundary delegation

Letting developers create IAM roles for their own workloads without letting them create a role more powerful than allowed. Each snippet shows when to use it, the code with comments, and the detail that usually decides the exam answer.

A permissions boundary is a managed policy set on a user or role as the maximum it may ever do. The effective permissions are the intersection of the identity's own policies and the boundary (and any SCPs); the boundary itself grants nothing. Delegation works in four parts: security writes the boundary, developers may create roles only if they attach it, nobody but security can remove or edit it, and developers may pass only those roles to services. The examples use account 222222222222, a boundary named AppBoundary, and application roles named app-*.

The boundary policy

Use whenDefining the most any developer-created application role may do.

AppBoundary (customer managed policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AppData",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:Query"
      ],
      "Resource": "arn:aws:dynamodb:*:222222222222:table/app-*"
    },
    {
      "Sid": "AppObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::app-*/*"
    },
    {
      "Sid": "Logs",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "*"
    }
  ]
}

Watch forA role whose own policy allows s3:* on every bucket still gets only GetObject and PutObject on app-* buckets. A role with this boundary but no identity policy can do nothing.

Create roles only with the boundary

Use whenDevelopers create execution roles for their own Lambda functions and containers.

DeveloperPolicy (part 1) 
{
  "Sid": "CreateAndEditAppRolesWithBoundary",
  "Effect": "Allow",
  "Action": [
    "iam:CreateRole",
    "iam:PutRolePolicy",
    "iam:AttachRolePolicy",
    "iam:DetachRolePolicy",
    "iam:DeleteRolePolicy",
    "iam:PutRolePermissionsBoundary"
  ],
  "Resource": "arn:aws:iam::222222222222:role/app-*",
  "Condition": {
    "StringEquals": {   // the request must attach exactly this boundary
      "iam:PermissionsBoundary": "arn:aws:iam::222222222222:policy/AppBoundary"
    }
  }
}

Watch forThe iam:PermissionsBoundary condition is what makes CreateRole fail unless the boundary is attached. The app-* resource keeps developers away from security and admin roles.

Protect the boundary from changes

Use whenMaking sure developers can't remove the boundary from a role or rewrite the boundary policy itself.

DeveloperPolicy (part 2) 
{
  "Sid": "NoRemovingBoundaries",
  "Effect": "Deny",
  "Action": "iam:DeleteRolePermissionsBoundary",
  "Resource": "*"
},
{
  "Sid": "NoSwappingBoundaries",
  "Effect": "Deny",
  "Action": "iam:PutRolePermissionsBoundary",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {   // allowed only when it sets AppBoundary again
      "iam:PermissionsBoundary": "arn:aws:iam::222222222222:policy/AppBoundary"
    }
  }
},
{
  "Sid": "NoEditingTheBoundaryPolicy",
  "Effect": "Deny",
  "Action": [
    "iam:CreatePolicyVersion",
    "iam:DeletePolicy",
    "iam:DeletePolicyVersion",
    "iam:SetDefaultPolicyVersion"
  ],
  "Resource": "arn:aws:iam::222222222222:policy/AppBoundary"
}

Watch forAlso deny changes to the developers' own role and policy (for example, iam:PutRolePolicy on role/Developer*), or they could simply grant themselves more.

Pass only application roles

Use whenDevelopers attach the roles they created to Lambda functions or ECS tasks.

DeveloperPolicy (part 3) 
{
  "Sid": "PassAppRolesToComputeOnly",
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::222222222222:role/app-*",
  "Condition": {
    "StringEquals": {
      "iam:PassedToService": [
        "lambda.amazonaws.com",
        "ecs-tasks.amazonaws.com"
      ]
    }
  }
}

Watch forWithout a PassRole limit, a developer could hand an existing admin role to a Lambda function and act through it, bypassing the boundary entirely.

A role with a boundary in CloudFormation

Use whenDevelopers deploy their application roles through templates.

app-role.yaml 
OrdersFunctionRole:
  Type: AWS::IAM::Role
  Properties:
    RoleName: app-orders-function   # matches role/app-*
    PermissionsBoundary: !Sub arn:aws:iam::${AWS::AccountId}:policy/AppBoundary
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:
            Service: lambda.amazonaws.com
          Action: sts:AssumeRole
    Policies:
      - PolicyName: orders-table
        PolicyDocument:
          Version: "2012-10-17"
          Statement:
            - Effect: Allow
              Action: [ dynamodb:GetItem, dynamodb:PutItem ]
              Resource: !GetAtt OrdersTable.Arn

Watch forIf the stack runs with the developer's credentials (or a CloudFormation service role with the same restrictions), leaving out PermissionsBoundary or using another name makes CreateRole fail with access denied.

A boundary on every role in a CDK app

Use whenTeams deploy with the CDK and must not be able to forget the boundary on any role, including roles that L2 and L3 constructs create for them.

bin/app.ts 
import * as iam from "aws-cdk-lib/aws-iam";

const boundary = iam.ManagedPolicy.fromManagedPolicyName(
  stack, "Boundary", "AppBoundary");

// every role and user in the stack gets the boundary
iam.PermissionsBoundary.of(stack).apply(boundary);
# bootstrap the account so CDK deployments use a named boundary
cdk bootstrap aws://222222222222/us-east-1 \
  --custom-permissions-boundary AppBoundary

Watch forPermissionsBoundary.of(scope).apply() reaches roles created inside constructs too; when boundaries are applied at several scopes, the one closest to the role wins. --example-permissions-boundary deploys an AWS-supplied example boundary instead; the two options can't be combined.

A boundary in an Identity Center permission set

Use whenPeople who sign in through IAM Identity Center get broad permissions but must stay inside a company-wide limit.

permission-set.yaml 
PowerUserBounded:
  Type: AWS::SSO::PermissionSet
  Properties:
    InstanceArn: arn:aws:sso:::instance/ssoins-1234567890abcdef
    Name: PowerUserBounded
    SessionDuration: PT8H
    ManagedPolicies:
      - arn:aws:iam::aws:policy/PowerUserAccess
    PermissionsBoundary:
      CustomerManagedPolicyReference:   # by name, resolved per account
        Name: AppBoundary
        Path: /

Watch forA customer managed policy is referenced by name and path, so a policy with that name must exist in every account the permission set is assigned to; deploy it with a StackSet first. Use ManagedPolicyArn instead to use an AWS managed policy as the boundary.
