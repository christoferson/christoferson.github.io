CodePipeline actions

The pipeline pieces exam scenarios are built from: Git triggers, approvals, cross-account and cross-Region deploys, variables, ECS deploys, Lambda actions and automatic rollback. Each snippet shows when to use it, the code with comments, and the detail that usually decides the exam answer.

Fragments of an AWS::CodePipeline::Pipeline resource in CloudFormation. Every action has an ActionTypeId (category, owner, provider, version) and a provider-specific Configuration; actions in a stage with the same RunOrder run in parallel.

Git source with trigger filters

Use whenA V2 pipeline should start only for pushes to main that touch the service's folder, or for pull requests.

PipelineType: V2
Triggers:
  - ProviderType: CodeStarSourceConnection
    GitConfiguration:
      SourceActionName: Source            # must match the action name below
      Push:
        - Branches:
            Includes: [ main ]
          FilePaths:
            Includes: [ "services/orders/**" ]
      PullRequest:
        - Events: [ OPEN, UPDATED ]
          Branches:
            Includes: [ main ]
Stages:
  - Name: Source
    Actions:
      - Name: Source
        ActionTypeId:
          Category: Source
          Owner: AWS
          Provider: CodeStarSourceConnection   # CodeConnections
          Version: "1"
        Configuration:
          ConnectionArn: !Ref GitHubConnection
          FullRepositoryId: acme/orders
          BranchName: main
          OutputArtifactFormat: CODE_ZIP        # or CODEBUILD_CLONE_REF
        OutputArtifacts:
          - Name: SourceOutput

Watch forA new connection stays PENDING until someone authorizes it once in the console. CODEBUILD_CLONE_REF passes a Git clone reference instead of a zip, so CodeBuild can run Git commands (history, tags); CodeBuild's role then needs codeconnections:UseConnection. Trigger filters are V2 only.

Manual approval

Use whenA person must sign off before production (continuous delivery).

- Name: ApproveRelease
  ActionTypeId:
    Category: Approval
    Owner: AWS
    Provider: Manual
    Version: "1"
  Configuration:
    NotificationArn: !Ref ReleaseApproversTopic    # SNS topic for approvers
    CustomData: "Check the staging test report before approving."
    ExternalEntityLink: https://staging.example.com
  RunOrder: 1

Watch forAn approval waits up to 7 days, then fails. Approvers need codepipeline:PutApprovalResult on the pipeline. "Changes must be reviewed before production" means an approval action; "no manual intervention" means alarms and automated tests instead.

Cross-account CloudFormation deploy

Use whenA pipeline in the tooling account 111111111111 deploys a stack into production 222222222222.

- Name: DeployProd
  ActionTypeId:
    Category: Deploy
    Owner: AWS
    Provider: CloudFormation
    Version: "1"
  # 1. CodePipeline assumes this role in production to run the action
  RoleArn: arn:aws:iam::222222222222:role/CrossAccountDeployRole
  Configuration:
    ActionMode: CREATE_UPDATE                # or CHANGE_SET_REPLACE + CHANGE_SET_EXECUTE
    StackName: orders-prod
    TemplatePath: BuildOutput::template.yaml  # ArtifactName::path
    Capabilities: CAPABILITY_IAM,CAPABILITY_AUTO_EXPAND
    # 2. CloudFormation uses this role to create the resources
    RoleArn: arn:aws:iam::222222222222:role/CfnExecutionRole
    ParameterOverrides: '{"Environment": "prod"}'
  InputArtifacts:
    - Name: BuildOutput

Watch forTwo different roles: the action-level RoleArn (assumed by CodePipeline) and Configuration.RoleArn (passed to CloudFormation). The artifact bucket must use a customer managed KMS key whose key policy, plus the bucket policy, allow the production deploy role.

Cross-Region action

Use whenOne pipeline in us-east-1 also deploys to eu-west-1.

ArtifactStores:                               # replaces ArtifactStore
  - Region: us-east-1
    ArtifactStore:
      Type: S3
      Location: artifacts-111111111111-us-east-1
      EncryptionKey:
        Id: !GetAtt ArtifactKeyUsEast1.Arn
        Type: KMS
  - Region: eu-west-1
    ArtifactStore:
      Type: S3
      Location: artifacts-111111111111-eu-west-1
      EncryptionKey:
        Id: arn:aws:kms:eu-west-1:111111111111:alias/artifacts
        Type: KMS
...
      - Name: DeployEu
        Region: eu-west-1                       # run this action in eu-west-1
        ActionTypeId:
          Category: Deploy
          Owner: AWS
          Provider: CloudFormation
          Version: "1"

Watch forEach Region with an action needs its own artifact bucket (and KMS key) in that Region; CodePipeline copies artifacts there. You can't specify both ArtifactStore and ArtifactStores.

Passing values with variables

Use whenA later action needs a value produced earlier, such as the commit ID or a stack output, or a value supplied when the pipeline starts.

Variables:                                    # pipeline-level variables (V2)
  - Name: DeployEnv
    DefaultValue: staging
Stages:
  - Name: Source
    Actions:
      - Name: Source
        Namespace: SourceVariables           # exposes CommitId, BranchName...
        ...
  - Name: Build
    Actions:
      - Name: Build
        Namespace: BuildVariables            # exported-variables from the buildspec
        Configuration:
          ProjectName: orders-build
          EnvironmentVariables: '[{"name":"COMMIT","value":"#{SourceVariables.CommitId}","type":"PLAINTEXT"},{"name":"ENV","value":"#{variables.DeployEnv}","type":"PLAINTEXT"}]'
  - Name: Approve
    Actions:
      - Name: Approve
        Configuration:
          CustomData: "Deploy image #{BuildVariables.IMAGE_TAG}?"

Watch forAction variables use #{Namespace.Name} and require the producing action to have a Namespace. Pipeline-level variables use #{variables.Name} and can be overridden at start. A CloudFormation action's stack outputs become variables in its namespace.

Deploying to ECS: rolling or blue/green

Use whenChoosing between the ECS standard deploy action and CodeDeploy blue/green.

# Rolling update by the ECS service; reads imagedefinitions.json
- Name: DeployStaging
  ActionTypeId:
    Category: Deploy
    Owner: AWS
    Provider: ECS
    Version: "1"
  Configuration:
    ClusterName: staging
    ServiceName: orders
    FileName: imagedefinitions.json
  InputArtifacts:
    - Name: BuildOutput

# Blue/green through CodeDeploy; needs taskdef.json, appspec.yaml, imageDetail.json
- Name: DeployProd
  ActionTypeId:
    Category: Deploy
    Owner: AWS
    Provider: CodeDeployToECS
    Version: "1"
  Configuration:
    ApplicationName: orders
    DeploymentGroupName: orders-prod
    TaskDefinitionTemplateArtifact: BuildOutput
    TaskDefinitionTemplatePath: taskdef.json
    AppSpecTemplateArtifact: BuildOutput
    AppSpecTemplatePath: appspec.yaml
    Image1ArtifactName: BuildOutput          # contains imageDetail.json
    Image1ContainerName: IMAGE1_NAME         # placeholder in taskdef.json
  InputArtifacts:
    - Name: BuildOutput

Watch forimagedefinitions.json is for the ECS provider; imageDetail.json is for CodeDeployToECS. Canary or linear traffic shifting and test listeners need the CodeDeploy route (or ECS built-in blue/green on the service itself).

Lambda invoke action

Use whenA custom step, such as a smoke test or a ticket update, needs to run inside the pipeline.

- Name: SmokeTest
  ActionTypeId:
    Category: Invoke
    Owner: AWS
    Provider: Lambda
    Version: "1"
  Configuration:
    FunctionName: orders-smoke-test
    UserParameters: https://staging.example.com/health
smoke_test.py 
import boto3, urllib.request
cp = boto3.client("codepipeline")

def handler(event, context):
    job = event["CodePipeline.job"]
    url = job["data"]["actionConfiguration"]["configuration"]["UserParameters"]
    try:
        urllib.request.urlopen(url, timeout=10)
        cp.put_job_success_result(jobId=job["id"])
    except Exception as e:
        cp.put_job_failure_result(
            jobId=job["id"],
            failureDetails={"type": "JobFailed", "message": str(e)[:500]},
        )

Watch forThe function must call PutJobSuccessResult or PutJobFailureResult; otherwise the action keeps running until it times out. Its role needs those two permissions. It can also return output variables for later actions.

Stage conditions and automatic rollback

Use whenProduction must not be deployed while an alarm is firing, and a failed deployment should roll back to the last successful version.

- Name: Production
  BeforeEntry:                                 # entry condition: FAIL or SKIP
    Conditions:
      - Result: FAIL
        Rules:
          - Name: ProdHealthy
            RuleTypeId:
              Category: Rule
              Owner: AWS
              Provider: CloudWatchAlarm
              Version: "1"
            Configuration:
              AlarmName: orders-prod-5xx
              WaitTime: "10"                     # minutes to wait for OK
  OnFailure:
    Result: ROLLBACK                           # redeploy the last successful run
  Actions:
    - ...

Watch forEntry conditions can fail or skip the stage; success conditions can fail or roll back; failure conditions roll back. Rollback only targets a previous execution started with the current pipeline structure. Conditions and stage rollback are V2 features.
