Overview

Task statement 1.2

Integrate automated testing into CI/CD pipelines.

A pipeline is only as safe as the tests inside it. This task tests whether you can choose the right kind of test for a requirement, place it at the right stage, and wire it in so that a failure actually stops the pipeline. Typical scenarios: "every pull request must be built and tested before merge", "the release must handle 10,000 requests per second", or "a validation function runs but the pipeline never moves on".

Exam guide itemWhat you need to be able to do
Knowledge: types of testsTell unit, integration, acceptance, UI and security tests apart, and know what each catches
Knowledge: tests at different stagesPut fast, cheap tests early and slow, expensive tests later
Skill: builds on pull requests and mergesTrigger CodeBuild on pull request events and report the result back
Skill: load tests and testing at scaleGenerate realistic load, measure performance and fail on regressions
Skill: health from exit codesMake sure every test step reports success or failure correctly

Skill: invoking AWS services for testingUse Lambda, Step Functions, CloudFormation and other services as test actions

Different types of tests

Knowledge

Each test type answers a different question. The exam often describes a problem that slipped through ("the API returned the wrong format to the mobile app") and asks which test would have caught it.

Test typeWhat it checksSpeedTypical tools on AWS
UnitOne function or class in isolation, with dependencies mockedSecondsJUnit, pytest, Jest run in CodeBuild
IntegrationComponents working together: the app with a real database, queue or APIMinutesCodeBuild against a test environment; LocalStack or containers for local dependencies
Acceptance (end-to-end)The system meets business requirements from the user's point of viewMinutesCodeBuild running Cucumber or API test suites against a deployed stage
User interfaceScreens and user flows in real browsers or devicesMinutesSelenium or Playwright in CodeBuild, AWS Device Farm, CloudWatch Synthetics canaries
SmokeA few critical paths work right after a deploymentSecondsCodeDeploy hooks, Lambda invoke actions, Synthetics canaries
Load and performanceLatency and throughput under expected and peak trafficTens of minutesDistributed Load Testing on AWS, JMeter, k6, Locust
Resilience (chaos)The system recovers when parts failTens of minutesAWS Fault Injection Service formerly Fault Injection Simulator

Security scans

Security scans are tests too. Each kind looks at a different layer:

ScanWhat it looks atExamples
Static analysis (SAST)Source code, for injection flaws, hard-coded credentials and unsafe patternsAmazon CodeGuru Reviewer, Amazon Q Developer code reviews, SonarQube
Dependency scanningOpen source libraries with known vulnerabilities (CVEs)Amazon Inspector, OWASP Dependency-Check
Container image scanningOS packages and libraries inside an imageAmazon ECR scanning (basic, or enhanced with Inspector)
Infrastructure as code scanningTemplates that would create insecure resources (public buckets, open security groups)cfn-lint, CloudFormation Guard, cfn-nag, Checkov
Secrets scanningCredentials committed to the repositorygit-secrets, Amazon CodeGuru Reviewer secrets detection
Dynamic analysis (DAST)A running application, probed from the outside like an attackerOWASP ZAP in CodeBuild against a test stage

"Find vulnerable libraries before the image is deployed" points to image or dependency scanning in the build stage. "Block templates that create public S3 buckets" points to IaC scanning (for example, CloudFormation Guard rules) before the deploy stage. AWS Config rules catch the same problem only after deployment.

Reasonable use of tests at different stages of the pipeline

Knowledge

The rule of thumb is fail fast and cheap. Run quick tests that need no infrastructure first, so most bad changes are rejected within minutes. Run slow tests that need a deployed environment later, on fewer changes. This is the test pyramid: many unit tests, fewer integration tests, and a small number of end-to-end and UI tests.

A typical layout, from the earliest stage to the last:

  1. Before merge
  2. Pull request validationBuild, lint, unit tests, static analysis and secrets scanning on every pull request. Results are posted back to the pull request, and merge is blocked until they pass.
  3. Build stage
  4. Unit tests and code coverageRun again on the merged code. Fail if coverage drops below the agreed threshold.
  5. Package and scanBuild the image or artifact, then scan dependencies, the image and the IaC templates.
  6. Test stage (deployed test environment)
  7. Integration and API testsDeploy to a test environment, then test against real AWS services such as DynamoDB, SQS or an RDS database.
  8. Acceptance and UI testsRun user journeys end to end, in browsers or on devices.
  9. Staging stage (production-like)
  10. Load, performance and resilience testsRun at production scale in an environment that mirrors production. Add DAST and fault injection experiments here.
  11. Manual approval (optional)Only if the scenario requires a human sign-off before production.
  12. Production stage
  13. Gradual rollout with alarmsCanary or linear deployment, with CloudWatch alarms that roll back automatically.
  14. Post-deployment smoke tests and monitoringCodeDeploy validation hooks run quick checks, and Synthetics canaries keep testing critical paths around the clock.

Running full load tests or long UI suites on every pull request slows feedback and costs money. Running only unit tests and then deploying straight to production misses integration problems. The exam expects the layered approach above.

Run load and chaos tests in a separate staging account. Generated traffic then can't exhaust production service quotas or trigger production alarms.

Running builds or tests on pull requests and code merges

Skill

GitHub, GitLab and Bitbucket: CodeBuild webhooks

A CodeBuild project with a webhook starts a build when the Git provider sends an event. Filter groups decide which events count. Inside a group, every filter must match (AND); across groups, any group can match (OR).

codebuild-pr-project.yml 
PullRequestBuild:
  Type: AWS::CodeBuild::Project
  Properties:
    Name: orders-pr-validation
    ServiceRole: !GetAtt CodeBuildRole.Arn
    Source:
      Type: GITHUB
      Location: https://github.com/example/orders.git
      ReportBuildStatus: true                      # green tick or red cross on the pull request
      BuildSpec: buildspec-pr.yml
    Triggers:
      Webhook: true
      FilterGroups:
        - - { Type: EVENT, Pattern: "PULL_REQUEST_CREATED,PULL_REQUEST_UPDATED,PULL_REQUEST_REOPENED" }
          - { Type: BASE_REF, Pattern: "^refs/heads/main$" }   # only pull requests into main
    Environment:
      Type: LINUX_CONTAINER
      ComputeType: BUILD_GENERAL1_SMALL
      Image: aws/codebuild/standard:7.0
    Artifacts: { Type: NO_ARTIFACTS }
  • Other filter types: HEAD_REF (source branch), FILE_PATH (changed files), ACTOR_ACCOUNT_ID (who triggered it), and COMMIT_MESSAGE (for example, skip builds on [skip ci]).
  • Branch protection: in the Git provider, require the CodeBuild status check to pass before merge. This is what actually blocks a bad merge.
  • Pipeline alternative: a CodePipeline V2 pipeline can trigger on pull request events directly. Use Parallel execution mode so pull requests don't queue behind each other.
  • After merge: the merge is a push to main, which starts the main delivery pipeline. That's where the full test sequence runs.
Skill

CodeCommit: EventBridge rule, CodeBuild and a Lambda function

CodeCommit doesn't use webhooks. Pull request events go to EventBridge instead, and you connect the pieces yourself:

  1. A developer opens or updates a pull requestCodeCommit emits a CodeCommit Pull Request State Change event.
  2. An EventBridge rule matches the eventIt filters on pullRequestCreated and pullRequestSourceBranchUpdated.
  3. The rule starts a CodeBuild buildIt passes the source commit as the source version, so the build tests the pull request's code.
  4. A second rule reacts to the build resultA Lambda function posts a comment on the pull request and can approve it (approval rule templates can require that approval).
eventbridge-rule.yml 
PullRequestRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [aws.codecommit]
      detail-type: [CodeCommit Pull Request State Change]
      resources: [arn:aws:codecommit:us-east-1:111111111111:orders]
      detail:
        event: [pullRequestCreated, pullRequestSourceBranchUpdated]
    Targets:
      - Id: start-pr-build
        Arn: !GetAtt PullRequestBuild.Arn             # the CodeBuild project
        RoleArn: !GetAtt EventsInvokeCodeBuildRole.Arn  # allows codebuild:StartBuild
        InputTransformer:
          InputPathsMap:
            commit: "$.detail.sourceCommit"
          InputTemplate: '{"sourceVersion": "<commit>"}'

"Automatically run tests on every CodeCommit pull request and show the result on the pull request" is answered by EventBridge + CodeBuild + Lambda (to comment or approve). It isn't a CodePipeline source action, which watches a single branch.

Running load and stress tests, performance benchmarks and application tests at scale

Skill

Kinds of performance test

  • Load test: expected peak traffic. Does the app meet its latency and error targets?
  • Stress test: traffic beyond the peak, to find the breaking point and see how the app fails.
  • Soak (endurance) test: steady load for hours, to find memory leaks and slow resource exhaustion.
  • Spike test: a sudden jump in traffic. Does auto scaling react fast enough?
  • Performance benchmark: the same test on every release, compared with a baseline to catch regressions.

Generating load at scale

One build container can't generate much traffic. To test at scale, run many load generators in parallel:

OptionHow it worksWhen to choose it
Distributed Load Testing on AWSAn AWS Solutions template that runs load test containers (JMeter and similar tools) as Fargate tasks across Regions, with a results dashboard and an APILarge tests with little setup. The pipeline starts a test through its API
CodeBuild batch buildsA build fan-out or build list runs many copies of the same load script in parallelModerate load from inside the pipeline
ECS tasks orchestrated by Step FunctionsStep Functions starts N Fargate tasks, waits for them, then collects resultsCustom, repeatable tests with your own tools
AWS Device FarmRuns UI tests on many real mobile devices and desktop browsers in parallelTesting a mobile or web app at scale across devices

Turning results into a pass or fail

A load test is useful in a pipeline only if it can fail the stage. Define thresholds in the test tool and exit non-zero when they're broken.

k6 load test (load-test.js) 
export const options = {
  stages: [
    { duration: "2m", target: 500 },     // ramp up to 500 virtual users
    { duration: "10m", target: 500 },    // hold the load
    { duration: "1m", target: 0 },
  ],
  thresholds: {
    http_req_duration: ["p(99)<800"],  // 99% of requests under 800 ms
    http_req_failed: ["rate<0.01"],     // under 1% errors, otherwise k6 exits non-zero
  },
};
  • Watch the system too: during the test, use CloudWatch metrics and dashboards (CPU, latency, throttling, queue depth) and X-Ray traces to find the bottleneck.
  • Find slow code: Amazon CodeGuru Profiler shows the most expensive code paths for benchmarking and optimization.

Resilience tests with AWS Fault Injection Service

FIS runs experiments that inject failures: stop or terminate EC2 instances, stop ECS tasks, add CPU or memory stress, add network latency, throttle API calls or fail over an Aurora cluster. Each experiment template has stop conditions: CloudWatch alarms that end the experiment automatically if the impact gets too big.

"Verify that the application keeps serving traffic when an Availability Zone's instances fail, and stop the test if errors exceed a limit" points to an FIS experiment with a CloudWatch alarm stop condition, started from the pipeline (for example, by a Step Functions or Lambda action).

Measuring application health based on application exit codes

Skill

Almost every AWS test integration decides pass or fail from an exit code or an explicit result call. Exit code 0 means success; anything else means failure. If a test step hides its failure, the pipeline happily promotes broken code.

WhereHow success or failure is decided
CodeBuildAny command that exits non-zero fails its phase, and the build fails
CodeDeploy hook scripts (EC2)A non-zero exit from a hook script, such as ValidateService, fails the deployment and can trigger rollback
CodeDeploy hooks (Lambda, ECS)The hook function calls PutLifecycleEventHookExecutionStatus with Succeeded or Failed
CodePipeline Lambda invoke actionThe function calls PutJobSuccessResult or PutJobFailureResult
ECS container health checkThe health check command exits 0 (healthy) or non-zero (unhealthy); unhealthy tasks are replaced
ECS task in a Step Functions testA container exit code other than 0 marks the task, and the step, as failed
Load balancer health checkHTTP status codes; by default 200 counts as healthy for an ALB target group

Exit codes that get lost

The usual failure: a test step fails, but the exit code is swallowed and the step "passes".

buildspec.yml 
version: 0.2
env:
  shell: bash
phases:
  build:
    commands:
      # Wrong: tee always exits 0, so a failing test run is hidden
      # - npm test | tee test-output.log

      # Wrong: "|| true" turns every failure into success
      # - ./run-integration-tests.sh || true

      # Right: pipefail returns the first failing command's exit code
      - |
        set -eo pipefail
        npm test | tee test-output.log
        ./run-integration-tests.sh
  • Multi-line scripts: use set -e so the script stops at the first failing command, and set -o pipefail so a pipe returns a failure from any stage.
  • Background processes: a command started with & doesn't report its exit code. Use wait on its process ID and check the result.
  • Wrapper scripts: make sure they end with exit $? or the test tool's own exit code, not a final echo.

"Tests fail in the logs but the build shows Succeeded" is almost always a swallowed exit code: a pipe without pipefail, || true, or a script that doesn't return the test result.

Automating unit tests and code coverage

Skill

CodeBuild reports turn test and coverage files into results you can browse in the console. They show pass and fail counts, duration and trends across builds.

Report typeSupported formats
Test reportsJUnit XML, NUnit XML, NUnit3 XML, TestNG XML, Visual Studio TRX, Cucumber JSON
Code coverage reportsJaCoCo XML, Clover XML, Cobertura XML, SimpleCov JSON, LCOV
buildspec.yml 
version: 0.2
phases:
  install:
    runtime-versions:
      java: corretto21
  build:
    commands:
      # jacoco:check fails the build (non-zero exit) if coverage is below the threshold in pom.xml
      - mvn -B verify jacoco:report jacoco:check
reports:
  unit-tests:                                # report group name
    files: ["**/*.xml"]
    base-directory: target/surefire-reports
    file-format: JUNITXML
  coverage:
    files: ["target/site/jacoco/jacoco.xml"]
    file-format: JACOCOXML
  • Report groups: each name under reports is a report group. CodeBuild creates it on first use if the build role has codebuild:CreateReportGroup, CreateReport, UpdateReport, BatchPutTestCases and BatchPutCodeCoverages.
  • Retention: report results are kept for 30 days. To keep them longer, export the raw files to S3 from the report group.
  • Failing on failed tests: the test runner's exit code fails the build. The report only displays the results.

CodeBuild doesn't enforce a coverage threshold on its own. A coverage report showing 40% doesn't fail anything. Enforce the threshold in the build tool (for example, jacoco:check, Jest coverageThreshold or pytest --cov-fail-under=80) so the build exits non-zero.

Skill

Lambda invoke action

CodePipeline invokes the function with a job. The function must report the result back. Returning normally isn't enough.

pipeline stage 
- Name: Test
  Actions:
    - Name: SmokeTest
      ActionTypeId: { Category: Invoke, Owner: AWS, Provider: Lambda, Version: "1" }
      Configuration:
        FunctionName: orders-smoke-test
        UserParameters: "https://test.orders.example.com/health"   # passed to the function
smoke_test.py 
import urllib.request
import boto3

codepipeline = boto3.client("codepipeline")

def handler(event, context):
    job = event["CodePipeline.job"]
    url = job["data"]["actionConfiguration"]["configuration"]["UserParameters"]
    try:
        with urllib.request.urlopen(url, timeout=10) as response:
            if response.status != 200:
                raise Exception(f"Health check returned {response.status}")
        codepipeline.put_job_success_result(jobId=job["id"])          # action succeeds
    except Exception as error:
        codepipeline.put_job_failure_result(                          # action fails, stage stops
            jobId=job["id"],
            failureDetails={"type": "JobFailed", "message": str(error)},
        )
  • Permissions: the function's execution role needs codepipeline:PutJobSuccessResult and codepipeline:PutJobFailureResult.
  • Long-running checks: a Lambda invocation lasts at most 15 minutes. For longer checks, report a continuation token to be invoked again, or use a Step Functions action instead.

"The Lambda test action runs successfully, but the pipeline stays In progress until it times out" means the function never called PutJobSuccessResult, or its role lacks permission to.

Skill

Ephemeral test environments with CloudFormation

Integration tests need real resources. Create a fresh stack for the test run, test against it, then delete it. Every run then starts clean, and you pay only while tests run.

pipeline stage 
- Name: IntegrationTest
  Actions:
    - Name: CreateTestStack
      RunOrder: 1
      Namespace: TestStackVars                      # stack outputs become #{TestStackVars.<OutputName>}
      ActionTypeId: { Category: Deploy, Owner: AWS, Provider: CloudFormation, Version: "1" }
      InputArtifacts: [{ Name: BuildOutput }]
      Configuration:
        ActionMode: CREATE_UPDATE
        StackName: orders-test
        TemplatePath: BuildOutput::template.yml
        RoleArn: arn:aws:iam::111111111111:role/CfnExecutionRole
    - Name: RunIntegrationTests
      RunOrder: 2                                    # runs after the stack exists
      ActionTypeId: { Category: Test, Owner: AWS, Provider: CodeBuild, Version: "1" }
      InputArtifacts: [{ Name: SourceOutput }]
      Configuration:
        ProjectName: orders-integration-tests
    - Name: DeleteTestStack
      RunOrder: 3
      ActionTypeId: { Category: Deploy, Owner: AWS, Provider: CloudFormation, Version: "1" }
      Configuration:
        ActionMode: DELETE_ONLY
        StackName: orders-test
        RoleArn: arn:aws:iam::111111111111:role/CfnExecutionRole
  • Finding the test environment: the test build needs the new stack's endpoint. Have the CloudFormation action write stack outputs to an output artifact (OutputFileName), or use its output variables (for example, #{TestStackVars.ApiUrl}) in the next action.
  • Change sets: CHANGE_SET_REPLACE followed by CHANGE_SET_EXECUTE lets you review or approve infrastructure changes before they're applied.

If the tests at RunOrder 2 fail, the stage stops and the delete action never runs, so the test stack stays behind. Plan for it: let the next run's CREATE_UPDATE reuse the stack, or clean up with a scheduled job or a Step Functions workflow that deletes the stack whatever the result.

Key takeaways

  • Fail fast and cheap: lint, unit tests and static scans first; integration and acceptance tests against a deployed test stage; load, DAST and chaos tests in production-like staging.
  • Scan in the pipeline before deployment: dependencies, container images (ECR or Inspector) and IaC templates (CloudFormation Guard, cfn-lint). AWS Config only catches problems after deployment.
  • Pull request builds: CodeBuild webhooks with filter groups for GitHub, GitLab and Bitbucket; EventBridge + CodeBuild + Lambda for CodeCommit.
  • Test at scale with Distributed Load Testing on AWS, CodeBuild batch builds or Fargate tasks, and fail the stage with thresholds such as p99 latency and error rate.
  • FIS experiments test resilience, with CloudWatch alarms as stop conditions.
  • Exit code 0 means pass. Watch for swallowed exit codes: pipes without pipefail, || true, wrapper scripts.
  • CodeBuild reports display test and coverage results but don't enforce a threshold. The build tool must exit non-zero below the threshold.
  • A Lambda invoke action must call PutJobSuccessResult or PutJobFailureResult, or the pipeline waits until it times out.
  • Ephemeral CloudFormation test stacks give clean environments, but plan for cleanup when tests fail.
