Overview

Task statement 6.3

Implement security monitoring and auditing solutions.

Auditing answers "who changed what, and when?". Monitoring answers "is something wrong right now?". The exam expects you to know which service records which evidence, how to keep that evidence trustworthy across an organization, and how to turn it into alerts. Typical scenarios: "prove the logs weren't altered", "alert when the root user signs in", "detect an EC2 instance talking to a crypto-mining pool", or "an access key was committed to a public repository".

Knowledge

AWS CloudTrail

Event typeExamplesLogged by default?
Management eventsCreateUser, RunInstances, PutBucketPolicy, console sign-insYes, in the 90-day event history. A trail is needed to keep them longer.
Data eventsS3 GetObject and PutObject, Lambda Invoke, DynamoDB item operationsNo. Enable per trail (extra cost); use advanced event selectors to limit them to specific buckets or tables.
Insights eventsAn unusual spike in API call rate or error rateNo. Enable on a trail.
Network activity eventsAPI calls passing through a VPC endpoint, including denied onesNo. Enable on a trail.
  • Organization trail: one trail created in the management account (or a delegated administrator) logs every account and Region, and member accounts can't change or delete it.
  • Log file integrity validation: CloudTrail delivers hourly signed digest files with a SHA-256 hash of each log file, so you can prove logs weren't modified or deleted.
  • Delivery: to S3 (with SSE-KMS), optionally CloudWatch Logs for metric filters and alarms, and EventBridge.
  • CloudTrail Lake closed to new customers since May 31, 2026: a managed event data store you query with SQL. Existing customers can keep using it; new setups query the S3 logs with Athena.

Event history covers management events only, for 90 days. "Who read this S3 object six months ago?" can only be answered if a trail was already recording S3 data events.

Knowledge

AWS Config

  • Configuration recorder: records a configuration item each time a resource changes (continuous) or once a day (daily recording, cheaper). The timeline links each change to the CloudTrail event that caused it.
  • Rules: managed rules, custom Lambda rules, or custom Guard rules. They evaluate when a resource changes and/or on a schedule.
  • Conformance packs: a set of rules and remediations deployed as one unit, across an organization.
  • Aggregator: collects configuration and compliance data from all accounts and Regions into one account, and supports advanced queries in SQL.
  • Remediation: automatic or manual, through Systems Manager Automation runbooks.

An advanced query across the aggregator, listing security groups that allow SSH from anywhere:

SELECT accountId, awsRegion, resourceId, resourceName
WHERE resourceType = 'AWS::EC2::SecurityGroup'
  AND configuration.ipPermissions.fromPort = 22
  AND configuration.ipPermissions.ipRanges = '0.0.0.0/0'
Knowledge

VPC Flow Logs

Flow logs capture metadata about IP traffic (not packet contents) for a VPC, a subnet or a single network interface, and deliver it to CloudWatch Logs, S3 or Data Firehose. You can record accepted, rejected or all traffic.

A record in the default format, field by field:

2 222222222222 eni-0a1b2c3d 203.0.113.12 10.0.1.25 49152 22 6 20 4000 1761700000 1761700060 REJECT OK
ValueField
2, 222222222222, eni-0a1b2c3dVersion, account, network interface
203.0.113.12 → 10.0.1.25Source and destination address
49152 → 22Source and destination port (SSH)
6Protocol (6 = TCP)
20, 4000Packets and bytes
Two timestampsStart and end of the capture window
REJECTBlocked by a security group or network ACL
  • Custom formats add fields such as vpc-id, subnet-id, pkt-srcaddr (the original source behind a NAT or load balancer) and flow-direction.
  • Not captured: traffic to the Amazon DNS server, instance metadata, Amazon Time Sync, DHCP, and the Windows license activation server.

A REJECT on inbound traffic plus an ACCEPT on the reply (or the reverse) points to a network ACL, which is stateless. Security groups are stateful, so they never reject a reply to allowed traffic.

Knowledge

CloudFormation drift detection

Drift detection compares each resource's current configuration with the properties in the stack's template. Each resource is reported as IN_SYNC, MODIFIED, DELETED or NOT_CHECKED, and the stack as DRIFTED or IN_SYNC.

aws cloudformation detect-stack-drift --stack-name orders-prod
aws cloudformation describe-stack-resource-drifts --stack-name orders-prod \
  --stack-resource-drift-status-filters MODIFIED DELETED
# shows expected vs actual values for each changed property
  • Scheduled checks: the AWS Config managed rule cloudformation-stack-drift-detection-check runs detection and marks drifted stacks noncompliant.
  • StackSets: drift detection runs across every stack instance in the set.
  • Fixing drift: revert the manual change, or update the template to match and redeploy. Prevent it with SCPs or IAM policies that limit console changes to break-glass roles.

Drift detection only checks properties set in the template (and only resource types that support it). A property left at its default and then changed by hand may not show as drift.

Amazon GuardDuty

GuardDuty analyzes CloudTrail management events, VPC Flow Logs and DNS query logs automatically. You don't need to turn those logs on yourself, and it doesn't affect your workloads. Optional protection plans add more sources:

Protection planDetects

EKS ProtectionSuspicious Kubernetes API activity in EKS audit logs

Malware ProtectionMalware on EBS volumes of flagged instances, and in newly uploaded S3 objects

  • Severity: low (1.0–3.9), medium (4.0–6.9), high (7.0–8.9), critical (9.0–10.0).
  • Extended Threat Detection: correlates related findings and events into a single attack sequence finding.
  • Tuning: trusted IP lists, threat IP lists, and suppression rules that auto-archive expected findings (for example, a known vulnerability scanner).
  • Organization: a delegated administrator auto-enables GuardDuty in all accounts. It's Regional, so enable it in every Region, including ones you don't use.

Amazon Inspector

  • EC2: scans for software vulnerabilities (CVEs) and network reachability, using the Systems Manager agent, or agentless scanning of EBS snapshots for instances without the agent.
  • ECR images: scans on push and continuously re-scans when new CVEs are published (enhanced scanning).
  • Lambda: scans function packages and layers, and optionally the code itself for issues such as hard-coded secrets.
  • Other features: an Inspector risk score that adjusts the CVE score for your environment, CIS benchmark assessments, SBOM export, and a CI/CD integration that scans images before they're pushed.

Amazon Inspector Classic superseded by the current Inspector used assessment templates and scheduled runs. The current Inspector scans continuously and is enabled across an organization with a delegated administrator.

IAM Access Analyzer

  • External access analyzer: with your account or organization as the zone of trust, it finds resources (S3 buckets, KMS keys, roles, Lambda functions, SQS queues, secrets, snapshots) that can be accessed from outside it.
  • Unused access analyzer: finds unused roles, access keys, passwords and permissions.
  • Archive rules: automatically archive expected findings, such as access granted to a known partner account.

"Identify any S3 bucket or KMS key shared with an account outside the organization" is IAM Access Analyzer with the organization as the zone of trust. "Detect that leaked credentials are being used" is GuardDuty.

Responding to an exposed access key

When AWS finds a key in a public repository, it sends the Health event and attaches a quarantine policy (AWSCompromisedKeyQuarantine) to the user to limit damage. You then:

  1. Deactivate the keyDon't delete it yet; you need its ID to search the logs.
  2. Review what it didSearch CloudTrail for the access key ID; look for new users, keys, roles, instances or changed policies.
  3. Clean upRemove anything the attacker created, rotate other credentials it could reach, then delete the key.
  4. Prevent recurrenceReplace the key with a role, and add secret scanning to the repository and pipeline.

This can be automated: an EventBridge rule on the Health event starts a Step Functions workflow or Systems Manager Automation runbook that deactivates the key and notifies the security team.

{
  "source": ["aws.health"],
  "detail-type": ["AWS Health Event"],
  "detail": { "eventTypeCode": ["AWS_RISK_CREDENTIALS_EXPOSED"] }
}

Implementing robust security auditing

Skill

"Robust" means the audit trail covers every account and Region, can't be switched off or altered by the people it records, and is kept as long as required. Assume this layout (the Control Tower default):

AccountIDRole
Management000000000000Owns the organization trail and SCPs
Log archive666666666666Holds the log bucket; almost nobody can sign in
Audit (security tooling)555555555555Delegated administrator for Config, GuardDuty, Security Hub; read access to logs
  1. Organization trailAll accounts, all Regions, management events plus selected data events, with log file validation on.
  2. Central, locked bucketLogs go to a bucket in 666666666666 with SSE-KMS, versioning, S3 Object Lock in compliance mode, and a bucket policy that only allows CloudTrail to write.
  3. Config everywhereConfig recording in every account and Region, with an aggregator in 555555555555.
  4. GuardrailsSCPs deny stopping or deleting CloudTrail, Config and GuardDuty, and deny changes to the log bucket.
  5. RetentionLifecycle rules move old logs to Glacier storage classes and expire them after the required period.
  6. VerifyRun integrity validation during audits and investigations.
org-trail.yaml (in 000000000000) 
OrgTrail:
  Type: AWS::CloudTrail::Trail
  Properties:
    TrailName: org-trail
    IsOrganizationTrail: true
    IsMultiRegionTrail: true
    IncludeGlobalServiceEvents: true          # IAM, STS, CloudFront
    EnableLogFileValidation: true             # signed digest files
    IsLogging: true
    S3BucketName: org-cloudtrail-666666666666
    KMSKeyId: arn:aws:kms:us-east-1:666666666666:key/1234abcd-12ab-34cd-56ef-1234567890ab
    CloudWatchLogsLogGroupArn: !GetAtt TrailLogGroup.Arn
    CloudWatchLogsRoleArn: !GetAtt TrailToLogsRole.Arn
    InsightSelectors:
      - { InsightType: ApiCallRateInsight }
      - { InsightType: ApiErrorRateInsight }
    AdvancedEventSelectors:
      - Name: Management events
        FieldSelectors:
          - { Field: eventCategory, Equals: [ Management ] }
      - Name: S3 data events for confidential buckets
        FieldSelectors:
          - { Field: eventCategory, Equals: [ Data ] }
          - { Field: resources.type, Equals: [ "AWS::S3::Object" ] }
          - { Field: resources.ARN, StartsWith: [ "arn:aws:s3:::confidential-" ] }

Proving the logs weren't changed:

aws cloudtrail validate-logs \
  --trail-arn arn:aws:cloudtrail:us-east-1:000000000000:trail/org-trail \
  --start-time 2026-10-01T00:00:00Z
# reports each log file as valid, modified or missing

"Prove the CloudTrail logs haven't been tampered with" is log file integrity validation. "Make sure nobody, including administrators, can delete the logs before seven years" is S3 Object Lock in compliance mode on the log bucket.

High-severity GuardDuty findings

In the audit account (the GuardDuty administrator receives every member account's findings), route findings of severity 7 or higher to the on-call topic and an isolation function:

guardduty-alerts.yaml 
HighSeverityFindingRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [ aws.guardduty ]
      detail-type: [ GuardDuty Finding ]
      detail:
        severity: [ { numeric: [ ">=", 7 ] } ]     # high and critical
    Targets:
      - Id: notify
        Arn: !Ref SecurityOnCallTopic
      - Id: isolate
        Arn: !GetAtt IsolateInstanceFunction.Arn  # swaps the instance's security group for a no-access one

Root user sign-in alarm

A metric filter on the trail's CloudWatch Logs log group turns matching events into a metric, and an alarm fires when it's above zero:

root-usage-alarm.yaml 
RootUsageFilter:
  Type: AWS::Logs::MetricFilter
  Properties:
    LogGroupName: !Ref TrailLogGroup
    FilterPattern: '{ $.userIdentity.type = "Root" && $.userIdentity.invokedBy NOT EXISTS && $.eventType != "AwsServiceEvent" }'
    MetricTransformations:
      - { MetricNamespace: Security, MetricName: RootUsage, MetricValue: "1" }

RootUsageAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: Security
    MetricName: RootUsage
    Statistic: Sum
    Period: 300
    EvaluationPeriods: 1
    Threshold: 1
    ComparisonOperator: GreaterThanOrEqualToThreshold
    TreatMissingData: notBreaching
    AlarmActions: [ !Ref SecurityOnCallTopic ]

EventBridge rules for CloudTrail API events receive them only on the default event bus in the Region where the call happened (global services such as IAM log in us-east-1). Read-only calls (Get*, List*, Describe*) only match rules whose state is ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS. To alert centrally, forward events to the security account's bus.

"Alert within minutes when anyone changes a security group in any account" is an EventBridge rule on AuthorizeSecurityGroupIngress (or the Config rule restricted-ssh for compliance). A metric filter works too, but adds the CloudWatch Logs delivery delay.

  Properties:
    LogGroupName: /app/orders

    KmsKeyId: !GetAtt LogsKey.Arn            # key policy must allow the logs service
    DataProtectionPolicy:                     # masks sensitive values in the console and queries
      Name: mask-pii
      Version: "2021-06-01"
      Statement:
        - Sid: audit
          DataIdentifier: [ arn:aws:dataprotection::aws:data-identifier/EmailAddress ]
          Operation: { Audit: { FindingsDestination: {} } }
        - Sid: mask
          DataIdentifier: [ arn:aws:dataprotection::aws:data-identifier/EmailAddress ]
          Operation: { Deidentify: { MaskConfig: {} } }

VpcFlowLog:
  Type: AWS::EC2::FlowLog
  Properties:
    ResourceType: VPC
    ResourceId: !Ref Vpc
    TrafficType: ALL
    LogDestinationType: s3
    LogDestination: arn:aws:s3:::org-flowlogs-666666666666/   # central bucket in the log archive account
    LogFormat: '${version} ${account-id} ${vpc-id} ${interface-id} ${pkt-srcaddr} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${action} ${flow-direction}'
    MaxAggregationInterval: 60
  • Centralizing CloudWatch Logs: a subscription filter in each account sends logs to a destination in the log archive account, typically Data Firehose writing to S3. CloudWatch cross-account observability lets a monitoring account view logs, metrics and traces without copying them.
  • Amazon Security Lake: collects CloudTrail, VPC Flow Logs, Route 53 resolver logs, Security Hub findings and others from all accounts into an S3 data lake in the open OCSF format, for SIEM tools and Athena.
  • Organization-wide setup: deploy flow logs, log groups and agents with StackSets, Config remediation (for example, enable flow logs on every VPC that lacks them), or Systems Manager State Manager for the CloudWatch agent.

"Logs stop arriving after encrypting the log group" means the KMS key policy doesn't allow logs.<region>.amazonaws.com. Similarly, CloudTrail needs the key policy to allow cloudtrail.amazonaws.com, and the bucket policy to allow it to write.

Example queries

Logs Insights, on the trail's log group: which principals are getting AccessDenied?

fields userIdentity.arn, eventSource, eventName, errorCode
| filter errorCode in ["AccessDenied", "UnauthorizedOperation"]
| stats count(*) as denied by userIdentity.arn, eventName
| sort denied desc
| limit 20

Athena, on CloudTrail logs in S3: everything one access key did in the last week:

SELECT eventtime, eventsource, eventname, awsregion, sourceipaddress, errorcode
FROM cloudtrail_logs
WHERE useridentity.accesskeyid = 'AKIAEXAMPLEKEY123456'
  AND eventtime > to_iso8601(current_timestamp - interval '7' day)
ORDER BY eventtime;

Logs Insights, on VPC Flow Logs: which sources are rejected most often?

fields srcAddr, dstPort
| filter action = "REJECT"
| stats count(*) as rejects by srcAddr, dstPort
| sort rejects desc
| limit 20

Investigating a finding

Assume GuardDuty reports UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS for the role on instance i-0abc123:

  1. Read the findingIt names the role, the instance, the external IP and the API calls made with the stolen credentials.
  2. ContainRevoke the role's active sessions, and isolate the instance with a no-access security group. Snapshot its volumes for forensics.
  3. ScopeIn Detective or CloudTrail, list everything that role session and the external IP did, in every Region.
  4. Find the entry pointInspector findings and flow logs for the instance: an unpatched application, an SSRF bug reaching instance metadata (IMDSv1), an open port.
  5. Fix and hardenPatch, require IMDSv2, narrow the role's permissions, and replace the instance from a clean image.

"Determine the root cause and full scope of a GuardDuty finding with the least effort" is Amazon Detective. "Run SQL over a year of CloudTrail logs in S3" is Athena (or CloudTrail Lake).

Key takeaways

  • CloudTrail for API calls (event history is 90 days of management events only; data, Insights and network activity events need a trail), Config for configuration history and compliance, Flow Logs for traffic metadata, drift detection for manual changes to stacks.
  • GuardDuty detects threats from CloudTrail, flow and DNS logs plus protection plans; Inspector finds CVEs on EC2, ECR and Lambda; Access Analyzer finds external and unused access; Config checks rules; Detective investigates.
  • Common threats: HTTP or weak TLS, exposed keys (Health event AWS_RISK_CREDENTIALS_EXPOSED, deactivate then investigate), public buckets (Block Public Access), missing encryption, open SSH, root use, logging turned off.
  • Robust auditing: organization trail, all Regions, log file validation, central bucket in a log archive account with KMS and Object Lock, Config aggregator, SCPs protecting it all.
  • Alerting: EventBridge on findings (severity >= 7) and on specific API calls (default bus, same Region); metric filters and alarms for counts such as root sign-ins; CloudTrail Insights for anomalies.
  • Logging: know where each log is turned on; set retention and KMS (with the key policy allowing the service); centralize with subscription filters, cross-account observability or Security Lake.
  • Analysis: Logs Insights for recent data, Athena or CloudTrail Lake for long ranges, Detective for scope and root cause, Security Hub insights for posture.
