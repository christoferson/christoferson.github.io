Deployment strategies

How a new version replaces the old one. The exam usually gives a constraint (no downtime, fastest rollback, lowest cost, keep full capacity) and asks for the strategy.

StrategyHow it worksDowntimeRollbackExtra cost
All at once (in-place)Every target is updated at the same timeYesRedeploy the old version (slow)None
RollingTargets are updated in batches, in placeNo, but capacity drops during each batchRedeploy (slow)None
Rolling with additional batchLaunches an extra batch first, so capacity never dropsNoRedeploy (slow)One extra batch during the deployment
ImmutableNew instances in a temporary Auto Scaling group; moved in only when healthyNoFast: terminate the new instancesDouble capacity during the deployment
Blue/greenA complete new environment; traffic switches by load balancer, DNS or aliasNoFastest: switch traffic backDouble capacity until the old environment is removed
CanaryA small share of traffic first (10%), then the rest after a bake timeNoFast: shift traffic backLow
LinearTraffic shifts in equal steps at fixed intervals (10% every minute)NoFast: shift traffic backLow

Where each strategy is available

PlatformOptions
EC2 and on premises (CodeDeploy)In-place with OneAtATime, HalfAtATime, AllAtOnce or a custom minimum healthy hosts; blue/green by copying the Auto Scaling group behind the load balancer
Elastic BeanstalkAll at once, rolling, rolling with additional batch, immutable, traffic splitting (canary to new instances); blue/green by swapping environment URLs
ECSRolling (minimumHealthyPercent and maximumPercent) with the deployment circuit breaker; built-in blue/green, linear and canary; or CodeDeploy blue/green with canary or linear traffic shifting
LambdaCodeDeploy on an alias: Canary10Percent5Minutes, Linear10PercentEvery1Minute, AllAtOnce, with alarms and hooks (SAM DeploymentPreference)
API GatewayCanary release settings on a stage
CloudFrontContinuous deployment: a staging distribution receives a share of traffic or requests with a header
Any HTTP workloadALB weighted target groups, or Route 53 weighted records (subject to DNS caching)

"Fastest rollback" means blue/green. "Keep full capacity at the lowest cost" on Beanstalk means rolling with additional batch. "Safest, new instances only" on Beanstalk means immutable. "Test with a small share of real users" means canary.

Elastic Beanstalk deployment policies

Beanstalk offers five deployment policies inside one environment, plus blue/green across two environments. They trade deployment speed against capacity and rollback speed.

PolicyHow it worksIf the deployment failsRollbackCapacity during deployDeployed to
All at onceDeploys the new version to every instance at the same timeDowntimeManual redeploy of the old versionDrops to zero while instances restartExisting instances
RollingTakes one batch out of service, deploys to it, then moves to the next batchOne batch out of service; batches already done run the new version (mixed versions)Manual redeployReduced by one batchExisting instances
Rolling with additional batchLaunches an extra batch first, then deploys in rolling batchesMinimal if the first batch fails; otherwise like rollingManual redeployFull capacity throughoutNew and existing instances
ImmutableLaunches a full set of new instances in a temporary Auto Scaling group; moves them into the environment when healthy, then terminates the old onesMinimal: the old instances never changedTerminate the new instancesDoubles during the deploymentNew instances
Traffic splittingLike immutable, but sends a percentage of traffic to the new instances for an evaluation period first (canary)Only the share of traffic sent to the new version is affectedReroute traffic and terminate the new instancesDoubles during the deploymentNew instances (needs an Application Load Balancer)
Blue/green (swap URLs)A second environment runs the new version; swapping environment URLs moves trafficMinimal: the old environment keeps runningSwap the URLs backA whole second environmentA new environment (a DNS change, so client caching delays the switch)
DetailFact
Speed orderAll at once is fastest, then rolling, then rolling with additional batch; immutable, traffic splitting and blue/green are slowest
Single-instance environmentsSupport only all at once and immutable
Batch sizeFixed number or percentage of instances (BatchSizeType, BatchSize)
Configuration changesChanges that replace instances (for example, instance type) use rolling updates or immutable updates, set separately from the deployment policy
DatabasesAn RDS database created inside the environment is deleted with it; for blue/green, create the database outside the environment and pass its endpoint in

"Zero downtime and full capacity at the lowest cost" is rolling with additional batch. "Safest rollback without a new environment" is immutable. "Test the new version on 10% of users" is traffic splitting. "Platform change that can't run side by side, instant switch back" is blue/green with a URL swap.

CodeDeploy deployment configurations

A deployment configuration tells CodeDeploy how fast to move. On EC2 it controls how many instances update at once; on Lambda and ECS it controls how traffic shifts to the new version.

EC2 and on premisesIn-place, or blue/green (new instances behind the same load balancer)OneAtATime (default), HalfAtATime, AllAtOnce; custom configurations set a minimum number or percentage of healthy hosts, optionally per AZRedeploys the last good revision (automatic on failure or alarm, if enabled)

The configuration names include the platform: CodeDeployDefault.LambdaCanary10Percent5Minutes, CodeDeployDefault.ECSLinear10PercentEvery1Minutes. Behind a Network Load Balancer, ECS supports only CodeDeployDefault.ECSAllAtOnce.

Updating instances in an Auto Scaling group

Three ways to replace running instances after the launch template changes. The first two are CloudFormation UpdatePolicy settings; the third is an Auto Scaling feature you start directly.

MethodHow it worksCapacityRollback
CloudFormation AutoScalingRollingUpdateDuring a stack update, replaces instances in batches (MaxBatchSize, MinInstancesInService, PauseTime, optional WaitOnResourceSignals)Can dip unless MinInstancesInService keeps enough runningStack rollback replaces instances again, batch by batch (slow)
CloudFormation AutoScalingReplacingUpdate (WillReplace: true)Creates a whole new Auto Scaling group, and deletes the old one only after the update succeedsDoubles during the updateFast: the new group is deleted and the old one never changed
Instance refreshAuto Scaling replaces instances in batches set by minimum and maximum healthy percentage; supports checkpoints, bake time, skip matching and a desired configurationKept at or above the minimum healthy percentage; 100% minimum launches new instances before terminating old onesRoll back on request, or automatically when the refresh fails or a CloudWatch alarm fires
Instance refresh settingEffect
Minimum healthy percentageShare of desired capacity that must stay in service; 90% replaces 10% at a time, 0% replaces everything at once
Maximum healthy percentageHow far capacity may grow during the refresh; above 100% allows launching replacements before terminating
CheckpointsPause after a percentage of instances is replaced, emitting EventBridge events, so you can verify before continuing
Skip matchingLeave instances that already match the desired configuration (doesn't detect code pulled by user data)
LimitsA refresh can run for at most 14 days; it fails after an hour of being unable to make progress

"Roll out a new AMI to an Auto Scaling group gradually, pause to verify, and roll back automatically on an alarm" is an instance refresh with checkpoints and auto rollback. "Fastest rollback when a CloudFormation update fails" is AutoScalingReplacingUpdate.

CloudFormation update behaviors and deletion policies

Every resource property is documented with what happens when it changes. Change sets show this before you deploy.

Update behaviorWhat happensExample
No interruptionThe resource is updated in place and keeps workingChanging tags, or a Lambda function's memory size
Some interruptionUpdated in place, but briefly unavailableChanging an EBS-backed EC2 instance's type (stop and start)
ReplacementA new resource with a new physical ID is created, references are updated, then the old one is deletedChanging an EC2 instance's AMI, or an RDS instance's identifier
Policy valueOn stack delete or removal from the templateNotes
DeleteThe resource is deletedThe default for most resources; S3 buckets must be empty first
RetainThe resource is kept and leaves CloudFormation's managementWorks on any resource; it still costs money
RetainExceptOnCreateKept, except when the stack operation that created it rolls backAvoids leaving empty resources behind after a failed create
SnapshotA snapshot is taken, then the resource is deletedEBS volumes, RDS instances and clusters, ElastiCache, Neptune, DocumentDB, Redshift. The default for RDS clusters, and for RDS instances that aren't in a cluster

DeletionPolicy doesn't apply when an update replaces a resource; that's UpdateReplacePolicy, with the same values. And a resource with a custom name (for example, a fixed BucketName) can't be replaced, because the new one would need the same name; the update fails.

Disaster recovery strategies

Ordered from cheapest and slowest to most expensive and fastest. Pick the cheapest strategy that still meets the stated RTO (how long to recover) and RPO (how much data can be lost).

StrategyRunning in the recovery RegionRPORTOCost

Pilot lightData replicated continuously; core services (databases) running; application servers off or at zeroSeconds to minutesTens of minutes: start and scale the application tierLow
Warm standbyA complete, smaller copy that serves (or can serve) trafficSecondsMinutes: scale outMedium
Multi-site active/activeFull capacity in every Region, all serving trafficNear zeroNear zeroHighest
Building blockTypical use
AWS Backup cross-Region and cross-account copiesBackup and restore
S3 Cross-Region Replication (with Replication Time Control)Any strategy, for object data
Aurora Global Database, RDS cross-Region read replicasPilot light and warm standby
DynamoDB global tablesMulti-site active/active
AWS Elastic Disaster RecoveryServers replicated at block level: RPO in seconds, RTO in minutes, at low standby cost

Read the RTO and RPO numbers first. "RTO of hours, lowest cost" is backup and restore. "Database must be current but compute can start on demand" is pilot light. "Minutes, already running at reduced size" is warm standby.

Queues and streams in detail

SQS queues hand each message to one consumer and delete it when processed. Kinesis Data Streams keeps an ordered log that many consumers read independently. Data Firehose delivers a stream to a destination without consumer code.

OrderingBest effort; messages can arrive out of orderStrict order within a message group (MessageGroupId)
DeliveryAt least once: occasional duplicates, so consumers must be idempotentExactly-once processing: duplicates within a 5-minute window are dropped (content-based or MessageDeduplicationId)
ThroughputNearly unlimited300 API calls per second per action, or 3,000 messages per second with batches of 10; high throughput mode goes much higher, depending on the Region
ParallelismAny number of consumers on any messageOne message group is processed in order by one consumer at a time; more groups means more parallelism

"Several applications must each process every event, and be able to reprocess the last day" is Kinesis Data Streams. "Decouple the order service from the shipping service and absorb spikes" is SQS. "Deliver CloudWatch Logs or clickstream data to S3 as Parquet" is Data Firehose.

A private subnet with a gateway endpoint to S3 still can't reach other services (for example, ECR, CloudWatch Logs, Secrets Manager): each needs its own interface endpoint, or a NAT gateway. "ECS tasks in private subnets can't pull images" often means the ECR (ecr.api, ecr.dkr) and S3 endpoints are missing.
