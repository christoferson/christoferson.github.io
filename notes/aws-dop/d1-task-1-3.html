Overview

Task statement 1.3

Build and manage artifacts.

An artifact is anything a build produces that's later deployed or reused: a JAR or zip file, a container image, an AMI, a Lambda package, a packaged CloudFormation template. This task tests where each kind belongs, how to keep it secure and traceable, how to clean up old versions, and how to automate image builds. Typical scenarios: "teams must only use approved open source packages", "old images fill up the repository", or "every AMI must be patched and hardened monthly".

Build once, deploy many

Build an artifact once, then promote the same artifact through dev, test and production. Rebuilding for each environment risks shipping something different from what was tested. Environment differences belong in configuration (Parameter Store, AppConfig, environment variables), not in the artifact.

"The version in production behaves differently from the one that passed testing" points to rebuilding per environment. The fix is one immutable artifact, identified by version or image digest, promoted through every stage.

Code signing with AWS Signer

  • Lambda code signing: create a Signer signing profile, sign the zip package in the pipeline, and attach a code signing configuration to the function. Set the untrusted artifact policy to Enforce to reject unsigned or tampered code, or Warn to allow it but log a warning.
  • Container images: AWS Signer works with the open source Notation tool to sign images in ECR. The cluster then verifies signatures before running them (for example, with an admission controller on EKS).

"Only code that came through the approved pipeline may run in the Lambda function" points to Lambda code signing with an Enforce policy.

What packaging a template does

aws cloudformation package (and sam package) uploads local files to S3 and rewrites the template to point at them. The output template is the deployable artifact.

template.yml (before) 
OrdersFunction:
  Type: AWS::Serverless::Function
  Properties:
    CodeUri: ./src/orders          # local folder
    Handler: app.handler
    Runtime: python3.12
aws cloudformation package \
  --template-file template.yml \
  --s3-bucket tooling-artifacts \
  --output-template-file packaged.yml
packaged.yml (after) 
OrdersFunction:
  Type: AWS::Serverless::Function
  Properties:
    CodeUri: s3://tooling-artifacts/5f2c9e1a8b7d...   # uploaded zip
    Handler: app.handler
    Runtime: python3.12

Versioning artifacts

  • Semantic versions (2.4.1) for libraries and releases people refer to.
  • Commit ID (for example, the first 8 characters of CODEBUILD_RESOLVED_SOURCE_VERSION) to trace any artifact back to its source.
  • Build number (CODEBUILD_BUILD_NUMBER) for a simple increasing sequence.
  • Image digest (sha256:...) as the exact, unchangeable identity of a container image. Tags can move; digests can't.

Deploying images by the latest tag makes deployments unpredictable and rollbacks impossible to reason about. Deploy a specific version tag (with tag immutability on) or the image digest.

Artifact lifecycle considerations

Knowledge

Every artifact goes through the same stages. Each one has a decision to automate:

  1. CreateBuilt by the pipeline, versioned and tagged with its commit.
  2. Store and scanPushed to its repository, encrypted, and scanned for vulnerabilities.
  3. PromoteThe same artifact moves to test, staging and production, or is copied to other accounts and Regions.
  4. Deploy and keep for rollbackKeep enough previous versions to roll back quickly.
  5. DeprecateMark old versions so new deployments stop using them.
  6. Delete or archiveRemove them automatically to control cost and clutter, or archive them for compliance.

Retention by store

StoreLifecycle tool
S3Lifecycle rules: move to cheaper storage classes, expire objects and old (noncurrent) versions. Object Lock for write-once retention
ECRLifecycle policies: expire images by count or age, filtered by tag status or tag prefix
CodeArtifactPackage version status (Published, Unlisted, Archived, Disposed), plus deleting versions. Published versions can't be overwritten
AMIsEC2 Image Builder lifecycle policies (deprecate, disable, delete); AMI deprecation time; Recycle Bin rules to recover deleted AMIs and snapshots

ECR lifecycle policy example

Rules are evaluated by priority, lowest number first. This policy deletes untagged images after 7 days and keeps only the 30 most recent release images.

ecr-lifecycle-policy.json 
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Delete untagged images after 7 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Keep the last 30 release images",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": ["release-"],
        "countType": "imageCountMoreThan",
        "countNumber": 30
      },
      "action": { "type": "expire" }
    }
  ]
}

S3 lifecycle rule example

artifact-bucket.yml 
ArtifactBucket:
  Type: AWS::S3::Bucket
  Properties:
    VersioningConfiguration: { Status: Enabled }
    LifecycleConfiguration:
      Rules:
        - Id: tidy-build-artifacts
          Status: Enabled
          Transitions:
            - { StorageClass: STANDARD_IA, TransitionInDays: 30 }   # rarely read after a month
          ExpirationInDays: 180                                    # delete current versions
          NoncurrentVersionExpiration: { NoncurrentDays: 30 }      # delete replaced versions
          AbortIncompleteMultipartUpload: { DaysAfterInitiation: 7 }

Versioned buckets keep every overwritten object as a noncurrent version. Without NoncurrentVersionExpiration, storage keeps growing even though the "current" files look tidy.

"Artifacts must be kept for 7 years and must not be deleted or changed" points to S3 Object Lock in compliance mode (often with a transition to S3 Glacier Deep Archive). Lifecycle rules alone don't prevent deletion.

Creating and configuring artifact repositories

Skill

AWS CodeArtifact

CodeArtifact is a managed package repository for npm, PyPI, Maven, NuGet, Swift, Ruby, Cargo and generic packages. It has two layers:

  • Domain: the shared storage and KMS key for many repositories. Usually one per organization, owned by a shared services account. A package stored once is available to every repository in the domain without being copied.
  • Repository: what developers and builds connect to. A repository can have up to 10 upstream repositories, searched in order when a package isn't found locally, and one external connection to a public registry such as npmjs, PyPI or Maven Central.

For example, a shared repository fetches packages from npmjs, and each team's repository uses the shared one as its upstream:

codeartifact.yml 
Domain:
  Type: AWS::CodeArtifact::Domain
  Properties:
    DomainName: example-corp
    EncryptionKey: !GetAtt ArtifactKey.Arn

SharedNpm:
  Type: AWS::CodeArtifact::Repository
  Properties:
    DomainName: !GetAtt Domain.Name
    RepositoryName: shared-npm
    ExternalConnections: [public:npmjs]           # fetch and cache from the public registry

OrdersTeamRepo:
  Type: AWS::CodeArtifact::Repository
  Properties:
    DomainName: !GetAtt Domain.Name
    RepositoryName: orders-team
    Upstreams: [!GetAtt SharedNpm.Name]          # falls back to shared-npm

A developer or build then connects with one command, which fetches a token (valid up to 12 hours) and configures the package manager:

aws codeartifact login --tool npm --domain example-corp --domain-owner 111111111111 --repository orders-team
  • Cross-account access: a domain policy allows other accounts to get tokens, and a repository policy allows them to read or publish.
  • Permissions to fetch a token: the caller needs codeartifact:GetAuthorizationToken and sts:GetServiceBearerToken.
  • Package origin controls: per package, decide whether versions may come from upstream (public) repositories, from direct publishing, or both. Blocking upstream for your internal package names stops a dependency confusion attack, where someone publishes a public package with the same name as your private one.
  • Approved packages only: remove the external connection from team repositories and let only a curated repository fetch from public registries.

"The build role has codeartifact:GetAuthorizationToken but aws codeartifact login is denied" usually means the role is missing sts:GetServiceBearerToken.

Skill

Amazon ECR

This repository scans every push, prevents tags from being overwritten, encrypts with KMS, cleans up old images, and lets a production account pull images:

ecr.yml 
OrdersRepository:
  Type: AWS::ECR::Repository
  Properties:
    RepositoryName: orders
    ImageTagMutability: IMMUTABLE                # v1.4.2 always means the same image
    ImageScanningConfiguration: { ScanOnPush: true }
    EncryptionConfiguration:
      EncryptionType: KMS
      KmsKey: !GetAtt ArtifactKey.Arn
    LifecyclePolicy:
      LifecyclePolicyText: '{"rules":[{"rulePriority":1,"selection":{"tagStatus":"untagged","countType":"sinceImagePushed","countUnit":"days","countNumber":7},"action":{"type":"expire"}}]}'
    RepositoryPolicyText:
      Version: "2012-10-17"
      Statement:
        - Sid: AllowProductionPull
          Effect: Allow
          Principal: { AWS: arn:aws:iam::222222222222:root }
          Action: [ecr:BatchGetImage, ecr:GetDownloadUrlForLayer, ecr:BatchCheckLayerAvailability]
  • The pulling account: the role there (for example, the ECS task execution role in 222222222222) still needs ecr:GetAuthorizationToken and the pull actions in its own IAM policy.
  • Scanning: basic scanning checks OS packages on push or on demand. Enhanced scanning, configured at the registry level, uses Amazon Inspector to rescan continuously as new vulnerabilities are published, and also covers language packages.
  • Replication: a registry-level replication configuration copies images to other Regions and accounts automatically, so each Region deploys from a nearby copy.
  • Pull through cache: a rule caches images from an upstream registry (ECR Public, Docker Hub, Quay, GitHub Container Registry and others) the first time they're pulled. Credentials for authenticated upstreams are stored in Secrets Manager.

"Builds fail because of Docker Hub rate limits" points to an ECR pull through cache rule.

Skill

Amazon S3 as an artifact store

Use S3 for anything that isn't a package or an image. A well-configured artifact bucket has:

  • Versioning, required for S3 pipeline sources and useful for rollback.
  • SSE-KMS encryption with a customer managed key if other accounts read it.
  • Block Public Access on, and a bucket policy that denies non-TLS requests.
  • Lifecycle rules for old and noncurrent versions.
  • Cross-Region replication when pipelines in other Regions need the same artifacts.
  • Object Lock when artifacts must be kept unchanged for compliance.
artifact-bucket-policy.yml 
ArtifactBucketPolicy:
  Type: AWS::S3::BucketPolicy
  Properties:
    Bucket: !Ref ArtifactBucket
    PolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Sid: DenyInsecureTransport
          Effect: Deny
          Principal: "*"
          Action: s3:*
          Resource: [!GetAtt ArtifactBucket.Arn, !Sub "${ArtifactBucket.Arn}/*"]
          Condition:
            Bool: { aws:SecureTransport: "false" }     # reject plain HTTP

Configuring build tools for generating artifacts

Skill

CodeBuild artifacts

The artifacts section of the buildspec decides which files leave the build. A build can produce one primary artifact and several secondary artifacts. In a pipeline, each one becomes a named output artifact for later actions.

buildspec.yml 
version: 0.2
phases:
  build:
    commands:
      - sam build
      - sam package --s3-bucket tooling-artifacts --output-template-file packaged.yml
      - mvn -B package -DskipTests
artifacts:
  files:
    - packaged.yml                            # primary artifact: the deployable template
  secondary-artifacts:
    AppJar:
      base-directory: target
      files: ["orders-*.jar"]
      discard-paths: yes                     # flatten folders in the output
    Reports:
      files: ["reports/**/*"]
  • Standalone builds (outside a pipeline) write artifacts to S3. The project settings choose the bucket, the name, zip or no packaging, and whether to include the build ID in the path.
  • Encryption: artifacts are encrypted with the project's KMS key (the AWS managed aws/s3 key by default). Use a customer managed key for cross-account use.

Lambda as an artifact generator

A Lambda invoke action in CodePipeline can also create artifacts, for example rendering configuration files or a manifest from pipeline variables. The job data CodePipeline sends to the function includes:

  • outputArtifacts: the S3 bucket and object key where the output must be written.
  • artifactCredentials: temporary credentials allowed to write to that location.

The function zips its output, uploads it using those credentials, then calls PutJobSuccessResult. The next action receives it as a normal input artifact.

Use CodeBuild for real builds (compiling, images, anything over 15 minutes). A Lambda action suits small, quick artifact-generation steps.

Automating EC2 instance and container image builds (EC2 Image Builder)

Skill

EC2 Image Builder builds, tests and distributes golden AMIs and container images on a schedule, with no build servers to manage. It's the AWS-native answer to "every instance must start from a patched, hardened image".

Building blocks

ResourceWhat it defines
ComponentA YAML document of steps, in build, validate and test phases. AWS provides managed components (for example, updating Linux, CIS hardening, installing the CloudWatch agent)
Image recipeThe parent (base) image plus an ordered list of components. A container recipe does the same for a Docker image and pushes it to ECR
Infrastructure configurationHow the build instance runs: instance type, instance profile, subnet, security group, SNS topic and log bucket
Distribution configurationWhere the output goes: Regions, accounts or organizations to share with, AMI names, and launch templates to update
Image pipelineTies it all together, with a schedule and image tests turned on

A component

install-nginx-component.yml 
name: install-nginx
description: Install and verify nginx
schemaVersion: 1.0
phases:
  - name: build                          # runs on the build instance
    steps:
      - name: InstallNginx
        action: ExecuteBash
        inputs:
          commands:
            - sudo dnf install -y nginx
            - sudo systemctl enable nginx
  - name: validate                       # still on the build instance, before the AMI is taken
    steps:
      - name: CheckInstalled
        action: ExecuteBash
        inputs:
          commands: ["nginx -v"]
  - name: test                           # on a new instance launched from the finished AMI
    steps:
      - name: CheckRunning
        action: ExecuteBash
        inputs:
          commands: ["systemctl is-active nginx"]

The pipeline

image-pipeline.yml 
GoldenAmiPipeline:
  Type: AWS::ImageBuilder::ImagePipeline
  Properties:
    Name: golden-al2023
    ImageRecipeArn: !Ref GoldenRecipe
    InfrastructureConfigurationArn: !Ref BuildInfrastructure
    DistributionConfigurationArn: !Ref Distribution
    ImageTestsConfiguration: { ImageTestsEnabled: true }
    Schedule:
      ScheduleExpression: "cron(0 3 ? * SUN *)"                         # every Sunday 03:00 UTC
      PipelineExecutionStartCondition: EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE

EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE runs on schedule only if the parent image or a component has a newer version. EXPRESSION_MATCH_ONLY runs every time.

What happens on each run

  1. Launch the build instanceImage Builder starts an instance from the parent image, using the infrastructure configuration.
  2. Run build and validate phasesEach component's steps run through Systems Manager. Any failing step fails the build.
  3. Create the imageAn AMI is created from the build instance, which is then terminated.
  4. Test the imageA new instance is launched from the AMI and the test phases run. A failure stops distribution.
  5. DistributeThe AMI is copied to the configured Regions, shared with accounts or the organization, and launch templates can be updated to the new AMI ID.
  6. Notify and roll outAn SNS or EventBridge event starts follow-up automation, for example a Lambda function that writes the new AMI ID to a Parameter Store parameter and starts an Auto Scaling group instance refresh.
  • Instance profile: it needs AmazonSSMManagedInstanceCore and EC2InstanceProfileForImageBuilder. Without Systems Manager access the build instance can't receive its steps.
  • Network access: the build subnet must reach Systems Manager and the package repositories (through a NAT gateway or VPC endpoints).
  • Scanning: Image Builder can use Amazon Inspector to scan the images it builds.
  • Lifecycle policies: Image Builder lifecycle policies deprecate, disable and finally delete old images and their snapshots automatically.

An Image Builder build that times out with the instance "not reachable" almost always means the instance profile is missing AmazonSSMManagedInstanceCore, or the subnet has no route to Systems Manager.

"Launch templates must always use the latest hardened AMI" points to an Image Builder distribution configuration that updates the launch template, or a Parameter Store parameter that launch templates reference (resolve:ssm:/golden-ami/latest).

Key takeaways

  • Build once, promote the same immutable artifact everywhere. Keep environment differences in configuration.
  • Packages go in CodeArtifact, images in ECR, AMIs in EC2, and everything else (zips, packaged templates, reports) in S3.
  • Secure artifacts with KMS (customer managed keys for cross-account), resource policies, private endpoints, immutable tags, Object Lock, scanning and code signing.
  • Lambda code signing with an Enforce policy blocks code that wasn't signed by the pipeline.
  • CodeArtifact: domain plus repositories, upstreams (up to 10), one external connection, package origin controls against dependency confusion. Token access needs sts:GetServiceBearerToken.
  • ECR: tag immutability, scan on push or enhanced scanning, lifecycle policies, replication and pull through cache.
  • S3 lifecycle rules need NoncurrentVersionExpiration on versioned buckets. Object Lock is for "must not be deleted".
  • EC2 Image Builder: components, recipe, infrastructure configuration, distribution configuration and pipeline. Image tests run on a new instance. The instance profile needs Systems Manager access.
