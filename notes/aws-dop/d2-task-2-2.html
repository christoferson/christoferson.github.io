Overview

Task statement 2.2

Deploy automation to create, onboard, and secure AWS accounts in a multi-account or multi-Region environment.

Large AWS estates run hundreds of accounts. This task tests whether you can structure them, create new accounts that are secure from the first minute, limit what any account can do, and run security services across all of them from one place. Typical scenarios: "every new account must have CloudTrail, Config and GuardDuty enabled automatically", "no account may use Regions outside the EU", or "the security team needs one view of findings from all accounts".

AWS account structures, best practices and related services

Knowledge

Why many accounts?

An AWS account is the strongest isolation boundary AWS offers. Separate accounts give you:

  • Security isolation: a compromised development account can't touch production resources by default.
  • Smaller blast radius: mistakes and quota exhaustion stay inside one account.
  • Clear billing: costs are reported per account.
  • Separate quotas: each account has its own service limits.
  • Simple policies: rules can apply to a whole account (or OU) instead of tagging every resource.

A recommended structure

AWS guidance groups accounts into organizational units (OUs) by function, so policies attach to the OU rather than to individual accounts:

OUAccountsPurpose
(Root)Management accountOrganizations, billing and Control Tower only. No workloads
SecurityLog Archive, Security Tooling (Audit)Immutable central logs; delegated administrator for security services
InfrastructureNetwork, Shared ServicesTransit Gateway, central DNS and endpoints; CI/CD tooling and shared directories
WorkloadsProduction and non-production accounts per applicationThe applications themselves, with stricter policies on production
SandboxOne per developer or teamExperiments, with budgets and few connections to anything else
Policy StagingTest accountsTry new SCPs and controls before applying them widely
SuspendedAccounts being closedA deny-all SCP while they wait for closure

SCPs never restrict the management account. Any workload placed there is outside your guardrails, which is why the management account should run nothing but organization-level tooling.

Organization building blocks

  • Organization: one management account plus member accounts, in OUs that can nest up to five levels below the root.
  • All features vs consolidated billing: policies (SCPs and others) need all features enabled; consolidated billing alone only combines bills.
  • Policy types:
    • Service control policies (SCPs): limit what principals in accounts can do.
    • Resource control policies (RCPs): limit what can be done to resources in accounts.
    • Management policies: tag policies, backup policies, AI services opt-out policies and declarative policies.
  • Trusted access: lets a service such as Config, CloudTrail, StackSets or Security Hub work across the organization.
  • Delegated administrator: hands day-to-day administration of a service to a member account (usually Security Tooling), so the management account isn't used.

Standardizing and automating account provisioning and configuration

Skill

"Account vending" means creating accounts on request with everything a team needs already applied. The options, from simplest to most flexible:

OptionHow it worksChoose it when
Organizations CreateAccount APICreates a member account with an OrganizationAccountAccessRole that the management account can assumeYou build all the automation yourself
Control Tower Account FactoryA Service Catalog product that creates an enrolled account: placed in an OU, with controls, logging and IAM Identity Center access appliedYou use Control Tower (the usual exam answer)
Account Factory Customization (AFC)Account Factory plus a blueprint (a Service Catalog product, such as a CloudFormation template) applied to the new accountEach account type needs its own resources
Customizations for Control Tower (CfCT)A pipeline that applies CloudFormation templates and SCPs from a manifest to OUs and accounts, and reapplies them to new accountsOrganization-wide customizations managed as code

An account vending flow

  1. A team requests an accountThrough the Account Factory product in Service Catalog, an internal portal, or a Git pull request (AFT).
  2. Control Tower creates and enrolls itThe account is placed in the chosen OU. CloudTrail and Config logging to the Log Archive account and the OU's controls are applied.
  3. A lifecycle event firesControl Tower emits a CreateManagedAccount event to EventBridge when enrollment succeeds.
  4. The baseline is appliedService-managed StackSets deploy automatically to the OU. CfCT, a blueprint or a Lambda function triggered by the event adds the rest.
  5. Access is grantedIAM Identity Center assigns permission sets to the team's groups.
  6. Security services pick it upGuardDuty, Security Hub and Inspector, set to auto-enable new accounts, start covering it.
eventbridge-pattern.json (new account enrolled) 
{
  "source": ["aws.controltower"],
  "detail-type": ["AWS Service Event via CloudTrail"],
  "detail": {
    "eventName": ["CreateManagedAccount"],
    "serviceEventDetails": {
      "createManagedAccountStatus": {
        "state": ["SUCCEEDED"]
      }
    }
  }
}

What a baseline usually contains

  • Logging: CloudTrail (organization trail) and AWS Config recording, delivered to the Log Archive account.
  • Security services: GuardDuty, Security Hub, IAM Access Analyzer and Inspector, administered from the Security Tooling account.
  • Roles: standard IAM roles for pipelines, break-glass access and security auditors.
  • Network: default VPCs removed; a VPC from IPAM-managed ranges attached to the Transit Gateway; resources shared from the Network account through AWS RAM.
  • Cost controls: AWS Budgets alerts and cost allocation tags.
  • Account details: alternate contacts (security, billing, operations).

"Every new account must automatically get the same IAM roles and Config rules" points to service-managed StackSets with automatic deployment on the OU, or Control Tower customizations (CfCT or AFC). Running a script by hand after each account is created is never the best answer.

Creating, consolidating and centrally managing accounts

Skill

AWS Organizations

  • Creating accounts: CreateAccount makes a new member account, with root credentials you never need to use and an OrganizationAccountAccessRole for administrators.
  • Consolidating existing accounts: the management account sends an invitation (a handshake). The account's owner accepts it. Invited accounts don't get OrganizationAccountAccessRole automatically, so create it yourself if you need it.
  • Moving accounts: move an account between OUs and it immediately inherits the new OU's policies.
  • Consolidated billing: one bill, combined usage for volume pricing tiers, and Reserved Instance and Savings Plans discounts shared across accounts (sharing can be turned off per account).
  • Closing accounts: closed accounts stay suspended for 90 days, during which they can be reopened.
Skill

AWS Control Tower

Control Tower sets up and runs a well-architected multi-account environment, called a landing zone, on top of Organizations. Setting it up creates:

  • Organization structure: a Security OU with a Log Archive account and an Audit account.
  • Central logging: an organization CloudTrail trail and AWS Config recording in every enrolled account, delivered to Log Archive.
  • Human access: IAM Identity Center for single sign-on into every account.
  • Account vending: Account Factory.
  • Controls: a set of mandatory controls on every enrolled account.

Controls (guardrails)

BehaviorImplemented withExample
PreventiveSCPs (and RCPs)Disallow changes to the CloudTrail trail Control Tower created
DetectiveAWS Config rulesDetect whether public read access is allowed on S3 buckets
ProactiveCloudFormation HooksBlock CloudFormation from creating an S3 bucket without encryption

Controls are mandatory (always on), strongly recommended or elective, and you enable them per OU. The Region deny control blocks the use of Regions outside the ones you govern.

Bringing in existing accounts

  1. Invite the account into the organizationIf it isn't a member yet.
  2. Prepare itCreate the AWSControlTowerExecution role that Control Tower uses to manage it, and remove anything that conflicts (for example, an existing Config recorder or delivery channel).
  3. Enroll itEnroll the single account, or register its whole OU so every account in it is enrolled.

Drift

Control Tower reports drift when its resources are changed outside Control Tower: an SCP it manages is edited, an enrolled account is moved to another OU, or a control's resources are deleted. Fix it by repairing the landing zone or re-registering the OU.

Editing a Control Tower-managed SCP directly in Organizations causes drift. Add your own SCPs alongside them instead, or manage customizations with CfCT.

Applying IAM solutions for multi-account and complex organization structures

Skill

Service control policies (SCPs)

An SCP sets the maximum permissions for every IAM user and role in the accounts it applies to. It never grants anything: a user still needs an IAM policy that allows the action. Think of it as a filter between your people and AWS: whatever their own policies say, nothing outside the filter gets through.

  • Who it affects: all users and roles in member accounts, including each member account's root user and administrators with AdministratorAccess.
  • Who it doesn't: the management account, service-linked roles, and principals outside the organization (even when they access your resources through a bucket or key policy). Resource control policies cover that last gap.
  • Prerequisites: the organization uses all features, and the SCP policy type is enabled on the root.

How an SCP is evaluated

When a user in a member account makes a request, the SCPs of that user's account decide the ceiling, whichever account owns the resource:

  1. Collect the SCPs on the pathThe root, every OU above the account, and the account itself.
  2. Any explicit Deny ends itA Deny matching the request at any level denies the request.
  3. Every level must allowEach level needs at least one SCP whose Allow covers the action. The default FullAWSAccess SCP allows everything, so with it attached everywhere, only Deny statements matter.
  4. Then the normal IAM evaluationIdentity policies, resource policies, permissions boundaries and session policies decide within that ceiling.

Deny list and allow list strategies

With a deny list, FullAWSAccess stays attached at every level and you add SCPs that deny specific actions. New AWS services work automatically; you only write the exceptions. This is the common approach and the one Control Tower uses.

With an allow list, you detach FullAWSAccess from a level and attach an SCP that allows only listed services. Because every level must allow an action, the effective permissions are the services allowed at all levels. For example:

  1. RootFullAWSAccess: everything passes.
  2. Workloads OUFullAWSAccess replaced by an SCP allowing ec2:*, s3:*, rds:*, cloudwatch:*, logs:*.
  3. Account 222222222222FullAWSAccess: everything passes at this level.
  4. Effective ceilingOnly EC2, S3, RDS, CloudWatch and CloudWatch Logs. Any other service is denied, even for administrators.
workloads-allow-list-scp.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowApprovedServicesOnly",
      "Effect": "Allow",
      "Action": [
        "ec2:*",
        "s3:*",
        "rds:*",
        "cloudwatch:*",
        "logs:*"
      ],
      "Resource": "*"
    }
  ]
}

Allow lists are stricter but costly to maintain: every new service a team needs means an SCP change, and forgetting supporting services (such as kms:* for encrypted volumes) breaks things in confusing ways.

Policy language and limits

  • Elements: Effect (Allow or Deny), Action or NotAction, Resource or NotResource, and Condition, in both Allow and Deny statements.
  • Specific resources: only Deny statements can name resource ARNs; an Allow statement's Resource must be "*".
  • No Principal: SCPs don't support Principal or NotPrincipal. To exempt a role, use a condition on aws:PrincipalArn.
  • Limits: up to 10,240 characters per SCP and up to 10 SCPs attached directly to the root, each OU and each account. OUs can be nested five levels deep.

Example: guardrails for the Workloads OU

Assume the organization must stay in two EU Regions, must not be able to switch off its security services, and must protect the pipeline role that deploys to every account (PipelineDeployRole).

workloads-guardrails-scp.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*", "organizations:*", "sts:*", "support:*",
        "cloudfront:*", "route53:*", "budgets:*", "health:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["eu-west-1", "eu-central-1"]
        }
      }
    },
    {
      "Sid": "ProtectSecurityServices",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging", "cloudtrail:DeleteTrail",
        "guardduty:DeleteDetector", "guardduty:DisassociateFromMasterAccount",
        "config:StopConfigurationRecorder", "config:DeleteConfigurationRecorder"
      ],
      "Resource": "*"
    },
    {
      "Sid": "ProtectPipelineRole",
      "Effect": "Deny",
      "Action": ["iam:DeleteRole", "iam:UpdateAssumeRolePolicy", "iam:PutRolePolicy", "iam:AttachRolePolicy"],
      "Resource": "arn:aws:iam::*:role/PipelineDeployRole",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/PlatformAdminRole"
        }
      }
    },
    {
      "Sid": "DenyLeavingOrganization",
      "Effect": "Deny",
      "Action": "organizations:LeaveOrganization",
      "Resource": "*"
    }
  ]
}
  • NotAction in the Region rule: exempts global services whose API calls go to us-east-1 (IAM, CloudFront, Route 53 and others). Without the exemption, the SCP would break them.
  • ArnNotLike on aws:PrincipalArn: lets one administrator role through while everyone else is denied.

Creating and attaching an SCP

SCPs are created and attached from the management account (or a delegated administrator for Organizations policies). As code, the policy and its targets are one CloudFormation resource:

workloads-guardrails.yaml (in the management account) 
WorkloadGuardrails:
  Type: AWS::Organizations::Policy
  Properties:
    Name: workloads-guardrails
    Type: SERVICE_CONTROL_POLICY
    TargetIds:
      - ou-ab12-workload1   # Workloads OU
    Content:
      Version: "2012-10-17"
      Statement:
        - Sid: DenyLeavingOrganization
          Effect: Deny
          Action: organizations:LeaveOrganization
          Resource: "*"

The same with the AWS CLI:

aws organizations create-policy \
  --name workloads-guardrails \
  --type SERVICE_CONTROL_POLICY \
  --content file://workloads-guardrails-scp.json

aws organizations attach-policy \
  --policy-id p-examplepolicyid111 \
  --target-id ou-ab12-workload1

Rolling out an SCP safely

  1. Test in a Policy Staging OUAttach the SCP to an OU that holds test accounts with the same workloads, not to production.
  2. Look for denialsIn CloudTrail, AccessDenied errors whose message says explicit deny in a service control policy show what the SCP blocked.
  3. Check real usage first for allow listsIAM last-accessed information (service and action level) shows which services accounts actually use before you remove them.
  4. Attach to the target OUStart low in the hierarchy and move up; attaching an untested SCP to the root affects every member account at once.

"An SCP denies an action, but the user has AdministratorAccess": the action is still denied. Conversely, "an SCP allows S3, but the user gets AccessDenied": SCPs don't grant, so the user's IAM policy must allow it too.

Resource control policies (RCPs)

An RCP sets the maximum permissions for resources in member accounts, whoever the caller is. SCPs can only limit your own principals; a bucket policy, key policy or role trust policy can still grant access to an account outside the organization, and no SCP stops that caller. An RCP is attached to the root, an OU or an account like an SCP, but it applies to requests made to the resources there, from anyone, including other organizations.

The main use is a data perimeter: data in your S3 buckets, KMS keys, secrets and queues can be reached only by your own organization's identities and by AWS services acting for you, even if someone writes an overly open resource policy.

How an RCP is evaluated

  1. Find the resource's ownerThe RCPs that apply are the ones on the path to the account that owns the resource, not the caller's account.
  2. Any explicit Deny ends itA matching Deny at any level denies the request, for any caller: your users, other accounts, other organizations, root users.
  3. Then the normal evaluationSCPs of the caller's account (if in your organization), identity policies and resource policies decide within that ceiling.
  • Not affected: resources in the management account, calls made by service-linked roles, and AWS managed KMS keys.
  • Services: RCPs apply only to services that support them. The list includes S3, STS, KMS, SQS, Secrets Manager, DynamoDB, ECR, CloudWatch Logs and Cognito, among about sixty; check the Organizations documentation for the current list.

Policy language and limits

  • Deny only: RCPs you write must use "Effect": "Deny". The only Allow is the AWS managed RCPFullAWSAccess, attached automatically to every root, OU and account when RCPs are enabled; it can't be detached and lets everything through until you add your own.
  • Principal is always "*": name the callers to exclude with conditions such as aws:PrincipalOrgID or aws:PrincipalArn.
  • Actions: must name a service ("s3:*", not "*"). NotAction and NotPrincipal aren't supported; Resource, NotResource and Condition are.
  • Limits: up to 5,120 characters per RCP, and up to 5 RCPs per root, OU or account, counting RCPFullAWSAccess.

Example 1: block callers from outside the organization

Assume the organization ID is o-a1b2c3d4e5, and the RCP is attached to the Workloads OU. It protects the resources in those accounts (S3 buckets and objects, KMS keys, Secrets Manager secrets and SQS queues), not the use of the services. Your own users keep using S3, KMS, Secrets Manager and SQS as their IAM permissions allow. What the RCP blocks is any request to these resources from a caller outside the organization, even if a bucket policy, key policy or secret policy says that caller is allowed.

deny-outside-callers-rcp.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyCallersOutsideOurOrganization",
      "Effect": "Deny",          // RCPs you write can only deny
      "Principal": "*",          // required in RCPs: applies to every caller
      "Action": [                // requests to resources of these services
        "s3:*",
        "kms:*",
        "secretsmanager:*",
        "sqs:*"
      ],
      "Resource": "*",           // every bucket, key, secret and queue in the OU
      "Condition": {
        // both conditions must be true for the Deny to apply
        "StringNotEqualsIfExists": {
          // true when the caller's account is NOT in our organization
          "aws:PrincipalOrgID": "o-a1b2c3d4e5"
        },
        "BoolIfExists": {
          // true when the caller is NOT an AWS service (CloudTrail, Config...)
          "aws:PrincipalIsAWSService": "false"
        }
      }
    }
  ]
}

The // comments are explanations only; JSON doesn't allow comments, so remove them before using the policy.

How the RCP treats different callers trying to read a secret or an S3 object in account 222222222222:

CallerConditionsResult
A developer role in 222222222222In the organization, so the first condition is false; no DenyThe RCP doesn't block it; the developer's IAM policies and the resource policy decide
A role in another of your accounts, 333333333333Same organization ID; no DenyAllowed if the resource policy and the role's IAM policy allow it
A partner's role in 999999999999, outside the organization, granted access in a bucket policyOutside the organization and not an AWS service; both conditions trueDenied, even though the bucket policy allows it
CloudTrail writing log files to a bucketAn AWS service, so the second condition is false; no DenyAllowed if the bucket policy allows CloudTrail
  • Why two conditions: with the organization check alone, AWS services that act on your behalf (CloudTrail delivering logs, Config writing snapshots) would be blocked, because they aren't principals in your organization.
  • IfExists: if a request doesn't carry the key at all, the condition counts as true, so requests that can't prove they come from your organization are denied rather than let through.
  • Exceptions: a partner that must read one bucket needs an exception, for example an extra condition that skips resources carrying an agreed tag. Design those before attaching the RCP, or the partner's access stops.

Why an RCP, and not an SCP or resource policies

Three tools can each stop part of this. The difference is whose requests they see and who can change them:

OptionStops outside callers?Covers every resource?Can an account admin remove it?
SCPNo. It limits only principals in your member accounts; the partner's account isn't in your organization, so your SCPs never evaluate its requestsNot applicableNo
Bucket, key, secret and queue policiesYes, with the same aws:PrincipalOrgID conditionOnly the resources whose owners add it; a new bucket created tomorrow has noneYes: whoever can edit the resource policy can delete the protection
RCPYes, for every callerYes, every supported resource in the OU, including ones created laterNo; only the management account (or a delegated admin) manages it

Resource policies are still the right tool for granting access, and for rules specific to one resource; the RCP is the ceiling none of them can exceed.

Example 2: HTTPS only, on every S3 bucket

This is the same deny-unless-HTTPS statement many teams put into each bucket policy. As an RCP it applies to every bucket in the OU at once, including buckets created later, and account administrators can't remove it by editing a bucket policy.

s3-https-only-rcp.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "S3OnlyOverHttps",
      "Effect": "Deny",
      "Principal": "*",          // every caller, inside or outside the organization
      "Action": "s3:*",
      "Resource": "*",           // every bucket and object in the OU
      "Condition": {
        "BoolIfExists": {
          // true when the request came over plain HTTP
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
  • Compared with an SCP: an SCP with the same condition would force your users onto HTTPS, but outside callers (a partner, a public website visitor) aren't covered by your SCPs.
  • Compared with a bucket policy: the statement works the same, but only on the buckets that have it, and anyone who can edit the bucket policy can delete it.
  • Before attaching: clients still using plain HTTP, such as an old script or a website served from an S3 website endpoint over HTTP, stop working. CloudTrail data events show which requests arrive without TLS.

Example 3: only your organization can assume your roles

Role trust policies are resource policies too. A mistake such as trusting "AWS": "*" lets anyone assume the role, and no SCP can stop an outside account from calling sts:AssumeRole. This RCP blocks role assumption from outside the organization, except for roles tagged as approved for a vendor:

deny-external-role-assumption-rcp.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAssumeRoleFromOutsideOrganization",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "sts:AssumeRole",   // the role being assumed is the resource
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": {
          // caller isn't in our organization...
          "aws:PrincipalOrgID": "o-a1b2c3d4e5",
          // ...and the role isn't tagged as an approved vendor role
          "aws:ResourceTag/dp:exclude:identity": "true"
        },
        "BoolIfExists": {
          // ...and the caller isn't an AWS service
          "aws:PrincipalIsAWSService": "false"
        }
      }
    }
  ]
}
  • Several keys under one operator are ANDed: the Deny applies only when the caller is outside the organization and the role lacks the exception tag and the caller isn't an AWS service.
  • The exception is controlled centrally: pair the RCP with an SCP that denies iam:TagRole and iam:UntagRole for the dp:exclude:identity key, except for the platform team, so account admins can't exempt their own roles.

Rolling out an RCP safely

  1. Find today's external accessIAM Access Analyzer external access findings list resources already shared outside the organization; each one either needs an exception or is a finding to fix.
  2. Attach to test accounts firstThen to lower OUs, then upwards. AWS strongly recommends not attaching an untested RCP to the root.
  3. Watch for denialsCloudTrail AccessDenied errors on the protected resources show callers the RCP blocked.

Skill

Assuming roles across accounts

Machines (pipelines, tools, Lambda functions) work across accounts by assuming a role in the target account. For example, assume a Security Tooling account (333333333333) whose automation must read every account's configuration:

security-audit-role.yml (deployed to every account by StackSets) 
SecurityAuditRole:
  Type: AWS::IAM::Role
  Properties:
    RoleName: SecurityAuditRole
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:   # only this role may assume it
            AWS: arn:aws:iam::333333333333:role/SecurityAutomation
          Action: sts:AssumeRole
          Condition:
            StringEquals:   # and only from inside our organization
              aws:PrincipalOrgID: o-a1b2c3d4e5
    ManagedPolicyArns:
      - arn:aws:iam::aws:policy/SecurityAudit                                # read-only security view

The SecurityAutomation role in 333333333333 also needs an IAM policy allowing sts:AssumeRole on arn:aws:iam::*:role/SecurityAuditRole. Cross-account access always needs both sides: the caller's permission and the target role's trust policy.

  • Third parties: when a vendor assumes a role in your account, require an external ID in the trust policy (sts:ExternalId). This prevents the confused deputy problem, where someone tricks the vendor into using your role.
  • Session duration: 1 hour by default and up to 12 hours, set per role. When one assumed role assumes another (role chaining), the session is limited to 1 hour.
  • Auditing: CloudTrail records AssumeRole calls in both accounts. Setting a source identity or session name makes them traceable to a person or job.
Skill

Human access with IAM Identity Center

People shouldn't have IAM users in each account. IAM Identity Center gives one sign-in for all accounts:

  • Identity source: Identity Center's own directory, Active Directory, or an external identity provider (Okta, Microsoft Entra ID) through SAML 2.0, with users and groups synchronized automatically by SCIM.
  • Permission set: a template of policies (for example, ReadOnly or DeveloperAccess) that Identity Center turns into a role in each assigned account.
  • Assignment: group + permission set + account. Assigning "Developers" to "DeveloperAccess" in 40 accounts creates the role in all 40.
  • Attribute-based access control: pass user attributes (such as team or costCenter) as session tags. Policies can then compare aws:PrincipalTag/team with aws:ResourceTag/team, so one permission set serves every team.

"Employees sign in with the corporate identity provider and need different access in different accounts" points to IAM Identity Center with an external IdP, SCIM, and permission sets assigned to groups. Creating IAM users per account is wrong.

Detective investigates; it doesn't detect threats on its own. GuardDuty findings are one of its main inputs, so enable GuardDuty alongside it. Older documentation required GuardDuty to run for 48 hours before Detective could be enabled; that prerequisite is no longer listed, but older practice questions may still assume it.

Organization trail

org-trail.yml (management or delegated administrator account) 
OrganizationTrail:
  Type: AWS::CloudTrail::Trail
  Properties:
    TrailName: org-trail
    IsOrganizationTrail: true                # every member account, including future ones
    IsMultiRegionTrail: true                 # every Region
    IncludeGlobalServiceEvents: true         # IAM, STS and other global events
    EnableLogFileValidation: true            # detect tampering with digest files
    S3BucketName: example-org-log-archive     # bucket in the Log Archive account
    KMSKeyId: arn:aws:kms:eu-west-1:444444444444:key/1234abcd-12ab-34cd-56ef-1234567890ab
    IsLogging: true

Member accounts can see the organization trail but can't modify or delete it.

From finding to automatic response

Detective controls become much stronger when findings trigger action automatically:

  1. A service raises a findingFor example, GuardDuty detects an EC2 instance talking to a known command-and-control server.
  2. Findings are centralizedThe finding appears in the delegated administrator account and in Security Hub.
  3. EventBridge matches itA rule filters on the finding type or severity (pattern below).
  4. Automation respondsA Lambda function or Systems Manager Automation runbook isolates the instance (swaps its security group), snapshots its volume for forensics, or disables an exposed access key.
  5. People are toldSNS or chat notifications go to the security team, who investigate in Detective.
eventbridge-pattern.json (high-severity GuardDuty findings) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }]
  }
}

AWS Config at organization scale

  • Aggregator: collects configuration and compliance data from all accounts and Regions into the audit account, for one view.
  • Organization rules and conformance packs: deploy from the delegated administrator to every account at once. A conformance pack is a collection of rules and remediation actions deployed as one unit, for example an operational best practices pack for PCI DSS.
  • Remediation: attach a Systems Manager Automation document to a rule, for example AWS-EnableS3BucketEncryption, and set it to run automatically on non-compliant resources.
  • "Prevent" or "must not be possible": a preventive control, such as an SCP, an RCP or a Control Tower preventive control.
  • "Detect", "report" or "show compliance": a detective control, such as Config rules or Security Hub.
  • "Before the resource is created": a proactive control, such as a CloudFormation Hook or a Control Tower proactive control.

Key takeaways

  • Organize by OU: Security (Log Archive, Security Tooling), Infrastructure, Workloads, Sandbox, Policy Staging, Suspended. Keep workloads out of the management account; SCPs don't apply to it.
  • Vend accounts with Control Tower Account Factory, extended by AFC blueprints, CfCT or AFT. Apply baselines with service-managed StackSets and the CreateManagedAccount lifecycle event.
  • Invited accounts don't get OrganizationAccountAccessRole. Enrolling them in Control Tower needs AWSControlTowerExecution.
  • Control Tower controls are preventive (SCPs), detective (Config rules) or proactive (Hooks). Editing its SCPs directly causes drift.
  • SCPs set maximum permissions, never grant, affect member root users, skip the management account and service-linked roles. Exempt global services in Region-deny SCPs.
  • Cross-account roles need the caller's permission and the target's trust policy; use aws:PrincipalOrgID and external IDs for third parties.
  • People use IAM Identity Center with permission sets assigned to groups, ideally from an external IdP with SCIM.
  • Security services: delegated administrator in Security Tooling, auto-enable for new accounts, organization CloudTrail trail, Config aggregator and conformance packs, findings to EventBridge for automatic response. Detective investigates using GuardDuty findings.
