Overview

Task statement 1.4

Implement deployment strategies for instance, container, and serverless environments.

This task is about the moment a release meets users. Questions give you a platform and a constraint (no downtime, lowest cost, fastest rollback, test with a small share of users first) and ask which strategy or configuration meets it. Others describe a deployment that failed and ask why.

Deployment methodologies for various platforms

Knowledge

Strategy vocabulary

The same names appear across every platform. Know what each one costs and how fast it rolls back.

StrategyHow it worksDowntimeRollbackExtra cost
All at onceUpdate every target at the same timeYesSlow: redeploy the old versionNone
RollingUpdate targets in batchesNo, but capacity drops during each batchSlow: roll back batch by batchNone
Rolling with additional batchAdd a new batch first, then roll, so capacity stays fullNoSlowOne extra batch, briefly
ImmutableLaunch new targets with the new version, then remove the old onesNoFast: delete the new targetsDouble capacity, briefly
Blue/greenRun a full new environment (green) next to the old one (blue), then switch trafficNoFastest: switch traffic backDouble capacity until blue is removed
CanarySend a small percentage of traffic to the new version, wait, then send the restNoFast: only the canary share is affectedSmall
LinearShift traffic in equal steps at fixed intervalsNoFastSmall
Knowledge

Amazon EC2 and Auto Scaling groups

There are three common ways to deploy to instances:

MethodWhat changesBest for
CodeDeploy in-placeThe agent replaces the application on existing instances, a batch at a timeFast application-only releases on long-lived instances
CodeDeploy blue/greenNew instances (often a copy of the Auto Scaling group) get the new version, the load balancer switches to them, and the old instances are terminatedZero downtime with instant rollback
New AMI plus instance refreshBake the release into an AMI, update the launch template, then replace instancesImmutable infrastructure; OS and app updates together

CodeDeploy deployment configurations for EC2

  • CodeDeployDefault.AllAtOnce: every instance at once (at least one must succeed).
  • CodeDeployDefault.HalfAtATime: up to half the instances at a time.
  • CodeDeployDefault.OneAtATime: one instance at a time; slowest and safest.
  • Custom: a minimum number or percentage of healthy hosts that must stay in service.

Auto Scaling group instance refresh

An instance refresh replaces instances in rolling batches so they pick up a new launch template version (a new AMI or user data). Its main settings:

  • Minimum healthy percentage: how much capacity must stay in service (default 90%). Maximum healthy percentage above 100% launches replacements before terminating, so capacity never drops.
  • Instance warmup: how long a new instance runs before it counts as healthy.
  • Checkpoints: pause at chosen percentages (for example, 20% and 50%) so you can check the release.
  • Skip matching: leave instances that already use the desired configuration alone.
  • Auto rollback: return to the previous launch template version if the refresh fails or a CloudWatch alarm goes into ALARM.

CloudFormation update policies for Auto Scaling groups

When CloudFormation changes an Auto Scaling group's launch template, the UpdatePolicy decides how instances are replaced:

web-asg.yml 
WebAsg:
  Type: AWS::AutoScaling::AutoScalingGroup
  CreationPolicy:
    ResourceSignal: { Count: 2, Timeout: PT15M }    # wait for 2 instances to report success
  UpdatePolicy:
    AutoScalingRollingUpdate:                     # rolling: replace in batches
      MinInstancesInService: 2
      MaxBatchSize: 1
      PauseTime: PT10M
      WaitOnResourceSignals: true                # each new instance must signal success
  Properties:
    MinSize: "2"
    MaxSize: "6"
    LaunchTemplate:
      LaunchTemplateId: !Ref WebLaunchTemplate
      Version: !GetAtt WebLaunchTemplate.LatestVersionNumber
    VPCZoneIdentifier: [!Ref SubnetA, !Ref SubnetB]

Each instance's user data runs the application setup, then reports the result:

/opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackName} --resource WebAsg --region ${AWS::Region}
  • AutoScalingRollingUpdate: replaces instances in batches inside the same group.
  • AutoScalingReplacingUpdate with WillReplace: true: creates a whole new Auto Scaling group, then deletes the old one once the new one succeeds. This is immutable, and rollback simply keeps the old group.

"The stack update fails with Received 0 SUCCESS signals" means the instances never ran cfn-signal before the timeout. Usual causes: the user data script failed or never reached the signal line, the instance has no route to the CloudFormation endpoint, or the timeout is too short for the setup.

AWS Elastic Beanstalk deployment policies

Elastic Beanstalk names its options directly, and the exam often lists them as answers:

PolicyWhat happensChoose it when
All at onceEvery instance updated together; brief outageDevelopment environments; speed matters most
RollingBatches taken out of service and updated; capacity dropsNo extra cost and reduced capacity is acceptable
Rolling with additional batchA new batch is launched first, so full capacity is keptFull capacity is needed, at a small extra cost
ImmutableA temporary Auto Scaling group with new instances; they join only when healthy, then the old ones are removedSafest in-place option; fast rollback by terminating new instances
Traffic splittingNew instances receive a set percentage of client traffic for an evaluation period (canary)Test the new version on real traffic first
Blue/green (swap environment URLs)Deploy to a cloned environment, then swap the CNAMEsPlatform or major changes; instant switch back

Blue/green on Elastic Beanstalk isn't a deployment policy. It's two environments plus a CNAME swap. Because it's DNS-based, some clients keep reaching the old environment until DNS caches expire. If the database is created inside the Beanstalk environment, it's tied to that environment's lifecycle; decouple it (create RDS separately) before using blue/green.

Knowledge

Amazon ECS

Every ECS release is a new task definition revision (usually a new image tag). How the service moves to it depends on its deployment controller:

ControllerStrategyKey settings
ECS (default)Rolling updateminimumHealthyPercent, maximumPercent, circuit breaker, deployment alarms
CODE_DEPLOYBlue/green with canary, linear or all-at-once traffic shiftingTwo target groups, production and test listeners, CodeDeploy deployment configuration
EXTERNALAny strategy run by a third-party tool through task setsManaged by the external tool
ecs-service.yml (rolling update) 
OrdersService:
  Type: AWS::ECS::Service
  Properties:
    Cluster: prod
    TaskDefinition: !Ref OrdersTaskDefinition
    DesiredCount: 4
    DeploymentConfiguration:
      MinimumHealthyPercent: 100       # never drop below 4 running tasks
      MaximumPercent: 200              # may run up to 8 tasks during the deployment
      DeploymentCircuitBreaker:
        Enable: true                    # stop if new tasks keep failing to start
        Rollback: true                  # and return to the last working revision
      Alarms:
        AlarmNames: [orders-5xx-high]
        Enable: true
        Rollback: true                  # roll back if this alarm fires during deployment
  • minimumHealthyPercent and maximumPercent: 100/200 keeps full capacity (new tasks start before old ones stop). 50/100 needs no spare capacity but halves it during the update.
  • Circuit breaker: detects tasks that fail to reach a steady state (crashing containers, failed health checks) and optionally rolls back.
  • Deployment alarms: watch application metrics such as 5xx errors and roll back even when the tasks themselves are "healthy".

Amazon ECS added built-in blue/green deployments in 2025. The exam guide predates this, so expect ECS blue/green questions to assume CodeDeploy (shown in the blue/green section below).

Knowledge

Amazon EKS

On EKS, Kubernetes does the deployment. A Deployment object rolls pods to a new image:

orders-deployment.yml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
spec:
  replicas: 6
  strategy:
    type: RollingUpdate               # or Recreate: stop all, then start all
    rollingUpdate:
      maxSurge: 2                     # up to 2 extra pods during the rollout
      maxUnavailable: 0               # never fewer than 6 ready pods
  selector:
    matchLabels: { app: orders }
  template:
    metadata:
      labels: { app: orders }
    spec:
      containers:
        - name: web
          image: 111111111111.dkr.ecr.us-east-1.amazonaws.com/orders:v1.4.2
          readinessProbe:              # a pod gets traffic only once this passes
            httpGet: { path: /health, port: 8080 }
  • Rollback: kubectl rollout undo deployment/orders returns to the previous ReplicaSet.
  • Blue/green: run two Deployments (orders-blue, orders-green) and switch the Service's selector, or use weighted target groups through the AWS Load Balancer Controller.
  • Canary: weighted routing at the load balancer or service mesh, or progressive delivery tools such as Argo Rollouts or Flagger.
  • From a pipeline: CodeBuild runs kubectl apply or helm upgrade, or a GitOps tool (Argo CD, Flux) syncs manifests from Git. The CodeBuild role must be granted access to the cluster with an EKS access entry (or the older aws-auth ConfigMap).

"CodeBuild has the IAM permission eks:DescribeCluster, but kubectl returns Unauthorized" means the role has no Kubernetes permissions inside the cluster. IAM alone isn't enough: add an access entry with an access policy for the role.

Knowledge

AWS Lambda

  • Version: an immutable snapshot of the function's code and configuration (1, 2, 3…). $LATEST is the only mutable version.
  • Alias: a named pointer (for example, live) to a version. Callers invoke the alias, never a version number.
  • Weighted alias: an alias can send a percentage of invocations to a second version. That's the mechanism behind canary and linear deployments.

CodeDeploy shifts the alias weight for you. Its configurations:

  • Canary: CodeDeployDefault.LambdaCanary10Percent5Minutes (also 10, 15 and 30 minutes): 10% first, then all traffic after the wait.
  • Linear: CodeDeployDefault.LambdaLinear10PercentEvery1Minute (also every 2, 3 and 10 minutes): 10% more at each interval.
  • All at once: CodeDeployDefault.LambdaAllAtOnce.

The easiest way to set this up is AWS SAM:

template.yml (SAM) 
OrdersFunction:
  Type: AWS::Serverless::Function
  Properties:
    CodeUri: src/
    Handler: app.handler
    Runtime: python3.12
    AutoPublishAlias: live                    # publish a version and point "live" at it
    DeploymentPreference:
      Type: Canary10Percent5Minutes            # CodeDeploy shifts the alias
      Alarms:
        - !Ref OrdersErrorsAlarm                # roll back if errors rise
      Hooks:
        PreTraffic: !Ref PreTrafficCheck        # runs before any traffic shifts
        PostTraffic: !Ref PostTrafficCheck      # runs after all traffic has shifted
  • Hook functions: each one must call codedeploy:PutLifecycleEventHookExecutionStatus with Succeeded or Failed.
  • API Gateway: a stage can also run a canary release (a percentage of requests goes to a canary deployment of the API), which is useful when the API definition itself changes.

Application storage patterns

Knowledge

Immutable and blue/green deployments throw compute away. Anything the application must keep has to live outside the instance or container. Where it should go depends on how it's used:

StorageScopeSurvives replacement?Use it for
Instance storeOne instanceNo: lost on stop or terminationCaches and scratch data only
Amazon EBSOne instance, one Availability ZoneOnly if not deleted on termination; otherwise use snapshotsBoot volumes, single-instance databases, low-latency block storage
Amazon EFSMany instances, containers and Lambda functions across AZsYesShared files: uploaded content, CMS media, shared configuration
Amazon S3Regional, accessed through the APIYesStatic assets, user uploads, artifacts, backups, data lakes
Databases (RDS, DynamoDB, ElastiCache)Managed serviceYesApplication data and sessions
  • Make compute stateless: sessions in ElastiCache or DynamoDB, uploads in S3 or EFS, data in a database. Then any instance can be replaced at any time.
  • Containers: ECS and EKS tasks lose their local storage when replaced (Fargate gives 20 GiB by default, configurable up to 200 GiB, deleted with the task). Mount EFS for anything that must persist or be shared.
  • Lambda: /tmp is per execution environment (512 MB to 10 GB) and temporary. Use S3 or a mounted EFS file system for persistent or shared files.
  • Static websites: deploy new files to S3 (ideally in a versioned prefix), then invalidate the CloudFront cache or switch the origin path.

"After a blue/green deployment, users lost files they had uploaded" means uploads were written to the instance's local disk or EBS volume. Move them to S3 or EFS.

EBS volumes are tied to one Availability Zone. "Several instances in different AZs must read and write the same files" points to EFS, not EBS (EBS Multi-Attach works only within one AZ, with io1 or io2 volumes and cluster-aware software).

Mutable compared with immutable deployment patterns

Knowledge
MutableImmutable
What happensExisting servers are changed in place: new code, patches, configurationServers are never changed; new ones are built from a new image, and old ones are discarded
ExamplesCodeDeploy in-place, Systems Manager patching, Beanstalk rolling, configuration management toolsNew AMI plus instance refresh, Beanstalk immutable, blue/green, new ECS task definitions, Lambda versions
SpeedFaster: only the changed part is updatedSlower: whole instances are launched
ConsistencyServers drift apart over time (configuration drift)Every server matches its image exactly
RollbackRedeploy the old version, which may fail the same wayPoint traffic back to the old, untouched servers
Failure riskA half-applied update can leave a server brokenA failed launch never takes traffic
RequirementsAgents and access to running serversStateless compute, image pipelines, capacity for two versions

"Servers configured the same way slowly became different" or "a failed update left instances in an unknown state" points to immutable infrastructure: bake an AMI or image and replace instances.

Tools and services available for distributing code

Knowledge
ToolDistributesTypical use
AWS CodeDeployApplication revisions to EC2, on-premises servers, ECS and LambdaControlled in-place, blue/green, canary and linear releases with automatic rollback
EC2 Image BuilderGolden AMIs and container imagesBake OS, agents and the application into an image, then roll it out with an instance refresh

Bake or bootstrap?

  • Bake: put everything into the AMI with Image Builder. Instances start fast and identically, which suits Auto Scaling. The cost is rebuilding the image for every change.
  • Bootstrap: start from a base AMI and install at launch with user data, Systems Manager or CodeDeploy. Images stay generic, but launches are slower and can fail if a download fails.
  • Hybrid (common): bake the OS, patches and agents; deploy the application with CodeDeploy or on container images.

"New instances take 15 minutes to become healthy during scale-out" points to baking more into the AMI, so less runs at launch.

Example: EC2 instance role for CodeDeploy

instance-role.yml 
WebInstanceRole:
  Type: AWS::IAM::Role
  Properties:
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - { Effect: Allow, Principal: { Service: ec2.amazonaws.com }, Action: sts:AssumeRole }
    ManagedPolicyArns:
      - arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore       # lets Systems Manager install and update the agent
    Policies:
      - PolicyName: read-revisions
        PolicyDocument:
          Version: "2012-10-17"
          Statement:
            - Effect: Allow
              Action: [s3:GetObject, s3:GetObjectVersion]
              Resource: arn:aws:s3:::tooling-artifacts/*                # where revisions are stored
            - Effect: Allow
              Action: kms:Decrypt
              Resource: arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab
WebInstanceProfile:
  Type: AWS::IAM::InstanceProfile
  Properties:
    Roles: [!Ref WebInstanceRole]

Mixing up the ECS task execution role and the task role is a classic distractor. "The task fails with CannotPullContainerError" or "the secret can't be injected" means the execution role. "The application gets AccessDenied calling DynamoDB" means the task role.

Configuring deployment agents (CodeDeploy agent)

Skill

CodeDeploy deployments to EC2 and on-premises servers are carried out by the CodeDeploy agent, a service running on each instance. ECS and Lambda deployments need no agent. The agent polls CodeDeploy over HTTPS (port 443, outbound only), downloads the revision and runs the AppSpec hooks.

Installing and keeping it updated

  • Systems Manager (recommended): install the AWSCodeDeployAgent package with Distributor, and keep it installed and updated with a State Manager association. The CodeDeploy console can set this up for a deployment group. The instance needs the SSM Agent and AmazonSSMManagedInstanceCore.
  • User data or the AMI: run the installer at launch, or bake the agent into the golden AMI.

Network access

  • Endpoints the agent must reach: the CodeDeploy endpoints and S3 (for the revision).
  • Private subnets without internet access: use VPC endpoints com.amazonaws.<region>.codedeploy and com.amazonaws.<region>.codedeploy-commands-secure, plus an S3 gateway endpoint.

Files worth knowing

File (Linux)Contains
/var/log/aws/codedeploy-agent/codedeploy-agent.logThe agent's own log: polling, errors, credentials problems
/opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.logOutput of your hook scripts for each deployment
/etc/codedeploy-agent/conf/codedeployagent.ymlAgent settings, such as :max_revisions: (how many old revisions to keep on disk; default 5)

On-premises servers

  1. Give the server an identityUse an IAM role assumed through temporary credentials (recommended), or an IAM user's access keys.
  2. Register itaws deploy register-on-premises-instance (or register), then add tags.
  3. Install the agent and configure itWrite the credentials and Region in /etc/codedeploy-agent/conf/codedeploy.onpremises.yml.
  4. Target itA deployment group selects on-premises servers by their tags, just like EC2 instances.

Troubleshooting deployment issues

Skill

Start from the symptom, then check the most likely cause first.

CodeDeploy on EC2 and on-premises

SymptomLikely causeFix
Deployment stays Pending, then times out; no lifecycle events on the instancesAgent not installed or not running, missing instance profile, or no network route to CodeDeployInstall or start the agent, attach the instance profile, add a NAT gateway or VPC endpoints
Fails at DownloadBundleInstance profile can't read the S3 revision or decrypt itAdd s3:GetObject and kms:Decrypt
Fails at ApplicationStopThe previous revision's stop script is brokenFix the script on the instance, or redeploy with --ignore-application-stop-failures

To find why a CodeDeploy deployment failed, open the deployment, then the failed instance's lifecycle events. The failing hook and its script output tell you where to look next.

Using different deployment methods (blue/green, canary)

Skill

Ways to switch traffic

Blue/green and canary are both about where traffic goes. The switching point decides how fast and how precisely you can move it:

Switching pointHowWatch out for
Route 53Weighted records shift a percentage of DNS answers, or one record is repointedDNS caching: clients keep the old answer until the TTL expires. Lower the TTL in advance
Load balancerALB weighted target groups on a listener rule, or swap which target group or Auto Scaling group is attachedInstant and precise; both versions sit behind one load balancer
Elastic BeanstalkSwap environment URLs (CNAME)DNS-based, so the same caching delay applies
CodeDeploy (EC2, ECS, Lambda)Moves traffic for you according to the deployment configurationRolls back automatically on failure or alarm
Lambda aliasWeighted alias routing between two versionsUsually managed by CodeDeploy through SAM
API GatewayStage canary settings send a percentage of requests to a canary deploymentPromote the canary when satisfied
CloudFrontContinuous deployment: a staging distribution receives a share of traffic, then is promotedTests configuration changes to a distribution safely

"After switching DNS to the green environment, some users still reach blue for hours" is DNS caching. The fix is a lower TTL set well before the switch, or switching at the load balancer instead.

ECS blue/green with CodeDeploy, end to end

Assume an ECS service orders in cluster prod behind an ALB with two listeners: production on port 443, and a test listener on port 8443. The service is created with DeploymentController: CODE_DEPLOY.

codedeploy-ecs.yml 
OrdersDeploymentGroup:
  Type: AWS::CodeDeploy::DeploymentGroup
  Properties:
    ApplicationName: !Ref OrdersApplication              # ComputePlatform: ECS
    ServiceRoleArn: !GetAtt CodeDeployEcsRole.Arn       # AWSCodeDeployRoleForECS
    DeploymentConfigName: CodeDeployDefault.ECSCanary10Percent5Minutes
    DeploymentStyle:
      DeploymentType: BLUE_GREEN
      DeploymentOption: WITH_TRAFFIC_CONTROL
    BlueGreenDeploymentConfiguration:
      DeploymentReadyOption:
        ActionOnTimeout: CONTINUE_DEPLOYMENT             # or STOP_DEPLOYMENT to wait for a manual go-ahead
      TerminateBlueInstancesOnDeploymentSuccess:
        Action: TERMINATE
        TerminationWaitTimeInMinutes: 15                # keep blue for a quick rollback window
    ECSServices:
      - { ClusterName: prod, ServiceName: orders }
    LoadBalancerInfo:
      TargetGroupPairInfoList:
        - TargetGroups: [{ Name: orders-blue }, { Name: orders-green }]
          ProdTrafficRoute: { ListenerArns: [!Ref ProdListener] }   # port 443
          TestTrafficRoute: { ListenerArns: [!Ref TestListener] }   # port 8443
    AutoRollbackConfiguration:
      Enabled: true
      Events: [DEPLOYMENT_FAILURE, DEPLOYMENT_STOP_ON_ALARM]
    AlarmConfiguration:
      Enabled: true
      Alarms: [{ Name: orders-5xx-high }]

The appspec.yml for this deployment names the service's container and port, and the hook that tests green:

appspec.yml 
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: "<TASK_DEFINITION>"     # replaced with the new revision by the pipeline
        LoadBalancerInfo:
          ContainerName: web
          ContainerPort: 8080
Hooks:
  - AfterAllowTestTraffic: RunSmokeTests     # Lambda function that tests port 8443

What happens during the deployment:

  1. Create the green task setCodeDeploy starts tasks from the new task definition and registers them with orders-green.
  2. Route test traffic to greenThe test listener (8443) points at green while production (443) still points at blue.
  3. Run the test hookAfterAllowTestTraffic runs smoke tests against 8443. A Failed result stops the deployment before users see anything.
  4. Shift production traffic10% of production traffic goes to green; after 5 minutes the remaining 90% follows.
  5. Watch the alarmIf orders-5xx-high fires during the deployment, CodeDeploy reroutes all traffic back to blue.
  6. Remove blueAfter the 15-minute wait, the blue task set is terminated. Until then, rollback is instant.

Choosing between configurations from the scenario:

  • "Test with real users before everyone gets it": canary.
  • "Increase traffic gradually": linear.
  • "Switch instantly and be able to switch back instantly": blue/green with all-at-once traffic shifting, plus a termination wait time.
  • "Test the new version before any production traffic": the ECS test listener with AfterAllowTestTraffic, or a Lambda PreTraffic hook.

Key takeaways

  • Know the strategy table: all at once, rolling, rolling with additional batch, immutable, blue/green, canary and linear, and each one's downtime, rollback speed and cost.
  • EC2: CodeDeploy in-place or blue/green, or a new AMI with an instance refresh (minimum healthy percentage, checkpoints, auto rollback). CloudFormation uses AutoScalingRollingUpdate or AutoScalingReplacingUpdate with cfn-signal.
  • Elastic Beanstalk: six policies; blue/green there means two environments and a CNAME swap.
  • ECS: rolling updates with circuit breaker and deployment alarms, or CodeDeploy blue/green with two target groups and a test listener.
  • EKS: Deployment rolling updates (maxSurge, maxUnavailable, readiness probes). Pipelines need an EKS access entry, not just IAM.
  • Lambda: versions and weighted aliases; SAM AutoPublishAlias plus DeploymentPreference with alarms and hooks.
  • Make compute stateless: S3 or EFS for files, databases for data. Local disks and EBS don't survive immutable replacement.
  • Instance profile reads revisions from S3. ECS execution role pulls images and injects secrets; the task role is for the app's own API calls.
  • The CodeDeploy agent polls over HTTPS. Install it with Systems Manager, and give private subnets the CodeDeploy and S3 endpoints.
  • Troubleshoot from lifecycle events: Pending means agent or network, DownloadBundle means S3 permissions, ApplicationStop means the old revision's script.
