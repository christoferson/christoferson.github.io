Overview

Task statement 4.2

Audit, monitor, and analyze logs and metrics to detect issues.

Collecting telemetry is only half the job; the other half is noticing when it says something is wrong. This task tests whether you can alarm on the right signals, detect unusual behavior without fixed thresholds, find risky changes and vulnerabilities, trace slow requests to their cause, and analyze logs at any scale. Typical scenarios: "latency varies by time of day, so a static alarm is noisy", "who deleted this security group?", "API Gateway requests are slow but Lambda looks fine", or "find the top sources of rejected traffic last month".

Anomaly detection alarms (CloudWatch anomaly detection)

Knowledge

A static threshold ("alarm above 500 ms") is wrong half the time when a metric follows a daily or weekly pattern: too sensitive at peak, too lax at night. Anomaly detection learns the metric's normal behavior and alarms when it leaves an expected band.

  • Model: trained on up to two weeks of the metric's history, including hourly, daily and weekly seasonality and trends. It keeps updating as new data arrives.
  • Band: the expected range, with a width you set in standard deviations (for example, 2). A wider band means fewer alarms.
  • Alarm direction: above the band, below it, or outside it either way. "Below" catches drops, such as orders suddenly falling to zero.
  • Exclusions: exclude known unusual periods (an outage, a sale) so they don't distort the model.
latency-anomaly-alarm.yml 
CheckoutLatencyAnomaly:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: checkout-latency-anomaly
    ComparisonOperator: GreaterThanUpperThreshold      # alarm only above the band
    EvaluationPeriods: 3
    ThresholdMetricId: band                             # the band is the threshold
    TreatMissingData: notBreaching
    Metrics:
      - Id: m1
        MetricStat:
          Metric:
            Namespace: AWS/ApplicationELB
            MetricName: TargetResponseTime
            Dimensions: [{ Name: LoadBalancer, Value: app/orders-alb/50dc6c495c0c9188 }]
          Period: 300
          Stat: p99
      - Id: band
        Expression: ANOMALY_DETECTION_BAND(m1, 2)        # 2 standard deviations wide
    AlarmActions: [!Ref OpsTopic]

Related machine learning features

  • CloudWatch Logs anomaly detection: learns the usual log patterns in a log group and flags new or unusual ones (for example, a never-seen error message).
  • Logs pattern analysis: groups similar log lines in Logs Insights results so you can see what's common.
  • Amazon DevOps Guru: analyzes metrics, events and logs across an application and raises insights about unusual behavior with likely causes.

"The metric has a strong daily pattern and static thresholds cause false alarms" points to a CloudWatch anomaly detection alarm.

Amazon Inspector and common assessment templates

Knowledge

Amazon Inspector finds software vulnerabilities and unintended network exposure, continuously and automatically:

ResourceWhat Inspector checks
EC2 instancesOS and language packages with known CVEs, using the SSM Agent (or agentless scanning of EBS snapshots); network reachability (ports reachable from the internet); CIS benchmark assessments on demand or on a schedule
ECR container imagesOS and language packages, on push and again whenever new CVEs are published (ECR enhanced scanning)
Lambda functionsVulnerable dependencies in the package (standard scanning), and code flaws such as injection or hard-coded secrets (code scanning)
  • Findings: each one has a severity and an Inspector risk score that adjusts the CVE score for your environment (for example, whether the instance is reachable from the internet).
  • Where findings go: to EventBridge and Security Hub for alerting and automation. Suppression rules hide accepted risks.
  • Organization-wide: a delegated administrator enables Inspector for all accounts and auto-enables new ones.
  • Remediation: patch with Systems Manager Patch Manager, or rebuild images with fixed packages.

Inspector Classic assessment templates

The exam guide's "assessment templates" come from Amazon Inspector Classic superseded by the current Inspector. There, you created an assessment target (instances selected by tag) and an assessment template with rules packages, then ran it on a schedule. The current Inspector replaces each rules package with continuous scanning:

Classic rules packageCurrent Inspector equivalent
Common Vulnerabilities and ExposuresContinuous package vulnerability scanning
CIS Operating System Security Configuration BenchmarksCIS scans for EC2
Network ReachabilityNetwork reachability findings
Security Best PracticesCIS scans, and Security Hub controls

"Automatically scan every new container image and every EC2 instance for CVEs, and rescan when new CVEs are published" points to Amazon Inspector (with ECR enhanced scanning). Inspector checks software; AWS Config checks resource configuration; GuardDuty detects threats in activity.

AWS Config rules

Knowledge

AWS Config records the configuration of resources over time, and rules evaluate whether each resource is COMPLIANT or NON_COMPLIANT.

ChoiceOptions
Rule typeManaged rules (hundreds, written by AWS); custom Lambda rules (your code); custom policy rules (written in CloudFormation Guard)
TriggerConfiguration changes (evaluate when a matching resource changes) or periodic (every 1, 3, 6, 12 or 24 hours)
Evaluation modeDetective (deployed resources) or proactive (check a resource definition before deployment)
ResponseRemediation actions (SSM Automation documents), manual or automatic
PackagingConformance packs: rules and remediation deployed together, across an organization

Commonly used managed rules

  • s3-bucket-public-read-prohibited, s3-bucket-server-side-encryption-enabled
  • encrypted-volumes, rds-storage-encrypted
  • restricted-ssh, vpc-sg-open-only-to-authorized-ports
  • iam-root-access-key-check, root-account-mfa-enabled, access-keys-rotated
  • cloudtrail-enabled, multi-region-cloudtrail-enabled
  • rds-multi-az-support, required-tags, approved-amis-by-id

Example: detect and fix open SSH automatically

restricted-ssh.yml 
RestrictedSshRule:
  Type: AWS::Config::ConfigRule
  Properties:
    ConfigRuleName: restricted-ssh
    Source:   # managed rule
      Owner: AWS
      SourceIdentifier: INCOMING_SSH_DISABLED
    Scope:
      ComplianceResourceTypes: [AWS::EC2::SecurityGroup]

RestrictedSshRemediation:
  Type: AWS::Config::RemediationConfiguration
  Properties:
    ConfigRuleName: !Ref RestrictedSshRule
    TargetType: SSM_DOCUMENT
    TargetId: AWS-DisablePublicAccessForSecurityGroup   # removes 0.0.0.0/0 on ports 22 and 3389
    Automatic: true
    MaximumAutomaticAttempts: 3
    RetryAttemptSeconds: 60
    Parameters:
      GroupId:   # the non-compliant security group
        ResourceValue: { Value: RESOURCE_ID }
      AutomationAssumeRole:
        StaticValue:
          Values: [!GetAtt ConfigRemediationRole.Arn]

AWS Config rules detect problems after resources exist (unless you use proactive mode). They don't block the change. To prevent it, use SCPs, CloudFormation Hooks or IAM; to fix it, add remediation.

This event shows a role opening SSH to the internet:

{
  "eventTime": "2026-10-28T09:14:03Z",
  "eventSource": "ec2.amazonaws.com",                 // which service
  "eventName": "AuthorizeSecurityGroupIngress",       // which API
  "awsRegion": "eu-west-1",
  "sourceIPAddress": "203.0.113.25",
  "userAgent": "aws-cli/2.17.0",
  "userIdentity": {
    "type": "AssumedRole",
    "arn": "arn:aws:sts::222222222222:assumed-role/DeveloperAccess/jane.doe@example.com",
    "sessionContext": {
      "sessionIssuer": {
        "arn": "arn:aws:iam::222222222222:role/DeveloperAccess"
      }
    }
  },
  "requestParameters": {
    "groupId": "sg-0abc1234",
    "ipPermissions": { "items": [{ "fromPort": 22, "toPort": 22,
      "ipRanges": { "items": [{ "cidrIp": "0.0.0.0/0" }] } }] }
  },
  "errorCode": null,                                  // present (for example AccessDenied) if the call failed
  "readOnly": false
}
  • userIdentity: who; for assumed roles, the session name often identifies the person or job.
  • eventSource and eventName: what was called.
  • requestParameters: exactly what was asked for.
  • errorCode: whether it was denied or failed; repeated AccessDenied errors are a common sign of probing.

Where to look

  • Event history: management events from the last 90 days, searchable in the console, free.
  • Trail to S3: long-term storage; files typically arrive within about 5 minutes. Query with Athena.
  • Trail to CloudWatch Logs: metric filters and alarms, and Logs Insights queries.
  • EventBridge: receives management events in near real time, so rules can react immediately (for example, to StopLogging).
  • CloudTrail Lake closed to new customers since May 31, 2026: a managed event data store queried with SQL, with retention up to 10 years. Existing customers can keep using it; otherwise query trail logs in S3 with Athena.

"CloudTrail shows who created the bucket but not who downloaded the file" means S3 data events weren't enabled. Management events don't include object-level reads.

Building CloudWatch dashboards and Amazon Quick Sight visualizations

Skill

CloudWatch dashboards

  • Widgets: line and stacked graphs, numbers, gauges, alarm status, Logs Insights query results, text, and Metrics Insights queries.
  • Several accounts and Regions: one dashboard can show metrics from many Regions and, with cross-account observability, many accounts.
  • Automatic dashboards: ready-made per service; Container Insights, Lambda Insights and Application Signals add their own.
  • Variables: one dashboard with a drop-down to switch between, for example, instances or environments.
  • Sharing: with specific email addresses, through single sign-on, or publicly.

Amazon Quick Sight

Quick Sight is a business intelligence service for interactive dashboards over larger or longer-term data, for audiences beyond the operations team.

  • Data sources: Athena (and so anything in S3: CloudTrail, ALB logs, Config snapshots, Cost and Usage Reports), Redshift, RDS, OpenSearch and others.
  • SPICE: its in-memory engine, which imports data for fast dashboards, refreshed on a schedule.
  • Typical DevOps uses: monthly compliance trends, deployment frequency and failure rates, cost by team, security findings over time.
  • "On-call engineers need a live view of system health": a CloudWatch dashboard.
  • "Managers want monthly trends of API activity or costs from logs in S3": Athena plus Quick Sight.

Associating CloudWatch alarms with CloudWatch metrics

Skill

An alarm watches one metric (or a metric math expression) and has three states: OK, ALARM and INSUFFICIENT_DATA.

SettingMeaning
Statistic and periodFor example, the p99 over 1 minute, or the Sum over 5 minutes
Evaluation periods and datapoints to alarm"M out of N": 3 of the last 5 periods must breach, which filters out single spikes
Treat missing datamissing, notBreaching, breaching or ignore. For metrics that only report when something happens (errors from a metric filter), use notBreaching; for heartbeat metrics, breaching
ActionsSNS notification; Lambda function; Auto Scaling policy; EC2 stop, terminate, reboot or recover; Systems Manager OpsItem or incident
  • Custom metrics: an alarm on a custom metric must name the exact namespace, metric name and full set of dimensions it was published with. A missing or extra dimension refers to a different metric with no data.
  • High-resolution custom metrics: allow alarm periods of 10 or 30 seconds.
  • EC2 automatic recovery: an alarm on StatusCheckFailed_System with the action arn:aws:automate:<region>:ec2:recover moves the instance to healthy hardware, keeping its ID, private IPs and EBS volumes.

Composite alarms: fewer, better alerts

A composite alarm combines other alarms with AND, OR and NOT. The underlying alarms do no notifying; only the composite pages someone. That cuts alert noise during an incident.

composite-alarm.yml 
CheckoutDegraded:
  Type: AWS::CloudWatch::CompositeAlarm
  Properties:
    AlarmName: checkout-degraded
    AlarmRule: >-
      ALARM("checkout-5xx-high") AND
      (ALARM("checkout-latency-anomaly") OR ALARM("checkout-unhealthy-hosts"))
    ActionsSuppressor: deployment-in-progress          # stay quiet while this alarm is in ALARM
    ActionsSuppressorWaitPeriod: 60
    ActionsSuppressorExtensionPeriod: 300
    AlarmActions: [!Ref PagerTopic]

"Too many alerts fire during one incident" or "only page when errors are high and latency is high" points to a composite alarm, with an actions suppressor for maintenance windows.

Configuring AWS X-Ray for different services

Skill

X-Ray follows each request through every service it touches, so you can see where time is spent and where errors start.

ConceptMeaning
TraceOne request end to end, identified by a trace ID passed in the X-Amzn-Trace-Id header
Segment and subsegmentThe work done by one service; subsegments for calls inside it (a database query, an HTTP call)
AnnotationsIndexed key-value pairs you can filter traces by (for example, customerTier = gold)
MetadataExtra details stored with the trace but not searchable
Sampling rulesHow many requests are traced. The default records the first request each second and 5% of the rest
Trace mapA graph of services with latency and error rates on each connection

To send traces, applications use the AWS Distro for OpenTelemetry (ADOT, the recommended option) or the X-Ray SDKs, plus a collector or the X-Ray daemon, which receives segments on UDP port 2000 and forwards them to X-Ray.

Per service

ServiceHow to turn on tracing
LambdaActive tracing on the function (TracingConfig: Mode: Active, or Tracing: Active in SAM). The execution role needs xray:PutTraceSegments and xray:PutTelemetryRecords (AWSXRayDaemonWriteAccess). Use the SDK or ADOT for subsegments inside the code
API Gateway (REST APIs)Enable X-Ray tracing on the stage (TracingEnabled: true)
ECS (EC2 and Fargate)Run the X-Ray daemon or an ADOT collector as a sidecar container in the task; the task role needs the X-Ray write permissions
EKSThe X-Ray daemon or ADOT collector as a DaemonSet (or sidecar), with permissions through IRSA or EKS Pod Identity
EC2 and on-premisesInstall the X-Ray daemon or the CloudWatch agent with X-Ray enabled; the instance profile needs write permissions
Elastic BeanstalkThe XRayEnabled option runs the daemon for you
Step Functions, SNS, SQS, App RunnerTracing options on the resource, or trace header propagation
ecs-task-with-xray.yml (container definitions) 
ContainerDefinitions:
  - Name: web
    Image: 111111111111.dkr.ecr.eu-west-1.amazonaws.com/orders:v1.4.2
    Environment:
      - Name: AWS_XRAY_DAEMON_ADDRESS   # send segments to the sidecar
        Value: "localhost:2000"
  - Name: xray-daemon
    Image: public.ecr.aws/xray/aws-xray-daemon:latest
    PortMappings: [{ ContainerPort: 2000, Protocol: udp }]
    Essential: false                                              # the app keeps running if tracing fails

"Traces from API Gateway are missing" for an HTTP API: X-Ray tracing is supported on API Gateway REST APIs, not HTTP APIs. Also check that sampling isn't simply dropping the requests you're looking for.

"Find which downstream call makes requests slow" or "see the dependencies between microservices" points to X-Ray (trace map and traces). "Filter traces by customer ID" needs that value as an annotation, not metadata.

Analyzing real-time log streams (Kinesis Data Streams)

Skill

When logs must be acted on within seconds (fraud signals, security events, live metrics), stream them through Kinesis Data Streams and analyze them as they flow.

  1. Producers write to the streamCloudWatch Logs subscription filters, applications using the Kinesis Producer Library, or agents.
  2. The stream holds ordered recordsEach shard takes up to 1 MB or 1,000 records per second in, and 2 MB per second out shared by consumers (or 2 MB per second each with enhanced fan-out). On-demand mode manages shards for you.
  3. Consumers analyzeLambda for per-record logic; Amazon Managed Service for Apache Flink formerly Kinesis Data Analytics for windowed aggregations and SQL over the stream; custom KCL applications.
  4. Results drive actionPublish metrics, raise alarms, send events to EventBridge, or write to OpenSearch for live dashboards. Firehose also archives the raw stream to S3.

Example: a Lambda consumer that counts errors

Records from a CloudWatch Logs subscription are base64-encoded and gzip-compressed, each containing several log events:

count_errors.py 
import base64, gzip, json
import boto3

cloudwatch = boto3.client("cloudwatch")

def handler(event, context):
    errors = 0
    for record in event["Records"]:
        payload = gzip.decompress(base64.b64decode(record["kinesis"]["data"]))
        data = json.loads(payload)
        if data["messageType"] != "DATA_MESSAGE":        # skip control messages
            continue
        for log_event in data["logEvents"]:
            if '"level":"ERROR"' in log_event["message"]:
                errors += 1
    cloudwatch.put_metric_data(
        Namespace="Orders/Stream",
        MetricData=[{"MetricName": "Errors", "Value": errors, "Unit": "Count"}],
    )
  • Event source mapping settings: batch size, batching window, a parallelization factor (up to 10 concurrent batches per shard), and on failure: bisect the batch, limit retries, and send failed records to an on-failure destination.
  • Health: watch IteratorAge. If it grows, consumers are falling behind: add shards, raise parallelization, or speed up the function.

"Compute per-minute error rates over a sliding window across all streamed logs" points to Managed Service for Apache Flink. "Run simple logic on each record" points to Lambda.

Athena

Athena runs SQL directly on files in S3 and charges per amount of data scanned. Define a table over the log location once (the CloudTrail console can create it for you), then query:

Who deleted security groups last week? (CloudTrail) 
SELECT eventtime, useridentity.arn, sourceipaddress,
       json_extract_scalar(requestparameters, '$.groupId') AS group_id
FROM cloudtrail_logs
WHERE eventname = 'DeleteSecurityGroup'
  AND eventtime > to_iso8601(current_timestamp - interval '7' day)
ORDER BY eventtime DESC;
Top sources of rejected traffic (VPC Flow Logs) 
SELECT srcaddr, dstport, count(*) AS rejected
FROM vpc_flow_logs
WHERE action = 'REJECT'
  AND day = '2026/10/27'                 -- partition column: scans one day only
GROUP BY srcaddr, dstport
ORDER BY rejected DESC
LIMIT 20;
  • Cost and speed: partition tables by date (partition projection avoids managing partitions by hand), store data compressed in a columnar format such as Parquet (Firehose can convert it), and select only the columns you need.
  • Control: workgroups separate teams, set per-query data limits and choose where results are stored.

CloudWatch Logs Insights

Rejected connections by source (VPC Flow Logs in CloudWatch Logs) 
filter action = "REJECT"
| stats count(*) as rejected by srcAddr, dstPort
| sort rejected desc
| limit 20
Slowest API routes (API Gateway access logs in JSON) 
fields routeKey, responseLatency
| stats avg(responseLatency) as avgMs, pct(responseLatency, 99) as p99Ms, count(*) as requests by routeKey
| sort p99Ms desc

An Athena query over a whole CloudTrail or ALB log bucket with no partition filter scans everything: slow and costly. Filter on the partition columns (Region, date) every time.

Key takeaways

  • Anomaly detection alarms (ANOMALY_DETECTION_BAND) suit metrics with daily or weekly patterns; Logs anomaly detection and DevOps Guru add machine learning on logs and applications.
  • Know key metrics: EC2 status checks (system vs instance), ALB ELB 5XX vs Target 5XX, RDS DiskQueueDepth and connections, Lambda Throttles and IteratorAge, SQS age of oldest message.
  • Inspector: continuous CVE scanning of EC2, ECR images and Lambda, network reachability, CIS scans. Inspector Classic's assessment templates are superseded by continuous scanning.
  • Config rules: managed, custom Lambda or Guard; change-triggered or periodic; detective or proactive; with SSM Automation remediation and conformance packs.
  • CloudTrail: management events (90-day Event history), data events (off by default), Insights events. Read userIdentity, eventName, requestParameters, errorCode.
  • CloudWatch dashboards for live operations (as code, cross-account); Quick Sight over Athena for business trends.
  • Alarms: M of N datapoints, treat missing data deliberately, exact dimensions for custom metrics, EC2 recover action, composite alarms with suppressors to cut noise.
  • X-Ray: Lambda active tracing, API Gateway REST stage tracing (not HTTP APIs), daemon or ADOT sidecars for containers; annotations are searchable, metadata isn't.
  • Real-time analysis: Kinesis Data Streams with Lambda or Managed Service for Apache Flink; watch iterator age.
  • Athena for S3 archives (partition and use Parquet), Logs Insights for recent CloudWatch logs.
