Overview

Task statement 2.3

Design and build automated solutions for complex tasks and large-scale environments.

At scale, anything done by hand is done late, inconsistently or not at all. This task tests whether you can turn operational work into reliable automation: picking the right service for the job, writing code that copes with throttling and many accounts, and using Systems Manager to keep thousands of servers inventoried, patched, configured and compliant. Typical scenarios: "patch 2,000 instances every month without downtime", "a cleanup script times out after 15 minutes", or "prove that every server runs the approved agent version".

Methods and strategies to interact with the AWS software-defined infrastructure

Knowledge

Everything in AWS is an API call, signed with Signature Version 4. The console, the AWS CLI, CloudShell, the SDKs and IaC tools are all ways of making those calls.

Strategies for automation code at scale

ConcernWhat to do
PaginationList and describe calls return pages; use the SDK paginators or you silently miss resources
ThrottlingRetry with exponential backoff and jitter. SDK retry modes: standard, or adaptive, which also slows the client down
IdempotencyMake reruns safe: pass client tokens (ClientToken, ClientRequestToken) and check before you create
Eventual consistencyA resource you just created may not be visible yet; use SDK waiters or retry
FilteringFilter on the server (Filters parameters) instead of fetching everything
CredentialsNever use long-lived keys in automation. Use roles: the Lambda execution role, the instance profile, or sts:AssumeRole into each account
Many accounts and RegionsList accounts from Organizations, assume a role in each, and loop over Regions

Example: find unattached EBS volumes in every account

Assume a role named AutomationRole exists in every member account (deployed by StackSets) and trusts the automation account:

find_unattached_volumes.py 
import boto3
from botocore.config import Config

retry = Config(retries={"max_attempts": 10, "mode": "adaptive"})   # backoff on throttling
org = boto3.client("organizations")
sts = boto3.client("sts")

def session_for(account_id):
    creds = sts.assume_role(
        RoleArn=f"arn:aws:iam::{account_id}:role/AutomationRole",
        RoleSessionName="unattached-volume-report",               # shows up in CloudTrail
    )["Credentials"]
    return boto3.Session(
        aws_access_key_id=creds["AccessKeyId"],
        aws_secret_access_key=creds["SecretAccessKey"],
        aws_session_token=creds["SessionToken"],
    )

for page in org.get_paginator("list_accounts").paginate():      # every page, not just the first
    for account in page["Accounts"]:
        session = session_for(account["Id"])
        for region in ["eu-west-1", "eu-central-1"]:
            ec2 = session.client("ec2", region_name=region, config=retry)
            volumes = ec2.get_paginator("describe_volumes").paginate(
                Filters=[{"Name": "status", "Values": ["available"]}]   # filtered on the server
            )
            for volume_page in volumes:
                for volume in volume_page["Volumes"]:
                    print(account["Id"], region, volume["VolumeId"], volume["Size"])

Reaching instances without SSH

  • Session Manager: a shell or port forwarding to managed instances through Systems Manager. There's no inbound port, SSH key or bastion host. Access is controlled by IAM, and every session can be logged to S3 or CloudWatch Logs.
  • EC2 Instance Connect: pushes a temporary SSH key for 60 seconds. With an EC2 Instance Connect Endpoint it reaches instances in private subnets without a public IP.

"Remove SSH access and bastion hosts, but administrators still need a shell, and every command must be audited" points to Session Manager with session logging.

Automating system inventory, configuration and patch management

Skill

Making instances manageable

Every Systems Manager capability works on managed nodes. An instance becomes one when three things are true:

  1. The SSM Agent is runningIt's preinstalled on Amazon Linux, Ubuntu Server and Windows Server AMIs from AWS.
  2. The instance has permissionAn instance profile with AmazonSSMManagedInstanceCore, or account-wide Default Host Management Configuration (DHMC), which grants it to every instance without an instance profile (IMDSv2 required).
  3. The agent can reach Systems ManagerThrough the internet, or through VPC endpoints ssm, ssmmessages and ec2messages in private subnets.

On-premises servers and other clouds join through a hybrid activation and get IDs starting with mi-.

"The instance doesn't appear in Fleet Manager, and Run Command can't target it" is almost always one of the three: no agent, no permission, or no network route to the Systems Manager endpoints.

Skill

Inventory

  • Systems Manager Inventory: a State Manager association that collects installed applications, AWS components, files, network configuration, Windows updates, services, registry keys and custom inventory from managed nodes on a schedule.
  • Resource Data Sync: sends inventory (and compliance data) from many accounts and Regions to one S3 bucket. Query it with Athena or visualize it in Amazon Quick Sight.
  • AWS Config: the inventory of AWS resources rather than software on servers. It records configuration history and relationships, and advanced queries search current configuration with SQL, across accounts through an aggregator.

"Which servers in all accounts still run OpenSSL 1.1?" points to Systems Manager Inventory with Resource Data Sync, queried in Athena. "Which security groups allow port 22 from anywhere?" points to AWS Config advanced queries.

Skill

Patch Manager

ConceptMeaning
Patch baselineWhich patches are approved for an operating system: rules by classification and severity, an auto-approval delay, and explicit approved and rejected lists. AWS provides a default baseline per OS
Patch groupInstances tagged with a patch group name use the baseline registered for that group
AWS-RunPatchBaselineThe document that does the work: Scan reports missing patches; Install installs them and reboots if needed
Maintenance windowThe schedule, targets and tasks for patching, with concurrency and error thresholds
Patch policiesQuick Setup configuration that patches across accounts and Regions of an organization from one place

A custom baseline for production Amazon Linux 2023

patch-baseline.yml 
ProdLinuxBaseline:
  Type: AWS::SSM::PatchBaseline
  Properties:
    Name: prod-al2023
    OperatingSystem: AMAZON_LINUX_2023
    ApprovalRules:
      PatchRules:
        - PatchFilterGroup:
            PatchFilters:
              - Key: CLASSIFICATION
                Values: [Security, Bugfix]
              - Key: SEVERITY
                Values: [Critical, Important]
          ApproveAfterDays: 7            # released patches wait 7 days (tested in non-prod first)
          ComplianceLevel: CRITICAL      # how missing patches are reported
    RejectedPatches: ["kernel-6.1.90*"]  # a known-bad patch
    PatchGroups: [prod-web]             # instances tagged "Patch Group: prod-web" use this baseline

A monthly patching run

  1. The maintenance window opensFor example, the second Sunday at 02:00, for 4 hours, targeting instances tagged Patch Group: prod-web.
  2. Take instances out of service in small batchesThe task's concurrency (for example, 10%) and error threshold (for example, 5%) stop the run if too many instances fail.
  3. Install patchesAWS-RunPatchBaseline with Operation: Install applies the baseline and reboots if required.
  4. Report complianceEach instance reports compliant or non-compliant to Systems Manager Compliance, which can be aggregated with Resource Data Sync and Security Hub.
  5. Scan between windowsA daily Scan association reports newly missing patches without installing anything.

"Patch without affecting availability" points to low concurrency in the maintenance window task, with instances behind a load balancer, or an immutable approach: patch the AMI with Image Builder and run an instance refresh.

An instance tagged with a patch group that has no registered baseline silently falls back to the AWS default baseline for its OS, which may approve different patches from what you expect.

Developing Lambda function automations for complex scenarios

Skill

Common Lambda automation patterns

  • Event-driven fix: an EventBridge rule on a CloudTrail API event (for example, AuthorizeSecurityGroupIngress opening port 22 to 0.0.0.0/0) invokes a function that reverts the change and notifies the owner.
  • Scheduled cleanup: EventBridge Scheduler invokes a function nightly to delete unattached volumes, old snapshots or untagged test resources.
  • Glue between services: a function enriches an alarm with context and opens a ticket, or updates a Parameter Store value after an AMI build.

Writing reliable automation functions

ConcernPractice
Duration15-minute maximum. Split long jobs or move them to Step Functions
IdempotencyEvents can be delivered more than once; make the function safe to repeat
Failures of asynchronous invocationsLambda retries twice by default. Configure an on-failure destination (or a dead-letter queue) so failed events aren't lost
ConcurrencyUse reserved concurrency to cap how hard a function can hit downstream APIs
SDK clientsCreate them outside the handler so they're reused across invocations
PermissionsOne least-privilege execution role per function

Step Functions for multi-step automation

Step Functions can call more than 200 AWS services directly through AWS SDK integrations (arn:aws:states:::aws-sdk:<service>:<action>), so many steps need no Lambda function at all. It also gives you:

  • Waits that cost nothing: a workflow can pause for seconds or days.
  • Error handling: per-step Retry with backoff and Catch to a fallback state.
  • Human approval: the .waitForTaskToken pattern pauses until someone sends the token back.
  • Scale: a Distributed Map runs up to 10,000 parallel child workflows, for example one per account or per S3 object.

Example: run a CodeBuild project and wait for it, without Lambda

Step Functions has an optimized integration for CodeBuild (Step Functions Developer Guide, Manage AWS CodeBuild builds with Step Functions). With the .sync ("run a job") pattern, the state starts the build and waits until it finishes; no Lambda function polls for the result.

run-tests-state.yaml (one state of a state machine) 
RunIntegrationTests:
  Type: Task
  Resource: arn:aws:states:::codebuild:startBuild.sync   # start, then wait for the result
  Parameters:
    ProjectName: orders-integration-tests
    SourceVersion.$: $.commitId
    EnvironmentVariablesOverride:
      - Name: TARGET_URL
        Type: PLAINTEXT
        Value.$: $.stagingUrl
  ResultSelector:
    buildId.$: $.Build.Id
    status.$: $.Build.BuildStatus
  ResultPath: $.tests
  Catch:
    - ErrorEquals: [ States.ALL ]   # a failed build fails this state
      Next: NotifyTestsFailed
  Next: PromoteToProduction
  • Patterns: codebuild:startBuild (request-response) returns as soon as the build starts; codebuild:startBuild.sync waits for completion. startBuildBatch.sync does the same for batch builds.
  • Permissions: for .sync, the state machine role needs codebuild:StartBuild, codebuild:StopBuild and codebuild:BatchGetBuilds on the project, plus events:PutRule, events:PutTargets and events:DescribeRule on the managed rule StepFunctionsGetEventForCodeBuildStartBuildRule, which Step Functions uses to learn when the build ends.

Example: approve, then roll out a new AMI and wait for the result

Assume the Auto Scaling group web-asg's launch template already points at the new AMI. This workflow waits for approval, starts an instance refresh and polls until it finishes:

ami-rollout.asl.yml 
StartAt: RequestApproval
States:
  RequestApproval:
    Type: Task
    Resource: arn:aws:states:::sns:publish.waitForTaskToken   # pause until SendTaskSuccess
    Parameters:
      TopicArn: arn:aws:sns:eu-west-1:111111111111:release-approvals
      Message.$: States.Format('Approve AMI {}. Token: {}', $.amiId, $$.Task.Token)
    TimeoutSeconds: 86400                                    # give up after a day
    Next: StartRefresh

  StartRefresh:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:autoscaling:startInstanceRefresh   # no Lambda needed
    Parameters:
      AutoScalingGroupName: web-asg
      Preferences:
        MinHealthyPercentage: 90
        AutoRollback: true
    ResultPath: $.refresh
    Retry:
      - ErrorEquals: [States.TaskFailed]
        IntervalSeconds: 30
        MaxAttempts: 3
        BackoffRate: 2
    Catch:
      - ErrorEquals: [States.ALL]
        Next: NotifyFailure
    Next: WaitForRefresh

  WaitForRefresh:
    Type: Wait
    Seconds: 60                                               # waiting is free
    Next: CheckRefresh

  CheckRefresh:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:autoscaling:describeInstanceRefreshes
    Parameters:
      AutoScalingGroupName: web-asg
      InstanceRefreshIds.$: States.Array($.refresh.InstanceRefreshId)
    ResultSelector:
      status.$: $.InstanceRefreshes[0].Status
    ResultPath: $.check
    Next: IsFinished

  IsFinished:
    Type: Choice
    Choices:
      - Variable: $.check.status
        StringEquals: Successful
        Next: Done
      - Or:
          - Variable: $.check.status
            StringEquals: Failed
          - Variable: $.check.status
            StringEquals: Cancelled
          - Variable: $.check.status
            StringEquals: RollbackSuccessful
        Next: NotifyFailure
    Default: WaitForRefresh                                   # still running: loop

  NotifyFailure:
    Type: Task
    Resource: arn:aws:states:::sns:publish
    Parameters:
      TopicArn: arn:aws:sns:eu-west-1:111111111111:release-alerts
      Message: AMI rollout to web-asg did not complete
    Next: RolloutFailed

  RolloutFailed: { Type: Fail }
  Done: { Type: Succeed }

The approver (or a small approval web page) calls SendTaskSuccess with the token to continue, or SendTaskFailure to stop. The state machine's role needs permission for every API it calls: sns:Publish, autoscaling:StartInstanceRefresh and autoscaling:DescribeInstanceRefreshes.

A Lambda function that loops with sleep() while waiting for a long operation wastes money and fails at 15 minutes. Use a Step Functions Wait state and a Choice loop instead.

Systems Manager Automation runbooks

For operational procedures, an Automation runbook is often simpler than a state machine. It has built-in actions for AWS APIs, scripts, commands on instances and approvals:

restart-web-service.yml (runbook) 
schemaVersion: "0.3"
description: Restart nginx on an instance after approval
assumeRole: "{{ AutomationAssumeRole }}"
parameters:
  InstanceId: { type: String }
  AutomationAssumeRole: { type: String }
mainSteps:
  - name: Approve
    action: aws:approve                                  # waits for an approver
    inputs:
      Approvers: [arn:aws:iam::111111111111:role/OpsLead]
      MinRequiredApprovals: 1
  - name: RestartNginx
    action: aws:runCommand                               # Run Command on the instance
    inputs:
      DocumentName: AWS-RunShellScript
      InstanceIds: ["{{ InstanceId }}"]
      Parameters:
        commands: ["sudo systemctl restart nginx", "systemctl is-active nginx"]
  • Other actions: aws:executeAwsApi (any API call), aws:executeScript (Python or PowerShell), aws:waitForAwsResourceProperty and aws:branch.
  • Rate control: run against many targets with a concurrency and error threshold.
  • Multi-account and multi-Region execution: from a central account, using an administration role there and an execution role in each target account.

Automating the configuration of software applications to the desired state

Skill

A State Manager association binds a document (what to apply) to targets (which instances) and a schedule (how often to reapply). New instances that match the targets get the association automatically, and drift is corrected at the next run.

DocumentApplies
AWS-ConfigureAWSPackageInstalls or updates a Distributor package (for example, the CloudWatch agent)
AWS-RunShellScript, AWS-RunPowerShellScriptYour own commands
AWS-RunRemoteScriptA script downloaded from S3 or GitHub
AWS-ApplyAnsiblePlaybooksAnsible playbooks from S3 or GitHub
AWS-ApplyChefRecipesChef recipes, without a Chef server
AWS-ApplyDSCMofsPowerShell Desired State Configuration on Windows
Your own Command documentAny steps you define (example below)

A custom document and its association

configure-nginx (Command document) 
schemaVersion: "2.2"
description: Ensure nginx is installed, configured and running
mainSteps:
  - action: aws:runShellScript
    name: EnsureNginx
    inputs:
      runCommand:
        - sudo dnf install -y nginx
        - sudo aws s3 cp s3://example-config/nginx/nginx.conf /etc/nginx/nginx.conf
        - sudo systemctl enable --now nginx
        - sudo systemctl reload nginx
association.yml 
NginxDesiredState:
  Type: AWS::SSM::Association
  Properties:
    Name: configure-nginx
    Targets:
      - { Key: tag:Role, Values: [web] }
    ScheduleExpression: rate(30 minutes)       # reapply, which corrects drift
    MaxConcurrency: "20%"                      # rate control
    MaxErrors: "5%"
    ComplianceSeverity: HIGH
    ApplyOnlyAtCronInterval: false            # also run immediately on new targets

Migrating from OpsWorks

AWS OpsWorks (Stacks, Chef Automate and Puppet Enterprise) reached end of life in May 2024. Run Chef recipes or Ansible playbooks through State Manager (AWS-ApplyChefRecipes, AWS-ApplyAnsiblePlaybooks) instead. The exam guide still lists OpsWorks, so recognize it as the old answer for "Chef or Puppet managed configuration".

Other desired-state options

  • CloudFormation cfn-init with cfn-hup: desired state declared in template metadata and reapplied when the stack changes.
  • Immutable images: bake configuration into an AMI or container image, so there's nothing to drift.
  • AppConfig: application-level settings and feature flags, deployed gradually with rollback.

Maintaining software compliance

Skill

Compliance means being able to show, at any moment, that every server has the approved software, versions and patches, and fixing it automatically when it doesn't.

ToolWhat it reports or enforces
Systems Manager CompliancePatch compliance (from Patch Manager), association compliance (from State Manager), and custom items you report with PutComplianceItems
AWS Config managed rulesec2-instance-managed-by-systems-manager, ec2-managedinstance-patch-compliance-status-check, ec2-managedinstance-association-compliance-status-check, ec2-managedinstance-applications-required
Amazon InspectorKnown vulnerabilities (CVEs) in installed packages on EC2, in container images and in Lambda functions
AWS License ManagerLicense rules and usage for commercial software (for example, a limit on cores running a licensed database)
Security HubOne view of findings from Config, Inspector and Systems Manager Patch Manager
Resource Data SyncCompliance and inventory data from all accounts and Regions in one S3 bucket, for Athena or Quick Sight reports

Detect and fix automatically

  1. Define the ruleFor example, the Config rule ec2-managedinstance-applications-required with the CloudWatch agent as a required application.
  2. Detect non-complianceThe rule evaluates instances using Systems Manager Inventory data and marks offenders NON_COMPLIANT.
  3. RemediateAn automatic remediation action runs an SSM Automation runbook (for example, one that runs AWS-ConfigureAWSPackage on the instance).
  4. ReportThe aggregator, conformance packs and Security Hub show compliance across the organization. Compliance changes also arrive in EventBridge for notifications.

"Report which instances are missing patches across all accounts" points to Patch Manager scanning plus Systems Manager Compliance, aggregated with Resource Data Sync or Security Hub. "Ensure every instance is managed by Systems Manager at all" points to the Config rule ec2-instance-managed-by-systems-manager.

Key takeaways

  • Lambda for short steps (15 minutes max), Step Functions for multi-step, long or approval-based workflows, SSM Automation for operational runbooks across accounts, EventBridge and EventBridge Scheduler to trigger them.
  • Step Functions Standard runs up to a year with exactly-once execution; Express runs up to 5 minutes for high volume. SDK integrations and Wait states avoid unnecessary Lambda code.
  • Automation code at scale: paginate, retry with backoff (adaptive mode), be idempotent, use waiters, filter on the server, assume roles per account.
  • Session Manager replaces SSH and bastions, with IAM control and session logging.
  • A managed node needs the SSM Agent, permissions (instance profile or DHMC) and a route to the Systems Manager endpoints.
  • Inventory plus Resource Data Sync answers "what software is where". AWS Config answers "how are AWS resources configured".
  • Patch Manager: baselines (classification, severity, approval delay), patch groups, AWS-RunPatchBaseline Scan or Install, maintenance windows with concurrency and error thresholds, patch policies for organizations.
  • State Manager associations keep software in its desired state and apply to new instances automatically. OpsWorks is retired; run Chef or Ansible through State Manager.
  • Compliance: Systems Manager Compliance, Config managed-instance rules with automatic remediation, Inspector for CVEs, Security Hub and Resource Data Sync for reporting.
