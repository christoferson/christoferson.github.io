Account vending with AWS Control Tower

A team asks for a new AWS account. Within the hour, without a ticket queue, the account exists in the right OU with logging, Config and guardrails already on, the company baseline deployed, the team's group able to sign in, and a budget and network ready, and the team is told it can start.

Scenario and requirements

A company with a Control Tower landing zone creates several new accounts every week, one per team and environment. The platform team wants every account created the same way, governed from its first minute, with no manual steps and an audit trail of who asked for what.

RequirementDesign choice
Accounts created on request, the same way every timeControl Tower Account Factory, driven from code (Service Catalog API or AFT)
Logging, Config and guardrails from the first minuteCreate the account inside a registered OU, so the Control Tower baseline and the OU's controls apply
Company baseline (roles, alarms, security settings) in every accountCustomizations for Control Tower (CfCT) deploying StackSets to the OU
Team access without IAM usersIAM Identity Center group assignment with a permission set
Extra setup that depends on the new account IDEventBridge rule on the CreateManagedAccount lifecycle event starting a Step Functions workflow
Audit trail of requestsAccount requests kept in Git (who, why, when), plus CloudTrail and the lifecycle events

Assume these accounts, with us-east-1 as the Control Tower home Region:

AccountIDWhat lives there
Management000000000000Organizations, Control Tower, Account Factory, the CfCT pipeline, the post-creation workflow
Log Archive666666666666CloudTrail and Config logs for every account (created by Control Tower)
Audit555555555555Security tooling and cross-account audit roles (created by Control Tower)

How it works

Steps marked AWS are done by Control Tower and other services; steps marked You build are pieces the platform team creates once.

  1. Request
  2. A team requests an accountYou buildA pull request adds an account request file (name, email, OU, owner, reason). Review and merge are the approval.
  3. The pipeline calls Account FactoryYou buildIt provisions the "AWS Control Tower Account Factory" product in Service Catalog with the request's parameters.
  4. Create and govern
  5. Organizations creates the accountAWSThe account is placed directly in the requested OU, never in the root.
  6. Control Tower applies its baselineAWSThe organization trail covers the account, Config starts recording to the Log Archive account, and Control Tower's roles are created.
  7. The OU's controls applyAWSPreventive controls (SCPs) take effect at once; detective controls (Config rules) start evaluating.
  8. Identity Center accessAWSThe user named in the request gets administrator access to the account through Identity Center.
  9. Customize
  10. CfCT deploys the baselineAWSThe new account joins the OU's StackSets, so the company roles, alarms and settings are created.
  11. The lifecycle event firesAWSControl Tower emits CreateManagedAccount with the new account ID and OU when everything has finished.
  12. The post-creation workflow runsYou buildAssigns the team's group, creates a budget, allocates a VPC CIDR from IPAM and creates the VPC.
  13. Hand over
  14. The team is notifiedYou buildA message with the account ID, the sign-in portal and what the baseline contains.

Build it

Step 1

OUs and controls

Accounts inherit governance from their OU, so the OU structure and its controls come first. Register each OU with Control Tower, then enable controls on it. Controls can be managed as code with the AWS::ControlTower::EnabledControl resource:

workload-controls.yaml (in 000000000000) 
Resources:
  ProdDisallowRootUser:   # preventive: an SCP behind the scenes
    Type: AWS::ControlTower::EnabledControl
    Properties:
      ControlIdentifier: arn:aws:controltower:us-east-1::control/AWS-GR_RESTRICT_ROOT_USER
      TargetIdentifier: arn:aws:organizations::000000000000:ou/o-a1b2c3d4e5/ou-ab12-prod0001

  ProdEncryptedVolumes:   # detective: a Config rule behind the scenes
    Type: AWS::ControlTower::EnabledControl
    Properties:
      ControlIdentifier: arn:aws:controltower:us-east-1::control/AWS-GR_ENCRYPTED_VOLUMES
      TargetIdentifier: arn:aws:organizations::000000000000:ou/o-a1b2c3d4e5/ou-ab12-prod0001
  • Identifiers: each control's API controlIdentifier is shown on its details page in the Control Tower console.
  • Per OU: stricter controls go on Workloads/Prod, lighter ones on Sandbox; every account placed in an OU gets that OU's controls.
Step 2

Requesting an account

Account Factory is a Service Catalog product in the management account. A request is a launch of that product with six parameters. From a pipeline, the request looks like this:

aws servicecatalog provision-product \
  --product-id prod-abcd1234efgh5 \
  --provisioning-artifact-id pa-abcd1234efgh5 \
  --provisioned-product-name orders-prod \
  --provisioning-parameters \
    Key=AccountName,Value=orders-prod \
    Key=AccountEmail,Value=aws+orders-prod@example.com \
    Key=ManagedOrganizationalUnit,Value="Prod (ou-ab12-prod0001)" \
    Key=SSOUserEmail,Value=platform-team@example.com \
    Key=SSOUserFirstName,Value=Platform \
    Key=SSOUserLastName,Value=Team
  • AccountEmail must not already belong to an AWS account; a plus-addressed mailbox per account is common.
  • SSOUserEmail gets administrator access to the account through Identity Center.
  • Concurrency: up to five accounts can be provisioned at a time; requests beyond that wait.

Teams using Terraform get the same result with Account Factory for Terraform (AFT): an account request file pushed to the aft-account-request repository starts AFT's pipeline.

aft-account-request/terraform/orders-prod.tf 
module "orders_prod" {
  source = "./modules/aft-account-request"

  control_tower_parameters = {
    AccountEmail              = "aws+orders-prod@example.com"
    AccountName               = "orders-prod"
    ManagedOrganizationalUnit = "Prod (ou-ab12-prod0001)"
    SSOUserEmail              = "platform-team@example.com"
    SSOUserFirstName          = "Platform"
    SSOUserLastName           = "Team"
  }

  account_tags = {
    "team"        = "orders"
    "cost-center" = "1234"
  }

  change_management_parameters = {
    change_requested_by = "orders-team"
    change_reason       = "Production account for the orders service"
  }

  custom_fields = {
    data_classification = "confidential"   # stored as SSM parameters in the new account
  }

  account_customizations_name = "production"   # folder in aft-account-customizations
}

For a nested OU, give ManagedOrganizationalUnit as OUName (OU-ID), as above. The Control Tower parameters can't be changed while the account is being provisioned.

Step 3

Baseline customizations with CfCT

Customizations for Control Tower runs a pipeline in the management account. Its manifest lists templates and policies and where they go; new accounts that land in a target OU receive the StackSet instances automatically.

manifest.yaml (CfCT configuration repository) 
region: us-east-1   # Control Tower home Region
version: 2021-03-15
resources:
  - name: baseline-roles
    resource_file: templates/baseline-roles.yaml
    deploy_method: stack_set   # CloudFormation StackSet
    deployment_targets:
      organizational_units:
        - Prod
        - NonProd
    regions:
      - us-east-1

  - name: security-alarms
    resource_file: templates/security-alarms.yaml
    deploy_method: stack_set
    parameters:
      - parameter_key: AlertEmail
        parameter_value: security@example.com
    deployment_targets:
      organizational_units:
        - Prod
    regions:
      - us-east-1
      - eu-west-1

  - name: deny-leave-organization
    resource_file: policies/deny-leave-organization.json
    deploy_method: scp   # SCPs and RCPs target OUs, not accounts
    deployment_targets:
      organizational_units:
        - Workloads
  • Without regions, stack instances deploy only in the home Region.
  • Management account: CfCT doesn't deploy stack instances there by default.
  • Alternatives: AFT account customizations (Terraform per account or per type), or Control Tower blueprints (a Service Catalog product applied when the account is created).
Step 4

Access for the team

The request's SSO user gets administrator access, but day-to-day access should come from the team's group with a least-privilege permission set. The workflow in step 5 creates the assignment once it knows the account ID:

assignment (created by the workflow) 
OrdersDevelopers:
  Type: AWS::SSO::Assignment
  Properties:
    InstanceArn: arn:aws:sso:::instance/ssoins-1234567890abcdef
    PermissionSetArn: arn:aws:sso:::permissionSet/ssoins-1234567890abcdef/ps-developer01
    PrincipalType: GROUP
    PrincipalId: 9067c4d2-1234-5678-9abc-def012345678   # Identity Center group ID
    TargetType: AWS_ACCOUNT
    TargetId: "111122223333"   # the new account
Step 5

Post-creation workflow

Control Tower records a lifecycle event when an account is fully created and enrolled. An EventBridge rule in the management account starts the workflow:

account-created-rule.json 
{
  "source": ["aws.controltower"],
  "detail-type": ["AWS Service Event via CloudTrail"],
  "detail": {
    "eventName": ["CreateManagedAccount", "UpdateManagedAccount"]
  }
}

The details are under serviceEventDetails.createManagedAccountStatus (or updateManagedAccountStatus): state (SUCCEEDED or FAILED), account.accountId, account.accountName, and the OU name and ID. The Step Functions workflow then:

  1. Checks the resultStops and alerts the platform team if state isn't SUCCEEDED.
  2. Reads the request metadataTeam, cost center and environment from the account tags.
  3. Assigns the team's groupIdentity Center CreateAccountAssignment with the developer permission set.
  4. Creates a budgetAn AWS Budgets budget with alerts to the team's distribution list.
  5. Allocates network spaceA CIDR from the VPC IPAM pool for the environment, then a VPC attached to the Transit Gateway.
  6. Notifies the teamAccount ID, sign-in portal URL and a link to the baseline documentation.

Lifecycle events reach EventBridge only if a CloudTrail trail with logging is active (Control Tower's organization trail does this). A retried request can end with UpdateManagedAccount instead of CreateManagedAccount, which is why the rule matches both.

Design decisions

DecisionWhy
Create accounts through Account Factory, not organizations:CreateAccountAccount Factory enrolls the account in Control Tower, so the baseline, controls and drift detection apply; a raw Organizations account starts ungoverned
Place the account in its final OU at creationGuardrails apply from the first minute; moving it later leaves a window without them and can cause drift
Requests as code in GitReview is the approval, history is the audit trail, and the request can be replayed
Baseline per OU (CfCT StackSets), not per accountNew accounts get it automatically; changing the template updates every account
Event-driven post-creation stepsThey run only after Control Tower has finished, with the real account ID, and failures are visible in the workflow's history
Group-based access through Identity CenterNo IAM users; joining or leaving the team changes access everywhere

Drift: moving an enrolled account to an OU outside Control Tower, editing a Control Tower-managed SCP in Organizations, or deleting its roles makes the landing zone report drift. Move accounts and change controls through Control Tower, add your own SCPs alongside its ones, and repair the landing zone if drift appears.

Alternatives

OptionWhen it fits better
Organizations plus your own scriptsNo Control Tower, or a need it can't meet; you then build logging, baselines and drift checks yourself
Account Factory for Terraform (AFT)The platform team works in Terraform; requests, global and per-account customizations all live in Git repositories
Customizations for Control Tower (CfCT)CloudFormation templates and SCPs per OU, applied to existing and new accounts by one pipeline
Control Tower blueprintsA small set of account types, each defined by one Service Catalog product chosen at creation
Landing Zone Accelerator on AWSRegulated environments needing a broad, configuration-driven baseline of security services and networking

Testing it

  1. Vend into a test OURequest an account into a Sandbox or Policy Staging OU first, with the same controls as the target OU.
  2. Check the baselineThe account appears as enrolled in Control Tower, the CfCT stack instances are CURRENT, and Config is recording.
  3. Check the guardrailsTry a denied action (for example, leaving the organization) and confirm the SCP blocks it.
  4. Check the workflowThe Step Functions execution succeeded, the team's group can sign in, and the budget and VPC exist.
