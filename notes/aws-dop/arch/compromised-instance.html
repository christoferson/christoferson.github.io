End-to-end architecture

Automated response to a compromised EC2 instance

GuardDuty spots an instance talking to a crypto-mining pool or leaking its credentials, in any account of the organization. Within a minute, without anyone logging in, the instance is cut off from the network, its disks are preserved for forensics, its stolen credentials stop working, Auto Scaling replaces it, and the on-call engineer is told what happened.

Scenario and requirements

A company runs web servers in Auto Scaling groups across many workload accounts. Security wants compromised instances contained automatically, around the clock, with evidence kept for investigation and no impact on the application's capacity.

RequirementDesign choice
Detect compromise in every account and Region, including new accountsGuardDuty with a delegated administrator and organization auto-enable
One place to respond fromMember findings arrive in the administrator (security) account's EventBridge
Act only on serious findings about instancesEventBridge pattern on resourceType and severity >= 7
Multi-step response with retries and an audit trailStep Functions Standard workflow
Act inside the affected accountA response role in every workload account, deployed with StackSets
Keep evidenceIsolate instead of terminating; snapshot the volumes
No loss of capacityDetach from the Auto Scaling group without lowering desired capacity, so a replacement launches
Stolen role credentials must stop workingRevoke the instance role's sessions issued before now

Assume these accounts, all in us-east-1:

AccountIDWhat lives there
Management000000000000Organizations; designates the GuardDuty administrator; runs the StackSet
Security555555555555GuardDuty administrator, EventBridge rule, Step Functions workflow, SNS topic
Workload222222222222 (and every other workload account)The web servers, an isolation security group per VPC, IncidentResponseRole

How it works

Steps marked AWS happen automatically inside AWS services; steps marked Workflow are states in the Step Functions workflow you build.

  1. Detect
  2. GuardDuty raises a findingAWSFor example CryptoCurrency:EC2/BitcoinTool.B!DNS on instance i-0abc123 in 222222222222, severity 8.
  3. The finding reaches the security accountAWSGuardDuty sends member findings to the administrator account, which emits a GuardDuty Finding event on its default bus.
  4. Route
  5. An EventBridge rule matchesAWSInstance findings with severity 7 or higher start the workflow, passing the account ID, Region and instance ID.
  6. Contain
  7. Gather contextWorkflowLooks up the instance's VPC, Auto Scaling group, instance role and the VPC's isolation security group.
  8. Tag the instanceWorkflowquarantine=true and the finding ID, so people and automation know not to touch it.
  9. Detach from the Auto Scaling groupWorkflowWithout decrementing desired capacity. The group launches a clean replacement and stops health-checking the bad one.
  10. Swap to the isolation security groupWorkflowA group with no inbound rules and no usable outbound rule.
  11. Revoke the role's sessionsWorkflowAdds a deny for sessions issued before now to the instance role, so credentials already stolen stop working.
  12. Preserve
  13. Snapshot every volumeWorkflowOne crash-consistent set of snapshots, tagged with the finding ID, for forensics.
  14. Notify
  15. Tell the respondersWorkflowSNS message to the on-call topic with the finding, the actions taken and the snapshot IDs.
  16. Investigate and recover (people)
  17. InvestigateResponderDetective for scope, the snapshots for forensics, CloudTrail for what the stolen credentials did.
  18. Fix and clean upResponderPatch the image, rotate secrets the instance could read, then terminate the quarantined instance.

Build it

Step 1

GuardDuty for the organization

From the management account, make the security account the administrator, then from the security account turn on auto-enable. Repeat in every Region you use, because GuardDuty is Regional.

# in 000000000000 (management)
aws guardduty enable-organization-admin-account --admin-account-id 555555555555

# in 555555555555 (security)
DETECTOR=$(aws guardduty list-detectors --query 'DetectorIds[0]' --output text)
aws guardduty update-organization-configuration \
  --detector-id "$DETECTOR" \
  --auto-enable-organization-members ALL      # existing and new accounts
Step 2

Workload account resources (StackSet)

Deploy this template from the management account as a service-managed StackSet targeting the Workloads OU, with automatic deployment on, so every new account gets it. The isolation security group is per VPC, so its template takes the VPC ID (or deploy it with the VPC's own stack).

incident-response-baseline.yaml 
Parameters:
  VpcId: { Type: AWS::EC2::VPC::Id }

Resources:
  IsolationSecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Quarantine - no traffic in or out
      VpcId: !Ref VpcId
      SecurityGroupEgress:                     # replaces the default allow-all egress rule
        - { IpProtocol: "-1", CidrIp: 127.0.0.1/32 }
      Tags:
        - { Key: purpose, Value: isolation }      # how the workflow finds it

  IncidentResponseRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: IncidentResponseRole
      AssumeRolePolicyDocument:
        Version: "2012-10-17"
        Statement:
          - Effect: Allow
            Principal: { AWS: arn:aws:iam::555555555555:role/IncidentResponseWorkflowRole }
            Action: sts:AssumeRole
      Policies:
        - PolicyName: contain-and-preserve
          PolicyDocument:
            Version: "2012-10-17"
            Statement:
              - Effect: Allow
                Action:
                  - ec2:DescribeInstances
                  - ec2:DescribeSecurityGroups
                  - ec2:CreateTags
                  - ec2:ModifyInstanceAttribute         # swap security groups
                  - ec2:CreateSnapshots
                  - autoscaling:DetachInstances
                Resource: "*"
              - Effect: Allow
                Action: iam:PutRolePolicy                  # revoke sessions
                Resource: !Sub arn:aws:iam::${AWS::AccountId}:role/app-*   # application roles only

A CloudFormation security group with no SecurityGroupEgress gets the default allow all outbound rule. To remove it, you must specify at least one egress rule; the 127.0.0.1/32 rule is the usual placeholder that allows nothing useful.

Step 3

EventBridge rule (security account)

ir-rule.yaml (in 555555555555) 
CompromisedInstanceRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [ aws.guardduty ]
      detail-type: [ GuardDuty Finding ]
      detail:
        resource:
          resourceType: [ Instance ]
        severity: [ { numeric: [ ">=", 7 ] } ]
        type: [ { prefix: "CryptoCurrency:EC2/" }, { prefix: "Backdoor:EC2/" }, { prefix: "Trojan:EC2/" }, { prefix: "UnauthorizedAccess:EC2/" } ]
    Targets:
      - Id: respond
        Arn: !Ref ResponseStateMachine
        RoleArn: !GetAtt EventsInvokeRole.Arn          # allows states:StartExecution
        InputTransformer:
          InputPathsMap:
            accountId: $.detail.accountId
            region: $.detail.region
            instanceId: $.detail.resource.instanceDetails.instanceId
            findingId: $.detail.id
            findingType: $.detail.type
          InputTemplate: '{"accountId":"<accountId>","region":"<region>","instanceId":"<instanceId>","findingId":"<findingId>","findingType":"<findingType>"}'

The input transformer passes the workflow only the five fields it needs, instead of the whole finding.

Step 4

Response workflow (security account)

Most steps are Step Functions AWS SDK integrations, so no Lambda code is needed. The Credentials field makes each call with IncidentResponseRole in the affected account. Two steps (gathering context and writing the revoke policy) use small Lambda functions, because they need logic that's awkward in JSONPath.

ir-state-machine.yaml (in 555555555555, Definition only) 
StartAt: GatherContext
States:
  GatherContext:                               # Lambda: VPC, ASG name, role name, isolation SG ID
    Type: Task
    Resource: arn:aws:states:::lambda:invoke
    Parameters: { FunctionName: ir-gather-context, Payload.$: $ }
    ResultSelector: { ctx.$: $.Payload }
    ResultPath: $.context
    Retry: [ { ErrorEquals: [ States.ALL ], MaxAttempts: 3, BackoffRate: 2 } ]
    Next: TagInstance

  TagInstance:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:ec2:createTags
    Credentials:
      RoleArn.$: States.Format('arn:aws:iam::{}:role/IncidentResponseRole', $.accountId)
    Parameters:
      Resources.$: States.Array($.instanceId)
      Tags:
        - { Key: quarantine, Value: "true" }
        - { Key: guardduty-finding, Value.$: $.findingId }
    ResultPath: null
    Next: InAutoScalingGroup?

  InAutoScalingGroup?:
    Type: Choice
    Choices:
      - { Variable: $.context.ctx.asgName, IsPresent: true, Next: DetachFromAsg }
    Default: Isolate

  DetachFromAsg:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:autoscaling:detachInstances
    Credentials:
      RoleArn.$: States.Format('arn:aws:iam::{}:role/IncidentResponseRole', $.accountId)
    Parameters:
      AutoScalingGroupName.$: $.context.ctx.asgName
      InstanceIds.$: States.Array($.instanceId)
      ShouldDecrementDesiredCapacity: false       # launch a replacement
    ResultPath: null
    Next: Isolate

  Isolate:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:ec2:modifyInstanceAttribute
    Credentials:
      RoleArn.$: States.Format('arn:aws:iam::{}:role/IncidentResponseRole', $.accountId)
    Parameters:
      InstanceId.$: $.instanceId
      Groups.$: States.Array($.context.ctx.isolationSgId)   # replaces all current groups
    ResultPath: null
    Next: RevokeSessions

  RevokeSessions:                              # Lambda: PutRolePolicy deny where aws:TokenIssueTime < now
    Type: Task
    Resource: arn:aws:states:::lambda:invoke
    Parameters: { FunctionName: ir-revoke-sessions, Payload.$: $ }
    ResultPath: null
    Next: Snapshot

  Snapshot:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:ec2:createSnapshots
    Credentials:
      RoleArn.$: States.Format('arn:aws:iam::{}:role/IncidentResponseRole', $.accountId)
    Parameters:
      InstanceSpecification: { InstanceId.$: $.instanceId }
      Description.$: States.Format('Forensics for {}', $.findingId)
      CopyTagsFromSource: volume
    ResultSelector: { ids.$: $.Snapshots[*].SnapshotId }
    ResultPath: $.snapshots
    Next: Notify

  Notify:
    Type: Task
    Resource: arn:aws:states:::sns:publish
    Parameters:
      TopicArn: arn:aws:sns:us-east-1:555555555555:security-oncall
      Subject.$: States.Format('Quarantined {} in {}', $.instanceId, $.accountId)
      Message.$: $
    End: true

Every Task state also gets a Catch that routes to a failure notification, so a half-finished containment is never silent. The workflow's own role (IncidentResponseWorkflowRole) needs sts:AssumeRole on arn:aws:iam::*:role/IncidentResponseRole, permission to invoke the two functions, and sns:Publish on the topic.

Design decisions

DecisionWhy
Isolate, don't terminateTerminating destroys memory and disk evidence. A quarantined instance costs little and can be examined.
Detach before isolatingOtherwise the ELB health check fails after isolation and Auto Scaling terminates the instance, destroying the evidence.
Step Functions, not one Lambda functionEach step retries independently, the execution history is an audit record of what was done, and SDK integrations need no code.
Respond from the security accountOne copy of the workflow for all accounts; workload account admins can't change it. A narrow cross-account role does the work.
Revoke sessions, not delete the roleDeleting the role would break the replacement instances. A deny on old sessions stops only the stolen credentials.
Severity and type filterLow-severity or non-instance findings would quarantine healthy servers. Start narrow and widen with experience.

Changing an instance's security group doesn't cut connections that are already tracked; an attacker's existing session can continue. For an immediate cut, also add a network ACL deny for the attacker's IP, or first switch to a group that allows all traffic (which makes connections untracked) and then to the isolation group.

Alternatives

OptionWhen it fits better
Systems Manager Automation runbook as the targetThe team already standardizes on runbooks, or wants approval steps through Change Manager
Security Hub custom actionA human should decide, by clicking an action on the finding, before containment runs
A single Lambda functionVery simple response (tag and notify) in one account
Forwarding findings to a central bus with PutEventsNot needed here: GuardDuty already aggregates member findings in the administrator account

Testing it

  1. Test the ruleaws guardduty create-sample-findings --finding-types CryptoCurrency:EC2/BitcoinTool.B!DNS produces a real event (with fake resource IDs), so you can check that the rule matches and the workflow starts.
  2. Test the workflowStart an execution by hand with the input of a real test instance in a sandbox account, and check each step's result in the execution history.
  3. Test end to endGenerate real findings from a test instance (for example, with the GuardDuty tester scripts) in a sandbox account.

You can't send a test event with source: aws.guardduty through PutEvents: sources starting with aws. are reserved for AWS services. That's why sample findings are the way to test the rule.

"Automatically isolate a compromised instance and preserve it for forensics" is GuardDuty, EventBridge and an automation (Step Functions, Lambda or Systems Manager) that swaps the security group and snapshots the volumes. Terminating the instance is the classic wrong answer because it destroys the evidence.
