End-to-end architecture

Organization-wide centralized logging

Every API call, configuration change, network flow and application log from every account and Region lands in one log archive account that nobody can tamper with. Logs are kept for seven years at the lowest storage cost, can be searched with SQL, and suspicious activity raises an alert within minutes. New accounts are covered the day they're created.

Scenario and requirements

A company has dozens of accounts in AWS Organizations and is audited every year. Auditors want proof that logs are complete and unaltered; the security team wants to search them and be alerted quickly; finance wants storage to stay cheap.

RequirementDesign choice
All accounts and all RegionsOne organization trail (multi-Region); Config, flow logs and log subscriptions rolled out with StackSets
Tamper-proofSeparate log archive account; S3 Object Lock in compliance mode; log file integrity validation; SCPs protecting trails and buckets
Kept for 7 yearsObject Lock default retention of 7 years; lifecycle expiry after 7 years
SearchableAthena tables with partition projection over the S3 logs
Near real-time alertingTrail events in CloudWatch Logs with metric filters and alarms; EventBridge rules for specific API calls
New accounts covered automaticallyOrganization trail covers them at once; service-managed StackSets with automatic deployment for everything else
Least costS3 instead of long CloudWatch Logs retention; lifecycle transitions to Glacier storage classes; short retention in source accounts

Assume these accounts, with us-east-1 as the home Region:

AccountIDWhat lives there
Management000000000000Organizations, the organization trail, SCPs, the StackSets
Log archive666666666666The log buckets, their KMS key, the CloudWatch Logs destination and Firehose stream. Almost nobody can sign in.
Security (audit)555555555555Config aggregator, Athena workgroup, read-only access to the logs, alerting
Workload222222222222 (and every other workload account)Applications writing to CloudWatch Logs, VPCs with flow logs

How it works

Steps marked AWS happen automatically once configured; steps marked You are what you build or run.

  1. Audit logs: CloudTrail and Config
  2. CloudTrail records every API callAWSThe organization trail in 000000000000 logs management events from every account and Region, plus selected data events.
  3. Log files land in the audit bucketAWSAbout every 5 minutes, under AWSLogs/o-a1b2c3d4e5/<account>/CloudTrail/<region>/, encrypted with the log archive's KMS key. Hourly digest files allow integrity validation.
  4. Object Lock makes them immutableAWSEach object version is locked in compliance mode for 7 years. Nobody, including the root user, can delete or overwrite it.
  5. A copy goes to CloudWatch LogsAWSThe trail also sends events to a log group, where metric filters and alarms watch for root sign-ins, failed console logins and policy changes.
  6. Config snapshots and history arriveAWSEach account's Config delivery channel writes to the operational bucket; the security account's aggregator shows compliance for every account.
  7. Operational logs: flow logs and applications
  8. Flow logs write straight to S3AWSEach VPC's flow log delivers to the operational bucket in 666666666666, in a custom format.
  9. Applications log to CloudWatch Logs locallyAWSLambda, ECS, API Gateway and the CloudWatch agent write to log groups in their own account, with short retention (for example 30 days).
  10. A subscription forwards each eventAWSAn account-level subscription filter (or one per log group) sends events to the CloudWatch Logs destination in 666666666666.
  11. Firehose writes them to S3AWSThe destination feeds a Data Firehose stream that decompresses the records, partitions them by source account and date, and buffers them into S3 objects.
  12. Lifecycle rules cut costAWSObjects move to Glacier storage classes after 90 days and expire after 7 years.
  13. Use
  14. Search with AthenaYouFrom the security account, SQL over any account, Region and date range, scanning only the matching partitions.
  15. Respond to alarmsYouAlarms and EventBridge rules notify the security team through SNS.

Build it

Step 1

Log archive buckets and key (in 666666666666)

Two buckets: an audit bucket for CloudTrail with Object Lock, and an operational bucket for Config, flow logs and application logs with versioning and lifecycle rules. One customer managed key encrypts both.

log-archive.yaml 
LogKey:
  Type: AWS::KMS::Key
  Properties:
    EnableKeyRotation: true
    KeyPolicy:
      Version: "2012-10-17"
      Statement:
        - Sid: AccountAdmin
          Effect: Allow
          Principal:
            AWS: arn:aws:iam::666666666666:root
          Action: kms:*
          Resource: "*"
        - Sid: CloudTrailEncrypt                        # without this, the trail can't deliver
          Effect: Allow
          Principal:
            Service: cloudtrail.amazonaws.com
          Action: [ kms:GenerateDataKey*, kms:DescribeKey ]
          Resource: "*"
          Condition:
            StringEquals:
              aws:SourceArn: arn:aws:cloudtrail:us-east-1:000000000000:trail/org-trail
        - Sid: LogDeliveryAndFirehose                   # Config, flow logs and Firehose writing SSE-KMS objects
          Effect: Allow
          Principal:
            Service: [ config.amazonaws.com, delivery.logs.amazonaws.com ]
          Action: [ kms:GenerateDataKey*, kms:Decrypt ]
          Resource: "*"                                  # add aws:SourceAccount / aws:SourceArn conditions for your accounts
        - Sid: SecurityReaders                          # Athena in the security account must decrypt
          Effect: Allow
          Principal:
            AWS: arn:aws:iam::555555555555:role/LogAnalyst
          Action: kms:Decrypt
          Resource: "*"

AuditBucket:
  Type: AWS::S3::Bucket
  Properties:
    BucketName: org-audit-666666666666
    VersioningConfiguration:   # required by Object Lock
      Status: Enabled
    ObjectLockEnabled: true
    ObjectLockConfiguration:
      ObjectLockEnabled: Enabled
      Rule:
        DefaultRetention:   # can be extended, never shortened
          Mode: COMPLIANCE
          Years: 7
    BucketEncryption:
      ServerSideEncryptionConfiguration:
        - ServerSideEncryptionByDefault:
            SSEAlgorithm: aws:kms
            KMSMasterKeyID: !Ref LogKey
          BucketKeyEnabled: true                       # far fewer KMS calls
    PublicAccessBlockConfiguration:
      { BlockPublicAcls: true, BlockPublicPolicy: true, IgnorePublicAcls: true, RestrictPublicBuckets: true }
    LifecycleConfiguration:
      Rules:
        - Id: archive-then-expire
          Status: Enabled
          Transitions:
            - StorageClass: GLACIER_IR   # still millisecond reads
              TransitionInDays: 90
            - StorageClass: DEEP_ARCHIVE
              TransitionInDays: 365
          ExpirationInDays: 2557                       # 7 years
          NoncurrentVersionExpiration:
            NoncurrentDays: 2557

# OperationalBucket (org-logs-666666666666): same encryption, versioning and lifecycle, no Object Lock

The audit bucket policy lets only the organization trail write, using the trail's ARN as aws:SourceArn:

      },

      },

        "arn:aws:s3:::org-audit-666666666666/AWSLogs/o-a1b2c3d4e5/*"

    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",

      }
    }

}

Object Lock needs versioning, and once enabled it can't be turned off. It can now be enabled on an existing bucket, but it only protects objects written afterwards. In compliance mode the retention can be extended but never shortened, and the only way to delete a locked object early is to close the account, so test with governance mode first.

Step 2

Organization trail (in 000000000000)

org-trail.yaml 
OrgTrail:
  Type: AWS::CloudTrail::Trail
  Properties:
    TrailName: org-trail
    IsOrganizationTrail: true                    # every account, now and in future
    IsMultiRegionTrail: true                     # every Region
    IncludeGlobalServiceEvents: true
    EnableLogFileValidation: true                # signed hourly digest files
    IsLogging: true
    S3BucketName: org-audit-666666666666
    KMSKeyId: arn:aws:kms:us-east-1:666666666666:key/1234abcd-12ab-34cd-56ef-1234567890ab
    CloudWatchLogsLogGroupArn: !GetAtt TrailLogGroup.Arn   # for metric filters and alarms
    CloudWatchLogsRoleArn: !GetAtt TrailToLogsRole.Arn

CloudTrail Lake closed to new customers since May 31, 2026 was an alternative to S3 plus Athena for querying. New setups use the S3 and Athena approach shown here.

Step 3

Config and VPC Flow Logs (StackSet to every account)

A service-managed StackSet from the management account, targeting the Workloads OU with automatic deployment, so new accounts get it. (Control Tower sets up Config delivery to its log archive for you.)

account-logging-baseline.yaml 
ConfigDelivery:
  Type: AWS::Config::DeliveryChannel
  Properties:
    S3BucketName: org-logs-666666666666            # bucket in the log archive account
    S3KeyPrefix: config
    S3KmsKeyArn: arn:aws:kms:us-east-1:666666666666:key/1234abcd-12ab-34cd-56ef-1234567890ab

VpcFlowLog:
  Type: AWS::EC2::FlowLog
  Properties:
    ResourceType: VPC
    ResourceId: !Ref VpcId
    TrafficType: ALL
    LogDestinationType: s3
    LogDestination: arn:aws:s3:::org-logs-666666666666/flowlogs/
    DestinationOptions:
      FileFormat: parquet
      HiveCompatiblePartitions: true
      PerHourPartition: true
    LogFormat: '${account-id} ${vpc-id} ${interface-id} ${pkt-srcaddr} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${action} ${flow-direction}'

The operational bucket's policy must allow config.amazonaws.com and delivery.logs.amazonaws.com to write under their prefixes, with aws:SourceAccount conditions for the accounts in the organization. In the security account, an organization aggregator collects Config data from every account:

OrgAggregator:
  Type: AWS::Config::ConfigurationAggregator
  Properties:
    ConfigurationAggregatorName: org
    OrganizationAggregationSource:
      AllAwsRegions: true
      RoleArn: !GetAtt AggregatorRole.Arn         # Config needs organizations:List* through this role
Step 4

Application log pipeline (in 666666666666)

A CloudWatch Logs destination is the cross-account entry point. Its access policy admits every account in the organization; behind it, a Firehose stream writes to the operational bucket.

app-log-pipeline.yaml 
AppLogsToS3:
  Type: AWS::KinesisFirehose::DeliveryStream
  Properties:
    ExtendedS3DestinationConfiguration:
      BucketARN: arn:aws:s3:::org-logs-666666666666
      RoleARN: !GetAtt FirehoseRole.Arn
      Prefix: 'applogs/account=!{partitionKeyFromQuery:account}/!{timestamp:yyyy/MM/dd}/'
      ErrorOutputPrefix: 'applogs-errors/!{firehose:error-output-type}/'
      BufferingHints:
        IntervalInSeconds: 300
        SizeInMBs: 128
      DynamicPartitioningConfiguration:
        Enabled: true
      ProcessingConfiguration:
        Enabled: true
        Processors:
          - Type: Decompression                   # CloudWatch Logs sends gzip records
            Parameters: [ { ParameterName: CompressionFormat, ParameterValue: GZIP } ]
          - Type: MetadataExtraction              # partition key from the record's "owner" (source account)
            Parameters:
              - ParameterName: MetadataExtractionQuery
                ParameterValue: '{account: .owner}'
              - ParameterName: JsonParsingEngine
                ParameterValue: JQ-1.6

AppLogsDestination:
  Type: AWS::Logs::Destination
  Properties:
    DestinationName: org-app-logs
    TargetArn: !GetAtt AppLogsToS3.Arn
    RoleArn: !GetAtt LogsToFirehoseRole.Arn       # trusts logs.amazonaws.com; firehose:PutRecord*
    DestinationPolicy: >
      {"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":"*",
        "Action":"logs:PutSubscriptionFilter",
        "Resource":"arn:aws:logs:us-east-1:666666666666:destination:org-app-logs",
        "Condition":{"StringEquals":{"aws:PrincipalOrgID":["o-a1b2c3d4e5"]}}}]}

A CloudWatch Logs destination is Regional: log groups can only subscribe to a destination in their own Region. A multi-Region organization needs a destination (and Firehose stream) in each Region, all writing to the same bucket.

Step 5

Subscriptions in every account (StackSet)

Either one account-level subscription filter policy that covers all log groups (excluding the ones that would loop), or a subscription filter on each important log group. With an organization-wide destination policy, each source account also needs a role that CloudWatch Logs uses to send to the destination.

# in each workload account: account-level policy covering every log group
aws logs put-account-policy \
  --policy-name org-central-logging \
  --policy-type SUBSCRIPTION_FILTER_POLICY \
  --scope ALL \
  --policy-document '{"DestinationArn":"arn:aws:logs:us-east-1:666666666666:destination:org-app-logs","RoleArn":"arn:aws:iam::222222222222:role/CWLtoOrgDestination","FilterPattern":"","Distribution":"Random"}' \
  --selection-criteria 'LogGroupName NOT IN ["/aws/lambda/log-forwarder"]'
  • An empty FilterPattern forwards every event; a pattern such as ?ERROR ?WARN forwards fewer and costs less.
  • Each log group can have up to 5 subscription filters, so existing per-team subscriptions keep working.

A subscription that captures the logs of the pipeline itself (a forwarding Lambda function, for example) creates an infinite loop and a large bill. Exclude those log groups with the selection criteria.

Step 6

Query and alert (security account)

An Athena table with partition projection computes partitions from the S3 path, so there's no crawler or MSCK REPAIR to run and queries scan only the days and accounts asked for.

cloudtrail-table.sql 
CREATE EXTERNAL TABLE cloudtrail_org (
  eventversion STRING, useridentity STRUCT<type:STRING, arn:STRING, accountid:STRING, accesskeyid:STRING>,
  eventtime STRING, eventsource STRING, eventname STRING, awsregion STRING,
  sourceipaddress STRING, errorcode STRING, requestparameters STRING
)
PARTITIONED BY (account STRING, region STRING, day STRING)
ROW FORMAT SERDE 'com.amazon.emr.hive.serde.CloudTrailSerde'
STORED AS INPUTFORMAT 'com.amazon.emr.cloudtrail.CloudTrailInputFormat'
OUTPUTFORMAT 'org.apache.hadoop.hive.ql.io.HiveIgnoreKeyTextOutputFormat'
LOCATION 's3://org-audit-666666666666/AWSLogs/o-a1b2c3d4e5/'
TBLPROPERTIES (
  'projection.enabled'='true',
  'projection.account.type'='enum',
  'projection.account.values'='222222222222,555555555555,666666666666',
  'projection.region.type'='enum',
  'projection.region.values'='us-east-1,eu-west-1',
  'projection.day.type'='date',
  'projection.day.format'='yyyy/MM/dd',
  'projection.day.range'='2026/01/01,NOW',
  'storage.location.template'='s3://org-audit-666666666666/AWSLogs/o-a1b2c3d4e5/${account}/CloudTrail/${region}/${day}'
);

-- who deleted security groups last week, in any account?
SELECT eventtime, account, useridentity.arn, sourceipaddress
FROM cloudtrail_org
WHERE eventname = 'DeleteSecurityGroup' AND day >= '2026/10/22';

For alerting, metric filters on the trail's log group turn matching events into metrics with alarms:

ConsoleLoginWithoutMfa:
  Type: AWS::Logs::MetricFilter
  Properties:
    LogGroupName: !Ref TrailLogGroup
    FilterPattern: '{ ($.eventName = "ConsoleLogin") && ($.additionalEventData.MFAUsed != "Yes") && ($.responseElements.ConsoleLogin = "Success") }'
    MetricTransformations:
      - MetricNamespace: Security
        MetricName: ConsoleLoginNoMfa
        MetricValue: "1"
# + an AWS::CloudWatch::Alarm on Security/ConsoleLoginNoMfa >= 1 that notifies SNS
Step 7

Guardrails (SCP on all OUs except the log archive admins)

scp-protect-logging.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectTrail",
      "Effect": "Deny",
      "Action": [ "cloudtrail:StopLogging", "cloudtrail:DeleteTrail", "cloudtrail:UpdateTrail", "cloudtrail:PutEventSelectors" ],
      "Resource": "*"
    },
    {
      "Sid": "ProtectLogBuckets",
      "Effect": "Deny",
      "Action": [ "s3:DeleteBucket", "s3:PutBucketPolicy", "s3:PutLifecycleConfiguration", "s3:PutBucketVersioning" ],
      "Resource": [ "arn:aws:s3:::org-audit-666666666666", "arn:aws:s3:::org-logs-666666666666" ],
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/LogArchiveAdmin"
        }
      }
    },
    {
      "Sid": "ProtectSubscriptions",
      "Effect": "Deny",
      "Action": [ "logs:DeleteAccountPolicy", "logs:DeleteSubscriptionFilter", "ec2:DeleteFlowLogs", "config:StopConfigurationRecorder" ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/stacksets-exec-*"
        }
      }
    }
  ]
}

SCPs don't apply to the management account, which owns the trail, so access to the management account itself must be tightly limited.

Design decisions

DecisionWhy
A separate log archive accountAdministrators of workload accounts, and an attacker who compromises one, can't reach the evidence.
Two bucketsCompliance-mode Object Lock is irreversible, so it's applied only where auditors need it (CloudTrail). Operational logs keep lifecycle flexibility.
Organization trail, not per-account trailsCovers new accounts instantly, and member accounts can't change or stop it.
Store in S3, not long CloudWatch Logs retentionS3 with Glacier classes is far cheaper for years of data; CloudWatch Logs keeps only recent data for live troubleshooting.
Firehose behind the destinationFully managed buffering, decompression, partitioning and delivery; no consumer code to run or scale.
Partition projectionNew accounts, Regions and days need no table maintenance, and queries scan only matching prefixes.
One KMS key with service-specific statementsCentral control and audit of who can read logs; readers need both bucket access and kms:Decrypt.

Most "logs stopped arriving" problems are key policy problems. CloudTrail, Config, log delivery, Firehose and CloudWatch Logs each need permission on the KMS key (and a matching bucket policy). Check the key policy before the bucket policy.

Alternatives

OptionWhen it fits better
CloudWatch Logs centralization rulesYou want application logs copied into CloudWatch Logs in a central account (and optionally a backup Region) for querying there, managed by rules from the management or delegated administrator account. Only new log data is copied.
CloudWatch cross-account observabilityA monitoring account needs to view and query logs, metrics and traces in place, without copying or long-term retention.
Amazon Security LakeSecurity tools (SIEM) should consume CloudTrail, flow logs, Route 53 resolver logs and findings in the standard OCSF format from a managed data lake.
Amazon OpenSearch ServiceAnalysts need full-text search and interactive dashboards over recent logs (Firehose can deliver to it as well as S3).
Control TowerStarting fresh: it creates the log archive and audit accounts, the organization trail and Config delivery for you.

Testing it

  1. Check delivery from a new accountCreate an account in the Workloads OU; within minutes its CloudTrail prefix appears in the audit bucket and the StackSet instance reaches CURRENT.
  2. Check the application pipelineWrite a test event with aws logs put-log-events in a workload account, then look for it under applogs/account=222222222222/ after the Firehose buffer interval.
  3. Prove immutabilityTry to delete a CloudTrail log object version as an administrator; it fails with access denied because of the retention period.
  4. Validate integrityaws cloudtrail validate-logs --trail-arn ... --start-time ... reports every file as valid.
  5. Fire an alarmSign in to a sandbox account's console without MFA and confirm the alarm notifies SNS.

"Centralize logs from all accounts, make them immutable for 7 years, at the lowest cost" is an organization trail and subscription filters into S3 in a log archive account, with Object Lock in compliance mode and lifecycle transitions to Glacier. Keeping seven years in CloudWatch Logs works but costs far more, and governance mode can be bypassed, so neither is the best answer.
