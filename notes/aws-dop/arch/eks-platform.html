End-to-end architecture

EKS platform with GitOps

A platform team runs one Amazon EKS cluster per environment for many application teams. Teams deploy by merging a change to Git; a GitOps controller applies it. Pods get only the AWS permissions they need, nodes appear and disappear with demand (on Spot where it's safe), all telemetry lands in CloudWatch, and Kubernetes upgrades are a routine, repeatable procedure.

Scenario and requirements

Twenty application teams run microservices on shared clusters, one per environment. The platform team owns the clusters; each application team owns one namespace per cluster and must not affect the others.

RequirementDesign choice
Clusters are reproducible and identical across environmentsClusters, add-ons and access defined as code (CloudFormation, CDK, Terraform or eksctl config files)
People get Kubernetes access through IAM, scoped per teamEKS access entries with access policies scoped to each team's namespace
Pods get least-privilege AWS permissionsEKS Pod Identity: one IAM role per service account
Deploy by merging to Git, with drift corrected automaticallyGitOps with Argo CD (the managed EKS capability, or self-installed) syncing a configuration repository
Nodes follow demand and use Spot where safeKarpenter NodePools (or EKS Auto Mode, which runs Karpenter-based autoscaling for you)
No user-facing disruption when nodes are replacedReadiness probes, several replicas and PodDisruptionBudgets on every service
Central logs, metrics and tracesThe Amazon CloudWatch Observability add-on (Container Insights and Application Signals) plus control plane logs
Routine, low-risk Kubernetes upgradesUpgrade insights first, staging before production, one minor version at a time

How it works

Steps marked AWS are done by AWS services or controllers on their own; Platform steps are set up once by the platform team; Team steps are what an application team does for each release.

  1. Cluster foundation
  2. Create the cluster from codePlatformThe cluster, its subnets, add-ons (VPC CNI, CoreDNS, kube-proxy, EKS Pod Identity Agent, CloudWatch Observability) and logging come from one template per environment.
  3. Grant access with access entriesPlatformThe platform role gets cluster-wide admin; each team role gets edit rights in its own namespace only.
  4. Give pods IAM rolesPlatformPod Identity associations map each service account to an IAM role with only the permissions that service needs.
  5. Release
  6. Merge to mainTeamCodeBuild builds the image, scans it, and pushes it to ECR tagged with the commit ID.
  7. Update the configuration repositoryTeamThe build commits the new image tag to the GitOps repository (staging path first). This commit is the deployment.
  8. Argo CD syncsAWSArgo CD sees the change, applies the manifests, and keeps correcting any manual drift.
  9. Rolling updateAWSKubernetes replaces pods gradually; a pod receives traffic only after its readiness probe passes.
  10. Nodes follow demandAWSKarpenter launches nodes for pods that can't be scheduled, and consolidates or removes nodes that are empty or underused.
  11. Promote to productionTeamA pull request copies the tag to the production path; once merged, Argo CD syncs the production cluster.
  12. Operate
  13. Telemetry flows to CloudWatchAWSContainer Insights metrics, container logs, Application Signals traces, and the enabled control plane logs.
  14. Upgrade KubernetesPlatformCheck upgrade insights, upgrade staging's control plane, then nodes and add-ons; repeat for production.

Build it

Step 1

Cluster access with access entries

An access entry links one IAM principal to Kubernetes permissions, through the EKS API rather than the aws-auth ConfigMap (Amazon EKS User Guide, Grant IAM users access to Kubernetes with EKS access entries). Permissions come from AWS-maintained access policies, scoped to the whole cluster or to namespaces:

access.sh (run against the production cluster) 
# Platform team: full admin on the whole cluster
aws eks create-access-entry --cluster-name production \
  --principal-arn arn:aws:iam::222222222222:role/PlatformAdmin
aws eks associate-access-policy --cluster-name production \
  --principal-arn arn:aws:iam::222222222222:role/PlatformAdmin \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster

# Orders team: edit rights in its own namespace only
aws eks create-access-entry --cluster-name production \
  --principal-arn arn:aws:iam::222222222222:role/OrdersTeam
aws eks associate-access-policy --cluster-name production \
  --principal-arn arn:aws:iam::222222222222:role/OrdersTeam \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy \
  --access-scope type=namespace,namespaces=orders
  • Access policies: AmazonEKSClusterAdminPolicy, AmazonEKSAdminPolicy, AmazonEKSEditPolicy and AmazonEKSViewPolicy, similar to the Kubernetes user-facing cluster roles. For finer control, give the entry Kubernetes group names and write RBAC bindings instead.
  • Node roles: managed node groups and Fargate profiles get their access entries automatically.
  • Recovery: because access lives in the EKS API, a lost admin can be restored with an API call, which isn't possible when a broken aws-auth ConfigMap locks everyone out.

When an existing cluster switches to access entries, only the cluster creator's access is created automatically. Roles that were added to the aws-auth ConfigMap are not migrated; create access entries for them before removing the ConfigMap, or those users lose access.

Step 2

Pod permissions with EKS Pod Identity

Each service runs under its own Kubernetes service account. A Pod Identity association maps that service account to an IAM role; the EKS Pod Identity Agent then gives the pods temporary credentials for it. The role's trust policy names the EKS Pod Identity service principal (Amazon EKS User Guide, Assign an IAM role to a Kubernetes service account):

orders-pod-role-trust.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "pods.eks.amazonaws.com"
      },
      "Action": [
        "sts:AssumeRole",
        "sts:TagSession"   // adds cluster, namespace and service account tags
      ]
    }
  ]
}
aws eks create-pod-identity-association --cluster-name production \
  --namespace orders --service-account orders-api \
  --role-arn arn:aws:iam::222222222222:role/OrdersApiPodRole
  • No annotation, no OIDC provider: unlike IAM roles for service accounts (IRSA), nothing is added to the service account, and the same role can be used by several clusters without editing its trust policy (AWS Containers Blog, Amazon EKS Pod Identity: a new way for applications on EKS to obtain IAM credentials).
  • Session tags: the tags Pod Identity adds let a single policy allow access based on the namespace or service account, for ABAC.
  • Who can create associations: the caller needs iam:PassRole for the role.
Step 3

Node autoscaling with Karpenter

Karpenter watches for pods that can't be scheduled and launches nodes that fit them, choosing instance types and purchase options from a NodePool. It also consolidates: removing empty nodes and replacing underused ones with cheaper ones.

nodepool-general.yaml 
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      nodeClassRef:   # AMI, subnets, security groups
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: [ "spot", "on-demand" ]   # Spot preferred when available
        - key: kubernetes.io/arch
          operator: In
          values: [ "amd64", "arm64" ]
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
    budgets:
      - nodes: "10%"   # replace at most 10% of nodes at a time
  limits:   # ceiling for this NodePool
    cpu: "1000"
    memory: 1000Gi
  • Several NodePools: a second NodePool restricted to on-demand, with a taint, keeps stateful or Spot-intolerant workloads off Spot.
  • Spot interruptions: Karpenter can watch an SQS queue fed by EventBridge for Spot interruption warnings and other EC2 events, and moves pods off a node before it's reclaimed.
  • EKS Auto Mode runs this Karpenter-based autoscaling as part of the cluster, and also handles Spot interruption notices, node OS updates and a 21-day maximum node lifetime (Amazon EKS User Guide, Automate cluster infrastructure with EKS Auto Mode). You add custom NodePools alongside its defaults.

Consolidation and node replacement evict pods. A Deployment with one replica, or with no PodDisruptionBudget, can have all its pods evicted at once and go down briefly. PodDisruptionBudgets are respected by Karpenter, by Auto Mode node updates and by managed node group upgrades.

Step 4

GitOps deployment with Argo CD

In GitOps, a Git repository holds the desired state of the cluster, and a controller in or next to the cluster continuously makes the cluster match it. Amazon EKS offers Argo CD as a fully managed EKS capability that runs in EKS rather than on your nodes and can deploy to several clusters from one instance (Amazon EKS User Guide, EKS Capabilities); Argo CD or Flux can also be installed in the cluster yourself.

apps/orders-production.yaml (Argo CD Application) 
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: orders-production
spec:
  project: orders
  source:
    repoURL: https://github.com/acme/platform-config.git
    targetRevision: main
    path: orders/overlays/production   # Kustomize overlay per environment
  destination:
    name: production   # a cluster registered with Argo CD
    namespace: orders
  syncPolicy:
    automated:
      prune: true   # delete what was removed from Git
      selfHeal: true   # undo manual changes in the cluster

The manifests Argo CD applies make the rollout safe:

orders/base/deployment.yaml (excerpt) 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0   # keep full capacity during a release
      maxSurge: 1
  template:
    spec:
      serviceAccountName: orders-api   # mapped to an IAM role by Pod Identity
      containers:
        - name: api
          image: 111111111111.dkr.ecr.us-east-1.amazonaws.com/orders:3f9c2e1
          readinessProbe:   # no traffic until this passes
            httpGet:
              path: /health
              port: 8080
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: orders-api
spec:
  minAvailable: 2   # evictions keep at least two pods running
  selector:
    matchLabels:
      app: orders-api
  • Rollback is a Git revert: the controller applies the previous state, and the history shows who changed what.
  • Cross-account images: the ECR repository policy in 111111111111 allows the node roles of both workload accounts to pull.
Step 5

CI that updates Git instead of the cluster

The build never calls the Kubernetes API. It pushes the image, then changes the image tag in the configuration repository; the GitOps controller does the deployment.

buildspec.yml 
version: 0.2
env:
  secrets-manager:
    GIT_TOKEN: ci/platform-config-token   # write access to the config repo only
phases:
  build:
    commands:
      - TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c1-7)
      - REPO=111111111111.dkr.ecr.us-east-1.amazonaws.com/orders
      - aws ecr get-login-password | docker login -u AWS --password-stdin $REPO
      - docker build -t $REPO:$TAG .
      - docker push $REPO:$TAG
  post_build:
    commands:
      - git clone https://x-access-token:$GIT_TOKEN@github.com/acme/platform-config.git
      - cd platform-config/orders/overlays/staging
      - kustomize edit set image orders=$REPO:$TAG   # staging first
      - git commit -am "orders $TAG to staging" && git push

The CodeBuild project needs privileged mode to build images. Promotion to production is a separate pull request that changes the production overlay, so a person reviews exactly which image goes live.

Step 6

Observability

The Amazon CloudWatch Observability EKS add-on installs the CloudWatch agent and Fluent Bit, turning on Container Insights (node, pod and container metrics and logs) and Application Signals by default. It can get its permissions through Pod Identity:

aws iam attach-role-policy --role-name CloudWatchAgentRole \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

aws eks create-addon --cluster-name production \
  --addon-name amazon-cloudwatch-observability \
  --pod-identity-associations serviceAccount=cloudwatch-agent,roleArn=arn:aws:iam::222222222222:role/CloudWatchAgentRole

Control plane logs are off by default. Turn on the types you need; they go to the log group /aws/eks/production/cluster:

aws eks update-cluster-config --name production \
  --logging '{"clusterLogging":[{"types":["api","audit","authenticator"],"enabled":true}]}'
  • audit records who changed which Kubernetes object; authenticator shows IAM authentication to the cluster, useful when someone gets Unauthorized. controllerManager and scheduler help with scheduling problems.
  • The logs are charged as normal CloudWatch Logs ingestion and storage, so enable the types you'll use.
Step 7

Routine upgrades

The upgrade order comes from the Amazon EKS User Guide (Update existing cluster to new Kubernetes version):

  1. Check readinessEKS upgrade insights scan for problems such as deprecated Kubernetes API use. Fix the manifests in Git first.
  2. Match node versionsNodes should run the same minor version as the control plane before you start.
  3. Upgrade the control planeOne minor version at a time (aws eks update-cluster-version); 1.30 to 1.32 means two upgrades. It can't be paused once started, and running applications keep working.
  4. Upgrade the nodesManaged node groups update in place; Karpenter replaces nodes as its NodeClass AMI selection picks up the new version; Auto Mode updates nodes itself, respecting PodDisruptionBudgets.
  5. Upgrade add-ons and toolsVPC CNI, CoreDNS, kube-proxy, other add-ons, then kubectl on clients.
  6. Staging firstRun the whole procedure in staging, test, then repeat in production.

If problems appear, a cluster can be rolled back to the previous minor version within 7 days of the upgrade.

Design decisions

DecisionWhy
Pod Identity instead of IRSANo OIDC provider per cluster, no service account annotations, and roles reused across clusters without trust policy edits. IRSA remains for cases Pod Identity doesn't cover
Access entries instead of aws-authManaged through the EKS API and IaC, audited in CloudTrail, recoverable if misconfigured, and scoped per namespace with access policies
Karpenter (or Auto Mode) instead of Cluster AutoscalerChooses instance types per pending pod instead of scaling fixed node groups, and consolidates to cut cost. Auto Mode also takes over node patching and add-on management
GitOps pull instead of pipeline pushThe pipeline needs no cluster credentials, drift is corrected automatically, and Git history is the audit trail and the rollback mechanism
One cluster per environmentStaging tests upgrades and platform changes before production; namespaces and access policies separate teams inside each cluster

Alternatives

OptionWhen it fits better
Amazon ECS on FargateTeams don't need Kubernetes; ECS has less to operate and built-in deployment rollback
EKS Fargate profilesNo nodes at all for chosen namespaces, at the cost of no DaemonSets and fewer instance choices
EKS Auto ModeThe platform team wants AWS to manage nodes, autoscaling, load balancing and storage drivers
Flux, or self-installed Argo CDAn existing GitOps setup, or features not offered by the managed capability
Pipeline push (CodeBuild running kubectl or Helm)Few clusters and a team that prefers pipeline-driven deploys; the build role needs an access entry on each cluster

Testing it

  1. AccessAs the Orders team role, confirm you can change objects in orders but get Forbidden in another namespace.
  2. Pod permissionsFrom an orders-api pod, call the allowed DynamoDB table (works) and another table (AccessDenied).
  3. DriftScale a Deployment by hand with kubectl; Argo CD's self-heal restores the replica count from Git.
  4. Scaling and consolidationScale a test workload up and down; watch Karpenter add nodes, then consolidate, while the PodDisruptionBudget keeps two pods running.
  5. Upgrade rehearsalUpgrade staging after clearing upgrade insights, and confirm every service stays available.
