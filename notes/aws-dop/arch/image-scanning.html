End-to-end architecture

Container image scanning and deployment gate

Every container image is checked for known vulnerabilities twice before it can run: once in the build, before it's pushed, and again in Amazon ECR after the push. An image with any CRITICAL or HIGH finding stops the pipeline. Images already running keep being rescanned, and the security team hears about it when a newly published CVE affects one of them.

Scenario and requirements

Teams build container images in CodeBuild, push them to Amazon ECR, and deploy them to Amazon ECS (and some to Amazon EKS). The security team sets the rules below.

RequirementDesign choice
Scan OS packages and application dependencies (npm, pip, Maven and so on)ECR enhanced scanning with Amazon Inspector, not basic scanning
Find problems as early as possibleScan the image in CodeBuild with the Inspector SBOM generator and Scan API before it's pushed
No image with CRITICAL or HIGH findings reaches staging or productionA pipeline gate (the CodePipeline InspectorScan action) with critical and high thresholds of zero, before every deploy stage
The image that was checked is the image that runsImmutable tags, and deployments that reference the image digest
Re-check deployed images when new CVEs are publishedContinuous scanning, plus an EventBridge rule on new CRITICAL findings for images in use
Accepted risks are recorded, not silently ignoredInspector suppression rules managed by the security account, with a written reason

Assume these accounts, all in us-east-1:

AccountIDWhat lives there
Tooling111111111111CodePipeline, CodeBuild, the ECR repositories
Production222222222222ECS services that pull images from the tooling account's ECR
Security555555555555Amazon Inspector delegated administrator: sees findings for all accounts and owns suppression rules

Basic and enhanced scanning

ECR offers two scanning types, chosen per Region for the whole private registry (Amazon ECR User Guide, Scan images for software vulnerabilities in Amazon ECR).

AspectBasic scanningEnhanced scanning
EngineAWS native technology using CVE dataAmazon Inspector
What it findsOperating system package vulnerabilitiesOS and programming language package vulnerabilities
When it scansOn push (for repositories matching a filter) or manually; each image at most once per 24 hoursOn push or continuously (rescanned as new CVEs appear); manual scans aren't supported
Repositories not matching a filterManual scanningNot scanned
Where findings appearECR (DescribeImageScanFindings)ECR and the Inspector console and API; also which ECS and EKS clusters use the image
EventBridge eventsECR Image Scan from aws.ecr when a scan completesInspector2 Scan (initial scan) and Inspector2 Finding (created, updated, closed) from aws.inspector2
CostNo chargeNo extra ECR charge; Inspector charges per image scanned and rescanned
  • Scan duration: with enhanced scanning, Inspector keeps rescanning images for a configurable period after push (by default until the image is deleted). When the period ends, the image's scan status becomes SCAN_ELIGIBILITY_EXPIRED.
  • Turning it on later: when enhanced scanning is first enabled, only images pushed in the last 14 days are scanned; older images show SCAN_ELIGIBILITY_EXPIRED and must be pushed again.
  • Switching types: moving between basic and enhanced means the previous type's scans are no longer available until you switch back.

Basic scanning: scan on push for every repository, and run or read a scan by hand:

aws ecr put-registry-scanning-configuration \
  --scan-type BASIC \
  --rules '[{"repositoryFilters":[{"filter":"*","filterType":"WILDCARD"}],
             "scanFrequency":"SCAN_ON_PUSH"}]'

aws ecr start-image-scan --repository-name orders --image-id imageTag=1.4.2

aws ecr describe-image-scan-findings --repository-name orders \
  --image-id imageTag=1.4.2 \
  --query 'imageScanFindings.findingSeverityCounts'

Enhanced scanning: continuous for production repositories, scan on push for everything else. If several filters match a repository, continuous scanning wins:

aws ecr put-registry-scanning-configuration \
  --scan-type ENHANCED \
  --rules '[{"repositoryFilters":[{"filter":"prod","filterType":"WILDCARD"}],
             "scanFrequency":"CONTINUOUS_SCAN"},
            {"repositoryFilters":[{"filter":"*","filterType":"WILDCARD"}],
             "scanFrequency":"SCAN_ON_PUSH"}]'

A filter without a wildcard matches any repository name that contains it, so prod matches orders-prod and prod-payments; with *, the wildcard stands for zero or more characters.

How it works

Steps marked AWS happen inside AWS services; steps marked Pipeline are stages and actions you define.

  1. Build
  2. Build the imagePipelineCodeBuild runs docker build for the commit.
  3. Scan before pushingPipelineThe Inspector SBOM generator lists the image's packages, the Inspector Scan API checks them, and the build fails on any CRITICAL or HIGH finding. Nothing vulnerable is ever pushed.
  4. Push with an immutable tagPipelineThe repository rejects any attempt to reuse a tag, so the tag always means the same digest.
  5. Gate
  6. Enhanced scan in ECRAWSInspector scans the pushed image and records findings for its digest.
  7. Pipeline gatePipelineAn InspectorScan action scans the ECR image and fails the stage if critical or high findings exceed zero. Later stages never start.
  8. Deploy
  9. Deploy by digestPipelineThe ECS task definition references orders@sha256:..., the exact image that passed the gate.
  10. After deployment
  11. Continuous rescansAWSWhen a new CVE is published for a package in the image, Inspector creates a finding and emits an Inspector2 Finding event.
  12. Alert on images in useAWSAn EventBridge rule in the security account matches new CRITICAL findings on images that ECS or EKS are running, and notifies the owning team.
  13. Fix forwardPipelineThe team updates the base image or dependency; the new image passes the same gates and replaces the old one.

Build it

Step 1

Registry scanning configuration and repository

The scanning configuration is a registry-wide resource; the repository adds immutable tags and a lifecycle policy:

ecr.yaml (in 111111111111) 
ScanningConfiguration:
  Type: AWS::ECR::RegistryScanningConfiguration
  Properties:
    ScanType: ENHANCED
    Rules:   # at most two rules
      - ScanFrequency: CONTINUOUS_SCAN
        RepositoryFilters:
          - Filter: "*"
            FilterType: WILDCARD

OrdersRepository:
  Type: AWS::ECR::Repository
  Properties:
    RepositoryName: orders
    ImageTagMutability: IMMUTABLE   # a tag can't be pushed twice
    LifecyclePolicy:
      LifecyclePolicyText: |
        {
          "rules": [{
            "rulePriority": 1,
            "description": "Keep the last 50 images",
            "selection": {
              "tagStatus": "any",
              "countType": "imageCountMoreThan",
              "countNumber": 50
            },
            "action": { "type": "expire" }
          }]
        }

Organization-wide, the security account (555555555555) is the Inspector delegated administrator and turns on ECR scanning for every member account, so new accounts are covered too.

Step 2

Scan in the build, before push

Amazon Inspector's CI/CD integration combines the Inspector SBOM generator (inspector-sbomgen), which produces a CycloneDX SBOM for an image, with the Inspector Scan API (inspector-scan:ScanSbom), which returns the vulnerabilities in it (Amazon Inspector User Guide, Integrating Amazon Inspector scans into your CI/CD pipeline). Plugins exist for Jenkins, TeamCity, GitHub Actions and GitLab; in CodeBuild, call the two directly. The build role needs inspector-scan:ScanSbom.

buildspec.yml 
version: 0.2
env:
  variables:
    REPO: 111111111111.dkr.ecr.us-east-1.amazonaws.com/orders
phases:
  install:
    commands:
      # install the inspector-sbomgen binary (see the Inspector docs)
      - ./scripts/install-sbomgen.sh
  build:
    commands:
      - TAG=$CODEBUILD_RESOLVED_SOURCE_VERSION
      - docker build -t $REPO:$TAG .
      # 1. list every package in the image
      - ./inspector-sbomgen container --image $REPO:$TAG -o sbom.json
      # 2. check the packages for known vulnerabilities
      - aws inspector-scan scan-sbom --sbom file://sbom.json --output-format INSPECTOR > scan.json
      # 3. fail the build on any CRITICAL or HIGH finding
      - CRIT=$(jq '.inspector.vulnerability_count.critical' scan.json)
      - HIGH=$(jq '.inspector.vulnerability_count.high' scan.json)
      - echo "critical=$CRIT high=$HIGH"
      - |
        if [ "$CRIT" -gt 0 ] || [ "$HIGH" -gt 0 ]; then
          echo "Vulnerabilities found; not pushing"; exit 1
        fi
      # 4. push only after the check passed (still in the build phase)
      - aws ecr get-login-password | docker login --username AWS --password-stdin ${REPO%%/*}
      - docker push $REPO:$TAG
artifacts:
  files: [ sbom.json, scan.json ]   # keep the evidence with the build
  • Output formats: the Scan API returns CycloneDX 1.5 (counts as amazon:inspector:sbom_scanner:critical_vulnerabilities properties) or Inspector JSON (counts under inspector.vulnerability_count), as used above.
  • One command: inspector-sbomgen container --image ... --scan-sbom generates and scans in a single step.

In a buildspec, post_build commands still run after a failed build phase. A push placed in post_build without checking CODEBUILD_BUILD_SUCCEEDING pushes the vulnerable image anyway, which defeats the gate.

Step 3

Gate in the pipeline, after push

The CodePipeline InspectorScan action (category Invoke, provider InspectorScan) scans either source code or an ECR image and fails the action when findings exceed the thresholds you set (AWS CodePipeline User Guide, Amazon Inspector InspectorScan invoke action reference). Each threshold is "the number of vulnerabilities beyond which CodePipeline should fail the action", so zero means any finding fails it.

pipeline stage (excerpt) 
- Name: SecurityGate
  Actions:
    - Name: ScanImage
      ActionTypeId:
        Category: Invoke
        Owner: AWS
        Provider: InspectorScan
        Version: "1"
      Namespace: Scan
      Configuration:
        InspectorRunMode: ECRImageScan
        ECRRepositoryName: orders
        ImageTag: "#{Build.IMAGE_TAG}"   # exported by the build action
        CriticalThreshold: 0
        HighThreshold: 0
      OutputArtifacts:
        - Name: ScanReport   # SBOM with vulnerability details
  • Output variable: HighestScannedSeverity (#{Scan.HighestScannedSeverity}) can be used by later actions, for example in a notification.
  • Permissions: the pipeline role needs inspector-scan:ScanSbom and ECR read actions on the repository. The action runs on managed CodeBuild compute, which is billed separately.

The gate can also be your own CodeBuild step that reads the enhanced findings for the pushed digest. With enhanced scanning, an image's scan status settles at ACTIVE (continuously monitored), not COMPLETE, so a script waits until findings are available rather than for a completed scan:

# findings Inspector holds for this exact image
aws inspector2 list-findings --filter-criteria '{
  "ecrImageHash":   [{"comparison":"EQUALS","value":"'"$DIGEST"'"}],
  "severity":       [{"comparison":"EQUALS","value":"CRITICAL"},
                     {"comparison":"EQUALS","value":"HIGH"}],
  "findingStatus":  [{"comparison":"EQUALS","value":"ACTIVE"}]
}' --query 'length(findings)'

With basic scanning, aws ecr wait image-scan-complete followed by describe-image-scan-findings and its findingSeverityCounts does the same job.

Step 4

Deploy by digest

A tag is only a pointer; a digest identifies the exact image content. Deploying the digest that passed the gate guarantees nothing was swapped in between.

imagedefinitions.json (ECS standard deploy action) 
[
  {
    "name": "orders",
    "imageUri": "111111111111.dkr.ecr.us-east-1.amazonaws.com/orders@sha256:4f1c..."
  }
]

For Amazon EKS, an admission controller (for example, a policy engine such as Kyverno or OPA Gatekeeper) can additionally refuse pods whose image doesn't come from the approved repository or isn't referenced by digest. That is an optional, cluster-side layer on top of the pipeline gate.

Step 5

Alert on new CVEs in images in use

Continuous scanning creates new findings for images that passed the gate months ago. Inspector finding events include the resource type and how many ECS tasks or EKS pods use the image, so a rule can focus on what's actually running (Amazon ECR User Guide, EventBridge events sent for enhanced scanning).

new-critical-in-use-rule.json (in 555555555555) 
{
  "source": ["aws.inspector2"],
  "detail-type": ["Inspector2 Finding"],
  "detail": {
    "severity": ["CRITICAL"],
    "status": ["ACTIVE"],
    "resources": {
      "type": ["AWS_ECR_CONTAINER_IMAGE"],
      "details": {
        "awsEcrContainerImage": {
          "inUseCount": [{ "numeric": [">", 0] }]   // running somewhere
        }
      }
    }
  }
}

Targets: an SNS topic for the owning team, an OpsCenter OpsItem or ticket, and optionally an automation that starts a rebuild pipeline with an updated base image. The same event exists in each member account and in the delegated administrator account.

Step 6

Track exceptions

Sometimes a finding is accepted: the vulnerable code path isn't used, or no fix exists yet. Inspector suppression rules hide matching findings from the default view; they don't close or remediate them, and Inspector keeps the findings until they're fixed (Amazon Inspector User Guide, Suppressing Amazon Inspector findings). Only the delegated administrator (or a standalone account) can create them.

aws inspector2 create-filter \
  --name accept-CVE-2024-0001-orders \
  --action SUPPRESS \
  --reason "Not reachable; fix expected in base image 2026.11" \
  --filter-criteria '{
    "vulnerabilityId":        [{"comparison":"EQUALS","value":"CVE-2024-0001"}],
    "ecrImageRepositoryName": [{"comparison":"EQUALS","value":"orders"}]
  }'

The pipeline gate should apply the same exceptions; otherwise the build keeps failing on an accepted risk. A short allow list of CVE IDs, kept in the repository and reviewed like code, is a common way to do that for the build-time scan.

Design decisions

DecisionWhy
Scan before push and after pushThe build scan stops vulnerable images from ever reaching the registry; the ECR scan is the record of truth and keeps watching after deployment
Enhanced rather than basic scanningMost critical findings today are in application dependencies (for example, a vulnerable Java library), which basic scanning doesn't check; continuous rescans catch CVEs published after release
A pipeline action as the gateScanning on push only reports; something in the release path must read the result and stop the deployment
Immutable tags and deploy by digestThe image that ran the gate is exactly the image that runs in production
Findings managed in the security accountOne place to see every account's images, and exceptions that teams can't grant themselves

Scan on push does not stop anything by itself: ECR still lets anyone pull a vulnerable image, and ECS will run it. Blocking needs a gate that fails on findings, and tags must be immutable, or a vulnerable image can be pushed under a tag that already passed.

Alternatives

OptionWhen it fits better
Basic scanning with an ECR Image Scan gateOnly OS packages matter and cost must be zero; the gate reads findingSeverityCounts after the scan completes
Inspector plugin for Jenkins, GitHub Actions or GitLabThe build runs outside CodeBuild; the plugin wraps the same SBOM generator and Scan API
Third-party scanner in the buildThe company has standardized on another tool; ECR enhanced scanning can still run alongside it
Image signing (AWS Signer with Notation) and verification at deploy timeYou must also prove who built an image (provenance), not only that it has no known vulnerabilities

Testing it

  1. Known-bad imageBuild an image from an old base image with published CRITICAL CVEs in a test repository. The build-time scan fails and nothing is pushed.
  2. Gate after pushPush the same image directly to a test repository and run only the gate stage; the InspectorScan action fails.
  3. Clean imageRebuild with a current base image; both scans pass and the deployment uses the digest.
  4. Tag reuseTry to push a different image under an existing tag; ECR rejects it.
  5. Alert pathCheck that the EventBridge rule matches a real CRITICAL finding (for example, from the known-bad test image while it's referenced by a test ECS task) and that the notification arrives.
