Multi-account CI/CD for a containerized service

A push to main builds and tests a container image once, in a central tooling account. The same image goes to a staging account for integration tests, waits for a person to approve, and then reaches production ECS on Fargate as a canary that rolls back by itself if an alarm fires.

Scenario and requirements

A team runs an orders API on ECS. They want every change released the same way: built once, tested in staging, approved, and released to production gradually, without anyone holding production credentials.

RequirementDesign choice
Code lives in GitHubA source action through AWS CodeConnections
Only changes to the service start a releaseA CodePipeline V2 trigger with branch and file-path filters
Build once, deploy the same image everywhereOne image in the tooling account's ECR, tagged with the commit ID, pulled by every environment
No release with known critical vulnerabilitiesAmazon Inspector enhanced scanning on push, checked by a build step
Teams can't deploy straight to productionDeploys run through roles in the target accounts that only the pipeline can assume
A person signs off before productionA manual approval action that notifies through SNS
Limit the impact of a bad releaseCodeDeploy blue/green for ECS with a canary, a test listener and alarm-based rollback

Assume these accounts, all in us-east-1:

AccountIDWhat lives there
Tooling111111111111CodePipeline (service role PipelineServiceRole), CodeBuild, the ECR repository orders, the artifact bucket tooling-artifacts-111111111111 and its customer managed KMS key
Staging333333333333ECS cluster and service orders, role PipelineDeployRole
Production222222222222ECS on Fargate behind an ALB, the CodeDeploy application and deployment group, role PipelineDeployRole

How it works

Steps marked AWS happen automatically inside AWS services; steps marked Pipeline are actions you define; Person needs a human.

  1. Source
  2. A developer pushes to mainAWSThe trigger checks the branch and changed file paths (src/**, Dockerfile); a README edit doesn't start a release.
  3. Fetch the sourcePipelineThe CodeConnections source action stores the commit in the encrypted artifact bucket and exposes the commit ID as a variable.
  4. Build (tooling account)
  5. Unit tests and image buildPipelineCodeBuild in privileged mode runs the tests, builds the image and pushes it to ECR tagged with the commit ID.
  6. Scan the imageAWSInspector enhanced scanning scans the image on push; the build waits for the result and fails on critical findings.
  7. Staging
  8. Deploy to stagingPipelineThe ECS deploy action runs as PipelineDeployRole in 333333333333 and updates the service with the new image (rolling update with the circuit breaker).
  9. Integration testsPipelineA second CodeBuild project calls the staging endpoint; failure stops the pipeline.
  10. Approval
  11. Approve the releasePersonThe approval action notifies an SNS topic; a release manager approves within 7 days or the action fails.
  12. Production
  13. Start a blue/green deploymentPipelineThe CodeDeployToECS action, as PipelineDeployRole in 222222222222, registers a new task definition and asks CodeDeploy to deploy it.
  14. Start the green task setAWSCodeDeploy starts new tasks in the second target group, reachable on the ALB's test listener (port 8443).
  15. Smoke-test the green tasksPipelineThe AfterAllowTestTraffic hook Lambda function calls the test listener and reports success or failure to CodeDeploy.
  16. Shift 10% of traffic, then the restAWSCodeDeployDefault.ECSCanary10Percent5Minutes: 10% for 5 minutes, then 100%. If a CloudWatch alarm goes off, CodeDeploy moves all traffic back to blue.
  17. Retire the blue tasksAWSAfter the termination wait time, the old task set is removed.

Build it

Step 1

Connection and ECR repository (tooling account)

tooling-shared.yaml (in 111111111111) 
GitHubConnection:
  Type: AWS::CodeStarConnections::Connection
  Properties:
    ConnectionName: github-acme
    ProviderType: GitHub                # created as PENDING; authorize once in the console

OrdersRepository:
  Type: AWS::ECR::Repository
  Properties:
    RepositoryName: orders
    ImageTagMutability: IMMUTABLE       # a commit tag can never point at a different image
    RepositoryPolicyText:
      Version: "2012-10-17"
      Statement:
        - Sid: PullFromWorkloadAccounts
          Effect: Allow
          Principal:
            AWS: [ arn:aws:iam::333333333333:root, arn:aws:iam::222222222222:root ]
          Action: [ ecr:BatchGetImage, ecr:GetDownloadUrlForLayer, ecr:BatchCheckLayerAvailability ]
    LifecyclePolicy:
      LifecyclePolicyText: |
        {"rules":[{"rulePriority":1,"description":"keep last 50 images",
          "selection": {
            "tagStatus":"any",
            "countType":"imageCountMoreThan",
            "countNumber":50
          },
          "action":{"type":"expire"}}]}

Turn on Inspector enhanced scanning for the registry (Inspector console or aws ecr put-registry-scanning-configuration --scan-type ENHANCED) so every pushed image is scanned, and re-scanned when new CVEs are published.

A new connection stays in PENDING until someone completes the handshake with GitHub in the console. A pipeline using it fails at the source action until then; CloudFormation can't authorize it for you.

Pulling a cross-account image needs both sides: this repository policy must allow the workload account, and the ECS task execution role in that account needs ecr:GetAuthorizationToken and the pull actions (the managed policy AmazonECSTaskExecutionRolePolicy covers them). Tasks stuck in PENDING with CannotPullContainerError usually mean one of the two is missing.

Step 2

Artifact key and bucket (tooling account)

Deploy actions in the other accounts read artifacts from this bucket, so both the key policy and the bucket policy must grant their deploy roles.

tooling-artifacts.yaml (in 111111111111) 
ArtifactKey:
  Type: AWS::KMS::Key
  Properties:
    EnableKeyRotation: true
    KeyPolicy:
      Version: "2012-10-17"
      Statement:
        - Sid: ToolingAccountAdmin
          Effect: Allow
          Principal:
            AWS: arn:aws:iam::111111111111:root
          Action: kms:*
          Resource: "*"
        - Sid: DeployRolesUseKey
          Effect: Allow
          Principal:
            AWS:
              - arn:aws:iam::333333333333:role/PipelineDeployRole
              - arn:aws:iam::222222222222:role/PipelineDeployRole
          Action: [ kms:Decrypt, kms:DescribeKey ]
          Resource: "*"

ArtifactBucket:
  Type: AWS::S3::Bucket
  Properties:
    BucketName: tooling-artifacts-111111111111
    BucketEncryption:
      ServerSideEncryptionConfiguration:
        - ServerSideEncryptionByDefault:
            SSEAlgorithm: aws:kms
            KMSMasterKeyID: !GetAtt ArtifactKey.Arn

ArtifactBucketPolicy:
  Type: AWS::S3::BucketPolicy
  Properties:
    Bucket: !Ref ArtifactBucket
    PolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Sid: DeployRolesReadArtifacts
          Effect: Allow
          Principal:
            AWS:
              - arn:aws:iam::333333333333:role/PipelineDeployRole
              - arn:aws:iam::222222222222:role/PipelineDeployRole
          Action: [ s3:GetObject, s3:GetObjectVersion ]
          Resource: !Sub ${ArtifactBucket.Arn}/*

The default AWS managed key aws/s3 can't be shared across accounts, because you can't edit its key policy. A cross-account pipeline needs a customer managed key like this one. "Access denied reading the input artifact" in a staging or production action points to the key policy or bucket policy.

Deploy the target accounts' roles (Step 3) before this stack. A key or bucket policy that names a role that doesn't exist yet is rejected.

Step 3

Deploy roles in the target accounts (StackSet)

Deploy this from the management account (or a delegated administrator) as a service-managed StackSet to the staging and production accounts, so every environment gets the same role.

pipeline-deploy-role.yaml (in 333333333333 and 222222222222) 
PipelineDeployRole:
  Type: AWS::IAM::Role
  Properties:
    RoleName: PipelineDeployRole
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:   # only the pipeline
            AWS: arn:aws:iam::111111111111:role/PipelineServiceRole
          Action: sts:AssumeRole
    Policies:
      - PolicyName: deploy-orders
        PolicyDocument:
          Version: "2012-10-17"
          Statement:
            - Effect: Allow                                 # ECS deploy action (staging)
              Action: [ ecs:DescribeServices, ecs:DescribeTaskDefinition, ecs:RegisterTaskDefinition, ecs:UpdateService, ecs:TagResource ]
              Resource: "*"
            - Effect: Allow                                 # CodeDeployToECS action (production)
              Action: [ codedeploy:CreateDeployment, codedeploy:GetDeployment, codedeploy:GetApplication, codedeploy:GetApplicationRevision, codedeploy:RegisterApplicationRevision, codedeploy:GetDeploymentConfig ]
              Resource: "*"
            - Effect: Allow
              Action: iam:PassRole                           # the task and execution roles
              Resource: !Sub arn:aws:iam::${AWS::AccountId}:role/orders-*
              Condition:
                StringEquals:
                  iam:PassedToService: ecs-tasks.amazonaws.com
            - Effect: Allow                                 # read artifacts from the tooling account
              Action: [ s3:GetObject, s3:GetObjectVersion ]
              Resource: arn:aws:s3:::tooling-artifacts-111111111111/*
            - Effect: Allow
              Action: [ kms:Decrypt, kms:DescribeKey ]
              Resource: arn:aws:kms:us-east-1:111111111111:key/*

In the tooling account, PipelineServiceRole needs sts:AssumeRole on arn:aws:iam::*:role/PipelineDeployRole in the two target accounts.

Step 4

buildspec.yml

The build project uses a standard Linux image with privileged mode on, which Docker builds need. It produces one artifact with everything both deploy actions read.

buildspec.yml 
version: 0.2
env:
  variables:
    REPO: 111111111111.dkr.ecr.us-east-1.amazonaws.com/orders
phases:
  pre_build:
    commands:
      - TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c1-12)      # commit ID
      - aws ecr get-login-password | docker login --username AWS --password-stdin ${REPO%%/*}
      - npm ci && npm test                                               # unit tests
  build:
    commands:
      - docker build -t $REPO:$TAG .
  post_build:
    commands:
      - docker push $REPO:$TAG
      - ./scripts/fail-on-critical.sh orders $TAG      # polls describe-image-scan-findings until findings are ready, exits 1 on CRITICAL
      - printf '[{"name":"orders","imageUri":"%s"}]' $REPO:$TAG > imagedefinitions.json   # ECS deploy action (staging)
      - printf '{"ImageURI":"%s"}' $REPO:$TAG > imageDetail.json                          # CodeDeployToECS (production)
reports:
  unit-tests:
    files: [ "reports/junit.xml" ]
    file-format: JUNITXML
artifacts:
  files:
    - imagedefinitions.json
    - imageDetail.json
    - deploy/taskdef-prod.json
    - deploy/appspec.yaml

The staging ECS deploy action uses imagedefinitions.json (container name and image). The production CodeDeployToECS action uses imageDetail.json (just the image URI) plus a task definition template and an AppSpec file. Mixing them up is a common cause of "file not found" deploy errors.

Step 5

Production deployment files

The pipeline fills in two placeholders: <IMAGE1_NAME> in the task definition becomes the image URI from imageDetail.json, and <TASK_DEFINITION> in the AppSpec becomes the ARN of the newly registered task definition.

deploy/taskdef-prod.json (excerpt) 
{
  "family": "orders",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "512", "memory": "1024",
  "executionRoleArn": "arn:aws:iam::222222222222:role/orders-execution-role",
  "taskRoleArn": "arn:aws:iam::222222222222:role/orders-task-role",
  "containerDefinitions": [{
    "name": "orders",
    "image": "<IMAGE1_NAME>",
    "portMappings": [{ "containerPort": 8080 }]
  }]
}
deploy/appspec.yaml 
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: <TASK_DEFINITION>
        LoadBalancerInfo:
          ContainerName: orders
          ContainerPort: 8080
Hooks:
  - AfterAllowTestTraffic: orders-smoke-test     # Lambda: call the test listener, report the result

The CodeDeploy deployment group in 222222222222 (created with the ECS service, using the CODE_DEPLOY deployment controller) holds the rest:

  • the ALB's production listener (443) and test listener (8443), and the blue and green target groups;
  • deployment configuration CodeDeployDefault.ECSCanary10Percent5Minutes;
  • automatic rollback on deployment failure and when alarms fire (5xx rate, p99 latency);
  • the wait time before the old tasks are terminated.
Step 6

The pipeline (tooling account)

pipeline.yaml (in 111111111111, abridged) 
OrdersPipeline:
  Type: AWS::CodePipeline::Pipeline
  Properties:
    PipelineType: V2
    ExecutionMode: QUEUED                         # releases run in order, none skipped
    RoleArn: arn:aws:iam::111111111111:role/PipelineServiceRole
    ArtifactStore:
      Type: S3
      Location: tooling-artifacts-111111111111
      EncryptionKey:   # customer managed key
        Type: KMS
        Id: !GetAtt ArtifactKey.Arn
    Triggers:
      - ProviderType: CodeStarSourceConnection
        GitConfiguration:
          SourceActionName: Source
          Push:
            - Branches: { Includes: [ main ] }
              FilePaths:
                Includes: [ "src/**", "Dockerfile", "deploy/**" ]
    Stages:
      - Name: Source
        Actions:
          - Name: Source
            ActionTypeId:
              Category: Source
              Owner: AWS
              Provider: CodeStarSourceConnection
              Version: "1"
            Configuration:
              ConnectionArn: !Ref GitHubConnection
              FullRepositoryId: acme/orders
              BranchName: main
            OutputArtifacts: [ { Name: SourceOutput } ]
            Namespace: SourceVariables                # exposes #{SourceVariables.CommitId}

      - Name: Build
        Actions:
          - Name: TestAndBuildImage
            ActionTypeId:
              Category: Build
              Owner: AWS
              Provider: CodeBuild
              Version: "1"
            Configuration:
              ProjectName: orders-build
            InputArtifacts: [ { Name: SourceOutput } ]
            OutputArtifacts: [ { Name: BuildOutput } ]

      - Name: Staging
        Actions:
          - Name: DeployStaging
            ActionTypeId:
              Category: Deploy
              Owner: AWS
              Provider: ECS
              Version: "1"
            RoleArn: arn:aws:iam::333333333333:role/PipelineDeployRole     # runs in staging
            Configuration:
              ClusterName: orders
              ServiceName: orders
              FileName: imagedefinitions.json
            InputArtifacts: [ { Name: BuildOutput } ]
            RunOrder: 1
          - Name: IntegrationTests
            ActionTypeId:
              Category: Test
              Owner: AWS
              Provider: CodeBuild
              Version: "1"
            Configuration:
              ProjectName: orders-integration-tests
            InputArtifacts: [ { Name: SourceOutput } ]
            RunOrder: 2

      - Name: Approval
        Actions:
          - Name: ReleaseManagerApproval
            ActionTypeId:
              Category: Approval
              Owner: AWS
              Provider: Manual
              Version: "1"
            Configuration:
              NotificationArn: arn:aws:sns:us-east-1:111111111111:release-approvals
              CustomData: "Commit #{SourceVariables.CommitId} passed staging. Approve for production?"

      - Name: Production
        Actions:
          - Name: BlueGreenDeploy
            ActionTypeId:
              Category: Deploy
              Owner: AWS
              Provider: CodeDeployToECS
              Version: "1"
            RoleArn: arn:aws:iam::222222222222:role/PipelineDeployRole     # runs in production
            Configuration:
              ApplicationName: orders
              DeploymentGroupName: orders-prod
              TaskDefinitionTemplateArtifact: BuildOutput
              TaskDefinitionTemplatePath: deploy/taskdef-prod.json
              AppSpecTemplateArtifact: BuildOutput
              AppSpecTemplatePath: deploy/appspec.yaml
              Image1ArtifactName: BuildOutput            # contains imageDetail.json
              Image1ContainerName: IMAGE1_NAME           # replaces <IMAGE1_NAME>
            InputArtifacts: [ { Name: BuildOutput } ]

Everything runs in one Region, so a single artifact store is enough. A cross-Region action would need an artifact store (and key) in each Region it deploys to.

Design decisions

DecisionWhy
Central tooling accountBuild tools, credentials and pipeline history live apart from workloads; developers get no deploy rights in production.
Build once, promote the same imageWhat was tested in staging is exactly what reaches production; immutable tags guarantee it.
Rolling update in staging, blue/green in productionStaging only needs speed. Production gets a test listener, a canary and instant rollback by moving traffic back.
Hook on AfterAllowTestTrafficTests the green tasks through the test listener before any customer traffic reaches them.
Alarm-based rollbackThe canary is only useful if something watches it; CodeDeploy rolls back as soon as an alarm fires.
Roles deployed with StackSetsNew environments get an identical, reviewed deploy role automatically.
Queued execution modeEach approved commit is released in order instead of newer runs superseding older ones.

Alternatives

OptionWhen it fits better
ECS built-in blue/green (deployment controller ECS)You want blue/green, canary or linear without a CodeDeploy application; the standard ECS deploy action can drive it.
ECS rolling update with the deployment circuit breakerSimple services where a short mixed-version period is acceptable
ECR source action (image push starts the pipeline)Images are built elsewhere and the pipeline only deploys
One pipeline per accountRarely better: harder to promote one artifact, and credentials spread across accounts
CDK PipelinesInfrastructure and application are both in CDK and the pipeline should update itself

Testing it

  1. Check the triggerPush a README-only change and confirm no execution starts; push a change under src/ and confirm it does.
  2. Check the scan gateBuild an image from a base image with a known critical CVE; the build should fail before staging.
  3. Check rollbackRelease a version that returns 500 on part of the traffic; the alarm should fire during the 10% canary and CodeDeploy should move traffic back to blue.
  4. Check isolationTry to assume PipelineDeployRole from a developer role; it should be denied.

"Deploy from a central account to several workload accounts" is one pipeline in a tooling account, a customer managed KMS key shared with the target accounts, and an action-level RoleArn pointing to a role in each target account. Answers that copy access keys into the pipeline or use the aws/s3 key are wrong.
