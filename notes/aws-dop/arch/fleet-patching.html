End-to-end architecture

Fleet patching and compliance across accounts

Hundreds of Linux and Windows instances in many accounts are patched every month inside approved maintenance windows, critical vulnerabilities are fixed within seven days, one security account sees the compliance of the whole fleet, and noncompliant instances are fixed automatically. Instances in Auto Scaling groups are not patched in place; they're replaced from a freshly built golden AMI.

Scenario and requirements

A company runs several hundred EC2 instances, Amazon Linux 2023 and Windows Server, in many workload accounts. Some are long-lived servers; others belong to Auto Scaling groups. Auditors require monthly patching, critical CVEs fixed within seven days, and a single place to prove compliance.

RequirementDesign choice
Every instance can be patched, including new onesSystems Manager manages all instances: Default Host Management Configuration (DHMC) or an instance profile
Same rules in every account and RegionA Quick Setup patch policy targeting the Workloads OU, with custom patch baselines
Patch only in approved hoursInstall on a schedule (patch policy) or in a maintenance window for servers with special timing
Know about critical CVEs quicklyAmazon Inspector continuous scanning, enabled organization-wide
One place to prove complianceConfig rules and Security Hub controls, aggregated in the security account
Fix critical findings within seven days, automaticallyEventBridge on critical Inspector findings starts an Automation runbook that patches the instance
Auto Scaling instances stay patched after scale-outEC2 Image Builder rebuilds the golden AMI; an instance refresh replaces running instances

How it works

Steps marked AWS happen automatically inside AWS services; steps marked You are configuration you build once.

  1. Make instances manageable
  2. Turn on DHMC in every account and RegionYouSystems Manager gives every instance with SSM Agent and IMDSv2 a default role, so no instance profile change is needed.
  3. Instances register as managed nodesAWSThey appear in Fleet Manager and can be scanned and patched.
  4. Patch on a schedule
  5. Define baselines and a patch policyYouThe baselines say which patches are approved; the policy targets the Workloads OU and both Regions with a daily scan and a monthly install schedule.
  6. Daily scanAWSAWS-RunPatchBaseline with Operation: Scan reports missing patches without changing anything.
  7. Monthly installAWSThe same document with Operation: Install installs approved patches and reboots if needed.
  8. Find vulnerabilities
  9. Inspector scans continuouslyAWSNew CVEs are matched against installed packages within hours, with findings in the security account.
  10. Report compliance
  11. Config rules evaluate every instanceAWSec2-instance-managed-by-systems-manager and ec2-managedinstance-patch-compliance-status-check; Security Hub shows them as controls SSM.1 and SSM.2.
  12. Remediate fast
  13. A critical finding raises an eventAWSEventBridge in the security account matches Inspector findings with severity CRITICAL.
  14. An Automation runbook patches that instanceAWSIt runs AWS-RunPatchBaseline with Install on the affected instance, in its own account, and notifies the owner.
  15. Auto Scaling groups
  16. Image Builder builds a new golden AMIAWSOn a schedule, or when updated packages are available, with tests before distribution.
  17. An instance refresh replaces instancesAWSIn batches, with a checkpoint and automatic rollback, so every new instance launches already patched.

Build it

Step 1

Make every instance managed

Default Host Management Configuration is an account- and Region-level setting: Systems Manager supplies a default role to every instance, so teams don't need to attach instance profiles. It needs IMDSv2 on the instances and SSM Agent 3.2.582.0 or later. Run in each workload account and Region (a StackSet or a Quick Setup host-management configuration can do this for the OU):

# the role DHMC gives instances
aws iam create-role \
  --role-name AWSSystemsManagerDefaultEC2InstanceManagementRole \
  --path /service-role/ \
  --assume-role-policy-document file://trust-ssm.json   # Principal: ssm.amazonaws.com

aws iam attach-role-policy \
  --role-name AWSSystemsManagerDefaultEC2InstanceManagementRole \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedEC2InstanceDefaultPolicy

# turn on DHMC in this account and Region
aws ssm update-service-setting \
  --setting-id arn:aws:ssm:us-east-1:222222222222:servicesetting/ssm/managed-instance/default-ec2-instance-management-role \
  --setting-value service-role/AWSSystemsManagerDefaultEC2InstanceManagementRole

If an instance already has an instance profile that allows ssm:UpdateInstanceInformation, SSM Agent uses the instance profile, not DHMC. Either way works; what matters is that every instance is managed.

Step 2

Patch baselines

A baseline approves patches by rule: here, security and bug-fix patches for Amazon Linux 2023 seven days after release, so a bad patch has time to be noticed first. A second baseline would do the same for Windows with CLASSIFICATION and MSRC_SEVERITY filters.

patch-baseline.yaml 
Al2023Baseline:
  Type: AWS::SSM::PatchBaseline
  Properties:
    Name: examplecorp-al2023
    OperatingSystem: AMAZON_LINUX_2023
    DefaultBaseline: true            # used when no other baseline applies
    ApprovalRules:
      PatchRules:
        - PatchFilterGroup:
            PatchFilters:
              - Key: CLASSIFICATION
                Values: [ Security, Bugfix ]
              - Key: SEVERITY
                Values: [ Critical, Important, Medium ]
          ApproveAfterDays: 7          # auto-approve a week after release
          ComplianceLevel: CRITICAL     # missing ones show as critical noncompliance
    ApprovedPatchesComplianceLevel: HIGH   # for patches approved by name
Step 3

Patch policy or maintenance window

Patch policies (created in Systems Manager Quick Setup, from the management account or the delegated administrator) are the recommended way to patch at scale. One policy chooses the baselines, the target OUs and Regions, a scan schedule and an install schedule, whether to reboot, and where to write logs. Quick Setup deploys it to every account in the OU, including accounts added later.

For servers that need a precise window or a specific order, a maintenance window runs the same document under your control:

maintenance-window.yaml 
PatchWindow:
  Type: AWS::SSM::MaintenanceWindow
  Properties:
    Name: monthly-patching
    Schedule: cron(0 2 ? * SUN#2 *)   # second Sunday, 02:00 UTC
    Duration: 4                       # hours
    Cutoff: 1                         # no new tasks in the last hour
    AllowUnassociatedTargets: false

PatchTargets:
  Type: AWS::SSM::MaintenanceWindowTarget
  Properties:
    WindowId: !Ref PatchWindow
    ResourceType: INSTANCE
    Targets:
      - Key: tag:PatchWindow
        Values: [ monthly ]

PatchTask:
  Type: AWS::SSM::MaintenanceWindowTask
  Properties:
    WindowId: !Ref PatchWindow
    TaskType: RUN_COMMAND
    TaskArn: AWS-RunPatchBaseline
    Priority: 1
    MaxConcurrency: 10%               # patch a tenth of the targets at a time
    MaxErrors: 5%                     # stop if more than 5% fail
    Targets:
      - Key: WindowTargetIds
        Values: [ !Ref PatchTargets ]
    TaskInvocationParameters:
      MaintenanceWindowRunCommandParameters:
        Parameters:
          Operation: [ Install ]          # Scan only reports
          RebootOption: [ RebootIfNeeded ]   # or NoReboot
  • Operation: Scan reports what's missing; Install installs approved patches. Compliance data is reported back to Patch Manager either way.
  • RebootOption: RebootIfNeeded (the default) reboots after installing anything. NoReboot leaves patches as installed pending reboot, and the instance shows as noncompliant until it reboots and is scanned again.
Step 4

Vulnerability scanning with Inspector

# in 000000000000 (management)
aws inspector2 enable-delegated-admin-account \
  --delegated-admin-account-id 555555555555

# in 555555555555: turn scanning on for accounts that join later
aws inspector2 update-organization-configuration \
  --auto-enable ec2=true,ecr=true,lambda=true

# ...and activate existing member accounts
aws inspector2 enable \
  --account-ids 222222222222 333333333333 \
  --resource-types EC2 ECR LAMBDA

Inspector uses the SSM Agent on managed instances (or agentless snapshot scanning for unmanaged ones), so Step 1 also improves vulnerability coverage.

Step 5

Compliance reporting

Two organization Config rules, deployed from the security account, answer the two audit questions: is every instance managed, and is every managed instance patched?

patch-compliance-rules.yaml (in 555555555555) 
InstancesManaged:
  Type: AWS::Config::OrganizationConfigRule
  Properties:
    OrganizationConfigRuleName: instances-managed-by-ssm
    OrganizationManagedRuleMetadata:
      RuleIdentifier: EC2_INSTANCE_MANAGED_BY_SSM

InstancesPatched:
  Type: AWS::Config::OrganizationConfigRule
  Properties:
    OrganizationConfigRuleName: instances-patch-compliant
    OrganizationManagedRuleMetadata:
      RuleIdentifier: EC2_MANAGEDINSTANCE_PATCH_COMPLIANCE_STATUS_CHECK

Security Hub runs the same checks as controls SSM.1 (instances managed by Systems Manager) and SSM.2 (patch compliance status COMPLIANT), and its cross-Region aggregation in the security account gives the auditors one dashboard. Patch Manager's own compliance reports can also be exported to S3 on a schedule for detailed, per-patch evidence.

Step 6

Fast fix for critical CVEs

Inspector findings from every member account arrive in the delegated administrator's EventBridge. A rule sends critical EC2 findings to an Automation runbook:

critical-cve-rule.yaml (in 555555555555) 
CriticalCveRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [ aws.inspector2 ]
      detail-type: [ Inspector2 Finding ]
      detail:
        severity: [ CRITICAL ]
        status: [ ACTIVE ]
        resources:
          type: [ AWS_EC2_INSTANCE ]
    Targets:
      - Id: patch-now
        Arn: !Sub arn:aws:ssm:${AWS::Region}:${AWS::AccountId}:automation-definition/PatchInstanceNow:$DEFAULT
        RoleArn: !GetAtt EventsToAutomationRole.Arn
        InputTransformer:
          InputPathsMap:
            instance: $.detail.resources[0].id
            account: $.detail.awsAccountId
          InputTemplate: '{"InstanceId":["<instance>"],"TargetAccount":["<account>"]}'

The PatchInstanceNow runbook assumes a role in the target account, runs AWS-RunPatchBaseline with Install on that instance (an aws:runCommand step), runs a scan, and notifies the instance owner. If the instance belongs to an Auto Scaling group, it instead starts the golden AMI pipeline from Step 7.

Step 7

Golden AMIs for Auto Scaling groups

Patching an Auto Scaling instance in place doesn't last: the next scale-out launches from the old AMI. Instead, Image Builder rebuilds the AMI and updates the launch template, and an instance refresh rolls it out.

golden-ami-pipeline.yaml (in each workload account) 
WebAmiPipeline:
  Type: AWS::ImageBuilder::ImagePipeline
  Properties:
    Name: web-golden-ami
    ImageRecipeArn: !Ref WebRecipe   # base AMI + components (updates, agents, hardening)
    InfrastructureConfigurationArn: !Ref BuildInfra
    DistributionConfigurationArn: !Ref WebDistribution   # updates the launch template
    ImageTestsConfiguration:
      ImageTestsEnabled: true
    Schedule:
      ScheduleExpression: cron(0 3 ? * MON *)
      PipelineExecutionStartCondition: EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE
# roll the new launch template version out to the group
aws autoscaling start-instance-refresh \
  --auto-scaling-group-name web-asg \
  --preferences '{
      "MinHealthyPercentage": 90,
      "InstanceWarmup": 300,
      "CheckpointPercentages": [20, 100],
      "CheckpointDelay": 600,
      "SkipMatching": true,
      "AutoRollback": true
    }'
  • EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE builds on the schedule only when the base image or components have changed, so unchanged weeks cost nothing.
  • Checkpoints pause after 20% of the instances so alarms can catch a bad AMI; AutoRollback returns to the previous launch template if the refresh fails.

Design decisions

DecisionWhy
Patch long-lived servers in place, replace Auto Scaling instancesServers keep their state and identity; Auto Scaling instances are disposable, and only a new AMI keeps future launches patched
Patch policies over patch groups and per-account windowsOne policy covers every account and Region in the OU, including new accounts; patch groups and windows must be created in each account
DHMC over instance profilesInstances become managed without every team changing their roles; instance profiles still work where teams already use them
ApproveAfterDays: 7A short delay lets bad patches be withdrawn before they reach production; critical CVEs are handled by the fast path instead
Scan daily, install monthlyCompliance data stays current without changing servers outside approved windows
Remediate from the security accountOne rule and one runbook for all accounts, which workload teams can't switch off

An instance that Systems Manager can't manage (no SSM Agent, no role, no route to the Systems Manager endpoints) doesn't appear in patch compliance at all, so it looks like nothing is wrong. That's why the ec2-instance-managed-by-systems-manager rule (SSM.1) is as important as the patch compliance rule.

Alternatives

OptionWhen it fits better
Maintenance windows onlyA few accounts, or servers that must be patched in a strict order with pre- and post-patch tasks
AWS-RunPatchBaselineWithHooksApplications that must be stopped and started around patching
Config remediation with AWS-RunPatchBaselineFix any noncompliant instance automatically from the Config rule, without Inspector
Immutable everything (AMI pipeline for all instances)Fully stateless fleets, where replacing is simpler than patching

Testing it

  1. Patch a canary group firstTarget a tagged group of non-production instances a week before production, using the same baselines.
  2. Check compliancePatch Manager's dashboard and Systems Manager Compliance show compliant, noncompliant and pending-reboot counts per account.
  3. Check the audit viewSSM.1 and SSM.2 in Security Hub, aggregated in the security account, must match what Patch Manager reports.
  4. Exercise the fast pathStart the PatchInstanceNow runbook by hand on a test instance, then confirm the instance becomes compliant.
  5. Rehearse rollbackFor Auto Scaling groups, roll back an instance refresh to the previous launch template; for servers, restore from the pre-patch AMI or snapshot.

"Patch EC2 instances across all accounts on a schedule with the least operational overhead" is a Systems Manager patch policy (Quick Setup) with patch baselines. "Report patch compliance across the organization" is the Config patch compliance rule or Security Hub SSM.2. "Instances in an Auto Scaling group keep coming back unpatched" means the fix belongs in the AMI: Image Builder plus an instance refresh.
