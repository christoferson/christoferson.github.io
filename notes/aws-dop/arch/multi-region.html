Multi-Region active/active web application

An online shop serves customers from two Regions at the same time. Each user goes to the nearest Region; if a Region fails, Route 53 stops sending traffic there within a minute or two, and the other Region, which already has the data and enough capacity, carries everything.

Scenario and requirements

The shop's checkout must keep working through the loss of a whole Region, and customers in Europe and North America should get low latency.

RequirementDesign choice
RTO under 5 minutesBoth Regions serve traffic all the time; failover is only a DNS change driven by health checks
RPO of about 1 secondDynamoDB global table (replication typically under a second); S3 Replication Time Control for assets
Low latency for users on both continentsRoute 53 latency-based records
Identical infrastructure in both RegionsOne template deployed to both Regions by the pipeline (cross-Region actions) or a StackSet
The surviving Region must carry all trafficEach Region runs with minimum capacity for the full load (or pre-scaled), and quotas raised in both
Operators can move traffic deliberatelyARC routing controls (or Region switch) to evacuate a Region
Nothing in one Region depends on the otherReplicated secrets, multi-Region KMS keys, ECR replication, per-Region endpoints

How it works

Steps marked AWS happen automatically; steps marked Operator are deliberate human actions.

  1. Normal request
  2. DNS lookupAWSRoute 53 answers shop.example.com with the healthy Region that has the lowest latency for the user: Paris users get eu-west-1, Boston users get us-east-1.
  3. Regional load balancerAWSThe ALB spreads requests over tasks in three Availability Zones.
  4. Local reads and writesAWSThe application uses the DynamoDB replica, the S3 bucket, the secret and the KMS key in its own Region.
  5. ReplicationAWSDynamoDB copies each write to the other Region, typically within a second; S3 replicates new objects.
  6. Region failure
  7. The deep health check failsAWSRoute 53 health checkers can't get a good answer from us-east-1's /health endpoint, which tests the database as well as the web tier.
  8. Route 53 stops answering with that RegionAWSAfter the failure threshold (for example 3 checks at 10-second intervals), only eu-west-1 is returned.
  9. Clients move as their DNS cache expiresAWSWith a 60-second TTL, most traffic moves within a couple of minutes. Some clients cache longer.
  10. The surviving Region absorbs the loadAWSIt already runs enough tasks for the full load; target tracking adds more if needed.
  11. Controlled evacuation and recovery
  12. Pin traffic away from the RegionOperatorTurn the Region's ARC routing control off, so traffic stays away even if its health check flaps back and forth.
  13. Check replication has caught upOperatorAfter the Region recovers, watch DynamoDB ReplicationLatency and S3 replication metrics return to normal.
  14. Return trafficOperatorTurn the routing control back on; latency routing sends nearby users to the Region again.

Build it

Step 1

The Regional stack, deployed to both Regions

One template contains the VPC, ALB, ECS service and alarms. The pipeline deploys it to each Region with a cross-Region CloudFormation action (each Region needs its own artifact bucket), one Region at a time, so a bad change can be stopped before it reaches the second Region.

pipeline deploy stage (excerpt) 
- Name: DeployProd
  Actions:
    - Name: Deploy-us-east-1
      Region: us-east-1
      RunOrder: 1                                   # first Region
      ActionTypeId: { Category: Deploy, Owner: AWS, Provider: CloudFormation, Version: "1" }
      Configuration:
        ActionMode: CREATE_UPDATE
        StackName: shop-regional
        TemplatePath: BuildOutput::regional.yaml
        TemplateConfiguration: BuildOutput::config-us-east-1.json
        RoleArn: arn:aws:iam::222222222222:role/CfnExecutionRole
      InputArtifacts: [ { Name: BuildOutput } ]
    - Name: Deploy-eu-west-1
      Region: eu-west-1
      RunOrder: 2                                   # only after the first Region succeeds
      ActionTypeId: { Category: Deploy, Owner: AWS, Provider: CloudFormation, Version: "1" }
      Configuration:
        ActionMode: CREATE_UPDATE
        StackName: shop-regional
        TemplatePath: BuildOutput::regional.yaml
        TemplateConfiguration: BuildOutput::config-eu-west-1.json
        RoleArn: arn:aws:iam::222222222222:role/CfnExecutionRole
      InputArtifacts: [ { Name: BuildOutput } ]

Inside the template, the ECS service keeps enough tasks to carry both Regions' traffic on its own:

regional.yaml (excerpt) 
ServiceScalingTarget:
  Type: AWS::ApplicationAutoScaling::ScalableTarget
  Properties:
    ServiceNamespace: ecs
    ScalableDimension: ecs:service:DesiredCount
    ResourceId: !Sub service/${Cluster}/${Service.Name}
    MinCapacity: 12          # peak global load, not just this Region's share
    MaxCapacity: 40

Active/active only works if the surviving Region can take all the traffic immediately. Scaling out from half capacity takes minutes, and Fargate, EC2 and other service quotas in that Region may block it. Size the minimum for the full load (or accept a short degradation) and raise quotas in both Regions in advance.

Step 2

DynamoDB global table

Create the table once (in us-east-1) with a replica in each Region. Every replica accepts reads and writes.

global-table.yaml (deployed once, in us-east-1) 
OrdersTable:
  Type: AWS::DynamoDB::GlobalTable
  Properties:
    TableName: orders
    BillingMode: PAY_PER_REQUEST                 # synchronized across replicas
    AttributeDefinitions:
      - { AttributeName: orderId, AttributeType: S }
    KeySchema:
      - { AttributeName: orderId, KeyType: HASH }
    StreamSpecification:
      StreamViewType: NEW_AND_OLD_IMAGES         # required for replication
    SSESpecification:
      SSEEnabled: true
      SSEType: KMS
    Replicas:
      - Region: us-east-1
        PointInTimeRecoverySpecification: { PointInTimeRecoveryEnabled: true }   # set per replica
        SSESpecification: { KMSMasterKeyId: alias/shop-data }
      - Region: eu-west-1
        PointInTimeRecoverySpecification: { PointInTimeRecoveryEnabled: true }
        SSESpecification: { KMSMasterKeyId: alias/shop-data }
  • Conflicts: in the default multi-Region eventual consistency mode, if the same item is written in both Regions at once, the write with the latest timestamp wins ("last writer wins"). Design so each item is usually written in one Region, for example by routing a user's session to one Region.
  • Synchronized settings: capacity mode, write capacity, key schema, GSIs, encryption type and TTL are kept identical across replicas. Point-in-time recovery, deletion protection and tags are not: set them on each replica.
  • Zero RPO: multi-Region strong consistency replicates each write synchronously, but needs exactly three Regions (or two replicas and a witness), must be chosen at creation, and doesn't support TTL or transactions.

Transactions in a global table are atomic only in the Region where they run; the other Region can briefly see part of a transaction. Keep multi-item invariants within one Region's flow.

Step 3

Assets, secrets, keys and images in both Regions

Each Region must be able to run alone, so nothing it needs can live only in the other Region.

replication.yaml (us-east-1 excerpt) 
AssetsBucket:
  Type: AWS::S3::Bucket
  Properties:
    BucketName: shop-assets-use1
    VersioningConfiguration: { Status: Enabled }   # required on both buckets
    ReplicationConfiguration:
      Role: !GetAtt ReplicationRole.Arn
      Rules:
        - Status: Enabled
          Priority: 1
          Filter: {}
          DeleteMarkerReplication: { Status: Enabled }
          Destination:
            Bucket: arn:aws:s3:::shop-assets-euw1
            ReplicationTime: { Status: Enabled, Time: { Minutes: 15 } }   # RTC: 99.99% within 15 minutes
            Metrics: { Status: Enabled, EventThreshold: { Minutes: 15 } }

PaymentApiSecret:
  Type: AWS::SecretsManager::Secret
  Properties:
    Name: prod/shop/payment-api
    KmsKeyId: alias/shop-data
    ReplicaRegions:
      - { Region: eu-west-1, KmsKeyId: alias/shop-data }   # read-only replica, same name

DataKey:
  Type: AWS::KMS::Key
  Properties:
    MultiRegion: true                            # primary; add an AWS::KMS::ReplicaKey in eu-west-1
    EnableKeyRotation: true
    KeyPolicy: ...
  • S3: for active/active writes to both buckets, add a rule in each direction (two-way replication). Replication covers new objects only; copy existing ones with S3 Batch Replication.
  • Secrets: the replica secret has the same name and value; rotation runs in the primary Region and replicates.
  • KMS: a multi-Region replica key has the same key material, so data encrypted in one Region decrypts in the other.
  • Images: ECR replication rules copy every pushed image to eu-west-1, so tasks there don't pull across Regions.
  • CloudFront (optional): in front of both ALBs, an origin group with failover retries the second origin on 5xx errors, but only for GET, HEAD and OPTIONS requests. Checkout POSTs still rely on DNS failover.
Step 4

Route 53 latency records with health checks

One latency record per Region, each tied to a health check on a deep /health endpoint that tests DynamoDB access as well as the web tier.

dns.yaml (global, deployed once) 
HealthUse1:
  Type: AWS::Route53::HealthCheck
  Properties:
    HealthCheckConfig:
      Type: HTTPS
      FullyQualifiedDomainName: use1.shop.example.com   # points at the us-east-1 ALB
      ResourcePath: /health
      RequestInterval: 10
      FailureThreshold: 3

ShopUse1:
  Type: AWS::Route53::RecordSet
  Properties:
    HostedZoneName: example.com.
    Name: shop.example.com.
    Type: A
    SetIdentifier: us-east-1
    Region: us-east-1                          # latency-based routing
    HealthCheckId: !Ref HealthUse1
    AliasTarget:
      DNSName: dualstack.shop-alb-use1-123456.us-east-1.elb.amazonaws.com
      HostedZoneId: Z35SXDOTRQ7X7K               # the ALB's hosted zone ID
      EvaluateTargetHealth: true              # also fail if the ALB has no healthy targets

# ShopEuw1: the same, with SetIdentifier and Region eu-west-1 and HealthEuw1

A health check on the load balancer's root page, or EvaluateTargetHealth alone, can stay green while the database is unreachable, so Route 53 keeps sending users to a broken Region. Point the health check at an endpoint that exercises the critical dependencies, but keep it cheap so health checkers don't overload it.

DNS failover is limited by caching. Use a short TTL for non-alias records (60 seconds), and remember some clients and resolvers ignore TTLs. Alias records use the target's TTL.

Step 5

Controlled evacuation with ARC

Health checks react to failures they can see. Operators also need a reliable switch to move traffic for failures they can't (a bad deployment, degraded but "healthy" responses, planned maintenance). Amazon Application Recovery Controller (ARC) provides:

ARC capabilityWhat it does here
Routing controlAn on/off switch per Region, backed by a highly available cluster. Each routing control has a Route 53 health check of type RECOVERY_CONTROL, attached to the Region's record next to the deep health check. Safety rules can stop both Regions being turned off at once.
Region switchA plan that orchestrates a full Region failover or switchover across resources and accounts, with steps you define (scale up, change DNS, run runbooks).
Readiness checkContinuously compares quotas, capacity and configuration between the two Regions so you know the other Region can take over. Not meant for the failover path itself.
Zonal shift and autoshiftMove traffic away from one impaired Availability Zone inside a Region, before a Region-level failover is needed.
evacuate us-east-1 
aws route53-recovery-cluster update-routing-control-state \
  --routing-control-arn arn:aws:route53-recovery-control::222222222222:controlpanel/abc/routingcontrol/use1 \
  --routing-control-state Off \
  --endpoint-url https://host-aaaaaa.us-west-2.example.route53-recovery-cluster.amazonaws.com/v1
# call one of the cluster's Regional endpoints (try each in turn): this data plane stays available
# when the Route 53 console and control plane are not
Step 6

Monitoring both Regions

  • One dashboard: CloudWatch dashboards can show metrics from several Regions; put both ALBs' latency and 5xx rates, ECS task counts and DynamoDB metrics side by side.
  • Replication: alarm on DynamoDB ReplicationLatency and on S3 replication metrics (ReplicationLatency, OperationsFailedReplication).
  • Health checks: Route 53 health check status is a CloudWatch metric in us-east-1; alarm when a Region goes unhealthy.
  • Users: Synthetics canaries in each Region run the checkout journey against both Regional endpoints.

Design decisions

DecisionWhy
DynamoDB global tables, not a relational databaseBoth Regions can write; failover needs no promotion step, which is what makes an RTO of minutes realistic.
Latency routing plus health checksGives users the nearest Region normally and removes a failed Region automatically.
Deploy one Region at a timeA bad release is caught in the first Region while the second keeps serving, so one change can't take down both.
Deep health checkA Region that serves pages but can't reach its data must count as unhealthy.
Full capacity in each RegionCosts more, but avoids a capacity crunch at the exact moment of failover.
ARC routing controls in addition to health checksOperators can evacuate a Region deliberately using a data plane that doesn't depend on the impaired Region or the Route 53 control plane.

Alternatives

OptionTrade-off
Warm standby (second Region scaled down, not serving)Cheaper; RTO is the time to scale up and switch DNS (minutes to tens of minutes). Use failover routing instead of latency routing.
Pilot light (data replicated, compute off)Cheaper still; RTO of tens of minutes or more while the application tier is created and scaled.
Aurora Global Database instead of DynamoDBKeeps SQL; only one Region writes (the other is read-only until a switchover or failover promotes it), so writes need a failover step. Write forwarding lets secondary Regions send writes to the primary.
DynamoDB multi-Region strong consistencyRPO of zero and no conflicts, but needs three Regions (or a witness), adds write latency, and loses TTL and transactions.
AWS Global Accelerator instead of DNS routingStatic anycast IPs and failover in seconds without DNS caching; adds cost.

Testing it

  1. Fail the health check on purposeMake /health in one Region return errors (a feature flag or a test header) and measure how long until all synthetic traffic arrives in the other Region.
  2. Pause replication with FISAWS Fault Injection Service can pause DynamoDB global table replication for a replica to simulate Region isolation, and test how the application handles stale data.
  3. Evacuate a Region in a game dayTurn the Region's routing control off during business hours, confirm the other Region carries the full load and that alarms and runbooks work, then turn it back on.
  4. Shift away from one AZStart a zonal shift on the ALB to prove each Region also survives the loss of an Availability Zone.
  5. Check readiness continuouslyReadiness checks and AWS Resilience Hub assessments catch drift between Regions (a quota raised in one Region only, a missing replica).

"RTO and RPO near zero, users in several Regions, writes in every Region" is active/active with DynamoDB global tables and Route 53 latency (or Global Accelerator) routing with health checks. If the database must be relational, the answer shifts to Aurora Global Database with a short failover, which is warm standby or active/passive for writes.
