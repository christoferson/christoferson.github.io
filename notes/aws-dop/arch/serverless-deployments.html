End-to-end architecture

Serverless application with gradual deployments

An orders API built on API Gateway, Lambda, DynamoDB and SQS is released several times a day. Every release goes through staging first, then reaches production gradually: 10% of traffic for five minutes, checked by a test function and by alarms, then everyone. If errors rise, traffic returns to the old version automatically, without anyone being paged to roll back.

Scenario and requirements

The orders service has two functions: OrdersApiFunction behind API Gateway handles requests and writes to a DynamoDB table, and OrdersWorkerFunction processes messages from an SQS queue. The team wants frequent, low-risk releases.

RequirementDesign choice
Releases without downtimeLambda versions behind an alias; callers always invoke the alias, which moves between versions
Try a release on a small share of production trafficCodeDeploy canary: 10% of invocations for five minutes, then 100%
Automatic rollback when errors riseCloudWatch alarms on the alias attached to the deployment; an alarm in ALARM shifts traffic back
Check the new version before any real user sees itA pre-traffic hook function that calls the new version directly
No cold-start latency spikes for the APIProvisioned concurrency on the alias
Failed queue messages don't block or disappearPartial batch responses and a dead-letter queue
Database changes can't break the version still serving trafficBackward-compatible (expand, then contract) data changes
Same release tested before productionOne packaged template deployed to staging, tested, approved, then deployed to production

How it works

Steps marked AWS are done by AWS services on their own; steps marked Pipeline are stages and actions you define; Hook is your test function.

  1. Build
  2. A commit reaches mainPipelineThe pipeline's source action picks up the change.
  3. Build and unit testPipelineCodeBuild runs sam build and the unit tests.
  4. PackagePipelinesam package uploads the function code to S3 and writes packaged.yaml, a template that points at it. Both environments deploy this same artifact.
  5. Staging
  6. Create and run a change setPipelineCloudFormation actions, through a role in 333333333333, update the staging stack.
  7. Gradual deployment in stagingAWSCodeDeploy shifts the alias exactly as it will in production, so the rollout itself is tested too.
  8. Integration testsPipelineA CodeBuild action calls the staging API end to end.
  9. Manual approvalPipelineA release manager approves the production deployment.
  10. Production
  11. Create and run a change setPipelineCloudFormation, through a role in 222222222222, publishes a new Lambda version for each changed function.
  12. CodeDeploy takes over the aliasAWSSAM created a CodeDeploy application and deployment group; the stack update starts a deployment instead of moving the alias directly.
  13. Pre-traffic testHookThe hook function invokes the new version directly and reports success or failure to CodeDeploy. No user traffic has moved yet.
  14. Canary: 10% for five minutesAWSThe alias sends 10% of invocations to the new version. CodeDeploy watches the alarms throughout.
  15. All traffic, or roll backAWSIf no alarm fired, the alias points fully at the new version. If an alarm fired or the hook failed, the alias points back at the old version and the stack update fails and rolls back.

Build it

Step 1

SAM template

AutoPublishAlias makes SAM publish a new version whenever the code or configuration changes and point the alias live at it. DeploymentPreference makes that move gradual through CodeDeploy.

template.yaml (excerpt) 
Transform: AWS::Serverless-2016-10-31

Globals:
  Function:
    Runtime: python3.12
    Timeout: 10
    Tracing: Active
    Environment:
      Variables:
        TABLE_NAME: !Ref OrdersTable

Resources:
  OrdersApiFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: api.handler
      CodeUri: src/
      AutoPublishAlias: live   # callers use the live alias
      ProvisionedConcurrencyConfig:   # applied to the alias
        ProvisionedConcurrentExecutions: 20
      DeploymentPreference:
        Type: Canary10Percent5Minutes
        Alarms:
          - !Ref ApiAliasErrorsAlarm
          - !Ref ApiAliasLatencyAlarm
        Hooks:
          PreTraffic: !Ref PreTrafficHookFunction
      Policies:
        - DynamoDBCrudPolicy:
            TableName: !Ref OrdersTable
      Events:
        CreateOrder:
          Type: Api
          Properties:
            Path: /orders
            Method: post

  OrdersWorkerFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: worker.handler
      CodeUri: src/
      AutoPublishAlias: live
      DeploymentPreference:
        Type: Linear10PercentEvery1Minute
      Policies:
        - DynamoDBCrudPolicy:
            TableName: !Ref OrdersTable
      Events:
        OrderQueue:
          Type: SQS
          Properties:
            Queue: !GetAtt OrdersQueue.Arn
            BatchSize: 10
            FunctionResponseTypes:
              - ReportBatchItemFailures   # retry only failed messages

  OrdersQueue:
    Type: AWS::SQS::Queue
    Properties:
      VisibilityTimeout: 60   # at least 6x the function timeout
      RedrivePolicy:
        deadLetterTargetArn: !GetAtt OrdersDlq.Arn
        maxReceiveCount: 5

  OrdersDlq:
    Type: AWS::SQS::Queue

  OrdersTable:
    Type: AWS::DynamoDB::Table
    DeletionPolicy: Retain
    UpdateReplacePolicy: Retain
    Properties:
      BillingMode: PAY_PER_REQUEST
      AttributeDefinitions:
        - AttributeName: orderId
          AttributeType: S
      KeySchema:
        - AttributeName: orderId
          KeyType: HASH
      PointInTimeRecoverySpecification:
        PointInTimeRecoveryEnabled: true
  • With AutoPublishAlias, the API event targets the alias, not $LATEST, so API Gateway follows whatever version the alias points to.
  • The SQS event source mapping is also created on the alias, so the worker shifts gradually too; ReportBatchItemFailures lets the handler return only the failed message IDs, so one bad message doesn't make the whole batch retry.
  • The table is kept on stack deletion or replacement, and point-in-time recovery allows restoring it to any second in the last 35 days.
Step 2

Alarms on the alias

Lambda publishes metrics per function and also per alias or version. The Resource dimension, set to function:alias, selects the invocations that went through the alias, which during the canary is the traffic CodeDeploy is shifting.

template.yaml (alarms) 
ApiAliasErrorsAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: AWS/Lambda
    MetricName: Errors
    Dimensions:
      - Name: FunctionName
        Value: !Ref OrdersApiFunction
      - Name: Resource
        Value: !Sub ${OrdersApiFunction}:live
    Statistic: Sum
    Period: 60
    EvaluationPeriods: 2
    Threshold: 5
    ComparisonOperator: GreaterThanOrEqualToThreshold
    TreatMissingData: notBreaching   # quiet periods aren't failures

ApiAliasLatencyAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: AWS/Lambda
    MetricName: Duration
    Dimensions:
      - Name: FunctionName
        Value: !Ref OrdersApiFunction
      - Name: Resource
        Value: !Sub ${OrdersApiFunction}:live
    ExtendedStatistic: p99
    Period: 60
    EvaluationPeriods: 2
    Threshold: 800   # milliseconds
    ComparisonOperator: GreaterThanThreshold
    TreatMissingData: notBreaching

To watch only the new version during the canary, add the ExecutedVersion dimension with the new version number (!GetAtt OrdersApiFunction.Version.Version). That isolates the 10% from the 90% still served by the old version, so a small error rate on the new version isn't diluted.

An alarm with only the FunctionName dimension counts every version together. During a 10% canary, a new version failing every request raises the overall error rate only slightly, and the alarm may never fire. Alarm on the alias (or the executed version) and keep thresholds tight.

Step 3

Pre-traffic hook

The hook is an ordinary Lambda function. CodeDeploy invokes it before shifting any traffic, and waits until the hook reports a result.

template.yaml (hook) 
PreTrafficHookFunction:
  Type: AWS::Serverless::Function
  Properties:
    FunctionName: CodeDeployHook_OrdersPreTraffic   # prefix required by the default role
    Handler: hook.handler
    CodeUri: hooks/
    DeploymentPreference:
      Enabled: false   # the hook itself deploys directly
    Environment:
      Variables:
        NEW_VERSION: !Ref OrdersApiFunction.Version
    Policies:
      - Statement:
          - Effect: Allow
            Action: codedeploy:PutLifecycleEventHookExecutionStatus
            Resource: "*"
          - Effect: Allow
            Action: lambda:InvokeFunction
            Resource: !Ref OrdersApiFunction.Version
hooks/hook.py 
import json, os
import boto3

codedeploy = boto3.client("codedeploy")
lam = boto3.client("lambda")

def handler(event, context):
    status = "Succeeded"
    try:
        # call the new version directly with a test order
        resp = lam.invoke(
            FunctionName=os.environ["NEW_VERSION"],
            Payload=json.dumps({"body": '{"item": "test", "qty": 1}'}),
        )
        result = json.loads(resp["Payload"].read())
        if resp.get("FunctionError") or result.get("statusCode") != 201:
            status = "Failed"
    except Exception:
        status = "Failed"

    # CodeDeploy waits for this call
    codedeploy.put_lifecycle_event_hook_execution_status(
        deploymentId=event["DeploymentId"],
        lifecycleEventHookExecutionId=event["LifecycleEventHookExecutionId"],
        status=status,
    )
  • A PostTraffic hook works the same way and runs after all traffic has moved, for checks that need the full load.
  • If the hook never reports, the deployment fails when the hook times out after one hour, so always report, even on unexpected errors.
Step 4

Build specification

buildspec.yml 
version: 0.2
phases:
  install:
    runtime-versions:
      python: 3.12
    commands:
      - pip install -r requirements-dev.txt
  build:
    commands:
      - python -m pytest tests/unit   # fail the build before packaging
      - sam build
      - sam package
          --s3-bucket tooling-artifacts-111111111111
          --kms-key-id alias/pipeline-artifacts
          --output-template-file packaged.yaml
artifacts:
  files:
    - packaged.yaml
    - params-staging.json
    - params-prod.json

sam package uploads each function's code to the artifact bucket and rewrites the CodeUri values to point at it. Because both stages deploy packaged.yaml, production runs exactly the code that passed staging.

Step 5

Pipeline stages

Each environment uses two CloudFormation actions: create a change set, then execute it. The action-level RoleArn is the role the pipeline assumes in the target account; Configuration.RoleArn is the role CloudFormation uses to create the resources.

pipeline.yaml (production stage) 
- Name: Production
  Actions:
    - Name: Approve
      RunOrder: 1
      ActionTypeId:
        Category: Approval
        Owner: AWS
        Provider: Manual
        Version: "1"

    - Name: CreateChangeSet
      RunOrder: 2
      ActionTypeId:
        Category: Deploy
        Owner: AWS
        Provider: CloudFormation
        Version: "1"
      RoleArn: arn:aws:iam::222222222222:role/PipelineDeployRole
      InputArtifacts:
        - Name: BuildOutput
      Configuration:
        ActionMode: CHANGE_SET_REPLACE
        StackName: orders
        ChangeSetName: orders-release
        TemplatePath: BuildOutput::packaged.yaml
        TemplateConfiguration: BuildOutput::params-prod.json
        Capabilities: CAPABILITY_IAM,CAPABILITY_AUTO_EXPAND
        RoleArn: arn:aws:iam::222222222222:role/CfnExecutionRole

    - Name: ExecuteChangeSet
      RunOrder: 3
      ActionTypeId:
        Category: Deploy
        Owner: AWS
        Provider: CloudFormation
        Version: "1"
      RoleArn: arn:aws:iam::222222222222:role/PipelineDeployRole
      Configuration:
        ActionMode: CHANGE_SET_EXECUTE
        StackName: orders
        ChangeSetName: orders-release
  • The execute action finishes only when the stack update finishes, which includes the whole CodeDeploy canary. A rollback in CodeDeploy fails the stack update, which fails the pipeline stage.
  • The artifact bucket's KMS key policy and bucket policy must allow PipelineDeployRole and CfnExecutionRole in both target accounts to read the artifacts.

Design decisions

DecisionWhy
CodeDeploy traffic shifting on the Lambda aliasWorks for every way the function is invoked (API, queue, direct), has hooks and alarm rollback built in, and SAM sets it up with a few lines
Alarms on the alias, not the functionSeparates the traffic being shifted from older versions, so the alarms react to the release
Same deployment preference in stagingTests the rollout mechanics (hook, alarms, permissions) before production depends on them
Expand, then contract for data changesDuring the canary both versions read and write the same table. Release 1 adds the new attribute and writes both formats; a later release stops reading the old one; only then is the old attribute removed
Provisioned concurrency on the aliasNew versions are initialized before they receive traffic, so shifting doesn't cause a burst of cold starts
Retain the tableA stack deletion or an accidental replacement can't delete production data

A table property change that requires replacement (for example, changing the key schema) can't be done in place, and the table has a fixed name in many templates, so the update fails. Data model changes belong in application code and new attributes, not in table replacements during a release.

Alternatives

OptionWhen it fits better
Weighted alias set manually (RoutingConfig on the alias)One-off experiments where you want to control the split yourself; there's no automatic rollback
API Gateway stage canaryThe change is in the API itself (new routes, mapping templates) rather than in function code; promotion is manual
CDK Pipelines with LambdaDeploymentGroupThe team writes infrastructure in CDK; the same CodeDeploy traffic shifting is available as constructs
Linear instead of canaryGradual increase matters more than a quick decision, for example with load-sensitive downstream systems

Testing it

  1. Successful releaseDeploy a harmless change and watch the CodeDeploy deployment move from 10% to 100% after five minutes.
  2. Failing hookMake the hook's test order fail in staging. The deployment stops before any traffic moves, and the stack rolls back.
  3. Errors during the canaryRelease a version that fails a share of requests, controlled by an environment variable or an AppConfig feature flag. The alias alarm fires and traffic returns to the old version.
  4. Injected faultsAWS FIS Lambda actions can add latency or errors to invocations of a chosen function, to confirm the latency alarm and rollback work.
