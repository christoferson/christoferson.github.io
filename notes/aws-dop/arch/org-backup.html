End-to-end architecture

Organization-wide backup and recovery

Every account in the organization backs up its tagged resources on a schedule, without each team building its own backup plans. Copies go to a separate backup account and a second Region, into vaults that nobody, not even an administrator with root credentials, can empty early. Restores are tested automatically, compliance is reported centrally, and failed jobs raise an alert.

Scenario and requirements

The organization has dozens of workload accounts running EC2 instances with EBS volumes, RDS and Aurora databases, DynamoDB tables, EFS file systems and S3 buckets. The security team's concern is ransomware or a compromised administrator deleting both the data and its backups, so backups must survive the loss of a whole account or Region.

How it works

Steps marked AWS are done by AWS Backup or AWS Organizations on their own; steps marked You are configuration you create once.

  1. Define
  2. Attach a backup policy to the OUYouThe policy describes the backup plan: schedule, retention, local vault, copy targets and tag selection.
  3. Each account gets the planAWSOrganizations turns the effective policy into a backup plan in every account under the OU, including accounts added later.
  4. Back up and copy
  5. Back up tagged resourcesAWSAt the scheduled time, AWS Backup backs up every resource tagged backup=daily into the account's local vault.
  6. Copy to the backup accountAWSA copy action sends each recovery point to the central vault in 777777777777, re-encrypted with that vault's key.
  7. Copy to the second RegionAWSA second copy action sends it to the central vault in us-west-2.
  8. Protect
  9. Vault Lock holds the copiesAWSThe central vaults are locked in compliance mode: no user, root user or AWS can delete a recovery point before its retention ends.
  10. Prove
  11. Restore tests run on a scheduleAWSIn the backup account, a restore testing plan restores a recent recovery point of each selected resource, waits for validation, then deletes the restored copy.
  12. Audit Manager evaluates the rulesAWSFramework controls check that resources are in a plan, copied cross-account and cross-Region, kept long enough and stored in a locked vault.
  13. Failures raise an alertAWSA failed backup or copy job emits an EventBridge event; a rule notifies the backup team through SNS.

Build it

Step 1

Organization settings (management account)

Backup policies, cross-account monitoring and cross-account backup are opted in from the management account (AWS Backup Developer Guide, Managing AWS Backup resources across multiple AWS accounts). Delegating administration to the Audit account keeps day-to-day work out of the management account.

# Let AWS Backup work with Organizations, and enable backup policies
aws organizations enable-aws-service-access \
  --service-principal backup.amazonaws.com
aws organizations enable-policy-type \
  --root-id r-ab12 \
  --policy-type BACKUP_POLICY

# Allow accounts to copy backups to other accounts in the organization
aws backup update-global-settings \
  --global-settings isCrossAccountBackupEnabled=true

# Make the Audit account the AWS Backup delegated administrator
aws organizations register-delegated-administrator \
  --account-id 555555555555 \
  --service-principal backup.amazonaws.com
  • In the AWS Backup console (Settings), also enable Backup policies and Cross-account monitoring; only the management account can turn on cross-account management.
  • Registering the delegated administrator lets it monitor jobs. To let it edit backup policies too, attach AWSBackupOrganizationAdminAccess to its administrators and create a resource-based delegation policy for backup policies in Organizations.
Step 2

Workload account baseline (StackSet)

A backup policy names a vault and an IAM role, but doesn't create them: each account must already have both, or the plan doesn't work. A service-managed StackSet on the Workloads OU deploys them to every existing and new account.

backup-baseline.yaml (every workload account) 
Resources:
  BackupKey:
    Type: AWS::KMS::Key
    Properties:
      EnableKeyRotation: true
      KeyPolicy:
        Version: "2012-10-17"
        Statement:
          - Sid: AccountAdmin
            Effect: Allow
            Principal:
              AWS: !Sub arn:aws:iam::${AWS::AccountId}:root
            Action: kms:*
            Resource: "*"
          - Sid: BackupAccountCanUseForCopies   # needed for EBS, RDS and other
            Effect: Allow                        # resources not fully managed
            Principal:
              AWS: arn:aws:iam::777777777777:root
            Action:   # the standard "use this key" actions for another account
              - kms:Encrypt
              - kms:Decrypt
              - kms:ReEncrypt*
              - kms:GenerateDataKey*
              - kms:DescribeKey
            Resource: "*"
          - Sid: BackupAccountCanCreateGrants   # services such as EBS use grants
            Effect: Allow
            Principal:
              AWS: arn:aws:iam::777777777777:root
            Action: kms:CreateGrant
            Resource: "*"
            Condition:
              Bool:
                kms:GrantIsForAWSResource: true   # only for AWS services, not people

  LocalVault:
    Type: AWS::Backup::BackupVault
    Properties:
      BackupVaultName: workload-vault
      EncryptionKeyArn: !GetAtt BackupKey.Arn

  OrgBackupRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: OrgBackupRole   # referenced by the backup policy
      AssumeRolePolicyDocument:
        Version: "2012-10-17"
        Statement:
          - Effect: Allow
            Principal:
              Service: backup.amazonaws.com
            Action: sts:AssumeRole
      ManagedPolicyArns:
        - arn:aws:iam::aws:policy/service-role/AWSBackupServiceRolePolicyForBackup
        - arn:aws:iam::aws:policy/service-role/AWSBackupServiceRolePolicyForRestores
  • AWSBackupServiceRolePolicyForBackup includes backup:CopyFromBackupVault and backup:CopyIntoBackupVault, which cross-account copy jobs need on the source side.
  • For resources fully managed by AWS Backup (for example, EFS, DynamoDB with advanced backup, S3), the backup is encrypted with the vault's key. For the others (EBS, EC2, RDS, Aurora), the backup keeps the source resource's key, so that key must be a customer managed key shared with the backup account.
Step 3

Central vaults (backup account)

In 777777777777, create one vault in us-east-1 and one in us-west-2, each with its own customer managed key and a vault access policy that lets accounts in the organization copy into it (AWS Backup Developer Guide, Creating backup copies across AWS accounts).

central-vault.yaml (777777777777, deployed in both Regions) 
CentralVault:
  Type: AWS::Backup::BackupVault
  Properties:
    BackupVaultName: central-vault
    EncryptionKeyArn: !GetAtt CentralVaultKey.Arn   # not the default vault
    AccessPolicy:
      Version: "2012-10-17"
      Statement:
        - Sid: AllowCopiesFromOurOrganization
          Effect: Allow
          Principal: "*"
          Action: backup:CopyIntoBackupVault
          Resource: "*"
          Condition:
            StringEquals:
              aws:PrincipalOrgID: o-a1b2c3d4e5
        - Sid: NoManualDeletes
          Effect: Deny
          Principal: "*"
          Action:
            - backup:DeleteRecoveryPoint
            - backup:UpdateRecoveryPointLifecycle
          Resource: "*"
  • The destination can't be the default vault, because its key can't be shared with other accounts.
  • Any cross-account action other than backup:CopyIntoBackupVault is rejected by the vault access policy.
  • Guardrails from the same guide: an SCP denying organizations:LeaveOrganization for the backup account (an account that leaves keeps its backups), and an SCP denying ec2:ModifySnapshotAttribute and ec2:ModifySnapshotTier except for the backup roles, because Vault Lock only governs actions taken through AWS Backup.
Step 4

Backup policy (Organizations)

Backup policies use the Organizations management-policy syntax, where each value is set with an operator such as @@assign so child policies can merge with or override parent ones (AWS Organizations User Guide, Backup policy syntax and examples). $account is replaced with each account's ID.

workloads-backup-policy.json (attached to the Workloads OU) 
{
  "plans": {
    "daily-tagged": {
      "regions": { "@@assign": [ "us-east-1" ] },
      "rules": {
        "daily": {
          "schedule_expression": {
            "@@assign": "cron(0 5 ? * * *)"
          },
          "start_backup_window_minutes": {
            "@@assign": "60"
          },
          "target_backup_vault_name": {
            "@@assign": "workload-vault"
          },
          "lifecycle": {
            "delete_after_days": {
              "@@assign": "35"
            }
          },
          "copy_actions": {
            "arn:aws:backup:us-east-1:777777777777:backup-vault:central-vault": {
              "target_backup_vault_arn": {
                "@@assign": "arn:aws:backup:us-east-1:777777777777:backup-vault:central-vault"
              },
              "lifecycle": {
                "delete_after_days": {
                  "@@assign": "365"
                }
              }
            },
            "arn:aws:backup:us-west-2:777777777777:backup-vault:central-vault": {
              "target_backup_vault_arn": {
                "@@assign": "arn:aws:backup:us-west-2:777777777777:backup-vault:central-vault"
              },
              "lifecycle": {
                "delete_after_days": {
                  "@@assign": "365"
                }
              }
            }
          }
        }
      },
      "selections": {
        "tags": {
          "daily-tag": {
            "iam_role_arn": {
              "@@assign": "arn:aws:iam::$account:role/OrgBackupRole"
            },
            "tag_key": { "@@assign": "backup" },
            "tag_value": { "@@assign": [ "daily" ] }
          }
        }
      }
    }
  }
}
  • The policy must name the Regions, the resources (by tag or resource type; individual resource ARNs aren't allowed in backup policies), the vault and the IAM role.
  • A child policy attached lower in the tree can override a value, for example a Finance OU keeping copies for seven years.
  • The copy lifecycle has no cold-storage transition, because AWS Backup doesn't support cross-account copies into cold storage tiers.

AWS describes the same organization-wide approach in the AWS Storage Blog posts Managing backups at scale in your AWS Organizations using AWS Backup and Adopt AWS Backup policies at enterprise scale using AWS Organizations.

Step 5

Vault Lock (backup account)

Vault Lock gives a vault write-once, read-many behavior. In governance mode, users with sufficient IAM permissions can remove the lock. In compliance mode, after a grace time of at least 3 days, the lock can't be changed or removed by any user or by AWS while the vault holds recovery points (AWS Backup Developer Guide, AWS Backup Vault Lock).

# Compliance mode: including --changeable-for-days is what selects it
aws backup put-backup-vault-lock-configuration \
  --backup-vault-name central-vault \
  --changeable-for-days 3 \
  --min-retention-days 30 \
  --max-retention-days 2557   # about 7 years

# Check: "Locked": true, and LockDate is when the grace time ends
aws backup describe-backup-vault --backup-vault-name central-vault
  • Minimum and maximum retention: new backup and copy jobs whose retention is outside the range fail; recovery points already in the vault keep their own lifecycle.
  • Grace time: until LockDate, the lock can still be changed or deleted, which is the time to test it.
  • Root user: any attempt to delete a recovery point or change its lifecycle in a locked vault is denied, including by the root user.

After the grace time, a compliance-mode lock is permanent, and the vault can't be deleted while it holds recovery points. A recovery point with retention set to "Always" would then be kept, and billed, forever. Check retention settings before the grace time ends.

Step 6

Logically air-gapped vault (optional)

A logically air-gapped vault is a specialized vault type that always has Vault Lock in compliance mode, is encrypted with an AWS owned key by default (or a customer managed key), and can be shared through AWS RAM, or accessed with Multi-party approval, so another account can restore from it (AWS Backup Developer Guide, Logically air-gapped vault). It's useful when recovery must work even if the account that owns the backups is compromised.

aws backup create-logically-air-gapped-backup-vault \
  --backup-vault-name airgapped-vault \
  --min-retention-days 7 \
  --max-retention-days 365
  • It can be a copy target, or a primary backup target: the backup policy key target_logically_air_gapped_backup_vault_arn sends supported fully managed resources straight to it.
  • Sharing through RAM is to individual account IDs (inside or outside the organization), not to OUs. Shared accounts can view and restore, but not create copies.

The AWS Storage Blog post Securing backup data against modern threats with AWS Backup covers these protections against ransomware and account compromise.

Step 7

Restore testing (backup account)

A restore testing plan restores recovery points on a schedule, measures how long the restore takes, and deletes the restored resources afterwards (AWS Backup Developer Guide, Restore testing). AWS recommends a designated account for restore tests; here, the backup account tests the copies it holds.

aws backup create-restore-testing-plan \
  --restore-testing-plan '{
    "RestoreTestingPlanName": "weekly_restore_test",
    "ScheduleExpression": "cron(0 3 ? * SUN *)",
    "StartWindowHours": 8,
    "RecoveryPointSelection": {
      "Algorithm": "RANDOM_WITHIN_WINDOW",
      "IncludeVaults": ["*"],
      "RecoveryPointTypes": ["SNAPSHOT"],
      "SelectionWindowDays": 30
    }
  }'

aws backup create-restore-testing-selection \
  --restore-testing-plan-name weekly_restore_test \
  --restore-testing-selection '{
    "RestoreTestingSelectionName": "rds_databases",
    "ProtectedResourceType": "RDS",
    "ProtectedResourceArns": ["*"],
    "IamRoleArn": "arn:aws:iam::777777777777:role/RestoreTestRole",
    "ValidationWindowHours": 4
  }'
  • Recovery point choice: LATEST_WITHIN_WINDOW or RANDOM_WITHIN_WINDOW; random tests the general health of older backups too.
  • Validation: an EventBridge rule on Restore Job State Change with status COMPLETED and the plan's ARN invokes a function that checks the restored resource (for example, runs a query) and reports with PutRestoreValidationResult.
  • Cleanup: restored resources are deleted when validation reports, or at the end of the validation window (up to 168 hours), whichever comes first. Removing their awsbackup-restore-test tag stops the automatic deletion.
  • Restores across accounts: AWS Backup can't restore directly into another account; copy the recovery point to that account first, then restore there.
Step 8

Compliance and alerts

AWS Backup Audit Manager frameworks group controls that are evaluated continuously and can produce daily reports. Controls that match this design (AWS Backup Developer Guide, Controls and remediation):

ControlChecks
Backup resources are included in at least one backup planTagged resources didn't miss the policy
Cross-account backup copy is scheduledCopies go to 777777777777
Cross-Region backup copy is scheduledCopies go to us-west-2
Resources are in a backup plan with an AWS Backup Vault LockBackups are immutable, within the given retention range
Minimum retention established for recovery pointRetention meets policy (35 days by default)
Last recovery point was createdA backup exists within the last day
Restore time for resources meet targetRestore tests finish within the target minutes (an RTO check)
Resources in a logically air-gapped vaultA copy reached the air-gapped vault recently, if one is used

For alerts, AWS Backup sends job state changes to EventBridge (best effort, about every 5 minutes):

backup-failure-rule.json (event pattern) 
{
  "source": ["aws.backup"],
  "detail-type": [
    "Backup Job State Change",
    "Copy Job State Change"
  ],
  "detail": {
    "state": ["FAILED", "EXPIRED", "ABORTED"]
  }
}

The events are emitted in each workload account, so either deploy this rule with the baseline StackSet and forward matches to a central event bus, or watch all accounts from the delegated administrator's cross-account monitoring view.

Design decisions

DecisionWhy
A separate backup accountAn attacker with administrator access to a workload account can delete its local backups, but not the copies in an account they can't sign in to
A second RegionA Regional outage or Regional key problem doesn't take every copy with it
Compliance-mode Vault Lock on the central vaults onlyImmutability where it matters, while local vaults stay flexible for short-term operational restores
Selection by tag in a backup policyTeams opt resources in with a tag; the backup team manages one policy instead of a plan per account
Customer managed keysAWS managed key policies can't be changed, so they can't be shared for cross-account copies of resources that aren't fully managed by AWS Backup
Restore testing plus Audit ManagerBackups that were never restored are an assumption; scheduled tests and restore-time controls turn them into evidence

"Cross-account copy jobs fail for RDS or EBS backups" usually means the source resource is encrypted with an AWS managed key (aws/rds, aws/ebs). Those keys can't be shared, so re-encrypt the source with a customer managed key shared with the backup account. The AWS Storage Blog post Protecting encrypted Amazon RDS instances with cross-account and cross-Region backups describes a way to keep using AWS managed keys.

Alternatives

OptionWhen it fits better
Service-native snapshots (Data Lifecycle Manager for EBS, RDS automated backups)One service in one account; no central policy, cross-account immutability or audit reporting
S3 replication with Object LockS3 data only, when objects must be replicated continuously rather than backed up on a schedule
DynamoDB point-in-time recoveryRestoring a table to any second in the last 35 days after a bad write; complements, rather than replaces, copies in another account
AWS Elastic Disaster RecoveryServers that need recovery in minutes with seconds of data loss (continuous replication), rather than daily recovery points
Backup plans per account instead of a policyA few accounts with very different needs; doesn't scale or stay consistent across an organization

Testing it

  1. Policy reaches an accountIn a test workload account, check that the backup plan from the policy appears, then tag a test volume and wait for the backup job.
  2. Copies arriveConfirm copy jobs complete into both central vaults, and that a failed copy (for example, a resource with an AWS managed key) raises the alert.
  3. Deletion is refusedDuring the grace time, try to delete a recovery point in the central vault; the request is denied. Only then let the grace time expire.
  4. Restore worksRun the restore testing plan on demand, check the validation result, and confirm the restored resource is deleted afterwards.
  5. Account loss drillCopy a recovery point from the central vault to a clean recovery account and restore it there.
