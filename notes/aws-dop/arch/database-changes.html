End-to-end architecture

Database changes with no downtime

An orders application runs on Amazon RDS for PostgreSQL. Two kinds of change keep coming: platform changes (a new major engine version, a bigger instance class) and schema changes that ship with every release. Both must happen with about a minute of interruption at most, and both need a way back if something goes wrong.

Scenario and requirements

The database is orders-db, a Multi-AZ RDS for PostgreSQL DB instance. The application connects through the instance endpoint. Platform changes happen a few times a year; schema changes go out with application releases, several times a week.

RequirementDesign choice
Major version upgrade and instance class change with minimal downtimeAmazon RDS Blue/Green Deployments: a synchronized copy is upgraded and tested, then switched over
Test the upgraded database with production data firstThe green environment stays in sync with production and can be tested read-only
No application configuration changeSwitchover renames the green instance and endpoint to the production names
No data loss and no surprise long outageSwitchover guardrails and a switchover timeout; a switchover that can't finish in time is rolled back
Schema changes released with the code, through the pipelineA CodeBuild step runs versioned migrations (Flyway) before the application deploys
A release can roll back without a database rollbackOnly backward-compatible migrations per release: expand first, contract in a later release
No database passwords in the pipelineCredentials read from Secrets Manager by CodeBuild at run time

How it works

Steps marked AWS are done by RDS or CodeBuild on their own; steps marked You are actions you start; Pipeline marks pipeline stages.

  1. Part A: engine upgrade with a blue/green deployment
  2. Create the blue/green deploymentYouName the source (blue) instance and the target engine version, parameter group and instance class for the copy (green).
  3. Green is built and kept in syncAWSRDS copies the topology (Multi-AZ, read replicas, monitoring settings) and replicates from blue to green. For a PostgreSQL major version upgrade, it uses logical replication.
  4. Test greenYouGreen is read-only by default. Run read-only tests and performance checks against its own endpoint while production keeps running on blue.
  5. Start the switchoverYouAt a quiet time, with a timeout, for example 600 seconds.
  6. Guardrails are checkedAWSReplication is healthy, replica lag is small enough, there are no long-running writes or DDL on blue, and (with logical replication) no unsupported changes such as DDL.
  7. Writes stop and replication catches upAWSNew writes stop on both environments and connections are dropped, so green holds every committed change.
  8. Names and endpoints swapAWSorders-db-green-… becomes orders-db with the production endpoint; blue becomes orders-db-old1. Writes resume on the new production instance, typically within a minute.
  9. Keep the old instance for a whileYouorders-db-old1 isn't deleted. Keep it for regression comparisons and for its point-in-time recovery history, then delete it.
  10. Part B: a schema change in a release
  11. Commit migration and code togetherPipelineThe release contains V42__add_order_status.sql and the code that uses it.
  12. MigrateAWSA CodeBuild project inside the VPC reads the migrator credentials from Secrets Manager and runs Flyway, which applies only migrations not yet recorded in its history table.
  13. Deploy the applicationPipelineOnly after the migration succeeds. Old and new application versions both work with the expanded schema during the rollout.
  14. Contract laterPipelineWhen no running version needs the old shape, a later release removes it.

Build it

Step 1

Prepare the source database

RDS for PostgreSQL uses physical replication for most blue/green deployments, and logical replication when you request a major version upgrade on a supported source version (Amazon RDS User Guide, PostgreSQL replication methods for blue/green deployments). A major version upgrade therefore needs logical replication prepared on blue:

  1. Automated backups onRequired for blue/green deployments.
  2. A custom parameter group with rds.logical_replication = 1Also size max_replication_slots, max_wal_senders, max_logical_replication_workers and max_worker_processes: each database needs its own slot and worker. Reboot so the instance is in sync with its parameter group, or creation fails.
  3. A primary key on every tableLogical replication can't replicate UPDATE or DELETE on tables without one.
  4. No external replicationBlue can't be the source or target of self-managed replication.
orders-pg16-params.yaml (parameter group for blue) 
OrdersPgParams:
  Type: AWS::RDS::DBParameterGroup
  Properties:
    Family: postgres16
    Description: orders-db with logical replication for blue/green
    Parameters:
      rds.logical_replication: "1"   # static: needs a reboot
      max_replication_slots: "20"
      max_wal_senders: "20"
      max_logical_replication_workers: "10"
      max_worker_processes: "20"

Logical replication doesn't carry everything over, so plan around these while the deployment exists: DDL on blue isn't replicated (and blocks switchover), large objects aren't replicated, sequence values are adjusted by RDS at switchover, materialized views must be refreshed on green, and unlogged tables aren't copied (Amazon RDS User Guide, Limitations and considerations for Amazon RDS blue/green deployments).

Step 2

Create the blue/green deployment

aws rds create-blue-green-deployment \
  --blue-green-deployment-name orders-pg17-upgrade \
  --source arn:aws:rds:us-east-1:222222222222:db:orders-db \
  --target-engine-version 17.4 \
  --target-db-parameter-group-name orders-pg17-params \
  --target-db-instance-class db.r7g.xlarge
# returns a BlueGreenDeploymentIdentifier such as bgd-1234567890abcdef
  • Parameter group: the target group must match the new major version's family; without one, green keeps blue's group.
  • Testing green: connect to green's own endpoint for read-only tests. Green is read-only by default; with logical replication, writes can be enabled per session, but the docs warn they can cause replication conflicts and unexpected data after switchover. With physical replication, green can't accept writes at all.
  • Monitoring: watch the ReplicaLag metric on green before switching over.

Blue/green deployments aren't supported through CloudFormation, and also not with cross-Region or cascading read replicas or Multi-AZ DB clusters (Amazon RDS User Guide, Limitations and considerations for Amazon RDS blue/green deployments). Run them with the CLI, API or console. If orders-db is managed by a stack, keep the stack's engine version and instance class matching what you switched to, so the next stack update doesn't try to change them back.

Step 3

Switch over

aws rds switchover-blue-green-deployment \
  --blue-green-deployment-identifier bgd-1234567890abcdef \
  --switchover-timeout 600   # 30 to 3,600 seconds; default 300
  • Guardrails: on green, replication health, replica lag and no active writes; on blue, no external replication, no long-running writes or DDL, and (logical replication) no unsupported changes. If a guardrail fails, the switchover doesn't start.
  • Timeout: if the switchover takes longer than the timeout, every change is rolled back and both environments stay as they were.
  • Clients: keep DNS caching at or below RDS's five-second TTL, or clients keep writing to the old instance. RDS Proxy (registered with blue before creating the deployment) and AWS smart drivers detect the change without waiting for DNS.
  • Afterwards: the old primary stays read-only. Point-in-time recovery of the new production instance starts from when green was created, so keep orders-db-old1 for at least your recovery window; restore it by its resource ID, because its name changed.
  • Events: switchover progress is published as blue/green deployment events, so an EventBridge rule can notify the team.

The launch post on the AWS News Blog walks through the same flow end to end: New – Fully Managed Blue/Green Deployments in Amazon Aurora and Amazon RDS.

Step 4

Migration build

The migration runs in a CodeBuild project attached to the database's VPC (private subnets, a security group the database accepts on port 5432). The secrets-manager mapping injects the secret's fields as environment variables, so no credential is stored in the project or the repository.

buildspec-migrate.yml 
version: 0.2
env:
  secrets-manager:   # secret-id:json-key
    DB_HOST: prod/orders/db-migrator:host
    DB_USER: prod/orders/db-migrator:username
    DB_PASSWORD: prod/orders/db-migrator:password
phases:
  install:
    commands:
      - ./scripts/install-flyway.sh   # pinned Flyway version
  build:
    commands:
      - flyway
          -url=jdbc:postgresql://${DB_HOST}:5432/orders
          -user=${DB_USER}
          -password=${DB_PASSWORD}
          -locations=filesystem:db/migrations
          migrate
      - flyway info -url=jdbc:postgresql://${DB_HOST}:5432/orders -user=${DB_USER} -password=${DB_PASSWORD}
  • Flyway records each applied migration in a history table, so re-running the step after a failure applies only what's missing.
  • The project's role needs secretsmanager:GetSecretValue on the secret (and kms:Decrypt if it uses a customer managed key); the VPC needs a Secrets Manager interface endpoint or a NAT gateway.
  • Liquibase works the same way; what matters is versioned, repeatable migrations run by the pipeline, not by hand.
Step 5

Pipeline stage order

In the production stage, the migration runs before the application deploy, through a role in 222222222222:

pipeline.yaml (production stage, excerpt) 
- Name: Production
  Actions:
    - Name: MigrateSchema
      RunOrder: 1
      ActionTypeId:
        Category: Build
        Owner: AWS
        Provider: CodeBuild
        Version: "1"
      RoleArn: arn:aws:iam::222222222222:role/PipelineDeployRole
      InputArtifacts:
        - Name: SourceOutput
      Configuration:
        ProjectName: orders-db-migrate   # project in 222222222222, in the VPC

    - Name: DeployApp
      RunOrder: 2   # only if the migration succeeded
      ActionTypeId:
        Category: Deploy
        Owner: AWS
        Provider: CodeDeploy
        Version: "1"
      RoleArn: arn:aws:iam::222222222222:role/PipelineDeployRole
      InputArtifacts:
        - Name: BuildOutput
      Configuration:
        ApplicationName: orders
        DeploymentGroupName: orders-prod

If the migration fails, the stage stops and the running application is untouched. Because each migration is backward-compatible, the application can be rolled back without undoing the schema.

Step 6

Expand and contract

During a rolling, canary or blue/green application deployment, old and new code run at the same time against one database. Every release must therefore work with both the schema it found and the schema it leaves. Renaming status to order_status becomes three releases:

  1. Release 1: expand
  2. Add, don't changeAdd the new column, nullable or with a default; the code writes both columns and reads the new one when it's set.
  3. Release 2: migrate data
  4. Backfill and switch readsCopy old values in batches; the code now reads and writes only the new column.
  5. Release 3: contract
  6. Remove the old shapeOnce no running version uses it, drop the old column.
db/migrations/V42__add_order_status.sql (release 1) 
-- expand: old code ignores the new column, new code uses it
ALTER TABLE orders ADD COLUMN order_status text;

-- build the index without blocking writes
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_order_status
  ON orders (order_status);
db/migrations/V45__drop_old_status.sql (release 3) 
-- contract: only after no deployed version reads "status"
ALTER TABLE orders DROP COLUMN status;

A destructive change (drop, rename, change a type) in the same release as the code that needs it breaks the old version still serving traffic during the rollout, and makes rolling back the application fail. Destructive steps always come in a later release.

Design decisions

DecisionWhy
Blue/green deployment for engine and instance changesThe change is made and tested on a synchronized copy; downtime is the switchover, typically under a minute, instead of the whole upgrade
Switchover with a timeoutIf replication can't catch up in time, RDS rolls back automatically rather than extending the outage
No schema changes while a deployment existsWith logical replication, DDL on blue isn't replicated and makes switchover unavailable; freeze migrations until the switchover is done
Keep the old instance after switchoverIt holds the point-in-time recovery history from before the switchover and is a reference for regression tests
Migrations in the pipeline, before the deployThe schema change is versioned, reviewed and applied the same way in every environment, and a failure stops the release early
Expand/contractEvery release is backward-compatible, so application rollback never needs a database rollback
Separate migrator credentialsThe application's database user doesn't need DDL rights; only the migration step does

Alternatives

OptionWhen it fits better
In-place upgrade (modify the instance)A maintenance window with longer downtime is acceptable and there's no need to test on a copy first
Snapshot restore on the new version, then AWS DMS to catch upThe change isn't supported by blue/green (for example, moving accounts or engines), at the cost of building and running replication yourself
Read replica promotionMoving to a new instance on the same engine version; promotion breaks replication and needs the application repointed
Aurora Blue/Green DeploymentsThe database is Aurora PostgreSQL; the same blue/green approach applies to Aurora clusters
Aurora fast database cloningTesting a migration against a full-size copy quickly and cheaply before it reaches production

Testing it

  1. Rehearse in stagingRun the whole blue/green deployment and switchover on a staging copy, and time the write outage seen by the application.
  2. Test green before switchingRead-only functional tests and query plans against green's endpoint; compare performance with blue.
  3. Exercise the guardrailsIn staging, start a switchover during a long-running transaction and confirm it's refused or rolled back within the timeout.
  4. Migrations in a clean databaseA pipeline test step runs all migrations from scratch on a temporary database, so a broken migration fails before production.
  5. Rollback drillDeploy release N+1 with an expand migration, then roll the application back to N and confirm N still works on the expanded schema.
