Overview

Task statement 5.3

Troubleshoot system and application failures.

Troubleshooting questions describe a symptom ("the pipeline fails at the deploy stage", "tasks keep stopping", "the Auto Scaling group can't launch instances") and ask for the cause or the next step. Knowing where each service records why it failed, and the handful of usual causes, answers most of them. Typical scenarios: "CloudFormation rolled back; which event explains it?", "ECS tasks exit with code 137", or "users report errors but the health checks are green".

AWS metrics and logging services for troubleshooting

Knowledge

Work from broad to narrow: metrics show that something is wrong and where, traces show which component is slow or failing, logs show exactly why.

  1. Confirm and scope with metricsWhich metric moved, when it started, and which dimension it's limited to: one AZ, one instance, one API route, one version.
  2. Locate with tracesX-Ray's trace map shows the failing or slow service; individual traces show the slow call and its error.
  3. Explain with logsLogs Insights queries over the affected component for the time window find the error message or stack trace.
  4. Correlate with changesCloudTrail, AWS Config timelines and deployment history show what changed just before.
ToolAnswers
CloudWatch metrics and dashboardsWhen did it start, how big is it, which dimension?
CloudWatch Logs InsightsWhat do the logs say in that window?
CloudWatch Contributor InsightsWho are the top contributors (clients, keys, URLs) to errors or load?
AWS X-Ray (traces, trace map, analytics)Which downstream call is slow or failing, and for which requests?
CloudWatch Application SignalsWhich service is breaking its SLO, and which operation?
Container Insights, Lambda InsightsResource usage per container, pod or function
Performance Insights, Database InsightsWhich SQL statements and wait events load the database?
Synthetics canaries, CloudWatch RUMWhat do users actually experience?
VPC Flow Logs, Reachability AnalyzerIs traffic blocked, and by which security group, network ACL or route?
CloudWatch investigationsAI-assisted analysis that suggests related metrics, logs, changes and likely causes

Contributor Insights

A Contributor Insights rule ranks the keys that contribute most to a pattern. This rule finds the client IPs producing the most 5xx responses in a JSON log group:

contributor-insights-rule.json 
{
  "Schema": { "Name": "CloudWatchLogRule", "Version": 1 },
  "LogGroupNames": ["/app/orders"],
  "LogFormat": "JSON",
  "Contribution": {
    "Keys": ["$.clientIp"],
    "Filters": [{ "Match": "$.status", "GreaterThan": 499 }]
  },
  "AggregateOn": "Count"
}
  • "Which customers or IP addresses cause most of the errors?": Contributor Insights.
  • "Which microservice adds the latency?": X-Ray.
  • "Why can't instance A reach database B?": Reachability Analyzer, and VPC Flow Logs showing REJECT.

AWS service health services

Knowledge

An early question in every incident: is it AWS or is it us?

ServiceWhat it tells you during an incident
AWS Health DashboardAWS issues affecting your resources (account-specific), plus the public service status by Region
Amazon CloudWatchYour alarms and metrics; Internet Monitor shows internet-side problems between users and your application
Systems Manager OpsCenterA central list of OpsItems, each with related resources, events, logs and suggested runbooks
Systems Manager ExplorerA summary of OpsItems, patch compliance and inventory across accounts and Regions
AWS Trusted AdvisorService quota usage and fault tolerance checks

OpsCenter

  • Where OpsItems come from: CloudWatch alarm actions, EventBridge rules (for example, on AWS Health or Security Hub events), AWS Config compliance changes, or manually.
  • Deduplication: repeated alerts for the same problem update one OpsItem instead of creating many.
  • Context: each OpsItem links related resources, the CloudTrail events and Config history around them, and recommended Automation runbooks (for example, restart an instance or increase volume size), which operators can run directly.

"Operators need one place to see operational issues across accounts with context and runbooks to fix them" points to Systems Manager OpsCenter (with Explorer for the overview).

Root cause analysis

Knowledge

Root cause analysis separates the symptom (users get 503 errors), the trigger (a deployment with a bad configuration value) and the root cause (nothing validated configuration before deployment).

  1. Mitigate firstRestore service (roll back, fail over, scale out) before the investigation is finished. Customers come before curiosity.
  2. Scope itWhich Regions, AZs, versions, customers or endpoints are affected, and which aren't?
  3. Build a timelineWhen did metrics change? What changed shortly before: deployments (CodeDeploy, CloudFormation events), configuration (AWS Config, Parameter Store), API calls (CloudTrail), AWS Health events?
  4. Test hypotheses with dataCompare healthy and unhealthy instances, versions or AZs. Traces and logs confirm or rule each one out.
  5. Ask "why" until you reach a fixable processThe "five whys": why did it fail, why wasn't it caught, why did it spread?
  6. Prevent recurrenceA blameless post-incident review (AWS calls it a correction of errors) with action items: new tests, alarms, guardrails or automation.

Most incidents follow a change. When a scenario says "it started after this morning's release", check the deployment and change history first, and roll back to mitigate.

Analyzing failed deployments

Skill

AWS CodePipeline

The pipeline's execution history shows which stage and action failed. The action's Details link opens the underlying service (CodeBuild logs, CodeDeploy deployment, CloudFormation events), which usually holds the real error.

SymptomLikely cause
Source action failsCodeConnections connection still pending or not authorized; the role lacks codeconnections:UseConnection; an S3 source bucket without versioning; the branch doesn't exist
An action fails with access denied on the artifactThe bucket policy or KMS key policy doesn't allow the role (common in cross-account pipelines, or when the default aws/s3 key is used)
A cross-account deploy action fails to startThe pipeline role can't assume the target account's role, or that role's trust policy doesn't name the pipeline role
Manual approval failsNobody approved within 7 days
A change never reaches a stageThe transition into the stage is disabled, or the execution was superseded by a newer one
Lambda invoke action times outThe function never called PutJobSuccessResult or PutJobFailureResult

After fixing the cause, retry the failed stage (or only its failed actions) instead of rerunning the whole pipeline. V2 pipelines can also roll a stage back to the last successful execution.

Skill

AWS CodeBuild

The build's phase details show which phase failed (for example, BUILD with COMMAND_EXECUTION_ERROR), and the build log in CloudWatch Logs or S3 shows the failing command and its output.

ErrorLikely cause
Cannot connect to the Docker daemonPrivileged mode isn't enabled on the project
Access denied pushing to ECR or reading S3, Secrets Manager or Parameter StoreThe CodeBuild service role lacks the permission (or kms:Decrypt)
CLIENT_ERROR in DOWNLOAD_SOURCEThe role can't read the source, or the connection isn't authorized
Timeouts reaching the internet or AWS APIsThe project runs in a VPC subnet without a NAT gateway or VPC endpoints
Build killed or very slowOut of memory or CPU for the compute type; no caching
toomanyrequests pulling base imagesDocker Hub rate limits; use an ECR pull through cache
"not a git repository"The source artifact is a zip; switch the pipeline source to full clone

For hard-to-reproduce failures, CodeBuild can pause a build with Session Manager: add codebuild-breakpoint in the buildspec and connect to the running build container to inspect it.

Skill

AWS CodeDeploy

Open the deployment, then a failed instance, then its lifecycle events. The first failed event and its log output point to the cause.

FailureLikely cause
Stuck in Pending, no lifecycle eventsAgent not installed or not running; no instance profile; no route to the CodeDeploy endpoints
DownloadBundleThe instance profile can't read the revision in S3 or decrypt it
ApplicationStopThe previous revision's stop script fails
InstallFiles already exist at the destination (set the file exists behavior)
ValidateService or a script timeoutThe application didn't start, or a script ran longer than its timeout
AllowTrafficInstances fail the target group health check
Automatic rollbackA CloudWatch alarm on the deployment group went into ALARM
ECS or Lambda deployment waits about an hour, then failsA hook function didn't report its status

On the instance, the agent's own log is /var/log/aws/codedeploy-agent/codedeploy-agent.log and hook script output is under /opt/codedeploy-agent/deployment-root/deployment-logs/.

Skill

AWS CloudFormation

When a stack fails, CloudFormation rolls back and records many events. The first CREATE_FAILED or UPDATE_FAILED event (in time order) has the real reason; later failures are usually "Resource creation cancelled" because of it. The console's Detect root cause option highlights that first failure for you.

Status reasonLikely cause and fix
Not authorized to perform an actionThe deploying role or the stack's service role lacks the permission
Resource already existsA fixed physical name (such as BucketName) is already used; let CloudFormation generate names
Limit exceededA service quota (VPCs, Elastic IPs, instances); request an increase
Received 0 SUCCESS signalsInstances didn't run cfn-signal before the CreationPolicy timeout
Stack waits about an hour on a custom resourceThe custom resource's Lambda never responded to the pre-signed URL
Invalid property or valueA wrong property for the resource type, or a value that isn't allowed (run cfn-lint)
Export cannot be updated or deletedAnother stack imports it with !ImportValue
DELETE_FAILED on an S3 bucketThe bucket isn't empty; empty it, or retain it and delete the stack
UPDATE_ROLLBACK_FAILEDThe rollback itself failed (often after a manual change); fix the resource, then ContinueUpdateRollback, skipping resources if needed
 
aws cloudformation describe-stack-events --stack-name orders-prod \
  --query "StackEvents[?contains(ResourceStatus, 'FAILED')].[Timestamp,LogicalResourceId,ResourceStatusReason]" \
  --output table

The last failure listed in a stack's events (shown newest first) is rarely the cause. Sort by time and read the earliest failure.

Skill

CloudWatch synthetic monitoring

Synthetics canaries are scripts (Node.js or Python, with a headless browser for UI checks) that run on a schedule against your endpoints, like a user who never sleeps. Blueprints cover heartbeats, API checks, broken link checks, visual comparison and multi-step GUI workflows.

  • Results: SuccessPercent and Duration metrics, plus screenshots, HAR files and logs for each run in S3.
  • Catch what health checks miss: a load balancer health check can pass while the login page or checkout flow is broken. A canary walking through the flow fails.
  • In deployments: run canaries right after a deployment (from the pipeline or a CodeDeploy hook) and alarm on SuccessPercent to trigger rollback.
  • Private endpoints: run the canary inside the VPC (subnets and security groups) to test internal applications.

To find why a canary failed, open the failed run: the screenshot and HAR file show what the page looked like and which request failed. "Users see errors but all health checks are green" points to adding a canary for the user journey.

Analyzing incidents regarding failed processes

Skill

Auto Scaling

The group's activity history records every launch and termination attempt, with a status message explaining failures:

aws autoscaling describe-scaling-activities --auto-scaling-group-name web-asg --max-items 10
SymptomLikely cause
Launches fail: InsufficientInstanceCapacityThe instance type isn't available in that AZ; use several types and AZs
Launches fail: vCPU limit exceededThe account's On-Demand or Spot vCPU quota
Launches fail: AMI, subnet or security group not foundThe launch template references something that was deleted
Launches fail: not authorized for the instance profileWhoever created or updated the group lacks iam:PassRole for that role
Instances start, then terminate immediately (encrypted volumes)The Auto Scaling service-linked role isn't allowed to use the customer managed KMS key for the EBS volumes
Instances replaced in a loopELB health checks fail (wrong path or port, app slow to start, health check grace period too short)
Group doesn't scale outAlready at maximum size; a scaling process is suspended; the alarm isn't firing; cooldown or warmup
Scale-in or scale-out takes up to an hourLifecycle hooks waiting for a CompleteLifecycleAction that never comes
Unhealthy instances never replacedThe group uses EC2 health checks only, or the HealthCheck or ReplaceUnhealthy process is suspended

Someone may have suspended Auto Scaling processes (such as Launch, HealthCheck or AZRebalance) during an earlier investigation and forgotten to resume them. Check the group's suspended processes when it "does nothing".

Skill

Amazon ECS

Stopped tasks keep a stopped reason, a stop code and each container's exit code for a while. The service's events show placement problems and deployment progress.

aws ecs describe-tasks --cluster prod --tasks 3f2a9c1e0b7d4e8f \
  --query "tasks[].{reason:stoppedReason,code:stopCode,containers:containers[].{name:name,exit:exitCode,reason:reason}}"
Message or exit codeMeaning
Exit code 137The container was killed (SIGKILL), usually for exceeding its memory limit (OOM); raise memory or fix the leak
Exit code 1 (or another non-zero code)The application exited with an error; read its logs
Exit code 139Segmentation fault in the application
Exit code 143Stopped by SIGTERM, for example during a deployment or scale-in
CannotPullContainerErrorWrong image or tag; the task execution role can't pull from ECR; no route to ECR (NAT, or the ecr.api, ecr.dkr and S3 endpoints)
ResourceInitializationError: unable to pull secrets or registry authThe task execution role can't read Secrets Manager or Parameter Store, or there's no route to them
unable to place a task because no container instance met all of its requirementsNot enough free CPU, memory or ports on EC2 container instances; add capacity or use Fargate
Task deregistered: failed ELB health checksWrong health check path or port, app slow to start, or the service's health check grace period too short
Deployment rolled back by the circuit breakerNew tasks kept failing to reach a steady state

ECS Exec opens a shell or runs a command inside a running container, through Systems Manager:

aws ecs execute-command --cluster prod --task 3f2a9c1e0b7d4e8f --container web --interactive --command "/bin/sh"

It needs enableExecuteCommand on the service or task, and the task role needs the ssmmessages permissions.

Skill

Amazon EKS

Kubernetes records its view of failures in pod status and events:

kubectl get pods -n orders                         # status: Pending, CrashLoopBackOff, ImagePullBackOff...
kubectl describe pod orders-7d9f8c6b5-x2k4q -n orders   # events at the bottom explain why
kubectl logs orders-7d9f8c6b5-x2k4q -n orders --previous   # logs from the crashed container
kubectl get events -n orders --sort-by=.lastTimestamp
StatusLikely cause
PendingNo node has enough CPU or memory for the pod's requests; taints without matching tolerations; a persistent volume in a different AZ from the available nodes; node autoscaler not working
ImagePullBackOffWrong image or tag, or the node role can't pull from ECR
CrashLoopBackOffThe container starts and exits repeatedly: configuration error, missing secret, failing dependency (read --previous logs)
OOMKilledThe container exceeded its memory limit
Running but receives no trafficThe readiness probe fails, so the pod isn't added to the Service's endpoints
Nodes NotReady, or pods stuck without IP addressesThe VPC CNI has run out of IP addresses in the subnets (use larger subnets or prefix delegation)
New nodes don't join the clusterThe node role isn't granted access (access entry or aws-auth), or the nodes can't reach the cluster endpoint
kubectl returns UnauthorizedYour IAM principal has no access entry or Kubernetes permissions
  • Control plane logs: API server, audit, authenticator, controller manager and scheduler logs can be sent to CloudWatch Logs, but they're off by default. Turn them on to investigate authentication or scheduling problems.
  • Metrics and logs: Container Insights (through the CloudWatch Observability add-on) gives node, pod and container metrics and logs.
  • Cluster insights: EKS flags upgrade blockers such as deprecated APIs.

"Pods are Pending although the cluster has free capacity" often means the pod's persistent volume is in a different AZ (EBS volumes are zonal), or a taint, node selector or affinity rule excludes the nodes that have room.

Key takeaways

  • Metrics to scope, traces to locate, logs to explain, change history to correlate. Contributor Insights for top offenders, Reachability Analyzer and Flow Logs for network paths.
  • Check the AWS Health Dashboard early ("AWS or us?"). OpsCenter centralizes OpsItems with context and runbooks.
  • Root cause analysis: mitigate first, scope, build a timeline of changes, test hypotheses, ask why, and fix the process in a blameless review.
  • CodePipeline: follow the failed action's details. Common causes are connection authorization, artifact KMS or bucket permissions, cross-account trust, expired approvals and Lambda actions that never report.
  • CodeBuild: phase details and logs; privileged mode for Docker, role permissions, VPC without NAT, memory, rate limits, full clone for Git commands.
  • CodeDeploy: lifecycle events per instance and the agent's logs; Pending means agent or network.
  • CloudFormation: read the first failure event; know name collisions, quotas, cfn-signal timeouts, custom resource responses, imported exports and ContinueUpdateRollback.
  • Synthetics canaries catch broken user journeys that health checks miss; screenshots and HAR files show why.
  • Auto Scaling: activity history, capacity and quotas, deleted references, KMS permissions for the service-linked role, health check loops, suspended processes.
  • ECS: stopped reasons and exit codes (137 = out of memory), execution role and network for image and secret pulls, placement capacity, ECS Exec. EKS: pod status and events, resource requests, zonal volumes, IP exhaustion, access entries, control plane logs.
