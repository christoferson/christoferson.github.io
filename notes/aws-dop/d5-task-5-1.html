Overview

Task statement 5.1

Manage event sources to process, notify, and take action in response to events.

Every change in an AWS environment produces an event: an instance is scheduled for retirement, an API call disables logging, a deployment fails, a message arrives. This task tests whether you know where those events come from, how to route them to the right consumers, and how to build processing that's reliable when volumes spike or consumers fail. Typical scenarios: "automatically handle EC2 scheduled maintenance", "react within seconds when someone stops CloudTrail", "several teams need the same order events", or "process events in order per customer".

AWS services that generate, capture and process events

Knowledge

AWS Health

AWS Health tells you about events at AWS that affect your resources: hardware failures, service issues in a Region, and planned maintenance.

Event categoryExample
issueIncreased error rates for a service in a Region
scheduledChangeEC2 instance retirement, RDS maintenance, a required database engine upgrade
accountNotificationAn expiring certificate, a deprecation notice for a runtime you use
  • AWS Health Dashboard: your account's events in the console, plus the public view of service status.
  • EventBridge integration: Health events arrive on the default event bus (source aws.health), available on every support plan. Events are delivered in the Region of the affected resource; global events arrive in us-east-1.
  • Health API: programmatic access, which requires a Business, Enterprise On-Ramp or Enterprise support plan.
  • Organizational view: aggregates Health events from every account in the organization, from the management account or a delegated administrator.

"Automatically act when AWS schedules maintenance or retirement for our instances" points to an EventBridge rule on AWS Health events. You don't need to poll the Health API.

Knowledge

Amazon EventBridge

EventBridge is the central router for events on AWS. Every event has the same envelope: source, detail-type, account, region, time, resources and a service-specific detail.

FeatureWhat it does
Default event busReceives events from AWS services in the account and Region
Custom event busesFor your applications' events, or for collecting events from other accounts
Partner event sourcesEvents from SaaS applications (for example, Zendesk, Datadog, Auth0)
RulesMatch events by pattern and send them to up to five targets
API destinationsSend events to any HTTP endpoint (a chat webhook, an incident tool) with managed authentication and rate limits
Archive and replayKeep events and replay them later
Schema registryDiscovers event structures and generates code bindings
EventBridge PipesPoint-to-point integration from a source (SQS, Kinesis, DynamoDB Streams, Amazon MQ, Kafka) through filtering and enrichment to a target
EventBridge SchedulerOne-time or recurring schedules that invoke targets
Global endpointsFail event ingestion over between two Regions

Other AWS services that emit useful events

  • Compute and containers: EC2 instance state changes, Auto Scaling launch and terminate events, ECS task and service state changes.
  • Delivery: CodePipeline, CodeBuild and CodeDeploy state changes.
  • Monitoring: CloudWatch alarm state changes.
  • Compliance and security: AWS Config compliance changes, and GuardDuty, Security Hub and Inspector findings.
  • Data and operations: S3 object events (when enabled on the bucket), Systems Manager automation and Parameter Store changes, Trusted Advisor check results.
Knowledge

AWS CloudTrail as an event source

Every API call recorded by CloudTrail can also reach EventBridge as an event with detail-type AWS API Call via CloudTrail. That turns any API action into a trigger: someone deleted a resource, changed a policy, opened a security group.

  • A trail is required: EventBridge receives these events only when a CloudTrail trail with logging is enabled in the account.
  • Write management events: matched by rules in the normal ENABLED state.
  • Read-only management events (Describe*, Get*, List*): matched only by rules whose state is ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS.
  • Data events: object-level S3 calls or Lambda invocations arrive only if the trail logs those data events.
  • Default bus only: CloudTrail events arrive on the default event bus. To use them elsewhere, add a rule there that forwards them to a custom bus or another account.
  • Other detail-types: AWS Console Signin via CloudTrail for console sign-ins, and AWS Service Event via CloudTrail for events AWS services generate themselves.
  • Timing and global services: events reach EventBridge within seconds to minutes, much faster than waiting for log files in S3. IAM, STS and console sign-in events arrive in us-east-1.

"An EventBridge rule for an API call never fires" usually means there's no active trail in the account, the rule is in a different Region from the call (or not in us-east-1 for global services), or the call is read-only and the rule isn't enabled for all management events.

"Detect a specific API call and respond within minutes" points to an EventBridge rule on AWS API Call via CloudTrail. Querying CloudTrail logs in S3 with Athena is for investigation afterwards.

Event-driven architectures: fan-out, event streaming and queuing

Knowledge
PatternHow it worksServicesChoose it when
Fan-out (publish-subscribe)One event is delivered to many independent subscribersSNS topics, EventBridge rulesSeveral systems must react to the same event
Queuing (point to point)Each message is processed by one consumer, at the consumer's paceSQS Standard and FIFOBuffer load, decouple a producer from a slower consumer, retry failed work
Event streamingAn ordered, durable log of records that several consumers read independently and can replayKinesis Data Streams, Amazon MSK, DynamoDB StreamsHigh volume, ordering per key, several consumers of the same data, replay

These patterns are often combined. SNS to SQS fan-out gives each subscriber its own durable queue, so a slow or failing consumer doesn't lose messages or slow the others.

Properties to design for

  • At-least-once delivery: SQS Standard, SNS, EventBridge and Kinesis can all deliver an event more than once. Make consumers idempotent (for example, record processed event IDs in DynamoDB).
  • Ordering: only guaranteed per SQS FIFO message group, per SNS FIFO topic message group, or per Kinesis shard (by partition key). Standard queues and EventBridge don't guarantee order.
  • Failure handling: dead-letter queues for SQS and SNS subscriptions, DLQs and retry policies for EventBridge targets, on-failure destinations for asynchronous Lambda, bisect-on-error for streams.
  • Orchestration vs choreography: a Step Functions workflow controlling each step, or services reacting to each other's events. Orchestration is easier to follow and debug; choreography couples services less.

A poison message (one that always fails) is retried until it expires and blocks progress. In a FIFO queue it blocks its whole message group; in a stream it blocks the shard. Set a maxReceiveCount with a dead-letter queue, or bisect and skip failed records in stream consumers.

Integrating AWS event sources

Skill

Acting on AWS Health events: instance retirement

When AWS schedules an EC2 instance for retirement because of degraded hardware, a stop and start moves it to healthy hardware. Automate that instead of waiting for the deadline:

  1. AWS Health raises the eventAWS_EC2_INSTANCE_RETIREMENT_SCHEDULED for the affected instance.
  2. An EventBridge rule matches itIn the instance's Region.
  3. Systems Manager Automation restarts the instanceAWS-RestartEC2Instance stops and starts it, which places it on new hardware.
  4. The team is toldA second target notifies the owners through SNS.
health-retirement-rule.yml 
InstanceRetirementRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [aws.health]
      detail-type: [AWS Health Event]
      detail:
        service: [EC2]
        eventTypeCode: [AWS_EC2_INSTANCE_RETIREMENT_SCHEDULED]
    Targets:
      - Id: restart-instance
        Arn: !Sub arn:aws:ssm:${AWS::Region}::automation-definition/AWS-RestartEC2Instance:$DEFAULT
        RoleArn: !GetAtt EventsRunAutomationRole.Arn          # allows ssm:StartAutomationExecution
        InputTransformer:
          InputPathsMap:
            instance: $.detail.affectedEntities[0].entityValue   # the instance ID
          InputTemplate: '{"InstanceId": ["<instance>"]}'
      - Id: notify-owners
        Arn: !Ref OpsTopic

Restarting immediately may not suit every workload. A gentler design stores the event, then restarts the instance during the next maintenance window, or replaces it through its Auto Scaling group.

Skill

Acting on API calls from CloudTrail

Assume the security team wants CloudTrail logging turned back on within a minute if anyone stops it:

stop-logging-rule.yml 
StopLoggingRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [aws.cloudtrail]
      detail-type: [AWS API Call via CloudTrail]
      detail:
        eventSource: [cloudtrail.amazonaws.com]
        eventName: [StopLogging, DeleteTrail, UpdateTrail]
    Targets:
      - Id: restart-logging
        Arn: !GetAtt RestartLoggingFunction.Arn
      - Id: alert-security
        Arn: !Ref SecurityAlertsTopic
restart_logging.py 
import boto3

cloudtrail = boto3.client("cloudtrail")

def handler(event, context):
    detail = event["detail"]
    trail = detail["requestParameters"]["name"]           # the trail that was stopped
    who = detail["userIdentity"].get("arn", "unknown")
    if detail["eventName"] == "StopLogging":
        cloudtrail.start_logging(Name=trail)
    print(f"{detail['eventName']} on {trail} by {who}; logging restored where possible")
  • Prevent as well as respond: an SCP denying cloudtrail:StopLogging stops this happening in member accounts at all. The rule then catches anything the SCP doesn't cover.
  • Other common triggers: CreateAccessKey for the root user, PutBucketPolicy or PutBucketAcl making data public, AuthorizeSecurityGroupIngress from 0.0.0.0/0, DisableKey on KMS keys.
Skill

Custom events and a central event bus

Applications publish their own events with PutEvents:

aws events put-events --entries '[{
  "EventBusName": "orders",
  "Source": "com.example.orders",
  "DetailType": "OrderPlaced",
  "Detail": "{\"orderId\":\"o-7781\",\"total\":129.50,\"country\":\"DE\"}"
}]'

To handle operational events from every account in one place, forward them to a central event bus. Assume a central operations account 333333333333:

central-bus.yml (operations account 333333333333) 
CentralOpsBus:
  Type: AWS::Events::EventBus
  Properties:
    Name: central-ops

CentralOpsBusPolicy:
  Type: AWS::Events::EventBusPolicy
  Properties:
    EventBusName: !Ref CentralOpsBus
    StatementId: allow-organization
    Statement:
      Effect: Allow
      Principal: "*"
      Action: events:PutEvents
      Resource: !GetAtt CentralOpsBus.Arn
      Condition:
        StringEquals:   # any account in our organization
          aws:PrincipalOrgID: o-a1b2c3d4e5
forward-rule.yml (every member account, deployed by StackSets) 
ForwardOpsEvents:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [aws.health, aws.guardduty, aws.codepipeline]
    Targets:
      - Id: central-ops
        Arn: arn:aws:events:eu-west-1:333333333333:event-bus/central-ops
        RoleArn: !GetAtt ForwardEventsRole.Arn                # allows events:PutEvents on the central bus

Rules on the central bus then notify teams, open tickets or run automation for all accounts at once. Events keep their original account field, so you always know where they came from.

"Send events to an external tool such as a chat channel or incident platform without writing code" points to an EventBridge API destination, which handles authentication and rate limiting for the HTTP call.

Skill

Fan-out with a queue per consumer

Assume order events must reach a billing service (all orders) and a customs service (international orders only):

order-fan-out.yml 
OrderEventsTopic:
  Type: AWS::SNS::Topic

BillingQueue:
  Type: AWS::SQS::Queue
  Properties:
    VisibilityTimeout: 180
    RedrivePolicy:
      deadLetterTargetArn: !GetAtt BillingDlq.Arn
      maxReceiveCount: 5

CustomsQueue:
  Type: AWS::SQS::Queue
  Properties:
    VisibilityTimeout: 180
    RedrivePolicy:
      deadLetterTargetArn: !GetAtt CustomsDlq.Arn
      maxReceiveCount: 5

BillingSubscription:
  Type: AWS::SNS::Subscription
  Properties:
    TopicArn: !Ref OrderEventsTopic
    Protocol: sqs
    Endpoint: !GetAtt BillingQueue.Arn
    RawMessageDelivery: true                    # deliver the message without the SNS envelope

CustomsSubscription:
  Type: AWS::SNS::Subscription
  Properties:
    TopicArn: !Ref OrderEventsTopic
    Protocol: sqs
    Endpoint: !GetAtt CustomsQueue.Arn
    RawMessageDelivery: true
    FilterPolicyScope: MessageBody
    FilterPolicy:   # only international orders
      international: [true]

QueuesAllowSns:
  Type: AWS::SQS::QueuePolicy
  Properties:
    Queues: [!Ref BillingQueue, !Ref CustomsQueue]
    PolicyDocument:
      Statement:
        - Effect: Allow
          Principal: { Service: sns.amazonaws.com }
          Action: sqs:SendMessage
          Resource: "*"
          Condition:
            ArnEquals:
              aws:SourceArn: !Ref OrderEventsTopic

BillingConsumer:
  Type: AWS::Lambda::EventSourceMapping
  Properties:
    EventSourceArn: !GetAtt BillingQueue.Arn
    FunctionName: !Ref BillingFunction
    BatchSize: 10
    FunctionResponseTypes: [ReportBatchItemFailures]   # retry only the failed messages
  • Queue policy: each queue must allow the topic to send to it, or messages are silently dropped.
  • Ordering per customer: use an SNS FIFO topic with SQS FIFO queues, and set MessageGroupId to the customer ID. Messages for one customer stay in order; different customers are processed in parallel.
  • Recovering failures: after fixing a bug, redrive messages from the dead-letter queue back to the source queue.

Lambda reading from SQS deletes a whole batch on success. Without ReportBatchItemFailures, one bad message makes the whole batch return to the queue and be processed again, duplicating the good ones.

Skill

Stream processing with Kinesis and Lambda

  1. Producers write recordsWith a partition key (for example, the device ID), so each key's records stay in order on one shard.
  2. Lambda reads batches per shardAn event source mapping polls each shard, starting from the latest record or a timestamp.
  3. Failures are containedBisect batch on error splits a failing batch to find the bad record; maximum retry attempts and record age limit how long it's retried; an on-failure destination (SQS or SNS) receives details of skipped records.
  4. Throughput scalesA parallelization factor (up to 10) processes several batches per shard at once while keeping order per partition key.
  5. Other consumers read the same dataFirehose archives the stream to S3; Managed Service for Apache Flink computes windowed metrics. Enhanced fan-out gives each consumer its own read throughput.

"Several applications must each process the same high-volume events, in order per device, and be able to reprocess the last 24 hours" points to Kinesis Data Streams, not SQS. SQS deletes messages once processed and has no replay.

Skill

Orchestrated response with Step Functions

When the response to an event has several steps and decisions, start a Step Functions workflow from the EventBridge rule. Assume high-severity GuardDuty findings on EC2 instances should be enriched, contained if critical, and always reported:

finding-triage.asl.yml 
StartAt: Enrich
States:
  Enrich:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:ec2:describeInstances   # owner tags, subnet, and so on
    Parameters:
      InstanceIds.$: States.Array($.detail.resource.instanceDetails.instanceId)
    ResultPath: $.instance
    Next: IsCritical

  IsCritical:
    Type: Choice
    Choices:
      - Variable: $.detail.severity
        NumericGreaterThanEquals: 8
        Next: Isolate
    Default: Notify

  Isolate:
    Type: Task
    Resource: arn:aws:states:::aws-sdk:ec2:modifyInstanceAttribute
    Parameters:
      InstanceId.$: $.detail.resource.instanceDetails.instanceId
      Groups: [sg-0quarantine00000]                         # a security group with no rules
    ResultPath: null
    Retry:
      - ErrorEquals: [States.TaskFailed]
        MaxAttempts: 3
        BackoffRate: 2
    Next: Notify

  Notify:
    Type: Task
    Resource: arn:aws:states:::sns:publish
    Parameters:
      TopicArn: arn:aws:sns:eu-west-1:333333333333:security-alerts
      Message.$: States.Format('GuardDuty {} on {}', $.detail.type, $.detail.resource.instanceDetails.instanceId)
    End: true

The EventBridge rule matches aws.guardduty findings with severity of 7 or more and targets the state machine, with a role allowing states:StartExecution.

Skill

EventBridge Pipes

A pipe connects one source to one target with optional filtering, enrichment and transformation, replacing "glue" Lambda functions that only read from a queue and call another service.

international-orders-pipe.yml 
InternationalOrdersPipe:
  Type: AWS::Pipes::Pipe
  Properties:
    RoleArn: !GetAtt PipeRole.Arn
    Source: !GetAtt OrdersQueue.Arn                            # read from SQS
    SourceParameters:
      SqsQueueParameters: { BatchSize: 10 }
      FilterCriteria:
        Filters:
          - Pattern: '{"body": {"international": [true]}}'     # only these messages continue (and are paid for)
    Enrichment: !GetAtt AddCustomsDataFunction.Arn              # add data before delivery
    Target: !Ref CustomsStateMachine                          # start a workflow per message
    TargetParameters:
      StepFunctionStateMachineParameters:
        InvocationType: FIRE_AND_FORGET
  • Many consumers of the same event, routed by content: EventBridge rules.
  • One source to one target with filtering or enrichment and no custom code: EventBridge Pipes.

Key takeaways

  • AWS Health: issues, scheduled changes and account notifications; events reach EventBridge on every support plan (the Health API needs Business support or higher); organizational view across accounts.
  • EventBridge: default bus for AWS events, custom buses, partner sources, rules with up to five targets, API destinations, archive and replay, Pipes, Scheduler.
  • CloudTrail delivers API calls to the default bus as AWS API Call via CloudTrail, only with an active trail. Read-only calls need the ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS rule state; global service events arrive in us-east-1.
  • Fan-out (SNS, EventBridge), queuing (SQS) and streaming (Kinesis) solve different problems; SNS-to-SQS gives each subscriber a durable queue.
  • Design for at-least-once delivery (idempotent consumers), limited ordering (FIFO groups, shards), and poison messages (DLQs, bisect, redrive).
  • Automate Health events (for example, instance retirement with AWS-RestartEC2Instance) and risky API calls (restart CloudTrail logging) with EventBridge rules.
  • Centralize events: member accounts forward to a central bus whose policy allows the organization (aws:PrincipalOrgID).
  • SQS with Lambda: queue policy for SNS, ReportBatchItemFailures, a DLQ with maxReceiveCount. Kinesis with Lambda: bisect on error, retry limits, on-failure destination, parallelization factor.
  • Step Functions for multi-step responses with decisions and retries; Pipes for point-to-point integration with filtering and enrichment.
