Overview

Task statement 4.3

Automate monitoring and event management of complex environments.

In a large environment, nobody can watch every dashboard. This task is about wiring telemetry to action: events that start processing, scaling that follows demand, alarms that notify the right people and fix common faults, and compliance problems corrected automatically. Typical scenarios: "process every log file as soon as it lands in S3", "notify the team when any pipeline fails", "the RDS volume is about to fill up", or "every new instance must report memory metrics".

Event-driven, asynchronous design patterns

Knowledge

In an event-driven design, something happens (a file arrives, an instance stops, a pipeline fails), an event describing it is published, and any number of consumers react on their own, asynchronously. Producers don't know or wait for consumers.

RoleServices
Event sourcesS3 (object events), AWS services (state changes sent to EventBridge), CloudTrail (API calls sent to EventBridge), CloudWatch alarms (state changes), AWS Health, your applications
RoutersAmazon EventBridge (rules with content filtering), Amazon SNS (topics with subscriptions)
BuffersAmazon SQS
ConsumersLambda, Step Functions, SSM Automation and Run Command, ECS tasks, API destinations (HTTP endpoints)

S3 Event Notifications or EventBridge?

S3 Event NotificationsS3 events through EventBridge
DestinationsSNS, SQS, LambdaAny EventBridge target (more than 20 services, plus other buses and HTTP endpoints)
FilteringEvent type plus key prefix and suffixAny field: key, size, requester, source IP and more
Several consumers of the same eventsNot for overlapping prefix and event combinations; fan out through SNS insteadMany rules on the same events
SetupNotification configuration on the bucketTurn on "Send notifications to EventBridge" for the bucket, then write rules
ExtrasSimple and directArchive and replay, retries with dead-letter queues per target

Patterns

  • Event to function: S3 or EventBridge invokes Lambda directly. Simple, for moderate volume.
  • Event to topic to many: SNS fans one event out to email, chat, Lambda and SQS subscribers.
  • Event to queue to function: SQS between the event and Lambda absorbs bursts, retries failures and lets you cap concurrency.
  • Event to workflow: EventBridge starts a Step Functions workflow or SSM Automation runbook for multi-step responses.

For asynchronous invocations (S3, SNS, EventBridge), Lambda retries a failed event twice and then drops it, unless you configure an on-failure destination or a dead-letter queue. Silent data loss here is a common exam scenario.

Alert notification and action capabilities

Knowledge

A CloudWatch alarm can take several kinds of action when it changes state:

ActionUse for
Amazon SNS topicNotifying people (email, SMS, mobile push, chat through Amazon Q Developer in chat applications) and systems (Lambda, SQS, HTTPS endpoints)
Lambda function (directly)Custom automated responses without an SNS topic in between
EC2 actionsStop, terminate, reboot or recover the instance the metric belongs to
Auto Scaling policyStep or simple scaling
Systems Manager OpsCenterCreate an OpsItem for operators to investigate, with runbooks attached

Every alarm state change is also sent to EventBridge as a CloudWatch Alarm State Change event, so a rule can route it to any EventBridge target.

EC2 automatic recovery

  • Simplified automatic recovery: on by default for supported instance types. AWS moves an instance to new hardware when the underlying host fails.
  • Alarm-based recovery: an alarm on StatusCheckFailed_System with the action arn:aws:automate:<region>:ec2:recover. The recovered instance keeps its instance ID, private and Elastic IP addresses, EBS volumes and metadata. Instance store data is lost.
  • Instance status check failures: StatusCheckFailed_Instance problems are inside the OS, so recovery doesn't help; a reboot action might.

SNS features that matter

  • Subscription filter policies: each subscriber gets only the messages it cares about (for example, only severity = critical).
  • Delivery: retries per protocol, and a dead-letter queue per subscription for messages that can't be delivered.
  • Encryption: server-side encryption with KMS.

Route 53 health check metrics (HealthCheckStatus) are published only in us-east-1. A CloudWatch alarm on a Route 53 health check must be created in us-east-1, whatever Region the application runs in.

Configuring solutions for auto scaling

Skill

DynamoDB provisioned capacity

dynamodb-autoscaling.yml 
OrdersWriteTarget:
  Type: AWS::ApplicationAutoScaling::ScalableTarget
  Properties:
    ServiceNamespace: dynamodb
    ResourceId: table/orders
    ScalableDimension: dynamodb:table:WriteCapacityUnits
    MinCapacity: 50
    MaxCapacity: 2000

OrdersWritePolicy:
  Type: AWS::ApplicationAutoScaling::ScalingPolicy
  Properties:
    PolicyName: orders-write-70
    PolicyType: TargetTrackingScaling
    ScalingTargetId: !Ref OrdersWriteTarget
    TargetTrackingScalingPolicyConfiguration:
      PredefinedMetricSpecification:
        PredefinedMetricType: DynamoDBWriteCapacityUtilization
      TargetValue: 70                          # keep consumed at about 70% of provisioned

Repeat for read capacity, and for each global secondary index (dynamodb:index:WriteCapacityUnits). For spiky or unpredictable traffic, on-demand mode avoids scaling delays entirely.

RDS storage auto scaling

rds.yml 
OrdersDb:
  Type: AWS::RDS::DBInstance
  Properties:
    Engine: postgres
    DBInstanceClass: db.r6g.large
    AllocatedStorage: "200"
    MaxAllocatedStorage: 1000                # turns on storage auto scaling, up to 1,000 GiB
    MultiAZ: true
    MasterUsername: appadmin
    ManageMasterUserPassword: true

ECS capacity provider with managed scaling

For ECS on EC2, a capacity provider keeps the Auto Scaling group sized to fit the tasks, so service auto scaling never waits for capacity:

ecs-capacity-provider.yml 
OrdersCapacityProvider:
  Type: AWS::ECS::CapacityProvider
  Properties:
    AutoScalingGroupProvider:
      AutoScalingGroupArn: !Ref EcsInstancesAsg     # group with NewInstancesProtectedFromScaleIn: true
      ManagedScaling:
        Status: ENABLED
        TargetCapacity: 100                        # 100 = no spare instances; 80 keeps 20% headroom
        MinimumScalingStepSize: 1
        MaximumScalingStepSize: 10
      ManagedTerminationProtection: ENABLED          # don't scale in instances still running tasks

ClusterProviders:
  Type: AWS::ECS::ClusterCapacityProviderAssociations
  Properties:
    Cluster: prod
    CapacityProviders: [!Ref OrdersCapacityProvider]
    DefaultCapacityProviderStrategy:
      - CapacityProvider: !Ref OrdersCapacityProvider
        Weight: 1

Managed scaling creates a target tracking policy on the group using the CapacityProviderReservation metric (how much of the capacity is needed). Pair it with ECS service auto scaling for the tasks themselves.

EC2 Auto Scaling groups

A target tracking policy on ALBRequestCountPerTarget or CPU is the default. Add scheduled actions for known peaks, predictive scaling for regular daily cycles, and a warm pool when instances take long to start.

Creating custom metrics, metric filters, alarms and notifications

Skill

The full chain from a log line to someone's phone:

  1. The application records somethingA custom metric through PutMetricData or the Embedded Metric Format, or a log line such as {"level":"ERROR","event":"payment_failed"}.
  2. A metric filter counts itFor log lines, a metric filter on the log group publishes PaymentFailures.
  3. An alarm evaluates itFor example, more than 5 in 3 of the last 5 minutes.
  4. SNS distributes itThe alarm publishes to a topic with email, chat and Lambda subscribers.
  5. A Lambda subscriber actsIt opens a ticket, adds context, or triggers a fix.
payment-alerting.yml 
PaymentFailuresFilter:
  Type: AWS::Logs::MetricFilter
  Properties:
    LogGroupName: /app/payments
    FilterPattern: '{ $.event = "payment_failed" }'
    MetricTransformations:
      - MetricNamespace: Payments/App
        MetricName: PaymentFailures
        MetricValue: "1"
        DefaultValue: 0

PaymentFailuresAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: Payments/App
    MetricName: PaymentFailures
    Statistic: Sum
    Period: 60
    EvaluationPeriods: 5
    DatapointsToAlarm: 3                         # 3 of the last 5 minutes
    Threshold: 5
    ComparisonOperator: GreaterThanThreshold
    AlarmActions: [!Ref PaymentsAlertsTopic]
    OKActions: [!Ref PaymentsAlertsTopic]            # tell people when it recovers too

PaymentsAlertsTopic:
  Type: AWS::SNS::Topic
  Properties:
    KmsMasterKeyId: !Ref AlertsKey               # customer managed key (see the trap below)
    Subscription:
      - Protocol: email
        Endpoint: payments-oncall@example.com
      - Protocol: lambda
        Endpoint: !GetAtt CreateTicketFunction.Arn

AllowSnsToInvokeTicketFunction:
  Type: AWS::Lambda::Permission
  Properties:
    FunctionName: !Ref CreateTicketFunction
    Action: lambda:InvokeFunction
    Principal: sns.amazonaws.com
    SourceArn: !Ref PaymentsAlertsTopic
  • Email subscriptions must be confirmed by the recipient before they receive anything.
  • Lambda subscriptions need a resource-based permission allowing sns.amazonaws.com to invoke the function.

An SNS topic encrypted with the AWS managed key aws/sns can't receive CloudWatch alarm notifications, because that key's policy can't be changed to allow CloudWatch. Use a customer managed key whose key policy allows cloudwatch.amazonaws.com to use kms:Decrypt and kms:GenerateDataKey*.

Configuring S3 events to process log files and deliver them elsewhere

Skill

Many AWS logs are delivered to S3 as files (ALB access logs, CloudTrail, VPC Flow Logs to S3, CloudFront standard logs). An S3 event can trigger processing the moment each file lands.

Example: ALB access logs to CloudWatch Logs

Assume ALB access logs arrive in orders-alb-logs as gzip files under AWSLogs/. A Lambda function parses each file and writes the 5xx requests to a CloudWatch log group, where metric filters and Logs Insights can use them. (The same function could send documents to OpenSearch instead.)

alb-log-processing.yml 
AlbLogsBucket:
  Type: AWS::S3::Bucket
  DependsOn: AllowS3ToInvokeProcessor              # the permission must exist first
  Properties:
    BucketName: orders-alb-logs
    NotificationConfiguration:
      LambdaConfigurations:
        - Event: s3:ObjectCreated:*
          Function: !GetAtt AlbLogProcessor.Arn
          Filter:
            S3Key:
              Rules:
                - { Name: prefix, Value: AWSLogs/ }
                - { Name: suffix, Value: .log.gz }

AllowS3ToInvokeProcessor:
  Type: AWS::Lambda::Permission
  Properties:
    FunctionName: !Ref AlbLogProcessor
    Action: lambda:InvokeFunction
    Principal: s3.amazonaws.com
    SourceArn: arn:aws:s3:::orders-alb-logs
    SourceAccount: !Ref AWS::AccountId
alb_log_processor.py 
import gzip, time, urllib.parse
import boto3

s3 = boto3.client("s3")
logs = boto3.client("logs")
LOG_GROUP, LOG_STREAM = "/alb/orders/5xx", "processor"

def handler(event, context):
    events = []
    for record in event["Records"]:
        bucket = record["s3"]["bucket"]["name"]
        key = urllib.parse.unquote_plus(record["s3"]["object"]["key"])   # keys arrive URL-encoded
        body = s3.get_object(Bucket=bucket, Key=key)["Body"].read()
        for line in gzip.decompress(body).decode().splitlines():
            fields = line.split(" ")
            if len(fields) > 8 and fields[8].startswith("5"):              # elb_status_code
                events.append({"timestamp": int(time.time() * 1000), "message": line})
    if events:
        logs.put_log_events(logGroupName=LOG_GROUP, logStreamName=LOG_STREAM, logEvents=events)
  • High volume: send the S3 events to an SQS queue and let Lambda read from it, so bursts are buffered and failures retried.
  • Several consumers: send the events to SNS or EventBridge and subscribe each processor.
  • Delivery without code: stream logs into Amazon Data Firehose instead, which delivers to OpenSearch, S3 or Splunk with optional transformation.

If the function writes its output back into the same bucket and prefix that triggers it, every output file triggers it again, in an endless and expensive loop. Write to a different bucket or prefix, and filter the trigger on prefix and suffix.

Configuring EventBridge to send notifications based on event patterns

Skill

An EventBridge rule on an event bus has an event pattern (which events match) and up to five targets (where matching events go). AWS services send events to the default bus in each account and Region automatically.

Pattern matching

PatternMatches
"state": ["FAILED"]Exact value (any value in the list)
"key": [{ "prefix": "logs/" }]Values starting with a string (also suffix, wildcard)
"state": [{ "anything-but": "running" }]Any value except these
"severity": [{ "numeric": [">=", 7] }]Numeric comparisons
"errorCode": [{ "exists": true }]The field is present (or absent with false)
"$or": [ {...}, {...} ]Either of two sets of conditions

Useful event patterns

Any failed pipeline execution 
{
  "source": ["aws.codepipeline"],
  "detail-type": ["CodePipeline Pipeline Execution State Change"],
  "detail": { "state": ["FAILED"] }
}
An EC2 instance stopped or terminated 
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": { "state": ["stopped", "terminated"] }
}
An ECS task stopped unexpectedly 
{
  "source": ["aws.ecs"],
  "detail-type": ["ECS Task State Change"],
  "detail": {
    "lastStatus": ["STOPPED"],
    "stopCode": [{ "anything-but": "UserInitiated" }]
  }
}
Scheduled maintenance announced by AWS Health 
{
  "source": ["aws.health"],
  "detail-type": ["AWS Health Event"],
  "detail": {
    "service": ["EC2", "RDS"],
    "eventTypeCategory": ["scheduledChange"]
  }
}

A readable notification with an input transformer

Raw events are long JSON documents. An input transformer picks fields and builds a short message for the SNS target:

pipeline-failure-rule.yml 
PipelineFailedRule:
  Type: AWS::Events::Rule
  Properties:
    EventPattern:
      source: [aws.codepipeline]
      detail-type: [CodePipeline Pipeline Execution State Change]
      detail:
        state: [FAILED]
    Targets:
      - Id: notify-team
        Arn: !Ref DeliveryAlertsTopic
        InputTransformer:
          InputPathsMap:
            pipeline: $.detail.pipeline
            execution: $.detail.execution-id
            region: $.region
          InputTemplate: '"Pipeline <pipeline> failed in <region> (execution <execution>)."'
        RetryPolicy:
          MaximumRetryAttempts: 5
          MaximumEventAgeInSeconds: 3600
        DeadLetterConfig:   # keep events that couldn't be delivered
          Arn: !GetAtt EventsDlq.Arn
  • SNS topic policy: the topic must allow events.amazonaws.com to publish to it.
  • Cross-account and cross-Region: a rule can send events to an event bus in another account or Region, to centralize events (for example, all security findings into one account).
  • Archive and replay: keep events and replay them later, for example to reprocess after fixing a consumer.

Events from global services (IAM, STS global endpoint, AWS sign-in for console logins) arrive through CloudTrail in us-east-1. A rule that watches for root console sign-ins must be created in us-east-1.

Installing and configuring agents on EC2 instances

Skill

SSM Agent

  • Preinstalled on Amazon Linux, Ubuntu Server, Windows Server and other AWS-provided AMIs. Other images need it installed (user data, or baked into the AMI).
  • To register as a managed node, it needs permissions (an instance profile with AmazonSSMManagedInstanceCore, or Default Host Management Configuration) and a route to the ssm, ssmmessages and ec2messages endpoints.
  • Keep it current with a State Manager association running AWS-UpdateSSMAgent, or the agent auto-update setting.

CloudWatch agent across the fleet

  1. Store the agent configuration in Parameter StoreFor example, AmazonCloudWatch-linux, with the metrics and log files to collect.
  2. Install the packageA State Manager association runs AWS-ConfigureAWSPackage with AmazonCloudWatchAgent.
  3. Apply the configurationA second association runs AmazonCloudWatch-ManageAgent reading that parameter.
  4. New instances get both automaticallyAssociations target tags, so anything launched with the tag is configured within minutes.
agent-associations.yml 
UpdateSsmAgent:
  Type: AWS::SSM::Association
  Properties:
    Name: AWS-UpdateSSMAgent
    Targets: [{ Key: tag:Environment, Values: [prod] }]
    ScheduleExpression: rate(14 days)

InstallCloudWatchAgent:
  Type: AWS::SSM::Association
  Properties:
    Name: AWS-ConfigureAWSPackage
    Parameters:
      action: [Install]
      name: [AmazonCloudWatchAgent]
    Targets: [{ Key: tag:Environment, Values: [prod] }]

ConfigureCloudWatchAgent:
  Type: AWS::SSM::Association
  Properties:
    Name: AmazonCloudWatch-ManageAgent
    Parameters:
      action: [configure]
      mode: [ec2]
      optionalConfigurationSource: [ssm]
      optionalConfigurationLocation: [AmazonCloudWatch-linux]   # the Parameter Store parameter
      optionalRestart: ["yes"]
    Targets: [{ Key: tag:Environment, Values: [prod] }]

The instance profile also needs CloudWatchAgentServerPolicy so the agent can publish metrics and logs and read its configuration. Quick Setup host management can set all of this up across an organization in a few clicks.

"Memory metrics must be collected from every instance, including ones launched in future, without logging in" points to State Manager associations installing and configuring the CloudWatch agent from Parameter Store.

Configuring AWS Config rules to remediate issues

Skill

A remediation configuration links a Config rule to a Systems Manager Automation document. When a resource becomes non-compliant, Config runs the document against it, manually or automatically.

  1. A resource changesSomeone creates a bucket without default encryption.
  2. The rule evaluates its3-bucket-server-side-encryption-enabled marks it NON_COMPLIANT.
  3. Remediation runsConfig starts AWS-EnableS3BucketEncryption with the bucket name, using the remediation role.
  4. The rule re-evaluatesThe bucket becomes COMPLIANT; the compliance change also reaches EventBridge for reporting.
s3-encryption-remediation.yml 
S3EncryptionRule:
  Type: AWS::Config::ConfigRule
  Properties:
    ConfigRuleName: s3-bucket-server-side-encryption-enabled
    Source:
      Owner: AWS
      SourceIdentifier: S3_BUCKET_SERVER_SIDE_ENCRYPTION_ENABLED
    Scope:
      ComplianceResourceTypes: [AWS::S3::Bucket]

S3EncryptionRemediation:
  Type: AWS::Config::RemediationConfiguration
  Properties:
    ConfigRuleName: !Ref S3EncryptionRule
    TargetType: SSM_DOCUMENT
    TargetId: AWS-EnableS3BucketEncryption
    Automatic: true
    MaximumAutomaticAttempts: 5
    RetryAttemptSeconds: 60
    Parameters:
      BucketName:   # filled with the non-compliant bucket
        ResourceValue: { Value: RESOURCE_ID }
      SSEAlgorithm:
        StaticValue: { Values: [AES256] }
      AutomationAssumeRole:
        StaticValue:
          Values: [!GetAtt ConfigRemediationRole.Arn]
  • Remediation role: trusted by ssm.amazonaws.com, with only the permissions the document needs (here, s3:PutEncryptionConfiguration).
  • Custom fixes: write your own Automation document when no AWS document fits.
  • Exceptions: remediation exceptions exclude specific resources that are allowed to differ.
  • At scale: deploy rules with remediation as conformance packs across the organization.

Remediation that runs but changes nothing usually means the AutomationAssumeRole is missing, isn't trusted by Systems Manager, or lacks the permission for the fix. Check the Automation execution's output in Systems Manager.

Configuring health checks (Route 53, ALB)

Skill

ALB target group health checks

target-group.yml 
WebTargetGroup:
  Type: AWS::ElasticLoadBalancingV2::TargetGroup
  Properties:
    VpcId: !Ref Vpc
    Protocol: HTTP
    Port: 8080
    HealthCheckProtocol: HTTP
    HealthCheckPath: /health
    HealthCheckIntervalSeconds: 15
    HealthCheckTimeoutSeconds: 5
    HealthyThresholdCount: 3
    UnhealthyThresholdCount: 2
    Matcher: { HttpCode: "200-299" }
  • Auto Scaling: set the group's HealthCheckType to ELB so failing instances are replaced, not just ignored.
  • ECS: set HealthCheckGracePeriodSeconds on the service so slow-starting tasks aren't killed before they're ready.

Route 53 health checks

route53-health-checks.yml 
ApiEndpointCheck:
  Type: AWS::Route53::HealthCheck
  Properties:
    HealthCheckConfig:
      Type: HTTPS_STR_MATCH                      # HTTPS plus a string in the response body
      FullyQualifiedDomainName: api.example.com
      ResourcePath: /health
      SearchString: '"status":"ok"'
      RequestInterval: 30
      FailureThreshold: 3
      Regions: [us-east-1, eu-west-1, ap-southeast-1]   # where the checkers run

InternalServiceCheck:
  Type: AWS::Route53::HealthCheck
  Properties:
    HealthCheckConfig:
      Type: CLOUDWATCH_METRIC                    # for private endpoints the checkers can't reach
      AlarmIdentifier:
        Name: internal-api-errors
        Region: eu-west-1
      InsufficientDataHealthStatus: LastKnownStatus

ApiHealthAlarm:                                    # must be created in us-east-1
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: AWS/Route53
    MetricName: HealthCheckStatus
    Dimensions: [{ Name: HealthCheckId, Value: !Ref ApiEndpointCheck }]
    Statistic: Minimum
    Period: 60
    EvaluationPeriods: 1
    Threshold: 1
    ComparisonOperator: LessThanThreshold        # 1 = healthy, 0 = unhealthy
    AlarmActions: [!Ref OpsTopic]
  • Calculated health checks: combine child checks (for example, healthy if 2 of 3 are healthy), to represent a whole service.
  • Firewall rules: the endpoint's security groups or firewall must allow Route 53 health checker IP ranges.
  • Failover: attaching a health check to a DNS record lets Route 53 stop returning that record while it's unhealthy.

Key takeaways

  • Event-driven: S3 Event Notifications (SNS, SQS, Lambda; prefix and suffix) or S3 to EventBridge (any target, rich filtering, many rules). Configure on-failure destinations for asynchronous Lambda.
  • Auto scaling: EC2 groups, RDS storage (MaxAllocatedStorage), Aurora replicas, DynamoDB (target utilization or on-demand), ECS tasks plus capacity providers, EKS HPA plus Karpenter, Lambda provisioned concurrency.
  • Alarm actions: SNS, Lambda, EC2 stop, terminate, reboot or recover, Auto Scaling, OpsItems. Recover fixes system check failures; reboot for instance check failures.
  • Health checks: ALB and NLB target groups, Auto Scaling ELB checks, ECS grace periods, Route 53 endpoint, calculated and alarm-based checks. Route 53 health check metrics live in us-east-1.
  • Notification chain: custom metric or metric filter, alarm, SNS (customer managed key if encrypted), email, chat and Lambda subscribers.
  • S3 log processing: event to Lambda (add the invoke permission first, URL-decode keys), SQS for volume, and never write output back to the triggering prefix.
  • EventBridge: patterns with exact, prefix, anything-but, numeric and exists matching; input transformers for readable messages; retries and DLQs on targets; global service events in us-east-1.
  • Agents: SSM Agent with permissions and endpoints, kept updated by AWS-UpdateSSMAgent; the CloudWatch agent installed and configured by State Manager from Parameter Store.
  • Config remediation: rule plus RemediationConfiguration pointing to an SSM Automation document, with an assume role trusted by Systems Manager; conformance packs for scale.
