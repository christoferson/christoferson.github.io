Overview

Task statement 1.1

Implement CI/CD pipelines.

This task tests whether you can assemble a working delivery pipeline from AWS developer tools and make the right design choices along the way. Expect scenario questions such as "a team in a tooling account must deploy to three workload accounts", "builds must not expose database credentials" or "the pipeline must deploy only when a release tag is pushed".

SDLC concepts, phases and models

Knowledge

Phases and how they map to a pipeline

A delivery pipeline automates the SDLC from commit to production. On AWS the phases map to services like this:

PhasePurposeTypical AWS services
SourceVersion-controlled code, IaC templates and configurationCodeCommit, GitHub/GitLab/Bitbucket via CodeConnections, S3, ECR
BuildCompile, package, build images, run unit testsCodeBuild, EC2 Image Builder
TestIntegration, acceptance, security and load testsCodeBuild, Lambda, Step Functions, Device Farm
ReleaseStore versioned, immutable artifacts; approve promotionS3, ECR, CodeArtifact, manual approval actions
DeployRoll the release out to environmentsCodeDeploy, CloudFormation, ECS, Elastic Beanstalk, Service Catalog
Operate and monitorObserve health and feed results backCloudWatch, X-Ray, AWS Config, Systems Manager

CI, continuous delivery and continuous deployment

  • Continuous integration (CI): every change is merged often to a shared branch, then built and tested automatically. The goal is fast feedback.
  • Continuous delivery: every change that passes the pipeline is releasable. Production deployment waits for a human decision, usually a manual approval action.
  • Continuous deployment: every change that passes all automated checks goes to production with no human gate. This needs strong automated tests, alarms and automatic rollback.

If a scenario says changes must be reviewed or signed off before production, the answer includes a manual approval action (continuous delivery). If it says "no manual intervention", look for automated tests plus alarm-based rollback (continuous deployment).

Development models and branching strategies

  • Waterfall: sequential phases with large, infrequent releases. Rarely the right answer on a DevOps exam.
  • Agile and DevOps: small, frequent increments with automated feedback loops and shared ownership of operations.
  • Trunk-based development: short-lived branches merged to main at least daily. One pipeline watches main, and feature flags (for example, AWS AppConfig) hide unfinished work.
  • GitFlow: long-lived develop, release/* and hotfix/* branches. This often means one pipeline per branch, or branch filters on pipeline triggers.
  • Feature-branch workflow with pull requests: build and test every pull request before merge (CodeBuild webhooks or pipeline pull request triggers), then deploy from main.

Pipeline deployment patterns for single- and multi-account environments

Knowledge

CodePipeline anatomy

  • Pipeline: an ordered set of stages. Each stage contains one or more actions.
  • Action categories: Source, Build, Test, Deploy, Approval and Invoke (Lambda or Step Functions).
  • runOrder: actions in a stage with the same runOrder run in parallel, and higher numbers run later.
  • Artifacts: each action passes input and output artifacts through the pipeline's artifact store, an S3 bucket encrypted with KMS.
  • Transitions: you can disable the transition between stages to pause promotion without editing the pipeline.
  • Manual approval: sends an optional SNS notification. The approval request expires after 7 days, and the action then fails.

Pipeline type V1 vs V2

FeatureV1V2
Triggers with filtersNo: any push to the configured branchYes: filter by branch, Git tag, file path or pull request event (connection-based sources)
Pipeline-level variablesNoYes: pass values at start time
Execution modesSuperseded onlySuperseded, Queued or Parallel
Stage rollback and conditionsNoYes: for example, roll back a stage or block it based on CloudWatch alarms
PricingPer active pipeline per monthPer action execution minute
  • Superseded: a newer execution replaces an older one waiting to enter a stage.
  • Queued: executions run one at a time, in order.
  • Parallel: executions run independently, which suits per-branch or per-pull-request validation.

Single-account pattern

One account holds the source, pipeline and every environment, typically one stage per environment: Source → Build → Deploy-Dev → Test → Approval → Deploy-Prod. It's simple, but the blast radius is large and environments aren't isolated. It's acceptable for small teams or sandboxes, but not the recommended answer for production isolation.

Knowledge

Multi-account pattern (central tooling account)

The pipeline lives in a dedicated tooling (shared services) account, and each environment is a separate workload account. This is the AWS-recommended pattern and the usual exam answer.

For the example below, assume two accounts:

AccountIDWhat lives there
Tooling account111111111111CodePipeline, its service role PipelineServiceRole, the S3 artifact bucket tooling-artifacts and its KMS key
Production account222222222222The application stack, plus two roles: CrossAccountDeployRole and CfnExecutionRole

When the pipeline reaches its production stage, this happens:

  1. The pipeline stores the build outputCodePipeline writes the artifact to tooling-artifacts, encrypted with the tooling account's customer managed KMS key.
  2. The pipeline assumes the production rolePipelineServiceRole calls sts:AssumeRole on CrossAccountDeployRole in 222222222222.
  3. The production role reads the artifactIt needs both the bucket policy and the KMS key policy in the tooling account to allow it.
  4. The production role calls CloudFormationIt starts a stack update in 222222222222 and passes CfnExecutionRole.
  5. CloudFormation creates the resourcesIt uses CfnExecutionRole's permissions, not the pipeline's.

Step 1: KMS key policy (tooling account)

The artifact key must be a customer managed key, and its key policy must allow the production account to use it.

tooling-account.yml 
ArtifactKey:
  Type: AWS::KMS::Key
  Properties:
    KeyPolicy:
      Version: "2012-10-17"
      Statement:
        - Sid: AllowToolingAccountAdmin
          Effect: Allow
          Principal:
            AWS: arn:aws:iam::111111111111:root
          Action: kms:*
          Resource: "*"
        - Sid: AllowProductionAccountToUseKey
          Effect: Allow
          Principal:   # the other account
            AWS: arn:aws:iam::222222222222:root
          Action: [kms:Decrypt, kms:DescribeKey, kms:Encrypt, kms:ReEncrypt*, kms:GenerateDataKey*]
          Resource: "*"

Step 2: Artifact bucket policy (tooling account)

tooling-account.yml 
ArtifactBucketPolicy:
  Type: AWS::S3::BucketPolicy
  Properties:
    Bucket: tooling-artifacts
    PolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Sid: AllowProductionDeployRole
          Effect: Allow
          Principal:
            AWS: arn:aws:iam::222222222222:role/CrossAccountDeployRole
          Action: [s3:GetObject, s3:GetObjectVersion, s3:PutObject, s3:GetBucketLocation, s3:ListBucket]
          Resource:
            - arn:aws:s3:::tooling-artifacts
            - arn:aws:s3:::tooling-artifacts/*

Step 3: Cross-account deploy role (production account)

The trust policy (AssumeRolePolicyDocument) lets the tooling account's pipeline role assume this role. The permissions let it run CloudFormation, pass the execution role and read the artifact.

production-account.yml 
CrossAccountDeployRole:
  Type: AWS::IAM::Role
  Properties:
    RoleName: CrossAccountDeployRole
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:   # who may assume it
            AWS: arn:aws:iam::111111111111:role/PipelineServiceRole
          Action: sts:AssumeRole
    Policies:
      - PolicyName: deploy-from-tooling
        PolicyDocument:
          Version: "2012-10-17"
          Statement:
            - Effect: Allow
              Action: [cloudformation:CreateStack, cloudformation:UpdateStack, cloudformation:DescribeStacks,
                       cloudformation:CreateChangeSet, cloudformation:ExecuteChangeSet,
                       cloudformation:DescribeChangeSet, cloudformation:DeleteChangeSet]
              Resource: "*"
            - Effect: Allow
              Action: iam:PassRole                                   # hand the execution role to CloudFormation
              Resource: arn:aws:iam::222222222222:role/CfnExecutionRole
            - Effect: Allow
              Action: [s3:GetObject, s3:GetObjectVersion, s3:PutObject]
              Resource: arn:aws:s3:::tooling-artifacts/*
            - Effect: Allow
              Action: [kms:Decrypt, kms:DescribeKey, kms:GenerateDataKey*]
              Resource: arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab

Step 4: CloudFormation execution role (production account)

CloudFormation itself assumes this role to create the application's resources, so its trust policy names the CloudFormation service.

production-account.yml 
CfnExecutionRole:
  Type: AWS::IAM::Role
  Properties:
    RoleName: CfnExecutionRole
    AssumeRolePolicyDocument:
      Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Principal:
            Service: cloudformation.amazonaws.com
          Action: sts:AssumeRole
    ManagedPolicyArns:
      - arn:aws:iam::aws:policy/PowerUserAccess   # example only: scope down to the stack's resources

Step 5: The pipeline's deploy action (tooling account)

This is where the two roles are wired in. The action-level RoleArn is the role CodePipeline assumes to run the action. The Configuration.RoleArn is the role CloudFormation uses to create resources.

tooling-account.yml (pipeline) 
ArtifactStore:
  Type: S3
  Location: tooling-artifacts
  EncryptionKey:   # customer managed key from step 1
    Id: !GetAtt ArtifactKey.Arn
    Type: KMS
Stages:
  # ... Source and Build stages ...
  - Name: Deploy-Production
    Actions:
      - Name: DeployStack
        ActionTypeId:
          Category: Deploy
          Owner: AWS
          Provider: CloudFormation
          Version: "1"
        RoleArn: arn:aws:iam::222222222222:role/CrossAccountDeployRole      # 1. CodePipeline assumes this
        InputArtifacts: [{ Name: BuildOutput }]
        Configuration:
          ActionMode: CREATE_UPDATE
          StackName: my-app
          TemplatePath: BuildOutput::template.yml
          Capabilities: CAPABILITY_IAM
          RoleArn: arn:aws:iam::222222222222:role/CfnExecutionRole          # 2. CloudFormation uses this

Finally, PipelineServiceRole in the tooling account needs sts:AssumeRole on arn:aws:iam::222222222222:role/CrossAccountDeployRole.

Permissions checklist

WhereWhatWhy
Tooling: KMS key policyAllow 222222222222 to decrypt and generate data keysThe artifact is encrypted with this key
Tooling: bucket policyAllow CrossAccountDeployRole to get (and put) objectsThe production role reads the artifact
Tooling: pipeline rolests:AssumeRole on CrossAccountDeployRoleTo start the action in production
Production: deploy role trustTrust PipelineServiceRoleSo the tooling account can assume it
Production: deploy role permissionsCloudFormation, iam:PassRole, S3 read, KMS decryptTo run the deployment
Production: execution roleTrust cloudformation.amazonaws.com; permissions for the stack's resourcesCloudFormation creates the resources

Deploy the production account's roles before the tooling account's bucket policy. A bucket policy that names a role ARN that doesn't exist yet is rejected.

The default AWS managed key (aws/s3) cannot be shared across accounts. A cross-account pipeline needs a customer managed key whose key policy grants the other accounts access. "Access denied when the deploy action reads the artifact" points to the key policy or the bucket policy.

Deploying to many accounts at scale

  • CloudFormation StackSets: deploy one template to many accounts and Regions from a single operation. With service-managed permissions (through AWS Organizations) you can target whole OUs, and accounts that later join the OU get the stack automatically. CodePipeline has StackSet deploy actions.
  • CDK Pipelines: a self-mutating pipeline defined in CDK. It updates its own structure, then deploys "stages" (groups of stacks) to each account and Region after the environments are bootstrapped with trust to the tooling account (cdk bootstrap --trust).
  • Service Catalog: publish approved products that teams in other accounts launch themselves.
Knowledge

Cross-Region actions

A single pipeline can run actions in other Regions by setting the action's region. CodePipeline needs an artifact store (S3 bucket) in every Region where actions run, and it copies artifacts there automatically. Each regional bucket needs its own KMS key in that Region. The console creates these for you; with IaC you declare ArtifactStores per Region.

"Deploy the same application to us-east-1 and eu-west-1 from one pipeline" calls for cross-Region actions with a regional artifact store, or StackSets for infrastructure. It doesn't need two separate pipelines.

Configuring code, image and artifact repositories

Skill

Code repositories

  • AWS CodeCommit: managed private Git, with IAM for authentication and authorization. It supports approval rule templates for pull requests, and repository events go to EventBridge.

    CodeCommit was closed to new customers in July 2024; the restriction has since been lifted. Exam questions still use it as the default AWS-native source.

  • AWS CodeConnections formerly CodeStar Connections: connects CodePipeline and CodeBuild to GitHub, GitHub Enterprise Server, GitLab (including self-managed) and Bitbucket. A connection is created in a pending state and must be completed (authorized) in the console. Using it requires the codeconnections:UseConnection permission (older policies use codestar-connections:UseConnection).
  • Amazon S3 as a source: a versioned bucket holding a zip file. The bucket must have versioning enabled.

Image repositories: Amazon ECR

  • Authentication: aws ecr get-login-password | docker login. The token is valid for 12 hours.
  • Image scanning: basic scanning (on push or manual) or enhanced scanning through Amazon Inspector, which continuously rescans images and also covers language packages.
  • Tag immutability: prevents tags such as v1.4.2 from being overwritten. Use it for release images.
  • Lifecycle policies: expire untagged or old images automatically (for example, keep the last 30 images).
  • Replication: cross-Region and cross-account replication rules for multi-Region deployments.
  • Repository policies: resource-based policies that allow other accounts to pull images.
  • Pull through cache: caches upstream public registries (for example, ECR Public, Docker Hub, GitHub Container Registry) in your private registry to avoid rate limits and add scanning.

Artifact repositories: AWS CodeArtifact and S3

  • CodeArtifact structure: a domain (shared storage and KMS encryption, often one per organization) contains repositories.
  • Upstream repositories: chain repositories so a team repository falls back to a shared one.
  • External connections: link a repository to public registries such as npmjs, PyPI or Maven Central so packages are fetched and cached on first request.
  • Authentication: aws codeartifact login --tool npm|pip|twine, or get-authorization-token for Maven and Gradle. Tokens last up to 12 hours.
  • Access control: domain and repository policies (resource-based) enable cross-account access.
  • S3: generic artifacts (zip bundles, CloudFormation packages, CodeDeploy revisions). Use versioning, encryption and lifecycle rules.

"Developers must only use approved open source packages" or "builds fail when the public registry is unavailable" points to CodeArtifact with an upstream repository and an external connection. "Container images must be scanned for vulnerabilities on push" points to ECR scan on push or enhanced scanning.

Using version control to integrate pipelines with application environments

Skill

How pipelines detect changes

SourceRecommended change detectionNotes
CodeCommitEventBridge rule on repository state changePolling is legacy and slower; avoid it in answers
GitHub, GitLab, BitbucketWebhooks managed by CodeConnectionsV2 triggers add branch, tag, file path and pull request filters
S3EventBridge rule on object eventsBucket versioning required
ECREventBridge rule on image pushTrigger on a specific repository and tag

Mapping branches and tags to environments

  • Branch per environment (develop → dev, main → prod): one pipeline per branch, or V2 triggers with branch filters.
  • Release on tag: a V2 trigger filtered on tags such as v* runs the production pipeline only for tagged releases.
  • Monorepos: V2 file path filters (for example, services/orders/**) start only the pipeline for the service that changed.
  • Pull request validation: CodeBuild webhooks with filter groups (event PULL_REQUEST_CREATED, PULL_REQUEST_UPDATED, base branch) build every pull request and report status back to the Git provider. V2 pipelines can also trigger on pull request events.

Source artifact format

  • Default (CODE_ZIP): a zip of the source without Git metadata. It's enough for most builds.
  • Full clone (CODEBUILD_CLONE_REF): passes a Git reference so CodeBuild clones the repository with history. It's needed when the build runs git commands (for example, git describe for versioning or git diff for changed files). It works only with a downstream CodeBuild action, and the CodeBuild role needs permission to use the connection (or codecommit:GitPull).

A build that fails with "not a git repository" while running git commands in CodeBuild means the source action uses the default zip output. Switch it to full clone.

Notifications on repository and pipeline events

  • Notification rules (AWS CodeStar Notifications) send CodeCommit, CodeBuild, CodeDeploy and CodePipeline events to SNS topics or to chat through Amazon Q Developer in chat applications (formerly AWS Chatbot).
  • EventBridge receives the same events for custom automation, for example invoking a Lambda function when a pipeline execution fails.

Setting up build processes (AWS CodeBuild)

Skill

The buildspec

CodeBuild runs each build in a fresh container. It reads buildspec.yml from the root of the source, or a different file or an inline buildspec set on the project or action.

version: 0.2
env:
  variables:
    APP_ENV: "staging"
  parameter-store:
    API_URL: "/myapp/staging/api-url"
  secrets-manager:
    DB_PASSWORD: "prod/myapp/db:password"      # secret-id:json-key
  exported-variables:
    - IMAGE_TAG                                # available to later pipeline actions
phases:
  install:
    runtime-versions:
      nodejs: 20
  pre_build:
    commands:
      - aws ecr get-login-password | docker login --username AWS --password-stdin $REPO_URI
      - export IMAGE_TAG=${CODEBUILD_RESOLVED_SOURCE_VERSION:0:8}
  build:
    on-failure: ABORT
    commands:
      - npm ci && npm test
      - docker build -t $REPO_URI:$IMAGE_TAG .
  post_build:
    commands:
      - docker push $REPO_URI:$IMAGE_TAG
      - printf '[{"name":"web","imageUri":"%s"}]' $REPO_URI:$IMAGE_TAG > imagedefinitions.json
reports:
  unit-tests:
    files: ["reports/junit.xml"]
    file-format: JUNITXML
artifacts:
  files:
    - imagedefinitions.json
cache:
  paths:
    - "node_modules/**/*"

Phase behaviour to remember

  • Phase order: install → pre_build → build → post_build. Any command that exits non-zero fails its phase.
  • post_build after a failure: post_build still runs when build fails. Check CODEBUILD_BUILD_SUCCEEDING (1 or 0) before pushing images or publishing artifacts.
  • Failure handling: a finally block in a phase always runs (use it for cleanup), and on-failure: CONTINUE lets later phases run after a failure.

  • Build can't reach the internet after being moved into a VPC: add a NAT gateway route or VPC endpoints.

Managing build and deployment secrets

Skill

Never store credentials in source code, buildspecs or plaintext environment variables, because they appear in logs and in the console. Reference them instead, and grant the CodeBuild or deployment role permission to read them.

Secrets ManagerSystems Manager Parameter Store
Best forCredentials that must rotate (database passwords, API keys)Configuration values and simple secrets
Automatic rotationBuilt in (managed rotation for RDS, Aurora, Redshift and others; Lambda for custom)No native rotation. Parameter policies (Advanced tier) can expire or notify
SizeUp to 64 KB4 KB (Standard), 8 KB (Advanced)
CostPer secret per month plus API callsStandard tier free; Advanced charged
EncryptionAlways KMSSecureString uses KMS; String is plaintext
Cross-accountResource policy plus a customer managed keyAdvanced parameters can be shared with AWS RAM
ReplicationMulti-Region replica secretsNo

Using them in pipelines

  • CodeBuild buildspec: the parameter-store and secrets-manager sections, as shown above. On the project, set the environment variable type to PARAMETER_STORE or SECRETS_MANAGER.
  • Permissions: the build role needs secretsmanager:GetSecretValue or ssm:GetParameters, plus kms:Decrypt for customer managed keys.
  • Private registries: CodeBuild can pull a private base image using credentials stored in Secrets Manager.
  • CloudFormation: dynamic references such as {{resolve:secretsmanager:prod/db:SecretString:password}} and {{resolve:ssm-secure:/app/key}} keep secrets out of templates and parameters.
  • Containers: ECS task definitions reference secrets with valueFrom, and the task execution role reads them at container start.

Putting a secret in a CodeBuild plaintext environment variable, or in a CloudFormation parameter without NoEcho, exposes it. If the scenario says "the password appears in the console or logs", the fix is a Secrets Manager or Parameter Store reference.

Determining appropriate deployment strategies (AWS CodeDeploy)

Skill

The deploy stage of a pipeline decides how a new release reaches users. With CodeDeploy, you deploy a revision (your packaged application plus an appspec file) to a deployment group (the target instances, ECS service or Lambda function) using a deployment configuration (how fast traffic or instances move to the new version). The strategies available depend on the compute platform.

PlatformStrategiesBuilt-in configurations
EC2 / on-premisesIn-place (rolling) or blue/green (new instances or ASG copy, then traffic switch at the load balancer)AllAtOnce, HalfAtATime, OneAtATime, or a custom minimum healthy hosts count or percentage
LambdaTraffic shifting between alias versionsLambdaCanary10Percent5Minutes (also 10, 15, 30 minutes), LambdaLinear10PercentEvery1Minute (also 2, 3, 10 minutes), LambdaAllAtOnce
ECSBlue/green with two target groups behind an ALB or NLB, plus an optional test listenerECSCanary10Percent5Minutes or 15Minutes, ECSLinear10PercentEvery1Minutes or 3Minutes, ECSAllAtOnce

All the names above are prefixed with CodeDeployDefault.

Picking a strategy from the scenario

  • Zero downtime and instant rollback: blue/green.
  • Expose a small share of users first and watch alarms: canary.
  • Increase traffic gradually and evenly: linear.
  • Keep capacity, cost and new infrastructure low on EC2: in-place with OneAtATime or HalfAtATime.
  • Speed matters more than safety (dev or test): all at once.

The AppSpec file (EC2 / on-premises)

Every revision has an appspec.yml at its root. It tells the CodeDeploy agent which files to copy where, and which of your scripts to run at each lifecycle hook.

appspec.yml 
version: 0.0
os: linux
files:                                   # copied during the Install step
  - source: /build
    destination: /var/www/myapp
permissions:
  - object: /var/www/myapp
    owner: webapp
hooks:
  ApplicationStop:
    - location: scripts/stop_server.sh
      timeout: 60
  BeforeInstall:
    - location: scripts/install_dependencies.sh
  AfterInstall:
    - location: scripts/configure_app.sh
  ApplicationStart:
    - location: scripts/start_server.sh
  ValidateService:
    - location: scripts/health_check.sh   # non-zero exit fails the deployment
      timeout: 120

Lifecycle hooks, in order

This is the order for an in-place deployment behind a load balancer. Without a load balancer, the first and last groups are skipped. Steps marked CodeDeploy are run by CodeDeploy itself and can't run your scripts; steps marked Your script run what you list under hooks.

  1. Take the instance out of service
  2. BeforeBlockTrafficYour scriptTasks before the instance stops receiving traffic, such as draining work in progress.
  3. BlockTrafficCodeDeployDeregisters the instance from the load balancer.
  4. AfterBlockTrafficYour scriptTasks once traffic has stopped.
  5. Replace the application
  6. ApplicationStopYour scriptStops the running application gracefully. Runs the script from the previous revision.
  7. DownloadBundleCodeDeployThe agent copies the new revision from S3 or GitHub to the instance.
  8. BeforeInstallYour scriptPrepares the instance: install packages, back up the current version, decrypt files.
  9. InstallCodeDeployCopies files to their destinations, as listed under files.
  10. AfterInstallYour scriptConfigures the application and sets file permissions.
  11. ApplicationStartYour scriptStarts the services stopped in ApplicationStop.
  12. ValidateServiceYour scriptChecks that the deployment worked, such as a local health check. A failure here fails the deployment.
  13. Put the instance back in service
  14. BeforeAllowTrafficYour scriptLast checks before traffic returns.
  15. AllowTrafficCodeDeployRegisters the instance with the load balancer again.
  16. AfterAllowTrafficYour scriptTasks once the instance is serving traffic again.

In a blue/green deployment, the install hooks run on the new (green) instances, AllowTraffic moves traffic to them, and BlockTraffic then runs on the original (blue) instances.

The AppSpec file for Lambda and ECS

For Lambda and ECS there are no files to copy. The AppSpec names what to deploy, and each hook is a Lambda function that runs a check and reports success or failure back to CodeDeploy.

appspec.yml (Lambda) 
version: 0.0
Resources:
  - OrdersFunction:
      Type: AWS::Lambda::Function
      Properties:
        Name: orders
        Alias: live              # traffic shifts on this alias
        CurrentVersion: "3"
        TargetVersion: "4"
Hooks:
  - BeforeAllowTraffic: PreTrafficCheck    # before any traffic reaches version 4
  - AfterAllowTraffic: PostTrafficCheck   # after all traffic has moved
appspec.yml (ECS) 
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: "<TASK_DEFINITION>"   # filled in by the pipeline
        LoadBalancerInfo:
          ContainerName: web
          ContainerPort: 8080
Hooks:
  - AfterAllowTestTraffic: RunSmokeTests   # tests hit the test listener first

ECS hooks, in order: BeforeInstall, AfterInstall, AfterAllowTestTraffic, BeforeAllowTraffic, AfterAllowTraffic.

ApplicationStop runs the script from the previously deployed revision. If that script is broken, the deployment fails before the new code is even downloaded. The fix is to correct the old script on the instances, or redeploy with ignoreApplicationStopFailures.

Rollbacks and safety

  • Automatic rollback: enable it on the deployment group for deployment failure and/or when a CloudWatch alarm goes into ALARM during the deployment.
  • How rollback works: CodeDeploy redeploys the last known good revision as a new deployment with a new deployment ID. It doesn't "undo" the failed one.
  • Agent: EC2 and on-premises targets need the CodeDeploy agent (installable with Systems Manager Distributor), plus an instance profile that can read the revision from S3.
  • Targets: deployment groups select instances by tags, Auto Scaling group or on-premises instance tags.

Amazon ECS added built-in blue/green deployments in 2025, alongside rolling updates. The exam guide predates this, so expect ECS blue/green questions to assume CodeDeploy.

Key takeaways

  • Production approvals mean continuous delivery (manual approval action). "No manual steps" means continuous deployment with automated tests and alarm-based rollback.
  • Multi-account pipelines: tooling account, customer managed KMS key, artifact bucket policy, cross-account roles, and a CloudFormation service role in each target account.
  • Cross-Region actions need an artifact store in every Region the pipeline touches.
  • V2 pipelines add trigger filters (branch, tag, file path, pull request), variables, execution modes and stage rollback.
  • ECR handles image scanning, tag immutability, lifecycle policies and replication. CodeArtifact handles packages, with upstream repositories and external connections.
  • CodeBuild needs privileged mode for Docker builds and a NAT gateway or endpoints when it runs in a VPC. post_build runs even if build fails.
  • Use Secrets Manager for secrets that rotate and Parameter Store for configuration. Never use plaintext environment variables.
  • CodeDeploy strategies: in-place or blue/green for EC2; canary, linear or all-at-once for Lambda and ECS. Rollback is a new deployment of the last good revision.
