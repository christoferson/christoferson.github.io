Overview

Task 1.3

Describe the AI/ML development lifecycle.

A model is a small part of an AI system. Most of the effort goes into getting the data ready, deploying the model so applications can use it, and keeping it accurate once real data starts changing. The exam expects you to know the stages in order, what happens in each, which AWS service supports it, and how you would tell whether the result is any good, both technically and for the business. You won't be asked to build a pipeline; the exam guide lists that as out of scope.

Components of an AI/ML pipeline

Skill 1.3.1Describe and differentiate components of an AI/ML pipeline

A pipeline is the sequence of steps that turns a business problem and raw data into a deployed model, and keeps it working. The stages below follow the order AWS uses in its Machine Learning Lens. It is a cycle, not a straight line: monitoring results send the team back to earlier stages, and evaluation often sends it back to data preparation.

The running example: an online retailer wants to predict which customers will stop buying in the next 90 days (churn), so it can send them a retention offer.

The stages of a traditional ML pipeline

1. Business goal and problem framing

Define the business outcome and turn it into an ML problem. "Reduce lost customers by 10%" becomes "predict, for each active customer, the probability they make no purchase in the next 90 days" (binary classification). This stage also sets how success will be measured, both as a model metric (recall on churners) and as a business metric (customers retained per dollar of offers), and checks whether ML is the right tool at all.

2. Data collection

Gather the data the model will learn from, from wherever it lives: order history in a database, website clickstreams, support tickets, marketing data from partners. Collect it into one place, usually a data lake in Amazon S3, and record where each data set came from (its lineage) and whether it may be used for this purpose. For supervised learning, the data needs labels: here, whether each past customer actually churned.

3. Exploratory data analysis (EDA)

Look at the data before changing it: summary statistics, distributions, charts, correlations, missing values, outliers. EDA answers "what do we actually have?" The retailer might find that 8% of records have no sign-up date, that one region's data stops in March, and that only 4% of customers churned, so the data is imbalanced. These findings decide what preparation is needed.

4. Data pre-processing

Clean and reshape the data into a form the algorithm can use: remove duplicates, fill or drop missing values, fix inconsistent formats ("NY", "New York", "new york"), handle outliers, convert categories into numbers, and scale numeric values to similar ranges. Then split the data into training, validation and test sets, so the model is judged on examples it hasn't seen. Data preparation often takes most of a project's time.

5. Feature engineering

Create the input variables (features) that best expose the pattern. Raw order records become "orders in the last 30 days", "days since last purchase", "average basket value", "number of returns" and "support complaints in the last quarter". Good features often improve a model more than a better algorithm does. Feature engineering also includes feature selection: dropping inputs that add noise, leak the answer, or raise fairness concerns.

6. Model training

Choose an algorithm (for tabular churn data, a gradient-boosted tree such as XGBoost is typical) and train it on the training set, so it adjusts its parameters to fit the examples. Training runs on managed compute and produces a model artifact (a file of learned parameters).

7. Hyperparameter tuning

Adjust the settings that control training (how deep each tree may grow, the learning rate, how many rounds to train) to find the combination that performs best on the validation set. Tuning runs many training jobs with different settings and keeps the best. It is distinct from training: training learns parameters from data; tuning chooses the hyperparameters people would otherwise set by hand.

8. Evaluation

Test the final model on the held-back test set using the metrics agreed at the start, and check it against the business goal. Does it catch enough churners? Does it perform equally well across customer groups? Is it better than a simple baseline, such as "customers who haven't bought in 60 days"? If not, go back to features, data or algorithm. Metrics are covered in Model and business metrics.

9. Deployment

Make the approved model available for predictions: register it as a version, then host it on an endpoint for real-time predictions or run batch jobs. The retailer scores every customer nightly with batch inference and sends the high-risk list to its marketing system. Deployment should be gradual and reversible, for example sending a small share of traffic to a new version first.

10. Monitoring

Watch the model in production: is the incoming data still like the training data (data drift)? Are predictions still accurate once actual outcomes are known (model drift or concept drift)? Are latency, errors and cost within limits? When quality drops, the model is re-trained on newer data, which restarts the cycle. After a competitor launches a loyalty scheme, customers who look safe start leaving; monitoring is how the retailer notices.

How a generative AI pipeline differs

With a foundation model, the provider has already done the expensive training. The pipeline shifts from building a model to building an application around one:

  1. Define the use case and success criteriaFor example, a support assistant that answers product questions correctly and cites the manual.
  2. Select a modelCompare candidate foundation models on quality, cost, latency, context length and modality.
  3. Prepare data for contextCollect documents, split them into chunks and create embeddings for retrieval (RAG), rather than labeling training data.
  4. Adapt the modelPrompt engineering first, then RAG, then fine-tuning only if needed.
  5. EvaluateTest answers for accuracy, relevance, faithfulness to sources, safety and cost, often with human reviewers or an LLM as judge.
  6. Deploy with safeguardsAdd guardrails, access control and logging, then release to users.
  7. Monitor and improveTrack answer quality, user feedback, cost per conversation and new failure types, then update prompts, documents or model.

Watch for the order of stages in ordering questions: collect data, explore it, pre-process it, engineer features, train, tune, evaluate, deploy, monitor. EDA comes before pre-processing (you explore before you change), and tuning comes before final evaluation on the test set.

Feature engineering and pre-processing are different stages. Pre-processing cleans and formats existing data; feature engineering creates new, more informative inputs from it.

Sources of models

Skill 1.3.2Describe sources of FM models (for example, open source pre-trained models, training custom models)

You don't have to train every model yourself. The choice is a trade-off between effort and control: the more of the model you build, the more it fits your problem, and the more it costs in data, time, compute and expertise. From least to most effort:

Proprietary foundation models through an API

Commercial models whose weights you never see, used as a service: Anthropic Claude, Amazon Nova, and others on Amazon Bedrock. The provider trained them on vast data at huge cost; you send prompts and pay per token. They are usually the most capable general-purpose models and the fastest to start with, but you can't inspect or move the weights, and customization is limited to what the provider supports (for example, fine-tuning some models on Bedrock).

Open source and open-weight pre-trained models

Models whose trained weights are published for others to download and use, such as Meta Llama, Mistral, Qwen, DeepSeek or OpenAI's gpt-oss, and thousands of smaller task-specific models on Hugging Face (image classifiers, sentiment models, embedding models). You can use them as they are, fine-tune them on your data, and host them where you like. "Open" varies: some licenses restrict commercial use or very large deployments, so the license must be checked, and many "open" models publish the weights but not the training data.

On AWSMany open-weight models are available as managed APIs on Amazon Bedrock. Amazon SageMaker JumpStart offers hundreds of pre-trained open source models you can deploy to your own SageMaker AI endpoint or fine-tune in a few clicks.

Customizing a pre-trained model

Start from a pre-trained model and adapt it: fine-tune it on labeled examples of your task, continue pre-training it on your industry's documents, or distill a large model's behavior into a smaller, cheaper one. This keeps most of the provider's investment and adds your specialization. Amazon Bedrock supports fine-tuning, reinforcement fine-tuning and distillation for selected models; SageMaker AI supports fine-tuning any model you can run. Task 3.3 covers these methods.

Training a custom model

Build a model from your own data. For traditional ML this is normal and affordable: a churn or fraud model trained on your own records with SageMaker AI built-in algorithms, often in hours. For a foundation model it is rare: pre-training from scratch needs enormous curated data, thousands of GPUs for weeks and a specialist team, and only makes sense for organizations with unique data and very large budgets (for example, a model trained on decades of proprietary financial or biomedical data).

Other model sources Extra
  • Amazon Bedrock Custom Model Import: bring weights of a supported open architecture (for example, a Llama or Mistral model you fine-tuned elsewhere) and run them on Bedrock as a managed API.
  • AWS Marketplace and Amazon Bedrock Marketplace: models from third-party sellers, deployed into your account.
  • Pre-trained AI services: Amazon Rekognition, Comprehend, Transcribe and similar services are themselves pre-trained models you use without seeing the model at all.

"Fastest", "least effort", "no ML expertise" points to a pre-trained model or service. "Proprietary data", "unique task", "full control" points to custom training or fine-tuning. "Avoid vendor lock-in", "host anywhere", "inspect the weights" points to an open-weight model.

Using a model in production

Skill 1.3.3Describe methods to use a model in production (for example, managed API service, self-hosted API)

Either way, applications call the model through an API: they send input and receive predictions. The difference is who runs the infrastructure behind that API.

Managed API service

The provider hosts and operates the model; you call its API. Amazon Bedrock for foundation models and the AI services (Comprehend, Transcribe, Rekognition and others) work this way. There are no servers, GPUs or scaling to manage, and you usually pay per use: per token, per request, per minute of audio. Security patching, availability and model hosting are the provider's responsibility.

  • Advantages: fastest to start, no infrastructure skills needed, scales automatically, pay only for what you use, access to models you couldn't host yourself.
  • Limitations: less control over the model version, configuration and hardware; you depend on the provider's model catalog, quotas and pricing; per-use pricing can become expensive at very high, steady volume.

Self-hosted API

You deploy the model on infrastructure you control and expose it through your own endpoint. On AWS that can be a SageMaker AI endpoint (AWS manages the servers but you choose instance types, scaling and the model container), or, with most control and most work, Amazon EC2, Amazon EKS or Amazon ECS. You pay for the compute you provision, whether or not it is busy.

  • Advantages: full control over the model, version, hardware and network; can run any model, including custom-trained and open-weight models; can be cheaper at steady high volume; can meet strict isolation requirements.
  • Limitations: you handle capacity, scaling, patching, availability and cost of idle capacity; needs ML engineering skills; slower to set up.

Choosing between them

A startup adding a writing assistant to its app next month

Managed API (Amazon Bedrock): no ML team, unknown volume, speed matters.

A bank with its own credit risk model trained on internal data

Self-hosted on a SageMaker AI endpoint: a custom model, needing control and isolation in its own VPC.

A media company running a fine-tuned open-weight model around the clock at high volume

Self-hosting may be cheaper at that steady load; Bedrock Custom Model Import or Provisioned Throughput are managed alternatives to compare.

A SageMaker AI endpoint is "managed infrastructure" but still counts as self-hosting the model: you choose and pay for the instances. Amazon Bedrock is the managed API service for foundation models.

AWS services for each stage

Skill 1.3.4Identify relevant AWS services and features for each stage of an AI/ML pipeline (for example, Amazon Bedrock, Amazon Quick, Kiro, SageMaker AI)

Amazon SageMaker AI covers the traditional ML pipeline end to end; Amazon Bedrock covers the generative AI pipeline; Kiro helps developers build the application code around either; Amazon Quick is where business users analyze data and results and use AI agents. Supporting data and operations services fill in around them.

The four services named in the exam guide

Amazon SageMaker AI

The fully managed platform for building, training and deploying your own ML models. Features by stage:

  • Explore and prepare: SageMaker Studio (web-based environment with notebooks); SageMaker Canvas, a no-code interface for business analysts that now includes Data Wrangler's data preparation (import, clean, transform and visualize data with hundreds of built-in transformations).
  • Features: SageMaker Feature Store, a central repository to store, share and reuse features, with an online store for low-latency lookups at inference and an offline store for training.
  • Train and tune: managed training jobs, built-in algorithms, automatic model tuning (hyperparameter optimization), and SageMaker JumpStart's pre-trained models.
  • Experiment and track: managed MLflow to record experiments, parameters and metrics.
  • Govern and deploy: SageMaker Model Registry (versions, approval status), SageMaker Model Cards (documentation of intended use, risk and evaluation), and real-time, serverless, asynchronous and batch inference.
  • Automate: SageMaker Pipelines to define and run the workflow repeatably (an MLOps feature, see below).

Amazon Bedrock

The fully managed service for generative AI with foundation models from Amazon and other providers through one API. Features by stage: model choice and the playground for model selection; Knowledge Bases for preparing documents for RAG; Prompt Management for versioned prompts; fine-tuning and distillation for customization; Evaluations for automatic, human and LLM-as-a-judge evaluation; Guardrails for safety at deployment; on-demand and batch inference for production; invocation logging and CloudWatch metrics for monitoring. Amazon Bedrock AgentCore extends this to deploying and operating agents.

Kiro

An AI-powered development environment (an IDE, a command-line tool and more) that helps developers build software "from prototype to production" with AI agents. Its distinctive approach is spec-driven development: from a prompt, Kiro writes a requirements file (user stories and acceptance criteria), a design file and a task list, and then implements the tasks, so the work is planned and reviewable rather than improvised. Steering files give it lasting knowledge of a project's conventions; hooks run agent actions automatically on events such as saving a file (for example, updating tests). It connects to external tools through MCP.

Pipeline stageBuilding and maintaining the code of an AI application: the API around a model, the RAG application, the agent, the pipeline scripts and the tests. Kiro is also the successor to Amazon Q Developer, whose IDE plugins reach end of support on April 30, 2027.

Amazon Quick

An AI-powered service for business users to analyze data, automate tasks, build simple web applications and research topics, mainly through chat with AI agents. Its parts include Quick Sight (business intelligence dashboards, evolved from Amazon QuickSight), Quick Index (connecting company documents and data so answers are grounded in them), Quick Research (cited research reports), Quick Flows (workflows described in plain language) and Quick Automate (multi-step business process automation with agents and human approval).

Pipeline stageExploring and visualizing data during EDA, building dashboards that track model and business metrics after deployment, and delivering AI to business users. Quick is also where Amazon Q Business customers are directed, since Q Business is no longer open to new customers.

Supporting services by stage

Data collection and storage

Amazon S3 (the data lake for training data and model artifacts); AWS Glue (data catalog and ETL jobs); AWS Lake Formation (permissions for the data lake); AWS Data Exchange (buying third-party data sets); Amazon Redshift (data warehouse); Amazon EMR (large-scale processing with Spark).

Data preparation and EDA

AWS Glue DataBrew (visual, no-code cleaning with over 250 built-in transformations); SageMaker Canvas and Studio; Quick Sight for charts.

Embeddings and vector storage for generative AI

Amazon OpenSearch Service, Amazon Aurora and Amazon RDS for PostgreSQL (pgvector), Amazon Neptune, Amazon DocumentDB, and Amazon S3 Vectors, usually managed through Bedrock Knowledge Bases.

Deployment and compute

SageMaker AI endpoints; Amazon Bedrock; AWS Lambda for small models and glue code; Amazon EC2, ECS and EKS for self-hosting.

Monitoring and operations

Amazon CloudWatch (metrics, logs, alarms, dashboards); AWS CloudTrail (who called which API); Bedrock model invocation logging; SageMaker Model Registry for version history.

SageMaker Model Monitor is no longer open to new customers. It automatically compared live endpoint data and predictions with a training baseline to detect data drift, model quality drift, bias drift and feature attribution drift. Existing customers can still use it. For new work, AWS points to open-source monitoring (MLflow with Evidently), Amazon CloudWatch and Quick Sight dashboards. Older questions that ask how to "detect drift in a SageMaker endpoint" expect Model Monitor.

MLOps fundamentals

Skill 1.3.5Describe fundamental concepts of ML operations (MLOps) (for example, experimentation, repeatable processes, scalable systems, managing technical debt, achieving production readiness, model monitoring, model re-training)

MLOps applies the discipline of DevOps (automation, version control, testing, continuous delivery) to machine learning. It exists because a model isn't finished when it is trained: data changes, models decay, and a model that only worked on one data scientist's laptop can't be rebuilt, audited or improved. MLOps makes the whole lifecycle reliable, repeatable and fast.

Experimentation

ML development is trial and error: different features, algorithms and hyperparameters, each tried and measured. Experimentation in MLOps means doing this systematically, recording every run's data version, code, settings and results, so the team can compare runs, explain why the chosen model won and reproduce it later. Without tracking, the best model is often lost, or can't be rebuilt when an auditor asks.

On AWSManaged MLflow in SageMaker AI for experiment tracking; Bedrock Evaluations and Prompt Management to compare prompts and models.

Repeatable processes

Every step, from data preparation to deployment, is defined as code and automated in a pipeline, so the same inputs always produce the same model. Data, code, features and models are all versioned. This replaces manual notebooks and hand-copied files, removes human error, and lets anyone on the team rebuild and retrain the model.

On AWSSageMaker Pipelines; Model Registry for model versions; Feature Store so training and inference use identical features.

Scalable systems

The system should handle more data, more models and more requests without being redesigned: training that can spread over many machines, endpoints that scale automatically with traffic, and pipelines that can run for hundreds of models. Managed services provide much of this; MLOps adds the automation so scaling doesn't need more people.

Managing technical debt

Technical debt is the future cost of shortcuts taken now. ML systems accumulate it easily: undocumented data dependencies, copy-pasted preprocessing code that differs between training and serving, models nobody remembers how to retrain, unused features still being computed, pipelines held together by manual steps. Managing it means documentation, shared feature definitions, code reviews, tests for data and models, and removing what isn't used, before the debt makes every change slow and risky.

Achieving production readiness

A model is production-ready when it is not only accurate, but also reliable, secure, monitored, documented and supported. A typical readiness check: evaluated on the agreed metrics and for bias; documented (a model card); approved in the registry; deployed with automatic scaling, logging and alarms; tested for latency and load; secured with least-privilege access and encryption; with a rollback plan and a named owner. Strategies such as canary or blue/green deployment release new versions to a small share of traffic first.

Model monitoring

Continuously checking a deployed model. Data drift: inputs no longer resemble the training data (new products, new customer types). Concept drift: the relationship between inputs and outcome changes (a recession changes who defaults). Model quality: accuracy measured against real outcomes as they become known. Plus operational health: latency, errors, throughput and cost. Monitoring needs baselines and alarms so drops are noticed and acted on.

Model re-training

Updating the model on newer data to restore or improve performance. It can be scheduled (every month), triggered by monitoring (when accuracy falls below a threshold or drift is detected), or event-driven (when enough new labeled data arrives). The retrained model goes through the same evaluation and approval as the original before replacing it. Automating this loop (monitor, retrain, evaluate, approve, deploy) is the mark of a mature MLOps practice.

"Reproduce the model later", "track which data and settings were used" points to experiment tracking and versioning. "Automate retraining and deployment" points to pipelines (SageMaker Pipelines). "Model accuracy declines over time" points to drift, monitoring and re-training. "Reuse features across teams consistently" points to SageMaker Feature Store.

Model and business metrics

Skill 1.3.6Describe model performance metrics (for example, accuracy, precision, recall, F1 score) and business metrics (for example, cost per user, development costs, customer feedback, return on investment [ROI]) to evaluate ML models

Model metrics tell you whether the model is technically good; business metrics tell you whether it is worth having. A model can score well and still fail the business (too expensive, not trusted, solving the wrong problem), so both are needed, and both should be agreed before building.

The confusion matrix

Classification metrics are all calculated from four counts, comparing predictions with what actually happened. Take a card fraud model checking 10,000 transactions, of which 100 are really fraudulent. It flags 120 as fraud; 80 of those are real fraud.

Fraud model results on 10,000 transactions
True positives (TP)
80: flagged as fraud, really fraud
False positives (FP)
40: flagged as fraud, actually genuine (customers wrongly blocked)
False negatives (FN)
20: not flagged, actually fraud (fraud missed)
True negatives (TN)
9,860: not flagged, really genuine

Model performance metrics

Accuracy

The share of all predictions that were correct: (TP + TN) ÷ total. Here (80 + 9,860) ÷ 10,000 = 99.4%.

It sounds excellent, but it is misleading on imbalanced data. A useless model that never flags anything would be correct on all 9,900 genuine payments: 99.0% accurate while catching zero fraud. Accuracy is a fair measure only when the classes are roughly balanced and both kinds of error cost about the same.

Precision

Of the cases the model flagged as positive, how many really were: TP ÷ (TP + FP). Here 80 ÷ 120 = 66.7%. One in three blocked payments was a genuine customer.

Prioritize precision when false positives are costly: wrongly blocking good customers, flagging legitimate email as spam, sending an expensive investigation team to a false alarm.

Recall

Of the cases that really were positive, how many the model caught: TP ÷ (TP + FN). Here 80 ÷ 100 = 80%. Also called sensitivity or the true positive rate.

Prioritize recall when false negatives are costly: missing a cancer on a scan, letting fraud through, missing a safety defect. Recall and precision usually trade off: lowering the threshold catches more (higher recall) but raises more false alarms (lower precision).

F1 score

A single number that balances precision and recall: their harmonic mean, 2 × (precision × recall) ÷ (precision + recall). Here 2 × (0.667 × 0.80) ÷ (0.667 + 0.80) = 0.73.

The harmonic mean is pulled down by whichever is lower, so F1 is only high when both are. Use it when you need both, and for comparing models on imbalanced data, where accuracy misleads. The never-flag model's F1 is 0.

"Minimize false alarms" or "cost of wrongly flagging" points to precision. "Don't miss any positive cases" points to recall. "Balance precision and recall" or "imbalanced data set" points to F1. "Overall share correct, balanced classes" points to accuracy.

Other model metrics Extra

AUC (area under the ROC curve)

Measures how well a classifier separates the classes across every possible threshold, from 0.5 (no better than a coin toss) to 1.0 (perfect). Useful for comparing models before a threshold is chosen. Earlier versions of the exam guide named it.

Regression metrics

For numeric predictions: MAE (mean absolute error, the average size of the miss, in the target's units: "off by 14 units on average"), RMSE (root mean squared error, which punishes large misses more), and R² (the share of the variation in the target that the model explains, up to 1.0).

Business metrics

Cost per user

The total cost of running the AI solution divided by the number of users (or per transaction, per conversation, per prediction). It reveals whether the solution can scale profitably: an assistant costing $120,000 a year in inference and operations for 2,000 employees costs $60 per user per year, or $5 a month. For foundation models, cost per user is driven by tokens per interaction, so longer prompts and answers raise it.

Development costs

The one-time cost of building the solution: data collection and labeling, staff time, training compute, experimentation, integration and testing. It is compared with the expected benefit to decide whether to build at all, and with alternatives such as buying a ready-made service or using a pre-trained model.

Customer feedback

What users think of the AI's output: ratings (thumbs up or down on an answer), satisfaction scores (CSAT, NPS), complaints, adoption and repeat use, and how often staff override or correct the model. Feedback captures quality problems that model metrics miss, such as answers that are correct but unhelpful, and it is a source of labeled data for improving the model.

Return on investment (ROI)

The value gained compared with the cost: (benefit − cost) ÷ cost. A support assistant costs $300,000 to build and $120,000 a year to run, and saves $600,000 a year in agent time. First-year ROI is ($600,000 − $420,000) ÷ $420,000 ≈ 43%; in later years, with only running costs, ($600,000 − $120,000) ÷ $120,000 = 400%. ROI is what decision makers use to approve, fund and scale AI projects.

Connecting the two

Model metrics should be chosen because of their business effect. For the fraud model, each missed fraud costs on average $400 and each wrongly blocked payment costs about $15 in lost sales and support calls. With those numbers, the business can calculate which threshold gives the lowest total cost, and the answer may favor recall even though precision falls.

A model with better accuracy isn't automatically the better choice. If it is twice as expensive per prediction, slower, or less trusted by users, the business metrics may favor the simpler model.

Key takeaways

  • The ML pipeline runs: business goal, data collection, EDA, pre-processing, feature engineering, training, hyperparameter tuning, evaluation, deployment, monitoring, and back to re-training. A generative AI pipeline selects and adapts a pre-trained model (prompts, RAG, fine-tuning) instead of training one.
  • Models come from proprietary FM APIs, open-weight pre-trained models (Bedrock, SageMaker JumpStart, Hugging Face), customization of a pre-trained model, or custom training, which is normal for small ML models and rare for foundation models.
  • A managed API (Bedrock, AI services) means no infrastructure and pay per use; a self-hosted API (SageMaker AI endpoint, EC2, EKS, ECS) gives control and any model, at the cost of running it.
  • SageMaker AI covers the ML pipeline (Canvas and Data Wrangler, Feature Store, training and tuning, MLflow, Model Registry, Model Cards, endpoints, Pipelines); Bedrock covers generative AI; Kiro builds the application code with spec-driven development; Quick serves business users with dashboards, research and agents.
  • MLOps brings experiment tracking, versioned and automated pipelines, scalability, technical-debt control, production-readiness checks, drift monitoring and triggered re-training. Model Monitor is closed to new customers.
  • Accuracy misleads on imbalanced data; precision limits false positives; recall limits false negatives; F1 balances both. Business metrics (cost per user, development cost, customer feedback, ROI) decide whether the model is worth it.
