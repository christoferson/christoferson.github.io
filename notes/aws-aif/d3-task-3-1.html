Criteria for choosing an FM

Skill 3.1.1Identify selection criteria to choose FMs (for example, cost, modality, latency, multi-lingual, model size, model complexity, customization, input/output length, prompt caching)

Start from the use case's requirements, rule out models that fail any hard requirement, test the rest on real examples, and choose the cheapest model that meets the quality bar. Amazon Bedrock makes this practical: many models behind one API, a playground for side-by-side comparison, and Bedrock Evaluations for systematic testing.

Cost

Price per input and output token (or per image, per second of video), multiplied by expected volume, plus any customization and hosting costs. Prices differ by more than an order of magnitude between small and large models. For the retailer's assistant at 50,000 questions a day, a model costing ten times more per token is ten times the monthly bill, so it must be clearly better to justify it.

Modality

The types of input and output the model handles: text only; text plus images, documents or video as input; images, video or speech as output; or embeddings. If customers will upload a photo of a broken part and ask "what is this and where do I buy a replacement?", the model must accept images. Choosing a text-only model rules that out.

Latency

How quickly the model responds: time to the first token and total time to finish. A live chat or voice assistant needs fast responses; an overnight report doesn't. Smaller models respond faster; Bedrock also offers latency-optimized inference for some models and the Priority service tier.

Multi-lingual support

Which languages the model reads and writes well. Quality often drops in less common languages, and the same text can take more tokens in some languages, raising cost. A retailer serving Canada needs strong English and French; check each model's documented languages and test in each one.

Model size

The number of parameters. Larger models generally know more and reason better, but cost more per token, respond more slowly and, if self-hosted, need bigger GPUs. Smaller models are fast and cheap and often enough for focused tasks such as classification, extraction and short answers.

Model complexity

How sophisticated the model's architecture and abilities are, for example reasoning models that work through problems step by step before answering, or mixture-of-experts models. More complex models handle harder, multi-step tasks but are slower, use more tokens (reasoning steps count) and cost more. Match complexity to the task: a router that classifies questions doesn't need a reasoning model.

Customization

Whether and how the model can be adapted: fine-tuning, reinforcement fine-tuning or distillation on Bedrock are available only for certain models; open-weight models can be customized freely on SageMaker AI. If you expect to fine-tune, choose a model that supports it, and check how a custom version is hosted and priced.

Input/output length

The context window limits the total tokens of prompt plus response; the maximum output length limits the response. A 300-page manual or a long conversation needs a large context window; generating a full report needs a high output limit. Longer inputs and outputs also cost more and take longer.

Prompt caching

Whether the model supports caching repeated prompt prefixes. If every request starts with the same long instructions, product catalog or tool definitions, caching lets later requests read that prefix from a cache at a lower price and with lower latency. On Bedrock it is supported for selected models (including Anthropic Claude and Amazon Nova models), with a cache lifetime of five minutes by default, reset on each hit. For an assistant that resends a 6,000-token policy document with every question, caching support can tip the choice between two otherwise equal models.

When a scenario gives one dominant requirement, it decides the answer: "accept photos" means modality; "respond in under a second" means latency (a smaller model); "customers in 12 languages" means multi-lingual support; "analyze whole contracts" means context window; "same long instructions on every call" means prompt caching.

Inference parameters

Skill 3.1.2Describe the effect of inference parameters on model responses (for example, temperature, input/output length)

Inference parameters are settings sent with each request that control how the model generates its response, without changing the model. To understand them, recall that at each step the model calculates a probability for every possible next token, then picks one. The parameters shape that choice and when generation stops.

Parameters that control randomness

Temperature

Controls how random the token choice is. At low temperature (near 0), the model strongly favors the most probable tokens, so outputs are focused, consistent and conservative. At high temperature (toward 1, or above on some models), less likely tokens get more chance, so outputs are more varied and creative, but also more likely to wander off topic or contain errors.

Example: asked "Suggest a name for a cordless drill", at temperature 0.1 the model returns "PowerDrive 20V" on nearly every run; at 0.9 it might return "TorqueMaster", "Spin Cycle Pro" or "The Driller Instinct". Use low temperature for factual answers, extraction, classification and code; higher for brainstorming, marketing copy and fiction.

Top P (nucleus sampling)

Limits the choice to the smallest set of most likely tokens whose probabilities add up to P. At top P 0.9, the model chooses only among tokens that together make up 90% of the probability, ignoring the unlikely tail. Lower values make output more focused; higher values allow more variety. It is usually adjusted instead of temperature, not together with it.

Top K

Limits the choice to the K most likely tokens. Top K 1 always picks the single most likely token; top K 250 allows wide variety. Not every model supports it.

Parameters that control length

Maximum output length (max tokens)

The maximum number of tokens the model may generate. It caps cost and latency, and keeps answers short. Set too low, it cuts responses off mid-sentence; the model doesn't plan its answer to fit the limit, it simply stops when the limit is reached. For the retailer's chat answers, 400 tokens might be right; for a generated installation guide, several thousand. Ask for brevity in the prompt as well, rather than relying on the limit alone.

Input length

The size of the prompt: instructions, examples, retrieved documents and history. It isn't a dial in the request, but it is a design parameter with direct effects: longer input gives the model more context (often better answers), but costs more, increases the time to the first token, uses up the context window (leaving less room for the answer), and too much irrelevant input can distract the model. Input plus output must fit within the context window.

Stop sequences

Strings that make the model stop generating when it produces them, for example stopping at "\n\nUser:" so the model doesn't invent the next turn of a conversation, or at the end of a list item.

Inference parameters in an Amazon Bedrock Converse API call (Python, boto3) 
import boto3

bedrock = boto3.client("bedrock-runtime")

response = bedrock.converse(
    modelId="amazon.nova-lite-v1:0",
    messages=[{
        "role": "user",
        "content": [{
            "text": "Drill bit for brick?"
        }],
    }],
    inferenceConfig={
        # about 300 words at most
        "maxTokens": 400,
        # low randomness: factual
        "temperature": 0.2,
        # skip the unlikely 10%
        "topP": 0.9,
        # don't invent the next turn
        "stopSequences": ["Customer:"],
    },
)

Temperature doesn't make the model more accurate or knowledgeable. Lowering it makes answers more consistent, but a model that lacks the facts will consistently give the same wrong answer. Missing knowledge is fixed with RAG, not parameters.

Retrieval Augmented Generation (RAG)

Skill 3.1.3Define Retrieval Augmented Generation (RAG) and describe its business applications (for example, Amazon Bedrock Knowledge Bases)

A foundation model only knows what was in its training data, which is general, stops at a cutoff date and excludes your company's private information. Asked about your products, policies or customers, it either says it doesn't know or, worse, makes something up. RAG fixes this by retrieving relevant information from your own data at the moment of the question and adding it to the prompt, so the model answers from those facts. The model itself isn't changed.

How RAG works

Two phases: preparing the data once (and whenever it changes), then retrieving for each question.

  1. IngestCollect the source documents: product manuals, how-to guides, policy pages, FAQs.
  2. Parse and chunkExtract the text (and tables or images) and split it into passages of a few hundred tokens.
  3. Embed and storeConvert each chunk into an embedding vector with an embedding model and store it, with its text and metadata (product, date, source), in a vector database.
  4. RetrieveWhen a question arrives, embed it with the same model and search the vector database for the most similar chunks, optionally filtering by metadata and reranking the results.
  5. AugmentAdd the retrieved chunks to the prompt with instructions: "Answer using only the information below, and cite the source."
  6. GenerateThe foundation model writes an answer grounded in the retrieved text, with citations to the source documents.

For the retailer: a customer asks "Can I use the X200 drill on concrete?" The system retrieves the X200 manual's section on masonry drilling and the product page's specifications, and the model answers "Yes, in hammer mode with a masonry bit up to 13 mm (X200 manual, page 14)."

Why RAG is used

  • Accuracy and fewer hallucinations: answers are based on real documents.
  • Current information: update the documents, and answers change; no retraining.
  • Private data: uses your information without putting it into the model's weights.
  • Traceability: citations let users check sources, which builds trust.
  • Access control: retrieval can be filtered so users only get documents they may see.
  • Cost: far cheaper and faster than fine-tuning for adding knowledge.

Amazon Bedrock Knowledge Bases

What it does

A fully managed RAG capability. You connect data sources and it handles the whole pipeline: connecting to the data (Amazon S3, SharePoint, Confluence, Salesforce, web crawlers and others), parsing (including tables and figures with advanced parsing options), chunking (default, fixed-size, hierarchical, semantic or none), embedding, storing in a vector store, keeping the index in sync with the data, retrieving, and generating answers with citations.

  • Retrieve API: returns the relevant chunks and their relevance scores, for your application to use as it likes.
  • RetrieveAndGenerate API: retrieves and has a model write the cited answer in one call, keeping session context for follow-up questions.
  • Vector store choice: a managed knowledge base where Bedrock runs the storage and search, or your own vector store, such as OpenSearch Serverless, Aurora PostgreSQL, Neptune Analytics, Amazon S3 Vectors, or partners such as Pinecone, Redis Enterprise Cloud and MongoDB Atlas.
  • Beyond documents: structured data stores (natural-language questions converted to SQL over databases such as Amazon Redshift) and GraphRAG with Amazon Neptune Analytics, which links related entities across documents.
  • Integration: Bedrock Guardrails apply to the question and the generated answer; Bedrock Evaluations can measure retrieval and answer quality.

Business applications

Customer support assistants

Answering product, order and policy questions from manuals, help-center articles and policies, for customers or for support staff.

Employee knowledge assistants

HR policies, IT how-tos, engineering standards, sales playbooks: one place to ask instead of searching intranets.

Legal, compliance and research

Searching and summarizing contracts, regulations and research papers, with citations a professional can verify.

Healthcare and financial services

Clinicians querying treatment guidelines; advisers querying product documentation and research, with access limited by role.

"The model doesn't know our internal or recent information", "reduce hallucinations about company data", "answers must cite sources", "data changes often" all point to RAG with Bedrock Knowledge Bases, not to fine-tuning.

Vector databases on AWS

Skill 3.1.4Identify AWS services that help store embeddings within vector databases (for example, Amazon OpenSearch Service, Amazon Aurora, Amazon Neptune, Amazon RDS for PostgreSQL)

A vector database stores embeddings and finds the stored vectors most similar to a query vector, quickly, even among millions or billions. Exact comparison against every vector would be too slow, so they use approximate nearest neighbor (ANN) indexes such as HNSW, trading a tiny loss in precision for large speed gains. Most AWS options are existing databases that added vector search, so the choice often follows what you already use.

Amazon OpenSearch Service

A managed search and analytics service with a vector engine (k-NN search), available as provisioned domains or OpenSearch Serverless. Its strength is combining vector search with keyword (full-text) search, called hybrid search, plus filtering, at high scale and low latency. It is the default vector store when you let Bedrock Knowledge Bases create one for you (OpenSearch Serverless).

Choose it forLarge-scale semantic and hybrid search, low latency at high throughput, teams already using OpenSearch for search or logs.

Amazon Aurora (PostgreSQL-Compatible Edition)

Aurora PostgreSQL supports the open source pgvector extension, which adds a vector data type and similarity search to SQL. Embeddings sit in the same tables as your business data, so one query can combine similarity with ordinary filters and joins ("products similar to this one that are in stock in the customer's region"). Aurora PostgreSQL is a supported Bedrock Knowledge Bases vector store.

Choose it forApplications already on relational data that want vectors alongside it, with SQL and transactions.

Amazon RDS for PostgreSQL

Also supports pgvector, giving the same SQL-plus-vectors approach on standard managed PostgreSQL. A good choice for smaller workloads or teams already running RDS.

Amazon Neptune

A managed graph database. Neptune Analytics stores vector embeddings alongside graph data, combining similarity search with relationships between entities (which products are compatible with which, which customers bought what). It powers GraphRAG in Bedrock Knowledge Bases, which retrieves not just similar passages but connected facts across documents.

Choose it forData where relationships matter: knowledge graphs, recommendations, fraud rings, GraphRAG.

Other AWS vector options Extra

Amazon S3 Vectors

Vector storage and querying built into Amazon S3, with vector buckets and indexes holding up to billions of vectors at very low cost, with sub-second query latency. Suited to large vector sets queried less often; a supported Bedrock Knowledge Bases store.

Amazon DocumentDB, Amazon MemoryDB and Amazon ElastiCache

DocumentDB (MongoDB-compatible) supports vector search on JSON documents. MemoryDB offers in-memory vector search with very low latency, used for semantic caching (reusing answers to similar questions) and real-time recommendations.

"Hybrid keyword and semantic search at scale" points to OpenSearch Service. "Keep vectors with existing relational data, use SQL" points to Aurora or RDS for PostgreSQL with pgvector. "Relationships between entities, knowledge graph, GraphRAG" points to Neptune. "Lowest-cost storage for huge vector sets" points to S3 Vectors.

Cost of customization approaches

Skill 3.1.5Explain the cost tradeoffs of various approaches to FM customization (for example, pre-training, fine-tuning, in-context learning, RAG, model distillation)

There are five ways to make a foundation model fit your needs, from cheapest to most expensive upfront. The rule: start at the top and move down only when the cheaper approach can't meet the requirement. Costs come in two kinds: upfront (data, training, setup) and ongoing (per-request inference, hosting, maintenance), and the approaches trade one against the other.

In-context learning (prompt engineering)

Guide the model with instructions and examples in the prompt (zero-shot or few-shot). The model doesn't change.

  • Upfront cost: very low; hours or days of prompt writing and testing.
  • Ongoing cost: examples and long instructions add tokens to every request; prompt caching reduces this.
  • Good for: formatting, tone, task instructions, simple classification. Limits: can't add much knowledge; constrained by the context window.

Retrieval Augmented Generation (RAG)

Retrieve relevant data at query time and add it to the prompt.

  • Upfront cost: moderate: building the knowledge base, embedding documents, setting up a vector store.
  • Ongoing cost: vector database running costs, embedding new content, and the retrieved text added to every prompt as input tokens.
  • Good for: adding private, changing or large knowledge, with citations. Limits: doesn't change the model's style or skills; quality depends on retrieval.

Fine-tuning

Further train a pre-trained model on labeled examples of your task, changing its weights.

  • Upfront cost: higher: preparing and labeling hundreds to thousands of high-quality examples, training compute (on Bedrock, charged per training token times the number of passes), and experimentation.
  • Ongoing cost: storing the custom model (a monthly fee) and hosting it, often with Provisioned Throughput billed by the hour, though some models support on-demand deployment; retraining when the base model or data changes. Shorter prompts can partly offset this.
  • Good for: consistent specialized style, format or behavior; domain terminology; tasks prompting can't get right. Limits: knowledge is frozen at training; poor for frequently changing facts.

Model distillation

Use a large "teacher" model to generate responses, and train a smaller "student" model on them, so the student reproduces the teacher's quality on your specific use case. Amazon Bedrock Model Distillation automates this from your prompts.

  • Upfront cost: teacher inference to create training data, plus training the student.
  • Ongoing cost: much lower inference cost and latency, because every request now runs on the small model.
  • Good for: high-volume applications where a large model's quality is needed but its cost and latency aren't affordable.

Pre-training (and continued pre-training)

Pre-training from scratch builds a new foundation model on a massive data set: by far the most expensive, needing huge curated data, thousands of accelerators for weeks or months and a specialist research team. Continued pre-training is cheaper: it keeps training an existing model on large amounts of unlabeled domain text (medical literature, legal archives) so it absorbs the domain's language and knowledge.

  • Upfront cost: continued pre-training high; full pre-training extreme (millions of dollars or more).
  • Ongoing cost: hosting your own model at scale.
  • Good for: organizations with unique data at enormous scale and needs no existing model can meet.

Choosing the approach

The assistant must answer from 3,000 product manuals that change weekly

RAG: large, changing knowledge, citations needed.

Every product description must follow the brand's exact style and structure

Try prompt engineering with examples first; fine-tune if results are still inconsistent at scale.

A large model classifies tickets well, but 5 million tickets a month make it too expensive

Distillation into a smaller model.

A pharmaceutical company wants a model fluent in its decades of research literature

Continued pre-training on the domain corpus, possibly combined with RAG.

Fine-tuning is not the way to keep a model's facts up to date. Every change would need retraining. Use RAG for knowledge, and fine-tuning for behavior and style.

AI agents

Skill 3.1.6Define the role of AI agents and describe AI agents' business applications

An AI agent is software that uses a foundation model to pursue a goal on its own: it breaks the goal into steps, chooses and calls tools (APIs, databases, knowledge bases, code), observes results, and adjusts until it is done or needs a person. Where a RAG assistant answers questions, an agent gets things done across systems.

The role agents play in an application

Orchestrating multi-step tasks

The agent decides the sequence of steps at run time, instead of a developer coding every path. Asked "my order arrived with a missing part", the retailer's agent finds the order, checks which part is missing from the packing list, checks stock, sends the part and confirms, choosing each step from what it found in the previous one.

Connecting the model to systems through tools

The foundation model can't access anything by itself; the agent gives it tools to read and change data in business systems (order management, CRM, ticketing, calendars), often through MCP and Amazon Bedrock AgentCore Gateway.

Keeping context and memory

The agent tracks what has happened in the task and remembers relevant facts across sessions (AgentCore Memory), so customers don't repeat themselves.

Acting within limits

The agent operates within permissions and business rules (refunds up to $100, no account deletions), hands over to a person when needed, and logs every action. Enforcing these limits outside the model, for example with Policy in AgentCore, keeps it safe even if the model is tricked.

Business applications

Customer service

Resolving requests end to end: returns, refunds, rebooking travel, changing a subscription, troubleshooting a device, with handover to staff for exceptions.

IT and operations

Investigating alerts by reading logs and metrics, suggesting or applying fixes, resetting access, provisioning resources on request.

Software development

Planning and writing features from specifications, writing tests, fixing bugs, and modernizing legacy code (Kiro, AWS Transform).

Finance and back office

Matching invoices to purchase orders and receipts, flagging mismatches, preparing expense reports, reconciling accounts.

Sales and marketing

Researching prospects across sources, drafting personalized outreach, updating the CRM, scheduling meetings.

Research and analysis

Searching many sources, extracting and comparing information, and writing cited reports (Amazon Quick Research).

When an agent isn't the right design

If the steps are always the same, a fixed workflow (AWS Step Functions, Bedrock Flows) is cheaper, faster, more predictable and easier to audit. If the task is answering questions from documents, RAG is enough. Agents earn their extra cost and risk when the path depends on what is found along the way.

"Complete multi-step tasks", "take actions in other systems", "call APIs", "decide the next step" point to an AI agent. "Answer questions from documents" points to RAG. "The same fixed sequence every time" points to a workflow.

Key takeaways

  • Choose FMs on cost, modality, latency, languages, size, complexity, customization support, context window and output length, and prompt caching support; pick the cheapest model that passes your own tests.
  • Temperature (and top P, top K) controls randomness: low for factual and consistent, high for creative. Max tokens caps output length, cost and latency but can truncate. Input length adds context but costs tokens and time.
  • RAG retrieves relevant chunks from your data at query time and grounds answers with citations: current, private and traceable without retraining. Bedrock Knowledge Bases manages ingestion, chunking, embedding, storage, retrieval and generation.
  • Vector stores: OpenSearch Service (hybrid search at scale), Aurora and RDS for PostgreSQL with pgvector (vectors with relational data), Neptune Analytics (graphs, GraphRAG), plus S3 Vectors, DocumentDB and MemoryDB.
  • Customization cost rises from in-context learning to RAG, fine-tuning, distillation and pre-training. Use RAG for knowledge, fine-tuning for behavior, distillation for cheaper inference at scale.
  • Agents plan and act through tools, memory and limits, to complete tasks across systems; use them when the path varies, and workflows or RAG when it doesn't.
