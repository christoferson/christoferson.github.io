Foundational GenAI concepts

Skill 2.1.1Define foundational GenAI concepts (for example, tokens, chunking, embeddings, vectors, prompt engineering, transformer-based large language models [LLMs], foundation models [FMs], multi-modal models, diffusion models)

The concepts build on each other. Text is split into tokens; tokens and passages are turned into embeddings, which are vectors; a transformer processes those vectors to predict the next token; a transformer trained on enormous data is a foundation model; prompt engineering is how you instruct it. Chunking prepares your own documents so the model can use them, and multimodal and diffusion models extend generation beyond text.

How models read text

Tokens

A token is the unit of text a model reads and writes: a whole word, part of a word, a punctuation mark or a space. "Unbelievable!" might be three tokens: "Un", "believ", "able!". Common words are usually one token; rare words, names, numbers and code split into several. As a rough guide for English, a token is about four characters or three-quarters of a word, so 1,000 tokens is about 750 words. Other languages often need more tokens for the same meaning.

Tokens matter for three reasons. Models are priced per token (input and output separately). Each model has a context window, the maximum number of tokens it can consider at once (prompt plus response), ranging from a few thousand to over a million. And models generate one token at a time, so longer answers take longer.

Chunking

Chunking is splitting long documents into smaller passages (chunks) before they are embedded and stored for retrieval. A 200-page manual can't be given to the model whole on every question, and searching it as one block would be useless. Split into chunks of a few hundred tokens, the system can find and supply only the few passages relevant to each question.

Chunk size is a trade-off. Too small, and a chunk loses context ("it must be replaced every 6 months" without saying what "it" is). Too large, and chunks mix several topics, match questions poorly and waste tokens. Common strategies: fixed-size chunks with some overlap so sentences at the edges aren't cut off; hierarchical chunks (small child chunks for precise matching, returning their larger parent for context); semantic chunking that splits where the meaning changes. Amazon Bedrock Knowledge Bases supports all three, with a default of about 300 tokens.

Vectors

A vector is an ordered list of numbers, such as [0.12, −0.48, 0.91, …]. Each number is one dimension; embedding vectors typically have hundreds to a few thousand dimensions. Vectors are how AI represents things numerically, so they can be compared mathematically: two vectors pointing in similar directions represent similar things. Similarity is measured with methods such as cosine similarity or Euclidean distance.

Embeddings

An embedding is a vector produced by an embedding model to represent the meaning of a piece of content (a word, sentence, document, image). Content with similar meaning gets similar vectors, even with no words in common: "How do I reset my password?" and "I forgot my login credentials" end up close together, while "password" in a security policy and "reset" in a tennis article don't.

Embeddings power semantic search (finding passages by meaning, not keywords), RAG (finding the chunks to give a model), recommendations (items similar to ones you liked), clustering and duplicate detection. They are stored and searched in vector databases: on AWS, Amazon OpenSearch Service, Amazon Aurora and RDS for PostgreSQL with pgvector, Amazon Neptune Analytics, Amazon DocumentDB, Amazon MemoryDB and Amazon S3 Vectors. Embedding models on Bedrock include Amazon Titan Text Embeddings, Amazon Nova multimodal embeddings and Cohere Embed.

An embedding model doesn't generate text. It turns content into vectors for search and comparison. A RAG system uses two models: an embedding model to find relevant chunks, and a text-generation model to write the answer.

How models generate

Transformer-based LLMs

The transformer is the neural network architecture behind nearly all modern LLMs (the "T" in GPT). Its key mechanism is self-attention: when processing each token, the model weighs how relevant every other token in the input is to it. In "The trophy didn't fit in the suitcase because it was too big", attention lets the model connect "it" to "trophy". Earlier architectures read text one word at a time and struggled with long-range connections; transformers look at the whole sequence at once, which also lets training run in parallel on GPUs, which made training on internet-scale data feasible.

An LLM generates text by repeatedly predicting the most likely next token given everything so far, adding it, and predicting again. Settings called inference parameters (such as temperature) control how adventurous that choice is; Task 3.1 covers them.

Foundation models (FMs)

A foundation model is a very large model pre-trained on broad, mostly unlabeled data (text, code, images) at huge scale, which can then be adapted to a wide range of tasks. The name reflects its role: a general foundation others build on, rather than a model trained for one job. One FM can summarize, classify, translate, answer questions, extract data and write code, steered by prompts, retrieval or fine-tuning.

LLMs are text FMs. Others include multimodal FMs, image-generation FMs and embedding FMs. On Amazon Bedrock, FMs come from Amazon (Amazon Nova, Titan) and providers such as Anthropic, Meta, Mistral AI, Cohere, AI21 Labs, Stability AI, DeepSeek, Qwen and OpenAI.

Multimodal models

A multimodal model can take in or produce more than one type of data (modality): text, images, audio, video, documents. It can describe a photo, answer questions about a chart, read a scanned invoice, generate an image from a description, or transcribe and summarize a video. They work by converting each modality into the same kind of internal representation, so the model can reason across them.

Examples: Amazon Nova Lite and Pro accept text, images and video and output text; Amazon Nova Canvas generates images and Nova Reel generates video; Amazon Nova Sonic handles real-time speech conversations.

Diffusion models

Diffusion models are the main technique for generating images (and increasingly video and audio). In training, the model learns to reverse a process of adding noise: real images are progressively blurred with random noise until nothing is left, and the model learns to remove the noise step by step. To generate, it starts from pure random noise and denoises it over many steps, guided by a text prompt, until an image matching the description emerges.

Uses: generating product images and marketing visuals, editing images (inpainting to replace part of an image, outpainting to extend it), changing backgrounds, creating design variations. Examples on Bedrock: Stability AI's Stable Diffusion models and Amazon Nova Canvas.

"Generates images from text by removing noise" means a diffusion model. "Self-attention" or "processes the whole sequence in parallel" means a transformer. "Accepts images and text together" means multimodal. "Represents meaning as numbers for similarity search" means embeddings.

How you instruct a model

Prompt engineering

A prompt is the input you give a foundation model: the instruction, plus any context, examples and data. Prompt engineering is the practice of designing prompts to get accurate, relevant, consistently formatted results, without changing the model itself. It is the cheapest and fastest way to adapt an FM, and always the first thing to try.

A good prompt typically states the role or task, gives the needed context, provides the input, specifies the output format and sets constraints ("answer only from the policy below; if the answer isn't there, say so"). Techniques such as zero-shot, few-shot and chain-of-thought prompting, and the risks of prompt injection, are covered in Task 3.2.

GenAI use cases

Skill 2.1.2Identify potential use cases for GenAI models (for example, image, video, and audio generation; summarization; AI assistants; translation; code generation; customer service agents; search; recommendation engines)

Generative AI fits tasks that involve creating, transforming or understanding unstructured content, where some variation in output is acceptable and a person or a check can catch errors.

Image, video and audio generation

Creating marketing images and product shots in different settings, concept art, video clips for social media, synthetic voices for narration, background music. A furniture retailer generates lifestyle images of a sofa in different rooms instead of staging photo shoots. Models: Amazon Nova Canvas and Stability AI (images), Amazon Nova Reel (video), Amazon Polly generative voices (speech).

Summarization

Condensing long content into the key points: call transcripts into case notes, contracts into key terms, research papers into abstracts, a week of support tickets into the top five issues, a meeting into decisions and actions. Valuable wherever people spend time reading.

AI assistants

Conversational helpers that answer questions, draft content and complete tasks for employees or customers: an HR assistant answering policy questions from the handbook, a sales assistant drafting follow-up emails from CRM notes, a research assistant writing cited reports. On AWS, Amazon Quick provides assistants for business users, and Bedrock is used to build custom ones.

Translation

Translating text while adapting tone, idioms and formality for the audience, which LLMs often do more naturally than word-for-word translation. Localizing marketing campaigns, translating support conversations, adapting product descriptions for regional markets. For high-volume, consistent translation, Amazon Translate remains the specialized option.

Code generation

Writing code from a description, completing code as you type, explaining unfamiliar code, writing tests and documentation, finding bugs, converting code between languages and modernizing legacy applications. Kiro brings this into a spec-driven development environment; AWS Transform applies agentic AI to large migrations such as mainframe and .NET modernization.

Customer service agents

Agents that resolve customer requests end to end: understanding the problem, looking up orders or accounts, applying policy, taking action (refund, rebooking, replacement) and handing over to a person when needed. They go beyond assistants that only answer, because they act through tools.

Search

Search by meaning rather than keywords, with a direct answer instead of a list of links. An engineer asks "what torque for the M8 bolts on the pump housing?" and gets the answer with a citation to the manual page. Built with embeddings, vector search and RAG; on AWS, Bedrock Knowledge Bases and Amazon OpenSearch Service.

Recommendation engines

Generative AI improves recommendations by understanding item descriptions and user requests in natural language ("a lightweight tent for two that packs small"), by generating personalized explanations ("because you liked…"), and by writing personalized marketing messages. Embeddings let the system match items by meaning. Traditional recommendation models such as Amazon Personalize still handle the core "what will this user click" prediction at scale.

More use cases Extra
  • Information extraction: pulling fields from varied documents (invoices, emails, forms) into structured data.
  • Content creation: product descriptions, marketing copy, reports, personalized emails.
  • Synthetic data: generating realistic test data or training examples where real data is scarce or sensitive.
  • Classification without training data: asking a model to categorize tickets or reviews with only instructions and a few examples.

The foundation model lifecycle

Skill 2.1.3Describe the FM lifecycle (for example, data selection, model selection, pre-training, fine-tuning, evaluation, deployment, feedback)

The lifecycle covers both sides: what the model provider does to create an FM, and what a business does to put one to use. Most organizations skip pre-training entirely and start at model selection.

1. Data selection

Choosing and preparing the data the model will learn from. For pre-training, that is trillions of tokens of text, code and images, filtered for quality, deduplicated, screened for harmful and personal content, and checked for licensing rights. For a business fine-tuning a model, it is a curated set of examples of the task. Data quality, diversity and legal right to use the data decide what the model can do, its biases and the organization's legal risk.

2. Model selection

Choosing the architecture and size (for a provider), or choosing an existing FM (for a business). Businesses compare candidate models on task quality, modality, context window, latency, cost per token, languages, customization options, license and compliance. Picking the smallest model that does the job well keeps cost and latency down.

3. Pre-training

Training the model from scratch on the broad data set, using self-supervised learning (predicting the next token or masked content), on thousands of GPUs or AI chips for weeks or months. This is where the model gains general knowledge, language ability and reasoning. It is extremely expensive, which is why few organizations do it.

4. Fine-tuning

Further training of a pre-trained model on a smaller, targeted data set to specialize it: labeled examples of a task (instruction tuning), domain text (continued pre-training), or human preference rankings (RLHF), which make it more helpful and safer. It changes the model's weights, unlike prompt engineering and RAG, which don't. Task 3.3 covers the methods.

5. Evaluation

Measuring whether the model is good enough for the use: accuracy, relevance and faithfulness, plus safety (toxicity, bias, refusals), robustness and cost and latency. Methods include benchmark data sets, automatic metrics, human review and LLM-as-a-judge. Amazon Bedrock Evaluations supports all of these. Task 3.4 covers them.

6. Deployment

Making the model available to applications with the right safeguards: through a managed API (Bedrock) or a self-hosted endpoint (SageMaker AI), with guardrails, access control, logging, scaling and cost controls. For agents, deployment includes the runtime, tool access and identity (AgentCore).

7. Feedback

Collecting signals from real use and feeding them back: user ratings, corrections, escalations, monitoring of quality and safety, new failure cases. Feedback drives improvements to prompts, retrieved documents, guardrails and, eventually, a new round of fine-tuning, closing the loop.

The order matters in ordering questions: data selection, model selection, pre-training, fine-tuning, evaluation, deployment, feedback. Pre-training comes before fine-tuning; evaluation comes before deployment, and continues after it.

Token-based pricing

Skill 2.1.4Describe the token-based pricing model and its effect on cost and performance for inference

Most foundation models are priced per token processed, with input tokens (everything you send: instructions, context, conversation history, retrieved documents, tool definitions) and output tokens (everything the model generates) priced separately. Output tokens usually cost several times more than input tokens, because each one requires a full pass through the model. Prices are quoted per thousand or per million tokens and vary greatly between models: a small model can be tens of times cheaper than a large one.

How the bill adds up

A support assistant, using illustrative prices of $0.003 per 1,000 input tokens and $0.015 per 1,000 output tokens:

Notice where the cost comes from: input is ten times the size of output, and most of the input is context, not the user's question. Halving the retrieved documents or trimming the history saves more than shortening answers.

Effect on cost

  • Prompt length: every token of instructions, examples, history and retrieved text is paid on every request. Long few-shot examples and full conversation histories multiply cost.
  • Response length: verbose answers cost more at the higher output rate; ask for concise answers and set a maximum output length.
  • Model choice: the biggest lever. A smaller model that is good enough can cut cost by an order of magnitude.
  • Agents: an agent makes many model calls per task (plan, call tool, read result, decide), each resending context, so one agentic task can cost many times a single chat answer.
  • Images, audio and video are also converted into tokens, often many per item.

Effect on performance

  • Latency grows with output: tokens are generated one at a time, so a 1,000-token answer takes roughly twice as long as a 500-token one. Streaming the response shows text as it is generated, improving perceived speed.
  • Latency grows with input: the model must process the whole prompt before the first output token appears (time to first token).
  • Context window limits: prompt plus answer must fit within the model's maximum tokens; overflowing it truncates history or fails the request.
  • Quotas: services limit tokens per minute, so token-heavy prompts reach throughput limits sooner.

Ways to reduce token cost on Amazon Bedrock

Prompt caching

When many requests start with the same long prefix (system instructions, a large document, tool definitions), Bedrock can cache it. Later requests that reuse the prefix within the cache lifetime (five minutes by default, reset on each hit; longer on some models) read it from the cache at a lower price and with lower latency. Cache writes can cost slightly more than normal input, so caching pays off when a prefix is reused often.

Batch inference and service tiers

Batch inference processes large sets of prompts asynchronously at about 50% less than on-demand prices for supported models. For on-demand calls, the Flex tier is cheaper for work that can tolerate longer processing; Priority costs more for the fastest responses; Standard is the default.

Provisioned Throughput

Instead of paying per token, you buy dedicated capacity (model units) by the hour, with discounts for one- or six-month commitments. It suits high, steady volume and is the way to run many custom (fine-tuned) models.

Design choices

Retrieve fewer, more relevant chunks; summarize long conversation histories; use smaller models for simple steps (routing, classification) and larger ones only where needed; distill a large model into a smaller one; limit maximum output tokens.

Token pricing means cost scales with usage, not with the number of users or servers. A pilot with ten users can look cheap and become expensive at ten thousand; always estimate tokens per interaction times expected volume.

Context engineering

Skill 2.1.5Describe the role of context engineering in FM applications

A foundation model knows only two things when it answers: what it learned in training, and what is in its context window for this request. Context engineering is the discipline of deciding what information enters the model's context window, when, and in what form. Prompt engineering focuses on how the instructions are worded; context engineering manages everything else the model sees, so it gets the right data at the right time without overflowing the window or wasting tokens. (This definition follows the Strands Agents documentation, AWS's open-source agent toolkit.)

It has become central because modern applications, especially agents, assemble their context from many sources on every call, and the quality of the answer depends more on that assembly than on the wording of the instructions.

What goes into the context

The components

  • System instructions: role, rules, tone, output format.
  • The user's request and relevant conversation history.
  • Retrieved knowledge: document chunks from a knowledge base (RAG), database records, search results.
  • Memory: facts and preferences from earlier sessions ("this customer prefers email; they own model X200").
  • Tool definitions (what the model can call) and tool results (what came back).
  • State: the current step of a task, plans and intermediate results.

Why it matters

  • Accuracy and grounding: missing context leads the model to guess, which causes hallucinations; the right retrieved facts let it answer correctly and cite sources.
  • Focus: too much irrelevant context dilutes the important parts and can make answers worse, not better.
  • Cost and latency: every token in the context is paid for and processed on every call.
  • Limits: long agent sessions accumulate history and tool results until they overflow the context window.
  • Security: only data the user is allowed to see should enter the context, and untrusted content (web pages, emails) can carry injected instructions.

Techniques

Select

Include only what is relevant to this step: retrieve the top few chunks rather than whole documents, load only the tools the task needs, pull only the memories that match the request.

Compress

Shrink what must stay: keep a sliding window of recent messages, summarize older turns, trim long tool outputs to the useful fields.

Isolate

Give sub-tasks their own context: a research sub-agent reads twenty web pages in its own context window and returns a one-paragraph summary to the main agent, instead of filling the main context with all twenty.

Externalize

Store large data outside the context and keep a reference: save a long report to a file or memory store and give the model its location and a summary, retrieving details only when needed.

Structure and order

Put stable content (instructions, tool definitions, reference documents) first so it can be cached, label sections clearly, and place the user's question where the model will attend to it.

On AWS, Bedrock Knowledge Bases handles retrieval, AgentCore Memory stores short- and long-term memory, AgentCore Gateway with semantic tool selection exposes only relevant tools, and prompt caching makes stable prefixes cheaper.

If a question says the model's instructions are fine but it lacks the right information, keeps forgetting earlier facts, or receives too much irrelevant data, the answer is about context (retrieval, memory, summarization), not about rewording the prompt.

Agentic AI concepts

Skill 2.1.6Define foundational agentic AI concepts (for example, multi-agent system patterns for complex AI applications, Model Context Protocol [MCP] and its role in connecting agents to external systems, multi-agent communication patterns, memory management, tool usage, and workflow orchestration)

An AI agent uses a foundation model to reason about a goal, decide on actions, carry them out through tools, observe the results and repeat until done. The Strands Agents documentation describes the loop simply: invoke the model; if it wants to use a tool, run the tool; invoke the model again with the result; repeat until the model produces a final response.

  1. GoalA customer writes: "I was charged twice for my March invoice."
  2. PlanFind the account, check March payments, refund a duplicate if there is one, confirm to the customer.
  3. Tool callLook up the customer's account (get_account).Account 88213, monthly plan $49.
  4. Tool callList March payments (list_payments).Two payments of $49 on March 3, two minutes apart.
  5. Tool callRefund the second payment (issue_refund, allowed up to $100).Refund R-5521 issued.
  6. Reply"You were charged twice on March 3. I've refunded $49 (reference R-5521); it will reach your card in 3 to 5 days."

The building blocks behind that run are tools, memory, orchestration and, as systems grow, multiple agents and the protocols that connect them.

Tool usage

How agents use tools

A tool is any function the agent can call: an API, a database query, a search, a calculator, a code sandbox, a web browser, another agent. Each tool is described to the model with a name, a description of what it does and when to use it, and an input schema listing its parameters. The model doesn't run the tool itself: it outputs a request ("call list_payments with account 88213, month March"), the application or agent runtime executes it, and the result is added to the context for the next step.

Tool design decides agent quality and safety. Clear descriptions help the model choose correctly; narrow tools (refund up to $100) are safer than broad ones (run any SQL); each tool should run with least-privilege permissions; actions with real-world effects (payments, deletions, emails) may need human approval.

On AWSAgentCore Gateway turns existing APIs and Lambda functions into tools; AgentCore Code Interpreter runs code in an isolated sandbox; AgentCore Browser lets agents use websites; in Strands Agents, any Python function becomes a tool with a decorator.

Model Context Protocol (MCP)

What MCP is

MCP is an open protocol that standardizes how applications provide context to language models: how an AI application discovers and uses external tools and data. Before MCP, every agent framework needed a custom integration for every system (CRM, ticketing, databases, file stores), so integrations multiplied. With MCP, a system is wrapped once as an MCP server, and any MCP-compatible agent or application can use it. It is often compared to a USB port for AI: one standard plug instead of a different cable for every device.

How MCP works

  • Host: the AI application the user works in (an agent, an IDE such as Kiro, a chat app such as Amazon Quick).
  • Client: a component inside the host that keeps a connection to one MCP server.
  • Server: a program that exposes capabilities of an external system.

Servers offer three kinds of capability: tools (actions the model can call, such as "create ticket"), resources (data the application can read, such as a file or record) and prompts (reusable prompt templates). Messages use JSON-RPC; local servers communicate over standard input/output (stdio) and remote servers over HTTP, typically secured with OAuth.

An MCP server describes each of its tools with the name, description and input schema the model needs:

A tool listed by an MCP server 
{
  // what the model calls
  "name": "create_ticket",
  // tells the model when to use it
  "description": "Open a support ticket for a customer issue. Use when the customer reports a fault that needs an engineer.",
  // the parameters the model must supply
  "inputSchema": {
    "type": "object",
    "properties": {
      "customer_id": { "type": "string" },
      "summary": { "type": "string" },
      "priority": {
        "type": "string",
        "enum": ["low", "normal", "high"]
      }
    },
    "required": ["customer_id", "summary"]
  }
}

On AWSAgentCore Gateway converts APIs, OpenAPI specifications and Lambda functions into MCP tools and can front existing MCP servers; AgentCore Runtime can host MCP servers; Strands Agents, Kiro and Amazon Quick can all connect to MCP servers; AWS publishes open-source MCP servers for its own services and documentation.

"Standard way to connect agents to external tools and data sources" means MCP. "Standard for agents to discover and talk to other agents" means the Agent-to-Agent (A2A) protocol. MCP connects an agent to tools; A2A connects agents to each other.

Memory management

Short-term memory

Memory within one session: the messages, tool calls and results of the current conversation or task, so the agent remembers that the customer already gave their account number three turns ago. It is usually held in the context window, so it must be managed (trimmed or summarized) as sessions grow.

Long-term memory

Memory that persists across sessions: facts ("owns two vehicles"), user preferences ("prefers short answers", "vegetarian"), summaries of past interactions, and episodic memory of past experiences and what was learned from them ("last time, the refund tool failed for annual plans; escalate those"). It is extracted from conversations, stored outside the model and retrieved into the context when relevant, often using embeddings.

On AWSAgentCore Memory provides both: short-term memory for events within a session, and long-term memory with built-in strategies (semantic facts, user preferences, summaries, episodic) that extract and consolidate insights automatically.

Managing memory well

Decide what is worth remembering, keep memories separate per user (one customer's details must never surface for another), set retention periods and allow deletion for privacy, and retrieve only relevant memories so they don't crowd the context.

Workflow orchestration

Orchestration is how the steps of a multi-step task are coordinated. The key distinction is who decides the path:

Deterministic workflows

The developer defines the steps and their order in advance; the model performs individual steps. Predictable, testable and auditable. AWS Prescriptive Guidance describes common patterns:

  • Prompt chaining: a sequence of model calls, each building on the previous output (extract facts, then draft, then check tone).
  • Routing: a classifier sends each request to the right specialized prompt, model or agent (billing questions to the billing agent).
  • Parallelization: independent subtasks run at the same time and the results are combined (review a contract for legal, financial and privacy issues simultaneously).
  • Evaluator and reflect-refine loop: one model generates, another critiques, and the output is revised until it passes.

On AWSAWS Step Functions, Amazon Bedrock Flows, and the Workflow pattern in Strands Agents.

Agent-driven orchestration

The model decides the next step at run time based on what it observes, as in the billing example above. Flexible enough for problems whose steps can't be known in advance, but less predictable, so it needs limits on steps, tools, spending and time, and checkpoints for human approval. Most production systems mix the two: a deterministic workflow with agentic steps inside it.

Multi-agent system patterns

Complex applications often split work across several specialized agents, each with focused instructions and tools, rather than one agent that does everything. Smaller, specialized agents are easier to build, test and secure, and can use different models. Common patterns:

Supervisor (orchestrator-workers)

A supervisor agent receives the request, breaks it into subtasks, delegates each to a specialist agent (researcher, analyst, writer), and combines their results. The supervisor stays in control. A simple version, agents as tools, exposes each specialist to the supervisor as if it were a tool; Strands Agents calls this the simplest starting point.

Hierarchical

Supervisors of supervisors: a top-level agent delegates to team-lead agents, which delegate to workers. Useful for large tasks with natural sub-teams, such as a due-diligence review split into legal, financial and technical teams.

Swarm (peer collaboration)

Agents work as a team of peers without a central controller, handing tasks to whichever agent is best suited and sharing working memory. Good for open-ended problems that benefit from several perspectives, but needs limits to stop endless hand-offs.

Graph and workflow

The developer defines which agents exist and how work can flow between them (as a graph of nodes and edges); a graph lets an agent choose which path to take next, while a workflow runs a fixed sequence of agent tasks, with independent ones in parallel.

Multi-agent communication patterns

Centralized (through a coordinator)

All messages go through the supervisor, which passes each agent what it needs and collects results. Easy to monitor and control; the coordinator can become a bottleneck.

Direct hand-off and peer-to-peer

Agents pass the task and context directly to each other ("this is a refund question; handing to the refunds agent"). Standard protocols such as Agent-to-Agent (A2A) let agents built on different frameworks discover each other through published agent cards describing their capabilities, and exchange tasks.

Shared memory (blackboard)

Agents read and write a shared store of facts and results instead of messaging each other. Each agent contributes when it has something to add. AWS guidance lists stores such as Amazon DynamoDB, S3 or OpenSearch for this.

Message queues and events

Agents communicate asynchronously by publishing and consuming messages or events (Amazon SQS, Amazon EventBridge), which decouples them so each can scale and fail independently.

On AWSStrands Agents supports agents-as-tools, swarm, graph, workflow and A2A; AgentCore Runtime hosts agents from any framework and supports MCP and A2A; Amazon Bedrock Agents Classic offered supervisor-based multi-agent collaboration but is no longer open to new customers.

More agents aren't automatically better. Every agent adds model calls, tokens, latency and failure points. Use a single agent until a task clearly needs specialization or parallel work.

Key takeaways

  • Tokens are the units models read, write and bill (about four characters in English); chunking splits documents into retrievable passages; embeddings are vectors capturing meaning, searched in vector databases.
  • Transformers use self-attention over the whole sequence; foundation models are huge pre-trained transformers adaptable to many tasks; multimodal models handle several data types; diffusion models generate images by removing noise.
  • GenAI suits creating, transforming and understanding content: media generation, summarization, assistants, translation, code, customer service agents, semantic search and richer recommendations.
  • FM lifecycle: data selection, model selection, pre-training, fine-tuning, evaluation, deployment, feedback. Most businesses start at model selection.
  • Input and output tokens are priced separately, output higher; context often dominates input cost; latency grows with tokens. Reduce cost with smaller models, less context, prompt caching, batch inference, Flex tier or Provisioned Throughput.
  • Context engineering decides what enters the context window (instructions, history, retrieved knowledge, memory, tools and results), using select, compress, isolate and externalize.
  • Agents loop through reasoning and tool calls. MCP standardizes connecting agents to tools and data (hosts, clients, servers; tools, resources, prompts); A2A connects agents to agents. Memory is short-term (session) or long-term (facts, preferences, summaries, episodes). Orchestration is deterministic (chaining, routing, parallelization, evaluator loops) or agent-driven; multi-agent patterns include supervisor, hierarchical, swarm and graph, communicating through a coordinator, hand-offs, shared memory or queues.
