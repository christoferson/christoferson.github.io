Guardrails

Configurable safety checks on what goes into and comes out of a model: harmful content, prompt attacks, off-limits topics, banned words, personal data, ungrounded answers and rule violations. Use them inline with Bedrock models, standalone on any text, or enforced across every account in an organization.

How a guardrail works

A guardrail is a Regional resource holding up to seven policies. You edit a DRAFT, publish numbered versions, and reference an ID and version at inference time or call it standalone.

  1. InputThe user's input is evaluated by all enabled policies in parallel.
  2. Blocked?If an input policy intervenes, the configured blocked message is returned and the model isn't called (you pay only for the guardrail).
  3. ModelOtherwise the model runs.
  4. OutputThe response is evaluated; it's replaced by the blocked message, masked, or returned unchanged.

Guardrails work on bedrock-runtime (Converse, ConverseStream, InvokeModel and its streaming variant), with Knowledge Bases, Agents, Flows and the AgentCore Harness, and on any text through ApplyGuardrail.

What guardrails don't check: retrieved Knowledge Base chunks (only the question and the generated answer), tool definitions, tool call arguments and tool results, and reasoning blocks. The bedrock-mantle endpoint has no Guardrails, and some models refuse a guardrail parameter (embedding and rerank models, Nova Sonic, OpenAI GPT-5.4 and 5.5, Marengo, Pegasus 1.5). For untrusted documents and tool output, check them yourself with ApplyGuardrail or InvokeGuardrailChecks.

The policies

  • Content filters (contentPolicyConfig): HATE, INSULTS, SEXUAL, VIOLENCE, MISCONDUCT (crime, fraud, harm) and PROMPT_ATTACK, each with an input and output strength (NONE, LOW, MEDIUM, HIGH; HIGH blocks the most), action (BLOCK or NONE) and modalities (TEXT, IMAGE). Images are PNG or JPEG up to 4 MB, 20 per request.
  • Prompt attacks: jailbreaks, prompt injection and (Standard tier) prompt leakage, evaluated on input. On InvokeModel they're checked only inside input tags.
  • Denied topics (topicPolicyConfig): up to 30, each with a name, a definition (200 characters on Classic, 1,000 on Standard) and up to 5 example phrases. Write crisp definitions of what the topic is, not instructions or exceptions, and use word or PII filters for specific entities.
  • Word filters (wordPolicyConfig, free): up to 10,000 words or phrases of up to three words, plus AWS's profanity list; case-insensitive whole-word matching.
  • Sensitive information (sensitiveInformationPolicyConfig): 31 PII types (names, emails, phone numbers, addresses, card numbers, SSNs, AWS keys, bank and passport numbers and more) with BLOCK, ANONYMIZE (replaced by {EMAIL} and so on) or NONE, plus up to 30 regex patterns (free).
  • Contextual grounding (contextualGroundingPolicyConfig): GROUNDING (is the answer supported by the source?) and RELEVANCE (does it answer the question?), each blocking below a threshold of 0 to 0.99; output only, with a source of up to 100,000 characters and responses up to 5,000.
  • Automated Reasoning (automatedReasoningPolicyConfig): up to 2 versioned policies that check answers against formal rules (below).

Classic and Standard tiers

Content filters, prompt attacks, denied topics and (since October 2026) contextual grounding come in two tiers, set with tierConfig: {"tierName": "STANDARD"} on each policy. Both cost the same.

Creating and versioning

A Standard-tier guardrail for a support chatbot, then version 1 (Python, boto3; fields from the API reference) 
import boto3

bedrock = boto3.client("bedrock", region_name="us-east-1")

resp = bedrock.create_guardrail(
    name="support-bot-guardrail",
    blockedInputMessaging="Sorry, I can't help with that request.",
    blockedOutputsMessaging="Sorry, I can't share that answer.",
    # Required for the Standard tier
    crossRegionConfig={"guardrailProfileIdentifier": "us.guardrail.v1:0"},
    contentPolicyConfig={
        "tierConfig": {"tierName": "STANDARD"},
        "filtersConfig": [
            {"type": "HATE", "inputStrength": "HIGH", "outputStrength": "HIGH"},
            {"type": "VIOLENCE", "inputStrength": "HIGH", "outputStrength": "HIGH"},
            # Detect only while tuning: report, don't block
            {"type": "MISCONDUCT", "inputStrength": "MEDIUM", "outputStrength": "MEDIUM",
             "inputAction": "NONE", "outputAction": "NONE"},
            {"type": "PROMPT_ATTACK", "inputStrength": "HIGH", "outputStrength": "NONE"},
        ],
    },
    topicPolicyConfig={
        "tierConfig": {"tierName": "STANDARD"},
        "topicsConfig": [{
            "name": "Investment Advice",
            "type": "DENY",
            "definition": "Guidance or recommendations about allocating money or assets to generate returns.",
            "examples": ["Should I buy gold?", "Are stocks better than bonds?"],
        }],
    },
    wordPolicyConfig={"managedWordListsConfig": [{"type": "PROFANITY"}]},
    sensitiveInformationPolicyConfig={
        "piiEntitiesConfig": [
            {"type": "EMAIL", "action": "ANONYMIZE"},
            {"type": "US_SOCIAL_SECURITY_NUMBER", "action": "BLOCK"},
        ],
        "regexesConfig": [{"name": "OrderId", "pattern": r"ORD-\d{8}", "action": "ANONYMIZE"}],
    },
    contextualGroundingPolicyConfig={
        "tierConfig": {"tierName": "STANDARD"},
        "filtersConfig": [{"type": "GROUNDING", "threshold": 0.7}, {"type": "RELEVANCE", "threshold": 0.7}],
    },
)
guardrail_id = resp["guardrailId"]
version = bedrock.create_guardrail_version(guardrailIdentifier=guardrail_id, description="v1")["version"]
  • A version is an immutable snapshot of the DRAFT (up to 20 per guardrail). Changes to DRAFT never reach production until you create a new version and switch the application to it.
  • UpdateGuardrail replaces the whole configuration: resend every policy you want to keep, and resend tierConfig, or the tier silently resets to Classic.
  • Optional: a customer managed KMS key (kmsKeyId), per-direction inputEnabled and outputEnabled (a disabled direction isn't charged). Deleting a guardrail without a version deletes all its versions; guardrails used by enforcement can't be deleted.

Guarding model calls

Converse with a guardrail on just the user's text, and reading the trace (Python, boto3) 
rt = boto3.client("bedrock-runtime", region_name="us-east-1")

resp = rt.converse(
    modelId="global.anthropic.claude-sonnet-5-5",
    # Not evaluated: the system prompt has no guardContent block
    system=[{"text": "You are a banking assistant."}],
    messages=[{"role": "user", "content": [
        # Skipped, because a guardContent block is present
        {"text": "Answer briefly."},
        {"guardContent": {"text": {"text": user_input}}},
    ]}],
    guardrailConfig={"guardrailIdentifier": guardrail_id, "guardrailVersion": "1", "trace": "enabled"},
    inferenceConfig={"maxTokens": 512},
)
if resp["stopReason"] == "guardrail_intervened":
    g = resp["trace"]["guardrail"]
    for assessment in g.get("inputAssessment", {}).values():
        for f in assessment.get("contentPolicy", {}).get("filters", []):
            print("input", f["type"], f["confidence"], f["action"])
        for t in assessment.get("topicPolicy", {}).get("topics", []):
            print("input topic", t["name"], t["action"])
    for assessments in g.get("outputAssessments", {}).values():
        for a in assessments:
            for p in a.get("sensitiveInformationPolicy", {}).get("piiEntities", []):
                # ANONYMIZED or BLOCKED; p["match"] holds the raw value
                print("output PII", p["type"], p["action"])
  • guardContent rules: with no guardContent block, all message content is evaluated; once any message has one, only the guardContent blocks are. The system prompt is evaluated only through its own guardContent block. Wrap just the latest user turn to save cost.
  • trace is enabled, enabled_full (also lists what passed) or disabled. The trace's appliedGuardrailDetails shows whether a guardrail came from the request, the account or the organization.
  • InvokeModel: pass guardrailIdentifier, guardrailVersion and trace as parameters (headers), add "amazon-bedrock-guardrailConfig": {"tagSuffix": "..."} to the body, and wrap the user's text in <amazon-bedrock-guardrails-guardContent_SUFFIX> tags. Use a new random suffix per request, so an attacker can't close the tag. The response adds amazon-bedrock-guardrailAction.
  • In Knowledge Bases, set guardrailConfiguration in RetrieveAndGenerate's generation settings (customer-managed) or policyConfiguration on agentic retrieval; in the AgentCore Harness, use the model's additionalParams.guardrailConfig; AgentCore Policy can also use Guardrails conditions on tool calls.

ApplyGuardrail and InvokeGuardrailChecks

ApplyGuardrail: a guardrail on any text

ApplyGuardrail runs a guardrail without calling a model, so it works with any model (including non-Bedrock ones), on retrieved documents, tool output or a finished answer. Only bedrock:ApplyGuardrail is needed.

Check user input before doing anything, and check a RAG answer for grounding (Python, boto3) 
# 1) Input check: cheaper than retrieving and generating first
r = rt.apply_guardrail(
    guardrailIdentifier=guardrail_id,
    guardrailVersion="1",
    source="INPUT",
    content=[{"text": {"text": user_input}}],
)
if r["action"] == "GUARDRAIL_INTERVENED":
    # The blocked message, or the masked text if only masking applied
    reply = r["outputs"][0]["text"]

# 2) Output grounding check: source and question are qualified, the answer is not
r = rt.apply_guardrail(
    guardrailIdentifier=guardrail_id,
    guardrailVersion="1",
    source="OUTPUT",
    content=[
        {"text": {"text": retrieved_passages, "qualifiers": ["grounding_source"]}},
        {"text": {"text": user_question, "qualifiers": ["query"]}},
        {"text": {"text": model_answer}},
    ],
    # Also return scores that passed
    outputScope="FULL",
)
for a in r["assessments"]:
    for f in a.get("contextualGroundingPolicy", {}).get("filters", []):
        print(f["type"], f["score"], f["threshold"], f["action"])

The response has action (NONE or GUARDRAIL_INTERVENED), outputs, assessments and usage in text units per policy.

InvokeGuardrailChecks: scores for agent loops

InvokeGuardrailChecks (16 June 2026) needs no guardrail resource: you pick the checks per request (content filters, prompt attack, sensitive information), and it returns scores without blocking anything, so your code decides. It's meant for the points guardrails don't cover in agents: before the model, after the response, before running a tool, and on tool results.

Scan a tool result for injection and secrets before the agent sees it (Python, boto3) 
r = rt.invoke_guardrail_checks(
    messages=[{"role": "user", "content": [{"text": tool_result_text}]}],
    checks={
        "promptAttack": {"categories": [{"category": "PROMPT_INJECTION"}, {"category": "JAILBREAK"}]},
        "sensitiveInformation": {"entities": [{"type": "EMAIL"}, {"type": "AWS_SECRET_KEY"}]},
    },
)
# Severity scores are 0, 0.2, 0.4 ... 1.0; the threshold is yours
if any(x["severityScore"] >= 0.6 for x in r["results"]["promptAttack"]["results"]):
    tool_result_text = "[tool output withheld]"
for e in r["results"]["sensitiveInformation"]["results"]:
    # Character offsets for redaction in your code
    print(e["type"], e["beginOffset"], e["endOffset"])

IAM bedrock:InvokeGuardrailChecks on *; 1,500 requests per minute; 7 Regions; cheaper per text unit than full guardrails (content filters $0.07, prompt attack $0.08, PII $0.10 per 1,000). No topics, words, grounding, regex or images.

Block, mask, detect and streaming

  • Block returns your blocked message. Mask (ANONYMIZE, PII and regex only) replaces values with {TYPE}. Detect (action NONE, April 2025) changes nothing but reports what it found in the trace: use it to tune strengths before switching to block.
  • Since April 2025 inputs and outputs have separate actions and can be switched off individually.
  • Streaming: sync mode (the default; streamProcessingMode in Converse's guardrail settings) holds chunks until they're checked, adding latency; async sends chunks immediately and checks in the background, so harmful content can reach the user before it's caught, and PII isn't masked. Relevance on streams is judged per chunk, so an off-topic answer may be flagged only after it has streamed.

A masked answer and a blocked answer both return stopReason: guardrail_intervened: only the trace (ANONYMIZED vs BLOCKED) tells them apart. The trace and model invocation logs contain the unmasked values by design, so treat them as sensitive (use CloudWatch Logs data protection on invocation logs).

Enforcement and sharing

IAM: require a guardrail on every call

Allow model calls only with guardrail version 1 (IAM policy, as in the Guardrails permissions guide) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowWithGuardrail",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": ["arn:aws:bedrock:us-east-1::foundation-model/*"],
      "Condition": {"StringEquals": {"bedrock:GuardrailIdentifier": "arn:aws:bedrock:us-east-1:111111111111:guardrail/GUARDRAIL_ID:1"}}
    },
    {
      "Sid": "DenyWithoutGuardrail",
      "Effect": "Deny",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": ["arn:aws:bedrock:us-east-1::foundation-model/*"],
      "Condition": {"StringNotEquals": {"bedrock:GuardrailIdentifier": "arn:aws:bedrock:us-east-1:111111111111:guardrail/GUARDRAIL_ID:1"}}
    },
    {
      "Sid": "ApplyGuardrail",
      "Effect": "Allow",
      "Action": ["bedrock:ApplyGuardrail"],
      "Resource": ["arn:aws:bedrock:us-east-1:111111111111:guardrail/GUARDRAIL_ID"]
    }
  ]
}

The value is the guardrail ARN with :VERSION (none means DRAFT; use ArnLike ...:* for any numbered version). Two limits: roles used for RetrieveAndGenerate, InvokeAgent and inline agents get AccessDenied under it (those make internal model calls without a guardrail), so use separate roles; and a caller can still skip input checks by tagging only harmless text, though output is always checked. Calls through inference profiles need profile statements too (inference profiles).

Account and organization enforcement

  • Account level (PutEnforcedGuardrailConfiguration): a numbered guardrail version applied to every InvokeModel and Converse call in the account and Region, with includedModels (or ALL) and excludedModels, and selectiveContentGuarding for system prompts and messages: COMPREHENSIVE (default; evaluate everything, closing the tagging loophole) or SELECTIVE (only tagged content).
  • Organization level (generally available 3 April 2026): an AWS Organizations policy of type BEDROCK_POLICY attached to the root, OUs or accounts names a versioned guardrail owned by the management account, per Region, with a resource policy letting member accounts call bedrock:ApplyGuardrail on it.
  • Request, account and organization guardrails all run, and the most restrictive result wins. Each is charged, to the calling account.
Enforce a guardrail on all models except embeddings in us-east-1 (AWS Organizations Bedrock policy, as in the Organizations guide) 
{"bedrock": {"guardrail_inference": {"us-east-1": {"config_1": {
  "identifier": {"@@assign": "arn:aws:bedrock:us-east-1:555555555555:guardrail/GUARDRAIL_ID:1"},
  "selective_content_guarding": {"system": {"@@assign": "comprehensive"}, "messages": {"@@assign": "comprehensive"}},
  "model_enforcement": {
    "included_models": {"@@assign": ["ALL"]},
    "excluded_models": {"@@assign": ["amazon.titan-embed-text-v2:0", "cohere.embed-english-v3"]}
  }
}}}}}

With an enforced guardrail, every caller needs bedrock:ApplyGuardrail on it, or all its Invoke and Converse calls fail with AccessDenied: test from every role before you turn it on. Enforced guardrails can't contain Automated Reasoning policies (runtime failures), must be numbered versions, are set per Region, and can't be deleted while enforced.

Sharing and cross-Region profiles

  • Resource-based policies on guardrails and guardrail profiles share them within your organization only (aws:PrincipalOrgID or OU paths; actions ApplyGuardrail and GetGuardrail). With cross-Region profiles, the policies on each destination Region's profile must be written through the source Region's endpoint, or they have no effect.
  • Guardrail profiles (no extra cost): us, us-gov, eu, uk, au, ca and apac .guardrail.v1:0. Configuration stays in your Region, but text may be processed elsewhere in the geography; the UK and Australia profiles stay in one Region. IAM needs ApplyGuardrail on the profile ARN in each destination Region.

Automated Reasoning checks

Automated Reasoning (generally available August 2025) checks whether an answer follows formal rules extracted from your documents, such as an HR leave policy or eligibility criteria, using a logic solver; language models translate the text into the policy's variables. It's detect only and English only, with no streaming.

  1. BuildCreateAutomatedReasoningPolicy, then a build workflow (StartAutomatedReasoningPolicyBuildWorkflow with INGEST_CONTENT and your PDF or text) generates rules (if-then logic) and variables; a fidelity report scores coverage.
  2. RefineImprove variable descriptions (the main lever for accuracy), resolve ambiguities and refine iteratively (June 2026).
  3. TestTest cases with expected results, plus generated scenarios.
  4. DeployCreateAutomatedReasoningPolicyVersion, then attach the versioned ARN to a guardrail (up to 2 policies) with a cross-Region profile.
  5. CheckCall ApplyGuardrail with source OUTPUT: the question as a query block and the answer unqualified.
  • Findings, worst first: TRANSLATION_AMBIGUOUS, IMPOSSIBLE, INVALID (contradicts a rule; the result names the rules), SATISFIABLE (could be true or false: missing conditions), VALID, plus TOO_COMPLEX and NO_TRANSLATIONS (nothing matched the policy's variables). VALID covers only the claims the policy's variables capture.
  • On Converse it runs only on guardContent blocks and is skipped silently otherwise: check that automatedReasoningPolicyUnits in usage is above 0.
  • It doesn't protect against prompt injection, and encoded text can make a whole submission go unevaluated.
  • Limits: 100 policies per account, 500 rules and 200 variables per policy. 7 Regions. $0.17 per 1,000 text units per policy, charged for every check. Customer managed KMS keys since October 2025.

Quotas, pricing and monitoring

  • Pricing per 1,000 text units (a text unit is up to 1,000 characters), only for enabled policies: content filters $0.15, denied topics $0.15, sensitive information $0.10, contextual grounding $0.10 (source plus question plus answer), images $0.00075 each; word filters and regex free. A blocked input costs only the guardrail; a blocked output also costs the model call. AWS's example: a chatbot with 1,000 queries an hour using content filters and topics costs about $0.90 an hour.
  • Quotas: 100 guardrails per account, 20 versions each, 30 topics, 10,000 words, 30 regex patterns. ApplyGuardrail allows 100 requests per second in the large Regions and 25 elsewhere, and text-units-per-second limits per policy are often low outside the big Regions: check Service Quotas before scaling.
  • Monitoring: CloudWatch namespace AWS/Bedrock/Guardrails with Invocations, InvocationsIntervened, TextUnitCount and latency, by policy type, input or output, and guardrail version. In CloudTrail, ApplyGuardrail is a data event (AWS::Bedrock::Guardrail, including evaluations made during model calls), off by default; watch it for AccessDenied after enabling enforcement.
  • Each enabled policy adds processing latency (guardrailProcessingLatency in the trace).

What's changed

  • 2026: organization and account enforcement generally available (3 April); InvokeGuardrailChecks and Automated Reasoning in Sydney (16 June); Guardrails in AgentCore Policy generally available (17 June); Automated Reasoning refinement workflows (23 June); Standard tier for contextual grounding (19 to 20 October).
  • 2025: IAM condition key bedrock:GuardrailIdentifier (18 March); image filters generally available (28 March); detect mode and per-direction actions (8 April); cross-Region guardrail profiles (May); Classic and Standard tiers (23 June); Automated Reasoning generally available (August); customer managed keys for Automated Reasoning (17 October); code-domain detection (19 November); sharing within an organization (21 November).
  • 2024: generally available (23 April); Knowledge Bases and Agents (May); Converse (June); contextual grounding and ApplyGuardrail (10 July); CloudWatch metrics (September); Flows (November); prices cut up to 85% (December); Automated Reasoning and image filter previews (December).
