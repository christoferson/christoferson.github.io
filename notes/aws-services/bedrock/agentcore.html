AgentCore and the Harness

How the AgentCore platform fits together, and how to build an agent with the Harness: a managed agent loop you configure instead of code. Model, tools, skills, memory and limits as settings; one isolated microVM per session; versions and endpoints for safe releases.

The AgentCore platform

Amazon Bedrock AgentCore is AWS's platform for building, running and operating agents with any framework and any model, inside or outside Bedrock. It's a set of services you can use together or one at a time, all billed by consumption. It became generally available in October 2025 and is now in 21 commercial Regions plus AWS GovCloud (US-West), though not every component is in every Region.

The 13 components

  • Harness: a managed agent loop; you declare model, prompt, tools, skills, memory and limits, and AgentCore runs the loop.
  • Runtime: serverless hosting for your own agent or tool code (any framework), with per-session isolation and sessions up to 8 hours.
  • Memory: short-term conversation events and long-term records (facts, preferences, summaries) extracted by strategies.
  • Gateway: turns Lambda functions, OpenAPI and Smithy APIs and MCP servers into one governed MCP tool endpoint.
  • Identity: agent identities, inbound JWT or IAM authentication, and a token vault for the OAuth tokens and API keys agents use outbound.
  • Code Interpreter and Browser: sandboxed code execution and a managed cloud Chrome for agents.
  • Observability: OpenTelemetry traces, logs and metrics in CloudWatch.
  • Evaluations and Optimization: scoring agent quality from traces, then recommending prompt and tool changes and A/B testing them.
  • Policy: deterministic authorization of every tool call that goes through a Gateway.
  • Registry: a governed catalog of agents, MCP servers and skills.
  • Payments: agent micropayments through x402 and the Machine Payments Protocol.

How the pieces fit in one request

  1. CallYour application calls InvokeHarness (or InvokeAgentRuntime for code), signed with IAM or carrying a user's JWT that Identity validates.
  2. SessionAgentCore starts or resumes the session's own microVM, keyed by the session ID you send.
  3. MemoryThe loop loads recent turns and relevant long-term records for the user (the actor).
  4. ModelThe loop calls the model: Bedrock through the execution role, or OpenAI, Gemini or LiteLLM with a key from the Identity token vault.
  5. ToolsTool calls go to the Gateway (where Policy authorizes each one), to MCP servers, Browser or Code Interpreter, to built-in shell and file tools, or back to your code.
  6. ObserveTraces and logs flow to CloudWatch automatically; Evaluations score them and Optimization suggests changes you release as new versions.

Harness or Runtime

Both run on the same isolated session infrastructure. The difference is who owns the agent loop.

HarnessRuntime
What you provide
Configuration (API, CLI harness.yaml or console); no codeYour code in any framework (Strands, LangGraph, CrewAI, OpenAI Agents SDK and others) as an ARM64 container or zip
The loop
AWS-managed, built on Strands Agents; built-in shell and file toolsYours: you call models, Memory, Gateway and tools through the SDK
Can't do
Choose the framework, voice or bidirectional streaming, graph workflows, per-stage prompts, custom orchestrators, routing multi-agent systemsNothing structural; you build what the Harness gives you for free
Shared
Session isolation, VPC, IAM and OAuth inbound, file system mounts, environment variables, shell commands into the session, versions and endpoints, Runtime quotas

AWS's guidance is to start with the Harness unless you have a reason to own the loop (an existing codebase or advanced orchestration). If you outgrow it, agentcore export harness generates equivalent Strands Python for Runtime, though it drops Gateway, Browser and Code Interpreter tools, AWS skills and managed memory, which you then wire up in code.

Not the same thing: Bedrock Managed Agents, powered by OpenAI (preview since September 2026, three US Regions, bedrock-mantle only) is an OpenAI-managed loop for OpenAI models. The Harness is AWS-managed and works with any provider.

How the Harness works

  • Each session (your runtimeSessionId, 33 to 100 characters) gets its own Firecracker microVM with a file system and a shell. Reusing the ID continues the conversation in the same VM; a new ID starts fresh.
  • Sessions end after the idle timeout (default 15 minutes) or maximum lifetime (default and maximum 8 hours). Anything you need beyond that goes in Memory, session storage or a mounted file system.
  • Every harness has two built-in tools, shell and file_operations, so the agent can run commands and edit files in its VM. Their definitions add about 900 input tokens to every model call.
  • The Harness is generally available since 17 June 2026 in 15 commercial Regions and GovCloud (US-West). It isn't in AgentCore's newer Regions (N. California, Milan, Spain, Malaysia, Hyderabad, Thailand).

Configuring a harness

The configuration is the same whether you use the CreateHarness API or the CLI's harness.yaml (which uses the API's field names). This file shows most settings:

app/assistant/harness.yaml (AgentCore CLI project; fields as in the CLI documentation) 
name: assistant
model:
  bedrockModelConfig:
    modelId: global.anthropic.claude-sonnet-5-5
    apiFormat: converse_stream
    # per model call
    maxTokens: 4096
tools:
  - name: research
    type: remote_mcp
    config:
      remoteMcp:
        url: https://mcp.example.com/mcp
  - name: company_tools
    type: agentcore_gateway
    config:
      agentCoreGateway:
        gatewayArn: arn:aws:bedrock-agentcore:us-west-2:111111111111:gateway/GATEWAY_ID
        outboundAuth:
          awsIam: {}
allowedTools: ["@builtin", "@research/search", "@company_tools"]
skills:
  - awsSkills:
      paths: [core-skills/aws-cdk]
memory:
  managedMemoryConfiguration:
    strategies: [SEMANTIC, SUMMARIZATION]
    eventExpiryDuration: 30
truncation:
  strategy: sliding_window
  config:
    slidingWindow:
      messagesCount: 40
maxIterations: 15
timeoutSeconds: 300
environmentVariables:
  LOG_LEVEL: info
environment:
  agentCoreRuntimeEnvironment:
    lifecycleConfiguration:
      idleRuntimeSessionTimeout: 900
      maxLifetime: 28800
    filesystemConfigurations:
      - sessionStorage:
          mountPath: /mnt/session
tags:
  team: support

Model

Set exactly one provider object. If you omit the model, the API uses global.anthropic.claude-sonnet-4-6; the CLI scaffolds global.anthropic.claude-sonnet-5-5.

  • bedrockModelConfig: modelId, apiFormat (converse_stream, the default, on bedrock-runtime; or responses / chat_completions on bedrock-mantle for models served there, such as OpenAI's), maxTokens per model call, temperature, topP, and additionalParams passed through unchanged (for example a guardrailConfig).
  • openAiModelConfig, geminiModelConfig, liteLlmModelConfig: the model ID plus apiKeyArn, the ARN of an Identity API key credential provider (not a Secrets Manager ARN); OpenAI and LiteLLM also accept apiBase for compatible endpoints.
  • Claude Sonnet 5 and 5.5 reject temperature: leave it unset for them.

Tools and allowedTools

Each tool has a type, an optional name, and a config key matching the type:

  • remote_mcp (remoteMcp): an MCP server url and optional headers; a header value can be ${arn:...apikeycredentialprovider/NAME}, which the harness swaps for the stored key at call time.
  • agentcore_gateway (agentCoreGateway): gatewayArn and outboundAuth (awsIam, the default, signs with the execution role; or oauth with a credential provider; or none).
  • agentcore_browser and agentcore_code_interpreter: the AWS-managed tools by default, or your custom ones by ARN.
  • inline_function (inlineFunction): a description and JSON inputSchema. The harness doesn't run it: it pauses and hands the call to your application (see inline functions). Use it for approvals and anything that must run in your own code.

allowedTools narrows what the model sees with patterns: *, @builtin, @builtin/shell, @git (every tool from the entry named git), @git/read_*. Omitted means all tools. It's a prompt filter, not a security control: it saves tokens but doesn't stop InvokeAgentRuntimeCommand, which IAM governs.

Skills

Skills are folders with a SKILL.md (YAML front matter with name and description) plus optional scripts and references. Only about 100 tokens of metadata go into the prompt; the agent loads the full skill when it needs it. Sources: awsSkills (AWS's curated catalog, optionally narrowed by paths), git (URL, subfolder, optional token from Identity; 60-second clone limit), s3 (a prefix, up to 1 GB per skill) or path (already in the VM). Skills are fetched once per session; a fetch failure fails the invocation.

Memory and truncation

  • managedMemoryConfiguration (the default if you omit memory, and billed): AgentCore creates a memory with 1 to 4 strategies (SEMANTIC and SUMMARIZATION by default, also USER_PREFERENCE and EPISODIC), an event expiry in days (default 30) and an optional KMS key set at creation.
  • agentCoreMemoryConfiguration: use an existing memory by ARN, with optional actorId and retrieval settings per namespace.
  • disabled: {}: no memory. Managed memory is deleted with the harness unless you pass deleteManagedMemory=false.
  • truncation keeps the prompt inside the context window: sliding_window (default; keep the last N messages), summarization (summarize older turns, keep recent ones) or none. It trims the prompt only, never Memory.

Limits and environment

  • maxIterations (default 75 model calls per invocation), timeoutSeconds (default 3,600) and maxTokens stop runaway loops; all three can be overridden per call. AWS's pages describe maxTokens both as per iteration and as a total per invocation, so test the behaviour before relying on it as a cost cap.
  • environment.agentCoreRuntimeEnvironment holds the session lifecycle (idleRuntimeSessionTimeout, maxLifetime, 60 to 28,800 seconds), the network (PUBLIC or VPC with subnets and security groups) and up to 5 file system mounts under /mnt: per-session storage (1 GB, kept across stop and resume of the same session ID), EFS access points and S3 Files access points (VPC only, up to 2 each).
  • environmentArtifact.containerConfiguration.containerUri swaps the managed base image (Python and bash) for your own linux/arm64 image, which must include bash, sh and core utilities (plus tar and a writable /tmp for fetched skills). The harness overrides its entry point.
  • environmentVariables (up to 50) are plain text: never put secrets there; use the Identity token vault.

harnessName (up to 40 characters, which in the CLI includes the project and target prefix) and endpoint names allow letters, digits and underscores only. Some AWS examples use hyphens (production-endpoint) and fail validation. And UpdateHarness replaces lists wholesale (tools, hooks, mounts, environment variables): send the full list, not just the new item.

Permissions

The execution role

The harness assumes an execution role for everything it does: calling models, writing logs and traces, using Memory, Browser, Code Interpreter and Gateway, and fetching keys from the token vault. The CLI creates it for you; with the API you create it yourself.

Trust policy (as on the harness security page) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "bedrock-agentcore.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
Core of the permissions policy (abridged from AWS's sample; add statements only for the features you configure)

  "Statement": [
    {
      "Sid": "BedrockModelInvocation",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": ["arn:aws:bedrock:*::foundation-model/*", "arn:aws:bedrock:us-west-2:111111111111:inference-profile/*"]
    },
    {
      "Sid": "CloudWatchLogs",
      "Effect": "Allow",
      "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents", "logs:DescribeLogStreams"],

AWS's full sample adds statements for the workload identity, the managed Browser and Code Interpreter, managed memory (memory/harness_*), and pulling the managed image. Add bedrock:ApplyGuardrail for guardrails, bedrock-agentcore:InvokeGateway for Gateway tools, s3:GetObject and s3:ListBucket for S3 skills, lambda:InvokeFunction (or sns:Publish, events:PutEvents) for hooks, and bedrock-agentcore:GetResourceApiKey plus secretsmanager:GetSecretValue on the vault secret for third-party model keys.

Caller permissions

Every harness action also needs the matching Runtime action, because a harness is built on a managed Runtime: invoking needs bedrock-agentcore:InvokeHarness and InvokeAgentRuntime; creating needs CreateHarness, CreateAgentRuntime and CreateMemory; invoking a named endpoint needs both the harness ARN and the endpoint ARN in the policy's resources.

Creating and invoking

End to end in Python

Harness code uses boto3: the control-plane client bedrock-agentcore-control creates and manages harnesses; the data-plane client bedrock-agentcore invokes them. (The AgentCore Python SDK has no harness module, and the AWS CLI has no invoke-harness command because the response is an event stream.)

Create a harness with an approval step, wait until ready, chat with streaming, then pin production (Python, boto3; field names from the API reference) 
import json
import time
import uuid

import boto3

REGION = "us-west-2"
ctl = boto3.client("bedrock-agentcore-control", region_name=REGION)
dp = boto3.client("bedrock-agentcore", region_name=REGION)

# An inline function: the harness pauses and your code decides
approve_tool = {
    "type": "inline_function",
    "name": "approve_purchase",
    "config": {"inlineFunction": {
        "description": "Ask a human to approve a purchase.",
        "inputSchema": {
            "type": "object",
            "properties": {"item": {"type": "string"}, "amount": {"type": "number"}},
            "required": ["item", "amount"],
        },
    }},
}

h = ctl.create_harness(
    harnessName="shopping_agent",
    executionRoleArn="arn:aws:iam::111111111111:role/HarnessExecutionRole",
    model={"bedrockModelConfig": {"modelId": "global.anthropic.claude-sonnet-5-5", "maxTokens": 4096}},
    systemPrompt=[{"text": "You help staff buy equipment. Always request approval before buying."}],
    tools=[{"type": "agentcore_browser", "name": "browser"}, approve_tool],
    # Managed memory is created (and billed) unless you disable it
    memory={"disabled": {}},
    truncation={"strategy": "sliding_window", "config": {"slidingWindow": {"messagesCount": 30}}},
    maxIterations=25,
    timeoutSeconds=900,
    environment={"agentCoreRuntimeEnvironment": {
        "lifecycleConfiguration": {"idleRuntimeSessionTimeout": 300, "maxLifetime": 3600},
    }},
    tags={"team": "procurement"},
)["harness"]
harness_id, harness_arn = h["harnessId"], h["arn"]

# Wait for READY (CREATING, CREATE_FAILED, READY, ...)
while (st := ctl.get_harness(harnessId=harness_id)["harness"])["status"] not in ("READY", "CREATE_FAILED"):
    time.sleep(5)
if st["status"] != "READY":
    raise RuntimeError(st.get("failureReason"))


def run(messages, session_id):
    """Stream one invocation; return (toolUseId, input) if the harness waits for approval."""
    r = dp.invoke_harness(harnessArn=harness_arn, runtimeSessionId=session_id, messages=messages)
    tool_id, idx, tool_input, last_stop = None, None, "", None
    for ev in r["stream"]:
        if "contentBlockStart" in ev:
            tu = ev["contentBlockStart"]["start"].get("toolUse")
            if tu and tu["name"] == "approve_purchase":
                tool_id, idx = tu["toolUseId"], ev["contentBlockStart"]["contentBlockIndex"]
        elif "contentBlockDelta" in ev:
            d = ev["contentBlockDelta"]
            if "text" in d["delta"]:
                print(d["delta"]["text"], end="", flush=True)
            elif "toolUse" in d["delta"] and d["contentBlockIndex"] == idx:
                tool_input += d["delta"]["toolUse"]["input"]
        elif "messageStop" in ev:
            last_stop = ev["messageStop"]["stopReason"]
        elif "metadata" in ev:
            print("\n[usage]", ev["metadata"]["usage"])
        elif "runtimeClientError" in ev:
            raise RuntimeError(ev["runtimeClientError"])
    if last_stop == "tool_use" and tool_id:
        return tool_id, json.loads(tool_input or "{}")
    return None


# At least 33 characters; reuse it to continue the same conversation
session = f"shop-{uuid.uuid4()}"
pending = run([{"role": "user", "content": [{"text": "Find a USB-C dock under $150 and buy it."}]}], session)
while pending:
    tool_use_id, args = pending
    ok = input(f"\nApprove {args}? [y/n] ") == "y"
    # Same session; send only the tool result
    pending = run([{"role": "user", "content": [{"toolResult": {
        "toolUseId": tool_use_id,
        "content": [{"text": "approved" if ok else "rejected by the user"}],
        "status": "success",
    }}]}], session)

# Pin a production endpoint to the tested version; callers pass qualifier="prod"
ctl.create_harness_endpoint(harnessId=harness_id, endpointName="prod",
                            targetVersion=st["harnessVersion"], description="Production")

Not executed here: it was assembled from the API reference and the getting-started guide. The ARN is in harness.arn of the create response; the ID looks like shopping_agent-AbCdEf1234.

The request

  • harnessArn (the full ARN) and optional qualifier (endpoint name; omitted means DEFAULT, the latest version).
  • runtimeSessionId (required, 33 to 100 characters; a UUID is 36), an optional end-user ID for user-scoped credentials, and W3C trace headers.
  • messages (user and assistant turns of text, tool results and reasoning; the last message can't be a tool use), actorId for Memory, and per-call overrides of model, systemPrompt, tools, skills (appended), allowedTools and the three limits. Memory, hooks and environment can't be overridden per call.

Stream events and stop reasons

One invocation streams several assistant turns and tool results: messageStart, then per content block contentBlockStart (tool calls and results), contentBlockDelta (text, partial tool input JSON, tool results, reasoning) and contentBlockStop, then messageStop with a stopReason, plus metadata (token usage, latency), hookEvent and error events. Read until the stream closes.

  • end_turn: finished. tool_result: tool results were streamed and more output may follow.
  • tool_use on the last messageStop: the harness is waiting for your inline function result.
  • max_iterations_exceeded, timeout_exceeded, max_output_tokens_exceeded: a harness limit stopped it. max_tokens: one model call hit its limit. model_context_window_exceeded: add or tighten truncation.
  • hook_stopped: a lifecycle hook denied the run. Others: content_filtered, malformed_model_output, malformed_tool_use, interrupted, partial_turn, stop_sequence.

Inline functions

  1. CaptureWhile streaming, note the toolUseId from contentBlockStart and join the toolUse.input fragments for that block.
  2. CheckOnly if the final messageStop is tool_use is the harness waiting for you.
  3. RunDo the work in your application (ask a human, call an internal system).
  4. ReturnInvoke again with the same session ID and only a user message holding the toolResult. Don't resend the assistant's tool use; if several inline calls came together, return all results in one request.

The AgentCore CLI can show an inline call but can't return its result; use the SDK.

The AgentCore CLI

The AgentCore CLI (npm package @aws/agentcore, Node.js 20.12 or later; version 1.0 since October 2026) scaffolds projects, deploys them with CDK, and runs, tests and observes them. It replaces the older Python starter toolkit, whose agentcore command can shadow it if both are installed.

From nothing to a deployed, versioned harness (shell) 
npm install -g @aws/agentcore
agentcore create --name ResearchProject --template empty
cd ResearchProject

agentcore add harness --name researcher \
  --model '{"provider":"bedrock","modelId":"global.anthropic.claude-sonnet-5-5"}' \
  --system-prompt "You are a research assistant. Cite sources." \
  --tools '[{"type":"agentcore_browser","name":"browser"}]' \
  --memory '{"mode":"managed","strategies":["SEMANTIC","SUMMARIZATION"],"eventExpiryDuration":30}' \
  --max-iterations 30 --timeout-seconds 900

# CDK deploy: creates the role, the harness and managed memory
agentcore deploy

SESSION="$(uuidgen)"
agentcore invoke --harness researcher --session-id "$SESSION" --prompt "Compare three EU Regions for latency to Lisbon."
agentcore logs harness --name researcher --since 1h --level error
agentcore traces harness list --name researcher --since 2h

# Pin prod to version 1, then call it
agentcore harness endpoint create --id HARNESS_ID --name prod --target-version 1
agentcore invoke --harness researcher --qualifier prod --prompt "Hello"

# Score real sessions, or move to code when configuration isn't enough
agentcore eval ondemand evaluate --agent HARNESS_ID --evaluators Builtin.Helpfulness --session-ids "$SESSION"
agentcore export harness --name researcher
  • A project keeps agentcore/agentcore.json, aws-targets.json, .env.local (local secrets; never commit), a CDK app, and app/NAME/harness.yaml with system-prompt.md. Edit the YAML, then agentcore deploy.
  • API keys for other providers: agentcore add credentials api-key --name NAME --api-key - (from stdin); deploy creates the Identity provider and grants the role. Inline secrets on the command line are rejected.
  • agentcore dev --mode browser deploys and opens a local inspector against the cloud harness; it doesn't run the harness locally, so it costs money.
  • The CLI-created role doesn't include VPC image-pull permissions: add them in agentcore/cdk/lib/cdk-stack.ts.

Versions and endpoints

  • Creating a harness makes version 1; every update creates a new immutable version holding the whole configuration.
  • The DEFAULT endpoint always follows the latest version. Named endpoints (CreateHarnessEndpoint with targetVersion) stay pinned until you move them; each shows a liveVersion and, while updating, the targetVersion.
  • A release pattern: let DEFAULT track the latest for development, keep stage and prod pinned, promote by moving stage and then prod with UpdateHarnessEndpoint, and roll back instantly by pointing prod at the previous version.
  • Limits: 10 endpoints and 1,000 versions per harness (Runtime quotas). Logs, traces and online evaluations can be filtered by endpoint.

Lifecycle hooks

Hooks (September 2026) run your checks at four points: beforeInvocation, beforeToolCall, afterToolCall and afterInvocation, up to 20 per harness. A Lambda target can allow or deny (synchronous); SNS and EventBridge targets only notify. A deny before invocation stops the run (hook_stopped), before a tool call skips that tool, after a tool call keeps the result but stops the run, and after invocation is only reported.

Configure a hook that blocks shell commands touching credentials (UpdateHarness, boto3) 
ctl.update_harness(
    harnessId=harness_id,
    hooks=[{"beforeToolCall": {
        "name": "guard_shell",
        "target": {"lambda": {
            "arn": "arn:aws:lambda:us-west-2:111111111111:function:harness-guard",
            "timeoutSeconds": 10,
            "failureMode": "deny",
        }},
    }}],
)
The Lambda function: return allow or deny with a reason (Python) 
def handler(event, context):
    # event: hookEventId, name, event, harnessArn, sessionId, context
    ctx = event.get("context", {})
    if event["event"] == "before_tool_call" and ctx.get("toolName") == "shell":
        command = str(ctx.get("toolInput", ""))
        if ".aws/credentials" in command or "env" in command.split():
            return {"decision": "deny", "reason": "Reading credentials is not allowed."}
    return {"decision": "allow"}
  • The context differs by event: messages before invocation, tool name, type, input and ID around tool calls, stop reason and usage after invocation; it's capped at 64 KiB with a truncated marker.
  • failureMode (deny by default) decides what happens if the Lambda errors or times out. Several Lambda hooks on one event run in parallel, and any deny wins.
  • For long hooks, raise the boto3 read timeout above the hook timeout. An allow on an inline function isn't proof the client did the action.

Security, logs, quotas and cost

Security

  • Each session is isolated in its own microVM. Commands sent with InvokeAgentRuntimeCommand run as root inside it, so grant that action (and the interactive shell action) narrowly.
  • Anyone who can invoke the harness reaches all its tools, and per-call overrides let callers change the model, apiBase, additionalParams and skills. If you pass user input through, strip or allowlist those fields: they can redirect inference, headers and instructions.
  • With IAM (SigV4) callers there's no per-user identity downstream; use a custom JWT authorizer when tools need user-scoped OAuth or on-behalf-of tokens. The end-user ID and actorId aren't authentication.
  • Keep provider keys in the Identity token vault; the agent never sees them. Apply Guardrails through additionalParams.guardrailConfig (with converse_stream only) and govern tool calls with Policy on the Gateway.
  • VPC mode needs interface endpoints for ECR (ecr.api, ecr.dkr), an S3 gateway endpoint and bedrock-runtime, plus ECR pull permissions on harness-* repositories; otherwise sessions fail with image pull timeouts. Git skills, remote MCP and public images need NAT.

Observability

Traces, logs and metrics are emitted for every model call, tool call, memory operation and command, with no extra setup; turn on CloudWatch Transaction Search once per account (agentcore deploy does it). Logs go to the managed Runtime's log group under /aws/bedrock-agentcore/runtimes/. In CloudTrail a harness appears as a Runtime resource: management events are CreateHarness and friends, but invocations are logged as InvokeAgentRuntime data events, not InvokeHarness.

Quotas

The Harness has no quotas of its own; Runtime's apply: 5,000 active sessions per account in us-east-1 and us-west-2 (2,500 elsewhere, adjustable), 25 new sessions per second, 1,000 data-plane calls per second shared across invoke actions, 2 vCPU and 8 GB per session, 60-minute streaming responses, and 8-hour sessions. Cross-account calls count against the owner's quotas.

Cost

There's no separate harness charge. You pay for the Runtime underneath (vCPU-seconds actually used, not while waiting on I/O, plus peak memory per second for the session's life), model tokens (the prompt includes the system prompt, history, retrieved memory, skill metadata and every allowed tool's definition), Memory if enabled, Browser and Code Interpreter sessions, Gateway calls, and CloudWatch. Shorter idle timeouts, allowedTools, tighter truncation and disabling unused memory all cut cost. Harness tags propagate to the managed Runtime and memory for cost allocation.

A Step Functions InvokeHarness task stops after 15 minutes, but the harness keeps running (and billing) until its own timeoutSeconds. Set the harness timeout to match the workflow.

Moving from Agents Classic

Bedrock Agents is now Agents Classic: closed to new customers since 30 July 2026 (accounts without recent use get a 403 on CreateAgent and InvokeInlineAgent), in maintenance mode with its model catalog frozen, and no end-of-life date. AWS's migration guide recommends the Harness and maps the concepts:

  • Action groups become Gateway targets exposed as MCP tools (or @tool functions on Runtime).
  • Knowledge bases become a Gateway-fronted Managed Knowledge Base or a retrieval tool; the knowledge bases themselves don't change.
  • Return of control and user input become inline functions; the code interpreter becomes agentcore_code_interpreter; session memory becomes AgentCore Memory.
  • Guardrails move to the model's guardrailConfig or to Policy on the Gateway; the trace view becomes AgentCore Observability.
  • Per-stage prompt overrides, custom orchestrators and supervisor-style multi-agent setups need Runtime code. Agent versions and aliases correspond naturally to harness versions and endpoints.

The AWS agent toolkit's amazon-bedrock skill can drive the migration from a coding assistant, and agentcore add runtime --agent-id ID --agent-alias-id ALIAS --framework strands imports a Classic agent as Runtime code. Use the CLI 1.0 flags shown on this page: the manual steps on AWS's migration page use older flags.
