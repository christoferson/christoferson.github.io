Memory and built-in tools

AgentCore Memory gives agents short-term conversation history and long-term knowledge about each user, extracted automatically. The built-in tools give them a sandbox to run code, a managed cloud browser, and web search, plus Payments for paid resources.

Memory concepts

  • A memory is a resource holding two kinds of data. Its name allows letters, digits and underscores only.
  • Short-term memory is events: immutable, timestamped records you write with CreateEvent, filed under an actor (actorId: a user, an agent, or both, such as agent-support/customer-456) and a session (sessionId). Use them to reload a conversation. They expire after the memory's eventExpiryDuration (3 to 365 days in the API; the quotas page says a minimum of 7), applied to each event when it's written.
  • Long-term memory is records that strategies extract from events in the background: facts, preferences, summaries and episodes. They're stored under namespaces and found by semantic search with RetrieveMemoryRecords.
  • An event's payload is a list of up to 100 items: conversational messages (roles USER, ASSISTANT, TOOL, OTHER), json data (up to 100 KB, August 2026), or blob data. Blobs are never extracted to long-term memory.
  • Branches (branch {name, rootEventId}) record alternative paths, for example when a user edits an earlier message. extractionMode: "SKIP" keeps an event short-term only.
  • AgentCore never invents actors or sessions: your application decides which user an actorId belongs to.

Long-term extraction is asynchronous (seconds to minutes), so something the user just said isn't retrievable as a record on the next turn: use the session's events for the current conversation and records for later ones. Strategies also process only events written after the strategy became active; there's no backfill.

AWS's rule of thumb for memory versus retrieval-augmented generation: long-term memory answers "who is this user and what happened before"; a knowledge base answers "what do trusted sources say now". Most assistants need both.

Strategies and namespaces

Built-in strategies

  • Semantic (semanticMemoryStrategy): facts about people, things and events.
  • User preference (userPreferenceMemoryStrategy): choices, likes and styles. Semantic and preference strategies read only USER and ASSISTANT messages.
  • Summary (summaryMemoryStrategy): summaries of each session, so its namespace must include {sessionId}. Besides summary chunks it keeps one full-session recap record (FULL_SESSION), updated as the session continues.
  • Episodic (episodicMemoryStrategy, December 2025): records each completed episode (situation, intent, outcome and lessons) and writes reflections across episodes. Include tool results in events for it to work well. A reflection namespace broader than the actor (such as /strategy/{memoryStrategyId}/) shares lessons across all users, which is a privacy decision.

Up to 6 strategies per memory. Built-in with overrides lets you append instructions to the extraction prompt and choose the Bedrock model, which runs in your account through memoryExecutionRoleArn (cheaper record storage, but you pay the model tokens and use your Bedrock quotas). Self-managed strategies deliver batches of events to your S3 bucket and SNS topic, and your own pipeline writes records back with BatchCreateMemoryRecords.

Namespaces

A namespace is a path like /users/{actorId}/preferences/, with one leading and one trailing slash. Built-in variables are {actorId}, {sessionId} and {memoryStrategyId}. Each strategy takes exactly one template in namespaceTemplates (the older namespaces field is deprecated). Since August 2026 you can declare up to 5 custom variables (namespaceKeys, lowercase) and pass their values on each event in extractionConfig.namespaceVariables, for example a tenant or project. If a value is missing, the event is stored but extraction for that strategy is silently skipped; only the NamespaceResolutionFailure metric tells you.

Using Memory with boto3

Create a memory, write a turn, reload the session and search long-term records (Python, boto3; field names from the API reference) 
import time
from datetime import datetime, timezone

import boto3

ctl = boto3.client("bedrock-agentcore-control", region_name="us-west-2")
dp = boto3.client("bedrock-agentcore", region_name="us-west-2")

mem = ctl.create_memory(
    # Letters, digits and underscores only
    name="SupportAgentMemory",
    # Days to keep raw events
    eventExpiryDuration=30,
    memoryStrategies=[
        {"userPreferenceMemoryStrategy": {
            "name": "Preferences",
            "namespaceTemplates": ["/users/{actorId}/preferences/"],
        }},
        {"summaryMemoryStrategy": {
            "name": "SessionSummary",
            "namespaceTemplates": ["/summaries/{actorId}/{sessionId}/"],
        }},
    ],
)["memory"]
while (status := ctl.get_memory(memoryId=mem["id"])["memory"]["status"]) not in ("ACTIVE", "FAILED"):
    time.sleep(10)

# Short-term: one event per turn
dp.create_event(
    memoryId=mem["id"],
    actorId="user-123",
    sessionId="session-0001",
    eventTimestamp=datetime.now(timezone.utc),
    payload=[
        {"conversational": {"role": "USER", "content": {"text": "I prefer aisle seats."}}},
        {"conversational": {"role": "ASSISTANT", "content": {"text": "Noted: aisle seats."}}},
    ],
)

# Reload this session's recent events
events = dp.list_events(memoryId=mem["id"], actorId="user-123", sessionId="session-0001", maxResults=20)["events"]

# Later: search this user's long-term records (exact namespace, or namespacePath for a subtree)
hits = dp.retrieve_memory_records(
    memoryId=mem["id"],
    namespace="/users/user-123/preferences/",
    searchCriteria={"searchQuery": "seat preference", "topK": 5},
)["memoryRecordSummaries"]
for h in hits:
    print(round(h["score"], 3), h["content"]["text"])
  • ListEvents doesn't guarantee newest first: sort by eventTimestamp if order matters.
  • ListMemoryRecords lists records without a query; GetMemoryRecord and DeleteMemoryRecord handle one record; batch create, update and delete take up to 100 (check failedRecords even on success).
  • The AgentCore CLI creates memories too (agentcore add memory --name X --strategies SEMANTIC,SUMMARIZATION) and inspects them (agentcore memory record list --namespace-path /), but can't change strategies on an existing memory.

Memory in agent frameworks

The bedrock-agentcore SDK's recommended interface is MemorySessionManager (sessions with add_turns and search_long_term_memories); the older MemoryClient is labelled legacy. For Strands, a session manager restores history and injects relevant long-term records into the prompt automatically.

A Strands agent with short-term history and long-term retrieval (Python, AgentCore SDK) 
from bedrock_agentcore.memory.integrations.strands.config import AgentCoreMemoryConfig, RetrievalConfig
from bedrock_agentcore.memory.integrations.strands.session_manager import AgentCoreMemorySessionManager
from strands import Agent

config = AgentCoreMemoryConfig(
    memory_id="MEMORY_ID",
    # Your backend maps the signed-in user to this
    actor_id="user-123",
    session_id="session-0001",
    # Keys are the strategies' namespace templates
    retrieval_config={
        "/users/{actorId}/preferences/": RetrievalConfig(top_k=5, relevance_score=0.5),
        "/summaries/{actorId}/{sessionId}/": RetrievalConfig(top_k=3),
    },
    # Buffer writes; the with block flushes them on exit
    batch_size=10,
)
with AgentCoreMemorySessionManager(config, region_name="us-west-2") as session_manager:
    agent = Agent(system_prompt="You are a travel assistant.", session_manager=session_manager)
    agent("Book me a flight to Lisbon next Friday.")

With batch_size above 1, always use the with block or call close(): buffered messages are lost otherwise. For LangGraph, the langgraph-checkpoint-aws package provides AgentCoreMemorySaver (checkpoints as events) and AgentCoreMemoryStore (long-term records). The Harness manages a memory for you by default.

More Memory features

  • Direct ingestion (IngestData, August 2026): send content straight to long-term extraction without storing it as an event, for example importing a CRM profile. Up to 100 KB per request, 10 requests per second per account.
  • Metadata filtering (April 2026): declare up to 10 indexedKeys (string, string list or number; they can never be removed), give strategies a metadata schema the model fills in or, for up to 3 keys, copies exactly from event metadata, then filter retrievals with operators such as EQUALS_TO, CONTAINS and AFTER. AWS's advice: use namespaces for who, metadata for what, when and how urgent; never metadata alone for tenant isolation.
  • Record expiry (October 2026): recordExpirySpecification with at least 31 days, for new records only; deletion can lag by a few days, so use DeleteMemoryRecord when removal must be immediate. It needs the separate permission UpdateMemoryRecordExpirySpecification. By default records never expire.
  • Streaming (March 2026): push record created, updated and deleted events (full content or metadata only) to a Kinesis data stream, for example to replicate long-term memory to another Region.
  • Failed extraction: ListMemoryExtractionJobs shows failures (often throttling, or model access for override strategies) and StartMemoryExtractionJob retries them.
  • Sharing and encryption: resource-based policies allow cross-account access (June 2026; callers pass the full memory ARN); a customer managed KMS key encrypts content, but event metadata isn't encrypted with it, so keep sensitive data out of metadata.

Separating users, quotas and cost

Memory only sees the calling IAM principal. If one backend role reads and writes memory for every user, a bug in actorId or a namespace shows one user another's memories. Constrain access with the condition keys bedrock-agentcore:actorId, sessionId, namespace and namespacePath (per-user IAM sessions), or put Memory behind a Gateway with its Memory connector and a Cedar policy that requires actorId to equal the JWT's sub, plus a resource policy that blocks direct access. Namespaces in IAM conditions must keep their slashes (/users/alice/*).

  • Quotas: 150 memories per Region (adjustable), 6 strategies per memory; CreateEvent up to 100 messages, 100 KB per message, 200 per second per account and 5 per second per actor and session; RetrieveMemoryRecords 30 per second; long-term extraction 150,000 tokens per minute per account for built-in strategies.
  • Short-term pricing (since 6 October 2026): $1.00 per GB ingested, $0.20 per GB retrieved, $0.10 per GB-month stored. Each event is billed as at least 12 KB and at most 64 KB for ingestion and retrieval, so several messages in one event cost less than many tiny events.
  • Long-term pricing: $0.75 per 1,000 records per month (built-in), $0.25 with overrides or self-managed (plus your model costs), and $0.50 per 1,000 retrieval calls, which usually dominate.
  • Metrics: latency, invocations, errors and throttles, plus TokenCount, FailedExtraction and NamespaceResolutionFailure.

Code Interpreter

Code Interpreter runs code the agent writes in an isolated microVM per session (2 vCPU, 8 GB), in Python, JavaScript or TypeScript (runtimes python, nodejs or deno, the default for JavaScript and TypeScript). Variables and files persist for the session. Python comes with pandas, numpy, matplotlib, scikit-learn, torch, requests and many more; install others with a command.

  • AWS-managed aws.codeinterpreter.v1 needs no set-up. A custom interpreter (CreateCodeInterpreter) chooses the network: SANDBOX (limited access, but still reaches Amazon S3), PUBLIC or VPC, plus an execution role for AWS calls, root certificates and EFS or S3 Files mounts.
  • Tools you invoke: executeCode, executeCommand, writeFiles, readFiles, listFiles, removeFiles, and startCommandExecution with getTask and stopTask for long commands. Inline uploads up to 100 MB; up to 5 GB through S3.
  • Sessions default to 15 minutes and can run up to 8 hours; they bill until stopped or timed out.
Upload a file and run pandas on it; the session always stops (Python, AgentCore SDK) 
from bedrock_agentcore.tools.code_interpreter_client import code_session

with code_session("us-west-2") as ci:
    ci.invoke("writeFiles", {"content": [{"path": "data.csv", "text": "a,b\n1,2\n3,4\n"}]})
    out = ci.invoke("executeCode", {
        "language": "python",
        "code": "import pandas as pd\nprint(pd.read_csv('data.csv').sum())",
    })
    for event in out["stream"]:
        print(event["result"])

Without the SDK: start_code_interpreter_session, invoke_code_interpreter(name="executeCode", arguments={...}) (results arrive as a stream of content blocks with stdout, stderr and exit code) and stop_code_interpreter_session on the bedrock-agentcore client. In Strands, add AgentCoreCodeInterpreter(region="us-west-2").code_interpreter from strands_tools.code_interpreter as a tool. Pricing is the Runtime V1 rate: $0.0895 per vCPU-hour and $0.00945 per GB-hour, no CPU charge while waiting; AWS's example of a 2-minute run costs about $0.0036. Up to 1,000 concurrent sessions per account.

Browser

Browser is a managed Chrome in its own microVM per session (1 vCPU, 4 GB), driven over the Chrome DevTools Protocol by Playwright, browser-use, Nova Act or the Strands browser tool. Use aws.browser.v1, or create a custom browser for VPC networking, session recording to S3, Web Bot Auth signing (preview) and enterprise policies.

Drive the browser with Playwright and print a live-view link (Python, AgentCore SDK) 
import asyncio

from bedrock_agentcore.tools.browser_client import browser_session
from playwright.async_api import async_playwright


async def main():
    with browser_session("us-west-2", viewport={"width": 1280, "height": 800}) as client:
        # A SigV4-signed WebSocket URL and headers for the automation stream
        ws_url, headers = client.generate_ws_headers()
        print("Live view:", client.generate_live_view_url(expires=300))
        async with async_playwright() as pw:
            browser = await pw.chromium.connect_over_cdp(ws_url, headers=headers)
            page = browser.contexts[0].pages[0]
            await page.goto("https://example.com")
            print(await page.title())
            await browser.close()
    # Leaving the with block stops the session and its billing


asyncio.run(main())
  • Live view lets a person watch (the presigned link lasts up to 5 minutes); take control (take_control(), or UpdateBrowserStream disabling automation) hands the session to a human, for example to type a password the agent should never see.
  • OS-level actions (InvokeBrowser, April 2026): mouse clicks, drags and scrolls, key presses and shortcuts, and full-screen PNG screenshots, for native dialogs and menus that CDP can't reach.
  • Profiles (February 2026) save cookies and local storage after a login for later sessions; proxies (HTTP and HTTPS, up to 5 per session) route traffic but aren't a network control; extensions (up to 10, 10 MB each), Chrome enterprise policies and custom root certificates (March 2026) customize the browser.
  • Set sessionTimeoutSeconds explicitly (up to 8 hours): AWS's pages disagree on the default. Same pricing as Code Interpreter; AWS's example 10-minute session at 80% I/O wait costs about $0.012.

Web Search and Web Answer

Both are used only as Gateway connectors: agents call them as MCP tools through a gateway, and the gateway role needs bedrock-agentcore:InvokeWebSearch or InvokeWebAnswer. Queries stay within AWS, backed by an Amazon web index.

  • Web Search (June 2026; 7 Regions including GovCloud): a query up to 200 characters, 1 to 25 results, domain include and exclude lists (up to 100 each, also fixed at the target level where the agent can't widen them) and published-date filters. Results arrive as a JSON string in content[0].text with text, URL, title and date: parse it. $7 per 1,000 queries; 10 per second. The SDK's WebSearchClient wraps the gateway call.
  • Web Answer (5 November 2026; us-east-1 only, geographic cross-Region inference): one call runs a search agent and returns a finished markdown answer with citations. $10 per 1,000 calls. Use it when you want a cited answer to a sub-question without filling your own context with search results.
  • Both require you to show the source citations to end users and forbid bulk copying of results.

Payments

AgentCore Payments (generally available 18 August 2026) lets agents pay for paid APIs, MCP servers and content with stablecoin micropayments over HTTP 402 protocols (x402, and the Machine Payments Protocol). You create a payment manager and a connector to a wallet provider (Coinbase CDP, which needs an AWS Marketplace subscription, or Stripe Privy); each user gets a wallet they fund; and each payment session has a spending limit (maxSpendAmount) and an expiry of 15 to 480 minutes enforced by AWS. When an agent hits a 402, the SDK plugin calls ProcessPayment within the session's budget and retries. AgentCore charges nothing; the wallet provider charges per operation. Keep the roles that set budgets separate from those that spend.

What's changed

  • November 2026: Web Answer connector (us-east-1).
  • October 2026: short-term memory moved to consumption pricing (6 October); record expiry; Web Search in more Regions and connector 1.3.0.
  • August 2026: JSON payloads, IngestData and custom namespace variables; Memory in GovCloud (US-West); Payments generally available (18 August); Web Search date and domain filters.
  • June 2026: strictly consistent metadata (15 June); Web Search (16 June); Harness managed memory by default (17 June); Memory cross-account access (23 June).
  • March to May 2026: Memory resource policies and record streaming; Code Interpreter Node.js runtime; Browser enterprise policies and root certificates (March); metadata filtering and Browser OS actions (April); Payments preview (7 May).
  • December 2025 to February 2026: episodic memory (2 December); Browser extensions, profiles and proxies (January to February).
  • 2025: preview (16 July); generally available (13 October); Web Bot Auth preview (30 October).
