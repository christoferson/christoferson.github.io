Observability, Evaluations and Optimization

Running agents in production: trace every model and tool call in CloudWatch, score real sessions with LLM judges and code, then turn the scores into better prompts and tool descriptions, proven with an A/B test before you ship them.

One data path, three layers

  1. ObserveYour agent emits OpenTelemetry spans and logs (through the AWS Distro for OpenTelemetry, ADOT) into CloudWatch, which shows sessions, traces and metrics.
  2. EvaluateEvaluators (LLM judges, Lambda functions or programmatic matchers) read those spans from CloudWatch and write scores back as logs and metrics.
  3. OptimizeRecommendations read the traces and scores and propose a better system prompt or tool descriptions; you store them as versioned configuration bundles and prove them with an A/B test through Gateway.

This works for agents on Runtime or the Harness and for agents hosted elsewhere (ECS, EKS, Lambda, outside AWS) that export ADOT telemetry to CloudWatch. For scoring models, prompts and Knowledge Bases on a fixed dataset, see Model and RAG evaluation.

Turning on observability

Step 1: CloudWatch Transaction Search (once per account and Region)

Without it there are no AgentCore spans, and evaluations and A/B tests return nothing. agentcore deploy turns it on for you (opt out with agentcore config transactionSearch false); otherwise run:

Let X-Ray write spans to CloudWatch Logs, then switch the destination (AWS CLI, as in the AgentCore and CloudWatch guides) 
aws logs put-resource-policy --policy-name TransactionSearchXRayAccess --policy-document '{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "TransactionSearchXRayAccess",
    "Effect": "Allow",
    "Principal": {"Service": "xray.amazonaws.com"},
    "Action": "logs:PutLogEvents",
    "Resource": [
      "arn:aws:logs:us-west-2:111111111111:log-group:aws/spans:*",
      "arn:aws:logs:us-west-2:111111111111:log-group:/aws/application-signals/data:*"
    ],
    "Condition": {
      "ArnLike": {"aws:SourceArn": "arn:aws:xray:us-west-2:111111111111:*"},
      "StringEquals": {"aws:SourceAccount": "111111111111"}
    }
  }]
}'

aws xray update-trace-segment-destination --destination CloudWatchLogs

# Optional: index 1% of spans as trace summaries (free); all spans are still stored
aws xray update-indexing-rule --name "Default" --rule '{"Probabilistic": {"DesiredSamplingPercentage": 1}}'

Spans take about 10 minutes to become searchable after enabling. To encrypt aws/spans with your KMS key when the log group already exists, enable without a key and then associate the key with the log group.

Step 2: agents on Runtime or the Harness

The Harness emits traces, logs and metrics automatically. Agents deployed to Runtime with the CLI are instrumented for you; in your own container add aws-opentelemetry-distro>=0.18.0 and start with opentelemetry-instrument python main.py, with a framework that emits OpenTelemetry (Strands does natively). The session header you send on invoke becomes session.id on every span. To send telemetry to another platform (Langfuse, Datadog and others), set DISABLE_ADOT_OBSERVABILITY=true and your own OTLP endpoint.

Step 3: agents hosted elsewhere

Environment for an agent on ECS, EKS or a server (as in the AgentCore observability configuration page; create the log group first) 
AGENT_OBSERVABILITY_ENABLED=true
OTEL_PYTHON_DISTRO=aws_distro
OTEL_PYTHON_CONFIGURATOR=aws_configurator
OTEL_RESOURCE_ATTRIBUTES=service.name=orders-agent,aws.log.group.names=/aws/bedrock-agentcore/runtimes/orders-agent
OTEL_EXPORTER_OTLP_LOGS_HEADERS=x-aws-log-group=/aws/bedrock-agentcore/runtimes/orders-agent,x-aws-log-stream=runtime-logs,x-aws-metric-namespace=bedrock-agentcore
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_TRACES_EXPORTER=otlp
# Keep model inputs and outputs and tool I/O on spans (needed for evaluations)
AWS_GENAI_CONTENT_EXTRACTION_OPT_OUT=true

Then run opentelemetry-instrument python agent.py (on Lambda, use the OpenTelemetry Lambda layer with AWS_LAMBDA_EXEC_WRAPPER=/opt/otel-instrument). Outside Runtime there's no session header, so set the session yourself:

Tag every span of a conversation with its session ID (Python, OpenTelemetry) 
from opentelemetry import baggage, context

token = context.attach(baggage.set_baggage("session.id", session_id))
try:
    result = agent(prompt)
finally:
    context.detach(token)

LangChain and LangGraph are instrumented through opentelemetry-instrumentation-langchain or OpenInference; other frameworks through OpenInference, OpenLLMetry, OpenLit or Traceloop. Add your own spans with trace.get_tracer(...).start_as_current_span(...) and business attributes, which become searchable.

Other components

Runtime creates its log group automatically. For Memory, Gateway and the built-in tools, enable log delivery (application logs to CloudWatch Logs, S3 or Firehose; default groups under /aws/vendedlogs/bedrock-agentcore/) and tracing per resource, in the console or with CloudWatch Logs delivery APIs. Runtime application logs include the request payload but not the response.

Where the data lands

  • Agent log group: /aws/bedrock-agentcore/runtimes/AGENT_ID-ENDPOINT, with stdout and stderr, OpenTelemetry log records (AWS's pages name the stream runtime-logs or otel-rt-logs), and, for agents created since 20 July 2026, a spans stream. Older agents send spans to the shared aws/spans group unless you set UNIFIED_TRACES_DESTINATION_ENABLED=true (needs ADOT 0.18.0 or later and logs:PutResourcePolicy on the execution role).
  • Consoles: the AgentCore observability page and CloudWatch GenAI Observability show agents, sessions, traces (with trajectory diagrams and timelines) and spans, plus Memory, Gateway, tools and Identity. agentcore dev opens a local inspector.
  • Metrics (namespace AWS/Bedrock-AgentCore, on by default): Runtime Invocations, Latency, Throttles, SystemErrors, UserErrors, SessionCount, ActiveSessionCount, CPU and memory used, and OverheadLatency on V2; Gateway latency, target execution time and errors per tool; Memory extraction tokens and failures; Identity token fetches; Policy allow and deny decisions. Your agent's own metrics go to bedrock-agentcore, evaluation scores to Bedrock-AgentCore/Evaluations.
  • Cross-account (April 2026): link source accounts to a monitoring account with CloudWatch cross-account observability to see agents, traces and evaluation results in one place, within a Region.
  • Cost: CloudWatch rates. AWS's example: about 10 million spans a month (200,000 invocations) cost about $6.50 in ingestion. Filter or redact spans with span processors to control cost and personal data.
Alarm on gateway errors (AWS CLI) 
aws cloudwatch put-metric-alarm --alarm-name orders-gateway-errors \
  --namespace AWS/Bedrock-AgentCore --metric-name SystemErrors --statistic Sum \
  --dimensions Name=Resource,Value=GATEWAY_ARN --period 300 --evaluation-periods 1 \
  --threshold 5 --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-west-2:111111111111:agent-alerts

Evaluators

AgentCore Evaluations (generally available 31 March 2026) scores agents at three levels: session (a whole conversation), trace (one request and response) and tool call.

Built-in evaluators

  • Session: Builtin.GoalSuccessRate (yes or no; optional assertions as ground truth), and programmatic trajectory matchers Builtin.TrajectoryExactOrderMatch, TrajectoryInOrderMatch and TrajectoryAnyOrderMatch, which compare the tools called with an expected list and use no model.
  • Trace: Builtin.Correctness (optional expected response), Faithfulness, Helpfulness, ResponseRelevance, Coherence, Conciseness, InstructionFollowing, Refusal, Harmfulness and Stereotyping.
  • Tool call: Builtin.ToolSelectionAccuracy and ToolParameterAccuracy; for skills (August 2026), SkillSelectionAccuracy and SkillInstructionFollowing.
  • Failure analysis (October 2026, batch only): Builtin.FailureAnalysis finds failures in each session, traces their root causes and groups them across sessions with suggested fixes. A score of 1.0 means failures were found, so higher is worse.

Built-in evaluators use AWS-managed judge models through cross-Region inference within your geography (global in a few Regions); their prompts can't be changed. List the exact IDs available to you with aws bedrock-agentcore-control list-evaluators. Third-party evaluators (August 2026) add ThirdParty.DeepEval.* metrics (bias, toxicity, PII leakage, task completion, knowledge retention and more) and ThirdParty.AutoEval.*.

Custom evaluators

An LLM judge that compares answers with an expected response (Python, boto3; shape from the API reference) 
import boto3

ctl = boto3.client("bedrock-agentcore-control", region_name="us-west-2")
ctl.create_evaluator(
    evaluatorName="ResponseSimilarity",
    level="TRACE",
    evaluatorConfig={"llmAsAJudge": {
        # Must include placeholders for the level; the service adds the output format
        "instructions": (
            "Compare the agent's actual response to the expected response.\n\n"
            "Context:\n{context}\n\nActual:\n{assistant_turn}\n\nExpected:\n{expected_response}"
        ),
        "ratingScale": {"numerical": [
            {"label": "No Match", "value": 0.0, "definition": "Contradicts or unrelated"},
            {"label": "High Similarity", "value": 0.67, "definition": "Covers most key points"},
            {"label": "Exact Match", "value": 1.0, "definition": "Semantically equivalent"},
        ]},
        "modelConfig": {"bedrockEvaluatorModelConfig": {
            "modelId": "global.anthropic.claude-sonnet-5-5",
            "inferenceConfig": {"maxTokens": 512},
        }},
    }},
)
  • Code evaluators: {"codeBased": {"lambdaConfig": {"lambdaArn": ..., "lambdaTimeoutInSeconds": 60}}}. The Lambda receives the session's spans and the target trace or span IDs, and returns {"label": "PASS", "value": 1.0, "explanation": "..."}. Use them for deterministic checks (format, policy rules, calling your own systems).
  • Multi-dimension (October 2026): one judge call scores up to 50 named dimensions. Derived evaluators run a built-in or third-party evaluator's logic on your own model, in your account.
  • Rating scales are numerical, categorical or multi-dimensional. Only evaluators returning a numeric value can drive recommendations and A/B tests, so a pass-fail categorical scale won't do there.
  • Evaluators that use ground truth ({expected_response}, assertions, expected trajectory) can't run online, because production traffic has no expected answers.

Online evaluation

An online evaluation configuration samples completed sessions from production logs and scores them continuously.

Score 10% of production sessions for goal success and helpfulness (Python, boto3) 
ctl.create_online_evaluation_config(
    # Letters, digits and underscores only
    onlineEvaluationConfigName="orders_agent_prod",
    dataSourceConfig={"cloudWatchLogs": {
        "logGroupNames": ["/aws/bedrock-agentcore/runtimes/OrdersAgent-AbCdEf1234-DEFAULT"],
        # Runtime agents: RUNTIME_NAME.ENDPOINT; elsewhere: your OTEL service.name
        "serviceNames": ["OrdersAgent.DEFAULT"],
    }},
    evaluators=[{"evaluatorId": "Builtin.GoalSuccessRate"}, {"evaluatorId": "Builtin.Helpfulness"}],
    rule={
        "samplingConfig": {"samplingPercentage": 10.0},
        # A session is complete after this much inactivity
        "sessionConfig": {"sessionTimeoutMinutes": 15},
    },
    evaluationExecutionRoleArn="arn:aws:iam::111111111111:role/AgentCoreEvaluationRole",
    enableOnCreate=True,
)
  • Up to 25 evaluators, sampling from 0.01% to 100%, and up to 5 filters on span attributes (for example only attributes.customer_tier equal to enterprise).
  • Results are log events in /aws/bedrock-agentcore/evaluations/results/CONFIG_ID (or the source or your own log group) and metrics you can alarm on; the agent's Evaluations tab in CloudWatch GenAI Observability charts them.
  • The execution role (trusted by bedrock-agentcore.amazonaws.com) queries the agent's logs, writes results, and invokes models for custom judges; the console and CLI can create it.
  • Custom evaluators used by an enabled configuration are locked: disable the configuration or clone the evaluator to change it. CLI: agentcore eval online-eval create --name N --agent ID --evaluators Builtin.GoalSuccessRate --sampling-rate 10, then pause, resume and logs.

"No spans were found for the session" usually means the serviceNames value doesn't match (it's RUNTIME_NAME.ENDPOINT such as OrdersAgent.DEFAULT on Runtime), Transaction Search is off, the session ID isn't on the spans, or you didn't wait: allow 2 to 5 minutes after an invocation before evaluating it.

On-demand and batch evaluation

  • On demand (Evaluate on the bedrock-agentcore client): synchronous, one evaluator and one session per call, up to 10 results returned (the last 10 traces or tool calls by default). You fetch the session's spans from CloudWatch Logs yourself, or let the SDK's EvaluationClient(region_name=...).run(evaluator_ids=[...], session_id=..., agent_id=...) collect them and batch the calls. Pass evaluationReferenceInputs for ground truth. CLI: agentcore eval ondemand evaluate --agent ID --session-ids S --evaluators Builtin.Helpfulness.
  • Batch (generally available June 2026, StartBatchEvaluation): scores up to 500 sessions from a time range or a list of session IDs with up to 10 evaluators, runs under the caller's credentials (no service role), and returns per-evaluator average scores, plus failure-analysis insights. Ground truth per session goes in evaluationMetadata.sessionMetadata. It costs 25% less than online evaluation. Run one batch before and one after a change and compare the averages.
  • Datasets and user simulation (datasets in preview): store scenarios (turns with expected responses, assertions, expected trajectories) as versioned datasets, let the SDK runners invoke your agent on them and evaluate, or have an LLM play the user with a goal and profile (bedrock-agentcore[simulation]) to test multi-turn behaviour before launch.

Evaluations parses traces from Strands, LangGraph, OpenAI Agents SDK, LlamaIndex, Google ADK, Claude Agent SDK and Vercel AI SDK, in Python and TypeScript, and any OpenTelemetry or OpenInference instrumentation that follows the generative AI conventions.

Optimization

Recommendations

StartRecommendation (generally available 17 June 2026) analyses recent traces against exactly one numeric evaluator (for example Builtin.GoalSuccessRate for task agents) and returns a recommended system prompt with an explanation; tool-description recommendations need no evaluator and suggest clearer descriptions where the agent picks the wrong tools. Traces come from CloudWatch Logs (by log group ARN, not name), inline spans, or an existing batch or online evaluation. Nothing changes automatically: you review and apply. Generating recommendations is free.

Configuration bundles

A configuration bundle is a versioned snapshot of an agent's dynamic settings (system prompt, model, temperature, tool descriptions, any JSON), keyed by Runtime or Gateway ARN, with git-like versions and branches. Updates must name the latest version as parent. With SDK 1.8 or later, the agent reads the active version from request baggage through BedrockAgentCoreContext.get_config_bundle() (returning {} when none is set), so a prompt changes without redeploying; in Strands, apply it in a hook before each model call. Gateway applies tool-description overrides from a bundle on tools/list.

A/B tests

  • CreateABTest on a gateway splits traffic between exactly two variants (C control and T1 treatment): two configuration bundle versions on the same agent, or two gateway targets (different agents or endpoints). Assignment is sticky per session ID; one test per gateway.
  • An online evaluation configuration (at 100% sampling during the test) scores both variants; results show sample size, mean, change, p-value, a 95% confidence interval and a significance flag per evaluator, about 15 minutes after sessions end. Check every evaluator: one can regress while another improves.
  • After stopping the test, route all traffic to the winner with a Gateway rule (AWS CLI create-gateway-rule). For a bundle test, add a configurationBundle.staticOverride rule even if the control won, because the agent's built-in prompt isn't the control bundle.
  • There's no A/B fee: you pay for the gateway calls, Runtime and evaluations used.

Status change. The preview Insights feature (failure, user-intent and execution-summary reports, including recurring reports) stopped accepting new jobs on 16 October 2026 and stopped recurring reports on 31 October 2026. Use the Builtin.FailureAnalysis evaluator in batch evaluation instead. Many code tabs in AWS's guide still use the retired Python starter toolkit and pre-1.0 CLI commands: use agentcore eval ... (CLI 1.0) and the bedrock_agentcore SDK.

Quotas, pricing and Regions

  • Evaluations pricing: built-in evaluators $0.0024 per 1,000 input tokens and $0.012 per 1,000 output tokens (model included); custom evaluators $1.50 per 1,000 evaluations plus your model or Lambda cost; batch 25% less. Each evaluation sends the whole relevant context, so tokens add up: AWS's example of 45,000 built-in evaluations at 15,000 input tokens each costs about $1,782 a month. Sample online traffic (1 to 10%) and use batch for regression runs.
  • Quotas: 1,000 online configurations, 25 evaluators each; built-in evaluations up to 1,000,000 input tokens and 1,200 evaluations per minute; on-demand 20,000 spans and one evaluator per call; batch 5 active jobs, 500 sessions and 10 evaluators per job; 10,000 custom evaluators; 5 active recommendations; 20 active A/B tests; 1,000 configuration bundles.
  • Regions: Evaluations in all AgentCore Regions including GovCloud (US-West); optimization in the commercial Regions only.

What's changed

  • October to November 2026: multi-dimension evaluators; Builtin.FailureAnalysis in batch evaluation; Insights preview retired (16 and 31 October); CLI 1.0 with evaluation commands under agentcore eval and Transaction Search on by default; OverheadLatency metric for Runtime V2.
  • September 2026: evaluations for TypeScript agents (Strands, LangGraph, OpenAI Agents, Vercel AI SDK).
  • August 2026: third-party and derived evaluators; skill evaluators.
  • July 2026: more frameworks for evaluations; per-agent span log groups by default for new agents (from 20 July); ActiveSessionCount metric; PrivateLink for evaluations and optimization.
  • June 2026: recommendations, batch evaluation and A/B tests generally available (17 June).
  • March to April 2026: Evaluations generally available with code evaluators and ground truth (31 March); one-click observability for Memory and Gateway; cross-account observability and trace UI improvements (April); optimization preview (30 April).
  • 2025: Observability in preview (16 July) and generally available (13 October); Evaluations preview (2 December).
