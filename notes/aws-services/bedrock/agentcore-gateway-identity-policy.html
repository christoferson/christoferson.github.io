Gateway, Identity and Policy

How agents reach tools safely: Gateway turns your APIs, Lambda functions and MCP servers into one governed MCP endpoint; Identity authenticates users and holds the OAuth tokens and API keys agents use downstream; Policy decides, outside the agent's code, which tool calls are allowed.

How the three fit together

  1. InboundA user signs in to your app; the agent (on Runtime, the Harness or anywhere) calls the gateway with the user's JWT or with IAM credentials. The gateway's authorizer checks it.
  2. DiscoverThe agent lists tools (or searches them) through one MCP endpoint that combines every target.
  3. AuthorizeFor each tool call, the Policy engine attached to the gateway evaluates the caller, the tool and its arguments, and denies unless a policy permits.
  4. OutboundThe gateway calls the target with its IAM role, or with an OAuth token or API key that Identity fetches from its token vault for this user.
  5. RecordMetrics, logs, traces and CloudTrail data events show what happened.

Gateway concepts

Three kinds of target

  • MCP targets are combined into one virtual MCP server with a single tool list: Lambda functions (you supply tool schemas), OpenAPI 3.0 or 3.1 specs (each operationId becomes a tool), Smithy models, API Gateway REST API stages (same account and Region), remote MCP servers (tools, prompts and resources are synchronized), and built-in connectors: Managed Knowledge Bases, Web Search, Web Answer (us-east-1 only) and Step Functions.
  • HTTP targets pass requests through unchanged, routed by path (/TARGET/...): an AgentCore Runtime agent, an A2A agent, an external MCP server or any HTTPS endpoint. No tool aggregation or search.
  • Inference targets make the gateway an LLM proxy at /inference, routing by model to Bedrock, OpenAI, Anthropic or compatible providers, with model fallback (October 2026). Callers then need only bedrock-agentcore:InvokeGateway, not Bedrock permissions.

Tools are named TARGET___TOOL with three underscores (for example Orders___get_order). Your Lambda receives the full name and must strip the prefix, and policies use the full name.

Inbound and outbound auth

  • Inbound (authorizerType): CUSTOM_JWT (tokens from your IdP, configured like Runtime's JWT authorizer), AWS_IAM (SigV4), AUTHENTICATE_ONLY (checks the SigV4 signature but authorizes nothing) or NONE (development only).
  • Outbound (one credentialProviderConfigurations entry per target): GATEWAY_IAM_ROLE (the gateway's role; the only option for Lambda and connectors), OAUTH (client credentials, authorization code for user consent, or token exchange), API_KEY (header or query parameter), CALLER_IAM_CREDENTIALS (forward the caller's IAM identity) and JWT_PASSTHROUGH (HTTP targets).

The gateway's IAM role is shared by every target that uses GATEWAY_IAM_ROLE, so it's the ceiling of what any caller can do through that gateway. Use separate gateways for separate trust boundaries. And NONE or AUTHENTICATE_ONLY gateways make no authorization decision: without a Policy engine, anyone who can reach them can call every tool.

Creating a gateway and a target

A JWT-protected MCP gateway with semantic search and a Lambda target (Python, boto3; field names from the API reference) 
import time

import boto3

ctl = boto3.client("bedrock-agentcore-control", region_name="us-west-2")

gw = ctl.create_gateway(
    # Letters, digits and single hyphens, up to 48 characters
    name="orders-gateway",
    roleArn="arn:aws:iam::111111111111:role/OrdersGatewayRole",
    # MCP only; omit protocolType to allow HTTP targets too
    protocolType="MCP",
    authorizerType="CUSTOM_JWT",
    authorizerConfiguration={"customJWTAuthorizer": {
        "discoveryUrl": "https://cognito-idp.us-west-2.amazonaws.com/USER_POOL_ID/.well-known/openid-configuration",
        # Cognito access tokens have client_id but no aud
        "allowedClients": ["APP_CLIENT_ID"],
    }},
    protocolConfiguration={"mcp": {
        "supportedVersions": ["2025-11-25"],
        "searchType": "SEMANTIC",
        "instructions": "Order tools for the support agent.",
    }},
)
gateway_id, gateway_url = gw["gatewayId"], gw["gatewayUrl"]
while ctl.get_gateway(gatewayIdentifier=gateway_id)["status"] != "READY":
    time.sleep(5)

ctl.create_gateway_target(
    gatewayIdentifier=gateway_id,
    # Tools become Orders___get_order
    name="Orders",
    targetConfiguration={"mcp": {"lambda": {
        "lambdaArn": "arn:aws:lambda:us-west-2:111111111111:function:orders-tools",
        "toolSchema": {"inlinePayload": [{
            "name": "get_order",
            "description": "Look up one order by its ID",
            "inputSchema": {
                "type": "object",
                "properties": {"orderId": {"type": "string"}},
                "required": ["orderId"],
            },
        }]},
    }}},
    # Exactly one entry; Lambda targets accept only the gateway role
    credentialProviderConfigurations=[{"credentialProviderType": "GATEWAY_IAM_ROLE"}],
)
The Lambda function behind the target (Python) 
def lambda_handler(event, context):
    # The event is the tool's arguments; the tool name arrives in the client context
    full_name = context.client_context.custom["bedrockAgentCoreToolName"]
    tool = full_name.split("___", 1)[1]
    if tool == "get_order":
        return {"orderId": event["orderId"], "status": "SHIPPED"}
    return {"error": f"unknown tool {tool}"}
  • The client context also carries the gateway ID, target ID, MCP message ID and request ID. The gateway role needs lambda:InvokeFunction on the function; its trust policy should add aws:SourceAccount and aws:SourceArn conditions for your gateway.
  • For an MCP server target use {"mcp": {"mcpServer": {"endpoint": "https://..."}}} with OAuth or an API key; tools are synchronized on create and update (or call SynchronizeGatewayTargets). For OpenAPI, pass the spec inline or from S3; only JSON bodies, no oneOf/anyOf/allOf, and the gateway blocks private IP addresses.
  • UpdateGateway is a full replacement: resend the name, role, authorizer type and configuration. While developing, exceptionLevel="DEBUG" returns detailed errors.

Calling a gateway

The MCP endpoint is the gatewayUrl: https://GATEWAY_ID.gateway.bedrock-agentcore.REGION.amazonaws.com/mcp (DNS can take a minute after creation). Clients send Accept: application/json, text/event-stream and, for JWT gateways, a bearer token.

A Strands agent using the gateway's tools (Python; tool listing is paginated) 
from mcp.client.streamable_http import streamablehttp_client
from strands import Agent
from strands.models import BedrockModel
from strands.tools.mcp.mcp_client import MCPClient

GATEWAY_URL = "https://GATEWAY_ID.gateway.bedrock-agentcore.us-west-2.amazonaws.com/mcp"
TOKEN = get_user_access_token()

mcp = MCPClient(lambda: streamablehttp_client(GATEWAY_URL, headers={"Authorization": f"Bearer {TOKEN}"}))
with mcp:
    tools, page = [], None
    while True:
        batch = mcp.list_tools_sync(pagination_token=page)
        tools.extend(batch)
        page = batch.pagination_token
        if page is None:
            break
    agent = Agent(model=BedrockModel(model_id="global.anthropic.claude-sonnet-5-5"), tools=tools)
    agent("Where is order 12345?")
  • IAM gateways: swap the transport for SigV4 signing from the mcp-proxy-for-aws package: aws_iam_streamablehttp_client(endpoint=GATEWAY_URL, aws_region="us-west-2", aws_service="bedrock-agentcore"). The caller needs bedrock-agentcore:InvokeGateway.
  • The Harness uses a gateway as an agentcore_gateway tool; LangGraph, Claude Code and other MCP clients connect the same way, and the Bedrock Responses API can run gateway tools server-side.
  • Unauthorized JWT calls get 401 with a WWW-Authenticate header pointing to the protected-resource metadata, so OAuth-aware clients can discover how to sign in.

Gateway features

  • Semantic tool search (searchType: SEMANTIC): adds a built-in tool, x_amz_bedrock_agentcore_search, listed first, that takes {"query": "..."} and returns only matching tools. Agents with hundreds of tools then send far fewer tool definitions to the model. Searches cost extra and are limited to 25 per minute.
  • MCP versions: 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28; the gateway accepts only those in supportedVersions. 2026-07-28 is stateless: every request carries Mcp-Method and Mcp-Name headers and _meta fields, and user prompts (elicitation) and sampling become multi-round-trip requests.
  • Sessions and streaming (May 2026, for earlier MCP versions): sessions last 15 minutes to 8 hours from the first initialize (default 1 hour) and are bound to the caller; streaming (enableResponseStreaming, and the client must send Accept: text/event-stream) passes progress, log, elicitation and sampling messages through. MCP Tasks (October 2026, 2026-07-28 only) handle tools that run longer than the 15-minute call limit.
  • Rate limits (August 2026): per tool, target, model, JWT claim or IAM principal, up to 50 per gateway; they fail open, so they're for fairness and cost, not security. Gateway rules split traffic two ways for A/B tests and route requests.
  • Interceptors: up to one request and one response Lambda that can inspect or rewrite traffic (headers only if passRequestHeaders is true). They can be retried, so make them idempotent.
  • Also: customer managed KMS keys, AWS WAF web ACLs, VPC egress to private targets through VPC Lattice, private certificate authorities for targets, and custom domains through CloudFront.

Running a gateway

  • Quotas: 1,000 gateways per account, 100 targets per gateway, 1,000 tools per target, 200 tool calls or lists per second per gateway and per account, 5,000 concurrent connections, 6 MB payloads, 15-minute calls; inline schemas up to 1 MB, S3 schemas 10 MB.
  • Pricing: $0.005 per 1,000 calls (list, call, ping), $0.025 per 1,000 searches, $0.02 per 100 tools indexed per month, $0.006 per GB of VPC egress; Web Search $7 and Web Answer $10 per 1,000.
  • Observability: metrics in AWS/Bedrock-AgentCore (invocations, throttles, errors, latency, target time); application logs need a log delivery you create (default group under /aws/vendedlogs/bedrock-agentcore/gateway/). Policy decisions aren't in those logs: a denied call leaves no request record there, so enable gateway tracing.
  • CloudTrail: InvokeGateway is a data event (AWS::BedrockAgentCore::Gateway), off by default. It records the JWT's claims, including sub, so keep personal data out of sub.
  • Access control: resource-based policies (bedrock-agentcore:InvokeGateway, exact ARN; JWT gateways need Principal: "*" with conditions such as aws:SourceVpce), PrivateLink (com.amazonaws.REGION.bedrock-agentcore.gateway), and SCP condition keys such as bedrock-agentcore:GatewayAuthorizerType to forbid NONE gateways.

AgentCore Identity

The model

  • Workload identities represent agents. Runtime and Gateway create one automatically; for agents hosted elsewhere, call CreateWorkloadIdentity. They live in one directory per account and Region.
  • The token vault stores OAuth access and refresh tokens and API keys, bound to the workload identity and the user, encrypted with an AWS-owned or customer managed KMS key.
  • Credential providers describe how to get credentials: OAuth2 providers (25 built-in vendors such as Google, GitHub, Slack, Salesforce, Microsoft, Atlassian, Okta, Auth0 and Cognito, or CustomOauth2), API key providers, and payment providers.
  • A workload access token is the AWS-signed token an agent presents to Identity. When a user calls with a JWT, Runtime and Gateway validate it and exchange it for a workload access token tied to that user (GetWorkloadAccessTokenForJWT), and your code receives it automatically.

Creating a credential provider

Register Google as an OAuth provider (AWS CLI) 
aws bedrock-agentcore-control create-oauth2-credential-provider \
  --name google-provider \
  --credential-provider-vendor GoogleOauth2 \
  --oauth2-provider-config-input '{"googleOauth2ProviderConfig": {"clientId": "CLIENT_ID", "clientSecret": "CLIENT_SECRET"}}'

The response includes a callbackUrl: register it as the redirect URI in your Google OAuth app. To keep the client secret out of shell history and in a secret you manage, pass "clientSecretSource": "EXTERNAL" with "clientSecretConfig": {"secretId": ..., "jsonKey": ...} instead (June 2026). Custom providers also support private-key JWT client authentication with a key held in KMS. API keys use create-api-key-credential-provider.

The flows

  • Machine to machine (M2M, OAuth client credentials): the agent acts as itself.
  • User federation (USER_FEDERATION, three-legged OAuth): the first call returns an authorizationUrl; the user consents; the provider redirects to AgentCore and then to your return URL; your app confirms the user and calls CompleteResourceTokenAuth within 10 minutes; later calls get the stored token. The return URL must be listed in the workload identity's allowedResourceOauth2ReturnUrls.
  • On-behalf-of token exchange (ON_BEHALF_OF_TOKEN_EXCHANGE, April 2026): exchanges the user's inbound token for a downstream token (RFC 8693, or the JWT authorization grant used by Microsoft), with no consent screen. AWS recommends it over passing the user's JWT through.
  • The consent portal (September 2026) is an AWS-hosted page per gateway where users connect their accounts, useful for IDE agents that can't show consent links.

SDK decorators

Tools that get credentials from the token vault (Python, AgentCore SDK) 
from bedrock_agentcore.identity.auth import requires_access_token, requires_api_key
from strands import tool


@tool
@requires_access_token(
    provider_name="google-provider",
    scopes=["https://www.googleapis.com/auth/drive.metadata.readonly"],
    auth_flow="USER_FEDERATION",
    # In production, send this link to the user's UI
    on_auth_url=lambda url: print("Authorize here:", url),
    # Must be in the workload identity's allowedResourceOauth2ReturnUrls
    callback_url="https://app.example.com/oauth/callback",
    # Google: ask for a refresh token
    custom_parameters={"access_type": "offline"},
)
async def list_drive_files(*, access_token: str) -> str:
    ...


@tool
@requires_api_key(provider_name="weather-api-key")
def weather(city: str, *, api_key: str) -> str:
    ...
Your OAuth callback endpoint: bind the consent to the signed-in user (Python, AgentCore SDK) 
from bedrock_agentcore.services.identity import IdentityClient, UserIdIdentifier


def oauth_callback(session_id: str, signed_in_user_id: str):
    # signed_in_user_id comes from YOUR app's session, after you verify it
    IdentityClient("us-west-2").complete_resource_token_auth(
        session_uri=session_id,
        user_identifier=UserIdIdentifier(user_id=signed_in_user_id),
    )

The decorator polls for up to 10 minutes after the consent link is issued. Run outside Runtime (for example on a laptop), the SDK quietly creates a workload identity and a random user ID and saves them in .agentcore.json, so tokens you authorize locally belong to that made-up user.

GetWorkloadAccessTokenForUserId (and the Runtime user-ID header) accepts any string as the user: whoever can call it can act as any user. Prefer the JWT-based exchange, deny the user-ID actions where you don't need them, and prefix user IDs per identity provider.

Quotas and pricing

11,000 workload identities, 50 OAuth2 and 50 API key providers per Region, 200 token requests per second. Identity is free through Runtime or Gateway; elsewhere $0.010 per 1,000 successful token or key requests.

AgentCore Policy

The model

A policy engine holds policies and is attached to one or more gateways (one engine per gateway). It intercepts every tool call, denies by default, and a forbid always wins over a permit. Policies are written in Cedar or Dogwood, an open-source superset of Cedar that AWS now recommends, which adds time- and session-based conditions and Guardrails checks. Policy has been generally available since 3 March 2026.

  • Principal: AgentCore::OAuthUser (JWT callers; claims become tags you test with principal.hasTag("role") and principal.getTag("role")) or AgentCore::IamEntity (IAM callers; principal.id is the caller's ARN).
  • Action: AgentCore::Action::"TARGET___TOOL"; action in AgentCore::Action::"TARGET" covers a whole target. No wildcards.
  • Resource: AgentCore::Gateway::"GATEWAY_ARN", which must be a specific gateway, so policies are written after the gateway exists.
  • Context: context.input (tool arguments), context.output (results), context.system.now (the time).
Refunds under $1,000 for support staff only; never return high-sensitivity results (Cedar, also valid Dogwood) 
permit (
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"Orders___process_refund",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:111111111111:gateway/GATEWAY_ID"
)
when {
  principal.hasTag("role") && principal.getTag("role") == "support" &&
  context.input.amount < 1000
};

forbid (
  principal,
  action == AgentCore::Action::"Reports___view_results",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:111111111111:gateway/GATEWAY_ID"
)
when { context.input.sensitivity == "high" };
Pay out only if this claim was approved earlier in the same session (Dogwood temporal policy, from AWS's examples) 
permit (
  principal,
  action == AgentCore::Action::"Insurance___disburse_payment",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:111111111111:gateway/GATEWAY_ID"
)
when temporal {
  formerly within 1h AgentCore::Action::"Insurance___approve_claim"::response{
    eventResource: resource,
    input.claimId: context.input.claimId,
    output.approved: true
  }
};
  • Temporal policies (August 2026) use formerly within, since within, counts and sums over earlier calls in a policy session you identify with the header x-amzn-bedrock-agentcore-policy-session-id on every request (the gateway never creates one). Windows up to 24 hours, 20 temporal policies per engine; adding or changing one ends open sessions with a 409.
  • Guardrails in policies (June 2026): when guardrails { ... } blocks score tool inputs with Bedrock Guardrails content filters, prompt-attack and sensitive-information checks, and a suppressOutput effect withholds a tool's response. The gateway role then needs bedrock:InvokeGuardrailChecks.

Creating and attaching

Create an engine, attach it in log-only mode, then add a policy (Python, boto3) 
import boto3

ctl = boto3.client("bedrock-agentcore-control", region_name="us-west-2")
GW_ARN = "arn:aws:bedrock-agentcore:us-west-2:111111111111:gateway/GATEWAY_ID"

eng = ctl.create_policy_engine(name="orders_policies", description="Tool rules for orders-gateway")
engine_id, engine_arn = eng["policyEngineId"], eng["policyEngineArn"]
# Poll get_policy_engine until it's ready, then attach (full update of the gateway)
ctl.update_gateway(
    gatewayIdentifier="GATEWAY_ID",
    name="orders-gateway",
    roleArn="arn:aws:iam::111111111111:role/OrdersGatewayRole",
    protocolType="MCP",
    authorizerType="CUSTOM_JWT",
    authorizerConfiguration={"customJWTAuthorizer": {
        "discoveryUrl": "https://cognito-idp.us-west-2.amazonaws.com/USER_POOL_ID/.well-known/openid-configuration",
        "allowedClients": ["APP_CLIENT_ID"],
    }},
    # Observe decisions first; switch to ENFORCE when they look right
    policyEngineConfiguration={"arn": engine_arn, "mode": "LOG_ONLY"},
)

ctl.create_policy(
    policyEngineId=engine_id,
    name="RefundLimit",
    definition={"cedar": {"statement": (
        'permit(principal, action == AgentCore::Action::"Orders___process_refund", '
        f'resource == AgentCore::Gateway::"{GW_ARN}") when {{ context.input.amount < 1000 }};'
    )}},
    validationMode="FAIL_ON_ANY_FINDINGS",
)
  • Use definition={"policy": {"statement": ...}} for Dogwood. Creation is asynchronous: poll for active or CREATE_FAILED with reasons.
  • Validation uses automated reasoning to flag policies that are overly permissive, overly restrictive or can never match. It can't interpret guardrail conditions, so a lone guardrail forbid looks unconditional and fails: write a permit with the inverse threshold, or use IGNORE_ALL_FINDINGS.
  • Two log-only switches: the gateway's mode (LOG_ONLY or ENFORCE, for the whole engine) and each policy's enforcementMode (ACTIVE or LOG_ONLY, to shadow-test one policy).
  • Natural-language authoring: StartPolicyGeneration turns a description such as "support staff can refund up to $1,000" into Dogwood for the gateway's tools; review the result before creating it.
  • The gateway role needs bedrock-agentcore:GetPolicyEngine, AuthorizeAction and PartiallyAuthorizeActions, or every call is denied. Tool listing shows a tool if any context could permit it; the call itself is still checked.

Attaching an engine in ENFORCE mode before any permit exists denies every tool call. Start in LOG_ONLY, check the AllowDecisions and DenyDecisions metrics and the decision spans, then enforce. Anyone allowed to call UpdateGateway can switch the mode or detach the engine: constrain it with the bedrock-agentcore:PolicyEngineMode condition key.

Quotas and pricing

1,000 engines per Region and 1,000 policies per engine (fixed), 10 KB per policy, 400 KB schema per engine. $0.000025 per authorization request; guardrail checks at Guardrails rates. Decisions appear as metrics and trace spans (allow or deny, reason, determining policies), not in gateway logs.

AWS Agent Registry

A private, governed catalog of agents (A2A agent cards), MCP servers, skills and custom resources, generally available since 31 August 2026 in 9 Regions. Records go from draft through approval to discoverable; editing an approved record creates a new draft while the approved version stays live. Search with SearchDiscoverableRegistryRecords (semantic plus keyword, with filters) or through the registry's own MCP endpoint, and share registries with AWS RAM. It moved to its own namespace (agent-registry service, endpoints under api.aws, IAM prefix agent-registry:, boto3 clients agent-registry and agent-registry-control); the preview namespace stopped working on 30 October 2026, so older samples using search_registry_records no longer work. A monthly free tier (5,000 records, 1 million searches) covers most teams.

What's changed

  • November 2026: Web Answer connector (us-east-1).
  • October 2026: MCP 2026-07-28 and MCP Tasks on Gateway; private CAs for targets; Step Functions connector; InvokeModel on inference targets with model fallback; Registry's old namespace retired (30 October).
  • September 2026: Identity consent portal (1 September).
  • August 2026: Dogwood temporal policies and configurable Gateway rate limits (6 August); Policy in GovCloud (US-West); Registry generally available (31 August).
  • July 2026: HTTP passthrough, Runtime and inference targets; Identity private-key JWT.
  • June 2026: Guardrails in policies generally available (17 June); bring-your-own Secrets Manager secrets for Identity; Web Search connector.
  • April to May 2026: user-consent OAuth for MCP targets; on-behalf-of token exchange (30 April); Registry preview (9 April); Gateway sessions, streaming, elicitation and sampling (May).
  • December 2025 to March 2026: Policy preview (2 December 2025) and general availability (3 March 2026); API Gateway stages as targets; custom JWT claims.
  • 2025: Gateway and Identity in preview (16 July) and generally available with MCP server targets (13 October).
