How hosting fits together

  1. ModelCreateModel: the container image, the model artifacts, environment variables, the execution role, and optional VPC and network isolation. One PrimaryContainer, or up to 15 Containers.
  2. Endpoint configurationCreateEndpointConfig: 1 to 10 production variants (model, instance type, count, traffic weight, or a serverless configuration), plus data capture, the KMS key and observability settings. It can't be changed; every update needs a new one.
  3. EndpointCreateEndpoint: SageMaker starts the instances, pulls the image, downloads the artifacts and waits for health checks. The status goes Creating to InService (or Failed, where only delete works).
  4. ChangeUpdateEndpoint with a new configuration builds a new fleet and then removes the old one, without downtime; UpdateEndpointWeightsAndCapacities changes weights and counts in place.

The container contract

  • SageMaker runs docker run IMAGE serve and talks to port 8080: POST /invocations for requests and GET /ping for health. Model artifacts are unpacked to /opt/ml/model (read-only).
  • /ping must answer 200 within 2 seconds, and do so consistently within 8 minutes of startup, or the deployment fails; for large models raise ContainerStartupHealthCheckTimeoutInSeconds and ModelDataDownloadTimeoutInSeconds (60 to 3,600 seconds each) on the variant. Later failing pings get the instance replaced (not on inference-component endpoints).
  • Each request must be answered within 60 seconds, and bodies are limited to 6 MB (see the overview's runtime limits for headers and error codes).
  • On scale-in and updates the container gets SIGTERM, then SIGKILL 30 seconds later. Don't bundle NVIDIA drivers in the image.

ModelDataUrl must be a single .tar.gz. For large language models, ModelDataSource points at uncompressed files under an S3 prefix instead, which skips the unpacking step, but it can't be used with serverless or multi-model endpoints, batch transform or Marketplace models.

Deploying a model

Deploy an image and artifacts, then call the endpoint (Python, SageMaker Python SDK V3) 
from sagemaker.serve import ModelBuilder
from sagemaker.serve.builder.schema_builder import SchemaBuilder

mb = ModelBuilder(
    image_uri="111111111111.dkr.ecr.us-east-1.amazonaws.com/churn-serve:1.4",
    s3_model_data_url="s3://ml-111111111111/churn/model.tar.gz",
    role_arn="arn:aws:iam::111111111111:role/SageMakerExecutionRole",
    instance_type="ml.m5.xlarge",
    # Sample input and output let ModelBuilder set up serialization
    schema_builder=SchemaBuilder(sample_input={"features": [0.1, 3, 12]}, sample_output={"churn": 0.82}),
)
mb.build()
endpoint = mb.deploy(endpoint_name="churn-ep", initial_instance_count=2)

# deploy() returns an Endpoint resource, not a V2 Predictor
resp = endpoint.invoke(body=b'{"features": [0.1, 3, 12]}', content_type="application/json")
print(resp.body.read())

ModelBuilder also takes model= a trained ModelTrainer, a training job, a model package, a JumpStart ID (see JumpStart) or an S3 URI, or an inference_spec= with your own load and invoke functions. In SDK V2 the same thing is Model(image_uri=..., model_data=..., role=...).deploy(initial_instance_count=2, instance_type="ml.m5.xlarge"), which returns a Predictor.

The same deployment through the API (Python, boto3) 
import boto3

sm = boto3.client("sagemaker")
smr = boto3.client("sagemaker-runtime")

sm.create_model(
    ModelName="churn-v14",
    ExecutionRoleArn="arn:aws:iam::111111111111:role/SageMakerExecutionRole",
    PrimaryContainer={
        "Image": "111111111111.dkr.ecr.us-east-1.amazonaws.com/churn-serve:1.4",
        "ModelDataUrl": "s3://ml-111111111111/churn/model.tar.gz",
        "Environment": {"LOG_LEVEL": "info"},
    },
)
sm.create_endpoint_config(
    EndpointConfigName="churn-cfg-v14",
    ProductionVariants=[{
        "VariantName": "AllTraffic",
        "ModelName": "churn-v14",
        "InstanceType": "ml.m5.xlarge",
        "InitialInstanceCount": 2,
    }],
)
# The config store is eventually consistent; AWS suggests describing it first
sm.describe_endpoint_config(EndpointConfigName="churn-cfg-v14")
sm.create_endpoint(EndpointName="churn-ep", EndpointConfigName="churn-cfg-v14")
sm.get_waiter("endpoint_in_service").wait(EndpointName="churn-ep")

r = smr.invoke_endpoint(EndpointName="churn-ep", ContentType="application/json",
                        Body=b'{"features": [0.1, 3, 12]}')
print(r["Body"].read())

Several models on one endpoint

  • Production variants (up to 10 per configuration): different models or instance types behind one endpoint, with traffic split by InitialVariantWeight (weight divided by the sum of weights). Callers can force one with TargetVariant; the response header x-Amzn-Invoked-Production-Variant says which answered. This is the classic A/B test.
  • Multi-model endpoints (Mode: MultiModel): AWS's choice for "a large number of models that use the same ML framework on a shared serving container". Models stay in S3 and load on first call with TargetModel="model-123.tar.gz"; idle ones are unloaded when memory runs short. Add a model by uploading it, remove it by deleting it. Callers must tolerate cold starts. CPU instances, or GPU with NVIDIA Triton. No serverless, data capture, Model Monitor, shadow tests or response streaming.
  • Multi-container endpoints: up to 15 containers with different frameworks on one endpoint, called directly with TargetContainerHostname (InferenceExecutionConfig.Mode = Direct).
  • Serial inference pipelines: 2 to 15 containers run in sequence on every instance (Mode = Serial), for example preprocessing, prediction and postprocessing. No extra charge; the pipeline is changed only by updating the endpoint.
  • Inference components: each model gets its own CPU, accelerator and memory reservation, its own number of copies, and its own scaling and updates. AWS calls them "the most flexible way to deploy multiple models to an endpoint"; they're the only way to scale to zero, host LoRA adapters or use GPU partitions.

Inference components

An inference-component endpoint has variants without a ModelName; the execution role (and VPC settings) move to the endpoint configuration, and models are added afterwards with CreateInferenceComponent.

An endpoint with a base model and a LoRA adapter (Python, boto3; sm and smr as above) 
import time

sm.create_endpoint_config(
    EndpointConfigName="llm-ic-cfg",
    ExecutionRoleArn="arn:aws:iam::111111111111:role/SageMakerExecutionRole",
    ProductionVariants=[{
        "VariantName": "main",
        "InstanceType": "ml.g6.12xlarge",
        "InitialInstanceCount": 1,
        # SageMaker adds and removes instances to fit the copies; 0 allows scale to zero
        "ManagedInstanceScaling": {"Status": "ENABLED", "MinInstanceCount": 0, "MaxInstanceCount": 4},
        "RoutingConfig": {"RoutingStrategy": "LEAST_OUTSTANDING_REQUESTS"},
    }],
)
sm.create_endpoint(EndpointName="llm-ep", EndpointConfigName="llm-ic-cfg")
sm.get_waiter("endpoint_in_service").wait(EndpointName="llm-ep")

sm.create_inference_component(
    InferenceComponentName="llama-base",
    EndpointName="llm-ep",
    VariantName="main",
    Specification={
        "ModelName": "llama31-8b",
        "ComputeResourceRequirements": {
            "NumberOfAcceleratorDevicesRequired": 1,
            "NumberOfCpuCoresRequired": 4,
            "MinMemoryRequiredInMb": 16384,
        },
    },
    RuntimeConfig={"CopyCount": 1},
)

# There's no waiter for inference components; poll the status
while sm.describe_inference_component(InferenceComponentName="llama-base")["InferenceComponentStatus"] != "InService":
    time.sleep(30)

# An adapter shares the base component's compute, so it has no resource requirements
sm.create_inference_component(
    InferenceComponentName="llama-support-adapter",
    EndpointName="llm-ep",
    Specification={
        "BaseInferenceComponentName": "llama-base",
        "Container": {"ArtifactUrl": "s3://ml-111111111111/adapters/support/adapter.tar.gz"},
    },
)

r = smr.invoke_endpoint(EndpointName="llm-ep", InferenceComponentName="llama-support-adapter",
                        ContentType="application/json",
                        Body=b'{"inputs": "My invoice is wrong", "parameters": {"max_new_tokens": 128}}')
  • Copies: UpdateInferenceComponentRuntimeConfig changes CopyCount (a separate IAM action); UpdateInferenceComponent changes the model or image with a rolling update, copy by copy, instead of doubling the fleet.
  • Placement: SchedulingConfig chooses SPREAD or BINPACK and how evenly copies sit across Availability Zones; ScaleInPolicy on the variant chooses IDLE_RELEASE (remove empty instances) or CONSOLIDATION (repack copies to free instances). DataCacheConfig caches the image and artifacts on each instance so new copies start faster.
  • Several instance types: Specifications (up to 5, one per instance type) works with instance pools.

Calling an endpoint

Stream tokens as they're generated (Python, boto3) 
import json

import boto3

smr = boto3.client("sagemaker-runtime")
resp = smr.invoke_endpoint_with_response_stream(
    EndpointName="llm-ep",
    InferenceComponentName="llama-base",
    ContentType="application/json",
    Body=json.dumps({"inputs": "Explain VPC endpoints.", "parameters": {"max_new_tokens": 256}, "stream": True}),
)

# Parts can split or join the container's lines, so buffer and split on newlines
buf = b""
for event in resp["Body"]:
    if "PayloadPart" in event:
        buf += event["PayloadPart"]["Bytes"]
        while b"\n" in buf:
            line, buf = buf.split(b"\n", 1)
            if line.strip():
                print(line.decode("utf-8"))
    elif "ModelStreamError" in event:
        raise RuntimeError(event["ModelStreamError"])

What each line contains depends on the container (TGI and vLLM send server-sent event lines). Streaming uses the sagemaker:InvokeEndpoint permission, isn't available in the AWS CLI, and doesn't work with multi-model endpoints.

OpenAI-compatible API (21 May 2026)

Every endpoint and inference component also answers OpenAI Chat Completions requests (including streaming) at /endpoints/NAME/openai/v1 (or /endpoints/NAME/inference-components/IC/openai/v1), if the container serves /v1/chat/completions: the SageMaker vLLM and SGLang containers do. Clients authenticate with a bearer token, a pre-signed SigV4 URL made locally from your credentials and valid for up to 12 hours.

Call an endpoint with the OpenAI SDK (Python) 
from datetime import timedelta

from openai import OpenAI
from sagemaker.core.token_generator import generate_token

region = "us-east-1"
# Valid for the shorter of the expiry and your credentials' remaining life
token = generate_token(region=region, expiry=timedelta(hours=1))

client = OpenAI(
    base_url=f"https://runtime.sagemaker.{region}.amazonaws.com/endpoints/llm-ep/openai/v1",
    api_key=token,
)
# model is passed through to the container and can be empty
reply = client.chat.completions.create(model="", messages=[{"role": "user", "content": "Explain VPC endpoints."}])
print(reply.choices[0].message.content)

Bearer-token calls need sagemaker:InvokeEndpoint on the endpoint and sagemaker:CallWithBearerToken on "*" (it has no resource-level permissions). The token carries all of its creator's permissions until it expires, so keep expiries short and treat it like a password.

  • Stateful sessions: send SessionId="NEW_SESSION"; the container returns a session ID with an expiry, and later requests with that ID go to the same instance (useful for cached context). The container decides how a session closes. A session can't be started with the streaming API, only continued.
  • Bidirectional streaming (25 November 2025): for speech and voice agents, the client keeps an HTTP/2 connection (port 8443, up to 30 minutes) and SageMaker relays it to a WebSocket in the container (/invocations-bidirectional-stream; the image needs the label com.amazonaws.sagemaker.capabilities.bidirectional-streaming=true). It's not in boto3 or the CLI; AWS provides an experimental HTTP/2 Python SDK.
  • Routing (RoutingConfig on the variant): LEAST_OUTSTANDING_REQUESTS, RANDOM, or PREFIX_AWARE, which sends requests sharing a prompt prefix (or a PrefixAwareId header) to the same instance to reuse its KV cache.

Autoscaling and scale to zero

Endpoints scale through Application Auto Scaling: register the variant (or inference component) as a scalable target, then attach target tracking, step or scheduled policies.

Target tracking on invocations per instance for a variant (Python, boto3) 
import boto3

aas = boto3.client("application-autoscaling")
resource = "endpoint/churn-ep/variant/AllTraffic"

aas.register_scalable_target(
    ServiceNamespace="sagemaker",
    ResourceId=resource,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    MinCapacity=2,
    MaxCapacity=8,
)
aas.put_scaling_policy(
    PolicyName="churn-invocations",
    ServiceNamespace="sagemaker",
    ResourceId=resource,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    PolicyType="TargetTrackingScaling",
    TargetTrackingScalingPolicyConfiguration={
        # Invocations per instance per minute; find it with a load test
        "TargetValue": 70.0,
        "PredefinedMetricSpecification": {"PredefinedMetricType": "SageMakerVariantInvocationsPerInstance"},
        "ScaleInCooldown": 600,
        "ScaleOutCooldown": 300,
    },
)
  • Predefined metrics: SageMakerVariantInvocationsPerInstance, SageMakerInferenceComponentInvocationsPerCopy, SageMakerVariantProvisionedConcurrencyUtilization (serverless), and the high-resolution concurrency metrics SageMakerVariantConcurrentRequestsPerModelHighResolution and SageMakerInferenceComponentConcurrentRequestsPerCopyHighResolution, published every 10 seconds and counting queued and still-streaming requests. They make scale-out faster for LLMs; scale-in isn't faster.
  • Cooldowns default to 300 seconds each way. A plain variant's minimum is 1; you can also scale on CloudWatch metrics such as CPUUtilization in /aws/sagemaker/Endpoints.
Scale an inference component to zero and back (Python, boto3; aas as above) 
import boto3

cw = boto3.client("cloudwatch")
ic = "inference-component/llama-base"
dim = "sagemaker:inference-component:DesiredCopyCount"

# Needs ManagedInstanceScaling MinInstanceCount 0 on the variant
aas.register_scalable_target(ServiceNamespace="sagemaker", ResourceId=ic,
                             ScalableDimension=dim, MinCapacity=0, MaxCapacity=4)
aas.put_scaling_policy(
    PolicyName="llama-per-copy", ServiceNamespace="sagemaker", ResourceId=ic, ScalableDimension=dim,
    PolicyType="TargetTrackingScaling",
    TargetTrackingScalingPolicyConfiguration={
        "TargetValue": 1.0,
        "PredefinedMetricSpecification": {"PredefinedMetricType": "SageMakerInferenceComponentInvocationsPerCopy"},
        "ScaleInCooldown": 300, "ScaleOutCooldown": 300,
    },
)

# Target tracking can't scale out from zero copies: a step policy does, fired by an alarm
step = aas.put_scaling_policy(
    PolicyName="llama-from-zero", ServiceNamespace="sagemaker", ResourceId=ic, ScalableDimension=dim,
    PolicyType="StepScaling",
    StepScalingPolicyConfiguration={
        "AdjustmentType": "ChangeInCapacity", "MetricAggregationType": "Maximum", "Cooldown": 60,
        "StepAdjustments": [{"MetricIntervalLowerBound": 0, "ScalingAdjustment": 1}],
    },
)
cw.put_metric_alarm(
    AlarmName="llama-no-capacity", Namespace="AWS/SageMaker", MetricName="NoCapacityInvocationFailures",
    Dimensions=[{"Name": "InferenceComponentName", "Value": "llama-base"}],
    Statistic="Sum", Period=60, EvaluationPeriods=1, Threshold=1,
    ComparisonOperator="GreaterThanThreshold", AlarmActions=[step["PolicyARN"]],
)

Scale to zero works only on inference-component endpoints. Coming back from zero "takes several minutes", and requests fail until an instance and a copy are ready, so the first callers need retries or a queue (or use asynchronous inference, which can also scale to zero).

Serverless inference

Serverless endpoints run on AWS-managed compute (built on Lambda), scale to zero by themselves and bill only while processing: right for intermittent traffic that can tolerate cold starts. Set a ServerlessConfig on the variant instead of an instance type and count.

A serverless variant with provisioned concurrency (Python, boto3) 
sm.create_endpoint_config(
    EndpointConfigName="churn-sls-cfg",
    ProductionVariants=[{
        "VariantName": "AllTraffic",
        "ModelName": "churn-v14",
        "ServerlessConfig": {
            # 1024 to 6144 in 1 GB steps; vCPUs scale with memory
            "MemorySizeInMB": 2048,
            "MaxConcurrency": 20,
            # Optional, warm capacity (billed while provisioned)
            "ProvisionedConcurrency": 2,
        },
    }],
)
sm.create_endpoint(EndpointName="churn-sls", EndpointConfigName="churn-sls-cfg")
  • Limits: memory 1,024 to 6,144 MB, 5 GB of disk, a 10 GB image, payloads up to 4 MB, responses within 60 seconds, and MaxConcurrency 1 to 200 per endpoint (requests above it are throttled).
  • Not supported: GPUs, Marketplace model packages, private Docker registries, multi-model endpoints, VPC configuration, network isolation, data capture, multiple variants, Model Monitor, inference pipelines, uncompressed ModelDataSource, deployment guardrails and shadow tests.
  • Cold starts depend on image and model size; watch OverheadLatency. Provisioned concurrency (up to MaxConcurrency) keeps instances warm, and can be scaled with Application Auto Scaling on sagemaker:variant:DesiredProvisionedConcurrency with SageMakerVariantProvisionedConcurrencyUtilization, or on a schedule (not through CloudFormation).
  • Conversion: a serverless endpoint can be updated to instances, but an instance-based endpoint can't become serverless, and the change can't be reversed.
  • Quotas: the account defaults are 5 serverless endpoints and a total concurrency of 10 per Region; the documented maximums are 50 endpoints and 1,000 (500 in smaller Regions) total concurrency after increases.

Safe deployments and testing

Deployment guardrails control how UpdateEndpoint shifts traffic. With no policy, SageMaker does blue/green all at once.

Canary rollout with automatic rollback on alarms (Python, boto3) 
sm.update_endpoint(
    EndpointName="churn-ep",
    EndpointConfigName="churn-cfg-v15",
    DeploymentConfig={
        "BlueGreenUpdatePolicy": {
            "TrafficRoutingConfiguration": {
                "Type": "CANARY",
                # Up to 50% of the fleet; then a baking period before the rest
                "CanarySize": {"Type": "CAPACITY_PERCENT", "Value": 10},
                "WaitIntervalInSeconds": 600,
            },
            # Keep the old fleet briefly after the switch
            "TerminationWaitInSeconds": 300,
            # Must exceed the total of the waits
            "MaximumExecutionTimeoutInSeconds": 3600,
        },
        "AutoRollbackConfiguration": {"Alarms": [{"AlarmName": "churn-ep-5xx"}, {"AlarmName": "churn-ep-p99-latency"}]},
    },
)
  • Traffic shifting: ALL_AT_ONCE, CANARY (one slice, bake, then the rest) or LINEAR (10 to 50% steps). Any alarm in ALARM during baking rolls back to the old fleet.
  • Rolling updates (RollingUpdatePolicy): replace the fleet in batches (MaximumBatchSize 5 to 50%, type INSTANCE_COUNT or CAPACITY_PERCENT) without doubling instances; good for large GPU fleets. Not for serverless or multi-variant endpoints.
  • Exclusions: the new configuration must keep the same variant name; Marketplace containers and Inf1 instances fall back to all at once with no baking.
  • Shadow tests (CreateInferenceExperiment, type ShadowMode): copy a percentage of live requests to a shadow variant, compare metrics, and return only the production response to callers. One production and one shadow variant, 7 days by default; you pay only for the shadow instances. Not for serverless, asynchronous, multi-model, multi-container, Marketplace or Inf1 endpoints.
  • A/B tests use variant weights, then UpdateEndpointWeightsAndCapacities to move traffic (for example 50/50, then 0/100) with no new fleet.

Capacity and GPUs

  • Instance pools (May 2026): give a variant InstancePools (up to 5 types with priorities 1 to 5) instead of one InstanceType; when a type is out of capacity SageMaker falls back to the next within VariantInstanceProvisionTimeoutInSeconds (300 to 3,600). Scale-in removes lower-priority instances first, and ModelNameOverride gives each type its own optimized model.
  • GPU partitioning (30 October 2026): AcceleratorPartitionLayouts on the variant splits P4d, P5, G7 and G7e GPUs into up to 7 MIG slices, and each inference component asks for an AcceleratorPartitionType such as mig-3g.40gb. The layout can't be changed on a running endpoint (create a new one), and partitioned endpoints don't publish GPU, CPU or memory utilization.
  • Reserved capacity: a training plan for endpoints, referenced by CapacityReservationConfig. When the plan ends, an endpoint set to capacity-reservations-only stops serving; deleting the endpoint doesn't refund the plan.
  • Drivers: InferenceAmiVersion picks the GPU driver and CUDA version, for example al2-ami-sagemaker-inference-gpu-3-1 (driver 550, CUDA 12.4) or al2023-ami-sagemaker-inference-gpu-4-1 (580, CUDA 13.0).
  • Faster scale-out: automatic container image caching (June 2026, no settings) and Fast Model Loader; the optimization page covers them.
  • Elastic Inference is gone: AcceleratorType is "no longer supported"; use small GPU or Inferentia instances.

Security

  • VPC: set VpcConfig on the model with at least two subnets in different Availability Zones; without internet access, add an S3 gateway endpoint for artifacts. Callers in a VPC reach the runtime privately through an interface endpoint (runtime.sagemaker), which must exist in their Availability Zone.
  • Network isolation (EnableNetworkIsolation) stops the container making any network calls; SageMaker still downloads the artifacts for it. It can't be combined with Fast Model Loader, and serverless doesn't support it.
  • Encryption: KmsKeyId on the endpoint configuration encrypts the EBS volume but not local NVMe storage, which instance hardware encrypts; data capture and core dumps take their own keys.
  • IAM: callers need sagemaker:InvokeEndpoint on the endpoint (and inference component); sagemaker:TargetModel restricts which multi-model artifacts they can call. Enforce settings at creation with sagemaker:InstanceTypes, sagemaker:VpcSubnets, sagemaker:NetworkIsolation, sagemaker:VolumeKmsKeyArn, sagemaker:ServerlessMaxConcurrency and sagemaker:ServerlessMemorySize.

Quotas and pricing

  • Quotas: instance-type quotas for endpoint usage start at 0 on new accounts, and 4 instances per endpoint and across endpoints by default (quotas). InvokeEndpoint is limited to 10,000 requests per second per account and Region (not adjustable); create, update and delete calls to 1 per second.
  • Real-time: per instance-hour while the endpoint exists, whether or not it gets traffic (in N. Virginia, for example, ml.m5.xlarge $0.23, ml.g5.xlarge $1.408, ml.g6.2xlarge $1.222, ml.p5.48xlarge $63.296), plus $0.016 per GB of data in and out.
  • Serverless: per second of compute at a rate set by memory ($0.00004 per second at 2 GB) plus data; AWS's example of 10 million 100 ms requests at 2 GB costs $40.16. Provisioned concurrency adds a charge for the time it's provisioned.
  • Savings: SageMaker Savings Plans (up to 64%, 1 or 3 years) cover real-time inference; serverless and asynchronous aren't listed. P4 and P5 prices fell by up to 45% in June 2025. Shadow-test data and inference pipelines add no charge.
  • Free tier (first two months, per the pricing page): 125 hours a month of ml.m4.xlarge or ml.m5.xlarge real-time hosting and 150,000 seconds of serverless inference.

What's changed

  • 2026: AI inference recommendations with benchmark jobs (April); instance pools with automatic fallback (May); the OpenAI-compatible API with bearer tokens (21 May); detailed observability with TTFT, inter-token latency and GPU metrics (June); automatic container image caching (30 June); G7 instances (July); GPU partitioning with MIG (30 October).
  • 2025: rolling updates for inference-component endpoints (10 March); up to 45% lower P4 and P5 prices (June); P6e-GB200 UltraServers (August); bidirectional streaming (25 November); training plans for endpoints (26 November).
  • 2024: InferenceAmiVersion (September); scale to zero and multi-adapter LoRA inference with inference components (25 November); container caching and Fast Model Loader (6 December).
