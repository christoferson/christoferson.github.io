How a training job works

A training job starts the instances you asked for, pulls your container image, copies or mounts the input data, runs the container with the argument train, uploads the result to S3 and shuts everything down. You pay from the start of the job to the end of the upload, including data download and model upload.

What the container sees

  • Inputs: data channels under /opt/ml/input/data/CHANNEL; hyperparameters in /opt/ml/input/config/hyperparameters.json (all values are strings); the cluster layout in resourceconfig.json (current_host such as algo-1, and the list of hosts).
  • Outputs: whatever the code writes to /opt/ml/model becomes model.tar.gz in the output path; /opt/ml/output/data becomes output.tar.gz; /opt/ml/checkpoints syncs to S3 continuously if checkpoints are configured; the first 1,024 characters of /opt/ml/output/failure become the job's FailureReason. Set CompressionType to NONE to skip the tar step for large models.
  • Environment: AWS framework containers (through the training toolkit) set SM_MODEL_DIR, SM_CHANNEL_TRAIN (one per channel), SM_HPS, SM_HOSTS, SM_CURRENT_HOST and SM_NUM_GPUS, and pass hyperparameters as command-line arguments.
  • Stopping: on a stop request or when the maximum run time is reached, the container gets SIGTERM and 120 seconds to save its work before SIGKILL.

Status, logs and metrics

The status is InProgress, Completed, Failed, Stopping or Stopped; the secondary status says what's happening: Starting, Pending (waiting for capacity), Downloading, Training, Interrupted (Spot capacity reclaimed), Uploading, MaxRuntimeExceeded or MaxWaitTimeExceeded. Logs go to CloudWatch group /aws/sagemaker/TrainingJobs with one stream per host. Instance metrics (CPU, memory, GPU, GPU memory, disk) are in the namespace of the same name per host, and your own metrics come from MetricDefinitions: up to 40 regular expressions that SageMaker matches against the log output and publishes to CloudWatch. Built-in algorithms define theirs automatically.

Three ways to bring an algorithm

Built-in algorithms

AWS-provided images you configure only with hyperparameters. CSV input must have no header and the label in the first column (unsupervised algorithms use text/csv;label_size=0); application/x-recordio-protobuf suits sparse data. The main ones by problem type:

  • Tabular classification and regression: XGBoost (CSV, LibSVM, Parquet; CPU, GPU from 1.2; memory-bound, so prefer M5 over C instances), Linear Learner, k-NN, Factorization Machines (sparse data such as click prediction and recommendations; recordIO-protobuf only), and LightGBM, CatBoost, AutoGluon-Tabular and TabTransformer.
  • Unsupervised: K-Means (clustering), PCA (dimensionality reduction), Random Cut Forest (anomaly detection, CPU only), IP Insights (unusual IP use), LDA and NTM (topic modelling).
  • Time series: DeepAR (JSON Lines or Parquet).
  • Text: BlazingText (Word2Vec and text classification), Object2Vec (pair embeddings), Seq2Seq (translation, summarization; GPU), Text Classification - TensorFlow.
  • Vision: Image Classification, Object Detection (MXNet and TensorFlow versions) and Semantic Segmentation, all GPU.

Only Image Classification - MXNet, Object Detection - MXNet and Semantic Segmentation support incremental training (a model channel pointing at the previous artifact). Built-in images are pulled with SageMaker's own credentials, so IAM can't restrict which built-in algorithm someone uses. Image URIs differ by Region and version (XGBoost in us-east-1 is 683313688378.dkr.ecr.us-east-1.amazonaws.com/sagemaker-xgboost:1.7-1; don't use :latest); image_uris.retrieve() in the SDK looks them up.

Script mode on AWS framework containers

You write train.py (plus requirements.txt) and run it on an AWS Deep Learning Container for PyTorch, TensorFlow or Hugging Face, or the SageMaker scikit-learn and XGBoost framework containers (account 763104351884 for the Deep Learning Containers). The container installs requirements, sets the SM_* variables and runs your script. This is the usual choice for custom models.

Your own container

Push an image to ECR with a train executable or an exec-form ENTRYPOINT that follows the /opt/ml layout; install sagemaker-training to get script-mode behaviour. Private registries work through TrainingImageConfig, and AWS Marketplace algorithms (AlgorithmName) always run with network isolation.

Getting data in

  • File mode (default): downloads the whole channel to the instance volume before training starts, so the volume must hold the data, model and checkpoints. Works with every data source type.
  • FastFile mode: presents S3 as a read-only file system and streams on demand, so training starts immediately and the data needn't fit on disk; best for sequential reads. S3 prefixes only (no manifests); end the prefix with /.
  • Pipe mode: streams S3 into a FIFO per channel per epoch; your code or algorithm must support it. AWS describes it as largely replaced by FastFile mode, but exams still ask about it as the way to start fast on large datasets.
  • Distribution: FullyReplicated gives every instance all the data; ShardedByS3Key gives each instance about 1/n of the objects, so split the data into at least as many files as instances.
  • FSx for Lustre and EFS (FileSystemDataSource): mounted in seconds whatever the size; needs a VpcConfig (for FSx, a subnet in its Availability Zone). Recommended for large distributed jobs that reread data.
  • Limits: 1 to 20 channels per job, data in the job's Region. VolumeSizeInGB sizes the EBS volume (default 30 in the SDKs); instance types with local NVMe storage (such as ml.p4d, ml.g5) use that instead.

Training with ModelTrainer

In SDK V3, ModelTrainer replaces Estimator and the framework estimators: you give it an image, source code and configuration objects, and it rejects any argument it doesn't know.

Distributed PyTorch on two GPU instances with Spot, checkpoints and a VPC (Python, SageMaker Python SDK V3) 
from sagemaker.core import image_uris
from sagemaker.core.helper.session_helper import Session, get_execution_role
# New home of the config classes; sagemaker.train.configs still works but is deprecated
from sagemaker.core.training.configs import (
    CheckpointConfig, Compute, InputData, Networking, OutputDataConfig, SourceCode, StoppingCondition,
)
from sagemaker.train import ModelTrainer
from sagemaker.train.distributed import Torchrun

session = Session()
image = image_uris.retrieve(framework="pytorch", region=session.boto_region_name, version="2.5.1",
                            py_version="py311", instance_type="ml.g5.12xlarge", image_scope="training")

trainer = ModelTrainer(
    training_image=image,
    role=get_execution_role(),
    base_job_name="ddp-demo",
    source_code=SourceCode(source_dir="./src", entry_script="train.py", requirements="requirements.txt"),
    # One process per GPU: ml.g5.12xlarge has 4
    distributed=Torchrun(process_count_per_node=4),
    # Spot can't be combined with warm pools or instance preference lists
    compute=Compute(instance_type="ml.g5.12xlarge", instance_count=2, volume_size_in_gb=100,
                    enable_managed_spot_training=True),
    # Wait time covers waiting for Spot capacity plus running
    stopping_condition=StoppingCondition(max_runtime_in_seconds=4 * 3600, max_wait_time_in_seconds=8 * 3600),
    checkpoint_config=CheckpointConfig(s3_uri="s3://ml-111111111111/ddp/checkpoints/"),
    output_data_config=OutputDataConfig(s3_output_path="s3://ml-111111111111/ddp/output/"),
    # The security group must allow all traffic from itself for the nodes to talk
    networking=Networking(subnets=["subnet-0aaa"], security_group_ids=["sg-0train"],
                          enable_inter_container_traffic_encryption=True),
    hyperparameters={"epochs": 5, "lr": 3e-4},
)
trainer.train(input_data_config=[InputData(channel_name="train", data_source="s3://ml-111111111111/ddp/train/")],
              wait=False)
The matching train.py: read the SageMaker environment, resume from a checkpoint, save the model (Python) 
import argparse
import json
import os

CKPT_DIR = "/opt/ml/checkpoints"


def main():
    p = argparse.ArgumentParser()
    # Hyperparameters arrive as command-line arguments
    p.add_argument("--epochs", type=int, default=10)
    p.add_argument("--lr", type=float, default=1e-3)
    p.add_argument("--model-dir", default=os.environ.get("SM_MODEL_DIR", "/opt/ml/model"))
    p.add_argument("--train", default=os.environ.get("SM_CHANNEL_TRAIN", "/opt/ml/input/data/train"))
    args = p.parse_args()
    host = os.environ.get("SM_CURRENT_HOST", "algo-1")

    # After a Spot interruption, SageMaker restores /opt/ml/checkpoints from S3
    ckpt = os.path.join(CKPT_DIR, f"ckpt-{host}.json")
    start = json.load(open(ckpt))["epoch"] if os.path.exists(ckpt) else 0

    for epoch in range(start, args.epochs):
        loss = 0.0  # real training goes here
        # A MetricDefinitions regex such as "train_loss=([0-9\.]+)" turns this into a metric
        print(f"epoch={epoch} train_loss={loss:.4f}")
        os.makedirs(CKPT_DIR, exist_ok=True)
        json.dump({"epoch": epoch + 1}, open(ckpt, "w"))

    # Everything in the model directory becomes model.tar.gz in S3
    os.makedirs(args.model_dir, exist_ok=True)
    json.dump({"trained": True}, open(os.path.join(args.model_dir, "model.json"), "w"))


if __name__ == "__main__":
    main()
  • Test locally first: ModelTrainer(training_mode=Mode.LOCAL_CONTAINER, compute=Compute(instance_type="local_cpu", ...)) runs the same container in Docker on your machine.
  • Other options: with_metric_definitions, with_retry_strategy, with_infra_check_config (hardware and network health check before training), with_remote_debug_config, MPI with MPI(), and @remote (from sagemaker.core.remote_function) to run a Python function as a training job.
  • V2 equivalent (what exam material shows): PyTorch(entry_point="train.py", framework_version=..., instance_type=..., instance_count=2, distribution={"torch_distributed": {"enabled": True}}, use_spot_instances=True, max_run=..., max_wait=..., checkpoint_s3_uri=...) then .fit({"train": "s3://..."}).

Some AWS documentation samples rewritten for V3 still pass V2-only arguments to ModelTrainer, such as distribution=, max_run=, enable_remote_debug= or compiler_config=. They fail, because ModelTrainer rejects unknown arguments. Use distributed=Torchrun(), StoppingCondition and the with_* methods instead.

Training with the API

Built-in XGBoost with Spot, checkpoints, a VPC, network isolation, KMS keys and a custom metric (Python, boto3) 
import boto3

sm = boto3.client("sagemaker", region_name="us-east-1")
KEY = "arn:aws:kms:us-east-1:111111111111:key/EXAMPLE-KEY-ID"


def channel(name, uri):
    # Built-in XGBoost CSV: label in the first column, no header
    return {"ChannelName": name, "ContentType": "text/csv",
            "DataSource": {"S3DataSource": {"S3DataType": "S3Prefix", "S3Uri": uri,
                                            "S3DataDistributionType": "FullyReplicated"}}}


sm.create_training_job(
    TrainingJobName="churn-xgb-2026-11-10-01",
    # The caller needs iam:PassRole on this role
    RoleArn="arn:aws:iam::111111111111:role/SageMakerTrainingRole",
    AlgorithmSpecification={
        "TrainingImage": "683313688378.dkr.ecr.us-east-1.amazonaws.com/sagemaker-xgboost:1.7-1",
        "TrainingInputMode": "File",
        # Built-ins publish their own metrics; MetricDefinitions matter most for your own code
        "MetricDefinitions": [{"Name": "train:loss", "Regex": "train_loss=([0-9\\.]+)"}],
    },
    # Values are always strings
    HyperParameters={"objective": "binary:logistic", "num_round": "300", "eval_metric": "auc"},
    InputDataConfig=[channel("train", "s3://ml-111111111111/churn/train/"),
                     channel("validation", "s3://ml-111111111111/churn/validation/")],
    OutputDataConfig={"S3OutputPath": "s3://ml-111111111111/churn/output/", "KmsKeyId": KEY},
    # VolumeKmsKeyId isn't allowed on instance types with local NVMe storage
    ResourceConfig={"InstanceType": "ml.m5.2xlarge", "InstanceCount": 1, "VolumeSizeInGB": 50, "VolumeKmsKeyId": KEY},
    EnableManagedSpotTraining=True,
    # MaxWaitTimeInSeconds (waiting plus running) must be at least MaxRuntimeInSeconds
    StoppingCondition={"MaxRuntimeInSeconds": 3600, "MaxWaitTimeInSeconds": 7200},
    CheckpointConfig={"S3Uri": "s3://ml-111111111111/churn/checkpoints/"},
    # Private subnets need an S3 gateway endpoint to reach the data
    VpcConfig={"Subnets": ["subnet-0aaa", "subnet-0bbb"], "SecurityGroupIds": ["sg-0train"]},
    # The container gets no network access and no AWS credentials
    EnableNetworkIsolation=True,
    Tags=[{"Key": "project", "Value": "churn"}],
)

job = sm.describe_training_job(TrainingJobName="churn-xgb-2026-11-10-01")
print(job["TrainingJobStatus"], job["SecondaryStatus"])
# When it completes: Spot saving % = (1 - BillableTimeInSeconds / TrainingTimeInSeconds) * 100

Also useful on CreateTrainingJob: RetryStrategy (1 to 30 automatic retries, only for internal service errors), InfraCheckConfig, RemoteDebugConfig, MlflowConfig to log to managed MLflow, and Environment (up to 100 variables). Don't put secrets in hyperparameters, environment variables or tags: DescribeTrainingJob shows them.

Spot, warm pools and capacity

Managed Spot training

Runs the job on spare capacity for up to 90% less (AWS's current figure; some API pages still say 80%). If capacity is reclaimed the job pauses (Interrupted) and resumes when capacity returns, restoring /opt/ml/checkpoints from S3, so write checkpoints unless the job is short. It never falls back to On-Demand: when MaxWaitTimeInSeconds passes, the job stops with MaxWaitTimeExceeded. Built-in algorithms that can't checkpoint are limited to a one-hour wait. Spot has its own instance quotas (20 per job, 4 across jobs by default).

Managed warm pools

Set KeepAlivePeriodInSeconds (up to 3,600 seconds per the guide) and the instances stay up after the job, so the next job with the same role, instance type and count, volume size and key, VPC settings and network isolation and encryption flags starts in seconds; a pool can be reused job after job for up to 28 days. You pay for the retained time. Warm pools don't work with Spot or heterogeneous clusters, and the warm pool quota is 0 per instance type by default, so without an increase no pool is kept. Set the period to 0 with UpdateTrainingJob to release a pool early.

Getting GPU capacity

  • Instance preference lists (September 2026): ResourceConfig.InstancePreferences lists up to five instance types tried in order; the job runs on the first one with capacity (SelectedInstanceType shows which). MaxPendingTimeInSeconds bounds the wait for accelerated types. Not combinable with Spot or InstanceType; the quota is checked for every type, and your code must run on all of them.
  • Flexible training plans: reserve GPU or Trainium instances (ml.p4d, p5, p5e, p5en, p6-b200, trn1, trn2 and others) for 1 to 182 days, up to 56 days ahead, paid upfront and not cancellable. Pass TrainingPlanArn; jobs wait as Pending until the plan is active. Plans are bought separately for training jobs, HyperPod, endpoints or Studio.
  • AWS Batch can queue SageMaker training jobs with priorities and fair share (July 2025), with quota management and preemption since March 2026, at no Batch charge.
  • Heterogeneous clusters (InstanceGroups, up to five groups) put CPU-heavy data preprocessing on cheap CPU instances so GPUs stay busy.
  • Faster starts: SOCI-indexed images (October 2026; Deep Learning Container tags ending -soci) load the image lazily, so large containers start in seconds.

Distributed training

  • Data parallel when the data is large: each GPU holds a copy of the model and processes different batches, and gradients are averaged. Model parallel when the model doesn't fit on one GPU: the model itself is split.
  • Launchers: PyTorch DDP and FSDP through torchrun (Torchrun() in V3, {"torch_distributed": {"enabled": True}} in V2), MPI, DeepSpeed and parameter servers all work.
  • SageMaker libraries: SMDDP (faster AllReduce and AllGather on ml.p4d and p4de, plus AllReduce on ml.p3dn) and SMP v2 (FSDP-based sharding, tensor, expert and context parallelism, FP8 on P5). Neither has a deprecation notice, but neither has had a release since April 2025 and SMP supports PyTorch only up to 2.5.1, while the Deep Learning Containers are at 2.10. Prefer native PyTorch unless you need a specific feature.
  • Networking: the security group must allow all traffic to and from itself (needed for EFA too). Inter-container traffic encryption adds IPsec between nodes (allow UDP 500 and ESP from the group) and slows deep learning jobs.
  • Training Compiler gets no new releases. For multi-week foundation model training on persistent, self-healing clusters, see HyperPod (feature page to come); for fine-tuning foundation models without managing instances, serverless model customization (feature page to come).

Debugging and monitoring

Debugger has been closed to new customers since 30 July 2026, and Profiler support ends 30 June 2027. Exams still ask about them: Debugger's free built-in rules (VanishingGradient, ExplodingTensor, Overfit, LossNotDecreasing, PoorWeightInitialization and others) watch tensors during training and can stop the job, and Profiler finds CPU, GPU and I/O bottlenecks. AWS's replacements: MLflow or TensorBoard for metrics and tracking, TensorBoard histograms for gradients and weights, CloudWatch for system profiling, and CloudWatch alarms plus MLflow run comparison for automatic checks.

  • MLflow: pass MlflowConfig on the job, or log from the script, to track parameters, metrics and models across runs. The old Experiments SDK works only in Studio Classic.
  • TensorBoard: write logs with TensorBoardOutputConfig and open them in the TensorBoard app in Studio (five Regions, ml.r5.large).
  • Interactive debugging: with RemoteDebugConfig enabled, open a shell in the running container with aws ssm start-session --target sagemaker-training-job:JOB_algo-1. Not available with network isolation or for built-in algorithms.

Automatic model tuning

Automatic model tuning runs many training jobs with different hyperparameters and keeps the one with the best objective metric. The tuning itself is free; you pay for the training jobs.

  • Bayesian (default) learns from finished jobs which values to try next, so it gets smarter with fewer jobs in parallel. Random scales to full parallelism without losing quality. Grid tries every combination of categorical values. Hyperband uses metrics reported during training to stop weak configurations early and move resources to promising ones; it's the fastest for large iterative jobs.
  • Ranges: integer, continuous and categorical. Use logarithmic scaling when a range spans orders of magnitude (a linear search of 0.0001 to 1.0 spends about 90% of the jobs between 0.1 and 1.0), and reverse logarithmic for values sensitive near 1, such as momentum.
  • Early stopping (Auto) stops a job whose objective is worse than the median of earlier jobs at the same epoch; the algorithm must report the metric every epoch, and it must be off for Hyperband. Completion criteria end the whole tuning job at a target value, after N jobs without improvement, or on convergence.
  • Warm start reuses up to five earlier tuning jobs: IdenticalDataAndAlgorithm (same data and image, new ranges) or TransferLearning (data, ranges or image version changed). Autotune chooses ranges, strategy and limits for you from hints.
  • Limits: 10 parallel training jobs per tuning job and 750 jobs per tuning job (not adjustable), 30 tunable hyperparameters. AWS suggests about 50 or more jobs for a typical search. Multi-objective tuning isn't supported: combine metrics into one.
Bayesian tuning of XGBoost with a log-scaled learning rate, early stopping and completion criteria (Python, boto3; reuses sm and channel() from the API example above) 
sm.create_hyper_parameter_tuning_job(
    # Up to 32 characters; becomes the prefix of every training job name
    HyperParameterTuningJobName="churn-xgb-bayes-01",
    HyperParameterTuningJobConfig={
        "Strategy": "Bayesian",
        "HyperParameterTuningJobObjective": {"Type": "Maximize", "MetricName": "validation:auc"},
        "ResourceLimits": {"MaxNumberOfTrainingJobs": 40, "MaxParallelTrainingJobs": 4},
        "ParameterRanges": {
            "ContinuousParameterRanges": [
                {"Name": "eta", "MinValue": "0.001", "MaxValue": "0.5", "ScalingType": "Logarithmic"},
                {"Name": "subsample", "MinValue": "0.5", "MaxValue": "1.0", "ScalingType": "Linear"},
            ],
            "IntegerParameterRanges": [{"Name": "max_depth", "MinValue": "3", "MaxValue": "10", "ScalingType": "Auto"}],
        },
        "TrainingJobEarlyStoppingType": "Auto",
        "TuningJobCompletionCriteria": {
            "TargetObjectiveMetricValue": 0.95,
            "BestObjectiveNotImproving": {"MaxNumberOfTrainingJobsNotImproving": 10},
        },
    },
    TrainingJobDefinition={
        "AlgorithmSpecification": {
            "TrainingImage": "683313688378.dkr.ecr.us-east-1.amazonaws.com/sagemaker-xgboost:1.7-1",
            "TrainingInputMode": "File",
        },
        "RoleArn": "arn:aws:iam::111111111111:role/SageMakerTrainingRole",
        "StaticHyperParameters": {"objective": "binary:logistic", "num_round": "300", "eval_metric": "auc"},
        "InputDataConfig": [channel("train", "s3://ml-111111111111/churn/train/"),
                            channel("validation", "s3://ml-111111111111/churn/validation/")],
        "OutputDataConfig": {"S3OutputPath": "s3://ml-111111111111/churn/hpo/"},
        "ResourceConfig": {"InstanceType": "ml.m5.2xlarge", "InstanceCount": 1, "VolumeSizeInGB": 30},
        # Tuning jobs can use Spot too
        "EnableManagedSpotTraining": True,
        "StoppingCondition": {"MaxRuntimeInSeconds": 1800, "MaxWaitTimeInSeconds": 3600},
    },
)

best = sm.describe_hyper_parameter_tuning_job(HyperParameterTuningJobName="churn-xgb-bayes-01")["BestTrainingJob"]
print(best["TrainingJobName"], best["FinalHyperParameterTuningJobObjectiveMetric"])

In SDK V3 the same job is HyperparameterTuner(model_trainer=trainer, objective_metric_name="validation:auc", hyperparameter_ranges={...}, strategy="Bayesian", max_jobs=40, max_parallel_jobs=4, early_stopping_type="Auto").tune(inputs=[...]), with range classes from sagemaker.core.parameter.

Security

  • By default the container can reach the internet. With a VpcConfig, SageMaker attaches network interfaces in your subnets; private subnets need an S3 gateway endpoint (or a NAT gateway) for data, interface endpoints for other AWS services, and endpoint or bucket policies to limit what can be read.
  • Network isolation blocks all network calls from the container except between nodes of the same job, and gives it no AWS credentials. SageMaker still downloads input and uploads output for it. Code that calls AWS APIs, installs packages from the internet or logs to a remote MLflow breaks under isolation.
  • Encryption: OutputDataConfig.KmsKeyId for artifacts in S3 and VolumeKmsKeyId for the EBS volume; local NVMe storage is encrypted by the instance hardware and doesn't take a key. Inter-container encryption protects traffic between nodes.
  • IAM: callers need iam:PassRole on the execution role. Enforce settings with sagemaker:VpcSubnets, sagemaker:NetworkIsolation, sagemaker:InterContainerTrafficEncryption, sagemaker:VolumeKmsKey, sagemaker:OutputKmsKey, sagemaker:InstanceTypes, sagemaker:ImageArns, sagemaker:EnableRemoteDebug and sagemaker:KeepAlivePeriod (see the overview's SCP example).

Quotas and pricing

  • Run time: MaxRuntimeInSeconds defaults to 1 day and can be set up to 28 days, but the account quota caps jobs at 5 days until you raise it.
  • Instances: 20 per job and 4 across all jobs by default, and most per-instance-type quotas start at 0 on new accounts (quotas). 1,024 GB of EBS per instance.
  • Per job: 100 hyperparameters (keys up to 256 characters, values up to 2,500), 20 channels, 40 metric definitions, 50 tags, names up to 63 characters unique per Region. CreateTrainingJob is limited to one call per second.
  • Pricing: per instance-hour for the instance type, plus storage, for the billable time (including download and upload). Tuning adds no charge; Debugger built-in rules are free. The free tier gives 50 hours a month of ml.m4.xlarge or ml.m5.xlarge training for two months; SageMaker Savings Plans cover training.
