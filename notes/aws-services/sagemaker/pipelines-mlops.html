The MLOps pieces

  1. BuildSageMaker Pipelines runs the repeatable workflow: prepare data, train, evaluate, and register the model only if it's good enough.
  2. VersionThe Model Registry keeps each registered model as a numbered version in a model package group, with metrics, an approval status and lifecycle stages.
  3. ApproveA person (or an automated test) sets the version to Approved; IAM can restrict who may do that.
  4. DeployThe approval event starts a deployment pipeline (CodePipeline, Lambda or a pipeline step) that rolls the version to staging, then production, with deployment guardrails.
  5. Trace and repeatLineage tracking records what data, code and image produced each model; monitoring or a schedule triggers retraining.

SageMaker Projects package all of this as templates with source repositories and CI/CD already wired up, and MLflow (see managed MLflow) tracks experiments. None of them is required: Pipelines works without a project.

How a pipeline is built

A pipeline is a directed graph of steps, defined in JSON and usually written with the Python SDK, the drag-and-drop designer in Studio (since August 2024) or the API. Order comes from data dependencies: when one step's input is another step's output property, the second waits for the first. depends_on adds an explicit order.

  • Job steps: Processing, Training, Tuning, AutoML (ensembling mode only), Transform, EMR and EMR Serverless, Notebook Job, and in the designer Execute code (runs as a training job) and Fine-tune model (a JumpStart model).
  • Model steps: ModelStep creates or registers a model (the older CreateModelStep and RegisterModel still work but are no longer supported); the designer has a Deploy model step, and SDK V3 added endpoint configuration, endpoint and inference component steps in September 2026.
  • Control steps: Condition (if and else branches), Fail (stops the run with a message), Callback (sends an SQS message and waits for SendPipelineExecutionStepSuccess or Failure), Lambda (up to 10 minutes, same Region), and in SDK V3 ForEach and Cleanup (October 2026).
  • Check steps: ClarifyCheck (bias and explainability) and QualityCheck (data and model quality) compare against baselines; both depend on Clarify and Model Monitor, which have been closed to new customers since 30 July 2026, so new users run the checks in a Processing step.
  • @step turns a plain Python function into a step that runs as a training job; it doesn't support caching or property files.
  • Parameters (ParameterString, ParameterInteger, ParameterFloat, ParameterBoolean; up to 200) are set per run. Properties mirror the step's Describe response, such as step_train.properties.ModelArtifacts.S3ModelArtifacts. JsonGet with a PropertyFile reads a value from a JSON file a Processing step wrote, such as an evaluation metric for a condition. Execution variables such as PIPELINE_EXECUTION_ID resolve at run time.

Don't put secrets in parameters or step environment variables: DescribePipeline returns them in the definition. Pass a Secrets Manager name and read it in the code instead.

A pipeline in SDK V3

In SDK V3 the primitives (parameters, properties, conditions, functions) are in sagemaker.core.workflow and the pipeline and steps in sagemaker.mlops.workflow. Steps get their arguments by calling the job's normal method (run(), train(), register()) under a PipelineSession, which records the request instead of starting a job.

Prepare, train, evaluate, and register only if the error is low enough (Python, SageMaker Python SDK V3) 
from sagemaker.core import image_uris
from sagemaker.core.helper.session_helper import Session, get_execution_role
from sagemaker.core.processing import ScriptProcessor
from sagemaker.core.shapes import ProcessingInput, ProcessingOutput, ProcessingS3Input, ProcessingS3Output
from sagemaker.core.training.configs import Compute, InputData
from sagemaker.core.workflow.conditions import ConditionLessThanOrEqualTo
from sagemaker.core.workflow.functions import JsonGet
from sagemaker.core.workflow.parameters import ParameterFloat, ParameterString
from sagemaker.core.workflow.pipeline_context import PipelineSession
from sagemaker.core.workflow.properties import PropertyFile
from sagemaker.mlops.workflow.condition_step import ConditionStep
from sagemaker.mlops.workflow.fail_step import FailStep
from sagemaker.mlops.workflow.model_step import ModelStep
from sagemaker.mlops.workflow.pipeline import Pipeline
from sagemaker.mlops.workflow.steps import CacheConfig, ProcessingStep, TrainingStep
from sagemaker.serve import ModelBuilder
from sagemaker.train import ModelTrainer

ps = PipelineSession()
role = get_execution_role()
region = Session().boto_region_name
bucket = "ml-111111111111"

input_uri = ParameterString(name="InputDataUrl", default_value=f"s3://{bucket}/raw/churn.csv")
mse_max = ParameterFloat(name="MseThreshold", default_value=6.0)
# Off by default; reuse a successful run with the same inputs for 30 days
cache = CacheConfig(enable_caching=True, expire_after="P30D")


def s3_in(name, uri):
    return ProcessingInput(input_name=name, s3_input=ProcessingS3Input(
        s3_uri=uri, local_path=f"/opt/ml/processing/{name}", s3_data_type="S3Prefix", s3_input_mode="File"))


def s3_out(name):
    return ProcessingOutput(output_name=name, s3_output=ProcessingS3Output(
        s3_uri=f"s3://{bucket}/churn/{name}", local_path=f"/opt/ml/processing/{name}", s3_upload_mode="EndOfJob"))


sk_image = image_uris.retrieve(framework="sklearn", region=region, version="1.2-1",
                               py_version="py3", instance_type="ml.m5.xlarge")
proc = ScriptProcessor(image_uri=sk_image, instance_type="ml.m5.xlarge", instance_count=1,
                       role=role, sagemaker_session=ps)

step_prep = ProcessingStep(name="Prep", cache_config=cache, step_args=proc.run(
    code="code/preprocess.py", inputs=[s3_in("raw", input_uri)],
    outputs=[s3_out("train"), s3_out("validation"), s3_out("test")]))

xgb_image = image_uris.retrieve(framework="xgboost", region=region, version="1.7-1")
trainer = ModelTrainer(training_image=xgb_image, role=role, sagemaker_session=ps,
                       compute=Compute(instance_type="ml.m5.xlarge", instance_count=1),
                       hyperparameters={"objective": "reg:squarederror", "num_round": 50})
prep_out = step_prep.properties.ProcessingOutputConfig.Outputs
# V3 TrainingStep has no estimator argument: step_args must come from train()
step_train = TrainingStep(name="Train", cache_config=cache, step_args=trainer.train(input_data_config=[
    InputData(channel_name="train", data_source=prep_out["train"].S3Output.S3Uri),
    InputData(channel_name="validation", data_source=prep_out["validation"].S3Output.S3Uri),
]))

model_uri = step_train.properties.ModelArtifacts.S3ModelArtifacts
report = PropertyFile(name="EvalReport", output_name="evaluation", path="evaluation.json")
step_eval = ProcessingStep(name="Evaluate", property_files=[report], step_args=proc.run(
    code="code/evaluate.py",
    inputs=[s3_in("model", model_uri), s3_in("test", prep_out["test"].S3Output.S3Uri)],
    outputs=[s3_out("evaluation")]))

mb = ModelBuilder(s3_model_data_url=model_uri, image_uri=xgb_image, role_arn=role, sagemaker_session=ps)
step_register = ModelStep(name="Register", step_args=mb.register(
    model_package_group_name="churn-models", content_types=["text/csv"], response_types=["text/csv"],
    inference_instances=["ml.m5.xlarge"], approval_status="PendingManualApproval"))

# Every condition in the list must be true; there's no nesting
step_check = ConditionStep(
    name="CheckMse",
    conditions=[ConditionLessThanOrEqualTo(
        left=JsonGet(step_name=step_eval.name, property_file=report, json_path="regression_metrics.mse.value"),
        right=mse_max)],
    if_steps=[step_register],
    else_steps=[FailStep(name="MseTooHigh", error_message="MSE above threshold")],
)

pipeline = Pipeline(name="churn-train", parameters=[input_uri, mse_max],
                    steps=[step_prep, step_train, step_eval, step_check], sagemaker_session=ps)
pipeline.upsert(role_arn=role)  # create, or update if it exists
execution = pipeline.start(parameters={"MseThreshold": 5.5})
execution.wait()

The evaluation script writes evaluation.json such as {"regression_metrics": {"mse": {"value": 4.2}}}. In SDK V2 the same classes live in sagemaker.workflow.*, training uses an Estimator (TrainingStep(step_args=estimator.fit(...))), and registration is ModelStep(step_args=model.register(...)); AWS's documentation pages still mix the two, so check the import paths when copying.

Running pipelines

  • Executions are Executing, Stopping, Stopped, Failed, Succeeded or CompletedWithFailures (with SDK V3 run conditions, when steps that run after a failure finish). Every update creates a pipeline version, and a run can name a PipelineVersionId.
  • Caching works for Processing, Training, Tuning, AutoML, Transform, check and EMR steps, within one pipeline, reusing the latest successful run with identical arguments until expire_after (an ISO 8601 duration).
  • Retries: service faults and throttling are retried automatically; add SageMakerJobStepRetryPolicy for CAPACITY_ERROR, RESOURCE_LIMIT or INTERNAL_ERROR with either max_attempts (up to 20) or expire_after_mins (up to 14,400), not both. RetryPipelineExecution restarts a failed run from the failed steps.
  • Selective execution reruns chosen steps and takes the other steps' outputs from an earlier run, handy while debugging one step.
  • Parallelism: ready steps run in parallel unless ParallelismConfiguration.MaxParallelExecutionSteps limits them, per execution.
  • Scheduling and triggers: a pipeline can be an EventBridge rule target (for example on new data in S3), or scheduled with pipeline.put_triggers(triggers=[PipelineSchedule(name=..., cron=...)], role_arn=...) through EventBridge Scheduler. Deleting a pipeline doesn't delete its schedules.
  • Local mode (LocalPipelineSession) runs Training, Processing, Transform, Model, Condition and Fail steps in Docker on your machine, one at a time, for quick tests.
  • Sharing: AWS RAM can share a pipeline read-only, or with permission to start, stop and retry runs, which then run in the owner's account.

A run that ends in a Fail step can't be retried, and nothing can depend on a Fail step. Callback and Lambda steps also block stopping: the run waits for the callback answer or the Lambda function to finish (or time out, by default after 120 seconds while the function keeps running).

Model Registry

A model package group holds the versions of one model (1, 2, 3...); each model package records the inference image and artifacts, supported content types and instance types, metrics reports (quality, bias, explainability), drift baselines, custom metadata (up to 50 entries), an optional model card and lineage. Groups can be organized into nested collections.

  • ModelApprovalStatus: PendingManualApproval, Approved or Rejected, changed with UpdateModelPackage (with an ApprovalDescription). Only Approved versions deploy from Studio and the project templates.
  • Lifecycle stages (November 2024): ModelLifeCycle with a Stage (such as Development, QA, PreProduction, Production, Archived) and a StageStatus (such as PendingApproval, Approved, Rejected, Retired). Stage changes are searchable and emit events, and IAM condition keys can limit who moves a model into a stage. A stage doesn't replace the approval status.
  • Rollback: with the project templates, changing an approved version to Rejected redeploys the latest remaining approved version.
  • MLflow: models registered in managed MLflow can be registered automatically in the Model Registry as well.
  • Deploy a version by naming it in the model: create_model(Containers=[{"ModelPackageName": ARN}]), or ModelBuilder(model=ARN, ...) in SDK V3; the image and artifacts come from the package.
  • Tags come from the group: CreateModelPackage with a group name can't take its own tags.

Deploying on approval

Every change to a model package emits a "SageMaker Model Package State Change" event. An EventBridge rule that matches approved versions of one group can start a CodePipeline deployment pipeline or a Lambda function.

EventBridge rule pattern: approved versions of churn-models (JSON) 
{
  "source": ["aws.sagemaker"],
  "detail-type": ["SageMaker Model Package State Change"],
  "detail": {
    "ModelPackageGroupName": ["churn-models"],
    "ModelApprovalStatus": ["Approved"]
  }
}
deploy_approved.py: create or update the endpoint for the approved version (Python, AWS Lambda) 
import time

import boto3
from botocore.exceptions import ClientError

sm = boto3.client("sagemaker")
ROLE = "arn:aws:iam::111111111111:role/SageMakerDeployRole"
ENDPOINT = "churn-prod"


def handler(event, context):
    arn = event["detail"]["ModelPackageArn"]
    # Events can repeat and fire for any field change, so check the current state
    pkg = sm.describe_model_package(ModelPackageName=arn)
    if pkg["ModelApprovalStatus"] != "Approved":
        return {"skipped": arn}

    model = f"churn-v{pkg['ModelPackageVersion']}-{int(time.time())}"
    sm.create_model(ModelName=model, ExecutionRoleArn=ROLE, Containers=[{"ModelPackageName": arn}])
    sm.create_endpoint_config(EndpointConfigName=model, ProductionVariants=[{
        "VariantName": "AllTraffic", "ModelName": model,
        "InstanceType": "ml.m5.xlarge", "InitialInstanceCount": 2,
    }])
    try:
        sm.describe_endpoint(EndpointName=ENDPOINT)
    except ClientError:
        sm.create_endpoint(EndpointName=ENDPOINT, EndpointConfigName=model)
        return {"created": arn}
    # Add a DeploymentConfig here for canary rollout and alarm rollback
    sm.update_endpoint(EndpointName=ENDPOINT, EndpointConfigName=model)
    return {"updated": arn}

AWS's deployment template does the same with CloudFormation: a build stage generates stack parameters for the approved version, deploys to staging, waits for a manual approval in CodePipeline, then deploys to production. Pipeline runs also emit "SageMaker Model Building Pipeline Execution Status Change" and step status events for notifications.

Across accounts

A common layout keeps a central registry in a shared account, trains in a development account and deploys from staging and production accounts. Share a group with a resource policy (PutModelPackageGroupPolicy) or through AWS RAM (since June 2024; custom RAM permissions must be promoted before the group is visible).

Model package group policy: let account 222222222222 read and deploy versions (JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadGroup",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::222222222222:root"},
      "Action": "sagemaker:DescribeModelPackageGroup",
      "Resource": "arn:aws:sagemaker:us-east-1:111111111111:model-package-group/churn-models"
    },
    {
      "Sid": "UseVersions",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::222222222222:root"},
      "Action": [
        "sagemaker:DescribeModelPackage",
        "sagemaker:ListModelPackages",
        "sagemaker:UpdateModelPackage",
        "sagemaker:CreateModel"
      ],
      "Resource": "arn:aws:sagemaker:us-east-1:111111111111:model-package/churn-models/*"
    }
  ]
}

The group policy alone isn't enough to deploy in another account: the ECR repository policy, the S3 bucket policy for the artifacts and a KMS key grant must also allow that account, and AWS requires the training output to be encrypted with a customer managed KMS key for cross-account deployment. To register from another account, allow sagemaker:CreateModelPackage on model-package/churn-models/* and call it with the group's ARN.

Projects

A project provisions an MLOps setup from a template and tags every resource with the project name and ID. AWS's templates connect to GitHub or Bitbucket through an AWS CodeStar connection (tagged sagemaker=true) and use CodePipeline and CodeBuild, or Jenkins:

  • Model building and training: a pipeline in the repository; each commit upserts and runs it.
  • Model deployment: deploys approved versions to staging, then, after a manual approval, to production.
  • Both together, with Model Monitor, or with a container image build.
  • Your own templates: CloudFormation templates in S3 (since October 2025, now AWS's recommendation) or AWS Service Catalog products, shown in Studio when tagged sagemaker:studio-visibility=true.

The CodeCommit-based project templates were removed (unsupported from 9 September 2024, removed by 28 October 2024) and didn't return when CodeCommit itself came back to general availability in November 2025. Some documentation pages still describe CodeCommit repositories in templates. MLA-C02 still names CodeCommit among the CI/CD services to know.

Projects need the AmazonSageMakerServiceCatalogProducts* service roles that Studio creates when project templates are turned on for the domain (don't create them by hand), and each user's execution role must be added to the "Amazon SageMaker Solutions and ML Ops products" portfolio. SageMaker Unified Studio projects are a different, DataZone-based construct.

Lineage, experiments and notebook jobs

  • ML Lineage Tracking records artifacts (datasets, images, models), actions (steps, deployments), contexts (endpoints, model groups) and their associations. Jobs, model packages and endpoints create entities automatically; QueryLineage walks up or down the graph (up to 10 hops), for example from an endpoint back to its training data. S3 artifacts are identified by URI, not content, so overwrite-in-place breaks the trail.
  • Experiments: the classic SageMaker Experiments SDK works only in Studio Classic; AWS recommends MLflow. Pipelines create an experiment per pipeline and a run group per execution, and can log to an MLflow experiment.
  • Notebook jobs run a notebook on a schedule (as a training job) from Studio or JupyterLab, or as a NotebookJobStep in a pipeline.

Other orchestrators

  • AWS Step Functions has optimized SageMaker integrations for training, processing, tuning, transform, model, endpoint configuration and endpoint calls (with .sync to wait for jobs). It suits workflows that mix ML with many other AWS services; it has no task-token callback for SageMaker jobs.
  • Apache Airflow (including Amazon MWAA) can drive SageMaker through its SageMaker integrations, for teams that already schedule data pipelines there.
  • Kubernetes: SageMaker operators and Kubeflow Pipelines components run SageMaker jobs from a cluster.
  • AWS Batch can queue training jobs with quotas and preemption between teams (2025 and 2026).

AWS lists Pipelines' advantages as serverless scaling, the visual editor, deep SageMaker integration, lineage and versioning; exam questions about "automating an ML workflow with SageMaker components and lineage" point to Pipelines.

Security, quotas and pricing

  • Roles: the pipeline's execution role runs each step unless the step's job names its own role (then the pipeline role needs iam:PassRole on it). The role needs create and describe permissions for each job type, and s3:GetObject for JsonGet. Callers need iam:PassRole on the pipeline role.
  • Job names: by default pipelines-EXECUTIONID-STEP-...; turn on custom prefixes (PipelineDefinitionConfig(use_custom_job_prefix=True)) to write IAM policies on job name patterns.
  • Network and encryption are set on each job (VPC, network isolation, KMS keys), and the usual condition keys (sagemaker:VpcSubnets, sagemaker:NetworkIsolation, sagemaker:VolumeKmsKey, sagemaker:OutputKmsKey) apply. sagemaker:ModelApprovalStatus on UpdateModelPackage limits who can approve.
  • Quotas: 500 pipelines per account and 20 concurrent executions (both adjustable), 50 steps per pipeline and 200 parameters (not adjustable), a 1 MB definition inline (larger from S3), 250 model package groups and 10,000 model packages, 500 projects.
  • Pricing: AWS says you pay only for Studio and the jobs and storage the pipeline uses; the Model Registry, Projects and lineage have no line on the pricing page, but Projects create CodePipeline, CodeBuild and other billable resources.

What's changed

  • 2026: EMR Serverless step in SDK V3 (January); Clarify and Model Monitor, behind the check steps, closed to new customers (30 July); fine-tuning trainers in pipelines (September); endpoint, inference component and lineage steps (24 September); MLA-C02 replaced MLA-C01 (29 September); JobStep (October); run conditions on dependencies (19 October); ForEach and Cleanup steps (21 October); AthenaStep (29 October).
  • 2025: Studio to Unified Studio upgrade (June); MLflow 3.0 (July); pipeline versioning (August); Projects templates from S3 (3 October); SDK V3 with sagemaker.mlops.workflow (November); MLflow Apps with automatic registration in the Model Registry (November); CodeCommit back to general availability (November).
  • 2024: Projects in the new Studio (April); model cards in the Model Registry (June); cross-account sharing of model groups through RAM (June); Pipelines visual designer (15 August); CodeCommit project templates retired (September and October); Model Registry lifecycle stages and lineage view (8 November).
