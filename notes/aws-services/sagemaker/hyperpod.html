What HyperPod is for

SageMaker HyperPod gives you a persistent cluster of accelerated instances that SageMaker AI watches and repairs: when a GPU or Trainium chip fails, it detects the fault, replaces or reboots the node, and lets the job resume. AWS's FAQ puts it at "longer and larger training workloads that require high amount of compute instances", and it can run training and inference on the same cluster. It's in 18 Regions.

  • Choose a training job when each run is self-contained: SageMaker starts and stops the instances, and you pay per job.
  • Choose serverless customization to fine-tune a supported model without choosing any instances.
  • Choose HyperPod for weeks-long pre-training or fine-tuning on dozens or hundreds of GPUs, for a shared cluster that several teams queue work on, for Slurm or Kubernetes tooling your researchers already use, or for Nova continued pre-training, which runs only on HyperPod.

You pay for the instances for as long as the cluster holds them, busy or not, so a cluster only pays off when it's kept full.

Since 26 February 2026 Slurm is configured through the API: each instance group gets SlurmConfig with a NodeType (Controller, Login or Compute, fixed once set) and, for compute groups, one PartitionNames entry. The old provisioning_parameters.json file in the lifecycle-script folder still works but is now called legacy. Orchestrator.Slurm.SlurmConfigStrategy decides what happens to manual edits of slurm.conf: Managed (the default) makes cluster updates fail if the file drifted, Overwrite replaces it, and Merge keeps your changes.

Creating a cluster

For EKS, first create the EKS cluster (Kubernetes 1.30 to 1.35, authentication mode API or API_AND_CONFIG_MAP) and, if you're not using the console or the CloudFormation quick start, install the HyperPod Helm chart from helm_chart/HyperPodHelmChart in the sagemaker-hyperpod-cli repository. It brings the health monitoring agent, the Kubeflow training and MPI operators, the NVIDIA, Neuron and EFA device plugins and Kueue. Install it before calling CreateCluster.

An EKS-orchestrated cluster with one GPU group (Python, boto3) 
import boto3

sm = boto3.client("sagemaker", region_name="us-west-2")
resp = sm.create_cluster(
    ClusterName="ml-cluster",
    Orchestrator={"Eks": {"ClusterArn": "arn:aws:eks:us-west-2:111111111111:cluster/ml-eks"}},
    InstanceGroups=[{
        "InstanceGroupName": "gpu-workers",
        "InstanceType": "ml.p5.48xlarge",
        "InstanceCount": 4,
        # The bucket name must start with sagemaker- or the instance role can't read it
        "LifeCycleConfig": {"SourceS3Uri": "s3://sagemaker-ml-111111111111/lifecycle/", "OnCreate": "on_create.sh"},
        "ExecutionRole": "arn:aws:iam::111111111111:role/HyperPodInstanceRole",
        "ThreadsPerCore": 1,
        # Adds about 2 hours per node before it takes work
        "OnStartDeepHealthChecks": ["InstanceStress", "InstanceConnectivity"],
        # Extra EBS volume, mounted at /opt/sagemaker
        "InstanceStorageConfigs": [{"EbsVolumeConfig": {"VolumeSizeInGB": 500}}],
    }],
    # Private subnets; the security group must allow all traffic from itself (EFA)
    VpcConfig={"SecurityGroupIds": ["sg-0hyperpod"], "Subnets": ["subnet-0aaa"]},
    NodeRecovery="Automatic",
    NodeProvisioningMode="Continuous",
    Tags=[{"Key": "team", "Value": "research"}],
)
print(resp["ClusterArn"])
  • Only ClusterName is required by the API; Orchestrator takes exactly one of Eks or Slurm. Each instance group needs a name, a count (0 to 6,758) and an execution role; up to 100 groups.
  • Continuous provisioning (NodeProvisioningMode="Continuous", now the default for new clusters) provisions nodes in the background with retries and partial success, keeps groups in service while they scale, records ListClusterEvents, and doesn't bill for launches that fail. Flexible instance groups (InstanceRequirements with up to 20 types in priority order), MinInstanceCount, customer managed EBS keys and logical node IDs all need it.
  • Fixed after creation: the cluster VpcConfig, a group's OverrideVpcConfig, its Spot or On-Demand capacity type, a Slurm NodeType and an EBS key. Plan subnets for growth: a p5.48xlarge takes 81 IP addresses on EKS and 32 on Slurm.
  • Other ways in: the console's quick and custom setups, CloudFormation AWS::SageMaker::Cluster, Terraform awscc_sagemaker_cluster, hyp init cluster-stack in the CLI, and the SageMaker AI MCP server.
  • Change it later with UpdateCluster (counts, new groups, InstanceGroupsToDelete), BatchAddClusterNodes and BatchDeleteClusterNodes.

Nodes, access and software

  • Lifecycle scripts: OnCreate (usually on_create.sh) runs on every new node; AWS's base scripts in aws-samples/awsome-distributed-training set up Slurm, users, FSx mounts and Docker. HyperPod writes a resource_config.json on each node describing the cluster. A failing script fails the node, so test changes on a small group.
  • Access: through Session Manager, with the target sagemaker-cluster:CLUSTERID_GROUPNAME-INSTANCEID (users need ssm:StartSession); SSH works through AWS-StartSSHSession as a proxy. On Slurm you arrive as root and switch to ubuntu. On EKS, users also need an EKS access entry and Kubernetes RBAC.
  • Images: HyperPod's public AMIs (Ubuntu 22.04 for Slurm, AL2023 for EKS), or your own AMI built from one (EKS since August 2025, Slurm since July 2026). Since July 2026 you can pin an ImageReleaseVersion, roll back, and set AutoPatchConfig to patch when nodes are idle.
  • UpdateClusterSoftware rolls nodes to a new AMI and replaces the root volume, so anything stored there is lost; keep data on FSx, S3 or the /opt/sagemaker volume.
  • EKS pods per node are limited because each HyperPod instance gets one network interface (49 pods on p5.48xlarge). Pods can't reach the instance metadata service unless they use the host network; give them AWS access with EKS Pod Identity or IRSA. Don't install a local NVMe CSI driver: it conflicts with the volume group the AMI builds.

Resiliency

  1. Check before workOptional deep health checks when nodes join: InstanceStress (DCGM diagnostics, NVLink, EFA loopback; Neuron tests on Trainium) and InstanceConnectivity (NCCL or NCCOM across nodes); the developer guide also lists MultiNodeTrainingValidation (Megatron runs, EKS on EFA GPUs). About 2 hours per node; failing nodes are replaced. StartClusterHealthCheck runs them on demand.
  2. WatchThe health monitoring agent on every GPU and Trainium node reads DCGM, nvidia-smi, Neuron monitors and EC2 platform logs.
  3. MarkOn EKS a faulty node gets the label sagemaker.amazonaws.com/node-health-status (Unschedulable, UnschedulablePendingReboot or UnschedulablePendingReplacement) and a NoSchedule taint; on Slurm it's drained.
  4. RepairWith NodeRecovery="Automatic", HyperPod reboots or replaces the node. You can also trigger it with BatchRebootClusterNodes or BatchReplaceClusterNodes (up to 25 nodes per call) or from the console.
  5. ResumeThe job restarts from its last checkpoint on healthy nodes, or keeps going without one (checkpointless training).

CPU-only nodes are never replaced automatically: the agent and deep health checks cover GPU and Trainium instances only. BatchReplaceClusterNodes wipes both the root and secondary volumes, and on a Karpenter-managed cluster a replaced node isn't guaranteed to come back.

train.sbatch: a Slurm job that resumes after a node is replaced (Bash) 
#!/bin/bash
#SBATCH --job-name=llama-pretrain
#SBATCH --nodes=8
#SBATCH --exclusive
#SBATCH --output=logs/%x_%j.out

# Auto-resume reruns this step on the replacement node set.
# Do all setup inside the script, and build the node list with scontrol there:
# $SLURM_JOB_NODELIST can be stale after a replacement.
srun --auto-resume=1 ./train_auto_resume.sh

Auto-resume applies only to the srun step it's on, needs an exclusive allocation, and always replaces rather than reboots the faulty node. The training code must save checkpoints to shared storage and load the latest one at start.

Training jobs on EKS

You can submit standard Kubeflow PyTorchJobs, but the HyperPod training operator (EKS add-on amazon-sagemaker-hyperpod-training-operator, which needs cert-manager and the EKS Pod Identity Agent) adds finer recovery: it restarts only the failed processes, watches logs for hangs, and can keep spare nodes. Its images must include the HyperPod elastic agent and start with hyperpodrun instead of torchrun.

job.yaml: a HyperPodPyTorchJob in a team queue (YAML, kubectl apply) 
apiVersion: sagemaker.amazonaws.com/v1
kind: HyperPodPyTorchJob
metadata:
  name: llama-sft
  namespace: hyperpod-ns-research
  labels:
    # Task governance queue and priority (see the next section)
    kueue.x-k8s.io/queue-name: hyperpod-ns-research-localqueue
    kueue.x-k8s.io/priority-class: training-priority
spec:
  nprocPerNode: "8"
  runPolicy:
    jobMaxRetryCount: 3
    cleanPodPolicy: None
  replicaSpecs:
    - name: workers
      replicas: 4
      template:
        spec:
          containers:
            - name: trainer
              image: 111111111111.dkr.ecr.us-west-2.amazonaws.com/llama-train:1.0
              command: ["hyperpodrun", "--nproc-per-node=8", "train.py"]
              resources:
                limits:
                  nvidia.com/gpu: 8
                  vpc.amazonaws.com/efa: 32

The CLI equivalent is hyp create hyp-pytorch-job --job-name llama-sft --image IMAGE --instance-type ml.p5.48xlarge --tasks-per-node 8 --queue-name hyperpod-ns-research-localqueue, after hyp set-cluster-context --cluster-name ml-cluster. The hyperpodrun arguments shown follow torchrun's; check the operator guide for the exact flags.

Checkpointless training (3 December 2025)

Keeps the training state spread across the cluster and, when a node fails, swaps in a replacement and copies the state from healthy peers, so recovery takes minutes instead of reloading a checkpoint. It needs EKS, training operator 1.2.0 or later and elastic agent 1.1.0 or later, and is built on NVIDIA NeMo; AWS provides recipes for gpt-oss 120B and Llama 3 70B on p5.48xlarge.

Elastic training (3 December 2025)

Lets a job grow and shrink its number of data-parallel replicas as nodes come and go (spec.elasticPolicy with minReplicas, maxReplicas and a step), with PyTorch DDP or FSDP and distributed checkpoints. It can't be combined with checkpointless training, managed tiered checkpointing or Spot.

Managed tiered checkpointing (8 September 2025)

Turned on per cluster with TieredStorageConfig={"Mode": "Enable"}: checkpoints go to CPU memory, are copied to neighbouring nodes and are written to S3 periodically, so frequent checkpoints cost little. Training code uses the amzn-sagemaker-checkpointing library with PyTorch distributed checkpoint async_save. EKS only.

Task governance, Spot and autoscaling

Task governance (EKS add-on amazon-sagemaker-hyperpod-taskgovernance, which installs its own Kueue, so remove any existing Kueue first) shares one cluster between teams:

  • Cluster policy (CreateClusterSchedulerConfig): up to 10 priority classes with weights, fair share on or off (off means first come, first served), and optional sharing of idle, unallocated capacity.
  • Compute allocation per team (CreateComputeQuota): instances, accelerators, vCPU or memory (including GPU partitions); whether the team lends idle capacity, borrows (up to a BorrowLimit percentage, 50 by default) or both; and whether higher-priority work may preempt the team's lower-priority tasks.
  • Naming: each team gets namespace hyperpod-ns-TEAM and queue hyperpod-ns-TEAM-localqueue; jobs pick a priority with the label kueue.x-k8s.io/priority-class: NAME-priority. An unknown class rejects the job; none means the lowest rank.
  • Spot (EKS only, since 24 November 2025): set CapacityRequirements={"Spot": {}} on an instance group, up to 90% off On-Demand. HyperPod drains the node on the best-effort two-minute notice and replaces capacity; jobs must checkpoint. The Spot quotas start at 0.
  • Karpenter autoscaling (18 September 2025): AutoScaling={"Mode": "Enable", "AutoScalerType": "Karpenter"} plus a ClusterRole that HyperPod assumes to add and remove nodes, groups starting at 0 instances, and a HyperpodNodeClass referenced from Karpenter NodePools. It can fall back from Spot to On-Demand groups.
  • GPU partitioning (MIG) on p4d, p4de, p5, p5e, p5en and B200 instances splits a GPU into up to seven slices for small jobs, notebooks and inference (not on flexible instance groups).

Recipes, data and observability

  • Recipes (aws/sagemaker-hyperpod-recipes, now version 2): tested YAML configurations for pre-training, SFT, DPO, LoRA and RL of Nova, Llama, Qwen, DeepSeek R1 Distill, gpt-oss, Gemma 4 and other families, launched with python3 main.py recipes=PATH cluster=k8s ... or the launcher scripts. The same recipes run on training jobs (ModelTrainer.from_recipe); on Slurm only the LLM fine-tuning recipes are supported.
  • HyperPod CLI v3 (pip install sagemaker-hyperpod, Linux and macOS): hyp list-cluster, hyp set-cluster-context, hyp create, list, describe, delete and get-logs for hyp-pytorch-job, plus template-driven hyp init, configure, validate. Some AWS pages still show the older hyperpod start-job commands of CLI v2.
  • Data: FSx for Lustre in the same Availability Zone for training data and checkpoints (set per group in InstanceStorageConfigs on Slurm), S3 through Mountpoint or a gateway endpoint, EFS, and EBS through the CSI driver.
  • Observability: the HyperPod observability add-on sends GPU, EFA, file system, Kueue and job metrics to Amazon Managed Service for Prometheus with Amazon Managed Grafana dashboards; cluster and node logs go to CloudWatch /aws/sagemaker/Clusters/...; Container Insights and EventBridge events cover status changes.
  • Developer tools: JupyterLab and Code Editor spaces on EKS clusters (the SageMaker Spaces add-on, November 2025), HyperPod clusters visible in Studio, the SageMaker AI MCP server (read-only unless started with --allow-write), and HyperPod troubleshooting skills for coding assistants (June 2026).

HyperPod inference

Since July 2025, EKS clusters can host models through the HyperPod inference operator (EKS add-on amazon-sagemaker-hyperpod-inference; it needs the AWS Load Balancer Controller, KEDA, cert-manager and the S3 and FSx CSI drivers). You declare a JumpStartModel (a public-hub model ID) or an InferenceEndpointConfig (your weights in S3 or FSx), and the operator runs it, puts a load balancer in front, scales it with KEDA on CloudWatch metrics and can register a SageMaker endpoint so clients call it with InvokeEndpoint.

llama.yaml: serve weights from S3 with vLLM and KV-cache-aware routing (YAML, kubectl apply) 
apiVersion: inference.sagemaker.aws.amazon.com/v1
kind: InferenceEndpointConfig
metadata:
  name: llama-s3
  namespace: default
spec:
  modelName: Llama-3.1-8B-Instruct
  instanceType: ml.g5.24xlarge
  invocationEndpoint: v1/chat/completions
  replicas: 2
  modelSourceConfig:
    modelSourceType: s3
    s3Storage:
      bucketName: models-111111111111
      region: us-west-2
    modelLocation: Llama-3.1-8B-Instruct
    prefetchEnabled: true
  # vLLM only; prefixaware is the default strategy
  intelligentRoutingSpec:
    enabled: true
    routingStrategy: prefixaware
  worker:
    image: vllm/vllm-openai:v0.19.1
    modelInvocationPort:
      containerPort: 8000
      name: http
    modelVolumeMount:
      name: model-weights
      mountPath: /opt/ml/model
    resources:
      limits:
        nvidia.com/gpu: 4
      requests:
        cpu: 30000m
        memory: 100Gi
        nvidia.com/gpu: 4
    args: ["--model", "/opt/ml/model", "--port", "8000", "--tensor-parallel-size", "4"]
  • Managed tiered KV cache and intelligent routing (November 2025): kvCacheSpec keeps attention caches in memory (L1) and in Redis or HyperPod tiered storage (L2), and routing sends requests to the replica most likely to hold the prefix: prefixaware, kvaware (needs invocationEndpoint set to /completions), session or roundrobin.
  • Inference Gateway (24 September 2026): part of the inference add-on from version 2.0.0, built on the Kubernetes Gateway API inference extension; enable it per model with spec.inferenceGateway.enabled, instead of (not with) intelligentRoutingSpec. Needs vLLM 0.9.2 or later or SGLang with metrics.
  • Also: data capture (May 2026), disaggregated prefill and decode (pdSpec, July 2026), model weight and image caching (September 2026), and fallback across instance types.

The Inference Gateway has no request authentication by default; AWS strongly recommends configuring spec.auth.jwt. KV cache data isn't encrypted at rest, and the managed tiered L2 store isn't isolated between deployments on the same cluster, so don't mix tenants that mustn't see each other's prompts.

Security and networking

  • Instance execution role: attach AmazonSageMakerClusterInstanceRolePolicy (CloudWatch metrics and logs, SSM messages, and S3 reads from buckets named sagemaker-*). EKS nodes also need network-interface and ECR permissions; Slurm in your own VPC needs network-interface permissions for auto-resume. AWS's IAM page says to start from AmazonSageMakerHyperPodServiceRolePolicy, but that is the policy of the service-linked role AWSServiceRoleForSageMakerHyperPod, which SageMaker creates for itself.
  • Enforce settings on CreateCluster and UpdateCluster with sagemaker:InstanceTypes, sagemaker:VpcSubnets and sagemaker:VpcSecurityGroupIds.
  • EFA: the security group must allow all inbound and outbound traffic to and from itself (an outbound rule to 0.0.0.0/0 alone makes EFA health checks fail), and EFA traffic can't cross Availability Zones, so keep a training group in one subnet. efa-only interfaces (June 2026) use no IP addresses.
  • Encryption: EBS volumes can use a customer managed key (VolumeKmsKeyId; the root volume with RootVolume: true) in continuous mode only, not in the console or on restricted instance groups, and the key can't be changed later. The role needs kms:CreateGrant and kms:DescribeKey.

Quotas and pricing

A new account can't create a useful cluster: "Total number of instances allowed across SageMaker HyperPod clusters", its Spot equivalent and every ml.TYPE for cluster usage quota start at 0. The 20-instances-per-cluster default is a separate quota. Request increases (and check the VPC network-interface quota) before you build; the console checks quotas before creating a cluster.

  • Instances: billed per instance for as long as the cluster holds it, at HyperPod On-Demand rates, plus extra EBS storage. The EKS control plane, FSx and S3 are billed by those services. AWS's example: 4 ml.g5.24xlarge at $10.18 an hour for 720 hours plus 100 GB each comes to $29,374.40. Savings Plans eligibility for HyperPod isn't stated.
  • Spot: up to 90% off On-Demand, EKS only.
  • Flexible training plans: reserve GPU capacity for a HyperPod cluster (TrainingPlanArn on the group) for 1 to 182 days, up to 56 days ahead, paid upfront and not cancellable; AWS claims up to 65% savings. HyperPod offerings are in one Availability Zone, plans end at 11:30 UTC, and HyperPod instances stop an hour before the reservation ends, so checkpoint before then. See training plans.
  • Task governance is free; AWS claims up to 40% savings from sharing idle capacity.
