Decoupling

Skill 1.1.1Identify tightly coupled and loosely coupled systems, and use AWS services to decouple system components.

Tight and loose coupling

Components are tightly coupled when one calls another directly and waits: the order service calls the kitchen service's API, and if the kitchen service is slow or down, ordering is slow or down too. A traffic spike in one component hits the next one at full force, and every caller has to know where the other component lives.

Components are loosely coupled when they communicate through something in between, such as a queue, a topic or an event bus. The order service records "order placed" and moves on; the kitchen service picks the order up when it can. Each side can fail, scale and be deployed on its own, and new consumers can be added without changing the producer.

ServiceModelUse it when
Amazon SQSQueue: one consumer group pulls each messageBuffering work for a worker; smoothing spikes; retrying failed work
Amazon SNSTopic: pushes each message to every subscriberFan-out of one message to many queues, functions, HTTP endpoints, email or SMS
Amazon EventBridgeEvent bus: routes events by content to targetsMany event types and consumers; filtering on event content; AWS and SaaS events
AWS Step FunctionsWorkflow: one controller runs the stepsA multi-step process needs order, branching, retries and a visible state
Amazon Kinesis Data StreamsOrdered, replayable streamHigh-volume ordered records read by several consumers (streaming)

Amazon SQS

A producer sends a message; a consumer receives it, processes it and deletes it. While a consumer works on a message, it is hidden from others for the visibility timeout (default 30 seconds, up to 12 hours). If the consumer doesn't delete it in time, the message becomes visible again and is retried, so consumers must cope with seeing a message more than once.

SettingValue
Message sizeUp to 1 MiB (raised from 256 KiB in August 2025); larger payloads go in S3 with the Extended Client Library
RetentionDefault 4 days, 60 seconds to 14 days
Visibility timeoutDefault 30 seconds, 0 to 12 hours
Delay0 to 15 minutes, per queue or per message
Long pollingWaitTimeSeconds up to 20 seconds: fewer empty responses and lower cost
BatchUp to 10 messages per send, receive or delete call

Standard or FIFO

Standard queues have nearly unlimited throughput, deliver each message at least once and in roughly the order sent. FIFO queues (name ends in .fifo) keep strict order within a message group (MessageGroupId, required) and remove duplicates sent within a 5-minute window, using a MessageDeduplicationId or content-based deduplication (a hash of the body). FIFO throughput is 300 calls per second per action (3,000 messages with batches of 10), or far more in high-throughput mode, which scales per message group. Since 2025, standard queues also support fair queues: send with a MessageGroupId and one noisy tenant can't starve the others.

Dead-letter queues

A redrive policy on the source queue names a dead-letter queue (DLQ) and a maxReceiveCount. A message received that many times without being deleted moves to the DLQ, so one bad message ("poison pill") doesn't block or loop forever. Fix the cause, then redrive the messages back to the source queue (console or StartMessageMoveTask). The DLQ of a FIFO queue must be FIFO.

Send and receive orders (Python) 
import json
import boto3

sqs = boto3.client("sqs")

sqs.send_message(
    QueueUrl=ORDERS_URL,
    MessageBody=json.dumps(order),
)

resp = sqs.receive_message(
    QueueUrl=ORDERS_URL,
    MaxNumberOfMessages=10,
    WaitTimeSeconds=20,
)
for msg in resp.get("Messages", []):
    prepare(json.loads(msg["Body"]))
    handle = msg["ReceiptHandle"]
    sqs.delete_message(
        QueueUrl=ORDERS_URL,
        ReceiptHandle=handle,
    )

Delete only after processing succeeds; a crash before the delete means the message reappears after the visibility timeout and is processed again.

Amazon SNS and fan-out

When one order must reach the kitchen, the notification service and analytics, publish once to an SNS topic and subscribe an SQS queue for each consumer: fan-out. Each queue buffers for its own consumer, so a slow analytics job doesn't delay the kitchen. A subscription filter policy sends each subscriber only the messages it wants, matched on message attributes (default) or on the message body. SNS FIFO topics deliver in order to SQS FIFO queues. Messages are up to 256 KiB by default; since September 2026 a topic can allow up to 1 MiB, for SQS, Lambda and Firehose subscribers only.

Amazon EventBridge

Producers put events on an event bus; rules match events by content with an event pattern and send them to targets (up to 5 per rule) such as Lambda, SQS, SNS, Step Functions or API destinations. The default bus receives AWS service events; custom buses carry your application's events; partner buses carry SaaS events. Failed deliveries are retried for up to 24 hours (185 attempts) and can go to a DLQ. Archives keep events so you can replay them, Pipes connect one source to one target with optional filtering and enrichment, and Scheduler invokes targets on a schedule.

In September 2026 EventBridge relaunched custom event buses. The new Custom Event Bus (AWS's recommendation for new applications) uses subscribers, each with one target, and adds built-in retention and replay, ordered delivery within an event group, deduplication and non-JSON formats; it has its own CLI (aws eventsv2) and SDK client. The existing rules-and-targets model continues as Custom Event Bus – Classic, and the default bus works the same way. Events can be up to 1 MB in most Regions since January 2026.

"Buffer requests so the backend processes at its own pace" points to SQS. "Send the same message to several independent consumers" points to SNS fan-out to SQS queues. "Route events to different targets based on their content" or "react to AWS service events" points to EventBridge. "Strict order and no duplicates" points to SQS FIFO. "Messages that keep failing" points to a dead-letter queue.

Sync and async

Skill 1.1.2Choose between synchronous and asynchronous patterns (for example, Amazon API Gateway synchronous invocation, Amazon SQS based asynchronous processing, Amazon EventBridge event-driven workflows).

The choice

SynchronousThe caller waits for the result: API Gateway calls a Lambda function and returns its response to the client. Simple and immediate, but the caller is tied to the callee's latency and availability, and both scale together. Use it when the caller needs the answer now (checking the menu, validating a promo code).

AsynchronousThe caller hands off the work and gets an acknowledgment: the order API puts the order on a queue and returns "202 Accepted" with an order ID. The work happens later, retries are built in, and spikes are absorbed by the queue. The client learns the result by polling, a WebSocket message, or a notification.

PatternLimits to know
API Gateway REST API to Lambda (sync)Integration timeout up to 29 seconds by default (can be raised for Regional and private REST APIs); payload 10 MB; Lambda sync payload 6 MB each way
Lambda asynchronous invokePayload up to 1 MB (raised from 256 KB in October 2025); 2 retries on function errors; events kept up to 6 hours
API Gateway to SQS (async)An AWS service integration sends the request body as a message with no Lambda function in between
EventBridge (event-driven)Producers don't know consumers; retries up to 24 hours
Step FunctionsStandard workflows run up to a year (exactly-once steps); Express up to 5 minutes (at-least-once)

Lambda invocation types

The same function can be called both ways. With InvocationType set to RequestResponse (the default), the caller waits and gets the result (HTTP 200). With Event, Lambda queues the event, returns HTTP 202 at once, and runs the function later, retrying on errors. DryRun only checks parameters and permissions.

Synchronous and asynchronous invokes (Python) 
lam = boto3.client("lambda")
body = json.dumps(order).encode()

# wait for the price
r = lam.invoke(
    FunctionName="quote-price",
    Payload=body,
)
price = json.loads(r["Payload"].read())

# fire and forget: returns 202
lam.invoke(
    FunctionName="send-receipt",
    InvocationType="Event",
    Payload=body,
)

A long-running task behind a synchronous API fails with a timeout no matter how long the Lambda timeout is: the API Gateway integration gives up first (29 seconds by default). Accept the request, queue the work, and return an ID the client can check, or use response streaming for long generated responses.

"The client needs the result immediately" points to synchronous. "Absorb traffic spikes", "the backend is sometimes unavailable" or "long-running processing" points to asynchronous with SQS. "Several services react to one business event" points to EventBridge.

Resilience

Skill 1.1.3Create and maintain fault-tolerant and resilient applications (for example, by configuring retry with backoff, graceful degradation).

Retries with backoff and jitter

Many failures are temporary: a throttled request, a brief network error, a service returning 503. Retrying usually works, but retrying immediately and in lockstep with every other client makes the overload worse. The fix is exponential backoff (wait longer after each failure) with jitter (a random part of that wait, so clients spread out), within a limit on attempts.

The AWS SDKs already do this. The retry mode is set with retry_mode (or AWS_RETRY_MODE): standard is the default and recommended mode, adaptive adds client-side rate limiting for heavily throttled clients, and legacy exists for compatibility. max_attempts (or AWS_MAX_ATTEMPTS) counts the first try, defaulting to 3. Throttling errors such as ThrottlingException, TooManyRequestsException and DynamoDB's ProvisionedThroughputExceededException, and transient 5xx errors, are retried; validation and access errors are not.

SDK retries and timeouts (Python) 
from botocore.config import Config

cfg = Config(
    retries={"mode": "standard",
             "max_attempts": 5},
    connect_timeout=2,
    read_timeout=10,
)
ddb = boto3.client("dynamodb", config=cfg)

Retry in one layer only. If the SDK, the function and the client each retry three times, one failure can become 27 calls.

Idempotency

Retries and at-least-once delivery mean the same request can arrive twice. An operation is idempotent when doing it twice has the same effect as once: charging an order must not charge twice. Give each request a unique key (an order ID, or a client token that many AWS APIs accept), record the result the first time, and return the stored result on repeats. Powertools for AWS Lambda has an idempotency utility that does this with a DynamoDB table:

An idempotent payment handler (Python, Powertools) 
from aws_lambda_powertools.utilities \
    .idempotency import (
        DynamoDBPersistenceLayer,
        IdempotencyConfig,
        idempotent,
    )

store = DynamoDBPersistenceLayer(
    table_name="idempotency")
cfg = IdempotencyConfig(
    event_key_jmespath="orderId",
    expires_after_seconds=3600)

@idempotent(persistence_store=store,
            config=cfg)
def handler(event, context):
    return charge(event["orderId"],
                  event["amount"])

Graceful degradation and other patterns

Graceful degradationKeep the core working when a dependency fails: if the recommendations service is down, show the menu without "you might also like"; if the payment provider is slow, accept the order and charge it from a queue.

TimeoutsSet connect and read timeouts on every call so a hung dependency doesn't tie up all your threads or your Lambda duration.

Circuit breakerAfter repeated failures, stop calling a dependency for a while and fail fast or use a fallback, then try again. Use it carefully: AWS notes it adds a mode that is hard to test.

Throttling your own APIAPI Gateway limits requests per second (10,000 per Region per account by default, with a burst of 5,000) and returns 429 when exceeded; usage plans with API keys set per-client limits on REST APIs. Clients should treat 429 as "back off and retry".

"Intermittent throttling errors" points to exponential backoff with jitter (the SDK's standard retry mode). "Duplicate charges after retries" points to idempotency keys. "The site should keep working when a non-critical service fails" points to graceful degradation.

APIs

Skill 1.1.4Create, extend, and maintain APIs (for example, configure response/request transformations, by enforcing validation rules).

REST, HTTP and WebSocket APIs

TypeChoose it for
REST APIThe full feature set: request validation, body transformations (mapping templates), API keys and usage plans, caching, AWS WAF, resource policies, private APIs, canary releases, mock integrations, response streaming
HTTP APISimpler, cheaper, lower-latency proxies to Lambda or HTTP backends; built-in JWT authorizers; automatic deployments
WebSocket APITwo-way, long-lived connections, such as live order status (messages up to 128 KB, connections up to 2 hours)

Integration types

AWS_PROXYLambda proxy: the whole request goes to the function as an event, and the function returns statusCode, headers and body. The most common choice.

AWSCall an AWS service API directly (for example SQS SendMessage or DynamoDB PutItem) with mapping templates shaping the request and response. No function to maintain.

HTTP_PROXY and HTTPPass the request through to an HTTP backend, or transform it with mapping templates first.

MOCKReturn a response without a backend: testing, stubs, CORS preflight responses.

Validation rules

REST APIs can reject bad requests before they reach your code, saving cost and code. A request validator checks that required query strings, headers and path parameters are present, and/or that the body matches a model (a JSON Schema draft 4 document) for its content type. Invalid requests get a 400 response.

Order model for body validation (JSON Schema) 
{
  "$schema":
    "http://json-schema.org/draft-04/schema#",
  "type": "object",
  "required": ["customerId", "items"],
  "properties": {
    "customerId": {"type": "string"},
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["sku", "qty"],
        "properties": {
          "sku": {"type": "string"},
          "qty": {"type": "integer",
                  "minimum": 1}
        }
      }
    }
  }
}

The schema URL is the one line over the width limit; it can't be split. Attach the model to the POST method's request body and enable a validator for the body.

Request and response transformations

With non-proxy integrations, mapping templates (Velocity Template Language) reshape the request before it reaches the backend and the response before it reaches the client. $input.json('$.path') reads part of the body, $input.params('name') reads a parameter, $context holds request details, and $util escapes and encodes. HTTP APIs offer simpler parameter mapping (headers, query strings, paths) but no body transformation.

Send the request body to SQS (mapping template) 
Action=SendMessage&MessageBody=$util.urlEncode($input.body)

This template, on an AWS integration with SQS and a Content-Type of application/x-www-form-urlencoded, turns the API into an asynchronous front door for the order queue. It is a single unbroken line in the template.

Maintaining APIs

  • Stages (dev, prod) are deployed snapshots; stage variables point each stage at a different function alias or backend.
  • Canary releases on REST stages send a percentage of traffic to a new deployment before promoting it.
  • Versioning: keep /v1 working while /v2 is adopted, with base path mappings or routing rules on a custom domain.
  • Gateway responses customize error responses (for example adding CORS headers to 4xx errors), and CORS must be enabled for browser clients on other origins.
  • Export and import APIs as OpenAPI definitions to keep them in source control.

"Reject malformed requests without invoking Lambda" points to a REST API request validator with a model. "Change the request format for a legacy backend" points to mapping templates. "Different backends per environment" points to stage variables. "Test a new version on 10% of traffic" points to a canary release.

SDKs and APIs

Skill 1.1.5Develop code that interacts with AWS services by using APIs and AWS SDKs.

How a call reaches AWS

Every AWS service is an HTTPS API. The SDKs and the AWS CLI build the request, sign it with Signature Version 4 using your credentials, send it to the Regional endpoint, parse the response, and retry what can be retried. Your code supplies the Region, the credentials (found automatically) and the parameters.

Credentials: the provider chain

Never put access keys in code. The SDKs search a chain of providers and use the first that has credentials; the order varies slightly per SDK, but in general:

  1. Explicit settingsCredentials passed to the client or session in code (avoid for long-term keys).
  2. Environment variablesAWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN; this is how Lambda gives a function its execution role's credentials.
  3. Shared config and credentials filesProfiles in ~/.aws/config and ~/.aws/credentials, including assume-role, web identity and IAM Identity Center (SSO) profiles.
  4. Container credentialsThe ECS task role, served to the container.
  5. Instance metadataThe EC2 instance profile role, through IMDS (use IMDSv2).

On AWS compute, attach a role (Lambda execution role, ECS task role, EC2 instance profile) and let the chain find it. Locally, use IAM Identity Center profiles rather than long-term keys.

Writing good SDK code

Create clients onceCreate clients outside the Lambda handler so warm invocations reuse them and their connections.

PaginateList and query calls return pages with a continuation token (NextToken, LastEvaluatedKey). Use the SDK's paginators instead of assuming one call returns everything.

WaitWaiters poll until a resource reaches a state (a table exists, an object is present) instead of hand-written sleep loops.

Handle errors by codeCatch the SDK's service error and branch on its error code; log the request ID.

Paginator, waiter and error handling (Python) 
from botocore import exceptions

s3 = boto3.client("s3")
lister = "list_objects_v2"
pages = s3.get_paginator(lister)
for page in pages.paginate(
        Bucket=BUCKET, Prefix="menus/"):
    for obj in page.get("Contents", []):
        print(obj["Key"])

s3.get_waiter("object_exists").wait(
    Bucket=BUCKET, Key="menus/today.json")

try:
    s3.head_object(Bucket=BUCKET, Key=KEY)
except exceptions.ClientError as e:
    code = e.response["Error"]["Code"]
    if code != "404":
        raise

The AWS CLI

The CLI is the same API from a shell. --query filters output with JMESPath, --output chooses json, yaml, text or table, and it paginates automatically (--max-items, --page-size and --starting-token control it).

Functions on the Python 3.13 runtime (AWS CLI) 
aws lambda list-functions \
  --query "Functions[?Runtime=='python3.13'].FunctionName" \
  --output text

The JMESPath expression is kept on one line so the query stays valid.

Older SDK major versions have reached end of support: the AWS SDK for JavaScript v2 (September 8, 2025), the AWS SDK for Java 1.x (December 31, 2025) and the AWS SDK for .NET v3 (June 1, 2026). AWS CLI version 1 entered maintenance on July 15, 2026 and reaches end of support on July 15, 2027. Use JavaScript v3, Java 2.x, .NET v4 and CLI version 2.

Hard-coded access keys in code or environment files are the classic wrong answer. On AWS, use roles; on a laptop, use temporary credentials from IAM Identity Center. If a list call "misses" items, the code probably ignores pagination.

Streaming data

Skill 1.1.6Manage streaming data by using AWS services.

A stream is a continuous, ordered flow of records that several consumers can read independently and re-read: the courier app sends a location every few seconds, and both the live map and the delivery-time model consume it.

Amazon Kinesis Data Streams

A stream is made of shards. Each record has a partition key; records with the same key go to the same shard and stay in order there. Use a key with many distinct values (the courier ID, not the city) so load spreads across shards.

LimitValue
Write per shard1 MB per second or 1,000 records per second
Read per shard2 MB per second shared by standard consumers (5 GetRecords calls per second); each enhanced fan-out consumer gets its own 2 MB per second, pushed
Record sizeUp to 10 MiB (raised from 1 MiB in October 2025, set per stream)
Retention24 hours by default, up to 365 days
Capacity modesOn-demand (scales automatically) or provisioned (you set the shard count)

Exceeding a shard's limits raises ProvisionedThroughputExceededException: retry with backoff, spread partition keys, add shards (or use on-demand mode), and batch writes with PutRecords (up to 500 records per call).

Write a location update (Python) 
kin = boto3.client("kinesis")
kin.put_record(
    StreamName="courier-locations",
    PartitionKey=courier_id,
    Data=json.dumps(position).encode(),
)

Consuming with Lambda

An event source mapping polls each shard and invokes the function with a batch, in order. Because order matters, a failing batch blocks its shard until it succeeds or expires, so configure failure handling:

  • Report partial failures: enable ReportBatchItemFailures and return the sequence numbers that failed; Lambda retries from the first failure instead of the whole batch.
  • Limit retries with MaximumRetryAttempts and MaximumRecordAgeInSeconds (both unlimited by default), split failing batches with BisectBatchOnFunctionError, and send records that still fail to an on-failure destination (SQS, SNS or S3).
  • Keep up: raise ParallelizationFactor (up to 10 concurrent batches per shard, order kept per partition key) or the batch size (default 100).
Report failed records from a Kinesis batch (Python) 
import base64

def handler(event, context):
    failed = []
    for rec in event["Records"]:
        k = rec["kinesis"]
        seq = k["sequenceNumber"]
        try:
            raw = base64.b64decode(
                k["data"])
            update_map(json.loads(raw))
        except Exception:
            failed.append(
                {"itemIdentifier": seq})
    return {"batchItemFailures": failed}

Other streaming services

Amazon Data FirehoseFormerly Kinesis Data Firehose. Delivers streaming data to S3, Redshift, OpenSearch, Splunk, HTTP endpoints and more with no consumer code: it buffers by size and time, can transform records with a Lambda function, and converts formats. Choose it when the goal is "land the stream somewhere".

Amazon Managed Service for Apache FlinkFormerly Kinesis Data Analytics. Runs Apache Flink applications for real-time processing such as windowed aggregations. The old SQL applications were discontinued in January 2026.

Amazon MSKManaged Apache Kafka, for teams that use Kafka clients and tools.

"Several consumers need the same ordered records, with replay" points to Kinesis Data Streams. "Load streaming data into S3 with minimal code" points to Firehose. "Hot shard" or ProvisionedThroughputExceededException points to a better partition key or more shards. "One bad record blocks processing" points to ReportBatchItemFailures, bisecting and an on-failure destination.

Serialization

Skill 1.1.7Serialize and deserialize data to integrate application code with AWS services.

Serialization turns an in-memory object into bytes or text to send or store; deserialization turns it back. Most AWS APIs speak JSON, and most mistakes come from three places: binary data, number types, and payloads that are JSON inside JSON.

WhereWhat to know
SQS message bodyText only (XML, JSON or plain text in allowed characters); base64-encode binary, or use binary message attributes
SNS to SQSThe SQS body is an SNS envelope whose Message field holds your message as a string, unless raw message delivery is enabled
Kinesis and FirehoseData is bytes; Lambda receives it base64-encoded in kinesis.data
API Gateway to Lambdabody is a string: parse it; binary bodies arrive base64-encoded with isBase64Encoded true
EventBridgedetail is a JSON object (not a string)
DynamoDB low-level APIEvery value is typed: {"S": "pizza"}, {"N": "12.5"} (numbers travel as strings), {"L": [...]}, {"M": {...}}

For DynamoDB, use the higher-level interfaces (the boto3 resource Table, the JavaScript DynamoDBDocumentClient, the Java enhanced client) to map native types, or the type serializer to convert yourself. In Python, DynamoDB numbers come back as Decimal, which the standard json module can't serialize without help.

Typed DynamoDB values and Decimals (Python) 
from decimal import Decimal
from boto3.dynamodb.types import (
    TypeSerializer, TypeDeserializer)

item = {"orderId": "o-1001",
        "total": Decimal("23.50")}
typed = {k: TypeSerializer().serialize(v)
         for k, v in item.items()}
# {"orderId": {"S": "o-1001"},
#  "total": {"N": "23.50"}}

back = {k: TypeDeserializer()
        .deserialize(v)
        for k, v in typed.items()}
text = json.dumps(back, default=str)

For compact, schema-checked messages between services, Avro, JSON Schema or Protobuf with the AWS Glue Schema Registry lets producers and consumers agree on and evolve a schema; the new EventBridge custom event bus also accepts Avro and Protobuf events.

An SQS consumer behind an SNS topic that calls json.loads(body) and expects the order gets the SNS envelope instead. Read body["Message"] and parse again, or enable raw message delivery on the subscription.

Event-driven patterns

Skill 1.1.8Implement event-driven patterns (for example, by using EventBridge, Amazon S3 Event Notifications, Amazon SQS, Amazon SNS).

In an event-driven design, services announce that something happened ("OrderPlaced", "MenuUploaded") and other services react. The producer doesn't know or wait for consumers, so new behavior is added by adding a consumer.

EventBridge rules and patterns

An event pattern matches fields of the event. Values are lists (any match), and operators refine matching: prefix, suffix, anything-but, numeric ranges, exists, equals-ignore-case, wildcard, and $or.

Large orders from the web app (event pattern) 
{
  "source": ["food.orders"],
  "detail-type": ["OrderPlaced"],
  "detail": {
    "channel": [{"anything-but": "test"}],
    "total": [{"numeric": [">=", 100]}]
  }
}
Publish the event (Python) 
events = boto3.client("events")
events.put_events(Entries=[{
    "EventBusName": "orders",
    "Source": "food.orders",
    "DetailType": "OrderPlaced",
    "Detail": json.dumps(order),
}])

Check the response's FailedEntryCount: PutEvents can partly fail without raising an error. An input transformer on a target can reshape the event (pick fields into a template) before delivery.

Amazon S3 Event Notifications

S3 can notify when objects are created, removed, restored or replicated. Notifications go to SNS, SQS (standard queues only), Lambda, or EventBridge. Filter by key prefix and suffix (no wildcards, and filters for the same event type can't overlap). Delivery is at least once, usually within seconds, and not guaranteed in order. Turning on EventBridge for a bucket sends all its events to EventBridge, where rules can filter on more fields and reach more targets.

  1. UploadA restaurant uploads menus/r-42.json.
  2. NotifyThe ObjectCreated event for prefix menus/ and suffix .json invokes a function.
  3. ProcessThe function reads the object, validates it and updates the menu table.
  4. Fan outIt publishes "MenuUpdated" to EventBridge for search indexing and caching.

A function triggered by uploads to a bucket that writes its output to the same bucket and prefix triggers itself in a loop. Write to a different bucket or prefix. Lambda detects and stops some recursive loops, but don't rely on it.

Choosing the pattern

NeedPattern
One producer, one worker, bufferingSQS queue
One message to many subscribersSNS topic, often fanned out to SQS queues
Route by content, many event types, AWS or SaaS eventsEventBridge
React to object uploadsS3 Event Notifications, or S3 events through EventBridge

Spec-driven development

Instead of prompting for code directly, a spec turns an idea into three documents you review before code is written:

  1. requirements.mdUser stories with acceptance criteria in EARS notation ("WHEN a customer submits an order with no items THE SYSTEM SHALL reject it with an error").
  2. design.mdThe technical design: components, data models, interfaces, error handling.
  3. tasks.mdAn ordered checklist of implementation tasks, each traced to requirements, which Kiro then carries out.

Specs keep generated code aligned with what was asked, and they document it.

Steering and hooks

Steering files (Markdown in .kiro/steering/, or a global folder) give Kiro standing project knowledge: the product, the tech stack, coding standards. They can be always included or only for matching files. Hooks run an agent action automatically on an event, such as saving a file (update the tests), creating a file, or before a tool runs.

.kiro/steering/tech.md (Markdown) 
# Tech stack
- Python 3.13 on Lambda, boto3 only
- Clients created outside handlers
- SDK standard retry mode; no
  hand-written retry loops
- All writes idempotent (orderId key)
- Tests: pytest with moto

Managed AI services

Skill 1.1.10Integrate managed AWS AI services into applications.

Managed AI services are APIs: you call them with the SDK like any other service, with IAM permissions, quotas, retries and costs to handle. Choosing models, writing prompts and designing RAG systems are out of scope for this exam; calling the services correctly is in scope.

Amazon Bedrock

Bedrock gives API access to foundation models from several providers. The Converse API (client bedrock-runtime) uses one request shape for every model: a list of messages, an optional system prompt, and inferenceConfig (maximum tokens, temperature). ConverseStream returns the answer as it's generated. The modelId can be a model ID or an inference profile, which routes requests across Regions for capacity.

Summarize a customer complaint (Python) 
brt = boto3.client("bedrock-runtime")

resp = brt.converse(
    modelId=MODEL_ID,
    system=[{"text": "Summarize in "
             "one sentence."}],
    messages=[{
        "role": "user",
        "content": [{"text": note}]}],
    inferenceConfig={"maxTokens": 100},
)
msg = resp["output"]["message"]
summary = msg["content"][0]["text"]
if resp["stopReason"] == "max_tokens":
    log.warning("summary cut off")

The role needs bedrock:InvokeModel (and bedrock:InvokeModelWithResponseStream for streaming) on the model or inference profile. Throttling (ThrottlingException) is handled like any other: backoff and retry.

Amazon Bedrock AgentCore

AgentCore hosts and operates AI agents. From application code, an agent deployed on AgentCore Runtime is called with invoke_agent_runtime on the bedrock-agentcore client, passing the runtime ARN, a session ID (to keep the conversation's context) and the payload; the permission is bedrock-agentcore:InvokeAgentRuntime.

Call a deployed agent (Python) 
ac = boto3.client("bedrock-agentcore")
resp = ac.invoke_agent_runtime(
    agentRuntimeArn=AGENT_ARN,
    runtimeSessionId=session_id,
    payload=json.dumps(
        {"prompt": question}).encode(),
)

The session ID must be long and unique per conversation; reuse it for follow-up questions in the same conversation.

Key takeaways

  • Decouple with SQS (buffer one consumer group; visibility timeout, DLQ, FIFO for order and deduplication), SNS (fan-out with filter policies) and EventBridge (content-based routing, retries, archives). Messages and events can be up to 1 MB now.
  • Synchronous when the caller needs the answer now; asynchronous (SQS, Lambda Event invokes, EventBridge) to absorb spikes, survive outages and run long work. Watch the 29-second API Gateway integration timeout.
  • Retry transient and throttling errors with exponential backoff and jitter (SDK standard mode), in one layer; make writes idempotent; set timeouts; degrade gracefully.
  • REST APIs validate requests with models and transform them with mapping templates; HTTP APIs are simpler and cheaper; stages, stage variables and canaries manage change.
  • SDKs sign requests and find credentials through a provider chain: use roles, not keys. Reuse clients, paginate, use waiters, branch on error codes. Move off end-of-support SDK versions.
  • Kinesis Data Streams: shards, partition keys, ordered and replayable; handle Lambda batch failures with partial batch responses, bisecting and on-failure destinations. Firehose loads streams into stores.
  • Serialization traps: SNS envelopes, base64 data in Kinesis and binary API bodies, typed DynamoDB values and Decimals.
  • Event-driven: EventBridge patterns, S3 Event Notifications (prefix and suffix filters, at-least-once, avoid loops), fan-out.
  • Kiro for spec-driven generation, steering, hooks, reviews and refactoring; Inspector for code security scanning; Q Developer and CodeGuru Reviewer are winding down.
  • Call Bedrock with Converse, AgentCore agents with InvokeAgentRuntime, and task-specific services (Comprehend, Textract, Transcribe, Translate) like any SDK call: IAM, quotas, retries, async jobs.
