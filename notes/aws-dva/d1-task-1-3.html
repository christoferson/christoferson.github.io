Overview

Task 1.3

Use data stores during application development.

Developers on AWS rarely design the database from scratch, but they choose stores, write the code that reads and writes them, set how long data lives, and add caches. Questions usually describe an access pattern (look up an order by ID, list a customer's orders by date, store menu photos, show the top dishes) and ask for the store, key design, query or cache that serves it.

The examples follow the food-ordering application from Task 1.1: orders and customer sessions in DynamoDB, menu photos and receipts in S3, restaurant and billing data in a relational database, and a cache for popular menus.

Data lifecycles

Skill 1.3.1Manage data lifecycles (for example, by using Amazon S3 Lifecycle policies, TTL, retention periods).

Data has a useful life. Keeping it longer costs money and can break privacy rules; deleting it too soon breaks the application or the law. Each store has its own mechanism for moving or removing data automatically.

S3 Lifecycle rules

A bucket's lifecycle configuration (up to 1,000 rules) applies actions to objects matching a filter (a prefix, tags, object size, or a combination):

ActionDoes
TransitionMoves objects to a cheaper storage class after a number of days
ExpirationDeletes objects (in a versioned bucket, adds a delete marker) after a number of days or on a date
Noncurrent version transition and expirationActs on old versions: NoncurrentDays, and NewerNoncurrentVersions to keep the newest few
Abort incomplete multipart uploadRemoves parts of uploads that never completed (expiration doesn't)
Expired object delete markerRemoves delete markers with no versions behind them

Rules run asynchronously (S3 evaluates objects daily), so there can be a delay before an action happens. Transitions only go "down" to colder classes, and a class's minimum storage duration is charged even if the object leaves earlier. Since September 2024, objects smaller than 128 KB aren't transitioned by default, because the per-object overhead would cost more than it saves; a size filter can override this.

Receipts: cheaper after 30 days, gone after 7 years (lifecycle JSON) 
{"Rules": [{
  "ID": "receipts",
  "Filter": {"Prefix": "receipts/"},
  "Status": "Enabled",
  "Transitions": [
    {"Days": 30,
     "StorageClass": "STANDARD_IA"},
    {"Days": 365,
     "StorageClass": "DEEP_ARCHIVE"}
  ],
  "Expiration": {"Days": 2555},
  "AbortIncompleteMultipartUpload":
    {"DaysAfterInitiation": 7}
}]}

Apply it with aws s3api put-bucket-lifecycle-configuration --bucket BUCKET --lifecycle-configuration file://rules.json; the call replaces the whole configuration, so include every rule. S3 now accepts objects up to 50 TB (since December 2025, with multipart upload; a single PUT is limited to 5 GB).

Retention that can't be shortened: Object Lock

When data must be kept, not just deleted on time, S3 Object Lock (on a versioned bucket) blocks deletion or overwriting of object versions until a retain-until date. In governance mode, users with s3:BypassGovernanceRetention can override it; in compliance mode, nobody can, not even the root user. A legal hold blocks deletion with no end date until it's removed.

TTL: expiring items

DynamoDB Time to Live deletes items after a time stored in an attribute you name. The attribute must be a Number holding a Unix epoch time in seconds. Deletion is free (no write capacity) but not immediate: expired items are typically removed within a few days and can still be returned by reads until then, so filter them out when it matters. TTL deletions appear in DynamoDB Streams marked as made by the service, which lets a function archive expired sessions.

Sessions that expire after 24 hours (Python) 
import time

ddb = boto3.client("dynamodb")
ddb.update_time_to_live(
    TableName="sessions",
    TimeToLiveSpecification={
        "Enabled": True,
        "AttributeName": "expiresAt"},
)

sessions = boto3.resource(
    "dynamodb").Table("sessions")
sessions.put_item(Item={
    "sessionId": sid,
    "customerId": cid,
    "expiresAt": int(time.time())
                 + 24 * 3600,
})

In caches, TTLs are set per key (for example the Valkey and Redis OSS SET key value EX 300, or EXPIRE) so stale entries age out.

A TTL value in milliseconds (the default in JavaScript's Date.now()) is a date thousands of years away, so items never expire. DynamoDB TTL wants seconds.

"Move objects to cheaper storage as they age" points to lifecycle transitions. "Delete session data automatically" points to DynamoDB TTL. "Logs cost too much" often points to log group retention. "Records must not be deleted for seven years, even by administrators" points to Object Lock in compliance mode.

Choosing a data store

Skill 1.3.2Choose AWS data stores (for example, Amazon ElastiCache, DynamoDB, Amazon S3, Amazon RDS) based on access patterns.

Start from the questions the application asks of its data: how is each item looked up, how big is it, do reads need joins across tables, does a write have to update several records together, how fast and how often?

StoreAccess pattern it fitsWatch out for
Amazon DynamoDBKnown lookups by key at any scale with single-digit millisecond latency: an order by ID, a customer's orders by date, sessions, carts. Serverless, on-demand or provisioned capacityItems up to 400 KB; queries must follow the key and index design; no joins
Amazon RDS and AuroraRelational data with joins, ad hoc queries, multi-row transactions and constraints: restaurants, menus, billing. Aurora serverless scales capacity automatically, down to zero when pausedConnection limits with many Lambda environments (use RDS Proxy); scaling writes is harder
Amazon ElastiCacheIn-memory, sub-millisecond reads: caching, sessions, leaderboards (sorted sets), rate limiting, pub/sub. Engines: Valkey, Redis OSS, Memcached; serverless or node-basedA cache, not usually the system of record
Amazon S3Files and blobs of any size (up to 50 TB): menu photos, receipts, exports, static web content, data lakesNot a database: no queries over contents, per-request cost and latency
Amazon OpenSearch ServiceFull-text search, relevance ranking, log analytics: "search dishes by name or ingredient"Usually a secondary index fed from the primary store

Many applications use several: orders in DynamoDB, the receipt PDF in S3 with its key stored on the order item, restaurant contracts in Aurora, and a cache in front of the busiest reads. Large binary data goes to S3 with a pointer in the database rather than into the database itself.

"Key-value lookups at massive scale with consistent low latency" points to DynamoDB. "Complex queries and joins" or "existing relational schema" points to RDS or Aurora. "Sub-millisecond reads of frequently accessed data" or "session store" points to ElastiCache. "Store images or large files" points to S3, with metadata in a database. "Search text" points to OpenSearch.

Caching

Skill 1.3.3Determine the appropriate caching solution based on data store selection.

Caching strategies

Lazy loading (cache-aside)Read from the cache; on a miss, read the database and write the result to the cache. Only requested data is cached and a lost cache node only means misses, but the first read is slow (a miss costs three trips) and data can be stale until it expires.

Write-throughWrite to the cache whenever you write to the database. Cached data is always current, but every write pays twice, and much of what's cached may never be read.

TTLAdd an expiry to both strategies so stale or unused entries age out. Adding a little randomness to TTLs keeps many keys from expiring at once and stampeding the database.

Cache-aside for menus with Valkey (Python) 
import valkey

cache = valkey.Valkey(host=CACHE_HOST,
                      port=6379, ssl=True)

def get_menu(rid):
    key = f"menu:{rid}"
    hit = cache.get(key)
    if hit:
        return json.loads(hit)
    menu = load_menu_from_db(rid)
    cache.set(key, json.dumps(menu),
              ex=300)
    return menu

When a menu changes, delete or overwrite its key so customers don't see the old one for five minutes. The Valkey Python client is API-compatible with the Redis client.

An RDS read replica is an alternative to a cache for read-heavy relational workloads that need SQL: it scales reads without new code, but at database rather than in-memory speed, and replicas lag slightly behind the primary.

DAX doesn't help strongly consistent reads; they go straight to DynamoDB. And an API Gateway cache that any client can flush (the Cache-Control: max-age=0 header) is a risk: require authorization for cache invalidation.

"Microsecond reads for a DynamoDB table with minimal code change" points to DAX. "Cache query results from RDS" points to ElastiCache with lazy loading. "Cache API responses for identical requests" points to API Gateway caching or CloudFront. "Serve static content to users worldwide" points to CloudFront.

Configuring DynamoDB

Skill 1.3.4Configure DynamoDB to support applications (for example, by selecting high-cardinality partition keys, applying read consistency models, performing query and scan operations, by defining keys, attributes, and indexes).

Keys and partitions

Every item has a primary key: a partition key alone, or a partition key plus a sort key (a composite key). DynamoDB hashes the partition key to place the item on a partition; items with the same partition key are stored together, ordered by sort key. Apart from the key, items are schemaless: each can have different attributes.

Each partition serves up to 3,000 read units and 1,000 write units per second. A high-cardinality partition key (many distinct, evenly used values such as orderId or customerId) spreads load; a low-cardinality one (status, today's date) creates a hot partition that throttles even when the table has spare capacity. Adaptive capacity and burst capacity soften short spikes, and write sharding (adding a random suffix to a hot key) spreads a hot value across partitions.

Access patternKey design
Get an order by IDPartition key orderId
A customer's orders, newest firstPartition key customerId, sort key orderDate (ISO 8601 strings sort by time); query with ScanIndexForward=False
A restaurant's open ordersA global secondary index on restaurantId and status

Capacity and consistency

Capacity modesOn-demand (the default and AWS's recommendation for most tables) bills per request and scales instantly up to double the previous peak; its price was cut 50% in November 2024, and you can set a maximum throughput. Provisioned sets read and write capacity units, optionally with auto scaling, for steady, predictable traffic.

Read unitsOne read capacity unit (RCU) is one strongly consistent read per second of an item up to 4 KB, or two eventually consistent reads; a transactional read costs two. Sizes round up: a 6 KB item needs 2 RCUs for a strong read.

Write unitsOne write capacity unit (WCU) is one write per second of up to 1 KB; a transactional write costs two. A 2.5 KB item needs 3 WCUs per write.

ConsistencyReads are eventually consistent by default (half the cost; may miss a write from the last moment). Set ConsistentRead=True for a strongly consistent read that reflects all successful writes, on the table or a local secondary index. Global secondary indexes and streams are always eventually consistent.

Worked example

The order API must read 80 orders per second, each 3 KB, strongly consistent: each read is 1 RCU (3 KB rounds up to 4 KB), so 80 RCUs; eventually consistent would be 40. It writes 20 orders per second of 3 KB: 3 WCUs each, so 60 WCUs.

Query and scan

Query reads one partition key value (equality required) and optionally narrows by the sort key (=, <, <=, >, >=, BETWEEN, begins_with). Scan reads every item in the table or index; it's slow and expensive on large tables, so use it for exports or small tables, and split big scans into segments read in parallel (Segment, TotalSegments).

  • A FilterExpression removes items after they're read: it saves bandwidth, not capacity.
  • A ProjectionExpression returns only the attributes you name.
  • Each call returns at most 1 MB (before filtering). When LastEvaluatedKey is present, pass it as ExclusiveStartKey to get the next page.
A customer's orders since October, all pages (Python) 
from boto3.dynamodb.conditions import Key

orders = boto3.resource(
    "dynamodb").Table("orders")

since = Key("orderDate").gte(
    "2026-10-01")
cond = Key("customerId").eq(cid) & since
args = {"KeyConditionExpression": cond,
        "ScanIndexForward": False}
items = []
while True:
    page = orders.query(**args)
    items += page["Items"]
    last = page.get("LastEvaluatedKey")
    if not last:
        break
    args["ExclusiveStartKey"] = last

Writes: conditions, updates and transactions

Conditional writesA ConditionExpression makes a write happen only if the item is in the expected state: create only if it doesn't exist (attribute_not_exists(orderId)), or update only if the version hasn't changed (optimistic locking). A failed condition raises ConditionalCheckFailedException.

Update expressionsSET, REMOVE, ADD and DELETE change attributes in place; SET n = n + :one is an atomic counter. Attribute names that are reserved words (status, name, date) need placeholders in ExpressionAttributeNames.

BatchesBatchGetItem reads up to 100 items and BatchWriteItem puts or deletes up to 25; neither is atomic, and unprocessed items come back in the response to retry with backoff.

TransactionsTransactWriteItems and TransactGetItems act on up to 100 items all-or-nothing (for example, create the order and decrement stock together), at twice the capacity cost.

Advance an order's status with optimistic locking (Python) 
from botocore import exceptions

CONFLICT = (
    "ConditionalCheckFailedException")
try:
    orders.update_item(
        Key={"customerId": cid,
             "orderDate": odate},
        UpdateExpression=(
            "SET #s = :new, "
            "version = :v2"),
        ConditionExpression=(
            "version = :v1"),
        ExpressionAttributeNames={
            "#s": "status"},
        ExpressionAttributeValues={
            ":new": "PREPARING",
            ":v1": ver, ":v2": ver + 1},
    )
except exceptions.ClientError as e:
    code = e.response["Error"]["Code"]
    if code == CONFLICT:
        reload_and_retry()
    else:
        raise

Secondary indexes

FeatureLocal secondary index (LSI)Global secondary index (GSI)
KeysSame partition key, different sort keyAny partition and sort key (since November 2025, up to four attributes each)

Limit5 per table; 10 GB per partition key value20 per table by default

An index's projection decides which attributes it copies: KEYS_ONLY, INCLUDE (named attributes) or ALL. Project what queries need to avoid extra reads. A sparse index contains only items that have the index key attribute, which makes it a cheap way to list, for example, only orders flagged for review.

A query on a GSI can't use ConsistentRead=True, and a newly written item may not appear in it immediately. If the access pattern needs strong consistency on an alternate sort key, the index must be an LSI, which has to be defined when the table is created.

"Throttling although total capacity isn't used" points to a hot partition: a higher-cardinality key or write sharding. "Query by an attribute that isn't the key" points to a GSI. "Prevent lost updates from concurrent writers" points to a condition on a version attribute. "Several items must change together" points to transactions. "Scan is slow" points to a query on a better key or index, or a parallel scan.

Key takeaways

  • S3 Lifecycle: filters plus transition and expiration actions, noncurrent versions, abort incomplete uploads; daily and asynchronous; minimum durations; small objects not transitioned by default. Object Lock (governance or compliance) for retention that must not be shortened.
  • DynamoDB TTL: Number attribute in epoch seconds, free deletes within days, expired items readable until removed. Set retention on CloudWatch Logs (default never expires), backups and point-in-time recovery.
  • Choose by access pattern: DynamoDB for key lookups at scale, RDS or Aurora for relational queries and transactions, ElastiCache for in-memory speed, S3 for objects, OpenSearch for search.
  • Caching: lazy loading or write-through plus TTLs; ElastiCache (Valkey, Redis OSS, Memcached) for any store, DAX for DynamoDB (eventually consistent reads), API Gateway or CloudFront for responses.
  • DynamoDB: high-cardinality partition keys; RCU per 4 KB (eventual half, transactional double), WCU per 1 KB; on-demand by default; Query over Scan, filters don't save capacity, paginate with LastEvaluatedKey; conditional writes, atomic updates, transactions; LSI at creation with strong reads, GSI any time with eventual reads.
