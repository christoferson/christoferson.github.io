Overview

Task 3.3

Deploy code by using AWS continuous integration and continuous delivery (CI/CD) services.

Continuous integration builds and tests every change automatically; continuous delivery takes the tested artifact through environments to production, with approvals where needed. On AWS the pieces are: a repository (through CodeConnections), CodeBuild to build and test, CodePipeline to orchestrate stages, and a deployer (CloudFormation or SAM for infrastructure, CodeDeploy or ECS for gradual traffic shifting). Designing pipelines is out of scope for this exam; using them, and the deployment settings developers own, is in scope.

The examples follow the food-ordering application: a SAM stack with the order API's Lambda functions, the kitchen service on ECS Fargate, and a pipeline that deploys to test, then production after approval.

Lambda packaging

Skill 3.3.1Use Lambda deployment packaging methods to optimize deployment efficiency (for example, .zip files, container images, layers).

MethodStrengthsWatch out for
.zip fileSimplest; fastest to build and deploy for small functions; works with every feature (layers, SnapStart, console editing)50 MB for direct upload (larger through S3), 250 MB unzipped with layers
LayersShare dependencies or a runtime between functions; deploy small code changes without re-uploading librariesUp to 5 per function; versioned, so updating a layer means updating each function to the new version
Container imageUp to 10 GB; same build tooling and scanning as other containers; large ML or native dependenciesOne architecture per image; no layers; the image must stay in ECR

Keep packages small (only production dependencies, no tests or docs) to speed up deployments and cold starts. In pipelines, sam build then sam package or sam deploy (or aws cloudformation package then deploy) uploads artifacts to S3 or ECR and deploys a template that references them.

Versions, aliases and gradual deployment with SAM

Production callers should invoke an alias, never $LATEST. In SAM, AutoPublishAlias publishes a new version whenever the code changes and moves the alias to it. Adding DeploymentPreference makes SAM create a CodeDeploy application and deployment group that shifts the alias's traffic gradually and rolls back on alarms or failed hooks.

A canary release of the order function (AWS SAM) 
OrderFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: app.handler
    Runtime: python3.13
    AutoPublishAlias: live
    DeploymentPreference:
      Type: Canary10Percent5Minutes
      Alarms:
        - !Ref OrderErrorsAlarm
      Hooks:
        PreTraffic: !Ref PreTrafficCheck
        PostTraffic: !Ref PostTrafficCheck

Canary10Percent5Minutes sends 10% of traffic to the new version for 5 minutes, then the rest. Other types: Canary10Percent10Minutes, 15Minutes, 30Minutes; Linear10PercentEvery1Minute (also every 2, 3 or 10 minutes); AllAtOnce. The hook functions test the new version before and after the shift and must report success or failure to CodeDeploy. Gradual shifting needs a previous version, so the very first deployment can't be gradual.

For development onlysam sync --watch and cdk deploy --hotswap push code straight to functions in seconds, bypassing CloudFormation (and causing drift); CloudFormation's express mode (2026) skips waiting for resources to stabilize and doesn't roll back. None of these are for production.

"Shift 10% of traffic to the new function version, then the rest after 10 minutes" points to Canary10Percent10Minutes. "Equal increments every minute" points to a linear type. "Run a test against the new version before it gets traffic" points to a PreTraffic hook. "Shared libraries change rarely, code changes often" points to layers.

Containers

Skill 3.3.2Deploy containerized applications by using AWS container orchestration services (for example, Amazon ECS task definitions, Amazon EKS manifests, AWS Fargate launch types, rolling updates).

ECS task definitions

A task definition is a versioned blueprint (family plus revision number) for one or more containers: image, CPU and memory, ports, environment variables and secrets, logging, and two roles. A service keeps a number of tasks running from one task definition revision and replaces them when you deploy a new revision.

kitchen task definition, key fields (JSON) 
{
  "family": "kitchen",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "512",
  "memory": "1024",
  "executionRoleArn": "EXEC_ROLE_ARN",
  "taskRoleArn": "TASK_ROLE_ARN",
  "containerDefinitions": [{
    "name": "kitchen",
    "image": "KITCHEN_IMAGE_URI",
    "portMappings": [
      {"containerPort": 8080}],
    "secrets": [{
      "name": "DB_PASSWORD",
      "valueFrom": "DB_SECRET_ARN"}],
    "logConfiguration": {
      "logDriver": "awslogs",
      "options": {
        "awslogs-group": "/ecs/kitchen",
        "awslogs-region": "us-east-1",
        "awslogs-stream-prefix": "app"}}
  }]
}

Fargate requires awsvpc networking and task-level CPU and memory. The execution role lets ECS pull the image, write logs and fetch the secret; the task role is what the application code uses to call AWS. Placeholders stand for the ARNs and image URI.

Rolling updates

The default ECS deployment replaces tasks gradually within two limits: minimumHealthyPercent (how many must stay running) and maximumPercent (how many may run in total during the deployment). With 4 tasks, 100% and 200% let ECS start 4 new tasks before stopping the old ones. The deployment circuit breaker, with rollback enabled, stops a deployment whose tasks keep failing and returns to the last completed deployment; CloudWatch alarms can trigger the same rollback.

Deploy a new task definition revision (AWS CLI) 
aws ecs register-task-definition \
  --cli-input-json file://taskdef.json

aws ecs update-service \
  --cluster orders --service kitchen \
  --task-definition kitchen:42 \
  --deployment-configuration \
    "deploymentCircuitBreaker={enable=true,rollback=true}"

The circuit breaker setting is one shorthand value. ECS resolves an image tag to a digest when it deploys, so pushing a new image under the same tag doesn't change running tasks; deploy a new revision, or use --force-new-deployment.

Blue/green, linear and canary on ECS

Since July 2025, ECS performs blue/green deployments natively (and linear and canary since October 2025): set the service's deployment strategy, give the load balancer listener two target groups, and ECS starts the new revision alongside the old one, shifts test and production traffic, waits a bake time, and can run Lambda hooks at each stage. The older way, CodeDeploy with an ECS deployment group, still works (below).

Fargate, EC2 and EKS

FargateServerless compute for tasks and pods: no instances to manage, billed per task. Choose it unless you need GPUs, special instance types or host-level control.

EC2 capacityTasks run on instances in your account, through capacity providers or ECS Managed Instances (2025, where AWS manages the instances).

Amazon EKSKubernetes manifests describe the app: a Deployment (replicas, container image, rolling update settings maxSurge and maxUnavailable) and a Service. Apply them with kubectl apply or the CodePipeline EKS deploy action (2025). Changing the image in the Deployment triggers a rolling update.

A kitchen Deployment on EKS (Kubernetes YAML) 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kitchen
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels: {app: kitchen}
  template:
    metadata:
      labels: {app: kitchen}
    spec:
      containers:
        - name: kitchen
          image: KITCHEN_IMAGE_URI
          ports:
            - containerPort: 8080

Containers in CodePipeline

The pipeline's ECS deploy action reads imagedefinitions.json (container name and new image URI), registers a new task definition revision and updates the service. CodeBuild writes the file in post_build after pushing the image:

buildspec.yml post_build for an ECS deploy 
post_build:
  commands:
    - docker push $REPO:$TAG
    - printf '[{"name":"kitchen","imageUri":"%s"}]' $REPO:$TAG > imagedefinitions.json
artifacts:
  files:
    - imagedefinitions.json

The printf line can't be split. For CodeDeploy blue/green deployments to ECS, the pipeline uses imageDetail.json (the image URI), a taskdef.json with an <IMAGE1_NAME> placeholder, and an appspec.yaml.

"Deployment keeps failing and should stop and revert automatically" points to the ECS deployment circuit breaker with rollback. "Container code can't access DynamoDB" points to the task role. "Tasks can't pull the image or write logs" points to the execution role. "Run containers without managing servers" points to Fargate.

Infrastructure as code

Skill 3.3.3Use infrastructure as code (IaC) templates (for example, CloudFormation templates, AWS SAM templates).

CloudFormation templates

SectionHolds
ParametersInputs per deployment (stage name, instance size); AWS::SSM::Parameter::Value types read from Parameter Store
MappingsLookup tables (per Region or per environment), read with Fn::FindInMap
ConditionsBooleans that create resources or set properties only sometimes (only in prod)
TransformMacros such as AWS::Serverless-2016-10-31 (SAM)
ResourcesThe only required section: the AWS resources to create
OutputsValues to show or Export for other stacks (Fn::ImportValue)

Intrinsic functions connect resources: !Ref (a parameter's value or a resource's ID), !GetAtt (an attribute such as an ARN), !Sub (build strings), !If, !Join, !ImportValue. Updates go through change sets so you can see replacements before they happen. DeletionPolicy: Retain or Snapshot (and UpdateReplacePolicy) protect data when a resource is deleted or replaced; stack policies and termination protection guard against accidental changes. Split large systems with nested stacks (a stack as a resource of another) or cross-stack references (exports and imports between independent stacks).

AWS SAM templates

SAM extends CloudFormation for serverless applications: with the SAM transform, short resource types expand into full CloudFormation. AWS::Serverless::Function creates the function, role, permissions and event sources; also Api, HttpApi, SimpleTable, LayerVersion, StateMachine, Application (nested applications), Connector (permissions between resources). Globals sets shared properties, and policy templates grant scoped permissions in one line.

The order API in SAM (YAML) 
AWSTemplateFormatVersion: "2010-09-09"
Transform: AWS::Serverless-2016-10-31
Parameters:
  Stage:
    Type: String
    AllowedValues: [dev, test, prod]
Globals:
  Function:
    Runtime: python3.13
    Timeout: 10
Resources:
  OrdersTable:
    Type: AWS::Serverless::SimpleTable
  OrderFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.handler
      Environment:
        Variables:
          TABLE: !Ref OrdersTable
      Policies:
        - DynamoDBCrudPolicy:
            TableName: !Ref OrdersTable
      Events:
        Post:
          Type: Api
          Properties:
            Path: /orders
            Method: post
Outputs:
  ApiUrl:
    Value: !Sub "https://${ServerlessRestApi}.execute-api.${AWS::Region}.amazonaws.com/Prod/"

The output URL is one unsplittable string; ServerlessRestApi is the API SAM creates for Api events. sam deploy creates a change set and deploys it; CDK apps synthesize to the same kind of templates (cdk synth, cdk deploy) from code, using constructs from low-level L1 (one CloudFormation resource) to L3 patterns.

"Share a VPC ID from one stack with others" points to an output export and Fn::ImportValue. "Keep the database when the stack is deleted" points to DeletionPolicy: Retain or Snapshot. "See what an update will replace" points to a change set. "Least-privilege permission to one table in one line" points to a SAM policy template.

CodeDeploy

Skill 3.3.4Deploy application revisions to target environments by using AWS CodeDeploy.

CodeDeploy deploys a revision (application files, or a new function or task definition version) to a deployment group (the targets) using a deployment configuration (how fast). The appspec file in the revision says what to deploy and which lifecycle hooks to run.

PlatformDeploysConfigurations
EC2 and on-premisesFiles and scripts to instances running the CodeDeploy agent; in-place (update each instance) or blue/green (new instances behind the load balancer)CodeDeployDefault.AllAtOnce, HalfAtATime, OneAtATime, or custom minimum healthy hosts
LambdaShifts an alias from the current version to the target versionLambdaCanary10Percent5Minutes (and 10, 15, 30), LambdaLinear10PercentEvery1Minute (and 2, 3, 10), LambdaAllAtOnce
ECSBlue/green: starts the new task set, shifts load balancer trafficECSCanary10Percent5Minutes, ECSCanary10Percent15Minutes, ECSLinear10PercentEvery1Minutes, ECSLinear10PercentEvery3Minutes, ECSAllAtOnce

appspec files

appspec.yml for EC2 instances 
version: 0.0
os: linux
files:
  - source: /
    destination: /opt/orders
hooks:
  ApplicationStop:
    - location: scripts/stop.sh
  BeforeInstall:
    - location: scripts/deps.sh
  AfterInstall:
    - location: scripts/config.sh
  ApplicationStart:
    - location: scripts/start.sh
  ValidateService:
    - location: scripts/health.sh
      timeout: 300

Hooks run in this order on each instance: ApplicationStop (from the previous revision), download, BeforeInstall, install (copy files), AfterInstall, ApplicationStart, ValidateService. Behind a load balancer, traffic hooks (BeforeBlockTraffic, AfterBlockTraffic, BeforeAllowTraffic, AfterAllowTraffic) surround removing and re-adding the instance. Each script can run up to an hour.

appspec.yml for a Lambda alias shift 
version: 0.0
Resources:
  - orderFunction:
      Type: AWS::Lambda::Function
      Properties:
        Name: order-api
        Alias: live
        CurrentVersion: "11"
        TargetVersion: "12"
Hooks:
  - BeforeAllowTraffic: CheckOrderApi
  - AfterAllowTraffic: SmokeTestOrderApi

For ECS, the appspec names the task definition and the container and port behind the load balancer, with hooks BeforeInstall, AfterInstall, AfterAllowTestTraffic, BeforeAllowTraffic and AfterAllowTraffic. Lambda and ECS hooks are Lambda functions that must call PutLifecycleEventHookExecutionStatus with Succeeded or Failed within an hour, or the deployment fails.

A traffic hook function (Python) 
cd = boto3.client("codedeploy")

def handler(event, context):
    ok = smoke_test()
    dep = event["DeploymentId"]
    hook = event[
        "LifecycleEventHookExecutionId"]
    status = ("Succeeded" if ok
              else "Failed")
    cd.put_lifecycle_event_hook_execution_status(
        deploymentId=dep,
        lifecycleEventHookExecutionId=hook,
        status=status,
    )

The method and parameter names can't be split. A failed hook, or a CloudWatch alarm on the deployment group, stops the deployment and rolls back (below).

"Run a script after the files are copied" points to AfterInstall. "Check the application is healthy before finishing" points to ValidateService. "Test the new ECS task set before production traffic" points to AfterAllowTestTraffic. "Deployment fails at a hook after an hour" points to a hook that never reported its status.

CodePipeline

Skill 3.3.5Use AWS CodePipeline to orchestrate CI/CD pipelines (for example, invoke pipelines from linked code repositories, orchestrate progression through multiple environments).

A pipeline is a sequence of stages (Source, Build, Test, Deploy-Test, Approve, Deploy-Prod), each with actions that pass artifacts through an S3 artifact store. Actions include sources (CodeConnections, S3, ECR), CodeBuild builds and tests, approvals, invokes (Lambda, Step Functions) and deploys (CloudFormation, CodeDeploy, ECS, EKS, Lambda, S3, Elastic Beanstalk).

  1. SourceA push to main on GitHub, through a CodeConnections connection, starts the pipeline and outputs the code.
  2. BuildCodeBuild runs buildspec.yml: install, test, sam build, sam package; outputs the packaged template.
  3. Deploy to testA CloudFormation action creates and executes a change set in the test account; integration tests run against it.
  4. ApproveA manual approval action notifies the release manager through SNS; it fails if not approved within 7 days (configurable).
  5. Deploy to productionThe same artifact deploys to production, with the gradual traffic shifting and alarms from the template.
buildspec.yml for the SAM application 
version: 0.2
env:
  parameter-store:
    ARTIFACT_BUCKET: /orders/ci/bucket
phases:
  install:
    runtime-versions:
      python: 3.13
  build:
    commands:
      - pytest
      - sam build
      - sam package
        --s3-bucket $ARTIFACT_BUCKET
        --output-template-file
          packaged.yaml
artifacts:
  files:
    - packaged.yaml

The sam package command continues over three lines as one YAML scalar. env can also read secrets-manager values and export variables to later actions.

Pipeline type V2

V2 pipelines (the default) add what multi-environment delivery needs:

  • Triggers with filters: start on pushes to chosen branches, on Git tags (for example only v* release tags), on pull requests, or only when certain file paths change.
  • Execution modes: SUPERSEDED (default; a newer run replaces a waiting one), QUEUED (runs one after another), PARALLEL.
  • Variables at the pipeline level, passed in when a run starts.
  • Stage conditions: checks before a stage (block deployments outside a deployment window, or while an alarm is active) and after it (roll back on failure, or fail if an alarm fires after success).
  • Stage rollback to the artifacts of the last successful run, manually or automatically on failure.

Cross-account deployments use an action role in the target account that the pipeline assumes, plus a KMS key the target account can use to read artifacts.

"Start the pipeline only when a release tag is pushed" points to a V2 trigger with a tag filter. "Require sign-off before production" points to a manual approval action. "Don't deploy when an alarm is active" points to a stage entry condition. "Deploy the same artifact to several accounts" points to cross-account actions with roles and a shared KMS key.

Deployment strategies

Skill 3.3.6Implement deployment strategies for application releases (for example, blue/green, canary, rolling).

StrategyHow it worksTrade-off
All at onceUpdate everything togetherFastest; downtime or full impact if it's bad
RollingUpdate in batches while others serve trafficNo extra capacity; reduced capacity and mixed versions during the update
Rolling with additional batchAdd a new batch first, then rollFull capacity throughout; a little extra cost
ImmutableDeploy to brand-new instances, then swap them inClean rollback (terminate the new ones); slower and costlier
Blue/greenRun the new version (green) beside the old (blue), test it, switch all trafficInstant switch and rollback; double capacity for a while
CanarySend a small share to the new version, wait, then the restLimits the impact of a bad release; needs metrics to judge it
LinearShift equal increments at fixed intervalsGradual and predictable; takes longer
WhereHow to do it
LambdaWeighted aliases, shifted by CodeDeploy (SAM DeploymentPreference) or the CodePipeline Lambda deploy action; canary, linear or all at once
ECSRolling (default), or native blue/green, linear and canary with bake time; or CodeDeploy blue/green
EC2CodeDeploy in-place (rolling by configuration) or blue/green with new instances
Elastic BeanstalkDeployment policies AllAtOnce, Rolling, RollingWithAdditionalBatch, Immutable, TrafficSplitting (canary with an ALB); blue/green by cloning the environment and swapping environment URLs (keep the database outside the environment)
API GatewayCanary settings on a REST stage
FeaturesAppConfig feature flags to turn code paths on gradually without a deployment

"Zero downtime and instant rollback" points to blue/green. "Expose a small share of users first" points to canary. "Elastic Beanstalk update without reducing capacity" points to rolling with additional batch or immutable. "Mixed versions must never serve traffic together" rules out rolling and canary.

Rollback

Skill 3.3.7Implement automatic or manual rollback by using AWS services (for example, CloudFormation, CodeDeploy).

CloudFormation

If a stack create or update fails, CloudFormation rolls back to the previous state automatically. Rollback triggers extend this to the application: up to 5 CloudWatch alarms watched during the update and for a monitoring period afterwards (up to 180 minutes); an alarm rolls the update back even though every resource succeeded. For troubleshooting, --disable-rollback (or the console's "preserve successfully provisioned resources") keeps what was created so you can fix and retry. If the rollback itself fails (UPDATE_ROLLBACK_FAILED), fix the cause and run continue-update-rollback, skipping stuck resources if needed (a --force-rollback option arrived in October 2026).

Update with an alarm rollback trigger (AWS CLI) 
aws cloudformation update-stack \
  --stack-name orders-prod \
  --use-previous-template \
  --rollback-configuration file://rb.json
rb.json 
{"RollbackTriggers": [{
   "Arn": "ORDER_ERRORS_ALARM_ARN",
   "Type": "AWS::CloudWatch::Alarm"}],
 "MonitoringTimeInMinutes": 15}

CodeDeploy

A deployment group can roll back automatically when a deployment fails and when a monitored alarm goes into alarm during the deployment. Rollback is a new deployment of the last known good revision (with a new deployment ID). For Lambda and ECS it shifts traffic back almost immediately, because the old version is still there. Manual rollback is redeploying an earlier revision, or stopping a deployment in progress with rollback.

Elsewhere

  • ECS: the deployment circuit breaker or alarms roll back to the last completed deployment.
  • Lambda: point the alias back to the previous version (instant).
  • CodePipeline: stage rollback redeploys the artifacts of the last successful run, manually or on failure.
  • Elastic Beanstalk: redeploy the previous application version, or swap URLs back after blue/green.

A rollback restores code and configuration, not data. Database migrations that dropped columns don't undo themselves; make schema changes backward compatible (expand first, contract later) so the previous version still works after a rollback.

Source control

Skill 3.3.8Use source control features to manage application versions and releases (for example, labels, branches).

BranchesTrunk-based development keeps short-lived feature branches merged into main often, with main always deployable. GitFlow keeps long-lived develop and release/* branches for scheduled releases. Pull requests carry review and automated checks before a merge.

Tags (labels)A Git tag marks the exact commit of a release (v2.3.0, following semantic versioning: major for breaking changes, minor for features, patch for fixes). Annotated tags record who tagged and why.

Linking releases to artifactsTag container images and name artifacts with the commit SHA or release tag, put the version in Lambda version descriptions, so anything running can be traced to its source.

Triggering on themCodePipeline V2 triggers can start on pushes to specific branches, on tags matching a pattern, or on pull request events. CodeBuild webhooks filter by event (PUSH, PULL_REQUEST_CREATED, PULL_REQUEST_MERGED…) and by HEAD_REF, BASE_REF, file path or tag name, for example to test every pull request into main.

Tag a release and push the tag (shell) 
git tag -a v2.3.0 -m "Express delivery"
git push origin v2.3.0

A pipeline triggered on v* tags then builds and releases exactly that commit.

"Deploy to production only for tagged releases" points to a tag-filtered pipeline trigger. "Run tests on every pull request" points to a CodeBuild webhook on pull request events. "Know exactly which code is running" points to commit-based image tags and versions.

AI tools for CI/CD

Skill 3.3.9Use AWS AI tools to support CI/CD workflows (for example, automated deployment approvals, environment provisioning, post-deployment validation).

NeedTool
Provision environmentsKiro generates and updates CDK, CloudFormation or SAM from a spec or a request, with AWS knowledge from Kiro powers (for CDK and CloudFormation, SAM) and AWS MCP servers; the result is reviewed and deployed like any template
Work inside the pipelineKiro CLI in headless mode in a CodeBuild step: review the change, generate missing tests, explain a failed build
Automated approvalsReplace or support a manual approval with checks: a stage condition with a Lambda rule (for example one that asks a model to assess test and scan results) or a CloudWatch alarm rule; keep a human approval for production when required
Post-deployment validationSynthetics canaries and alarms watched by CodeDeploy, ECS or stage conditions; AWS DevOps Agent (generally available since March 2026) investigates incidents by correlating telemetry, code and deployments and proposes fixes such as reverting a change; CloudWatch investigations suggest root causes from an alarm

An AI tool that can deploy can also break production. Give pipeline agents least-privilege roles, keep their changes in reviewed pull requests or change sets, and leave the final production approval and the rollback triggers in place.

"Find which deployment caused the error spike" points to AWS DevOps Agent or CloudWatch investigations. "Generate infrastructure code for a new environment" points to Kiro with AWS powers. "Approve automatically when checks pass" points to stage conditions with Lambda or alarm rules.

Key takeaways

  • Lambda: zip for most functions, layers for shared libraries, images for large dependencies; deploy versions behind aliases; SAM AutoPublishAlias plus DeploymentPreference (canary, linear, all at once; alarms; pre and post traffic hooks).
  • ECS: task definitions (Fargate needs awsvpc; execution role versus task role), rolling updates with minimum and maximum percent, circuit breaker rollback, native blue/green, linear and canary; EKS Deployments with rolling updates; imagedefinitions.json for the pipeline.
  • IaC: CloudFormation sections and intrinsic functions, change sets, deletion policies, nested stacks and exports; SAM transform, resource types, Globals and policy templates.
  • CodeDeploy: appspec per platform, hook order on EC2, Lambda and ECS traffic hooks that must report status, predefined configurations, automatic rollback on failure or alarm.
  • CodePipeline: stages, actions and artifacts; CodeBuild buildspec; manual approvals; V2 triggers on branches, tags and paths, execution modes, stage conditions and rollback; cross-account roles.
  • Strategies: all at once, rolling, rolling with extra batch, immutable, blue/green, canary, linear; Elastic Beanstalk policies and URL swap.
  • Rollback: CloudFormation automatic and alarm triggers, CodeDeploy redeploys the last good revision, ECS circuit breaker, alias shift back, pipeline stage rollback; keep data changes backward compatible.
  • Source control: branches, release tags, commit-traced artifacts, tag and pull request triggers. AI: Kiro and Kiro CLI for code and checks, AWS DevOps Agent for post-deployment investigation, automated approval rules.
