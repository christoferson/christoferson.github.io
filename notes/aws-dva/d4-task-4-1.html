Task 4.1: Assist in a root cause analysis

Finding out why something broke: recognizing what an error message means, reading metrics, logs and traces to locate the failing part, querying logs for the evidence, working back from a failed deployment's output, and letting AI tools speed up the search.

Overview

Task 4.1

Assist in a root cause analysis.

A root cause analysis works from the symptom to the cause: which request failed, in which component, with what error, and why. In a distributed application the failing piece is often not where the error appears: the API returns 502 because the function returned the wrong shape; the function times out because it has no route to a service from its VPC. Error messages, metrics, logs and traces each answer part of the question, and knowing what the common ones mean is most of the skill. Setting up good logging, metrics and tracing is Task 4.2.

The examples follow the food-ordering application: an order API on API Gateway and Lambda, DynamoDB tables, an SQS kitchen queue, receipts in S3, and deployments through CloudFormation, CodeBuild, CodeDeploy and ECS.

Debugging code and integrations

Skill 4.1.1Debug application code and service integration issues to identify defects.

Lambda function errors

SymptomLikely causeFix
"Task timed out after 3.00 seconds"The function's timeout is too short for the work, a downstream call hangs, or init is slowRaise the timeout or memory (more memory means more CPU), add timeouts to downstream calls, make init leaner
Timeouts or "connect ETIMEDOUT" after moving into a VPCNo route to the internet or AWS servicesNAT gateway for private subnets, or VPC endpoints
"Unable to import module" or "Cannot find module"The handler's file name doesn't match, or a dependency is missing or built for the wrong platformCheck the handler setting and the package contents
"…handler is undefined or not exported"The handler's function name doesn't matchMatch file.function to the code
"Runtime exited…" or Runtime.ExitError in the REPORT lineThe process crashed, often out of memoryCompare Max Memory Used with Memory Size; raise memory or fix the leak
AccessDenied when the code calls a serviceThe execution role lacks the permission (or a key policy, bucket policy or SCP denies it)Add the action to the role; read the error message for the policy type
No logs at allThe role can't write to CloudWatch LogsAttach AWSLambdaBasicExecutionRole

Errors returned by the Lambda Invoke API itself (rather than by your code) mean the function couldn't run: TooManyRequestsException (429, throttled by concurrency limits), ResourceNotReadyException (the function is inactive after being idle), ResourceConflictException while the function is Pending (its VPC network interfaces are being created), network interface errors for VPC functions, and KMSAccessDeniedException when Lambda can't decrypt the environment variables. A function that throws an exception still returns HTTP 200 to a synchronous caller, with an error header and the error in the payload.

API Gateway errors

StatusUsual meaning
502 Bad GatewayThe Lambda proxy integration returned something other than statusCode, headers and a string body, or the function errored
504 Gateway TimeoutThe integration didn't respond within the timeout (29 seconds by default)
403 "Missing Authentication Token"Usually the wrong path, method or stage (the resource doesn't exist), not a missing token
403 otherAn authorizer, resource policy or AWS WAF denied it, or an API key is invalid
401The authorizer rejected the token
429Throttled by stage, method or usage plan limits, or a quota was exceeded
500 from an authorizerThe Lambda authorizer failed or returned an invalid policy

A browser "CORS" error with a proxy integration usually means the function didn't return Access-Control-Allow-Origin (it must, on every response, including errors), or the OPTIONS preflight isn't configured.

Other integrations

DynamoDBRetry ProvisionedThroughputExceededException and ThrottlingException with backoff (the SDK does), and look for a hot partition. Don't retry ConditionalCheckFailedException (the condition really failed) or ValidationException (the request is wrong: a missing key attribute, a reserved word without a placeholder, a wrong type).

SQSMessages processed more than once usually mean the consumer took longer than the visibility timeout, or didn't delete the message after success. For Lambda, set the visibility timeout to at least six times the function timeout; messages that keep failing need a dead-letter queue.

S3 403Check the identity policy, bucket policy, Block Public Access, object ownership and ACLs, and for KMS-encrypted objects the key policy (kms:Decrypt to read, kms:GenerateDataKey to write). S3's access denied messages now name the policy type that denied the request, and for explicit denies the policy ARN.

Finding permission problems

IAM access denied messages say which kind of policy is responsible: "because no identity-based policy allows…" (nothing grants it, an implicit deny) or "with an explicit deny in a service control policy…" (something blocks it). Since January 2026 they also include the ARN of the denying policy for supported services. CloudTrail event history (90 days, on by default) lists denied calls by error code, and the IAM policy simulator tests what a set of policies allows.

Recent access denied errors from CloudTrail (AWS CLI) 
aws cloudtrail lookup-events \
  --lookup-attributes \
    AttributeKey=EventSource,AttributeValue=dynamodb.amazonaws.com \
  --max-results 20 \
  --query "Events[].CloudTrailEvent"

The lookup attribute is one unsplittable value; filter the returned JSON for errorCode values such as AccessDenied.

Debugging tools

  • sam local invoke -d 5858 runs a function locally with a debugger port your IDE attaches to.
  • The AWS Toolkit for VS Code can debug a deployed function remotely, with breakpoints, through a temporary debug layer (since July 2025).
  • Live Tail streams a function's logs in real time in the Lambda console or the CLI while you reproduce the problem; sam logs --tail --include-traces does it from SAM.
  • X-Ray or CloudWatch Application Signals service maps show which integration is failing or slow (below).

"502 from API Gateway with a Lambda proxy" points to the response format. "504 after 29 seconds" points to the integration timeout. "403 Missing Authentication Token" points to a wrong URL path or stage. "Timeouts after adding the function to a VPC" points to a missing NAT gateway or endpoint. "Messages processed twice" points to the visibility timeout.

Metrics, logs and traces

Skill 4.1.2Interpret application metrics, logs, and traces.

Metrics that point to causes

MetricRising means
Lambda ErrorsExceptions or timeouts in the code (Invocations counts these too, but not throttles)
Lambda ThrottlesConcurrency limit reached: account, reserved, or event source maximum
Lambda Duration (p99)Slower code or downstream services; near the timeout means imminent timeouts
Lambda IteratorAgeA Kinesis or DynamoDB stream consumer is falling behind (errors blocking a shard, or too little parallelism)
Lambda AsyncEventAge, AsyncEventsDropped, DeadLetterErrors, DestinationDeliveryFailuresAsynchronous events retrying, expiring, or failing to reach their DLQ or destination
API Gateway 5XXError and 4XXErrorServer-side (integration, function) or client-side (auth, validation, throttling) failures; the Average statistic is the error rate
API Gateway Latency vs IntegrationLatencyIf both rise, the backend is slow; if only Latency, the time is in API Gateway (authorizers, mapping)
SQS ApproximateAgeOfOldestMessageConsumers aren't keeping up, or a message keeps failing
DynamoDB ThrottledRequests, read and write throttle eventsCapacity or a hot partition key
DynamoDB UserErrors vs SystemErrorsBad requests from your code (4xx) vs service-side errors (5xx)

Choose statistics carefully: Average hides outliers, so latency problems show in p95 or p99; Sum counts events; Maximum catches spikes. Standard metrics have 1-minute resolution; high-resolution custom metrics go down to 1 second.

The Lambda REPORT line

Every invocation ends with a REPORT log line:

A cold-start invocation (Lambda log) 
REPORT RequestId: 8f5c-...
Duration: 2817.52 ms
Billed Duration: 3148 ms
Memory Size: 512 MB
Max Memory Used: 498 MB
Init Duration: 330.12 ms
XRAY TraceId: 1-6720-... Sampled: true

Shown one field per line for reading; in the log it's one line. Init Duration appears only on cold starts, and since August 2025 it's billed for zip functions on managed runtimes (so Billed Duration includes it). Max Memory Used close to Memory Size, as here, warns of out-of-memory crashes; far below it means memory could be reduced. Duration close to the timeout warns of timeouts.

Traces

A trace follows one request across services. Each service records a segment, with subsegments for downstream calls (DynamoDB, HTTP APIs), so the trace shows where the time went and where the error started. The trace map (service map) draws the components with their latency and error rates: red for faults (5xx), yellow for errors (4xx), purple for throttling (429).

AnnotationsIndexed key-value pairs (customer tier, order ID) that you can filter traces by, for example finding all slow traces for one restaurant.

MetadataAny data attached to a segment for context, not indexed or searchable.

SamplingBy default the first request each second and 5% of the rest are traced, so a specific failed request may not have a trace. CloudWatch Transaction Search (since November 2024) can ingest all spans as logs.

Application SignalsBuilds service dashboards, dependency maps and SLOs from the same telemetry, including for Lambda.

"Which downstream call makes the API slow" points to X-Ray traces and the trace map. "Stream processing delayed" points to IteratorAge. "Backend or API Gateway latency?" points to comparing Latency with IntegrationLatency. "Some requests are slow but the average is fine" points to p99 duration.

Querying logs

Skill 4.1.3Query logs to find relevant data.

CloudWatch Logs Insights

Logs Insights queries one or more log groups with a pipeline of commands: fields (choose fields), filter (keep matching events; like and regular expressions), stats (aggregate with count(), avg(), pct(), grouped by bin(5m) or a field), sort, limit, parse (extract values from text), dedup and pattern (group similar messages). Since 2026 it also supports joins across log groups and sub-queries. For Lambda it discovers fields such as @timestamp, @message, @requestId, @type, @duration, @billedDuration, @memorySize and @maxMemoryUsed; JSON log fields are discovered automatically.

Errors per 5 minutes in the order function (Logs Insights) 
fields @timestamp, @message
| filter @message like /ERROR|Exception/
| stats count(*) as errors by bin(5m)
| sort errors desc
The 20 slowest invocations (Logs Insights) 
filter @type = "REPORT"
| fields @requestId, @duration,
    @maxMemoryUsed, @memorySize
| sort @duration desc
| limit 20
Cold start percentage (Logs Insights) 
filter @type = "REPORT"
| stats sum(strcontains(@message,
    "Init Duration")) / count(*) * 100
    as coldStartPct by bin(5m)
Every log line for one failed request (Logs Insights, JSON logs) 
fields @timestamp, level, message, orderId
| filter @requestId = "8f5c-..."
    or orderId = "o-1042"
| sort @timestamp asc

The last query works because the function writes structured JSON logs with an orderId field (Task 4.2). Logs Insights can also write a query from a plain-language question, summarize results with AI, and run OpenSearch PPL or SQL. Query only the log groups and time range you need: cost depends on data scanned.

Other ways to search logs

Live TailStreams new log events from log groups in real time, with filters, in the console or with aws logs start-live-tail.

CLIaws logs tail /aws/lambda/order-api --follow --since 10m --filter-pattern ERROR follows a log group; filter-log-events searches with filter patterns (terms, JSON property matches like { $.level = "ERROR" }, or regular expressions).

Metric filtersTurn matching log events into a metric you can graph and alarm on (for example a count of "payment declined").

Subscription filtersStream matching events to Lambda, Kinesis or Firehose for processing elsewhere.

CloudTrailWho called which API: event history for 90 days, trails to S3 (queried with Athena) for longer. CloudTrail Lake closed to new customers on May 31, 2026; AWS points to CloudWatch for querying.

"Find all errors in the last hour across functions" points to a Logs Insights query over several log groups. "Watch logs while reproducing a bug" points to Live Tail. "Alarm when a specific message appears" points to a metric filter. "Who deleted the table?" points to CloudTrail.

Deployment failures

Skill 4.1.4Troubleshoot deployment failures by using output logs.

CloudFormation and SAM

A failed stack shows CREATE_FAILED or UPDATE_FAILED events with a status reason, followed by rollback events. Find the first failure in time order: later failures are often just resources cancelled because of it. Since November 2025 each stack operation has an operation ID, and the console and describe-events can show only the failed events of one operation. The console can also show a deployment timeline and link a failure to the matching CloudTrail events. sam deploy prints the same events.

Failure reasons from the last stack events (AWS CLI) 
aws cloudformation describe-stack-events \
  --stack-name orders-prod \
  --query "StackEvents[?contains(ResourceStatus,'FAILED')].[LogicalResourceId,ResourceStatusReason]" \
  --output table

The JMESPath query is one unsplittable value. Common reasons: a missing IAM permission for the deploying role, a name already in use, an invalid property value, a resource limit, or a custom resource or Lambda function that failed to respond.

CodeBuild

The build log (in CloudWatch Logs or S3) shows each phase (DOWNLOAD_SOURCE, INSTALL, PRE_BUILD, BUILD, POST_BUILD, UPLOAD_ARTIFACTS) with its status and the output of every command; the failing command's exit code and the lines before it are the evidence. Frequent causes: a buildspec YAML error, a failing test, "toomanyrequests" when pulling from Docker Hub (use ECR or a pull-through cache), the build container running out of memory (larger compute type), and missing permissions in the CodeBuild service role ("Unable to locate credentials", "not authorized to perform"). Sandbox debugging (2025) lets you connect to a build environment to investigate.

CodeDeploy on EC2

The deployment's events in the console show which lifecycle event failed on which instance, with the last lines of the script output. On the instance:

  • Agent log: /var/log/aws/codedeploy-agent/codedeploy-agent.log
  • Script output: /opt/codedeploy-agent/deployment-root/DEPLOYMENT_GROUP_ID/DEPLOYMENT_ID/logs/scripts.log
ErrorMeaning
ScriptFailed, ScriptTimedOutA hook script exited non-zero or ran past its timeout
ScriptMissing, ScriptNotExecutableThe appspec points at a file that isn't in the revision or isn't executable
HEALTH_CONSTRAINTSToo many instances failed for the deployment configuration's minimum healthy hosts
AGENT_ISSUEThe CodeDeploy agent isn't installed or running
IAM_ROLE_PERMISSIONS, IAM_ROLE_MISSINGThe service role or instance profile lacks permissions (for example to read the revision from S3)

ApplicationStop runs the scripts of the previous successful revision, so a broken old stop script fails every new deployment; deploy once with the option to ignore ApplicationStop failures to get past it. For Lambda and ECS deployments, check the hook functions' own logs: a hook that never reports its status fails the deployment after an hour.

ECS

A service that can't reach its desired count shows service events ("unable to place a task", "task is unhealthy in target group", "unable to consistently start tasks"). For each stopped task (visible in the console for an hour, longer through the API), describe-tasks gives stoppedReason and each container's reason:

Stopped reasonCheck
CannotPullContainerErrorImage URI and tag exist; execution role can pull from ECR; the task has a route to ECR (NAT or VPC endpoints); Docker Hub rate limits
ResourceInitializationErrorThe execution role can read the secrets or parameters, and the network can reach Secrets Manager or Parameter Store
OutOfMemoryErrorTask or container memory too small
Essential container exitedThe application crashed at startup: read its logs in CloudWatch Logs
Failed health checksHealth check path and port, startup time vs grace period, security groups between load balancer and tasks
Why did the kitchen tasks stop? (AWS CLI) 
TASKS=$(aws ecs list-tasks \
  --cluster orders \
  --service-name kitchen \
  --desired-status STOPPED \
  --query "taskArns" --output text)
aws ecs describe-tasks \
  --cluster orders --tasks $TASKS \
  --query "tasks[].[stoppedReason,containers[0].reason]"

Elastic Beanstalk environments provide tail logs (last 100 lines of each log) and bundle logs (all logs) from the console or eb logs, and can stream logs to CloudWatch Logs.

"Stack rolled back, many resources failed" points to the first failed event's reason. "CodeDeploy fails on every instance at ApplicationStop" points to the previous revision's script. "ECS tasks stop immediately with CannotPullContainerError" points to the image, the execution role or the network path to ECR. "Build fails pulling base images" points to Docker Hub limits.

AI tools for errors

Skill 4.1.5Use AWS AI tools to analyze errors and to generate troubleshooting suggestions.

ToolHelps with
KiroPaste or reference an error (the #terminal and #problems context), let the agent read the code, explain the cause and propose a fix; bugfix specs record current, expected and unchanged behavior before the fix; AWS MCP servers and the AWS Observability power let it read CloudWatch logs, metrics and CloudTrail directly
Diagnose with Amazon Q (console)Explains console error messages and permission errors for Lambda, ECS, S3, EC2, Step Functions and IAM, with resolution steps; CloudFormation's "Diagnose" and ECS's "Inspect" buttons analyze failed stacks and stopped tasks
CloudWatch investigationsStarts from an alarm or a graph, gathers related metrics, logs, traces, deployments and CloudTrail events, and proposes root-cause hypotheses and remediation steps
CloudWatch Logs AI featuresWrite queries from plain language, summarize query results, group similar messages with pattern analysis, and flag unusual log patterns with anomaly detection
AWS DevOps AgentInvestigates incidents across telemetry, code and deployments and suggests mitigations such as reverting a change
Elastic Beanstalk AI analysisAnalyzes an unhealthy environment's events, health and logs (eb logs --analyze)

The Amazon Q Developer end of support (April 30, 2027) applies to its IDE plugins; the console error diagnosis is a separate experience. In Kiro, the same work is done by asking the agent with the relevant context.

An AI explanation is a hypothesis. Confirm it with the evidence (the log line, the metric, the trace) before changing code or permissions, and be wary of fixes that broaden IAM permissions to make an error disappear.

"Quickly understand a permission error in the console" points to Diagnose with Amazon Q. "An alarm fired; find related signals and likely causes" points to CloudWatch investigations. "Write a Logs Insights query without knowing the syntax" points to natural-language query generation. "Explain a stack trace and fix the code" points to Kiro.

Key takeaways

  • Know the common errors: Lambda timeouts, import and handler errors, out of memory, VPC timeouts, throttling (429), inactive or pending functions; API Gateway 502 (proxy format), 504 (timeout), 403 Missing Authentication Token (wrong path or stage); DynamoDB errors to retry or not; SQS visibility timeout; S3 403 causes including KMS.
  • Permission errors: messages name the policy type (and now often its ARN); CloudTrail event history and the policy simulator confirm.
  • Metrics: Errors, Throttles, Duration p99, IteratorAge, async event metrics; API Latency vs IntegrationLatency; SQS oldest message age; DynamoDB throttles. The REPORT line gives duration, billed duration (including init), memory used and init duration.
  • Traces: segments and subsegments, trace map colors for errors, faults and throttles, annotations for filtering, sampling limits.
  • Logs Insights: fields, filter, stats, sort, parse, pattern, joins; Lambda fields like @duration; structured logs make queries easy. Live Tail, aws logs tail, metric and subscription filters.
  • Deployment failures: first failed CloudFormation event, CodeBuild phase logs, CodeDeploy agent and script logs and error codes, ECS stopped reasons and service events, Beanstalk logs.
  • AI: Kiro for code-level diagnosis, console Diagnose with Amazon Q, CloudWatch investigations, Logs AI features, DevOps Agent; verify before acting.
