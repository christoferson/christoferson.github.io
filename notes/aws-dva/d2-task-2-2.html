Task 2.2: Implement encryption and manage sensitive data by using AWS services

Protecting data wherever it sits or travels: choosing the right encryption and keys, managing TLS certificates, encrypting in code, finding and hiding personal data, and keeping passwords and API keys out of code and configuration.

Overview

Task 2.2

Implement encryption and manage sensitive data by using AWS services.

Most AWS services encrypt data at rest by default now, and every AWS API endpoint requires TLS 1.2 or later. The developer's decisions are about control: which key (and who can use it), whether to encrypt before data leaves the application, how to keep certificates valid, how to stop personal data spreading into logs, and where secrets live.

The examples follow the food-ordering application: receipts and photos in S3, orders in DynamoDB, a payment provider API key and a database password, customer addresses and phone numbers that must not appear in logs, and an HTTPS API on a custom domain.

At rest and in transit

Skill 2.2.1Apply encryption at rest and in transit.

Encryption at rest

At-rest encryption with AWS services is mostly a choice of key. An AWS owned key is free and invisible to you. An AWS managed key (aws/s3, aws/dynamodb) lives in your account's KMS and appears in CloudTrail, but you can't change its policy. A customer managed key lets you write the key policy, control rotation, disable it, and use it across accounts.

ServiceDefaultOptions and notes
S3SSE-S3 (S3-managed keys) on every new object since January 2023SSE-KMS (with S3 Bucket Keys to cut KMS requests and cost by up to 99%), DSSE-KMS (two layers), SSE-C (your key, sent with each request)
DynamoDBAlways encrypted, AWS owned keyAWS managed or customer managed KMS key
EBSNot encrypted unless "encryption by default" is turned on for the RegionDefault key aws/ebs or a customer managed key
RDS and AuroraChosen at creationCovers storage, backups, snapshots and replicas; the key can't be changed later, and an unencrypted database is encrypted by restoring an encrypted copy of a snapshot
SQSSSE-SQS for new queuesSSE-KMS; the data key is reused for 5 minutes by default
SNS, KinesisOff until enabledKMS-based server-side encryption
Lambda environment variablesEncrypted with an AWS managed keyA customer managed key; still keep credentials in Secrets Manager
CloudWatch LogsAlways encryptedAssociate a customer managed KMS key with a log group

S3 is phasing out SSE-C by default: since April 2026 it's disabled for new general purpose buckets (and for existing buckets in accounts with no SSE-C objects). A bucket's BlockedEncryptionTypes setting turns it back on; while blocked, SSE-C requests fail with 403.

Require SSE-KMS for uploads (S3 bucket policy) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyNonKmsUploads",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:PutObject",
    "Resource": "RECEIPTS_BUCKET_ARN/*",
    "Condition": {"StringNotEquals": {
      "s3:x-amz-server-side-encryption":
        "aws:kms"}}
  }]
}

Usually simpler: set the bucket's default encryption to SSE-KMS with your key, and objects are encrypted that way without any header from clients. The policy above additionally rejects uploads that explicitly ask for something else.

Encryption in transit

  • All AWS service endpoints require TLS 1.2 or later (since February 2024); the SDKs use HTTPS by default. Some endpoints (KMS, ACM, Secrets Manager) also offer hybrid post-quantum key exchange.
  • Deny plain HTTP in resource policies with the aws:SecureTransport condition set to false.
  • Terminate HTTPS at CloudFront, Application Load Balancers or API Gateway with ACM certificates, and choose a security policy that sets the minimum TLS version and ciphers.
  • Encrypt database connections: require TLS on RDS (for example the rds.force_ssl parameter for PostgreSQL) and trust the current RDS certificate authorities.
Deny any request not made over HTTPS (policy statement) 
{
  "Sid": "HttpsOnly",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "RECEIPTS_BUCKET_ARN",
    "RECEIPTS_BUCKET_ARN/*"],
  "Condition": {"Bool": {
    "aws:SecureTransport": "false"}}
}

"Control and audit who can decrypt the data" points to a customer managed KMS key. "Reduce KMS costs for millions of S3 objects" points to S3 Bucket Keys. "Encrypt an existing unencrypted RDS database" points to an encrypted snapshot copy and restore. "Reject unencrypted connections" points to aws:SecureTransport.

Certificates

Skill 2.2.2Manage certificates by using AWS services (for example, AWS Certificate Manager, AWS Private CA).

AWS Certificate Manager

ACM issues free public TLS certificates for domains you control and deploys them to integrated services: Elastic Load Balancing, CloudFront, API Gateway, App Runner, Amplify, Elastic Beanstalk, Cognito custom domains and others. You prove control of the domain with DNS validation (a CNAME record, recommended: renewal is automatic while the record stays) or email validation. ACM renews certificates that are in use automatically, and the private key never leaves AWS (except for exportable certificates, a paid option since 2025).

  • Certificates are Regional. CloudFront (and edge-optimized API Gateway endpoints) need the certificate in us-east-1; load balancers and Regional APIs need it in their own Region.
  • Public certificates now last at most 198 days (since February 2026, following CA/Browser Forum rules) and renew 45 days before expiry; the maximum drops below 100 days in 2027. Email validation ends for new certificates in March 2027.
  • Imported certificates (from another CA) are never renewed by ACM. Watch the DaysToExpiry CloudWatch metric or the "approaching expiration" EventBridge events, and reimport before they expire.
Request a DNS-validated certificate (AWS CLI) 
aws acm request-certificate \
  --domain-name api.example.com \
  --subject-alternative-names \
    www.example.com \
  --validation-method DNS

aws acm describe-certificate then shows the CNAME record to create (Route 53 can create it from the console).

AWS Private CA

For internal names and machine identities that browsers don't need to trust (service-to-service TLS, mutual TLS, IoT devices, IAM Roles Anywhere), AWS Private CA runs a private certificate authority. ACM can issue and renew private certificates from it for integrated services. A general-purpose CA issues certificates of any validity; a cheaper short-lived certificate CA issues certificates valid for up to 7 days, which removes the need for revocation.

"HTTPS for a public website with automatic renewal" points to an ACM public certificate with DNS validation. "Certificate for CloudFront" points to us-east-1. "Internal TLS or mutual TLS between services" points to AWS Private CA. "Imported certificate expired" points to monitoring DaysToExpiry and reimporting.

Client-side or server-side

Skill 2.2.3Select and apply client-side or server-side encryption.

Server-side encryptionThe service encrypts data after receiving it and decrypts it when an authorized caller reads it. No code changes, works with every feature of the service. The service (and anyone with read permission and key access) sees the plaintext.

Client-side encryptionYour application encrypts data before sending it, so the service only ever stores ciphertext. Use it when data must be protected end to end, when the storage shouldn't be trusted with plaintext, or when individual fields need protection inside a record. The cost: more code, key handling in the app, and the service can't search or process the encrypted content.

NeedChoose
Encrypt S3 objects with audit of every key useSSE-KMS with a customer managed key
Encrypt S3 objects with no KMS cost or request limitsSSE-S3
Two independent layers for complianceDSSE-KMS
Data encrypted before it leaves the applicationClient-side: AWS Encryption SDK or the Amazon S3 Encryption Client
Encrypt and sign individual DynamoDB attributes, and still search themAWS Database Encryption SDK (formerly the DynamoDB Encryption Client), with searchable encryption beacons

The AWS Encryption SDK is a client-side library for any data: it does envelope encryption with KMS keys (via keyrings), stores the encrypted data key with the ciphertext in one portable message, binds an encryption context (non-secret key-value pairs that must match on decrypt), and can cache data keys to reduce KMS calls.

Server-side SSE-KMS calls KMS for objects you write and read, so very high request rates can hit KMS quotas (ThrottlingException) and add cost. S3 Bucket Keys or the Encryption SDK's data key caching reduce the calls.

Using encryption keys

Skill 2.2.4Use encryption keys to encrypt and decrypt data.

KMS keys

An AWS KMS key never leaves KMS unencrypted; you send data or data keys to KMS to be encrypted and decrypted. Most keys are symmetric (AES-256-GCM, SYMMETRIC_DEFAULT), used by AWS services and for envelope encryption. Asymmetric keys (RSA, elliptic curve, and post-quantum ML-DSA for signing) can encrypt or sign with a public key usable outside AWS. HMAC keys create and verify message authentication codes.

Key policyEvery KMS key has a key policy; the default one lets the account's IAM policies grant access. Without key policy or grant permission, IAM policies alone can't use the key. Conditions such as kms:ViaService limit a key to use through one service (for example S3 in one Region), and kms:EncryptionContext: keys require a specific context.

AliasesFriendly names (alias/orders) that code can use instead of key IDs, and that can be re-pointed to another key.

RotationAutomatic rotation of customer managed symmetric keys, every 90 to 2,560 days (365 by default), plus on-demand rotation; old key material is kept, so existing ciphertext still decrypts. AWS managed keys rotate yearly.

DeletionScheduled with a 7 to 30-day waiting period; data encrypted under a deleted key is lost, so disable a key first to find out what still uses it.

Quotas and costSymmetric cryptographic requests share a per-account, per-Region quota (10,000 per second in most Regions, more in the largest); exceeding it raises ThrottlingException. A customer managed key costs $1 per month plus a charge per 10,000 requests.

Encrypt and decrypt directly

Encrypt accepts at most 4 KB of plaintext, so it's for small secrets like a token or a password. Decrypt doesn't need the key ID for symmetric keys (it's in the ciphertext), but naming it is safer.

Encrypt a small value with an encryption context (Python) 
kms = boto3.client("kms")
ctx = {"tenant": "r-42", "purpose": "pos"}

ct = kms.encrypt(
    KeyId="alias/orders",
    Plaintext=api_token.encode(),
    EncryptionContext=ctx,
)["CiphertextBlob"]

pt = kms.decrypt(
    CiphertextBlob=ct,
    KeyId="alias/orders",
    EncryptionContext=ctx,
)["Plaintext"]

The encryption context isn't secret, but decryption fails unless the same context is supplied, and it's recorded in CloudTrail, which shows what each decryption was for.

Envelope encryption

For anything larger than 4 KB, encrypt the data locally with a data key and keep that data key encrypted under the KMS key:

  1. Get a data keyGenerateDataKey returns the data key twice: in plaintext and encrypted under the KMS key.
  2. Encrypt locallyEncrypt the data with the plaintext data key (AES-GCM), then erase the plaintext key from memory.
  3. Store togetherStore the ciphertext with the encrypted data key.
  4. DecryptSend the encrypted data key to KMS Decrypt, get the plaintext data key back, and decrypt the data locally.
Envelope encryption of a receipt (Python) 
import os
from cryptography.hazmat.primitives \
    .ciphers.aead import AESGCM

dk = kms.generate_data_key(
    KeyId="alias/orders",
    KeySpec="AES_256")
nonce = os.urandom(12)
ct = AESGCM(dk["Plaintext"]).encrypt(
    nonce, receipt_pdf, None)
record = {"data": ct, "nonce": nonce,
          "key": dk["CiphertextBlob"]}

# later
resp = kms.decrypt(
    CiphertextBlob=record["key"])
key = resp["Plaintext"]
pdf = AESGCM(key).decrypt(
    record["nonce"], record["data"], None)

Only data keys travel to KMS, so large data never hits the 4 KB limit and KMS sees one request per data key, not per byte. The AWS Encryption SDK implements this pattern for you; prefer it over hand-written code. GenerateDataKeyWithoutPlaintext returns only the encrypted copy, for a component that will need the key later. ReEncrypt moves ciphertext to another KMS key without exposing plaintext.

"Encrypt a file larger than 4 KB with KMS" points to envelope encryption (GenerateDataKey). "KMS ThrottlingException under load" points to data key caching, S3 Bucket Keys, or a quota increase. "Only allow the key to be used by S3" points to kms:ViaService. "Another account must decrypt" points to the key policy (customer managed keys only).

Development certificates and SSH keys

Skill 2.2.5Generate certificates and SSH keys for development purposes.

SSH access to instances

EC2 key pairsEC2 can create a key pair (RSA, or ED25519 for Linux only) and give you the private key once, or import a public key you generated with ssh-keygen. Windows instances need an RSA key to decrypt the administrator password.

EC2 Instance ConnectPushes a temporary public key to the instance for 60 seconds, authorized by IAM, so no long-lived keys are shared. An EC2 Instance Connect Endpoint reaches instances in private subnets without a bastion host.

Session ManagerAWS Systems Manager Session Manager opens a shell with no inbound ports, no bastions and no SSH keys, controlled by IAM and logged. It's usually the preferred answer for administrative access.

Create a key pair and connect (shell) 
aws ec2 create-key-pair \
  --key-name dev-key \
  --key-type ed25519 \
  --query KeyMaterial \
  --output text > dev-key.pem
chmod 400 dev-key.pem
ssh -i dev-key.pem ec2-user@HOST

Certificates for development

For local HTTPS testing, a self-signed certificate is enough; clients must be told to trust it. For anything shared (a test environment others use), use ACM public certificates on a test domain, or Private CA for internal names. A self-signed or third-party certificate can be imported into ACM for use with load balancers, but ACM won't renew it.

A self-signed certificate valid for 30 days (OpenSSL) 
openssl req -x509 -newkey rsa:2048 \
  -nodes -days 30 \
  -keyout dev.key -out dev.crt \
  -subj "/CN=localhost"

"Admins need shell access without opening port 22 or managing keys" points to Session Manager. "Short-lived SSH access controlled by IAM" points to EC2 Instance Connect. "Test HTTPS locally" points to a self-signed certificate; "trusted internal certificates" points to Private CA.

Sensitive data

Skill 2.2.6Identify, mask, and limit access to sensitive data (for example, personally identifiable information [PII], protected health information [PHI]) by using AWS services.

PII (personally identifiable information) is data that identifies a person: names, addresses, phone numbers, card numbers. PHI (protected health information) is health data tied to a person, regulated under laws such as HIPAA in the United States. The goal is to know where it is, hide it where it isn't needed, and limit who can see it.

Identify

Amazon MacieScans S3 for sensitive data with managed data identifiers (names, addresses, credentials, financial and health data) and your own custom identifiers. Automated discovery samples buckets continuously; discovery jobs scan chosen buckets. Findings go to EventBridge and Security Hub.

Amazon ComprehendDetectPiiEntities finds PII types and their positions in text (up to 100 KB per call); ContainsPiiEntities just says which types are present; asynchronous jobs can redact whole documents. Amazon Comprehend Medical DetectPHI does the same for health information.

Mask

CloudWatch Logs data protectionA data protection policy on a log group (or the account) audits and masks sensitive data as logs arrive: email addresses, card numbers, addresses and more show as asterisks in the console, Logs Insights, subscriptions and exports. Users with logs:Unmask can see the original. Masking applies from when the policy is set, not retroactively.

Masking in codeRedact before logging or returning data: log an order ID, not the customer's address; show the last four digits of a card. Use Comprehend in a pipeline to redact free text, such as delivery notes, before storing it in analytics.

For AI servicesBedrock Guardrails sensitive information filters block or mask PII in model inputs and outputs (Task 2.3).

Mask email and card numbers in a log group (data protection policy) 
{
  "Name": "orders-logs-protection",
  "Version": "2021-06-01",
  "Statement": [
    {"Sid": "audit",
     "DataIdentifier": [
       "arn:aws:dataprotection::aws:data-identifier/EmailAddress",
       "arn:aws:dataprotection::aws:data-identifier/CreditCardNumber"],
     "Operation": {"Audit": {
       "FindingsDestination": {}}}},
    {"Sid": "redact",
     "DataIdentifier": [
       "arn:aws:dataprotection::aws:data-identifier/EmailAddress",
       "arn:aws:dataprotection::aws:data-identifier/CreditCardNumber"],
     "Operation": {"Deidentify": {
       "MaskConfig": {}}}}
  ]
}

The data identifier ARNs can't be split. Apply it with aws logs put-data-protection-policy --log-group-identifier /aws/lambda/order-api --policy-document file://policy.json.

Limit access

  • Keep sensitive data in separate stores or attributes and restrict them with IAM: DynamoDB's dynamodb:Attributes condition limits which attributes a role can read; S3 prefixes or separate buckets limit objects.
  • Encrypt with a dedicated customer managed KMS key whose key policy names only the roles that may decrypt.
  • Tag data by classification and use ABAC conditions on the tags.

SNS message data protection is closed to new customers, and S3 Object Lambda (once used to redact data on read) is in maintenance. Redact in your own code or with CloudWatch Logs data protection instead.

"Find PII in S3 buckets" points to Macie. "Detect PII in text from the application" points to Comprehend (Comprehend Medical for PHI). "Customer emails appear in Lambda logs" points to a CloudWatch Logs data protection policy, and to not logging them. "Support staff must not see card numbers" points to masking plus IAM limits on the attribute.

Secrets

Skill 2.2.7Use secret management services to secure sensitive data.

Secrets (database passwords, API keys, tokens) don't belong in code, repositories, AMIs or plain environment variables. Store them in a managed service, encrypted with KMS, retrieved at runtime with IAM permissions, and audited in CloudTrail.

FeatureAWS Secrets ManagerParameter Store (Systems Manager)
Made forSecrets that should rotate: database credentials, API keysConfiguration values and simple secrets (SecureString)
RotationBuilt in: managed rotation for RDS, Aurora, Redshift and DocumentDB, or a Lambda rotation function for anything else; as often as every 4 hoursNone built in
SizeUp to 64 KB4 KB standard, 8 KB advanced
Cost$0.40 per secret per month plus API callsStandard parameters free (up to 10,000); advanced charged, with expiration policies and cross-account sharing
ExtrasCross-Region replication, resource policies, versions with staging labelsHierarchies (/orders/prod/...), String and StringList types; default 40 requests per second, more with higher throughput

Rotation in Secrets Manager

Each secret has versions marked by staging labels: AWSCURRENT (what GetSecretValue returns by default), AWSPENDING (being rotated in) and AWSPREVIOUS. A rotation function runs four steps: createSecret (make the new value as AWSPENDING), setSecret (change it in the database or service), testSecret, and finishSecret (move AWSCURRENT). The alternating users strategy switches between two database users so connections never break during rotation. For RDS, letting RDS manage the master password (--manage-master-user-password) stores and rotates it in Secrets Manager for you.

Reading secrets in code

Fetch secrets at init and cache them, rather than on every request: Secrets Manager's client-side caching libraries, or the AWS Parameters and Secrets Lambda Extension, which serves secrets and parameters from a local cache on localhost:2773 (cached for up to 300 seconds by default). Refresh when a call fails with an authentication error, because the secret may have rotated.

Read the payment API key once per environment (Python) 
sm = boto3.client("secretsmanager")
_cache = {}

def payment_key():
    if "pay" not in _cache:
        r = sm.get_secret_value(
            SecretId="prod/payments/api")
        _cache["pay"] = json.loads(
            r["SecretString"])["apiKey"]
    return _cache["pay"]
Read a SecureString parameter (Python) 
ssm = boto3.client("ssm")
url = ssm.get_parameter(
    Name="/orders/prod/kitchen-url",
    WithDecryption=True,
)["Parameter"]["Value"]

The role needs secretsmanager:GetSecretValue or ssm:GetParameter, plus kms:Decrypt on the key if it's a customer managed key.

Secrets in deployments

CloudFormationDynamic references resolve secrets at deploy time without putting them in the template: {{resolve:secretsmanager:prod/db:SecretString:password}} or {{resolve:ssm-secure:/orders/prod/token}} (on supported properties).

ECSTask definitions map secrets to environment variables with secrets and valueFrom (a Secrets Manager or Parameter Store ARN); the task execution role needs read permission. Values are read when the container starts, so a rotated secret needs new tasks.

LambdaRead from Secrets Manager or Parameter Store at init (or through the extension) instead of storing the value in an environment variable.

"Database password must rotate automatically" points to Secrets Manager. "Store configuration and a few encrypted values cheaply" points to Parameter Store SecureString. "Don't put the password in the CloudFormation template" points to dynamic references. "Fewer calls to Secrets Manager from Lambda" points to caching or the Parameters and Secrets extension.

Key takeaways

  • At rest: S3 (SSE-S3 default; SSE-KMS with Bucket Keys; SSE-C now blocked by default on new buckets), DynamoDB always encrypted, EBS by-default setting, RDS at creation only. Choose AWS owned, AWS managed or customer managed keys. In transit: TLS 1.2+ everywhere, aws:SecureTransport, security policies.
  • ACM: free public certificates, DNS validation, automatic renewal for certificates in use (now up to 198 days), us-east-1 for CloudFront; imported certificates aren't renewed. Private CA for internal and mutual TLS.
  • Server-side encryption is transparent; client-side encryption (Encryption SDK, S3 Encryption Client, Database Encryption SDK) protects data before it leaves the application.
  • KMS: key policies, aliases, rotation (90 to 2,560 days or on demand), 4 KB Encrypt limit, envelope encryption with GenerateDataKey, encryption context, request quotas.
  • Development: EC2 key pairs, Instance Connect (60-second keys), Session Manager (no keys or ports), self-signed certificates locally.
  • Sensitive data: Macie for S3, Comprehend (and Comprehend Medical) for text, CloudWatch Logs data protection to mask logs, IAM attribute limits and dedicated keys to restrict access.
  • Secrets Manager for rotating secrets (staging labels, rotation functions, managed rotation); Parameter Store for configuration and SecureStrings; cache in code; dynamic references in CloudFormation; valueFrom in ECS.
