Overview

Task 4.2

Apply logging, monitoring, and observability best practices.

Observability means being able to answer new questions about a running system from what it emits: logs (what happened, in detail), metrics (how much and how fast, over time), and traces (the path of one request through services). This task is about producing those signals deliberately in code and configuration, then alerting on them. Reading them during an incident is Task 4.1.

The examples follow the food-ordering application: Lambda functions for the order API and payments, an ECS kitchen service behind a load balancer, and a pipeline that deploys both.

Logging strategies

Skill 4.2.1Implement effective logging strategies to record application behavior and state (for example, by using structured logging for application events and user actions).

Structured logging

A structured log line is a JSON object with named fields instead of free text. "Order o-1042 for c-9 failed: card declined" is readable, but {"level": "ERROR", "event": "payment_failed", "orderId": "o-1042", "reason": "card_declined"} can be filtered, counted and joined in Logs Insights without fragile text parsing. Good practice:

  • Use consistent field names across services (orderId, not sometimes order_id).
  • Include a correlation ID (the API request ID, or one generated at the edge and passed on) and the trace ID, so one request's lines can be found in every service.
  • Log events and decisions (order placed, payment declined, retry attempted) with the state that explains them, at the right level: DEBUG for detail, INFO for normal events, WARN for recoverable problems, ERROR for failures.
  • Log user actions (who did what to which order) for support and audit; CloudTrail separately records AWS API calls.
  • Never log secrets or full personal data; log IDs instead, and mask what slips through with CloudWatch Logs data protection (Task 2.2).

Lambda's logging controls

Since November 2023 a function can emit its logs as JSON and filter them by level without code changes: set the log format to JSON, an application log level (TRACE to FATAL) and a system log level (for Lambda's own START and REPORT records), and optionally a custom or shared log group. Each JSON line includes timestamp, level, message and requestId; in Python, fields passed in extra become top-level keys.

JSON logs at INFO and above (AWS CLI) 
aws lambda update-function-configuration \
  --function-name order-api \
  --logging-config LogFormat=JSON,ApplicationLogLevel=INFO,SystemLogLevel=WARN

The logging configuration is one shorthand value. Level filtering only works with the JSON format, and a level set in code overrides it.

Powertools for AWS Lambda: Logger

Powertools (for Python, TypeScript, Java and .NET) adds a logger that writes structured JSON with the function context (name, memory, cold start, request ID), a correlation ID taken from the event, and keys you append for the rest of the invocation:

Structured logs with a correlation ID (Python, Powertools) 
from aws_lambda_powertools import Logger
from aws_lambda_powertools.logging \
    import correlation_paths

logger = Logger(service="orders")
API = correlation_paths.API_GATEWAY_REST

@logger.inject_lambda_context(
    correlation_id_path=API)
def handler(event, context):
    order = json.loads(event["body"])
    logger.append_keys(
        orderId=order["orderId"])
    count = len(order["items"])
    logger.info("order received",
                extra={"items": count})
    ...

Every later line in the invocation carries orderId and the correlation ID. POWERTOOLS_SERVICE_NAME and POWERTOOLS_LOG_LEVEL set the service and level from environment variables, and a sample rate can log at DEBUG for a small share of requests.

Where logs go and what they cost

Log classesCloudWatch Logs has a Standard class and a cheaper Essentials class (formerly Infrequent Access) that lacks features such as metric filters, subscription filters, embedded metric extraction and Live Tail. The class is chosen when the log group is created.

RetentionSet a retention period on every log group; the default is to keep logs forever.

Lambda log destinationsSince May 2025, Lambda logs have tiered volume pricing and can also be sent directly to S3 or Data Firehose, which is cheaper for logs you rarely query.

ContainersECS tasks send stdout to CloudWatch Logs with the awslogs driver (use the default non-blocking mode so a logging outage can't hang the application), or route logs anywhere with FireLens (a Fluent Bit sidecar). On EC2, the CloudWatch agent ships log files.

"Search logs by order ID across services" points to structured JSON logs with consistent fields and a correlation ID. "Too many debug logs in production" points to Lambda application log levels or Powertools log levels. "Reduce log costs for rarely read logs" points to the Essentials class, retention, or delivery to S3.

Custom metrics

Skill 4.2.2Implement code that emits custom metrics.

AWS publishes infrastructure metrics; only your code knows business and application facts: orders placed, payments declined, cart value, time to prepare. A custom metric has a namespace, a name, optional dimensions (name-value pairs such as Restaurant=r-42), a value and a unit.

Three ways to emit them

PutMetricDataAn API call per batch (up to 1,000 metrics and 1 MB per request; up to 30 dimensions per metric; StorageResolution 1 for high-resolution, per-second metrics). Simple, but each call adds latency and cost.

Embedded metric format (EMF)Write a JSON log line in a specific shape and CloudWatch extracts the metrics from the logs asynchronously. From Lambda, just print it: no API call, no added latency, and the log line keeps the detail (order ID) for investigation. Needs a Standard-class log group.

Metric filtersCount or extract values from existing log lines that match a pattern, with no code change.

PutMetricData (Python) 
cw = boto3.client("cloudwatch")
cw.put_metric_data(
    Namespace="FoodOrders",
    MetricData=[{
        "MetricName": "OrdersPlaced",
        "Dimensions": [{
            "Name": "Channel",
            "Value": "mobile"}],
        "Value": 1,
        "Unit": "Count",
    }],
)
The same metric in embedded metric format (one log line) 
{
  "_aws": {
    "Timestamp": 1762380000000,
    "CloudWatchMetrics": [{
      "Namespace": "FoodOrders",
      "Dimensions": [["Channel"]],
      "Metrics": [{"Name": "OrdersPlaced",
                   "Unit": "Count"}]
    }]
  },
  "Channel": "mobile",
  "OrdersPlaced": 1,
  "orderId": "o-1042"
}

Shown on several lines; emitted as one. orderId isn't in the dimensions, so it stays in the log for searching without creating a metric per order.

Metrics with Powertools (Python) 
from aws_lambda_powertools import Metrics
from aws_lambda_powertools.metrics \
    import MetricUnit

metrics = Metrics(namespace="FoodOrders",
                  service="orders")

@metrics.log_metrics(
    capture_cold_start_metric=True)
def handler(event, context):
    metrics.add_dimension(
        name="Channel", value="mobile")
    metrics.add_metric(
        name="OrdersPlaced",
        unit=MetricUnit.Count, value=1)

Powertools writes EMF when the handler returns (and adds a cold-start metric). Add metrics inside the handler, not at module level, or they're only emitted on cold starts.

Every unique combination of dimension values is a separate, billed metric. A dimension like orderId or requestId creates millions of metrics. Keep dimensions low-cardinality (channel, restaurant tier, status) and put high-cardinality values in the log fields instead.

"Emit business metrics from Lambda without slowing it down" points to EMF (or Powertools Metrics). "Count occurrences of a message already in the logs" points to a metric filter. "Per-second metric for a fast alarm" points to high-resolution metrics.

Notification alerts

Skill 4.2.3Implement notification alerts for specific actions (for example, quota limits, deployment completions).

CloudWatch alarms

An alarm watches one metric, a metric math expression, or the result of other alarms (a composite alarm), and moves between OK, ALARM and INSUFFICIENT_DATA. It evaluates the last N periods and goes into alarm when M of them breach the threshold ("datapoints to alarm", M out of N), which avoids alerts on single spikes. Missing data can count as breaching, not breaching, ignored, or missing. Instead of a fixed threshold, an anomaly detection alarm learns the metric's normal band, including daily and weekly patterns. Actions run when the state changes: notify an SNS topic, invoke a Lambda function, scale, stop or recover an EC2 instance, create a Systems Manager OpsItem or incident, or start a CloudWatch investigation; every state change is also an EventBridge event.

Alarm when more than 1% of order requests fail (AWS CLI) 
aws cloudwatch put-metric-alarm \
  --alarm-name order-api-5xx \
  --namespace AWS/ApiGateway \
  --metric-name 5XXError \
  --dimensions Name=ApiName,Value=orders \
  --statistic Average \
  --period 60 \
  --evaluation-periods 5 \
  --datapoints-to-alarm 3 \
  --threshold 0.01 \
  --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions ONCALL_TOPIC_ARN

The Average of 5XXError is the error rate; the alarm fires when 3 of the last 5 minutes exceed 1%.

Delivering notifications

Amazon SNSThe usual alarm target: email, SMS, HTTPS, Lambda or SQS subscribers.

ChatAmazon Q Developer in chat applications (renamed from AWS Chatbot in February 2025) posts SNS notifications to Slack or Microsoft Teams channels.

AWS User NotificationsA central place to configure notifications from EventBridge events (for example alarm state changes or AWS Health events) to email, chat channels and the AWS Console Mobile App.

Alerts for deployments and other events

Most services publish state changes to EventBridge; a rule matches the ones you care about and sends them to SNS, chat or a function.

Notify when a production deployment completes (event pattern) 
{
  "source": ["aws.codepipeline"],
  "detail-type": [
    "CodePipeline Pipeline Execution State Change"],
  "detail": {
    "pipeline": ["orders-pipeline"],
    "state": ["SUCCEEDED", "FAILED"]
  }
}

The detail-type string can't be split. In the developer tools console, notification rules on a pipeline, build project or deployment application create such rules for you, targeting SNS or chat.

Quota limits

  • Many services publish usage to the AWS/Usage namespace. An alarm on the metric math expression m1/SERVICE_QUOTA(m1)*100 warns at, say, 80% of a quota; the Service Quotas console can create it for you.
  • Service Quotas automatic management (2025) notifies at 80% and 95% of quotas and can request increases automatically.
  • For Lambda, alarm on ClaimedAccountConcurrency against the account's concurrency limit, and on Throttles.

"Alert only if the error rate stays high, not on one spike" points to M out of N datapoints. "Alert when either the API errors or the queue backs up, but only page once" points to a composite alarm. "Notify the team channel when a deployment finishes" points to an EventBridge rule or notification rule to SNS or chat. "Warn before hitting a service quota" points to SERVICE_QUOTA() alarms or Service Quotas notifications.

Instrumenting code

The AWS X-Ray SDKs and daemon entered maintenance mode on February 25, 2026 (security fixes only). AWS recommends OpenTelemetry: the AWS Distro for OpenTelemetry (ADOT) SDKs, the AWS Lambda layer for OpenTelemetry, and the CloudWatch agent or an OpenTelemetry Collector in place of the daemon. Traces still appear in the X-Ray and CloudWatch trace views. Powertools Tracer (capture_lambda_handler, put_annotation) wraps the X-Ray SDK, so it inherits that status.

Lambda with OpenTelemetryAdd the AWS OpenTelemetry Lambda layer, set AWS_LAMBDA_EXEC_WRAPPER=/opt/otel-instrument, and the runtime's AWS SDK, HTTP and database calls are traced automatically. The same setup enables CloudWatch Application Signals.

ContainersRun the ADOT Collector (or the CloudWatch agent) as a sidecar or daemon; applications send spans to it over OTLP. Application Signals can auto-instrument Java, Python, Node.js and .NET on ECS, EKS and EC2.

Custom spans and attributesWrap important steps (validate, charge, notify) in spans and add attributes such as the restaurant tier, which become searchable, like X-Ray annotations.

A custom span with attributes (Python, OpenTelemetry) 
from opentelemetry import trace

tracer = trace.get_tracer("orders")

def charge(order):
    with tracer.start_as_current_span(
            "charge_payment") as span:
        span.set_attribute(
            "order.id", order["orderId"])
        span.set_attribute(
            "payment.provider", "acme")
        return payments.charge(order)

Sampling and context

Tracing every request is costly at volume, so traces are sampled. X-Ray sampling rules (priority, a fixed reservoir of requests per second, then a percentage rate, matched by service, method and path) are set centrally in the console without redeploying; for example, trace every payment request but 1% of menu reads. CloudWatch Transaction Search can capture all spans as logs. Context travels between services in the X-Amzn-Trace-Id header (Root=...;Parent=...;Sampled=1) or the W3C traceparent header.

"See time spent in each downstream call of a Lambda function" points to active tracing plus instrumentation. "Trace through SQS to the consumer" points to propagated trace headers. "Trace more of one critical path" points to a custom sampling rule. "New project, X-Ray SDK or OpenTelemetry?" points to OpenTelemetry (ADOT).

Workload health

Skill 4.2.5Monitor workload health (for example, by using application health checks, liveness and readiness probes).

Health checks let the platform route around and replace unhealthy copies of an application automatically. Two kinds of question are asked: liveness (is the process working at all, or should it be restarted?) and readiness (can it serve traffic right now, or should traffic go elsewhere?).

Load balancer health checks

An Application Load Balancer target group sends a request to each target's health check path (default /) every interval (default 30 seconds), marks it unhealthy after a number of failures (default 2) and healthy again after successes (default 5), with a timeout (default 5 seconds) and accepted status codes (default 200). Unhealthy targets get no traffic; if all are unhealthy, the load balancer sends traffic to all of them anyway (fails open).

ECS and EKS

An ECS container health check in the task definition runs a command inside the container; a task whose essential container becomes unhealthy is replaced. The service's health check grace period stops load balancer and container checks from killing tasks that are still starting.

Container health check (task definition JSON) 
"healthCheck": {
  "command": ["CMD-SHELL",
    "curl -f http://localhost:8080/health || exit 1"],
  "interval": 30,
  "timeout": 5,
  "retries": 3,
  "startPeriod": 60
}

The command string can't be split. On EKS, Kubernetes probes do the same job: a startup probe waits for slow starts, a liveness probe restarts a stuck container, and a readiness probe removes a pod from the Service while it can't serve.

Probes for the kitchen container (Kubernetes YAML) 
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
startupProbe:
  httpGet:
    path: /health/live
    port: 8080
  failureThreshold: 30
  periodSeconds: 5

Designing health endpoints

Keep the liveness check shallow: can the process respond? If it checks the database too, a database outage makes every container fail liveness and restart, which only makes things worse. A readiness check can include critical dependencies, so a copy that can't reach them stops receiving traffic. Health endpoints should be fast and cheap, and shouldn't need authentication.

Watching from the outside

CloudWatch Synthetics canariesScripts (Node.js with Puppeteer or Playwright, Python with Selenium, or Java) that run on a schedule against your endpoints from outside, from blueprints such as heartbeat checks, API canaries, broken link checks and multi-step workflows. They catch problems users would see, even when no one is using the app.

Route 53 health checksCheck an endpoint, a CloudWatch alarm, or other health checks, and fail DNS over to a healthy Region or a static page.

LambdaHas no health check: monitor its Errors, Throttles, Duration and, for streams, IteratorAge, with alarms, plus canaries against the API.

OthersEC2 status checks (system, instance, attached EBS volumes), Elastic Beanstalk enhanced health reporting, and Application Signals SLOs (service level objectives on latency and availability).

"Restart containers that hang" points to a liveness probe or container health check. "Don't send traffic to a pod still warming its cache" points to a readiness probe. "New tasks are killed before they finish starting" points to a health check grace period or startup probe. "Know the API is down before customers report it" points to a Synthetics canary.

Key takeaways

  • Logging: structured JSON with consistent fields, correlation and trace IDs, sensible levels, no secrets or personal data. Lambda's JSON format and log levels; Powertools Logger for context and correlation; log classes, retention and delivery to S3 for cost.
  • Custom metrics: PutMetricData, embedded metric format (Lambda stdout, no latency), Powertools Metrics, metric filters; keep dimensions low-cardinality; high resolution for fast alarms.
  • Alerts: alarms with M out of N datapoints, missing-data handling, anomaly detection and composite alarms; SNS, chat and User Notifications; EventBridge rules for pipeline, build, CodeDeploy, ECS and Health events; quota alarms with SERVICE_QUOTA() and Service Quotas notifications.
  • Tracing: active tracing for Lambda, API Gateway stages and Step Functions; trace context through SQS and SNS; OpenTelemetry (ADOT, Lambda layer, collector) replaces the X-Ray SDK and daemon; custom spans and attributes; central sampling rules.
  • Health: ALB target group checks, ECS container health checks and grace periods, Kubernetes startup, liveness and readiness probes; shallow liveness, dependency-aware readiness; Synthetics canaries and Route 53 health checks from outside; alarms for Lambda.
