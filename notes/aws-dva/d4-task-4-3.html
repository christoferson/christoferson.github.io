Task 4.3: Optimize applications by using AWS services and features

Overview

Task 4.3

Optimize applications by using AWS services and features.

Optimization starts from measurement, not guesses: find the slowest or most expensive part, change one setting, and measure again. The levers in this task are concurrency (how many requests run at once, and against what limits), resources (memory, CPU and instance size), messaging (fewer, bigger, better-targeted messages), and caching (not doing the same work twice). Several build on earlier tasks: Lambda concurrency controls in Task 1.2, caching strategies in Task 1.3, metrics and traces in Task 4.1.

The examples follow the food-ordering application under a lunchtime peak: the order API on Lambda in front of an Aurora database, the kitchen service on ECS, the order queue, and popular menus read thousands of times a minute.

Concurrency

Skill 4.3.1Apply concurrency concepts (for example, AWS Lambda provisioned concurrency, Amazon EC2 Auto Scaling, thread pool management, connection pooling).

Sizing Lambda concurrency

Concurrency needed is roughly requests per second × average duration in seconds. At the lunch peak, 400 orders per second taking 0.25 seconds each need about 100 concurrent executions; if a slow database makes them take 1 second, the same traffic needs 400. Faster code needs less concurrency, which is why optimization and scaling go together.

GoalUse
No cold starts for an interactive API at a known baselineProvisioned concurrency on an alias, sized to peak plus about 10%, scaled on a schedule or by target tracking (charged while configured)
Faster cold starts without paying for idle environmentsSnapStart (Java, Python, .NET; not together with provisioned concurrency)
Guarantee a function capacity, or cap it to protect a databaseReserved concurrency (no charge)
Limit how fast a queue drains into a functionMaximum concurrency on the SQS event source mapping
Scale provisioned concurrency to 70% utilization (AWS CLI) 
aws application-autoscaling \
  register-scalable-target \
  --service-namespace lambda \
  --resource-id function:order-api:live \
  --scalable-dimension \
    lambda:function:ProvisionedConcurrency \
  --min-capacity 20 --max-capacity 200

aws application-autoscaling \
  put-scaling-policy \
  --service-namespace lambda \
  --resource-id function:order-api:live \
  --scalable-dimension \
    lambda:function:ProvisionedConcurrency \
  --policy-name pc-70 \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration file://pc.json
pc.json 
{"TargetValue": 0.7,
 "PredefinedMetricSpecification": {
   "PredefinedMetricType":
     "LambdaProvisionedConcurrencyUtilization"}}

The dimension name and the long option name can't be split. Target tracking reacts within minutes, so for a predictable daily peak add a scheduled action that raises the minimum before lunch. ProvisionedConcurrencySpilloverInvocations counts requests that overflowed to on-demand environments (and possibly cold starts): if it's often above zero, provision more.

Scaling instances and containers

EC2 Auto ScalingTarget tracking (recommended) keeps a metric near a target, such as average CPU at 50% or ALBRequestCountPerTarget at 1,000. Step scaling adds capacity in steps by alarm size; scheduled scaling changes capacity at known times; predictive scaling forecasts daily and weekly patterns and scales ahead of them. Set a default instance warmup so new instances' metrics don't trigger more scaling before they're ready, use a health check grace period for slow starts, and keep pre-initialized instances in a warm pool for applications that take minutes to boot.

ECS Service Auto ScalingScales the service's task count with target tracking on CPU, memory or requests per target, step, scheduled or predictive scaling (since November 2024); target tracking on CPU and memory can use 20-second metrics (2026) for faster reaction.

DynamoDBOn-demand capacity scales by itself; provisioned tables can use auto scaling with a target utilization.

Thread pools and connection pools in code

Parallelism inside one process helps when work waits on I/O (calling several services at once), but unbounded parallelism exhausts connections and memory. Use a bounded pool of workers (Java ExecutorService, Python concurrent.futures, limited Promise batches in Node.js) and size the SDK's HTTP connection pool to match: botocore allows 10 connections per client by default, the Java and JavaScript SDKs 50.

Fetch several restaurant menus in parallel (Python) 
from concurrent.futures import (
    ThreadPoolExecutor)
from botocore.config import Config

s3 = boto3.client("s3", config=Config(
    max_pool_connections=20))

def fetch(key):
    obj = s3.get_object(Bucket=BUCKET,
                        Key=key)
    return obj["Body"].read()

pool = ThreadPoolExecutor(max_workers=20)
with pool:
    menus = list(pool.map(fetch, keys))

Twenty workers and twenty pooled connections: more workers than connections just wait for a free one.

Database connection pooling and RDS Proxy

Each Lambda environment holds its own database connection, so 400 concurrent functions mean 400 connections, and a burst can exceed the database's connection limit or memory. Open connections outside the handler so warm invocations reuse them, and put Amazon RDS Proxy in front of RDS or Aurora: it keeps a pool of database connections and lends one to each transaction (multiplexing), so thousands of clients share far fewer database connections. Clients can authenticate to the proxy with IAM while the proxy uses Secrets Manager credentials for the database, and failovers are faster because the proxy endpoint stays the same and requests wait instead of failing. Session-level changes (for example SET statements) pin a client to one connection and reduce the benefit.

Connect through RDS Proxy with IAM authentication (Python) 
import pymysql

rds = boto3.client("rds")
_conn = None

def db():
    global _conn
    if _conn is None or not _conn.open:
        token = rds.generate_db_auth_token(
            DBHostname=PROXY_ENDPOINT,
            Port=3306,
            DBUsername="orders")
        _conn = pymysql.connect(
            host=PROXY_ENDPOINT,
            port=3306,
            user="orders", password=token,
            database="orders",
            ssl={"ca": "/opt/rds-ca.pem"})
    return _conn

The connection is created once per environment and reused; the IAM token replaces a stored password. JavaScript SDK v3 and most SDKs keep HTTP connections alive by default, which saves a TLS handshake per AWS call.

"Database runs out of connections when Lambda scales" points to RDS Proxy (and reserved concurrency as a cap). "Cold starts hurt a latency-sensitive API" points to provisioned concurrency. "Traffic doubles every weekday at noon" points to scheduled or predictive scaling. "Requests wait although CPU is low" points to too few pooled connections or workers.

Memory and compute

Skill 4.3.2Optimize memory and compute power for an application.

Lambda

Lambda gives CPU in proportion to memory (one full vCPU at 1,769 MB), so memory is also the CPU and network setting. A CPU-bound function at 128 MB may run ten times faster at 1,024 MB for about the same cost, because cost is memory × duration. Find the best setting by measuring:

  • AWS Lambda Power Tuning, an open-source Step Functions state machine, runs a function at several memory sizes with a sample payload and charts speed and cost, choosing for cost, speed or a balance.
  • AWS Compute Optimizer (opt in) analyzes 14 days of metrics and flags functions whose memory is over- or under-provisioned.
  • The REPORT line's Max Memory Used shows how much is really used (Task 4.1).
Power Tuning input (state machine execution) 
{
  "lambdaARN": "ORDER_FUNCTION_ARN",
  "powerValues": [256, 512, 1024, 1769],
  "num": 50,
  "payload": {"orderId": "o-1042"},
  "strategy": "balanced"
}

It invokes the real function 50 times at each size, so use a test environment and a harmless payload.

ArchitectureSwitching to arm64 (Graviton) usually gives better price-performance for the same code, if native dependencies are available for it.

Cold startsSmaller packages, fewer and lighter dependencies, lazy initialization of rarely used clients, SnapStart, and provisioned concurrency. Since August 2025 init time is billed for zip functions on managed runtimes, so leaner init also saves money.

Containers and instances

FargateTask CPU and memory come in fixed combinations (for example 0.5 vCPU with 1 to 4 GB, 1 vCPU with 2 to 8 GB, up to 16 vCPU with 120 GB, and 32 vCPU since 2026). Size from Container Insights utilization, and let Compute Optimizer recommend task sizes for ECS on Fargate.

EC2Match the family to the work: compute optimized (C) for CPU-heavy work, memory optimized (R) for large caches and in-memory data, general purpose (M) for balanced loads, burstable (T) for mostly idle workloads that burst occasionally (watch CPU credits). Compute Optimizer recommends instance types and also finds idle resources.

"Function is CPU-bound and slow" points to more memory. "Find the cheapest memory setting" points to Lambda Power Tuning or Compute Optimizer. "Same code, better price-performance" points to arm64. "Instances are mostly idle but sometimes spike" points to burstable instances.

Messaging

Skill 4.3.3Optimize application messaging (for example, by using Amazon SQS queues, Amazon SNS fan-out patterns).

SQS

Long pollingA receive with WaitTimeSeconds above 0 (up to 20), or the queue's ReceiveMessageWaitTimeSeconds, waits for messages instead of returning empty at once, and queries all of the queue's servers. Fewer empty responses means fewer requests, lower cost and lower latency.

BatchingSendMessageBatch, DeleteMessageBatch and ChangeMessageVisibilityBatch handle up to 10 messages per call (1 MiB in total). SQS bills per request in 64 KB chunks, so batching small messages cuts requests by up to ten times.

Lambda consumersA larger batch size (up to 10,000 for standard queues) with a batching window (MaximumBatchingWindowInSeconds) means fewer, fuller invocations; partial batch responses avoid reprocessing successes. Set the queue's visibility timeout to at least six times the function timeout plus the batching window. Provisioned mode for the event source mapping (2025, raised in 2026 to 10,000 pollers) scales faster for spiky queues.

Throughput and fairnessHigh-throughput FIFO for ordered, high-volume queues; fair queues so one busy tenant can't delay the rest; large payloads in S3 with the Extended Client Library.

Batch send and long-poll receive (Python) 
entries = [{"Id": str(i),
            "MessageBody": json.dumps(t)}
           for i, t in enumerate(tickets)]
for i in range(0, len(entries), 10):
    sqs.send_message_batch(
        QueueUrl=KITCHEN_URL,
        Entries=entries[i:i + 10])

resp = sqs.receive_message(
    QueueUrl=KITCHEN_URL,
    MaxNumberOfMessages=10,
    WaitTimeSeconds=20)
done = []
for m in resp.get("Messages", []):
    if handle(m):
        done.append({
            "Id": m["MessageId"],
            "ReceiptHandle":
                m["ReceiptHandle"]})
if done:
    sqs.delete_message_batch(
        QueueUrl=KITCHEN_URL,
        Entries=done)

Check each batch response's Failed list: a batch call can succeed while some entries fail.

SNS fan-out

Publishing once to an SNS topic with one SQS queue per consumer gives each consumer its own buffer and pace. Make it efficient:

  • Filter policies on subscriptions (on message attributes or the body) so each queue gets only relevant messages: the loyalty service doesn't receive orders under a threshold. Unfiltered fan-out means every consumer pays to receive and discard.
  • Raw message delivery on SQS (and Firehose) subscriptions sends the message without the SNS JSON envelope, so it's smaller and consumers don't unwrap it.
  • Use SNS FIFO to fan out to SQS FIFO queues when order matters.
  • Choose EventBridge instead when routing needs richer content matching, many event types, or SaaS sources; choose Kinesis enhanced fan-out when several consumers each need the full stream with low latency (each gets its own 2 MB/s per shard, pushed).
Raw delivery and a filter on one subscription (AWS CLI) 
aws sns set-subscription-attributes \
  --subscription-arn LOYALTY_SUB_ARN \
  --attribute-name RawMessageDelivery \
  --attribute-value true

aws sns set-subscription-attributes \
  --subscription-arn LOYALTY_SUB_ARN \
  --attribute-name FilterPolicy \
  --attribute-value '{"total": [{"numeric": [">=", 30]}]}'

The filter policy is one JSON value; it matches a numeric total message attribute of 30 or more.

"Many empty receives, high SQS cost" points to long polling. "Too many API calls for small messages" points to batching. "Consumers receive and discard most messages" points to subscription filter policies. "Consumer has to parse an SNS envelope" points to raw message delivery.

Caching

Skill 4.3.4Implement caching by using AWS services (for example, Amazon ElastiCache, Amazon DynamoDB Accelerator [DAX], Amazon CloudFront).

Choosing a cache and a strategy is covered in Task 1.3; this section is about wiring them in and getting a good hit ratio.

ElastiCache

Connect to the right endpoint: with cluster mode disabled, the primary endpoint for writes and the reader endpoint to spread reads across replicas; with cluster mode enabled, the configuration endpoint with a cluster-aware client; for ElastiCache Serverless, its single endpoint. Use TLS, create the client outside the handler, and set TTLs on every key. Watch CacheHitRate (or hits and misses), Evictions (memory too small for the working set) and EngineCPUUtilization.

DAX

For DynamoDB, DAX is close to a drop-in change: swap the client for the DAX client pointed at the cluster endpoint, and reads served from cache return in microseconds. Writes go through to DynamoDB and update the item cache; query results are cached separately until their TTL expires. Strongly consistent reads always go to DynamoDB.

Read menus through DAX (Python) 
import amazondax

dax = amazondax.AmazonDaxClient.resource(
    endpoint_url=DAX_ENDPOINT,
    region_name="us-east-1")
menus = dax.Table("menus")

item = menus.get_item(
    Key={"restaurantId": "r-42"})["Item"]

The table object has the same methods as a boto3 DynamoDB table, so the rest of the code doesn't change. DAX metrics such as ItemCacheHits and QueryCacheHits show whether the cache is working.

CloudFront

CloudFront caches responses at edge locations close to users. The cache policy decides the cache key and TTLs. The managed CachingOptimized policy leaves query strings, cookies and most headers out of the key and caches for a day by default, which suits static assets; CachingDisabled suits personalized API responses. To raise the hit ratio:

  • Include in the cache key only what changes the response (forward the lang query string, not every tracking parameter). Values the origin needs but that don't change the response go in an origin request policy instead.
  • Send long Cache-Control: max-age headers for content that rarely changes, and use versioned file names (app.3f2a.js) so new releases don't need invalidations. Invalidations are free for the first 1,000 paths a month.
  • Add Origin Shield as a central caching layer to reduce load on the origin.
  • Use CloudFront Functions (lightweight, at viewer request and response) to normalize cache keys or rewrite URLs; Lambda@Edge when you need network access, the request body or origin events.

API Gateway and in-function caches

A REST API stage cache stores responses per method, keyed by the parameters you select (--cache-key-parameters method.request.querystring.lang); watch CacheHitCount and CacheMissCount, and flush with flush-stage-cache after a data change. Inside Lambda, values kept in a variable outside the handler (configuration, a small reference table) survive between warm invocations for free.

A low hit ratio usually means the cache key is too detailed: forwarding all headers or cookies makes every request unique. A sudden expiry of many popular keys can send a burst of misses to the database at once; stagger TTLs and refresh hot keys before they expire.

Finding bottlenecks

Skill 4.3.5Detect performance bottlenecks by using AWS services (for example, Amazon CloudWatch).

ToolShows
CloudWatch metrics and dashboardsLatency percentiles, throttles, queue age, capacity use per component, side by side
X-Ray traces and Application SignalsWhich service or downstream call takes the time in a request; service maps, latency and error rates per operation, SLOs
Lambda InsightsPer-function CPU, memory, network and cold start details
Container InsightsCPU, memory and network per cluster, service, task and container on ECS and EKS (enhanced observability since 2024)
Contributor InsightsTop contributors in log data, such as the IP addresses or customers sending most requests; for DynamoDB, the most accessed and most throttled keys (hot partitions)
CloudWatch Database InsightsDatabase load by wait event, SQL statement and host for RDS and Aurora; it replaces Performance Insights, which reached end of life on July 31, 2026
Amazon CodeGuru ProfilerWhich methods in running Java and Python code use the most CPU and memory (flame graphs); it has no new features since 2022
  1. Find the slow requestsDashboards show the API's p99 latency rising at lunchtime.
  2. Find the slow componentTraces show most of the time is in the order function's database call.
  3. Find the causeDatabase Insights shows one query waiting on locks, and Lambda concurrency shows 400 environments competing for connections.
  4. Fix and measureAdd an index, put RDS Proxy in front, cache menus; compare the same metrics after the change.
Slowest operations by p95 from structured logs (Logs Insights) 
filter ispresent(operation)
| stats pct(durationMs, 95) as p95,
    count(*) as calls by operation
| sort p95 desc
| limit 10

This assumes the code logs operation and durationMs fields for each step (Task 4.2).

"Which part of the request is slow" points to traces. "Which DynamoDB key is hot" points to Contributor Insights for DynamoDB. "Which SQL statements load the database" points to Database Insights. "Which code paths use the most CPU" points to a profiler such as CodeGuru Profiler.

Key takeaways

  • Concurrency is RPS × duration. Provisioned concurrency (scaled by schedule or target tracking) removes cold starts; reserved concurrency caps and guarantees; SnapStart speeds init. EC2 and ECS scale with target tracking, step, scheduled or predictive policies, warmup and warm pools.
  • Bound parallelism with worker pools sized to the SDK connection pool; reuse clients and database connections; RDS Proxy pools and multiplexes connections for Lambda, with IAM auth and faster failover (avoid pinning).
  • Memory is CPU in Lambda: tune with Power Tuning or Compute Optimizer, try arm64, trim cold starts. Size Fargate tasks and EC2 families from utilization.
  • Messaging: long polling, batching (10 per call, 64 KB billing chunks), bigger Lambda batches with windows, filter policies and raw delivery for SNS fan-out, EventBridge or Kinesis enhanced fan-out when they fit better.
  • Caching: the right ElastiCache endpoint and TTLs; DAX as a client swap for DynamoDB reads; CloudFront cache policies with minimal cache keys, long TTLs, versioned files and Origin Shield; API Gateway cache keys; watch hit ratios and evictions.
  • Bottlenecks: dashboards and percentiles, traces and Application Signals, Lambda and Container Insights, Contributor Insights for hot keys, Database Insights (replacing Performance Insights), profilers.
  • AI: Compute Optimizer and Cost Optimization Hub, Q Developer cost questions, Kiro for code efficiency, investigations and DevOps Agent for bottlenecks; always measure the result.
