Task 2.1: Implement authentication and authorization mechanisms for applications and AWS services

Overview

Task 2.1

Implement authentication and authorization mechanisms for applications and AWS services.

Two kinds of identity meet in an AWS application. End users sign in to the application (customers ordering food), usually through Amazon Cognito or another identity provider. Principals in AWS (roles, users, services) call AWS APIs, and IAM decides each call. The skills in this task connect the two: verify users, turn identities into short-lived AWS credentials, and write the policies that limit what each can do.

The examples follow the food-ordering application from earlier tasks: customers sign in with Cognito, the mobile app uploads profile photos directly to S3, the order API runs on Lambda behind API Gateway, and a delivery partner's system calls an API in account 111111111111 from its own AWS account.

Identity federation

Skill 2.1.1Implement identity federation.

Federation means trusting an identity proven somewhere else instead of creating an IAM user for every person or system. A user signs in with an identity provider (IdP); the application or AWS trusts the token the IdP issues.

Amazon Cognito user pools

A user pool is a user directory and OAuth 2.0 / OpenID Connect provider for your application. It handles sign-up, sign-in, password reset, MFA, and sign-in through social providers (Google, Apple, Facebook, Amazon) or enterprise IdPs over SAML or OIDC. After sign-in, it issues three JSON Web Tokens (JWTs):

TokenContainsUse it to
ID tokenWho the user is: sub, email, name, cognito:groupsPersonalize the app; authorize with an API Gateway Cognito authorizer
Access tokenWhat the user may access: scopes, groups, client_idCall your APIs (scopes) and user pool APIs
Refresh tokenAn opaque tokenGet new ID and access tokens without signing in again

ID and access tokens last between 5 minutes and 1 day; refresh tokens between 60 minutes and 10 years (30 days by default). Refresh token rotation (2025) issues a new refresh token on each use. App clients for browsers and mobile apps are public clients with no secret and should use the authorization code grant with PKCE; server-side clients are confidential with a client secret. Service-to-service (machine-to-machine) access uses the client credentials grant, which needs a secret.

Feature plans

Since November 2024, user pools have three plans: Lite, Essentials (the default for new pools: managed login pages, passwordless sign-in with passkeys or one-time codes, email MFA, access token customization) and Plus (adds threat protection: compromised-credential and risky sign-in detection, formerly "advanced security features").

Lambda triggers

Functions customize the flow: pre sign-up (validate or auto-confirm users), post confirmation (create the customer record), pre token generation (add or remove claims), custom authentication challenges, custom message, and user migration (move users from an old system at their first sign-in). Cognito waits at most 5 seconds for a trigger.

Verifying tokens

An API that receives a Cognito token must verify it, not just decode it: check the signature against the user pool's public keys (the JWKS at https://cognito-idp.REGION.amazonaws.com/POOL_ID/.well-known/jwks.json), then the issuer, the audience or client ID, token_use and the expiry. API Gateway does this for you with a Cognito user pool authorizer (REST APIs) or a JWT authorizer (HTTP APIs). In code, use a library such as aws-jwt-verify:

Verify an access token (TypeScript) 
import { CognitoJwtVerifier }
  from "aws-jwt-verify";

const verifier =
  CognitoJwtVerifier.create({
    userPoolId: USER_POOL_ID,
    tokenUse: "access",
    clientId: CLIENT_ID,
  });

const claims = await verifier.verify(
  token);
const groups = claims["cognito:groups"];

Amazon Cognito identity pools

When the app itself must call AWS services (upload to S3, read a DynamoDB item), an identity pool exchanges a token from a user pool, a social provider, or a SAML or OIDC provider for temporary AWS credentials from STS. Each pool has an authenticated role and optionally an unauthenticated (guest) role, and can choose roles by rules on token claims or by the user pool group's role. Each user gets an identity ID usable in policies as ${cognito-identity.amazonaws.com:sub}.

  1. Sign inThe user signs in to the user pool and the app gets an ID token.
  2. Get an identityThe app calls GetId with the token and receives an identity ID.
  3. Get credentialsGetCredentialsForIdentity returns temporary credentials for the role Cognito chose.
  4. Call AWSThe app uses the credentials with the SDK; the role's policy limits it to the user's own data.

Federation into IAM roles

OIDC providersRegister an OIDC identity provider in IAM and let tokens from it assume a role with AssumeRoleWithWebIdentity. GitHub Actions deploying to AWS is the typical case: the trust policy must check the token's sub claim (repository and branch), which IAM enforces for GitHub since 2025.

SAML providersCorporate IdPs sign users in to the console or CLI with AssumeRoleWithSAML.

IAM Identity CenterWorkforce single sign-on to many accounts with permission sets; developers configure the CLI with aws configure sso and sign in with aws sso login.

Kubernetes on EKSEKS Pod Identity (or the older IAM roles for service accounts) gives each pod its own role.

"Users sign up and sign in to the app" points to a Cognito user pool. "Mobile users need temporary credentials to upload to S3 directly" points to a Cognito identity pool. "Sign in with Google or a corporate SAML IdP" points to a user pool with federated IdPs. "CI/CD from GitHub without stored keys" points to an IAM OIDC provider and AssumeRoleWithWebIdentity.

Access control

Skill 2.1.2Implement access control (for example, fine-grained permissions, security tokens, MFA).

How IAM decides

  1. Default denyEvery request starts denied.
  2. Explicit deny winsA Deny in any applicable policy (identity, resource, permissions boundary, SCP, RCP, session policy) ends the evaluation.
  3. Allow neededOtherwise an Allow must exist, and every limiting policy that applies (boundary, SCP, RCP, session policy) must also allow the action.
  4. Cross-accountA principal in another account needs both: its own identity policy must allow the action, and the resource's policy must allow that principal.
Policy typeAttached toRole in evaluation
Identity-based (managed or inline)A user, group or roleGrants permissions
Resource-basedA resource: S3 bucket, SQS queue, SNS topic, KMS key, Lambda function, role trust policyGrants access to named principals, including other accounts
Permissions boundaryA user or roleCaps what identity policies can grant
Service control policy (SCP)Accounts in AWS OrganizationsCaps what principals in the accounts can do
Resource control policy (RCP)Accounts in AWS Organizations (since November 2024)Caps what can be done to resources in the accounts
Session policyAn assumed-role or federated sessionNarrows that session's permissions

Fine-grained permissions

Narrow policies with specific actions, resource ARNs and conditions. Policy variables such as ${aws:username}, ${aws:PrincipalTag/team} or ${cognito-identity.amazonaws.com:sub} make one policy give each caller access to only their own data. For DynamoDB, the dynamodb:LeadingKeys condition restricts access to items whose partition key equals the caller's ID:

Each customer reads and writes only their own items (IAM policy) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "dynamodb:GetItem",
      "dynamodb:Query",
      "dynamodb:PutItem"],
    "Resource": "CARTS_TABLE_ARN",
    "Condition": {
      "ForAllValues:StringEquals": {
        "dynamodb:LeadingKeys": [
          "${cognito-identity.amazonaws.com:sub}"]
      }
    }
  }]
}

Attached to the identity pool's authenticated role (a placeholder stands for the table ARN; the variable can't be split). Policy variables need the 2012-10-17 policy version. The same idea in S3 uses a resource ARN like bucket/users/${cognito-identity.amazonaws.com:sub}/*.

Condition keyUse
aws:MultiFactorAuthPresent, aws:MultiFactorAuthAgeRequire recent MFA for sensitive actions
aws:SourceIp, aws:SourceVpce, aws:SourceVpcAllow only from known networks or VPC endpoints
aws:SecureTransportDeny requests not made over HTTPS
aws:PrincipalTag, aws:ResourceTagAttribute-based access control (ABAC): match the caller's tags to the resource's
aws:RequestedRegionLimit actions to approved Regions

Security tokens and MFA

Temporary credentials from STS (an access key ID, secret key and session token) are the norm: they expire on their own, so a leak does limited damage. To require MFA for CLI or API use, a policy denies actions unless aws:MultiFactorAuthPresent is true, and the user gets MFA-backed credentials with GetSessionToken (or AssumeRole) passing the MFA device's serial number and a current code.

Get MFA-backed credentials (AWS CLI) 
aws sts get-session-token \
  --serial-number MFA_DEVICE_ARN \
  --token-code 123456 \
  --duration-seconds 3600

For IAM users these sessions last 15 minutes to 36 hours (12 hours by default). aws:MultiFactorAuthPresent only exists in requests made with temporary credentials, so policies usually use BoolIfExists in a deny statement to also catch long-term keys.

Authorizing API calls

API Gateway optionUse it when
IAM authorizationCallers are AWS principals (other services, partner accounts) signing requests with SigV4
Cognito user pool authorizer (REST) or JWT authorizer (HTTP)Callers are signed-in users with Cognito (or other OIDC) tokens
Lambda authorizerCustom logic: third-party tokens, headers, IP checks. REQUEST type (recommended) sees headers, query strings and context; TOKEN type sees one header. It returns an IAM policy, cached 300 seconds by default (up to 3,600)
Resource policyRestrict a REST API to accounts, IP ranges or VPC endpoints

API keys and usage plans meter and throttle clients; they don't authenticate them. AWS says not to use API keys for authentication or authorization. Also, a Lambda authorizer's cached policy applies to every request with the same identity source for the cache period, so a policy that allows only one path can block others.

"Each user may access only their own items" points to policy variables and dynamodb:LeadingKeys or a per-user S3 prefix. "Require MFA for deleting resources" points to an aws:MultiFactorAuthPresent condition. "Validate a third-party bearer token at the API" points to a Lambda authorizer. "Find unused or overly broad permissions" points to IAM Access Analyzer.

Programmatic access

Skill 2.1.3Configure programmatic access to AWS.

Programmatic access means credentials for the CLI, SDKs and tools. The rule is the same everywhere: prefer temporary credentials that are issued and rotated for you, and keep long-term access keys for the rare case nothing else works. The SDKs find credentials through their provider chain (Task 1.1), so the code doesn't change between a laptop and production.

Where the code runsHow it gets credentials
Developer laptopaws login (since November 2025, CLI 2.32 and later) turns a console sign-in into temporary credentials for the CLI and SDKs, refreshed automatically; or IAM Identity Center with aws configure sso and aws sso login
EC2 instanceAn instance profile role, read from the instance metadata service; require IMDSv2 (session tokens)
ECS taskThe task role for the application's calls; the separate task execution role lets ECS pull the image, write logs and fetch secrets
Lambda functionThe execution role, delivered as environment variables
CI/CD outside AWSOIDC federation (GitHub Actions and others) to assume a role
Servers outside AWSIAM Roles Anywhere: X.509 certificates from your certificate authority exchanged for role credentials
~/.aws/config with Identity Center and a role profile 
[sso-session company]
sso_start_url = https://example.awsapps.com/start
sso_region = us-east-1
sso_registration_scopes = sso:account:access

[profile dev]
sso_session = company
sso_account_id = 111111111111
sso_role_name = Developer
region = us-east-1

[profile partner-admin]
role_arn = arn:aws:iam::222222222222:role/OrdersAdmin
source_profile = dev
mfa_serial = MFA_DEVICE_ARN

The start URL and ARNs are unsplittable values. aws s3 ls --profile dev uses Identity Center credentials; --profile partner-admin makes the CLI assume the role with the dev credentials, prompting for an MFA code.

If you must use access keysAn IAM user can have two access keys, which allows rotation: create the second key, switch the application to it, deactivate the first, then delete it. Never commit keys; never use root user keys (AWS Organizations can now remove root credentials from member accounts centrally).

"Configure the EC2 instance with an access key in a config file" is the wrong answer when an instance profile role is possible. Likewise in ECS, application permissions belong in the task role, not the task execution role.

Presigned URLs

Skill 2.1.4Use presigned URLs to provide secure, time-limited access (for example, by using Amazon S3 and Amazon CloudFront).

S3 presigned URLs

A presigned URL lets someone without AWS credentials perform one specific S3 operation (download or upload one object) until it expires. Your code signs the URL with its own credentials, so the request is allowed only if the signer is allowed to do it. The URL is a bearer token: anyone who has it can use it until it expires.

  • Expiry is up to 7 days when signed with an IAM user's long-term credentials. With temporary credentials (a Lambda or ECS role), the URL stops working when those credentials expire, whatever expiry you asked for.
  • Bucket policies can restrict presigned access further, for example by signature age (s3:signatureAge) or source IP.
  • A presigned PUT overwrites an object that already has that key; generate unique keys.
Let the app upload a photo and later show it (Python) 
s3 = boto3.client("s3")
key = (f"photos/{customer_id}/"
       f"{uuid4()}.jpg")

upload_url = s3.generate_presigned_url(
    "put_object",
    Params={"Bucket": BUCKET, "Key": key,
            "ContentType": "image/jpeg"},
    ExpiresIn=300,
)
view_url = s3.generate_presigned_url(
    "get_object",
    Params={"Bucket": BUCKET, "Key": key},
    ExpiresIn=3600,
)

The app sends the photo with an HTTP PUT to upload_url using the same content type; the bytes never pass through Lambda or API Gateway, which avoids their payload limits. For browser form uploads with conditions (maximum size, key prefix), use a presigned POST (generate_presigned_post). From a shell, aws s3 presign s3://bucket/key --expires-in 600 creates a download URL.

CloudFront signed URLs and signed cookies

For private content delivered through CloudFront, CloudFront itself checks a signature made with a key from a trusted key group (public keys you upload; the legacy CloudFront key pairs require the root user and are discouraged).

OptionUse it for
Signed URL, canned policyOne file with an expiry time; shorter URL
Signed URL, custom policyAdds a start time, an IP range, and wildcards in the resource path so one signature covers several files
Signed cookiesMany files without changing URLs (a members' video library, streaming segments); the browser sends the cookies with every request

Keep the S3 bucket itself private with origin access control (OAC): the bucket policy allows only the CloudFront service principal, for your distribution's ARN, so users can't bypass CloudFront and its signature checks. OAC replaces the older origin access identity.

"Let users upload directly to S3 without AWS credentials" or "download a private object for a limited time" points to S3 presigned URLs. "Restrict premium content served by CloudFront" points to CloudFront signed URLs (one file) or signed cookies (many files). "The presigned URL stops working after an hour although it was created for a day" points to temporary credentials expiring.

Authenticated calls

Skill 2.1.5Make authenticated calls to AWS services.

AWS APIs authenticate each request with Signature Version 4 (SigV4). The secret key never travels; instead the client proves it holds the key by signing the request, and AWS recomputes the signature.

  1. Canonical requestThe method, path, sorted query string, signed headers and a hash of the body, in a fixed format.
  2. String to signThe algorithm (AWS4-HMAC-SHA256), the timestamp, the scope (date, Region, service) and a hash of the canonical request.
  3. Signing keyDerived from the secret key by chaining HMACs over the date, Region, service and aws4_request, so it's valid for one day, Region and service.
  4. SignatureSent in the Authorization header, or in the query string for presigned URLs. Temporary credentials add the session token (X-Amz-Security-Token).

The SDKs and CLI do all of this. You sign by hand only when calling an AWS-authenticated HTTP endpoint without an SDK client for it, such as an API Gateway API with IAM authorization or a Lambda function URL with AWS_IAM auth; the SDKs' signer classes help there. SigV4a produces signatures valid in several Regions (needed for S3 Multi-Region Access Points).

Call an IAM-authorized API Gateway endpoint (Python) 
import requests
from botocore.auth import SigV4Auth
from botocore.awsrequest import AWSRequest

creds = boto3.Session().get_credentials()
req = AWSRequest(method="GET", url=URL)
SigV4Auth(creds, "execute-api",
          "us-east-1").add_auth(req)
resp = requests.get(
    URL, headers=dict(req.headers))
ErrorUsual cause
SignatureDoesNotMatchWrong secret key, wrong Region or service in the scope, or the request changed after signing
RequestExpired or a clock skew errorThe client clock is more than 15 minutes off, or a presigned URL expired
ExpiredTokenThe temporary credentials' session ended; get new ones
AccessDeniedAuthenticated, but no policy allows the action (an authorization problem, not a signing one)

Permissions for principals and resources

Skill 2.1.6Define permissions for IAM principals (for example, users, roles, services) and resources.

Principals

IAM users and groupsLong-term identities for people or legacy systems; attach permissions to groups. Prefer federation for people.

RolesIdentities with no long-term credentials, assumed by users, applications, services or other accounts. A role has a trust policy (who may assume it) and permissions policies (what it may do).

Service roles and service-linked rolesA service role is one you create for a service to assume (a Lambda execution role, a CodeBuild role). A service-linked role is created and managed by the service itself, with permissions it defines.

Service principalsNames such as lambda.amazonaws.com or events.amazonaws.com used in trust and resource policies.

Writing least-privilege policies

Grant only the actions and resources the code uses, start from AWS managed policies only for prototypes, and move to customer managed policies scoped to your resources. Validate policies with IAM Access Analyzer, and use its unused-access findings and policy generation (from CloudTrail activity) to tighten them.

The order function's execution role permissions (IAM policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow",
     "Action": ["dynamodb:PutItem",
                "dynamodb:UpdateItem"],
     "Resource": "ORDERS_TABLE_ARN"},
    {"Effect": "Allow",
     "Action": "sqs:SendMessage",
     "Resource": "KITCHEN_QUEUE_ARN"},
    {"Effect": "Allow",
     "Action":
       "secretsmanager:GetSecretValue",
     "Resource": "PAYMENT_SECRET_ARN"}
  ]
}

Placeholders stand for the ARNs. The function can write orders, queue kitchen work and read one secret, nothing else.

Resource-based policies

Some resources carry their own policy naming who may use them: S3 bucket policies, SQS queue policies, SNS topic policies, KMS key policies, Lambda resource policies, API Gateway resource policies, Secrets Manager secret policies. They're how you grant access to another account or an AWS service without a role. When a service is the principal, add aws:SourceArn or aws:SourceAccount conditions so only your resource can use the permission (the confused deputy protection).

Let one SNS topic send to the queue (SQS queue policy) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "sns.amazonaws.com"},
    "Action": "sqs:SendMessage",
    "Resource": "KITCHEN_QUEUE_ARN",
    "Condition": {"ArnEquals": {
      "aws:SourceArn":
        "ORDERS_TOPIC_ARN"}}
  }]
}

Passing roles

When you create a Lambda function, an ECS task or an EC2 instance with a role, you pass the role to the service, which needs iam:PassRole on that role. Limit it to specific roles and use the iam:PassedToService condition, or a developer could pass an administrator role to a resource they control.

"Another account must write to our bucket" points to a bucket policy naming that account (plus permissions in that account). "S3 must invoke our function" points to a Lambda resource policy with aws:SourceArn. "Developer can't create the function with the role" points to missing iam:PassRole. "Limit what developers can grant themselves" points to permissions boundaries.

Assuming a role

Skill 2.1.7Assume an IAM role.

Assuming a role exchanges your current credentials for the role's temporary credentials. Two policies must agree: the role's trust policy must allow your principal to call sts:AssumeRole, and your own permissions must allow sts:AssumeRole on that role (for cross-account roles).

Trust policy for a delivery partner's account (IAM role) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS":
        "arn:aws:iam::222222222222:root"},
    "Action": "sts:AssumeRole",
    "Condition": {"StringEquals": {
      "sts:ExternalId": "partner-7f3a"}}
  }]
}

The root principal means the whole partner account, which then decides which of its roles may assume this one. The external ID protects against a confused deputy when a third party assumes roles for many customers.

Assume the role and use its credentials (Python) 
sts = boto3.client("sts")
resp = sts.assume_role(
    RoleArn=ROLE_ARN,
    RoleSessionName="partner-sync",
    ExternalId="partner-7f3a",
    DurationSeconds=3600,
)
c = resp["Credentials"]
ddb = boto3.client(
    "dynamodb",
    aws_access_key_id=c["AccessKeyId"],
    aws_secret_access_key=c[
        "SecretAccessKey"],
    aws_session_token=c["SessionToken"],
)
ParameterMeaning
RoleSessionNameAppears in the assumed-role ARN and CloudTrail; identifies who did what
DurationSeconds15 minutes up to the role's maximum session duration (1 to 12 hours; 1 hour by default). Role chaining (assuming a role from a role session) is limited to 1 hour
ExternalIdA shared value the trust policy requires, for third parties
Policy, PolicyArnsSession policies that narrow the session's permissions
TagsSession tags for ABAC (the trust policy must allow sts:TagSession)
SerialNumber, TokenCodeMFA, when the trust policy requires it

Check which identity the code is using with aws sts get-caller-identity. Use Regional STS endpoints (the SDK default), which keep working if another Region has problems.

"Access resources in another account without sharing keys" points to a cross-account role. "A third-party SaaS needs access to our account" points to a role with an external ID. "Credentials expire after an hour although the role allows 12" points to role chaining. "Find out which role a script runs as" points to get-caller-identity.

Key takeaways

  • Cognito user pools sign users in and issue ID, access and refresh tokens (Lite, Essentials, Plus plans; Lambda triggers); verify JWTs or use API Gateway authorizers. Identity pools exchange tokens for temporary AWS credentials with authenticated and guest roles. OIDC and SAML providers federate into IAM roles.
  • IAM: default deny, explicit deny wins, cross-account needs both sides. Fine-grained access with conditions and policy variables (dynamodb:LeadingKeys, per-user S3 prefixes); MFA with aws:MultiFactorAuthPresent and GetSessionToken.
  • Programmatic access: roles on AWS compute (instance profile, ECS task role, Lambda execution role), aws login or Identity Center locally, OIDC for CI, Roles Anywhere off AWS; access keys only as a last resort, rotated.
  • S3 presigned URLs grant one operation on one object until expiry (up to 7 days, limited by the signer's credentials); CloudFront signed URLs or cookies with trusted key groups, and OAC to keep the bucket private.
  • SigV4 signs every request; the SDKs do it. Know the errors: signature mismatch, clock skew, expired token, access denied.
  • Least-privilege identity policies, resource policies for cross-account and service access with aws:SourceArn, iam:PassRole limited to specific roles.
  • Assume roles with AssumeRole: trust policy plus caller permission, session name, duration (1 hour default, chaining capped at 1 hour), external ID for third parties, session policies and tags.
