Overview

Task 2.3

Identify and mitigate security risks associated with using and integrating AI services into application development.

An AI feature adds risks a normal API doesn't have. Users can type instructions that try to override yours (prompt injection). Models can return harmful, off-topic or invented content, or repeat personal data. Agents take actions with real permissions. And prompts and responses, full of customer data, can end up in logs. The developer's job is to apply the controls AWS provides at each point; designing safety frameworks and governance programs is out of scope for this exam.

The examples follow the food-ordering application: a support assistant built on Amazon Bedrock that answers questions about orders, and an agent on Amazon Bedrock AgentCore that can look up orders and issue refunds through tools. Deeper treatment of guardrails, agents and AI monitoring is in the Generative AI Developer guide.

Access to AI services

Skill 2.3.1Request and manage access to AI services.

Model access in Amazon Bedrock

Since October 2025, Bedrock's serverless models are available in commercial Regions without a separate access request; access is controlled with IAM and service control policies. The first time a third-party model is used in an account, Bedrock subscribes to it in AWS Marketplace in the background, which needs:

  • Marketplace permissions for the first caller (aws-marketplace:Subscribe, aws-marketplace:Unsubscribe, aws-marketplace:ViewSubscriptions) and a valid payment method;
  • for Anthropic models, a one-time use-case form (which a management account can submit for the whole organization).

If a prerequisite is missing, later calls fail with AccessDeniedException. To stop a model being used, deny bedrock:InvokeModel on it in IAM or an SCP; denying the Marketplace permission alone doesn't block the first call.

IAM permissions for model calls

  • Converse and InvokeModel need bedrock:InvokeModel; the streaming forms need bedrock:InvokeModelWithResponseStream. There is no separate Converse action.
  • Foundation model ARNs have no account ID: arn:aws:bedrock:REGION::foundation-model/MODEL_ID.
  • Calling through a cross-Region inference profile needs permission on the profile and on the model in every Region the profile can route to.
  • Condition keys tighten this: bedrock:InferenceProfileArn forces calls through a profile, and bedrock:GuardrailIdentifier requires a specific guardrail (below).
The assistant may call one model through one profile (IAM policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow",
     "Action": [
       "bedrock:InvokeModel",
       "bedrock:InvokeModelWithResponseStream"],
     "Resource": "INFERENCE_PROFILE_ARN"},
    {"Effect": "Allow",
     "Action": [
       "bedrock:InvokeModel",
       "bedrock:InvokeModelWithResponseStream"],
     "Resource": "arn:aws:bedrock:*::foundation-model/MODEL_ID",
     "Condition": {"StringEquals": {
       "bedrock:InferenceProfileArn":
         "INFERENCE_PROFILE_ARN"}}}
  ]
}

The action name and the model ARN pattern can't be split. The second statement allows the model in any Region, but only when the request comes through that profile.

Bedrock API keys

Since July 2025, Bedrock also accepts API keys as bearer tokens (the AWS_BEARER_TOKEN_BEDROCK environment variable or an Authorization: Bearer header), for tools that can't sign SigV4 requests. Short-term keys last up to 12 hours, carry the creating identity's permissions, and are the recommended kind. Long-term keys are tied to an IAM user and are meant only for exploration. Administrators can block API keys by denying bedrock:CallWithBearerToken. Treat them like passwords: never commit them.

Other access controls

AgentCore RuntimeInvoking an agent needs bedrock-agentcore:InvokeAgentRuntime. Each runtime accepts either IAM (SigV4) callers (the default) or OAuth/JWT tokens from your identity provider, for example Cognito, configured as an inbound authorizer with allowed clients and audiences.

QuotasBedrock limits tokens and requests per minute per model and Region; throttled calls return ThrottlingException. Request increases through Service Quotas, and retry with backoff.

Amazon QuickAdministrators restrict which AI capabilities users get with permission profiles.

"Restrict developers to approved models" points to IAM or SCP deny on bedrock:InvokeModel for other model ARNs. "AccessDenied on first use of a third-party model" points to missing Marketplace permissions or the Anthropic use-case form. "A tool can only send a bearer token" points to a short-term Bedrock API key.

Data privacy

Skill 2.3.2Use data privacy controls to transmit data to AI services (for example, by using VPC endpoints to establish private connectivity, ensuring that inputs and outputs are not used to train AI models).

What happens to the data

AWS states that it and the model providers will not use inputs to or outputs from Amazon Bedrock to train Amazon or third-party models, and providers have no access to customers' prompts, completions or logs. Data is encrypted in transit and at rest in the Region you use. Fine-tuning creates a private copy of the model for your account.

Cross-Region inferenceInference profiles route requests to other Regions for capacity. Geographic profiles (US, EU, APAC) keep processing inside that geography; global profiles can use any commercial Region. Traffic stays on the AWS network, and CloudTrail records where each request ran. If data must stay in one Region, use the Regional model ID; if it must stay in a geography, use a geographic profile.

Other AI servicesSome AWS AI services (for example Comprehend, Transcribe, Translate, Textract, Lex, Polly, Rekognition, Q Developer and Quick) may store and use content to improve the service unless you opt out; an AI services opt-out policy in AWS Organizations opts out every account at once. Bedrock isn't on that list because it doesn't use content that way.

KiroFree and individual users can turn off content collection and telemetry in the settings; enterprise accounts are opted out of content use automatically.

Opt the whole organization out (AI services opt-out policy) 
{"services": {
  "default": {
    "opt_out_policy": {
      "@@assign": "optOut"}}}}

Private connectivity

Application code in private subnets reaches AI services through interface VPC endpoints (AWS PrivateLink) instead of the internet or a NAT gateway: bedrock-runtime for model calls, bedrock-agent-runtime for knowledge bases and classic agents, bedrock-mantle for the OpenAI-compatible endpoint, bedrock for control-plane calls, and bedrock-agentcore (plus bedrock-agentcore.gateway) for AgentCore. With private DNS enabled, the SDK's default endpoints resolve to the VPC endpoint with no code change.

An endpoint policy limits what can be done through the endpoint, for example only bedrock:InvokeModel on approved models, by approved roles. In IAM policies, aws:SourceVpce conditions can require that calls arrive through the endpoint.

Endpoint policy: only model calls by the assistant's role 
{
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "ASSISTANT_ROLE_ARN"},
    "Action": [
      "bedrock:InvokeModel",
      "bedrock:InvokeModelWithResponseStream"],
    "Resource": "*"
  }]
}

"Calls to Bedrock must not traverse the internet" points to an interface VPC endpoint for bedrock-runtime with private DNS. "Are our prompts used to train the model?" points to Bedrock's commitment that they aren't. "Stop other AI services from storing our content" points to an AI services opt-out policy. "Data must stay in the EU" points to EU Regions or an EU geographic inference profile, not a global one.

Filtering inputs and outputs

Skill 2.3.3Filter and control AI model inputs and outputs (for example, by applying content filtering, sensitive information detection, PII/PHI redaction, denied topic policies, prompt injection and manipulation protection).

Amazon Bedrock Guardrails

A guardrail is a reusable set of policies that checks user input before it reaches a model and model output before it reaches the user. When a policy is violated, the guardrail blocks the content (returning your configured message) or masks parts of it.

PolicyCatches
Content filtersHate, insults, sexual content, violence and misconduct, in text and images, at a chosen strength separately for input and output
Prompt attack filterJailbreaks and prompt injection in user input ("ignore your instructions and…")
Denied topicsSubjects the application must not discuss, defined in plain language (for the support assistant: medical or legal advice)
Word filtersExact words and phrases, plus a managed profanity list
Sensitive information filtersPII types (names, emails, phone numbers, card numbers, addresses…) and custom regular expressions, blocked or masked (replaced with a label such as {EMAIL})
Contextual grounding checkAnswers not supported by the provided source text, or not relevant to the question
Automated Reasoning checksAnswers that contradict rules written as a formal policy

Guardrails come in two tiers: Classic (English, French and Spanish) and Standard (more languages, more robust detection, code; requires the guardrail to use cross-Region inference through a guardrail profile).

Applying a guardrail in code

With Converse, pass guardrailConfig. Wrap the user's text in a guardContent block so the guardrail knows what came from the user: once a request has any guardContent, only those blocks are checked as input, so your own instructions aren't mistaken for an attack.

Converse with a guardrail (Python) 
user = {"guardContent": {"text": {
    "text": customer_message}}}
guard = {
    "guardrailIdentifier": GUARDRAIL_ID,
    "guardrailVersion": "1",
    "trace": "enabled",
}
resp = brt.converse(
    modelId=PROFILE_ID,
    system=[{"text": SYSTEM_PROMPT}],
    messages=[{"role": "user",
               "content": [user]}],
    guardrailConfig=guard,
)
stop = resp["stopReason"]
if stop == "guardrail_intervened":
    log.info("blocked by guardrail")
reply = resp["output"]["message"]

When the guardrail blocks, stopReason is guardrail_intervened and the output contains the blocked-message text you configured; the trace says which policy acted.

ApplyGuardrail checks any text without calling a model: user input before it goes to a self-hosted model, a tool's result before it goes back to the model, or text from a document. Set source to INPUT or OUTPUT; the response's action is GUARDRAIL_INTERVENED or NONE, with masked or replacement text in outputs.

Check a tool result before the model sees it (Python) 
chk = brt.apply_guardrail(
    guardrailIdentifier=GUARDRAIL_ID,
    guardrailVersion="1",
    source="INPUT",
    content=[{"text": {
        "text": tool_text}}],
)
blocked = "GUARDRAIL_INTERVENED"
if chk["action"] == blocked:
    tool_text = "[content removed]"

Requiring guardrails

An IAM policy can allow model calls only when a specific guardrail is attached, with the bedrock:GuardrailIdentifier condition (the guardrail ARN with its version). Since November 2025, administrators can also enforce guardrails for a whole account or organization, so every model call in it is checked regardless of what the code sends.

Deny model calls without the approved guardrail (policy statement) 
{
  "Effect": "Deny",
  "Action": [
    "bedrock:InvokeModel",
    "bedrock:InvokeModelWithResponseStream"],
  "Resource": "*",
  "Condition": {"StringNotEquals": {
    "bedrock:GuardrailIdentifier":
      "GUARDRAIL_ARN:1"}}
}

Defending against prompt injection

  • Separate instructions from data. Put your instructions in system, user text in the user message (wrapped in guardContent), and documents or tool output clearly marked as data.
  • Filter all untrusted text. Guardrails in Converse don't evaluate tool results or tool definitions, so text an agent fetches from a web page, email or document (indirect prompt injection) needs ApplyGuardrail on it. With InvokeModel, the prompt attack filter only checks text inside guard-content tags.
  • Limit the damage. Give the model's tools least-privilege permissions, validate tool arguments in code, and require approval for sensitive actions (below).
  • Check outputs too. Filter responses for PII and unsafe content before showing them, and never execute model output as code or queries without validation.

For PII and PHI outside Bedrock, Amazon Comprehend (DetectPiiEntities) and Comprehend Medical (DetectPHI) can find and redact them before text is sent to any model (Task 2.2).

A guardrail attached in Converse doesn't see tool results, and the prompt attack filter doesn't see untagged text. An agent that reads customer emails or web pages is exposed to indirect prompt injection unless that content is checked separately.

"Block harmful or off-topic responses" points to content filters and denied topics. "Mask customer emails and phone numbers in model responses" points to sensitive information filters with the mask action. "Users try to override the system prompt" points to the prompt attack filter with guardContent. "Check text without calling a model" points to ApplyGuardrail. "Every model call must use the guardrail" points to the bedrock:GuardrailIdentifier condition or enforced guardrails.

Securing agents

Skill 2.3.4Secure AI agent interactions (for example, by using tool-use authorization, session isolation, human-in-the-loop approval flows for sensitive actions).

An agent chooses and calls tools on its own, so a manipulated or mistaken agent acts with whatever permissions its tools have. Secure who can call the agent, what each tool call may do, whose data each session can see, and which actions need a person to approve.

Tool-use authorization

AgentCore IdentityAuthenticates callers to agents and gateways (IAM or OAuth/JWT), and gets credentials for the services the agent calls: OAuth tokens on behalf of a user (with their consent) or for the agent itself, and API keys. Credentials are kept in a token vault and are usable only by the same agent and user that obtained them, so code never holds long-lived secrets.

AgentCore GatewayExposes APIs, Lambda functions and existing MCP servers as tools over the Model Context Protocol, authenticating inbound callers and calling targets with IAM roles, OAuth or API keys.

Policy in AgentCore(Generally available since March 2026.) Cedar policies attached to a gateway are evaluated on every tool call, outside the agent's code, using the caller's identity, the tool and the tool's arguments. Everything is denied unless a policy permits it, and a forbid always wins. It can run in log-only mode before enforcing.

Allow refunds only under 50 (Cedar policy) 
permit(
  principal,
  action ==
    AgentCore::Action::"Refunds___issue",
  resource ==
    AgentCore::Gateway::"GATEWAY_ARN"
) when {
  context.input.amount < 50
};

The action name joins the gateway target and tool names. Larger refunds are denied by default, so they need another path, such as human approval.

Least privilege for toolsEach tool's role or credentials allow only what that tool does: the order-lookup tool reads orders, the refund tool calls one payment API. Validate tool arguments in the tool itself (amounts, order ownership) rather than trusting the model.

Session isolation

AgentCore Runtime runs each session in its own microVM, with its own memory and file system, and sanitizes it when the session ends, so one customer's conversation can't leak into another's. The caller supplies the session ID (at least 33 characters), and AgentCore doesn't check which user owns which session: your backend must create unique, unguessable session IDs and map them to the authenticated user. AgentCore Memory separates stored memories by actor and session namespaces, and IAM conditions on actor and session IDs can restrict access to the caller's own memories.

Human in the loop

For irreversible or costly actions (large refunds, cancellations, account changes), pause the agent and ask a person to confirm:

  1. ProposeThe agent decides to call the refund tool and returns the proposed action instead of executing it.
  2. WaitA workflow stores the request and waits, for example a Step Functions task with .waitForTaskToken, which can wait up to a year.
  3. ApproveA support lead approves or rejects in a review screen, which calls SendTaskSuccess or SendTaskFailure with the token.
  4. ContinueThe workflow runs the tool, or tells the agent the action was rejected.

Classic Bedrock Agents offer user confirmation and return of control for the same purpose; AgentCore Gateway can pass MCP elicitation requests to the user and connect to Step Functions for approval flows.

Amazon Bedrock Agents is now Bedrock Agents Classic and closed to new customers since July 30, 2026. AWS recommends Amazon Bedrock AgentCore for new agents.

"The agent's tools need OAuth access to a third-party API for each user" points to AgentCore Identity. "Limit which tools a user's agent may call, and with what arguments" points to Policy in AgentCore (Cedar). "One customer's session data must never reach another" points to per-session isolation in AgentCore Runtime and unique session IDs. "Refunds above a limit need approval" points to a human-in-the-loop step such as Step Functions task tokens.

Sensitive content in logs

Skill 2.3.5Protect sensitive content in monitoring logs during interactions with AI services.

Prompts and responses are full of customer data, and AI observability tools record them by design. Decide what's logged, mask what must be logged, encrypt it, and restrict who can read it.

LogWhat it containsProtect it with
Bedrock model invocation logsFull request and response bodies, token counts, caller identity (off by default; you choose text, image, embedding and other data types)Log only the data types you need; KMS encryption on the log group or bucket; tight IAM read access; retention periods; data protection policies
Guardrail tracesWhich policies acted, including the original PII values that were matchedDon't write raw traces to application logs; log the policy and action only
AgentCore observability spansInputs and outputs of agent steps and tool callsPer-agent log groups (since July 2026) with their own access and KMS keys; data protection policies
Application logsWhatever your code printsLog IDs and metadata, not prompts or answers; mask in code
CloudTrailWho called which API and when (model calls are management events; agent, knowledge base and guardrail calls are data events)Standard trail protection; use it for audit, not content

A CloudWatch Logs data protection policy on the invocation log group masks managed data identifiers (emails, card numbers, addresses, health identifiers) as events arrive, everywhere they're read; only principals with logs:Unmask see the originals. Masking starts when the policy is applied, so set it up before turning on invocation logging. Note that content a guardrail blocked still appears unmasked in invocation logs unless such a policy masks it.

Mask PII in the invocation log group (AWS CLI) 
aws logs put-data-protection-policy \
  --log-group-identifier \
    /bedrock/invocations \
  --policy-document file://mask.json

mask.json has an audit statement and a deidentify statement listing the data identifiers to mask, as in Task 2.2.

"Invocation logs must not expose customer PII" points to a CloudWatch Logs data protection policy plus restricted access and KMS. "Support engineers need to see unmasked values for an investigation" points to logs:Unmask for that role only. "Who called the model and when, without content" points to CloudTrail.

Key takeaways

  • Access: Bedrock models are enabled automatically; control them with IAM and SCPs on bedrock:InvokeModel (Converse uses it), model and inference profile ARNs, and condition keys. First use of third-party models needs Marketplace permissions (and the Anthropic form). Prefer short-term Bedrock API keys; AgentCore Runtime uses SigV4 or JWT callers.
  • Privacy: Bedrock doesn't use inputs or outputs to train models; data stays in the Region unless you choose cross-Region profiles (geographic or global). Use interface VPC endpoints with endpoint policies; opt out of content use for other AI services with an Organizations policy.
  • Filtering: Bedrock Guardrails content, prompt attack, denied topic, word, sensitive information, grounding and Automated Reasoning policies; guardContent for user input; ApplyGuardrail for any text including tool results; require guardrails with bedrock:GuardrailIdentifier or enforced guardrails.
  • Agents: AgentCore Identity for inbound auth and outbound credentials, Gateway for tools, Policy (Cedar) for per-call authorization, least-privilege tools, microVM session isolation with unique session IDs, Memory namespaces, and human approval for sensitive actions.
  • Logs: invocation logs and agent traces contain prompts; mask with CloudWatch Logs data protection, encrypt with KMS, restrict and expire; keep raw prompts and guardrail match details out of application logs.
