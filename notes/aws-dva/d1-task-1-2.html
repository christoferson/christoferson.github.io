Overview

Task 1.2

Develop code for AWS Lambda.

Lambda runs your code in response to events without servers to manage. Each function runs in execution environments: Lambda creates one (the init phase loads the runtime and your code, outside the handler), reuses it for later requests while it's warm, and adds more as concurrent requests grow. Code outside the handler runs once per environment, which is why SDK clients and database connections are created there.

The examples follow the food-ordering application from Task 1.1: an order API backed by Lambda, a payment function that reads a database in a VPC, and functions triggered by the order queue and by changes to the orders table.

The Lambda documentation now calls standard functions Lambda Event Functions (renamed in October 2026; the APIs, CLI and templates are unchanged), and lists newer options beside them: Lambda Managed Instances (functions on Lambda-managed EC2 instances in your account, November 2025), durable functions (long-running, checkpointed workflows written in code, December 2025), Lambda MicroVMs (isolated environments for running generated code, June 2026) and Lambda Web Functions (Node.js web servers, October 2026). This page covers standard functions, which is what the exam's skills describe.

VPC access

Skill 1.2.1Grant Lambda functions access to private resources in VPCs.

How it works

By default a function runs in a Lambda-owned network with internet access but no route into your VPCs. To reach an RDS database, an ElastiCache cluster or an internal service in private subnets, attach the function to the VPC with a VPC configuration: subnets (use at least two Availability Zones) and security groups.

  1. ConfigureSet VpcConfig with subnet IDs and security group IDs.
  2. Lambda creates network interfacesLambda creates a Hyperplane elastic network interface for each subnet and security group combination, shared by functions with the same combination. The function is Pending until it's ready (it can take minutes), then Active.
  3. Traffic flowsRequests from the function leave through those interfaces with the function's security groups; the database's security group must allow inbound traffic from them.

The execution role needs permission to manage the network interfaces (ec2:CreateNetworkInterface, ec2:DescribeNetworkInterfaces, ec2:DeleteNetworkInterface and related actions), most simply through the AWS managed policy AWSLambdaVPCAccessExecutionRole.

Attach a function to two private subnets (AWS CLI) 
aws lambda update-function-configuration \
  --function-name charge-order \
  --vpc-config SubnetIds=subnet-0a1,subnet-0b2,SecurityGroupIds=sg-0c3

The --vpc-config value is one shorthand argument and can't be split (a JSON file passed with file:// works too). An empty subnet and security group list detaches the function.

Reaching other services from the VPC

Once attached, the function's traffic follows the VPC's routes, so it loses the default internet access:

To reachUse
The internet or a public APIPrivate subnets with a route to a NAT gateway in a public subnet. A function in a public subnet still gets no public IP and no internet access
S3 or DynamoDBA gateway VPC endpoint (no charge)
Other AWS services (Secrets Manager, SQS, Bedrock…)Interface VPC endpoints (AWS PrivateLink), with private DNS enabled
A relational database at high concurrencyAmazon RDS Proxy, which pools connections so thousands of environments don't exhaust the database's connections

A function that was moved into a VPC and now times out calling S3, Secrets Manager or a third-party API has no route out. Adding an internet gateway or a public subnet doesn't help; add a NAT gateway route for private subnets, or VPC endpoints for AWS services.

"Function must reach an RDS database in a private subnet" points to a VPC configuration with the right security groups. "Too many database connections from Lambda" points to RDS Proxy. "Require all functions to be in a VPC" points to IAM conditions on lambda:VpcIds or lambda:SubnetIds.

Environment variables

Environment variables pass configuration to code without changing it: the table name, a log level, a feature flag. They total up to 4 KB, are encrypted at rest (with a customer managed KMS key if you set one), and some names are reserved, such as AWS_REGION and AWS_LAMBDA_FUNCTION_NAME. Don't store secrets in plain environment variables; keep them in Secrets Manager or Parameter Store and read them at init (the Parameters and Secrets Lambda extension caches them locally).

Memory, timeout and environment (AWS CLI) 
aws lambda update-function-configuration \
  --function-name charge-order \
  --memory-size 1024 \
  --timeout 30 \
  --environment file://env.json
env.json 
{"Variables": {
  "TABLE": "orders",
  "LOG_LEVEL": "INFO"
}}
Read configuration once per environment (Python) 
import os
import boto3

TABLE = os.environ["TABLE"]
table = boto3.resource(
    "dynamodb").Table(TABLE)

def handler(event, context):
    item = table.get_item(
        Key={"orderId": event["orderId"]})
    return item.get("Item")

Layers and extensions

LayersZip archives of libraries, a custom runtime or shared code, extracted to /opt and added to the function. Up to 5 layers per function, counted in the 250 MB unzipped limit; each layer version is immutable. Use them to share dependencies across functions or keep the deployment package small. Container image functions don't use layers; build dependencies into the image.

ExtensionsCompanion code that runs alongside the function for monitoring, security or configuration. External extensions are separate processes (shipped in a layer under /opt/extensions) that start before the function and can keep working after each invocation, for example sending telemetry. Internal extensions run inside the runtime process. Examples: CloudWatch Lambda Insights, the AWS Distro for OpenTelemetry, the Parameters and Secrets extension.

Versions and aliases

Publishing creates an immutable, numbered version of the code and configuration; $LATEST is the editable one. An alias (prod, beta) is a named pointer to a version; callers use the alias ARN, so releasing means moving the alias. An alias can split traffic between two versions (for example 90% and 10%) for a canary release, which CodeDeploy can automate (Task 3.3).

Concurrency

Concurrency is the number of requests being handled at the same moment. Each concurrent request needs its own environment.

ControlWhat it doesUse it to
Account limit1,000 concurrent executions per Region by default (can be raised), shared by all functionsKnow when functions start throttling
Reserved concurrencySets aside concurrency for one function and caps it at that number; 0 stops all invocationsGuarantee capacity for a critical function, or protect a downstream database by limiting a function
Provisioned concurrencyKeeps a number of environments initialized on a version or alias (not $LATEST); billed while configured; can be scaled with Application Auto ScalingRemove cold starts for latency-sensitive APIs

Each function can scale out by 1,000 execution environments every 10 seconds. Requests beyond the available concurrency are throttled: synchronous callers get HTTP 429 (TooManyRequestsException), while asynchronous events and event source mappings are retried.

Reserved and provisioned concurrency (AWS CLI) 
aws lambda put-function-concurrency \
  --function-name charge-order \
  --reserved-concurrent-executions 50

aws lambda put-provisioned-concurrency-config \
  --function-name order-api \
  --qualifier prod \
  --provisioned-concurrent-executions 20

Cold starts and SnapStart

A cold start is the init time of a new environment: downloading code, starting the runtime and running your init code. Reduce it by keeping packages small, initializing only what you need, and choosing provisioned concurrency for steady latency-sensitive traffic. SnapStart (Java 11 and later, Python 3.12 and later, .NET 8 and later) snapshots an initialized environment when you publish a version and restores from it; code that creates unique values (IDs, random seeds) or connections during init should refresh them after restore with the runtime hooks. SnapStart can't be combined with provisioned concurrency.

Other settings worth knowing

Function URLsA dedicated HTTPS endpoint for a function, with AWS_IAM or NONE authentication and CORS settings. Since October 2025, new function URLs require callers to have both lambda:InvokeFunctionUrl and lambda:InvokeFunction.

LoggingLogs go to the CloudWatch Logs group /aws/lambda/<function> by default, or a group you choose. JSON log format with application and system log levels lets you filter noise without code changes.

Recursive loop detectionLambda stops a function that keeps triggering itself through SQS, SNS, S3 or EventBridge custom buses after about 16 invocations in a chain (on by default). It doesn't cover every service, such as DynamoDB.

"CPU-bound function is slow" points to more memory. "Cold starts on a latency-sensitive API" points to provisioned concurrency (or SnapStart for supported runtimes). "A function overwhelms the database" or "must always have capacity" points to reserved concurrency. "Share libraries across functions" points to layers. "Same code, different settings per environment" points to environment variables with aliases.

Errors and event lifecycles

Skill 1.2.3Handle event lifecycles and errors (for example, by using Lambda destinations, dead-letter queues).

What happens to a failed event depends on how the function was invoked. Getting this right is the difference between a retried order and a lost one.

InvocationOn errorWhere failures go
Synchronous (API Gateway, function URL, SDK RequestResponse)The error goes back to the caller (the response has an X-Amz-Function-Error header); Lambda doesn't retryThe caller decides: retry, return an error to the user
Asynchronous (S3, SNS, EventBridge, SDK Event)Lambda retries up to 2 more times (configurable 0 to 2) and keeps events up to 6 hours (configurable 60 seconds to 6 hours)An on-failure destination or a dead-letter queue
Event source mapping, queue (SQS)The batch's messages become visible again and are retriedThe queue's own dead-letter queue (redrive policy)
Event source mapping, stream (Kinesis, DynamoDB Streams, Kafka)The batch is retried until it succeeds or expires, blocking the shardAn on-failure destination on the mapping (SQS, SNS or S3)

Destinations for asynchronous invocations

A destination receives a record of each asynchronous invocation's outcome: on success and/or on failure (after retries are exhausted or the event is too old). Targets are an SQS queue, an SNS topic, another Lambda function, an EventBridge bus, or (on failure) an S3 bucket. The record includes the original event (requestPayload), the function's response or error (responsePayload), and context such as why it failed (condition: RetriesExhausted or EventAgeExceeded) and how many times it ran. The execution role needs permission to send to the target.

Retries, event age and destinations (AWS CLI) 
aws lambda put-function-event-invoke-config \
  --function-name send-receipt \
  --maximum-retry-attempts 1 \
  --maximum-event-age-in-seconds 3600 \
  --destination-config file://dest.json
dest.json 
{
  "OnSuccess": {
    "Destination": "SUCCESS_TOPIC_ARN"
  },
  "OnFailure": {
    "Destination": "FAILED_QUEUE_ARN"
  }
}

Destinations must be standard (not FIFO) queues and topics.

Dead-letter queues

A function's dead-letter queue (an SQS queue or SNS topic, set with --dead-letter-config) is the older mechanism for failed asynchronous events. It receives only failures, and only the event itself plus error attributes. Destinations carry more context and also cover success, so they are the better choice for new designs; a function can have both.

For an SQS-triggered function, a dead-letter queue or destination on the function does nothing: the function is invoked synchronously by the event source mapping. Configure a redrive policy with a dead-letter queue on the source queue (a maxReceiveCount of at least 5 is recommended), and set the queue's visibility timeout to at least six times the function timeout.

Partial batch failures

With batches, one bad message shouldn't make the whole batch fail and repeat. Enable ReportBatchItemFailures on the mapping and return the IDs of the failed items; only those are retried. For SQS the identifier is the messageId; for streams it's the sequence number (Task 1.1 shows the Kinesis version).

Partial batch response for SQS (Python) 
def handler(event, context):
    failed = []
    for rec in event["Records"]:
        body = rec["body"]
        try:
            prepare(json.loads(body))
        except Exception:
            failed.append(
                {"itemIdentifier":
                 rec["messageId"]})
    return {"batchItemFailures": failed}

All event sources deliver at least once, so make processing idempotent: a retried or duplicated event must not create a second order or charge.

"Capture failed asynchronous events with the error details" points to an on-failure destination. "Trigger the next step when an asynchronous invocation succeeds" points to an on-success destination. "Failed SQS messages" points to the source queue's redrive policy. "One bad record stops a stream" points to on-failure destinations, bisecting and partial batch responses.

Integrations

Skill 1.2.4Integrate Lambda functions with AWS services by using code, event source mappings, and destinations (for example, API Gateway, Amazon DynamoDB).

Three ways in, one way out

Services push eventsAPI Gateway, function URLs, Application Load Balancers and Cognito triggers invoke synchronously; S3, SNS, EventBridge and CloudWatch Logs invoke asynchronously. The service needs permission in the function's resource-based policy.

Lambda polls a sourceAn event source mapping is a Lambda-side poller that reads SQS, Kinesis, DynamoDB Streams, Amazon MSK, self-managed Kafka, Amazon MQ or DocumentDB, batches records and invokes the function synchronously. The execution role needs permission to read the source.

Your code calls servicesThe function uses the SDK with its execution role's permissions, for example writing to DynamoDB or publishing to SNS.

Results flow onDestinations pass asynchronous outcomes to the next service without code.

Two different policies: the resource-based policy says who may invoke the function (for example apigateway.amazonaws.com for one API). The execution role says what the function may do. "API Gateway gets permission denied invoking the function" is the first; "the function can't read the queue or write the table" is the second.

Let one API invoke the function (AWS CLI) 
aws lambda add-permission \
  --function-name order-api \
  --statement-id apigw-orders \
  --action lambda:InvokeFunction \
  --principal apigateway.amazonaws.com \
  --source-arn "arn:aws:execute-api:us-east-1:111111111111:a1b2c3/*/POST/orders"

The source ARN (an unsplittable token) limits the permission to one API, stage pattern, method and path. Since August 2026 a function can also have a full IAM resource-based policy (put-resource-policy), which replaces the whole policy rather than adding a statement.

API Gateway

With a Lambda proxy integration, the function receives the whole HTTP request as the event (method, path, headers, query string parameters, and body as a string) and must return a response object. HTTP APIs offer payload format 1.0 (the REST API shape) or 2.0 (simpler: rawPath, a cookies list, and a plain returned object becomes a 200 JSON response).

A proxy integration handler (Python) 
def handler(event, context):
    try:
        order = json.loads(event["body"])
    except (TypeError, ValueError):
        return {"statusCode": 400,
                "body": "invalid JSON"}
    order_id = place(order)
    return {
        "statusCode": 201,
        "headers": {
            "Content-Type":
                "application/json"},
        "body": json.dumps(
            {"orderId": order_id}),
    }

A function that returns anything else (no statusCode, a non-string body) causes a 502 "Malformed Lambda proxy response" from a REST API.

DynamoDB Streams

A DynamoDB stream records item changes for 24 hours. With an event source mapping, Lambda reads each shard in order and invokes the function with batches (default 100 records). The stream's view type decides what each record holds: KEYS_ONLY, NEW_IMAGE, OLD_IMAGE or NEW_AND_OLD_IMAGES. Typical uses: send a notification when an order's status changes, keep a search index or cache in sync, or aggregate totals.

React to order status changes (Python) 
def handler(event, context):
    for rec in event["Records"]:
        if rec["eventName"] != "MODIFY":
            continue
        ddb = rec["dynamodb"]
        new = ddb["NewImage"]["status"]
        old = ddb["OldImage"]["status"]
        if new["S"] != old["S"]:
            notify(ddb["Keys"], new["S"])

Stream records use DynamoDB's typed JSON ({"S": ...}), and the old image needs the NEW_AND_OLD_IMAGES view type.

Only process paid orders from the stream (AWS CLI) 
aws lambda create-event-source-mapping \
  --function-name kitchen-ticket \
  --event-source-arn STREAM_ARN \
  --starting-position TRIM_HORIZON \
  --batch-size 100 \
  --filter-criteria file://filter.json
filter.json (the pattern is a JSON string) 
{"Filters": [{"Pattern":
  "{\"dynamodb\": {\"NewImage\": {\"status\": {\"S\": [\"PAID\"]}}}}"
}]}

The pattern string is one unsplittable value; it matches records whose new image has status set to PAID.

In AWS SAM

Templates usually declare all of this together on the function: Events (API, SQS, DynamoDB, schedule triggers), VpcConfig, Layers, Environment, ReservedConcurrentExecutions, ProvisionedConcurrencyConfig with AutoPublishAlias, EventInvokeConfig (retries and destinations) and DeadLetterQueue.

A queue-triggered function (AWS SAM, YAML) 
KitchenFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: app.handler
    Runtime: python3.13
    MemorySize: 512
    Timeout: 30
    Environment:
      Variables:
        TABLE: !Ref OrdersTable
    Events:
      Orders:
        Type: SQS
        Properties:
          Queue: !GetAtt OrderQueue.Arn
          BatchSize: 10
          FunctionResponseTypes:
            - ReportBatchItemFailures

SAM adds the queue permissions to the execution role for SQS events. The queue's visibility timeout should be at least 180 seconds here (six times the 30-second timeout).

"Process changes to a DynamoDB table" points to DynamoDB Streams with an event source mapping. "Invoke only for some messages" points to filter criteria. "Limit how fast a queue drains into a database" points to maximum concurrency on the mapping (or reserved concurrency). "502 from API Gateway" points to a malformed proxy response.

Key takeaways

  • VPC access: subnets and security groups, network interfaces created by Lambda (role needs the EC2 network interface permissions). No internet without a NAT gateway; use VPC endpoints for AWS services and RDS Proxy for databases.
  • Configure memory (CPU follows it), timeout (max 15 minutes), /tmp, runtime, handler, architecture and environment variables (4 KB, encrypted; secrets in Secrets Manager). Initialize clients outside the handler.
  • Layers share libraries (up to 5, /opt); extensions add monitoring and caching alongside the function. Versions are immutable; aliases point to them and can split traffic.
  • Concurrency: 1,000 per Region by default; reserved concurrency guarantees and caps; provisioned concurrency removes cold starts; SnapStart speeds up init for Java, Python and .NET.
  • Errors: synchronous errors return to the caller; asynchronous events retry (0 to 2 times, up to 6 hours) then go to on-failure destinations or a DLQ; SQS failures go to the queue's DLQ; stream failures to the mapping's on-failure destination; use partial batch responses and idempotency.
  • Integrations: push services need resource-based policy permission; event source mappings poll SQS, streams, Kafka, MQ and DocumentDB with batch, filter and concurrency settings; your code uses the execution role. Proxy handlers must return statusCode, headers and a string body.
