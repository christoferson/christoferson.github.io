Overview

Task 3.1

Prepare application artifacts to be deployed to AWS.

An artifact is what a deployment ships: a zip file for Lambda, a container image, a template. A good artifact is built once, contains everything the code needs to run, and is the same in every environment; only configuration (table names, endpoints, feature flags) changes between dev, test and prod. This task is about getting that separation right. Deploying the artifacts is Task 3.3.

The examples follow the food-ordering application: Python Lambda functions for the order API, a containerized kitchen service on ECS, source code on GitHub, and dev, test and prod environments.

Dependencies

Skill 3.1.1Manage dependencies for code modules (for example, environment variables, configuration files, container images) within packages.

What goes in the package

Code and librariesEverything the code imports, at pinned versions (a lock file or exact versions in requirements.txt), so every build produces the same artifact.

Static configuration filesSettings that are the same everywhere (logging format, defaults) can ship in the package.

Not in the packageAnything that differs per environment (table names, URLs, flags) and every secret: these come from environment variables, AppConfig, Parameter Store or Secrets Manager at runtime (below).

Lambda zip packages by language

RuntimeHow to package
PythonInstall dependencies into a folder (pip install --target) and zip them with the code. Packages with native code need wheels built for Lambda's Linux and architecture
Node.js and TypeScriptBundle with esbuild into one file, which also removes unused code; or zip node_modules
JavaA single "uber" JAR with all dependencies (Maven Shade plugin), or a zip with dependency JARs in lib/
Container imageDependencies installed in the image from an AWS Lambda base image (up to 10 GB)
Install Linux arm64 wheels for a Python 3.13 function (shell) 
pip install \
  --target ./package \
  --platform manylinux_2_28_aarch64 \
  --implementation cp \
  --python-version 3.13 \
  --only-binary=:all: \
  -r requirements.txt
cd package && zip -r ../function.zip .
cd .. && zip function.zip app.py

Python 3.12 and later run on Amazon Linux 2023 (use manylinux_2_28 wheels); earlier versions run on Amazon Linux 2 (manylinux2014). Use x86_64 instead of aarch64 for x86 functions. A dependency bundled in the package takes precedence over the copy in the runtime, so bundling one SDK component without the others can cause version mismatches.

Build tools

AWS SAMsam build installs each function's dependencies and prepares the artifacts. --use-container builds inside a Lambda-like Docker image, which is the simple fix for native dependencies built on a Mac or Windows laptop; --cached and --parallel speed it up.

AWS CDKNodejsFunction bundles TypeScript with esbuild using your lock file; the Python construct installs requirements in a Lambda-compatible container.

LayersShared libraries can live in a Lambda layer (up to 5 per function, extracted to /opt, counted in the 250 MB unzipped limit) instead of every function's zip.

AWS CodeArtifactA private package repository for pip, npm, Maven, NuGet and others. It can proxy and cache public registries (PyPI, npm) through upstream repositories and external connections, and hold your own internal packages. aws codeartifact login --tool pip configures the package manager with a token (12 hours by default).

"The function works locally but fails in Lambda with an import error for a compiled library" is a native dependency built for the wrong operating system or architecture. Build with sam build --use-container, download matching wheels, or use a container image.

Container images

Skill 3.1.2Build and manage container images for deployment (for example, by using Amazon ECR, Docker files, container image tagging, lifecycle policies).

Dockerfiles

Put all dependencies in the image, run one process per container, log to standard output, and handle the stop signal (SIGTERM) so tasks shut down cleanly. Keep images small with slim base images and multi-stage builds (compile in one stage, copy only the result into the final one), exclude local files with .dockerignore, and run as a non-root user.

Kitchen service image, multi-stage (Dockerfile) 
FROM python:3.13 AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --prefix=/install \
    -r requirements.txt

FROM python:3.13-slim
WORKDIR /app
COPY --from=build /install /usr/local
COPY src/ ./src/
USER 1000
CMD ["python", "-m", "src.kitchen"]
A Lambda function as a container image (Dockerfile) 
FROM public.ecr.aws/lambda/python:3.13
COPY requirements.txt ${LAMBDA_TASK_ROOT}
RUN pip install -r requirements.txt
COPY app.py ${LAMBDA_TASK_ROOT}
CMD ["app.handler"]

AWS base images include the runtime interface client that connects the code to Lambda; other base images need it added. A Lambda image must be built for one architecture, and its file system is read-only except /tmp. Test it locally with the runtime interface emulator included in the base image.

Amazon ECR

Amazon Elastic Container Registry stores images in private repositories. Images are addressed as ACCOUNT.dkr.ecr.REGION.amazonaws.com/REPO:TAG, or by digest (@sha256:...) for an exact, unchangeable reference.

Build for x86 and push to ECR (shell) 
REG=111111111111.dkr.ecr.us-east-1.amazonaws.com
aws ecr get-login-password \
  --region us-east-1 |
  docker login --username AWS \
  --password-stdin $REG

TAG=$(git rev-parse --short HEAD)
docker buildx build \
  --platform linux/amd64 \
  -t $REG/kitchen:$TAG .
docker push $REG/kitchen:$TAG

The registry host name can't be split. The login token is valid for 12 hours. For Lambda images, add --provenance=false so the build produces a single-architecture manifest Lambda accepts.

ECR featureWhat it does
Tag immutabilityPrevents pushing a different image under an existing tag (ImageTagAlreadyExistsException); since 2025 you can exclude tags such as latest by filter
Image scanningBasic scanning finds operating system vulnerabilities on push or on demand; enhanced scanning (Amazon Inspector) also covers language packages and rescans continuously
Lifecycle policiesExpire old or untagged images automatically, or move rarely used ones to the archive storage class (2025)
Pull-through cacheCaches images from public registries (ECR Public, Docker Hub, Quay, GitHub, others) in your account
ReplicationCopies images to other Regions or accounts
Repository creation templatesSettings for repositories ECR creates automatically, including on first push (since December 2025)
SigningSign images with AWS Signer, including automatic managed signing on push (2025)

Tagging and lifecycle policies

Tag each image with something that identifies its source, such as the git commit SHA or a release version, and deploy that tag (or the digest). latest moves with every push, so it can't tell you what's running or let you roll back; with immutable tags, a tag always means the same image.

Keep the newest 20 release images, delete untagged after 7 days (lifecycle policy) 
{"rules": [
  {"rulePriority": 1,
   "description": "untagged",
   "selection": {
     "tagStatus": "untagged",
     "countType": "sinceImagePushed",
     "countUnit": "days",
     "countNumber": 7},
   "action": {"type": "expire"}},
  {"rulePriority": 2,
   "description": "releases",
   "selection": {
     "tagStatus": "tagged",
     "tagPrefixList": ["v"],
     "countType": "imageCountMoreThan",
     "countNumber": 20},
   "action": {"type": "expire"}}
]}

Rules are evaluated by priority (lowest number first), actions happen within about 24 hours, and the console can preview which images a policy would remove before you apply it.

"Prevent an image tag from being overwritten" points to tag immutability. "Repository storage keeps growing" points to a lifecycle policy. "Find vulnerabilities in images, including application libraries" points to enhanced scanning. "Docker Hub rate limits during builds" points to a pull-through cache rule.

Code repositories

Skill 3.1.3Use code repositories in deployment environments.

Pipelines start from a repository: a push or merge to a branch triggers a build and deployment. AWS services reach third-party Git hosts through AWS CodeConnections (renamed from AWS CodeStar Connections in 2024): GitHub, GitHub Enterprise Server, GitLab (cloud and self-managed), Bitbucket Cloud and Azure DevOps.

  1. Create the connectionIn the console, CLI or CloudFormation. A connection created outside the console stays PENDING.
  2. Authorize itComplete the handshake in the console, installing the provider's app (for example the AWS Connector for GitHub) for the chosen repositories. This step can't be done from the CLI.
  3. Use itCodePipeline's source action (provider CodeStarSourceConnection, with the connection ARN, owner/repo and branch) and CodeBuild projects read the repository, and pushes trigger pipelines. Connections can be shared across accounts with AWS RAM.

Build settings in the repositoryKeep buildspec.yml (CodeBuild), the SAM or CDK app, Dockerfiles and appspec.yml (CodeDeploy) in the repository with the code, so changes to the build are reviewed and versioned too.

Branches per environmentA common pattern maps branches to environments (feature branches to previews, main to production). Amplify Hosting deploys each connected branch as its own environment and can create previews for pull requests.

Pipeline source artifactBy default the source action passes a zip of the code; the CODEBUILD_CLONE_REF output format passes a full Git clone reference to CodeBuild when the build needs Git history or tags.

AWS CodeCommit closed to new customers in July 2024 and became generally available to new customers again in November 2025; it isn't on the DVA-C03 in-scope list. Its repositories are reached over HTTPS with Git credentials, SSH, or git-remote-codecommit (which uses IAM and temporary credentials).

"Trigger CodePipeline from a GitHub repository" points to a CodeConnections connection and the source action. "Connection created by CloudFormation doesn't work" points to the pending handshake. "Separate environment per branch for a web front end" points to Amplify branch deployments.

Environment configuration

Skill 3.1.4Manage environment-specific application configuration by using AWS services (for example, AWS AppConfig, AWS Systems Manager Parameter Store, AWS Secrets Manager, Amazon API Gateway, AWS Lambda).

The same artifact runs in every environment; what it connects to and how it behaves comes from configuration chosen at deploy or run time.

WhereBest forPer-environment pattern
Lambda environment variablesSmall, non-secret settings read at startupSet per function by the template; they're part of a published version, so an alias points each environment at a version with its values
Parameter StoreConfiguration values and SecureStrings, shared across servicesA hierarchy such as /orders/prod/...; read a whole level with GetParametersByPath
Secrets ManagerCredentials and keys that rotateOne secret per environment, named by convention (prod/orders/db)
AWS AppConfigSettings and feature flags changed often at runtime, validated and rolled out graduallyAn AppConfig environment per stage, each with its own deployments
API Gateway stage variablesPer-stage backend targetsA variable pointing each stage at a Lambda alias or backend URL
TemplatesValues fixed at deploy timeCloudFormation parameters, mappings and conditions; SAM samconfig.toml sections per environment
Read every prod setting under one path (Python) 
ssm = boto3.client("ssm")
pages = ssm.get_paginator(
    "get_parameters_by_path")
config = {}
for page in pages.paginate(
        Path="/orders/prod/",
        Recursive=True,
        WithDecryption=True):
    for p in page["Parameters"]:
        key = p["Name"].rsplit("/", 1)[-1]
        config[key] = p["Value"]

AWS AppConfig

AppConfig manages configuration that changes without a code deployment, safely: an application has environments and configuration profiles. A profile is either a feature flag profile or a freeform configuration stored in AppConfig's hosted store or in S3, Parameter Store or Secrets Manager. Each change becomes a version that you deploy to an environment:

  1. ValidateA JSON Schema or a Lambda validator rejects a bad configuration before it's deployed.
  2. Roll out graduallyA deployment strategy controls how fast clients receive it: AppConfig.Linear20PercentEvery6Minutes (recommended for production), AppConfig.Canary10Percent20Minutes, AppConfig.AllAtOnce, or your own.
  3. Bake and roll backDuring the rollout and a bake time afterwards, AppConfig watches CloudWatch alarms and rolls back automatically if one fires.

Applications read configuration with the AppConfig Data API: StartConfigurationSession returns a token, and GetLatestConfiguration returns the configuration and the next token (the older GetConfiguration API is deprecated). In Lambda and containers, the AppConfig Agent (a Lambda extension or a sidecar) polls in the background and serves the latest configuration locally, which is simpler and cheaper because AppConfig charges per configuration request.

Read a feature flag from the AppConfig Lambda extension (Python) 
import urllib.request

FLAGS = ("http://localhost:2772"
         "/applications/orders"
         "/environments/prod"
         "/configurations/flags")

def flags():
    req = urllib.request.urlopen(FLAGS)
    with req as r:
        return json.loads(r.read())

def handler(event, context):
    express = flags()["express-delivery"]
    if express["enabled"]:
        offer_express(event)

The extension (added as a layer) refreshes the cached configuration every 45 seconds by default, so a flag change reaches all functions within a minute without redeploying them.

Stage variables and Lambda aliases

An API Gateway integration can name its Lambda function as order-api:${stageVariables.alias}, so the dev stage (with alias=dev) calls the dev alias and prod calls prod. Because the function name isn't fixed, you must add the Lambda permission for each alias yourself. Stage variables aren't for secrets.

samconfig.toml with two environments 
version = 0.1

[default.deploy.parameters]
stack_name = "orders-dev"
parameter_overrides = "Stage=dev"

[prod.deploy.parameters]
stack_name = "orders-prod"
parameter_overrides = "Stage=prod"
confirm_changeset = true

sam deploy --config-env prod deploys the same template with the prod settings.

"Change a feature flag without redeploying, roll it out gradually and roll back on errors" points to AppConfig with a deployment strategy and alarms. "Validate configuration before it's used" points to AppConfig validators. "Hierarchical configuration per environment" points to Parameter Store paths. "Each API stage calls a different function version" points to stage variables with Lambda aliases.

API Gateway stages and endpoints

Skill 3.1.5Use API Gateway features and resources (for example, stage-specific URLs, endpoints).

Deployments and stages

A REST API's changes take effect only after you create a deployment (a snapshot) and point a stage at it; forgetting to redeploy is a classic "my change didn't work". Each stage has its own URL, https://API_ID.execute-api.REGION.amazonaws.com/STAGE/, its own stage variables, and its own logging, throttling, caching and canary settings. HTTP APIs can deploy automatically, and their $default stage is served at the base URL with no stage name.

Deploy the REST API to the test stage (AWS CLI) 
aws apigateway create-deployment \
  --rest-api-id a1b2c3 \
  --stage-name test \
  --description "build 1234"

A REST stage can also run a canary: a percentage of its traffic goes to a new deployment, with its own stage variable overrides, before you promote it.

Custom domain names

Clients should call api.example.com, not the generated URL. A custom domain needs an ACM certificate (in us-east-1 for edge-optimized domains, in the API's Region for Regional ones) and a DNS record. API mappings connect paths to APIs and stages (/orders to the orders API's prod stage). For REST APIs, routing rules (2025, now recommended over mappings) route by headers and base path, for example sending requests with a version header to a new API. Private APIs can have private custom domain names (since November 2024). Once clients use the custom domain, you can turn off the default execute-api endpoint (disableExecuteApiEndpoint) so all traffic goes through it.

Private API resource policy: only through one VPC endpoint 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "execute-api:Invoke",
    "Resource": "execute-api:/*",
    "Condition": {"StringEquals": {
      "aws:SourceVpce": "vpce-0abc1234"}}
  }]
}

Export a stage's definition as OpenAPI (aws apigateway get-export --export-type oas30) to share it with client teams or generate SDKs.

"Changes to a REST API don't appear" points to a missing deployment. "API only reachable from inside the VPC" points to a private endpoint type with a VPC endpoint and resource policy. "Global clients, lower latency" points to edge-optimized. "Friendly URL for several APIs" points to a custom domain with API mappings or routing rules.

Key takeaways

  • Build one artifact with pinned dependencies; keep per-environment values and secrets out of it. Native Python dependencies need wheels for Lambda's Linux and architecture (sam build --use-container helps); bundle Node.js with esbuild; uber JARs for Java; layers and CodeArtifact for shared packages.
  • Container images: small multi-stage Dockerfiles, one process, stdout logs; push to ECR with commit-based tags or digests; tag immutability, enhanced scanning, lifecycle policies (expire or archive), pull-through cache, replication.
  • Repositories: CodeConnections to GitHub, GitLab, Bitbucket and Azure DevOps (complete the handshake in the console); build files in the repository; branches per environment.
  • Configuration: Lambda environment variables with versions and aliases, Parameter Store hierarchies, Secrets Manager per environment, AppConfig for validated, gradual, alarm-protected changes and feature flags (read through the agent), stage variables, template parameters and samconfig.toml.
  • API Gateway: deploy REST changes to a stage; stage URLs, variables, settings and canaries; edge-optimized, Regional or private endpoints; custom domains with ACM certificates and API mappings or routing rules.
