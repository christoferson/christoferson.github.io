Overview

Task 3.2

Implement and automate application testing in AWS environments.

Cloud applications are tested in layers. Unit tests run the code alone, with AWS calls mocked, in seconds. Infrastructure tests check that templates are valid and produce the intended resources. Integration tests run against real AWS services in a test environment, because local emulation never matches the cloud exactly. AWS's tooling (SAM, CDK, CloudFormation, CodeBuild) covers each layer, and pipelines run them on every change (Task 3.3).

The examples follow the food-ordering application: a SAM application with an order API, a function triggered by uploads of restaurant menus to S3, a payment provider whose API isn't available in test, and dev, test and prod environments.

Developing and validating tests

Skill 3.2.1Develop and validate tests (for example, by using AWS SAM, AWS CDK, AWS CloudFormation).

Testing with AWS SAM

CommandDoes
sam local invokeRuns one function once in a local Docker container that mimics Lambda, with an event file (-e) and environment variable overrides (--env-vars)
sam local start-apiServes the template's API locally (port 3000) so you can call it with a browser or curl
sam local start-lambdaRuns a local Lambda endpoint (http://127.0.0.1:3001) that tests can call with the SDK
sam local generate-eventPrints a sample event for a service (S3, SQS, SNS, API Gateway, DynamoDB…) to edit and reuse
sam remote invokeInvokes a deployed function, state machine, queue or stream in the cloud with an event
sam remote test-eventSaves and shares test events in the cloud (the same shareable events the Lambda console uses)
sam sync --watchPushes code changes to a development stack in seconds as you save (dev environments only)
sam validate --lintChecks the template, including cfn-lint rules
Local and cloud tests for the menu function (shell) 
sam local generate-event s3 put \
  --bucket menus-dev > events/s3.json

sam build
sam local invoke MenuFunction \
  -e events/s3.json \
  --env-vars env.json

sam remote invoke MenuFunction \
  --stack-name orders-test \
  --event-file events/s3.json

Local runs need Docker and run the code on your machine with your credentials, so calls to S3 or DynamoDB from the function reach the real services. --env-vars points functions at test resources; --docker-network connects the container to other local containers (for example a local database). For bugs that only happen in the cloud, the AWS Toolkit for VS Code can debug a deployed function remotely (since July 2025).

Call the local Lambda endpoint from a test (Python) 
from botocore import UNSIGNED
from botocore.config import Config

local = boto3.client(
    "lambda",
    endpoint_url="http://127.0.0.1:3001",
    use_ssl=False, verify=False,
    config=Config(
        signature_version=UNSIGNED,
        retries={"max_attempts": 0}),
)
r = local.invoke(
    FunctionName="OrderFunction",
    Payload=json.dumps(order))
out = json.loads(r["Payload"].read())
assert out["ok"]

Testing CDK apps

The aws-cdk-lib/assertions module tests the CloudFormation template a CDK stack synthesizes, without deploying. Fine-grained assertions check specific resources and properties (partial matches by default); snapshot tests compare the whole template with a stored copy, which catches unexpected changes but also fires on harmless ones after CDK upgrades, so use them alongside assertions.

Assert the queue and function settings (TypeScript, Jest) 
import { App } from "aws-cdk-lib";
import { Match, Template }
  from "aws-cdk-lib/assertions";
import { OrdersStack }
  from "../lib/orders";

test("orders stack", () => {
  const app = new App();
  const t = Template.fromStack(
    new OrdersStack(app, "Test"));

  t.resourceCountIs("AWS::SQS::Queue", 2);
  t.hasResourceProperties(
    "AWS::Lambda::Function", {
      Runtime: "nodejs22.x",
      Timeout: 30,
      Environment: Match.objectLike({
        Variables: Match.objectLike({
          TABLE: Match.anyValue() }) }),
    });
  expect(t.toJSON()).toMatchSnapshot();
});

Capture grabs a value to inspect further, Match.absent() asserts a property isn't set, and Annotations checks warnings and errors. cdk diff shows what a deployment would change; cdk-nag checks stacks against security rules; the experimental integ-tests-alpha module and integ-runner deploy a stack and run assertions against the real resources.

Validating CloudFormation templates

ToolCatches
aws cloudformation validate-templateMalformed JSON or YAML and template structure; not invalid property values
cfn-lintInvalid properties, types and values against the resource specifications, plus best-practice rules
CloudFormation GuardPolicy violations you write as rules (for example "every bucket must be encrypted"); runs locally or in CI
Pre-deployment validationInvalid property syntax and resource name conflicts before provisioning starts, plus warnings for change sets (non-empty buckets, quotas); on by default since June 2026
Change setsWhat will be added, modified or replaced before you execute
CloudFormation HooksRules enforced by the service itself (Guard rules or Lambda) that block or warn on non-compliant resources during deployment

validate-template passing doesn't mean the stack will deploy: it checks syntax, not that a property value is allowed or that a bucket name is free. Use cfn-lint and a change set, and rely on pre-deployment validation for name conflicts.

"Test a function locally with a sample S3 event" points to sam local generate-event and sam local invoke. "Test the deployed function with the same event" points to sam remote invoke. "Unit test that a CDK stack creates an encrypted bucket" points to Template.fromStack with hasResourceProperties. "Enforce organization rules on templates in CI" points to cfn-guard or Hooks.

Mocking dependencies

Skill 3.2.2Use mock APIs for external dependencies by using AWS services and tools (for example, API Gateway).

Tests shouldn't depend on systems you don't control: the payment provider's sandbox is slow and sometimes down, and another team's API may not exist yet. A mock stands in with predictable responses.

API Gateway mock integrations

A REST API method with integration type MOCK returns a response without calling any backend. The integration request mapping template chooses a status code, and the integration response mapping template returns the fixed body. Front-end and mobile teams can build against the mock while the real service is written, and switching later means changing only the integration.

Integration request template (application/json) 
{"statusCode": 200}
Integration response template for 200 
{
  "paymentId": "pay-test-0001",
  "status": "APPROVED",
  "amount": $input.json('$.amount')
}

Velocity logic can return different results for different inputs, for example a decline for a test card number, so tests can cover both paths. Mock integrations are a REST API feature (HTTP APIs don't have them); they're also commonly used to answer CORS preflight OPTIONS requests. Point the test stage's payment client at the mock API's URL with a stage variable or environment variable.

Other ways to mock

Mock AWS calls in unit testsPython: moto (@mock_aws) fakes AWS services in memory, and botocore's Stubber queues exact responses for one client. JavaScript SDK v3: aws-sdk-client-mock. These make unit tests fast and free.

Step Functions TestStateThe TestState API runs a state or a whole definition with mocked service responses (or mocked errors) since November 2025, without deploying or calling the real services. It replaces Step Functions Local, which is no longer supported.

EventBridge patternsThe TestEventPattern API (and the console sandbox) checks whether an event matches a rule's pattern without creating the rule.

Stub functionsA small Lambda function returning canned data can stand in for a dependency in an integration test environment.

Mock DynamoDB in a unit test (Python, moto) 
from moto import mock_aws

@mock_aws
def test_save_order():
    ddb = boto3.resource(
        "dynamodb",
        region_name="us-east-1")
    ddb.create_table(
        TableName="orders",
        KeySchema=[{
            "AttributeName": "orderId",
            "KeyType": "HASH"}],
        AttributeDefinitions=[{
            "AttributeName": "orderId",
            "AttributeType": "S"}],
        BillingMode="PAY_PER_REQUEST")
    save_order({"orderId": "o-1"})
    item = ddb.Table("orders").get_item(
        Key={"orderId": "o-1"})["Item"]
    assert item["orderId"] == "o-1"

"Front-end team needs the API before the backend exists" points to an API Gateway mock integration. "Unit tests must not call AWS" points to SDK mocking libraries. "Test a state machine without deploying" points to the Step Functions TestState API. "Check an event pattern" points to TestEventPattern.

Test events

Skill 3.2.3Create application test events (for example, by using JSON payloads to test Lambda functions and API Gateway APIs).

A Lambda function's input is a JSON event whose shape depends on what invokes it, so a good test uses an event with exactly that shape. Start from sam local generate-event or the console's templates, then edit the values.

SourceKey fields
API Gateway REST (proxy, format 1.0)httpMethod, path, headers, queryStringParameters, pathParameters, body (a string), isBase64Encoded
API Gateway HTTP API (format 2.0)routeKey, rawPath, rawQueryString, requestContext.http.method, lowercase headers, body
S3Records[].eventName (for example ObjectCreated:Put), s3.bucket.name, s3.object.key (URL-encoded)
SQSRecords[].messageId, receiptHandle, body, messageAttributes
SNSRecords[].Sns.Message, Sns.MessageAttributes
DynamoDB StreamsRecords[].eventName (INSERT, MODIFY, REMOVE), dynamodb.Keys, NewImage, OldImage
EventBridgesource, detail-type, detail (an object), time
events/order.json (REST proxy event, trimmed) 
{
  "httpMethod": "POST",
  "path": "/orders",
  "headers": {
    "Content-Type": "application/json"},
  "queryStringParameters": null,
  "pathParameters": null,
  "body": "{\"customerId\":\"c-9\",\"items\":[{\"sku\":\"pizza\",\"qty\":1}]}",
  "isBase64Encoded": false
}

The body is a JSON string inside the event and can't be split. Keep events like this in the repository next to the tests.

Where to run them

Lambda consoleSaved test events are private (only you, up to 10 per function) or shareable (everyone in the account; stored in the EventBridge schema registry lambda-testevent-schemas, which needs schema registry permissions). sam remote test-event manages the same shareable events from the CLI.

AWS CLIaws lambda invoke with --payload. CLI version 2 expects payloads in base64 by default, so pass --cli-binary-format raw-in-base64-out for plain JSON.

API Gateway console TestInvokes a REST API method directly (with chosen path, query, headers, body and stage variables) and shows the integration request, response and logs. It really calls the backend, so a test DELETE really deletes. HTTP APIs don't have it.

Invoke the deployed function with a JSON payload (AWS CLI v2) 
aws lambda invoke \
  --function-name order-api:test \
  --cli-binary-format raw-in-base64-out \
  --payload file://events/order.json \
  out.json
cat out.json

In Python handlers, Powertools' event source data classes (for example APIGatewayProxyEventV2, SQSEvent, S3Event) give typed access to these fields, which also makes test events easier to get right.

A proxy-integration function tested with a hand-written event like {"customerId": "c-9"} passes in the console and then fails behind API Gateway, where the order arrives as a string in body. Test with the real event shape for the trigger.

Test environments

Skill 3.2.4Create and configure application environments (for example, Lambda aliases, container image tags, AWS Amplify branches, AWS Copilot environments, API Gateway APIs).

Tests need somewhere that looks like production but isn't: same code and infrastructure, different data, endpoints and permissions. The strongest isolation is a separate AWS account per environment (dev, test, prod), deployed from the same templates with different parameters. Within an account, these mechanisms separate environments:

MechanismHow it separates environments
Separate stacksThe same SAM or CDK app deployed as orders-dev, orders-test, orders-prod, with per-environment parameters (samconfig.toml sections, CDK stage props)
Lambda aliasesdev, test and prod aliases point at different versions of one function; weighted aliases send a slice of traffic to a new version for testing
Container image tagsEach environment runs a specific tag or digest; an image is promoted by deploying the tag that passed tests, not by rebuilding
API Gateway stages or APIsA stage per environment with its own stage variables, or a separate API per environment for full isolation
Amplify branchesEach connected Git branch deploys its own front end and backend; pull request previews give each change a temporary URL
Ephemeral environmentsA stack per feature branch or pull request, created by the pipeline and deleted after merge (the CDK Toolkit Library is designed for this)

The exam guide names AWS Copilot environments: in the Copilot CLI, an environment held the shared networking, ECS cluster and load balancer that services in it used (copilot env init, copilot svc deploy --env test). The Copilot CLI reached end of support on June 12, 2026 and its repository is archived. AWS recommends Amazon ECS Express Mode (since November 2025: give it a container image and roles, and it creates a Fargate service with a load balancer, HTTPS URL and auto scaling, all editable in your account) or CDK L3 constructs.

"Test a new function version on 10% of traffic" points to a weighted alias. "Promote exactly what was tested" points to deploying the same image tag or digest, or the same Lambda version. "Preview each front-end pull request" points to Amplify previews. "Strongest isolation between test and production" points to separate accounts.

AI tools for testing

Skill 3.2.5Use AWS AI tools to generate tests and automate repetitive testing workflows (for example, automated test execution, test result analysis, regression testing automation, test coverage).

Kiro

Generating testsKiro writes unit tests alongside code it generates, or on request for existing code. In a spec, tasks include the tests for each requirement, so coverage follows the requirements.

Property-based testingFrom the spec's requirements, Kiro derives properties that must always hold ("an order total is never negative", "cancelling twice has the same result as once") and generates hundreds of random inputs to try to break them, shrinking any failure to the smallest example. It's strong evidence the code matches the spec, not a proof.

Automating with hooksHooks run an agent prompt or a shell command on events: run the tests for a file when it's saved, or run the suite after each task completes, so regressions surface immediately.

In pipelinesKiro CLI runs headless (no interactive session, authenticated with an API key) in CI to generate tests, review changes or triage failing builds.

Hooks are saved as JSON files in .kiro/hooks/, usually created from Kiro's hook panel by describing what should happen ("when a Python file under src/ is saved, run the tests that cover it"). A hook's action is either an agent prompt or a plain shell command, such as pytest, which costs no AI credits.

Amazon Q Developer stopped accepting new sign-ups on May 15, 2026, and its IDE plugins reach end of support on April 30, 2027; Amazon Q Developer for GitHub ends on January 30, 2027, replaced by the Kiro GitHub App. Use Kiro for test generation.

Test execution and results in CodeBuild

CodeBuild runs the test commands from buildspec.yml and, with a reports section, turns result files into test reports (pass and fail counts, durations, failure messages) and coverage reports (line and branch coverage) in the console. Supported formats include JUnit XML (the default), Cucumber JSON, NUnit, TestNG and Visual Studio TRX for tests, and JaCoCo, Cobertura, Clover, SimpleCov and LCOV for coverage. Reports are kept for 30 days in a report group.

buildspec.yml with test and coverage reports 
version: 0.2
phases:
  install:
    commands:
      - pip install -r requirements.txt
  build:
    commands:
      - pytest --cov=src --cov-report=xml
        --junitxml=reports/junit.xml
reports:
  unit-tests:
    files: ["junit.xml"]
    base-directory: reports
    file-format: JUNITXML
  coverage:
    files: ["coverage.xml"]
    file-format: COBERTURAXML

The pytest command continues on the next line as part of one YAML scalar. A pipeline can fail the build on test failures, and the reports show which tests regressed between builds.

Regression in productionCloudWatch Synthetics canaries run scripted checks against APIs and web pages on a schedule, catching regressions after deployment.

"Generate unit tests for existing code" points to Kiro. "Run tests automatically when files change" points to Kiro hooks. "View test results and coverage for each build" points to CodeBuild report groups. "Continuously check the live API" points to Synthetics canaries.

Key takeaways

  • Layers of tests: unit (mocked AWS), infrastructure (templates), integration (real services in a test environment).
  • SAM: local invoke, local start-api, local start-lambda, local generate-event, remote invoke, remote test-event, sync --watch, validate --lint; local runs need Docker.
  • CDK: Template.fromStack fine-grained assertions and snapshot tests; cdk diff; integ tests. CloudFormation: validate-template (syntax only), cfn-lint, Guard, pre-deployment validation, change sets, Hooks.
  • Mocks: API Gateway MOCK integrations (REST) with mapping templates; moto, Stubber and aws-sdk-client-mock in unit tests; Step Functions TestState with mocks; TestEventPattern.
  • Test events must match the trigger's shape (proxy events carry body as a string); private or shareable console events; CLI v2 needs --cli-binary-format raw-in-base64-out.
  • Environments: separate accounts or stacks, Lambda aliases, image tags or digests, API stages, Amplify branches, ephemeral stacks. Copilot CLI is out of support; ECS Express Mode replaces it.
  • AI: Kiro generates unit and property-based tests and runs them through hooks or headless CLI; CodeBuild reports show results and coverage; Q Developer is winding down.
