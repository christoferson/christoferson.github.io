Overview

Task 1.4

Design and implement vector store solutions.

A vector store holds chunks of your documents with their embeddings (numeric vectors that capture meaning) and metadata, and returns the chunks closest to a query. This page is about the store: which one, how it's organized, how it scales and how it stays in sync. Task 1.5 covers how content is chunked, embedded and searched.

The examples use the retailer's support knowledge: product manuals in S3, help articles in a wiki, and policies in SharePoint.

Vector store architectures

Skill 1.4.1Create advanced vector database architectures specifically for FM augmentation to enable efficient semantic retrieval beyond traditional search capabilities (for example, by using Amazon Bedrock Knowledge Bases for hierarchical organization, Amazon OpenSearch Service with the Neural plugin for Amazon Bedrock integration for topic-based segmentation, Amazon RDS with Amazon S3 document repositories, Amazon DynamoDB with vector databases for metadata and embeddings)

Amazon Bedrock Knowledge Bases

Managed RAG

A knowledge base connects to your documents, parses and chunks them, creates embeddings, stores them, and answers Retrieve (return chunks) and RetrieveAndGenerate (return an answer with citations) calls. It comes in two forms:

  • Managed knowledge base (added in March 2026 and generally available since June 2026, now AWS's recommended default): Bedrock runs the vector store, the embedding model and a reranker for you, scales automatically, always uses hybrid (keyword plus semantic) search, filters results by each document's access permissions, and has built-in connectors (S3, SharePoint, Confluence, web crawler, Google Drive, OneDrive, custom) with sync schedules.
  • Customer-managed knowledge base: you choose and run the vector store, and choose the embedding model and chunking. Use it when you need a specific store, embedding model or index design.

Other knowledge base types query structured data (generating SQL against a data warehouse) or a graph (Neptune Analytics, for GraphRAG over connected entities).

Amazon Kendra entered maintenance on June 30, 2026 and closed to new customers on July 30, 2026; AWS recommends managed knowledge bases instead. From September 30, 2026, customer-managed knowledge bases can't add new Confluence, SharePoint, Salesforce or web crawler connectors (existing ones keep working); use a managed knowledge base, or export the content to S3.

Hybrid search through a knowledge base works only on Aurora, OpenSearch Serverless and MongoDB; on other stores it falls back to semantic search.

Other building blocks

OpenSearch with Bedrock models (the Neural plugin)

Outside knowledge bases, OpenSearch can call Bedrock embedding models itself through ML Commons connectors: you register a connector (signed with an IAM role OpenSearch assumes) and a model, then an ingest pipeline embeds documents as they're indexed and neural search embeds queries, so applications send plain text. The OpenSearch console's integrations page has CloudFormation templates that set this up for Amazon Titan and Cohere embedding models. Separate indexes per topic (or per product line) give topic-based segmentation: each query searches only the relevant segment.

RDS with S3 document repositories

A common pattern keeps the original documents in S3 (cheap, versioned) and a relational table in RDS or Aurora with each document's metadata, version, owner and S3 key, plus the vectors themselves with pgvector. Retrieval returns chunks with their document IDs; the application joins to the metadata and links to the original in S3.

DynamoDB for metadata, not vector search

DynamoDB has no vector search. Use it for what it's good at: document metadata, chunk-to-document mappings, processing state and conversation history. For vector search over DynamoDB data, the zero-ETL integration with OpenSearch (through OpenSearch Ingestion) copies an initial export and then streams changes from DynamoDB Streams into an OpenSearch index.

Other databases with vector search

DocumentDB, MemoryDB and ElastiCache for Valkey also support vector search. In-memory stores suit low-latency uses such as a semantic cache of previous answers (Task 4.1) or agent memory.

Aurora PostgreSQL table for a knowledge base (SQL) 
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE kb.manuals (
  id uuid PRIMARY KEY,
  embedding vector(1024),
  chunks text,
  metadata json,
  custom_metadata jsonb
);
-- similarity search
CREATE INDEX ON kb.manuals
  USING hnsw (embedding vector_cosine_ops)
  WITH (ef_construction = 256);
-- keyword part of hybrid search
CREATE INDEX ON kb.manuals
  USING gin (
    to_tsvector('simple', chunks));
-- metadata filters
CREATE INDEX ON kb.manuals
  USING gin (custom_metadata);

The knowledge base also needs the RDS Data API enabled and database credentials in Secrets Manager. Field mappings can't be changed after the knowledge base is created.

Metadata frameworks

Skill 1.4.2Develop comprehensive metadata frameworks to improve search precision and context awareness for FM interactions (for example, by using S3 object metadata for document timestamps, custom attributes for authorship information, tagging systems for domain classification)

Why metadata matters

Similarity alone can't tell the 2026 returns policy from the 2023 one, or a kettle manual from a toaster manual that uses the same words. Metadata lets retrieval filter before ranking (only current documents, only this product line, only content this user may see) and gives the model context to cite (title, date, author).

A metadata scheme

Metadata in a knowledge base

The sidecar file

For an S3 data source, put a file named <document>.metadata.json next to each document (up to 10 KB). Attributes can be simple key-value pairs or typed (string, number, boolean, string list). Setting includeForEmbedding on an attribute also adds it to the text that gets embedded, which helps similarity (for example, the product name). The knowledge base doesn't read S3 object tags or user metadata itself, so a pipeline that already tags objects should write these files from them.

kettle-k200-manual.pdf.metadata.json 
{
  "metadataAttributes": {
    "product_line": {
      "value": {
        "type": "STRING",
        "stringValue": "kitchen"
      },
      "includeForEmbedding": true
    },
    "author": "Support Docs Team",
    "published": 20260915,
    "doc_type": "manual"
  }
}

Filtering at retrieval

Filters use operators such as equals, notEquals, greaterThan and lessThan (numbers), in and notIn, stringContains, listContains and startsWith (support varies by store; OpenSearch Serverless supports the most), combined with andAll and orAll. A knowledge base can also build the filter itself from the user's question (implicit filtering).

Retrieve current kitchen manuals only (Python) 
kb = boto3.client("bedrock-agent-runtime")

flt = {"andAll": [
    {"equals": {"key": "product_line",
                "value": "kitchen"}},
    {"greaterThan": {"key": "published",
                     "value": 20250101}},
]}
resp = kb.retrieve(
    knowledgeBaseId=KB_ID,
    retrievalQuery={
        "text": "How do I descale it?"},
    retrievalConfiguration={
        "vectorSearchConfiguration": {
            "numberOfResults": 5,
            "filter": flt}},
)

Filters fail silently or error if the store isn't set up for them: OpenSearch filter fields must be keyword type, Aurora needs the custom_metadata JSONB column indexed, and S3 Vectors and managed knowledge bases don't support startsWith or stringContains. Store dates as numbers if you need ranges.

High-performance stores

Skill 1.4.3Implement high-performance vector database architectures to optimize semantic search performance at scale for FM retrieval (for example, by using OpenSearch sharding strategies, multi-index approaches for specialized domains, hierarchical indexing techniques)

OpenSearch at scale

Vector index basics

Vectors are stored in knn_vector fields and indexed with HNSW graphs using the faiss engine (the one Bedrock requires; nmslib is deprecated). HNSW graphs live in memory, so memory is usually the limit: watch the KNNGraphMemoryUsage metric. Ways to fit more: quantization (FP16 or binary vectors, or the compression settings of newer serverless vector collections) and disk-based vector search, trading a little recall for much less memory. GPU-accelerated index builds make indexing large collections faster and cheaper.

Sharding

  • Size shards at about 10 to 30 GiB when search latency matters (30 to 50 GiB for write-heavy indexes).
  • Primary shards are roughly (data plus growth) times 1.1, divided by the target shard size, and are hard to change later: decide before indexing.
  • Add replicas for search throughput and availability; spread shards evenly across data nodes and Availability Zones.

Multiple indexes

Separate indexes per domain (manuals, policies, help articles) let each have its own mapping, embedding model, shard count and refresh settings, and let queries target only what's relevant, which is faster and more precise. An alias can group them when a query really needs all of them.

One domain index with a filterable field (OpenSearch) 
PUT manuals-kitchen
{
  "settings": {
    "index.knn": true,
    "number_of_shards": 3,
    "number_of_replicas": 1
  },
  "mappings": {"properties": {
    "embedding": {
      "type": "knn_vector",
      "dimension": 1024,
      "method": {"name": "hnsw",
        "engine": "faiss",
        "space_type": "l2"}},
    "text": {"type": "text"},
    "product": {"type": "keyword"}
  }}
}

Hierarchical organization

Small chunks to find, large chunks to answer

Hierarchical chunking in a knowledge base stores small child chunks for precise matching and returns their larger parent chunk as context. It is also a storage decision: parents add data per vector, and on S3 Vectors large parents can exceed the per-vector metadata limit. Hierarchy can also be applied at the index level: a summary index of whole documents to pick candidates, then a detailed index of their chunks. Chunking strategies are compared in Task 1.5.

"Search latency grows as the collection grows" points to shard sizing, replicas, quantization, and splitting into domain indexes. "Billions of vectors at the lowest cost, latency isn't critical" points to S3 Vectors. "High query rate on that data" points to OpenSearch (S3 Vectors data can be exported to it).

Direct ingestion to a custom data source

A custom data source receives documents through IngestKnowledgeBaseDocuments (up to 25 per call) as inline text, bytes or an S3 location, and never needs a sync; DeleteKnowledgeBaseDocuments removes them. That suits a wiki connector that pushes each page when it changes.

Push one wiki page into the knowledge base (Python) 
ba = boto3.client("bedrock-agent")

doc = {"content": {
    "dataSourceType": "CUSTOM",
    "custom": {
        "customDocumentIdentifier":
            {"id": "wiki-4411"},
        "sourceType": "IN_LINE",
        "inlineContent": {
            "type": "TEXT",
            "textContent":
                {"data": page_text}},
    }}}
ba.ingest_knowledge_base_documents(
    knowledgeBaseId=KB_ID,
    dataSourceId=CUSTOM_DS_ID,
    documents=[doc],
)

PermissionsContent from systems with access controls needs those controls at retrieval, or an assistant can reveal documents a user couldn't open. Managed knowledge bases filter by each connector's permissions; with a customer-managed store, record access groups as metadata and filter on the caller's groups (Task 3.2).

Keeping stores current

Skill 1.4.5Design and deploy data maintenance systems to ensure that vector stores contain current and accurate information for FM augmentation (for example, by using incremental update mechanisms, real-time change detection systems, automated synchronization workflows, scheduled refresh pipelines)

How knowledge base sync works

  • Incremental: after the first full sync, an ingestion job (StartIngestionJob) processes only added, changed and deleted documents. Changed documents are re-ingested; deleted ones are removed (or kept, if the data deletion policy is RETAIN).
  • Metadata-only changes (just the .metadata.json file) are applied without re-embedding, in most cases.
  • Job status and per-document statistics come from GetIngestionJob; failed documents are listed, so a pipeline can alert on them.
  • Don't run direct ingestion and an ingestion job on the same data source at the same time.

Choosing the refresh pattern

NeedPattern
Daily or weekly refreshManaged knowledge base: a built-in sync schedule. Customer-managed: EventBridge Scheduler invoking Lambda that calls StartIngestionJob
Near real timeS3 Event Notifications or EventBridge on each change, then direct ingestion (or a debounced sync)
Changes in a databaseDynamoDB Streams (zero-ETL to OpenSearch, or Lambda writing documents)
Multi-step refresh (extract, clean, enrich, sync, verify)Step Functions orchestrating each step, with validation (Task 1.3)
New embedding model or chunking strategyA full re-index into a new data source or index, switched over when complete; chunking can't be changed on an existing data source
Scheduled sync for a customer-managed knowledge base (Lambda) 
import boto3

ba = boto3.client("bedrock-agent")

# invoked nightly by EventBridge Scheduler
def handler(event, context):
    job = ba.start_ingestion_job(
        knowledgeBaseId=KB_ID,
        dataSourceId=S3_DS_ID,
    )
    info = job["ingestionJob"]
    return info["ingestionJobId"]

Changing the embedding model means every stored vector is incompatible with new query vectors: you must re-embed everything, not just new documents. Build the new index alongside the old and switch when it's complete.

Key takeaways

  • Bedrock managed knowledge bases (2026) are the default: managed store, embeddings, reranking, hybrid search, permission filtering, connectors and schedules. Customer-managed knowledge bases let you choose the store; Kendra is closed to new customers.
  • Stores: OpenSearch Serverless (general purpose, best filtering), OpenSearch clusters (control), Aurora pgvector (with relational data), S3 Vectors (cheapest at huge scale), Neptune Analytics (GraphRAG). DynamoDB holds metadata; zero-ETL brings its data to OpenSearch for vector search.
  • Metadata (.metadata.json sidecars: topic, numeric dates, author, audience) enables filters with equals, ranges, in and more; check each store's filter support and field types.
  • Scale OpenSearch with right-sized shards (10 to 30 GiB for search), replicas, faiss HNSW, quantization or disk-based search, GPU builds, and separate domain indexes.
  • Connect sources with managed connectors, S3 data sources, or Lambda pipelines and direct ingestion to custom data sources; carry access permissions into retrieval.
  • Keep current with incremental ingestion jobs on a schedule, event-driven direct ingestion, Streams for databases, and full re-indexing when the embedding model or chunking changes.
