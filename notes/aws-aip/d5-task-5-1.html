Overview

Task 5.1

Implement evaluation systems for GenAI.

A classifier is right or wrong, so accuracy on a labeled test set settles most questions. A generative model writes free text: many different answers can be correct, a fluent answer can be false, and the same prompt can give different answers each time. Evaluation therefore uses several measures at once (is it relevant, true, grounded, consistent, well written, safe, fast and affordable?) and several judges (algorithms, another model, and people).

The examples follow the retailer from earlier tasks: a customer support assistant that answers product questions from a knowledge base of manuals and handles orders and returns through tools, and a nightly job that summarizes support tickets. The team keeps a golden set of 300 real questions with approved answers.

Assessment frameworks

Skill 5.1.1Develop comprehensive assessment frameworks to evaluate the quality and effectiveness of FM outputs beyond traditional ML evaluation approaches (for example, by using metrics for relevance, factual accuracy, consistency, and fluency)

The quality dimensions

DimensionQuestion it answersHow it's measured
RelevanceDoes it address what was asked?LLM judge (relevance, helpfulness); embedding similarity between question and answer
Factual accuracyIs it true?Comparison with a reference answer (judge correctness, F1, BERTScore); knowledge benchmarks
Faithfulness (groundedness)Is it supported by the provided context?LLM judge faithfulness; guardrail contextual grounding score
CompletenessDoes it cover everything needed?LLM judge against a reference
ConsistencySame answer to the same or reworded question?Repeated runs and perturbed prompts (robustness); similarity of the answers
Fluency and coherenceIs it well written and logically ordered?LLM judge (coherence, style and tone)
SafetyHarmful, biased, or wrongly refused?Toxicity score; judge harmfulness, stereotyping, refusal

Pick the few that matter for the use case and set a target for each. For the support assistant: faithfulness and correctness first (a wrong warranty answer costs money), then completeness and helpfulness, then style. For ticket summaries: completeness and faithfulness (no invented details), then conciseness. Add business-specific measures as custom metrics, such as "follows the refund policy" or "uses the brand's tone".

Kinds of evaluator

Algorithmic metricsCheap, repeatable and fast: exact match, F1 overlap with a reference, BERTScore (similarity of meaning using embeddings), word error rate, toxicity classifiers. They reward wording close to the reference and miss correct answers phrased differently.

LLM-as-a-judgeA strong model scores each response against a rubric and explains its score. Close to human judgment on many criteria at a fraction of the cost, but it can be biased (toward longer answers, its own style, or the first option shown) and must itself be checked against human ratings.

Human evaluationThe reference standard for subtle quality, tone and domain correctness; slow and costly, so used for calibration, high-stakes changes and samples.

A high BLEU, ROUGE or F1 score doesn't mean an answer is correct, and a low one doesn't mean it's wrong: these count word overlap. For open-ended answers, use a judge model or people, with reference answers where you have them.

Model evaluation

Skill 5.1.2Create systematic model evaluation systems to identify optimal configurations (for example, by using Amazon Bedrock Model Evaluations, A/B testing and canary testing of FMs, multi-model evaluation, cost-performance analysis to measure token efficiency, latency-to-quality ratios, and business outcomes)

Amazon Bedrock evaluations

Bedrock runs evaluation jobs against Bedrock models (foundation, custom, imported, Marketplace, Provisioned Throughput, prompt routers) or against responses you generated anywhere else (bring your own inference, BYOI). Results go to S3 and to a report card in the console.

Job typeHow it scoresUse it for
ProgrammaticAlgorithms: accuracy, robustness to small prompt changes, toxicity, per task type (general generation, summarization, question answering, classification)A quick, cheap first screen of candidate models, on built-in or your own datasets
Model as a judgeA judge model you choose scores built-in metrics (correctness, completeness, faithfulness, helpfulness, coherence, relevance, following instructions, style and tone, harmfulness, stereotyping, refusal) and up to 10 custom metricsComparing models and prompts on open-ended answers
HumanYour own work team rates or compares up to two models' responsesSubtle quality, final decisions, calibrating the judge
RAGJudge metrics for retrieval and for retrieve-and-generateKnowledge bases or any RAG system (see below)

A custom dataset is a JSONL file in S3 with up to 1,000 prompts. Each line has a prompt, an optional referenceResponse (the approved answer, used by correctness and completeness), and an optional category so scores are broken down by type of question. For BYOI, each line also carries the response to score:

One judge-dataset record with your own response (JSONL) 
{"prompt": "How long is the K200
  warranty?",
 "referenceResponse": "Two years
  from the date of purchase.",
 "category": "warranty",
 "modelResponses": [{
   "response": "The K200 has a
    two-year warranty.",
   "modelIdentifier": "support-v7"}]}

Wrapped for reading; in the file each record is one line and strings don't break. A BYOI job has one response per prompt and one modelIdentifier.

A model-as-a-judge job (Python) 
bedrock = boto3.client("bedrock")

ds = {"name": "support-golden",
      "datasetLocation": {"s3Uri": DATA}}
metrics = ["Builtin.Correctness",
           "Builtin.Completeness",
           "Builtin.Faithfulness",
           "Builtin.Helpfulness"]
judge = {"bedrockEvaluatorModels": [
    {"modelIdentifier": JUDGE_ID}]}
model = {"bedrockModel": {
    "modelIdentifier": MODEL_ID,
    "inferenceParams": PARAMS_JSON}}

bedrock.create_evaluation_job(
    jobName="support-v7-judge",
    roleArn=ROLE_ARN,
    applicationType="ModelEvaluation",
    evaluationConfig={"automated": {
        "datasetMetricConfigs": [{
            "taskType": "General",
            "dataset": ds,
            "metricNames": metrics}],
        "evaluatorModelConfig": judge}},
    inferenceConfig={"models": [model]},
    outputDataConfig={"s3Uri": OUT},
)

PARAMS_JSON is a JSON string of inference parameters such as the maximum tokens and temperature. For BYOI, replace bedrockModel with precomputedInferenceSource and its inferenceSourceIdentifier. The generating model and judge must be in the same Region.

Multi-model comparison and cost-performance

Run the same dataset and metrics against each candidate (one job per model), then put quality next to cost and speed. A model is only "better" for a purpose:

MeasureFrom
Quality score per metricEvaluation job results
Token efficiency (tokens per answer, cost per answer)Token counts in the job output or invocation logs, times the price
Latency-to-quality (for example correctness per second of p90 latency)Benchmarks under realistic load
Cost per acceptable answerCost per answer ÷ share of answers meeting the bar
Business outcomeResolution rate, escalations, conversion in an online test

Offline evaluation narrows the field; only live traffic shows business outcomes. The worked cost-per-acceptable-answer comparison is in Task 4.1.

A/B and canary testing

A/B testSplit live traffic between the current configuration and a candidate (for example 90/10) for long enough to compare business and quality metrics with confidence. Route with a feature flag (AWS AppConfig feature flags and experimentation), tag each request with its variant in requestMetadata, and compare per variant.

CanaryRelease the candidate to a small share of traffic first, watch alarms on errors, latency, guardrail interventions and online quality scores, then increase in steps or roll back. On SageMaker AI endpoints, deployment guardrails do this natively (blue/green with all-at-once, canary or linear traffic shifting and automatic rollback on CloudWatch alarms); shadow tests send a copy of live traffic to the candidate without returning its answers to users.

CloudWatch Evidently (feature flags and A/B experiments) was discontinued on October 17, 2025. Use AWS AppConfig feature flags and AppConfig experimentation for A/B tests and gradual rollouts.

"Compare several FMs on our own prompts with minimal effort" points to Bedrock evaluation jobs. "Score responses from a model hosted outside Bedrock" points to bring your own inference. "Compare on real user outcomes" points to an A/B test. "Release safely to a small share of traffic" points to a canary.

User-centered evaluation

Skill 5.1.3Develop user-centered evaluation mechanisms to continuously improve FM performance based on user experience (for example, by using feedback interfaces, rating systems for model outputs, annotation workflows to assess response quality)

Feedback interfaces

Users are the most direct judges, but they rarely leave feedback unless it costs one tap. Collect both kinds:

  • Explicit: thumbs up or down on each answer, an optional reason ("incorrect", "not helpful", "unsafe", "too long"), a free-text comment, or a 1-to-5 rating at the end of a conversation.
  • Implicit: the user copied the answer, asked the same thing again, asked for a human, abandoned the chat, or the ticket reopened. Implicit signals cover every conversation, not only the few who click.

Store feedback with the identifiers that link it to everything else: conversation ID, message ID, prompt version, model ID and variant. A simple design is an API Gateway route to a Lambda function that writes to DynamoDB and emits a metric:

Storing a rating linked to the response (Python) 
table = boto3.resource(
    "dynamodb").Table("feedback")

def handler(event, context):
    fb = json.loads(event["body"])
    table.put_item(Item={
        "conversation_id": fb["conv"],
        "message_id": fb["msg"],
        "rating": fb["rating"],
        "reason": fb.get("reason", ""),
        "prompt_version": fb["pv"],
        "model_id": fb["model"],
        "ts": int(time.time()),
    })
    return {"statusCode": 204}

Validate the fields and the caller in a real handler. The prompt version and model ID come from the response the client was shown, so each rating can be attributed to the configuration that produced it.

Rating systems

MethodGood for
Thumbs up or downHigh volume, low effort; a clear pass or fail
Likert scale (1 to 5)Degrees of quality on one criterion
Side-by-side comparison (choice or comparative Likert)Deciding between two models or prompts; people judge relative quality more reliably than absolute
RankingOrdering several candidate answers

Bedrock human evaluation jobs offer these same methods (thumbs, individual Likert, comparison Likert, choice and ordinal rank) for a work team you bring: create a team in the console, up to 50 workers, with a set number of workers per prompt, at a price per completed task.

Annotation workflows

  1. SamplePick conversations to review: a random sample, plus every thumbs-down, escalation and low judge score.
  2. AnnotateDomain experts label each answer against a written guide (correct, partly correct, wrong; grounded or not; error type such as wrong product, outdated policy, invented detail) and write the correct answer.
  3. AgreeHave two people label a share of items and measure agreement; unclear guidelines show up as disagreement.
  4. Use the labelsAdd corrected examples to the golden set, calibrate the LLM judge against the human labels, and feed error types back to prompt and retrieval fixes.

Amazon SageMaker Ground Truth and Amazon Augmented AI (A2I), AWS's labeling and human review services, are no longer open to new customers. For annotation, use Bedrock human evaluation jobs with your own team, or a small review application (for example Step Functions with a task token, DynamoDB and a web page).

Quality assurance

Skill 5.1.4Create systematic quality assurance processes to maintain consistent performance standards for FMs (for example, by using continuous evaluation workflows, regression testing for model outputs, automated quality gates for deployments)

Regression testing

Anything can change the answers: a prompt edit, a new model version, a different chunk size, a guardrail tweak, a new tool description. A regression suite is the golden set plus every confirmed past failure, run on every change and compared with the last accepted results. Look at averages and at individual items that got worse: an average can stay flat while the refund questions break.

  • Keep test cases versioned with the prompts (Bedrock Prompt Management versions or files in the repository).
  • Fix what can be fixed: low temperature for test runs, the same judge model and rubric between runs, so differences come from the change.
  • Run cheap checks first (format, length, required phrases, JSON schema), then the judge job.

Automated quality gates

Bedrock evaluation jobs don't pass or fail a release on their own; the pipeline does. A CodePipeline or GitHub Actions stage starts the job, waits for it, reads the scores and fails the build if any metric falls below its threshold:

  1. StartCall CreateEvaluationJob with the regression dataset and the candidate prompt or model.
  2. WaitPoll GetEvaluationJob until the status is Completed (or use a Step Functions wait loop).
  3. ScoreRead the output JSONL from S3 and average each metric.
  4. DecideCompare with absolute thresholds and with the current production scores; fail on any drop beyond tolerance.
Gate on evaluation scores (Python) 
THRESHOLDS = {
    "Builtin.Correctness": 0.85,
    "Builtin.Faithfulness": 0.90,
    "Builtin.Helpfulness": 0.80,
}

def averages(lines):
    totals, counts = {}, {}
    for line in lines:
        rec = json.loads(line)
        key = "automatedEvaluationResult"
        for s in rec[key]["scores"]:
            name = s["metricName"]
            totals[name] = (
                totals.get(name, 0)
                + s["result"])
            counts[name] = (
                counts.get(name, 0) + 1)
    return {n: totals[n] / counts[n]
            for n in totals}

scores = averages(read_output(OUT))
failed = {m: scores.get(m, 0)
          for m, t in THRESHOLDS.items()
          if scores.get(m, 0) < t}
if failed:
    sys.exit(f"quality gate: {failed}")

read_output stands for code that lists and reads the job's output JSONL files under the S3 prefix. Judge scores are normalized between 0 and 1.

Continuous evaluation

Gates catch problems your changes cause; continuous evaluation catches problems that arrive on their own: user questions shifting to a new product, documents going stale, a managed model behaving differently. Run the regression suite on a schedule (EventBridge Scheduler), score a sample of live traffic (AgentCore Evaluations online mode, or exported conversations as BYOI jobs), and alarm on trends. The monitoring side is in Task 4.3.

Multiple perspectives

Skill 5.1.5Develop comprehensive assessment systems to ensure thorough evaluation from multiple perspectives for FM outputs (for example, by using RAG evaluation, automated quality assessment with LLM-as-a-Judge techniques, human feedback collection interfaces)

RAG evaluation

A RAG answer can fail in two places, so evaluate both. Bedrock RAG evaluation jobs work with a knowledge base or, through BYOI, with any RAG system:

JobMetricsFinds
Retrieve onlyContext relevance (are the retrieved passages relevant to the question?); context coverage (do they contain everything in the reference answer?)Retrieval problems: chunking, embeddings, search settings
Retrieve and generateCorrectness, completeness, helpfulness, logical coherence, faithfulness, citation precision and citation coverage, harmfulness, stereotyping, refusalGeneration problems: ignoring context, inventing details, citing the wrong passage

Reading the combination: low context relevance means fix retrieval first; high context relevance with low faithfulness means the model isn't sticking to the passages (fix the prompt or model); good faithfulness with low correctness means the documents themselves are wrong or out of date.

One RAG evaluation record (JSONL) 
{"conversationTurns": [{
  "prompt": {"content": [{"text":
    "Can I descale the K200 with
     vinegar?"}]},
  "referenceResponses": [{"content": [
    {"text": "Yes: half water, half
     white vinegar, then rinse
     twice."}]}]
}]}

Wrapped for reading. For BYOI, each turn also has an output: for retrieve-only jobs the retrieved results; for retrieve-and-generate jobs the answer text and the retrieved passages.

LLM-as-a-judge done well

  • Write a rubric. Built-in metrics come with tested prompts. For custom metrics, give the judge a role, the task, explicit criteria and a rating scale with a definition for each value, then the input variables {{prompt}}, {{prediction}} and {{ground_truth}}.
  • Prefer references. Judging against an approved answer is more reliable than judging from the judge's own knowledge.
  • Use a strong, different judge. A judge from another model family reduces self-preference; keep the judge fixed between runs you compare.
  • Calibrate. Compare judge scores with human labels on a sample and adjust the rubric until they agree.
  • Read the explanations. The judge explains each score; low scores with reasons are the fastest route to the fix.
A custom judge metric (JSON, in customMetricConfig) 
{"customMetricDefinition": {
  "name": "RefundPolicy",
  "instructions": "You check support
    answers against the refund policy.
    ... Answer: {{prediction}}
    Reference: {{ground_truth}}",
  "ratingScale": [
    {"definition": "Follows policy",
     "value": {"floatValue": 1}},
    {"definition": "Partly",
     "value": {"floatValue": 0.5}},
    {"definition": "Violates policy",
     "value": {"floatValue": 0}}]
}}

Wrapped for reading; the instructions are one string up to 5,000 characters, with the criteria where the ellipsis is. Add the metric's name to metricNames; a job can have up to 10 custom metrics. Scale values must be all numbers or all strings.

Human feedback

People see what metrics miss: an answer that is correct but cold, or technically grounded but useless. Use human evaluation jobs for side-by-side comparisons before major changes, end-user feedback continuously, and expert annotation for calibration (above). The three perspectives check each other: when the judge and users disagree, find out why.

Retrieval testing

Skill 5.1.6Implement retrieval quality testing to evaluate and optimize information retrieval components for FM augmentation (for example, by using relevance scoring, context matching verification, retrieval latency measurements)

Relevance scoring

Two ways to score retrieval: with a judge (the context relevance and coverage metrics above, no labels needed beyond reference answers) or with labels, where for each test question you record which chunks or documents are relevant. Labels allow the classic information retrieval metrics:

MetricMeaning
Recall@kShare of the relevant chunks found in the top k; the key one for RAG, since the model can't use what wasn't retrieved
Precision@kShare of the top k that are relevant; low precision means noisy, longer prompts
Hit rate@kShare of questions with at least one relevant chunk in the top k
MRRMean of 1 ÷ rank of the first relevant result; rewards putting the best chunk first
NDCG@kRank-weighted relevance, allowing graded labels (highly relevant, somewhat relevant)

Context matching and latency

Context matching verification checks that the retrieved text actually contains what the answer needs: the expected document IDs appear, the key fact ("two years") is present in a retrieved chunk, and metadata filters returned the right product. Measure retrieval latency in the same run, because a change that adds a reranker or query decomposition improves relevance at a cost in time. Bedrock evaluation jobs don't report latency, so time the calls yourself:

Recall, MRR and latency for a knowledge base (Python) 
kb = boto3.client("bedrock-agent-runtime")

def run(case, k=5):
    query = {"text": case["q"]}
    cfg = {"vectorSearchConfiguration":
           {"numberOfResults": k}}
    t0 = time.perf_counter()
    r = kb.retrieve(
        knowledgeBaseId=KB_ID,
        retrievalQuery=query,
        retrievalConfiguration=cfg)
    ms = (time.perf_counter() - t0) * 1000
    got = []
    for x in r["retrievalResults"]:
        loc = x["location"]["s3Location"]
        got.append(loc["uri"])
    want = set(case["relevant"])
    found = want & set(got)
    recall = len(found) / len(want)
    rr = 0.0
    for rank, uri in enumerate(got, 1):
        if uri in want:
            rr = 1 / rank
            break
    return recall, rr, ms

Each test case lists its question and the S3 URIs of the documents that answer it. Average recall and reciprocal rank over the cases, and report p50 and p95 latency. Compare settings (chunking, number of results, hybrid search, reranking) on the same cases. The tuning options themselves are in Task 1.5.

Agent evaluation

Skill 5.1.7Develop agent performance frameworks to ensure that agents perform tasks correctly and efficiently (for example, by using task completion rate measurements, tool usage effectiveness evaluations, Amazon Bedrock Agent evaluations, reasoning quality assessment in multi-step workflows)

An agent's final answer can be right after a wasteful path, or wrong because of one bad tool call five steps earlier. Evaluate at three levels: the whole session (did it achieve the goal?), each turn (was the response good?), and each tool call (right tool, right arguments?).

Amazon Bedrock AgentCore Evaluations

AgentCore Evaluations (generally available since March 2026) scores agent traces in OpenTelemetry format, from agents on AgentCore Runtime or elsewhere (for example Strands or LangGraph instrumented with ADOT). Its built-in evaluators are LLM judges at three levels:

LevelBuilt-in evaluators
SessionGoal success rate (did the agent accomplish what the user wanted, optionally checked against assertions)
Trace (turn)Correctness, faithfulness, helpfulness, coherence, conciseness, instruction following, response relevance, harmfulness, stereotyping, refusal
ToolTool selection accuracy and tool parameter accuracy

With ground truth you can add expected responses, session assertions ("the agent must check the order status before offering a refund") and an expected trajectory: the tool names the agent should call. Trajectory evaluators compare the actual tool sequence by exact order, in order, or any order, without a model call. You can also write custom evaluators, as an LLM judge with your own instructions or as code in a Lambda function.

ModeHow it runsUse it for
OnlineContinuously scores a sampled percentage of live sessions; results in CloudWatchProduction quality monitoring
On-demandThe Evaluate API scores given traces now, with ground truthTests in CI/CD
BatchAsynchronously scores many sessions from CloudWatch Logs; a failure-analysis evaluator groups root causesBaselines, before-and-after comparisons

The exam guide's "Amazon Bedrock Agent evaluations" refers to evaluating agents built with Bedrock Agents, now Bedrock Agents Classic and closed to new customers since July 30, 2026. Classic agents have traces (with each step's rationale, action and observation) but no dedicated evaluation feature; AWS's current agent evaluation service is AgentCore Evaluations. The open-source Strands Evals library offers similar test cases, output and trajectory evaluators, and simulated users for Strands agents.

The agent scorecard

Task completion rateShare of sessions where the goal was achieved (judge goal success, or a checkable end state such as "return created with the right order number").

Tool usage effectivenessSelection and parameter accuracy, tool error rate, and redundant calls (the same lookup twice).

EfficiencySteps, model calls, tokens and seconds per completed task; an agent that completes 95% of tasks in 14 steps may be worse than one that completes 93% in 4.

Reasoning qualityWhether each step follows from the previous observation: judge the trace step by step, and check trajectories against the expected path for multi-step workflows.

SafetyActions taken without the required confirmation, policy violations, refusals of valid requests.

"The agent's answers are fine but it calls the wrong APIs" points to tool selection and parameter accuracy. "Check the agent calls tools in the required order" points to trajectory evaluation with ground truth. "Monitor agent quality on live traffic" points to online evaluation with sampling.

Reporting

Skill 5.1.8Create comprehensive reporting systems to communicate performance metrics and insights effectively to stakeholders for FM implementations (for example, by using visualization tools, automated reporting mechanisms, model comparison visualizations)

Reports for each audience

EngineersPer-metric scores, score distributions, and the lowest-scoring examples with the judge's explanations. The Bedrock console report card shows a summary per metric, histograms and example explanations; the full per-prompt results are in S3.

Product ownersA comparison of candidates: quality per metric and per question category, cost per answer, latency, and the trade-off between them.

Leadership and riskTrends over releases, business outcomes (resolution rate, satisfaction), safety and compliance indicators, and open issues.

Automating it

  1. Land the resultsEvery evaluation job writes JSONL to S3 under a predictable prefix per job and model; a Glue crawler or table definition makes them queryable.
  2. QueryAthena joins scores with job metadata (model, prompt version, date, category) and cost from token counts.
  3. VisualizeAmazon Quick Sight dashboards (part of Amazon Quick, formerly QuickSight) for comparisons across models and releases; CloudWatch dashboards for live online-evaluation metrics and feedback rates.
  4. DistributeScheduled reports or a release note generated after each gated build, with the scores against thresholds and the biggest changes.

Good model comparison visuals: grouped bars per metric for each candidate, a scatter of quality against cost per answer (the efficient candidates sit at the top left), score distributions rather than averages alone, and a per-category heat map that shows where a model wins or loses.

Deployment validation

Skill 5.1.9Create deployment validation systems to maintain reliability during FM updates (for example, by using synthetic user workflows, AI-specific output validation for hallucination rates and semantic drift, automated quality checks to ensure response consistency)

FM updates happen even when you don't deploy code: a provider releases a new model version, a model you use reaches end of life, a prompt or knowledge base changes. Validate each one before it reaches all users.

Synthetic user workflows

Scripted end-to-end conversations that exercise real paths through the system: ask about the K200's warranty, then start a return, then change the delivery address. Run them against the candidate in a staging environment and, after release, on a schedule against production as canaries (CloudWatch Synthetics can run scripted checks against your API). For broader coverage, generate test conversations: AgentCore Evaluations' simulation feature drives multi-turn conversations with an LLM-played user who has a persona and a goal, and a model can draft varied test questions from your documents for people to review.

Hallucination and semantic drift checks

Hallucination rateRun the golden set and measure faithfulness and correctness; on live traffic, track contextual grounding interventions. For rules that can be written down (refund eligibility, warranty terms), Automated Reasoning checks in Bedrock Guardrails (generally available since August 2025) validate answers against a formal policy and return findings such as VALID, INVALID or SATISFIABLE; they detect rather than block, and don't support streaming.

Semantic driftCompare the candidate's answers on the golden set with the current production answers by meaning (embedding similarity, or a judge asked "do these say the same thing?"). Expected changes are fine; unexpected ones on questions that shouldn't change (policies, specifications) need review. The same comparison over time on production answers shows gradual drift.

Response consistency

Ask each golden question several times and in reworded forms, and compare the answers' meaning and key facts; Bedrock programmatic jobs measure robustness the same way by perturbing prompts (case changes, typos, numbers written as words, extra spaces). Low consistency on factual questions is a hallucination warning. A worked consistency check is in Task 4.3.

The release sequence

  1. Offline gateRegression suite, judge job, consistency and drift checks against thresholds.
  2. StagingSynthetic user workflows end to end, including tools and guardrails.
  3. Shadow or canaryA copy of traffic or a small share of users, with alarms on errors, latency, interventions and online quality scores.
  4. Full rolloutIncrease traffic in steps; keep the previous model or prompt version ready to switch back by flag or alias.

Switching to a newer version of the "same" model is a model change. Run the full validation: answers, length, refusals, parameter support and costs can all differ.

Key takeaways

  • Evaluate generative output on several dimensions (relevance, factual accuracy, faithfulness, completeness, consistency, fluency, safety) with algorithmic metrics, LLM judges and people; word-overlap scores alone mislead.
  • Bedrock evaluations: programmatic, model-as-a-judge (built-in plus up to 10 custom metrics), human (your own team, up to two models compared) and RAG jobs; up to 1,000 prompts; bring your own inference for models outside Bedrock.
  • Compare candidates on quality, tokens, latency and cost per acceptable answer offline, then on business outcomes with A/B tests; release with canaries or shadow tests (AppConfig for traffic splits; Evidently is discontinued).
  • Collect explicit and implicit user feedback linked to prompt version and model; annotate samples with experts; use labels to grow the golden set and calibrate the judge. Ground Truth and A2I are closed to new customers.
  • Quality gates are a pipeline step: run the job, read the S3 scores, fail below thresholds or on regressions. Re-run on a schedule and sample live traffic.
  • RAG: retrieve-only metrics (context relevance, coverage) locate retrieval problems; retrieve-and-generate metrics (faithfulness, citations, correctness) locate generation problems. With labels, use recall@k, precision@k, MRR and NDCG, and time the calls.
  • Agents: AgentCore Evaluations at session, trace and tool level, trajectory checks with ground truth, online, on-demand and batch modes. Track task completion, tool accuracy, steps and cost per task.
  • Report scores, distributions and trade-offs per audience; automate from S3 through Athena to dashboards. Validate every model or prompt update with regression, synthetic workflows, drift and consistency checks, then a staged rollout.
