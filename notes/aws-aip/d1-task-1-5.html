Overview

Task 1.5

Design retrieval mechanisms for FM augmentation.

Most bad RAG answers are retrieval failures: the right passage was never returned, or was buried under near-misses. Each stage of the retrieval path is a lever: chunking decides what can be found, embeddings decide what counts as similar, search settings and hybrid search decide what's returned, reranking decides the order, and query handling decides what's actually searched for. Task 1.4 covered the store itself; Task 5.2 covers troubleshooting retrieval.

Chunking

Skill 1.5.1Develop effective document segmentation approaches to optimize retrieval performance for FM context augmentation (for example, by using Amazon Bedrock chunking capabilities, Lambda functions to implement fixed-size chunking, custom processing for hierarchical chunking based on content structure)

The trade-off

Small chunks embed one idea each, so they match questions precisely, but may lack the context needed to answer. Large chunks carry context but blur several topics into one vector, so they match less precisely and use more of the prompt. The right size depends on the documents: short FAQ entries suit small chunks, long procedures suit larger or hierarchical ones.

Bedrock Knowledge Base strategies

StrategyHow it splitsUse for
DefaultAbout 300 tokens, keeping sentences wholeA sensible start
Fixed-sizeYour token size (up to 8,192) and overlap percentageUniform content; overlap keeps ideas that span a boundary
HierarchicalSmall child chunks inside larger parent chunks; search matches children, returns parentsLong, structured documents where answers need surrounding context
SemanticSplits where meaning changes between sentences, using a model (extra cost)Documents without clear structure that change topic often
No chunkingEach file is one chunkContent you've already split yourself
Custom (Lambda)Your function processes the parsed content after chunking (or does all chunking, with "no chunking")Splitting by your own structure (headings, sections), adding chunk-level metadata

The chunking strategy is fixed when a data source is created; changing it means a new data source and re-ingestion. Managed knowledge bases offer default, fixed-size and no chunking, with a managed parser. With parsed documents, a matching chunk inside a table can be replaced by the whole table or page (if small enough), so the model sees the complete table.

Hierarchical and semantic settings (data source vectorIngestionConfiguration) 
"chunkingConfiguration": {
  "chunkingStrategy": "HIERARCHICAL",
  "hierarchicalChunkingConfiguration": {
    "levelConfigurations": [
      {"maxTokens": 1500},
      {"maxTokens": 300}
    ],
    "overlapTokens": 60
  }
}
"chunkingConfiguration": {
  "chunkingStrategy": "SEMANTIC",
  "semanticChunkingConfiguration": {
    "maxTokens": 300,
    "bufferSize": 1,
    "breakpointPercentileThreshold": 90
  }
}

In the semantic example, bufferSize 1 compares each sentence together with its neighbours, and a threshold of 90 splits at the 10% least-similar boundaries; raise it for fewer, larger chunks.

"Answers miss steps that sit just outside the matched passage" points to hierarchical chunking or more overlap. "Retrieved chunks mix unrelated topics" points to smaller or semantic chunks. "Split manuals by their own section headings" points to a custom Lambda transformation.

Embeddings

Skill 1.5.2Select and configure optimal embedding solutions to create efficient vector representations for semantic search (for example, by using Amazon Titan embeddings based on dimensionality and domain fit, by evaluating performance characteristics of Amazon Bedrock embedding models, by using Lambda functions to batch generate embeddings)

Bedrock embedding models

ModelInputsDimensionsNotes
Amazon Titan Text Embeddings V2Text, up to 8,192 tokens1,024, 512 or 256Optimized for English; float or binary output; normalized by default
Amazon Titan Multimodal EmbeddingsText and images1,024, 384 or 256Search images by text or by image
Amazon Nova Multimodal EmbeddingsText, documents, images, video, audio in one space3,072, 1,024, 384 or 256Long media embedded in segments asynchronously
Cohere Embed (v3, v4)Text (v4 also images); multilingual versionsUp to 1,536 (v4)Separate input types for documents and queries; compressed int8 and binary outputs

Choosing

  • Modality and language: multimodal content needs a multimodal model; mixed-language content needs a multilingual one (Titan V2 is optimized for English).
  • Dimensions: fewer dimensions mean smaller storage, less memory and faster search, at a small cost in accuracy. Test 1,024 against 512 or 256 on your data before choosing.
  • Binary embeddings cut storage sharply (supported by OpenSearch stores), at some accuracy cost.
  • Same model both ways: documents and queries must be embedded with the same model and dimensions; with Cohere, set the document and query input types correctly.
  • Measure: a Bedrock RAG evaluation in retrieve-only mode scores context relevance and context coverage for each candidate (Task 5.1).
Embed a query with Titan V2 at 512 dimensions (Python) 
body = {"inputText": query,
        "dimensions": 512,
        "normalize": True}
resp = brt.invoke_model(
    modelId="amazon.titan-embed-text-v2:0",
    body=json.dumps(body),
)
out = json.loads(resp["body"].read())
vector = out["embedding"]

Generating embeddings in bulk

Embedding models are throttled by requests per minute, so millions of chunks need planning. For a one-off or nightly load, use batch inference (JSONL in S3, results to S3; supported for Titan and Nova embedding models). For continuous loads, a Lambda function consuming an SQS queue embeds chunks in parallel with bounded concurrency and backoff on throttling. A knowledge base does this for you during ingestion.

Switching embedding model or dimensions invalidates every stored vector: re-embed the whole corpus into a new index (Task 1.4).

Vector search settings

Skill 1.5.3Deploy and configure vector search solutions to enable semantic search capabilities for FM augmentation (for example, by using OpenSearch Service with vector search capabilities, Amazon Aurora with the pgvector extension, Amazon Bedrock Knowledge Bases with managed vector store functionality)

The settings that matter

SettingEffect
Distance metricCosine, dot product (inner product) or Euclidean (L2); match what the embedding model was trained for. With normalized vectors, cosine and dot product rank the same
HNSW m and ef_constructionGraph connectivity and build effort: higher means better recall, more memory and slower indexing; fixed when the index is built
ef_searchSearch effort per query: higher means better recall and more latency; can be tuned per query in pgvector
Number of results (k)More results raise the chance of including the answer but use more prompt and can add noise; knowledge bases allow 1 to 100 (default 5)

By store

Bedrock Knowledge Bases

The store's index is set up for you (or by you, to its required schema). At query time you set numberOfResults, a metadata filter, the search type (HYBRID or SEMANTIC, on stores that support hybrid) and reranking. Managed knowledge bases manage the index entirely.

OpenSearch

A knn_vector field with an HNSW method (faiss engine), a space type (l2 by default, or cosinesimil, innerproduct), and k-NN or neural queries (OpenSearch embeds the query text itself through its Bedrock connector). Set size as well as k, or you get k results per shard.

Aurora PostgreSQL with pgvector

Order by a distance operator: <=> cosine distance, <-> Euclidean, <#> negative inner product. The index must use the matching operator class (for example vector_cosine_ops for cosine).

Top 5 chunks by cosine similarity (SQL) 
-- more recall for this session
SET hnsw.ef_search = 100;

SELECT id, chunks,
       1 - (embedding <=> $1) AS score
FROM kb.manuals
WHERE custom_metadata
      @> '{"product_line": "kitchen"}'
ORDER BY embedding <=> $1
LIMIT 5;

Hybrid search and reranking

Skill 1.5.4Create advanced search architectures to improve the relevance and accuracy of retrieved information for FM context (for example, by using OpenSearch for semantic search, hybrid search that combines keywords and vectors, Amazon Bedrock reranker models)

Why hybrid

Semantic search finds passages with the same meaning in different words; keyword search finds exact terms that embeddings handle poorly: product codes (K200), error numbers, names, rare jargon. Hybrid search runs both and merges the results, and usually beats either alone.

In a knowledge base

Set overrideSearchType to HYBRID (supported on Aurora, OpenSearch Serverless and MongoDB stores; others fall back to semantic). Managed knowledge bases always search hybrid.

In OpenSearch

A hybrid query combines a keyword match with a neural or k-NN query. A search pipeline merges the two result lists: a normalization processor rescales scores (min-max by default) and combines them with weights, or a score ranker uses reciprocal rank fusion (RRF), which merges by rank and needs no score tuning.

Search pipeline and hybrid query (OpenSearch) 
PUT _search/pipeline/hybrid-norm
{
  "phase_results_processors": [{
    "normalization-processor": {
      "normalization":
        {"technique": "min_max"},
      "combination": {
        "technique": "arithmetic_mean",
        "parameters":
          {"weights": [0.3, 0.7]}}
    }
  }]
}

GET manuals-kitchen/_search
    ?search_pipeline=hybrid-norm
{
  "query": {"hybrid": {"queries": [
    {"match": {"text": "K200 descale"}},
    {"neural": {"embedding": {
      "query_text": "K200 descale",
      "model_id": "bedrock-titan-v2",
      "k": 20}}}
  ]}}
}

The weights (one per query, summing to 1) favor the semantic result 0.7 to 0.3 here.

Reranking

A second, more careful pass

Vector search compares precomputed vectors, which is fast but approximate. A reranker reads the query together with each candidate passage and scores relevance directly, so it orders results far better. The pattern: retrieve a wide set (20 to 50), rerank, and pass only the top few (3 to 5) to the model, improving answers while shrinking the prompt.

  • Bedrock offers Amazon Rerank and Cohere Rerank models (Regional availability differs: check before choosing a Region).
  • Use them through the Rerank API on any results, or inside a knowledge base Retrieve call. Pricing is per query of up to 100 passages.
  • Managed knowledge bases include a managed reranker by default.
Hybrid retrieval of 20, reranked to 5 (Python) 
rerank = {
    "type": "BEDROCK_RERANKING_MODEL",
    "bedrockRerankingConfiguration": {
        "modelConfiguration":
            {"modelArn": RERANK_ARN},
        "numberOfRerankedResults": 5},
}
resp = kb.retrieve(
    knowledgeBaseId=KB_ID,
    retrievalQuery={"text": question},
    retrievalConfiguration={
        "vectorSearchConfiguration": {
            "numberOfResults": 20,
            "overrideSearchType": "HYBRID",
            "rerankingConfiguration":
                rerank}},
)

"Searches for part numbers and error codes return irrelevant results" points to hybrid search. "The right passage is retrieved but ranked too low to be used" points to a reranker. "Prompt too long and costly from many retrieved chunks" points to retrieving more, reranking, and keeping fewer.

Query handling

Skill 1.5.5Develop sophisticated query handling systems to improve the retrieval effectiveness and result quality for FM augmentation (for example, by using Amazon Bedrock for query expansion, Lambda functions for query decomposition, Step Functions for query transformation)

Transforming the question

TechniqueWhat it doesHelps when
RewritingA model turns a chatty or follow-up question into a standalone search query ("and the warranty?" becomes "K200 kettle warranty period")Multi-turn conversations
ExpansionAdds synonyms, product names or several alternative phrasings, searched togetherUsers' words differ from the documents'
DecompositionSplits a compound question into sub-questions, retrieves for each, combinesComparisons and multi-part questions
Hypothetical answer (HyDE)A model drafts an answer; its embedding is used to searchShort questions that look nothing like the documents
Filter extractionA model turns "manuals for kitchen products since 2025" into metadata filtersQuestions that imply constraints

Built into knowledge bases

  • Query decomposition in RetrieveAndGenerate: set the query transformation type to QUERY_DECOMPOSITION.
  • Implicit filtering: a model builds metadata filters from the question and a description of your metadata.
  • Agentic retrieval (AgenticRetrieveStream, managed knowledge bases): a model plans sub-queries, retrieves iteratively across one or more knowledge bases, and returns an answer with citations and a trace of its steps.
RetrieveAndGenerate with query decomposition (Python) 
qt = {"queryTransformationConfiguration":
      {"type": "QUERY_DECOMPOSITION"}}
cfg = {
    "type": "KNOWLEDGE_BASE",
    "knowledgeBaseConfiguration": {
        "knowledgeBaseId": KB_ID,
        "modelArn": MODEL_ARN,
        "orchestrationConfiguration": qt,
    },
}
q = ("Is the K200 or the K300 "
     "easier to descale?")
resp = kb.retrieve_and_generate(
    input={"text": q},
    retrieveAndGenerateConfiguration=cfg,
)
print(resp["output"]["text"])

Building your own pipeline

  1. RewriteA Step Functions task calls a small Bedrock model to produce a standalone query, sub-questions and filters as JSON.
  2. Fan outA Map state retrieves for each sub-question in parallel.
  3. MergeA Lambda function de-duplicates, fuses (for example with reciprocal rank fusion) and reranks.
  4. AnswerThe main model answers from the merged passages, with citations.

Each extra model call adds latency and cost; apply transformations only when a cheap check (question length, a comparison word, a follow-up turn) says they're needed.

Retrieval as a tool

Function calling

Instead of always retrieving, give the model a tool it can choose to call. Define it in Converse's toolConfig; when the model wants it, the response has stopReason tool_use and the arguments. Your code runs Retrieve and returns a toolResult, and the model continues with the results. Bedrock never runs the tool itself.

A search tool the model can call (Python) 
tools = {"tools": [{"toolSpec": {
    "name": "search_manuals",
    "description": "Search product "
        "manuals. Use for how-to and "
        "troubleshooting questions.",
    "inputSchema": {"json": {
        "type": "object",
        "properties": {
            "query": {"type": "string"},
            "product": {"type": "string"}},
        "required": ["query"]}},
}}]}

resp = brt.converse(modelId=MODEL_ID,
    messages=messages, toolConfig=tools)
if resp["stopReason"] == "tool_use":
    # run Retrieve with the tool input,
    # append a toolResult, call again
    ...

MCP

The Model Context Protocol standardizes how agents discover and call tools, so one retrieval tool serves every MCP-capable agent and IDE:

  • AgentCore Gateway can expose a managed knowledge base's Retrieve and agentic retrieval as MCP tools, secured with IAM, with the administrator fixing which parameters callers may set.
  • AWS's open-source Bedrock Knowledge Base retrieval MCP server lets MCP clients list and query tagged knowledge bases; an OpenSearch MCP server exposes index search.
  • A Lambda function or API Gateway API wrapping your retrieval logic can also be registered as an AgentCore Gateway target (Task 2.1).

A standard retrieval API

For many applications, put retrieval behind one internal API (API Gateway and Lambda) with a fixed request and response shape: query, filters and top-k in; passages, scores, source links and document IDs out. Teams then share the same chunking, embedding, hybrid search, reranking and access checks, and the implementation can change behind the API.

Key takeaways

  • Chunking: default about 300 tokens; fixed-size with overlap; hierarchical (match children, return parents) for long structured documents; semantic for unstructured text; custom Lambda for your own structure. It can't be changed on an existing data source.
  • Embeddings: pick by modality and language (Titan V2 text, Titan or Nova multimodal, Cohere multilingual), test dimensions on your data, use the same model for documents and queries, batch inference for bulk loads; changing models means re-embedding everything.
  • Search settings: distance metric to match the model, HNSW m, ef_construction and ef_search for recall versus speed, and a sensible number of results; pgvector operators must match the index's operator class.
  • Hybrid search (keyword plus vector, merged by normalization or RRF) handles exact terms; rerankers (Amazon, Cohere) reorder a wide candidate set so only the best few reach the prompt.
  • Query handling: rewrite follow-ups, expand terms, decompose compound questions (built into RetrieveAndGenerate), extract filters, or use agentic retrieval; orchestrate custom pipelines with Step Functions.
  • Access: Retrieve, RetrieveAndGenerate with citations, AgenticRetrieveStream; retrieval as a Converse tool; MCP through AgentCore Gateway or open-source servers; one standard internal retrieval API.
