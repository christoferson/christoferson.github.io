Overview

Task 3.1

Implement input and output safety controls.

A model will try to answer whatever it's sent, and its answers can be harmful, off-topic, leak data, or be confidently wrong. Safety controls sit on both sides of the model: they inspect what goes in (harmful requests, injection attempts, personal data) and what comes out (harmful or ungrounded content, leaked data), and they are layered so no single control is the only line of defense.

The examples continue the retailer's support assistant, which must stay on topic, never give financial or medical advice, never reveal card numbers, and answer only from the product manuals.

Input safety

Skill 3.1.1Develop comprehensive content safety systems to protect against harmful user inputs to FMs (for example, by using Amazon Bedrock guardrails to filter content, Step Functions and Lambda functions to implement custom moderation workflows, real-time validation mechanisms)

Amazon Bedrock Guardrails

A guardrail is a reusable set of policies, applied to inputs, outputs or both, on Bedrock model calls, knowledge bases, agents and flows, or to any text through the ApplyGuardrail API. Each policy below is configured separately.

PolicyWhat it catchesKey settings
Content filtersHate, insults, sexual content, violence, misconduct, in text and imagesStrength none, low, medium or high, separately for input and output
Prompt attacksJailbreaks, prompt injection and (Standard tier) prompt leakageInput only; user input must be marked with input tags
Denied topicsSubjects the application must not discussUp to 30 topics, each a definition plus sample phrases
Word filtersProfanity (managed list) and your own words or phrasesUp to 10,000 custom entries; whole-word match; free
Sensitive informationPersonal data (names, emails, card numbers, AWS keys and more) and custom regex patternsBlock, mask (anonymize) or detect, per entity type and direction
Contextual groundingAnswers not supported by the source, or not relevant to the questionGrounding and relevance thresholds (0 to 0.99); output only
Automated ReasoningAnswers that contradict rules extracted from your policy documentsDetect only (never blocks); see below

How filters decide

Each filter classifies content with a confidence of none, low, medium or high, and compares it with the strength you set: at high strength even low-confidence detections are blocked; at low, only high-confidence ones. Higher strength catches more but blocks more legitimate requests, so tune it. Every policy can run in detect mode (action NONE), which records what it would have blocked without affecting users: start there with real traffic, review, then switch to blocking.

Denied topics

Describe each topic in plain terms ("Investment advice: recommendations about buying, selling or holding securities or other financial products") with a few sample phrases. Don't write instructions or negative definitions ("anything except product questions") into a topic; use topics for subjects, and word filters for specific words or names.

Safeguard tiers

The Standard tier (2025) is more accurate than the original Classic tier, supports many more languages (Classic covers English, French and Spanish), allows longer topic definitions, detects prompt leakage, and catches harmful content hidden in code (comments, names, strings). It costs the same, but it requires cross-Region inference for the guardrail (a guardrail profile), so check data residency. The default is Classic, and updating a guardrail without specifying the tier resets it to Classic.

The support assistant's guardrail (Python) 
filters = [
    {"type": "HATE",
     "inputStrength": "HIGH",
     "outputStrength": "HIGH"},
    {"type": "MISCONDUCT",
     "inputStrength": "MEDIUM",
     "outputStrength": "MEDIUM"},
    # prompt attacks are input-only
    {"type": "PROMPT_ATTACK",
     "inputStrength": "HIGH",
     "outputStrength": "NONE"},
]
topic = {
    "name": "Investment advice",
    "definition": "Recommendations on "
        "buying, selling or holding "
        "financial products.",
    "examples": ["Should I buy shares?"],
    "type": "DENY",
}
pii = [
    {"type": "EMAIL",
     "action": "ANONYMIZE"},
    {"type": "CREDIT_DEBIT_CARD_NUMBER",
     "action": "BLOCK"},
]
bedrock.create_guardrail(
    name="support-assistant",
    blockedInputMessaging=SORRY_IN,
    blockedOutputsMessaging=SORRY_OUT,
    contentPolicyConfig={
        "filtersConfig": filters,
        "tierConfig":
            {"tierName": "STANDARD"}},
    topicPolicyConfig=
        {"topicsConfig": [topic]},
    sensitiveInformationPolicyConfig=
        {"piiEntitiesConfig": pii},
    crossRegionConfig={
        "guardrailProfileIdentifier":
            GUARDRAIL_PROFILE},
)

Then create a numbered version and reference that version in applications; the draft stays editable.

Applying guardrails

  • Converse: pass guardrailConfig (ID, version, optional trace). A blocked request returns your blocked message with stopReason guardrail_intervened; the trace says which policy fired.
  • ApplyGuardrail: checks any text (or image) against a guardrail without calling a model, with source set to INPUT or OUTPUT. Use it for self-hosted or third-party models, for content from tools, and for custom pipelines.
  • Knowledge bases, agents and flows accept a guardrail in their configuration.
  • Enforcement across an account or organization, or by IAM condition, guarantees a guardrail is always applied (Task 2.3).

Guardrails evaluate user messages, system prompts and model responses, but not tool results, tool definitions or the arguments the model generates for tool calls. In an agent, content returned by a tool (a web page, an email, a retrieved document) bypasses the guardrail unless you check it yourself with ApplyGuardrail.

Custom moderation workflows

When guardrails aren't enough

Some cases need more than a filter: industry-specific rules, a second opinion on borderline content, human review, or moderation of images and video. A Step Functions workflow can run several checks and decide:

  1. ValidateA Lambda function checks length, language, encoding and format in real time, rejecting malformed input.
  2. ScreenIn parallel: ApplyGuardrail, Amazon Comprehend toxicity detection (labels such as hate speech, harassment, profanity, with a toxicity score; English), and Amazon Rekognition moderation labels for images.
  3. Classify borderline casesA small model with a moderation prompt, or a safety classifier model such as gpt-oss-safeguard on Bedrock, applies your written policy.
  4. DecideA Choice state allows, blocks, or sends the item to a human review queue.
  5. RecordLog the decision and scores for audit and tuning.

Comprehend's separate prompt safety classifier is closed to new customers; use the guardrail prompt-attack filter instead.

Output safety

Skill 3.1.2Create content safety frameworks to prevent harmful outputs (for example, by using Amazon Bedrock guardrails to filter responses, specialized FM evaluations for content moderation and toxicity detection, text-to-SQL transformations to ensure deterministic results)

Filtering responses

The same guardrail checks responses with its output settings: content filters, denied topics, word filters, masking or blocking personal data the model produced, and grounding. With streaming, choose the processing mode:

ModeBehaviourTrade-off
Synchronous (default)Buffers and checks each chunk before sending itSafer; adds latency to the stream
AsynchronousSends chunks immediately, checks in the background, stops the stream when something is foundFaster; harmful content may already have been shown, and PII masking isn't supported

Evaluating outputs for safety

Before release and on samples in production, run Bedrock evaluation jobs with LLM-as-a-judge responsible-AI metrics (harmfulness, stereotyping, refusal) on a test set that includes provocative prompts. A rising harmfulness score after a model or prompt change should block the release (Task 5.1).

Deterministic answers with text-to-SQL

Let the database answer

For questions about numbers ("how many orders shipped late last week?"), a model answering from memory or text can make figures up. Instead, have the model write a SQL query, run it against the database, and return the actual result: the numbers come from data, not generation. A Bedrock knowledge base with a structured data store does this over Amazon Redshift (or the Glue Data Catalog), and its GenerateQuery API returns the SQL alone.

Generated SQL is untrusted code. AWS's guidance: run it with a restricted, read-only identity, ideally against a read-only copy, with only SELECT granted.

A read-only identity for generated queries (Redshift SQL) 
CREATE USER kb_reader PASSWORD DISABLE;
GRANT USAGE ON SCHEMA sales
  TO kb_reader;
GRANT SELECT ON ALL TABLES
  IN SCHEMA sales TO kb_reader;
-- no INSERT, UPDATE, DELETE or DDL

Reducing hallucinations

Skill 3.1.3Develop accuracy verification systems to reduce hallucinations in FM responses (for example, by using Amazon Bedrock Knowledge Base to ground responses and perform fact-checking, confidence scoring and semantic similarity search for verification, JSON Schema to enforce structured outputs)

Ground, then verify

Grounding with a knowledge base

Retrieval gives the model the facts; instructions tell it to answer only from them and say when they don't contain the answer; RetrieveAndGenerate returns citations linking each part of the answer to its source, so users and reviewers can check it.

Contextual grounding check

A guardrail policy that scores the response for grounding (is every claim supported by the source? new information counts as ungrounded) and relevance (does it answer the question?), and blocks or flags responses below your thresholds (0.7 is a suggested starting point for the Standard tier). It needs three inputs, marked in Converse with guardContent qualifiers: the grounding_source, the query, and the content to guard. With streaming, relevance is judged per chunk, so a mostly irrelevant answer can pass if one chunk is relevant.

Automated Reasoning checks

For answers governed by explicit rules (return windows, eligibility, pricing policies), Automated Reasoning checks verify the answer with formal logic. You upload the policy document; the service extracts rules and variables into a policy you review and version. At run time, models translate the question and answer into logic and a solver checks them against the rules:

  • VALID: follows from the rules (supporting rules are returned for audit).
  • INVALID: contradicts them (contradicting rules are returned, so the app can ask the model to correct itself).
  • SATISFIABLE: true only under some conditions (the answer is incomplete).
  • TRANSLATION_AMBIGUOUS, IMPOSSIBLE and others: the input couldn't be checked reliably, or the premises conflict.

It only detects, never blocks: your application decides whether to serve, correct or ask a clarifying question. It doesn't support streaming, works in English, and doesn't protect against prompt injection.

Confidence and similarity checks you build

  • Semantic similarity: embed the answer and the retrieved passages and compare them (cosine similarity); a low maximum similarity suggests the answer didn't come from the sources.
  • Self-consistency: ask the same question several times (or to several models); disagreement signals low confidence.
  • A judge: a second model scores faithfulness to the sources.
  • Structured outputs: a JSON Schema guarantees the shape of the answer (Task 1.3), so required fields such as a source ID are always present.
Flag answers far from their sources (Python) 
import numpy as np

def embed(text):
    body = json.dumps({"inputText": text})
    r = brt.invoke_model(
        modelId=EMBED_MODEL, body=body)
    v = json.loads(r["body"].read())
    return np.array(v["embedding"])

def grounded(answer, passages, t=0.75):
    a = embed(answer)
    best = max(
        float(a @ embed(p))
        for p in passages)
    # Titan V2 vectors are normalized,
    # so the dot product is the cosine
    return best >= t

"Answers must be supported by our documents" points to a knowledge base with citations plus the contextual grounding check. "Answers must comply with written policy rules, provably" points to Automated Reasoning checks. "Figures must be exact" points to text-to-SQL.

Defense in depth

Skill 3.1.4Create defense-in-depth safety systems to provide comprehensive protection against FM misuse (for example, by using Amazon Comprehend to develop pre-processing filters, Amazon Bedrock to implement model-based guardrails, Lambda functions to perform post-processing validation, API Gateway to implement API response filtering)

Layers on the request path

  1. EdgeAWS WAF in front of the API: rate-based rules against floods and scripted abuse, managed rule groups, bot control.
  2. APIAPI Gateway: authentication, per-client throttling, request validation and size limits (Task 2.4).
  3. Pre-processingLambda with Amazon Comprehend: detect and mask personal data, detect language and toxicity, normalize and sanitize input.
  4. Model guardrailsA Bedrock guardrail on input and output: content, topics, prompt attacks, personal data, grounding.
  5. Post-processingLambda validates the response: schema, allowed values, links only to approved domains, no internal identifiers, citations present.
  6. Response filtering and renderingAPI Gateway (or the Lambda) strips or masks fields before the response leaves; the front end escapes model output before rendering HTML or Markdown, so generated text can't inject scripts.
  7. Least privilege and monitoringTools and data access limited by IAM; logs, metrics and alarms on blocks and anomalies.

Each layer catches what another misses: a guardrail may not catch a domain-specific leak that a post-processing rule does, and a WAF stops a flood before it costs any tokens. Remember that personal data masked by a guardrail can still appear in model invocation logs; protect those separately (CloudWatch Logs data protection).

Detecting injection and jailbreaks

Marking what the user wrote

The prompt-attack filter must know which text came from the user, or it would flag your own system prompt's instructions. With InvokeModel, wrap user input in input tags whose suffix you choose at random per request (so an attacker can't close the tag early); without tags, prompt attacks aren't checked at all. With Converse, put user text in guardContent blocks: once any are present, only those are evaluated.

Mark the user's text for the guardrail (Converse) 
messages = [{
    "role": "user",
    "content": [{"guardContent": {
        "text": {"text": user_text}}}],
}]
resp = brt.converse(
    modelId=MODEL_ID,
    system=[{"text": SYSTEM_PROMPT}],
    messages=messages,
    guardrailConfig={
        "guardrailIdentifier": GR_ID,
        "guardrailVersion": "3"},
)

Indirect injection

Instructions planted in a web page, email or document reach the model through retrieval or tools, not from the user, and guardrails skip tool results. Check such content with ApplyGuardrail (as input) before the model sees it, keep it clearly delimited as data, and make sure a successful injection can't do much: tools with minimal permissions, and approval for consequential actions.

Screen tool output before the model reads it (Python) 
r = brt.apply_guardrail(
    guardrailIdentifier=GR_ID,
    guardrailVersion="3",
    source="INPUT",
    content=[{"text":
        {"text": tool_output}}],
)
if r["action"] == "GUARDRAIL_INTERVENED":
    tool_output = "[content removed]"

Sanitization and classifiers

Normalize input (decode and strip hidden characters, unusual Unicode and encoded payloads that try to slip past filters), cap length, and remove markup that could be read as instructions. For policies beyond the built-in categories, a safety classifier model such as gpt-oss-safeguard on Bedrock evaluates content against your own written policy.

Detection in production and adversarial testing

  • Amazon GuardDuty AI protection analyzes Bedrock, AgentCore and SageMaker AI activity for threats such as anomalous model invocation, cost harvesting with stolen credentials and, when guardrail prompt-attack detection is on, direct prompt injection; its foundational detections also flag guardrails being removed or invocation logging being turned off.
  • Automated adversarial testing: keep a growing library of attack prompts (jailbreaks, injections, leakage attempts, encoded variants) and run it in the pipeline (Step Functions or CodeBuild) against every new prompt, model or guardrail version, failing the release if more attacks succeed. Open-source red-teaming tools can generate variants.
  • AWS Security Agent runs AI-driven penetration tests and design reviews of applications.

"The guardrail flags our own system prompt as an attack" points to missing input tags (or guardContent). "An agent followed instructions hidden in a web page" points to checking tool output with ApplyGuardrail and limiting tool permissions.

Key takeaways

  • Guardrails policies: content filters (strength per direction, text and images), prompt attacks (input only, needs input tags), denied topics (up to 30), word filters, sensitive information (block or mask, regex), contextual grounding (output), Automated Reasoning (detect only). Start in detect mode; version guardrails.
  • Standard tier is more accurate, multilingual and code-aware with prompt leakage detection, but requires cross-Region guardrail inference; Classic is the default.
  • Apply guardrails in Converse (guardrail_intervened), with ApplyGuardrail for any model or content, in knowledge bases, agents and flows; they skip tool results and tool-call arguments.
  • Custom moderation in Step Functions: validation, guardrail, Comprehend toxicity, Rekognition moderation, safety classifier models, human review. Streaming guardrails are synchronous (safer) or asynchronous (faster).
  • Hallucinations: knowledge base grounding with citations, contextual grounding check, Automated Reasoning for rules, similarity and self-consistency checks, structured outputs, text-to-SQL with a read-only identity for exact figures.
  • Defense in depth: WAF, API Gateway, Comprehend pre-filters, guardrails, Lambda post-validation, response filtering and output escaping, least privilege; protect invocation logs separately.
  • Threats: OWASP LLM Top 10; mark user input, screen indirect content, sanitize, use classifiers, run adversarial test suites in the pipeline, and watch GuardDuty AI protection findings.
