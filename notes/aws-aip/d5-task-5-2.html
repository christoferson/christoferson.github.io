Overview

Task 5.2

Troubleshoot GenAI applications.

Generative AI failures are often silent: a request succeeds but the answer is cut off, ignores half the document, cites the wrong manual, or comes back in a slightly different JSON shape that breaks the next step. Troubleshooting starts with evidence (the stop reason, the request ID, the exact prompt sent, the passages retrieved, the trace) rather than guesses, and changes one thing at a time.

The examples follow the retailer from earlier tasks: a customer support assistant grounded in a knowledge base of product manuals, with order and returns tools, and a nightly job that summarizes support tickets. Where to find logs and traces is covered in Task 2.5 and Task 4.3; this page is about reading them to find causes.

Content handling

Skill 5.2.1Resolve content handling issues to ensure that necessary information is processed completely in FM interactions (for example, by using context window overflow diagnostics, dynamic chunking strategies, prompt design optimization, truncation-related error analysis)

Reading the stop reason

Every Converse response says why the model stopped. It is the first thing to check when an answer looks incomplete or odd:

stopReasonMeaningFix
end_turnThe model finished normallyIf the answer is still incomplete, the prompt or context is the problem
max_tokensOutput hit maxTokens and was cut offRaise maxTokens, ask for shorter output, or split the task; with structured output the JSON is incomplete
model_context_window_exceededInput plus output didn't fit the model's context windowSend less: trim history, fewer or smaller chunks, summarize, or use a longer-context model
stop_sequenceA stop sequence was generatedExpected, unless the sequence also appears inside normal answers
tool_useThe model wants a tool resultRun the tool and continue the loop
guardrail_intervened, content_filteredA guardrail or content filter blocked itCheck the guardrail trace (below)
malformed_model_output, malformed_tool_useThe model produced output or a tool call that couldn't be parsedRetry; simplify the tool schema or use strict tools

If the input is too long before generation even starts, the call fails with a ValidationException (HTTP 400) saying the input is too long. Either way, the fix is to measure what you send. The CountTokens API (free, for supported models) returns the exact input token count the model would bill, so you can check before calling:

Check the prompt fits before calling (Python) 
LIMIT = CONTEXT_WINDOW - MAX_OUTPUT

def fits(msgs, system):
    r = brt.count_tokens(
        modelId=MODEL_ID,
        input={"converse": {
            "messages": msgs,
            "system": system}},
    )
    return r["inputTokens"] <= LIMIT

while not fits(msgs, system):
    msgs = drop_oldest_turn(msgs)

drop_oldest_turn removes the oldest user and assistant pair (keeping tool use and tool result blocks together). Counting needs the bedrock:CountTokens permission; token counts differ between models, so count with the model you'll call.

Fixing overflow and truncation

Long conversations

Keep the system prompt fixed and trim or compress history: a sliding window of recent turns, or a running summary of older ones. Strands Agents does this with conversation managers: the default sliding-window manager keeps recent messages and truncates the oldest tool results first; the summarizing manager replaces older messages with a summary while keeping the most recent ones. Store long-term facts in a memory store (AgentCore Memory) instead of the transcript.

Large documents

Don't paste a 200-page manual into a prompt. Retrieve the relevant chunks (RAG), or process it in pieces: summarize each section, then summarize the summaries (map-reduce), or extract fields section by section. For very long single documents, a model with a larger context window works, but Claude's 1M-token context is a beta feature and requests over 200,000 input tokens are billed at a higher long-context rate for the whole request.

Large tool results

A tool that returns a full order history or a raw web page can fill the context in one step. Return only the fields the model needs, paginate, or summarize tool output before passing it back.

Embedding input limits

Embedding models have their own input limits, much smaller than chat models for some: Titan Text Embeddings V2 accepts up to 8,192 tokens, Cohere Embed v3 only 512 tokens per text. Cohere truncates over-long input by default (the end is dropped) unless truncate is set to NONE, which returns an error instead. Silent truncation means the end of a long chunk never makes it into the vector: keep chunks well within the limit.

Dynamic chunking strategies

When content is processed in pieces, the chunk size should follow the content, not one fixed number. In knowledge bases:

SymptomLikely causeTry
Answers miss details spread over neighboring paragraphsChunks too small; context splitHierarchical chunking (small child chunks for search, the larger parent returned) or more overlap
Retrieved chunks are long and mostly irrelevantChunks too largeSmaller fixed size, or semantic chunking that splits at topic changes
Tables and procedures arrive broken in halfFixed-size split ignores structureAdvanced parsing (Bedrock Data Automation or a foundation model parser), semantic chunking, or a custom Lambda chunker that splits on headings
Fewer results than numberOfResultsHierarchical chunking: several children share a parentExpected; raise the number if needed

Changing the chunking strategy of an existing data source requires re-ingesting it; chunking options are in Task 1.5.

Prompt design for complete processing

  • Put long documents first and the question and instructions last; models handle "the question after the material" better on long inputs.
  • Wrap each document in tags with an ID (<doc id="manual-k200">) and ask the model to cite them, so you can see which ones it used.
  • Ask for a structure that forces coverage: "for each of the five sections, list...". Then check every section appears.
  • For lists of items (all 40 tickets), process in batches and assemble the results in code rather than trusting one long generation.

"Answers end mid-sentence" points to max_tokens. "Long conversations start failing" points to context window overflow: trim or summarize history. "The end of long documents is never found in search" points to embedding input truncation or oversized chunks.

FM integration issues

Skill 5.2.2Diagnose and resolve FM integration issues to identify and fix API integration problems specific to GenAI services (for example, by using error logging, request validation, response analysis)

Bedrock Runtime errors

Error (HTTP)Usual causeAction
ValidationException (400)Malformed request: bad message structure, unsupported parameter, input too long, invalid schemaFix the request; don't retry
AccessDeniedException (403)IAM, SCP or model access prerequisitesSee the checklist below; don't retry
ResourceNotFoundException (404)Wrong model or profile ID, or the model isn't offered in this RegionCheck the ID and Region
ModelTimeoutException (408)The model took too longRetry; shorten the request or stream
ModelErrorException (424)The model failed processing this requestRetry; check the input
ThrottlingException (429)Your quota (requests or tokens per minute) exceededBack off with jitter, bound concurrency, request a quota increase, cross-Region inference
ModelNotReadyException (429)The model isn't ready to serve yetThe SDK retries automatically
InternalServerException (500), ServiceUnavailableException (503)Service-side; 503 is capacity, not your quotaRetry with backoff; cross-Region inference

With ConverseStream, errors can also arrive inside the stream after it has started (a modelStreamErrorException, throttling or validation event). Handle them in the event loop: discard the partial answer or tell the user, and retry. Long calls through a NAT gateway, VPC endpoint or Network Load Balancer can be cut by their 350-second idle timeout; enable TCP keepalive in the client and the operating system, or stream.

Access denied checklist

Bedrock now enables serverless models automatically on first use (since October 2025), so "model access not granted" is no longer the usual cause. Check instead:

  1. IAM and SCPsDoes the caller's policy allow the action (bedrock:InvokeModel also covers Converse; InvokeModelWithResponseStream covers ConverseStream) on this resource? Does an SCP deny the Region or model? CloudTrail shows the denied call and often the policy type.
  2. Inference profilesCalling through a cross-Region profile needs permission on the profile ARN and the foundation model ARN in every Region the profile routes to.
  3. ConditionsA condition such as aws:SourceIp fails for calls through a VPC endpoint, where the source IP isn't a public address.
  4. First-use prerequisitesThird-party models need AWS Marketplace subscribe permissions for the first call, a valid payment method, and for Anthropic models a submitted use-case form.

Error logging

Log enough to reproduce: the error code and message, the AWS request ID, the model or profile ID, the operation, input token count, the stop reason, your conversation ID and prompt version. Not the full prompt text in application logs if it holds personal data; the invocation logs, with their access controls, hold that.

Classify and log Bedrock errors (Python) 
from botocore import exceptions

RETRYABLE = {
    "ThrottlingException",
    "ModelTimeoutException",
    "ModelErrorException",
    "ServiceUnavailableException",
    "InternalServerException",
}

def call(**kwargs):
    try:
        return brt.converse(**kwargs)
    except exceptions.ClientError as e:
        err = e.response["Error"]
        resp = e.response
        md = resp["ResponseMetadata"]
        log.error("bedrock_error", extra={
            "code": err["Code"],
            "message": err["Message"],
            "request_id": md["RequestId"],
            "model": kwargs["modelId"],
            "conv": CONV_ID,
        })
        if err["Code"] in RETRYABLE:
            raise RetryLater() from e
        raise

The SDK's standard retry mode already retries throttling and transient errors a few times; RetryLater stands for your next layer (requeue to SQS, fall back to another model, or return a friendly message). Validation and access errors are bugs to fix, not to retry.

Request validation

Catch malformed requests before they reach the model, especially when messages are assembled from stored history:

  • Roles are user and assistant; the conversation starts with a user message and normally alternates. Instructions go in system.
  • Every toolUse block from the assistant must be answered by a toolResult block in the next user message with the same toolUseId; trimming history must never separate them.
  • Images and documents go only in user messages: up to 20 images (3.75 MB each) and 5 documents (4.5 MB each) per request; a document needs its format and a text block alongside it.
  • When the model ID is a Prompt Management prompt ARN, the prompt supplies the model settings, so the request can't also set inferenceConfig, system or toolConfig.
  • At the API edge, validate user input length and type (API Gateway request validation or the Lambda handler) before it costs tokens.

Response analysis

A successful response still needs checking: the stop reason, whether the output parses and matches the expected schema (below), token usage compared with normal (a sudden jump suggests a loop or prompt growth), and latency. Log anomalies with the request ID so you can open the invocation log record for the exact request and response.

Retrying every error makes things worse: validation and access errors fail again every time, and retrying throttles without backoff deepens the throttling. Classify first: fix 400 and 403 errors, back off on 429, retry 5xx a bounded number of times.

Prompt engineering problems

Skill 5.2.3Troubleshoot prompt engineering problems to improve FM response quality and consistency beyond basic prompt adjustments (for example, by using prompt testing frameworks, version comparison, systematic refinement)

Symptoms and causes

SymptomCommon causes
Ignores an instructionBuried in a long prompt, contradicted elsewhere, phrased as a suggestion, or placed before a long document
Inconsistent formatFormat described but not shown; no example; high temperature; no schema enforcement
Different answers each runHigh temperature, ambiguous instructions, missing context the model fills in by guessing
Invented detailsNo instruction to answer only from the context and say when it doesn't know; context missing the fact
Worked before, broke nowPrompt edit, model version change, new retrieved content, a variable filled with unexpected text

Prompt testing frameworks

Treat a prompt like code: a test suite of inputs with checks, run on every change. Checks range from cheap to expensive: does it parse, does it contain required fields or phrases, does it avoid forbidden ones, is it under a length, and finally an LLM judge or comparison with a reference answer. Bedrock evaluation jobs run the judge part at scale (Task 5.1); open-source harnesses run assertion-style tests in CI. Include the inputs that broke before, edge cases (empty context, a question in another language, an angry customer) and adversarial inputs.

Version comparison

When quality changes, find what changed. Bedrock Prompt Management keeps immutable versions of each prompt; in the console you can select two versions and compare them side by side (fields added or removed are highlighted), then fill in test variables and run each. In code, call a specific version by passing its ARN as the model ID in Converse with promptVariables, so the test suite can run old and new versions on the same inputs and diff the results.

Systematic refinement

  1. Collect failuresGather failing examples from feedback, low judge scores and logs, and group them by error type.
  2. Form a hypothesis"The model ignores the return window because the policy text comes after the 3,000-token manual."
  3. Change one thingMove the instruction, add an example, add a rule, tighten the format, or lower the temperature.
  4. Test on everythingRun the fix on the failing cases and the whole suite, since fixes often break something else.
  5. Version and releaseSave a new prompt version with a note on what changed and why, and roll it out behind a flag.

Bedrock can help with the rewriting. Prompt optimization rewrites a single prompt for a chosen model. Advanced Prompt Optimization (May 2026) goes further: given a template, sample inputs, optional ground truth and one evaluation method (steering criteria, an LLM judge or a Lambda function), it generates optimized versions for up to five models and reports scores, latency and time to first token for each against the original. Treat its output as a candidate that still goes through your tests.

"Find what changed between the prompt that worked and the one that doesn't" points to Prompt Management version comparison. "Improve a prompt and compare it across several models with evaluation data" points to Advanced Prompt Optimization. "Stop regressions from prompt edits" points to a prompt test suite in CI.

Retrieval issues

Skill 5.2.4Troubleshoot retrieval system issues to identify and resolve problems that affect information retrieval effectiveness for FM augmentation (for example, by using model response relevance analysis, embedding quality diagnostics, drift monitoring, vectorization issue resolution, chunking and preprocessing remediation, vector search performance optimization)

Locate the failure first

For a bad RAG answer, look at what was retrieved before blaming the model. Call Retrieve with the same question and settings: each result has its text, source location, metadata and a relevance score.

  1. Is the answer in the source documents at all?If not, it's a content gap: add or fix the document.
  2. Was the document ingested?Check the sync results and the knowledge base logs for that file.
  3. Is the right chunk retrieved?If not, it's a retrieval problem: parsing, chunking, embeddings, search settings or filters.
  4. Is it retrieved but ranked low?Raise the number of results, add hybrid search or reranking.
  5. Retrieved and ranked well, answer still wrong?It's a generation problem: the prompt or model (see prompt problems).
Inspect what a question retrieves (Python) 
kb = boto3.client("bedrock-agent-runtime")
cfg = {"vectorSearchConfiguration":
       {"numberOfResults": 10}}
r = kb.retrieve(
    knowledgeBaseId=KB_ID,
    retrievalQuery={"text": question},
    retrievalConfiguration=cfg,
)
for x in r["retrievalResults"]:
    loc = x["location"]["s3Location"]
    print(round(x["score"], 3),
          loc["uri"],
          x.get("metadata", {}),
          x["content"]["text"][:80])

Compare the scores and sources with what you expected. Run it with and without your metadata filter: if the right chunk only appears without the filter, its metadata is wrong or missing.

Ingestion and preprocessing

Sync results report documents scanned, indexed, modified, deleted, skipped and failed. For the reason per file, deliver the knowledge base's application logs to CloudWatch Logs and query them:

Files that failed to embed or index (Logs Insights) 
fields @timestamp,
  event.document_location.s3_location.uri
    as file,
  event.status as status,
  event.status_reasons as why
| filter status in ["EMBEDDING_FAILED",
    "INDEXING_FAILED",
    "PARTIALLY_INDEXED",
    "RESOURCE_IGNORED"]
| sort @timestamp desc
CauseFix
Unsupported file type, or file over the size limit (50 MB for text files)Convert or split the file
Scanned PDFs, tables or charts lost by the default text-only parserAdvanced parsing with Bedrock Data Automation or a foundation model parser (charged per page or per token)
Metadata file ignoredIt must be named FILE.metadata.json in the same folder, valid JSON, and at most 10 KB
Boilerplate (headers, footers, legal text) dominating chunksClean it in a custom transformation Lambda or before upload
Outdated answersThe source changed but the data source wasn't re-synced; schedule or trigger syncs

Embedding quality and vectorization issues

Model mismatchQueries must be embedded with the same model, version and dimension as the documents. A knowledge base can't switch its embedding model (it can't be updated); create a new knowledge base and re-ingest. In a self-managed index, a vector of the wrong dimension is rejected at indexing or query time.

Index configurationAn OpenSearch index for a knowledge base must use the faiss engine and the embedding model's dimension (Titan V2: 1024, 512 or 256), with the vector, text and metadata field names the knowledge base was given.

Weak embeddings for the domainProduct codes, internal jargon and other languages may embed poorly. Diagnose with known pairs: embed questions and the passages that answer them, and check that each question's passage is its nearest neighbor. Fix with hybrid search (keywords catch codes), a better or multilingual embedding model, or including metadata in the embedded text.

Truncated inputChunks longer than the embedding model's limit lose their ends (see content handling).

Drift monitoring

Retrieval quality decays even without code changes: new products whose manuals weren't added, users asking about topics the documents don't cover, wording that shifts (customers start saying "pod" for a capsule). Watch for it with a retrieval canary set run after every sync (recall of known passages), the average top relevance score of live queries (a falling score means questions match the documents less well), the share of "I don't know" answers, and clusters of low-scoring live questions, which show the content gaps to fill.

Vector search performance

Slow or failing searches usually come from the index rather than the query: k-NN graphs that don't fit in memory (circuit breaker trips, evictions), too high an ef_search or result count, restrictive filters that force extra scanning, or under-provisioned capacity. The metrics to watch and the tuning options are in Task 4.3 and Task 4.2.

"The right document exists but is never retrieved" points to checking ingestion logs, parsing and metadata. "Results got worse after switching embedding models" points to a mismatch: re-embed everything into a new index. "Tables in PDFs come back garbled" points to advanced parsing. "Quality falls as the catalog grows" points to drift: canary sets and content gap analysis.

Prompt maintenance

Skill 5.2.5Troubleshoot prompt maintenance issues to continuously improve the performance of FM interactions (for example, by using template testing and CloudWatch Logs to diagnose prompt confusion, X-Ray to implement prompt observability pipelines, schema validation to detect format inconsistencies, systematic prompt refinement workflows)

Prompts degrade as everything around them changes: variables start carrying longer or odder values, new retrieved content conflicts with instructions, a new tool's description overlaps an old one, a model upgrade reads instructions differently. Maintenance means testing templates, seeing the final prompt actually sent, and validating outputs continuously.

Template testing

A template is only as good as what fills it. Test each Prompt Management template (variables written {{name}}) with realistic and extreme values: empty strings, very long values, text containing instructions ("ignore the above"), other languages, and special characters. Check that every variable is filled (a literal {{order_id}} in a sent prompt means rendering failed) and that the rendered prompt stays within budget.

Diagnosing prompt confusion with CloudWatch Logs

"Prompt confusion" is the model misreading what the prompt asks: answering the wrong question, mixing up two products, following text in a retrieved document as if it were an instruction. The cause is visible only in the prompt that was actually sent, which invocation logs record. Query them by feature or prompt version (tagged in requestMetadata) and read the failing requests:

Prompts behind bad answers for one prompt version (Logs Insights) 
fields @timestamp, requestId,
  input.inputTokenCount as inT,
  output.outputBodyJson.stopReason
    as stop
| filter requestMetadata.prompt_ver
    = "returns-v12"
| filter inT > 6000 or stop != "end_turn"
| sort inT desc
| limit 50

Unusually long prompts and abnormal stop reasons are good first suspects; open those records to read the full input body. Look for duplicated context, conflicting instructions, variables filled with the wrong content, and instructions placed after very long material.

Prompt observability pipelines

Traces show how a prompt was built and what happened next across services. The X-Ray SDKs are in maintenance mode, so instrument with OpenTelemetry through ADOT; traces still appear in the X-Ray and CloudWatch trace views. Add spans for each stage (template render, retrieval, model call, output validation, tool calls) with attributes such as the prompt ID and version, variable sizes, retrieved chunk IDs, model ID and token usage. Agent frameworks such as Strands emit standard gen_ai.* attributes (model, operation, tool name, input and output tokens) for you. For Bedrock Flows, validate the definition before deploying (ValidateFlowDefinition) and invoke with enableTrace to see each node's inputs and outputs and which condition branch was taken.

Schema validation for format inconsistencies

Downstream code breaks when the model returns JSON in a slightly different shape: a missing field, a number as a string, extra prose before the JSON. Two layers fix it:

  • Constrain: Bedrock structured outputs (generally available February 2026, now for all Claude models) constrain the response to a JSON Schema you supply through outputConfig, or strict tool definitions (Task 1.3 has the request). An unsupported schema fails immediately with a 400, for example when an object doesn't set additionalProperties to false or has too many optional properties.
  • Validate: still validate every response in code, because not every model supports constrained output, a max_tokens stop leaves the JSON incomplete, and the values can be valid JSON but wrong. Count validation failures per prompt version as a metric.
Validate and count format failures (Python) 
from jsonschema import validate
from jsonschema import ValidationError

def parse_ticket(resp):
    if resp["stopReason"] == "max_tokens":
        raise Truncated()
    msg = resp["output"]["message"]
    text = msg["content"][0]["text"]
    try:
        data = json.loads(text)
        validate(data, TICKET_SCHEMA)
        return data
    except (ValueError,
            ValidationError) as e:
        emit_metric("FormatError",
                    prompt_ver=PROMPT_VER)
        raise BadFormat(str(e)) from e

emit_metric stands for an embedded metric format writer. A rise in FormatError after a release identifies the prompt version that broke the format; retrying once with the validation error added to the prompt often repairs it.

Guardrail interventions

When answers are unexpectedly blocked, enable the guardrail trace (trace set to enabled or enabled_full in guardrailConfig). The response's trace.guardrail shows the input and output assessments: which policy (content filter, denied topic, word filter, sensitive information, contextual grounding, automated reasoning) acted and why. A grounding threshold set too high, or a denied topic defined too broadly, are common causes of false blocks.

A refinement workflow that sticks

  1. DetectAlarms on format errors, judge scores, guardrail interventions and feedback per prompt version.
  2. DiagnoseOpen the traces and invocation logs of failing requests; classify the failure.
  3. Fix and testChange the template, then run the template tests and the prompt test suite.
  4. ReleasePublish a new version, roll it out gradually, and keep the previous version one switch away.
  5. LearnAdd the failing inputs to the test suite.

"See the exact prompt that produced a bad answer" points to model invocation logs. "Trace prompt construction across services" points to OpenTelemetry (ADOT) spans viewed in X-Ray or CloudWatch. "Downstream parser fails intermittently" points to structured outputs plus schema validation. "Answers blocked unexpectedly" points to the guardrail trace.

Key takeaways

  • Start from evidence: stop reason, request ID, the exact prompt (invocation logs), retrieved passages and the trace. Change one thing at a time.
  • max_tokens means the output was cut off; model_context_window_exceeded or a "too long" ValidationException means the input didn't fit. Count tokens with CountTokens, trim or summarize history, retrieve instead of pasting, and keep chunks within embedding limits.
  • Classify API errors: fix 400 and 403, back off on 429, retry 5xx with limits; handle errors inside streams. Access denied is now usually IAM, SCPs, inference profile permissions or first-use prerequisites, not model access.
  • Validate requests (roles, tool use and result pairs, attachment limits) and responses (stop reason, schema, token usage); log the request ID and prompt version.
  • Prompt problems: test suites in CI, Prompt Management version comparison, a hypothesis-driven refinement loop, and prompt optimization (Advanced Prompt Optimization compares up to five models).
  • Retrieval: check retrieved results and scores first; then ingestion logs, parsing, metadata files, chunking and embedding model consistency (changing it means a new knowledge base); monitor drift with canary sets and relevance scores.
  • Maintenance: test templates with extreme values, read failing prompts in invocation logs, trace prompt construction with OpenTelemetry, constrain and validate JSON output, and use the guardrail trace for unexpected blocks.
