Overview

Task 1.2

Select and configure FMs.

Models change faster than applications: new versions arrive every few months, older ones are retired, and a model can be throttled or degraded for a while. A good design treats the model as a replaceable, configurable dependency: chosen on evidence, referenced by configuration, backed by a fallback, and deployed through the same safe release process as code.

Choosing a model

Skill 1.2.1Assess and choose FMs to ensure optimal alignment with specific business use cases and technical requirements (for example, by using performance benchmarks, capability analysis, limitation evaluation)

The criteria

CriterionQuestions to ask
Quality for this taskHow well does it answer our questions? Public benchmarks are a starting point only
ModalitiesText only, or images, video, audio, speech? Does it need to output images or embeddings?
Context window and output lengthWill the documents, history and instructions fit, and is the maximum output long enough?
Latency and costPrice per input and output token, time to first token, throughput at our volume
Feature supportConverse, streaming, tool use, structured outputs, guardrails, Knowledge Bases, prompt caching, fine-tuning
AvailabilityIn our Region, through a geographic or global inference profile, and in which service tiers?
Licence and lifecycleDo the provider's terms suit the use? When does it reach end of life?

Evidence for the choice

Bedrock model cards

Each model's card lists its modalities, context window and maximum output, knowledge cutoff, supported APIs, which Bedrock features it supports, its service tiers, Regional and cross-Region availability with model IDs, and its lifecycle dates. Feature support varies per model, even within a family: check the card before designing around structured outputs, prompt routing or evaluation support.

Families, not versions

Within a family, smaller models are faster and cheaper, larger ones better at complex reasoning. The Amazon Nova family runs from Micro (text only, fastest and cheapest) through Lite (low-cost multimodal) to Pro (balanced, multimodal), with second-generation models, speech-to-speech Sonic models and multimodal embeddings. Other providers' families (Anthropic, Meta, Mistral, OpenAI open-weight models, Cohere and more) follow the same pattern. Version numbers change monthly; the exam tests the reasoning.

Evaluate on your own data

Run a Bedrock evaluation job comparing candidates on a dataset of your real prompts: automatic metrics, LLM-as-a-judge, human review, or RAG evaluation for retrieval-based apps. Evaluations can include customized, imported and Marketplace models and prompt routers. Combine the quality scores with measured latency and cost (Task 1.1) to pick the smallest model that meets the bar.

"Choose a model that meets quality requirements at the lowest cost" means evaluating several candidates on representative data and picking the cheapest that passes, not picking the top of a public leaderboard.

The model lifecycle

Active, Legacy, end of life

Bedrock models move from Active to Legacy to end of life (EOL), and the state can differ by Region. Model cards show the earliest EOL date ("EOL no sooner than") and the length of the Legacy period. In Legacy:

  • New customers can't start using the model, and accounts that haven't used it for 15 days may lose access.
  • No new Provisioned Throughput or fine-tuning jobs; existing ones keep working.

After EOL, requests fail; migration is never automatic. Check each model's modelLifecycle status with GetFoundationModel or ListFoundationModels in every Region you use, and plan the move while the replacement can still be evaluated calmly.

Switching models without code changes

Skill 1.2.2Create flexible architecture patterns to enable dynamic model selection and provider switching without requiring code modifications (for example, by using AWS Lambda, Amazon API Gateway, AWS AppConfig)

The pattern

  1. One entry pointApplications call your API (API Gateway), never a model directly.
  2. A thin model layerA Lambda function builds the request and calls Bedrock.
  3. Configuration decides the modelThe model ID, fallback, prompt version and parameters come from AWS AppConfig (or Parameter Store), not from code.
  4. One request formatThe Converse API uses the same message format for every model that supports it, so changing provider is a configuration change.

AWS AppConfig

Configuration with safe rollout

AppConfig stores feature flags and free-form configuration (in its own store, S3, Parameter Store or Secrets Manager) and deploys changes gradually:

  • Validators (a JSON Schema or a Lambda function) reject a bad configuration before it deploys.
  • Deployment strategies roll out linearly or exponentially (for example the recommended AppConfig.Linear20PercentEvery6Minutes, or AppConfig.Canary10Percent20Minutes).
  • During the bake time, AppConfig watches CloudWatch alarms and rolls back automatically if one fires.

So moving the assistant to a new model is: change one value, deploy it to 10% of traffic, watch error and quality alarms, and let AppConfig roll back if they fire.

Free-form configuration for the assistant (JSON) 
{
  "assistant": {
    "modelId": "us.amazon.nova-pro-v1:0",
    "fallbackModelId":
      "us.amazon.nova-lite-v1:0",
    "promptVersion": "3",
    "maxTokens": 400
  }
}

Reading it in Lambda

The AppConfig Lambda extension (a layer) caches the configuration inside the execution environment and refreshes it in the background, so the function reads it from localhost:2772 with no extra API calls or latency.

Lambda: model chosen by configuration (Python) 
import json, urllib.request
import boto3

brt = boto3.client("bedrock-runtime")
URL = ("http://localhost:2772/"
       "applications/"
       "support/environments/prod/"
       "configurations/model-config")

def handler(event, context):
    with urllib.request.urlopen(URL) as r:
        cfg = json.load(r)["assistant"]
    resp = brt.converse(
        modelId=cfg["modelId"],
        messages=event["messages"],
        inferenceConfig={
            "maxTokens": cfg["maxTokens"]},
    )
    return resp["output"]["message"]

Other ways to decouple

  • Application inference profiles: create a profile per application that points at a model (or a cross-Region profile) and pass its ARN as the modelId. It also carries cost allocation tags and its own metrics.
  • Intelligent prompt routing: one endpoint that picks between two models of the same family per request, by predicted quality, to save cost without code logic.
  • OpenAI-compatible endpoints: applications written against the OpenAI SDK can point at Bedrock with a Bedrock API key and a base URL, easing moves between providers.
  • Bedrock Prompt Management: prompts versioned outside the code, referenced by version in configuration (Task 1.6).

Converse makes the request format portable, not the behavior: a different model needs its prompts re-tested and may lack features (tool use, structured outputs, image input). Validate the new model with an evaluation before switching the configuration.

Resilient designs

Skill 1.2.3Design resilient AI systems to ensure continuous operation during service disruptions (for example, by using AWS Step Functions circuit breaker patterns, Amazon Bedrock Cross-Region Inference for models that have limited regional availability, cross-Region model deployment, graceful degradation strategies)

What goes wrong

  • ThrottlingException (429): the account's requests or tokens per minute for that model are used up.
  • 503 and model-not-ready errors: temporary capacity or service problems.
  • The model isn't offered in your Region, or a Region has an outage.
  • Slow responses that exceed the application's timeout.

Bedrock's SLA is 99.9% monthly uptime per Region; designing for more means combining the measures below. Cross-Region inference on its own doesn't guarantee availability: AWS recommends bounded retries plus multi-Region or multi-model fallback.

The layers of resilience

Cross-Region inference

An inference profile spreads requests across several Regions, raising throughput and riding out a busy Region, and makes models available from Regions where they aren't hosted. Use a geographic profile (US, EU, APAC) when data must stay in a geography, or a global profile for the most capacity at a lower price. Global profiles need IAM permissions on the Region-less model ARN and must be allowed by Region-restricting SCPs.

Retries with backoff

Retry only retryable errors (throttling, 5xx), with exponential backoff and jitter and a limited number of attempts. The AWS SDKs do this for you: standard retry mode is the default, adaptive adds client-side rate limiting for heavily throttled single resources. Unlimited retries make an overload worse.

Fallback models and graceful degradation

When the primary model keeps failing, call a fallback (a smaller model, or the same model through another profile). If that fails too, degrade gracefully: a cached answer to a common question, a simpler non-AI path, or an honest "the assistant is busy, here's how to reach us".

Retries, then a fallback model, then a static answer 
import boto3
from botocore.config import Config
from botocore.exceptions import ClientError

brt = boto3.client(
    "bedrock-runtime",
    config=Config(retries={
        "mode": "standard",
        "total_max_attempts": 6}),
)
RETRYABLE = {"ThrottlingException",
             "ServiceUnavailableException",
             "ModelNotReadyException"}

def ask(messages, cfg):
    for model in (cfg["modelId"],
                  cfg["fallbackModelId"]):
        try:
            return brt.converse(
                modelId=model,
                messages=messages)
        except ClientError as e:
            c = e.response["Error"]["Code"]
            if c not in RETRYABLE:
                raise
    return STATIC_BUSY_ANSWER

Circuit breaker with Step Functions

Retries help with short blips; a circuit breaker stops calling a dependency that is clearly down, so requests fail fast (or go straight to the fallback) instead of waiting on timeouts. AWS's prescriptive pattern:

  1. Check the circuitA Step Functions workflow reads the model's status from a DynamoDB table.
  2. Open: skipIf the circuit is open, go straight to the fallback branch.
  3. Closed: callOtherwise call the model, with retries.
  4. Trip on failureIf retries are exhausted, write an "open" record with an expiry time (DynamoDB TTL removes it), so calls resume automatically later.

Cross-Region deployment

For models you host yourself (SageMaker AI endpoints, or customized models), deploy to a second Region and route between Regions, for example with Route 53 failover records in front of a Regional API, the same active-passive or active-active patterns as any multi-Region application.

"The model isn't available in our Region" points to a cross-Region inference profile. "Throttling at peak" points to retries with backoff, cross-Region inference, a smaller model for simple requests, or Provisioned Throughput. "Keep answering even if Bedrock is impaired" points to a fallback model plus graceful degradation behind a circuit breaker.

Parameter-efficient adaptation

LoRA and adapters

LoRA (low-rank adaptation) trains a small set of extra weights, an adapter of megabytes rather than the gigabytes of the base model, while the base weights stay frozen. Training is cheaper and faster, and at serving time many adapters can share one copy of the base model.

On SageMaker AI, deploy the base model as an inference component, then add each adapter as its own inference component that references the base and shares its compute. Each team or customer domain gets its own adapter, invoked by name, without a separate GPU endpoint per model.

Add a LoRA adapter to a running base model (Python) 
sm = boto3.client("sagemaker")

sm.create_inference_component(
    InferenceComponentName="ret-lora-v3",
    EndpointName="llm-shared",
    Specification={
        "BaseInferenceComponentName":
            "llama-base",
        "Container": {"ArtifactUrl":
            "s3://models/ret/v3.tar.gz"},
    },
)

# call the adapter by name
smr = boto3.client("sagemaker-runtime")
smr.invoke_endpoint(
    EndpointName="llm-shared",
    InferenceComponentName="ret-lora-v3",

Versioning with the Model Registry

Model package groups and approval

The SageMaker Model Registry keeps each model as a model package group of numbered versions, each with its metrics, lineage and model card. A version's approval status is PendingManualApproval, Approved or Rejected, and changing it emits an EventBridge event, which is what drives deployment pipelines. Models registered in MLflow can be synced into the registry automatically.

Approve a version after it passes the evaluation gate 
sm.update_model_package(
    ModelPackageArn=version_arn,
    ModelApprovalStatus="Approved",
    ApprovalDescription=
        "Passed eval gate",
)

Automated deployment and rollback

  1. Train or customizeA SageMaker pipeline (or Bedrock customization job) produces a candidate.
  2. EvaluateAutomatic evaluation against a fixed test set; fail the pipeline if quality drops (Task 5.1).
  3. RegisterA new version in the Model Registry, pending approval.
  4. ApproveA person or an automated gate approves; EventBridge starts the deployment pipeline (CodePipeline).
  5. Deploy safelyUpdate the endpoint with deployment guardrails, watching alarms.
  6. Roll backAutomatically on alarms, or by rejecting the version; with SageMaker project templates, the latest approved version is then redeployed.

SageMaker AI deployment guardrails

Endpoint updates can use blue/green deployment that shifts traffic all at once, as a canary, or linearly, with a baking period and automatic rollback when CloudWatch alarms fire, or a rolling update in batches. Shadow tests send a copy of live traffic to the new model and compare it without affecting users.

Canary update with automatic rollback (deploy.json) 
{
  "BlueGreenUpdatePolicy": {
    "TrafficRoutingConfiguration": {
      "Type": "CANARY",
      "CanarySize": {
        "Type": "CAPACITY_PERCENT",
        "Value": 10
      },
      "WaitIntervalInSeconds": 600
    },
    "TerminationWaitInSeconds": 600
  },
  "AutoRollbackConfiguration": {
    "Alarms": [
      {"AlarmName": "support-llm-5xx"},
      {"AlarmName": "support-llm-latency"}
    ]
  }
}
aws sagemaker update-endpoint \
  --endpoint-name support-llm \
  --endpoint-config-name support-llm-v2 \
  --deployment-config file://deploy.json

Retiring and replacing

  • Bedrock base models: watch the lifecycle status. Re-customize on an Active base before the old base becomes Legacy (Legacy blocks new fine-tuning and Provisioned Throughput), evaluate, then switch the model ID in configuration.
  • SageMaker AI models: deploy the replacement through guardrails, keep the previous version registered for rollback, and delete old endpoints and inference components to stop paying for them.
  • Record why: the registry's lineage and model cards document which version was live when, for audits (Task 3.3).

Key takeaways

  • Choose models on evidence: model card capabilities and feature support, then Bedrock evaluations on your own data, then latency and cost; pick the smallest model that passes.
  • Models go Active, Legacy, end of life; Legacy blocks new fine-tuning and Provisioned Throughput; check modelLifecycle per Region and migrate before EOL.
  • Keep the model in configuration: API Gateway and Lambda in front, AppConfig (validators, gradual rollout, alarm-based rollback) choosing the model, Converse keeping the request format the same. Re-test prompts when switching.
  • Resilience in layers: cross-Region inference (geographic for residency, global for capacity), SDK retries with backoff, a fallback model, a circuit breaker, graceful degradation, and multi-Region deployment for self-hosted models.
  • Customized models: LoRA adapters share one base model as SageMaker inference components; the Model Registry versions and approves them; approval drives CI/CD; deployment guardrails give canary or linear rollout with automatic rollback; shadow tests compare safely.
