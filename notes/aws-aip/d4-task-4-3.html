Task 4.3: Implement monitoring systems for GenAI applications

Knowing what a generative AI application is doing and whether it is doing it well: collecting the right metrics, logs and traces, watching quality as well as uptime, catching unusual token and cost patterns, keeping an audit trail, following tools and agents, keeping vector stores healthy, and diagnosing failures that only language models have.

Overview

Task 4.3

Implement monitoring systems for GenAI applications.

Traditional monitoring asks "is it up, is it fast, is it erroring?" A generative AI application can answer every request quickly with HTTP 200 and still be failing: inventing facts, drifting in tone, looping through tools, or burning tokens. So monitoring has two layers: operational signals (latency, errors, throttles, tokens, cost) and quality signals (groundedness, correctness, guardrail interventions, user feedback). Both need the raw material to investigate: the prompts and responses themselves.

The examples follow the retailer from earlier tasks: a customer support assistant (an agent with order-lookup and returns tools, grounded in a knowledge base of product manuals) and a nightly job that summarizes support tickets. Performance metrics such as time to first token are explained in Task 4.2; cost attribution in Task 4.1.

Tracing FM interactions

A single support question touches API Gateway, a Lambda function or container, the knowledge base, one or more model calls, and tools such as order lookup. Instrument the application with OpenTelemetry through the AWS Distro for OpenTelemetry (ADOT) and turn on CloudWatch Transaction Search once per account, which stores every span as a structured log so you can search and filter traces. Each span records a step's duration, status and attributes (model ID, token counts, tool name), and the trace ties them together under one ID.

CloudWatch's generative AI observability (generally available since October 2025, no extra charge beyond normal CloudWatch telemetry) builds on these: a Model Invocations view for any Bedrock model (invocations, tokens, latency percentiles, errors, and a table of invocation logs), and an AgentCore view for agents, memory, built-in tools and gateways with session and trace drill-down. Agents built with Strands, LangChain or LangGraph send traces through ADOT; AgentCore Runtime emits them automatically.

Since July 2026, AgentCore sends an agent's traces, prompts and logs to one log group per agent (the default for agents created from July 20, 2026), so access and encryption can be scoped per agent. In September 2026 AWS also launched CloudWatch Omni, an AI-first CloudWatch experience with agent observability and evaluation workflows; the building blocks on this page are the same.

Business impact dashboards

Leaders don't read latency percentiles. Publish business events as custom metrics and put them next to the operational ones: conversations resolved without a human, escalations, thumbs up or down, refunds approved by the agent, and cost per resolved conversation (token cost from cost attribution divided by resolutions). The cheapest way to emit them from code is the CloudWatch embedded metric format (EMF): print a JSON log line in a set shape and CloudWatch extracts the metric, while the log line keeps the details for investigation.

A feedback metric in embedded metric format (Python) 
import json, time

DIMS = [["Feature", "Variant"]]
HELPFUL = {"Name": "Helpful",
           "Unit": "Count"}

def record_feedback(feature, variant,
                    helpful, conv_id):
    now = int(time.time() * 1000)
    print(json.dumps({
        "_aws": {
            "Timestamp": now,
            "CloudWatchMetrics": [{
                "Namespace": "Support/AI",
                "Dimensions": DIMS,
                "Metrics": [HELPFUL],
            }],
        },
        "Feature": feature,
        "Variant": variant,
        "Helpful": 1 if helpful else 0,
        "ConversationId": conv_id,
    }))

In Lambda, anything printed goes to CloudWatch Logs, where EMF lines become metrics. The average of Helpful is the helpful rate per feature and prompt variant; ConversationId is kept in the log (not as a dimension, which would create a metric per conversation) so you can find the transcript.

GenAI monitoring

Skill 4.3.2Implement comprehensive GenAI monitoring systems to proactively identify issues and evaluate key performance indicators specific to FM implementations (for example, by using CloudWatch to track token usage; prompt effectiveness; hallucination rates; and response quality, anomaly detection for token burst patterns and response drift, Amazon Bedrock Model Invocation Logs to perform detailed request and response analysis, performance benchmarks, cost anomaly detection)

Model invocation logs

Bedrock model invocation logging is off by default and is set per account and Region. Once on, it records every Converse, ConverseStream, InvokeModel and InvokeModelWithResponseStream call on the bedrock-runtime endpoint to CloudWatch Logs, S3, or both (in the same account and Region).

  • What a record holds: timestamp, account, Region, request ID, operation, model or inference profile ID, the caller's identity.arn, your requestMetadata, the input and output bodies, and input and output token counts.
  • What to include: choose the data types to log (text, image, embedding, video and audio). Bodies over 100 KB and binary data go to S3, so a CloudWatch destination needs an S3 location for large data.
  • Protect it: logs contain customer prompts. Encrypt with KMS, restrict who can read the log group and bucket, set retention, and add a CloudWatch Logs data protection policy to mask personal data such as email addresses and card numbers in queries and exports.
logging.json for put-model-invocation-logging-configuration 
{
  "cloudWatchConfig": {
    "logGroupName": "/bedrock/invoke",
    "roleArn": "LOGGING_ROLE_ARN",
    "largeDataDeliveryS3Config": {
      "bucketName": "BUCKET",
      "keyPrefix": "large/"
    }
  },
  "s3Config": {
    "bucketName": "BUCKET",
    "keyPrefix": "invocations/"
  },
  "textDataDeliveryEnabled": true,
  "imageDataDeliveryEnabled": false,
  "embeddingDataDeliveryEnabled": false
}

Apply it with aws bedrock put-model-invocation-logging-configuration --logging-config file://logging.json. The role must be assumable by bedrock.amazonaws.com and allowed to write log events; the bucket policy must let Bedrock write objects.

Invocation logging is not on unless someone turned it on, and it covers only the Region where it was configured. "We need to see the prompts that produced a bad answer last week" can't be answered retroactively. Enable it in every Region you use (including Regions your cross-Region profiles are called from) before going live.

The GenAI key indicators

IndicatorSignal
Token usageInputTokenCount, OutputTokenCount and cache token metrics per model; per feature or user from invocation logs and requestMetadata
Prompt effectivenessHelpful rate, task success, retries and rephrased questions, per prompt version or variant (custom metrics)
Hallucination rateGuardrail contextual grounding interventions; sampled responses scored for faithfulness by an LLM judge
Response qualityJudge scores (correctness, helpfulness, relevance) on sampled live traffic; user feedback
SafetyInvocationsIntervened by policy type and by input or output
PerformanceLatency, time to first token, throttles, compared with a benchmark baseline

Guardrail metrics are in the AWS/Bedrock/Guardrails namespace. InvocationsIntervened with the dimension GuardrailPolicyType set to ContextualGroundingPolicy counts responses blocked as ungrounded or irrelevant, which makes a practical hallucination-rate signal when divided by invocations. For quality you can't count, sample: score a percentage of live traces with AgentCore Evaluations online evaluation (generally available since March 2026, with built-in LLM-as-a-judge evaluators such as correctness, faithfulness, helpfulness, goal success and tool selection accuracy), or export logged conversations and run Bedrock evaluation jobs on them as your own inference responses.

Anomaly detection: token bursts and drift

Static thresholds fail for traffic with daily and weekly cycles: 50,000 tokens a minute is normal at noon and alarming at 3 a.m. CloudWatch anomaly detection learns a metric's expected band from its history and alarms when the value leaves the band. Use it for token bursts (a loop, a scraper, a prompt injection that triggers huge outputs), sudden drops (a broken client), and slow drift.

Token burst alarm (CloudFormation YAML) 
TokenBurstAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: bedrock-input-token-burst
    ComparisonOperator:
      GreaterThanUpperThreshold
    EvaluationPeriods: 3
    DatapointsToAlarm: 2
    ThresholdMetricId: band
    TreatMissingData: notBreaching
    AlarmActions:
      - !Ref OpsTopic
    Metrics:
      - Id: t
        ReturnData: true
        MetricStat:
          Metric:
            Namespace: AWS/Bedrock
            MetricName: InputTokenCount
          Period: 300
          Stat: Sum
      - Id: band
        Expression: >-
          ANOMALY_DETECTION_BAND(t, 3)

The second argument of ANOMALY_DETECTION_BAND sets the band width (higher is wider, fewer alarms). Without a ModelId dimension the metric covers all models in the Region.

Response drift (answers getting longer, shorter, more refusals, a different tone) shows up as anomalies in OutputTokenCount per request, the refusal or intervention rate, and judge scores over time. On the log side, CloudWatch Logs anomaly detection learns normal log patterns and flags new ones, and the Logs Insights pattern command clusters log lines to show which kinds of errors or responses are growing.

Cost anomaly detection

AWS Cost Anomaly Detection watches spend (about three times a day) with monitors per service, linked account, cost allocation tag or cost category, and alerts subscribers by email or SNS when spend jumps beyond expected. With application inference profiles tagged per application, a tag-based monitor spots the one feature whose Bedrock spend tripled. It complements the token alarm: the alarm fires within minutes, the cost monitor confirms the money impact.

"Detect unusual spikes in token usage without fixed thresholds" points to CloudWatch anomaly detection. "Alert when Bedrock spend for a team rises unexpectedly" points to Cost Anomaly Detection with a tag or cost category monitor. "Analyze the exact prompts and responses" points to model invocation logs. "Track hallucinations" points to contextual grounding interventions and sampled faithfulness evaluations.

Dashboards for each audience

OperationsA CloudWatch dashboard per application: invocations, latency percentiles, throttles, errors, guardrail interventions, token rate against quota, vector store latency. Alarms shown on the same dashboard. With several accounts, CloudWatch cross-account observability lets a monitoring account see metrics, logs and traces from source accounts.

Compliance monitoring

  • AWS Config records configuration of Bedrock resources (guardrails, knowledge bases, data sources, flows, prompts, application inference profiles) and AgentCore resources, so rules can flag drift such as a guardrail changed outside the pipeline.
  • Amazon GuardDuty raises a finding when Bedrock invocation logging is disabled, and its AI Protection plan (July 2026) analyzes Bedrock, AgentCore and SageMaker AI activity for anomalous model invocations, cost harvesting with stolen credentials, and direct prompt injection.
  • Service control policies and organization-level enforced guardrails make compliance a control rather than just a report (Task 3.3).

Forensic traceability

After an incident ("the assistant promised a customer a refund it shouldn't have") you need to reconstruct who asked what, which model and prompt version answered, what context it retrieved, and which tools it called. Three trails together give that:

  1. CloudTrailWho called which API, when, from where. Bedrock model calls (InvokeModel, Converse and their streaming forms) are management events, logged by default. Knowledge base retrievals, agent and flow invocations, guardrail checks and prompt rendering are data events that you must enable with advanced event selectors.
  2. Invocation logsThe actual prompt and response bodies and token counts, linked by request ID and caller ARN.
  3. Traces and application logsThe conversation ID, prompt version, retrieved chunk IDs, tool calls and their results, linked by trace ID.
CloudTrail data events for retrievals and agents (advanced event selectors JSON) 
[
  {"Name": "KB retrievals",

     {"Field": "resources.type",
      "Equals": [
       "AWS::Bedrock::KnowledgeBase"]}
   ]},
  {"Name": "Agent invocations",
   "FieldSelectors": [
     {"Field": "eventCategory",
      "Equals": ["Data"]},

Pass this file to aws cloudtrail put-event-selectors --trail-name TRAIL --advanced-event-selectors file://selectors.json. Data events are billed per event, so select the resource types you need.

Make the evidence trustworthy: deliver trails and logs to a separate log-archive account, turn on CloudTrail log file integrity validation, and use S3 Object Lock for retention periods that nobody can shorten. Put the same correlation IDs in every trail: pass the conversation ID and user ID in requestMetadata so they appear in invocation logs.

One conversation's model calls (Logs Insights) 
fields @timestamp, modelId,
  identity.arn,
  input.inputTokenCount as inT,
  output.outputTokenCount as outT
| filter requestMetadata.conversation
    = "c-7f3a91"
| sort @timestamp asc

AWS CloudTrail Lake closed to new customers on May 31, 2026; existing users keep it with critical fixes only. AWS recommends CloudWatch's unified data management for querying CloudTrail and other logs together. Trails and CloudTrail Insights are unaffected.

User interaction and model behavior patterns

Track how people use the assistant (topics asked, conversation length, abandonment, repeated questions that signal a bad answer) and how the model behaves (answer length, refusal rate, tool use per conversation, citation rate). Run Logs Insights queries or scheduled Athena queries over the invocation logs and publish the results as metrics, so a change in pattern (for example refusals doubling after a prompt release) raises an alarm instead of waiting for complaints.

Tool and agent monitoring

Skill 4.3.4Create tool performance frameworks to ensure optimal tool operation and utilization for FMs (for example, by using call pattern tracking, performance metric collection, tool calling observability and multi-agent coordination tracking, usage baselines for anomaly detection)

In an agent, the model decides which tools to call, with what arguments, and how often. Failures look different from normal code: the agent calls the wrong tool, calls the right tool with bad arguments, retries the same failing call in a loop, or never calls a tool and answers from memory. Monitor each tool like a service, and the agent's choices like a behavior.

What to collect per tool

MeasureShows
Calls per conversation, per toolCall patterns; loops show as a spike
Error and timeout rateA broken backend or bad arguments from the model
Tool execution timeSlow backends, separate from model time
Selection and argument accuracyWhether the model picks the right tool with the right parameters (evaluated, not counted)
Steps per taskReasoning cycles needed; rising values mean confusion or worse prompts

Where the numbers come from: AgentCore Gateway publishes invocations, errors, throttles, Latency and TargetExecutionTime (time inside the tool, so you can tell a slow tool from a slow gateway) per target type (MCP, Lambda or OpenAPI). Strands Agents returns per-tool call counts, successes, errors and time with each result and exports OpenTelemetry spans. AgentCore Evaluations scores tool selection and tool parameter accuracy. Classic Bedrock Agents publish metrics in AWS/Bedrock/Agents and a step-by-step trace when enableTrace is set.

Per-tool metrics from a Strands agent (Python) 
result = agent(question)
tools = result.metrics.tool_metrics
for name, m in tools.items():
    record_tool_metric(
        tool=name,
        calls=m.call_count,
        errors=m.error_count,
        seconds=m.total_time,
    )

record_tool_metric stands for an EMF writer like the feedback example above, with the tool name as a dimension.

Multi-agent coordination

When a supervisor agent hands work to specialist agents (orders, returns, product questions), a single trace must follow the hand-offs. With OpenTelemetry, propagate the trace context on every call between agents so each collaborator's spans join the supervisor's trace; AgentCore and Strands do this for you. Classic Bedrock Agents traces show the collaborator name and caller chain. Watch for hand-off loops (agents passing work back and forth), collaborators that are never used, and one collaborator dominating latency.

Usage baselines

Record what normal looks like for a few weeks: calls per conversation for each tool, the usual ratio of order lookups to refunds, typical latency. Then alarm on departures with CloudWatch anomaly detection on the per-tool metrics. A refund tool suddenly called five times as often relative to conversations may be a prompt injection talking the agent into refunds, not a business trend. CloudTrail Insights can baseline API call rates for data events too.

A tool returning HTTP 200 doesn't mean the agent used it well. Pair tool health metrics with evaluations of tool selection and arguments; otherwise an agent that never calls the order lookup tool and guesses order status looks perfectly healthy.

Vector store operations

Performance monitoring

StoreWatch

OpenSearch Service domainsKNNGraphMemoryUsagePercentage, KNNCircuitBreakerTriggered, KNNCacheCapacityReached, KNNEvictionCount, KNNHitCount and KNNMissCount, plus search latency and JVM memory

Knowledge base ingestionIngestion job statistics and knowledge base logs (documents indexed, skipped, failed)

For OpenSearch k-NN, the graphs must fit in memory: a tripped k-NN circuit breaker or rising evictions mean graphs are being dropped and reloaded, and searches slow down or fail. Fixes are more memory, compression or disk-based mode, or fewer replicas of cold indexes.

Automated index optimization

  • Merge segments after bulk loads or many deletes (OpenSearch force merge in a quiet window), since many small segments mean many small graphs to search.
  • Rebuild with new settings through a blue-green pattern: build a new index with changed HNSW or compression settings, re-embed if the model changed, test recall, then switch an alias. Schedule it with EventBridge Scheduler and Step Functions.
  • Use the managed options: OpenSearch Service can build vector indexes on GPUs and auto-optimize index settings (December 2025); newer OpenSearch Serverless vector collections manage engine and compression settings themselves.
  • Maintain pgvector tables: regular VACUUM and ANALYZE, and rebuild the HNSW index (REINDEX CONCURRENTLY) after large changes.

Data quality validation

Retrieval is only as good as what was indexed. Check after every sync:

  1. Ingestion resultsCompare scanned, indexed, skipped and failed counts with expectations; any failed documents raise an alert.
  2. CoverageEvery product in the catalog has at least one manual chunk; no document is older than its source.
  3. MetadataRequired fields (product line, date, access group) present and valid on every chunk, or filters silently miss them.
  4. Retrieval canariesA fixed set of questions with known correct passages, run after each sync; alert if the right passage drops out of the top results.
Fail the pipeline on ingestion errors (Python) 
agent = boto3.client("bedrock-agent")
job = agent.get_ingestion_job(
    knowledgeBaseId=KB_ID,
    dataSourceId=DS_ID,
    ingestionJobId=JOB_ID,
)["ingestionJob"]
stats = job["statistics"]
failed = stats["numberOfDocumentsFailed"]
reasons = job.get("failureReasons")
if job["status"] != "COMPLETE" or failed:
    raise RuntimeError(
        f"ingestion: {failed} failed, "
        f"reasons {reasons}")

For per-document reasons, deliver the knowledge base's application logs (ingestion status changes and ignored resources) to CloudWatch Logs, S3 or Firehose.

FM troubleshooting

Skill 4.3.6Develop FM-specific troubleshooting frameworks to identify unique GenAI failure modes that are not present in traditional ML systems (for example, by using golden datasets to detect hallucinations, output diffing techniques to conduct response consistency analysis, reasoning path tracing to identify logical errors, specialized observability pipelines)

A traditional ML model returns a number or a label you can compare with ground truth. A foundation model returns free text that can be fluent and wrong, different every time it's asked, and right for the wrong reasons. Its failure modes need their own tools.

Golden datasets

A golden dataset is a curated set of inputs with known-good answers (and, for RAG, the passages that should support them): "How long is the K200 warranty?" with "two years, from the date of purchase" and the manual page. Run it on every prompt, model, retrieval or guardrail change, and on a schedule to catch drift in a managed model.

  • Bedrock evaluation jobs take reference answers (referenceResponse) and score correctness, completeness and, for RAG, faithfulness and citation precision. They can also score responses you generated elsewhere.
  • AgentCore Evaluations accepts ground truth (reference answers, expected tool sequences, behavioral assertions) and runs on demand in CI/CD.
  • Add every confirmed production failure to the set, so it can't come back unnoticed.

A drop in faithfulness on the golden set with stable retrieval scores points at the model or prompt; a drop in context relevance points at retrieval.

Output diffing

Because sampling adds randomness, ask the same question several times, or before and after a change, and compare the answers. Exact text comparison is too strict for prose, so compare meaning (embedding similarity) and facts (extracted fields such as amounts, dates and yes or no):

Consistency check by embedding similarity (Python) 
def embed(text):
    body = json.dumps({"inputText": text})
    r = brt.invoke_model(
        modelId=EMBED_MODEL_ID, body=body)
    out = json.loads(r["body"].read())
    return out["embedding"]

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = sum(x * x for x in a) ** 0.5
    nb = sum(y * y for y in b) ** 0.5
    return dot / (na * nb)

answers = [ask(q) for _ in range(5)]
vecs = [embed(a) for a in answers]
low = min(cosine(vecs[0], v)
          for v in vecs[1:])
if low < 0.85:
    flag_inconsistent(q, answers)

The 0.85 threshold is illustrative; calibrate it on answers you have judged by hand. Inconsistent answers to a factual question are a strong hallucination signal: when the model knows, it tends to say the same thing each time.

Reasoning path tracing

When an answer is wrong, find the step where it went wrong. Was the right passage retrieved? Did the agent call the right tool, with the right arguments? Did it misread the tool's result?

  • Agent traces show each step: in AgentCore and Strands as OpenTelemetry spans (model call, tool call, memory, gateway); in classic Bedrock Agents as orchestration trace events with the model's rationale, the action it invoked and the observation it received.
  • Reasoning content: models with extended or adaptive thinking can return reasoning blocks in the Converse response (reasoningContent), often summarized or partly redacted. Log them with the trace to see the plan the model followed, but treat them as a debugging aid, not proof of why the model answered.
  • Retrieval records: log retrieved chunk IDs and scores per request, so "wrong answer" can be split into "right context, bad answer" and "wrong context".

A specialized observability pipeline

  1. CaptureInvocation logs, traces with conversation and prompt version IDs, retrieval records and feedback.
  2. ScoreSample traffic for online evaluation (faithfulness, correctness, tool accuracy); run guardrail checks inline.
  3. DetectAlarms on score drops, intervention rates and anomaly bands; consistency checks on high-risk answer types.
  4. InvestigateFrom the alarm, open the traces and logs of the affected conversations; CloudWatch investigations can suggest likely causes from related telemetry.
  5. Fix and guardChange the prompt, retrieval or model, add the failing cases to the golden set, and re-run evaluations before release.

"Detect hallucinations before release" points to a golden dataset with reference answers. "Same question, different answers" points to output diffing. "Find which step of the agent's reasoning went wrong" points to traces and reasoning content. "Monitor quality in production" points to online evaluation of sampled traces.

Key takeaways

  • Monitor two layers: operational (latency, errors, throttles, tokens, cost) and quality (grounding, correctness, guardrail interventions, feedback). Combine metrics, OpenTelemetry traces, invocation logs and business metrics; CloudWatch generative AI observability brings them together for Bedrock models and AgentCore agents.
  • Model invocation logging is off by default and per Region: enable it everywhere before launch, send large bodies to S3, encrypt, restrict, set retention and mask personal data.
  • Hallucination signals: contextual grounding interventions and sampled faithfulness scores. Use anomaly detection bands for token bursts and drift, Logs anomaly detection and pattern for log changes, and Cost Anomaly Detection for spend.
  • Forensics: CloudTrail (model calls are management events; knowledge base, agent, flow and guardrail calls are data events), invocation logs and traces linked by shared IDs, kept tamper-evident. CloudTrail Lake is closed to new customers.
  • Tools and agents: per-tool calls, errors and execution time; selection and argument accuracy from evaluations; one trace across agent hand-offs; anomaly baselines on tool usage.
  • Vector stores: watch search latency, errors, capacity and k-NN memory; merge, rebuild blue-green and use managed optimization; validate ingestion results, metadata and retrieval canaries after every sync.
  • FM troubleshooting: golden datasets for regressions and hallucinations, output diffing by meaning for consistency, and traces plus reasoning content to find the failing step.
