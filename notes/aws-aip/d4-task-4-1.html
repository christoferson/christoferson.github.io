Overview

Task 4.1

Implement cost optimization and resource efficiency strategies.

With per-token pricing, cost is roughly requests × tokens per request × price per token, and each factor is a lever: cache to avoid requests, trim to cut tokens, choose models and tiers to lower the price. Output tokens typically cost several times as much as input tokens, so shortening answers often saves more than shortening prompts. None of it helps unless you can see costs by application, team and feature first.

Exact prices change and vary by model and Region; use the Bedrock pricing page for current rates. Related levers covered elsewhere: service tiers, batch and cross-Region inference (Task 1.1), Provisioned Throughput, cascading and distillation (Task 2.2), and token counting (Task 2.5).

Tokens per feature from invocation logs (Logs Insights) 
fields requestMetadata.feature as f,
  input.inputTokenCount as inT,
  output.outputTokenCount as outT
| stats sum(inT) as totalIn,
  sum(outT) as totalOut,
  count() as calls by f
| sort totalOut desc

Multiply the totals by the model's input and output prices to get cost per feature, and divide by calls for cost per request.

Different models tokenize the same text differently (a newer tokenizer can produce noticeably more tokens for the same prompt). After switching models, re-measure token counts, budgets and costs instead of reusing the old figures.

Cost-effective model selection

Price-to-performance

The useful measure isn't price per token but cost per acceptable answer: run the same evaluation set through each candidate (Task 5.1), record the pass rate and the average tokens and cost per request, and divide.

CandidatePass rateCost per requestCost per passing answer
Large model96%$0.0120$0.0125
Mid-size model93%$0.0030$0.0032
Small model71%$0.0006$0.0008, but fails the 90% bar

Illustrative figures. With a 90% quality bar, the mid-size model wins; the small one is cheapest per answer but not good enough on its own, which makes it a candidate for the easy tier below.

Tiers by complexity

  • Route by difficulty: a cheap classifier (or rules) sends simple requests to a small model and complex ones to a larger model; Bedrock intelligent prompt routing does this between two models of one family.
  • Cascade: try the small model and escalate only when a check fails (Task 2.2).
  • Match the inference option to urgency: interactive traffic on Standard (or Priority where latency is worth paying for), tolerant traffic on Flex (about half price where offered), offline jobs in batch (about half price).
  • Avoid the model entirely when deterministic code, a search query or a cached answer will do.

Throughput and utilization

Skill 4.1.3Develop high-performance FM systems to maximize resource utilization and throughput for GenAI workloads (for example, by using batching strategies, capacity planning, utilization monitoring, auto-scaling configurations, provisioned throughput optimization)

How quotas are consumed

Reservation, then reconciliation

When a request starts, Bedrock reserves input tokens plus maxTokens against the tokens-per-minute quota. When it ends, the request is charged input tokens, cache-write tokens and output tokens (for some models output counts several times over, the "burndown rate"), and the unused reservation is returned. Cache reads don't count. Billing is always on actual tokens.

So an oversized maxTokens doesn't raise the bill, but it ties up quota while requests are in flight, which lowers how many can run at once and causes throttling:

SettingReserved at startCharged at end
maxTokens 32,00036,000 tokens9,000 tokens
maxTokens 1,2505,250 tokens9,000 tokens

AWS's example: the same request, same final charge, but the first setting reserves seven times as much quota. Set maxTokens from the real output sizes in the CloudWatch token metrics.

Capacity planning

  1. MeasurePeak requests per minute and average input and output tokens per request, from CloudWatch and invocation logs.
  2. ComputePeak tokens per minute: requests × (input + output × burndown rate), plus headroom for growth and bursts.
  3. CompareWith the on-demand quota per model and Region (and the daily token quota).
  4. Close the gapRequest a quota increase in Service Quotas, spread load with cross-Region inference, move tolerant work to Flex or batch, or reserve capacity (Reserved tier or Provisioned Throughput).
  5. WatchAlarm on throttles and on token usage approaching the quota; the estimated quota usage metric is a rough guide, not a planning basis on its own.

Using reserved capacity well

  • Provisioned Throughput is billed every hour whether used or not: size model units to measured peak tokens per minute, test with a no-commitment purchase before committing for 1 or 6 months, and delete units you no longer need.
  • Batch inference suits large offline volumes: group records into files within the job quotas; results come back unordered, matched by record ID. Batch doesn't use prompt caching.
  • SageMaker AI endpoints pay per instance hour: scale with target tracking on concurrent-request metrics (high-resolution versions react within a minute), add scheduled scaling for known peaks, share GPUs with inference components, and scale idle development endpoints to zero.

Bedrock prompt caching

How it's billed and how to get hits

The model stores the processed state of a prompt prefix up to a cache checkpoint; later requests with the same prefix read it instead of reprocessing. Writing to the cache can cost more than normal input (Anthropic, for example, prices a 5-minute cache write at 1.25 times its input price) and reading costs much less (a tenth, or less on newer models), so a prefix reused even once or twice pays off; check the Bedrock pricing page for each model's rates. Rules for getting hits:

  • Put static content first (tools, then system prompt, then fixed documents) and the variable question last; any change before a checkpoint invalidates everything after it.
  • The cached prefix must reach a minimum length (from 512 to 4,096 tokens depending on the model).
  • Entries live for 5 minutes (1 hour on some models), reset on each hit; low-traffic prompts may expire between requests. Hits aren't guaranteed, especially across Regions with cross-Region inference.
  • Some models (such as Nova) also cache implicitly, which improves latency without a cache-read discount.

Watch the CacheReadInputTokenCount and CacheWriteInputTokenCount metrics: mostly writes and few reads mean the prefix changes too often or expires before reuse.

Exact-match caching

Deterministic request hashing

Hash a normalized form of everything that determines the answer (model, parameters, prompt version, messages, and the tenant or user if the answer is specific to them) and use the hash as a key in DynamoDB (with a TTL) or ElastiCache. Identical requests then return the stored answer. It is only correct when the same request should get the same answer: temperature 0 or fixed outputs, no time-sensitive data, and nothing personal shared across users.

A cache key that changes whenever the answer could (Python) 
import hashlib, json

def cache_key(tenant, model, params,
              prompt_ver, messages):
    norm = []
    for m in messages:
        text = m["content"][0]["text"]
        norm.append({"role": m["role"],
            "text": text.strip().lower()})
    blob = json.dumps(
        {"t": tenant, "m": model,
         "p": params, "v": prompt_ver,
         "msgs": norm},
        sort_keys=True)
    return hashlib.sha256(
        blob.encode()).hexdigest()

Result fingerprinting applies the same idea to outputs: store a hash of each generated result with its inputs, so identical results can be de-duplicated and an unchanged document's summary or embedding is never recomputed.

Semantic caching

Reuse answers to similar questions

  1. EmbedTurn the incoming question into an embedding.
  2. SearchLook for the nearest stored question in a vector index (ElastiCache for Valkey or MemoryDB vector search, or OpenSearch).
  3. DecideIf the similarity is above a threshold (AWS's example uses 0.8 cosine), return the stored answer.
  4. Otherwise callCall the model, then store the question's embedding and the answer with a TTL.

AWS reported large savings with this pattern on a public benchmark (up to 86% lower model cost and 88% lower latency), with the caveat that a similar question doesn't always have the same intent. Protect against wrong reuse: keep the threshold strict and test it, scope the cache per tenant (and never share personal answers), set TTLs and invalidate entries when the source documents change, and cache only answer types where reuse is safe.

"Is my order 1042 delivered?" and "Is my order 1043 delivered?" are nearly identical as embeddings but need different answers. Exclude personal, account-specific and time-sensitive questions from a shared semantic cache.

Edge and API caching

For responses that really are shared (a generated FAQ page, product descriptions, translated help articles), cache whole HTTP responses: CloudFront cache policies at the edge, or API Gateway stage caching for REST APIs (per stage, billed hourly, GET by default, TTL up to an hour, keys from chosen parameters, hit and miss metrics). Never cache authenticated or personalized responses this way unless the cache key includes the user.

Key takeaways

  • Cost is requests × tokens × price; output tokens cost more. Attribute cost with IAM principal attribution (CUR 2.0), application inference profiles (tags), and request metadata in invocation logs; alert with Budgets and anomaly detection.
  • Fewer tokens: compress prompts, prune context (rerank, top-k, summarize history), limit responses (maxTokens, stop sequences, concise or structured output), resize images; re-measure after switching models.
  • Choose models by cost per acceptable answer from evaluations; tier by complexity, cascade, and match the inference option (Standard, Priority, Flex, batch) to urgency.
  • Quota: input plus maxTokens is reserved up front and output may burn down at a multiple; realistic maxTokens raises concurrency. Plan capacity from measured peaks; size Provisioned Throughput to use; scale endpoints on concurrency.
  • Caching: prompt caching for static prefixes (static first, minimum length, short TTL, writes may cost more, reads much less); exact-match caches keyed on a hash of everything that changes the answer; semantic caches with strict thresholds, tenant scoping and TTLs; edge or API caches only for shared content.
