Overview

Task 2.4

Implement FM API integrations.

Model calls differ from ordinary API calls: they take seconds, produce output incrementally, are rate-limited by tokens, and fail in new ways mid-response. Integrations have to choose the right calling style (wait, stream, or queue), protect the model from bad and excessive requests, and keep working when a model is busy.

The examples continue with the retailer's support assistant (interactive chat) and its ticket summarizer (background work).

All are available in every AWS SDK (Python, JavaScript, Java, .NET, Go and others), so any compute environment (Lambda, containers, EC2, on premises) can call them. The modelId can be a model, an inference profile, a managed prompt, a prompt router, a provisioned or custom model deployment, or a Marketplace endpoint. The AWS CLI can't call the streaming operations.

Asynchronous processing with SQS

Queue, then process

When the caller doesn't need the answer immediately (summarize a ticket, classify an email), put the request on an SQS queue and let a Lambda function (or container workers) process it. The queue absorbs bursts, retries failures, and keeps Bedrock calls within quota by limiting how many workers run.

  • Visibility timeout at least 6 times the function timeout, so a message isn't redelivered while still being processed.
  • Dead-letter queue after several receives (5 or more), so a message that always fails stops being retried and can be inspected.
  • Partial batch failures (ReportBatchItemFailures) so only failed messages return to the queue, not the whole batch.
  • Maximum concurrency on the event source (2 to 1,000) caps parallel model calls below the Bedrock quota.
  • Idempotency: delivery is at least once, so processing a message twice must not do the work twice (Powertools for AWS Lambda has an idempotency utility backed by DynamoDB).
  • FIFO queues keep order per message group, for example per customer conversation.
Summarizer: report only failed messages (Python) 
def handler(event, context):
    failed = []
    for rec in event["Records"]:
        try:
            job = json.loads(rec["body"])
            summarize(job)
        except Exception:
            failed.append({
                "itemIdentifier":
                    rec["messageId"]})
    return {"batchItemFailures": failed}
aws lambda create-event-source-mapping \
  --function-name summarizer \
  --event-source-arn "$QUEUE_ARN" \
  --batch-size 5 \
  --function-response-types \
    ReportBatchItemFailures \
  --scaling-config MaximumConcurrency=10

Results go where the requester can find them (DynamoDB or S3), with a notification (SNS, an EventBridge event, or a push over a WebSocket).

Validating requests in API Gateway

Reject bad requests before they cost tokens

REST APIs can validate each request before it reaches your code or the model: required parameters must be present, and the body must match a model (a JSON Schema, draft 4) for its content type. Failures return 400 immediately, at no model cost. Validation is a REST API feature; HTTP APIs don't have it. Limits worth knowing: 10 MB payloads, and mapping templates (VTL) to reshape requests for the backend.

Request model for POST /ask (JSON Schema) 
{
  "$schema":
    "http://json-schema.org/draft-04/schema#",
  "type": "object",
  "required": ["question"],
  "properties": {
    "question": {"type": "string",
      "minLength": 1, "maxLength": 4000},
    "language": {"type": "string",
      "enum": ["en", "es"]}
  },
  "additionalProperties": false
}

A maximum length on free text also caps how many tokens a single request can send to the model.

Real-time responses

Streaming from Bedrock

Reading a ConverseStream

The stream is a sequence of events: messageStart, then contentBlockDelta events carrying text, messageStop with the stop reason, and metadata with token usage and latency. Errors can arrive in the middle of a stream (throttling, a model stream error, service unavailable), after part of the answer was sent, so the client must handle a partial response.

Forward text as it arrives (Python) 
from botocore.exceptions import (
    EventStreamError)

resp = brt.converse_stream(
    modelId=MODEL_ID, messages=messages)
try:
    for ev in resp["stream"]:
        if "contentBlockDelta" in ev:
            d = ev["contentBlockDelta"]
            text = d["delta"].get("text")
            send(text or "")
        elif "messageStop" in ev:
            stop = ev["messageStop"][
                "stopReason"]
        elif "metadata" in ev:
            meta = ev["metadata"]
            usage = meta["usage"]
except EventStreamError:
    # part of the answer was sent:
    # tell the client, offer a retry
    send_error("interrupted")

Server-sent events

Server-sent events (SSE) are a simple one-way stream over an ordinary HTTP response (Content-Type: text/event-stream), with each chunk on a data: line and a blank line between events. Browsers read them natively, and the OpenAI-compatible streaming APIs use this format. Use SSE when only the server sends; use WebSockets when the client also sends during the session (interrupting, follow-up messages).

What an SSE response body looks like 
data: {"text": "To descale"}

data: {"text": " the K200,"}

data: {"text": " fill it with..."}

event: done
data: {"stopReason": "end_turn"}

Pushing over a WebSocket

The backend posts each chunk to the client's connection through the API Gateway management API (@connections). A connection that has closed returns GoneException: stop generating, and don't pay for tokens nobody will read.

Push chunks to a WebSocket client (Python) 
api = boto3.client(
    "apigatewaymanagementapi",
    endpoint_url=WS_CALLBACK_URL)

def send(text):
    api.post_to_connection(
        ConnectionId=connection_id,
        Data=text.encode())

"Users wait several seconds for a blank screen" points to streaming. "One-way token stream to a browser" points to SSE (REST response streaming or a function URL). "Bidirectional chat with interruptions" points to WebSockets. "Live speech conversation" points to the bidirectional streaming API.

Resilience and observability

Errors and what to do about them

ErrorMeaningResponse
429 ThrottlingExceptionYour requests or tokens per minute are used upBack off and retry; cap concurrency; cross-Region inference; a quota increase or reserved capacity
529 overloadedTemporary capacity shortage, not your quotaBack off with jitter, honour Retry-After; another Region or profile
503 service unavailableService-side problemRetry; fall back to another Region, profile or model
408 model timeout, 424 model errorThe model failed to produce a responseRetry once; shorten input; fall back
400 validationBad request (too long, wrong format)Don't retry; fix the request

The SDKs retry transient errors with exponential backoff and jitter (standard retry mode); fallbacks and circuit breakers are covered in Task 1.2, with an example.

Long requests and idle connections

NAT gateways, interface VPC endpoints and Network Load Balancers drop TCP connections idle for 350 seconds. A long reasoning call or a slow stream can be cut silently. Turn on TCP keepalive in the SDK (and set the operating system's keepalive interval below 350 seconds), and raise the SDK read timeout for long calls.

Client for long calls behind a NAT gateway (Python) 
brt = boto3.client(
    "bedrock-runtime",
    config=Config(
        tcp_keepalive=True,
        read_timeout=900,
        retries={"mode": "standard"}))

Rate limiting at the API

API Gateway throttles at several levels, applied in order: per client (usage plans with API keys, including quotas per day or month), per stage and method, the account limit per Region (10,000 requests per second with a 5,000 burst by default), and AWS's own limits. Excess requests get 429. Set per-client limits so one team or customer can't use up the shared model quota, and keep the API's limits aligned with the Bedrock quota behind it.

Tracing across services

X-Ray and OpenTelemetry

A request crosses API Gateway, Lambda, a queue, Step Functions and Bedrock. Distributed tracing follows it end to end, showing where time goes (often the model call) and where errors start. API Gateway REST APIs (not HTTP APIs), Lambda and Step Functions can send traces to X-Ray, viewed in CloudWatch.

The X-Ray SDKs and daemon entered maintenance mode in February 2026; AWS recommends OpenTelemetry instead: the AWS Distro for OpenTelemetry or OpenTelemetry SDKs to instrument code, the OpenTelemetry Lambda layer (which also feeds CloudWatch Application Signals), and the CloudWatch agent or OpenTelemetry Collector in place of the daemon. CloudWatch Transaction Search stores all spans as logs so any single request can be found.

Add the model ID, token counts and prompt version as trace attributes (or requestMetadata on the call), so a slow or expensive request can be tied to the model and prompt that caused it (Task 4.3).

    "classify":
        "us.amazon.nova-micro-v1:0",

    default = ROUTES["answer"]
    return ROUTES.get(task, default)

Content-based routing with Step Functions

  1. ClassifyA small model (Bedrock InvokeModel task) labels the request: order, how_to, complaint.
  2. ChooseA Choice state branches on the label.
  3. SpecializeOrders go to an agent with order tools; how-to questions to a knowledge base query with a mid-size model; complaints to a stronger model and a human review queue.
  4. DefaultUnrecognized labels go to the general path.

Metric-based routing

Publish per-model latency, error rate and throttles (Bedrock's own CloudWatch metrics, plus your own), and let the router prefer the healthiest option: if the primary model's throttles or latency alarm fires, AppConfig flips the route to an alternative profile or Region until it recovers.

Key takeaways

  • Pick the API by style: Converse or InvokeModel to wait, the streaming versions for chat, StartAsyncInvoke for long jobs to S3, bidirectional streaming for speech, OpenAI-compatible endpoints for OpenAI SDK code; any SDK and compute can call them.
  • Queue background work in SQS: visibility timeout of 6 times the function timeout, a dead-letter queue, partial batch failures, maximum concurrency below the model quota, idempotent processing.
  • Validate at the edge with API Gateway REST request validators and JSON Schema models (400 before any tokens are spent); cap input length.
  • Stream to users: ConverseStream events (deltas, stop reason, metadata, mid-stream errors); REST response streaming, function URL SSE, WebSockets with @connections, or AppSync subscriptions.
  • Resilience: retry 429, 529 and 503 with backoff and jitter, don't retry 400s, fall back to other models or Regions, enable TCP keepalive for long calls, throttle per client with usage plans; trace with OpenTelemetry (X-Ray SDKs are in maintenance).
  • Route by static configuration, a classifier and Choice state, intelligent prompt routing, live metrics, API Gateway rules, or a model gateway.
