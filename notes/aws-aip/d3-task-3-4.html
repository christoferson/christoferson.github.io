Overview

Task 3.4

Implement responsible AI principles.

AWS describes responsible AI in dimensions such as fairness, explainability, transparency, safety and governance (Task 3.3). This task covers three of them in practice: transparency (users can see what the system based its answer on and how confident it is), fairness (quality doesn't drop for some groups of people), and policy compliance (written rules are enforced and checked automatically).

The examples continue the retailer's support assistant, which serves customers of different ages, languages and backgrounds, and must follow a published customer communication policy.

"Prompt Flows" in the exam guide is now Amazon Bedrock Flows. SageMaker Clarify, often used for bias metrics, is no longer open to new customers; use Bedrock evaluations and the open-source fmeval library for foundation models.

Explaining an answer

Model reasoning

Reasoning models can return their reasoning separately from the answer: in Converse, as reasoningContent blocks next to the text. What you get varies by model, which matters for what you can show users:

  • Some return the full reasoning text; newer Claude models return a summary of it (while billing for the full reasoning); Amazon Nova 2 models return the reasoning redacted; some content may come back encrypted.
  • Reasoning blocks carry a signature and must be sent back unchanged in later turns of the conversation.
  • Raw reasoning can be long, tentative and confusing for users, and isn't guaranteed to reflect how the answer was produced.

A dependable user-facing explanation is therefore usually something you ask for: a short "why" field in a structured output, written for the user, alongside the sources used. Keep raw reasoning in logs for reviewers.

Answer with its own explanation and sources (JSON Schema) 
{
  "type": "object",
  "properties": {
    "answer": {"type": "string"},
    "explanation": {"type": "string"},
    "sources": {"type": "array",
      "items": {"type": "string"}},
    "confidence": {"type": "string",
      "enum": ["high", "medium", "low"]}
  },
  "required": ["answer", "explanation",
               "sources", "confidence"],
  "additionalProperties": false
}
Separate reasoning from the answer (Python) 
answer, reasoning = None, None
msg = resp["output"]["message"]
for block in msg["content"]:
    if "reasoningContent" in block:
        rc = block["reasoningContent"]
        if "reasoningText" in rc:
            rt = rc["reasoningText"]
            reasoning = rt["text"]
    elif "text" in block:
        answer = block["text"]
# reasoning goes to the audit log,
# the answer to the user
log_for_review(reasoning)

Agent reasoning traces

Seeing every step

With tracing enabled, a Bedrock agent (Agents Classic) returns trace events for each step: pre-processing (was the input valid, and why), orchestration (the agent's rationale, the action or knowledge base it chose, its input, and the observation returned), post-processing, guardrail assessments, and failure reasons. In multi-agent setups the trace includes the chain of collaborators. AgentCore agents and frameworks such as Strands emit OpenTelemetry traces with a span per model call and tool call, viewable in CloudWatch. Traces let reviewers see why an agent refunded an order, not just that it did.

Presenting evidence

Show the sources behind an answer: RetrieveAndGenerate returns citations linking each span of the answer to the documents it came from (with their location and metadata; for PDFs in some stores, the page number); Converse can return citations from documents passed in the request. Display them as links or footnotes beside the text they support. (If you customize the knowledge base prompt template, keep its output format instruction placeholder, or citations stop being returned.)

Confidence and uncertainty

Signals you can use

Bedrock models generally don't expose token probabilities, so confidence comes from signals around the answer:

  • Retrieval scores and reranker scores: weak matches mean weak evidence.
  • The contextual grounding score from a guardrail: how well the answer is supported by the sources.
  • Automated Reasoning findings for rule-based answers.
  • Agreement between several samples or models (self-consistency).
  • A judge model's rating, or the model's own stated confidence in a structured field (useful but not calibrated).

Publish these as custom CloudWatch metrics (per feature and model) to quantify uncertainty over time and alarm on drops, and use them in the interface: show "high confidence" answers directly, add a caution or a "talk to an agent" option for low ones.

Disclosure and provenance

Tell users when they are talking to AI and label AI-generated content. For images and video, Amazon Nova Canvas and Titan Image Generator add an invisible watermark, and Nova Canvas and Nova Reel attach content credentials (C2PA) that anyone can verify; Bedrock's watermark detection (in preview) checks whether an image was generated by those models.

Fairness evaluations

Skill 3.4.2Apply fairness evaluations to ensure unbiased FM outputs (for example, by using pre-defined fairness metrics in CloudWatch, Amazon Bedrock Prompt Management and Amazon Bedrock Prompt Flows to perform systematic A/B testing, Amazon Bedrock with LLM-as-a-judge solutions to perform automated model evaluations)

What fairness means for a GenAI app

For a support assistant, fairness means every group of customers gets equally correct, helpful and respectful answers: a question asked by "Maria" or "Mohammed", in English or Spanish, by an older or younger customer, should get the same quality of reply, and replies should contain no stereotypes, positive or negative. Bias shows up as differences in quality, tone, refusals or recommendations between groups.

Measuring it

Counterfactual test sets

Build pairs or sets of prompts that are identical except for a demographic attribute (name, gender, age, language, nationality), tag each with a category, and run them through a Bedrock evaluation. Evaluation datasets accept a category field and report scores per category, so a gap between groups is visible directly.

Counterfactual prompts, one line each in the dataset (JSONL) 
{"prompt": "Hi, I'm Maria. My order
 1042 is late. Can I get a refund?",
 "category": "name-female"}
{"prompt": "Hi, I'm David. My order
 1042 is late. Can I get a refund?",
 "category": "name-male"}
{"prompt": "Hola, soy Maria. Mi pedido
 1042 llega tarde. Reembolso?",
 "category": "lang-es"}

Each record is a single line in the real file; they are wrapped here to fit.

Metrics

  • LLM-as-a-judge: the built-in Stereotyping metric checks responses for stereotypes of any kind; Harmfulness and Refusal catch harmful content and unequal refusals; quality metrics (correctness, helpfulness, professional style and tone) compared across categories show unequal quality. Up to 10 custom metrics per job encode your own fairness criteria with a rating rubric.
  • Programmatic evaluations use built-in datasets such as BOLD and RealToxicityPrompts for toxicity and robustness; there's no dedicated bias metric, so per-category comparisons do that job.
  • The open-source fmeval library includes a prompt stereotyping evaluation (based on the CrowS-Pairs dataset) covering attributes such as race, gender, religion, age and disability.

Fairness metrics in CloudWatch

Evaluation jobs are snapshots. To watch fairness continuously, score a sample of live conversations (with a judge, or with user ratings), attach the group where you lawfully have it (language, region, or attributes inferred only for testing), and publish scores as custom metrics with the group and prompt variant as dimensions. Alarm when the gap between the best- and worst-served group exceeds a threshold.

Publish a helpfulness score per group (Python) 
cw.put_metric_data(
    Namespace="SupportAssistant/Fairness",
    MetricData=[{
        "MetricName": "Helpfulness",
        "Dimensions": [
            {"Name": "Group",
             "Value": group},
            {"Name": "PromptVersion",
             "Value": prompt_version}],
        "Value": judge_score,
    }],
)

A/B testing prompts for fairness

  1. VariantsPrompt Management holds the current prompt and a candidate (for example with added guidance on inclusive, consistent tone), each a version.
  2. AssignThe application assigns each user a variant by hashing the user ID (Bedrock Flows has no built-in traffic split, but a condition node can route on the assigned variant to prompt nodes that reference each version).
  3. MeasureScore both variants per group with the same judge and metrics.
  4. DecideAdopt the candidate only if it improves the worst-served group without hurting others; record the result.
Stable variant assignment (Python) 
import hashlib

VARIANTS = {"A": PROMPT_V4_ARN,
            "B": PROMPT_V5_ARN}

def variant_for(user_id, b_share=0.1):
    h = hashlib.sha256(
        user_id.encode()).digest()[0]
    if h < 256 * b_share:
        return "B"
    return "A"

Testing only on English, generic prompts hides bias. Include every language and customer group the system serves, and compare per group: an average score can look fine while one group is served much worse.

Policy-compliant systems

Skill 3.4.3Develop policy-compliant AI systems to ensure adherence to responsible AI practices (for example, by using Amazon Bedrock guardrails based on policy requirements, model cards to document FM limitations, Lambda functions to perform automated compliance checks)

From policy text to guardrail

Translate each rule in the organization's AI or communication policy into the control that enforces it:

Policy statementControl
"The assistant does not give legal, medical or investment advice."Denied topics, one per subject
"No offensive or discriminatory language."Content filters (hate, insults) on input and output; word filters for specific terms
"Card and national ID numbers are never displayed."Sensitive information filters: block or mask those entity types
"Answers must be based on our published policies."Contextual grounding check; Automated Reasoning policy built from the policy document
"Refunds follow the refund rules exactly."Automated Reasoning checks; refund tool with server-side rules
"Every assistant uses the approved safeguards."Guardrail enforced by organization or account policy, or required by the IAM condition key (Task 2.3)

Documenting limitations

A model card (Task 3.3) records what the system is for and, as important, what it is not for: known failure modes (for example weaker answers in some languages), groups where evaluation showed gaps, and required human oversight. AWS's AI Service Cards do the same for AWS models and features; reference them for the models you use. Link the card's limitations to the controls that mitigate them.

Automated compliance checks

At three points

  • Before deployment (policy as code): a CloudFormation Guard rule in the pipeline rejects templates that create agents without a guardrail, knowledge bases without customer managed keys, or log groups without retention.
  • Continuously (configuration): AWS Config has no managed rule that checks a guardrail is attached, so write a custom rule (a Lambda function or Guard rule) that evaluates agents, flows and application settings, with automatic remediation where possible.
  • At run time (outputs): a Lambda function (in the application, a Flows Lambda node, or an agent's post-processing step) checks each response against rules the guardrail can't express: required disclaimers present, no promises outside policy, links only to approved domains, the correct template for regulated communications.
Pipeline rule: every agent must have a guardrail (CloudFormation Guard) 
let agents = Resources.*[
  Type == 'AWS::Bedrock::Agent' ]

rule agents_have_guardrail
    when %agents !empty {
  # a guardrail block with an ID
  %agents.Properties.GuardrailConfiguration exists
  %agents.Properties.GuardrailConfiguration.GuardrailIdentifier exists
}

Keep each property path on one line. Test a rule like this with cfn-guard validate against your templates, then run it in CodeBuild before deployment so a failed rule stops the pipeline.

"Show users why the assistant answered as it did" points to citations and a user-facing explanation (not raw model reasoning). "Prove the assistant treats customers equally" points to counterfactual evaluation sets with per-category scores and per-group CloudWatch metrics. "Ensure no agent is deployed without safeguards" points to a policy-as-code check in the pipeline plus a custom Config rule.

Key takeaways

  • Transparency: reasoning content varies by model (full, summarized, redacted) and is for reviewers; give users a structured explanation plus citations from RetrieveAndGenerate or document citations; agent traces show rationale, chosen actions and observations.
  • Confidence without token probabilities: retrieval and rerank scores, grounding scores, Automated Reasoning findings, self-consistency and judges, published as custom CloudWatch metrics and reflected in the interface. Disclose AI use; Nova and Titan images carry watermarks and content credentials.
  • Fairness: counterfactual prompt sets tagged by category, evaluated per category with LLM-as-a-judge (Stereotyping, Harmfulness, Refusal, quality metrics, custom metrics) or fmeval; per-group metrics in CloudWatch with gap alarms; A/B tests of prompt versions judged on the worst-served group.
  • Policy compliance: map each policy statement to a guardrail policy, Automated Reasoning or a tool rule; document limitations in model cards; check automatically before deployment (Guard rules), continuously (custom Config rules) and at run time (Lambda output checks).
