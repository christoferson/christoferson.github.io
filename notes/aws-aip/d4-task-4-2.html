Task 4.2: Optimize application performance

Making a generative AI application feel fast and stay fast under load: showing the first words sooner, doing less work per request, retrieving the right passages quickly, keeping many requests in flight without throttling, and finding where the time actually goes.

Overview

Task 4.2

Optimize application performance.

A model call has two phases. In prefill the model reads the whole prompt; its length sets the time to first token (TTFT). In decode the model writes the answer one token at a time; output length divided by the output tokens per second (OTPS) sets the rest. So total latency is roughly TTFT plus output tokens ÷ OTPS. Every technique on this page shortens one of those terms, hides it from the user, or stops requests from waiting in a queue first.

The examples follow the retailer from earlier tasks: a customer support assistant that answers questions about products (the K200 kettle and others) from a knowledge base of manuals, and a nightly job that summarizes support tickets. Cost-focused versions of some levers (caching, quotas, Provisioned Throughput) are in Task 4.1; here the goal is speed.

Responsive systems

Streaming

For a chat interface, streaming is the first fix: the user starts reading after the time to first token, typically well under the full response time. Use ConverseStream (or InvokeModelWithResponseStream) and forward each text delta to the browser over server-sent events or a WebSocket (the transport options are in Task 2.4). The stream's final metadata event carries token usage and the total latency, which is also how you measure TTFT from the client:

Measuring time to first token (Python) 
import time
import boto3

brt = boto3.client("bedrock-runtime")

t0 = time.monotonic()
resp = brt.converse_stream(
    modelId=MODEL_ID,
    messages=msgs,
)
ttft = None
for ev in resp["stream"]:
    if "contentBlockDelta" in ev:
        if ttft is None:
            ttft = time.monotonic() - t0
        block = ev["contentBlockDelta"]
        d = block["delta"]
        send(d.get("text", ""))
    if "metadata" in ev:
        meta = ev["metadata"]
        usage = meta["usage"]
        metrics = meta["metrics"]
        total_ms = metrics["latencyMs"]

send stands for your code that pushes text to the client. A non-streaming Converse response has the same metrics.latencyMs field.

Pre-computation

Many questions are predictable: "how do I descale the K200", "what is the return window", the summary of a product's reviews. Generate those answers ahead of time, for example with a nightly batch inference job over the top questions and every product page, store them in DynamoDB or S3 keyed by question or product, and serve them in milliseconds. Pre-compute other expensive inputs too: document summaries, embeddings and extracted metadata at ingestion time rather than per query. Regenerate when the source changes (an S3 event or a knowledge base sync) and set an age limit so stale answers expire.

Latency-optimized inference

Bedrock can run some models on faster infrastructure when the request sets performanceConfig to optimized (the default is standard). It works with Converse, ConverseStream and InvokeModel, only through cross-Region inference profiles, and only for a short list of models and Regions. When the latency-optimized usage quota is used up, Bedrock quietly serves the request at standard latency and price, so read the setting the response reports back:

Requesting latency-optimized inference (Python) 
resp = brt.converse(
    modelId=PROFILE_ID,
    messages=msgs,
    performanceConfig={
        "latency": "optimized"},
)
# "standard" here means it fell back
perf = resp["performanceConfig"]
used = perf["latency"]

This feature is still marked preview, and its model list has stayed with older model generations (Nova Pro, Claude 3.5 Haiku, Llama 3.1). Learn the pattern and the parameter name; check the current list before relying on it. For queueing delay under heavy load, the Priority service tier (serviceTier set to priority) serves requests ahead of Standard and Flex for a premium.

Parallel requests

When a workflow has independent steps, run them at the same time. To answer "Compare the K200 and K300 for a small kitchen", the assistant can retrieve and summarize each product concurrently, then make one final call to compare. Total time becomes the slowest branch plus the final step instead of the sum. Step Functions Parallel and Map states do the same in orchestrated workflows, and agent frameworks can call several tools at once.

Independent calls in parallel (Python) 
from concurrent.futures import (
    ThreadPoolExecutor)

def summarize(product):
    msgs = [{"role": "user", "content": [
        {"text": prompt_for(product)}]}]
    r = brt.converse(modelId=MODEL_ID,
                     messages=msgs)
    out = r["output"]["message"]
    return out["content"][0]["text"]

with ThreadPoolExecutor(2) as pool:
    notes = list(pool.map(
        summarize, ["K200", "K300"]))
answer = compare(notes)

A boto3 client can be shared across threads; create it once. Parallel branches each use quota at the same moment, so they need the concurrency limits described under Throughput.

Benchmarking

Measure before and after every change, with realistic prompts (real lengths, real retrieved context) and realistic concurrency, because a model that is fast for one user can queue under fifty.

  1. Define the workloadSample real prompts and record their input and output token distributions and the expected number of concurrent users.
  2. Choose the metricsTTFT and total latency at p50 and p90 or p99, output tokens per second, requests per minute sustained, error and throttle rate, and cost per request.
  3. Run the loadRamp concurrency in steps, changing one thing at a time (model, tier, prompt length, Region profile).
  4. Compare against qualityA faster configuration only wins if its answers still pass your evaluations.

AWS's open-source LLMeter library (awslabs) runs latency and throughput tests against Bedrock and other endpoints. For self-hosted models, SageMaker AI's inference recommendations benchmark a model on real instances and report TTFT, inter-token latency, latency percentiles, throughput and cost (see Resource allocation).

"Users wait too long before seeing anything" points to streaming. "The same questions are asked all day" points to pre-computation or caching. "A multi-part request runs its steps one after another" points to parallel requests. "Time-sensitive application, supported model" points to latency-optimized inference.

Retrieval performance

Skill 4.2.2Enhance retrieval performance to improve the relevance and speed of retrieved information for FM context augmentation (for example, by using index optimization, query preprocessing, hybrid search implementation with custom scoring)

In a RAG application, retrieval runs before the model sees anything, so its latency adds straight to TTFT, and its quality decides how much context you need to send. Better retrieval is usually faster overall: fewer, better passages mean a shorter prompt and a shorter prefill.

Index optimization

Vector indexes use approximate nearest-neighbor search, most often an HNSW graph. Its settings trade recall against speed and memory:

SettingRaise it forCost of raising it
m (links per node)Recall on large or high-dimension indexesMore memory, slower build; fixed at build time
ef_constructionA better-quality graphSlower indexing; fixed at build time
ef_searchRecall per querySlower queries; tunable at query time
Compression (quantization)Lower memory, bigger indexes per nodeSome recall, recovered by rescoring

In OpenSearch the defaults are m 16, ef_construction 100 and ef_search 100, with the faiss engine (the older nmslib engine is deprecated). To fit large indexes in less memory, set mode to on_disk: vectors are compressed (32× by default) for a fast first pass, then the best candidates are rescored with full-precision vectors from disk. Other options are fp16 or byte vectors. In Aurora PostgreSQL with pgvector, prefer an HNSW index to IVFFlat for its better speed-recall balance, and tune hnsw.ef_search (default 40) per transaction.

Disk-based vector field (OpenSearch) 
PUT manuals-v2
{
  "settings": {"index.knn": true},
  "mappings": {"properties": {
    "embedding": {
      "type": "knn_vector",
      "dimension": 1024,
      "space_type": "innerproduct",
      "mode": "on_disk",
      "compression_level": "32x"
    },
    "product_line": {"type": "keyword"}
  }}
}

Other index-level speedups: use a smaller embedding dimension if the model offers one (Titan Text Embeddings V2 supports 256, 512 or 1024), keep shards sized sensibly, and split very different content into separate indexes so each search scans less. For the newest OpenSearch Serverless vector collections, AWS manages engine and compression settings for you.

Query preprocessing

Clean and shape the query before searching. Cheap steps cost almost nothing: normalize spacing and case, strip greetings and signatures, and pull out exact identifiers (order numbers, model codes such as K200) for a keyword or metadata filter. Model-based steps (rewriting a follow-up into a standalone question, decomposing a comparison into sub-questions) improve relevance but add a model call each; use a small, fast model, run sub-queries in parallel, and cache rewrites of frequent questions. Knowledge bases offer decomposition through the QUERY_DECOMPOSITION query transformation, which trades some latency for accuracy on multi-part questions. The full set of rewriting techniques is in Task 1.5.

Metadata filters are also a speed tool: filtering on product_line or document date shrinks the candidate set before ranking. In a knowledge base, keep numberOfResults as low as quality allows (1 to 100, default 5).

Hybrid search with custom scoring

Hybrid search runs a keyword (BM25) query and a vector query and merges the results, which handles both exact codes and paraphrases. The scores live on different scales, so merging needs a scoring method, and that is where you customize:

Normalize and combine

An OpenSearch normalization processor rescales each list (min_max, l2 or z_score) and combines them by arithmetic, geometric or harmonic mean, with weights per query that sum to 1. Tune the weights on a labeled test set: more keyword weight for catalogs full of part numbers, more vector weight for free-text questions.

Reciprocal rank fusion

A score ranker processor with RRF (OpenSearch 2.19 and later) ignores raw scores and adds 1 ÷ (rank constant + rank) for each list a document appears in. It needs no score tuning, which makes it a robust starting point.

RRF search pipeline (OpenSearch) 
PUT _search/pipeline/hybrid-rrf
{
  "phase_results_processors": [{
    "score-ranker-processor": {
      "combination": {
        "technique": "rrf",
        "rank_constant": 60
      }
    }
  }]
}

Use the pipeline with a hybrid query that contains the keyword and vector sub-queries (?search_pipeline=hybrid-rrf). In a Bedrock knowledge base you set overrideSearchType to HYBRID (Aurora, OpenSearch Serverless and MongoDB stores) and the service does the merging. A reranker can then reorder the merged list; retrieving 20 and reranking to 5 improves relevance but adds a model call, so measure its latency.

"Recall is fine but searches are slow and memory is high" points to compression or disk-based mode. "Missed results, latency to spare" points to a higher ef_search. "Exact codes missed" points to hybrid search. "Combine keyword and vector scores without tuning" points to RRF.

Throughput

Skill 4.2.3Implement FM throughput optimization to address the specific throughput challenges of GenAI workloads (for example, by using token processing optimization, batch inference strategies, concurrent model invocation management)

Generative AI throughput is limited by tokens, not just requests: Bedrock enforces tokens per minute and requests per minute per model, a single request can hold thousands of tokens of quota for many seconds, and long outputs keep a request open. A throughput plan has to manage all three.

Token processing

  • Set a realistic maxTokens. Bedrock reserves input plus maxTokens against the quota when a request starts, so an oversized value blocks other requests even though you're only billed for what's generated (Task 4.1 has AWS's worked example).
  • Shorter prompts finish prefill faster and use less quota: trim history, send fewer retrieved passages, and put static instructions first so prompt caching can skip re-reading them.
  • Shorter outputs finish decode faster: ask for concise or structured answers and use stop sequences.

Concurrent invocation management

Unlimited concurrency doesn't raise throughput past the quota; it just turns the excess into ThrottlingException (HTTP 429) errors and retry storms. AWS's guidance for scaling Bedrock traffic:

  1. Bound concurrencyCap requests in flight per process with a semaphore or worker pool, and queue the rest in a bounded queue (SQS for asynchronous work).
  2. Limit by tokens, not just requestsA client-side limiter that counts expected tokens (input plus maxTokens) keeps you under the tokens-per-minute quota; a requests-only limiter doesn't.
  3. Retry with backoff and jitterRetry throttles with exponential backoff and jitter within a fixed retry budget. HTTP 503 means service capacity rather than your quota, and also deserves a backoff.
  4. Set timeouts carefullyMake connect and read timeouts longer than a valid long generation, so the client doesn't give up and resend work the model is still doing.
  5. Add capacityCross-Region inference profiles spread load across Regions (geographic profiles keep data in one geography; global profiles use any commercial Region). Provisioned Throughput or the Reserved tier gives dedicated capacity for sustained load. Ramp traffic up gradually.
Bounded concurrency with retries (Python) 
import threading
import boto3
from botocore.config import Config

cfg = Config(
    retries={"total_max_attempts": 6,
             "mode": "standard"},
    connect_timeout=5,
    read_timeout=120,
    max_pool_connections=32,
)
brt = boto3.client("bedrock-runtime",
                   config=cfg)
# at most 16 calls in flight
slots = threading.BoundedSemaphore(16)

def ask(msgs):
    with slots:
        return brt.converse(
            modelId=PROFILE_ID,
            messages=msgs,
            inferenceConfig={
                "maxTokens": 400},
        )

The standard retry mode backs off with jitter and retries throttling errors. Keep the connection pool at least as large as the number of concurrent calls.

Batch inference strategies

Work that doesn't need an answer now (the nightly ticket summaries, pre-computed FAQ answers, re-tagging a catalog) belongs in batch inference: CreateModelInvocationJob reads a JSONL file from S3 in which each line has a recordId and a modelInput (in InvokeModel or Converse format), and writes results to S3. Batch runs outside your on-demand quota at a lower price, so it doesn't slow the live assistant.

  • Jobs have per-model quotas: a minimum and maximum number of records per job, and size limits per file and per job. Split large workloads into several jobs and stay under the in-progress job limit.
  • Output order isn't guaranteed: match results by recordId.
  • Set the job timeout (24 to 168 hours) and react to completion through EventBridge state-change events rather than polling.
  • For small or urgent batches below the job minimum, use bounded concurrent on-demand calls or the Flex tier instead.
One batch record (JSONL, Converse format) 
{"recordId": "T-20261103-0001",
 "modelInput": {
  "messages": [{
   "role": "user",
   "content": [{
    "text": "Summarize: TICKET"}]}],
  "inferenceConfig": {
   "maxTokens": 300}}}

Shown across lines for reading; in the file each record is one line, and TICKET stands for the full ticket text.

"Thousands of documents overnight, cost matters, no user waiting" points to batch inference. "Throttling at peak, real-time traffic" points to bounded concurrency with backoff, then cross-Region inference or reserved capacity. "Requests throttled though few tokens are generated" points to an oversized maxTokens.

Inference parameters

Skill 4.2.4Enhance FM performance to achieve optimal results for specific GenAI use cases (for example, by using model-specific parameter configurations, A/B testing to evaluate improvements, appropriate temperature and top-k/top-p selection based on requirements)

What the parameters do

At each step the model scores every possible next token. Sampling parameters decide how it picks one:

TemperatureSharpens or flattens the probabilities. Low values (near 0) make the model pick the likeliest tokens, giving consistent, repeatable output; high values (toward 1) make less likely tokens more common, giving variety. Range 0 to 1 in Converse.

Top-pSamples only from the smallest set of tokens whose probabilities add up to p (0.9 keeps the top 90% of probability mass). Lower values cut off unlikely tokens.

Top-kSamples only from the k likeliest tokens. Not every model supports it.

Max tokens and stop sequencesDon't change how tokens are chosen, but cap the length. These are the parameters that affect speed: decode time grows with output length, while temperature and top-p barely change it.

Choosing values by use case

Use caseStarting pointWhy
Classification, extraction, JSON outputTemperature 0 to 0.2, short max tokens, stop sequenceThe same input should give the same, parseable output
Grounded answers (RAG support assistant)Low temperature (about 0.2 to 0.3)Stay close to the retrieved passages; fewer invented details
Code generationLow temperatureCorrectness matters more than variety
Marketing copy, brainstormingHigher temperature (0.7 to 1)Variety is the point; generate several and pick

These are starting points: defaults and sensible ranges differ per model, so tune with evaluations. Change one sampling parameter at a time; the usual advice is to adjust temperature or top-p, not both.

Converse's inferenceConfig has four common fields: maxTokens, stopSequences, temperature and topP. Model-specific parameters, such as Claude's top_k, go in additionalModelRequestFields:

Common and model-specific parameters (Python) 
resp = brt.converse(
    modelId=MODEL_ID,
    messages=msgs,
    inferenceConfig={
        "temperature": 0.2,
        "maxTokens": 300,
        "stopSequences": ["</answer>"],
    },
    additionalModelRequestFields={
        "top_k": 50},
)

Some newer models reject requests that set both temperature and topP (Claude Sonnet 4.5 and Haiku 4.5 accept one or the other). Code that worked with an older model can fail after a model upgrade; check each model's parameter page.

A/B testing

A parameter, prompt or model change is an improvement only if it measurably helps on real traffic or a representative test set. Test offline first, then online:

  1. Offline comparisonBedrock Prompt Management stores prompt variants (different text, model or parameters) and the console compares up to three side by side. A Bedrock evaluation job (automatic metrics, LLM-as-a-judge or human review) scores each candidate on the same dataset.
  2. Online splitRoute a share of live traffic to the candidate with a feature flag. AWS AppConfig supports multi-variant feature flags, and AppConfig experimentation adds A/B and multivariate tests with gradual rollouts.
  3. MeasureTag each request with its variant (for example in requestMetadata) and compare quality signals (thumbs up, resolution rate, judge scores), latency and token cost per variant.
  4. DecidePromote the winner as a new prompt version or flag value; roll back by switching the flag.

Amazon CloudWatch Evidently, AWS's earlier service for feature flags and A/B experiments, was discontinued on October 17, 2025. Use AWS AppConfig feature flags and AppConfig experimentation instead.

Resource allocation

Skill 4.2.5Create efficient resource allocation systems specifically for FM workloads (for example, by using capacity planning for token processing requirements, utilization monitoring for prompt and completion patterns, auto-scaling configurations that are optimized for GenAI traffic patterns)

Planning capacity in tokens

Requests per second alone is a poor capacity unit for generative AI: a request with a 10,000-token prompt and a 1,000-token answer needs far more capacity than a one-line question. Plan in tokens:

  1. Measure the shapeFrom invocation logs, find input and output tokens per request at p50 and p95, per feature.
  2. Find the peakRequests per minute at the busiest minute, not the daily average.
  3. ConvertPeak tokens per minute is roughly peak requests per minute × (input + output tokens at p95). Compare with the model's tokens-per-minute and requests-per-minute quotas (some models count output tokens several times over).
  4. Check concurrencyConcurrent requests are roughly requests per second × average latency in seconds; long outputs mean more requests open at once.
  5. Choose the capacityOn-demand with a quota increase, cross-Region profiles, Provisioned Throughput or the Reserved tier for a steady base, or a self-hosted endpoint sized by benchmark.
Prompt and completion sizes per minute (Logs Insights) 
fields input.inputTokenCount as inT,
  output.outputTokenCount as outT
| stats count() as calls,
  pct(inT, 95) as in95,
  pct(outT, 95) as out95,
  sum(inT) + sum(outT) as tokens
  by bin(1m)
| sort tokens desc
| limit 20

The top rows are the busiest minutes: their token totals are the number to compare with the tokens-per-minute quota.

Monitoring prompt and completion patterns

Watch for drift in the shape of traffic, not just its volume. Prompts that grow week by week (longer histories, more retrieved chunks) push up TTFT and quota use; answers that grow push up decode time. Useful signals in the AWS/Bedrock namespace are InputTokenCount, OutputTokenCount, Invocations, InvocationThrottles, InvocationLatency and TimeToFirstToken. EstimatedTPMQuotaUsage approximates quota consumption, but AWS warns not to rely on it alone for capacity planning. With service tiers, the ResolvedServiceTier dimension shows which tier actually served each request.

Auto scaling for GenAI traffic

Bedrock on-demand scales for you within quota. Self-hosted models on SageMaker AI endpoints need scaling built for GenAI traffic, which differs from web traffic in three ways: each request keeps an accelerator busy for seconds, so CPU use is a poor signal; scaling out is slow, because a new instance must load many gigabytes of weights; and traffic is often bursty or idle overnight.

  • Scale on concurrency. Target-tracking policies on ConcurrentRequestsPerModel (or ConcurrentRequestsPerCopy with inference components) react to load faster than invocation counts.
  • Make scale-out faster. Fast model loading streams pre-sharded weights from S3 straight to the accelerators, and ahead-of-time compilation avoids compiling at startup.
  • Scale to zero for idle models: with inference components, the minimum copy count can be 0; scaling back out from zero needs a step scaling policy driven by a CloudWatch alarm, and the first requests wait minutes or fail until capacity returns, so use it only where that's acceptable.
  • Pre-scale with scheduled actions before known peaks such as a sale launch.

To pick the instance type and configuration in the first place, SageMaker AI inference recommendations take the model, your token distributions, your concurrency and a goal (lowest cost, lowest latency or highest throughput), benchmark up to three instance types on real hardware, and return deployable configurations with TTFT, inter-token latency, latency percentiles, throughput and cost.

Scaling a self-hosted LLM on CPU utilization or on a short cooldown tuned for web servers leads to late scale-out and thrashing. Scale on concurrent requests, allow for minutes of model loading, and keep a minimum capacity if users can't wait.

System performance

Skill 4.2.6Optimize FM system performance for GenAI workflows (for example, by using API call profiling for prompt-completion patterns, vector database query optimization for retrieval augmentation, latency reduction techniques specific to LLM inference, efficient service communication patterns)

Profiling API calls

Before optimizing, find where the time goes. Trace a request end to end: API Gateway, the application, retrieval, each model call, tool calls, and the response. The CloudWatch generative AI observability views show model invocations and AgentCore agents with end-to-end traces; AgentCore Observability emits OpenTelemetry data (latency, duration, tokens, errors per session and step), and your own code can add spans with the AWS Distro for OpenTelemetry (ADOT).

For the model calls themselves, separate "the model got slower" from "the answers got longer". Bedrock publishes InvocationLatency and, for streaming calls, TimeToFirstToken, but no output-speed metric. AWS documents computing output tokens per second with metric math:

Output tokens per second (Python, CloudWatch metric math) 
def q(i, name):
    m = {"Namespace": "AWS/Bedrock",
         "MetricName": name,
         "Dimensions": [{
             "Name": "ModelId",
             "Value": MODEL_ID}]}
    stat = {"Metric": m, "Period": 300,
            "Stat": "Average"}
    return {"Id": i, "ReturnData": False,
            "MetricStat": stat}

otps = {"Id": "otps",
        "Expression":
        "1000 * outT / (lat - ttft)"}
cw.get_metric_data(
    MetricDataQueries=[
        q("outT", "OutputTokenCount"),
        q("lat", "InvocationLatency"),
        q("ttft", "TimeToFirstToken"),
        otps],
    StartTime=start, EndTime=end)

Here cw is a CloudWatch client. The formula is only meaningful for streaming traffic, because only streaming calls report TTFT. AWS suggests alarming when output speed drops below about 80% of its baseline, or using anomaly detection. A rising TTFT with steady output speed points at longer prompts or queueing; falling output speed points at the model or capacity.

Optimizing vector queries

  • Filter early. Metadata filters narrow the search, but with HNSW a strict filter can leave too few matches among the nearest neighbors. pgvector 0.8 and later can keep scanning (hnsw.iterative_scan) until enough rows pass the filter.
  • Return only what you need. Ask for a sensible k, and leave the vectors themselves out of the response; just the text and metadata.
  • Tune effort per query. Raise ef_search only for queries that need high recall.
  • Pick the store for the query rate. S3 Vectors is cheap for large, rarely queried indexes (sub-second queries, about 100 ms when queried frequently); for high query rates or hybrid search, use OpenSearch.
Filtered HNSW query with iterative scan (PostgreSQL) 
BEGIN;
SET LOCAL hnsw.ef_search = 80;
SET LOCAL hnsw.iterative_scan
  = relaxed_order;
SELECT id, chunks
FROM kb.manuals
WHERE custom_metadata
      @> '{"product_line": "kitchen"}'
ORDER BY embedding <=> $1
LIMIT 5;
COMMIT;

SET LOCAL keeps the settings to this transaction. With relaxed_order, results may come back slightly out of distance order; re-sort them if exact order matters.

Efficient service communication

Reuse clientsCreate SDK clients once (outside the Lambda handler) so connections are reused instead of repeating TLS handshakes on every call.

Stay closePut the application, the vector store and the model endpoint in the same Region where data rules allow, and reach Bedrock through VPC interface endpoints (bedrock-runtime, bedrock-agent-runtime) to keep traffic private on the AWS network.

Stream end to endStreaming from the model is wasted if a later hop buffers the whole answer. Lambda response streaming (native on Node.js runtimes; Python needs a custom runtime or the Lambda Web Adapter) and API Gateway REST API response streaming (responseTransferMode set to STREAM, up to 15 minutes, not compatible with API caching) pass tokens through as they arrive.

Respect timeoutsAPI Gateway's REST integration timeout defaults to 29 seconds; it can be raised for Regional and private APIs, or avoided with streaming or an asynchronous pattern (accept the request, queue it, return the result later through polling, a WebSocket or a callback).

Go asynchronous for long workAgent runs and document processing that take minutes belong behind SQS or Step Functions, not in a synchronous HTTP call.

The AWS X-Ray SDKs and daemon entered maintenance mode on February 25, 2026 (security fixes only). Instrument new code with OpenTelemetry through ADOT; traces still appear in X-Ray and CloudWatch.

"TTFT grew while output speed stayed the same" points to longer prompts or queueing. "Streaming enabled but users still wait for the whole answer" points to a buffering hop (a non-streaming Lambda or API). "Long repeated system prompt, slow first token" points to prompt caching.

Key takeaways

  • Latency is roughly TTFT (prompt length, queueing) plus output tokens ÷ output speed. Stream to hide the wait, pre-compute predictable answers, run independent steps in parallel, and use latency-optimized inference (preview, few models) or the Priority tier where it matters.
  • Benchmark with real prompts and concurrency: TTFT and total latency percentiles, output tokens per second, throttles and cost, alongside quality.
  • Retrieval: tune HNSW (ef_search per query; m and ef_construction at build), compress with disk-based mode, filter on metadata, keep k low, preprocess queries cheaply, and merge hybrid results with weighted normalization or RRF.
  • Throughput is a token budget: realistic maxTokens, bounded and token-aware concurrency, backoff with jitter, cross-Region profiles or reserved capacity, and batch inference for work nobody waits for.
  • Low temperature for factual and structured output, higher for creative work; change temperature or top-p, not both; top-k goes in model-specific fields. A/B test offline with Prompt Management variants and evaluations, online with AppConfig (Evidently is discontinued).
  • Plan capacity in tokens from p95 prompt and completion sizes at peak; watch prompt growth; scale SageMaker endpoints on concurrent requests with fast model loading, scheduled pre-scaling and scale to zero only where cold starts are acceptable.
  • Profile end to end with OpenTelemetry and the CloudWatch generative AI views; compute output speed with metric math; reuse clients, stay in-Region with VPC endpoints, stream through every hop, and go asynchronous for long work.
