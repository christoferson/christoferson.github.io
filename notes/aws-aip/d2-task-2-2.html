Overview

Task 2.2

Implement model deployment strategies.

"Deploying a model" means two different things. With Amazon Bedrock the model is already running; you decide how you call it and whether to reserve capacity. With SageMaker AI (or your own containers) you run the model: you pick GPUs, load tens of gigabytes of weights, and scale instances. Questions give a workload (traffic pattern, latency, model size, a customized model, budget) and ask for the deployment that fits.

The examples use the retailer's two workloads again: the interactive support assistant, with daytime peaks, and a fine-tuned open model for product-description generation that the company hosts itself.

Lambda as the on-demand caller

A serverless front for Bedrock

For most applications the "deployment" is a Lambda function behind API Gateway that builds the request and calls Bedrock: no servers, scales with traffic, pays per use on both sides. Things to get right:

  • Time limits: a Lambda function runs for at most 15 minutes (default 3 seconds, so raise it). Long generations, and reasoning models with large outputs, also need a longer SDK read timeout, or streaming.
  • Streaming to users: Lambda response streaming (through function URLs, InvokeWithResponseStream or API Gateway) sends tokens as they arrive, up to 200 MB per response. It's native on Node.js runtimes; Python needs a custom runtime or the Lambda Web Adapter. Function URLs can't stream from inside a VPC.
  • Concurrency against quotas: Lambda can scale to hundreds of concurrent calls in seconds, faster than the account's Bedrock tokens-per-minute quota allows. Cap it with reserved concurrency so excess requests queue or fail fast rather than all being throttled.
  • Cold starts: provisioned concurrency keeps environments warm for latency-sensitive paths.
Client set up for long generations (Python) 
from botocore.config import Config

brt = boto3.client(
    "bedrock-runtime",
    config=Config(
        # seconds to wait for the response
        read_timeout=300,
        retries={"mode": "standard",
                 "total_max_attempts": 4},
    ),
)
# cap the function below the model quota
aws lambda put-function-concurrency \
  --function-name support-chat \
  --reserved-concurrent-executions 50

When Lambda isn't the right host

Use containers (ECS on Fargate, or EKS) when requests run longer than 15 minutes, when connections stay open (WebSocket chat sessions held by the server), or when the backend runs heavy libraries or local models. Lambda Managed Instances, a newer option, runs functions on EC2 instances in your account with no cold starts and many concurrent requests per environment, which suits steady, high-volume Bedrock proxies; it doesn't scale to zero.

Bedrock Provisioned Throughput

Dedicated capacity for one model

You buy model units for a specific model; each unit gives that model a fixed number of input and output tokens per minute (the figure varies by model). Billing is hourly, with no commitment (delete any time) or cheaper 1-month and 6-month terms. You call it with the provisioned model ARN as the model ID. Only some models support it, and purchases use a "contextual" model ID that includes the context length.

Buy two model units for one month (CLI) 
aws bedrock \
  create-provisioned-model-throughput \
  --provisioned-model-name support-pt \
  --model-id amazon.nova-pro-v1:0:300k \
  --model-units 2 \
  --commitment-duration OneMonth

Customized models used to require Provisioned Throughput. Now models customized on supported bases (recent Nova and Llama customizations) can use on-demand custom model deployment instead, paying per token; others still need Provisioned Throughput.

"Steady, predictable, high traffic on a base model" points to the Reserved tier (or Provisioned Throughput). "Serve a fine-tuned model with unpredictable traffic" points to on-demand custom model deployment if the base supports it. "Spiky or low traffic" stays on demand: reserved capacity is paid for whether used or not.

Scaling endpoints for LLMs

Invocation counts are a poor signal for LLMs because one request can occupy a GPU for seconds. Scale on concurrent requests per model (or per inference component copy), which counts queued and in-progress requests, including streaming ones until the last token. High-resolution versions publish every 10 seconds, so scale-out reacts much faster. Scaling an endpoint to zero works only with inference components, and the first request after zero fails until capacity arrives, so it suits development and occasional workloads, not live chat.

Hybrid with Bedrock

  • Bedrock Marketplace deploys a specialized model to a SageMaker-managed endpoint that you size, while applications call it through the Bedrock APIs, so Guardrails, Knowledge Bases and agents work with it.
  • Custom Model Import brings weights you trained (supported open architectures) into Bedrock's serverless serving, billed per model copy in 5-minute windows while it's used.
  • A common split: managed Bedrock models for general tasks, a SageMaker endpoint for the one custom model that needs special hardware or a custom container, behind one gateway (Task 2.3).

Sizing GPU memory

Weights plus KV cache

Weights need about parameters times bytes per parameter: 2 bytes in FP16 or BF16, 1 in FP8 or INT8, about 0.5 in 4-bit. On top comes the KV cache, the stored attention state of every token of every request in progress, which grows with batch size and sequence length, plus framework overhead.

ModelWeights in FP16Implication
8 billion parametersAbout 16 GBFits one 24 GB or larger GPU, with room for the cache
70 billion parametersAbout 140 GBNeeds several GPUs (for example four 48 GB GPUs with tensor parallelism), or quantization to about 35 to 70 GB

Serving containers

Large Model Inference (LMI) containers

SageMaker AI's LMI containers (DJL Serving) package optimized LLM serving engines, chiefly vLLM and TensorRT-LLM (AWS Deep Learning Containers also offer vLLM, SGLang and Triton images). The engine handles the LLM-specific work:

  • Tensor parallelism: splits each layer across several GPUs so a model larger than one GPU can run.
  • Continuous batching: adds new requests to the running batch as others finish, instead of waiting for a whole batch, which keeps GPUs busy and raises throughput.
  • Paged attention: allocates KV-cache memory in blocks, so more requests fit in the same memory.
  • Quantization (AWQ, GPTQ, FP8) and speculative decoding (below).

The Hugging Face Text Generation Inference (TGI) container no longer appears in AWS's current container list; prefer LMI or vLLM images for new deployments.

Hardware

NVIDIA GPU instances range from g5, g6 and g6e (cost-effective, up to mid-size models) to p4d, p5 and p6 (the largest models, highest throughput). AWS Inferentia2 (inf2) and Trainium (trn1, trn2) instances offer lower cost per token for supported models, using the AWS Neuron SDK. Newer endpoint options split one GPU into isolated partitions (MIG) for small models, and let an endpoint fall back across several instance types when one is short of capacity.

Loading models faster

  • Uncompressed artifacts: point the model at an S3 prefix of plain files (S3Prefix, compression None) instead of one large model.tar.gz, which avoids the decompression step.
  • Fast model loading: weights pre-sharded per GPU stream directly from S3 into GPU memory, skipping local disk and host memory, so new instances serve sooner.
  • Timeouts: raise the model download and container startup health-check timeouts (each up to 3,600 seconds) and the volume size, or large models fail to deploy.
  • Scale out early: because new capacity takes minutes, scale on high-resolution concurrency metrics and keep spare capacity at peaks.
A 70B model on four GPUs from uncompressed files (Python) 
# plain files under an S3 prefix
src = {"S3DataSource": {
    "S3Uri": "s3://models/70b/",
    "S3DataType": "S3Prefix",
    "CompressionType": "None"}}
# split each layer across 4 GPUs
env = {"OPTION_TENSOR_PARALLEL_DEGREE": "4"}

sm.create_model(
    ModelName="desc-gen-70b",
    ExecutionRoleArn=ROLE_ARN,
    PrimaryContainer={
        "Image": LMI_IMAGE_URI,
        "ModelDataSource": src,
        "Environment": env},
)

# give big weights time to load
variant = {
    "VariantName": "main",
    "ModelName": "desc-gen-70b",
    "InstanceType": "ml.g6e.12xlarge",
    "InitialInstanceCount": 1,
    "ModelDataDownloadTimeoutInSeconds":
        1800,
    "ContainerStartupHealthCheckTimeoutInSeconds":
        1800,
}
sm.create_endpoint_config(
    EndpointConfigName="desc-gen-70b",
    ProductionVariants=[variant],
)

The ml.g6e.12xlarge has four 48 GB GPUs, enough for the roughly 140 GB of FP16 weights split four ways plus the cache.

Self-managed and HyperPodTeams running Kubernetes can serve with vLLM on EKS, or use SageMaker HyperPod inference, which adds a tiered KV cache, cache-aware request routing and separate prefill and decode stages on shared training and inference capacity.

Optimized deployments

Skill 2.2.3Develop optimized FM deployment approaches to balance performance and resource requirements for GenAI workloads (for example, by selecting appropriate models, by using smaller pre-trained models for specific tasks, by using API-based model cascading to perform routine queries)

Use the smallest model that works

Every step down in model size cuts latency and cost per token, often several-fold. Many production tasks (classification, extraction, routing, short answers from retrieved text) are handled well by small models such as Amazon Nova Micro or Lite, or small open models. Evaluate on your own data (Task 1.2) and keep the large model only for the requests that need it.

  • Task-specific small models: a small model fine-tuned on one narrow task can match a large general model on that task.
  • Distillation: Bedrock model distillation has a large teacher model generate answers to your prompts (or uses your invocation logs), then fine-tunes a smaller student on them.

Model cascading

  1. Try smallSend the request to a small, cheap model.
  2. CheckValidate the answer: does it parse, does it cite a source, does a quick judge or confidence check pass?
  3. EscalateOnly if the check fails, send the request to a larger model.

If most requests are routine, most never reach the expensive model. Bedrock intelligent prompt routing is a managed form of this for two models in one family (currently Nova and Llama models), choosing per request by predicted quality.

Cascade from a small to a large model (Python) 
SMALL = "us.amazon.nova-lite-v1:0"
LARGE = "us.amazon.nova-pro-v1:0"

def answer(messages):
    for model in (SMALL, LARGE):
        resp = brt.converse(
            modelId=model,
            messages=messages)
        text = (resp["output"]["message"]
                ["content"][0]["text"])
        if passes_checks(text):
            return text, model
    return HANDOFF_MESSAGE, None

SageMaker AI's inference optimization toolkit applies these to supported models, and its generative AI inference recommendations benchmark a model on candidate instance types against a goal (cost, latency or throughput), reporting time to first token, inter-token latency, throughput and cost.

Per token or per hour

Per-token pricing (Bedrock on demand) wins for spiky or modest traffic; you pay nothing when idle. Per-hour capacity (an endpoint, Provisioned Throughput, the Reserved tier) wins only when it is kept busy. Compare expected monthly tokens times the per-token price with the instance hours needed at peak times the hourly rate, including idle hours.

A SageMaker endpoint sized for the daytime peak and left running overnight can cost more than Bedrock on demand for the same traffic. Scale it down off-peak (or to zero with inference components where a cold start is acceptable), or stay on per-token pricing.

Key takeaways

  • Bedrock on demand for most traffic; Reserved tier or Provisioned Throughput (model units, hourly, no commitment, 1 or 6 months) for steady volume; on-demand custom model deployment for supported fine-tuned models; SageMaker AI for models and containers you control.
  • Lambda as the caller: raise its timeout (15-minute maximum) and the SDK read timeout, stream responses (up to 200 MB), cap reserved concurrency below Bedrock quotas; containers for longer or stateful work.
  • SageMaker for LLMs: real-time endpoints, inference components (shared GPUs, scale to zero), asynchronous endpoints for long jobs; serverless has no GPUs. Scale on high-resolution concurrent-request metrics.
  • LLM serving: weights are parameters times bytes per parameter plus the KV cache; LMI containers (vLLM, TensorRT-LLM) provide tensor parallelism, continuous batching and paged attention; load faster with uncompressed S3 artifacts, fast model loading and longer startup timeouts.
  • Optimize: the smallest model that passes evaluation, distillation, cascading (or intelligent prompt routing), quantization, compilation and speculative decoding; compare per-token and per-hour costs at real utilization.
