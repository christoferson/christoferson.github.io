Overview

Task 1.1

Analyze requirements and design GenAI solutions.

Professional-level questions describe a business with constraints (data must stay in the EU, responses in under a second, a fixed budget, millions of documents overnight) and ask for the design that meets all of them. The skill is mapping each constraint to a design choice: the hosting option, the API pattern and the inference option.

The examples follow a retailer building two applications: a customer support assistant that answers questions in real time, and a nightly job that summarizes the day's support tickets for analysts.

AWS's own guidance is to start on Bedrock with prompt engineering and RAG, move to customization only when that isn't enough, and deploy wherever fits. Models customized in SageMaker AI can be imported back into Bedrock. Task 1.2 covers choosing the model itself.

The usual order of preference to give a model new knowledge or behavior, cheapest first: prompt engineering, then RAG, then tools or agents, then fine-tuning or distillation, then continued pre-training. A question that says "frequently changing information" points to RAG, not fine-tuning.

Integration patterns

Synchronous: the Converse API

Converse is one request format for every chat-capable model, with system prompts, tool use and guardrails, so switching models is a change of modelId, not of code. InvokeModel takes each model's native request body, for features Converse doesn't expose. Both are on the bedrock-runtime endpoint, which also accepts OpenAI-compatible requests.

The support assistant answers one question (Python) 
import boto3

brt = boto3.client("bedrock-runtime")

resp = brt.converse(
    # a US cross-Region inference profile
    modelId="us.amazon.nova-lite-v1:0",
    system=[{"text": "You are a support "
             "assistant for a retailer."}],
    messages=[{
        "role": "user",
        "content": [{"text": "Where is "
                     "my order 1042?"}],
    }],
    inferenceConfig={"maxTokens": 300,
                     "temperature": 0.2},
)
msg = resp["output"]["message"]
print(msg["content"][0]["text"])
# inputTokens, outputTokens
print(resp["usage"])

Streaming

ConverseStream (or InvokeModelWithResponseStream) returns tokens as they're generated, so the user sees the answer start in a fraction of a second even when the full response takes several. Use it for every chat interface; deliver it to browsers with WebSockets or server-sent events (Task 2.4).

Batch inference

For large offline jobs, such as the nightly ticket summaries: put a JSONL file of requests in S3, start a batch job, and collect the results from S3. It costs about 50% less than on-demand. Results aren't in input order (match them by recordId), and job state changes arrive as EventBridge events, so there's no need to poll.

One record of the batch input file (one line per record in the real .jsonl file; wrapped here) 
{"recordId": "T-000123",
 "modelInput": {
   "messages": [{"role": "user",
     "content": [{"text":
       "Summarize this ticket: ..."}]}],
   "inferenceConfig": {"maxTokens": 200}
 }}

Asynchronous and event-driven

When a caller can't wait but the job isn't a nightly batch (a document uploaded for analysis, say), queue the request with SQS or trigger it from an EventBridge or S3 event, process it with Lambda or Step Functions, and store or notify the result. This also absorbs bursts that would otherwise hit throttling limits.

Latency-optimized inference for a few models is still in preview. Task 4.1 covers cost optimization in depth.

Quotas

On-demand use is limited per model and Region in requests per minute and tokens per minute; exceeding them returns ThrottlingException. A request reserves its input tokens plus its maxTokens against the quota when it starts (for some models output tokens count several times over), and unused tokens are returned when it ends. Setting maxTokens close to the real output size therefore raises effective throughput. Billing is always on actual tokens.

"Data must not leave the EU" rules out a global cross-Region inference profile; use an EU geographic profile in an EU Region. Organization policies restricting Regions also need to allow the profile's destination Regions, or calls fail with access denied.

Proof of concept

Skill 1.1.2Develop technical proof-of-concept implementations to validate feasibility, performance characteristics, and business value before proceeding to full-scale deployment (for example, by using Amazon Bedrock)

Getting started

Model access

Serverless Bedrock models are now available by default in commercial Regions: the first call to a third-party model subscribes the account through AWS Marketplace automatically, so the caller needs aws-marketplace:Subscribe permission. Anthropic models also need a one-time use-case form per account (or once for an organization). To stop teams using a model, deny bedrock:InvokeModel on it in an IAM policy or SCP; denying the Marketplace subscription alone doesn't block it.

Where to experiment

The Bedrock console playgrounds try prompts against models side by side. Amazon Bedrock in SageMaker Unified Studio (formerly Bedrock IDE, earlier Bedrock Studio) lets a team build and share prototype chat apps, flows, knowledge bases and guardrails without writing infrastructure. The step after that is a small script or notebook against the API, like the example above.

What a proof of concept must prove

  1. Define success firstBusiness metrics (tickets deflected, minutes saved per analyst) and technical targets (answer quality, time to first token, cost per request). The Generative AI Lens puts this in the scoping phase.
  2. Build a test setRepresentative questions with expected answers, including hard and adversarial cases.
  3. Compare candidatesTwo or three models and prompt variants on the same test set.
  4. Evaluate qualityWith Bedrock evaluations: automatic metrics, LLM-as-a-judge, human review or RAG evaluation (Task 5.1).
  5. Measure performance and costLatency and token counts per request, projected to production volume.
  6. DecideGo, change the design, or stop, with the numbers to justify it.

Time to first token and usage from a stream 
import time

start = time.time()
resp = brt.converse_stream(
    modelId="us.amazon.nova-lite-v1:0",
    # same messages list as above
    messages=messages,
)
first = None
for event in resp["stream"]:
    if ("contentBlockDelta" in event
            and first is None):
        first = time.time() - start
    if "metadata" in event:
        meta = event["metadata"]
        print(meta["usage"])
        print(meta["metrics"]["latencyMs"])
print(f"first token: {first:.2f} s")

Projecting cost

Cost per request is input tokens times the input price plus output tokens times the (higher) output price, adjusted for cached tokens and any tier or batch discount. Multiply by expected daily requests: a design that is cheap in a demo can be expensive at a million requests a day, which is when caching, a smaller model or routing pays off.

Standardized components

Skill 1.1.3Create standardized technical components to ensure consistent implementation across multiple deployment scenarios (for example, by using the AWS Well-Architected Framework, AWS WA Tool Generative AI Lens)

The Generative AI Lens

What it adds to Well-Architected

The Well-Architected Framework's six pillars (operational excellence, security, reliability, performance efficiency, cost optimization, sustainability) apply to every workload. The Generative AI Lens, first published in April 2025 and revised in November 2025 with agentic AI guidance, applies them to foundation model workloads on Bedrock and SageMaker AI. The Machine Learning Lens covers traditional ML; use the Generative AI Lens for FMs, prompts, RAG and agents.

Design principles

  • Design for controlled autonomy: limit what models and agents can do.
  • Implement comprehensive observability: of prompts, responses, quality and cost.
  • Optimize resource efficiency: the right model and inference option for each job.
  • Establish distributed resilience: survive Regional or quota problems.
  • Standardize resource management: central catalogs of approved models, prompts and permissions.
  • Secure interaction boundaries: between users, models, data and tools.

Lifecycle

  1. ScopingBusiness case, success metrics, feasibility and risk.
  2. Model selectionCandidates by capability, cost and constraints.
  3. Model customizationPrompting, RAG, agents, fine-tuning, distillation, as needed.
  4. Development and integrationApplication, data and tool integration.
  5. DeploymentProduction rollout with safeguards.
  6. Continuous improvementMonitoring, evaluation and iteration.

Reviewing workloads in the WA Tool

The Well-Architected Tool includes the Generative AI and Machine Learning lenses in its lens catalog: apply them to a workload, answer the questions, and get a list of high and medium risks with improvement plans. Organizations can also write custom lenses (JSON) for their own standards and share them across accounts.

Key takeaways

  • Map each requirement to a decision: latency to sync, streaming or batch; residency to Region and geographic inference profiles; missing knowledge to RAG; actions to tools and agents; volume to model, caching and tiers.
  • Bedrock is the default (serverless, per token, managed RAG, guardrails, evaluations); Marketplace and Custom Model Import extend its catalog; SageMaker AI gives control of the serving stack.
  • Converse gives one API across models; stream for chat; batch from S3 for large offline jobs at about half price; queue and event-driven patterns for asynchronous work.
  • Inference options: Standard, Priority, Flex and Reserved tiers; geographic or global cross-Region inference; Provisioned Throughput (needed for most custom models); prompt caching; intelligent prompt routing. Keep maxTokens realistic for quota.
  • A proof of concept defines success metrics first, tests on a representative set, compares models with Bedrock evaluations, and measures time to first token, latency, tokens and projected cost.
  • Standardize with the Well-Architected Generative AI Lens (six design principles, six lifecycle phases, reviews in the WA Tool) and shared components: prompt templates, guardrails, IaC, Service Catalog, inference profiles and a gateway.
