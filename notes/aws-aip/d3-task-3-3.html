Overview

Task 3.3

Implement AI governance and compliance mechanisms.

Regulators, auditors and internal risk teams ask the same questions of an AI system: what is it for, what risks were considered, what data shaped it, who approved it, how is it monitored, and what did it say to whom? Governance is the set of documents, records, controls and processes that answer those questions with evidence, continuously rather than once.

Several governance services changed status: SageMaker Clarify, Model Monitor, Augmented AI and Role Manager are no longer open to new customers; AWS Audit Manager can't be set up in new accounts from April 30, 2026 (AWS points to Config conformance packs); and CloudTrail Lake closed to new customers on May 31, 2026 (AWS recommends CloudWatch). Model cards, the Model Dashboard and ML Lineage Tracking remain available.

SageMaker model cards

Documentation as a versioned resource

A model card records a model's overview, intended uses (with a risk rating of high, medium, low or unknown and the reasons), business details, training details, evaluation results, and ethical considerations and caveats. It has a status (Draft, PendingReview, Approved, Archived), every edit creates a new version, and it can be exported to PDF for auditors. Model packages in the Model Registry carry a simplified card, and cards can be shared across accounts with AWS RAM.

Creating cards programmatically, in the same pipeline that trains or customizes the model, keeps them accurate: the pipeline fills in the training data, parameters and evaluation scores it just produced, and a reviewer moves the card to PendingReview and Approved as part of the release approval (Task 1.2).

Create a model card from the pipeline (Python) 
card = {
    "model_overview": {
        "model_description":
            "Support reply model",
        "model_owner": "Support AI team"},
    "intended_uses": {
        "intended_uses":
            "Drafts replies for agents",
        "risk_rating": "Medium",
        "explanations_for_risk_rating":
            "Agent reviews each reply"},
}
# evaluation results can be added from
# evaluation reports in S3
sm.create_model_card(
    ModelCardName="support-reply-v7",
    Content=json.dumps(card),
    ModelCardStatus="Draft",
)

Cards for models you don't train

For Bedrock models, AWS publishes AI Service Cards (for example for Amazon Nova models and Bedrock Guardrails) describing intended uses, limitations and responsible AI design choices. Keep your own record per application as well: the model and version used, the prompts, guardrail and knowledge base, the evaluation results and the approval, because that combination is what users experience.

Decision logs

Invocation logging records the raw request and response. A decision log adds what an auditor needs to reconstruct a decision: the application and feature, model and prompt versions, guardrail outcome, retrieved document IDs, any tool actions, and the final result, written as structured JSON to CloudWatch Logs with a retention period that matches the regulation, and masked by a data protection policy (Task 3.2).

Data source tracking

Skill 3.3.2Implement data source tracking to maintain traceability in GenAI applications (for example, by using AWS Glue Data Catalog to register data sources, metadata tagging for source attribution in FM-generated content, CloudTrail for audit logging)

Registering sources

AWS Glue Data Catalog

The Data Catalog is the central register of data sets: databases and tables, populated by crawlers or by hand, with schema versions, column statistics, data quality results and Lake Formation permissions. Registering every source that feeds a model or knowledge base gives one place to answer "what data do we use, who owns it, and how good is it?".

Lineage

SageMaker Catalog (in SageMaker Unified Studio, built on Amazon DataZone) records data lineage, from source tables through jobs to outputs, in the open OpenLineage format. It captures lineage automatically from Glue crawlers and Redshift, and from Spark jobs on Glue and EMR with the OpenLineage listener; other tools can post OpenLineage events through an API. SageMaker ML Lineage Tracking links datasets, training jobs, models and endpoints for ML workflows.

Send Spark job lineage to SageMaker Catalog (Spark settings) 
# the listener that emits lineage events
spark.extraListeners=io.openlineage.spark.agent.OpenLineageSparkListener
# deliver them to SageMaker Catalog
spark.openlineage.transport.type=amazon_datazone_api
spark.openlineage.transport.domainId=dzd_abc123

Keep each setting on one line; the long class name can't be split.

Attribution in generated content

From document to answer

  1. Tag the sourceEach document carries metadata: owner, source system, version, date, classification (Task 1.4).
  2. Retrieve with itRetrieval returns chunks with their metadata and location.
  3. CiteRetrieveAndGenerate returns citations: each part of the answer linked to the retrieved references (content, S3 or web location, metadata).
  4. Store the trailLog the answer with its source IDs and versions, so an answer can be traced to the document version that produced it.
Collect the sources behind an answer (Python) 
sources = []
for c in resp["citations"]:
    for ref in c["retrievedReferences"]:
        loc = ref["location"]
        s3 = loc.get("s3Location", {})
        meta = ref.get("metadata", {})
        sources.append({
            "uri": s3.get("uri"),
            "ver": meta.get("version"),
            "owner": meta.get("owner"),
        })
log_decision(answer_id, sources)

For direct model calls, put the feature, tenant and prompt version in Converse requestMetadata (up to 16 pairs), so invocation logs can be filtered by them.

Audit logging

CloudTrail records who did what: model calls and configuration changes as management events, and retrievals, agent, flow, prompt and guardrail use as data events. For new customers, query trails delivered to S3 with Athena, or send events to CloudWatch, since CloudTrail Lake is closed to new customers.

Organizational governance

Skill 3.3.3Create organizational governance systems to ensure consistent oversight of FM implementations (for example, by using comprehensive frameworks that align with organizational policies, regulatory requirements, and responsible AI principles)

Frameworks to align with

FrameworkWhat it gives you
AWS responsible AI dimensionsEight dimensions to design for: fairness, explainability, privacy and security, safety, controllability, veracity and robustness, governance, transparency
Well-Architected Responsible AI Lens and Generative AI Lens (November 2025)Review questions and best practices, applied to workloads in the Well-Architected Tool
ISO/IEC 42001An international standard for an AI management system; AWS was certified in 2024 for services including Bedrock (certificate in AWS Artifact)
NIST AI Risk Management FrameworkA voluntary US framework organized as Govern, Map, Measure and Manage
EU AI ActLaw classifying AI by risk (prohibited, high-risk, limited risk with transparency duties, minimal), with obligations phased in from 2025 to 2027; check current dates, as amendments to the timeline have been proposed
Generative AI Security Scoping MatrixFive scopes, from using a consumer app (1) or an enterprise app (2), through building on pre-trained (3) or fine-tuned (4) models, to training your own (5); responsibilities grow with each scope

AWS Artifact shows AWS's own compliance; your application's compliance is yours to demonstrate. The frameworks are not checklists: they guide which risks to assess and which evidence to keep.

A governance operating model

  1. OwnershipAn AI governance board or center of excellence sets policy; each AI system has a named business owner and technical owner.
  2. Inventory and risk tierEvery use case is registered with its scope and risk tier (for example by EU AI Act category and data sensitivity).
  3. Approved building blocksApproved models, guardrails, prompt templates and reference architectures, offered as Service Catalog products or infrastructure-as-code modules.
  4. Review before launchHigher tiers need evaluation results, a model card, a privacy assessment and sign-off.
  5. Enforce in the platformOrganization policies make the rules hold everywhere (below).
  6. Monitor and re-reviewContinuous monitoring, incident handling and periodic reassessment.

Enforcing it across accounts

  • Amazon Bedrock policies in AWS Organizations (a declarative policy type, not an SCP) enforce a specific guardrail version on model calls across accounts and Regions, optionally only for chosen models; account-level enforcement does the same for one account. The strictest combination of organization, account and request guardrails applies.
  • SCPs deny unapproved models (deny both InvokeModel and InvokeModelWithResponseStream), unapproved Regions, long-term API keys, and changes to logging and guardrails.
  • AWS Config rules and conformance packs check configurations (managed rules exist for Bedrock data source encryption and several AgentCore settings; there are none for guardrails or invocation logging, so write custom rules for those), with automatic remediation. Security Hub CSPM includes a Bedrock control for data source encryption.

"Ensure every team's model calls apply the company guardrail, whatever the application code does" points to an Organizations Bedrock policy. "Prove to auditors which AWS services are certified" points to AWS Artifact. "Classify our use cases by legal risk" points to an inventory with EU AI Act risk tiers.

Continuous monitoring

Skill 3.3.4Implement continuous monitoring and advanced governance controls to support safety audits and regulatory readiness (for example, by using automated detection for misuse, drift, and policy violations, bias drift monitoring, automated alerting and remediation workflows, token-level redaction, response logging, AI output policy filters)

What to watch

RiskSignalSource
MisuseSpikes in guardrail interventions, unusual callers, volumes or costGuardrail metrics, GuardDuty AI protection findings, CloudTrail

Bias driftQuality or outcomes diverging between groupsMetrics broken down by segment, compared over time

Monitoring without Clarify and Model Monitor

With Clarify and Model Monitor closed to new customers, AWS points to: the open-source fmeval library and Bedrock evaluations for foundation model quality and safety; standard libraries (pandas, scikit-learn, SHAP) for tabular bias and explainability metrics; and sample monitoring solutions using MLflow on SageMaker AI with the open-source Evidently library for data drift, per-segment bias drift and LLM inference monitoring, with alerts through EventBridge and SNS.

Alerting and remediation

Guardrail metrics

Guardrails publish CloudWatch metrics in the AWS/Bedrock/Guardrails namespace, including Invocations, InvocationsIntervened and TextUnitCount, broken down by guardrail, version, policy type and whether the content was input or output. A rise in interventions can mean an attack, a change in users, or a guardrail set too strictly after an update.

Alarm when interventions spike (CLI) 
aws cloudwatch put-metric-alarm \
  --alarm-name guardrail-blocks-high \
  --namespace AWS/Bedrock/Guardrails \
  --metric-name InvocationsIntervened \
  --dimensions \
    Name=GuardrailArn,Value="$GR_ARN" \
    Name=GuardrailVersion,Value=3 \
  --statistic Sum \
  --period 300 \
  --evaluation-periods 1 \
  --threshold 50 \
  --comparison-operator \
    GreaterThanThreshold \
  --alarm-actions "$TOPIC_ARN"

Automated responses

  • Findings to action: GuardDuty AI protection findings (anomalous model invocation, cost harvesting, direct prompt injection), Config non-compliance and CloudWatch alarms arrive in EventBridge; rules start Lambda functions or Systems Manager Automation runbooks.
  • Typical remediations: revoke a compromised role's sessions, switch the application's model or prompt configuration back to the last good version (Task 1.2), tighten a guardrail, pause a feature, notify the owner and open a ticket.
Route AI-related GuardDuty findings to a response (EventBridge pattern) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {"type": [
    "Impact:IAMUser/AnomalousModelInvocation",
    "Impact:IAMUser/CostHarvesting",
    "Impact:IAMUser/PromptInjection.Direct"
  ]}
}

Controls that make audits possible

  • Response logging: invocation logging plus decision logs, retained for the required period (Task 1.6).
  • Token-level redaction: guardrail masking of personal data in prompts and responses, and CloudWatch Logs data protection for the logs (Task 3.2).
  • Output policy filters: guardrails, contextual grounding and Automated Reasoning checks, with their results logged as evidence (Task 3.1).
  • Evidence collection: Config conformance packs (with an operational best practices pack for AI and ML), Config history, Athena queries over logs, and exported reports in place of Audit Manager.

Key takeaways

  • Compliance evidence: SageMaker model cards (intended uses, risk rating, evaluations; statuses, versions, PDF export; created programmatically in the pipeline), AWS AI Service Cards for AWS models, decision logs in CloudWatch Logs, CloudTrail.
  • Traceability: register sources in the Glue Data Catalog; lineage in SageMaker Catalog (OpenLineage) and ML Lineage Tracking; source metadata and citations in answers; requestMetadata in invocation logs.
  • Governance: align with AWS responsible AI dimensions, the Responsible AI and Generative AI Lenses, ISO/IEC 42001, NIST AI RMF, the EU AI Act and the scoping matrix; run an inventory, risk tiers, approved building blocks and pre-launch review.
  • Enforce across the organization with Bedrock policies (required guardrails), SCPs (models, Regions, keys), and Config rules and conformance packs with remediation.
  • Monitor misuse (guardrail metrics, GuardDuty AI protection), violations, input and output drift (embeddings, scheduled evaluations) and bias drift (per-segment metrics); respond through EventBridge to Lambda or runbooks.
  • Status: Clarify, Model Monitor, A2I and Role Manager closed to new customers (use fmeval, Bedrock evaluations, open-source monitoring); Audit Manager and CloudTrail Lake closed to new customers (use Config conformance packs and CloudWatch).
