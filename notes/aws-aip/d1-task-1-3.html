Overview

Task 1.3

Implement data validation and processing pipelines for FM consumption.

A foundation model answers from what it's given. Empty fields, garbled encodings, duplicated records, a scanned PDF passed as text, or a request in the wrong shape all produce bad answers or errors, and they are cheaper to catch before the model call than after. This task is about the pipeline in front of the model: validate, process, format, enhance.

The examples use the retailer's support data: a nightly table of support tickets, product manuals as PDFs, photos customers attach, and recorded support calls.

Validating data

Skill 1.3.1Create comprehensive data validation workflows to ensure data meets quality standards for FM consumption (for example, by using AWS Glue Data Quality, SageMaker Data Wrangler, custom Lambda functions, Amazon CloudWatch metrics)

AWS Glue Data Quality

Rules in DQDL

Glue Data Quality checks datasets against rules written in DQDL (Data Quality Definition Language): completeness, uniqueness, allowed values and patterns, lengths, freshness, row counts, custom SQL, and anomaly detection that learns normal ranges from past runs. It's serverless and billed per DPU-hour. It can also recommend rules by profiling the data.

Ruleset for the nightly ticket table 
Rules = [
  IsComplete "ticket_id",
  IsUnique "ticket_id",
  Completeness "body" > 0.99,
  ColumnLength "body" between 20 and 9999,
  ColumnValues "language" in ["en","es"],
  ColumnValues "created_at"
    > (now() - 1 days),
  RowCount > 1000
]

Two places to run it

  • On Data Catalog tables: checks data at rest on a schedule, with rule recommendations; good for monitoring a source.
  • In a Glue ETL job: the Evaluate Data Quality transform checks data in flight and can route failing rows aside before they're loaded, so only clean records reach the embedding or prompt stage.

Results go to S3, publish CloudWatch metrics (rules passed and failed), and emit an EventBridge event with the overall score, which can stop the pipeline or alert someone. Nested data must be flattened first; rules don't evaluate inside nested structures.

EventBridge pattern: stop when the score is 0.7 or lower 
{
  "source": ["aws.glue-dataquality"],
  "detail": {
    "score": [{ "numeric": ["<=", 0.7] }]
  }
}

Other validation tools

SageMaker Data Wrangler

A visual data preparation tool, now part of SageMaker Canvas in current SageMaker Studio. Its Data Quality and Insights report profiles a dataset (missing values, duplicates, outliers, data types) before you build a flow of transformations, which can be exported to a pipeline or a processing job. Use it for exploring and preparing tabular data interactively; use Glue Data Quality for automated rules in production pipelines.

Lambda validators and CloudWatch metrics

For files arriving one at a time (an uploaded document, a chat message), a Lambda function triggered by S3 or called in the request path can check what rules can't: the file is a real PDF and under the size limit, text decodes as UTF-8, a JSON payload matches its schema, the language is supported. Publish the results as custom metrics so rejections show up on dashboards and alarms. The embedded metric format (EMF) creates metrics from a structured log line, with no API call.

Count rejected documents with EMF (Python) 
import json, time

def reject(source, reason):
    now = int(time.time() * 1000)
    metric = {
        "Namespace": "SupportDocs",
        "Dimensions": [["Source"]],
        "Metrics": [{"Name": "Rejected",
                     "Unit": "Count"}],
    }
    print(json.dumps({
        "_aws": {"Timestamp": now,
            "CloudWatchMetrics": [metric]},
        "Source": source,
        "Rejected": 1,
        "Reason": reason,
    }))

Reason is logged but isn't a dimension: keep dimensions low-cardinality, because each distinct combination becomes a separately billed metric.

"Ensure only complete, fresh, de-duplicated records are embedded into the knowledge base" points to Glue Data Quality rules in the ETL job with failed rows routed aside, plus an EventBridge alert on the score.

Multimodal input to the model

Content blocks in Converse

A user message can mix text with images (PNG, JPEG, GIF, WebP; up to 20 per message, each up to 3.75 MB), documents (PDF, CSV, Word, Excel, HTML, text, Markdown; up to 5, each up to 4.5 MB, always with a text block too) and, for models that support it, video from bytes or S3. Images and documents are only allowed in user turns.

A customer photo checked against the order (Python) 
with open("damage.jpg", "rb") as f:
    photo = f.read()
with open("order-1042.pdf", "rb") as f:
    order = f.read()

ask = ("Which items in the photo are "
       "damaged, and are they on "
       "this order?")
image = {"format": "jpeg",
         "source": {"bytes": photo}}
doc = {"format": "pdf", "name": "order",
       "source": {"bytes": order}}

messages = [{
    "role": "user",
    "content": [{"text": ask},
                {"image": image},
                {"document": doc}],
}]
resp = brt.converse(
    modelId="us.amazon.nova-pro-v1:0",
    messages=messages)

The document name is seen by the model, so a user-controlled file name is a prompt injection risk: set a neutral name yourself.

Amazon Bedrock Data Automation

Structured output from unstructured content

Bedrock Data Automation (BDA) processes documents, images, audio and video into structured results, with no prompt engineering. Standard output gives each modality's default (document text and summary, video scene summaries, audio transcripts); custom output uses blueprints that define the fields to extract (for documents, images and audio). Both are configured in a project, and jobs run asynchronously from S3 to S3, announcing completion through EventBridge.

Process a call recording with a BDA project (Python) 
bda = boto3.client(
    "bedrock-data-automation-runtime")

job = bda.invoke_data_automation_async(
    inputConfiguration={
        "s3Uri": "s3://calls/in/c1.wav"},
    outputConfiguration={
        "s3Uri": "s3://calls/out/"},
    dataAutomationConfiguration={
        "dataAutomationProjectArn":
            PROJECT_ARN,
        "stage": "LIVE"},
    dataAutomationProfileArn=PROFILE_ARN,
    notificationConfiguration={
        "eventBridgeConfiguration": {
            "eventBridgeEnabled": True}},
)
print(job["invocationArn"])

Parsing for Knowledge Bases

When documents feed a Bedrock knowledge base, choose the parser: the default parser extracts text only (free); the BDA parser or a foundation model parser also extract tables, charts and figures from PDFs and images, at a per-page or per-token cost. Use the advanced parsers when manuals are full of tables and diagrams that text extraction would lose.

Specialized services

Amazon Transcribe

Turns speech into text, in batch (files in S3) or streaming. Features that matter before an FM sees the transcript: speaker diarization (who said what), channel identification, automatic language identification, custom vocabularies for product names, and PII redaction. Call Analytics adds sentiment, issue detection and call summaries.

Amazon Textract

Extracts text, forms (key-value pairs), tables, layout and answers to natural-language queries from scans and PDFs, synchronously for single pages or with asynchronous jobs for multipage documents; AnalyzeExpense handles invoices and receipts. Tables extracted as structure reach the model far more reliably than flattened OCR text.

SageMaker Processing

Runs your own (or a built-in scikit-learn or Spark) container on managed instances that exist only for the job: data is copied from S3 to /opt/ml/processing/input, your script writes to /opt/ml/processing/output, and the results go back to S3. Input can be sharded by S3 key across instances. Use it for heavy custom preprocessing, such as cleaning and chunking millions of documents.

A multimodal pipeline

  1. LandFiles arrive in S3; an S3 event starts a Step Functions workflow.
  2. Route by typeA Choice state sends PDFs to Textract or BDA, audio to Transcribe, images to a multimodal model or BDA.
  3. ValidateCheck the extracted output (empty, too short, low confidence) and route failures to a review queue.
  4. NormalizeConvert everything to one schema: text, source, type, date, language, and extracted fields.
  5. UseEmbed into the knowledge base, or pass to the model for the business task.

Formatting requests

Skill 1.3.3Format input data for FM inference according to model-specific requirements (for example, by using JSON formatting for Amazon Bedrock API requests, structured data preparation for SageMaker AI endpoints, conversation formatting for dialog-based applications)

Bedrock requests

Converse: one format

  • system: instructions, as a list of text blocks.
  • messages: the conversation, each with a role (user or assistant) and a list of content blocks (text, image, document, video, tool use, tool result).
  • inferenceConfig: only maxTokens, temperature, topP and stopSequences. Anything model-specific, such as top_k, goes in additionalModelRequestFields.
  • Also: toolConfig, guardrailConfig, outputConfig for structured output, and a service tier.

Check stopReason in the response: max_tokens means the answer was cut off and model_context_window_exceeded means the input was too long (Task 5.2).

InvokeModel: each provider's own body

The native API takes a body in the provider's format, so the same request looks different per model family:

Amazon Nova native body 
{
  "schemaVersion": "messages-v1",
  "system": [{"text": "You are a ..."}],
  "messages": [{"role": "user",
    "content": [{"text": "Hello"}]}],
  "inferenceConfig": {
    "maxTokens": 300, "topK": 50}
}
Anthropic Claude native body 
{
  "anthropic_version":
    "bedrock-2023-05-31",
  "max_tokens": 300,
  "system": "You are a ...",
  "messages": [{"role": "user",
    "content": [{"type": "text",
                 "text": "Hello"}]}]
}

That difference is the main reason to prefer Converse: code that builds one format works across providers.

Structured outputs

When code consumes the answer, ask for JSON that matches a schema: in Converse, set outputConfig with a JSON Schema, and the model's output is constrained to it (supported models only; check the model card). Schemas must set additionalProperties to false and can't use recursion or numeric and length limits. The first request with a new schema is slow while it compiles; later ones reuse it.

Extract ticket fields as guaranteed JSON (Python) 
SCHEMA = {
    "type": "object",
    "properties": {
        "category": {"type": "string",
            "enum": ["delivery", "refund",
                     "damage", "other"]},
        "order_id": {"type": "string"},
        "urgent": {"type": "boolean"},
    },
    "required": ["category", "urgent"],
    "additionalProperties": False,
}
fmt = {"type": "json_schema",
       "structure": {"jsonSchema": {
           "name": "ticket",
           "schema": json.dumps(SCHEMA)}}}
resp = brt.converse(
    modelId=MODEL_ID,
    messages=messages,
    outputConfig={"textFormat": fmt},
)

Conversations

Keeping dialog context

Models are stateless: every request must carry the conversation so far. Store turns (DynamoDB keyed by session), send them back in order as alternating user and assistant messages, and keep within the context window by trimming the oldest turns or replacing them with a running summary. Put standing instructions in system, not in the first user message, so they survive trimming (Task 1.6).

SageMaker AI endpoints

Payloads for self-hosted models

InvokeEndpoint sends whatever the container expects, declared with ContentType (the body can be up to 6 MB, and the container must respond within 60 seconds). Large Model Inference (LMI) containers accept a text-generation payload or a chat-style messages payload.

LMI text-generation payload 
{
  "inputs": "Summarize: ...",
  "parameters": {
    "max_new_tokens": 256,
    "temperature": 0.2,
    "top_p": 0.9
  }
}

max_new_tokens defaults to only 30, a common reason for "truncated" answers from a newly deployed model.

Improving input quality

Skill 1.3.4Enhance input data quality to improve FM response quality and consistency (for example, by using Amazon Bedrock to reformat text, Amazon Comprehend to extract entities, Lambda functions to normalize data)

Techniques

TechniqueWithWhy it helps
Normalize textLambda: Unicode normalization, whitespace, consistent date and number formats, remove boilerplate (signatures, disclaimers)Same content looks the same to the model and the embedding
De-duplicateHash of normalized text; Glue uniqueness rulesFewer repeated chunks crowding retrieval results
Detect languageComprehend dominant languageRoute to the right prompt, model or translation
Extract entities and key phrasesComprehend entities and key phrases (or custom entity recognition)Structured fields (order IDs, products) for metadata filters and prompts
Find and mask PIIComprehend PII detection; Transcribe redactionSensitive data never reaches the model or the logs (Task 3.2)
Rewrite or summarizeA small Bedrock modelMessy notes become clean, consistent text before the main call
Entities and PII from a ticket (Python) 
cmp = boto3.client("comprehend")
text = ticket["body"]

ents = cmp.detect_entities(
    Text=text, LanguageCode="en")
pii = cmp.detect_pii_entities(
    Text=text, LanguageCode="en")

# mask PII, from the end so offsets hold
for e in sorted(pii["Entities"],
        key=lambda e: -e["BeginOffset"]):
    text = (text[:e["BeginOffset"]]
            + f"[{e['Type']}]"
            + text[e["EndOffset"]:])

Comprehend's topic modeling, event detection and prompt safety classification are no longer open to new customers. AWS suggests Bedrock models for topics and events, and the Bedrock Guardrails prompt-attack filter for prompt safety. Entity, key phrase, language, sentiment and PII detection remain available.

"Responses are inconsistent because inputs vary in format" points to a normalization step (Lambda, or a small model that rewrites inputs into a standard form) before the main model call, not to changing the main model.

Key takeaways

  • Validate before the model: Glue Data Quality rules (DQDL, anomaly detection) on catalog tables or in ETL jobs with failing rows routed aside; Data Wrangler in Canvas for exploring; Lambda for per-file checks; CloudWatch metrics (EMF) and EventBridge score events for alerting.
  • Process by type: Converse content blocks for images, documents and video; Bedrock Data Automation for structured output at scale; Textract for forms and tables; Transcribe for speech with diarization and redaction; SageMaker Processing for heavy custom jobs; Step Functions to orchestrate.
  • Format for the model: Converse is one format (system, messages, inferenceConfig, additionalModelRequestFields); InvokeModel bodies differ by provider; structured outputs enforce a JSON Schema; conversations carry their history; SageMaker LMI payloads need max_new_tokens set.
  • Enhance inputs: normalize, de-duplicate, detect language, extract entities, mask PII, and rewrite messy text with a small model before the main call.
