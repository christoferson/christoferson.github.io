Task 3.2: Implement data security and privacy controls

Protecting the data that flows through a GenAI system: what Bedrock does and doesn't do with it, keeping environments and data access locked down and watched, finding personal data before it spreads, deleting it on schedule, and masking it in ways that keep the model useful.

Overview

Task 3.2

Implement data security and privacy controls.

Personal data enters a GenAI system from many directions (chat messages, documents in the knowledge base, call transcripts, tool results) and can end up in many places (prompts, logs, memory, vector stores, answers). This task is about controlling each of those: who and what can reach the data, where it travels, how long it stays, and what the model actually sees.

The examples use the retailer's support data: tickets and call transcripts with customer names, emails, addresses and occasionally card numbers, and an analytics data lake with order history.

Protected environments

Skill 3.2.1Develop protected AI environments to ensure comprehensive security for FM deployments (for example, by using VPC endpoints to isolate networks, IAM policies to enforce secure data access patterns, AWS Lake Formation to provide granular data access, CloudWatch to monitor data access)

Network isolation

Keep traffic private

  • Bedrock interface endpoints (runtime, agent runtime and others) keep model calls inside the AWS network, with endpoint policies limiting what passes (Task 2.3).
  • S3 gateway endpoints keep access to training and knowledge base data private; endpoint policies can restrict them to approved buckets.
  • Model customization jobs can run in your VPC (subnets and security groups in the job's VPC configuration), so training data moves through your network; the bucket policy can then deny access from anywhere else.
  • SageMaker AI network isolation (EnableNetworkIsolation) stops a training or model container from making any outbound call, even to S3, and gives it no AWS credentials; SageMaker itself moves the data in and out. Use it for untrusted or third-party model code.
  • Vector stores: an OpenSearch Serverless network policy can allow only your VPC endpoints and the Bedrock service; keep Aurora in private subnets.
Training data bucket: only reachable from the job's VPC 
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::support-train",
    "arn:aws:s3:::support-train/*"
  ],
  "Condition": {"StringNotEquals": {
    "aws:sourceVpc": "vpc-0abc1234"
  }}
}

A blanket deny like this also blocks administrators and services working from outside the VPC (including a knowledge base's own ingestion, which runs from the Bedrock service): scope it to the buckets it's meant for and add exceptions for the roles that need them.

Granular data access

IAM patterns

  • Separate roles for ingestion, the application, evaluation and administrators, each with only the buckets, tables, models and knowledge bases it needs.
  • Resource policies on buckets and KMS keys so data is readable only by those roles; customer managed keys so access to data requires access to the key.
  • Confused-deputy protection (aws:SourceAccount, aws:SourceArn) in the trust policies of roles that Bedrock assumes.
  • Per-user document access in retrieval through metadata filters or a managed knowledge base's permission filtering (Task 1.4).

AWS Lake Formation

For data lakes, Lake Formation adds permissions below the table level: column-level (hide the email column), row-level (only this region's customers) and cell-level security through data filters, plus tag-based access (LF-Tags) across many tables. Athena, EMR and Redshift Spectrum enforce them. A Bedrock knowledge base that answers questions over Glue Data Catalog tables (a structured data store) queries through them too: its role needs Lake Formation SELECT (and DESCRIBE) on exactly the permitted columns, so the model can never query columns it shouldn't see.

Masking the logs themselves

Invocation logs contain whatever users typed, and guardrail masking doesn't apply to them. A CloudWatch Logs data protection policy (per log group or for the whole account) finds sensitive data with managed identifiers (emails, card numbers, credentials and many more) and masks it wherever the logs are read: the console, Logs Insights, metric filters and subscriptions. Only principals with logs:Unmask see the original. It applies to data ingested after the policy is set, and can send audit findings to S3, Firehose or another log group.

Privacy-preserving systems

Skill 3.2.2Develop privacy-preserving systems to protect sensitive information during FM interactions (for example, by using Amazon Comprehend and Amazon Macie to detect personally identifiable information [PII], Amazon Bedrock native data privacy features, Amazon Bedrock guardrails to filter outputs, Amazon S3 Lifecycle configurations to implement data retention policies)

What Bedrock does with your data

  • No training, no sharing: inputs and outputs aren't used to train Amazon or third-party models and aren't shared with model providers.
  • Providers can't see it: each provider's models run in model deployment accounts owned by the Bedrock team; providers have no access to them, to logs or to prompts and completions.
  • Encryption: TLS 1.2 or later in transit (FIPS endpoints available), encryption at rest, and customer managed KMS keys for custom models and customization jobs, knowledge base ingestion and vector stores, agents, guardrails, evaluation jobs, sessions, AgentCore Memory and log destinations.
  • Location: content is stored in the Region where you use Bedrock; a fine-tuned model is a private copy that stays in your Region.
  • Compliance: Bedrock is in scope for programs including SOC, ISO, HIPAA eligibility and FedRAMP Moderate, and can be used in compliance with GDPR; reports are in AWS Artifact.

Abuse detection and data retention

What may be kept, and how to control it

Bedrock works on a zero-operator-access model, with model-specific exceptions for abuse detection: some models (certain OpenAI models, and the newest Claude models) retain traffic for up to 30 days for abuse review, and content suspected to be child sexual abuse material is blocked and may be reported. Retained data isn't shared with providers.

In 2026 Bedrock added data retention modes, set per Region for the account (or per project on the OpenAI-compatible endpoint): none (zero data retention), default (the model's own policy), aws_review, and a legacy mode; new accounts inherit. A model that requires more retention than the mode allows simply fails, so a none setting blocks those models. An SCP using the bedrock:DataRetentionMode condition key can enforce zero retention across the organization.

"Bedrock doesn't use our data for training" is true for all models; "Bedrock stores nothing" depends on the model and the retention mode. With the OpenAI-compatible Responses API, responses are stored for 30 days by default unless you turn storage off (and under zero-retention mode, storage is refused).

Redaction (rather than offsets only) is available through these asynchronous jobs. Macie's findings arrive as EventBridge events, so a pipeline can quarantine a bucket's new files before the next knowledge base sync. Transcribe's redaction alone doesn't meet HIPAA de-identification requirements.

A right to erasure request must reach every copy: the source document, its chunks in the vector store, conversation history, memory, logs and any fine-tuning data. Data baked into a fine-tuned model can't be selectively removed, which is a strong reason to keep personal data out of training sets.

Privacy with utility

Skill 3.2.3Create privacy-focused AI systems to protect user privacy while maintaining FM utility and effectiveness (for example, by using data masking techniques, Amazon Comprehend PII detection, anonymization strategies for sensitive information, Amazon Bedrock guardrails)

The techniques

TechniqueWhat it doesReversibleEffect on the model
RedactionRemoves the value or replaces it with characters (****)NoLoses meaning: the model can't tell a name from a date
Typed placeholderReplaces with the entity type ([NAME], {EMAIL})NoKeeps the role of the value, so answers still make sense
Tokenization (pseudonymization)Replaces with a token ([NAME_1]) and stores the mapping in a protected vaultYes, with the vaultKeeps distinct people distinct; real values restored after generation
HashingA one-way hash (for example SHA-256)No (but guessable for short values)Consistent IDs for joining, no meaning
AnonymizationRemoves or generalizes data so no one can be re-identified (age 34 becomes 30 to 39)NoFine for analytics; limits personalized answers
Data minimizationSends only the fields the task needsNot applicableUsually none; the cheapest control

Pseudonymized data is still personal data under laws such as GDPR, because it can be re-identified with the mapping; only true anonymization takes data out of scope.

Tokenize, generate, restore

  1. DetectComprehend finds personal data in the ticket with offsets.
  2. TokenizeReplace each value with an indexed placeholder ([NAME_1], [EMAIL_1]) and store the mapping, encrypted with KMS, for this request only.
  3. GenerateThe model works with placeholders: "Dear [NAME_1], your refund to [EMAIL_1]..."
  4. RestoreReplace placeholders in the response with the real values before it goes to the authorized agent or customer.
  5. DiscardDelete the mapping when the request completes (or keep it under a short TTL).
Indexed placeholders from Comprehend offsets (Python) 
def tokenize(text):
    ents = cmp.detect_pii_entities(
        Text=text, LanguageCode="en"
    )["Entities"]
    vault, count = {}, {}
    # replace from the end, keep offsets
    ents.sort(
        key=lambda e: e["BeginOffset"],
        reverse=True)
    for e in ents:
        if e["Score"] < 0.8:
            continue
        kind = e["Type"]
        n = count.get(kind, 0) + 1
        count[kind] = n
        tok = f"[{kind}_{n}]"
        b = e["BeginOffset"]
        end = e["EndOffset"]
        vault[tok] = text[b:end]
        text = text[:b] + tok + text[end:]
    return text, vault

def restore(text, vault):
    for tok, value in vault.items():
        text = text.replace(tok, value)
    return text

Balancing privacy and usefulness

  • Mask selectively: card numbers and passwords never need to reach the model; a first name might, if the reply addresses the customer. Choose entity types per use case.
  • Prefer typed or indexed placeholders to blank redaction, so the model still knows what kind of value it's handling.
  • Mask at the source for stored data (knowledge base documents, training sets, memory), and at run time for live input; use guardrails' anonymize action as the last line on outputs.
  • Measure the cost: run the evaluation set with and without masking to see the quality impact.
  • Aggregate analytics: for statistics across customers, techniques such as differential privacy (offered in AWS Clean Rooms) add calibrated noise so no individual can be singled out.

"Agents need the customer's real details in the reply, but the model must never see them" points to tokenize, generate, restore. "Keep personal data out of the knowledge base" points to Macie scanning plus Comprehend redaction jobs before ingestion. "Logs must not expose PII" points to CloudWatch Logs data protection.

Key takeaways

  • Protected environments: interface and gateway endpoints with policies, customization jobs in your VPC, SageMaker network isolation for untrusted code, private vector stores, least-privilege roles and key policies, Lake Formation row, column and cell filters (also for knowledge bases over Glue tables).
  • Monitor with CloudTrail management and data events, invocation logging (runtime only, set retention), CloudWatch alarms and GuardDuty; mask logs with CloudWatch Logs data protection policies.
  • Bedrock: no training on your data, no sharing with providers, provider-inaccessible deployment accounts, TLS and KMS keys; some models retain traffic up to 30 days for abuse detection; 2026 data retention modes (none for zero retention) enforceable by SCP.
  • Find personal data with Comprehend (real time, or redaction jobs), Macie (S3 buckets), Transcribe (speech), Glue (pipelines), guardrails (live calls).
  • Retention: S3 Lifecycle including noncurrent versions, DynamoDB TTL, log retention, AgentCore Memory expiry; erasure must reach every copy, and fine-tuned models can't forget.
  • Utility: minimize, mask selectively, use typed or indexed placeholders, tokenize and restore for personalized replies, anonymize for analytics, and measure the quality cost.
