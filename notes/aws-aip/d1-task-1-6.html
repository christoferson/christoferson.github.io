Overview

Task 1.6

Implement prompt engineering strategies and governance for FM interactions.

In production, a prompt is code: changing a sentence can change every answer the application gives. So prompts need the same disciplines as code: one source of truth, versions, reviews before release, tests, and an audit trail of what ran. The basics of prompting are in the AI Practitioner guide; this page is about doing it at scale.

The examples continue the retailer's support assistant.

Instruction frameworks

Skill 1.6.1Create effective model instruction frameworks to control FM behavior and outputs (for example, by using Amazon Bedrock Prompt Management to enforce role definitions, Amazon Bedrock Guardrails to enforce responsible AI guidelines, template configurations to format responses)

Amazon Bedrock Prompt Management

Prompts as managed resources

A managed prompt holds the template (with {{variables}}), the model, the inference settings, and for chat models the system prompt, example messages, tools and prompt caching. It can have several variants (different wording or models) to compare side by side, a working draft, and immutable numbered versions for production.

Applications call the model with the prompt version ARN as the modelId and supply only the variables. Because the role definition, format rules and settings live in the prompt, an application can't quietly change them: when you pass a prompt ARN, Converse doesn't accept your own system, inferenceConfig, toolConfig or extra model fields. Any messages you send are appended after the prompt's own.

The template's system prompt (chat template) 
You are the support assistant for
{{brand}}. Answer only from the manual
excerpts inside <manual> tags. If the
answer isn't there, say so and offer to
connect the customer to an agent.

Reply in {{language}} with:
1. A one-sentence answer.
2. Numbered steps, if any.
3. The manual section you used.
Call version 3 of the prompt (Python) 
resp = brt.converse(
    modelId=PROMPT_V3_ARN,
    promptVariables={
        "brand": {"text": "Northwind"},
        "language": {"text": "English"},
        "question": {"text": user_q},
    },
)

Guardrails as the enforcement layer

Instructions are requests; a model can be talked out of them. Bedrock Guardrails enforce rules independently of the prompt: denied topics, content filters, word filters, PII handling and grounding checks, applied to inputs and outputs. Attach one in the Converse call (it covers the whole managed prompt, or only the parts marked as user content), on a Flows prompt node, or enforce one across the organization. Details are in Task 3.1.

"Ensure every team's assistant uses the same approved persona and response format" points to Prompt Management versions referenced by ARN. "Ensure the assistant never discusses competitors, whatever the prompt says" points to a guardrail with a denied topic.

Keeping context

Skill 1.6.2Build interactive AI systems to maintain context and improve user interactions with FMs (for example, by using Step Functions for clarification workflows, Amazon Comprehend for intent recognition, DynamoDB for conversation history storage)

Conversation history

DynamoDB

Models remember nothing between calls, so the application stores the conversation and resends it. A DynamoDB table keyed by session ID (partition key) and timestamp (sort key) holds each turn; a TTL attribute expires old sessions. Each request loads the last few turns, appends the new question, and keeps within the context window by dropping or summarizing older turns.

Load the last 10 turns of a session (Python) 
from boto3.dynamodb.conditions import Key

table = boto3.resource(
    "dynamodb").Table("chat-history")

def history(sid, n=10):
    resp = table.query(
        KeyConditionExpression=
            Key("sessionId").eq(sid),
        # newest first
        ScanIndexForward=False,
        Limit=n,
    )
    msgs = []
    for t in reversed(resp["Items"]):
        msgs.append({
            "role": t["role"],
            "content": [{"text": t["text"]}]})
    return msgs

Managed memory

  • AgentCore Memory: short-term memory stores each session's events; long-term memory extracts lasting information across sessions using strategies (semantic facts, user preferences, summaries, episodes), so an assistant remembers that a customer owns a K200 next week.
  • Bedrock session management APIs (preview) checkpoint conversation state for frameworks such as LangGraph.

Understanding intent

Classify before you answer

Routing by intent (refund, delivery, product help) lets each request use a focused prompt, the right knowledge base, or a human. Options: an Amazon Comprehend custom classifier trained on labeled messages (multi-class, at least 50 examples per class) served from a real-time endpoint; an Amazon Lex bot; or a small, fast FM with a classification prompt.

Clarification workflows

Pausing to ask the user

When a request is ambiguous ("my order is wrong", but which order?), a Step Functions Standard workflow can pause on a .waitForTaskToken task: it sends the clarifying question with a task token (through SQS, SNS, Lambda or API Gateway), and resumes when the reply arrives with SendTaskSuccess. Set HeartbeatSeconds so an abandoned conversation times out instead of waiting indefinitely.

Ask the customer and wait (Step Functions state) 
"AskCustomer": {
  "Type": "Task",
  "Resource":
    "arn:aws:states:::sqs:sendMessage.waitForTaskToken",
  "Parameters": {
    "QueueUrl": "${ClarifyQueueUrl}",
    "MessageBody": {
      "question.$": "$.clarifyQ",
      "token.$": "$$.Task.Token"
    }
  },
  "HeartbeatSeconds": 900,
  "Next": "Answer"
}

Prompt governance

Skill 1.6.3Implement comprehensive prompt management and governance systems to ensure consistency and oversight of FM operations (for example, by using Amazon Bedrock Prompt Management to create parameterized templates and approval workflows, Amazon S3 to store template repositories, AWS CloudTrail to track usage, Amazon CloudWatch Logs to log access)

An approval workflow

Prompt Management has no built-in approval step, so build one from versions, IAM and a pipeline:

  1. Source of truthPrompt templates live in Git or an S3 repository (versioned bucket), defined as CloudFormation AWS::Bedrock::Prompt resources.
  2. ChangeAn author edits the template; the change goes through review.
  3. TestThe pipeline runs the regression tests below against the draft.
  4. ApproveA manual approval stage in CodePipeline.
  5. ReleaseThe pipeline creates a new AWS::Bedrock::PromptVersion and updates the configuration the application reads (Task 1.2).

Separating duties with IAM

  • Authors may create and update prompts (drafts) but not create versions.
  • Only the pipeline role may create versions.
  • Applications may only render specific versions (bedrock:RenderPrompt) and invoke the model.
Application role: use only approved version 3 
{
  "Effect": "Allow",
  "Action": "bedrock:RenderPrompt",
  "Resource":
    "arn:aws:bedrock:*:*:prompt/PR12AB:3"
}

A prompt can keep at most 10 versions, so retire old ones as part of the release process.

Auditing

AWS CloudTrail

Model calls (InvokeModel, Converse) and prompt changes (CreatePrompt, CreatePromptVersion) are management events, recorded by default. Use of a managed prompt at runtime is a data event on the AWS::Bedrock::Prompt resource type, recorded only if you add it with an advanced event selector (data events cost extra). Similar data events cover flows, agents, knowledge bases and guardrails.

Record prompt usage on a trail (sel.json) 
[{
  "Name": "Managed prompt usage",
  "FieldSelectors": [
    {"Field": "eventCategory",
     "Equals": ["Data"]},
    {"Field": "resources.type",
     "Equals": ["AWS::Bedrock::Prompt"]}
  ]
}]
aws cloudtrail put-event-selectors \
  --trail-name genai-audit \
  --advanced-event-selectors \
    file://sel.json

Model invocation logging

CloudTrail records that a call happened; model invocation logging records what was said: the full request and response, token counts, the caller's identity and any request metadata tags. It's off by default and set per account and Region, delivering to CloudWatch Logs (with a role Bedrock can assume), S3, or both; bodies over 100 KB and binary data go to S3. Query it with CloudWatch Logs Insights or Athena.

Turn on invocation logging (log.json) 
{
  "cloudWatchConfig": {
    "logGroupName": "/bedrock/inv",
    "roleArn":
      "arn:aws:iam::111122223333:role/bl",
    "largeDataDeliveryS3Config": {
      "bucketName": "genai-logs",
      "keyPrefix": "large/"}
  },
  "textDataDeliveryEnabled": true,
  "imageDataDeliveryEnabled": false,
  "embeddingDataDeliveryEnabled": false
}
aws bedrock \
  put-model-invocation-logging-configuration \
  --logging-config file://log.json

Invocation logs contain prompts and answers, so they contain whatever users typed, including personal data. Encrypt the log group and bucket with KMS, restrict who can read them, set retention, and mask PII before logging where required (Task 3.2).

Prompt quality assurance

Skill 1.6.4Develop quality assurance systems to ensure prompt effectiveness and reliability for FMs (for example, by using Lambda functions to verify expected output, Step Functions to test edge cases, CloudWatch to test prompt regression)

A prompt regression suite

  1. Golden datasetRepresentative questions in S3 with expected answers or required properties, including edge cases: empty input, another language, a question outside scope, an injection attempt.
  2. RunA Step Functions Map state sends every case through the candidate prompt version.
  3. Check deterministicallyLambda asserts what can be checked exactly: valid JSON matching the schema, required fields present, no forbidden phrases, length limits, refusal on out-of-scope questions.
  4. Score the restA Bedrock evaluation job (LLM-as-a-judge, or bring-your-own responses) scores correctness, faithfulness and style.
  5. Compare and gatePublish the pass rate and scores as CloudWatch metrics; an alarm or pipeline condition fails the release if they fall below the current version's.
Deterministic checks for one test case (Lambda) 
import json, boto3

cw = boto3.client("cloudwatch")
REQUIRED = {"category", "urgent"}

def handler(event, context):
    out = event["output"]
    try:
        data = json.loads(out)
        ok = REQUIRED <= data.keys()
    except ValueError:
        ok = False
    cw.put_metric_data(
        Namespace="PromptTests",
        MetricData=[{
            "MetricName": "CasePassed",
            "Dimensions": [{
                "Name": "PromptVersion",
                "Value": event["ver"]}],
            "Value": 1 if ok else 0}],
    )
    return {"passed": ok}

Advanced prompt optimization in Prompt Management can also run evaluation-driven optimization: it rewrites a prompt, scores original and optimized versions on your samples with an LLM judge or a Lambda evaluator across several models, and reports quality and latency.

Refining prompts

Skill 1.6.5Enhance FM performance to refine prompts iteratively and improve response quality beyond basic prompting techniques (for example, by using structured input components, output format specifications, chain-of-thought instruction patterns, feedback loops)

Techniques

TechniqueHowHelps with
Structured inputSeparate parts with tags or delimiters: <instructions>, <manual>, <question>The model knows what is instruction and what is data; harder to inject
Few-shot examplesTwo to five input-output pairs, in <example> tagsConsistent format and tone
Output specificationExact format, length, fields; structured outputs with a JSON Schema when code parses itParseable, predictable answers
Chain-of-thoughtAsk the model to reason step by step (inside <thinking> tags) before answeringMulti-step reasoning, calculations
Reasoning modelsTurn on the model's built-in reasoning (for example extended or adaptive thinking) instead of prompting for itHard problems; costs more output tokens and latency
PrefillStart the assistant's reply yourself (for example with {)Forcing a format (not compatible with built-in reasoning)
ParametersLow temperature for factual and extraction tasks, higher for creative onesConsistency versus variety (Task 4.2)

Feedback loops

Refinement should be driven by evidence, not taste: collect thumbs-up and thumbs-down ratings and comments in the application, sample poorly rated conversations from invocation logs, add them to the test set, change the prompt, run the regression suite, and release through the approval workflow. Over time the golden dataset becomes a record of every failure the assistant has had and fixed.

"The model sometimes treats text from retrieved documents as instructions" points to structured input with clear delimiters plus a guardrail's prompt-attack filter. "Answers vary in format and break the parser" points to output specifications and structured outputs, with a low temperature.

Complex prompt systems

Skill 1.6.6Design complex prompt systems to handle sophisticated tasks with FMs (for example, by using Amazon Bedrock Prompt Flows for sequential prompt chains, conditional branching based on model responses, reusable prompt components, integrated pre-processing and post-processing steps)

Amazon Bedrock Flows

The exam guide's "Prompt Flows" is now Amazon Bedrock Flows: a visual or API-defined workflow that links prompts, knowledge bases, agents, code and logic, so a multi-step task runs as one invocation (InvokeFlow).

NodeDoes
Input, OutputOne entry point; one or more results
PromptCalls a model with an inline prompt or a Prompt Management prompt (reusable component), optionally with a guardrail
ConditionBranches on values (for example the category a previous prompt returned), with a default branch
Iterator, CollectorProcess each item of a list, then gather the results
Loop (DoWhile)Repeats steps until a condition is met, with a maximum number of iterations
Knowledge base, Agent, LexRetrieve or answer from a knowledge base, delegate to an agent, classify with a Lex bot
Lambda, Inline codePre- and post-processing: validation, normalization, calling other systems (inline Python code is in preview)
S3 storage and retrievalSave or load data in S3

A support triage flow

  1. InputThe customer's message.
  2. Pre-processA Lambda node masks PII and detects the language.
  3. ClassifyA prompt node (small model) returns the category as JSON.
  4. BranchA condition node: "refund" goes to an agent node that can look up the order; "how-to" goes to a knowledge base node; anything else to a handoff message.
  5. Post-processA prompt node rewrites the answer in the brand's style and the customer's language.
  6. OutputThe final reply.

Operating flows

  • Validate the definition before preparing it; trace each node's inputs and outputs when testing.
  • Versions are immutable snapshots; aliases point applications at a version, so rolling back is repointing the alias.
  • Newer options (in preview): multi-turn flows that pause for user input through an agent node, and asynchronous executions for long-running flows.
  • Data events on the flow alias in CloudTrail record each invocation.

"A fixed sequence of prompts with branches, no code to host" points to Bedrock Flows. "Long-running, many AWS service steps, human approval, error handling and retries" points to Step Functions. "The model decides which steps to take" points to an agent (Task 2.1).

Key takeaways

  • Prompt Management holds templates with variables, system prompts, settings and variants, with immutable versions; apps call a version ARN with variables and can't override its settings. Guardrails enforce rules the prompt can't guarantee.
  • Context: store turns in DynamoDB (session key, timestamp, TTL) and resend them; AgentCore Memory for short- and long-term memory; classify intent with Comprehend, Lex or a small model; pause for clarification with Step Functions task tokens.
  • Governance: templates in Git or S3, a pipeline with tests and manual approval creating prompt versions, IAM separating authors, the pipeline and applications (RenderPrompt on specific versions), CloudTrail data events for prompt usage, and invocation logging (CloudWatch Logs and S3) for content.
  • QA: a golden dataset with edge cases, deterministic Lambda checks, evaluation-job scores, CloudWatch metrics and a release gate; advanced prompt optimization for evaluation-driven rewrites.
  • Refinement: structured, delimited inputs; few-shot examples; explicit output formats and structured outputs; chain-of-thought or built-in reasoning; prefill; feedback loops feeding the test set.
  • Bedrock Flows (formerly Prompt Flows) chains prompt, condition, loop, knowledge base, agent, Lambda and code nodes, with versions and aliases; Step Functions for long-running service workflows.
