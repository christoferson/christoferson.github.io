Overview

Skill 6.3

Operational Handoff Completeness: "Identifying the missing assumption, dependency, or runbook element in a handoff package that would block the team receiving a Claude system entering operation, and specifying the documentation that closes the gap."

Exam items describe a handoff package and an incident or question the new team can't handle, and ask what was missing. The monitoring itself is skill 3.4; the error patterns behind the runbooks are skill 3.8; handing over a business user's workflow is in the Associate notes (CCAO-F 4.3).

A handoff package must let the new team run the system without the builders

Skill 6.3What this skill asks, and a handoff to check.

Questions on this skill describe a handoff package for a Claude system about to go into operation and ask which missing assumption, dependency or runbook would block the team taking it over, and what document closes the gap.

Take a refund agent: support agents that issue refunds by calling a payments system through an MCP server. It is moving from the team that built it to the support-platform team, who will run it day to day. A complete package has four parts:

Assumptions: what the system was designed for

Skill 6.3The conditions the design depends on.

The expected traffic and its peak; the quality floor and how it’s measured; and exactly what the agent may and may not do, meaning its tools and which actions wait for approval.

Dependencies: everything the system relies on, with an owner for each

Skill 6.3The Claude-specific items most often left out.

  • Models: the model IDs in use and their retirement dates.
  • Keys: the API workspace, the key type, its owner and how it’s rotated. Service-account keys survive their creator; personal keys stop working when that person leaves.
  • Limits: the usage tier, the spend cap and any workspace limits, and who can raise them.
  • MCP servers: which versions are pinned, and who owns each.
  • Data: the data arrangement (zero data retention or the retention terms) and its exceptions.

Runbooks: one for each event that is likely to happen

Skill 6.3What to do, written so the new team can act at 3 a.m.

Rate or ramp limits being hit; the spend cap being reached; the model being overloaded, and switching to the fallback; MCP connection failures; a suspected prompt injection; a wrong or harmful answer reported by a customer; and a model deprecation notice arriving.

Operations: how to watch it, test it and roll it back

Skill 6.3The tools for running the system day to day.

Dashboards and alerts; the evaluation suite, its baseline scores and how to rerun it; prompt and configuration versions, with how to roll back; and the on-call rota with escalation contacts, both internal and at Anthropic.

Checking the build team’s package

Skill 6.3The refund agent’s package against the four parts.

  • Gaps that block operation. No spend-cap runbook and no record of the tier, the cap or who can raise it, so the first month’s peak could take the service down with nobody able to fix it. No evaluation suite or baseline scores, so the new team can’t safely change a prompt.
  • Gaps that leave a risk open. No runbook for injection or for a harmful answer, no procedure for a deprecation notice, and no record of the data arrangement’s exceptions.
  • A gap in ownership. No on-call rota and no escalation contacts.

The code below checks the package against the four parts and lists what is missing:

handoff_check.py (handoff_check.py)Optional 
"""Check a handoff package for the gaps that would stop the receiving operations team.

System: a refund agent that issues refunds through a payments MCP server, moving from the build team to the support-platform team."""

REQUIRED = {
    "assumptions": ["traffic profile and peak (conversations/day, peak hour)", "quality floor and how it's measured",
                    "what the agent may and may not do (tool list, approval gates)"],
    "dependencies": ["model IDs with retirement dates", "API workspace, key type and owner; rotation schedule",
                     "usage tier, spend cap, workspace limits and who can raise them",
                     "MCP servers: owner, version pin, credentials", "data arrangement (ZDR / retention) and its exceptions"],
    "runbooks": ["429 with retry-after (rate or ramp limit)", "429 without retry-after (spend cap)",
                 "529 overloaded / fallback routing", "MCP server connection failures",
                 "suspected prompt injection", "a wrong or harmful answer reported by a customer",
                 "model deprecation notice received"],
    "operations": ["dashboards and alerts (outcome reconciliation, per-tool errors, telemetry freshness)",
                   "evaluation suite, baseline scores and how to rerun", "prompt and config versions, and how to roll back",
                   "on-call rota and escalation contacts at Anthropic and internally"],
}


def check(package: dict) -> list[str]:
    gaps = []
    for section, items in REQUIRED.items():
        have = set(package.get(section, []))
        gaps += [f"{section}: {item}" for item in items if item not in have]
    return gaps


PACKAGE = {  # what the build team handed over
    "assumptions": ["traffic profile and peak (conversations/day, peak hour)", "what the agent may and may not do (tool list, approval gates)"],
    "dependencies": ["model IDs with retirement dates", "MCP servers: owner, version pin, credentials",
                     "API workspace, key type and owner; rotation schedule"],
    "runbooks": ["429 with retry-after (rate or ramp limit)", "529 overloaded / fallback routing", "MCP server connection failures"],
    "operations": ["dashboards and alerts (outcome reconciliation, per-tool errors, telemetry freshness)",
                   "prompt and config versions, and how to roll back"],
}

if __name__ == "__main__":
    for gap in check(PACKAGE):
        print("missing:", gap)

Closing a gap: the spend-cap runbook

Skill 6.3The runbook the package lacked, and what it must say.

  • How to recognise it precisely. The spend cap returns a 429 error with no retry-after header and the error code enforced_spend_limit_reached. A rate or ramp limit looks different and has its own runbook.
  • What to do, from the documentation. Retries can’t succeed. A tier increase is requested from the Console, or usage resumes at the start of the next month. A spend limit you set on a workspace returns a 400 instead.
  • The people. Who to page, who has the permission to raise the tier, and what customers see in the meantime.
runbook_spend_cap.txt (Spend-cap runbook)Optional 
RUNBOOK: refund agent returns errors to every customer; API responds 429 with no retry-after

Recognise
  - All requests fail at once, not a gradual rise; 429 rate_limit_error with no retry-after header.
  - error.details.error_code = enforced_spend_limit_reached  -> monthly spend cap for the usage tier.
    (ramp_limit_exceeded or a retry-after header means a rate or ramp limit instead: see RB-03.)

Act now (first 15 minutes)
  1. Stop automatic retries for this error: they cannot succeed until the cap changes.
  2. Switch the chat widget to degraded mode: "Our assistant is unavailable; here is how to reach us."
  3. Page the platform owner (rota: support-platform-oncall). Only org admins can change limits.

Restore
  4. If a workspace spend limit we set was hit (400 invalid_request_error), raise it in Console > Spend limits.
  5. If the tier cap was hit, request a tier increase on the Console Rate limits page, or contact Anthropic
     support for urgent cases. Usage otherwise resumes at 00:00 UTC on the 1st of next month.
  6. Turn degraded mode off; watch error rate and cost per hour for 30 minutes.

Afterwards
  7. Find what drove spend (cost by route, cache-read share, long sessions) - see RB-11.
  8. Add or lower a workspace spend limit with alerts at 70% and 90% of the cap.

“The code and the architecture diagram are enough” is the usual reason handoffs fail. The new team can read the code; they can’t read the assumptions, the limits nobody wrote down, or what the builders would have done at 3 a.m.

Gaps that look small but block operation

Skill 6.3And why each one matters.

  • A personal API key in production: it stops working when that person’s account is removed, often right after the handoff.
  • Deprecation emails going to one person’s inbox: the 60 days’ notice is wasted if nobody on the new team receives it.
  • No baseline scores: without them, “the answers got worse” can’t be confirmed or ruled out.
  • An MCP server that isn’t pinned: a change upstream alters the system’s behaviour with no change in your own code.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A team takes over an agent whose package has code, a diagram and dashboards, but no record of the usage tier, spend cap or who can raise it. What is the risk?
  1. A. None; dashboards are enough
  2. B. The first traffic peak could hit the spend cap and stop the service with nobody able to fix it
  3. C. The model will change
  4. D. Latency will rise
Answer
B
Why
The spend cap stops all requests until the next month or a tier increase, and retries can’t help. Without knowing the tier and who can raise it, the new team can’t recover quickly.
Question 2
Scenario
A production agent uses an API key belonging to the engineer who built it. That engineer is leaving. What should the handoff require?
  1. A. Nothing
  2. B. Move production to a service-account key with a named owner and rotation
  3. C. Share the engineer’s password
  4. D. Disable the key after they leave
Answer
B
Why
Personal keys stop working when the account is removed, often right after a handoff. Service-account keys survive their creator.
Question 3
Scenario
The new team wants to change a prompt but has no evaluation suite or baseline scores. Why is that a blocking gap?
  1. A. It isn’t; prompts can be changed freely
  2. B. Without a baseline they can’t tell whether the change made answers worse
  3. C. It only affects cost
  4. D. Prompts can’t be changed after a handoff
Answer
B
Why
Baseline scores and a way to rerun the evaluation are what make a change safe. Without them, “the answers got worse” can’t be confirmed or ruled out.
Question 4
Scenario
Which item belongs in the spend-cap runbook?
  1. A. Retry the request with exponential backoff
  2. B. How to recognise it (429, no retry-after, enforced_spend_limit_reached), who can raise the tier, and what customers see
  3. C. Switch to another model
  4. D. Lower the temperature
Answer
B
Why
A runbook says how to recognise the event precisely and who acts. Retries and other models on the same account hit the same cap.

Key takeaways

  • A handoff package needs assumptions, dependencies, runbooks and operations, not just code and diagrams.
  • Claude-specific dependencies: model IDs and retirement dates, key type and owner, tier, spend cap and limits, pinned MCP servers and their owners, and the data arrangement with its exceptions.
  • Runbooks for the likely events: rate and ramp limits, the spend cap, overload and fallback, MCP failures, injection, harmful answers and deprecation notices.
  • Operations: dashboards and alerts, the evaluation suite with baselines, versioned prompts with rollback, on-call and escalation.
  • Close each gap with the specific document, written so the new team can act without the builders.

  • Model deprecations (Claude API docs): retirement dates and notice
