6.3: Operational Handoff Completeness

Before a Claude system passes from the people who built it to the people who'll run it, checking the handoff package for what the new team can't work out on their own: the assumptions it was built on, everything it depends on, and what to do when each likely thing goes wrong.

Overview

Skill 6.3

Operational Handoff Completeness: "Identifying the missing assumption, dependency, or runbook element in a handoff package that would block the team receiving a Claude system entering operation, and specifying the documentation that closes the gap."

Exam items describe a handoff package and an incident or question the new team can't handle, and ask what was missing. The monitoring itself is skill 3.4; the error patterns behind the runbooks are skill 3.8; handing over a business user's workflow is in the Associate notes (CCAO-F 4.3).

Sources: Claude documentation on rate and spend limits, errors, model deprecations, API keys and data retention, as used on earlier pages, and paraphrased. The checklist sections are my own framing; the package, runbook and code are my own, and the check is tested.

Running example. The refund agent from skill 3.4 moves from the team that built it to the support-platform team, who'll run it day to day.

What a Claude handoff must contain

Skill 6.3Four sections, with the Claude-specific items in each.

  • Assumptions: the traffic profile and peak, the quality floor and how it's measured, and exactly what the agent may and may not do (tools, approval gates).
  • Dependencies: model IDs and their retirement dates; API workspace, key type, owner and rotation (service-account keys survive their creator, personal keys don't); usage tier, spend cap and workspace limits, and who can raise them; MCP servers with owners, version pins and credentials; the data arrangement (for example ZDR) and its exceptions.
  • Runbooks: one per likely event: rate or ramp limits, the spend cap, model overload and fallback, MCP connection failures, suspected prompt injection, a wrong or harmful answer, and a model deprecation notice.
  • Operations: dashboards and alerts, the evaluation suite with baseline scores and how to rerun it, prompt and configuration versions with rollback, and on-call and escalation contacts.

Checking a package

Skill 6.3The build team's package against the checklist.

handoff_check.py (handoff_check.py) 
"""Check a handoff package for the gaps that would stop the receiving operations team.

System: the refund agent from skill 3.4, moving from the build team to the support-platform team."""

REQUIRED = {
    "assumptions": ["traffic profile and peak (conversations/day, peak hour)", "quality floor and how it's measured",
                    "what the agent may and may not do (tool list, approval gates)"],
    "dependencies": ["model IDs with retirement dates", "API workspace, key type and owner; rotation schedule",
                     "usage tier, spend cap, workspace limits and who can raise them",
                     "MCP servers: owner, version pin, credentials", "data arrangement (ZDR / retention) and its exceptions"],
    "runbooks": ["429 with retry-after (rate or ramp limit)", "429 without retry-after (spend cap)",
                 "529 overloaded / fallback routing", "MCP server connection failures",
                 "suspected prompt injection", "a wrong or harmful answer reported by a customer",
                 "model deprecation notice received"],
    "operations": ["dashboards and alerts (outcome reconciliation, per-tool errors, telemetry freshness)",
                   "evaluation suite, baseline scores and how to rerun", "prompt and config versions, and how to roll back",
                   "on-call rota and escalation contacts at Anthropic and internally"],
}


def check(package: dict) -> list[str]:
    gaps = []
    for section, items in REQUIRED.items():
        have = set(package.get(section, []))
        gaps += [f"{section}: {item}" for item in items if item not in have]
    return gaps


PACKAGE = {  # what the build team handed over
    "assumptions": ["traffic profile and peak (conversations/day, peak hour)", "what the agent may and may not do (tool list, approval gates)"],
    "dependencies": ["model IDs with retirement dates", "MCP servers: owner, version pin, credentials",
                     "API workspace, key type and owner; rotation schedule"],
    "runbooks": ["429 with retry-after (rate or ramp limit)", "529 overloaded / fallback routing", "MCP server connection failures"],
    "operations": ["dashboards and alerts (outcome reconciliation, per-tool errors, telemetry freshness)",
                   "prompt and config versions, and how to roll back"],
}

if __name__ == "__main__":
    for gap in check(PACKAGE):
        print("missing:", gap)

  • Blocking gaps: no spend-cap runbook and no record of the tier, cap or who can raise it, so the first month's peak could take the service down with nobody able to fix it; no evaluation suite or baseline, so the new team can't safely change a prompt or model.
  • Risk gaps: no runbook for injection or for a harmful answer, no deprecation procedure, and no record of the data arrangement's exceptions.
  • Ownership gap: no on-call rota or escalation contacts.

Closing a gap: a runbook

Skill 6.3The spend-cap runbook the package lacked.

runbook_spend_cap.txt (Spend-cap runbook) 
RUNBOOK: refund agent returns errors to every customer; API responds 429 with no retry-after

Recognise
  - All requests fail at once, not a gradual rise; 429 rate_limit_error with no retry-after header.
  - error.details.error_code = enforced_spend_limit_reached  -> monthly spend cap for the usage tier.
    (ramp_limit_exceeded or a retry-after header means a rate or ramp limit instead: see RB-03.)

Act now (first 15 minutes)
  1. Stop automatic retries for this error: they cannot succeed until the cap changes.
  2. Switch the chat widget to degraded mode: "Our assistant is unavailable; here is how to reach us."
  3. Page the platform owner (rota: support-platform-oncall). Only org admins can change limits.

Restore
  4. If a workspace spend limit we set was hit (400 invalid_request_error), raise it in Console > Spend limits.
  5. If the tier cap was hit, request a tier increase on the Console Rate limits page, or contact Anthropic
     support for urgent cases. Usage otherwise resumes at 00:00 UTC on the 1st of next month.
  6. Turn degraded mode off; watch error rate and cost per hour for 30 minutes.

Afterwards
  7. Find what drove spend (cost by route, cache-read share, long sessions) - see RB-11.
  8. Add or lower a workspace spend limit with alerts at 70% and 90% of the cap.
  • Recognise it precisely: the spend cap returns 429 without retry-after and the error code enforced_spend_limit_reached; a rate or ramp limit looks different and has its own runbook.
  • Act on what the docs say: retries can't succeed; a tier increase is requested from the Console, or usage resumes at the start of the next month; a workspace limit you set returns 400 instead.
  • Include the human side: who to page, who has the permission, and what customers see in the meantime.

"The code and the architecture diagram are enough" is the usual reason handoffs fail. The new team can read the code; they can't read the assumptions, the limits that nobody wrote down, or what the builders would have done at 3 a.m.

Gaps that look small

Skill 6.3And why they block operation.

  • A personal API key in production: it stops working when that person's account is removed, often right after the handoff.
  • Deprecation emails going to one inbox: the at-least-60-day notice is wasted if nobody on the new team receives it.
  • No baseline scores: without them, "the answers got worse" can't be confirmed or refuted.
  • An unpinned MCP server: an upstream change alters behaviour with no change in your code.

Key takeaways

  • A handoff package needs assumptions, dependencies, runbooks and operations, not just code and diagrams.
  • Claude-specific dependencies: model IDs and retirement dates, key type and owner, tier, spend cap and limits, MCP server pins and owners, the data arrangement and its exceptions.
  • Runbooks for the likely events: rate and ramp limits, the spend cap, overload and fallback, MCP failures, injection, harmful answers, deprecation notices.
  • Operations: dashboards and alerts, the evaluation suite with baselines, versioned prompts with rollback, on-call and escalation.
  • Close each gap with the specific document, written so the receiving team can act on it without the builders.
