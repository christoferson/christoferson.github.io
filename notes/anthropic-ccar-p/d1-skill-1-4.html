1.4: Orchestrator and Subagent Decomposition

Overview

Skill 1.4

Orchestrator and Subagent Decomposition: "Evaluating a proposed orchestrator/subagent decomposition for a multi-step workload against stated observability and error-recovery requirements, and identifying where task boundaries, control flow, or result synthesis will fail."

Exam items describe a multi-agent design and a requirement (every decision must be traceable; a failed step must not restart the whole job) and ask where it breaks. Building coordinator and subagent systems with the Agent SDK is covered in the Foundations notes (CCAR-F 1.2 and 1.3); this skill is the evaluation.

A split across subagents can fail in three places

Skill 1.4What the design looks like, what the exam asks of it, and where it breaks.

In an orchestrator and subagent design, one agent (the orchestrator) splits a large job into parts, gives each part to a subagent with a written brief, and combines what comes back into one answer. Each subagent works in its own context: it sees only its brief, not the orchestrator’s conversation or the other subagents’ work, and only its final result returns.

Take a review of an outside vendor before a company signs a contract with it. There are four areas, each with its own documents: the vendor’s security policies, its independent audit report, its data-handling agreement, and its list of the other companies it passes data to. The orchestrator gives each area to a subagent and writes the final assessment.

Exam questions describe such a design and two requirements: observability (you can see what each part did and why the result came out as it did) and error recovery (a failure in one part doesn’t ruin or restart the whole job). They ask where the design breaks. It breaks in one of three places:

  • Task boundaries: the way the work is split and briefed.
  • Control flow: what happens when a subagent fails, hangs or returns rubbish.
  • Synthesis: how the results are combined into the final answer.

The sections below take each place in turn, then look at recording what happened, a design that holds up, and when not to split at all.

Give each subagent its own clearly bounded task

Skill 1.4Task boundaries: most failures start with a vague split.

A subagent knows only what its brief says. Anthropic found, building its own multi-agent research system, that without detailed task descriptions subagents duplicated each other’s work, left gaps, or missed information. Look for these faults in a proposed split:

  • Overlap. Two subagents both read the audit report; their findings conflict and the cost doubles. Fix: assign each subagent its sources, not only its topic.
  • Gaps. No subagent owns the list of other companies, so the assessment says nothing about it. Fix: check that the task list covers every part of the requirement before running anything.
  • Hidden dependencies. The data-handling subagent needs the access-control subagent’s conclusion, but subagents can’t see each other’s work. Fix: run dependent tasks one after the other and pass the earlier result in the brief, or merge them into one task.
  • Thin briefs. “Check data security”, with no scope, sources or output format, invites a subagent to drift. Fix: give every brief an objective, the output format to return, which tools and sources to use, and what belongs to someone else.
  • Over-splitting. A subagent for every document in a small review adds cost and coordination for nothing. Fix: split by independent area, and only when the work is big enough.

A failed subagent must not stop or restart the whole job

Skill 1.4Control flow: what happens when one part goes wrong.

Agents run for a long time and build up state, so small failures add up. Anthropic’s write-up warns that without safeguards, “minor system failures can be catastrophic”. These are the usual faults, each with its fix:

  • No timeout or retry limit. One stuck subagent holds up the whole review. Fix: a timeout and a fixed number of attempts for each subagent.
  • Starting over after a failure. The last area fails and the job reruns the three that had already succeeded. Fix: save each finished result (a checkpoint), so a rerun redoes only what failed. Anthropic built its system to resume from where an agent was when the error happened.
  • Accepting whatever comes back. A subagent returns loose prose instead of the agreed structure, and the orchestrator carries on as if it had findings. Fix: check each result against the expected format in code, and count a bad result as a failed attempt.
  • Hiding failures from the agent. Anthropic found it worked well to tell the agent when a tool is failing so it can adapt, combined with retry logic in code and regular checkpoints.
  • No limits on the tree. Nothing caps how many subagents can start, how many turns they take, or what they spend. The Agent SDK has caps for nesting depth, concurrent subagents and budget; set them deliberately.

Record every subagent run, so the result can be explained

Skill 1.4Observability: being able to answer “why does the report say this?”

What goes wrong. The assessment’s section on other companies is empty, and nobody can say whether the subagent found nothing, failed, or was never started.

What fixes it. Write a record for every subagent run: which task, which attempt, the outcome, how long it took, and a reference to what it produced. Record retries, reuse of a saved result, and the synthesis too. Anthropic credits full production tracing with making its system’s failures diagnosable; it monitored the agents’ decision patterns and how they interacted, without monitoring the content of the conversations, which keeps sensitive documents out of the trace.

The final answer must keep its sources and name its gaps

Skill 1.4Synthesis: the last step is where evidence gets lost.

  • Silent omission. A failed area simply doesn’t appear, and the assessment reads as complete. Fix: a failed area becomes a named gap in the report, and the overall verdict says “incomplete”.
  • Details lost in summaries. Each layer summarises the one below, and the specifics (which control, which page of the evidence) disappear. Anthropic calls this a “game of telephone”. Fix: subagents store their full results and pass back a short reference; the synthesis reads the stored results.
  • Conflicts smoothed over. Two findings disagree and the summary picks one without saying so. Fix: show both, with where each came from.
  • No trail to the evidence. A conclusion can’t be traced to the subagent and document behind it. Fix: every finding keeps its area and a reference to its evidence all the way into the report.

“Have the orchestrator summarise whatever the subagents return” fails both requirements at once: nobody can see what each subagent did, and a failure turns into a confident report with a hole in it.

A design that meets both requirements

Skill 1.4The fixes above, put together in one orchestrator.

  • Clear tasks. Each task names its objective, the sources it may read and the format of its result, so areas don’t overlap and nothing relies on shared history.
  • Bounded, resumable runs. Each area gets a fixed number of attempts, a malformed result counts as a failure, and finished results are saved, so a rerun redoes only what failed.
  • A synthesis that keeps evidence. Findings are read from the stored results, keep their area and evidence reference, and a failed area becomes a named gap with an “incomplete” verdict.
  • A trace line for everything: every run, retry and reuse, and the synthesis itself, without document contents in the trace.

The test runs it with one area that returns a malformed result once and another that always fails, and checks the retries, the named gap, the trace, and that a rerun reuses the three finished areas.

"""Orchestrator for vendor reviews: one subagent per evidence area, then synthesis.

The decomposition is designed for the two stated requirements:
- observability: every subagent run leaves a trace record (task, outcome, timing, result reference);
- error recovery: results are checkpointed, so a rerun skips finished areas, and a failed area
  becomes a named gap in the report instead of a silent omission.
run_subagent is injected: in production it starts an Agent SDK subagent or a Messages API loop."""
import json
import time
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Task:                       # the contract each subagent gets: no shared history, so be explicit
    area: str
    objective: str
    sources: tuple                # what it may read: the boundary that stops overlap
    output: str = "JSON: {findings: [{control, status, evidence_ref}], open_questions: []}"


TASKS = [
    Task("access", "Assess identity and access controls (SSO, MFA, joiner-leaver process).", ("policies/iam*", "audit/access*")),
    Task("data", "Assess encryption, retention and data residency.", ("policies/data*", "dpa.pdf")),
    Task("incident", "Assess incident response and breach notification times.", ("policies/ir*", "audit/incident*")),
    Task("vendors", "Assess the other companies the vendor passes data to.", ("other_companies.csv",)),
]


class Orchestrator:
    def __init__(self, run_subagent, store: Path, max_attempts: int = 2):
        self.run_subagent, self.store, self.max_attempts = run_subagent, store, max_attempts
        self.store.mkdir(parents=True, exist_ok=True)
        self.trace = self.store / "trace.jsonl"

    def _log(self, **event):
        with self.trace.open("a") as f:
            f.write(json.dumps({"t": round(time.time(), 3), **event}) + "\n")

    def run_area(self, task: Task) -> dict:
        ref = self.store / f"{task.area}.json"
        if ref.exists():                                       # checkpoint: resume, don't redo
            self._log(area=task.area, outcome="reused", ref=ref.name)
            return {"area": task.area, "status": "done", "ref": ref.name}
        for attempt in range(1, self.max_attempts + 1):
            start = time.time()
            try:
                result = self.run_subagent(asdict(task))
                if not isinstance(result.get("findings"), list):
                    raise ValueError("output missing 'findings' list")
                ref.write_text(json.dumps(result))             # store externally, pass a reference
                self._log(area=task.area, attempt=attempt, outcome="ok", secs=round(time.time() - start, 2), ref=ref.name)
                return {"area": task.area, "status": "done", "ref": ref.name}
            except Exception as e:                             # retry once, then record a gap
                self._log(area=task.area, attempt=attempt, outcome="error", error=str(e)[:200])
        return {"area": task.area, "status": "gap", "ref": None}

    def review(self, vendor: str) -> dict:
        results = [self.run_area(t) for t in TASKS]
        findings, gaps = [], []
        for r in results:
            if r["status"] == "gap":
                gaps.append(r["area"])
                continue
            data = json.loads((self.store / r["ref"]).read_text())
            findings += [dict(f, area=r["area"]) for f in data["findings"]]
        report = {"vendor": vendor, "findings": findings, "gaps": gaps,
                  "verdict": "incomplete: rerun or review gaps manually" if gaps else "complete"}
        self._log(outcome="synthesised", gaps=gaps, findings=len(findings))
        return report

Use subagents only for broad, independent work

Skill 1.4Splitting costs tokens and coordination, so it has to pay for itself.

The cost. Anthropic measured its multi-agent runs using roughly 15 times the tokens of a chat. Waiting for every subagent to finish is also a bottleneck: the orchestrator can’t steer them while they work, and one slow subagent holds up the rest; running them asynchronously removes the wait but makes coordination and error handling harder.

When it pays off. Work that splits into separate areas with separate sources, where each part can be done without the others and a synthesis at the end brings them together, like the four evidence areas above.

When it doesn’t. Work where every part needs the same context and depends on the others (Anthropic gives most coding work as an example), and small jobs, where one agent with a few tool calls is cheaper and easier to follow.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Two subagents in a research design both read the same 200-page report and return conflicting findings. What should the brief have done?
  1. A. Asked them to agree
  2. B. Assigned each subagent its own sources, not only its topic
  3. C. Used a larger model
  4. D. Run them one after the other
Answer
B
Why
Overlap comes from briefs that name topics but not sources. Assigning sources keeps the areas apart and avoids paying twice for the same reading.
Question 2
Scenario
In a four-area review, the last subagent fails and the whole job reruns all four areas. Which requirement does this break, and what fixes it?
  1. A. Observability; add logging
  2. B. Error recovery; save each finished result so a rerun redoes only what failed
  3. C. Latency; use a faster model
  4. D. Cost; use batches
Answer
B
Why
A failure in one part shouldn’t restart everything. Checkpointing finished results lets a rerun resume from the failure, as Anthropic built its research system to do.
Question 3
Scenario
A subagent times out, and the final report simply omits its area while reading as complete. What should the synthesis do instead?
  1. A. Leave it out to keep the report clean
  2. B. Name the failed area as a gap and mark the overall verdict incomplete
  3. C. Guess the missing findings
  4. D. Retry forever
Answer
B
Why
A failed area must surface as a named gap, never disappear. Otherwise a confident report hides a hole, failing both observability and error recovery.
Question 4
Scenario
A small task needs three tool calls and shares one context throughout. A team proposes splitting it across four subagents. What is the main objection?
  1. A. Subagents can’t call tools
  2. B. Multi-agent runs cost far more tokens and add coordination; small, coupled work suits one agent
  3. C. Subagents always fail
  4. D. It breaks the context window
Answer
B
Why
Anthropic measured multi-agent runs at roughly 15 times the tokens of a chat. Subagents pay off for broad, independent work, not for small jobs that share context.

Key takeaways

  • An orchestrator and subagent design fails in one of three places: how the work is split and briefed, what happens when a subagent fails, and how the results are combined.
  • Briefs need an objective, an output format, the sources to use and clear limits; check the split for overlap, gaps and hidden dependencies.
  • Error recovery: timeouts, a fixed number of attempts, results checked in code, and saved results so a rerun redoes only what failed.
  • Observability: a record for every subagent run, retry and reuse, without storing document contents.
  • Synthesis: pass references to stored results rather than summaries, keep each finding’s evidence, show conflicts, and turn a failed area into a named gap.
  • Multi-agent runs cost far more tokens; use them for broad, independent work, not for small or tightly coupled jobs.
