1.4: Orchestrator and Subagent Decomposition

Reviewing a design where a lead agent hands work to subagents: will you be able to see what happened, will it recover when one piece fails, and where will the split itself break: overlapping or missing tasks, a stuck control flow, or a final answer that quietly drops what a subagent found?

Overview

Skill 1.4

Orchestrator and Subagent Decomposition: "Evaluating a proposed orchestrator/subagent decomposition for a multi-step workload against stated observability and error-recovery requirements, and identifying where task boundaries, control flow, or result synthesis will fail."

Exam items describe a multi-agent design and a requirement (every decision must be traceable; a failed step must not restart the whole job) and ask where it breaks. Building coordinator and subagent systems with the Agent SDK is covered in the Foundations notes (CCAR-F 1.2 and 1.3); this skill is the evaluation.

Sources: Anthropic's engineering post on its multi-agent research system and the Agent SDK subagents documentation, checked on 20 November 2026 and paraphrased. The workload and code are my own; the code is tested with a fake subagent runner.

Running example. A procurement team reviews suppliers' security evidence (policies, a SOC 2 report, a data processing agreement, a subprocessor list). An orchestrator gives each evidence area to a subagent and writes the final assessment.

What Anthropic learned in production

Skill 1.4From its multi-agent research system.

  • Errors compound: agents run long and hold state, so without mitigations "minor system failures can be catastrophic". Anthropic built the system to resume from where an agent was when the error occurred, rather than starting over.
  • Tell the agent, and add safeguards: letting the agent know a tool is failing so it can adapt worked well, combined with deterministic retry logic and regular checkpoints.
  • Trace everything: full production tracing made failures diagnosable; they monitored decision patterns and interaction structure without monitoring conversation contents.
  • Detailed task descriptions: without them, subagents duplicated work, left gaps or missed information. Each needs an objective, an output format, guidance on tools and sources, and clear boundaries.
  • Pass references, not copies: subagents stored their work externally and passed lightweight references back, avoiding loss in a "game of telephone".
  • Synchronous waiting is a bottleneck: the lead can't steer subagents, they can't coordinate, and one slow subagent blocks everything; going asynchronous makes coordination, state consistency and error propagation harder.
  • Cost: multi-agent runs used roughly 15 times the tokens of a chat.

Where task boundaries fail

Skill 1.4Warning signs in a proposed split.

  • Overlap: two subagents both read the SOC 2 report; findings conflict and the cost doubles. Fix: assign sources, not just topics.
  • Gaps: nobody owns subprocessors, so the assessment is silent on them. Fix: check the task list covers the whole requirement.
  • Hidden dependencies: the data subagent needs the access subagent's conclusion. Subagents don't see each other's work or the parent's history, so dependent work must run in sequence or be merged.
  • Thin briefs: a subagent receives only its prompt; "check data security" without scope, sources or output format invites drift.
  • Over-splitting: a subagent per document for a small review adds cost and coordination for nothing.

Where control flow fails

Skill 1.4What happens when one subagent fails, stalls or misbehaves.

  • No retry or timeout: one stuck subagent blocks the whole review.
  • Restart from scratch: a failure in the last area reruns the three that succeeded, against an error-recovery requirement.
  • Unvalidated output: a subagent returns prose instead of the agreed structure, and the orchestrator carries on as if it had findings.
  • Unbounded spawning: no cap on subagents, turns or budget. The Agent SDK has caps (spawn depth, concurrent subagents, a budget limit), but the design must set them deliberately.
  • Nothing to trace: without a record per subagent run (task, attempt, outcome, timing), "why is the vendors section empty?" can't be answered.

Where synthesis fails

Skill 1.4The last step is where evidence gets lost.

  • Silent omission: a failed area simply doesn't appear, and the report reads as complete.
  • Telephone effect: each layer summarises the one below, and specifics (which control, which page of evidence) disappear.
  • Conflicts flattened: two findings disagree and the summary picks one without saying so.
  • No provenance: a conclusion can't be traced to the subagent and evidence behind it.

"Have the orchestrator summarise whatever the subagents return" fails both requirements at once: you can't see what each subagent did, and a failure turns into a confident report with a hole in it.

A decomposition built for both requirements

Skill 1.4What a split that holds up looks like.

"""Orchestrator for supplier security reviews: one subagent per evidence area, then synthesis.

The decomposition is designed for the two stated requirements:
- observability: every subagent run leaves a trace record (task, outcome, timing, result reference);
- error recovery: results are checkpointed, so a rerun skips finished areas, and a failed area
  becomes a named gap in the report instead of a silent omission.
run_subagent is injected: in production it starts an Agent SDK subagent or a Messages API loop."""
import json
import time
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Task:                       # the contract each subagent gets: no shared history, so be explicit
    area: str
    objective: str
    sources: tuple                # what it may read: the boundary that stops overlap
    output: str = "JSON: {findings: [{control, status, evidence_ref}], open_questions: []}"


TASKS = [
    Task("access", "Assess identity and access controls (SSO, MFA, joiner-leaver process).", ("policies/iam*", "soc2/CC6*")),
    Task("data", "Assess encryption, retention and data residency.", ("policies/data*", "dpa.pdf")),
    Task("incident", "Assess incident response and breach notification times.", ("policies/ir*", "soc2/CC7*")),
    Task("vendors", "Assess the supplier's own subprocessors.", ("subprocessors.csv",)),
]


class Orchestrator:
    def __init__(self, run_subagent, store: Path, max_attempts: int = 2):
        self.run_subagent, self.store, self.max_attempts = run_subagent, store, max_attempts
        self.store.mkdir(parents=True, exist_ok=True)
        self.trace = self.store / "trace.jsonl"

    def _log(self, **event):
        with self.trace.open("a") as f:
            f.write(json.dumps({"t": round(time.time(), 3), **event}) + "\n")

    def run_area(self, task: Task) -> dict:
        ref = self.store / f"{task.area}.json"
        if ref.exists():                                       # checkpoint: resume, don't redo
            self._log(area=task.area, outcome="reused", ref=ref.name)
            return {"area": task.area, "status": "done", "ref": ref.name}
        for attempt in range(1, self.max_attempts + 1):
            start = time.time()
            try:
                result = self.run_subagent(asdict(task))
                if not isinstance(result.get("findings"), list):
                    raise ValueError("output missing 'findings' list")
                ref.write_text(json.dumps(result))             # store externally, pass a reference
                self._log(area=task.area, attempt=attempt, outcome="ok", secs=round(time.time() - start, 2), ref=ref.name)
                return {"area": task.area, "status": "done", "ref": ref.name}
            except Exception as e:                             # retry once, then record a gap
                self._log(area=task.area, attempt=attempt, outcome="error", error=str(e)[:200])
        return {"area": task.area, "status": "gap", "ref": None}

    def review(self, supplier: str) -> dict:
        results = [self.run_area(t) for t in TASKS]
        findings, gaps = [], []
        for r in results:
            if r["status"] == "gap":
                gaps.append(r["area"])
                continue
            data = json.loads((self.store / r["ref"]).read_text())
            findings += [dict(f, area=r["area"]) for f in data["findings"]]
        report = {"supplier": supplier, "findings": findings, "gaps": gaps,
                  "verdict": "incomplete: rerun or review gaps manually" if gaps else "complete"}
        self._log(outcome="synthesised", gaps=gaps, findings=len(findings))
        return report
  • Boundaries: each Task names its objective, the sources it may read and its output format, so areas don't overlap and nothing is assumed from shared history.
  • Control flow: each area gets a bounded number of attempts; malformed output counts as a failure; results are checkpointed, so a rerun redoes only what failed.
  • Synthesis: findings are read from stored references, keep their area and evidence reference, and a failed area becomes a named gap with an "incomplete" verdict.
  • Observability: every run, retry, reuse and the synthesis itself is a trace line, without storing document contents in the trace.
  • Tested: one area returns malformed output once, another always fails; the test checks retries, the gap, the trace and that a rerun reuses the three finished areas.

When not to decompose

Skill 1.4Multi-agent isn't free.

  • Shared context and many dependencies are a poor fit, Anthropic notes; most coding work is an example.
  • Small or simple workloads don't justify the token cost; one agent with a few tool calls is cheaper and easier to trace.
  • Parallel, independent, breadth-heavy work is where subagents pay off: separate areas, separate sources, a synthesis at the end.

Key takeaways

  • Evaluate a decomposition at three points: task boundaries (overlap, gaps, dependencies, thin briefs), control flow (retries, timeouts, restarts, caps, validation) and synthesis (omissions, telephone effect, conflicts, provenance).
  • Observability needs a trace per subagent run; error recovery needs checkpoints so a failure resumes rather than restarts.
  • Anthropic's lessons: errors compound, so resume from the failure point; tell the agent about failing tools and add deterministic retries; trace decisions; write detailed task descriptions; pass references, not copies.
  • A failed subagent must surface as a named gap, never disappear from the final answer.
  • Decompose parallel, independent, breadth-heavy work; keep tightly coupled or small work in one agent.
