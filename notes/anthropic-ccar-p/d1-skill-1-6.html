1.6: Deployment Surface and Agent Runtime Selection

Two decisions that constrain everything else: where Claude is called from (Anthropic's API or a cloud provider), and who runs the agent loop (your service, your containers, or Anthropic). Hard constraints decide first; the page then names what each choice costs in features, latency, hosting, state, sandboxing and custody.

Overview

Skill 1.6

Deployment Surface and Agent Runtime Selection: "Selecting a deployment surface (Anthropic API, Amazon Bedrock, Google Vertex AI, Microsoft Foundry) and an agent runtime (Messages API loop, self-hosted Agent SDK or headless Claude Code, Claude Managed Agents) under data residency, compliance, model-availability, and operational-ownership constraints, and justifying the trade-offs the selection imposes on latency, feature availability, hosting, session state, sandboxing, and data custody."

Exam items state constraints and preferences that pull in different directions and ask which combination satisfies the hard ones, and what has to be given up. The runtimes themselves, and how to build on each, are in the developer notes (CCDV-F 1.1).

Two choices: where requests go, and who runs the agent loop

Skill 1.6What this skill asks you to decide.

Every Claude system makes two choices that are easy to blur together:

  • The surface: which platform serves the model. That can be Anthropic’s own Claude API, or a cloud provider’s service (Amazon Bedrock, Google Cloud, Microsoft Foundry). The surface decides which features you get, which regions the model can run in, and whose terms apply to your data.
  • The runtime: who runs the agent loop, meaning the code that sends a request, runs the tools Claude asks for, sends the results back and keeps the session’s state. You can write it yourself, run Anthropic’s ready-made loop on your own machines, or let Anthropic run it for you.

Questions on this skill give constraints that pull in different directions: data must stay in one region, a compliance rule applies, a needed model is only on some platforms, the team doesn’t want to run servers. You pick the combination that meets the hard constraints and say what it costs in latency, features, hosting, session state, sandboxing and who holds the data.

Anthropic-operated surfaces get every feature first

Skill 1.6The Claude API, and Claude Platform on AWS.

The Claude API is Anthropic’s own endpoint. New features arrive here first, including betas, server tools (tools that Anthropic runs for you, such as code execution and web search), the Files API, Agent Skills, Message Batches and Claude Managed Agents. You choose where the model runs with the inference_geo setting, described below.

Claude Platform on AWS is also run by Anthropic, but you buy it through AWS Marketplace and it appears on your AWS bill. Features typically arrive on the same day as on the Claude API, and it supports inference_geo and Managed Agents. It suits an organisation that wants to buy through AWS without giving up features.

Cloud-provider surfaces trade features for your existing cloud

Skill 1.6Amazon Bedrock, Google Cloud and Microsoft Foundry.

Why choose one. Your contracts, security reviews, identity system and data are already with that provider, or you need a region that only the provider’s regional endpoints offer.

  • Amazon Bedrock is run by AWS: requests are authenticated with AWS IAM, and you choose the region through an inference profile. Its bedrock-runtime endpoint doesn’t support the Files API, server tools (code execution, web search and web fetch), Agent Skills, the MCP connector, Message Batches or Managed Agents. A newer Bedrock endpoint accepts the native Messages API shape with fuller feature parity. AWS, not Anthropic, sets the dates when models are retired there.
  • Google Cloud offers two options: one managed by Anthropic, which supports inference_geo and Managed Agents, and one managed by Google, where the endpoint you call sets the region.
  • Microsoft Foundry deployments on Azure can use the US Data Zone Standard deployment type to keep inference in the US.

What it costs. Features arrive later, and some never arrive on a given endpoint, so check every feature the design needs against the surface before choosing it.

Where the model runs isn’t where your data is stored

Skill 1.6The two residency settings, and what neither of them covers.

  • Inference geo: where the model runs. Set per request or as a workspace default. On the Claude API the choices are global (the default) and us; keeping inference in the US multiplies all token prices by 1.1 for Claude 4.6 models and later. A workspace can restrict which choices are allowed.
  • Workspace geo: where data is stored. This covers data at rest and processing done at the endpoint, such as code execution. It’s set when the workspace is created and can’t be changed afterwards; only us is available today.
  • Any other region means a cloud provider. Bedrock’s regional inference profiles cover the US, the EU, Japan and Asia-Pacific for the models listed, at a 10% premium over global routing. Check that the model you need has a profile in your region.
  • Residency isn’t retention. Zero data retention (ZDR) controls how long data is kept, not where it’s processed. The two are separate requirements with separate settings; data residency is itself compatible with ZDR and HIPAA arrangements.

Decide who runs the agent loop

Skill 1.6Three runtimes, from most control to least to look after.

A Messages API loop in your own service

You write the loop yourself: call the API, run the tools Claude requests, return the results, keep the history. It works on every surface and gives you full control, at the cost of writing and maintaining the most code. It suits short, well-defined tasks where you don’t need a full agent harness.

The Agent SDK or headless Claude Code, on your machines

Anthropic’s ready-made agent loop, with built-in tools for files and shell commands, running in your own containers. Each session runs as a Claude Code command-line process, and its transcript is written to that machine’s disk. You own everything around it: storing sessions so they survive a restart, sandboxing the tools (for example with gVisor or Firecracker), scaling, and limits on turns and spend. It suits teams that want a capable agent but need the tools to run inside their own network.

Claude Managed Agents

Anthropic runs the loop and keeps the session state, so long-running and background work needs nothing hosted by you. It’s in beta. A cloud environment gives each session a fresh container run by Anthropic. A self-hosted sandbox runs the shell and file tools on your own workers, but the conversation history and tool results still reach Anthropic. Managed Agents isn’t eligible for ZDR or HIPAA, except in a fully self-hosted arrangement made through Anthropic’s account team.

Let the hard constraints choose first

Skill 1.6The order of the decision.

  1. Hard constraints remove options. A region the Claude API can’t serve, a contract that keeps data with one cloud provider, a HIPAA or ZDR requirement, a model that’s only on some surfaces.
  2. Who must run the loop picks the runtime. Must the loop or its tools run inside your network, and can your team run and support it? Or should Anthropic run it?
  3. Preferences decide among what’s left. Newest features, lowest latency, least code. A preference that conflicts with a hard constraint isn’t met; it becomes a trade-off you state.

“Use Managed Agents to avoid hosting” fails wherever Managed Agents isn’t offered, or where HIPAA or ZDR eligibility is required. “Use the newest model everywhere” fails when that model isn’t available on the surface or in the region a hard constraint has already fixed.

Worked example: four organisations, four answers

Skill 1.6The same order applied to different constraints.

  • A games studio has no residency or compliance requirement, wants the newest features, and doesn’t want to host anything. Nothing removes an option, so the preferences decide: the Claude API with Managed Agents.
  • A clinic’s software supplier handles health data, so HIPAA applies, which rules out Managed Agents in its hosted form. Its calls are short and well defined, so it doesn’t need an agent harness: a Messages API loop on the Claude API, using only HIPAA-eligible features.
  • An EU retailer must keep inference in the EU, which the Claude API’s inference_geo doesn’t offer. That leaves a regional Bedrock profile. Managed Agents isn’t on Bedrock, so the runtime has to be self-hosted, and arriving later on features is the price.
  • A factory has an AWS contract and tools that must run on its plant network. Claude Platform on AWS keeps the AWS billing; a self-hosted sandbox would keep the tools on the plant network if it’s available there, and otherwise the Agent SDK on the factory’s own machines.

The code below writes the same rules down and runs them on the four organisations:

select_platform.py (select_platform.py)Optional 
"""Choose a deployment surface and an agent runtime from hard constraints first, preferences second.

Facts encoded (Claude docs, November 2026):
- Claude API inference_geo offers "us" (1.1x price) or "global"; workspace geo is "us" only.
- Bedrock sets the region by inference profile; regional (us, eu, jp, apac) costs 10% more than global.
  Its bedrock-runtime endpoint lacks the Files API, server tools, Agent Skills, the MCP connector,
  Message Batches and Managed Agents.
- Claude Platform on AWS is Anthropic-operated, billed through AWS Marketplace, typically same-day features.
- Managed Agents: beta; not ZDR or HIPAA eligible except self-hosted Managed Agents."""
from dataclasses import dataclass, field


@dataclass
class Needs:
    inference_region: str = "any"           # "any", "us", "eu", ...
    must_stay_in_cloud: str = ""            # "aws", "gcp", "azure" if contracts require that provider
    hipaa_or_zdr: bool = False
    newest_features: bool = False           # Skills, server tools, Files API, betas on day one
    host_the_loop: str = "either"           # "us" = we must run it; "anthropic" = we won't run it
    long_running_sessions: bool = False
    tools_on_our_network: bool = False      # internal, non-routable systems


@dataclass
class Choice:
    surface: str
    runtime: str
    tradeoffs: list = field(default_factory=list)


def choose(n: Needs) -> Choice:
    t = []
    # 1. Surface: residency and provider contracts are hard constraints.
    if n.inference_region not in ("any", "us"):
        surface = "Amazon Bedrock (regional inference profile)"
        t += ["regional endpoint costs 10% more than global",
              "feature lag: no Files API, server tools, Skills, MCP connector, Batches or Managed Agents on bedrock-runtime",
              f"confirm the model you need has a '{n.inference_region}' inference profile"]
    elif n.must_stay_in_cloud == "aws":
        surface = "Claude Platform on AWS"
        t += ["Anthropic-operated, AWS Marketplace billing; features typically same day"]
    elif n.must_stay_in_cloud == "gcp":
        surface = "Claude on Google Cloud"
        t += ["check the feature list for the managed variant you use"]
    elif n.must_stay_in_cloud == "azure":
        surface = "Claude in Microsoft Foundry"
        t += ["US Data Zone Standard deployments keep inference in the US (1.1x)"]
    else:
        surface = "Claude API"
        if n.inference_region == "us":
            t += ["inference_geo='us' adds 1.1x to token prices"]
    # 2. Runtime: who runs the loop, where tools must execute, compliance eligibility.
    managed_ok = surface in ("Claude API", "Claude Platform on AWS", "Claude on Google Cloud") and n.host_the_loop != "us"
    if n.hipaa_or_zdr and managed_ok and n.host_the_loop == "anthropic":
        runtime = "self-hosted Claude Managed Agents (talk to the account team)"
        t += ["you operate the whole service; the only Managed Agents option eligible for ZDR/HIPAA"]
    elif managed_ok and not n.hipaa_or_zdr and (n.long_running_sessions or n.host_the_loop == "anthropic"):
        runtime = "Claude Managed Agents" + (" with a self-hosted sandbox" if n.tools_on_our_network else ", cloud environment")
        t += ["beta; sessions and transcripts held by Anthropic until deleted"]
        if n.tools_on_our_network:
            t += ["you run the sandbox workers; conversation history and tool results still reach Anthropic"]
    elif n.long_running_sessions or n.tools_on_our_network:
        runtime = "self-hosted Agent SDK (or headless Claude Code) in your containers"
        t += ["you own session storage, isolation, scaling and max_turns"]
    else:
        runtime = "Messages API loop in your service"
        t += ["you write the loop, tools and state; maximum control"]
    if n.hipaa_or_zdr:
        t += ["needs a ZDR or HIPAA arrangement with Anthropic; use only features marked eligible"]
    if "self-hosted sandbox" in runtime and surface != "Claude API":
        t += [f"check self-hosted sandbox availability on {surface}"]
    return Choice(surface, runtime, t)


SCENARIOS = {
    "games studio: newest features, nothing to host": Needs(newest_features=True, host_the_loop="anthropic", long_running_sessions=True),
    "clinic software: HIPAA, short calls": Needs(hipaa_or_zdr=True),
    "EU retailer: inference must stay in the EU": Needs(inference_region="eu", long_running_sessions=True),
    "factory: tools on the plant network, AWS contract": Needs(must_stay_in_cloud="aws", long_running_sessions=True, tools_on_our_network=True),
}

if __name__ == "__main__":
    for name, needs in SCENARIOS.items():
        c = choose(needs)
        print(f"{name}\n  surface: {c.surface}\n  runtime: {c.runtime}")
        for x in c.tradeoffs:
            print(f"  - {x}")

Say what the choice costs

Skill 1.6The six trade-offs the guide asks you to justify.

  • Latency: global routing gives the most capacity; a regional endpoint gives up some of that for residency. Fast mode is only offered on some surfaces.
  • Feature availability: the Claude API and Claude Platform on AWS get features first; endpoints run by cloud providers lag and may lack server tools, Skills, Batches or Managed Agents.
  • Hosting: running the loop yourself means containers, scaling and someone on call; Managed Agents removes that, but it’s still in beta.
  • Session state: either in your own store (the Agent SDK’s session store, your database) or Anthropic’s (Managed Agents sessions are kept until you delete them).
  • Sandboxing: your own container isolation, Anthropic’s container for each session, or your own sandbox workers.
  • Data custody: who ends up holding which data. With a self-hosted sandbox, files stay with you, but the conversation history and tool results still reach Anthropic; on a cloud provider, that provider’s terms and logs apply.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A company needs data processed only in the EU and wants the newest Claude features. The Claude API offers US or global inference. What should the architect say?
  1. A. Use the Claude API with inference_geo set to eu
  2. B. Use a cloud provider’s EU regional endpoint, and state that some features will arrive later or not at all
  3. C. Ignore the residency requirement
  4. D. Use Managed Agents
Answer
B
Why
Hard constraints come first: EU-only processing rules out the Claude API’s options. The preference for the newest features then becomes a stated trade-off, not a requirement that overrides the constraint.
Question 2
Scenario
A team wants an agent that runs long background tasks with nothing to host, and has no ZDR or HIPAA requirement. Which runtime fits?
  1. A. A Messages API loop in their own service
  2. B. Claude Managed Agents
  3. C. The Agent SDK on their own servers
  4. D. Headless Claude Code on a laptop
Answer
B
Why
Managed Agents runs the loop and keeps session state for long-running work, with nothing for the team to host. It fits here because no ZDR or HIPAA requirement rules it out.
Question 3
Scenario
A design says “we use US-only inference, so Anthropic doesn’t keep our data”. What is wrong?
  1. A. Nothing
  2. B. Residency (where inference runs) and retention (how long data is kept) are separate settings; retention needs its own arrangement such as ZDR
  3. C. US inference costs less
  4. D. US inference isn’t available
Answer
B
Why
Inference geo decides where the model runs; it says nothing about how long data is kept. Zero data retention is a separate arrangement with its own scope.
Question 4
Scenario
A factory’s agent must run tools on the plant’s internal network, and the team can host containers. Which runtime keeps the tools inside the network?
  1. A. Managed Agents with Anthropic’s cloud environment
  2. B. The Agent SDK running in the factory’s own containers
  3. C. The Claude apps
  4. D. Batches
Answer
B
Why
Running the Agent SDK on your own machines keeps tool execution inside your network; you then own session storage, sandboxing and scaling. Anthropic’s cloud environment runs tools in its own containers.

Key takeaways

  • Two choices: the surface (which platform serves the model) and the runtime (who runs the agent loop and keeps its state).
  • The Claude API and Claude Platform on AWS get features first; Bedrock’s bedrock-runtime endpoint lacks the Files API, server tools, Skills, the MCP connector, Batches and Managed Agents.
  • Inference geo is where the model runs (global or us on the Claude API, 1.1 times the price for US); workspace geo is where data is stored (US only, fixed at creation); other regions mean a cloud provider’s regional profile. Residency isn’t retention.
  • Runtimes: your own Messages API loop (most control, most code), the Agent SDK or headless Claude Code on your machines (you own state, sandbox and scaling), or Managed Agents (Anthropic runs it; beta; not ZDR or HIPAA eligible unless fully self-hosted).
  • Decide by hard constraints, then who must run the loop, then preferences; a preference that conflicts with a constraint becomes a stated trade-off.
  • Justify the choice on latency, features, hosting, session state, sandboxing and who holds the data.
