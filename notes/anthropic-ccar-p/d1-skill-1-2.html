Overview

Skill 1.2

End-to-End Architecture Evaluation: "Evaluating whether a proposed end-to-end architecture (input, processing, output, feedback) satisfies stated scalability, maintainability, and access-control requirements, and identifying the component that fails first under a specified load or trust condition."

Exam items describe an architecture and a condition, such as a seasonal peak, a new tenant or untrusted input, and ask which component fails first or which requirement is unmet. The answer is usually one specific component, not "the model". Choosing the pattern is skill 1.3; relieving a performance constraint in depth is skill 3.3.

Sources: the Claude API rate limits documentation and the API key and workspace guidance, checked on 20 November 2026 and paraphrased. The pipeline and its capacities are my own; the capacity model is tested.

Running example. A freight forwarder processes customs documents: invoices and packing lists arrive by email, Claude (Sonnet 5.5) extracts and validates the fields against a tariff extract, results go into the ERP, flagged documents go to customs brokers, and broker corrections feed back into the prompts. Peak season triples the volume.

Four stages, three requirements

Skill 1.2A grid to walk any architecture through (my framing).

  • Input (email intake, file parsing, queues): scale means burst handling and back-pressure; access control means who can send content in, and whether that content is trusted.
  • Processing (Claude calls, tools, retrieval): scale means rate limits, latency and cost per item; access control means what each call can read and do.
  • Output (ERP writes, notifications): scale means the downstream system's capacity; access control means the credentials the writer holds and whether writes can be repeated safely.
  • Feedback (human review, corrections, evaluation): scale means reviewer capacity; maintainability means corrections reach prompts and tests through a controlled change, not ad hoc edits.

For each cell, ask: what is the stated requirement, what is the capacity or control, and what happens at the stated condition?

The model's limits

Skill 1.2What the Messages API actually caps.

  • Three rate limits per model: requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM), set by the organisation's usage tier. For Sonnet 5.5 they are 4,000 / 2,000,000 / 400,000 on the Start tier and 10,000 / 5,000,000 / 1,000,000 on Build. Exceeding any one returns a 429 that names it.
  • Token bucket: capacity refills continuously, so short bursts can trip a limit even when the per-minute average is fine.
  • Cache-aware ITPM: only uncached input counts. Tokens read from the prompt cache don't count toward ITPM, so caching a large, repeated prefix raises effective throughput.
  • Ramp limits: a sharp increase in usage can return 429 below the rate limits; grow by about a step per minute, and start bulk jobs slowly. The Message Batches API isn't subject to ramp limits and has its own limits, including a cap on batch requests in the processing queue.
  • Spend caps: each tier has a monthly cap; reaching it returns a 429 with no retry-after, and retries keep failing until the month resets or the tier rises.
  • Workspaces: you can give each workspace lower limits so one workload can't starve another; organisation limits always apply.

Finding the first to fail under load

Skill 1.2Utilisation of every component at the stated load.

first_to_fail.py (first_to_fail.py) 
"""Which component of the customs-document pipeline fails first under a given load?

Each component has a capacity per minute; demand is derived from the documents arriving per minute.
Utilisation above 100% means that component is the binding constraint. Limits for the model are the
Messages API's per-model RPM, ITPM (uncached input only) and OTPM for the organisation's tier."""
from dataclasses import dataclass


@dataclass
class Load:
    docs_per_min: float
    calls_per_doc: int = 2               # extract, then validate
    prompt_tokens: int = 12_000          # instructions + tariff extract, identical on every call
    doc_tokens: int = 6_000              # the document itself, different every time
    output_tokens: int = 900
    cache_hit_rate: float = 0.0          # share of prompt_tokens read from the cache


@dataclass
class Limits:                            # Sonnet 5.5, Start tier (rate limits page, Nov 2026)
    rpm: int = 4_000
    itpm: int = 2_000_000
    otpm: int = 400_000
    erp_writes_per_min: int = 400        # the ERP's import API
    reviewers: int = 14                  # customs brokers checking flagged documents
    review_minutes: float = 4.0
    flag_rate: float = 0.05              # share of documents sent to a broker


def utilisation(load: Load, lim: Limits) -> dict:
    calls = load.docs_per_min * load.calls_per_doc
    uncached = load.prompt_tokens * (1 - load.cache_hit_rate) + load.doc_tokens
    return {
        "model RPM": calls / lim.rpm,
        "model ITPM": calls * uncached / lim.itpm,              # cache reads don't count toward ITPM
        "model OTPM": calls * load.output_tokens / lim.otpm,
        "ERP import": load.docs_per_min / lim.erp_writes_per_min,
        "broker review": load.docs_per_min * lim.flag_rate * lim.review_minutes / lim.reviewers,
    }


def first_to_fail(load: Load, lim: Limits) -> tuple[str, float]:
    name, u = max(utilisation(load, lim).items(), key=lambda kv: kv[1])
    return name, round(u, 2)


if __name__ == "__main__":
    lim = Limits()
    for label, load in [("normal: 20 docs/min", Load(docs_per_min=20)),
                        ("peak x3, no caching", Load(docs_per_min=60)),
                        ("peak x3, 90% cache hits", Load(docs_per_min=60, cache_hit_rate=0.9))]:
        u = utilisation(load, lim)
        print(f"{label:24} " + "  ".join(f"{k} {v:.0%}" for k, v in u.items()))
        print(f"{'':24} highest: {first_to_fail(load, lim)}")
run_output.txt (Output) 
normal: 20 docs/min      model RPM 1%  model ITPM 36%  model OTPM 9%  ERP import 5%  broker review 29%
                         highest: ('model ITPM', 0.36)
peak x3, no caching      model RPM 3%  model ITPM 108%  model OTPM 27%  ERP import 15%  broker review 86%
                         highest: ('model ITPM', 1.08)
peak x3, 90% cache hits  model RPM 3%  model ITPM 43%  model OTPM 27%  ERP import 15%  broker review 86%
                         highest: ('broker review', 0.86)
  • At peak without caching, input tokens per minute hit 108%: each call sends a 12,000-token instruction and tariff prefix plus a 6,000-token document. RPM is only 3%, so "add more workers" or "request more RPM" doesn't help.
  • Caching the prefix takes ITPM to 43%, because cache reads don't count. The model is no longer the constraint.
  • The broker queue is next at 86%: a human feedback stage, not a technical one, and the next one to fail if volume grows further.

"Use a more capable model" or "add retries" are common wrong answers to a throughput failure. A bigger model doesn't change the limit that binds, and retries add load to a component already over capacity.

After the first bottleneck

Skill 1.2Each fix moves the constraint somewhere else.

  • Model limits: cache stable prefixes, trim what's sent, move non-urgent work to Message Batches (half price, within 24 hours), raise the tier, or isolate workloads in workspaces with their own limits.
  • Peak arrival: a queue between intake and processing smooths bursts and respects ramp limits, at the cost of latency.
  • Downstream writes: batch ERP writes and make them idempotent, so a retried write doesn't duplicate a record.
  • Human review: tune the flag rate with evaluation data, add reviewers for the season, or prioritise the queue by risk.

Failing first under a trust condition

Skill 1.2When the condition is untrusted input or a new party, not load.

  • Untrusted documents: inbound email is attacker-controlled. If the extraction step also holds a tool that writes to the ERP, an instruction hidden in an invoice can reach it. The component that fails first is the one combining untrusted input with write access; split reading from writing and validate outputs before the write.
  • A second client or business unit: one shared API key, one retrieval index without per-tenant filtering, or one reviewer queue with everyone's documents fails access control first. Separate workspaces with workspace-scoped keys, tenant filters on retrieval, and per-tenant queues.
  • Keys in the wrong place: a key in a browser or desktop client can be read by anyone; calls belong in the back end, with IP allowlisting limiting where a leaked key works.
  • Broad credentials: an output connector with admin rights turns any processing error into a data-integrity incident; give it only the operations it needs.

Maintainability

Skill 1.2Signs an architecture won't stay correct as it changes.

  • Prompts and tariff data hard-coded in several services, so one change needs several releases.
  • Corrections applied directly to prompts without an evaluation set, so a fix for one document type breaks another unnoticed.
  • No per-stage metrics: without throughput, error and queue-length figures for each stage, the first-to-fail component is found in production.
  • Model choice baked in: pin model IDs in configuration with a tested upgrade path.

Key takeaways

  • Walk input, processing, output and feedback against each stated requirement: scalability, maintainability, access control.
  • The Messages API limits RPM, ITPM and OTPM per model by tier, with token-bucket refills, ramp limits on sharp increases, and spend caps that return a 429 without retry-after.
  • Cache reads don't count toward ITPM, so caching a large repeated prefix often removes an input-token bottleneck; Batches suit non-urgent work and skip ramp limits.
  • Compute utilisation for every component at the stated load; the highest one fails first, and fixing it moves the constraint, often to a human review queue.
  • Under a trust condition, the first to fail is the component that mixes untrusted input with write access, or shares keys, indexes or queues across parties.
