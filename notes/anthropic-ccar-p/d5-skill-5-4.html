5.4: Human-in-the-Loop Checkpoints

Putting a person in front of the actions that can't be undone or that carry real risk, and only those, with gates that park the request until someone decides rather than freezing the whole agent, so the routine work keeps flowing.

Overview

Skill 5.4

Human-in-the-Loop Checkpoints: "Analyzing where human-in-the-loop checkpoints must sit in an agentic workflow containing irreversible or high-stakes actions, and specifying gates that pause execution without stalling acceptable-risk paths."

Exam items describe a workflow with some dangerous actions and ask where approvals go and how, often against a design that gates too much or too little. The guide's own sample question in this area isn't reproduced here. Deciding what a process delegates to Claude at all is skill 1.1; guardrails without a person are skill 5.1.

Sources: the Agent SDK hooks and permissions documentation, checked on 19 and 20 November 2026 and paraphrased. The agent, risk classes and code are my own; the code is tested.

Running example. A software company's operations agent diagnoses incidents and acts on cloud infrastructure: reads logs and metrics, restarts and scales services, and can (with the right tools) delete volumes, change access policies and deploy.

Where checkpoints must sit

Skill 5.4Immediately before the effect, for the actions that need it.

  • Irreversible: deleting data, dropping a database, rotating root keys. A person approves every time, in any environment.
  • High blast radius: access-policy changes, production deploys, changes outside a bounded range. A person approves.
  • Bounded and reversible: scaling production up to double the current size, restarting a staging service. No gate; monitor and allow rollback.
  • Read-only: logs, metrics, descriptions. Never gated.
  • At the effect, not the plan: the gate sits on the tool call that changes the world, so the agent can investigate and prepare freely, and the approver sees the exact action and arguments.

Gates that pause, not stall

Skill 5.4The Agent SDK mechanisms.

  • A PreToolUse hook can return allow (an empty result), deny, ask or defer for each tool call; when several hooks answer, the most restrictive wins (deny, then defer, then ask, then allow).
  • Defer ends the turn with stop reason tool_deferred, so the call can be resumed later. Nothing sits waiting on an open process while the approver is at lunch; the application records the request and resumes the session when a decision arrives.
  • Ask or a can_use_tool callback waits for an answer in the moment, which suits an interactive user beside the agent, not an overnight queue.
  • Deny with a reason tells the agent why, so it can take another route or report back.

Gating a cloud-operations agent

Skill 5.4Classify, then allow or defer.

ops_gates.py (ops_gates.py)Optional 
"""Human checkpoints for a cloud-operations agent, as an Agent SDK PreToolUse hook.

Most actions are routine and run straight away. Irreversible or high-blast-radius ones are deferred:
the hook returns "defer", the turn ends with stop_reason "tool_deferred", a request goes to the
on-call engineer, and the session is resumed when they decide. Nothing waits on an open process."""
import json
import uuid

PENDING = {}                                     # in production: a table the approval UI reads and writes


def classify(tool: str, args: dict) -> str:
    env = args.get("env", "staging")
    if tool in ("describe", "get_logs", "get_metrics"):
        return "auto"                            # read-only
    if tool in ("restart_service", "scale_service") and env == "staging":
        return "auto"
    if tool == "scale_service" and env == "prod" and args.get("replicas", 0) <= 2 * args.get("current", 1):
        return "auto"                            # bounded and reversible: at most double, scale back any time
    if tool in ("delete_volume", "drop_database", "change_iam_policy", "rotate_root_keys"):
        return "human"                           # irreversible or high blast radius
    if env == "prod":
        return "human"                           # anything else in production
    return "auto"


async def gate(input_data, tool_use_id, context):
    tool = input_data["tool_name"].split("__")[-1]
    args = input_data["tool_input"]
    if classify(tool, args) == "auto":
        return {}
    ticket = str(uuid.uuid4())[:8]
    PENDING[ticket] = {"tool": tool, "args": args, "tool_use_id": tool_use_id, "status": "waiting"}
    return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "defer",
            "permissionDecisionReason": f"Sent to on-call for approval (ticket {ticket}). Continue with other work."}}


def decide(ticket: str, approved: bool, who: str) -> dict:
    """Called by the approval UI; the application then resumes the session with the outcome."""
    PENDING[ticket].update(status="approved" if approved else "rejected", by=who)
    return PENDING[ticket]
  • Routine paths never wait: reads, staging restarts and bounded production scaling run straight away. The test checks that scaling from 4 to 6 replicas isn't gated, while 4 to 20 is.
  • Irreversible means everywhere: dropping a database is deferred even in staging.
  • A safe default: any production action not explicitly classed as routine goes to a person.
  • The agent keeps working: the deferral message tells it to carry on with other work while the request waits.

"Require approval for every production tool call" stalls the routine work, builds a queue and trains approvers to click through. "Let the agent ask the user in chat" leaves the gate in the model's hands. Gate the specific risky actions, in code.

Keeping approvals meaningful

Skill 5.4So the person actually checks.

  • Show the exact action: tool, arguments, environment, and the agent's reason, not a summary.
  • Route to someone accountable for that system, with the authority to say no.
  • Time out to "no": an unanswered request expires as rejected, never as approved.
  • Watch the rates: very high approval rates on a gate suggest it could be narrowed; very fast approvals suggest nobody is reading.
  • Log decisions with who decided, for the audit trail.

Key takeaways

  • Put checkpoints immediately before irreversible or high-blast-radius actions, in every environment; leave read-only and bounded, reversible actions ungated.
  • Gate the effect, not the investigation, and show the approver the exact action.
  • Agent SDK hooks return allow, deny, ask or defer; defer ends the turn with tool_deferred so the call resumes after approval without holding a process open.
  • Use a safe default (unclassified production actions go to a person) and time out to rejection.
  • Too many gates stall work and breed rubber-stamping; too few let the agent act alone on what matters.
