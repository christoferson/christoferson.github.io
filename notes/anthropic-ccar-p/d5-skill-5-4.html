5.4: Human-in-the-Loop Checkpoints

Overview

Skill 5.4

Human-in-the-Loop Checkpoints: "Analyzing where human-in-the-loop checkpoints must sit in an agentic workflow containing irreversible or high-stakes actions, and specifying gates that pause execution without stalling acceptable-risk paths."

Exam items describe a workflow with some dangerous actions and ask where approvals go and how, often against a design that gates too much or too little. Deciding what a process delegates to Claude at all is skill 1.1; guardrails without a person are skill 5.1.

Put a person in the loop exactly where an action can’t be undone

Skill 5.4What this skill asks you to place.

Questions on this skill describe an agent workflow that includes some dangerous actions, and ask where approvals belong and how they should work. The designs on offer often gate too much (everything waits for a person) or too little (dangerous actions run alone). The aim is gates that stop the risky actions and let everything else run.

Take a software company’s operations agent. It diagnoses incidents and acts on cloud infrastructure: it reads logs and metrics, restarts and scales services, and with the right tools could also delete storage volumes, change access policies and deploy code.

Actions that can’t be undone: a person approves every time, everywhere

Skill 5.4Deleting data, dropping a database, rotating root keys.

Once these happen they can’t be reversed, so a person approves each one, in every environment. Dropping a database waits for approval even in staging.

Actions with a wide reach: a person approves

Skill 5.4Access-policy changes, production deploys, changes outside a normal range.

These can be reversed, but a mistake affects many people or systems before anyone notices. A person approves them.

Bounded, reversible actions and reads: no gate

Skill 5.4Let these run, and monitor them.

Scaling a production service up to double its current size, or restarting a staging service, is limited in effect and easy to undo: no gate, but monitoring and a way to roll back. Reading logs, metrics and descriptions is never gated. In the agent’s rules, scaling from 4 to 6 replicas runs straight away, while scaling from 4 to 20 waits for a person.

A safe default: any production action not explicitly listed as routine goes to a person.

Gate the action itself, not the investigation before it

Skill 5.4Where in the workflow the approval sits.

Put the gate on the tool call that changes something. The agent can then investigate and prepare freely, and the approver sees the exact action and its arguments, not a plan that might change before it’s carried out.

Pause the action without stalling the agent

Skill 5.4The Agent SDK mechanisms for gates.

  • Four answers per tool call. A PreToolUse hook can return allow (an empty result), deny, ask or defer. When several hooks answer, the most restrictive wins: deny, then defer, then ask, then allow.
  • Defer for approvals that take time. Defer ends the turn with the stop reason tool_deferred, so the call can be resumed later. Nothing sits waiting on an open process while the approver is at lunch: your application records the request and resumes the session when a decision arrives.
  • Ask for someone sitting beside the agent. Ask, or a can_use_tool callback, waits for an answer in the moment, which suits an interactive user, not an overnight queue.
  • Deny with a reason, so the agent knows why and can take another route or report back.
  • Keep the agent working. The deferral message tells it to carry on with other work while the request waits.

The code below classifies each tool call and allows or defers it; its test checks that routine calls never wait and that irreversible ones always do:

ops_gates.py (ops_gates.py)Optional 
"""Human checkpoints for a cloud-operations agent, as an Agent SDK PreToolUse hook.

Most actions are routine and run straight away. Irreversible or high-blast-radius ones are deferred:
the hook returns "defer", the turn ends with stop_reason "tool_deferred", a request goes to the
on-call engineer, and the session is resumed when they decide. Nothing waits on an open process."""
import json
import uuid

PENDING = {}                                     # in production: a table the approval UI reads and writes


def classify(tool: str, args: dict) -> str:
    env = args.get("env", "staging")
    if tool in ("describe", "get_logs", "get_metrics"):
        return "auto"                            # read-only
    if tool in ("restart_service", "scale_service") and env == "staging":
        return "auto"
    if tool == "scale_service" and env == "prod" and args.get("replicas", 0) <= 2 * args.get("current", 1):
        return "auto"                            # bounded and reversible: at most double, scale back any time
    if tool in ("delete_volume", "drop_database", "change_iam_policy", "rotate_root_keys"):
        return "human"                           # irreversible or high blast radius
    if env == "prod":
        return "human"                           # anything else in production
    return "auto"


async def gate(input_data, tool_use_id, context):
    tool = input_data["tool_name"].split("__")[-1]
    args = input_data["tool_input"]
    if classify(tool, args) == "auto":
        return {}
    ticket = str(uuid.uuid4())[:8]
    PENDING[ticket] = {"tool": tool, "args": args, "tool_use_id": tool_use_id, "status": "waiting"}
    return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "defer",
            "permissionDecisionReason": f"Sent to on-call for approval (ticket {ticket}). Continue with other work."}}


def decide(ticket: str, approved: bool, who: str) -> dict:
    """Called by the approval UI; the application then resumes the session with the outcome."""
    PENDING[ticket].update(status="approved" if approved else "rejected", by=who)
    return PENDING[ticket]

“Require approval for every production tool call” stalls routine work, builds a queue and trains approvers to click through. “Let the agent ask the user in chat” leaves the gate in the model’s hands. Gate the specific risky actions, in code.

Make each approval mean something

Skill 5.4So the person actually checks.

  • Show the exact action: the tool, its arguments, the environment and the agent’s reason, not a summary.
  • Send it to someone accountable for that system, with the authority to say no.
  • Expire unanswered requests as “no”, never as approved.
  • Watch the rates. A gate approved almost every time could probably be narrowed; approvals given within seconds suggest nobody is reading.
  • Log each decision with who made it, for the audit trail.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
An operations agent can read logs, restart staging services, scale production up to double, and delete storage volumes. Which actions should wait for a person?
  1. A. All of them in production
  2. B. Only deleting storage volumes, in every environment, plus any production action not listed as routine
  3. C. None; monitoring is enough
  4. D. Only reading logs
Answer
B
Why
Irreversible actions need approval everywhere; bounded, reversible ones and reads should run, with monitoring. A safe default sends unlisted production actions to a person. Gating everything stalls the routine work.
Question 2
Scenario
An approval for a risky action may take hours, and the team doesn’t want a process held open waiting. Which Agent SDK mechanism fits?
  1. A. A PreToolUse hook that returns defer, so the turn ends with tool_deferred and resumes after approval
  2. B. A system-prompt instruction to wait
  3. C. A can_use_tool callback that waits for an answer
  4. D. Deny the call every time
Answer
A
Why
Defer ends the turn so the request can be recorded and the session resumed when the decision arrives. A callback waiting in the moment suits an interactive user; a prompt instruction isn’t a gate.
Question 3
Scenario
Approvers on one gate approve 99.8% of requests within five seconds. What does that suggest?
  1. A. The gate is working perfectly
  2. B. Nobody is really reading, and the gate is probably too broad
  3. C. The agent is never wrong
  4. D. More gates are needed
Answer
B
Why
Near-total, very fast approval is the sign of rubber-stamping. Narrow the gate to the truly risky actions and show the exact action, so approvals mean something.
Question 4
Scenario
What should happen to an approval request nobody answers before it expires?
  1. A. It is approved, so work continues
  2. B. It is rejected
  3. C. It is retried every minute forever
  4. D. The agent decides
Answer
B
Why
An unanswered request must expire as a no; expiring as approved would turn the gate into a delay rather than a control.

Key takeaways

  • Put approvals immediately before actions that can’t be undone or that reach widely, in every environment; leave reads and bounded, reversible actions ungated.
  • Gate the action itself, not the investigation, and show the approver the exact action and arguments.
  • Agent SDK hooks return allow, deny, ask or defer; defer ends the turn with tool_deferred, so the call resumes after approval without holding a process open.
  • Use a safe default (unlisted production actions go to a person), and expire unanswered requests as “no”.
  • Too many gates stall work and breed rubber-stamping; too few let the agent act alone on what matters.
