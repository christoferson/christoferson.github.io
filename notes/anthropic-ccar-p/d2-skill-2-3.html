2.3: Prompting Technique Selection

Each prompting technique fixes a particular kind of failure. The skill is reading the failure, applying the one technique that addresses it, and not paying for techniques the task doesn't need.

Overview

Skill 2.3

Prompting Technique Selection: "Applying the prompting technique (zero-shot, few-shot, prompted reasoning versus native thinking, structured output) that addresses an observed failure pattern for a task of stated complexity without unnecessary token cost."

Exam items describe a task, its complexity and a failure pattern, and ask which technique to add. Distractors usually add a technique that works but doesn't address the failure, or that costs far more than needed. Diagnosing a system prompt's gaps is skill 2.2; effort over a long session is skill 2.6.

Sources: Anthropic's prompting best practices and the structured outputs documentation, checked on 20 November 2026 and paraphrased. The task and code are my own; the code is tested against a mocked API, and its token counts are estimates.

Running example. An appliance maker triages 100,000 warranty claims a month with Sonnet 5.5, labelling each as defect, accidental damage, wear, installation or not covered, and sometimes computing a pro-rated refund.

What each technique fixes

Skill 2.3One failure pattern each.

  • Zero-shot: clear instructions only. The default, and enough when the task is well defined and evaluations pass. Adding more costs tokens for nothing.
  • Few-shot (multishot): for format, tone or boundary cases the instructions don't pin down. Anthropic calls examples one of the most reliable ways to steer output; use 3–5 that are relevant, diverse (including edge cases, so no unintended pattern is learned) and wrapped in <example> tags. A single example tends to be copied too literally.
  • Native thinking (more effort): for multi-step reasoning errors: calculations, multi-constraint decisions, long chains of logic. Raise effort rather than writing a step-by-step plan; Anthropic notes that a general instruction such as "think thoroughly" often beats hand-written steps.
  • Structured output: for shape failures: malformed JSON, missing fields, labels outside the allowed set. A JSON schema (or a tool with an enum) guarantees the shape, not the correctness of the content.

Prompted reasoning or native thinking

Skill 2.3The distinction the guide names, by model.

  • Always on: Fable 5.2, Opus 5.5 and the Mythos models think regardless of settings.
  • On by default: Opus 5, Sonnet 5.5, Sonnet 5 and Haiku 5.5 think when the thinking parameter is omitted. Opus 5 and Haiku 5.5 can turn it off only at effort high or below; Sonnet 5.5's lowest setting is between_tools.
  • Off when omitted: Opus 4.6 to 4.8 and Sonnet 4.6.
  • Prompted reasoning is the fallback: when thinking is off, ask Claude to think through the problem first and put the final answer in <answer> tags. On Fable 5.2, Fable 5.1, Fable 5, Opus 5.5, Opus 5 and Sonnet 5.5, Anthropic says to rely on thinking instead, at lower effort if cost matters: a prompt asking for written-out reasoning, for example in <thinking> tags, might be declined.
  • Examples still help with thinking: worked examples shape how Claude approaches similar problems in its own thinking.
  • Cost: thinking tokens are billed as output, so more effort is the most expensive fix per call; keep it for failures that need reasoning.

Failure to technique, with cost

Skill 2.3Each fix adds only what its failure needs.

technique_for_failure.py (technique_for_failure.py) 
"""Warranty-claim triage at an appliance maker: match each observed failure to the cheapest technique that fixes it.

Baseline is a zero-shot request on Sonnet 5.5. Each fix adds only what its failure needs, and the
extra cost is counted per 100,000 claims a month (Sonnet 5.5: $2 input, $10 output per million tokens)."""
import copy

LABELS = ["defect", "accidental_damage", "wear", "installation", "not_covered"]

BASE = {
    "model": "claude-sonnet-5-5",
    "max_tokens": 2048,
    "output_config": {"effort": "low"},
    "system": "Classify the warranty claim into one label and give a one-line reason.",
    "messages": [{"role": "user", "content": "<claim>{claim}</claim>"}],
}

EXAMPLES = """<examples>
<example><claim>Door seal split after 3 weeks of normal use.</claim><label>defect</label></example>
<example><claim>Dropped the kettle; base cracked.</claim><label>accidental_damage</label></example>
<example><claim>Water on the floor; the hose was never tightened by our fitter.</claim><label>installation</label></example>
<example><claim>Filter clogged after 4 years.</claim><label>wear</label></example>
</examples>"""                                  # ~180 tokens; diverse, and covers the confusable water cases


def fix(failure: str) -> tuple[dict, int, int]:
    """Return (request, extra input tokens, extra output tokens) for one observed failure."""
    r = copy.deepcopy(BASE)
    if failure == "labels outside the allowed set or malformed JSON":
        r["output_config"]["format"] = {"type": "json_schema", "schema": {
            "type": "object", "additionalProperties": False, "required": ["label", "reason"],
            "properties": {"label": {"type": "string", "enum": LABELS}, "reason": {"type": "string"}}}}
        return r, 60, 0                        # schema is small; guarantees shape, not correctness
    if failure == "confusable cases mislabelled (leak: defect or installation?)":
        r["system"] += "\n" + EXAMPLES          # few-shot: steers the boundary cases
        return r, 180, 0                        # too short to cache on its own; worth it if it fixes the cases
    if failure == "wrong pro-rated refund on multi-year contracts":
        r["output_config"]["effort"] = "medium"   # native thinking, more effort; no 'show your reasoning' text
        return r, 0, 400                        # thinking tokens are billed as output
    if failure == "none: zero-shot accuracy meets the target":
        return r, 0, 0
    raise ValueError(failure)


def monthly_extra(extra_in: int, extra_out: int, claims: int = 100_000) -> float:
    return round(claims * (extra_in * 2.00 + extra_out * 10.00) / 1e6, 2)


if __name__ == "__main__":
    for f in ["none: zero-shot accuracy meets the target",
              "labels outside the allowed set or malformed JSON",
              "confusable cases mislabelled (leak: defect or installation?)",
              "wrong pro-rated refund on multi-year contracts"]:
        req, xi, xo = fix(f)
        print(f"{f}\n  -> effort={req['output_config']['effort']}, schema={'format' in req['output_config']}, "
              f"examples={'<examples>' in req['system']}; extra ${monthly_extra(xi, xo)}/month")
run_output.txt (Output) 
none: zero-shot accuracy meets the target
  -> effort=low, schema=False, examples=False; extra $0.0/month
labels outside the allowed set or malformed JSON
  -> effort=low, schema=True, examples=False; extra $12.0/month
confusable cases mislabelled (leak: defect or installation?)
  -> effort=low, schema=False, examples=True; extra $36.0/month
wrong pro-rated refund on multi-year contracts
  -> effort=medium, schema=False, examples=False; extra $400.0/month
  • Shape failures: a schema with an enum of labels, about $12 a month extra here; no examples or extra effort needed.
  • Boundary confusion (a leak: defect or installation?): four diverse examples covering the confusable cases, about $36 a month.
  • Calculation errors: effort from low to medium so native thinking works the arithmetic, about $400 a month in extra output tokens, and no request to "show your reasoning".
  • Nothing failing: stay zero-shot.

Common mismatches

Skill 2.3Techniques that don't address the failure in front of you.

  • More effort for malformed JSON: thinking doesn't guarantee shape; structured output does.
  • A schema for wrong labels: the schema keeps labels in the set but doesn't choose the right one; that needs examples or clearer definitions.
  • "Think step by step in <thinking> tags" on Opus 5.5: may be declined, and duplicates what native thinking already does.
  • Twenty examples for a simple task: pays for tokens on every call; 3–5 diverse ones usually suffice.
  • One example: copied too literally, so outputs mimic its length and wording.

"Add chain-of-thought, examples and a schema to be safe" fixes the failure at several times the necessary cost. The guide's phrase is "without unnecessary token cost": one technique per failure.

Key takeaways

  • Zero-shot until evaluations fail; few-shot (3–5 diverse examples) for format and boundary cases; native thinking with more effort for reasoning errors; structured output for shape errors.
  • Thinking is always on for Fable 5.2 and Opus 5.5, on by default for Sonnet 5.5 and Haiku 5.5, and off when omitted on Opus 4.6–4.8 and Sonnet 4.6.
  • Prompted reasoning with <answer> tags is the fallback when thinking is off; on current models that think, rely on thinking, since a request for written-out reasoning may be declined.
  • A schema guarantees shape, not correctness; examples fix judgement at boundaries; effort fixes reasoning, at output-token cost.
  • Apply one technique per failure, and count its cost at the stated call volume.
