2.3: Prompting Technique Selection

Each prompting technique fixes a particular kind of failure. The skill is reading the failure, applying the one technique that addresses it, and not paying for techniques the task doesn't need.

Overview

Skill 2.3

Prompting Technique Selection: "Applying the prompting technique (zero-shot, few-shot, prompted reasoning versus native thinking, structured output) that addresses an observed failure pattern for a task of stated complexity without unnecessary token cost."

Exam items describe a task, its complexity and a failure pattern, and ask which technique to add. Distractors usually add a technique that works but doesn't address the failure, or that costs far more than needed. Diagnosing a system prompt's gaps is skill 2.2; effort over a long session is skill 2.6.

Add only the technique that fixes the failure you see

Skill 2.3What this skill asks you to choose.

Questions on this skill describe a task, how complex it is, and how its output goes wrong, then ask which prompting technique to add. Each technique fixes one kind of failure, and each adds tokens to every call. The wrong answers either add a technique that helps in general but doesn’t touch this failure, or stack several techniques “to be safe” at many times the cost.

The next four sections take the techniques one at a time: what each fixes, how to use it, and what it costs.

Start with clear instructions alone

Skill 2.3Zero-shot: the default.

A zero-shot prompt gives clear instructions and no examples. It’s the right choice when the task is well defined and the evaluation already passes. Adding anything else then costs tokens on every call and buys nothing, so when nothing is failing, the answer is to change nothing.

Show a few examples when instructions can’t pin the answer down

Skill 2.3Few-shot: for format, tone and borderline cases.

What it fixes. Output that is in the wrong style, or wrong on the borderline cases that are hard to describe in words: is a leaking washing machine a manufacturing defect or a bad installation? Anthropic calls examples one of the most reliable ways to steer output.

How to use it. Give three to five examples. Make them relevant to the real inputs and varied, including the edge cases, so the model doesn’t pick up a pattern you didn’t intend. Wrap each in <example> tags so it isn’t mistaken for an instruction or for the real input. A single example tends to be copied too closely, so outputs mimic its length and wording.

What it costs. The examples are sent with every call, so keep them few and short.

Use more thinking for reasoning errors, not a written-out plan

Skill 2.3Native thinking, prompted reasoning, and which models do which.

What it fixes. Mistakes in work that takes several steps: a calculation, a decision with several conditions, a long chain of logic.

How to use it. Current models can think before they answer (native thinking), and the effort setting controls how much. Raise the effort rather than writing a step-by-step plan into the prompt; Anthropic notes that a general instruction such as “think thoroughly” often works better than hand-written steps. Worked examples still help: they shape how Claude approaches similar problems in its own thinking.

Which models think.

  • Always: Fable 5.2, Opus 5.5 and the Mythos models think whatever the settings.
  • By default: Opus 5, Sonnet 5.5, Sonnet 5 and Haiku 5.5 think when the thinking parameter is left out. Opus 5 and Haiku 5.5 can turn it off only at effort high or below; Sonnet 5.5’s lowest setting is between_tools.
  • Only when turned on: Opus 4.6 to 4.8 and Sonnet 4.6.

Prompted reasoning is the fallback. On a model with thinking off, ask Claude to work through the problem first and put its final answer in <answer> tags. On models that think (Fable 5.2, 5.1 and 5, Opus 5.5 and 5, Sonnet 5.5), Anthropic says to rely on thinking instead, at a lower effort if cost matters: a prompt asking for the reasoning to be written out, for example in <thinking> tags, may be declined.

What it costs. Thinking tokens are billed as output tokens, so more effort is the most expensive fix per call. Keep it for failures that really need reasoning.

Use structured output for shape errors

Skill 2.3A schema guarantees the shape, not the content.

What it fixes. Output that a program can’t use: malformed JSON, missing fields, a label that isn’t one of the allowed values.

How to use it. Give a JSON schema, or a tool whose input lists the allowed labels as an enum. The response is then guaranteed to match that shape.

What it doesn’t fix. Whether the content is right. A schema keeps every label inside the allowed set, but it can’t make the model choose the correct one; that takes examples or clearer definitions.

Worked example: four failures in warranty-claim triage

Skill 2.3Each failure gets only the fix it needs, with its monthly cost.

An appliance maker uses Sonnet 5.5 to sort 100,000 warranty claims a month into five labels (defect, accidental damage, wear, installation, not covered) and sometimes to work out a pro-rated refund. Four situations, and the right response to each:

  • Nothing is failing: zero-shot accuracy meets the target, so stay zero-shot. Extra cost: none.
  • Labels outside the allowed set, or broken JSON: add a schema with the five labels as an enum. No examples or extra effort are needed. Extra cost: about $12 a month.
  • Confusable cases mislabelled (a leak: defect or installation?): add four varied examples that cover exactly those cases. Extra cost: about $36 a month.
  • Wrong pro-rated refunds on multi-year contracts: raise the effort from low to medium so native thinking works through the arithmetic, and don’t ask for the reasoning to be written out. Extra cost: about $400 a month in output tokens.

The code below maps each failure to its technique and estimates the extra monthly cost:

technique_for_failure.py (technique_for_failure.py)Optional 
"""Warranty-claim triage at an appliance maker: match each observed failure to the cheapest technique that fixes it.

Baseline is a zero-shot request on Sonnet 5.5. Each fix adds only what its failure needs, and the
extra cost is counted per 100,000 claims a month (Sonnet 5.5: $2 input, $10 output per million tokens)."""
import copy

LABELS = ["defect", "accidental_damage", "wear", "installation", "not_covered"]

BASE = {
    "model": "claude-sonnet-5-5",
    "max_tokens": 2048,
    "output_config": {"effort": "low"},
    "system": "Classify the warranty claim into one label and give a one-line reason.",
    "messages": [{"role": "user", "content": "<claim>{claim}</claim>"}],
}

EXAMPLES = """<examples>
<example><claim>Door seal split after 3 weeks of normal use.</claim><label>defect</label></example>
<example><claim>Dropped the kettle; base cracked.</claim><label>accidental_damage</label></example>
<example><claim>Water on the floor; the hose was never tightened by our fitter.</claim><label>installation</label></example>
<example><claim>Filter clogged after 4 years.</claim><label>wear</label></example>
</examples>"""                                  # ~180 tokens; diverse, and covers the confusable water cases


def fix(failure: str) -> tuple[dict, int, int]:
    """Return (request, extra input tokens, extra output tokens) for one observed failure."""
    r = copy.deepcopy(BASE)
    if failure == "labels outside the allowed set or malformed JSON":
        r["output_config"]["format"] = {"type": "json_schema", "schema": {
            "type": "object", "additionalProperties": False, "required": ["label", "reason"],
            "properties": {"label": {"type": "string", "enum": LABELS}, "reason": {"type": "string"}}}}
        return r, 60, 0                        # schema is small; guarantees shape, not correctness
    if failure == "confusable cases mislabelled (leak: defect or installation?)":
        r["system"] += "\n" + EXAMPLES          # few-shot: steers the boundary cases
        return r, 180, 0                        # too short to cache on its own; worth it if it fixes the cases
    if failure == "wrong pro-rated refund on multi-year contracts":
        r["output_config"]["effort"] = "medium"   # native thinking, more effort; no 'show your reasoning' text
        return r, 0, 400                        # thinking tokens are billed as output
    if failure == "none: zero-shot accuracy meets the target":
        return r, 0, 0
    raise ValueError(failure)


def monthly_extra(extra_in: int, extra_out: int, claims: int = 100_000) -> float:
    return round(claims * (extra_in * 2.00 + extra_out * 10.00) / 1e6, 2)


if __name__ == "__main__":
    for f in ["none: zero-shot accuracy meets the target",
              "labels outside the allowed set or malformed JSON",
              "confusable cases mislabelled (leak: defect or installation?)",
              "wrong pro-rated refund on multi-year contracts"]:
        req, xi, xo = fix(f)
        print(f"{f}\n  -> effort={req['output_config']['effort']}, schema={'format' in req['output_config']}, "
              f"examples={'<examples>' in req['system']}; extra ${monthly_extra(xi, xo)}/month")

  -> effort=low, schema=False, examples=False; extra $0.0/month
labels outside the allowed set or malformed JSON
  -> effort=low, schema=True, examples=False; extra $12.0/month
confusable cases mislabelled (leak: defect or installation?)
  -> effort=low, schema=False, examples=True; extra $36.0/month

  -> effort=medium, schema=False, examples=False; extra $400.0/month

Mismatches to avoid

Skill 2.3Techniques that don’t address the failure in front of you.

  • More effort for broken JSON. Thinking harder doesn’t guarantee the shape; structured output does.
  • A schema for wrong labels. The schema keeps labels in the allowed set but doesn’t choose the right one; that needs examples or clearer definitions.
  • “Think step by step in <thinking> tags” on Opus 5.5. It may be declined, and it repeats what native thinking already does.
  • Twenty examples for a simple task. Every call pays for them; three to five varied ones are usually enough.
  • A single example. It gets copied too closely, so every output mimics its length and wording.

“Add chain-of-thought, examples and a schema to be safe” fixes the failure at several times the necessary cost. The guide’s phrase is “without unnecessary token cost”: one technique per failure.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A classifier’s output sometimes isn’t valid JSON, and sometimes uses a label outside the allowed list. The labels it does choose are usually right. Which technique fits?
  1. A. More effort, so it thinks harder
  2. B. Structured output: a JSON schema with the allowed labels as an enum
  3. C. Twenty more examples
  4. D. A longer system prompt
Answer
B
Why
These are shape failures, which a schema guarantees against. More thinking doesn’t guarantee shape, and extra examples cost tokens on every call without fixing it.
Question 2
Scenario
A classifier keeps confusing two similar categories on borderline cases, though its output format is always valid. Which technique fits best?
  1. A. A schema
  2. B. Three to five varied examples covering the confusable cases, in example tags
  3. C. Maximum effort
  4. D. Prompted reasoning in thinking tags on Opus 5.5
Answer
B
Why
Examples fix judgement at boundaries the instructions don’t pin down. A schema keeps labels in the set but doesn’t choose the right one.
Question 3
Scenario
A task that involves multi-step calculations returns wrong totals on a model with native thinking. What should be tried first?
  1. A. Ask it to write out its reasoning in thinking tags
  2. B. Raise the effort level so native thinking works through the steps
  3. C. Add a schema
  4. D. Use one example
Answer
B
Why
Reasoning errors call for more thinking, which on models that think is controlled by effort; a request to write the reasoning out may be declined and duplicates what native thinking does. Thinking tokens are billed as output.
Question 4
Scenario
Evaluations pass on a well-defined extraction task with clear instructions. A colleague suggests adding examples, a schema and higher effort “to be safe”. What is the right call?
  1. A. Add all three
  2. B. Change nothing: stay zero-shot, because every addition costs tokens on every call
  3. C. Add only higher effort
  4. D. Switch to a larger model
Answer
B
Why
Each technique fixes one kind of failure. With nothing failing, extra techniques only add cost.

Key takeaways

  • Add only the technique that fixes the observed failure; each one adds tokens to every call.
  • Zero-shot when the evaluation passes; few-shot (three to five varied examples in <example> tags) for format and borderline cases; more effort for reasoning errors; structured output for shape errors.
  • Fable 5.2 and Opus 5.5 always think; Sonnet 5.5 and Haiku 5.5 think by default; Opus 4.6 to 4.8 and Sonnet 4.6 only when turned on. Prompted reasoning with <answer> tags is the fallback when thinking is off, and a request to write the reasoning out may be declined on models that think.
  • A schema guarantees the shape, not the right answer; examples fix judgement at the boundary; effort fixes reasoning, billed as output tokens.
  • “Add everything to be safe” fixes the failure at several times the necessary cost.
