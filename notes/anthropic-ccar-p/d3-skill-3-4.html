An agent can fail for days while every dashboard stays green

Skill 3.4What this skill asks, and an incident that shows why.

Questions on this skill describe a failure that monitoring missed and ask which monitoring would have caught it. Agent failures are easy to miss because the model keeps working normally while the task fails.

Take a retailer that handles about 2,000 refund conversations a day with Agent SDK agents, which call a payments system through an MCP server. After a certificate was renewed, the payments server rejected every connection for three days. The agents apologised (“I’ve raised your refund”), the conversations ended normally, and every dashboard stayed green. No refunds were paid.

Five reasons agent failures go unseen

Skill 3.4The usual blind spots.

  • The model is measured, not the outcome. Requests succeed, response times and token counts are normal, and the business result (a refund paid) never happens. The model answering isn’t the task succeeding.
  • Agents recover politely. A failing tool produces an apology or a workaround, not an exception, so the application’s error rate stays flat.
  • Averages hide the broken part. One customer, one tool or one region failing disappears into a healthy average across the whole fleet.
  • Delegation hides the cause. A subagent’s failure shows up only as a weaker final answer, unless its trace is linked to its parent’s.
  • The telemetry fails too. If export stops, dashboards show “no errors” because they show nothing.

Anthropic makes the same point from its own multi-agent system: agents don’t behave the same way twice, so full tracing in production was what made failures diagnosable. It monitored decision patterns and how agents interacted, not the content of conversations.

Check the outcome against the system of record

Skill 3.4The strongest monitor, because it doesn’t need to know how things fail.

Compare what the conversations promised with what actually happened where it counts: refund conversations against refunds the payments system recorded. In the incident above, this check would have shown hundreds of promised refunds and none recorded on the first day. It needs no knowledge of how the failure happens, so it catches failures nobody anticipated.

Break the rates down by tool, connection and customer

Skill 3.4So one broken part doesn’t disappear into an average.

  • Connection health for each MCP server. The failed connection events were being exported for the whole three days; nobody had an alert on them.
  • Error rate for each tool. issue_refund failing while lookup_order succeeds is obvious per tool and invisible in the total.
  • Rates for each customer. When only one customer’s integration breaks, a per-customer rate names who is affected.

Alert when the telemetry itself goes quiet

Skill 3.4No data isn’t good news.

Set an alert that fires when no telemetry has arrived for, say, 15 minutes. The Agent SDK’s observability guide warns that export errors are silent by default; setting CLAUDE_CODE_OTEL_DIAG_STDERR=1 makes them visible.

What the Agent SDK can export

Skill 3.4OpenTelemetry from the Claude Code process the SDK runs.

  • Three kinds of signal. Metrics (tokens, cost, sessions, tool decisions), log events (each prompt, API request, API error and tool result) and traces (a span for each interaction, model request, tool call and hook; traces are in beta). Nothing is exported until CLAUDE_CODE_ENABLE_TELEMETRY=1 and an exporter are set.
  • Traces that follow delegation. A subagent’s spans nest under the parent’s tool span, so one trace shows the whole chain. Spans carry a session ID, and the SDK passes on your application’s trace context.
  • Security events. tool_decision, tool_result, mcp_server_connection and permission_mode_changed make an audit trail you can send to a security monitoring system.
  • Who did it. By default, events identify your service’s credential, not the end user. Add enduser.id and tenant.id as resource attributes on each run.
  • Content only if you ask. By default telemetry records structure, not content; prompts, tool inputs and tool output are added only with explicit settings, which should be used only where the pipeline may store that data.

The code below sets the environment for an agent run with these options:

otel_env.py (otel_env.py)Optional 
"""Telemetry settings for each refund-agent run (Agent SDK, exported over OTLP)."""
from urllib.parse import quote

from claude_agent_sdk import ClaudeAgentOptions


def options_for(user_id: str, tenant_id: str) -> ClaudeAgentOptions:
    return ClaudeAgentOptions(env={
        "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
        "CLAUDE_CODE_ENHANCED_TELEMETRY_BETA": "1",       # traces (beta): spans per model request and tool call
        "OTEL_TRACES_EXPORTER": "otlp", "OTEL_METRICS_EXPORTER": "otlp", "OTEL_LOGS_EXPORTER": "otlp",
        "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
        "OTEL_EXPORTER_OTLP_ENDPOINT": "http://otel-collector.internal:4318",
        "OTEL_SERVICE_NAME": "refund-agent",
        # who the agent acted for: without this, every event shows only the service's own credential
        "OTEL_RESOURCE_ATTRIBUTES": f"enduser.id={quote(user_id)},tenant.id={quote(tenant_id)},service.version=3.2.0",
        "CLAUDE_CODE_OTEL_DIAG_STDERR": "1",               # export errors are silent unless surfaced
        # content stays out by default; OTEL_LOG_TOOL_DETAILS / _CONTENT only if the pipeline may hold it
    })

The monitors that would have caught the refund incident

Skill 3.4Five checks, any of which would have fired on the first day.

The code below runs the five checks from the sections above (the outcome check, MCP connection health, per-tool and per-customer error rates, and telemetry freshness) over sample telemetry from the incident:

detect_gaps.py (detect_gaps.py)Optional 
"""Monitors that would have caught a silent failure in a scaled refund-agent fleet.

What happened: for three days the payments MCP server rejected the agent's connection after a
certificate rotation. Agents apologised ("I've raised your refund") and ended normally. HTTP status,
latency and token dashboards all looked healthy, because they measure the model calls, not the outcome.

Input: telemetry records exported from the Agent SDK (OpenTelemetry log events such as tool_result
and mcp_server_connection, plus the session's end), simplified to the fields used here, and the
payments system's own count of refunds actually issued."""
from collections import Counter, defaultdict


def monitors(events: list[dict], refunds_issued: int, last_export_minutes_ago: float) -> list[str]:
    alerts = []
    # 1. Outcome, not activity: refund intents should match refunds the payments system recorded.
    intents = sum(1 for e in events if e["name"] == "session_end" and e.get("intent") == "refund")
    if intents and refunds_issued / intents < 0.8:
        alerts.append(f"outcome: {refunds_issued} refunds issued for {intents} refund conversations")
    # 2. Connection health of every MCP server, which a model-call dashboard never shows.
    conn = Counter(e["status"] for e in events if e["name"] == "mcp_server_connection")
    if conn["failed"] and conn["failed"] / sum(conn.values()) > 0.05:
        alerts.append(f"mcp: {conn['failed']} of {sum(conn.values())} connections failed")
    # 3. Tool error rate per tool, not in aggregate.
    per_tool = defaultdict(Counter)
    for e in events:
        if e["name"] == "tool_result":
            per_tool[e["tool"]][e["success"]] += 1
    for tool, c in per_tool.items():
        if c[False] / (c[True] + c[False]) > 0.1:
            alerts.append(f"tool: {tool} failing {c[False]} of {c[True] + c[False]}")
    # 4. Per tenant: a healthy average can hide one customer's broken integration.
    by_tenant = defaultdict(Counter)
    for e in events:
        if e["name"] == "tool_result":
            by_tenant[e["tenant"]][e["success"]] += 1
    for tenant, c in by_tenant.items():
        if c[False] / (c[True] + c[False]) > 0.2:
            alerts.append(f"tenant: {tenant} tool failures {c[False]} of {c[True] + c[False]}")
    # 5. The telemetry itself: export failures are silent, so alert on missing data.
    if last_export_minutes_ago > 15:
        alerts.append(f"telemetry: no data for {last_export_minutes_ago:.0f} minutes")
    return alerts

“Add more latency and token dashboards” doesn’t help here: the model was fine. The missing signal was whether the action the conversation promised actually happened.

Match each kind of failure to the signal that shows it

Skill 3.4Which monitoring catches which problem.

  • A tool or integration failing quietly: the outcome check against the system of record, plus per-tool error rates and connection events.
  • Answers slowly getting worse, with no errors: a sample of conversations scored by an evaluation, tracked over time.
  • Runaway loops, or agents spawning too many subagents: tokens, cost and tool calls per session, with alerts on unusual sessions rather than on averages.
  • One customer broken: customer and user identifiers on every event.
  • Misuse: tool decisions and permission-mode changes, tied to end users, in the security monitoring system.
  • Missing telemetry: freshness alerts and exporter diagnostics.

Key takeaways

  • Agent failures hide: the model works, the agent apologises, averages look healthy, and telemetry can stop without anyone noticing.
  • The strongest monitor compares what conversations promised with what the system of record shows.
  • Break rates down by MCP connection, tool and customer, and alert on unusual sessions rather than averages.
  • Alert when telemetry stops arriving; Agent SDK export errors are silent unless CLAUDE_CODE_OTEL_DIAG_STDERR=1 is set.
  • The Agent SDK exports metrics, log events (including tool_result and mcp_server_connection) and beta traces with subagent spans nested; add end-user and customer attributes; content is off by default.
