3.4: Instrumentation and Monitoring Gaps

When an agent system fails quietly for days, asking what it was measuring instead, and choosing the signal that would have shown the problem: whether the work actually got done, not just whether the model answered.

Overview

Skill 3.4

Instrumentation and Monitoring Gaps: "Analyzing the instrumentation gap in a scaled agentic architecture where a described failure went undetected, and selecting the monitoring strategy that would have surfaced it."

Exam items describe an incident that dashboards missed and ask which monitoring would have caught it. Designing observability into a multi-agent decomposition is skill 1.4; evaluation and testing are Domain 4.

Sources: the Agent SDK's OpenTelemetry guide and Anthropic's multi-agent research post, checked on 20 November 2026 and paraphrased. The incident and code are my own; the monitors are tested on synthetic telemetry with simplified event fields.

Running example. A retailer runs about 2,000 refund conversations a day through Agent SDK agents that call a payments MCP server. After a certificate rotation, the server rejected every connection for three days. Agents apologised ("I've raised your refund"), sessions ended normally, and every dashboard was green.

Why agent failures go unseen

Skill 3.4The usual blind spots (my list).

  • Measuring the model, not the outcome: request success, latency and tokens can all be normal while the business result (a refund paid) never happens. The model answering is not the task succeeding.
  • Agents recover gracefully: a failing tool produces an apology or a workaround, not an exception, so error rates in the application stay flat.
  • Aggregates hide segments: one tenant, one tool or one region failing disappears into a healthy fleet average.
  • Delegation hides cause: a subagent's failure surfaces only as a weaker final answer unless its spans are linked to the parent's.
  • The telemetry fails too: if export stops, dashboards show "no errors" because they show nothing.

Anthropic's multi-agent post makes the same point from production: agents are non-deterministic, so full production tracing was what made failures diagnosable, monitoring decision patterns and interaction structure rather than conversation contents.

What the Agent SDK can export

Skill 3.4OpenTelemetry from the Claude Code CLI the SDK runs.

  • Three signals: metrics (tokens, cost, sessions, tool decisions), log events (each prompt, API request, API error and tool result) and traces (spans for each interaction, model request, tool call and hook; in beta). Telemetry is off until CLAUDE_CODE_ENABLE_TELEMETRY=1 and an exporter are set.
  • Traces that follow delegation: a subagent's model and tool spans nest under the parent's tool span, so one trace shows the whole chain; spans carry a session ID, and the SDK propagates your application's trace context.
  • Security events: tool_decision, tool_result, mcp_server_connection and permission_mode_changed form an audit trail you can send to a SIEM.
  • Attribution: by default events identify your service's credential, not the end user; add enduser.id and tenant.id as resource attributes on each run.
  • Content is opt-in: telemetry is structural by default; prompts, tool inputs and tool output are added only with explicit variables, which should be set only if the pipeline may store that data.
  • Silent export failure: the guide warns that the CLI fails silently on export errors by default; set CLAUDE_CODE_OTEL_DIAG_STDERR=1 to see them.

from urllib.parse import quote

from claude_agent_sdk import ClaudeAgentOptions


def options_for(user_id: str, tenant_id: str) -> ClaudeAgentOptions:
    return ClaudeAgentOptions(env={
        "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
        "CLAUDE_CODE_ENHANCED_TELEMETRY_BETA": "1",       # traces (beta): spans per model request and tool call
        "OTEL_TRACES_EXPORTER": "otlp", "OTEL_METRICS_EXPORTER": "otlp", "OTEL_LOGS_EXPORTER": "otlp",
        "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
        "OTEL_EXPORTER_OTLP_ENDPOINT": "http://otel-collector.internal:4318",
        "OTEL_SERVICE_NAME": "refund-agent",
        # who the agent acted for: without this, every event shows only the service's own credential
        "OTEL_RESOURCE_ATTRIBUTES": f"enduser.id={quote(user_id)},tenant.id={quote(tenant_id)},service.version=3.2.0",
        "CLAUDE_CODE_OTEL_DIAG_STDERR": "1",               # export errors are silent unless surfaced
        # content stays out by default; OTEL_LOG_TOOL_DETAILS / _CONTENT only if the pipeline may hold it
    })

Monitors for one incident

Skill 3.4Five checks, any of which would have fired on day one.

detect_gaps.py (detect_gaps.py)Optional 
"""Monitors that would have caught a silent failure in a scaled refund-agent fleet.

What happened: for three days the payments MCP server rejected the agent's connection after a
certificate rotation. Agents apologised ("I've raised your refund") and ended normally. HTTP status,
latency and token dashboards all looked healthy, because they measure the model calls, not the outcome.

Input: telemetry records exported from the Agent SDK (OpenTelemetry log events such as tool_result
and mcp_server_connection, plus the session's end), simplified to the fields used here, and the
payments system's own count of refunds actually issued."""
from collections import Counter, defaultdict


def monitors(events: list[dict], refunds_issued: int, last_export_minutes_ago: float) -> list[str]:
    alerts = []
    # 1. Outcome, not activity: refund intents should match refunds the payments system recorded.
    intents = sum(1 for e in events if e["name"] == "session_end" and e.get("intent") == "refund")
    if intents and refunds_issued / intents < 0.8:
        alerts.append(f"outcome: {refunds_issued} refunds issued for {intents} refund conversations")
    # 2. Connection health of every MCP server, which a model-call dashboard never shows.
    conn = Counter(e["status"] for e in events if e["name"] == "mcp_server_connection")
    if conn["failed"] and conn["failed"] / sum(conn.values()) > 0.05:
        alerts.append(f"mcp: {conn['failed']} of {sum(conn.values())} connections failed")
    # 3. Tool error rate per tool, not in aggregate.
    per_tool = defaultdict(Counter)
    for e in events:
        if e["name"] == "tool_result":
            per_tool[e["tool"]][e["success"]] += 1
    for tool, c in per_tool.items():
        if c[False] / (c[True] + c[False]) > 0.1:
            alerts.append(f"tool: {tool} failing {c[False]} of {c[True] + c[False]}")
    # 4. Per tenant: a healthy average can hide one customer's broken integration.
    by_tenant = defaultdict(Counter)
    for e in events:
        if e["name"] == "tool_result":
            by_tenant[e["tenant"]][e["success"]] += 1
    for tenant, c in by_tenant.items():
        if c[False] / (c[True] + c[False]) > 0.2:
            alerts.append(f"tenant: {tenant} tool failures {c[False]} of {c[True] + c[False]}")
    # 5. The telemetry itself: export failures are silent, so alert on missing data.
    if last_export_minutes_ago > 15:
        alerts.append(f"telemetry: no data for {last_export_minutes_ago:.0f} minutes")
    return alerts
  • Outcome reconciliation (the strongest): refund conversations against refunds the payments system recorded. It needs no knowledge of how the failure happens.
  • MCP connection health: the mcp_server_connection failures were exported the whole time; nobody alerted on them.
  • Per-tool error rate: issue_refund failing while lookup_order succeeds.
  • Per-tenant rate: names which customer is affected when only one integration breaks.
  • Telemetry freshness: an alert when no data has arrived for 15 minutes.

"Add more latency and token dashboards" doesn't help here: the model was fine. The missing signal was whether the action the conversation promised actually happened.

Matching the gap to the monitor

Skill 3.4Which signal surfaces which kind of failure.

  • Silent tool or integration failure: outcome reconciliation against the system of record, plus per-tool error rates and connection events.
  • Quality drift (answers getting worse, no errors): sampled transcripts scored by an evaluation, tracked over time (Domain 4).
  • Runaway loops or delegation storms: tokens, cost and tool calls per session, with alerts on outliers rather than averages.
  • One customer broken: per-tenant and per-user attribution on every event.
  • Security misuse: tool decisions and permission-mode changes, attributed to end users, in the SIEM.
  • Missing telemetry: freshness alerts and exporter diagnostics.

Key takeaways

  • Agent failures hide: the model succeeds, the agent apologises, the average looks healthy, and the telemetry itself can stop silently.
  • Monitor outcomes against the system of record, not just model calls: the action the conversation promised must show up where it lands.
  • Break rates down by tool, MCP server, tenant and user; alert on per-session outliers for loops and cost.
  • Agent SDK OpenTelemetry: metrics, log events (including tool_result and mcp_server_connection) and beta traces with subagent spans nested; add end-user and tenant attributes; content off by default.
  • Watch the telemetry itself: export errors are silent by default, so alert on missing data.
