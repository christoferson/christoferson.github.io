Overview

Skill 2.6

Reasoning Effort and Context Lifecycle: "Allocating reasoning effort and selecting a context lifecycle strategy (context editing, memory tool, compaction) that sustains task performance across the stated session length for a long-running agent workload with stated latency and accuracy requirements."

Exam items describe a long-running agent, how its context grows and its latency and accuracy targets, and ask which effort and lifecycle strategy fit. The developer view, diagnosing bloat in a session that's already struggling, is CCDV-F 6.1; this skill is designing for the whole session up front.

A long-running agent needs a plan for thinking effort and for its context

Skill 2.6What this skill asks you to design.

An agent that runs for hours faces two problems a short chat doesn’t. Its work varies: some steps are routine and some are hard judgement calls, so one effort level for the whole run is either wasteful or risky. And its context keeps growing with tool results and conversation until it fills up or becomes too long to work well. Questions on this skill describe such an agent, how its context grows, and its speed and accuracy requirements, and ask which effort settings and which context tools keep it working for the whole session.

Spend thinking effort where mistakes are costly

Skill 2.6Effort is a budget to allocate by phase, not one setting for the session.

  • What effort does. The levels are low, medium, high, xhigh (Opus 4.7 and newer) and max. More effort means more thinking: more thorough, but slower and more output tokens. Opus 5.5 defaults to medium.
  • Allocate by phase. Planning and hard judgement calls get more effort; repetitive tool loops get less. One high setting for six hours of routine work wastes time and money; one low setting risks the hard cases.
  • Change it during the session. Each request can set its own effort. On Opus 5.5 (and Fable 5.2 and 5.1) a system message part-way through the conversation can also change it (in beta), and Anthropic’s caching notes say a change of effort per message keeps the cached part of the prompt.
  • Turns where someone is waiting, such as a status check, get low effort and a small context, not the agent’s whole working state.

Clear old tool results with context editing

Skill 2.6For context filled by query results and file reads the agent no longer needs.

What it does. Context editing (clear_tool_uses_20250919, in beta) replaces old tool results with placeholders once the input passes a trigger, 100,000 tokens by default, keeping the most recent few (3 by default). You can exclude tools whose results must stay. Your application still holds the full history.

When it fits. Tool output piles up and the old results aren’t needed again. Nothing in the conversation is summarised, so the agent’s decisions and reasoning stay exactly as they were.

Keep progress that must survive in the memory tool

Skill 2.6For facts that must outlive the context window or the session.

What it does. The memory tool (memory_20250818) gives Claude a set of files it reads and writes through your code. Claude checks its memory before starting and records its progress as it goes, so the work survives the context being cleared, or the whole agent being restarted. The files are stored on your side, so it’s eligible for zero data retention and HIPAA. Your code should check every file path Claude asks for.

When it fits. Progress, decisions made, and what’s left to do. It’s the only one of the three tools that survives a restart.

Summarise a long conversation with compaction

Skill 2.6For when the conversation itself, not tool output, is what grows.

What it does. Compaction (compact_20260112, in beta) has the server summarise the older turns into a compaction block once the input passes a trigger (150,000 tokens by default, and at least 50,000). You send that block back unchanged in later requests. Instructions can say what must be kept word for word.

When it fits. Long back-and-forth discussions or many turns of reasoning. Summaries lose detail by design, so tell compaction to keep identifiers and decisions verbatim, and don’t rely on it for exact values that matter.

A fourth option. Bulk reading that doesn’t need to be kept at all can go to a subagent, so it never enters the main context.

Match the tool to what is filling the context

Skill 2.6The three tools solve different problems.

“Turn on compaction and let it handle everything” loses exact values in the summary and does nothing for a restart. Progress that must survive belongs in memory, and bulky tool output is cleared, not summarised.

Worked example: an overnight agent, phase by phase

Skill 2.6Effort and context settings for each part of the run.

A retail chain runs an overnight agent on Opus 5.5 that cleans 40,000 product records. It runs for about six hours and may be interrupted; it must not put wrong prices live at 06:00; and it must answer a 07:00 status check within seconds.

  • Planning (high effort): read the memory files, see what’s already done, and decide the batches.
  • Bulk fixes (low effort, context editing): thousands of routine corrections; old query results are cleared, except anything read from memory.
  • Ambiguous records (xhigh effort, context editing): conflicting supplier data, where a wrong price is the costly mistake.
  • A long discussion with an operator (medium effort, compaction): if a person starts a long back-and-forth, older turns are summarised, with every changed product code kept word for word.
  • The 07:00 status check (low effort, no tools): answered quickly from the progress file in memory.
  • A safety net outside the model: fixes are proposed to a validation job rather than written live, so accuracy doesn’t depend on effort alone.

The code below builds the request settings for each phase:

lifecycle_plan.py (lifecycle_plan.py)Optional 
"""Overnight catalogue clean-up agent (40,000 product records): effort and context lifecycle by phase.

Requirements: fixes must be right (wrong prices go live at 06:00), the run lasts about six hours and
may be interrupted, and the 07:00 status check-in must answer within seconds.
Context tools (Claude API, Nov 2026):
  clear_tool_uses_20250919  context editing: drops old tool results, keeps recent ones (beta header below)
  memory_20250818           client-side memory files: durable progress across context resets and restarts
  compact_20260112          server compaction of older turns at an input-token threshold (beta header below)"""

MODEL = "claude-opus-5-5"
MEMORY_TOOL = {"type": "memory_20250818", "name": "memory"}
DB_TOOLS = [{"name": "query_products", "description": "Read up to 200 product records matching a filter.",
             "input_schema": {"type": "object", "properties": {"filter": {"type": "string"}}, "required": ["filter"]}},
            {"name": "propose_fix", "description": "Queue a change to one record for the 05:30 validation job.",
             "input_schema": {"type": "object", "properties": {"sku": {"type": "string"}, "change": {"type": "object"}},
                              "required": ["sku", "change"]}}]

PRUNE = {"edits": [{"type": "clear_tool_uses_20250919",
                    "trigger": {"type": "input_tokens", "value": 60_000},
                    "keep": {"type": "tool_uses", "value": 4},
                    "exclude_tools": ["memory"]}]}           # never clear what it read from memory
COMPACT = {"edits": [{"type": "compact_20260112", "trigger": {"type": "input_tokens", "value": 150_000},
                      "instructions": "Keep every SKU, field and value changed, verbatim, and open questions."}]}


def plan(phase: str) -> dict:
    """Request settings for each phase of the run."""
    base = {"model": MODEL, "max_tokens": 16_000, "tools": [MEMORY_TOOL, *DB_TOOLS]}
    if phase == "plan":                 # once: read memory, decide the batches; worth the thinking
        return {**base, "output_config": {"effort": "high"}}
    if phase == "bulk":                 # thousands of routine fixes: fast, cheap turns; tool output piles up
        return {**base, "output_config": {"effort": "low"},
                "betas": ["context-management-2025-06-27"], "context_management": PRUNE}
    if phase == "ambiguous":            # conflicting supplier data: accuracy matters more than speed
        return {**base, "output_config": {"effort": "xhigh"},
                "betas": ["context-management-2025-06-27"], "context_management": PRUNE}
    if phase == "long_discussion":      # the conversation itself grows (operator back-and-forth): summarise it
        return {**base, "output_config": {"effort": "medium"},
                "betas": ["compact-2026-01-12"], "context_management": COMPACT}
    if phase == "status":               # 07:00 check-in: answer from memory, quickly, with no tools needed
        return {"model": MODEL, "max_tokens": 1_000, "output_config": {"effort": "low"}}
    raise ValueError(phase)

Test that it still works at the end of the session

Skill 2.6Checks that the plan holds for the stated session length.

  • Test the full length. Run an evaluation as long as a real session; accuracy in hour five is what matters.
  • Test an interruption. Stop the run part-way and confirm it resumes from memory without redoing or skipping work.
  • Watch the triggers. Track how often context editing and compaction fire, and whether quality drops after they do.
  • Mind the cache. Clearing or compacting changes the prompt, so expect cache writes after each event, and set the triggers so they don’t fire every few turns.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
An agent runs for six hours. Most of its work is routine, but a few decisions are costly if wrong. How should effort be set?
  1. A. High for the whole session
  2. B. Low for the whole session
  3. C. Per phase: more for planning and hard decisions, less for routine loops
  4. D. Effort can’t change during a session
Answer
C
Why
Effort is a budget. One high setting wastes time and money on routine work; one low setting risks the hard cases. Each request can set its own effort.
Question 2
Scenario
An agent’s context fills with old query results it no longer needs, while its decisions must stay exact. Which tool fits?
  1. A. Compaction
  2. B. Context editing, which clears old tool results and summarises nothing
  3. C. The memory tool
  4. D. A larger context window
Answer
B
Why
Context editing replaces old tool results with placeholders above a trigger, so decisions in the conversation stay exactly as they were. Compaction would summarise them and can lose exact values.
Question 3
Scenario
An agent may be restarted part-way through a long job and must not redo or skip work. Where should its progress be kept?
  1. A. In the conversation history
  2. B. In the memory tool’s files, which survive a restart
  3. C. In a compaction summary
  4. D. In the system prompt
Answer
B
Why
The memory tool keeps files outside the context window, so progress survives a reset or a restart. History and compaction summaries are lost when the session ends.
Question 4
Scenario
A team turns on compaction and relies on it for everything. What problems remain?
  1. A. None
  2. B. Summaries lose exact values, and nothing survives a restart; durable progress needs memory, and bulky tool output should be cleared
  3. C. Compaction is always slower
  4. D. Compaction raises the price per token
Answer
B
Why
Compaction is lossy by design and lives in the session. Match the tool to what is growing: clear tool output, keep durable facts in memory, and compact long conversations with instructions to keep key values verbatim.

Key takeaways

  • Allocate effort by phase: more for planning and costly judgement calls, less for routine loops and for turns where someone is waiting; each request can set its own effort.
  • Context editing clears old tool results above a trigger (default 100,000 tokens), keeping the latest few and any tools you exclude.
  • The memory tool keeps progress in files outside the context, so it survives a reset or a restart; compaction summarises older turns above a trigger (default 150,000, minimum 50,000) and loses detail by design.
  • Match the tool to what is growing: tool output, clear it; facts that must survive, memory; a long conversation, compaction with verbatim instructions; bulk reading, a subagent.
  • Test over the full session length, through an interruption, and keep an accuracy safety net outside the model.
