2.6: Reasoning Effort and Context Lifecycle

Keeping a long-running agent sharp for hours: spending reasoning where accuracy needs it and saving it where speed matters, and choosing how the context is kept healthy as it fills: clearing old tool output, keeping durable notes outside the window, or summarising the conversation.

Overview

Skill 2.6

Reasoning Effort and Context Lifecycle: "Allocating reasoning effort and selecting a context lifecycle strategy (context editing, memory tool, compaction) that sustains task performance across the stated session length for a long-running agent workload with stated latency and accuracy requirements."

Exam items describe a long-running agent, how its context grows and its latency and accuracy targets, and ask which effort and lifecycle strategy fit. The developer view, diagnosing bloat in a session that's already struggling, is CCDV-F 6.1; this skill is designing for the whole session up front.

Sources: the Claude documentation on effort, compaction, context editing, the memory tool and prompt caching, checked on 19 and 20 November 2026 and paraphrased. The agent and code are my own; each phase's request is tested against the SDK with a mocked API.

Running example. A retail chain runs an overnight agent on Opus 5.5 that cleans 40,000 product records. It runs for about six hours, may be interrupted, must not push wrong prices live at 06:00, and must answer a 07:00 status check within seconds.

Effort as a budget

Skill 2.6Spend it where errors are costly.

  • Levels: low, medium, high, xhigh (Opus 4.7 and newer) and max. More effort means more thinking: more thorough, but slower and more output tokens. Opus 5.5 defaults to medium.
  • Allocate by phase, not by session: planning and hard judgement calls get more; repetitive tool loops get less. One high setting for six hours of routine work wastes time and money; one low setting risks the hard cases.
  • Changing effort mid-session: each request can set its own effort. On Opus 5.5 (and Fable 5.2 and 5.1) a mid-conversation system message can change effort, in beta, and Anthropic's caching notes say a per-message effort change keeps the cached prefix.
  • Latency-bound turns (a status check, a user waiting) get low effort and a small context, not the agent's full working state.

Three lifecycle tools

Skill 2.6What each one keeps and what it drops.

  • Context editing (clear_tool_uses_20250919, beta): when input passes a trigger (100,000 tokens by default), old tool results are replaced with placeholders, keeping the most recent few (3 by default). You can exclude tools whose results must stay. Your application still holds the full history.
  • Memory tool (memory_20250818): a set of files Claude reads and writes through your code. Claude checks its memory before starting and records progress, so work survives a context reset or a restart. It's client-side storage, eligible for zero data retention and HIPAA. Validate every path it asks for.
  • Compaction (compact_20260112, beta): when input passes a trigger (150,000 by default, at least 50,000), the server summarises older turns into a compaction block, which you send back as it is. Custom instructions say what must survive verbatim.

Which tool for which growth

Skill 2.6Match the tool to what is filling the window (my mapping).

  • Tool output piles up (query results, file reads) and old results aren't needed: context editing. Nothing in the conversation is summarised, so decisions stay exact.
  • Facts must outlive the window or the session (progress, decisions, what's left): the memory tool. It's the only one of the three that survives a restart.
  • The conversation itself grows (long operator discussions, many reasoning turns): compaction, with instructions to keep identifiers and decisions verbatim. It's lossy by design, so don't rely on it for exact values that matter.
  • Bulk reading that doesn't need to stay at all: a subagent, so the reading never enters the main context.

"Turn on compaction and let it handle everything" loses exact values in the summary and does nothing for a restart. Durable state belongs in memory; bulky tool output is cleared, not summarised.

An overnight agent, phase by phase

Skill 2.6Effort and context settings for each part of the run.

lifecycle_plan.py (lifecycle_plan.py)Optional 
"""Overnight catalogue clean-up agent (40,000 product records): effort and context lifecycle by phase.

Requirements: fixes must be right (wrong prices go live at 06:00), the run lasts about six hours and
may be interrupted, and the 07:00 status check-in must answer within seconds.
Context tools (Claude API, Nov 2026):
  clear_tool_uses_20250919  context editing: drops old tool results, keeps recent ones (beta header below)
  memory_20250818           client-side memory files: durable progress across context resets and restarts
  compact_20260112          server compaction of older turns at an input-token threshold (beta header below)"""

MODEL = "claude-opus-5-5"
MEMORY_TOOL = {"type": "memory_20250818", "name": "memory"}
DB_TOOLS = [{"name": "query_products", "description": "Read up to 200 product records matching a filter.",
             "input_schema": {"type": "object", "properties": {"filter": {"type": "string"}}, "required": ["filter"]}},
            {"name": "propose_fix", "description": "Queue a change to one record for the 05:30 validation job.",
             "input_schema": {"type": "object", "properties": {"sku": {"type": "string"}, "change": {"type": "object"}},
                              "required": ["sku", "change"]}}]

PRUNE = {"edits": [{"type": "clear_tool_uses_20250919",
                    "trigger": {"type": "input_tokens", "value": 60_000},
                    "keep": {"type": "tool_uses", "value": 4},
                    "exclude_tools": ["memory"]}]}           # never clear what it read from memory
COMPACT = {"edits": [{"type": "compact_20260112", "trigger": {"type": "input_tokens", "value": 150_000},
                      "instructions": "Keep every SKU, field and value changed, verbatim, and open questions."}]}


def plan(phase: str) -> dict:
    """Request settings for each phase of the run."""
    base = {"model": MODEL, "max_tokens": 16_000, "tools": [MEMORY_TOOL, *DB_TOOLS]}
    if phase == "plan":                 # once: read memory, decide the batches; worth the thinking
        return {**base, "output_config": {"effort": "high"}}
    if phase == "bulk":                 # thousands of routine fixes: fast, cheap turns; tool output piles up
        return {**base, "output_config": {"effort": "low"},
                "betas": ["context-management-2025-06-27"], "context_management": PRUNE}
    if phase == "ambiguous":            # conflicting supplier data: accuracy matters more than speed
        return {**base, "output_config": {"effort": "xhigh"},
                "betas": ["context-management-2025-06-27"], "context_management": PRUNE}
    if phase == "long_discussion":      # the conversation itself grows (operator back-and-forth): summarise it
        return {**base, "output_config": {"effort": "medium"},
                "betas": ["compact-2026-01-12"], "context_management": COMPACT}
    if phase == "status":               # 07:00 check-in: answer from memory, quickly, with no tools needed
        return {"model": MODEL, "max_tokens": 1_000, "output_config": {"effort": "low"}}
    raise ValueError(phase)
  • Plan (high): read memory, see what's done, decide the batches.
  • Bulk (low, context editing): thousands of routine fixes; old query results are cleared, but anything read from memory is excluded.
  • Ambiguous records (xhigh, context editing): conflicting supplier data, where a wrong price is the costly error.
  • Long operator discussion (medium, compaction): if a person starts a long back-and-forth, older turns are summarised with every changed SKU kept verbatim.
  • 07:00 status (low, no tools): answers from the progress file in memory, quickly.
  • Safety net outside the model: fixes are proposed to a validation job, not written live; accuracy doesn't depend on effort alone.

Sustaining performance

Skill 2.6Checks that the strategy holds for the stated session length.

  • Test the whole length: run an evaluation that lasts as long as production sessions; accuracy at hour five is what matters.
  • Test interruption: kill the run midway and confirm it resumes from memory without redoing or skipping work.
  • Watch the triggers: how often context editing and compaction fire, and whether quality drops after they do.
  • Mind the cache: clearing content or compacting changes the prompt, so expect cache writes after each event; place triggers so they don't fire every few turns.

Key takeaways

  • Allocate effort by phase: high or xhigh where errors are costly, low for routine loops and latency-bound replies; each request can set its own effort.
  • Context editing clears old tool results (trigger, keep, exclude); the memory tool keeps durable state outside the window and across restarts; compaction summarises older turns at a threshold (default 150,000, minimum 50,000).
  • Match the tool to the growth: tool output, clear it; durable facts, memory; long conversation, compaction with verbatim instructions; bulk reading, a subagent.
  • Compaction is lossy and doesn't survive a restart; don't make it the only strategy.
  • Prove the strategy over the full session length, through an interruption, and with an accuracy safety net outside the model.
