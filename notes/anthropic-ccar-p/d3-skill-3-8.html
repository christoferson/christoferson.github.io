Overview

Skill 3.8

Production Reliability Controls: "Analyzing the failure pattern in error traces or throughput data from a production integration, and specifying the reliability control (rate-limit handling, retry and backoff, idempotency for side-effecting tools, or fallback routing) that addresses it without introducing duplicate effects."

Exam items give error traces or throughput data and ask which control addresses the pattern. The API's error semantics in code are in the developer notes (CCDV-F 2.4); capacity planning is skill 1.2.

Read the failure pattern, then apply the control that fits it

Skill 3.8What this skill asks you to choose.

Questions on this skill give error traces or throughput data from a production integration and ask which reliability control addresses the pattern: handling rate limits, retrying with backoff, making side-effecting tools idempotent, or falling back to another model. The catch in the guide’s wording is “without introducing duplicate effects”: a retry that repeats a payment fixes one failure by causing another.

The examples below use a retailer’s fulfilment agent that buys courier labels for orders, a paid action, through a buy_label tool. The on-call engineer has a week of traces.

What each pattern in the trace means

Skill 3.8The API’s errors and stop reasons, read as causes.

  • 429 errors with a retry-after header, in bursts at 09:00: a rate limit, or a ramp limit after a sharp jump in traffic. It clears by itself: wait the stated time, and smooth out the spike.
  • 429 errors without retry-after, constantly, from the 28th of the month: the usage tier’s monthly spend cap. Retries keep failing until the month resets or the tier is raised; the error detail says enforced_spend_limit_reached.
  • 529 “overloaded” for a few minutes: the model is temporarily overloaded. A few retries, then another model.
  • 400, 401 or 403 errors: the request, the credential or the permission is wrong. Retrying sends the same mistake again.
  • Everything succeeded, but a label was bought twice: not an API error at all. A tool with side effects ran twice for the same piece of business.
  • A 200 response with stop_reason: "refusal": a refusal by Anthropic’s safety classifiers. It never shows up in error-rate dashboards, so monitor it separately.

Rate limits: wait as told, spread the load, and stop on a spend cap

Skill 3.8For 429 errors.

Honour retry-after. Ramp traffic up gradually rather than starting everything at 09:00. Queue bulk work and spread it out, or send it through the Message Batches API, which isn’t subject to ramp limits. Set workspace limits so one workload can’t use up another’s capacity. A spend-cap 429 is different: retrying can’t succeed, so stop and alert someone who can raise the tier.

Retry temporary errors with backoff, a limited number of times

Skill 3.8For 408, 429, 500 and 529 errors.

Wait longer before each attempt (exponential backoff), add a random element so many clients don’t retry in step (jitter), and cap the number of attempts. The Anthropic SDK already retries these errors twice by default and honours retry-after. If you add your own retry loop on top, set the SDK’s max_retries deliberately, or every failure is retried several times over.

Make every tool with side effects idempotent

Skill 3.8So running it twice has the effect of running it once.

Give each action a key based on what it means for the business (this order, this parcel), not on the attempt. When the tool sees a key it has seen before, it returns the existing result instead of acting again. Pass the key on to the downstream system too, if it accepts one. It is also the only control that covers duplicates no retry setting causes, described in the last section.

Fall back to another model after the retries run out

Skill 3.8For overload that outlasts a few retries.

After a limited number of retries on an overloaded model, send the request to another one. The API offers server-side fallback in beta (up to three named models, on the Claude API and Anthropic-managed Google Cloud); the SDK offers middleware; or you retry with another model yourself. Fallback must be set up on every request path, it doesn’t carry over into tool-execution calls, and later turns of the conversation should stay on the fallback model.

The controls in code

Skill 3.8Error classification, backoff, fallback and an idempotent tool.

The code below classifies each error, backs off and falls back, and makes buy_label idempotent. Its test covers each branch: a spend-cap 429 stops at once; a 429 waits its retry-after; a 529 backs off three times and then falls back to the second model; and a second buy_label call for the same order and parcel returns the first label without buying another.

"""Reliability controls for a fulfilment agent that buys courier labels (a paid, side-effecting action).

Trace patterns seen in production, and the control for each:
  429 with retry-after at the 09:00 order spike    -> wait retry-after, back off with jitter, smooth the spike
  429 without retry-after (monthly spend cap)        -> stop retrying; alert; it will not recover by itself
  529 overloaded on the primary model                 -> bounded retries, then fall back to another model
  duplicate labels after long sessions                -> idempotency on the tool, keyed by the business action
The last one: after old tool results were cleared from context, the agent sometimes called buy_label
again for an order it had already handled. Retrying the model can't fix that; the tool must."""
import random
import time


def action_for(status: int, headers: dict, attempt: int, max_attempts: int = 4) -> tuple[str, float]:
    if status == 429 and "retry-after" not in headers:
        return "stop", 0.0                                  # spend cap: retries keep failing
    if attempt >= max_attempts:
        return "fallback" if status in (529, 500) else "stop", 0.0
    if status == 429:
        return "retry", float(headers["retry-after"]) + random.uniform(0, 1)
    if status in (408, 500, 529):
        return "retry", min(30.0, 2 ** attempt) + random.uniform(0, 1)   # exponential backoff, capped, jittered
    return "stop", 0.0                                      # 400, 401, 403...: fix the request, don't retry


class LabelTool:
    """buy_label made idempotent: the same order and parcel always maps to one label."""

    def __init__(self, courier):
        self.courier, self.done = courier, {}               # in production: a database table with a unique key

    def buy_label(self, order_id: str, parcel: int, service: str) -> dict:
        key = f"label:{order_id}:{parcel}"                  # the business action, not the attempt or the call ID
        if key in self.done:
            return {**self.done[key], "note": "already purchased; returning the existing label"}
        label = self.courier.purchase(order_id, parcel, service, idempotency_key=key)   # courier dedupes too
        self.done[key] = label
        return label


def call_with_controls(send, models=("claude-sonnet-5-5", "claude-haiku-5-5"), sleep=time.sleep):
    """send(model) returns (status, headers, body). Tries the primary with backoff, then the fallback model."""
    for model in models:
        for attempt in range(1, 5):
            status, headers, body = send(model)
            if status == 200:
                return {"model": model, "body": body}
            act, wait = action_for(status, headers, attempt)
            if act == "retry":
                sleep(wait)
                continue
            if act == "fallback":
                break
            raise RuntimeError(f"not retryable: {status}")
    raise RuntimeError("all models exhausted")

Duplicates have four sources, and idempotency covers all of them

Skill 3.8Why retries are the usual culprit, but not the only one.

  • A retry of a call that had already worked. The response was lost, not the action. Any retry on a call with side effects needs idempotency underneath it.
  • The model asking twice. In this agent, old tool results were cleared from the context in long sessions, and the model sometimes bought a label it had already bought. No retry setting causes this or fixes it; the tool’s idempotency does.
  • Two workers picking up the same order. A unique key on the action stops both from buying.
  • A fallback after part of the work was done. Switching models in the middle of a task can repeat steps; with side effects behind idempotent tools, a repeat is harmless.

“Turn off retries to stop the duplicates” trades duplicates for lost work, and does nothing about the model asking twice. “Retry more aggressively” during a spend cap or a burst of rate limiting makes things worse. Match the control to the pattern.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
From the 27th of each month, every request returns 429 with no retry-after header, and the error detail says enforced_spend_limit_reached. What should the integration do?
  1. A. Retry with exponential backoff
  2. B. Fall back to a different Claude model on the same account
  3. C. Stop sending, and alert someone who can raise the usage tier
  4. D. Switch to the Message Batches API
Answer
C
Why
This is the tier’s monthly spend cap: every retry fails until the month resets or the tier is raised, and other models or batches on the same account hit the same cap. Retrying only adds load.
Question 2
Scenario
Each weekday at 09:00 a batch job starts 5,000 requests at once and receives bursts of 429 errors with a retry-after header, which clear within minutes. Which change fits best?
  1. A. Ramp the job up gradually, or move it to the Message Batches API
  2. B. Turn off the SDK’s retries
  3. C. Fall back to another model
  4. D. Raise max_tokens
Answer
A
Why
A sharp jump in traffic triggers rate or ramp limits. Spreading the load, or using batches, which aren’t subject to ramp limits, removes the spike. Turning off retries loses work; another model doesn’t remove the spike.
Question 3
Scenario
An agent occasionally sends two refunds for the same order. Logs show the refund API succeeded the first time, but its response timed out and the client retried. Which control prevents the duplicate?
  1. A. Turn off retries for the refund tool
  2. B. Lower the timeout
  3. C. An idempotency key based on the order, so a repeated call returns the first refund
  4. D. A stricter system prompt
Answer
C
Why
The action happened; only the response was lost. Keying the action by the order makes a repeat harmless, whatever triggered it. Turning off retries trades duplicates for lost refunds; a prompt can’t control a client retry.
Question 4
Scenario
A model returns 529 errors for several minutes during a regional surge. Retries with backoff haven’t helped. What is the next control?
  1. A. Retry indefinitely until it succeeds
  2. B. Fall back to another model after a limited number of retries, on every request path
  3. C. Treat it as a spend cap and stop
  4. D. Remove the retry-after handling
Answer
B
Why
529 is temporary overload. After a few retries, falling back to another model keeps the service running; it has to be configured on every request path, and later turns should stay on the fallback model.

Key takeaways

  • Read the trace: 429 with retry-after clears; 429 without it is a spend cap that won’t; 529 is temporary overload; 400, 401 and 403 aren’t worth retrying; refusals arrive as 200s.
  • Rate limits: honour retry-after, ramp up gradually, spread bulk work (batches skip ramp limits), set workspace limits; stop and alert on a spend cap.
  • Retries: exponential backoff with jitter and a cap, for temporary errors only; the SDK already retries twice.
  • Idempotency: key side-effecting actions by what they mean for the business and return the existing result on a repeat; it covers retries, the model asking twice and parallel workers.
  • Fallback: limited retries, then another model, set up on every request path, staying on it for later turns.
