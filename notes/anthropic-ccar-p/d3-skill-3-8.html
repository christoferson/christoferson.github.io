3.8: Production Reliability Controls

Reading what the traces say (bursts of rate-limit errors, an overloaded model, a cap that won't lift, the same action done twice) and applying the one control that fixes that pattern, making sure the fix can't repeat something that should only happen once.

Overview

Skill 3.8

Production Reliability Controls: "Analyzing the failure pattern in error traces or throughput data from a production integration, and specifying the reliability control (rate-limit handling, retry and backoff, idempotency for side-effecting tools, or fallback routing) that addresses it without introducing duplicate effects."

Exam items give error traces or throughput data and ask which control addresses the pattern. The guide's own sample question for this skill isn't reproduced here. The API's error semantics in code are in the developer notes (CCDV-F 2.4); capacity planning is skill 1.2.

Sources: the Claude API documentation on errors, rate limits, streaming and refusals and fallback, checked on 19 and 20 November 2026 and paraphrased. The agent and code are my own and tested.

Running example. A retailer's fulfilment agent buys courier labels for orders, a paid action, through a buy_label tool. The on-call engineer has a week of traces.

Reading the trace

Skill 3.8What each pattern means, from the API's error semantics.

  • 429 with retry-after, in bursts at 09:00: a rate limit (or a ramp limit after a sharp jump). It clears; wait the stated time and smooth the spike.
  • 429 without retry-after, constantly, from the 28th: the tier's monthly spend cap. Retries keep failing until the month resets or the tier rises; the error detail says enforced_spend_limit_reached.
  • 529 overloaded, for a few minutes: the model is temporarily overloaded; bounded retries, then another model.
  • 400, 401, 403: the request, credential or permission is wrong; retrying sends the same mistake again.
  • Success, but the action happened twice: not an API error at all; a side-effecting tool ran twice for the same business action.
  • 200 with stop_reason: "refusal": a classifier refusal, invisible to error-rate dashboards; monitor it separately.

The four controls

Skill 3.8Each one for a specific pattern.

  • Rate-limit handling: honour retry-after; ramp traffic up gradually rather than all at 09:00; queue and spread bulk work, or send it through the Message Batches API, which isn't subject to ramp limits; set workspace limits so one workload can't starve another. Treat a spend-cap 429 as a stop-and-alert, not a retry.
  • Retry with backoff: for transient errors (408, 429, 500, 529): exponential backoff with jitter and a cap on attempts. The Anthropic SDK already retries these twice by default and honours retry-after, so if you add your own loop, set the SDK's max_retries deliberately, or every failure is retried several times over.
  • Idempotency for side-effecting tools: key each action by what it means in the business (this order, this parcel), not by the attempt, and return the existing result when the key has been seen. Pass the key to the downstream system too, if it supports one.
  • Fallback routing: after bounded retries on an overloaded model, try another. The API offers server-side fallback in beta (up to three named models, on the Claude API and Anthropic-managed Google Cloud), the SDK offers middleware, or you retry manually. Fallback must be configured on every request path, it doesn't carry into tool-execution calls, and later turns should stay on the fallback model.

Controls in code

Skill 3.8Error classification, backoff, fallback and an idempotent tool.

reliability.py (reliability.py) 
"""Reliability controls for a fulfilment agent that buys courier labels (a paid, side-effecting action).

Trace patterns seen in production, and the control for each:
  429 with retry-after at the 09:00 order spike    -> wait retry-after, back off with jitter, smooth the spike
  429 without retry-after (monthly spend cap)        -> stop retrying; alert; it will not recover by itself
  529 overloaded on the primary model                 -> bounded retries, then fall back to another model
  duplicate labels after long sessions                -> idempotency on the tool, keyed by the business action
The last one: after old tool results were cleared from context, the agent sometimes called buy_label
again for an order it had already handled. Retrying the model can't fix that; the tool must."""
import random
import time


def action_for(status: int, headers: dict, attempt: int, max_attempts: int = 4) -> tuple[str, float]:
    if status == 429 and "retry-after" not in headers:
        return "stop", 0.0                                  # spend cap: retries keep failing
    if attempt >= max_attempts:
        return "fallback" if status in (529, 500) else "stop", 0.0
    if status == 429:
        return "retry", float(headers["retry-after"]) + random.uniform(0, 1)
    if status in (408, 500, 529):
        return "retry", min(30.0, 2 ** attempt) + random.uniform(0, 1)   # exponential backoff, capped, jittered
    return "stop", 0.0                                      # 400, 401, 403...: fix the request, don't retry


class LabelTool:
    """buy_label made idempotent: the same order and parcel always maps to one label."""

    def __init__(self, courier):
        self.courier, self.done = courier, {}               # in production: a database table with a unique key

    def buy_label(self, order_id: str, parcel: int, service: str) -> dict:
        key = f"label:{order_id}:{parcel}"                  # the business action, not the attempt or the call ID
        if key in self.done:
            return {**self.done[key], "note": "already purchased; returning the existing label"}
        label = self.courier.purchase(order_id, parcel, service, idempotency_key=key)   # courier dedupes too
        self.done[key] = label
        return label


def call_with_controls(send, models=("claude-sonnet-5-5", "claude-haiku-5-5"), sleep=time.sleep):
    """send(model) returns (status, headers, body). Tries the primary with backoff, then the fallback model."""
    for model in models:
        for attempt in range(1, 5):
            status, headers, body = send(model)
            if status == 200:
                return {"model": model, "body": body}
            act, wait = action_for(status, headers, attempt)
            if act == "retry":
                sleep(wait)
                continue
            if act == "fallback":
                break
            raise RuntimeError(f"not retryable: {status}")
    raise RuntimeError("all models exhausted")

The test covers each branch: a spend-cap 429 stops at once, a 429 waits its retry-after, a 529 backs off three times and then falls back to the second model, and a second buy_label call for the same order and parcel returns the first label without buying another.

Where duplicates come from

Skill 3.8And why retries are the usual culprit.

  • Client-side retries of calls that already took effect: the response was lost, not the action. Any retry policy on a side-effecting call needs idempotency underneath it.
  • The model asking twice: in this agent, old tool results were cleared from context in long sessions, and the model sometimes bought a label it had already bought. No retry setting causes this or fixes it; the tool's idempotency does.
  • Parallel workers: two workers pick up the same queued order; a unique key on the action prevents both from buying.
  • Fallback after partial work: switching models mid-task can re-run steps; keep side effects behind idempotent tools so a replay is harmless.

"Turn off retries to stop the duplicates" trades duplicates for lost work and leaves the model-repeat case untouched. "Retry more aggressively" during a spend cap or a rate-limit storm makes things worse. Match the control to the pattern.

Key takeaways

  • Read the trace: 429 with retry-after clears; 429 without it is a spend cap that won't; 529 is temporary overload; 4xx request errors aren't retryable; refusals are 200s.
  • Rate limits: honour retry-after, ramp gradually, spread bulk work (Batches skip ramp limits), use workspace limits.
  • Retries: exponential backoff with jitter and a cap, for transient errors only; remember the SDK already retries twice.
  • Idempotency: key side-effecting tools by the business action and return the existing result on a repeat; it covers retries, model repeats and parallel workers.
  • Fallback: bounded retries, then another model, configured on every request path; stay on it for later turns.
