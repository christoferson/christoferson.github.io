2.1: Model Tier Selection

Overview

Skill 2.1

Model Tier Selection: "Selecting the Claude model tier that satisfies all binding latency, cost, and quality constraints for a stated workload profile, and identifying why each rejected alternative fails."

Exam items state a workload and three limits, and ask which tier satisfies all of them; the distractors each break one. Value trade-offs across whole architectures are skill 1.5; effort and long sessions are skill 2.6.

Pick the tier that passes every limit, and say why the others fail

Skill 2.1What this skill asks you to decide.

Questions on this skill describe a workload and give it limits, usually three: how fast each answer must arrive, how much each unit of work may cost, and how often the work must come out right. You choose the Claude model tier that meets all three, and for every other tier you say which limit it breaks. The wrong answers are built to tempt: one tier has the best quality, another is the cheapest, and each breaks a different limit.

Know what each tier is for

Skill 2.1The current models, from Anthropic’s models overview (November 2026).

  • Fable 5.2: for demanding reasoning and long agentic work. Latency “Moderate”; $8 per million input tokens and $40 per million output tokens; thinking is always on, and the default effort is high.
  • Opus 5.5: for long-running agentic coding and knowledge work, and Anthropic’s recommended starting point for most workloads. “Moderate”; $4 and $20; thinking always on; default effort medium.
  • Sonnet 5.5: described as “the best combination of speed and intelligence”. “Fast”; $2 and $10; default effort high.
  • Haiku 5.5: for high-volume tasks where speed matters, such as classification, extraction and routing. “Fastest”; from $0.10 and $0.50; default effort medium.

All four have a 1M-token context window, up to 128K tokens of output, and a June 2026 knowledge cutoff, so those don’t separate them. The latency labels are only relative: real response times depend on how long the prompt is, how much the model writes and how much it thinks. That’s why the decision needs your own measurements.

A limit is pass or fail, measured on your own workload

Skill 2.1What the guide means by a binding constraint.

  • Each limit is a requirement, not a goal. A response time at the 95th percentile, a cost per conversation, a minimum success rate: missing any one rules the tier out. Doing very well on the other two doesn’t make up for it.
  • Measure on the real work. Quality comes from your own evaluation set, response time from runs at the effort level you’ll actually use, and cost from the tokens your conversations actually use. Anthropic’s guidance on choosing a model starts with building a good evaluation set for exactly this reason.
  • Effort is part of the choice. The same model at a different effort level is faster or slower, cheaper or dearer, and more or less accurate, so “Sonnet 5.5 at medium effort” and “Sonnet 5.5 at high effort” are different candidates.
  • If several tiers pass, take the cheapest, unless the question names another way to break the tie, such as keeping headroom for growth.

Worked example: a booking-change chat with three limits

Skill 2.1Every tier checked against every limit.

An online travel agency’s live chat changes bookings: moving a flight, swapping a hotel night. Its limits: 95% of replies within 5 seconds, no more than $0.12 of model spend per conversation, and at least 92% of evaluation conversations completing the change correctly. The team measured each tier on its own evaluation conversations:

  • Fable 5.2 at high effort: 97% correct, but 9.8 seconds and $0.49 per conversation.
  • Opus 5.5 at medium effort: 95% correct, but 6.1 seconds and $0.23.
  • Sonnet 5.5 at medium effort: 93% correct, 3.4 seconds, $0.11.
  • Haiku 5.5 at low effort: 1.6 seconds and under a cent, but only 84% correct.

The decision. Sonnet 5.5 at medium effort is the only tier that passes all three limits, so it’s the choice. It isn’t the best on any single measure; it’s chosen because it’s the only one that passes.

The code below holds the measurements and checks each tier against each limit:

"""Select the model tier that meets every binding constraint, and say why each other tier fails.

Workload: an online travel agency's live chat that changes bookings (re-time a flight, swap a hotel night).
Quality and latency are measured on the team's own eval set at each model's chosen effort; cost per
conversation is computed from measured tokens and list prices (USD per million tokens, Nov 2026)."""

PRICES = {"claude-fable-5-2": (8.00, 40.00), "claude-opus-5-5": (4.00, 20.00),
          "claude-sonnet-5-5": (2.00, 10.00), "claude-haiku-5-5": (0.10, 0.50)}

MEASURED = {  # model: (effort, task success on 400 eval conversations, p95 seconds per turn, in tokens, out tokens)
    "claude-fable-5-2":  ("high",   0.97, 9.8, 42_000, 3_900),
    "claude-opus-5-5":   ("medium", 0.95, 6.1, 41_000, 3_100),
    "claude-sonnet-5-5": ("medium", 0.93, 3.4, 41_000, 2_800),
    "claude-haiku-5-5":  ("low",    0.84, 1.6, 40_000, 2_200),
}

CONSTRAINTS = {"min_success": 0.92, "max_p95_seconds": 5.0, "max_cost_per_conversation": 0.12}


def cost(model: str) -> float:
    pin, pout = PRICES[model]
    _, _, _, tin, tout = MEASURED[model]
    return (tin * pin + tout * pout) / 1e6


def assess(model: str, c=CONSTRAINTS) -> list[str]:
    effort, success, p95, _, _ = MEASURED[model]
    fails = []
    if success < c["min_success"]:
        fails.append(f"quality {success:.0%} < {c['min_success']:.0%}")
    if p95 > c["max_p95_seconds"]:
        fails.append(f"p95 {p95}s > {c['max_p95_seconds']}s")
    if cost(model) > c["max_cost_per_conversation"]:
        fails.append(f"cost ${cost(model):.3f} > ${c['max_cost_per_conversation']}")
    return fails


def select(c=CONSTRAINTS):
    passing = [m for m in MEASURED if not assess(m, c)]
    return min(passing, key=cost) if passing else None      # cheapest that meets every constraint


if __name__ == "__main__":
    for m in MEASURED:
        f = assess(m)
        print(f"{m:18} effort={MEASURED[m][0]:6} ${cost(m):.3f}  " + ("PASS" if not f else "FAIL: " + "; ".join(f)))
    print("selected:", select())

For every rejected tier, name the limit it breaks

Skill 2.1The second half of the answer the guide asks for.

  • Fable 5.2 has the highest quality, but its 9.8-second response time breaks the 5-second limit and its $0.49 cost breaks the $0.12 limit: two limits fail.
  • Opus 5.5 is accurate enough, but 6.1 seconds and $0.23 break the time and cost limits. It would be the choice if the limits allowed 7 seconds and $0.30.
  • Haiku 5.5 is by far the fastest and cheapest, but 84% correct misses the 92% floor. A booking change done wrong costs far more than the tokens it saves.

“Choose the most capable model to be safe” and “choose the cheapest because the volume is high” are the two standard wrong answers. Each one optimises a single measure and breaks another limit.

Before changing tier, try the cheaper levers

Skill 2.1Changes Anthropic suggests that can bring a tier inside a limit.

  • Change the effort level. It’s often a better lever than changing model: try the levels on your evaluation set before moving up or down a tier.
  • Cache what repeats. If every call starts with the same instructions or reference text, caching it cuts cost (cached reads cost 5% of the input price on Opus and Sonnet 5.5) and can bring a tier under a cost limit.
  • Send work that can wait to batches, at half price.
  • Use fast mode for speed. On Opus 5.5 and Fable 5.2 it gives faster output at a higher price (Opus 5.5 at $8 and $40), which can bring a tier under a response-time limit if the budget allows.
  • Use two models. A cheaper model for most turns and a stronger one only for the hard cases, once one model is working well.
  • Re-test after every change. Model IDs are fixed snapshots with retirement dates (Opus 5.5, for example, not before 22 September 2027); whenever you change model or effort, run the evaluation again.

Key takeaways

  • Choose the tier that meets every stated limit (response time, cost, quality) and, for each other tier, name the limit it breaks.
  • Tiers: Fable 5.2 (most capable, Moderate latency, $8/$40), Opus 5.5 (the usual starting point, Moderate, $4/$20), Sonnet 5.5 (Fast, $2/$10), Haiku 5.5 (Fastest, from $0.10/$0.50); all have a 1M-token context and 128K output.
  • Limits are pass or fail and must be measured on your own workload at the effort you’ll run; the same model at another effort is a different candidate.
  • If several tiers pass, take the cheapest; the usual wrong answers are “most capable” and “cheapest”, which each break a different limit.
  • Before changing tier, try effort, caching, batches, fast mode or a two-model split, and re-test after every change.
