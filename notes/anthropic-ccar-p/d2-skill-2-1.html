2.1: Model Tier Selection

Picking the tier that passes every hard limit on latency, cost and quality at once, rather than the best or the cheapest, and being able to say exactly which limit each other tier breaks.

Overview

Skill 2.1

Model Tier Selection: "Selecting the Claude model tier that satisfies all binding latency, cost, and quality constraints for a stated workload profile, and identifying why each rejected alternative fails."

Exam items state a workload and three limits, and ask which tier satisfies all of them; the distractors each break one. Value trade-offs across whole architectures are skill 1.5; effort and long sessions are skill 2.6.

Sources: the Claude models overview, "Choosing the right model" and "Optimizing for cost and intelligence", and the pricing page, checked on 20 November 2026 and paraphrased. The workload and its measurements are my own; the filter is tested.

Running example. An online travel agency's live chat changes bookings: re-timing a flight, swapping a hotel night. Each turn must answer within 5 seconds at p95, a conversation may cost at most $0.12 in model spend, and at least 92% of evaluation conversations must complete the change correctly.

The current tiers

Skill 2.1From the models overview, November 2026.

  • Fable 5.2: demanding reasoning and long-horizon agentic work. Latency "Moderate"; $8 / $40 per million input / output tokens; thinking always on; default effort high.
  • Opus 5.5: long-running agentic coding and knowledge work, and the recommended starting point for most workloads. "Moderate"; $4 / $20; thinking always on; default effort medium.
  • Sonnet 5.5: "the best combination of speed and intelligence". "Fast"; $2 / $10; default effort high.
  • Haiku 5.5: high-volume, latency-sensitive tasks such as classification, extraction and routing. "Fastest"; from $0.10 / $0.50; default effort medium.
  • Common to all four: 1M-token context, 128K max output, June 2026 knowledge cutoff.

The latency labels are relative; actual latency depends on prompt length, output length and thinking effort, which is why the decision needs your own measurements.

Binding constraints

Skill 2.1What makes a constraint binding.

  • Hard limits, not goals: a p95 latency, a cost per unit of work, a minimum task-success rate. Missing any one rules the tier out; doing well on the others doesn't compensate.
  • Measured on the workload: quality from your evaluation set, latency at the effort you'll actually run, cost from measured tokens per conversation. Anthropic's model guidance puts a good evaluation set first.
  • Effort is part of the tier choice: the same model at a different effort is a different point on the latency-cost-quality curve.
  • After the filter, prefer the cheapest passing tier, unless the brief names another tie-breaker such as headroom.

Filtering tiers

Skill 2.1Every tier against every limit.

tier_filter.py (tier_filter.py)Optional 
"""Select the model tier that meets every binding constraint, and say why each other tier fails.

Workload: an online travel agency's live chat that changes bookings (re-time a flight, swap a hotel night).
Quality and latency are measured on the team's own eval set at each model's chosen effort; cost per
conversation is computed from measured tokens and list prices (USD per million tokens, Nov 2026)."""

PRICES = {"claude-fable-5-2": (8.00, 40.00), "claude-opus-5-5": (4.00, 20.00),
          "claude-sonnet-5-5": (2.00, 10.00), "claude-haiku-5-5": (0.10, 0.50)}

MEASURED = {  # model: (effort, task success on 400 eval conversations, p95 seconds per turn, in tokens, out tokens)
    "claude-fable-5-2":  ("high",   0.97, 9.8, 42_000, 3_900),
    "claude-opus-5-5":   ("medium", 0.95, 6.1, 41_000, 3_100),
    "claude-sonnet-5-5": ("medium", 0.93, 3.4, 41_000, 2_800),
    "claude-haiku-5-5":  ("low",    0.84, 1.6, 40_000, 2_200),
}

CONSTRAINTS = {"min_success": 0.92, "max_p95_seconds": 5.0, "max_cost_per_conversation": 0.12}


def cost(model: str) -> float:
    pin, pout = PRICES[model]
    _, _, _, tin, tout = MEASURED[model]
    return (tin * pin + tout * pout) / 1e6


def assess(model: str, c=CONSTRAINTS) -> list[str]:
    effort, success, p95, _, _ = MEASURED[model]
    fails = []
    if success < c["min_success"]:
        fails.append(f"quality {success:.0%} < {c['min_success']:.0%}")
    if p95 > c["max_p95_seconds"]:
        fails.append(f"p95 {p95}s > {c['max_p95_seconds']}s")
    if cost(model) > c["max_cost_per_conversation"]:
        fails.append(f"cost ${cost(model):.3f} > ${c['max_cost_per_conversation']}")
    return fails


def select(c=CONSTRAINTS):
    passing = [m for m in MEASURED if not assess(m, c)]
    return min(passing, key=cost) if passing else None      # cheapest that meets every constraint


if __name__ == "__main__":
    for m in MEASURED:
        f = assess(m)
        print(f"{m:18} effort={MEASURED[m][0]:6} ${cost(m):.3f}  " + ("PASS" if not f else "FAIL: " + "; ".join(f)))
    print("selected:", select())

Sonnet 5.5 at medium effort is the only tier that passes all three; it's selected because it passes, not because it scores best on any single measure.

Stating why each alternative fails

Skill 2.1The answer the guide asks for, for each rejected tier.

  • Fable 5.2: highest quality (97%), but p95 9.8 s breaks the 5 s limit and $0.49 per conversation breaks the cost limit. Two binding constraints fail.
  • Opus 5.5: 95% quality, but 6.1 s p95 and $0.23 per conversation; it would be the choice if latency allowed 7 s and the budget $0.30.
  • Haiku 5.5: fastest and cheapest by far, but 84% success misses the 92% floor; a booking change done wrong costs more than the tokens saved.

"Choose the most capable model to be safe" and "choose the cheapest because volume is high" are the two standard distractors. Each optimises one dimension and breaks another binding limit.

Before switching tier

Skill 2.1Cheaper levers Anthropic recommends trying first.

  • Effort: often a better lever than changing model; sweep it before moving up or down a tier.
  • Caching and token hygiene: caching stable prefixes cuts cost (reads at 5% of input price on Opus and Sonnet 5.5) and can bring a tier inside a cost limit.
  • Batches for anything not interactive: 50% off.
  • Fast mode on Opus 5.5 or Fable 5.2 for latency, at premium pricing (Opus 5.5 at $8 / $40), if cost allows.
  • Two models: a cheaper model for most turns and a stronger one for the hard cases, once one model is tuned.
  • Stay current: model IDs are pinned snapshots with retirement dates (for example Opus 5.5 not before 22 September 2027); rerun the evaluation when you change model or effort.

Key takeaways

  • Tiers: Fable 5.2 (most capable, Moderate latency, $8/$40), Opus 5.5 (default start, Moderate, $4/$20), Sonnet 5.5 (Fast, $2/$10), Haiku 5.5 (Fastest, from $0.10/$0.50); all 1M context, 128K output.
  • Binding constraints are pass-or-fail; measure quality, latency and cost on your workload at the effort you'll run.
  • Select the tier that passes every constraint (cheapest among those that pass), and give the specific failed limit for each rejected tier.
  • The usual distractors are "most capable" and "cheapest": each breaks a different binding limit.
  • Try effort, caching, batches, fast mode or a two-model split before changing tier; rerun evaluations after any change.
