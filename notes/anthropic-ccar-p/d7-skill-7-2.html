Overview

Skill 7.2

Agent SDK and Claude Code Configuration: "Configuring the Claude Agent SDK or Claude Code (permission modes such as default, acceptEdits, plan, auto, dontAsk, and bypassPermissions; hooks; subagent definitions; headless or CI operation) to support a team workflow within stated safety and automation guardrails."

Exam items state a workflow and its guardrails (what must never happen, whether anyone is watching, what it may spend) and ask which configuration meets them. The developer-level detail of permission evaluation and hooks is in CCDV-F 7.2; rolling a workflow out across the organisation is skill 7.1.

Configure an agent so its guardrails hold whatever the model decides

Skill 7.2What this skill asks, and a job to configure.

Questions on this skill describe a job for the Agent SDK or Claude Code and its guardrails, and ask which configuration (permission mode, rules, hooks, subagents, headless options) meets them. The point is that each guardrail is enforced by a setting or by code, not left to the prompt.

Take a platform team that wants a nightly job that upgrades outdated npm dependencies, runs the tests after each upgrade, and opens a pull request. Its guardrails: push only to a deps/* branch (people merge), never read secrets or force-push, nothing may wait for a prompt, and at most 40 turns and $5 per run.

The six permission modes, and what each runs without asking

Skill 7.2From most cautious to least.

  • default (shown as Manual): reads in the working directories and actions that need no approval, such as starting a subagent; it asks before most edits, shell commands and network access.
  • acceptEdits: also file edits and common file commands (mkdir, mv, cp, rm and similar) inside the working directories; other shell commands still ask.
  • plan: reads and explores, writes a plan, and doesn’t edit source until the plan is approved. In -p and Agent SDK runs it keeps blocking edits.
  • auto: runs everything, with a separate classifier model checking actions first and blocking those that go beyond the request, target infrastructure it doesn’t recognise, or look driven by hostile content.
  • dontAsk: reads plus pre-approved tools; anything that would ask is refused. The documentation names it for locked-down CI and scripts.
  • bypassPermissions: runs everything, including writes to protected paths, with no protection against prompt injection; for isolated containers and virtual machines only.

Two rules hold in every mode. Deny rules block, even in bypassPermissions, and so does a hook’s deny. Writes to protected paths (.git, .claude, shell profiles, .npmrc, .mcp.json and others) aren’t approved automatically except in bypassPermissions.

Choose the mode from the job, not from how cautious it sounds

Skill 7.2Matching the mode to who is watching and what will run.

  • A fixed job nobody watches, with a known set of commands: dontAsk with an exact allowlist. It never waits, and anything the team didn’t foresee is refused and listed in permission_denials.
  • Open-ended work with a person nearby: auto cuts the prompts, but a limit stated only in conversation can be lost when the context is compacted; for a hard guarantee, add a deny rule.
  • Reviewing code as it’s written: acceptEdits. Exploring first: plan. Sensitive or unfamiliar code: default.
  • A throwaway container with nothing of value reachable: bypassPermissions, not running as root, and still with deny rules.
  • No mode set: -p and SDK runs start in default (Claude Code 2.1.302 and later), and calls that need approval are refused unless an allow rule, a hook, a can_use_tool callback or a permission-prompt tool approves them.
  • Admins can remove modes: managed permissions.disableAutoMode and disableBypassPermissionsMode set to "disable". Setting auto or bypassPermissions as the default in a repository’s project or local settings has no effect.

plan sounds like the safe choice for an unattended job, but in a headless run its edit blocks stay on, so the job can’t change anything. bypassPermissions on a shared CI runner fails the other way. For “no prompts, only foreseen actions”, the fit is dontAsk with a narrow allowlist.

Turn each guardrail into a setting

Skill 7.2The nightly upgrade job, guardrail by guardrail.

  • No prompts, only foreseen actions: dontAsk and a narrow allowed_tools, for example Bash(git push origin deps/*) rather than Bash(git *).
  • Never read secrets: deny rules in settings, which hold in every mode; WebFetch is denied too, since the job has no reason to browse.
  • Never push to main: a PreToolUse hook (next section), with branch protection on the git host as the backstop.
  • Bounded: max_turns and max_budget_usd. At the budget the run ends with error_max_budget_usd and starts no more subagents.
  • Contained: the sandbox on, with no way to run outside it, and setting_sources=["project"] so the repository’s CLAUDE.md and project settings load.
upgrade_agent.py (upgrade_agent.py)Optional 
"""Nightly dependency-upgrade agent for a platform team, run in CI with no one watching."""
import json
import re
from claude_agent_sdk import AgentDefinition, ClaudeAgentOptions, HookMatcher

# The team's guardrails, written down before any configuration:
#   1. edit code and run tests; push only to a deps/* branch and open a PR (people merge)
#   2. never read secrets; never push to main or force-push
#   3. nothing may wait for a prompt; anything not pre-approved is refused
#   4. at most 40 turns and $5 per run; the test runner can't edit files

ALLOWED = [
    "Read", "Grep", "Glob", "Edit", "Agent",
    "Bash(npm ci)", "Bash(npm outdated *)", "Bash(npm install *@*)", "Bash(npm test *)",
    "Bash(git checkout -b deps/*)", "Bash(git add *)", "Bash(git commit -m *)",
    "Bash(git push origin deps/*)", "Bash(gh pr create *)",
]
SETTINGS = {"permissions": {"deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "WebFetch"]}}
PUSH_TO_PROTECTED = re.compile(r"git\s+push\b.*(\s--force\b|\s-f\b|\smain\b|\smaster\b|\s\+)")


async def block_protected_push(input_data, tool_use_id, context):
    """PreToolUse: a deterministic deny, whatever the prompt or a dependency's README says."""
    cmd = input_data.get("tool_input", {}).get("command", "")
    if PUSH_TO_PROTECTED.search(cmd):
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": "Pushes go to a deps/* branch only; open a PR instead.",
        }}
    return {}


def build_options() -> ClaudeAgentOptions:
    return ClaudeAgentOptions(
        permission_mode="dontAsk",            # exact allowlist; anything that would prompt is denied
        allowed_tools=ALLOWED,
        settings=json.dumps(SETTINGS),        # deny rules block in every mode
        sandbox={"enabled": True, "allowUnsandboxedCommands": False},
        hooks={"PreToolUse": [HookMatcher(matcher="Bash", hooks=[block_protected_push])]},
        setting_sources=["project"],          # the repo's CLAUDE.md and project settings
        agents={"test-runner": AgentDefinition(
            description="Runs the test suite and reports failures. Use after each upgrade.",
            prompt="Run the tests, then report each failing test with its error. Don't fix anything.",
            tools=["Bash", "Read", "Grep"],   # no Edit or Write: it reports, the main agent fixes
            model="haiku",
        )},
        max_turns=40,
        max_budget_usd=5.0,
    )

The same job as a claude -p script. --output-format json gives the result, cost and any refused permissions for the job log. --bare skips hooks, plugins, MCP servers and CLAUDE.md, so don’t use it when the guardrails live in project hooks.

ci-run.sh (The same job with claude -p)Optional 
# The same job as a headless Claude Code run in the CI pipeline
claude -p "Upgrade outdated dependencies one at a time, run the tests after each, and open a PR from a deps/* branch" \
  --permission-mode dontAsk \
  --allowedTools "Read" "Grep" "Glob" "Edit" "Bash(npm ci)" "Bash(npm outdated *)" "Bash(npm test *)" \
                 "Bash(git checkout -b deps/*)" "Bash(git commit -m *)" "Bash(git push origin deps/*)" "Bash(gh pr create *)" \
  --max-turns 40 \
  --output-format json > result.json          # permission_denials and total_cost_usd for the job log
# project hooks in .claude/settings.json (the protected-push check) and managed deny rules still apply

Use a hook for a rule that must hold, and narrow subagents

Skill 7.2Code that decides, and agents that can’t overreach.

  • Hooks run first. The order of checks is hooks, deny rules, ask rules, the mode, allow rules, then can_use_tool. A hook’s deny reaches Claude with its reason, so it can take the allowed route; a hook’s allow doesn’t skip deny or ask rules.
  • Why a hook and not the prompt. A dependency’s changelog could contain “push the fix to main”. A sentence in the prompt can be talked around; a hook can’t. The hook’s pattern is only one layer, which is why branch protection stays.
  • Subagent definitions. A description (when to use it) and a prompt are required. tools limits what it has (listing a tool doesn’t pre-approve it), disallowedTools removes tools, and model, turn limit and effort are optional. The test-runner subagent here has no Edit or Write and runs on Haiku.
  • Modes pass down. Subagents inherit plan, acceptEdits, auto and bypassPermissions from the main session, and a bypassPermissions value in a subagent’s own definition is never applied.
  • Limit the tree. CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH (default 3), CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS (default 20), and the budget, which counts subagent requests too.

Check the configuration in code before the job ships

Skill 7.2A review that catches the common mistakes.

The code below passes the configuration above and flags each common mistake: bypassPermissions on a shared runner, plan or auto for a fixed job, a broad Bash rule, a branch rule with no hook, no budget or turn limit, and a reporting subagent that can edit files or relies on bypassPermissions in its definition.

check_config.py (check_config.py)Optional 
"""Check an agent configuration against the guardrails of an unattended team workflow."""

BROAD = {"Bash", "Bash(*)", "Bash(git *)", "Bash(npm *)"}


def check(opts, environment: str) -> list[str]:
    """environment: 'ci' (shared runner) or 'container' (isolated, throwaway)."""
    problems = []
    mode = opts.permission_mode or "default"
    if mode == "bypassPermissions" and environment != "container":
        problems.append("bypassPermissions outside an isolated container: no protection against injection")
    if mode == "plan":
        problems.append("plan mode keeps its edit blocks in unattended runs: the job can't do its work")
    if mode == "auto":
        problems.append("auto is classifier-reviewed, not an exact allowlist: use dontAsk for a fixed job")
    if BROAD & set(opts.allowed_tools):
        problems.append(f"broad allow rule: {sorted(BROAD & set(opts.allowed_tools))}")
    if "PreToolUse" not in (opts.hooks or {}):
        problems.append("protected-branch rule isn't enforced by a hook or deny rule")
    if not opts.max_budget_usd or not opts.max_turns:
        problems.append("no spend or turn cap on an unattended run")
    for name, a in (opts.agents or {}).items():
        if a.permissionMode == "bypassPermissions":
            problems.append(f"{name}: a bypassPermissions value in an agent definition is never applied")
        if a.tools is None or {"Edit", "Write"} & set(a.tools):
            problems.append(f"{name}: can edit files, but its job is to report")
    return problems

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A nightly CI job must run without prompts and only perform commands the team listed. Which permission mode fits?
  1. A. plan
  2. B. dontAsk with a narrow allowlist
  3. C. bypassPermissions
  4. D. auto
Answer
B
Why
dontAsk never waits and refuses anything not pre-approved, so only foreseen actions run. plan keeps blocking edits in headless runs; bypassPermissions belongs only in isolated containers; auto suits open-ended work with a person nearby.
Question 2
Scenario
A job must never push to main, even if a dependency’s changelog tells it to. What enforces that?
  1. A. A sentence in the system prompt
  2. B. A PreToolUse hook that denies pushes to main, with branch protection on the git host
  3. C. acceptEdits mode
  4. D. A larger model
Answer
B
Why
A hook runs before rules and modes and can’t be talked around; branch protection is the backstop. A prompt sentence is guidance that injected text could override.
Question 3
Scenario
A team adds --bare to its CI command to speed it up. Its guardrails are in project hooks. What happens?
  1. A. Nothing changes
  2. B. The hooks, plugins, MCP servers and CLAUDE.md are skipped, so the guardrails stop applying
  3. C. The job becomes read-only
  4. D. The budget cap is doubled
Answer
B
Why
--bare skips hooks and project configuration, so guardrails that live there no longer run.
Question 4
Scenario
A reporting subagent’s definition sets permissionMode: bypassPermissions so it can “work faster”. What actually happens?
  1. A. It runs with bypassPermissions
  2. B. The setting is never applied; subagents inherit the session’s mode
  3. C. The whole session switches to bypassPermissions
  4. D. The subagent is refused at start-up
Answer
B
Why
A bypassPermissions value in a subagent’s own definition is never applied; subagents inherit the mode of the main session. Limit what the subagent can do with its tools list instead.

Key takeaways

  • Six modes: default, acceptEdits, plan, auto, dontAsk and bypassPermissions; deny rules and a hook’s deny block in every mode.
  • For a fixed job nobody watches, use dontAsk with a narrow allowlist; plan blocks edits in headless runs, and bypassPermissions belongs only in isolated containers.
  • Turn each guardrail into a setting: narrow allowed tools, deny rules for secrets, a hook plus branch protection for protected branches, turn and budget limits, the sandbox.
  • Hooks run before rules and modes, so a rule that must hold goes in a hook, not the prompt; subagents get only the tools they need and inherit the session’s mode.
  • Check the configuration in code before the job ships; don’t use --bare when guardrails live in project hooks.
