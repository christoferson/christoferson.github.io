7.2: Agent SDK and Claude Code Configuration

Turning a team’s written guardrails into configuration: which permission mode fits an unattended job, which rules a hook enforces regardless of what the model is told, how subagents are restricted, and what changes when no one is there to answer a prompt.

Overview

Skill 7.2

Agent SDK and Claude Code Configuration: "Configuring the Claude Agent SDK or Claude Code (permission modes such as default, acceptEdits, plan, auto, dontAsk, and bypassPermissions; hooks; subagent definitions; headless or CI operation) to support a team workflow within stated safety and automation guardrails."

Exam items state a workflow and its guardrails (what must never happen, whether anyone is watching, what it may spend) and ask which configuration meets them. The developer-level detail of permission evaluation and hooks is in CCDV-F 7.2; rolling a workflow out across the organisation is skill 7.1.

Sources: the Claude Code documentation on permission modes, headless runs and subagents, and the Agent SDK documentation on permissions, hooks and subagents, checked on 20 November 2026 and paraphrased. The team, files and code are my own; the code is tested against the installed Python Agent SDK, with no API calls.

Running example. A platform team wants a nightly job that upgrades outdated npm dependencies, runs the tests after each upgrade and opens a pull request. Its guardrails: push only to a deps/* branch (people merge), never read secrets or force-push, nothing may wait for a prompt, and at most 40 turns and $5 per run.

The six permission modes

Skill 7.2What each mode runs without asking.

  • default (shown as Manual): reads in the working directories and actions that need no approval, such as starting a subagent; it asks before most edits, shell commands and network access.
  • acceptEdits: also file edits and common filesystem commands (mkdir, mv, cp, rm and similar) inside the working directories; other shell commands still ask.
  • plan: reads and explores, writes a plan, and doesn’t edit source until the plan is approved. In -p and Agent SDK runs it keeps its blocks.
  • auto: everything, with a separate classifier model reviewing actions first and blocking ones that go beyond the request, target unrecognised infrastructure or look driven by hostile content. The documentation is plain that it "does not guarantee safety".
  • dontAsk: reads plus pre-approved tools; anything that would prompt is denied. The documentation names it for locked-down CI and scripts.
  • bypassPermissions: everything, including writes to protected paths, with no protection against prompt injection; for isolated containers and VMs only.

Two rules hold across all of them: deny rules block in every mode, including bypassPermissions, and so does a hook’s deny. Writes to protected paths (.git, .claude, shell profiles, .npmrc, .mcp.json and others) aren’t pre-approved by allow rules, and dontAsk denies them.

Choosing a mode for the job

Skill 7.2Matching the guardrails (my reasoning).

  • A fixed, unattended job with a known set of commands: dontAsk with an exact allowlist. It never waits, and anything the team didn’t foresee is refused and listed in permission_denials.
  • Open-ended work with a person nearby: auto cuts prompts, but a boundary stated in conversation can be lost to compaction; for a hard guarantee the documentation says to add a deny rule.
  • Reviewing code while it’s written: acceptEdits. Exploring first: plan. Sensitive or unfamiliar code: default.
  • A throwaway container with nothing of value reachable: bypassPermissions, not as root, and still with deny rules.
  • With no mode set, -p and SDK runs start in default (Claude Code 2.1.302 and later), and calls that need approval are denied unless an allow rule, hook, can_use_tool callback or permission-prompt tool approves them.
  • Admins can remove modes: managed permissions.disableAutoMode and disableBypassPermissionsMode set to "disable". Setting auto or bypassPermissions as the default in a repository’s project or local settings has no effect.

plan sounds like the safe choice for an unattended job, but in a headless run its edit blocks stay on, so the job can’t change anything. bypassPermissions on a shared CI runner fails the other way. The fit for "no prompts, only these commands" is dontAsk with an allowlist.

The configuration

Skill 7.2Each guardrail mapped to a setting.

upgrade_agent.py (upgrade_agent.py) 
"""Nightly dependency-upgrade agent for a platform team, run in CI with no one watching."""
import json
import re
from claude_agent_sdk import AgentDefinition, ClaudeAgentOptions, HookMatcher

# The team's guardrails, written down before any configuration:
#   1. edit code and run tests; push only to a deps/* branch and open a PR (people merge)
#   2. never read secrets; never push to main or force-push
#   3. nothing may wait for a prompt; anything not pre-approved is refused
#   4. at most 40 turns and $5 per run; the test runner can't edit files

ALLOWED = [
    "Read", "Grep", "Glob", "Edit", "Agent",
    "Bash(npm ci)", "Bash(npm outdated *)", "Bash(npm install *@*)", "Bash(npm test *)",
    "Bash(git checkout -b deps/*)", "Bash(git add *)", "Bash(git commit -m *)",
    "Bash(git push origin deps/*)", "Bash(gh pr create *)",
]
SETTINGS = {"permissions": {"deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "WebFetch"]}}
PUSH_TO_PROTECTED = re.compile(r"git\s+push\b.*(\s--force\b|\s-f\b|\smain\b|\smaster\b|\s\+)")


async def block_protected_push(input_data, tool_use_id, context):
    """PreToolUse: a deterministic deny, whatever the prompt or a dependency's README says."""
    cmd = input_data.get("tool_input", {}).get("command", "")
    if PUSH_TO_PROTECTED.search(cmd):
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": "Pushes go to a deps/* branch only; open a PR instead.",
        }}
    return {}


def build_options() -> ClaudeAgentOptions:
    return ClaudeAgentOptions(
        permission_mode="dontAsk",            # exact allowlist; anything that would prompt is denied
        allowed_tools=ALLOWED,
        settings=json.dumps(SETTINGS),        # deny rules block in every mode
        sandbox={"enabled": True, "allowUnsandboxedCommands": False},
        hooks={"PreToolUse": [HookMatcher(matcher="Bash", hooks=[block_protected_push])]},
        setting_sources=["project"],          # the repo's CLAUDE.md and project settings
        agents={"test-runner": AgentDefinition(
            description="Runs the test suite and reports failures. Use after each upgrade.",
            prompt="Run the tests, then report each failing test with its error. Don't fix anything.",
            tools=["Bash", "Read", "Grep"],   # no Edit or Write: it reports, the main agent fixes
            model="haiku",
        )},
        max_turns=40,
        max_budget_usd=5.0,
    )
  • No prompts, only foreseen actions: dontAsk and a narrow allowed_tools, for example Bash(git push origin deps/*) rather than Bash(git *).
  • Never read secrets: deny rules through settings, which hold in every mode; WebFetch is denied too, since the job has no reason to browse.
  • Never push to main: a PreToolUse hook (next section), with branch protection on the git host as the backstop.
  • Bounded: max_turns and max_budget_usd; at the spend cap the run ends with error_max_budget_usd and spawns no more subagents.
  • Contained: the sandbox on with no unsandboxed escape, and setting_sources=["project"] so the repository’s CLAUDE.md and project settings load.
ci-run.sh (The same job with claude -p) 
# The same job as a headless Claude Code run in the CI pipeline
claude -p "Upgrade outdated dependencies one at a time, run the tests after each, and open a PR from a deps/* branch" \
  --permission-mode dontAsk \
  --allowedTools "Read" "Grep" "Glob" "Edit" "Bash(npm ci)" "Bash(npm outdated *)" "Bash(npm test *)" \
                 "Bash(git checkout -b deps/*)" "Bash(git commit -m *)" "Bash(git push origin deps/*)" "Bash(gh pr create *)" \
  --max-turns 40 \
  --output-format json > result.json          # permission_denials and total_cost_usd for the job log
# project hooks in .claude/settings.json (the protected-push check) and managed deny rules still apply

In a script, --output-format json gives the result, cost and any permission denials for the job log. The --bare flag skips hooks, plugins, MCP servers and CLAUDE.md, so don’t use it when the guardrails live in project hooks.

Hooks and subagents

Skill 7.2Code that decides, and agents that can’t overreach.

  • Hooks run first: the evaluation order is hooks, deny rules, ask rules, mode, allow rules, then can_use_tool. A hook’s deny reaches Claude with its reason, so it can take the allowed route; a hook’s allow doesn’t skip deny or ask rules.
  • Why a hook and not the prompt: a dependency’s changelog could carry "push the fix to main". A sentence in the prompt can be talked around; a hook can’t. The regex is only an illustration, which is why branch protection stays.
  • Subagent definitions: description (when to use it) and prompt are required. tools limits what it has (listing a tool doesn’t pre-approve it), disallowedTools removes tools, and model, maxTurns and effort are optional. The test runner here has no Edit or Write and runs on Haiku.
  • Modes pass down: subagents inherit plan, acceptEdits, auto and bypassPermissions from the main session, and a bypassPermissions value in an agent definition is never applied.
  • Bounding the tree: CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH (default 3), CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS (default 20), and the spend cap, which counts subagent requests too.

Checking the configuration

Skill 7.2A review in code, run before the job ships.

check_config.py (check_config.py) 
"""Check an agent configuration against the guardrails of an unattended team workflow."""

BROAD = {"Bash", "Bash(*)", "Bash(git *)", "Bash(npm *)"}


def check(opts, environment: str) -> list[str]:
    """environment: 'ci' (shared runner) or 'container' (isolated, throwaway)."""
    problems = []
    mode = opts.permission_mode or "default"
    if mode == "bypassPermissions" and environment != "container":
        problems.append("bypassPermissions outside an isolated container: no protection against injection")
    if mode == "plan":
        problems.append("plan mode keeps its edit blocks in unattended runs: the job can't do its work")
    if mode == "auto":
        problems.append("auto is classifier-reviewed, not an exact allowlist: use dontAsk for a fixed job")
    if BROAD & set(opts.allowed_tools):
        problems.append(f"broad allow rule: {sorted(BROAD & set(opts.allowed_tools))}")
    if "PreToolUse" not in (opts.hooks or {}):
        problems.append("protected-branch rule isn't enforced by a hook or deny rule")
    if not opts.max_budget_usd or not opts.max_turns:
        problems.append("no spend or turn cap on an unattended run")
    for name, a in (opts.agents or {}).items():
        if a.permissionMode == "bypassPermissions":
            problems.append(f"{name}: a bypassPermissions value in an agent definition is never applied")
        if a.tools is None or {"Edit", "Write"} & set(a.tools):
            problems.append(f"{name}: can edit files, but its job is to report")
    return problems

The check passes the configuration above and flags each common mistake: bypassPermissions on a shared runner, plan or auto for a fixed job, a broad Bash rule, a branch rule with no hook, no spend or turn cap, and a reporting subagent that can edit or relies on bypassPermissions in its definition.

Key takeaways

  • Write the guardrails down first, then map each one to a setting: mode, allowlist, deny rule, hook or cap.
  • Unattended fixed jobs: dontAsk with a narrow allowlist. plan blocks edits when headless, auto is reviewed rather than guaranteed, and bypassPermissions is for isolated containers only.
  • Deny rules and hook denies hold in every mode; use them, not prompt text, for what must never happen.
  • Subagents need a description and prompt, and restricted tools; they inherit the session’s mode, and a bypass value in a definition is ignored.
  • Cap turns, spend, depth and concurrency, and log denials and cost from the JSON output.
