Overview

Skill 4.1

Evaluation Coverage Gaps: "Analyzing an existing evaluation suite after a failure reached production to determine which metric dimension (accuracy, groundedness, latency, cost, safety, security) or grading target was missing, and specifying the metric that would have detected the failure pre-release."

Exam items describe an evaluation suite and a production failure and ask what was missing. Building evaluations, golden sets and calibrated judges is in the developer notes (CCDV-F 4.1); deciding what an evaluation should test from the business process is skill 4.2.

When a failure reaches production, find what the evaluation didn’t measure

Skill 4.1What this skill asks, and an incident that shows it.

Questions on this skill describe an evaluation suite and a failure that got past it into production, and ask what was missing: a whole dimension the suite never measured, or the wrong part of the output being graded. Then they ask for the metric that would have caught the failure before release.

Take an energy retailer’s billing assistant. Its release gate graded only whether final answers were correct, on 400 short, single-turn questions. In the month after release, six different failures reached customers. Each one maps to something the suite didn’t measure, and each section below takes one.

Anthropic’s guidance on defining success criteria makes the general point: most applications need evaluation on several dimensions, its list of common criteria includes latency and price alongside task accuracy, and even areas that sound hard to measure, such as safety, can be given a number (for example, fewer than 0.1% of 10,000 trials flagged).

Groundedness: a right-looking answer from the wrong source

Skill 4.1Is every claim supported by the material the system was meant to use?

What got through. The assistant quoted a tariff from an out-of-date price sheet. The answer looked right, so a grader checking only correctness accepted it.

The missing metric. The share of factual claims supported by a cited, current source document, judged by a model grader whose verdicts have been checked against people’s.

Latency: test at the input sizes production really sees

Skill 4.1Short test prompts hide slow real ones.

What got through. For customers with 18 months of account history, 1 answer in 20 took 14 seconds or longer (the 95th percentile). The short test questions never carried that much history.

The missing metric. The 95th-percentile time per turn, on inputs sampled to match the context lengths production actually sends.

Cost: tokens per conversation, with a budget

Skill 4.1A prompt change can multiply cost without changing a single answer.

What got through. A prompt change tripled the tokens per conversation. Every answer was still correct, so the gate passed it.

The missing metric. Input and output tokens per conversation, with cache reads counted separately, and a budget the release must stay within.

Safety: test the risky requests on purpose

Skill 4.1Ordinary test questions never ask for anything harmful.

What got through. The assistant told a customer behind on payments how to bypass a prepayment meter.

The missing metric. The rate of answers that break policy on a red-team set: a collection of deliberately harmful or risky requests, with a target near zero.

Security: test whether content can steer the system

Skill 4.1Instructions hidden in documents and tool results.

What got through. A customer uploaded a PDF bill containing hidden instructions, and the assistant followed them and emailed out account details.

The missing metric. The rate at which the system follows instructions embedded in documents and tool results, measured on a set of documents built to contain them.

Grade the actions and the in-between steps, not only the final text

Skill 4.1The grading target: which part of the output is checked.

What got through. The assistant refunded the wrong account. Its final message to the customer was polite and correct, so grading the text found nothing wrong.

What to grade.

  • The actions (the trajectory): which tools were called, with which arguments, in which order: the right account, the right amount.
  • The steps in between: the passages retrieved, the fields extracted, a subagent’s report, wherever an error there wouldn’t show in the final answer.
  • The test inputs themselves: they must look like production, with real lengths, conversations of several turns, and the rare and hostile cases. Anthropic’s test-design guidance says test sets should mirror the real distribution of tasks and include edge cases.

Write the missing metric so that it would have blocked the release

Skill 4.1Specific enough to fail the bad release.

  • Name the measure and the set: “the share of claims supported by a current source, on 300 sampled production questions”, not “check groundedness”.
  • Give a threshold the bad release would have failed. Anthropic asks for criteria that are specific, measurable, achievable and relevant.
  • Choose the grader: code for exact checks (token counts, response times, tool arguments), a model grader for judgement (groundedness), checked against people before it is trusted, and people for spot checks.
  • Add the incident itself as a test case, so this exact failure can’t come back unnoticed.

The code below takes the six incidents and names, for each, the missing dimension and the metric to add:

coverage_audit.py (coverage_audit.py)Optional 
"""Which metric would have caught each production failure before release?

Suite: an energy retailer's billing assistant. Its release gate graded only the final answer's
correctness on 400 short single-turn questions. Six failures reached production anyway."""

SUITE = {
    "dimensions": {"accuracy"},          # what is measured
    "grading_target": "final_answer",    # what is graded: final text only, not the steps or tool calls
    "inputs": "short, single-turn",
}

INCIDENTS = [
    ("quoted a tariff from a superseded price sheet; answer looked right", "groundedness"),
    ("p95 latency 14 s for customers with 18 months of history", "latency"),
    ("token cost per conversation tripled after a prompt change", "cost"),
    ("told a customer in arrears how to bypass a prepayment meter", "safety"),
    ("followed instructions hidden in an uploaded PDF bill and emailed account details", "security"),
    ("issued a refund to the wrong account; the final message was polite and correct", "grading_target"),
]

METRIC = {
    "groundedness": "share of factual claims supported by a cited, current source document (LLM grader, calibrated)",
    "latency": "p95 time per turn on inputs sampled at production context lengths, not short prompts",
    "cost": "input + output tokens per conversation (with cache reads counted separately), with a regression budget",
    "safety": "rate of policy-violating answers on a red-team set of harmful or risky requests (target near zero)",
    "security": "rate of following instructions embedded in documents and tool results, on an injection set",
    "grading_target": "grade the tool calls and their arguments (right account, right amount), not only the final text",
}


def audit(suite=SUITE, incidents=INCIDENTS):
    gaps = []
    for what, dim in incidents:
        covered = dim in suite["dimensions"] or (dim == "grading_target" and suite["grading_target"] != "final_answer")
        if not covered:
            gaps.append((what, dim, METRIC[dim]))
    return gaps


if __name__ == "__main__":
    for what, dim, metric in audit():
        print(f"- {what}\n    missing: {dim}\n    add: {metric}")

“Add more test cases” doesn’t help if they’re graded on the same dimension. Four hundred more correctness questions wouldn’t have caught any of these six failures.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A travel assistant passed an evaluation that checked final answers for correctness. In production it quoted a hotel policy that had been withdrawn months earlier; the answer read well and was accepted. Which dimension was missing?
  1. A. Latency
  2. B. Groundedness: whether each claim is supported by a current source
  3. C. Cost
  4. D. Security
Answer
B
Why
The answer looked correct but came from an out-of-date source, which only a groundedness check against current documents would catch. Latency and cost don’t judge content; security concerns content steering the system.
Question 2
Scenario
An agent that books meetings sends polite, accurate confirmations, but sometimes books the wrong room. The evaluation grades the confirmation text. What should be added?
  1. A. More confirmation-text test cases
  2. B. Grading of the tool calls and their arguments
  3. C. A latency budget
  4. D. A larger model
Answer
B
Why
The error is in the action, not the text, so the grading target must include the trajectory: which tool was called, with which room. More text cases grade the same thing; latency and model size don’t reveal the wrong booking.
Question 3
Scenario
After a prompt update, all evaluation answers stayed correct, but the monthly bill rose by 150%. What should the release gate have included?
  1. A. Tokens per conversation with a regression budget
  2. B. A groundedness grader
  3. C. A red-team set
  4. D. More single-turn questions
Answer
A
Why
Cost is a dimension of its own: a change can multiply tokens without changing any answer. A token budget in the gate would have failed the update; the other options measure content or safety.
Question 4
Scenario
Which metric is specific enough to block a release that leaked account details by following instructions inside uploaded documents?
  1. A. “Check security before release”
  2. B. The share of answers rated helpful by customers
  3. C. The rate of following embedded instructions on a set of documents built to contain them, with a threshold near zero
  4. D. p95 latency on long documents
Answer
C
Why
A useful metric names the measure, the set and a threshold the bad release would have failed. A vague instruction can’t block anything; helpfulness and latency don’t measure injection.

Key takeaways

  • Map each production failure to the dimension that would have caught it: accuracy, groundedness, latency, cost, safety or security.
  • Check the grading target too: grading only the final text misses wrong actions; grade tool calls, their arguments and the steps in between.
  • Test inputs must look like production: real lengths, several turns, rare and hostile cases.
  • Write the missing metric concretely (measure, set, threshold, grader) so that it would have failed the release, and add the incident as a test case.
  • More test cases graded on the same dimension don’t close a gap in another one.
