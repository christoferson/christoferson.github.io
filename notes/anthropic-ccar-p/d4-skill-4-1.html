4.1: Evaluation Coverage Gaps

When something an evaluation suite should have caught gets to production, working out what the suite wasn't measuring (a whole dimension, or the wrong part of the output) and naming the metric that would have stopped the release.

Overview

Skill 4.1

Evaluation Coverage Gaps: "Analyzing an existing evaluation suite after a failure reached production to determine which metric dimension (accuracy, groundedness, latency, cost, safety, security) or grading target was missing, and specifying the metric that would have detected the failure pre-release."

Exam items describe an evaluation suite and a production failure and ask what was missing. Building evaluations, golden sets and calibrated judges is in the developer notes (CCDV-F 4.1); deciding what an evaluation should test from the business process is skill 4.2.

Sources: Anthropic's documentation on defining success criteria and developing tests, checked on 19 and 20 November 2026 and paraphrased. The incidents and code are my own; the audit is tested.

Running example. An energy retailer's billing assistant passed a release gate that graded only the correctness of final answers on 400 short, single-turn questions. Six failures reached production in the following month.

Dimensions an evaluation can miss

Skill 4.1The guide's six, with what each catches.

  • Accuracy: is the answer right? The one most suites have.
  • Groundedness: is each claim supported by the sources the system was meant to use? An answer can be plausible, even correct by luck, and still come from a stale or wrong document.
  • Latency: response time at the input sizes production actually sees, not the short prompts in a test set.
  • Cost: tokens per task or conversation, which a prompt change or longer history can multiply without changing any answer.
  • Safety: harmful or policy-violating output on risky requests.
  • Security: whether the system can be steered by content it reads, such as instructions hidden in a document or tool result.

Anthropic's success-criteria guidance makes the same point: most use cases need multidimensional evaluation, its list of common criteria includes latency and price alongside task fidelity, and even "hazy" areas such as safety can be measured, for example under 0.1% of 10,000 trials flagged. Its test-design guidance adds that test sets should mirror the real task distribution and include edge cases.

The grading target

Skill 4.1Measuring the right thing on the right part of the output (my framing).

  • Final text only: misses agents that took the wrong action and then wrote a fine summary.
  • Trajectory: grade tool calls and arguments (right record, right amount, right order of steps) for agents whose actions matter.
  • Intermediate outputs: retrieved passages, extracted fields or a subagent's report, when an error there is invisible in the end result.
  • Distribution: the set graded must look like production: real lengths, multi-turn conversations, the hard and rare cases.

Auditing a suite after incidents

Skill 4.1Each incident traced to the dimension or target the suite lacked.

coverage_audit.py (coverage_audit.py)Optional 
"""Which metric would have caught each production failure before release?

Suite: an energy retailer's billing assistant. Its release gate graded only the final answer's
correctness on 400 short single-turn questions. Six failures reached production anyway."""

SUITE = {
    "dimensions": {"accuracy"},          # what is measured
    "grading_target": "final_answer",    # what is graded: final text only, not the steps or tool calls
    "inputs": "short, single-turn",
}

INCIDENTS = [
    ("quoted a tariff from a superseded price sheet; answer looked right", "groundedness"),
    ("p95 latency 14 s for customers with 18 months of history", "latency"),
    ("token cost per conversation tripled after a prompt change", "cost"),
    ("told a customer in arrears how to bypass a prepayment meter", "safety"),
    ("followed instructions hidden in an uploaded PDF bill and emailed account details", "security"),
    ("issued a refund to the wrong account; the final message was polite and correct", "grading_target"),
]

METRIC = {
    "groundedness": "share of factual claims supported by a cited, current source document (LLM grader, calibrated)",
    "latency": "p95 time per turn on inputs sampled at production context lengths, not short prompts",
    "cost": "input + output tokens per conversation (with cache reads counted separately), with a regression budget",
    "safety": "rate of policy-violating answers on a red-team set of harmful or risky requests (target near zero)",
    "security": "rate of following instructions embedded in documents and tool results, on an injection set",
    "grading_target": "grade the tool calls and their arguments (right account, right amount), not only the final text",
}


def audit(suite=SUITE, incidents=INCIDENTS):
    gaps = []
    for what, dim in incidents:
        covered = dim in suite["dimensions"] or (dim == "grading_target" and suite["grading_target"] != "final_answer")
        if not covered:
            gaps.append((what, dim, METRIC[dim]))
    return gaps


if __name__ == "__main__":
    for what, dim, metric in audit():
        print(f"- {what}\n    missing: {dim}\n    add: {metric}")

  • Superseded tariff: accuracy graders accepted a plausible figure; only groundedness checks the source.
  • 14-second p95: short test prompts never exercised 18 months of account history.
  • Tripled cost: no token budget in the gate, so a prompt change passed.
  • Bypass advice and the injected PDF: no red-team or injection sets at all.
  • Refund to the wrong account: the final message was correct; the tool call wasn't, and nothing graded it.

"Add more test cases" doesn't help if they're graded on the same dimension. Four hundred more accuracy questions wouldn't have caught any of these six failures.

Writing the missing metric

Skill 4.1Specific enough to block a release.

  • Name the measure and the set: "share of claims supported by a current source, on 300 sampled production questions", not "check groundedness".
  • Give a threshold that would have failed the bad release: Anthropic asks for criteria that are specific, measurable, achievable and relevant.
  • Choose the grader: code for exact checks (token counts, latency, tool arguments), a calibrated model grader for judgement (groundedness), people for spot checks; Anthropic recommends testing an LLM grader's reliability before scaling it.
  • Add the incident itself as a regression case, so this exact failure can't return unnoticed.

Key takeaways

  • Map each production failure to the dimension that would have caught it: accuracy, groundedness, latency, cost, safety or security.
  • Check the grading target too: final text alone misses wrong actions; grade trajectories, tool arguments and intermediate outputs where they matter.
  • Test sets must mirror production inputs: lengths, turns, rare and adversarial cases.
  • Specify the missing metric concretely (measure, set, threshold, grader) so it would have failed the release, and add the incident as a regression case.
  • More cases on the same dimension don't close a coverage gap.
