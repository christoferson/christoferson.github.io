5.3: Risk Assessment and Ranking

Going through a proposed deployment category by category (how it can be attacked, how it can fail on its own, how it can run out of tokens or budget, and what it depends on) and putting the risks in order of how exposed the system really is, taking into account the controls already in place.

Overview

Skill 5.3

Risk Assessment and Ranking: "Analyzing a proposed deployment for risk categories (attack surface, failure modes, token and quota exhaustion, dependency and supply-chain risk) and ranking them by exposure."

Exam items describe a proposed deployment and ask which risk ranks highest, or which is missing from an assessment. Specific controls are covered elsewhere: injection in skill 5.2, guardrails in skill 5.1, reliability in skill 3.8.

Sources: the Claude documentation on rate and spend limits, model deprecations, prompt injection, Agent Skills and MCP security, as used on earlier pages, and paraphrased. The scoring method and register are my own; the ranking code is tested.

Running example. A city council plans a resident-services agent on its website: it answers questions, books bulky-waste collections, reports potholes through an MCP server in front of the works-management system, and reads photos and documents residents upload.

The four categories

Skill 5.3What each covers, with the Claude-specific facts that matter.

  • Attack surface: how an adversary gets in: direct jailbreaks, injected instructions in uploads, tool results and MCP responses, and what each tool would let a successful attack do.
  • Failure modes: how it goes wrong without an attacker: stale or wrong answers, hallucinated specifics, duplicate actions, tools that fail silently.
  • Token and quota exhaustion: each usage tier has a monthly spend cap; when it's reached, API usage pauses until the next month and requests return 429 without a retry-after, so retries keep failing. Rate and ramp limits also cut in on sudden surges, and a looping agent can burn budget unless turns and spend are capped.
  • Dependency and supply chain: third-party MCP servers, Skills and packages (Anthropic's guidance is to install Skills only from trusted sources and audit them); model versions that retire, with at least 60 days' notice; the platform itself, where fallback routing reduces the impact of overload.

Ranking by exposure

Skill 5.3A simple, explainable method (my framing).

  • Exposure = likelihood × impact, each on a 1–5 scale, scored after the controls already in the design. That ranks the residual risk you actually carry.
  • Likelihood rises with how reachable the path is (public website, anyone can upload) and how often the trigger happens (every storm, every release).
  • Impact rises with harm and scope: everyone affected at once (a spend cap stops the whole service) outranks a single resident's bad answer.
  • An uncontrolled risk usually tops the list, even when a better-known risk sounds more alarming, because the alarming one already has controls.

A risk register

Skill 5.3Eight risks across the four categories, ranked.

risk_register.py (risk_register.py) 
"""Rank the risks of a proposed deployment by exposure: a city council's resident-services agent.

The agent answers residents on the website, books bulky-waste collections and reports potholes via an
MCP server in front of the works-management system, and reads uploaded photos and documents.
Exposure = likelihood x impact (1-5 each), scored after the controls already in the design."""

RISKS = [
    # category, risk, likelihood, impact, existing control
    ("attack surface", "injected instructions in uploaded documents trigger bookings or reveal other residents' data",
     3, 4, "untrusted uploads go in tool results; booking tool scoped to the signed-in resident"),
    ("attack surface", "jailbreak produces offensive replies on a public council site", 3, 3, "harmlessness screen"),
    ("failure mode", "wrong bin-day or eligibility answer from stale policy pages", 4, 3, "weekly re-index"),
    ("failure mode", "agent books the same collection twice after a timeout", 3, 2, "booking tool idempotent per resident and date"),
    ("token and quota exhaustion", "monthly spend cap reached in a storm-damage surge; every request then fails with 429",
     3, 5, "none: no workspace limit, no alert, no degraded mode"),
    ("token and quota exhaustion", "a looping session burns tokens retrying a broken tool", 3, 2, "max_turns 15"),
    ("dependency and supply chain", "community MCP server package for the works system is updated with malicious code",
     2, 5, "none: installed from a public registry, auto-updated"),
    ("dependency and supply chain", "model version retired before the council's procurement cycle allows a change",
     2, 3, "deprecation notices go to one person's inbox"),
]


def rank(risks):
    scored = [(l * i, cat, risk, ctl) for cat, risk, l, i, ctl in risks]
    return sorted(scored, key=lambda r: -r[0])


if __name__ == "__main__":
    for exposure, cat, risk, ctl in rank(RISKS):
        print(f"{exposure:>2}  {cat:28} {risk}\n    existing control: {ctl}")

  • Top: the spend cap in a storm surge (15). No workspace limit, no alert and no degraded mode; when it's hit, every resident gets errors at the moment demand peaks.
  • Next: injection through uploads and stale answers (12 each). Injection is the best-known risk, but tool scoping already limits what it can do.
  • Supply chain (10): rare but severe; an auto-updated community MCP package can change under you.
  • Low: duplicate bookings (the tool is idempotent) and looping sessions (turns are capped).

Ranking by how frightening a risk sounds (injection first, always) instead of by residual exposure misses the quiet, uncontrolled risk, here a budget that runs out during the busiest week of the year.

From ranking to action

Skill 5.3What the top items would get.

  • Spend cap: a workspace spend limit below the cap with alerts, a higher tier before winter, and a degraded mode (a static page of contact routes) when limits are near.
  • Injection: screening of uploads, and keep the booking tool scoped to the signed-in resident.
  • Stale answers: re-index on page change rather than weekly, and a groundedness check in the evaluation (skill 4.1).
  • Supply chain: pin and review the MCP server version, run it with only the permissions it needs, and route deprecation notices to a team mailbox.
  • Re-score after each change, so the register stays a ranking of what's left, not of what was.

Key takeaways

  • Cover all four categories: attack surface, failure modes, token and quota exhaustion, dependency and supply chain.
  • Rank by exposure (likelihood × impact) after existing controls, so the list shows residual risk.
  • Quota risks are easy to miss: at a tier's monthly spend cap the API stops serving until the next month, and retries can't help.
  • Supply-chain risks include third-party MCP servers and Skills, model retirements and the platform itself.
  • The highest-ranked risk is often the one with no control, not the most familiar one; re-score after every mitigation.
