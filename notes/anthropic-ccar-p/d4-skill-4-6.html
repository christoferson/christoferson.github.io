4.6: Cost and Latency Optimization

Overview

Skill 4.6

Cost and Latency Optimization: "Analyzing cost and latency telemetry, including cache hit rates, to determine where spend or latency is concentrated, and specifying the optimization that reduces it without violating the stated quality floor."

Exam items show telemetry (cost by route, cache hit rates, latency percentiles) and a quality floor, and ask which change to make. Pricing a single context is skill 2.4, placing cache breakpoints skill 2.5, and trading accuracy against latency skill 3.3; this skill starts from production data.

Cut cost and latency where they’re concentrated, and keep quality above the floor

Skill 4.6What this skill asks you to do.

Questions on this skill give telemetry from a running system (cost by route, how much input is read from cache, response times) and a target, and ask which optimisation reduces cost or latency without letting quality fall below a stated floor. The skill is in reading the telemetry to find where the money and time actually go, and then choosing the lever that fits that spot.

Take a company platform with four Claude routes, which spent about $39,400 last month. Leadership wants that cut by a third, and every route must stay at or above a quality score of 0.90 on its evaluation set.

Find where the spend is before changing anything

Skill 4.6The views of the telemetry that locate it.

  • Cost by route, feature or agent. Usually a few routes carry most of the spend; start there, not with a change across the board.
  • The share of input read from cache. Anthropic reports a median of 84% for agent loops, and suggests that below about 80% something is breaking the cached part of the prompt. The Console’s Usage page charts this for each model.
  • Tokens per request, split by part: tool definitions, retrieved text, history and output, to see what’s growing.
  • Response-time percentiles per route, and whether a person is waiting at all.
  • The tail. Anthropic recommends pricing the long tail of the workload: a few very long sessions can dominate a route’s cost.
  • In Claude Code, /usage breaks usage down by Skill, subagent, plugin and MCP server, and flags long contexts and frequent cache misses.

Apply the levers in Anthropic’s order, cheapest and safest first

Skill 4.6From the guidance on optimising for cost and intelligence.

  1. Caching, which Anthropic calls usually the largest lever: answers don’t change, cost falls, and the first token arrives sooner.
  2. Token hygiene: remove unused tool definitions, trim tool results, and cut duplicated text.
  3. Batching work nobody is waiting for: half price on every token, which Anthropic calls the second-largest free lever after caching for unattended agent work.
  4. A prompt audit: instructions that cause long outputs or unnecessary steps.
  5. Then the model and effort: move up if you’re a model or two behind, otherwise try different effort levels; tune one model well before adding a second.

Worked example: four routes, four different levers

Skill 4.6The telemetry for each route, and the first lever that applies.

  • A document-comparison agent (54% of spend, 31% read from cache): far below the 80% mark, so something is breaking the cached prefix, such as a timestamp, tools listed in a changing order, or per-user text near the top. Fixing the caching cuts the cost and the 18-second response time together, without touching the answers.
  • Nightly customer letters (25% of spend): already well cached, but nobody waits for them, so batches halve the cost.
  • Document intake (16%): the cache rate is fine, but 9,000 tokens of unused tool definitions go with every call. Defer or remove them.
  • Chat triage (5%): small, but a cheaper model setting still scores 0.95 against the 0.90 floor, so it qualifies. It’s the last place to look, not the first.

The code below ranks the routes by spend and picks the first lever that applies to each:

optimize.py (optimize.py)Optional 
"""Find where spend and latency concentrate, then pick the cheapest safe optimization per hot spot.

Telemetry: one month of request logs from a company's agent platform, aggregated by route.
Order of levers follows Anthropic's "Optimizing for cost and intelligence": caching first, then token
hygiene, then batching, then a prompt audit; model or effort changes only after those, and only if the
evaluation stays above the quality floor."""

ROUTES = {  # route: monthly cost $, share of input read from cache, p95 s, interactive?, quality on eval
    "comparison agent": {"cost": 21_400, "cache_read": 0.31, "p95": 18.0, "interactive": True,  "quality": 0.93},
    "nightly letters": {"cost": 9_800, "cache_read": 0.86, "p95": 40.0, "interactive": False, "quality": 0.95},
    "chat triage":          {"cost": 1_900, "cache_read": 0.88, "p95": 2.1,  "interactive": True,  "quality": 0.97},
    "document intake":      {"cost": 6_300, "cache_read": 0.82, "p95": 6.5,  "interactive": True,  "quality": 0.91,
                             "unused_tool_tokens": 9_000},
}
QUALITY_FLOOR = 0.90


def hot_spots(routes, share=0.8):
    """The few routes that make up most of the spend (Pareto)."""
    total = sum(r["cost"] for r in routes.values())
    acc, out = 0, []
    for name, r in sorted(routes.items(), key=lambda kv: -kv[1]["cost"]):
        out.append((name, round(r["cost"] / total, 2)))
        acc += r["cost"]
        if acc / total >= share:
            break
    return out


def lever(r: dict, eval_delta: dict) -> str:
    if r["cache_read"] < 0.80:
        return "caching: find what breaks the prefix (timestamps, reordered tools, per-user text up front)"
    if r.get("unused_tool_tokens", 0) > 5_000:
        return "token hygiene: drop or defer unused tool definitions; trim tool results"
    if not r["interactive"]:
        return "batching: Message Batches at 50% off; nobody is waiting"
    downgrade = eval_delta.get("smaller model or lower effort")
    if downgrade is not None and r["quality"] + downgrade >= QUALITY_FLOOR:
        return "model/effort: cheaper setting passes the quality floor on the eval"
    return "keep: no safe lever left; revisit the prompt audit"


if __name__ == "__main__":
    print("hot spots:", hot_spots(ROUTES))
    deltas = {"chat triage": {"smaller model or lower effort": -0.02},
              "document intake": {"smaller model or lower effort": -0.04}}
    for name, r in ROUTES.items():
        print(f"{name:24} -> {lever(r, deltas.get(name, {}))}")

“Switch every route to a smaller model” is the tempting answer to a cost target. It risks the quality floor everywhere, and leaves the real problem in place: a broken cache on the route that is more than half the spend.

Know which levers can move quality, and test those

Skill 4.6Holding the quality floor.

  • Caching and batching don’t change answers, so they’re safe by construction; just check that the batch turnaround fits the schedule.
  • Token hygiene can change answers. Removing a tool or trimming a result might remove something a hard case needed, so rerun the evaluation.
  • Changing the model or effort does change answers. Accept it only when the evaluation, ideally a paired comparison, shows the new setting above the floor.
  • Keep watching afterwards: cost per route, cache rate and quality, so a later prompt change doesn’t quietly undo the saving.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A route accounts for 60% of monthly spend, and only 25% of its input is read from cache. What should be tried first?
  1. A. Move the route to a smaller model
  2. B. Find and remove what breaks the cached prefix, such as a timestamp near the top
  3. C. Lower the effort level
  4. D. Move the route to batches
Answer
B
Why
A cache read share far below about 80% means something is breaking the prefix, and fixing it cuts cost without changing answers. A smaller model or lower effort risks quality; batches don’t suit a route where users wait.
Question 2
Scenario
A nightly job that drafts reports is well cached, costs 20% of spend, and nobody reads the reports until morning. Which lever fits?
  1. A. Message Batches at half price
  2. B. Fast mode
  3. C. A larger model
  4. D. Removing caching
Answer
A
Why
Work nobody is waiting for is exactly what batching is for: half price on every token, with no effect on the answers.
Question 3
Scenario
Which change can lower quality, and must therefore be checked against the quality floor before release?
  1. A. Turning on prompt caching
  2. B. Moving unattended work to batches
  3. C. Removing tool definitions and trimming tool results
  4. D. Nothing; all cost levers are safe
Answer
C
Why
Caching and batching leave answers unchanged. Removing tools or trimming results might remove something a hard case needed, so the evaluation has to be rerun.
Question 4
Scenario
Leadership asks for a 30% cost cut across four routes. One route is 55% of the spend with a broken cache. What is the usual wrong answer?
  1. A. Fix the caching on the large route
  2. B. Switch every route to a smaller model
  3. C. Rank routes by spend before choosing levers
  4. D. Re-evaluate any model change against the floor
Answer
B
Why
A blanket switch to a smaller model risks the quality floor on every route and leaves the real problem, the broken cache on the biggest route, in place.

Key takeaways

  • Locate the spend: cost by route, the share of input read from cache, tokens by part, response times and the tail; a few routes usually dominate.
  • A cache read share well below about 80% (Anthropic’s median for agent loops is 84%) means something is breaking the prefix: fix that first.
  • Apply levers in Anthropic’s order: caching, token hygiene, batching unattended work, a prompt audit, then model or effort.
  • Caching and batching don’t change answers; token hygiene and model or effort changes must be re-evaluated against the quality floor.
  • Keep monitoring cost, cache rate and quality so the saving lasts.
