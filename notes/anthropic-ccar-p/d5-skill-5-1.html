5.1: Guardrail Placement

For each way the system could be misused, finding the point where a control actually stops it, and checking that the control doesn't also stop the customers it's meant to serve. The right guardrail is usually as close as possible to the capability being abused.

Overview

Skill 5.1

Guardrail Placement: "Analyzing guardrail placement in a system design against a described misuse path, and selecting the control that closes the path without degrading a stated legitimate use case."

Exam items describe a system, a misuse path and a legitimate use that must keep working, and ask which control to add. Injection from untrusted content is skill 5.2; human approval gates are skill 5.4; enforcing controls with hooks and sandboxes is in the developer notes (CCDV-F 7.2).

Put the guardrail where it closes the misuse path without blocking real users

Skill 5.1What this skill asks you to choose.

Questions on this skill describe a system, a way someone could misuse it, and a legitimate use that must keep working. They ask which control closes the misuse path without breaking the legitimate use. The same control in the wrong place can fail both ways: it misses the attack and blocks real customers.

Take a mobile operator’s support agent, which chats with customers and can look up accounts, change plans and issue replacement SIM cards. Red-team testing found three ways to misuse it, worked through later on this page.

Six places a guardrail can sit

Skill 5.1From the outside in.

  • Screening the input. A lightweight model checks each request before the main model sees it. Anthropic’s guidance on jailbreaks suggests a harmlessness screen with Haiku 5.5 and structured output, treating a refusal from the screen itself as a harmful verdict, plus checks against known attack patterns.
  • The prompt. Instructions on boundaries and how to decline. Useful, but the model can be persuaded, so it guides rather than enforces.
  • Authorisation inside the tool. The tool checks who is asking and what they may access, from the verified identity.
  • Gates before actions. A permission check, a hook or an approval before anything with consequences. These are code, so they hold whatever the model decides.
  • Filtering the output. Checks on what leaves the system.
  • Monitoring and response. Watching for patterns of abuse, and throttling or banning repeat offenders, as Anthropic’s guidance suggests.

Judge every candidate control on two numbers

Skill 5.1How much misuse gets through, and how much legitimate use is blocked.

  • Misuse left: the share of red-team attempts on this path that still succeed with the control in place.
  • Legitimate requests blocked: the share of real, legitimate requests the control wrongly stops.
  • Limits from the stated use. In this example, no more than 2% of misuse attempts may succeed and no more than 5% of legitimate requests may be blocked. A control that fails either limit is in the wrong place.

SIM-swap fraud: check identity inside the tool that issues the SIM

Skill 5.1An attacker with leaked personal details asks for a new SIM.

A classifier looking for fraud-like wording misses most attempts, because fraudsters sound polite. A prompt rule refusing SIM swaps stops every legitimate replacement. A step-up check inside the SIM-swap tool (a code sent to the current SIM, or ID shown in a store) closes the path and blocks only 3% of real requests, mostly people who have lost their phone, who can go to a store.

Another customer’s data: bind the account tool to the caller

Skill 5.1A caller asks for someone else’s call history.

Hiding numbers on the way out breaks legitimate answers and still leaks other details. Binding the account tool to the authenticated caller’s own account removes the path altogether: the tool can’t return anyone else’s data, whatever the model is asked.

Jailbreaks for harmful content: screen the input with a small model

Skill 5.1A user tries to get instructions for something harmful.

Blocking keywords such as “ignore previous instructions” is trivially avoided by rewording. A Haiku 5.5 harmlessness screen on the input catches nearly all attempts and wrongly blocks almost no real requests. Here the right place is the outside layer, because the request needs judgement, not a fixed rule.

The code below measures each candidate control on the three paths against the two limits and picks the one that passes both:

placement.py (placement.py)Optional 
"""Choose where a guardrail goes: the control that closes a misuse path with the least harm to legitimate use.

System: a mobile operator's account-support agent (chat) with tools get_account, update_plan, issue_sim_swap.
Each candidate control was tried against a red-team set for the misuse path and a legitimate-use set;
the numbers are the share of misuse attempts still succeeding and of legitimate requests wrongly blocked."""

PATHS = {
    "SIM-swap fraud: attacker with leaked personal details asks for a new SIM": {
        "input classifier for 'fraud' wording":          {"misuse_left": 0.40, "legit_blocked": 0.06},
        "prompt rule: refuse SIM swaps":                 {"misuse_left": 0.10, "legit_blocked": 1.00},
        "step-up check in issue_sim_swap (code sent to the current SIM, or in-store ID)":
                                                         {"misuse_left": 0.01, "legit_blocked": 0.03},
    },
    "data exposure: caller asks for another customer's call history": {
        "output filter that redacts phone numbers":      {"misuse_left": 0.25, "legit_blocked": 0.30},
        "get_account bound to the authenticated caller's account ID":
                                                         {"misuse_left": 0.00, "legit_blocked": 0.00},
    },
    "jailbreak: user tries to get instructions for harmful content": {
        "Haiku 5.5 harmlessness screen on input":        {"misuse_left": 0.02, "legit_blocked": 0.01},
        "block any message mentioning 'ignore previous'": {"misuse_left": 0.60, "legit_blocked": 0.00},
    },
}

MAX_MISUSE_LEFT, MAX_LEGIT_BLOCKED = 0.02, 0.05


def choose(controls: dict) -> str | None:
    ok = {c: m for c, m in controls.items() if m["misuse_left"] <= MAX_MISUSE_LEFT and m["legit_blocked"] <= MAX_LEGIT_BLOCKED}
    return min(ok, key=lambda c: (ok[c]["legit_blocked"], ok[c]["misuse_left"])) if ok else None


if __name__ == "__main__":
    for path, controls in PATHS.items():
        print(f"{path}\n  -> {choose(controls)}")

data exposure: caller asks for another customer's call history

“Add an instruction to the system prompt” is the usual wrong answer when a misuse path ends in a tool call. The model can be persuaded; the tool’s own check can’t.

General rules for placing guardrails

Skill 5.1What the three cases have in common.

  • Put the control at the capability. Check data access in the data tool and actions in the action tool. Filters further out guess at intent; checks at the capability enforce rights.
  • Use code for actions and a model for content. Deterministic checks suit actions; model-based screening suits content, where judgement is needed.
  • Gate the risky variant, not the whole action: a SIM swap without a step-up check, not every SIM request.
  • Layer controls, because each one fails sometimes. Anthropic’s jailbreak guidance recommends chaining safeguards and monitoring.
  • Retest legitimate use after every new control, so safety gains aren’t paid for unnoticed in usefulness.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
An airline’s agent can change bookings. Attackers with a stolen booking reference ask it to redirect refunds to their own card. Which control closes the path with least harm to real customers?
  1. A. A system-prompt rule never to change refund destinations
  2. B. A step-up check inside the refund tool, such as a code sent to the email on file
  3. C. A keyword filter on “refund”
  4. D. Refusing all refund changes
Answer
B
Why
Checking identity inside the tool that performs the change closes the path whatever the model is persuaded to do, and only affects the risky variant. A prompt rule can be talked around; a keyword filter or a blanket refusal blocks legitimate requests.
Question 2
Scenario
A healthcare chatbot can look up appointments. A user asks for another patient’s appointment by giving their name. Where should the control sit?
  1. A. In the output filter, removing names
  2. B. In the appointments tool, bound to the authenticated patient’s own record
  3. C. In the system prompt
  4. D. In monitoring only
Answer
B
Why
Binding the tool to the verified caller removes the path entirely: it can’t return another patient’s data. Output filtering guesses after the fact and can still leak; monitoring only notices afterwards.
Question 3
Scenario
A candidate control stops 99% of misuse attempts but blocks 20% of legitimate requests. The stated limits are 2% misuse and 5% blocked. What is the verdict?
  1. A. Accept it, because it stops almost all misuse
  2. B. Reject it, because it fails the limit on legitimate requests
  3. C. Accept it and monitor complaints
  4. D. Lower the limit on legitimate requests
Answer
B
Why
A control must pass both limits; one that blocks a fifth of real users is in the wrong place, however much misuse it stops.
Question 4
Scenario
Users try many rewordings to get a coding assistant to produce malware. Which guardrail fits best?
  1. A. A list of banned phrases
  2. B. A harmlessness screen on the input using a small model such as Haiku 5.5
  3. C. A longer system prompt
  4. D. Limiting answers to 100 words
Answer
B
Why
Requests needing judgement suit a model-based screen, which catches rewordings a phrase list misses. Anthropic’s jailbreak guidance describes this screen, combined with other safeguards and monitoring.

Key takeaways

  • Guardrails can sit at input screening, the prompt, authorisation inside tools, gates before actions, output filtering and monitoring.
  • Judge each candidate on misuse that still succeeds and legitimate requests it wrongly blocks; choose one that passes both limits.
  • Controls at the capability (an account tool bound to the caller, a step-up check in the SIM-swap tool) usually close a path with the least harm to real use.
  • Prompt rules and keyword filters are weak enforcement; a small-model harmlessness screen suits requests for harmful content.
  • Layer controls, monitor for repeat abuse, and retest legitimate use after every change.
