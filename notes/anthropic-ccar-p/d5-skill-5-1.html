5.1: Guardrail Placement

For each way the system could be misused, finding the point where a control actually stops it, and checking that the control doesn't also stop the customers it's meant to serve. The right guardrail is usually as close as possible to the capability being abused.

Overview

Skill 5.1

Guardrail Placement: "Analyzing guardrail placement in a system design against a described misuse path, and selecting the control that closes the path without degrading a stated legitimate use case."

Exam items describe a system, a misuse path and a legitimate use that must keep working, and ask which control to add. Injection from untrusted content is skill 5.2; human approval gates are skill 5.4; enforcing controls with hooks and sandboxes is in the developer notes (CCDV-F 7.2).

Sources: Anthropic's guidance on mitigating jailbreaks and the Agent SDK permissions documentation, checked on 20 November 2026 and paraphrased. The system and numbers are my own; the code is tested.

Running example. A mobile operator's support agent chats with customers and can look up accounts, change plans and issue replacement SIMs. Three misuse paths came out of red-team testing.

Where a guardrail can sit

Skill 5.1The layers, from the outside in.

  • Input screening: a lightweight model checks the request before the main model sees it. Anthropic's jailbreak guidance suggests a harmlessness screen with Haiku 5.5 and structured output, treating a refusal from the screen itself as a harmful verdict; also input validation against known patterns.
  • The prompt: instructions on boundaries and how to decline. Useful, but a model-level control, not an enforcement point.
  • Tool-level authorisation: the tool checks who is asking and what they may access, from the verified identity (skill 3.2).
  • Action gates: a permission check, a hook or an approval before an action with consequences; deterministic controls hold whatever the model decides.
  • Output filtering: checks what leaves the system.
  • Monitoring and response: watch for abuse patterns and throttle or ban repeat offenders, as the jailbreak guidance suggests.

Measuring a control both ways

Skill 5.1Two numbers per candidate.

  • Misuse left: the share of red-team attempts on this path that still succeed with the control in place.
  • Legitimate blocked: the share of real, legitimate requests the control wrongly stops.
  • Thresholds from the stated use: here, at most 2% misuse left and at most 5% legitimate requests blocked. A control that fails either one is the wrong placement.

Three misuse paths

Skill 5.1Candidates measured; the chooser picks the one that passes both limits.

placement.py (placement.py) 
"""Choose where a guardrail goes: the control that closes a misuse path with the least harm to legitimate use.

System: a mobile operator's account-support agent (chat) with tools get_account, update_plan, issue_sim_swap.
Each candidate control was tried against a red-team set for the misuse path and a legitimate-use set;
the numbers are the share of misuse attempts still succeeding and of legitimate requests wrongly blocked."""

PATHS = {
    "SIM-swap fraud: attacker with leaked personal details asks for a new SIM": {
        "input classifier for 'fraud' wording":          {"misuse_left": 0.40, "legit_blocked": 0.06},
        "prompt rule: refuse SIM swaps":                 {"misuse_left": 0.10, "legit_blocked": 1.00},
        "step-up check in issue_sim_swap (code sent to the current SIM, or in-store ID)":
                                                         {"misuse_left": 0.01, "legit_blocked": 0.03},
    },
    "data exposure: caller asks for another customer's call history": {
        "output filter that redacts phone numbers":      {"misuse_left": 0.25, "legit_blocked": 0.30},
        "get_account bound to the authenticated caller's account ID":
                                                         {"misuse_left": 0.00, "legit_blocked": 0.00},
    },
    "jailbreak: user tries to get instructions for harmful content": {
        "Haiku 5.5 harmlessness screen on input":        {"misuse_left": 0.02, "legit_blocked": 0.01},
        "block any message mentioning 'ignore previous'": {"misuse_left": 0.60, "legit_blocked": 0.00},
    },
}

MAX_MISUSE_LEFT, MAX_LEGIT_BLOCKED = 0.02, 0.05


def choose(controls: dict) -> str | None:
    ok = {c: m for c, m in controls.items() if m["misuse_left"] <= MAX_MISUSE_LEFT and m["legit_blocked"] <= MAX_LEGIT_BLOCKED}
    return min(ok, key=lambda c: (ok[c]["legit_blocked"], ok[c]["misuse_left"])) if ok else None


if __name__ == "__main__":
    for path, controls in PATHS.items():
        print(f"{path}\n  -> {choose(controls)}")
run_output.txt (Output) 
SIM-swap fraud: attacker with leaked personal details asks for a new SIM
  -> step-up check in issue_sim_swap (code sent to the current SIM, or in-store ID)
data exposure: caller asks for another customer's call history
  -> get_account bound to the authenticated caller's account ID
jailbreak: user tries to get instructions for harmful content
  -> Haiku 5.5 harmlessness screen on input
  • SIM-swap fraud: a fraud-wording classifier misses most attempts (fraudsters sound polite); a prompt rule refusing SIM swaps stops all legitimate replacements. A step-up check inside the SIM-swap tool (a code to the current SIM, or ID in store) closes the path and blocks only 3% of real requests, mostly people who've lost their phone, who go to a store.
  • Another customer's data: redacting numbers on the way out breaks legitimate answers and still leaks; binding the account tool to the authenticated caller removes the path entirely.
  • Jailbreaks for harmful content: a keyword block on "ignore previous" is trivially avoided; a Haiku 5.5 harmlessness screen on input catches nearly all attempts with almost no false blocks.

"Add an instruction to the system prompt" is the usual wrong answer for a misuse path that ends in a tool call. The model can be persuaded; the tool's own check can't.

Placement principles

Skill 5.1General rules (my summary).

  • Put the control at the capability: data access is checked in the data tool, actions in the action tool. Filters further out guess at intent; controls at the capability enforce rights.
  • Prefer deterministic enforcement for actions and model-based screening for content, where judgement is needed.
  • Narrow, not blanket: gate the risky variant of an action (a SIM swap without step-up), not the action itself.
  • Layer, because each control fails sometimes: Anthropic's guidance on jailbreaks recommends chaining safeguards, plus monitoring.
  • Re-test with the legitimate set after every new control, so safety gains aren't paid for silently in usefulness.

Key takeaways

  • Guardrails can sit at input screening, the prompt, tool-level authorisation, action gates, output filtering and monitoring.
  • Measure each candidate on the misuse path (attempts that still succeed) and on legitimate use (requests wrongly blocked); choose one that passes both.
  • Controls at the capability (an authorised account tool, a step-up check in the SIM-swap tool) usually close a path with the least harm to legitimate use.
  • Prompt rules and keyword filters are weak enforcement; a lightweight-model harmlessness screen suits harmful-content requests.
  • Layer controls, monitor for repeat abuse, and re-test legitimate use after every change.
