Overview

Skill 3.5

Retrieval Architecture Selection: "Selecting among retrieval architectures (pre-built RAG pipeline, agentic search with tools, full-corpus context) based on corpus characteristics, query pattern, and latency and cost limits, and, when indexing is chosen, specifying the contextual-retrieval and fallback configuration that maximizes retrieval quality within those limits."

Exam items describe a corpus (size, how often it changes), how it's queried and the limits, and ask which architecture fits, or how to configure the index. Grounding answers with citations is in the developer notes (CCDV-F 6.4); loading context progressively is skill 3.7.

Choose how Claude reaches your documents from the corpus, the questions and the limits

Skill 3.5What this skill asks you to decide.

When answers have to come from your own documents, there are three ways to get the right text in front of Claude: put all of it in the prompt, search a prepared index before each answer, or let an agent search for itself. Questions on this skill describe the documents (how big, how often they change), how they’re queried (how many questions, how deep), and the limits on time and cost, and ask which approach fits. When the answer is an index, they also ask how to set it up so it finds the right passages.

Put the whole corpus in the prompt when it’s small

Skill 3.5No retrieval step, so nothing to miss.

Anthropic’s advice is that for a knowledge base under about 200,000 tokens (roughly 500 pages), you can simply include all of it in the prompt. Prompt caching makes the repeated text cheap and fast after the first call. There is no index to build, no index to go out of date, and no search that can return the wrong passage.

Build an index when the corpus is large and questions are many

Skill 3.5A RAG pipeline: search prepared in advance, used before each answer.

The documents are split into chunks ahead of time, and each chunk is stored as an embedding (for searching by meaning) and in a keyword index. Before each answer, your code searches and passes the top passages to Claude. It’s fast and cheap per question, which suits high volumes and fairly stable material. The answers are only as good as the index: it can miss the passage that matters, and it’s out of date until changed documents are indexed again.

Let an agent search when data changes fast or questions need digging

Skill 3.5Agentic search: the model decides what to look at, at run time.

The agent has search and read tools and follows leads as it goes, keeping only short references until it needs the full text (Anthropic calls this “just in time” context; Claude Code uses grep and glob on files rather than an index). It always reads the current data and handles investigations that take several steps. Anthropic notes that searching at run time is slower than retrieving prepared results, and that an agent without good guidance can waste context on dead ends.

A hybrid retrieves some material up front for speed and lets the agent explore further when needed; Anthropic suggests it suits material that changes less often.

Worked example: three collections of documents, three answers

Skill 3.5Size, rate of change, query volume and limits, weighed together.

  • A travel and expenses policy: 120,000 tokens, updated each quarter. It fits in the prompt with room to spare, so include it whole and cache it; there’s no index to maintain.
  • Product documentation: 8 million tokens across 40 releases, 50,000 questions a day, and a 3-second limit. It’s far too big for the prompt, and too many questions with too tight a limit for an agent to search each time. Build an index, with contextual retrieval and reranking (below).
  • Service logs and runbooks: they change every hour, and are used for a few dozen deep investigations a day where minutes are acceptable. An index would always be behind, so let an agent search the current data.

The code below makes these choices; its size and volume thresholds are only illustrative:

retrieval_choice.py (retrieval_choice.py)Optional 
"""Choose a retrieval architecture from corpus, query pattern and limits; then configure the indexed one.

Anthropic's Contextual Retrieval post: under about 200,000 tokens, put the whole knowledge base in the
prompt (with caching). Contextual embeddings + contextual BM25 + reranking cut top-20 retrieval failures
by 67% in its tests. Its context-engineering post: just-in-time agentic search avoids stale indexes but
is slower than retrieving pre-computed data."""


def choose(corpus_tokens: int, changes: str, queries_per_day: int, latency_s: float) -> str:
    if corpus_tokens <= 200_000:
        return "full corpus in context, cached"
    if changes == "hourly" or latency_s >= 30:
        return "agentic search with tools (grep, query, read)"
    return "indexed RAG: contextual embeddings + contextual BM25 + reranking"


def retrieve(query: str, bm25, dense, rerank, agentic, k: int = 20, pool: int = 150, floor: float = 0.35):
    """Hybrid retrieval with two fallbacks. bm25/dense return [(chunk_id, score)]; rerank returns [(chunk_id, score)]."""
    candidates = {}
    for source in (bm25(query, pool), dense(query, pool)):         # both indexes built on contextualised chunks
        for cid, s in source:
            candidates[cid] = s                                     # union only: the reranker sets the order
    if not candidates:
        return {"route": "agentic", "chunks": agentic(query)}       # fallback 1: nothing matched, search live
    ranked = rerank(query, list(candidates))[:k]                    # rerank the pool, keep the top k
    if ranked[0][1] < floor:
        return {"route": "agentic", "chunks": agentic(query)}       # fallback 2: weak best match
    return {"route": "index", "chunks": [cid for cid, _ in ranked]}


CONTEXT_PROMPT = """<document>{doc}</document>
Here is a chunk from the document: <chunk>{chunk}</chunk>
Give a short context (50-100 tokens) that situates this chunk within the document, for search retrieval.
Answer only with the context."""   # run once per chunk at indexing time, with the document cached


if __name__ == "__main__":
    for name, args in [("travel and expenses policy", (120_000, "quarterly", 300, 5)),
                       ("product documentation, 40 releases", (8_000_000, "weekly", 50_000, 3)),
                       ("service logs and runbooks", (30_000_000, "hourly", 40, 120))]:
        print(f"{name:36} -> {choose(*args)}")

Give each chunk its context before indexing it

Skill 3.5Contextual retrieval: why chunks lose their meaning, and the fix.

What goes wrong. A chunk such as “revenue grew 3% over the previous quarter” doesn’t say which company or which quarter, so neither a search by meaning nor a keyword search can match it to a question that names them.

What fixes it. Before indexing, have Claude write a short note (usually 50 to 100 tokens) placing each chunk in its document, and add it to the front of the chunk. Doing this for the embeddings is called contextual embeddings; doing it for the keyword index is called contextual BM25.

What it achieved in Anthropic’s tests, measured as how often the right chunk was missing from the top 20: contextual embeddings cut those failures by 35%, adding contextual BM25 cut them by 49%, and adding reranking as well cut them by 67%.

What it costs. Writing the notes is a one-time cost when indexing, about $1.02 per million document tokens in Anthropic’s test, because each document is cached while its chunks are processed.

Other settings that matter: chunk size, where chunks break and how much they overlap; the embedding model; and how many chunks to pass (20 worked best of 5, 10 and 20 in Anthropic’s tests). Measure on your own questions, with recall at 20.

Search two ways, rerank, and fall back when matches are weak

Skill 3.5The rest of a good index configuration.

  • Two searches, one pool. Keyword search catches exact terms such as part numbers and error codes; search by meaning catches paraphrases. Both run on the chunks with their added context, and the results are combined.
  • Rerank, then cut. A reranker orders a large pool (Anthropic reranked 150) and the top 20 go to the model. It adds time and cost, so check that the limits allow it.
  • Fall back when nothing matches, to agentic search or to a clarifying question, rather than answering from nothing.
  • Fall back when the best match is weak. A minimum score sends low-confidence questions the same way; set it using labelled questions.
  • Keep the index current. Re-index changed documents as often as they change, and track recall over time.

“Build a vector index” for a 100-page policy adds a part that can miss the answer and go out of date, when the whole document fits in the prompt. “Let the agent search” for 50,000 questions a day under a 3-second limit fails on time and cost.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A legal team wants an assistant that answers questions about its 90-page contract playbook, which is revised twice a year. About 200 questions a day; answers within 10 seconds. Which retrieval approach fits best?
  1. A. A vector index with hybrid search and reranking
  2. B. The whole playbook in the prompt, cached
  3. C. An agent that searches the playbook with grep and read tools
  4. D. Fine-tuning a model on the playbook
Answer
B
Why
Ninety pages is far under about 200,000 tokens, so the whole playbook fits in the prompt and caching makes the repeated text cheap. An index adds a step that can miss the answer and must be rebuilt after each revision; agentic search is slower for no benefit; fine-tuning isn’t a retrieval approach and is out of scope.
Question 2
Scenario
An on-call team investigates incidents using logs and runbooks that change every few minutes. There are about 30 investigations a day, each allowed several minutes. Which approach fits best?
  1. A. Agentic search over the live logs and runbooks
  2. B. A vector index rebuilt every night
  3. C. The whole log archive in the prompt
  4. D. A keyword index with a strict score floor
Answer
A
Why
The data changes faster than any index can be rebuilt, the volume is low and the time limit is generous, which is exactly where an agent reading the current data fits. A nightly index is always behind; the archive is far too large for the prompt.
Question 3
Scenario
An indexed help-centre assistant often fails questions such as “what changed in the 4.2 release?” because the matching chunk says only “this release adds offline mode”. Which change addresses the cause?
  1. A. Retrieve 50 chunks instead of 20
  2. B. Switch to a larger model
  3. C. Add a short note to each chunk, before indexing, saying which document and release it comes from
  4. D. Lower the reranker’s score floor
Answer
C
Why
The chunk has lost its context: nothing in it names release 4.2, so neither search can match the question. Contextual retrieval adds that context before indexing. Retrieving more or lowering the floor passes more unrelated chunks; a larger model can’t answer from a passage it never receives.
Question 4
Scenario
An indexed assistant sometimes answers confidently from passages that don’t contain the answer, when the best match scores low. What should the design add?
  1. A. A minimum match score, below which the question goes to agentic search or a clarifying question
  2. B. A system prompt telling the model never to guess
  3. C. A larger embedding model
  4. D. Caching of the retrieved passages
Answer
A
Why
A score floor detects weak matches and routes them to a fallback instead of answering from nothing. A prompt instruction doesn’t stop the weak passages arriving; a different embedding model may help recall but doesn’t handle the case when nothing good is found; caching changes cost, not what is retrieved.

Key takeaways

  • Under about 200,000 tokens, put the whole corpus in the prompt and cache it: no retrieval step to fail.
  • Large, fairly stable collections with many questions and tight limits: a prepared index. Fast-changing data and deep, occasional investigations: agentic search. A hybrid for mostly stable material that sometimes needs exploring.
  • Contextual retrieval adds 50 to 100 tokens of document context to each chunk before indexing it both ways; with reranking it cut missed chunks in the top 20 by 67% in Anthropic’s tests, for a one-time indexing cost.
  • Combine keyword and meaning-based search, rerank a large pool down to about 20, and fall back to agentic search or a clarifying question when nothing matches or the best match is weak.
  • Measure recall at 20 on your own questions, and re-index as often as the documents change.
