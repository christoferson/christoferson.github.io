3.5: Retrieval Architecture Selection

Deciding how Claude gets at a body of knowledge: all of it in the prompt, an index searched before each answer, or an agent that looks things up as it goes, and, when an index is the answer, setting it up so it finds the right passages and has somewhere to go when it doesn't.

Overview

Skill 3.5

Retrieval Architecture Selection: "Selecting among retrieval architectures (pre-built RAG pipeline, agentic search with tools, full-corpus context) based on corpus characteristics, query pattern, and latency and cost limits, and, when indexing is chosen, specifying the contextual-retrieval and fallback configuration that maximizes retrieval quality within those limits."

Exam items describe a corpus (size, how often it changes), how it's queried and the limits, and ask which architecture fits, or how to configure the index. Grounding answers with citations is in the developer notes (CCDV-F 6.4); loading context progressively is skill 3.7.

Sources: Anthropic's engineering posts on Contextual Retrieval (September 2024) and on effective context engineering for agents (September 2025), checked on 20 November 2026 and paraphrased. The corpora, thresholds and code are my own; the code is tested with fake retrievers.

Three architectures

Skill 3.5What each is good at.

  • Full corpus in context: no retrieval step to fail. Anthropic's advice: for a knowledge base under about 200,000 tokens (roughly 500 pages), just include all of it in the prompt, with prompt caching making it cheaper and faster.
  • Indexed RAG pipeline: chunks embedded (and indexed for keyword search) ahead of time, searched before each answer. Fast and cheap per query at high volume; quality depends on the index, and the index can go stale.
  • Agentic search with tools: the agent searches, reads and follows leads at run time, keeping only lightweight references until it needs the content (the "just in time" approach; Claude Code uses grep and glob instead of an index). Always current and good at multi-step investigation, but Anthropic notes run-time exploration is slower than retrieving pre-computed data, and an unguided agent can waste context on dead ends.
  • Hybrid: retrieve some content up front for speed and let the agent explore further; Anthropic suggests it suits less dynamic content.

Choosing by corpus and queries

Skill 3.5Three corpora, three answers.

retrieval_choice.py (retrieval_choice.py)Optional 
"""Choose a retrieval architecture from corpus, query pattern and limits; then configure the indexed one.

Anthropic's Contextual Retrieval post: under about 200,000 tokens, put the whole knowledge base in the
prompt (with caching). Contextual embeddings + contextual BM25 + reranking cut top-20 retrieval failures
by 67% in its tests. Its context-engineering post: just-in-time agentic search avoids stale indexes but
is slower than retrieving pre-computed data."""


def choose(corpus_tokens: int, changes: str, queries_per_day: int, latency_s: float) -> str:
    if corpus_tokens <= 200_000:
        return "full corpus in context, cached"
    if changes == "hourly" or latency_s >= 30:
        return "agentic search with tools (grep, query, read)"
    return "indexed RAG: contextual embeddings + contextual BM25 + reranking"


def retrieve(query: str, bm25, dense, rerank, agentic, k: int = 20, pool: int = 150, floor: float = 0.35):
    """Hybrid retrieval with two fallbacks. bm25/dense return [(chunk_id, score)]; rerank returns [(chunk_id, score)]."""
    candidates = {}
    for source in (bm25(query, pool), dense(query, pool)):         # both indexes built on contextualised chunks
        for cid, s in source:
            candidates[cid] = s                                     # union only: the reranker sets the order
    if not candidates:
        return {"route": "agentic", "chunks": agentic(query)}       # fallback 1: nothing matched, search live
    ranked = rerank(query, list(candidates))[:k]                    # rerank the pool, keep the top k
    if ranked[0][1] < floor:
        return {"route": "agentic", "chunks": agentic(query)}       # fallback 2: weak best match
    return {"route": "index", "chunks": [cid for cid, _ in ranked]}


CONTEXT_PROMPT = """<document>{doc}</document>
Here is a chunk from the document: <chunk>{chunk}</chunk>
Give a short context (50-100 tokens) that situates this chunk within the document, for search retrieval.
Answer only with the context."""   # run once per chunk at indexing time, with the document cached


if __name__ == "__main__":
    for name, args in [("travel and expenses policy", (120_000, "quarterly", 300, 5)),
                       ("product documentation, 40 releases", (8_000_000, "weekly", 50_000, 3)),
                       ("service logs and runbooks", (30_000_000, "hourly", 40, 120))]:
        print(f"{name:36} -> {choose(*args)}")

Contextual retrieval

Skill 3.5Why chunks lose meaning, and the fix.

  • The problem: a chunk such as "revenue grew 3% over the previous quarter" doesn't say which company or quarter, so neither embeddings nor keyword search can match it to a question that names them.
  • The fix: before indexing, generate a short context for each chunk (usually 50–100 tokens) situating it in its document, and prepend it. Doing this for embeddings is contextual embeddings; doing it for the keyword index is contextual BM25. The prompt in the code shows the idea.
  • Results reported by Anthropic (failure to retrieve the relevant chunk in the top 20): contextual embeddings cut failures by 35%; adding contextual BM25, by 49%; adding reranking as well, by 67%.
  • Cost: generating the contexts is a one-time indexing cost, about $1.02 per million document tokens in Anthropic's test, because each document is cached while its chunks are processed.
  • Other settings that matter: chunk size, boundaries and overlap; the embedding model; how many chunks to pass (20 worked best of 5, 10 and 20 in their tests); measure with recall at 20 on your own questions.

Hybrid search, reranking and fallbacks

Skill 3.5The retrieve function above, explained.

  • Two indexes, one pool: keyword search catches exact terms (part numbers, error codes); embeddings catch paraphrases. Both run on the contextualised chunks, and their results are combined.
  • Rerank, then cut: a reranker orders a large pool (Anthropic reranked 150) and the top 20 go to the model. It adds latency and cost, so check the limit allows it.
  • Fallback when nothing matches: route to agentic search (or a clarifying question) rather than answering from nothing.
  • Fallback when the best match is weak: a score floor sends low-confidence queries the same way; tune the floor on labelled questions.
  • Keep it current: re-index changed documents on a schedule matched to how often they change, and track recall over time.

"Build a vector index" for a 100-page policy adds a component that can miss the answer and go stale; the whole document fits in context. And "let the agent search" for 50,000 queries a day at 3 seconds fails the latency and cost limits.

Key takeaways

  • Under about 200,000 tokens, put the whole corpus in context and cache it; no retrieval step to fail.
  • Large, fairly stable corpora with high query volume and tight latency: an indexed pipeline. Fast-changing data and deep, low-volume investigations: agentic search. Hybrid for mostly stable content that sometimes needs exploration.
  • Contextual retrieval prepends 50–100 tokens of document context to each chunk before embedding and keyword indexing; with reranking it cut top-20 retrieval failures by 67% in Anthropic's tests, for a one-time indexing cost.
  • Configure hybrid keyword plus embedding search, rerank a large pool to about 20, and fall back to agentic search or clarification when nothing matches or the best match is weak.
  • Measure recall at 20 on your own questions, and re-index as often as the corpus changes.
