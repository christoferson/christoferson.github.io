Overview

Skill 5.5

Architectural Controls for Compliance Obligations: "Evaluating candidate architectural controls (data residency and deployment surface, retention and zero-data-retention configuration, PII detection and redaction, audit logging, tenant isolation) against a stated compliance obligation, and selecting the control set that evidences the obligation."

Exam items state an obligation and offer control sets, some of which address a different obligation. Choosing a surface and runtime under residency constraints is skill 1.6; key handling and authorisation are skill 3.2.

Choose the controls that meet the obligation, and the evidence that proves it

Skill 5.5What this skill asks you to select.

Questions on this skill state a compliance obligation and offer several sets of controls, some of which address a different obligation entirely. You choose the set that meets the stated one and that you can prove you meet. Each control below answers one kind of obligation; retention and residency in particular are easy to confuse.

Contract terms are the final word on what an arrangement covers; the sections below follow Anthropic’s documentation.

Zero data retention: Anthropic doesn’t keep your content

Skill 5.5For an obligation that the vendor must not store customer content.

What it is. Under zero data retention (ZDR), Anthropic doesn’t store prompts or responses at rest once the response is returned. It’s an arrangement made per organisation, through Anthropic’s sales team. Without it, Anthropic states that conversation content isn’t retained by default, except for models that require 30-day retention, and that retained data isn’t used for training without permission.

What it doesn’t cover. The Console; Managed Agents, unless fully self-hosted; features marked ineligible, such as code execution; and the Fable 5.x and Mythos models, which require 30-day retention. Organisations under ZDR also can’t call the API from a browser.

The evidence. The contract and the account team’s confirmation; an allowlist in the code that builds requests, so only eligible features and models are used, checked automatically in CI; calls made only from your back end.

HIPAA readiness: for health information

Skill 5.5For an obligation to protect patients’ health information (PHI).

What it is. A signed business associate agreement (BAA) and a HIPAA-enabled organisation on the Claude API, or Microsoft Foundry with its HIPAA configuration. The API rejects features that aren’t eligible with a 400 error.

What it doesn’t cover. It isn’t available on Claude Platform on AWS, and it doesn’t cover Claude Code, use of the Console, or most beta features. Don’t put health information in JSON schemas: compiled schemas are cached without the same protections.

The evidence. The BAA and the HIPAA setting in the Console; the 400 errors that show ineligible features were blocked; schema review in code review; and redaction of health information before it reaches logs and analytics, with sampled audits.

Data residency: where the model runs

Skill 5.5For an obligation that processing stays in a region.

What it is. The inference_geo setting chooses where inference runs (us or global on the Claude API), and a workspace’s allowed inference geos can restrict it so us is enforced. Workspace geo decides where data is stored (US only today). On Bedrock and Google-managed Vertex, the cloud provider’s regional endpoints decide.

The evidence. Each response’s usage.inference_geo field, logged, shows where inference ran; an export of the workspace settings shows the restriction.

Your own controls: redaction, audit logs and keeping clients apart

Skill 5.5The parts of compliance that live in your architecture, not Anthropic’s.

What they are. Removing personal information before logs and analytics; recording who accessed what, with the client involved; and separating clients by workspace, API key, retrieval index and tool permissions.

The evidence. An inventory of keys by workspace; integration tests showing that client A can’t read client B’s documents; and a log-retention policy with sample queries. Isolation is shown by a test, not asserted.

The code below maps four obligations (no vendor storage, health information under HIPAA, inference in the US, and per-client separation with an access audit) to their controls and evidence:

compliance_controls.py (compliance_controls.py)Optional 
"""Map each compliance obligation to the architectural controls that evidence it, and catch conflicts.

Facts encoded (Claude API data retention and data residency pages, Nov 2026):
- ZDR: per organization, by arrangement; not for Console, Managed Agents (except self-hosted), Fable 5.x /
  Mythos models (30-day retention required), code execution and other features marked ineligible.
- HIPAA readiness: BAA + HIPAA-enabled organization on the Claude API; not on Claude Platform on AWS,
  Bedrock or Claude Code; ineligible features return 400; no PHI in JSON schemas.
- Residency: inference_geo "us" per request, workspace allowed_inference_geos to enforce it.
- Flagged content may be retained up to 2 years under any arrangement."""

CONTROLS = {
    "no vendor storage of customer content": [
        ("ZDR arrangement for the organization", "contract + account-team confirmation"),
        ("only ZDR-eligible features and models", "request builder allowlist; CI check"),
        ("calls from our back end only", "ZDR orgs can't call the API from browsers"),
    ],
    "PHI under HIPAA": [
        ("signed BAA and HIPAA-enabled organization on the Claude API", "Console HIPAA card, BAA version"),
        ("eligible features only", "the API returns 400 for ineligible ones; keep the error as evidence"),
        ("no PHI in JSON schemas, file names or metadata", "schema review in code review"),
        ("PHI redaction before logs and analytics", "logging pipeline config + sampled audit"),
    ],
    "inference in the US": [
        ("inference_geo 'us' on every request", "usage.inference_geo logged per response"),
        ("workspace allowed_inference_geos = ['us']", "workspace settings export"),
    ],
    "per-client separation and access audit": [
        ("one workspace and scoped key per client", "key inventory by workspace"),
        ("per-client retrieval index and tool scopes", "integration tests: client A can't read client B"),
        ("audit log of who accessed what, with client ID", "log retention policy + sample queries"),
    ],
}


def plan(obligations: list[str], design: dict) -> dict:
    controls = [c for o in obligations for c in CONTROLS[o]]
    conflicts = []
    if "no vendor storage of customer content" in obligations:
        if design["model"].startswith(("claude-fable", "claude-mythos")):
            conflicts.append(f"{design['model']} requires 30-day retention: not available under ZDR without express authorization")
        if design["runtime"] == "managed agents (cloud)":
            conflicts.append("Managed Agents keeps session transcripts until deleted: not covered by ZDR")
        if "code_execution" in design["features"]:
            conflicts.append("code execution is not ZDR-eligible")
    if "PHI under HIPAA" in obligations and design["surface"] in ("claude platform on aws", "bedrock"):
        conflicts.append(f"HIPAA readiness isn't available through Anthropic on {design['surface']}")
    return {"controls": controls, "conflicts": conflicts,
            "residual": "flagged content may still be retained up to 2 years (disclose in the DPIA)"}

Catch the design choices an obligation rules out

Skill 5.5Conflicts the code above checks for.

  • ZDR with a Fable 5.2 model: the model requires 30-day retention, so it isn’t available under ZDR without express authorisation.
  • ZDR with Managed Agents hosted by Anthropic: session transcripts are kept until they are deleted.
  • ZDR with code execution: it isn’t an eligible feature.
  • HIPAA on Claude Platform on AWS: HIPAA readiness isn’t available there.

The test gives a design with all four conflicts and checks that each is flagged, and that a compliant design returns none.

“Use ZDR to keep data in the US” or “use US inference to stop the vendor storing data” each picks a real control for the wrong obligation. Retention and residency are separate settings, with separate evidence.

State what no configuration removes

Skill 5.5The remaining risk to disclose.

  • Flagged content. Even under ZDR or HIPAA arrangements, content flagged by Anthropic’s trust and safety systems may be kept for up to 2 years, and data may be kept where the law requires.
  • Third-party integrations. MCP servers, search providers and other tools handle data on their own terms, outside these arrangements.
  • Your own copies. Logs, caches, evaluation sets and traces hold the same data; redact or minimise them under the same obligation.

Record these in the data protection impact assessment, rather than claiming the obligation is met absolutely.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A contract requires that Anthropic keep no copy of customer prompts or responses. Which control set addresses it?
  1. A. Set inference_geo to us
  2. B. A ZDR arrangement, eligible features and models only, and calls from the back end
  3. C. Encrypt the prompts before sending them
  4. D. Use a HIPAA-enabled organisation
Answer
B
Why
Vendor storage is a retention obligation, met by ZDR with only eligible features and models. Residency settings decide where processing happens, not whether content is kept; HIPAA readiness answers a different obligation.
Question 2
Scenario
A design under ZDR proposes Fable 5.2 and code execution. What should the review say?
  1. A. Both are fine under ZDR
  2. B. Both conflict: Fable 5.x requires 30-day retention and code execution isn’t ZDR-eligible
  3. C. Only the model choice matters
  4. D. ZDR covers everything except the Console
Answer
B
Why
Fable 5.x models require 30-day retention, so they aren’t available under ZDR without express authorisation, and code execution isn’t an eligible feature. Both have to change for the design to meet the obligation.
Question 3
Scenario
A health-tech company wants HIPAA coverage for patient data and plans to buy Claude through Claude Platform on AWS. What is the problem?
  1. A. None
  2. B. HIPAA readiness isn’t available on Claude Platform on AWS
  3. C. HIPAA needs the US inference geo only
  4. D. HIPAA covers Claude Code by default
Answer
B
Why
HIPAA readiness requires a BAA and a HIPAA-enabled organisation on the Claude API (or Foundry with its HIPAA configuration); it isn’t available on Claude Platform on AWS.
Question 4
Scenario
An auditor asks for proof that inference ran in the US for every request last quarter. What is the best evidence?
  1. A. A statement in the security policy
  2. B. The logged usage.inference_geo field from each response, plus the workspace’s allowed-geo setting
  3. C. The ZDR contract
  4. D. A screenshot of the Console home page
Answer
B
Why
The platform reports where inference ran on each response, and the workspace restriction shows it was enforced. A policy statement is a claim; the ZDR contract concerns retention, not location.

Key takeaways

  • Match each obligation to the controls that address it: ZDR for vendor storage, HIPAA readiness (a BAA and a HIPAA-enabled organisation) for health data, inference_geo with workspace restrictions for residency, and your own redaction, audit logs and client separation for the rest.
  • Pair every control with evidence: contracts and settings, allowlists and CI checks, logged usage.inference_geo, isolation tests.
  • Catch conflicts: Fable 5.x models, Anthropic-hosted Managed Agents and code execution aren’t covered by ZDR; HIPAA readiness isn’t available on Claude Platform on AWS; no health data in JSON schemas.
  • Retention and residency are different obligations with different controls.
  • Disclose what remains: flagged content (up to 2 years), legal holds, third-party tools and your own logs.
