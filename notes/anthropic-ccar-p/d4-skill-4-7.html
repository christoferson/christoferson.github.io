4.7: Model Version Migration

When a model you depend on is being retired, or a newer one is on offer, reading the timeline and the regression results together and choosing what to do: stay put for now, adjust the prompts, fix the evaluation, or wait, without running out of time.

Overview

Skill 4.7

Model Version Migration: "Evaluating migration readiness from a model deprecation timeline and regression results for a candidate version, and selecting the response (pin, re-tune prompts, re-baseline evaluations, or defer) that manages behavioral drift within the timeline."

Exam items give a deprecation date, today's date and a regression report, and ask which response fits. Planning releases with regression evaluations from the developer side is CCDV-F 5.2; designing the comparison itself is skill 4.4.

When a model is being retired, choose how to move off it

Skill 4.7What this skill asks you to decide.

Questions on this skill give a model’s retirement timeline and the regression results for its replacement, and ask which response manages the change: keep using the current model (pin), adjust the prompts (re-tune), fix the evaluation (re-baseline), or postpone the switch (defer). The timeline decides how much choice you have; the kind of regression decides the rest.

Know the lifecycle rules

Skill 4.7What Anthropic’s deprecations page commits to.

  • Four stages. Active (fully supported); legacy (no more updates); deprecated (still works but isn’t recommended, has a replacement and a retirement date, and may be less reliable); retired (requests fail).
  • Notice. At least 60 days before a publicly released model retires, by email and in the docs.
  • Whose dates. The published dates apply to platforms Anthropic operates (the Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud, Microsoft Foundry). Bedrock and Google-managed Vertex set their own schedules.
  • Pinned model IDs. Every model ID is a fixed snapshot, including the IDs without dates from the 4.6 generation on. Pinning keeps behaviour stable, but only until that snapshot retires.
  • A live example. Claude Sonnet 4.5 was deprecated on 30 September 2026 and retires on 30 November 2026, with Sonnet 5.5 as its replacement.
  • Finding every caller. The Console’s Usage page exports usage by API key and model.

Inside the notice window, migrate: fix what you can and guard the rest

Skill 4.7The timeline overrides the other choices.

Once the retirement date is close, pinning or deferring only lasts until requests start failing. Migrate before the date, fix the regressions that can be fixed, and put a guard (human review, or a fallback path) on the segments that can’t be fixed in time.

Re-tune the prompts when the regression is behaviour you can fix in the prompt

Skill 4.7Longer answers, different formatting, more literal instruction following.

A new model often writes differently: longer, with different formatting, or following instructions more literally. These are usually fixable in the prompt. Adjust it, then rerun the regression suite.

Re-baseline the evaluation when reviewers prefer the candidate

Skill 4.7A lower score isn’t always a worse model.

If the candidate scores lower but the people reviewing its outputs prefer them, the evaluation is probably the problem: the graders or the golden answers reward the old model’s style. Fix the evaluation, and recheck any LLM judge against people, before deciding.

Pin and defer when retirement is distant and the candidate isn’t ready

Skill 4.7For regressions in capability that a prompt may not fix.

If the current model has no retirement date close by, and the candidate regresses on something that matters, keep the pinned current model, report the regression with examples, and test again on the next release.

Worked example: three migrations, three responses

Skill 4.7The timeline and the regression together decide each one.

  • A support bot on Sonnet 4.5, ten days before retirement. Sonnet 5.5 is better overall but four points worse in two segments, because its replies got longer. That’s fixable in the prompt: re-tune the length instructions now and migrate before 30 November.
  • Extraction on Opus 4.6, with retirement not before February 2027 and no deprecation notice yet, so at least 60 days’ warning remains. Opus 5.5 drops seven points on nested tables, a capability problem a prompt change may not fix: pin Opus 4.6, defer the switch, report the regression and retest later.
  • Summaries on Opus 4.8. The candidate scores three points lower, but reviewers prefer its summaries; the golden answers reward the old phrasing. Re-baseline the evaluation first.

The test adds a fourth case: a serious capability regression with only ten days left can’t be deferred, so the answer is to migrate and add a guard for the affected segment. The code below applies these rules:

"""Decide the migration response from the deprecation timeline and the candidate's regression results.

Responses: pin (stay on the pinned current model for now), re-tune prompts (fix specific regressions
for the new model), re-baseline evaluations (the eval, not the model, is wrong), defer (no move yet).
Dates from the model deprecations page (Nov 2026): Sonnet 4.5 retires November 30, 2026, replacement
Sonnet 5.5; Opus 4.6 not sooner than February 5, 2027. Notice is at least 60 days."""
from datetime import date


def respond(today: date, retirement: date | None, regression: dict) -> list[str]:
    """regression: overall delta, worst segment delta, cause of the worst drop, human review of it."""
    days = (retirement - today).days if retirement else None
    plan = []
    if regression.get("human_prefers_candidate"):
        plan.append("re-baseline evaluations: graders or golden answers encode the old model's style")
    if regression["worst_segment"] < -0.02 and regression.get("cause") in ("verbosity", "format", "instruction literalness"):
        plan.append(f"re-tune prompts: {regression['cause']} regression is prompt-fixable; rerun the suite")
    serious = regression["worst_segment"] < -0.05 and regression.get("cause") not in ("verbosity", "format", "instruction literalness")
    if days is not None and days <= 30:
        plan.append(f"migrate before {retirement}: {days} days left, retired models' requests fail")
        if serious:
            plan.append("escalate: a capability regression with no time to defer; add a guard (human review or a fallback path) for that segment")
    elif serious:
        plan.append("pin the current model and defer the switch; report the regression with examples; retest on the next release")
    elif not plan:
        plan.append("migrate: no meaningful regression")
    return plan


SCENARIOS = {
    "support bot on Sonnet 4.5 -> Sonnet 5.5": (date(2026, 11, 20), date(2026, 11, 30),
        {"overall": 0.03, "worst_segment": -0.04, "cause": "verbosity"}),
    "extraction on Opus 4.6 -> Opus 5.5": (date(2026, 11, 20), date(2027, 2, 5),
        {"overall": -0.02, "worst_segment": -0.07, "cause": "nested table extraction"}),
    "summaries on Opus 4.8 -> Opus 5.5": (date(2026, 11, 20), date(2027, 5, 28),
        {"overall": -0.03, "worst_segment": -0.03, "cause": "style", "human_prefers_candidate": True}),
}

if __name__ == "__main__":
    for name, (today, retire, reg) in SCENARIOS.items():
        print(name)
        for step in respond(today, retire, reg):
            print("  -", step)

“Pin the retiring model to avoid drift” works only until its retirement date, after which requests fail. “Migrate as soon as a new model ships”, without a regression run, swaps a known system for an untested one.

A migration checklist

Skill 4.7From the deprecations page, plus practice.

  • Find every use: the Console’s usage export by key and model; in Claude Code, check which model actually sits behind each alias, and change it everywhere, including in subagent definitions.
  • Read the new model’s notes on what’s new and how to migrate: breaking changes (for example, sampling parameters such as temperature are rejected under API version 2026-10-21) and changed defaults such as effort.
  • Run the regression suite on the candidate, per segment, with a paired comparison, and try the effort levels.
  • Test early. Anthropic’s advice is to test well before the retirement date; a newer model may also differ in tone and length.
  • Roll out gradually, and keep the old model available until the new one has run cleanly in production, if it hasn’t retired yet.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A support bot runs on a model that retires in 12 days. Its replacement is better overall but writes longer replies, lowering two segments. What should the team do?
  1. A. Pin the current model until the replacement improves
  2. B. Re-tune the prompt for length and migrate before the retirement date
  3. C. Defer the decision to next quarter
  4. D. Re-baseline the evaluation
Answer
B
Why
Inside the notice window, pinning or deferring only lasts until requests fail. Longer replies are fixable in the prompt, so re-tune and migrate before the date.
Question 2
Scenario
A candidate model scores 3 points lower on a summarisation evaluation, but reviewers prefer its summaries in side-by-side checks. What is the right response?
  1. A. Reject the candidate
  2. B. Re-baseline the evaluation, because its golden answers reward the old model’s style
  3. C. Pin the current model permanently
  4. D. Raise the candidate’s effort
Answer
B
Why
When people prefer the lower-scoring outputs, the evaluation is measuring the old style, not quality. Fix it (and recheck any judge) before deciding.
Question 3
Scenario
A model has no deprecation notice and retires no earlier than in 10 months. Its replacement drops 7 points on nested tables, which a prompt change hasn’t fixed. What fits?
  1. A. Migrate now and accept the drop
  2. B. Pin the current model, defer the switch, report the regression and retest later
  3. C. Re-baseline the evaluation
  4. D. Remove the nested-table cases from the suite
Answer
B
Why
With retirement distant and a capability regression that a prompt doesn’t fix, keep the current model and retest on the next release. Removing the failing cases hides the problem.
Question 4
Scenario
A team says it will avoid behaviour changes by pinning its current model ID forever. Why doesn’t that work?
  1. A. Pinned IDs change behaviour every week
  2. B. A pinned snapshot keeps behaviour stable only until it retires, after which requests fail
  3. C. Pinning isn’t supported
  4. D. Pinning raises the price
Answer
B
Why
Every model ID is a fixed snapshot with a retirement date. Pinning delays change; it doesn’t prevent the migration, so the team still needs a tested path to the replacement.

Key takeaways

  • Lifecycle: active, legacy, deprecated (works, has a retirement date), retired (requests fail); at least 60 days’ notice; Bedrock and Google-managed Vertex set their own dates.
  • Re-tune prompts for behaviour a prompt can fix; re-baseline the evaluation when reviewers prefer the candidate; pin and defer when retirement is distant and the candidate isn’t ready.
  • Inside the notice window the timeline wins: migrate, fix what you can, guard what you can’t.
  • Pinning a retiring model only delays the problem until its retirement date.
  • Find every caller (usage export, aliases, subagents), read the breaking changes, run per-segment regressions, test early and roll out gradually.
