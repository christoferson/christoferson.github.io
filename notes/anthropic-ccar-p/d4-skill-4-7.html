4.7: Model Version Migration

When a model you depend on is being retired, or a newer one is on offer, reading the timeline and the regression results together and choosing what to do: stay put for now, adjust the prompts, fix the evaluation, or wait, without running out of time.

Overview

Skill 4.7

Model Version Migration: "Evaluating migration readiness from a model deprecation timeline and regression results for a candidate version, and selecting the response (pin, re-tune prompts, re-baseline evaluations, or defer) that manages behavioral drift within the timeline."

Exam items give a deprecation date, today's date and a regression report, and ask which response fits. Planning releases with regression evaluations from the developer side is CCDV-F 5.2; designing the comparison itself is skill 4.4.

Sources: the Claude model deprecations page and models overview, checked on 20 November 2026 and paraphrased. The scenarios and regression figures are my own; the decision code is tested.

The lifecycle rules

Skill 4.7What the deprecations page commits to.

  • Stages: active (fully supported); legacy (no more updates); deprecated (still works, not recommended, has a replacement and a retirement date, likely less reliable); retired (requests fail).
  • Notice: at least 60 days before retirement for publicly released models, by email and in the docs.
  • Whose dates: the published dates apply to Anthropic-operated platforms (Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud, Microsoft Foundry); Bedrock and Google-managed Vertex set their own schedules. Claude Code on the Claude API follows the API's dates.
  • Pinned IDs: every model ID is a pinned snapshot, including the dateless IDs from the 4.6 generation on; pinning keeps behaviour stable only until that snapshot retires.
  • A live example: Claude Sonnet 4.5 was deprecated on 30 September 2026 and retires on 30 November 2026, with Sonnet 5.5 as the replacement.
  • Finding usage: the Console's Usage page exports usage by API key and model, to find every caller of a deprecated model.

The four responses

Skill 4.7When each one fits (my mapping).

  • Pin: keep the current pinned model while the candidate regresses on something that matters, as long as the current model isn't near retirement.
  • Re-tune prompts: the regression is behavioural and fixable in the prompt: longer answers, different formatting, more literal instruction following. Adjust, then rerun the suite.
  • Re-baseline evaluations: the candidate scores lower but people reviewing the outputs prefer it, because graders or golden answers encode the old model's style. Fix the evaluation (and re-check the judge, skill 4.3) before deciding.
  • Defer: postpone the switch when the current model has a distant retirement date and the candidate isn't ready; report the regression and retest on the next release.
  • The timeline overrides: inside the notice window there's no deferring; migrate, fix what can be fixed, and guard what can't.

Three migrations

Skill 4.7Timeline plus regression, three answers.

migration.py (migration.py) 
"""Decide the migration response from the deprecation timeline and the candidate's regression results.

Responses: pin (stay on the pinned current model for now), re-tune prompts (fix specific regressions
for the new model), re-baseline evaluations (the eval, not the model, is wrong), defer (no move yet).
Dates from the model deprecations page (Nov 2026): Sonnet 4.5 retires November 30, 2026, replacement
Sonnet 5.5; Opus 4.6 not sooner than February 5, 2027. Notice is at least 60 days."""
from datetime import date


def respond(today: date, retirement: date | None, regression: dict) -> list[str]:
    """regression: overall delta, worst segment delta, cause of the worst drop, human review of it."""
    days = (retirement - today).days if retirement else None
    plan = []
    if regression.get("human_prefers_candidate"):
        plan.append("re-baseline evaluations: graders or golden answers encode the old model's style")
    if regression["worst_segment"] < -0.02 and regression.get("cause") in ("verbosity", "format", "instruction literalness"):
        plan.append(f"re-tune prompts: {regression['cause']} regression is prompt-fixable; rerun the suite")
    serious = regression["worst_segment"] < -0.05 and regression.get("cause") not in ("verbosity", "format", "instruction literalness")
    if days is not None and days <= 30:
        plan.append(f"migrate before {retirement}: {days} days left, retired models' requests fail")
        if serious:
            plan.append("escalate: a capability regression with no time to defer; add a guard (human review or a fallback path) for that segment")
    elif serious:
        plan.append("pin the current model and defer the switch; report the regression with examples; retest on the next release")
    elif not plan:
        plan.append("migrate: no meaningful regression")
    return plan


SCENARIOS = {
    "support bot on Sonnet 4.5 -> Sonnet 5.5": (date(2026, 11, 20), date(2026, 11, 30),
        {"overall": 0.03, "worst_segment": -0.04, "cause": "verbosity"}),
    "extraction on Opus 4.6 -> Opus 5.5": (date(2026, 11, 20), date(2027, 2, 5),
        {"overall": -0.02, "worst_segment": -0.07, "cause": "nested table extraction"}),
    "summaries on Opus 4.8 -> Opus 5.5": (date(2026, 11, 20), date(2027, 5, 28),
        {"overall": -0.03, "worst_segment": -0.03, "cause": "style", "human_prefers_candidate": True}),
}

if __name__ == "__main__":
    for name, (today, retire, reg) in SCENARIOS.items():
        print(name)
        for step in respond(today, retire, reg):
            print("  -", step)

  • Support bot on Sonnet 4.5: ten days to retirement. Sonnet 5.5 is better overall but four points worse in two segments because replies got longer: re-tune the length instructions now and migrate before 30 November.
  • Extraction on Opus 4.6: retirement not before February 2027 and no deprecation notice yet, so at least 60 days' warning remains. Opus 5.5 drops seven points on nested tables, a capability problem a prompt tweak may not fix: pin 4.6, defer, report, retest.
  • Summaries on Opus 4.8: a three-point drop, but reviewers prefer the new summaries; the golden answers reward the old phrasing. Re-baseline the evaluation first.
  • The test adds a fourth: a serious capability regression with ten days left can't be deferred; migrate and add a guard (human review or a fallback path) for the affected segment.

"Pin the retiring model to avoid drift" works only until its retirement date, after which requests fail. And "migrate as soon as a new model ships" without a regression run trades a known system for an untested one.

A migration checklist

Skill 4.7From the deprecations page, plus practice.

  • Find every use: the Console usage export by key and model; in Claude Code, check the actual model behind aliases and change it everywhere, including subagent definitions.
  • Read the new model's "what's new" and migration notes: breaking changes (for example, sampling parameters such as temperature are rejected under API version 2026-10-21) and default changes such as effort.
  • Run the regression suite on the candidate, per segment, with the paired design from skill 4.4, and sweep effort.
  • Test early: Anthropic's advice is to test well before the retirement date; a newer model may also differ in tone and length.
  • Roll out gradually and keep the old model reachable until the new one has run cleanly in production, if it hasn't retired.

Key takeaways

  • Lifecycle: active, legacy, deprecated (works, has a retirement date), retired (requests fail); at least 60 days' notice; partner platforms set their own dates.
  • Pin when the candidate regresses and time allows; re-tune prompts for behavioural regressions; re-baseline evaluations when reviewers prefer the candidate; defer when retirement is distant and the candidate isn't ready.
  • Inside the notice window, the timeline wins: migrate, fix what you can, guard what you can't.
  • Pinning a retiring model only delays the problem until its retirement date.
  • Find every caller (usage export, aliases, subagents), read the breaking changes, run segment-level regressions, test early and roll out gradually.
