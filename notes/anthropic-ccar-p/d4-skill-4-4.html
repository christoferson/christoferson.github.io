4.4: Experimental Design for Configuration Comparison

Setting up an A/B comparison of two prompts or models so that a difference in scores reflects the change and not luck: the same cases for both, enough runs per case to average out the model's randomness, enough cases to detect the effect you care about, and error bars on the answer.

Overview

Skill 4.4

Experimental Design for Configuration Comparison: "Applying an experimental design that, within a stated sample and cost budget, yields an interpretable comparison of two candidate prompt or model configurations, including the number of trials per case needed to separate the configuration effect from run-to-run variance."

Exam items give two configurations, a budget and some pilot numbers, and ask which design produces a trustworthy comparison, or whether an observed difference is real. Choosing what to measure is skill 4.2; judge reliability is skill 4.3.

Sources: Anthropic's research post "A statistical approach to model evaluations" (November 2024), checked on 20 November 2026 and paraphrased. The variance formula is standard statistics in my words; the scenario and code are my own and tested.

Running example. A legal-operations team extracts clauses from supplier contracts and wants to know whether a revised prompt beats the current one. They have 400 labelled contracts, $600 to spend on runs at about $0.05 each, and outputs vary from run to run.

Anthropic's five recommendations

Skill 4.4From the statistics post.

  • Use the Central Limit Theorem: treat the score as an estimate of the average over all possible questions, report its standard error, and give a 95% interval as the mean plus or minus 1.96 standard errors.
  • Cluster standard errors when cases come in related groups (several questions on one passage, several clauses from one contract); clustered errors can be more than three times the naive ones.
  • Reduce variance within questions: resample each answer several times and use the per-question average.
  • Analyse paired differences: when both configurations answer the same questions, compare them question by question; the post reports question-level scores of frontier models correlating between 0.3 and 0.7, a "free" reduction in variance.
  • Use power analysis to decide how many questions, and how many resamples, are needed to detect the difference you care about.

Two sources of variance

Skill 4.4Why you run each case more than once.

  • Between cases: some contracts are hard, some easy. More cases reduces it; pairing removes much of it, because a hard contract is hard for both configurations.
  • Within a case: the same configuration on the same contract scores differently from run to run. Only more runs per case reduces it.
  • For a paired difference averaged over k runs: its variance is about 2 × between-case variance × (1 − correlation) + 2 × within-case variance ÷ k. The first term shrinks with pairing and more cases; the second with more runs.
  • The detectable difference at 5% significance and 80% power is about 2.8 × √(variance ÷ number of cases).

Planning within a budget

Skill 4.4400 labelled cases, $600, pilot estimates of both variances.

experiment.py (experiment.py)Optional 
"""Compare two prompt configurations for a contract-clause extractor within a fixed budget.

Following Anthropic's statistical approach to evals: run both configurations on the same cases and
analyse paired differences; resample each case several times to average out run-to-run noise; size
the experiment with a power calculation; report the mean difference with its standard error and CI.

Variance model for a case's score difference between configurations (A - B), averaged over k runs:
    var(d) = 2 * sb2 * (1 - rho) + 2 * sw2 / k
sb2 = between-case variance, sw2 = run-to-run variance within a case, rho = correlation of the two
configurations' case-level scores (Anthropic reports 0.3-0.7 between frontier models)."""
from math import sqrt
from statistics import mean, stdev

Z_ALPHA, Z_POWER = 1.96, 0.84          # 5% two-sided test, 80% power


def detectable_effect(n_cases: int, k: int, sb2: float, sw2: float, rho: float) -> float:
    var_d = 2 * sb2 * (1 - rho) + 2 * sw2 / k
    return (Z_ALPHA + Z_POWER) * sqrt(var_d / n_cases)


def plan(budget: float, cost_per_run: float, sb2: float, sw2: float, rho: float,
         labelled_cases: int, max_k: int = 10) -> dict:
    """Split a budget between cases (capped by how many labelled cases exist) and runs per case."""
    best = None
    for k in range(1, max_k + 1):
        n = min(labelled_cases, int(budget / (2 * k * cost_per_run)))   # 2 configurations x k runs per case
        if n < 30:
            break
        mde = detectable_effect(n, k, sb2, sw2, rho)
        if best is None or mde < best["detectable_effect"]:
            best = {"cases": n, "runs_per_case": k, "detectable_effect": round(mde, 3)}
    return best


def analyse(scores_a: dict, scores_b: dict) -> dict:
    """scores_x: case_id -> list of run scores. Paired on case, averaged over runs."""
    diffs = [mean(scores_a[c]) - mean(scores_b[c]) for c in scores_a]
    m, se = mean(diffs), stdev(diffs) / sqrt(len(diffs))
    return {"mean_diff": round(m, 3), "se": round(se, 3), "ci95": (round(m - 1.96 * se, 3), round(m + 1.96 * se, 3)),
            "significant": abs(m) > 1.96 * se}


if __name__ == "__main__":
    # 400 labelled cases, $600 budget, $0.05 per run; pilot estimates: sb2 0.06, sw2 0.04, rho 0.5
    for k in (1, 2, 3, 5, 8):
        print(f"k={k}: detectable difference {detectable_effect(400, k, 0.06, 0.04, 0.5):.3f}, "
              f"cost ${400 * 2 * k * 0.05:.0f}")
    print("plan:", plan(600, 0.05, 0.06, 0.04, 0.5, labelled_cases=400))
    print("same 400 cases, k=3, but unpaired (different cases per configuration):",
          f"{detectable_effect(400, 3, 0.06, 0.04, 0.0):.3f}")

  • One run per case can only detect a difference of about 5 points, too coarse if the revision is expected to gain 3 or 4.
  • Three runs bring it to about 4 points for $120; beyond that, gains shrink (eight runs reach 3.7 points for $320). The rest of the budget is better spent labelling more cases, if any can be labelled.
  • Pairing matters as much as resampling: the same 400 cases with three runs but split between configurations (unpaired) can only detect about 5.4 points.
  • Estimate the variances first: a small pilot (a few dozen cases, several runs each) gives the numbers the plan needs.

Reading the result

Skill 4.4What an interpretable comparison reports.

  • The mean paired difference, its standard error and its 95% interval, as the analyse function returns; plus the correlation between configurations, as the post recommends.
  • An interval that excludes zero is evidence of a real difference; one that straddles zero means the experiment can't tell, not that the configurations are equal.
  • Cluster by contract if several scored clauses come from the same contract.
  • Fix everything else: same model version, temperature or effort, judge and cases for both arms; only the configuration under test changes.

"Run each configuration once on all 400 cases and compare the two accuracy figures" confounds the change with run-to-run noise and gives no error bar; a 2-point difference from that design can easily be luck.

Key takeaways

  • Anthropic's statistics post: report standard errors and 95% intervals, cluster related cases, resample answers per question, analyse paired differences, and use power analysis.
  • Run both configurations on the same cases; pairing removes case-difficulty variance (question-level correlations of 0.3–0.7 between frontier models).
  • Run each case several times to average out run-to-run variance; returns diminish after a few runs.
  • Plan within the budget: estimate both variances from a pilot, then choose cases and runs per case to detect the effect size that matters.
  • Report the mean difference with its interval; an interval spanning zero means "can't tell", and everything except the configuration must stay fixed.
