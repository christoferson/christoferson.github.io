4.4: Experimental Design for Configuration Comparison

Setting up an A/B comparison of two prompts or models so that a difference in scores reflects the change and not luck: the same cases for both, enough runs per case to average out the model's randomness, enough cases to detect the effect you care about, and error bars on the answer.

Overview

Skill 4.4

Experimental Design for Configuration Comparison: "Applying an experimental design that, within a stated sample and cost budget, yields an interpretable comparison of two candidate prompt or model configurations, including the number of trials per case needed to separate the configuration effect from run-to-run variance."

Exam items give two configurations, a budget and some pilot numbers, and ask which design produces a trustworthy comparison, or whether an observed difference is real. Choosing what to measure is skill 4.2; judge reliability is skill 4.3.

Compare two configurations in a way that can actually tell them apart

Skill 4.4What this skill asks you to design.

Model outputs vary from run to run, and some test cases are harder than others, so two configurations can score differently by luck alone. Questions on this skill give two candidate prompts or models, a number of test cases and a budget, and ask for an experiment that gives an answer you can trust, including how many times to run each case.

Take a legal-operations team that extracts clauses from supplier contracts and wants to know whether a revised prompt beats the current one. It has 400 labelled contracts, $600 to spend at about $0.05 a run, and outputs that vary between runs. The sections below follow Anthropic’s research on the statistics of model evaluations.

Report every score with its uncertainty

Skill 4.4A score from a test set is an estimate, not a fact.

  • Treat the score as an estimate. A test set is a sample of all the questions the system could face, so its score estimates the true average. Report the standard error with it, and a 95% interval: the mean plus or minus 1.96 standard errors.
  • Group related cases. When cases come in groups that are alike, such as several clauses from the same contract, the errors are related too. Clustered standard errors account for that; Anthropic found they can be more than three times larger than the simple ones.

Two sources of noise: hard cases and run-to-run variation

Skill 4.4Why the number of runs per case is part of the design.

  • Between cases. Some contracts are hard and some easy. More cases reduce this noise, and comparing both configurations on the same cases removes much of it, because a hard contract is hard for both.
  • Within a case. The same configuration on the same contract scores differently from one run to the next. Only running each case more times reduces this.

For a comparison on the same cases, averaged over k runs each, the noise in the difference is roughly: 2 × (between-case variance) × (1 − the correlation between the two configurations), plus 2 × (within-case variance) ÷ k. The first part shrinks with pairing and more cases; the second with more runs. The smallest difference you can reliably detect, at 5% significance and 80% power, is about 2.8 times the square root of that noise divided by the number of cases.

Run both configurations on the same cases

Skill 4.4Pairing: a free reduction in noise.

When both configurations answer the same cases, compare them case by case and analyse the differences. Anthropic reports that the case-level scores of frontier models are correlated at between 0.3 and 0.7, so pairing removes a large part of the between-case noise at no extra cost. In the contract example, the same 400 cases with three runs each can detect a difference of about 4 points paired, but only about 5.4 points if each configuration gets different cases.

Run each case several times, but not many

Skill 4.4Resampling, and where it stops paying.

Running each case several times and averaging per case reduces the run-to-run noise. The gain shrinks quickly: in the contract example, one run per case can only detect a difference of about 5 points, three runs bring it to about 4 points for $120, and eight runs reach only 3.7 points for $320. Beyond a few runs, the budget does more good spent on labelling more cases, if any can be labelled.

Plan the experiment within the budget before running it

Skill 4.4Power analysis: how many cases and runs to detect the difference that matters.

  • Estimate both kinds of noise first, with a small pilot: a few dozen cases, several runs each.
  • Decide what difference matters. If the revision is expected to gain 3 or 4 points, an experiment that can only detect 5 points can’t answer the question.
  • Choose cases and runs per case so the detectable difference is below that size, within the budget.

The code below works out the detectable difference and the cost for different numbers of runs per case, and for an unpaired design:

experiment.py (experiment.py)Optional 
"""Compare two prompt configurations for a contract-clause extractor within a fixed budget.

Following Anthropic's statistical approach to evals: run both configurations on the same cases and
analyse paired differences; resample each case several times to average out run-to-run noise; size
the experiment with a power calculation; report the mean difference with its standard error and CI.

Variance model for a case's score difference between configurations (A - B), averaged over k runs:
    var(d) = 2 * sb2 * (1 - rho) + 2 * sw2 / k
sb2 = between-case variance, sw2 = run-to-run variance within a case, rho = correlation of the two
configurations' case-level scores (Anthropic reports 0.3-0.7 between frontier models)."""
from math import sqrt
from statistics import mean, stdev

Z_ALPHA, Z_POWER = 1.96, 0.84          # 5% two-sided test, 80% power


def detectable_effect(n_cases: int, k: int, sb2: float, sw2: float, rho: float) -> float:
    var_d = 2 * sb2 * (1 - rho) + 2 * sw2 / k
    return (Z_ALPHA + Z_POWER) * sqrt(var_d / n_cases)


def plan(budget: float, cost_per_run: float, sb2: float, sw2: float, rho: float,
         labelled_cases: int, max_k: int = 10) -> dict:
    """Split a budget between cases (capped by how many labelled cases exist) and runs per case."""
    best = None
    for k in range(1, max_k + 1):
        n = min(labelled_cases, int(budget / (2 * k * cost_per_run)))   # 2 configurations x k runs per case
        if n < 30:
            break
        mde = detectable_effect(n, k, sb2, sw2, rho)
        if best is None or mde < best["detectable_effect"]:
            best = {"cases": n, "runs_per_case": k, "detectable_effect": round(mde, 3)}
    return best


def analyse(scores_a: dict, scores_b: dict) -> dict:
    """scores_x: case_id -> list of run scores. Paired on case, averaged over runs."""
    diffs = [mean(scores_a[c]) - mean(scores_b[c]) for c in scores_a]
    m, se = mean(diffs), stdev(diffs) / sqrt(len(diffs))
    return {"mean_diff": round(m, 3), "se": round(se, 3), "ci95": (round(m - 1.96 * se, 3), round(m + 1.96 * se, 3)),
            "significant": abs(m) > 1.96 * se}


if __name__ == "__main__":
    # 400 labelled cases, $600 budget, $0.05 per run; pilot estimates: sb2 0.06, sw2 0.04, rho 0.5
    for k in (1, 2, 3, 5, 8):
        print(f"k={k}: detectable difference {detectable_effect(400, k, 0.06, 0.04, 0.5):.3f}, "
              f"cost ${400 * 2 * k * 0.05:.0f}")
    print("plan:", plan(600, 0.05, 0.06, 0.04, 0.5, labelled_cases=400))
    print("same 400 cases, k=3, but unpaired (different cases per configuration):",
          f"{detectable_effect(400, 3, 0.06, 0.04, 0.0):.3f}")

Read the result for what it can and can’t show

Skill 4.4What an interpretable comparison reports.

  • Report the mean difference between the configurations, its standard error and its 95% interval, and the correlation between them.
  • An interval that excludes zero is evidence of a real difference. One that includes zero means the experiment can’t tell, not that the configurations are equal.
  • Group by contract if several scored clauses come from the same contract.
  • Keep everything else fixed: the same model version, effort, judge and cases for both; only the thing under test changes.

“Run each configuration once on all 400 cases and compare the two accuracy figures” mixes the change up with run-to-run noise and gives no error bar. A 2-point difference from that design can easily be luck.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Two prompts are each run once on 400 test cases. Prompt B scores 81% and prompt A 79%. Outputs vary between runs. What can the team conclude?
  1. A. B is better by 2 points
  2. B. Nothing yet: there’s no error bar, and a single run mixes the change with run-to-run noise
  3. C. A is better, because it is the current prompt
  4. D. They are equal
Answer
B
Why
Without a standard error and interval, and with only one run per case, a 2-point gap can easily be luck. The comparison needs pairing, several runs per case and an interval before anything is concluded.
Question 2
Scenario
A team has 300 labelled cases and a fixed budget. Which design detects a smaller difference between two configurations?
  1. A. Each configuration on a different 150 cases
  2. B. Both configurations on the same 300 cases, compared case by case
  3. C. Each configuration on 300 new unlabelled cases
  4. D. One configuration run many times, the other once
Answer
B
Why
Pairing removes much of the noise from case difficulty, because a hard case is hard for both; splitting the cases throws that benefit away.
Question 3
Scenario
An evaluation shows a mean improvement of 1.5 points with a 95% interval from −0.8 to 3.8 points. How should it be reported?
  1. A. The new configuration is better
  2. B. The configurations are proven equal
  3. C. The experiment can’t tell them apart yet; more cases or runs are needed to detect a difference this small
  4. D. The old configuration is better
Answer
C
Why
An interval that includes zero means the experiment can’t distinguish the two, not that they are equal. A larger or better-designed experiment is needed if a 1.5-point difference matters.
Question 4
Scenario
A pilot shows that most of the noise comes from the same case scoring differently from run to run. What reduces it?
  1. A. More different cases only
  2. B. More runs per case, averaged
  3. C. A different judge
  4. D. Removing the hardest cases
Answer
B
Why
Run-to-run noise within a case is reduced only by running each case more times and averaging; more cases reduce the between-case part. Removing hard cases biases the result.

Key takeaways

  • Report each score with its standard error and a 95% interval, and cluster related cases.
  • Run both configurations on the same cases: pairing removes case-difficulty noise (case-level correlations of 0.3 to 0.7 between frontier models).
  • Run each case several times to average out run-to-run noise; returns shrink after a few runs.
  • Plan within the budget: estimate both kinds of noise from a pilot, then choose cases and runs per case to detect the difference that matters.
  • Report the mean difference with its interval; an interval that includes zero means “can’t tell”, and everything except the change under test must stay fixed.
