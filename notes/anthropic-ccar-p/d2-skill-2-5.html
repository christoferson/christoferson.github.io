2.5: Cache Breakpoints and Reusable Packaging

Arranging a prompt that runs again and again so its unchanging parts come first, putting cache breakpoints where each layer stops changing, matching their lifetimes to how often the calls actually arrive, and packaging reusable content so it isn't carried when it isn't needed.

Overview

Skill 2.5

Cache Breakpoints and Reusable Packaging: "Applying cache breakpoints and modular or Skill-based packaging to a repeated prompt sequence so that stable content precedes dynamic content and reuse is maximized across the stated call pattern."

Exam items describe a repeated prompt and how calls arrive, and ask where to put breakpoints, which TTL to use, or why the cache hit rate is low. Pricing a context is skill 2.4; the developer's view of cost diagnosis with caching is in CCDV-F 5.3.

Sources: the Claude prompt caching documentation, "Optimizing for cost and intelligence" and the Agent Skills documentation, checked on 19 and 20 November 2026 and paraphrased. The assistant and simulation are my own; the simulation simplifies the caching rules and is tested.

Running example. An engineering firm's tender-review assistant: analysts ask about ten questions about each tender, a few minutes apart, against the firm's 12,000-token review guide and a 40,000-token set of tender documents.

Breakpoint rules

Skill 2.5What cache_control actually does.

  • A breakpoint marks the end of a cached prefix. Writes happen only at breakpoints; on a later request the system finds the longest prefix already cached.
  • Up to four breakpoints, so sections that change at different rates can be cached separately. Each breakpoint looks back up to 20 blocks for a match.
  • Order is fixed: tools, then system, then messages. A change to an earlier part invalidates everything after it; changing tool definitions invalidates the whole cache.
  • Lifetimes: 5 minutes by default (writes at 1.25 times input price) or 1 hour (2 times); a 1-hour entry must come before any 5-minute entry. The lifetime is measured from the start of the request.
  • Minimum size: 512 tokens on current models; below that, nothing is cached and no error is raised.
  • Automatic caching (a top-level cache_control) places the breakpoint on the last block; it's the wrong choice when that block changes every request.

Layering by rate of change

Skill 2.5Most stable first, one breakpoint per layer.

  • Layer 1, changes rarely: tool definitions and the firm-wide guide; same for everyone all day. 1-hour breakpoint.
  • Layer 2, changes per work item: the tender's documents; same for a run of questions. 5-minute breakpoint.
  • Layer 3, changes per call: the question, after the last breakpoint.
  • Keep volatile values out of stable layers: timestamps, user names, request IDs and "today's date" at the top of a system prompt make every prefix unique. Put them after the last breakpoint, or leave them out.

A morning's calls, two layouts

Skill 2.5Same content, same calls; only the order and breakpoints differ.

tender_cache.py (tender_cache.py)Optional 
"""An engineering firm's tender-review assistant: lay out the prompt so the call pattern reuses the cache.

Call pattern (one analyst's morning): 3 tenders, about 10 questions each, a few minutes apart.
Layers, most stable first:
  1. firm review guide + tools      12,000 tokens, same all day   -> 1-hour breakpoint
  2. this tender's documents        40,000 tokens, same per tender -> 5-minute breakpoint
  3. the question                       150 tokens, new every call -> after the last breakpoint
Simplified model of the prompt-caching rules: a breakpoint's prefix is read if the same prefix was
written or read within its TTL, otherwise written; anything after a changed block is uncached."""

GUIDE, TENDER, QUESTION = 12_000, 40_000, 150


def good_request(tender_id: str, docs: str, question: str) -> dict:
    return {
        "model": "claude-sonnet-5-5", "max_tokens": 2048,
        "system": [
            {"type": "text", "text": "<firm review guide>", "cache_control": {"type": "ephemeral", "ttl": "1h"}},
            {"type": "text", "text": f"<tender id='{tender_id}'>{docs}</tender>", "cache_control": {"type": "ephemeral"}},
        ],
        "messages": [{"role": "user", "content": question}],
    }


def bad_request(tender_id: str, docs: str, question: str, now: str) -> dict:
    return {  # a timestamp first and the question before the documents: nothing stable leads the prompt
        "model": "claude-sonnet-5-5", "max_tokens": 2048,
        "system": [{"type": "text", "text": f"Current time: {now}\n<firm review guide>",
                    "cache_control": {"type": "ephemeral"}}],
        "messages": [{"role": "user", "content": f"{question}\n<tender id='{tender_id}'>{docs}</tender>"}],
    }


def simulate(calls, layout: str) -> dict:
    """calls: list of (minute, tender_id). Returns tokens billed as write, read and plain input."""
    seen, tot = {}, {"write": 0, "read": 0, "input": 0}

    def hit(key, ttl, minute):
        ok = key in seen and minute - seen[key] <= ttl
        seen[key] = minute                         # a write or a read refreshes the entry
        return ok

    for minute, tender in calls:
        if layout == "good":
            tot["read" if hit("guide", 60, minute) else "write"] += GUIDE
            tot["read" if hit(("tender", tender), 5, minute) else "write"] += TENDER
            tot["input"] += QUESTION
        else:                                      # timestamp changes every call: the prefix never matches
            tot["write"] += GUIDE
            tot["input"] += TENDER + QUESTION
    return tot


def cost(t: dict) -> float:                        # Sonnet 5.5: write $2.50, read $0.10, input $2.00 per MTok
    return round((t["write"] * 2.50 + t["read"] * 0.10 + t["input"] * 2.00) / 1e6, 2)


MORNING = [(m, "T1") for m in range(0, 30, 3)] + [(m, "T2") for m in range(30, 60, 3)] + \
          [(m, "T3") for m in range(60, 100, 4)]

if __name__ == "__main__":
    for layout in ("bad", "good"):
        t = simulate(MORNING, layout)
        share = t["read"] / sum(t.values())
        print(f"{layout:4}  write {t['write']:>8,}  read {t['read']:>8,}  input {t['input']:>8,}  "
              f"cache-read share {share:.0%}  cost ${cost(t)}")
run_output.txt (Output)Optional 
bad   write  360,000  read        0  input 1,204,500  cache-read share 0%  cost $3.31
good  write  132,000  read 1,428,000  input    4,500  cache-read share 91%  cost $0.48
  • Bad layout: a timestamp opens the system prompt and the documents follow the question, so no prefix ever repeats: $3.31 for the morning, 0% read from cache.
  • Good layout: guide (1 hour), then tender (5 minutes), then question: the guide is written once, each tender once, and everything else is read: $0.48, 91% read from cache.
  • A useful benchmark: Anthropic reports that agent loops read a median 84% of their input from cache, and suggests that below about 80% you look for something breaking the prefix.

Matching TTLs to the call pattern

Skill 2.5The stated call pattern decides the lifetime.

  • Calls closer together than 5 minutes: the default lifetime is enough, and each read keeps the entry warm.
  • Gaps longer than 5 minutes but under an hour (an analyst who reads for ten minutes between questions): the 5-minute entry expires and the 40,000 tokens are written again; a 1-hour entry costs more to write (2 times rather than 1.25 times) but saves the rewrites. The test shows one pause of nine minutes adding a second write.
  • Shared across users: the firm guide serves every analyst, so a 1-hour entry at the front is reused by everyone's calls.
  • Batches: caching within the Message Batches API is best-effort, so don't count on cache hits there.

Modular and Skill-based packaging

Skill 2.5Don't carry what most calls don't need.

  • Modules: split the guide into a core module (always loaded, cached) and specialist modules added only for the tenders that need them, each in its own block in a fixed order so combinations still share the core prefix.
  • Skills: package procedures that apply to some tenders (structural steel checks, environmental compliance) as Agent Skills. Only each Skill's name and description, about 100 tokens, sits in context until it's needed; the body and any scripts load when a request triggers it.
  • Skills' requirements: on the API they run in the code execution container (no network access, up to 20 Skills a request); custom Skills are shared workspace-wide through the Skills API; they aren't eligible for zero data retention or HIPAA.
  • Stability still matters: changing which tools or Skills are present changes the front of the prompt; keep the set fixed for a workload rather than toggling per call.

"Add a breakpoint after every block" doesn't help: there are only four, writes cost more than plain input, and a breakpoint after content that changes every call writes a cache that's never read.

Key takeaways

  • Order content by rate of change: tools and firm-wide guidance, then per-item material, then the per-call request; one breakpoint at the end of each stable layer (four at most).
  • Keep volatile values (timestamps, names, IDs) out of the stable layers; one changing token at the front makes every prefix unique.
  • Choose TTLs from the call pattern: 5 minutes for bursts, 1 hour (2x write) when gaps are longer or content is shared across users; 1-hour entries come first.
  • Measure the share of input read from cache; Anthropic's median for agent loops is 84%, and below about 80% something is breaking the prefix.
  • Package rarely needed procedures as modules or Skills (about 100 tokens each until triggered), and keep the tool and Skill set stable across calls.
