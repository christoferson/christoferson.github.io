2.5: Cache Breakpoints and Reusable Packaging

Arranging a prompt that runs again and again so its unchanging parts come first, putting cache breakpoints where each layer stops changing, matching their lifetimes to how often the calls actually arrive, and packaging reusable content so it isn't carried when it isn't needed.

Overview

Skill 2.5

Cache Breakpoints and Reusable Packaging: "Applying cache breakpoints and modular or Skill-based packaging to a repeated prompt sequence so that stable content precedes dynamic content and reuse is maximized across the stated call pattern."

Exam items describe a repeated prompt and how calls arrive, and ask where to put breakpoints, which TTL to use, or why the cache hit rate is low. Pricing a context is skill 2.4; the developer's view of cost diagnosis with caching is in CCDV-F 5.3.

Put what stays the same first, so every call can reuse it

Skill 2.5What this skill asks you to arrange.

When the same long material is sent with call after call (a reference guide, a set of documents), prompt caching lets later calls read it from a cache at a fraction of the price instead of paying for it in full again. But the cache only covers the beginning of the prompt, up to the point where something changes. Questions on this skill describe a repeated prompt and how the calls arrive, and ask where to put the cache breakpoints, how long the cache should last, or why little is being read from the cache. The answer is almost always about order: what stays the same must come before what changes.

How cache breakpoints work

Skill 2.5What cache_control actually does.

  • A breakpoint marks the end of a cached section. You add cache_control to a block, and everything up to and including that block can be cached. Caches are written only at breakpoints; on a later request, the system finds the longest beginning that is already cached.
  • You can use up to four breakpoints, so sections that change at different rates can be cached separately. Each breakpoint looks back up to 20 blocks for an earlier match.
  • The order is fixed: tools, then the system prompt, then the messages. A change in an earlier part invalidates everything after it, and changing the tool definitions invalidates the whole cache.
  • Two lifetimes. The default is 5 minutes, and writing costs 1.25 times the normal input price; a 1-hour cache costs 2 times to write. A 1-hour section must come before any 5-minute section. The lifetime is counted from the start of the request.
  • A minimum size. Sections under 512 tokens on current models aren’t cached, and no error says so.
  • Automatic caching (one cache_control at the top level of the request) puts the breakpoint on the last block. That’s the wrong choice when the last block changes on every request.

Order the prompt by how often each part changes

Skill 2.5Most stable first, with one breakpoint at the end of each stable layer.

Take a document-review assistant. Reviewers ask about ten questions about each set of documents, a few minutes apart, against a shared 12,000-token review guide and the set’s 40,000 tokens of documents.

  • Layer 1, changes rarely: the tool definitions and the shared review guide, the same for everyone all day. Breakpoint at its end, with a 1-hour lifetime.
  • Layer 2, changes once per document set: that set’s documents, the same for a run of questions. Breakpoint at its end, with a 5-minute lifetime.
  • Layer 3, changes on every call: the reviewer’s question, after the last breakpoint.

Keep values that change out of the stable layers. A timestamp, a user’s name, a request ID or “today’s date” at the top of the system prompt makes every request’s beginning unique, so nothing is ever read from the cache. Put such values after the last breakpoint, or leave them out.

The same morning’s calls in two layouts

Skill 2.5Same content, same calls; only the order and the breakpoints differ.

  • Bad layout: a timestamp opens the system prompt, and the documents come after the question. No beginning ever repeats, so nothing is read from the cache: $3.31 for the morning.
  • Good layout: the guide (1-hour breakpoint), then the document set (5-minute breakpoint), then the question. The guide is written once, each document set once, and everything else is read from the cache: $0.48, with 91% of input read from cache.

A useful benchmark: Anthropic reports that agent loops read a median 84% of their input from the cache, and suggests that if you’re below about 80%, something is breaking the beginning of the prompt.

The code below simulates both layouts over the same calls (it simplifies the caching rules):

review_cache.py (review_cache.py)Optional 
"""A document-review assistant: lay out the prompt so the call pattern reuses the cache.

Call pattern (one reviewer's morning): 3 document sets, about 10 questions each, a few minutes apart.
Layers, most stable first:
  1. shared review guide + tools     12,000 tokens, same all day   -> 1-hour breakpoint
  2. this set's documents        40,000 tokens, same per document set -> 5-minute breakpoint
  3. the question                       150 tokens, new every call -> after the last breakpoint
Simplified model of the prompt-caching rules: a breakpoint's prefix is read if the same prefix was
written or read within its TTL, otherwise written; anything after a changed block is uncached."""

GUIDE, DOCSET, QUESTION = 12_000, 40_000, 150


def good_request(set_id: str, docs: str, question: str) -> dict:
    return {
        "model": "claude-sonnet-5-5", "max_tokens": 2048,
        "system": [
            {"type": "text", "text": "<firm review guide>", "cache_control": {"type": "ephemeral", "ttl": "1h"}},
            {"type": "text", "text": f"<documents id='{set_id}'>{docs}</documents>", "cache_control": {"type": "ephemeral"}},
        ],
        "messages": [{"role": "user", "content": question}],
    }


def bad_request(set_id: str, docs: str, question: str, now: str) -> dict:
    return {  # a timestamp first and the question before the documents: nothing stable leads the prompt
        "model": "claude-sonnet-5-5", "max_tokens": 2048,
        "system": [{"type": "text", "text": f"Current time: {now}\n<firm review guide>",
                    "cache_control": {"type": "ephemeral"}}],
        "messages": [{"role": "user", "content": f"{question}\n<documents id='{set_id}'>{docs}</documents>"}],
    }


def simulate(calls, layout: str) -> dict:
    """calls: list of (minute, set_id). Returns tokens billed as write, read and plain input."""
    seen, tot = {}, {"write": 0, "read": 0, "input": 0}

    def hit(key, ttl, minute):
        ok = key in seen and minute - seen[key] <= ttl
        seen[key] = minute                         # a write or a read refreshes the entry
        return ok

    for minute, docset in calls:
        if layout == "good":
            tot["read" if hit("guide", 60, minute) else "write"] += GUIDE
            tot["read" if hit(("docset", docset), 5, minute) else "write"] += DOCSET
            tot["input"] += QUESTION
        else:                                      # timestamp changes every call: the prefix never matches
            tot["write"] += GUIDE
            tot["input"] += DOCSET + QUESTION
    return tot


def cost(t: dict) -> float:                        # Sonnet 5.5: write $2.50, read $0.10, input $2.00 per MTok
    return round((t["write"] * 2.50 + t["read"] * 0.10 + t["input"] * 2.00) / 1e6, 2)


MORNING = [(m, "T1") for m in range(0, 30, 3)] + [(m, "T2") for m in range(30, 60, 3)] + \
          [(m, "T3") for m in range(60, 100, 4)]

if __name__ == "__main__":
    for layout in ("bad", "good"):
        t = simulate(MORNING, layout)
        share = t["read"] / sum(t.values())
        print(f"{layout:4}  write {t['write']:>8,}  read {t['read']:>8,}  input {t['input']:>8,}  "
              f"cache-read share {share:.0%}  cost ${cost(t)}")

Let the gaps between calls choose the cache lifetime

Skill 2.55 minutes or 1 hour, from the stated call pattern.

  • Calls less than 5 minutes apart: the default lifetime is enough, and each read keeps the cache alive.
  • Gaps longer than 5 minutes but under an hour, such as a reviewer who reads for ten minutes between questions: a 5-minute cache expires, and the 40,000 tokens of documents are written again. A 1-hour cache costs more to write (2 times instead of 1.25 times) but saves those rewrites. In the simulation, a single nine-minute pause causes a second write.
  • Material shared across users: the shared guide serves every reviewer, so a 1-hour cache at the front is reused by everyone’s calls.
  • Batches: caching in the Message Batches API is best-effort, so don’t count on cache reads there.

Package occasional material as modules or Skills

Skill 2.5Don’t send every call what only some calls need.

  • Modules. Split the guide into a core module, always sent and cached, and specialist modules added only for the document sets that need them. Keep each module in its own block, always in the same order, so different combinations still share the cached core.
  • Skills. Package procedures that only some document sets need (specialist checks) as Agent Skills. Only each Skill’s name and description, about 100 tokens, sit in the context until a request needs it; then its full instructions and any scripts load.
  • What Skills require. On the API they run in the code execution container, which has no network access, with up to 20 Skills per request. Custom Skills are shared across a workspace through the Skills API. They aren’t eligible for zero data retention or HIPAA.
  • Keep the set stable. Adding or removing tools or Skills changes the beginning of the prompt and invalidates the cache, so fix the set for a workload rather than changing it per call.

“Add a breakpoint after every block” doesn’t help. There are only four, writing costs more than plain input, and a breakpoint after content that changes every call writes a cache that is never read.

Key takeaways

  • The cache covers only the beginning of the prompt, up to the first thing that changes, so put what stays the same before what changes.
  • A breakpoint (cache_control) ends a cached section; up to four per request, in the fixed order tools, system, messages; under 512 tokens nothing is cached.
  • Layer by how often each part changes, with one breakpoint at the end of each stable layer; keep timestamps, names and IDs out of the stable layers.
  • Choose the lifetime from the gaps between calls: 5 minutes for calls close together, 1 hour (2 times the write price) for longer gaps or material shared across users; 1-hour sections come first.
  • A cache read share below about 80% means something is breaking the beginning of the prompt (Anthropic’s median for agent loops is 84%).
  • Send occasional material as modules or Skills (about 100 tokens each until needed), and keep the set of tools and Skills fixed for a workload.
