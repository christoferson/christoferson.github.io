3.6: Connection Mechanism Selection

Three ways to connect an agent to something else: an MCP server, a direct call to the system's API or CLI, or handing the work to another agent. The scenario's limits on speed, security and state decide which one fits each integration.

Overview

Skill 3.6

Connection Mechanism Selection: "Evaluating MCP, direct API/CLI, and agent-to-agent handoff against scenario constraints on latency, security, and statefulness, and selecting the connection mechanism the constraints favor."

Exam items describe an integration and its constraints and ask which mechanism they favour. Choosing among built-in tools, custom tools, Skills and MCP for a capability is in the developer notes (CCDV-F 8.3); building an MCP server is CCDV-F 8.2.

Three ways to connect an agent to another system

Skill 3.6What this skill asks you to choose, and the question that settles most cases.

An agent can reach another system through a direct tool or command-line program, through an MCP server, or by handing the task to another agent. Questions on this skill describe an integration and its constraints on speed, security and state, and ask which mechanism they favour. Two questions settle most cases: does the work need its own judgement or credentials, and do many clients need the same system?

A direct tool or CLI: least overhead, for one consumer

Skill 3.6A custom tool in your own service, or a command-line program the agent already knows.

Your service defines a tool that calls the system directly, or a coding agent uses an existing command-line program. Claude Code’s best practices say that if a system has a CLI, that’s usually the easiest way in: with gh signed in, Claude opens pull requests without further explanation. There’s no extra network hop and everything stays under your control, but each application builds and maintains its own.

An MCP server: build it once, use it from every client

Skill 3.6For systems many agents, teams or apps need.

One server can be used by any MCP client: Claude Code, the Claude apps, the Agent SDK, and the Messages API’s MCP connector (in beta, tools only, and only for servers on the public internet over HTTPS). That makes it the right choice when many agents, teams or applications need the same system. Connected servers add their tool names and instructions to the context even when they aren’t used, so turn off the ones a task doesn’t need.

A handoff to another agent: a separate boundary and judgement

Skill 3.6Another agent takes the task with its own tools, permissions and context.

The other agent sees only the brief you send, not your conversation, and returns its result. It suits work that needs its own judgement over several steps, a different security boundary (credentials your agent should never hold), or its own approval chain.

Tight time limits favour direct calls

Skill 3.6How each mechanism adds time.

A direct tool inside your service adds no extra hop. A remote MCP server adds a network round trip and its own processing. A handoff adds a whole agent run. Large intermediate results cost time and tokens with any of them; Anthropic’s “Code execution with MCP” post shows presenting MCP servers to the agent as code it can call, so the results stay in the execution environment. That cut one workflow from 150,000 tokens to 2,000, at the cost of running a sandbox.

Separate credentials and approvals favour a handoff

Skill 3.6Where each mechanism puts the security boundary.

A handoff is the clearest boundary: the other agent holds credentials your agent never sees. An MCP server gathers credentials and authorisation into one place, which then needs careful handling of tokens and scopes. A direct tool keeps everything inside your service, so limiting what it can do is entirely up to you.

MCP doesn’t keep sessions, so state goes behind handles

Skill 3.6Where each mechanism keeps state between calls.

The current draft of the MCP specification has no sessions at the protocol level. A server that needs continuity, such as a booking in progress, returns an explicit handle and ties it to the verified user. A direct tool keeps state in your application. A handoff carries state only in the brief and the result, so pass references to stored work rather than copies.

Worked example: a freight company’s four integrations

Skill 3.6Four integrations, four choices.

A freight company’s dispatch agent needs four integrations:

  • Its own shipment database: one consumer and a 150-millisecond budget, so a narrow direct tool.
  • Five carriers’ booking systems: used by five agents and apps, so one MCP server per carrier, with bookings in progress behind handles tied to the user.
  • Customs declarations: judgement over several steps, under a licensed broker’s credentials and approval chain, so a handoff to a customs agent with its own permissions.
  • Infrastructure changes made from Claude Code: the cloud provider’s CLI already exists and Claude knows it, so use it, limited by permission rules.

The code below makes these choices from each integration’s constraints:

connection_choice.py (connection_choice.py)Optional 
"""Pick a connection mechanism for each integration of a freight company's dispatch agent.

Mechanisms:
  direct      a custom tool in our service calling the system's API (or a CLI in a coding agent)
  mcp         an MCP server, reusable by any MCP client (Claude Code, Claude apps, the Agent SDK,
              the Messages API connector for public HTTPS servers, tools only)
  handoff     pass the task to another agent that owns its own tools, permissions and context"""
from dataclasses import dataclass


@dataclass
class Integration:
    name: str
    consumers: int                 # how many different agents or apps need it
    latency_ms: int                # budget for this step
    needs_own_permissions: bool    # must run under a different identity / approval chain
    multi_step_judgement: bool     # the work is a task, not a call
    has_cli: bool = False
    state: str = "none"            # "none", "per_call", "long_lived"


def choose(i: Integration) -> tuple[str, str]:
    if i.needs_own_permissions or i.multi_step_judgement:
        return "handoff", "a separate agent with its own identity and context; pass an explicit brief, get a result back"
    if i.consumers > 1:
        why = "one server reused by every client and team"
        if i.state == "long_lived":
            why += "; MCP itself is stateless, so keep state behind explicit handles bound to the user"
        return "mcp", why
    if i.has_cli:
        return "direct", "an existing CLI the coding agent already knows; nothing to build"
    return "direct", f"one consumer and a {i.latency_ms} ms budget: a narrow custom tool, no extra hop"


INTEGRATIONS = [
    Integration("shipment database lookup", consumers=1, latency_ms=150, needs_own_permissions=False, multi_step_judgement=False),
    Integration("carrier booking systems", consumers=5, latency_ms=2_000, needs_own_permissions=False,
                multi_step_judgement=False, state="long_lived"),
    Integration("customs declarations", consumers=1, latency_ms=600_000, needs_own_permissions=True, multi_step_judgement=True),
    Integration("infrastructure changes from Claude Code", consumers=1, latency_ms=10_000,
                needs_own_permissions=False, multi_step_judgement=False, has_cli=True),
]

if __name__ == "__main__":
    for i in INTEGRATIONS:
        m, why = choose(i)
        print(f"{i.name:40} {m:8} {why}")

“Wrap everything in MCP for consistency” adds a hop and context to a lookup with one consumer and a tight time limit. “Let the dispatch agent call the customs system directly” gives it credentials and authority that belong behind a separate boundary.

Real systems mix mechanisms

Skill 3.6The choices aren’t exclusive.

  • A handoff that uses MCP. The customs agent can use MCP servers itself: the handoff decides who acts, and MCP decides how they connect.
  • Direct now, MCP later. Start with a direct tool for one consumer, and move it to an MCP server when a second team needs the same system.
  • Keep the context small whichever you choose: return only what the agent needs, load rarely used tools only when needed, and turn off servers a task doesn’t use.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A web shop’s chat agent needs to look up stock levels in the shop’s own database. Only this agent uses the data, and the lookup must return in under 100 milliseconds. Which connection fits?
  1. A. An MCP server, so the stock data is available to every future client
  2. B. A narrow direct tool in the agent’s own service
  3. C. A handoff to a stock-management agent
  4. D. The Messages API’s MCP connector
Answer
B
Why
One consumer and a tight time limit favour a direct tool with no extra network hop. An MCP server adds a hop and context for reuse nobody needs yet; a handoff adds a whole agent run; the MCP connector needs a public HTTPS server.
Question 2
Scenario
A company’s HR system will be used by its support agent, a manager assistant, Claude Code for internal tools and an analytics app. Which connection fits?
  1. A. A separate direct tool in each application
  2. B. One MCP server for the HR system
  3. C. A handoff to an HR agent from each application
  4. D. Pasting the HR records into each prompt
Answer
B
Why
Many clients need the same system, so one MCP server built once and reused by every client fits. Separate direct tools duplicate the work and drift apart; a handoff is for separate judgement or credentials, not for sharing access.
Question 3
Scenario
A sales agent must sometimes file regulatory reports, which need a compliance officer’s credentials and sign-off and several steps of judgement. How should the sales agent reach the reporting system?
  1. A. Give the sales agent the compliance credentials as a tool
  2. B. Hand the task off to a compliance agent with its own permissions
  3. C. Expose the reporting system through an MCP server the sales agent calls
  4. D. Tell the sales agent in its prompt to ask for sign-off
Answer
B
Why
Separate credentials, judgement and an approval chain call for a handoff: the compliance agent holds credentials the sales agent never sees and returns only its result. Giving the sales agent the credentials, directly or through MCP, removes the boundary; a prompt instruction isn’t a control.
Question 4
Scenario
A booking MCP server must remember a reservation that a user builds over several tool calls. How should it keep that state?
  1. A. Rely on the MCP session to hold it
  2. B. Store it in the agent’s system prompt
  3. C. Return a random handle tied on the server to the verified user, and accept it in later calls
  4. D. Use a sequential reservation number the client passes back
Answer
C
Why
The current MCP draft has no protocol-level sessions, so the server returns an explicit handle and ties it to the verified user. A sequential number can be guessed to reach another user’s reservation; the system prompt isn’t a store for per-user state.

Key takeaways

  • Direct tool or CLI: one consumer, tight time limits, nothing to share; an existing CLI is often the easiest way in for a coding agent.
  • MCP server: many clients need the same system; built once and reused; servers cost context even when idle; the Messages API connector supports tools only, on public HTTPS servers.
  • Handoff: the work needs its own judgement, credentials or approval chain; the other agent sees only the brief and returns a result.
  • Tight time limits favour direct calls; separate credentials favour handoffs; MCP keeps no sessions, so state lives behind handles tied to the user, in your application, or in references passed in a handoff.
  • Mix mechanisms deliberately, and keep what each returns small.
