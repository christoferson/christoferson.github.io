3.6: Connection Mechanism Selection

Three ways to connect an agent to something else: an MCP server, a direct call to the system's API or CLI, or handing the work to another agent. The scenario's limits on speed, security and state decide which one fits each integration.

Overview

Skill 3.6

Connection Mechanism Selection: "Evaluating MCP, direct API/CLI, and agent-to-agent handoff against scenario constraints on latency, security, and statefulness, and selecting the connection mechanism the constraints favor."

Exam items describe an integration and its constraints and ask which mechanism they favour. Choosing among built-in tools, custom tools, Skills and MCP for a capability is in the developer notes (CCDV-F 8.3); building an MCP server is CCDV-F 8.2.

Sources: Claude Code best practices, Anthropic's "Code execution with MCP" post, the MCP connector and Agent SDK subagents documentation, and the MCP security best practices, checked on 19 and 20 November 2026 and paraphrased. The company and code are my own; the code that makes the choice is tested.

Running example. A freight company's dispatch agent needs four integrations: its own shipment database, five carriers' booking systems, customs declarations, and infrastructure changes made from Claude Code.

The three mechanisms

Skill 3.6What each one is, and its strengths.

  • Direct API call or CLI: a custom tool in your own service that calls the system, or an existing command-line tool for a coding agent. Claude Code's best practices say that if a system has a CLI, that's usually the easiest way in (with gh signed in, Claude opens pull requests without further explanation). Least overhead, fully under your control, but built and maintained per application.
  • MCP server: one server, reusable by any MCP client: Claude Code, Claude apps, the Agent SDK, and the Messages API's MCP connector (beta; tools only, public HTTPS servers only). Best when many agents, teams or apps need the same system. Connected servers add their tool names and instructions to context even when unused, so turn off the ones a task doesn't need.
  • Agent-to-agent handoff: another agent takes the task with its own tools, permissions and context. It sees only the brief you pass, not your history, and returns its result. Best when the work needs its own judgement, a different security boundary, or a separate approval chain.

Latency, security, statefulness

Skill 3.6How each constraint pushes the choice.

  • Latency: a direct in-process tool adds no extra hop; a remote MCP server adds a network round trip and its own processing; a handoff adds a whole agent run. Tight budgets favour direct calls. Large intermediate results cost time and tokens either way: Anthropic's "Code execution with MCP" post shows presenting MCP servers as code APIs, so results stay in the execution environment, cutting one workflow from 150,000 to 2,000 tokens, at the cost of running a sandbox.
  • Security: a handoff is the clearest boundary, because the other agent holds credentials yours never sees. MCP centralises credentials and authorisation in one server, which then needs proper token and scope handling (skill 3.2). Direct tools keep everything inside your service, so its least-privilege design is yours alone.
  • Statefulness: the current MCP draft is stateless with no protocol-level sessions; servers that need continuity mint explicit handles, bound to the verified user. Direct tools keep state in your application. A handoff carries state only in the brief and the returned result, so pass references to stored work rather than copies.

Four integrations

Skill 3.6Four integrations, four choices.

connection_choice.py (connection_choice.py)Optional 
"""Pick a connection mechanism for each integration of a freight company's dispatch agent.

Mechanisms:
  direct      a custom tool in our service calling the system's API (or a CLI in a coding agent)
  mcp         an MCP server, reusable by any MCP client (Claude Code, Claude apps, the Agent SDK,
              the Messages API connector for public HTTPS servers, tools only)
  handoff     pass the task to another agent that owns its own tools, permissions and context"""
from dataclasses import dataclass


@dataclass
class Integration:
    name: str
    consumers: int                 # how many different agents or apps need it
    latency_ms: int                # budget for this step
    needs_own_permissions: bool    # must run under a different identity / approval chain
    multi_step_judgement: bool     # the work is a task, not a call
    has_cli: bool = False
    state: str = "none"            # "none", "per_call", "long_lived"


def choose(i: Integration) -> tuple[str, str]:
    if i.needs_own_permissions or i.multi_step_judgement:
        return "handoff", "a separate agent with its own identity and context; pass an explicit brief, get a result back"
    if i.consumers > 1:
        why = "one server reused by every client and team"
        if i.state == "long_lived":
            why += "; MCP itself is stateless, so keep state behind explicit handles bound to the user"
        return "mcp", why
    if i.has_cli:
        return "direct", "an existing CLI the coding agent already knows; nothing to build"
    return "direct", f"one consumer and a {i.latency_ms} ms budget: a narrow custom tool, no extra hop"


INTEGRATIONS = [
    Integration("shipment database lookup", consumers=1, latency_ms=150, needs_own_permissions=False, multi_step_judgement=False),
    Integration("carrier booking systems", consumers=5, latency_ms=2_000, needs_own_permissions=False,
                multi_step_judgement=False, state="long_lived"),
    Integration("customs declarations", consumers=1, latency_ms=600_000, needs_own_permissions=True, multi_step_judgement=True),
    Integration("infrastructure changes from Claude Code", consumers=1, latency_ms=10_000,
                needs_own_permissions=False, multi_step_judgement=False, has_cli=True),
]

if __name__ == "__main__":
    for i in INTEGRATIONS:
        m, why = choose(i)
        print(f"{i.name:40} {m:8} {why}")

  • Shipment database: one consumer, a 150 ms budget: a narrow direct tool.
  • Carrier booking systems: needed by five agents and apps: one MCP server per carrier, with booking state behind user-bound handles.
  • Customs declarations: multi-step judgement under a licensed broker's credentials and approval chain: hand off to a customs agent with its own permissions.
  • Infrastructure changes from Claude Code: the cloud CLI already exists and Claude knows it: use it, scoped by permission rules.

"Wrap everything in MCP for consistency" adds a hop and context to a single-consumer, latency-critical lookup. And "let the dispatch agent call the customs system directly" gives it credentials and authority that belong behind a separate boundary.

Combining them

Skill 3.6Real systems mix mechanisms.

  • Handoff over MCP: the customs agent can itself use MCP servers; the handoff decides who acts, MCP decides how they connect.
  • Direct today, MCP later: start with a direct tool for one consumer; move to an MCP server when a second team needs the same system.
  • Keep the context small: whichever mechanism, return only what the agent needs, defer rarely used tools (skill 3.1), and turn off unused servers.

Key takeaways

  • Direct API or CLI: one consumer, tight latency, nothing to share; an existing CLI is often the easiest way in for a coding agent.
  • MCP: many clients need the same system; one server, reused everywhere; servers cost context even when idle; the Messages API connector supports tools only, on public HTTPS servers.
  • Agent-to-agent handoff: the work needs its own judgement, identity or approval chain; the other agent sees only the brief and returns a result.
  • Latency favours direct calls; security boundaries favour handoffs; MCP is stateless, so state lives in user-bound handles, your application, or references passed in a handoff.
  • Mix mechanisms deliberately, and keep what each returns small.
