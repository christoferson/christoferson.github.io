3.1: Least-Privilege Tool Configuration

Going through every tool an agent has and asking whether the task needs it, whether it needs all of what the tool can do, and whether there's a way to get the same information that costs less context. Each tool ends up kept, removed, narrowed, or replaced.

Overview

Skill 3.1

Least-Privilege Tool Configuration: "Evaluating an agent or subagent tool configuration against least-privilege and minimal-footprint principles, and determining which tool connections to remove, scope down, or replace with a context-efficient access pattern."

Exam items list an agent's tools and its task and ask which change to make. Enforcing limits with hooks, permission rules and sandboxes is in the developer notes (CCDV-F 7.2); credentials and authorisation are skill 3.2.

Sources: the Claude documentation on the tool search tool, programmatic tool calling and Agent SDK permissions and subagents, checked on 19 and 20 November 2026 and paraphrased. The agent, audit rules and code are my own and tested.

Running example. A B2B software company's "renewal-risk researcher" subagent reads account, billing, usage and support data and returns a risk summary to the account manager. It was set up quickly with every connector the team had.

Two principles

Skill 3.1What each asks of a tool list (my reading of the guide's terms).

  • Least privilege: each tool grants only the capabilities the task needs: read rather than write, one object type rather than the whole system, specific fields rather than full records. If an injected instruction or a reasoning error gets through, a narrow tool limits the damage.
  • Minimal footprint: the agent carries and touches as little as it can: few tool definitions in context, small tool results, no side effects it doesn't need, and no paths out of the system (sending, posting, fetching the web) unless the task requires them.
  • Why it matters twice: fewer tools is also better tool use. Anthropic's tool search documentation notes that Claude's ability to pick the right tool degrades past 30–50 available tools.

Auditing a subagent

Skill 3.1Each tool's capabilities against the task, plus 30 days of usage.

tool_audit.py (tool_audit.py) 
"""Audit a subagent's tools against its task: remove, scope down, or replace with a context-efficient pattern.

Subagent: "renewal-risk researcher" at a B2B software company. Task: read account data and usage,
write a risk summary for the account manager. It never needs to change records or contact customers."""

TASK_NEEDS = {"read"}                          # the job only reads; the summary is returned, not sent

TOOLS = {  # name: (capabilities, definition tokens)
    "crm_full":          ({"read", "write", "delete"}, 2_400),   # admin-scoped CRM connector
    "billing_lookup":    ({"read"}, 600),
    "usage_query":       ({"read"}, 700),
    "email_send":        ({"send"}, 500),
    "slack_post":        ({"send"}, 450),
    "file_write":        ({"write"}, 300),
    "web_fetch":         ({"read", "egress"}, 400),
    "support_tickets":   ({"read"}, 650),
}

USAGE_30D = {"crm_full": 410, "billing_lookup": 380, "usage_query": 3_900, "support_tickets": 25,
             "email_send": 0, "slack_post": 0, "file_write": 2, "web_fetch": 0}   # calls in the last 30 days
CALLS_PER_RUN = {"usage_query": 30}            # 30 weekly usage pulls per account, each returning ~2,000 tokens


def audit():
    findings = []
    for name, (caps, tokens) in TOOLS.items():
        extra = caps - TASK_NEEDS
        used = USAGE_30D.get(name, 0)
        if not caps & TASK_NEEDS:
            findings.append((name, "remove", f"capability {sorted(caps)} not needed by the task"))
        elif used == 0:
            findings.append((name, "remove", f"unused in 30 days, and {sorted(extra) or 'it'} widens the footprint"))
        elif extra:
            findings.append((name, "scope down", f"drop {sorted(extra)}; keep a read-only, field-limited tool"))
        elif CALLS_PER_RUN.get(name, 0) >= 10:
            findings.append((name, "replace pattern", "many calls per run: aggregate behind one tool, or call it "
                             "from code (programmatic tool calling) so only the result returns"))
        else:
            findings.append((name, "keep", f"read-only and used ({used} calls)"))
    return findings


if __name__ == "__main__":
    for name, action, why in audit():
        print(f"{name:16} {action:15} {why}")
    before = sum(t for _, t in TOOLS.values())
    removed = {n for n, a, _ in audit() if a == "remove"}
    assert len(TOOLS) < 10, "with 10+ tools or 10k+ tokens of definitions, add tool search (defer_loading)"
    print(f"definition tokens: {before:,} before, {before - sum(TOOLS[n][1] for n in removed):,} after removals "
          f"(less again once crm_full is replaced by a narrow read tool)")
run_output.txt (Output)

support_tickets  keep            read-only and used (25 calls)

Remove and scope down

Skill 3.1The first two outcomes.

  • Remove what the task never needs: email_send, slack_post and file_write give a read-only researcher ways to act and to send data out. Remove what's unused, too: web_fetch has had no calls in 30 days and is an egress path.
  • Scope down what's needed but too broad: the admin CRM connector can read, write and delete across the whole CRM; the task needs a read-only tool for one account's fields. Narrow it at the source (a read-only credential or a purpose-built tool), not only in the prompt.
  • Keep what's needed and already narrow: the billing and support lookups are read-only and used.
  • Deny as well as remove: list removed tools in disallowed_tools too, so a server that adds them back doesn't quietly restore them.

"Tell the subagent in its prompt never to send emails" leaves the capability in place. Least privilege is about what the agent can do; instructions are what it's asked to do.

Context-efficient access patterns

Skill 3.1When a needed tool costs too much context.

  • Aggregate behind one tool: 30 raw weekly usage pulls of about 2,000 tokens each become one tool that returns the trend. The detail stays in the system; only the answer enters context.
  • Programmatic tool calling (Messages API): Claude writes code that calls the tool inside the code execution container, so intermediate results don't enter its context window; it needs allowed_callers on the tool and code execution code_execution_20260120 or later. It isn't eligible for zero data retention.
  • Tool search: mark rarely used tools defer_loading: true and let Claude search for them. Anthropic cites a multi-server setup with about 55,000 tokens of definitions that tool search typically cuts by over 85%, and recommends it from about 10 tools or 10,000 tokens of definitions; below that, standard tool calling fits better. Keep the 3–5 most-used tools loaded.
  • Move bulk work to a subagent whose context is discarded, returning only its conclusion.

The configuration after

Skill 3.1The researcher as an Agent SDK subagent.

researcher_after.py (researcher_after.py) 
"""The renewal-risk researcher after the audit, as an Agent SDK subagent."""
from claude_agent_sdk import AgentDefinition, ClaudeAgentOptions

researcher = AgentDefinition(
    description="Researches renewal risk for one account and returns a summary. Read-only.",
    prompt="Read the account, billing, usage and support data for the account named in the task. "
           "Return a risk summary with evidence. You can't change records or contact anyone.",
    tools=["mcp__crm__get_account",            # was crm_full: now one read-only, field-limited tool
           "mcp__billing__lookup",
           "mcp__support__tickets",
           "mcp__usage__weekly_trend"],        # replaces 30 raw usage pulls with one aggregate per account
    model="sonnet",
    maxTurns=20,
)

options = ClaudeAgentOptions(
    agents={"renewal-researcher": researcher},
    disallowed_tools=["Write", "Edit", "Bash", "WebFetch", "WebSearch",
                      "mcp__email__send", "mcp__slack__post"],   # removed, and denied in case a server re-adds them
)
  • Four read-only tools, one of them an aggregate; no sending, writing, shell or web access.
  • Removed tools are also denied, and turns are capped.
  • The return path is the summary itself: the parent agent or the application decides what happens with it.

Key takeaways

  • Audit every tool against the task's needed capabilities and its actual usage.
  • Remove tools the task doesn't need or doesn't use, especially ones that send, write or reach outside; deny them too.
  • Scope down tools that are needed but too broad: read-only credentials, single-object tools, limited fields, enforced at the source.
  • Replace context-heavy access with aggregate tools, programmatic tool calling (results stay out of context), tool search with deferred loading (10+ tools or 10k+ tokens of definitions), or a subagent.
  • Prompt instructions don't reduce privilege; capabilities do. Fewer, narrower tools also improve tool selection.
