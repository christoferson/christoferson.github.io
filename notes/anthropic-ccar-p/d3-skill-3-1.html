3.1: Least-Privilege Tool Configuration

Overview

Skill 3.1

Least-Privilege Tool Configuration: "Evaluating an agent or subagent tool configuration against least-privilege and minimal-footprint principles, and determining which tool connections to remove, scope down, or replace with a context-efficient access pattern."

Exam items list an agent's tools and its task and ask which change to make. Enforcing limits with hooks, permission rules and sandboxes is in the developer notes (CCDV-F 7.2); credentials and authorisation are skill 3.2.

Give an agent only the tools its task needs

Skill 3.1What this skill asks you to decide.

Agents are often set up quickly with every connector a team has, and then keep them. Questions on this skill list an agent’s tools and its task, and ask what to change. For each tool there are four possible answers: remove it, scope it down so it can do less, change how the agent reaches it so it costs less context, or keep it. Two principles decide which: least privilege and minimal footprint.

Least privilege: each tool can do only what the task needs

Skill 3.1Limit what can go wrong, not just what is likely to.

Each tool should grant only the capability the task needs: read rather than write, one kind of record rather than the whole system, specific fields rather than whole records. The reason is what happens when something goes wrong. If a document the agent reads contains hidden instructions, or the model simply reasons badly, a narrow tool limits the damage to what that tool can do. A tool that can delete records turns every mistake into a possible deletion.

Minimal footprint: carry and touch as little as possible

Skill 3.1Fewer tools in context, smaller results, no unneeded ways out.

The agent should carry few tool definitions, receive small tool results, cause no side effects it doesn’t need, and have no way to send data out of the system (sending email, posting messages, fetching web pages) unless the task requires it. This also makes the agent better at its job: Anthropic’s tool search documentation notes that Claude’s ability to pick the right tool gets worse once more than about 30 to 50 tools are available.

Audit every tool against the task and its real use

Skill 3.1Three questions per tool, answered with 30 days of usage data.

Take a software company’s “renewal-risk researcher”: a subagent that reads a customer’s account, billing, usage and support data and returns a risk summary to the account manager. It was given every connector the team had. Checking each tool’s capabilities against the task, and its last 30 days of use, gives:

  • Remove email_send, slack_post and file_write: a researcher that only reports has no need to send or write anything. Remove web_fetch too: it hasn’t been called in 30 days and it’s a way for data to leave.
  • Scope down the full CRM connector, which can read, write and delete across the whole CRM; the task needs read-only access to one account’s fields.
  • Change the pattern for usage_query, which is called many times per run and fills the context with raw data.
  • Keep the billing and support lookups: read-only, and used.

The code below runs that audit from each tool’s capabilities and usage:

tool_audit.py (tool_audit.py)Optional 
"""Audit a subagent's tools against its task: remove, scope down, or replace with a context-efficient pattern.

Subagent: "renewal-risk researcher" at a B2B software company. Task: read account data and usage,
write a risk summary for the account manager. It never needs to change records or contact customers."""

TASK_NEEDS = {"read"}                          # the job only reads; the summary is returned, not sent

TOOLS = {  # name: (capabilities, definition tokens)
    "crm_full":          ({"read", "write", "delete"}, 2_400),   # admin-scoped CRM connector
    "billing_lookup":    ({"read"}, 600),
    "usage_query":       ({"read"}, 700),
    "email_send":        ({"send"}, 500),
    "slack_post":        ({"send"}, 450),
    "file_write":        ({"write"}, 300),
    "web_fetch":         ({"read", "egress"}, 400),
    "support_tickets":   ({"read"}, 650),
}

USAGE_30D = {"crm_full": 410, "billing_lookup": 380, "usage_query": 3_900, "support_tickets": 25,
             "email_send": 0, "slack_post": 0, "file_write": 2, "web_fetch": 0}   # calls in the last 30 days
CALLS_PER_RUN = {"usage_query": 30}            # 30 weekly usage pulls per account, each returning ~2,000 tokens


def audit():
    findings = []
    for name, (caps, tokens) in TOOLS.items():
        extra = caps - TASK_NEEDS
        used = USAGE_30D.get(name, 0)
        if not caps & TASK_NEEDS:
            findings.append((name, "remove", f"capability {sorted(caps)} not needed by the task"))
        elif used == 0:
            findings.append((name, "remove", f"unused in 30 days, and {sorted(extra) or 'it'} widens the footprint"))
        elif extra:
            findings.append((name, "scope down", f"drop {sorted(extra)}; keep a read-only, field-limited tool"))
        elif CALLS_PER_RUN.get(name, 0) >= 10:
            findings.append((name, "replace pattern", "many calls per run: aggregate behind one tool, or call it "
                             "from code (programmatic tool calling) so only the result returns"))
        else:
            findings.append((name, "keep", f"read-only and used ({used} calls)"))
    return findings


if __name__ == "__main__":
    for name, action, why in audit():
        print(f"{name:16} {action:15} {why}")
    before = sum(t for _, t in TOOLS.values())
    removed = {n for n, a, _ in audit() if a == "remove"}
    assert len(TOOLS) < 10, "with 10+ tools or 10k+ tokens of definitions, add tool search (defer_loading)"
    print(f"definition tokens: {before:,} before, {before - sum(TOOLS[n][1] for n in removed):,} after removals "
          f"(less again once crm_full is replaced by a narrow read tool)")

Remove what the task doesn’t need, and deny it too

Skill 3.1A capability that isn’t there can’t be misused.

Remove tools the task never needs, especially ones that send, write or reach outside the system, and tools that are never used. Then list the removed tools in disallowed_tools as well, so that if an MCP server adds them back later, they don’t quietly return.

“Tell the subagent in its prompt never to send emails” leaves the capability in place. Least privilege is about what the agent can do; an instruction is only what it’s asked to do.

Scope down at the source, not in the prompt

Skill 3.1For tools that are needed but can do far more than the task.

When the task needs some of what a tool does, narrow the tool itself: a read-only credential, or a purpose-built tool that returns only one account’s relevant fields. Writing “only read” into the prompt leaves the write and delete capability one mistake away.

When a needed tool costs too much context, change how it’s reached

Skill 3.1Four patterns that keep raw data out of the agent’s context.

  • Put an aggregate behind one tool. Thirty raw weekly usage pulls of about 2,000 tokens each become one tool that returns the trend. The detail stays in the system; only the answer enters the context.
  • Call the tool from code (programmatic tool calling). On the Messages API, Claude can write code that calls the tool inside the code execution container, so the intermediate results never enter its context window. The tool needs allowed_callers set, and code execution must be code_execution_20260120 or later. It isn’t eligible for zero data retention.
  • Load rarely used tools only when needed (tool search). Mark them defer_loading: true and Claude searches for them when a task calls for one. Anthropic cites a setup with about 55,000 tokens of tool definitions that tool search typically cuts by over 85%, and recommends it from about 10 tools or 10,000 tokens of definitions; below that, ordinary tool calling fits better. Keep the 3 to 5 most-used tools always loaded.
  • Hand bulk work to a subagent whose context is thrown away afterwards, so only its conclusion comes back.

The researcher after the audit

Skill 3.1The same subagent, defined in the Agent SDK with only what it needs.

  • Four read-only tools, one of them the usage aggregate. No sending, writing, shell or web access.
  • The removed tools are also denied, and the number of turns is capped.
  • Its only output is the summary. The parent agent or the application decides what happens with it.
researcher_after.py (researcher_after.py)Optional 
"""The renewal-risk researcher after the audit, as an Agent SDK subagent."""
from claude_agent_sdk import AgentDefinition, ClaudeAgentOptions

researcher = AgentDefinition(
    description="Researches renewal risk for one account and returns a summary. Read-only.",
    prompt="Read the account, billing, usage and support data for the account named in the task. "
           "Return a risk summary with evidence. You can't change records or contact anyone.",
    tools=["mcp__crm__get_account",            # was crm_full: now one read-only, field-limited tool
           "mcp__billing__lookup",
           "mcp__support__tickets",
           "mcp__usage__weekly_trend"],        # replaces 30 raw usage pulls with one aggregate per account
    model="sonnet",
    maxTurns=20,
)

options = ClaudeAgentOptions(
    agents={"renewal-researcher": researcher},
    disallowed_tools=["Write", "Edit", "Bash", "WebFetch", "WebSearch",
                      "mcp__email__send", "mcp__slack__post"],   # removed, and denied in case a server re-adds them
)

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A subagent that only writes a summary report has tools to send email, post to chat, write files and fetch web pages. None of them is needed for its task. What should be done?
  1. A. Tell it in its prompt not to use them
  2. B. Remove the tools and list them as disallowed too
  3. C. Keep them in case they are useful later
  4. D. Move them to a larger model
Answer
B
Why
Least privilege is about what the agent can do. Remove tools the task doesn’t need, especially ones that send or write, and deny them so a server can’t quietly add them back. A prompt instruction leaves the capability in place.
Question 2
Scenario
An agent needs to read one customer’s record, but its connector can read, write and delete across the whole system. Which change fits?
  1. A. Keep the connector and add a prompt rule
  2. B. Scope it down at the source: a read-only credential or a tool limited to that record’s fields
  3. C. Remove the connector entirely
  4. D. Log every call
Answer
B
Why
The task needs some of what the tool does, so narrow the tool itself. Removing it breaks the task; a prompt rule leaves delete one mistake away.
Question 3
Scenario
An agent calls a usage tool 30 times per run, each returning about 2,000 tokens of raw data, only to compute a trend. Which pattern fits?
  1. A. Load all the raw data into the system prompt
  2. B. An aggregate tool that returns the trend, or calling the tool from code so only the result returns
  3. C. A larger context window
  4. D. More turns
Answer
B
Why
Keep raw data out of the context: an aggregate tool, programmatic tool calling, or a subagent returns only the answer the agent needs.
Question 4
Scenario
An agent has 120 tool definitions, about 60,000 tokens, and picks the wrong tool more often than it used to. What helps both cost and accuracy?
  1. A. More detailed tool descriptions only
  2. B. Tool search with deferred loading, keeping the 3 to 5 most-used tools loaded
  3. C. Splitting each tool into two
  4. D. Raising effort
Answer
B
Why
Tool choice gets worse past about 30 to 50 tools, and tool search cuts definition tokens sharply. Anthropic suggests it from about 10 tools or 10,000 tokens of definitions.

Key takeaways

  • For every tool, decide: remove it, scope it down, change how it’s reached, or keep it.
  • Least privilege: each tool does only what the task needs (read not write, one kind of record, specific fields), so an injected instruction or a reasoning error can do little.
  • Minimal footprint: few tool definitions, small results, no unneeded side effects and no way to send data out; tool choice also gets worse past about 30 to 50 tools.
  • Remove unneeded and unused tools and deny them too; scope needed tools down at the source, not in the prompt.
  • Keep raw data out of context with an aggregate tool, programmatic tool calling, tool search with deferred loading (from about 10 tools or 10,000 tokens of definitions), or a subagent.
  • A prompt instruction doesn’t reduce privilege; only removing or narrowing the capability does.
