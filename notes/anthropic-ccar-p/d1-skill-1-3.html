Overview

Skill 1.3

Architectural Pattern Selection: "Selecting among workflow, agentic, augmented-LLM, and Skills-based architectural patterns for a use case with stated reuse, governance, and risk-profile constraints, and justifying the delegation boundary the selected pattern establishes."

Exam items give a use case with constraints (reused by many teams, must be auditable, low tolerance for error) and ask which pattern fits and why. Implementing these patterns is covered in the Foundations notes, such as agentic loops and decomposition; this skill is the selection and its justification. Splitting a single process between Claude and people is skill 1.1.

The patterns differ in how much the model decides

Skill 1.3What the exam asks, and the one idea that separates the patterns.

Anthropic describes four ways to build with Claude: an augmented LLM, a workflow, an agent, and a Skills-based design. They don’t differ in which model they use. They differ in who decides what happens next: the model, your code, or a person.

The exam guide calls this line the delegation boundary: everything on one side the model decides, everything on the other side is fixed by your code or left to a person. Choosing a pattern means choosing where that line sits, and the question gives you the constraints that decide it: whether many teams will reuse the solution, whether it must be auditable, and how costly a mistake would be.

The next four sections describe each pattern, where it puts the boundary and when it fits. The sections after that take each constraint in turn.

Augmented LLM: one call that looks things up for itself

Skill 1.3The basic building block: a single request, with retrieval, tools and memory.

What it is. Your application sends one request to an LLM that has been given retrieval (a search over your documents, often a vector database), tools and memory. Within that request the model decides what to search for, which tool to call and what to keep, then returns an answer. Retrieval-augmented generation (RAG) is the familiar case.

Who decides. The model decides how to use its retrieval, tools and memory inside the one request. Your application decides when to call it, and the person using the answer decides what to do with it. The model doesn’t plan or run a multi-step process.

When it fits. A question with an answer, grounded in your own material. For example, a field engineer asks a troubleshooting assistant why a transformer is tripping; the assistant searches the equipment manuals and answers, and the engineer decides what to do. Anthropic notes that a single well-built call like this, with retrieval and good examples, is enough for many applications.

Workflow: your code fixes the steps

Skill 1.3Models and tools run along paths you wrote in advance.

What it is. Anthropic defines workflows as systems where models and tools are “orchestrated through predefined code paths”. Your code calls the model at set points and decides what happens between them. Anthropic names five common shapes:

  • Prompt chaining: a fixed sequence of calls, each working on the previous one’s output, such as outline, then draft, then check.
  • Routing: one call classifies the input, and code sends it to a step built for that kind of input.
  • Parallelisation: independent parts run at the same time (sectioning), or the same task runs several times and the results are compared (voting).
  • Orchestrator-workers: a central model splits the task into subtasks as it goes and hands them to worker calls, then combines the results.
  • Evaluator-optimiser: one call produces a result, another judges it and sends feedback, and the loop repeats until it passes.

Who decides. The model decides inside each step (a label, a draft, a verdict); your code decides the order, the branches and when to stop. Because the boundary is in code, anyone can read it, test it and audit it.

When it fits. The steps are known in advance, the same every time, or the inputs fall into clear categories.

A routing workflow: the model labels, your code decides

Skill 1.3How a workflow keeps a must-hold rule out of the model’s hands.

  • The model only labels. It reads the incoming item and picks one label from a fixed list. It doesn’t decide what happens next.
  • Your code decides. An ordinary if on the label sends urgent items straight to a person. No prompt, and nothing written in the item itself, can change that, because the rule isn’t in a prompt.
  • Routine items get help, not autonomy. The model drafts a response, and a person approves it before it’s sent.
  • When in doubt, a person. If the model can’t pick a label, or declines, the item goes to human review.
  • Easy to audit. Every route is a line of code that can be read and tested.

The code below applies this to field reports at a power utility. “Urgent” there means a safety risk, such as a live wire on the ground, and the person is the utility’s emergency desk.

route_reports.py (route_reports.py)Optional 
"""Field reports at a power utility, handled as a routing workflow.

The model classifies; code decides what happens next. Safety reports never reach a model step that
acts: they go straight to the control-room queue. Routine reports get an augmented-LLM step
(retrieval over the maintenance manual) that drafts a work order for a planner to approve."""
import json

import anthropic

client = anthropic.Anthropic()

ROUTE_SCHEMA = {
    "type": "object",
    "properties": {
        "category": {"type": "string", "enum": ["safety", "outage", "routine_fault", "other"]},
        "asset_id": {"type": "string"},
        "reason": {"type": "string"},
    },
    "required": ["category", "asset_id", "reason"],
    "additionalProperties": False,
}


def classify(report: str) -> dict:
    r = client.messages.create(
        model="claude-haiku-5-5",                     # high volume, simple decision
        max_tokens=1024,
        output_config={"effort": "low", "format": {"type": "json_schema", "schema": ROUTE_SCHEMA}},
        system="Classify a field engineer's report. 'safety' = any risk to people (live wires down, "
               "fire, gas, injury). Use 'other' if unsure.",
        messages=[{"role": "user", "content": f"<report>{report}</report>"}],
    )
    if r.stop_reason != "end_turn":                   # refusal or truncation: no trustworthy label
        return {"category": "other", "asset_id": "", "reason": f"unclassified ({r.stop_reason})"}
    return json.loads(next(b.text for b in r.content if b.type == "text"))


def draft_work_order(report: str, asset_id: str, search) -> str:
    passages = search(asset_id)                       # retrieval: the augmentation
    r = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=2048,
        system="Draft a work order from the report, using only the manual passages given. "
               "List parts and steps; say 'not in manual' for anything the passages don't cover.",
        messages=[{"role": "user", "content": f"<manual>{passages}</manual>\n<report>{report}</report>"}],
    )
    return next(b.text for b in r.content if b.type == "text")


def handle(report: str, search, queues: dict) -> str:
    label = classify(report)
    if label["category"] == "safety":                 # boundary set in code, not by the model
        queues["control_room"].append(report)
        return "control_room"
    if label["category"] == "routine_fault":
        queues["planner"].append(draft_work_order(report, label["asset_id"], search))
        return "planner"
    queues["dispatcher"].append(report)               # outages and anything unclear: a person triages
    return "dispatcher"

Agent: the model chooses its own steps

Skill 1.3For open-ended problems where nobody can list the steps in advance.

What it is. The model runs in a loop: it decides which tool to call, looks at the result, decides the next step, and stops when it judges the task done.

Who decides. The model decides the sequence, the tools and when to finish. What stays with you is the frame around it: which tools it has, what permissions they carry, hooks that check calls, a limit on the number of turns, and a sandbox. Those are the only controls, so they have to be designed with care.

The cost. Agents take more calls, so they’re slower and more expensive, and a mistake early in the loop carries into every later step. Anthropic recommends testing them extensively in a sandbox, with guardrails, before trusting them.

When it fits. Investigations where the next step depends on what the last one found. For example, finding out why one area keeps losing power: which logs, sensor histories and work orders matter only becomes clear along the way. Keeping such an agent read-only, with a turn limit and a written report as its only output, keeps the risk low.

Skills-based: one agent and a shared library of procedures

Skill 1.3Write a procedure once and let every team use it.

What it is. Instead of building a separate agent for every use case, you run one general-purpose agent and give it a library of Skills. A Skill is a folder of instructions, with optional scripts and reference files, that the agent loads when a task calls for it and then follows. Only each Skill’s name and description sit in the agent’s context until it’s needed, so a large library stays cheap. The same Skill works in the Claude apps, Claude Code, the Agent SDK and the API.

Who decides. The model decides which Skill fits the task and follows it. The Skill’s author decides what the procedure says. Whoever approves the shared library decides which Skills exist at all. A Skill is instructions, so it guides what the model does but can’t force it: anything that must always hold still belongs in code.

When it fits. The same procedure is needed by many teams. For example, twelve depots each produce the same regulator report: one reviewed Skill, updated in one place, replaces twelve slightly different custom agents.

When many teams need the same thing, build it once

Skill 1.3The reuse constraint.

What goes wrong. Each team builds its own agent for the same job. They drift apart, each needs its own fixes, and a change in the rules has to be made a dozen times.

What fits. A Skill, if the shared part is a procedure that an agent should follow, or a shared workflow service, if the shared part is a fixed sequence of steps that every team calls.

When every decision must be auditable, keep it in code

Skill 1.3The governance constraint.

What goes wrong. An auditor asks why a case went one way rather than another. If an agent chose the path, the answer is in a transcript of the model’s reasoning, which can differ from run to run.

What fits. A workflow, where every branch is a line of code that can be read, tested and shown to an auditor. A Skills library needs governance of its own: who may publish a Skill, review before it’s released, and Skills only from trusted sources, because a Skill’s instructions are followed as written.

When mistakes are costly, narrow what the model decides

Skill 1.3The risk-profile constraint.

What goes wrong. An agent with broad tools takes an action that can’t be undone, or a safety case waits on the model’s judgment.

What fits. Move the boundary toward code and people. Use a workflow with checks between steps, or, if an agent is needed, give it only the tools the task needs, put approval gates before anything irreversible, and keep it read-only where possible. Open-ended work where mistakes are cheap, such as an investigation that only writes a report, can safely use an agent.

Start with the simplest pattern that works

Skill 1.3Anthropic’s rule for every choice above.

Anthropic’s advice is to find the simplest solution possible and add complexity only when it clearly improves results, which can mean not building an agent at all. A single augmented call is simpler than a workflow, and a workflow is simpler than an agent. Each step up costs more calls, more time and more paths to test, so justify it with evaluation results, not with the idea that more flexibility is safer.

A quick guide from the shape of the work: steps known in advance, a workflow; inputs in clear categories, routing; steps that can’t be known in advance, an agent; the same procedure for many teams, Skills.

“Use an agent because it’s the most flexible” is the usual wrong answer when the steps are known and the use case must be auditable. Flexibility costs something there: more paths to test, and decisions the governance team can’t see in code.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A bank must sort incoming complaints into five fixed categories, and regulators must be able to see exactly why each complaint went where it did. Which pattern fits?
  1. A. An agent that decides how to handle each complaint
  2. B. A routing workflow: the model labels, code decides the route
  3. C. A Skills-based design
  4. D. An augmented LLM with web search
Answer
B
Why
The categories are known and the routes must be auditable, so a workflow fits: every branch is a line of code. An agent would choose its own path, which is harder to show an auditor.
Question 2
Scenario
An engineering team needs an assistant that investigates why a service keeps slowing down; nobody knows in advance which logs or metrics will matter. Mistakes cost little because it only writes a report. Which pattern fits?
  1. A. A fixed prompt chain
  2. B. An agent with read-only tools, a turn limit and a report as its only output
  3. C. A routing workflow
  4. D. A single call with no tools
Answer
B
Why
Open-ended investigation where the next step depends on the last is what agents are for, and keeping it read-only with a turn limit keeps the risk low.
Question 3
Scenario
Thirty departments each need to produce the same quarterly compliance summary in a standard format. Which pattern best meets the reuse constraint?
  1. A. Thirty custom agents, one per department
  2. B. One reviewed Skill used by a general agent across departments
  3. C. A separate prompt in each department’s wiki
  4. D. An agent per report section
Answer
B
Why
One governed Skill, updated in one place, replaces many near-identical agents that would drift apart. Skills need governance of their own: who may publish them and review before release.
Question 4
Scenario
A team proposes “an agent, because it’s the most flexible”, for a task with known steps that must be auditable. What is the best response?
  1. A. Agree; flexibility is always safer
  2. B. Prefer the simplest pattern that works: a workflow, with the steps in code
  3. C. Use two agents to be safe
  4. D. Use a larger model instead
Answer
B
Why
Anthropic’s advice is to add complexity only when it improves results. Here flexibility is a cost: more paths to test and decisions an auditor can’t see in code.

Key takeaways

  • The four patterns differ in who decides what happens next. The line between the model’s decisions and your code’s or a person’s is the delegation boundary.
  • Augmented LLM: one request in which the model uses retrieval, tools and memory itself; your application and the user decide what happens with the answer.
  • Workflow: your code fixes the order and branches, and the model decides inside each step; the boundary is in code and easy to audit.
  • Agent: the model chooses its own steps in a loop; your controls are its tools, permissions, hooks, turn limit and sandbox. It costs more, and errors compound.
  • Skills-based: one general agent and a shared, governed library of procedures it loads when needed; Skills guide the model but don’t enforce anything.
  • Reuse points to Skills or a shared workflow, auditability to a workflow, and a high cost of mistakes to narrowing what the model decides. Start with the simplest pattern that works.
