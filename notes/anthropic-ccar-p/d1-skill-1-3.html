1.3: Architectural Pattern Selection

Picking the simplest pattern that meets the use case's reuse, governance and risk constraints: a single augmented call, a workflow in code, an agent that directs itself, or a general agent with Skills, and saying where each one puts the line between what the model decides and what the system decides.

Overview

Skill 1.3

Architectural Pattern Selection: "Selecting among workflow, agentic, augmented-LLM, and Skills-based architectural patterns for a use case with stated reuse, governance, and risk-profile constraints, and justifying the delegation boundary the selected pattern establishes."

Exam items give a use case with constraints (reused by many teams, must be auditable, low tolerance for error) and ask which pattern fits and why. Implementing these patterns is covered in the Foundations notes, such as agentic loops and decomposition; this skill is the selection and its justification. Splitting a single process between Claude and people is skill 1.1.

Sources: Anthropic's engineering posts "Building effective agents" and "Equipping agents for the real world with Agent Skills", and the Agent Skills documentation, checked on 20 November 2026 and paraphrased. The use cases and code are my own; the code is tested against a mocked API.

Running example. A regional power utility has four candidate uses for Claude: routing field engineers' reports, a troubleshooting assistant, investigating repeat outages, and producing regulator reports in a standard format across twelve depots.

The four patterns

Skill 1.3What each is, in Anthropic's terms.

  • Augmented LLM: a model enhanced with retrieval, tools and memory, used in a single call or a short exchange. Anthropic notes that optimising single calls with retrieval and in-context examples is usually enough for many applications.
  • Workflow: models and tools "orchestrated through predefined code paths": prompt chaining, routing (classify, then send to a specialised step), parallelisation (sectioning or voting), orchestrator-workers, evaluator-optimiser.
  • Agentic: the model directs its own process and tool use in a loop, for open-ended problems where the number of steps can't be predicted. Anthropic flags higher costs and compounding errors, and recommends extensive sandboxed testing with guardrails.
  • Skills-based: one general-purpose agent specialised by Skills (folders of instructions, scripts and resources it discovers and loads as needed) instead of a separate custom agent per use case. Only each Skill's name and description sit in context until it's needed.

Anthropic's guiding rule: find the simplest solution possible and add complexity only when it demonstrably improves results, which may mean not building an agent at all.

The delegation boundary each sets

Skill 1.3Who decides the next step (my framing).

  • Augmented LLM: the model decides the content of one answer; your code decides everything around it, including whether to use the answer.
  • Workflow: the model decides within each step (a label, a draft); code decides the sequence and branches. The boundary is visible in the code and easy to audit.
  • Agentic: the model decides the sequence, which tools to call and when it's done; the system's controls are the tool set, permissions, hooks, turn limits and sandbox.
  • Skills-based: the model decides which Skill applies and follows it; the Skill's author decides the procedure inside it; whoever governs the Skill library decides what's available.

Choosing under constraints

Skill 1.3How each stated constraint pushes the choice.

  • Reuse: the same procedure needed by many teams or surfaces points to Skills (written once, loaded on demand, portable across Claude apps, Claude Code, the Agent SDK and the API) or to a shared workflow service. Many near-identical custom agents is the anti-pattern.
  • Governance: auditable, predictable paths point to workflows, where every branch is in code. Skills need governance of their own: who may publish them, review before release, and trusted sources only.
  • Risk profile: low tolerance for error or irreversible effects narrows the model's discretion: a workflow with checks between steps, or an agent with tightly limited tools and approval gates. Open-ended, low-stakes investigation can use an agent.
  • Predictability of steps: known steps, workflow; distinct input categories, routing; unknown steps, agent.
  • Cost and latency: agents and multi-step workflows trade speed and cost for quality; justify the trade with evaluation results.

"Use an agent because it's the most flexible" is the usual wrong answer when the steps are known and the use case must be auditable. Flexibility is a cost there: more paths to test, and decisions the governance team can't see in code.

A routing workflow in code

Skill 1.3The model classifies; code holds the boundary.

route_reports.py (route_reports.py) 
"""Field reports at a power utility, handled as a routing workflow.

The model classifies; code decides what happens next. Safety reports never reach a model step that
acts: they go straight to the control-room queue. Routine reports get an augmented-LLM step
(retrieval over the maintenance manual) that drafts a work order for a planner to approve."""
import json

import anthropic

client = anthropic.Anthropic()

ROUTE_SCHEMA = {
    "type": "object",
    "properties": {
        "category": {"type": "string", "enum": ["safety", "outage", "routine_fault", "other"]},
        "asset_id": {"type": "string"},
        "reason": {"type": "string"},
    },
    "required": ["category", "asset_id", "reason"],
    "additionalProperties": False,
}


def classify(report: str) -> dict:
    r = client.messages.create(
        model="claude-haiku-5-5",                     # high volume, simple decision
        max_tokens=1024,
        output_config={"effort": "low", "format": {"type": "json_schema", "schema": ROUTE_SCHEMA}},
        system="Classify a field engineer's report. 'safety' = any risk to people (live wires down, "
               "fire, gas, injury). Use 'other' if unsure.",
        messages=[{"role": "user", "content": f"<report>{report}</report>"}],
    )
    if r.stop_reason != "end_turn":                   # refusal or truncation: no trustworthy label
        return {"category": "other", "asset_id": "", "reason": f"unclassified ({r.stop_reason})"}
    return json.loads(next(b.text for b in r.content if b.type == "text"))


def draft_work_order(report: str, asset_id: str, search) -> str:
    passages = search(asset_id)                       # retrieval: the augmentation
    r = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=2048,
        system="Draft a work order from the report, using only the manual passages given. "
               "List parts and steps; say 'not in manual' for anything the passages don't cover.",
        messages=[{"role": "user", "content": f"<manual>{passages}</manual>\n<report>{report}</report>"}],
    )
    return next(b.text for b in r.content if b.type == "text")


def handle(report: str, search, queues: dict) -> str:
    label = classify(report)
    if label["category"] == "safety":                 # boundary set in code, not by the model
        queues["control_room"].append(report)
        return "control_room"
    if label["category"] == "routine_fault":
        queues["planner"].append(draft_work_order(report, label["asset_id"], search))
        return "planner"
    queues["dispatcher"].append(report)               # outages and anything unclear: a person triages
    return "dispatcher"
  • Routing, then augmentation: a fast model classifies with a schema-constrained answer; only routine faults go on to a retrieval-backed drafting step.
  • The boundary is a line of code: safety reports go to the control room without any further model step. No prompt wording can change that.
  • Fail toward people: refusals, truncation and unclear categories go to a human dispatcher.
  • Auditable: each branch can be tested; the test covers all four routes and checks that safety reports trigger no second call.

Four use cases, four patterns

Skill 1.3The utility's choices and their justification.

  • Routing field reports: workflow (routing). Distinct categories, high volume, a safety branch that must never depend on the model's judgment. Boundary: code.
  • Troubleshooting assistant: augmented LLM. One question, one answer grounded in the manuals by retrieval; the engineer decides what to do. Boundary: the engineer acts, the model only answers.
  • Investigating repeat outages: agentic. Open-ended: which logs, sensor histories and work orders matter isn't known in advance. Low direct risk because the agent is read-only, with a turn limit and a written report as its only output. Boundary: tools and permissions.
  • Regulator reports across twelve depots: Skills-based. The same format and checks reused by many teams and surfaces; one governed Skill instead of twelve custom agents, updated in one place. Boundary: the Skill's procedure, under library governance.

Key takeaways

  • Augmented LLM (retrieval, tools, memory in one call), workflow (predefined code paths), agentic (model directs its own steps), Skills-based (a general agent loading packaged expertise on demand).
  • Start with the simplest pattern; add complexity only when evaluation shows it helps; agents cost more and errors compound.
  • Reuse points to Skills or a shared workflow; governance to workflows (and governed Skill libraries); low risk tolerance to narrow model discretion.
  • Each pattern sets a delegation boundary: code (workflow), the user (augmented LLM), tools and permissions (agent), the Skill and its governance (Skills).
  • Put must-hold rules, such as safety routing, in code, and fail toward people when the model's output can't be trusted.
