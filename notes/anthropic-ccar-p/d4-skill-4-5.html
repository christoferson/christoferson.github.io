4.5: Root-Cause Isolation from Logs and Traces

A wrong answer can come from five different places: a tool that failed, a model or prompt that isn't the one tested, a search that missed the right document, a model that invented something, or an instruction that wasn't clear. The trace shows which, if you read it in the right order.

Overview

Skill 4.5

Root-Cause Isolation from Logs and Traces: "Isolating the root cause of a failing Claude system from its logs or traces among prompt failure, retrieval failure, hallucination, tool or subagent error, and model mismatch, and specifying the corrective action."

Exam items give a trace excerpt or log lines and ask what went wrong and what to fix. The developer view of failure modes in a single exchange (refusals, under-acting, format drift) is CCDV-F 4.2; designing the telemetry is skill 3.4.

Sources: Anthropic's guidance on reducing hallucinations and prompting best practices, and the Agent SDK observability guide, checked on 20 November 2026 and paraphrased. The checking order is my own; the system and code are my own and tested.

Running example. An IT-support assistant retrieves knowledge-base articles, can hand ticket lookups to a subagent, and answers with citations. Five wrong answers were flagged this week, each with a full trace.

What each cause leaves in a trace

Skill 4.5The evidence to look for (my mapping).

  • Tool or subagent error: an error status or exception on a tool span or a subagent's result, often followed by an answer that sounds confident anyway. In Agent SDK traces, a subagent's spans sit under the parent's tool span, so the failure is visible in context.
  • Model mismatch: the model name on the request spans, or the prompt version, differs from what the evaluation approved: a silent fallback, a config change, a new default.
  • Retrieval failure: the article that answers the question isn't among the retrieved results; the model answered from what it was given, or from general knowledge.
  • Hallucination: the right article was retrieved, but the answer contains a claim no retrieved text supports.
  • Prompt failure: inputs complete and claims supported, yet the answer breaks an instruction: wrong scope, wrong format, a step it shouldn't take. Anthropic notes current models follow instructions precisely, so an ambiguous instruction produces a literal answer.

Checking in order

Skill 4.5Each check rules out a cause before the next one is blamed.

triage.py (triage.py)Optional 
"""Isolate the root cause of a bad answer from one trace of an IT-support assistant.

Pipeline: retrieve knowledge-base articles -> (optionally) a ticket-lookup subagent -> answer with
citations. Evidence is checked in an order where each step rules out a cause before blaming the next:
infrastructure first, then configuration, then inputs to the model, then what the model did with them."""


def triage(t: dict) -> tuple[str, str]:
    # 1. Tool or subagent error: the model was answering without data it asked for.
    for step in t["steps"]:
        if step.get("error"):
            return "tool/subagent error", f"{step['name']} failed ({step['error']}); surface the error to the model, retry or fail the request, alert"
    # 2. Model mismatch: production isn't running what was evaluated.
    if t["served_model"] != t["evaluated_model"] or t["prompt_version"] != t["evaluated_prompt"]:
        return "model mismatch", f"served {t['served_model']} / prompt {t['prompt_version']}, evaluated {t['evaluated_model']} / {t['evaluated_prompt']}; pin versions in config and re-run the eval before switching"
    # 3. Retrieval failure: the article that answers the question never reached the model.
    if t["gold_doc"] not in t["retrieved"]:
        return "retrieval failure", f"{t['gold_doc']} not retrieved; fix the index or query (contextual chunks, hybrid search, reranking), not the prompt"
    # 4. Hallucination: the right article was there, but the answer asserts something it doesn't say.
    unsupported = [c for c in t["claims"] if not c["supported_by"]]
    if unsupported:
        return "hallucination", f"claim not in any retrieved text: {unsupported[0]['text']!r}; require quotes or citations per claim, allow 'I don't know'"
    # 5. Prompt failure: grounded and complete inputs, but the answer breaks an instruction.
    if t["violations"]:
        return "prompt failure", f"{t['violations'][0]}; clarify the instruction or add an example, then add this case to the eval set"
    return "no fault found", "compare with a known-good trace; check the grader"

  • Infrastructure first: a failed tool explains a missing document better than the retriever does; the test plants both and expects the tool error.
  • Then configuration: if production isn't running the evaluated model and prompt, every later check is about the wrong system.
  • Then inputs: only once the right document was retrieved can an unsupported claim be called a hallucination.
  • Then behaviour: with good inputs and grounded claims, what's left is the instruction.

"The answer is wrong, so it's a hallucination; add 'don't make things up' to the prompt" is the most common misdiagnosis. If the right article was never retrieved, or the ticket subagent failed, no prompt change fixes it.

The corrective action for each

Skill 4.5Fix the cause, then lock it in.

  • Tool or subagent error: return the error to the model so it can adapt rather than guess, retry or fail the request explicitly, and alert; then fix the tool (a 403 means a credential or permission).
  • Model mismatch: pin model and prompt versions in configuration, and rerun the evaluation before any switch takes effect.
  • Retrieval failure: improve the index or query (contextual chunks, hybrid keyword and embedding search, reranking; skill 3.5), and track recall on the failing questions.
  • Hallucination: Anthropic's guidance: let the model say it doesn't know, have it quote the source before answering, require citations and retract claims without one, and restrict it to the provided documents.
  • Prompt failure: state the instruction explicitly or add an example of the boundary case.
  • Every case: add the failing trace's input to the evaluation set as a regression test.

What the trace must contain

Skill 4.5You can only isolate what you recorded.

  • Per step: name, status, errors, timing.
  • Per request: model ID and prompt version.
  • Retrieval: the IDs of what was retrieved (and scores), so you can check whether the right document was there.
  • The answer's claims and citations, so support can be checked claim by claim.
  • Linked spans for subagents, so their failures appear in the parent's trace.

Key takeaways

  • Five causes, five signatures: an error on a tool or subagent span; a served model or prompt that differs from the evaluated one; the answering document not retrieved; a claim no retrieved text supports; a clear breach of an instruction despite good inputs.
  • Check in order: infrastructure, configuration, inputs, then model behaviour, so a downstream symptom isn't blamed on the wrong cause.
  • Fix the cause: surface tool errors and alert; pin versions and re-evaluate; fix retrieval; ground and cite answers; clarify instructions.
  • Add each failure as a regression case.
  • Record what isolation needs: step status, model and prompt versions, retrieved IDs, claims with citations, and linked subagent spans.
