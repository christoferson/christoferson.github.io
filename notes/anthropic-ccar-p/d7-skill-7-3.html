7.3: Accountability for AI-Generated Code

When Claude writes more of the code, someone still has to own each change: understand it, answer for it and fix it when it breaks. This page looks at where a team’s review process quietly loses that owner, and the control that keeps one.

Overview

Skill 7.3

Accountability for AI-Generated Code: "Analyzing the review and accountability process of a team adopting AI-assisted development, and identifying the control that preserves human ownership of AI-generated code."

Exam items describe a team’s process (who prompts, who reviews, what the AI reviewer does, who merges) and ask which gap breaks accountability or which control restores it. Configuring the agents that write the code is skill 7.2.

Sources: the Claude Code documentation on Code Review, its pull-request findings and customisation, GitHub Actions and the attribution settings, checked on 20 November 2026 and paraphrased. The ownership rules are my own reasoning from those documents and common review practice; the team, files and code are my own, and the gate is tested.

Running example. An online retailer’s web and payments teams now open many pull requests with Claude: some from engineers working in Claude Code, some from a @claude mention in GitHub, some from a dependency agent. Claude Code Review comments on every pull request.

Where ownership slips

Skill 7.3Patterns that leave a change with no one answerable for it.

  • The AI review counted as the second reviewer: "Claude reviewed it" replaces the human approval the process used to require.
  • An agent’s pull request with no person behind it: a scheduled or bot-triggered job opens it, and nobody is named as the one who asked for or owns it.
  • Self-approval by proxy: the engineer who prompted the change approves it, so the only human who looked at it is its author.
  • A diff the author can’t explain: a large generated change merged because the tests pass, with no one able to say why it’s right.
  • No record of what was AI-written: attribution switched off, so a later incident review can’t tell how the code came to be.

What AI review is, and isn’t

Skill 7.3Advice with severities, never a decision.

  • What it does: several agents read the change with the surrounding code, a verification step checks findings, and the review posts inline comments ranked Important (fix before merging), Nit or Pre-existing, plus a summary and a check run.
  • What it doesn’t do: a review never approves or blocks the pull request, so "the decision to merge stays with your team", and its check run never concludes as a failure. It has read-only access to the repository and pushes no commits.
  • Its own limit, stated by the documentation: it "may miss bugs, security vulnerabilities, or other issues"; a review with no findings doesn’t mean the code is error-free or secure.
  • Making it count without making it the decider: a CI job can read the check run’s severity counts and fail when Important findings are open, and branch protection can require review threads to be resolved before merging.
  • Its instructions can’t be changed by the change itself: REVIEW.md is read from the base or default branch, never from the pull request, so protect that branch.
  • Not on every plan or configuration: it needs Team or Enterprise and GitHub, and isn’t available with Zero Data Retention, the HIPAA configuration or customer-managed keys; /code-review runs locally on any plan.

The control: a named owner and an independent approval

Skill 7.3The rule that keeps a person accountable.

  • Every change has a named human owner: the engineer who wrote it with Claude, or for an agent’s pull request, the engineer who asked for or runs the agent. That person answers for it as if they had typed it.
  • Merge needs approval from a human who isn’t the owner, from the code owners of the area touched, enforced by the code host’s branch protection rather than by convention. Bot approvals don’t count.
  • Agents can’t merge: they push to branches and open pull requests. The GitHub Action already rejects bot actors unless they’re listed, requires the triggering user to have write access, and its documentation says to review Claude’s changes before merging; auto mode blocks merging unapproved pull requests by default.
  • Important findings are closed by a person: fixed, or dismissed with a reason by the owner or reviewer.

Adding a second AI reviewer, or a stricter AI review level, improves what gets caught but doesn’t restore ownership; no number of AI reviews makes a person answerable. Banning AI-written code throws away the benefit instead of fixing the process. The control is the human owner plus an independent human approval, enforced at merge.

A merge gate

Skill 7.3The rules as a check CI can run before merge.

pr_gate.py (pr_gate.py)Optional 
"""Merge gate: every AI-assisted change has a named human owner and an independent human approval."""
import json
import sys

BOTS = {"claude[bot]", "deps-agent[bot]"}


def check(pr: dict, codeowners: dict) -> list[str]:
    problems = []
    # 1. A person owns the change. An agent's PR names the engineer who asked for it.
    owner = pr["requested_by"] if pr["author"] in BOTS else pr["author"]
    if owner is None or owner in BOTS:
        problems.append("no human owner: an agent opened this PR and nobody is named as accountable")
    # 2. Approval by a human who isn't the owner; an AI review is advice, not an approval.
    humans = {a for a in pr["approvals"] if a not in BOTS and a != owner}
    if not humans:
        problems.append("no independent human approval (the owner's and bots' approvals don't count)")
    # 3. Code owners of every touched area sign off.
    for path in pr["files"]:
        area = next((a for a in codeowners if path.startswith(a)), None)
        if area and not humans & set(codeowners[area]):
            problems.append(f"{path}: needs approval from a code owner of {area}")
    # 4. Important AI-review findings are fixed or dismissed by a person, with a reason.
    for f in pr["ai_findings"]:
        if f["severity"] == "Important" and f.get("resolved_by") not in humans | {owner}:
            problems.append(f"open Important finding: {f['title']}")
    # 5. The record shows that AI wrote it, so reviewers and auditors can tell.
    if pr["ai_assisted"] and not pr["trailer"]:
        problems.append("AI-assisted commits carry no attribution trailer")
    return problems


if __name__ == "__main__":
    data = json.load(open(sys.argv[1]))
    for pr in data["prs"]:
        print(pr["number"], check(pr, data["codeowners"]) or "ready to merge")

Keeping ownership real

Skill 7.3Practices that make the approval mean something.

  • The owner can explain the change: what it does, why, and how it was tested. A reviewer who asks and gets "Claude did it" has found the gap.
  • Small pull requests: ask for changes in reviewable pieces; a reviewer can’t own a diff they can’t read.
  • Attribution left on: Claude Code’s attribution setting controls the commit trailer and pull-request line (the older includeCoAuthoredBy is deprecated). Keeping it gives reviewers and incident reviews a record of what was AI-assisted.
  • Standards written down: CLAUDE.md for how code is written, REVIEW.md for what review flags, both changed through the same review.
  • Measured, not assumed: track defects and reverts in AI-assisted changes the way you would for any change, and adjust the review depth where they cluster.

Key takeaways

  • AI code review is advisory: it never approves or blocks, may miss issues, and "no findings" isn’t a clean bill.
  • The control that preserves ownership is a named human owner for every change plus approval by an independent human code owner, enforced by branch protection.
  • Agents push branches and open pull requests; they don’t approve or merge, and bot approvals don’t count.
  • Gate merges on open Important findings, resolved by a person, and keep attribution on for traceability.
  • More AI review improves detection but doesn’t replace an accountable person.
