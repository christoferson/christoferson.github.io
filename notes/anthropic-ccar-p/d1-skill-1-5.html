1.5: Value-Based Architectural Decisions

Choosing between competing designs by what they're worth to the business, measured, inside the limits you've been given: a budget, a latency target, or both. The best option is the most valuable one that fits, not the most capable one.

Overview

Skill 1.5

Value-Based Architectural Decisions: "Selecting the architectural option that maximizes measurable business outcome under a stated cost or SLA ceiling, weighing competing feature proposals against stated business value pillars such as efficiency, transformation, productivity, solution cost, and performance SLAs."

Exam items give two to four options with figures and a ceiling, and ask which to choose. The usual trap is the option with the best raw quality that breaks the ceiling. Choosing a model tier in depth is skill 2.1; diagnosing cost problems is in Domain 4.

Sources: the Claude API pricing documentation and Anthropic's model-selection guidance, checked on 20 November 2026 and paraphrased. The options and figures are my own; the scorecard is tested.

Running example. A broadband provider's support team handles 120,000 tickets a month at about $6.50 each when a person resolves them. Leadership allows $9,000 a month in model spend, and live chat must answer within 8 seconds at the 95th percentile.

Value pillars as measures

Skill 1.5The guide's pillars, each turned into something you can measure (my mapping).

  • Efficiency: work removed or cost avoided, such as tickets resolved without a person, times the cost of a person handling one.
  • Productivity: output per person for work that stays human, such as handling time per escalated ticket.
  • Transformation: something the business couldn't do before, such as 24-hour support in a new language; value it with the revenue or retention it's expected to bring, and say how you'll check.
  • Solution cost: model spend plus the cost to build, run and review; often a ceiling rather than a pillar to maximise.
  • Performance SLAs: latency, availability and throughput targets; usually a pass-or-fail constraint.

"Measurable" is the key word in the guide. A pillar without a number from an evaluation or a pilot can't decide between options.

The cost levers

Skill 1.5Claude API prices that change the arithmetic.

  • Model tier (per million input / output tokens): Opus 5.5 $4 / $20, Sonnet 5.5 $2 / $10, Haiku 5.5 $0.10 / $0.50 for prompts up to 100,000 tokens (higher above that), Fable 5.2 $8 / $40.
  • Prompt caching: cache reads cost 0.05 times the input price on Opus and Sonnet 5.5; writes cost more than plain input (1.25 times for a 5-minute cache). A large, stable prefix read many times is the big saving.
  • Batch API: 50% off input and output for asynchronous work, if the SLA allows waiting.
  • Fast mode: up to 2.5 times the output speed at premium pricing (Opus 5.5 at $8 / $40); not available with batches. It buys latency, not quality.
  • US-only inference: a 1.1 times multiplier on all token prices, when residency requires it.
  • Combining models: a cheap model for most traffic and a stronger one for the hard part, so most tokens are billed at the lower rate.

Ceilings first, then value

Skill 1.5The order of the decision.

  • Remove options that break a stated ceiling: over budget, or slower than the SLA. No amount of value elsewhere rescues them.
  • Among the rest, maximise the measured outcome: net value, or the stated primary pillar.
  • Check sensitivity: if a lower ceiling or a slightly worse resolution rate changes the answer, say so.
  • Prefer the simpler option when values are close: it's cheaper to run and change.

A scorecard

Skill 1.5Three designs, priced and checked against both ceilings.

value_scorecard.py (value_scorecard.py) 
"""Pick the support-automation design with the most measurable value inside the cost and SLA ceilings.

Prices: Claude API pricing page, November 2026 (USD per million tokens). Value inputs (resolution
rate, latency) come from the team's own evaluation runs, not from the model card."""
from dataclasses import dataclass

PRICE = {  # input, cache read, output
    "opus-5.5": (4.00, 0.20, 20.00), "sonnet-5.5": (2.00, 0.10, 10.00), "haiku-5.5": (0.10, 0.01, 0.50),
}
TICKETS = 120_000                 # per month
AGENT_COST = 6.50                 # cost of a ticket handled by a person
CEILING = 9_000                   # monthly model spend allowed
SLA_P95_SECONDS = 8               # first answer in live chat


@dataclass
class Option:
    name: str
    steps: list                   # (model, share of tickets, input tokens, cached share, output tokens)
    resolved: float               # share resolved without a person (measured on the eval set)
    p95_seconds: float            # measured
    fast_mode: bool = False       # Opus 5.5 fast mode: 2x price ($8/$40), faster output


def model_cost(o: Option) -> float:
    total = 0.0
    for model, share, tin, cached, tout in o.steps:
        pin, pcache, pout = PRICE[model]
        mult = 2 if o.fast_mode and model == "opus-5.5" else 1
        per = (tin * (1 - cached) * pin + tin * cached * pcache + tout * pout) / 1e6 * mult
        total += per * share * TICKETS
    return round(total, 2)


def evaluate(o: Option, ceiling: float = CEILING) -> dict:
    cost = model_cost(o)
    savings = o.resolved * TICKETS * AGENT_COST          # efficiency pillar, in money
    return {"option": o.name, "model_cost": cost, "savings": round(savings), "net": round(savings - cost),
            "within_cost": cost <= ceiling, "meets_sla": o.p95_seconds <= SLA_P95_SECONDS}


OPTIONS = [
    Option("A: Opus 5.5 for every ticket", [("opus-5.5", 1.0, 9_000, 0.0, 700)], resolved=0.46, p95_seconds=11),
    Option("B: Haiku triage, Sonnet answers, cached KB", [("haiku-5.5", 1.0, 1_500, 0.0, 60),
           ("sonnet-5.5", 0.7, 9_000, 0.8, 600)], resolved=0.41, p95_seconds=6),
    Option("C: as B, Opus 5.5 fast mode for escalations", [("haiku-5.5", 1.0, 1_500, 0.0, 60),
           ("sonnet-5.5", 0.7, 9_000, 0.8, 600), ("opus-5.5", 0.3, 9_000, 0.8, 700)],
           resolved=0.45, p95_seconds=7, fast_mode=True),
]


def choose(options=OPTIONS, ceiling: float = CEILING) -> dict:
    feasible = [r for r in (evaluate(o, ceiling) for o in options) if r["within_cost"] and r["meets_sla"]]
    return max(feasible, key=lambda r: r["net"]) if feasible else {}


if __name__ == "__main__":
    for r in map(evaluate, OPTIONS):
        print(r)
    print("choose at $9,000 ceiling:", choose()["option"])
    print("choose at $2,000 ceiling:", choose(ceiling=2_000)["option"])

choose at $9,000 ceiling: C: as B, Opus 5.5 fast mode for escalations
choose at $2,000 ceiling: B: Haiku triage, Sonnet answers, cached KB
  • Option A resolves the most tickets but its 11-second p95 breaks the SLA, so it's out, whatever its savings.
  • Option C wins at a $9,000 ceiling: Haiku triage and cached Sonnet answers for most tickets, plus Opus 5.5 in fast mode for the hardest 30%, nearly matching A's resolution within the SLA.
  • At a $2,000 ceiling the answer changes to B, because C's fast-mode escalations cost about $2,500 a month.
  • Simplification: the model ignores cache-write cost and assumes the measured resolution rates hold in production; a real decision would add both, plus the cost of building and reviewing.

"Choose the option with the highest quality score" ignores the ceilings the question states. Equally, "choose the cheapest" ignores value: B is cheapest but leaves about $30,000 a month of savings unclaimed when the budget allows C.

Weighing feature proposals

Skill 1.5When teams compete for the same budget.

  • Put each proposal in the same units: expected change in the measured pillar, cost, and effect on the SLA.
  • Ask which pillar the stakeholders named: if the brief prioritises efficiency, a transformation feature with a vague benefit loses to a measurable saving.
  • Count second-order costs: more human review, more evaluation, higher latency elsewhere in the system.
  • Stage uncertain bets: pilot the transformation feature with a measure and a stop rule rather than committing the budget.

Key takeaways

  • Turn each value pillar (efficiency, productivity, transformation, solution cost, performance SLAs) into a measured number; unmeasured value can't decide.
  • Apply stated ceilings first: an option over budget or slower than the SLA is out, however good.
  • Among feasible options, maximise the measured outcome, check sensitivity to the ceiling, and prefer the simpler option when close.
  • Cost levers: tier (Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 5.5 $0.10/$0.50), cache reads at 0.05x, batches at 50% off, fast mode at premium for latency, US-only inference at 1.1x, model combinations.
  • Compare competing proposals in the same units against the pillar stakeholders named; pilot uncertain bets.
