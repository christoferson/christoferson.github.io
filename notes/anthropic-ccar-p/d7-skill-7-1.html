7.1: Packaging and Distributing Claude Code Workflows

Taking a Claude Code workflow that works for one team and rolling it out to the whole engineering organisation: bundling it as a plugin, publishing it through a marketplace, and using managed settings to lock the safety-critical parts while teams keep control of the rest.

Overview

Skill 7.1

Packaging and Distributing Claude Code Workflows: "Evaluating how to package and distribute a Claude Code workflow proven on one team across an organization, including plugin contents (skills, hooks, subagents, commands, MCP configuration), marketplace, and managed settings, and deciding which controls are enforced centrally versus left to teams so the workflow stays safe when it runs unattended."

Exam items describe a rollout and ask what should go in the plugin, what managed settings should enforce, or why the workflow isn't safe in CI. Building the individual extensions (skills, hooks, subagents) is in the developer notes (CCDV-F 3.2); configuring permission modes is skill 7.2.

Turn one team’s workflow into something the whole organisation can install

Skill 7.1What this skill asks, and a workflow to roll out.

Questions on this skill describe a Claude Code workflow that works well on one team and ask how to package and distribute it across an organisation: what goes in the plugin, how it reaches every machine, what is locked centrally and what teams can change.

Take a payments team that built a secure code-review workflow in Claude Code: a review procedure, a subagent that checks dependencies, a hook that blocks edits to database migrations and secrets, and an internal code-search MCP server. Every engineering team should now use it.

Package the workflow as one plugin

Skill 7.1One unit that installs, updates and is checked together.

  • What it can contain: Skills (each also runnable as a slash command), subagents, hooks and MCP server configuration. Only plugin.json goes in .claude-plugin/; everything else sits at the plugin’s root.
  • Paths: hooks refer to their scripts through ${CLAUDE_PLUGIN_ROOT}, in quotes, because the installed location changes with each update.
  • Versions: a version number in plugin.json, and sources from git can be pinned to a tag or a commit.
  • Checking: claude plugin validate checks the plugin and the marketplace file before anyone installs them.
  • Cost and trust: an enabled plugin’s Skill and subagent descriptions are in context every turn, its MCP servers run, and its hooks fire with the user’s permissions. Anthropic doesn’t verify plugin contents, so treat installing one like installing software.

Publish it through a private marketplace

Skill 7.1A git repository that lists the organisation’s plugins.

A marketplace is a git repository with a .claude-plugin/marketplace.json file that lists plugins by name and where to get them; it can be private. Each entry’s name must match the plugin’s own name. Teams can also pick optional plugins from it.

Make it organisation-wide with managed settings

Skill 7.1Settings that users can’t override.

  • How they arrive: from the claude.ai admin console, through device management (MDM), or as a managed-settings.json file. Users can’t override them.
  • What they do here: extraKnownMarketplaces registers the marketplace on every machine, and enabledPlugins set to true installs and turns on a plugin. A user turning it off in their own settings doesn’t stop it loading; setting a plugin to false blocks it everywhere.
  • Per repository instead: the same keys in a repository’s .claude/settings.json apply once the folder is trusted, but each contributor still installs the plugin themselves.

Lock what keeps the workflow safe, and leave the rest to teams

Skill 7.1Central controls versus team choices.

  • Locked centrally (safety and supply chain): an allowlist of marketplace sources (strictKnownMarketplaces); the core review plugin turned on for everyone; sideloading turned off (disableSideloadFlags rejects --plugin-dir and the SDK’s plugins option); deny rules for secrets and force-pushes; and the sandbox on, with no way out of it.
  • Left to teams: optional plugins from the allowed marketplace, their own Skills and project instructions, and their own model and effort choices.
  • Stricter options, if the risk warrants them: allowManagedHooksOnly limits which hooks run, and strictPluginOnlyCustomization blocks Skills, subagents, hooks and MCP servers that don’t come from plugins. Both take freedom away from teams.
  • A detail that catches people out: an allowlist without a {"source": "skills-dir"} entry stops plugins kept in teams’ Skills directories from loading.

The managed settings below apply this policy, and the code after them checks that it locks the right things (including that missing allowlist entry):

managed-settings.json (managed-settings.json)Optional 
{
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "anthropics/claude-plugins-official" },
    { "source": "github", "repo": "acme/acme-dev-plugins" },
    { "source": "skills-dir" }
  ],
  "extraKnownMarketplaces": {
    "acme-dev-plugins": {
      "source": { "source": "github", "repo": "acme/acme-dev-plugins" },
      "autoUpdate": true
    }
  },
  "enabledPlugins": {
    "secure-review@acme-dev-plugins": true
  },
  "disableSideloadFlags": true,
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(git push --force *)"]
  },
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false
  }
}
check_policy.py (check_policy.py)Optional 
"""Check that a managed policy enforces the central controls and leaves team choices alone."""
import json
import sys

CENTRAL = {  # must be enforced centrally for the workflow to stay safe unattended
    "marketplace allowlist": lambda p: bool(p.get("strictKnownMarketplaces")),
    "org marketplace registered": lambda p: "acme-dev-plugins" in p.get("extraKnownMarketplaces", {}),
    "core plugin force-enabled": lambda p: p.get("enabledPlugins", {}).get("secure-review@acme-dev-plugins") is True,
    "no sideloaded plugins": lambda p: p.get("disableSideloadFlags") is True,
    "secrets denied": lambda p: any(".env" in r for r in p.get("permissions", {}).get("deny", [])),
    "sandbox on, no escape": lambda p: p.get("sandbox", {}).get("enabled") is True
                                         and p.get("sandbox", {}).get("allowUnsandboxedCommands") is False,
}
TEAM_CHOICES = ["team-extras@acme-dev-plugins"]          # left to teams: not forced on or off


def check(policy: dict) -> list[str]:
    problems = [f"missing central control: {name}" for name, ok in CENTRAL.items() if not ok(policy)]
    for p in TEAM_CHOICES:
        if p in policy.get("enabledPlugins", {}):
            problems.append(f"over-centralised: {p} is a team choice")
    if policy.get("strictKnownMarketplaces") and {"source": "skills-dir"} not in policy["strictKnownMarketplaces"]:
        problems.append("allowlist without skills-dir: plugins in teams' skills directories stop loading")
    return problems


if __name__ == "__main__":
    print(check(json.load(open(sys.argv[1]))) or "policy OK")

“Ask every team to install the plugin and follow the rules” leaves the safety controls optional. The opposite mistake, turning on every helper for everyone, takes away the teams’ ability to adapt. Lock what keeps the workflow safe; leave the rest.

Make it work the same in CI and containers

Skill 7.1When nobody is at the keyboard.

  • Managed settings still apply in headless and CI runs. Marketplaces and plugins install in the background, so set CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1 to wait for them before the first query.
  • Containers that can’t reach git: build a plugin seed into the image and point CLAUDE_CODE_PLUGIN_SEED_DIR at it. Seeds are read-only and never update themselves.
  • Cloud sessions receive only settings managed from the server, not MDM or file-based ones.
  • Confirm what loaded: a claude -p run with --output-format stream-json --verbose lists the loaded plugins in its first event.
  • Audit: OpenTelemetry events record plugin installs and loads across every machine.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A security team wants every engineer’s Claude Code to load the company review plugin, with no way to turn it off. What achieves that?
  1. A. Ask every team to install it
  2. B. Managed settings with extraKnownMarketplaces and enabledPlugins set to true
  3. C. A note in each repository’s README
  4. D. A user-level setting on each laptop
Answer
B
Why
Managed settings can’t be overridden by users, and force-enabling a plugin there loads it even if a user turns it off. Asking teams leaves it optional.
Question 2
Scenario
A plugin’s hook works in development but fails after an update moves the plugin. What should the hook use?
  1. A. An absolute path to the developer’s machine
  2. B. A quoted ${CLAUDE_PLUGIN_ROOT} path
  3. C. A relative path from the user’s home folder
  4. D. A URL
Answer
B
Why
The installed location changes with updates, so hooks refer to their scripts through the plugin root variable, in quotes.
Question 3
Scenario
An organisation allowlists its marketplaces, and teams’ plugins kept in their own Skills directories stop loading. What is the likely cause?
  1. A. The plugins are broken
  2. B. The allowlist has no {"source": "skills-dir"} entry
  3. C. Sideloading is enabled
  4. D. The sandbox is on
Answer
B
Why
An allowlist without that entry blocks plugins kept in Skills directories; adding it restores them while keeping the allowlist.
Question 4
Scenario
A CI container has no network access to git, but must run the review plugin. What fits?
  1. A. Install the plugin at the start of each job from git
  2. B. Build a plugin seed into the image and set CLAUDE_CODE_PLUGIN_SEED_DIR
  3. C. Skip the plugin in CI
  4. D. Copy the plugin into the prompt
Answer
B
Why
A seed baked into the image provides the plugin without network access; seeds are read-only and don’t update themselves.

Key takeaways

  • Package the workflow as one plugin (Skills, subagents, hooks, MCP configuration), versioned and validated, with hooks using a quoted ${CLAUDE_PLUGIN_ROOT}.
  • Publish it in a private marketplace, and make it organisation-wide with managed extraKnownMarketplaces and enabledPlugins, which users can’t override.
  • Lock the safety and supply-chain parts centrally (marketplace allowlist, core plugin on, no sideloading, deny rules, sandbox), and leave optional plugins, Skills and model choices to teams.
  • In CI and containers, wait for plugin installs, use a plugin seed where git isn’t reachable, and confirm what loaded.
  • Plugins run with the user’s permissions and aren’t verified by Anthropic, so review them like software.
