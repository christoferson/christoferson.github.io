7.1: Packaging and Distributing Claude Code Workflows

Taking a Claude Code workflow that works for one team and rolling it out to the whole engineering organisation: bundling it as a plugin, publishing it through a marketplace, and using managed settings to lock the safety-critical parts while teams keep control of the rest.

Overview

Skill 7.1

Packaging and Distributing Claude Code Workflows: "Evaluating how to package and distribute a Claude Code workflow proven on one team across an organization, including plugin contents (skills, hooks, subagents, commands, MCP configuration), marketplace, and managed settings, and deciding which controls are enforced centrally versus left to teams so the workflow stays safe when it runs unattended."

Exam items describe a rollout and ask what should go in the plugin, what managed settings should enforce, or why the workflow isn't safe in CI. Building the individual extensions (skills, hooks, subagents) is in the developer notes (CCDV-F 3.2); configuring permission modes is skill 7.2.

Sources: the Claude Code documentation on plugins, creating marketplaces, managing plugins for an organisation, settings and sandboxing, checked on 20 November 2026 and paraphrased. The company, files and code are my own; the policy check is tested.

Running example. A payments team built a secure code-review workflow in Claude Code: a review procedure, a dependency-checking subagent, a hook that blocks edits to migrations and secrets, and an internal code-search MCP server. Engineering wants it on every developer machine and in CI.

Packaging the workflow as a plugin

Skill 7.1One unit that installs together.

layout.txt (Marketplace and plugin layout) 
acme-dev-plugins/                          the organization's marketplace (a git repository)
  .claude-plugin/marketplace.json          name "acme-dev-plugins", owner, plugins[]
  plugins/
    secure-review/                         the workflow the payments team proved, packaged
      .claude-plugin/plugin.json           name "secure-review", version "1.4.0"
      skills/review-pr/SKILL.md            /secure-review:review-pr  (the review procedure)
      agents/dependency-auditor.md         subagent: read-only tools, checks new dependencies
      hooks/hooks.json                     PreToolUse: block edits to migrations/ and .env*
      scripts/block-paths.sh               called by the hook as "${CLAUDE_PLUGIN_ROOT}/scripts/block-paths.sh"
      .mcp.json                            the internal code-search MCP server (read-only)
    team-extras/                           optional helpers teams may enable or not
  • Contents: a plugin can carry skills (each also runnable as a command), subagents, hooks and MCP server configuration; only plugin.json goes in .claude-plugin/, everything else at the plugin root.
  • Paths: hooks refer to their scripts through ${CLAUDE_PLUGIN_ROOT}, quoted, because the installed location changes with updates.
  • Versioned: a version in plugin.json, and git sources can be pinned to a ref or commit.
  • Validated: claude plugin validate checks the plugin and the marketplace file before anyone installs.
  • Cost and trust: an enabled plugin's skill and agent descriptions are in context every turn, its MCP servers run, and its hooks fire, with the user's permissions; Anthropic doesn't verify plugin contents, so treat it like installing software.

Distributing it

Skill 7.1A marketplace, then managed settings.

  • The marketplace: a git repository with .claude-plugin/marketplace.json listing plugins by name and source; it can be private. Each entry's name must match its plugin's own name.
  • Managed settings make it organisation-wide: delivered from the claude.ai admin console, by MDM, or as a managed-settings.json file; users can't override them.
  • extraKnownMarketplaces registers the marketplace on every machine, and enabledPlugins set to true installs and force-enables a plugin; a user disabling it at their own scope doesn't stop it loading. Setting a plugin to false blocks it everywhere.
  • Per repository instead: the same keys in a repository's .claude/settings.json apply after the folder is trusted, and each contributor still installs the plugin.

Central controls versus team choices

Skill 7.1A managed policy, and a check that it locks the right things.

managed-settings.json (managed-settings.json) 
{
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "anthropics/claude-plugins-official" },
    { "source": "github", "repo": "acme/acme-dev-plugins" },
    { "source": "skills-dir" }
  ],
  "extraKnownMarketplaces": {
    "acme-dev-plugins": {
      "source": { "source": "github", "repo": "acme/acme-dev-plugins" },
      "autoUpdate": true
    }
  },
  "enabledPlugins": {
    "secure-review@acme-dev-plugins": true
  },
  "disableSideloadFlags": true,
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(git push --force *)"]
  },
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false
  }
}
check_policy.py (check_policy.py) 
"""Check that a managed policy enforces the central controls and leaves team choices alone."""
import json
import sys

CENTRAL = {  # must be enforced centrally for the workflow to stay safe unattended
    "marketplace allowlist": lambda p: bool(p.get("strictKnownMarketplaces")),
    "org marketplace registered": lambda p: "acme-dev-plugins" in p.get("extraKnownMarketplaces", {}),
    "core plugin force-enabled": lambda p: p.get("enabledPlugins", {}).get("secure-review@acme-dev-plugins") is True,
    "no sideloaded plugins": lambda p: p.get("disableSideloadFlags") is True,
    "secrets denied": lambda p: any(".env" in r for r in p.get("permissions", {}).get("deny", [])),
    "sandbox on, no escape": lambda p: p.get("sandbox", {}).get("enabled") is True
                                         and p.get("sandbox", {}).get("allowUnsandboxedCommands") is False,
}
TEAM_CHOICES = ["team-extras@acme-dev-plugins"]          # left to teams: not forced on or off


def check(policy: dict) -> list[str]:
    problems = [f"missing central control: {name}" for name, ok in CENTRAL.items() if not ok(policy)]
    for p in TEAM_CHOICES:
        if p in policy.get("enabledPlugins", {}):
            problems.append(f"over-centralised: {p} is a team choice")
    if policy.get("strictKnownMarketplaces") and {"source": "skills-dir"} not in policy["strictKnownMarketplaces"]:
        problems.append("allowlist without skills-dir: plugins in teams' skills directories stop loading")
    return problems


if __name__ == "__main__":
    print(check(json.load(open(sys.argv[1]))) or "policy OK")
  • Central (safety and supply chain): an allowlist of marketplace sources (strictKnownMarketplaces), the core review plugin force-enabled, sideloading turned off (disableSideloadFlags rejects --plugin-dir and the SDK's plugins option), deny rules for secrets and force-pushes, and the sandbox on with no unsandboxed escape.
  • Left to teams: optional plugins from the allowed marketplace, their own skills and project instructions, their own model and effort choices.
  • Stricter options, if needed: allowManagedHooksOnly restricts which hooks run, and strictPluginOnlyCustomization blocks skills, agents, hooks and MCP servers that don't come from plugins; both reduce team freedom, so use them where the risk warrants it.
  • A detail that bites: an allowlist without a {"source": "skills-dir"} entry stops plugins kept in teams' skills directories from loading; the check flags it.

"Ask every team to install the plugin and follow the rules" leaves the safety controls optional. The opposite mistake, force-enabling every helper, removes the teams' ability to adapt. Lock what keeps the workflow safe; leave the rest.

When it runs unattended

Skill 7.1CI and containers.

  • Managed settings still apply in headless and CI runs; marketplaces and plugins install in the background, so set CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1 to wait for them before the first query.
  • Containers without network access to git: build a plugin seed into the image and point CLAUDE_CODE_PLUGIN_SEED_DIR at it; seeds are read-only and never auto-update.
  • Cloud sessions receive only server-managed settings, not MDM or file-based ones.
  • Confirm what loaded: a claude -p run with --output-format stream-json --verbose lists the loaded plugins in its init event.
  • Audit: OpenTelemetry events record plugin installs and loads across the fleet.

Key takeaways

  • Package the workflow as one plugin (skills, subagents, hooks, MCP configuration), versioned, validated, with hooks using a quoted ${CLAUDE_PLUGIN_ROOT}.
  • Distribute through a marketplace; make it organisation-wide with managed extraKnownMarketplaces and enabledPlugins, which users can't override.
  • Centralise safety and supply chain: marketplace allowlist, force-enabled core plugin, no sideloading, deny rules, sandbox; leave optional plugins and project content to teams.
  • Plugins run with users' permissions and aren't verified by Anthropic; review them like software.
  • Unattended runs: managed settings still apply; sync plugin installs in CI, use seeds in offline containers, check the init event, and audit with telemetry.
