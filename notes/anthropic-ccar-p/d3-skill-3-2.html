Overview

Skill 3.2

Authentication and Authorization Posture: "Analyzing the authentication and authorization posture of an integration design to identify credential exposure and privilege escalation risks, and specifying the mitigation for each."

Exam items describe an integration (keys, tokens, MCP servers, service accounts) and ask which risk is present and what fixes it. Handling Anthropic API keys day to day is in the developer notes (CCDV-F 7.3); reducing what tools can do is skill 3.1.

Find where credentials leak and where a caller gets more than their rights

Skill 3.2What this skill asks you to find.

Questions on this skill describe how an integration authenticates (API keys, tokens, MCP servers, service accounts) and ask which risk is present and what fixes it. The risks fall into two groups:

  • Credential exposure: a key or token ends up somewhere an attacker can read it.
  • Privilege escalation: a user, through the agent, can do more than they’re allowed to do themselves.

The examples below use an agent that drafts and approves orders through an MCP server in front of the company’s back-office system. Staff use it from a mobile app and from the web.

Credential exposure: five ways secrets leak

Skill 3.2Each leak, and its fix.

A key shipped inside a client app

Anyone can read a key built into a web page or a mobile app. Call Claude from your own back end instead. Apple apps can use App Attest, which issues short-lived tokens limited to one workspace for the Messages API.

A long-lived key in production

A key that never expires is valid for anyone who gets a copy, for as long as nobody notices. Anthropic describes Workload Identity Federation, which exchanges your cloud identity for short-lived tokens, as preferred over long-lived keys. Otherwise keep keys in a secrets manager, give them an expiry, rotate them, and use IP allowlisting so a leaked key doesn’t work from anywhere else.

A key tied to a person

A personal key stops working when that person leaves and their account is removed, which can take production down. Production workloads should use service-account keys, which don’t depend on whoever created them. Admin keys (sk-ant-admin) belong only in tools that manage the organisation.

An unvetted local MCP server

A local MCP server runs with the user’s own permissions, and its start-up command can read and send away the user’s files. The MCP security guidance: install servers only from trusted sources, show the user the exact command before running it, and run it in a sandbox.

Secrets in prompts or tool results

Anything in the model’s context can end up repeated in its output or in logs. Give tools their credentials outside the model, for example through a proxy that adds them to outgoing requests.

Privilege escalation: six ways a caller gets more than their rights

Skill 3.2Each path, and how to close it.

One powerful account for everyone

If the agent calls the back-office system as an administrator account for every user, any user can ask the agent to approve an order they couldn’t approve themselves. Fix: act on behalf of the user with a token delegated by them, or check the user’s own rights before each action.

Passing the client’s token straight through

The MCP server forwards the token it received from the client to the back-office system. The MCP specification forbids this: a server must reject tokens that weren’t issued for it (an audience check), and passing tokens on bypasses the downstream system’s own controls and confuses the audit trail. Fix: check the audience, and get a separate token for the back-office system.

A confused deputy

An MCP server that acts as a proxy to a third-party sign-in service using one fixed client ID can be tricked into getting authorisation without the user’s consent. Fix: the proxy collects consent for each client and checks redirect addresses exactly.

Handles anyone can guess

If draft orders are referred to by sequential numbers passed as tool arguments, one user can act on another user’s draft by changing the number. Having a handle isn’t proof of who you are. Fix: random handles, tied on the server to the verified user.

Scopes that are too wide

A token with orders:* turns any leak into full access. Fix: start with the smallest scopes, and ask for more (a step-up) only when a privileged operation is first needed.

Instructions hidden in what the agent reads

A document or tool result can contain instructions, and an agent with broad credentials carries them out with those credentials. Narrow credentials limit what such an injection can do.

The checks every MCP server makes before acting

Skill 3.2Authorisation belongs in the server that performs the action.

  • Audience: the token was issued for this server, not for the back-office system or anything else.
  • Identity from the token: the user comes from the verified token, never from a field the client sends.
  • The user’s rights, not the server’s: a buyer who may draft orders but not approve them is refused an approval, even though the server’s own back-office credential could do it.
  • Its own token downstream: the server gets its own token for the back-office system instead of forwarding the client’s.

“Tell the agent to check the user’s role before approving” puts authorisation in the prompt, where an injected instruction or a simple mistake can skip it. The server that performs the action has to check.

Reviewing a design: seven findings

Skill 3.2The order-approval design checked against all of the above.

The original design has seven of these problems: a key in the mobile app, a long-lived production key, token passthrough, an administrator account for every user, guessable draft handles, a wildcard scope and an unvetted local MCP server. The code below reviews a design description and reports each finding with its fix; the test applies all seven fixes and checks that the review then finds nothing.

posture_review.py (posture_review.py)Optional 
"""Review the auth posture of an order-approval agent design: find credential exposure and privilege escalation.

Each finding names the risk and the mitigation. The second half is the check an MCP server must make
before acting on a request: the token was issued for this server, and the action is within the
caller's own rights, not the server's."""

DESIGN = {
    "anthropic_key":   {"kind": "static API key", "where": ["mobile app", "agent container env"], "expires": "never"},
    "backend_mcp_server":  {"accepts": "user SSO token", "forwards_token_downstream": True},
    "backend_credential":  {"principal": "backend-admin service account", "shared_by_all_users": True},
    "state_handles":   {"format": "sequential order-draft IDs", "bound_to_user": False},
    "oauth_scopes":    ["orders:*"],
    "local_mcp":       {"source": "unvetted npm package", "startup_command_shown_to_user": False},
}


def review(d: dict) -> list[tuple[str, str]]:
    f = []
    k = d["anthropic_key"]
    if "mobile app" in k["where"]:
        f.append(("exposure: key shipped in a client app", "call Claude from a back end; for Apple apps, App Attest's short-lived tokens"))
    if k["kind"] == "static API key" and k["expires"] == "never":
        f.append(("exposure: long-lived key in production", "Workload Identity Federation, or a key with an expiry, rotation, IP allowlisting"))
    if d["backend_mcp_server"]["forwards_token_downstream"]:
        f.append(("escalation: token passthrough", "accept only tokens issued for this MCP server (audience check); obtain its own downstream token"))
    c = d["backend_credential"]
    if c["shared_by_all_users"] and "admin" in c["principal"]:
        f.append(("escalation: agent acts with admin rights for every user", "act on behalf of the user (delegated token) or check the user's own entitlement per action"))
    s = d["state_handles"]
    if not s["bound_to_user"] or "sequential" in s["format"]:
        f.append(("escalation: guessable state handles", "random handles bound server-side to the verified user; possession is not authentication"))
    if any(x.endswith(":*") for x in d["oauth_scopes"]):
        f.append(("blast radius: wildcard scope", "minimal initial scopes; step-up challenges for privileged operations"))
    if not d["local_mcp"]["startup_command_shown_to_user"]:
        f.append(("exposure: unvetted local MCP server", "trusted sources only; show the exact command; run it sandboxed"))
    return f


def authorize(token: dict, action: dict, server_audience: str, entitlements: dict) -> str:
    """What the MCP server checks before executing an action."""
    if token.get("aud") != server_audience:
        return "reject: token not issued for this server"
    user = token["sub"]                                    # from the verified token, never from the client
    if action["type"] not in entitlements.get(user, set()):
        return f"reject: {user} may not {action['type']}"
    return "allow"


if __name__ == "__main__":
    for risk, fix in review(DESIGN):
        print(f"- {risk}\n    fix: {fix}")

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A mobile app calls the Claude API directly with an API key built into the app. What is the risk, and the fix?
  1. A. No risk; apps are compiled
  2. B. Anyone can extract the key; call Claude from your back end, or use App Attest tokens for Apple apps
  3. C. The key will expire
  4. D. The app will be slower
Answer
B
Why
A key shipped in a client can be read by anyone with the app. Keep keys on your server, or use short-lived tokens issued through App Attest for Apple apps.
Question 2
Scenario
An MCP server receives a user’s token and forwards the same token to the internal system behind it. What is wrong?
  1. A. Nothing; it saves a login
  2. B. Token passthrough: the server must reject tokens not issued for it and get its own token for the system behind it
  3. C. The token should be longer
  4. D. It should forward it twice
Answer
B
Why
The MCP specification forbids passthrough: it bypasses the downstream system’s controls and confuses the audit trail. Check the audience, then use the server’s own token downstream.
Question 3
Scenario
An agent acts for every user with one administrator account. A user who may only draft orders asks the agent to approve one. What should stop it?
  1. A. A prompt telling the agent to check roles
  2. B. The server checking the user’s own rights, from the verified token, before acting
  3. C. Nothing, because the admin account allows it
  4. D. A larger model
Answer
B
Why
Authorisation belongs in the server that performs the action, based on the user’s identity and rights, not the server’s own credential. A prompt can be skipped by a mistake or an injection.
Question 4
Scenario
Draft records are referred to by sequential numbers passed as tool arguments. What is the risk?
  1. A. None
  2. B. Another user can guess the next number and act on someone else’s draft; use random handles tied to the verified user
  3. C. The numbers run out
  4. D. Drafts will be slower
Answer
B
Why
Having a handle isn’t proof of identity. Random handles, checked on the server against the verified user, stop one user reaching another’s data.

Key takeaways

  • Look for two kinds of risk: credentials an attacker can read, and users who can do more through the agent than on their own.
  • Exposure fixes: no keys in client apps (back end, or App Attest for Apple apps); Workload Identity Federation or expiring, rotated, IP-allowlisted keys; service-account keys for production; vetted, sandboxed local MCP servers; credentials kept out of the model’s context.
  • Escalation fixes: act on behalf of the user or check their rights per action; no token passthrough; per-client consent in proxies; random handles bound to the verified user; minimal scopes with step-up.
  • Every MCP server checks the token’s audience, takes the user from the verified token, applies the user’s own rights, and gets its own downstream token.
  • Authorisation belongs in the server that acts, never in the prompt.
