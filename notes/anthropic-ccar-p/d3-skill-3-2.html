3.2: Authentication and Authorization Posture

Reading an integration design for two kinds of hole: credentials that can leak or outlive their purpose, and paths by which a user or an attacker gets the agent to do more than they're allowed to. Each one gets a specific fix.

Overview

Skill 3.2

Authentication and Authorization Posture: "Analyzing the authentication and authorization posture of an integration design to identify credential exposure and privilege escalation risks, and specifying the mitigation for each."

Exam items describe an integration (keys, tokens, MCP servers, service accounts) and ask which risk is present and what fixes it. Handling Anthropic API keys day to day is in the developer notes (CCDV-F 7.3); reducing what tools can do is skill 3.1.

Sources: the Claude authentication and Admin API documentation, and the Model Context Protocol security best practices, checked on 20 November 2026 and paraphrased. The design and code are my own and tested.

Running example. A manufacturer's procurement agent drafts and approves purchase orders through an MCP server in front of its ERP system. Staff use it from a mobile app and from the web.

Credential exposure

Skill 3.2Where secrets leak, and the fix for each.

  • Keys in client code: anyone can read a key shipped in a browser or mobile app. Call Claude from your back end; Apple apps can use App Attest, which issues short-lived, workspace-scoped tokens for the Messages API.
  • Long-lived static keys in production: Anthropic describes Workload Identity Federation (short-lived tokens exchanged from your cloud identity provider) as preferred over long-lived keys. Otherwise store keys in a secrets manager, set an expiry, rotate, and use IP allowlisting so a leaked key doesn't work elsewhere.
  • Keys that outlive people: personal keys stop when the user is removed; production workloads should use service account keys, which survive the creator, and admin keys (sk-ant-admin) belong only in organisation-management tooling.
  • Unvetted local MCP servers: a local server runs with the user's privileges; its startup command can exfiltrate files. The MCP guidance: install from trusted sources, show the exact command before running it, and sandbox it.
  • Secrets in prompts or tool results: anything in context can be repeated in output or logs; inject tool credentials outside the model (for example through an egress proxy).

Privilege escalation

Skill 3.2Ways a caller gets more than their own rights.

  • Shared high-privilege credential: the agent calls the ERP as an admin service account for everyone, so any user can ask it to approve orders they couldn't approve themselves. Act on behalf of the user with a delegated token, or check the user's own entitlement for each action.
  • Token passthrough: the MCP server forwards the client's token to the ERP. The MCP specification forbids this: servers must not accept tokens that weren't issued for them (an audience check), and passing tokens on bypasses downstream controls and muddies audit trails.
  • Confused deputy: an MCP proxy using one static client ID with a third-party authorisation server can be tricked into issuing codes without the user's consent; proxies must collect per-client consent and validate redirect URIs exactly.
  • Guessable state handles: a sequential draft ID passed as a tool argument lets one user act on another's draft. Possession of a handle isn't authentication: use random handles bound server-side to the verified user.
  • Wide scopes: a token with erp:* turns any leak into full access. Start with minimal scopes and step up for privileged operations when they're first needed.
  • Prompt injection through tools: content read by the agent can carry instructions; with broad credentials, an injection inherits them. Narrow credentials limit what an injection can do.

Reviewing a design

Skill 3.2Seven findings in the procurement design.

posture_review.py (posture_review.py)Optional 
"""Review the auth posture of a procurement agent design: find credential exposure and privilege escalation.

Each finding names the risk and the mitigation. The second half is the check an MCP server must make
before acting on a request: the token was issued for this server, and the action is within the
caller's own rights, not the server's."""

DESIGN = {
    "anthropic_key":   {"kind": "static API key", "where": ["mobile app", "agent container env"], "expires": "never"},
    "erp_mcp_server":  {"accepts": "user SSO token", "forwards_token_downstream": True},
    "erp_credential":  {"principal": "erp-admin service account", "shared_by_all_users": True},
    "state_handles":   {"format": "sequential order-draft IDs", "bound_to_user": False},
    "oauth_scopes":    ["erp:*"],
    "local_mcp":       {"source": "unvetted npm package", "startup_command_shown_to_user": False},
}


def review(d: dict) -> list[tuple[str, str]]:
    f = []
    k = d["anthropic_key"]
    if "mobile app" in k["where"]:
        f.append(("exposure: key shipped in a client app", "call Claude from a back end; for Apple apps, App Attest's short-lived tokens"))
    if k["kind"] == "static API key" and k["expires"] == "never":
        f.append(("exposure: long-lived key in production", "Workload Identity Federation, or a key with an expiry, rotation, IP allowlisting"))
    if d["erp_mcp_server"]["forwards_token_downstream"]:
        f.append(("escalation: token passthrough", "accept only tokens issued for this MCP server (audience check); obtain its own downstream token"))
    c = d["erp_credential"]
    if c["shared_by_all_users"] and "admin" in c["principal"]:
        f.append(("escalation: agent acts with admin rights for every user", "act on behalf of the user (delegated token) or check the user's own entitlement per action"))
    s = d["state_handles"]
    if not s["bound_to_user"] or "sequential" in s["format"]:
        f.append(("escalation: guessable state handles", "random handles bound server-side to the verified user; possession is not authentication"))
    if any(x.endswith(":*") for x in d["oauth_scopes"]):
        f.append(("blast radius: wildcard scope", "minimal initial scopes; step-up challenges for privileged operations"))
    if not d["local_mcp"]["startup_command_shown_to_user"]:
        f.append(("exposure: unvetted local MCP server", "trusted sources only; show the exact command; run it sandboxed"))
    return f


def authorize(token: dict, action: dict, server_audience: str, entitlements: dict) -> str:
    """What the ERP MCP server checks before executing an action."""
    if token.get("aud") != server_audience:
        return "reject: token not issued for this server"
    user = token["sub"]                                    # from the verified token, never from the client
    if action["type"] not in entitlements.get(user, set()):
        return f"reject: {user} may not {action['type']}"
    return "allow"


if __name__ == "__main__":
    for risk, fix in review(DESIGN):
        print(f"- {risk}\n    fix: {fix}")

The check every MCP server makes

Skill 3.2Before acting on any request.

  • Audience: the token was issued for this server, not for the ERP or anything else.
  • Identity from the token: the user comes from the verified token, never from a field the client supplies.
  • The user's rights, not the server's: Ana may draft orders but not approve them, so the server refuses her approval even though its own ERP credential could do it.
  • Downstream: the server obtains its own token for the ERP rather than forwarding the client's.

"Tell the agent to check the user's role before approving" puts authorisation in the prompt, where an injection or a mistake can skip it. Authorisation belongs in the server that performs the action.

Key takeaways

  • Credential exposure: no keys in clients (back end, or App Attest for Apple apps); prefer Workload Identity Federation; otherwise expiring, rotated, IP-allowlisted keys in a secrets manager; service accounts for production; vet local MCP servers.
  • Privilege escalation: a shared admin credential lets every user act as admin; act on behalf of the user or check each user's entitlement.
  • MCP servers must reject tokens not issued for them, must not pass client tokens downstream, and must not treat a state handle as authentication.
  • Proxies need per-client consent and exact redirect URI checks; scopes start minimal and step up.
  • Enforce authorisation in the server that acts, from the verified identity; never in the prompt.
