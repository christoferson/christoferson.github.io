3.3: Relieving the Binding Performance Constraint

When a system is either too slow or not accurate enough, finding which of the available changes fixes that one problem while giving away as little as possible on the other: the faster option that keeps accuracy, or the more accurate option that keeps latency.

Overview

Skill 3.3

Relieving the Binding Performance Constraint: "Evaluating candidate configuration changes (retrieval depth, model tier, caching, call pattern) for a system whose dominant constraint is accuracy or latency, and selecting the change that relieves the binding constraint at least cost to the other."

Exam items give a system's current accuracy and latency, a target that one of them misses, and several changes. Usually one change fixes the problem but breaks the other limit, one barely helps, and one fixes it cheaply. Choosing a model tier from scratch is skill 2.1; capacity under load is skill 1.2.

Fix the limit that’s failing, at the least cost to the other

Skill 3.3What this skill asks you to choose.

Questions on this skill give a system’s current accuracy and response time, targets for both, and a list of possible changes. One of the two measures misses its target. Usually one change fixes it but pushes the other measure past its own limit, one helps too little, and one fixes it cheaply. You choose that last one. The skill names four kinds of change: the model tier (and its effort setting), caching, how much is retrieved, and the pattern of calls.

Find the limit that binds, and the room left on the other

Skill 3.3One measure is failing; the other has headroom you can spend.

  • The binding constraint is the one missing its target now. That’s the one to fix.
  • Headroom is how far the other measure is from its limit. A change may use some of that room, but never all of it.
  • Measure each change on its own on the evaluation set: how much it moves accuracy and how much it moves the 95th-percentile response time. Changing two things at once hides which one helped and which one hurt.
  • Choose the change that brings the failing measure inside its target, keeps the other inside its limit, and uses the least headroom. If no single change is enough, choose the smallest combination that is.

Anthropic’s advice on order: get the prompt working well first, then reduce latency. Cutting latency too early hides what good performance looks like.

Model tier and effort move both measures, in opposite directions

Skill 3.3The biggest lever, and the most likely to break the other limit.

A faster tier or a lower effort setting cuts response time and usually costs some accuracy; a stronger tier or more effort does the opposite. Anthropic’s latency guide lists model choice first, with Haiku 5.5 for work where speed is critical and effort as the main way to control speed. Because it moves both measures, check the other limit before choosing it.

Caching makes long prompts faster at no cost to accuracy

Skill 3.3Often the cheapest fix for a latency problem.

When every call starts with the same long material, such as a product catalogue, caching it lets later calls reuse it. Anthropic says this generally shortens the time to the first token for long documents. The answer doesn’t change at all, so accuracy is untouched. If follow-up questions come more than 5 minutes apart, a 1-hour cache keeps the benefit.

Retrieval depth and reranking trade time for accuracy

Skill 3.3How much the model reads, and how well it’s chosen.

Retrieving more passages can raise accuracy, but it adds tokens and time; retrieving fewer is faster but can miss the answer. Reranking (ordering a larger set of candidates and passing only the best to the model) usually improves what the model sees at a smaller cost in time than reading everything. Measure both on your own questions.

Changing the call pattern saves time without changing the answer

Skill 3.3Parallel steps, fewer steps, shorter prompts, streaming.

Steps that don’t depend on each other can run at the same time; steps that do little can be merged; prompts and outputs can be shorter; the reply can be streamed so the user sees it start sooner. Anthropic’s latency guide recommends shorter prompts and outputs and streaming. None of these change what the model knows, so they cost little or no accuracy.

Worked example: one system too slow, one not accurate enough

Skill 3.3The same way of choosing, applied to each.

A product Q&A system that is too slow

It answers in 6.0 seconds against a 4.0-second target; accuracy is 92% against an 89% floor, so it has 3 points of headroom. The measured changes:

  • Switch to Sonnet 5.5: 2.6 seconds faster, but 4 points less accurate. That falls under the floor, so it’s out.
  • Cache the 30,000-token catalogue: 1.4 seconds faster, no accuracy lost.
  • Retrieve 8 passages instead of 20: 1.1 seconds faster, 1 point less accurate.
  • Run the lookup and the drafting at the same time: 0.9 seconds faster, no accuracy lost.

No single change that keeps accuracy above the floor is enough. Three pairs reach the target: caching plus fewer passages (3.5 seconds, 91%), fewer passages plus parallel calls (exactly 4.0 seconds, 91%), and caching plus parallel calls (3.7 seconds, 92%). Only the last uses none of the accuracy headroom, so it’s the choice.

A warranty-terms assistant that isn’t accurate enough

It’s 84% accurate against a 90% target, and answers in 2.1 seconds against a 5-second limit. The measured changes:

  • Switch to Opus 5.5: 7 points more accurate, 1.8 seconds slower.
  • Raise effort from low to medium: 5 points more accurate, 1.2 seconds slower. Not enough on its own.
  • Rerank the retrieved passages: 6 points more accurate, 0.9 seconds slower.
  • Retrieve 15 passages instead of 5: 3 points more accurate, 0.6 seconds slower. Not enough on its own.

Opus 5.5 and reranking both reach the target. Reranking uses half as much of the time headroom, so it’s the choice.

When nothing fits. With a tighter 2.5-second limit for the assistant, no change or pair works, and the right answer is to say so rather than pick the least bad option.

The code below holds both systems’ measurements and makes the choice:

binding_constraint.py (binding_constraint.py)Optional 
"""Pick the change that relieves the binding constraint at least cost to the other one.

Each candidate's effect was measured on the system's eval set (accuracy in points, p95 latency in
seconds). The selector keeps changes that fix the binding constraint without breaking the other limit,
then picks the one that costs the other constraint least; if no single change works, it tries pairs."""
from itertools import combinations


def select(current: dict, limits: dict, candidates: dict, binding: str) -> list[str]:
    other = "latency" if binding == "accuracy" else "accuracy"

    def apply(names):
        acc = current["accuracy"] + sum(candidates[n]["accuracy"] for n in names)
        lat = current["latency"] + sum(candidates[n]["latency"] for n in names)
        return {"accuracy": acc, "latency": lat}

    def ok(r):
        return r["accuracy"] >= limits["min_accuracy"] and r["latency"] <= limits["max_latency"]

    def harm(r):                                   # how much of the other constraint's headroom is used
        return current["latency"] - r["latency"] if other == "latency" else r["accuracy"] - current["accuracy"]

    for size in (1, 2):
        options = [(names, apply(names)) for names in combinations(candidates, size) if ok(apply(names))]
        if options:
            best = max(options, key=lambda o: harm(o[1]))
            return list(best[0])
    return []


# A: product Q&A for an electronics retailer, Opus 5.5. Binding: latency (p95 6.0 s, SLA 4.0 s).
QA_NOW = {"accuracy": 92.0, "latency": 6.0}
QA_LIMITS = {"min_accuracy": 89.0, "max_latency": 4.0}
QA_CANDIDATES = {
    "switch to Sonnet 5.5":            {"accuracy": -4.0, "latency": -2.6},   # breaks the accuracy floor
    "cache the 30k-token catalogue":   {"accuracy": 0.0,  "latency": -1.4},   # faster time to first token
    "retrieval depth 20 -> 8":         {"accuracy": -1.0, "latency": -1.1},
    "run lookup and drafting in parallel": {"accuracy": 0.0, "latency": -0.9},
}

# B: warranty-terms assistant, Sonnet 5.5. Binding: accuracy (84%, target 90%); latency 2.1 s of 5 s.
WT_NOW = {"accuracy": 84.0, "latency": 2.1}
WT_LIMITS = {"min_accuracy": 90.0, "max_latency": 5.0}
WT_CANDIDATES = {
    "switch to Opus 5.5":              {"accuracy": 7.0, "latency": 1.8},
    "effort low -> medium":            {"accuracy": 5.0, "latency": 1.2},
    "rerank retrieved passages":       {"accuracy": 6.0, "latency": 0.9},
    "retrieval depth 5 -> 15":         {"accuracy": 3.0, "latency": 0.6},
}

if __name__ == "__main__":
    print("A (latency-bound):", select(QA_NOW, QA_LIMITS, QA_CANDIDATES, "latency"))
    print("B (accuracy-bound):", select(WT_NOW, WT_LIMITS, WT_CANDIDATES, "accuracy"))

Why the obvious change usually loses

Skill 3.3The usual wrong answers.

  • “Switch to a faster model” for a latency problem. Often the biggest gain, but it can push accuracy under its floor.
  • “Upgrade the model” for an accuracy problem. It works, but it uses more time than a targeted fix such as reranking or better retrieval.
  • “Retrieve more”. More context doesn’t mean more accuracy if the right passage wasn’t among the candidates, and it adds time either way.
  • Changing two things at once without measuring each. You can’t tell which one helped, or which one hurt.

Improving the measure that isn’t failing, such as making a fast-enough system faster when accuracy is the problem, is the classic wrong answer: it spends effort and headroom without moving the number that fails.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A question-answering system takes 5.5 seconds against a 4-second target; accuracy is 93% against a 90% floor. Switching to a faster model would take it to 3 seconds but drop accuracy to 87%. What should the architect do?
  1. A. Switch to the faster model
  2. B. Look for changes that cut time without spending all the accuracy headroom, such as caching a long, repeated prompt or running steps in parallel
  3. C. Raise the accuracy floor
  4. D. Retrieve more passages
Answer
B
Why
Latency is the binding limit and accuracy has 3 points of headroom. The faster model breaks the floor; caching and parallel calls cut time without changing the answers.
Question 2
Scenario
An assistant is 82% accurate against an 88% target, and answers in 2 seconds against a 6-second limit. Upgrading the model adds 7 points and 2 seconds; reranking retrieved passages adds 7 points and 0.8 seconds. Which should be chosen?
  1. A. Upgrade the model
  2. B. Rerank the retrieved passages
  3. C. Both
  4. D. Neither
Answer
B
Why
Both fix the binding limit; reranking uses less of the time headroom, so it’s the choice. Combining both spends headroom for no extra benefit.
Question 3
Scenario
A team changes the model and the retrieval depth at once, and accuracy improves by 4 points. What is the problem?
  1. A. None; accuracy improved
  2. B. They can’t tell which change helped or which one hurt; each change should be measured on its own
  3. C. Accuracy can’t improve that much
  4. D. The latency target is ignored
Answer
B
Why
Measuring one change at a time shows each change’s effect on both limits, which is what the choice depends on.
Question 4
Scenario
A system is fast enough but not accurate enough. A colleague proposes streaming the replies. Why is that the wrong answer?
  1. A. Streaming is slower
  2. B. It improves the measure that isn’t failing and does nothing for accuracy
  3. C. Streaming isn’t supported
  4. D. It breaks caching
Answer
B
Why
Fix the binding constraint. Improving a limit that already passes uses effort without moving the failing number.

Key takeaways

  • Find the measure that misses its target (the binding constraint) and how much room the other measure has left.
  • Measure each change on its own; choose the one that fixes the failing measure while using the least of the other’s headroom, or the smallest combination if no single change is enough.
  • Model tier and effort move accuracy and latency in opposite directions; caching speeds up long prompts at no accuracy cost; reranking usually beats retrieving more; parallel calls, shorter prompts and streaming save time without changing the answer.
  • A faster model can break the accuracy floor; a bigger model can use more time than a targeted retrieval fix.
  • If nothing fits, say so; and get the prompt right before reducing latency.
