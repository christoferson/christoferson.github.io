3.3: Relieving the Binding Performance Constraint

When a system is either too slow or not accurate enough, finding which of the available changes fixes that one problem while giving away as little as possible on the other: the faster option that keeps accuracy, or the more accurate option that keeps latency.

Overview

Skill 3.3

Relieving the Binding Performance Constraint: "Evaluating candidate configuration changes (retrieval depth, model tier, caching, call pattern) for a system whose dominant constraint is accuracy or latency, and selecting the change that relieves the binding constraint at least cost to the other."

Exam items give a system's current accuracy and latency, a target that one of them misses, and several changes. Usually one change fixes the problem but breaks the other limit, one barely helps, and one fixes it cheaply. Choosing a model tier from scratch is skill 2.1; capacity under load is skill 1.2.

Sources: the Claude documentation on reducing latency and on prompt caching, and the models overview, checked on 20 November 2026 and paraphrased. The systems, measurements and code are my own; the code that makes the choice is tested.

The four levers

Skill 3.3What each tends to do to accuracy and latency.

  • Model tier and effort: the biggest lever on both. A faster tier or lower effort cuts latency and usually some accuracy; a stronger tier or higher effort does the reverse. Anthropic's latency guide names model choice first, with Haiku 5.5 for speed-critical work and effort as its main speed control.
  • Caching: reuses a long, stable prefix. Anthropic says it generally improves time to first token for long documents, and it changes nothing about the answer, so it costs no accuracy. A 1-hour cache helps when follow-ups come more than 5 minutes apart.
  • Retrieval depth and quality: more passages can raise accuracy but add tokens and time; fewer passages are faster but can miss the answer. Reranking a candidate set improves what reaches the model at a smaller latency cost than reading everything (measure it on your own questions).
  • Call pattern: running independent steps in parallel, merging steps, streaming the reply, or trimming prompt and output length. Anthropic's guide recommends shorter prompts and outputs and streaming; none of these change what the model knows.

Anthropic's advice on order: get the prompt working well first, then reduce latency; cutting latency early hides what good performance looks like.

Identify the binding constraint first

Skill 3.3One constraint is failing; the other has headroom.

  • Binding: the one that misses its target now. That's the one to fix.
  • Headroom: how far the other constraint is from its limit. A change may spend some of it, but never all.
  • Measure each candidate on the evaluation set: its change in accuracy and in p95 latency, one change at a time.
  • Choose: among changes that bring the binding constraint inside its limit without pushing the other past its limit, the one that spends the least headroom. If no single change is enough, the smallest combination.

Two systems, one way to choose

Skill 3.3A latency-bound Q&A system and an accuracy-bound assistant.

binding_constraint.py (binding_constraint.py)Optional 
"""Pick the change that relieves the binding constraint at least cost to the other one.

Each candidate's effect was measured on the system's eval set (accuracy in points, p95 latency in
seconds). The selector keeps changes that fix the binding constraint without breaking the other limit,
then picks the one that costs the other constraint least; if no single change works, it tries pairs."""
from itertools import combinations


def select(current: dict, limits: dict, candidates: dict, binding: str) -> list[str]:
    other = "latency" if binding == "accuracy" else "accuracy"

    def apply(names):
        acc = current["accuracy"] + sum(candidates[n]["accuracy"] for n in names)
        lat = current["latency"] + sum(candidates[n]["latency"] for n in names)
        return {"accuracy": acc, "latency": lat}

    def ok(r):
        return r["accuracy"] >= limits["min_accuracy"] and r["latency"] <= limits["max_latency"]

    def harm(r):                                   # how much of the other constraint's headroom is used
        return current["latency"] - r["latency"] if other == "latency" else r["accuracy"] - current["accuracy"]

    for size in (1, 2):
        options = [(names, apply(names)) for names in combinations(candidates, size) if ok(apply(names))]
        if options:
            best = max(options, key=lambda o: harm(o[1]))
            return list(best[0])
    return []


# A: product Q&A for an electronics retailer, Opus 5.5. Binding: latency (p95 6.0 s, SLA 4.0 s).
QA_NOW = {"accuracy": 92.0, "latency": 6.0}
QA_LIMITS = {"min_accuracy": 89.0, "max_latency": 4.0}
QA_CANDIDATES = {
    "switch to Sonnet 5.5":            {"accuracy": -4.0, "latency": -2.6},   # breaks the accuracy floor
    "cache the 30k-token catalogue":   {"accuracy": 0.0,  "latency": -1.4},   # faster time to first token
    "retrieval depth 20 -> 8":         {"accuracy": -1.0, "latency": -1.1},
    "run lookup and drafting in parallel": {"accuracy": 0.0, "latency": -0.9},
}

# B: warranty-terms assistant, Sonnet 5.5. Binding: accuracy (84%, target 90%); latency 2.1 s of 5 s.
WT_NOW = {"accuracy": 84.0, "latency": 2.1}
WT_LIMITS = {"min_accuracy": 90.0, "max_latency": 5.0}
WT_CANDIDATES = {
    "switch to Opus 5.5":              {"accuracy": 7.0, "latency": 1.8},
    "effort low -> medium":            {"accuracy": 5.0, "latency": 1.2},
    "rerank retrieved passages":       {"accuracy": 6.0, "latency": 0.9},
    "retrieval depth 5 -> 15":         {"accuracy": 3.0, "latency": 0.6},
}

if __name__ == "__main__":
    print("A (latency-bound):", select(QA_NOW, QA_LIMITS, QA_CANDIDATES, "latency"))
    print("B (accuracy-bound):", select(WT_NOW, WT_LIMITS, WT_CANDIDATES, "accuracy"))

  • A, latency-bound (6.0 s against a 4.0 s SLA, accuracy 92% against an 89% floor): Sonnet 5.5 would reach 3.4 s but drop accuracy to 88%, under the floor. No single remaining change is enough; caching the catalogue plus parallel calls reaches 3.7 s with no accuracy lost.
  • B, accuracy-bound (84% against a 90% target, 2.1 s of a 5 s SLA): Opus 5.5 and reranking both reach the target; reranking costs 0.9 s against Opus's 1.8 s, so it's the choice. Raising effort or retrieval depth alone falls short.
  • When nothing fits: with a tighter 2.5 s limit, no change or pair works, and the code says so rather than picking the least bad option.

Why the obvious change loses

Skill 3.3The usual distractors.

  • "Switch to a faster model" for a latency problem: often the biggest gain, but it can push accuracy under its floor; check the other constraint before choosing it.
  • "Upgrade the model" for an accuracy problem: works, but spends more latency than a targeted fix such as reranking or better retrieval.
  • "Retrieve more": more context isn't more accuracy if the right passage wasn't in the candidate set; it adds latency either way.
  • Changing two things at once without measuring each: you can't tell which one helped, or which one hurt.

Optimising the constraint that isn't binding (making a fast-enough system faster when accuracy is the problem) is the classic wrong answer: it uses effort and headroom without moving the failing number.

Key takeaways

  • Find the binding constraint (the one missing its target) and the headroom on the other.
  • Levers: model tier and effort (big effect on both), caching (faster time to first token for long prefixes, no accuracy cost), retrieval depth and reranking, call pattern (parallel steps, shorter prompts and outputs, streaming).
  • Measure each change on the evaluation set; choose the one that fixes the binding constraint while spending least of the other's headroom, or the smallest combination if no single change is enough.
  • Faster models can break the accuracy floor; bigger models can spend latency that a targeted retrieval fix wouldn't.
  • Get the prompt right first; then reduce latency, one technique at a time, with quality checked after each.
