3.7: Progressive Discovery vs. Monolithic Context Loading

Two ways to give an agent what it needs: put it all in the prompt at the start, or give it a map and let it fetch pieces as it goes. One is faster when everything fits; the other is the only option when it doesn't, and often the more accurate one when most of the material isn't relevant.

Overview

Skill 3.7

Progressive Discovery vs. Monolithic Context Loading: "Evaluating progressive discovery against loading everything into context up front for a task with stated context demands and latency tolerance, and selecting the strategy whose context economics fit the workload."

Exam items state how much material a task might need and how long it can take, and ask which loading strategy fits. Choosing a retrieval architecture is skill 3.5; trimming tools and results is skill 3.1; the cost arithmetic of a context is skill 2.4.

Load everything up front, or let the agent fetch what it needs

Skill 3.7What this skill asks you to choose.

An agent can be given everything it might need before it starts (monolithic loading), or given a map and left to fetch pieces as it needs them (progressive discovery). Questions on this skill say how much material the task could need and how long an answer may take, and ask which strategy fits. The two differ in speed, cost, accuracy and what they can handle at all.

Monolithic loading: one call, nothing to look up

Skill 3.7Everything goes into the prompt before the first turn.

The whole of the material is in the prompt from the start. There’s one round trip, nothing to search for, and because the prompt is the same every time, it caches well. For a knowledge base under about 200,000 tokens, Anthropic’s advice is simply to include all of it.

Progressive discovery: a map, and tools to fetch the pieces

Skill 3.7The agent loads context when it needs it.

The prompt holds a map (names, descriptions, file paths, queries) and the agent uses tools to load the pieces a task turns out to need. Anthropic’s context-engineering post calls this just-in-time context: the agent keeps short references and finds what’s relevant by exploring.

Anthropic’s own products mix both strategies. Claude Code puts CLAUDE.md in context up front and finds everything else with grep and glob. Agent Skills keep only each Skill’s name and description (about 100 tokens) loaded until one is needed. The tool search tool loads tool definitions on demand.

Each piece fetched costs another round trip

Skill 3.7Latency.

Monolithic loading answers in one round trip. Progressive discovery adds a model turn and a tool call for every piece it loads, and Anthropic notes that exploring at run time is slower than retrieving prepared data. Where someone is waiting a few seconds for an answer, that difference decides the question.

The costs grow in different ways

Skill 3.7Tokens.

Monolithic loading pays for the whole of the material on every call, though an unchanging prompt is cached and read at a fraction of the price (0.05 times the input price on Opus and Sonnet 5.5). Progressive discovery pays only for the map and what it loads, but each later turn re-reads everything earlier turns loaded, so a long exploration grows expensive too.

More context isn’t always better context

Skill 3.7Accuracy, and the hard limit.

Anthropic describes “context rot”: as the context grows, the model gets worse at recalling what’s in it, so context is a limited resource with diminishing returns. A huge prompt that is mostly irrelevant can hurt the answer as well as cost more. And the context window itself (1M tokens on current models) is a hard limit: material larger than that can only be discovered piece by piece. The risk on the other side is that an agent without good guidance wastes its context on the wrong tools and dead ends.

Worked example: two workloads, opposite answers

Skill 3.7Tokens per task and round trips, side by side.

  • Questions about a product specification, answered in seconds. The specification is 120,000 tokens and rarely changes, and there are thousands of quick questions. Loading it all answers in one round trip (about 2.5 seconds), and caching makes the repeated 120,000 tokens cheap. Discovering it would take four round trips (about 11 seconds), which breaks the expectation of an answer within 3 seconds. Load it all.
  • Changes to a large code repository. The repository is 6 million tokens, which can’t fit in a 1M-token window, and each task needs about eight files. Discovery is the only option, and minutes of latency are acceptable. Discover as you go, and clear old tool results as they pile up.

The code below models both workloads under both strategies; its per-step latencies are assumptions:

loading_strategy.py (loading_strategy.py)Optional 
"""Monolithic loading vs progressive discovery: tokens and round trips per task for two workloads.

Monolithic: everything relevant is in the prompt from the start (cacheable if it's stable).
Progressive: the prompt holds an index (names, descriptions, paths); the agent loads pieces with tools.
Latency per step and per round trip are illustrative assumptions; measure your own."""

STEP_SECONDS = 2.5          # one model turn that ends in a tool call (assumed)
TOOL_SECONDS = 0.4          # one tool call (assumed)


def monolithic(corpus_tokens: int, tasks: int) -> dict:
    return {"input_tokens_per_task": corpus_tokens, "round_trips": 1,
            "first_answer_s": STEP_SECONDS, "fits": corpus_tokens <= 1_000_000}   # 1M-token context window


def progressive(index_tokens: int, pieces_needed: int, piece_tokens: int) -> dict:
    trips = 1 + pieces_needed                  # one turn per lookup, then the answer
    # each turn re-reads the growing context: index + pieces loaded so far
    tokens = sum(index_tokens + i * piece_tokens for i in range(trips))
    return {"input_tokens_per_task": tokens, "round_trips": trips,
            "first_answer_s": round(trips * STEP_SECONDS + pieces_needed * TOOL_SECONDS, 1), "fits": True}


WORKLOADS = {
    # many quick questions over one stable 120k-token product spec; answers needed in ~3 s
    "spec Q&A (latency-sensitive)": (monolithic(120_000, 5_000), progressive(2_000, 3, 4_000)),
    # deep tasks over a 6M-token monorepo; each task touches ~8 files; minutes are acceptable
    "monorepo changes (context-heavy)": (monolithic(6_000_000, 40), progressive(3_000, 8, 6_000)),
}

if __name__ == "__main__":
    for name, (mono, prog) in WORKLOADS.items():
        print(name)
        print(f"  monolithic : {mono}")
        print(f"  progressive: {prog}")

“Load everything, the context window is 1M tokens” ignores context rot and the per-call cost of material that is mostly irrelevant. “Always discover just in time” ignores latency when everything needed would fit and cache.

Make the map good enough to navigate

Skill 3.7How to design progressive discovery so the agent finds the right piece first.

  • A clear index. Meaningful names, short descriptions and paths that say what’s inside, so the agent picks the right piece the first time.
  • A core loaded up front. Load what nearly every task needs (conventions, the data schema, the most-used tools) and discover the rest; Anthropic suggests such a hybrid suits material that changes less often.
  • Summaries before full text. The start or end of a large file, or a query that counts rather than lists, so whole objects enter the context only when needed.
  • Keep the growth in check. Clear old tool results or compact during long runs, or hand bulk reading to a subagent.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A support assistant answers questions about a 60,000-token product manual that changes monthly. Customers expect a reply within 3 seconds. Which loading strategy fits?
  1. A. Progressive discovery with search tools over the manual
  2. B. Load the whole manual into the prompt and cache it
  3. C. A subagent per chapter
  4. D. Load only the table of contents and fetch chapters as needed
Answer
B
Why
The manual fits comfortably and caches well, and one round trip is the only way to stay within a few seconds. Discovering chapters adds a round trip per piece, which breaks the time limit; subagents add whole agent runs.
Question 2
Scenario
An agent must make changes in a codebase of about 4 million tokens. Each task touches a handful of files, and tasks may take several minutes. Which strategy fits?
  1. A. Load the whole codebase into a 1M-token context
  2. B. Progressive discovery: a map of the repository plus search and read tools
  3. C. Load a random sample of files up front
  4. D. Summarise the whole codebase once and load the summary
Answer
B
Why
The codebase is larger than the context window, so it can only be explored piece by piece, and minutes of latency are acceptable. A random sample misses what the task needs; a summary loses the exact code the change depends on.
Question 3
Scenario
A team loads 600,000 tokens of policy documents into every call “because the window is 1M”. Answers to simple questions have become less reliable and costs are high. What explains the problem?
  1. A. The cache is too short
  2. B. Context rot: recall falls as mostly irrelevant context grows, and every call pays for it
  3. C. The model needs more output tokens
  4. D. Monolithic loading can’t be cached
Answer
B
Why
Anthropic describes context rot: as the context grows, the model recalls what’s in it less well, so a huge, mostly irrelevant prompt can hurt as well as cost. Monolithic prompts can be cached; that lowers cost but doesn’t fix recall.
Question 4
Scenario
An agent using progressive discovery often opens the wrong files before finding the right one, wasting turns and context. Which change helps most?
  1. A. Load every file up front instead
  2. B. Give the map meaningful names, short descriptions and paths that say what’s inside
  3. C. Raise the turn limit
  4. D. Switch to a larger model
Answer
B
Why
Discovery is only as good as its map: clear names and descriptions let the agent pick the right piece first time. Loading everything may not fit; more turns or a bigger model spend more without fixing the guidance.

Key takeaways

  • Monolithic loading: one round trip and good caching; best when the material fits comfortably (under about 200,000 tokens) and answers must be fast.
  • Progressive discovery: a map plus tools to fetch pieces; needed when the material is larger than the window or mostly irrelevant to any one task; slower per task.
  • Weigh latency (round trips), tokens (the whole corpus per call versus a context that grows), accuracy (context rot) and the hard window limit.
  • Anthropic’s products mix both: CLAUDE.md up front and grep later; Skill names up front and bodies on demand; tool search for large tool sets.
  • Make discovery work with a clear index, a core loaded up front, summaries before full text, and clearing or subagents to contain growth.
