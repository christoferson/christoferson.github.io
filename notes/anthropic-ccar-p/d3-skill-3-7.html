3.7: Progressive Discovery vs. Monolithic Context Loading

Two ways to give an agent what it needs: put it all in the prompt at the start, or give it a map and let it fetch pieces as it goes. One is faster when everything fits; the other is the only option when it doesn't, and often the more accurate one when most of the material isn't relevant.

Overview

Skill 3.7

Progressive Discovery vs. Monolithic Context Loading: "Evaluating progressive discovery against loading everything into context up front for a task with stated context demands and latency tolerance, and selecting the strategy whose context economics fit the workload."

Exam items state how much material a task might need and how long it can take, and ask which loading strategy fits. Choosing a retrieval architecture is skill 3.5; trimming tools and results is skill 3.1; the cost arithmetic of a context is skill 2.4.

Sources: Anthropic's posts on effective context engineering and Contextual Retrieval, and the Agent Skills and tool search documentation, checked on 20 November 2026 and paraphrased. The workloads and model are my own; per-step latencies in the model are assumptions, and it is tested.

The two strategies

Skill 3.7And where Anthropic uses each.

  • Monolithic loading: everything the task might need goes into the prompt before the first turn. One call, nothing to look up, and a stable prompt caches well. For knowledge bases under about 200,000 tokens, Anthropic's advice is simply to include the whole thing.
  • Progressive discovery: the prompt holds a map (names, descriptions, file paths, queries) and the agent loads pieces with tools when it needs them. Anthropic's context-engineering post calls this just-in-time context and progressive disclosure: the agent keeps lightweight references and discovers relevant context through exploration.
  • Anthropic's own products use both: Claude Code puts CLAUDE.md in context up front and finds everything else with grep and glob; Agent Skills keep only each Skill's name and description (about 100 tokens) loaded until one is needed; the tool search tool loads 3–5 tool definitions on demand.

The economics

Skill 3.7What each strategy costs, and when.

  • Latency: monolithic is one round trip; progressive adds a model turn and a tool call per piece. Anthropic notes that run-time exploration is slower than retrieving pre-computed data.
  • Tokens: monolithic pays for the whole corpus every call, though a stable prefix is cached (reads at 0.05 times the input price on Opus and Sonnet 5.5). Progressive pays for the map plus what it loads, but each later turn re-reads what earlier turns loaded.
  • Accuracy: Anthropic describes context rot: as context grows, the model's ability to recall information from it decreases, so context is a finite resource with diminishing returns. A huge, mostly irrelevant prompt can hurt as well as cost.
  • Hard limit: the context window (1M tokens on current models). Anything beyond it can only be discovered.
  • Risk on the progressive side: without good guidance, an agent can waste context on wrong tools and dead ends.

Two workloads

Skill 3.7Tokens per task and round trips, side by side.

"""Monolithic loading vs progressive discovery: tokens and round trips per task for two workloads.

Monolithic: everything relevant is in the prompt from the start (cacheable if it's stable).
Progressive: the prompt holds an index (names, descriptions, paths); the agent loads pieces with tools.
Latency per step and per round trip are illustrative assumptions; measure your own."""

STEP_SECONDS = 2.5          # one model turn that ends in a tool call (assumed)
TOOL_SECONDS = 0.4          # one tool call (assumed)


def monolithic(corpus_tokens: int, tasks: int) -> dict:
    return {"input_tokens_per_task": corpus_tokens, "round_trips": 1,
            "first_answer_s": STEP_SECONDS, "fits": corpus_tokens <= 1_000_000}   # 1M-token context window


def progressive(index_tokens: int, pieces_needed: int, piece_tokens: int) -> dict:
    trips = 1 + pieces_needed                  # one turn per lookup, then the answer
    # each turn re-reads the growing context: index + pieces loaded so far
    tokens = sum(index_tokens + i * piece_tokens for i in range(trips))
    return {"input_tokens_per_task": tokens, "round_trips": trips,
            "first_answer_s": round(trips * STEP_SECONDS + pieces_needed * TOOL_SECONDS, 1), "fits": True}


WORKLOADS = {
    # many quick questions over one stable 120k-token product spec; answers needed in ~3 s
    "spec Q&A (latency-sensitive)": (monolithic(120_000, 5_000), progressive(2_000, 3, 4_000)),
    # deep tasks over a 6M-token monorepo; each task touches ~8 files; minutes are acceptable
    "monorepo changes (context-heavy)": (monolithic(6_000_000, 40), progressive(3_000, 8, 6_000)),
}

if __name__ == "__main__":
    for name, (mono, prog) in WORKLOADS.items():
        print(name)
        print(f"  monolithic : {mono}")
        print(f"  progressive: {prog}")

  • Spec Q&A, latency-sensitive: a stable 120,000-token product spec and thousands of quick questions. Monolithic answers in one round trip, and caching makes the repeated 120,000 tokens cheap; progressive needs four round trips, which breaks a 3-second expectation. Load it all.
  • Monorepo changes, context-heavy: 6 million tokens can't fit a 1M window, and each task needs about eight files. Progressive is the only option, and minutes of latency are acceptable. Discover as you go, with context editing for what piles up.

"Load everything, the context window is 1M tokens" ignores context rot and per-call cost for material that's mostly irrelevant. "Always discover just in time" ignores latency when everything needed would fit and cache.

Designing progressive discovery well

Skill 3.7Making the map good enough to navigate.

  • A good index: meaningful names, short descriptions and paths that say what's inside, so the agent picks the right piece first time.
  • Hybrid: load what nearly every task needs up front (conventions, the schema, the top tools) and discover the rest; Anthropic suggests a hybrid suits less dynamic content.
  • Load summaries before full text: head or tail of a large file, a query that counts rather than lists, so whole objects never enter context unless needed.
  • Keep the growth in check: clear old tool results or compact during long runs (skill 2.6), or push bulk reading into a subagent.

Key takeaways

  • Monolithic: one round trip, caches well, best when the material fits comfortably (Anthropic: under about 200,000 tokens) and latency is tight.
  • Progressive discovery: a map plus tools to fetch pieces; needed when material exceeds the window or most of it is irrelevant to any one task; slower per task.
  • Weigh latency (round trips), tokens (whole corpus per call versus a growing context), accuracy (context rot) and the hard window limit.
  • Anthropic's products mix both: CLAUDE.md up front and grep later; Skills metadata up front and bodies on demand; tool search for large tool sets.
  • Make discovery work with a clear index, a hybrid core loaded up front, summaries before full text, and context editing or subagents to contain growth.
