2.4: Context Composition and Token Economics

Taking a request apart section by section (tool definitions, instructions, documents, history, tool results), pricing each at real call volumes with caching in mind, and cutting the tokens that don't help the task while keeping the ones that do.

Overview

Skill 2.4

Context Composition and Token Economics: "Analyzing context composition and caching behavior against a token budget and a defined call volume to determine where token consumption can be reduced without loss of task-relevant information."

Exam items give a request's composition, a call volume and a budget, and ask which change cuts cost without hurting results. Placing breakpoints and packaging reusable content is skill 2.5; managing context over a long session is skill 2.6.

Sources: the Claude prompt caching, pricing and rate limits documentation, checked on 19 and 20 November 2026 and paraphrased. The agent and its token counts are my own; the budget model is tested.

Running example. An online retailer's support agent on Sonnet 5.5 makes 200,000 model calls a month, about four per conversation. Finance wants the input bill roughly halved.

How caching changes the arithmetic

Skill 2.4The rules that decide what a token really costs.

  • Prefix only: a cache covers everything up to a breakpoint, in the order tools, system, then messages. Anything that varies per request breaks the prefix from that point on.
  • Prices: writing costs 1.25 times the input price for a 5-minute cache (2 times for 1 hour); reading costs 0.05 times on Opus and Sonnet 5.5 (0.1 times on most others, 0.025 times on Fable 5.2).
  • Minimum length: 512 tokens on the current models (1,024 on some older ones); shorter prefixes are silently not cached.
  • Invalidation: changing tool definitions invalidates the whole cache; changing system-level settings invalidates system and messages; changing tool_choice or images invalidates messages.
  • Throughput too: cache reads don't count toward the input-tokens-per-minute rate limit (skill 1.2).

So a token's cost depends on where it sits: a stable token near the front is cheap after the first call; a token that changes every call is paid in full every time.

A budget by section

Skill 2.4Three compositions at 200,000 calls a month.

context_budget.py (context_budget.py)Optional 
"""Where do a support agent's input tokens go, and which cuts keep the task-relevant information?

Sonnet 5.5 prices (USD per million tokens, Nov 2026): input $2.00, 5-minute cache write $2.50,
cache read $0.10. Caching needs a prefix of at least 512 tokens and covers everything before the
breakpoint, in the order tools -> system -> messages."""

CALLS = 200_000          # model calls a month
TURNS = 4                # calls per conversation: the cache is written once, read on later turns

BEFORE = [  # section, tokens, stable across calls?
    ("tool definitions (40 tools; 6 used in 95% of chats)", 14_000, True),
    ("system prompt", 3_000, True),
    ("all 22 policy documents, pasted in", 30_000, True),
    ("conversation history", 8_000, False),
    ("order lookup results (full JSON)", 6_000, False),
    ("customer message", 300, False),
]

KEEP_ALL_POLICIES = [   # alternative: no retrieval risk, everything stable is cached
    ("tool definitions (6 core tools; others loaded on demand)", 3_000, True),
    ("system prompt", 3_000, True),
    ("all 22 policy documents, pasted in", 30_000, True),
    ("conversation history", 8_000, False),
    ("order lookup results (fields the agent needs)", 900, False),
    ("customer message", 300, False),
]

AFTER = [
    ("tool definitions (6 core tools; others loaded on demand)", 3_000, True),
    ("system prompt", 3_000, True),
    ("policy sections retrieved for this question (top 3)", 4_000, False),
    ("conversation history", 8_000, False),
    ("order lookup results (fields the agent needs)", 900, False),
    ("customer message", 300, False),
]


def monthly_cost(sections, cache: bool) -> float:
    stable = sum(t for _, t, s in sections if s)
    dynamic = sum(t for _, t, s in sections if not s)
    if not cache or stable < 512:
        return CALLS * (stable + dynamic) * 2.00 / 1e6
    writes = CALLS / TURNS                         # first call of each conversation writes the prefix
    reads = CALLS - writes                         # (a pessimistic case: no sharing across conversations)
    return (writes * stable * 2.50 + reads * stable * 0.10 + CALLS * dynamic * 2.00) / 1e6


if __name__ == "__main__":
    for label, sections in [("before", BEFORE), ("trim tools and JSON, keep all policies", KEEP_ALL_POLICIES),
                            ("trim tools and JSON, retrieve policies", AFTER)]:
        total = sum(t for _, t, _ in sections)
        print(f"{label}: {total:,} input tokens per call")
        for name, t, s in sections:
            print(f"  {t:>6,}  {'stable ' if s else 'dynamic'}  {name}")
        print(f"  monthly input cost: no cache ${monthly_cost(sections, False):,.0f}, "
              f"stable prefix cached ${monthly_cost(sections, True):,.0f}")

  • Before: 61,300 tokens a call, $24,520 a month uncached. Caching the stable 47,000-token prefix halves it, but that prefix carries 34 unused tools and 22 policies when a question needs two or three.
  • Trim tools and JSON, keep all policies: six core tools (others loaded only when needed) and only the order fields the agent uses; cached, $8,720. No risk of a missing policy.
  • Also retrieve policies: the top three sections per question instead of all 22; cached, $6,120. Cheapest, but retrieved text is dynamic and can miss the section that matters.
  • The model is pessimistic: it assumes each conversation writes its own cache; when many conversations share a prefix within the cache lifetime, reads replace more writes.

Where tokens can go

Skill 2.4A checklist, roughly from safest to riskiest (my ordering).

  • Cache what's stable: tools, system prompt and reference material at the front, above the 512-token minimum. No information is lost.
  • Trim tool results: return the fields the agent uses, not whole records; large JSON is often the biggest dynamic cost.
  • Prune tool definitions: keep the tools used in most conversations; load rare ones on demand (for example with the tool search tool) or move them to a specialised step.
  • Remove duplication: the same policy pasted in the system prompt and in retrieved text; instructions repeated every turn.
  • Retrieve instead of pasting everything: only after checking retrieval finds what the answers need.
  • Shorten history: summarise or clear old tool results in long sessions (skill 2.6).

Keeping task-relevant information

Skill 2.4"Without loss" has to be measured.

  • Run the evaluation set before and after each cut; a cheaper prompt that answers fewer questions correctly hasn't saved anything.
  • For retrieval, check recall: on a sample of real questions, does the retrieved set contain the policy the correct answer depends on?
  • Know what's load-bearing: tools used in 5% of chats may be the ones for refunds or safety recalls; route those cases rather than dropping the tools.
  • Prefer cuts that are clearly irrelevant (unused JSON fields, duplicate text) over cuts that are probably irrelevant (documents a retriever didn't pick).

"Switch to a cheaper model" is the usual distractor in a token-economics question. It cuts price per token but leaves the waste in place, and changes quality; the question asks where tokens can be removed or made cheaper without losing information.

Key takeaways

  • Price each section of the context at the stated volume: stable content near the front is cheap once cached; dynamic content is paid in full every call.
  • Caching: prefix order tools, system, messages; at least 512 tokens on current models; writes 1.25x (5 minutes) or 2x (1 hour), reads 0.05x on Opus and Sonnet 5.5; tool changes invalidate everything.
  • Safest cuts first: cache the stable prefix, trim tool results, prune rarely used tools, remove duplicates; then retrieval and history shortening.
  • "Without loss" means measured: run the evaluation set before and after, and check retrieval recall.
  • A cheaper model isn't a context fix; remove waste first.
