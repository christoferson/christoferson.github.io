Overview

Skill 2.4

Context Composition and Token Economics: "Analyzing context composition and caching behavior against a token budget and a defined call volume to determine where token consumption can be reduced without loss of task-relevant information."

Exam items give a request's composition, a call volume and a budget, and ask which change cuts cost without hurting results. Placing breakpoints and packaging reusable content is skill 2.5; managing context over a long session is skill 2.6.

Find tokens to remove or make cheaper, without losing what the task needs

Skill 2.4What this skill asks you to do.

Every Claude request is made of parts: tool definitions, the system prompt, reference documents, the conversation so far, tool results and the user’s message. Questions on this skill give you that make-up, how many calls are made a month, and a budget, and ask which change cuts cost without making the answers worse. Two ideas do most of the work: where a token sits decides what it costs once caching is on, and some cuts are much safer than others.

A token’s cost depends on where it sits in the prompt

Skill 2.4The prompt caching rules that change the arithmetic.

  • Only the start of the prompt can be cached. A cache covers everything up to a point you mark (a breakpoint), in a fixed order: tools first, then the system prompt, then the messages. Anything that changes from one request to the next stops the cache at that point; everything after it is paid in full.
  • Reading the cache is very cheap; writing it costs a little extra. Writing costs 1.25 times the normal input price for a cache that lasts 5 minutes (2 times for 1 hour). Reading costs 0.05 times the input price on Opus and Sonnet 5.5 (0.1 times on most other models, 0.025 times on Fable 5.2).
  • Short prefixes aren’t cached. The minimum is 512 tokens on current models (1,024 on some older ones); below that nothing is cached, and no error tells you so.
  • Some changes throw the cache away. Changing the tool definitions invalidates the whole cache; changing system-level settings invalidates the system prompt and messages; changing tool_choice or images invalidates the messages.
  • Cached reads also free up rate limit. They don’t count toward the input-tokens-per-minute limit.

So a token that stays the same and sits near the front is cheap after the first call, and a token that changes every call is paid in full every time.

Cut from the safest place to the riskiest

Skill 2.4Where tokens can go, in the order to try them.

  1. Cache what doesn’t change. Put the tools, system prompt and reference material at the front, above the 512-token minimum, and cache them. Nothing is lost; the same tokens just cost less.
  2. Trim tool results. Return only the fields the agent uses, not whole records. Large JSON from lookups is often the biggest part that changes every call.
  3. Prune tool definitions. Keep the tools used in most conversations; load rare ones only when needed (for example with the tool search tool), or move them to a separate, specialised step.
  4. Remove duplication. The same policy pasted into the system prompt and again in retrieved text, or instructions repeated every turn.
  5. Retrieve instead of pasting everything, but only after checking that retrieval reliably finds the passages the answers depend on.
  6. Shorten long histories by summarising or clearing old tool results in long sessions.

Worked example: halving a support agent’s input bill

Skill 2.4Three versions of the same request, priced at 200,000 calls a month.

An online retailer’s support agent runs on Sonnet 5.5 and makes 200,000 model calls a month, about four per conversation. Finance wants the input bill roughly halved.

  • As it is: 61,300 input tokens a call. That’s 14,000 of definitions for 40 tools (only 6 are used in 95% of chats), a 3,000-token system prompt, all 22 policy documents pasted in (30,000), and then the parts that change: 8,000 of history, 6,000 of full order JSON and the customer’s message. Uncached it costs $24,520 a month; caching the stable 47,000-token front brings it to $12,300.
  • Trim the tools and the JSON, keep every policy: 6 core tools with the rest loaded on demand (3,000 tokens), and only the order fields the agent uses (900). Cached, $8,720 a month, and there’s no risk of a missing policy.
  • Also retrieve policies: the top three policy sections for each question (4,000 tokens) instead of all 22. Cached, $6,120 a month: the cheapest, but the retrieved text changes every call and can miss the section that matters.

The choice. Trimming the tools and the JSON already cuts the bill from $24,520 to $8,720, well over half, without any risk to the answers; retrieval saves another $2,600 a month only if a recall check shows it finds the right policy.

What the model leaves out. It assumes each conversation writes its own cache. When many conversations share the same front part within the cache’s lifetime, more calls read it instead of writing it, and the real bill is lower.

The code below prices each version section by section:

context_budget.py (context_budget.py)Optional 
"""Where do a support agent's input tokens go, and which cuts keep the task-relevant information?

Sonnet 5.5 prices (USD per million tokens, Nov 2026): input $2.00, 5-minute cache write $2.50,
cache read $0.10. Caching needs a prefix of at least 512 tokens and covers everything before the
breakpoint, in the order tools -> system -> messages."""

CALLS = 200_000          # model calls a month
TURNS = 4                # calls per conversation: the cache is written once, read on later turns

BEFORE = [  # section, tokens, stable across calls?
    ("tool definitions (40 tools; 6 used in 95% of chats)", 14_000, True),
    ("system prompt", 3_000, True),
    ("all 22 policy documents, pasted in", 30_000, True),
    ("conversation history", 8_000, False),
    ("order lookup results (full JSON)", 6_000, False),
    ("customer message", 300, False),
]

KEEP_ALL_POLICIES = [   # alternative: no retrieval risk, everything stable is cached
    ("tool definitions (6 core tools; others loaded on demand)", 3_000, True),
    ("system prompt", 3_000, True),
    ("all 22 policy documents, pasted in", 30_000, True),
    ("conversation history", 8_000, False),
    ("order lookup results (fields the agent needs)", 900, False),
    ("customer message", 300, False),
]

AFTER = [
    ("tool definitions (6 core tools; others loaded on demand)", 3_000, True),
    ("system prompt", 3_000, True),
    ("policy sections retrieved for this question (top 3)", 4_000, False),
    ("conversation history", 8_000, False),
    ("order lookup results (fields the agent needs)", 900, False),
    ("customer message", 300, False),
]


def monthly_cost(sections, cache: bool) -> float:
    stable = sum(t for _, t, s in sections if s)
    dynamic = sum(t for _, t, s in sections if not s)
    if not cache or stable < 512:
        return CALLS * (stable + dynamic) * 2.00 / 1e6
    writes = CALLS / TURNS                         # first call of each conversation writes the prefix
    reads = CALLS - writes                         # (a pessimistic case: no sharing across conversations)
    return (writes * stable * 2.50 + reads * stable * 0.10 + CALLS * dynamic * 2.00) / 1e6


if __name__ == "__main__":
    for label, sections in [("before", BEFORE), ("trim tools and JSON, keep all policies", KEEP_ALL_POLICIES),
                            ("trim tools and JSON, retrieve policies", AFTER)]:
        total = sum(t for _, t, _ in sections)
        print(f"{label}: {total:,} input tokens per call")
        for name, t, s in sections:
            print(f"  {t:>6,}  {'stable ' if s else 'dynamic'}  {name}")
        print(f"  monthly input cost: no cache ${monthly_cost(sections, False):,.0f}, "
              f"stable prefix cached ${monthly_cost(sections, True):,.0f}")

Prove that nothing the task needs was lost

Skill 2.4“Without loss” has to be measured.

  • Run the evaluation set before and after each cut. A cheaper prompt that answers fewer questions correctly hasn’t saved anything.
  • For retrieval, check recall. On a sample of real questions, does the retrieved text include the policy the correct answer depends on?
  • Know which rare parts carry weight. Tools used in 5% of chats may be the ones for refunds or safety recalls; route those chats to a step that has the tools rather than dropping them.
  • Prefer cuts that are clearly irrelevant (JSON fields nothing reads, duplicated text) over cuts that are only probably irrelevant (documents a retriever didn’t pick).

“Switch to a cheaper model” is the usual wrong answer here. It lowers the price per token but leaves the waste in place, and it changes the quality of the answers. The question asks where tokens can be removed or made cheaper without losing information.

Key takeaways

  • Price each part of the request at the stated call volume: unchanging parts near the front are cheap once cached; parts that change every call are paid in full every time.
  • Caching covers the front of the prompt in the order tools, system, messages; writes cost 1.25 times input (5 minutes) or 2 times (1 hour), reads 0.05 times on Opus and Sonnet 5.5; prefixes under 512 tokens aren’t cached; changing tools invalidates everything.
  • Cut in order of safety: cache the stable part, trim tool results, prune tool definitions, remove duplicates, then retrieve instead of pasting and shorten long histories.
  • “Without loss” is measured: run the evaluation before and after, and check retrieval recall.
  • A cheaper model isn’t a fix for wasted context; remove the waste first.
