Task 4.5: Understand data privacy and governance

Governance is the set of rules that decide what data exists, where it may live, who may use it and how changes are tracked. This task covers sharing data safely, finding personal data, keeping data in approved Regions, recording configuration changes, meeting sovereignty requirements, controlling access through a business catalog, and the frameworks that tie it together.

Data sharing permissions

Skill 4.5.1Grant permissions for data sharing (for example, data sharing for Amazon Redshift).

Redshift data sharing gives another warehouse live access to tables without copying them (Task 2.1). Permissions are granted in three layers: objects into the datashare, the datashare to a consumer, then the consumer's own users.

Producer: build and grant the datashare

Share the sales schema with a partner account 
CREATE DATASHARE salesshare;

ALTER DATASHARE salesshare
  ADD SCHEMA sales;
ALTER DATASHARE salesshare
  ADD ALL TABLES IN SCHEMA sales;
-- include tables created later
ALTER DATASHARE salesshare
  SET INCLUDENEW = TRUE FOR SCHEMA sales;

GRANT USAGE ON DATASHARE salesshare
  TO ACCOUNT '444455556666';
  • Add the schema first; adding a schema does not add its objects. INCLUDENEW covers only future objects and can be set only by a superuser.
  • Redshift is moving to GRANT ... TO DATASHARE syntax for objects (GRANT SELECT ON TABLE t TO DATASHARE s). Granting INSERT or UPDATE to the datashare lets consumers write; writes need Serverless or RA3/RG and snapshot isolation.
  • GRANT USAGE ON DATASHARE goes to a namespace (same account) or an account, one consumer per statement; it cannot go to users or groups.
  • Tables protected by dynamic data masking cannot be shared, and cross-account sharing needs both warehouses encrypted (Task 4.3).

Cross-account: two administrator steps

After the grant to an account, the datashare sits in pending_authorization. A producer account administrator must authorize it, and a consumer account administrator must associate it with the whole account, specific namespaces, or a Region. Sharing between namespaces in the same account needs neither step.

Producer admin, then consumer admin 
# in 111111111111
aws redshift authorize-data-share \
  --data-share-arn "$SHARE_ARN" \
  --consumer-identifier 444455556666

# in 444455556666
aws redshift associate-data-share-consumer \
  --data-share-arn "$SHARE_ARN" \
  --associate-entire-account

The IAM actions are redshift:AuthorizeDataShare and redshift:AssociateDataShareConsumer; cross-account writes also need --allow-writes on both calls.

Consumer: a database from the share

Mount the share, grant per object 
CREATE DATABASE partner_sales
  WITH PERMISSIONS
  FROM DATASHARE salesshare
  OF ACCOUNT '111111111111'
  NAMESPACE '<producer-namespace-id>';

GRANT USAGE ON DATABASE partner_sales
  TO ROLE analyst;
GRANT SELECT
  ON partner_sales.sales.orders
  TO ROLE analyst;

SELECT region, SUM(amount)
FROM partner_sales.sales.orders
GROUP BY region;

The two consumer modes behave oppositely. Without WITH PERMISSIONS, GRANT USAGE ON DATABASE opens every shared object. With it, USAGE grants nothing until you also grant each object by its three-part name. Consumers cannot re-share the database, and cannot attach RLS or masking policies to shared objects.

  • Cross-Region sharing: the consumer pays data transfer, metered on bytes scanned with a 10 MB minimum per query; usage limits can cap it.
  • Lake Formation-managed datashares (GRANT USAGE ... TO ACCOUNT ... VIA DATA CATALOG): Lake Formation grants then control access in the consumer account. The producer's RLS and column-level security are ignored — re-create them in Lake Formation.
  • AWS Data Exchange datashares license Redshift data to subscribers.
  • Inspect sharing with SVV_DATASHARES, SVV_DATASHARE_OBJECTS and SVV_DATASHARE_CONSUMERS.

Finding PII

Skill 4.5.2Implement PII identification (for example, Amazon Macie with Lake Formation).

You cannot protect personal data you do not know you have. Amazon Macie discovers sensitive data in S3 — and only S3; to scan RDS or DynamoDB data, export it to S3 first.

How Macie finds sensitive data

ModeHow it works
Automated sensitive data discoveryContinuously samples representative objects across all buckets and gives each bucket a sensitivity score; results start within 48 hours. Good for "where is our sensitive data?"
Sensitive data discovery jobsOne-time or scheduled (daily, weekly, monthly) scans of chosen buckets or bucket criteria, with a sampling percentage. Good for thorough checks of specific data
  • Managed data identifiers detect credentials, financial data and personal information (PII and PHI) using machine learning and patterns.
  • Custom data identifiers add your own formats: a regex (up to 512 characters), optional keywords within a maximum distance, and ignore words. They cannot be edited after creation.
  • Allow lists stop known non-sensitive values (test card numbers, the company's own address) from generating findings.
  • Macie reads text formats, JSON, CSV, Parquet, Avro, Office documents, PDFs and compressed archives. It does not scan Glacier Flexible Retrieval or Deep Archive objects, directory buckets, or images.
Scan the raw zone once, fully 
aws macie2 create-classification-job \
  --job-type ONE_TIME \
  --name pii-raw-zone \
  --managed-data-identifier-selector \
    RECOMMENDED \
  --sampling-percentage 100 \
  --s3-job-definition file://job.json
job.json 
{
  "bucketDefinitions": [{
    "accountId": "111111111111",
    "buckets": ["retail-lake"]
  }]
}
A custom identifier for loyalty IDs 
aws macie2 create-custom-data-identifier \
  --name loyalty-id \
  --regex "LOY-[0-9]{8}" \
  --keywords loyalty member \
  --maximum-match-distance 30

Findings

  • Sensitive data findings (SensitiveData:S3Object/Personal, /Financial, /Credentials, /CustomIdentifier) report what was found in an object. Policy findings report bucket risks such as public access, disabled encryption or replication to an external account.
  • Findings are kept 90 days. To keep detailed discovery results longer, Macie writes them to an S3 bucket encrypted with a customer managed KMS key in the same Region.
  • Every finding goes to EventBridge (aws.macie, Macie Finding); Security Hub receives policy findings by default.
  • In an organization, a delegated Macie administrator manages discovery for all member accounts.
  • Pricing is per bucket monitored, per object monitored for automated discovery, and per GB inspected.

Macie with Lake Formation

Macie knows which S3 objects hold PII; Lake Formation controls who can query the tables over them. The join is automation: Macie findings trigger a workflow that tags the affected tables or columns with an LF-Tag such as classification=pii, and tag-based grants (Task 4.2) then keep those columns from everyone not cleared for PII. AWS's Analytics Lens recommends recording data classifications in the catalog for exactly this kind of tag-based access control.

  1. A Glue crawler catalogs the raw data; new tables can start tagged as sensitive by default.
  2. A Macie job scans the S3 location and publishes findings to EventBridge.
  3. A rule starts Step Functions or Lambda, which maps findings to Glue tables and columns and updates their LF-Tags.
  4. LF-Tag grants decide who sees the classified columns in Athena, Redshift Spectrum and EMR.
EventBridge pattern: sensitive data findings only 
{
  "source": ["aws.macie"],
  "detail-type": ["Macie Finding"],
  "detail": {
    "type": [{"prefix": "SensitiveData:"}]
  }
}

Macie scans files at rest in S3; Glue Sensitive Data Detection scans data inside a running ETL job and can mask it on the way through (Task 4.3). Use Macie to discover and monitor the lake; use the Glue transform to stop PII landing in curated zones.

Keeping data in approved Regions

Skill 4.5.3Implement data privacy strategies to prevent backups or replications of data to disallowed AWS Regions.

Data stays in the Region where you put it unless something copies it: replication, backup copies, snapshot copies, global tables, key or secret replicas. A privacy strategy blocks those paths to unapproved Regions, preferably once for the whole organization.

The Region-deny SCP

AWS's example SCP denies any request outside approved Regions, using aws:RequestedRegion, with two escape hatches: NotAction exempts global services (IAM, Organizations, Route 53, CloudFront, STS, Support and others) whose calls go to a single Region, and a principal condition exempts a privileged administration role. AWS now publishes its example SCPs in the aws-samples/service-control-policy-examples repository.

Deny everything outside two EU Regions (trimmed) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOutsideApprovedRegions",
    "Effect": "Deny",
    "NotAction": [
      "iam:*",
      "organizations:*",
      "route53:*",
      "cloudfront:*",
      "sts:*",
      "support:*",
      "kms:*"
    ],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:RequestedRegion": [
          "eu-central-1",
          "eu-west-1"
        ]
      },
      "ArnNotLike": {
        "aws:PrincipalARN":
          "arn:aws:iam::*:role/OrgAdmin"
      }
    }
  }]
}

The real example lists about forty global services in NotAction. AWS Control Tower offers the same protection as a built-in Region deny control for the landing zone or for chosen OUs, plus data residency controls (for example, disallowing cross-Region networking).

Copy paths the SCP does not catch

A Region SCP blocks an action only when the call is made in a denied Region. Some copies are requested in the source Region, so they need their own controls:

Copy pathWhere it is calledControl
RDS snapshot copy, cross-Region read replicaThe destination RegionThe Region SCP blocks it
DynamoDB global table replicaChecked against the replica RegionThe Region SCP blocks it
AWS Backup copy jobSourceDeny backup:CopyFromBackupVault unless backup:CopyTargets is an approved vault ARN
KMS multi-Region key replicaPrimary RegionDeny kms:ReplicateKey by kms:ReplicaRegion — needed because the example SCP exempts kms:*
Secrets Manager replicaSourceDeny by secretsmanager:AddReplicaRegions
S3 replicationSourceNo destination-Region condition key: restrict s3:PutReplicationConfiguration to administrators, block bucket creation elsewhere, and detect with Config and Macie
Redshift cross-Region snapshot copySourceNo destination-Region key: deny redshift:EnableSnapshotCopy except for administrators
Extra statements: key replicas and backup copies 
[
  {
    "Sid": "DenyKeyReplicasElsewhere",
    "Effect": "Deny",
    "Action": "kms:ReplicateKey",
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "kms:ReplicaRegion": [
          "eu-central-1",
          "eu-west-1"
        ]
      }
    }
  },
  {
    "Sid": "DenyBackupCopiesElsewhere",
    "Effect": "Deny",
    "Action":
      "backup:CopyFromBackupVault",
    "Resource": "*",
    "Condition": {
      "ForAnyValue:ArnNotLike": {
        "backup:CopyTargets": [
          "arn:aws:backup:eu-central-1:*:backup-vault:*",
          "arn:aws:backup:eu-west-1:*:backup-vault:*"
        ]
      }
    }
  }
]
  • Resource control policies add a resource-side guardrail for S3, KMS, Secrets Manager, DynamoDB and others, such as denying access from outside the organization.
  • Opt-in Regions launched after March 2019 are disabled until an account enables them — leave unneeded ones off.
  • AWS Backup Audit Manager reports whether backup copies comply with policy; Vault Lock protects the copies you do keep (Task 2.3).

Configuration changes

Skill 4.5.4Viewing configuration changes that have occurred in an account (for example, AWS Config).

AWS Config records what each resource's configuration was at every point in time, and evaluates it against rules. It answers "what did this bucket's policy look like last Tuesday, and when did encryption get turned off?" — while CloudTrail answers who made the call.

Recording

  • The configuration recorder records all supported resource types or a chosen subset (inclusion or exclusion lists). Global resources such as IAM roles should be recorded in only one Region.
  • Recording is continuous (every change) or daily (periodic, since November 2023), with per-type overrides.
  • Each recorded state is a configuration item; the sequence for one resource is its configuration history, and a snapshot captures all resources at once. The delivery channel sends them to S3 and optionally SNS. Items are kept 7 years by default (30 days to 7 years).
  • The console resource timeline shows each change alongside the related CloudTrail events, and resource relationships.
Record everything daily, S3 buckets continuously 
aws configservice put-configuration-recorder \
  --configuration-recorder \
    file://rec.json \
  --recording-group allSupported=true
rec.json 
{
  "name": "default",
  "roleARN":
    "arn:aws:iam::111111111111:role/config-role",
  "recordingMode": {
    "recordingFrequency": "DAILY",
    "recordingModeOverrides": [{
      "description": "Buckets continuous",
      "resourceTypes": [
        "AWS::S3::Bucket"
      ],
      "recordingFrequency": "CONTINUOUS"
    }]
  }
}

Pricing is per configuration item: $0.003 for continuous recording and $0.012 for daily, so daily recording only saves money for resources that change several times a day.

Rules, packs and aggregation

  • Managed rules check common requirements; custom rules run Lambda functions or Guard policies. Rules evaluate on change, on a schedule, or both, and can run proactively against resources before they are deployed.
  • Remediation runs Systems Manager Automation documents, manually or automatically.
  • Conformance packs deploy a set of rules and remediations as one unit, across an organization if needed.
  • Aggregators give a read-only, multi-account, multi-Region view at no extra cost; they cannot deploy rules.
  • Advanced queries run SQL-style SELECT statements over current configuration, across accounts through an aggregator.
Managed ruleChecks
s3-bucket-public-read-prohibitedNo public read access on buckets
s3-bucket-server-side-encryption-enabledDefault encryption on buckets
s3-bucket-cross-region-replication-enabledWhich buckets replicate to another Region
rds-storage-encryptedEncrypted RDS storage
redshift-cluster-public-access-checkNo publicly accessible Redshift clusters
dynamodb-pitr-enabledPoint-in-time recovery on tables
multi-region-cloudtrail-enabledA multi-Region trail exists
Deploy a managed rule 
aws configservice put-config-rule \
  --config-rule file://rule.json
rule.json 
{
  "ConfigRuleName": "s3-sse-enabled",
  "Scope": {
    "ComplianceResourceTypes": [
      "AWS::S3::Bucket"
    ]
  },
  "Source": {
    "Owner": "AWS",
    "SourceIdentifier":
      "S3_BUCKET_SERVER_SIDE_ENCRYPTION_ENABLED"
  }
}
How many buckets in each Region? 
aws configservice select-resource-config \
  --expression "SELECT awsRegion, COUNT(*)
    WHERE resourceType = 'AWS::S3::Bucket'
    GROUP BY awsRegion"

Pair the two services in audit answers: Config for "what changed, and is it compliant?", CloudTrail for "who changed it, from where?". For data residency, a Config query like the one above, run across an aggregator, finds buckets in Regions they should not be in.

Data sovereignty

Skill 4.5.5Maintain data sovereignty.

Data residency is about where data is stored. Data sovereignty goes further: which country's laws apply, and who can control and access the data. AWS puts it as customers deciding "where their data is stored, how it's stored, and who has access to it".

LeverHow it helps
Region choiceData stays in the Region where it is stored unless you move it
SCPs, RCPs and Control Tower controlsPrevent use of, and copies to, other Regions (above)
Customer managed KMS keysControl over who can decrypt; an external key store keeps key material outside AWS, and CloudHSM in dedicated hardware
Local Zones, Dedicated Local Zones, OutpostsInfrastructure in a specific city, country or your own premises
AWS European Sovereign CloudA separate cloud inside the EU (below)
AWS ArtifactCompliance reports and agreements, such as the GDPR data processing terms built into the AWS Service Terms

The AWS European Sovereign Cloud became generally available on January 15, 2026, with its first Region in Brandenburg, Germany. It is physically and logically separate from other AWS Regions, with its own infrastructure, identity and network, operated by EU-based entities and staff, and launched with more than 90 services.

  • Global services complicate residency: CloudFront and Global Accelerator are global by design, and Config records IAM, CloudFront and Route 53 items in a single Region. Control Tower's data residency controls can disallow cross-Region networking such as CloudFront distributions.
  • Log and security data have residency rules too: Security Lake rollup Regions keep consolidated logs in an approved Region (Task 4.4).

Access through SageMaker Catalog

Skill 4.5.6Manage data access through Amazon SageMaker Catalog projects.

In SageMaker Catalog, access is granted to projects, not people: a project subscribes to a published asset, an owner approves, and the catalog creates the underlying grants for the subscribing project's role. Joining or leaving a project therefore changes what a person can reach. Domains, projects and designations are on Task 4.1.

How a subscription becomes real access

AssetWhat approval creates
Glue table (Lake Formation-managed)Lake Formation grants to the subscribing project. The publishing project's role needs DESCRIBE and SELECT with grant option
Redshift table or viewA direct grant in the same database; a view in another database of the same cluster; or a datashare plus a view for another cluster or account
Unmanaged asset (for example an Athena view)An EventBridge event; your own automation creates the grant and reports back
  1. Request. A member of the consumer project requests access, with a reason (and any metadata forms the domain requires).
  2. Approve. A member of the owning project approves — full access, or filtered access through asset filters. Approval is automatic only when the asset was published without requiring approval, or when the requester is an owner or contributor in both projects.
  3. Grant. The catalog creates the grants and records subscription and grant events in EventBridge.
  4. Revoke or unsubscribe. The owner revokes (optionally keeping the underlying permissions to clean up later), or the consumer unsubscribes. A revoked subscription cannot be re-approved; the consumer must request again.

Asset filters

Asset filters give a subscriber only some rows or columns. For Glue tables they become a single Lake Formation data cell filter; for Redshift, a late-binding view.

An EU-only row filter on the orders asset 
aws datazone create-asset-filter \
  --domain-identifier dzd_4p9n6sw4qt9xgn \
  --asset-identifier "$ORDERS_ASSET_ID" \
  --name eu-only \
  --configuration file://eu-filter.json
eu-filter.json 
{
  "rowConfiguration": {
    "rowFilter": {
      "expression": {
        "equalTo": {
          "columnName": "region",
          "value": "EU"
        }
      }
    }
  }
}
Approve with the filter, later revoke 
aws datazone accept-subscription-request \
  --domain-identifier dzd_4p9n6sw4qt9xgn \
  --identifier "$REQUEST_ID" \
  --asset-scopes \
    assetId="$ASSET",filterIds="$FILTER"

aws datazone revoke-subscription \
  --domain-identifier dzd_4p9n6sw4qt9xgn \
  --identifier "$SUBSCRIPTION_ID" \
  --no-retain-permissions
  • Data products bundle assets so one approval covers the whole bundle.
  • Domain unit authorization policies decide who can create projects and manage membership, and so who can subscribe at all.
  • Associated accounts (shared through AWS RAM) let projects use data and resources in other accounts.

Governance and sharing patterns

Skill 4.5.7Describe governance data framework and data sharing patterns.

AWS describes data governance as the "processes and policies that ensure data is in the proper condition" and that decide who can do what with which data. Its capabilities fall into three groups: curate (quality, integration, master data), discover and understand (profiling, lineage, catalogs), and protect and share (privacy, security, access). Everything in this guide maps onto one of them.

RoleResponsibility
Data ownerAccountable for a dataset: who may use it and for what
Data stewardDay-to-day quality, definitions and metadata
Data engineer (producer)Builds and runs the pipelines that publish the data
Data consumerAnalysts, scientists and applications that use it

Organizational patterns

  • Centralized: one team and one account own the lake and all its rules. Simple and consistent, but the central team becomes a bottleneck.
  • Data mesh: AWS lists four principles — domain-oriented decentralized ownership, data as a product, self-serve data infrastructure, and federated governance. Domains publish data products; a central function sets the shared rules.
  • Hub and spoke: AWS's data mesh reference architecture puts producer, consumer and a central governance domain each in its own account. The governance account holds the catalog, permissions and audit trail; producers keep their data in place.

Sharing patterns

The core choice is copy or share in place. Copies drift, multiply storage and multiply the places sensitive data lives; sharing in place keeps one governed source.

PatternAWS services
Centralized data lakeS3, Glue Data Catalog and Lake Formation in a central account
Hub and spoke, federated governanceA governance account with Lake Formation or a SageMaker Catalog domain; producer and consumer accounts connected through RAM
Data meshSageMaker Catalog domains, domain units, projects and data products; LF-Tag-based access
Share in place, liveRedshift datashares, Lake Formation cross-account sharing with resource links, S3 Access Points
Third-party or licensed dataAWS Data Exchange, including Redshift datashares
Joint analysis without sharing raw dataAWS Clean Rooms
Replicate operational data without pipelinesZero-ETL integrations into Redshift

Read scenarios for the ownership model. "Each business unit owns and publishes its own data, with company-wide standards" → data mesh with SageMaker Catalog and Lake Formation. "Partners must analyze overlapping customers without seeing each other's lists" → Clean Rooms. "Another team's warehouse needs today's numbers, not yesterday's copy" → Redshift data sharing.

Key takeaways

  • Redshift data sharing: CREATE DATASHARE, add the schema then its objects (INCLUDENEW for future tables, superuser only), GRANT USAGE ... TO NAMESPACE | ACCOUNT. Cross-account needs producer authorize-data-share and consumer associate-data-share-consumer.
  • Consumers: CREATE DATABASE ... FROM DATASHARE; without WITH PERMISSIONS, USAGE opens everything; with it, nothing until per-object grants. Cross-Region transfer is paid by the consumer. Lake Formation-managed datashares ignore the producer's RLS and column security.
  • Macie: S3 only; automated discovery samples every bucket and scores it; jobs scan chosen buckets; managed and custom identifiers (custom ones cannot be edited); no Glacier Flexible Retrieval or Deep Archive. Findings last 90 days and flow to EventBridge.
  • Macie with Lake Formation: findings trigger automation that sets LF-Tags (for example classification=pii), and tag-based grants restrict those columns. Glue Sensitive Data Detection handles PII inside pipelines.
  • Region control: the Region-deny SCP on aws:RequestedRegion with global-service exemptions, or Control Tower's Region deny. Add kms:ReplicaRegion (the example exempts kms:*), backup:CopyTargets and secretsmanager:AddReplicaRegions denies. S3 replication and Redshift snapshot copy have no destination-Region key; RDS copies are called in the destination Region, so the SCP stops them.
  • AWS Config: continuous or daily recording, configuration history and timeline, managed and custom rules with SSM remediation, conformance packs, free read-only aggregators, advanced queries. Config shows what changed; CloudTrail shows who.
  • Sovereignty adds control and jurisdiction to residency: Region choice, SCPs, customer managed keys (including external key stores), Local Zones and Outposts, and the AWS European Sovereign Cloud (GA January 2026, Brandenburg).
  • SageMaker Catalog grants access to projects: Lake Formation grants for Glue tables, grants, views or datashares for Redshift, events for unmanaged assets. Asset filters become a cell filter or late-binding view; revoked subscriptions cannot be re-approved.
  • Governance: curate, discover, protect and share; owners, stewards, producers, consumers. Patterns: centralized, data mesh (four principles), hub and spoke; share in place rather than copy, Data Exchange for licensed data, Clean Rooms for joint analysis without raw data.
