Optimizing code

Skill 1.4.1Optimize code to reduce runtime for data ingestion and transformation.

Task 1.2 covered diagnosing failures; this is making working code faster. AWS publishes a prescriptive guidance series, "Best practices for performance tuning AWS Glue for Apache Spark jobs", whose chapter list is itself a good checklist: scale cluster capacity, use the latest Glue version, reduce the amount of data scanned, parallelize tasks, optimize shuffles, optimize user-defined functions, and minimize planning overhead.

Getting the parallelism right

Spark creates one task per partition and runs one task per vCPU core, so partition count is the whole story. The documented arithmetic for S3 sources:

InputInitial partitions
Object 64 MB or smallerOne partition per object
Object larger than 64 MBSize divided by 64 MB
Unsplittable gzipOne partition per object — a 10 GB .csv.gz is a single task

A single large gzip file is the classic reason a Glue job uses one worker and takes hours. Gzip is not splittable, so no amount of extra capacity helps. Split the file upstream, or convert to Parquet or an uncompressed/splittable format first.

The target partition count is slots × executors, where executors is NumberOfWorkers minus one (the driver takes one) and slots per executor are 4 on G.1X, 8 on G.2X, 16 on G.4X and 32 on G.8X. Glue 4.0 with ten G.1X workers therefore wants about 36 partitions — two or three times that if task durations are uneven. The repartition rule of thumb AWS gives is "two or three times the number of cores available".

SettingValue and note
spark.sql.shuffle.partitionsDefault 200; above 2,001 Spark switches to a compressed memory format
spark.sql.adaptive.advisoryPartitionSizeInBytes128m — keep output files "within a moderate range (for example, 128 MB)"
spark.driver.maxResultSizeDefault 1 GB — the real limit on what collect() can return
spark.sql.dynamicPartitionPruning.enabledDefault true on EMR 5.26.0 and later

coalesce(N) is described as a "low-cost" reduction in partition count; repartition(N) shuffles to equalize them. Use coalesce to cut small output files, repartition when the data is skewed.

User-defined functions are the expensive mistake

AWS publishes a measured comparison over 10 million rows, and the ratios are worth remembering:

ApproachTime
Python UDF3.20 s
pandas (vectorized) UDF0.59 s — "5 times faster"
Spark SQL built-in function0.087 s

The cause is serialization: moving every row between the JVM and the Python interpreter through pickle has a cost AWS calls "very high". So the order of preference is built-in SQL function → pandas UDF → Python UDF. Enable Arrow with spark.sql.execution.arrow.pyspark.enabled=true; a vectorized UDF shows up in the plan as ArrowEvalPython. Glue 6.0 adds Arrow-native Python UDFs natively.

Avoid collect(), count() and show() in production code paths — they pull data to the driver and are bounded by the 1 GB spark.driver.maxResultSize. Note too that "salting" is not AWS vocabulary: the documented remedies for skew are AQE skew join and higher-cardinality or composite keys.

Partition keys must be STRING for predicate pushdown to reach the Glue Data Catalog. A partition column typed as INT silently stops pruning, and the query scans everything.

Redshift tuning

The modern answer to most Redshift design questions is to let Redshift decide. "You don't need to choose the distribution style" — AUTO plus Automatic Table Optimization is the documented default advice, and ATO applies keys "within hours". Likewise: "we recommend that you create your tables with SORTKEY AUTO."

ChoiceGuidance
Distribution styleAUTO by default; KEY to collocate a join; ALL for small dimensions; EVEN when nothing else fits
Sort typeCOMPOUND is the default and "recommended when you update your tables regularly with INSERT, UPDATE, or DELETE"; INTERLEAVED allows max 8 columns
ANALYZE"In most cases, you don't need to explicitly run the ANALYZE command" — auto-analyze is on, with analyze_threshold_percent defaulting to 10
VACUUM"Amazon Redshift automatically sorts data and runs VACUUM DELETE in the background"

The mechanism behind sort keys is worth knowing because it explains the payoff: Redshift stores columns in 1 MB blocks with min and max values in the metadata, which can "remove up to 98 percent of the disk blocks from the scan". For interleaved sort keys, VACUUM REINDEX "takes significantly longer than VACUUM FULL" — reindex when SVV_INTERLEAVED_COLUMNS.interleaved_skew exceeds 1.4.

Short query acceleration is enabled by default in the default and all new parameter groups, covers CTAS and read-only queries, and runs them in service class 14 so a long query cannot block a quick one. Automatic WLM is likewise on in the default parameter group, with up to 8 queues in service classes 100–107.

Lambda concurrency

Skill 1.4.2Configure Lambda functions to meet concurrency and performance needs.

Task 1.1 covered the default 1,000 concurrency and why it throttles ingestion. This is the configuration layer.

Reserved concurrencyProvisioned concurrency
What it does"Acts as both a lower and upper bound" — guarantees a share and caps itPre-initializes environments for "double-digit millisecond response times"
CostNo extra chargeCharged per GB-second reserved and per GB-second used; no free tier
Applies toThe functionA version or alias — never $LATEST

You can set both on one function, but "the provisioned concurrency cannot exceed the reserved concurrency". And reserving has an account-level floor: "you can reserve up to the unreserved account concurrency value minus 100" — AWS always keeps 100 units unreserved, so you cannot reserve your entire quota.

The target value must be between 10% and 90%. Scale-in triggers at 90% of the target, and the policy needs three datapoints (roughly three minutes) to act — so provisioned concurrency auto scaling handles daily curves, not sudden spikes. For a nightly batch, a scheduled change is usually better than target tracking.

SnapStart

SnapStart takes a Firecracker microVM snapshot when you publish a version and restores from it, adding a Restore phase in place of a full initialization. It is available for Java 11+, Python 3.12+ and .NET 8+.

"SnapStart does not support provisioned concurrency, Amazon EFS, Amazon S3 Files, or ephemeral storage greater than 512 MB." So SnapStart and provisioned concurrency are mutually exclusive, and SnapStart is unavailable to any function that mounts a file system — which rules it out for much data work. Java SnapStart is still free; other runtimes pay a cache and restore charge. Java-only quirk: the snapshot is deleted after 14 days idle, and the next invoke raises SnapStartNotReadyException.

Restore hooks let you re-establish anything that must not be snapshotted (a database connection, a random seed): Java uses CRaC beforeCheckpoint and afterRestore, Python uses snapshot_restore_py with register_before_snapshot and register_after_restore, and .NET uses SnapshotRestore.RegisterBeforeSnapshot.

Cold starts and the init phase

"The Init phase is limited to 10 seconds… Lambda retries the Init phase at the time of the first function invocation with the configured function timeout" (the log line is INIT_REPORT … Status: timeout). Importantly, this limit does not apply to provisioned concurrency, SnapStart or Lambda Managed Instances — those get up to 15 minutes. A heavyweight import that works under provisioned concurrency can fail on a cold on-demand start.

Context for exam framing: "cold starts typically occur in under 1% of invocations… from under 100 ms to over 1 second". Memory runs 128 to 10,240 MB in 1 MB steps, and "at 1,769 MB, a function has the equivalent of one vCPU" — which is why raising memory speeds up CPU-bound transforms.

Packaging heavy dependencies

pandas and pyarrow do not fit comfortably in a 250 MB unzipped package. Three routes: a layer (5 maximum), a container image up to 10 GB uncompressed, or the managed AWS SDK for pandas layer, whose ARN follows the shape arn:aws:lambda:<region>:336392948345:layer:AWSSDKPandas-Python312:<version>.

Copy that layer ARN from the documentation rather than constructing it — the owning account differs in some Regions, and there are separate x86 and -Arm64 variants per Python version.

Guard rails and metrics

Recursive loop detection is on by default at no charge: "if your function is invoked approximately 16 times in the same chain of requests, then Lambda automatically stops the next function invocation". It covers your own Lambda functions, SQS, S3, SNS and EventBridge custom event buses — but not DynamoDB. Watch RecursiveInvocationsDropped.

MetricUse
ConcurrentExecutionsHow close you are to the ceiling — view as MAX, not average
ClaimedAccountConcurrency"The amount of concurrency that is unavailable for on-demand invocations" — unreserved plus allocated. Alarm with (ClaimedAccountConcurrency / SERVICE_QUOTA(ConcurrentExecutions)) * 100
ProvisionedConcurrencySpilloverInvocationsInvocations that overflowed provisioned capacity into on-demand — the signal to raise it
ThrottlesRejected invocations; they do not count as Invocations or Errors

Lambda's documentation now calls the classic function type an "Event Function" — a rename only, with API, CLI and ARNs unchanged. The one 2026 addition that matters for data work is Lambda Managed Instances, which raise the timeout for asynchronous and event source mapping invocations to 5,400 seconds (90 minutes) and are exempt from the 10-second init limit. That is the escape hatch from the 15-minute wall, priced as EC2 plus a 15% management fee, and it scales to a configured minimum rather than to zero. Response streaming, incidentally, allows 200 MB — not 20 MB — but is Node.js managed runtimes only.

Lambda runtime deprecations

Runtimes matter because a deprecated one blocks deployments. The policy: new managed runtimes track language LTS releases, deprecation is announced at least 180 days ahead, and the phases are deprecation (no patches), then at least 30 days later function creation is blocked, then at least 60 days after that updates are blocked. Existing functions keep invoking indefinitely.

Engineering practices

Skill 1.4.4Use software engineering best practices for data engineering (for example, version control, testing, logging, monitoring).

Version control

AWS CodeCommit returned to full general availability in November 2025, reversing the 2024 wind-down — there is no closed-to-new-customers banner and no end-of-support date. By contrast AWS Cloud9 is closed to new customers ("existing customers… can continue to use the service as normal", pointing to the IDE Toolkits or CloudShell), and AWS CodeStar is retired with its documentation removed. CodeStar Connections was renamed AWS CodeConnections in March 2024 and is how CodePipeline and CodeBuild reach GitHub, GitLab, Bitbucket and Azure DevOps.

Glue Studio has a Version Control tab that connects a job to CodeCommit, GitHub, GitLab or Bitbucket. It pushes and pulls the job definition JSON plus the script, stored at <job-name>/<job-name>.json, and needs the glue:UpdateJobFromSourceControl and glue:UpdateSourceControlFromJob permissions.

Two limits on Glue source control: notebooks are not supported, and a push overwrites the repository rather than merging. Treat the Git repo as the source of truth and the console as a view, not the other way round.

Testing

The documented way to test Glue code locally is the official Docker image, public.ecr.aws/glue/aws-glue-libs, tagged :5 for Glue 5.0 (Spark 3.5.4, Python 3.11.6, default user hadoop). AWS gives a pytest recipe directly.

Run Glue unit tests locally (Bash) 
docker run -it --rm \
  -v ~/.aws:/home/hadoop/.aws \
  -v "$PWD":/home/hadoop/workspace \
  -e AWS_REGION=eu-west-1 \
  public.ecr.aws/glue/aws-glue-libs:5 \
  -c "python3 -m pytest -q"

Several Glue features do not work in the local container, and the list is good exam material: job bookmarks, the Glue Parquet writer, FillMissingValues, FindMatches, Glue Data Quality, sensitive data detection, customJdbcDriverS3Path and Lake Formation credential vending. Anything depending on those needs an integration test in a real account.

For interactive development, Glue interactive sessions offer a Livy type and, from Glue 5.1, a Spark Connect type. Note that moto, LocalStack, dbt tests and Great Expectations are community tools, not AWS services — useful in practice, but not exam answers.

Logging

Lambda advanced logging controls give three settings that remove most custom logging code: LogFormat (JSON or Text), ApplicationLogLevel, SystemLogLevel, plus a LogGroup for a custom destination.

Log-level filtering only works when LogFormat is JSON. Setting ApplicationLogLevel on a text-format function does nothing. The JSON structure "adheres to the OpenTelemetry (OTel) Logs Data Model", and a custom log group name must not begin with aws/.

Powertools for AWS Lambda Logger adds structured logging with standard keys (level, location, message, timestamp, service, xray_trace_id), and inject_lambda_context adds cold_start, function_name, function_memory_size and function_request_id — which is how you answer "how many of last night's invocations were cold".

CloudWatch Logs classTrade-off
Standard$0.50 per GB ingested; all features
Essentials (formerly Infrequent Access)$0.25 per GB ingested — but no Live Tail, metric filters, subscription filters, field indexing, anomaly detection, GetLogEvents/FilterLogEvents, Container or Lambda Insights, or embedded metric format

Classes differ in ingestion cost only (storage is $0.03 per GB-month either way) and cannot be changed after the log group is created. Because Essentials has no metric filters or EMF, choosing it for a pipeline's logs quietly removes your ability to alarm on them. Retention also defaults to Never Expire, which is the single most common source of surprise CloudWatch Logs bills.

Glue logging is version-dependent: up to Glue 4.0 continuous logging is opt-in via --enable-continuous-cloudwatch-log, while Glue 5.0 gives every job real-time logging — system and Spark output to /aws-glue/jobs/error, user stdout and stderr to /aws-glue/jobs/output.

Infrastructure as code

Skill 1.4.5Use Infrastructure as Code (IaC) to deploy data engineering solutions.

Skill 1.4.8Use infrastructure as code (IaC) for repeatable resource deployment (for example, AWS CloudFormation and AWS CDK).

Two skills, one subject. Read 1.4.8 as "know the tools and their mechanics" and 1.4.5 as "apply them to a data pipeline" — the second is where DeletionPolicy on a data store and environment promotion live.

CloudFormation template anatomy

Resources is the only required section. The others are Parameters, Outputs, Mappings, Conditions, Rules, Metadata, Transform, Description and AWSTemplateFormatVersion. Pseudo parameters worth knowing by name: AWS::AccountId, AWS::Region, AWS::Partition, AWS::StackName and AWS::NoValue.

The AWS::LanguageExtensions transform unlocks Fn::ForEach, Fn::Length and Fn::ToJsonString — genuinely useful for generating one Glue job or crawler per data set. Two gotchas: it must precede AWS::Serverless if both are listed, and the SAM CLI does not support Fn::ForEach.

Protecting data resources

This is the part of IaC that matters most for a data engineer, because a careless stack update can delete a warehouse.

AttributeValid values
DeletionPolicyDelete (default), Retain, RetainExceptOnCreate, Snapshot
UpdateReplacePolicyDelete (default), Retain, Snapshot — RetainExceptOnCreate is not valid here

RetainExceptOnCreate is DeletionPolicy-only — a classic exam trap. It retains the resource on stack deletion but still cleans up after a failed create, which is exactly what you want for a data store. Also note the default is not uniformly Delete: for RDS DBCluster and DBInstance the default is Snapshot. Snapshot-capable types include AWS::Redshift::Cluster, AWS::RDS::DBCluster, AWS::RDS::DBInstance, AWS::Neptune::DBCluster, AWS::EC2::Volume and the ElastiCache types — and setting Snapshot on an unsupported type silently falls back to Delete.

The other half of the risk is knowing which property change forces a Replacement rather than an in-place update:

Resource and propertyUpdate behaviour
AWS::S3::Bucket → BucketNameReplacement
AWS::DynamoDB::Table → TableNameReplacement (BillingMode, GSIs, PITR and Streams are no interruption)
AWS::Redshift::Cluster → ClusterIdentifierReplacement (also DBName, MasterUsername, ClusterSubnetGroupName; NodeType and NumberOfNodes are no interruption)
AWS::Glue::Database → DatabaseNameReplacement (DatabaseInput is no interruption)
AWS::Glue::Job → NameReplacement (Command and Role are no interruption)

The safe habit follows from this table: let CloudFormation generate physical names for data resources. Naming a bucket, table or cluster explicitly means any later rename replaces it — and replacement on a stateful resource means data loss unless UpdateReplacePolicy is Retain or Snapshot.

Nested stacks (AWS::CloudFormation::Stack, always updated from the root) decompose one large deployment; StackSets deploy one template across many accounts and Regions, with self-managed or service-managed permissions — the latter integrating with Organizations to deploy automatically to newly added accounts.

Three newer CloudFormation capabilities worth recognizing. Stack refactoring (February 2025) moves resources between stacks and renames logical IDs without recreating them — but it cannot create or delete resources, is unsupported on stacks with a stack policy, and excludes some types including AWS::EMR::Cluster and AWS::Glue::Schema. The IaC generator scans a Region and produces a template from existing resources (scans expire after 30 days, 500 resources per template). Git sync watches a repository for a template plus a deployment file and updates the stack on commit, through CodeConnections.

Policy-as-code splits into two tools with different jobs. cfn-lint validates templates against resource provider schemas. cfn-guard evaluates rules written in its own DSL — and the docs are explicit that it does not validate syntax and provides no server-side enforcement. Enforcement is CloudFormation Hooks, which run preCreate, preUpdate and preDelete handlers with a 30-second timeout and 3 retries, in FAIL or WARN mode (AWS recommends starting in WARN).

AWS CDK

CDK synthesizes CloudFormation from code. Constructs come in three levels: L1 (Cfn*, one CloudFormation resource with no defaults), L2 (curated defaults and helper methods), and L3 (opinionated patterns).

cdk bootstrap deploys the CDKToolkit stack: a staging S3 bucket, an ECR repository, five roles (CloudFormationExecutionRole, DeploymentActionRole, FilePublishingRole, ImagePublishingRole, LookupRole) and a version parameter under the default qualifier hnb659fds.

hasResourceProperties matches partially by default, which is what makes fine-grained assertions robust against CDK upgrades. AWS's own docs warn that snapshot tests are poor regression tests for CDK, because any library upgrade churns the snapshot. Assert on the properties you care about instead.

Two corrections about the wider IaC landscape. Terraform CDK (CDKTF) was sunset and archived on December 10, 2025 and is no longer maintained by HashiCorp — cdk8s is unaffected. And AWS Proton reached end of support on October 7, 2026: deployed infrastructure remains, but the console and resources become inaccessible. Note also that cdk gc (garbage collection of orphaned assets) exists but is not GA — it needs --unstable=gc.

AWS publishes no head-to-head IaC comparison table, so treat any four-way matrix as editorial. The defensible framing: CloudFormation for declarative templates and the widest resource coverage; CDK when you need loops, conditionals and reusable constructs; SAM for serverless with local testing; Terraform when a platform team has standardized on it. AWS Service Catalog supports Terraform product types if you need governed self-service.

Lambda storage

Skill 1.4.7Use and mount storage volumes from within Lambda functions.

A function that transforms a file needs somewhere to put it. Three options, and the choice is usually settled by size and sharing.

OptionSizeRight when
/tmp ephemeral storage512 MB default, up to 10,240 MBScratch space for one invocation; caching static assets between invocations
Amazon EFSEffectively unlimited, sharedMany functions need the same files, or you need POSIX semantics and appends
Amazon S3UnlimitedThe default for data — stream objects in and out, no VPC needed

Ephemeral /tmp

Configured with --ephemeral-storage '{"Size":1024}' or SAM's EphemeralStorage.Size, in 1 MB increments from 512 to 10,240 MB. "All data stored in /tmp is encrypted at rest with a key managed by AWS", and storage above the free 512 MB costs $0.0000000309 per GB-second.

/tmp belongs to the execution environment, not the invocation — it persists across invocations and is not cleared by an invocation failure. That makes it good for caching a lookup table or a model file ("cache static assets locally in the /tmp directory") and bad for anything user-specific, since the next request may see the previous one's data. AWS documentation warns against storing user data there. Note also that customer managed KMS keys are not supported for /tmp.

Mounting Amazon EFS

EFS gives Lambda a shared, persistent POSIX file system. The prerequisites are strict: the function must be in a VPC, there must be a mount target in every subnet the function uses, you mount through an access point, NFS needs TCP 2049, and the local mount path must start with /mnt/.

Attach a file system to a function (CLI) 
# the EFS access point ARN
AP=arn:aws:elasticfilesystem:eu-west-1:111111111111:access-point/fsap-0a1b2c3d

aws lambda update-function-configuration \
  --function-name curate-orders \
  --file-system-configs \
    "Arn=$AP,LocalMountPath=/mnt/lake"
ConstraintDetail
IAMelasticfilesystem:ClientMount and ClientWrite (managed policy AmazonElasticFileSystemClientReadWriteAccess)
One per functionFileSystemConfigs has a "maximum number of 1 item"
Connections25,000 per file system, hard — the real ceiling on concurrency for EFS-attached functions
Mount timeHappens when the environment is prepared, "often within hundreds of milliseconds"; with provisioned concurrency it happens during init

The locking caveat is explicit and important for concurrent writers: "Amazon EFS only supports advisory locking and read/write operations don't check for conflicting locks before executing… your application must be aware of NFS semantics (such as close-to-open consistency)." There is a limit of 512 locks per file. So EFS from Lambda is safe for many readers and careful appends, not for uncoordinated concurrent writes to one file.

On EFS configuration: Elastic is the default and recommended throughput mode, and for performance mode the documentation is blunt — Max I/O is "a previous generation performance type" and "we recommend using General Purpose performance mode for all file systems". Elastic throughput bills per GB read and written rather than provisioned capacity, which suits bursty pipeline access.

Newer alternatives

ServiceWhat it offers
Amazon S3 Files"A shared file system that connects any AWS compute resource directly with your data in Amazon S3… built using Amazon EFS" — NFS, mountable from EC2, Lambda, EKS and ECS. Supports read-after-write consistency, file locking and POSIX permissions, with small files cached and large reads streamed from S3
Mountpoint for Amazon S3A FUSE client for sequential and random reads and append-only writes to new objects. Linux only, "cannot modify existing files or delete directories", no file locking — and no documented Lambda support (it runs on EC2, ECS, EKS and on-premises)
S3 Express One ZoneA storage class using directory buckets, "consistent single-digit millisecond" latency and "up to 10x faster" than S3 Standard, with request costs "up to 80% lower"

A function can use either EFS or S3 Files, but not both. And if a question asks how to give a Lambda function a POSIX view of S3 data, S3 Files is the current answer, not Mountpoint — Mountpoint has no Lambda support. The Mountpoint CSI driver for EKS is also static-provisioning only and does not support Fargate.

S3 Express One Zone trades features for speed, and the exclusions matter: no Versioning, no Replication, no Object Lock, no lifecycle transitions, no Event Notifications, no object tags, no S3 Select, no Transfer Acceleration (expiration is supported). Also s3 sync is unsupported — use cp --recursive — and a bucket idle for 90 days goes inactive and returns 503 until reactivated.

For container-image functions the limit is a 10 GB uncompressed image including all layers. Lambda "optimizes the image" after upload, and if the function is not invoked for several weeks it "reclaims its optimized version", moving the function to Inactive — the next invoke is rejected while it re-optimizes. Worth knowing for a monthly batch job packaged as a container.

CI/CD

Skill 1.4.9Describe continuous integration and continuous delivery (CI/CD) (implementation, testing, and deployment of data pipelines).

A data pipeline is code, so it belongs in a pipeline of its own. The twist is that deploying a Glue job or a Redshift schema change is not like deploying a web service — there is state, and you cannot simply roll back a table.

AWS CodePipeline

There are two pipeline types, V1 and V2, and the difference is substantial.

V1V2
Pricing$1.00 per month per active pipeline$0.002 per action execution minute
TriggersBasic source changeFilters on Git tags, pull requests, branches or file paths
Execution modesSuperseded onlyAdds PARALLEL and QUEUED
Rollback—Stage-level rollback, manual or automatic on failure
Other—Pipeline-level variables, stage conditions, the Commands action, automatic stage retry

Action categories are Source, Build, Test, Deploy, Approval, Invoke and Compute. Actions sharing the same runOrder run in parallel. Stage conditions (July 2024) are the feature worth naming for data work: an Entry condition can FAIL or SKIP a stage, OnFailure can ROLLBACK or RETRY, and OnSuccess can ROLLBACK or FAIL — with rule providers including CloudWatchAlarm, LambdaInvoke, VariableCheck and DeploymentWindow, which is how you stop a deployment landing mid-batch.

A manual approval action fails after seven days with no response (the timeout is configurable). And a Source stage cannot be rolled back. For cross-account pipelines, the artifact store requires a customer managed KMS key — aliases are not recognized cross-account, so use the key ID or ARN — and the console cannot create or edit cross-account actions; you must use update-pipeline.

CodeDeploy for Lambda

The deployment configuration names are worth memorizing because they appear verbatim: CodeDeployDefault.LambdaAllAtOnce, LambdaCanary10Percent5Minutes (plus 10, 15 and 30-minute variants), and LambdaLinear10PercentEvery1Minute (plus 2, 3 and 10 minutes).

Lambda AppSpec hooks are only BeforeAllowTraffic and AfterAllowTraffic — one function each, run once per deployment. Each hook function must call putLifecycleEventHookExecutionStatus, and no response within one hour fails the deployment. A hook that forgets to report back hangs the release.

Dependencies and artifacts

CodeArtifact hosts private Python packages and proxies public ones. Every repository belongs to a domain, packages can never be made public, and there is one external connection per repository — documented names include public:pypi, public:npmjs and public:maven-central.

Schema change as deployment

The data-specific half of this skill. A schema change is a deployment you cannot roll back by redeploying, so compatibility is the control.

Glue Schema Registry modeChecks
NONENo check — development only
DISABLEDNo new versions accepted at all
BACKWARD (recommended)Consumers can read current and previous; checked when you delete fields or add optional fields
FORWARDCurrent and subsequent; checked when you add fields or delete optional fields
FULLAdd or remove optional fields only
_ALL variantsThe same checks against all previous versions, not just the checkpoint

There are eight modes in total (the five above plus BACKWARD_ALL, FORWARD_ALL and FULL_ALL), and compatibility is evaluated against the version marked as the checkpoint — the first version by default. BACKWARD is the recommended default because it lets producers move ahead while existing consumers keep working, which is exactly the expand-then-contract migration pattern.

For table schemas, Iceberg evolution is cheap: "Iceberg schema updates are metadata-only changes. No data files are changed." You can add, drop, rename and reorder columns, with type promotion limited to int→bigint, float→double and increasing decimal precision.

Blue/green for a Glue job is not an AWS-documented feature. The honest approach is to version the script artifact in S3, deploy a second job under a new name, run both against a sample, then switch the orchestrator's target — the switch happens in Step Functions or Airflow, not in Glue.

Distributed computing

Skill 1.4.10Define distributed computing.

Conceptual, but the concepts explain almost every number elsewhere on this page.

ConceptHow it shows up on AWS
Partition as the unit of parallelism"Each task that Spark creates corresponds to an RDD partition on a 1:1 basis"; in Kinesis it is the shard, in Kafka the partition, in Redshift the slice
Driver and executorThe driver "splits an application into tasks… provisions executors"; "a Spark executor is a worker for holding data and running tasks", with one task per vCPU by default
Jobs, stages, tasks"Stages – based on the shuffles created for an RDD" — a stage boundary is a shuffle
Shared-nothing MPPRedshift's leader node "assigns a portion of the data to each compute node", and "a compute node is partitioned into slices"
Shuffle versus broadcast"Spark supports two types of join: shuffle join and broadcast hash join" — shuffle cost scales as mappers × reducers

Consistency

ServiceGuarantee
Amazon S3Strong read-after-write for PUT and DELETE in all Regions, including overwrites, and for LIST. "Updates to a single key are atomic" — but "bucket configurations have an eventual consistency model"
DynamoDBEventually consistent by default; strongly consistent reads available on tables and LSIs but not on GSIs or Streams. "Eventually consistent reads are half the cost"
KinesisOrdering is per shard; "an MD5 hash function is used to map partition keys to 128-bit integer values and to map associated data records to shards"

The S3 bucket-configuration caveat is a real operational trap: after enabling versioning, AWS says to "wait for 15 minutes" before relying on it, and a deleted bucket can still appear in a listing. Object data is strongly consistent; the control plane is not.

Coordination and leader election

Distributed systems need someone to decide who does what, and the pattern on AWS is almost always a lease. The KCL is the clearest documented example: "lease – data that defines the binding between a worker and a shard", stored in a DynamoDB table, where "every worker will contend to hold all available leases… but only one worker will successfully hold each lease", with "a single elected worker leader" performing shard synchronization.

Elsewhere: Kafka KRaft replaces ZooKeeper for metadata (selected by a version string such as 3.7.x.kraft; "version 3.9 is the last version to support both ZooKeeper and KRaft", and Kafka 4.0 "deprecates metadata management via Apache ZooKeeper"), and Redshift has a dedicated leader node that parses, plans and compiles before distributing work.

Fault tolerance

Distributed engines survive node loss by being able to recompute. The Glue guide puts it plainly: "RDDs replicate data across available nodes, so they can automatically recover from node failures." Spot interruptions get explicit handling on EMR — spark.blacklist.decommissioning.enabled, a 20-second decommissioning threshold matching the Spot warning, and spark.stage.attempt.ignoreOnDecommissionFetchFailure.

The task-versus-core-node distinction is a fault-tolerance decision: "task nodes process data but do not hold persistent data in HDFS… no data is lost" if one disappears. That is precisely why task nodes are the right place for Spot and core nodes are not.

Some familiar vocabulary is general computer science rather than AWS documentation, and is worth labelling as such: the CAP theorem does not appear in the AWS Builders' Library article on distributed systems challenges, Amdahl's law appears on no AWS page, and spark.speculation is absent from both the EMR Spark configuration page and the Glue tuning guide — AWS documents AQE skew-join splitting and node decommissioning instead. The concepts are still useful for reasoning; just do not expect them phrased that way in a question.

Data structures

Skill 1.4.11Describe data structures and algorithms (for example, graph data structures and tree data structures).

The useful framing is: which structure is a given AWS service actually using, and what does that imply about how you should design against it?

Hashing and partitioning

ServiceHash use
Kinesis Data StreamsMD5 of the partition key mapped to a 128-bit integer and then to a shard
DynamoDB"DynamoDB uses the value of the partition key as input to an internal hash function" (the algorithm is not named)
Spark"In a shuffle join, partitions are determined for each hash value of a key"; repartition(N, "key")
Apache IcebergThe bucket(N, col) transform — "partition by hashed value mod N buckets", as in PARTITIONED BY (category, bucket(16, id))

This is why key cardinality decides everything upstream: a hash spreads keys evenly only if there are many distinct keys. One hot key means one hot shard, one hot partition, one long task — the same failure in four different services.

Trees and skip indexes

Redshift has no secondary indexes and does not use B-trees. The documentation is explicit: "some PostgreSQL features that are suited to smaller-scale OLTP processing, such as secondary indexes and efficient single-row data manipulation operations, have been omitted to improve performance." What it uses instead is block-level min and max metadata: "Amazon Redshift stores columnar data in 1 MB disk blocks. The min and max values for each block are stored as part of the metadata… the query processor can use the min and max values to rapidly skip over large numbers of blocks." (AWS never uses the phrase "zone map", common though it is elsewhere.)

The same idea is the foundation of columnar formats generally — "each block holds statistics for the block, such as maximum and minimum values. Spark can use these statistics to determine whether the block should be read or skipped" — and Athena extends it for Iceberg with Parquet column indexes, adding "page-level min/max statistics in addition to row group-level statistics".

Several internals commonly attributed to AWS services are not in AWS documentation: LSM trees for DynamoDB, Merkle trees for S3 or DynamoDB global tables, and B-trees for RDS or Aurora. What S3 does document is composite versus full-object checksums — "a composite checksum is calculated based on the individual checksums of each part", with a multipart ETag being an MD5 of the concatenated part MD5s plus a dash and the part count, and a default algorithm of CRC-64/NVME. That is the closest documented relative of the Merkle idea.

Graphs also appear as a modelling idea rather than a database: AWS calls the Glue visual job model "the representation of a directed acyclic graph", Airflow DAGs are the same structure, and data lineage is a graph — SageMaker ML Lineage Tracking documents "an example lineage graph". A question about "tracing which upstream table caused a bad report" is a lineage-graph question, not a Neptune question.

Probabilistic structures

StructureWhere AWS documents it

The engineering point behind all three: trade a little accuracy for a lot of memory. An exact COUNT(DISTINCT) over billions of rows has to hold every distinct value; HyperLogLog holds a fixed-size sketch. And because HLL sketches combine, they turn a nightly exact recount into an incremental merge.

Sorting and clustering

Sorting is a skip-index strategy. Redshift offers compound (the default) and interleaved sort keys (maximum 8 columns), while in the lake the equivalent is Iceberg compaction ordering.

Z-order is documented for S3 Tables maintenance compaction, described as "blending multiple attributes into a single scalar value that can be used for sorting", with strategies auto (the default), binpack, sort and z-order; sort and z-order require an Iceberg sort_order table property and cost more than bin-packing. Athena's own OPTIMIZE statement documents BIN_PACK only. Hilbert curves are not in AWS documentation.

Choose by query shape: a compound sort key or plain sort wins when queries filter on the leading column; interleaved or z-order wins when queries filter on different combinations of several columns with no dominant one. The cost is maintenance — VACUUM REINDEX on Redshift, or more expensive compaction on S3 Tables.

Key takeaways

  • Spark parallelism is partition count: one task per partition, one task per vCPU, target slots × (workers − 1). Unsplittable gzip gives one partition per file, so a 10 GB .csv.gz is a single task no matter how many workers you add.
  • UDF cost order, measured by AWS over 10M rows: built-in SQL 0.087 s, pandas UDF 0.59 s, Python UDF 3.20 s. Prefer built-ins, then Arrow-based vectorized UDFs (spark.sql.execution.arrow.pyspark.enabled). spark.driver.maxResultSize defaults to 1 GB, which is the real cap on collect().
  • Redshift: let AUTO distribution and SORTKEY AUTO decide, COMPOUND for regularly updated tables, and remember block min/max metadata can skip "up to 98 percent" of blocks. Athena partition keys must be STRING for pushdown, and join order puts the large table left unless Glue column statistics enable the cost-based optimizer.
  • Lambda: reserved concurrency is a floor and ceiling and is free; provisioned concurrency applies to a version or alias only and costs money. You can reserve only up to unreserved account concurrency minus 100. Provisioned concurrency target tracking accepts 10–90%.
  • SnapStart is mutually exclusive with provisioned concurrency, EFS, S3 Files and /tmp above 512 MB — which rules it out for most file-handling functions. The 10-second init limit does not apply to provisioned concurrency, SnapStart or Managed Instances.
  • Languages: Glue has exactly three job types (Spark, Ray, Python shell); Redshift Python UDFs are unsupported after June 30, 2026 — use Lambda UDFs. Amazon Linux 2's June 2026 end of life drives the cluster of Lambda runtime deprecations, and dotnet8 goes on November 10, 2026.
  • Practices: CodeCommit returned to full GA in November 2025, while Cloud9 is closed to new customers and CodeStar is retired. Lambda log-level filtering only works with LogFormat: JSON, and the CloudWatch Logs Essentials class (formerly Infrequent Access) has no metric filters, subscription filters or EMF — and the class cannot be changed later.
  • IaC: RetainExceptOnCreate is valid on DeletionPolicy but not UpdateReplacePolicy; RDS defaults to Snapshot, not Delete; and renaming a bucket, DynamoDB table, Redshift cluster, Glue database or Glue job forces Replacement. Let CloudFormation generate physical names for stateful resources.
  • cfn-lint validates, cfn-guard evaluates rules with no server-side enforcement, and Hooks enforce (30-second timeout, FAIL or WARN). CDK bootstrapping creates the CDKToolkit stack; assert with hasResourceProperties rather than snapshots.
  • SAM: Transform: AWS::Serverless-2016-10-31 is required; SimpleTable has one String key named id and no GSIs; policy templates cover S3, DynamoDB, Kinesis, Firehose and Athena but not Glue. --use-container is the fix for natively compiled dependencies; sam sync is development-only; sam local cannot test Step Functions.
  • Lambda storage: /tmp is 512 MB to 10,240 MB and survives across invocations even after a failure; EFS needs a VPC, an access point and a /mnt/ path, caps at 25,000 connections and offers advisory locking only. S3 Files is the current way to mount S3 from Lambda — Mountpoint has no Lambda support — and a function can use EFS or S3 Files, not both.
  • CI/CD: CodePipeline V2 bills per action-minute and adds Git-tag/PR/file-path triggers, stage rollback and stage conditions (including DeploymentWindow). Lambda AppSpec has only BeforeAllowTraffic and AfterAllowTraffic, each needing putLifecycleEventHookExecutionStatus within an hour. Glue Schema Registry has eight compatibility modes with BACKWARD recommended, and Iceberg schema changes are metadata-only.
  • Distributed computing and structures: the partition is the unit of parallelism everywhere; S3 object data is strongly consistent but bucket configurations are eventually consistent; DynamoDB strong reads do not work on GSIs.
