Schema design

Skill 2.4.1Design schemas for Amazon Redshift, DynamoDB, and Lake Formation.

The three stores ask for opposite habits. Redshift rewards a modelled warehouse with wide fact tables and compact columns. DynamoDB rewards designing backwards from the queries, often in a single table. A data lake rewards a clear layering of buckets and a predictable folder layout.

Redshift: facts, dimensions and columns

Redshift "is designed to work effectively with whatever schema design you choose", and AWS's distribution guidance uses a star schema — a fact table of events surrounded by dimension tables — as its example. Distribute the fact table and its largest dimension on their common join column so matching rows sit together, and let smaller dimensions use AUTO or ALL.

Sales star schema: fact and largest dimension 
CREATE TABLE dim_customer (
  customer_id  BIGINT NOT NULL,
  tier         VARCHAR(16),
  region       CHAR(2),
  PRIMARY KEY (customer_id)
)
DISTKEY (customer_id);

CREATE TABLE fact_sales (
  order_id     BIGINT NOT NULL,
  customer_id  BIGINT NOT NULL,
  store_id     INT,
  sold_at      TIMESTAMP,
  amount       DECIMAL(12,2),
  basket       SUPER
)
DISTKEY (customer_id)
SORTKEY (sold_at);
  • Column sizes: "Don't make it a practice to use the maximum column size for convenience." CHAR holds single-byte characters only (up to 4,096 bytes, blank-padded); VARCHAR holds multibyte characters, up to 65,535 bytes, and defaults to 256 when no length is given. Use real date and time types for dates.
  • Compression: ENCODE AUTO is the default. Specifying an encoding on any column turns ENCODE AUTO off for the whole table. Without it, sort key columns get RAW, numbers, dates and timestamps get AZ64, and strings get LZO. ANALYZE COMPRESSION only recommends encodings, and takes an exclusive lock while it does.
  • Constraints: primary, foreign and unique keys are "informational only" — not enforced, but used by the query planner. AWS advises not declaring them unless your loads guarantee them, because wrong constraints can give wrong results.
  • IDENTITY columns generate unique (not consecutive or ordered) values for INT or BIGINT surrogate keys.

Semi-structured data: SUPER

The SUPER type stores JSON-like nested data — the basket of items in each sale — up to 16 MB per value, and PartiQL navigates and unnests it in SQL. Set enable_case_sensitive_super_attribute when JSON keys differ only by case.

Unnest the basket array 
SELECT f.order_id, item.sku, item.qty
FROM fact_sales AS f,
     f.basket AS item
WHERE item.qty > 1;

Redshift Spectrum external tables can only be referenced in a late-binding view — a view created WITH NO SCHEMA BINDING, with every table name schema-qualified. A normal view over an external table fails.

Recent sales plus the lake archive 
CREATE VIEW all_sales AS
SELECT order_id, amount
FROM public.fact_sales
UNION ALL
SELECT order_id, amount
FROM lake.sales_archive
WITH NO SCHEMA BINDING;

DynamoDB: design from the access patterns

AWS's rule: "You shouldn't start designing your schema… until you know the questions it will need to answer." List the access patterns first, then choose keys that answer each one with a GetItem or Query, and "maintain as few tables as possible". A single table can hold several entity types, distinguished by key prefixes.

CUST#48213PROFILEName, tier, join date
CUST#48213ORDER#2026-11-07#9001One order; begins_with(sk, "ORDER#2026-11") lists a month
CUST#48213OFFER#BF26A loyalty offer with an expireAt TTL
STORE#12CUST#48213An edge: customer shops at store (adjacency list)
PatternSolves
Composite sort keyHierarchies such as ORDER#date#id, queried with begins_with and between
Adjacency listMany-to-many relationships: each edge is an item, and a GSI on the sort key gives the reverse lookup. For multi-hop graph queries AWS points to Neptune
Sparse indexOnly items that have the index key appear in a GSI, so an index on open_ticket holds only open tickets

Write sharding matters because each partition is "designed to deliver a maximum capacity of 3,000 read units per second and 1,000 write units per second". Burst capacity keeps up to five minutes of unused capacity, and adaptive capacity can isolate a hot item onto its own partition — but not beyond those per-partition limits.

Calculated shard suffix (Python) 
import zlib

SHARDS = 10

def shard_key(day, order_id):
    # same order always maps to same shard
    n = zlib.crc32(order_id.encode())
    return f"{day}#{n % SHARDS + 1}"

Since November 2025, a GSI's partition and sort keys can each have up to four attributes, so you no longer need synthetic A#B#C strings for index keys. Sort key attributes are matched left to right. Base-table keys are still single attributes.

Lake Formation: the data lake's shape

Lake Formation governs databases and tables in the Glue Data Catalog, so "designing a schema for Lake Formation" means designing the lake those tables describe. AWS Prescriptive Guidance recommends at least three layers, each in its own bucket:

LayerHolds
Landing (optional)Incoming data containing PII, masked before it reaches raw
RawData in its original format, with versioning on
StageCleaned and converted (for example CSV to Parquet), cataloged
AnalyticsAggregated, consumption-ready tables

Within each layer, use Hive-style key=value folders with lower-case names, one table per folder tree, and Iceberg for tables that need updates. Separate buckets per layer make Lake Formation grants and lifecycle rules simple: analysts get the analytics layer, only pipelines touch raw.

Lake Formation governed tables (ACID tables managed by Lake Formation) no longer have user-guide documentation. Use Apache Iceberg for transactional lake tables.

Changing data

Skill 2.4.2Address changes to the characteristics of data.

Data changes shape (new or renamed columns, new types), meaning (a customer moves region), and size or speed (volume doubles before the holidays). Each needs a different response.

Schema changes in Athena tables

Whether a change is safe depends on how the format matches columns. By default Parquet is read by name and ORC is read by index (position), which makes them safe for opposite changes.

ChangeParquet (by name)ORC (by index)CSV / TSVJSON, Avro
Add column at endSafeSafeSafeSafe
Add column in the middleSafeBreaksBreaksSafe
Drop columnSafeBreaksBreaksSafe
Reorder columnsSafeBreaksBreaksSafe
Rename columnBreaksSafeSafeBreaks

Adding columns at the end is safe everywhere. Type changes are allowed in every format but need testing; for Parquet and ORC they work only on partitioned tables.

Iceberg removes most of this worry: add, drop, rename and reorder are metadata-only changes that never rewrite data. Type promotion is limited to int to bigint, float to double, and a higher decimal precision, and Athena does not support REPLACE COLUMNS on Iceberg tables.

Evolve an Iceberg table (Athena) 
ALTER TABLE retail.orders_ice
ADD COLUMNS (channel string);

-- rename and move in one statement
ALTER TABLE retail.orders_ice
CHANGE status order_status string
AFTER order_id;

Schema changes in Redshift

Redshift's ALTER TABLE is narrow. ADD COLUMN takes one column per statement and cannot add a distribution key, sort key or identity column. DROP COLUMN cannot drop the distribution key or a sort key column. And ALTER COLUMN ... TYPE only changes the size of a VARCHAR — any other type change means adding a new column, copying data and dropping the old one, or rebuilding the table.

What Redshift allows 
ALTER TABLE dim_customer
ADD COLUMN email VARCHAR(320);

ALTER TABLE dim_customer
ALTER COLUMN tier TYPE VARCHAR(32);

ALTER TABLE dim_customer
RENAME COLUMN region TO region_code;

Inconsistent types in Glue

When one field has different types in different records — amount is a number in most files and a string in some — a Glue DynamicFrame keeps both as a choice type instead of failing. resolveChoice settles it: cast:type converts, make_cols splits into amount_double and amount_string, make_struct keeps both in a struct, project:type keeps one type and drops the rest, and match_catalog casts to the catalog table's types.

Resolve choice types (Glue PySpark) 
# one field: force a numeric type
fixed = dyf.resolveChoice(
    specs=[("amount", "cast:double")])

# every choice: keep both as columns
split = dyf.resolveChoice(
    choice="make_cols")

Changes in meaning: slowly changing dimensions

When a customer moves from the WA to the CA region, should last year's sales report the old region or the new one?

  • Type 1 overwrites the value. History is lost, which is fine for corrections. A MERGE upsert does it.
  • Type 2 keeps history: close the current row with an end timestamp and insert a new current row. Facts join to the row that was valid at the time.
Type 2 change in one transaction (Redshift) 
BEGIN;

-- close rows whose region changed
UPDATE dim_customer_hist d
SET valid_to = s.change_ts,
    is_current = FALSE
FROM stg_customer s
WHERE d.customer_id = s.customer_id
  AND d.is_current
  AND d.region <> s.region;

-- add a current row where none exists
INSERT INTO dim_customer_hist
SELECT s.customer_id, s.region,
       s.change_ts, '2999-12-31', TRUE
FROM stg_customer s
LEFT JOIN dim_customer_hist d
  ON d.customer_id = s.customer_id
 AND d.is_current
WHERE d.customer_id IS NULL;

END;

Changes in volume and quality

  • Redshift resize: elastic resize adds or removes nodes or changes node type in about ten minutes on average, within limits (generally up to four times larger or a quarter the size). Classic resize handles bigger changes and keeps the cluster readable and writable while it runs in the background. Serverless simply scales RPUs.
  • Partitioning chosen for last year's volume may be too fine or too coarse now; Iceberg's partition evolution changes it without rewriting old data.
  • Drift detection: Glue Data Quality rules such as ColumnCount, SchemaMatch and ColumnDataType catch shape changes. Dynamic rules compare with recent runs (last(k), supported in Glue ETL only), and anomaly detection learns trend and seasonality after at least three data points. Data quality is covered in depth in Domain 3.
DQDL: alert when the data changes shape 
Rules = [
  ColumnCount = 6,
  RowCount > avg(last(3)) * 0.5,
  DistinctValuesCount "store_id"
    between min(last(10)) - 1
    and max(last(10)) + 1
]

Schema conversion

Skill 2.4.3Perform schema conversion (for example, by using AWS SCT and AWS DMS Schema Conversion).

Moving between different database engines (heterogeneous migration) needs two things: the schema and code objects rewritten for the target, and the data copied. AWS splits these: schema conversion handles tables, views, stored procedures and functions; AWS DMS moves the rows. The retail platform is converting its legacy Oracle orders database to Aurora PostgreSQL.

DMS Schema Conversion

DMS Schema Conversion (DMS SC) is a "fully managed, web-based feature that builds on the AWS SCT conversion engine", run from the DMS console or API. It converts schema, not data. It uses three resources:

ResourceHolds
Instance profileNetwork (VPC and subnets), security and encryption settings for the conversion
Data providerConnection details for the source or the target database
Migration projectSource and target data providers, the instance profile, and the Secrets Manager secrets with credentials
  1. Assess. The assessment report shows what converts automatically and lists action items needing manual work, exportable as PDF or CSV.
  2. Convert. DMS SC converts the selected objects, applying any transformation rules. An extension pack emulates source features the target lacks. A virtual target lets you convert before the target database exists.
  3. Apply or export. Apply the converted code to the target, or save it as SQL in S3 for review.
  4. Move the data. A DMS task (full load plus CDC) copies rows into the converted schema.
SourceTargets in DMS SC
OracleAurora/RDS PostgreSQL, Aurora/RDS MySQL, Amazon Redshift
SQL ServerAurora/RDS PostgreSQL, Aurora/RDS MySQL
Db2 LUW, SAP ASEAurora/RDS PostgreSQL
Db2 for z/OSAurora/RDS PostgreSQL, RDS for Db2 (API and CLI only)
PostgreSQL / MySQLAurora/RDS MySQL / Aurora/RDS PostgreSQL

Generative AI conversion (generally available since December 2024) uses Bedrock models to convert code that rules cannot, such as complex procedures. It now covers the Oracle, SQL Server, Db2 and SAP ASE paths to PostgreSQL, but not triggers, dynamic SQL, indexes, constraints or column types.

AWS SCT

The AWS Schema Conversion Tool is the desktop application DMS SC grew out of, and it is still published. AWS notes that "AWS SCT supports more source and target databases than DMS Schema Conversion". Reach for it when DMS SC does not cover the path:

  • Data warehouses to Redshift: Teradata, Oracle, Netezza, Greenplum, Vertica, Snowflake, BigQuery, Azure Synapse and SQL Server data warehouses, with data extraction agents that pull data in parallel. SCT can also recommend Redshift sort and distribution keys.
  • ETL and application code: SSIS packages to Glue, Teradata BTEQ scripts to RSQL, and embedded SQL in applications.
  • NoSQL: Apache Cassandra to DynamoDB.

The exam guide's in-scope service list names DMS but not AWS SCT, while skill 2.4.3 names both. Expect DMS SC for managed, console-based conversions between relational engines, and SCT for warehouse migrations to Redshift and the less common paths.

When no conversion is needed

  • Homogeneous migrations (Oracle to RDS for Oracle, PostgreSQL to Aurora PostgreSQL) need no conversion. DMS homogeneous data migrations use native database tools and carry secondary objects such as functions and procedures with the data.
  • Babelfish for Aurora PostgreSQL accepts SQL Server's wire protocol and T-SQL on port 1433, so SQL Server applications can move "with few code changes" instead of a full conversion.

Data lineage

Skill 2.4.4Establish data lineage by using AWS tools (for example, Amazon SageMaker ML Lineage Tracking and Amazon SageMaker Catalog).

Lineage records where data came from and what was done to it: this report reads daily_sales, which a Glue job built from raw_pos, which a crawler cataloged from S3. It answers "which dashboards break if I change this table?" (downstream) and "why is this number wrong?" (upstream), and it is evidence for auditors.

SageMaker Catalog lineage

SageMaker Catalog (built on Amazon DataZone) captures and draws OpenLineage-compatible lineage for data assets, including column-level lineage. Lineage is versioned per event, so you can view the graph as it was at a point in time and compare versions.

SageMaker ML Lineage Tracking

ML Lineage Tracking records the steps of a machine learning workflow — which dataset trained which model, which model is behind which endpoint — for reproducibility and audit. SageMaker creates the entities automatically for training, processing and transform jobs, model packages and endpoints. AWS documents it as a Studio Classic feature, and Studio Classic is closed to new onboarding.

Optimization

Skill 2.4.5Describe best practices for indexing, partitioning strategies, compression, and other data optimization techniques.

Almost every lake and warehouse optimization is a way to read less data: skip partitions, skip files, skip row groups, skip columns, or read compressed bytes. The techniques differ by store.

Partitioning

  • Partition on what queries filter on, at the grain they filter: AWS warns not to partition by hour when queries span days, and to sort by timestamp inside partitions instead.
  • Do not over-partition. "Too many partition keys can result in fragmented datasets with too many files and files that are too small." High-cardinality columns such as customer ID make poor partition keys.
  • Filter partitions with equality where possible, remove old and empty partitions, and keep files flat inside each partition folder.
  • Spread hot prefixes: S3 supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per partitioned prefix, with no limit on the number of prefixes. Exceeding it returns 503 SlowDown.

File size and the small-files problem

Thousands of tiny files cost more in S3 requests and per-file overhead than in reading data. Compact them: Glue can group small input files (groupFiles), jobs can write fewer larger files, and Iceberg tables use OPTIMIZE or managed compaction (Task 2.1). Inside Parquet and ORC files, Athena's defaults are 128 MB row groups and 64 MB stripes, and AWS does not recommend going below them.

Bucketing

Bucketing hashes rows into a fixed number of files by a column. Use it for high-cardinality, evenly distributed columns queried by single values — the customer ID that makes a poor partition key. A query for one customer then reads one bucket per partition. Athena does not support INSERT INTO on bucketed tables, and Iceberg uses a bucket(n, col) partition transform instead.

Compression and formats

Columnar formats (Parquet, ORC) read only the columns a query needs and skip row groups using min/max statistics — which works best when files are sorted by the filter column. Compression then shrinks what is read.

Athena writesDefault compression
Parquet and text (Hive tables)GZIP
ORCZLIB
Iceberg tablesZSTD (level 3)

Athena also supports Snappy, LZ4, BZIP2 and others, set with write_compression. CTAS (CREATE TABLE AS SELECT) is the quick way to convert raw CSV or JSON into a partitioned, compressed Parquet table; its default format is Parquet, partition columns must come last in the SELECT, and one CTAS or INSERT INTO can write at most 100 partitions.

Rewrite raw sales as optimized Parquet 
CREATE TABLE retail.sales_opt
WITH (
  format = 'PARQUET',
  write_compression = 'ZSTD',
  external_location =
    's3://retail-lake/cur/sales_opt/',
  partitioned_by = ARRAY['sale_date'],
  bucketed_by = ARRAY['customer_id'],
  bucket_count = 8
) AS
SELECT order_id, customer_id, amount,
       sale_date
FROM retail.sales_raw;

Indexing across stores

StoreHow it avoids full scans

Let the engines tune themselves

  • Redshift automatic table optimization watches queries and applies sort and distribution keys "within hours" — but setting an explicit key takes the table out of it. Automatic VACUUM DELETE, automatic table sort and automatic ANALYZE run in the background.
  • Redshift result caching (on by default) answers repeated queries from the leader node, but not for Spectrum tables or tables that changed.
  • Athena query result reuse returns a previous result within the same workgroup, for up to 60 minutes by default (7 days maximum), but not for Lake Formation-governed data or non-deterministic functions.

Vectorization

Skill 2.4.6Describe vectorization concepts (for example, Amazon Bedrock knowledge base).

Embeddings are, in AWS's words, "numerical representations of real-world objects" that "capture inherent properties and relationships". An embedding model turns a piece of text (or an image) into a vector of numbers, and texts with similar meanings land close together. Search then means finding the stored vectors nearest to the query's vector — with an index type from Task 2.1.

How a Bedrock knowledge base builds vectors

  1. Connect a data source, such as an S3 prefix of product documents.
  2. Parse each file: the default text parser, a foundation model for documents with tables and images, or Bedrock Data Automation.
  3. Chunk the text into passages.
  4. Embed each chunk with the chosen embedding model.
  5. Store the vectors, chunk text and metadata in a vector store, mapped back to the source file.
  6. Sync when the source changes. Ingestion is incremental: only added, changed or deleted files are processed.

Chunking

StrategyHow it splits
DefaultAbout 300 tokens, respecting sentence boundaries
Fixed sizemaxTokens per chunk with an overlapPercentage between neighbours
HierarchicalTwo levels: small child chunks are searched, their larger parent chunks are returned for context
SemanticSplits where meaning shifts, using a foundation model (costs more); tuned by buffer size and breakpoint threshold
NoneOne chunk per file; you lose page-level citations

The trade-off, in AWS's words: "Small text embeddings are more precise, but retrieval aims for comprehensive context." Hierarchical chunking exists to get both. A Lambda function can apply custom chunking.

The chunking configuration cannot be changed after the data source is created. Neither can the knowledge base's embedding model. Changing either means a new data source or knowledge base and a full re-ingestion.

Embedding models and dimensions

ModelDimensionsVector types
Amazon Titan Text Embeddings V2256, 512 or 1,024 (default)Float or binary
Cohere Embed English / Multilingual v31,024Float or binary

Fewer dimensions and binary vectors cut storage and cost, at some loss of accuracy. Titan V2 normalizes vectors by default and takes up to 8,192 tokens of input. The query must be embedded with the same model and dimensions as the documents, because the index is built for one vector size. Binary vectors can only be stored in OpenSearch Serverless or OpenSearch managed clusters.

Vector stores

A knowledge base can store vectors in OpenSearch Serverless, OpenSearch managed clusters, S3 Vectors (lowest cost, float vectors only), Aurora PostgreSQL (pgvector), Neptune Analytics (for GraphRAG), or the third-party Pinecone, Redis Enterprise Cloud and MongoDB Atlas. Hybrid search (keyword plus semantic) works only with Aurora/RDS, OpenSearch Serverless and MongoDB stores that have a filterable text field.

Metadata filtering

Put a <file>.metadata.json file (up to 10 KB) next to each source file, and queries can filter on its attributes before ranking by similarity — for example, only documents about shoes.

Beyond plain vectors

  • Structured knowledge bases skip vectors altogether: Bedrock translates questions into SQL run by Redshift, against Redshift tables or Lake Formation-governed Glue tables.
  • GraphRAG on Neptune Analytics links chunks through extracted entities; S3 is its only data source.
  • Reranking models reorder retrieved chunks by relevance at query time.

From September 30, 2026, new Confluence, SharePoint, Salesforce and web crawler connectors can no longer be created on customer-managed knowledge bases (existing ones keep working). AWS now points to the Bedrock Managed Knowledge Base (March 2026), where Bedrock manages the vector store, embedding model and reranker. For a customer-managed knowledge base, the data sources are S3 and custom.

Key takeaways

  • Redshift: star schemas with the fact table and largest dimension on a shared distribution key; smallest sensible column sizes; specifying any encoding turns ENCODE AUTO off for the table. Primary and foreign keys are not enforced but the planner trusts them. SUPER holds up to 16 MB of nested data, and Spectrum tables appear only in late-binding views.
  • DynamoDB: access patterns first, few tables, composite sort keys, adjacency lists, sparse and overloaded GSIs. Each partition tops out at 3,000 RCU and 1,000 WCU, so shard hot keys with a suffix. GSIs can now use up to four attributes per key.
  • Data lake: raw, stage and analytics layers in separate buckets (plus a landing zone for PII), Hive-style lower-case folders, Iceberg for updatable tables. Lake Formation governed tables are no longer documented.
  • Athena schema changes: Parquet reads by name (add, drop and reorder are safe, rename breaks); ORC reads by index (rename is safe, drop and reorder break); adding at the end is always safe. Iceberg changes are metadata-only, with type promotion limited to int→bigint, float→double and wider decimals.
  • Redshift ALTER TABLE: one column per ADD COLUMN, no new distribution or sort key columns, and ALTER COLUMN TYPE only resizes a VARCHAR. Glue resolves mixed types with resolveChoice (cast, make_cols, make_struct, project, match_catalog).
  • Slowly changing dimensions: Type 1 overwrites (MERGE upsert), Type 2 closes the old row and inserts a new one. Elastic resize for most capacity changes, classic resize beyond its limits; Glue Data Quality dynamic rules and anomaly detection catch drift.
  • Schema conversion: DMS Schema Conversion converts schema and code, not data, using an instance profile, data providers and a migration project; generative AI conversion targets PostgreSQL. AWS SCT covers more paths, including warehouses to Redshift with extraction agents. Homogeneous migrations and Babelfish avoid conversion.
  • Lineage: SageMaker Catalog captures OpenLineage lineage automatically from crawlers, Redshift and visual ETL; Glue jobs need Glue 5.0+ and DataFrames, not DynamicFrames; custom tools post RunEvents. ML Lineage Tracking links datasets, jobs, models and endpoints, queried to a depth of 10.
  • Optimization: partition on common filters at the right grain, do not over-partition, compact small files, bucket high-cardinality lookup columns. Athena defaults: GZIP for Parquet and text, ZLIB for ORC, ZSTD for Iceberg; CTAS writes at most 100 partitions. S3 handles 3,500 writes and 5,500 reads per second per prefix.
  • Vectorization: parse, chunk, embed, store, sync incrementally. Chunking and the embedding model cannot be changed later. Titan V2 offers 256, 512 or 1,024 dimensions; binary vectors need OpenSearch; hybrid search needs Aurora/RDS, OpenSearch Serverless or MongoDB; metadata files are up to 10 KB.
