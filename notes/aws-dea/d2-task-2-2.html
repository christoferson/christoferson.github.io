Task 2.2: Understand data cataloging systems

A data lake is only usable if engines can find out what is in it. This task covers the catalog that answers that question: how engines read through it, how it is built and populated, how partitions are kept in step with S3, how it connects to databases, and the business catalog that helps people find data.

Consuming through a catalog

Skill 2.2.1Use data catalogs to consume data from the data's source.

The AWS Glue Data Catalog stores metadata only — AWS calls it "an index to the location, schema, and runtime metrics of your data sources". A table entry says where the files are, what columns they have, how to parse them and how they are partitioned. The data itself stays in S3 or in the source database, and every engine that reads the catalog reads the same definition.

EngineHow it uses the Glue Data Catalog
Amazon AthenaThe default catalog, named AwsDataCatalog. Athena DDL such as CREATE EXTERNAL TABLE writes the table into Glue without crawling anything
Amazon RedshiftAn external schema (FROM DATA CATALOG), or the auto-mounted awsdatacatalog database queried with three-part names
Amazon EMRHive and Spark use Glue as their metastore instead of a cluster-local one, set by a configuration classification
AWS Glue ETLfrom_catalog reads a table by name, including its partition columns
Amazon QuickAn Athena dataset picks catalog, database and table. (Quick evolved from QuickSight; the BI part is now Amazon Quick Sight)

Redshift: the auto-mounted catalog

With data_catalog_auto_mount on, Redshift shows the whole Glue Data Catalog as a database called awsdatacatalog, with no external schema to create. Queries are read-only, and the setting takes effect after a cluster reboot or a Serverless pause and resume.

Query a lake table by its three-part name 
SHOW data_catalog_auto_mount;

ALTER SYSTEM
  SET data_catalog_auto_mount = on;

SELECT store_id, SUM(amount)
FROM "awsdatacatalog"."retail"."pos_sales"
GROUP BY store_id;

GRANT USAGE ON DATABASE awsdatacatalog
  TO "IAMR:analyst";

EMR: Glue as the Hive metastore

By default each EMR cluster keeps its own Hive metastore, which disappears with the cluster. Pointing Hive and Spark at Glue gives a persistent metastore shared across clusters, services and accounts, which is what AWS recommends when you need one.

Cluster configuration for Spark 
[
  {
    "Classification": "spark-hive-site",
    "Properties": {
      "hive.metastore.client.factory.class":
        "com.amazonaws.glue.catalog.metastore.AWSGlueDataCatalogHiveClientFactory"
    }
  }
]

Use hive-site for Hive. To read another account's catalog, add hive.metastore.glue.catalogid with that account ID.

With Glue as the metastore, EMR does not support Hive transactions, renaming tables, Hive authorization (use Glue resource policies or Lake Formation instead), temporary tables or Hive constraints. A migration plan that relies on ALTER TABLE ... RENAME TO from Hive will break.

Glue ETL: read only the partitions you need

Reading through the catalog lets a Glue job prune partitions before it lists any S3 objects. There are two filters, and you can use both:

  • push_down_predicate filters after Glue lists every partition from the catalog, but before it lists S3 files. Spark SQL syntax.
  • catalogPartitionPredicate filters on the catalog server using partition indexes — the option for tables with millions of partitions. It uses a different (JSQL) parser.
Read the last week of clickstream 
PRED = "dt >= '2026-11-01'"
opts = {"catalogPartitionPredicate": PRED}

read = glueContext.create_dynamic_frame
dyf = read.from_catalog(
    database="retail",
    table_name="clickstream",
    # skips S3 listing of old partitions
    push_down_predicate=PRED,
    # prunes on the catalog side first
    additional_options=opts,
)

Use from_catalog rather than from_options when the table is partitioned: only the catalog read adds the partition columns to the DynamicFrame. Exclude patterns set on a crawler are stored as table properties and are honoured by from_catalog too.

Catalogs of catalogs

The Glue Data Catalog is no longer just databases and tables. It now holds a hierarchy of catalogs: the default catalog, Redshift managed catalogs, S3 Tables catalogs, and federated catalogs that expose external sources — other Iceberg REST catalogs (Snowflake Horizon and Polaris, Databricks Unity Catalog), external Hive metastores and dozens of databases — without copying their metadata. Lake Formation governs access to all of them, and engines outside AWS can reach Glue through its Iceberg REST endpoint (https://glue.<region>.amazonaws.com/iceberg, signed with SigV4).

Cross-account access

Another account can read your catalog through a Glue resource policy, an IAM role it assumes, or Lake Formation grants. Callers pass your account ID as the CatalogId. A Glue resource policy is limited to one per catalog and 10 KB, and covers Data Catalog resources only (databases, tables, functions, connections), not jobs or crawlers. If Lake Formation cross-account grants already exist, put-resource-policy needs --enable-hybrid TRUE. Athena in the other account registers your catalog as an Athena data catalog.

Technical catalogs

Skill 2.2.2Build and reference a technical data catalog (for example, AWS Glue Data Catalog, Apache Hive metastore).

A technical catalog describes data for machines: location, schema, file format, serializer, partitions. (A business catalog, in skill 2.2.6, describes it for people.) The Glue Data Catalog is a managed, Hive-metastore-compatible technical catalog.

What the Glue Data Catalog holds

ObjectWhat it is
CatalogThe top level: the account's default catalog, or a managed or federated one
DatabaseA namespace that groups tables
TableSchema, location, format and SerDe, partition keys, table properties such as classification
PartitionOne value combination of the partition keys and its S3 location
Partition indexA server-side index over partition keys for fast filtering
Column statisticsMin, max, nulls, distinct values and lengths, used by cost-based optimizers
Connection, crawler, classifierThe objects that reach sources and populate tables

Quotas and pricing

Quota (per Region)Default

These quotas are adjustable. Athena can query a table with 10 million partitions but "cannot read more than 1 million partitions in a single scan", so filter on partition keys.

Pricing: the first million objects stored and the first million requests each month are free; beyond that, storage is $1.00 per 100,000 objects per month. An object is a table, table version, partition, partition index, statistic, database or catalog — so a table with millions of partitions has a real catalog bill.

Partition indexes

Without an index, filtering partitions means fetching every partition and discarding most of them. A partition index lets the catalog return only matching partitions.

  • Up to 3 indexes per table. Keys can be string, numeric or date types.
  • Supported operators are =, >, >=, <, <= and BETWEEN, joined with AND. The first key of the index must appear in the filter, or the index is not used.
  • Redshift Spectrum, EMR and Glue Spark DataFrames use indexes automatically. Athena needs the table property partition_filtering.enabled, and Glue DynamicFrames need catalogPartitionPredicate.
  • Crawlers create partition indexes by default for S3 and Delta Lake targets, but do not set Athena's property.
Index by date, then let Athena use it 
aws glue create-partition-index \
  --database-name retail \
  --table-name clickstream \
  --partition-index \
    '{"Keys":["dt"],"IndexName":"by_dt"}'
Athena 
ALTER TABLE clickstream
SET TBLPROPERTIES (
  'partition_filtering.enabled' = 'true'
);

Column statistics

Athena and Redshift use Glue column statistics for cost-based optimization, such as choosing join order. Glue computes them with a background Spark job, on demand, on a schedule, or automatically for new tables with catalog-level settings. On-demand statistics are not refreshed on their own, and generation is billed at $0.44 per DPU-hour.

Compute statistics from a 10% sample 
aws glue start-column-statistics-task-run \
  --database-name retail \
  --table-name pos_sales \
  --role "$STATS_ROLE_ARN" \
  --sample-size 10.0

STATS_ROLE_ARN holds the ARN of a role that can read the table's S3 data and write statistics to the catalog.

Hive metastore options

Teams moving from on-premises Hadoop arrive with an Apache Hive metastore. There are three ways forward:

OptionHowChoose when
Migrate to GlueAWS's Hive metastore migration scripts (in the aws-glue-samples repository) copy databases, tables and partitions into GlueYou want one managed catalog and can retire the old metastore
Federate from GlueA Glue connection to the Hive metastore through a Lambda function and API Gateway creates a federated database, governed by Lake Formation (Hive 3 and later)The metastore must stay, but Athena, Redshift and EMR should see it
Athena Hive connectorA Lambda-based connector registers the Hive metastore as an Athena data catalogOnly Athena needs it; DDL support is limited

An EMR cluster can also keep an external Hive metastore on Amazon RDS or Aurora, which survives cluster termination — but it is a database you run, while the Glue Data Catalog is serverless.

A table created through the Glue CreateTable API or CloudFormation AWS::Glue::Table without a TableType (EXTERNAL_TABLE or VIRTUAL_VIEW) makes Athena DDL fail with "NullPointerException Name is null". Athena DDL and crawlers set the type for you; hand-built tables must set it.

Crawlers

Skill 2.2.3Discover schemas and use AWS Glue crawlers to populate data catalogs.

A Glue crawler connects to a data store, samples the data, works out its format and schema with classifiers, groups files into tables and partitions, and writes the result to the Data Catalog. It is the hands-off way to catalog data whose layout you do not want to type in.

What a crawler can read

AccessData storesInclude path
NativeS3, DynamoDB, and the open table formats Delta Lake, Apache Iceberg and Apache Hudibucket/folder/
JDBCRedshift, Snowflake, Aurora, MariaDB, SQL Server, MySQL, Oracle, PostgreSQLdatabase/schema/table (database/table for MySQL and Oracle); % can replace schema or table but not database
MongoDB clientMongoDB, MongoDB Atlas, Amazon DocumentDBdatabase/collection

JDBC and MongoDB sources need a Glue connection. There are no crawlers for data streams — stream tables are defined by hand or by the Schema Registry. For S3, exclude patterns use Unix glob relative to the include path: * stays inside one folder, ** crosses folders. A sample size of 1–249 files per leaf folder speeds up crawls of large, uniform folders; without one, every file is read.

An Iceberg crawler must be the only writer of its catalog table — no table optimizers or Spark jobs committing to the same entry. A Hudi merge-on-read table produces two catalog tables, suffixed _ro (read-optimized) and _rt (real-time).

Classifiers

A classifier recognises a format and returns a certainty between 0.0 and 1.0.

  1. Custom classifiers run first, in the order you list them. The first to return certainty 1.0 wins outright.
  2. Otherwise the built-in classifiers run: Avro, ORC, Parquet, JSON, BSON, XML, Ion, common log formats, then CSV.
  3. The highest certainty wins. If nothing scores above 0.0, the classification is UNKNOWN.

Custom classifiers come in four kinds: grok (log lines), XML, JSON (with a JSON path to the records) and CSV (custom delimiter, quote character and header). The built-in CSV classifier needs at least two columns and two rows and guesses the header; when it cannot, columns are named col1, col2 and so on — a sign you need a custom CSV classifier.

Changing a classifier does not reclassify data already crawled. The crawler remembers what it classified. AWS's fix is to create a new crawler (or delete and re-create the table).

Controlling what the crawler writes

SettingValuesUse it to
SchemaChangePolicy.UpdateBehaviorUPDATE_IN_DATABASE, LOGLOG stops the crawler overwriting a schema you curated
SchemaChangePolicy.DeleteBehaviorLOG, DELETE_FROM_DATABASE, DEPRECATE_IN_DATABASEDecide what happens to tables whose data vanished
RecrawlPolicyCRAWL_EVERYTHING, CRAWL_NEW_FOLDERS_ONLY, CRAWL_EVENT_MODEFull crawls, incremental crawls of new folders, or S3-event-driven crawls
Tables.AddOrUpdateBehaviorMergeNewColumnsAdd new columns only, never change existing ones
Partitions.AddOrUpdateBehaviorInheritFromTableMake every partition use the table's schema, so partitions never drift

Incremental crawls (CRAWL_NEW_FOLDERS_ONLY) force both behaviours to LOG and never detect changed or deleted partitions. They are fast for append-only layouts, but a schema change in old folders will not be picked up until a full crawl.

Why a crawler makes too many tables

The classic complaint is "one dataset, hundreds of tables". The crawler creates a separate table whenever folders look incompatible — different formats, compression or schemas, or files at unexpected depths. The fixes:

  • CombineCompatibleSchemas ("Create a single schema for each S3 path") ignores schema differences and groups by path, so year=2025 with columns A, B and year=2026 with C, D become one table with a year partition.
  • TableLevelConfiguration fixes the folder depth where tables start (the bucket's top level is 1).
  • Remove stray files sitting next to partition folders — empty marker files left by jobs are a common cause.
  • TableThreshold makes the crawler fail and write nothing if it would create more tables than the limit, so a bad layout cannot flood the catalog.

Folders that are not in Hive key=value style get partition columns named partition_0, partition_1, and so on, which you can rename afterwards.

    RecrawlBehavior=CRAWL_EVERYTHING \

Permissions and cost

A crawler runs as an IAM role that needs read access to the source and write access to the catalog. When the S3 location is registered with Lake Formation, set LakeFormationConfiguration with UseLakeFormationCredentials, grant the role data location permission and database CREATE, and give it lakeformation:GetDataAccess. For DynamoDB, the scan rate (0.1–1.5 of read capacity, 0.5 by default for provisioned tables) caps how much of the table's capacity a crawl may use.

Crawlers cost $0.44 per DPU-hour, billed per second. A crawler that runs every hour against a stable layout is wasted money; an event-mode crawler or partition projection (next section) is usually cheaper.

Partition sync

Skill 2.2.4Synchronize partitions with a data catalog.

For Hive-style tables, a query engine reads only the partitions the catalog knows about. When a job writes dt=2026-11-07/ to S3, the files are there but invisible until the partition is registered. "The new data is in S3 but the query returns nothing" is almost always this.

MethodHow it worksBest for
Glue crawlerDiscovers new folders on a schedule or from S3 eventsChanging schemas and layouts you do not control
MSCK REPAIR TABLEAthena scans the table location and adds missing Hive-style partitionsThe first load of a table
ALTER TABLE ADD PARTITIONRegisters named partitions, with an explicit LOCATION if neededDaily additions, and any non-Hive layout
Partition projectionAthena computes partitions from rules in table properties; nothing is registeredPredictable keys (dates, integers, enums) and very many partitions
Glue job enableUpdateCatalogThe job registers the partitions it writesPipelines that already write with Glue
BatchCreatePartition APIYour code adds up to 100 partitions per callCustom writers, such as a Lambda function

Iceberg tables need none of this. Their partitions live in the table's own metadata (hidden partitioning), so every commit is visible immediately with no repair or ADD PARTITION step. That is one more reason new lake tables are often Iceberg.

MSCK REPAIR TABLE and ALTER TABLE

MSCK REPAIR TABLE has a list of documented limits: it works only with Hive-style key=value paths; it only adds partitions and never removes stale ones (use ALTER TABLE DROP PARTITION); it fails silently on values containing a colon, such as timestamps; it ignores partition columns starting with _; and it can time out partway, so you rerun it. AWS recommends it for a table's first load and ALTER TABLE ADD PARTITION for daily additions.

Register, repair and drop partitions (Athena) 
-- non-Hive layout: LOCATION is required
ALTER TABLE pos_sales ADD IF NOT EXISTS
  PARTITION (dt = '2026-11-07')
  LOCATION
    's3://retail-lake/raw/pos/2026/11/07/';

-- Hive-style dt=... folders only
MSCK REPAIR TABLE clickstream;

-- MSCK never removes; do it yourself
ALTER TABLE pos_sales
  DROP PARTITION (dt = '2025-11-07');

IF NOT EXISTS also avoids zero-byte _$folder$ placeholder files. Redshift Spectrum uses the same ALTER TABLE ... ADD IF NOT EXISTS PARTITION ... LOCATION statement on external tables.

Partition projection

With partition projection, Athena calculates partition values and locations from table properties instead of looking them up in the catalog. New partitions need no registration at all, and queries over tables with huge numbers of partitions skip the catalog lookup. Projection types are enum, integer, date and injected. AWS recommends it for Firehose output, whose default prefix is yyyy/MM/dd/HH/.

Clickstream from Firehose, projected by hour 
CREATE EXTERNAL TABLE clicks (
  session_id string,
  page       string,
  ts         timestamp
)
PARTITIONED BY (datehour string)
ROW FORMAT SERDE
  'org.openx.data.jsonserde.JsonSerDe'
LOCATION 's3://retail-lake/raw/clicks/'
TBLPROPERTIES (
  'projection.enabled' = 'true',
  'projection.datehour.type' = 'date',
  'projection.datehour.format' =
    'yyyy/MM/dd/HH',
  'projection.datehour.range' =
    '2026/01/01/00,NOW',
  'projection.datehour.interval' = '1',
  'projection.datehour.interval.unit' =
    'HOURS',
  'storage.location.template' =
    's3://retail-lake/raw/clicks/${datehour}/'
);

Partition projection is Athena-only. Once it is enabled, Athena ignores partitions registered in the catalog — but Redshift Spectrum, EMR and Athena for Spark ignore projection and still need real partitions. SHOW PARTITIONS does not list projected partitions, and a projected partition with no data returns zero rows, not an error. AWS's warning: if more than half the projected partitions would be empty, use ordinary partitions.

Registering partitions from a Glue job

A Glue job can add the partitions it writes by setting enableUpdateCatalog and partitionKeys on its sink. updateBehavior defaults to UPDATE_IN_DATABASE; with LOG it still adds partitions but leaves the table schema alone. It works only for S3 targets in JSON, CSV, Avro or Parquet (through the Glue Parquet writer), and the partition keys must match the table's keys in the same order.

Write daily order partitions and register them 
sink = glueContext.getSink(
    connection_type="s3",
    path="s3://retail-lake/cur/orders/",
    enableUpdateCatalog=True,
    updateBehavior="UPDATE_IN_DATABASE",
    partitionKeys=["year","month","day"],
)
sink.setFormat("glueparquet")
sink.setCatalogInfo(
    catalogDatabase="retail",
    catalogTableName="orders")
sink.writeFrame(dyf)

Firehose dynamic partitioning writes data into partition-style prefixes but its documentation says nothing about registering those partitions in the catalog. Pair it with partition projection, a crawler, or your own BatchCreatePartition call.

Connections

Skill 2.2.5Create new source or target connections for cataloging (for example, AWS Glue).

A Glue connection is a Data Catalog object that holds how to reach a data store: endpoint, credentials (or a pointer to a secret), SSL settings and the VPC placement. Crawlers use it to catalog the store, and jobs reuse it to read or write, so one definition serves both.

Connection typeReachesKey properties
JDBCRelational databases and RedshiftJDBC_CONNECTION_URL (or host, port and engine), SECRET_ID (or user name and password), JDBC_ENFORCE_SSL
MONGODBMongoDB and DocumentDBCONNECTION_URL and credentials
KAFKAMSK or self-managed Kafka (for jobs)KAFKA_BOOTSTRAP_SERVERS, SASL options including AWS_MSK_IAM

Marketplace and customConnectors from AWS Marketplace or your ownShown as type UNKNOWN in the console

For a JDBC source in a VPC, the connection's subnet and security group decide where Glue places its network interfaces, so the security group needs a self-referencing rule and the subnet needs a route to the database (covered on Task 1.2).

Version 2 connections and secrets

Since December 2024 Glue also has version 2 ("unified") connections: one definition that Glue, Athena and SageMaker Unified Studio can all use, with per-engine property sets. Glue Studio creates v2 connections by default, and their credentials live in Secrets Manager. That has a networking consequence: a job in a private subnet then needs VPC endpoints (or a NAT gateway) for Secrets Manager and STS.

  • A Secrets Manager secret for a connection stores keys username and password. The managed AWSGlueServiceRole policy does not grant secretsmanager:GetSecretValue; add it to the role.
  • With JDBC_ENFORCE_SSL, Glue validates the server certificate and host name. A custom certificate must be X.509 in DER encoding, supplied as base64 PEM.
  • An ETL job can use JDBC connections in only one subnet, so sources in different subnets need routing between them.
conn.json: Aurora orders, credentials in a secret 
{
  "Name": "aurora-orders",
  "ConnectionType": "JDBC",
  "ConnectionProperties": {
    "JDBC_CONNECTION_URL":
      "jdbc:postgresql://retail-orders.cluster-abc123.us-east-1.rds.amazonaws.com:5432/orders",
    "SECRET_ID": "prod/aurora/orders",
    "JDBC_ENFORCE_SSL": "true"
  },
  "PhysicalConnectionRequirements": {
    "SubnetId": "subnet-0a1b2c3d",
    "SecurityGroupIdList": [
      "sg-0a1b2c3d"
    ],
    "AvailabilityZone": "us-east-1a"
  }
}
Create it, test it, crawl through it 
aws glue create-connection \
  --connection-input file://conn.json

aws glue test-connection \
  --connection-name aurora-orders
Crawler target: every table in public 
{
  "JdbcTargets": [{
    "ConnectionName": "aurora-orders",
    "Path": "orders/public/%"
  }]
}

When a crawler or job "cannot connect", check in this order: does test-connection succeed; does the security group allow itself; does the subnet route to the database; can the role read the secret; and, for v2 connections in a private subnet, are the Secrets Manager and STS endpoints there.

Connections for federated catalogs

Connections also power catalog federation. To expose a source without crawling it, you create a Glue connection to it, register it in Lake Formation with register-resource --with-federation, and create a federated catalog with glue create-catalog. Queries then discover the remote tables at run time, and Lake Formation controls who sees what. This is how the Data Catalog reaches Snowflake and Databricks Iceberg catalogs and external Hive metastores.

Business catalogs

Skill 2.2.6Create and manage business data catalogs (for example, Amazon SageMaker Catalog).

A technical catalog tells Athena that retail.pos_sales has a column amt_net. It does not tell a marketing analyst that this is "net sales after returns", who owns it, whether it is trustworthy, or how to get access. A business catalog adds that layer.

AspectTechnical catalog (Glue Data Catalog)Business catalog (SageMaker Catalog)
AudienceEngines and engineersAnalysts, data scientists, data owners
HoldsSchema, location, format, partitionsBusiness names, descriptions, glossary terms, owners, quality scores
AccessIAM and Lake Formation grantsSubscription requests approved by the owner, then fulfilled as grants

What SageMaker Catalog is

Amazon SageMaker Catalog is the governance part of SageMaker Unified Studio, announced in December 2024 with the next generation of SageMaker and generally available since March 13, 2025. It is "built on Amazon DataZone": DataZone is still documented as its own service, the CLI is still aws datazone, and domain IDs still start with dzd_. On the exam, treat the two names as the same capability.

ConceptMeaning
DomainThe top-level boundary for assets, users and projects
Domain unitA sub-division (such as a business unit) with delegated authority
ProjectA team's collaboration and permissions boundary; it owns assets and subscribes to others
Data sourceA scheduled or on-demand import of technical metadata from Glue or Redshift
AssetA cataloged data object — table, view, file, dashboard — with versions
Data productA bundle of assets that consumers subscribe to with one request
Business glossaryDefined terms, owned by a project but visible across the domain, attached to assets and columns
Metadata formA custom set of typed fields (boolean, date, decimal, integer, string, glossary term) added to assets

From Glue table to subscribed asset

  1. Import. A data source in the producer project pulls tables from the retail Glue database into the project's inventory, visible only to that project.
  2. Enrich. Owners add business names, descriptions, glossary terms and metadata forms. AI recommendations (generated with Amazon Bedrock) can draft names, descriptions and glossary terms, but each suggestion must be accepted or edited — unreviewed suggestions are left out when you publish.
  3. Publish. Publishing makes the asset discoverable across the domain. Changes need republishing; only the latest published version is visible.
  4. Subscribe. A consumer project finds the asset and submits a request with a justification; the owning project approves or rejects it.
  5. Fulfil. For managed assets — Lake Formation-managed Glue tables and Redshift tables and views — the grant is made automatically. For anything else, SageMaker Catalog emits an EventBridge event so your own automation can grant access.

Automatic fulfilment for a Glue table requires the table to be managed by Lake Formation, and the publishing project's role needs DESCRIBE and SELECT with grant option. LF-Tag-based access control, cross-Region sharing and cross-account sharing of federated-catalog assets are not supported for automatic grants.

Quality, lineage and cost

  • Data quality: a Glue data source can import Glue Data Quality scores (autoImportDataQualityResult), shown on the asset and updated without republishing. Other tools post results through the API.
  • Lineage is OpenLineage-compatible and covered on Task 2.4.
  • Pricing: there has been no per-user charge since November 1, 2024. You pay per request ($10 per 100,000 beyond 4,000 free a month, with core APIs such as search free), metadata storage ($0.40 per GB beyond 20 MB) and compute units, plus Bedrock tokens for AI recommendations.

The Glue Data Catalog itself is gaining business context — glossary terms, custom metadata fields and semantic search — but that feature is in preview in four Regions. For the exam, the business catalog is SageMaker Catalog.

Key takeaways

  • The Glue Data Catalog stores metadata only; data stays at the source. Athena uses it as AwsDataCatalog, Redshift through external schemas or the auto-mounted, read-only awsdatacatalog database, EMR as its Hive metastore through hive-site or spark-hive-site, and Glue jobs through from_catalog.
  • EMR with Glue as the metastore does not support Hive transactions, table renames, Hive authorization or temporary tables. In Glue jobs, push_down_predicate prunes after listing partitions; catalogPartitionPredicate prunes on the server using partition indexes.
  • Glue resource policy: one per catalog, 10 KB, Data Catalog resources only; add --enable-hybrid TRUE when Lake Formation grants exist. The catalog now holds federated catalogs (Snowflake, Databricks, Hive metastores) and an Iceberg REST endpoint.
  • Quotas: 10 million partitions per table, 20 million per account, 200,000 tables per database; Athena reads at most 1 million partitions per scan. First million objects and requests free each month, then $1 per 100,000 objects — partitions, indexes and statistics all count.
  • Partition indexes: 3 per table, the first key must be in the filter, and Athena needs partition_filtering.enabled. Column statistics feed Athena and Redshift cost-based optimization. Hand-built Glue tables need a TableType or Athena DDL fails.
  • Hive metastore: migrate with AWS's scripts, federate through a Lambda-backed Glue connection (Hive 3+), or use the Athena-only Hive connector.
  • Crawlers: S3, DynamoDB, Delta, Iceberg and Hudi natively; JDBC and MongoDB through connections; none for streams. Custom classifiers run first and certainty 1.0 wins; changing a classifier does not reclassify old data.
  • Crawler output: UpdateBehavior=LOG protects a curated schema, MergeNewColumns only adds columns, InheritFromTable stops partitions drifting. Incremental crawls force LOG and miss changed partitions. Too many tables: CombineCompatibleSchemas, TableLevelConfiguration, remove stray files, TableThreshold.
  • Partition sync: MSCK REPAIR TABLE is Hive-style only and never removes partitions; use ALTER TABLE ADD/DROP PARTITION for daily changes and non-Hive layouts. Glue jobs can register partitions with enableUpdateCatalog; BatchCreatePartition takes 100 per call. Iceberg needs no sync.
  • Partition projection is Athena-only: Athena then ignores catalog partitions, while Spectrum and EMR still need real ones. It suits Firehose's yyyy/MM/dd/HH layout and huge partition counts; avoid it when most projected partitions are empty.
  • Connections: JDBC, MongoDB, Kafka, Network and native SaaS types; credentials in Secrets Manager (add GetSecretValue to the role). v2 connections in a private subnet need Secrets Manager and STS endpoints. A job's JDBC connections must share one subnet.
  • SageMaker Catalog is built on DataZone: domains, projects, data sources from Glue or Redshift, assets, data products, glossaries and metadata forms. Publish to share; subscriptions are approved by the owner and fulfilled automatically only for Lake Formation-managed Glue tables and Redshift. AI suggestions must be accepted before publishing; no per-user fee.
