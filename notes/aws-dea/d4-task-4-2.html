Task 4.2: Apply authorization mechanisms

Once an identity is known, every request asks one question: is it allowed? This task covers writing IAM policies that answer it precisely, keeping credentials safe, granting access inside Redshift, governing the data lake with Lake Formation, choosing between role-, tag- and attribute-based models, and proving that nothing has more access than it needs.

Custom IAM policies

Skill 4.2.1Create custom IAM policies when a managed policy does not meet the needs.

AWS says plainly that its managed policies "don't grant least privilege permissions". They are a starting point: broad, maintained by AWS (they can change), and not editable. When a job needs one bucket prefix, one database or one workgroup, you write a customer managed policy (reusable, up to 5 versions kept) or, for a one-off, an inline policy that lives and dies with one identity.

How a request is evaluated

  1. An explicit deny in any applicable policy wins, always.
  2. Otherwise the request needs an allow. In one account, an allow in either the identity policy or the resource policy is enough.
  3. Guardrails must also allow it: a permissions boundary (on the identity), SCPs (on the account's principals) and RCPs (on the account's resources). These never grant anything; the result is the intersection.
  4. Anything not allowed is implicitly denied.

Resource control policies (November 2024) are the newest guardrail: an SCP limits what your principals can do; an RCP limits who can reach your resources, including principals outside your organization. RCPs cover services such as S3, KMS, Secrets Manager, DynamoDB, SQS and STS — but not Glue, Athena, Redshift or Lake Formation — and do not apply to the management account.

Writing policies for data services

  • S3 listing is a bucket-level action: limit it with the s3:prefix condition, and grant object actions on the prefix ARN.
  • Glue Data Catalog: "All operations performed on a Data Catalog resource require permission on the resource and all the ancestors" — so reading a table needs the catalog, database and table ARNs. Access is per table; individual partitions cannot be scoped.
  • Athena: scope query actions to a workgroup ARN, and grant the S3 query-results location.
  • Policy variables such as ${aws:PrincipalTag/team} make one policy serve many identities. ${aws:username} works only for IAM users, not roles.
Analyst queries the retail database in the etl workgroup 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "QueryInWorkgroup",
      "Effect": "Allow",
      "Action": [
        "athena:StartQueryExecution",
        "athena:GetQueryExecution",
        "athena:GetQueryResults",
        "athena:StopQueryExecution",
        "athena:GetWorkGroup"
      ],
      "Resource":
        "arn:aws:athena:us-east-1:111111111111:workgroup/etl"
    },
    {
      "Sid": "ReadCatalog",
      "Effect": "Allow",
      "Action": [
        "glue:GetDatabase",
        "glue:GetTable",
        "glue:GetTables",
        "glue:GetPartitions"
      ],
      "Resource": [
        "arn:aws:glue:us-east-1:111111111111:catalog",
        "arn:aws:glue:us-east-1:111111111111:database/retail",
        "arn:aws:glue:us-east-1:111111111111:table/retail/*"
      ]
    },
    {
      "Sid": "ReadData",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource":
        "arn:aws:s3:::retail-lake/cur/*"
    },
    {
      "Sid": "QueryResults",
      "Effect": "Allow",
      "Action": [
        "s3:GetBucketLocation",
        "s3:ListBucket",
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": [
        "arn:aws:s3:::retail-results",
        "arn:aws:s3:::retail-results/etl/*"
      ]
    }
  ]
}

Allowing one workgroup "does not limit users to only this workgroup" if another policy allows others. To confine someone, add an explicit deny for other workgroups. And if the table is governed by Lake Formation, these IAM permissions are necessary but not sufficient — Lake Formation must grant it too (below).

Limits

  • A managed policy holds up to 6,144 characters (white space not counted); inline policies total up to 10,240 characters per role.
  • A role can have 20 managed policies attached by default (raisable to 25); a user 10 (up to 20); a group 10.

Storing credentials

Skill 4.2.2Store application and database credentials (for example, Secrets Manager, AWS Systems Manager Parameter Store).

Rotation mechanics are on Task 4.1. Here the question is where to keep a credential and how pipelines read it.

Automatic rotationYesNo

Database credentials that should rotate → Secrets Manager. Endpoints, flags and non-rotating settings → Parameter Store (free standard tier). Parameter Store can also reference a secret through /aws/reference/secretsmanager/<name>, so code that reads parameters can read secrets the same way.

An encrypted parameter, and reading it back 
aws ssm put-parameter \
  --name /retail/etl/api-key \
  --value "$API_KEY" \
  --type SecureString \
  --key-id alias/retail-etl

aws ssm get-parameter \
  --name /retail/etl/api-key \
  --with-decryption

SecureString encrypts only the value (not the name) with a symmetric KMS key, and reading it needs kms:Decrypt. An advanced parameter cannot be downgraded to standard.

  --cluster-identifier retail-dw \
  --database retail \
  --secret-arn "$RS_SECRET_ARN" \
  --sql "SELECT COUNT(*) FROM orders"

The managed policy AmazonRedshiftDataFullAccess allows GetSecretValue only on secrets tagged with the key RedshiftDataFullAccess. An untagged secret fails with access denied even though the policy looks broad.

MWAA configuration: Airflow connections from Secrets Manager 
secrets.backend =
  airflow.providers.amazon.aws.secrets.secrets_manager.SecretsManagerBackend
secrets.backend_kwargs =
  {"connections_prefix":
     "airflow/connections",
   "variables_prefix":
     "airflow/variables"}

Sharing a secret with another account needs three things: a resource policy on the secret, a customer managed KMS key whose key policy allows that account (the default aws/secretsmanager key cannot be shared), and an identity policy in the caller's account.

Access inside Redshift

Skill 4.2.3Provide database users, groups, and roles access and authority in a database (for example, for Amazon Redshift).

IAM decides who may connect to Redshift; inside the database, SQL privileges decide what each user may touch. Redshift supports users, legacy groups, and roles (role-based access control), which can be nested by granting one role to another.

System-defined roles

RoleCan
sys:monitorRead catalog and system tables
sys:operatorMonitor, plus ANALYZE, VACUUM and cancelling queries
sys:dbaCreate and drop schemas, tables, views, procedures and functions
sys:secadminManage users and roles and row-level security and masking policies — but cannot read user tables unless granted
sys:superuserEverything

Separating sys:secadmin from data access lets a security team manage permissions without seeing the data.

Granting privileges

An analyst role over the sales schema 
CREATE ROLE analyst;
GRANT ROLE analyst TO alice;

GRANT USAGE ON SCHEMA sales
  TO ROLE analyst;
GRANT SELECT ON ALL TABLES IN SCHEMA sales
  TO ROLE analyst;

-- tables created later, by anyone
GRANT SELECT FOR TABLES IN SCHEMA sales
  TO ROLE analyst;

-- only some columns of a sensitive table
GRANT SELECT (order_id, region, amount)
  ON sales.customers TO ROLE analyst;
  • A table grant is useless without USAGE on its schema.
  • ON ALL TABLES IN SCHEMA covers existing tables only. For future tables, scoped permissions (GRANT ... FOR TABLES IN SCHEMA) cover objects created by any user, while ALTER DEFAULT PRIVILEGES covers only objects created by one named user.
  • Stored procedures take only EXECUTE. System permissions such as CREATE USER or IGNORE RLS can be granted only to roles.
  • External schemas (Spectrum): USAGE on the schema; when the tables are governed by Lake Formation, access is granted in Lake Formation to the cluster's IAM role.

Row-level security

Redshift RLS policies filter rows per role. The policy below lets each analyst see only regions listed for them in a mapping table.

Analysts see only their own regions 
CREATE RLS POLICY by_region
WITH (region VARCHAR(20))
USING (region IN (
  SELECT region FROM sec.user_region
  WHERE user_name = current_user));

GRANT SELECT ON sec.user_region
  TO RLS POLICY by_region;

ATTACH RLS POLICY by_region
  ON sales.orders TO ROLE analyst;

ALTER TABLE sales.orders
  ROW LEVEL SECURITY ON;

Once ROW LEVEL SECURITY ON is set, a user with no attached policy sees no rows. Policies attached to superusers and sys:secadmin are ignored, and roles granted IGNORE RLS bypass filtering. Creating and attaching policies needs a superuser or sys:secadmin. Masking columns instead of hiding rows is dynamic data masking (Task 4.3).

Federated identities

  • Users from IAM appear as IAM:name (users) or IAMR:name (roles).
  • With IAM Identity Center, you choose a namespace when setting up the integration, and Identity Center groups map to Redshift roles named "<namespace>:<group>". Users removed from Identity Center are not dropped from Redshift automatically.
  • The newer Redshift federated permissions let permissions, RLS and masking be defined once and enforced in every registered warehouse.

RDS and Aurora PostgreSQL use the same ideas — PostgreSQL roles, GRANT and default privileges.

Lake Formation permissions

Skill 4.2.4Manage permissions through AWS Lake Formation (for Amazon Redshift, Amazon EMR, Amazon Athena, and Amazon S3).

IAM can grant a whole table and a whole S3 prefix, but not "these columns" or "rows where region is EMEA". Lake Formation adds database-style grants over Glue Data Catalog objects and the S3 data under them, enforced by every integrated engine. It costs nothing extra.

How it works

  1. Register the S3 location with Lake Formation, using a role it can assume to read the data.
  2. Appoint data lake administrators and grant permissions on databases, tables, columns and filters.
  3. When Athena, Redshift Spectrum, EMR or Glue queries a table, it calls GetDataAccess; Lake Formation checks the grants and vends temporary credentials scoped to the data. The engine applies column and row filtering and must fail closed.

For compatibility, Lake Formation starts with Super granted to IAMAllowedPrincipals and "Use only IAM access control" on for new databases and tables — meaning IAM alone decides and Lake Formation grants have no effect. Remove those defaults (empty CreateDatabaseDefaultPermissions and CreateTableDefaultPermissions; upgrade existing resources), or use hybrid access mode to opt in principals one at a time.

  • Register with the service-linked role in simple cases, but a custom role is required for access from EMR, for buckets encrypted with the AWS managed aws/s3 key, and for locations in another account.
  • Callers still need IAM permissions for the API calls (glue:GetTable, lakeformation:GetDataAccess); Lake Formation decides the data access.
Register the lake and switch off IAM-only defaults 
aws lakeformation register-resource \
  --resource-arn \
    arn:aws:s3:::retail-lake \
  --role-arn "$LF_REGISTER_ROLE_ARN"

aws lakeformation put-data-lake-settings \
  --data-lake-settings \
    file://settings.json
settings.json 
{
  "DataLakeAdmins": [{
    "DataLakePrincipalIdentifier":
      "arn:aws:iam::111111111111:role/LFAdmin"
  }],
  "CreateDatabaseDefaultPermissions": [],
  "CreateTableDefaultPermissions": []
}

Permissions

ResourcePermissions
DatabaseCREATE_TABLE, ALTER, DROP, DESCRIBE, ALL (Super)
TableSELECT, INSERT, DELETE, ALTER, DROP, DESCRIBE, ALL
Data locationDATA_LOCATION_ACCESS — needed only to create tables pointing at the location, not to query them

Any permission can be granted with grant option. Grantees can be IAM users and roles, SAML and Identity Center users and groups, Quick Sight users, and other accounts, organizations or OUs.

SELECT on two columns of orders 
aws lakeformation grant-permissions \
  --principal \
    DataLakePrincipalIdentifier="$ROLE" \
  --permissions SELECT \
  --resource file://orders-cols.json

ROLE holds the analyst role's ARN.

orders-cols.json 
{
  "TableWithColumns": {
    "DatabaseName": "retail",
    "Name": "orders",
    "ColumnNames": ["order_id", "region"]
  }
}

Data filters: row, column and cell security

A data filter combines a row filter expression with included or excluded columns; together they give cell-level security. Filters work with SELECT only.

EMEA rows, without the email column 
aws lakeformation create-data-cells-filter \
  --table-data file://emea-filter.json
emea-filter.json 
{
  "TableCatalogId": "111111111111",
  "DatabaseName": "retail",
  "TableName": "orders",
  "Name": "emea_no_email",
  "RowFilter": {
    "FilterExpression": "region = 'EMEA'"
  },
  "ColumnWildcard": {
    "ExcludedColumnNames": ["email"]
  }
}
  • Row filter expressions are a PartiQL subset under 2,048 characters: no functions, and a column can be compared with a constant but not with another column. String comparisons are case sensitive.
  • At most 100 filters per principal per table. Cell-level security does not work on nested columns, views or resource links.

LF-Tags: tag-based access control

Granting on named tables does not scale: n principals times m tables. LF-Tags attach key-value labels to databases, tables and columns, and grants target tag expressions, so a new table tagged domain=sales is covered automatically.

Tag the orders table and grant by tag 
aws lakeformation create-lf-tag \
  --tag-key domain \
  --tag-values sales finance

aws lakeformation add-lf-tags-to-resource \
  --resource file://orders-table.json \
  --lf-tags TagKey=domain,TagValues=sales

aws lakeformation grant-permissions \
  --principal \
    DataLakePrincipalIdentifier="$ROLE" \
  --permissions SELECT DESCRIBE \
  --resource file://sales-tag-policy.json
orders-table.json 
{
  "Table": {
    "DatabaseName": "retail",
    "Name": "orders"
  }
}
sales-tag-policy.json 
{
  "LFTagPolicy": {
    "CatalogId": "111111111111",
    "ResourceType": "TABLE",
    "Expression": [{
      "TagKey": "domain",
      "TagValues": ["sales"]
    }]
  }
}
  • Tags inherit from database to table to column and can be overridden. A resource has one value per key, up to 50 LF-Tags; keys and values are stored in lower case.
  • In an expression, values of one key are OR'd; different keys are AND'd.
  • LF-Tags are not IAM tags; they exist only in Lake Formation. Since April 2025, Lake Formation can also grant to principals by their IAM tags (Lake Formation ABAC).

RBAC, TBAC and ABAC

Skill 4.2.5Apply authorization methods that address business needs (role-based, tag-based, and attribute-based).

ModelHow it decidesStrength and weakness
Role-based (RBAC)Permissions per job function, attached to roles or groupsSimple to understand; but "when you or your users add new resources... you have to update the policies"
Tag-based (Lake Formation TBAC)LF-Tags on catalog objects, grants on tag expressionsScales to thousands of tables; applies only to Lake Formation-governed data
Attribute-based (IAM ABAC)IAM tags on principals compared with tags on resourcesFewer policies, new tagged resources covered automatically; depends on disciplined tagging

ABAC with IAM

An ABAC policy matches a tag on the caller with the same tag on the resource. One policy then serves every project: a principal tagged project=orders reaches only resources tagged project=orders. Attributes can arrive as session tags from a SAML or OIDC identity provider, or as IAM Identity Center attributes for access control, so the corporate directory drives access.

Secrets for your own project only 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action":
      "secretsmanager:GetSecretValue",
    "Resource": "*",
    "Condition": {
      "StringEquals": {
        "aws:ResourceTag/project":
          "${aws:PrincipalTag/project}"
      }
    }
  }]
}
S3 objects tagged for your project 
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource":
    "arn:aws:s3:::retail-lake/*",
  "Condition": {
    "StringEquals": {
      "s3:ExistingObjectTag/project":
        "${aws:PrincipalTag/project}"
    }
  }
}

Tag-based authorization keeps spreading: DynamoDB tables (November 2024), S3 access points, directory buckets and S3 Tables (2025), and S3 general purpose buckets once ABAC is turned on for the bucket. Protect the tags themselves — whoever can change a resource's tag can change who may access it, so restrict tagging actions with aws:RequestTag and aws:TagKeys.

Matching the mechanism to the need

Business needMechanism
Teams split by department or projectIAM ABAC on a project tag, or LF-Tags on catalog objects
Regional analysts see only their regionLake Formation row filter; Redshift RLS; Quick Sight row-level security for dashboards
PII columns hidden from most usersLake Formation column or cell filter, an LF-Tag on the column, or Redshift column grants (masking is Task 4.3)
Thousands of tables and many teamsLF-Tag-based grants rather than named-resource grants
A partner account reads a datasetLake Formation cross-account sharing, or a resource policy plus a customer managed KMS key
Database job functions (loader, analyst, auditor)Redshift roles, including sys:secadmin for the security team

Least privilege

Skill 4.2.6Construct custom policies that meet the principle of least privilege.

Least privilege means granting only the actions, on only the resources, under only the conditions a task needs. In practice: start narrow, add what is proven necessary, and keep checking for access nobody uses.

A least-privilege policy for the ETL job

Glue job: read raw, write curated, nothing else 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOnlyItsPrefixes",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource":
        "arn:aws:s3:::retail-lake",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["raw/pos/*",
                        "cur/orders/*"]
        }
      }
    },
    {
      "Sid": "ReadRaw",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource":
        "arn:aws:s3:::retail-lake/raw/pos/*"
    },
    {
      "Sid": "WriteCurated",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource":
        "arn:aws:s3:::retail-lake/cur/orders/*"
    }
  ]
}

Pair it with guardrails on the bucket itself, such as denying any request not made over TLS:

Bucket policy statement: TLS only 
{
  "Sid": "RestrictToTLSRequestsOnly",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::retail-lake",
    "arn:aws:s3:::retail-lake/*"
  ],
  "Condition": {
    "Bool": {
      "aws:SecureTransport": "false"
    }
  }
}

Least-privilege habits the exam rewards: specific actions instead of s3:*; resource ARNs down to the prefix or table; conditions (s3:prefix, tags, aws:SecureTransport, aws:SourceVpce); separate roles per job rather than one shared role; permissions boundaries for roles that developers create; and generated policies refined over time.

Key takeaways

  • AWS managed policies do not grant least privilege; write customer managed policies (versioned, reusable) or inline policies (one identity). Explicit deny wins; otherwise an allow is needed; boundaries, SCPs and RCPs grant nothing and intersect. RCPs do not cover Glue, Athena, Redshift or Lake Formation.
  • Glue catalog access needs the catalog, database and table ARNs; Athena is scoped by workgroup ARN plus the results bucket; s3:prefix limits listing. ${aws:username} does not work for roles. Roles take 20 managed policies by default; managed policies hold 6,144 characters.
  • Secrets Manager for rotating secrets (64 KB, replicas, resource policies); Parameter Store for configuration (no rotation, standard tier free, 40 TPS shared by default). Cross-account secrets need a customer managed KMS key. AmazonRedshiftDataFullAccess reads only secrets tagged RedshiftDataFullAccess.
  • Redshift: roles (nestable) and system roles; sys:secadmin manages security without reading data. Grant schema USAGE plus table privileges; scoped permissions for future tables; column-level grants. With RLS on, users without a policy see no rows. Identity Center groups map to roles named "namespace:group".
  • Lake Formation: register locations (custom role for EMR, aws/s3-encrypted buckets or other accounts); remove the IAMAllowedPrincipals defaults or use hybrid mode, or grants do nothing. Engines get vended credentials through GetDataAccess.
  • Data filters give row, column and cell security (row expressions with no functions, 100 filters per principal per table). LF-Tags: one value per key per resource, OR within a key and AND across keys, inherited down to columns, not IAM tags. Athena SQL and Spectrum support all levels; EMR needs runtime roles; Glue 5.0+ with DataFrames; Athena Spark is not supported.
  • RBAC per job function; Lake Formation TBAC for many tables; IAM ABAC comparing aws:PrincipalTag with aws:ResourceTag for many teams. Protect tagging permissions, since tags become access.
  • Least privilege: specific actions and resources plus conditions, then Access Analyzer — policy generation (no data events or PassRole), validation, custom checks such as check-no-new-access in pipelines, and unused access findings.
