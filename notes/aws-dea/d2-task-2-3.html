Task 2.3: Manage the lifecycle of data

Data is born, moved, cooled, kept for as long as the rules say and then destroyed — and it must survive failures throughout. This task covers moving data between S3 and Redshift, tiering and expiring S3 objects, versioning and TTL, deleting data on demand, and keeping it available.

Load and unload

Skill 2.3.1Perform load and unload operations to move data between Amazon S3 and Amazon Redshift.

Redshift moves bulk data with two commands: COPY loads from S3 (and from DynamoDB, EMR or remote hosts over SSH) and UNLOAD writes query results to S3. Both run in parallel on every slice. AWS's guidance is blunt: COPY "loads large amounts of data much more efficiently than using INSERT statements" — row-by-row INSERT is the wrong answer for bulk loads.

COPY basics

Load gzipped CSV parts 
COPY sales
FROM 's3://retail-lake/curated/sales/'
IAM_ROLE default
CSV IGNOREHEADER 1 GZIP
MAXERROR 10;
  • Formats: CSV, delimited text (pipe by default), fixed-width, JSON, Avro, Parquet and ORC. For JSON, 'auto' matches keys to column names case-sensitively, 'auto ignorecase' ignores case, and a JSONPaths file maps nested fields explicitly.
  • Authorization: IAM_ROLE 'arn...', or IAM_ROLE default for the role set as default on the cluster or namespace. To load from another account, chain roles: 'arn:...:role/RoleA,arn:...:role/RoleB', no spaces.
  • Other Region: add REGION when the bucket is in another Region (data transfer charges apply).
  • Errors: MAXERROR (default 0) tolerates bad rows, and NOLOAD validates without loading. Look in SYS_LOAD_ERROR_DETAIL; the older STL_LOAD_ERRORS covers only main provisioned clusters, not Serverless or concurrency scaling.
  • Housekeeping: COMPUPDATE chooses column encodings (by default only when the table is empty) and STATUPDATE refreshes statistics.
Why did the load fail? (works on Serverless) 
SELECT file_name, line_number,
       column_name, error_message
FROM sys_load_error_detail
ORDER BY start_time DESC
LIMIT 10;

Splitting files for parallel load

COPY gives files to slices, so a single large file loads on one slice while the rest of the cluster waits. Redshift automatically splits uncompressed CSV, Parquet and ORC files of 128 MB or more. Files it cannot split — JSON, and CSV compressed with gzip and similar codecs — should be split by the producer into files "close in size, from 1 MB to 1 GB after compression", with the file count "a multiple of the number of slices in your cluster".

Prefixes and manifests

The FROM path is a key prefix: sales/2026-11 also matches sales/2026-11.bak and sales/2026-11-old/. A manifest lists exactly which files to load, and "mandatory": true makes COPY fail if one is missing — the fix for "COPY loaded a stray file" and "COPY silently skipped a late file".

pos.manifest 
{
  "entries": [
    {"url":
      "s3://retail-lake/in/pos-1.csv.gz",
     "mandatory": true},
    {"url":
      "s3://retail-lake/in/pos-2.csv.gz",
     "mandatory": true}
  ]
}
Load exactly those files 
COPY sales
FROM 's3://retail-lake/in/pos.manifest'
IAM_ROLE default
CSV GZIP
MANIFEST;

Manifest files can point to several buckets, but all must be in the cluster's Region. A file listed twice is loaded twice. For Parquet and ORC, each entry also needs "meta": {"content_length": n}.

Columnar COPY has its own rules

COPY from Parquet or ORC maps columns by position (the column counts must match), requires the bucket to be in the same Region, and supports only a short list of options — no REGION, no MAXERROR, no IGNOREALLERRORS, no automatic compression. Any bad row fails the whole load.

Load Parquet 
COPY sales
FROM 's3://retail-lake/curated/pq/'
IAM_ROLE default
FORMAT AS PARQUET;

Auto-copy jobs

A COPY JOB (generally available since October 30, 2024, on Serverless and RA3) watches an S3 prefix and loads each new file once, automatically. It needs an S3 event integration between the bucket and the warehouse first, created with aws redshift create-integration.

Load every new POS file as it lands 
COPY public.pos_events
FROM 's3://retail-lake/in/pos/'
IAM_ROLE
  'arn:aws:iam::111111111111:role/rs-load'
FORMAT AS JSON 'auto'
JOB CREATE pos_events_job
AUTO ON;

A COPY JOB does not load files that were already in the prefix when it was created, does not accept IAM_ROLE default, MAXERROR or manifests, and job names cannot contain a hyphen. Monitor it in SYS_COPY_JOB and SYS_COPY_JOB_DETAIL.

Upserts: stage, then MERGE

COPY only appends. To apply changes, load them into a staging table and MERGE them into the target. The target must not match more than one source row ("Found multiple matches to update the same tuple"), so deduplicate the staging table first. When source and target have the same columns, the short form REMOVE DUPLICATES updates matches, inserts the rest, and performs better.

Apply a day's corrections 
COPY sales_staging
FROM 's3://retail-lake/in/fixes/'
IAM_ROLE default
FORMAT AS PARQUET;

MERGE INTO sales
USING sales_staging s
  ON sales.order_id = s.order_id
REMOVE DUPLICATES;

UNLOAD

UNLOAD runs a query and writes the result to S3, by default one or more files per slice in parallel. AWS says Parquet is "up to 2x faster to unload and consumes up to 6x less storage" than text.

Export sales as partitioned Parquet 
UNLOAD ('SELECT order_id, store_id,
          amount,
          TRUNC(sold_at) AS sale_date
         FROM sales')
TO 's3://retail-lake/export/sales/'
IAM_ROLE default
FORMAT AS PARQUET
PARTITION BY (sale_date)
MAXFILESIZE 256 MB
CLEANPATH;
OptionBehaviour
PARTITION BYHive-style sale_date=.../ folders. Partition columns are left out of the files unless you add INCLUDE. It does not register partitions in the Glue catalog
MAXFILESIZE5 MB to 6.2 GB; the default and maximum file size is 6.2 GB
PARALLEL OFFWrites serially, for a single ordered output (still split at the size limit)
CLEANPATH / ALLOWOVERWRITEUNLOAD fails if files exist. CLEANPATH deletes them first; ALLOWOVERWRITE overwrites. They cannot be combined
MANIFEST, HEADERA list of written files; a header row for text formats
ENCRYPTED, KMS_KEY_IDSSE-S3 is the default; Parquet with ENCRYPTED supports SSE-KMS only

Parquet UNLOAD cannot take HEADER, delimiters or compression options (row groups are always Snappy-compressed), and the outer SELECT cannot have a LIMIT — nest it in a subquery. Client-side encryption for COPY and UNLOAD was removed after April 30, 2026; use SSE-S3 or SSE-KMS.

Running loads from a pipeline

Lambda functions and Step Functions run COPY and UNLOAD through the Redshift Data API: asynchronous HTTPS calls with no drivers or open connections, authenticated with IAM or a Secrets Manager secret. batch-execute-statement runs several statements in one transaction. Pass a ClientToken so a retried call does not load twice.

Start a load from the CLI or a function 
aws redshift-data execute-statement \
  --workgroup-name retail \
  --database dev \
  --sql file://load_sales.sql

Lifecycle transitions

Skill 2.3.2Manage S3 Lifecycle policies to change the storage tier of S3 data.

S3 storage classes trade storage price against retrieval cost and speed. A Lifecycle configuration moves objects to cheaper classes as they age, automatically. Every class has eleven nines of durability; they differ in availability, Availability Zones, minimum storage duration and retrieval.

ClassAvailabilityMinimum durationRetrieval
Standard99.99%, 3+ AZsNoneMilliseconds
Intelligent-Tiering99.9%, 3+ AZsNoneMilliseconds (hours for optional archive tiers); no retrieval fees, a per-object monitoring fee
Standard-IA99.9%, 3+ AZs30 daysMilliseconds, per-GB fee
One Zone-IA99.5%, 1 AZ30 daysMilliseconds, per-GB fee
Glacier Instant Retrieval99.9%, 3+ AZs90 daysMilliseconds, higher per-GB fee
Glacier Flexible Retrieval99.99% after restore90 daysRestore first: minutes to 12 hours
Glacier Deep Archive99.99% after restore180 daysRestore first: 12 to 48 hours

The IA classes and Glacier Instant Retrieval bill a minimum object size of 128 KB. Glacier Flexible Retrieval and Deep Archive add about 40 KB of metadata per object (8 KB billed at the Standard rate). Both rules make archiving many small files expensive.

How transitions work

  • Downhill only. Transitions go to colder classes: Standard to anything; Standard-IA to Intelligent-Tiering, One Zone-IA or any Glacier class; Glacier Flexible Retrieval only to Deep Archive. Nothing transitions out of Deep Archive — restore and copy instead.
  • Small objects stay put. Since September 2024, lifecycle by default does not transition objects smaller than 128 KB to any class. Override this with an ObjectSizeGreaterThan/ObjectSizeLessThan filter or the default-minimum-size setting.
  • Minimum durations chain. One rule cannot move an object out of a class before that class's minimum duration: Glacier Instant Retrieval at day 30 means Deep Archive no earlier than day 120.
  • Each transition is a billed request, and moving or deleting an object before its minimum duration is charged for the rest of that duration.
  • Asynchronous. Lifecycle actions can lag by days, but billing changes as soon as an object becomes eligible (transitions into Intelligent-Tiering bill once complete).
  • Filters: one prefix, any number of tags (combined with And) and object size. There is no exclude filter; use tags. A bucket holds up to 1,000 rules (not adjustable), and a PUT replaces the whole configuration.
lc.json: tier raw POS files as they age 
{
  "Rules": [{
    "ID": "tier-raw-pos",
    "Status": "Enabled",
    "Filter": {
      "And": {
        "Prefix": "raw/pos/",
        "ObjectSizeGreaterThan": 131072
      }
    },
    "Transitions": [
      {"Days": 30,
       "StorageClass": "STANDARD_IA"},
      {"Days": 90,
       "StorageClass": "GLACIER_IR"},
      {"Days": 365,
       "StorageClass": "DEEP_ARCHIVE"}
    ]
  }]
}
Apply it (replaces existing rules) 
aws s3api put-bucket-lifecycle-configuration \
  --bucket retail-lake \
  --lifecycle-configuration file://lc.json

Intelligent-Tiering instead of rules

When access patterns are unknown or changing, Intelligent-Tiering moves each object for you: to Infrequent Access after 30 days without access, Archive Instant Access after 90, and — only if you activate them — Archive Access (90 to 730 days) and Deep Archive Access (180 to 730 days). An access moves the object back to Frequent. Objects under 128 KB are never monitored and stay in Frequent Access. Lifecycle rules win when the pattern is known ("raw files are never read after a month"); Intelligent-Tiering wins when it is not.

To decide, use Storage Class Analysis, which watches access for about 30 days or more but recommends only Standard to Standard-IA transitions, and S3 Storage Lens dashboards, which show the effect of rules (noncurrent bytes, delete markers, incomplete multipart uploads).

Restoring archived objects

TierGlacier Flexible RetrievalDeep Archive
Expedited1–5 minutes (objects under 250 MB)Not available
Standard3–5 hoursWithin 12 hours
Bulk5–12 hoursWithin 48 hours

A restore creates a temporary copy for the number of days you ask for, billed at the Standard rate on top of the archive. The object's storage class does not change; to bring it back permanently, copy it over itself into another class. Watch for the s3:ObjectRestore:Completed event or check head-object.

Restore last year's POS file for a week 
aws s3api restore-object \
  --bucket retail-lake \
  --key raw/pos/2025/11/07.csv.gz \
  --restore-request '{"Days": 7,
    "GlacierJobParameters":
      {"Tier": "Bulk"}}'

The original vault-based service, now called Amazon Glacier, is no longer accepting new customers; AWS points to the S3 Glacier storage classes instead. Objects in those classes are not visible through the vault API. An answer that creates a Glacier vault for new archives is out of date.

Expiration

Skill 2.3.3Expire data when it reaches a specific age by using S3 Lifecycle policies.

Expiration is the lifecycle action that deletes. It is how retention policies such as "delete raw clickstream after 13 months" are enforced without a cleanup job.

ActionWhat it does
Expiration (Days or Date)Expires the current version at an age, or from a date onwards (midnight UTC; not both in one rule)
NoncurrentVersionExpirationPermanently deletes old versions NoncurrentDays after they were replaced; NewerNoncurrentVersions (1–100) keeps the latest few
ExpiredObjectDeleteMarkerRemoves delete markers that have no versions left behind them
AbortIncompleteMultipartUploadDeletes the parts of uploads never completed DaysAfterInitiation days after they started

What "expire" means depends on versioning

  • Unversioned bucket: the object is permanently removed.
  • Versioning enabled: S3 adds a delete marker and the object becomes a noncurrent version — still stored and still billed until NoncurrentVersionExpiration removes it.
  • Versioning suspended: S3 adds a delete marker with a null version ID, which replaces any existing null version.

Expiring objects in a versioned bucket makes the object count go up, not down: every expiration adds a delete marker and keeps the data. A retention rule on a versioned bucket needs both Expiration and NoncurrentVersionExpiration, plus a cleanup of expired delete markers.

Timing and billing

S3 counts from the object's creation time and rounds up to the next midnight UTC: an object created on January 15 at 10:30 with a 3-day rule becomes eligible on January 19 at 00:00 UTC. Deletion happens asynchronously afterwards, but "you are not charged for expiration or the storage time associated with an object that has expired". Expiring an IA object before 30 days, or a Glacier object before 90 or 180, still bills the minimum duration.

Retention for a versioned log prefix 
{
  "Rules": [
    {
      "ID": "expire-clicks",
      "Status": "Enabled",
      "Filter": {"Prefix": "raw/clicks/"},
      "Expiration": {"Days": 395},
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 30,
        "NewerNoncurrentVersions": 3
      },
      "AbortIncompleteMultipartUpload": {
        "DaysAfterInitiation": 7
      }
    },
    {
      "ID": "clean-markers",
      "Status": "Enabled",
      "Filter": {"Prefix": "tmp/"},
      "Expiration": {
        "ExpiredObjectDeleteMarker": true
      }
    }
  ]
}

The marker cleanup is a separate rule because ExpiredObjectDeleteMarker cannot sit in the same Expiration as Days; rules with Days clean up their own expired markers anyway.

Three restrictions catch people. ExpiredObjectDeleteMarker and AbortIncompleteMultipartUpload cannot be used in a rule with a tag filter. Expiration does not remove incomplete multipart uploads — only the abort action does, and those hidden parts are billed. And bucket-policy Deny statements do not stop lifecycle actions.

For deadline-bound legal deletions, AWS advises not to rely on lifecycle timing alone. Use S3 Inventory, whose report includes each object's lifecycle expiration date, to find stragglers and delete them yourself.

Versioning and TTL

Skill 2.3.4Manage S3 versioning and DynamoDB TTL.

Two opposite tools. S3 versioning keeps data you overwrite or delete, so mistakes can be undone. DynamoDB TTL removes data automatically once it is no longer needed.

S3 Versioning

  • A bucket is unversioned (the default), enabled or suspended. Once enabled, it can never return to unversioned; suspending stops new versions but keeps existing ones.
  • Every overwrite creates a new version with its own ID. Objects that existed before versioning have version ID null.
  • A DELETE without a version ID adds a delete marker, so the object seems gone but can be recovered by deleting the marker. A DELETE with a version ID removes that version permanently.
  • Every version is a full, billed object: three versions of a 1 GB file are 3 GB. Pair versioning with NoncurrentVersionExpiration.
  • Versioning is required for replication and for Object Lock.
Turn on versioning, then list versions 
aws s3api put-bucket-versioning \
  --bucket retail-lake \
  --versioning-configuration \
    Status=Enabled

aws s3api list-object-versions \
  --bucket retail-lake \
  --prefix curated/sales/

MFA Delete requires an MFA code to change the versioning state or permanently delete a version. Only the bucket owner's root user can enable it, only through the CLI or API, and it cannot be used on a bucket with a lifecycle configuration. For most data lakes, Object Lock or replication to a locked-down account is the more practical protection.

S3 Object Lock

Object Lock makes object versions write-once-read-many (WORM), and has been assessed for SEC 17a-4, CFTC and FINRA requirements. It can be enabled on existing buckets, but once on it cannot be turned off and versioning cannot be suspended.

ProtectionWho can remove it
Governance modeUsers with s3:BypassGovernanceRetention who send the bypass header — protection against accidents, not against administrators
Compliance modeNobody, including the root user; the retention cannot be shortened. AWS: the only way to delete such objects early is to delete the account
Legal holdAnyone with s3:PutObjectLegalHold. It has no expiry and is independent of retention periods

Lifecycle rules respect locks: S3 takes no action on locked noncurrent versions, and expiring a locked current version only adds a delete marker.

DynamoDB TTL

Time to Live deletes items after a timestamp you store in each item. The retail platform puts an expireAt attribute on short-lived loyalty offers.

  • The TTL attribute must be a Number holding Unix epoch seconds. Other types, or values more than five years in the past, are ignored.
  • Expired items are deleted "typically within a few days" — not at the exact second — and TTL deletes consume no write capacity. They are removed from indexes too.
  • Expired items still appear in reads and still count towards storage until deleted, so filter them out with a condition such as expireAt > :now.
  • One TTL attribute per table. Enabling takes about an hour, and a repeated call within that hour fails.
  • Global tables: in the default multi-Region eventual-consistency mode, the delete replicates and each replica Region pays for the replicated write. Multi-Region strong consistency tables do not support TTL.
Enable TTL on the loyalty table 
aws dynamodb update-time-to-live \
  --table-name loyalty \
  --time-to-live-specification \
    "Enabled=true, AttributeName=expireAt"

TTL deletes appear in DynamoDB Streams as REMOVE records with userIdentity.type of Service and principal dynamodb.amazonaws.com, which separates them from deletes your users make. That is the standard way to archive expired items to S3 before they are gone. The stream needs a view type that includes old images.

Archive only TTL deletes (Lambda, Python) 
def is_ttl_delete(r):
    who = r.get("userIdentity", {})
    removed = r["eventName"] == "REMOVE"
    by_ttl = who.get("type") == "Service"
    return removed and by_ttl

def handler(event, context):
    for r in event["Records"]:
        if not is_ttl_delete(r):
            continue
        # item as it was before deletion
        archive(r["dynamodb"]["OldImage"])

TTL deletes are identifiable this way only in the Region where the deletion happened, not in global-table replica Regions.

Deleting data

Skill 2.3.5Delete data to meet business and legal requirements.

Two kinds of requirement drive deletion. Retention limits ("keep transactions seven years, then delete") are age-based and suit lifecycle rules and TTL. Erasure requests ("delete everything about customer 48213 within 30 days") target specific records scattered across many files and stores, and are much harder. Both must reach every copy — including old versions, replicas and backups.

Erasing records in a data lake

S3 objects are immutable, so removing one customer's rows means rewriting every file that contains them.

  • Iceberg tables make it a SQL statement: DELETE, then compaction and snapshot expiry so the old files that still contain the rows are physically removed (see Task 2.1). Until the old snapshots expire, time travel can still read the deleted rows.
  • Plain Parquet or CSV needs a rewrite job. AWS's Amazon S3 Find and Forget solution shows the pattern: Athena finds the objects containing the identifiers, Fargate workers rewrite them without the matching rows, Step Functions orchestrates, and the old object versions are deleted so the erasure cannot be undone.
  • S3 Batch Operations has no "delete objects" operation. Its operations include copy, tagging, restore, Object Lock settings, replication and Invoke Lambda; bulk deletes go through a Lambda function or lifecycle expiration.
Erase a customer from an Iceberg table (Athena) 
DELETE FROM retail.customer_events
WHERE customer_id = 48213;

-- rewrite files, then expire snapshots
OPTIMIZE retail.customer_events
REWRITE DATA USING BIN_PACK;
VACUUM retail.customer_events;

Deleting in Redshift and DynamoDB

Redshift DELETE only marks rows; the space is reclaimed by a vacuum. Redshift runs a DELETE ONLY vacuum automatically in the background, but it pauses under load, so a compliance job can run one explicitly. To empty a table, TRUNCATE is much faster and needs no vacuum — but it commits the current transaction.

Redshift: delete and reclaim 
DELETE FROM sales
WHERE customer_id = 48213;

VACUUM DELETE ONLY sales TO 95 PERCENT;

In DynamoDB, DeleteItem removes an item immediately and TTL removes it within days. Neither touches backups.

Copies that outlive the delete

CopyHow long it keeps deleted data
S3 noncurrent versionsUntil a version-ID delete or NoncurrentVersionExpiration
S3 replicasVersion-ID deletes are never replicated; delete the replica separately
DynamoDB PITRUp to 35 days of history; deleting a PITR-enabled table leaves a system backup for 35 days
DynamoDB on-demand backupsUntil you delete the backup
RDS automated backups0–35 days (default 1 day through the API and CLI, 7 in the console)
RDS and Redshift manual snapshotsUntil deleted — they survive deletion of the instance or cluster
CloudWatch LogsForever by default; set a log group retention (1 day to 10 years)

A common design is to keep backups short (for example 35 days) and document that erased data ages out of them within that window, rather than editing backups. Retention settings are then part of the compliance answer, not an afterthought.

Preventing deletion

Legal requirements sometimes forbid deletion. S3 Object Lock in compliance mode and legal holds (see versioning) block deletes in S3. For backups, AWS Backup Vault Lock does the same:

  • Governance mode can be removed by users with the right IAM permissions.
  • Compliance mode has a grace period of at least 72 hours (ChangeableForDays, 3 to 36,500). After it ends the lock is immutable — not even AWS can remove it.
  • Minimum and maximum retention settings make backup jobs that do not comply fail.
Lock a backup vault: 7 to 35 days, compliance 
aws backup put-backup-vault-lock-configuration \
  --backup-vault-name retail-vault \
  --changeable-for-days 3 \
  --min-retention-days 7 \
  --max-retention-days 35

Deleting Glacier Flexible Retrieval or Deep Archive objects before 90 or 180 days incurs a pro-rated early-deletion charge. A legal deletion is still required, but budget for it.

Resiliency

Skill 2.3.6Protect data with appropriate resiliency and availability.

Start with two numbers from the AWS disaster recovery whitepaper. RPO (recovery point objective) is the "maximum acceptable amount of time since the last data recovery point" — how much data you can lose. RTO (recovery time objective) is the "maximum acceptable delay between the interruption of service and restoration of service" — how long you can be down. Lower numbers cost more.

StrategyWhat runs in the recovery RegionRPO / RTO
Backup and restoreBackups onlyHours; cheapest
Pilot lightData replicated and live; compute switched offMinutes / tens of minutes
Warm standbyA scaled-down but working copy that can take traffic at onceSeconds / minutes
Multi-site active/activeFull capacity serving trafficNear zero; most expensive

Replication protects against losing a Region, not against bad data: a corrupting job or accidental delete replicates too. Even active/active designs need point-in-time backups.

Amazon S3

S3 Standard is designed for 99.99% availability across at least three Availability Zones. One Zone-IA (99.5%) and S3 Express One Zone keep data in one AZ and lose it if that AZ is destroyed — use them only for data you can recreate.

S3 Replication copies objects to another bucket in the same Region (SRR) or another Region (CRR), keeping metadata and version IDs. Both buckets need versioning, and S3 needs an IAM role.

  • Existing objects are not replicated by a new rule; use S3 Batch Replication for them and for objects that failed.
  • Replication Time Control replicates "99.9 percent" of objects within 15 minutes, backed by an SLA, with metrics and missed-threshold events.
  • Not replicated: lifecycle actions (including lifecycle delete markers), version-ID deletes, objects in Glacier Flexible Retrieval or Deep Archive, and bucket settings. Delete markers replicate only if delete marker replication is enabled.
  • Replica modification sync copies tag, ACL and Object Lock changes back from the replica, for two-way setups. Multi-Region Access Points give one global endpoint that routes to the nearest bucket and supports failover.
repl.json: curated zone to the DR Region 
{
  "Role":
    "arn:aws:iam::111111111111:role/s3-repl",
  "Rules": [{
    "ID": "dr-curated",
    "Status": "Enabled",
    "Priority": 1,
    "Filter": {"Prefix": "curated/"},
    "DeleteMarkerReplication":
      {"Status": "Enabled"},
    "Destination": {
      "Bucket":
        "arn:aws:s3:::retail-lake-dr",
      "StorageClass": "STANDARD_IA",
      "ReplicationTime": {
        "Status": "Enabled",
        "Time": {"Minutes": 15}},
      "Metrics": {
        "Status": "Enabled",
        "EventThreshold": {"Minutes": 15}}
    }
  }]
}
Apply it 
aws s3api put-bucket-replication \
  --bucket retail-lake \
  --replication-configuration \
    file://repl.json

DynamoDB

  • Point-in-time recovery restores to any second in the recovery window, up to about five minutes ago. Since January 2025 the window is configurable from 1 to 35 days (default 35), but a shorter window does not lower the price. A restore always creates a new table, without the original's tags, TTL setting or stream.
  • On-demand backups are kept until you delete them. Copying DynamoDB backups to another Region or account needs AWS Backup's advanced DynamoDB features.
  • Global tables raise the availability SLA to 99.999%. The default mode (multi-Region eventual consistency) replicates "typically within a second" with last-writer-wins conflicts. Multi-Region strong consistency (GA June 2025) gives an RPO of zero across exactly three Regions, but no TTL, LSIs or transactions.
PITR with a two-week window, then a restore 
aws dynamodb update-continuous-backups \
  --table-name loyalty \
  --point-in-time-recovery-specification \
    '{"PointInTimeRecoveryEnabled": true,
      "RecoveryPeriodInDays": 14}'

aws dynamodb restore-table-to-point-in-time \
  --source-table-name loyalty \
  --target-table-name loyalty-restored \
  --restore-date-time 2026-11-07T08:00:00Z

Redshift

  • Automated snapshots are taken about every 8 hours or 5 GB per node of change, and kept 1 day by default (1–35). On RA3 and RG they cannot be disabled. Manual snapshots are kept until you delete them.
  • Cross-Region snapshot copy sends snapshots to one other Region; copied automated snapshots are kept 7 days by default. Redshift is in AWS Backup, but AWS Backup cannot copy Redshift backups across Regions or accounts, so use this native feature.
  • Serverless recovery points are created every 30 minutes and kept for 24 hours; take snapshots for anything longer.
  • Relocation moves a cluster to another AZ in the same Region, keeping its endpoint; Multi-AZ (Task 2.1) keeps it running through an AZ failure.

Streams, EMR and AWS Backup

  • Kinesis Data Streams "synchronously replicates data across three Availability Zones". MSK Replicator copies topics, configuration, ACLs and consumer offsets to another MSK cluster in the same account, in the same or another Region.
  • EMR clusters run in one AZ; keep durable data in S3 so a lost cluster costs only compute time.
  • AWS Backup centralizes backup plans, retention and cross-Region and cross-account copies for S3, DynamoDB, RDS, Aurora, Redshift, DocumentDB, Neptune and Timestream. A logically air-gapped vault adds built-in compliance locking and can be shared with a recovery account.

Key takeaways

  • COPY, not INSERT, for bulk loads. Split unsplittable files (JSON, gzip CSV) to 1 MB–1 GB compressed, in a multiple of the slice count; uncompressed CSV, Parquet and ORC of 128 MB or more split automatically. Use a manifest to load exactly the right files, and SYS_LOAD_ERROR_DETAIL to see errors on Serverless.
  • Parquet/ORC COPY maps by position, same Region only, no MAXERROR. COPY JOB auto-loads new files only (not existing ones), needs an S3 event integration and an explicit role. Upsert by staging and MERGE.
  • UNLOAD: Parquet is smaller and faster; PARTITION BY writes Hive folders but does not update the catalog; files cap at 6.2 GB; no HEADER with Parquet; CLEANPATH or ALLOWOVERWRITE if files exist. Pipelines call the Redshift Data API.
  • Storage class minimums: IA 30 days, Glacier Instant and Flexible 90, Deep Archive 180; IA classes bill at least 128 KB per object. Transitions only go colder, and objects under 128 KB do not transition by default (since September 2024). Up to 1,000 rules per bucket.
  • Restores: Flexible Retrieval Expedited 1–5 minutes, Standard 3–5 hours, Bulk 5–12; Deep Archive Standard within 12 hours, Bulk within 48, no Expedited. A restore is a temporary copy. Intelligent-Tiering suits unknown access patterns.
  • Expiration rounds up to the next midnight UTC and stops billing when eligible. In a versioned bucket it only adds a delete marker — add NoncurrentVersionExpiration. AbortIncompleteMultipartUpload is the only cleanup for orphaned parts, and it and ExpiredObjectDeleteMarker cannot use tag filters.
  • Versioning can be suspended but never removed, and every version is billed. MFA Delete is root-only, CLI-only and incompatible with lifecycle rules. Object Lock compliance mode cannot be bypassed by anyone; legal holds have no expiry.
  • DynamoDB TTL: epoch seconds in a Number attribute, deletes "within a few days" at no write cost, expired items still readable until then. TTL deletes show in Streams as Service / dynamodb.amazonaws.com — the hook to archive them. Strongly consistent global tables cannot use TTL.
  • Erasure must reach every copy: Iceberg DELETE plus snapshot expiry, rewrite jobs (S3 Find and Forget) for plain files, old versions, replicas, backups and logs. S3 Batch Operations cannot delete objects directly. Redshift reclaims deleted rows with (automatic) VACUUM DELETE ONLY.
  • Vault Lock compliance mode becomes immutable after a grace period of at least 72 hours. CloudWatch Logs never expire unless you set retention.
  • Resiliency: replication does not protect against bad data, so keep point-in-time backups. S3 replication skips existing objects (use Batch Replication), lifecycle actions and version-ID deletes; RTC covers 99.9% within 15 minutes.
  • DynamoDB PITR is 1–35 days and restores to a new table; global tables give 99.999%, with strong consistency in exactly three Regions. RDS Multi-AZ instance standbys cannot serve reads, Multi-AZ clusters have two readable standbys; Backtrack is Aurora MySQL only. Redshift automated snapshots keep 1 day by default, Serverless recovery points 24 hours; copy across Regions with native snapshot copy.
