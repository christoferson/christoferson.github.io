Extracting logs for audits

Skill 3.3.1Extract logs for audits.

An auditor asks a question — "who changed the orders table in October?" — and wants evidence. Extraction means knowing which log answers it, how far back that log goes, and how to hand over a copy.

QuestionLogHow far back
Who called an AWS API (dropped a table, changed a policy)?CloudTrail event history90 days, management events only, free
The same, older than 90 days, or object-level reads and writes?A CloudTrail trail delivering to S3As long as you keep the files
Who ran which SQL in Redshift?Redshift user activity logAs long as its S3 or CloudWatch retention
Who ran which Athena query?Athena query history; CloudTrail StartQueryExecutionHistory 45 days; CloudTrail for longer
Who read data governed by Lake Formation?CloudTrail GetDataAccess eventsTrail retention
What did the job print?CloudWatch LogsThe log group's retention (never expires by default)
Recent DeleteTable calls from event history 
aws cloudtrail lookup-events \
  --lookup-attributes '[{
    "AttributeKey": "EventName",
    "AttributeValue": "DeleteTable"}]' \
  --max-results 20

Handing logs to auditors

CloudTrail files are already in S3. For CloudWatch Logs, CreateExportTask copies a time range to an S3 bucket. It is a one-off tool: only one export task can be active per account per Region, data can take up to 12 hours to become exportable, and the bucket must be in the same Region (another account is allowed). AWS recommends subscription filters to Firehose for continuous archiving instead.

Export October's Redshift activity log 
aws logs create-export-task \
  --task-name rs-audit-2026-10 \
  --log-group-name \
    /aws/redshift/cluster/retail-dw/useractivitylog \
  --from 1790812800000 \
  --to 1793491200000 \
  --destination retail-audit-export \
  --destination-prefix redshift/2026-10

The --from and --to values are epoch milliseconds (October 1 and November 1, 2026, UTC). For tamper evidence, export into a bucket with S3 Object Lock; log file integrity validation is covered on Task 4.4.

Logging for traceability

Skill 3.3.2Deploy logging and monitoring solutions to facilitate auditing and traceability.

Much of the useful logging on a data platform is off by default. Traceability means switching it on before the incident, not after.

ServiceWhat to turn onWhere it goes
All servicesA multi-Region CloudTrail trail; data events for data buckets (off by default)S3, optionally CloudWatch Logs
Amazon RedshiftAudit logging (connection, user and user activity logs) — off by defaultS3 or CloudWatch Logs; Serverless to CloudWatch only
RDS and AuroraLog exports: audit, error, general, slow query (MySQL) or postgresqlCloudWatch Logs, /aws/rds/instance/<name>/<type>
AWS GlueOn by default for Glue 5.0+; continuous logging opt-in for 4.0 and earlier; Spark UI event logs/aws-glue/jobs/error and /aws-glue/jobs/output; event logs to S3
Amazon EMRA log URI (console clusters have it; CLI and API clusters need --log-uri)S3, with persistent application UIs for 30 days
Amazon S3CloudTrail data events (recommended) or server access logsS3 (access logs can now also go to CloudWatch Logs)
Lake FormationNothing extra: GetDataAccess is a CloudTrail eventThe trail

Redshift audit logging

The three audit logs are the connection log (logins and disconnections), the user log (user changes) and the user activity log (every query before it runs). The user activity log needs a second switch: the enable_user_activity_logging parameter, which defaults to false. With an S3 destination, the bucket must use SSE-S3 and must not have Object Lock; AWS calls CloudWatch Logs "a recommended alternative".

Audit logs to CloudWatch, including queries 
aws redshift enable-logging \
  --cluster-identifier retail-dw \
  --log-destination-type cloudwatch \
  --log-exports connectionlog \
    userlog useractivitylog

aws redshift \
  modify-cluster-parameter-group \
  --parameter-group-name retail-dw-pg \
  --parameters '[{
    "ParameterName":
      "enable_user_activity_logging",
    "ParameterValue": "true"}]'

S3 server access logs or CloudTrail data events?

AspectServer access logsCloudTrail data events
DeliveryBest effort: records may be late, duplicated or missingReliable, about every 5 minutes
ScopeWhole bucket onlyFilter by prefix, operation and more
CostStorage only$0.10 per 100,000 events
IntegrityNo validationLog file integrity validation
Unique contentAuthentication failures, lifecycle transitions and expirationsFull identity details, same format as all other API activity

AWS recommends CloudTrail for auditing. Server access logs remain useful for cheap traffic analysis and the few things only they record.

Glue and EMR logs

  • Glue 5.0 and later log in real time automatically: driver, executor and Glue logger output to /aws-glue/jobs/error, and stdout and stderr to /aws-glue/jobs/output. On Glue 4.0 and earlier, enable --enable-continuous-cloudwatch-log (log group /aws-glue/jobs/logs-v2).
  • Glue Spark UI: --enable-spark-ui writes Spark event logs to S3 every 30 seconds, viewable in the Glue console.
  • EMR keeps logs under /mnt/var/log/ on the nodes and archives them to the log URI. From EMR 6.9.0, logs are also archived when nodes scale down, so they survive node termination. Persistent application UIs (Spark History Server, YARN timeline, Tez UI) are available off-cluster for 30 days after an application ends.

An EMR cluster created with the CLI or API without --log-uri has no S3 logs. When it terminates, its step and container logs are gone. Always set a log URI in templates.

Alerts

Skill 3.3.3Use notifications during monitoring to send alerts.

SNS topics, filter policies and pipeline events worth alerting on are covered on Task 1.3. Here are the CloudWatch alarm mechanics that decide whether an alert fires at the right time.

Alarm behaviour

  • States are OK, ALARM and INSUFFICIENT_DATA. Actions run on a state change, not repeatedly while in alarm.
  • Actions can notify SNS, invoke a Lambda function directly, create a Systems Manager OpsItem, start a CloudWatch investigation, or act on EC2 and Auto Scaling.
  • "M out of N": --datapoints-to-alarm (M) of --evaluation-periods (N) must breach, which stops a single spike paging someone.
  • Missing data is treated as missing by default. For a metric that is only published when something goes wrong — such as an error count from a metric filter — use notBreaching, or the alarm sits in INSUFFICIENT_DATA. The other options are breaching and ignore.
Alarm on Glue job errors from logs 
aws cloudwatch put-metric-alarm \
  --alarm-name etl-errors \
  --namespace DataPlatform \
  --metric-name EtlErrorCount \
  --statistic Sum --period 300 \
  --evaluation-periods 3 \
  --datapoints-to-alarm 2 \
  --threshold 1 \
  --comparison-operator \
    GreaterThanOrEqualToThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions "$OPS_TOPIC_ARN"

The metric comes from a log metric filter (CloudWatch Logs). Newer log alarms skip the filter: they run a Logs Insights query on a schedule and alarm on its result.

Reducing noise

A composite alarm combines other alarms with AND, OR and NOT, so on-call is paged once for a real problem rather than for every symptom. Composite alarms can notify and invoke Lambda but cannot take EC2 or Auto Scaling actions. Metric math alarms alarm on a formula, such as failed runs divided by total runs.

Page only when errors and lateness coincide 
aws cloudwatch put-composite-alarm \
  --alarm-name etl-degraded \
  --alarm-rule file://rule.txt \
  --alarm-actions "$OPS_TOPIC_ARN"
rule.txt 
ALARM("etl-errors") AND ALARM("etl-late")

Service-specific notifications

  • Glue: a job's delay notification threshold (NotifyDelayAfter, in minutes) emits an event when a run takes longer than expected — an early warning before the timeout.
  • Redshift event subscriptions send cluster events (configuration, management, monitoring, security) to SNS, filtered by severity. Monitoring events include problems writing audit logs to S3.
  • EventBridge rules on Glue, EMR, Athena and Step Functions state-change events route failures to SNS (Task 3.1).
  • AWS User Notifications gives one console for configuring notifications from EventBridge-based sources, including CloudWatch alarms, to email, chat and the AWS Console Mobile App.

Performance issues

Skill 3.3.4Troubleshoot performance issues.

The engine-level causes — Glue memory and shuffle, Spark skew, YARN memory, Athena failure modes — are on Task 1.2. This section is about finding the slow part with each service's monitoring tools. The first question is always the same: is the query or job waiting, or working?

Amazon Redshift

SYS_QUERY_HISTORY works on provisioned clusters and Serverless and splits each query's time into queue, planning, execution and lock wait. A long queue_time means not enough capacity or the wrong WLM queue; a long execution_time means the query or table design.

The slowest queries of the last hour 
SELECT query_id, status,
  queue_time / 1000000 AS queue_s,
  execution_time / 1000000 AS exec_s,
  compute_type
FROM sys_query_history
WHERE start_time >
      DATEADD(hour, -1, GETDATE())
ORDER BY execution_time DESC
LIMIT 10;
  • STL_ALERT_EVENT_LOG (provisioned only) flags known problems with a suggested fix: missing statistics, nested loop joins, large broadcasts or redistribution, and scans of deleted ("ghost") rows.
  • Workload management: automatic WLM with query priorities is the default; short query acceleration lets short queries skip the queue, and concurrency scaling adds capacity for bursts (compute_type shows when it was used).
  • Query monitoring rules act on runaway queries: up to 25 rules, each with up to three predicates. Actions are log, hop (manual WLM only), abort, or change priority (automatic WLM only), recorded in STL_WLM_RULE_ACTION. Serverless now supports queues and rules too.
  • Redshift Advisor recommends distribution keys, sort keys and compression from your workload.
QMR rules inside a WLM queue 
"rules": [
  {"rule_name": "abort_runaway",
   "predicate": [{
     "metric_name":
       "query_execution_time",
     "operator": ">",
     "value": 3600}],
   "action": "abort"},
  {"rule_name": "log_nested_loop",
   "predicate": [{
     "metric_name":
       "nested_loop_join_row_count",
     "operator": ">",
     "value": 100}],
   "action": "log"}
]

Amazon Athena

Each query's Query stats show rows and bytes read and a runtime split into queuing, planning, execution and service processing; Execution details shows the stage graph and operators. High queuing points to concurrency quotas (or the case for capacity reservations); high planning time often points to too many partitions or files; high data scanned points to missing partition filters or row-based formats.

Amazon EMR

EMR publishes free CloudWatch metrics every 5 minutes. The ones that diagnose most problems:

MetricTells you
YARNMemoryAvailablePercentage, ContainerPendingRatioWhether the cluster is short of capacity (scaling signals)
AppsPendingApplications waiting for resources
HDFSUtilization, CapacityRemainingGBWhether HDFS is filling up
MRUnhealthyNodes, MRLostNodesNodes failing, often because a local disk is full
IsIdleA cluster doing nothing — alarm on 30 minutes or more, not one data point

Managed scaling adjusts capacity from these signals; its own metrics show units requested versus running.

Dashboards

A CloudWatch dashboard per pipeline — Glue job duration and failures, Redshift queue time, Athena data scanned, EMR pending containers — gives the first place to look. Anomaly detection alarms learn a metric's normal band and alert when it leaves it, which suits job durations that vary by day of week.

AWS CloudTrail

Skill 3.3.5Use AWS CloudTrail to track API calls.

CloudTrail records API calls made in your account: who (userIdentity), what (eventSource and eventName), when (eventTime, UTC), from where (sourceIPAddress, vpcEndpointId), with which parameters (requestParameters), and whether it failed (errorCode).

Event history and trails

  • Event history shows the last 90 days of management events in each Region, free and with no setup.
  • A trail delivers events to S3 (about every 5 minutes, not guaranteed), and optionally to CloudWatch Logs and EventBridge. The console creates multi-Region trails; the CLI and API default to a single-Region trail.
  • The first copy of management events on a trail is free; additional copies cost $2.00 per 100,000 events.

Event categories

CategoryRecordsDefault
Management eventsControl-plane calls: CreateTable, DeleteTable, PutBucketPolicy, StartQueryExecutionLogged
Data eventsHigh-volume data-plane calls: S3 GetObject and DeleteObject, Lambda Invoke, DynamoDB item operations, Kinesis records, Redshift Data API, and moreOff; $0.10 per 100,000
Network activity eventsAPI calls through VPC endpoints, including those denied by an endpoint policy (VpceAccessDenied)Off
Insights eventsUnusual API call rates or error ratesOff; $0.35 per 100,000 management events analyzed

"Who deleted this S3 object?" can be answered only if data events were enabled for that bucket when it happened — DeleteObject is a data event, while DeleteBucket and DeleteTable are management events. Athena has no data event type: its queries are management events.

Scoping data events

Advanced event selectors log only what you need — one bucket prefix, only writes — which is how you keep data events affordable. Fields include eventCategory, resources.type, resources.ARN, eventName and readOnly, with Equals, StartsWith and EndsWith operators (no wildcards). Applying advanced selectors replaces a trail's existing selectors.

Log writes to the raw zone only 
aws cloudtrail put-event-selectors \
  --trail-name retail-audit \
  --advanced-event-selectors \
    file://selectors.json
selectors.json 
[{
  "Name": "RawZoneWrites",
  "FieldSelectors": [
    {"Field": "eventCategory",
     "Equals": ["Data"]},
    {"Field": "resources.type",
     "Equals": ["AWS::S3::Object"]},
    {"Field": "readOnly",
     "Equals": ["false"]},
    {"Field": "resources.ARN",
     "StartsWith": [
       "arn:aws:s3:::retail-lake/raw/"]}
  ]
}]

Never log S3 data events on the bucket that receives the trail's own log files: each delivery is an S3 write, which is logged, which is delivered — a loop that grows your bill. Exclude that bucket or keep logs in another account.

  • Insights events learn a baseline and flag spikes, such as a sudden burst of DeleteObject calls or AccessDenied errors. The first Insights events can take up to 36 hours to appear.
  • CloudTrail Lake (SQL over events) closed to new customers on May 31, 2026; see Task 4.4.

Maintaining Glue and EMR

Skill 3.3.6Troubleshoot and maintain pipelines (for example, AWS Glue, Amazon EMR).

Common Glue failures

Error or symptomCause and fix
ConcurrentRunsExceededExceptionThe job's maximum concurrency (default 1) is reached. Raise it, or enable job run queuing
"Resource unavailable"The subnet has run out of IP addresses or ENIs for Glue workers
"Could not find S3 endpoint or NAT gateway for subnetId"A job in a VPC needs an S3 gateway endpoint (or NAT) to reach S3
JDBC connection timeoutThe connection's security group lacks a self-referencing rule, or the subnet has no route to the database
Job reprocesses all data, or noneBookmark problems: missing job.commit() or transformation_ctx, or concurrency above 1
Run never endsSet a realistic timeout: the default is 480 minutes on Glue 5.0+ (2,880 on older versions), maximum 7 days. Timed-out runs are not retried

To reprocess data on purpose, reset the bookmark, either fully or back to a given run:

Start the next run from scratch 
aws glue reset-job-bookmark \
  --job-name orders-etl

Keeping Glue current

  • Glue 0.9, 1.0 and 2.0 reached end of life on April 1, 2026: their jobs no longer start. Glue 5.1 is the default for new jobs, and Glue 6.0 is available.
  • Spark upgrades with generative AI analyze a PySpark job, propose code changes for a newer Glue version and validate them with test runs in your account (billed as normal runs). Expect several failed validation runs, so silence failure alarms during an upgrade.
  • Glue crawlers log to /aws-glue/crawlers.

EMR: finding why a step failed

  1. describe-step returns FailureDetails with a reason, a message and the log file location.
  2. Read the step's stderr and controller logs under <log-uri>/<cluster-id>/steps/<step-id>/.
  3. For Spark failures, open the persistent Spark History Server and the YARN container logs under containers/.
Why did the step fail, and where are its logs? 
aws emr describe-step \
  --cluster-id j-3SD91U2E1L2QX \
  --step-id s-3LZC0QUT43AM \
  --query 'Step.Status.FailureDetails'

aws s3 ls \
  s3://retail-logs/j-3SD91U2E1L2QX/steps/s-3LZC0QUT43AM/

AWS Systems Manager runbooks such as AWSSupport-AnalyzeEMRLogs scan EMR logs for known errors.

Keeping EMR current

EMR releases get 24 months of standard support, then 12 months of end of support, then end of life. Releases 5.35 and earlier and 6.5 and earlier reached end of support on September 1, 2026. Plan release upgrades as routine maintenance; AWS offers a Spark upgrade agent for EMR as well.

CloudWatch Logs

Skill 3.3.7Use Amazon CloudWatch Logs to log application data (with a focus on configuration and automation).

Logs are organized as log groups (one per application or job) containing log streams (one per source, such as a job run or instance). Configuration lives on the log group, so automating it means managing log groups as code.

Log group settings

SettingKnow this
RetentionNever expire by default; 1 day to 10 years. Account-level policies can set retention for all groups or a name prefix
EncryptionAlways encrypted; add a KMS key per log group for control (the key policy must allow the CloudWatch Logs service)
Log classStandard, or the cheaper Essentials (formerly Infrequent Access), which lacks metric filters, subscription filters, Live Tail, anomaly detection and EMF. The class cannot be changed later
Deletion protectionNew: blocks accidental deletion of a log group; off by default
Data protection policyDetects and masks sensitive data (such as card numbers) in log events; viewing unmasked data needs logs:Unmask

Metric filters

A metric filter turns matching log events into a CloudWatch metric that you can alarm on (Alerts). Up to 100 per log group; it sees only events ingested after it was created. JSON patterns look like { $.level = "ERROR" } or { $.latency_ms > 500 }.

Count ERROR lines from the ETL job 
aws logs put-metric-filter \
  --log-group-name /app/orders-etl \
  --filter-name EtlErrors \
  --filter-pattern \
    '{ $.level = "ERROR" }' \
  --metric-transformations \
    file://transform.json
transform.json 
[{
  "metricName": "EtlErrorCount",
  "metricNamespace": "DataPlatform",
  "metricValue": "1",
  "defaultValue": 0
}]

Subscription filters

A subscription filter streams matching events in near real time (usually under 3 minutes, at least once) to Kinesis Data Streams, Firehose or Lambda, and through Lambda to OpenSearch. A log group can now have up to 5, plus one account-level subscription filter per Region. Firehose to S3 is the standard way to archive logs continuously.

Archive everything through Firehose 
aws logs put-subscription-filter \
  --log-group-name /app/orders-etl \
  --filter-name to-archive \
  --filter-pattern "" \
  --destination-arn "$FIREHOSE_ARN" \
  --role-arn "$CWL_FIREHOSE_ROLE_ARN"

Getting logs in, and as code

  • AWS services (Lambda, Glue, RDS, Redshift, EMR on EKS, Step Functions) write to CloudWatch Logs natively once enabled.
  • The unified CloudWatch agent collects logs and metrics from EC2 instances and on-premises servers.
  • Embedded Metric Format lets an application write structured JSON logs from which CloudWatch extracts metrics, with no separate metric API calls.
CloudFormation: log group and error metric 
EtlLogGroup:
  Type: AWS::Logs::LogGroup
  Properties:
    LogGroupName: /app/orders-etl
    RetentionInDays: 90
    KmsKeyId: !GetAtt LogKey.Arn
    DeletionProtectionEnabled: true

EtlErrorFilter:
  Type: AWS::Logs::MetricFilter
  Properties:
    LogGroupName: !Ref EtlLogGroup
    FilterPattern: >-
      { $.level = "ERROR" }
    MetricTransformations:
      - MetricName: EtlErrorCount
        MetricNamespace: DataPlatform
        MetricValue: "1"
        DefaultValue: 0

Define log groups in your templates before the job first runs. Otherwise the service creates the group on first write with no retention (never expire) and no KMS key, and logs accumulate cost forever.

Watching logs

  • Live Tail streams new events interactively while you debug.
  • Anomaly detection learns a log group's normal patterns over two weeks and surfaces unusual ones, at no charge to create detectors.
  • Field indexes speed up and cheapen Logs Insights queries on fields you filter often.
  • Cross-account observability lets a monitoring account query log groups in source accounts.

Pricing is per GB ingested (Essentials about half of Standard), per GB-month stored, and per GB scanned by Logs Insights.

CloudWatch Logs Insights

Queries are pipelines of commands: fields, filter, parse, stats ... by bin(5m), sort and limit. A query can cover up to 50 named log groups (more by prefix), runs for up to 60 minutes, and its results are kept for 7 days. It is billed per GB scanned, so narrow the time range. Logs Insights also accepts OpenSearch PPL and SQL.

Errors per 5 minutes in the job's log group 
fields @timestamp, @message
| filter @message like /ERROR/
| stats count(*) as errors by bin(5m)
Latency percentiles from text logs 
parse @message /latency_ms=(?<lat>\d+)/
| stats avg(lat), pct(lat, 95), max(lat)
  by bin(5m)

Athena over CloudTrail and S3 logs

AWS documents ready-made Athena tables for CloudTrail and S3 server access logs that use partition projection on the date in the S3 path, so new days need no partition maintenance (Task 2.2). With a CloudTrail table defined, the auditor's question becomes SQL:

Who deleted Glue tables in October? 
SELECT eventtime,
  useridentity.arn AS who,
  sourceipaddress,
  json_extract_scalar(requestparameters,
    '$.databaseName') AS db,
  json_extract_scalar(requestparameters,
    '$.name') AS tbl
FROM cloudtrail_logs
WHERE eventsource = 'glue.amazonaws.com'
  AND eventname = 'DeleteTable'
  AND "timestamp" >= '2026/10/01'
ORDER BY eventtime DESC;

OpenSearch Service

  • OpenSearch Ingestion is a managed pipeline (based on Data Prepper) that receives, transforms and buffers log data into OpenSearch, billed per ingestion OCU.
  • OpenSearch Dashboards gives search, visualizations and alerting.
  • Direct query analyzes data in S3 and in CloudWatch Logs from OpenSearch without ingesting it first.
  • Older log indexes move to UltraWarm and cold storage through Index State Management policies, cutting cost for retained logs.

Big data application logs

Spark and Hadoop produce their own logs: Spark event logs (replayed by the Spark History Server), YARN container logs (stdout and stderr of each executor), and the driver log. Glue shows the Spark UI in its console for current versions; for older event logs you can run a Spark History Server yourself from AWS's CloudFormation template or Docker image. On EMR, persistent application UIs and the S3 log URI hold the same information after a cluster is gone.

Key takeaways

  • CloudTrail event history covers 90 days of management events only; anything older or object-level needs a trail. Athena keeps query history 45 days. CreateExportTask allows one active export per account and Region; use subscription filters to Firehose for continuous archives.
  • Turn logging on in advance: CloudTrail data events, Redshift audit logs (plus enable_user_activity_logging for queries; Serverless logs to CloudWatch only), RDS log exports, an EMR log URI (CLI clusters have none by default). Glue 5.0+ logs to /aws-glue/jobs/error and /output automatically.
  • S3 server access logs are best effort and bucket-wide; AWS recommends CloudTrail data events for audit. Lake Formation data access appears as GetDataAccess in CloudTrail.
  • Alarms act on state changes; use M-of-N datapoints, and notBreaching for metrics published only on errors (the default is missing). Composite alarms cut noise; alarms can invoke Lambda directly; Glue's NotifyDelayAfter warns of slow runs.
  • Performance: Redshift SYS_QUERY_HISTORY (queue versus execution), STL_ALERT_EVENT_LOG, QMR actions log, hop (manual WLM), abort, change priority (auto WLM); Athena query stats split queuing, planning and execution; EMR YARNMemoryAvailablePercentage, AppsPending, MRUnhealthyNodes.
  • CloudTrail: management events logged by default, data events off and charged ($0.10 per 100,000) — scope them with advanced selectors. Console trails are multi-Region; CLI trails default to one Region. Athena has no data events; S3 DeleteObject does. Do not log data events on the trail's own bucket.
  • Glue maintenance: ConcurrentRunsExceededException (raise concurrency or queue runs), IP exhaustion, missing S3 endpoints, bookmark resets; Glue 2.0 and older are end of life. EMR: describe-step then steps/<id>/stderr; releases 5.35 and 6.5 and older are past end of support.
  • CloudWatch Logs: retention never expires by default; the log class is fixed at creation; up to 100 metric filters and 5 subscription filters per log group; data protection masks sensitive values. Create log groups in templates with retention and KMS before first use.
  • Analysis: Logs Insights for recent CloudWatch logs (50 log groups, 60-minute timeout, billed per GB scanned); Athena with partition projection for CloudTrail and S3 logs; OpenSearch for search and dashboards; EMR Spark for huge volumes; Spark History Server and YARN logs for application debugging.
