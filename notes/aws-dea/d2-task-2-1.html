Cost and performance

Skill 2.1.1Implement the appropriate storage services for specific cost and performance requirements (for example, Amazon Redshift, Amazon EMR, AWS Lake Formation, Amazon RDS, Amazon DynamoDB, Amazon Kinesis Data Streams, Amazon Managed Streaming for Apache Kafka [Amazon MSK]).

Start from the shape of the work. Analytics (big scans, aggregates, joins over history) belongs in Redshift or in S3 queried by Athena, EMR or Redshift. Transactions (small reads and writes by key, many at once) belong in RDS, Aurora or DynamoDB. Streams (an ordered, replayable buffer of events) belong in Kinesis Data Streams or MSK. Cost and speed tuning happens inside each choice.

AWS publishes two decision guides worth reading once: Choosing an AWS database service, which is OLTP-focused and sends OLAP to Redshift, and Choosing an AWS analytics service.

Amazon Redshift

Redshift comes as provisioned clusters or Redshift Serverless. On provisioned clusters, compute and storage are separate: you pay per node-hour, and data lives in Redshift managed storage (RMS), billed per GB-month at one rate whether the data sits on local SSD or in S3.

OptionPick it whenDetail
RG nodesSteady workloads on a new provisioned clusterThe newer Graviton-based family (rg.large to rg.12xlarge). AWS now says choose "RG or RA3". RG runs data lake queries on the cluster's own compute, so there is no separate Spectrum charge
RA3 nodesExisting clusters, or where RG is not offeredra3.large, ra3.xlplus, ra3.4xlarge, ra3.16xlarge. Data lake queries go through Redshift Spectrum at $5 per TB scanned
ServerlessSpiky, unpredictable or intermittent useBilled per RPU-hour, per second with a 60-second minimum. Base capacity defaults to 128 RPU and can be set to 4, or 8 to 512 in steps of 8 (up to 1,024 in five large Regions). Data lake queries carry no separate charge

DC2 nodes are gone. The Redshift documentation history for November 2, 2026 says "DC2 node types are no longer available", and DC2 has been removed from the node-type pages. An answer that offers dense-compute nodes as the cheap option is out of date — the current choices are RG, RA3 or Serverless.

Two Redshift cost levers turn up often. Multi-AZ (RG or RA3 only) runs compute in two Availability Zones behind one endpoint and doubles compute cost but not storage. Small base capacity limits how much data a Serverless workgroup can hold: 4 RPU supports up to 32 TB of managed storage, 8–24 RPU up to 128 TB, and more than that needs at least 32 RPU.

Serverless workgroup with a small base 
aws redshift-serverless create-workgroup \
  --workgroup-name retail-adhoc \
  --namespace-name retail \
  # 32 RPU instead of the default 128
  --base-capacity 32

Amazon EMR

EMR runs open-source engines (Spark, Hive, Trino, HBase) on three platforms: EMR on EC2 for full control and long-running clusters, EMR on EKS when you already run Kubernetes, and EMR Serverless when you want no cluster at all. The storage question inside EMR is HDFS versus S3.

  • HDFS on the cluster's disks is fast but ephemeral: it disappears when the cluster ends. AWS recommends it for intermediate results between steps.
  • S3 separates storage from compute, so clusters can be transient — start, process, terminate — which is the main EMR cost saving.
  • Spot belongs on task nodes, which hold no HDFS data. Spot on core nodes risks HDFS data loss, and losing the primary node ends the cluster. The data-safe pattern is On-Demand primary and core, Spot task nodes; instance fleets mix the two with a target capacity per fleet.
  • EMR Serverless pre-initialized capacity (initialCapacity) keeps warm drivers and workers so jobs start in seconds — but you pay for them while idle. Auto-stop releases them after 15 minutes idle by default.

From EMR 7.10.0, s3:// paths use the open-source S3A connector instead of EMRFS. Older study material that ties every EMR S3 feature to "EMRFS" describes earlier releases.

Amazon RDS and Aurora

RDS storage choices are gp3 (3,000 IOPS and 125 MiB/s baseline below 400 GiB; from 400 GiB the baseline is 12,000 IOPS and 500 MiB/s) and io2 Block Express (up to 256,000 IOPS, sub-millisecond latency) for I/O-bound databases. Magnetic storage is deprecated, and from July 1, 2026 you cannot restore a snapshot to it.

Aurora has its own two cost levers:

LeverRule
Aurora I/O-OptimizedNo per-I/O charges; AWS says it is "the best choice when your I/O spending is 25% or more of your total Aurora database spending". You can switch to it once every 30 days and back to Standard at any time
Aurora ServerlessCapacity in ACUs (about 2 GiB of memory each), 0–256 ACU for MySQL and up to 384 for recent PostgreSQL versions. A minimum of 0 ACU lets the instance auto-pause when idle, after 300 seconds by default; resuming takes about 15 seconds. Compute is free while paused, storage is not

Some features stop auto-pause. An instance connected to RDS Proxy, the writer of a global database, or the source of a zero-ETL integration never pauses at 0 ACU. If a dev database "never scales to zero", look for one of those three.

Switch the orders cluster to I/O-Optimized 
aws rds modify-db-cluster \
  --db-cluster-identifier retail-orders \
  --storage-type aurora-iopt1 \
  --apply-immediately
Let a dev cluster pause when idle 
aws rds modify-db-cluster \
  --db-cluster-identifier orders-dev \
  --serverless-v2-scaling-configuration \
    MinCapacity=0,MaxCapacity=8

Amazon DynamoDB

  • On-demand is now "the default and recommended throughput option". On-demand throughput prices fell 50% from November 1, 2024, which removed much of the old reason to run provisioned capacity.
  • Provisioned with auto scaling still wins for steady, predictable traffic. You can switch from provisioned to on-demand up to four times in a rolling 24 hours, and back at any time.
  • Standard-IA table class lowers storage price for the same performance; AWS says it helps "when storage exceeds 50% of the throughput (reads and writes) cost". You can change class twice in 30 days.
  • Item size is capped at 400 KB, attribute names included. Large payloads go to S3 with a pointer in the item.
  • Warm throughput shows how much traffic a table can absorb instantly. Raising it (pre-warming) before a sale is charged and cannot be lowered later.

Kinesis, MSK and Lake Formation as storage

Streams store data, but only for a while. Kinesis Data Streams keeps records for 24 hours by default and up to 8,760 hours (365 days), with extra charges beyond 24 hours. MSK retention is a Kafka topic setting, with tiered storage for cheaper long retention (see replayability on Task 1.1). Neither replaces a data lake — they are replay buffers.

Keep clickstream for three days 
aws kinesis increase-stream-retention-period \
  --stream-name retail-clickstream \
  --retention-period-hours 72

Lake Formation is not a store at all. It is a governance layer that adds fine-grained permissions over S3 data cataloged in the Glue Data Catalog. Permissions and sharing are free; you pay for the underlying S3 and Glue usage. In a "cheapest durable store with fine-grained access" question, the answer is usually S3 plus Lake Formation.

A quick map for scenario questions: petabyte SQL analytics → Redshift (Serverless if spiky); open-source Spark at scale with custom tuning → EMR with Spot task nodes and S3; relational transactions → Aurora (I/O-Optimized at ≥25% I/O spend); key-value at any scale with single-digit-millisecond latency → DynamoDB on-demand; replayable event buffer → Kinesis or MSK; cheapest durable governed lake → S3 + Lake Formation.

Access patterns

Skill 2.1.2Configure the appropriate storage services for specific access patterns and requirements (for example, Amazon Redshift, Amazon EMR, Lake Formation, Amazon RDS, DynamoDB).

Skill 2.1.1 picks the store; this skill sets it up for the queries it will actually serve. The same data can be fast or slow depending on how it is laid out.

Redshift: distribution and sort keys

Redshift spreads each table's rows across node slices. The distribution style decides which slice gets which row, and therefore how much data moves between nodes during a join.

StyleWhat it doesUse for
AUTOThe default when you specify nothing. Starts small tables as ALL, may switch to KEY as they grow, falls back to EVENMost tables; let Redshift decide
KEYRows with the same value in the key column go to the same sliceLarge tables joined on that column, so matching rows sit together
ALLA full copy on every nodeSlow-changing dimension tables; AWS notes there "isn't a significant benefit" for small dimensions
EVENRound-robin across slicesTables that are not joined

The sort key orders rows on disk so Redshift can skip blocks whose min/max values fall outside a filter. AWS recommends SORTKEY AUTO. A compound key (the default type) works best when queries filter on its leading column and for tables updated regularly; an interleaved key weights up to eight columns equally but makes VACUUM REINDEX slower. Redshift can also apply multidimensional data layout sorting, an AUTO sort key built from the predicates your workload repeats.

Sales fact table, joined by store 
CREATE TABLE sales (
  order_id  BIGINT,
  store_id  INT,
  sold_at   TIMESTAMP,
  amount    DECIMAL(12,2)
)
-- colocate rows joined on store_id
DISTSTYLE KEY DISTKEY (store_id)
-- most queries filter by date
SORTKEY (sold_at);

Two more Redshift features shape access. Data sharing gives other clusters, workgroups, accounts or Regions live access to the same data without copies — the consumer pays for its own compute, and writes through a share are now supported as well as reads. Multi-AZ provisioned clusters run in two Availability Zones with an RPO of zero.

RDS and Aurora: read scaling

  • RDS read replicas are asynchronous and you create them yourself; RDS does not add them automatically. MySQL and MariaDB replicas can be made writable; PostgreSQL, Oracle, SQL Server and Db2 replicas cannot.
  • Aurora replicas share the cluster volume, so they add read capacity without copying data — up to 15 readers across three Availability Zones, behind a reader endpoint.
  • RDS Proxy pools connections, which matters when many short-lived Lambda functions hit one database.

Read-heavy reporting against an OLTP database is a classic scenario. The answer is a read replica or Aurora reader endpoint for the reports, so the writer keeps serving orders. If the reports are really analytics over history, the better answer is moving them to Redshift through zero-ETL (see remote access).

DynamoDB: keys and indexes

DynamoDB is fast only for the access patterns you design for. The partition key spreads data and load (pick a high-cardinality value), and the optional sort key orders items inside a partition for range queries. Every other query pattern needs an index.

IndexRules
Local secondary index (LSI)Same partition key, different sort key. Only at table creation, maximum 5, allows strongly consistent reads, and limits each partition key value to 10 GB
Global secondary index (GSI)Any partition and sort key. Can be added later, 20 per table by default, eventually consistent reads only, its own throughput

Read cost depends on consistency: one RCU buys one strongly consistent or two eventually consistent reads per second of up to 4 KB, and transactional reads and writes cost double. DAX adds an in-memory cache in front of the table for microsecond reads.

    {"AttributeName": "pk",
     "AttributeType": "S"},
    {"AttributeName": "sk",
     "AttributeType": "S"},
    {"AttributeName": "tier",
     "AttributeType": "S"}
  ],

    {"AttributeName": "pk",
     "KeyType": "HASH"},
    {"AttributeName": "sk",
     "KeyType": "RANGE"}

EMR and Lake Formation

On EMR, configure storage by access pattern: HDFS for scratch data that steps re-read many times, S3 for anything that must outlive the cluster or be read by other services. HDFS replication defaults to 3 with ten or more core nodes, 2 with four to nine, and 1 with three or fewer — so a tiny cluster has no HDFS redundancy at all.

For Lake Formation, the access-pattern question is who reads, not how fast: register the S3 location, then grant database, table, column or row access to each consumer. The grant model itself is covered in Domain 4.

Purpose-built use cases

Skill 2.1.3Apply storage services to appropriate use cases (for example, using indexing algorithms like Hierarchical Navigable Small Worlds [HNSW] with Amazon Aurora PostgreSQL and using Amazon MemoryDB for fast key/value pair access).

The two examples in the skill point to the same idea: AWS has a purpose-built store for most data shapes, and the exam expects you to know when the specialist beats the general-purpose choice.

Vector search in Aurora PostgreSQL

Aurora PostgreSQL and RDS for PostgreSQL support the open-source pgvector extension, which adds a vector column type, distance operators and approximate nearest-neighbour indexes (HNSW and IVFFlat, compared in vector index types). The use case is similarity search next to relational data: the retail platform keeps product embeddings in the same database as the product catalog, so one SQL query can filter by category and rank by similarity.

Product embeddings with an HNSW index 
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE product_embeddings (
  sku        TEXT PRIMARY KEY,
  category   TEXT,
  embedding  vector(1024)
);

-- cosine distance, pgvector defaults
CREATE INDEX ON product_embeddings
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
"More like this", within a category 
SELECT sku
FROM product_embeddings
WHERE category = 'shoes'
-- <=> is cosine distance
ORDER BY embedding <=> $1
LIMIT 5;
  • The latest Aurora PostgreSQL minor versions ship pgvector 0.8.2. An engine upgrade does not upgrade the extension; run ALTER EXTENSION vector UPDATE;.
  • Using Aurora as a Bedrock knowledge base vector store needs pgvector 0.5.0 or later, the release that added HNSW.
  • Aurora Optimized Reads on NVMe instance classes (R6gd, R8gd, R6id) adds a tiered cache up to five times instance memory, and AWS names pgvector search over millions of embeddings as a use case. The tiered cache works only on I/O-Optimized clusters; on Standard clusters you get faster temporary objects only.

Choose pgvector on Aurora when the team already runs PostgreSQL, the vectors must join with relational rows, and the scale is millions rather than billions. For billions of rarely queried vectors at the lowest cost, look at S3 Vectors; for heavy hybrid text-and-vector search, OpenSearch.

MemoryDB for fast key-value access

Amazon MemoryDB is an in-memory database compatible with Valkey and Redis OSS that gives microsecond reads and single-digit-millisecond writes. What sets it apart from a cache is durability: every write goes to a Multi-AZ transaction log before it is acknowledged, so MemoryDB can be the primary database rather than a copy of one.

NeedPick
Durable primary store at in-memory speedMemoryDB
Cache in front of another database, data can be rebuiltElastiCache (Valkey, Memcached or Redis OSS)
Microsecond cache in front of DynamoDB, same APIDAX
Single-digit milliseconds at any scale, not in memoryDynamoDB

MemoryDB for Valkey (October 2024) is priced 30% below MemoryDB for Redis OSS, and data written is free up to 10 TB a month. MemoryDB also has vector search with FLAT and HNSW indexes for the lowest-latency similarity lookups.

Shopping carts in MemoryDB (Python) 
from redis.cluster import RedisCluster

# MemoryDB is always cluster mode, TLS on
r = RedisCluster(
    host=ENDPOINT, port=6379, ssl=True)

key = "cart:s-81f2"
r.hset(key, "SKU-1001", 2)
# drop abandoned carts after a day
r.expire(key, 86400)
print(r.hgetall(key))

Migration tools

Skill 2.1.4Integrate migration tools into data processing systems (for example, AWS Transfer Family).

"Integrate" is the key word: the exam cares less about running a one-off migration than about wiring the tool so that arriving data starts processing automatically.

AWS Transfer Family

Transfer Family is a managed file-transfer server for partners who can only speak file protocols. The retail platform's suppliers upload nightly inventory files by SFTP, and the files land straight in S3.

SettingOptions
ProtocolsSFTP, FTPS, FTP, AS2, plus browser-based web apps (S3 only)
StorageS3 or EFS, chosen at creation and not changeable later. AS2 requires S3
Identity providerSERVICE_MANAGED (SSH keys stored in the service), AWS_DIRECTORY_SERVICE, AWS_LAMBDA, API_GATEWAY
EndpointPUBLIC, or VPC (internal, or internet-facing with Elastic IPs — the way to give partners a fixed IP to allowlist)
OutboundSFTP connectors make Transfer Family the client, pulling from or pushing to a partner's SFTP server

FTP and FTPS need a VPC endpoint and a non-service-managed identity provider (Directory Service, Lambda or API Gateway); FTPS also needs an ACM certificate. Plain FTP cannot be internet-facing at all. A question that pairs FTP with "service-managed users on a public endpoint" describes something you cannot build.

Pricing is $0.30 per protocol per hour while the server exists, plus $0.04 per GB transferred. A server with SFTP and FTPS enabled pays for two protocols around the clock, so stop or delete servers you do not need.

Starting processing when a file arrives

There are three ways to trigger the pipeline from an upload:

  1. Managed workflows run after an SFTP, FTPS or FTP upload, with steps to copy, tag, delete, decrypt (PGP) or call a custom Lambda step. Limits: 10 workflows per Region, 8 steps, 30 minutes per custom step. Workflows do not fire for 0-byte files or AS2 messages.
  2. EventBridge: Transfer Family sends events such as SFTP Server File Upload Completed to the default bus automatically. Server events are best-effort; connector and AS2 events are durable.
  3. S3 Event Notifications on the landing bucket, which see the object regardless of how it arrived.
SFTP server with a post-upload workflow 
aws transfer create-server \
  --protocols SFTP \
  --identity-provider-type \
    SERVICE_MANAGED \
  --endpoint-type PUBLIC \
  --domain S3 \
  --workflow-details file://wf.json

Federated queries

A federated query reads live tables in Aurora or RDS for PostgreSQL and MySQL through an external schema. Redshift's compute nodes send subqueries to the source and push predicates down, so filters run at the source. The source must be reachable from the cluster's VPC, and credentials come from Secrets Manager.

Live orders from Aurora PostgreSQL 
CREATE EXTERNAL SCHEMA orders_live
FROM POSTGRES
DATABASE 'orders' SCHEMA 'public'
URI 'retail-orders.cluster-abc123.us-east-1.rds.amazonaws.com'
PORT 5432
IAM_ROLE
  'arn:aws:iam::111111111111:role/rs-fed'
SECRET_ARN
  'arn:aws:secretsmanager:us-east-1:111111111111:secret:orders-ro-AbCdEf';
Join today's orders with history 
SELECT h.store_id,
       SUM(h.amount) AS history,
       SUM(o.amount) AS today
FROM sales h
JOIN orders_live.orders o
  ON o.store_id = h.store_id
WHERE o.created_at >= CURRENT_DATE
GROUP BY h.store_id;

For MySQL the statement is FROM MYSQL with no SCHEMA clause. Federated activity is logged in SVL_FEDERATED_QUERY.

Federated queries put load on the production database. They suit small, filtered lookups; they do not suit repeated scans of a large table. If analysts query the operational data all day, a zero-ETL integration or a read replica is the better answer.

Spectrum and data lake queries

An external schema over the Glue Data Catalog makes lake tables queryable alongside local ones. On RA3 these queries run on the Spectrum fleet at $5 per TB scanned (10 MB minimum per query; failed queries and DDL are free). RG clusters and Serverless run them on their own compute with no separate scan charge. Either way, partitioned columnar files are what keep the scan small.

Expose the lake to Redshift 
CREATE EXTERNAL SCHEMA lake
FROM DATA CATALOG
DATABASE 'retail_lake'
IAM_ROLE
  'arn:aws:iam::111111111111:role/rs-lake'
CREATE EXTERNAL DATABASE IF NOT EXISTS;

Materialized views

A materialized view stores a query's result and refreshes it. Redshift chooses incremental refresh when it can and full refresh when it cannot; outer joins, UNION, window functions, DISTINCT aggregates and subqueries force a full refresh.

Daily revenue, kept fresh automatically 
CREATE MATERIALIZED VIEW daily_sales
AUTO REFRESH YES
AS
SELECT store_id,
       TRUNC(sold_at) AS sale_date,
       SUM(amount)    AS revenue
FROM sales
GROUP BY 1, 2;
  • Auto refresh runs every 300 seconds by default; an INTERVAL of 60 to 86,400 seconds can be set per view.
  • Automatic query rewrite answers queries against the base table from a fresh MV without changing the SQL.
  • AutoMV (on by default) lets Redshift create MVs from your workload, with no compute charge for creating them.
  • MVs over data lake tables, including Iceberg, refresh incrementally — but get no AutoMV and no automatic query rewrite.
  • Streaming ingestion is also an MV: an external schema FROM KINESIS or FROM MSK plus a streaming MV (covered on Task 1.1).

Zero-ETL integrations

A zero-ETL integration replicates a source into Redshift continuously, with no pipeline to build. Sources now include Aurora MySQL and PostgreSQL, RDS for MySQL, PostgreSQL and Oracle, DynamoDB, self-managed MySQL, PostgreSQL, SQL Server and Oracle, and SaaS applications such as Salesforce, SAP, ServiceNow and Zendesk.

Zero-ETL has setup requirements the exam likes: the target must be Serverless or an RG/RA3 cluster, encrypted if provisioned, with case sensitivity enabled; source tables need a primary key; and the replicated database is read-only in Redshift. DynamoDB integrations refresh no faster than every 15 minutes and SaaS ones every hour.

Outside Redshift

Athena Federated Query does the same job for Athena: connectors push predicates down to DynamoDB, DocumentDB, OpenSearch, Redshift, relational engines and other clouds, and are read-only. Since April 21, 2026, some new connectors register as Glue catalogs and no longer need a Lambda function in your account.

Locks

Skill 2.1.6Manage locks to prevent access to data (for example, Amazon Redshift, Amazon RDS).

Locks stop two writers from corrupting each other's work, and stop readers from seeing half-finished changes. The skill covers taking locks deliberately, finding the session that holds one, and avoiding deadlocks.

Redshift isolation

Redshift supports two isolation levels, and the default has changed:

LevelBehaviour
SNAPSHOTNow the default for new provisioned clusters and Serverless workgroups. Each transaction sees a snapshot; fewer conflicts are cancelled
SERIALIZABLEStricter: prevents write skew, and cancels a conflicting transaction with ERROR: 1023 Serializable isolation violation

Check the level in STV_DB_ISOLATION_LEVEL and change it with ALTER DATABASE retail ISOLATION LEVEL SNAPSHOT;, which cannot target dev, cannot run inside a transaction block, and fails while other users are connected. AWS's fixes for error 1023 are: retry the transaction, move unrelated SELECTs out of it, lock every table at the start in the same order, or switch to snapshot isolation.

Taking and finding Redshift locks

LOCK always takes an ACCESS EXCLUSIVE lock, which blocks reads and writes until the transaction ends. It only means something inside a transaction, and views cannot be locked. DROP TABLE and TRUNCATE take the same lock.

Nightly merge that must not interleave 
BEGIN;
-- same order in every job: no deadlock
LOCK sales, sales_staging;
DELETE FROM sales
USING sales_staging s
WHERE sales.order_id = s.order_id;
INSERT INTO sales
SELECT * FROM sales_staging;
END;
Who holds a lock, and who waits 
-- current table locks (superuser)
SELECT table_id, last_update,
       lock_owner, lock_owner_pid
FROM stv_locks;

-- sessions still waiting for one
SELECT xid, pid, relation, lock_mode
FROM svv_transactions
WHERE granted = 'f';

-- end the blocker; its work rolls back
SELECT pg_terminate_backend(8585);

Snapshot isolation has its own deadlock. Concurrent INSERT or COPY into one table share a lock, so a later UPDATE, DELETE, MERGE or DDL in the same transactions can deadlock. AWS's advice is to run the exclusive statements in a separate transaction or add retries. For several tables, always write or lock them in the same order.

RDS and Aurora

Relational engines lock rows, not whole tables, for ordinary writes. You take explicit row locks with locking reads, and tune how long sessions wait.

MySQL: reserve stock, then decrement 
START TRANSACTION;
SELECT qty FROM inventory
WHERE sku = 'SKU-1001'
FOR UPDATE;           -- row lock
UPDATE inventory SET qty = qty - 1
WHERE sku = 'SKU-1001';
COMMIT;               -- lock released
  • MySQL: FOR SHARE (which replaces LOCK IN SHARE MODE) and FOR UPDATE; NOWAIT fails at once and SKIP LOCKED skips rows another worker holds, which suits queue tables. innodb_lock_wait_timeout sets the wait, and innodb_print_all_deadlocks logs every deadlock to the error log.
  • PostgreSQL: lock_timeout caps waits, pg_blocking_pids() names the blocker, pg_locks lists ungranted locks, and advisory locks let applications lock an idea (such as "the nightly load") rather than a row.
PostgreSQL: find and avoid blockers 
SET lock_timeout = '5s';

SELECT pid,
       pg_blocking_pids(pid) AS blockers,
       query
FROM pg_stat_activity
WHERE cardinality(
        pg_blocking_pids(pid)) > 0;

-- only one loader at a time
SELECT pg_try_advisory_lock(42);

RDS Performance Insights pages now describe CloudWatch Database Insights, which RDS enables in Advanced mode by default and which includes lock analysis. Expect either name in questions about "which session is blocking".

Locks without a database server

  • DynamoDB optimistic locking: store a version attribute and make every write conditional on it. A lost race fails with ConditionalCheckFailedException instead of overwriting. TransactWriteItems groups up to 100 items all-or-nothing. Global tables use last-writer-wins, so version checks do not protect writes across Regions.
  • S3 conditional writes: If-None-Match: * creates an object only if the key does not exist — a simple lock file for "only one run at a time". If-Match with an ETag is compare-and-swap. A lost race returns 412 Precondition Failed.
DynamoDB: update only if unchanged 
aws dynamodb update-item \
  --table-name loyalty \
  --key file://key.json \
  --update-expression \
    "SET points = :p, version = :new" \
  --condition-expression \
    "version = :old" \
  --expression-attribute-values \
    file://values.json
values.json 
{
  ":p":   {"N": "1250"},
  ":new": {"N": "4"},
  ":old": {"N": "3"}
}
S3: take a run lock, or fail with 412 
aws s3api put-object \
  --bucket retail-lake \
  --key locks/nightly-load \
  --body lock.json \
  --if-none-match "*"

Open table formats

Skill 2.1.7Manage open table formats (for example Apache Iceberg).

A plain folder of Parquet files has no transactions: two writers can collide, a reader can see half a job's output, and updating one row means rewriting files by hand. An open table format adds a metadata layer — snapshots, manifests and a pointer to the current state — that turns the folder into a table with database-like behaviour, while the data stays as open files in S3.

Iceberg featureWhat it gives you
ACID commitsReaders see a whole snapshot or none of it; concurrent writers do not corrupt the table
Row-level changesUPDATE, DELETE and MERGE on files in S3, which makes CDC and GDPR deletes practical
Time travelQuery the table as of a timestamp or snapshot ID, for audits and reproducible reports
Schema evolutionAdd, drop, rename or reorder columns as a metadata change, without rewriting data
Hidden partitioningPartition by a transform such as day(ts); queries filter on ts and still prune partitions
Partition evolutionChange the partition scheme later; old data keeps its old layout

Row-level changes come in two styles. Copy-on-write rewrites the affected data files at write time (fast reads, slow writes). Merge-on-read writes small delete files and merges them at read time (fast writes, reads slow down until compaction). Iceberg v3 replaces v2's positional delete files with deletion vectors.

Who reads and writes Iceberg

ServiceIceberg support
Amazon AthenaRead and write; creates v2 tables. Its DML always uses merge-on-read — copy-on-write table properties are ignored. Cannot read v3 tables
AWS Glue and EMR SparkRead and write, including all maintenance procedures. v3 from Glue 5.1 and EMR 7.12
Amazon RedshiftReads, and can now create and write Iceberg tables registered in the Glue Data Catalog. No Iceberg time travel in Redshift, and no COPY from Iceberg (use INSERT or CTAS)
Amazon Data FirehoseDelivers streams into Iceberg tables or S3 Tables, applying inserts, updates and deletes
Amazon S3 TablesManaged Iceberg storage with built-in maintenance; supports v3

Upgrading a table from Iceberg v2 to v3 is one-way, and Athena cannot read v3 tables. If Athena users query the table, keep it on v2 — an upgrade for deletion vectors or the variant type would cut them off with no way back.

Working with Iceberg in Athena

Athena creates Iceberg tables with CREATE TABLE and the table_type property; CREATE EXTERNAL TABLE fails for Iceberg. Partition transforms are year, month, day, hour, bucket(N, col) and truncate(L, col).

Orders table with hidden daily partitions 
CREATE TABLE retail.orders_ice (
  order_id  bigint,
  store_id  int,
  amount    decimal(12,2),
  status    string,
  ts        timestamp
)
PARTITIONED BY (day(ts))
LOCATION
  's3://retail-lake/iceberg/orders/'
TBLPROPERTIES (
  'table_type' = 'ICEBERG',
  'format' = 'parquet'
);
Apply a batch of CDC changes 
MERGE INTO retail.orders_ice t
USING retail.orders_changes c
  ON t.order_id = c.order_id
WHEN MATCHED AND c.op = 'D'
  THEN DELETE
WHEN MATCHED
  THEN UPDATE SET status = c.status
WHEN NOT MATCHED
  THEN INSERT (order_id, store_id,
               amount, status, ts)
  VALUES (c.order_id, c.store_id,
          c.amount, c.status, c.ts);
Time travel: yesterday, or one snapshot 
SELECT count(*)
FROM retail.orders_ice
FOR TIMESTAMP AS OF
  (current_timestamp - interval '1' day);

SELECT count(*)
FROM retail.orders_ice
FOR VERSION AS OF 949530903748831860;

Because Athena writes merge-on-read delete files, an Iceberg table that takes frequent MERGEs needs regular maintenance. OPTIMIZE compacts small files and folds deletes into data files; VACUUM expires old snapshots and removes orphan files.

Compact, then expire snapshots older than 3 days 
OPTIMIZE retail.orders_ice
REWRITE DATA USING BIN_PACK;

ALTER TABLE retail.orders_ice
SET TBLPROPERTIES (
  'vacuum_max_snapshot_age_seconds'
    = '259200'
);

VACUUM retail.orders_ice;

The default snapshot age for VACUUM is 432,000 seconds (5 days), keeping at least one snapshot. Expiring a snapshot also removes your ability to time-travel to it — so retention is a trade between storage cost and how far back audits can look.

Maintenance in Spark

Glue and EMR Spark jobs use Iceberg's stored procedures. Here the Spark catalog is named lake:

Iceberg maintenance procedures (Spark SQL) 
CALL lake.system.expire_snapshots(
  table => 'retail.orders_ice',
  older_than =>
    TIMESTAMP '2026-10-01 00:00:00',
  retain_last => 10);

CALL lake.system.remove_orphan_files(
  table => 'retail.orders_ice',
  dry_run => true);

-- cluster files by two filter columns
CALL lake.system.rewrite_data_files(
  table => 'retail.orders_ice',
  strategy => 'sort',
  sort_order => 'zorder(store_id,ts)');

Managed maintenance

Two services can run that maintenance for you.

  • Glue Data Catalog table optimizers (Iceberg tables only) offer compaction (bin-pack, sort or z-order), snapshot retention (defaults 5 days and 1 snapshot, off until you enable it) and orphan file deletion. Compaction is suspended after four consecutive failures, and the optimizers do not work across accounts or Regions.
  • S3 Tables store Iceberg tables in table buckets (bucket → namespace → table), with maintenance on by default: compaction to 512 MB target files, snapshot management (1 snapshot minimum, 120 hours maximum age) and unreferenced file removal. Analytics services see them through the s3tablescatalog federated catalog in Glue.

Apache Hudi and Delta Lake

Athena reads both but writes neither: Hudi supports snapshot and read-optimized queries but no incremental queries, and Delta Lake is read-only with no time travel. Writes for both go through Glue or EMR Spark. Hudi's two table types are named for their trade-off: copy-on-write for read-heavy tables, merge-on-read for write-heavy ones. When a question needs writes from several AWS engines, Iceberg is the format with the broadest support.

Vector index types

Skill 2.1.8Describe vector index types (for example, HNSW, IVF).

A vector search finds the stored embeddings closest to a query embedding. Comparing the query with every vector is exact but slow at scale, so vector stores build approximate nearest-neighbour (ANN) indexes that trade a little recall (the share of true nearest neighbours found) for a lot of speed. How embeddings are produced is covered on Task 2.4; this skill is about the index.

IndexHow it worksTrade-offs
Flat (exact)Compares the query with every vectorPerfect recall, cost grows linearly with data. Fine for small sets or as a check on ANN recall
HNSWHierarchical Navigable Small World: a layered graph, sparse at the top and dense at the bottom; a search hops greedily from coarse to fine layersBest recall for the speed, no training, can be built on an empty table and handles inserts well. Slower to build and uses more memory
IVF (IVFFlat)Inverted file: clusters vectors around centroids into lists, then searches only the nearest few lists (probes)Faster to build and smaller in memory, but lower recall at the same speed. Needs data (or training) before building, and recall drifts as the data changes

Parameters

ParameterIndexEffect
mHNSWLinks per node. Higher means better recall, more memory. pgvector default 16
ef_constructionHNSWCandidate list size while building. Higher means a better graph, slower build. pgvector default 64
ef_searchHNSWCandidate list size per query; the main recall-versus-latency knob. pgvector default 40
listsIVFNumber of clusters. AWS guidance: rows ÷ 1,000 up to a million rows, √rows beyond
probesIVFLists searched per query; start near √lists. pgvector default 1
pgvector IVFFlat for a million products 
-- build after the table has data
CREATE INDEX ON product_embeddings
  USING ivfflat
    (embedding vector_cosine_ops)
  WITH (lists = 1000);

-- about sqrt(1000)
SET ivfflat.probes = 32;
pgvector HNSW: tune per session 
-- more recall, more latency
SET hnsw.ef_search = 100;

-- 0.8.0+: keep scanning when a
-- WHERE filter drops too many rows
SET hnsw.iterative_scan = relaxed_order;

Pick by the scenario's constraint. Data changes constantly or the table starts empty → HNSW. Memory is tight and the data is loaded in bulk then rarely changes → IVF. Recall must be exact → flat. pgvector indexes the vector type up to 2,000 dimensions (halfvec up to 4,000).

Shrinking vectors

Memory, not CPU, is usually the cost of vector search, so indexes can store compressed vectors. Product quantization (PQ) splits vectors into sub-vectors and stores a code for each (lossy, needs training). Scalar quantization stores fewer bits per dimension (such as fp16) with no training. Binary vectors use one bit per dimension and Hamming distance. OpenSearch's disk-based mode ("mode": "on_disk") keeps compressed vectors in memory — 32× by default — and rescores the top candidates with full-precision vectors from disk.

The index also fixes the distance metric: Euclidean (L2), inner product, or cosine. It must match how the embedding model was trained; most text embedding models are meant for cosine. In pgvector the operators are <-> (L2), <#> (negative inner product) and <=> (cosine), and the index's operator class (vector_cosine_ops, vector_l2_ops) must match the operator in the query or the index is not used.

Key takeaways

  • Redshift: DC2 is gone — choose RG, RA3 or Serverless. RG and Serverless run lake queries on their own compute; RA3 pays Spectrum's $5 per TB scanned. Serverless base capacity defaults to 128 RPU (4 to 512, up to 1,024 in five Regions), and small bases cap managed storage.
  • Aurora: I/O-Optimized pays off at 25% or more of spend on I/O (switch once per 30 days). Serverless can scale to 0 ACU and pause, except with RDS Proxy, a global database writer or a zero-ETL source. Optimized Reads' tiered cache needs I/O-Optimized.
  • DynamoDB: on-demand is the default and recommended mode after the 50% price cut; Standard-IA helps when storage exceeds half the throughput cost; items cap at 400 KB. LSIs only at creation (5, 10 GB per key value); GSIs 20 by default, eventually consistent only.
  • EMR: S3 for anything that must outlive the cluster, HDFS for scratch; Spot on task nodes, On-Demand primary and core. From EMR 7.10.0 s3:// uses S3A, not EMRFS. Kinesis keeps data 24 hours to 365 days — a replay buffer, not a lake.
  • Redshift layout: AUTO is the default distribution; KEY for large joined tables, ALL for slow-changing dimensions, EVEN for unjoined tables. SORTKEY AUTO is recommended; compound for prefix filters, interleaved for up to eight equally weighted columns.
  • Purpose-built: pgvector on Aurora for vectors joined with relational data (engine upgrades do not upgrade the extension); MemoryDB is a durable primary store with a Multi-AZ transaction log, ElastiCache is a cache. Timestream for LiveAnalytics is closed to new customers; use Timestream for InfluxDB. S3 Vectors holds up to 2 billion vectors per index.
  • Transfer Family: SFTP, FTPS, FTP, AS2 and web apps onto S3 or EFS. FTP/FTPS need a VPC endpoint and a non-service-managed identity provider; managed workflows skip 0-byte files and AS2. Trigger processing with a workflow, the SFTP Server File Upload Completed EventBridge event, or S3 notifications.
  • Migration: DataSync for file shares and HDFS (Enhanced mode, agent on premises), DMS for databases with CDC. Snow Family is closed to new customers and Snowball support ends December 31, 2026; DataSync Discovery is gone.
  • Remote access: federated queries for small live lookups into RDS/Aurora PostgreSQL and MySQL; Spectrum for the lake; zero-ETL for a continuous read-only replica (target needs case sensitivity on; sources need primary keys); MVs with auto refresh every 300 seconds by default. Lake-table MVs get no AutoMV or automatic rewrite.
  • Locks: Redshift's default is now SNAPSHOT isolation; error 1023 comes from SERIALIZABLE. LOCK is always ACCESS EXCLUSIVE and blocks reads; lock tables in the same order everywhere; find blockers in STV_LOCKS and SVV_TRANSACTIONS, end them with PG_TERMINATE_BACKEND. RDS uses row locks (FOR UPDATE, SKIP LOCKED), DynamoDB optimistic locking with condition expressions, S3 If-None-Match for lock files.
  • Iceberg: ACID, row-level changes, time travel, schema and partition evolution. Athena writes v2 only, always merge-on-read, and cannot read v3 — and the v3 upgrade is one-way. Maintain with OPTIMIZE and VACUUM (5-day default), Spark procedures, Glue table optimizers, or S3 Tables with maintenance on by default.
  • Vector indexes: HNSW is a layered graph with no training, best recall, more memory; IVF clusters into lists, builds faster and smaller but needs data first; flat is exact. Tune ef_search or probes for recall. OpenSearch Serverless classic collections allow faiss HNSW only, and nmslib is deprecated.
