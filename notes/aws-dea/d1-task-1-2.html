Containers

Skill 1.2.1Optimize container usage for performance needs (for example, Amazon EKS, Amazon ECS).

Data processing runs in containers whether you see them or not — Glue, EMR Serverless and Lambda all hide them. This skill is about the cases where you size them yourself, and the levers are the same each time: how much CPU and memory per worker, how many workers, how fast they start, and whether they run on Spot.

EMR on EKS

A virtual cluster is a registration against a single EKS namespace — not a billable resource, and you can have many on one EKS cluster. Jobs go in through StartJobRun in the emr-containers API namespace, and job templates can mandate values so individual submissions cannot override them.

The optimization lever is the pod template: a YAML file in S3 referenced by spark.kubernetes.driver.podTemplateFile and spark.kubernetes.executor.podTemplateFile. It accepts nodeSelector, tolerations, affinity, topologySpreadConstraints, initContainers, volumes, priorityClassName and schedulerName.

Executors on Spot, driver on On-Demand (YAML) 
apiVersion: v1
kind: Pod
spec:
  nodeSelector:
    eks.amazonaws.com/capacityType: SPOT
  tolerations:
    - key: spot
      operator: Exists
      effect: NoSchedule
  containers:
    # name is fixed by EMR on EKS
    - name: spark-kubernetes-executors

The container names in a pod template are fixed: spark-kubernetes-driver and spark-kubernetes-executors. Use anything else and your settings are ignored. The submitter pod cannot use templates at all.

EKS Pod Identity is the current way to give jobs S3 access, supported from emr-7.3.0. It exists because IRSA caps out at roughly 12 clusters per role — the role's trust policy hits the 4,096-character limit. One exception: Pod Identity does not work on Fargate, so EMR on EKS on Fargate must still use IRSA.

EKS Fargate has real limits for Spark: no DaemonSets, no privileged containers, no GPUs, no EBS volumes (only static EFS), private subnets only, no instance metadata, no Fargate Spot and no Graviton on EKS Fargate. Pricing is the $0.10 per hour EKS cluster fee, plus EC2 or Fargate, plus an EMR uplift charged on the pod's requested vCPU and memory, metered per second from image pull to pod termination.

spark.dynamicAllocation.preallocateExecutors is on by default on EMR on EKS. A job that only needs a handful of executors can request a storm of them at startup. Set initialExecutors and minExecutors, or turn preallocation off.

JDBC and ODBC

Skill 1.2.2Connect to different data sources (for example, Java Database Connectivity [JDBC], Open Database Connectivity [ODBC]).

JDBC is the Java standard, ODBC the language-neutral C one. Spark, Glue and EMR are JVM-based, so JDBC is the path for data processing; ODBC matters for BI and desktop tools. The Redshift documentation puts the choice plainly: "if your client tool supports JDBC, you might choose to use that type of connection rather than ODBC due to the ease of configuration that JDBC provides."

Glue connections

A connection object stores the URI, credentials (ideally a Secrets Manager reference) and VPC details in the Data Catalog, and jobs and crawlers reuse it. Built-in connection types cover mysql, postgresql, oracle, sqlserver, redshift, snowflake, bigquery, saphana, teradata, vertica, mongodb, documentdb, opensearch, dynamodb, kinesis, kafka, s3 and azuresql, plus custom.* and marketplace.* connectors.

Glue 5.x bundles drivers for SQL Server, MySQL, Oracle, PostgreSQL and Redshift. To use your own, set customJdbcDriverS3Path and customJdbcDriverClassName on the connection, or pass --extra-jars with --user-jars-first: true so your JAR wins over the bundled one.

Reading a large table in parallel

By default a JDBC read is a single connection pulling every row through one executor — the most common reason a Glue job over a big table is slow. The fix is partitioned reads, and the option names differ depending on which API you use. This distinction is examinable.

    "useConnectionProperties": "true",

Pick a hashfield or partitionColumn that is evenly distributed and indexed. A skewed column gives one partition most of the rows, which is slower than no partitioning at all plus heavier on the source database. Note also that a Glue job run attaches to only one subnet, and job arguments are capped at 260 KB.

Redshift connectivity

The current drivers are JDBC 2.x (open source) and ODBC 2.x; 32-bit ODBC has been discontinued, and redshift_connector is the Python option. IAM authentication uses the jdbc:redshift:iam:// URL form, and Plugin_Name selects a federation plugin — including BrowserIdcAuthPlugin and IdpTokenAuthPlugin for IAM Identity Center. IAMDuration ranges from 900 to 3,600 seconds and SSLMode defaults to verify-full.

For bulk movement, the Redshift Spark connector is bundled in EMR (native from 6.9.0) and Glue 4.0 and later. It does not stream rows over JDBC: it issues COPY and UNLOAD through an S3 staging area, with autopushdown on by default and unload_s3_format defaulting to Parquet.

The Spark connector requires a tempdir (or redshiftTmpDir) S3 location, and it does not clean it up. Without a lifecycle rule on that prefix you accumulate staging data indefinitely. Also, the S3 temporary credentials it uses expire after one hour, which caps a single read or write.

"PostgreSQL drivers are not tested and not supported by the Amazon Redshift team." Redshift speaks the PostgreSQL wire protocol, so a PostgreSQL driver often appears to work — but it is unsupported, and Glue 4.0 changed Redshift REAL to map to Spark FLOAT rather than DOUBLE, with VARBYTE unsupported.

Athena drivers and federated query

Athena's current drivers are JDBC 3.x (the "new generation" driver, which reads results straight from S3) and ODBC 2.x. Both need outbound port 444 open and the athena:GetQueryResultsStream permission, and both support trusted identity propagation through IAM Identity Center.

Athena Federated Query queries a source in place with a connector. There are now two flavours, and the difference is where the compute lives:

FlavourHow it works
Glue Data Catalog federated connectorUses a Glue connection and supports Lake Formation fine-grained access control. "Starting April 21, 2026, certain newly created connectors are automatically registered as Glue Data Catalogs and do not use a Lambda function in your AWS account"
Athena data catalog federated connectorA Lambda function in your own account, from about 30 prebuilt connectors or one you build with the SDK

Federated query limits catch pipeline designs: no INSERT INTO or any write to an external catalog, no quoted identifiers, Secrets Manager needs a VPC endpoint, and only some connectors paginate table listings. The generic AthenaJdbcConnector is deprecated. Connectors also spill to S3 (spill_bucket, spill_prefix, default subfolder athena-federation-spill) — put a lifecycle rule on it.

Redshift federated query is the warehouse-side equivalent: CREATE EXTERNAL SCHEMA ... FROM POSTGRES (or MYSQL) with a SECRET_ARN and IAM_ROLE, against Aurora or RDS PostgreSQL 9.6+ and MySQL 5.6+. It is read-only, cannot create objects, and does not work with concurrency scaling — which quietly removes a cost and performance feature from any workload that uses it. Activity is logged in SVL_FEDERATED_QUERY.

Federation versus ingestion is a recurring exam choice. Federate when the data is small, needed occasionally, or must not be copied. Ingest when queries are frequent, joins are large, or the source is a production database you should not be loading. "Analysts run this join hourly against the production orders database" is an ingestion answer, not a federation one.

Integrating sources

Skill 1.2.3Integrate data from multiple sources.

Integration is where schemas disagree. The same customer appears with three different identifiers, a column is an integer in one file and a string in the next, and one source sends nested JSON while another sends flat CSV. Glue's DynamicFrame exists for exactly this.

DynamicFrame versus DataFrame

A DynamicFrame is "an extension to an Apache Spark SQL DataFrame" that does not require one fixed schema per column. When a field holds more than one type, it becomes a choice type — for example provider id: choice <long|string> — and you decide what to do about it.

resolveChoice actionResult
cast:{type}Force one type; values that will not cast become null
make_colsSplit into {col}_{type} columns, keeping everything
make_structOne struct column with a field per type
project:{type}Keep only values of that type, drop the rest
match_catalogCast to whatever the Data Catalog table says. Only valid with the choice argument, and needs a database and table name
Resolve a mixed-type column (Python, Glue) 
clean = orders.resolve_choice(
    specs=[
        # ids arrive as both int and str
        ("customer_id", "cast:string"),
        # keep both shapes for review
        ("discount", "make_cols"),
    ])

mapped = clean.apply_mapping([
    ("customer_id", "string",
     "customer_id", "string"),
    ("order_ts", "string",
     "ordered_at", "timestamp"),
    ("total", "double",
     "total_gbp", "decimal(12,2)"),
])

apply_mapping drops silently: "unspecified fields are omitted". Add a column upstream and forget to list it here, and it vanishes from the output with no error. Array paths need empty brackets, as in myList[].price.

Other transforms worth knowing by name: relationalize flattens a nested schema and pivots arrays out into separate tables joined by id and index; unnest flattens structs in place; mergeDynamicFrame merges a staging frame into a source frame on primary keys, which is the closest thing Glue has to a built-in upsert; and toDF() / fromDF() convert to and from a Spark DataFrame.

AWS's own guidance on when to convert: "Try using a Spark high-level API such as SparkSQL, DataFrame, and Datasets instead of the RDD API or DynamicFrame join … these join operations internally take advantage of query optimization by the Catalyst optimizer." So use DynamicFrames for ingestion, schema drift and Glue-native sinks, then toDF() for heavy joins and aggregations.

Joining efficiently

When one side of a join is small, a broadcast join sends it to every executor and avoids a shuffle entirely — the single highest-leverage Spark optimization for a fact-to-dimension join. Either call broadcast(df_small) or add a /*+ BROADCAST(t) */ hint. "In AWS Glue 3.0 and later, you can take advantage of broadcast hash joins automatically by enabling Adaptive Query Execution", and AQE is on by default from Glue 4.0.

The familiar 10 MB spark.sql.autoBroadcastJoinThreshold default is an Apache Spark figure, not something AWS documents for Glue. Know it as Spark behaviour, and raise it deliberately if your dimension tables are larger than that and memory allows.

Matching records across sources

When sources have no shared key, AWS Entity Resolution is the managed answer. It reads Glue tables (up to 20 data inputs), starts with a schema mapping, and offers three techniques:

TechniqueDetail
Rule-basedOrdered rules; output is tagged with the matching rule number, and a lower number means a more precise match. Supports automatic incremental processing
ML matchingMatches on name, email, phone, address and date of birth with a confidence score from 0.0 to 1.0; tolerates missing fields

GetMatchId gives a near-real-time synchronous lookup, which is what lets a streaming pipeline resolve an identity inline rather than in a nightly batch.

Slowly changing dimensions come up in integration questions but AWS publishes no prescriptive SCD pattern to cite. Build it from the primitives: mergeDynamicFrame for key-based merges, an Iceberg MERGE INTO for atomic upserts with history, and the blueprint snapshot-versus-incremental distinction for how much you reload.

For EMR on EC2, a Savings Plan or Reserved Instance covers the EC2 instance-hour portion, but the EMR charge is a separate per-instance-hour line item that is not in the eligibility list. Scanning less data

Athena charges per byte scanned, so the format and layout of the lake is the Athena bill. Redshift capacity

Concurrency scaling adds transient clusters during bursts, and the free allowance is specific: "each cluster earns up to one hour of free Concurrency Scaling credits per day", accumulating "while your main cluster is running", up to a maximum of 30 hours. Beyond the credits you pay the main cluster's per-second rate with a one-minute minimum per activation.

Concurrency scaling does not apply to everything. It is RA3 or RG only, multi-node, up to 32 compute nodes, and it is not supported with interleaved sort keys, temporary tables, Python or Lambda UDFs, DISTSTYLE ALL targets, identity columns, or federated query. The default max_concurrency_scaling_clusters is 1, so raising it is often the real fix.

For Redshift Serverless, 1 RPU is 16 GB of memory, the default base capacity is 128 RPUs, and you can set it from 4 to 512 RPUs (in units of 8 at or above 8). Billing is per second with a 60-second minimum. AI-driven scaling is on by default for new workgroups with a Balanced price-performance target, and maximum capacity and usage limits "are always honored and enforced regardless of the price-performance target setting" — so a usage limit is the hard stop, and the slider is only a preference.

Athena CTAS and INSERT INTO

SQL-only transformation of lake data, including format conversion. The limit that shapes every design here is 100 partitions per write, confirmed for both statements: CTAS "has a write limit of 100 partitions" and INSERT INTO "supports writing a maximum of 100 partitions".

Convert CSV to partitioned Parquet (SQL) 
CREATE TABLE retail_curated.orders_parquet
WITH (
  format = 'PARQUET',
  parquet_compression = 'SNAPPY',
  external_location =
    's3://retail-lake/curated/orders/',
  partitioned_by = ARRAY['order_month']
) AS
SELECT
  order_id,
  customer_id,
  total,
  -- partition cols must come last
  substr(order_date, 1, 7) AS order_month
FROM retail_raw.orders_csv
WHERE order_date >= '2026-01-01';

Three CTAS rules that break jobs. Partition columns must be last in the SELECT list. external_location "must specify a location that is empty… and never overwrites the data if the location already has data in it" — so CTAS writes once; re-running needs a new location or a cleared one. And exceeding the partition limit raises HIVE_TOO_MANY_OPEN_PARTITIONS: Exceeded limit of 100 open writers for partitions/buckets. The workaround is CTAS for the first 100 partitions, then successive INSERT INTO statements of 100 at a time.

INSERT INTO is not supported on bucketed tables or federated queries, and each statement creates new files rather than appending to existing ones — which is how a CTAS-plus-insert pipeline quietly creates a small-files problem.

On dbt: the only first-party AWS documentation is "Using dbt with Amazon MWAA", which installs dbt-core and dbt-redshift into a virtual environment and runs it with a BashOperator. dbt-glue is published by AWS in aws-samples and is a dbt Labs trusted adapter; dbt-redshift and dbt-athena are dbt Labs or community adapters, not AWS-documented products.

Distributed Map for file-level fan-out

When the transform is per-file and embarrassingly parallel, Step Functions Distributed Map beats a Spark job. Its ItemReader accepts CSV, JSON, JSONL, PARQUET and MANIFEST (an Athena result manifest or an S3 Inventory report). Open table formats and conversion

Glue 3.0 and later support Hudi, Delta Lake and Iceberg natively with no separate connector. Versions matter and the engines disagree:

Glue crawlers support Apache Iceberg v2 and v3 (including the v3 types VARIANT, UNKNOWN, Geography and Geometry) as of September 2026, while Athena is still v2 only — "Athena only creates and operates on Iceberg v2 tables". Converting a table to v3 can therefore make it crawlable but not queryable from Athena. Athena's Iceberg support also requires the Glue catalog with Glue optimistic locking only: "using Athena to modify an Iceberg table with any other lock implementation will cause potential data loss and break transactions."

Iceberg v3's headline additions are deletion vectors (at most one per data file, and "writers are not allowed to add new position delete files to v3 tables"), row lineage (_row_id and _last_updated_sequence_number), default column values, and the new types. Practically: v2 made merge-on-read possible through position and equality deletes, and v3 makes it cheaper.

Glue observability and insights

Two features exist specifically for this skill. Observability metrics (--enable-observability-metrics, true, Glue 4.0 and later) publish to the CloudWatch namespace Glue every 30 seconds, in four groups: reliability (error classes), performance (skewness), throughput per source and sink, and resource utilization. Glue partition pruning: the exam distinction

Two options filter partitions, and they work at different stages.         database="retail_raw",

            "order_month = '2026-11'",

They can be used together, and the syntaxes differ: "push_down_predicate… uses Spark SQL standard syntax and the later one uses JSQL parser." For millions of partitions, create partition indexes and use catalogPartitionPredicate; push_down_predicate alone still pays the full catalog listing.

EMR and YARN memory

The string to recognize is "Container killed by YARN for exceeding memory limits. 5.5 GB of 5.5 GB physical memory used. Consider boosting spark.yarn.executor.memoryOverhead." Overhead is executorMemory × memoryOverheadFactor, where the factor defaults to 0.10 with a 384 MB minimum, and AWS notes it "tends to grow with the executor size (typically 6-10%)". PySpark, off-heap memory and native libraries all live in that overhead, which is why Python-heavy jobs need it raised.

When running Spark on Spot, EMR 5.11.0 and later have decommissioning settings that stop a reclaimed node failing the stage: spark.blacklist.decommissioning.enabled, a one-hour timeout and spark.stage.attempt.ignoreOnDecommissionFetchFailure. Also note maximizeResourceAllocation=true, which sizes executors from the core instance group — but AWS warns against using it with HBase or with instance fleets.

Athena's timeouts are account and Region Service Quotas, shared across all workgroups — not a per-workgroup setting. AWS AppSync

GraphQL lets a client ask for exactly the fields it wants, and AppSync resolves each field from a data source: DynamoDB, Lambda, RDS or Aurora through the RDS Data API, OpenSearch Service, HTTP endpoints, EventBridge, or NONE for local pub/sub-only mutations.

Resolvers come in two shapes. A unit resolver is one handler against one data source. A pipeline resolver runs a before handler, then ordered functions each with their own data source, then an after handler — sharing state through ctx.stash and reading the previous step with ctx.prev.result. That is how one GraphQL field joins DynamoDB and Aurora.

The APPSYNC_JS JavaScript runtime is the documented first-class path — "you can write your resolvers using JavaScript and run them in the AWS AppSync (APPSYNC_JS) environment" — and the guide includes a "Migrating from VTL to JavaScript" topic. VTL still works, but new resolvers should be JavaScript. Use util.error to abort, util.appendError to continue with a partial result, and runtime.earlyReturn to skip the rest of a pipeline.

AWS AppSync Events is a separate product: serverless WebSocket pub/sub with no resolver code, publishing events to channels inside namespaces, with wildcard subscriptions and optional OnPublish and OnSubscribe handlers for transforming or rejecting events. Useful for pushing pipeline status to dashboards.

Serving SQL over HTTP

The Redshift Data API doubles as an API layer: no persistent connection, no VPC requirement for the caller, and asynchronous by design. The quotas that bound an API built on it are a 500 MB result size after compression, results retained 24 hours, 500 active queries per cluster, and a 200 KB statement size. GetStatementResultV2 returns CSV in 1 MB chunks up to 15 MB per request.

The RDS Data API is the Aurora equivalent, with credentials from Secrets Manager. Current support is Aurora PostgreSQL and Aurora MySQL, both provisioned and Serverless v2.

Three RDS Data API limits shape designs. Queries "run only on writer instances", so a global database secondary fails even for reads until promoted. It is not supported on T instance classes. And "the response size limit is 1 MiB. If the call returns more than 1 MiB of response data, the call is terminated" — so paginate in SQL with LIMIT and OFFSET or a keyset, not in the client.

Lambda function URLs are the minimal option: a https://<id>.lambda-url.<region>.on.aws endpoint with AWS_IAM or NONE auth and built-in CORS. Throttling is derived, not configured — "the maximum request rate per second is equivalent to 10 times the configured reserved concurrency", with excess returning HTTP 429. They are public internet only, with no PrivateLink, and setting reserved concurrency to 0 deactivates the URL.

A data mart is "a data warehouse that serves the needs of a specific business unit", structured and summarized, built bottom-up. A lakehouse is AWS's term for "an architecture that unifies the scalability and cost-effectiveness of data lakes with the performance and reliability characteristics of data warehouses" — ACID transactions, schema evolution, separated compute and storage, open standards such as Iceberg, and one source of truth for both batch and real-time.

LLMs for processing

Skill 1.2.10Integrate large language models (LLMs) for data processing.

New in guide version 1.1. The engineering content is not prompt writing — it is treating a model as a processing step with quotas, costs, retries and output guarantees. Four mechanisms carry most of the weight: batch inference, structured outputs, Bedrock Data Automation and Redshift ML.

Bedrock batch inference

The right default for pipeline work. You write a JSONL file to S3, start a job, and collect results from S3 — at 50% of on-demand pricing, confirmed: Bedrock offers select models "for batch inference at a 50% lower price compared to on-demand inference pricing".

Batch input records (JSONL) 
{"recordId": "ord-1001",
 "modelInput": {
   "messages": [{"role": "user",
     "content": [{"text":
       "Classify this return reason: item
        arrived damaged in transit"}]}]}}

Wrapped here for readability: in the real file each record must be a single line, the file must have a .jsonl extension, and modelInput matches either the InvokeModel body or the Converse request body depending on the invocation type you chose. "If you omit the recordId field, Amazon Bedrock adds it in the output."

QuotaValue

Three documented behaviours that break naive pipelines. "The order of records in the output JSONL file is not guaranteed to match the order of records in the input" — join on recordId, never on position. "Batch inference isn't supported for provisioned models." And tool calling is restricted: "batch inference doesn't support tool calling for jobs that use the Converse invocation type. Records that include toolConfig fail with a 400 error. To use tool calling with batch inference, create the job with the InvokeModel invocation type."

The minimum of 100 records is the detail that decides architecture: batch is not usable for small or ad-hoc jobs, so a pipeline that enriches a handful of rows must use on-demand invocation instead. Monitor job state through EventBridge rather than polling.

Bedrock has four service tiers, selected with a "service_tier" parameter: reserved, priority, default (Standard) and flex.

Cross-Region inference profiles spread load across Regions. Geographic profiles route within one geography at standard pricing — "choose Geographic for compliance requirements". "There's no additional routing cost… the price is calculated based on the Region from which you call an inference profile." Note that inference profiles do not support Provisioned Throughput.

Throttling and retries

Bedrock quotas are token-based, not request-based, and that changes how you throttle a pipeline.

ResponseMeaning
HTTP 429 ThrottlingExceptionQuota or rate exceeded — back off
HTTP 429 ModelNotReadyExceptionThe model is warming up
HTTP 503Temporary capacity constraint, not a quota breach
HTTP 529 overloaded_errorTransient capacity — honour Retry-After

The throttling error is ThrottlingException, not ServiceQuotaExceededException. And "a quota is an upper bound, not a guarantee that every on-demand request will be served immediately" — so a 503 is not something to fix by raising a quota. AWS's explicit guidance: "do not use RPM as the only control signal… use token-aware client-side rate limiting, bounded concurrency, and bounded queues."

    # to compile a new schema

brt = boto3.client("bedrock-runtime",
                   config=cfg)

Structured outputs: the mechanism that makes this reliable

Parsing prose out of a model response is the fragile part of any LLM pipeline. Structured outputs removes it: "a capability on Amazon Bedrock that ensures model responses conform to user-defined JSON schemas and tool definitions, reducing the need for custom parsing and validation." Two mechanisms, usable together — a JSON Schema output format (outputConfig.textFormat on Converse), and strict tool use by adding "strict": true to a tool definition. It works on Converse, InvokeModel, cross-Region inference and batch inference "without any additional setup".

The documented workaround for needing more than 12 possibly-absent fields: list them all in required and make each nullable with "type": ["string","null"], up to the 16 union-type limit. Also "set the maximum number of response tokens high enough to contain the complete JSON object" — otherwise you get truncated JSON with a max_tokens stop reason even with structured outputs on. Structured outputs are incompatible with citations for Anthropic models (400 error).

Bedrock Data Automation

BDA is "a cloud-based service that simplifies the process of extracting valuable insights from unstructured content—such as documents, images, video, and audio… uses generative AI to automate the transformation of multi-modal data into structured formats", with "built-in safeguards, such as visual grounding and confidence scores". It became generally available on March 3, 2025, and gained synchronous invocation in November 2025.

Output is either standard (predefined per modality) or custom via blueprints, where a blueprint defines the fields you want extracted. Pricing for custom output is per page by blueprint complexity: "the per page price for any blueprint with 30 fields or less is $0.040".

Calling a model from SQL: Redshift ML

The documented way to apply a model to warehouse rows. CREATE EXTERNAL MODEL with MODEL_TYPE BEDROCK registers an inference function you then call in SELECT.

Summarize review text in SQL (Redshift) 
CREATE EXTERNAL MODEL review_summary
FUNCTION summarize_review
IAM_ROLE
  'arn:aws:iam::111111111111:role/redshift-bedrock'
MODEL_TYPE BEDROCK
SETTINGS (
  MODEL_ID 'anthropic.claude-v2:1',
  PROMPT 'Summarize this review:',
  -- UNIFIED maps to the Converse API
  REQUEST_TYPE UNIFIED,
  RESPONSE_TYPE SUPER);

SELECT
  product_id,
  summarize_review(
    review_text,
    object('temperature', 0.2,
           'maxtokens', 200)) AS summary
FROM retail.reviews
WHERE review_date = '2026-11-01';

REQUEST_TYPE UNIFIED is the default and "has a unified and consistent interface with Amazon Bedrock for all Foundation Models that support messages"; "if an FM doesn't support messages, then you must set the request_type setting to RAW", where you build the model-native JSON as a SUPER value yourself. RESPONSE_TYPE SUPER returns the full JSON including token counts.

Two documented cautions matter for pipelines. "The throughput of inference queries is limited by the runtime quotas of the different models offered by Amazon Bedrock", and "inference queries with large amounts of data might get throttling exceptions… Amazon Redshift retries requests multiple times, but queries can still get throttled." So a SELECT over millions of rows calling a model is not a safe design — use batch inference, or Provisioned Throughput for guaranteed capacity. Also: "the names of the parameters for all Amazon Bedrock models are case sensitive. If your parameters do not match the ones required by the model, Amazon Bedrock might quietly ignore them."

Athena ML is SageMaker-only: USING EXTERNAL FUNCTION points at a SageMaker endpoint that "must accept and return text/csv". There is no native Athena-to-Bedrock function. Likewise, calling Bedrock per row from a Glue or EMR Spark UDF is a community pattern, not AWS-documented guidance — the documented options for LLM-per-row at scale are Bedrock batch inference, Redshift ML and SageMaker Processing.

Guardrails as a pipeline step

Bedrock Guardrails sensitive information filters can detect, mask or block PII, which makes them usable as a redaction stage. Modes are set separately for input and output: Block, Mask (replaced with the entity type, such as {NAME} or {EMAIL}), or None (detect only). Built-in entities span general, finance, IT, US, Canada and UK categories, plus custom regex (1 to 500 characters, no lookaround).

Masking has gaps that matter for compliance. It "does not evaluate… PII the model generates into tool call arguments… PII in tool results… PII in the tool definitions". It does not apply to model invocation logs — "the input field in Amazon CloudWatch Logs always contains the original, unmodified request regardless of guardrail intervention" (use CloudWatch Logs data protection) — nor to the guardrail trace, where the matched value "contains the original PII value, not the masked output… by design". Guardrails are also "a probabilistic machine learning based solution", not a deterministic redactor.

When not to use a model

Use deterministic transforms — SQL, Spark, Glue transforms, Athena CTAS — for parsing, casting, joins, aggregations, deduplication and any reproducible business rule. A model is right for classification, summarization, extraction from unstructured text and enrichment that genuinely needs language understanding. The cost arithmetic makes it obvious: one million rows at roughly 1,000 input and 200 output tokens each is about a billion input tokens, so the documented levers are batch inference or Flex at 50% off, global cross-Region inference at about 10% off, a smaller model, and strict max_tokens discipline.

Key takeaways

  • Containers: EMR on EKS is tuned with pod templates (driver On-Demand, executors Spot) and uses EKS Pod Identity from emr-7.3.0 — except on Fargate, which still needs IRSA. EMR Serverless pre-initialized capacity removes a 120-second cold start; Fargate task sizes are fixed CPU and memory combinations with 20–200 GiB ephemeral storage; Fargate Spot is up to 70% off with a two-minute warning.
  • JDBC parallel reads use different option names by API: hashfield and hashpartitions (default 7) for DynamicFrames, partitionColumn and numPartitions for Spark JDBC. The Redshift Spark connector needs a tempdir it never cleans up.
  • Integration: DynamicFrames handle schema drift through choice types and resolveChoice; apply_mapping silently drops unlisted fields; convert with toDF() for heavy joins because AWS recommends the Catalyst-optimized APIs. Federate for occasional reads, ingest for frequent joins.
  • Cost: Savings Plans cover only EC2, Fargate, Lambda and SageMaker AI — not Glue, EMR, Athena or Redshift. Glue Flex is about 34% cheaper for non-urgent jobs; EMR Serverless wins below 70% cluster utilization but Spot on EC2 still beats it; Compute Optimizer covers neither EMR nor Redshift.
  • Redshift concurrency scaling earns one free hour per 24 hours, accumulating to 30 hours, and does not work with federated query, interleaved sort keys or temporary tables. 1 RPU is 16 GB; Serverless usage limits are enforced regardless of the price-performance target.
  • Service choice is usually settled by one disqualifier: Lambda's 15 minutes (90 on Managed Instances for async), Athena's 100-partition write limit, Python shell's lack of bookmarks, or where the data already lives.
  • Format conversion: columnar wins on per-column compression, predicate pushdown from min/max statistics, splittability and schema evolution. Glue Parquet uses useGlueParquetWriter (not glueparquet), 128 MB row groups and 1 MB pages; Iceberg defaults to ZSTD in Athena; Athena can read but not write LZ4 or LZO Parquet.
  • Small files: Glue groupFiles works for text formats only and auto-enables above 50,000 files; S3DistCp cannot concatenate Parquet; use Iceberg OPTIMIZE or rewrite_data_files (512 MB target), or S3 Tables automatic compaction.
  • Troubleshooting: Command Failed with Exit Code 1 is driver OOM from listing too many files (fix with grouping); Container killed by YARN is executor memory (overhead defaults to 10% with a 384 MB floor); No space left on device wants the S3 shuffle plugin, which you disable by removing the flag. Use catalogPartitionPredicate with partition indexes for millions of partitions, not just push_down_predicate.
  • Athena's query timeout is an account-level quota shared by all workgroups: 30 minutes default, adjustable to 240 for DML. Redshift's STL_ALERT_EVENT_LOG pairs each problem with its documented fix, and SYS_* views are now preferred.
  • Data APIs: REST for keys, usage plans and caching (TTL max 3,600 s); AppSync pipeline resolvers with the APPSYNC_JS runtime to join sources per field; RDS Data API is writer-only, no T classes, 1 MiB response cap; S3 Object Lambda is closed to new customers since November 7, 2025.
  • LLMs: batch inference at 50% off needs at least 100 records, returns results out of order (join on recordId) and rejects toolConfig on Converse jobs. Structured outputs guarantee schema-conformant JSON but cap optional properties at 12 and take up to 90 seconds to compile a new schema. Throttling is ThrottlingException, not ServiceQuotaExceededException. Redshift ML CREATE EXTERNAL MODEL is the documented SQL path, but large SELECTs will throttle — use batch instead.
