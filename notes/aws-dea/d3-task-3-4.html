Task 3.4: Ensure data quality

Bad data that reaches a dashboard costs far more than bad data stopped at the door. This task covers checking data inside the pipeline, writing the rules those checks enforce, confirming that copies agree with their sources, sampling sensibly, and dealing with data that piles up unevenly.

Checks during processing

Skill 3.4.1Run data quality checks while processing the data (for example, checking for empty fields).

Glue Data Quality is serverless, "built on top of the open-source DeeQu framework", and runs in two places:

WhereUse it forNotes
In a Glue ETL jobStopping or quarantining bad data before it is loadedOnly ETL identifies the individual failing rows. No separate fee: you pay for the extra job time
On a Data Catalog tableChecking data at rest on a schedule, and generating rule recommendationsBilled per DPU-hour, minimum 2 DPUs and 1 minute

The EvaluateDataQuality transform

In a Glue Studio job, an Evaluate Data Quality node takes a DQDL ruleset and produces two outputs:

  • ruleOutcomes: one row per rule with its outcome, failure reason and measured value.
  • rowLevelOutcomes: the original data plus four columns — DataQualityRulesPass, DataQualityRulesFail, DataQualityRulesSkip and DataQualityEvaluationResult (Passed or Failed).

Dataset-level rules such as RowCount, ColumnCount, CustomSql and RowCountMatch cannot mark individual rows, so they appear under "skip" at row level. A row can be Passed while the ruleset as a whole fails.

On ruleset failureWhat happens
None (default)The job continues and loads everything
Fail job after loading data to targetThe job fails; set an S3 location to keep the quality results
Fail job without loading to target dataThe job fails immediately and writes nothing, not even the results

Quarantining bad rows

Failing the whole job is often too blunt: one bad row stops a million good ones. The usual pattern evaluates each row, lets passing rows continue, and writes failing rows to a quarantine prefix for review.

Check orders, split good and bad (Glue PySpark) 
from awsgluedq.transforms import (
    EvaluateDataQuality)
from awsglue.transforms import (
    SelectFromCollection)

ruleset = """Rules = [
  IsComplete "order_id",
  ColumnValues "email" != EMPTY,
  ColumnValues "qty" > 0
]"""

opts = {
    "dataQualityEvaluationContext":
        "orders_dq",
    "enableDataQualityCloudWatchMetrics":
        True,
    "enableDataQualityResultsPublishing":
        True,
}

dq = EvaluateDataQuality().process_rows(
    frame=orders_dyf,
    ruleset=ruleset,
    publishing_options=opts,
)

rows = SelectFromCollection.apply(
    dfc=dq, key="rowLevelOutcomes",
    transformation_ctx="rows").toDF()

result = rows.DataQualityEvaluationResult
good = rows.filter(result == "Passed")
bad = rows.filter(result == "Failed")

bad.write.mode("append").parquet(
    "s3://retail-lake/quarantine/orders/")

Checking for empty fields

An empty string is not null. In a CSV file, a blank value in a string column is read as "", so it passes IsComplete and Completeness, which only count nulls. (In a numeric column a blank becomes NULL and fails.) To catch empty text, add ColumnValues "email" != EMPTY; DQDL also has the keywords NULL and WHITESPACES_ONLY.

  • IsComplete "c" requires 100% non-null; Completeness "c" > 0.95 allows up to 5% nulls.
  • Most ColumnValues rules fail NULL rows, but != and not in let NULLs pass. To fail them, add NULL to the list: ColumnValues "status" not in ["X", NULL].

Alerts from quality results

Results publish to CloudWatch as glue.data.quality.rules.passed and glue.data.quality.rules.failed, and to EventBridge as Data Quality Evaluation Results Available events carrying the score. AWS recommends EventBridge for alerting.

EventBridge events are published only if the CloudWatch metrics option stays on. In the PySpark API, enableDataQualityCloudWatchMetrics defaults to False (the console default is on), so a code-only job may produce no events at all.

Alert when the quality score drops below 0.7 
{
  "source": ["aws.glue-dataquality"],
  "detail-type": [
    "Data Quality Evaluation Results Available"
  ],
  "detail": {
    "score": [{"numeric": ["<=", 0.7]}]
  }
}

Checking tables at rest

On a Data Catalog table, a recommendation run profiles the data and proposes rules (completeness, uniqueness, allowed values, length ranges) to accept as a starting ruleset; an ADVANCED mode added in 2026 uses Amazon Bedrock on a sample of rows. An evaluation run then scores the table — the percentage of rules that passed — on demand or on a schedule, optionally limited to recent partitions.

Score the orders table (CLI) 
aws glue \
  start-data-quality-ruleset-evaluation-run \
  --data-source file://orders-table.json \
  --role GlueDQRole \
  --ruleset-names orders_rules \
  --additional-run-options \
    '{"CloudWatchMetricsEnabled": true}'
orders-table.json 
{
  "GlueTable": {
    "DatabaseName": "retail",
    "TableName": "orders"
  }
}

Other in-pipeline options: a Step Functions Choice state that routes on the quality score, a Lambda check on each arriving file (Task 3.2), and Deequ (the open-source library Glue Data Quality is built on) in Spark on EMR.

Defining rules

Skill 3.4.2Define data quality rules (for example, DataBrew).

A rule turns an expectation ("every order has a customer") into something a machine can test. Two AWS rule systems appear on the exam: DQDL in Glue Data Quality, and rulesets in DataBrew.

DQDL rule types

ChecksRules
CompletenessIsComplete, Completeness
UniquenessIsUnique, Uniqueness, IsPrimaryKey, UniqueValueRatio, DistinctValuesCount
Values and formatsColumnValues (lists, ranges, regex with matches, dates), ColumnLength, ColumnDataType
StatisticsMean, Sum, StandardDeviation, Entropy, ColumnCorrelation
ShapeRowCount, ColumnCount, ColumnExists, ColumnNamesMatchPattern
FreshnessDataFreshness, FileFreshness
Across datasetsReferentialIntegrity, DatasetMatch, RowCountMatch, AggregateMatch, SchemaMatch
FilesFileMatch, FileSize, FileUniqueness
Custom and learnedCustomSql, DetectAnomalies
Orders ruleset (DQDL) 
Rules = [
  # completeness
  IsComplete "order_id",
  Completeness "email" > 0.95,
  ColumnValues "email" != EMPTY,
  # uniqueness
  IsPrimaryKey "order_id",
  # allowed values and formats
  ColumnValues "status" in
    ["NEW", "PAID", "SHIPPED"],
  ColumnValues "sku" matches
    "[A-Z]{3}-[0-9]{4}",
  # ranges
  ColumnValues "qty" between 0 and 1000,
  ColumnValues "price" > 0
    with threshold > 0.99,
  # every order's customer exists
  ReferentialIntegrity "customer_id"
    "customers.customer_id" = 1.0,
  # data arrived in the last day
  DataFreshness "order_date"
    <= 24 hours
]

DQDL syntax to know

  • Rules live in Rules = [ ... ], separated by commas; DQDL is case sensitive; # starts a comment.
  • with threshold (only on ColumnValues, ColumnDataType and CustomSql) passes the rule if enough rows comply: with threshold > 0.99 allows 1% exceptions.
  • between is exclusive of its bounds; not between is inclusive.
  • where applies a rule to a subset (a Spark SQL condition), written before any threshold: ColumnValues "state" in ["CA","WA"] where "country = 'US'".
  • Composite rules join parenthesized rules with and or or.
  • Cross-dataset rules refer to other data by an alias (customers above) supplied when the ruleset runs.
  • Labels tag rules for reporting and constants reuse values, both new in late 2025; labels, dynamic rules and analyzers work in ETL jobs only, not on Data Catalog runs.

DataBrew rulesets

A DataBrew ruleset is tied to one dataset and runs only as part of a profile job — recipe jobs do not evaluate rules. If any rule fails, the ruleset fails.

  • A rule has one or more checks, and passes when all (or any) checks pass. It can apply to one column, several, or columns matched by a regex selector.
  • Aggregate checks test the dataset or a column as a whole: row count, duplicate rows, missing, distinct or unique value counts and percentages, statistics, Z-score outliers.
  • Value checks test each row (in a list, between two values, string matches, length) and take a threshold as a count or percentage of rows. A single rule cannot mix the two kinds.
  • The console offers recommended rules from the profile. Profile jobs sample 20,000 rows by default, so percentage thresholds apply to that sample unless you profile the full dataset.
rules.json for aws databrew create-ruleset 
{
  "Name": "orders-dq",
  "TargetArn":
    "arn:aws:databrew:us-east-1:111111111111:dataset/orders",
  "Rules": [
    {
      "Name": "few-duplicate-rows",
      "CheckExpression":
        "AGG(DUPLICATE_ROWS_PERCENTAGE) < :v",
      "SubstitutionMap": {":v": "1"}
    },
    {
      "Name": "ids-present",
      "ColumnSelectors": [
        {"Regex": ".*_id"}],
      "CheckExpression":
        "AGG(MISSING_VALUES_PERCENTAGE) < :v",
      "SubstitutionMap": {":v": "5"}
    },
    {
      "Name": "qty-in-range",
      "CheckExpression":
        ":col IS_BETWEEN :lo and :hi",
      "SubstitutionMap": {
        ":col": "`qty`",
        ":lo": "0", ":hi": "1000"},
      "Threshold": {
        "Value": 95,
        "Type": "GREATER_THAN_OR_EQUAL",
        "Unit": "PERCENTAGE"}
    }
  ]
}

Choose by who writes the rules and what must happen to bad data. Glue Data Quality: engineers, rules inside pipelines, row-level quarantine, cross-dataset and anomaly rules. DataBrew: analysts working visually, validation reports from profile jobs, no row-level routing.

Data consistency

Skill 3.4.3Investigate data consistency (for example, DataBrew).

Data is consistent when the same fact looks the same everywhere: formats agree across sources, every reference points to something that exists, a copy has the same rows and totals as its source, and no key has two conflicting values. Investigating it means comparing — within a dataset, and between a dataset and its source.

Within a dataset: DataBrew

A DataBrew profile is the quick first look: duplicate row counts, distinct and unique value counts, the most common values, value distributions, and minimum and maximum string lengths that expose mixed formats (dates written two ways, codes with and without padding). Rule checks then pin these down: duplicate-row percentages, values matching a regular expression, lengths in a range. DataBrew does not document a feature for comparing two datasets; use Glue Data Quality for that.

Between datasets: Glue Data Quality

RuleCompares
RowCountMatchRow counts, as a ratio of primary to reference
AggregateMatchA sum or avg on both sides (only those two); NULLs ignored
DatasetMatchRows joined on key columns, optionally comparing value columns. Keys must be unique and non-null; otherwise use AggregateMatch
SchemaMatchColumn names and types, in any order
ReferentialIntegrityWhether every value in one dataset exists in another
Reconcile the curated table with raw (DQDL) 
Rules = [
  RowCountMatch "src" = 1.0,
  AggregateMatch "sum(amount)"
    "sum(src.amount)" = 1.0,
  DatasetMatch "src" "order_id"
    >= 0.99,
  SchemaMatch "src" = 1.0
]

The alias src is supplied at run time: as an extra input node with an alias in Glue Studio, or with --additional-data-sources on a Data Catalog evaluation run.

Run it with raw.orders as src

After a migration: DMS validation

AWS DMS can validate a migration by comparing every source row with its target row, after the full load and then for ongoing changes. It needs a primary key or unique index on each table, adds query load on both databases, and stops after 10,000 failed records by default. A validation-only task checks data already migrated without moving anything.

Task settings: validate without migrating 
"ValidationSettings": {
  "EnableValidation": true,
  "ValidationOnly": true,
  "ThreadCount": 10,
  "HandleCollationDiff": true,
  "FailureMaxCount": 10000
}

Mismatches appear in the table statistics (ValidationFailed, ValidationSuspended) and in the awsdms_validation_failures_v1 table on the target, with a failure type such as RECORD_DIFF, MISSING_SOURCE or MISSING_TARGET and the differing values.

By hand: reconciliation queries

Rows in raw that never reached curated (Athena) 
SELECT order_id, amount
FROM retail_raw.orders
EXCEPT
SELECT order_id, amount
FROM retail.orders;

Run it in both directions to find missing and extra rows; Redshift supports EXCEPT (and MINUS) the same way.

Sampling

Skill 3.4.4Describe data sampling techniques.

Sampling examines a subset so profiling, development and testing are fast and cheap. The risk is bias: a sample that does not look like the whole leads to wrong conclusions.

TechniqueHowWatch out for
Simple randomEvery row has the same chanceRare groups may be missed
StratifiedSample within each group (region, class) at chosen ratesNeeds the grouping column; keeps rare groups represented
SystematicEvery k-th rowPatterns that repeat every k rows
ClusterWhole blocks, files or partitionsRows in a block are alike, so variety is lower
First NThe top of the file or tableOften the oldest or one source — biased
ReservoirA fixed-size random sample from a stream of unknown lengthStreaming use

In SQL

Athena: row-level or segment-level samples 
-- each row kept with 10% probability
SELECT * FROM retail.orders
TABLESAMPLE BERNOULLI (10);

-- whole segments kept or skipped
SELECT * FROM retail.orders
TABLESAMPLE SYSTEM (10);

TABLESAMPLE BERNOULLI still scans every block of the table — it reduces the rows returned, not the data scanned or the bill. SYSTEM keeps or drops whole segments, which is cheaper but clumpy (a cluster sample). To cut Athena cost, filter on partitions instead.

Redshift has no TABLESAMPLE. Use ORDER BY RANDOM() LIMIT n for a random sample; SET SEED makes RANDOM() repeatable per slice, but results across slices are still not deterministic.

Redshift: 1,000 random orders 
SELECT *
FROM orders
ORDER BY RANDOM()
LIMIT 1000;

In Spark

Random and stratified samples (PySpark) 
# about 5%, repeatable with the seed
dev = df.sample(fraction=0.05, seed=42)

# stratified: keep rare returns
strat = df.sampleBy(
    "is_return",
    fractions={0: 0.02, 1: 0.5},
    seed=42)

sample returns roughly, not exactly, the fraction asked for. sampleBy samples each value of a column at its own rate; values missing from fractions are dropped.

Sampling inside AWS services

  • DataBrew projects sample the first N, last N or random rows (up to 5,000). Profile jobs sample 20,000 rows by default, or the full dataset if you choose.
  • Glue crawlers can sample 1–249 files per folder to speed up schema discovery.
  • Glue Data Quality ADVANCED recommendations look at a random sample of rows.

For rules that must hold on every row — a primary key, no negative amounts — sampling can miss the one bad row. Sample for exploration and profiling; check the full data for rules that guard a load.

Data skew

Skill 3.4.5Implement data skew mechanisms.

Skew is uneven distribution: one partition, key, slice or shard gets far more data or traffic than the rest, so the whole job waits for the busiest worker while the others sit idle. The cure is always to spread the load — but each service exposes skew differently.

Spark on Glue and EMR

In the Spark UI, skew shows as one task running far longer than the others in a stage (maximum duration well above the 75th percentile). Glue 4.0+ publishes glue.driver.skewness.stage and glue.driver.skewness.job, based on the ratio of maximum to median task time against a factor of 5. Adaptive Query Execution splits skewed join partitions automatically when they are big enough (Task 1.2); otherwise:

  • Broadcast the small table so the big one is not shuffled at all.
  • Use a better key: higher cardinality, or composite.
  • Isolate hot keys: process the few heavy keys separately and union the results.
  • Salt the key: add a random number to it on the big side, and copy the small side once per salt value, so one hot key becomes many smaller partitions.
Salting a skewed join (PySpark) 
from pyspark.sql import functions as F

N = 16  # salt values

# big side: a random salt per row
big_s = orders.withColumn(
    "salt",
    (F.rand(7) * N).cast("int"))

# small side: one copy per salt value
salts = F.array(
    *[F.lit(i) for i in range(N)])
small_s = customers.withColumn(
    "salt", F.explode(salts))

joined = big_s.join(
    small_s, ["customer_id", "salt"]
).drop("salt")

Glue job run insights write root-cause analysis only for failed runs. A run that succeeds slowly because of skew produces no insight — use the skewness metrics and the Spark UI.

Amazon Redshift

A distribution key with few values, or one dominant value, puts most rows on a few slices. SVV_TABLE_INFO.skew_rows is the ratio of rows in the fullest slice to the emptiest; values far above 1 mean skew. The fixes are a higher-cardinality DISTKEY, EVEN, or AWS's recommendation, DISTSTYLE AUTO (Task 2.1).

The most skewed tables 
SELECT "schema", "table", diststyle,
       skew_rows, skew_sortkey1,
       tbl_rows
FROM svv_table_info
ORDER BY skew_rows DESC
LIMIT 10;

DynamoDB and Kinesis

  • DynamoDB: a hot partition key is throttled at the per-partition limit. CloudWatch Contributor Insights for DynamoDB lists the most accessed and most throttled keys; its THROTTLED_KEYS mode (August 2025) bills only for throttled requests, so it can stay on. Fix hot keys with write sharding (Task 2.4).
  • Kinesis Data Streams: records with the same partition key go to the same shard, so a low-cardinality key creates a hot shard (write limits per shard: 1 MB or 1,000 records per second). Use high-cardinality keys or ExplicitHashKey, find hot shards with enhanced shard-level metrics, and split them. On-demand streams can now use an AUTO record distribution that spreads records evenly but gives up per-key ordering.
  • MSK partitions behave like shards: spread keys or add partitions.
Find the hottest keys in the loyalty table 
aws dynamodb update-contributor-insights \
  --table-name loyalty \
  --contributor-insights-action ENABLE \
  --contributor-insights-mode \
    THROTTLED_KEYS

Recognize skew in a scenario by its signature: most workers finish, one runs on (Spark); one slice is full (Redshift); throttling while total capacity is unused (DynamoDB, Kinesis). Adding capacity rarely helps — changing how keys spread does.

Key takeaways

  • Glue Data Quality runs in ETL jobs (row-level results, quarantine, no separate fee) or on Data Catalog tables (recommendations, schedules, minimum 2 DPUs). EvaluateDataQuality outputs ruleOutcomes and rowLevelOutcomes with a DataQualityEvaluationResult column for splitting good and bad rows.
  • On failure: none (default), fail after loading, or fail without loading anything. EventBridge results need the CloudWatch metrics option on — off by default in the PySpark API.
  • Empty strings pass IsComplete and Completeness; use ColumnValues "c" != EMPTY. Most ColumnValues rules fail NULLs, but != and not in pass them.
  • DQDL: thresholds only on ColumnValues, ColumnDataType and CustomSql; between is exclusive; where filters rows; composite rules with and/or; labels, dynamic rules and analyzers are ETL-only.
  • DataBrew rulesets belong to one dataset and run only in profile jobs (20,000-row sample by default); aggregate and per-row checks cannot be mixed in one rule. DataBrew for analysts, Glue Data Quality for pipelines.
  • Consistency: RowCountMatch, AggregateMatch (sum and avg only), DatasetMatch (unique, non-null keys), SchemaMatch and ReferentialIntegrity against an aliased reference. DMS validation needs primary keys and supports validation-only tasks; EXCEPT queries reconcile by hand.
  • Sampling: random, stratified, systematic, cluster, reservoir; first-N is biased. Athena TABLESAMPLE BERNOULLI scans everything; SYSTEM samples segments. Redshift has no TABLESAMPLE (use ORDER BY RANDOM()). Spark sample and sampleBy for stratified samples.
  • Skew: in Spark, broadcast, better keys, isolate hot keys or salt; watch glue.driver.skewness.stage. In Redshift, check skew_rows and use DISTSTYLE AUTO or a better key. In DynamoDB, Contributor Insights finds hot keys; in Kinesis, high-cardinality keys, shard splits or AUTO distribution on on-demand streams.
