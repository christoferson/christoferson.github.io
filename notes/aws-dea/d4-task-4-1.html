Task 4.1: Apply authentication mechanisms

Security groups

Skill 4.1.1Update VPC security groups.

A security group is a virtual firewall on a network interface. Security groups versus network ACLs, prefix lists and static egress IPs are on Task 1.1; here are the rules you change most.

  • Stateful: replies to allowed traffic are allowed automatically.
  • Allow rules only — "You can specify allow rules, but not deny rules." To block one address, use a network ACL.
  • A new security group has no inbound rules and allows all outbound traffic. The VPC's default security group allows inbound traffic from its own members.
  • Changes apply to every attached resource automatically, as quickly as possible.
  • Quotas: 60 inbound and 60 outbound rules per group (counted separately for IPv4 and IPv6), and 5 security groups per network interface (adjustable to 16).

Reference groups, not addresses

The best rule for "the ETL job may reach the warehouse" names the job's security group as the source, not its IP range. The rule then follows every interface in that group as it scales, and it counts as a single rule however many members the group has. Inbound references can point to groups in the same VPC, a peered VPC, or a VPC connected through a transit gateway.

Let Glue reach Redshift on 5439, then undo it 
aws ec2 authorize-security-group-ingress \
  --group-id sg-0redshift0000000 \
  --protocol tcp --port 5439 \
  --source-group sg-0glueetl00000000

aws ec2 revoke-security-group-ingress \
  --group-id sg-0redshift0000000 \
  --protocol tcp --port 5439 \
  --source-group sg-0glueetl00000000

Ports and rules for data services

ServiceInbound rule on the service's group

  • EMR uses managed security groups for the primary and core/task nodes, plus a service-access group in private subnets; EMR adds any missing inbound rules when a cluster starts. Clusters that share the default managed groups can talk to each other, so isolate sensitive clusters with custom ones.
  • EMR block public access is on by default: a cluster in a public subnet will not launch if a group opens any port other than 22 to 0.0.0.0/0.
  • Lambda in a VPC gets elastic network interfaces in your subnets with the security groups you choose. A function in a public subnet still has no internet access — it needs a NAT gateway or VPC endpoints.

Newer options reduce duplication: a security group can now be associated with several VPCs in the same Region and account, and shared through AWS RAM with other accounts in the organization (supported by services including EMR and Glue).

IAM identities and endpoints

Skill 4.1.2Create and update IAM groups, roles, endpoints, and services.

IdentityWhat it isUse it for
IAM userA person or application with long-term credentialsOnly where federation is not possible; AWS recommends temporary credentials instead
IAM groupA collection of users that share policiesManaging user permissions together. A group cannot be a principal in a policy and groups cannot be nested
IAM roleAn identity with no long-term credentials, assumed for temporary onesServices, workloads and federated people
IAM Identity Center userA workforce identity, from a directory or external identity providerPeople: single sign-on to accounts and applications

Anatomy of a role

  • A trust policy (resource-based) says who may assume the role — for a Glue job role, the Glue service.
  • A permissions policy says what the role may do.
  • A service role is one you create for a service and can edit. A service-linked role is created and owned by the service; you can view but not edit it.
  • An instance profile carries exactly one role onto EC2 instances, which is how EMR nodes get permissions (EMR_EC2_DefaultRole). EMR's own service role is EMR_DefaultRole_V2.
  • Sessions last 1 hour by default and up to the role's maximum (1–12 hours). Role chaining — assuming a role from another role's session — is capped at 1 hour.
glue-trust.json 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "glue.amazonaws.com"
    },
    "Action": "sts:AssumeRole"
  }]
}
Create the job role and attach Glue's policy 
aws iam create-role \
  --role-name AWSGlueServiceRole-orders \
  --assume-role-policy-document \
    file://glue-trust.json

aws iam attach-role-policy \
  --role-name AWSGlueServiceRole-orders \
  --policy-arn \
    arn:aws:iam::aws:policy/service-role/AWSGlueServiceRole

Glue's managed policies expect role names starting with AWSGlueServiceRole; any other name needs its own iam:PassRole permission. The role also needs S3 access to the job's data.

VPC endpoints

VPC endpoints let resources in private subnets reach AWS services without the internet. There are two kinds:

AspectGateway endpointInterface endpoint (PrivateLink)
ServicesS3 and DynamoDB onlyMost AWS services, including S3, Glue, Athena, Kinesis, Secrets Manager, STS
HowA route in your route tables to the service's prefix listNetwork interfaces with private IPs in your subnets, protected by security groups
CostFreePer endpoint per AZ per hour, plus per GB processed
Reachable from on-premises, other Regions, transit gatewayNoYes

For S3, use a gateway endpoint for traffic from inside the VPC (free) and add an interface endpoint only when on-premises systems need private access over VPN or Direct Connect. S3 can send in-VPC traffic through the gateway and on-premises traffic through the interface endpoint automatically.

Free S3 access for private subnets 
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-1a2b3c4d \
  --service-name \
    com.amazonaws.us-east-1.s3 \
  --route-table-ids rtb-11aa22bb

Each endpoint can carry an endpoint policy (default: allow everything) that limits what can be done through it; examples are in skill 4.1.5. Through a VPC endpoint, aws:SourceIp is not available in policies — use aws:SourceVpce, aws:SourceVpc or aws:VpcSourceIp.

Credentials and rotation

Skill 4.1.3Create and rotate credentials for password management (for example, AWS Secrets Manager).

Database passwords and API keys should live in AWS Secrets Manager, never in code, job parameters or environment variables, and should change on a schedule without anyone touching an application. Choosing between Secrets Manager and Parameter Store is on Task 4.2.

Let the database service manage its own password

The simplest option: RDS, Aurora and Redshift can create and rotate their master or admin password in Secrets Manager themselves.

Aurora manages its master password 
aws rds modify-db-cluster \
  --db-cluster-identifier retail-orders \
  --manage-master-user-password \
  --apply-immediately
ServiceSettingDefault rotation
RDS and Aurora--manage-master-user-passwordEvery 7 days
Redshift provisioned--manage-master-passwordEvery 30 days
Redshift ServerlessmanageAdminPassword on the namespaceEvery 30 days

A paused Redshift cluster (or a Serverless namespace with no workgroup) fails rotation, and automatic rotation then stops until you call RotateSecret again. Also, RDS-managed passwords are not supported with blue/green deployments, Aurora global databases or cross-Region read replicas.

Rotation for everything else

For other credentials, Secrets Manager offers managed rotation for supported services (including some partner SaaS credentials, as "managed external secrets") or Lambda rotation, where a function runs four steps:

  1. createSecret: generate a new value and store it with the label AWSPENDING.
  2. setSecret: change the password in the database or service.
  3. testSecret: log in with the pending value.
  4. finishSecret: move AWSCURRENT to the new version; the old one becomes AWSPREVIOUS.
StrategyHowUse when
Single userChange one user's password in place"Appropriate for most use cases"; a brief window where new logins can fail
Alternating usersKeep two users (user and user_clone) and switch between themHigh availability; needs a separate superuser secret to manage the clone
Store a secret, then rotate it every 30 days 
aws secretsmanager create-secret \
  --name prod/etl/orders-db \
  --secret-string file://creds.json

aws secretsmanager rotate-secret \
  --secret-id prod/etl/orders-db \
  --rotation-lambda-arn "$ROTATOR_ARN" \
  --rotation-rules \
    '{"ScheduleExpression":
      "rate(30 days)"}'
  • Schedules use rate() or cron() in UTC; the shortest interval is every 4 hours.
  • rotate-secret rotates immediately by default as well as setting the schedule.
  • Pricing is $0.40 per secret per month plus $0.05 per 10,000 API calls; new versions created by rotation are free.

Reading secrets in code

Fetch the database credentials (Python) 
import json
import boto3

sm = boto3.client("secretsmanager")
resp = sm.get_secret_value(
    SecretId="prod/etl/orders-db")
creds = json.loads(resp["SecretString"])

AWS recommends caching secrets to cut latency and cost; the aws-secretsmanager-caching library refreshes them hourly by default. Because rotation moves the AWSCURRENT label rather than changing the secret name, applications pick up new passwords without redeploying.

No password at all: IAM authentication

  • RDS and Aurora IAM database authentication: the client generates a signed token (generate-db-auth-token, IAM action rds-db:connect) valid for 15 minutes, used only to log in, over TLS.
  • Redshift: GetClusterCredentials returns a temporary database password (900–3,600 seconds), and GetClusterCredentialsWithIAM maps the database user to the calling IAM identity. Redshift Serverless uses get-credentials.
  • IAM users' access keys, where they must exist: a user can have two keys, so rotate by creating the second, switching applications, deactivating, then deleting the first. IAM Access Analyzer and last-accessed data find unused credentials.

Roles for services and tools

Skill 4.1.4Set up IAM roles for access (for example, AWS Lambda, Amazon API Gateway, AWS CLI, AWS CloudFormation).

Every service that acts on your behalf needs a role it is allowed to assume, and every caller that triggers it needs permission to do so. The pattern repeats across services: a trust policy naming the service, a permissions policy, and often a resource-based policy on the target.

AWS Lambda

  • The execution role trusts lambda.amazonaws.com and gives the function its permissions. AWSLambdaBasicExecutionRole covers CloudWatch Logs; AWSLambdaVPCAccessExecutionRole adds the network-interface permissions a VPC function needs.
  • Who may invoke the function is a separate, resource-based policy on the function. For S3 triggers, include --source-account, because bucket ARNs contain no account ID.
Allow the raw bucket to trigger the function 
aws lambda add-permission \
  --function-name start-orders-etl \
  --action lambda:InvokeFunction \
  --statement-id s3-raw-bucket \
  --principal s3.amazonaws.com \
  --source-arn arn:aws:s3:::retail-lake \
  --source-account 111111111111

Amazon API Gateway

  • For an AWS service integration (for example, writing directly to Kinesis), API Gateway assumes a credentials role that trusts apigateway.amazonaws.com. For Lambda integrations, a Lambda resource policy can be used instead.
  • Logging to CloudWatch needs a role set once at the account level (cloudWatchRoleArn) in each Region.
  • Callers authenticate with IAM (SigV4 signing), a Lambda authorizer, a Cognito user pool, or API keys with usage plans; resource policies can limit callers by IP or VPC endpoint.

The AWS CLI

Profiles in ~/.aws/config tell the CLI how to get credentials. A role profile assumes a role from another profile (optionally with MFA); an SSO profile signs in through IAM Identity Center with aws sso login.

~/.aws/config 
[profile etl-admin]
role_arn = arn:aws:iam::111111111111:role/EtlAdmin
source_profile = dev-user
mfa_serial = arn:aws:iam::111111111111:mfa/dev
role_session_name = etl-admin-cli

[profile analyst]
sso_session = retail
sso_account_id = 111111111111
sso_role_name = DataAnalyst
region = us-east-1

[sso-session retail]
sso_start_url = https://retail.awsapps.com/start
sso_region = us-east-1
sso_registration_scopes = sso:account:access
Check which identity a profile resolves to 
aws sso login --profile analyst
aws sts get-caller-identity \
  --profile analyst

role_session_name appears in CloudTrail, which makes CLI activity traceable to a person. credential_process lets an external program supply credentials, and newer CLI versions can sign in with console credentials using aws login.

AWS CloudFormation

  • A service role (trusting cloudformation.amazonaws.com) lets a stack create resources with permissions the deploying user does not have. Passing it requires iam:PassRole.
  • Once a stack has a service role, CloudFormation always uses it and it cannot be removed — and anyone allowed to update the stack can use it.
  • Templates that create IAM resources must acknowledge it with CAPABILITY_IAM, or CAPABILITY_NAMED_IAM when the resources have custom names; otherwise the deployment fails with InsufficientCapabilities.
  • StackSets with self-managed permissions use an administration role in the admin account and an execution role in each target account.
Deploy the pipeline stack with a service role 
aws cloudformation deploy \
  --template-file pipeline.yaml \
  --stack-name orders-pipeline \
  --capabilities CAPABILITY_NAMED_IAM \
  --role-arn "$CFN_DEPLOY_ROLE_ARN"

iam:PassRole

Whenever you hand a role to a service — a Glue job role, an EMR role, a Step Functions role, a CloudFormation service role — you need iam:PassRole on that role. It is a permission, not an API call, so CloudTrail logs no separate event for it. Restrict it to specific role ARNs and use iam:PassedToService to name the service.

  • EMR runtime roles (EMR 6.7.0 and later) give each step its own role instead of the cluster-wide instance profile, submitted with add-steps --execution-role-arn. They are what enable Lake Formation fine-grained access on EMR.
  • EMR Serverless jobs run with a job runtime role passed at start-job-run.

Policies on endpoints and access points

Skill 4.1.5Apply IAM policies to roles, endpoints, and services (for example, S3 Access Points, AWS PrivateLink).

Policies attach in two places. Identity-based policies attach to users, groups and roles. Resource-based policies attach to a resource — a bucket, KMS key, Lambda function, SQS queue, VPC endpoint, access point or the Glue Data Catalog — and must name a principal. Within one account, an allow in either is enough; across accounts, both sides must allow.

S3 Access Points

A large shared bucket's policy becomes unmanageable when dozens of teams need different access. An access point is a named entry point to the bucket with its own policy, so each team or application gets one access point and one small policy.

  • A request through an access point must be allowed by both the access point policy and the bucket policy. AWS recommends delegating control: the bucket policy allows anything that arrives through the account's access points (s3:DataAccessPointAccount).
  • A VPC-only access point accepts requests only from one VPC. The network origin and Block Public Access settings are fixed when the access point is created.
  • Up to 10,000 access points per account per Region. Each has an ARN (arn:aws:s3:us-east-1:111111111111:accesspoint/name) and an alias usable wherever a bucket name is expected for object operations.
  • Access points now also front FSx for ONTAP and OpenZFS volumes and S3 directory buckets. Multi-Region Access Points give one global endpoint over buckets in several Regions; S3 Access Grants map prefixes to IAM principals or directory users.
An access point for the ETL VPC only 
aws s3control create-access-point \
  --name orders-etl-ap \
  --account-id 111111111111 \
  --bucket retail-lake \
  --vpc-configuration VpcId=vpc-1a2b3c4d
Access point policy: the ETL role, curated prefix 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS":
        "arn:aws:iam::111111111111:role/AWSGlueServiceRole-orders"
    },
    "Action": [
      "s3:GetObject",
      "s3:PutObject"
    ],
    "Resource":
      "arn:aws:s3:us-east-1:111111111111:accesspoint/orders-etl-ap/object/curated/*"
  }]
}
Bucket policy: delegate to this account's access points 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"AWS": "*"},
    "Action": "*",
    "Resource": [
      "arn:aws:s3:::retail-lake",
      "arn:aws:s3:::retail-lake/*"
    ],
    "Condition": {
      "StringEquals": {
        "s3:DataAccessPointAccount":
          "111111111111"
      }
    }
  }]
}

Locking a bucket to a VPC endpoint

Two complementary policies keep data on the private path. The endpoint policy limits what can be reached through the endpoint — stopping a compromised instance copying data to some other bucket. The bucket policy limits where requests to the bucket may come from.

Gateway endpoint policy: only the lake bucket 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": [
      "s3:ListBucket",
      "s3:GetObject",
      "s3:PutObject"
    ],
    "Resource": [
      "arn:aws:s3:::retail-lake",
      "arn:aws:s3:::retail-lake/*"
    ]
  }]
}
Bucket policy: deny anything not via the endpoint 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyNotViaVpce",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": [
      "arn:aws:s3:::retail-lake",
      "arn:aws:s3:::retail-lake/*"
    ],
    "Condition": {
      "StringNotEquals": {
        "aws:SourceVpce": "vpce-1a2b3c4d"
      }
    }
  }]
}

That deny also blocks the S3 console and any service that reaches the bucket from outside the VPC, including administrators. Gateway endpoint policies must use "Principal": "*" (restrict principals with aws:PrincipalArn), and some AWS services need access to AWS-owned buckets through the endpoint, which a tight endpoint policy can break.

  • Data perimeters add organization keys: aws:PrincipalOrgID (the caller belongs to your organization) and aws:ResourceOrgID (the resource does).
  • PrivateLink for Redshift: Redshift-managed VPC endpoints give another VPC or account private access to a cluster or workgroup without peering.
  • Permissions boundaries cap what an identity's own policies can grant, and SCPs cap whole accounts; neither grants anything (Task 4.2).

Managed and unmanaged services

Skill 4.1.6Describe the differences between managed services and unmanaged services.

Under the shared responsibility model, AWS secures the cloud itself, and what you secure "will be determined by the AWS Cloud services that a customer selects". The more managed the service, the less you operate — and the more authentication runs through IAM rather than through software you configure.

AspectUnmanaged (for example, Kafka or a database on EC2)Managed (MSK, RDS, S3, DynamoDB)
Operating systemYou patch and harden itAWS does
Software versionsYou install and upgradeAWS provides; you choose versions (or none to choose)
AuthenticationThe software's own users, Kerberos, certificates — all yours to runIAM integration where offered, plus the engine's own users where relevant
NetworkSecurity groups and everything inside the instanceSecurity groups or endpoint and resource policies
Your data and access policiesYoursStill yours, always

For fully abstracted services such as S3 and DynamoDB, "AWS operates the infrastructure layer, the operating system, and platforms", and you manage data, encryption, classification and IAM. Managed services still differ in how much identity work they leave you:

  • Amazon RDS: IAM controls management actions, but database logins use "the security features of your DB engine", optionally with IAM database authentication.
  • Amazon MSK: clients authenticate with IAM, mutual TLS, or SASL/SCRAM. SCRAM secrets must be named with the prefix AmazonMSK_ and encrypted with a customer managed KMS key — the default Secrets Manager key does not work.
  • OpenSearch Service: network placement, a resource-based domain access policy, and optional fine-grained access control with its own or IAM users.
  • Amazon MWAA: access to the Airflow UI, CLI and REST API is granted through IAM (airflow:CreateWebLoginToken and similar), mapped to Airflow roles.

When a scenario stresses "least operational overhead" or "no servers to patch", the managed service wins. When it needs a feature or version the managed service does not offer, the unmanaged option — with all its authentication and patching work — may be the only answer.

SageMaker Unified Studio access

Skill 4.1.7Use domain, domain units, and projects for SageMaker Unified Studio.

SageMaker Unified Studio organizes people and data in a domain, divided into domain units, where work happens in projects. The catalog side — assets, glossaries, publishing, subscriptions — is on Task 2.2; this section is about who gets in and what a project can reach.

Two kinds of domain

Domain typeUsers sign in withProject access runs through
IAM Identity Center-basedSingle sign-on through IAM Identity Center (often from an external identity provider), plus IAM for administratorsA project role per project (datazone_usr_role_...), or trusted identity propagation
IAM-based (newer)IAM roles; one domain per account per RegionA project execution role shared by all members

Users reach the Studio web application through the domain's URL. IAM roles, IAM users, SSO users and SSO groups can all be added; a role added to the domain becomes a group profile, and each person using it gets a session user profile.

Domain units and authorization policies

Domain units form a hierarchy under the root — for example finance and marketing — each with owners who hold delegated authority. Authorization policies on a unit say who may:

  • create child domain units, create projects, and manage project membership;
  • take over ownership of domain units or projects;
  • create glossaries, metadata forms and custom asset types (granted to projects).

Policies can go to selected users and groups or to all users, and can cascade to child units. Separate authorization on each blueprint says which domain units' projects may use it.

Projects

  • Members hold designations: the managed Owner and Contributor, or custom designations that domain administrators define. A project holds up to 100 user profiles and 20 group profiles. The creator becomes the first owner.
  • A project profile (created by domain administrators) is a set of blueprints — Tooling, Lakehouse database and catalog, Redshift Serverless, EMR on EC2, EMR Serverless, Workflows (MWAA), and others — that decide what each new project gets.
  • The Tooling blueprint deploys first and provisions the project's S3 storage, its IAM role, default connections, Athena workgroups and Lake Formation permissions. The project role is what actually reads S3, Glue and Redshift data when members run queries and jobs.
  • Associated accounts, shared through AWS RAM, let projects deploy resources into and use data from other accounts.
A domain unit, a project in it, and a member 
aws datazone create-domain-unit \
  --domain-identifier dzd_4p9n6sw4qt9xgn \
  --parent-domain-unit-identifier \
    "$ROOT_UNIT_ID" \
  --name finance

aws datazone create-project \
  --domain-identifier dzd_4p9n6sw4qt9xgn \
  --name sales-etl \
  --domain-unit-id "$FINANCE_UNIT_ID" \
  --project-profile-id "$SQL_PROFILE_ID"

aws datazone create-project-membership \
  --domain-identifier dzd_4p9n6sw4qt9xgn \
  --project-identifier "$PROJECT_ID" \
  --designation PROJECT_CONTRIBUTOR \
  --member userIdentifier="$USER_ID"

In an IAM-based domain, every project member shares the project's execution role, so everyone in the project gets the same data and compute access. To give people different access, put them in different projects. The administrator's execution role also becomes a Lake Formation administrator automatically.

Key takeaways

  • Security groups are stateful and allow-only; reference the caller's security group rather than IP ranges. Defaults: 60 inbound and 60 outbound rules, 5 groups per interface. Redshift 5439, PostgreSQL 5432, MySQL 3306, MSK 9092/9094/9096/9098. EMR block public access stops public-subnet clusters with ports open to the world.
  • Prefer roles and IAM Identity Center over IAM users; groups cannot be principals. A role has a trust policy (who assumes) and permissions (what it does); role chaining caps sessions at 1 hour; instance profiles carry roles to EC2 and EMR nodes.
  • Gateway endpoints: S3 and DynamoDB only, free, in-VPC traffic only. Interface endpoints: most services, billed, reachable from on-premises. Through an endpoint, use aws:SourceVpce rather than aws:SourceIp.
  • Let RDS/Aurora (7-day default rotation) and Redshift (30-day) manage their own passwords in Secrets Manager. Lambda rotation runs createSecret, setSecret, testSecret, finishSecret, moving AWSPENDING to AWSCURRENT; minimum interval 4 hours; rotate-secret rotates immediately by default. A paused Redshift cluster stops rotation.
  • IAM database authentication avoids passwords: RDS tokens last 15 minutes; Redshift temporary credentials 15–60 minutes.
  • Lambda: execution role plus a resource policy for invokers (--source-account for S3). API Gateway: a credentials role for service integrations and a per-Region CloudWatch logging role. CLI: role and SSO profiles. CloudFormation: a service role that cannot be removed once set, and CAPABILITY_NAMED_IAM for custom-named IAM resources. Handing roles to services needs iam:PassRole.
  • S3 Access Points: both access point and bucket policies must allow, so delegate with s3:DataAccessPointAccount; VPC-only origin is fixed at creation; 10,000 per account per Region. Combine an endpoint policy with a bucket policy on aws:SourceVpce — which also blocks console access.
  • Managed services move patching and much authentication to AWS and IAM; your data and access policies stay yours. MSK SCRAM secrets need the AmazonMSK_ prefix and a customer managed KMS key.
  • SageMaker Unified Studio: Identity Center-based or IAM-based domains (one IAM-based domain per account per Region); domain units with owners and authorization policies; projects with Owner and Contributor designations, built from project profiles and blueprints, reaching data through the project role that Tooling provisions with Lake Formation permissions.
