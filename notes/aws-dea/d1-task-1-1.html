Overview

Task 1.1

Perform data ingestion.

Twelve skills, and they divide neatly in two. Half are about which service reads which source — streams, files, databases, SaaS applications, APIs — and half are about making ingestion survive reality: rate limits, network rules, duplicate records, reprocessing, and where state lives. Exam questions rarely ask "what is Kinesis"; they describe a pipeline that is throttling, falling behind, dropping records or re-reading the same file, and ask which setting fixes it.

Streaming sources

Skill 1.1.1Read data from streaming sources (for example, Amazon Kinesis, Amazon Managed Streaming for Apache Kafka [Amazon MSK], Amazon DynamoDB Streams, AWS DMS, AWS Glue, Amazon Redshift).

A stream is an append-only, ordered, time-bounded log. Producers write records; consumers read from a position they choose and move forward at their own pace. That last part is what separates a stream from a queue: records are not deleted when read, so several consumers can read the same data independently, and one consumer can go back and read it again.

Kinesis Data Streams: capacity modes

A stream is a set of shards. Each record carries a partition key; Kinesis hashes it to pick the shard, which is why the partition key decides both ordering and how evenly load spreads. Ordering is guaranteed within a shard, never across shards.

ModeHow capacity worksNotes
On-demand StandardStarts at 4 MB/s write and 8 MB/s read, scales automaticallyDefault choice; up to 20 registered fan-out consumers
On-demand AdvantageAccount-level mode added November 2025; no per-stream-hour feeUp to 50 fan-out consumers, free configurable warm throughput, manual scale-down, 25 MiB/s in and out billing floor
ProvisionedYou set the shard count and pay per shard-hourThe only mode that allows manual resharding

On-demand scaling is not instant. It absorbs up to double the trailing 30-day peak, and throttles if traffic more than doubles inside 15 minutes. It splits a shard that passes about 500 KB/s, but it does not isolate a single hot partition key. You can switch capacity mode twice per 24 hours.

The widely repeated "1 MB maximum record, 5 MB per PutRecords" figures are out of date: records can now be 10 MiB and a PutRecords request can carry 10 MiB across its 500 records. The 500-record cap has not changed.

Writing to a stream

PutRecord writes one record. PutRecords writes a batch and is what you want for throughput — but it reports failures per record instead of failing the call. The response keeps the request order and sets FailedRecordCount, with an ErrorCode on each failed entry. Records that succeeded are not retried, so the batch as a whole is not ordered and you must resend the failures yourself.

Batch write with retry of failures (Python) 
import json, time, boto3

kinesis = boto3.client("kinesis")
STREAM = "retail-clickstream"

def put_batch(events):
    records = [
        {"Data": json.dumps(e).encode(),
         # spread load across shards
         "PartitionKey": e["session_id"]}
        for e in events
    ]
    delay = 0.1
    while records:
        r = kinesis.put_records(
            StreamName=STREAM,
            Records=records)
        if not r["FailedRecordCount"]:
            return
        # keep only the failed entries
        records = [
            rec for rec, res in zip(
                records, r["Records"])
            if "ErrorCode" in res
        ]
        time.sleep(delay)
        delay = min(delay * 2, 5)

The error code to recognize is ProvisionedThroughputExceededException: the shard's write limit was exceeded. The fixes are to slow down, retry with exponential backoff, re-key for higher cardinality, or (provisioned mode only) split the hot shard.

Reading a stream

A consumer gets a shard iterator, then calls GetRecords in a loop. The iterator type is the "where do I start" decision, and it matters for replay (see replayability).

Iterator typeStarts at
TRIM_HORIZONThe oldest record still in the stream
LATESTOnly records written after you start reading
AT_TIMESTAMPA point in time; falls back to the trim horizon if older
AT_SEQUENCE_NUMBERA specific record
AFTER_SEQUENCE_NUMBERJust after a specific record — the checkpoint pattern

Hand-written GetRecords loops are rare in production. The Kinesis Client Library (KCL) does the work: it discovers shards, assigns one worker per shard, checkpoints progress and rebalances when workers come and go. KCL 3.x is current and balances shards by worker CPU utilization; KCL 1.x reached end of support on January 30, 2026. On the producer side the Kinesis Producer Library (KPL) batches records (see fan-in).

GetRecords.IteratorAgeMilliseconds is the single most useful stream metric: it is how far behind the consumer is. Alarm on the Maximum statistic, because one lagging shard is the problem and an average hides it. If age approaches half the retention period, you are at risk of losing data you have not read.

Amazon MSK

MSK runs Apache Kafka. A topic is divided into partitions; a partition is the unit of ordering and of consumer parallelism, and consumer groups are how you fan out, each group tracking its own offsets.

DeploymentWhat you manageKey constraints
Provisioned, Standard brokersBroker type and count, storage per broker30 brokers per cluster with ZooKeeper, 60 with KRaft; the only option that supports tiered storage
Provisioned, Express brokersBroker type and count onlyGA November 2024; up to 3x throughput per broker, virtually unlimited storage with nothing to provision, 3 Availability Zones only, best-practice defaults built in
ServerlessNothing but topics200 MBps in and 400 MBps out per cluster, 2,400 partitions, unlimited retention, IAM access control only

Authentication on provisioned clusters is IAM access control, SASL/SCRAM with credentials in AWS Secrets Manager, mutual TLS with AWS Private CA, or unauthenticated. SASL/SCRAM and mTLS use Kafka ACLs for authorization; IAM uses IAM policies.

MSK Serverless does not support Kafka ACLs, so it does not support SASL/SCRAM or mTLS — IAM access control is the only choice. Tiered storage is likewise provisioned Standard brokers only (not Express, not Serverless, not t3.small), needs a minimum three-day remote retention, and once disabled on a topic it cannot be re-enabled.

Kafka versions are supported until a published end-of-support date, after which MSK auto-upgrades the cluster to the recommended version with no prior notification. Version 3.9.x is the recommended version and the last to support both ZooKeeper and KRaft. MSK Replicator handles managed cross-Region or same-Region replication of data, topic configurations, ACLs and consumer offsets, with Prefixed (default) or Identical topic naming — Identical is what makes failover work without reconfiguring clients.

DynamoDB Streams

Turning on a stream gives you an ordered log of item-level changes. The view type is chosen once and cannot be edited: to change it you disable the stream and create a new one, which gets a new ARN.

View typeEach record contains
KEYS_ONLYOnly the key attributes of the changed item
NEW_IMAGEThe item as it is after the change
OLD_IMAGEThe item as it was before the change
NEW_AND_OLD_IMAGESBoth — what you need to compute a delta

Retention is 24 hours, fixed. Each record "appears exactly once in the stream", and records for a given item appear in the order the modifications happened — ordering is per item, not per partition or per table. Shards are managed for you (no manual resharding), each open shard maps to one table partition, parent shards must be processed before their children, and a shard supports at most two simultaneous readers. A write that changes nothing emits no record.

Kinesis Data Streams for DynamoDB sends the same changes to a Kinesis stream instead, which buys retention up to 365 days, enhanced fan-out and many consumers. The trade-off is explicit in the documentation: records "might appear in a different order than when the item changes occurred" and "might also appear more than once" — it is at-least-once and possibly reordered, so order and deduplicate on ApproximateCreationDateTime.

Pick the signal from the question: "react to writes in Lambda, nothing fancy" is DynamoDB Streams; "more than 24 hours of history", "several teams consuming", or "enhanced fan-out" is Kinesis Data Streams for DynamoDB; "load changes into Redshift or OpenSearch with no pipeline code" is a zero-ETL integration.

AWS DMS as a streaming source

A DMS task with migration type cdc (or full-load-and-cdc) reads the source database's own transaction log — Oracle redo through LogMiner or the binary reader, SQL Server MS-CDC, MySQL row-based binlog, PostgreSQL logical replication — and applies each change to the target. Targets relevant here include S3, Kinesis Data Streams, MSK, Redshift, OpenSearch and DynamoDB.

DMS CDC is not a real-time stream. The documentation states plainly that it "does not provide real-time replication" and that there are no SLAs for CDC latency. If a question demands sub-second propagation, DMS is the wrong answer.

Glue streaming and Redshift streaming ingestion

An AWS Glue streaming job (job command gluestreaming) runs Spark Structured Streaming over Kinesis, Kafka or MSK with a default 100-second window, and writes micro-batches to the lake. Two things catch people out: streaming jobs use checkpoints, not job bookmarks (to reprocess, delete the checkpoint folder), and a Kafka or MSK source needs a Glue connection on TLS port 9094 because plaintext is not supported.

Redshift streaming ingestion skips staging entirely: you create an external schema over a Kinesis stream or MSK topic and a materialized view on top of it. "There isn't a temporary landing area, such as an Amazon S3 bucket." It gives exactly-once processing.

Redshift streaming ingestion (SQL) 
CREATE EXTERNAL SCHEMA clicks
FROM KINESIS
IAM_ROLE
  'arn:aws:iam::111111111111:role/redshift-stream';

CREATE MATERIALIZED VIEW clickstream_mv
AUTO REFRESH YES AS
SELECT
  approximate_arrival_timestamp
    AS arrived,
  -- SUPER column, query with PartiQL
  JSON_PARSE(kinesis_data) AS payload
FROM clicks."retail-clickstream";

AUTO REFRESH must be set explicitly — manual refresh is the default, and a view nobody refreshes silently stops being current. The materialized view must be incrementally maintainable, so joins are not supported; land the stream first, then join downstream. Errors appear in SYS_STREAM_SCAN_ERRORS.

Getting files into S3

For objects of 100 MB or larger AWS calls multipart upload a best practice: parts upload in parallel, a failed part is retried alone, and a stalled upload can resume. A single PUT handles up to 5 GB; multipart allows up to 10,000 parts of 5 MiB to 5 GiB each (the last part has no minimum).

Incomplete multipart uploads keep their parts in the bucket and you keep paying for them, invisible to a normal object listing. Add an AbortIncompleteMultipartUpload lifecycle rule to every bucket that receives large uploads.

S3 Transfer Acceleration routes uploads through CloudFront edge locations onto AWS's optimized network path. Use it for uploads from around the world into one bucket, or for regular cross-continent transfers. It needs virtual-hosted-style requests and a bucket name with no periods, takes up to 20 minutes to activate, and adds data-transfer charges. The alternative for bulk on-premises movement is AWS DataSync.

The AWS Snow Family and AWS Application Discovery Service both closed to new customers on November 7, 2025; existing customers continue to use them. For offline or bandwidth-limited transfer the current answers are DataSync, AWS Data Transfer Terminal and AWS Outposts. AWS Data Pipeline is closed to new customers and in maintenance mode, with no new features or Region expansions planned; AWS points migrations at Glue, Step Functions and Amazon MWAA.

Amazon AppFlow

A flow connects a SaaS source to an AWS destination with field mapping, filters and simple transformations. Three trigger types: run on demand, run on event (the application pushes change events — Salesforce needs CDC enabled), and run on schedule. Scheduled flows can transfer everything or do an incremental pull based on a timestamp field you choose.

"The first schedule-triggered flow will pull 30 days of past records." If you need a different initial window, run the flow on demand with a filter first, then let the schedule take over. The schedule offset must be under 10 hours (default 0), and S3 source files should stay under 125 MB.

Private flows use AWS PrivateLink for the supported connectors (including Salesforce and Snowflake); AppFlow creates and deletes the endpoint service configuration itself, though metadata API calls still traverse public endpoints.

Batch configuration

Skill 1.1.3Implement appropriate configuration options for batch ingestion.

This skill is the settings layer under the previous one: the knobs that decide whether a batch job re-reads yesterday's data, truncates a column, costs twice what it should, or falls over at scale.

Glue job bookmarks

A bookmark is per-job state, keyed by job name and run version, that records how far a source has been read. Individual sources are keyed by their transformation_ctx. State is read at job.init() and saved atomically at job.commit() — a job that never commits never advances its bookmark.

A bookmarked S3 read (Python, Glue) 
import sys
from awsglue.context import GlueContext
from awsglue.job import Job
from awsglue.utils import \
    getResolvedOptions
from pyspark.context import SparkContext

args = getResolvedOptions(
    sys.argv, ["JOB_NAME"])
sc = SparkContext.getOrCreate()
gc = GlueContext(sc)
job = Job(gc)
# loads saved bookmark state
job.init(args["JOB_NAME"], args)

orders = gc.create_dynamic_frame \
    .from_catalog(
        database="retail_raw",
        table_name="orders",
        # names this source's bookmark
        transformation_ctx="orders_src")

gc.write_dynamic_frame.from_options(
    frame=orders,
    connection_type="s3",
    connection_options={
        "path":
            "s3://retail-lake/"
            "curated/orders/",
        "partitionKeys": ["order_date"]},
    format="parquet",
    transformation_ctx="orders_sink")

# saves the bookmark
job.commit()

Bookmarks track sources only, never targets: if a job writes its output twice, bookmarks will not deduplicate it. They are also unsupported in Python shell jobs and with Lake Formation cell-level filters, and streaming jobs use checkpoints instead.

Auto scaling and Flex

With --enable-auto-scale: true (Glue 3.0 and later), NumberOfWorkers becomes a maximum rather than a fixed size, and Glue adds and removes executors as stages demand. It also derives spark.sql.shuffle.partitions and spark.default.parallelism from the maximum DPUs. Watch numberMaxNeededExecutors against numberAllExecutors to see whether the ceiling is binding.

Flex execution runs non-urgent jobs on spare capacity at lower cost, billed as the sum of each worker's own runtime instead of maximum capacity multiplied by duration. It needs Glue 3.0 or later and only G.1X and G.2X — the large and memory-optimized worker types do not support it.

Default job timeout is 480 minutes on Glue 5.0 and later (it was 2,880 minutes up to Glue 4.0), with a maximum of 7 days. Enable job run queuing so runs wait instead of failing outright when a quota or IP address limit is hit.

Glue crawlers

A crawler infers schemas and partitions and writes tables into the Data Catalog. Its configuration is where incremental ingestion is won or lost.

Incremental crawls ("crawl new sub-folders only") do a full listing on the first run and then add only new partitions. The documented limitation is the one that matters: "incremental crawls don't detect modifications or deletions of existing partitions". Turning it on also forces UpdateBehavior and DeleteBehavior to LOG and locks the S3 targets.

Event mode is the scalable option for a busy bucket: instead of listing the target, the crawler consumes S3 event notifications from an SQS queue. The first crawl is still a full listing, there is a cap of 100,000 messages per crawl, only one target is allowed, and the crawler role needs SQS permissions including ReceiveMessage, DeleteMessage and GetQueueAttributes.

"AWS Glue does not support crawlers for data streams." Streams have no schema to crawl — you create the Catalog table by hand (or let a streaming job detect the schema). Crawlers also do not write to a target's catalog table for Iceberg unless the crawler is the sole writer.

Redshift COPY

COPY loads in parallel across slices and is "the most efficient way to load a table"; the documentation calls row-by-row INSERT "much less efficient". The guidance on file layout is explicit and examinable: split data so the number of files is a multiple of the number of slices, and keep files roughly equal in size, from 1 MB to 1 GB after compression, because "Amazon Redshift doesn't take file size into account when dividing the workload".

Manifest load and an auto-copy job (SQL) 
COPY retail.orders
FROM 's3://retail-lake/raw/orders/m.json'
IAM_ROLE
  'arn:aws:iam::111111111111:role/redshift-copy'
MANIFEST
GZIP
FORMAT AS JSON 'auto';

-- continuous load from an S3 prefix
COPY retail.orders
FROM 's3://retail-lake/raw/orders/'
IAM_ROLE
  'arn:aws:iam::111111111111:role/redshift-copy'
GZIP
JOB CREATE load_orders AUTO ON;

A manifest names the exact files to load and may span buckets — it is how you make a load deterministic instead of trusting a prefix. Auto-copy requires an S3 event integration first, then tracks which files have already been loaded; monitor it through SYS_COPY_JOB, SYS_COPY_JOB_DETAIL and SYS_LOAD_HISTORY. Limits: 200 COPY JOBs per cluster or workgroup, 50 S3 event integrations per target, same Region, and a bucket name without periods.

Compression for COPY is BZIP2, GZIP, LZOP or ZSTD (S3 only). Uncompressed delimited files are split automatically by scan ranges — but not when ESCAPE, REMOVEQUOTES or FIXEDWIDTH is used, so those loads are single-threaded per file and file splitting matters even more.

Consuming data APIs

Skill 1.1.4Consume data APIs.

Some sources have no connector: a partner REST API, a provider's data set, or an AWS service you drive through its own API. Three things make an API consumer reliable — pagination, retries and a cursor you can resume from.

Pagination

AWS APIs return bounded pages. MaxResults (or limit) sets the page size, not the total: the paginator keeps fetching until the token is gone. Use the SDK's paginators rather than hand-rolling the loop.

Paginating a listing (Python)

Retries and client-side rate limiting

SDK retry behaviour has three modes: standard (the default), adaptive and legacy. Maximum attempts default to 3, meaning one initial call plus two retries. Backoff is exponential with jitter, and the SDK honours a x-amz-retry-after header when the service sends one.

The distinction worth knowing: standard mode retries after a failure, while adaptive mode adds a client-side rate limiter that can delay or block the initial request based on the throttling it has seen. That makes adaptive right for a latency-tolerant batch loader hammering one resource, and wrong as a general default — the limiter is per client instance and will slow traffic that was never the problem.

Adaptive retries for a bulk loader (Python) 
from botocore.config import Config

cfg = Config(
    retries={"mode": "adaptive",
             "max_attempts": 10},
    connect_timeout=5,
    read_timeout=60)

ddb = boto3.client("dynamodb", config=cfg)

Codes that mean "slow down" and should be retried with backoff: ThrottlingException, ProvisionedThroughputExceededException, TooManyRequestsException, RequestLimitExceeded and SlowDown. Codes that will never succeed on retry: ValidationException, AccessDeniedException and ResourceNotFoundException.

API Gateway as an ingestion front door

AWS Data Exchange

Glue triggers and workflows

Inside Glue, a trigger starts jobs and crawlers. Three types: scheduled (cron), conditional (watch jobs and crawlers and fire when ANY or ALL reach listed states), and on-demand. Watched job states are SUCCEEDED, STOPPED, FAILED and TIMEOUT; crawler states are SUCCEEDED, FAILED and CANCELLED. A trigger may watch at most two crawlers.

A conditional trigger only fires if the job or crawler it watched was itself started by a trigger. Every chain must descend from a scheduled or on-demand trigger — starting a job by hand to "test the chain" silently does nothing downstream.

Workflows add a visual graph, run-level monitoring, run properties readable and writable mid-run, a maximum-concurrent-runs setting, and a start trigger that can be a schedule, on demand, or an EventBridge event. An EventBridge start trigger takes a batch size (required, defaults to 1) and an optional batch window (default and maximum 900 seconds), whichever is reached first — which is how you turn a flood of S3 events into one run per batch. Keep jobs, crawlers and triggers per workflow under 100.

Event-driven ingestion starts work when data arrives instead of on a clock: lower latency, no empty runs, and no guessing at when the upstream system finished.

S3 Event Notifications

A bucket can notify exactly four kinds of destination: an SNS topic (standard only, no FIFO), an SQS queue (no FIFO), a Lambda function, or EventBridge. SNS, SQS and Lambda destinations must be in the same Region as the bucket.

Filtering is prefix and suffix only — there is no wildcard. And there is a rule that trips up multi-pipeline buckets: for the same event type, configurations cannot have overlapping prefixes, overlapping suffixes, or overlapping prefix-and-suffix combinations. Overlapping prefixes are allowed only when the suffixes do not overlap, and a configuration with no filter acts as a root prefix that overlaps everything. Two suffixes overlap if one string can end with both: jpg and pg overlap, .jpg and .png do not. Overlapping filters are allowed across different event types.

Three things come free with this path: archive and replay (because the events are on the default bus), cross-account and cross-Region targets, and FIFO SQS as a destination, which direct S3 notifications cannot reach. Routing through EventBridge does not upgrade the delivery guarantee. The only guarantee AWS documents anywhere for S3 events remains at least once; claims of "100% reliable" delivery are marketing language, not documentation. Keep ingestion idempotent on bucket, key and version ID, tolerate out-of-order arrival, and reconcile periodically against S3 Inventory or a listing.

S3 itself provides strong read-after-write consistency for PUT and DELETE in all Regions, including overwrites, and for LIST and HEAD. So a consumer can always read the object a notification names — the uncertainty is in the notification layer, not in S3. Bucket configurations, by contrast, are eventually consistent.

Partial batch responses

Without ReportBatchItemFailures, one bad record fails the whole batch and the batch is retried in full — so good records are reprocessed repeatedly and the shard stalls. With it, the function returns the sequence numbers it could not handle and Lambda retries only from there.

Report only the failed records (Python) 
import base64, json

def handler(event, context):
    failures = []
    for rec in event["Records"]:
        k = rec["kinesis"]
        seq = k["sequenceNumber"]
        try:
            raw = base64.b64decode(
                k["data"])
            payload = json.loads(raw)
            process(payload)
        except Exception:
            failures.append(
                {"itemIdentifier": seq})
    # Lambda retries from the
    # lowest reported sequence number
    return {"batchItemFailures": failures}

On-failure destinations

When retries are exhausted, the ESM can send a record about the failed batch to SQS, SNS, S3 or a Kafka topic. What it sends differs, and the difference decides whether you can recover the data.

DestinationContent
SQS or SNSMetadata only — KinesisBatchInfo with shard ID, start and end sequence numbers, batch size and stream ARN. You replay from the stream by sequence number
Amazon S3The same metadata plus a payload field containing the records, written under aws/lambda/<ESM-UUID>/<shard>/YYYY/MM/DD/

With an SQS or SNS destination you must re-read the stream before retention expires — the metadata is a pointer, not the data. Note also that the Kinesis ESM parameters page still lists only SQS and SNS; S3 is supported and documented on the on-failure destination page.

Scaling, enhanced fan-out and provisioned mode

To give the function its own dedicated read throughput, point EventSourceArn at a stream consumer ARN instead of the stream ARN: the ESM then uses enhanced fan-out, with 2 MB/s per shard for this consumer alone.

Provisioned mode for event source mappings does not exist for Kinesis. It is available for Amazon MSK, self-managed Kafka and SQS only, where you set MinimumPollers and MaximumPollers and monitor ProvisionedPollers. For Kinesis, throughput is governed by shard count, parallelization factor and fan-out.

Combining enhanced fan-out with KPL aggregation has a sharp edge: records inside an aggregate whose partition key differs from the aggregate's key are dropped, and are not sent to the on-failure destination. Silent data loss, so keep aggregated records on one partition key.

Filter criteria work on the ESM too (five patterns by default, ten by quota increase), and for Kinesis the filter key is data. The ESM metrics worth alarming on are PolledEventCount, FilteredOutEventCount, InvokedEventCount, FailedInvokeEventCount, DroppedEventCount, OnFailureDestinationDeliveredEventCount and IteratorAge.

For DynamoDB Streams the parameters are nearly identical, with two differences: StartingPosition accepts only TRIM_HORIZON or LATEST (no AT_TIMESTAMP), and the on-failure destination is a standard SQS queue or standard SNS topic. Because polling start-up is eventually consistent, LATEST can miss events while the ESM is being created or updated — use TRIM_HORIZON if you cannot lose any.

Glue connections in a VPC

A Glue connection stores credentials, URI and VPC details in the Data Catalog and is reused by jobs and crawlers. It is required for JDBC, MongoDB, Atlas and DocumentDB sources, and a Network-type connection covers VPC-internal sources with no credentials.

The security group on a Glue connection needs a self-referencing inbound rule — type All TCP, protocol TCP, ports 0–65535, source set to that same security group ID. Glue's distributed workers must talk to each other; without this rule a job hangs or fails to start, and it is the most common Glue VPC misconfiguration. It does not open the VPC to anything else. Outbound needs either all traffic, or the same self-referencing rule plus HTTPS to the S3 gateway endpoint's prefix list. Also remember: "an ETL job can use JDBC connections within only one subnet."

MWAA has the same requirement — a self-referencing inbound rule allowing all traffic — plus a choice of routing. Public routing adds two public subnets, an internet gateway and a NAT gateway with an Elastic IP per public subnet. Private routing needs a VPC endpoint for every AWS service the DAGs use, with private DNS enabled, and no NAT or internet gateway route at all.

A static egress address

When a SaaS provider says "give us your IP address", the answer is a public NAT gateway. It must be given an Elastic IP at creation, and the internet gateway maps outbound traffic to that EIP — so everything leaving through it presents one stable address, while nothing can initiate a connection inwards.

A public NAT gateway only uses its Elastic IP as the source address when paired with an internet gateway in the same VPC. Traffic routed out through a transit gateway or virtual private gateway presents the NAT gateway's private IP instead, which breaks the allowlist. Private NAT gateways cannot have an Elastic IP at all.

The alternative to allowlisting is removing the public path entirely. Interface endpoints (AWS PrivateLink) create ENIs with private IPs in your subnets and accept security groups and endpoint policies; gateway endpoints exist only for S3 and DynamoDB, are route-table based, and take no security group.

Throttling and rate limits

Skill 1.1.9Implement throttling and overcoming rate limits (for example, DynamoDB, Amazon RDS, Kinesis).

Every ingestion target has a ceiling. The exam tests whether you can tell apart not enough capacity, capacity unevenly used, and a quota that needs raising — because the fix for each is different.

DynamoDB

The limit that explains most DynamoDB throttling is per partition, not per table: "every partition in a DynamoDB table is designed to deliver a maximum capacity of 3,000 read units per second and 1,000 write units per second". Item size feeds into that — a 20 KB item costs 5 RCUs strongly consistent, so around 600 reads per second of one item saturates its partition while the table looks idle.

Quota or behaviourValue
Per-table default40,000 read and 40,000 write units (on-demand or provisioned), adjustable

Two features exist specifically for bulk ingestion. Maximum throughput for on-demand tables (MaxReadRequestUnits and MaxWriteRequestUnits, added May 2024) bounds cost by throttling beyond a ceiling you set. Warm throughput (November 2024) reports what a table can absorb right now — DescribeTable returns WarmThroughput, which defaults to 12,000 read and 4,000 write units per second for a new table, rises automatically with usage, can never be decreased, and can be pre-warmed deliberately (at a charge) before a large load.

"We are loading 50 million rows tonight and the first minutes throttle" has three valid answers, and the question's wording picks one: pre-warm with warm throughput, ramp up traffic over 30 or more minutes so on-demand doubling keeps pace, or switch to provisioned capacity for the duration. Adaptive capacity applies in both modes and isolates frequently accessed items automatically, but it is not instant and will not rescue a genuinely hot key.

Batch writes need their own handling. BatchWriteItem takes up to 25 put or delete requests, 16 MB per call, 400 KB per item; it cannot update items and cannot use conditions. Crucially, throttled items come back in UnprocessedItems rather than as an error, and AWS "strongly recommends" an exponential backoff loop over them. BatchGetItem is 100 items and 16 MB, returning UnprocessedKeys.

Retry unprocessed items (Python) 
def write_all(table, items):
    req = {table: [
        {"PutRequest": {"Item": i}}
        for i in items]}
    delay = 0.05
    while req:
        r = ddb.batch_write_item(
            RequestItems=req)
        # throttled items return here,
        # not as an exception
        req = r.get(
            "UnprocessedItems") or {}
        if req:
            time.sleep(delay)
            delay = min(delay * 2, 10)

A silent data-loss bug: ignoring UnprocessedItems. The call returns HTTP 200, so nothing looks wrong, and the skipped items are simply never written.

Comparing ThrottledRequests against ReadThrottleEvents tells you what is throttling: a small number of requests with many events means one operation type is the culprit. Dimensioning on TableName alone excludes indexes — add GlobalSecondaryIndexName to see index throttling, which is a common cause of write throttling on an otherwise healthy table.

Kinesis

Kinesis throttling is almost always a hot shard: the partition key maps records unevenly, so one shard hits 1 MB/s or 1,000 records/s while the stream has capacity to spare. The guidance is to choose "a partition key that allows you to distribute put operations evenly across all shards" — high cardinality, no low-cardinality fields such as a status code or a day-rounded date.

MetricWatch it for
WriteProvisionedThroughputExceededProducers exceeding 1 MB/s or 1,000 records/s on a shard
ReadProvisionedThroughputExceededConsumers exceeding 2 MB/s or 5 reads/s on a shard
PutRecords.ThrottledRecordsHow many records inside batches were rejected
GetRecords.IteratorAgeMillisecondsConsumer lag — alarm on Maximum

A rounding detail with real consequences: PutRecord rounds each record up to the nearest KB, while PutRecords rounds the cumulative total. Six hundred records of 1.1 KB cost 600 KB in one PutRecords call but 1,200 KB as individual PutRecord calls. Batching is a throttling fix, not just an efficiency one. Shard-level metrics need EnableEnhancedMonitoring and cost extra.

Relational sources and Lambda

Relational databases run out of connections before they run out of CPU. Default max_connections is a formula on instance memory — PostgreSQL on RDS uses LEAST({DBInstanceClassMemory/9531392}, 5000), MySQL {DBInstanceClassMemory/12582880} — so a db.t3.micro allows around 60 connections. A hundred concurrent Lambda functions each opening a connection will exhaust that long before the database is busy.

Amazon RDS Proxy is the documented fix, in words that describe this exact pattern: "if your applications frequently open and close connections, or keep a large number of long-lived connections open, we recommend that you use Amazon RDS Proxy". It pools and multiplexes connections, caps its share with MaxConnectionsPercent, queues rather than oversubscribing, and holds connections through a failover.

Pinning is how RDS Proxy stops helping: when session state changes, the proxy ties the session to one connection and multiplexing stops. One documented trigger is size, not syntax — "any statement with a text size greater than 16 KB causes the proxy to pin the session". Generated bulk INSERT statements routinely exceed that.

On the Lambda side the ceiling is 1,000 concurrent executions per Region by default, with a per-function scaling limit of 1,000 new execution environments every 10 seconds. The documentation calls out the mismatch directly: API Gateway defaults to 10,000 requests per second while Lambda defaults to 1,000 concurrency. Throttled invocations appear as the Throttles metric and, importantly, "don't count as either Invocations or Errors" — so a dashboard watching only errors shows nothing while requests are being rejected.

Fan-in and fan-out

Fan-in is many producers into one stream; fan-out is one stream to many consumers. Both are usually limited by a quota rather than by throughput.

  --stream-arn \

The quota that bites is registered consumers per stream: 20 on On-demand Standard and Provisioned, or 50 with On-demand Advantage. Teams add consumers until they hit it. A SubscribeToShard subscription also lives only 5 minutes and must be renewed, at one call per second per consumer per shard.

Fan-in

The structural problem with many small producers is the 1,000 records per second per shard limit, which bites long before the 1 MB/s limit. The KPL solves it with two independent batching modes, both on by default:

KPL modeWhat it does
AggregationPacks many user records into one Kinesis record — 1,000 records of 512 bytes become 10 records of 50 KB, cutting record count by 100x. The KCL deaggregates transparently using checkpointSubSequenceNumber
CollectionSends many Kinesis records in one PutRecords request (500 records, 10 MiB)

Other fan-in paths: Firehose Direct PUT absorbs many producers at 500,000 records/s, 2,000 requests/s and 5 MiB/s in the largest Regions, and auto-raises throughput on sustained throttling, so keep retrying instead of giving up; that quota does not apply when the source is a Kinesis stream. The Kinesis Agent tails log files with checkpointing, file rotation and retries. And API Gateway's direct service integration is the no-Lambda front door for external producers.

Aggregation is the answer to "many tiny records are throttling the stream but total bytes are low". Note the interaction with enhanced fan-out: aggregated records whose inner partition key differs from the aggregate's key are dropped silently.

Replayability

Skill 1.1.11Describe replayability of data ingestion pipelines.

Replay is what lets you fix a bug and reprocess, add a consumer that needs history, or recover from a bad deployment. Whether you can replay is decided when you design the pipeline, not when you need it.

SourceReplay windowHow you replay
Kinesis Data Streams24 hours by default, up to 365 daysTRIM_HORIZON, AT_TIMESTAMP, or a sequence number
Amazon MSKlog.retention.hours; effectively unbounded with tiered storageauto.offset.reset=earliest, or reset the group's offsets

The architectural answer to replayability is the raw landing zone: write every ingested record to S3 unmodified before transforming it. Streams expire and schemas change, but a durable copy of the raw bytes makes every future reprocessing possible. Versioning plus S3 Object Lock protects it — GOVERNANCE mode can be bypassed with s3:BypassGovernanceRetention, while COMPLIANCE mode cannot be bypassed by anyone, including the root user.

DecreaseStreamRetentionPeriod "takes effect almost immediately". Lowering retention from 7 days to 24 hours discards six days of data straight away, with no confirmation step and no undo.

Replaying through EventBridge and SQS

An EventBridge archive captures events on a bus, optionally filtered by a pattern, and a replay sends them back. The constraints matter: a replay goes only back to the source bus, at most 10 concurrent replays per account per Region, replays are deleted after 90 days, a managed rule prevents replayed events re-entering the archive, and ordering is not preserved — replay works in one-minute buckets. Wait about 10 minutes before replaying recent events.

For SQS, the replay tool is the dead-letter queue: maxReceiveCount in the redrive policy decides when a message is moved aside, and DLQ redrive (console or StartMessageMoveTask) moves messages back to the source queue once the bug is fixed.

A standard queue preserves a message's original enqueue timestamp when it moves to the DLQ. If the DLQ's retention period is the same as the source queue's, messages can expire in the DLQ almost immediately — set DLQ retention longer than the source. FIFO queues reset the timestamp instead.

For Firehose, reprocessing depends on the error prefix. ErrorOutputPrefix must contain !{firehose:error-output-type}, whose values are processing-failed, format-conversion-failed, AmazonOpenSearchService-failed, splunk-failed and http-endpoint-failed. Set it and failures are quarantined in S3 by cause, ready to re-drive; leave it unset and the useful detail is lost. A Direct PUT stream also buffers undelivered data for 24 hours if the destination is down.

Stateful and stateless

Skill 1.1.12Define stateful and stateless data transactions.

A stateless operation produces its result from the input alone: parse a record, validate it, write it. A stateful operation needs something remembered across records or invocations: a running count, a window, a position in a stream, a de-duplication set. Stateless work scales trivially; stateful work needs somewhere durable to keep the state and a story for what happens when the worker dies.

Lambda is stateless

Execution environments are reused, so globals and /tmp often survive between invocations — but never for correctness. Ephemeral storage is 512 MB by default and configurable up to 10,240 MB; treat it as a scratch pad, and put anything that matters in DynamoDB, S3 or ElastiCache.

The exception is tumbling windows, where Lambda manages state for you — available for Kinesis and DynamoDB Streams only, with TumblingWindowInSeconds from 0 to 900.

A tumbling-window aggregation (Python) 
def handler(event, context):
    # state carried from the last
    # invocation in this window
    total = event.get("state", {}) \
                 .get("revenue", 0)

    for rec in event["Records"]:
        total += amount_of(rec)

    final = event.get(
        "isFinalInvokeForWindow")
    if final:
        publish_window_total(total)
        return {}

    # must return state or the
    # invocation counts as failed
    return {"state": {"revenue": total}}

The KCL lease table is worth knowing concretely: one row per shard, keyed by leaseKey (the shard ID), holding checkpoint (the last processed sequence number), leaseCounter and leaseOwner. KCL 3.x creates three tables — the lease table plus <App>-WorkerMetricStats and <App>-CoordinatorState — all on-demand capacity, none deleted automatically, and all requiring extra IAM permissions.

Two applications sharing a KCL application name share the lease table, so each steals the other's leases and neither processes the stream correctly. The name must be unique per consumer. And since the tables are never auto-deleted, decommissioned consumers leave DynamoDB tables (and bills) behind.

Flink checkpoints and snapshots

Amazon Managed Service for Apache Flink is the stateful streaming engine in scope. Checkpoints are automatic and service-managed: with ConfigurationType=DEFAULT, checkpointing is enabled with a 60-second interval and a 5-second minimum pause. Snapshots (savepoints) are manual, created with CreateApplicationSnapshot and restored through UpdateApplication.

ConfigurationType=DEFAULT overrides checkpoint settings made in your code or through the CLI. If your tuned checkpoint interval appears to be ignored, this is why — set ConfigurationType=CUSTOM.

Enabling snapshots is what gives exactly-once processing semantics across application updates, scaling and maintenance; without them, a restart loses state. End-to-end exactly-once still needs a transactional or idempotent sink.

Transactions

DynamoDB's TransactWriteItems is the all-or-nothing write: up to 100 actions over 100 distinct items, 4 MB aggregate, across tables in the same account and Region, with Put, Update, Delete and ConditionCheck actions. No two actions may target the same item, and indexes cannot be used.

Delivery semantics

The last piece of this skill is knowing what each service actually promises, because it decides whether your consumer needs deduplication.

Service or pathGuarantee
Kinesis Data StreamsAt-least-once; ordered within a shard
Amazon Data FirehoseAt-least-once except for S3, Apache Iceberg Tables and Snowflake
Lambda event source mappingAt-least-once — "duplicate processing of records can occur"
DynamoDB StreamsRecords appear exactly once in the stream, but Lambda consumption is still at-least-once
Kinesis Data Streams for DynamoDBAt-least-once and possibly reordered
SQS standardAt-least-once, best-effort ordering
SQS FIFOExactly-once processing within the 5-minute deduplication window, strict order per group
S3 Event NotificationsAt-least-once, unordered
Managed Service for Apache FlinkExactly-once within the application with snapshots enabled
Redshift streaming ingestionExactly-once
Apache KafkaAt-least-once by default; exactly-once with transactions and read_committed

Only three paths in this list give exactly-once: SQS FIFO within its window, Flink with snapshots, and Redshift streaming ingestion. Everything else needs the consumer to be idempotent. When a question says "records are appearing twice in the warehouse", the answer is almost never a service setting — it is a deduplication key.

Key takeaways

  • Kinesis Data Streams: shards at 1 MB/s or 1,000 records/s write and 2 MB/s read, records up to 10 MiB, PutRecords 500 records and 10 MiB. On-demand absorbs double the trailing peak; only provisioned mode allows resharding. Watch IteratorAgeMilliseconds (Maximum).
  • MSK: partitions cap consumer parallelism, consumer groups are fan-out. Serverless is IAM-only; tiered storage is provisioned Standard brokers only; Express brokers trade tuning for throughput and unlimited storage. Clusters auto-upgrade after a version's end of support.
  • DynamoDB Streams is 24 hours, per-item ordered, view type fixed at creation. Kinesis Data Streams for DynamoDB buys retention and fan-out but is at-least-once and can reorder.
  • Batch config: Glue bookmarks track sources only and reprocess modified S3 files; --enable-auto-scale turns NumberOfWorkers into a maximum; Flex is G.1X and G.2X only; Glue 5.1 is the default version and Glue 6.0 drops EMRFS; 2.0 and earlier are end of life.
  • DMS: migration type decides whether views move; Limited LOB mode truncates past LobMaxSize; validation needs a primary key and stops after 10,000 failures; CDC has no latency SLA.
  • Redshift COPY: files a multiple of the slice count, roughly equal, 1 MB to 1 GB compressed; manifests make loads deterministic; auto-copy tracks loaded files; streaming ingestion lands in a materialized view with no joins and needs AUTO REFRESH set.
  • APIs: paginate, use standard retries (adaptive only for bulk loaders), and give the Redshift Data API a stable ClientToken — Step Functions does not retry it by default.
  • Schedulers: EventBridge Scheduler for scale, time zones, flexible windows and retries (scheduled rules are now legacy); MWAA for DAGs with dependencies, triggered externally through InvokeRestApi; Glue triggers only fire on trigger-started runs; Step Functions .sync waits for a job and is Standard-only.
  • Triggers: S3 notifications filter by prefix and suffix only, cannot overlap within one event type, are at-least-once and unordered, and lifecycle deletes raise a different event. Routing through EventBridge removes the filter limits and adds archive, replay and FIFO targets.
  • Lambda from Kinesis is an event source mapping: batch size, batching window, parallelization factor, 6 MB payload cap, ReportBatchItemFailures, bisect on error. Provisioned mode does not exist for Kinesis; only an S3 on-failure destination carries the payload.
  • Network: self-referencing security group rules for Glue and MWAA; a public NAT gateway with an Elastic IP for a static egress address; prefix lists and ip-ranges.json instead of hard-coded CIDRs; Enhanced VPC Routing to force COPY traffic through the VPC.
  • Throttling: DynamoDB partitions cap at 3,000 RCU and 1,000 WCU, loop over UnprocessedItems, pre-warm or ramp for big loads, and use KeyRange throttle metrics to spot hot partitions. Kinesis throttling means a hot partition key. RDS Proxy for connection exhaustion — beware 16 KB statement pinning.
  • Replay: keep a raw landing zone in S3, extend retention before you need it, know that EventBridge replay is unordered and bounded to 10 concurrent, set DLQ retention longer than the source, and make every consumer idempotent — only SQS FIFO, Flink with snapshots and Redshift streaming ingestion are exactly-once.
