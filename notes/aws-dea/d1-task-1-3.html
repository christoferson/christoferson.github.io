Overview

Task 1.3

Orchestrate data pipelines.

Only four skills, but they sit on top of everything in Task 1.1 and Task 1.2. Ingestion and transformation are the steps; orchestration is what makes them a pipeline — what runs after what, what happens when a step fails, how you redeploy it safely, and who finds out.

Questions here usually describe a pipeline that half-worked: a job failed and the next one ran anyway, a transient error took down the whole run, a retry storm hammered a database, or nobody noticed for a day. The answer is almost always a specific setting in a specific orchestrator.

The examples continue the retail analytics platform in account 111111111111: a nightly pipeline that crawls new inventory files, runs a Glue job to curate orders, loads Redshift, and refreshes a dashboard — with alerts when any of it fails.

Orchestration services

Skill 1.3.1Use orchestration services to build workflows for data ETL pipelines (for example, Lambda, EventBridge, Amazon Managed Workflows for Apache Airflow [Amazon MWAA], AWS Step Functions, AWS Glue workflows).

Five named options with genuinely different shapes. Task 1.1 covered their scheduling side; this is the orchestration side — dependencies, error handling and state.

ServiceModelCost shape
AWS Step FunctionsA state machine: states, transitions, retries, catches, parallelismPer state transition (Standard) or per request plus duration (Express)

Lambda chaining is the wrong answer for orchestration whenever the question mentions visibility, dependencies or error handling. There is no state, no graph, no retry semantics you did not write yourself, and no place to see where a run got to. It appears in the skill statement as a building block, not as an orchestrator.

Step Functions: the error-handling model

This is the single densest exam area in the task. Every Task, Map and Parallel state can carry Retry and Catch.

Retry fieldDefaultEffect
ErrorEqualsRequiredWhich errors this retrier matches
IntervalSeconds1Delay before the first retry
MaxAttempts3Retries after the first failure; 0 means never retry
BackoffRate2.0Multiplier applied to each successive interval
MaxDelaySecondsNoneCaps exponential growth — without it there is no cap
JitterStrategyNONEFULL randomizes each interval between 0 and the computed value
Retry and catch around a Glue job (ASL) 
"CurateOrders": {
  "Type": "Task",
  "Resource":
    "arn:aws:states:::glue:startJobRun.sync",
  "Arguments": {
    "JobName": "curate-orders"
  },
  "Retry": [{
    "ErrorEquals": ["Glue.ConcurrentRunsExceededException"],
    "IntervalSeconds": 60,
    "MaxAttempts": 5,
    "BackoffRate": 2,
    // cap the wait and spread retries
    "MaxDelaySeconds": 600,
    "JitterStrategy": "FULL"
  }],
  "Catch": [{
    "ErrorEquals": ["States.ALL"],
    "ResultPath": "$.errorInfo",
    "Next": "NotifyFailure"
  }],
  "Next": "LoadRedshift"
}

Catch takes ErrorEquals, Next and ResultPath. Setting ResultPath matters: it defaults to $, which overwrites the entire state input with the error object, so the failure handler loses the context it needed. Point it at a child field instead, as above.

Predefined errorMeans
States.ALLAny error — must appear alone and last
States.TaskFailedA wildcard matching everything except States.Timeout
States.TimeoutThe task exceeded TimeoutSeconds or missed a heartbeat
States.HeartbeatTimeoutA heartbeat was not received in time
States.PermissionsThe execution role lacks a permission
States.DataLimitExceededState input or output exceeded 256 KiB
States.ExceedToleratedFailureThresholdA Distributed Map passed its tolerated failures
States.QueryEvaluationErrorA JSONata expression failed
States.RuntimeA problem in the state machine itself — never retriable

The rule that catches people out: States.ALL cannot catch States.DataLimitExceeded or States.Runtime. A payload that grows past 256 KiB therefore fails the execution outright no matter how carefully you wrote the catch block. Also note that Catch exists only on Task, Map and Parallel states — there is no execution-level catch. For whole-execution failure, wrap it in a parent state machine or react to the EventBridge status-change event.

The documented retry list for Lambda tasks is worth memorizing as a pattern: Lambda.ClientExecutionTimeoutException, Lambda.ServiceException, Lambda.AWSLambdaException and Lambda.SdkClientException, with IntervalSeconds: 2, MaxAttempts: 6 and BackoffRate: 2. Add Lambda.TooManyRequestsException for throttling and Lambda.Unknown or Sandbox.Timedout for runtime timeouts.

Timeouts and heartbeats

A detail with real consequences: activities, .sync waits and .waitForTaskToken callbacks have no default timeout. A stuck worker can hang an execution for up to a year, silently, because nothing has failed.

Set an explicit TimeoutSeconds on every Task, and set HeartbeatSeconds to something smaller than the timeout — it must be a positive integer less than TimeoutSeconds. The payoff is diagnostic: a heartbeat timeout means "the worker died", while a task timeout means "the job is genuinely slow". Those need different fixes. The HTTP Task is hard-capped at 60 seconds regardless.

The 256 KiB payload limit

Any state's input or output is capped at 256 KiB of UTF-8. This is the limit that breaks data pipelines, because it is tempting to pass a result set between states.

Never pass data through a state machine — pass pointers. Write the result to S3 and carry the object key. Beyond that, trim what you do carry with ResultSelector and OutputPath (JSONPath) or Output (JSONata), so a verbose service response does not accumulate through the workflow.

JSONata and variables

Since November 2024 a state machine or individual state can set QueryLanguage to "JSONata" instead of the default "JSONPath". JSONata replaces the five JSONPath fields (InputPath, Parameters, ResultSelector, ResultPath, OutputPath) with just Arguments and Output, and adds Assign for variables that later states can read — which removes most of the payload-threading that used to bloat state input.

JSONata with a stored variable (ASL) 
"RecordRunId": {
  "QueryLanguage": "JSONata",
  "Type": "Pass",
  // available to every later state
  "Assign": {
    "runId": "{% $uuid() %}",
    "loadDate": "{% $states.input.date %}"
  },
  "Next": "Curate"
}

Expressions go in {% %}, the .$ suffix disappears, and $states exposes .input, .result, .context and .errorOutput (in a catch). Step Functions adds helper functions including $partition, $range, $hash, $uuid and $parse. A failing expression raises States.QueryEvaluationError, which is both retriable and catchable.

Map, Parallel and concurrency

Inline MapDistributed Map
Concurrency40 iterations10,000 parallel child executions by default
Runs asStates inside this executionA separate child execution per iteration
HistoryCounts against the 25,000-event limitEach child has its own history
CostNo extra state transitionsOne state transition per iteration

Reach for Distributed Map when the data set exceeds 256 KiB, when history would pass 25,000 events, or when you need more than 40 concurrent iterations. Because it bills one transition per iteration, use ItemBatcher to group items per child — that is the difference between a million transitions and a few thousand.

ToleratedFailurePercentage defaults to 0, so a single failed item fails the whole Map Run with States.ExceedToleratedFailureThreshold. For a nightly job over thousands of files that is rarely what you want — set a tolerance and send the failures to S3 with ResultWriter.

Quotas that shape designs

The 25,000-event ceiling is the usual reason a long pipeline fails near the end. The two documented escapes are Distributed Map (children get their own histories) and nested state machines — a Task state that calls StartExecution on another state machine. The nested pattern also saves money: put short, idempotent, high-rate steps in an Express child inside a Standard parent.

Standard versus Express, and redrive

StandardExpress
SemanticsExactly-once per stepAt-least-once
Rate2,000 executions/s, 4,000 transitions/s100,000 executions/s, unlimited transitions
Pricing$0.000025 per state transition (4,000 free per month)$1.00 per million requests plus duration, billed in 64 MB memory chunks
Missing features—No .sync, no .waitForTaskToken, no activities, no redrive, no Distributed mode, and no history unless you configure CloudWatch Logs

Redrive (RedriveExecution) restarts a failed execution from the step that failed, keeping successful results. It is Standard only, works on executions that did not succeed, and must be used within 14 days of completion. It reuses the same execution ARN and name, resets per-state retry counters, and is billed as transitions.

Redrive reuses "the same definition/version/alias as the original attempt" — so if you fixed the bug by changing the state machine, redrive will not pick up the fix. Deploy the change and start a new execution instead. Express workflows cannot be redriven at all, which is a real argument for Standard in a nightly pipeline.

Express workflows keep no execution history: "GetExecutionHistory is unavailable for Express". Configure CloudWatch Logs or you are debugging blind. Log levels are ALL, ERROR, FATAL and OFF plus includeExecutionData, delivery is best-effort, and AWS recommends prefixing log groups with /aws/vendedlogs/states to stay inside the CloudWatch resource-policy character limit.

Amazon MWAA: the reliability knobs

Airflow's value for a data pipeline is that dependencies, retries and backfills are declarative DAG settings rather than code you write. These are the ones worth knowing by name.

SettingEffect
retries, retry_delayPer-task retries, with retry_exponential_backoff and max_retry_delay to spread them
execution_timeoutBounds each attempt; raises AirflowTaskTimeout, which is retryable
depends_on_pastRequires the same task in the previous run to have succeeded — the setting that stops a broken day cascading forward
max_active_runs, max_active_tasksCaps concurrency per DAG, protecting downstream systems
pool, pool_slotsA shared concurrency budget — the right way to limit how many tasks hit one database. default_pool has 128 slots
priority_weight, weight_ruleOrders contenders for a free slot; default weight 1, rules downstream (default), upstream or absolute
on_failure_callbackWhere an alert is raised from the DAG itself

AirflowFailException always skips the remaining retries — use it for errors that cannot succeed on a retry. And a sensor's own timeout raises AirflowSensorTimeout, which makes the sensor fail immediately without retrying, unlike a task timeout.

Trigger rules

A task's trigger_rule decides when it runs given its upstream states. The default is all_success; the full set is all_success, all_failed, all_done, all_done_setup_success, all_done_min_one_success, all_skipped, one_failed, one_success, one_done, none_failed, none_failed_min_one_success, none_skipped and always.

Two carry most of the weight in pipelines. all_done is the cleanup or notification task that must run whether the pipeline succeeded or not. none_failed_min_one_success is the join after a branch — exactly what you need when a BranchPythonOperator skipped some paths and you want the merge to proceed anyway.

Sensors and the triggerer

A sensor that waits for a file is the classic pipeline building block, and how it waits decides whether your environment scales.

ModeBehaviour
poke (default)Holds a worker slot for the entire wait — a handful of long sensors can starve the environment
rescheduleFrees the worker slot between checks, but only resumes on a timer
deferrable=TrueHands the wait to the triggerer: no worker slot and, by default, no pool slot, resuming when the condition is met. One triggerer handles 1,000 concurrent triggers

On MWAA the triggerer runs alongside the scheduler on the same Fargate task, so the only way to add deferral capacity is to raise the scheduler count (2 to 5). Deferral also requires class-based operators — a PythonOperator or TaskFlow function cannot defer. AWS deferrable operators need aiobotocore installed through requirements.txt.

Data-aware scheduling with assets

Instead of guessing that the upstream DAG finished by 02:00, a consumer DAG can be triggered by the data. A producer task declares outlets=[Asset(...)] and a consumer sets schedule=[asset].

Producer and consumer DAGs (Python, Airflow 3) 
from airflow.sdk import Asset, dag, task

curated = Asset(
    "s3://retail-lake/curated/orders/")

@dag(schedule="15 2 * * *", catchup=False)
def curate_orders():
    # marks the asset updated only
    # if this task succeeds
    @task(outlets=[curated])
    def write_curated():
        run_glue_job("curate-orders")
    write_curated()

# runs when the asset is updated
@dag(schedule=[curated], catchup=False)
def load_warehouse():
    @task
    def copy_to_redshift():
        run_copy()
    copy_to_redshift()

An asset is marked updated only if the producing task succeeds — which is exactly the dependency guarantee a time-based schedule cannot give. A list of assets is an implicit AND, and conditional expressions compose them: (a | (b & c)). Asset URIs are opaque, so there is no glob or regex matching; for S3 arrivals the pattern is S3 → EventBridge or SQS → an AssetWatcher, since there is no native "S3 event to asset" operator.

Airflow v2.4.3, v2.5.1 and v2.6.3 reached end of support on December 30, 2025.

XComs and passing data

XComs are "only designed for small amounts of data; do not use them to pass around large values, like dataframes". They default to storing values in the metadata database — which on MWAA is the Aurora PostgreSQL instance your whole environment depends on. Pass S3 URIs and metadata, and configure an object-storage XCom backend if you need more.

Sizing and monitoring MWAA

MWAA publishes two CloudWatch namespaces: AmazonMWAA for Airflow's own StatsD metrics, and AWS/MWAA for infrastructure. The saturation signals are the ones to alarm on.

MetricWhat it tells you
QueuedTasks rising with RunningTasks flatNot enough workers, or a pool or concurrency cap is binding
ApproximateAgeOfOldestTaskHow long work is sitting unstarted — the clearest backlog signal

TotalParseTime, ImportErrorsDAG files too slow or broken — a common cause of "my DAG never appeared"

There is one log group per enabled option, named airflow-<EnvName>-<LogType> for DAGProcessing, Scheduler, Task, WebServer and Worker. Workers scale on (running + queued) / tasks per worker between the minimum and maximum, and web servers scale out above 70% CPU or 15 active connections.

Provisioned MWAA has no scale-to-zero. The environment, its 2 included schedulers and its 2 included web servers bill by the hour whether or not a DAG runs — a small environment is roughly $449 a month, a large one roughly $1,047, before additional workers at $0.055 to $0.22 per hour. For a pipeline that runs for ten minutes a night, that baseline is the whole cost argument against Airflow.

MWAA Serverless now exists as a second deployment model: workflows authored in YAML or Python with "no Apache Airflow configuration required", run on demand or on a schedule, paying only for execution time with a one-minute minimum per task. The amazon provider ships matching operators (MwaaServerlessStartWorkflowRun and friends). It changes the cost argument above substantially — though at the time of writing there is no separate user guide, so treat the details cautiously.

Glue workflows and EventBridge

Glue workflows are the zero-extra-cost option when every step is a Glue job or crawler. Task 1.1 covered trigger types; the limits are what decide whether a workflow is viable.

Three documented Glue workflow constraints: keep total jobs, crawlers and triggers at or under 100 per workflow or resume and stop stop working; a run that would exceed the workflow concurrency limit is simply not started and is not retried; and a failed event-triggered run discards that batch of events. None of these is recoverable from inside the workflow, which is the practical reason to graduate to Step Functions or MWAA.

EventBridge alone is orchestration by implication: each step emits an event, the next reacts. It is cheap, decoupled and genuinely appropriate for event-driven ingestion — but there is no run, no state, no graph and no way to ask "did last night's pipeline finish?". Use it to start workflows and to react to their state changes, not as the workflow itself.

Choosing between them

There is no "Choosing an AWS orchestration service" decision guide. The closest official comparisons are "Choosing an AWS application integration service" (April 2025), which groups Step Functions and MWAA together under "Workflows" — "design, coordinate and manage workflows or sequences of tasks… handling dependencies and sequencing, allowing parallelism and conditional branching while providing fault tolerance, error handling, and retries" — and "Choosing an AWS serverless service" (refreshed September 2026), which maps orchestration to Step Functions and names Standard for "ETL pipelines" specifically.

CriterionStep FunctionsAmazon MWAA

BackfillNo primitive — restart executions, or Distributed Map over a date listFirst-class backfill and catchup

OperationsZero maintenanceVersion upgrades, pinned requirements, plugins, sizing
Integrations.sync for Glue, EMR, EMR Serverless, Athena, Batch, SageMaker, BedrockThe amazon provider's operators and sensors

Decide on the exam by the keywords. "Backfill", "reprocess historical dates", "existing Airflow DAGs", "complex cross-DAG dependencies", "Python" point to MWAA. "Serverless", "pay per use", "visual workflow", "no infrastructure to manage", "wait for a Glue job to finish", "retry with backoff" point to Step Functions. "Only Glue jobs and crawlers" points to Glue workflows.

A 2026 wrinkle worth knowing: Lambda now documents Durable Functions, which run multi-step workflows up to a year using checkpoints and replay — after an interruption the code reruns from the beginning but skips completed checkpoints, and its wait operations "suspend execution without incurring compute charges". AWS publishes a "Durable functions or Step Functions" comparison and still recommends Step Functions for cross-service orchestration, visual design and zero maintenance, with durable functions for application logic inside Lambda.

Availability: which services are multi-AZ

ServicePosture
Step Functions, Lambda, AWS Glue, SQS, SNS, EventBridgeRegional managed services — multi-AZ is handled for you
Amazon MWAARequires two private subnets in two different Availability Zones; that is how it rebuilds a container elsewhere if an AZ fails
Amazon EMRSingle-AZ — "the cluster can reside only in one Availability Zone or subnet"

EMR multi-primary HA does not mean multi-AZ. Three primary nodes give you resilience against a node failure, but all three sit in the same Availability Zone (EC2 placement groups keep them on distinct hardware). If a question asks how to survive an AZ failure with EMR, the answer is to run the job in another AZ or another Region, not to enable multiple primaries.

Retries, and retry amplification

Every layer retries, and that is the danger. A single transient fault can be multiplied through the stack: SNS retries AWS-managed endpoints 100,015 times over 23 days, Lambda asynchronous invocation retries twice by default, SQS redrives up to maxReceiveCount, Step Functions retries three times per retrier by default, and Airflow retries per task.

Multiply those together and a brief database blip becomes a sustained hammering — a retry storm that keeps the dependency down long after the original fault cleared. Bound every layer: MaxDelaySeconds and MaxAttempts in Step Functions, MaximumRetryAttempts and MaximumEventAgeInSeconds on event source mappings, maxReceiveCount on queues, and reserved concurrency on Lambda to cap how hard the pipeline can hit a downstream database at all.

Jitter is the documented antidote to synchronized retries: JitterStrategy: FULL "reduces simultaneous retry attempts by spreading these out over a randomized delay interval". Without it, every parallel branch retries at exactly the same moment. Combine BackoffRate for growth, MaxDelaySeconds for a ceiling, and FULL jitter for spread.

Dead-letter queues, layer by layer

"Where does a failed message go?" has a different answer per service, and the differences matter.

LayerFailure capture
Lambda async, legacy DeadLetterConfigA standard SQS queue or standard SNS topic (no FIFO). Carries only RequestID, ErrorCode and ErrorMessage — not the payload
Lambda on-failure destinationsSQS, SNS, S3, another Lambda function or EventBridge. A full JSON record with requestContext.condition (such as RetriesExhausted), approximateInvokeCount, the request payload and the response
Lambda event source mappingsOn-failure destinations for Kinesis, DynamoDB Streams and Kafka (see Task 1.1). For SQS sources, the DLQ goes on the queue, not the function
EventBridge rules and SchedulerAn SQS dead-letter queue per target or schedule
Amazon SNSA per-subscription redrive policy to an SQS queue in the same account and Region
Step FunctionsNo DLQ exists

Prefer on-failure destinations over the legacy Lambda DLQ. The documentation is explicit that destinations "support additional targets and include details about the function's response" — and crucially, only destinations carry the payload, so only destinations let you reprocess. The legacy DLQ gives you a request ID and a shrug.

Setting Lambda reserved concurrency to 0 sends new asynchronous events straight to the DLQ or on-failure destination with no retries at all. That is useful as a deliberate kill switch, and a nasty surprise if you did it to "pause" a function.

Because Step Functions has no DLQ, the substitutes are: a Catch into a failure-handling state, RedriveExecution within 14 days, Distributed Map's ToleratedFailureCount with a ResultWriter so failed items land in S3, and the EventBridge execution-status-change event for anything that escapes.

Idempotency and exactly-once

Retries mean steps run more than once, so correctness depends on idempotency rather than on hoping. The workflow type decides how much you need:

Step Functions Standard is exactly-once per step; Express is at-least-once. Idempotency is therefore mandatory for Express, and mandatory for any retried step in either. The techniques are the ones from Task 1.1: natural deduplication keys, DynamoDB conditional writes, and the Powertools idempotency utility.

Designing around quotas

A pipeline that works at pilot scale and fails in production is usually hitting a quota, not a bug. Service Quotas publishes usage into the AWS/Usage CloudWatch namespace, and metric math has a function for exactly this.

Alarm at 80% of a quota (metric math) 
# m1 is a usage metric from AWS/Usage
(m1 / SERVICE_QUOTA(m1)) * 100

SERVICE_QUOTA() "returns the service quota for the given usage metric… to set alarms that warn you when you approach the quota". Set the alarm's missing-data treatment to notBreaching, since usage metrics are sparse. Also check whether a quota is Adjustable before designing around a raise, and remember that an increase takes time to be granted — it is not a runtime remedy.

Disaster recovery for a data platform

ComponentCross-Region option
S3 data lakeCross-Region Replication, optionally with Replication Time Control
Amazon RedshiftCross-Region snapshot copy
Glue Data CatalogNo managed replication — re-crawl, or replicate the metadata yourself
Pipelines themselvesInfrastructure as code redeployed in the second Region (see serverless workflows)

For a data platform, backup and restore is usually the right DR strategy and the cheapest defensible answer: the data is in S3 with replication, the pipeline definitions are in code, and an RPO measured in hours is acceptable for analytics. Reserve pilot light or warm standby for pipelines that feed something operational. Keep the vocabulary straight — RPO is how much data you can afford to lose, RTO is how long you can afford to be down.

Testing before you deploy

The TestState API tests a single state without running the workflow, and it became substantially more capable in November 2025: it can now mock AWS service integrations and HTTP tasks, test Map, Parallel, Activity, .sync and .waitForTaskToken states, set the execution context (including a retry count), and assert on retryIndex, catchIndex and nextState.

Test a state with a mocked result (CLI) 
aws stepfunctions test-state \
  --definition file://curate-state.json \
  --input '{"date":"2026-11-06"}' \
  --mock '{"result":{"JobRunState":"SUCCEEDED"}}' \
  --inspection-level DEBUG

Inspection levels are INFO (default), DEBUG (which exposes the intermediate results after each JSONPath field, and for Map states after ItemsPath, ItemSelector and ItemBatcher) and TRACE (HTTP Task only). Status values are SUCCEEDED, FAILED, RETRIABLE and CAUGHT_ERROR — which is how you prove a retrier and a catcher actually fire. Mocking and Map or Parallel testing are CLI and SDK only; the console does not support them yet.

Step Functions Local is now explicitly labelled "unsupported" with no feature parity (its last build was 2.0.0 in May 2024). The documentation steers testing to TestState instead.

Safe deployment: versions and aliases

PublishStateMachineVersion creates an immutable numbered version, and an alias points to at most two versions with routing weights that must sum to 100 — which is how you do a canary or blue-green rollout of a pipeline.

Shift 10% of executions to a new version (CLI) 
aws stepfunctions update-state-machine-alias \
  --state-machine-alias-arn \
    arn:aws:states:eu-west-1:111111111111:stateMachine:nightly-etl:live \
  --routing-configuration '[
    {"stateMachineVersionArn":
      "arn:aws:states:eu-west-1:111111111111:stateMachine:nightly-etl:7",
     "weight": 90},
    {"stateMachineVersionArn":
      "arn:aws:states:eu-west-1:111111111111:stateMachine:nightly-etl:8",
     "weight": 10}
  ]'

Aliases cannot point to other aliases, and only two versions at a time. Calling StartExecution on the unversioned state machine ARN always uses the latest revision, bypassing your routing — so point schedulers and triggers at the alias, not at the bare state machine.

.waitForTaskTokenAnything external or human: the task pauses until SendTaskSuccess or SendTaskFailure arrives, with SendTaskHeartbeat to prove it is alive
ActivitiesWorkers that poll GetActivityTask — keep at least 100 open polls per activity ARN to avoid head-of-line blocking

Both callback patterns are Standard only. This is frequently what forces the workflow-type choice in a data pipeline: if you need to wait for a Glue job or an EMR step, you need Standard.

A customer managed key has a side effect that bites alerting: EventBridge execution-status-change events omit input, output, error and cause when a CMK is used. Any alert that quoted the error message from the event stops being useful — fetch the detail through the API instead. Also, disabling or deleting the key fails running executions and makes their data unrecoverable, and activities are immutable, so changing their encryption means creating a new resource.

Notifications

Skill 1.3.4Use notification services to send alerts (for example, Amazon SNS, Amazon SQS).

A pipeline that fails silently has failed twice. The pattern is almost always the same: a state change or metric becomes an EventBridge event or a CloudWatch alarm, which publishes to an SNS topic, which fans out to people and systems.

Pipeline events worth alerting on

Knowing the exact source and detail-type is what makes an EventBridge rule work first time.

Amazon SNS for alerts

SNS fans one message out to many subscribers. Three documented behaviours decide whether your alerting design is sound.

SNS FIFO topics deliver only to SQS queues. The documentation is explicit: FIFO topics "can't deliver messages to customer managed endpoints, such as email addresses, mobile apps, phone numbers for text messaging (SMS), or HTTP(S) endpoints… attempts to subscribe customer managed endpoints to SNS FIFO topics result in errors." So FIFO is not a general alerting option — and reaching Lambda from a FIFO topic needs an SQS queue in between.

Endpoint classRetry behaviour
AWS-managed (SQS, Lambda, Firehose)100,015 attempts over 23 days: 3 immediate, 2 pre-backoff at 1 s, 10 backoff from 1 to 20 s, then 100,000 at 20 s
Customer-managed (email, SMS, mobile push)50 attempts over 6 hours: 2 pre-backoff at 10 s, 10 backoff from 10 to 600 s, then 38 at 600 s
HTTP/SThe only protocol with a custom delivery policy — default 3 retries, up to 100, total retry time hard-capped at 3,600 s

SNS retries only 5XX and 429 responses; everything else is treated as permanent. Delivery status logging is available for Firehose, SQS, Lambda, HTTPS and mobile push endpoints — but not for email or SMS, which is exactly where you most want to know whether the alert arrived.

Email as an alert channel has sharp edges: the body cannot be customized, it is "intended to provide internal system alerts, not marketing", it works on standard topics only, and it is throttled to 10 messages per second per subscription — exceeding which auto-suspends the subscription for 30 days. A bounce suppresses the address for 7 days, and unconfirmed subscriptions are deleted after 48 hours. For anything formatted or high-volume, use SES instead.

Filtering so alerts stay useful

One topic per pipeline with filtered subscriptions beats a topic per alert type. FilterPolicyScope is MessageAttributes by default, or MessageBody to match on the payload itself.

Route only critical failures (subscription filter policy) 
{
  "pipeline": ["nightly-etl"],
  "severity": [
    {"anything-but": ["info"]}],
  "stage": [{"prefix": "prod"}]
}
ConstraintValue
Keys per policyAt most 5 (leaf keys only)
Value combinationsAt most 150 — the product of the array sizes
Operatorsexists, prefix, suffix, anything-but, equals-ignore-case, numeric ranges, cidr, wildcard, $or
NestingPayload-based filtering allows nested policies; attribute-based filtering does not, and ignores Binary attributes

Filter policy changes take up to 15 minutes to take effect. If you are testing a new filter and nothing matches, wait before concluding it is wrong. Note also that applying a filter policy to a FIFO topic turns exactly-once delivery into at-most-once.

Add an SNS subscription dead-letter queue (RedrivePolicy) to every alerting subscription. It captures both client-side errors that are never retried and server-side retries that were exhausted — otherwise an endpoint that was broken all night leaves no trace. Alarm on the DLQ's ApproximateNumberOfMessagesVisible and keep 14-day retention.

SQS in an alerting path

SNS to Lambda is push with no buffer, so a concurrency throttle or a poison message loses alerts. Putting SQS in between adds a durable buffer, consumer-paced retry, a visibility timeout and its own redrive — which is why "reliable alert processing" questions tend to end with a queue rather than a direct Lambda subscription.

CloudWatch alarms

Not every failure raises an event; some are the absence of success. That is an alarm's job. The documented alarm types are now metric, composite, PromQL and log alarms — the last being a scheduled Logs Insights query evaluated M out of N.

Missing data treatmentEffect
missingThe default — the alarm goes to INSUFFICIENT_DATA
notBreachingTreated as good; right for sparse usage and quota metrics
breachingTreated as bad — this is how you alarm on "the job did not run at all"
ignoreThe alarm keeps its current state

For a nightly pipeline, the most valuable alarm is often on absence: a metric that should be published once a night, with missing data treated as breaching. A pipeline that silently never started produces no failure event, so only this catches it.

Composite alarms exist to cut noise: their rules combine child alarm states with ALARM(), OK(), INSUFFICIENT_DATA(), AND, OR and NOT, and the documentation says plainly that "using composite alarms can reduce alarm noise". The actionsSuppressor field is the specific tool for "don't page me about every step when the whole platform is down". Composite alarms can trigger SNS, investigations, OpsItems and incidents, but cannot perform EC2 or Auto Scaling actions.

Alarm actions fire only on a state change, alarm history is retained 30 days, and alarm state changes reach EventBridge as source: aws.cloudwatch with detail type CloudWatch Alarm State Change — and that delivery is guaranteed, unlike most best-effort service events.

Key takeaways

  • Step Functions retry defaults: IntervalSeconds 1, MaxAttempts 3, BackoffRate 2.0, no MaxDelaySeconds cap and JitterStrategy NONE — so add a cap and full jitter deliberately. Catch's ResultPath defaults to $ and will overwrite your whole input.
  • States.ALL cannot catch States.DataLimitExceeded or States.Runtime, and there is no execution-level catch — use a parent state machine or the EventBridge status event. States.TaskFailed matches everything except States.Timeout.
  • Activities, .sync and .waitForTaskToken have no default timeout: set TimeoutSeconds on every task and HeartbeatSeconds below it, so "worker died" is distinguishable from "job is slow".
  • The 256 KiB state payload limit means passing S3 pointers, not data; the 25,000-event history limit means Distributed Map or nested state machines. Inline Map caps at 40 concurrent iterations, Distributed Map at 10,000 children and one state transition per iteration — batch with ItemBatcher.
  • Standard is exactly-once with .sync, callbacks and redrive; Express is at-least-once, five minutes, and has no history unless you configure CloudWatch Logs. Redrive reuses the original definition, so it will not pick up your bug fix.
  • MWAA gives what Step Functions cannot: first-class backfill, depends_on_past, pools, trigger rules (all_done for cleanup, none_failed_min_one_success for a branch join) and asset-based triggering, where an asset updates only if the producing task succeeds.
  • Use deferrable=True rather than poke-mode sensors; on MWAA the triggerer shares the scheduler's task, so more schedulers means more deferral capacity. Airflow 3 removed SLAs, renamed datasets to assets and defaults catchup to False; MWAA allows minor upgrades only, never 2.x to 3.x.
  • Provisioned MWAA never scales to zero, which is the whole cost case against it for short nightly pipelines. Glue workflows are free but capped at 100 nodes, and a run blocked by the concurrency limit is not started and not retried.
  • Resilience: everything retries, so bound every layer or a blip becomes a retry storm. Prefer Lambda on-failure destinations over the legacy DLQ because only they carry the payload; Step Functions has no DLQ — use Catch, redrive, and Distributed Map tolerances with a ResultWriter.
  • Availability: Step Functions, Lambda, Glue, SQS, SNS and EventBridge are Regional; MWAA needs two AZs; EMR is single-AZ, and multi-primary HA keeps all three primaries in that one AZ. Alarm near quotas with (m1 / SERVICE_QUOTA(m1)) * 100.
  • Maintenance: test states with TestState and mocks (Step Functions Local is unsupported); deploy with versions and an alias weighted across at most two versions summing to 100, and point triggers at the alias, not the bare ARN. A customer managed KMS key strips input, output and error from EventBridge events.
  • Alerting: know the event source and detail-type pairs; the Redshift Data API event needs WithEvent=true and MWAA emits no task-level events. SNS FIFO delivers only to SQS, email is capped at 10 messages per second with auto-suspension, filter policy changes take 15 minutes, and composite alarms with an actions suppressor are the documented way to cut noise.
