Task 4.3: Ensure data encryption and masking

Access control decides who may read data; encryption and masking decide what they see if they do — and what anyone sees who gets around the controls. This task covers hiding sensitive values from the people who should not see them, encrypting data with KMS, sharing encrypted data across accounts, and protecting data on the wire.

Overview

Task 4.3

Ensure data encryption and masking.

Four skills, each with many service-specific details. KMS is at the centre: almost every "encrypt this" answer is a KMS key, and almost every "it fails across accounts" answer is the wrong kind of key or a missing policy. Row and column filters (hiding data by access control) are on Task 4.2; finding PII with Macie is on Task 4.5.

The examples continue the retail analytics platform in account 111111111111: a payments table with card numbers in Redshift, a customers table in the lake, the retail-lake bucket encrypted with the customer managed key alias/retail-lake, and a partner analytics account, 444455556666.

Masking and anonymization

Skill 4.3.1Apply data masking and anonymization according to compliance laws or company policies.

TechniqueWhat it doesReversible?
Masking (full or partial)Shows XXXX-XXXX-XXXX-1234 instead of the card numberNot by the reader
HashingReplaces a value with a fixed digest; the same input gives the same output, so joins still workNo, but low-variety values (phone numbers, SSNs) can be guessed unless salted or keyed
TokenizationReplaces a value with a random token, mapped back in a secure vaultYes, through the vault
EncryptionScrambles data with a keyYes, by anyone with the key
Generalization and aggregationAge bands instead of birth dates, the first 3 ZIP digits, totals instead of rowsNo

Pseudonymized is not anonymized. Under GDPR, hashed or tokenized data that can still be linked back to a person remains personal data; only truly anonymous data falls outside its scope. Masking and hashing reduce risk and exposure, but the dataset usually still needs to be protected and governed.

Redshift dynamic data masking

Dynamic data masking (DDM) masks values at query time according to the user's role, without changing the stored data. Superusers and sys:secadmin create and attach policies. When several policies apply to a column, the one with the highest priority wins.

Card numbers: hidden, last 4, or clear by role 
-- everyone: fully masked
CREATE MASKING POLICY mask_card_full
WITH (card VARCHAR(19))
USING (
  'XXXX-XXXX-XXXX-XXXX'::VARCHAR(19));

-- analysts: last four digits
CREATE MASKING POLICY mask_card_last4
WITH (card VARCHAR(19))
USING (('XXXX-XXXX-XXXX-'
  || RIGHT(card, 4))::VARCHAR(19));

-- auditors: the real value
CREATE MASKING POLICY card_clear
WITH (card VARCHAR(19))
USING (card);

ATTACH MASKING POLICY mask_card_full
ON payments(card_no) TO PUBLIC;

ATTACH MASKING POLICY mask_card_last4
ON payments(card_no)
TO ROLE analyst PRIORITY 20;

ATTACH MASKING POLICY card_clear
ON payments(card_no)
TO ROLE auditor PRIORITY 50;
  • The policy's output type must match the column (and fit its length). Expressions can call SQL or Lambda UDFs; avoid Python UDFs, which are unsupported after June 30, 2026.
  • Conditional masking uses other columns in the expression — for example, mask a value only when is_fraud is false.
  • Paths inside SUPER columns can be masked.
  • Row-level security is applied before masking. Two policies on the same column cannot share a priority, and the PUBLIC policy must have the lowest.

DDM and data sharing do not mix: a table with an attached masking policy cannot be added to a datashare, and attaching a policy to an already shared table breaks consumer queries. DDM also cannot be attached to external tables (Spectrum), system tables or temporary tables.

Finding and masking PII in Glue jobs

The Glue Detect Sensitive Data transform finds personal data in a DataFrame during ETL, using hundreds of managed entity types (names, emails, card numbers, national IDs by country, HIPAA identifiers) plus custom regex patterns with optional context words.

ChoiceOptions
Scan modeDetect PII in each cell (all rows), or detect fields containing PII (sample rows, then label whole columns past a threshold)
ActionDetect only (add a results column), redact, partial redact, or SHA-256 hash — one masking action per column
SensitivityHigh (the console default) or low
ScopeInclude or exclude columns, and a different action per entity type
Hash SSNs, partly redact phone numbers 
{
  "USA_SSN": [{
    "action": "SHA256_HASH",
    "sourceColumns": ["ssn"]
  }],
  "PHONE_NUMBER": [{
    "action": "PARTIAL_REDACT",
    "sourceColumns": ["phone"],
    "actionOptions": {
      "numLeftCharsToExclude": 1,
      "numRightCharsToExclude": 0,
      "redactChar": "*"
    }
  }]
}

Detection runs inside the job and is billed as normal job time. Masking in the pipeline means the curated zone never holds the raw values at all, which is stronger than masking at query time.

Masking with SQL views

A view can expose a pseudonymized copy of a table. Use a keyed hash (HMAC) or a secret salt, so nobody can rebuild the mapping by hashing every possible value.

Athena: a pseudonymized customer view 
CREATE VIEW retail.customers_pseudo AS
SELECT
  to_hex(hmac_sha256(
    to_utf8(email),
    to_utf8('<secret-key>'))) AS email_id,
  substr(zip, 1, 3) AS zip3,
  lifetime_value
FROM retail.customers;
Redshift: salted SHA-256 
SELECT SHA2('<salt>' || email, 256)
  AS email_hash
FROM customers;

Grant analysts the view, not the base table. A secret written into a view definition is visible to anyone who can read the view's DDL, so keep the key in a restricted UDF or apply hashing in the pipeline.

Other places to mask

  • Lake Formation column exclusion and cell filters hide columns entirely (Task 4.2).
  • Glue DataBrew recipes mask, hash, shuffle or encrypt columns for analyst-prepared data (Task 3.1).
  • CloudWatch Logs data protection masks sensitive data in logs (Task 3.3).
  • Quick Sight column-level security shows restricted values as "Not Authorized".
  • Bedrock Guardrails can block or anonymize PII in model input and output, as {NAME} or {EMAIL}.
  • AWS Clean Rooms lets partners analyze combined data without sharing raw rows, with analysis rules, cryptographic computing and differential privacy.

Choose by where the raw value may exist. Must never land in the lake → mask or hash in the Glue job. Some roles need the real value → Redshift DDM or Lake Formation filters. Two companies want joint insight without sharing rows → Clean Rooms.

Encryption keys

Skill 4.3.2Use encryption keys to encrypt or decrypt data (for example, AWS KMS).

Kinds of KMS key

KeyWho controls itRotationCost
AWS ownedThe service, in its own account; you never see itBy the serviceFree
AWS managed (aws/s3, aws/rds...)AWS, in your account; you can see its policy but not change itEvery year, fixedNo monthly fee; requests billed
Customer managedYou: key policy, grants, rotation, deletionOptional, configurable$1 per key-month plus requests

AWS managed keys are a legacy type, no longer created for new services since 2021, and they cannot be used across accounts. Choose a customer managed key whenever you need control over who uses the key, cross-account sharing, custom rotation, or a key you can disable in an emergency.

  • Key specs: symmetric (AES-256, the default and what data services use), asymmetric (RSA, ECC and post-quantum ML-DSA and ML-KEM) and HMAC.
  • Multi-Region keys share key material and ID (mrk- prefix) across Regions, so data encrypted in one Region decrypts in another; each replica has its own policy. A single-Region key cannot be converted.
  • Imported key material (bring your own key) and custom key stores (CloudHSM or an external key manager) serve stricter compliance requirements.

Envelope encryption

KMS Encrypt accepts at most 4 KB of data. Larger data uses envelope encryption: GenerateDataKey returns a data key in plaintext and encrypted form; you encrypt the data locally with the plaintext key, throw it away, and store the encrypted key next to the data. To decrypt, KMS decrypts the data key. This is what S3, Redshift, EBS and the Encryption SDK do under the hood.

Envelope encryption by hand (Python) 
import os
import boto3
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

kms = boto3.client("kms")
ctx = {"dataset": "orders"}

dk = kms.generate_data_key(
    KeyId="alias/retail-lake",
    KeySpec="AES_256",
    EncryptionContext=ctx)

nonce = os.urandom(12)
ciphertext = AESGCM(dk["Plaintext"]) \
    .encrypt(nonce, b"rows", None)
# store ciphertext, nonce and the
# encrypted key dk["CiphertextBlob"]
del dk["Plaintext"]

The encryption context is a set of non-secret key-value pairs bound to the ciphertext: decryption must supply exactly the same pairs. It appears in CloudTrail (so never put secrets in it) and can be required in key policies, which makes it useful for auditing and for limiting a key to one dataset. In practice, use the AWS Encryption SDK rather than hand-written envelope code.

Who may use a key

  • Every KMS key has exactly one key policy. The default policy gives the account root principal full access, and that statement is what lets IAM policies grant use of the key — remove it and IAM allows stop working.
  • IAM policies then grant use to roles, for example kms:Decrypt on the key ARN.
  • Grants give temporary, narrow permissions, mostly used by services such as EBS, RDS and Redshift on your behalf.
  • Condition keys narrow use: kms:ViaService (only through S3 in this Region, for example), kms:CallerAccount, and kms:EncryptionContext:....

Rotation and deletion

  • Automatic rotation for customer managed symmetric keys is off by default; when on, the period is configurable from 90 to 2,560 days (default 365, since April 2024). On-demand rotation rotates immediately without changing the schedule.
  • Rotation creates new key material but keeps the old material to decrypt existing data; the key ID and ARN do not change, and existing data is not re-encrypted.
  • Each rotation adds $1 a month for the first two rotations only, so a key costs at most $3 a month. Asymmetric and HMAC keys are rotated manually (a new key plus an alias change).
  • Deletion waits 7 to 30 days (default 30) and is irreversible afterwards; data encrypted under a deleted key is lost. Disable the key instead if you might need it back.
  • The shared request quota for symmetric operations is 10,000 per second by default (20,000 or 100,000 in the largest Regions), and cross-account calls count against the caller's account.
A lake key with 180-day rotation 
aws kms create-key \
  --description "retail lake" \
  --key-spec SYMMETRIC_DEFAULT \
  --key-usage ENCRYPT_DECRYPT

aws kms create-alias \
  --alias-name alias/retail-lake \
  --target-key-id "$KEY_ID"

aws kms enable-key-rotation \
  --key-id "$KEY_ID" \
  --rotation-period-in-days 180

Amazon S3

Every new object has been encrypted with SSE-S3 since January 2023. Options are SSE-KMS (your KMS key, with CloudTrail records of key use and control through the key policy), DSSE-KMS (two layers, for strict compliance) and SSE-C (keys you supply on each request).

Default SSE-KMS with an S3 Bucket Key 
aws s3api put-bucket-encryption \
  --bucket retail-lake \
  --server-side-encryption-configuration \
    file://encryption.json
encryption.json 
{
  "Rules": [{
    "ApplyServerSideEncryptionByDefault": {
      "SSEAlgorithm": "aws:kms",
      "KMSMasterKeyID":
        "alias/retail-lake"
    },
    "BucketKeyEnabled": true
  }]
}
  • S3 Bucket Keys cut KMS request costs by up to 99%. The encryption context becomes the bucket ARN instead of the object ARN, so update any policies written against object ARNs. Bucket Keys do not work with DSSE-KMS and apply only to new objects.
  • To force a specific key, deny PutObject when s3:x-amz-server-side-encryption-aws-kms-key-id is missing or different.
  • Changing default encryption does not re-encrypt existing objects; copy them (for example with S3 Batch Operations) to apply it.

Since April 2026, SSE-C is disabled by default on new general purpose buckets (and on existing buckets in accounts with no SSE-C objects): SSE-C uploads get 403 until you unblock it with BlockedEncryptionTypes. Athena and EMR never supported SSE-C.

Across accounts

Skill 4.3.3Configure encryption across AWS account boundaries.

Sharing encrypted data means sharing the key as well as the data. Two rules cover almost every case.

  1. Use a customer managed key. AWS managed keys cannot be shared: their policies cannot be edited, so "you cannot share resources encrypted under an AWS managed key with other accounts".
  2. Allow it on both sides. The key policy in the owning account must allow the other account (who can use the key), and an IAM policy in the other account must allow its role (who does). "Neither... alone is sufficient."
Key policy statement in 111111111111 
{
  "Sid": "AllowPartnerAccount",
  "Effect": "Allow",
  "Principal": {
    "AWS":
      "arn:aws:iam::444455556666:root"
  },
  "Action": [
    "kms:Decrypt",
    "kms:DescribeKey"
  ],
  "Resource": "*"
}
IAM policy on the partner's role in 444455556666 
{
  "Effect": "Allow",
  "Action": [
    "kms:Decrypt",
    "kms:DescribeKey"
  ],
  "Resource":
    "arn:aws:kms:us-east-1:111111111111:key/<key-id>"
}
  • The caller must name the key by its full ARN; an alias resolves in the caller's own account.
  • Only cryptographic and grant operations work across accounts; administrative actions such as scheduling deletion do not.
  • CloudTrail records the call in both accounts, and the request counts against the caller's KMS quota.

Service by service

SharingWhat it takes
S3 objects with SSE-KMSBucket policy plus the key policy and IAM permission for kms:Decrypt; a customer managed key referenced by full ARN
S3 replication of SSE-KMS objectsOpt in with SseKmsEncryptedObjects and give a ReplicaKmsKeyID in the destination Region; the replication role needs kms:Decrypt on the source key and kms:Encrypt on the destination key. A wrong key is not rejected at setup — replication just fails
RDS and Aurora snapshotsCannot share snapshots encrypted with aws/rds. Copy the snapshot under a customer managed key whose policy allows the target account, share it, and let the target copy it under its own key

Redshift: copy encrypted snapshots to us-west-2 
# run in the destination Region
aws redshift create-snapshot-copy-grant \
  --snapshot-copy-grant-name dr-grant \
  --kms-key-id "$DR_KEY_ID" \
  --region us-west-2

# run in the source Region
aws redshift enable-snapshot-copy \
  --cluster-identifier retail-dw \
  --destination-region us-west-2 \
  --snapshot-copy-grant-name dr-grant

For cross-Region rather than cross-account, services usually need a key in the destination Region (S3 replication, RDS copies, Redshift snapshot copy). Multi-Region keys help most with client-side encryption, where the same key material must decrypt in another Region.

In transit and before transit

Skill 4.3.4Enable encryption in transit or before transit for data.

All AWS API endpoints require TLS 1.2 or later (TLS 1.0 and 1.1 ended in February 2024), and SDKs use HTTPS by default. The work is in the connections you configure: clients to databases, clients to brokers, and nodes to each other.

Requiring TLS on each service

ServiceHow to require encryption in transit
Amazon S3Bucket policy denying aws:SecureTransport false (Task 4.2); s3:TlsVersion sets a minimum version
Amazon RedshiftParameter require_ssl — true by default in the current default parameter group (since January 2025); clients use sslmode=verify-full
RDS PostgreSQLrds.force_ssl — 1 by default from PostgreSQL 15, 0 on older versions
RDS MySQLrequire_secure_transport — off by default
Amazon MSKClient-broker TLS (default), TLS_PLAINTEXT or PLAINTEXT; in-cluster encryption on by default; TLS 1.3 policies available for provisioned clusters
OpenSearch Service"Require HTTPS" plus node-to-node encryption, which cannot be turned off once enabled and is required for fine-grained access control
Amazon EMRIn-transit encryption in a security configuration, with certificates from EMR or a PEM file in S3
Glue JDBC connectionsJDBC_ENFORCE_SSL (Task 2.2)
DynamoDB, Kinesis, FirehoseHTTPS endpoints only — nothing to configure
Require TLS on Redshift and Aurora PostgreSQL 
aws redshift \
  modify-cluster-parameter-group \
  --parameter-group-name retail-dw-pg \
  --parameters \
    '[{"ParameterName": "require_ssl",
       "ParameterValue": "true"}]'

aws rds modify-db-cluster-parameter-group \
  --db-cluster-parameter-group-name \
    retail-orders-pg \
  --parameters \
    '[{"ParameterName": "rds.force_ssl",
       "ParameterValue": "1",
       "ApplyMethod": "immediate"}]'
MSK: encrypted at rest and in transit 
{
  "EncryptionAtRest": {
    "DataVolumeKMSKeyId": "<key-arn>"
  },
  "EncryptionInTransit": {
    "InCluster": true,
    "ClientBroker": "TLS"
  }
}

In S3 bucket policies, aws:SecureTransport and s3:TlsVersion are not present on some service-to-service calls, so a blanket deny can break AWS services writing to the bucket. AWS suggests adding "aws:PrincipalIsAWSService": "false" to such deny statements.

Hybrid links add their own encryption: Site-to-Site VPN uses IPsec, and Direct Connect supports MACsec on supported dedicated connections. PrivateLink keeps traffic on the AWS network, and TLS still applies on top.

Encrypting before transit

Client-side encryption encrypts data before it leaves the application, so the storage service only ever holds ciphertext — "plaintext data isn't available to any third party, including AWS". Use it when a policy says no service, operator or administrator may see the data in clear.

LibraryUse for
AWS Encryption SDKGeneral-purpose envelope encryption with KMS keyrings, encryption context and data key caching (which avoids KMS throttling)
Amazon S3 Encryption ClientEncrypting objects client-side for S3 (current major version 4, for Java and Go). Athena can read its output (CSE-KMS); it cannot read Encryption SDK output
AWS Database Encryption SDK (formerly the DynamoDB Encryption Client)Encrypting and signing individual DynamoDB attributes, with searchable encryption through beacons

Client-side encryption costs features: services cannot index, query, compress or scan what they cannot read. AWS recommends SSE-KMS over client-side encryption for Athena query results, and Athena's CSE-KMS has no cross-Region support. Encrypt client-side only the fields or datasets that truly need it.

Key takeaways

  • Masking hides values, hashing keeps joins (salt or key it), tokenization is reversible through a vault, encryption is reversible with a key. Pseudonymized data is still personal data under GDPR.
  • Redshift dynamic data masking: policies attached to roles with priorities (highest wins, PUBLIC lowest), applied after row-level security, managed by superusers or sys:secadmin. Masked tables cannot go into datashares.
  • Glue Detect Sensitive Data: managed and custom entity types, per-cell or sampled column detection, and one masking action per column (redact, partial redact, SHA-256). Masking in the pipeline keeps raw values out of the lake.
  • KMS keys: AWS owned (free, invisible), AWS managed (yearly rotation, not shareable), customer managed (full control, $1 a month, at most $3 with rotations). The default key policy's root statement is what makes IAM policies work.
  • Encrypt takes 4 KB; larger data uses envelope encryption with data keys. The encryption context must match on decrypt and is logged. Rotation is configurable from 90 to 2,560 days, keeps old material, and never re-encrypts data; deletion waits 7–30 days.
  • S3: SSE-S3 by default; SSE-KMS with Bucket Keys (up to 99% fewer KMS calls, bucket-ARN encryption context); SSE-C blocked by default on new buckets since April 2026. Redshift can encrypt an existing cluster; RDS only at creation; DynamoDB always; Glue jobs through security configurations; Athena results through the workgroup.
  • Across accounts: a customer managed key, allowed in the key policy and by IAM in the other account, named by full ARN. RDS snapshots cannot be shared under aws/rds; Redshift snapshot copy needs a copy grant in the destination Region; cross-account datashares need encryption on both sides.
  • In transit: TLS 1.2 minimum on all AWS APIs; Redshift require_ssl now true by default; rds.force_ssl default on PostgreSQL 15+, MySQL require_secure_transport off by default; MSK TLS client-broker by default; OpenSearch node-to-node encryption cannot be undone.
  • Before transit: the AWS Encryption SDK, the S3 Encryption Client (readable by Athena as CSE-KMS) and the AWS Database Encryption SDK for DynamoDB — when even AWS must never see plaintext.
