Overview

Task 1.1

Design architectures built for the cloud.

Professional questions describe a whole system with several constraints at once (ordering per customer, exactly-once payments, a partner account that must receive events, a burst of traffic, tenants that must never see each other's data) and offer four designs that each satisfy most of them. The right one meets every constraint with the least operational overhead. This page builds on the Associate-level patterns in the SAA notes on loosely coupled architectures and the Developer notes, and concentrates on the trade-offs between options.

Running example. The company from the SAA notes has grown: dozens of accounts in AWS Organizations, a web application and mobile API on ECS and EKS, Aurora PostgreSQL, an SQS-based order pipeline, a Kinesis clickstream, a SaaS reporting product sold to business customers, and partner accounts that receive order events. Account 111111111111 is the production orders account; primary Region us-east-1, recovery Region us-west-2.

Status changes to know. AWS App Mesh reached end of support on 30 September 2026; AWS points ECS users to ECS Service Connect and EKS users to Amazon VPC Lattice. EventBridge relaunched its custom event bus (September 2026) with ordering and deduplication; the earlier one is now "Custom Event Bus - Classic". Lambda durable functions arrived in December 2025, ECS Managed Instances in September 2025, CloudFront multi-tenant distributions (SaaS Manager) in April 2025, and EventBridge direct cross-account targets in January 2025. Message size limits rose to 1 MiB for SQS (2025) and SNS (2026), 10 MiB per record for Kinesis, and 1 MB for EventBridge events.

Event-driven messaging

Skill 1.1.1Design event-driven architectures that use appropriate messaging patterns such as idempotency, ordering, and delivery guarantees (for example, by using Amazon EventBridge, Amazon SQS FIFO queues and standard queues, Amazon SNS, Amazon Kinesis with partition keys).

  • SQS standard: nearly unlimited throughput, at-least-once delivery and best-effort ordering. Fair queues (July 2025) use the message group ID on a standard queue to stop one noisy tenant delaying everyone else.
  • SQS FIFO: strict order per message group ID and exactly-once processing through a deduplication ID (or content-based deduplication) within a 5-minute window. Throughput is lower than standard (higher with high-throughput mode), so spread work over many group IDs.
  • SNS: fan-out to many subscribers; FIFO topics keep order and deduplicate into FIFO queues (with a subscription filter policy, delivery becomes at-most-once).
  • EventBridge: content-based routing with rules, at-least-once delivery, retries for up to 24 hours (185 attempts) and a dead-letter queue. The new custom event bus adds FIFO subscribers ordered per event group and deduplication.
  • Kinesis Data Streams: the partition key decides the shard, and order holds per key within a shard; many consumers can replay the stream; plan for duplicates from producer and consumer retries.
  • Idempotency everywhere: at-least-once means duplicates will arrive. Make consumers idempotent with a deduplication record (for example a conditional write to DynamoDB keyed by message or order ID; Powertools for AWS Lambda has an idempotency utility for this).
Keep each customer's order events in order and drop duplicates (Python, boto3) 
import json

import boto3

sqs = boto3.client("sqs")
sqs.send_message(
    QueueUrl="https://sqs.us-east-1.amazonaws.com/111111111111/order-events.fifo",
    MessageBody=json.dumps({"orderId": "o-1001", "status": "PAID"}),
    MessageGroupId="customer-48213",          # order is kept per customer, not globally
    MessageDeduplicationId="o-1001-PAID",     # a retry within 5 minutes is dropped
)

A single message group ID for all messages makes a FIFO queue process one message at a time. A constant deduplication ID drops everything after the first message. For SQS with Lambda, set the queue's visibility timeout to at least six times the function timeout (Lambda now rejects a trigger whose function timeout is longer than the visibility timeout) and use a redrive policy with a maxReceiveCount of at least 5.

Stateless applications

Skill 1.1.2Design stateless applications that use externalized state management (for example, by using Amazon DynamoDB, Amazon S3, Amazon ElastiCache).

Instances, tasks and functions that keep no state can be replaced, scaled and spread across Availability Zones freely. Move the state out:

  • Sessions and short-lived state: ElastiCache (Valkey or Redis OSS) for sub-millisecond reads; ElastiCache Serverless removes capacity planning (one endpoint, Multi-AZ, 99.99% availability SLA, billed per GB stored and per ECPU). DynamoDB with a TTL attribute for durable sessions; TTL deletes can take a few days, so filter expired items when reading.
  • Durable application state: DynamoDB for key-value access at any scale; conditional writes give optimistic locking (update only if the version you read is still current).
  • Files and large objects: S3, referenced by key from the database.
  • Cache or database? MemoryDB is a durable, Redis-compatible primary database; ElastiCache is a cache (node-based ElastiCache for Valkey 9.0 and later can add an optional durability log, so read the answer options carefully).
Update a cart only if nobody changed it since it was read (AWS CLI) 
aws dynamodb update-item \
    --table-name Carts \
    --key '{"cartId":{"S":"c-48213"}}' \
    --update-expression "SET items = :items, version = :next" \
    --condition-expression "version = :read" \
    --expression-attribute-values '{":items":{"L":[]},":next":{"N":"8"},":read":{"N":"7"}}'
# ConditionalCheckFailedException means someone else wrote first: re-read and retry

Optimistic locking doesn't work across DynamoDB global tables, which resolve concurrent writes with "last writer wins". A conditional write that checks the attribute it updates is idempotent; an atomic counter (SET n = n + :one) is not.

Serverless data pipelines

Skill 1.1.3Design serverless data processing and analysis pipelines (for example, by using Amazon Kinesis Data Streams, AWS Glue, Amazon Athena, AWS Lambda).

  • Ingest: Kinesis Data Streams in on-demand mode (no shard planning; the On-demand Advantage option from November 2025 suits steady high volumes) or provisioned mode; Data Firehose to land data in S3, Iceberg tables or S3 Tables without code; Amazon MSK Serverless when producers already speak Kafka.
  • Process: Lambda for light per-record or per-batch work; AWS Glue (serverless Spark) for heavy batch or streaming ETL.
  • Query: Athena over S3 (columnar formats and partitions cut cost; workgroups separate teams and limits; federated queries reach other databases).
  • Lambda with Kinesis: a parallelization factor (1 to 10 concurrent batches per shard) adds throughput while keeping order per partition key; bisect batch on error, maximum retries and an on-failure destination stop one bad record blocking a shard; tumbling windows aggregate over time.
Consume the clickstream with more parallelism and poison-record handling (AWS CLI) 
aws lambda create-event-source-mapping \
    --function-name clickstream-enricher \
    --event-source-arn arn:aws:kinesis:us-east-1:111111111111:stream/clickstream \
    --starting-position LATEST \
    --batch-size 500 \
    --parallelization-factor 4 \
    --bisect-batch-on-function-error \
    --maximum-retry-attempts 3 \
    --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:us-east-1:111111111111:clickstream-failed"}}'

The Data Engineer notes go deeper on Kinesis, Glue and Athena; Task 1.5 covers lakehouse and analytics design.

Durable workflows

Skill 1.1.4Design multi-step workflows that have durable execution patterns (for example, by using AWS Step Functions, durable Lambda functions).

  • Step Functions Standard: up to a year per execution, exactly-once state transitions, full history, waits for a task token (human approval, external systems), retries and catches per state, redrive from the failed state, Distributed Map for large fan-out. Billed per state transition.
  • Step Functions Express: up to 5 minutes, at-least-once, billed per request and duration, for high-volume short workflows; no task-token waits.
  • Lambda durable functions (December 2025): the workflow is ordinary code. Each step is checkpointed, and wait or wait_for_callback suspends the function without paying for compute, for up to a year (asynchronous invocation; synchronous calls are limited to 15 minutes). Durable execution must be enabled when the function is created, steps run at least once (so make them idempotent), and failures go to a DLQ (destinations aren't supported).
  • Which: AWS suggests durable functions for code-first, Lambda-centred logic owned by developers, and Step Functions for orchestrating many AWS services, visual workflows reviewed by non-developers, and minimal code; combining them is common.
An order-approval workflow as a durable function (Python, Lambda durable execution SDK) 
from aws_durable_execution_sdk_python import DurableContext, WaitConfig, durable_execution

@durable_execution
def lambda_handler(event, context: DurableContext):
    order = context.step(lambda _: reserve_stock(event["orderId"]), name="reserve-stock")
    # Suspends until a person approves (or 24 hours pass); no compute is billed while waiting
    decision = context.wait_for_callback(send_approval_request, name="manager-approval",
                                         config=WaitConfig(timeout=86400))
    if decision["approved"]:
        context.step(lambda _: charge_card(order), name="charge-card")  # must be idempotent
    return {"orderId": event["orderId"], "approved": decision["approved"]}

Create it with aws lambda create-function ... --durable-config '{"ExecutionTimeout": 86400, "RetentionPeriodInDays": 14}' and invoke a version or alias, not the unqualified name. Starting two executions with the same DurableExecutionName returns the existing one, which makes the start idempotent.

Cross-account and cross-Region events

Skill 1.1.5Implement cross-account and cross-Region event routing patterns that use event buses and event forwarding.

  • Bus to bus: a rule in the sending account targets an event bus in another account or Region; the receiving bus's resource policy allows events:PutEvents, often for the whole organization with aws:PrincipalOrgID. New cross-account bus targets need an IAM role in the sending account. The sender pays.
  • No second hop: an event forwarded from account A to account B isn't forwarded again to account C (nor between three buses in one account), so design hub-and-spoke: producers send to a central bus whose rules deliver to each consumer.
  • Direct cross-account targets (January 2025): a rule can deliver straight to an SQS queue, SNS topic, Lambda function, Kinesis stream or API Gateway in another account, with a role in the sender and a resource policy on the target, without a receiving bus.
  • New custom event bus (September 2026): shared with other accounts through AWS RAM, in the same Region only.
  • Regional failover: EventBridge global endpoints (Classic buses) fail producers over to a bus with the same name in a second Region using a Route 53 health check, with optional replication of events back to the primary; recovery takes about 6 minutes.
  • Archive and replay to reprocess past events into the same bus after a fix (not in original order).
Let every account in the organization send events to the central bus (Python, boto3) 
import boto3

boto3.client("events").put_permission(
    EventBusName="central-orders",
    Action="events:PutEvents",
    Principal="*",
    StatementId="AllowOrgAccounts",
    Condition={"Type": "StringEquals", "Key": "aws:PrincipalOrgID", "Value": "o-a1b2c3d4e5"},
)
# Rules on the central bus should match on the "account" field; "*" in a pattern never matches

Container orchestration

Skill 1.1.6Design container orchestration for microservices by using managed services (for example, Amazon EKS, Amazon ECS, AWS Fargate).

  • Amazon ECS: AWS-native and simpler; the default when there's no Kubernetes requirement.
  • Amazon EKS: when the organization standardises on Kubernetes, needs its ecosystem (Helm, operators) or portability.
  • Where tasks run: Fargate (no instances to manage; on EKS up to 16 vCPU and 120 GB per pod, no Fargate Spot, no EKS Pod Identity); ECS Managed Instances (September 2025: AWS-managed EC2 capacity for ECS, with instance type choice and GPUs, but no custom AMIs or SSH); EC2 capacity providers for full control; EKS Auto Mode, where AWS runs the nodes (Bottlerocket, replaced at least every 21 days), load balancing, storage, networking and upgrades, built on Karpenter.
  • Permissions for pods: EKS Pod Identity (simpler, no OIDC provider per cluster) or IAM roles for service accounts (IRSA, still needed on Fargate).

"Least operational overhead for containers, no Kubernetes needed" points to ECS on Fargate. "Kubernetes, but AWS should manage the nodes and add-ons" points to EKS Auto Mode. "GPU or specific instance types without managing EC2" points to ECS Managed Instances.

Service-to-service networking

Skill 1.1.7Design service mesh architectures that facilitate microservice communication and observability (for example, by using Amazon VPC Lattice, Amazon ECS Service Connect).

  • ECS Service Connect: service discovery and a managed proxy (injected into each task) for ECS-to-ECS traffic, using a Cloud Map namespace: retries, outlier detection, optional TLS with AWS Private CA, and per-service traffic metrics in CloudWatch (HTTP metrics need appProtocol on the port mapping). No extra charge beyond the proxy's resources. Namespaces can be shared across accounts in a Region through RAM (September 2025), but the VPCs still need connectivity.
  • Amazon VPC Lattice: an application networking layer across VPCs and accounts for ECS, EKS (through the Gateway API controller), EC2 and Lambda, with no VPC peering or Transit Gateway needed between them. Service networks group services and are shared with RAM; services have listeners (HTTP, HTTPS, TLS), rules and weighted target groups; auth policies (IAM, requests signed with SigV4) allow or deny each call; overlapping CIDRs are fine. TCP resources such as an RDS database are reached through resource configurations and a resource gateway. Billed per service-hour, per GB and per request.
  • Choosing: Service Connect for ECS services in one namespace; Lattice for mixed compute, many accounts and VPCs, and IAM-based authorization between services; PrivateLink to expose one service to consumers without network-level access.
Only principals in the organization may call services in the network (JSON, VPC Lattice auth policy) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "vpc-lattice-svcs:Invoke",
    "Resource": "*",
    "Condition": {"StringEquals": {"aws:PrincipalOrgID": ["o-a1b2c3d4e5"]}}
  }]
}

With IAM auth turned on and no auth policy attached, VPC Lattice denies all traffic; the caller's identity policy, the service network policy and the service policy must all allow the call. App Mesh is past end of support: questions that offer it for new designs are wrong.

Container images

Skill 1.1.8Manage container images by configuring security scans and lifecycle policies (for example, by using Amazon ECR).

  • Scanning: basic scanning (OS packages, on push) or enhanced scanning with Amazon Inspector (OS and language packages, re-scanned continuously as new CVEs are published, findings sent to EventBridge and Security Hub). Set it once at the registry level for all repositories.
  • Lifecycle policies expire or archive untagged and old images automatically; tag immutability stops a release tag being overwritten.
  • Replication copies images to other Regions (for recovery and lower pull latency) and other accounts; only the destination registry needs a policy allowing it. Replication copies only new pushes (a backfill option arrived in October 2026), goes one hop, and doesn't copy repository settings, which come from repository creation templates.
  • Pull-through cache mirrors public registries (and other ECR registries) into your account, so builds don't depend on the internet.

Configuration examples are in the MLA-C02 notes on containers; Task 5.2 covers scanning in CI/CD pipelines.

Auto scaling patterns

Skill 1.1.9Design auto scaling patterns for serverless and containerized workloads (for example, by using Lambda concurrency, Horizontal Pod Autoscaler, Cluster Autoscaler, Amazon ECS service auto scaling, AWS Application Auto Scaling).

  • Lambda: each function scales by 1,000 execution environments every 10 seconds, up to the account limit. Reserved concurrency guarantees and caps a function's share (free; 0 stops it); provisioned concurrency keeps environments initialized for predictable latency (billed, needs a version or alias, and can itself be autoscaled on utilisation).
  • ECS service auto scaling (Application Auto Scaling): target tracking on CPU, memory or ALB requests per target, step and scheduled scaling, and predictive scaling (November 2024) that forecasts from history and scales ahead of daily peaks. Pair predictive with target tracking, since it never scales in on its own. Scale-in pauses during deployments.
  • EKS: two layers. Pods scale with the Horizontal Pod Autoscaler (or KEDA for queue or event-driven scaling); nodes scale with Karpenter (fast, chooses instance types to fit pending pods; best for varied or spiky workloads), Cluster Autoscaler (scales node groups), or EKS Auto Mode (Karpenter managed by AWS).
  • Queues: scale workers on backlog per task (queue depth divided by running tasks) rather than CPU.
Forecast daily peaks for the API service, in forecast-only mode first (JSON, ECS predictive scaling policy) 
{
  "MetricSpecifications": [{
    "TargetValue": 50,
    "PredefinedMetricPairSpecification": {"PredefinedMetricType": "ECSServiceCPUUtilization"}
  }],
  "SchedulingBufferTime": 600,
  "MaxCapacityBreachBehavior": "HonorMaxCapacity",
  "Mode": "ForecastOnly"
}

Attach it with aws application-autoscaling put-scaling-policy --service-namespace ecs --resource-id service/prod-cluster/orders-api --scalable-dimension ecs:service:DesiredCount --policy-type PredictiveScaling --predictive-scaling-policy-configuration file://policy.json, then switch Mode to ForecastAndScale once the forecast looks right (it needs at least 24 hours of history).

Ingress patterns

Skill 1.1.10Design ingress patterns and optimize resources for specific usage patterns (for example, Application Load Balancer, Network Load Balancer, AWS Load Balancer Controller, Amazon API Gateway).

  • Application Load Balancer (layer 7): routing on host, path, headers, method and query; weighted target groups for canaries; user sign-in with Cognito or OIDC; JWT validation for service-to-service calls (November 2025); host and URL rewrites (October 2025); and Target Optimizer, which caps concurrent requests per target for LLM and GPU inference (November 2025).
  • Network Load Balancer (layer 4): TCP, UDP and TLS at very high throughput, static IPs per Availability Zone, client IP preservation, and the front of a PrivateLink endpoint service; it can sit in front of an ALB to give it static IPs.
  • Gateway Load Balancer: inserts firewalls and inspection appliances transparently (Task 1.4).
  • API Gateway: REST APIs for API keys and usage plans per client, caching, request validation, AWS WAF, private APIs and response streaming; HTTP APIs are cheaper and simpler with a native JWT authorizer. The 29-second integration timeout can be raised for Regional and private REST APIs.
  • Kubernetes: the AWS Load Balancer Controller turns an Ingress (or Gateway) into an ALB and a LoadBalancer Service into an NLB; use IP targets to route straight to pods (required on Fargate). EKS Auto Mode has this built in.
Require sign-in through Cognito before reaching the reporting service (JSON, ALB listener rule actions) 
[
  {"Type": "authenticate-cognito", "Order": 1,
   "AuthenticateCognitoConfig": {
     "UserPoolArn": "arn:aws:cognito-idp:us-east-1:111111111111:userpool/us-east-1_AbCdEf123",
     "UserPoolClientId": "4h57kxmplexample",
     "UserPoolDomain": "reports-login",
     "OnUnauthenticatedRequest": "authenticate"}},
  {"Type": "forward", "Order": 2,
   "TargetGroupArn": "arn:aws:elasticloadbalancing:us-east-1:111111111111:targetgroup/reports/0123456789abcdef"}
]

ALB authentication works only on HTTPS listeners, and the targets receive the user's claims in the signed x-amzn-oidc-data header (verify the signer). Without the AWS Load Balancer Controller, Kubernetes creates a Classic Load Balancer; with it, NLBs default to the internal scheme.

Edge architectures

Skill 1.1.11Design edge architectures to meet latency requirements (for example, by using Amazon CloudFront Functions, Lambda@Edge).

  • CloudFront Functions: lightweight JavaScript on viewer request and viewer response only, sub-millisecond, millions of requests per second, cheapest. For URL rewrites and redirects, header manipulation, cache key normalisation, simple token checks, A/B routing and, since 2024 and 2025, choosing or changing the origin. They can read CloudFront KeyValueStore (up to 5 MB per store) for redirect tables or feature flags. No network calls or request bodies.
  • Lambda@Edge: Node.js or Python on all four events (viewer and origin, request and response), up to 30 seconds, with network access and request bodies: for calls to other services, complex authentication or generating responses. It's deployed from us-east-1 as a numbered version, and has no VPC access, environment variables, layers or arm64.
  • Caching and origins: Origin Shield adds one regional caching layer to protect the origin; VPC origins put a private ALB or instance behind CloudFront without public exposure; multi-tenant distributions (SaaS Manager) serve many customer domains from one template, each tenant with its own certificate and WAF settings.
Send mobile users to the mobile origin path at the edge (JavaScript, CloudFront Function, viewer request) 
function handler(event) {
    var request = event.request;
    var device = request.headers['cloudfront-is-mobile-viewer'];
    if (device && device.value === 'true' && request.uri.indexOf('/m/') !== 0) {
        request.uri = '/m' + request.uri;  // rewrite before the cache lookup
    }
    return request;
}

The device header must be included in the cache policy or origin request policy for the function to see it.

WebSocket and pub/sub

Skill 1.1.12Design architectures that support real-time data processing by using WebSocket and publish-subscribe patterns (for example, by using API Gateway WebSocket APIs).

  • API Gateway WebSocket APIs: clients keep a connection open; messages route by a field in the body to $connect, $disconnect, $default or custom routes; authorization happens on $connect only. Your backend stores connection IDs (usually in DynamoDB) and pushes messages through the @connections API. Connections last at most 2 hours and close after 10 minutes idle; messages up to 128 KB (32 KB frames); the 29-second integration timeout can't be raised.
  • AWS AppSync Events (October 2024): managed WebSocket pub/sub with channels and wildcard subscriptions, so there is no connection table to build; handlers can filter or transform events.
  • AppSync GraphQL subscriptions when the application already uses a GraphQL data model.
  • SNS and EventBridge for server-side fan-out to queues and functions (not to browsers).
Push an order status update to a connected customer (Python, boto3) 
import json

import boto3

ws = boto3.client("apigatewaymanagementapi",
                  endpoint_url="https://a1b2c3d4e5.execute-api.us-east-1.amazonaws.com/prod")
try:
    ws.post_to_connection(ConnectionId=connection_id,
                          Data=json.dumps({"orderId": "o-1001", "status": "SHIPPED"}).encode())
except ws.exceptions.GoneException:
    remove_connection(connection_id)  # the client has disconnected; $disconnect is best-effort

Multi-tenant isolation

Skill 1.1.13Design multi-tenant architectures that use tenant isolation patterns (for example, siloed or pooled resources, Amazon Cognito tenant context, row-level security, tenant-specific encryption).

  • Models (AWS SaaS Lens): silo gives each tenant dedicated resources (an account, a database or a stack); pool shares resources and isolates in software; bridge mixes them (for example premium tenants siloed). Identity, onboarding and operations stay shared in every model.
  • Tenant context: put the tenant ID in the user's token. Cognito supports a pool per tenant, an app client per tenant, groups, an immutable custom attribute, or custom scopes; a pre token generation trigger (version 2 for users, version 3 for machine-to-machine) adds claims to access tokens. AWS notes custom attributes alone aren't strong isolation.
  • Enforce isolation in the data layer, not just in application code: DynamoDB fine-grained access with dynamodb:LeadingKeys matched to the caller's tenant tag (scoped credentials from STS with a tenant session tag); PostgreSQL row-level security policies on a tenant column; per-tenant S3 prefixes with ABAC.
  • Tenant-specific encryption: a KMS key per tenant for siloed or premium tiers (separate key policy, tenant can be revoked), or a shared key with the tenant ID in the encryption context, enforced with the kms:EncryptionContext:tenantId condition.
  • Noisy neighbours: API Gateway usage plans per tenant tier, SQS fair queues, Lambda reserved concurrency per tier.
Tenant-scoped credentials can touch only that tenant's items (JSON, IAM policy statement) 
{
  "Effect": "Allow",
  "Action": ["dynamodb:GetItem", "dynamodb:Query", "dynamodb:PutItem", "dynamodb:UpdateItem"],
  "Resource": "arn:aws:dynamodb:us-east-1:111111111111:table/ReportData",
  "Condition": {
    "ForAllValues:StringEquals": {"dynamodb:LeadingKeys": ["${aws:PrincipalTag/TenantID}"]},
    "Null": {"dynamodb:LeadingKeys": "false"}
  }
}

ForAllValues is true when the key is missing (a Scan has no partition key), so add the Null check and never grant Scan. PostgreSQL row-level security is bypassed by superusers and by the table owner unless FORCE ROW LEVEL SECURITY is set, so connect as a non-owner role. Encryption context is logged in plain text in CloudTrail: never put secrets in it.

Key takeaways

  • Messaging: SQS standard is at-least-once; FIFO orders per group and deduplicates in 5 minutes; Kinesis orders per partition key; EventBridge routes by content with retries and a DLQ; every consumer must be idempotent.
  • State: externalize sessions to ElastiCache (Serverless for no capacity planning) or DynamoDB with TTL; optimistic locking with conditional writes (not across global tables).
  • Pipelines: Kinesis or Firehose in, Lambda or Glue to process, Athena to query; parallelization factor, bisect on error and failure destinations for Lambda stream consumers.
  • Workflows: Step Functions Standard for long, audited, service-orchestrating flows, Express for high-volume short ones; Lambda durable functions for code-first workflows with checkpoints and long waits.
  • Event routing: hub-and-spoke buses (events don't chain twice), org-wide bus policies, direct cross-account targets, global endpoints for Regional failover, archive and replay.
  • Containers: ECS by default, EKS for Kubernetes; Fargate, ECS Managed Instances or EKS Auto Mode to hand compute management to AWS; Pod Identity except on Fargate.
  • Service networking: Service Connect inside ECS, VPC Lattice across compute types, VPCs and accounts with IAM auth policies; App Mesh is gone.
  • Scaling: Lambda reserved and provisioned concurrency; ECS target tracking plus predictive; EKS needs both a pod scaler (HPA, KEDA) and a node scaler (Karpenter, Auto Mode).
  • Ingress and edge: ALB for layer 7 and sign-in, NLB for static IPs and PrivateLink, REST API Gateway for usage plans and WAF; CloudFront Functions for cheap viewer logic, Lambda@Edge for heavier work.
  • Real time and tenancy: WebSocket APIs with a connection table, or AppSync Events for managed pub/sub; silo, pool or bridge with tenant context in tokens and isolation enforced in IAM, the database and encryption.
