Task 2.5: Design security and responsible AI controls

Keeping the GenAI support assistant safe and accountable: filtering what goes in and comes out of every model call across the organization, giving each agent its own identity and only the tools and data the user is allowed, and putting a person in the loop before the agent does anything that costs money or can't be undone.

Overview

Task 2.5

Design security and responsible AI controls.

Professional questions here test where a control sits and whether it can be bypassed: a guardrail the caller chooses versus one the organization enforces, an agent acting as itself versus on behalf of the user, an approval an LLM decides versus one a deterministic rule decides. How the services work in detail is on the service pages for Bedrock Guardrails and AgentCore Gateway, Identity and Policy; the multi-account AI layout is on Task 1.2, and invocation logging on Task 2.3.

Running example. The support assistant runs in the agent platform account (333333333333) on AgentCore Runtime, calls models through the central GenAI account (222222222222), and reaches order tools (look up orders, issue refunds, update addresses) through an AgentCore Gateway. Customers sign in with Cognito; support staff sign in through Identity Center. Refunds over $500 need a human.

Status changes to know. Bedrock Agents is now Agents Classic and closed to new customers (30 July 2026), so its user confirmation and return-of-control features aren't the answer for new builds, even though some AWS guidance still cites them. New: Guardrails Standard tier (June 2025), Automated Reasoning checks (generally available August 2025), the bedrock:GuardrailIdentifier condition key (March 2025), account-level and Organizations-enforced guardrails (April 2026), InvokeGuardrailChecks for agent loops (June 2026), AgentCore Policy (generally available March 2026, with guardrail conditions from June 2026 and Dogwood as the recommended policy language), and AgentCore Identity on-behalf-of token exchange (April 2026) and consent portal (September 2026).

Content filtering and enforcement

Skill 2.5.1Implement content filtering and compliance controls for generative AI services (for example, by using Amazon Bedrock Guardrails).

  • What a guardrail checks: content filters (hate, insults, sexual, violence, misconduct) and prompt attacks (jailbreaks, prompt injection, and prompt leakage on the Standard tier); denied topics; word filters; sensitive information (PII types and regex, blocked or masked); contextual grounding (is the answer supported by the retrieved source and relevant to the question); and Automated Reasoning checks against a formal policy (detect only).
  • Tiers: the Standard tier handles more languages, typos and code, and is the recommended one, but it requires a cross-Region guardrail profile, so prompts may be processed elsewhere in the geography. Classic covers English, French and Spanish only.
  • Roll out safely: start filters in detect mode (action NONE, findings only in the trace), tune strengths, then switch to block. Publish numbered versions; production should call a version, not the draft.
  • Where it runs: on Converse and InvokeModel calls, inside knowledge base and agent calls, or standalone with ApplyGuardrail for any model, including models outside Bedrock. Guardrails don't check tool results, tool arguments or retrieved chunks, so agent loops should call ApplyGuardrail or InvokeGuardrailChecks on untrusted tool output (indirect prompt injection).
  • Making it mandatory, from weakest to strongest:
    • Developer's choice: the application passes a guardrail on each call.
    • IAM: the bedrock:GuardrailIdentifier condition key requires a specific guardrail and version on model calls.
    • Account-level enforced guardrail: applies to every call in the account and Region.
    • Organizations Bedrock policy: attaches a management-account guardrail to every member account. It can't be removed by the member, and it evaluates all content regardless of input tags (comprehensive mode).
  • Layers combine: organization, account and request guardrails all run, and the most restrictive result wins. Monitor interventions with CloudWatch guardrail metrics and ApplyGuardrail data events in CloudTrail.

      }
    }

}

With the IAM condition alone, a caller can still skip input checks by wrapping only harmless text in guardrail input tags; an enforced guardrail in comprehensive mode closes that gap. The IAM condition also breaks roles used for RetrieveAndGenerate or agent calls, which make internal model calls without a guardrail, so give those their own roles. Every caller needs bedrock:ApplyGuardrail on an enforced guardrail, or all its model calls fail. Masked PII still appears unmasked in the trace and in invocation logs, and the bedrock-mantle endpoint has no guardrails.

Access control for AI applications and agents

Skill 2.5.2Implement access controls for generative and agentic AI applications (for example, by using Amazon Bedrock AgentCore Identity).

  • Who may call the agent (inbound): AgentCore Runtime and Gateway accept SigV4 (IAM) or OAuth tokens from your IdP (Cognito, Okta, Entra ID) through a JWT authorizer that checks issuer, audience or client, scopes and custom claims. A gateway with no authorizer (or authenticate-only) does no authorization, so add a policy engine or interceptor.
  • Agent identity: every runtime and gateway gets a workload identity. When a user calls in with a JWT, AgentCore issues a workload access token bound to the agent and that user, so downstream credentials are always tied to both.
  • What the agent may reach (outbound): credential providers in the token vault hold OAuth clients and API keys (secrets in Secrets Manager, tokens encrypted with KMS), so agent code never stores secrets.
    • M2M (client credentials): the agent acts as itself.
    • User federation (three-legged OAuth): the user consents once to, say, their calendar.
    • On-behalf-of token exchange: the user's token is exchanged for a narrower one for the downstream API, so the downstream system enforces the user's own permissions.
  • Which tools, with which arguments: AgentCore Policy attaches a policy engine to the gateway and evaluates every tool call outside the model, with Cedar or Dogwood policies on the principal (JWT claims or IAM role), the tool and its input. It's default deny and forbid wins; temporal conditions (for example, only after an approval in this session) and guardrail scores can be part of a rule.
  • Data access: knowledge base metadata filters or document-level ACLs per user, trusted identity propagation for Lake Formation-governed data (Task 2.1), and tenant-scoped IAM credentials in multi-tenant agents.
  • AWS credentials: the runtime's execution role and the gateway's service role are the ceiling of what any user can make the agent do; keep them least privilege and split gateways by trust boundary.
AgentCore Policy (Cedar): support staff may refund up to $500 through this gateway; nothing else is permitted 
permit (
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"OrdersTarget___issue_refund",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-east-1:333333333333:gateway/support-gw-a1b2c3d4e5"
)
when {
  principal.hasTag("role") && principal.getTag("role") == "support" &&
  context.input.amount <= 500
};

A policy engine in ENFORCE mode with no permit policies denies every tool call: start in LOG_ONLY. Anyone with bedrock-agentcore:UpdateGateway can switch the mode or detach the engine, so treat that permission as privileged. GetWorkloadAccessTokenForUserId trusts any user ID string; prefer the JWT variant and deny the user-ID call where it isn't needed. Listing a tool doesn't mean the call will be allowed; every call is evaluated.

Human oversight and approvals

Skill 2.5.3Design human oversight workflows that include approval mechanisms for AI operations (for example, by using AWS Step Functions).

  • Tier by risk, deterministically: read-only actions run on their own, low-risk writes need one reviewer, and financial transactions, deletions and external messages need stricter approval. The classification must come from rules or a policy engine, never from an LLM that has read the same untrusted input (Agentic AI Lens AGENTSEC04-BP02, rated high risk).
  • Step Functions callback pattern: a Standard workflow task with .waitForTaskToken sends a task token through SNS, email or a webhook to an approval app and pauses (at no compute cost) until the app calls SendTaskSuccess or SendTaskFailure. Set TimeoutSeconds or HeartbeatSeconds with a Catch that escalates or blocks: on timeout the safe answer is no. Express workflows don't support task tokens.
  • Several approvers: Parallel branches send blind requests to each reviewer, and a Lambda function checks consensus (unanimous for two, majority with escalation for three or more), with reviewers from Identity Center (AGENTSEC07-BP03).
  • Inside the agent: AgentCore harness hooks (beforeToolCall returning allow or deny), MCP elicitation through the gateway, or a temporal AgentCore Policy that permits a payout only after an approval event in the same session. AgentCore Runtime async tasks can wait while the session reports busy, but Runtime sessions end after 8 hours, so approvals that may take days belong in Step Functions (up to a year) or Lambda durable functions.
  • Accountability: store the full decision context in S3 before asking the reviewer, log who approved what and when, and keep invocation logs and policy decisions (Task 2.4) as the audit trail.
Step Functions: refunds over $500 wait up to 24 hours for a human, then are rejected by default 
{
  "StartAt": "NeedsApproval",
  "States": {
    "NeedsApproval": {
      "Type": "Choice",
      "Choices": [
        { "Variable": "$.amount", "NumericGreaterThan": 500, "Next": "RequestApproval" }
      ],
      "Default": "IssueRefund"
    },
    "RequestApproval": {
      "Type": "Task",
      "Resource": "arn:aws:states:::sns:publish.waitForTaskToken",
      "Parameters": {
        "TopicArn": "arn:aws:sns:us-east-1:333333333333:refund-approvals",
        "Message": {
          "TaskToken.$": "$$.Task.Token",
          "OrderId.$": "$.orderId",
          "Amount.$": "$.amount"
        }
      },
      "TimeoutSeconds": 86400,
      "Catch": [
        { "ErrorEquals": ["States.Timeout", "States.TaskFailed"], "Next": "RejectRefund" }
      ],
      "Next": "IssueRefund"
    },
    "IssueRefund": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "issue-refund", "Payload.$": "$" },
      "End": true
    },
    "RejectRefund": { "Type": "Fail", "Error": "RefundNotApproved" }
  }
}
Approval app: the reviewer approves, and the workflow resumes 
aws stepfunctions send-task-success \
  --task-token "<token from the SNS message>" \
  --task-output '{"approvedBy": "reviewer@example.com", "approved": true}'

"The agent must not issue large refunds without a manager" means a deterministic threshold that routes to a Step Functions approval (or a Policy rule plus approval), not an instruction in the prompt. "Approvals can take several days" rules out waiting inside an agent session. "The AI must not decide whether something is risky" means rules or a policy engine classify the action.

Key takeaways

  • Guardrails: content, prompt attack, topic, word, PII, grounding and Automated Reasoning checks; detect mode first, numbered versions, Standard tier with a guardrail profile; check tool output yourself with ApplyGuardrail or InvokeGuardrailChecks.
  • Enforcement: IAM bedrock:GuardrailIdentifier, then account-level, then an Organizations Bedrock policy in comprehensive mode; all layers apply and the strictest wins.
  • Agent access: JWT or IAM inbound, a workload identity bound to the user, token vault credentials with M2M, user federation or on-behalf-of exchange, AgentCore Policy on every tool call (start in LOG_ONLY, protect UpdateGateway).
  • Human oversight: deterministic risk tiers, Step Functions task tokens with timeouts that fail safe, parallel blind reviews for critical actions, full context and approver identity logged; Agents Classic features aren't for new builds.
