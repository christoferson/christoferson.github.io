Overview

Task 4.3

Design solutions to meet business continuity and resiliency requirements.

Task 4.2 is about recovering from a disaster; this task is about the everyday resilience around it: backup governance, designs that tolerate failure, immutable copies, and proof through testing. The Well-Architected Reliability Pillar frames most of it (REL05, REL10, REL11, REL12, REL13), and the security-side backup details are in the SCS data at rest notes.

Running example. The order platform spans three AZs in us-east-1 with DR in us-west-2. A central backup account (888888888888) holds copies of every account's backups. A ransomware attack on a peer company has the board asking whether a compromised administrator could delete all the company's backups, and how long recovery would really take.

Centralized backup governance

Skill 4.3.1Configure centralized backup governance and cross-account backup policies (for example, by using AWS Backup).

  • Turn on cross-account management in the management account's AWS Backup settings: backup policies, cross-account monitoring (jobs from every account, from the moment you opt in), cross-account backup (copies to other accounts in the organization) and delegated administrator.
  • Organizations backup policies deploy backup plans to OUs or accounts: schedules, retention, cold storage, copy actions to a central or DR vault, and resource selection by tag or resource type (not by individual ARN). Each member account needs the vault and IAM role the policy names, which is usually deployed with StackSets. Inheritance operators let a parent policy stop child OUs weakening protection.
  • Delegated administrator: register a backup account so the management account isn't used day to day. Registration alone gives monitoring only; to manage policies, also attach AWSBackupOrganizationAdminAccess to its roles and add an Organizations delegation policy.
  • Centralized copies: copy actions write to a vault in a separate backup account (and Region) whose vault access policy denies deletion. A cross-account copy target names the account ID literally; $account means the same account.
  • Audit: Backup Audit Manager frameworks check that resources are in a plan, that backups are frequent, retained, encrypted, copied across Regions and accounts, locked, and restorable within a target time. Organization-wide reports come from the management account or delegated administrator (CSV, to a bucket in that account). Restore testing restores samples on a schedule and records how long it took.
Organizations backup policy: daily backups of tagged resources, copied to the central backup account for a year 
{
  "plans": {
    "Critical_Daily": {
      "regions": { "@@append": ["us-east-1", "us-west-2"] },
      "rules": {
        "Daily": {
          "schedule_expression": { "@@assign": "cron(0 5 ? * * *)" },
          "start_backup_window_minutes": { "@@assign": "60" },
          "target_backup_vault_name": { "@@assign": "LocalBackupVault" },
          "lifecycle": { "delete_after_days": { "@@assign": "35" } },
          "copy_actions": {
            "arn:aws:backup:$region:888888888888:backup-vault:CentralVault": {
              "target_backup_vault_arn": {
                "@@assign": "arn:aws:backup:$region:888888888888:backup-vault:CentralVault"
              },
              "lifecycle": { "delete_after_days": { "@@assign": "365" } }
            }
          }
        }
      },
      "selections": {
        "tags": {
          "critical": {
            "iam_role_arn": { "@@assign": "arn:aws:iam::$account:role/AWSBackupRole" },
            "tag_key": { "@@assign": "backup" },
            "tag_value": { "@@assign": ["critical"] }
          }
        }
      }
    }
  }
}
Management account: make the backup account a delegated administrator 
aws organizations register-delegated-administrator \
  --account-id 888888888888 \
  --service-principal backup.amazonaws.com

A backup policy that names a vault or role missing from a member account silently fails for that account. Plans created from a policy follow the management account's resource opt-in settings, not the member's. Backup Audit Manager can't deliver reports to another account's bucket. Copies of unencrypted Aurora, DocumentDB and Neptune backups stay unencrypted.

Failover tests and recovery times

Skill 4.3.2Design failover tests and measure recovery times (for example, by using AWS Fault Injection Service, Amazon Route 53 health checks).

  • Test the real failure modes:
    • AZ: FIS stops instances in one AZ, disrupts a subnet's connectivity, forces an RDS or Aurora failover, pauses EBS I/O, or runs the AZ power-interruption scenario. It can also start a zonal autoshift to test the recovery.
    • Region: run Region switch plans and DRS drills (Task 4.2).
    • Dependencies: inject API errors or throttling for a role.
  • Measure from the user's view:
    • CloudWatch Synthetics canaries run scripted journeys as often as every minute, giving success percentage and duration over time.
    • Route 53 health check metrics (HealthCheckStatus, HealthCheckPercentageHealthy, TimeToFirstByte) show when an endpoint went unhealthy and when it recovered.
    The gap between the first failed canary and the first good one is the measured recovery time.
  • Record evidence: FIS experiment reports (a PDF with CloudWatch dashboard graphs annotated with start and end times), Region switch execution reports, and Backup Audit Manager's restore-time control, all kept in S3.
  • Compare with targets: Resilience Hub gives an estimated RTO and RPO from configuration; only drills and game days show the actual numbers (Well-Architected REL13-BP03: "the only error recovery that works is the path you test frequently").
  • Health check design: the request interval (30 or 10 seconds) and protocol can't be changed after creation; calculated health checks combine up to 256 child checks; a disabled health check counts as healthy; checks based on CloudWatch alarms can't use metric math or M-out-of-N alarms.

"Measure how long customers are affected during an AZ failure" points to an FIS experiment plus Synthetics canaries, not to Resilience Hub's estimate. "Fail over automatically when the application, not just the server, is unhealthy" points to a Route 53 health check on a CloudWatch alarm or a calculated health check.

Resilient architecture

Skill 4.3.3Design technically resilient architectures that have features such as redundancy, fault tolerance, and self-healing capabilities.

  • Redundancy across fault boundaries: at least two, preferably three AZs for every tier; Multi-AZ databases; zonal services where possible (Availability Zone independence keeps a request in one AZ, so a bad AZ affects fewer requests).
  • Static stability (REL11-BP05): the system keeps working without making changes when something fails. With three AZs, run enough capacity that losing one needs no new launches (about 50% over steady-state need). Launching capacity only after a failure is "bimodal" behavior and depends on control planes that may be impaired.
  • Self-healing (REL11-BP03):
    • Auto Scaling health checks replace instances, and EC2 automatic recovery handles hardware failures.
    • ECS and EKS restart failed tasks and pods.
    • Aurora fails over to a replica.
    • Zonal autoshift moves traffic away from an impaired AZ.
    • EventBridge rules trigger Systems Manager runbooks for anything else.
    Rely on data plane actions during recovery (REL11-BP04).
  • Limit the blast radius (REL10-BP03):
    • Cell-based architecture: independent copies of the whole stack behind a thin router, with customers mapped to cells by a partition key, so one bad cell affects only its share of customers.
    • Shuffle sharding: gives each customer a different combination of workers. With 8 workers and shards of 2, a single customer's bad traffic affects 1 in 28 combinations instead of 1 in 4.
  • Interactions that withstand failure (REL05):
    • Graceful degradation: serve partial results, or buffer writes in SQS when the database is down.
    • Throttle and shed load: keep "goodput" up under overload.
    • Retries and timeouts: capped retries with backoff and jitter, client timeouts, and failing fast instead of queueing.
    • Stateless services and emergency levers: keep state out of compute, and have switches to turn features off.
  • Constant work: systems that do the same work whatever happens (for example pulling a full configuration every few seconds) have no untested modes.

A two-AZ design running each AZ near 100% isn't statically stable: losing one AZ means scaling up during the event. Deep health checks on load balancers can take a whole fleet out when a shared dependency fails; load balancers and Route 53 fail open when every target is unhealthy. S3 One Zone-IA and single-AZ caches aren't statically stable across AZs.

Ransomware and accidental deletion

Skill 4.3.4Protect data against ransomware and accidental deletion (for example, by using Amazon S3 Object Lock, Amazon EBS snapshot lock, AWS Backup Vault Lock).

  • Assume an administrator can be compromised. Protections must hold even against the account's own root user and admins, which means locks in compliance mode and copies in a separate account.
  • AWS Backup Vault Lock:
    • Governance mode: can be removed by users with permission.
    • Compliance mode: after a grace time of at least 3 days, the vault and its lock can't be changed or deleted by anyone, including AWS. It enforces minimum and maximum retention on new backups.
  • Logically air-gapped vaults always use compliance-mode locking, store backups in an AWS-owned account, and can be shared with a recovery account through RAM. With multi-party approval, a group of approvers can grant access for restore even if the owning account is lost or locked out.
  • Service-level immutability:
    • S3 Object Lock: compliance or governance retention, plus legal holds, on versioned buckets.
    • EBS Snapshot Lock: governance or compliance, with an optional cooling-off period of up to 72 hours, after which compliance locks can only be extended.
    • AWS Backup legal holds: stop deletion of selected recovery points indefinitely.
    • Recycle Bin rules (lockable): recover deleted EBS snapshots, volumes and AMIs.
  • Restrict and detect: SCPs that deny deleting vaults, recovery points, lock configurations and snapshots except for a break-glass role; vault access policies denying backup:DeleteRecoveryPoint; GuardDuty malware scanning of recovery points so you restore a clean copy; MFA delete or versioning on buckets.
  • Recover cleanly: restore into an isolated account, scan, then promote; point-in-time recovery (DRS, Aurora, DynamoDB) to a moment before the encryption started.
Central vault: compliance-mode lock after a 3-day grace period, retention between 35 days and 7 years 
aws backup put-backup-vault-lock-configuration \
  --backup-vault-name CentralVault \
  --changeable-for-days 3 \
  --min-retention-days 35 \
  --max-retention-days 2555
# --changeable-for-days makes it compliance mode: after 3 days nobody can
# remove the lock or delete recovery points before their retention ends

Replication isn't protection: CRR and global tables copy encrypted or deleted data within seconds. Compliance-mode locks can't be undone, so test with short retention first. Vault access policies cover only AWS Backup APIs, not native EBS or RDS deletes, so add SCPs. Legal holds don't carry over to copies in other Regions or accounts.

Chaos engineering

Skill 4.3.5Implement chaos engineering with controlled failure scenarios (for example, by using AWS Fault Injection Service experiment templates, steady-state hypotheses).

  • The loop (REL12-BP04):
    1. Steady state: a measurable output that shows normal behavior, for example 300 orders per second at 99% success under 500 ms.
    2. Hypothesis: "If one AZ loses its web instances, the order workload keeps success above 99% because the load balancer and spare capacity in the other AZs absorb the traffic".
    3. Run the experiment.
    4. Verify against the steady state.
    5. Improve and repeat.
    If you already know it will fail, fix it instead of running the experiment.
  • FIS experiment templates define targets (by tags, ARNs or filters, with a selection such as one instance, a count or a percentage), actions (with durations in ISO 8601, run in sequence or parallel), stop conditions (CloudWatch alarms that halt the experiment, up to five) and the IAM role. Multi-account experiments run from an orchestrator account.
  • Control the blast radius:
    • Start small in non-production; AWS's FIS guidance says never to start in production.
    • Graduate to production under real load with canaries and stop conditions, as Well-Architected recommends.
    • Tell operations teams first.
    • The FIS safety lever (one per account and Region) stops all running experiments at once and cancels new ones until it's disengaged.
  • Make it continuous: once a hypothesis holds, run the experiment as a regression test in the deployment pipeline (REL08-BP03), and hold game days on a schedule with the people involved (REL12-BP05). Experiment reports keep the evidence.
FIS template: stop half the web instances in one AZ for 10 minutes, halt if the order-success alarm fires 
{
  "description": "AZ loss of web tier, us-east-1a",
  "roleArn": "arn:aws:iam::111111111111:role/FisExperimentRole",
  "targets": {
    "webInstances": {
      "resourceType": "aws:ec2:instance",
      "resourceTags": { "tier": "web" },
      "filters": [
        { "path": "Placement.AvailabilityZone", "values": ["us-east-1a"] }
      ],
      "selectionMode": "PERCENT(50)"
    }
  },
  "actions": {
    "stopWeb": {
      "actionId": "aws:ec2:stop-instances",
      "parameters": { "startInstancesAfterDuration": "PT10M" },
      "targets": { "Instances": "webInstances" }
    }
  },
  "stopConditions": [
    {
      "source": "aws:cloudwatch:alarm",
      "value": "arn:aws:cloudwatch:us-east-1:111111111111:alarm:orders-success-below-99"
    }
  ],
  "experimentReportConfiguration": {
    "outputs": {
      "s3Configuration": { "bucketName": "example-fis-reports", "prefix": "az-loss/" }
    },
    "dataSources": {
      "cloudWatchDashboards": [
        { "dashboardIdentifier": "arn:aws:cloudwatch::111111111111:dashboard/orders" }
      ]
    }
  }
}

Scenario library templates don't include stop conditions; add your own before running them. A stopped experiment can't be resumed; start a new one. FIS doesn't produce reports for cancelled runs or target-preview runs, the report bucket must be in the experiment's Region, and reports take graphs from one dashboard only.

Key takeaways

  • Backup governance: cross-account management in the management account, Organizations backup policies by tag, a delegated administrator with the extra policy and delegation, copies to a separate backup account, Backup Audit Manager and restore testing.
  • Testing: FIS for AZ and dependency failures, Synthetics canaries and Route 53 health check metrics to measure recovery, reports as evidence, estimates are not measurements.
  • Design: three AZs with static stability, self-healing from data plane actions, cells and shuffle sharding to limit blast radius, graceful degradation, load shedding, capped retries and timeouts.
  • Ransomware: compliance-mode Vault Lock, logically air-gapped vaults with multi-party approval, Object Lock, EBS Snapshot Lock, legal holds, SCPs against deletion, malware scans before restore.
  • Chaos engineering: steady state, hypothesis, run, verify, improve; FIS templates with stop conditions, small blast radius, safety lever, then continuous experiments in pipelines and game days.
