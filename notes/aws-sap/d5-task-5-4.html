Task 5.4: Design operational automation and resilient systems

Running the estate with as little manual work as possible: noticing health, quota and capacity problems before they bite, fixing things automatically but within safe limits, scaling ahead of demand, replacing what breaks without anyone acting, and turning every routine operation and incident step into a runbook.

Overview

Task 5.4

Design operational automation and resilient systems.

Automation that can't be trusted gets switched off, so this task is as much about guardrails (rate limits, approvals, change windows, rollback) as about automating. Monitoring and alarms are on Task 5.3, resilience patterns and chaos testing on Task 4.3, and day-to-day automation detail in the DOP event-driven configuration notes.

Running example. The order platform runs EC2 web servers in Auto Scaling groups with a sharp daily peak, ECS services, Lambda event processing and Step Functions order workflows. The operations team wants quota problems caught early, unhealthy capacity replaced automatically, fixes rolled out a few servers at a time outside the Black Friday freeze, and incidents triaged before anyone is paged.

Status changes to know. Systems Manager Change Manager and Incident Manager closed to new customers on 7 November 2025 (use Change Calendar, Automation approvals, OpsCenter and partner ITSM tools). The AWS SDKs' new retry behavior (announced May 2026) becomes the default in November 2026. New: Service Quotas automatic management with optional auto-adjust, the AWS DevOps Agent (generally available March 2026) for incident triage, EC2 Auto Scaling VPC Lattice and EBS health checks, a replace-root-volume instance refresh strategy, and new ECS circuit breaker threshold options.

Health, capacity and operational responses

Skill 5.4.1Implement health monitoring, capacity planning, and operational responses (for example, by using CloudWatch alarms, Amazon EventBridge, AWS Systems Manager, Service Quotas).

  • Quotas before they become outages:
    • Usage alarms: many services publish usage metrics to AWS/Usage, so a CloudWatch alarm on m1/SERVICE_QUOTA(m1)*100 above 80% warns early. It can be created from the Service Quotas console, or from a monitoring account for linked accounts.
    • Automatic management: AWS watches usage and notifies at 80% and 95%, through AWS Health and EventBridge. In notify and auto-adjust mode it also requests increases for quotas that support automatic approval.
    • New accounts: quota request templates raise up to 10 quotas automatically in every new account in the organization.
  • AWS Health: service issues, scheduled changes (instance retirements, maintenance) and account notifications as EventBridge events.
    • The organizational view gathers every account's events in the management or delegated administrator account.
    • Create rules in each Region you use. Global events (such as IAM) arrive in us-east-1, and us-west-2 receives backup copies, so de-duplicate on the communication ID.
  • Capacity planning: load-test to find each component's limit, keep headroom for an AZ loss (static stability), reserve critical capacity with On-Demand Capacity Reservations or Capacity Blocks for ML, and raise quotas in the DR Region in advance.
  • Operational responses: EventBridge rules route health, quota, alarm and service events to Systems Manager Automation runbooks, Lambda, Step Functions, OpsItems or notifications. Trusted Advisor and Compute Optimizer add regular checks.
EventBridge rule: any quota approaching its limit or failing to increase, across the account 
{
  "source": ["aws.health"],
  "detail-type": ["AWS Health Event"],
  "detail": {
    "service": ["SERVICEQUOTAS"],
    "eventTypeCode": [
      "AWS_SERVICEQUOTAS_APPROACHING_THRESHOLD",
      "AWS_SERVICEQUOTAS_THRESHOLD_BREACH",
      "AWS_SERVICEQUOTAS_INCREASE_REQUEST_FAILED"
    ]
  }
}

Quota events come from aws.health, not a Service Quotas source. A threshold breach event means the quota can't be raised, so usage must come down. Auto-adjust requests can be rejected even when a manual request for the same quota would be approved. Quota request templates apply only to new accounts and not in opt-in Regions. The Health API needs Business Support+ or higher.

Controlled remediation

Skill 5.4.2Configure controlled remediation solutions that have safety constraints (for example, circuit breakers, rate limits, bulkhead patterns, retry patterns with exponential backoff).

  • Limit how fast automation acts:
    • Systems Manager Automation rate control: run across targets selected by tag with a maximum concurrency (a number or percentage, ramping up from one) and an error threshold that stops the rollout.
    • Approvals: an aws:approve step pauses for named approvers before risky steps.
    • Change Calendar: a runbook checks it and refuses to run during freezes.
  • Retries with exponential backoff and jitter:
    • AWS SDKs: standard mode (3 attempts, full jitter, a retry quota that fails fast when retries are exhausted) is the recommended default; adaptive mode adds client-side rate limiting for single-resource, throttling-heavy clients.
    • Step Functions: retriers take an interval, back-off rate, maximum delay and full jitter.
    • Where to retry: at one layer only, since retries at every layer multiply load, and make operations idempotent.
  • Circuit breakers: stop calling a failing dependency for a while instead of retrying into it. AWS's pattern uses Step Functions with a DynamoDB table of open circuits that expire with TTL. Deployments have their own breakers: the ECS deployment circuit breaker, and alarm-based rollback in CodeDeploy and instance refresh.
  • Rate limits: API Gateway throttling per account, stage, method and usage plan (best-effort, not a hard ceiling), Lambda reserved concurrency, SQS between producers and consumers, and load shedding.
  • Bulkheads: separate pools so one failure can't drain everything. Examples are per-function reserved concurrency, separate queues and Auto Scaling groups per workload or tenant tier, cells, and separate accounts.
Restart the order agent on prod web servers, 10% at a time, stop after the first failure 
aws ssm start-automation-execution \
  --document-name OrdersRestartAgent \
  --targets Key=tag:Role,Values=web Key=tag:Environment,Values=prod \
  --target-parameter-name InstanceId \
  --max-concurrency 10% \
  --max-errors 0
Runbook step: refuse to run while the freeze calendar is closed 
- name: CheckFreezeCalendar
  action: aws:assertAwsResourceProperty
  inputs:
    Service: ssm
    Api: GetCalendarState
    CalendarNames: ["arn:aws:ssm:us-east-1:111111111111:document/BlackFridayFreeze"]
    PropertySelector: "$.State"
    DesiredValues: [OPEN]

Automations already running when the error threshold is hit still finish, so set concurrency to 1 for a strict limit. aws:executeScript doesn't retry throttled calls for you and stops after 10 minutes. Approval steps don't work in multi-account, multi-Region automations. Adaptive SDK retry mode rate-limits the whole client, which hurts multi-tenant clients.

Auto scaling policies

Skill 5.4.3Configure auto scaling policies that are based on metrics and scheduled scaling policies (for example, target tracking scaling, predictive scaling for Auto Scaling groups).

  • Target tracking keeps a metric at a target. Good targets are average CPU, network, or ALB requests per target. Raw request count, latency or raw queue length are poor targets; use backlog per instance for queues. With several policies, the group scales out if any one says so and in only when all agree.
  • Step scaling for different responses at different breach sizes; scheduled scaling for known events (business hours, sales) and dev environments.
  • Predictive scaling:
    • Learns daily and weekly patterns from at least 24 hours (ideally two weeks) of history, and forecasts 48 hours ahead every 6 hours.
    • Start in forecast only mode to check accuracy, then forecast and scale, with a scheduling buffer so instances are ready before the peak.
    • It only scales out, so pair it with target tracking for scale-in and unexpected spikes.
  • Faster scale-out: warm pools of pre-initialized (stopped or hibernated) instances, a default instance warmup so metrics from booting instances don't skew decisions, and lean AMIs.
  • Application Auto Scaling applies the same policy types to ECS services (including predictive), DynamoDB, Aurora replicas, Lambda provisioned concurrency, ElastiCache, SageMaker AI endpoints and more.
Web tier: forecast-based scaling with instances launched 5 minutes before the forecast need 
{
  "MetricSpecifications": [
    {
      "TargetValue": 50,
      "PredefinedMetricPairSpecification": { "PredefinedMetricType": "ASGCPUUtilization" }
    }
  ],
  "Mode": "ForecastAndScale",
  "SchedulingBufferTime": 300
}

A new Auto Scaling group (for example after a blue/green swap) needs 24 hours of history before predictive scaling forecasts again. Letting predictive scaling raise the maximum capacity leaves the higher maximum in place until you change it. Predictive scaling assumes instances are the same size, so be careful with mixed instance types. Don't edit the alarms that target tracking creates.

Automated failure recovery

Skill 5.4.4Design automated failure recovery solutions that use health checks and replacement strategies (for example, by using Auto Scaling health checks, Amazon ECS task replacement, AWS Lambda retry policies).

  • EC2 Auto Scaling health checks:
    • Types: EC2 status checks (always on), plus ELB, VPC Lattice and EBS checks you turn on, and custom health set by your own tooling. Use ELB checks so instances failing the application check are replaced.
    • Grace period: set one so instances can boot (300 seconds in the console, 0 by default from the CLI).
    • Replacement pace: Auto Scaling replaces unhealthy instances gradually (up to 10% of capacity at a time).
    • Instance maintenance policy: chooses launch-before-terminate or terminate-and-launch.
  • Instance refresh rolls a new AMI or configuration through the group with minimum and maximum healthy percentages, checkpoints and bake time, and rolls back automatically when a CloudWatch alarm fires. This requires a desired configuration with a numbered launch template version.
  • ECS: the service scheduler replaces tasks that stop or fail container or load balancer health checks, starting the replacement first when capacity allows. The deployment circuit breaker and alarm-based rollback return a bad deployment to the last completed one.
  • Lambda:
    • Asynchronous invocations retry function errors up to twice, then send the event to an on-failure destination (SQS, SNS, Lambda, EventBridge or S3) or a dead-letter queue; destinations include the error context.
    • SQS triggers: rely on the queue's visibility timeout and its own dead-letter queue, with partial batch responses so only failed messages return.
    • Stream triggers: retry limits, batch bisection and on-failure destinations keep one bad record from blocking a shard.
  • Step Functions: Retry for transient errors, then Catch to a compensating path (a saga). Redrive restarts a failed Standard execution from the failed step.
Roll a new launch template version through the web tier, rolling back if 5XX errors alarm 
aws autoscaling start-instance-refresh \
  --auto-scaling-group-name orders-web \
  --desired-configuration '{"LaunchTemplate":{"LaunchTemplateName":"orders-web","Version":"7"}}' \
  --preferences '{"MinHealthyPercentage":90,"MaxHealthyPercentage":110,
    "AutoRollback":true,"AlarmSpecification":{"Alarms":["orders-web-5xx"]}}'
Step Functions: retry a throttled payment call with capped, jittered backoff 
{
  "Retry": [
    {
      "ErrorEquals": ["Lambda.TooManyRequestsException", "States.Timeout"],
      "IntervalSeconds": 2,
      "MaxAttempts": 4,
      "BackoffRate": 2,
      "MaxDelaySeconds": 30,
      "JitterStrategy": "FULL"
    }
  ]
}

Instance refresh rollback doesn't work with $Latest or $Default template versions, and an alarm already firing blocks the refresh from starting (whereas an ECS deployment ignores alarms already in ALARM at its start). For SQS-triggered functions the dead-letter queue belongs on the queue, not the function. A Lambda async dead-letter queue carries only the payload; destinations add the response. Step Functions States.ALL doesn't catch States.Runtime, and jitter is off unless you set it.

Runbooks and incident response

Skill 5.4.5Configure automated runbooks and incident response procedures for operational tasks such as patching, remediation, and scaling.

  • Runbooks as code: Systems Manager Automation documents (AWS-provided or your own) for restarts, AMI creation, snapshot and restore, scaling and failover, kept in source control and shared across accounts.
    • Branching with aws:branch handles different outcomes.
    • Scripts with aws:executeScript handle custom logic.
    • Approvals with aws:approve pause for a human.
    Multi-account, multi-Region executions run the same runbook across the organization.
  • Triggers:
    • EventBridge rules: alarm state changes, Health events, Config noncompliance or GuardDuty findings start runbooks.
    • AWS Config remediation runs Automation documents for noncompliant resources.
    • State Manager associations re-apply configuration on a schedule.
    • Maintenance windows and EventBridge Scheduler handle timed work.
  • Patching: Patch Manager patch policies scan and install across accounts and Regions on schedules (Task 2.3), with rate control, maintenance windows and change calendars; immutable workloads rebuild images instead.
  • Incident response:
    • Tracking: OpsItems in OpsCenter link the alarm, related resources and recommended runbooks.
    • Investigation: CloudWatch investigations and the AWS DevOps Agent (generally available March 2026) analyse metrics, logs, traces, deployments and changes to suggest root causes and next steps.
    • Communication: Amazon Q Developer in chat applications brings alerts and actions into Slack or Teams.
    • Escalation: Incident Manager and Change Manager are closed to new customers, so on-call paging and formal change approval use partner tools (PagerDuty, ServiceNow, Jira) together with OpsCenter and Change Calendar.
  • Learn from incidents: after each one, turn the manual steps into a runbook, add the missing alarm, and test the fix with FIS (Task 4.3).

"Restart the service automatically when its health alarm fires, but never more than a few servers at once" is EventBridge to a Systems Manager Automation runbook with rate control. "Don't run automated changes during the holiday freeze" is Change Calendar. "Speed up root-cause analysis across many accounts" points to CloudWatch investigations or the AWS DevOps Agent. A State Manager association running an Automation runbook starts a new run on every newly launched instance unless it's set to apply only at its scheduled interval.

Key takeaways

  • Health and capacity: quota alarms with SERVICE_QUOTA(), Service Quotas automatic management and request templates, AWS Health organizational view through EventBridge, headroom and reservations for critical capacity.
  • Safe remediation: Automation rate control and error thresholds, approvals, Change Calendar, retries with backoff and jitter at one layer, circuit breakers, throttling and bulkheads.
  • Scaling: target tracking on good metrics, scheduled for known events, predictive (forecast first, scale-out only) with warm pools and warmup, Application Auto Scaling for other services.
  • Recovery: ELB, Lattice and EBS health checks with grace periods, instance refresh with alarm rollback, ECS task replacement and circuit breaker, Lambda retries with destinations, Step Functions Retry and Catch.
  • Runbooks and incidents: Automation documents triggered by EventBridge, Config, State Manager and schedules; patch policies; OpsCenter, CloudWatch investigations and DevOps Agent; partner tools for paging and change approval.
