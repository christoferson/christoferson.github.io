Overview

Task 5.3

Design observability and monitoring solutions.

The Professional questions are about standards and placement: one way to instrument everything, one place to see it across accounts, and alerts tied to what users experience. Observability cost is on Task 3.4, organization-wide log centralization on Task 2.3, and the CloudWatch detail in the DOP logs and metrics notes.

Running example. A monitoring account in the organization views metrics, logs and traces from every workload account. The order API runs on ECS and EKS, the web shop is a single-page app, and the support assistant runs on AgentCore and Bedrock. The business has promised 99.9% availability for checkout.

Status changes to know. The X-Ray SDKs and daemon entered maintenance mode on 25 February 2026 (use OpenTelemetry). Incident Manager is closed to new customers (November 2025). SageMaker Model Monitor and Clarify closed to new customers on 30 July 2026. AWS Chatbot is now Amazon Q Developer in chat applications (February 2025). New: CloudWatch OTLP endpoints and OpenTelemetry metrics, Application Signals SLOs with request-based SLIs and burn-rate alarms (2024), mobile RUM (late 2025), log alarms and alarm warm-up periods (2026), and CloudWatch Omni (September 2026).

Metrics, logs and traces

Skill 5.3.1Implement observability by collecting metrics, logs, and distributed tracing by using standardized instrumentation (for example, by using Amazon CloudWatch, AWS X-Ray, AWS Distro for OpenTelemetry).

  • Standardize on OpenTelemetry: applications are instrumented with the AWS Distro for OpenTelemetry (ADOT) SDKs or upstream OpenTelemetry, often automatically (Java, Python, .NET and Node.js agents, a Lambda layer, or the CloudWatch Observability add-on for EKS). New code shouldn't use the X-Ray SDKs.
  • Collect with the CloudWatch agent, which AWS now positions as its managed OpenTelemetry collector and recommends for most cases (it supports Application Signals, enhanced Container Insights and entity correlation), or send OTLP directly to CloudWatch's HTTP endpoints for traces, logs and metrics. Traces need CloudWatch Transaction Search enabled; it indexes a configurable share of spans, 1% free.
  • Signals and where they land: metrics (AWS service metrics, custom metrics, embedded metric format, OpenTelemetry metrics queryable with PromQL), logs (CloudWatch Logs, queried with Logs Insights), traces (X-Ray, span data in CloudWatch). Correlate them with a trace ID in every log line and consistent service and environment attributes.
  • Application Signals builds on this telemetry: it discovers services, operations and dependencies, draws an application map, and gives latency, fault and error metrics per operation without custom dashboards.
  • Cross-account view: CloudWatch cross-account observability links source accounts to a monitoring account for metrics, logs, traces and Application Signals in one Region. Nothing is copied, and data stays visible only while the link exists.
  • Open-source stacks: Amazon Managed Service for Prometheus and Amazon Managed Grafana, fed by the same collectors.
Lambda function: turn on OpenTelemetry auto-instrumentation for Application Signals 
aws lambda update-function-configuration \
  --function-name orders-validator \
  --layers "$ADOT_LAMBDA_LAYER_ARN" \
  --environment "Variables={AWS_LAMBDA_EXEC_WRAPPER=/opt/otel-instrument}"
# The execution role also needs CloudWatchLambdaApplicationSignalsExecutionRolePolicy;
# --environment replaces all variables, so include any existing ones

CloudWatch's OTLP endpoints accept HTTP only (no gRPC). OpenTelemetry traces sent to CloudWatch need Transaction Search turned on first. Cross-account observability works within one Region; each Region needs its own links. The X-Ray service still accepts data from the old SDKs, but they get no new features.

Containers

Skill 5.3.2Implement monitoring for containerized applications (for example, by using Amazon ECS, Amazon EKS with Container Insights).

  • Container Insights collects cluster, service, task or pod, and container metrics and logs.
    • Enhanced observability adds container-level detail and curated dashboards for ECS and EKS. On EKS it's billed per observation, and on ECS at a flat per-metric rate.
    • For EKS, the newer OpenTelemetry-based Container Insights (billed per GB, with more labels per metric) is the recommended option.
  • Turning it on: an ECS account setting or cluster setting (enhanced), and the Amazon CloudWatch Observability add-on on EKS, which also deploys Application Signals instrumentation and Fluent Bit for logs.
  • Logs from containers: the awslogs driver or FireLens (Fluent Bit) on ECS, Fluent Bit on EKS; filter at the source and route audit logs to S3.
  • Prometheus metrics: Amazon Managed Service for Prometheus with its managed collector for EKS, queried from Grafana, when teams already use Prometheus.
  • Agents in containers: AgentCore Runtime and self-hosted agents report through the same OpenTelemetry path into CloudWatch GenAI observability (Skill 5.3.5).
ECS: enhanced Container Insights for every new cluster in the account 
aws ecs put-account-setting \
  --name containerInsights \
  --value enhanced \
  --principal-arn arn:aws:iam::111111111111:root
# Without --principal-arn the setting applies only to the calling user;
# existing clusters: aws ecs update-cluster-settings --settings name=containerInsights,value=enhanced

"See CPU and memory per container and which deployment caused a spike" is enhanced Container Insights. "Team already has Prometheus dashboards and alerts" is Managed Service for Prometheus and Managed Grafana. "Trace requests across ECS services and Lambda" is OpenTelemetry instrumentation with Application Signals.

Multi-account log aggregation

Skill 5.3.3Implement multi-account log aggregation with cross-account subscriptions and centralized archives (for example, by using Amazon CloudWatch Logs subscriptions, Amazon S3 archival storage tiers).

  • Three patterns:
    • Cross-account subscriptions stream log events in real time to Kinesis Data Streams, Firehose or Lambda in a central account, for processing, a SIEM or an archive.
    • Centralization rules copy whole log groups into a central account and Region (one copy free).
    • Cross-account observability only lets the monitoring account view the data.
  • Subscriptions across accounts:
    • Receiving account: create a CloudWatch Logs destination pointing at the stream, with a role that CloudWatch Logs assumes, and a destination policy allowing the organization (aws:PrincipalOrgID).
    • Sending accounts: subscribe log groups to the destination ARN (not the stream ARN), or apply an account-level subscription filter policy that covers every log group except those you exclude.
    • Limits: up to five subscription filters per log group, and the log group and destination must be in the same Region.
  • Cheap archive: Firehose writes the stream to S3 (compressed, partitioned by date), lifecycle rules move it to Glacier Flexible Retrieval or Deep Archive, and Object Lock keeps it immutable for audits. Query it with Athena when needed. Keep only recent data in CloudWatch with short retention.
  • Service logs (VPC Flow Logs, CloudFront, ALB, WAF) can be delivered straight to S3 or Firehose as vended logs, skipping CloudWatch ingestion cost.
Central account: destination policy allowing every account in the organization 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["logs:PutSubscriptionFilter", "logs:PutAccountPolicy"],
      "Resource": "arn:aws:logs:us-east-1:888888888888:destination:org-log-archive",
      "Condition": { "StringEquals": { "aws:PrincipalOrgID": ["o-a1b2c3d4e5"] } }
    }
  ]
}
Each workload account: send all log groups (except noisy ones) to the central destination 
aws logs put-account-policy \
  --policy-name org-log-archive \
  --policy-type SUBSCRIPTION_FILTER_POLICY \
  --scope ALL \
  --selection-criteria 'LogGroupName NOT IN ["/aws/lambda/debug-noise"]' \
  --policy-document '{"RoleArn":"arn:aws:iam::555555555555:role/CWLtoSubscriptionRole",
    "DestinationArn":"arn:aws:logs:us-east-1:888888888888:destination:org-log-archive",
    "FilterPattern":"","Distribution":"Random"}'

With an organization-wide destination policy, the sender's account policy must include a role in the sender account. Avoid loops: exclude the log groups of the function that processes the logs. Throttled deliveries are retried for 24 hours and then dropped, so watch the DeliveryThrottling metric and size the stream (or use on-demand capacity).

Alerting

Skill 5.3.4Configure alerting solutions (for example, by using CloudWatch alarms, Amazon SNS, AWS Systems Manager).

  • Alarm types:
    • Metric alarms: static thresholds, metric math or anomaly detection bands.
    • Metrics Insights query alarms: one SQL-style alarm covers many resources, including new ones, with a contributor per series.
    • PromQL alarms on OpenTelemetry metrics.
    • Log alarms on scheduled Logs Insights queries.
    • Composite alarms combine others with AND, OR and NOT.
  • Actions: SNS (email, SMS, HTTPS, and on to Slack or Teams through Amazon Q Developer in chat applications), Lambda directly, EC2 stop, reboot or recover, Auto Scaling, Systems Manager OpsItems for tracking in OpsCenter, and CloudWatch investigations. Every state change is also an EventBridge event, so rules can start Systems Manager Automation runbooks or Step Functions. AWS User Notifications delivers alerts to email, chat, the console and the mobile app.
  • Cutting noise: composite alarms that page only when user-facing symptoms and a cause agree; an actions suppressor to silence child alarms while a parent (for example "deployment in progress") is in alarm; mute rules for maintenance windows; warm-up periods so new resources don't alarm immediately; and alarm recommendations for AWS services.
  • Alert on symptoms first: error rate, latency and SLO burn rate page someone; resource metrics (CPU, queue depth) go to dashboards or tickets.
Page only when checkout errors and latency both breach, silenced during deployments 
aws cloudwatch put-composite-alarm \
  --alarm-name checkout-user-impact \
  --alarm-rule 'ALARM("checkout-5xx-rate") AND ALARM("checkout-p99-latency")' \
  --actions-suppressor deployment-in-progress \
  --actions-suppressor-wait-period 120 \
  --actions-suppressor-extension-period 300 \
  --alarm-actions arn:aws:sns:us-east-1:555555555555:checkout-oncall

Alarm actions fire only on a state change (except Auto Scaling, which repeats). Composite alarms can't take EC2 or Auto Scaling actions and can't span accounts. Multi-series Metrics Insights alarms can't take EC2 or Auto Scaling actions either. Incident Manager is still listed as an action but closed to new customers; use OpsItems, SNS or partners.

AI and ML workloads

Skill 5.3.5Monitor metrics for AI/ML workloads, including model performance, AI agent performance, inference latency, and model drift.

  • Bedrock models:
    • Metrics: AWS/Bedrock has invocations, invocation latency, time to first token, throttles, errors and input, output and cache token counts per model.
    • Logs: model invocation logs hold prompts and responses.
    • Dashboards: CloudWatch GenAI observability has a model invocations view.
    • Guardrails: its metrics show how often content is blocked.
  • Agents:
    • AgentCore metrics: runtime invocations, latency, errors and throttles, plus gateway, memory, tool and identity metrics. The GenAI observability view shows sessions, traces and tool calls.
    • Evaluations: AgentCore Evaluations score live sessions (goal success, tool selection accuracy, helpfulness) and write the scores to CloudWatch for alarms.
    • Self-hosted agents: agents on ECS or EKS report the same way through OpenTelemetry.
  • Inference endpoints: SageMaker AI endpoint metrics (model latency, overhead latency, invocations, 4XX and 5XX errors, GPU and memory use) in CloudWatch, with alarms and auto scaling on them.
  • Model quality and drift:
    • Capture inputs and outputs (SageMaker data capture, invocation logs) and compare their statistics with a training or launch baseline on a schedule.
    • With SageMaker Model Monitor and Clarify closed to new customers, AWS points to open-source monitoring (for example with MLflow and Evidently), CloudWatch metrics with anomaly detection, and QuickSight.
    • For generative AI, run Bedrock or AgentCore evaluations regularly against a golden dataset and alarm when scores fall.
  • Business signals: track cost per request (token counts), user feedback rates and escalation rates next to technical metrics.
Alarm when the assistant's gateway starts returning server errors 
aws cloudwatch put-metric-alarm \
  --alarm-name support-gateway-system-errors \
  --namespace AWS/Bedrock-AgentCore \
  --metric-name SystemErrors \
  --dimensions Name=Resource,Value="$SUPPORT_GATEWAY_ARN" \
  --statistic Sum --period 300 --evaluation-periods 1 \
  --threshold 5 --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:333333333333:assistant-oncall

AgentCore evaluations and A/B tests depend on CloudWatch Transaction Search being on in the account and Region. Gateway metrics aren't on the GenAI observability page; use the metrics console. Accuracy-type drift needs ground truth labels, which often arrive late, so watch input and prediction distributions as an early signal.

User experience

Skill 5.3.6Design monitoring solutions for the user experience by using strategies such as synthetic transactions and real user monitoring (for example, by using Amazon CloudWatch Synthetics, Amazon CloudWatch RUM).

  • CloudWatch Synthetics canaries are scripted user journeys (Node.js, Python or Java; browser automation with Playwright, Puppeteer or Selenium) run on a schedule as often as every minute, from several Regions if needed. They find failures before users do, even with no traffic, and measure availability and latency of critical paths like sign-in and checkout. They feed Application Signals and SLOs.
  • CloudWatch RUM collects what real users experience in web and mobile apps:
    • Data: page loads and Core Web Vitals (LCP, INP, CLS), JavaScript and HTTP errors, sessions by browser, device and location, and X-Ray traces from the browser through the backend.
    • Mobile: mobile app monitoring adds crashes, app hangs and launch times.
    • Setup: add the app monitor's snippet (NPM recommended; CDN snippets are often blocked by ad blockers), and authorize data with a Cognito identity pool or a resource-based policy.
    • Cost and retention: priced per event, so set a session sample rate. Data is kept 30 days unless copied to CloudWatch Logs.
  • Use both: synthetics give a constant, comparable baseline and catch outages at night; RUM shows the real spread across devices and networks and which pages hurt most.

"Detect a broken checkout at 3 a.m. when nobody is shopping" is a Synthetics canary. "Which countries and browsers see slow page loads" is RUM. "Correlate a slow page with the backend call that caused it" is RUM with X-Ray tracing and Application Signals.

Service-level objectives

Skill 5.3.7Design service-level objectives (SLOs) that have measurable indicators and alerts (for example, by using CloudWatch, CloudWatch Application Signals).

  • SLI, SLO, error budget: an indicator (availability or latency of an operation, or any CloudWatch metric or math expression), an attainment goal (for example 99.9%) over an interval (rolling, such as 30 days, or calendar), and the error budget that the goal allows (0.1% of the interval).
  • Two SLI styles in Application Signals:
    • Period-based: each minute (or other period) is good or bad. The budget only shrinks during the interval.
    • Request-based: good requests divided by all requests. The budget can recover as good traffic arrives.
    Availability counts server faults (5XX) as bad; client errors (4XX) don't lower it.
  • Burn-rate alarms say how fast the budget is being used (1 means exactly on budget). AWS's documented pattern pairs a long and a short window, so pages are both significant and current, combined with composite alarms:
    • 1 hour with 5 minutes at 2% of the budget.
    • 6 hours with 30 minutes at 5%.
    • 3 days with 6 hours at 10%.
  • Running them:
    • A warning threshold flags a nearly spent budget.
    • Time window exclusions leave maintenance out.
    • Composite SLOs cover several operations of a service.
    • Recommended SLOs are suggested from 30 days of data.
    There's no separate SLO fee; SLOs generate Application Signals signals.
  • Pick SLIs users feel: checkout availability and latency, not CPU. Use the error budget to decide between shipping features and fixing reliability.
Application Signals SLO: checkout availability 99.9% over 30 rolling days, with burn-rate windows (API shape) 
{
  "Name": "checkout-availability",
  "SliConfig": {
    "SliMetricConfig": {
      "KeyAttributes": { "Type": "Service", "Name": "orders-api", "Environment": "ecs:prod" },
      "OperationName": "POST /checkout",
      "MetricType": "AVAILABILITY",
      "PeriodSeconds": 60
    },
    "MetricThreshold": 99.9,
    "ComparisonOperator": "GreaterThanOrEqualTo"
  },
  "Goal": {
    "AttainmentGoal": 99.9,
    "Interval": { "RollingInterval": { "Duration": 30, "DurationUnit": "DAY" } },
    "WarningThreshold": 30
  },
  "BurnRateConfigurations": [
    { "LookBackWindowMinutes": 60 },
    { "LookBackWindowMinutes": 5 }
  ]
}

Changing an SLO's core configuration (SLI, period) resets its history. Burn-rate look-back windows must be multiples of the SLO period and shorter than the interval, and the three-pair pattern needs an interval of at least 3 hours. An SLO can be created on an operation only after it has reported metrics.

Key takeaways

  • Instrumentation: OpenTelemetry (ADOT) everywhere, the CloudWatch agent as collector or OTLP straight to CloudWatch, Transaction Search for traces, Application Signals for service maps, cross-account observability for a monitoring account.
  • Containers: enhanced or OpenTelemetry Container Insights, FireLens or Fluent Bit for logs, Managed Prometheus and Grafana where teams use them.
  • Logs: cross-account subscriptions to a central destination (account-level policies), Firehose to S3 with lifecycle to Glacier, centralization rules for copies, observability links for viewing.
  • Alerts: metric, Metrics Insights, PromQL, log and composite alarms; SNS, Lambda, OpsItems and EventBridge to runbooks; suppressors, mute rules and symptom-based paging.
  • AI, users and SLOs: Bedrock, AgentCore and SageMaker metrics plus regular evaluations and drift checks; Synthetics and RUM for user experience; Application Signals SLOs with multi-window burn-rate alarms.
