Overview

Task 2.3

Design multi-account governance and compliance solutions.

The Professional questions here are about where things live and which tool applies at which scope: which account owns the trail, which service has a delegated administrator, what RAM can share and what needs a resource policy, which guardrail is preventive and which only detects. The details of each service are in the SCS account strategy notes, SCS logging notes and SCS compliance notes; perimeter policies are on Task 2.1.

Running example. The company runs a Control Tower landing zone: a management account, a log archive account, a security tooling account (delegated administrator for GuardDuty, Security Hub, Inspector and Config), a shared-network account that owns the Transit Gateway and shared VPCs, and workload OUs per business unit. The central GenAI account (222222222222) serves the support assistant on Bedrock, and the auditors want every prompt and response kept for a year.

Status changes to know. The original Security Hub is now Security Hub CSPM; the new AWS Security Hub (generally available December 2025) correlates CSPM, Inspector, GuardDuty and Macie findings into exposures. AWS Audit Manager is closed to new customers (use Config conformance packs). SageMaker Model Monitor is no longer open to new customers. Control Tower landing zone 4.0 (November 2025) makes service integrations optional, no longer creates a Security OU, and no longer applies mandatory controls by default. New: CloudWatch Logs cross-account centralization (September 2025), Organizations policies for Security Hub, Inspector, GuardDuty and Bedrock guardrails, the GuardDuty AI Protection plan (July 2026), and RAM sharing for security groups, EBS volumes and EventBridge buses.

Organization structure and landing zones

Skill 2.3.1Design organizational structures that include features such as guardrails, landing zones, and automated account provisioning (for example, by using AWS Organizations, OUs, AWS Control Tower, AWS Control Tower Account Factory).

  • OUs by policy, not by org chart: group accounts that need the same guardrails. AWS's recommended layout has Security and Infrastructure OUs, Workloads OUs with Prod and SDLC children, a Sandbox OU, a Policy Staging OU for testing new SCPs, and a Suspended OU for accounts on their way out. Keep the management account empty of workloads, because SCPs and RCPs never apply to it.
  • Delegated administrators: run GuardDuty, Security Hub, Inspector, Config, Macie, IAM Identity Center and CloudTrail from a security or tooling account, not the management account. Control Tower is the exception: it has no delegated administrator and runs from the management account.
  • Control Tower builds the landing zone (log archive and audit accounts, an organization trail, Config, Identity Center) and governs OUs with controls: preventive (SCPs, RCPs, declarative policies), detective (Config rules) and proactive (CloudFormation hooks). Since landing zone 4.0 you can even run a controls-only setup. Accounts moved into a registered OU get its controls only if auto-enrollment is on.
  • Account vending: Account Factory creates enrolled accounts in a chosen OU; Account Factory Customization applies a CloudFormation or Terraform blueprint from a hub account; Account Factory for Terraform (AFT) runs a GitOps pipeline that requests accounts and applies global and per-account customizations. Accounts created directly in Organizations aren't enrolled in Control Tower.
  • Beyond Control Tower: CloudFormation StackSets with service-managed permissions deploy baselines automatically to every account added to an OU, and Organizations policies (backup, tag, AI opt-out, EC2, Security Hub, Inspector, GuardDuty, Bedrock) set service configuration centrally; unlike SCPs, these do apply to the management account.
Control Tower: allow only the primary and DR Regions for a workload OU, with read-only exemptions 
aws controltower update-enabled-control \
  --enabled-control-identifier arn:aws:controltower:us-east-1:111111111111:enabledcontrol/EXAMPLE_NAME \
  --parameters '[
    {"key":"AllowedRegions","value":["us-east-1","us-west-2"]},
    {"key":"ExemptedPrincipalArns",
     "value":["arn:aws:iam::*:role/ReadOnly"]}]'
# Changes the parameters of an OU-level Region deny control already enabled with enable-control

Invited accounts don't get OrganizationAccountAccessRole automatically, and an account needs the AWSControlTowerExecution role and no existing Config recorder before Control Tower can enroll it. Closed accounts stay in the organization for 90 days and count toward the account quota. In landing zone 4.0, drift notifications go to EventBridge in the management account, not SNS.

Centralized logging, including AI

Skill 2.3.2Implement centralized logging and configuration management solutions, including solutions for AI model invocations and responses (for example, by using AWS CloudTrail organization trails, AWS Config aggregation, AWS GuardDuty, Amazon Security Lake, AWS Security Hub, Amazon CloudWatch Logs).

  • API activity: one multi-Region organization trail (created by the management account or one of up to three CloudTrail delegated administrators) writes every account's events to the log archive bucket; member accounts can see it but not change it. Add data events (S3 objects, Lambda, Bedrock agents) with advanced event selectors where needed.
  • Application and service logs: CloudWatch Logs centralization rules copy log groups from accounts, OUs or the whole organization into one account and Region (one copy free); CloudWatch cross-account observability lets a monitoring account view metrics, logs and traces without copying.
  • Configuration: a Config organization aggregator in the security account gives a read-only view of resources and compliance across accounts and Regions, with SQL-like advanced queries.
  • Threats and posture: GuardDuty, Security Hub CSPM and Inspector each with one delegated administrator, auto-enabled for new accounts and aggregated to a home Region. Security Lake stores CloudTrail, VPC Flow Logs, Route 53, EKS audit, WAF and Security Hub findings in OCSF format in S3 for your own analytics and third-party SIEM subscribers.
  • AI model invocations and responses:
    • CloudTrail records InvokeModel and Converse calls as management events (who called which model), so the organization trail already has them, but without the prompt or response. Agents, knowledge base retrieval, flows and ApplyGuardrail are data events.
    • The content comes from Bedrock model invocation logging: off by default, set per account and Region, delivering full request and response bodies, token counts and caller identity to CloudWatch Logs and/or S3. Bodies over 100 KB and binary data go to S3 only.
    • Bedrock delivers only to a log group or bucket in the same account and Region, so centralizing is a second step: a CloudWatch Logs centralization rule, or S3 replication to the log archive account.
    • AgentCore agents send OpenTelemetry traces and logs to CloudWatch (GenAI observability, with Transaction Search on). SageMaker endpoints use data capture to S3.
  • Encrypt central log stores with customer managed keys, apply S3 Object Lock where logs are evidence, and remember that guardrail-blocked content still appears in plain text in invocation logs.
Central GenAI account 222222222222: log every prompt and response, large payloads to S3 
aws bedrock put-model-invocation-logging-configuration \
  --region us-east-1 \
  --logging-config '{
    "cloudWatchConfig": {
      "logGroupName": "/genai/bedrock-invocations",
      "roleArn": "arn:aws:iam::222222222222:role/BedrockInvocationLogging",
      "largeDataDeliveryS3Config": {
        "bucketName": "example-genai-invocation-logs-222222222222",
        "keyPrefix": "large"
      }
    },
    "textDataDeliveryEnabled": true,
    "imageDataDeliveryEnabled": true,
    "embeddingDataDeliveryEnabled": false
  }'
# Bucket and log group must be in this account and Region; a CloudWatch Logs
# centralization rule then copies the log group to the log archive account

No AWS Config managed rule, Security Hub CSPM control or CloudWatch telemetry rule turns on or checks Bedrock invocation logging. Deploy it with StackSets, protect it with an SCP, check it with a custom Config rule, and rely on the GuardDuty finding DefenseEvasion:IAMUser/BedrockLoggingDisabled. Config aggregators are read-only; you can't deploy rules or remediate through one.

Cross-account resource sharing

Skill 2.3.3Configure cross-account resource sharing (for example, AWS Resource Access Manager [AWS RAM], AWS Transit Gateway).

  • Turn on sharing with the organization from RAM (in the management account), which creates RAM's service-linked role. Then shares to the organization or an OU need no invitations, and accounts gain or lose access as they join or leave. Outside accounts get an invitation they must accept.
  • Managed permissions define what consumers can do with a shared resource: the AWS managed default, or a customer managed permission for least privilege on supported types. Consumer principals still need their own IAM permissions, and a resource shared with you can't be shared on.
  • What RAM shares: subnets and security groups (within the organization only), Transit Gateways, prefix lists, IPAM pools, Route 53 Resolver rules, Network Firewall policies and firewalls, VPC Lattice service networks and resource configurations, Private CAs, Aurora clusters (for cloning), Glue catalogs (through Lake Formation), License Manager configurations, Outposts, Bedrock custom models, EventBridge custom buses and EBS volumes. Services with native resource policies (S3, KMS, SQS, Lambda, Secrets Manager) share through those instead.
  • VPC sharing: the shared-network account owns the VPC, subnets, route tables, NACLs, gateways, endpoints and Transit Gateway attachment; participant accounts launch their own instances, databases and functions into shared subnets and own their security groups. Fewer VPCs, fewer attachments and less IP waste, with network control kept central.
  • Transit Gateway sharing: share the TGW, and consumer accounts attach their own VPCs. Leave auto accept shared attachments off so the network team accepts each attachment; route tables stay with the owner, so segmentation is central. The VPC owner pays attachment hours and the sender pays data processing, unless the owner sets a metering policy.
Shared-network account: share workload subnets with the Prod OU only 
aws ram create-resource-share \
  --name prod-shared-subnets \
  --no-allow-external-principals \
  --principals arn:aws:organizations::111111111111:ou/o-a1b2c3d4e5/ou-ab12-prod0001 \
  --resource-arns arn:aws:ec2:us-east-1:111111111111:subnet/subnet-0a1b2c3d4e5f60001 \
  --permission-arns arn:aws:ram::aws:permission/AWSRAMDefaultPermissionSubnet
SCP: no resource shares that allow principals outside the organization 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyExternalOnCreate",
      "Effect": "Deny",
      "Action": "ram:CreateResourceShare",
      "Resource": "*",
      "Condition": {
        "BoolIfExists": { "ram:RequestedAllowsExternalPrincipals": "true" }
      }
    },
    {
      "Sid": "DenyExternalOnUpdate",
      "Effect": "Deny",
      "Action": "ram:UpdateResourceShare",
      "Resource": "*",
      "Condition": {
        "Bool": { "ram:RequestedAllowsExternalPrincipals": "true" }
      }
    }
  ]
}

Enabling trusted access for RAM from the Organizations side doesn't create RAM's service-linked role, and sharing with the organization then fails. allowExternalPrincipals defaults to true, which is why the SCP uses BoolIfExists. Only the VPC owner can attach a shared VPC to a Transit Gateway, and participants can't use the VPC's default security group. A new version of an AWS managed permission isn't applied to existing shares until you update them.

SCPs and RCPs

Skill 2.3.4Design policy enforcement by using SCPs and RCPs.

  • SCPs cap what principals in member accounts can do (including their root users and delegated administrator accounts); RCPs cap what can be done to resources in member accounts, even by principals outside the organization. Neither grants anything, neither affects the management account or service-linked roles, and a Deny at any level wins.
  • Deny list, not allow list: keep FullAWSAccess and add Deny statements. An allow list means removing it and allowing only listed services at every level, which is hard to maintain. In Allow statements the resource can only be "*".
  • Typical SCPs: deny unused Regions (with exceptions for global services), deny leaving the organization, deny turning off CloudTrail, GuardDuty, Config, Security Hub or invocation logging, require IMDSv2 or encryption, and protect platform roles. Exempt the platform team with an aws:PrincipalArn condition.
  • Typical RCPs: the identity perimeter on S3, KMS, SQS, Secrets Manager and STS, enforcing TLS, and confused-deputy protection with aws:SourceOrgID (see Task 2.1).
  • Limits: 10 SCPs per target with up to 10,240 characters each; 5 RCPs per target (including the default) with up to 5,120 characters.
  • Rollout: attach to the Policy Staging OU first, check IAM last-accessed data and CloudTrail for what would break, then move up the tree.
SCP: only the platform role (which also deploys the logging setup) can change audit logging or threat detection 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectAuditAndDetection",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "guardduty:DeleteDetector",
        "guardduty:DisassociateFromAdministratorAccount",
        "config:StopConfigurationRecorder",
        "config:DeleteConfigurationRecorder",
        "bedrock:DeleteModelInvocationLoggingConfiguration",
        "bedrock:PutModelInvocationLoggingConfiguration"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/PlatformSecurityAdmin"
        }
      }
    }
  ]
}

"Stop any account from using a service" or "stop our principals reaching other organizations' buckets" means an SCP. "Stop anyone, including outside principals, from reading our buckets" means an RCP. "Enable GuardDuty or Inspector in every account and Region automatically" means an Organizations service policy or delegated administrator auto-enable, not an SCP. SCPs and RCPs never restrict the management account.

Automated compliance monitoring

Skill 2.3.5Implement automated compliance monitoring (for example, by using AWS Config rules, AWS Security Hub CSPM).

  • Config rules evaluate recorded resources: managed rules, or custom rules in Lambda or Guard; triggered on change or on a schedule, and in proactive mode against templates before deployment. Conformance packs bundle rules and remediations for a framework (PCI DSS, HIPAA, NIST and others) and deploy across the organization from the delegated administrator.
  • Remediation: Config runs Systems Manager Automation documents automatically or on demand; Security Hub sends findings to EventBridge for Lambda, Step Functions or ticketing.
  • Security Hub CSPM runs standards (AWS Foundational Security Best Practices, CIS, PCI DSS, NIST 800-53) on Config's service-linked rules. With central configuration, the delegated administrator sets standards and controls per OU and aggregates findings to the home Region. It needs Config recording in every account and Region it checks.
  • Evidence for auditors: Audit Manager is closed to new customers, so use conformance pack compliance history, Config advanced queries and AWS Artifact reports.
Security account: noncompliant resources across the organization, from the aggregator 
aws configservice select-aggregate-resource-config \
  --configuration-aggregator-name org-aggregator \
  --expression "SELECT configuration.complianceType, COUNT(*)
    WHERE resourceType = 'AWS::Config::ResourceCompliance'
    GROUP BY configuration.complianceType"

Security Hub CSPM is Regional and only sees findings created after it's enabled; full CIS coverage needs it in every Region. Record global IAM resource types in only one Region to avoid duplicate items and cost. Organization rules and conformance packs deployed from the management account and from the delegated administrator can't see each other.

Vulnerability scanning and patching

Skill 2.3.6Implement automated vulnerability scanning and patch management (for example, by using Amazon Inspector, AWS Systems Manager Patch Manager).

  • Amazon Inspector scans continuously, with one delegated administrator for the organization:
    • EC2: agent-based through SSM, or agentless from EBS snapshots for unmanaged instances, plus network reachability.
    • ECR images: on push and when new CVEs appear.
    • Lambda: functions and layers, with optional code scanning.
    • Also: code repositories, AMIs, CIS benchmark scans and SBOM export.
    • Findings flow to Security Hub and EventBridge.
  • Organization-wide enablement: an Organizations Inspector policy turns scan types on per Region for every account, including new ones; a disable list wins over an enable list.
  • Patch Manager patch policies (Quick Setup) are the recommended way to patch across accounts and Regions: one policy with separate scan and install schedules and patch baselines per OS, running AWS-RunPatchBaseline. Compliance is reported per account and Region and can be exported to Security Hub CSPM.
  • Close the loop: an EventBridge rule on critical Inspector findings starts an Automation runbook or a patch run, and immutable workloads are fixed by rebuilding the image (EC2 Image Builder with Inspector scanning) rather than patching in place.
Organizations Inspector policy: EC2 and ECR scanning in the primary and DR Regions 
{
  "inspector": {
    "enablement": {
      "ec2_scanning": {
        "enable_in_regions": { "@@assign": ["us-east-1", "us-west-2"] }
      },
      "ecr_scanning": {
        "enable_in_regions": { "@@assign": ["us-east-1", "us-west-2"] }
      }
    }
  }
}

Detaching an Inspector, Security Hub or GuardDuty Organizations policy leaves the service on but stops auto-enabling new accounts. Predefined patch baselines can't be edited; copy one to change approval rules. With NoReboot, patched nodes stay noncompliant (InstalledPendingReboot) until they restart and are scanned again, and the Security Hub finding isn't closed automatically.

Key takeaways

  • Structure: OUs grouped by guardrails, an empty management account, delegated administrators in a security account, Control Tower controls and Account Factory (or AFT) for enrolled accounts, StackSets and Organizations service policies for baselines.
  • Logging: organization trail to the log archive, CloudWatch Logs centralization rules, a Config organization aggregator, GuardDuty, Security Hub and Security Lake in the security account.
  • AI logging: CloudTrail shows who called which model; Bedrock invocation logging (same account and Region) holds prompts and responses, then gets centralized and protected with an SCP and GuardDuty.
  • Sharing: enable RAM organization sharing from RAM, share subnets, Transit Gateways and other resources to OUs, block external principals with an SCP, keep route tables and attachments with the network account.
  • Enforcement: SCPs on principals, RCPs on resources, deny lists with platform-role exceptions, staged rollout; compliance with Config rules, conformance packs and Security Hub CSPM central configuration; Inspector policies and Patch Manager patch policies for scanning and patching.
