Overview

Task 1.4

Design network architectures.

Network questions at Professional level describe an organization that has grown: overlapping CIDRs from an acquisition, a security team that wants all traffic inspected, a partner that needs access to one service, IPv4 addresses running out. The answer is usually the option that meets the requirement with the least to operate. The SAA Task 3.4 notes cover the building blocks (Transit Gateway, Cloud WAN, peering basics) and the Advanced Networking notes go deeper; Direct Connect, VPN and hybrid DNS are in Task 1.3.

Running example. A shared-network account owns the Transit Gateways in us-east-1 and us-west-2, the IPAM pools, the inspection VPC and the Direct Connect gateway. Business-unit accounts run production, staging and development VPCs; a newly acquired subsidiary uses 10.0.0.0/16, which overlaps a production VPC; and a payments partner needs private access to one API.

Status changes to know. New since late 2024: cross-Region PrivateLink for your own endpoint services (November 2024) and for about nine AWS services (November 2025), VPC Lattice resource configurations and resource gateways (December 2024), PrivateLink tunnel endpoints (September 2026), the Regional NAT gateway (November 2025), IPAM policies and the IPAM prefix list resolver (late 2025), Network Firewall's native Transit Gateway attachment (June 2025) and active threat defense (June 2025), and Route 53 geoproximity directly in record sets. Network Firewall now recommends Next Generation policies for new firewalls; Classic policies remain fully supported. The Network Firewall proxy is still in preview. AWS WAF Classic support ended on 30 September 2025.

Multi-VPC and multi-account connectivity

Skill 1.4.1Design multi-VPC architectures that provide hybrid and multi-account connectivity (for example, VPC peering, AWS PrivateLink).

Choose by what has to be connected:

  • VPC peering: a one-to-one link, cross-account and cross-Region, no data processing charge, but not transitive, no overlapping CIDRs and no edge-to-edge routing (you can't reach a peer's NAT gateway, VPN or Direct Connect). Fine for a few VPCs with heavy traffic between them.
  • Transit Gateway: the hub for many VPCs, VPNs and Direct Connect, with route tables for segmentation and $0.02 per GB processed. Cloud WAN runs the same model globally from one policy.
  • PrivateLink endpoint services: a provider puts a service behind an NLB (or a GWLB for appliances); consumers create interface endpoints in their own VPCs. Access is one way, and overlapping CIDRs don't matter. The provider lists --supported-regions to offer the service cross-Region, and the consumer passes --service-region. AWS services such as S3, KMS, ECR and Lambda can now be reached cross-Region too.
  • VPC Lattice resource configurations: share a single resource (an IP address, domain name or RDS database) through a resource gateway in the provider VPC, with no NLB. They are TCP only and shared through AWS RAM. Consumers connect with a resource endpoint, a service network endpoint or a service network VPC association. Lattice services handle HTTP and gRPC service-to-service traffic (Task 1.1).
  • PrivateLink tunnel endpoints: share whole CIDR ranges rather than single resources. The consumer's hosts build GENEVE tunnels (UDP 6081) to the endpoint; overlapping CIDRs work because the provider addresses exist only inside the tunnel.
  • Shared VPCs (AWS RAM): the network account owns the VPC, subnets, routes, gateways and NACLs; participant accounts launch their own resources into shared subnets and keep their own IAM and billing. Fewer VPCs and no inter-VPC routing, but one blast radius and shared VPC quotas. A common pattern is one shared VPC per environment or portfolio, joined by Transit Gateway.
Offer the partner API to consumers in us-west-2 too, then connect from there (AWS CLI) 
# Provider (us-east-1): an endpoint service behind the API's NLB, open to another Region
aws ec2 create-vpc-endpoint-service-configuration --region us-east-1 \
    --network-load-balancer-arns arn:aws:elasticloadbalancing:us-east-1:111111111111:loadbalancer/net/payments-api/0a1b2c3d4e5f6071 \
    --acceptance-required \
    --supported-regions us-east-1 us-west-2

# Consumer (in us-west-2): an interface endpoint to the service hosted in us-east-1
aws ec2 create-vpc-endpoint --region us-west-2 --vpc-endpoint-type Interface \
    --vpc-id vpc-0a1b2c3d4e5f60001 \
    --service-name com.amazonaws.vpce.us-east-1.vpce-svc-0a1b2c3d4e5f60002 \
    --service-region us-east-1 \
    --subnet-ids subnet-0a1b2c3d4e5f60003 subnet-0a1b2c3d4e5f60004

Cross-Region PrivateLink needs the permission-only IAM action vpce:AllowMultiRegion on both sides, so an SCP that denies it blocks the design. PrivateLink fails over between Availability Zones but never between Regions: for Regional resilience, deploy the service in both Regions. A resource shared through RAM can be added to the consumer's own service network and shared onward unless the provider blocks association with shareable service networks.

Subnets, IPAM and segmentation

Skill 1.4.2Design VPC architectures by using subnet strategies, IP address management, and network segmentation (for example, by using Amazon VPC IP Address Manager [IPAM], public and private subnets).

  • IPAM pools: a top-level pool for the organization, Regional pools below it, then pools per environment or business unit (up to 10 levels deep). Allocation rules set minimum, maximum and default netmask lengths and required resource tags. IPAM tracks every VPC and subnet as compliant or not and flags overlaps. Resource planning pools extend this to subnets inside a VPC.
  • Organization setup: delegate IPAM to a member account (the shared-network account) through IPAM itself (enable-ipam-organization-admin-account), not through the Organizations delegated administrator command, which leaves IPAM unable to monitor member accounts. Share pools with AWS RAM. Managing private IPv4 across Regions or accounts needs the Advanced tier ($0.00027 per active IP per hour).
  • Newer IPAM features: the prefix list resolver keeps customer-managed prefix lists (used in security groups and route tables) in step with IPAM pools and tagged resources; IPAM policies make Elastic IPs, ALBs, RDS and Regional NAT gateways take public IPv4 addresses from your BYOIP pools.
  • Subnet tiers: public (load balancers, NAT), private application, private data, plus small dedicated subnets for Transit Gateway attachments and firewall endpoints in each AZ. Each subnet loses 5 addresses to AWS. Add secondary CIDRs when a VPC runs out; 100.64.0.0/10 secondary ranges for EKS pods with custom networking (or an IPv6 cluster) solve pod IP exhaustion.
  • Overlapping networks (the acquired subsidiary): a private NAT gateway translates to a routable range, PrivateLink or Lattice exposes only the services needed, or Transit Gateway or Cloud WAN 1:1 NAT (October 2026) maps whole ranges.
  • Regional NAT gateway: one NAT gateway ID for every AZ, no public subnet required, and it expands to a new AZ when workloads appear there (taking up to 60 minutes). It's billed per active AZ and can't do private NAT.
SCP: no VPC or extra CIDR unless it comes from an IPAM pool (attached to the workload OUs) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireIpamForVpcCidrs",
      "Effect": "Deny",
      "Action": ["ec2:CreateVpc", "ec2:AssociateVpcCidrBlock"],
      "Resource": "arn:aws:ec2:*:*:vpc/*",
      "Condition": {
        "Null": { "ec2:Ipv4IpamPoolId": "true" }
      }
    }
  ]
}
A workload account then creates its VPC from the shared production pool (AWS CLI) 
aws ec2 create-vpc --ipv4-ipam-pool-id ipam-pool-0a1b2c3d4e5f60001 --ipv4-netmask-length 22

"Prevent overlapping CIDRs across hundreds of accounts" points to IPAM pools shared through RAM plus an SCP like the one above. "Security group rules must follow a changing set of CIDRs" points to the prefix list resolver. "Partners must allow-list our egress IPs" points to BYOIP through IPAM, with IPAM policies so new NAT gateways and Elastic IPs use those addresses.

Inspection and filtering

Skill 1.4.3Design network security architectures that include traffic inspection, traffic filtering, and application layer protection (for example, by using AWS Network Firewall, AWS WAF, Gateway Load Balancers, security groups, network ACLs, VPC Flow Logs).

Where to inspect:

  • Centralized: one inspection VPC on the Transit Gateway inspects east-west (VPC to VPC), egress to the internet and hybrid traffic. Spoke route tables send 0.0.0.0/0 to the inspection attachment. Turn on appliance mode on that attachment so both directions of a flow use the same AZ, and attach exactly one Transit Gateway to the inspection VPC. Network Firewall's native Transit Gateway attachment builds this for you, with appliance mode always on.
  • Distributed: a firewall in each VPC, often for internet ingress, using an IGW route table (ingress routing) that sends inbound traffic to the firewall endpoint before the application subnets. Many designs combine both.
  • Firewall Manager applies WAF, Shield Advanced, security group, NACL, Network Firewall and DNS Firewall policies across the organization, including new accounts. It needs AWS Config, and RAM sharing for Network Firewall and DNS Firewall policies.

What does the inspecting:

  • AWS Network Firewall: managed stateful inspection with Suricata-compatible rules, domain lists (by TLS SNI or HTTP Host), TLS inspection, AWS managed threat signatures and active threat defense, scaling to 100 Gbps per AZ. Each endpoint needs its own subnet, because an endpoint can't filter its own subnet. Next Generation policies have a firewall engine (drop by default) followed by an IPS engine.
  • Gateway Load Balancer: third-party appliances behind GWLB endpoints, using GENEVE on port 6081. Cross-zone load balancing is off by default, and GENEVE adds 68 bytes, so appliances need a larger MTU.
  • AWS WAF: layer 7 rules on CloudFront, ALB, API Gateway, AppSync, Cognito, App Runner and Verified Access: managed rule groups, rate-based rules, Bot Control and fraud prevention (ATP and ACFP). Use WAF at CloudFront for internet-facing web traffic, with Shield Advanced for DDoS protection and cost protection.
  • Security groups and NACLs: security groups are stateful and can reference groups in peered VPCs in the same Region, or across a Transit Gateway once security group referencing is turned on (inbound only). NACLs are stateless (allow ephemeral ports 1024-65535 for return traffic), with up to 40 rules each way. VPC Block Public Access overrides both to stop internet traffic at the account or Region level.
  • Visibility: VPC Flow Logs with custom fields (pkt-srcaddr for the address behind a NAT, traffic-path, reject-reason, and the new tag and next-hop fields), Traffic Mirroring for full packet copies, Reachability Analyzer for one path, and Network Access Analyzer to prove that no unintended paths exist (for example, nothing in production reaches an IGW without passing the firewall).
Egress allow-list in strict order: block old TLS, allow only partner domains (Suricata rules, Network Firewall stateful rule group) 
reject tls $HOME_NET any -> $EXTERNAL_NET any (msg:"TLS 1.0 or 1.1"; ssl_version:tls1.0,tls1.1; sid:100;)
pass tls $HOME_NET any -> $EXTERNAL_NET 443 (tls.sni; dotprefix; content:".payments.example.net"; nocase; endswith; flow:to_server, established; sid:200;)
pass http $HOME_NET any -> $EXTERNAL_NET 80 (http.host; dotprefix; content:".updates.example.org"; endswith; flow:to_server, established; sid:300;)
The firewall policy: strict order, and drop anything the rules don't pass (firewall policy JSON, excerpt) 
{
  "StatelessDefaultActions": ["aws:forward_to_sfe"],
  "StatelessFragmentDefaultActions": ["aws:forward_to_sfe"],
  "StatefulEngineOptions": { "RuleOrder": "STRICT_ORDER" },
  "StatefulDefaultActions": ["aws:drop_established", "aws:alert_established"],
  "StatefulRuleGroupReferences": [
    { "ResourceArn": "arn:aws:network-firewall:us-east-1:111111111111:stateful-rulegroup/egress-allow", "Priority": 100 }
  ]
}

Domain lists and $HOME_NET cover only the firewall's own VPC by default; in a centralized inspection VPC, set HOME_NET to the spoke CIDRs or spoke traffic isn't matched. The automatic "drop everything else" rule of an allow-list is created only with default action order; with strict order you set StatefulDefaultActions yourself, and the rule order can't be changed after the policy is created. Network Firewall can't inspect VPC peering traffic, Global Accelerator traffic with client IP preservation, or TLS an ALB has already terminated.

IPv6 and dual-stack

Skill 1.4.4Design IPv6 adoption and dual-stack migration strategies.

  • Why: IPv4 exhaustion (especially for EKS pods), the $0.005 per hour charge on every public IPv4 address, and customers or regulators that require IPv6.
  • Migration path: you can't remove IPv4 from a VPC, and there's no way to convert an IPv4-only subnet to IPv6-only. Add an IPv6 CIDR to the VPC and subnets (dual-stack), add ::/0 routes (internet gateway for public subnets, egress-only internet gateway for private ones), update security groups and NACLs, then build new IPv6-only subnets for workloads that support it.
  • Addresses: Amazon gives a /56 per VPC and /64 subnets; IPAM can hand out IPv6 from your own (BYOIP) or Amazon-provided contiguous blocks, and is the only source of private IPv6 (ULA) addresses.
  • Reaching IPv4 from IPv6-only: turn on DNS64 on the subnet and route 64:ff9b::/96 to a NAT gateway, which always performs NAT64. This works for IPv4-only destinations on the internet and on premises.
  • Service support: EC2 on Nitro, ECS, EFS, ElastiCache, CloudFront and Network Firewall work IPv6-only; Lambda, RDS and Aurora, API Gateway, S3, Transit Gateway and Global Accelerator are dual-stack only. An internet-facing ALB can be dualstack-without-public-ipv4 to drop public IPv4 charges (IPv4-only clients then can't reach it).
  • EKS: the IP family is fixed when the cluster is created. In an IPv6 cluster pods get IPv6 addresses and reach IPv4 through the node's address, without NAT64; it can't be combined with custom networking or Windows nodes.
An IPv6-only subnet that can still reach IPv4-only services (AWS CLI) 
aws ec2 modify-subnet-attribute --subnet-id subnet-0a1b2c3d4e5f60005 --enable-dns64

# Synthesised IPv4 destinations go to the NAT gateway, everything else IPv6 to the egress-only IGW
aws ec2 create-route --route-table-id rtb-0a1b2c3d4e5f60006 \
    --destination-ipv6-cidr-block 64:ff9b::/96 --nat-gateway-id nat-0a1b2c3d4e5f60007
aws ec2 create-route --route-table-id rtb-0a1b2c3d4e5f60006 \
    --destination-ipv6-cidr-block ::/0 --egress-only-internet-gateway-id eigw-0a1b2c3d4e5f60008

Security groups and NACLs need rules for 64:ff9b::/96 too. An interface endpoint with IP address type ipv6 requires every chosen subnet to be IPv6-only; use dualstack in dual-stack subnets. Moving the ALB to dualstack-without-public-ipv4 before checking access logs for IPv4-only clients cuts them off.

Global traffic routing

Skill 1.4.5Design global traffic routing strategies for multi-Region applications (for example, by using Route 53 routing policies, AWS Global Accelerator).

Route 53 routing policies:

  • Latency: sends users to the Region with the lowest measured latency, for active-active.
  • Geolocation: answers by continent, country or US state, for content rights or data residency. Add a default (*) record, or users from unmapped locations get no answer.
  • Geoproximity: answers by distance to an AWS Region, Local Zone or coordinates, and shifts boundaries with a bias from -99 to 99. It's now set directly on records, without Traffic Flow.
  • Weighted: splits traffic by weight (0 to 255), for canary or blue/green moves between Regions.
  • Failover: a primary and a secondary, for active-passive.
  • IP-based: answers by the resolver's CIDR (for example by ISP); not available in private hosted zones.
  • Multivalue answer: up to 8 healthy records.

Policies can be nested (geolocation to weighted to failover) with alias records. Health checks decide which records are returned. If every record in a group is unhealthy, Route 53 answers as if all are healthy.

AWS Global Accelerator gives two static anycast IPv4 addresses (four with dual-stack) at the AWS edge, then carries traffic over the AWS network to endpoint groups in each Region (ALBs, NLBs, EC2 instances, Elastic IPs). It reacts to unhealthy endpoints without waiting for DNS caches to expire.

  • Traffic dials (0 to 100%) per Region and endpoint weights (0 to 255, default 128) per endpoint shift traffic.
  • It works for any TCP or UDP application, which suits games, VoIP and partners that allow-list fixed IP addresses.
  • Custom routing accelerators map users to specific EC2 instances and ports, with no health checks or failover.

CloudFront remains the answer for cacheable HTTP content and edge compute. For DR, prefer data-plane mechanisms (health-checked records or ARC routing controls, Task 4.2) over editing records or dials during an incident.

Latency routing between the two Regions, each answer tied to its ALB's health (change batch for aws route53 change-resource-record-sets) 
{
  "Comment": "Latency records for api.example.com",
  "Changes": [
    { "Action": "UPSERT", "ResourceRecordSet": {
        "Name": "api.example.com", "Type": "A", "SetIdentifier": "use1", "Region": "us-east-1",
        "AliasTarget": { "HostedZoneId": "Z35SXDOTRQ7X7K", "DNSName": "web-use1-1234567890.us-east-1.elb.amazonaws.com", "EvaluateTargetHealth": true } } },
    { "Action": "UPSERT", "ResourceRecordSet": {
        "Name": "api.example.com", "Type": "A", "SetIdentifier": "usw2", "Region": "us-west-2",
        "AliasTarget": { "HostedZoneId": "Z1H1FL5HABSF5", "DNSName": "web-usw2-1234567890.us-west-2.elb.amazonaws.com", "EvaluateTargetHealth": true } } }
  ]
}
Drain us-west-2 behind the accelerator before maintenance (AWS CLI) 
aws globalaccelerator update-endpoint-group --region us-west-2 \
    --endpoint-group-arn arn:aws:globalaccelerator::111111111111:accelerator/0a1b2c3d-1111-2222-3333-444455556666/listener/0a1b2c3d/endpoint-group/0a1b2c3d4e5f \
    --traffic-dial-percentage 0

A traffic dial is a percentage of the traffic already headed to that Region, not of all traffic; the rest goes to other Regions. Dial and weight changes affect new connections only; established connections stay on an endpoint, even an unhealthy one, until the idle timeout (340 seconds for TCP, 30 for UDP). Like Route 53, a standard accelerator with no healthy endpoints sends traffic to all of them.

Key takeaways

  • Connectivity: peering for a few VPCs, Transit Gateway or Cloud WAN as the hub, PrivateLink (now cross-Region) for one-way service access, Lattice resource configurations for single TCP resources, tunnel endpoints for whole ranges, shared VPCs to reduce VPC count.
  • IP planning: IPAM pools by Region and environment in a delegated member account, shared with RAM and enforced by SCP; prefix list resolver and IPAM policies; Regional NAT gateway for simpler egress, private NAT or 1:1 NAT for overlaps.
  • Inspection: centralized on Transit Gateway with appliance mode (or the native Network Firewall attachment) or distributed with ingress routing; widen HOME_NET; set default actions under strict order; Firewall Manager for the organization.
  • IPv6: dual-stack first, then new IPv6-only subnets; DNS64 plus a 64:ff9b::/96 route to a NAT gateway for IPv4 destinations; know which services are dual-stack only.
  • Global routing: Route 53 policies for DNS-based steering (latency, geolocation, geoproximity, weighted, failover), Global Accelerator for static IPs and fast failover for any TCP or UDP application.
