Overview

Task 5.1

Design infrastructure as code.

The Professional angle is design across many accounts: which tool fits which team, where checks run (in the IDE, at synthesis, at deployment, after deployment), how drift is found and fixed, and how one template reaches every account. Template mechanics, StackSets options and Hooks setup are in the DOP infrastructure as code notes and the SCS secure deployment notes.

Running example. The platform team writes the landing zone baselines (Config, logging roles, VPCs) in CloudFormation and deploys them with StackSets to every account. Application teams build services in the CDK in TypeScript. Security requires encrypted, versioned buckets, no plaintext secrets in any template, and an automatic fix when someone changes a stack by hand.

Status changes to know. In the CDK, Stage.policyValidationBeta1 is deprecated in favor of Validations.of(scope).addPlugins() (April 2026), and SecretValue.plainText is deprecated. New: CDK Aspect priorities (December 2024), CloudFormation stack refactoring (February 2025) and cdk refactor (preview, September 2025), cdk drift (May 2025), the CDK Toolkit Library (May 2025), Control Tower proactive controls activated as Hooks (September 2025), drift-aware change sets (November 2025), CloudFormation pre-deployment validation (change sets November 2025, every stack operation June 2026), CDK Mixins (2026), Fn::GetStackOutput for cross-account and cross-Region references (May 2026), and a development-only express mode (July 2026).

Declarative and imperative IaC

Skill 5.1.1Implement infrastructure as code by using declarative and imperative approaches (for example, AWS CloudFormation, AWS CDK).

  • CloudFormation (declarative): you describe the end state in JSON or YAML, and CloudFormation works out the order, creates and updates resources, and rolls back on failure. Change sets preview updates; stack policies, termination protection and a service role limit what an update may do. Fn::ForEach (with the AWS::LanguageExtensions transform) cuts repetition. The IaC generator creates templates from existing resources.
  • AWS CDK (imperative code, declarative result): you write TypeScript, Python, Java, C# or Go, and cdk synth produces CloudFormation templates.
    • Construct levels: L1 constructs map one-to-one to CloudFormation resources, L2 adds sensible defaults and helper methods (bucket.grantRead(role)), and L3 patterns combine many resources.
    • Structure: an App holds Stages, which hold Stacks.
    • Commands: cdk diff compares your code with the deployed template, and cdk deploy runs a change set.
  • Choosing: CloudFormation suits baselines that StackSets and Control Tower deploy, and teams that review plain templates. The CDK suits application teams who want loops, types, tests and shared construct libraries. Either way, CloudFormation does the deployment, so its features (rollback, Hooks, drift detection, StackSets) still apply.
  • CDK Pipelines are self-mutating CodePipeline pipelines that deploy stages to accounts and Regions in waves, with approvals. Target accounts are bootstrapped to trust the pipeline account with a scoped-down execution policy (the default is AdministratorAccess).
  • Restructuring without replacement: CloudFormation stack refactoring and cdk refactor move resources between stacks or rename them without recreating them, as long as nothing else changes in the same operation.
  • Cross-stack values: exports and Fn::ImportValue give strong references in one account and Region. Fn::GetStackOutput reads outputs across accounts and Regions as a weak reference that doesn't stop the producer being changed.

"Developers want to define infrastructure in the same language as the application, with unit tests" points to the CDK. "Rename a construct without the database being replaced" points to cdk refactor or stack refactoring. "Find out what will change before deploying" is a change set or cdk diff.

Policy as code and drift

Skill 5.1.2Design policy as code to perform proactive validation, enforcement, and drift remediation (for example, by using AWS CloudFormation Hooks, AWS CDK aspects, AWS Config rules, SCPs).

  • Layers, earliest to latest:
    1. In the IDE and pipeline: cfn-lint, cfn-guard and cdk-nag on templates.
    2. At synthesis (CDK):
      • Aspects visit every construct. Mutating aspects (tagging) run before read-only checks, by priority. Annotations.of(node).addError() fails the synth.
      • Validation plugins such as CfnGuardValidator run Guard rules, including Control Tower proactive control rules.
    3. At deployment:
      • CloudFormation Hooks check resources, whole stacks, change sets and Cloud Control API calls before provisioning, and fail or warn. They can be written as Guard Hooks, Lambda Hooks, or Control Tower proactive controls.
      • Pre-deployment validation catches property errors and name conflicts.
    4. Always: SCPs and RCPs deny what must never happen, whatever tool is used.
    5. After deployment: AWS Config rules detect noncompliant resources, including ones changed outside IaC, and remediate with Systems Manager Automation.
  • Synth-time checks can be bypassed (someone can deploy a template by hand), so AWS pairs them with Hooks, Config or SCPs for enforcement.
  • Drift: CloudFormation drift detection (and cdk drift) compares the deployed template with live resources. It only reports, and it checks only explicitly set properties. Two ways to fix drift:
    • Drift-aware change sets (--deployment-mode REVERT_DRIFT, or cdk deploy --revert-drift) compare actual state, the previous deployment and the new template, and put drifted properties back. A normal change set leaves out-of-band changes in place if the template didn't change.
    • Config runs the managed rule cloudformation-stack-drift-detection-check for continuous detection.
CDK Aspect: fail synthesis for any bucket without versioning, after tagging aspects have run 
import { Aspects, AspectPriority, Annotations, IAspect, Tokenization } from 'aws-cdk-lib';
import * as s3 from 'aws-cdk-lib/aws-s3';
import { IConstruct } from 'constructs';

class RequireVersioning implements IAspect {
  public visit(node: IConstruct): void {
    if (!(node instanceof s3.CfnBucket)) return;   // the L2 Bucket wraps a CfnBucket
    const v = node.versioningConfiguration;
    if (Tokenization.isResolvable(v)) return;      // can't check unresolved tokens
    const status = (v as s3.CfnBucket.VersioningConfigurationProperty)?.status;
    if (status !== 'Enabled') {
      Annotations.of(node).addError('S3 buckets must have versioning enabled');
    }
  }
}

Aspects.of(app).add(new RequireVersioning(), { priority: AspectPriority.READONLY });
// Apply to each Stage too: aspects don't cross Stage boundaries
Put a hand-edited stack back to what the template says 
aws cloudformation create-change-set \
  --stack-name orders-network \
  --change-set-name revert-manual-changes \
  --use-previous-template \

Aspects don't cross Stage boundaries, so in CDK Pipelines add them to each Stage. Drift detection ignores default values, nested stacks (run it on each one), KMSKeyId properties and write-only values. Hooks start in WARN mode during rollout; in FAIL mode a Hook that times out or errors blocks the deployment. Config remediation can run against resources that are already compliant, because it works from earlier evaluations.

Secrets in infrastructure code

Skill 5.1.3Manage secrets in infrastructure code (for example, by using AWS Secrets Manager, AWS Systems Manager Parameter Store).

  • Let the service own the secret: RDS and Aurora with ManageMasterUserPassword create the master password in Secrets Manager, rotate it every 7 days by default, and never show it in the template. An IAM condition on rds:ManageMasterUserPassword can require it. AWS::SecretsManager::Secret with GenerateSecretString creates other secrets inside the stack.
  • Reference, don't embed:
    • Secrets Manager: dynamic references ({{resolve:secretsmanager:...}}) resolve at deployment time in any resource property, and need the full ARN for a secret in another account.
    • Parameter Store: {{resolve:ssm-secure:...}} works only on a fixed list of properties (such as RDS and Redshift master passwords and ElastiCache auth tokens) and never across accounts.
    • Limits: up to 60 dynamic references per template; none in EC2 user data or cfn-init metadata.
  • Prefer runtime retrieval: pass the secret's ARN, not its value, and have the application read it with the SDK, the Secrets Manager Lambda extension, ECS secrets or the CSI driver. Secrets passed through environment variables or templates aren't refreshed when they rotate; a resource using a dynamic reference only re-reads it when that resource is updated.
  • CDK: SecretValue.secretsManager() and Secret.fromSecretAttributes() produce dynamic references, and StringParameter.valueForStringParameter() a deploy-time token. valueFromLookup() reads at synthesis and writes the value into the template and cdk.context.json, so never use it for secrets.
  • Choosing the store: Secrets Manager for credentials (rotation, cross-Region replication, resource policies, 64 KB) and Parameter Store for configuration (free standard tier, advanced tier for 8 KB values, policies and sharing).
  • Never put secrets in parameters with defaults, Outputs or Metadata; NoEcho masks parameter values in describe calls but not in outputs or metadata.
CloudFormation: Aurora with an RDS-managed master secret, and an app that gets only the ARN 
OrdersCluster:
  Type: AWS::RDS::DBCluster
  Properties:
    Engine: aurora-postgresql
    MasterUsername: orders_admin
    ManageMasterUserPassword: true          # RDS creates and rotates the secret
    MasterUserSecret:
      KmsKeyId: !Ref OrdersSecretsKey       # can't be changed later

OrdersApi:
  Type: AWS::Lambda::Function
  Properties:
    # ... runtime, handler, role, code ...
    Environment:
      Variables:
        DB_SECRET_ARN: !GetAtt OrdersCluster.MasterUserSecret.SecretArn

ManageMasterUserPassword can't be combined with MasterUserPassword, can't change its KMS key later, and isn't supported for most read replicas, Blue/Green deployments or RDS Custom. ssm-secure references can't read parameters from other accounts. Using a rotated secret through a dynamic reference doesn't update the resource until the stack changes that resource.

Multi-account and multi-Region deployments

Skill 5.1.4Design multi-account and multi-Region infrastructure deployments (for example, by using CloudFormation StackSets).

  • StackSets deploy one template as stack instances in many accounts and Regions.
    • Service-managed permissions (with Organizations) target OUs or the whole organization, create roles automatically, and with automatic deployment add stacks to accounts that join an OU and remove them when accounts leave. Up to five delegated administrators can operate them, and stacks are never deployed to the management account.
    • Self-managed permissions use your own administration and execution roles and can target any account, including outside the organization.
  • Roll out safely:
    • Operation preferences: maximum concurrent accounts, failure tolerance per Region, sequential or parallel Regions in a chosen order, and the concurrency mode (strict or soft failure tolerance).
    • Managed execution queues conflicting operations instead of failing them.
    • Dependencies: auto-deployment can declare dependencies on other StackSets.
    • Parameter overrides: set per account and Region values; auto-deployed accounts get the defaults.
  • Limits to design around: service-managed StackSets don't support nested stacks, macros or transforms (including SAM and AWS::Include); template updates go to all instances; StackSet drift detection doesn't remediate.
  • Other paths: CDK Pipelines with waves and stages per account and Region for application stacks; Control Tower Account Factory customizations or AFT for account baselines; CloudFormation Git sync for GitOps on single stacks.
Baseline to every account in the workload OUs, both Regions, one account at a time per Region 
aws cloudformation create-stack-set \
  --stack-set-name security-baseline \
  --template-url https://s3.us-east-1.amazonaws.com/example-iac-templates/baseline.yaml \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation create-stack-instances \
  --stack-set-name security-baseline \
  --deployment-targets OrganizationalUnitIds=ou-ab12-prod0001,ou-ab12-dev00001 \
  --regions us-east-1 us-west-2 \
  --operation-preferences RegionConcurrencyType=SEQUENTIAL,MaxConcurrentCount=1,FailureToleranceCount=0

Auto-deployment ignores account filters and gives new accounts the default parameter values. A delegated administrator must pass --call-as DELEGATED_ADMIN, and can deploy to any account in the organization. With strict failure tolerance, maximum concurrency can't exceed the tolerance plus one. A StackSet is Regional: manage it in the Region where it was created.

Key takeaways

  • IaC: CloudFormation for declarative baselines, the CDK for application teams (L1, L2, L3 constructs, synth to CloudFormation), CDK Pipelines for multi-account delivery, refactoring without replacement.
  • Policy as code: linters and cdk-nag early, Aspects and validation plugins at synth, Hooks and proactive controls at deployment, SCPs always, Config rules with remediation after; synth checks alone can be bypassed.
  • Drift: detection reports only; drift-aware change sets or cdk deploy --revert-drift fix it; Config watches continuously.
  • Secrets: service-managed secrets (RDS), dynamic references or ARNs instead of values, runtime retrieval for rotation, never valueFromLookup, outputs or defaults for secrets.
  • Multi-account: service-managed StackSets with auto-deployment to OUs, careful operation preferences, no transforms or nested stacks, CDK Pipelines and AFT for other layers.
