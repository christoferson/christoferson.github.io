Task 5.2: Design CI/CD and DevSecOps pipelines

Overview

Task 5.2

Design CI/CD and DevSecOps pipelines.

The design questions are about where the pipeline lives, what gates it, and how it reaches other accounts and Regions. Detailed pipeline configuration is in the DOP CI/CD pipeline notes, DOP automated testing notes and DOP deployment strategy notes; infrastructure templates and StackSets are on Task 5.1.

Running example. A DevOps (tools) account (111111111111) runs the pipelines. Source is in GitHub through CodeConnections. Container services deploy to ECS in dev, staging and prod accounts in us-east-1 and us-west-2; Lambda functions and CloudFormation stacks follow the same path. Security requires scanned, signed images only, and the support assistant must not ship a prompt change that lowers answer quality.

Build and deployment pipelines

Skill 5.2.1Design CI/CD solutions to orchestrate automated build and deployment pipelines (for example, by using AWS CodePipeline, AWS CodeBuild, AWS CodeDeploy, AWS CodeCommit).

  • CodePipeline V2 (billed per action-minute; pipelines default to V1 unless you choose V2):
    • Triggers on Git tags, branches, file paths and pull requests for GitHub, GitLab, Bitbucket and Azure DevOps sources through CodeConnections. CodeCommit and S3 sources use EventBridge.
    • Execution modes: superseded (the default, newer runs overtake waiting ones), queued (one at a time, in order) or parallel (independent runs, for feature branches).
    • Stage conditions: on entry, block or skip a stage, for example during a deployment window or while an alarm is firing. On failure, roll back or retry. On success, fail or roll back if an alarm fires during the bake time.
    • Stage rollback goes back to the last successful execution of that stage.
  • Actions:
    • Build and test: CodeBuild, the Commands action for quick shell steps, and ECRBuildAndPublish for container images.
    • Scanning: InspectorScan.
    • Deploy: CloudFormation and StackSets, ECS, EKS, EC2, Lambda (with canary or linear traffic shifting), CodeDeploy, and S3.
    • Control: manual approval, and invoking another pipeline.
  • CodeBuild: managed build containers, Lambda compute for fast small builds, and reserved capacity fleets for builds that can't wait for provisioning (or need macOS or VPC access). It can also act as a self-hosted runner for GitHub Actions, GitLab or Buildkite, and run batch builds as matrices or dependency graphs.
  • CodeDeploy deploys to EC2 and on-premises servers (in-place or blue/green), Lambda and ECS, with lifecycle hooks for tests and automatic rollback.
  • Source: GitHub or GitLab through CodeConnections (shareable across accounts with RAM), or CodeCommit.
CodePipeline V2 prod stage (part): enter only while the staging error alarm is quiet, roll back automatically on failure 
{
  "name": "DeployProd",
  "beforeEntry": {
    "conditions": [
      {
        "result": "FAIL",
        "rules": [
          {
            "name": "StagingHealthy",
            "ruleTypeId": { "category": "Rule", "owner": "AWS", "provider": "CloudWatchAlarm", "version": "1" },
            "configuration": { "AlarmName": "orders-staging-errors", "WaitTime": "1" }
          }
        ]
      }
    ]
  },
  "onFailure": { "result": "ROLLBACK" },
  "actions": []
}

Queued and parallel modes, triggers, stage conditions and stage rollback need a V2 pipeline. Parallel mode can't use stage rollback or rollback conditions. A source stage can't be rolled back. Automatic stage retry can't be combined with on-failure conditions.

Security scanning and signing

Skill 5.2.2Implement security scanning in pipelines to assess vulnerabilities and sign artifacts (for example, by using Amazon Inspector, Amazon ECR image scanning).

  • Shift left, then keep watching:
    • Code: Inspector code security (static analysis, dependency checks and IaC checks on GitHub repositories), Amazon Q Developer code reviews in the IDE, and cfn-guard or cdk-nag for templates.
    • Build: the CodePipeline InspectorScan action, or inspector-sbomgen plus the Inspector scan API in any CI tool. It fails the build above severity thresholds and outputs an SBOM.
    • Registry: ECR scanning. Basic scanning (AWS native, OS packages, manual or on push) or enhanced scanning by Inspector (OS and language packages, on push or continuously as new CVEs appear).
    • Running: Inspector continues scanning EC2, Lambda and in-use images, and Security Hub collects the findings.
  • Sign what you built:
    • Containers: sign images with AWS Signer (Notation format) by digest, or let ECR managed signing sign every image pushed to matching repositories automatically. Verify before running: in EKS with an admission controller (Kyverno, or Gatekeeper with Ratify) and a Notation trust policy.
    • Lambda: code signing configurations with Signer profiles, set to Enforce to reject unsigned or tampered packages (the default is Warn).
  • Other gates: secret scanning, unit and integration tests, DAST in staging, and SBOM storage for audits.
ECR managed signing: sign every image pushed to prod repositories with the release profile 
{
  "rules": [
    {
      "signingProfileArn": "arn:aws:signer:us-east-1:111111111111:/signing-profiles/release_images",
      "repositoryFilters": [
        { "filter": "prod-*", "filterType": "WILDCARD_MATCH" }
      ]
    }
  ]
}
Pipeline action (YAML): fail on any critical finding in the built image 
name: ScanImage
actionTypeId:
  category: Invoke
  owner: AWS
  provider: InspectorScan
  version: '1'
configuration:
  InspectorRunMode: ECRImageScan
  ECRRepositoryName: prod-orders
  ImageTag: '#{BuildVariables.IMAGE_TAG}'
  CriticalThreshold: 0
outputArtifacts:
  - name: ImageSbom

ECR managed signing works across accounts but not across Regions: the Signer profile must be in the registry's Region. Enhanced ECR scanning has no manual scans, and repositories outside its filters aren't scanned; on first enabling it, only recently pushed images are picked up. Basic scanning allows one scan per image per 24 hours. Answers mentioning Clair are out of date.

Multi-account and multi-Region pipelines

Skill 5.2.3Configure multi-account and multi-Region deployment pipelines that include features such as role delegation and artifact promotion (for example, by using CodePipeline cross-account deployments).

  • Pipeline in a tools account, deployments into workload accounts:
    • Artifact store: the S3 artifact bucket is encrypted with a customer managed KMS key (referenced by key ARN, not alias), whose key policy and the bucket policy grant the target accounts.
    • Target roles: each target account has a role that trusts the pipeline's service role. Each action names it in its roleArn.
    • CloudFormation: the action also names a deployment role (configuration.RoleArn) in the same target account, which CloudFormation uses to create the resources.
    • Setup: cross-account actions are created with the CLI, SDK or IaC, not the console.
  • Cross-Region: replace the single artifact store with an artifactStores map holding a bucket and KMS key per Region (in the pipeline account), and set region on each action. Source actions can't be cross-Region.
  • Promote the same artifact: build once, then deploy the same image digest or package through dev, staging and prod with manual approvals and alarm gates between them, instead of rebuilding per environment. ECR replication (cross-account and cross-Region) or pull permissions make images available in each account and Region.
  • Alternatives: CDK Pipelines generate this structure (bootstrap target accounts with --trust); CloudFormation StackSets actions roll infrastructure out to many accounts from one pipeline step.
Prod stack action: assume the deploy role in the prod account, deploy in us-west-2 
{
  "name": "DeployOrdersStackWest",
  "region": "us-west-2",
  "roleArn": "arn:aws:iam::555555555555:role/PipelineCrossAccountRole",
  "actionTypeId": { "category": "Deploy", "owner": "AWS", "provider": "CloudFormation", "version": "1" },
  "configuration": {
    "ActionMode": "CHANGE_SET_REPLACE",
    "StackName": "orders-service",
    "ChangeSetName": "orders-release",
    "TemplatePath": "BuildOutput::template.yaml",
    "Capabilities": "CAPABILITY_NAMED_IAM",
    "RoleArn": "arn:aws:iam::555555555555:role/CloudFormationDeployRole"
  },
  "inputArtifacts": [ { "name": "BuildOutput" } ]
}

The default AWS managed S3 key can't be used across accounts. A KMS alias resolves only in the account that owns the key, so use the key ARN. With CodeDeploy to EC2, the instance role in the target account also needs read access to the artifact bucket and key. Each Region an action deploys to needs its own artifact bucket and key.

Evaluating AI applications

Skill 5.2.4Evaluate AI/ML applications and validate outputs (for example, by using Amazon Bedrock Evaluations).

  • Amazon Bedrock Evaluations runs evaluation jobs on a dataset of prompts (JSONL in S3, up to 1,000 prompts):
    • Automatic: algorithmic metrics for accuracy, robustness and toxicity.
    • LLM-as-a-judge: correctness, completeness, faithfulness, helpfulness, harmfulness and others, plus your own custom metrics.
    • RAG evaluation: scores retrieval (context relevance and coverage) and generation (faithfulness, citation precision).
    • Human evaluation: with your own work team.
  • Bring your own inference: score responses produced elsewhere (an agent, another model, a Managed Knowledge Base) without Bedrock calling the model.
  • As a pipeline gate: there's no built-in pass/fail. A pipeline step starts the job, waits for it, reads the results from S3 and compares each metric with a threshold or with the current production baseline. Use the same judge model, dataset and settings every time so scores are comparable.
  • Agents: AgentCore Evaluations scores agent sessions, traces and tool use from telemetry (goal success, tool selection accuracy).
  • Cost: evaluations are charged only for model inference (including the judge's tokens), plus a per-task fee for human evaluations.
  • After release: keep validating outputs with Guardrails, invocation logs and user feedback; SageMaker Clarify foundation model evaluation is closed to new customers.

Details of metrics, datasets and the API are on the Bedrock evaluation service page.

"Block a prompt or model change that lowers answer quality" points to a pipeline step running a Bedrock evaluation job against a golden dataset and comparing scores with the baseline. "Check that the RAG assistant's answers are grounded in the retrieved documents" points to a RAG evaluation with faithfulness and citation metrics. Higher harmfulness, stereotyping and refusal scores are worse.

Deployment strategies and rollback

Skill 5.2.5Implement deployment strategies that provide rollback capabilities (for example, blue/green, canary, rolling deployments).

  • Rolling: replace instances or tasks in batches (CodeDeploy one at a time, half at a time, or a minimum number of healthy hosts per fleet or AZ; ECS rolling with the deployment circuit breaker). Cheap, but old and new versions run side by side, and rollback means rolling back again.
  • Blue/green: a full new environment receives traffic in one switch after tests. Rollback is switching back while the old environment is still there.
    • ECS native blue/green (with bake time and lifecycle hooks) is the newer option; AWS publishes a migration guide from CodeDeploy for ECS.
    • CodeDeploy blue/green for EC2 Auto Scaling groups.
  • Canary and linear: shift a small share of traffic first, then the rest (canary) or in equal steps (linear), with alarms watching each step. Supported by:
    • Lambda aliases, through CodeDeploy or the CodePipeline Lambda deploy action.
    • ECS native canary and linear strategies.
    • API Gateway REST stage canaries.
    • AppConfig deployment strategies for configuration and feature flags.
  • Automatic rollback: CodeDeploy rolls back on failure or on a CloudWatch alarm (as a new deployment of the last good revision); ECS, Lambda deploy and AppConfig strategies watch alarms and roll back; CodePipeline stage conditions roll back the whole stage. Good alarms (error rate, latency, business metrics) matter more than the strategy.
  • Databases and schemas: design changes to be backward compatible (expand, then contract) so a code rollback doesn't need a database rollback.
CodePipeline Lambda deploy action (YAML): 10% for 5 minutes, then the rest, rolled back if the error alarm fires 
name: DeployOrdersFunction
actionTypeId:
  category: Deploy
  owner: AWS
  provider: Lambda
  version: '1'
configuration:
  FunctionName: orders-validator
  FunctionAlias: live
  DeployStrategy: Canary10Percent5Minutes
  Alarms: orders-validator-errors
inputArtifacts:
  - name: BuildOutput

A CodeDeploy rollback is a new deployment with a new ID, not an undo. CodeDeploy's one-at-a-time configuration still counts as success if only the last instance fails. ECS through CodeDeploy with a Network Load Balancer supports only all-at-once shifting. Canary without alarms is just a slower all-at-once.

Key takeaways

  • Pipelines: CodePipeline V2 with Git triggers, the right execution mode, stage conditions and rollback; CodeBuild fleets, Lambda compute and runners; CodeDeploy for EC2, Lambda and ECS.
  • Security: Inspector code security and InspectorScan in the pipeline, ECR enhanced scanning, Signer or ECR managed signing verified at admission, Lambda code signing in Enforce mode.
  • Multi-account: tools account pipeline, customer managed KMS key by ARN, cross-account roles per action, a bucket and key per Region, build once and promote the same artifact with approvals.
  • AI quality: Bedrock evaluation jobs (judge, RAG, BYOI) as a threshold gate against a golden dataset, AgentCore Evaluations for agents.
  • Deployments: rolling, blue/green, canary and linear with alarm-driven automatic rollback; backward-compatible schema changes.
