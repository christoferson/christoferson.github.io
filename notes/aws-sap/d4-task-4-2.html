Task 4.2: Design disaster recovery architectures

Getting the company back when a Region or a data centre is lost: choosing a recovery strategy each workload can afford, replicating servers and data continuously, writing and automating the recovery steps, switching traffic and databases between Regions reliably, proving it works with regular tests, and doing the same for container platforms.

Overview

Task 4.2

Design disaster recovery architectures.

The RPO is how much data you can lose (time since the last recovery point) and the RTO is how long you can be down. Both are business decisions, and cost rises as they shrink. A well-built Multi-AZ workload already survives an AZ failure; DR is about losing a Region, a data centre, or data itself (corruption, ransomware). The database replication options are on Task 1.5, global routing on Task 1.4, and AZ-level resilience on Task 4.3.

Running example. Production runs in us-east-1 with DR in us-west-2. The order system (Aurora PostgreSQL global database, ECS services, DynamoDB) needs an RTO of 15 minutes and an RPO under a minute; the reporting tier can wait a day. Some servers stay on premises for now and need protecting in AWS, and the platform team runs an EKS cluster in each Region.

Status changes to know. CloudEndure Disaster Recovery was discontinued on 29 September 2025 (except in China), with no upgrade path (use Elastic Disaster Recovery). The ARC readiness check closed to new customers on 30 April 2026 (use Region switch plan evaluation), and Systems Manager Incident Manager on 7 November 2025 (use OpsCenter or partner tools). New: ARC Region switch (August 2025, now 19 types of execution block), AWS Backup for EKS (November 2025), managed Argo CD in EKS Capabilities (November 2025), ECS native blue/green deployments (July 2025), Elastic Disaster Recovery recovery plans (August 2026), and the next-generation Resilience Hub with resilience testing (2026).

Choosing a DR strategy

Skill 4.2.1Design disaster recovery solutions to meet business requirements (for example, RTO, RPO, costs).

  • Four strategies, from cheapest to fastest:
    • Backup and restore: recovery in hours. Backups copied to the DR Region, infrastructure redeployed with IaC.
    • Pilot light: tens of minutes. Data is replicated live, but application servers aren't running (ideally not even deployed) until needed.
    • Warm standby: minutes. A smaller but working copy serves traffic at once and scales up.
    • Multi-site active/active or hot standby: near zero. Full capacity in both Regions.
  • Match each workload, not the company: the order system on warm standby or hot standby with an Aurora global database and DynamoDB global tables; reporting on backup and restore; on-premises servers on Elastic Disaster Recovery (a pilot light for whole servers).
  • Data is the hard part: asynchronous replication across Regions means RPO is never quite zero, and replication copies corruption too, so keep point-in-time backups (AWS Backup with vault lock and logically air-gapped vaults) for data disasters. Active/active needs a write pattern: write to one Region (global), write locally (DynamoDB global tables), or partition writes.
  • Statically stable recovery: prefer data plane actions (Route 53 health checks, ARC routing controls) over control plane actions (creating resources, changing weights, scaling) during an event. Pre-provision what recovery needs, and raise service quotas in the DR Region in advance. Capacity reservations guarantee instances that scaling alone doesn't.
  • Isolation: separate accounts per Region (or for backups) limit the blast radius of a compromised account.

"Lowest cost, recovery within a day" is backup and restore. "Database must be current but compute can start after the disaster" is pilot light. "Must take traffic immediately at reduced capacity" is warm standby. "No downtime and serve users from both Regions" is multi-site active/active. "Protect against ransomware or accidental deletes" needs immutable backups, not just replication.

Continuous replication

Skill 4.2.2Configure continuous replication to recover quickly from incidents (for example, by using AWS Elastic Disaster Recovery).

  • AWS Elastic Disaster Recovery (DRS) replicates whole servers at block level from physical servers, VMware, Hyper-V, other clouds, or EC2 in another AZ or Region.
    • Staging area: data lands on low-cost replication servers and EBS volumes, so you don't run full-size servers.
    • Objectives: RPO is typically seconds and RTO minutes (mostly boot time).
    • Recovery points: point-in-time snapshots (kept 7 days by default) let you recover from before an incident such as ransomware.
  • Cost: a flat $0.028 per source server per hour while replicating, including drills and recoveries, plus the staging EBS volumes, snapshots and replication instances, and the recovery instances only while they run.
  • Launch settings per server (instance type right-sizing, copying the private IP and tags, licensing) and an EC2 launch template control what gets launched. Post-launch actions run Systems Manager Automation or Command documents after launch, for example to install agents, check connectivity or create an AMI.
  • Drills and recovery plans: drills launch copies without stopping replication, so they don't affect RPO or the source. Run them in an isolated subnet, especially with domain controllers. Recovery plans (August 2026) order servers into steps, for example databases, then application servers, then web servers, with wait steps between them, in one account and Region.
  • Failback: on-premises sources fail back with the DRS Failback Client. EC2 workloads protected across Regions or AZs use reverse replication to protect the recovered instances and return later. DRS can also replicate the source VPC configuration (subnets, security groups, route tables) and deploy it as a CloudFormation stack in the recovery Region.
  • Scale: up to 300 replicating servers per account and Region, a limit that can't be raised; spread larger estates across several staging accounts and recover them into one target account.
  • Data-level replication for managed services: Aurora global databases, DynamoDB global tables, S3 Replication, RDS cross-Region read replicas, ElastiCache Global Datastore, EFS replication, and AWS Backup cross-Region copies (Task 1.5).
Quarterly drill: launch two protected servers from a point in time, without stopping replication 
aws drs start-recovery \
  --region us-west-2 \
  --is-drill \
  --source-servers \
    sourceServerID=s-1234567890abcdef0,recoverySnapshotID=pit-0a1b2c3d4e5f60001 \
    sourceServerID=s-0fedcba0987654321
# Without recoverySnapshotID, DRS takes an on-demand (latest) snapshot

The 300 replicating-server quota per account and Region isn't adjustable. OS disk encryption such as BitLocker must be off on the source. DRS recovery plans can't call Lambda or SSM steps or span accounts; cross-service orchestration needs ARC Region switch, which itself has no DRS block, so call DRS from a custom Lambda step.

Assessment and recovery procedures

Skill 4.2.3Establish disaster recovery assessment and recovery procedures (for example, by using AWS Resilience Hub, AWS Systems Manager runbooks).

  • AWS Resilience Hub:
    • Policy: define an application from its CloudFormation stacks, resource groups, EKS clusters or tags, and attach a resiliency policy with RTO and RPO targets for application, infrastructure, AZ and Region disruptions.
    • Assessment: estimates what the current architecture can achieve and reports "policy met" or "policy breached".
    • Recommendations: architecture changes, CloudWatch alarms, standard operating procedures (SOPs) and FIS experiments.
    • Drift: flags policy or resource drift when the application changes.
    • Next generation (2026): adds AI-assisted failure-mode assessment, dependency discovery and pre-built resilience tests.
  • SOPs as code: Resilience Hub generates a CloudFormation template for each recommended SOP. It holds the IAM role, an SSM parameter that maps the Systems Manager document to the resource, and an FIS experiment that tests the SOP. Keep custom documents in the application's repository so they deploy with it.
  • Systems Manager Automation runbooks make the steps repeatable, for example AWS-CreateImage, AWSSupport-RestoreEC2InstanceFromSnapshot, AWS-CreateRdsSnapshot and AWS-StartStopAuroraCluster, plus your own runbooks for application steps. Start them from EventBridge rules, from DRS post-launch actions, or from a Region switch Lambda step; the Region switch SSM block runs only Command documents.
  • Incident response: with Incident Manager closed to new customers, track recovery work in Systems Manager OpsCenter or a partner tool, and route alarms with EventBridge.
  • Write the decision down: who declares a disaster, which signals are used, and when to fail back. AWS's DR guidance prefers a human decision with automated steps over fully automatic Region failover, which can flap.

An assessment is an estimate from configuration, not proof; only tests show the real RTO. Automation runbooks used in recovery must not depend on the failed Region (run them in the recovery Region, with copies of documents and parameters there). Incident Manager response plans are a distractor in new designs.

Multi-Region failover

Skill 4.2.4Implement multi-Region disaster recovery solutions that include features such as data replication and failover (for example, by using Amazon Route 53 health checks, AWS Global Accelerator, Amazon Application Recovery Controller).

  • Route 53 failover records with health checks: DNS answers switch to the secondary when the primary's health check fails. Health checks are data plane and highly reliable, but clients cache DNS for the TTL. Changing record weights during an event is a control plane action.
  • Global Accelerator: static anycast IPs, with endpoint groups per Region and failover on health (from ELB health checks for ALB and NLB endpoints) in about 30 seconds, with no DNS caching. Traffic dials and endpoint weights shift traffic deliberately, but they are control plane calls (made in us-west-2), and failover traffic ignores a dial of 0.
  • ARC routing controls are on/off switches that drive Route 53 health checks. They have a highly available data plane spread across five Regions (100% SLA) and safety rules such as "at least one Region on", for manual, reliable failover. They cost $2.50 per cluster-hour.
  • ARC Region switch ($70 per plan per month) orchestrates the whole recovery between exactly two Regions, active/passive or active/active.
    • Execution blocks: scale EC2 Auto Scaling groups, ECS services and EKS workloads; switch over or fail over Aurora global databases, DocumentDB and Neptune global clusters; promote RDS replicas; flip routing controls or Region switch-managed health checks; pause for manual approval; run Lambda or Systems Manager commands; and nest child plans.
    • Triggers: plans can be started by CloudWatch alarms.
    • Checks: plans are evaluated every 30 minutes for permissions, configuration, capacity and quota parity.
    • Evidence: each execution produces a PDF report.
    • Independence: each Region has its own data plane, so a plan doesn't depend on the Region you're leaving.
  • Graceful vs ungraceful: a graceful run does an Aurora switchover with no data loss when both Regions are healthy. An ungraceful run fails over even if the primary is unreachable, accepting some data loss, and skips steps that need the failed Region.
  • After recovery: a post-recovery workflow rebuilds replicas back to the old Region once it's healthy, ready for failback.
Region switch: move the order system to us-west-2 even though us-east-1 is impaired 
aws arc-region-switch start-plan-execution \
  --plan-arn "$ORDERS_DR_PLAN_ARN" \
  --target-region us-west-2 \
  --action activate \
  --mode ungraceful \
  --comment "us-east-1 regional event, declared by incident lead"

Region switch scaling blocks request capacity but don't guarantee it, so reserve critical capacity with On-Demand Capacity Reservations. The cheaper Route 53 health check block depends on the Region you're activating, while routing controls don't. The plan's IAM roles, documents and secrets must exist in both Regions. Readiness check answers are outdated; plan evaluation replaced it.

DR testing

Skill 4.2.5Establish disaster recovery testing and validation procedures (for example, by using AWS Resilience Hub).

  • Test on a schedule, not only after changes: DRS drills, Region switch plan runs during game days, AWS Backup restore testing, and Aurora switchovers. Measure actual RTO and RPO against the policy.
  • Resilience Hub recommends and runs tests (pre-configured resilience tests built on FIS in the next generation), tracks results in the resiliency score, and keeps the evidence for auditors.
  • AWS Fault Injection Service runs controlled experiments with stop conditions (CloudWatch alarms) and costs $0.10 per action-minute.
    • Actions: stop instances, inject API errors, disrupt network connectivity, fail over RDS, pause EBS I/O, and container faults.
    • AZ Availability: Power Interruption (scenario library) simulates losing an AZ.
    • Cross-Region: Connectivity cuts Transit Gateway and peering paths and pauses S3, DynamoDB and MemoryDB replication, so you can see how the application behaves when the Regions are split.
  • Validate data, not just services: check row counts or checksums after failover, confirm replication lag alarms, and test restores of point-in-time backups into an isolated account.
  • Run game days: practise the whole process including people (who decides, who communicates), then fix what the test exposed and re-test.

"Prove the 15-minute RTO to auditors" points to scheduled Region switch executions with their PDF reports, or Resilience Hub assessments plus FIS tests. "Find out what happens if replication between Regions stops" is the FIS cross-Region connectivity scenario. Tests without stop conditions in production are a risk; scenarios in the library don't include stop conditions by default.

Containers across clusters

Skill 4.2.6Implement multi-cluster container strategies to provide high availability and disaster recovery (for example, by using Amazon EKS, Amazon ECS).

  • One cluster per Region, identical by construction: clusters are Regional, so DR means a second cluster deployed from the same IaC and pipelines.
    • EKS: GitOps with Argo CD (now a managed EKS Capability, which can deploy to clusters in other Regions and accounts) keeps workloads in sync. Make sure the GitOps hub itself doesn't live only in the failed Region.
    • ECS: deploy the same task definitions and services to both Regions; Service Connect namespaces are Regional, so each Region has its own.
  • Traffic between clusters: each cluster has its own load balancers, with Route 53 failover or latency records or Global Accelerator in front, as for any multi-Region application. Within a Region, ARC zonal shift and autoshift move traffic away from an AZ for EKS and for the load balancers in front of ECS. Zonal shift cordons nodes and removes endpoints; it doesn't move pods, so keep spare capacity.
  • Images: ECR cross-Region replication (only new pushes, one hop; backfill copies existing images; repository policies aren't replicated, so use creation templates) so the DR cluster can pull without the primary Region.
  • State: keep databases and files outside the cluster in replicated services (Aurora global database, DynamoDB global tables, S3, EFS replication). AWS Backup for EKS backs up cluster state (Kubernetes objects, node groups, Pod Identity associations) and EBS, EFS and S3 volumes as one composite recovery point. It copies across Regions and accounts, and restores into an existing or a new cluster without overwriting objects. It doesn't include ECR images or VPCs. ECS services are stateless and redeployed from IaC.
  • Capacity and recovery: Region switch has EKS and ECS scaling blocks that scale the standby cluster to match the primary's recent peak. Use EKS Pod Identity rather than IRSA so roles keep working in a restored or new cluster, whose OIDC issuer differs.
  • Upgrades as a resilience risk: blue/green clusters, or the EKS control plane rollback to the previous version within 7 days, and ECS native blue/green, linear or canary deployments with bake time and automatic rollback.
  • Testing: FIS EKS actions (pod delete, pod network latency, terminating node group instances) and ECS actions (stop tasks, drain instances, task network faults).
Back up the EKS cluster state and its volumes, then copy the recovery point to us-west-2 
aws backup start-backup-job \
  --backup-vault-name platform-vault \
  --resource-arn arn:aws:eks:us-east-1:333333333333:cluster/platform-prod \
  --iam-role-arn arn:aws:iam::333333333333:role/service-role/AWSBackupDefaultServiceRole
# The cluster needs authentication mode API or API_AND_CONFIG_MAP;
# a backup plan rule with a copy action sends it to the DR Region vault
ECR: replicate order-service images to the DR Region 
{
  "rules": [
    {
      "destinations": [
        { "region": "us-west-2", "registryId": "333333333333" }
      ],
      "repositoryFilters": [
        { "filter": "orders", "filterType": "PREFIX_MATCH" }
      ]
    }
  ]
}

EBS-backed pods can't move to another AZ, and restored EBS volumes are pinned to one. EKS zonal shift doesn't cover Fargate, and ECS isn't a zonal shift resource itself (shift its load balancer). An EKS restore keeps the source cluster's OIDC issuer for IRSA, which breaks roles; Pod Identity avoids this. AWS Backup restores skip objects that already exist rather than overwriting them.

Key takeaways

  • Strategy: backup and restore, pilot light, warm standby, multi-site, chosen per workload by RTO, RPO and cost; immutable backups for data disasters; data plane actions and pre-provisioned capacity and quotas for recovery.
  • Replication: Elastic Disaster Recovery for whole servers (flat per-server fee, drills without RPO impact, recovery plans, failback, 300 servers per account), managed-service replication for data.
  • Procedures: Resilience Hub policies, assessments and SOPs as code, Systems Manager runbooks started from EventBridge, DRS or Region switch; OpsCenter instead of Incident Manager.
  • Failover: Route 53 health checks and ARC routing controls on the data plane, Global Accelerator for fast IP-level failover, ARC Region switch to orchestrate databases, compute and traffic between two Regions.
  • Testing and containers: scheduled drills, plan runs and FIS scenarios with stop conditions; one cluster per Region from GitOps and IaC, ECR replication, AWS Backup for EKS, state outside the cluster, Pod Identity for portability.
