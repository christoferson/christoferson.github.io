Task 4.1: Design migration strategies by using AWS frameworks

Overview

Task 4.1

Design migration strategies by using AWS frameworks.

AWS's migration guidance follows three phases: assess (business case, readiness, first portfolio view), mobilize (landing zone, detailed portfolio, operating model, close readiness gaps) and migrate and modernize (waves run by a migration factory). The AWS Cloud Adoption Framework's six perspectives (Business, People, Governance, Platform, Security, Operations) frame the readiness work. Network and hybrid connectivity are on Task 1.3, and the landing zone on Task 2.3.

Running example. The data centre runs several hundred VMware VMs, Oracle and SQL Server databases, a Java order monolith and a COBOL mainframe batch for billing, connected to AWS by Direct Connect. The landing zone in AWS Organizations is ready, and the lease ends in 18 months.

Status changes to know. AWS Application Migration Service is now AWS Transform MGN (June 2026; same aws mgn APIs), and its agentless vCenter replication is no longer available for new deployments (October 2026). Closed to new customers on 7 November 2025: Application Discovery Service, Migration Hub (with Strategy Recommendations and Orchestrator), Migration Hub Refactor Spaces, App2Container and Porting Assistant for .NET; their features now come through AWS Transform (May 2025). The AWS Mainframe Modernization managed runtime closed to new customers on 7 November 2025 and the self-managed experience on 30 July 2026, and AWS Blu Age is now AWS Transform for mainframe. DMS Fleet Advisor reached end of support on 20 May 2026, and the Snow Family is closed to new customers. Some AWS guidance pages still recommend the closed tools.

Discovery, assessment and waves

Skill 4.1.1Design discovery and portfolio assessment solutions to map dependencies and plan migration waves.

  • The 7 Rs per application:
    • Retire: turn it off. "Zombie" servers average under 5% CPU and memory.
    • Retain: keep it on premises for now, for compliance, high risk, waiting dependencies, or mid-range hardware.
    • Rehost: lift and shift.
    • Relocate: move the platform as-is, for example VMware to Amazon EVS, or to another VPC or account.
    • Repurchase: move to SaaS.
    • Replatform: lift, tinker and shift.
    • Refactor: re-architect.
    AWS's large-migration guidance: mostly rehost, replatform, relocate and retire, and modernize after the move rather than refactoring during it.
  • Discovery: the AWS Transform discovery tool (an appliance on vCenter or Hyper-V, or a Linux installer) collects servers, utilization, databases (including Oracle and SQL Server details) and network connections over WinRM and SSH. RVTools exports, CMDB data and third-party tools are accepted too. Network connections are what reveal dependencies between servers.
  • Business case: AWS Transform assessment builds a TCO case from the inventory in minutes, with what-if scenarios (Savings Plans, Graviton, licensing, right-sizing). Migration Evaluator still offers Quick Insights and an AWS-built business case.
  • Wave planning:
    • Group servers into move groups that must move together: a shared database, the same owner, the same patch or outage window.
    • Waves are one or more move groups, planned 4 to 5 waves ahead and sized to the network bandwidth.
    • Early waves stay small (under 10 servers, dev and test, low complexity) to learn fast.
    • Shared services such as Active Directory aren't a reason to group; build domain controllers in AWS first.
  • Migration factory: standard runbooks and automation repeated wave after wave by small teams; AWS cites a team of four rehosting about 50 servers a week. AWS Transform can run parallel waves in separate workspaces.

Application Discovery Service and Migration Hub answers are now wrong for new customers: use AWS Transform (or Migration Evaluator for a business case). An inventory without network connection data can't show dependencies, so move groups built only from server lists risk splitting an application from its database.

Rehosting

Skill 4.1.2Implement rehosting strategies (for example, by using AWS Transform MGN [previously known as AWS Application Migration Service], AWS Transform).

  • How Transform MGN works:
    • Replication: a replication agent on each source server (physical, VMware, Hyper-V or another cloud) does a block-level copy, then continuous replication, to lightweight replication servers in a staging area subnet.
    • Launch: a conversion server makes the disks bootable on AWS, and test and cutover instances launch from per-server launch templates.
    • Post-launch actions run Systems Manager documents, for example to install agents or change configuration.
  • Lifecycle: initial sync, ready for testing, test (each new test replaces the last), ready for cutover, cutover, then finalize, which stops replication, deletes the replicated data and removes the agent. Servers are grouped into applications and waves, and actions run at server, application or wave level, across accounts in the organization.
  • Network: TCP 443 from source servers and the staging subnet to the MGN endpoint (control) and TCP 1500 from source servers to the replication servers (data, encrypted).
  • Cost: 2,160 free replication hours (90 days of continuous replication) per source server, starting when the agent is installed. Staging EC2 and EBS and launched instances are billed as usual.
  • AWS Transform for VMware (and other sources) adds an agentic, guided flow on the same MGN engine. It covers discovery, wave planning, a landing zone (or IaC for one), translating the on-premises network and firewall rules into VPCs and security groups, and rehosting through MGN. It's free for these migration jobs. Each job targets one Region and one account per wave in the organization.
  • Other rehost and relocate paths: VM Import/Export for one-off images, and Amazon EVS to run the VMware stack itself on AWS.
Source server: install the replication agent without prompts 
sudo ./aws-replication-installer-init \
  --region us-east-1 \
  --no-prompt
# Credentials come from a role with AWSApplicationMigrationAgentInstallationPolicy;
# at scale, the MGN connector installs agents over SSH or WinRM
Cutover for the first wave's servers after a successful test 
aws mgn start-cutover \
  --source-server-ids s-1234567890abcdef0 s-0fedcba0987654321
# Then finalize the cutover once traffic runs on AWS (stops replication, removes the agent)

Agentless MGN replication through vCenter is gone for new deployments, and AWS Transform never supported it, so plan for agents. Don't swap the ports: 1500 carries data and 443 carries control. Finalizing cutover is one-way; keep the source servers until the application is accepted. For disaster recovery rather than migration (or a target on Outposts), AWS points to Elastic Disaster Recovery, covered in Task 4.2.

Database and data migration

Skill 4.1.3Design database and data migration strategies (for example, by using AWS Database Migration Service, AWS DataSync).

  • AWS DMS moves data with a full load, ongoing change data capture (CDC), or both. Use full load plus CDC to keep the target in sync until a short cutover.
    • For very large databases, restore a native backup on the target, then start CDC from the backup's log position (--cdc-start-position).
    • DMS Serverless sizes and scales capacity in DMS capacity units between a minimum and maximum, and suits variable or heterogeneous migrations.
    • Use Multi-AZ for long CDC runs.
  • Homogeneous migrations (MySQL, MariaDB, PostgreSQL, MongoDB, DocumentDB) can use DMS homogeneous data migrations, which run native tools serverlessly. Oracle to Oracle and SQL Server to SQL Server use standard DMS or native tools (RMAN, backups, log shipping).
  • Heterogeneous migrations (Oracle or SQL Server to Aurora PostgreSQL) convert the schema first with DMS Schema Conversion, which is free and managed, with generative AI for code the rules can't convert, then move the data with DMS. The desktop Schema Conversion Tool remains for data warehouses and ETL code.
  • SQL Server to Babelfish for Aurora PostgreSQL lets applications keep T-SQL and the SQL Server protocol. Assess with Babelfish Compass, load with DMS, and send CDC to the Aurora PostgreSQL endpoint, not the Babelfish one.
  • Quality: premigration assessments catch unsupported types and settings; data validation compares source and target rows, and needs a primary key or unique index. Limited LOB mode is faster but truncates larger LOBs, so size it from the data.
  • Files and bulk data:
    • DataSync for NFS, SMB, HDFS and object stores to S3, EFS or FSx, with scheduling and verification.
    • Transfer Family when partners keep using SFTP or AS2.
    • Storage Gateway for hybrid access.
  • Transfer time: 100 TB takes about 12 days over 1 Gbps at 80% utilization, or about a day over 10 Gbps. With Snowball closed to new customers, very large one-off loads can use AWS Data Transfer Terminal: you bring your own storage to an AWS facility and upload over 100 Gbps links, billed per port-hour. The user guide limits it to Enterprise Support customers.
Oracle orders schema to Aurora PostgreSQL: full load, then ongoing changes, with validation 
aws dms create-replication-task \
  --replication-task-identifier orders-oracle-to-aurora \
  --source-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:ORACLESRC \
  --target-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:AURORATGT \
  --replication-instance-arn arn:aws:dms:us-east-1:111111111111:rep:ORDERSRI \
  --migration-type full-load-and-cdc \
  --table-mappings file://table-mappings.json \
  --replication-task-settings '{"ValidationSettings":{"EnableValidation":true}}'
table-mappings.json: every table in the ORDERS schema 
{
  "rules": [
    {
      "rule-type": "selection",
      "rule-id": "1",
      "rule-name": "orders-schema",
      "object-locator": { "schema-name": "ORDERS", "table-name": "%" },
      "rule-action": "include",
      "filters": []
    }
  ]
}

DMS homogeneous data migrations don't support Oracle or SQL Server and have no built-in validation. DMS Serverless can't scale down during a full load, needs VPC endpoints to reach services such as S3 and Secrets Manager, and after its first start can only resume. DMS moves tables and data, not every database object: schema conversion and secondary objects (triggers, sequences, procedures) need their own step.

Replatforming

Skill 4.1.4Design replatforming strategies that use managed services to reduce operational overhead (for example, Amazon RDS, Amazon Aurora, Amazon ECS, AWS Lambda).

  • Replatform = small changes for a big operational gain: the application stays the same, but what it runs on becomes managed.
  • Databases: self-managed SQL Server, Oracle, MySQL or PostgreSQL to RDS (same engine, managed backups, patching and Multi-AZ), or to Aurora for MySQL and PostgreSQL, with faster failover, storage that grows by itself and up to 15 readers. RDS Custom covers engines that need OS access.
  • Applications:
    • VMs to containers on ECS (Fargate, or ECS Express Mode for simple web services) or EKS. AWS Transform can containerize from source code; App2Container is closed to new customers.
    • Scheduled scripts and event handlers to Lambda.
    • Elastic Beanstalk for simple web apps.
  • Other common replatforms: file servers to FSx (Windows File Server, NetApp ONTAP), message brokers to Amazon MQ (same ActiveMQ or RabbitMQ protocols), Hadoop to EMR, Windows to Linux, x86 to Graviton, cron to EventBridge Scheduler.
  • Licensing: moving to license-included RDS or to open-source engines (Oracle to Aurora PostgreSQL) often matters more to the business case than the infrastructure.

"Reduce operational overhead with minimal code changes" points to replatforming to RDS, Aurora, ECS on Fargate or Amazon MQ, not to a rewrite. "Keep the same message broker protocol" is Amazon MQ, while SQS would need code changes. "Need OS-level access to the database host" points to RDS Custom or EC2, not standard RDS.

Refactoring

Skill 4.1.5Implement refactor strategies such as microservices decomposition, serverless adoption, and incremental modernization patterns (for example, strangler fig pattern).

  • Strangler fig: put a routing layer in front of the monolith (API Gateway or an ALB routing by path, host name or header), build new capabilities as separate services, and move routes over one at a time until the monolith can be retired.
    • Anti-corruption layer: code inside the monolith that translates its calls into the new services' interfaces.
    • Data sync: data stays consistent through events, as a temporary measure while ownership moves.
    • Rewrite instead: small applications are cheaper to rewrite than to strangle.
  • No managed router any more: Refactor Spaces, which automated this routing, is closed to new customers, so you build the facade with API Gateway (serverless and Multi-AZ, so it isn't a single point of failure) or ALB rules.
  • Finding service boundaries: domain-driven design and event storming, decomposing by business capability or subdomain. Give each service its own data store, and replace cross-service transactions with sagas (Step Functions) and events.
  • Serverless adoption: Lambda, Step Functions, EventBridge, SQS and DynamoDB for new services; circuit breakers on synchronous calls back to the monolith. Event and workflow design is on Task 1.1.
  • Incremental, measurable steps: start with a capability that changes often or needs to scale separately, and keep the monolith running until the last route moves.

Refactoring during a large data centre exit slows the migration; AWS advises migrating first and modernizing after. The routing layer and the anti-corruption layer are both temporary; plan their removal. Sharing the monolith's database with new services defeats the point of decomposing.

Modernizing legacy workloads

Skill 4.1.6Modernize legacy workloads, including mainframes, applications, and databases.

  • Mainframes: AWS Transform for mainframe (free; z/OS COBOL and PL/I with JCL, CICS, Db2, VSAM and IMS, and Fujitsu GS21). Its agents:
    • analyse and document the code and extract business logic;
    • decompose it into domains and plan waves, with human approval;
    • refactor COBOL into Java with generated infrastructure code;
    • generate tests;
    • since December 2025, can "reimagine" the application as microservices.
    The refactored application runs on EC2, ECS or EKS. Replatforming the COBOL as-is now means a vendor's own offering (such as Rocket Software), because the Mainframe Modernization service is closed to new customers.
  • Mainframe data: Db2 for z/OS to Aurora PostgreSQL with DMS (through a Db2 Connect gateway) and DMS Schema Conversion.
  • .NET: AWS Transform for .NET ports .NET Framework applications to cross-platform .NET 8 or 10 on Linux, removing Windows licensing. It's free up to a monthly allowance of agent minutes.
  • SQL Server: AWS Transform's SQL Server modernization converts databases to Aurora PostgreSQL and updates the .NET data-access code to match (target Aurora only). Babelfish is the lower-change alternative that keeps T-SQL.
  • Java and other code: AWS Transform custom runs language, framework and SDK upgrades (Java 8 to 17, Spring Boot 2 to 3, AWS SDK v1 to v2, x86 to Graviton) at $0.035 per agent minute.
  • Keep humans in the loop: Transform jobs pause for approvals on plans and code, and output still needs testing; functional equivalence testing is the main risk in any automated refactor.

"Modernize COBOL to Java on AWS" is now AWS Transform for mainframe, not the Mainframe Modernization managed runtime, which is closed to new customers. "Remove Windows licensing from a .NET Framework application" is AWS Transform for .NET. "Keep the SQL Server application code but move to PostgreSQL" points to Babelfish; "convert it fully" points to AWS Transform SQL Server modernization or DMS Schema Conversion.

Key takeaways

  • Frameworks: assess, mobilize, migrate and modernize; the 7 Rs per application, mostly rehost, replatform, relocate and retire in a large migration, modernize afterwards.
  • Discovery: AWS Transform discovery and assessment (Discovery Service and Migration Hub are closed to new customers), network connections for dependencies, move groups and small early waves, a migration factory.
  • Rehost: Transform MGN with agents (agentless is gone), staging subnet, ports 1500 and 443, test then cutover then finalize, 90 free days per server; AWS Transform for the guided VMware path.
  • Data: DMS full load plus CDC, Serverless for variable loads, Schema Conversion for heterogeneous moves, Babelfish for SQL Server compatibility, DataSync for files, Data Transfer Terminal for huge one-off loads.
  • Modernize: replatform to RDS, Aurora, ECS, Lambda and Amazon MQ; strangler fig with API Gateway or ALB routing and an anti-corruption layer; AWS Transform for mainframe, .NET, SQL Server and code upgrades.
