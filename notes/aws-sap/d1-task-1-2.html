Overview

Task 1.2

Integrate AI and ML services into architectures.

This task is about architecture, not model building: who in the organization may call which models, from which accounts, through which network path, with what quotas, guardrails and audit trail, and how agents, inference endpoints and knowledge bases fit into that. The service mechanics are covered in depth elsewhere and linked here: MLA-C02 (inference, RAG, agents), AIP-C01 (generative AI applications), and the Amazon Bedrock and SageMaker AI service notes.

Running example. The company from Task 1.1 is adding a support assistant that answers from help articles and order data, an agent that can look up orders and open refund requests in an on-premises system, and a churn model served to several business units, each in its own AWS accounts.

Generative AI in a multi-account organization

Skill 1.2.1Design generative AI integrations for applications, including for multi-account deployment patterns (for example, by using Amazon Bedrock).

Where do model calls happen? The AWS Security Reference Architecture adds a Generative AI OU with an application account and a generative AI account that hosts Bedrock and is reached through APIs; it also says to merge them, or use one account with IAM roles, when risk profiles are uniform and only pre-trained models are used. The two shapes:

  • Central generative AI account (hub): one place for approved models, guardrails, prompt management, invocation logging and cost reporting. Workload accounts reach it by assuming a role or through a gateway (API Gateway and Lambda, an ALB-fronted proxy such as AWS's multi-provider generative AI gateway solution, or AgentCore Gateway). Bedrock has no resource-based policy for invoking models, so a direct cross-account call isn't possible. Trade-off: every consumer shares the hub's quotas.
  • Bedrock in each workload account (spokes): each account has its own quotas and blast radius; governance comes from the organization instead: SCPs restricting models and Regions, organization-level guardrail enforcement and data retention policy, tagged application inference profiles for cost attribution, and Service Quotas request templates (up to 10 quotas, applied to new accounts only).
A workload account calls the approved model through the central GenAI account (Python, boto3) 
import boto3

creds = boto3.client("sts").assume_role(
    RoleArn="arn:aws:iam::222222222222:role/GenAIInvoker-Support",  # role in the central GenAI account
    RoleSessionName="support-assistant",
)["Credentials"]

runtime = boto3.client(
    "bedrock-runtime", region_name="us-east-1",
    aws_access_key_id=creds["AccessKeyId"],
    aws_secret_access_key=creds["SecretAccessKey"],
    aws_session_token=creds["SessionToken"],
)
resp = runtime.converse(
    # A tagged application inference profile in the hub attributes cost to this team
    modelId="arn:aws:bedrock:us-east-1:222222222222:application-inference-profile/a1b2c3d4e5f6",
    messages=[{"role": "user", "content": [{"text": "Where is order o-1001?"}]}],
    guardrailConfig={"guardrailIdentifier": "gr-support", "guardrailVersion": "3"},
)
  • Integration styles: synchronous Converse for chat, streaming for perceived speed, StartAsyncInvoke for long jobs that write to S3, batch inference for large offline jobs, and Step Functions (its optimized Bedrock integration calls InvokeModel, with payloads over 256 KiB passed through S3) for multi-step processes. Bedrock's EventBridge events cover customization and batch jobs, not individual calls.
  • Private access: interface VPC endpoints for bedrock-runtime keep calls off the internet (Task 1.4).
  • Custom models across accounts: share a fine-tuned model with another account in the same organization through AWS RAM; the receiving account must copy it (CreateModelCopyJob) before using it, and it can't leave the organization. Imported models can be deployed from a central account too.
  • SCPs: denying bedrock:InvokeModel also blocks Converse and asynchronous invocation (add CreateModelInvocationJob to block batch). A Region-deny SCP can break cross-Region inference, whose requests run in other Regions; carve out the inference profile ARNs (or use the Control Tower control for allowed Regions with exemptions).

"Let every account call Bedrock in the shared account with a resource policy" is wrong: there's no such policy for invocation; use role assumption or a gateway. A central account concentrates all tokens-per-minute demand on one set of quotas, which is a common reason to put Bedrock in each workload account instead.

Agent architectures with tools

Skill 1.2.2Design AI agent architectures that integrate with tools (for example, by using Amazon Bedrock AgentCore, Amazon Bedrock Knowledge Bases).

  • Pattern first: AWS Prescriptive Guidance separates rule-based orchestration (Step Functions: known steps, a full audit trail, compliance) from AI-native orchestration (agents: unstructured requests, goal-driven, flexible), and lists agent patterns such as tool-based agents, workflow orchestration agents (a central coordinator) and multi-agent collaboration (peers). Hybrid designs, a workflow that calls an agent for one fuzzy step, are common.
  • Platform: AgentCore Runtime (or a harness) runs the agent in isolated sessions; AgentCore Gateway turns Lambda functions, APIs and MCP servers into tools behind one endpoint, with per-tool authorization (Policy), rate limits and outbound credentials; Identity can exchange the user's token on their behalf so downstream systems see the real user; Memory holds conversation and long-term facts; the Agent Registry catalogues agents and tools across the organization.
  • Tools in other accounts: a Gateway's Lambda target can live in another account; the gateway service role needs lambda:InvokeFunction, and the function needs a resource policy naming that role. Runtimes, gateways and memories support resource-based policies for cross-account callers (a cross-account runtime needs policies on both the runtime and its endpoint).
  • Private systems: Runtime in VPC mode, and Gateway targets reached through VPC connectivity, so the agent can call the on-premises refund system over Direct Connect without public endpoints.
  • Human approval: the Agentic AI Lens asks for risk-tiered approval decided by deterministic rules (not the model): read-only actions run, low-risk writes need one approver, high-risk actions (payments, deletions, external messages) need stricter approval, and a timeout must fall back to blocking. Approvals that can take days belong in Step Functions with a task token, since an agent session lasts at most 8 hours.
Let the agent platform's gateway call the refund tool in the orders account (Bash, AWS CLI in account 111111111111) 
aws lambda add-permission \
    --function-name open-refund-request \
    --statement-id AllowAgentGateway \
    --action lambda:InvokeFunction \
    --principal arn:aws:iam::333333333333:role/AgentGatewayServiceRole
# The gateway role in account 333333333333 also needs lambda:InvokeFunction on this function's ARN

More on Gateway, Identity and Policy in the AgentCore notes, and on agent deployment in MLA-C02 Task 3.1.

ML inference architectures

Skill 1.2.3Design ML inference architectures (for example, Amazon SageMaker AI endpoints).

  • Pick the style by traffic (details in MLA-C02 Task 3.1): real-time endpoints for steady low-latency traffic, serverless inference for intermittent traffic, asynchronous inference for large payloads and long processing (scales to zero), batch transform for whole datasets; inference components to pack several models onto shared instances.
  • Availability in a Region: run at least two instances in subnets in different Availability Zones (SageMaker spreads them only if there are two or more); with inference components, more than two copies on at least two instances. Deploy with deployment guardrails (canary or linear with alarm rollback).
  • Across Regions: there's no built-in cross-Region failover for endpoints. Replicate model artifacts (S3 replication) and images (ECR replication), deploy the same endpoint in each Region with infrastructure as code, and route with Route 53 in front of a Regional API layer.
  • Across accounts: endpoints have no resource-based policy and can't be shared with RAM. Serve other accounts through an API Gateway (with IAM or Cognito auth, throttling and caching, which the ML Lens recommends anyway) or a PrivateLink endpoint service, let them assume a role in the ML account, or share the model package group (which RAM can share) and let each account deploy its own copy.
  • Bedrock or SageMaker AI? Bedrock for foundation models without infrastructure; SageMaker AI endpoints for your own models, open-weight models needing a custom stack, or strict control of instances and networking.

"Several business units need the churn model, each billed separately, with minimal duplication" points to one endpoint in a central ML account behind API Gateway with usage plans per unit. "Each unit must run its own copy in its own account" points to sharing the model package group with RAM and deploying from it.

RAG architectures

Skill 1.2.4Design RAG architectures, including ingestion and retrieval strategies (for example, Amazon Bedrock knowledge bases that use vector stores).

  • Managed knowledge base (AWS's default recommendation): Bedrock runs parsing, embedding, storage, hybrid search and reranking, with connectors, document-level permissions and scheduled syncs. Customer-managed when you need your own vector store, chunking, SQL retrieval over Redshift or graph retrieval (MLA-C02 Task 2.1 compares the patterns).
  • Vector store by need: S3 Vectors for large, rarely queried indexes at low storage cost (sub-second); OpenSearch for low-millisecond, high-QPS search with hybrid and faceted filtering; Aurora pgvector when the data already lives in PostgreSQL; Neptune Analytics for relationships across documents. Fewer embedding dimensions shrink the index (an AWS test at 512 dimensions halved it with no quality loss).
  • Ingestion: event-driven syncs from S3 changes (customer-managed knowledge bases don't sync on a schedule), Bedrock Data Automation to parse complex documents and media, redaction before indexing, and a blue/green rebuild when the embedding model or chunking changes (MLA-C02 Task 3.3).
  • Retrieval: hybrid search for exact terms, reranking, metadata filters (a server-side tenant filter for multi-tenant data), query decomposition or agentic retrieval for complex questions.
  • Across accounts: a managed knowledge base's resource policy allows other accounts only Retrieve and GetDocumentContent; generating answers there (RetrieveAndGenerate), or using a customer-managed knowledge base, means assuming a narrowly scoped role in the knowledge base's account. AWS's guidance: use native cross-account retrieval when retrieval is enough, a direct call when every request needs one deterministic answer, and an agent only when the model must decide when to query.
  • Across Regions: the Generative AI Lens says to replicate embeddings and indexes to the recovery Region, within data-sovereignty limits.

Knowledge base settings that determine the index (embedding model, vector store) can't be changed after creation, so plan the store for the expected scale. Multi-tenant RAG is usually one shared knowledge base with a mandatory tenant metadata filter applied by the server, not a knowledge base per tenant (a knowledge base allows only 5 data sources).

Key takeaways

  • Multi-account GenAI: a central GenAI account reached by role assumption or a gateway (one quota pool), or Bedrock per workload account governed by SCPs, org-level guardrails and tagged inference profiles; Bedrock has no invocation resource policy.
  • Custom models are shared within the organization through RAM and copied before use; SCPs on InvokeModel also block Converse, and Region denies need cross-Region inference carve-outs.
  • Agents: Step Functions for known, audited steps, agents for open-ended goals, often combined; AgentCore Runtime, Gateway (cross-account Lambda tools need a resource policy), Identity, Memory and Registry; risk-tiered human approval with deterministic rules and Step Functions for long waits.
  • Inference: two or more instances across zones; no cross-Region failover, so replicate artifacts and route with Route 53; endpoints can't be shared, so front them with API Gateway or PrivateLink, or share the model package group.
  • RAG: managed knowledge base by default; vector store by scale and query rate; event-driven ingestion and blue/green re-indexing; cross-account retrieval allows only Retrieve and GetDocumentContent.
