Task 3.4: Optimize storage and database costs

Paying for data by how it's used: storage that tiers itself as it cools, volumes sized for the IOPS they actually need, databases on the right capacity mode and commitment, backups kept only as long as the rules require, and logs and metrics that don't cost more than the systems they watch.

Overview

Task 3.4

Optimize storage and database costs.

Storage and database costs grow quietly: data is rarely deleted, volumes are sized for a peak that never comes, and logs are kept forever by default. The detailed prices are in the SAA cost-optimized storage notes and SAA cost-optimized database notes; this page is about the decisions. Prices are us-east-1 list prices.

Running example. Order documents and images build up in S3 and are rarely read after a month; shared files sit on EFS; EC2 still has gp2 volumes from the original build; Aurora PostgreSQL carries the order database with a heavy, steady I/O load; dev databases sit idle overnight; DynamoDB holds a large order-history table that is mostly stored, not read; backups are kept seven years for regulators; and CloudWatch Logs is now one of the biggest lines on the bill.

Status changes to know. The vault-based Amazon Glacier service no longer accepts new customers (use the S3 Glacier storage classes). Since September 2024, S3 Lifecycle doesn't transition objects under 128 KB by default. The CloudWatch Logs Infrequent Access class is now Essentials (read APIs return the new name from December 2026). The X-Ray SDKs and daemon entered maintenance mode in February 2026 (use OpenTelemetry). New: Database Savings Plans (December 2025), Aurora Serverless v2 auto-pause to zero capacity, gp3 volumes up to 80,000 IOPS (September 2025), the AWS Backup low-cost warm tier for S3 backups, Lambda logs billed at tiered vended-log rates (May 2025), and CloudWatch Logs Intelligent Tiering for log storage (2026).

Storage tiering and lifecycle

Skill 3.4.1Implement intelligent storage tiering and lifecycle policies (for example, by using Amazon S3 Intelligent-Tiering, S3 Lifecycle policies, S3 Glacier storage classes, Amazon EFS lifecycle policies).

  • Unknown or changing access: S3 Intelligent-Tiering. It moves objects to Infrequent Access after 30 days without access and Archive Instant Access after 90, with no retrieval fees and no minimum duration, for a small monitoring fee per object. Turn on the optional Archive Access and Deep Archive Access tiers only if hours of restore time are acceptable.
  • Known patterns: Lifecycle rules. For example Standard, then Standard-IA at 30 days, Glacier Flexible Retrieval at 90, Deep Archive at 180, and expire at the retention limit. Expire noncurrent versions and abort incomplete multipart uploads too. Storage Class Analysis and S3 Storage Lens show where rules would pay off.
  • Choosing a Glacier class:
    • Glacier Instant Retrieval: millisecond reads for data read about once a quarter. It charges per GB retrieved, so it costs more if read often.
    • Glacier Flexible Retrieval: minutes to hours, with free bulk restores.
    • Glacier Deep Archive: the cheapest at about $1 per TB-month, with restores in 12 to 48 hours.
  • Small objects: each transition is a billed request, IA classes bill at least 128 KB per object, and Glacier Flexible Retrieval and Deep Archive add 40 KB per object. Aggregate small files before archiving; Lifecycle skips objects under 128 KB by default.
  • Minimum durations: 30 days (IA), 90 days (Glacier Instant and Flexible), 180 days (Deep Archive). Deleting earlier still bills the remainder.
  • EFS lifecycle moves files not accessed for a set time to Infrequent Access (default 30 days) and Archive (default 90 days), and can move them back on first access. EFS One Zone costs about half of Regional storage when multi-AZ resilience isn't needed.
S3 Lifecycle: tier order documents larger than 128 KB, keep 3 old versions, expire after 7 years 
{
  "Rules": [
    {
      "ID": "tier-order-documents",
      "Status": "Enabled",
      "Filter": { "And": { "Prefix": "orders/", "ObjectSizeGreaterThan": 131072 } },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" },
        { "Days": 180, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "NoncurrentVersionTransitions": [
        { "NoncurrentDays": 30, "StorageClass": "GLACIER_IR", "NewerNoncurrentVersions": 3 }
      ],
      "Expiration": { "Days": 2555 }
    }
  ]
}
EFS: tier cold files, bring them back when read 
aws efs put-lifecycle-configuration \
  --file-system-id fs-0a1b2c3d4e5f60001 \
  --lifecycle-policies '[{"TransitionToIA":"AFTER_30_DAYS"},
    {"TransitionToArchive":"AFTER_90_DAYS"},
    {"TransitionToPrimaryStorageClass":"AFTER_1_ACCESS"}]'

Lifecycle only moves data down the chain: One Zone-IA can't go to Glacier Instant Retrieval, and Deep Archive is one-way. Intelligent-Tiering never tiers objects under 128 KB. Restoring an archived object bills a temporary copy at Standard rates as well as the archive copy. EFS Archive needs Elastic Throughput, and EFS IA costs more with Bursting or Provisioned Throughput than with Elastic.

Block storage

Skill 3.4.2Optimize block storage costs by selecting appropriate volume types and provisioning appropriate input/output operations per second (IOPS) (for example, Amazon EBS gp3 volumes, EBS gp2 volumes, Provisioned IOPS).

  • gp3 by default: 20% cheaper per GB than gp2 ($0.08 vs $0.10 per GB-month), with 3,000 IOPS and 125 MiB/s included at any size. Extra IOPS (up to 80,000) and throughput (up to 2,000 MiB/s) are bought separately, so you don't over-buy capacity to get speed.
  • gp2 ties IOPS to size (3 IOPS per GB with burst credits), so large gp2 volumes were often bought only for IOPS. Migrating to gp3 with Elastic Volumes needs no downtime.
  • io2 Block Express (Provisioned IOPS) only when you need more than gp3 offers, sub-millisecond consistency, or higher durability for critical databases; IOPS are charged per provisioned IOPS-month whether used or not.
  • Throughput HDD: st1 for large sequential reads (logs, data processing) and sc1 for cold sequential data are far cheaper per GB, but can't be boot volumes.
  • Find waste: Compute Optimizer recommends volume type, size, IOPS and throughput; Cost Optimization Hub and Trusted Advisor flag unattached and idle volumes.
  • Snapshots: Data Lifecycle Manager or AWS Backup for retention; snapshot archive ($0.0125 vs $0.05 per GB-month) for snapshots kept 90 days or more, such as monthly or yearly copies.
Move a gp2 volume to gp3 in place, with the included baseline performance 
aws ec2 modify-volume \
  --volume-id vol-0a1b2c3d4e5f60001 \
  --volume-type gp3 \
  --iops 3000 \
  --throughput 125

EBS volumes can grow but not shrink in place; downsizing means a new volume and a copy. Archiving a snapshot turns an incremental snapshot into a full one and has a 90-day minimum, so archiving daily snapshots costs more, not less. Deleted volumes and snapshots held in Recycle Bin keep billing until retention ends.

Database capacity and commitments

Skill 3.4.3Optimize database costs by selecting appropriate capacity modes and reserved capacity (for example, DynamoDB capacity modes, Amazon RDS reserved DB instances, Amazon Aurora serverless, Aurora I/O-Optimized, Database Savings Plans).

  • DynamoDB:
    • On-demand is AWS's default recommendation and suits spiky or unknown traffic.
    • Provisioned with auto scaling is much cheaper per request for steady, predictable load. Fully used, it costs about a third of on-demand per write.
    • Reserved capacity (up to 77% off for 3 years) applies only to provisioned mode on the Standard table class in a single Region.
    • Standard-IA table class pays off when storage is more than half the table's throughput cost.
  • RDS:
    • Reserved DB instances: 1 or 3 years; No Upfront only on 1-year terms. Size flexibility within a family, except SQL Server and Oracle License Included.
    • Multi-AZ: a Multi-AZ instance costs about twice Single-AZ, and a Multi-AZ cluster about 2.8 times.
    • Dev and test: stop idle databases; they restart automatically after 7 days.
  • Aurora:
    • Standard charges per I/O request.
    • I/O-Optimized charges nothing for I/O, but about 30% more per instance-hour and 2.25 times more for storage. It pays for I/O-heavy clusters such as the order database.
    • Serverless v2 scales in fine steps for variable load, and can now auto-pause to zero capacity for idle dev clusters. Auto-pause doesn't happen with RDS Proxy, Global Database, replication or zero-ETL attached, or while connections are open.
  • Database Savings Plans (up to 35%, 1-year No Upfront only) cover Aurora, RDS, DynamoDB, ElastiCache, DocumentDB, Neptune, Keyspaces and others across engines. They cover newer instance generations and serverless usage only, and don't stack with RIs or reserved capacity on the same usage. Use RIs for 3-year terms and older generations.
  • Other levers: Graviton instance classes, ElastiCache and MemoryDB for Valkey (cheaper than Redis OSS), caching to shrink the database, Aurora cloning instead of full copies for test, and Compute Optimizer recommendations for RDS, Aurora and DynamoDB.
Idle dev cluster: let Aurora Serverless v2 pause after an hour without connections 
aws rds modify-db-cluster \
  --db-cluster-identifier orders-dev \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=16,SecondsUntilAutoPause=3600
Order-history table: storage-heavy, so switch to the Standard-IA table class 
aws dynamodb update-table \
  --table-name order-history \
  --table-class STANDARD_INFREQUENT_ACCESS
# At most two table class changes in 30 days; reads and writes cost more on IA

"Aurora bill dominated by I/O charges on a steady workload" points to I/O-Optimized. "Dev databases idle at night and weekends" points to Serverless v2 auto-pause (or stopping instances). "Commit across RDS, Aurora and DynamoDB in one purchase" is a Database Savings Plan; "3-year commitment on db.r6g" still needs RIs.

Backup and retention

Skill 3.4.4Implement backup and disaster recovery mechanisms that use cost-optimized retention policies (for example, by using AWS Backup, Amazon Data Lifecycle Manager).

  • Retention by rule, not by habit: daily backups kept for weeks, monthly for a year, yearly for the regulatory period, each with its own lifecycle in AWS Backup plans, deployed organization-wide with backup policies.
  • Cold storage (AWS Backup lifecycle) for EFS, DynamoDB (with advanced features), EBS (through snapshot archive) and others: cheaper per GB, but backups must stay at least 90 days in cold storage. RDS, Aurora, DocumentDB and Neptune backups can't move to cold storage. For long-term database archives, export snapshots to S3 as Parquet and tier them with Lifecycle, knowing that an export can't be restored as a database.
  • S3 backups can move to a low-cost warm tier after at least 60 days (up to 30% cheaper). Expire old versions and delete markers, because each counts as at least 128 KB.
  • Data Lifecycle Manager (no extra charge) automates EBS snapshots and EBS-backed AMIs by tag, with retention by count or age, archiving and cross-Region copies; its default policies back up any volume without a recent backup, kept 2 to 14 days.
  • Database-native retention: RDS automated backups up to 35 days (point-in-time recovery). Manual and final snapshots outlive the instance and keep billing. Aurora backup storage beyond the free amount is cheaper than RDS ($0.021 vs $0.095 per GB-month).
  • Cross-Region copies pay inter-Region transfer plus storage in the DR Region, so copy only what the recovery plan needs and keep shorter retention there.
AWS Backup plan rule: daily EFS backups, cold after 30 days, deleted after a year 
{
  "BackupPlan": {
    "BackupPlanName": "efs-daily",
    "Rules": [
      {
        "RuleName": "daily-1y",
        "TargetBackupVaultName": "regulated-vault",
        "ScheduleExpression": "cron(0 3 ? * * *)",
        "Lifecycle": {
          "MoveToColdStorageAfterDays": 30,
          "DeleteAfterDays": 365
        }
      }
    ]
  }
}

DeleteAfterDays must be at least 90 days after the move to cold storage. A cold-storage setting in a plan has no effect on RDS or Aurora backups. Backing up S3 objects in IA or Glacier Instant Retrieval incurs retrieval charges, and backing up Intelligent-Tiering objects moves them back to the frequent tier.

Cost-effective observability

Skill 3.4.5Design cost-effective observability solutions that include features such as log filtering, metric aggregation, and retention optimization.

  • Logs cost three ways: ingestion ($0.50 per GB on the Standard class), storage ($0.03 per GB-month, compressed) and queries ($0.005 per GB scanned).
    • Essentials log class halves ingestion ($0.25 per GB). It has no subscription or metric filters, embedded metrics, field indexes or Live Tail, and the class is fixed when the log group is created.
    • Logs Intelligent Tiering (an account and Region setting) moves stored logs to $0.018 and then $0.006 per GB-month when they go unread.
  • Filter at the source:
    • Lambda: set JSON log format and log levels, so DEBUG lines aren't ingested in production.
    • CloudWatch agent: include and exclude filters drop noise before it's sent.
    • Fluent Bit (FireLens): filters do the same for containers.
  • Route by purpose:
    • Audit-only logs: send VPC Flow Logs and Lambda logs straight to S3 or Firehose ($0.25 per GB at the first tier). Vended and Lambda log tiers are pooled, so volume lowers the rate.
    • Continuous archive: use a subscription filter to Firehose and S3, not repeated export tasks.
    • Centralization: the first centralized copy is free; extra copies cost $0.05 per GB.
  • Retention: log groups never expire by default; set retention on every group, enforce it with an account-level retention policy or a Config rule, and keep long-term archives in S3 with Lifecycle instead of CloudWatch.
  • Metric aggregation:
    • Price: custom metrics cost $0.30 per metric-month for the first 10,000, and every unique dimension combination is a separate metric. Never use request IDs or user IDs as dimensions; put them in log fields instead.
    • CloudWatch agent: send only roll-ups with aggregation_dimensions plus drop_original_metrics.
    • Embedded metric format: metrics come from logs, so you pay for both the log ingestion and the metrics.
    • New custom metrics: AWS now recommends OpenTelemetry, billed per GB.
    • Third-party tools: metric streams are cheaper than polling with GetMetricData, which is always charged.
  • Alarms and traces: standard alarms ($0.10) unless 10-second evaluation is needed ($0.30); composite alarms to cut alert noise. Sample traces at the entry service (default 1 request per second plus 5%), and index only a small share of spans in Transaction Search.
  • Containers: Container Insights with enhanced observability for EKS is billed per observation, and the OpenTelemetry-based version per GB; compare with Amazon Managed Service for Prometheus (billed per sample ingested, with per-label-set series limits).
Production function: JSON logs, only errors from the code and warnings from the platform 
aws lambda update-function-configuration \
  --function-name order-validator \
  --logging-config LogFormat=JSON,ApplicationLogLevel=ERROR,SystemLogLevel=WARN
Let stored logs tier down automatically in this account and Region 
aws logs put-storage-tier-policy --storage-tier INTELLIGENT_TIERING
# Separate from the Essentials log class, which only lowers ingestion cost

Lambda log levels work only with JSON format (text is still the default), and a level set in code overrides the setting. Setting retention on an existing log group deletes older events at once. The CloudWatch agent's aggregation without drop_original_metrics doubles the metric count. Trace sampling rules apply only where no upstream decision exists, so set them on the entry service.

  • AWS Lambda introduces tiered pricing for Amazon CloudWatch logs and additional logging destinations (AWS Compute Blog, May 2025): Lambda log tiers and direct delivery to S3 and Firehose.

Key takeaways

  • Storage: Intelligent-Tiering for unknown access, Lifecycle for known patterns with expiration and noncurrent-version rules, aggregate small objects, mind minimum durations; EFS lifecycle and One Zone.
  • Block: gp3 everywhere with IOPS and throughput bought separately, io2 only when needed, Compute Optimizer for sizing, snapshot archive only for long-kept snapshots.
  • Databases: DynamoDB on-demand vs provisioned plus reserved capacity, Standard-IA when storage dominates; RDS RIs; Aurora I/O-Optimized for I/O-heavy and Serverless v2 auto-pause for idle; Database Savings Plans for 1-year cross-engine commitments.
  • Backups: tiered retention in AWS Backup plans, cold storage where supported (not RDS or Aurora), snapshot export to S3 for long-term data, DLM for EBS, short retention for DR copies.
  • Observability: filter and set log levels at the source, Essentials and Intelligent Tiering for logs, retention on every group, S3 for audit logs, low-cardinality aggregated metrics, sampled traces.
