Data-centre migration: VMware and Oracle to AWS

One programme to empty the data centre before the lease ends: a business case and a dependency map, a strategy per application, small waves that grow, VMware servers rehosted with AWS Transform MGN, Oracle databases moved with minimal downtime, files and archives copied in bulk, and a cutover that can always be rolled back until the old racks are switched off.

Scenario and requirements

The company's data centre runs several hundred VMware virtual machines and its Oracle databases, connected to AWS by Direct Connect. The landing zone in AWS Organizations (o-a1b2c3d4e5) is already in place: management, security tooling, log archive and shared-network (666666666666) accounts, and prod, staging and dev accounts per business unit. The lease ends in 18 months, so the board treats the exit as one programme with one budget and one deadline, not as a series of team projects. The mainframe billing batch and the SQL Server estate are part of the same exit but follow their own paths on Task 4.1; this page covers the VMware servers, the Oracle databases and the file data.

How it works

Four stages repeat for every wave once the pilot has proven them. Steps marked AWS happen automatically.

  1. Assess and plan
  2. Discover the estateMigration teamThe AWS Transform discovery tool, an appliance on vCenter, collects servers, utilization, Oracle database details and network connections over WinRM and SSH.
  3. Business case and groupsAWSAWS Transform assessment turns the inventory into a TCO business case with scenarios, and the connection data shows which servers talk to which, the raw material for move groups.
  4. Decide and scheduleMigration teamEach application group gets one of the 7 Rs, move groups become waves, and the pilot wave (under 10 dev and test servers) goes first, into 121212121212.
  5. Rehost a wave
  6. Install agentsMigration teamThe replication agent goes on every server in the wave; block-level data flows over Direct Connect on TCP 1500 to replication servers in the target account's staging subnet.
  7. Continuous replicationAWSAfter the initial sync, Transform MGN keeps the staging volumes current until launch. Launches use the account's launch configuration template, including the MAP tag.
  8. Test, then cut overMigration teamA test launch is checked by post-launch actions and the application owner; in the cutover window the team launches cutover instances and moves traffic.
  9. Move the databases
  10. Convert and loadDBADMS Schema Conversion converts the orders schema to PostgreSQL; DMS runs a full load, then change data capture (CDC) from the Oracle redo logs, with validation.
  11. Switch writersDBAAt cutover, writes stop on Oracle, CDC drains to zero lag, applications point at the target, and a reverse task keeps Oracle current for rollback.
  12. Accept and decommission
  13. HypercareApplication ownerFor an agreed period the old systems stay intact. DNS weights move back if the decision matrix calls for rollback.
  14. Finalize and switch offMigration teamFinalizing cutover stops replication and removes the agent; the source VMs are archived and powered off, and the tags show the wave's cost.

Build it

Step 1

Business case, portfolio and tracking tags

The phases. AWS's large-migration guidance and MAP use the same three phases: assess (business case, readiness, TCO), mobilize (landing zone, detailed portfolio, operating model, closing readiness gaps) and migrate and modernize (an initialization period, then waves run by a migration factory). The Cloud Adoption Framework's six perspectives (Business, People, Governance, Platform, Security, Operations) frame the readiness review: who owns each application after the move, who signs off a cutover, which skills the operations team lacks. MAP adds funding and partner support across those phases, and in return expects migrated resources to carry the MAP tag (below). The Well-Architected Migration Lens gives best practices per phase, though it predates AWS Transform.

The business case. AWS Transform assessment builds a TCO case in minutes from an inventory (RVTools exports, a CMDB, a discovery tool), with what-if scenarios for purchase options, Graviton, licensing and right-sizing, exported as PowerPoint, Excel or PDF. Migration Evaluator still offers Quick Insights and an AWS-built business case and is not closed. The Professional-level point is that the case rests on utilization data, not on the VMs' allocated sizes: on-premises servers are usually oversized, and right-sizing plus Savings Plans after the move is where much of the saving comes from (Task 3.1). For Oracle, licensing often outweighs infrastructure in the case, which is why the refactor of the orders schema is in scope at all.

Portfolio and the 7 Rs. The discovery data and interviews with owners place each application group in one of the 7 Rs. For this estate:

  • Retire: about one server in ten is a "zombie" (averaging under 5% CPU and memory); they are switched off after an owner confirms, which removes cost and wave effort at once.
  • Retain: the mainframe until AWS Transform for mainframe finishes, and a lab system tied to on-premises hardware.
  • Rehost: the bulk of the VMs, including the order monolith's application servers, with Transform MGN.
  • Replatform: the finance database to RDS for Oracle; file shares to S3 and FSx.
  • Refactor: only the orders schema to Aurora PostgreSQL, because the company already runs Aurora PostgreSQL and the Oracle licence renewal falls inside the programme. AWS advises against refactoring during a large migration otherwise: migrate first, modernize after.
  • Repurchase: the on-premises HR system moves to SaaS. Relocate (Amazon EVS) is the fallback in Alternatives.

Move groups and waves. A move group is everything that must move in the same window: servers sharing a database, a single owner or a patch window. Network connections reveal these groups; a server list alone doesn't, and that's how applications end up split from their databases across a slow link. Shared services such as Active Directory are not a reason to group; domain controllers are built in AWS first. Waves are one or more move groups, planned 4 to 5 waves ahead and sized to the network bandwidth and the team (AWS cites a team of four rehosting about 50 servers a week). The pilot wave is dev and test servers only, so the runbook and post-launch actions get fixed where mistakes are cheap.

Tracking from day one. MAP benefits depend on migrated resources carrying the map-migrated tag, and finance wants spend per wave. A tag policy fixes the spelling and the allowed wave names, and the management account activates both keys as cost allocation tags before the pilot, because tags only allocate costs from the moment they're on a resource and activated.

Tag policy: one spelling for the MAP and wave tags, with the allowed wave names enforced on EC2 instances (Organizations tag policy, attached to the workload OUs) 
{
  "tags": {
    "map-migrated": {
      "tag_key": { "@@assign": "map-migrated" }
    },
    "migrationwave": {
      "tag_key": { "@@assign": "MigrationWave" },
      "tag_value": { "@@assign": ["pilot", "wave-01", "wave-02", "wave-03", "wave-04"] },
      "enforced_for": { "@@assign": ["ec2:instance"] }
    }
  }
}
Activate the migration tags for billing (AWS CLI, management account) 
aws ce update-cost-allocation-tags-status \
  --cost-allocation-tags-status \
    TagKey=map-migrated,Status=Active \
    TagKey=MigrationWave,Status=Active

A tag policy controls spelling and values when a tag is used; it doesn't make the tag required. The MAP tag value comes from the MAP agreement, so the policy doesn't list values for it. Untagged resources launched before activation can't be backfilled into history that never existed.

Step 2

Landing zone readiness and the replication network

Target accounts. Migrated servers land in the same business unit accounts as the cloud-native workloads, never in a "migration account" that would need splitting later. The accounts come from Control Tower Account Factory with the organization's baseline already applied: organization trail, Config, GuardDuty and Security Hub CSPM delegated to the security tooling account, and SCPs from the workload OUs (Task 2.3; the full baseline is on the SCS multi-account security baseline). Each target account gets a staging subnet for replication servers and target subnets for the launched instances, in spoke VPCs attached to the Transit Gateway owned by 666666666666 (see the ANS Transit Gateway hub and spoke for segmentation and route tables). Migration engineers and application testers sign in through IAM Identity Center permission sets scoped to the wave's accounts; nobody uses IAM users for agent installs (SCS workforce identity).

Connectivity. Replication runs over the existing Direct Connect: a transit VIF to a Direct Connect gateway associated with the Transit Gateway, two locations for resiliency, and Site-to-Site VPN as a backup that carries traffic only when Direct Connect fails (Task 1.3; the ANS resilient Direct Connect architecture goes deeper). Two flows must be open: TCP 443 from source servers and the staging subnet to the Transform MGN endpoint (control), and TCP 1500 from source servers to the replication servers (data, encrypted). Swapping the two is a classic mistake. Hybrid DNS, with Route 53 Resolver forwarding corp.example.com to the on-premises resolvers, lets migrated servers keep finding systems that haven't moved yet.

Bandwidth. Wave size follows the link, not ambition. Initial syncs, the DMS full loads and DataSync all share the connection with production traffic, so the plan staggers them: big initial syncs at night and at weekends, DataSync throttled during business hours (Step 6), and the replication servers sized to the wave as AWS's right-sizing post describes. As a rule of thumb from Task 4.1, 100 TB takes about 12 days over 1 Gbps at 80% utilization.

Install the replication agent on a source server without prompts; at scale the MGN connector does this over SSH or WinRM (Linux source server) 
# Credentials come from a role with AWSApplicationMigrationAgentInstallationPolicy
sudo ./aws-replication-installer-init \
  --region us-east-1 \
  --no-prompt

Agentless replication through vCenter is gone for new deployments, and AWS Transform never supported it, so every wave needs agents, change tickets and credentials for each server. Automating the agent install with the MGN connector or the AWS Transform workflow is what keeps the factory's pace.

Step 3

Rehost the VMware servers with Transform MGN

How it works. The agent does a block-level copy of each disk, then continuous replication, to lightweight replication servers in the staging subnet; staging EBS volumes hold the copy. At launch, a conversion server makes the disks bootable on EC2, and test or cutover instances start from the server's EC2 launch template. Lifecycle: initial sync, ready for testing, testing (each new test replaces the last), ready for cutover, cutover, then finalize. Servers are grouped into applications and waves, and actions run at server, application or wave level, across accounts in the organization through global view. Each source server gets 2,160 free replication hours (90 days of continuous replication) from agent install, so agents go on shortly before the wave, not months ahead; the staging and launched resources are billed as usual.

AWS Transform for VMware runs the same engine through an agentic, guided job: discovery, wave planning, translating on-premises networks and firewall rules into VPCs and security groups, and rehosting through MGN. It's free for these jobs, but each job targets one Region and one account per wave, and its waves can run in parallel workspaces for separate teams. The company uses it for the bulk waves and drives Transform MGN directly for the few servers that need special handling.

The launch configuration template sets defaults for every new server in the account: right-sizing from the source's CPU and RAM (overriding the template's instance type), keeping the source's private IP where the target subnet's range allows it, transferring the source server's tags, and the MAP tag. With MAP tagging on, Transform MGN tags migrated resources with the key map-migrated and the value supplied. Post-launch actions run Systems Manager documents on test and cutover instances; one that must succeed blocks cutover until it does.

Account launch defaults: right-sizing, MAP tag, tag transfer, and a hardening document that must pass before cutover (AWS CLI, production account 111111111111) 
aws mgn create-launch-configuration-template \
  --target-instance-type-right-sizing-method BASIC \
  --copy-tags \
  --launch-disposition STARTED \
  --boot-mode USE_SOURCE \
  --enable-map-auto-tagging \
  --map-auto-tagging-mpe-id MAP_TAG_VALUE \
  --post-launch-actions '{
    "deployment": "TEST_AND_CUTOVER",
    "s3LogBucket": "mgn-postlaunch-logs-111111111111",
    "ssmDocuments": [{
      "actionName": "post-migration-hardening",
      "ssmDocumentName": "Company-PostMigrationHardening",
      "timeoutSeconds": 3600,
      "mustSucceedForCutover": true
    }]
  }'

The command returns the template ID (here lct-0a1b2c3d4e5f6a7b8). Further actions can be added to it with aws mgn put-template-action, which takes the template ID, an action ID and name, the document, an order between 1001 and 10000, and an optional category such as SECURITY or VALIDATION. Template changes apply to servers added afterwards, not to servers already in the console, so the template is set before the first agent of a wave is installed. Windows servers that bring their own licence need a Dedicated Host: the EC2 launch template's tenancy must be host, or the launch fails.

Test launch for the pilot application's two servers once both show ready for testing (AWS CLI, account 121212121212) 
aws mgn start-test \
  --source-server-ids s-1234567890abcdef0 s-0fedcba0987654321

The test instances run in an isolated test subnet so they can't write to production systems, while replication carries on. The application owner signs off the test; the cutover, finalize and rollback commands are in Step 7.

Step 4

Refactor the orders database to Aurora PostgreSQL

Schema first. DMS moves tables and data, not every database object. DMS Schema Conversion, managed and free, converts the Oracle schema and PL/SQL code to Aurora PostgreSQL, with generative AI (and since 2026 agentic assistance) for code the rules can't convert. Its assessment report is part of the business case: the share of code needing manual work decides whether refactoring fits in the programme's timeline. Secondary objects (triggers, sequences, foreign keys) are created after the full load so they don't slow it or fire during it. The desktop Schema Conversion Tool remains only for data warehouses and ETL code.

Data. A full load copies the existing rows, then CDC applies changes read from the Oracle redo logs, so the target stays seconds behind until cutover. The table mapping includes every ORDERS table and turns Oracle's upper-case names into lower case, which PostgreSQL treats as unquoted identifiers. Oracle names in rules must be given in upper case.

table-mappings.json: every table in the ORDERS schema, with schema, table and column names converted to lower case (DMS table mapping) 
{
  "rules": [
    {
      "rule-type": "selection",
      "rule-id": "1",
      "rule-name": "orders-schema",
      "object-locator": { "schema-name": "ORDERS", "table-name": "%" },
      "rule-action": "include"
    },
    {
      "rule-type": "transformation",
      "rule-id": "2",
      "rule-name": "lowercase-schema",
      "rule-action": "convert-lowercase",
      "rule-target": "schema",
      "object-locator": { "schema-name": "ORDERS" }
    },
    {
      "rule-type": "transformation",
      "rule-id": "3",
      "rule-name": "lowercase-tables",
      "rule-action": "convert-lowercase",
      "rule-target": "table",
      "object-locator": { "schema-name": "ORDERS", "table-name": "%" }
    },
    {
      "rule-type": "transformation",
      "rule-id": "4",
      "rule-name": "lowercase-columns",
      "rule-action": "convert-lowercase",
      "rule-target": "column",
      "object-locator": { "schema-name": "ORDERS", "table-name": "%", "column-name": "%" }
    }
  ]
}

DMS Serverless fits this load: heavy during the full load, light during weeks of CDC. It scales between minimum and maximum DMS capacity units (1 DCU is 2 GB of RAM, up to 384), can't scale down during a full load, needs VPC endpoints to reach services such as S3 and Secrets Manager, and after its first start can only resume. Multi-AZ protects the long CDC phase.

Serverless full load plus CDC for the orders schema, Multi-AZ, with validation on (AWS CLI, production account 111111111111) 
aws dms create-replication-config \
  --replication-config-identifier orders-oracle-to-aurora \
  --source-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:ORACLESRC \
  --target-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:AURORATGT \
  --replication-type full-load-and-cdc \
  --compute-config MinCapacityUnits=4,MaxCapacityUnits=64,MultiAZ=true,ReplicationSubnetGroupId=dms-migration-subnets \
  --table-mappings file://table-mappings.json \
  --replication-settings '{"ValidationSettings":{"EnableValidation":true}}'

Validation compares source and target rows and needs a primary key or unique index on each table, so tables without one are found in the premigration assessment and fixed first. LOB columns use limited LOB mode, sized from the largest real LOB, because limited mode truncates anything larger. The AWS Oracle-to-PostgreSQL blog series follows the same discovery, assessment, planning and post-cutover tuning stages.

Step 5

Replatform the finance database to RDS for Oracle

The finance application is a packaged product its vendor supports only on Oracle, so refactoring isn't an option. RDS for Oracle keeps the engine and removes the operating work (backups, patching, Multi-AZ), with licensing either included or brought by the company (BYOL); which one is cheaper depends on the licences the company already owns and their terms, a question for the licence team, not the architects. If the vendor's agents need OS access, RDS Custom for Oracle is the managed option that allows it; otherwise EC2 with full control.

Oracle to Oracle doesn't qualify for DMS homogeneous data migrations (those cover MySQL, MariaDB, PostgreSQL, MongoDB and DocumentDB only). For a large database the fastest path is native: export or restore with Oracle's own tools (Data Pump or RMAN) into RDS, recording the system change number (SCN) the copy is consistent to, then start a DMS CDC-only task from that SCN to catch up and stay in sync.

Catch the finance database up from the SCN of its native export, then keep it in sync until cutover (AWS CLI, production account 111111111111) 
aws dms create-replication-task \
  --replication-task-identifier finance-oracle-cdc \
  --source-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:FINORASRC \
  --target-endpoint-arn arn:aws:dms:us-east-1:111111111111:endpoint:RDSORATGT \
  --replication-instance-arn arn:aws:dms:us-east-1:111111111111:rep:FINRI \
  --migration-type cdc \
  --cdc-start-position "<SCN recorded by the Data Pump export>" \
  --table-mappings file://finance-mappings.json \
  --replication-task-settings '{"ValidationSettings":{"EnableValidation":true}}'

This one uses a provisioned replication instance, because the CDC load is steady and the instance can be sized once. RDS Blue/Green deployments don't support Oracle, so later engine upgrades of this database are planned as their own changes, not part of the migration.

DMS homogeneous data migrations don't support Oracle or SQL Server, and DMS Fleet Advisor is past end of support, so database inventory now comes from the AWS Transform discovery tool (which collects Oracle details). A refactor to PostgreSQL removes Oracle licence cost; a replatform to RDS for Oracle removes operating effort but keeps the licence.

Step 6

File shares and archives

Online with DataSync. The NFS share used by the order monolith (80 TB, new on this page) moves to S3 with DataSync: an agent on premises, transfer over Direct Connect, verification of what was copied, and repeated incremental runs until cutover, when a final run takes only the changes. Several agents add speed, not availability. During business hours the task is throttled so replication and production traffic keep their share.

Migration task for the order monolith NFS share, throttled to about 400 MB/s and reporting errors to S3 (AWS CLI, production account 111111111111) 
aws datasync create-task \
  --name nfs-share-migration \
  --source-location-arn arn:aws:datasync:us-east-1:111111111111:location/loc-0a1b2c3d4e5f60001 \
  --destination-location-arn arn:aws:datasync:us-east-1:111111111111:location/loc-0a1b2c3d4e5f60003 \
  --options VerifyMode=ONLY_FILES_TRANSFERRED,TransferMode=CHANGED,PreserveDeletedFiles=PRESERVE,BytesPerSecond=419430400,LogLevel=BASIC \
  --task-report-config '{"Destination":{"S3":{"S3BucketArn":"arn:aws:s3:::dc-archive-111111111111","Subdirectory":"datasync-reports/","BucketAccessRoleArn":"arn:aws:iam::111111111111:role/datasync-report-writer"}},"OutputType":"SUMMARY_ONLY","ReportLevel":"ERRORS_ONLY"}'

The BytesPerSecond limit is in bytes (419430400 is 400 × 1024 × 1024); a separate night task without the limit, or updating the task's options before each night run, uses the full link. The report role datasync-report-writer is new on this page.

Offline with Data Transfer Terminal. The backup and media archive (600 TB, new on this page) would take weeks over the shared link. Snowball is closed to new customers, so the company uses AWS Data Transfer Terminal: staff bring the company's own storage devices to an AWS facility and upload over 100 Gbps links, billed per port-hour with no per-GB fee. The user guide limits it to Enterprise Support customers, which the company is. The archive is moved once, early, because it doesn't change.

Step 7

Cutover, rollback and decommission

Before the window. Every cutover has a written rollback plan with a decision-maker named in advance, a timebox (if the problem and its fix can't be explained within it, roll back) and a decision matrix of severity, scope and time to fix, as AWS's rollback post recommends. DNS TTLs are lowered days before. For databases, a reverse DMS task from the new target back to the old source is built and tested in the pilot, so the source can be kept current during hypercare.

In the window. Writes stop at the source, DMS CDC drains to zero lag and validation shows no mismatches; applications switch connection strings (kept in Secrets Manager); cutover instances launch from the last replicated state; post-launch actions pass; traffic moves.

Launch cutover instances for the wave's servers (AWS CLI, production account 111111111111) 
aws mgn start-cutover \
  --source-server-ids s-1234567890abcdef0 s-0fedcba0987654321

The partner portal's web tier is stateless, so its traffic moves gradually: weighted records send 10% of DNS answers to the new load balancer, then more as error rates hold. Rollback is a single change setting the AWS weight to 0. The on-premises record and the load balancer alias have the same name and type, and AWS recommends a TTL of 60 seconds on non-alias records grouped with a load balancer alias.

Canary step for partners.example.com: 90% on premises, 10% on the new ALB (change batch for aws route53 change-resource-record-sets) 
{
  "Comment": "Wave 2 cutover, canary 10 percent",
  "Changes": [
    { "Action": "UPSERT", "ResourceRecordSet": {
        "Name": "partners.example.com", "Type": "A", "SetIdentifier": "on-premises", "Weight": 90, "TTL": 60,
        "ResourceRecords": [ { "Value": "203.0.113.10" } ] } },
    { "Action": "UPSERT", "ResourceRecordSet": {
        "Name": "partners.example.com", "Type": "A", "SetIdentifier": "aws-use1", "Weight": 10,
        "AliasTarget": { "HostedZoneId": "Z35SXDOTRQ7X7K", "DNSName": "partners-use1-1234567890.us-east-1.elb.amazonaws.com", "EvaluateTargetHealth": true } } }
  ]
}

Stateful applications can't split traffic, so for them the same records move straight from 100/0 to 0/100 after the database switch, and back again if the rollback criteria are met while the reverse task runs. A change batch is applied all or nothing, so both weights always change together.

Hypercare and decommission. Hypercare (two weeks for this company) keeps the source VMs, the reverse replication and the on-premises record. Then, and only then, the team finalizes: finalizing stops replication, deletes the replication resources within about 90 minutes and tells the agent to uninstall itself, but leaves the launched instances running. It's one-way.

After acceptance: finalize each server, which removes its replication resources and agent (AWS CLI, production account 111111111111) 
aws mgn finalize-cutover --source-server-id s-1234567890abcdef0
aws mgn finalize-cutover --source-server-id s-0fedcba0987654321

The source VMs are powered off and kept for the retention period the risk team sets, then deleted; the DMS tasks and the reverse task are stopped and removed; on-premises DNS records, firewall rules and backup jobs for the wave are retired; and the hardware list for the lease return is updated. Operations take over through a structured handoff, so the migration team can start the next wave without being pulled back. Cost Explorer grouped by MigrationWave shows each wave's run cost against the business case, and right-sizing and Savings Plans follow once usage has settled for a few weeks.

Design decisions

Migrate first, modernize after

Rehost and replatform carry most of the estate because the lease, not the architecture, sets the deadline, and AWS's large-migration guidance recommends exactly that. The one refactor (orders to Aurora PostgreSQL) earns its place through the licence saving and an existing Aurora PostgreSQL skill set. The cost is that rehosted servers bring their inefficiencies with them; the modernization backlog (containers, managed services, the strangler fig on the order monolith) starts after the exit (Task 4.1).

Waves sized by dependencies and bandwidth

Move groups come from network connection data, and wave size from the link and the team's measured pace. A small pilot slows the first month but fixes the runbook, the post-launch documents and the rollback before production waves depend on them. Bigger waves look faster on a plan and fail in practice when the initial syncs saturate Direct Connect.

Agent-based replication into the final accounts

Agents are the only Transform MGN option for new deployments, so the design invests in automated installs. Replicating straight into the business unit accounts means no second move later, at the price of a staging subnet and security groups in every target account, which the account baseline creates.

Native load plus CDC for the large Oracle database

For the finance database, a native Oracle copy is faster than a DMS full load and keeps every Oracle object; DMS CDC from the copy's SCN closes the gap. The cost is two tools and a DBA who knows both. The orders database uses DMS for both phases because the engines differ and validation is needed.

Rollback kept open until finalize

Source servers, reverse replication and DNS weights stay ready through hypercare, which costs two environments for a few weeks per wave. That cost buys the ability to say yes to a cutover window, and AWS's rollback guidance treats it as engineering maturity, not pessimism (Task 4.3).

Alternatives

Relocate the VMware estate to Amazon EVS

Amazon Elastic VMware Service runs VMware Cloud Foundation in the company's own VPC on EC2 bare metal, and VMware HCX can move VMs with no conversion. It's the fastest way out of the building and keeps the VMware tools and skills, but it keeps the VMware licensing and the hypervisor layer too, and every later modernization still starts from VMs. It suits a deadline that rehosting can't meet, or workloads that can't take an agent.

Everything Oracle to RDS for Oracle (or everything to PostgreSQL)

Replatforming both databases is simpler and faster, but keeps all the Oracle licensing the business case was meant to reduce. Refactoring both would put the vendor's finance product out of support. The split follows what each application allows.

VM Import/Export or a migration factory of scripts

VM Import/Export fits a handful of one-off images but has no continuous replication, so downtime equals copy time. The Cloud Migration Factory on AWS solution automates wave metadata, prerequisite checks, agent installs and cutover across hundreds of servers; its README still mentions CloudEndure Migration, and for new programmes AWS Transform covers wave planning and orchestration.

Network-only migration of data

Copying the 600 TB archive over Direct Connect avoids handling devices, but takes weeks of shared bandwidth from replication. Data Transfer Terminal costs port-hours and staff time instead, and suits large one-off data sets that don't change.

Testing it

  1. Prove the dependency mapBefore a wave is approved, compare its move groups with the discovery tool's network connections for the last 30 days: any connection from a wave server to a server in a later wave needs an owner's sign-off and a firewall rule over Direct Connect.
  2. Rehearse in the pilotRun the full runbook in 121212121212: agent install, test launch, post-launch actions (the hardening document must fail a deliberately noncompliant server and block its cutover), cutover, rollback by DNS, and a second cutover.
  3. Database cutover rehearsalOn a copy of the orders database, measure how long CDC takes to drain after writes stop and whether validation reports zero mismatched rows; run the reverse task and confirm Oracle receives a test write made on Aurora. The measured time sets the real cutover window.
  4. Performance and load testsLoad test the test instances at peak volume before cutover, because right-sized instances can be smaller than the VMs they replace; check that the Aurora version of the top queries is within the agreed latency.
  5. Tagging and cost checksAfter each wave, the tag policy compliance report and Cost Explorer grouped by map-migrated and MigrationWave must show every launched instance and volume tagged; untagged resources mean lost MAP credit and are fixed the same week.
  6. Decommission checkBefore the lease return, confirm no traffic reaches the old IP ranges for two weeks (firewall and DNS query logs), every server is finalized or archived in Transform MGN, and no DMS task or DataSync schedule still points on premises.

"Migrate hundreds of VMware VMs in 12 months with minimal changes and minimal downtime" is rehost with AWS Transform MGN (or AWS Transform for VMware), in waves, not refactoring. "Discover dependencies before planning waves" is AWS Transform discovery with network connection data; Application Discovery Service and Migration Hub answers are wrong for new customers. "Oracle to PostgreSQL with minimal downtime" is DMS Schema Conversion, then DMS full load plus CDC. "Keep the vendor-certified Oracle engine but stop managing it" is RDS for Oracle (RDS Custom if OS access is required). "Track migrated resources for MAP credits" is the map-migrated tag, applied automatically by Transform MGN. "Hundreds of terabytes, one time, link too slow" is now Data Transfer Terminal, not Snowball.
