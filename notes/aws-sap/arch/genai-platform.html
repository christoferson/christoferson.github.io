Reference architecture

Multi-account generative AI platform

Every business unit wants generative AI, and nobody wants a dozen unmanaged copies of it. One platform team runs approved models, shared knowledge, agents, guardrails and the audit trail in two central accounts, and each unit gets access, a cost line and a quota share instead of its own stack.

Scenario and requirements

The support assistant worked, and now every business unit wants generative AI: marketing for drafts, finance for report summaries, the EU business unit for its own customers. Left alone, each would build its own stack, and nobody could tell the auditors what the model was asked, by whom, and what it said. Task 1.2 already set up two central accounts: the central GenAI account 222222222222 (approved models, guardrails, knowledge bases, invocation logs) and the agent platform account 333333333333 (AgentCore runtimes and gateways). This page turns them into a platform for the whole organization o-a1b2c3d4e5.

The requirements:

  • Controlled access: units call only approved models, only through the platform, with no long-lived keys.
  • Chargeback: each unit's spend is visible and billed back to it, and one unit can't use up everyone's quota.
  • Safety by default: every model call passes a guardrail the calling team can't remove, and risky agent actions need a person.
  • Residency: EU customer prompts are processed only in the EU (Task 2.4).
  • Evidence: every prompt and response is kept as tamper-evident evidence for a year (Task 2.3).

Reused from the SAP task pages: role GenAIInvoker-Support and application inference profile a1b2c3d4e5f6 in 222222222222 (Task 1.2); guardrail support-gr version 3, gateway support-gw-a1b2c3d4e5, topic refund-approvals and the $500 refund rule (Task 2.5); the /genai/bedrock-invocations log group and the PlatformSecurityAdmin role (Task 2.3); the EU business unit account 555555555555 (Task 2.4); the refund tool open-refund-request in the production account 111111111111. New on this page:

  • Inference profile: support-assistant-prod, the name of profile a1b2c3d4e5f6, copied from a us. system profile and tagged BusinessUnit and CostCenter.
  • Knowledge: managed knowledge base support-articles in 222222222222 (written KB_ID in code), fed from bucket example-support-articles-222222222222.
  • Agents: runtime execution role support-agent-runtime in 333333333333, the gateway tool request_refund and state machine refund-approval.
  • EU: the EU unit runs Bedrock in its own account in eu-central-1 with eu. profiles (Step 2 explains why).

Status changes to know. Bedrock Agents is now Agents Classic, closed to new customers since 30 July 2026: new agents run on AgentCore. AWS Agent Registry became generally available on 31 August 2026 in its own agent-registry namespace; the preview namespace was shut down on 30 October 2026. Organization-enforced guardrails arrived in April 2026, AgentCore Policy in March 2026, global cross-Region inference profiles in October 2025, and the GuardDuty AI Protection plan in July 2026. The bedrock-mantle endpoint (OpenAI-compatible APIs) isn't captured by invocation logging and has no guardrails, so this platform uses bedrock-runtime.

How it works

A customer asks the support assistant about a refund. Steps marked AWS happen automatically.

  1. The request reaches the agent
  2. Sign in and askCustomerThe web app sends the question with the customer's Cognito token to the AgentCore Runtime endpoint in 333333333333; the runtime's JWT authorizer checks issuer, audience and scopes.
  3. Start a sessionAWSThe runtime starts an isolated session and issues a workload access token bound to both the agent and this customer.
  4. Retrieve and reason
  5. Retrieve help articlesAgentThe agent calls Retrieve on support-articles in 222222222222 with the full knowledge base ARN, allowed by the knowledge base's resource policy.
  6. Call the modelAgentThe agent assumes its invoker role in 222222222222 and calls Converse with the application inference profile and guardrail support-gr version 3.
  7. Check, route and logAWSThe request guardrail and the organization guardrail both run (the strictest result wins); the us. profile picks a US Region with capacity; invocation logging writes prompt, response, token counts and caller identity to /genai/bedrock-invocations.
  8. Act on the order system
  9. Call a toolAgentThe agent asks the gateway to run issue_refund for $120. AgentCore Policy evaluates the Cedar policies against the user's claims and the amount, permits it, and the gateway invokes open-refund-request in 111111111111.
  10. Escalate a large refundAWSFor $900 the policy denies issue_refund; the agent can only call request_refund, which starts refund-approval. Step Functions publishes a task token to refund-approvals and waits up to 24 hours.
  11. Approve or rejectSupport managerThe approval app calls SendTaskSuccess, and the workflow, not the agent, issues the refund. No answer in 24 hours means rejected.

Build it

Step 1

The access path into the hub

No resource policy for invocation. Bedrock has no resource-based policy for invoking models, so a business unit can't call a model in another account directly. Two ways in (Task 1.2):

  • Assume a role in the hub. Each consuming unit gets its own invoker role in 222222222222 (GenAIInvoker-Support, GenAIInvoker-Marketing and so on), trusted only by that unit's workload role. One role per unit matters later: IAM principal cost attribution then shows each unit by name.
  • Call a gateway. An AgentCore Gateway with inference targets, or a LiteLLM-based gateway such as AWS's multi-provider generative AI gateway guidance, exposes one endpoint. Callers need permission on the gateway, not on Bedrock; the gateway's role holds the Bedrock permissions and can enforce rate limits per caller.

A profile per unit and use case. In the hub, the platform team creates an application inference profile for each consumer, copied from a system cross-Region profile, and tags it. Callers use its ARN as modelId; metrics and cost carry its tags.

Central GenAI account 222222222222: a tagged profile for the support assistant, routing across US Regions (AWS CLI) 
aws bedrock create-inference-profile \
  --region us-east-1 \
  --inference-profile-name support-assistant-prod \
  --description "Support assistant production traffic" \
  --model-source copyFrom=arn:aws:bedrock:us-east-1:222222222222:inference-profile/us.anthropic.claude-sonnet-5-5 \
  --tags key=BusinessUnit,value=support key=CostCenter,value=CC-1001
A business unit's workload calls the approved model through the hub (Python, boto3) 
import boto3

# Role in the central GenAI account, trusted only by this unit's workload role
creds = boto3.client("sts").assume_role(
    RoleArn="arn:aws:iam::222222222222:role/GenAIInvoker-Support",
    RoleSessionName="support-assistant",
)["Credentials"]

runtime = boto3.client(
    "bedrock-runtime", region_name="us-east-1",
    aws_access_key_id=creds["AccessKeyId"],
    aws_secret_access_key=creds["SecretAccessKey"],
    aws_session_token=creds["SessionToken"],
)

# The application inference profile attributes cost and metrics to this unit
resp = runtime.converse(
    modelId="arn:aws:bedrock:us-east-1:222222222222:application-inference-profile/a1b2c3d4e5f6",
    messages=[{"role": "user", "content": [{"text": "Where is order o-1001?"}]}],
    guardrailConfig={"guardrailIdentifier": "support-gr", "guardrailVersion": "3"},
)

Application inference profiles exist only in the API (not the console), work with Converse and InvokeModel but not the Responses or Chat Completions APIs, and their tags reach billing only after the payer account activates them (up to 24 hours, not retroactive). Interface VPC endpoints for bedrock-runtime keep calls private (Task 1.4; Bedrock inference notes).

"Grant the other accounts access with a resource policy on the model" is wrong; there isn't one. A hub also pools every unit's tokens-per-minute demand on the hub's per-account, per-Region quotas, so one noisy unit can throttle all the others unless a gateway rate-limits by caller.

Step 2

Keep EU processing in the EU

Cross-Region inference is the default, not an exception. The us. profile above sends requests to any US Region in its list for capacity. Geographic profiles (eu., us., apac.) keep processing inside the geography; global profiles (global.) can route to any commercial Region, including Regions the account hasn't enabled. Global is about 10% cheaper and has its own quota, but it isn't residency-safe (Task 2.4).

Where the SCP must sit. An SCP restricts principals in the accounts it's attached to. If the EU unit assumed a role in the hub, a hub principal would make the call and the EU OU's SCP wouldn't apply. So the EU unit runs Bedrock in its own account 555555555555 (the spoke pattern), in eu-central-1 with eu. profiles, under the EU OU's SCP, with the organization guardrail (Step 5), its own invocation logging (Step 7), tagged profiles and its own quota.

SCP for the EU OU: no global cross-Region inference (geographic eu. profiles still work) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyGlobalCrossRegionInference",
      "Effect": "Deny",
      "Action": "bedrock:*",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "aws:RequestedRegion": "unspecified" },
        "ArnLike": {
          "bedrock:InferenceProfileArn": "arn:aws:bedrock:*:*:inference-profile/global.*"
        }
      }
    }
  ]
}

How it reads: global profiles appear to IAM with the Region "unspecified", so a deny listing Regions by name never catches them. Conversely, an eu. profile needs every destination Region allowed by the OU's Region deny (or an exemption by bedrock:InferenceProfileArn), or requests fail. Check destinations with get-inference-profile from each source Region rather than trusting the prefix.

Data at rest stays in the source Region, but prompts and outputs may be stored in the destination Region for abuse detection, so the geography, not the Region, is the residency boundary. Guardrails on the Standard tier also need a cross-Region guardrail profile, so prompts can be checked elsewhere in the geography.

Step 3

Shared knowledge for RAG

Managed by default. The help articles live in example-support-articles-222222222222, and a managed knowledge base support-articles in the hub handles parsing, embedding, storage, hybrid search and reranking, with scheduled syncs. A customer-managed knowledge base is the choice when a unit needs its own vector store or chunking: S3 Vectors for large, rarely queried indexes at low cost; OpenSearch for low-millisecond, high-QPS hybrid search; Aurora pgvector when the data is already in PostgreSQL; Neptune Analytics for relationships across documents (Task 1.2; the managed and customer-managed knowledge base notes).

Cross-account retrieval. A managed knowledge base accepts a resource policy that allows other accounts bedrock:Retrieve and bedrock:GetDocumentContent, nothing else, with no wildcards in Resource or Action. The agent's role also needs an identity policy for the same actions and passes the full ARN as knowledgeBaseId.

kb-policy.json: the agent platform's runtime role may retrieve from the support articles 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAgentPlatformRetrieve",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::333333333333:role/support-agent-runtime" },
      "Action": ["bedrock:Retrieve", "bedrock:GetDocumentContent"],
      "Resource": "arn:aws:bedrock:us-east-1:222222222222:knowledge-base/KB_ID"
    }
  ]
}
Attach it in the central GenAI account 222222222222 (AWS CLI) 
aws bedrock-agent put-resource-policy \
  --region us-east-1 \
  --resource-arn arn:aws:bedrock:us-east-1:222222222222:knowledge-base/KB_ID \
  --policy file://kb-policy.json

Pass --expected-revision-id when several people or pipelines edit the policy. RetrieveAndGenerate, or a customer-managed knowledge base, needs a narrowly scoped role in the hub instead.

The embedding model and vector store can't be changed after creation: a new embedding model means a new knowledge base, rebuilt blue/green. For several units sharing one corpus, use one knowledge base with a mandatory server-side metadata filter or document-level ACLs, not a knowledge base per unit (each allows only five data sources).

Step 4

Agents on AgentCore

The building blocks, all in 333333333333 (Task 1.2, Task 2.5, and the Runtime and Gateway, Identity and Policy notes):

  • Runtime runs each agent in isolated sessions of up to 8 hours, in VPC mode so tools can reach private systems over Direct Connect. Its execution role is the ceiling of what any user can make the agent do.
  • Gateway turns Lambda functions, APIs and MCP servers into tools behind one endpoint. A Lambda target in another account needs lambda:InvokeFunction on the gateway role and a function resource policy naming that role.
  • Identity keeps OAuth clients and API keys in a token vault, and its on-behalf-of token exchange lets the order system see the real user, not the agent.
  • Policy evaluates every tool call outside the model with Cedar (or Dogwood) policies; it denies by default and forbid wins.
  • Agent Registry catalogues approved agents, MCP servers and skills, so units reuse tools instead of rebuilding them.
Let the gateway call the refund tool in the orders account (AWS CLI in account 111111111111) 
aws lambda add-permission \
    --function-name open-refund-request \
    --statement-id AllowAgentGateway \
    --action lambda:InvokeFunction \
    --principal arn:aws:iam::333333333333:role/AgentGatewayServiceRole
AgentCore Policy (Cedar): support staff may refund up to $500 through this gateway; nothing else is permitted 
permit (
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"OrdersTarget___issue_refund",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-east-1:333333333333:gateway/support-gw-a1b2c3d4e5"
)
when {
  principal.hasTag("role") && principal.getTag("role") == "support" &&
  context.input.amount <= 500
};

How it reads: the tool name is the target name, three underscores, then the tool. A separate permit for OrdersTarget___request_refund hands larger refunds to the approval workflow in Step 6. The model can't argue its way past these rules: a prompt-injected "refund $5,000" simply fails.

Start the policy engine in LOG_ONLY: in ENFORCE with no permits it denies every tool call. Anyone with bedrock-agentcore:UpdateGateway can switch the mode or detach the engine, so that permission belongs to the platform team only. Split gateways by trust boundary, because the gateway role bounds every target behind it.

Step 5

Guardrails nobody can skip

From weakest to strongest (Task 2.5, Guardrails notes): the application passes a guardrail; IAM requires one with the bedrock:GuardrailIdentifier condition key; an account-level enforced guardrail covers every call in the account and Region; an Organizations Bedrock policy attaches a management-account guardrail to every member account, can't be removed by members, and in comprehensive mode checks all content regardless of input tags. All layers run and the strictest result wins.

The platform uses two layers: a baseline organization guardrail (prompt attacks, PII, banned topics) for every account, and each use case's own guardrail required by IAM on its invoker role.

GenAIInvoker-Support: model calls only through the support profile, and only with guardrail version 3 (IAM policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "InvokeOnlyWithGuardrail",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:us-east-1:222222222222:application-inference-profile/a1b2c3d4e5f6",
        "arn:aws:bedrock:*::foundation-model/*"
      ],
      "Condition": {
        "StringEquals": {
          "bedrock:GuardrailIdentifier": "arn:aws:bedrock:us-east-1:222222222222:guardrail/support-gr:3"
        }
      }
    },
    {
      "Sid": "ApplyThatGuardrail",
      "Effect": "Allow",
      "Action": "bedrock:ApplyGuardrail",
      "Resource": "arn:aws:bedrock:us-east-1:222222222222:guardrail/support-gr"
    }
  ]
}

Converse is authorized as bedrock:InvokeModel. The foundation-model ARN uses a Region wildcard because a cross-Region profile runs the model in its destination Regions.

Management account: create the organization guardrail policy (AWS CLI; the policy JSON is the one on Task 2.5) 
aws organizations create-policy \
  --type BEDROCK_POLICY \
  --name org-guardrail-baseline \
  --description "Baseline guardrail for every model call in member accounts" \
  --content file://org-guardrail-policy.json

First enable the policy type (EnablePolicyType) and give the management account's guardrail in each Region a resource policy granting bedrock:ApplyGuardrail to the organization (aws:PrincipalOrgID); then attach the policy and check it from a member with DescribeEffectivePolicy. Guardrail charges go to the calling account.

Every caller needs bedrock:ApplyGuardrail on an enforced guardrail, or all its model calls fail. The IAM condition breaks roles used for RetrieveAndGenerate or agent internals, which call models without a guardrail, so give those their own roles. Guardrails don't check tool results or retrieved chunks: the agent calls ApplyGuardrail or InvokeGuardrailChecks on untrusted tool output to catch indirect prompt injection.

Step 6

Human approval for risky actions

Tier by rule, not by model. The Agentic AI Lens asks for approval levels set by deterministic rules (AGENTSEC04-BP02): read-only tools run alone, small writes run within limits, and payments, deletions and external messages need a person. Approvals can take hours or days, longer than an agent session, so they live in a Step Functions Standard workflow with the .waitForTaskToken callback (Task 2.5).

refund-approval (excerpt): refunds over $500 wait up to 24 hours for a human, then are rejected by default (Amazon States Language) 
{
  "StartAt": "NeedsApproval",
  "States": {
    "NeedsApproval": {
      "Type": "Choice",
      "Choices": [
        { "Variable": "$.amount", "NumericGreaterThan": 500, "Next": "RequestApproval" }
      ],
      "Default": "IssueRefund"
    },
    "RequestApproval": {
      "Type": "Task",
      "Resource": "arn:aws:states:::sns:publish.waitForTaskToken",
      "Parameters": {
        "TopicArn": "arn:aws:sns:us-east-1:333333333333:refund-approvals",
        "Message": {
          "TaskToken.$": "$$.Task.Token",
          "OrderId.$": "$.orderId",
          "Amount.$": "$.amount"
        }
      },
      "TimeoutSeconds": 86400,
      "Catch": [
        { "ErrorEquals": ["States.Timeout", "States.TaskFailed"], "Next": "RejectRefund" }
      ],
      "Next": "IssueRefund"
    },
    "IssueRefund": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "issue-refund", "Payload.$": "$" },
      "End": true
    },
    "RejectRefund": { "Type": "Fail", "Error": "RefundNotApproved" }
  }
}

How it reads: the workflow pauses at no compute cost until the approval app calls SendTaskSuccess or SendTaskFailure with the token; on timeout the answer is no. Store the decision context in S3 before asking, and log who approved. Express workflows don't support task tokens.

"The agent must not issue large refunds without a manager" is a deterministic threshold in AgentCore Policy plus a Step Functions approval, not an instruction in the system prompt. "Approvals may take several days" rules out waiting inside an agent session.

Step 7

Evidence, quotas and cost

Two kinds of record (Task 2.3). The organization trail already has InvokeModel and Converse as management events: who called which model, without the content. Knowledge base retrieval, ApplyGuardrail and agent calls are data events, added with advanced event selectors where needed. The prompts and responses come only from model invocation logging, which is off by default, set per account and per Region, and writes only to a log group or bucket in the same account and Region. It's turned on in the hub, in the EU spoke and in every Region they use.

Central GenAI account 222222222222: log every prompt and response, large payloads to S3 (AWS CLI; repeat per Region and in 555555555555) 
aws bedrock put-model-invocation-logging-configuration \
  --region us-east-1 \
  --logging-config '{
    "cloudWatchConfig": {
      "logGroupName": "/genai/bedrock-invocations",
      "roleArn": "arn:aws:iam::222222222222:role/BedrockInvocationLogging",
      "largeDataDeliveryS3Config": {
        "bucketName": "example-genai-invocation-logs-222222222222",
        "keyPrefix": "large"
      }
    },
    "textDataDeliveryEnabled": true,
    "imageDataDeliveryEnabled": true,
    "embeddingDataDeliveryEnabled": false
  }'

A CloudWatch Logs centralization rule or S3 replication copies the logs to the log archive account, under Object Lock with one-year retention (Task 2.4). The Task 2.3 SCP lets only PlatformSecurityAdmin change logging, and GuardDuty raises DefenseEvasion:IAMUser/BedrockLoggingDisabled if it's turned off anyway. The GuardDuty AI Protection plan adds findings for Bedrock and SageMaker AI such as anomalous invocations and cost harvesting (its direct prompt-injection finding needs the guardrail's prompt-attack filter). AgentCore traces go to CloudWatch GenAI observability, viewed from the monitoring account through cross-account observability (Task 5.3).

Quotas are per account and Region (tokens per minute per model, a daily cross-model token cap, separate cross-Region quotas). The hub watches InvocationThrottles and EstimatedTPMQuotaUsage, raises quotas before launches, and caps units at the gateway.

Cost levers (Task 3.1):

  • On-demand Standard tier by default. Priority (75% premium) for latency-critical chat; Flex (50% off) for work that can wait; bedrock:ServiceTier stops teams choosing Priority on their own.
  • Reserved tier (reserved tokens per minute for serverless models, through the account team) for steady critical traffic. Provisioned Throughput is billed per model unit per hour whether used or not, starts with a quota of zero, can't be used through inference profiles, and is needed mainly for custom models.
  • Prompt caching for the assistant's long system prompt and tool definitions (cache reads don't count toward the TPM quota); batch inference at 50% off for overnight summaries, best effort and without prompt caching.
Catch a runaway agent loop hours before the bill does (AWS CLI, 222222222222) 
aws cloudwatch put-metric-alarm \
  --alarm-name bedrock-output-tokens-high \
  --namespace AWS/Bedrock \
  --metric-name OutputTokenCount \
  --dimensions Name=ModelId,Value=example-model-id \
  --statistic Sum --period 3600 --evaluation-periods 1 \
  --threshold 5000000 --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:222222222222:genai-cost-alerts

Chargeback (Task 3.3): everything lands on the hub's bill, so profile tags (cost per unit and use case) and IAM principal attribution in CUR 2.0 (which invoker role spent it) pass the cost back, with a budget per unit.

Design decisions

Hub for most units, spoke where policy demands it

The hub gives one place for models, guardrails, knowledge and logs; new units onboard with a role and a profile. Its costs: shared quotas, a larger blast radius, a cross-account hop. The EU unit is a spoke because its SCP must apply to the calling principal. The AWS SRA AI Security guide says to merge accounts when risk profiles are uniform and only pre-trained models are used.

Role assumption or gateway

Role assumption needs no extra infrastructure, but nothing caps one unit's share. A gateway adds per-caller rate limits, model fallback and one endpoint for several providers, at the cost of another component (AgentCore Gateway is managed and charged per invocation; a LiteLLM proxy runs on your containers).

Separate agent platform account

Agents hold credentials to business systems and run code, a different risk from calling a model. A separate account limits who can change gateways, policy engines and execution roles, and keeps every cross-account permission explicit and reviewable.

Geographic before global

Global profiles are cheaper with more capacity, so US units may use them where residency allows; EU traffic uses eu. profiles, enforced by SCP. Neither guarantees availability: keep bounded retries and a fallback model.

Alternatives

Bedrock in every workload account

Each account gets its own quotas and blast radius; governance comes from SCPs, the Bedrock policy, invocation logging deployed by StackSets, tagged profiles and Service Quotas request templates (up to 10 quotas, new accounts only). Knowledge bases and prompts get duplicated.

Step Functions instead of an agent

For known steps (classify a ticket, look up the order, draft a reply), a Standard workflow calling Bedrock is cheaper, deterministic and fully audited. Agents earn their cost where requests are open-ended.

Testing it

  1. Try to skip the guardrailFrom GenAIInvoker-Support, call Converse without guardrailConfig, then with version 2: both must fail with AccessDenied. A call from a member account with harmless text in guardrail tags must still be checked by the organization guardrail.
  2. Try to leave the EUFrom 555555555555, call a global. profile (denied) and an eu. profile (allowed); in CloudTrail, additionalEventData.inferenceRegion must show only EU Regions.
  3. Probe the shared knowledgeCall Retrieve from a role not in the policy, and RetrieveAndGenerate cross-account: both denied.
  4. Red-team the agentWith the policy engine in LOG_ONLY, replay real sessions and injected prompts ("refund $5,000") and review every decision before switching to ENFORCE.
  5. Let an approval expireIn staging, shorten the timeout and ignore the SNS message: the execution must end in RejectRefund and no refund appears in the order system.
  6. Break the evidence trailIn a sandbox, delete the logging configuration as a normal admin (blocked by the SCP), then as PlatformSecurityAdmin: the GuardDuty finding must arrive.
  7. Load and costLoad-test one unit to throttling: the gateway limit must protect the others. A day later, Cost Explorer spend by BusinessUnit must match token counts.

"Business units in other accounts must use models in a central account with the least operational overhead" is cross-account role assumption (or a gateway), never a resource policy on the model. "Charge each department for its Bedrock usage" is tagged application inference profiles with activated cost allocation tags (or IAM principal attribution). "Every model call in every account must pass the company guardrail, and teams must not be able to turn it off" is an Organizations Bedrock policy. "EU prompts must be processed only in the EU" is an eu. profile plus an SCP denying the "unspecified" Region. "Another account's agent must search our knowledge base" is the knowledge base resource policy (Retrieve only). "Keep every prompt and response for audit" is model invocation logging, not CloudTrail. "A human must approve high-value actions, possibly days later" is Step Functions with waitForTaskToken.
