Reference architecture

Multi-Region disaster recovery tiers

One recovery design for the whole company, not one per team: every workload gets a DR tier from its RTO, RPO and the cost the business will pay, from nightly backups copied to us-west-2 up to a checkout that runs in both Regions all the time, with one orchestrated, tested way to move between Regions.

Scenario and requirements

Production runs in us-east-1 (production account 111111111111 and the business unit accounts), with us-west-2 for recovery. Every application is already Multi-AZ, so AZ failures stay inside the Region (Task 4.3); this design covers losing a Region or losing data. The board wanted one answer per system to "what if us-east-1 is down for a day", with a price on each, so the architects grouped the portfolio into four tiers.

WorkloadTier, targets and main services
Internal tools (wiki, HR portal, build servers)Backup and restore: RPO 24 hours, RTO 24 hours; AWS Backup copies to us-west-2, redeploy from IaC
Reporting systemPilot light: RPO minutes, RTO 4 hours; headless Aurora Global Database secondary, compute only in templates
Rehosted EC2 servers not yet modernizedElastic Disaster Recovery: RPO seconds, RTO under an hour; staging area in us-west-2, recovery plans
Mobile APIWarm standby: RPO under a minute, RTO 15 minutes; scaled-down ECS service, Aurora Global Database, Route 53 failover
CheckoutActive/active: RPO seconds, RTO near zero; DynamoDB global tables, latency routing, full capacity in both Regions

Reused from the SAP task pages: orders-global and orders-usw2 and the S3 invoice replication (Task 1.5), the Region switch and DRS drill patterns (Task 4.2), the api.example.com latency records for checkout (Task 1.4), and FisExperimentRole and example-fis-reports (Task 4.3). New on this page:

  • Backup: vaults internal-tools-vault (us-east-1) and dr-vault (us-west-2) in 111111111111.
  • Databases: reporting global database reporting-global with clusters reporting-use1 and reporting-usw2; DynamoDB table Checkout.
  • Mobile API: record mobile.example.com, ECS service mobile-api on cluster mobile-usw2, secret prod/mobile-api/db, Region switch plan ARN shown as $MOBILE_DR_PLAN_ARN.
  • DRS: source servers s-0a1b2c3d4e5f60011 and s-0a1b2c3d4e5f60012, snapshot pit-0a1b2c3d4e5f60021; alarm checkout-success-below-99.

Status changes to know. CloudEndure Disaster Recovery was discontinued on 29 September 2025 (outside China); use Elastic Disaster Recovery (DRS). The ARC readiness check closed to new customers on 30 April 2026 (replaced by Region switch plan evaluation), and Incident Manager on 7 November 2025. Newer than the DR whitepaper: ARC Region switch (August 2025), the Aurora global writer endpoint (October 2024), DynamoDB multi-Region strong consistency (June 2025) and DRS recovery plans (August 2026).

How it works

Replication runs all the time; recovery runs only when someone declares a disaster. Steps marked AWS happen automatically.

  1. Every day, before anything fails
  2. Copy and replicateAWSAWS Backup copies to dr-vault; Aurora, DynamoDB global tables, S3, ECR and Secrets Manager replicate to us-west-2; DRS replicates server disks into a staging area.
  3. Evaluate the planAWSARC Region switch checks each plan every 30 minutes for permissions, configuration, capacity and quota parity, and Route 53 health checks watch both Regions.
  4. A Regional event in us-east-1
  5. DeclareIncident leadUsing written criteria, the incident lead declares us-east-1 impaired. Checkout needs no decision: its latency records already skip the unhealthy Region.
  6. Run the Region switch planIncident leadOne ungraceful execution, started in us-west-2: an approval step, then ECS scaling for the mobile API, Aurora global failover, and the health check flip that moves mobile.example.com.
  7. Recover servers and reportingPlatform teamThe DRS recovery plan launches the protected servers in order; the reporting team adds an instance to the headless secondary, fails it over and deploys reporting compute from templates.
  8. Restore internal toolsPlatform teamLast in priority: restore from dr-vault and redeploy the tools' stacks in us-west-2.
  9. After the event
  10. Rebuild and fail backPlatform teamThe post-recovery workflow rebuilds replicas in us-east-1; DRS reverse replication protects the recovered servers; a planned, graceful switchover returns production later, with no data loss.

Build it

Step 1

Assign a tier to every workload

Targets come from the business. The RPO is how much data a workload can lose and the RTO how long it can be down. The architects ask each owner what an hour of downtime or of lost orders costs, then show the price of each tier; one aggressive target for everything means paying active/active prices for the wiki. The strategies map to recovery times: backup and restore in hours, pilot light in tens of minutes, warm standby in minutes, active/active near zero (Task 4.2).

Data first. Asynchronous replication between Regions means RPO is never quite zero, and it copies corruption and deletions instantly, so even checkout keeps point-in-time backups. The immutable, cross-account backup design is the SCS ransomware resilience page.

Tier as metadata. Each resource carries the dr-tier tag (tag policy pattern from Task 3.3). AWS Backup selects by it, Resilience Hub applications with a resiliency policy per tier are defined by it, and Cost Explorer grouped by it shows each tier's real cost.

Activate the tier tag for cost reporting (AWS CLI, management account) 
aws ce update-cost-allocation-tags-status \
  --cost-allocation-tags-status TagKey=dr-tier,Status=Active

"Multi-AZ" isn't a DR strategy for a Regional event, and replication alone isn't one for a data disaster. A Professional answer names both: replication or copies to the second Region for availability, and point-in-time, immutable backups for corruption.

Step 2

Backup and restore for internal tools

The internal tools are a wiki, an HR portal and build servers on EC2 and EBS with small RDS databases. They can be down for a day, so they pay only for backup storage in two Regions. A backup plan takes a daily backup in us-east-1 and a copy action sends each recovery point to dr-vault in us-west-2. At organization scale the same rule comes from an Organizations backup policy, a delegated administrator and a separate backup account; that design is the DOP organization backup page.

plan.json: daily backup kept 35 days, copied to the us-west-2 vault (input for aws backup create-backup-plan --backup-plan file://plan.json, production account 111111111111) 
{
  "BackupPlanName": "internal-tools-daily",
  "Rules": [
    {
      "RuleName": "daily-copy-to-usw2",
      "TargetBackupVaultName": "internal-tools-vault",
      "ScheduleExpression": "cron(0 5 ? * * *)",
      "StartWindowMinutes": 60,
      "Lifecycle": { "DeleteAfterDays": 35 },
      "CopyActions": [
        {
          "DestinationBackupVaultArn": "arn:aws:backup:us-west-2:111111111111:backup-vault:dr-vault",
          "Lifecycle": { "DeleteAfterDays": 35 }
        }
      ]
    }
  ]
}

A backup selection assigns every resource tagged dr-tier=backup-restore to the plan. A backup alone isn't a recovery: the tools' networks and instances are CloudFormation stacks deployable to us-west-2, and quotas there are raised in advance. Restore testing restores sample recovery points on a schedule and records how long each took, the evidence for the 24-hour RTO; Backup Audit Manager reports whether cross-Region copies are scheduled and restore times meet the target (Task 4.3).

A copy in us-west-2 is only useful if everything needed to use it is there too: templates, images, secrets and keys. Data the applications encrypt themselves needs a multi-Region key (Step 4), or the DR Region can't decrypt it while us-east-1 is down.

Step 3

Pilot light for reporting, DRS for the remaining servers

Reporting. Finance can wait four hours for reports but can't redo a day of reconciliations. The reporting-global Aurora PostgreSQL global database has a headless secondary, reporting-usw2: storage replicates continuously but no DB instances run, so the standby costs mainly replicated storage. The catch: a headless secondary needs an instance added before it can be switched over or failed over to, a control plane action during the event that a four-hour RTO can absorb. Reporting compute exists only as templates and images in us-west-2.

Rehosted servers. About forty EC2 servers rehosted from the data centre can't be rebuilt from templates, so Elastic Disaster Recovery replicates their disks at block level into a low-cost staging area in us-west-2 (replication servers and EBS volumes, not full-size copies). RPO is typically seconds and RTO minutes; point-in-time snapshots (seven days by default) allow recovery from before a corruption. Launch settings (right-sizing, private IPs, tags) and post-launch actions (Systems Manager documents) shape what launches, and a recovery plan orders servers into steps (databases, application, web) with wait steps between.

Monthly drill in us-west-2: launch two protected servers, one from a point in time, without stopping replication (AWS CLI, production account 111111111111) 
aws drs start-recovery \
  --region us-west-2 \
  --is-drill \
  --source-servers \
    sourceServerID=s-0a1b2c3d4e5f60011,recoverySnapshotID=pit-0a1b2c3d4e5f60021 \
    sourceServerID=s-0a1b2c3d4e5f60012

Without a snapshot ID, DRS launches from an on-demand snapshot of the latest state. Drills use an isolated subnet and don't stop replication. After a real recovery, reverse replication protects the recovered instances and leads back to us-east-1. DRS costs a flat $0.028 per source server per hour, drills included, plus staging resources; recovered instances cost only while they run.

DRS allows 300 replicating servers per account and Region, a quota that can't be raised; larger estates use several staging accounts. DRS recovery plans can't call Lambda or SSM steps or span accounts, and Region switch has no DRS block, so call DRS from a Region switch Lambda step.

Step 4

Warm standby for the mobile API: data and artifacts

The mobile API must take traffic within 15 minutes and lose under a minute of orders. In us-west-2 the mobile-api ECS service on Fargate runs behind its own ALB at a fraction of production's task count, passing health checks and smoke tests daily; it only needs to scale. Its data is the orders-global Aurora global database, whose secondary orders-usw2 has a reader instance and storage-level replication with lag typically under a second. Applications use the global writer endpoint, which follows the primary after a switchover or failover.

The two ways to move the writer have different RPOs. A switchover (healthy clusters: rotation, game days, failback) syncs the secondary, makes the primary read-only, then promotes: RPO 0. A failover with --allow-data-loss (us-east-1 unreachable) doesn't wait for sync, attempts best-effort write fencing, and tries to snapshot the old primary so lost writes can be found later. Pick the secondary with the lowest AuroraGlobalDBRPOLag.

Planned rotation, then the unplanned version (AWS CLI) 
# Planned: run in the primary Region; Aurora syncs first, so no data is lost
aws rds switchover-global-cluster --region us-east-1 \
    --global-cluster-identifier orders-global \
    --target-db-cluster-identifier arn:aws:rds:us-west-2:111111111111:cluster:orders-usw2

# Unplanned (us-east-1 is down): run in the secondary Region and accept losing the replication lag
aws rds failover-global-cluster --region us-west-2 \
    --global-cluster-identifier orders-global \
    --target-db-cluster-identifier arn:aws:rds:us-west-2:111111111111:cluster:orders-usw2 \
    --allow-data-loss

Everything else the standby needs must already be in us-west-2, because recovery can't depend on the Region being left:

  • Images: ECR registry replication copies new pushes to us-west-2 (one hop; existing images need replication backfill; repository policies aren't replicated, so use repository creation templates).
  • Secrets: the database secret is replicated, so the standby reads it locally.
  • Keys: multi-Region KMS keys share key material, so us-west-2 decrypts data encrypted in us-east-1 without a cross-Region call; policies, grants and aliases are set per Region (Task 2.2).
  • Objects: invoices replicate to us-west-2 with S3 Replication Time Control, which replicates 99.9% of objects within 15 minutes and adds replication metrics and missed-threshold events (Task 1.5).
Replicate the mobile API's database secret to the DR Region (AWS CLI, us-east-1) 
aws secretsmanager replicate-secret-to-regions \
    --secret-id prod/mobile-api/db \
    --add-replica-regions Region=us-west-2
Step 5

Orchestrated failover with Route 53 and ARC Region switch

DNS. mobile.example.com has a failover record pair: PRIMARY to the us-east-1 ALB and SECONDARY to the us-west-2 ALB. Each alias record sets EvaluateTargetHealth (required for failover aliases) and carries a health check. Route 53 health checks are data plane and keep working in a Regional event; changing records or weights during the event is a control plane action that may not be available, so the design never edits records to fail over.

Failover records for mobile.example.com, each tied to a health check (change batch for aws route53 change-resource-record-sets) 
{
  "Comment": "Warm standby failover for the mobile API",
  "Changes": [
    { "Action": "UPSERT", "ResourceRecordSet": {
        "Name": "mobile.example.com", "Type": "A", "SetIdentifier": "primary-use1", "Failover": "PRIMARY",
        "HealthCheckId": "USE1_HEALTH_CHECK_ID",
        "AliasTarget": { "HostedZoneId": "Z35SXDOTRQ7X7K", "DNSName": "mobile-use1-1234567890.us-east-1.elb.amazonaws.com", "EvaluateTargetHealth": true } } },
    { "Action": "UPSERT", "ResourceRecordSet": {
        "Name": "mobile.example.com", "Type": "A", "SetIdentifier": "secondary-usw2", "Failover": "SECONDARY",
        "HealthCheckId": "USW2_HEALTH_CHECK_ID",
        "AliasTarget": { "HostedZoneId": "Z1H1FL5HABSF5", "DNSName": "mobile-usw2-1234567890.us-west-2.elb.amazonaws.com", "EvaluateTargetHealth": true } } }
  ]
}

Which health checks? AWS's DR guidance prefers a human decision with automated steps over automatic Region failover, which can flap, so the records use health checks the recovery tooling controls. The cheaper choice is the Region switch Route 53 health check block, which creates per-Region checks that the plan flips but depends on the Region being activated. The stronger choice is ARC routing controls, with a data plane across five Regions and safety rules, at $2.50 per cluster-hour (about $1,800 a month, shared across applications), built on the DOP multi-Region active/active page.

Region switch plan. The mobile API's plan ($70 per plan per month) covers the two Regions, active/passive, with a 15-minute RTO objective: an approval block, an ECS capacity block that scales mobile-api in us-west-2 to production's recent peak, a global Aurora block (switchover when graceful, failover when ungraceful), then the health check block. Each Region has its own Region switch data plane, the plan's roles and documents exist in both Regions, and each execution writes a PDF report.

Declared disaster: move the mobile API to us-west-2 even though us-east-1 is impaired (AWS CLI) 
aws arc-region-switch start-plan-execution \
  --plan-arn "$MOBILE_DR_PLAN_ARN" \
  --target-region us-west-2 \
  --action activate \
  --mode ungraceful \
  --comment "us-east-1 regional event, declared by incident lead"

A graceful run loses no data and is what game days use; an ungraceful run accepts data loss and skips steps that need the failed Region. A post-recovery action rebuilds replicas in us-east-1 for failback. A parent plan for Region evacuation nests the mobile API and checkout plans, with a custom Lambda block starting the DRS recovery plan.

Region switch scaling blocks request capacity but don't guarantee it. For a 15-minute RTO, reserve the critical capacity with On-Demand Capacity Reservations in us-west-2, billed at the On-Demand rate whether used or not and discounted by Savings Plans or Regional Reserved Instances (Task 3.1). For Fargate the equivalent is raised quotas and a standby that's already running.

Step 6

Active/active checkout

Checkout runs in both Regions all the time, each able to carry all the traffic. That is static stability: losing a Region needs no launches, scaling or control plane calls, because launching after a failure is "bimodal" and depends on systems that may be impaired. api.example.com uses latency records with EvaluateTargetHealth to each Region's ALB (Task 1.4), so an unhealthy Region drops out of DNS answers without anyone acting.

Write pattern. Checkout writes locally: the Checkout DynamoDB table is a global table in the default multi-Region eventual consistency (MREC) mode between us-east-1 and us-west-2, with last writer wins and an RPO equal to the replication delay (driven by DynamoDB Streams, which stay on). Sessions are keyed by their own ID and requests are idempotent, so conflicting writes are rare. Payments go through the API to whichever Region holds the Aurora writer, the "write global" pattern for data that can't tolerate conflicts.

Add the us-west-2 replica to the Checkout table, making it a global table with the default eventual consistency (AWS CLI) 
aws dynamodb update-table --region us-east-1 --table-name Checkout \
    --replica-updates '[{"Create":{"RegionName":"us-west-2"}}]'

Strong consistency? Multi-Region strong consistency (MRSC) gives RPO 0, but needs exactly three Regions (or two plus a witness), adds write latency, has no transactions or TTL, and is fixed at creation. Checkout uses transactions in two Regions, so it stays on MREC; the cart table on Task 1.5 shows MRSC with a witness.

Region switch also supports active/active plans, whose deactivate action takes a Region out without failing anything over, for partial impairments that health checks miss. Global tables carry a 99.999% SLA; evacuation with routing controls is on the DOP multi-Region active/active page.

Step 7

Game days and fault injection

An assessment estimates RTO; only a test measures it (Well-Architected REL13-BP03). Besides graceful plan runs and DRS drills, FIS tests what DR plans tend to miss: both Regions up but unable to reach each other. The Cross-Region: Connectivity scenario blocks traffic from the experiment Region to the destination Region through transit gateways and subnet route tables and pauses S3, DynamoDB and MemoryDB replication, for 3 hours by default (up to 12). It targets resources by tag and has no stop conditions, so the template adds them.

FIS template, trimmed from the Cross-Region: Connectivity scenario: cut us-east-1 off from us-west-2 for one hour and pause checkout replication, stopping if checkout success drops (input for aws fis create-experiment-template, staging account first) 
{
  "description": "Split us-east-1 from us-west-2 for checkout",
  "roleArn": "arn:aws:iam::111111111111:role/FisExperimentRole",
  "targets": {
    "Subnet": {
      "resourceType": "aws:ec2:subnet",
      "resourceTags": { "DisruptSubnet": "Allowed" },
      "selectionMode": "ALL"
    },
    "DynamoDB-Global-Table": {
      "resourceType": "aws:dynamodb:global-table",
      "resourceTags": { "DisruptDynamoDb": "Allowed" },
      "selectionMode": "ALL"
    }
  },
  "actions": {
    "Disrupt-Subnet-Connectivity": {
      "actionId": "aws:network:route-table-disrupt-cross-region-connectivity",
      "parameters": { "duration": "PT1H", "region": "us-west-2" },
      "targets": { "Subnets": "Subnet" }
    },
    "Pause-DynamoDB-Replication": {
      "actionId": "aws:dynamodb:global-table-pause-replication",
      "parameters": { "duration": "PT1H" },
      "targets": { "Tables": "DynamoDB-Global-Table" }
    }
  },
  "stopConditions": [
    { "source": "aws:cloudwatch:alarm", "value": "arn:aws:cloudwatch:us-east-1:111111111111:alarm:checkout-success-below-99" }
  ],
  "experimentReportConfiguration": {
    "outputs": { "s3Configuration": { "bucketName": "example-fis-reports", "prefix": "cross-region/" } }
  }
}

Hypothesis: "if replication between the Regions stops for an hour, checkout keeps 99% success in both Regions and the backlog drains afterwards". At $0.10 per action-minute this experiment costs about $12, and the account's safety lever stops every running experiment at once if needed.

Design decisions

Tier per workload, not per company

Running everything active/active would roughly double compute and add conflict handling where it isn't needed; running everything on backups would leave checkout down for hours. Tiers make the trade explicit, and the dr-tier tag shows the standby cost per tier (Task 3.1).

Cost of each tier

Backup and restore pays for backup storage and copy transfer. Pilot light adds replicated Aurora storage; DRS adds the per-server fee and a small staging area. Warm standby adds a reader, a few tasks, an ALB, reserved capacity and the $70 plan. Active/active pays for full capacity in both Regions plus replicated writes, the biggest step, which is why only checkout takes it.

Human decision, automated steps

Only checkout fails over without a person, because it serves from either Region at any time. The other tiers move a database writer, which loses data in an ungraceful run, so an incident lead declares the disaster and one Region switch execution does the rest, without flapping on transient errors.

Data plane for recovery, control plane for preparation

Everything a recovery calls during the event is data plane: health checks, routing controls, the Region switch data plane in us-west-2. Everything that creates resources (instances, replicas, quotas, reservations, IAM roles) is done beforehand and checked by plan evaluation. The pilot light's headless secondary is the deliberate exception, accepted because its RTO is hours (Task 5.4).

Alternatives

Global Accelerator instead of DNS failover

Static anycast IPs fail over on health in about 30 seconds with no DNS caching, which suits partners that allow-list IPs. Traffic dials are control plane calls (made in us-west-2). The mobile apps resolve DNS well, so Route 53 suffices.

DRS for the mobile API instead of warm standby

DRS could protect EC2-based tiers with seconds of RPO and no running standby, but the mobile API is containers with Aurora: DRS replicates server disks, not managed databases or Fargate tasks. For cloud-native tiers, managed-service replication plus IaC is the fit; DRS is for servers that can't be rebuilt.

Detach and promote, or cross-Region read replicas

Removing the secondary from the global database and promoting it works when managed failover can't (incompatible engine versions), but breaks the topology, which must be rebuilt for failback. RDS cross-Region read replicas suit RDS engines; Aurora Global Database has lower lag and managed switchover.

Step Functions or runbooks as the orchestrator

Step Functions or Systems Manager Automation can do the same steps, but must run from the recovery Region with copies of everything they need, and give no plan evaluation or execution reports. Region switch covers Aurora, ECS, EKS, Auto Scaling and Route 53 natively, with Lambda for the rest.

Testing it

  1. Restore tests for tier 4AWS Backup restore testing restores a sample of internal-tool recovery points from dr-vault each week; the recorded restore times plus the stack deployment time must stay under 24 hours, and Backup Audit Manager must show the cross-Region copy control compliant.
  2. Pilot light rehearsalTwice a year, add an instance to the reporting secondary in a test copy, fail over, deploy the reporting stack and time it against four hours.
  3. DRS drillsMonthly drills launch the recovery plan into an isolated subnet; check that every server boots, post-launch actions pass and the application answers, then terminate the drill instances.
  4. Graceful game dayQuarterly, run the mobile API plan gracefully to us-west-2, serve production from there for a business day, and switch back; the PDF execution report shows the measured RTO, and order counts before and after the switchover must match (RPO 0).
  5. Split-Region experimentRun the FIS template in staging, then production; watch Route 53 HealthCheckStatus, checkout success per Region and DynamoDB replication latency until the backlog drains.
  6. Evaluation and costRegion switch plan evaluation must show "passed" (quota and capacity parity) before each game day; a monthly Cost Explorer view grouped by dr-tier compares each tier's standby cost with its budget.

"Lowest cost, recovery within a day" is backup and restore with cross-Region copies and IaC. "Database must be current but compute can start after the disaster" is pilot light. "Must take traffic immediately at reduced capacity" is warm standby. "No downtime, serve users from both Regions" is multi-site active/active with DynamoDB global tables. "Planned Region rotation with no data loss" is Aurora switchover; "primary Region unreachable" is failover with --allow-data-loss. "Replicate on-premises or EC2 servers with RPO in seconds and test without impact" is Elastic Disaster Recovery drills. "Orchestrate database, compute and DNS failover in one step with evidence for auditors" is ARC Region switch, and "most reliable manual traffic switch" is ARC routing controls.
