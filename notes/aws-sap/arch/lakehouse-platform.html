Reference architecture

Lakehouse data platform

One analytics account owns the company's data: order events and database changes land in Apache Iceberg tables within minutes, one catalog and one permission model govern every engine, and business units query the data in their own accounts, on their own bill, without copies.

Scenario and requirements

Analytics grew up account by account, with a different copy of the orders data, and a different answer, in every business unit. Task 1.5 already placed the lakehouse in the analytics account 444444444444, with business-unit accounts querying it. This page builds that lakehouse for the whole organization o-a1b2c3d4e5. The basics of Glue, Athena, Iceberg and Redshift are in the DEA-C01 notes; this page is about the multi-account design and its trade-offs.

The requirements:

  • Fresh data: order events are queryable within minutes, and order and customer data from Aurora PostgreSQL arrives without a hand-built pipeline.
  • One copy, many engines: Athena, Redshift and Spark jobs read the same tables, under one set of permissions.
  • Least privilege across accounts: each business unit sees only its domains, and the EU business unit sees only EU customers, without contact details (Task 2.4).
  • Encryption and evidence: customer managed keys per data domain, and an audit trail of who read what (Task 2.2, Task 2.3).
  • Cost on the right bill: consumers pay for their own queries, with caps, and storage costs fall as data ages (Task 3.4).

Reused from the SAP task pages: table bucket analytics-tables with its sales namespace, role SalesAnalyst and the LF-Tag domain=sales (Task 1.5); bucket example-curated and its customer managed key in 444444444444 (Task 2.2); the cart service's cart-lake-reader role (Task 2.1); the central-orders bus and the order-analytics queue in 444444444444 (event-driven modernization); the EU business unit account 555555555555. New on this page:

  • Ingestion: Lambda function order-analytics-forwarder and Firehose stream order-events-to-lake, writing table order_events in a new orders namespace of analytics-tables.
  • Warehouse: Redshift Serverless namespace and workgroup analytics in 444444444444, fed by a zero-ETL integration from the orders database orders on the Aurora PostgreSQL cluster in 111111111111; datashare orders_share.
  • Curated tables: Glue database curated with Iceberg table customers on example-curated; data filter eu_customers_no_contact; LF-Tag domain=orders.
  • Keys and query controls: KMS alias alias/lake-orders for the orders domain; Athena workgroup eu-analysts in 555555555555.

Status changes to know. The S3 Tables integration with AWS analytics services now uses IAM access control by default, with Lake Formation optional; moving an old Lake Formation-mode integration to IAM mode removes all its Lake Formation grants. "SageMaker Lakehouse" was the launch name; the documentation now says "the lakehouse architecture of Amazon SageMaker". The Firehose database change data capture preview was removed in September 2025, so database changes arrive through zero-ETL here.

How it works

A customer places an order, and an analyst in the EU business unit sees it in a report a few minutes later. Steps marked AWS happen automatically.

  1. Data arrives
  2. Publish the eventOrders serviceThe orders service in 111111111111 puts OrderConfirmed on central-orders; a rule delivers it to the order-analytics queue in 444444444444.
  3. Forward to FirehoseLambdaorder-analytics-forwarder reads batches from the queue and sends one JSON object per record to order-events-to-lake.
  4. Commit to IcebergAWSFirehose buffers the records and commits them to order_events in the table bucket, encrypted with the table bucket's KMS key. Records that don't match the table schema go to the S3 error prefix.
  5. Replicate database changesAWSThe zero-ETL integration copies inserts, updates and deletes from the orders database into the analytics Redshift Serverless namespace in near real time.
  6. Data is curated and governed
  7. Build curated tablesScheduled SQLRedshift runs MERGE and CTAS jobs that write Iceberg tables: sales aggregates into the sales namespace of analytics-tables, the regulated customers table into example-curated.
  8. Data is consumed
  9. Query in AthenaEU analystSigned in through IAM Identity Center, the analyst queries a resource link in 555555555555 from the eu-analysts workgroup.
  10. Authorize and filterAWSLake Formation checks the cross-account grant and applies eu_customers_no_contact: only EU rows, no e-mail or phone columns. Athena reads the files with credentials Lake Formation vends for this query, and CloudTrail records the access in both accounts.
  11. Query the warehouseFinance teamThe EU unit's own Redshift Serverless workgroup reads orders_share live, paying for its own compute while the analytics account pays for storage.

Build it

Step 1

Table buckets and keys per domain

Where Iceberg tables live. There are two homes for an Iceberg table, and this platform uses both (Task 1.5):

  • S3 Tables (table buckets): tables are subresources of a bucket built for Iceberg. Compaction and snapshot management are on by default, access uses s3tables resource policies at bucket and table level, and the bucket can default to SSE-KMS and the Intelligent-Tiering storage class. The default quota is now 100 table buckets per Region per account (raised from 10 on 30 September 2026). The high-churn streaming tables and the shared sales tables go here.
  • Iceberg on a general purpose bucket: you manage maintenance yourself, or let the Glue Data Catalog's table optimizers handle compaction, snapshot expiry and orphan files. You keep the familiar bucket features and policies. The regulated customers table goes on example-curated, whose key policy from Task 2.2 already limits decryption to S3 for that bucket.

A key per domain. Each data domain gets its own customer managed key in 444444444444, so revoking or auditing one domain doesn't touch the others, and key policies name the consumers of that domain only. The orders table bucket defaults to alias/lake-orders; a table can override the bucket default.

Analytics account 444444444444: a table bucket for the next domain, SSE-KMS by default, Intelligent-Tiering for new tables, tagged for cost allocation (AWS CLI) 
aws s3tables create-table-bucket \
  --region us-east-1 \
  --name payments-tables \
  --encryption-configuration sseAlgorithm=aws:kms,kmsKeyArn=arn:aws:kms:us-east-1:444444444444:key/KEY_ID \
  --storage-class-configuration storageClass=INTELLIGENT_TIERING \
  --tags domain=payments,CostCenter=CC-2001

The existing analytics-tables holds two domains in separate namespaces, so its orders tables set alias/lake-orders at table level. The caller needs s3tables:PutTableBucketEncryption, s3tables:PutTableBucketStorageClass and s3tables:TagResource as well as s3tables:CreateTableBucket. Tags on table buckets and tables (from November 2025) work for both ABAC and cost allocation.

With SSE-KMS, the key policy must let the S3 Tables maintenance principal use the key, or compaction and snapshot expiry can't read and rewrite the files; every integrated engine's role also needs KMS permissions. For Firehose, set the KMS key on the table bucket, not in the Firehose stream: Firehose ignores its own KMS settings when it delivers to S3 Tables.

Step 2

Stream order events into Iceberg

The path. The central-orders rule can't target Firehose in another account directly (cross-account direct targets are SQS, SNS, Lambda, Kinesis Data Streams and API Gateway), so it already delivers to the order-analytics queue in the analytics account. A small forwarder function turns queue messages into Firehose records. Firehose then writes to Iceberg tables, either self-managed in S3 or in S3 Tables, can route records from one stream to several tables, and can apply inserts, updates and deletes (Task 1.1).

order-analytics-forwarder: send each order event to Firehose as one JSON object per record (Python, Lambda with an SQS event source) 
import json
import boto3

firehose = boto3.client("firehose")

def handler(event, context):
    records = []
    for msg in event["Records"]:
        detail = json.loads(msg["body"])["detail"]
        # Flat, first-level fields only: Firehose maps top-level JSON keys to columns
        row = {
            "order_id": detail["orderId"],
            "customer_id": detail["customerId"],
            "status": "CONFIRMED",
            "amount": detail["amount"],
            "event_time": detail["confirmedAt"],
        }
        # One JSON object per Firehose record; several objects in one record fail
        records.append({"Data": (json.dumps(row) + "\n").encode()})

    resp = firehose.put_record_batch(DeliveryStreamName="order-events-to-lake", Records=records)
    # Fail the batch so SQS retries; consumers downstream must tolerate duplicates
    if resp["FailedPutCount"]:
        raise RuntimeError(f"{resp['FailedPutCount']} records rejected")

Limits that shape the design (Firehose Iceberg considerations):

  • Throughput: a Direct PUT stream to Iceberg starts at 5 MiB per second in us-east-1, us-west-2 and eu-west-1 and 1 MiB per second elsewhere; Firehose raises it under throttling, but plan a limit increase before a launch. Setting AppendOnly (insert only, API only) lets the stream scale automatically, which suits order events.
  • Partitions: higher throughput means fewer active partitions (about 3,000 at up to 20 MB/s, 100 at 40–400 MB/s), so partition by day, not by customer.
  • Schema: column names and types must match the table exactly; mismatches go to the S3 error prefix and extra fields are skipped. Databases and tables must be created through Iceberg's GlueCatalog API and can't contain hyphens, hence order_events.
  • One writer per table: Iceberg uses optimistic concurrency, so two streams writing one table keep retrying each other's commits. MSK Serverless isn't supported as a source.

Every Firehose commit creates a snapshot and new files, so a table fed every minute fills with small files and metadata quickly. On a general purpose bucket that is your problem (Glue optimizers, Athena OPTIMIZE and VACUUM); in a table bucket compaction runs for you. This is the main reason the streaming tables sit in S3 Tables.

Step 3

Database changes through zero-ETL

No pipeline to run. An Aurora zero-ETL integration replicates data and schema changes from the orders cluster into the analytics Redshift Serverless namespace in near real time; Aurora also supports a lakehouse of Amazon SageMaker as a target. Several clusters can feed one target, so the cart and payments databases can join later. The integration crosses accounts (cluster in 111111111111, warehouse in 444444444444); the Redshift side must authorize the source account before the integration can be created (the Redshift zero-ETL documentation covers the steps). AWS DMS with change data capture remains the option when data must be transformed on the way.

Requirements to plan for (Aurora zero-ETL limitations):

  • An Aurora PostgreSQL source needs at least one data filter pattern, at minimum one database such as orders.*.*; every table in the filter needs a primary key (otherwise it fails), and databases must be UTF-8.
  • Source and target must be in the same Region, and the source can't be an Aurora Limitless Database or a cross-account clone.
  • The first seeding, and any table resynchronization, can take 20–25 minutes or more; DDL such as ALTER TABLE on the source can trigger a resync that makes the table unavailable meanwhile.
  • Quotas: 100 integrations per account, 50 per target, 5 per source cluster.

The orders cluster is an Aurora Global Database with DR in us-west-2 (Task 4.2). If the primary fails over to the secondary, the integration becomes inactive and must be deleted and recreated, in the new Region, with a full reseed. A blue/green switchover also needs the integration deleted first. Put "recreate the zero-ETL integration" in the DR runbook, and don't promise analytics an RPO the integration can't keep.

Curating into Iceberg. Redshift now creates and writes Iceberg tables (CTAS, INSERT, UPDATE, DELETE, MERGE) in S3 and in table buckets, registered in the Glue Data Catalog, so the warehouse can publish curated tables that every engine reads.

Scheduled curation in the analytics workgroup: one regulated table on the general purpose bucket, one shared aggregate in the table bucket (Redshift SQL) 
-- Default Glue catalog: LOCATION is required and must be an empty prefix in this Region
CREATE TABLE awsdatacatalog.curated.customers
USING ICEBERG
LOCATION 's3://example-curated/iceberg/customers/'
TABLE PROPERTIES ('format-version'='2')
AS SELECT customer_id, full_name, email, phone, country, region, loyalty_tier
FROM orders_zeroetl.public.customers;

-- Table bucket: no LOCATION allowed; S3 Tables places and maintains the files
CREATE TABLE "analytics-tables@s3tablescatalog".sales.daily_orders
USING ICEBERG
AS SELECT order_date, region, COUNT(*) AS orders, SUM(amount) AS revenue
FROM orders_zeroetl.public.orders
GROUP BY order_date, region;

How it reads: orders_zeroetl is the Redshift database created from the integration (a new name). Format version 2 is deliberate: Athena creates only v2 tables and can't read v3. Later runs use MERGE, which needs S3 DELETE permission on a general purpose bucket because Redshift removes intermediate files (not needed for S3 Tables). DROP TABLE only removes the catalog entry, so the files on example-curated stay until orphan-file cleanup removes them.

Step 4

One permission model in Lake Formation

IAM mode or Lake Formation. The S3 Tables integration works with IAM alone, which is enough when whole tables go to whole roles. This platform needs column, row and cell permissions, tag-based grants and cross-account sharing to hundreds of principals, so the analytics account turns Lake Formation on for both catalogs. With Lake Formation, IAM and Lake Formation grants together decide access (Task 1.5; DEA-C01 Task 4.2 for the basics).

Settings that block sharing if you miss them (Lake Formation cross-account notes):

  • Cross-account version 4 or higher: needed to share objects in a federated catalog (the S3 Tables catalog is one) or resources in hybrid access mode. Version 5 shares unlimited tables through wildcard RAM shares, and can't be downgraded.
  • No IAMAllowedPrincipals on Lake Formation-mode resources: revoke it before cross-account grants, or Lake Formation throws AccessDeniedException; new databases should default to no permissions.
  • Catalog encryption with a customer managed key: a catalog encrypted with the Glue service-managed key can't be shared; recipients need decrypt permission on the catalog key.
settings.json for aws lakeformation put-data-lake-settings --data-lake-settings file://settings.json (it replaces the whole settings object, so read the current one first) 
{
  "DataLakeAdmins": [
    { "DataLakePrincipalIdentifier": "arn:aws:iam::444444444444:role/LakeAdmin" }
  ],
  "CreateDatabaseDefaultPermissions": [],
  "CreateTableDefaultPermissions": [],
  "Parameters": { "CROSS_ACCOUNT_VERSION": "4" }
}

Tags, not table lists. Each table carries LF-Tags (domain=orders, domain=sales); a grant to an LF-Tag expression covers every current and future table with those tags. Values inside one tag are OR, separate tags are AND. From version 3, LF-Tag grants to another account travel through AWS RAM (the recipient accepts an invitation; grants to an OU or the organization need none). The Task 1.5 grant of domain=sales to 555555555555 is the pattern; the EU unit gets domain=orders the same way.

Regulated customer data: a data filter. A data cells filter combines a row filter (a PartiQL predicate) and a column list or exclusion list. The EU unit gets SELECT on the filter, never on the table, so it sees EU customers only and never the contact columns.

Analytics account 444444444444: EU rows only, without e-mail and phone (aws lakeformation create-data-cells-filter --cli-input-json file://input.json) 
{
  "TableData": {
    "TableCatalogId": "444444444444",
    "DatabaseName": "curated",
    "TableName": "customers",
    "Name": "eu_customers_no_contact",
    "RowFilter": { "FilterExpression": "region = 'EU'" },
    "ColumnWildcard": { "ExcludedColumnNames": ["email", "phone"] }
  }
}

Column-level control in Athena and Redshift Spectrum is inclusion-only, and Glue ETL doesn't support it; Spark jobs that need fine-grained control run on engines with Lake Formation integration.

A recipient account can re-grant a shared resource only to its own principals, never to another account, organization or IAMAllowedPrincipals, and the grant needs the grant option for the consumer's data lake administrator to re-grant at all. Revoke cross-account grants before deleting a table, or orphaned RAM shares remain.

Step 5

Consumers in their own accounts

Athena. The EU unit's data lake administrator accepts the RAM share and creates resource links to the shared databases; Athena and Redshift Spectrum need them. Analysts query from a workgroup that enforces its settings, encrypts results with the unit's key and cancels any query that would scan more than a set amount. With IAM Identity Center trusted identity propagation, Lake Formation authorizes the signed-in analyst, not just a role, and CloudTrail names the user (Task 2.1).

EU business unit 555555555555: a workgroup that overrides client settings and stops any query scanning over 1 TB (AWS CLI) 
aws athena create-work-group \
  --name eu-analysts \
  --description "EU business unit analysts on the shared lakehouse" \
  --configuration '{
    "ResultConfiguration": {
      "OutputLocation": "s3://example-athena-results-555555555555/eu-analysts/",
      "EncryptionConfiguration": { "EncryptionOption": "SSE_KMS", "KmsKey": "arn:aws:kms:us-east-1:555555555555:key/KEY_ID" }
    },
    "EnforceWorkGroupConfiguration": true,
    "PublishCloudWatchMetricsEnabled": true,
    "BytesScannedCutoffPerQuery": 1000000000000
  }' \
  --tags Key=BusinessUnit,Value=eu Key=CostCenter,Value=CC-3001

Redshift data sharing. For dashboards and heavy SQL, the producer shares live tables from the analytics namespace with the EU unit's own workgroup. The consumer is charged for compute and any cross-Region transfer, the producer for storage; both sides must be encrypted, though not with the same key.

Producer, analytics workgroup in 444444444444: create the share and add tables (Redshift SQL) 
CREATE DATASHARE orders_share;
-- ADD SCHEMA grants USAGE only; ADD TABLE grants SELECT only
ALTER DATASHARE orders_share ADD SCHEMA reporting;
ALTER DATASHARE orders_share ADD TABLE reporting.order_facts;
GRANT USAGE ON DATASHARE orders_share TO ACCOUNT '555555555555';
Producer account 444444444444: authorize the consumer account, read-only (AWS CLI) 
aws redshift authorize-data-share \
  --data-share-arn arn:aws:redshift:us-east-1:444444444444:datashare:NAMESPACE_ID/orders_share \
  --consumer-identifier 555555555555 \
  --no-allow-writes

Writes through a share are opt-in (grants to the share, --allow-writes, consumer association), and re-authorizing without the flag revokes them. Stored procedures and Python or Lambda UDFs can't be shared. To make the whole namespace readable by Iceberg engines instead, the producer can register the namespace in the Glue Data Catalog: every database and table is then shared under Lake Formation control, where a datashare goes object by object.

Applications, ML and GenAI read curated tables under the same grants: the cart service through cart-lake-reader (Task 2.1), ML training jobs (MLA-C02 notes), and data assistants on the GenAI platform querying Athena as the signed-in user.

Step 6

Maintenance, retention and cost

Iceberg maintenance in S3 Tables. Compaction (table level) merges small files and applies row-level deletes, with a default target of 512 MB (configurable from 64 to 512 MB). Strategies: auto (default: sort if the table has a sort order, otherwise binpack), binpack, sort and z-order. Compaction is charged, and sort and z-order can cost more than binpack. Choose sort when queries filter on one dominant column, z-order when they filter on several.

order_events is filtered mostly by event_time: sort compaction (AWS CLI, 444444444444; needs a sort order in the table properties) 
aws s3tables put-table-maintenance-configuration \
  --table-bucket-arn arn:aws:s3tables:us-east-1:444444444444:bucket/analytics-tables \
  --type icebergCompaction \
  --namespace orders \
  --name order_events \
  --value='{"status":"enabled","settings":{"icebergCompaction":{"strategy":"sort"}}}'

Retention. Snapshot management keeps at least MinimumSnapshots (default 1) and expires snapshots older than MaximumSnapshotAge (default 120 hours). Files referenced only by expired snapshots become noncurrent and are deleted, permanently, after the NoncurrentDays of the unreferenced file removal policy. That chain matters for privacy: a row removed with DELETE is still readable through time travel until its snapshots expire and the files are removed (Task 2.4).

customers-facing tables keep two weeks of time travel, at least 10 snapshots (AWS CLI, 444444444444) 
aws s3tables put-table-maintenance-configuration \
  --table-bucket-arn arn:aws:s3tables:us-east-1:444444444444:bucket/analytics-tables \
  --namespace sales \
  --name daily_orders \
  --type icebergSnapshotManagement \
  --value '{"status":"enabled","settings":{"icebergSnapshotManagement":{"minSnapshotsToKeep":10,"maxSnapshotAgeHours":336}}}'

Snapshot management fails for the whole table if any user-defined Iceberg tag or branch exists, or if history.expire.max-snapshot-age-ms or history.expire.min-snapshots-to-keep is set as a table property; then nothing expires and storage grows silently. Engines' own retention properties don't apply in S3 Tables: use the maintenance configuration. Check get-table-maintenance-job-status for FAILED.

Storage cost (Task 3.4): table buckets default new tables to INTELLIGENT_TIERING (from December 2025), which moves table data between access tiers as it cools. S3 Tables replication (also December 2025) can copy tables to us-west-2 for DR.

Compute cost controls:

  • Athena: the per-query scan cutoff in each workgroup (Step 5), columnar files, partitions and compaction to cut bytes scanned.
  • Redshift Serverless: base capacity defaults to 128 RPUs (range 4–512); usage limits cap RPU-hours and cross-Region data sharing per workgroup. Serverless and RG don't pay Spectrum's per-TB charge; RA3 does.
  • Spark: EMR Serverless is cheaper than an EMR on EC2 cluster that would run below about 70% utilization On-Demand (50% with Savings Plans); with Spot, EMR on EC2 or EKS stays cheaper.
Analytics workgroup 444444444444: alarm at 2,000 RPU-hours a month, then switch user queries off at a hard cap (AWS CLI) 
aws redshift-serverless create-usage-limit \
  --resource-arn arn:aws:redshift-serverless:us-east-1:444444444444:workgroup/WORKGROUP_ID \
  --usage-type serverless-compute \
  --amount 2000 --period monthly --breach-action emit-metric

aws redshift-serverless create-usage-limit \
  --resource-arn arn:aws:redshift-serverless:us-east-1:444444444444:workgroup/WORKGROUP_ID \
  --usage-type serverless-compute \
  --amount 3000 --period monthly --breach-action deactivate

The amount is RPU-hours (terabytes for cross-region-datasharing). deactivate stops queries, so the hard cap sits well above the alert.

Design decisions

Central producer account, consumers on their own bill

One analytics account owns storage, catalog, keys and grants; units query from their own accounts. The cost: the analytics team becomes a bottleneck for new data products, which is when a data mesh (Alternatives) pays off.

Table buckets for churn, a general purpose bucket for the regulated table

Table buckets remove maintenance work, which matters most for tables written every minute. The regulated customers table stays on example-curated, where the existing key policy, bucket policies, lifecycle rules and replication already satisfy the auditors. The cost is two maintenance models: S3 Tables configuration for one, Glue optimizers for the other.

Lake Formation rather than IAM-only access

IAM and table bucket policies grant whole tables and namespaces. Lake Formation adds rows, columns, cells, tags and cross-account RAM shares in one place across Athena, Redshift and EMR. The price is a second permission system to learn and audit, and settings (cross-account version, IAMAllowedPrincipals, catalog key) that silently block sharing when wrong.

Alternatives

Data mesh with producer accounts

Each domain account owns its tables and keys and shares data products through the central catalog, with SageMaker Catalog (built on DataZone) for discovery and access requests. It scales ownership but multiplies accounts, keys and RAM shares.

Testing it

  1. Prove the filterAs an EU analyst, SELECT * on the customers resource link must return only region = 'EU' rows and no email or phone columns; a query naming email must fail. A role in another business unit must get AccessDenied.
  2. Break the schemaSend an event with a renamed field through the forwarder: the record must land in the Firehose error prefix, an alarm must fire, and order_events must keep its schema.
  3. Watch maintenanceRun aws s3tables get-table-maintenance-job-status for each table weekly; any FAILED snapshot job (a forgotten branch or retention property) is a finding.
  4. Rehearse a DR failoverIn staging, fail over the orders Global Database: confirm the integration goes inactive, recreate it in us-west-2 and measure reseeding time against the analytics recovery objective.
  5. Test a deletion requestDelete a test customer, then confirm time travel still shows the row until the snapshot ages out, and that it is gone after expiry and NoncurrentDays.
  6. Check the billRun a query over the scan cutoff (cancelled), push the staging workgroup past its usage limit (metric, then deactivation), and confirm Cost Explorer splits storage by the domain tag and query cost by consumer account.

"Business units in other accounts must query the central data lake with column- and row-level restrictions and the least operational overhead" is Lake Formation with LF-Tag grants through AWS RAM and data filters, with resource links in the consumer account, not bucket policies or copies. "Each consuming team must pay for its own warehouse queries on live data" is Redshift data sharing (consumer pays compute). "Load Aurora changes into the warehouse continuously without building a pipeline" is a zero-ETL integration. "Streaming Iceberg tables suffer from many small files" is S3 Tables automatic compaction (or Glue table optimizers). "The cross-account grant fails with AccessDeniedException" points to IAMAllowedPrincipals, the cross-account version or a catalog encrypted with the Glue service-managed key.
