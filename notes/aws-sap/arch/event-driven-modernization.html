Reference architecture

Monolith to event-driven microservices

The order system came to AWS as a rehosted monolith. Now it is taken apart one capability at a time behind a routing facade: new services own their data, publish events instead of sharing tables, coordinate the order flow with a saga, and the monolith shrinks until the last route moves.

Scenario and requirements

During the data-centre exit the order monolith was rehosted to EC2 behind an Application Load Balancer, and its Oracle schema was refactored to Aurora PostgreSQL (the data-centre migration architecture), following AWS's advice to migrate first and modernize after (Task 4.1). It runs in the production orders account 111111111111 in us-east-1: one release train for everything, a slow inventory query that stalls payments, and nightly extracts for the analytics account 444444444444.

The business asked for four things:

  • No big-bang rewrite: orders keep flowing, and each step can be rolled back.
  • Independent teams for orders, payments, inventory and notifications, each deploying on its own schedule.
  • Correctness: no charge for a failed order, no stock reserved twice, and each customer's order events in order.
  • Events for others: analytics and partner accounts get order events within seconds.

Reused from the SAP task pages: the central-orders bus and its organization-wide policy, the order-events.fifo queue with one message group per customer, the prod-cluster ECS cluster with the orders-api service (Task 1.1), and the organization o-a1b2c3d4e5. New on this page:

  • Facade: the shop ALB's HTTPS listener ($SHOP_LISTENER_ARN) with target groups monolith-web and orders-svc.
  • Data: Aurora PostgreSQL cluster orders-svc-db; DynamoDB tables Payments, Inventory and ProcessedMessages; an outbox table in the monolith's database.
  • Messaging: order-events-dlq.fifo, the notifications queue, central-orders-dlq, KMS alias alias/orders-events, and queue order-analytics in 444444444444 reached with role central-orders-to-analytics.
  • Workflow: state machine order-saga with Lambda functions reserve-inventory, authorize-payment, confirm-order and the compensations release-inventory and void-payment.

Status changes to know. Migration Hub Refactor Spaces, which automated the strangler facade, is closed to new customers, so the facade is built with ALB rules or API Gateway. AWS App Mesh reached end of support on 30 September 2026; ECS services use ECS Service Connect, and EKS or mixed compute use VPC Lattice. EventBridge relaunched its custom event bus in September 2026 with FIFO subscribers and deduplication; the earlier bus is now "Custom Event Bus - Classic". The X-Ray SDKs entered maintenance on 25 February 2026 (use OpenTelemetry). Lambda durable functions arrived in December 2025.

How it works

The state halfway through the programme: orders have moved to the new service, while catalogue and account pages still run in the monolith. Steps marked AWS happen automatically.

  1. A customer places an order
  2. Route at the facadeAWSThe ALB checks its listener rules: /api/orders/* goes to the orders-svc target group (ECS on Fargate); every other path falls through to the default rule and the monolith.
  3. Accept the orderOrders serviceThe service writes the order to orders-svc-db as PENDING, starts an order-saga execution named after the order ID, and returns 202.
  4. Run the sagaAWSStep Functions reserves stock, authorizes the payment and confirms the order. If a step fails, it runs the compensations in reverse order and the order ends FAILED.
  5. Publish the outcomeAWSThe confirm step puts an OrderConfirmed event on central-orders, with the order ID and a correlation ID.
  6. Everyone who cares about the order
  7. Fan out by ruleAWSOne rule sends the event to the notifications queue; another delivers it straight to order-analytics in 444444444444. Deliveries that exhaust their retries land in central-orders-dlq.
  8. Consume onceNotifications serviceA Lambda function sends the e-mail only if a conditional write to ProcessedMessages succeeds, so a redelivered event does nothing.
  9. Meanwhile, in the monolith
  10. Keep old screens in syncMonolithThe monolith's own order edits go into an outbox row in the same transaction. A relay sends them to order-events.fifo in order per customer, and the orders service applies them until the monolith stops writing orders.

Build it

Step 1

Put a facade in front of the monolith

The strangler fig. A routing layer sits in front of the monolith; each capability is rebuilt as a separate service, and its routes move one at a time until nothing is left for the monolith to serve (Task 4.1). The existing ALB becomes the facade. Rules are evaluated lowest priority first, and the default rule (forward to monolith-web) catches everything else, so doing nothing keeps the old behaviour.

Move routes gradually. The orders rule uses a weighted forward action, so a small share of /api/orders/* reaches the new service first. The weight rises while error rates and latency hold, and goes back to zero to roll back. Where the new service needs behaviour still in the monolith, an anti-corruption layer translates between the old model and the new one.

conditions.json: match the orders API paths (input for aws elbv2 create-rule --conditions) 
[
  {
    "Field": "path-pattern",
    "PathPatternConfig": { "Values": ["/api/orders/*", "/api/orders"] }
  }
]
Send 10% of order traffic to the new service, the rest still to the monolith (AWS CLI, production account 111111111111) 
aws elbv2 create-rule \
  --listener-arn "$SHOP_LISTENER_ARN" \
  --priority 10 \
  --conditions file://conditions.json \
  --actions '[{"Type":"forward","ForwardConfig":{"TargetGroups":[{"TargetGroupArn":"'"$ORDERS_SVC_TG_ARN"'","Weight":10},{"TargetGroupArn":"'"$MONOLITH_TG_ARN"'","Weight":90}]}}]'

Path patterns are case-sensitive. Later capabilities get their own rules (/api/payments/*, /api/stock/*). When the monolith's target group gets no traffic, the default rule becomes a fixed 404 response and the monolith is retired.

The facade and the anti-corruption layer are temporary; plan their removal, or they become a second monolith. Sharing the monolith's database with the new services defeats the point of decomposing. Refactor Spaces is closed to new customers, so it isn't the answer for new designs.

Step 2

Carve out services with their own data

Where to cut. Domain-driven design and event storming found four business capabilities that change for different reasons. Orders moved first, because it changes most often and must scale separately at peak (Task 4.1).

Database per service. Each service owns its store and nobody else reads it; other services use its API or its events:

  • Orders: Aurora PostgreSQL (orders-svc-db), for relations, reporting queries and a schema the team knows.
  • Payments: DynamoDB (Payments), keyed by order ID, where a conditional write makes "authorize once" safe.
  • Inventory: DynamoDB (Inventory), keyed by product, with conditional updates so stock never goes below zero.
  • Notifications: no business data, only ProcessedMessages for deduplication.

Separate stores lose the monolith's ACID transactions, and a two-phase commit across them isn't an option, so Step 5 replaces the transaction with a saga and accepts eventual consistency.

Compute per service. The orders API, with steady traffic and connection pools to Aurora, runs on ECS on Fargate, the default for containers without a Kubernetes requirement. Payments, inventory and notifications are short, event-triggered steps on Lambda, which scales to zero (Task 1.1).

Service-to-service calls. Calls back to the monolith go through the anti-corruption layer with timeouts and a circuit breaker. Between ECS services, ECS Service Connect gives short names from a Cloud Map namespace and a managed proxy in each task with retries, outlier detection, optional TLS through AWS Private CA, and per-service metrics, at no charge beyond the proxy's CPU and memory. Clients outside ECS can't resolve its names; for EKS, many VPCs and accounts, or IAM authorization between services, VPC Lattice is the fit.

App Mesh is past end of support: an answer that adds it to a new design is wrong. An ECS service can't be in an App Mesh mesh and a Service Connect namespace at once, so migrating services are recreated, not converted in place.

Step 3

Publish the monolith's changes with a transactional outbox

The dual-write problem. While the monolith still edits orders, the new service must hear about every change. Writing the database and then sending a message loses the event on a crash; sending first can announce a change that rolls back. The transactional outbox closes the gap: the monolith writes the order change and an outbox row (with a timestamp and a sequence number) in the same transaction, so a rollback removes both.

The relay reads committed outbox rows in order, sends them to order-events.fifo, and deletes them once SQS accepts them. As in AWS's sample code, the message group ID is the aggregate (here the customer) and the deduplication ID is the outbox row ID, so a relay retry within five minutes is dropped. A crash between sending and deleting can still resend a row later, so consumers stay idempotent (Step 6).

attributes.json: FIFO queue with high-throughput mode, KMS encryption and a FIFO dead-letter queue after 5 receives (input for aws sqs create-queue --queue-name order-events.fifo --attributes file://attributes.json) 
{
  "FifoQueue": "true",
  "ContentBasedDeduplication": "true",
  "DeduplicationScope": "messageGroup",
  "FifoThroughputLimit": "perMessageGroupId",
  "VisibilityTimeout": "180",
  "KmsMasterKeyId": "alias/orders-events",
  "RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:us-east-1:111111111111:order-events-dlq.fifo\",\"maxReceiveCount\":\"5\"}"
}

A FIFO queue's DLQ must be FIFO; the two throughput settings turn on high-throughput mode; the visibility timeout is six times the consumer's 30-second timeout, as AWS advises for Lambda. Lambda concurrency on FIFO is capped at the number of message groups, so the group is the customer, not a constant.

Change data capture instead? Services that own a DynamoDB table need no outbox table: DynamoDB Streams capture each item change in order, and a function or EventBridge Pipes (charged only for events that pass its filter) forwards it. DMS ongoing replication appears in the SAP sources as a migration tool that keeps a target database in sync until cutover, not as a way to publish business events.

"Write to the database, then call SNS or EventBridge" in one request handler is the dual-write bug, not a design. A FIFO queue with one message group for all messages processes one message at a time, and a constant deduplication ID drops everything after the first.

Step 4

The event backbone: EventBridge, SQS and SNS

Which bus. Business events (OrderPlaced, OrderConfirmed, PaymentFailed) go to the central-orders custom bus, which already lets every account in o-a1b2c3d4e5 put events (Task 1.1). It stays a Classic bus on purpose: schema discovery and global endpoints both reject the new Custom Event Bus, and ordered streams already use the FIFO queue from Step 3. Classic delivery is at least once and unordered, with retries for up to 24 hours (185 attempts) by default.

Rules and targets. A rule matches events by content and sends them to up to five targets, each with its own retry policy and dead-letter queue, so one failing consumer doesn't affect the others.

Match confirmed orders from the orders account on the central bus (AWS CLI, production account 111111111111) 
aws events put-rule \
  --name order-confirmed-to-notifications \
  --event-bus-name central-orders \
  --event-pattern '{"source":["com.example.orders"],"detail-type":["OrderConfirmed"],"account":["111111111111"]}' \
  --state ENABLED
targets.json: the notifications queue, retried for up to 2 hours and 20 attempts, then sent to the dead-letter queue (input for aws events put-targets --rule order-confirmed-to-notifications --event-bus-name central-orders --targets file://targets.json) 
[
  {
    "Id": "notifications-queue",
    "Arn": "arn:aws:sqs:us-east-1:111111111111:notifications",
    "RetryPolicy": { "MaximumRetryAttempts": 20, "MaximumEventAgeInSeconds": 7200 },
    "DeadLetterConfig": { "Arn": "arn:aws:sqs:us-east-1:111111111111:central-orders-dlq" }
  }
]

Matching on account matters on a bus the whole organization can write to: without it, any account could publish an OrderConfirmed and trigger e-mails. Both queues use a customer managed key whose policy lets events.amazonaws.com use kms:Decrypt and kms:GenerateDataKey, because EventBridge can't deliver to a queue encrypted with an AWS owned key, as a target or as a DLQ.

Other accounts. A second rule delivers the same events to order-analytics in 444444444444 as a direct cross-account target: an execution role (central-orders-to-analytics) in the sending account and a queue policy in the analytics account that allows it, with no receiving bus. The sender pays, at the custom event rate. Forwarded events don't chain a second time, so the design is hub and spoke: one rule per consumer on the central bus.

Schemas. Schema discovery on central-orders adds every event shape, including cross-account events, to the discovered-schemas registry as versioned OpenAPI 3 or JSONSchema Draft4 schemas, with downloadable code bindings. The first five million processed events a month are free, and discovery doesn't work on a bus encrypted with a customer managed key. It documents contracts without enforcing them, so producers only add fields.

Archive and replay. An archive keeps the bus's events for a set number of days. After a bug fix, a replay sends them back to the same bus (all rules or chosen ones), without their original order and with a replay-name field, so consumers must not assume order.

Step 5

The order saga: orchestration with compensations

Why a saga. A saga runs a local transaction in each one and, if a later step fails, runs compensating actions that undo the earlier ones: release the stock, void the payment authorization. It is eventually consistent and lacks isolation, so the last item in stock is protected by a semantic lock (a RESERVED status other orders respect).

Orchestration or choreography. In choreography each service reacts to events and nobody owns the flow, which suits listeners. The money path needs one place showing every order's state, so an orchestrator runs it. Step Functions runs across Availability Zones, so the orchestrator isn't the single point of failure a home-grown coordinator would be.

Standard, not Express. The saga is a Standard workflow: exactly-once state transitions, up to a year per execution, 90 days of history for audits, waits for a task token (the card processor's callback) and redrive from the failed state. Express workflows (up to 5 minutes, at-least-once when asynchronous, no task-token waits) are cheaper for high-volume, short work such as rendering notification templates.

order-saga.asl.json (excerpt): reserve stock, authorize payment, confirm; on failure, compensate in reverse order (Amazon States Language, JSONPath) 
{
  "Comment": "Order saga with compensations",
  "StartAt": "ReserveInventory",
  "States": {
    "ReserveInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:111111111111:function:reserve-inventory",
      "Retry": [ {
        "ErrorEquals": ["Lambda.ServiceException", "Lambda.SdkClientException", "Lambda.TooManyRequestsException"],
        "IntervalSeconds": 1, "MaxAttempts": 3, "BackoffRate": 2.0, "JitterStrategy": "FULL"
      } ],
      "Catch": [ { "ErrorEquals": ["States.ALL"], "ResultPath": "$.error", "Next": "OrderFailed" } ],
      "ResultPath": "$.reservation",
      "Next": "AuthorizePayment"
    },
    "AuthorizePayment": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:111111111111:function:authorize-payment",
      "Catch": [ { "ErrorEquals": ["States.ALL"], "ResultPath": "$.error", "Next": "ReleaseInventory" } ],
      "ResultPath": "$.payment",
      "Next": "ConfirmOrder"
    },
    "ConfirmOrder": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:111111111111:function:confirm-order",
      "Catch": [ { "ErrorEquals": ["States.ALL"], "ResultPath": "$.error", "Next": "VoidPayment" } ],
      "End": true
    },
    "VoidPayment": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:111111111111:function:void-payment",
      "Retry": [ { "ErrorEquals": ["States.ALL"], "IntervalSeconds": 2, "MaxAttempts": 5, "BackoffRate": 2.0 } ],
      "ResultPath": "$.voided",
      "Next": "ReleaseInventory"
    },
    "ReleaseInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:111111111111:function:release-inventory",
      "Retry": [ { "ErrorEquals": ["States.ALL"], "IntervalSeconds": 2, "MaxAttempts": 5, "BackoffRate": 2.0 } ],
      "ResultPath": "$.released",
      "Next": "OrderFailed"
    },
    "OrderFailed": { "Type": "Fail", "Error": "OrderFailed", "Cause": "A saga step failed; completed steps were compensated" }
  }
}

How it reads: each forward step catches every error and jumps to the compensations for the steps already done, in reverse order. "ResultPath": "$.error" adds the error to the state's input instead of replacing it, so the compensations still have the order ID and reservation. Compensations retry hard; if one still fails, an alarm fires and an operator redrives the execution. Every step must be idempotent, because retries and redrives run it again.

Executions are named after the order ID, and the orders service checks the order's status before starting one, so a retried API call can't start a second saga.

Lambda durable functions (December 2025) are the code-first alternative: checkpointed steps and waits of up to a year inside one function. AWS suggests them for Lambda-centred logic owned by developers, and Step Functions for orchestrating many AWS services with a visual workflow. The money path spans several teams' services, so it stays on Step Functions (Task 1.1).

Step 6

Idempotent consumers

Every hop on this page can deliver twice, so each consumer makes a second delivery harmless. The notifications function records each event ID with a conditional write before it acts and skips the event if the record already exists. A TTL attribute removes the records after about a week.

Notifications consumer: act on each event once, keyed by the event's ID (Python, boto3) 
import time

import boto3

dynamodb = boto3.client("dynamodb")


def first_time(message_id: str) -> bool:
    try:
        dynamodb.put_item(
            TableName="ProcessedMessages",
            Item={
                "messageId": {"S": message_id},
                "expiresAt": {"N": str(int(time.time()) + 7 * 86400)},
            },
            # Succeeds only for the first delivery of this ID
            ConditionExpression="attribute_not_exists(messageId)",
        )
        return True
    except dynamodb.exceptions.ConditionalCheckFailedException:
        # Already handled: a retry, a redelivery or a replay
        return False

The key must be stable across retries: a business ID (order ID plus event type), never a timestamp or a fresh UUID. For payments, the provider receives the order ID as its idempotency key, and Payments records the outcome with a condition on the order's status. Powertools for AWS Lambda packages the same pattern (@idempotent with a DynamoDB persistence layer).

An atomic counter (SET n = n + :one) is not idempotent; a conditional write that checks the attribute it updates is. Conditional writes protect nothing across DynamoDB global tables, which resolve conflicts with "last writer wins".

Step 7

Observe and deploy

Following one order. Every service is instrumented with OpenTelemetry (ADOT SDKs or auto-instrumentation), and Application Signals builds the service map with Latency, Fault and Error metrics per operation. Asynchronous hops break traces easily, so every event carries the order ID and a correlationId in its detail, and every log line includes them with the trace ID (Task 5.3).

Turn on OpenTelemetry auto-instrumentation for a saga function (AWS CLI) 
aws lambda update-function-configuration \
  --function-name authorize-payment \
  --layers "$ADOT_LAMBDA_LAYER_ARN" \
  --environment "Variables={AWS_LAMBDA_EXEC_WRAPPER=/opt/otel-instrument}"

The execution role also needs CloudWatchLambdaApplicationSignalsExecutionRolePolicy. An SLO with burn-rate alarms covers "place order"; other alarms watch for messages in any DLQ, the age of the oldest message in order-events.fifo, EventBridge failed invocations and failed saga executions.

Independent pipelines. Each service has its own repository and pipeline, deploying through dev and staging accounts into production (the DOP multi-account pipeline architecture). Lambda services shift traffic with alarm-guarded canaries on aliases and the orders API uses ECS blue/green (the DOP serverless deployments page and Task 5.2). Because services deploy separately, event contracts and database schemas change backward-compatibly, in expand-then-contract steps.

Design decisions

Strangle, don't rewrite

A full rewrite freezes features and cuts over in one risky weekend. The strangler fig delivers value per capability, and each step can be reversed with one rule weight; the cost is running two systems, the facade and the sync for the whole programme. Small applications are cheaper to rewrite than to strangle.

Orchestrate the money path, choreograph the rest

Payments and stock need an owner, compensations and an audit trail; notifications, analytics and partner feeds only react, so they subscribe without touching the orders service. Standard costs $0.025 per 1,000 state transitions (retries count as transitions), a few cents per thousand orders; Express costs $1.00 per million requests plus duration, which is why high-volume short work runs there.

Lambda for spiky steps, Fargate for the steady API

Lambda bills nothing while idle, which suits per-order steps. The orders API runs all day, where Fargate is usually cheaper than per-request billing. Compute Savings Plans cover both, and Arm (Graviton) is 20% cheaper than x86 for each (Task 3.1).

The price of a database per service

Several stores cost more than one. The small services use DynamoDB on demand, which costs little between orders, and only orders keeps an Aurora cluster; Database Savings Plans can cover the steady part. Cross-account events are charged to the sender, and Service Connect adds only proxy resources.

FIFO only where order matters

Only the monolith-to-service sync needs per-customer order, so only that path uses SQS FIFO, with one group per customer for parallelism. Everything else uses unordered, at-least-once delivery with idempotent consumers, which scales further and costs less.

Alternatives

API Gateway as the facade

A REST API gives the same route-by-route strangling, adds per-client API keys, usage plans, request validation and AWS WAF, and can send a route straight to Lambda or Step Functions. It's serverless and Multi-AZ, so it isn't a new single point of failure. The ALB was already there and shifts weights between two backends natively.

The new Custom Event Bus

FIFO subscribers per event group, five-minute deduplication ("exactly-once ingestion" with a FIFO subscriber), retention up to 365 days with replay by starting position, and RAM sharing could replace the FIFO queue for ordered order events. It lacks schema discovery and global endpoints today, and RAM sharing works only within a Region, but AWS recommends it for new applications, so it is the likely next step.

Testing it

  1. Canary the routesCompare the new service's responses with the monolith's in staging, then hold 10% in production for a week; the 5XX rate and p99 latency of both target groups must match before the weight rises.
  2. Force every saga branchIn staging, make authorize-payment and then confirm-order fail on purpose. Execution histories must show the compensations in reverse order, and Inventory and Payments must end where they started.
  3. Send everything twiceReplay a day of archived events into staging and resend outbox rows: no second e-mail, no double charge, and ConditionalCheckFailedException counts show the duplicates were caught.
  4. Break a consumerRemove the queue policy on notifications in staging: events must land in central-orders-dlq (within the 2-hour retry limit at the latest) and fire the DLQ alarm. Restore it, then redrive.
  5. Peak load and costLoad-test at twice last year's peak, watching FIFO message age, Lambda throttles and Aurora connections; then compare the cost per thousand orders, by service tag, with the monolith baseline in Cost Explorer.

"Modernize a monolith gradually with minimal risk" is the strangler fig behind ALB path rules or API Gateway. "Keep data consistent across microservices without distributed transactions" is a saga on Step Functions Standard with compensating steps. "Publish an event reliably when the database changes" is the transactional outbox or DynamoDB Streams, never two writes in a row. "Each customer's events in order" is SQS FIFO with a message group per customer. "Duplicates must not cause double charges" is an idempotent consumer with a DynamoDB conditional write. "Route events to other accounts with the least code" is an EventBridge rule with a cross-account target. "Traffic between ECS services" is ECS Service Connect, not App Mesh.
