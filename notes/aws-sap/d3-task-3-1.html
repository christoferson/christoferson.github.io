Overview

Task 3.1

Design architectures based on AWS pricing models.

Professional cost questions combine options: a baseline covered by Savings Plans, peaks on On-Demand, batch on Spot, a reservation only for the capacity you can't lose. The rates, billing rules and discount percentages are in the SAA cost-optimized compute notes; this page is about matching them to usage patterns across an organization.

Running example. The web tier and order APIs run steadily on EC2 and ECS around the clock, with daily peaks; nightly reporting and image processing can be interrupted; dev and test only run in office hours; a quarterly model fine-tune needs GPUs on a known date; and the GenAI assistant's usage is growing fast, with an overnight job that summarizes the day's support tickets.

Status changes to know. AWS App Runner is closed to new customers (use ECS Express Mode). Lambda functions are now Lambda Event Functions, alongside new Lambda Web Functions billed for active CPU (October 2026). The legacy RequestSpotFleet and RequestSpotInstances APIs get no further investment (use Auto Scaling groups or EC2 Fleet). Developer and Business Support end on 1 January 2027 (Business Support+ replaces them). New: Database Savings Plans (December 2025), Lambda Managed Instances and ECS Managed Instances (2025), interruptible capacity reservations (November 2025), Graviton5 instances (2026), and Bedrock service tiers (Priority, Standard, Flex and Reserved, November 2025).

Purchase options

Skill 3.1.1Select appropriate purchase options based on usage patterns, including commitment-based and capacity-based options (for example, provisioned capacity, Reserved Instances, AWS Savings Plans, Spot Instances, On-Demand Instances).

  • Steady baseline: Savings Plans.
    • Compute Savings Plans (up to 66% off) follow the workload across instance families, Regions, Fargate and Lambda.
    • EC2 Instance Savings Plans (up to 72%) lock to one family in one Region.
    • Database Savings Plans (up to 35%, 1-year No Upfront only) cover Aurora, RDS, DynamoDB, ElastiCache and others.
    • SageMaker AI Savings Plans (up to 64%).
    AWS recommends Savings Plans over Reserved Instances for EC2. Commit to the lowest steady hourly spend, buy small amounts often, and buy in an account with no usage (such as the management account) so the discount is shared across the organization.
  • Reserved Instances still matter for RDS, ElastiCache, OpenSearch and Redshift (reserved nodes), and zonal EC2 RIs reserve capacity in one AZ. Only Standard RIs can be sold on the Marketplace; Convertible RIs can be exchanged.
  • Interruptible work: Spot (up to 90% off, 2-minute notice). Stay flexible across many instance types and all AZs, use the price-capacity-optimized strategy, set no maximum price, and checkpoint work. Savings Plans never apply to Spot.
  • Peaks and short-lived work: On-Demand, billed per second for Linux and Windows.
  • Capacity, not discounts:
    • On-Demand Capacity Reservations guarantee instances in an AZ at the On-Demand rate whether used or not. Savings Plans and Regional RIs discount them; future-dated ones suit planned events.
    • Capacity Blocks for ML reserve GPU or Trainium capacity for a set period, up to 8 weeks ahead, paid upfront.
    • Provisioned capacity in other services (DynamoDB provisioned with reserved capacity, Bedrock Provisioned Throughput, Kinesis shards) is cheaper only when utilization is high and steady.
  • Licensing: Dedicated Hosts allow full bring-your-own-license by socket or core; Dedicated Instances add a per-Region fee and allow only partial BYOL.

A capacity reservation has no discount of its own, and zonal RI discounts don't apply to it. Regional RIs don't reserve capacity. Savings Plans can't be cancelled (small, recent ones can be returned within 7 days in the same month). Turning off RI and Savings Plans discount sharing in the management account can raise the bill of every other account.

Cost-optimized compute choices

Skill 3.1.2Design cost-optimized architectures to meet workload requirements (for example, by using Graviton-based instances, AWS Step Functions Standard Workflows or Express Workflows, AWS Lambda functions).

  • Graviton: instances cost up to 20% less than comparable x86 instances, and Lambda and Fargate on Arm cost 20% less than on x86. Most managed services (RDS, Aurora, ElastiCache, OpenSearch) also offer Graviton. Check that every dependency has an Arm build, and compare actual prices: Spot prices vary by pool, and not every newer x86 or AMD family is cheaper.
  • Lambda vs containers vs instances:
    • Lambda scales to zero and suits bursty or event-driven traffic; you pay per request and per GB-second.
    • Sustained, high-volume traffic is usually cheaper on Fargate, ECS on EC2 with Savings Plans, or Lambda Managed Instances. Managed Instances run on EC2 in your VPC with a 15% management fee and don't scale to zero.
    • Lambda Web Functions bill only active CPU, which helps request handlers that mostly wait on downstream calls.
  • Step Functions Standard or Express: Standard is billed per state transition and runs up to a year with exactly-once steps, history and human approvals; Express is billed by executions and duration, runs up to 5 minutes, and is far cheaper for high-volume, short workflows such as event processing or API orchestration. A Standard parent with Express child workflows (for example in a Distributed Map) combines both.
  • Remove idle cost: serverless databases and caches for spiky use, S3 storage classes and lifecycle rules, schedules that stop dev and test outside office hours (Instance Scheduler on AWS claims up to 70% savings for business-hours-only instances), and no idle NAT gateways, load balancers or public IPv4 addresses.
  • Managed fees to watch: the EKS cluster fee rises from $0.10 to $0.60 per hour on extended support, and EKS Auto Mode and ECS Managed Instances add a per-instance management fee on top of EC2.

"Millions of short workflow executions a day" points to Express Workflows. "Long-running order process with approvals" points to Standard. "Steady API traffic, Lambda bill keeps growing" points to containers with Savings Plans or Lambda Managed Instances. "Cut cost with no code change for an interpreted runtime" often points to Graviton (Arm) for Lambda, Fargate or RDS.

Rightsizing and scaling

Skill 3.1.3Implement rightsizing and scaling strategies based on performance metrics (for example, by using AWS Compute Optimizer, scheduled scaling, target tracking policies, AWS Fargate Spot).

  • Compute Optimizer (opt-in, free, organization-wide from the management account or a delegated administrator) recommends sizes for EC2, Auto Scaling groups, EBS, Lambda, ECS on Fargate, RDS and Aurora, DynamoDB, ElastiCache and others, and flags idle resources. Enhanced infrastructure metrics (paid) extend the lookback to 93 days; install the CloudWatch agent so memory is included. Cost Optimization Hub gathers these and Savings Plans recommendations in one place.
  • Rightsize before you commit: buying Savings Plans for oversized instances locks in waste. Rightsize, then commit to the new baseline.
  • Match capacity to demand:
    • Target tracking keeps a metric near a target, for example CPU at 50% or requests per target.
    • Step scaling reacts to alarm thresholds.
    • Scheduled scaling sets capacity for known patterns, such as office hours or month end.
    • Predictive scaling forecasts daily and weekly cycles.
    Scale down as carefully as up, and use warm pools if launch time limits how far you can scale in.
  • Fargate Spot runs interruptible ECS tasks for up to 70% off with a 2-minute warning. Mix it with regular Fargate in a capacity provider strategy so a base always runs on regular capacity; it isn't available for EKS.
  • Databases and storage: Aurora Serverless v2 and DynamoDB on-demand for variable load, gp3 instead of gp2, and lifecycle rules to cheaper storage classes.
ECS service: two tasks always on Fargate, extra tasks three-to-one on Fargate Spot 
aws ecs create-service \
  --cluster reporting \
  --service-name image-workers \
  --task-definition image-worker:7 \
  --desired-count 8 \
  --capacity-provider-strategy \
      capacityProvider=FARGATE,base=2,weight=1 \
      capacityProvider=FARGATE_SPOT,weight=3 \
  --network-configuration "awsvpcConfiguration={subnets=[subnet-0a1b2c3d4e5f60001],securityGroups=[sg-0a1b2c3d4e5f60001]}"
Dev environment Auto Scaling group: scale to zero at night, back to two at 08:00 on weekdays 
aws autoscaling put-scheduled-update-group-action \
  --auto-scaling-group-name dev-web \
  --scheduled-action-name nightly-off \
  --recurrence "0 19 * * 1-5" --time-zone "America/New_York" \
  --min-size 0 --max-size 0 --desired-capacity 0

aws autoscaling put-scheduled-update-group-action \
  --auto-scaling-group-name dev-web \
  --scheduled-action-name morning-on \
  --recurrence "0 8 * * 1-5" --time-zone "America/New_York" \
  --min-size 2 --max-size 4 --desired-capacity 2

Compute Optimizer must be opted in, and without memory metrics it can't see memory-bound instances. Instance Scheduler can't stop instances that belong to an Auto Scaling group (use the group's own schedules). Fargate Spot is ECS only.

AI and ML costs

Skill 3.1.4Optimize costs for AI/ML workloads by selecting the appropriate service tier, implementing batching strategies, and designing caching patterns (for example, by using Amazon Bedrock, Amazon SageMaker AI).

  • Pick the smallest model that meets quality: model evaluation to compare, intelligent prompt routing between two models of a family (AWS cites up to 30% savings), and model distillation to train a smaller model on a larger one's answers.
  • Bedrock service tiers per request (supported models only):
    • Priority (75% premium) for latency-critical user traffic.
    • Standard (the default).
    • Flex (50% off, lower priority under load) for evaluations, summarization and agent work that can wait.
    • Reserved (account-level token-per-minute capacity) for steady critical traffic.
    The bedrock:ServiceTier condition key can stop teams using Priority.
  • Batching: Bedrock batch inference processes JSONL files from S3 at 50% of the on-demand price for supported models, best effort with no completion guarantee and no prompt caching. SageMaker batch transform and asynchronous inference (queues requests and can scale to zero) suit large offline jobs.
  • Caching:
    • Prompt caching charges reduced rates for a repeated prefix (system prompt, tools, documents). Put the stable content first and add a cache point after it; entries expire after 5 minutes (1 hour on some models) unless reused. Cache writes can cost more than normal input.
    • A semantic cache (ElastiCache for Valkey vector search) returns stored answers to similar questions without calling the model at all.
    • Plain response caching suits identical requests.
  • SageMaker AI hosting:
    • Serverless inference for intermittent traffic.
    • Inference components pack several models on one endpoint and can scale each to zero.
    • Multi-model endpoints for many small models.
    • Graviton or Inferentia instances where models support them.
  • SageMaker AI training: managed Spot training with checkpoints to S3, and SageMaker AI Savings Plans for steady use.
  • Provisioned capacity only when needed: Bedrock Provisioned Throughput is billed per model unit per hour whether used or not, and is required for most custom models unless on-demand custom model deployment is supported.
  • Attribute and cap spend: application inference profiles, IAM principal cost attribution and request metadata show which team or feature spends what; Budgets and quotas stop runaway use.
Overnight ticket summaries: Flex tier, with the long system prompt cached (boto3 Converse) 
import boto3

brt = boto3.client("bedrock-runtime", region_name="us-east-1")

response = brt.converse(
    modelId="arn:aws:bedrock:us-east-1:222222222222:application-inference-profile/ticket-summaries",
    system=[
        {"text": LONG_SUMMARY_INSTRUCTIONS},
        {"cachePoint": {"type": "default"}},   # cache everything above
    ],
    messages=[{"role": "user", "content": [{"text": ticket_text}]}],
    serviceTier={"type": "flex"},               # 50% off; waits under load
)

usage = response["usage"]
# inputTokens counts only uncached input; add the cache read and write counts
total_in = (usage["inputTokens"]
            + usage.get("cacheReadInputTokens", 0)
            + usage.get("cacheWriteInputTokens", 0))

Not every model supports every tier, and a request may be served on a different tier than asked (the response says which). Batch inference has no prompt caching, no completion guarantee and no tool definitions in Converse-format records. Prompt cache entries live where the request was processed, so cross-Region inference can lower the hit rate. SageMaker inference components can scale to zero, but scaling back up from zero isn't instant, so it suits workloads that can wait.

Key takeaways

  • Purchase options: Savings Plans for the steady baseline (Compute, EC2 Instance, Database, SageMaker AI), RIs where Savings Plans don't reach, Spot for interruptible work, On-Demand for peaks, reservations and Capacity Blocks only for capacity.
  • Compute choices: Graviton for about 20% off, Lambda for bursty work and containers or Managed Instances for steady load, Step Functions Express for high-volume short workflows and Standard for long ones.
  • Rightsizing and scaling: Compute Optimizer with memory metrics, rightsize before committing, target tracking plus scheduled and predictive scaling, Fargate Spot behind a regular Fargate base.
  • AI and ML: smallest adequate model, Flex tier and batch at 50% off for deferrable work, Priority only where latency pays, prompt and semantic caching, SageMaker serverless, scale-to-zero and Spot training, cost attribution per team.
