Task 2.1: Design identity security architectures

Who and what can reach the company's accounts and data: employees federated from the corporate identity provider, customers and partner systems signing in to the apps, workloads in containers, on premises and in other clouds, and the organization-wide guardrails that keep data inside trusted identities, resources and networks.

Overview

Task 2.1

Design identity security architectures.

Professional questions on identity are about choosing the mechanism, not writing the policy: Identity Center or direct IAM federation, a user pool or an identity pool, Pod Identity or IRSA, an SCP or an RCP, Roles Anywhere or OIDC. The mechanics (policy evaluation, error messages, MFA, Cognito tokens) are in the SCS authentication notes and SCS authorization notes, and the basics in the SAA secure access notes.

Running example. Employees sign in through the corporate identity provider to IAM Identity Center, which reaches dozens of accounts. Customers use the web app and mobile API; a logistics partner's systems call the orders API. The cart service runs on EKS in 111111111111 and reads lake data in the analytics account (444444444444). Batch servers still run in the on-premises data centre, and an external auditing vendor needs read-only access to the security account.

Status changes to know. The original Identity Center AD Sync was deprecated on 17 April 2025 (use configurable AD sync), and "identity-aware sessions" are now identity-enhanced console sessions. Cognito moved to feature plans (Lite, Essentials, Plus) with managed login in November 2024, and Amazon Cognito Sync closed to new customers in July 2026. Since 6 June 2025, trust policies for shared OIDC providers such as GitHub Actions are rejected unless they check the required claim (for example sub). New: resource control policies (November 2024, many more services from January 2026), the aws:VpceOrgID keys (August 2025), Pod Identity target roles for cross-account access (June 2025), Verified Access for TCP applications (February 2025), outbound identity federation (November 2025), Identity Center multi-Region (February 2026), Cognito user pool multi-Region replication (2026), the IAM account access manager (announced November 2026) and Roles Anywhere automatic revocation checking (November 2026).

Workforce federation

Skill 2.1.1Implement identity federation by using standard protocols (for example, AWS IAM Identity Center, SAML 2.0, OpenID Connect, System for Cross-domain Identity Management [SCIM]).

  • Identity Center for people: AWS recommends it for human access across an organization. The corporate IdP signs users in with SAML 2.0, and SCIM keeps users and groups in sync (the SCIM token lasts one year, then sync silently stops). Use the organization instance with a delegated administrator; account instances are for single-account apps.
  • Direct IAM federation (an IAM SAML or OIDC provider in each account): AWS limits it to short-term, small-scale human access and to machine identities such as CI pipelines. It's also the choice when the IdP must send encrypted SAML assertions, which Identity Center and Cognito identity pools don't accept.
  • Permission sets or IAM roles: permission sets give uniform access as roles that Identity Center provisions and protects. The new account access manager assigns existing IAM roles in member accounts to Identity Center users and groups instead, for per-account roles, role tags and trust conditions on IdP claims.
  • ABAC from the IdP: attributes for access control (department, cost centre) become session tags you match with aws:PrincipalTag. They come from the Identity Center directory or from https://aws.amazon.com/SAML/Attributes/AccessControl: attributes in the assertion; if both send a key, the directory value wins.
  • Trusted identity propagation: passes the signed-in user, not just a role, to Redshift, Athena, EMR, Q Business, Quick (formerly QuickSight) and others, so Lake Formation or S3 Access Grants authorize the real user and CloudTrail logs them. It works only with OAuth 2.0 applications. An app holding a token from the corporate IdP registers that IdP as a trusted token issuer (up to 10 per instance) and swaps the token with CreateTokenWithIAM; the users must already exist in Identity Center.
  • Scale and resilience: up to 3,500 permission sets and 7,000 accounts per instance, and since 2026 replication to other Regions (it needs an organization instance, a multi-Region KMS key and an IdP that accepts several sign-in URLs; it isn't available with an AD identity source).
Permission set inline policy: read only the S3 prefixes for the user's department (the department session tag comes from attributes for access control) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOwnDepartment",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-reports/${aws:PrincipalTag/department}/*"
    },
    {
      "Sid": "ListOwnDepartment",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::example-reports",
      "Condition": {
        "StringLike": { "s3:prefix": "${aws:PrincipalTag/department}/*" }
      }
    }
  ]
}

Identity Center MFA settings don't apply to users from an external IdP; the IdP owns MFA. Disabling a user doesn't end their existing role sessions. A customer managed policy in a permission set must already exist with the same name and path in every target account. Trusted identity propagation doesn't support SAML apps, and tokens from a trusted token issuer never go to AWS services directly.

Application authentication

Skill 2.1.2Design application authentication and authorization solutions (for example, by using Amazon Cognito user pools, identity pools, OAuth 2.0, Amazon EKS Pod Identity).

  • User pools authenticate; identity pools hand out AWS credentials. A user pool is the app's directory and OAuth 2.0 / OIDC server (sign-up, MFA, passkeys, federation to SAML and OIDC IdPs, tokens for API Gateway or an ALB). An identity pool swaps a token from a user pool or other IdP for temporary credentials to call AWS directly, for example uploading from the mobile app to S3.
  • Identity pool roles: use the enhanced flow, where the pool picks the role from the default, from rules on token claims, or from the token's cognito:preferred_role. The basic flow lets the client choose any role that trusts the pool and fails when role mappings exist. For ABAC, map claims to principal tags (the trust policy then needs sts:TagSession), and map only attributes users can't change.
  • Machine-to-machine: define a resource server with custom scopes and give the partner a confidential app client. It gets an access token holding only those scopes, through the client credentials grant at /oauth2/token (needs a user pool domain) or the newer GetClientToken API (no domain). M2M is billed per app client and per token request.
  • Multi-tenant SaaS: a user pool per tenant gives the strongest isolation and per-tenant settings at the cost of automation; an app client per tenant is lighter, but the managed-login session cookie lets a local user move between app clients in the same pool. Groups, a custom attribute or custom scopes per tenant are the other documented patterns, and all tenants share the pool's quotas.
  • Customizing tokens: the pre token generation trigger adds or suppresses claims and scopes; access-token and M2M customization need the Essentials or Plus plan.
  • EKS Pod Identity is AWS's recommended way to give pods AWS credentials. A role trusts pods.eks.amazonaws.com (actions sts:AssumeRole and sts:TagSession), so the same role works in any cluster without per-cluster OIDC providers, and an association maps a service account to it. EKS adds transitive session tags (cluster, namespace, service account, pod) for ABAC. A target role in another account gives cross-account access with automatic role chaining.
  • IRSA is still the answer where Pod Identity isn't supported: Fargate, Windows nodes, Outposts, EKS Anywhere and self-managed Kubernetes.
Partner M2M client and token (Cognito, no user pool domain needed) 
# Confidential client limited to the orders scope
aws cognito-idp create-user-pool-client \
  --user-pool-id us-east-1_EXAMPLE \
  --client-name logistics-partner \
  --generate-secret \
  --explicit-auth-flows ALLOW_CLIENT_TOKEN_AUTH \
  --allowed-o-auth-scopes "orders-api/orders.read"

# Partner side: returns AccessToken, ExpiresIn 3600, TokenType Bearer
aws cognito-idp get-client-token \
  --client-id 1example23456789 \
  --secret exampleClientSecret123EXAMPLE \
  --scopes "orders-api/orders.read"
Cart pods in 111111111111 read lake data in 444444444444 (Pod Identity target role) 
aws eks create-pod-identity-association \
  --cluster-name prod-cart \
  --namespace cart \
  --service-account cart-api \
  --role-arn arn:aws:iam::111111111111:role/cart-pod-identity \
  --target-role-arn arn:aws:iam::444444444444:role/cart-lake-reader
# Target role trust: the cluster account, sts:AssumeRole and sts:TagSession,
# with aws:PrincipalArn = cart-pod-identity and the namespace session tag

Only map tenant or role claims that the user can't edit: an attribute left in an app client's writable attributes (all of them when the list is unset) lets a user change their own tags. M2M access tokens carry only custom scopes and there's no ID or refresh token. With a Pod Identity target role, credentials are cached for 59 minutes and association changes need a pod restart; a session policy on an association needs session tags turned off.

Least privilege across accounts

Skill 2.1.3Design least-privilege access controls such as cross-account access and temporary credentials (for example, by using IAM roles, IAM policies, permissions boundaries, external IDs, session policies, attribute-based access control [ABAC]).

  • Roles, not keys: cross-account access is a role in the resource account whose trust policy names the other account or role, or a resource-based policy (S3, KMS, SQS, Secrets Manager) where the service supports one. Resource policies keep the caller's own permissions (no role switch), which matters when a job reads from one account and writes to another.
  • External ID for third parties: when a vendor assumes a role in your account, require the external ID the vendor gives you, to stop the confused deputy problem (another vendor customer pointing the vendor at your role). It isn't a secret and isn't needed between your own accounts.
  • Permissions boundaries cap what a developer-created role can do: delegate iam:CreateRole only if the new role has the boundary attached. Session policies cut a session down further at AssumeRole time. Both only limit; neither grants.
  • ABAC at scale: one policy matching aws:ResourceTag/project to ${aws:PrincipalTag/project} replaces a policy per team, and tags flow from the IdP, Pod Identity or Roles Anywhere. Mark tags transitive to keep them through role chaining, and set a source identity so the original user stays in CloudTrail; neither can be changed later in the chain. Check the ABAC column of the services table: API Gateway invoke, S3 Tables and DAX don't support it, and S3 general purpose buckets need ABAC turned on per bucket.
  • Temporary credentials: role sessions last up to the role's maximum (up to 12 hours), but a chained role session is capped at 1 hour.
  • Tooling: Access Analyzer policy generation from CloudTrail, unused access findings, and custom policy checks in the pipeline (see SCS Task 4.2).
Trust policy: the auditing vendor (777777777777) assumes a read-only role in the security account 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::777777777777:role/AuditScanner" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "a7f3c9e2-example" }
      }
    }
  ]
}
Support engineer: chained session cut down to one bucket, with the user recorded 
aws sts assume-role \
  --role-arn arn:aws:iam::111111111111:role/SupportReadOnly \
  --role-session-name jdoe-ticket-4182 \
  --source-identity jdoe \
  --duration-seconds 3600 \
  --policy '{"Version":"2012-10-17","Statement":[{"Effect":"Allow",
    "Action":"s3:GetObject",
    "Resource":"arn:aws:s3:::example-support-logs/*"}]}'
# Needs sts:SetSourceIdentity in the caller's policy and the trust policy;
# effective access = role policy AND session policy

"A vendor's SaaS product needs access to our accounts" means a role with an external ID condition. "Developers must create roles for their Lambda functions without escalating privilege" means a permissions boundary condition on iam:CreateRole. "One policy for hundreds of project teams" means ABAC. "Show who really made the call after several role hops" means source identity.

Data perimeters

Skill 2.1.4Design data perimeter controls and external access validation solutions (for example, by using AWS Identity and Access Management Access Analyzer, VPC endpoint policies, AWS Verified Access).

  • Three perimeters, three policy types:
    • Trusted identities (only our principals reach our resources): an RCP on resources and a VPC endpoint policy on the network, using aws:PrincipalOrgID.
    • Trusted resources (our principals reach only our resources): an SCP on identities and the endpoint policy, using aws:ResourceOrgID.
    • Expected networks: an SCP (our identities only from our networks) and an RCP (our resources only from our networks), using aws:SourceIp, aws:SourceVpc or the newer aws:VpceOrgID, which covers every endpoint in the organization without listing endpoint IDs.
  • RCPs set the maximum permissions on resources in member accounts, even for principals outside the organization. They now cover about 90 services, but not Lambda, RDS, API Gateway or Kinesis Data Streams (use resource policies there). They don't apply to the management account, to service-linked roles or to AWS managed KMS keys, and a target can hold at most 5 RCPs, including the default RCPFullAWSAccess.
  • Exceptions every perimeter needs: AWS service principals (CloudTrail writing logs, for example) with aws:PrincipalIsAWSService, and services acting with your credentials with aws:ViaAWSService. Use the ...IfExists operators because these keys are often absent. Test on a low OU first, and use the data-perimeter-helper tool to predict impact from CloudTrail.
  • Validating external access: an Access Analyzer external access analyzer with the organization as its zone of trust lists every resource policy that grants access outside it, using automated reasoning, not logs. Archive rules hide expected findings, and CheckNoPublicAccess blocks public policies in the pipeline.
  • AWS Verified Access replaces the VPN for corporate apps: every request is checked against a Cedar policy using user identity (Identity Center or OIDC) and device posture (Jamf, CrowdStrike, JumpCloud). Endpoints can be load balancers, network interfaces, CIDR ranges or RDS databases, and TCP applications have been supported since February 2025 through the Connectivity Client. HTTP(S) apps are billed per application-hour and per GB.
RCP: only organization principals (plus the auditing vendor account) reach S3, except AWS services 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceOrgIdentities",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:PrincipalOrgID": "o-a1b2c3d4e5",
          "aws:PrincipalAccount": ["777777777777"]
        },
        "BoolIfExists": { "aws:PrincipalIsAWSService": "false" }
      }
    }
  ]
}
VPC endpoint policy: organization identities to organization resources 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgIdentitiesToOrgResources",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:PrincipalOrgID": "o-a1b2c3d4e5",
          "aws:ResourceOrgID": "o-a1b2c3d4e5"
        }
      }
    },
    {
      "Sid": "AwsServicePrincipals",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "*",
      "Resource": "*",
      "Condition": { "Bool": { "aws:PrincipalIsAWSService": "true" } }
    }
  ]
}

Access Analyzer external findings don't yet take RCP denies into account, and an RCP change can take up to 24 hours to show. Archive rules apply only to new findings unless you archive existing ones too. The aws:VpceOrgID keys work only with the services that support them; for others use aws:SourceVpc or aws:SourceVpce. Network keys aren't kept when a service calls another service for you, which is why the aws:ViaAWSService exception is needed.

Hybrid and multi-cloud workloads

Skill 2.1.5Design workload identities for hybrid and multi-cloud environments (for example, by using IAM Roles Anywhere).

  • IAM Roles Anywhere gives servers outside AWS temporary credentials in exchange for an X.509 certificate from your CA, so there are no long-term access keys on premises.
    • A trust anchor registers the CA (AWS Private CA or your own), and a profile lists the roles, an optional session policy and a session length of 15 minutes to 12 hours.
    • Certificate fields become session tags (aws:PrincipalTag/x509Subject/CN, x509SAN/URI for SPIFFE IDs) to narrow the trust policy.
  • Keys and revocation: the credential helper reads keys from files, PKCS#11 HSMs, TPM 2.0, Windows CNG or the macOS Keychain. There's no OCSP: import CRLs (their next-update date isn't checked, so re-import on schedule) or turn on automatic CRL distribution-point checking (November 2026), which fails closed if no valid CRL can be fetched.
  • Credential helper modes: credential-process for the CLI and SDK profiles, update to refresh a credentials file, and serve for an IMDS-like local endpoint (any local process can then read the credentials).
  • Workloads in another cloud or CI: if the platform already issues signed OIDC tokens (another cloud's workload identity, GitHub Actions), register its issuer as an IAM OIDC provider and call AssumeRoleWithWebIdentity; no PKI is needed. Roles Anywhere suits workloads that already hold certificates.
  • AWS workloads calling other clouds: outbound identity federation (November 2025) gives each account an OIDC issuer; sts:GetWebIdentityToken returns a short-lived JWT the other cloud or SaaS trusts, replacing stored secrets. It isn't available on the STS global endpoint.
  • For connecting the on-premises network itself, see Task 1.3.
Trust policy: only batch servers from our trust anchor, by certificate CN 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "rolesanywhere.amazonaws.com" },
      "Action": ["sts:AssumeRole", "sts:TagSession", "sts:SetSourceIdentity"],
      "Condition": {
        "ArnEquals": {
          "aws:SourceArn": "arn:aws:rolesanywhere:us-east-1:111111111111:trust-anchor/EXAMPLE-ta-id"
        },
        "StringLike": { "aws:PrincipalTag/x509Subject/CN": "batch-*.corp.example.com" }
      }
    }
  ]
}
On-premises server: ~/.aws/config profile that calls the credential helper 
[profile batch]
credential_process = aws_signing_helper credential-process
    --certificate /etc/pki/batch01.pem
    --private-key /etc/pki/batch01.key
    --trust-anchor-arn arn:aws:rolesanywhere:us-east-1:111111111111:trust-anchor/EXAMPLE-ta-id
    --profile-arn arn:aws:rolesanywhere:us-east-1:111111111111:profile/EXAMPLE-profile-id
    --role-arn arn:aws:iam::111111111111:role/OnPremBatch
# Shown wrapped for reading; in the file this is one line

A Roles Anywhere trust policy without aws:SourceArn and certificate conditions lets any certificate from the CA assume the role. A profile session longer than the role's maximum session duration returns an error rather than being shortened. Shared OIDC providers now reject trust policies that don't check sub (or the provider's required claim), so a pipeline in another tenant can't assume your role.

Key takeaways

  • People: Identity Center with the corporate IdP over SAML and SCIM, permission sets or (new) existing IAM roles, IdP attributes as ABAC tags, trusted identity propagation for OAuth apps; direct IAM federation only for small or machine cases and encrypted assertions.
  • Apps: user pools authenticate, identity pools issue AWS credentials (enhanced flow), resource servers and scopes for M2M, a tenancy pattern chosen by isolation need.
  • Pods: Pod Identity with session tags and target roles; IRSA only where Pod Identity isn't supported.
  • Least privilege: roles and resource policies across accounts, external IDs for vendors, boundaries for delegated role creation, session policies, transitive tags and source identity; chained sessions last 1 hour.
  • Perimeters: RCPs and endpoint policies for trusted identities, SCPs and endpoint policies for trusted resources, both for expected networks, with service-principal exceptions; Access Analyzer to validate, Verified Access instead of a VPN.
  • Outside AWS: Roles Anywhere for certificate holders, OIDC federation for platforms that issue tokens, outbound identity federation for AWS workloads calling elsewhere.
