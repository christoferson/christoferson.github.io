Overview

Task 2.2

Design solutions to implement encryption and key management strategies.

At Professional level the questions are about ownership and fit: which account owns a key, why an AWS managed key breaks cross-account sharing, whether a regulation really needs single-tenant HSMs, and which parts of post-quantum TLS AWS does for you. Service-by-service encryption settings, imported key material, external key stores and secrets rotation are in the SCS data at rest notes, SCS data in transit notes and SCS keys and secrets notes.

Running example. Regulated customer data sits in Aurora and S3 in us-east-1 with DR in us-west-2. The analytics account (444444444444) shares curated S3 data with business-unit accounts such as 555555555555. Card tokenization still runs on an on-premises HSM, and the security team must show a plan for quantum-safe cryptography in the next audit.

Status changes to know. The CloudHSM hsm1.medium type reached end of support on 31 March 2026 (clusters were migrated to hsm2m.medium). S3 has blocked SSE-C by default on new general purpose buckets since April 2026. ACM public certificates are now valid for 198 days, falling to under 100 days from 15 March 2027 and under 47 days from 15 March 2029, so only managed renewal is practical. The Secrets Manager Agent is now the AWS Workload Credentials Provider. New: custom KMS rotation periods and on-demand rotation (April 2024), ML-DSA signing keys in KMS (June 2025), post-quantum ELB policies (September 2025), Private CA ML-DSA certificates (November 2025), exportable public ACM certificates, key last-usage tracking (2026) and ML-KEM keys in KMS (October 2026).

Encryption at rest with KMS

Skill 2.2.1Implement encryption at rest by using customer managed keys and automatic key rotation (for example, by using AWS KMS).

  • Customer managed keys when control matters: you own the key policy, rotation, grants and deletion, and only customer managed keys can be used across accounts. AWS managed keys (aws/s3, aws/rds) can't, so encrypted snapshots, S3 objects or backups under them can't be shared; and RCPs don't apply to them.
  • Who owns the keys:
    • Keys in each workload account keep the blast radius small and let teams manage their own keys; a central team enforces standards with SCPs, Config rules and IaC.
    • A central key account gives one place to administer and audit keys, but one bad key policy or deletion affects every user.
    • Request quota doesn't decide it: KMS throttles the calling account, not the account that owns the key. The shared symmetric quota is 10,000 to 100,000 requests per second per account per Region, depending on the Region.
  • Cross-account use needs a key policy statement in the owner account and an IAM policy in the caller account. Callers must use the key ARN (an alias resolves in their own account), and admin actions such as deleting the key never work cross-account.
  • Narrow the key policy with kms:ViaService (only through S3 or RDS), kms:CallerAccount, and kms:EncryptionContext: keys. S3 Bucket Keys cut KMS calls and cost for SSE-KMS buckets, and make the encryption context the bucket ARN.
  • Rotation: automatic rotation applies to symmetric customer managed keys with KMS-generated material. It's off by default, and the period can be 90 to 2,560 days (default 365). On-demand rotation (up to 25 per key) also works for imported material. Rotation keeps the key ID and old material, so old ciphertext still decrypts and no data is re-encrypted. Asymmetric, HMAC and custom key store keys rotate manually: create a new key and move the alias.
  • Keys across Regions: multi-Region keys share key material so the DR Region decrypts without a cross-Region call; policies, grants and aliases are set per Region.
Key policy in the analytics account: business unit 555555555555 may decrypt only through S3, only for the curated bucket 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "KeyAdmins",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::444444444444:root" },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "BusinessUnitDecryptViaS3",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::555555555555:root" },
      "Action": ["kms:Decrypt", "kms:DescribeKey"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "s3.us-east-1.amazonaws.com",
          "kms:EncryptionContext:aws:s3:arn": "arn:aws:s3:::example-curated"
        }
      }
    }
  ]
}
Rotate every 180 days, and once now after a suspected exposure 
aws kms enable-key-rotation \
  --key-id arn:aws:kms:us-east-1:444444444444:key/1234abcd-12ab-34cd-56ef-1234567890ab \
  --rotation-period-in-days 180

aws kms rotate-key-on-demand \
  --key-id arn:aws:kms:us-east-1:444444444444:key/1234abcd-12ab-34cd-56ef-1234567890ab
# Rotation doesn't re-encrypt data keys already in use: a leaked data key
# still needs the data re-encrypted under a new one

"Share encrypted snapshots or replicate SSE-KMS objects to another account" fails with an AWS managed key; the answer is a customer managed key with a cross-account key policy. Never use ForAllValues with kms:EncryptionContext: keys (KMS rejects it). Some resources can only be encrypted at creation (RDS, EFS): encrypting later means copy or snapshot, then restore.

Encryption in transit and certificates

Skill 2.2.2Implement encryption in transit by using certificate management (for example, TLS 1.3, AWS Certificate Manager [ACM], AWS Private CA).

  • Where TLS ends: at CloudFront (certificate in us-east-1), at the ALB or NLB (re-encrypt to targets when end-to-end encryption is required), or at the target with an NLB TCP pass-through or ALB mutual TLS. Pick TLS 1.3 security policies; the console default for new ELB HTTPS listeners is a TLS 1.3 post-quantum policy, but the CLI and CloudFormation still default to the 2016 policy that allows TLS 1.0.
  • Force TLS on the data path: aws:SecureTransport and s3:TlsVersion in bucket policies, rds.force_ssl or require_secure_transport for databases, in-transit encryption for ElastiCache and MSK.
  • ACM public certificates are free on integrated services (ELB, CloudFront, API Gateway) and renew automatically. With validity shrinking to 198 days now and much shorter later, avoid imported certificates, which ACM never renews. Exportable public certificates (paid) cover EC2, containers and on-premises servers.
  • AWS Private CA for internal TLS, mTLS and device identity:
    • Build a root plus subordinate CAs in a central account and share them through RAM. Member accounts request private certificates in ACM, which renews them; the receiving account owns that renewal.
    • General-purpose mode costs $400 per CA per month. Short-lived mode costs $50 per month and issues certificates valid for up to 7 days (no revocation needed), but ACM can't issue from it.
    • CAs are Regional, so DR needs a CA in the DR Region.
  • Service-to-service: ECS Service Connect and VPC Lattice terminate TLS with Private CA or ACM certificates (App Mesh has reached end of support).
Orders API listener with TLS 1.3 and hybrid post-quantum key exchange (set the policy explicitly in IaC) 
aws elbv2 create-listener \
  --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:111111111111:loadbalancer/app/orders/50dc6c495c0c9188 \
  --protocol HTTPS --port 443 \
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09 \
  --certificates CertificateArn=arn:aws:acm:us-east-1:111111111111:certificate/example-cert-id \
  --default-actions Type=forward,TargetGroupArn=arn:aws:elasticloadbalancing:us-east-1:111111111111:targetgroup/orders/73e2d6bc24d8a067
Member account: private certificate from the shared CA, renewed by ACM 
aws acm request-certificate \
  --domain-name orders.internal.example.com \
  --certificate-authority-arn arn:aws:acm-pca:us-east-1:111111111111:certificate-authority/example-ca-id

"Internal services need certificates that rotate every few days" points to a short-lived Private CA used directly, not ACM. "Hundreds of accounts need private certificates without running a CA each" points to one CA hierarchy shared with RAM. "End-to-end encryption to the instances" means HTTPS target groups or NLB pass-through, not just an HTTPS listener.

Dedicated HSMs

Skill 2.2.3Implement dedicated hardware security modules to comply with regulations (for example, AWS CloudHSM).

  • KMS first: KMS keys already live in FIPS 140-3 Level 3 validated HSMs, so "FIPS Level 3" alone isn't a reason for CloudHSM. Choose CloudHSM when the requirement is a single-tenant HSM that only you control (AWS has no access to keys, and lost credentials can't be recovered), standard HSM interfaces (PKCS#11, JCE, OpenSSL, Windows CNG/KSP), or algorithms KMS doesn't offer.
  • Typical uses: TLS offload for web servers, Oracle TDE, protecting the private key of your own issuing CA, and lifting an on-premises HSM application. Payment workloads (PIN blocks, card keys) belong in AWS Payment Cryptography instead.
  • Cluster design: HSMs in your VPC across AZs, with at least 2 HSMs in 2 AZs for production and 3 for mission-critical workloads. A cluster holds up to 28 HSMs, and you pay per HSM-hour whether it's busy or not. The cluster mode (FIPS or non-FIPS) is fixed at creation.
  • Durability and DR: AWS takes backups automatically; copy them to the DR Region and create a cluster there from the backup.
  • CloudHSM key store: KMS keys whose material is generated and used in your cluster, so integrated services (S3, EBS, RDS) still work. It needs 2 active HSMs in different AZs, a kmsuser crypto user, and no mTLS on the cluster. It supports symmetric keys only, with no automatic rotation, no multi-Region keys and no SLA, and every key store shares a fixed 1,800 requests per second. AWS prefers it over an external key store when a custom store is required.
CloudHSM: copy the latest backup to the DR Region, then back KMS keys with the cluster 
aws cloudhsmv2 copy-backup-to-region \
  --backup-id backup-1234567890abcdef0 \
  --destination-region us-west-2

aws kms create-custom-key-store \
  --custom-key-store-name tokenization-store \
  --cloud-hsm-cluster-id cluster-1a23b4cdefg \
  --key-store-password "<kmsuser password>" \
  --trust-anchor-certificate file://customerCA.crt
# Then connect-custom-key-store and create keys with --origin AWS_CLOUDHSM

A cluster restored from a copied backup in another Region is a different cluster to KMS: keys in a key store there can't decrypt ciphertext from the original store. Between backups, you alone are responsible for keys created in the HSMs. Turning on mTLS on the cluster breaks the KMS key store connection.

Post-quantum cryptography

Skill 2.2.4Design post-quantum cryptography strategies (for example, by using AWS KMS with Module-Lattice Digital Signature Algorithm [ML-DSA], Module-Lattice-Based Key-Encapsulation Mechanism [ML-KEM]).

  • The threat: traffic recorded today could be decrypted by a future quantum computer ("harvest now, decrypt later"), and signatures on long-lived firmware or roots of trust could be forged. Symmetric encryption with 256-bit keys is considered safe, so data at rest under AES-256 KMS keys doesn't need re-encrypting. Data in transit comes first.
  • AWS's migration plan has four workstreams: inventory and planning; hybrid key exchange (classical ECDH plus ML-KEM) on public endpoints; ML-DSA signing for long-lived roots of trust; and post-quantum certificates for session authentication as standards mature.
  • What AWS does for you: KMS, ACM, IAM, STS, S3, Secrets Manager and CloudFront (viewer side, TLS 1.3) negotiate hybrid ML-KEM with any client that offers it. CloudFront to origin is not there yet.
  • What you must do:
    • Update clients: SDKs, the CLI or runtimes with OpenSSL 3.5 or later; defaults differ by SDK and platform.
    • Opt in on resources you configure: ELB ...-PQ-2025-09 policies, API Gateway SecurityPolicy_TLS13_1_2_PQ_2025_09, Transfer Family TransferSecurityPolicy-2025-03 for SFTP, and newer RDS and Aurora engine versions.
    • Move off the Classic Load Balancer, which has no post-quantum plan.
  • Prove it: CloudTrail records tlsDetails.keyExchange (for example X25519MLKEM768), so a metric filter can flag callers still on classical key exchange.
  • ML-DSA in KMS (ML_DSA_44, 65, 87) signs code, firmware and documents with one algorithm, ML_DSA_SHAKE_256. Raw messages can be up to 4,096 bytes; for larger ones send the 64-byte message representative (EXTERNAL_MU). Private CA can issue ML-DSA CAs and certificates for code signing, device identity and mTLS.
  • ML-KEM in KMS (ML_KEM_512, 768, 1024) establishes a shared secret with Encapsulate and Decapsulate, which you feed into a key derivation function. A wrong key or tampered ciphertext returns random bytes rather than an error, so both sides must confirm they derived the same secret.
  • Crypto agility: keep algorithms in configuration, not code, and use aliases and envelope encryption so keys and algorithms can change without touching data.
Release signing key with ML-DSA; sign the 64-byte mu of a large firmware image 
aws kms create-key \
  --key-spec ML_DSA_65 \
  --key-usage SIGN_VERIFY \
  --description "Firmware release signing"

aws kms sign \
  --key-id alias/firmware-signing \
  --message fileb://firmware-mu.bin \
  --message-type EXTERNAL_MU \
  --signing-algorithm ML_DSA_SHAKE_256
CloudWatch Logs metric filter: KMS calls that didn't use post-quantum key exchange 
{ ($.eventSource = "kms.amazonaws.com") &&
  ($.userIdentity.invokedBy NOT EXISTS) &&
  (($.tlsDetails.keyExchange != "*MLKEM*") ||
   ($.tlsDetails.keyExchange NOT EXISTS)) }

"Protect against harvest-now-decrypt-later" means hybrid ML-KEM TLS (update clients, opt in on load balancers and APIs), not re-encrypting S3 data. "Signatures must stay trustworthy for 20 years" means ML-DSA keys in KMS. Calls AWS services make for you don't show tlsDetails, which is why the filter excludes them.

Key takeaways

  • At rest: customer managed keys for anything shared across accounts, key policy plus IAM policy, kms:ViaService and encryption context to narrow use, automatic rotation 90 to 2,560 days plus on-demand rotation; quotas are charged to the caller.
  • In transit: TLS 1.3 policies set explicitly in IaC, ACM managed renewal as validity shrinks, Private CA hierarchy shared by RAM, short-lived mode for certificates of up to 7 days.
  • HSMs: KMS is already FIPS 140-3 Level 3; CloudHSM for single-tenant control and HSM interfaces, at least 2 HSMs in 2 AZs, backups copied for DR, a CloudHSM key store to keep service integrations.
  • Post-quantum: transit first with hybrid ML-KEM (automatic on many AWS endpoints, opt-in on ELB and API Gateway, updated clients), ML-DSA for long-lived signatures, ML-KEM keys for shared secrets, verify with CloudTrail tlsDetails.
