Overview

Task 1.5

Design data, storage, and database architectures.

This task is broad, and the questions reward knowing each service's limits: which database can take writes in two Regions with no data loss, which file system serves Windows and Linux clients from the same data, which cache sees stale results after a write. The SAA database notes and SAA storage notes cover the basics, and the Data Engineer notes go deeper on Glue, Lake Formation, Redshift and streaming.

Running example. Orders are in Aurora PostgreSQL in us-east-1 with a DR copy in us-west-2; the cart service runs on DynamoDB; clickstream flows through Kinesis to S3. An analytics account (444444444444) runs the lakehouse, business-unit accounts query it, and a retail partner wants to measure campaign overlap without either side seeing the other's customer list.

Status changes to know. S3 Select has been closed to new customers since 25 July 2024 and S3 Object Lambda since 7 November 2025. The original vault-based Amazon Glacier service no longer accepts new customers (use the Glacier storage classes in S3). Timestream for LiveAnalytics closed to new customers on 20 June 2025 (use Timestream for InfluxDB). QLDB is no longer offered. The legacy Clean Rooms SQL engine reached end of support on 17 December 2025 (Spark SQL is now the only engine). ElastiCache for Redis OSS 4 and 5 left standard support on 31 January 2026 and now incur Extended Support charges. New: Aurora DSQL (generally available May 2025, foreign keys August 2026), DynamoDB multi-Region strong consistency (June 2025), MemoryDB Multi-Region (December 2024), S3 Vectors (December 2025), S3 Metadata (January 2025), gp3 volumes up to 80,000 IOPS (September 2025), and the 50 TB maximum S3 object (December 2025).

Data lakes and lakehouses

Skill 1.5.1Design data lake and lakehouse architectures (for example, by using Amazon S3, AWS Lake Formation, Amazon Redshift Spectrum, Apache Iceberg).

  • Storage layer: S3 in zones (raw, cleaned, curated), with Apache Iceberg tables for ACID updates, schema evolution and time travel. S3 Tables (table buckets) manage Iceberg for you, including compaction and snapshot cleanup, with their own resource policies at bucket and table level.
  • Catalog and permissions: the Glue Data Catalog holds the tables; Lake Formation adds table, column, row and cell permissions and tag-based access control. S3 Tables now integrate with analytics services using IAM by default, with Lake Formation optional.
  • Query engines: Athena for ad hoc SQL, EMR or Glue for Spark, and Redshift for the warehouse. Redshift can query the lake through Spectrum and now creates and writes Iceberg tables (INSERT, UPDATE, DELETE, MERGE) in S3 or table buckets.
  • Lakehouse in both directions: register a Redshift namespace in the Glue Data Catalog so Iceberg engines (Athena, EMR) read warehouse data under Lake Formation control, and use zero-ETL integrations to land Aurora, RDS or DynamoDB data in Redshift or the lakehouse without pipelines. Amazon SageMaker Unified Studio is the workspace over all of this.
Table bucket policy: business-unit account 555555555555 may read the sales namespace (S3 Tables resource policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadSalesTables",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::555555555555:role/SalesAnalyst" },
      "Action": ["s3tables:GetTableData", "s3tables:GetTableMetadataLocation"],
      "Resource": "arn:aws:s3tables:us-east-1:444444444444:bucket/analytics-tables/table/*",
      "Condition": { "StringLike": { "s3tables:namespace": "sales" } }
    }
  ]
}

Table bucket and table policies are evaluated together with IAM, so a Deny in either wins. Writers also need s3tables:UpdateTableMetadataLocation. Moving an old Lake Formation-mode S3 Tables integration to IAM mode removes its existing Lake Formation grants. Redshift's DROP TABLE on an Iceberg table removes only the catalog entry; the data files stay in S3.

Analytics pipelines

Skill 1.5.2Design real-time and batch analytics pipelines (for example, by using Amazon EMR, Amazon Redshift, Amazon Managed Streaming for Apache Kafka [Amazon MSK], Amazon AppFlow).

  • Streaming ingestion:
    • Kinesis Data Streams: AWS-native, simple, with on-demand capacity.
    • Amazon MSK: for Kafka APIs, existing Kafka tools or very high throughput. Express brokers have unlimited storage and fast scaling. MSK Serverless is for variable, smaller workloads: IAM authentication only, and 200 MBps in per cluster. MSK Connect runs Kafka Connect connectors, and MSK Replicator copies topics between clusters and Regions.
  • Stream processing: Managed Service for Apache Flink for stateful, windowed processing; Lambda for simple per-record work; Firehose to deliver to S3, Iceberg tables, S3 Tables, Redshift or OpenSearch with buffering and format conversion.
  • Batch:
    • EMR on EC2: for long-running clusters, full control and Spot.
    • EMR Serverless: for jobs without clusters. AWS says it costs less when an EC2 cluster would be under about 70% utilized on On-Demand, or 50% with Savings Plans.
    • EMR on EKS: to share a Kubernetes platform.
    • Glue: for serverless ETL.
    • Redshift: for SQL transformations inside the warehouse.
  • SaaS sources: Amazon AppFlow moves data from applications such as Salesforce, ServiceNow or Zendesk to S3 or Redshift, on demand, on a schedule or on events, over PrivateLink where supported.

A common combined design: clickstream into Kinesis or MSK, Flink for real-time aggregates and alerts, Firehose writing raw events into Iceberg tables, then scheduled EMR Serverless or Glue jobs and Redshift for the curated layer, with Step Functions or Amazon MWAA orchestrating the batch side.

"Existing Kafka applications, minimal code change" points to MSK. "Unpredictable, low volume, no capacity planning" points to MSK Serverless or Kinesis on-demand. "Spark jobs a few hours a day" points to EMR Serverless; "large always-on Spark cluster on Spot" points to EMR on EC2. "Pull CRM data into the lake on a schedule without code" points to AppFlow.

Choosing a database

Skill 1.5.3Select appropriate database services based on workload requirements such as access patterns, consistency needs, and scalability (for example, Amazon RDS, Amazon Aurora, Amazon DynamoDB, Amazon Redshift).

  • Amazon RDS: engine-specific or commercial needs: Oracle, SQL Server and Db2 (license included or BYOL), MySQL, MariaDB, PostgreSQL. RDS Custom for OS-level access to Oracle or SQL Server.
  • Aurora (provisioned or Serverless v2): full MySQL or PostgreSQL with one writer and up to 15 replicas, storage across three AZs, and Serverless v2 scaling down to 0 ACUs. I/O-Optimized storage when I/O is a large share of the bill.
  • Aurora Limitless Database: when one PostgreSQL writer is the bottleneck, with tables sharded across a shard group (up to 6,144 ACUs). It needs I/O-Optimized storage and doesn't support Global Database, RDS Proxy, Blue/Green or read replicas.
  • Aurora DSQL: serverless, PostgreSQL-compatible, active-active in one Region or two peered Regions plus a witness Region, with strong consistency and 99.999% multi-Region availability. Uses optimistic concurrency (no locks; the app retries on conflict). Each transaction can modify at most 3,000 rows and 10 MiB, and can run at most 5 minutes. There are no triggers, PL/pgSQL or temporary tables. Best for new applications.
  • DynamoDB: key-value and document access with known patterns at any scale, single-digit millisecond latency, on-demand or provisioned capacity. Reads are eventually consistent unless you ask for strong consistency; transactions cover up to 100 items and 4 MB, at twice the capacity cost.
  • Purpose-built:
    • DocumentDB: MongoDB-compatible documents.
    • Neptune: graphs.
    • Keyspaces: Cassandra.
    • MemoryDB: a durable in-memory database.
    • Timestream for InfluxDB: time series.
    • OpenSearch: search and log analytics.
    • Redshift: OLAP and columnar analytics, never OLTP. Multi-AZ RA3 clusters raise its SLA to 99.99%.

"Relational, writes in two Regions, zero data loss" points to Aurora DSQL. "Oracle with custom OS agents" points to RDS Custom for Oracle. "Millions of writes per second on PostgreSQL, one database" points to Aurora Limitless. "Key-value at massive scale, single-digit milliseconds" points to DynamoDB. "Ledger with verifiable history" no longer points to QLDB; AWS recommended Aurora PostgreSQL with audit tables.

Database high availability

Skill 1.5.4Design database scaling solutions to provide high availability (for example, by using read replicas, Amazon Aurora Global Database, Amazon DynamoDB global tables, Amazon RDS Multi-AZ deployments).

  • Within a Region:
    • RDS Multi-AZ DB instance: one standby that can't serve reads.
    • RDS Multi-AZ DB cluster: MySQL and PostgreSQL only. Two readable standbys in three AZs, failover typically under 35 seconds.
    • Aurora replicas: up to 15, with failover priority tiers.
    • RDS Proxy: keeps connection pools through a failover.
    • Read replicas: scale reads and can be promoted, but replicate asynchronously.
  • Aurora Global Database:
    • One writer Region and up to 10 read-only secondary Regions, replicated at the storage layer with lag typically under a second.
    • Switchover (planned) waits for sync, so there's no data loss. Failover (unplanned) uses --allow-data-loss, with best-effort write fencing of the old primary.
    • The global writer endpoint follows the primary.
    • Write forwarding lets secondary-Region apps send occasional writes to the primary.
  • DynamoDB global tables:
    • Multi-Region eventual consistency (the default): active-active with last writer wins, replication typically within a second, and replicas can be added any time.
    • Multi-Region strong consistency: RPO 0, but exactly 3 Regions (3 replicas, or 2 plus a witness). It's set when you convert an empty table and has no transactions, TTL or local secondary indexes.
  • Blue/Green deployments (Aurora, and RDS for MySQL, MariaDB and PostgreSQL) switch to an upgraded copy in about a minute without changing endpoints.
  • Other engines: DocumentDB global clusters (up to 10 secondary Regions), Neptune global database (up to 5), and active-active multi-Region for Keyspaces and MemoryDB (last writer wins).
Planned Region rotation, then the unplanned version (AWS CLI) 
# Planned: run in the primary Region; Aurora syncs first, so no data is lost
aws rds switchover-global-cluster --region us-east-1 \
    --global-cluster-identifier orders-global \
    --target-db-cluster-identifier arn:aws:rds:us-west-2:111111111111:cluster:orders-usw2

# Unplanned (us-east-1 is down): run in the secondary Region and accept losing the replication lag
aws rds failover-global-cluster --region us-west-2 \
    --global-cluster-identifier orders-global \
    --target-db-cluster-identifier arn:aws:rds:us-west-2:111111111111:cluster:orders-usw2 \
    --allow-data-loss
Make the empty cart table strongly consistent across three Regions: two replicas plus a witness (AWS CLI) 
aws dynamodb update-table --region us-east-1 --table-name Carts \
    --replica-updates '[{"Create":{"RegionName":"us-east-2"}}]' \
    --global-table-witness-updates 'Create={RegionName=us-west-2}' \
    --multi-region-consistency STRONG

With multi-Region eventual consistency, a strongly consistent read is only current for writes made in the same Region. Multi-Region strong consistency can't add a fourth Region later and rejects transactions, so a design needing both TransactWriteItems and zero RPO across Regions points elsewhere (Aurora DSQL). Without --allow-data-loss, failover-global-cluster performs a switchover. Aurora Limitless isn't a multi-Region answer: it can't join a Global Database.

Storage by access pattern

Skill 1.5.5Design storage architectures based on access patterns and performance requirements (for example, by using Amazon S3, Amazon EBS, Amazon EFS, Amazon FSx).

Amazon S3:

  • Request rates: at least 3,500 writes and 5,500 reads per second per prefix, so spread hot keys across prefixes.
  • S3 Express One Zone: directory buckets give single-digit millisecond access in one AZ, with append and atomic rename. It's single-AZ, so keep a durable copy in a Regional storage class.
  • S3 Vectors: vector buckets for large, infrequently queried embeddings, up to 2 billion vectors per index. OpenSearch is for high query rates.
  • S3 Metadata: queryable Iceberg tables of object changes and inventory.
  • Multi-Region Access Points: one global endpoint over buckets in several Regions. Pair them with Cross-Region Replication (RTC replicates 99.9% of objects within 15 minutes).
  • Glacier classes: restores take minutes (Expedited) to 48 hours (Deep Archive Bulk).

Amazon EBS: gp3 now reaches 80,000 IOPS and 2,000 MiB/s; io2 Block Express goes to 256,000 IOPS with sub-millisecond latency and Multi-Attach in one AZ. Volumes restored from snapshots can use a provisioned initialization rate (100 to 300 MiB/s) for a predictable time to full performance.

File storage, by need:

  • Amazon EFS: elastic NFS across AZs for Linux shared storage, with Elastic throughput. Replication (including cross-account) has a 15-minute RPO, and the destination is read-only until you delete the replication.
  • FSx for Windows File Server: SMB with Active Directory, DFS Namespaces and SQL Server continuously available shares. Multi-AZ fails over in under 30 seconds.
  • FSx for NetApp ONTAP: the same data over NFS, SMB, iSCSI and NVMe/TCP, with SnapMirror from on-premises NetApp, tiering and deduplication. It's the multi-protocol answer.
  • FSx for OpenZFS: very low-latency NFS (up to 2 million IOPS) with snapshots and clones, including a Multi-AZ option.
  • FSx for Lustre: HPC and ML training linked to S3 (data repository associations), with EFA and GPUDirect Storage and an Intelligent-Tiering storage class. It's single-AZ only.
Replicate invoices to us-west-2 with Replication Time Control (replication configuration for aws s3api put-bucket-replication) 
{
  "Role": "arn:aws:iam::111111111111:role/s3-replication",
  "Rules": [
    {
      "ID": "invoices-to-usw2",
      "Status": "Enabled",
      "Priority": 1,
      "Filter": { "Prefix": "invoices/" },
      "DeleteMarkerReplication": { "Status": "Disabled" },
      "Destination": {
        "Bucket": "arn:aws:s3:::invoices-usw2-111111111111",
        "ReplicationTime": { "Status": "Enabled", "Time": { "Minutes": 15 } },
        "Metrics": { "Status": "Enabled", "EventThreshold": { "Minutes": 15 } }
      }
    }
  ]
}

Multi-Region Access Points don't replicate data, their bucket list is fixed at creation, and failover is a manual change of routing (minutes). FSx for Windows Multi-AZ failover is transparent to Windows clients but not to Linux clients, and DFS Replication works only on Single-AZ 1 file systems. FSx File Gateway is closed to new customers.

Caching

Skill 1.5.6Design data caching strategies to optimize performance (for example, by using ElastiCache, DynamoDB Accelerator [DAX]).

  • Patterns: lazy loading (cache on a miss; stale data possible, three trips on a miss), write-through (update the cache on every write; never stale, but caches data nobody reads), and a TTL on everything. AWS recommends combining all three.
  • ElastiCache:
    • Serverless: Valkey, Redis OSS or Memcached, no nodes to size.
    • Node-based clusters: cluster mode for sharding, and data tiering on R6gd nodes to keep less-used items on SSD.
    • Valkey: 33% cheaper than Redis OSS on Serverless and 20% cheaper on nodes, and you can upgrade in place.
    • Global Datastore: one writable Region plus up to two read-only Regions, promoted manually in about a minute. It's same-account only and not available for Serverless.
  • DAX: a write-through, in-VPC cache for DynamoDB with microsecond reads, using the DAX client. It has an item cache (GetItem) and a separate query cache (Query, Scan). Run at least 3 nodes across AZs in production; a cluster serves only its own Region.
  • MemoryDB when the in-memory store is the durable primary database. MemoryDB Multi-Region is active-active across up to 5 Regions, but has no TTL and no automatic failover.
  • Other layers: CloudFront for HTTP content at the edge, Aurora reader endpoints and read replicas for read scaling. RDS Proxy pools connections; it isn't a cache.
A serverless Valkey cache for the product catalog, with cost ceilings (AWS CLI) 
aws elasticache create-serverless-cache --serverless-cache-name catalog-cache \
    --engine valkey --major-engine-version 8 \
    --cache-usage-limits 'DataStorage={Maximum=100,Unit=GB},ECPUPerSecond={Maximum=500000}' \
    --subnet-ids subnet-0a1b2c3d4e5f60001 subnet-0a1b2c3d4e5f60002 \
    --security-group-ids sg-0a1b2c3d4e5f60003 \
    --snapshot-retention-limit 7

Writes through DAX update the item cache but not the query cache, so Query and Scan results stay stale until their TTL expires. Strongly consistent reads and TransactGetItems are never cached; they go straight to DynamoDB. Writes made directly to DynamoDB (or replicated from another global table Region) bypass DAX entirely.

Catalogs and cross-account sharing

Skill 1.5.7Design data cataloging and cross-account data sharing patterns (for example, AWS Glue Data Catalog, Lake Formation, AWS Clean Rooms).

Lake Formation cross-account sharing:

  • How grants work: the analytics account grants databases or tables (by name, or by LF-Tag expression) to an account, an organization, an OU or an IAM principal. AWS RAM carries the share, and the consumer's data lake administrator re-grants to local principals. Athena and Redshift Spectrum need resource links to the shared database or table.
  • Cross-account versions: version 3 adds tag-based sharing through RAM and direct grants to IAM principals; version 4 is needed to share hybrid-access-mode resources or federated catalogs; version 5 uses wildcard shares for very large numbers of tables and can't be downgraded.
  • Encryption: a catalog encrypted with the Glue service-managed key can't be shared; use a customer managed KMS key.

Redshift data sharing gives live, transactionally consistent access across clusters, workgroups, accounts and Regions with no copies:

  • Billing: the consumer pays the compute and the producer pays the storage.
  • Writes: consumers can be allowed to write (authorize-data-share --allow-writes) on RA3 or Serverless with snapshot isolation.
  • Limits: stored procedures and Python UDFs can't be shared.

AWS Clean Rooms lets companies analyse combined data without sharing the raw rows:

  • How it works: members create a collaboration and link configured tables that stay in their own S3, Athena, Snowflake or Databricks sources.
  • Analysis rules: each table carries one. Aggregation allows only aggregates with minimum counts, list allows overlap lists, and custom allows approved queries or PySpark jobs, with optional differential privacy.
  • Billing: the creator decides who pays for compute.

Discovery and access requests across the company go through Amazon DataZone (SageMaker Catalog in Unified Studio). Data Exchange handles licensed third-party data.

Share every table tagged domain=sales with a business-unit account (AWS CLI, in the analytics account) 
aws lakeformation grant-permissions \
    --principal DataLakePrincipalIdentifier=555555555555 \
    --permissions "SELECT" "DESCRIBE" \
    --permissions-with-grant-option "SELECT" "DESCRIBE" \
    --resource '{"LFTagPolicy":{"CatalogId":"444444444444","ResourceType":"TABLE","Expression":[{"TagKey":"domain","TagValues":["sales"]}]}}'
Clean Rooms aggregation rule: the partner can only count overlapping customers in groups of 100 or more (analysis rule policy) 
{
  "v1": {
    "aggregation": {
      "aggregateColumns": [
        { "columnNames": ["customer_hash"], "function": "COUNT_DISTINCT" }
      ],
      "joinColumns": ["customer_hash"],
      "joinRequired": "QUERY_RUNNER",
      "dimensionColumns": ["region", "loyalty_tier"],
      "scalarFunctions": ["CAST"],
      "outputConstraints": [
        { "columnName": "customer_hash", "minimum": 100, "type": "COUNT_DISTINCT" }
      ]
    }
  }
}

In Clean Rooms the most restrictive control across the tables in a query wins, rows below a threshold are dropped silently, and join columns can never be returned. Differential privacy and the custom-rule thresholds apply only to SQL; PySpark jobs need a separate configured table. A consumer account can't re-share a Lake Formation grant to another account.

Key takeaways

  • Lakehouse: S3 with Iceberg (or S3 Tables), the Glue Data Catalog and Lake Formation for permissions, Athena, EMR and Redshift (now writing Iceberg) as engines, zero-ETL from operational databases.
  • Pipelines: Kinesis or MSK (Express, Serverless) in, Flink for real time, Firehose to the lake, EMR Serverless or EMR on EC2 by utilization, AppFlow for SaaS sources.
  • Databases: RDS for engine needs, Aurora for MySQL and PostgreSQL, Limitless for write scale, DSQL for active-active relational, DynamoDB for key-value scale, purpose-built engines for graphs, documents and time series.
  • High availability: Multi-AZ instance or cluster, Aurora Global Database (switchover with no loss, failover with --allow-data-loss), DynamoDB global tables (eventual by default, strong with exactly 3 Regions).
  • Storage: S3 classes and Express One Zone, gp3 or io2 by IOPS, EFS for Linux shared files, FSx chosen by protocol and workload (Windows, ONTAP multi-protocol, OpenZFS, Lustre for HPC).
  • Caching and sharing: combine lazy loading, write-through and TTL; DAX query cache goes stale; Lake Formation tags and RAM for lake sharing, Redshift datashares for the warehouse, Clean Rooms for partners.
