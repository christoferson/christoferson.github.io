Task 2.4: Design architectures to meet compliance requirements

Turning regulations into architecture: protecting customer data end to end, keeping it (and the AI that processes it) inside a country or region, keeping audit trails that can't be altered, handing auditors evidence for both AWS's controls and yours, and finding the risks before an attacker does.

Overview

Task 2.4

Design architectures to meet compliance requirements.

This task reuses the building blocks of Tasks 2.1 (identity and perimeters), 2.2 (encryption) and 2.3 (organization-wide logging and controls) and asks how to combine them for a specific rule: "data must not leave the EU", "logs must be kept unaltered for seven years", "prove to the auditor that AWS's data centres are certified". Shared responsibility runs through all of it: AWS proves its side through Artifact reports, and you prove yours with configuration evidence.

Running example. Card and health data from US customers lives in us-east-1 under PCI DSS and HIPAA (a business associate addendum is accepted for the organization). A new EU business unit (account 555555555555) must keep EU customer data, and the AI support assistant's processing of it, inside the EU. Regulators require seven years of tamper-evident audit logs, including what the assistant was asked and answered.

Status changes to know. AWS Audit Manager is closed to new customers (use Config conformance packs and AWS Artifact), and CloudTrail Lake stopped accepting new customers on 31 May 2026 (CloudWatch is the suggested alternative; trails are unaffected). New: the AWS European Sovereign Cloud (January 2026, its own partition), the Well-Architected Digital Sovereignty Lens (updated September 2026), global cross-Region inference profiles in Bedrock (2025), the AWS Artifact Assurance Assistant for compliance questionnaires (June 2026), AgentCore Policy (generally available March 2026), and AWS Security Incident Response (December 2024).

Data protection

Skill 2.4.1Design architectures to meet data protection requirements (for example, by implementing encryption, access controls, audit logging).

  • Start from classification: tag data by sensitivity (Macie finds personal data in S3), and isolate regulated workloads in their own accounts and OUs so the scope of an audit (the PCI "cardholder data environment") stays small.
  • Encrypt with keys you control: customer managed KMS keys per data class, key policies that allow use only through the owning service, TLS 1.2 or later enforced in bucket and database settings. Tokenize or mask the most sensitive fields so most systems never see them.
  • Restrict access: least-privilege roles through Identity Center, ABAC on data tags, Lake Formation for column and row access, VPC endpoints with policies so data paths avoid the internet, and an RCP so no outside principal can reach regulated buckets or keys.
  • Log every access: CloudTrail management and data events (S3 object reads on regulated buckets), database audit logs (Aurora and RDS audit plugins or Database Activity Streams), and VPC Flow Logs, all delivered to the log archive account.
  • Detect and respond: GuardDuty, Macie and Security Hub CSPM standards (PCI DSS, NIST 800-53), with automated remediation through Config and EventBridge.
  • Use only services in scope for the program: AWS publishes which services are covered by each certification, and a BAA covers only HIPAA-eligible services.
Regulated bucket: refuse any request not using TLS 1.2 or later 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::example-cardholder-data",
        "arn:aws:s3:::example-cardholder-data/*"
      ],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    },
    {
      "Sid": "DenyOldTls",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::example-cardholder-data",
        "arn:aws:s3:::example-cardholder-data/*"
      ],
      "Condition": { "NumericLessThan": { "s3:TlsVersion": "1.2" } }
    }
  ]
}

"Reduce the scope of the PCI audit" points to a separate account or OU for cardholder data plus tokenization, not more controls on everything. "Prove who read a customer's file" needs S3 data events, which an organization trail doesn't record unless you add them.

Regulatory and sovereignty requirements

Skill 2.4.2Design solutions to meet regulatory requirements such as data sovereignty controls.

  • Sovereignty is more than location. AWS's Digital Sovereignty Pledge has four parts: control over where data is, verifiable control over who can access it, encryption everywhere, and resilience. Requirements usually combine residency (Skill 2.4.4) with limits on operator access and on foreign legal reach.
  • Operator access: the Nitro System is designed so that no one at AWS can access customer workloads on EC2, a claim independently reviewed by NCC Group (2023). For keys, use customer managed keys, a CloudHSM key store, or an external key store (XKS) when the keys must stay outside AWS.
  • AWS European Sovereign Cloud: a separate partition (aws-eusc, first Region in Brandenburg, Germany) run by EU-based EU residents, with its own billing, IAM, Route 53 and EU legal entities. It needs new accounts that can't interoperate with other AWS Regions, and its compliance reports are downloaded from Artifact inside the partition.
  • In-country options: Dedicated Local Zones are AWS infrastructure for one customer or community in a location they choose (for example, a government); Outposts run AWS services in your own data centre when data must stay on premises.
  • Design review: the Well-Architected Digital Sovereignty Lens asks about locality, access control, continuity, portability and transparency, and Control Tower's digital sovereignty controls implement much of the locality and access part.

A standard EU Region (Frankfurt, Ireland) gives data residency but not the separate operation and legal structure of the European Sovereign Cloud; if the requirement is "operated only by EU residents with no dependency on non-EU infrastructure", only the sovereign partition fits. Moving there means new accounts and copying data, not enabling a Region.

Audit trails for regulated workloads

Skill 2.4.3Implement audit trail management for regulated workloads, including for AI services.

  • Tamper-evident CloudTrail: turn on log file integrity validation. Every hour CloudTrail delivers a digest file with SHA-256 hashes of the log files, signed with RSA and chained to the previous digest, so deleted or edited files are detectable with validate-logs.
  • Tamper-proof storage: keep the trail and other logs in a log archive account bucket with SSE-KMS, versioning and S3 Object Lock.
    • Compliance mode: no one, not even the root user, can delete or shorten retention before it ends (assessed for SEC 17a-4, FINRA and CFTC rules).
    • Governance mode: users with s3:BypassGovernanceRetention can override it.
    • Legal holds: keep objects with no end date.
  • Retention in CloudWatch Logs: set a retention period on each log group (up to 10 years, or never expire), or an account-level retention policy by name prefix. An account policy overrides a log group's own setting, even a longer one, so check it with a dry run first.
  • AI services:
    • CloudTrail shows who invoked which model, and for cross-Region inference where it ran (additionalEventData.inferenceRegion).
    • Bedrock model invocation logs hold the full prompts and responses (same account and Region, then centralized as in Task 2.3) and inherit the bucket's Object Lock and retention.
    • Guardrail traces in responses record which policies intervened.
    • AgentCore Policy logs every allow or deny decision on agent tool calls.
  • Review checks: the Generative AI Lens (GENSEC03) asks how you monitor and audit control plane and data access to models, and the Agentic AI Lens asks that agent decisions be logged, traced and auditable.
Log archive bucket: 7-year compliance-mode retention by default 
aws s3api put-object-lock-configuration \
  --bucket example-audit-archive \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": { "DefaultRetention": { "Mode": "COMPLIANCE", "Years": 7 } }
  }'
Prove a month of organization trail files hasn't been changed 
aws cloudtrail validate-logs \
  --region us-east-1 \
  --trail-arn arn:aws:cloudtrail:us-east-1:111111111111:trail/org-trail \
  --account-id 555555555555 \
  --start-time 2026-10-01T00:00:00Z \
  --end-time 2026-11-01T00:00:00Z
# Validates only files still in their original S3 location;
# --account-id selects the member account's logs in an organization trail

Turning on validation only delivers digests; nothing checks them until you run validate-logs. With SSE-KMS and validation, a bucket policy that allows only aws:kms uploads breaks the trail. Compliance-mode Object Lock can't be undone: a test with a long retention leaves objects you can only remove by closing the account. Guardrail-blocked text still appears in plain text in invocation logs, so those logs are themselves regulated data.

Data residency

Skill 2.4.4Design data residency controls such as AWS Region-specific deployments and transfer restrictions.

  • Deploy per Region: separate stacks and accounts per jurisdiction (an EU OU with EU Regions only), global services configured to match (CloudFront geographic restrictions per distribution, Route 53 geolocation routing), and DR pairs inside the same jurisdiction (for example Frankfurt and Ireland).
  • Region deny: the Control Tower OU-level control (CT.MULTISERVICE.PV.1) takes a list of allowed Regions (which must include the home Region) and exempt principals; global services such as IAM, Organizations, CloudFront, Route 53 and KMS are exempt through NotAction. The landing zone Region deny applies to every governed OU.
  • Control Tower data residency controls also deny internet gateways, VPN connections and cross-Region networking (VPC and Transit Gateway peering, CloudFront distributions, Global Accelerator), plus detective rules for public exposure. None of them blocks S3 cross-Region replication or snapshot copies.
  • Transfer restrictions: Region deny stops copies that are requested in a denied Region (an EBS snapshot copy is called in the destination Region), but S3 replication is configured on the source bucket, so control who can set replication (s3:PutReplicationConfiguration, iam:PassRole) and restrict destinations to your organization's buckets. Detect drift with Config and Macie.
  • Bedrock cross-Region inference:
    • Geographic profiles (eu., us., apac.) keep processing inside the geography, which is the residency-safe choice. Data at rest stays in the source Region, though prompts and outputs may be stored in the destination Region for abuse detection.
    • Global profiles (global.) can route to any commercial Region, and to Regions your account hasn't enabled.
    • Allowing a geographic profile in an SCP means allowing every destination Region in the profile, or exempting calls by bedrock:InferenceProfileArn.
    • Global profiles appear in IAM with Region "unspecified". A Region-deny SCP with StringNotEquals silently blocks them, while one that lists denied Regions misses them.
SCP for the EU OU: no global cross-Region inference (geographic eu. profiles still work) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyGlobalCrossRegionInference",
      "Effect": "Deny",
      "Action": "bedrock:*",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "aws:RequestedRegion": "unspecified" },
        "ArnLike": {
          "bedrock:InferenceProfileArn": "arn:aws:bedrock:*:*:inference-profile/global.*"
        }
      }
    }
  ]
}

"EU customer prompts must be processed only in the EU" means an eu. geographic profile plus an SCP denying global profiles, with every EU destination Region allowed. "Block all Regions except two" is the OU Region deny control, not a hand-edited Control Tower SCP (edits cause drift). "No data may leave the country, and there's no Region there" points to Outposts or a Dedicated Local Zone.

Compliance evidence

Skill 2.4.5Implement compliance evidence collection and reporting solutions (for example, by using AWS Artifact).

  • AWS's side, from AWS Artifact: on-demand SOC, ISO, PCI and other reports (watermarked, for your auditors and regulators only), and agreements such as the HIPAA BAA, which the management account can accept for the whole organization. Fine-grained IAM permissions control who downloads which report series, and AWS User Notifications announce new reports. The Assurance Assistant drafts cited answers to security questionnaires about AWS's controls.
  • Your side, from your configuration:
    • Config conformance packs: compliance scores and history per framework.
    • Config advanced queries: point-in-time inventory exports.
    • Security Hub CSPM: standard scores and findings.
    • Logs: CloudTrail and invocation logs as the record of activity.
    • Backup Audit Manager: backup compliance reports.
  • Automate collection: deliver Config snapshots and Security Hub findings to the log archive account, query them with Athena or Security Lake, and schedule reports, rather than taking screenshots before each audit. Audit Manager isn't available to new customers, so don't propose it in a new design.
Download the latest SOC report for the auditors (CLI) 
aws artifact list-reports
aws artifact get-term-for-report \
  --report-id report-abcdef0123456789 --report-version 3
# Accept the terms, then use the returned term token
aws artifact get-report \
  --report-id report-abcdef0123456789 --report-version 3 \
  --term-token "<term token>"
# Returns documentPresignedUrl for the PDF

Artifact reports describe AWS's controls only; they're not evidence of your configuration. A BAA accepted in one account covers only that account; an organization agreement is accepted or ended only from the management account. Artifact reports for the European Sovereign Cloud are available only from accounts inside it.

Risk assessment and threat modeling

Skill 2.4.6Implement risk assessment solutions for cloud architectures such as threat modeling and mitigation strategies.

  • Threat model early and often: Well-Architected SEC01-BP07 rates skipping it as high risk. Use the four questions (what are we working on, what can go wrong, what are we going to do about it, did we do a good job), a data flow diagram, and STRIDE (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege) to find threats.
  • Threat Composer is AWS's open-source tool for writing threats in a consistent grammar, linking them to mitigations and exporting the model; run it in the browser, self-host it with CDK, or use the VS Code extension. It isn't a managed AWS service.
  • GenAI and agents: add the OWASP Top 10 for LLM applications and MITRE ATLAS (prompt injection, data poisoning, excessive agency, sensitive data disclosure), and aim for at least one preventive and one detective control per threat, such as Guardrails plus invocation logging (Task 2.5 covers these controls).
  • Prioritize and track: rank by likelihood and impact; record risks as high or medium risk issues in Well-Architected Tool reviews (custom lenses can encode your own questions and risk rules and are shareable across the organization); track mitigations to closure.
  • Validate continuously: Security Hub exposure findings show attack paths, Inspector shows exploitable vulnerabilities, Resilience Hub and FIS test resilience assumptions, and AWS Security Incident Response provides triage and responders when a risk turns into an incident.
Custom lens question: risk rules turn answers into high or medium risk issues 
{
  "id": "residency_q1",
  "title": "How do you keep AI processing of EU data inside the EU?",
  "choices": [
    { "id": "q1_geo", "title": "Only eu. geographic inference profiles are allowed" },
    { "id": "q1_scp", "title": "An SCP denies global inference profiles" },
    { "id": "q1_no", "title": "None of these" }
  ],
  "riskRules": [
    { "condition": "q1_geo && q1_scp", "risk": "NO_RISK" },
    { "condition": "q1_geo", "risk": "MEDIUM_RISK" },
    { "condition": "default", "risk": "HIGH_RISK" }
  ]
}

AWS Security Incident Response doesn't detect threats or triage compliance findings; it works from GuardDuty and Security Hub findings. A threat model done once at design time goes stale: revisit it when the architecture changes, for example when the assistant gains new tools.

Key takeaways

  • Data protection: classify, isolate regulated workloads to shrink audit scope, customer managed keys and enforced TLS, least privilege and perimeters, data events and database audit logs, in-scope services only.
  • Sovereignty: residency plus operator-access limits (Nitro, customer-controlled keys), the European Sovereign Cloud for separate EU operation, Dedicated Local Zones or Outposts for in-country needs.
  • Audit trails: CloudTrail validation digests, Object Lock compliance mode in the log archive, CloudWatch retention (beware account policies shortening it), invocation logs and AgentCore Policy decisions for AI.
  • Residency: per-Region deployments, the OU Region deny control, data residency controls, control over replication settings, Bedrock geographic profiles with global profiles denied by the "unspecified" Region.
  • Evidence and risk: Artifact for AWS's side, Config, Security Hub and logs for yours; threat model with STRIDE and Threat Composer, track risks in Well-Architected reviews, validate continuously.
