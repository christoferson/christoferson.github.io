Overview

Task 4.2

Design, implement, and troubleshoot authorization strategies.

Authorization questions are policy-reading questions: given an identity policy, a resource policy, an SCP, a boundary and a session policy, is the request allowed, and why not? The basic evaluation flow, policy types, permissions boundary delegation and SCPs and RCPs are in the Solutions Architect guide; this page covers the rules that decide specialty questions, the cross-account cases, and the tools that explain a denial. Organization-wide data perimeters are Task 6.1.

Running example. The same company. Teams own resources in their workload accounts, the security tooling account (222222222222) reads data from every account, an analytics account (777777777777) reads the data platform's S3 buckets and secrets, the customer application needs per-customer authorization inside the app, and project teams change often, so the platform team wants tag-based access.

Designing and evaluating authorization

Skill 4.2.1Design and evaluate authorization controls for human, application, and system access (for example, Amazon Verified Permissions, IAM paths, IAM Roles Anywhere, resource policies for cross-account access, IAM role trust policies).

How AWS reaches a decision

  1. Explicit deny anywhereAn explicit Deny in an SCP, RCP, resource-based policy, identity-based policy, permissions boundary or session policy ends evaluation with Deny.
  2. RCPsResource control policies on the resource's account must allow the action (the attached RCPFullAWSAccess allows everything until you add denies).
  3. SCPsService control policies on the principal's account must allow it.
  4. Resource-based policyAn Allow here can be enough on its own in the same account, depending on which principal it names.
  5. Identity-based policyOtherwise an identity policy must allow it.
  6. Permissions boundaryIf the principal has one, it must allow the action.
  7. Session policyIf the session was created with one, it must allow the action.

Same account: which principal the resource policy names matters

In one account, an Allow in either the identity policy or the resource policy is normally enough. But whether a resource policy grant escapes a permissions boundary or session policy depends on the principal it names:

  • An IAM user ARN: not limited by an implicit deny in the user's identity policy or boundary.
  • A role session ARN (arn:aws:sts::...:assumed-role/role/session): not limited by identity policy, boundary or session policy.
  • A role ARN: still limited by the role's boundary and session policy, whether in Principal or an aws:PrincipalArn condition, unless the policy uses "Principal": "*" with an aws:PrincipalArn condition.

An explicit deny in a boundary always wins. Two resource policies are exceptions to "either is enough": role trust policies and KMS key policies must explicitly allow the principal.

Cross-account: both sides must allow

For a request across accounts, AWS evaluates the caller's account (identity policy, SCPs, boundaries) and the resource's account (resource policy, RCPs) separately, and both must return Allow. Naming another account in Principal ("AWS": "arn:aws:iam::777777777777:root" or just the account ID) delegates to that whole account, whose administrator then decides which of its principals get access; it doesn't mean only the root user. A specific role ARN in Principal is stored as the role's unique ID (AROA...), so deleting and recreating the role breaks the policy; an aws:PrincipalArn condition survives recreation.

Cross-account resource policies

KMS keys

A key policy grants nothing to the account automatically. The default key policy's "Enable IAM User Permissions" statement (the account root as principal) is what makes IAM policies work at all; without it, IAM allows for the key have no effect (IAM denies still do). Cross-account use needs a key policy statement naming the other account or role and an IAM policy there allowing the key's ARN. Only cryptographic operations, grants and describe calls work across accounts; management calls such as ScheduleKeyDeletion never do.

Let the analytics account decrypt with the data platform key (two statements: the key policy in prod, the IAM policy in analytics) 
[
  {
    "Sid": "AllowAnalyticsAccountToUseKey",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::777777777777:role/analytics-etl" },
    "Action": ["kms:Decrypt", "kms:DescribeKey"],
    "Resource": "*"
  },
  {
    "Sid": "AllowUseOfProdDataKey",
    "Effect": "Allow",
    "Action": ["kms:Decrypt", "kms:DescribeKey"],
    "Resource": "arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab"
  }
]

Cryptographic operations accept the key ARN or an alias ARN from another account; grant operations need the key ARN. A bare key ID or alias name is always looked up in the caller's own account.

Secrets, functions, queues and repositories

  • Secrets Manager: a resource policy on the secret, an identity policy in the other account, and a customer managed KMS key, because the aws/secretsmanager key can't be used across accounts. Never grant secretsmanager:PutResourcePolicy to others; it lets them rewrite access. BlockPublicPolicy on PutResourcePolicy rejects public policies.
  • Lambda: a function resource policy (add-permission or put-resource-policy); new function URLs need both lambda:InvokeFunctionUrl and lambda:InvokeFunction.
  • SQS and SNS: queue and topic policies, with aws:SourceArn when another service sends.
  • ECR: a repository policy for pull and push, plus ecr:GetAuthorizationToken in the caller's IAM policy.
  • S3: a bucket policy (ACLs are disabled by default with bucket owner enforced), and for access points both the access point policy and the bucket policy (often delegating with s3:DataAccessPointAccount) must allow.
  • AWS RAM shares supported resources with the organization or OUs without listing accounts, and shared resources appear in the consumer's console; the managed permission is the maximum, and the consumer's IAM policies still apply.

Limit any resource policy to the organization with aws:PrincipalOrgID (or aws:PrincipalOrgPaths for OUs), paired with aws:PrincipalIsAWSService exceptions where AWS services write to the resource.

Role trust policies for third parties

A vendor assuming a role in your account should present an external ID that the vendor generates and keeps unique per customer, so another of its customers can't trick it into using your role (the confused deputy problem):

Trust a monitoring vendor's account only with your external ID (IAM role trust policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::999999999999:root" },
    "Action": "sts:AssumeRole",
    "Condition": { "StringEquals": { "sts:ExternalId": "vendor-assigned-7f3c2a" } }
  }
}

IAM paths

Grouping roles and policies for delegation

A path (for example /team-a/) puts users, roles and customer managed policies into named groups that ARNs can match with wildcards: arn:aws:iam::111111111111:role/team-a/*. Paths are set with the API, CLI or CloudFormation, not the console, and IAM enforces nothing by itself; their value is in policies. Team A's administrators can be allowed to create and attach only roles and policies under their path:

Team A manages only its own roles and policies (identity policy JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ManageTeamRoles",
      "Effect": "Allow",
      "Action": ["iam:CreateRole", "iam:PutRolePolicy", "iam:DeleteRole", "iam:TagRole"],
      "Resource": "arn:aws:iam::111111111111:role/team-a/*"
    },
    {
      "Sid": "AttachOnlyTeamPolicies",
      "Effect": "Allow",
      "Action": "iam:AttachRolePolicy",
      "Resource": "arn:aws:iam::111111111111:role/team-a/*",
      "Condition": { "ArnLike": { "iam:PolicyARN": "arn:aws:iam::111111111111:policy/team-a/*" } }
    }
  ]
}

A role's path can't be changed after creation (only users and groups can move), and role names are unique across paths. Service-linked roles live under /aws-service-role/ and Identity Center roles under /aws-reserved/sso.amazonaws.com/, which is how policies and SCPs exempt or target them.

Systems outside AWS: Roles Anywhere profiles

Limiting what certificate holders get

The trust policy (Task 4.1) decides which certificates can assume a role; condition it on both the subject and the issuer, or any certificate from the CA or its subordinates qualifies. The profile then limits the session: which roles it covers, managed or inline session policies, and duration (up to 12 hours). Attribute mapping decides which certificate fields become principal tags for conditions:

Map only the subject CN and OU into session tags (AWS CLI) 
aws rolesanywhere put-attribute-mapping \
  --profile-id a1b2c3d4-5678-90ab-cdef-EXAMPLE11111 \
  --certificate-field x509Subject \
  --mapping-rules specifier=CN specifier=OU

Since May 2026, VPC endpoint policies apply to Roles Anywhere CreateSession, so a restrictive endpoint policy can block credential issuance.

Authorization inside your application

Amazon Verified Permissions

IAM authorizes calls to AWS. For decisions inside your own application (can this customer view this order?), Amazon Verified Permissions stores Cedar policies in a policy store with a schema, and the app asks it with IsAuthorized (or IsAuthorizedWithToken, passing a Cognito or OIDC token so the principal comes from the token). Forbid always overrides permit, and with no matching policy the answer is deny.

Customers can read their own orders (Cedar policy) 
permit (
  principal in Shop::Role::"Customer",
  action == Shop::Action::"GetOrder",
  resource
) when {
  resource.owner == principal
};
  • Policy templates with ?principal and ?resource placeholders create template-linked policies, for example "share this order with this user"; changing the template changes every linked policy.
  • Validation mode STRICT checks policies against the schema; with no schema, every policy fails, so define the schema first.
  • API Gateway integration builds a Lambda authorizer that calls Verified Permissions for each request (caching decisions for 120 seconds by default).
  • Pricing fell to $5 per million single authorization requests in June 2025.

"Fine-grained permissions inside our SaaS app, managed outside the code" points to Verified Permissions. "Another account must read our encrypted secret" points to a secret resource policy plus a customer managed key. "Give a vendor access to our account" points to a role with an external ID.

ABAC and RBAC

Skill 4.2.2Design attribute-based access control (ABAC) and role-based access control (RBAC) strategies (for example, by configuring resource access based on tags or attributes).

Choosing between them

RBACABAC
Permissions follow
A job function: a role or permission set per job (developer, auditor, DBA)Attributes: tags on the principal match tags on the resource
When something new appears
Update policies to list the new resources or create new rolesTag the new resource or person; no policy change
Watch out for
Role explosion as teams and projects multiplyAnyone who can change tags can change access; not every action supports tag conditions

Most organizations combine them: Identity Center permission sets by job function (RBAC), with ABAC conditions inside them so one permission set serves every project.

Building ABAC

The condition keys

  • aws:PrincipalTag/key: a tag on the user or role, or a session tag passed at sign-in.
  • aws:ResourceTag/key: a tag on the resource being accessed (only for resources that support tag-based authorization).
  • aws:RequestTag/key and aws:TagKeys: tags in a create or tag request, used to require and restrict tags.

Tag keys are case-insensitive in conditions, values case-sensitive. The decisive part of an ABAC design is protecting the tags themselves: deny changing the access tags on resources and principals, and require them at creation.

Project teams manage only their project's secrets, must tag new ones, and can't remove access tags (identity policy JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SameProjectSameTeam",
      "Effect": "Allow",
      "Action": "secretsmanager:*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/access-project": "${aws:PrincipalTag/access-project}",
          "aws:ResourceTag/access-team": "${aws:PrincipalTag/access-team}"
        },
        "StringEqualsIfExists": {
          "aws:RequestTag/access-project": "${aws:PrincipalTag/access-project}",
          "aws:RequestTag/access-team": "${aws:PrincipalTag/access-team}"
        },
        "ForAllValues:StringEquals": { "aws:TagKeys": ["access-project", "access-team", "Name", "OwnedBy"] }
      }
    },
    {
      "Sid": "DenyRemovingAccessTags",
      "Effect": "Deny",
      "Action": "secretsmanager:UntagResource",
      "Resource": "*",
      "Condition": { "ForAnyValue:StringLike": { "aws:TagKeys": "access-*" } }
    },
    {
      "Sid": "DenyPolicyManagement",
      "Effect": "Deny",
      "Action": "secretsmanager:*Policy",
      "Resource": "*"
    }
  ]
}

For EC2, tagging at launch also authorizes ec2:CreateTags; allow it only during creation with the ec2:CreateAction condition (for example "ec2:CreateAction": "RunInstances"), and require tags with aws:RequestTag on the creating action.

Attributes from the identity provider

Session tags carry directory attributes (department, cost center, project) into AWS. With direct IAM SAML federation the IdP sends https://aws.amazon.com/SAML/Attributes/PrincipalTag:CostCenter (and the trust policy must allow sts:TagSession). With IAM Identity Center, turn on attributes for access control; the IdP sends https://aws.amazon.com/SAML/Attributes/AccessControl:CostCenter, or Identity Center maps its own user attributes, which take precedence. Either way, policies read them as ${aws:PrincipalTag/CostCenter}. Up to 50 session tags; transitive tags survive role chaining; session tags override role tags with the same key.

An ABAC policy is only as strong as the controls on tagging. If developers can run iam:TagRole on their own role or ec2:CreateTags on any instance, they can give themselves another project's access. Deny tagging of the access keys outside the creation path, and keep principal tags under central control (Identity Center attributes or SCIM).

Least privilege policies

Skill 4.2.3Design, interpret, and implement IAM policies by following the principle of least privilege (for example, permission boundaries, session policies).

Limits that only take away

Boundaries and session policies

A permissions boundary (a managed policy set on a user or role) and a session policy (passed when a role session is created: one inline policy and up to 10 managed policy ARNs, 2,048 characters combined) grant nothing; effective permissions are the intersection with identity policies (and SCPs). Boundaries suit delegation: teams create roles only with the team boundary attached (the pattern is in the Solutions Architect guide). Session policies suit a broker or application that assumes one role for many users and narrows each session, for example to one customer's S3 prefix. Remember the resource policy rules above: a boundary doesn't cap what a resource policy grants directly to a user or session.

Policy elements that grant more than they look

NotAction, NotPrincipal and conditions

  • NotAction with Allow allows every action in every service except those listed, including services launched later. Prefer explicit actions; use NotAction mainly in Deny statements.
  • NotPrincipal works only with Deny, can't be used in identity, trust, SCP or RCP policies, always denies principals that have a permissions boundary, and AWS no longer recommends it. Use "Principal": "*" with an aws:PrincipalArn condition instead.
  • Missing keys: a condition on a key absent from the request is false, but negated operators (StringNotEquals) are true. ...IfExists treats a missing key as true, and a Deny with StringNotEqualsIfExists still denies when the key is absent.
  • ForAllValues returns true when the key is missing or empty, so an Allow with it can allow requests with no tags at all; add "Null": {"aws:TagKeys": "false"}. Don't use set operators with single-valued keys such as aws:PrincipalTag.
  • Policy variables need "Version": "2012-10-17"; without it ${aws:username} is a literal string.
Deny the audit bucket to everyone except the auditor role, without NotPrincipal (S3 bucket policy statement, JSON) 
{
  "Sid": "OnlyAuditorRole",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::audit-evidence-444444444444", "arn:aws:s3:::audit-evidence-444444444444/*"],
  "Condition": { "ArnNotEquals": { "aws:PrincipalArn": "arn:aws:iam::222222222222:role/auditor" } }
}

Getting to least privilege

IAM Access Analyzer policy tools

  • Policy generation (free) builds a policy from up to 90 days of the role's CloudTrail activity. It can't see iam:PassRole or data events such as S3 object reads, so review and add those.
  • Policy validation (free) reports errors, security warnings (such as PASS_ROLE_WITH_STAR_IN_RESOURCE, FORALLVALUES_WITH_SINGLE_VALUED_KEY, MISSING_GITHUB_REPO_CONDITION_KEY), warnings and suggestions, in the console editor or with validate-policy.
  • Custom policy checks ($2 per 1,000 calls) answer yes or no in a pipeline: does a new policy grant more than the old one (check-no-new-access), does a policy grant any of these sensitive actions (check-access-not-granted), does a resource policy allow public access (check-no-public-access)?
Fail the build if a policy change adds access, or if any policy allows deleting backups (AWS CLI in a pipeline) 
aws accessanalyzer check-no-new-access \
  --existing-policy-document file://deployed-policy.json \
  --new-policy-document file://proposed-policy.json \
  --policy-type IDENTITY_POLICY
# {"result": "FAIL", "message": "The modified permissions grant new access compared to your existing policy.", ...}

aws accessanalyzer check-access-not-granted \
  --policy-document file://proposed-policy.json \
  --access actions="backup:DeleteRecoveryPoint","backup:DeleteBackupVault" \
  --policy-type IDENTITY_POLICY

Quotas that shape designs

Managed policies attached to a role now default to 20 (maximum 25; it was 10 until August 2026); users default to 10. A managed policy holds 6,144 characters; inline policies per role 10,240 in total. Customer managed policies keep 5 versions. Role session duration is 1 to 12 hours. Hitting these limits usually means the policies should be restructured, not the quota raised.

Analyzing authorization failures

Skill 4.2.4Analyze authorization failures to determine causes or effects (for example, IAM Policy Simulator, IAM Access Analyzer).

Reading the error

Access denied messages name the policy type

Most services now say which policy type denied the request, and whether the deny was explicit (a Deny statement matched) or implicit (nothing allowed it). Since January 2026, explicit denies in SCPs, RCPs, identity policies, session policies and boundaries also include the ARN of the policy, within the same account or organization; inline policies show no ARN, and only one policy type is reported even if several denied.

The message tells you where to look (examples of AccessDenied messages) 
User: arn:aws:iam::111111111111:role/orders-api is not authorized to perform: secretsmanager:GetSecretValue
on resource: arn:aws:secretsmanager:us-east-1:111111111111:secret:*
with an explicit deny in a resource control policy: arn:aws:organizations::555555555555:policy/o-exampleorgid/resource_control_policy/p-examplepolicyid456

User: arn:aws:iam::111111111111:role/orders-api is not authorized to perform: codedeploy:ListDeployments
because no permissions boundary allows the codedeploy:ListDeployments action

User: arn:aws:iam::111111111111:user/ops-break-glass is not authorized to perform: sts:AssumeRole
because no role trust policy allows the sts:AssumeRole action
  • "No identity-based policy allows": add a permission to the caller.
  • "No permissions boundary allows" or "no session policy allows": the identity policy may be fine; the limit isn't.
  • "Explicit deny in a service control policy" or "resource control policy": an organization guardrail; changing local IAM won't help.
  • "No VPC endpoint policy allows": the endpoint policy on the path, which may belong to another account.

S3 gives the same detail within the account or organization (phrased "with policy ARN:"), but a generic "Access Denied" across organizations and none for VPC endpoint denials. S3 Block Public Access denials say which setting blocked the request. EC2 returns an encoded authorization message; decode it with aws sts decode-authorization-message --encoded-message ... (needs sts:DecodeAuthorizationMessage) to see the matched statement and context.

The IAM policy simulator

Testing a principal against actions and resources

The policy simulator, now part of the IAM console (July 2026), evaluates a principal's identity policies, permissions boundary, SCPs and a resource policy you supply against actions, resources and context keys you set. It doesn't evaluate RCPs, doesn't show which SCP statement matched, and in the console fetches resource policies only for S3, SQS, SNS and Glacier. Context keys other than the principal's own must be supplied, or conditions on them won't match.

Would the ETL role be allowed to read the object at the time of the job? (AWS CLI) 
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::777777777777:role/analytics-etl \
  --action-names s3:GetObject \
  --resource-arns arn:aws:s3:::shop-data-111111111111/orders/2026/11/09.parquet \
  --context-entries "ContextKeyName=aws:SourceVpce,ContextKeyValues=vpce-0abc1234def567890,ContextKeyType=string"
# EvalDecision: allowed | explicitDeny | implicitDeny, with MatchedStatements and MissingContextValues

The output now has one result per action, with per-resource decisions in ResourceSpecificResults, and --policy-exclusion-list lets you test what happens without a given policy.

Common causes by service

  • KMS: the key policy lacks the account root statement (so IAM allows don't count), or, across accounts, either the key policy or the caller's IAM policy is missing. S3 SSE-KMS uploads need kms:GenerateDataKey, downloads kms:Decrypt.
  • AssumeRole: the trust policy doesn't name the caller (or names a deleted and recreated role), the caller's own policy or boundary doesn't allow sts:AssumeRole, or a condition (external ID, MFA, source identity) isn't met.
  • S3: bucket policy deny, Block Public Access, object owned by another account with ACLs, or a VPC endpoint policy.
  • Cross-account generally: only one side allows. CloudTrail in the caller's account shows the error; the resource account may not log the denied attempt.

"The policy simulator says allowed but the call fails" points to something the simulator doesn't see: an RCP, a VPC endpoint policy, a missing context key, or a resource policy that wasn't supplied.

Correcting unintended permissions

Skill 4.2.5Investigate and correct unintended permissions, authorizations, or privileges granted to a resource, service, or entity (for example, IAM Access Analyzer).

IAM Access Analyzer findings

Three analyzer types

  • External access (free, per Region): resources whose policies grant access outside the zone of trust (the account or the organization): S3 buckets, IAM role trust policies, KMS keys, Lambda functions and layers, SQS queues, Secrets Manager secrets, SNS topics, EBS and RDS snapshots, ECR repositories, EFS file systems, and DynamoDB tables and streams. Policies are re-analyzed within about 30 minutes of a change. Archive rules auto-archive findings for intended sharing (for example, the analytics account). Access previews show what a policy change would expose before you apply it.
  • Internal access (June 2025, $9 per monitored resource per month): which principals inside the organization or account can reach chosen critical resources (S3 buckets, RDS snapshots, DynamoDB tables and streams).
  • Unused access ($0.20 per role or user per month): unused roles, access keys, passwords and permissions over a tracking period you set (1 to 365 days), with recommended policies to remove the unused permissions.

An external access analyzer only covers the Region it's created in, so an organization needs one in every Region it uses (the delegated administrator in the security tooling account usually creates them all). A finding marked resolved means the access was removed; an archived finding means someone accepted it, which is worth reviewing periodically.

Other sources of unintended privilege

Credentials and escalation paths

The IAM credential report (at most every four hours) lists every user's password, MFA and access key status and last use, which finds old keys and users without MFA. Beyond that, look for permissions that let a principal give itself more. AWS doesn't publish one list, but these combinations follow directly from how IAM works:

  • iam:PassRole on any role plus lambda:CreateFunction or ec2:RunInstances: run code with a more powerful role.
  • iam:CreatePolicyVersion or iam:SetDefaultPolicyVersion on a policy attached to yourself; iam:AttachUserPolicy, iam:PutRolePolicy or iam:AddUserToGroup on yourself.
  • iam:CreateAccessKey or iam:CreateLoginProfile on other users; iam:UpdateAssumeRolePolicy on a privileged role.
  • KMS key administrators changing the key policy; secretsmanager:PutResourcePolicy on secrets; tag permissions in an ABAC design.

Access Analyzer validation flags the wide iam:PassRole patterns; scope PassRole with iam:PassedToService and role paths (Task 3.2), protect boundary policies from edits, and restrict IAM changes with SCPs.

Correcting

Fix the policy at its source (the bucket policy, the trust policy, the key policy) rather than adding denies elsewhere; replace wide grants with organization conditions (aws:PrincipalOrgID); remove unused roles and keys found by the unused access analyzer; and stop the same mistake returning with custom policy checks in the pipeline and preventive SCPs and RCPs. After the change, Access Analyzer marks the finding resolved, which is the confirmation.

"Find every resource shared with accounts outside the organization" points to an external access analyzer with the organization as zone of trust. "Which of our own roles can read the customer database snapshots" points to an internal access analyzer. "Remove permissions roles haven't used in 90 days" points to an unused access analyzer or policy generation.

Key takeaways

  • Evaluation: any explicit deny, then RCPs, SCPs, resource policy, identity policy, boundary, session policy. Same account: a resource policy naming a user or session ARN escapes boundaries; naming a role ARN doesn't. Trust policies and KMS key policies must always allow explicitly. Cross-account: both sides must allow.
  • An account in Principal delegates to the whole account; role ARNs are stored as unique IDs (recreating breaks them). KMS cross-account needs key policy plus IAM policy; Secrets Manager cross-account needs a customer managed key; external IDs for vendors.
  • Paths group roles and policies for delegation (role/team-a/*) and can't be changed on roles. Roles Anywhere profiles and attribute mapping limit certificate sessions. Verified Permissions with Cedar for in-app authorization (STRICT needs a schema).
  • ABAC with aws:PrincipalTag, aws:ResourceTag, aws:RequestTag and aws:TagKeys; protect the tags; session tags via PrincipalTag: (IAM SAML) or AccessControl: (Identity Center) attributes. RBAC by job function; combine both.
  • Least privilege: boundaries and session policies only reduce; beware NotAction allows, NotPrincipal, ForAllValues on empty sets and negated IfExists denies. Access Analyzer generation (no PassRole or data events), validation and custom checks in pipelines. Roles now take 20 managed policies by default.
  • Failures: AccessDenied names the policy type, explicit or implicit, and now the policy ARN; decode EC2 messages with STS; the simulator covers SCPs but not RCPs or VPC endpoint policies.
  • Unintended access: external (per Region, archive rules, access previews), internal (critical resources) and unused access analyzers; credential report; known escalation combinations around PassRole and policy editing.
