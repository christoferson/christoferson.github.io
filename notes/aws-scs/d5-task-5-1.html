Task 5.1: Design and implement controls for data in transit

Making sure data is encrypted while it moves: TLS required at every listener and endpoint with modern policies, private paths that never touch the internet, and encryption between the instances, containers and nodes inside a cluster.

Overview

Task 5.1

Design and implement controls for data in transit.

Domain 5 is 18% of the exam. In-transit questions usually turn on a default that isn't what you'd expect (a listener created from the CLI accepting TLS 1.0, a load balancer that doesn't check the target's certificate, a Direct Connect link that isn't encrypted), or on choosing between TLS at the application and encryption the network provides. Encrypting links to on premises (VPN, MACsec) is in Task 3.3; CloudFront viewer TLS and mutual TLS in Task 3.1; private certificate authorities in Task 5.3.

Running example. The same company. The web application and APIs run behind CloudFront, an Application Load Balancer and API Gateway; data sits in Aurora MySQL, RDS for PostgreSQL, ElastiCache for Valkey, OpenSearch and MSK; the analytics team runs EMR and SageMaker AI training jobs; containers run on EKS and on ECS with Service Connect; and a payments partner offers its API to the company through PrivateLink.

Status changes. AWS App Mesh reached end of support on 30 September 2026; its console and resources are no longer accessible, so service mesh answers now point to ECS Service Connect, VPC Lattice or open-source meshes on EKS. All AWS API endpoints require at least TLS 1.2 (since February 2024) and support TLS 1.3 (since June 2024). The RDS rds-ca-2019 certificate authority expired in August 2024.

Requiring encryption on connections

Skill 5.1.1Design and configure mechanisms to require encryption when connecting to resources (for example, by configuring Elastic Load Balancing [ELB] security policies, by enforcing TLS configurations).

Load balancer security policies

Choosing the policy

An ALB HTTPS listener or NLB TLS listener uses a predefined security policy for TLS versions and ciphers. Names describe them: TLS13-1-2 supports TLS 1.3 with a minimum of 1.2, TLS13-1-3 is TLS 1.3 only, Res means a restricted cipher set, FIPS uses FIPS-validated cryptography, and PQ (2025-09) adds hybrid post-quantum key exchange (ML-KEM) for clients that support it while staying compatible with others. AWS now recommends ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09 (or its FIPS variant). ALBs don't accept custom policies; Classic Load Balancers do.

The default policy depends on how the listener is created. The console uses the PQ TLS 1.3 policy, but the CLI, CloudFormation and CDK use ELBSecurityPolicy-2016-08, which still allows TLS 1.0 and 1.1. Always set the policy in infrastructure as code. Also note that the long-recommended ELBSecurityPolicy-TLS13-1-2-2021-06 no longer passes Security Hub CSPM control ELB.17.

An HTTPS listener with the post-quantum policy, and port 80 redirecting to it (AWS CLI) 
aws elbv2 create-listener \
  --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:111111111111:loadbalancer/app/shop-web/50dc6c495c0c9188 \
  --protocol HTTPS --port 443 \
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09 \
  --certificates CertificateArn=arn:aws:acm:us-east-1:111111111111:certificate/12345678-1234-1234-1234-123456789012 \
  --default-actions Type=forward,TargetGroupArn=arn:aws:elasticloadbalancing:us-east-1:111111111111:targetgroup/shop-web/73e2d6bc24d8a067

aws elbv2 create-listener \
  --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:111111111111:loadbalancer/app/shop-web/50dc6c495c0c9188 \
  --protocol HTTP --port 80 \
  --default-actions '[{"Type": "redirect", "RedirectConfig": {"Protocol": "HTTPS", "Port": "443", "Host": "#{host}", "Path": "/#{path}", "Query": "#{query}", "StatusCode": "HTTP_301"}}]'

To stop teams creating weak listeners, IAM and SCP conditions can test elasticloadbalancing:ListenerProtocol (HTTPS, TLS) and elasticloadbalancing:SecurityPolicy on CreateListener and ModifyListener. Security Hub CSPM controls ELB.1 (HTTP redirects to HTTPS), ELB.17 (recommended policies), ELB.18 (encrypted listeners), ELB.21 (encrypted health checks) and ELB.22 (encrypted target groups) cover ALBs and NLBs; ELB.2, ELB.3 and ELB.8 are for Classic Load Balancers.

Behind the listener

  • Re-encryption: HTTPS or TLS target groups encrypt from the load balancer to targets. The load balancer doesn't validate target certificates (self-signed or expired ones work), and you can't choose the backend policy; it's derived from the listener policies. CloudFront, by contrast, does validate origin certificates and returns 502 for a self-signed or expired one.
  • End-to-end TLS: an ALB always terminates TLS. If the target itself must decrypt (or do client-certificate checks itself), use an NLB with a TCP listener on 443, which passes TLS through untouched.
  • Mutual TLS on ALB: in verify mode the ALB checks client certificates against a trust store (CA bundle and optional CRLs from S3, from AWS Private CA or another CA); in passthrough mode it forwards the certificate chain to targets in the X-Amzn-Mtls-Clientcert header for them to verify. NLB doesn't do mutual TLS.
Require partner client certificates on the API listener (AWS CLI) 
aws elbv2 create-trust-store --name partner-cas \
  --ca-certificates-bundle-s3-bucket shop-pki-111111111111 \
  --ca-certificates-bundle-s3-key trust/partner-ca-bundle.pem

aws elbv2 modify-listener \
  --listener-arn arn:aws:elasticloadbalancing:us-east-1:111111111111:listener/app/shop-api/50dc6c495c0c9188/f2f7dc8efc522ab2 \
  --mutual-authentication "Mode=verify,TrustStoreArn=arn:aws:elasticloadbalancing:us-east-1:111111111111:truststore/partner-cas/73e2d6bc24d8a067"

Requiring TLS service by service

S3 and other resource policies

S3 accepts HTTP unless a bucket policy denies it. Deny requests where aws:SecureTransport is false (Security Hub CSPM control S3.5), and optionally require a minimum version with s3:TlsVersion, a numeric key. Because AWS services calling S3 on your behalf don't carry this network context, AWS recommends excluding them with aws:PrincipalIsAWSService:

TLS only, version 1.2 or later, for callers other than AWS services (S3 bucket policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::shop-data-111111111111", "arn:aws:s3:::shop-data-111111111111/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false", "aws:PrincipalIsAWSService": "false" } }
    },
    {
      "Sid": "DenyOldTls",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::shop-data-111111111111", "arn:aws:s3:::shop-data-111111111111/*"],
      "Condition": {
        "NumericLessThan": { "s3:TlsVersion": "1.2" },
        "Bool": { "aws:PrincipalIsAWSService": "false" }
      }
    }
  ]
}

SNS topic and SQS queue policies use the same aws:SecureTransport deny pattern; encrypting a topic or queue with KMS protects data at rest and doesn't reject HTTP. S3 website endpoints don't support HTTPS at all; put CloudFront in front.

Databases and caches

  • RDS for PostgreSQL: rds.force_ssl (default on for PostgreSQL 15 and later). RDS for MySQL: require_secure_transport, no reboot. Aurora MySQL: require_secure_transport is a cluster parameter (on by default from 8.4). RDS for SQL Server: rds.force_ssl is static, so it needs a reboot. DocumentDB: the tls parameter is on by default and static. Redshift: require_ssl. Neptune accepts only TLS.
  • RDS certificates: the default CA is now rds-ca-rsa2048-g1 (with RSA 4096 and ECC 384 options); move instances with aws rds modify-db-instance --ca-certificate-identifier rds-ca-rsa2048-g1, and have clients trust the RDS root bundle and verify the hostname (for PostgreSQL, sslmode=verify-full).
  • ElastiCache (Valkey, Redis OSS): in-transit encryption encrypts client and node-to-node traffic. On an existing replication group, switch --transit-encryption-mode to preferred, move clients to TLS, then to required. Memcached TLS can only be set at creation. TLS 1.2 has been the minimum since April 2026; ElastiCache doesn't do mutual TLS.
  • OpenSearch: EnforceHTTPS with a TLS policy such as Policy-Min-TLS-1-2-PFS-2023-10, and node-to-node encryption, which is required for fine-grained access control and can't be turned off once on.
  • MSK: client-broker encryption (TLS only by default) and in-cluster encryption between brokers (on by default, set at creation), and since 2026 TLS security policies such as MSK-TLSv1.3-2026.

API Gateway

REST APIs choose a security policy, and the defaults are weak: Regional and edge-optimized REST APIs default to TLS_1_0 (private APIs and custom domains to TLS_1_2). The newer enhanced policies (SecurityPolicy_TLS13_1_3_2025_09, PQ and FIPS variants) require an endpoint access mode; STRICT also rejects requests arriving through the wrong endpoint type or with mismatched host names. HTTP and WebSocket APIs are fixed at TLS 1.2.

TLS 1.3 only, and strict endpoint access, for the orders API (AWS CLI) 
aws apigateway update-rest-api --rest-api-id a1b2c3d4e5 \
  --patch-operations '[{"op": "replace", "path": "/securityPolicy", "value": "SecurityPolicy_TLS13_1_3_2025_09"},
                       {"op": "replace", "path": "/endpointAccessMode", "value": "STRICT"}]'

AWS suggests BASIC first, checking access logs ($context.tlsVersion), then STRICT.

Certificates

AWS Certificate Manager

ACM issues public certificates for ELB, CloudFront, API Gateway and other integrated services, with DNS validation and managed renewal (the private key never leaves AWS). Public certificates are now valid for 198 days, following the CA/Browser Forum schedule (shorter again from March 2027), and ACM renews them 45 days before expiry if they're in use and the validation CNAME records still exist. Imported certificates are never renewed by ACM; watch their expiry with the ACM certificate expiration events. Exportable public certificates (with their private key, for EC2, containers or on premises) are a paid option, and ACM now also supports ACME-based issuance, but those certificates can't be attached to ELB, CloudFront or API Gateway. Internal certificates come from AWS Private CA (Task 5.3).

"Encrypt end to end, including from the load balancer to the instances" points to an HTTPS target group (or NLB TCP passthrough). "Clients must present a certificate" points to ALB mutual TLS in verify mode. "Make sure no listener allows TLS 1.0" points to a modern security policy set explicitly plus an SCP condition and Security Hub ELB.17.

Other types: Gateway Load Balancer endpoints (inspection appliances), service network endpoints (all services in a VPC Lattice service network through one endpoint) and newer tunnel endpoints. Every endpoint can carry an endpoint policy, which by default allows everything; the organization data perimeter version is in Task 3.3.

DNS for interface endpoints

With private DNS enabled (the VPC needs DNS hostnames and DNS support), the service's normal name, such as kms.us-east-1.amazonaws.com, resolves to the endpoint's private IPs, so SDKs need no changes. On-premises clients can't use the VPC resolver directly; they need Route 53 Resolver inbound endpoints and forwarding rules. Deploy endpoints in at least two Availability Zones.

S3: gateway and interface together

A gateway endpoint is free but only serves the VPC; on-premises servers need an S3 interface endpoint. With both, the interface endpoint's private DNS only for inbound endpoints option keeps VPC traffic on the free gateway endpoint and sends only traffic arriving through the inbound Resolver endpoint to the interface endpoint:

S3 interface endpoint for the warehouses, while VPC traffic keeps using the gateway endpoint (AWS CLI) 
aws ec2 create-vpc-endpoint --region us-east-1 \
  --vpc-id vpc-0shop1234567890ab \
  --vpc-endpoint-type Interface \
  --service-name com.amazonaws.us-east-1.s3 \
  --subnet-ids subnet-0app1a234567890ab subnet-0app1b234567890ab \
  --security-group-ids sg-0s3endpoint123456 \
  --private-dns-enabled \
  --dns-options PrivateDnsOnlyForInboundResolverEndpoint=true

S3 interface endpoints support only TLS 1.2: no TLS 1.3 and no post-quantum TLS. A requirement for TLS 1.3 to S3 can't be met through an interface endpoint. Gateway endpoints can't be reached from on premises or another Region at all.

PrivateLink for your own services

Endpoint services

The payments partner exposes its API as an endpoint service in front of a Network Load Balancer (or a Gateway Load Balancer for appliances). Nobody can connect until the provider adds allowed principals (accounts, roles or users; * with automatic acceptance would make it effectively public), and with acceptance required the provider approves each endpoint connection. Traffic flows only from consumer to provider; the provider can't open connections into the consumer's VPC. A private DNS name for the service requires the provider to prove ownership of the domain with a TXT record. The provider sees the NLB's addresses as the source unless Proxy Protocol v2 is enabled.

Cross-Region PrivateLink

Interface endpoints can now reach endpoint services, and a set of AWS services (S3, IAM, KMS, ECR, ECS, Lambda, Data Firehose, Managed Service for Apache Flink and Route 53), in another Region. The caller needs the permission-only action vpce:AllowMultiRegion, allowed in both IAM and SCPs, and the condition keys ec2:VpceServiceRegion and ec2:VpceSupportedRegion restrict which Regions are allowed, which is how data residency rules are enforced. Only Regional DNS names work across Regions, and PrivateLink doesn't fail over between Regions.

An endpoint in us-east-1 for S3 in us-west-2 (AWS CLI) 
aws ec2 create-vpc-endpoint --region us-east-1 \
  --vpc-id vpc-0shop1234567890ab \
  --vpc-endpoint-type Interface \
  --service-name com.amazonaws.us-west-2.s3 \
  --service-region us-west-2 \
  --subnet-ids subnet-0app1a234567890ab subnet-0app1b234567890ab

Users: Client VPN and Verified Access

For people rather than workloads, Client VPN gives TLS-encrypted network access to VPC ranges, and Verified Access gives per-application access over HTTPS (or TCP through its client) checked against identity and device posture, both covered with their policies in Task 3.3. Either way the traffic is encrypted and no application is exposed to the internet.

"On-premises servers must reach S3 privately over Direct Connect" points to an S3 interface endpoint (not a gateway endpoint) with inbound Resolver DNS. "Offer our service to customer VPCs without peering or exposing our network" points to a PrivateLink endpoint service. "Private access to one database in another account without a load balancer" points to a resource endpoint.

Encryption between resources

Skill 5.1.3Design and configure inter-resource encryption in transit (for example, inter-node encryption configurations for Amazon EMR, Amazon EKS, SageMaker AI, Nitro encryption).

What AWS encrypts for you

The network and Nitro

AWS encrypts traffic between Availability Zones and across Regions at the physical layer, and cross-Region peering and Transit Gateway peering traffic when it leaves a Region. Between instances, many current instance types use the Nitro system to encrypt traffic automatically (256-bit AEAD, no performance cost), but only when all three conditions hold:

  • both instances are supported types (for example M6i, C7g, R8g, the "n" variants such as M5n and C5n; not older M5, C5 or T3);
  • they're in the same Region;
  • they're in the same VPC or peered VPCs, and the traffic doesn't pass through a load balancer, transit gateway or similar device.
Which instance types encrypt traffic between instances automatically (AWS CLI) 
aws ec2 describe-instance-types \
  --filters Name=network-info.encryption-in-transit-supported,Values=true \
  --query "InstanceTypes[*].InstanceType" --output text

VPC Encryption Controls (Task 1.2 shows the flow log field) turns this into a guarantee: monitor mode reports unencrypted flows, and enforce mode blocks resources that can't encrypt. In enforce mode an NLB can't offload TLS on a TLS listener, and Gateway Load Balancer and Network Firewall aren't supported in the VPC.

Nitro encryption stops at a load balancer or transit gateway. Two supported instances talking through an internal ALB or across a transit gateway aren't covered, so a requirement to encrypt all traffic between tiers still needs TLS on that hop.

Cluster services

Amazon EMR

An EMR security configuration turns on the open-source TLS features of the cluster's applications (the list varies by release) using certificates from one of three providers: EMR (EMR creates and manages the certificates, storing the CA in Secrets Manager), PEM (a zip in S3) or Custom (your own provider class). EMRFS traffic to S3 always uses TLS; Security Hub CSPM control EMR.4 checks in-transit encryption.

In-transit encryption with certificates from S3 (EMR security configuration, AWS CLI) 
aws emr create-security-configuration --name analytics-tls --security-configuration '{
  "EncryptionConfiguration": {
    "EnableInTransitEncryption": true,
    "EnableAtRestEncryption": false,
    "InTransitEncryptionConfiguration": {
      "TLSCertificateConfiguration": {
        "CertificateProviderType": "PEM",
        "S3Object": "s3://shop-pki-111111111111/emr/analytics-certs.zip"
      }
    }
  }
}'

Amazon EKS

AWS's EKS best practices list four ways to encrypt pod traffic: Nitro instances (same limits as above), TLS at ingress and load balancers (AWS Load Balancer Controller annotations), a service mesh with mutual TLS (Istio or Linkerd; App Mesh has reached end of support), and cert-manager with AWS Private CA to issue short-lived certificates to pods. End-to-end encryption means the pod terminates TLS. Network policies control flows but don't encrypt.

SageMaker AI

Distributed training jobs exchange model weights between instances. Inter-container traffic encryption (EnableInterContainerTrafficEncryption on training and tuning jobs) protects them with IPsec, so the job's security group must allow UDP 500 and ESP (protocol 50) from itself; it can make distributed training slower and more expensive, and does nothing for single-instance jobs. Network isolation (EnableNetworkIsolation) is a separate control: the container can't make any outbound call, not even to S3.

ECS Service Connect, VPC Lattice and data services

  • ECS Service Connect TLS encrypts service-to-service traffic with certificates ECS issues from an AWS Private CA (tagged AmazonECSManaged: true), TLS 1.3 only, rotated every 5 days by default; the private keys are stored as Secrets Manager secrets prefixed ecs-sc!, which other roles shouldn't be able to read. It's the AWS migration path from App Mesh.
  • VPC Lattice HTTPS listeners terminate TLS 1.2 or 1.3 and can re-encrypt to HTTPS target groups; TLS listeners pass TLS through to the target.
  • Node-to-node: OpenSearch node-to-node encryption, ElastiCache in-transit encryption and MSK in-cluster encryption cover traffic inside those clusters. Amazon MQ for RabbitMQ doesn't encrypt traffic between cluster nodes with TLS.

"Encrypt traffic between training instances" points to inter-container traffic encryption (with UDP 500 and ESP allowed). "Encrypt service-to-service traffic for ECS services with managed certificates" points to Service Connect TLS. "Encrypt pod-to-pod traffic on EKS with mutual TLS" points to a service mesh or cert-manager with Private CA.

Key takeaways

  • ELB policies: TLS13-1-2-Res-PQ-2025-09 is AWS's recommendation; console defaults to it, but CLI, CloudFormation and CDK default to 2016-08; TLS13-1-2-2021-06 fails ELB.17. Enforce with elasticloadbalancing:SecurityPolicy conditions.
  • Load balancers don't validate target certificates; CloudFront validates origin certificates. NLB TCP passthrough for end-to-end TLS; ALB mutual TLS in verify (trust store) or passthrough mode; NLB has no mutual TLS.
  • S3: deny aws:SecureTransport false and s3:TlsVersion below 1.2 (numeric), excluding AWS service principals. Database parameters: rds.force_ssl, require_secure_transport (cluster-level on Aurora), DocumentDB tls, Redshift require_ssl; RDS CA now rds-ca-rsa2048-g1.
  • ElastiCache preferred then required (Memcached only at creation); OpenSearch HTTPS plus node-to-node (irreversible); MSK TLS policies; API Gateway REST defaults to TLS 1.0, enhanced policies need an endpoint access mode.
  • ACM public certificates last 198 days and renew 45 days ahead if in use and validated by DNS; imported ones don't renew; exportable and ACME certificates are separate options.
  • Endpoints: gateway (S3, DynamoDB, free, VPC only), interface (PrivateLink, private DNS, on premises via inbound Resolver, cross-Region with vpce:AllowMultiRegion), resource endpoints for single resources; S3 interface endpoints are TLS 1.2 only.
  • Endpoint services: NLB or GWLB, allowed principals, acceptance, verified private DNS, consumer-to-provider only.
  • Between resources: Nitro encryption only for supported types in the same or peered VPC with no load balancer or transit gateway; VPC Encryption Controls to enforce; EMR security configurations; EKS mesh or Private CA certificates; SageMaker inter-container encryption (UDP 500, ESP); ECS Service Connect TLS; App Mesh is gone.
