Overview

Task 3.3

Design and troubleshoot network security controls.

The associate-level picture (security groups are stateful and allow-only, NACLs stateless with deny rules, NAT gateways, VPC endpoints, VPN and Direct Connect basics) is in the Solutions Architect guide. This task goes further: where security group references stop working, what Network Firewall's rule order does to an allow list, which links are encrypted and which aren't, how Verified Access differs from a VPN, and how to prove no unintended path exists. Containment with security groups and NACLs is in Task 2.2.

Running example. The same company. Each workload account has its own VPCs, connected through a transit gateway in a shared network account; internet egress goes through a central egress VPC with NAT gateways and AWS Network Firewall. The head office and warehouses connect over Direct Connect with Site-to-Site VPN as backup, analytics partners use another cloud provider, and employees and contractors need access to internal admin applications.

Permitting and preventing traffic

Skill 3.3.1Design and troubleshoot appropriate network controls to permit or prevent network traffic as required (for example, security groups, network ACLs, AWS Network Firewall).

Security groups at specialty depth

References, quotas and sharing

  • Referencing another security group allows traffic from the private IPs of whatever uses that group. It works in the same VPC and across VPC peering (inbound and outbound), and across a transit gateway for inbound rules only, if referencing is enabled on both the transit gateway and the attachment, within one transit gateway (not across peering).
  • References don't work when the traffic passes through a middlebox: through a Network Firewall or Gateway Load Balancer inspection VPC, or an appliance in the same VPC. Use CIDR ranges there.
  • Quotas: 60 inbound and 60 outbound rules per group (counted separately for IPv4 and IPv6), 5 groups per network interface (up to 16), and rules times groups can't exceed 1,000. A customer-managed prefix list counts as its maximum size, not its current entries.
  • Sharing: one security group can be associated with several VPCs in the same Region (associate-security-group-vpc), or shared through AWS RAM within the organization; default security groups can't be shared.
  • Neither security groups nor NACLs can block DNS queries to the VPC resolver, instance metadata or Amazon Time Sync; DNS needs DNS Firewall.

Network ACLs

NACLs are evaluated in rule-number order, first match wins, separately for each direction; the default NACL allows everything, a new custom NACL denies everything. The quota is 20 rules per direction (up to 40). Because they're stateless, return traffic needs the client's ephemeral ports, which depend on the client: 32768 to 61000 for many Linux systems including Amazon Linux, 49152 to 65535 for recent Windows, and 1024 to 65535 for NAT gateways, load balancers and Lambda. Put specific deny rules before a broad ephemeral allow.

VPC Block Public Access

VPC Block Public Access (November 2024, no charge) overrides route tables and security groups to block internet gateway traffic for every VPC in an account and Region: bidirectional (no internet traffic either way) or ingress-only (outbound through NAT gateways and egress-only gateways still works). Up to 50 exclusions for VPCs or subnets that must stay public, such as the central egress VPC. It doesn't affect VPN, Direct Connect private connectivity, Transit Gateway, Cloud WAN, Client VPN or Verified Access, but it does block internet-facing load balancers, NAT gateways and Network Firewall endpoints in subnets that aren't excluded.

Block inbound internet traffic everywhere except the egress VPC (AWS CLI, then the organization-wide version as an EC2 policy) 
aws ec2 create-vpc-block-public-access-exclusion --vpc-id vpc-0egress1234567890 \
  --internet-gateway-exclusion-mode allow-bidirectional
aws ec2 modify-vpc-block-public-access-options --internet-gateway-block-mode block-ingress

# Organizations EC2 policy: sets the mode for every account (exclusions are still made in each account)
{
  "ec2_attributes": {
    "vpc_block_public_access": {
      "internet_gateway_block": {
        "mode": { "@@assign": "block_ingress" },
        "exclusions_allowed": { "@@assign": "enabled" }
      }
    }
  }
}

The policy values use underscores (block_ingress), the CLI hyphens (block-ingress). Security Hub CSPM control EC2.172 checks the setting.

AWS Network Firewall

Architecture

Network Firewall is a managed stateful firewall and intrusion prevention system (built on Suricata) that inspects traffic routed through its endpoints, one per Availability Zone in dedicated firewall subnets. Routing must send traffic through the endpoint in both directions; for internet ingress, an edge route table on the internet gateway sends traffic for the workload subnets to the endpoint. An endpoint can't inspect traffic in its own subnet. Deployment models:

  • Distributed: a firewall in each VPC (Firewall Manager can create them).
  • Centralized: an inspection VPC on the transit gateway with appliance mode on its attachment, so both directions of a flow use the same AZ. Firewalls can now attach to a transit gateway directly (appliance mode always on), without building the inspection VPC yourself.
  • Extra endpoints in other VPCs through VPC endpoint associations (May 2025) share one firewall's policy.

Rule groups and evaluation order

Stateless rule groups look at single packets and pass, drop or forward them to the stateful engine; forward everything unless you have a reason not to. Stateful rule groups come in three forms: 5-tuple rules, domain lists (allow or deny by TLS SNI or HTTP Host header), and Suricata-compatible rules. The policy chooses an evaluation order:

  • Action order (the original default): all pass rules, then drop, then reject, then alert, regardless of group.
  • Strict order (recommended): rule groups by priority, rules in the order written, plus default actions such as Drop established (drop anything in an established connection no rule passed) or Application drop established, which waits for the TLS SNI or HTTP Host before deciding.
Egress allow list: only these domains over HTTPS and HTTP (Network Firewall domain list rule group, JSON) 
{
  "RulesSource": {
    "RulesSourceList": {
      "Targets": [".amazonaws.com", "api.payments.example.net", ".github.com"],
      "TargetTypes": ["TLS_SNI", "HTTP_HOST"],
      "GeneratedRulesType": "ALLOWLIST"
    }
  }
}

Create it with aws network-firewall create-rule-group --rule-group-name egress-allow --type STATEFUL --rule-group file://egress-allow.json --capacity 1000. A leading dot matches the domain and all subdomains. Other GeneratedRulesType values are DENYLIST, REJECTLIST and ALERTLIST.

An ALLOWLIST domain group generates its own "drop everything else" rule only under action order. In a strict order policy it only passes the listed domains; nothing drops the rest unless the policy's default action is Drop established (or an application drop variant). And in a centralized inspection VPC, domain lists only inspect traffic from HOME_NET, which defaults to the inspection VPC's own CIDR; set it to include the spoke VPCs, or their traffic isn't filtered.

Suricata rules, threat intelligence and TLS inspection

A few strict order rules for the egress firewall (Suricata rules) 
# Refuse TLS 1.0 and 1.1 outright
reject tls any any -> any any (msg:"TLS 1.0 or 1.1"; ssl_version:tls1.0,tls1.1; sid:2023070518;)
# No outbound connections to high-risk ports
drop ip $HOME_NET any -> $EXTERNAL_NET [1389,53,4444,445,135,139,389,3389] (msg:"Deny high risk destination ports"; sid:278670;)
# TLS straight to an IP address, with no DNS lookup first, is a common malware pattern
reject tls $HOME_NET any -> $EXTERNAL_NET any (ssl_state:client_hello; tls.sni; content:"."; pcre:"/^(?:[0-9]{1,3}\.){3}[0-9]{1,3}$/"; msg:"IP in TLS SNI"; flow:to_server; sid:1239848;)
# SSH only on port 22, and port 22 only for SSH
reject ssh $HOME_NET any -> $EXTERNAL_NET !22 (msg:"SSH on non-standard port"; flow:to_server; sid:2171010;)
reject tcp $HOME_NET any -> $EXTERNAL_NET 22 (msg:"Non-SSH protocol on TCP 22"; flow:to_server; app-layer-protocol:!ssh; sid:2171009;)
  • Managed rule groups: AWS threat signature groups, and active threat defense (June 2025, group AttackInfrastructure), which blocks malware staging, botnet command-and-control and mining pool infrastructure from Amazon's MadPot threat intelligence. Rules can also match geoip, JA3 and JA4 hashes, and since January 2026 URL and domain categories (aws_url_category needs TLS inspection for HTTPS; aws_domain_category doesn't).
  • TLS inspection decrypts, inspects and re-encrypts. Inbound uses your server certificates in ACM. Outbound uses a CA certificate you import into ACM; certificates issued by AWS Private CA aren't supported for this, nor are destination servers with private CA certificates.
  • Domain lists trust the SNI or Host header the client sends, which can be spoofed; resolved IP validation (October 2026) also checks the destination IP was what the VPC resolver returned for that domain.

Gateway Load Balancer and DNS Firewall

For third-party firewall appliances, a Gateway Load Balancer sends all traffic to an appliance fleet (GENEVE on port 6081), with GWLB endpoints as the next hop in route tables. Route 53 Resolver DNS Firewall filters DNS queries from VPCs against domain lists (your own and AWS managed malware, botnet and GuardDuty threat lists), and DNS Firewall Advanced detects DNS tunnelling and domain generation algorithms. It fails closed by default: if DNS Firewall doesn't answer, queries return SERVFAIL; enable fail open if availability matters more.

Hybrid and multicloud connectivity

Skill 3.3.2Design secure connectivity between hybrid and multi-cloud networks (for example, AWS Site-to-Site VPN, AWS Direct Connect, MAC Security [MACsec]).

Site-to-Site VPN

Strong tunnel options

Each VPN connection has two IPsec tunnels ending in different Availability Zones. AWS accepts any algorithm enabled in the tunnel options and evaluates proposals starting from the lowest configured value, whatever the customer gateway prefers, so restrict the options to strong ones. Authentication is a pre-shared key or a certificate from AWS Private CA (which lets the customer gateway change IP addresses). Turn on tunnel logs to CloudWatch Logs; Security Hub CSPM controls EC2.171 (logging) and EC2.183 (IKEv2) check both.

Only IKEv2, AES-256-GCM, SHA-384 and DH group 20 or higher on a tunnel (AWS CLI) 
aws ec2 modify-vpn-tunnel-options \
  --vpn-connection-id vpn-0abc1234def567890 \
  --vpn-tunnel-outside-ip-address 203.0.113.10 \
  --tunnel-options '{
    "IKEVersions": [{ "Value": "ikev2" }],
    "Phase1EncryptionAlgorithms": [{ "Value": "AES256-GCM-16" }],
    "Phase2EncryptionAlgorithms": [{ "Value": "AES256-GCM-16" }],
    "Phase1IntegrityAlgorithms": [{ "Value": "SHA2-384" }],
    "Phase2IntegrityAlgorithms": [{ "Value": "SHA2-384" }],
    "Phase1DHGroupNumbers": [{ "Value": 20 }, { "Value": 21 }],
    "Phase2DHGroupNumbers": [{ "Value": 20 }, { "Value": 21 }]
  }'

Accelerated VPN (over Global Accelerator) and the newer 5 Gbps large bandwidth tunnels work only with transit gateways or Cloud WAN, not virtual private gateways.

Direct Connect

Not encrypted unless you encrypt it

Direct Connect doesn't encrypt traffic. A private line isn't an encrypted one, so a requirement for encryption in transit needs one of these:

  • MACsec (IEEE 802.1AE): layer 2 encryption between your router and the AWS Direct Connect device, at line rate and no extra charge. Only on dedicated 10, 100 and 400 Gbps connections (and LAGs and partner interconnects) at supported locations, not hosted connections. Keys are a CKN/CAK pair stored in Secrets Manager (static CAK mode). Set the encryption mode to must_encrypt; the default for new MACsec connections, should_encrypt, falls back to unencrypted if MACsec fails. It protects the link to the AWS device, not end to end.
  • Site-to-Site VPN over Direct Connect: IPsec over a public VIF, or a private IP VPN over a transit VIF with a Direct Connect gateway and a transit gateway, using private addresses at both ends and no public endpoints.
Require MACsec on the head office connection (AWS CLI) 
# Associate the CKN/CAK pair (stored in Secrets Manager), then refuse to pass traffic unencrypted
aws directconnect associate-mac-sec-key --connection-id dxcon-fgabc123 \
  --ckn 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef \
  --cak fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210
aws directconnect update-connection --connection-id dxcon-fgabc123 --encryption-mode must_encrypt

A Direct Connect gateway doesn't route between the VPCs or transit gateways associated with it, and allowed prefixes limit what each association advertises.

"Encrypt traffic over our existing 1 Gbps hosted Direct Connect connection" can't be MACsec (hosted connections and 1 Gbps aren't supported). The answer is IPsec VPN over Direct Connect.

Other clouds

AWS Interconnect - multicloud

AWS Interconnect - multicloud (preview since November 2025, starting with Google Cloud, with Microsoft Azure in preview) provides private links between AWS and another cloud, attached on the AWS side to a Direct Connect gateway. The physical links between AWS and the partner are MACsec-encrypted by default. The alternative is Site-to-Site VPN between AWS and the other cloud's VPN gateway, encrypted with IPsec over the internet.

Access for users and workloads on premises

Skill 3.3.3Determine and configure security workload requirements for communication between hybrid environments and AWS (for example, by using AWS Verified Access).

AWS Verified Access

Zero trust access without a VPN

Verified Access gives users access to specific applications without a network connection into the VPC. Every request is checked against Cedar policies that use identity from a user trust provider (IAM Identity Center or any OIDC provider) and device posture from a device trust provider (CrowdStrike, Jamf or JumpCloud). All access is denied until a policy permits it; when both a group policy and an endpoint policy exist, both must allow the request. Endpoints can be load balancers, network interfaces, CIDR ranges or RDS databases, and since February 2025 non-HTTP applications (SSH, RDP, databases) are supported through the Connectivity Client. Logs are in OCSF format, and a WAF web ACL can protect the instance.

Admin app: finance group members with a verified email on a low-risk managed device (Verified Access policy, Cedar) 
permit(principal, action, resource)
when {
    context.idc.groups has "c242c5b0-6081-1845-6fa8-6e0d9513c107"
    && context.idc.user.email.verified == true
    && context.jamf.risk == "LOW"
};

idc and jamf are the policy reference names given to the trust providers. Pricing is per application hour for HTTP apps and per endpoint hour plus connection hour for TCP apps.

Workload-to-workload requirements

For systems on premises calling AWS services and the reverse, the security requirements are usually: encrypted transport (MACsec or IPsec on the link, TLS on top), private access to AWS APIs through interface VPC endpoints reachable over the private connection (with endpoint policies), DNS resolution through Resolver inbound and outbound endpoints (with DNS Firewall applying to inbound queries), and security groups and Network Firewall rules that allow only the on-premises CIDRs and ports the integration uses. Client VPN uses an ACM server certificate, authorization rules for each group, and can run a Lambda client connect handler for extra checks.

"Contractors need access to two internal web apps, only from compliant devices, without network access to the VPC" points to Verified Access with a device trust provider. "Remote engineers need access to many hosts and ports in the VPC" points to Client VPN.

Network segmentation

Skill 3.3.4Design network segmentation based on security requirements (for example, north/south and east/west traffic protections, isolated subnets).

North-south and east-west

Two kinds of traffic, different controls

North-south traffic crosses the boundary: internet to application, VPC to internet, data center to AWS. The controls are the edge (Task 3.1), internet and NAT gateways only in designated public and egress subnets, VPC Block Public Access everywhere else, and Network Firewall on centralized egress with a domain allow list. East-west traffic moves between workloads: VPC to VPC, account to account, tier to tier. The controls are security groups that reference each other, transit gateway route tables or Cloud WAN segments that only connect what should talk, inspection for traffic between segments, and service-level authorization.

An isolated subnet has no route to an internet gateway or NAT gateway at all, only local routes and VPC endpoints; databases and the forensics VPC from Task 2.1 belong there.

Segmentation tools

Transit Gateway and Cloud WAN

  • Transit gateway route tables create separate routing domains: prod VPC attachments associate with a prod table that has routes only to prod and shared services, dev with a dev table, so prod and dev can't reach each other because there's simply no route. Blackhole routes drop traffic for specific ranges, and turning off default route table association and propagation stops new attachments joining everything automatically.
  • Cloud WAN segments are routing domains defined in a policy document. isolate-attachments stops attachments in a segment talking to each other, and segment actions insert inspection: send-via for east-west traffic between segments and send-to for north-south traffic, through network function groups containing inspection VPCs.
Send all development segment egress through the inspection VPCs (Cloud WAN policy segment action, JSON) 
{
  "action": "send-to",
  "segment": "development",
  "via": { "network-function-groups": ["inspection-vpc"] }
}

Service-level segmentation

  • PrivateLink exposes one service to consumers in other VPCs without routing between the networks at all; the consumer can reach only that endpoint.
  • VPC Lattice service networks connect services across VPCs and accounts, with auth policies (IAM policy syntax, SigV4-signed requests) deciding which principals and VPCs can call which services and paths.
  • VPC endpoint policies limit what can be done through an endpoint; with aws:PrincipalOrgID and aws:ResourceOrgID they form a data perimeter: only the organization's identities, only the organization's resources.
Only organization principals, only to organization resources, through this endpoint (VPC endpoint policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowRequestsByOrgsIdentitiesToOrgsResources",
      "Effect": "Allow",
      "Principal": { "AWS": "*" },
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:PrincipalOrgID": "o-exampleorgid",
          "aws:ResourceOrgID": "o-exampleorgid"
        }
      }
    }
  ]
}
Orders service callable only by authenticated principals from the shop VPC (VPC Lattice auth policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "vpc-lattice-svcs:Invoke",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:PrincipalType": "Anonymous" },
        "StringEquals": { "vpc-lattice-svcs:SourceVpc": "vpc-0shop1234567890ab" }
      }
    }
  ]
}

The organization-wide data perimeter pattern needs exceptions for AWS services acting on your behalf (aws:PrincipalIsAWSService) and for AWS-owned resources some services use; AWS publishes complete examples in its data perimeter policy repository. Data perimeters across all accounts are Task 6.1.

A transit gateway attaching every VPC to one default route table puts prod, dev and partner VPCs in the same routing domain: any security group mistake becomes a cross-environment path. Separate route tables (or Cloud WAN segments) are the segmentation; security groups are the second layer, not the first.

Finding unnecessary access

Skill 3.3.5Identify unnecessary network access (for example, AWS Verified Access, Network Access Analyzer, Amazon Inspector network reachability findings).

All three analyze configuration, not live packets. Network Access Analyzer works within one account and Region and doesn't evaluate Network Firewall rules, so a path through a firewall may be reported even if the firewall would drop it.

Network Access Analyzer scopes

A network access scope states paths that shouldn't exist (MatchPaths), with exceptions (ExcludePaths), by resource type, resource, address, port and protocol. AWS provides scopes such as All-IGW-Ingress and AWS-VPC-Egress. In the running example, the rule is that internet traffic must always pass the firewall:

Find any path from an internet gateway to the app subnets that doesn't go through Network Firewall (network access scope, JSON) 
{
  "MatchPaths": [
    {
      "Source": { "ResourceStatement": { "ResourceTypes": ["AWS::EC2::InternetGateway"] } },
      "Destination": { "ResourceStatement": { "Resources": ["subnet-0app1a234567890ab", "subnet-0app1b234567890ab"] } }
    }
  ],
  "ExcludePaths": [
    {
      "ThroughResources": [{ "ResourceStatement": { "ResourceTypes": ["AWS::NetworkFirewall::Firewall"] } }]
    }
  ]
}
Create the scope and analyze it (AWS CLI) 
aws ec2 create-network-insights-access-scope --cli-input-json file://igw-bypass-scope.json
aws ec2 start-network-insights-access-scope-analysis --network-insights-access-scope-id nis-0123456789abcdef0
aws ec2 get-network-insights-access-scope-analysis-findings --network-insights-access-scope-analysis-id nisa-0123456789abcdef0

Continuous checks

Security Hub CSPM, Config and Firewall Manager

  • Security Hub CSPM controls: EC2.2 (default security groups allow nothing), EC2.13 and EC2.14 (no SSH or RDP from anywhere), EC2.18 (only authorized ports, by default 80 and 443, open to the internet), EC2.19 (no unrestricted access to high-risk ports such as 22, 3389, 3306 and 5432), EC2.21 (NACLs don't allow SSH or RDP from anywhere), EC2.172 (VPC Block Public Access), and the NetworkFirewall controls (multi-AZ, logging, stateless default action drop or forward).
  • Firewall Manager security group policies: common policies apply baseline groups to resources, content audit policies flag or remove rules outside an allowed range, and usage audit policies remove unused and redundant security groups.
  • Verified Access itself reduces unnecessary access: replacing a VPN that gives network-wide reach with per-application access removes every path users never needed.

"Prove there is no path from the internet to the database subnets except through the firewall" points to Network Access Analyzer. "Why can't the app reach the database" points to Reachability Analyzer. "Continuously report instances with ports open to the internet" points to Inspector network reachability or Security Hub CSPM controls.

Key takeaways

  • Security groups: references work in the same VPC, over peering, and over a transit gateway for inbound rules only (enabled on both sides), but not through firewalls or appliances; 60 rules per direction, rules times groups max 1,000; prefix lists count at maximum size; can't block VPC DNS or IMDS.
  • NACLs: numbered, first match, 20 rules per direction (40 max), ephemeral ports by client type. VPC Block Public Access: bidirectional or ingress-only, 50 exclusions, organization-wide through EC2 policies; doesn't affect VPN, TGW or Verified Access.
  • Network Firewall: endpoints per AZ, symmetric routing, appliance mode for central inspection (or direct TGW attachment); strict order with Drop established, because an allow list only drops the rest under action order; set HOME_NET for spokes; Suricata rules, active threat defense, categories; outbound TLS inspection needs an imported CA in ACM.
  • DNS Firewall fails closed by default; GWLB with GENEVE 6081 for third-party appliances.
  • VPN: restrict tunnel options (IKEv2, AES256-GCM, SHA-384, DH 20+), log tunnels. Direct Connect isn't encrypted: MACsec on dedicated 10/100/400 Gbps with must_encrypt, or IPsec over DX (private IP VPN on a transit VIF). AWS Interconnect multicloud links are MACsec-encrypted.
  • Verified Access: per-application, per-request Cedar policies with user and device trust, both group and endpoint policies must allow, TCP apps through the Connectivity Client, OCSF logs. Client VPN for network-level remote access.
  • Segmentation: isolated subnets, separate TGW route tables and blackholes, Cloud WAN segments with send-via and send-to, PrivateLink, VPC Lattice auth policies, endpoint policies with organization conditions.
  • Unnecessary access: Network Access Analyzer scopes (account and Region, ignores firewall rules), Reachability Analyzer for one path, Inspector reachability every 12 hours, Security Hub CSPM EC2 controls, Firewall Manager audit policies.
