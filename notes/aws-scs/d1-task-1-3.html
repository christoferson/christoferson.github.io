Task 1.3: Troubleshoot security monitoring, logging, and alerting solutions

Working out why a log is empty, a health check fails or an alert never arrived, and fixing it: usually a missing permission, a setting in the wrong Region or account, a key policy, or a log class that doesn't support the feature.

Overview

Task 1.3

Troubleshoot security monitoring, logging, and alerting solutions.

Troubleshooting questions describe a symptom: "the log group is empty", "the alarm stays in INSUFFICIENT_DATA", "the Lambda function is never invoked by the rule". The answer is almost always one of a short list of causes, and checking them in the same order each time finds it quickly. Task 1.1 and Task 1.2 showed how these pieces are set up; this page is about why they stop working.

Running example. The same company: AWS Organizations with security tooling (222222222222), log archive (444444444444) and workload accounts (prod is 111111111111); a web application behind CloudFront, AWS WAF and an Application Load Balancer, a REST API on API Gateway backed by Lambda, containers on EKS and ECS, EC2 instances running the CloudWatch agent, and an S3 data platform, in us-east-1 with us-west-2 for disaster recovery.

A checking order that works

  1. Is it turned on?Logging level, trail logging, flow log status, the right log class, the feature enabled in this Region.
  2. Is the writer allowed?The execution role, service role or service principal can write, and the bucket, log group or key policy lets it.
  3. Is it going where you're looking?The right account, Region (us-east-1 for global services) and log group name.
  4. Does the consumer match it?Metric filter and event pattern syntax, the alarm's missing data setting, target permissions.
  5. Has it had time?Many logs are delivered in minutes to hours, and filters only see new events.

Analyzing logging and health check setups

Skill 1.3.1Analyze the functionality, permissions, and configuration of resources (for example, Lambda function logging, Amazon API Gateway logging, health checks, Amazon CloudFront logging).

Lambda function logging

Permissions and log groups

Lambda writes to /aws/lambda/<function name> using the function's execution role, which needs logs:CreateLogGroup, logs:CreateLogStream and logs:PutLogEvents; the managed policy AWSLambdaBasicExecutionRole has exactly those. The console adds them when it creates a role, the CLI and infrastructure as code don't, so a function deployed from a pipeline with a hand-written role often has no logs. After fixing the role, make a trivial configuration change: running execution environments keep their old credentials until they're replaced.

A function can write to a custom log group (several functions can share one), set with --logging-config LogGroup=...; the role must allow writing to it. A custom name starting with aws/ silently receives nothing. If the log group uses a customer managed KMS key, the key policy must allow the Regional logs.<region>.amazonaws.com principal (Task 1.2).

Advanced logging controls

With JSON log format, Lambda can filter by application log level (TRACE to FATAL) and system log level (DEBUG, INFO, WARN). Level filtering only works with JSON; both levels default to INFO, and a level set in the function's code wins over the configuration. If security events are logged at INFO but the level is set to ERROR, they're dropped before they reach CloudWatch.

JSON logs, application events from INFO up, system events from WARN up (AWS CLI) 
aws lambda update-function-configuration \
  --function-name orders-api \
  --logging-config LogFormat=JSON,ApplicationLogLevel=INFO,SystemLogLevel=WARN,LogGroup=/prod/lambda/orders

Logs can also be missing with correct permissions when CloudWatch Logs throttles the account's API quotas, or when one stream exceeds about 2 MB per second. Attaching a function to your VPC doesn't change the Lambda-managed environment that captures its basic logs, and AWS doesn't list a NAT gateway or endpoint as a requirement for them; extensions such as Lambda Insights, which send from inside the function, do need a route or the com.amazonaws.<region>.logs endpoint.

Lambda can deliver logs straight to S3 or Firehose through a log group of class DELIVERY, which keeps events for only 2 days and doesn't support Logs Insights. An Essentials log group (formerly Infrequent Access) has no metric filters, subscription filters or Live Tail. Either class explains "the metric filter on the function's logs never matches", and a log group's class can't be changed after creation.

API Gateway logging

Execution logs and access logs

REST and WebSocket APIs have two independent log types. Execution logs are API Gateway's own trace (authorizer results, integration requests, errors) in API-Gateway-Execution-Logs_{rest-api-id}/{stage}, turned on per stage with loggingLevel ERROR or INFO. Access logs are one line per request in a format you define with $context variables, sent to a log group or to a Firehose stream whose name starts with amazon-apigateway-. HTTP APIs have access logs only, to CloudWatch Logs only.

For REST and WebSocket APIs, API Gateway writes to CloudWatch Logs with a role set on the account, in each Region. Without it, enabling logging on a stage fails. The role trusts apigateway.amazonaws.com and has the AmazonAPIGatewayPushToCloudWatchLogs managed policy; AWS STS must be enabled in the Region.

Set the API Gateway logging role for this Region (AWS CLI, once per Region per account) 
aws apigateway update-account \
  --region us-west-2 \
  --patch-operations op='replace',path='/cloudwatchRoleArn',value='arn:aws:iam::111111111111:role/APIGatewayToCloudWatchLogs'

For security investigations, an access log format that captures caller identity, authorizer and WAF results is worth more than execution logs. The format must include $context.requestId or $context.extendedRequestId; the extended ID can't be overridden by clients.

Security-focused access log format (stage access log format, JSON) 
{
  "requestId": "$context.extendedRequestId",
  "sourceIp": "$context.identity.sourceIp",
  "userArn": "$context.identity.userArn",
  "principalId": "$context.authorizer.principalId",
  "authorizerError": "$context.authorizer.error",
  "wafStatus": "$context.waf.status",
  "webAclArn": "$context.webaclArn",
  "status": "$context.status",
  "errorMessage": "$context.error.message",
  "tlsVersion": "$context.tlsVersion"
}

dataTraceEnabled logs full request and response bodies, which can put tokens and personal data into logs; AWS recommends not enabling it for production. Standard execution log events are also cut at 1 KB. REST execution logs can now be delivered through CloudWatch vended logs to a log group of your choice, S3 or Firehose, with events up to 1 MB; but once such a delivery exists, the old API-Gateway-Execution-Logs_... group stops receiving events, so alarms and metric filters on it go quiet.

Health checks

Load balancer target health

aws elbv2 describe-target-health (or the target group's resource map) shows each target's state and a reason code. The common ones:

  • Target.Timeout: no response in time, usually a security group or network ACL blocking the health check port. The target's security group must allow the health check port from the load balancer's security group, and network ACLs must allow the return traffic on ephemeral ports.
  • Target.ResponseCodeMismatch: the path answered, but not with the expected code (default 200), for example a redirect to a login page, or a virtual host rejecting the health check's Host header, which is the target's private IP.
  • Target.FailedHealthChecks, Elb.InitialHealthChecking, Target.NotRegistered, Target.NotInUse (no listener rule uses the group, or the Availability Zone isn't enabled), Target.HealthCheckDisabled.

ALB health check logs (off by default, delivered to S3 every 5 minutes) record every check with a reason such as TimedOut, ConnectionReset or ResponseCodeMismatch. Both ALB and NLB fail open: when every target is unhealthy, traffic goes to all of them. An NLB HTTPS health check fails against targets that only support TLS 1.3.

Route 53 health checks

Route 53 health checkers come from the internet, so a failing endpoint check is usually a firewall or security group that doesn't allow them. Allow the ROUTE53_HEALTHCHECKS ranges from ip-ranges.json, or reference the AWS-managed prefix list com.amazonaws.<region>.route53-healthchecks in the security group. Other causes:

  • The endpoint IP is private: Route 53 can't check private, local or non-routable addresses. Use a CloudWatch alarm-based health check on a metric from inside the VPC instead.
  • A string match fails because the string isn't in the first 5,120 bytes of the body.
  • HTTPS checks don't validate certificates, so an expired certificate doesn't fail the check. Monitor certificate expiry separately (Task 5.1).
Allow Route 53 health checkers to reach the web tier, then see why a check failed (AWS CLI) 
# Find the managed prefix list for health checkers
aws ec2 describe-managed-prefix-lists \
  --filters Name=prefix-list-name,Values=com.amazonaws.us-east-1.route53-healthchecks

# Allow HTTPS from it on the web tier's security group
aws ec2 authorize-security-group-ingress \
  --group-id sg-0abc1234def567890 \
  --ip-permissions 'IpProtocol=tcp,FromPort=443,ToPort=443,PrefixListIds=[{PrefixListId=pl-0123456789abcdef0}]'

# What each checker saw last (not available for calculated health checks)
aws route53 get-health-check-last-failure-reason --health-check-id 01234567-89ab-cdef-0123-456789abcdef

CloudFront logging

Legacy, version 2 and real-time logs

  • Legacy standard logs (S3 only) need ACLs enabled on the bucket: CloudFront grants the awslogsdelivery account FULL_CONTROL. New buckets have ACLs disabled (Object Ownership "bucket owner enforced") by default, which stops delivery, and buckets in opt-in Regions aren't supported. With SSE-KMS, only a customer managed key works, with a key policy for delivery.logs.amazonaws.com.
  • Standard logs version 2 (since November 2024) use the CloudWatch Logs delivery APIs, which must be called in us-east-1, with a Firehose destination also in us-east-1. A distribution can have only one delivery source, and the output format can't be changed after the destination is created.
  • Real-time logs go to Kinesis Data Streams through a role trusted by cloudfront.amazonaws.com with kinesis:PutRecord, kinesis:PutRecords and the Describe actions, plus kms:GenerateDataKey if the stream is encrypted. Missing records usually mean too few shards.

Standard logs are delivered up to several times an hour and can be up to 24 hours late; AWS says delivery becomes reliable about four hours after logging is enabled. "No logs ten minutes after enabling" isn't a fault.

"CloudFront access logs stopped after the bucket was recreated" or "...in a new account" points to bucket ACLs: enable ACLs (Object Ownership "bucket owner preferred") or move to standard logging v2.

Remediating missing logs and silent alerts

Skill 1.3.2Remediate misconfiguration of resources (for example, by troubleshooting CloudWatch Agent configurations, troubleshooting missing logs).

The CloudWatch agent

Where to look

Start with the agent's status and its own logs. If it won't start, the configuration didn't validate; if it runs but nothing arrives, the agent log shows the API errors.

Check the agent on a Linux instance (shell) 
# Running? Which version?
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -m ec2 -a status

# Why it won't start
sudo cat /opt/aws/amazon-cloudwatch-agent/logs/configuration-validation.log

# Why data isn't arriving (AccessDenied, endpoint, credential errors)
sudo tail -n 50 /opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log

# Editing the JSON does nothing until the agent loads it again
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s -c ssm:AmazonCloudWatch-linux

On Windows, the logs are under %ProgramData%\Amazon\AmazonCloudWatchAgent\Logs. For a fleet, the AWSSupport-TroubleshootCloudWatchAgent runbook checks the instance profile, permissions, agent status and endpoint connectivity.

The usual causes

  • Permissions: the instance profile lacks CloudWatchAgentServerPolicy, or the configuration parameter isn't named AmazonCloudWatch-*, so ssm:GetParameter is denied.
  • Credentials on premises: the agent uses the AmazonCloudWatchAgent profile referenced in common-config.toml, started with -m onPremise. Environment variables aren't visible when the agent runs as a systemd service.
  • No route to the endpoint: instances in private subnets need a NAT gateway or the com.amazonaws.<region>.logs interface endpoint (and monitoring for metrics, plus SSM endpoints for Parameter Store). Live Tail uses a separate stream-logs endpoint.
  • Containers: with IMDSv2, the instance metadata hop limit must be 2, or the agent can't get credentials or tags (the log says to increase the hop limit).
  • Files: a file_path glob ships only the newest matching file; the user the agent runs as (root, or run_as_user) must be able to read the file; and conflicting retention_in_days values for one log group stop the agent.

Missing logs, source by source

CloudTrail

aws cloudtrail get-trail-status answers most questions: IsLogging (a trail that was stopped), LatestDeliveryError (S3 delivery, almost always the bucket policy or KMS key policy), LatestDigestDeliveryError, LatestNotificationError (SNS topic policy) and LatestCloudWatchLogsDeliveryError. Status is per Region, and member accounts must pass the organization trail's full ARN. CloudTrail keeps retrying a misconfigured bucket for 30 days, and you're charged for it.

A trail whose bucket policy was changed (get-trail-status output, abridged) 
{
  "IsLogging": true,
  "LatestDeliveryError": "AccessDenied",
  "LatestDeliveryTime": "2026-11-08T14:05:12Z",
  "LatestDigestDeliveryError": "AccessDenied",
  "LatestCloudWatchLogsDeliveryTime": "2026-11-09T09:41:57Z"
}

Here the trail is logging and CloudWatch Logs delivery still works, but S3 delivery has failed since yesterday, so the bucket policy or its KMS key is the place to look. For CloudTrail to CloudWatch Logs, the log group must be in the trail's own account, and the role trusted by cloudtrail.amazonaws.com must allow logs:CreateLogStream and logs:PutLogEvents on streams named <account>_CloudTrail_<region>* (plus <org ID>_* for an organization trail). CloudTrail doesn't send events over 256 KB to CloudWatch Logs or EventBridge.

VPC Flow Logs

aws ec2 describe-flow-logs shows the status and DeliverLogsErrorMessage. Access error means the role's trust (vpc-flow-logs.amazonaws.com) or permissions are wrong. A new flow log with no records may just need 10 minutes, and its log group appears only once traffic is recorded. For S3, an "undeliverable" destination means the bucket's default SSE-KMS key is given as a key ID rather than an ARN, and a bucket policy that grew past 20 KB (one statement per flow log) should use arn:aws:s3:::bucket/*. In records, NODATA means no traffic in the interval, not a fault; SKIPDATA means records were skipped.

Logs that need a specific bucket or log group

  • ALB access logs: bucket in the same Region, SSE-S3 only (SSE-KMS isn't supported), policy for logdelivery.elasticloadbalancing.amazonaws.com, and no AWSLogs in the prefix.
  • S3 server access logs: destination bucket in the same Region and account, SSE-S3, no Object Lock default retention, no Requester Pays, and a bucket policy for logging.s3.amazonaws.com. Delivery takes hours.
  • WAF logs: the destination's name must start with aws-waf-logs-, in the same Region and account as the web ACL.
  • Route 53 public DNS query logs: the log group must be in us-east-1.

Services that deliver vended logs to CloudWatch Logs (Route 53, WAF, flow logs and others) need a resource policy allowing delivery.logs.amazonaws.com. An account can have only 10 resource policies per Region; when that's reached, new deliveries can't add permissions. Newer deliveries put the policy on the log group itself, and log groups named under /aws/vendedlogs/ can share one account-level policy.

Alerts that don't arrive

EventBridge rules

If the rule's TriggeredRules metric is zero, the pattern doesn't match or the rule is in the wrong Region; if FailedInvocations rises, the target refused the event. Checks, in order:

  • Region: API events for global services such as IAM appear only in us-east-1 (so do AWS Health global events, Task 1.1).
  • Pattern: exact strings and ARNs; CloudTrail API events have an empty resources field, so match on detail instead. Test with aws events test-event-pattern or the console sandbox.
  • Lambda target: the function's resource policy must allow events.amazonaws.com from the rule's ARN, without a SourceAccount field.
  • SNS or SQS target encrypted with KMS: it must use a customer managed key; the AWS managed key for SNS can't be granted to EventBridge or CloudWatch alarms.
Let EventBridge invoke the responder function (AWS CLI) 
aws lambda add-permission \
  --function-name quarantine-responder \
  --statement-id allow-guardduty-rule \
  --action lambda:InvokeFunction \
  --principal events.amazonaws.com \
  --source-arn arn:aws:events:us-east-1:222222222222:rule/guardduty-high
Let EventBridge and CloudWatch alarms publish to an encrypted topic (one statement of the KMS key policy) 
{
  "Sid": "AllowEventSourcesToUseTheKey",
  "Effect": "Allow",
  "Principal": { "Service": ["events.amazonaws.com", "cloudwatch.amazonaws.com"] },
  "Action": ["kms:GenerateDataKey*", "kms:Decrypt"],
  "Resource": "*"
}

The topic policy must also allow sns:Publish from those principals. AWS notes that aws:SourceAccount, aws:SourceArn and aws:SourceOrgID conditions in the key policy aren't supported for EventBridge publishing to encrypted topics, so don't add them there.

Alarms and metric filters

A metric filter only counts events ingested after it was created, so testing it against yesterday's root sign-in shows nothing. Without a default value, a filter on a rare event publishes no data points at all, and the alarm sits in INSUFFICIENT_DATA, because the default missing data treatment is missing. For a count of bad events, treat missing data as notBreaching (or set the filter's defaultValue to 0).

An alarm on a rare event that stays OK between occurrences (AWS CLI) 
aws cloudwatch put-metric-alarm \
  --alarm-name root-usage \
  --namespace LogMetrics --metric-name RootUsageCount \
  --statistic Sum --period 300 --evaluation-periods 1 \
  --threshold 1 --comparison-operator GreaterThanOrEqualToThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions arn:aws:sns:us-east-1:222222222222:security-alerts

The other end matters too: an email subscription stays "pending confirmation" until someone clicks the link, and unconfirmed subscriptions are deleted after 48 hours.

Findings that don't appear

Security Hub CSPM, Config and GuardDuty

  • Security Hub CSPM controls show WARNING (control status Unknown) rather than FAILED when AWS Config isn't recording the resource type the control checks, and Config.1 fails. Fix the recorder: aws configservice describe-configuration-recorder-status shows recording, lastStatus and lastErrorCode. When both Security Hub CSPM and the new Security Hub are enabled, CSPM creates its own service-linked recorder, and this problem goes away.
  • No data on a control means it's new, unavailable in the Region, or all its findings are suppressed.
  • GuardDuty findings missing for one Region: the delegated administrator and member enablement are per Region; auto-enable NEW misses accounts that opted into a Region after joining, so use ALL.
  • Findings missing from Security Hub CSPM or EventBridge but present in GuardDuty or Macie: a suppression rule archived them, or (for Macie) only policy findings are published by default (Task 1.1).

Diagnostic tools

Find the blocking permission or network path

  • IAM policy simulator: test whether a role can call an action, with identity policies and SCPs taken into account.
  • IAM Access Analyzer policy validation: catch errors and security warnings in a bucket, key or trust policy before applying it.
  • Reachability Analyzer: show which security group, network ACL or route blocks the path from a load balancer to a target.
  • CloudWatch Logs Live Tail: watch events arrive in a log group in real time while you test (Standard class only).
  • CloudTrail Event history: find the failed management call (for example PutBucketPolicy or StopLogging) that started the problem.
Can the flow logs role write to CloudWatch Logs? (AWS CLI) 
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::111111111111:role/FlowLogsToCloudWatch \
  --action-names logs:CreateLogStream logs:PutLogEvents \
  --resource-arns arn:aws:logs:us-east-1:111111111111:log-group:/aws/vpc/prod:*
# EvalDecision: allowed, explicitDeny or implicitDeny for each action

"Logs stopped arriving after a change nobody remembers" points to CloudTrail (who changed the bucket policy, key policy or role) and AWS Config (what the resource looked like before). Then fix the configuration and prevent it with an SCP or Config rule.

Key takeaways

  • Check in order: turned on, writer allowed, right account, Region and name, consumer matching, time to arrive.
  • Lambda: execution role with the three logs actions (the CLI doesn't add them), no aws/ prefix on custom log groups, log levels need JSON, DELIVERY and Essentials log groups lack metric and subscription filters.
  • API Gateway: CloudWatch role set on the account in every Region; execution logs (loggingLevel, 1 KB events) vs access logs ($context format, Firehose names amazon-apigateway-); HTTP APIs have access logs only; avoid dataTraceEnabled in production.
  • Health checks: Target.Timeout is usually a security group; ALB and NLB fail open; Route 53 needs its checker ranges or prefix list allowed, can't check private IPs, and doesn't validate HTTPS certificates.
  • CloudFront: legacy logs need bucket ACLs (no opt-in Region buckets, customer managed KMS key only); v2 is configured in us-east-1; logs can lag hours.
  • Agent: status, configuration-validation.log and amazon-cloudwatch-agent.log; fetch-config after edits; AmazonCloudWatch- parameter names; logs endpoint in private subnets; IMDSv2 hop limit 2 in containers.
  • Delivery: get-trail-status errors, flow log Access error and key-ID-not-ARN, ALB logs SSE-S3 only, S3 access logs same account and Region, aws-waf-logs- names, 10 resource policies per Region.
  • Alerts: global events only in us-east-1, Lambda resource policy for events.amazonaws.com, customer managed KMS keys for encrypted SNS and SQS targets, metric filters not retroactive, notBreaching for rare-event alarms. Security Hub CSPM WARNING means Config isn't recording.
