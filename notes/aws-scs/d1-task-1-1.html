Overview

Task 1.1

Design and implement monitoring and alerting solutions for an AWS account or organization.

SCS-C03 questions about monitoring are rarely about a single alarm. They describe an organization with dozens of accounts and ask how to make sure a detector is on everywhere, including in accounts created next month, how findings reach one team, and which service raises which kind of finding. The pattern behind most right answers is the same: a delegated administrator in a dedicated security tooling account, auto-enable for all members, findings aggregated into one home Region, and EventBridge rules for the findings that need a response.

Running example. A company runs its workloads in AWS Organizations: a management account, a Security OU with a security tooling account (where the security team works) and a log archive account (where logs are kept), and prod, staging and dev workload accounts (prod is 111111111111). It runs a customer-facing web application behind CloudFront and an Application Load Balancer, containers on Amazon EKS and Amazon ECS on Fargate, a data platform on Amazon S3, and a new generative AI assistant built on Amazon Bedrock. Its main Region is us-east-1, with us-west-2 for disaster recovery. Every task page in this guide reuses it.

Security Hub has two products now. The exam guide says "Security Hub"; read the question for which job is meant. Both are compared in Skill 1.1.3.

Deciding what to monitor

Skill 1.1.1Analyze workloads to determine monitoring requirements.

Start from the workload, not the service list

Questions to ask about each workload

For each workload, ask what an attacker would want (credentials, data, compute for mining, a foothold to move sideways), which logs would show it, and who has to act when it happens. That gives the monitoring requirements: the signals, the detector that reads them, how fast an alert must arrive, and how long the evidence must be kept. Compliance requirements add to the list; a PCI DSS scope, for example, needs the controls in that standard checked continuously.

In the running example the answers map to services like this:

  • Every account and Region: account takeover, unusual API calls and crypto-mining point to Amazon GuardDuty. Its foundational data sources (CloudTrail management events, VPC Flow Logs and Route 53 Resolver DNS query logs) are read from an independent copy of the logs, so it needs no trail, flow logs or query logging of its own. AWS recommends turning it on in every Region, including Regions you don't use, because an attacker with stolen keys will.
  • The S3 data platform: exfiltration and suspicious data access point to GuardDuty S3 Protection (CloudTrail S3 data events). Where the sensitive data is and which buckets are public or unencrypted point to Amazon Macie. Malware in uploaded files points to GuardDuty Malware Protection for S3, which can run even without GuardDuty enabled.
  • EKS and ECS on Fargate: suspicious Kubernetes API calls point to EKS Protection (audit logs). Process, file and network activity inside containers points to Runtime Monitoring, which uses a GuardDuty security agent on EKS, ECS (including Fargate) and EC2. Known vulnerabilities in images point to Amazon Inspector.
  • The generative AI assistant: anomalous model invocations, cost harvesting and direct prompt injection against Amazon Bedrock and SageMaker AI point to GuardDuty AI Protection (added July 2026). Whether the AI resources are configured securely points to the AI Security Best Practices standard in Security Hub CSPM.
  • Configuration drift everywhere: resources that break the company's rules point to AWS Config rules and Security Hub CSPM controls.

GuardDuty protection plans

What each plan adds

Foundational detection is always on once GuardDuty is enabled. Each protection plan adds a data source and is enabled per account and Region (or for the whole organization, Skill 1.1.3). The feature names are the ones the API and CLI use.

  • S3 Protection (S3_DATA_EVENTS): S3 data events.
  • EKS Protection (EKS_AUDIT_LOGS): Kubernetes audit logs.
  • Runtime Monitoring (RUNTIME_MONITORING): OS-level events from the agent on EKS, ECS and EC2. The older EKS_RUNTIME_MONITORING can't be set together with it.
  • Malware Protection for EC2 (EBS_MALWARE_PROTECTION): scans EBS volumes when a finding suggests malware, or on demand. Malware Protection for S3 and for AWS Backup (snapshots, AMIs and recovery points, added November 2025) are set up separately.
  • RDS Protection (RDS_LOGIN_EVENTS): login activity on Aurora and RDS.
  • Lambda Protection (LAMBDA_NETWORK_LOGS): network activity of Lambda functions.
  • AI Protection (AI_PROTECTION): CloudTrail data events from Bedrock, Bedrock AgentCore and SageMaker AI.

The first time GuardDuty is enabled, it turns on every plan except Runtime Monitoring and includes them in a 30-day free trial per Region. Plans launched later are not turned on for existing users automatically. GuardDuty keeps findings for 90 days; anything longer needs an export (Skill 1.1.4).

"Enable VPC Flow Logs and a CloudTrail trail so GuardDuty can analyze them" is a distractor. GuardDuty reads its own duplicate stream and discards it. You still need a trail for your own records and investigations (Task 1.2), but not for GuardDuty. Amazon Security Lake is the opposite: of its native sources, CloudTrail management events are the only one you must configure yourself.

Workload monitoring and health checks

Skill 1.1.2Design and implement workload monitoring strategies (for example, by configuring resource health checks).

Health checks are a security tool as well as an availability tool: a sudden failure of every target can be a denial of service, a broken deployment or a security group change. The CloudWatch metric and alarm basics are covered on the CloudOps guide's alarms section; this page covers the security angle.

Load balancer and Route 53 health checks

Target group health checks

An Application Load Balancer checks each target on a path (default /) every 30 seconds by default, marks it unhealthy after 2 failures and healthy again after 5 successes, and expects HTTP 200 unless you set another matcher. If every target is unhealthy, the ALB fails open and sends traffic to all of them, so "all targets unhealthy" doesn't take the site down by itself; alarm on the UnHealthyHostCount metric to see it.

Route 53 health checks

Route 53 has three kinds: endpoint checks (HTTP, HTTPS or TCP from checkers around the world, optionally matching a string in the response), calculated checks (healthy when enough child checks are healthy) and CloudWatch alarm checks, which follow an alarm's data stream. An endpoint is unhealthy when fewer than 18% of checkers report it healthy. Alarm-based checks only work with standard-resolution metrics, no metric math and no "M out of N" alarms, and the alarm must be in the same account.

Route 53 health check metrics exist only in US East (N. Virginia). An alarm on HealthCheckStatus created in any other Region has no data, whatever Region the endpoint is in.

AWS Health security events

Events AWS raises about your account

AWS Health sends events to EventBridge with source aws.health and detail-type AWS Health Event (or AWS Health Abuse Event for abuse reports). Some are security events. The most testable is AWS_RISK_CREDENTIALS_EXPOSED (service RISK): AWS found one of your IAM access keys in a public code repository and has temporarily restricted what the key can do. AWS publishes a sample response that deletes the key, looks up its last 24 hours of activity in CloudTrail and notifies the team.

Rule for exposed access keys (EventBridge event pattern, us-east-1) 
{
  "source": ["aws.health"],
  "detail-type": ["AWS Health Event"],
  "detail": {
    "service": ["RISK"],
    "eventTypeCode": ["AWS_RISK_CREDENTIALS_EXPOSED"]
  }
}

Events for global services such as IAM appear only in us-east-1, so this rule must be created there. Every Region's events are also copied to a backup Region (us-west-2, or us-east-1 for us-west-2's own events) with backupEvent set to true, so filter on it or deduplicate. With the organizational view turned on, the management account or a delegated administrator gets one feed of every member account's events, in the AWS Health console and on its own EventBridge bus.

"Automatically respond when AWS detects that an access key was published on GitHub" points to an EventBridge rule on AWS_RISK_CREDENTIALS_EXPOSED in us-east-1, triggering Lambda or Step Functions to deactivate the key.

Aggregating security events

Skill 1.1.3Aggregate security and monitoring events.

The delegated administrator pattern

One security tooling account sees everything

GuardDuty, Security Hub CSPM, Macie, Amazon Inspector and Amazon Detective all work the same way in an organization. The management account names a delegated administrator (in the running example, the security tooling account). That account then enables the service for member accounts, turns on auto-enable so new accounts join without anyone acting, and sees all member findings. These services are Regional, so the designation and settings are made in each Region you use. How the Security OU and these accounts fit into the organization is covered in the Solutions Architect guide's multi-account section; account strategy in depth is Task 6.1.

For GuardDuty, the delegated administrator runs this in each Region. ALL also enables existing members (it can take up to 24 hours); NEW covers only accounts that join later; changing to NONE doesn't disable anyone.

Enable GuardDuty and two protection plans for every member (AWS CLI, in the security tooling account) 
# Run once per Region; the detector ID is the administrator's own detector in that Region
aws guardduty update-organization-configuration \
  --detector-id 12abc34d567e8fa901bc2d34EXAMPLE \
  --auto-enable-organization-members ALL \
  --features '[{"Name": "S3_DATA_EVENTS", "AutoEnable": "ALL"},
               {"Name": "RUNTIME_MONITORING", "AutoEnable": "ALL",
                "AdditionalConfiguration": [{"Name": "EKS_ADDON_MANAGEMENT", "AutoEnable": "ALL"},
                                            {"Name": "ECS_FARGATE_AGENT_MANAGEMENT", "AutoEnable": "ALL"}]}]'

Some settings belong to the administrator only and apply to every member: GuardDuty suppression rules, trusted and threat lists, and how often updated findings are published. EventBridge rules in the administrator account fire for member findings too, so one rule can cover the organization; filter on detail.accountId when a rule is for one account.

Amazon Security Lake is the exception. Its delegated administrator is registered with the Security Lake API (aws securitylake register-data-lake-delegated-administrator), not with the Organizations command, it's the same account in every Region, and AWS recommends the log archive account rather than the security tooling account. Removing that delegated administrator deletes the data lake.

Security Hub CSPM across accounts and Regions

Central configuration and the home Region

With central configuration, the delegated administrator manages Security Hub CSPM from one home Region (the console used to call it the aggregation Region, and some API fields still do). Configuration policies (up to 20) say whether Security Hub CSPM is on, which standards are enabled, which controls are on or off and any custom control parameters. A policy is applied to the root, an OU or an account, and children inherit it. Accounts that are centrally managed can't change their own standards or controls.

A policy lists either the controls to enable (everything else is off, including controls AWS adds later) or the controls to disable (everything else is on, including new controls). Most organizations want the second, so new controls arrive automatically.

Org policy: FSBP on, one control off, one parameter changed (AWS CLI, home Region us-east-1) 
aws securityhub create-configuration-policy \
  --name "org-baseline" \
  --configuration-policy '{
    "SecurityHub": {
      "ServiceEnabled": true,
      "EnabledStandardIdentifiers": [
        "arn:aws:securityhub:us-east-1::standards/aws-foundational-security-best-practices/v/1.0.0"
      ],
      "SecurityControlsConfiguration": {
        "DisabledSecurityControlIdentifiers": ["CloudTrail.2"],
        "SecurityControlCustomParameters": [
          {
            "SecurityControlId": "ACM.1",
            "Parameters": { "daysToExpiration": { "ValueType": "CUSTOM", "Value": { "Integer": 15 } } }
          }
        ]
      }
    }
  }'

Cross-Region aggregation

A finding aggregator in the home Region replicates findings, finding updates, insights, control statuses and security scores from linked Regions, at no extra cost. Updates replicate both ways, so closing a finding in the home Region closes it in its own Region too. It only collects from Regions where Security Hub CSPM is enabled; it doesn't enable it there. The linking modes are ALL_REGIONS and ALL_REGIONS_EXCEPT_SPECIFIED (both add new Regions automatically), SPECIFIED_REGIONS (doesn't), and NO_REGIONS. An opt-in Region can be linked but can't be the home Region.

Aggregate every Region into us-east-1 (AWS CLI, in the home Region) 
aws securityhub create-finding-aggregator \
  --region us-east-1 \
  --region-linking-mode ALL_REGIONS

ASFF in brief

Security Hub CSPM findings use the AWS Security Finding Format (ASFF, SchemaVersion 2018-10-08). The fields that show up in questions are ProductArn (who produced it, for example arn:aws:securityhub:us-east-1::product/aws/guardduty), Severity.Label (INFORMATIONAL to CRITICAL), Workflow.Status (NEW, NOTIFIED, RESOLVED, SUPPRESSED), Compliance.Status for control findings (PASSED, FAILED, WARNING, NOT_AVAILABLE) and RecordState (ACTIVE or ARCHIVED). Producers send findings with BatchImportFindings; analysts and tools change workflow, severity and notes with BatchUpdateFindings.

Other aggregation paths

Amazon Security Lake

Security Lake keeps security data in S3 buckets in your own account, converted to the Open Cybersecurity Schema Framework (OCSF) in Apache Parquet, with one Lake Formation table per source. Its native sources are CloudTrail management events, CloudTrail data events for S3 and Lambda, EKS audit logs, Route 53 Resolver query logs, Security Hub CSPM findings, VPC Flow Logs and AWS WAF logs. GuardDuty, Inspector and Macie findings arrive only through the Security Hub CSPM findings source. A rollup Region collects data from contributing Regions. Storage, subscribers and analysis are covered in Task 1.2.

Collect Security Hub CSPM findings from every account (AWS CLI, Security Lake delegated administrator) 
# Omitting "accounts" means every account in the organization
aws securitylake create-aws-log-source \
  --sources '[{"regions": ["us-east-1", "us-west-2"], "sourceName": "SH_FINDINGS", "sourceVersion": "2.0"}]'

A central EventBridge bus

When events that no delegated administrator collects (application security events, custom detections) need to reach the security team, member accounts send them to an event bus in the security tooling account. The bus's resource policy allows events:PutEvents for the organization with the aws:PrincipalOrgID condition. The sending rule needs an IAM role for the cross-account target, and forwarding isn't transitive: an event received from one account and sent on to a third isn't delivered.

Let every account in the organization send to the security bus (event bus resource policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOrgPutEvents",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "events:PutEvents",
      "Resource": "arn:aws:events:us-east-1:222222222222:event-bus/security-events",
      "Condition": { "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" } }
    }
  ]
}

"Findings from all accounts and all Regions in one place, with new accounts included automatically" points to delegated administrator + auto-enable + a Security Hub CSPM finding aggregator. "Keep normalized security logs for a year and query them with SQL" points to Security Lake (CloudTrail Lake closed to new customers on 31 May 2026).

Metrics, alerts and dashboards

Skill 1.1.4Create metrics, alerts, and dashboards to detect anomalous data and events (for example, Amazon GuardDuty, Amazon Security Lake, AWS Security Hub, Amazon Macie).

GuardDuty findings

Severity and attack sequences

GuardDuty severity is a number from 1.0 to 10.0: Low 1.0–3.9, Medium 4.0–6.9, High 7.0–8.9 and Critical 9.0–10.0. Critical findings come from Extended Threat Detection (launched December 2024), which links API activity and existing findings over a rolling 24-hour window into one attack sequence finding, such as AttackSequence:IAM/CompromisedCredentials or AttackSequence:EKS/CompromisedCluster. It's on by default at no extra cost, and it covers more when S3 Protection, EKS Protection and Runtime Monitoring are on.

Alerting with EventBridge

New GuardDuty findings reach EventBridge in near real time with source aws.guardduty and detail-type GuardDuty Finding. Repeat occurrences of an existing finding are published on a schedule the administrator sets: every 15 minutes, 1 hour or 6 hours (the default). A numeric match keeps the rule short.

High and critical GuardDuty findings from any member account (EventBridge event pattern) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }]
  }
}

For retention beyond 90 days, export findings to S3. The export requires a KMS key whose policy lets guardduty.amazonaws.com call kms:GenerateDataKey, and the key and bucket must be in the same Region. The administrator's export includes member findings from that Region.

A GuardDuty suppression rule archives matching findings as they arrive, and suppressed findings aren't sent to Security Hub CSPM, S3, Detective or EventBridge. They're also not used as signals by Extended Threat Detection, so a broad suppression rule can hide the start of an attack sequence. Suppress narrowly (a known scanner's IP, a specific finding type on a specific resource), or add the scanner to a trusted list.

Macie and Security Hub CSPM findings

Macie

Macie raises two kinds of finding. Policy findings report a bucket's security getting worse: public access block disabled, the bucket made public, shared or replicated outside the account, encryption turned off. They're only raised for changes made after Macie was enabled. Sensitive data findings report credentials, financial or personal data, or a custom identifier match in an object. Both go to EventBridge (source aws.macie, detail-type Macie Finding). By default only policy findings are published to Security Hub CSPM; sensitive data findings have to be added in the publication settings.

"Macie was enabled yesterday, but no finding shows that bucket has been public for a year" is expected behavior: policy findings cover changes after enablement. The bucket inventory on the Macie dashboard does show its current public status.

Security Hub CSPM to people and tickets

Every new or updated finding produces a Security Hub Findings - Imported event (source aws.securityhub). For analyst-driven actions, create a custom action (up to 50): an analyst selects findings in the console and chooses the action, which sends a Security Hub Findings - Custom Action event naming the action's ARN, and an EventBridge rule routes it to a ticketing Lambda function or a runbook. In the administrator account and home Region, both event types include member and linked-Region findings.

Route the "send to ticketing" custom action (EventBridge event pattern) 
{
  "source": ["aws.securityhub"],
  "detail-type": ["Security Hub Findings - Custom Action"],
  "resources": ["arn:aws:securityhub:us-east-1:222222222222:action/custom/send_to_ticketing"]
}

CloudWatch metrics and alarms on CloudTrail

CIS-style metric filters

When a trail delivers to CloudWatch Logs, a metric filter turns matching events into a metric, and an alarm notifies an SNS topic. The CIS AWS Foundations Benchmark defines a set of them: root user activity, unauthorized API calls, console sign-in without MFA, CloudTrail and KMS key changes, security group changes and more. Security Hub CSPM's checks for these (CloudWatch.1 to CloudWatch.14) only pass when the filter text is exactly the CIS one.

Alarm whenever the root user makes a call (AWS CLI, in the account that owns the trail's log group) 
# 1. Count root user activity that isn't an AWS service acting on the account's behalf
aws logs put-metric-filter \
  --log-group-name org-trail-logs \
  --filter-name RootUsage \
  --filter-pattern '{$.userIdentity.type="Root" && $.userIdentity.invokedBy NOT EXISTS && $.eventType !="AwsServiceEvent"}' \
  --metric-transformations metricName=RootUsageCount,metricNamespace=LogMetrics,metricValue=1,defaultValue=0

# 2. Alarm on any occurrence in five minutes
aws cloudwatch put-metric-alarm \
  --alarm-name root-usage \
  --namespace LogMetrics --metric-name RootUsageCount \
  --statistic Sum --period 300 --evaluation-periods 1 \
  --threshold 1 --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions arn:aws:sns:us-east-1:222222222222:security-alerts

The CloudWatch.x metric filter controls only exist in the CIS v1.2.0 and v1.4.0 standards in Security Hub CSPM. In CIS v3.0.0 and v5.0.0 (the version AWS recommends, added October 2025) they're manual checks. With an organization trail, the controls report no data in member accounts, because the log group lives in the trail owner's account.

Anomaly detection and dashboards

CloudWatch anomaly detection alarms learn a metric's normal band and alarm outside it, which suits counts such as UnauthorizedApiCalls that are never zero. CloudWatch Logs anomaly detection learns patterns in a log group over two weeks and flags new ones; AWS says it isn't suited to CloudTrail or VPC flow logs, so use it for application logs and let GuardDuty handle CloudTrail. Contributor Insights shows the top contributors in log data, for example the source IPs behind most WAF blocks. A composite alarm combines alarm states with AND, OR and NOT so one notification fires instead of five.

For one dashboard across accounts, CloudWatch cross-account observability links source accounts to a monitoring account (through Organizations, so new accounts join automatically); the setup is on the CloudOps guide's dashboards section. For findings rather than metrics, the Security Hub CSPM and new Security Hub consoles in the administrator account are the dashboards, and Security Lake data can be queried with Athena or visualized with Amazon Managed Grafana.

Automated assessments and investigations

Skill 1.1.5Create and manage automations to perform regular assessments and investigations (for example, by deploying AWS Config conformance packs, Security Hub, AWS Systems Manager State Manager).

AWS Config conformance packs

A set of rules deployed as one unit

A conformance pack is a YAML template of Config rules and their remediation actions, deployed as one unit to an account and Region, or with an organization conformance pack to every account. AWS publishes sample templates (Operational Best Practices for CIS, NIST 800-53, PCI DSS, HIPAA and others) in the awslabs/aws-config-rules repository; AWS notes the samples alone don't make you compliant. Config must be recording in every member account. Only the management account or a delegated administrator (up to 3, registered for config-multiaccountsetup.amazonaws.com) can deploy organization packs.

Deploy a CIS pack to every account except a sandbox (AWS CLI, Config delegated administrator) 
# Template from S3 (up to 300 KB); --template-body allows only 51,200 bytes inline.
# The optional delivery bucket name must start with "awsconfigconforms".
aws configservice put-organization-conformance-pack \
  --organization-conformance-pack-name org-cis-baseline \
  --template-s3-uri s3://awsconfigconforms-templates-222222222222/cis-level1.yaml \
  --delivery-s3-bucket awsconfigconforms-results-222222222222 \
  --excluded-accounts 333333333333

The pack is deployed by the service-linked role AWSServiceRoleForConfigConforms in each member, which can create the rules even when the member's own IAM policies deny it (SCPs don't restrict service-linked roles either). Rules are either change-triggered (when a resource in scope changes), periodic (on a schedule) or both. Remediation runs an SSM Automation document, manually or automatically with retries, for example AWS-DisableS3BucketPublicReadWrite on a bucket that fails a public-read rule. An aggregator gives a read-only view of compliance across the organization; you can't deploy rules through it.

Security Hub CSPM automations

Checks on a schedule you don't set

After a standard is enabled, Security Hub CSPM runs its checks within two hours (most within 25 minutes). Change-triggered checks then run when Config records a change; periodic checks run every 12 or 24 hours, and you can't change that. Control findings are consolidated: one finding per control across all enabled standards, updated in place when the status changes (since July 2025).

Automation rules

Automation rules change findings as they arrive: raise the severity of any finding on a resource tagged env=prod, set a note for a known exception, or mark findings from a dev account as SUPPRESSED. Criteria match ASFF fields (account, control ID, resource type and tags, severity, product and more); actions change severity, workflow status, note, types, criticality, confidence and user-defined fields. Rules are created in the administrator account, per Region, up to 100. They act on findings created or updated through BatchImportFindings after the rule exists, not on BatchUpdateFindings, and when several rules match, the one with the highest rule order number has the last word.

"A control isn't relevant to our environment" points to disabling the control in the configuration policy: no checks run and nothing is charged. Suppressing its findings with an automation rule keeps paying for checks you ignore.

State Manager and Amazon Inspector

Systems Manager State Manager

A State Manager association keeps managed instances in a defined state on a schedule: an SSM document, its parameters, targets (by tag, instance ID, resource group or all nodes) and a cron or rate expression of at least 30 minutes. It runs once immediately on creation unless you ask it to wait for the next cron interval. Typical security uses are keeping an endpoint agent installed and running, keeping the SSM Agent updated and running inventory or CIS scripts. Association compliance feeds Security Hub CSPM control SSM.3. AWS is phasing out the service-linked role for State Manager in favour of a role you pass as AssociationDispatchAssumeRole.

Keep the SSM Agent current on every web server weekly (AWS CLI) 
aws ssm create-association \
  --association-name "update-ssm-agent-weekly" \
  --name AWS-UpdateSSMAgent \
  --targets Key=tag:ServerRole,Values=WebServer \
  --schedule-expression "rate(7 days)"

Amazon Inspector: continuous vulnerability assessment

Inspector finds and keeps scanning EC2 instances, ECR images, Lambda functions, AMIs (since September 2026) and code repositories, rescanning when packages change and when new CVEs are published, and closing findings once fixed. The delegated administrator enables it for the organization and auto-enables new members. Code security (since June 2025) scans repositories in GitHub or GitLab Self Managed with SAST, SCA (dependencies) and IaC rules, on push and pull request events or weekly or monthly. It's the scanner to use where the exam guide names Amazon CodeGuru Security, which is no longer in the AWS documentation.

Scan every repository on push, pull request and weekly (AWS CLI, Inspector delegated administrator) 
aws inspector2 create-code-security-scan-configuration \
  --name org-default \
  --level ORGANIZATION \
  --configuration '{"ruleSetCategories": ["SAST", "SCA", "IAC"],
                    "continuousIntegrationScanConfiguration": {"supportedEvents": ["PUSH", "PULL_REQUEST"]},
                    "periodicScanConfiguration": {"frequency": "WEEKLY"}}' \
  --scope-settings projectSelectionScope=ALL

Investigations

Amazon Detective and GuardDuty Investigation

Amazon Detective builds a behavior graph from CloudTrail, VPC Flow Logs and GuardDuty findings (plus optional EKS audit logs and Security Hub CSPM findings) and keeps up to a year of history, so an analyst can see what a role or IP did before and after a finding. It no longer requires GuardDuty to be enabled (since February 2024), uses the same delegated administrator pattern, and groups related findings with generated summaries. GuardDuty has added its own AI-assisted Investigation feature, in preview since June 2026. How investigations fit into incident response is Task 2.2.

  1. DetectGuardDuty, Macie, Inspector and Config raise findings in member accounts.
  2. CollectThe delegated administrator receives them; Security Hub CSPM aggregates them into the home Region.
  3. TriageAutomation rules adjust severity and workflow; the new Security Hub correlates them into exposures.
  4. AlertEventBridge rules on high-severity findings notify the team or open tickets.
  5. InvestigateDetective and Security Lake show what happened around the finding.

Status changes. The Systems Manager Explorer page will be deprecated on 31 December 2026 (its resource data sync moves to OpsCenter), so don't design new dashboards around it. AWS Audit Manager can't be set up in new accounts from 30 April 2026; for evidence of compliance, use Config conformance packs and Security Hub CSPM standards (Task 6.3).

Key takeaways

  • Map each workload to its threats: GuardDuty everywhere (foundational sources need no logging setup), S3 Protection and Macie for data, EKS Protection, Runtime Monitoring and Inspector for containers, AI Protection for Bedrock and SageMaker AI.
  • Health: ALB health checks fail open when every target is unhealthy; Route 53 health check metrics live only in us-east-1; AWS_RISK_CREDENTIALS_EXPOSED and other global Health events need a us-east-1 rule.
  • Aggregate with a delegated administrator in the security tooling account plus auto-enable (ALL includes existing accounts), per Region. Security Lake's delegated administrator is registered with its own API, usually the log archive account.
  • Security Hub CSPM: central configuration policies from a home Region (a disabled-controls list keeps new controls on), a free two-way finding aggregator, ASFF findings. The new Security Hub correlates CSPM, Inspector, GuardDuty and Macie in OCSF and turns CSPM on.
  • Alerts: GuardDuty severity 1–10 (attack sequences are Critical), EventBridge GuardDuty Finding with a numeric match, export to S3 needs a same-Region KMS key; suppression hides findings everywhere, including from Extended Threat Detection.
  • Macie policy findings only cover changes after enablement and are the only Macie findings sent to Security Hub CSPM by default. CIS metric filter controls exist only in CIS v1.2.0 and v1.4.0 and must match exactly.
  • Automation: organization conformance packs (template from S3, bucket prefix awsconfigconforms), Config remediation with SSM Automation, Security Hub CSPM automation rules (admin only, BatchImportFindings only, highest order wins), State Manager associations (30-minute minimum), Inspector continuous and code scanning.
