Task 5.2: Design and implement controls for data at rest

Protecting stored data: choosing who holds the keys and where encryption happens, proving data hasn't changed, keeping it exactly as long as required and no longer, and replicating and backing it up so ransomware or a deleted account can't take it away.

Overview

Task 5.2

Design and implement controls for data at rest.

Most AWS storage is encrypted by default now, so exam questions are rarely "turn on encryption". They ask which key type meets a requirement (who can audit it, rotate it, share it across accounts), whether encryption can be added later, how to prove data wasn't altered, and how to keep backups out of an attacker's reach. Object Lock, Backup Vault Lock, air-gapped vaults and point-in-time restores are in Task 2.2; key rotation, imported key material, multi-Region keys and secrets are Task 5.3.

Running example. The same company. The S3 data platform holds customer data that compliance says must use keys the company controls and can audit; the payments team needs a single-tenant HSM for a legacy application; order records must be kept for 7 years unchanged; and every backup must survive the loss of the prod account.

Choosing encryption at rest

Skill 5.2.1Design, implement, and configure data encryption at rest based on specific requirements (for example, by selecting the appropriate encryption key service such as AWS CloudHSM or AWS KMS or by selecting the appropriate encryption type such as client-side encryption or server-side encryption).

AWS calls AWS managed keys a legacy type no longer created for new services, which use AWS owned keys. For the running example's "keys we control and can audit", the answer is a customer managed key; "share encrypted snapshots, replicate or copy backups to another account" also always needs one.

KMS, CloudHSM or a custom key store

AWS KMS

KMS keys are held in FIPS 140-3 Level 3 validated HSMs and never leave KMS unencrypted. A key's spec is fixed at creation: SYMMETRIC_DEFAULT (AES-256-GCM, the one storage services use), RSA and ECC for encryption, signing or key agreement, HMAC keys, and now post-quantum ML-DSA (signing) and ML-KEM (key establishment). Encrypt takes at most 4 KB, so data is encrypted with envelope encryption: GenerateDataKey returns a data key in plaintext and encrypted under the KMS key; encrypt locally with the plaintext key, discard it, and store the encrypted key with the data. Services do this for you; the AWS Encryption SDK does it in your code.

Limit a key to use through particular services with kms:ViaService, so a role can use the data key for EBS and RDS but not call Decrypt directly:

The app role can use the key only through EC2 (EBS) and RDS (key policy statement, JSON) 
{
  "Sid": "UseOnlyThroughEbsAndRds",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111111111111:role/orders-app" },
  "Action": ["kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*", "kms:GenerateDataKey*", "kms:CreateGrant", "kms:DescribeKey"],
  "Resource": "*",
  "Condition": { "StringEquals": { "kms:ViaService": ["ec2.us-east-1.amazonaws.com", "rds.us-east-1.amazonaws.com"] } }
}

AWS CloudHSM

CloudHSM gives single-tenant HSMs in your VPC (cluster of hsm2m.medium HSMs across AZs, in FIPS or non-FIPS mode chosen at creation). You create and manage the HSM users and keys yourself, outside IAM, and AWS can't see them. Applications use standard interfaces: PKCS #11, JCE, Windows CNG and OpenSSL. Choose it when a requirement says single-tenant or customer-exclusive HSM, or for uses KMS doesn't cover: SSL/TLS offload for web servers, Oracle TDE, a private CA's signing key, or applications that need PKCS #11. The payments team's legacy application in the running example is that case.

Custom key stores

A CloudHSM key store lets KMS keys live in your CloudHSM cluster (KMS integrations, your HSMs); an external key store keeps key material in an HSM outside AWS through a proxy (Task 5.3). Both support only symmetric encryption keys, have no SLA and limited throughput, and AWS advises using them only when regulation requires key material in a single-tenant or customer-controlled HSM, preferring a CloudHSM key store over an external one. Imported key material in a normal KMS key is often the simpler way to show control.

"Keys must be in a single-tenant HSM that only we control" points to CloudHSM (or a CloudHSM key store if services need KMS integration). "Encrypt S3 and EBS with keys we can audit and disable" points to a customer managed KMS key. "Data larger than 4 KB with KMS" points to envelope encryption.

Where encryption happens

Server-side options in S3

  • SSE-S3: S3-managed keys; the default for every bucket since January 2023, at no cost.
  • SSE-KMS: a KMS key (in the bucket's Region, symmetric). Uploads need kms:GenerateDataKey, downloads kms:Decrypt. S3 Bucket Keys cut KMS requests by up to 99% by deriving data keys from a short-lived bucket key; the encryption context becomes the bucket ARN, so key policy conditions on object ARNs stop matching.
  • DSSE-KMS: two independent layers of AES-256, for standards that demand multi-layer encryption; no Bucket Keys.
  • SSE-C: you send the key with each request and S3 never stores it. It's now blocked by default; requests that specify it get 403 until the bucket's BlockedEncryptionTypes is set to NONE.
Default SSE-KMS with the data platform key and a Bucket Key, and SSE-C kept blocked (AWS CLI) 
aws s3api put-bucket-encryption --bucket shop-data-111111111111 \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyID": "arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab"
      },
      "BucketKeyEnabled": true,
      "BlockedEncryptionTypes": { "EncryptionType": ["SSE-C"] }
    }]
  }'
Refuse uploads that name any other KMS key (S3 bucket policy statement, JSON) 
{
  "Sid": "RequireDataPlatformKey",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::shop-data-111111111111/*",
  "Condition": {
    "StringNotEqualsIfExists": {
      "s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab"
    }
  }
}

Changing the default doesn't re-encrypt existing objects; copy them in place with S3 Batch Operations. Objects encrypted with aws/s3 can't be shared with another account.

Client-side encryption

When data must be encrypted before it reaches AWS (so AWS never sees plaintext), encrypt in the application: the AWS Encryption SDK for any data (it can wrap each data key under several keys, such as KMS and an on-premises HSM), the Amazon S3 Encryption Client for S3 objects, and the AWS Database Encryption SDK (formerly the DynamoDB Encryption Client) to encrypt and sign individual DynamoDB attributes. The application then owns key handling; AWS services can't read, index or process the data.

Services that decide at creation

  • Encryption only at creation: RDS and Aurora (snapshot, copy the snapshot with encryption, restore), EFS (create a new encrypted file system and replicate), node-based ElastiCache (back up and restore into a new encrypted cluster). The KMS key of an RDS instance can't be changed either.
  • Changeable later: DynamoDB (always encrypted; switch between AWS owned, AWS managed and customer managed keys any time), Redshift (modify encryption in place), OpenSearch (enable on existing domains, not disable; manual snapshots aren't covered).
  • Message services: SQS (SSE-SQS by default or SSE-KMS, message body only), SNS and Kinesis (KMS, only data written after enabling). An SNS topic receiving CloudWatch alarm or EventBridge messages needs a customer managed key that allows those service principals.
  • EFS, FSx and Lambda: enforce EFS encryption with the elasticfilesystem:Encrypted condition (SCP or IAM); FSx for Lustre is always encrypted; Lambda environment variables are encrypted at rest (use a customer managed key to control who can read them, and Secrets Manager for real secrets).

"Encrypt an existing unencrypted RDS database" can't be done by modifying it. The answer is snapshot, copy with encryption, restore (or blue/green). The same "at creation only" rule catches EFS and node-based ElastiCache.

Protecting data integrity

Skill 5.2.2Design and configure mechanisms to protect data integrity (for example, S3 Object Lock, S3 Glacier Vault Lock, versioning, digital code signing, file validation).

Write once, read many

Object Lock, versioning and MFA delete

For new designs, WORM storage on AWS is S3 Object Lock (compliance and governance modes, legal holds; Task 1.2), with versioning underneath. Versioning alone keeps every version but lets anyone with s3:DeleteObjectVersion remove them; MFA delete adds a second factor for permanently deleting versions and changing the versioning state. MFA delete can only be enabled by the root user, only through the CLI or API, and can't be used on a bucket with lifecycle rules.

Turn on versioning with MFA delete (AWS CLI, root user credentials) 
aws s3api put-bucket-versioning --bucket audit-evidence-444444444444 \
  --versioning-configuration Status=Enabled,MFADelete=Enabled \
  --mfa "arn:aws:iam::444444444444:mfa/root-account-mfa-device 123456"

Object Lock protects versions from deletion, but not from losing their KMS key: if the key is deleted, locked objects may become unreadable. Protect the key too (Task 5.3).

Glacier Vault Lock

The original Glacier vault service has Vault Lock: initiate-vault-lock attaches a lock policy in an InProgress state for 24 hours to test, and complete-vault-lock makes it permanent; after that the policy can't be changed or deleted. Typical lock policies deny glacier:DeleteArchive for archives younger than the retention period. The vault service no longer accepts new customers, so this applies to existing vaults; S3 Glacier storage classes with Object Lock replace it.

Proving data hasn't changed

Checksums and validation

  • S3 checksums: SDKs and the console send a checksum with every upload and S3 rejects mismatches (BadDigest); the default since December 2024 is CRC64NVME, with SHA-256, SHA-512 and others available. The S3 Batch Operations Compute checksum operation calculates checksums of stored objects, in any storage class, without downloading or restoring them, and writes a report: periodic proof that the archive is intact.
  • CloudTrail log file validation proves logs weren't modified (Task 1.2).
  • DataSync always checks data in transit, and with VerifyMode ONLY_FILES_TRANSFERRED (recommended) or POINT_IN_TIME_CONSISTENT (all data, Basic mode only) also compares source and destination after the transfer.
  • KMS signatures and MACs: asymmetric keys sign and verify (aws kms sign, now including ML-DSA), and HMAC keys generate and verify MACs, for application data such as exported files or tokens.

Code signing

AWS Signer signs code and images (Lambda packages, container images through Notation, IoT firmware). A Lambda code signing configuration lists the allowed signing profiles and what to do with code that fails: Warn (the default, which still deploys it and records a metric) or Enforce (block). Layers must be signed too, and checks happen at deployment, with no runtime cost. Require a code signing configuration on every function with an IAM condition:

Functions can only be created with the company code signing configuration (identity policy statement, JSON) 
{
  "Sid": "RequireCodeSigning",
  "Effect": "Deny",
  "Action": "lambda:CreateFunction",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "lambda:CodeSigningConfigArn": "arn:aws:lambda:us-east-1:111111111111:code-signing-config:csc-0d4518bd353a0a7c6"
    }
  }
}

A code signing configuration left at the default Warn lets unsigned or tampered code deploy. Only Enforce blocks it, and it applies to new deployments, not code already running.

Lifecycle and retention

Skill 5.2.3Design automatic lifecycle management and retention solutions for data (for example, S3 Lifecycle policies, S3 Object Lock, Amazon EFS Lifecycle policies, Amazon FSx for Lustre backup policies).

S3 Lifecycle

Keep exactly as long as required

Lifecycle rules (up to 1,000 per bucket, filtered by prefix, tags and size) transition objects to cheaper classes and expire them. For versioned buckets, also expire noncurrent versions (otherwise "deleted" data stays forever), remove expired delete markers, and abort incomplete multipart uploads. For the 7-year order records: lock them with Object Lock for 7 years, move them to Glacier classes, and expire them after the retention ends.

Order records: to Glacier Instant Retrieval at 90 days, Deep Archive at 1 year, deleted after 7 years (S3 lifecycle configuration, JSON) 
{
  "Rules": [
    {
      "ID": "orders-7-years",
      "Status": "Enabled",
      "Filter": { "Prefix": "orders/" },
      "Transitions": [
        { "Days": 90, "StorageClass": "GLACIER_IR" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 2557 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}

Applied with aws s3api put-bucket-lifecycle-configuration --bucket shop-data-111111111111 --lifecycle-configuration file://lifecycle.json.

  • Locks win: a lifecycle expiration can't delete an Object Lock-protected version; it only adds a delete marker, and the version is removed after its retention ends.
  • Minimum durations (charged even if deleted early): 30 days for Standard-IA and One Zone-IA, 90 for Glacier Instant and Flexible Retrieval, 180 for Deep Archive. Objects under 128 KB aren't transitioned by default.
  • Lifecycle actions aren't in CloudTrail (they appear in server access logs), and billing changes when the rule is met even if the action runs later. For deletion deadlines that must be proven, check S3 Inventory's expiration date.
  • Intelligent-Tiering moves objects between access tiers automatically when access patterns are unknown.

File systems and volumes

EFS lifecycle

EFS moves files to Infrequent Access and Archive after a period without access, and back to Standard on first access:

IA after 30 days, Archive after 90, back to Standard when read (AWS CLI) 
aws efs put-lifecycle-configuration --file-system-id fs-0123456789abcdef0 \
  --lifecycle-policies '[{"TransitionToIA": "AFTER_30_DAYS"}, {"TransitionToArchive": "AFTER_90_DAYS"}, {"TransitionToPrimaryStorageClass": "AFTER_1_ACCESS"}]'

FSx backups

FSx for Lustre backs up persistent file systems that aren't linked to an S3 data repository (not scratch file systems): automatic daily backups kept 0 to 90 days (0 turns them off, the API default), plus user-initiated backups that never expire and survive deletion of the file system. FSx for Windows File Server has daily automatic backups on by default. For longer retention, cross-account copies and central policy, use AWS Backup.

Amazon Data Lifecycle Manager

DLM creates, copies and deletes EBS snapshots and EBS-backed AMIs by tag-based policy at no extra cost: up to four schedules, count or age retention, cross-Region copies (encrypted with a key you choose), cross-account sharing (only for unencrypted or customer-managed-key snapshots), fast snapshot restore and archiving. Default policies back up every volume or instance in a Region that has no recent backup, with 2 to 14 days of retention.

Daily snapshots of tagged volumes, keep 7, copy encrypted to us-west-2 (DLM policy details, JSON) 
{
  "PolicyType": "EBS_SNAPSHOT_MANAGEMENT",
  "ResourceTypes": ["VOLUME"],
  "TargetTags": [{ "Key": "backup", "Value": "daily" }],
  "Schedules": [{
    "Name": "daily",
    "CreateRule": { "Interval": 24, "IntervalUnit": "HOURS", "Times": ["03:00"] },
    "RetainRule": { "Count": 7 },
    "CopyTags": true,
    "CrossRegionCopyRules": [{
      "Target": "us-west-2",
      "Encrypted": true,
      "CmkArn": "arn:aws:kms:us-west-2:111111111111:key/abcd1234-ab12-cd34-ef56-abcdef123456",
      "CopyTags": true,
      "RetainRule": { "Interval": 7, "IntervalUnit": "DAYS" }
    }]
  }]
}

In AWS Backup, a rule that moves recovery points to cold storage must keep them at least 90 days after the move, and only some resource types (EFS, DynamoDB with advanced backup, EBS through snapshot archive and a few others) support cold storage.

Replication and backup

Skill 5.2.4Design and configure secure replication and backup solutions (for example, Amazon Data Lifecycle Manager, AWS Backup, ransomware protection, AWS DataSync).

S3 replication

Replicating encrypted and locked objects

Cross-Region and same-Region replication copy new objects (versioning on both buckets, an IAM role S3 assumes). Objects encrypted with SSE-KMS or DSSE-KMS aren't replicated unless the rule opts in with SseKmsEncryptedObjects and names a key in the destination Region; the role needs kms:Decrypt on the source key and kms:Encrypt on the destination key. Across accounts, the keys must be customer managed.

Replicate the data platform, including SSE-KMS objects, to the DR bucket in another account within 15 minutes (S3 replication configuration, JSON) 
{
  "Role": "arn:aws:iam::111111111111:role/s3-replication",
  "Rules": [
    {
      "ID": "dr-copy",
      "Status": "Enabled",
      "Priority": 1,
      "Filter": {},
      "DeleteMarkerReplication": { "Status": "Disabled" },
      "SourceSelectionCriteria": { "SseKmsEncryptedObjects": { "Status": "Enabled" } },
      "Destination": {
        "Bucket": "arn:aws:s3:::shop-data-dr-888888888888",
        "Account": "888888888888",
        "AccessControlTranslation": { "Owner": "Destination" },
        "EncryptionConfiguration": { "ReplicaKmsKeyID": "arn:aws:kms:us-west-2:888888888888:key/5678efgh-56ef-78gh-90ij-5678efgh90ij" },
        "ReplicationTime": { "Status": "Enabled", "Time": { "Minutes": 15 } },
        "Metrics": { "Status": "Enabled", "EventThreshold": { "Minutes": 15 } }
      }
    }
  ]
}
  • Replication doesn't replicate deletes of specific versions, which protects the copy from malicious deletion; delete markers replicate only if enabled.
  • Existing objects, failed objects and replicas need S3 Batch Replication; Replication Time Control (15 minutes) doesn't cover it.
  • The owner override ("Owner": "Destination") gives the destination account ownership of replicas; with bucket owner enforced on the destination, ownership is automatic.
  • Object Lock buckets can replicate to Object Lock destinations, and retention settings travel with the objects.

AWS Backup

Plans, copies and vault policies

A backup plan schedules backups of selected resources into a vault, with lifecycle and copy actions to other Regions or accounts; Organizations backup policies deploy plans to every account. A vault access policy can deny deleting recovery points to everyone but a break-glass role, and AWS Backup Vault Lock makes retention immutable (Task 2.2).

Only the backup admin role can delete recovery points in the prod vault (backup vault access policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyDeleteExceptBackupAdmin",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "backup:DeleteRecoveryPoint",
      "Resource": "*",
      "Condition": { "ArnNotEquals": { "aws:PrincipalArn": "arn:aws:iam::111111111111:role/backup-admin" } }
    }
  ]
}

A vault access policy only controls AWS Backup APIs; it doesn't stop someone deleting an EBS snapshot or RDS snapshot through EC2 or RDS, so add IAM and SCP denies (or EBS Snapshot Lock). Independent encryption (the vault's key, regardless of the source) applies only to fully managed resource types such as S3, EFS and DynamoDB with advanced backup; EBS, RDS, Aurora and FSx backups keep the source's key, so the source must be encrypted with a customer managed key for cross-account copies. AWS Backup Audit Manager frameworks report whether backups exist, are encrypted and are copied as required.

Ransomware resilience

  1. Back up everything by policyOrganizations backup policies so no account can skip it.
  2. Copy out of the accountCopy actions to a vault in a separate backup account (or a logically air-gapped vault), so the prod account's credentials can't reach the copies.
  3. Make retention immutableVault Lock in compliance mode, EBS Snapshot Lock, S3 Object Lock.
  4. Keep the keys safeCustomer managed keys in the backup account, with deletion denied by SCP.
  5. Prove you can restore cleanMalware scanning of recovery points and restore testing.

EBS Snapshot Lock and Recycle Bin

EBS Snapshot Lock (November 2023) locks snapshots for 1 to 36,500 days. Governance mode can be changed by authorized users; compliance mode allows changes only during an optional cooling-off period of up to 72 hours, after which the lock can only be extended. Recycle Bin keeps deleted snapshots, EBS-backed AMIs and (since November 2025) EBS volumes for a retention period, so an accidental or malicious deletion can be undone; a locked Region-level rule can't be changed or deleted without a 7 to 30 day unlock delay.

Lock a snapshot in compliance mode after a 24-hour cooling-off, and keep deleted snapshots for 30 days (AWS CLI) 
aws ec2 lock-snapshot --snapshot-id snap-0abcdef1234567890 \
  --lock-mode compliance --cool-off-period 24 --lock-duration 365

aws rbin create-rule --resource-type EBS_SNAPSHOT \
  --retention-period RetentionPeriodValue=30,RetentionPeriodUnit=DAYS \
  --description "Keep deleted snapshots for 30 days" \
  --lock-configuration 'UnlockDelay={UnlockDelayUnit=DAYS,UnlockDelayValue=7}'

Other replication paths

  • RDS cross-Region automated backups replicate snapshots and logs for point-in-time restore in another Region, with a KMS key in the destination Region (start-db-instance-automated-backups-replication).
  • DynamoDB export to S3 (needs point-in-time recovery) copies tables to a bucket in another account or Region without consuming capacity.
  • AWS DataSync moves data between on premises, other clouds and AWS storage with TLS in transit and post-transfer verification, writing into encrypted S3, EFS or FSx destinations through an IAM role.

"Backups must survive compromise of the production account" points to cross-account copies into a locked vault (or a logically air-gapped vault). "Replicate KMS-encrypted objects to another Region" points to SseKmsEncryptedObjects plus a destination key. "Recover snapshots someone deleted" points to Recycle Bin.

Key takeaways

  • Keys: AWS owned (invisible, free), AWS managed (aws/, auditable, no policy control, not cross-account), customer managed (full control, cross-account). KMS HSMs are FIPS 140-3 Level 3; 4 KB Encrypt limit means envelope encryption; kms:ViaService limits use to services.
  • CloudHSM for single-tenant HSMs you manage (PKCS #11, TLS offload, Oracle TDE); custom key stores only when regulation demands, symmetric keys only, no SLA.
  • S3: SSE-S3 default; SSE-KMS with Bucket Keys (encryption context becomes the bucket ARN); DSSE-KMS for dual layers; SSE-C blocked by default since April 2026; client-side with the Encryption SDK, S3 Encryption Client or Database Encryption SDK.
  • Encrypt at creation only: RDS and Aurora, EFS, node-based ElastiCache; DynamoDB keys switchable, Redshift and OpenSearch can be enabled later.
  • Integrity: Object Lock (keys still matter), versioning with MFA delete (root, CLI, no lifecycle), Glacier Vault Lock (24-hour test, then permanent; service closed to new customers), CRC64NVME checksums and Batch Compute checksum, DataSync verification, KMS signing and HMAC, Lambda code signing in Enforce mode.
  • Lifecycle: transitions and expiration including noncurrent versions and incomplete uploads; locks override expiration; minimum durations 30/90/180 days; EFS IA and Archive; FSx for Lustre backups for persistent file systems only; DLM for EBS snapshots and AMIs; Backup cold storage needs 90 more days.
  • Replication and backup: S3 replication needs opt-in for SSE-KMS objects and doesn't replicate version deletes; AWS Backup plans, copy actions, vault access policies (Backup APIs only), independent encryption for fully managed types; ransomware pattern of cross-account immutable copies; EBS Snapshot Lock and Recycle Bin with rule lock.
