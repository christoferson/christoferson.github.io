Overview

Task 1.2

Design and implement logging solutions.

Task 1.1 was about findings: conclusions that detectors such as GuardDuty reach. This task is about the raw evidence underneath them. Questions give a requirement (keep API activity for seven years, prove logs weren't altered, let a third-party SIEM read everything, find which host made a DNS query) and ask for the source, the configuration and the store that meet it. Most correct answers share three habits: log at the organization level so new accounts are covered, deliver to a separate log archive account that workload administrators can't touch, and encrypt and lock what's stored there.

Running example. The same company as in Task 1.1: AWS Organizations with a management account (555555555555), a security tooling account (222222222222), a log archive account (444444444444) and workload accounts (prod is 111111111111). It runs a web application behind CloudFront, AWS WAF and an Application Load Balancer, containers on EKS and ECS on Fargate, a data platform on S3, and a generative AI assistant on Amazon Bedrock, in us-east-1 with us-west-2 for disaster recovery. VPCs in each account connect through a transit gateway in a shared network account.

Choosing log sources and storage

Skill 1.2.1Identify sources for log ingestion and storage based on requirements.

What each source records

CloudTrail event types

CloudTrail records who called which AWS API, from where and with what result. It has four kinds of event, and only the first is logged by default:

  • Management events: control-plane calls such as AttachRolePolicy, CreateSubnet or StopLogging, plus sign-in events such as ConsoleLogin. The first copy delivered to S3 is free.
  • Data events: high-volume calls on resources: S3 object reads and writes, Lambda invocations, DynamoDB item activity and many more. They're charged ($0.10 per 100,000 events) and must be selected.
  • Network activity events: API calls made through your VPC endpoints, recorded for the endpoint owner, including calls the endpoint policy denied (VpceAccessDenied). Generally available since February 2025 for more than 70 services. Use them to spot credentials from outside the organization trying to use your endpoints.
  • Insights events: unusual API call rates or error rates compared with a learned baseline, for management events and (on trails only) data events.

The console's Event history shows only the last 90 days of management events, per account and per Region. Anything longer, or across accounts, needs a trail.

Service and application logs

Beyond CloudTrail, each layer of the running example has its own log: CloudFront and ALB access logs (every request), WAF logs (every request the web ACL evaluated, with the rule that matched), EKS control plane audit logs, VPC Flow Logs and transit gateway flow logs (IP traffic), Route 53 Resolver query logs (DNS lookups from VPCs), Network Firewall logs, and application and OS logs collected by the CloudWatch agent. Network sources are compared in Skill 1.2.6.

For S3 object access, AWS recommends CloudTrail data events over S3 server access logs: they arrive in about five minutes, support integrity validation and can be filtered by prefix. Server access logs are best effort and can be hours late, but they're the only one of the two that records requests that failed authentication (bad credentials) and lifecycle actions. CloudTrail does record authorization failures (AccessDenied) and anonymous requests.

The three combine. In the running example, the organization trail writes to an S3 bucket in the log archive account for seven-year retention, also delivers to CloudWatch Logs for alarms, and Security Lake collects CloudTrail, VPC Flow Logs, Resolver logs, WAF logs and Security Hub CSPM findings for the security team's analytics.

CloudWatch Logs has two main log classes. Standard supports everything. Essentials (the renamed Infrequent Access class) costs half as much to ingest but has no subscription filters, metric filters, Live Tail or anomaly detection; it still supports Logs Insights, KMS and masking. A log group's class can't be changed later, so logs that feed alarms or a SIEM must be Standard.

Configuring logging

Skill 1.2.2Configure logging for AWS services and applications (for example, by configuring an AWS CloudTrail trail for an organization, by creating a dedicated Amazon CloudWatch logging account, by configuring the Amazon CloudWatch Logs agent).

An organization trail

Who creates it, and what members can do

An organization trail logs every account in the organization, including accounts that join later. It needs all features enabled in Organizations and trusted access for cloudtrail.amazonaws.com. It can be created by the management account or by a CloudTrail delegated administrator (up to three per organization); the management account still owns it. Member accounts can see the trail but can't stop, change or delete it, which is the point: a compromised workload administrator can't turn off the evidence.

Create and start an organization trail (AWS CLI, management account or CloudTrail delegated administrator) 
# Console-created organization trails are always multi-Region; on the CLI you must say so.
# Log file validation is off by default; turn it on.
aws cloudtrail create-trail \
  --name org-trail \
  --s3-bucket-name org-cloudtrail-444444444444 \
  --is-organization-trail \
  --is-multi-region-trail \
  --enable-log-file-validation \
  --kms-key-id arn:aws:kms:us-east-1:444444444444:key/1234abcd-12ab-34cd-56ef-1234567890ab

# A new trail doesn't log until you start it
aws cloudtrail start-logging --name org-trail

The bucket policy in the log archive account

The bucket lives in the log archive account, and its policy lets the CloudTrail service write under AWSLogs/<organization ID>/ (one folder per member account below it). The aws:SourceArn condition must use the management account ID in the trail ARN, even if a delegated administrator created the trail. AWS's sample policy also keeps a statement for AWSLogs/<management account ID>/ in case the trail is converted back to an account trail.

Organization trail bucket policy (S3 bucket policy JSON, log archive account) 
{
  "Version": "2012-10-17",

Encrypting with KMS

By default, log files are encrypted with SSE-S3. With --kms-key-id, CloudTrail uses SSE-KMS for the log files and, since May 2025, the digest files too. The key policy needs three things: kms:GenerateDataKey* for CloudTrail, kms:DescribeKey for CloudTrail, and kms:Decrypt for whoever reads the logs. Reading a log then needs permission on both the bucket and the key, which keeps logs private even from someone with broad S3 access.

Let CloudTrail encrypt with the key (one statement of the KMS key policy) 
{
  "Sid": "AllowCloudTrailEncryptLogs",
  "Effect": "Allow",
  "Principal": { "Service": "cloudtrail.amazonaws.com" },
  "Action": "kms:GenerateDataKey*",
  "Resource": "*",
  "Condition": {
    "StringEquals": { "aws:SourceArn": "arn:aws:cloudtrail:us-east-1:555555555555:trail/org-trail" },
    "StringLike": { "kms:EncryptionContext:aws:cloudtrail:arn": "arn:aws:cloudtrail:*:555555555555:trail/*" }
  }
}

The readers' statement allows kms:Decrypt with the condition "Null": { "kms:EncryptionContext:aws:cloudtrail:arn": "false" }, so the permission only works on CloudTrail logs. If the key is disabled or its policy is wrong, CloudTrail can't deliver logs at all.

Choosing events with advanced event selectors

Data events for one bucket, KMS noise out

Advanced event selectors filter on fields such as eventCategory, resources.type, resources.ARN, eventName, eventSource, readOnly and userIdentity.arn, with operators Equals, NotEquals, StartsWith, NotStartsWith, EndsWith and NotEndsWith; there are no wildcards. Setting advanced selectors replaces any basic ones. KMS Encrypt, Decrypt and GenerateDataKey calls are over 99% of KMS events, so excluding kms.amazonaws.com from management events cuts volume sharply, at the cost of losing those records.

All management events except KMS, plus data events on the customer-data bucket (AWS CLI) 
# For S3 objects, StartsWith with a trailing "/" is required to match every object ARN.
# Leaving out readOnly logs both read and write events.
aws cloudtrail put-event-selectors \
  --trail-name org-trail \
  --advanced-event-selectors '[
    {
      "Name": "Management events except KMS",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Management"] },
        { "Field": "eventSource", "NotEquals": ["kms.amazonaws.com"] }
      ]
    },
    {
      "Name": "S3 data events on customer data",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::S3::Object"] },
        { "Field": "resources.ARN", "StartsWith": ["arn:aws:s3:::customer-data-111111111111/"] }
      ]
    }
  ]'

Network activity events use eventCategory NetworkActivity and one selector per eventSource, optionally filtered to errorCode VpceAccessDenied to keep only calls the endpoint policy blocked.

Don't log S3 data events for the bucket the trail writes to: every delivery creates more events about itself. Deliver to a bucket in the log archive account and exclude it (or simply don't select it).

Proving logs weren't changed

Log file integrity validation

With validation on, CloudTrail delivers a digest file every hour to a CloudTrail-Digest folder in the same bucket. It lists the SHA-256 hash of every log file delivered in that hour, is signed with a per-Region private key, and contains the previous digest's signature, so the digests form a chain. Turning validation on only produces digests; you validate with the CLI, which detects modified, deleted or moved log and digest files.

Check a day of organization trail logs for one member account (AWS CLI) 
# Region-specific; --account-id is required for organization trails.
# Files must still be in their original S3 location to be validated.
aws cloudtrail validate-logs \
  --trail-arn arn:aws:cloudtrail:us-east-1:555555555555:trail/org-trail \
  --account-id 111111111111 \
  --start-time 2026-11-01T00:00:00Z \
  --end-time 2026-11-02T00:00:00Z \
  --region us-east-1 \
  --verbose

"Prove to auditors that CloudTrail logs haven't been modified or deleted" points to log file integrity validation plus validate-logs. "Make sure nobody can delete them, not even an administrator" points to S3 Object Lock in compliance mode (Skill 1.2.3).

A dedicated CloudWatch logging account

Log centralization rules (since September 2025)

The simplest way to get every account's CloudWatch Logs into the log archive account is cross-account cross-Region log centralization. The management account or a delegated administrator creates a centralization rule that selects source accounts or OUs, source Regions and log groups, and copies new log events to a destination account and Region, with an optional backup Region. Destination log group names can include ${source.accountId} and ${source.region} so accounts don't merge into one group. Only data ingested after the rule is created is copied. The first copy is free; each extra copy, including the backup Region, costs $0.05 per GB.

Cross-account subscriptions

The older pattern, still used when logs must stream to Kinesis Data Streams or Firehose for a SIEM, is a subscription. In the log archive account you create a destination in front of a stream, with a destination policy that lets the organization subscribe. Each sending account then adds a subscription filter that points at the destination. A log group can have up to five subscription filters, and each account can also have one account-level subscription filter per Region that covers every log group.

Accept subscriptions from the whole organization (destination access policy, log archive account) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "logs:PutSubscriptionFilter",
      "Resource": "arn:aws:logs:us-east-1:444444444444:destination:org-security-logs",
      "Condition": { "StringEquals": { "aws:PrincipalOrgID": ["o-exampleorgid"] } }
    }
  ]
}
Send every log group in a workload account, except the noisy ones (AWS CLI, account-level filter) 
# NOT IN is the only operator the selection criteria support.
# Exclude log groups on the delivery path to avoid a loop.
aws logs put-account-policy \
  --policy-name org-security-feed \
  --policy-type SUBSCRIPTION_FILTER_POLICY \
  --scope ALL \
  --selection-criteria 'LogGroupName NOT IN ["/aws/lambda/log-forwarder", "/app/debug"]' \
  --policy-document '{"DestinationArn": "arn:aws:logs:us-east-1:444444444444:destination:org-security-logs", "RoleArn": "arn:aws:iam::111111111111:role/CWLtoSubscriptionRole", "FilterPattern": "", "Distribution": "Random"}'

When the destination policy names the organization rather than individual accounts, each sender needs a role trusted by logs.amazonaws.com, passed as RoleArn. Subscriptions only work on Standard log groups.

Turning logging on everywhere: telemetry enablement rules

Centralizing only helps if the logs exist. CloudWatch telemetry enablement rules (2025) turn on logging for resource types across the organization, an OU or an account: VPC Flow Logs, Route 53 Resolver query logs, WAF logs, EKS control plane logs, ALB and NLB logs, CloudFront, S3 server access logs and others, including resources created later. OU and account rules can collect more than the organization rule but not less. An AWS Config rule with automatic remediation is the older way to achieve the same thing.

Protecting what's in CloudWatch Logs

KMS keys and masking

Log groups are always encrypted; for your own key, associate a customer managed key (CLI or API only for existing log groups). The key policy must allow the Regional service principal, for example logs.us-east-1.amazonaws.com, scoped with the kms:EncryptionContext:aws:logs:arn condition. Disabling the key later makes the data it encrypted unreadable.

A data protection policy finds sensitive data (credentials, financial data, personal data, IP addresses and up to 10 custom identifiers) as it's ingested, masks it everywhere it leaves (console, Logs Insights, metric and subscription filters) and can report findings. Only principals with logs:Unmask see the original. It applies to a log group or the whole account, and only to data ingested after it's set.

Mask email addresses and AWS secret keys in the app's log group (data protection policy JSON) 
{
  "Name": "app-data-protection",
  "Version": "2021-06-01",
  "Statement": [
    {
      "Sid": "audit",
      "DataIdentifier": [
        "arn:aws:dataprotection::aws:data-identifier/EmailAddress",
        "arn:aws:dataprotection::aws:data-identifier/AwsSecretKey"
      ],
      "Operation": { "Audit": { "FindingsDestination": {} } }
    },
    {
      "Sid": "mask",
      "DataIdentifier": [
        "arn:aws:dataprotection::aws:data-identifier/EmailAddress",
        "arn:aws:dataprotection::aws:data-identifier/AwsSecretKey"
      ],
      "Operation": { "Deidentify": { "MaskConfig": {} } }
    }
  ]
}

The policy always has exactly these two statements, with the same identifiers in both: one that audits and one that masks. It's applied with aws logs put-data-protection-policy --log-group-identifier ... --policy-document file://policy.json.

The CloudWatch agent

Collecting OS and application logs

The agent ships log files and Windows event logs from EC2 and on-premises servers. Installing it, metrics and the wizard are covered in the CloudOps guide's agent section; the security points are below. The logs section lists files with file_path, log_group_name, log_stream_name and optionally retention_in_days and log_group_class; Windows channels such as Security go under windows_events.

Collect the Linux auth log and Windows logon events (CloudWatch agent configuration, logs section) 
{
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "file_path": "/var/log/secure",
            "log_group_name": "/prod/os/secure",
            "log_stream_name": "{instance_id}",
            "retention_in_days": 365
          }
        ]
      },
      "windows_events": {
        "collect_list": [
          {
            "event_name": "Security",
            "event_ids": [4624, 4625, 4672],
            "log_group_name": "/prod/windows/security",
            "log_stream_name": "{instance_id}"
          }
        ]
      }
    }
  }
}

Store the configuration in Parameter Store with a name starting AmazonCloudWatch-, because the managed policies only allow those parameters: CloudWatchAgentServerPolicy on every instance can read them, CloudWatchAgentAdminPolicy (which can also write them) belongs only on the instance used to create the configuration. Each instance then loads it with amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s -c ssm:AmazonCloudWatch-linux, or the fleet is configured with the AmazonCloudWatch-ManageAgent Run Command document. To send logs to another account, set credentials.role_arn in the configuration to a role in that account.

Setting retention_in_days on a log group that already exists deletes every event older than that many days. The agent also needs logs:PutRetentionPolicy to set it.

Log storage and data lakes

Skill 1.2.3Implement log storage and log data lakes (for example, Security Lake) and integrate with third-party security tools.

A tamper-resistant log archive

The log archive bucket

The bucket in the log archive account combines several controls. S3 Object Lock (which requires versioning) stores objects as write once, read many: in compliance mode no user, including the root user, can delete or overwrite a locked version or shorten its retention until it expires. In governance mode users with s3:BypassGovernanceRetention can, which is useful for testing. A legal hold has no end date and is removed by anyone with s3:PutObjectLegalHold. A bucket default retention applies to every new object. Add to that:

  • SSE-KMS with an S3 Bucket Key, which cuts KMS request costs for high-volume logs.
  • A bucket policy that denies non-TLS requests with aws:SecureTransport false, and that only lets the logging services write.
  • Lifecycle rules to move older logs to S3 Glacier storage classes and expire them when retention ends.
  • Access for workload administrators limited to nothing: they don't need to read the archive, and SCPs can stop anyone outside the security team changing the bucket.

An object locked in compliance mode can only be deleted early by closing the AWS account. Test retention settings in governance mode first; a 10-year compliance-mode default on the wrong bucket can't be undone.

Amazon Security Lake

Storage and retention

Security Lake's sources and delegated administrator are covered in Task 1.1. It stores data in an S3 bucket per Region in the account where it runs (the log archive account in the running example), as OCSF in Apache Parquet and, for version 2 sources, Apache Iceberg tables. Retention and storage class transitions are set per Region in Security Lake, not with S3 lifecycle rules on its bucket, which can remove its metadata. Contributing Regions can replicate into a rollup Region so one place holds everything.

Keep a year of data, moving it to One Zone-IA after 30 days (AWS CLI, Security Lake administrator) 
aws securitylake update-data-lake \
  --configurations '[{"region": "us-east-1",
                      "encryptionConfiguration": {"kmsKeyId": "S3_MANAGED_KEY"},
                      "lifecycleConfiguration": {"expiration": {"days": 365},
                                                 "transitions": [{"days": 30, "storageClass": "ONEZONE_IA"}]}}]' \
  --meta-store-manager-role-arn arn:aws:iam::444444444444:role/service-role/AmazonSecurityLakeMetaStoreManager

Security Lake doesn't support S3 Object Lock; enabling it with a default retention on the lake's bucket interrupts delivery. If logs must be immutable, keep the original CloudTrail delivery in a locked log archive bucket and use Security Lake as the analysis copy.

Subscribers and third-party tools

Other tools reach Security Lake data as subscribers, each identified by an AWS account ID and external ID and limited to the sources you choose (up to 10):

  • Data access: the subscriber reads the S3 objects directly and is told about new ones through an SQS queue or an HTTPS endpoint. This suits a SIEM that ingests everything.
  • Query access: Lake Formation shares the tables with the subscriber's account through AWS RAM (the invitation must be accepted within 12 hours), and the subscriber queries them with Athena or similar engines, paying for its own queries. This suits an analytics team that queries in place.

A subscriber only sees data in the Region where it's created, so point it at the rollup Region. Third-party tools can also write into the lake as custom sources (up to 50), as long as they deliver OCSF in Parquet under the partition layout Security Lake expects.

"Give a partner SIEM all security logs from every account and Region without building pipelines" points to a Security Lake subscriber with data access in the rollup Region. "Our analysts want to run SQL on the lake from their own account" points to a query access subscriber.

Analyzing logs

Skill 1.2.4Use AWS services to analyze logs (for example, CloudWatch Logs Insights, Amazon Athena, Security Hub findings).

CloudWatch Logs Insights

Interactive queries over log groups

Logs Insights queries one or more log groups, charged per GB scanned. It has three languages: Logs Insights QL (pipe-separated commands such as fields, filter, stats, sort, limit and parse), OpenSearch PPL and OpenSearch SQL, which can join log groups. Fields in CloudTrail, VPC Flow Logs, Route 53 and JSON logs are discovered automatically. From a CloudWatch cross-account observability monitoring account, one query can cover log groups in linked accounts.

Who is getting denied, and for what (Logs Insights QL, CloudTrail log group) 
filter errorCode = "AccessDenied" or errorCode like /UnauthorizedOperation/
| stats count(*) as denied by userIdentity.arn, eventSource, eventName
| sort denied desc
| limit 20
Top sources of rejected traffic (Logs Insights QL, VPC Flow Logs log group) 
filter action = "REJECT"
| stats count(*) as rejects by srcAddr
| sort rejects desc
| limit 20

Amazon Athena

SQL over the log archive

Athena queries logs where they sit in S3, charged per TB scanned ($5 per TB in AWS's examples). For CloudTrail, AWS's table definition uses the CloudTrail input format and partition projection on the date folders, so new days are queryable without adding partitions and a query with a date filter reads only those days. The JSON SerDe lets you declare just the columns you need.

CloudTrail table for one account and Region with partition projection (Athena SQL, shortened column list) 
CREATE EXTERNAL TABLE cloudtrail_prod_use1 (
  eventversion STRING,
  useridentity STRUCT<type: STRING, principalid: STRING, arn: STRING, accountid: STRING,
                      invokedby: STRING, accesskeyid: STRING, username: STRING>,
  eventtime STRING,
  eventsource STRING,
  eventname STRING,
  awsregion STRING,
  sourceipaddress STRING,
  useragent STRING,
  errorcode STRING,
  errormessage STRING,
  requestparameters STRING,
  responseelements STRING,
  eventid STRING,
  readonly STRING,
  recipientaccountid STRING
)
PARTITIONED BY (`timestamp` STRING)
ROW FORMAT SERDE 'org.apache.hive.hcatalog.data.JsonSerDe'
STORED AS INPUTFORMAT 'com.amazon.emr.cloudtrail.CloudTrailInputFormat'
OUTPUTFORMAT 'org.apache.hadoop.hive.ql.io.HiveIgnoreKeyTextOutputFormat'
LOCATION 's3://org-cloudtrail-444444444444/AWSLogs/o-exampleorgid/111111111111/CloudTrail/us-east-1'
TBLPROPERTIES (
  'projection.enabled' = 'true',
  'projection.timestamp.type' = 'date',
  'projection.timestamp.format' = 'yyyy/MM/dd',
  'projection.timestamp.range' = '2024/01/01,NOW',
  'projection.timestamp.interval' = '1',
  'projection.timestamp.interval.unit' = 'DAYS',
  'storage.location.template' = 's3://org-cloudtrail-444444444444/AWSLogs/o-exampleorgid/111111111111/CloudTrail/us-east-1/${timestamp}'
);

-- What did one access key do last week?
SELECT eventtime, eventsource, eventname, sourceipaddress, errorcode
FROM cloudtrail_prod_use1
WHERE "timestamp" BETWEEN '2026/11/01' AND '2026/11/07'
  AND useridentity.accesskeyid = 'AKIAIOSFODNN7EXAMPLE'
ORDER BY eventtime;

Security Lake tables are already in the Glue Data Catalog, named by Region and source, for example amazon_security_lake_glue_db_us_east_1.amazon_security_lake_table_us_east_1_vpc_flow_2_0. Version 2 tables are partitioned on time_dt, and OCSF uses the same field names across sources (src_endpoint.ip, actor.user), which makes one query pattern work on many sources. The caller needs Lake Formation SELECT on the tables.

Everything one IP did in the VPC (Athena SQL, Security Lake version 2 table) 
SELECT time_dt, accountid, src_endpoint.ip, dst_endpoint.ip, dst_endpoint.port
FROM "amazon_security_lake_glue_db_us_east_1"."amazon_security_lake_table_us_east_1_vpc_flow_2_0"
WHERE time_dt > TIMESTAMP '2026-11-01'
  AND src_endpoint.ip = '198.51.100.7'
ORDER BY time_dt DESC
LIMIT 50;

Security Hub CSPM findings

Insights

An insight groups findings by one attribute (GroupByAttribute) after filters, to answer "which resources have the most critical findings" or "which principals show suspicious access key activity". Security Hub CSPM includes managed insights such as "AWS resources with the most findings" and "S3 buckets with public write or read permissions", which can't be edited but can be copied into custom insights. With cross-Region aggregation, insights in the home Region cover linked Regions too.

Roles with critical findings, grouped by role (AWS CLI, Security Hub CSPM administrator) 
aws securityhub create-insight \
  --name "Critical role findings" \
  --group-by-attribute "ResourceId" \
  --filters '{"ResourceType": [{"Comparison": "EQUALS", "Value": "AwsIamRole"}],

Filters on the same attribute are combined with OR, on different attributes with AND. For analysis beyond grouping, Security Hub CSPM findings can be sent to Security Lake (the SH_FINDINGS source) or, through a telemetry rule, to a CloudWatch log group, and queried with Athena or Logs Insights.

Normalizing, parsing and correlating

Skill 1.2.5Use AWS services to normalize, parse, and correlate logs (for example, Amazon OpenSearch Service, AWS Lambda, Amazon Managed Grafana).

Every source has its own format: CloudTrail JSON, space-separated flow log records, WAF JSON, syslog text. Correlating them, for example joining a GuardDuty finding to the flow logs and DNS queries of the same instance, is far easier once they share field names. OCSF is the common schema AWS uses for that.

Inside CloudWatch

Log transformers and pipelines

A log transformer on a log group (or the whole account) parses events as they're ingested, with processors such as parseJSON, grok, csv and parseKeyValue, built-in parsers for WAF, VPC, CloudFront and Route 53 logs, and parseToOCSF, which converts CloudTrail, Route 53 Resolver, VPC Flow, EKS audit and WAF logs to OCSF 1.1 or 1.5. The original event is kept alongside the transformed one, metric and subscription filters see the transformed version, and transformers only work on Standard log groups.

Convert CloudTrail events to OCSF on arrival (transformer processor configuration) 
[
  {
    "parseToOCSF": {
      "eventSource": "CloudTrail",
      "ocsfVersion": "V1.5"
    }
  }
]

CloudWatch pipelines (December 2025) are a managed collector that ingests from S3, CloudWatch Logs and third-party sources, applies processors including OCSF conversion, and routes to log groups. Unlike a transformer, a pipeline doesn't keep the raw event. CloudWatch Logs can also expose log data as Apache Iceberg tables in S3 Tables for Athena, at no extra charge.

Lambda and Amazon Data Firehose

Custom parsing and enrichment

When the logic is your own (look up the instance's owner tag, drop health check noise, add geo data), a Lambda function does it, either as a CloudWatch Logs subscription target or as a Firehose transformation. A subscription delivers a batch of events base64-encoded and gzip-compressed in awslogs.data:

Unpack a CloudWatch Logs subscription batch (Lambda handler, Python) 
import base64, gzip, json

def handler(event, context):
    # The batch arrives base64-encoded and gzip-compressed
    batch = json.loads(gzip.decompress(base64.b64decode(event["awslogs"]["data"])))
    if batch["messageType"] == "CONTROL_MESSAGE":   # test message sent when the filter is created
        return
    for log_event in batch["logEvents"]:
        record = json.loads(log_event["message"])    # CloudTrail events are JSON
        # enrich, normalize and forward here
        print(batch["owner"], batch["logGroup"], record.get("eventName"))

Amazon Data Firehose (formerly Kinesis Data Firehose) buffers records, can decompress CloudWatch Logs batches, transform them with Lambda (each record returned as Ok, Dropped or ProcessingFailed) and deliver to S3, OpenSearch, Splunk and other destinations. Dynamic partitioning writes S3 prefixes from fields in the data, for example by account and date; it can only be turned on when the stream is created and can't be turned off.

Firehose can't deliver CloudWatch Logs subscription data to an OpenSearch destination, because CloudWatch packs several log events into one Firehose record. Use the CloudWatch Logs subscription to OpenSearch (which uses a Lambda function), or Firehose to S3 and OpenSearch Ingestion from there.

OpenSearch Service and Managed Grafana

Amazon OpenSearch Service

OpenSearch is the choice for full-text search and correlation across large volumes. Three features matter here:

  • Security Analytics (managed domains, OpenSearch 2.5 or later): detectors run open-source Sigma rules, mapped to MITRE ATT&CK, against log types such as CloudTrail, VPC Flow Logs and DNS, and raise findings and alerts.
  • OpenSearch Ingestion pipelines can read Security Lake as a subscriber (S3 data access with SQS notifications) using a ready-made Security Lake blueprint, and index the OCSF data.
  • Direct query analyzes CloudWatch Logs, S3 and Security Lake in place, without ingestion pipelines, using PPL or SQL.

Amazon Managed Grafana

Managed Grafana workspaces visualize data where it lives, with data sources for CloudWatch, Athena (and so S3 and Security Lake), OpenSearch and others, and sign-in through IAM Identity Center or a SAML identity provider. It doesn't store logs; it's the shared dashboard that puts CloudTrail error rates, WAF blocks and GuardDuty finding counts side by side. Grafana version 8 workspaces are no longer supported (from October 2026); current workspaces run versions 10, 12 or 13.

"Normalize logs from many AWS and third-party sources into one schema" points to OCSF: Security Lake, a parseToOCSF transformer or a CloudWatch pipeline. "Detect threats in logs with Sigma rules" points to OpenSearch Security Analytics. "Dashboard over several data sources, no data copied" points to Managed Grafana.

Network log sources

Skill 1.2.6Determine and configure appropriate log sources based on network design, threats, and attacks (for example, VPC Flow Logs, transit gateway flow logs, Amazon Route 53 Resolver logs).

Pick the source by the question being asked. "Which IP talked to which, and was it allowed?" is flow logs. "Which domain did this host look up?" is Resolver query logs. "What HTTP request was blocked, by which rule?" is WAF or ALB logs. "Which stateful firewall rule fired?" is Network Firewall alert logs. Capturing packet payloads (Traffic Mirroring) is out of scope for this exam.

VPC Flow Logs

What they record, and what they don't

Flow logs capture IP traffic metadata for a VPC, subnet or network interface (including those of load balancers, NAT gateways and RDS), for ACCEPT, REJECT or ALL traffic, to CloudWatch Logs, S3 or Firehose. Records are aggregated over up to 10 minutes (or 1 minute; Nitro instances always 1 minute) and arrive in minutes, not in real time. The default format is version 2 (addresses, ports, protocol, packets, bytes, start, end, action, status). A custom format adds fields such as:

  • pkt-srcaddr and pkt-dstaddr: the original addresses behind a NAT gateway or for EKS pods, where srcaddr shows the network interface's address.
  • tcp-flags (SYN 2, SYN-ACK 18, FIN 1, RST 4), useful for spotting scans that never complete a handshake.
  • flow-direction, traffic-path (how egress left: internet gateway, peering, VPN and so on) and pkt-src-aws-service.
  • Newer fields: ecs-* task and service fields, reject-reason (for example, blocked by VPC Block Public Access), encryption-status, and instance and interface tags.
Flow logs for the prod VPC with the fields an investigation needs, to the log archive (AWS CLI) 
# A flow log's format can't be changed later; delete it and create a new one instead.
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0abc1234def567890 \
  --traffic-type ALL \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::org-flow-logs-444444444444/prod/ \
  --log-format '${version} ${account-id} ${vpc-id} ${subnet-id} ${instance-id} ${interface-id} ${srcaddr} ${dstaddr} ${pkt-srcaddr} ${pkt-dstaddr} ${srcport} ${dstport} ${protocol} ${tcp-flags} ${packets} ${bytes} ${start} ${end} ${action} ${flow-direction} ${traffic-path} ${log-status}'

For an S3 destination, the bucket policy lets delivery.logs.amazonaws.com write, with aws:SourceAccount and aws:SourceArn conditions; Parquet output with hourly partitions makes Athena queries much cheaper. For CloudWatch Logs, flow logs use a role trusted by vpc-flow-logs.amazonaws.com.

Flow logs don't record traffic to the Amazon DNS server (traffic to your own DNS server is recorded), instance metadata at 169.254.169.254, Amazon Time Sync at 169.254.169.123, DHCP, ARP, Windows license activation, or traffic to the VPC router's reserved address. "Find which instance queried a malicious domain" can't be answered from flow logs; it needs Resolver query logs.

Transit gateway flow logs

Traffic between VPCs and on premises

In the running example, traffic between accounts' VPCs crosses the transit gateway. Transit gateway flow logs, created on the transit gateway or one attachment by its owner, record those flows with source and destination VPC, account, subnet and attachment IDs. There's no ACCEPT or REJECT field, because a transit gateway has no security groups; dropped traffic shows in counters such as packets-lost-no-route, packets-lost-blackhole, packets-lost-mtu-exceeded and packets-lost-ttl-expired. Use them to see east-west movement between accounts that no single VPC's flow logs show end to end.

DNS logs

Route 53 Resolver query logs

Resolver query logs record DNS queries from resources in associated VPCs, queries arriving through inbound Resolver endpoints from on premises, and queries sent through outbound endpoints: the name, type, response code, answers, source IP and the instance ID. Queries that match Route 53 Resolver DNS Firewall rules also carry firewall_rule_action and the rule group and domain list IDs, so DNS Firewall needs no separate log. Only queries the Resolver actually answers are logged; answers served from a cache aren't. Destinations are CloudWatch Logs, S3 or Firehose in the same Region, and a configuration can be associated with VPCs directly or through a Route 53 Profile.

These logs reveal DNS-based threats: instances resolving known command-and-control domains, DNS tunnelling (long, random-looking subdomains), and lookups of domains a DNS Firewall rule blocked. GuardDuty reads the same DNS data on its own, but the query logs are what an investigator searches.

Public DNS query logs

For a public hosted zone, Route 53 public DNS query logging records the queries resolvers on the internet send to Route 53, by edge location. The log group must be in us-east-1, and because resolvers cache answers, the log can show as few as one query in several thousand.

Firewall, load balancer and CDN logs

AWS Network Firewall

Network Firewall has three log types: flow logs for traffic sent to the stateful engine, alert logs for traffic matching stateful rules with drop, alert or reject actions, and TLS logs for TLS inspection errors. Each type goes to S3, CloudWatch Logs or Firehose. Traffic handled only by stateless rules isn't logged, so a "pass" in a stateless rule leaves no record.

AWS WAF, ALB and CloudFront

  • WAF logs go to a CloudWatch log group, S3 bucket or Firehose stream whose name starts with aws-waf-logs-. Sensitive fields such as headers can be redacted (shown as xxx) and log filters can keep only blocked requests. The WAF console now calls web ACLs "protection packs (web ACLs)".
  • ALB access logs go to an S3 bucket in the same Region, which can only use SSE-S3, not SSE-KMS. The bucket policy allows the service principal logdelivery.elasticloadbalancing.amazonaws.com (Regions available before August 2022 also accept the older per-Region ELB account). ALBs also have connection logs, which record TLS details for mutual TLS clients.
  • CloudFront standard logs (version 2) are configured through the CloudWatch Logs delivery APIs in us-east-1 and go to CloudWatch Logs, Firehose or S3, with a choice of fields and formats. Real-time logs arrive within seconds but only to Kinesis Data Streams.

Key takeaways

  • CloudTrail: management events by default; data events and network activity events (VPC endpoint calls, VpceAccessDenied) cost extra; Event history is 90 days per account. CloudTrail Lake is closed to new customers from 31 May 2026.
  • Organization trail from the management account or a delegated administrator (up to 3); members can't change it. Bucket policy path AWSLogs/o-.../ with aws:SourceArn using the management account ID. CLI trails need --is-multi-region-trail, validation and start-logging.
  • Advanced event selectors: no wildcards, StartsWith with a trailing slash for S3, exclude kms.amazonaws.com to cut volume. Integrity validation: hourly signed, chained digests checked with validate-logs.
  • Central logging account: centralization rules (first copy free), or a destination with an organization policy plus subscription filters (5 per log group, 1 account-level per Region, Standard class only). Log group KMS keys need the Regional logs.<region>.amazonaws.com principal; masking needs logs:Unmask to reverse.
  • Agent: configuration in Parameter Store under AmazonCloudWatch-; ServerPolicy reads, AdminPolicy writes; retention_in_days on an existing group deletes older events.
  • Storage: log archive bucket with Object Lock (compliance mode can't be undone), SSE-KMS with Bucket Keys, TLS-only policy, lifecycle. Security Lake: OCSF Parquet, retention set in Security Lake, no Object Lock, rollup Regions, data or query subscribers, custom sources.
  • Analysis: Logs Insights (QL, PPL, SQL; cross-account from a monitoring account), Athena with partition projection and Security Lake tables, Security Hub CSPM insights grouped by one attribute.
  • Normalize: OCSF through Security Lake, parseToOCSF transformers or CloudWatch pipelines; Lambda for custom enrichment; Firehose with dynamic partitioning (not to OpenSearch from CloudWatch Logs); OpenSearch Security Analytics with Sigma rules; Grafana for dashboards.
  • Network: flow logs (no Amazon DNS or metadata traffic, can't edit, pkt-srcaddr behind NAT), transit gateway flow logs (no ACCEPT/REJECT, packets-lost counters), Resolver query logs with DNS Firewall fields, public DNS logs in us-east-1, WAF destinations named aws-waf-logs-, ALB logs SSE-S3 only.
