Overview

Task 2.1

Design and test an incident response plan.

Incident response questions reward preparation. Responders who need an account created, a role granted or a tool installed during an incident lose hours; the right answer has them in place already, tested, with the repeatable steps automated. This page covers planning, preparation, rehearsal and automation design. The response itself (capturing evidence, scoping, containing, eradicating, recovering and finding the root cause) is Task 2.2.

Running example. The same company as in Domain 1: AWS Organizations with a Security OU (security tooling account 222222222222, log archive account 444444444444), workload accounts (prod is 111111111111), a web application behind CloudFront, AWS WAF and an Application Load Balancer, containers on EKS and ECS, an S3 data platform and a generative AI assistant on Amazon Bedrock, in us-east-1 with us-west-2 for disaster recovery. The security team now adds a Forensics OU and writes its incident response plan.

Response plans and runbooks

Skill 2.1.1Design and implement response plans and runbooks to respond to security incidents (for example, Systems Manager OpsCenter, Amazon SageMaker AI notebooks).

The AWS incident response model

Three phases

The AWS Security Incident Response Guide follows NIST SP 800-61 (revision 2) and divides the work into three phases: Preparation (people, process and technology), Operations (detect, analyze, contain, eradicate and recover) and Post-incident activity (lessons learned, metrics such as mean time to detect, contain and recover, and sharing indicators of compromise). It groups cloud incidents into three domains, which decide who can act and how:

  • Service domain: the AWS account itself, such as IAM credentials, permissions and resource policies. Response happens through AWS APIs.
  • Infrastructure domain: instances, networks and data, such as a compromised EC2 instance or a cryptominer in a container.
  • Application domain: your code and the software you run, such as SQL injection or a web shell.

What the plan contains

The guide's plan has five parts: the incident response team, its roles and responsibilities (a RACI chart including legal, HR, executives, application owners and partners), a communication plan with an out-of-band channel in case normal tools are compromised (AWS Wickr is its example), the phases and the actions for each, and severity and prioritization definitions. Keep current architecture diagrams alongside it.

Playbooks

A playbook is the prescriptive set of steps for one type of incident: an overview, prerequisites, stakeholders, the steps for each phase (detect, analyze, contain, eradicate, recover) and the expected outcome. AWS suggests one for each expected incident type (credential compromise, ransomware, denial of service, data exposure) and one for each GuardDuty finding type you could receive. Once a playbook's steps have proven consistent, they become the requirements for automation (Skill 2.1.4). AWS publishes sample playbooks in the aws-samples/aws-incident-response-playbooks repository (refreshed in 2026, including playbooks for Bedrock AgentCore agents) and a framework for writing your own in aws-samples/aws-customer-playbook-framework.

Running the plan with Systems Manager

OpsCenter

OpsCenter is where incidents become work items. An OpsItem is created automatically from a CloudWatch alarm or an EventBridge rule (for example, every high-severity GuardDuty finding), with a title, severity, category, related resources and operational data, and a deduplication string so repeats update one OpsItem. Each OpsItem lists Automation runbooks a responder can run against its resources with one click, and keeps a 30-day record of runs.

OpsCenter can also sync with Security Hub CSPM: by default it creates OpsItems for critical and high findings, and status and severity changes sync both ways. Turned on from the Security Hub CSPM administrator account, it creates the OpsItems for every member account in the administrator account, which is what the security team wants but counts toward that account's quota (10,000 OpsItems a month).

Automation runbooks

A Systems Manager Automation runbook is the executable form of a playbook step. It's a document (schemaVersion 0.3) of steps: aws:executeAwsApi calls any API, aws:executeScript runs Python or PowerShell, aws:branch chooses a path, and aws:approve pauses for a human. AWS provides ready-made ones for incident response, such as AWS-QuarantineEC2Instance and the containment runbooks used by AWS Security Incident Response (below).

Isolate an instance after a responder approves (Automation runbook, YAML) 
description: Wait for a responder to approve, then move the instance to the isolation security group.
schemaVersion: '0.3'
assumeRole: '{{ AutomationAssumeRole }}'
parameters:
  AutomationAssumeRole:
    type: String
  InstanceId:
    type: String
  IsolationGroupId:
    type: String
mainSteps:
  - name: approveIsolation
    action: aws:approve
    timeoutSeconds: 3600            # give up after an hour (default 7 days, maximum 30)
    onFailure: Abort
    inputs:
      NotificationArn: arn:aws:sns:us-east-1:111111111111:AutomationIRApprovals   # topic name must start with "Automation"
      Message: 'Isolate {{ InstanceId }} for incident response?'
      MinRequiredApprovals: 1
      Approvers:
        - arn:aws:iam::111111111111:role/IncidentResponder
  - name: isolateInstance
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: ModifyInstanceAttribute
      InstanceId: '{{ InstanceId }}'
      Groups:
        - '{{ IsolationGroupId }}'
    isEnd: true

An approval step allows up to 10 approvers, and isn't supported when the runbook runs across several accounts or Regions at once.

AWS Security Incident Response

A managed service with AWS responders

AWS Security Incident Response triages GuardDuty findings and third-party findings that arrive through Security Hub CSPM, and escalates only what needs action. It opens proactive cases when its triage finds a real threat, and you open reactive cases: AWS-supported cases get the Security Incident Response engineering team 24 hours a day with a 15-minute response objective, or you keep a case self-managed. Every case event goes to EventBridge, and AWS publishes sample integrations with Jira, ServiceNow and Slack.

Containment is off until you pre-authorize it and deploy its roles to every account with CloudFormation StackSets. It then uses three reversible runbooks, AWSSupport-ContainEC2Instance, AWSSupport-ContainIAMPrincipal and AWSSupport-ContainS3Resource, all of which default to DryRun: true. The service investigates from logs; it doesn't do disk or memory forensics and doesn't carry out recovery. It's priced per finding ingested (the first 10,000 a month free) and is free with Enterprise Support.

Notebooks as investigation runbooks

SageMaker AI notebooks

A Jupyter notebook mixes explanation and code, so a playbook's analysis steps can be written as cells that query CloudTrail, DNS and Security Lake data with Athena and record what was found. AWS's jupyter-notebook-for-incident-response sample has a detection and a containment notebook for each playbook type and runs on a SageMaker AI notebook instance, which gives responders temporary role credentials instead of keys on a laptop. Give the notebook's execution role read access to the logs and only the containment actions the playbook needs.

Notebook instances on Amazon Linux 2 reached end of support on 30 June 2026 and can't be created or restarted from 1 July 2026; use the notebook-al2023-v1 platform. SageMaker Studio Classic stopped receiving updates at the end of 2024 and accepts no new onboarding. A plan that depends on either needs updating.

Preparing services for incidents

Skill 2.1.2Use AWS service features and capabilities to configure services to be prepared for incidents (for example, by provisioning access, deploying security tools, minimizing the blast radius, configuring AWS Shield Advanced protections).

Access, accounts and tools

Provision access in advance

Responders need least-privilege access to every account before an incident, documented and tested. In the running example that's an IAM Identity Center permission set for incident responders, assigned to the responder group in all accounts, plus a cross-account role that the security tooling account can assume for automation. Because these credentials are privileged, AWS recommends an approval flow or retrieving them from a vault, restricting and monitoring their use, and never using them day to day. Plan for the identity provider itself being unavailable: IAM Identity Center's emergency access guidance is direct SAML federation to a few accounts, set up and tested in advance.

Forensic accounts and pre-built tools

AWS recommends a Forensics OU with a forensics account (or one per Region you operate in), created and instrumented well before it's needed, because creating accounts takes time. In the running example the forensics accounts hold:

  • An S3 evidence bucket with Object Lock and SSE-KMS, writable by the response automation.
  • A forensic AMI built with EC2 Image Builder, and an isolated analysis VPC with no internet access.
  • KMS key policies that let snapshots shared from workload accounts be copied and decrypted.

Detection tooling (GuardDuty, Security Hub CSPM, logging) is deployed organization-wide in advance, as in Domain 1. Keep the security contact on every account current, so AWS notifications reach the team.

Minimize the blast radius

Preparation also limits how far an incident can spread: separate accounts per workload and environment (a compromise in dev can't reach prod data), SCPs that stop anyone disabling CloudTrail, GuardDuty or Config, permissions boundaries on roles that teams create, VPC segmentation with security groups that reference each other rather than wide CIDR ranges, and short-lived credentials everywhere. Account strategy is Task 6.1; network segmentation is Task 3.3.

AWS Shield Advanced

Protections, groups and health-based detection

Shield Advanced doesn't protect anything until you add a protection to each resource, or let a Firewall Manager Shield Advanced policy add them across the organization. It protects CloudFront distributions, Route 53 hosted zones, Global Accelerator accelerators, Elastic IP addresses (covering EC2 instances and Network Load Balancers), Application Load Balancers and Classic Load Balancers. A protection group treats several resources as one for detection (all resources, all of one type, or a list).

Health-based detection associates a Route 53 health check with a protection (any type except hosted zones), so Shield detects and mitigates sooner when the application is actually unhealthy. Health checks are required for proactive engagement.

Group the web tier's protections and give the Shield Response Team access (AWS CLI) 
# One protection group for every protected ALB in the account, detected as a sum
aws shield create-protection-group \
  --protection-group-id web-albs \
  --aggregation SUM \
  --pattern BY_RESOURCE_TYPE \
  --resource-type APPLICATION_LOAD_BALANCER

# Role the SRT can assume: trusts drt.shield.amazonaws.com, has AWSShieldDRTAccessPolicy
aws shield associate-drt-role --role-arn arn:aws:iam::111111111111:role/ShieldResponseTeamAccess

# Let the SRT read the WAF and ALB logs it needs (SSE-S3 or unencrypted buckets only)
aws shield associate-drt-log-bucket --log-bucket prod-alb-logs-111111111111

The Shield Response Team and proactive engagement

With Business or Enterprise Support, the Shield Response Team (SRT) can help during an attack, using the role you associate (managed policy AWSShieldDRTAccessPolicy) to view and change your WAF rules. Proactive engagement has the SRT contact you when a protected resource's health check goes unhealthy during an event; it needs a health check on each resource, web ACLs, and up to 10 emergency contacts with at least one phone number. The subscription costs US$3,000 a month per payer account with a one-year commitment, and includes WAF for protected resources and cost protection for scaling charges caused by an attack.

The SRT can't read log buckets encrypted with KMS keys; buckets you share must use SSE-S3 or no encryption. And since 26 March 2026, the AWS WAF Anti-DDoS managed rule group (AWSManagedRulesAntiDDoSRuleSet, 50 WCU) is the default protection against HTTP request floods, replacing Shield Advanced's automatic application layer mitigation for new customers. Proactive engagement isn't triggered by events that rule group detects.

Testing the plan

Skill 2.1.3Recommend procedures to test and validate the effectiveness of an incident response plan (for example, AWS Fault Injection Service, AWS Resilience Hub).

Simulations

Three kinds of exercise

  • Tabletop exercise: discussion only, walking through a scenario with written injects; no tools or scripts are used. Low effort, good for testing roles, communication and decisions.
  • Purple team exercise: attackers and defenders work together to test detections, tools and procedures.
  • Red team exercise: a covert attack within an agreed scope, testing the whole response without warning.

AWS requires you to review its penetration testing policy before purple or red team exercises. Game days, where the team practices the response in a real but non-production environment, also train new responders.

  1. Define the exerciseScenario and objectives, agreed with leadership.
  2. Identify stakeholdersWho takes part, who observes, who must be told.
  3. Build and test the scenarioInjects, accounts, sample data.
  4. Run the simulationA facilitator keeps it moving and records decisions.
  5. Write the after action reportWhat worked, what didn't, and the changes to the plan, playbooks and automation.

Testing detection-to-response wiring

Sample findings and test events

The cheapest test is whether a finding actually reaches the responder and triggers the automation. GuardDuty sample findings are marked [SAMPLE] in the title and "sample": true in the details, and flow through EventBridge like real ones, so they test rules, OpsItems and runbooks. For real findings, AWS's GuardDuty tester (awslabs/amazon-guardduty-tester) generates over 100 of them; run it only in a dedicated non-production account, since it may enable protection plans.

Fire a sample finding and check a rule's pattern (AWS CLI) 
# A sample high-severity EC2 finding in the security tooling account's detector
aws guardduty create-sample-findings \
  --detector-id 12abc34d567e8fa901bc2d34EXAMPLE \
  --finding-types Backdoor:EC2/C&CActivity.B

# Does the rule's pattern match an event? Returns {"Result": true} or false
aws events test-event-pattern \
  --event-pattern file://guardduty-high-pattern.json \
  --event file://sample-guardduty-event.json

Automation built on these tests should ignore sample findings in production, or a test can isolate a real instance.

AWS Fault Injection Service

Experiments for the infrastructure side of a response

AWS Fault Injection Service (FIS) runs controlled experiments from a template: targets (resources by tag, ARN or filter), actions (stop or terminate instances, disrupt a subnet's network connectivity, inject API errors, run an SSM command or Automation runbook), stop conditions (CloudWatch alarms that end the experiment), and a role FIS uses. It can run across accounts from an orchestrator account. For incident response it tests what a response does to the workload: does isolating a subnet or stopping instances in one AZ keep the application up, do the alarms fire, does the runbook work.

Cut one subnet off for 10 minutes and run the isolation runbook, stopping if the site goes down (FIS experiment template) 
{
  "description": "IR game day: isolate an app subnet and run the quarantine runbook",
  "roleArn": "arn:aws:iam::111111111111:role/FISExperimentRole",
  "targets": {
    "AppSubnet": {
      "resourceType": "aws:ec2:subnet",
      "resourceTags": { "fis-target": "ir-gameday" },
      "selectionMode": "COUNT(1)"
    }
  },
  "actions": {
    "IsolateSubnet": {
      "actionId": "aws:network:disrupt-connectivity",
      "parameters": { "scope": "all", "duration": "PT10M" },
      "targets": { "Subnets": "AppSubnet" }
    },
    "RunQuarantineRunbook": {
      "actionId": "aws:ssm:start-automation-execution",
      "parameters": {
        "documentArn": "arn:aws:ssm:us-east-1:111111111111:document/IR-IsolateInstance",
        "documentParameters": "{\"InstanceId\": \"i-0abc1234def567890\", \"IsolationGroupId\": \"sg-0123456789abcdef0\", \"AutomationAssumeRole\": \"arn:aws:iam::111111111111:role/IRAutomationRole\"}",
        "maxDuration": "PT15M"
      }
    }
  },
  "stopConditions": [
    { "source": "aws:cloudwatch:alarm", "value": "arn:aws:cloudwatch:us-east-1:111111111111:alarm:web-5xx-high" }
  ]
}

FIS doesn't simulate attackers: it has no action that behaves like a compromised credential or malware. Use it to rehearse the effects of a response; use sample findings, the GuardDuty tester and purple team exercises to test detection.

AWS Resilience Hub

Checking recovery objectives

Resilience Hub assesses an application against a resiliency policy of recovery time and recovery point objectives (RTO and RPO) for application, infrastructure, Availability Zone and Region disruptions, reports whether the policy is met, detects drift, and recommends alarms, standard operating procedures and FIS experiments. The next-generation Resilience Hub (May 2026) adds failure mode assessments and pre-configured resilience tests built on FIS. For incident response, it answers whether the recovery steps in the plan can meet the RTO the business expects.

"Validate the plan with no impact on systems" points to a tabletop exercise. "Verify the automation triggers on GuardDuty findings" points to sample findings. "Confirm the application survives an AZ being isolated during response" points to FIS. "Check recovery can meet RTO and RPO" points to Resilience Hub.

Automated remediation

Skill 2.1.4Use AWS services to automatically remediate incidents (for example, Systems Manager, Automated Forensics Orchestrator for Amazon EC2, AWS Step Functions, Amazon Application Recovery Controller, Lambda functions).

Choosing the engine

EventBridge plus a target

Almost every automated response starts with an EventBridge rule on a finding (Task 1.1) and a target that does the work:

  • Lambda for one quick action: deactivate an access key, remove a public bucket policy, add an IP to a WAF IP set.
  • Systems Manager Automation for steps on AWS resources and instances, with AWS-provided runbooks, approvals and an audit trail; also run from Config remediation and OpsCenter.
  • Step Functions for multi-step workflows with branching, parallel evidence collection, retries, waiting for a human, and long runs (up to a year for Standard workflows).
Run the isolation runbook from a GuardDuty rule (EventBridge targets file for put-targets) 
[
  {
    "Id": "isolate-instance",
    "Arn": "arn:aws:ssm:us-east-1:111111111111:automation-definition/IR-IsolateInstance",
    "RoleArn": "arn:aws:iam::111111111111:role/EventBridgeStartAutomation",
    "InputTransformer": {
      "InputPathsMap": { "instance": "$.detail.resource.instanceDetails.instanceId" },
      "InputTemplate": "{\"InstanceId\": [<instance>], \"IsolationGroupId\": [\"sg-0123456789abcdef0\"], \"AutomationAssumeRole\": [\"arn:aws:iam::111111111111:role/IRAutomationRole\"]}"
    }
  }
]

Runbook parameters sent from EventBridge must be arrays of strings, and the target ARN uses automation-definition/, not document/. Apply it with aws events put-targets --rule guardduty-ec2-high --targets file://targets.json.

Step Functions with a human in the loop

Destructive steps (terminating an instance, deleting a user) usually wait for approval. A Step Functions task with .waitForTaskToken sends a token (for example in an SNS message) and pauses until something calls SendTaskSuccess or SendTaskFailure with it; callbacks work only in Standard workflows. Evidence collection runs first, so approval delays don't lose volatile data.

Snapshot, ask for approval, then isolate (Step Functions state machine, JSONPath) 
{
  "Comment": "Compromised instance response",
  "StartAt": "SnapshotVolumes",
  "States": {
    "SnapshotVolumes": {
      "Type": "Task",
      "Resource": "arn:aws:states:::aws-sdk:ec2:createSnapshots",
      "Parameters": {
        "InstanceSpecification": { "InstanceId.$": "$.instanceId" },
        "Description": "IR evidence",
        "CopyTagsFromSource": "volume"
      },
      "ResultPath": "$.snapshots",
      "Next": "RequestApproval"
    },
    "RequestApproval": {
      "Type": "Task",
      "Resource": "arn:aws:states:::sns:publish.waitForTaskToken",
      "Parameters": {
        "TopicArn": "arn:aws:sns:us-east-1:222222222222:ir-approvals",
        "Message": {
          "instanceId.$": "$.instanceId",
          "taskToken.$": "$$.Task.Token"
        }
      },
      "TimeoutSeconds": 3600,
      "ResultPath": "$.approval",
      "Next": "Isolate"
    },
    "Isolate": {
      "Type": "Task",
      "Resource": "arn:aws:states:::aws-sdk:ec2:modifyInstanceAttribute",
      "Parameters": {
        "InstanceId.$": "$.instanceId",
        "Groups": ["sg-0123456789abcdef0"]
      },
      "End": true
    }
  }
}

A state machine without a top-level QueryLanguage uses JSONPath, as here; JSONata is the alternative AWS suggests for new workflows.

AWS-provided automation

Automated Security Response on AWS

Automated Security Response on AWS is an AWS solution that deploys remediation playbooks (EventBridge rules, Automation runbooks, Step Functions) to the Security Hub administrator and member accounts. Remediations run from a Security Hub CSPM custom action, its web UI, its API, or fully automatically for chosen controls. It's actively maintained: version 3 (November 2025) added a web UI and support for the new Security Hub, version 4 (August 2026) added remediation for GuardDuty, Inspector and Macie findings. Remediating resources managed by CloudFormation causes stack drift, so fix the template too.

Automated Forensics Orchestrator for Amazon EC2

Now titled Guidance for Automated Forensics Orchestrator for Amazon EC2 and EKS, this AWS Guidance automates evidence capture for compromised instances. A Security Hub finding reaches EventBridge, a Step Functions triage step decides on isolation and acquisition, then in parallel it captures memory through SSM (before isolating the instance, so volatile data isn't lost) and disk as EBS snapshots shared with the forensics account, where an instance built from a forensic AMI analyzes them. Version 2.0.0 (August 2026) moved the analysis host to Amazon Linux 2023. Evidence handling itself is Task 2.2.

Application Recovery Controller

Moving traffic away during an incident

Amazon Application Recovery Controller (ARC) moves traffic away from a part of the system that's impaired, which during a security incident can buy time to contain and rebuild:

  • Zonal shift moves load balancer, Auto Scaling group and EKS traffic out of one Availability Zone temporarily (up to three days, extendable); zonal autoshift lets AWS do it for AZ impairments.
  • Routing control switches DNS between Regions with on and off controls, with safety rules to prevent switching everything off, and overrides for emergencies.
  • Region switch (August 2025) runs a plan of steps (scale up capacity, fail over databases, shift traffic, wait for approval) to move an application to another Region, triggered manually or by CloudWatch alarms.

In the running example, if the us-east-1 workload account is compromised and must be rebuilt, a Region switch plan moves the application to clean infrastructure in us-west-2 while the team investigates.

"Respond automatically, but a person must approve before anything is deleted" points to Step Functions with .waitForTaskToken or a runbook with aws:approve. "Remediate Security Hub CSPM findings across the organization with AWS-maintained playbooks" points to Automated Security Response on AWS. "Capture memory and disk from a compromised EC2 instance automatically" points to the Automated Forensics Orchestrator guidance.

Key takeaways

  • AWS model (NIST SP 800-61 r2): Preparation, Operations (detect, analyze, contain, eradicate, recover), Post-incident activity; service, infrastructure and application domains. The plan covers team, RACI, out-of-band communication, phases and severity.
  • Playbooks per incident type and per GuardDuty finding; consistent playbook steps become automation. OpsCenter OpsItems from EventBridge and alarms, with runbooks attached; Security Hub CSPM sync is two-way. Incident Manager and Change Manager are closed to new customers.
  • Automation runbooks: schema 0.3, aws:executeAwsApi, aws:executeScript, aws:branch, aws:approve (topic named Automation..., up to 10 approvers, not multi-account). AWS Security Incident Response: managed triage and AWS responders, pre-authorized reversible containment runbooks (DryRun by default), no forensics or recovery.
  • Prepare: responder permission sets and cross-account roles in advance, emergency access, Forensics OU accounts with evidence buckets and forensic AMIs, security contacts, blast radius limited by accounts, SCPs and segmentation.
  • Shield Advanced: explicit protections (or Firewall Manager), protection groups, Route 53 health checks for health-based detection and proactive engagement, SRT role with AWSShieldDRTAccessPolicy, SSE-S3 log buckets only; the Anti-DDoS managed rule group is now the default L7 flood protection.
  • Test: tabletop (discussion only), purple and red team (pen testing policy), after action reports; GuardDuty sample findings and test-event-pattern for wiring; FIS for the effects of a response (it doesn't simulate attackers); Resilience Hub for RTO and RPO.
  • Automate: EventBridge to Lambda, Automation (string-array inputs, automation-definition/ ARN) or Step Functions (.waitForTaskToken for approvals, Standard only); Automated Security Response on AWS; the Automated Forensics Orchestrator guidance; ARC zonal shift, routing control and Region switch to move traffic away.
