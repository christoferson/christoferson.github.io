Overview

Task 3.1

Design, implement, and troubleshoot security controls for network edge services.

The edge is where most internet attacks can be absorbed cheaply: at CloudFront's edge locations, Shield and AWS WAF filter traffic before it costs the origin anything, and requests they reject aren't charged. Questions ask which service or rule stops a described attack, how to make sure attackers can't go around the edge to the origin, and why a rule blocks good traffic or misses bad traffic. The associate-level basics of WAF, Shield and CloudFront origin access are in the Solutions Architect guide; Shield Advanced setup is in Task 2.1.

Running example. The same company. Its customer web application is served through CloudFront in front of an Application Load Balancer in prod (111111111111), with images in an S3 bucket, a REST API on API Gateway for the mobile app, a login and sign-up flow attackers target, and a fleet of IoT sensors in its warehouses publishing to AWS IoT Core.

Edge security strategy

Skill 3.1.1Define and select edge security strategies based on anticipated threats and attacks.

Matching threats to edge services

From the DDoS resiliency best practices

AWS's Best Practices for DDoS Resiliency (revised August 2026) maps services to attack layers. The points that decide questions:

  • Infrastructure attacks (UDP reflection, SYN floods): absorbed by Shield Standard on CloudFront, Global Accelerator and Route 53 at the edge, and by ALBs, which only accept well-formed TCP connections. Security groups and network ACLs reduce the attack surface but don't absorb floods.
  • Application layer attacks (HTTP floods, scraping, credential stuffing): need AWS WAF, on CloudFront or the ALB. Global Accelerator has no layer 7 protection, so a web application behind Global Accelerator alone has no defense against HTTP floods.
  • Geographic dispersion comes only from the global edge services: CloudFront, Global Accelerator and Route 53.

For the running example that means Route 53 for DNS, CloudFront with a web ACL in front of everything web-facing, the ALB kept off the internet, Shield Advanced on the distribution and the API for cost protection and Shield Response Team support, and auto scaling to absorb what gets through.

Web threats and the WAF tool for each

  • OWASP Top 10 injection and common exploits (SQL injection, cross-site scripting, local and remote file inclusion, server-side request forgery to the metadata service): the core rule set, the SQL database rule set and known bad inputs (Log4j and Java deserialization exploits).
  • Known malicious sources: the Amazon IP reputation list and the anonymous IP list (VPNs, Tor, hosting providers).
  • Bots and scrapers: Bot Control.
  • Credential stuffing and fake sign-ups: Fraud Control account takeover prevention (ATP) and account creation fraud prevention (ACFP).
  • HTTP floods: rate-based rules and the Anti-DDoS managed rule group (the default HTTP flood protection since March 2026).

Keeping attackers off the origin

Load balancer and EC2 origins

Edge protection is pointless if the origin is reachable directly. Three ways to close it, strongest first:

  • CloudFront VPC origins (November 2024): the ALB, NLB or EC2 instance sits in a private subnet with no public address, and CloudFront reaches it through a service-managed network interface. The origin's security group can allow only the CloudFront-VPCOrigins-Service-SG security group. The VPC still needs an internet gateway attached, though traffic doesn't use it.
  • The CloudFront origin-facing prefix list (com.amazonaws.global.cloudfront.origin-facing) in the ALB's security group, so only CloudFront's addresses connect. It counts as 55 rules toward the security group's default quota of 60.
  • A secret custom header that CloudFront adds to origin requests, checked by an ALB listener rule (or a WAF rule on the ALB), with the default action returning 403. Use HTTPS to the origin so the header can't be read, generate random values and rotate them by allowing two headers during the change.

The prefix list alone doesn't stop someone else's CloudFront distribution reaching your ALB, so combine it with the custom header, or use VPC origins.

S3 origins

Origin access control signs CloudFront's requests to S3 with SigV4. The bucket policy allows the cloudfront.amazonaws.com service principal with an AWS:SourceArn condition naming the distribution, and the bucket stays private with Block Public Access on. OAC supports SSE-KMS (the key policy grants the same principal), PUT and DELETE requests and every Region; OAI supports none of those. An S3 website endpoint can't use OAC or OAI at all; it's a custom origin.

"Users must not be able to bypass CloudFront and reach the ALB" points to VPC origins (private ALB) or the custom header plus prefix list pattern. "Only CloudFront can read the bucket, which uses SSE-KMS" points to OAC, never OAI.

Edge protections

AWS WAF

Where web ACLs apply

A web ACL protects CloudFront distributions (scope CLOUDFRONT, and the web ACL, IP sets, regex sets and rule groups must all be in us-east-1), and, in its own Region, Application Load Balancers, API Gateway REST API stages, AppSync APIs, Cognito user pools, App Runner services, Verified Access instances and Bedrock AgentCore gateways. Amplify apps are protected through the CLOUDFRONT scope. Each resource has at most one web ACL; a web ACL used by CloudFront can't also be used by regional resources. On API Gateway, WAF runs before resource policies and authorizers.

Rules are evaluated in priority order. Allow and Block end evaluation; Count records a match and continues; CAPTCHA and Challenge end evaluation only if the client has no valid token. Rules can add labels, which later rules can match. Each rule costs WCUs (web ACL capacity units): 1,500 are included in the base price, up to 5,000 at extra cost.

AWS managed rule groups

Most protection comes from managed rule groups (vendor AWS). The ones questions use, with their WCU cost:

  • AWSManagedRulesCommonRuleSet (core rule set, 700): XSS, file inclusion, SSRF to the instance metadata address, bad user agents, and size limits including SizeRestrictions_BODY (bodies over 8 KB).
  • AWSManagedRulesKnownBadInputsRuleSet (200): Log4j and Java deserialization exploits, localhost Host headers, exploitable paths.
  • AWSManagedRulesSQLiRuleSet (200): SQL injection in query, body, cookie and path. Also Linux, Unix, Windows, PHP and WordPress sets for those stacks.
  • AWSManagedRulesAmazonIpReputationList (25) and AWSManagedRulesAnonymousIpList (50): Amazon threat intelligence, VPNs, Tor and hosting providers. The IP list's DDoS rule defaults to Count.
  • AWSManagedRulesBotControlRuleSet, AWSManagedRulesATPRuleSet and AWSManagedRulesACFPRuleSet (50 each, extra charges): see Skill 3.1.3.

Body inspection limits

WAF only inspects the first part of a request body: 8 KB on ALBs and AppSync (fixed), and 16 KB by default on CloudFront, API Gateway, Cognito, App Runner and Verified Access, configurable up to 64 KB for an extra charge per 16 KB. What happens to the rest is the oversize handling setting: CONTINUE (the default through the API) inspects what fits, MATCH treats the request as matching, NO_MATCH as not matching. An attacker can put a payload after the limit, so AWS recommends a size rule early in the web ACL that blocks bodies larger than the limit:

Block bodies too large to inspect, before any other rule (WAF rule JSON, CloudFront web ACL at 16 KB) 
{
  "Name": "block-uninspectable-bodies",
  "Priority": 0,
  "Statement": {
    "SizeConstraintStatement": {
      "FieldToMatch": { "Body": { "OversizeHandling": "MATCH" } },
      "ComparisonOperator": "GT",
      "Size": 16384,
      "TextTransformations": [{ "Priority": 0, "Type": "NONE" }]
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "block-uninspectable-bodies" }
}

Behind an ALB, a 10 KB request body is only partly inspected, whatever the web ACL says, because ALB inspection is fixed at 8 KB. Putting WAF on CloudFront in front of the ALB raises that to 16 to 64 KB.

CloudFront security settings

Security response headers

A response headers policy adds browser security headers to every response. The managed SecurityHeadersPolicy adds HSTS (one year), X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, Referrer-Policy and X-XSS-Protection, but has no Content-Security-Policy, and except for X-Content-Type-Options it keeps whatever value the origin sends. For a CSP or stricter values, create your own policy:

Custom security headers that override the origin (CloudFront response headers policy config, JSON) 
{
  "Name": "shop-security-headers",
  "SecurityHeadersConfig": {
    "StrictTransportSecurity": { "Override": true, "AccessControlMaxAgeSec": 63072000, "IncludeSubdomains": true, "Preload": true },
    "ContentSecurityPolicy": { "Override": true, "ContentSecurityPolicy": "default-src 'self'; img-src 'self' https://images.example.com; frame-ancestors 'none'" },
    "ContentTypeOptions": { "Override": true },
    "FrameOptions": { "Override": true, "FrameOption": "DENY" },
    "ReferrerPolicy": { "Override": true, "ReferrerPolicy": "strict-origin-when-cross-origin" }
  }
}

TLS, signed URLs and client certificates

  • Viewer TLS: with a custom certificate (in ACM in us-east-1) and SNI, choose a security policy such as TLSv1.2_2021, TLSv1.2_2025 or TLSv1.3_2025 (TLS 1.3 only). With the default *.cloudfront.net certificate, CloudFront uses the TLSv1 policy and you can't change it. Set the viewer protocol policy to redirect HTTP to HTTPS.
  • Private content: signed URLs and signed cookies, verified with public keys in trusted key groups (up to 4 per distribution, 5 keys each), set per cache behavior. The old CloudFront key pairs need the root user and aren't recommended. Check behavior path order: the first match wins, and an unsigned behavior earlier in the list bypasses signing.
  • Mutual TLS (November 2025): CloudFront can require client certificates validated against a trust store, which suits device and partner APIs.
  • Edge code: CloudFront Functions are fast enough to validate a token on every viewer request; Lambda@Edge can also read the body and call other services.

AWS IoT policies

Each device only its own topics

IoT devices authenticate to AWS IoT Core with X.509 certificates, and an IoT policy attached to the certificate says what the device can do over MQTT: iot:Connect (on a client/ ARN), iot:Publish and iot:Receive (on topic/ ARNs) and iot:Subscribe (on topicfilter/ ARNs). Policy variables let one policy serve every device:

One policy for every warehouse sensor, each limited to its own topics (AWS IoT policy JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "iot:Connect",
      "Resource": "arn:aws:iot:us-east-1:111111111111:client/${iot:Connection.Thing.ThingName}",
      "Condition": { "Bool": { "iot:Connection.Thing.IsAttached": "true" } }
    },
    {
      "Effect": "Allow",
      "Action": "iot:Publish",
      "Resource": "arn:aws:iot:us-east-1:111111111111:topic/sensor/device/${iot:Connection.Thing.ThingName}"
    },
    {
      "Effect": "Allow",
      "Action": "iot:Subscribe",
      "Resource": "arn:aws:iot:us-east-1:111111111111:topicfilter/command/device/${iot:Connection.Thing.ThingName}"
    },
    {
      "Effect": "Allow",
      "Action": "iot:Receive",
      "Resource": "arn:aws:iot:us-east-1:111111111111:topic/command/device/${iot:Connection.Thing.ThingName}"
    }
  ]
}

The IsAttached condition means the certificate must belong to that registered thing, so a stolen certificate can't connect as another device. AWS IoT Device Defender audits flag overly permissive policies (a client/${iot:ClientId} resource without that condition counts as a wildcard), shared or expiring certificates and revoked CAs still in use.

In IoT policies, the MQTT wildcards + and # are ordinary characters; policy wildcards are * and ?. And iot:Subscribe takes topicfilter/ ARNs while publish and receive take topic/ ARNs, so a policy with the wrong prefix lets the device connect but never subscribe.

S3 cross-origin resource sharing

CORS isn't access control

A CORS configuration tells browsers which other sites' pages may make requests to a bucket and read the responses. It doesn't grant or deny access: the bucket policy, OAC and IAM still decide that, and a non-browser client ignores CORS completely. The first matching rule wins; allowed methods are GET, PUT, POST, DELETE and HEAD.

Let only the shop's own site upload and read from the media bucket in the browser (S3 CORS configuration, JSON) 
{
  "CORSRules": [
    {
      "ID": "shop-site",
      "AllowedOrigins": ["https://www.example.com"],
      "AllowedMethods": ["GET", "PUT"],
      "AllowedHeaders": ["Content-Type", "x-amz-*"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3000
    }
  ]
}

It's applied with aws s3api put-bucket-cors --bucket shop-media-111111111111 --cors-configuration file://cors.json, which replaces any existing configuration. Behind CloudFront, allow the OPTIONS method on the behavior, forward the Origin and Access-Control-Request-* headers (the managed CORS-S3Origin origin request policy) and include Origin in the cache key, or cached responses carry the wrong CORS headers.

"A browser shows a CORS error but the same request works from the CLI" points to the CORS configuration (origin, method or header not allowed, or CloudFront not forwarding Origin). "Stop other websites using our bucket" isn't solved by CORS; that needs the bucket policy or OAC.

Geography, rate and fingerprint rules

Skill 3.1.3Design and implement AWS edge controls and rules based on requirements (for example, geography, geolocation, rate limiting, client fingerprinting).

Geography

CloudFront geo restriction or WAF geo match

CloudFront geo restriction is an allow list or block list of countries for the whole distribution; blocked viewers get a 403, and requests whose location can't be determined are served. A WAF geo match statement is more flexible: up to 50 country codes per statement, combinable with other conditions (only the login path, only POST), and it labels every request it inspects with the country and the region (ISO 3166-2, for example awswaf:clientip:geo:region:US-CA). To act on a region, run a geo rule in Count and match the region label in a later rule:

Block one US state where the service isn't licensed (two WAF rules, JSON) 
[
  {
    "Name": "label-us-traffic",
    "Priority": 30,
    "Statement": { "GeoMatchStatement": { "CountryCodes": ["US"] } },
    "Action": { "Count": {} },
    "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "label-us-traffic" }
  },
  {
    "Name": "block-unlicensed-region",
    "Priority": 31,
    "Statement": { "LabelMatchStatement": { "Scope": "LABEL", "Key": "awswaf:clientip:geo:region:US-WA" } },
    "Action": { "Block": {} },
    "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "block-unlicensed-region" }
  }
]

Geo, ASN and rate-based statements can evaluate a forwarded IP header (ForwardedIPConfig) when a proxy sits in front, but only the first address in the header, and if the header is missing the rule doesn't apply at all. Route 53 geolocation routing chooses where to send users; it isn't a security control.

Rate limiting

Rate-based rules

A rate-based rule counts requests per key over an evaluation window of 60, 120, 300 (default) or 600 seconds and acts on keys over the limit (minimum 10 requests since August 2024). The key is the client IP, a forwarded IP, a constant (count all matching requests together, which needs a scope-down statement), or up to five custom keys: header, cookie, query argument or string, URI path, HTTP method, IP, label namespace, JA3 or JA4 fingerprint or ASN. A scope-down statement limits counting to the requests that matter.

At most 100 login attempts per client IP and TLS fingerprint in 5 minutes (WAF rule JSON) 
{
  "Name": "login-rate-limit",
  "Priority": 20,
  "Statement": {
    "RateBasedStatement": {
      "Limit": 100,
      "EvaluationWindowSec": 300,
      "AggregateKeyType": "CUSTOM_KEYS",
      "CustomKeys": [
        { "IP": {} },
        { "JA4Fingerprint": { "FallbackBehavior": "MATCH" } }
      ],
      "ScopeDownStatement": {
        "ByteMatchStatement": {
          "FieldToMatch": { "UriPath": {} },
          "PositionalConstraint": "STARTS_WITH",
          "SearchString": "/login",
          "TextTransformations": [{ "Priority": 0, "Type": "LOWERCASE" }]
        }
      }
    }
  },
  "Action": { "Block": {} },
  "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "login-rate-limit" }
}

Rate-based rules can't use Allow, can't be nested, and their limits are approximate (WAF checks rates about every 10 seconds). For the REST API, API Gateway throttling adds per-method and per-client (usage plan) limits behind WAF; the account default is 10,000 requests per second with a burst of 5,000, and throttled clients get 429.

Client fingerprinting and bots

JA3 and JA4

A JA3 or JA4 fingerprint is a hash of the client's TLS Client Hello, which stays the same for a given client program even when it rotates IP addresses. WAF can match it (byte, regex or size statements, not SQLi or XSS) and use it as a rate key, on CloudFront and ALB only; you find the attacker's fingerprint in the WAF logs. JA3 matching arrived in 2023, JA4 in December 2024.

Bot Control, CAPTCHA and Challenge

Bot Control at the COMMON level identifies self-declared bots (search engines, monitors, scrapers, AI crawlers), labels them, and blocks unverified ones by category; its CategoryAI rule blocks AI bots even when verified. The TARGETED level adds browser interrogation, fingerprinting, token reuse checks and machine learning for bots that pretend to be browsers. Its rules use Challenge (a silent JavaScript check) and CAPTCHA (a puzzle); a client that passes gets an aws-waf-token cookie valid for the immunity time (default 300 seconds; up to 3 days). Add a scope-down statement to Bot Control to limit cost.

Fraud Control for logins and sign-ups

Account takeover prevention (ATP) inspects login requests to a configured path, checks credentials against a database of stolen credentials, and limits attempts per IP and per session; on CloudFront it can also inspect responses to count failed logins. Account creation fraud prevention (ACFP) protects the sign-up page and creation endpoint, scoring risk and catching repeated phone numbers and addresses. Neither works on Cognito user pools, and response inspection is CloudFront-only.

An ALB behind CloudFront using Challenge, CAPTCHA, Bot Control targeted or ATP needs CloudFront to forward the aws-waf-token cookie and the CloudFront domain in the web ACL's token domains; otherwise every token is rejected as a domain mismatch and users are challenged on every request.

"Attackers rotate IP addresses, so IP rate limits don't work" points to JA3/JA4 fingerprint keys or Bot Control targeted. "Block credential stuffing on the login page" points to ATP. "Limit requests per API key" points to API Gateway usage plans.

Integrations and troubleshooting

Skill 3.1.4Configure integrations with AWS edge services and third-party services (for example, by ingesting data in Open Cybersecurity Schema Framework [OCSF] format, by using third-party WAF rules).

Edge data in OCSF

Security Lake and CloudWatch

WAF logs reach OCSF-based tools two ways. Amazon Security Lake collects them natively (source WAF, since May 2024) from its own copy of the data, so WAF logging doesn't even have to be configured, and converts them to OCSF in Parquet for subscribers such as a SIEM (Task 1.2). Or, with WAF logging to CloudWatch Logs, a parseToOCSF transformer with event source AWSWAF converts each record as it arrives. A web ACL's data protection settings (redacting fields) also apply to what Security Lake receives.

Third-party rules and organization-wide deployment

AWS Marketplace rule groups

Security vendors sell managed rule groups through AWS Marketplace (in the new console under Add-on protections). After subscribing, you add one like any managed group, with a ManagedRuleGroupStatement naming the vendor and group; the vendor maintains the rules and supports them, and you pay its monthly and request fees on top of WAF's. Unsubscribing doesn't stop the charges until the group is removed from every web ACL.

Firewall Manager

AWS Firewall Manager WAF policies deploy rule groups to web ACLs across the organization: first rule groups run before the account's own rules and last rule groups after them, so the security team guarantees a baseline while application teams add their own rules in between. Policies can apply to new resources automatically and, since October 2024, retrofit existing web ACLs. A Marketplace rule group in a Firewall Manager policy needs every member account to subscribe. Firewall Manager also deploys Shield Advanced protections, security group, Network Firewall and DNS Firewall policies (Task 3.3).

CloudFront flat-rate pricing plans (November 2025) include WAF and DDoS protection, with blocked requests not counted, but a distribution protected by Shield Advanced or whose web ACL is managed by Firewall Manager can't use them, and they don't support rule groups, Marketplace rules, Bot Control targeted, ATP or ACFP. A question requiring those features rules the plans out.

Troubleshooting edge rules

Test in Count, fix false positives with labels

Deploy new rules and managed groups in Count first and watch the rule's CloudWatch metrics and sampled requests (up to 100 per rule from the last 3 hours); the WAF logs show the terminating rule and labels of every request. A common false positive is the core rule set's SizeRestrictions_BODY blocking legitimate uploads. Don't disable the group: override that one rule to Count, then block on its label everywhere except the upload path.

Core rules with one rule in Count, then block its matches except on uploads (two WAF rules, JSON) 
[
  {
    "Name": "aws-core-rules",
    "Priority": 10,
    "Statement": {
      "ManagedRuleGroupStatement": {
        "VendorName": "AWS",
        "Name": "AWSManagedRulesCommonRuleSet",
        "RuleActionOverrides": [{ "Name": "SizeRestrictions_BODY", "ActionToUse": { "Count": {} } }]
      }
    },
    "OverrideAction": { "None": {} },
    "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "aws-core-rules" }
  },
  {
    "Name": "large-bodies-only-on-uploads",
    "Priority": 11,
    "Statement": {
      "AndStatement": {
        "Statements": [
          { "LabelMatchStatement": { "Scope": "LABEL", "Key": "awswaf:managed:aws:core-rule-set:SizeRestrictions_Body" } },
          { "NotStatement": { "Statement": { "ByteMatchStatement": {
              "FieldToMatch": { "UriPath": {} }, "PositionalConstraint": "STARTS_WITH", "SearchString": "/api/upload",
              "TextTransformations": [{ "Priority": 0, "Type": "NONE" }] } } } }
        ]
      }
    },
    "Action": { "Block": {} },
    "VisibilityConfig": { "SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "large-bodies-only-on-uploads" }
  }
]

Rule groups use OverrideAction, not Action; setting the whole group's override to Count only changes the group's final result and isn't a good way to test. A misspelled rule name in RuleActionOverrides on an AWS managed group is silently ignored, so check the override took effect in the metrics.

Where a 403 comes from

At the edge, a 403 can be a WAF block (403 unless a custom response says otherwise), CloudFront geo restriction, a missing or invalid signed URL or cookie, or S3 denying the origin request (OAC misconfigured). CloudFront access logs can't tell a geo restriction 403 apart from others; WAF logs name the terminating rule. An ALB whose web ACL has no rules produces no sampled requests or metrics at all.

Key takeaways

  • Infrastructure floods are absorbed by Shield at CloudFront, Global Accelerator, Route 53 and ALB; application floods, bots and injection need WAF on CloudFront or the ALB. Global Accelerator has no layer 7 protection.
  • Close the origin: VPC origins (private ALB or EC2), or the origin-facing prefix list (55 rules) plus a secret custom header over HTTPS; OAC for S3 (SSE-KMS, PUT, all Regions), never OAI; website endpoints can't use either.
  • WAF: CloudFront web ACLs and their sets in us-east-1; one web ACL per resource; 1,500 WCU included (5,000 maximum); core rule set 700 WCU; body inspection 8 KB on ALB, 16 to 64 KB on CloudFront and API Gateway, oversize default CONTINUE, so add a size block rule.
  • CloudFront: managed SecurityHeadersPolicy has no CSP and mostly doesn't override; default certificate forces TLSv1; trusted key groups for signed URLs; mTLS for device and partner clients.
  • IoT: certificate-attached policies with ${iot:Connection.Thing.ThingName} and IsAttached; topicfilter/ for Subscribe; + and # are literal; Device Defender audits. S3 CORS controls browsers only, not access.
  • Rules: WAF geo match with region labels (Count then label match), forwarded IP uses the first address and skips requests without the header; rate-based rules from 10 requests, 60 to 600 second windows, up to 5 custom keys including JA3/JA4 and ASN; JA3/JA4 only on CloudFront and ALB.
  • Bot Control common and targeted, Challenge and CAPTCHA tokens (forward aws-waf-token and set token domains behind CloudFront), ATP for logins and ACFP for sign-ups (not on Cognito).
  • Integrations: Security Lake WAF source and parseToOCSF (AWSWAF) for OCSF; Marketplace rule groups; Firewall Manager first and last rule groups (every account subscribes to Marketplace groups). Troubleshoot with Count, sampled requests, logs, rule overrides and label-based exceptions.
