Task 5.3: Design and implement controls to protect confidential data, credentials, secrets, and cryptographic key materials

Overview

Task 5.3

Design and implement controls to protect confidential data, credentials, secrets, and cryptographic key materials.

This task is about the things that unlock everything else. Questions test whether rotation actually happens without breaking applications, what changes when you bring your own key material, what's lost when a key or its material is deleted, and how keys and certificates behave across Regions and accounts. Key types and choosing between KMS and CloudHSM are in Task 5.2.

Running example. The same company. Aurora and RDS databases, a Snowflake account and third-party API keys hold credentials; compliance requires one key to use material generated in the company's own HSM; a regulator in one market requires key material to stay outside AWS; logs and notifications must not expose customer personal data; and the platform runs in us-east-1 and us-west-2 with internal TLS everywhere.

Managing and rotating secrets

Skill 5.3.1Design management and rotation of credentials and secrets (for example, AWS Secrets Manager).

Rotation in Secrets Manager

Three ways secrets rotate

  • Managed rotation: the owning service rotates its own secret with no Lambda function, for RDS, Aurora, DocumentDB and Redshift master users and ECS Service Connect certificates. RDS-managed master passwords (--manage-master-user-password) rotate every 7 days by default; deleting the database deletes the secret, the KMS key can't be changed later, and they don't work with Blue/Green deployments or RDS Custom.
  • Managed external secrets (November 2025): partner SaaS credentials such as Salesforce and Snowflake, rotated by Secrets Manager with no Lambda in your account.
  • Lambda rotation for everything else, from AWS templates or your own function.
  1. createSecretGenerate a new value and store it as a new version labelled AWSPENDING.
  2. setSecretChange the credential in the database or service to the pending value.
  3. testSecretSign in with the pending value to prove it works.
  4. finishSecretMove AWSCURRENT to the new version; the old one becomes AWSPREVIOUS, the last known good value.

Strategies and schedules

The single user strategy changes one user's password; it's the simplest and fits most cases, but there's a short window where clients holding the old password fail, so use retries. The alternating users strategy keeps two users in the secret and switches between them, so the old credential keeps working until the next rotation; it needs a separate superuser secret to create and change the clone user, and RDS Proxy doesn't support it.

Schedules are rate() or cron() expressions in UTC, as often as every 4 hours, with a rotation window (Duration). Turning rotation on rotates immediately by default; with --no-rotate-immediately, only the testSecret step runs to validate the setup.

Rotate the third-party API key on the 1st and 15th of each month at 04:00 UTC, within a 2-hour window (AWS CLI) 
aws secretsmanager rotate-secret \
  --secret-id prod/partner-api-key \
  --rotation-lambda-arn arn:aws:lambda:us-east-1:111111111111:function:rotate-partner-key \
  --rotation-rules '{"ScheduleExpression": "cron(0 4 1,15 * ? *)", "Duration": "2h"}'

# The rotation function must allow Secrets Manager to invoke it
aws lambda add-permission --function-name rotate-partner-key \
  --statement-id SecretsManager --action lambda:InvokeFunction \
  --principal secretsmanager.amazonaws.com --source-account 111111111111

A rotation function in a VPC needs a route or a Secrets Manager VPC endpoint to call the API. Security Hub CSPM controls check that rotation is on (SecretsManager.1), succeeding (SecretsManager.2), recent (SecretsManager.4, 90 days by default), and that unused secrets are removed (SecretsManager.3).

Getting secrets into applications

Retrieval patterns and their catches

  • Caching: the AWS Workload Credentials Provider (formerly the Secrets Manager Agent) serves secrets on localhost:2773 with a 5-minute cache and an SSRF token header, on EC2, ECS, EKS and Lambda; the Parameters and Secrets Lambda extension does the same for functions. Caches don't notice rotation; use the provider's refreshNow option or handle authentication failures by fetching again.
  • ECS: the secrets section of a task definition injects values at container start using the task execution role; running tasks keep the old value after rotation until they're replaced.
  • EKS: the Secrets Store CSI Driver with the AWS provider mounts secrets as files, authenticated with Pod Identity or IRSA.
  • CloudFormation: {{resolve:secretsmanager:prod/db:SecretString:password}} resolves at deployment, and isn't re-read when only the secret changes.

Replication, deletion and other credentials

Replica secrets copy a secret to other Regions (each can use a key in its Region); rotation happens in the primary and propagates. For disaster recovery, promote a replica with stop-replication-to-replica from the replica's Region. A deleted secret waits 7 to 30 days (default 30) before it's gone, and a primary with replicas can't be deleted until they're removed. Beyond Secrets Manager: rotate IAM user access keys (create the second key, switch, deactivate, delete; the access-keys-rotated Config rule flags keys older than 90 days), and prefer RDS IAM database authentication (15-minute tokens, MySQL, MariaDB and PostgreSQL) where an application can use it instead of a stored password.

"Rotation broke the application" usually means the app cached the password (ECS environment variable, CloudFormation reference, agent cache) or the single user strategy was used for a workload that can't retry. The fixes are re-fetching on authentication failure, replacing tasks after rotation, or the alternating users strategy.

Imported key material and external key stores

Skill 5.3.2Manage and use imported key material (for example, by managing and rotating imported key material, by managing and configuring external key stores).

Bringing your own key material

The import

A KMS key created with --origin EXTERNAL has no material and sits in PendingImport. You download a wrapping public key and import token (valid 24 hours), wrap your material with it, and import. Symmetric, asymmetric (except ML-DSA and ML-KEM) and HMAC keys can be imported, but not into custom key stores.

Create the key, get import parameters, import material that expires in a year (AWS CLI) 
aws kms create-key --origin EXTERNAL --description "Customer data key, material from corporate HSM"

aws kms get-parameters-for-import --key-id 1234abcd-12ab-34cd-56ef-1234567890ab \
  --wrapping-algorithm RSAES_OAEP_SHA_256 --wrapping-key-spec RSA_4096

# Wrap the material with the downloaded public key in your HSM, then:
aws kms import-key-material --key-id 1234abcd-12ab-34cd-56ef-1234567890ab \
  --encrypted-key-material fileb://EncryptedKeyMaterial.bin \
  --import-token fileb://ImportToken.bin \
  --expiration-model KEY_MATERIAL_EXPIRES \
  --valid-to 2027-11-01T00:00:00Z
  • Wrapping: RSA_4096 is the recommended wrapping key; RSA private keys must be wrapped with RSA_AES_KEY_WRAP_SHA_256; PKCS #1 v1.5 wrapping is no longer supported.
  • Expiry: the default expiration model is KEY_MATERIAL_EXPIRES, at most 365 days ahead. When it expires, KMS deletes the material and the key returns to PendingImport; re-import the same material to use it again. Alarm on approaching expiry.
  • Deleting material: delete-imported-key-material takes effect immediately and is reversible by re-importing, a fast kill switch that scheduled key deletion (7 to 30 days, irreversible) isn't. Without --key-material-id it deletes the current material.

Rotating imported material

Imported keys still can't rotate automatically, but symmetric ones can now rotate on demand: import new material as NEW_KEY_MATERIAL (it waits as PENDING_ROTATION), then rotate. Old material stays associated so existing ciphertext still decrypts, which also means you must keep every version: if any of the key's material is lost, the key becomes unusable.

Rotate to new imported material (AWS CLI) 
aws kms import-key-material --key-id 1234abcd-12ab-34cd-56ef-1234567890ab \
  --encrypted-key-material fileb://NewEncryptedKeyMaterial.bin \
  --import-token fileb://NewImportToken.bin \
  --expiration-model KEY_MATERIAL_DOES_NOT_EXPIRE \
  --import-type NEW_KEY_MATERIAL \
  --key-material-description "2026 Q4 rotation"

aws kms rotate-key-on-demand --key-id 1234abcd-12ab-34cd-56ef-1234567890ab

For a multi-Region imported key, import the new material into the primary, import the same material into each replica (as EXISTING_KEY_MATERIAL; until then the state is PENDING_MULTI_REGION_IMPORT_AND_ROTATION), then rotate on the primary. Replicas of imported keys start in PendingImport because you must import the same material into each one.

External key stores

Key material that never enters AWS

An external key store (XKS) backs KMS keys with keys in your own key manager outside AWS. KMS sends requests to an XKS proxy you run (built to AWS's open specification), reached over a public endpoint or, better, a VPC endpoint service (a PrivateLink service in front of an NLB in at least two AZs). KMS authenticates to the proxy with a SigV4 proxy authentication credential you create (not IAM keys), and data is double encrypted: first with KMS material for that key, then by your external key, so neither side can decrypt alone.

Create an external key store reached through PrivateLink, then a key in it (AWS CLI) 
aws kms create-custom-key-store \
  --custom-key-store-name market-x-xks \
  --custom-key-store-type EXTERNAL_KEY_STORE \
  --xks-proxy-connectivity VPC_ENDPOINT_SERVICE \
  --xks-proxy-vpc-endpoint-service-name com.amazonaws.vpce.us-east-1.vpce-svc-0123456789abcdef0 \
  --xks-proxy-uri-endpoint https://xks.internal.example.com \
  --xks-proxy-uri-path /kms/xks/v1 \
  --xks-proxy-authentication-credential AccessKeyId=EXAMPLEXKSACCESSID,RawSecretAccessKey=EXAMPLEXKSSECRET

aws kms connect-custom-key-store --custom-key-store-id cks-1234567890abcdef0
aws kms create-key --origin EXTERNAL_KEY_STORE --custom-key-store-id cks-1234567890abcdef0 --xks-key-id bb8562717f809024

The trade-offs are significant: you own availability, latency and durability (no SLA; requests time out at 250 ms; 1,800 requests per second per store, not adjustable), and keys are symmetric only, with no automatic rotation, multi-Region or imported material. Revoking access at the external manager "crypto-shreds" everything encrypted under those keys. AWS says external key stores are not recommended unless there's an explicit requirement to keep material outside AWS, and to prefer a CloudHSM key store if a custom key store is needed. Suitable only for low-volume uses such as EBS and RDS encryption.

"Material must be generated in our HSM, but we want normal KMS integrations and availability" points to imported key material. "Material must never leave our premises, and we must be able to cut AWS off" points to an external key store. "Single-tenant HSM in AWS behind KMS" points to a CloudHSM key store.

Imported versus AWS-generated key material

Skill 5.3.3Describe the differences between imported key material and AWS generated key material.

A key's origin is fixed at creation: AWS_KMS (generated by KMS), EXTERNAL (imported), AWS_CLOUDHSM (CloudHSM key store) or EXTERNAL_KEY_STORE. The condition key kms:KeyOrigin can restrict which origins people may create.

A deleted symmetric KMS key can't be recreated, even if you still hold the imported material: KMS binds unique metadata into every ciphertext. Asymmetric and HMAC material can be imported into a new key, but it gets a new key ID, policy and aliases. Deleting imported material is reversible; deleting the key isn't.

Masking sensitive data

Skill 5.3.4Mask sensitive data (for example, CloudWatch Logs data protection policies, Amazon SNS message data protection).

Masking in logs and messages

CloudWatch Logs data protection

A data protection policy on a log group or the account masks managed and custom data identifiers as data is ingested, everywhere it's read; only principals with logs:Unmask see the original. The policy shape and limits are in Task 1.2. It works in the Standard and Essentials log classes and applies only to data ingested after it's set.

SNS message data protection, and its replacement

SNS message data protection let a topic policy audit, mask, redact or deny messages containing sensitive data, inbound (on publish) or outbound (on delivery). It's closed to new customers since 30 April 2026 (existing users keep it, with security fixes only), so recognize the shape but design new masking with AWS's recommended pattern: publish to an intake topic, have a Lambda function check and redact content with Bedrock Guardrails sensitive information filters (Task 3.2), and publish the clean message to the delivery topic.

The existing-customer shape: mask card numbers for subscribers, block publishes carrying AWS secret keys (SNS data protection policy, JSON) 
{
  "Name": "orders-topic-protection",
  "Version": "2021-06-01",
  "Statement": [
    {
      "Sid": "MaskCardsOnDelivery",
      "DataDirection": "Outbound",
      "Principal": ["*"],
      "DataIdentifier": ["arn:aws:dataprotection::aws:data-identifier/CreditCardNumber"],
      "Operation": { "Deidentify": { "MaskConfig": { "MaskWithCharacter": "#" } } }
    },
    {
      "Sid": "DenySecretsOnPublish",
      "DataDirection": "Inbound",
      "Principal": ["*"],
      "DataIdentifier": ["arn:aws:dataprotection::aws:data-identifier/AwsSecretKey"],
      "Operation": { "Deny": {} }
    }
  ]
}

Masking data sets

Analytics and data lakes

  • AWS Glue sensitive data detection scans columns or cells in ETL jobs and can redact, partially redact or replace values with a SHA-256 hash before data lands in the lake.
  • Lake Formation data filters hide columns and rows (together, individual cells) from users querying through Athena and other engines, without copying data.
  • Amazon Comprehend detects and redacts PII in text, for example support tickets.
  • Amazon Macie finds sensitive data in S3 but doesn't mask it; use it to decide what the masking must cover.

"Developers need the application logs, but not the customers' emails in them" points to a CloudWatch Logs data protection policy. "Analysts may query the table but not see card numbers" points to Lake Formation data filters or Glue redaction. "Mask PII in messages for a new SNS design" points to Lambda with Bedrock Guardrails, not message data protection.

Keys and certificates across Regions

Skill 5.3.5Create and manage encryption keys and certificates across a single AWS Region or multiple Regions (for example, AWS KMS customer managed AWS KMS keys, AWS Private Certificate Authority).

KMS keys in one or many Regions

Single-Region or multi-Region keys

AWS's advice is that single-Region keys fit most needs: one key per Region, data re-encrypted when it moves. A multi-Region key (ID starting mrk-) shares its key ID and material with replicas in other Regions, so ciphertext from one Region decrypts in another without a cross-Region call. That suits client-side encryption of data replicated between Regions (DynamoDB global tables, S3 objects encrypted by the application) and disaster recovery. Most AWS services still treat it as a Regional key.

  • Shared (from the primary): key ID, material, key spec and usage, origin, rotation. Independent: key policy, grants, aliases, tags, description, enabled state. A replica created without a policy gets the default key policy, not a copy of the primary's.
  • You can't convert a single-Region key to multi-Region or back. Rotation is configured on the primary only. Each primary and replica is billed as a key.
Replicate the client-side encryption key to the DR Region, and move the primary there if needed (AWS CLI) 
aws kms replicate-key \
  --key-id arn:aws:kms:us-east-1:111111111111:key/mrk-1234abcd12ab34cd56ef1234567890ab \
  --replica-region us-west-2 \
  --policy file://dr-key-policy.json

aws kms update-primary-region \
  --key-id arn:aws:kms:us-east-1:111111111111:key/mrk-1234abcd12ab34cd56ef1234567890ab \
  --primary-region us-west-2

Rotation, policies and deletion

Automatic rotation (enable-key-rotation --rotation-period-in-days 180, anywhere from 90 to 2,560 days) and on-demand rotation (rotate-key-on-demand, up to 25 times per key) create new material and keep the old for decryption; they don't re-encrypt data, and they don't help if a data key was exposed. Asymmetric, HMAC and custom key store keys rotate only by creating a new key and moving the alias.

Separate key administrators (manage the key, can't use it) from key users (use it, can't manage it); note that the console's default administrator permissions include ScheduleKeyDeletion unless you untick it. Deletion waits 7 to 30 days in PendingDeletion; during that time, an alarm on attempts to use the key (from CloudTrail) catches anything still depending on it, and disabling the key first is the safer test. A common guardrail is an SCP that denies scheduling deletion except for a break-glass role:

Only the key custodian role can schedule key deletion, anywhere in the organization (SCP statement, JSON) 
{
  "Sid": "ProtectKmsKeysFromDeletion",
  "Effect": "Deny",
  "Action": ["kms:ScheduleKeyDeletion", "kms:DeleteImportedKeyMaterial"],
  "Resource": "*",
  "Condition": {
    "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/key-custodian" }
  }
}

Security Hub CSPM controls KMS.3 (keys not scheduled for deletion, Critical), KMS.4 (rotation enabled) and KMS.5 (no public key policy) watch for mistakes. The newer GetKeyLastUsage API shows when a key was last used, but AWS advises disabling the key and watching CloudTrail before deleting rather than relying on it alone.

AWS Private CA

Internal certificates

AWS Private CA runs private root and subordinate CAs whose keys are held in HSMs (FIPS 140-2 Level 3 by default), with RSA, ECDSA and, since November 2025, ML-DSA keys. Two modes:

  • General purpose ($400 per CA per month): certificates of any validity, usually with revocation.
  • Short-lived certificate ($50 per CA per month): certificates valid at most 7 days, where expiry replaces revocation. A short-lived CA must be the last CA in its chain, and ACM can't issue from it.

Best practice is a root CA used only to sign subordinate CAs, and subordinates (one per Region or purpose) that issue certificates; templates such as SubordinateCACertificate_PathLen0/V1 limit what each can sign. CAs are Regional and can be shared with other accounts through AWS RAM.

Revocation and issuance

CRLs and OCSP are both off by default. CRLs are written to an S3 bucket (with Block Public Access on, set the object ACL to BUCKET_OWNER_FULL_CONTROL and serve it through a custom CNAME), and partitioned CRLs allow far more certificates per CA. Certificates come two ways:

  • Through ACM (aws acm request-certificate --certificate-authority-arn ...): managed private certificates that attach to load balancers and other integrated services and renew automatically.
  • With IssueCertificate from your own CSR: unmanaged certificates, not visible in or renewed by ACM; you track expiry.
Issue a one-year certificate for an internal service from a CSR (AWS CLI) 
aws acm-pca issue-certificate \
  --certificate-authority-arn arn:aws:acm-pca:us-east-1:111111111111:certificate-authority/11223344-1234-1122-2233-112233445566 \
  --csr fileb://orders-api.csr \
  --signing-algorithm SHA256WITHRSA \
  --template-arn arn:aws:acm-pca:::template/EndEntityServerAuthCertificate/V1 \
  --validity Value=365,Type=DAYS

Certificates across Regions

ACM is Regional

ACM certificates exist in one Region and renew independently in each; a certificate for CloudFront must be in us-east-1. Imported certificates are never renewed by ACM. Watch expiry with the DaysToExpiry CloudWatch metric, the Config rule acm-certificate-expiration-check (Security Hub CSPM ACM.1) and the ACM EventBridge event, which starts 30 days ahead for public certificates and 45 for private and imported ones:

Alert on certificates nearing expiry in every account (EventBridge event pattern) 
{
  "source": ["aws.acm"],
  "detail-type": ["ACM Certificate Approaching Expiration"]
}

A private certificate issued with IssueCertificate doesn't renew, and an ACM private certificate in an account using a shared CA renews only if that account still has ACM's service-linked role and permission on the CA. Expired internal certificates are a common outage; issue through ACM where the service supports it, or use short-lived certificates with automated reissue.

"Decrypt in us-west-2 data that the application encrypted in us-east-1, without calling us-east-1" points to a multi-Region key. "Internal TLS certificates that renew themselves on load balancers" points to ACM private certificates from Private CA. "Certificates for containers that live a few days" points to short-lived certificate mode.

Key takeaways

  • Secrets Manager rotation: managed (RDS, Aurora, DocumentDB, Redshift, external SaaS secrets) or Lambda; createSecret, setSecret, testSecret, finishSecret with AWSPENDING, AWSCURRENT, AWSPREVIOUS; single user or alternating users (needs superuser secret, not with RDS Proxy); every 4 hours at most often; rotates immediately when turned on.
  • RDS-managed master passwords rotate every 7 days; caches, ECS environment variables and CloudFormation references don't pick up rotation by themselves. Parameter Store has no rotation and 4 or 8 KB limits; replica secrets for other Regions; 7 to 30 day deletion window.
  • Imported material: --origin EXTERNAL, 24-hour import token, RSA_4096 wrapping, expiry up to 365 days (default expires), instant reversible deletion, on-demand rotation with NEW_KEY_MATERIAL, you keep every version; multi-Region imports into each replica.
  • External key stores: XKS proxy over PrivateLink, SigV4 proxy credential, double encryption, no SLA, 250 ms and 1,800 requests per second, symmetric single-Region only; not recommended unless required.
  • Origins differ in rotation (automatic 90 to 2,560 days only for AWS_KMS), expiry, durability (you for imported) and SLA (none for custom key stores). Deleted symmetric keys can never be recreated.
  • Masking: CloudWatch Logs data protection with logs:Unmask; SNS message data protection closed to new customers (use Lambda and Bedrock Guardrails); Glue redaction and hashing, Lake Formation filters, Comprehend; Macie finds but doesn't mask.
  • Multi-Region keys share material and ID but not policies; can't convert; rotation on the primary. Separate key admins from users, deny deletion by SCP, watch KMS.3 to KMS.5.
  • Private CA: general purpose or short-lived (7 days, last in chain, not via ACM), root and subordinates with path-length templates, CRL and OCSP off by default, RAM sharing; ACM-managed private certificates renew, IssueCertificate ones don't; ACM is Regional, CloudFront certificates in us-east-1.
