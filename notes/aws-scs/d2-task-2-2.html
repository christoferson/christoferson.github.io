Task 2.2: Respond to security events

The response itself: preserving evidence before it disappears, following the attacker through the logs, working out what was touched, cutting off access, removing what the attacker left behind, restoring clean systems, and finding out how it happened.

Overview

Task 2.2

Respond to security events.

This is the operations phase of the plan from Task 2.1: analyze, contain, eradicate, recover, then learn. Exam questions here are full of traps where the obvious action destroys evidence or doesn't actually stop the attacker: stopping an instance before capturing memory, swapping a security group and assuming open connections are closed, rotating a KMS key to "revoke" it, deleting an access key while sessions it created keep working. The details below are the ones that decide those questions.

Running example. The same company. GuardDuty in the security tooling account (222222222222) raises UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS: credentials from the role on a web server in prod (111111111111) are being used from an IP address outside AWS. The responders, using the access and Forensics OU accounts prepared in Task 2.1, work through this page's steps.

Capturing forensic artifacts

Skill 2.2.1Capture and store relevant system and application logs as forensic artifacts.

A compromised EC2 instance

Volatile evidence first

Memory holds running processes, network connections and decrypted secrets that exist nowhere else. AWS's EC2 forensics playbook says to capture memory before isolating or shutting the instance down. Stopping, hibernating or terminating an instance also cryptographically erases its instance store volumes, so copy anything there first. A reboot keeps instance store but loses memory. The order in the running example:

  1. Preserve the instanceTurn on termination and stop protection, set shutdown behavior to stop, set DeleteOnTermination to false on every volume, and take the instance out of its Auto Scaling group (detach, or enter standby) and target groups so it isn't replaced or terminated.
  2. Record metadataInstance ID and type, AMI, IP addresses, security groups, VPC and subnet, role, launch time, tags; console output and a screenshot.
  3. Capture memoryRun a memory acquisition tool (AWS samples use AVML; LiME is the other common one) through SSM Run Command, writing to the evidence bucket.
  4. Snapshot the disksCrash-consistent snapshots of every attached volume in one call, tagged with the case ID.
  5. Then containNetwork and credential containment (Skill 2.2.4), now that the evidence is safe.
Preserve, record and snapshot the web server (AWS CLI, prod account) 
# 1. Don't let anything terminate or replace it
aws ec2 modify-instance-attribute --instance-id i-0abc1234def567890 --disable-api-termination
aws ec2 modify-instance-attribute --instance-id i-0abc1234def567890 --disable-api-stop
aws ec2 modify-instance-attribute --instance-id i-0abc1234def567890 \
  --block-device-mappings '[{"DeviceName": "/dev/xvda", "Ebs": {"DeleteOnTermination": false}}]'
aws autoscaling enter-standby --auto-scaling-group-name web-asg \
  --instance-ids i-0abc1234def567890 --should-decrement-desired-capacity

# 2. What the console showed (Nitro: --latest gives the most recent output)
aws ec2 get-console-output --instance-id i-0abc1234def567890 --latest --output text > console-output.txt
aws ec2 get-console-screenshot --instance-id i-0abc1234def567890

# 4. One crash-consistent snapshot per attached volume, tagged for the case
aws ec2 create-snapshots \
  --instance-specification InstanceId=i-0abc1234def567890 \
  --copy-tags-from-source volume \
  --description "IR-2026-117 evidence" \
  --tag-specifications 'ResourceType=snapshot,Tags=[{Key=case,Value=IR-2026-117}]'

Termination protection isn't available for Spot Instances; detach a Spot instance from its group and rely on scale-in protection instead. And don't stop the instance "to be safe": memory and instance store evidence are gone the moment it stops.

Moving evidence to the forensics account

Sharing encrypted snapshots

The investigation happens in the forensics account, in the same Region as the incident (moving data between jurisdictions can have legal consequences). Snapshots are shared with modify-snapshot-attribute, but only if they're unencrypted or encrypted with a customer managed key: snapshots encrypted with the default aws/ebs key can't be shared. If that's what you have, copy the snapshot with a customer managed key first. The key policy must let the forensics account use the key, including creating grants for EBS.

Let the forensics account use the evidence key (two statements of the KMS key policy, prod account) 
[
  {
    "Sid": "AllowForensicsAccountToUseTheKey",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::666666666666:root" },
    "Action": ["kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*", "kms:GenerateDataKey*", "kms:DescribeKey"],
    "Resource": "*"
  },
  {
    "Sid": "AllowForensicsAccountToCreateGrantsForEBS",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::666666666666:root" },
    "Action": ["kms:CreateGrant", "kms:ListGrants", "kms:RevokeGrant"],
    "Resource": "*",
    "Condition": { "Bool": { "kms:GrantIsForAWSResource": true } }
  }
]
Share the snapshot; the forensics account then copies it with its own key (AWS CLI) 
# In prod (111111111111)
aws ec2 modify-snapshot-attribute --snapshot-id snap-0abcdef1234567890 \
  --attribute createVolumePermission --operation-type add --user-ids 666666666666

# In the forensics account (666666666666): make its own copy, encrypted with its own key
aws ec2 copy-snapshot --source-region us-east-1 --source-snapshot-id snap-0abcdef1234567890 \
  --encrypted --kms-key-id arn:aws:kms:us-east-1:666666666666:key/forensics-key-id \
  --description "IR-2026-117 working copy"

CloudTrail in the owner account records use of the shared snapshot (SharedSnapshotCopyInitiated, SharedSnapshotVolumeCreated), which becomes part of the chain of custody. RDS has the same rule: snapshots encrypted with the default RDS key can't be shared.

Handling evidence

Treat evidence as read-only: work only on copies, mount evidence volumes read-only on the forensic instance, and record who accessed what and when. Store memory images and exported logs in the forensics account's S3 bucket with Object Lock (Task 1.2), so nobody can alter or delete them, and let CloudTrail data events record every read. The EBS direct APIs return a SHA-256 checksum for each block read from a snapshot, which helps show the data wasn't altered in transit. Once the case closes, delete the forensic instance and copies unless a legal or regulatory requirement says to keep them.

Other resource types

Containers, functions and databases

  • EKS: find the pod's node (kubectl get pods <pod> -o=jsonpath='{.spec.nodeName}') and its instance ID, label the pod and node for the investigation, capture container state and logs on the node with crictl ps and crictl logs, then capture node memory and snapshot its volumes as for EC2. If one pod of a Deployment is compromised, assume all of them are. Keep the cluster's control plane audit logs (Task 1.2).
  • ECS on Fargate: there's no host to image, so the evidence is the task's logs, its definition and image, and CloudTrail; GuardDuty's guidance is to isolate the task's traffic, then stop it.
  • Lambda: aws lambda get-function --function-name orders-api --qualifier 7 returns the configuration (role, layers, environment variables) and a link to download that version's code, valid for 10 minutes. Download it before anyone redeploys. Environment variable values are omitted from CloudTrail.
  • RDS and Aurora: take a manual snapshot (aws rds create-db-snapshot) and keep the database's audit and error logs.
  • S3: with versioning, earlier versions of changed objects are evidence; CloudTrail data events and server access logs show who read what.

"Preserve evidence from a compromised instance with minimal data loss" points to memory capture first, then EBS snapshots, then isolation, with termination protection and the instance taken out of its Auto Scaling group. Automating that sequence is what the Automated Forensics Orchestrator guidance does (Task 2.1).

Searching and correlating logs

Skill 2.2.2Search and correlate logs for security events across applications and AWS services.

Following the credentials

Access key IDs

An access key ID tells you what kind of credential you're chasing. Keys starting AKIA are long-term keys of an IAM user (or the root user); keys starting ASIA are temporary credentials from AWS STS. aws sts get-access-key-info --access-key-id ... returns only the owning account ID, not who owns it or whether it's still active. For an AKIA key, the IAM credential report names the user; for an ASIA key, find the STS call that issued it.

Role sessions and chains

Every call made with a role session carries userIdentity.accessKeyId (the session's ASIA key) and userIdentity.sessionContext.sessionIssuer (the role it came from), with attributes.creationDate saying when the session started and ec2RoleDelivery showing whether the credentials came from IMDSv1 or IMDSv2. The AssumeRole event that created a session lists the new key in responseElements.credentials.accessKeyId, so searching for that key follows the attacker into the next role. If roles are assumed with a source identity (sts:SetSourceIdentity), it appears in sessionContext.sourceIdentity on every later call and can't be changed, even through chained roles, unlike the role session name.

Where to search

CloudTrail Event history

For a quick first look, lookup-events searches the last 90 days of management events in the current Region (and Insights events with --event-category insight). It takes one attribute per call (AccessKeyId, EventName, EventSource, ResourceName, ResourceType, Username, ReadOnly or EventId), returns up to 50 events per page and allows two requests per second.

Everything the stolen session key did in us-east-1 recently (AWS CLI) 
aws cloudtrail lookup-events \
  --region us-east-1 \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=ASIAIOSFODNN7EXAMPLE \
  --start-time 2026-11-08T00:00:00Z \
  --query 'Events[].[EventTime,EventName,EventSource]' --output table

Athena over the organization trail

Event history can't see data events, other Regions or anything older than 90 days, so the real investigation runs on the organization trail in the log archive (with the Athena table from Task 1.2) or on Security Lake. The two questions that matter first: where did the stolen credentials come from, and what did they do?

Every call made with the instance role from outside the VPC, by source IP and action (Athena SQL) 
SELECT eventtime, sourceipaddress, useragent, eventsource, eventname, errorcode,
       useridentity.accesskeyid
FROM cloudtrail_prod_use1
WHERE "timestamp" >= '2026/11/07'
  AND useridentity.sessioncontext.sessionissuer.arn = 'arn:aws:iam::111111111111:role/web-server-role'
  AND sourceipaddress NOT LIKE '10.%'          -- the VPC's own range
ORDER BY eventtime;

The documented CloudTrail table definition doesn't include sessioncontext.sourceidentity; add it to the useridentity struct if you trace sessions by source identity. Then pivot on what the query returns: the attacker's IP in VPC Flow Logs and WAF logs, domains the instance resolved in Resolver query logs, and requests in application logs. Logs Insights can do the same across log groups, and its OpenSearch SQL language can join log groups in one query.

lookup-events isn't an organization-wide search: it covers one account and one Region, management events only. "Find every S3 object the attacker downloaded" needs S3 data events from the trail (Athena, Security Lake), not Event history.

Validating findings and scoping impact

Skill 2.2.3Validate findings from AWS security services to assess the scope and impact of an event.

Is the finding real?

Reading a GuardDuty finding

  • Resource role: TARGET means your resource was acted on (the finding has an Actor section); ACTOR means your instance attacked something else (it has a Target section).
  • Count, created and updated: how often the activity recurred, and whether it's still going on (updated later than created).
  • Action: network connection, port probe, DNS request, AWS API call (with the API, user agent and whether the remote account is affiliated with you) or RDS login attempt.
  • Evidence: for threat intelligence findings, the threat list and indicator that matched.

For an attack sequence (Extended Threat Detection), the signals show each step that was linked: high-risk API calls, unusual ASNs, malicious IPs or domains, and, since 2026, vulnerabilities and misconfigurations. For credential exfiltration, InsideAWS means the credentials were used from another AWS account (check whether it's one of yours) and OutsideAWS from outside AWS.

GuardDuty learns. If credential exfiltration findings for an instance stop appearing, it may be because the model now treats the remote host as expected, not because the attacker has gone. Silence isn't evidence of containment; check CloudTrail.

False positives

If the activity is legitimate (a vulnerability scanner, a known egress IP), there are two tools. A suppression rule archives matching findings as they arrive; build them only for findings you've repeatedly confirmed as false positives, with at least two criteria (finding type plus scanner AMI, bastion tag or egress IP). A trusted entity list (IPs, and since August 2025 domains) stops GuardDuty generating findings for those public addresses at all. Both hide data from Extended Threat Detection, Security Hub CSPM, Detective and EventBridge, so keep them narrow.

How far did it reach?

What the credentials could do and did do

The role's policies and the IAM last accessed data (service level, and action level for most services) show what the stolen credentials could reach and what was actually used; combine that with CloudTrail for the incident window. IAM Access Analyzer adds external access findings (resources shared outside the organization, perhaps by the attacker) and unused access findings.

Which services and actions the role has used (AWS CLI) 
JOB=$(aws iam generate-service-last-accessed-details \
  --arn arn:aws:iam::111111111111:role/web-server-role \
  --granularity ACTION_LEVEL --query JobId --output text)
aws iam get-service-last-accessed-details --job-id "$JOB"

AWS warns not to decide permissions only on the absence of last accessed data: tracking started at different dates for different services.

Data and vulnerabilities

  • Data exposure: if the role could read S3 buckets, Macie sensitive data findings and automated discovery show which of those buckets hold personal, financial or credential data, which decides notification obligations. GuardDuty S3 findings with an ANONYMOUS_PRINCIPAL caller mean a public bucket was read.
  • Exploitability: Amazon Inspector findings on the instance show whether a vulnerability has a known exploit and a fix (exploitAvailable, fixAvailable) and, for EC2, which ports are reachable from the internet, which helps answer how the attacker got in and which other instances share the weakness. For container images, Inspector shows how many running tasks and pods use the image.

Containing, eradicating and recovering

Skill 2.2.4Respond to affected resources by containing and eradicating threats, and recover resources (for example, by implementing network containment controls, restoring backups).

Containing credentials

Long-term access keys

Deactivate rather than delete first (aws iam update-access-key --user-name app-user --access-key-id AKIA... --status Inactive): deactivation is reversible and keeps the key ID for the investigation; delete it once the replacement works. When AWS finds an exposed key it attaches AWSCompromisedKeyQuarantineV3 to the user and opens a support case; follow the case instead of removing the policy. Deactivating a key also invalidates every presigned URL signed with it, even ones with a later expiry.

Role sessions can't be deleted, only denied

Temporary credentials stay valid until they expire (up to 36 hours), and deleting the key that created them doesn't end them. Instead, add a deny that applies to them. Revoke active sessions on the role (console, Revoke sessions tab) attaches an inline policy named AWSRevokeOlderSessions that denies everything to sessions issued before the moment you clicked; new sessions, including the legitimate workload's next credentials, keep working.

What "revoke active sessions" attaches to the role (IAM inline policy, with the time you revoked) 
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Deny",
    "Action": "*",
    "Resource": "*",
    "Condition": {
      "DateLessThan": { "aws:TokenIssueTime": "2026-11-09T14:32:00Z" }
    }
  }
}

To deny one principal or session rather than every older session, AWS's examples use aws:userid (for example "AROAEXAMPLEROLEID:*" for all sessions of a role), aws:PrincipalArn or aws:SourceIdentity. Sessions revoked this way can still use permissions a resource-based policy grants them, so add the deny there too for sensitive resources. Revoking doesn't work on service-linked roles.

Stolen instance credentials

In the running example the instance role's credentials are being used from outside AWS. Revoking older sessions on the role stops the stolen copy, but the instance will fetch new credentials, so the root cause (often IMDSv1 and a server-side request forgery bug, or a compromised host) must also be closed. AWS documents a policy that denies instance credentials used anywhere except from their own instance's VPC, usable in identity policies, SCPs and resource policies:

Instance role credentials only work from the instance's own VPC (SCP or identity policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireSameVPC",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:SourceVpc": "${aws:Ec2InstanceSourceVpc}" },
        "Null": { "ec2:SourceInstanceARN": "false" },
        "BoolIfExists": { "aws:ViaAWSService": "false" }
      }
    }
  ]
}

aws:SourceVpc is only in the request when the call goes through a VPC endpoint, so this pattern assumes the workload reaches AWS APIs through endpoints. Removing or replacing the instance profile (disassociate-iam-instance-profile) stops new credentials but doesn't invalidate ones already issued, so revoke sessions as well. A deny on ec2:RoleDelivery below 2.0 blocks credentials obtained through IMDSv1.

IAM Identity Center users and member account root users

Roles created by Identity Center permission sets can't be edited, so contain the user: AWS recommends a pre-staged SCP that denies everything when identitystore:userId equals the user's ID, then removing the user's assignments, disabling them in the identity provider, deleting their active sessions before disabling the user (afterwards the console can't end them), and leaving the deny in place for at least 12 hours. For a member account's root user, centralized root access lets the management account or a delegated administrator run aws sts assume-root with the IAMDeleteRootUserCredentials task policy (through a Regional STS endpoint) to remove the root password, keys and MFA without ever signing in as root.

Containing the network

Security groups don't cut existing connections

The standard isolation step is replacing all of an instance's security groups with an isolation security group that has no inbound and no outbound rules. But security groups are stateful: when you change them, tracked connections already open continue until they time out, and an idle established TCP connection stays tracked for 5 days by default on most instance types (350 seconds on the newest Nitro generation). An attacker's open reverse shell survives the swap. AWS's GuardDuty remediation, the EC2 documentation and the AWS containment runbook all say this.

To break existing connections immediately, use a network ACL: NACLs are stateless, so a deny rule stops packets at once, but it applies to the whole subnet. The exception to the tracking rule: flows allowed by rules open to 0.0.0.0/0 on all ports in both directions aren't tracked, so removing those rules drops them at once.

Cut every session to and from the attacker's network at once (AWS CLI, subnet's NACL) 
# NACL rules are evaluated lowest number first; put the denies ahead of the allows
aws ec2 create-network-acl-entry --network-acl-id acl-0abc1234def567890 \
  --ingress --rule-number 10 --protocol -1 --cidr-block 203.0.113.0/24 --rule-action deny
aws ec2 create-network-acl-entry --network-acl-id acl-0abc1234def567890 \
  --egress --rule-number 10 --protocol -1 --cidr-block 203.0.113.0/24 --rule-action deny

Other network controls complete the picture: add attacker IPs to a WAF IP set used by a block rule (update-ip-set replaces the whole list, so get the current list and its lock token first, then write the merged list), block domains with Route 53 Resolver DNS Firewall (security groups don't control DNS queries to the VPC resolver), and add rules to Network Firewall for traffic between VPCs and the internet.

Containing other resources

Buckets, containers and functions

  • S3: turn on Block Public Access for the bucket (or the account), add a bucket policy deny for everything but the responders, and deactivate the keys that signed any leaked presigned URLs. A bucket policy can also refuse signatures older than a set age with s3:signatureAge.
  • EKS: apply a deny-all NetworkPolicy to the compromised pods, cordon the node (kubectl cordon), remove AWS permissions from the node's role, and remove the attacker's access entry or aws-auth mapping. A network policy doesn't help if the attacker controls the node; then isolate the node with security groups. Fargate pods can't be cordoned, so the network policy is the tool there.
  • ECS: block the task's traffic, find other tasks using the same image, start fixed replacements, then stop the compromised tasks and remove the image from the repository.
  • Lambda: set reserved concurrency to 0 (aws lambda put-function-concurrency --function-name orders-api --reserved-concurrent-executions 0), which stops all invocations until removed; then remove or fix triggers and redeploy a known-good version.
Isolate the compromised pods (Kubernetes NetworkPolicy) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ir-deny-all
  namespace: shop
spec:
  podSelector:
    matchLabels:
      status: quarantine       # label applied to the compromised pods
  policyTypes:
    - Ingress
    - Egress                   # no rules listed, so nothing is allowed either way

Eradication

Remove everything the attacker left

AWS's guidance is to work in phases: high-value changes first, longer-term hardening later. Look for persistence in every Region, including ones the company never uses: new IAM users, access keys, roles and policies, new SAML or OIDC identity providers, instances and AMIs (including stopped ones), snapshots, Lambda functions and layers, EventBridge rules, and changes that weaken detection (deleted trails, GuardDuty detectors or Config recorders, Block Public Access removed). Then:

  • Rebuild, don't clean: replace compromised instances and containers with new ones from a trusted AMI or image, patched (Systems Manager Patch Manager) and with the vulnerability fixed.
  • Rotate what may have been read: Secrets Manager secrets (aws secretsmanager rotate-secret --secret-id prod/orders/db), database passwords, API keys and anything in environment variables the attacker could see.
  • Don't rely on KMS key rotation: rotating a KMS key keeps the old key material, so old ciphertext still decrypts and a compromised data key stays compromised. Fix the key policy and grants, or disable the key.

Recovery

Restoring from protected backups

Backups help only if the attacker couldn't delete or encrypt them. AWS Backup Vault Lock enforces retention on a vault: in governance mode users with the right IAM permissions can remove the lock; in compliance mode, once the grace time (at least 72 hours) has passed, nobody can change or delete the vault or its lock, not even AWS. A logically air-gapped vault always uses compliance mode, stores backups in an AWS-owned account, can be shared with a recovery account through AWS RAM, and since November 2025 can be the primary backup target; with multi-party approval you can restore from it even if the owning account is lost. A legal hold keeps chosen backups from deletion indefinitely.

Lock the prod vault in compliance mode after a 3-day grace time (AWS CLI) 
# --changeable-for-days makes it compliance mode; omit it for governance mode
aws backup put-backup-vault-lock-configuration \
  --backup-vault-name prod-vault \
  --changeable-for-days 3 \
  --min-retention-days 35 \
  --max-retention-days 365

Before restoring, make sure the backup itself is clean: GuardDuty Malware Protection for AWS Backup (November 2025) scans EBS snapshots, AMIs and recovery points. AWS Backup restore testing checks regularly that restores work at all.

Point-in-time recovery

  • DynamoDB point-in-time recovery restores to any second in a window of 1 to 35 days, always into a new table.
  • RDS restores to a point in time as a new DB instance (restore-db-instance-to-point-in-time), so the compromised one stays for investigation.
  • S3 versioning restores an object by copying an earlier version over the current one, or by deleting the bad current version.
  • AWS Elastic Disaster Recovery recovers whole servers to a point in time before the attack (useful against ransomware), and supports drills without disrupting replication.

Reconnect restored systems only after the eradication steps are complete and the restored versions are patched; otherwise the attacker comes straight back in through the same route.

"Immediately terminate the attacker's active SSH session to the instance" points to a network ACL deny, not a security group change. "Stop stolen role credentials working without breaking the application" points to revoke active sessions on the role. "Backups that can't be deleted even by an administrator with full access" points to Vault Lock in compliance mode or a logically air-gapped vault.

Root cause analysis

Skill 2.2.5Describe methods to conduct root cause analysis (for example, Amazon Detective).

Amazon Detective

A behavior graph of the organization

Detective builds a behavior graph from CloudTrail, VPC Flow Logs and GuardDuty findings (plus optional EKS audit logs and Security Hub CSPM findings, or Security Lake data), keeps up to a year of history, and uses its own copy of the data, so it doesn't affect your logging. For any entity (a role, a user, an IP, an instance) it shows activity during a scope time compared with the 45 days before: new geolocations, unusual API calls, new user agents, traffic volumes. That comparison is what turns "this role was used from a new country" into a root cause.

  • Finding groups collect related findings and entities into one event, with a timeline and a generative AI summary (on by default, at no extra charge).
  • Detective Investigation analyzes an IAM user or role for indicators of compromise: attack tactics, impossible travel, flagged IP addresses and related finding groups, producing a report.
  • From a GuardDuty finding, Investigate in Detective opens the entity with the right scope time.
Investigate the instance role over the incident window (AWS CLI, Detective administrator) 
aws detective start-investigation \
  --graph-arn arn:aws:detective:us-east-1:222222222222:graph:fdac8011456e4e6182facb26dfceade0 \
  --entity-arn arn:aws:iam::111111111111:role/web-server-role \
  --scope-start-time 2026-11-07T00:00:00Z \
  --scope-end-time 2026-11-09T15:00:00Z

Detective no longer requires GuardDuty to be enabled (since February 2024), uses the same delegated administrator pattern as the other services, and needs about two weeks of data before its baselines are meaningful.

Other investigation tools

AI-assisted investigation

  • GuardDuty Investigation (preview since June 2026, in 10 Regions) analyzes a finding, an account or the organization over the last 90 days and returns a risk level, a summary, MITRE ATT&CK techniques and recommended actions. It's enabled as the AI_ANALYST feature on the detector.
  • AWS Security Incident Response runs an AI investigative agent on AWS-supported cases (not self-managed ones), building a timeline from CloudTrail, IAM and EC2 data.
  • CloudWatch investigations is for operational incidents (metrics, deployments, AWS Health), not security root cause.

Finishing the analysis

The root cause in the running example is the first event in the chain: Athena shows the instance's credentials first used outside the VPC minutes after an HTTP request in the ALB and WAF logs that reached the instance metadata service through a server-side request forgery bug, and ec2RoleDelivery shows the credentials came from IMDSv1. The fixes that follow (require IMDSv2 everywhere with an SCP or declarative policy, fix the code, add the WAF rule, add the same-VPC credential policy) and the incident metrics (time to detect, contain and recover, and attacker dwell time) go into the post-incident report and back into the playbooks.

If the investigation shows AWS resources being used to attack others, or abuse by another AWS customer, report it to AWS Trust & Safety (the abuse form or trustandsafety@support.aws.com); for credentials used from another AWS account, GuardDuty's guidance is to include the finding's full JSON. Respond quickly to abuse notices AWS sends you.

"Determine how the compromised role was used and where the activity came from over the past weeks" points to Amazon Detective. "Query a year of CloudTrail data events for exactly what was read" points to Athena or Security Lake. Detective shows patterns and context; the logs hold the detail.

Key takeaways

  • Evidence order: protect the instance (termination and stop protection, DeleteOnTermination false, out of its Auto Scaling group), record metadata, capture memory, snapshot every volume with create-snapshots, then isolate. Stopping erases memory and instance store.
  • Share evidence snapshots only with a customer managed key (never aws/ebs); grant the forensics account in the key policy; it copies with its own key; same Region; Object Lock evidence bucket; work on copies.
  • AKIA keys are long-term, ASIA keys are STS; get-access-key-info gives only the account; follow AssumeRole response keys and sourceIdentity. Event history: 90 days, management events, one attribute, 50 per page; use Athena or Security Lake for everything else.
  • Scope: GuardDuty resource role, count and action details, attack sequence signals; findings can stop because GuardDuty learns; suppression and trusted lists hide data; last accessed data, Access Analyzer, Macie and Inspector show reach and impact.
  • Credentials: deactivate keys (also kills their presigned URLs); revoke older role sessions with aws:TokenIssueTime; same-VPC policy with aws:Ec2InstanceSourceVpc; Identity Center: pre-staged SCP on identitystore:userId, delete sessions before disabling; root via assume-root.
  • Network: security group changes leave tracked connections open (up to 5 days idle); NACL denies cut them at once; WAF IP sets (replace the whole list), DNS Firewall, Network Firewall. EKS deny-all NetworkPolicy and cordon; Lambda reserved concurrency 0.
  • Eradicate in every Region: persistence in IAM, identity providers, compute and automation; rebuild from trusted images; rotate secrets; KMS rotation doesn't revoke anything.
  • Recover: Vault Lock compliance mode (immutable after at least 72 hours), logically air-gapped vaults, legal holds, Malware Protection for Backup, restore testing; DynamoDB and RDS point-in-time restores create new resources; S3 versions; Elastic Disaster Recovery.
  • Root cause: Detective behavior graph (45-day baseline, finding groups, Investigation for IAM users and roles), GuardDuty Investigation (preview), Security IR AI agent; fixes and metrics into the post-incident report.
