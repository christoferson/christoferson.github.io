Reference architecture

Workforce identity and temporary elevated access

Every employee signs in once, through the corporate identity provider, and lands in the accounts their groups allow with short-lived role credentials. Day-to-day access is read-mostly and tag-scoped; production changes need an approved, time-boxed elevation; and when the normal path fails there is a sealed, alerted way in that nobody uses otherwise.

Scenario and requirements

The company (organization o-exampleorgid) already has its accounts laid out as the security baseline describes, with IAM Identity Center and centralized root access delegated to the identity account 666600006666. What it lacks is a coherent access design: some teams federate straight into accounts, contractors have IAM users with keys, and the platform team holds standing administrator access to production. Everyone, contractors included, lives in the corporate identity provider (IdP).

How it works

One payments developer, one normal day and one production change. Steps marked AWS happen without anyone acting.

  1. Provisioned before the first sign-in
  2. Joiner added in the IdPHR and IdP adminsThe developer is created in the corporate IdP with department and cost center attributes, and added to the group aws-payments-developers.
  3. SCIM pushes user and groupAWSThe IdP's SCIM client creates the user and group membership in Identity Center. Users must exist there before they can sign in; SAML doesn't create them on the fly.
  4. Daily access
  5. Sign in at the access portalDeveloperThe start URL redirects to the IdP, which checks the password and MFA and sends a SAML assertion back. Identity Center's own MFA settings don't apply to IdP users.
  6. Portal shows assigned accountsAWSThe group is assigned DeveloperAccess in the non-prod accounts and ReadOnlyAccess in 121212121212. The portal session lasts 8 hours by default.
  7. Role session with session tagsAWSChoosing an account assumes the AWSReservedSSO_DeveloperAccess_... role there. Attributes for access control add CostCenter and Department as session tags, which the permission set's ABAC conditions compare with resource tags.
  8. A production change
  9. Request elevationDeveloperIn the TEAM application tile, request ProdChange on 121212121212 for one hour, with the change ticket as justification.
  10. ApproveApprover groupA member of the payments approvers group approves; the company keeps requesters out of the approver groups for their own accounts. Unanswered requests expire.
  11. Assignment granted, then removedAWSTEAM's workflow creates the account assignment for that user, waits the approved duration, then removes it. The session activity is kept for auditors.
  12. Watched throughout
  13. Events reach the security teamAWSSign-in, assignment and role events go to the organization trail in 444444444444; EventBridge rules page the team on root or break-glass sign-ins; unused access findings land in 222222222222.

Build it

Step 1

Organization instance, delegated administration and the external IdP

Only an organization instance of Identity Center gives permission sets for multi-account access (Task 4.1). The instance always resides in the management account; registering 666600006666 as delegated administrator moves most administration out of it.

AWS's delegated administration guidance says what stays in the management account:

  • Management account access. Permission sets provisioned to the management account can only be changed by an Identity Center administrator in the management account; the delegated administrator can't alter them.
  • Users, not groups, there. Assign users directly to management account permission sets; otherwise whoever controls group membership (the IdP admin included) decides who reaches it.
  • Enabling and delegating. Turning Identity Center on and registering or deregistering the delegated administrator happen in the management account.

AWS also recommends separating configuration (identity source, SCIM tokens, session timeouts) from permission set management: the company has IdentityCenterConfigAdmin and PermissionSetAdmin.

Identity source. The external IdP is connected with SAML 2.0 for sign-in and SCIM for provisioning. The SAML NameID must match the SCIM user name. SCIM access tokens expire after one year (reminders start 90 days before); an expired token stops sync silently, so joiners can't sign in and leavers keep access.

Stop identity account admins adding users to groups or creating SCIM bearer tokens (SCP from AWS's delegated administration guidance, attached to 666600006666) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "IdpOwnsGroupMembership",
      "Effect": "Deny",
      "Action": ["identitystore:CreateGroupMembership"],
      "Resource": ["*"]
    },
    {
      "Sid": "NoScimTokensFromDelegatedAdmin",
      "Effect": "Deny",
      "Action": ["sso-directory:CreateBearerToken"],
      "Resource": ["*"]
    }
  ]
}

SCIM sync is unaffected; the yearly token rotation lifts the second statement for a short, recorded window.

MFA and sessions. With an external IdP, the IdP enforces MFA (phishing-resistant factors for the AWS application); Identity Center's MFA settings apply only to its own directory and AD sources. The portal session keeps its 8-hour default (15 minutes to 90 days); role sessions (1 to 12 hours per permission set) run independently, so disabling a user doesn't end sessions already issued (Task 2.2 covers containment).

Step 2

Permission sets: managed, customer managed, inline and a boundary

A permission set holds AWS managed policies, customer managed policies referenced by name, one inline policy and an optional permissions boundary, plus the session duration. Assigning it creates a protected AWSReservedSSO_ role in each account; editing that role in IAM fails, and every change goes through Identity Center. The company's catalogue is short:

  • ReadOnlyAccess: the AWS managed ReadOnlyAccess policy, 8 hours, for every engineer in the accounts their team uses.
  • DeveloperAccess: a customer managed policy plus an ABAC inline policy (Step 4) and a boundary, 8 hours, non-prod only.
  • ProdChange: change rights in production, never assigned permanently; only TEAM assigns it, for 1 hour.
  • PlatformAdmin and IncidentResponder: broad rights for the platform and response teams, both eligible through TEAM rather than standing (the responders' use is described on the incident response page).
  • MgmtAdmin and the two admin sets from Step 1: assigned to named users.
Create DeveloperAccess with an 8-hour session (AWS CLI, identity account 666600006666, us-east-1) 
# The instance ARN comes from aws sso-admin list-instances; session duration is ISO-8601
aws sso-admin create-permission-set \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --name DeveloperAccess \
  --description "Workload developers, non-prod, scoped by CostCenter tag" \
  --session-duration PT8H \
  --tags Key=owner,Value=identity-team

Customer managed policies by name and path. A permission set only references a customer managed policy; Identity Center doesn't create it. A policy with the same name and path must already exist in every account the permission set is assigned to, or provisioning there fails (Task 4.1). A service-managed stack set deploys /company/workload-developer and /company/developer-boundary to the Workloads OU ou-abcd-33333333 first, and auto-deployment covers new accounts.

Reference the customer managed policy, set the boundary and add the inline ABAC policy (AWS CLI, identity account) 
# The policy must exist as /company/workload-developer in every assigned account
aws sso-admin attach-customer-managed-policy-reference-to-permission-set \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --permission-set-arn arn:aws:sso:::permissionSet/ssoins-1111222233334444/ps-aaaa1111bbbb2222 \
  --customer-managed-policy-reference Name=workload-developer,Path=/company/

# A boundary can be an AWS managed policy ARN or a customer managed reference; this one caps the whole role
aws sso-admin put-permissions-boundary-to-permission-set \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --permission-set-arn arn:aws:sso:::permissionSet/ssoins-1111222233334444/ps-aaaa1111bbbb2222 \
  --permissions-boundary 'CustomerManagedPolicyReference={Name=developer-boundary,Path=/company/}'

# One inline policy per permission set (up to 32,768 characters); it replaces any previous one
aws sso-admin put-inline-policy-to-permission-set \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --permission-set-arn arn:aws:sso:::permissionSet/ssoins-1111222233334444/ps-aaaa1111bbbb2222 \
  --inline-policy file://developer-abac.json

# Changes reach accounts that already have the permission set only when it is re-provisioned
aws sso-admin provision-permission-set \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --permission-set-arn arn:aws:sso:::permissionSet/ssoins-1111222233334444/ps-aaaa1111bbbb2222 \
  --target-type ALL_PROVISIONED_ACCOUNTS

The permissions boundary caps whatever inline policy the access team adds: effective permissions are the intersection with developer-boundary, which denies IAM user creation, changes to the organization trail and any action on resources under the /aws-reserved/sso.amazonaws.com/ path (Task 4.2).

Editing a permission set doesn't change roles already provisioned. create-account-assignment provisions the current version to a new account, but existing accounts keep the old policies until provision-permission-set runs, so "we fixed the permission set but users still have the old access" means it wasn't re-provisioned.

Step 3

Assign groups to accounts, OU by OU

Assignments are always group + permission set + account; the target type is AWS_ACCOUNT only, so there's no single "assign to this OU" call. An assignment pipeline in the identity account reads a mapping of group, permission set and OU, lists each OU's accounts and creates missing assignments; it also runs when Account Factory vends an account, so prod-payments gets its assignments with no manual step.

  • Non-prod OU ou-abcd-22222222: aws-payments-developers → DeveloperAccess and ReadOnlyAccess.
  • Prod OU ou-abcd-11111111: aws-payments-developers → ReadOnlyAccess; ProdChange only through TEAM.
  • Security OU ou-abcd-66666666: aws-security-analysts → read and investigation permission sets in 222222222222 and 444444444444.
  • Forensics OU ou-abcd-55555555 and every workload account: IncidentResponder eligible for aws-incident-responders through TEAM.
  • Management account 555555555555: MgmtAdmin assigned to two named users, done from the management account.
One assignment: the payments developers read-only in prod-payments (AWS CLI, identity account) 
# principal-id is the Identity Center group ID (from aws identitystore list-groups); the call is asynchronous
aws sso-admin create-account-assignment \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --target-id 121212121212 \
  --target-type AWS_ACCOUNT \
  --permission-set-arn arn:aws:sso:::permissionSet/ssoins-1111222233334444/ps-cccc3333dddd4444 \
  --principal-type GROUP \
  --principal-id PAYMENTS_DEVELOPERS_GROUP_ID

The call returns a status and request ID; the pipeline polls DescribeAccountAssignmentCreationStatus and fails on FAILED, catching a missing customer managed policy before users do.

Group assignment makes leavers safe: removal from the IdP group removes access everywhere on the next sync. Direct user assignments are only for the management account and TEAM grants.

Step 4

Attribute-based access control with attributes for access control

Job-function permission sets would multiply if each team needed its own. Instead DeveloperAccess is one permission set whose conditions compare the caller's session tags with resource tags (RBAC outside, ABAC inside, as Task 4.2 recommends).

Identity Center passes user attributes as session tags when attributes for access control is enabled. With an external IdP there are two ways: map attributes from the Identity Center identity store (which SCIM fills) in the instance configuration, or have the IdP send them in the SAML assertion as https://aws.amazon.com/SAML/Attributes/AccessControl:CostCenter. If both supply the same key, the identity store value wins. Attributes must be single-valued, and up to 50 can be configured.

Enable ABAC with two attributes from the SCIM-synced enterprise fields (AWS CLI, identity account) 
aws sso-admin create-instance-access-control-attribute-configuration \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --instance-access-control-attribute-configuration '{
    "AccessControlAttributes": [
      { "Key": "CostCenter", "Value": { "Source": ["${path:enterprise.costCenter}"] } },
      { "Key": "Department", "Value": { "Source": ["${path:enterprise.department}"] } }
    ]
  }'

Mapping from the identity store (not the assertion) keeps the values visible in Identity Center and fed by the same SCIM sync as groups. Policies use the key exactly: ${aws:PrincipalTag/CostCenter}.

developer-abac.json: start, stop and reboot only instances and read only secrets of your own cost center; resource access tags can't be changed after creation (inline policy JSON for DeveloperAccess) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OperateOwnCostCenterInstances",
      "Effect": "Allow",
      "Action": ["ec2:StartInstances", "ec2:StopInstances", "ec2:RebootInstances"],
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringEquals": { "aws:ResourceTag/CostCenter": "${aws:PrincipalTag/CostCenter}" }
      }
    },
    {
      "Sid": "ReadOwnCostCenterSecrets",
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue", "secretsmanager:DescribeSecret"],
      "Resource": "*",
      "Condition": {
        "StringEquals": { "aws:ResourceTag/CostCenter": "${aws:PrincipalTag/CostCenter}" }
      }
    },
    {
      "Sid": "NoRetaggingEc2OutsideCreation",
      "Effect": "Deny",
      "Action": ["ec2:CreateTags", "ec2:DeleteTags"],
      "Resource": "*",
      "Condition": {
        "ForAnyValue:StringEquals": { "aws:TagKeys": ["CostCenter"] },
        "Null": { "ec2:CreateAction": "true" }
      }
    },
    {
      "Sid": "NoRetaggingSecrets",
      "Effect": "Deny",
      "Action": ["secretsmanager:TagResource", "secretsmanager:UntagResource"],
      "Resource": "*",
      "Condition": {
        "ForAnyValue:StringEquals": { "aws:TagKeys": ["CostCenter"] }
      }
    }
  ]
}

Protecting the tags is the real control. The denies stop a developer re-tagging another team's resources into their cost center, while ec2:CreateAction still allows tags at launch. On the principal side, the tag comes from the identity store, which only SCIM writes (Step 1's SCP keeps identity account admins out of group membership), and Identity Center sets the session tags at sign-in; the user doesn't choose them.

A user whose costCenter is empty in the IdP has no value to send as that session tag, so every ABAC allow fails: "a new joiner gets AccessDenied on everything their team owns" is usually a missing IdP attribute, not a policy bug.

Step 5

Temporary elevated access with TEAM

Temporary elevated access (just-in-time access) means requesting, approving and tracking a permission for a specific task and time. Identity Center's guide lists validated Security Competency partner solutions; AWS also publishes TEAM (Temporary Elevated Access Management), an open-source, self-hosted solution in AWS Samples.

Where it runs. TEAM must be deployed in the Identity Center delegated administrator account, here 666600006666, which AWS advises keeping for Identity Center and TEAM only. It appears in the portal as a custom SAML 2.0 application.

Policies. TEAM admins (a named group set at deployment) define:

  • Eligibility policies: a user or group, accounts or OUs, permission sets, and whether approval is needed. aws-payments-developers are eligible for ProdChange in the Prod OU, approval required; aws-incident-responders are eligible for IncidentResponder everywhere.
  • Approval policies: which group may approve for which accounts or OUs. Each account requiring approval needs one.
  • Settings: mandatory fields (the company makes the ticket number mandatory), default timeouts and the maximum duration.

When an eligibility or approval policy names an OU, TEAM covers only the accounts directly under that OU, not those in child OUs. Naming the Workloads OU ou-abcd-33333333 wouldn't reach Prod and Non-prod, so those OUs are named explicitly.

The time-boxed flow is a set of Step Functions workflows behind a DynamoDB stream, according to TEAM's architecture documentation:

  1. RequestThe requester chooses account, permission set, start time, duration and justification.
  2. ApprovalThe approver group is notified; if nobody acts within the timeout (1 hour by default, configurable), the request expires.
  3. ScheduleAn approved request waits until its start time.
  4. GrantTEAM assigns the permission set in the account to the requester's user in Identity Center, then waits for the approved duration.
  5. RevokeTEAM removes the assignment and notifies the requester; the requester or an approver can also end it early.
  6. AuditRequesters, approvers and auditors see the request history and the session's activity.
What the grant step amounts to: a user-level assignment that exists only for the approved window (AWS CLI equivalent, identity account) 
# TEAM makes this call itself and removes the assignment when the duration ends; nobody runs it by hand
aws sso-admin create-account-assignment \
  --instance-arn arn:aws:sso:::instance/ssoins-1111222233334444 \
  --target-id 121212121212 \
  --target-type AWS_ACCOUNT \
  --permission-set-arn arn:aws:sso:::permissionSet/ssoins-1111222233334444/ps-eeee5555ffff6666 \
  --principal-type USER \
  --principal-id REQUESTER_USER_ID

ProdChange has a 1-hour session duration (PT1H), so a session started late in the window can't run on for 8 hours. The Step 3 pipeline ignores ProdChange, so it never removes or widens TEAM's grants.

TEAM's architecture uses AWS CloudTrail Lake for its session activity view. CloudTrail Lake closed to new customers on 31 May 2026, so a new deployment may not be able to create that event data store; check TEAM's current documentation. The company's audit record is the organization trail in 444444444444 and the security data lake.

Step 6

Break-glass access and root

Break-glass access is the planned way in when the normal path fails (Task 6.1); there is one layer per failure:

  • Identity Center unavailable, IdP working. AWS's emergency access configuration: an emergency operations account (131313131313) federated directly to the IdP with IAM SAML 2.0, an EmergencyOperations role there, an EmergencyAccess role trusting it in each critical account, and an IdP group aws-emergency-operations with no members. In a disruption the IdP admins add named responders, who sign in through the IdP and switch roles onward. AWS says to build it in advance and test it.
  • IdP unavailable as well. Two IAM users, ops-break-glass and a second, exist in the emergency operations account only, with FIDO2 keys and passwords held by different people, able to assume the same EmergencyAccess roles.
  • Root-only tasks. Members have no root credentials (security baseline); a 15-minute sts assume-root session from the identity account, scoped by a task policy such as S3UnlockBucketPolicy, does the job. Only one role there may call sts:AssumeRoot, reachable only through TEAM.
Trust policy of EmergencyOperations: only the corporate IdP's SAML assertions, for the sign-in endpoint (IAM role, emergency operations account 131313131313) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Federated": "arn:aws:iam::131313131313:saml-provider/CorpIdP" },
      "Action": "sts:AssumeRoleWithSAML",
      "Condition": {
        "StringEquals": { "SAML:aud": "https://us-east-1.signin.aws.amazon.com/saml" }
      }
    }
  ]
}

The emergency path is deliberately separate from Identity Center: no permission set reaches the emergency operations account, the EmergencyAccess roles are deployed by stack set with the trust pinned to arn:aws:iam::131313131313:role/EmergencyOperations.

Step 7

Monitoring, unused access and the command line

Sign-in events. Identity Center sign-ins produce CredentialChallenge (a factor was requested), CredentialVerification (it succeeded or failed; external IdP failures show type EXTERNAL_IDP) and UserAuthentication (all challenges passed), linked by an AuthWorkflowID (Task 4.1). Role sessions then appear in each account as assumed-role sessions of the AWSReservedSSO_ role. AWS changed the user identity fields in these events (fully deployed by November 2025), so check older detections. Federated users always show MFAUsed: "No", since AWS can't see the IdP's MFA.

Administrative events. Permission set changes, account assignments and the ABAC configuration are Identity Center management events in the identity account, logged by the organization trail. The security team alerts on MgmtAdmin or ProdChange assignments TEAM didn't make, and on attribute configuration changes, which alter every ABAC decision at once.

Unused access. An organization-wide unused access analyzer in the security tooling account (Access Analyzer's delegated administrator) reports unused roles, access keys, passwords and permissions over a 90-day tracking period ($0.20 per role or user per month). A finding on an AWSReservedSSO_ role means shrinking the permission set; an IAM user outside the emergency account is a leftover to delete.

The CLI. Engineers get CLI credentials with aws configure sso and aws sso login; the profile holds the start URL and role name, never keys. aws login (CLI 2.32.0 or later, with the SignInLocalDevelopmentAccess policy) gives IAM, root and directly federated users up to 12 hours of credentials from a browser sign-in, and is the only CLI path for passkey or security key MFA; the break-glass users use it, never access keys.

Two profiles from one sign-in: read-only in prod-payments, and the elevated set while a TEAM grant is active (~/.aws/config) 
[sso-session corp]

sso_registration_scopes = sso:account:access

[profile payments-readonly]
sso_session = corp

sso_role_name = ReadOnlyAccess

# Works only while the TEAM assignment exists; afterwards the role isn't offered
[profile payments-prodchange]
sso_session = corp

Workload identity is a different design. On-premises servers use IAM Roles Anywhere certificates pinned to the trust anchor and subject; EKS pods use EKS Pod Identity associations; GitHub Actions deploys with OIDC federation with a sub condition (Task 4.1).

Design decisions

Identity Center delegated to a dedicated identity account

Delegation takes daily access administration out of the management account,; an account that does nothing else keeps the blast radius small. The cost: it becomes one of the most sensitive accounts, so few people, SCPs on identity store writes and SCIM tokens.

External IdP as the single source of truth

One joiner-mover-leaver process and one MFA policy for every system. The trade-offs: the IdP's MFA policy must be right, the SCIM token is a yearly dependency, and an IdP outage blocks normal access, hence the IAM user break-glass layer.

RBAC permission sets with ABAC inside

A few job-function permission sets stay reviewable, and ABAC stops them multiplying per team. The cost is tag discipline: every resource needs a correct CostCenter at creation, and not every action supports resource tag conditions.

No standing production write access

TEAM turns production change and incident response into requested, approved, time-boxed and logged events. The costs: a self-hosted application to operate, approvers needed at night (the on-call lead approves responders; break-glass covers TEAM being down), and the CloudTrail Lake dependency.

Session lengths matched to risk

8 hours for read-only and non-prod work, 1 hour for ProdChange and PlatformAdmin: shorter sessions limit how long a stolen session works, at the price of more sign-ins. Identity Center multi-Region replication (2026; needs a multi-Region KMS key) is planned to us-west-2 for Regional resilience, alongside, not instead of, emergency access.

Alternatives

Direct SAML federation into every account

An IAM SAML provider and roles per account gives full control of trust policies, tags and paths, but every account needs its own IdP mapping and there is no organization-wide view of access. The company uses it only for emergency access.

AWS account access manager

A new IAM capability (November 2026) assigns users and groups from the Identity Center organization instance to your own IAM roles in specific accounts through entitlements, keeping custom trust policies, role tags, paths and per-user attribution through trusted identity propagation. It fits accounts whose roles differ too much for uniform permission sets and can run alongside them. The company is evaluating it.

A partner just-in-time solution or IdP privileged groups

The validated Security Competency partner products (for example Okta Access Requests or CyberArk Secure Cloud Access) are supported products with licensing cost. IdP group activation (for example Entra PIM) keeps approvals in the IdP but relies on SCIM sync. TEAM is free but is sample code the company supports itself.

Testing it

  1. Provisioning end to endCreate a test user in the IdP, add them to aws-payments-developers, and confirm ReadOnlyAccess appears in 121212121212; remove them and confirm it disappears after the next sync.
  2. ABAC with the policy simulatorSimulate the DeveloperAccess policies with the session tag CostCenter=payments against an instance tagged payments (allowed) and analytics (denied), and simulate ec2:CreateTags with the key CostCenter on an existing instance (explicit deny).
  3. Customer managed policy guardAssign DeveloperAccess to a test account without the stack set; the assignment status must be FAILED and the pipeline must stop. Deploy the policy, re-run, and confirm SUCCEEDED.
  4. Elevation lifecycleRequest ProdChange for 15 minutes, approve it as a different user, and confirm the assignment is gone afterwards. Let a second request time out; it must expire. No developer may be in the Prod approver group.
  5. Guardrails on the identity accountAs PermissionSetAdmin, try to add a user to a group and to create a SCIM token: both must fail with an explicit SCP deny. Try to change MgmtAdmin from the identity account: it must fail.
  6. Break-glass game dayTwice a year, add two responders to aws-emergency-operations, reach the forensics account through EmergencyOperations, sign in once as ops-break-glass, and confirm both pages arrive within minutes. Then rotate and empty the group.
  7. Unused access reviewCheck the unused access findings for AWSReservedSSO_ roles and IAM users each month; an IAM user outside 131313131313 or a permission set unused for 90 days is a ticket.

"Engineers need production administrator access only during approved change windows, with an audit trail and the least operational overhead" is temporary elevated access on IAM Identity Center (TEAM or a validated partner solution), not standing permission sets or shared IAM users. "One permission set must give each team access only to its own resources" is ABAC with attributes for access control and aws:PrincipalTag. "Users can't see a permission set in some accounts" is a missing customer managed policy with that name and path. "Keep console access if IAM Identity Center is disrupted" is the emergency access configuration with direct SAML federation, built and tested in advance.
