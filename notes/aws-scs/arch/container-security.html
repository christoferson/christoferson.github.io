Reference architecture

Container and EKS workload security

A container platform where only scanned, signed images from the pipeline can run, the cluster API is private and every human and pod has its own narrow identity. Pods can't borrow the node's role, read each other's secrets or talk to anything the platform team didn't allow. Each layer, from image to running pod, assumes the one before it may fail.

Scenario and requirements

The company (organization o-exampleorgid) runs its container workloads in production account 111111111111: an EKS cluster for the shop's APIs and ECS on Fargate for batch jobs. The security tooling account 222222222222 is the delegated administrator for GuardDuty and Inspector and owns the golden AMI pipeline. A review of the cluster found the usual gaps. Developers had cluster-admin through the aws-auth ConfigMap, the API endpoint was public, tags like latest were overwritten in place, pods could reach the node's instance role through IMDS, and any pod could reach any other pod.

RequirementDesign choice

How it works

The path of one release of orders-api, from commit to running pod. Steps marked AWS happen automatically.

  1. Build and release
  2. Build from a minimal basePipelineThe pipeline, running as shop-image-pipeline, builds from a base image pulled through an ECR pull-through cache. It runs as a non-root user with no secrets in its layers. The InspectorScan action fails the stage on any critical finding (Task 3.2).
  3. Push with an immutable tagPipelineThe image is pushed as shop/orders-api:2.7.0. The repository is IMMUTABLE, so nobody can later push different content under that tag. Layers are encrypted with alias/shop-containers.
  4. ECR signs the imageAWSA managed signing rule matching shop/* signs the image on push with the shop_release Signer profile. The signature, in Notation format, is stored next to the image.
  5. Inspector scans and keeps scanningAWSEnhanced scanning checks OS and language packages on push, then rescans continuously as new CVEs are published. Findings go to Security Hub CSPM in 222222222222.
  6. Deploy
  7. Deployer calls the private APIPipelineThe deploy job assumes orders-deployer and reaches the API server's private endpoint from inside the VPC. The orders-deployer access entry has AmazonEKSEditPolicy scoped to namespace orders only.
  8. Admission checksKubernetesPod Security Admission rejects a pod spec that breaks the restricted profile, for example a root user or added capabilities. The signature verification webhook rejects an image with no valid shop_release signature.
  9. Scheduled on a hardened nodeAWSThe pod lands on a node built from golden-eks-al2023-*, with IMDSv2 required and a hop limit of 1. The kubelet pulls the image by digest through the VPC endpoints.
  10. Run
  11. Pod gets its own credentialsAWSThe Pod Identity agent hands the pod temporary credentials for orders-api-pod-role, tagged with eks-cluster-name, kubernetes-namespace, kubernetes-service-account and the pod's name and UID.
  12. Secret mounted as a fileAWSThe Secrets Store CSI driver's AWS provider reads prod/orders/db with the pod's Pod Identity role and mounts it into the pod. The secret's tags must match the session's namespace and cluster tags.
  13. Traffic is fencedAWSDefault-deny network policies in orders allow only the ingress path and named dependencies. Service-to-service calls use TLS. A request to IMDS from the pod never gets a token back, because the response can't make the extra hop.
  14. Everything is watchedAWSAPI server audit logs go to CloudWatch Logs, and GuardDuty EKS Protection reads its own copy. The Runtime Monitoring agent watches processes; its findings and the crypto-mining playbook are on the detection page.

Build it

Step 1

Images, ECR repositories and scanning

Nodes and containers are hardened in different places. Node AMIs come from an EC2 Image Builder pipeline in 222222222222, which applies CIS or STIG hardening components on top of the EKS-optimized base and is shared with the workload accounts (Task 3.2, and the AWS post on hardening EKS node images). Container images start from minimal bases, cached through a pull-through cache so even public bases are stored, scanned and controlled in the company's registry. They run as non-root, with no shell unless needed.

Release repositories are fully IMMUTABLE: deployments name a version tag or a digest, never latest. The shop/web repository on Task 3.2 keeps latest movable with IMMUTABLE_WITH_EXCLUSION, but that only suits development repositories. Encryption is chosen when the repository is created: KMS with the company's own key gives a key policy and CloudTrail record that the AWS managed key can't. The key must be in the repository's Region.

Create the release repository and turn on enhanced scanning for the registry (AWS CLI, production account 111111111111) 
# immutable tags, customer managed key (same Region as the repository)
aws ecr create-repository --repository-name shop/orders-api \
  --image-tag-mutability IMMUTABLE \
  --encryption-configuration encryptionType=KMS,kmsKey=alias/shop-containers

# registry level: Inspector enhanced scanning, continuous for shop/*, on push for everything else
aws ecr put-registry-scanning-configuration --scan-type ENHANCED \
  --rules '[{"scanFrequency":"CONTINUOUS_SCAN","repositoryFilters":[{"filter":"shop/*","filterType":"WILDCARD"}]},
            {"scanFrequency":"SCAN_ON_PUSH","repositoryFilters":[{"filter":"*","filterType":"WILDCARD"}]}]'

Scanning is a registry setting: the repository-level scanOnPush setting (and put-image-scanning-configuration) is being deprecated in favour of it. With ENHANCED, Inspector scans, only SCAN_ON_PUSH and CONTINUOUS_SCAN apply, and a registry holds at most two rules. Inspector itself is turned on for every account by the delegated administrator (Task 1.1, security baseline Step 3). Continuous rescanning lasts for a set period after push or last use, which defaults to 7 days for activations from October 2026. Inspector's SBOM export lists every package for supply chain audits.

The repository policy decides who can pull and push. Only the pipeline role may push. Organization principals may pull, which covers the node role here, ECS tasks and the DR account. The data perimeter's RCP and the ECR endpoint policies (data perimeter Step 5) still apply on top.

Pull for the organization, push only for the pipeline (ECR repository policy, applied with set-repository-policy) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowPullFromOrg",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["ecr:BatchGetImage", "ecr:GetDownloadUrlForLayer", "ecr:BatchCheckLayerAvailability"],
      "Condition": { "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" } }
    },
    {
      "Sid": "DenyPushExceptPipeline",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["ecr:PutImage", "ecr:InitiateLayerUpload", "ecr:UploadLayerPart", "ecr:CompleteLayerUpload"],
      "Condition": {
        "ArnNotEquals": { "aws:PrincipalArn": "arn:aws:iam::111111111111:role/shop-image-pipeline" }
      }
    }
  ]
}

Every caller also needs ecr:GetAuthorizationToken in its IAM policy (Task 4.2). IAM Access Analyzer flags the repository if a statement ever grants access outside the organization. A blanket push deny can also catch features that write to the repository on your behalf, such as replication or managed signing, so the staging tests in Testing it confirm that signatures still appear before the deny reaches production.

Step 2

Sign on push, verify at admission

Scanning says an image has no known CVEs. A signature says it came from the company's pipeline and hasn't changed since. ECR managed signing (November 2025) moves signing into the registry. A registry-level rule names an AWS Signer signing profile and a repository filter, and ECR signs every matching image on push. Signer manages the keys and certificates, and the signature is stored in the repository in Notation format. The signature validity defaults to 135 months.

Sign every image pushed to shop/* repositories, and let the pipeline role sign (signing configuration JSON and IAM statement) 
# signing-config.json, applied with: aws ecr put-signing-configuration --signing-configuration file://signing-config.json
{
  "rules": [
    {
      "signingProfileArn": "arn:aws:signer:us-east-1:111111111111:/signing-profiles/shop_release",
      "repositoryFilters": [{ "filter": "shop/*", "filterType": "WILDCARD_MATCH" }]
    }
  ]
}

# statement in shop-image-pipeline's policy: signing uses the pusher's credentials
{
  "Sid": "SignOnPush",
  "Effect": "Allow",
  "Action": "signer:SignPayload",
  "Resource": "arn:aws:signer:us-east-1:111111111111:/signing-profiles/shop_release"
}

Signing uses the credentials of whoever pushed, so the push fails to sign if that principal lacks signer:SignPayload. Together with the push-only-for-the-pipeline policy from Step 1, only the pipeline can produce a signed shop/ image.

Verification happens in the cluster. An admission controller such as Kyverno or Ratify, with the AWS Signer plugin for Notation, checks each pod's images against a trust policy that trusts only the shop_release profile, and rejects unsigned or foreign images before the pod is created. On ECS, the same AWS post uses a service lifecycle hook at PRE_SCALE_UP that calls a Lambda function. The function verifies the task definition's images with the Notation CLI and can block or only log on failure.

The 2023 AWS post on securing the image build pipeline with AWS Signer shows signing with the Notation CLI inside the pipeline, plus the EKS verification setup. It predates ECR managed signing: its verification half still applies, but signing no longer needs a step in the build. Admission webhooks see only new pods, so images already running when the policy goes live are verified by redeploying them.

Step 3

Cluster access, private endpoint, encryption and audit logs

Access entries replace the aws-auth ConfigMap, which the EKS best practices guide now calls deprecated. An access entry maps one IAM principal to the cluster through the EKS API, with calls CloudTrail records, instead of a ConfigMap where one typo can lock everyone out. Access policies are EKS-managed permission sets, such as AmazonEKSClusterAdminPolicy (like cluster-admin), AmazonEKSEditPolicy and AmazonEKSViewPolicy. Each is scoped to the whole cluster or to named namespaces, and Kubernetes RBAC through --kubernetes-groups still works alongside them.

The authentication mode moves from CONFIG_MAP through API_AND_CONFIG_MAP (both sources, access entries win) to API once the old mappings are migrated. New clusters are created with bootstrapClusterCreatorAdminPermissions=false in --access-config, so the creator doesn't keep a hidden permanent admin binding.

Private endpoint, audit logging, the customer managed key and API-only authentication (AWS CLI, production account) 
# API server reachable only from inside the cluster VPC (and connected networks)
aws eks update-cluster-config --name shop-prod \
  --resources-vpc-config endpointPublicAccess=false,endpointPrivateAccess=true

# control plane logs to CloudWatch Logs: audit and authenticator matter most for security
aws eks update-cluster-config --name shop-prod \
  --logging '{"clusterLogging":[{"types":["api","audit","authenticator"],"enabled":true}]}'

# bring our own KMS key as the key encryption key for Kubernetes API data
aws eks associate-encryption-config --cluster-name shop-prod \
  --encryption-config '[{"resources":["secrets"],"provider":{"keyArn":"arn:aws:kms:us-east-1:111111111111:alias/shop-containers"}}]'

# after migrating aws-auth entries: access entries only
aws eks update-cluster-config --name shop-prod --access-config authenticationMode=API
Platform admins for the whole cluster, the orders team only in its namespace (AWS CLI) 
aws eks create-access-entry --cluster-name shop-prod \
  --principal-arn arn:aws:iam::111111111111:role/eks-platform-admin
aws eks associate-access-policy --cluster-name shop-prod \
  --principal-arn arn:aws:iam::111111111111:role/eks-platform-admin \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster

aws eks create-access-entry --cluster-name shop-prod \
  --principal-arn arn:aws:iam::111111111111:role/orders-deployer
aws eks associate-access-policy --cluster-name shop-prod \
  --principal-arn arn:aws:iam::111111111111:role/orders-deployer \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy \
  --access-scope type=namespace,namespaces=orders

Access entries take IAM roles or users, never STS session ARNs, and an entry stops working if its role is deleted and re-created with the same ARN. Node roles use the EC2_LINUX type, which can't carry access policies. Humans reach these roles through IAM Identity Center permission sets (workforce identity).

Envelope encryption. Clusters on Kubernetes 1.28 or later already envelope-encrypt all Kubernetes API data with KMS v2 and an AWS owned key. A customer managed key adds a key policy, CloudTrail records and the ability to revoke. The resources field is deprecated and has no effect on what is encrypted, but if set it must be ["secrets"]. The key must be symmetric and in the cluster's Region. The risk runs the other way too: if the key is disabled, the cluster is put in a degraded state and can't start its API server without a cached key, and the key should be re-enabled within 30 days. A deleted key, or revoked grants, leave the cluster unrecoverable. So the key's policy keeps kms:DisableKey and kms:ScheduleKeyDeletion with the key administrators only, behind an alarm (KMS at scale Steps 2 and 6).

Audit logs. GuardDuty EKS Protection reads the audit log from its own independent stream and needs no control plane logging. The company still exports audit and authenticator logs to CloudWatch, because investigators need their own copy and GuardDuty doesn't make it available. Telemetry enablement rules turn this logging on for every new cluster, and the logs feed Security Lake's EKS audit source (security data lake Step 2, Task 1.2).

Step 4

Hardened nodes: golden AMIs, IMDSv2 with hop limit 1, no SSH

Managed node groups launch from the shop-prod-nodes launch template. It names the current golden-eks-al2023-* AMI, has no key pair and no SSH security group rule, and sets the metadata options below. Administrative access, when it is needed at all, goes through Session Manager with logged sessions (Task 3.2). Nodes are replaced rather than patched in place: a new AMI version rolls through the node group.

Node launch template: IMDSv2 only, and a hop limit of 1 so pods can't reach the node's credentials (AWS CLI) 
aws ec2 create-launch-template --launch-template-name shop-prod-nodes \
  --version-description "golden-eks-al2023, IMDSv2, hop limit 1" \
  --launch-template-data '{
    "ImageId": "GOLDEN_EKS_AMI_ID",
    "MetadataOptions": {
      "HttpEndpoint": "enabled",
      "HttpTokens": "required",
      "HttpPutResponseHopLimit": 1
    }
  }'

Why 1 and not 2: a pod's request to IMDS crosses one extra network hop, so with a limit of 1 the IMDSv2 token response never reaches the pod. Pods using Pod Identity or IRSA get their credentials elsewhere and never need IMDS. Without the block, a pod with Pod Identity can still fall back to the node role, which can pull every image and manage network interfaces. Keep HttpEndpoint enabled: node agents such as the termination handler need IMDS. Task 3.2 sets the account default hop limit to 2 for general EC2 hosts running containers; this launch template overrides it for EKS nodes. The SCP with ec2:MetadataHttpTokens from the same task stops anyone launching a node without IMDSv2.

EKS Auto Mode changes who does this step. Auto Mode nodes run Bottlerocket-based AMIs that AWS treats as immutable, with SELinux in enforcing mode, a read-only root file system and no SSH or SSM access. They are replaced after at most 21 days (you can shorten this), and AWS patches them. The Pod Identity agent and network policy enforcement are built in. The customer still owns the containers, the VPC and cluster configuration, which is the shared responsibility split described in the Auto Mode security whitepaper.

Step 5

Pod Identity, least privilege and secrets

Each application gets its own service account and its own role. EKS Pod Identity associates the orders-api service account with orders-api-pod-role, whose trust policy names pods.eks.amazonaws.com with sts:AssumeRole and sts:TagSession (Task 3.2). Unlike IRSA, there is no per-cluster OIDC provider, the same role works in any cluster, and every session carries six tags: eks-cluster-arn, eks-cluster-name, kubernetes-namespace, kubernetes-service-account, kubernetes-pod-name and kubernetes-pod-uid. The tags are transitive, so they follow the session into role chaining.

The association, and a permissions policy that reads only secrets tagged for this cluster and namespace (AWS CLI and identity policy JSON) 
aws eks create-pod-identity-association --cluster-name shop-prod \
  --namespace orders --service-account orders-api \
  --role-arn arn:aws:iam::111111111111:role/orders-api-pod-role

# orders-api-pod-role permissions (secret prod/orders/db is tagged kubernetes-namespace=orders, eks-cluster-name=shop-prod)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOwnNamespaceSecrets",
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue", "secretsmanager:DescribeSecret"],
      "Resource": "arn:aws:secretsmanager:us-east-1:111111111111:secret:prod/orders/*",
      "Condition": {
        "StringEquals": {
          "secretsmanager:ResourceTag/kubernetes-namespace": "${aws:PrincipalTag/kubernetes-namespace}",
          "secretsmanager:ResourceTag/eks-cluster-name": "${aws:PrincipalTag/eks-cluster-name}"
        }
      }
    }
  ]
}

Creating an association requires iam:PassRole on the role, so the orders team's deployer can't attach the platform's roles to its pods (Task 4.2). The association's optional --policy is a session policy that narrows a shared role per association. It requires --disable-session-tags, so ABAC on session tags and session policies are alternatives, not a combination. For access in another account, --target-role-arn makes EKS chain into a role there, and the association's generated external ID goes in that role's trust policy to prevent a confused deputy. The secret's customer managed key must also allow kms:Decrypt for the pod role (KMS at scale Step 4).

Mount the database secret into the orders pods with Pod Identity (Secrets Store CSI driver, AWS provider) 
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: orders-db
  namespace: orders
spec:
  provider: aws
  parameters:
    objects: |
      - objectName: "prod/orders/db"        # secret name or ARN in Secrets Manager
        objectType: "secretsmanager"
    usePodIdentity: "true"                 # use the pod's Pod Identity role, not IRSA

The AWS Secrets and Configuration Provider (ASCP) mounts the secret as a file in the pod's volume, so it isn't in the image, the manifest or etcd. Rotation (Task 5.3) changes the value in Secrets Manager, and the application must reread the file or fall back on an authentication error. The AWS Workload Credentials Provider is the alternative for apps that prefer a local HTTP call to a file.

Pod Identity is not supported on Fargate or Windows nodes; there, IRSA is still the answer (Task 3.2). On ECS, the equivalent split is the task role for the application's own calls, and the task execution role for the agent's image pulls, log writes and secret injection. Answers that give the execution role the app's S3 permissions mix them up.

Step 6

Pod Security Admission, network policies and security groups for pods

Pod Security Admission is built into Kubernetes and enforces the Pod Security Standards per namespace through labels. restricted builds on baseline, which blocks host namespaces, hostPath, host ports and added capabilities. It also requires a non-root user, allowPrivilegeEscalation: false, dropping ALL capabilities and a RuntimeDefault or Localhost seccomp profile. All three modes are set, because enforce alone rejects the pods but lets the Deployment through silently.

Restricted profile for the orders namespace, in all three modes (Kubernetes Namespace) 
apiVersion: v1
kind: Namespace
metadata:
  name: orders
  labels:
    pod-security.kubernetes.io/enforce: restricted   # reject violating pods
    pod-security.kubernetes.io/audit: restricted     # annotate the audit log event
    pod-security.kubernetes.io/warn: restricted      # warn the client (kubectl, the deploy job)

System namespaces whose agents need privileges stay at privileged or baseline, deployable only by the platform team. A read-only root file system is set in each pod's securityContext. Rules beyond PSA's three levels, such as "images only from our registry", need a policy-as-code engine such as Kyverno or OPA Gatekeeper, the same webhook layer that verifies signatures in Step 2.

Network policies. By default every pod can reach every other pod. The Amazon VPC CNI enforces standard Kubernetes NetworkPolicy (version 1.21.0 or later also supports cluster-wide ClusterNetworkPolicy with Admin and Baseline tiers) on EC2 Linux nodes, but not on Fargate or Windows. The orders namespace starts from deny-all, then allows only what it needs.

Default deny for the namespace, then ingress from the ingress controller and DNS out (Kubernetes NetworkPolicy) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: orders
spec:
  podSelector: {}            # every pod in the namespace
  policyTypes:
    - Ingress
    - Egress                 # no rules listed: nothing in, nothing out
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-api-allow
  namespace: orders
spec:
  podSelector:
    matchLabels:
      app: orders-api
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress   # the load balancer controller's targets live here
      ports:
        - protocol: TCP
          port: 8443
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
    - ports:                 # HTTPS to AWS APIs and the database; destinations are policed by the egress firewall and data perimeter
        - protocol: TCP
          port: 443

The quarantine policy ir-deny-all from Task 2.2 is pre-staged in orders too, so responders only need to label a pod. Enforcement is reliable for pods that a controller such as a Deployment manages; AWS warns it may not be for standalone pods. Pods that still use the instance role would need an explicit allow to IMDS, which this design doesn't have.

Security groups for pods give a pod its own EC2 security group through a SecurityGroupPolicy, so only the orders pods, not every pod on the node, reach the Aurora cluster. Network policies handle traffic inside the cluster and pod security groups handle AWS resources. Pod security groups need trunking-capable Nitro instance types (no t family) and Linux nodes; Auto Mode has its own variant. TLS between services comes from a service mesh with mutual TLS or cert-manager with AWS Private CA issuing short-lived pod certificates, because network policies control flows but don't encrypt (Task 5.1).

Design decisions

Prevent in admission, detect at runtime

Every control on this page acts before or as a pod starts: the pipeline gate, immutable tags, the signature check, PSA and IAM scoping. Runtime detection is the backstop for what prevention can't see, such as a zero-day in a signed image. EKS Protection watches the audit log, for example anonymous access or a pod created with a sensitive host mount. Runtime Monitoring's agent (the aws-guardduty-agent add-on, managed for the organization through EKS_ADDON_MANAGEMENT as on the security baseline) watches processes. The response playbooks live on the detection page and the evidence steps on the forensics page. Inspector findings that matter most are the ones on images in use, which enhanced scanning reports for EKS and ECS.

Pod Identity over IRSA, and IRSA where it must stay

Pod Identity needs no OIDC provider per cluster or trust policy edits for blue/green upgrades, its session tags let one policy pattern serve every namespace, and it doesn't use the account's STS quota. IRSA remains for Fargate pods and for workloads that call sts:AssumeRoleWithWebIdentity directly into another account. With IRSA, the trust policy must pin the :sub claim to the namespace and service account (Task 4.2).

Namespace as the tenancy boundary, one cluster

Teams share shop-prod, fenced by namespace at every layer: access policy scope, PSA labels, network policies, session tags and tagged secrets. That is soft multi-tenancy. Untrusted code or a compliance boundary gets its own cluster or account, because a container escape on a shared node crosses every namespace.

Customer managed key for the cluster, with tight key administration

The AWS owned key is free. The customer managed key costs a dollar a month plus requests (KMS v2 caching keeps them low) and gives CloudTrail records and a kill switch. The kill switch is also the risk, so key administration is separate from cluster administration. The key isn't shared with other clusters, because AWS warns that a disabled key shared by many clusters widens the impact. It is shared with this platform's ECR repositories, so a disable would also stop image pulls, one more reason for the alarm.

A private endpoint, and how people still reach it

Engineers reach the private endpoint over the transit gateway, and the pipeline's runners sit in the VPC. A public endpoint limited by publicAccessCidrs is the weaker half-step: a stolen credential from an allowed IP still reaches the API.

Alternatives

ECS on Fargate instead of EKS

Fargate gives each task (or EKS pod) its own isolated compute environment with no shared node, and it can't run privileged containers or use host networking. That removes the node hardening, IMDS hop limit and pod escape concerns at once. The trade-offs: no network policies (use security groups per task or pod), no DaemonSets (GuardDuty's agent runs as a managed sidecar on ECS Fargate), and on EKS no Pod Identity. Service-to-service TLS on ECS is Service Connect TLS (Task 5.1).

EKS Auto Mode

Auto Mode hands AWS the node layer of Step 4: immutable Bottlerocket nodes, no shell access, regular replacement and built-in network policy enforcement and Pod Identity. It suits teams who don't want to run an AMI pipeline. The cost is less control: you don't edit the default node pools, and custom node-level tooling has to run as DaemonSets.

Kubernetes Secrets with envelope encryption

Native Secrets are envelope-encrypted in etcd, but anyone with get secrets in the namespace reads them in plain text, and rotation is manual. Secrets Manager through ASCP keeps the source of truth outside the cluster, with IAM, rotation and CloudTrail.

Testing it

  1. The supply chain holdsPush a different image under an existing tag of shop/orders-api: ECR rejects it. Push from a developer role: the repository policy denies it. Push an image with a known critical CVE through the pipeline: the InspectorScan action fails the stage. Check that a pipeline-built image shows a signature in the console.
  2. Admission rejects bad podsIn a staging copy of the namespace, apply a Deployment that runs as root, and another using an unsigned image from a scratch repository. Both Deployments are created but their pods aren't. The client sees the PSA warning, the audit log carries the annotation and the webhook logs the signature failure. Labelling a namespace that already has pods prints warnings for existing violators without evicting them, which is the safe way to roll out enforce.
  3. Access is as narrow as designedAs orders-deployer, try to list pods in kube-system or read secrets in another namespace: denied. Confirm no principal outside the platform team has a cluster-scoped access entry. From outside the VPC, the API endpoint doesn't answer at all.
  4. Pods can't borrow the node roleFrom a test pod, request an IMDSv2 token: the call times out because of the hop limit. Then call aws sts get-caller-identity from the orders pod: it returns orders-api-pod-role, not the node role. Check that credential refresh through the Pod Identity agent still works with default-deny egress in place.
  5. Secrets and tags line upAssociate a test service account in another namespace with the same role and try to mount prod/orders/db: the tag condition denies GetSecretValue. The IAM policy simulator can evaluate the policy with the session tag values set as context keys.
  6. Network policy and detectionFrom a pod in another namespace, connect to orders-api on 8443: blocked. Generate GuardDuty sample findings for EKS and runtime finding types to exercise the routing from the detection page. Run a game day that labels a pod status=quarantine and confirms it is cut off.
  7. Continuous checksSecurity Hub CSPM controls for EKS and ECR, and AWS Config rules, track drift such as a public endpoint, missing logging or mutable tags. Inspector's coverage information shows any repository that isn't being scanned.

"Pods must use only their own IAM permissions, not the worker node's" is EKS Pod Identity (or IRSA) plus IMDSv2 with a hop limit of 1 on the nodes. "Grant a team access to one namespace without editing the aws-auth ConfigMap" is an access entry with a namespace-scoped access policy. "Ensure only images built by our pipeline run in the cluster" is signing (ECR managed signing with AWS Signer) plus an admission controller that verifies signatures, not scanning alone. "Detect newly published CVEs in images already deployed" is Inspector enhanced scanning with continuous rescans. Basic scanning on push is the distractor.
