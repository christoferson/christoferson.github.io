Reference architecture

Secure CI/CD and governance as code

One delivery path for application code and infrastructure, where nothing reaches production without passing the same checks and nobody holds a long-lived key. Pull requests are scanned before merge, templates are checked in the pipeline and again inside CloudFormation, a human approves the change set, and the deployment role can't grant more than its boundary allows. After deployment, the same rules keep running as detective controls and leave the evidence trail the auditors ask for.

Scenario and requirements

The company (organization o-exampleorgid) has its multi-account baseline in place and its containers hardened (container security). The weak point is now delivery. Some teams deploy CloudFormation from laptops as administrators, one GitHub workflow holds an IAM user's access key, and the last audit found an unencrypted production bucket from a template nobody reviewed. The security team wants one checked path for code and infrastructure.

RequirementDesign choice
No long-lived credentials anywhere in the pipelineGitHub OIDC federation with a pinned sub claim, one role per stage, cross-account roles assumed by the pipeline
Vulnerable code, dependencies and secrets are caught before mergeAmazon Inspector code security on push and pull request, Amazon Q Developer reviews in the IDE, the InspectorScan action as a pipeline gate
Insecure templates can't deploy, whatever tool deploys themcfn-lint and Guard in the pipeline; the managed Guard hook and Control Tower proactive controls inside CloudFormation

Drift and non-compliance are found, and auditors get evidenceDrift detection, organization conformance packs, Security Hub CSPM standards, Config history and CloudTrail

  • Repository example-org/shop-infra for the CloudFormation and CDK code, next to the application repository example-org/shop.

  • Policies and stacks: the permissions boundary shop-workload-boundary, the production stack shop-web-prod with change set release, and the stack set guard-hook-baseline.

How it works

The path of one infrastructure change, from pull request to the auditor's evidence. Steps marked AWS happen automatically.

  1. Review
  2. Developer opens a pull requestDeveloperA change to example-org/shop-infra adds an S3 bucket and an IAM role, already reviewed by Amazon Q Developer in the IDE.
  3. Inspector scans the pull requestAWSInspector code security runs SAST, SCA and IaC rules on the PULL_REQUEST event and comments fixes for critical and high findings, including hardcoded secrets.
  4. Checks run with a short-lived roleGitHub ActionsThe workflow exchanges its OIDC token for the read-only github-pr-checks role and runs cfn-lint, Guard and Access Analyzer checks. Branch protection requires them and a reviewer before merge.
  5. Build and verify
  6. Merge starts the releaseGitHub ActionsOn main, the workflow assumes github-release (trusted only for this repository's main branch) and starts the pipeline in 151515151515.
  7. Pipeline gates the sourceAWSInspectorScan fails the stage above its thresholds; the build reruns cfn-lint, Guard with its unit tests, and cdk-nag for CDK apps.
  8. Deploy
  9. Change set created in productionAWSThe pipeline assumes pipeline-deploy in 111111111111, which creates change set release on shop-web-prod with cfn-exec-shop as the CloudFormation role.
  10. Hooks evaluate the changeAWSThe Guard hook Private::Guard::CompanyBaseline and Control Tower proactive controls check the change inside CloudFormation, so a bypassed pipeline still meets them.
  11. A release manager approvesApproverThe manual approval action notifies release-approvals; the approver reviews the change set, especially replacements.
  12. Change set executesAWSCloudFormation acts as cfn-exec-shop, which can create the role only with shop-workload-boundary attached.
  13. Govern
  14. Detective controls keep checkingAWSConformance packs and Security Hub CSPM controls evaluate the new resources, findings go to the central routing, and drift detection runs on a schedule.
  15. Evidence accumulatesAWSCloudTrail, Config history and the pipeline's approval history form the audit trail.

Build it

Step 1

Pipeline identities without keys

The pipelines live in a dedicated deployment account, apart from production and from the security tooling account that watches it, with one role per stage. GitHub Actions exchanges a per-job OIDC token through sts:AssumeRoleWithWebIdentity for short-lived credentials (Task 4.1); the IAM user and its key are deleted.

Only the main branch of the infrastructure repository can start a release (IAM role trust policy for github-release, deployment account 151515151515) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Federated": "arn:aws:iam::151515151515:oidc-provider/token.actions.githubusercontent.com" },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:example-org/shop-infra:ref:refs/heads/main"
        }
      }
    }
  ]
}

The sub claim is the security boundary: without it, any GitHub organization's workflow could assume the role. IAM rejects a new or changed trust policy for GitHub's provider whose sub condition is missing or only a wildcard. github-pr-checks uses StringLike with repo:example-org/shop-infra:* (any branch, as in AWS's documentation) and gets only read and validation permissions, because pull request branches are untrusted. Workload accounts never trust GitHub directly.

In each workload account, the cross-account role pipeline-deploy trusts only the shop-pipeline-service role in 151515151515, not the whole account. It may call CloudFormation on the company's stacks, pass cfn-exec-shop and read the artifacts. CodePipeline requires the CloudFormation role to be in the same account as the action role. The artifact bucket uses a customer managed KMS key shared with the workload accounts, named by key ID or ARN, because an alias resolves only in the key's own account.

The permissions boundary. A deployment role that can create roles can make itself an administrator, so cfn-exec-shop may create roles only with shop-workload-boundary and can't remove or edit it, the IAM delegation pattern (Task 4.2).

Part of the cfn-exec-shop permissions policy: roles only with the boundary, and the boundary can't be removed or edited (identity policy JSON, workload account 111111111111) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CreateRolesOnlyWithBoundary",
      "Effect": "Allow",
      "Action": ["iam:CreateRole", "iam:PutRolePolicy", "iam:AttachRolePolicy", "iam:DetachRolePolicy", "iam:DeleteRolePolicy", "iam:PutRolePermissionsBoundary"],
      "Resource": "arn:aws:iam::111111111111:role/shop/*",
      "Condition": {
        "StringEquals": { "iam:PermissionsBoundary": "arn:aws:iam::111111111111:policy/shop-workload-boundary" }
      }
    },
    {
      "Sid": "NoBoundaryRemoval",
      "Effect": "Deny",
      "Action": "iam:DeleteRolePermissionsBoundary",
      "Resource": "*"
    },
    {
      "Sid": "NoBoundaryPolicyEdit",
      "Effect": "Deny",
      "Action": ["iam:CreatePolicyVersion", "iam:DeletePolicy", "iam:DeletePolicyVersion", "iam:SetDefaultPolicyVersion"],
      "Resource": "arn:aws:iam::111111111111:policy/shop-workload-boundary"
    }
  ]
}

Stack-created roles sit under the /shop/ path, away from the platform's roles. The boundary and both deployment roles come from a stack set (Step 6), never from the pipeline they constrain. For CDK, cdk bootstrap runs with --trust 151515151515 and a scoped --cloudformation-execution-policies instead of the default AdministratorAccess (Task 6.2).

A CloudFormation service role is used by anyone who can update the stack, even without iam:PassRole. If developers can still call UpdateStack on shop-web-prod directly, they deploy with cfn-exec-shop's permissions and skip the approval. Step 4's SCP keeps stack changes in production limited to the pipeline.

Step 2

Code security on every pull request

Scanning happens at three points (Task 3.2). In the IDE, Amazon Q Developer code reviews flag security issues, secrets, IaC problems and vulnerable dependencies. In the repository, Amazon Inspector code security runs SAST on first-party code, SCA on dependencies and IaC rules on CloudFormation, Terraform and CDK; it connects to GitHub through the Amazon Inspector app and to GitLab Self Managed with a personal access token. In the pipeline, the InspectorScan action can stop a release.

The exam guide names Amazon CodeGuru Security for pipeline scanning. It is no longer in the AWS documentation, and AWS points to Amazon Inspector code security and Amazon Q Developer code reviews instead. Inspector code security is the current answer for scanning repositories in the pipeline.

Scan every repository on push and pull request, and weekly (AWS CLI, Inspector delegated administrator 222222222222) 
aws inspector2 create-code-security-scan-configuration \
  --name org-default \
  --level ORGANIZATION \
  --configuration '{"ruleSetCategories": ["SAST", "SCA", "IAC"],
                    "continuousIntegrationScanConfiguration": {"supportedEvents": ["PUSH", "PULL_REQUEST"]},
                    "periodicScanConfiguration": {"frequency": "WEEKLY"}}' \
  --scope-settings projectSelectionScope=ALL

projectSelectionScope=ALL makes this the default configuration for every existing and future project; without it, a general configuration must be associated with projects one by one. frequency takes WEEKLY, MONTHLY or NEVER; the schedule catches new CVEs in repositories nobody has pushed to. Findings name the file, line and commit and flow through EventBridge like other Inspector findings.

Secret scanning. Inspector's SAST rules and Q Developer report hardcoded secrets. A found secret is exposed: rotate it and move it to Secrets Manager, because deleting the line leaves it in the history (Task 5.3).

The pipeline gate scans the exact source about to deploy, which also covers AWS CodeCommit repositories (CodeCommit returned to full general availability in November 2025).

Fail the release if the source has any critical or high finding (CodePipeline action, pipeline structure YAML) 
name: ScanSource
actionTypeId:
  category: Invoke
  owner: AWS
  provider: InspectorScan
  version: '1'
runOrder: 1
configuration:
  InspectorRunMode: SourceCodeScan
  CriticalThreshold: '0'
  HighThreshold: '0'
inputArtifacts:
  - name: SourceArtifact
outputArtifacts:
  - name: SourceSbom
region: us-east-1

The action runs on managed CodeBuild compute (billed as CodeBuild), outputs an SBOM and needs inspector-scan:ScanSbom in the service role. Images use ECRImageScan mode (container page).

Step 3

Template checks in the pipeline: cfn-lint, Guard and cdk-nag

Policy as code checks the company's own rules: every bucket encrypted, every role with a boundary, nothing public. The build runs three tools (Task 6.2). cfn-lint catches template errors and unsafe patterns, such as W1011 (a secret passed as a parameter instead of a dynamic reference). CloudFormation Guard evaluates the company rules. cdk-nag applies rule packs such as AWS Solutions or NIST 800-53 to CDK apps and records each suppression in metadata.

Every IAM role in a template must carry a permissions boundary (Guard rule, iam_boundary.guard, in the shared rules repository) 
let iam_roles = Resources.*[ Type == 'AWS::IAM::Role' ]

rule IAM_ROLE_HAS_PERMISSIONS_BOUNDARY when %iam_roles !empty {
  %iam_roles.Properties.PermissionsBoundary exists
  <<
    Violation: Every IAM role must have a permissions boundary.
    Fix: Set PermissionsBoundary to the shop-workload-boundary policy ARN
  >>
}
Run the rules and their unit tests in the build (shell, CodeBuild) 
# Unit-test the rules against known good and bad snippets first, so a broken rule can't pass everything
cfn-guard test -r rules/iam_boundary.guard -t rules/iam_boundary_tests.yaml

# Then validate the template against the rule (repeat for each rule file)
cfn-guard validate -d templates/shop-web.yaml -r rules/iam_boundary.guard

A rule whose resource type isn't in the template is skipped, not failed, which is why the rules have unit tests. The rules live in a security-owned repository and are published to platform-guard-rules-222222222222, so the pipeline and the Step 4 hook use the same files. The Guard Rules Registry adds ready-made rules for CIS, NIST and PCI DSS, named after the matching Config managed rules. IAM Access Analyzer validate-policy and custom policy checks review the policies in templates (Task 4.2).

Terraform. Guard also reads Terraform plan JSON. State, which often holds secrets in plain text, goes in an S3 backend with SSE-KMS, versioning, locking and a restrictive bucket policy; applies assume a role in each target account.

Step 4

Hooks that every deployment meets

Pipeline checks protect only pipeline deployments. CloudFormation hooks run inside CloudFormation before a resource, stack, change set or Cloud Control API operation, so a template deployed from a laptop meets the same rules. The managed Guard hook runs Guard rules from S3 with no code. Hooks are activated per account and Region, so a stack set deploys them.

The Guard hook as a resource, deployed to every workload account by the guard-hook-baseline stack set (CloudFormation YAML) 
Resources:
  GuardHookRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: guard-hook-execution
      AssumeRolePolicyDocument:
        Version: '2012-10-17'
        Statement:
          - Effect: Allow
            Principal:
              Service:
                - hooks.cloudformation.amazonaws.com
            Action: 'sts:AssumeRole'
      Policies:
        - PolicyName: read-guard-rules
          PolicyDocument:
            Version: '2012-10-17'
            Statement:
              - Effect: Allow
                Action:
                  - s3:GetObject
                  - s3:GetObjectVersion
                  - s3:ListBucket
                Resource:
                  - arn:aws:s3:::platform-guard-rules-222222222222
                  - arn:aws:s3:::platform-guard-rules-222222222222/*
              - Effect: Allow
                Action:
                  - s3:PutObject
                Resource:
                  - arn:aws:s3:::platform-guard-reports-222222222222/*
  GuardHook:
    Type: AWS::CloudFormation::GuardHook
    Properties:
      Alias: Private::Guard::CompanyBaseline
      ExecutionRole: !GetAtt GuardHookRole.Arn
      # start with WARN in the Policy Staging OU, then FAIL everywhere
      FailureMode: FAIL
      HookStatus: ENABLED
      LogBucket: platform-guard-reports-222222222222
      RuleLocation:
        Uri: s3://platform-guard-rules-222222222222/baseline.guard
      TargetOperations:
        - STACK
        - RESOURCE
        - CHANGE_SET
      TargetFilters:
        Actions:
          - CREATE
          - UPDATE

The rules and reports buckets in the security tooling account grant guard-hook-execution in organization accounts read and write respectively. Rules are downloaded on every invocation, so the bucket is versioned and only the security release job writes to it. Each invocation has a 30-second timeout. StackFilters can exclude stacks, but every exclusion is a way around the rules.

Create the hook stack set and deploy it to the workload OUs, now and for every new account (AWS CLI, security tooling account as StackSets delegated administrator) 
aws cloudformation create-stack-set --call-as DELEGATED_ADMIN \
  --stack-set-name guard-hook-baseline \
  --template-url https://s3.us-east-1.amazonaws.com/platform-templates-222222222222/guard-hook-baseline.yaml \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false \
  --managed-execution Active=true \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation create-stack-instances --call-as DELEGATED_ADMIN \
  --stack-set-name guard-hook-baseline \
  --deployment-targets OrganizationalUnitIds=ou-abcd-11111111,ou-abcd-22222222 \
  --regions us-east-1 us-west-2 \
  --operation-preferences MaxConcurrentPercentage=25,FailureTolerancePercentage=10,RegionConcurrencyType=PARALLEL

Control Tower proactive controls are hooks that Control Tower manages, enabled per OU (enable-control is on the baseline page). A blocked deployment shows AWS::ControlTower::Hook in the stack events, and the console's hook invocation summary names the failed control, such as CT.S3.PR.1, and the fix. Company-specific rules, such as the boundary rule, stay in the company's own hook, which runs alongside them (Task 6.1).

Only the pipeline and the platform team may change stacks or hook settings in production (SCP, attached to the Prod OU ou-abcd-11111111) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "StackChangesOnlyThroughPipeline",
      "Effect": "Deny",
      "Action": [
        "cloudformation:CreateStack",
        "cloudformation:UpdateStack",
        "cloudformation:DeleteStack",
        "cloudformation:CreateChangeSet",
        "cloudformation:ExecuteChangeSet",
        "cloudformation:SetTypeConfiguration",
        "cloudformation:ActivateType"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": [
            "arn:aws:iam::*:role/pipeline-deploy",
            "arn:aws:iam::*:role/platform-admin",
            "arn:aws:iam::*:role/SCLaunchRole-*",
            "arn:aws:iam::*:role/AWSControlTowerExecution"
          ]
        }
      }
    }
  ]
}

The SCLaunchRole-* exception lets Service Catalog products (Step 6) provision through CloudFormation. StackSets and Control Tower deploy through their own roles in each account. Test the SCP in the Policy Staging OU (101010101010) and confirm that stack sets, Control Tower, Service Catalog and the pipeline still work. Hooks see only CloudFormation and Cloud Control deployments; a console click or direct API call meets SCPs and declarative policies (prevent) and Config (detect).

Step 5

Change sets, approval and stack protection

Production never gets a direct stack update. The release stage creates a change set showing what will be added, modified or replaced, waits for a person, then executes it.

Release stage: create the change set in production, wait for approval, execute (CodePipeline stage, pipeline structure YAML, deployment account 151515151515) 
name: ReleaseProd
actions:
  - name: CreateChangeSet
    actionTypeId:
      category: Deploy
      owner: AWS
      provider: CloudFormation
      version: '1'
    runOrder: 1
    # the pipeline assumes this role in the production account
    roleArn: arn:aws:iam::111111111111:role/pipeline-deploy
    configuration:
      ActionMode: CHANGE_SET_REPLACE
      StackName: shop-web-prod
      ChangeSetName: release
      TemplatePath: BuildArtifact::shop-web.yaml
      TemplateConfiguration: BuildArtifact::prod-config.json
      Capabilities: CAPABILITY_NAMED_IAM
      # CloudFormation acts as this role; it must be in the same account as the action role
      RoleArn: arn:aws:iam::111111111111:role/cfn-exec-shop
    inputArtifacts:
      - name: BuildArtifact
  - name: ApproveRelease
    actionTypeId:
      category: Approval
      owner: AWS
      provider: Manual
      version: '1'
    runOrder: 2
    configuration:
      NotificationArn: arn:aws:sns:us-east-1:151515151515:release-approvals
      CustomData: Review change set release on shop-web-prod, especially any Replacement entries.
  - name: ExecuteChangeSet
    actionTypeId:
      category: Deploy
      owner: AWS
      provider: CloudFormation
      version: '1'
    runOrder: 3
    roleArn: arn:aws:iam::111111111111:role/pipeline-deploy
    configuration:
      ActionMode: CHANGE_SET_EXECUTE
      StackName: shop-web-prod
      ChangeSetName: release

RoleArn isn't applied at execution; the change set keeps the role it was created with. The TemplateConfiguration file carries parameters, stack tags and a stack policy. Stack tags propagate to the resources, which guarantees example:cost-center and example:environment. Approval rights are granted on this action only, through a release manager permission set, so developers can't approve their own release (workforce identity).

Stack protection. The stack policy denies Update:Replace and Update:Delete on the database; once set, a stack policy protects everything it doesn't allow and can't be deleted (Task 6.2). Termination protection stops stack deletion.

Protect the stack from deletion, and check it for drift on a schedule (AWS CLI, production account) 
aws cloudformation update-termination-protection \
  --stack-name shop-web-prod \
  --enable-termination-protection

# Returns a StackDriftDetectionId; describe-stack-resource-drifts then lists what changed
aws cloudformation detect-stack-drift --stack-name shop-web-prod

Drift detection checks only properties the template sets, skips nested stacks (check each one itself) and never fixes. create-change-set --deployment-mode REVERT_DRIFT creates a drift-aware change set that compares actual state, last deployment and template, and goes through the same approval. CloudTrail shows who made the manual change.

Step 6

Deploying at scale and self-service

The account baseline (pipeline-deploy, cfn-exec-shop, the boundary, the hook, Config rules) doesn't belong in an application pipeline. Service-managed StackSets from the security tooling account deploy it, and auto-deployment covers each account as it joins a target OU, so a new account such as prod-payments (121212121212) can receive releases on day one. The security-baseline stack set (Task 6.2) carries the roles and boundary; guard-hook-baseline carries the hook.

  • Operation preferences limit a bad change: 25 percent of accounts at a time, stopping once failures pass the per-Region tolerance. Policy Staging gets changes first.
  • Limits: no management account, no nested stacks, macros or transforms; auto-deployment ignores account filters and parameter overrides, so the baseline avoids per-account overrides.

Self-service: teams that need a standard resource without a template use AWS Service Catalog products that already pass the Guard rules. A launch constraint provisions with a platform role, so teams need only Service Catalog permissions (Task 6.2).

The encrypted bucket product launches with the platform role in whichever account it is shared to (AWS CLI, Service Catalog administrator) 
aws servicecatalog create-constraint \
  --portfolio-id port-y3fnkesxxxxx \
  --product-id prod-cfrfxmraxxxxx \
  --type LAUNCH \
  --parameters '{"LocalRoleName": "SCLaunchRole-EncryptedBucket"}'

LocalRoleName works everywhere because the baseline stack set creates the role in every account. TagOptions add required tags, and the Guard hook still checks each launch.

Tags. Tag policies standardize keys and values, and an SCP with aws:RequestTag and aws:TagKeys denies creation without them (Task 6.2). Pipeline stack tags satisfy it automatically.

Step 7

Governance after deployment and the evidence trail

Prevention misses paths nobody thought of, and rules change after resources exist, so the same intent runs as detective controls. The security tooling account, as Config delegated administrator, deploys organization conformance packs through a service-linked role, even where member policies deny config:PutConfigRule (Task 6.3). org-cis-baseline is already on the baseline; the payments audit adds the PCI DSS sample pack.

Deploy the PCI DSS operational best practices pack to every account except the sandbox (AWS CLI, security tooling account 222222222222) 
aws configservice put-organization-conformance-pack \
  --organization-conformance-pack-name org-pci-dss \
  --template-s3-uri s3://awsconfigconforms-templates-222222222222/operational-best-practices-pci-dss-4.yaml \
  --delivery-s3-bucket awsconfigconforms-results-222222222222 \
  --excluded-accounts 333333333333

The delivery bucket name must start with awsconfigconforms, and remediation goes in the pack template, because the API can't attach it to service-linked rules. A CUSTOM_POLICY rule lets the Step 3 boundary rule run as a detective check, on the guard-2.x.x runtime, so test it separately.

  • Security Hub CSPM standards measure posture: FSBP everywhere through central configuration, PCI DSS v4.0.1 for payments. Disable controls that don't apply instead of suppressing findings, which inflates the score (Task 6.3).
  • Firewall Manager keeps the WAF baseline on every production ALB and API stage, including new ones (Task 6.2); it needs continuous Config recording.
  • Remediation and alerts follow the detection and response page.

Evidence for the auditor. What changed: CloudTrail records every CreateChangeSet and ExecuteChangeSet with its role session, and Config history shows each resource before and after. Who approved: the pipeline's approval history. Compliant over time: conformance pack history, advanced query exports, and Security Hub CSPM findings copied to S3 (archived findings last 30 days). AWS's own attestations come from AWS Artifact.

AWS Audit Manager is in maintenance mode: from 30 April 2026 it can't be set up in new accounts and gets no new frameworks. Its evidence finder runs on CloudTrail Lake, which closed to new customers on 31 May 2026. AWS recommends Config conformance packs, with Security Hub CSPM, Control Tower or partner tools for the rest.

Design decisions

A deployment account, separate from security tooling

Pipelines write to production; security tooling must not be changeable by those it watches. Combining them in 222222222222 would make the pipeline a path into the security account. A compromised deployment account yields deployment roles, limited by the SCP and approval, but no evidence. The cost is one more account and cross-account plumbing (key, bucket policy, a role per account), delivered by stack sets.

Check in the pipeline and in CloudFormation

The pipeline gives fast feedback before deployment; the hook enforces whatever path someone took. The same Guard rules serve both, proactive controls cover common AWS rules, and conformance packs catch what arrived outside CloudFormation.

Permissions boundary rather than a fixed role list

Templates legitimately create roles for functions and tasks; forbidding IAM would bring back tickets. A boundary allows any role inside a known ceiling, checked by Guard before deployment and by the IAM condition at the API. The ceiling needs upkeep, and it doesn't limit what a resource policy grants directly to a role session (Task 4.2).

Manual approval only where it adds review

Non-prod deploys skip approval so the gate doesn't become a rubber stamp. Production approvers review the change set, which shows what will actually happen, giving the auditor separation of duties.

Alternatives

GitHub Actions deploying directly

The workflow can assume a role in each account through OIDC and run the change set itself, with GitHub environments as the approval. Simpler, but the approval trail lives in GitHub, every account trusts GitHub, and each sub condition must be exact. AWS recommends deployment branch protection on environments used in OIDC policies.

Terraform with HCP Terraform

HCP Terraform federates through OIDC, and IAM requires app.terraform.io:sub in the trust policy. Hooks never see Terraform deployments, so prevention rests on SCPs and plan checks, with conformance packs as the safety net.

Lambda hooks and Config proactive evaluation

A Lambda hook runs your function for checks Guard can't express, at the cost of code. Config proactive evaluation (start-resource-evaluation) checks a configuration before it exists but never blocks, so it isn't an enforcement point.

Testing it

  1. Identity is pinnedFrom a feature branch, assuming github-release fails on sub. A trust policy without sub is rejected by IAM. validate-policy shows no MISSING_GITHUB_REPO_CONDITION_KEY, and no pipeline principal has access keys.
  2. Code findings block the mergeA pull request with a known critical CVE dependency and a fake credential gets Inspector comments, and fails InspectorScan if merged anyway.
  3. The rules are rightcfn-guard test with passing and failing fixtures catches a rule that silently skips everything; a role without a boundary fails cfn-guard validate.
  4. The hook catches a bypassIn 101010101010, deploy the bad template from the CLI. In WARN it deploys with a warning in the invocation summary; in FAIL it stops before creation. A public bucket fails with AWS::ControlTower::Hook.
  5. No privilege escalationThe policy simulator allows cfn-exec-shop iam:CreateRole only with the iam:PermissionsBoundary context key set, and denies iam:DeleteRolePermissionsBoundary. A developer's UpdateStack on shop-web-prod hits the SCP.
  6. Approval and driftA release that replaces a resource waits at ApproveRelease showing the replacement. A hand-edited security group shows as drifted and is reverted with a drift-aware change set.
  7. Detective controls and evidenceA resource created outside CloudFormation turns a conformance pack rule NON_COMPLIANT and alerts the team. Then pull what an auditor would ask for: the release's CloudTrail events, the bucket's Config history and the approval record.

"Prevent any team from deploying a non-compliant resource with CloudFormation, even outside the pipeline" is a CloudFormation Guard hook (or Control Tower proactive controls), not a pipeline step, and not a Config rule, which only detects afterwards. "A GitHub workflow needs to deploy without stored credentials" is OIDC federation with a trust policy that pins the sub claim. "Scan application code for vulnerabilities in the pipeline", where the options name CodeGuru Security, tests static analysis. The current service is Amazon Inspector code security or the InspectorScan action. "Developers must create IAM roles in templates without being able to escalate" is a permissions boundary required by condition. "Every new account must get the baseline automatically" is service-managed StackSets with auto-deployment.
