Reference architecture

Encryption and key management at scale

One key management design for every account: customer managed keys per workload, classification and environment, key policies that keep the people who manage keys apart from the code that uses them, guardrails that make a deleted key almost impossible, and evidence that every bucket, volume and secret is encrypted with the key it should be.

Scenario and requirements

The company (organization o-exampleorgid) runs its web app, EKS containers, S3 data platform and GenAI assistant in production account 111111111111, in us-east-1 with us-west-2 as the disaster recovery Region. The analytics account 777777777777 reads the data platform, and the DR account 888888888888 receives replicated data and backup copies. An audit found hand-made keys whose administrators could also delete them, data under AWS managed keys that can't be shared with other accounts, and no record of which key protected what.

  • Aliases: alias/prod/data-platform/confidential for the data platform key, alias/prod/web-app/internal for the web app's EBS and RDS key (placeholder WEB_APP_KEY_ID) and alias/prod/secrets/confidential for production secrets (placeholder SECRETS_KEY_ID).

How it works

Three paths show the design at work: a cross-account read of SSE-KMS data, an encrypted EBS volume that relies on a grant, and an attempt to delete a key. Steps marked AWS happen automatically.

  1. The analytics account reads the data platform
  2. ETL job calls S3Workloadanalytics-etl in 777777777777 calls s3:GetObject on shop-data-111111111111; bucket and IAM policies allow it (and the data perimeter applies).
  3. S3 asks KMS for the data keyAWSS3 calls Decrypt on the caller's behalf with encryption context aws:s3:arn = the bucket ARN (a Bucket Key is in use), so kms:ViaService is s3.us-east-1.amazonaws.com.
  4. Both accounts must allowAWSThe key policy names analytics-etl for kms:Decrypt through S3 for this bucket only, and the role's IAM policy allows the key ARN. If either is missing, S3 returns AccessDenied.
  5. Logged with its contextAWSThe organization trail records the Decrypt with the encryption context, showing which bucket the key was used for.
  6. A web server boots from an encrypted volume
  7. Auto Scaling launches an instanceWorkloadEBS encryption by default is on in us-east-1, with alias/prod/web-app/internal as the account's default key, so the new root volume is encrypted with it.
  8. EC2 creates a grantAWSEC2 calls CreateGrant on the caller's behalf, allowed only when kms:GrantIsForAWSResource is true. The grant lets EC2 decrypt the volume's data key at each attach.
  9. Someone tries to delete a key
  10. ScheduleKeyDeletionAdministratorAn administrator tries to schedule deletion of the data platform key. The SCP denies it: only key-custodian may, and never with fewer than 30 days.
  11. Alerts and findingsAWSIf the custodian does schedule it, EventBridge pages the security team, an alarm fires on any use during the waiting period, and Security Hub CSPM raises KMS.3 (Critical).

Build it

Step 1

Key inventory, aliases and tags

Which kind of key. An AWS managed key (alias aws/<service>) is visible and logged, and rotates yearly, but you can't change its policy. That policy allows only principals in the same account, through that service (the aws/ebs policy combines kms:CallerAccount with kms:ViaService), so data under it can't be shared with another account: snapshots for the DR or forensics accounts fail under aws/ebs, and S3 objects under aws/s3 can't be shared. RCPs don't restrict AWS managed keys either. The standard is therefore a customer managed key for all company data (Task 5.2).

How many keys. Following AWS's guidance, there are separate keys per data classification, application and environment. The production inventory (non-prod accounts mirror it with nonprod in the alias):

Key (alias)Account, owner and what it protects
alias/prod/data-platform/confidential111111111111, data platform team: shop-data-111111111111, its Glue catalog and Athena results
alias/prod/web-app/internal111111111111, web team: EBS volumes, the Aurora cluster and their snapshots
alias/prod/secrets/confidential111111111111, platform team: Secrets Manager secrets for every production workload
Client-side multi-Region key (mrk-)111111111111, orders team: order attributes encrypted by the application before they're stored, readable in us-west-2 (Step 5)
DR and backup keys888888888888, platform team: replica bucket and backup vault copies in us-west-2
Log and evidence keys444444444444, 222222222222 and 666666666666, security team (security data lake and forensics pages)

The platform pipeline creates every key from one module, never in the console, so the Step 2 policy and the tags are always there. The same alias name exists in each account and Region, and moving an alias to a new key is how keys that can't rotate automatically are replaced. Cross-account callers must use the key ARN, because an alias is looked up in the caller's own account.

Create the data platform key with its policy and tags, then name it (AWS CLI, production account 111111111111, run by the pipeline as kms-key-admin) 
aws kms create-key \
  --description "Data platform, confidential, prod" \
  --policy file://data-platform-key-policy.json \
  --tags TagKey=data-classification,TagValue=confidential TagKey=environment,TagValue=prod TagKey=workload,TagValue=data-platform TagKey=owner,TagValue=data-platform-team

# The returned key ID is 1234abcd-12ab-34cd-56ef-1234567890ab
aws kms create-alias \
  --alias-name alias/prod/data-platform/confidential \
  --target-key-id 1234abcd-12ab-34cd-56ef-1234567890ab

Tags and aliases are not just labels. KMS supports attribute-based access control, so a policy can allow use of keys by tag or alias, and AWS warns that principals who can change tags or aliases can change who can use a key. In this design only kms-key-admin may tag keys or change aliases.

Step 2

The key policy template: administrators, users and services apart

A key policy grants nothing to the account automatically; the Enable IAM User Permissions statement is what lets IAM policies count at all (Task 4.2). The console's default policy adds key administrators, who manage but can't use the key, and key users. The template keeps that split and tightens it three ways:

  • Administrators can't delete. The console's administrator statement includes kms:ScheduleKeyDeletion and kms:CancelKeyDeletion unless you clear "allow key administrators to delete this key". The template gives them to key-custodian only.
  • Use only through a service. kms:ViaService limits orders-app to requests S3 makes on its behalf, so it can't call kms:Decrypt directly on a stolen ciphertext.
  • Use only for its data. kms:EncryptionContext:aws:s3:arn ties the key to one bucket. With S3 Bucket Keys the context is the bucket ARN, not the object ARN.
Data platform key policy: account statement, administrators without deletion, the custodian, and in-account and cross-account users through S3 for one bucket (KMS key policy, data-platform-key-policy.json) 
{
  "Version": "2012-10-17",
  "Id": "data-platform-key-policy",
  "Statement": [
    {
      "Sid": "Enable IAM User Permissions",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111111111111:root" },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "Allow access for Key Administrators",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111111111111:role/kms-key-admin" },
      "Action": [
        "kms:Create*", "kms:Describe*", "kms:Enable*", "kms:List*", "kms:Put*",
        "kms:Update*", "kms:Revoke*", "kms:Disable*", "kms:Get*", "kms:Delete*",
        "kms:TagResource", "kms:UntagResource", "kms:RotateKeyOnDemand"
      ],
      "Resource": "*"
    },
    {
      "Sid": "AllowKeyCustodianDeletion",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111111111111:role/key-custodian" },
      "Action": ["kms:ScheduleKeyDeletion", "kms:CancelKeyDeletion", "kms:DescribeKey"],
      "Resource": "*"
    },
    {
      "Sid": "AllowOrdersAppThroughS3ForThisBucket",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111111111111:role/orders-app" },
      "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "s3.us-east-1.amazonaws.com",
          "kms:EncryptionContext:aws:s3:arn": "arn:aws:s3:::shop-data-111111111111"
        }
      }
    },
    {
      "Sid": "AllowAnalyticsReadThroughS3ForThisBucket",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::777777777777:role/analytics-etl" },
      "Action": "kms:Decrypt",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "s3.us-east-1.amazonaws.com",
          "kms:EncryptionContext:aws:s3:arn": "arn:aws:s3:::shop-data-111111111111"
        }
      }
    }
  ]
}

S3 needs kms:GenerateDataKey to write and kms:Decrypt to read (both for multipart uploads), so those are the only user actions. Administrators can still change the policy and create grants, and so could give themselves use of the key, as AWS warns. That's why kms:PutKeyPolicy is limited to the pipeline's kms-key-admin role by SCP (Step 6).

The account statement stays: without it, deleting the named roles leaves the key unmanageable until AWS Support helps. The cost is that an IAM policy in 111111111111 could grant direct kms:Decrypt. IAM changes go only through the pipeline, and Security Hub CSPM KMS.1 and KMS.2 flag IAM policies allowing decryption on all keys.

kms:ViaService answers "the role may use the key only through S3 (or EBS, RDS, Secrets Manager)". kms:CallerAccount together with "Principal": {"AWS": "*"} answers "every principal in this account". Encryption context conditions answer "only for this bucket, this secret, this tenant".

Step 3

Grants and cross-account use

Grants are the third way, after key policies and IAM policies, to allow use of a key, and suit temporary or service-driven permissions: create, use, retire, with no policy edit. Services such as EBS and Redshift create grants on the caller's behalf, which is what the Allow attachment of persistent resources statement allows: kms:CreateGrant, kms:ListGrants and kms:RevokeGrant only when kms:GrantIsForAWSResource is true, so a role can't hand itself a grant directly.

Grants also cover one-off jobs. Objects written before the key standard (under aws/s3) are re-encrypted by an S3 Batch Operations copy in place running as s3-batch-reencrypt, which gets a grant for the bucket's encryption context instead of a key policy entry.

A temporary grant for the re-encryption job, limited to the bucket's encryption context and retirable by the key administrator (AWS CLI, production account 111111111111) 
aws kms create-grant \
  --key-id arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab \
  --grantee-principal arn:aws:iam::111111111111:role/s3-batch-reencrypt \
  --operations Decrypt GenerateDataKey \
  --constraints '{"EncryptionContextSubset": {"aws:s3:arn": "arn:aws:s3:::shop-data-111111111111"}}' \
  --retiring-principal arn:aws:iam::111111111111:role/kms-key-admin \
  --name s3-batch-reencrypt-2026-11

The command returns a GrantId and a GrantToken. Grants are eventually consistent (usually under five minutes), so a job starting at once passes the token, and --name stops retries creating duplicates. When the job ends, the grant is retired, or revoked by its GrantId.

Cross-account use needs both sides: the key policy names the other account or role (Step 2), and an IAM policy there allows the key ARN. Only cryptographic, grant and describe operations work across accounts, never ScheduleKeyDeletion or PutKeyPolicy, so a compromised analytics account can't delete or rewrite the key.

The analytics side: allow decryption with the production data platform key only (IAM policy on analytics-etl, account 777777777777) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowUseOfProdDataKey",
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab"
    }
  ]
}

The forensics sharing key applies the same pattern to snapshots (incident response and forensics).

Step 4

Default encryption for EBS and S3, and keys for secrets

EBS. Encryption by default is a per-Region account setting: new volumes are always encrypted, existing ones are unchanged, and instance types without encryption support can't launch. The AWS SRA code example ec2_default_ebs_encryption turns it on in every account and governed Region with the default key; the company then sets its customer managed key as the default, so snapshots and AMIs can be shared.

Encrypt every new volume, with the web app key as the default (AWS CLI, run per account and Region by StackSets) 
aws ec2 enable-ebs-encryption-by-default --region us-east-1

aws ec2 modify-ebs-default-kms-key-id --region us-east-1 \
  --kms-key-id alias/prod/web-app/internal

The key must be symmetric, and if it's disabled or deleted, instances fail to launch. EC2 checks it asynchronously, so a wrong alias appears to succeed and fails later. Its policy copies the shape of the aws/ebs policy:

Any principal in the production account may use the web app key, but only through EC2 (EBS) and RDS (KMS key policy statement for WEB_APP_KEY_ID) 
{
  "Sid": "AllowUseThroughEc2AndRdsForThisAccount",
  "Effect": "Allow",
  "Principal": { "AWS": "*" },
  "Action": ["kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*", "kms:GenerateDataKey*", "kms:CreateGrant", "kms:DescribeKey"],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:CallerAccount": "111111111111",
      "kms:ViaService": ["ec2.us-east-1.amazonaws.com", "rds.us-east-1.amazonaws.com"]
    }
  }
}

S3. The data platform default is SSE-KMS with its key (by ARN, in the bucket's Region), a Bucket Key, and SSE-C blocked; the bucket policy refuses uploads naming any other key.

Default SSE-KMS with the data platform key and a Bucket Key, SSE-C blocked (AWS CLI, production account) 
aws s3api put-bucket-encryption --bucket shop-data-111111111111 \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyID": "arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab"
      },
      "BucketKeyEnabled": true,
      "BlockedEncryptionTypes": { "EncryptionType": ["SSE-C"] }
    }]
  }'
Refuse uploads that ask for any other KMS key (S3 bucket policy statement) 
{
  "Sid": "RequireDataPlatformKey",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::shop-data-111111111111/*",
  "Condition": {
    "StringNotEqualsIfExists": {
      "s3:x-amz-server-side-encryption-aws-kms-key-id": "arn:aws:kms:us-east-1:111111111111:key/1234abcd-12ab-34cd-56ef-1234567890ab"
    }
  }
}

This is envelope encryption: S3 asks KMS for a data key, encrypts the object with the plaintext copy, discards it and stores the encrypted copy with the object. A Bucket Key adds a short-lived bucket-level key from which object data keys are derived, cutting KMS requests by up to 99 percent, which matters for millions of small objects. The trade-offs: the encryption context (and CloudTrail) shows the bucket, not the object, and DSSE-KMS can't use Bucket Keys. IfExists lets header-less uploads through to the bucket default. Changing the default doesn't re-encrypt existing objects; that's the Step 3 batch job.

Secrets. Secrets Manager encrypts each secret version with its own data key. Production secrets use alias/prod/secrets/confidential, not aws/secretsmanager, which can't be used across accounts or narrowed. Requests carry the encryption context SecretARN and SecretVersionId, so the policy limits each workload to its own secrets:

The orders application may decrypt only production secrets under prod/orders/, only through Secrets Manager (KMS key policy statement for SECRETS_KEY_ID) 
{
  "Sid": "AllowOrdersSecretsThroughSecretsManager",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111111111111:role/orders-app" },
  "Action": "kms:Decrypt",
  "Resource": "*",
  "Condition": {
    "StringEquals": { "kms:ViaService": "secretsmanager.us-east-1.amazonaws.com" },
    "StringLike": { "kms:EncryptionContext:SecretARN": "arn:aws:secretsmanager:us-east-1:111111111111:secret:prod/orders/*" }
  }
}

Secret rotation itself is on Task 5.3; the rotation function also needs kms:GenerateDataKey through Secrets Manager to write new versions. When a secret's key changes, Secrets Manager re-encrypts the current, pending and previous versions and keeps older versions readable with the old key, so the old key stays until nothing depends on it.

Certificates are the other key material. Internal TLS uses ACM private certificates from AWS Private CA subordinate CAs, which renew themselves on load balancers; CA keys stay in Private CA's HSMs, outside the KMS inventory (Task 5.3, Task 5.1).

Step 5

Rotation, multi-Region keys and imported material

Rotation. Automatic rotation creates new material every 90 to 2,560 days (365 by default); on-demand rotation does it at once, up to 25 times per key. Key ID, aliases and policy stay the same, and old material is kept so existing ciphertext still decrypts. Rotation does not re-encrypt data, doesn't help if a data key was exposed, and doesn't apply to asymmetric, HMAC or custom key store keys, which are replaced by a new key and an alias move.

Rotate the confidential key every 180 days, and rotate now after a suspected exposure of key administrator credentials (AWS CLI, production account) 
aws kms enable-key-rotation \
  --key-id 1234abcd-12ab-34cd-56ef-1234567890ab \
  --rotation-period-in-days 180

aws kms rotate-key-on-demand \
  --key-id 1234abcd-12ab-34cd-56ef-1234567890ab

kms:RotationPeriodInDays can limit the periods teams choose, and each rotation sends a KMS CMK Rotation event to EventBridge as audit evidence.

Multi-Region keys. AWS says single-Region keys fit most needs, and the design uses them for every service-side copy: S3 replication to shop-data-dr-888888888888 re-encrypts under the DR account's own key 5678efgh-56ef-78gh-90ij-5678efgh90ij, since most services treat multi-Region keys as single-Region keys anyway, and backup and snapshot copies also re-encrypt in the destination Region. A multi-Region key earns its place only where the application encrypts data that is copied between Regions: the orders team's client-side encrypted attributes, which the DR copy decrypts in us-west-2 without a call to us-east-1.

Create the multi-Region primary and replicate it to the DR Region with its own policy (AWS CLI, production account 111111111111) 
aws kms create-key --multi-region \
  --description "Orders client-side encryption, confidential, prod" \
  --policy file://orders-cse-key-policy.json \
  --tags TagKey=data-classification,TagValue=confidential TagKey=environment,TagValue=prod

aws kms replicate-key \
  --key-id arn:aws:kms:us-east-1:111111111111:key/mrk-1234abcd12ab34cd56ef1234567890ab \
  --replica-region us-west-2 \
  --policy file://orders-cse-replica-policy.json \
  --tags TagKey=data-classification,TagValue=confidential TagKey=environment,TagValue=prod

The replica is in the same account: ReplicateKey can't replicate to another account. When the DR runbook runs the application in 888888888888, the replica's own policy (not copied from the primary; without --policy it gets the default policy) names the DR role, whose IAM policy allows the replica ARN. Material, key ID and rotation are shared; policy, grants, aliases, tags and enabled state are set per Region. Each replica is billed as a key.

Elsewhere multi-Region keys are avoided: the same material in several Regions can conflict with data residency, single-Region keys can't be converted, and interoperable keys widen the impact of a policy mistake. An SCP lets only kms-key-admin create them (Step 6).

Imported material and custom key stores. A payments key in prod-payments (121212121212) must use material from the company's HSM, so it has origin EXTERNAL and material imported with an expiry at most 365 days ahead (commands on Task 5.3). The company must keep every version of the material; if any is lost, the key is unusable. Expired material is deleted and the key returns to PendingImport until re-imported, so a scheduled check reads ValidTo from DescribeKey 30 days ahead, with the KMS Imported Key Material Expiration event as a backstop. For the one market whose regulator requires material outside AWS, an external key store (XKS) serves only that market's low-volume EBS and RDS keys; a CloudHSM key store would fit a single-tenant HSM requirement inside AWS. Both support only symmetric keys, have no SLA and can't hold multi-Region keys.

Step 6

Guardrails, alarms and evidence

Key deletion is irreversible: a deleted symmetric key can't be recreated, and everything under it is lost, including Object Lock-protected logs and backups. Deletion waits 7 to 30 days (30 by default) in PendingDeletion, when it can be cancelled. The SCP below, tested in Policy Staging ou-abcd-44444444 and then attached to r-abcd, forces the full 30 days, lets only key-custodian start it, and keeps key policies and special key types with the pipeline.

Organization guardrails for KMS keys (SCP, attached to the root r-abcd) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectKmsKeysFromDeletion",
      "Effect": "Deny",
      "Action": ["kms:ScheduleKeyDeletion", "kms:DeleteImportedKeyMaterial"],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/key-custodian" }
      }
    },
    {
      "Sid": "RequireFullWaitingPeriod",
      "Effect": "Deny",
      "Action": "kms:ScheduleKeyDeletion",
      "Resource": "*",
      "Condition": {
        "NumericLessThan": { "kms:ScheduleKeyDeletionPendingWindowInDays": "30" }
      }
    },
    {
      "Sid": "OnlyPipelineChangesKeyPolicies",
      "Effect": "Deny",
      "Action": "kms:PutKeyPolicy",
      "Resource": "*",
      "Condition": {
        "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/kms-key-admin" }
      }
    },
    {
      "Sid": "OnlyPipelineCreatesMultiRegionKeys",
      "Effect": "Deny",
      "Action": "kms:CreateKey",
      "Resource": "*",
      "Condition": {
        "Bool": { "kms:MultiRegion": "true" },
        "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/kms-key-admin" }
      }
    },
    {
      "Sid": "OnlyPipelineCreatesCustomKeyStoreKeys",
      "Effect": "Deny",
      "Action": "kms:CreateKey",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "kms:KeyOrigin": ["EXTERNAL_KEY_STORE", "AWS_CLOUDHSM"] },
        "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/kms-key-admin" }
      }
    }
  ]
}

kms:ScheduleKeyDeletionPendingWindowInDays limits the waiting period a caller may request; kms:KeyOrigin and kms:MultiRegion apply to CreateKey. The custodian role is assumable only through the break-glass process. SCPs don't cover the management account, which holds no workload keys, and the security data lake adds a stricter SCP for the log keys. AWS's unused-keys blog adds a key policy layer: deny deletion and disabling of keys used recently, with kms:TrailingDaysWithoutKeyUsage.

Page the security team when anyone schedules deletion, disables a key, changes a key policy or deletes imported material (EventBridge event pattern, deployed to every account and Region) 
{
  "source": ["aws.kms"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventSource": ["kms.amazonaws.com"],
    "eventName": ["ScheduleKeyDeletion", "DisableKey", "PutKeyPolicy", "DeleteImportedKeyMaterial"]
  }
}

These are write management events, which a rule in the default ENABLED state matches while a trail is logging. A second rule forwards KMS's own KMS CMK Deletion and KMS Imported Key Material Expiration events; both target the security tooling account 222222222222 (threat detection and response).

During a waiting period, the question is whether anything still uses the key. KMS documents a metric filter on the trail's log group for requests failing with "is pending deletion", alarmed at 1 or more:

Metric filter pattern for use of a key pending deletion (CloudWatch Logs, organization trail log group) 
{ $.eventSource = kms* && $.errorMessage = "* is pending deletion."}

Before any deletion the runbook disables the key and watches for failures, checks Last used (GetKeyLastUsage, tracked since April 2026 in most Regions), and confirms no EBS volumes or snapshots use the key, since volumes can depend on a key without calling KMS for long periods.

Evidence. Config rules in the organization conformance pack (Task 6.3): ec2-ebs-encryption-by-default, encrypted-volumes with kmsId, s3-default-encryption-kms with kmsKeyArns and cmk-backing-key-rotation-enabled. Security Hub CSPM adds:

  • KMS.1, KMS.2 (Medium): IAM policies must not allow kms:Decrypt or kms:ReEncryptFrom on all keys (conditions are ignored).
  • KMS.3 (Critical): keys not scheduled for deletion.
  • KMS.4 (Medium): rotation enabled, a CIS item.
  • KMS.5 (Critical): no public key policy; it also fails if Config can't read the policy.

Behind it all, CloudTrail logs every GenerateDataKey, Decrypt and CreateGrant with the caller, the calling service (invokedBy) and the encryption context (security data lake).

Design decisions

Workload-owned keys, central templates

AWS describes decentralized ownership as the usual default, with centralized ownership for organizations that need strict central compliance oversight, and a hybrid in between. The company runs the hybrid. Keys live in the account of the data they protect, so the account boundary limits who can reach them, and applications in different accounts get separate keys, as the AWS guidance recommends. The security team owns the template, the SCP and the evidence. A central key account was rejected: every use would become cross-account, needing a key policy statement and an IAM policy for each consumer, and a mistake in one key policy would expose many workloads (Task 6.1).

Key granularity: classification, workload, environment

Per classification, confidential data gets narrower users and shorter rotation; per workload, one team's administrators stay out of another's data; per environment, no non-prod role can decrypt production data. Going finer (per bucket or tenant) adds monthly key charges and policies to review; an encryption context condition per tenant on one key gives most of the benefit.

Separation of duties inside the key policy

Administrators manage but can't use, users use but can't manage, the custodian alone deletes, and services get grants only for AWS resources. Because administrators can rewrite the policy, PutKeyPolicy is pipeline-only and reviewed as code, and EventBridge reports any other change (Task 4.2).

Rotation period by classification

Confidential keys rotate every 180 days and others yearly. Rotation is cheap and invisible to applications, but it isn't a response to a leaked data key. That needs re-encryption of the affected data under a new key, which is why the Batch Operations grant pattern exists.

Bucket Keys on by default

Bucket Keys cut KMS request costs for the data platform and log buckets, at the price of coarser logging and policies that name the bucket ARN. Data needing per-object KMS audit goes in a separate bucket without them.

Alternatives

AWS managed keys everywhere

No key policies to write and yearly rotation for free. But they can't be shared across accounts, used for cross-account replication or backup copies, or restricted beyond the account, and RCPs don't restrict them. They fit data that never leaves one account, which in this design is almost nothing.

One central key account

All keys in one security-owned account, with key policies granting each workload account. It gives one place to audit and a strict separation between key owners and data owners, which some regulated organizations require. The costs are cross-account permissions for every consumer, a large blast radius for policy errors, and one team on the critical path for every new workload.

CloudHSM directly, or custom key stores

CloudHSM gives single-tenant HSMs managed outside IAM, for PKCS #11, TLS offload or Oracle TDE; custom key stores put KMS keys on HSMs you control. AWS recommends them only when regulation requires, preferring CloudHSM key stores to external ones, and with XKS the company owns availability and latency (Task 5.2, Task 5.3).

Multi-Region keys for all DR data

Simpler on paper, but S3 replication re-encrypts under the destination key anyway, the replica can't live in the DR account, and the material spreads further. Single-Region keys in 888888888888 keep DR copies independent of production, as ransomware resilience needs.

Testing it

  1. Check the policies before they deployThe pipeline runs Access Analyzer policy validation and a custom policy check that fails the build if a key policy grants new access compared to the approved template.
  2. Prove the conditions workAs orders-app, call aws kms decrypt directly on an object's ciphertext: expect AccessDeniedException, because the request isn't through S3. As analytics-etl, read an SSE-KMS object from a second test bucket encrypted with the same key: expect a denial, because the encryption context names a different bucket.
  3. Try to delete a keyIn the test account 101010101010 in Policy Staging, try ScheduleKeyDeletion as kms-key-admin (expect an explicit SCP deny), as key-custodian with 7 days (deny) and with 30 days (allowed). The EventBridge rule must page within minutes and KMS.3 must appear. Then encrypt with the pending key, check that the metric filter alarm fires, and cancel the deletion.
  4. Find unintended accessIAM Access Analyzer external access findings for KMS keys should list only the intended grants: the data platform key to 777777777777 and the forensics sharing key to 666666666666, both archived by archive rules. Any other finding is fixed in the key policy. GetKeyLastUsage shows keys nobody uses.
  5. Read the compliance evidenceThe Config aggregator shows the four encryption rules compliant everywhere and Security Hub CSPM shows no failed KMS controls; an unencrypted test volume must turn non-compliant.
  6. Game day in the DR RegionDisable the primary multi-Region key in us-east-1 and run the DR application in 888888888888: it must decrypt with the replica, and the replicated bucket must be readable with the DR key.
