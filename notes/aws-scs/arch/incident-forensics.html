Reference architecture

Incident response and forensics

Detection and automated containment hand the security team a case: an isolated instance, a few snapshots and a finding. This design is what happens next. A forensics account that already exists, evidence captured in the right order and kept where nobody can change it, logs that answer what the attacker did, identities shut out without breaking the workload, and a clean rebuild that feeds lessons back into the plan.

Scenario and requirements

The company (organization o-exampleorgid, root r-abcd) runs the security baseline and the threat detection and response pipeline. In the incident this page follows (case IR-2026-117 from Task 2.2), GuardDuty reports that credentials of web-server-role, the role on web server i-0abc1234def567890 in production 111111111111, are being used from outside AWS. The ec2-compromise-response workflow in the security tooling account 222222222222 tags the instance, protects it, snapshots its volumes, waits for a responder, and swaps it into the isolation group sg-0123456789abcdef0. That is where the detection page stops and this one starts. In the previous incident the forensics account 666666666666 had no tooling, the aws/ebs snapshots couldn't be shared, and the stolen role kept working for hours.

Build it

Steps 1 and 2 happen before any incident; steps 3 to 7 are the playbook the responders run, with the repeatable parts automated.

Step 1

Prepare the forensics account, access and tooling

Creating an account takes time, so AWS says to create and instrument forensics accounts well before they are needed. The Forensics OU ou-abcd-55555555 sits directly under r-abcd, away from the Workloads OU, and holds one forensics account, 666666666666. AWS also allows one account per Region; the company instead builds an analysis VPC in each Region it uses (us-east-1, us-west-2), because evidence should stay in the Region of the incident (moving data between jurisdictions can have legal consequences).

What the account holds.

  • An analysis VPC per Region with private subnets only (no internet gateway, NAT or transit gateway). Systems Manager reaches instances through interface endpoints for ssm, ec2messages and ssmmessages, and an S3 gateway endpoint serves the evidence bucket. Analysts use Session Manager; no inbound port is open.
  • A forensic tooling AMI built with EC2 Image Builder, with the disk and memory analysis tools installed.
  • SageMaker AI notebooks for log investigation (AWS's notebook-for-incident-response sample), querying Athena with the notebook's role instead of keys on a laptop, on the notebook-al2023-v1 platform (Amazon Linux 2 notebook instances can't be created or restarted from 1 July 2026).
  • The evidence key and evidence bucket (Step 2).

Access. Responders get an IncidentResponder permission set from IAM Identity Center (identity account 666600006666) in every account, including the forensics account: documented, tested before an incident, monitored and never used day to day, as AWS recommends. If Identity Center itself is unavailable, AWS's emergency access guidance is direct SAML federation to a few accounts, set up in advance; that is the company's break-glass path to the security tooling and forensics accounts, alerted on every use.

Pre-provisioned roles. IRAutomationRole already exists in every workload account (StackSets to ou-abcd-33333333). The forensics account adds IRForensicsRole, which the workflow in the security tooling account assumes to copy shared snapshots and write case records.

Trust policy of IRForensicsRole: only the response workflow's role in the security tooling account may assume it (IAM, forensics account) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::222222222222:role/ec2-compromise-response-sfn" },
      "Action": "sts:AssumeRole"
    }
  ]
}

AWS Security Incident Response. The organization is also enrolled in the managed service. It triages GuardDuty findings and third-party findings arriving through Security Hub CSPM and opens proactive cases for real threats; responders open reactive cases, either AWS-supported (the Security Incident Response engineering team, 24 hours a day, 15-minute engagement objective) or self-managed. Containment runs only once pre-authorized, with its roles deployed by StackSets, through reversible runbooks such as AWSSupport-ContainEC2Instance that default to a dry run; case events go to EventBridge. Its engineers investigate from logs only: no disk or memory forensics, and recovery is recommended, not carried out. The forensics account stays the company's job.

The plan (team and RACI, an out-of-band channel such as AWS Wickr, severity definitions) and the playbooks, started from AWS's sample playbooks, are on Task 2.1.

Step 2

The evidence bucket: write once, encrypted, per case

Memory images, exported logs, finding JSON and case notes go to one bucket in the forensics account, laid out with one prefix per case (IR-2026-117/), as AWS's April 2026 post on collecting forensic artifacts recommends. It combines four controls:

  • S3 Object Lock (with versioning) and a default retention in compliance mode: nobody, the root user included, can delete or overwrite a locked version or shorten its retention.
  • SSE-KMS with the customer managed evidence key, so reading needs both bucket and key permissions.
  • A bucket policy that refuses non-TLS requests and lets writers add objects only under the prefix of an open case.
  • CloudTrail data events recording every read and write.
Create the bucket with Object Lock, then set a 90-day compliance-mode default (AWS CLI, forensics account) 
aws s3api create-bucket \
  --bucket ir-evidence-666666666666-us-east-1 \
  --region us-east-1 \
  --object-lock-enabled-for-bucket

aws s3api put-object-lock-configuration \
  --bucket ir-evidence-666666666666-us-east-1 \
  --object-lock-configuration '{ "ObjectLockEnabled": "Enabled", "Rule": { "DefaultRetention": { "Mode": "COMPLIANCE", "Days": 90 }}}'

Test in governance mode on a test bucket first: a compliance-mode object can only be removed early by closing the account.

Evidence bucket policy: TLS only, and the compromised instance's role may only add objects to its own case prefix while the case is open (bucket policy, forensics account) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::ir-evidence-666666666666-us-east-1",
        "arn:aws:s3:::ir-evidence-666666666666-us-east-1/*"
      ],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    },
    {
      "Sid": "CaseIR2026117Upload",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111111111111:role/web-server-role" },
      "Action": ["s3:PutObject", "s3:AbortMultipartUpload"],
      "Resource": "arn:aws:s3:::ir-evidence-666666666666-us-east-1/IR-2026-117/*"
    }
  ]
}

The workflow adds the second statement when the case opens and removes it when capture ends. Letting the compromised role write sounds risky, but the upload must use credentials on the instance, and the role can only add objects: it can't read, delete or overwrite a locked version (a second write just creates a newer version). The evidence key grants it kms:GenerateDataKey only with kms:ViaService for S3.

Step 3

EC2: memory first, then disks, then move the evidence

AWS's EC2 forensics playbook says to capture memory before isolation or shutdown. The isolation group has no outbound rules, and SSM Agent connects out to the Systems Manager endpoints, so once the instance is isolated Run Command can't reach it. This page therefore adds memory capture to ec2-compromise-response in parallel with the snapshot state and before approval, as the AWS Guidance for Automated Forensics Orchestrator for Amazon EC2 and EKS does. Nothing stops the instance: that would destroy memory and erase instance store volumes.

The tool. AWS names third-party acquisition tools: the EKS Best Practices Guide names LiME (and Volatility for analysis), the aws-samples EKS forensics playbook uses Microsoft's AVML, and the forensics guidance supports both. The company keeps a pinned copy of AVML in a tools bucket, fetched through the VPC's S3 endpoint, rather than downloading it from the internet mid-incident. The only usage shown is the playbook's: AVML given an output path.

Capture memory through Run Command, hash it and upload it to the case prefix (AWS CLI, run by the workflow through IRAutomationRole in 111111111111) 
# The capture is written to /mnt/ir, a scratch EBS volume the workflow attaches, so the root volume changes as little as possible
aws ssm send-command \
  --instance-ids "i-0abc1234def567890" \
  --document-name "AWS-RunShellScript" \
  --comment "IR-2026-117 memory capture" \
  --timeout-seconds 600 \
  --parameters 'commands=["aws s3 cp s3://ir-tools-666666666666-us-east-1/avml /mnt/ir/avml", "chmod +x /mnt/ir/avml", "/mnt/ir/avml /mnt/ir/memory.dmp", "sha256sum /mnt/ir/memory.dmp > /mnt/ir/memory.dmp.sha256", "aws s3 cp /mnt/ir/memory.dmp s3://ir-evidence-666666666666-us-east-1/IR-2026-117/i-0abc1234def567890/memory.dmp --sse aws:kms --sse-kms-key-id arn:aws:kms:us-east-1:666666666666:key/FORENSICS_KEY_ID --checksum-algorithm SHA256", "aws s3 cp /mnt/ir/memory.dmp.sha256 s3://ir-evidence-666666666666-us-east-1/IR-2026-117/i-0abc1234def567890/memory.dmp.sha256 --sse aws:kms --sse-kms-key-id arn:aws:kms:us-east-1:666666666666:key/FORENSICS_KEY_ID"]' \
  --output-s3-bucket-name "ir-evidence-666666666666-us-east-1" \
  --output-s3-key-prefix "IR-2026-117/run-command"

The command output lands under the case prefix too, and two hashes exist: the one computed on the instance and the SHA-256 checksum S3 verifies on upload. The tools bucket ir-tools-666666666666-us-east-1 is new on this page. The same state saves instance metadata (ID, type, AMI, IPs, security groups, subnet, role, launch time, tags), console output and a screenshot (Task 2.2).

Disks. The detection workflow already made crash-consistent snapshots of every attached volume. Snapshots encrypted with the AWS managed key aws/ebs can't be shared, only those under a customer managed key, which must be shared too. Rather than letting the forensics account use production's everyday EBS key, the workflow copies each snapshot with a dedicated sharing key.

Re-encrypt with the sharing key, share the copy, and take ownership in the forensics account (AWS CLI) 
# In prod (111111111111): copy the evidence snapshot, re-encrypting it with the IR sharing key
aws ec2 copy-snapshot --source-region us-east-1 --source-snapshot-id snap-0abcdef1234567890 \
  --encrypted --kms-key-id arn:aws:kms:us-east-1:111111111111:key/IR_SHARE_KEY_ID \
  --description "IR-2026-117 share copy"

# In prod: let the forensics account create volumes from (and copy) the new snapshot
aws ec2 modify-snapshot-attribute --snapshot-id snap-0fedcba9876543210 \
  --attribute createVolumePermission --operation-type add --user-ids 666666666666

# In the forensics account (666666666666), as IRForensicsRole: its own copy, under its own key, same Region
aws ec2 copy-snapshot --source-region us-east-1 --source-snapshot-id snap-0fedcba9876543210 \
  --encrypted --kms-key-id arn:aws:kms:us-east-1:666666666666:key/FORENSICS_KEY_ID \
  --description "IR-2026-117 working copy"
Two statements in the sharing key's policy that let the forensics account use it, and create grants only for AWS resources such as EBS (KMS key policy, prod account) 
[
  {
    "Sid": "AllowForensicsAccountToUseTheKey",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::666666666666:root" },
    "Action": ["kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*", "kms:GenerateDataKey*", "kms:DescribeKey"],
    "Resource": "*"
  },
  {
    "Sid": "AllowForensicsAccountToCreateGrantsForEBS",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::666666666666:root" },
    "Action": ["kms:CreateGrant", "kms:ListGrants", "kms:RevokeGrant"],
    "Resource": "*",
    "Condition": { "Bool": { "kms:GrantIsForAWSResource": true } }
  }
]

Inside the forensics account, an IAM policy limits use of the key to IRForensicsRole. CloudTrail in production records SharedSnapshotCopyInitiated, which goes into the case record. Once the forensics copy exists, production's share copy is deleted, and the forensics copy can be locked with EBS Snapshot Lock in compliance mode (Task 5.2). Analysts mount volumes made from it read-only on an analysis instance, and note who did what, when, with which results.

Step 4

Other workloads: EKS pods and nodes, Lambda, RDS, S3

EKS pods and nodes. On prod-eks, the evidence lives on the node: find the pod's node and its instance ID, label pod and node for the case, capture container state and logs with crictl on the node through Run Command, then capture node memory and snapshot its volumes exactly as in Step 3. If one pod of a Deployment is compromised, assume all are. The control plane audit log (Task 1.2) shows what the attacker asked the API server to do.

Find the node behind a compromised pod and record container state (kubectl from the responder's workstation, then commands on the node) 
# Which node runs the pod, and which EC2 instance that node is
kubectl get pods POD_NAME --namespace shop -o=jsonpath='{.spec.nodeName}{"\n"}'
kubectl get nodes NODE_NAME -o custom-columns=NAME:.metadata.name,INSTANCEID:.spec.providerID

# Mark the node for the investigation
kubectl label node NODE_NAME status=quarantine

# On the node, through Run Command: running containers and one container's logs
crictl ps
crictl logs CONTAINER_ID

Lambda. There's no host: the evidence is the version that ran, its configuration and its code, which get-function returns as a link valid for 10 minutes. Save it before anyone redeploys.

Preserve the function version that ran (AWS CLI, workload account) 
aws lambda get-function --function-name orders-api --qualifier 7

RDS and Aurora. A manual snapshot (aws rds create-db-snapshot) plus the database's audit and error logs. As with EBS, snapshots under the default RDS key can't be shared.

S3. With versioning, earlier versions of changed objects are the evidence; CloudTrail data events and server access logs show who read and wrote what. Macie findings show whether sensitive data was exposed.

Step 5

Logs and chain of custody

What to pull. CloudTrail, VPC Flow Logs and Resolver query logs are AWS's basic logging trifecta. The organization trail in 444444444444 holds data events, every Region and more than 90 days, which Event history can't give.

Every call made with the web server's role from outside the VPC since the day before the finding (Athena SQL, table from Task 1.2 over the organization trail) 
SELECT eventtime, awsregion, sourceipaddress, useragent, eventsource, eventname, errorcode,
       useridentity.accesskeyid
FROM cloudtrail_prod_use1
WHERE "timestamp" >= '2026/11/07'
  AND useridentity.sessioncontext.sessionissuer.arn = 'arn:aws:iam::111111111111:role/web-server-role'
  AND sourceipaddress NOT LIKE '10.%'
ORDER BY eventtime;

The query needs sessioncontext inside useridentity, which the full documented CloudTrail table has (the Task 1.2 version is shortened). Each returned ASIA key, searched for in AssumeRole response elements, follows the attacker into the next role; the attacker's IP becomes the pivot in VPC Flow Logs, WAF, ALB and Resolver logs. Detective compares the role's activity with its 45-day baseline, and the GuardDuty finding JSON is saved to the case, as are query results. The security data lake page covers Security Lake for longer hunts.

Chain of custody. For each artifact the case record shows origin, time, handler and integrity:

  • Hashes: SHA-256 computed at capture and stored next to the artifact, and the S3 checksum on the object. For snapshots, the EBS direct API GetSnapshotBlock returns a SHA-256 checksum per block.
  • Tags: the case ID tag on the instance and on every snapshot and copy.
  • Records of access: CloudTrail data events on the evidence bucket and the SharedSnapshotCopyInitiated event in production.
  • Immutability: compliance-mode Object Lock, plus a legal hold when counsel says the evidence may go to court.
Keep the memory image beyond its 90-day retention while legal proceedings are possible (AWS CLI, forensics account, legal role) 
aws s3api put-object-legal-hold \
  --bucket ir-evidence-666666666666-us-east-1 \
  --key IR-2026-117/i-0abc1234def567890/memory.dmp \
  --legal-hold Status=ON

A legal hold has no end date and anyone with s3:PutObjectLegalHold can remove it, so only the legal role has that permission. Without a hold, evidence expires after 90 days and a lifecycle rule removes it, in line with AWS's playbook advice to delete forensic copies unless a legal or regulatory requirement says otherwise.

Step 6

Contain the identities

Isolation stops the instance, not the credentials copied off it, so identity containment runs as soon as memory is captured.

Role sessions. Temporary credentials can't be deleted. Revoke active sessions on web-server-role attaches an inline policy named AWSRevokeOlderSessions that denies everything to sessions issued before that moment; new sessions, including the replacement instances', keep working.

What revoking active sessions attaches to the role (IAM inline policy AWSRevokeOlderSessions, with the time of revocation) 
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Deny",
    "Action": "*",
    "Resource": "*",
    "Condition": {
      "DateLessThan": { "aws:TokenIssueTime": "2026-11-09T14:32:00Z" }
    }
  }
}

Resource-based policies can still grant old sessions access, so sensitive buckets and keys get the same deny. While the root cause (IMDSv1 and a server-side request forgery bug) is open, the attacker can fetch fresh credentials, so the same-VPC credential policy from Task 2.2 goes on the role too.

Access keys. app-user's key, seen in the attacker's activity, is deactivated, not deleted: that is reversible, keeps the key ID for the investigation, and invalidates presigned URLs it signed. If AWS attached AWSCompromisedKeyQuarantineV3, the team follows the support case and leaves the policy alone.

Deactivate the user's key (AWS CLI, prod account) 
aws iam update-access-key --user-name app-user --access-key-id AKIAIOSFODNN7EXAMPLE --status Inactive

A bucket locked against its owner. In this incident the attacker had replaced the policy on a production bucket with one that denies every principal, administrators included. Centralized root access, delegated to the identity account 666600006666, removes it without anyone signing in as root: a short session scoped by the S3UnlockBucketPolicy task policy, through a Regional STS endpoint (the global endpoint isn't supported). Identity Center users are contained differently, with a pre-staged SCP on identitystore:userId (Task 2.2).

Delete a bucket policy that locks everyone out (AWS CLI, from the identity account with sts:AssumeRoot) 
# A 15-minute privileged session in prod, allowed only the S3 bucket policy task
aws sts assume-root \
  --region us-east-1 \
  --target-principal 111111111111 \
  --task-policy-arn arn=arn:aws:iam::aws:policy/root-task/S3UnlockBucketPolicy \
  --duration-seconds 900

# With the AccessKeyId, SecretAccessKey and SessionToken from the response set as the CLI's credentials:
aws s3api get-bucket-policy --bucket prod-data-platform-111111111111
aws s3api delete-bucket-policy --bucket prod-data-platform-111111111111

The policy text is saved to the case first: it is evidence. IAMDeleteRootUserCredentials does the same for a member account's root credentials.

Step 7

Eradicate, recover and learn

Eradicate. AWS recommends a phased approach: high-value changes first, longer-term hardening later. The team searches every Region, unused ones included, for persistence: new IAM users, keys, roles, identity providers, instances, AMIs, functions, EventBridge rules, and anything that weakens detection. Compromised instances are rebuilt, not cleaned: replacements come from the golden AMI with IMDSv2 required and the SSRF fix deployed. Everything the role could read is rotated.

Rotate the database secret the role could read (AWS CLI, prod account) 
aws secretsmanager rotate-secret --secret-id prod/orders/db

Recover. Backups go to a Vault Lock vault in compliance mode with a copy in a logically air-gapped vault, and GuardDuty Malware Protection for AWS Backup scans the recovery point first. The orders database is restored to a point before the first malicious call as a new instance, so the compromised one stays for the investigation. Restored systems reconnect only after eradication is complete (Task 2.2).

Learn. The after action report records the root cause chain (an SSRF request in the ALB and WAF logs, then IMDSv1 credentials used outside the VPC minutes later), the timeline, and the metrics AWS lists: time to detect, acknowledge, contain and recover, and dwell time. Each lesson becomes a change with an owner (IMDSv2 required by policy, the WAF rule, memory capture ahead of isolation, the playbook), tested at the next game day.

Design decisions

A separate OU and account, not a forensics VPC in production

An account is the strongest boundary AWS has: production administrators, and an attacker holding production credentials, have no path into 666666666666. Its own OU keeps workload SCPs and StackSets out. The cost is the cross-account plumbing: a sharing key, IRForensicsRole and bucket policy grants, all built and tested before they are needed.

Memory before isolation, even though isolation waits

An isolated instance can't run Run Command, and stopping it loses memory. Capturing first adds minutes of exposure; when a live attacker session must be cut at once, a network ACL deny does it.

A dedicated sharing key

Granting the forensics account use of the production EBS key would let it decrypt every production volume. A dedicated key keeps the grant narrow, for one extra snapshot copy and a monthly key charge.

Short compliance retention plus legal holds

Compliance mode makes evidence unchangeable, but a long default would keep every case's memory images (and the personal data in them) for years. A 90-day default covers most cases; a legal hold, removable only by the legal role, keeps what matters for longer. Governance mode can be bypassed by privileged users.

Cost

Standing cost is small: interface endpoints (hourly), AMI snapshots, keys and a near-empty bucket; analysis instances run only during a case. Memory images are as large as the instance's RAM, so retention matters. Security Incident Response is priced per finding ingested, with the first 10,000 a month free, and is free with Enterprise Support.

Alternatives

Rely on AWS Security Incident Response alone

Triage, cases, AWS responders and pre-authorized containment suit a team without round-the-clock cover, but disk and memory forensics, recovery and legal guidance are out of its scope: it complements this design.

The Automated Forensics Orchestrator guidance

The AWS Guidance for Automated Forensics Orchestrator for Amazon EC2 and EKS automates what Step 3 does: triage, parallel memory capture through SSM and disk snapshots shared to the forensics account, then analysis on an instance from a forensic AMI. The company kept its own workflow because it already had the approval states.

Terminate and rebuild without forensics

Fast for a stateless instance, but it destroys the evidence of how the attacker got in, so the hole stays open. Never the answer when a question asks to preserve evidence.

  2. Prove the evidence is immutableAs an administrator of the forensics account, try to delete a version of a test artifact and to shorten its retention: both must fail, and CloudTrail data events must show the attempts.
  3. Check the access is as narrow as designedIAM Access Analyzer external access findings should show only the expected grants: the sharing key in production to 666666666666, and the evidence bucket's case-prefix write to production. The policy simulator confirms web-server-role can put but not get or delete.
  4. Test the people and the break-glass pathEach quarter every responder signs in to the forensics account with IncidentResponder, the emergency SAML path is exercised, and a tabletop walks the bucket-lockout scenario including assume-root.
  5. Game dayGenerated findings, purple team exercises (after reviewing AWS's penetration testing policy) and FIS (Task 2.1), each ending in an after action report.
  6. MeasureTime from hand-off to memory captured, evidence transferred and identities contained.

"Share an encrypted EBS snapshot with the forensics account" fails with aws/ebs: copy it with a customer managed key, grant the other account in the key policy, then modify-snapshot-attribute. "Preserve evidence with minimal data loss" is memory first, then snapshots, then isolation, never stop the instance. "Evidence nobody can delete, not even the root user" is S3 Object Lock in compliance mode, and "keep it indefinitely for litigation" is a legal hold. "Stolen role credentials must stop working without an outage" is revoke active sessions (aws:TokenIssueTime). "A bucket policy denies everyone, including administrators" is sts:AssumeRoot with S3UnlockBucketPolicy. "AWS should do disk forensics for us" is not something AWS Security Incident Response does.
