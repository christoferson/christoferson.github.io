Reference architecture

Multi-account security baseline (AWS Security Reference Architecture)

Every account the company opens arrives already logged, already monitored, already fenced in, and without a root password. The AWS Security Reference Architecture (SRA) says which account does what; Control Tower, delegated administrators, organization policies and centralized root access make it true for the next account as well as the current ones.

Scenario and requirements

The company (organization o-exampleorgid) runs a web app, EKS and ECS containers, an S3 data platform and a GenAI assistant. Its accounts grew one by one, and an audit found Regions with no GuardDuty, accounts without a security contact, member root passwords nobody could find, and a test workload in the management account. The company is moving onto Control Tower (Task 6.1) and wants the result to match the AWS SRA, so a new account needs no manual security work.

RequirementDesign choice

The SRA organizes accounts into an Org Management account, a Security OU with Security Tooling and Log Archive, an Infrastructure OU with Network and Shared Services, and a Workloads OU with application accounts. The company's accounts take these roles:

  • Org Management → management account 555555555555: Organizations, Control Tower, billing and Artifact agreements only.
  • Security Tooling → security tooling account 222222222222 (Control Tower's Config aggregator account, formerly called Audit): delegated administrator for the detection services, Access Analyzer, Config, Firewall Manager and StackSets.
  • Log Archive → log archive account 444444444444 (Control Tower's CloudTrail administrator account): log buckets, and the Security Lake delegated administrator.
  • Network → shared network account 777700007777: transit gateway, central egress and interface endpoints.
  • Shared Services → split. The SRA makes Shared Services the IAM Identity Center administrator; following the multi-account whitepaper, the company's identity account 666600006666 (Infrastructure OU) holds Identity Center, centralized root access and Organizations policy delegation.
  • Application → production 111111111111 and analytics 777777777777 in the Prod OU, plus non-prod accounts in the Non-prod OU.
  • Additions outside the core SRA diagram: forensics 666666666666 in its own Forensics OU, sandbox 333333333333 in the Sandbox OU, DR 888888888888 in a Business Continuity OU, and the test account 101010101010 in the Policy Staging OU.

Reused from other pages: root r-abcd, Workloads OU ou-abcd-33333333 and Policy Staging OU ou-abcd-44444444 (from the data perimeter page), and ou-abcd-11111111 and ou-abcd-22222222, the two workload OUs that Task 6.2 deploys to. New on this page: those two are the Prod and Non-prod OUs nested under the Workloads OU, and the newly vended account prod-payments (the name from Task 6.1's create-account example) gets ID 121212121212.

How it works

The baseline proves itself each time a workload account is vended. The steps below follow prod-payments from request to hand-over. Steps marked AWS happen without anyone acting.

  1. Created and enrolled
  2. Request the accountPlatform teamAn Account Factory (or AFT) request: name prod-payments, a group mailbox as root email, target OU Prod ou-abcd-11111111. Not organizations create-account, which leaves the account unenrolled.
  3. Account createdAWSOrganizations creates 121212121212 in the Prod OU. Because root credentials management is on, the account is created with no root password, access keys or MFA device.
  4. Enrolled by Control TowerAWSThe Prod OU is registered (the Control Tower baseline is enabled on it), so the account gets the organization trail into 444444444444, Config recording in the governed Regions, the security roles trusted by 222222222222 and Identity Center access.
  5. Guardrails apply
  6. Preventive controls inheritedAWSFrom its first API call, the SCPs, RCPs and declarative policies on r-abcd, the Workloads OU and the Prod OU apply: approved Regions, protected security services, the data perimeter, S3 Block Public Access, no public snapshots or AMIs.
  7. Detective and proactive controlsAWSControl Tower's detective controls arrive as service-linked Config rules; proactive controls (CloudFormation hooks) check templates the team deploys later.
  8. Stack sets auto-deployAWSService-managed stack sets on the Prod OU deploy the company's security-baseline (Task 6.2) and the SRA account-level solutions, such as default EBS encryption and the IAM password policy.
  9. Detection switches itself on
  10. Delegated administrators auto-enableAWSGuardDuty, Security Hub CSPM (central configuration from the root), Inspector, Macie and Detective add the account as a member in each Region, administered from 222222222222. The organization analyzer and Config aggregator cover it automatically.
  11. Findings flow to the security teamAWSFindings reach the security tooling account and its central EventBridge bus, aggregated in us-east-1.
  12. Checked and handed over
  13. Root and contacts verifiedSecurity teamAn IAMAuditRootUserCredentials root session confirms no root credentials exist; the security contact is set.
  14. Access grantedPlatform teamIdentity Center permission sets are assigned from 666600006666; the team deploys.

Build it

Step 1

Lay out the OUs and the Control Tower landing zone

The OU tree follows AWS's multi-account whitepaper: Security (security tooling and log archive only), Infrastructure, Workloads with Prod and Non-prod, Sandbox, Forensics, Business Continuity, and the procedural OUs (Policy Staging, Exceptions, Transitional, Suspended).

The landing zone is version 4.0 (Task 6.1): service integrations are optional, no Security OU is created (integration accounts just share an OU under the root), and mandatory controls aren't applied by default. The company switches the integrations on explicitly.

Landing zone 4.0 with CloudTrail and Config integrations on, logging to the log archive account and Config aggregated in the security tooling account (AWS CLI and manifest, management account) 
aws controltower create-landing-zone --landing-zone-version 4.0 --manifest file://manifest.json

# manifest.json (key and kms settings as on Task 6.1, shortened)
{
  "governedRegions": ["us-east-1", "us-west-2"],
  "centralizedLogging": { "enabled": true, "accountId": "444444444444" },
  "config": { "enabled": true, "accountId": "222222222222" },
  "securityRoles": { "enabled": true, "accountId": "222222222222" },
  "accessManagement": { "enabled": true }
}

The AWS SRA code examples README says the library is compatible with Control Tower 4.0, but that the AWS Config and CloudTrail integrations are optional in 4.0 and must be enabled in the landing zone for the SRA solutions to work.

Each workload OU is registered by enabling the Control Tower baseline on it, which enrolls its accounts. Look up the AWSControlTowerBaseline ARN and version with the ListBaselines API.

Register the Prod OU so its accounts are enrolled (AWS CLI, management account) 
aws controltower enable-baseline \
  --baseline-identifier BASELINE_ARN \
  --baseline-version BASELINE_VERSION \
  --target-identifier arn:aws:organizations::555555555555:ou/o-exampleorgid/ou-abcd-11111111

Existing accounts enroll only with the AWSControlTowerExecution role and no existing Config recorder or delivery channel. With auto-enrollment (October 2025) on, an account moved into a registered OU with move-account picks up its baselines and controls instead of drifting.

Step 2

Keep the management account empty: delegate the security services

SCPs and RCPs never restrict the management account, so anything running there is outside the guardrails. The SRA keeps it to organization tasks (Organizations, Control Tower, billing, Artifact agreements, the Identity Center tasks that must stay there), with MFA for every user, a business-managed root email, current contacts and access reviewed at least quarterly.

Most detection services have their own "enable admin account" call, run from the management account in each Region; others are registered with organizations register-delegated-administrator after trusted access (Task 6.1). GuardDuty, Security Hub CSPM, Macie and Access Analyzer allow one administrator each, and the SRA says Detective's must match GuardDuty's and Security Hub CSPM's, so all go to 222222222222.

Make the security tooling account the administrator for the Regional detection services (AWS CLI, management account; repeat with --region us-west-2) 
aws guardduty enable-organization-admin-account --admin-account-id 222222222222 --region us-east-1

# --feature defaults to Security Hub CSPM; the parameter also accepts SecurityHubV2
aws securityhub enable-organization-admin-account --admin-account-id 222222222222 --region us-east-1

aws inspector2 enable-delegated-admin-account --delegated-admin-account-id 222222222222 --region us-east-1

aws macie2 enable-organization-admin-account --admin-account-id 222222222222 --region us-east-1

# Detective registers the account with Organizations itself if no delegated administrator exists yet
aws detective enable-organization-admin-account --account-id 222222222222 --region us-east-1

Per the SRA, the Security Hub CSPM administrator automatically becomes the new Security Hub's administrator, and removing it from either removes it from both. The SRA recommends both: CSPM runs the control checks (needing Config in every account and Region), and the new Security Hub correlates signals into exposure findings.

Config, Security Lake, a scoped Firewall Manager administrator and centralized root access (AWS CLI, management account) 
# AWS Config: one principal for organization rules and conformance packs, one for aggregators
aws organizations enable-aws-service-access --service-principal config-multiaccountsetup.amazonaws.com
aws organizations enable-aws-service-access --service-principal config.amazonaws.com
aws organizations register-delegated-administrator --service-principal config-multiaccountsetup.amazonaws.com --account-id 222222222222
aws organizations register-delegated-administrator --service-principal config.amazonaws.com --account-id 222222222222

# Security Lake uses its own API, one administrator in every Region, the log archive account
aws securitylake register-data-lake-delegated-administrator --account-id 444444444444

# A second Firewall Manager administrator for the network team, limited to the workload OUs and two policy types
aws fms put-admin-account --admin-account 777700007777 \
  --admin-scope '{"OrganizationalUnitScope": {"OrganizationalUnits": ["ou-abcd-11111111", "ou-abcd-22222222"], "AllOrganizationalUnitsEnabled": false, "ExcludeSpecifiedOrganizationalUnits": false}, "PolicyTypeScope": {"PolicyTypes": ["NETWORK_FIREWALL", "DNS_FIREWALL"], "AllPolicyTypesEnabled": false}, "RegionScope": {"AllRegionsEnabled": true}}'

# Centralized root access, delegated to the identity account
aws organizations enable-aws-service-access --service-principal iam.amazonaws.com
aws organizations register-delegated-administrator --service-principal iam.amazonaws.com --account-id 666600006666

Firewall Manager's default administrator (222222222222) is set when the organization is onboarded; put-admin-account adds scoped administrators (up to 10 in total). The Access Analyzer administrator is added in the console's Analyzer settings; changing it later disables the old administrator's analyzers.

Security Lake is the odd one out: it isn't registered with register-delegated-administrator, AWS recommends the log archive account rather than the security tooling account, and removing its delegated administrator deletes the data lake.

Step 3

Auto-enable every service for every account, now and later

Delegation alone doesn't add members. In the security tooling account, each service is set to cover existing and new accounts in every Region (details on Task 1.1).

GuardDuty for all accounts with S3 and runtime protection, and Inspector scanning for new accounts (AWS CLI, security tooling account 222222222222, per Region) 
# ALL also enables existing members (can take up to 24 hours); NEW would cover only accounts that join later
aws guardduty update-organization-configuration \
  --detector-id 12abc34d567e8fa901bc2d34EXAMPLE \
  --auto-enable-organization-members ALL \
  --features '[{"Name": "S3_DATA_EVENTS", "AutoEnable": "ALL"}, {"Name": "RUNTIME_MONITORING", "AutoEnable": "ALL", "AdditionalConfiguration": [{"Name": "EKS_ADDON_MANAGEMENT", "AutoEnable": "ALL"}, {"Name": "ECS_FARGATE_AGENT_MANAGEMENT", "AutoEnable": "ALL"}]}]'

# ec2 and ecr are required values; existing accounts are activated separately
aws inspector2 update-organization-configuration --auto-enable ec2=true,ecr=true,lambda=true,lambdaCode=true

Security Hub CSPM uses central configuration: one policy (FSBP on, a disabled-controls list so new controls arrive automatically) on the root, and a finding aggregator into us-east-1. Macie and Detective auto-enable new members.

Newer organization policies for Security Hub, Inspector and GuardDuty express the same as policy, by Region for every account under the target; the company plans to move to them later.

Organization-wide analyzer, aggregator and a baseline conformance pack (AWS CLI, security tooling account) 
# Access Analyzer is Regional: one organization analyzer per Region
aws accessanalyzer create-analyzer --region us-east-1 --analyzer-name org-external-access --type ORGANIZATION

aws configservice put-configuration-aggregator --configuration-aggregator-name org-compliance \
  --organization-aggregation-source '{"RoleArn": "arn:aws:iam::222222222222:role/config-org-aggregator", "AllAwsRegions": true}'

# The sandbox is excluded from the CIS pack; it gets the lighter Sandbox OU controls instead
aws configservice put-organization-conformance-pack \
  --organization-conformance-pack-name org-cis-baseline \
  --template-s3-uri s3://awsconfigconforms-templates-222222222222/cis-level1.yaml \
  --delivery-s3-bucket awsconfigconforms-results-222222222222 \
  --excluded-accounts 333333333333

Where logs go is the subject of the security logging and data lake architecture. The SRA's latest update (30 October 2026) makes the CloudWatch unified data store in the security tooling account the recommended primary pattern for central log collection, with Security Lake in log archive as a secondary option; it also recommends managing the organization trail from security tooling while the bucket stays in log archive. This page only makes sure every account feeds that design.

Step 4

Preventive guardrails: SCPs, RCPs, declarative policies and controls

Guardrails stop anyone in a member account, administrators included, from switching the baseline off. Four tools share the work (Task 6.1):

  • SCPs cap what member-account principals can do: Regions, protected security services.
  • RCPs cap what can be done to resources: TLS only, and the perimeters on the data perimeter page.
  • Declarative policies fix service configuration, and also apply to the management account when attached at the root.
  • Control Tower controls: preventive (the three above), detective (Config rules) and proactive (CloudFormation hooks).
Protect the baseline: nobody but the platform role and Control Tower may stop detectors, recorders or trails, or leave the organization (SCP, attached to r-abcd) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectSecurityBaseline",
      "Effect": "Deny",
      "Action": [
        "guardduty:DeleteDetector",
        "guardduty:DisassociateFromMasterAccount",
        "guardduty:UpdateDetector",
        "securityhub:DisableSecurityHub",
        "securityhub:DisassociateFromAdministratorAccount",
        "config:StopConfigurationRecorder",
        "config:DeleteConfigurationRecorder",
        "config:DeleteDeliveryChannel",
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "organizations:LeaveOrganization"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": [
            "arn:aws:iam::*:role/platform-admin",
            "arn:aws:iam::*:role/AWSControlTowerExecution"
          ]
        }
      }
    }
  ]
}

The LeaveOrganization deny matters because AWS's responders see attackers try to leave the organization to escape its SCPs and monitoring. If the SRA solutions manage these services, add their execution role to the exceptions (check its name in the deployed common prerequisites). Rollout goes Policy Staging ou-abcd-44444444, one account, then the root.

S3 Block Public Access as an organization policy, and a Control Tower control on the Prod OU (AWS CLI, management account) 
aws organizations enable-policy-type --root-id r-abcd --policy-type S3_POLICY

# s3-bpa.json: {"s3_attributes": {"public_access_block_configuration": {"@@assign": "all"}}}
aws organizations create-policy --content file://s3-bpa.json \
  --name org-s3-block-public-access --type S3_POLICY \
  --description "All four S3 Block Public Access settings in every account"

# use the policy ID returned above
aws organizations attach-policy --policy-id $S3_POLICY_ID --target-id r-abcd

# Control identifiers are opaque; take the ARN from the Control Catalog
aws controltower enable-control \
  --control-identifier CONTROL_ARN \
  --target-identifier arn:aws:organizations::555555555555:ou/o-exampleorgid/ou-abcd-11111111 \
  --region us-east-1

The EC2 policy from Task 6.1 (no public snapshot or AMI sharing) is attached at the root the same way. Proactive controls only see resources deployed through CloudFormation.

With landing zone 4.0, mandatory controls are no longer applied by default. The SRA says you must keep mandatory controls enabled and should enable the strongly recommended ones, so check the enabled controls after creating or upgrading the landing zone. Don't assume the log buckets are protected.

Step 5

Centralize root access and set the security contacts

With centralized root access, new accounts have no root credentials and existing ones are deleted centrally. Root-only tasks (unlocking a bucket or queue policy that denies everyone, allowing password recovery) run as short AssumeRoot sessions from the delegated administrator, each scoped to one task policy (Task 4.1, Task 2.2).

Turn on both capabilities (AWS CLI, management account; trusted access and delegation are in Step 2) 
# Root credentials management: remove and block member root credentials
aws iam enable-organizations-root-credentials-management

# Privileged root actions: needed to recover root or unlock a policy later
aws iam enable-organizations-root-sessions
Delete the root credentials left in an older account (AWS CLI, identity account 666600006666, Regional STS endpoint) 
# Returns 15-minute credentials limited to this task policy; then delete the login profile, keys and MFA in that session
aws sts assume-root \
  --target-principal 111111111111 \
  --task-policy-arn arn=arn:aws:iam::aws:policy/root-task/IAMDeleteRootUserCredentials \
  --duration-seconds 900

The management account's root user is unaffected: it keeps MFA (FIDO2 keys), split custody of password and devices, and EventBridge alerts on root sign-in in us-east-1, us-east-2 and us-west-2.

AWS sends security notices to each account's security alternate contact. With trusted access for AWS Account Management, the management account sets it for every member, one call per account. The SRA's account alternate contacts solution applies the same contacts to all accounts, so the platform team doesn't have to remember each new one.

Point the new account's security contact at the security team (AWS CLI, management account) 
aws organizations enable-aws-service-access --service-principal account.amazonaws.com

aws account put-alternate-contact --account-id 121212121212 \
  --alternate-contact-type SECURITY \
  --email-address security-team@example.com \
  --name "Security Operations" \
  --phone-number "+1-206-555-0100" \
  --title "Security"

The SRA recommends delegating centralized root access to the Security Tooling account. The company delegates it to the identity account instead, following the multi-account whitepaper and Task 6.1. Either works if the delegate is tightly controlled; whichever account holds it needs sts:AssumeRoot granted explicitly to a small, monitored role.

Step 6

Implement it with the AWS SRA code examples

The SRA guide links an AWS sample repository, aws-samples/aws-security-reference-architecture-examples, with CloudFormation (including CfCT) and Terraform solutions. The README calls its configurations "deliberately very restrictive", illustrating a pattern rather than a complete solution, so each template is reviewed before use. The prerequisites: Organizations (always required), the security tooling and log archive accounts in place (names may differ), an OU structure aligned with the SRA, and the common prerequisites solution deployed once, since every other solution depends on it.

Easy Setup is the recommended path. One template from the management account stages the code library in an sra-staging- bucket, deploys the common prerequisites, and then deploys each solution whose parameter is set to Yes, through CloudFormation StackSets or through CfCT. Trusted access for StackSets has to be enabled first.

Easy Setup in a Control Tower organization, starting with GuardDuty, Security Hub and Config for the management account (AWS CLI, management account; parameters from the Easy Setup README) 
# The template is larger than 51,200 bytes, so CloudFormation needs a staging bucket for it
aws cloudformation deploy --template-file ./sra-easy-setup.yaml \
  --stack-name sra-easy-setup \
  --s3-bucket TEMPLATE_BUCKET \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides pDeployGuardDutySolution=Yes pDeploySecurityHubSolution=Yes pDeployConfigManagementSolution=Yes pSRAAlarmEmail=security-team@example.com

More solutions are switched on by later stack updates; with CfCT, the template goes in the configuration repository and the AWSControlTowerExecution role is deployed into the management account first. config_management_account exists because Control Tower doesn't record Config in the management account. The solutions the company uses, all AWS sample code:

  • common: common prerequisites, CfCT setup, and register delegated administrator, which other solutions depend on.
  • cloudtrail_org: an organization trail that defaults to S3 and Lambda data events, so it doesn't duplicate Control Tower's management-event trail.
  • guardduty_org, inspector_org, macie_org and detective_org: delegated administrator and auto-enable for all accounts and governed Regions (Detective depends on the GuardDuty solution).
  • securityhub_org: delegated administrator for all accounts and governed Regions; it needs Config in every account. The README still says "Security Hub", so check whether the templates configure Security Hub CSPM, the new Security Hub or both before relying on it.
  • iam_access_analyzer: the organization analyzer in the delegated administrator plus an account analyzer in each account.
  • ec2_default_ebs_encryption, s3_block_account_public_access (requires Control Tower) and iam_password_policy: account-level settings in every account.
  • account_alternate_contacts: billing, operations and security contacts for all accounts.
  • config_conformance_pack_org: a conformance pack in all accounts and chosen Regions. The config_org solution is incompatible with Control Tower, so it is not used.
  • firewall_manager_org and shield_advanced: example security group and WAF policies for all accounts, and Shield Advanced for chosen existing and future accounts (for the public web app).

Where a solution overlaps an organization policy, one owner wins: S3 Block Public Access comes from the S3 policy (unchangeable in the account, and it covers the management account), so that SRA solution stays off.

Design decisions

One security tooling account for all detection services

GuardDuty, Security Hub CSPM and Macie allow a single delegated administrator each, and Detective's must match GuardDuty's and Security Hub CSPM's, so splitting them gains nothing and breaks pivots. One account means one place to work and one account to lock down: few roles, view-only access for investigations, and SCPs still apply to it. The cost is concentration, so its access is reviewed most often.

Logs stored in log archive, analysed from security tooling

The log archive account holds data and nothing else; consumers get read-only access and SCPs on the Security OU block deletion. Security Lake's administrator sits there too, as AWS recommends. The SRA's October 2026 update moves the recommended analytics hub to the CloudWatch unified data store in the security tooling account, with a WORM copy in S3 Object Lock in log archive, because CloudWatch Logs isn't immutable. That trade-off is designed on the logging architecture page.

Control Tower plus code, not Control Tower alone

Control Tower gives enrollment, the trail, Config and controls, but doesn't enable GuardDuty, Inspector or Macie, and has no delegated administrator. The SRA examples and the company's stack sets fill the gap, with each setting owned by one mechanism: the trail by Control Tower, data events by cloudtrail_org, S3 Block Public Access by the S3 policy.

Root access delegated to the identity account

The SRA suggests the security tooling account; the company keeps root sessions with the identity account so that the team investigating findings isn't also the team that can act as root in any account. The trade-off is one more highly privileged account, which is why sts:AssumeRoot is limited to a single break-glass-style role there, alerted on every use.

Guardrails at the root, exceptions by OU

Protection of security services and the Region restriction are attached at r-abcd, so no OU can be created without them. Accounts needing a documented exception move to the Exceptions OU with account-level policies. SCPs allow 10 per target and RCPs 5 (one is RCPFullAWSAccess), so statements are merged rather than one policy per rule.

Two governed Regions, everything else denied

The SRA says to replicate the architecture in every Region used and deny the rest. The company governs us-east-1 and us-west-2, repeats every delegation and auto-enable step in both, and blocks other Regions so nothing hides where nobody watches.

Alternatives

Landing Zone Accelerator on AWS

LZA deploys a multi-account security foundation from configuration files, now with a Universal Configuration baseline and a compliance workbook. It covers more in one tool, but is a larger solution to operate.

Organizations without Control Tower

The SRA Easy Setup also runs on Organizations alone (pControlTower=false with the log archive and security account IDs and governed Regions). That suits organizations with their own account pipeline, but enrollment, drift detection and the managed control library have to be replaced. Control Tower's controls-dedicated experience is the middle path: managed controls without a full landing zone.

Account Factory for Terraform, or CfCT

AFT provisions and customizes accounts from a Terraform pipeline in its own account; CfCT deploys CloudFormation templates, SCPs and RCPs on Control Tower lifecycle events, and is one of the SRA deployment methods. Either replaces console Account Factory requests; the baseline itself stays the same.

Several organizations

A separate organization isolates an acquired business or regulated unit, but duplicates the whole baseline and security tooling, and the data perimeter keys are per organization.

Testing it

  1. Check the delegationsFrom the management account, aws organizations list-delegated-administrators must list 222222222222 for the detection services and Config, 444444444444 for Security Lake and 666600006666 for IAM, and list-delegated-services-for-account --account-id 222222222222 must show nothing unexpected. Repeat the service-level checks in both Regions.
  2. Vend a test account end to endVend an account into Policy Staging (or move the test account 101010101010 between registered OUs) and time how long until it is a member in every detection service and the Config aggregator. Security Hub coverage findings, which the SRA recommends using to check that the services are enabled uniformly, show any gaps.
  3. Try to break the baselineAs an administrator in the test account, call cloudtrail:StopLogging, guardduty:DeleteDetector and organizations:LeaveOrganization, and make a bucket public. Each must fail with an explicit deny, recorded in log archive.
  4. Check root statusRun an IAMAuditRootUserCredentials root session against a sample of accounts; none should have a password, keys or MFA. The Config and Security Hub CSPM root MFA checks then show "not applicable" rather than failed for those accounts.
  5. Check declarative policies and controlsaws organizations describe-effective-policy shows the merged S3 and EC2 policy for an account, and the declarative policy account status report shows whether each attribute is uniform. The Control Tower enabled controls page must list the mandatory controls, and an EventBridge rule in the management account must receive drift events.
  6. Assess against the SRARun SRA Verify, AWS's open-source assessment tool, to compare the deployed services with SRA recommendations, and keep the conformance pack compliance score per account as the running measure.

"Ensure every new account in the organization automatically has GuardDuty and Security Hub enabled and sends findings to the security team, with the least operational overhead" is a delegated administrator in a security tooling account with auto-enable (and Security Hub central configuration), not a script in the management account. "Prevent anyone in member accounts from disabling these services" adds an SCP. "Remove root credentials from all member accounts but keep the ability to unlock a bucket policy" is centralized root access with both root credentials management and root sessions. Answers that run security services from the management account are the distractor.
