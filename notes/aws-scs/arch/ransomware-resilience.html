Reference architecture

Ransomware resilience and data recovery

Assume the attacker already has administrator credentials in production. The design makes sure they can't delete, shorten, re-encrypt or hide the company's backups, that the security team hears about every attempt within minutes, and that a clean copy can be restored into an account the attacker never touched.

Scenario and requirements

The company (organization o-exampleorgid) runs its web app, EKS containers, S3 data platform and GenAI assistant in production account 111111111111 in us-east-1, with us-west-2 as the disaster recovery Region. AWS says ransomware on AWS starts with valid stolen credentials, usually long-term access keys, not a flaw in a service. So the design assumes the worst case: an attacker holds an administrator role in production and wants to make the company pay. On AWS that looks like:

  • Destroying the way back: DeleteRecoveryPoint, DeleteBackupVault, shortening lifecycles with UpdateRecoveryPointLifecycle, deleting EBS snapshots, AMIs and RDS snapshots, or turning off versioning.
  • Making data unreadable: CopyObject over every object with SSE-C and a key only the attacker holds (the pattern in AWS's January 2025 post), or re-encryption under an attacker's KMS key in another account.
  • Taking the keys away: ScheduleKeyDeletion on the customer managed keys, so data and backups under them become unreadable after the waiting period.
  • Opening or locking the door: PutBucketPolicy to grant an outside account or deny the owner, and lifecycle rules that quietly expire data.

How it works

The attack is played out against the controls, then the recovery. Steps marked AWS happen automatically.

  1. An attacker with administrator credentials in production
  2. Deletes backupsAttackerCalls DeleteRecoveryPoint and UpdateRecoveryPointLifecycle on prod-vault. The SCP denies both before AWS Backup looks at them; even without it, the vault's compliance-mode lock refuses, root user included.
  3. Deletes snapshots and AMIsAttackerDeletes EBS snapshots made outside AWS Backup and deregisters AMIs. The locked Region-level Recycle Bin rules keep them recoverable for 30 days, and locked snapshots can't be deleted at all.
  4. Re-encrypts or exposes S3 dataAttackerSSE-C writes are blocked, uploads naming another KMS key are denied by the bucket policy, and overwrites only create new versions; Object Lock keeps earlier versions for 14 days. PutBucketPolicy and lifecycle changes are denied by SCP.
  5. Schedules key deletionAttackerThe KMS SCP lets only key-custodian schedule deletion, with a 30-day wait (key management at scale).
  6. Detection
  7. Findings and alertsAWSGuardDuty raises Impact:IAMUser/AnomalousBehavior and S3 Impact:S3/AnomalousBehavior.Delete findings; the EventBridge rule on destructive Backup, S3, EC2 and KMS calls pages the security team in 222222222222, which starts the ransomware playbook.
  8. Recovery, away from production
  9. Copies are untouchedAWSLast night's copies sit in central-vault and dr-lag-vault in 888888888888, us-west-2. No role in 111111111111 can reach them; cross-account calls other than backup:CopyIntoBackupVault are rejected.
  10. Pick a clean pointRecovery teamGuardDuty Malware Protection for AWS Backup scan results and the CloudTrail timeline identify the last recovery point before the attacker's first action.
  11. Restore and cut overRecovery teamIn 141414141414, which already has the air-gapped vault through AWS RAM, the team restores into a VPC with no path to production, validates, and only then moves traffic.

Build it

Step 1

Guardrails before backups

Backups are the last line; the first is stopping the destructive calls. Least privilege comes first: no human has standing administrator access in production, and long-term access keys are banned (workforce identity). The data perimeter stops data leaving for outside accounts, and the KMS guardrails protect the keys. This page adds an SCP for the data protection controls themselves.

The AWS Backup docs say why each part is needed. A vault access policy only governs AWS Backup APIs, so EBS and RDS snapshots can still be reached through EC2 and RDS. Vault Lock doesn't govern sharing or tier changes made through EC2: a snapshot recovery point can still be shared with ModifySnapshotAttribute or re-tiered with ModifySnapshotTier. And disabling an AMI blocks restores of EC2 backups even in a locked vault. AWS recommends denying those EC2 actions except to the roles backup plans use, because AWS Backup itself uses them for cross-account copies and cold storage.

Protect backup vaults, recovery points, snapshots, Recycle Bin rules and S3 data protection settings; only backup-admin and the AWS Backup role are exempt (SCP, attached to ou-abcd-33333333 and ou-abcd-77777777) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectBackupVaultsAndRecoveryPoints",
      "Effect": "Deny",
      "Action": [
        "backup:DeleteRecoveryPoint",
        "backup:UpdateRecoveryPointLifecycle",
        "backup:DeleteBackupVault",
        "backup:PutBackupVaultAccessPolicy",
        "backup:DeleteBackupVaultAccessPolicy",
        "backup:PutBackupVaultLockConfiguration",
        "backup:DeleteBackupVaultLockConfiguration",
        "backup:PutBackupVaultNotifications",
        "backup:DeleteBackupVaultNotifications",
        "backup:DeleteBackupPlan",
        "backup:UpdateBackupPlan"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/backup-admin" }
      }
    },
    {
      "Sid": "ProtectSnapshotsAmisAndRecycleBin",
      "Effect": "Deny",
      "Action": [
        "ec2:ModifySnapshotAttribute",
        "ec2:ModifySnapshotTier",
        "ec2:UnlockSnapshot",
        "ec2:DisableImage",
        "rbin:UpdateRule",
        "rbin:DeleteRule",
        "rbin:UnlockRule"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": ["arn:aws:iam::*:role/backup-admin", "arn:aws:iam::*:role/backup-service"]
        }
      }
    },
    {
      "Sid": "ProtectS3DataProtectionSettings",
      "Effect": "Deny",
      "Action": [
        "s3:PutBucketVersioning",
        "s3:PutLifecycleConfiguration",
        "s3:PutBucketObjectLockConfiguration",
        "s3:BypassGovernanceRetention",
        "s3:PutReplicationConfiguration",

        "s3:DeleteBucketPolicy"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/backup-admin" }
      }
    }
  ]
}

Plans that come from the organization backup policy are managed by AWS Backup, not by IAM principals in the account, so the deny on plan changes doesn't break them. In practice the platform pipeline role is added to the S3 exception, because bucket policies and lifecycle rules change through it; nothing else is. backup-admin is a break-glass role assumable only through the same approval process as key-custodian, and every use of it pages the security team. The rollout follows the baseline: Policy Staging, one account, then the OUs (Task 6.1).

SSE-C. S3 has blocked SSE-C by default for new buckets (and existing buckets in accounts that never used it) since April 2026, and the data platform bucket sets BlockedEncryptionTypes explicitly (key management at scale). Because the company never uses SSE-C, AWS's RCP from the January 2025 post also goes on the root, so a bucket created with an older setting is still covered:

Deny any upload that carries an SSE-C key, in every account (RCP, attached to r-abcd) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RestrictSSECObjectUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "*",
      "Condition": {
        "Null": { "s3:x-amz-server-side-encryption-customer-algorithm": "false" }
      }
    }
  ]
}

CopyObject is authorized as s3:PutObject on the destination, which is why this one action covers the copy-over-itself attack.

Step 2

Organization backup policies from a delegated administrator

A backup plan created by hand in each account is one forgotten setting away from a gap. An Organizations backup policy is a declarative policy that AWS Backup turns into a backup plan in every account it reaches; the plan is visible but owned by the organization.

The management account enables cross-account management in AWS Backup (backup policies, cross-account monitoring, cross-account backup) and registers a delegated administrator. Registering only enables cross-account job monitoring; to edit backup policies too, the delegated account also needs the AWSBackupOrganizationAdminAccess managed policy on its roles and a resource-based delegation policy in Organizations. The company delegates to the DR account 888888888888, run by the platform team's data protection group, keeping the management account out of daily work.

Register the DR account as the AWS Backup delegated administrator (AWS CLI, management account 555555555555) 
aws organizations register-delegated-administrator \
  --account-id 888888888888 \
  --service-principal "backup.amazonaws.com"

The policy can't create the vault or the IAM role: both must already exist in every account and Region it covers, which is why a service-managed StackSet deploys prod-vault and backup-service to the Prod OU first (Task 6.2). Selection is by tag or resource type, not by individual ARN.

Daily backups of everything tagged backup=daily, kept 35 days, copied to the locked vault and the air-gapped vault in the DR account and Region (backup policy, attached to the Prod OU ou-abcd-11111111) 
{
  "plans": {
    "org-daily": {
      "regions": { "@@assign": ["us-east-1"] },
      "rules": {
        "daily": {
          "schedule_expression": { "@@assign": "cron(0 5 ? * * *)" },
          "start_backup_window_minutes": { "@@assign": "60" },
          "complete_backup_window_minutes": { "@@assign": "1440" },
          "target_backup_vault_name": { "@@assign": "prod-vault" },
          "lifecycle": {
            "delete_after_days": { "@@assign": "35" }
          },
          "copy_actions": {
            "arn:aws:backup:us-west-2:888888888888:backup-vault:central-vault": {
              "target_backup_vault_arn": { "@@assign": "arn:aws:backup:us-west-2:888888888888:backup-vault:central-vault" },
              "lifecycle": { "delete_after_days": { "@@assign": "90" } }
            },
            "arn:aws:backup:us-west-2:888888888888:backup-vault:dr-lag-vault": {
              "target_backup_vault_arn": { "@@assign": "arn:aws:backup:us-west-2:888888888888:backup-vault:dr-lag-vault" },
              "lifecycle": { "delete_after_days": { "@@assign": "90" } }
            }
          }
        }
      },
      "selections": {
        "tags": {
          "daily-tagged": {
            "iam_role_arn": { "@@assign": "arn:aws:iam::$account:role/backup-service" },
            "tag_key": { "@@assign": "backup" },
            "tag_value": { "@@assign": ["daily"] }
          }
        }
      }
    }
  }
}

$account becomes each member's own account ID, while the copy targets use the real DR account ID, as the syntax requires for cross-account copies. A second rule with enable_continuous_backup gives RDS, Aurora and S3 point-in-time restore (at most 35 days' retention, so it has no long-term copies). The policy can also carry scan_actions with scan_settings so GuardDuty Malware Protection for AWS Backup scans new recovery points. Resource types differ in whether they support a copy that is both cross-account and cross-Region; the AWS Backup feature availability table is checked for each one, and anything that can't do both is copied in two hops.

Backup policies are one of the Organizations management policy types, like tag policies (Task 6.1). "Ensure every account backs up its resources the same way, even new ones" is a backup policy attached to an OU, not an SCP and not a Config rule.

Step 3

Vaults, keys and Vault Lock

Each vault has its own KMS key. For fully managed resource types (S3, EFS, DynamoDB with advanced backup and others) recovery points are encrypted with the vault's key, independent of the source. EBS, RDS, Aurora and FSx backups keep the source's encryption, so those sources must use customer managed keys for cross-account copies. That's one more reason for the no AWS managed keys rule. In 888888888888, central-vault uses the DR backup key, owned there with its own deletion SCP, so a key problem in production can't make the copies unreadable.

The destination vault must let the source accounts copy in; backup:CopyIntoBackupVault is the only action AWS Backup accepts across accounts:

Let accounts in the organization copy into central-vault, and nothing else (backup vault access policy, DR account 888888888888) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCopyFromOrganization",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "backup:CopyIntoBackupVault",
      "Resource": "*",
      "Condition": {
        "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" }
      }
    }
  ]
}

Vault Lock makes the vault write-once-read-many: nobody, the root user included, can delete a backup or change its lifecycle in a locked vault until its retention ends. It comes in two modes:

  • Governance mode (no ChangeableForDays): users with enough IAM permissions can remove or change the lock. Good for testing and for internal policy, not against an administrator.
  • Compliance mode (ChangeableForDays, 3 to 36,500): during this grace time, the cooling-off period, the lock can still be changed or removed. After it, the vault and lock are immutable; nobody, not even AWS, can change or delete them while recovery points remain.
Lock central-vault in compliance mode after a 3-day grace time; copies must keep 30 to 400 days (AWS CLI, DR account 888888888888, us-west-2) 
aws backup put-backup-vault-lock-configuration --region us-west-2 \
  --backup-vault-name central-vault \
  --changeable-for-days 3 \
  --min-retention-days 30 \
  --max-retention-days 400

Minimum and maximum retention apply to new jobs, which fail if their lifecycle falls outside them; recovery points already in the vault keep their lifecycle. Before the grace time ends, the team checks describe-backup-vault (Locked and LockDate) and that no rule keeps points "always", since in a compliance vault those can never be deleted and keep costing money. prod-vault is locked the same way (Task 2.2). One limit remains: if an account is closed, AWS deletes its vault contents after the 90-day post-closure period, Vault Lock or not. That is why copies live in a second account.

AWS Backup Vault Lock is not S3 Glacier Vault Lock. The Glacier feature (24-hour test, then a permanent vault lock policy) belongs to the original Glacier vault service, which no longer accepts new customers (Task 5.2).

Step 4

The logically air-gapped vault, shared with the recovery account

A logically air-gapped vault is a second type of AWS Backup vault. It always has Vault Lock in compliance mode, its recovery points are stored in AWS service-owned accounts, and it can be shared with other accounts, in or outside the organization, through AWS RAM. A shared account can view and restore, but not copy. So the company's recovery account can restore directly from it without copying first, even if the owning account is compromised.

Encryption defaults to an AWS owned key, which AWS Backup recommends; since November 2025 a customer managed key is optional, preferably in a different account. The company keeps the AWS owned key: AWS's August 2026 post notes this removes the risk of losing access through a deleted or misconfigured customer managed key. Sources of non fully managed types (EBS, RDS) must still be under customer managed keys to be copied in, and unencrypted Aurora clusters aren't supported.

Create the air-gapped vault with 30 to 400 days' retention (AWS CLI, DR account 888888888888) 
aws backup create-logically-air-gapped-backup-vault \
  --region us-west-2 \
  --backup-vault-name dr-lag-vault \
  --min-retention-days 30 \
  --max-retention-days 400

The minimum accepted is 7 days; copies with retention outside the range fail. The vault starts in CREATING. Next it is shared, by account ID only (RAM can't share it with an OU or the whole organization), with the recovery account and the forensics account, as in AWS's 2024 reference design. The recipient has 12 hours to accept.

Share the air-gapped vault with the recovery and forensics accounts (AWS CLI, DR account 888888888888) 
aws ram create-resource-share \
  --name dr-lag-vault-share \
  --resource-arns arn:aws:backup:us-west-2:888888888888:backup-vault:dr-lag-vault \
  --principals 141414141414 666666666666 \
  --region us-west-2

RAM sharing depends on the owning account. Multi-party approval covers the case where it is lost: an approval team, signing in through a separate identity path, can grant another account access to the vault, and that access can't be revoked from the source account. Backups stay reachable through it until the post-closure period ends. AWS's May 2026 cyber recovery post recommends putting the approval team in a second organization, because a compromised management account could disable approval in the same one. The company runs RAM sharing now and has MPA onboarding on its roadmap. With MPA, a backup policy can also send backups straight into an air-gapped vault (target_logically_air_gapped_backup_vault_arn) to save the cost of a second copy.

Step 5

Service-level protection: S3, EBS, RDS and DynamoDB

S3. The data platform bucket has versioning, so an overwrite or delete creates a new version or delete marker instead of destroying data (Task 5.2). Versioning alone isn't enough, because anyone with s3:DeleteObjectVersion can remove versions. MFA delete would add a second factor, but only the root user can enable it, only through the CLI or API, and it can't be used on a bucket with lifecycle rules, which the data platform needs. Security Hub CSPM S3.20 doesn't report buckets with lifecycle rules for that reason. The bucket uses Object Lock instead:

Keep every version of the data platform for at least 14 days in governance mode (AWS CLI, production account 111111111111) 
aws s3api put-object-lock-configuration \
  --bucket shop-data-111111111111 \
  --object-lock-configuration '{ "ObjectLockEnabled": "Enabled", "Rule": { "DefaultRetention": { "Mode": "GOVERNANCE", "Days": 14 }}}'

Governance mode, not compliance, because privacy requests sometimes need a record deleted early. Doing that requires s3:BypassGovernanceRetention, which the Step 1 SCP leaves only to backup-admin, so a production administrator can't. Object Lock protects versions but not their key, so the key guardrails matter as much.

S3 Replication copies new versions to shop-data-dr-888888888888 in us-west-2 through s3-replication, opting in to SSE-KMS objects and re-encrypting under the DR account's key (Task 5.2). Two settings make it ransomware-relevant. The owner override ("Owner": "Destination") makes the DR account own replicas, so the production account has no rights over them. Delete marker replication is off, and deletes of specific versions never replicate, so a mass deletion in production doesn't reach the copy. The DR bucket has Object Lock, so replicated objects keep their retention.

EBS snapshots and AMIs. AWS Backup's own EBS snapshots can't be deleted through EC2, but the golden AMIs and snapshots from other tools can. Two controls cover them. Recycle Bin keeps deleted EBS snapshots and EBS-backed AMIs for 1 to 365 days (EBS volumes 1 to 7 days). A Region-level rule (no resource tags) covers everything of its type, and a locked rule can't be changed or deleted until an unlock delay of 7 to 30 days has passed after someone unlocks it.

Keep deleted snapshots and AMIs for 30 days, with rules that need a 14-day unlock delay (AWS CLI, every workload account and Region, by StackSets) 
aws rbin create-rule --resource-type EBS_SNAPSHOT \
  --retention-period RetentionPeriodValue=30,RetentionPeriodUnit=DAYS \
  --description "Region-level: keep deleted snapshots for 30 days" \
  --lock-configuration 'UnlockDelay={UnlockDelayUnit=DAYS,UnlockDelayValue=14}'

aws rbin create-rule --resource-type EC2_IMAGE \
  --retention-period RetentionPeriodValue=30,RetentionPeriodUnit=DAYS \
  --description "Region-level: keep deregistered AMIs for 30 days" \
  --lock-configuration 'UnlockDelay={UnlockDelayUnit=DAYS,UnlockDelayValue=14}'

EBS Snapshot Lock goes further for the snapshots behind the golden AMI: locked for 1 to 36,500 days, in governance mode (changeable by authorized users) or compliance mode, where changes are possible only during an optional cooling-off period of up to 72 hours. After that the lock can only be extended.

Lock the golden AMI's snapshot in compliance mode for a year after a 24-hour cooling-off (AWS CLI, production account) 
aws ec2 lock-snapshot --snapshot-id snap-0abcdef1234567890 \
  --lock-mode compliance --cool-off-period 24 --lock-duration 365

RDS and Aurora. The orders database is an encrypted Aurora cluster under the web app key, backed up by the policy's continuous rule for point-in-time restore. Restores always create a new cluster or instance, so the damaged one stays for investigation (Task 2.2).

DynamoDB. The GenAI assistant's tables have point-in-time recovery (restore to any second in a window of 1 to 35 days, always into a new table) and deletion protection. They are also tagged for the backup policy, because PITR lives in the same account and dies with it.

Step 6

Detection and evidence

GuardDuty, delegated to 222222222222 (threat detection and response), is the anomaly layer. Impact:IAMUser/AnomalousBehavior (High) covers unusual delete, update and put calls such as PutBucketPolicy. Exfiltration:IAMUser/AnomalousBehavior covers calls like PutBucketReplication and CreateSnapshot that copy data out. DefenseEvasion:IAMUser/AnomalousBehavior covers delete, disable and stop calls, and Stealth:IAMUser/CloudTrailLoggingDisabled covers logging changes. With S3 Protection, Impact:S3/AnomalousBehavior.Delete (High), .Write and .Permission flag mass deletion, mass overwriting and policy changes, and Extended Threat Detection links them into an attack sequence.

EventBridge covers the attempts that matter even when they fail or look normal. AWS Backup's own events (source aws.backup, such as Backup Vault State Change) say what happened; the CloudTrail events say who called what:

Page the security team on any attempt to delete or weaken backups, Recycle Bin rules, snapshot locks, bucket protection or keys (EventBridge event pattern, every account and Region, forwarded to 222222222222) 
{
  "source": ["aws.backup", "aws.ec2", "aws.s3", "aws.kms"],
  "detail-type": ["AWS API Call via CloudTrail"],
  "detail": {
    "eventName": [
      "DeleteBackupVault", "DeleteRecoveryPoint", "UpdateRecoveryPointLifecycle",
      "DeleteBackupVaultLockConfiguration", "PutBackupVaultAccessPolicy", "DeleteBackupVaultAccessPolicy",
      "DeleteBackupPlan", "UnlockSnapshot", "DisableImage",
      "PutBucketPolicy", "DeleteBucketPolicy", "PutBucketVersioning", "PutBucketLifecycle",
      "ScheduleKeyDeletion", "DisableKey"
    ]
  }
}

Each event name belongs to one of the four services, so a single rule covers them all; a similar rule watches Recycle Bin rule changes. Calls the SCP denied are still recorded in CloudTrail with an errorCode, and a burst of them from one principal is itself a finding; the security data lake keeps the history (security data lake). A second rule watches AWS Backup's Scan Job State Change events for "scanResultStatus": "THREATS_FOUND", so an infected recovery point is marked before anyone restores it.

AWS Backup Audit Manager is a feature of AWS Backup that runs controls and produces daily reports:

  • Resources are included in at least one backup plan.
  • Vaults prevent manual deletion of recovery points (except up to five roles, here backup-admin).
  • Cross-account and cross-Region backup copies are scheduled.
  • Resources are in a backup plan with Vault Lock.
  • Resources have a recovery point in a logically air-gapped vault within, here, 7 days.
  • Restore time for resources meets the target (fed by restore testing).

Don't confuse it with AWS Audit Manager, the separate evidence-collection service, which is in maintenance and has accepted no new accounts since 30 April 2026 (Task 6.3). AWS Backup Audit Manager is part of AWS Backup and not affected.

Security Hub CSPM adds the configuration view across accounts: Backup.1 (recovery points encrypted), S3.14 (versioning), S3.15 (Object Lock, with the mode parameter), S3.7 (cross-Region replication), S3.20 (MFA delete), DynamoDB.2 (PITR), DynamoDB.4 (in a backup plan, with backupVaultLockCheck set to true to require a locked vault) and DynamoDB.6 (deletion protection), next to the KMS controls.

Step 7

Recovery into a clean account

A backup that has never been restored is a hope, not a control. AWS Backup restore testing runs scheduled restores, from chosen vaults, of the latest or a random recovery point within a selection window of up to 365 days. It records how long each restore takes and deletes the restored resources after an optional validation window of 1 to 168 hours. AWS recommends a designated account for restore tests. The company runs plans in 888888888888 against central-vault, weekly for the orders database and monthly for the rest, and the "restore time meets target" control turns the timings into evidence. The plan and selection are created with create-restore-testing-plan and create-restore-testing-selection; the restore role needs the permissions in AWSBackupServiceRolePolicyForRestores and use of the vault's key. Every quarter the recovery team also restores by hand from the shared dr-lag-vault in 141414141414, the path a real incident would use.

The isolated recovery environment in 141414141414 follows AWS's cyber recovery reference approach: no trust relationship with production, no peering or transit gateway attachment, no internet-facing resources, and AWS APIs only through VPC endpoints. Its IAM Identity Center permission set is assigned only to the recovery team; production roles have no path in. The incident response and forensics playbook decides when recovery starts. Investigation, containment and the CloudTrail timeline happen there; this page adds the recovery runbook:

  1. Contain firstRevoke the attacker's sessions and isolate 111111111111 as the forensics playbook says. Nothing is restored into it.
  2. Choose the recovery pointThe last point before the first malicious call in the CloudTrail timeline, with a clean GuardDuty Malware Protection scan.
  3. Restore in isolationIn 141414141414, from the RAM-shared dr-lag-vault, into the isolated VPC, with keys owned by the recovery account.
  4. ValidateApplication checks, data integrity checks against the replica bucket, and a vulnerability scan; the entry point (often a leaked key) is closed before anything goes live.
  5. Cut overDNS moves to the restored stack; production becomes the forensics team's evidence until the case closes.

Design decisions

Copies in a second account, not just a locked vault in production

A compliance-mode vault in production survives an administrator, but not the closure of the account, and keeps the copy under the same identity boundary as the attack. AWS's CIRT guidance and its 2026 posts both put copies in a separate account. The cost is a second copy's storage and cross-account transfer, plus a destination vault policy and key to maintain (Task 5.2).

Compliance mode for copies, governance mode for live S3 data

Compliance mode is the only setting an attacker with full rights can't undo, so it protects every copy. It is also unforgiving: a wrong retention can't be fixed and costs money for its whole life, which is why the grace time is used to check it. Live data platform objects need early deletion for privacy requests, so they get governance mode guarded by an SCP on the bypass permission.

Both a locked standard vault and an air-gapped vault

central-vault uses the company's key and supports every copy type and restore testing in the DR account; dr-lag-vault adds service-owned storage, an AWS owned key and RAM sharing to the recovery account. Both double the copy cost, accepted for production; non-prod uses only central-vault.

Delegated administrator in the DR account

Running backup policies from the management account would mean daily use of the most powerful account. The DR account is the natural owner, but whoever controls it could weaken future plans. Vault Lock protects the existing copies, policy changes go through the pipeline, and EventBridge reports any change to the policies.

Alternatives

Per-account backup plans or Control Tower's backup integration

Teams could deploy plans with StackSets, but a team can change its own plan. The Control Tower landing zone's optional backup integration sets up a central backup account, cross-Region copies and organization backup policies, a good start for new landing zones (Task 6.1). The company still adds the air-gapped vault and the SCPs itself.

Primary backups straight into a logically air-gapped vault

Since November 2025, after onboarding to multi-party approval, backups can go directly into an air-gapped vault, so there is one copy instead of two, as AWS's April 2026 post describes. Fully managed types write there directly; others still make a temporary, billed snapshot first. It cuts cost but leaves a single copy in one Region, so AWS still recommends cross-Region copies for resilience.

AWS Elastic Disaster Recovery for servers

For whole servers, Elastic Disaster Recovery keeps continuous replication and recovers to a point in time before the attack, with drills that don't disrupt replication (Task 2.2). It suits lift-and-shift servers; the company's containerized and managed services fit AWS Backup better.

Data Lifecycle Manager only

DLM snapshots EBS volumes and AMIs for free, with cross-Region copies, and cross-account sharing for snapshots under customer managed keys. But it covers only EBS, has no vault lock or air gap, and the policies live in the account under attack. It stays for the golden AMI pipeline, protected by Snapshot Lock and Recycle Bin.

"Backups that nobody can delete, not even the root user or AWS" is Vault Lock in compliance mode after the grace time (at least 3 days); "only authorized administrators may remove the lock" is governance mode. "Backups must survive a full compromise or closure of the production account" is a copy to another account, ideally a logically air-gapped vault shared through AWS RAM with a recovery account, or multi-party approval if the owner is lost. "Enforce backups in every account" is an Organizations backup policy. "Recover snapshots someone deleted" is Recycle Bin, and "stop anyone changing that rule" is a locked rule. "An attacker re-encrypted objects with their own key" points to versioning plus blocking SSE-C. "Prove restores work regularly" is AWS Backup restore testing.
