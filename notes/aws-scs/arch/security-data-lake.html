Reference architecture

Security logging and the security data lake

Detectors raise findings; logs are the evidence underneath them. This design gives the whole organization one logging system: every account and Region recorded from the day it is created, originals kept where nobody can change them, a central store the security team can search in seconds, a normalized lake for SIEMs and long hunts, and proof for the auditor that all of it is still switched on.

Scenario and requirements

The company (organization o-exampleorgid, root r-abcd) already runs the security baseline: Control Tower enrolls every account, delegated administrators sit in the security tooling account 222222222222, and the log archive account 444444444444 holds the log buckets and is the Security Lake delegated administrator. The threat detection and response page routes findings, and the incident response and forensics page queries the trail during case IR-2026-117. What was missing is the logging design itself: some logs lived only in workload accounts, the security team searched them one account at a time, and an auditor's request to prove seven years of API history were complete and unaltered took two weeks.

How it works

One log event, from the account where it happens to the analyst who reads it. Steps marked AWS happen without anyone acting.

  1. Record
  2. Activity is recorded at the sourceAWSAn API call in prod 111111111111 is captured by the organization trails; flow logs, Resolver query logs, WAF, ALB, Network Firewall and EKS audit logs capture the traffic around it.
  3. Logging is switched on everywhereAWSTelemetry enablement rules turn on VPC, DNS, WAF and EKS logging for new resources and new accounts.
  4. Keep the original
  5. Delivered to the log archiveAWSCloudTrail, flow logs, ALB, WAF and firewall logs land in S3 buckets in 444444444444, encrypted with KMS and locked in compliance mode; CloudTrail adds hourly signed digests.
  6. Centralize
  7. Copied to the central storeAWSA centralization rule copies new events from every account's log groups into the CloudWatch unified data store in 222222222222, with a backup copy in us-west-2.
  8. WORM copy of CloudWatch-only logsAWSAn account-level subscription filter streams them through Firehose to an Object Lock bucket in the log archive.
  9. Normalized into the lakeAWSSecurity Lake in 444444444444 converts native sources to OCSF Parquet and replicates us-west-2 into the rollup Region us-east-1.
  10. Use
  11. Searched and huntedSecurity teamLogs Insights on the central store, Athena on the lake through a query subscriber and on the trail bucket for exact evidence.
  12. Fed to the SIEMAWSA data access subscriber notifies the managed SIEM in 999999999999 of new objects.
  13. Prove
  14. Evidence for the auditorCompliance teamConformance pack results, validate-logs runs and the Object Lock configuration show the controls were on throughout.

Build it

Each step is deployed by the logging pipeline as log-pipeline-deploy, not by hand; Step 4 makes that the only way.

Step 1

The organization trails: what to record, and who owns them

Two trails, one job each. Control Tower's organization trail records read and write management events in every Region into the log archive account, which is also what Security Lake needs before it can collect CloudTrail management events. The second trail, org-trail, records only data events and network activity events: only the first copy of management events is free, so a second copy would be paid for twice. This matches the baseline's split (the trail by Control Tower, data events by the SRA's cloudtrail_org solution).

Who manages them. The AWS SRA says the organization trail SHOULD be managed from a CloudTrail delegated administrator, the security tooling account, with the bucket in log archive "to separate the management and usage of CloudTrail log privileges". The trail still belongs to the management account 555555555555, so its ARN and the aws:SourceArn conditions use that ID. Member accounts can't stop, change or delete organization trails.

Data events for the customer-data and data platform buckets, Lambda invocations, and endpoint calls that a VPC endpoint policy denied (AWS CLI, CloudTrail delegated administrator 222222222222) 
# Advanced selectors replace any basic selectors on the trail. No wildcards: S3 prefixes use StartsWith with a trailing slash.
# The trail's own bucket isn't selected: logging writes to it would create events about themselves.
aws cloudtrail put-event-selectors \
  --trail-name arn:aws:cloudtrail:us-east-1:555555555555:trail/org-trail \
  --advanced-event-selectors '[

      "Name": "S3 data events on sensitive buckets",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::S3::Object"] },
        { "Field": "resources.ARN", "StartsWith": ["arn:aws:s3:::customer-data-111111111111/", "arn:aws:s3:::prod-data-platform-111111111111/"] }
      ]
    },
    {
      "Name": "Lambda invocations",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::Lambda::Function"] }
      ]
    },
    {
      "Name": "S3 calls denied by an endpoint policy",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["NetworkActivity"] },
        { "Field": "eventSource", "Equals": ["s3.amazonaws.com"] },
        { "Field": "errorCode", "Equals": ["VpceAccessDenied"] }

        { "Field": "errorCode", "Equals": ["VpceAccessDenied"] }
      ]
    }
  ]'

Network activity events need one selector per event source, and VpceAccessDenied is the only error code they can filter on. Logging only denials shows outside credentials trying the company's endpoints (the data perimeter) without paying for every allowed call.

Integrity and encryption. Log file validation makes CloudTrail write an hourly signed digest of every log file's SHA-256 hash, chained to the previous digest. With a KMS key, log and (since May 2025) digest files use SSE-KMS; the key policy lets cloudtrail.amazonaws.com generate data keys for the trail's aws:SourceArn and readers decrypt only CloudTrail logs (Task 1.2), so reading needs both object and key permissions.

The full policy adds the GetBucketAcl statement and AWS's statement for AWSLogs/555555555555/ (Task 1.2). The trail also delivers to org-trail-logs for the CIS alarms (Task 1.1); that log group must be in the trail's own account, the management account, and Step 3 collects it from there.

CloudTrail Lake is closed to new customers from 31 May 2026. Existing customers get critical fixes and security updates only, and AWS points to Amazon CloudWatch instead (event data can be imported with aws logs create-import-task). Trails and Insights are unaffected. New designs query CloudTrail with Athena on S3, CloudWatch Logs or Security Lake, as here.

Step 2

Service and network logs, turned on everywhere

The AWS SRA's primary log types are the organization trail, VPC flow logs, CloudFront and WAF logs and Route 53 DNS logs. Each source has its own delivery rules, which is where most "missing logs" questions come from (Task 1.3):

  • VPC flow logs go to org-flow-logs-444444444444 in a custom format (pkt-srcaddr, tcp-flags, traffic-path), as Parquet with hourly partitions; the bucket policy admits delivery.logs.amazonaws.com with aws:SourceAccount and aws:SourceArn. Transit gateway flow logs show traffic between accounts.
  • Route 53 Resolver query logs reach every VPC through a Route 53 Profile and carry DNS Firewall actions; flow logs never show DNS traffic to the Amazon resolver.
  • WAF logs are set by a Firewall Manager policy, which the SRA says SHOULD log centrally to log archive; destinations start with aws-waf-logs-.
  • ALB access logs need a same-Region bucket with SSE-S3 only; CloudFront standard logs v2 are configured in us-east-1.
  • Network Firewall alert and flow logs go to S3; stateless-only traffic leaves no record.
  • EKS audit logs for prod-eks go to CloudWatch Logs and feed Security Lake's EKS_AUDIT source.
  • Findings: GuardDuty exports to a KMS-encrypted bucket in log archive for retention beyond 90 days, as the SRA recommends; Security Hub CSPM findings go to the lake (Step 5).
Let ALB log delivery write prod's access logs (one statement of the S3 bucket policy, org-elb-logs-444444444444-us-east-1) 
{
  "Sid": "AllowELBLogDelivery",
  "Effect": "Allow",
  "Principal": { "Service": "logdelivery.elasticloadbalancing.amazonaws.com" },
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::org-elb-logs-444444444444-us-east-1/prod/AWSLogs/111111111111/*"
}

Turning logging on everywhere. CloudWatch telemetry enablement rules from the CloudWatch delegated administrator turn on flow logs, Resolver, WAF, EKS control plane, load balancer and CloudFront logs for the organization, an OU or an account, including resources created later; OU and account rules can add to the organization rule but not reduce it. A Config rule with automatic remediation covers anything else.

Step 3

The CloudWatch unified data store in the security tooling account

What the AWS SRA now recommends. The SRA's update of 30 October 2026 changed where central log analysis lives. In its words, "Amazon CloudWatch Unified Data Store is the recommended primary option, deployed in Security Tooling account under the Security OU", and "Amazon Security Lake remains available as a secondary option for organizations with existing investments or specific subscriber-based access requirements". The security tooling account becomes the CloudWatch delegated administrator for pipelines, centralization rules and organization-wide collection. Because "CloudWatch Logs does not provide write-once-read-many (WORM) immutability", CloudWatch MUST send a copy of logs needing immutability to S3 Object Lock (compliance mode) in the log archive account, which "serves as a storage sink only". Users MUST NOT read log data directly; they use scoped grants or Lake Formation-governed S3 Tables.

The task pages and older material centralize CloudWatch Logs into the log archive account instead. The exam guide predates the October 2026 update, so recognize both; in both, the immutable originals live in log archive.

Centralization rules. A rule copies new log events from source accounts and Regions into one destination account and Region, with an optional backup Region. It is forward-only, so the SRA says to set it up early, through the landing zone. The first copy is free; each extra copy costs $0.05 per GB. Trusted access for CloudWatch must be on in Organizations.

Copy every account's security log groups from both Regions into the security tooling account, encrypted with its own key (AWS CLI, CloudWatch delegated administrator 222222222222) 
# Scope keys: OrganizationId, OrganizationalUnitId, AccountId. The organization scope includes the management account, home of org-trail-logs.
# The destination key must carry the tag LogsManaged = true so the centralization service can use it.
aws observabilityadmin create-centralization-rule-for-organization \
  --rule-name org-security-logs \
  --rule '{
    "Source": {
      "Regions": ["us-east-1", "us-west-2"],
      "Scope": "OrganizationId = '\''o-exampleorgid'\''",
      "SourceLogsConfiguration": {
        "LogGroupSelectionCriteria": "LogGroupName LIKE '\''org-trail-logs%'\'' OR LogGroupName LIKE '\''/aws/eks/%'\'' OR LogGroupName LIKE '\''aws-waf-logs-%'\'' OR LogGroupName LIKE '\''/prod/%'\''",
        "EncryptedLogGroupStrategy": "ALLOW"
      }
    },
    "Destination": {
      "Region": "us-east-1",
      "Account": "222222222222",
      "DestinationLogsConfiguration": {
        "LogsEncryptionConfiguration": {
          "EncryptionStrategy": "CUSTOMER_MANAGED",
          "KmsKeyArn": "arn:aws:kms:us-east-1:222222222222:key/TOOLING_LOGS_KEY_ID",
          "EncryptionScope": "NEW_DESTINATION_LOG_GROUPS"
        },
        "BackupConfiguration": { "Region": "us-west-2" },
        "LogGroupNameConfiguration": { "LogGroupNamePattern": "/central/${source.accountId}/${source.region}${source.logGroup}" },
        "LogGroupDeletionProtection": "ENABLED"
      }
    }
  }'

Without the name pattern, same-named groups from every account merge into one. ALLOW copies groups under customer managed keys too, so those keys must allow CloudWatch Logs. Deletion protection covers only groups the rule creates after it is set.

Pipelines and OCSF. The SRA also uses CloudWatch pipelines to collect AWS vended logs and third-party sources and convert them to OCSF with the built-in processor; for a few log groups, a parseToOCSF transformer does the same and keeps the original event (Task 1.2).

The WORM copy. S3 deliveries are already locked (Step 4), so the copy is needed only for logs whose only home is CloudWatch: agent, EKS audit and Lambda logs. The SRA names no mechanism; the company uses an account-level subscription filter in security tooling (these work on centralized log groups) to the Firehose stream cwl-to-archive, which writes to org-cwl-archive-444444444444.

Stream every log group in the security tooling account to the archive stream, except the stream's own error logs (AWS CLI, 222222222222) 
# One account-level subscription filter per Region; only Standard log groups can be subscribed.
aws logs put-account-policy \
  --policy-name worm-archive-feed \
  --policy-type SUBSCRIPTION_FILTER_POLICY \
  --scope ALL \
  --selection-criteria 'LogGroupName NOT IN ["/aws/kinesisfirehose/cwl-to-archive"]' \
  --policy-document '{"DestinationArn": "arn:aws:firehose:us-east-1:222222222222:deliverystream/cwl-to-archive", "RoleArn": "arn:aws:iam::222222222222:role/CWLtoFirehoseRole", "FilterPattern": ""}'

Excluding the stream's own log group avoids a loop; dynamic partitioning, set when the stream is created, writes by account and date.

Step 4

The immutable archive and the guardrails around it

The SRA's first objective for the log archive account is that log storage MUST be immutable, with access limited to controlled, automated and monitored mechanisms. Four layers do that here.

S3 Object Lock in compliance mode. The log buckets are created with Object Lock (and so versioning) and a default retention: seven years for CloudTrail, one year for the others. Nobody, the root user included, can delete or overwrite a locked version or shorten its retention; the only early way out is closing the account, so settings are tried in governance mode on a test bucket first.

Seven-year compliance-mode default on the trail bucket, then lifecycle to Glacier storage classes (AWS CLI, log archive account 444444444444) 
aws s3api create-bucket \
  --bucket org-cloudtrail-444444444444 \
  --region us-east-1 \
  --object-lock-enabled-for-bucket

aws s3api put-object-lock-configuration \
  --bucket org-cloudtrail-444444444444 \
  --object-lock-configuration '{ "ObjectLockEnabled": "Enabled", "Rule": { "DefaultRetention": { "Mode": "COMPLIANCE", "Years": 7 }}}'

# lifecycle.json: Glacier Instant Retrieval at 90 days, Deep Archive at 1 year, expire after 7 years (2557 days)
aws s3api put-bucket-lifecycle-configuration \
  --bucket org-cloudtrail-444444444444 \
  --lifecycle-configuration file://lifecycle.json

Locks win: an expiration only adds a delete marker until retention ends (lifecycle JSON on Task 5.2). Default encryption is SSE-KMS with ARCHIVE_KEY_ID and an S3 Bucket Key, which cuts KMS request costs for millions of small objects.

No MFA delete. Only the root user can enable it, only through the CLI or API, and never on a bucket with lifecycle rules, which every log bucket needs.

The key is part of the archive. A deleted or disabled key makes locked logs unreadable and stops CloudTrail delivering. Only logging services may encrypt, reader roles decrypt, and log-pipeline-deploy administer it.

SCPs. The baseline SCP on the root already denies cloudtrail:StopLogging and cloudtrail:DeleteTrail (security baseline, Step 4). SCPs don't apply to the management account, and member accounts can't change organization trails anyway; the gap is the rest of the Security OU, including the trail's delegated administrator, so a second SCP goes on ou-abcd-66666666:

Only the logging pipeline may change trails, log buckets, the lake, log retention or the log keys in the Security OU (SCP, attached to ou-abcd-66666666)

Step 5

Amazon Security Lake in the log archive account

Where it lives, and why. The baseline registered 444444444444 as the Security Lake delegated administrator with register-data-lake-delegated-administrator (removing it deletes the lake). The SCS guide and the SRA agree on the account: the SRA says it SHOULD be log archive, next to the other security logs. What changed is its role: since October 2026 it is the SRA's secondary option, for existing deployments or subscriber-based access. The company keeps it because its managed SIEM ingests Security Lake natively and analysts want OCSF tables for long hunts.

Enable the lake in both Regions with a customer managed key, keep a year of data, and roll us-west-2 up into us-east-1 (AWS CLI, Security Lake delegated administrator 444444444444) 
aws securitylake create-data-lake \
  --configurations '[
    {"region": "us-east-1",
     "encryptionConfiguration": {"kmsKeyId": "LAKE_KEY_ID"},
     "lifecycleConfiguration": {"expiration": {"days": 365}, "transitions": [{"days": 30, "storageClass": "ONEZONE_IA"}]}},
    {"region": "us-west-2",
     "encryptionConfiguration": {"kmsKeyId": "LAKE_KEY_ID"},
     "lifecycleConfiguration": {"expiration": {"days": 30}},
     "replicationConfiguration": {"regions": ["us-east-1"], "roleArn": "arn:aws:iam::444444444444:role/SecurityLakeReplicationRole"}}
  ]' \
  --meta-store-manager-role-arn arn:aws:iam::444444444444:role/service-role/AmazonSecurityLakeMetaStoreManager

Retention and transitions are set per Region in Security Lake, never with S3 lifecycle rules on its buckets, which can remove its metadata. us-west-2 keeps 30 days; the rollup Region a year. One Zone-IA sits in a single Availability Zone, acceptable for an analysis copy. The replication role name is new on this page. Security Lake doesn't support Object Lock (a default retention interrupts delivery), so the originals stay in Step 4's buckets.

Step 6

Query it: Logs Insights, Athena on the lake, Athena on the trail

Logs Insights, for minutes-old events. Logs Insights (QL, PPL or SQL, charged per GB scanned) queries many central log groups at once, so the Task 1.2 AccessDenied query runs once instead of in each account.

Athena on the lake, for normalized hunts. Version 2 tables are in the Glue Data Catalog, partitioned on time_dt, region and accountid; the caller needs Lake Formation SELECT. OCSF field names are shared across sources, so the attacker IP from case IR-2026-117 is one value to search:

Everything one IP did against AWS APIs in the last 30 days, every account (Athena SQL, query subscriber 222222222222, CloudTrail management events, source version 2) 
SELECT time_dt, accountid, region, api.service.name, api.operation,
       api.response.error, actor.user.uid, http_request.user_agent
FROM "amazon_security_lake_glue_db_us_east_1"."amazon_security_lake_table_us_east_1_cloud_trail_mgmt_2_0"
WHERE time_dt > CURRENT_TIMESTAMP - INTERVAL '30' DAY
  AND src_endpoint.ip = '198.51.100.7'
ORDER BY time_dt DESC
LIMIT 100;

The same filter works on vpc_flow_2_0 and route53_2_0, and the version 2 observables array finds an indicator wherever it appears. Keep time filters inside the retention window.

Athena on the trail bucket, for exact evidence. The evidential copy is the original CloudTrail JSON in the locked bucket. The Task 1.2 table covers one account and Region; projecting account and Region as well as date makes one table cover the organization, with no partitions to add:

  'projection.enabled' = 'true',
  'projection.account.type' = 'enum',
  'projection.account.values' = '111111111111,222222222222,333333333333,444444444444,555555555555',

The account vending pipeline extends the account list. Athena charges per TB scanned, so the date filter is the cost control. Investigation queries on this table are on the forensics page and Task 2.2.

Step 7

When logs go missing

Every delivery path can break silently. Use the Task 1.3 order: is it on, is the writer allowed, is it going where you're looking, does the consumer match, has it had time. Here the likely causes are:

  • CloudTrail to S3: a changed bucket or key policy, shown by get-trail-status.
  • Flow logs: DeliverLogsErrorMessage in describe-flow-logs; "undeliverable" when the bucket's default key is a key ID, not an ARN.
  • Vended logs to CloudWatch: a missing resource policy for delivery.logs.amazonaws.com (10 per Region per account).
  • Centralization: rule health UNHEALTHY with a FailureReason, typically a destination key without CloudWatch Logs permissions or the LogsManaged = true tag, DestinationEncryptionMismatch, trusted access off, or selection criteria that miss the group. Alarm on CentralizationError and IncomingCopiedBytes.
  • The WORM feed: an Essentials (formerly Infrequent Access) log group can't be subscribed, and its class can't be changed.
  • Security Lake: management events stop when their trail stops; Object Lock or lifecycle rules on its bucket break delivery.
The org trail's status, checked from a member account with the trail's full ARN (AWS CLI; status is per Region) 
aws cloudtrail get-trail-status \
  --name arn:aws:cloudtrail:us-east-1:555555555555:trail/org-trail \
  --region us-east-1

# In the output: IsLogging, LatestDeliveryError (S3: bucket or key policy), LatestDigestDeliveryError,
# LatestNotificationError (SNS topic policy) and LatestCloudWatchLogsDeliveryError (role or log group)

CloudTrail retries a misconfigured bucket for 30 days, and charges for it. The trail shows who made the PutBucketPolicy or PutKeyPolicy call, Config shows the previous configuration, and the Step 4 SCP prevents a repeat.

Design decisions

Store the record in log archive, analyse in security tooling

The log archive account holds data and nothing else, so its few administrators aren't the people whose actions the logs record; analysis and its users live in security tooling. The cost is cross-account plumbing: bucket and key policies, RAM shares, cross-account Firehose delivery.

CloudWatch as primary, Security Lake kept for its subscribers

Following the SRA's October 2026 update, searches run in CloudWatch, where alarms and Logs Insights already are. The lake stays because it feeds the SIEM without a custom pipeline. Running both stores some logs twice; without a Security Lake-native SIEM the company would drop the lake.

Compliance mode with lifecycle, not MFA delete

Compliance mode stops even root and works with lifecycle rules; MFA delete needs root and rules lifecycle out. The trade is irreversibility, hence governance-mode testing and the pipeline.

Cost

The large items are CloudWatch ingestion (Essentials ingests at half the price but can't feed subscriptions or metric filters), extra centralization copies, data events ($0.10 per 100,000, so only sensitive buckets are selected; the CloudTrail Data Event Coverage console page shows what is left out), Security Lake normalization and Athena scans ($5 per TB in AWS's examples). Controls: Parquet, partition projection, Bucket Keys, Glacier and lake transitions, and the CloudWatch Logs Intelligent Tiering the SRA suggests.

Alternatives

Security Lake as the primary store

The pre-October 2026 SRA pattern most exam material assumes: everything normalized in log archive, consumed through subscribers. Near-real-time alarms still need CloudWatch Logs.

Subscription filters to a destination in log archive

The older pattern from Task 1.2: a CloudWatch Logs destination with an aws:PrincipalOrgID policy and an account-level subscription filter in every account. It fits streaming to a third-party tool; centralization rules need nothing in source accounts.

OpenSearch Service as the SIEM

A Security Lake ingestion blueprint, Sigma rules in Security Analytics and direct query over CloudWatch Logs and Security Lake, if detection engineering moves in-house.
