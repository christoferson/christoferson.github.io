Reference architecture

Centralized threat detection and automated response

Every detector in the organization already reports to the security tooling account. This design turns that stream of findings into action: tuned so that people only see what matters, routed by EventBridge to the right responder, and answered by playbooks that contain the common incidents in minutes, with a human approving anything destructive.

Scenario and requirements

The company (organization o-exampleorgid) finished its multi-account security baseline: GuardDuty, Security Hub CSPM, Inspector, Macie, Detective, Config and Access Analyzer are delegated to the security tooling account 222222222222 and auto-enabled in every account and governed Region, with us-east-1 as the aggregation Region. That page ends where this one starts: findings exist. The team gets several hundred a week, most low severity or expected, and the last real incident (stolen instance credentials in production 111111111111, Task 2.2) took hours to contain because every step was manual.

How it works

The path from a detector's first signal to a closed incident, using a high-severity GuardDuty finding on a production instance as the example. Steps marked AWS happen without anyone acting.

  1. Detect
  2. A detector raises a findingAWSGuardDuty in 111111111111 sees the instance talking to a known command-and-control host and raises a High finding with resource type Instance. Inspector, Macie, Access Analyzer and Security Hub CSPM controls do the same in each member account and Region.
  3. Findings reach the security tooling accountAWSThe GuardDuty administrator 222222222222 sees the member finding, and its EventBridge default bus in that Region receives a GuardDuty Finding event. Security Hub CSPM imports the same finding in ASFF and replicates it to the home Region us-east-1.
  4. Triage
  5. Noise removed at the sourceAWSSuppression rules archive known false positives; Security Hub CSPM automation rules escalate production findings and suppress sandbox ones.
  6. CorrelationAWSGuardDuty Extended Threat Detection may link this finding with others into a Critical attack sequence; the new AWS Security Hub correlates it with Inspector vulnerabilities and reachability into an exposure finding.
  7. Route
  8. EventBridge rules matchAWSIn 222222222222, a rule for High and Critical findings on instances starts the ec2-compromise-response workflow; another sends a short message to security-alerts, which posts to the team's Slack channel.
  9. Respond
  10. Evidence firstAWSThe workflow skips sample findings and exempt instances, then tags the instance with a case ID, turns on termination protection and snapshots every volume, using a role in the workload account.
  11. Approve containmentOn-call responderThe responder approves isolation from chat (or rejects it as a false positive), returning the task token to Step Functions.
  12. ContainAWSThe instance's security groups are replaced with the isolation group; the finding's workflow status is set to NOTIFIED and a ticket is opened.
  13. Investigate and hand offSecurity teamDetective shows what the instance role did before and after the finding; the snapshots and case go to the forensics account 666666666666, as described on the incident response and forensics page.
  14. Learn
  15. Close and measureSecurity teamThe finding is resolved (or marked false positive, which feeds a suppression rule); time to detect, contain and close is recorded for the playbook.

Build it

Everything below runs in the security tooling account 222222222222 unless a step says otherwise, and is repeated in us-west-2 where the service is Regional. Enabling and delegating the services is on the security baseline page and Task 1.1.

Step 1

Tune findings at the source

A rule that isolates instances on every High finding will isolate the vulnerability scanner every week. Tuning happens in two places, both administrator-only, so member accounts can't hide their own findings.

GuardDuty. First decide what to detect. Foundational detection (CloudTrail management events, VPC Flow Logs and DNS logs) is always on; the company also runs S3 Protection for the data platform, EKS Protection and Runtime Monitoring for the containers, Malware Protection for EC2 and for S3 uploads, RDS Protection and Lambda Protection, and AI Protection for the assistant (Task 1.1). These plans also widen what Extended Threat Detection correlates into attack sequences (always Critical, no extra cost).

Then remove known noise. GuardDuty advises suppression rules only for repeatedly confirmed false positives, with at least two criteria. A suppression rule is a saved filter with the action ARCHIVE; its findings are not sent to Security Hub CSPM, EventBridge, S3 or Detective, and are not used as attack sequence signals, so a broad rule blinds the whole pipeline.

Suppress port scan findings from the approved scanner image only (AWS CLI, GuardDuty administrator, per Region) 
# Two criteria: the finding type AND the scanner's AMI. Without --action ARCHIVE this would only be a saved filter.
aws guardduty create-filter \
  --detector-id 12abc34d567e8fa901bc2d34EXAMPLE \
  --name suppress-approved-scanner \
  --action ARCHIVE \
  --rank 1 \
  --finding-criteria '{"Criterion": {"type": {"Eq": ["Recon:EC2/Portscan"]}, "resource.instanceDetails.imageId": {"Eq": ["ami-0a7a207083example"]}}}'

For traffic to a known-good public address (a partner's API, the company's on-premises egress), a trusted entity list (IPs and domains, since August 2025) stops GuardDuty generating those findings at all. Each account and Region allows one trusted entity list and one trusted IP list; the administrator's lists apply to every member.

Security Hub CSPM. Automation rules change findings as they arrive, before any EventBridge rule sees them. They are created in the administrator account per Region (up to 100) and act only on findings imported after the rule exists. The company uses three: escalate MEDIUM findings on env=prod resources to HIGH, suppress findings from the sandbox 333333333333, and note known exceptions.

Escalate production findings so that routing treats them as urgent (AWS CLI, Security Hub CSPM administrator, us-east-1) 
aws securityhub create-automation-rule \
  --rule-name "escalate-prod-medium" \
  --rule-order 10 \
  --rule-status ENABLED \
  --description "Medium findings on prod-tagged resources become High" \
  --criteria '{"ResourceTags": [{"Key": "env", "Value": "prod", "Comparison": "EQUALS"}], "SeverityLabel": [{"Value": "MEDIUM", "Comparison": "EQUALS"}]}' \
  --actions '[{"Type": "FINDING_FIELDS_UPDATE", "FindingFieldsUpdate": {"Severity": {"Label": "HIGH"}, "Note": {"Text": "Escalated: production resource", "UpdatedBy": "automation-rule-escalate-prod-medium"}}}]'

Lower rule order numbers apply first and the highest has the last word. An irrelevant control is disabled in the central configuration policy instead, which stops checks and charges; suppressing its findings keeps paying for them.

Two Security Hubs. The original service is now AWS Security Hub CSPM: same securityhub API, standards, controls, ASFF findings and Security Hub Findings - Imported events. The newer AWS Security Hub (generally available since 2 December 2025) turns CSPM on, reads its results, and correlates them with Inspector, GuardDuty and Macie signals into exposure findings in OCSF format, with its own event type (Findings Imported V2), its own automation rules and outbound ticketing to Jira Cloud and ServiceNow. It doesn't accept third-party findings. This page routes on CSPM events and uses the new Security Hub to prioritize exposures.

Step 2

Route findings in the security tooling account: notify and ticket

No organization-wide bus is needed for findings. EventBridge rules in the GuardDuty administrator account fire for member findings, and in the Security Hub CSPM administrator's home Region the Imported events include every member and linked Region. So the rules live on the default bus of 222222222222: GuardDuty rules in each governed Region (its events stay Regional), Security Hub CSPM rules once in us-east-1. The security-events bus stays for sources with no delegated administrator, such as application events; detail.accountId identifies the member account.

Rule 1: High and Critical GuardDuty findings on EC2 instances start the containment workflow (EventBridge event pattern) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }],
    "resource": { "resourceType": ["Instance"] }
  }
}
Rule 2: every attack sequence pages the on-call responder, whatever the resource (EventBridge event pattern) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "type": [{ "prefix": "AttackSequence:" }]
  }
}

Notifications go to the security-alerts topic, delivered to Slack by Amazon Q Developer in chat applications. An input transformer keeps the message to severity, type, account, Region and a console link, as a single-line JSON template because GuardDuty's description can contain control characters. An encrypted topic needs a customer managed key that EventBridge may use (Task 1.3).

Findings that need an owner become tickets, fed from Security Hub CSPM, which carries GuardDuty, Inspector, Macie, Access Analyzer and control findings in one format after the automation rules have adjusted them.

Rule 3: new, active High and Critical Security Hub CSPM findings go to the ticketing function (EventBridge event pattern, us-east-1) 
{
  "source": ["aws.securityhub"],
  "detail-type": ["Security Hub Findings - Imported"],
  "detail": {
    "findings": {
      "Severity": { "Label": ["HIGH", "CRITICAL"] },
      "Workflow": { "Status": ["NEW"] },
      "RecordState": ["ACTIVE"]
    }
  }
}

The Workflow.Status filter matters: every BatchUpdateFindings call also sends an Imported event, so once the ticketing function sets NOTIFIED, later updates don't open a second ticket. Analysts can also use the send_to_ticketing custom action (Task 1.1), and OpsCenter can create OpsItems with runbooks attached (Task 2.1).

A rule that "never fires" usually has one of three causes: it is in the wrong Region (GuardDuty events stay in their Region; AWS Health global events appear only in us-east-1), the pattern doesn't match the real event (test it with aws events test-event-pattern), or the finding was archived by a suppression rule and never sent.

Step 3

Posture findings: Automated Security Response and the public bucket playbook

Most findings are misconfigurations, not attacks. Rather than writing a runbook per control, the company deploys Automated Security Response on AWS (ASR, formerly SHARR), an AWS Solution maintained by AWS, currently version 4.1.1. Version 3 added a web UI and support for the new Security Hub; version 4 added remediation of GuardDuty, Inspector and Macie findings in both ASFF and OCSF form.

It deploys as three CloudFormation templates:

  • Admin stack (automated-security-response-admin.template) in the Security Hub administrator 222222222222: the orchestrator Step Functions workflow, optional web UI, and a nested stack per playbook. The company selects only the Security Controls (SC) playbook, recommended with consolidated control findings.
  • Member roles (automated-security-response-member-roles.template): the remediation roles in each member account.
  • Member stack (automated-security-response-member.template): the Systems Manager Automation runbooks and permissions in each member account, including the admin account.

Both member templates go out with service-managed StackSets to the Workloads OU ou-abcd-33333333, so every new account gets them (Task 6.2). Remediations start from the CSPM Actions menu, the web UI or the API; a few low-risk controls get fully automated remediation. Rollback is off by default, and remediating a stack-owned resource causes drift, so the template is fixed too.

Public bucket playbook. The baseline's S3 organization policy already forces Block Public Access, so this is the safety net for Exceptions OU accounts and rollout gaps, and the attempt itself is a signal. GuardDuty raises Policy:S3/BucketBlockPublicAccessDisabled (Low) and Policy:S3/BucketAnonymousAccessGranted (High) from CloudTrail management events, with no S3 Protection needed; Macie raises policy findings for the same changes.

Rule 4: someone opened a bucket to the internet or removed its Block Public Access (EventBridge event pattern) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "type": ["Policy:S3/BucketAnonymousAccessGranted", "Policy:S3/BucketBlockPublicAccessDisabled", "Policy:S3/BucketPublicAccessGranted"]
  }
}

The target is a Lambda function: one quick, reversible action needs no approval. It reads the bucket from detail.resource.s3BucketDetails and the account from detail.accountId, assumes IRAutomationRole there, turns Block Public Access back on and tells the bucket owner:

What the responder function does in the workload account (AWS CLI equivalent) 
# All four settings; existing public policies and ACLs stop working at once
aws s3api put-public-access-block \
  --bucket prod-data-platform-111111111111 \
  --public-access-block-configuration "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true" \
  --expected-bucket-owner 111111111111

Whether sensitive data was exposed (Macie sensitive data findings, S3 data events) is an investigation, not something to automate.

Step 4

Compromised EC2 instance: evidence, approval, isolation, hand-off

This is Task 2.2's playbook automated. The order matters more than the tools: preserve before you isolate, because stopping an instance erases memory and instance store. The security group swap doesn't cut tracked connections, so a live reverse shell may survive it; a network ACL deny ends a session at once.

The runbook lives in each workload account (deployed by StackSets) because aws:approve isn't supported in executions spanning several accounts or Regions. Responders run it from an OpsItem; the approval topic name must start with Automation.

IR-IsolateInstance, this page's version: tag, protect and snapshot first, then wait for approval, then isolate (Automation runbook, YAML, workload account) 
description: Preserve evidence from an instance, then isolate it after a responder approves.
schemaVersion: '0.3'
assumeRole: '{{ AutomationAssumeRole }}'
parameters:
  AutomationAssumeRole:
    type: String
  InstanceId:
    type: String
  IsolationGroupId:
    type: String
  CaseId:
    type: String
mainSteps:
  - name: tagInstance
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: CreateTags
      Resources:
        - '{{ InstanceId }}'
      Tags:
        - Key: ir-case
          Value: '{{ CaseId }}'
  - name: protectInstance
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: ModifyInstanceAttribute
      InstanceId: '{{ InstanceId }}'
      DisableApiTermination:
        Value: true
  - name: snapshotVolumes
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: CreateSnapshots
      InstanceSpecification:
        InstanceId: '{{ InstanceId }}'
      Description: 'IR evidence {{ CaseId }}'
      CopyTagsFromSource: volume
  - name: approveIsolation
    action: aws:approve
    # an unanswered request aborts after an hour (default 7 days)
    timeoutSeconds: 3600
    onFailure: Abort
    inputs:
      NotificationArn: arn:aws:sns:us-east-1:111111111111:AutomationIRApprovals
      Message: 'Evidence captured for {{ InstanceId }} ({{ CaseId }}). Isolate it now?'
      MinRequiredApprovals: 1
      Approvers:
        - arn:aws:iam::111111111111:role/IncidentResponder
  - name: isolateInstance
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: ModifyInstanceAttribute
      InstanceId: '{{ InstanceId }}'
      Groups:
        - '{{ IsolationGroupId }}'
    isEnd: true

The automatic path from Rule 1 is the ec2-compromise-response Standard workflow in the security tooling account, built as on Task 2.1. A first Lambda state drops sample findings (marked in the finding's additional information) and exempt instances; the evidence steps run through IRAutomationRole in the finding's account; then an sns:publish.waitForTaskToken task to ir-approvals pauses until the approval link returns the token. After an hour unanswered, the workflow escalates to the incident lead instead of isolating.

Rule 1's target: pass only what the workflow needs (EventBridge targets file for put-targets) 
[
  {
    "Id": "ec2-compromise-response",
    "Arn": "arn:aws:states:us-east-1:222222222222:stateMachine:ec2-compromise-response",
    "RoleArn": "arn:aws:iam::222222222222:role/EventBridgeStartIRWorkflows",
    "InputTransformer": {
      "InputPathsMap": {
        "account": "$.detail.accountId",
        "instance": "$.detail.resource.instanceDetails.instanceId",
        "finding": "$.detail.id",
        "type": "$.detail.type"
      },
      "InputTemplate": "{\"accountId\": <account>, \"instanceId\": <instance>, \"findingId\": <finding>, \"findingType\": <type>}"
    }
  }
]
What the approval handler sends back to the paused workflow (AWS CLI equivalent) 
# The token arrived in the SNS message; the output becomes the result of the approval state
aws stepfunctions send-task-success \
  --task-token "$TASK_TOKEN" \
  --task-output '{"approved": true, "approver": "oncall-responder"}'

Then the case leaves this design: Detective compares the instance role's activity with its 45-day baseline, and snapshot sharing and analysis happen in the forensics account 666666666666 (the incident response and forensics page; Task 2.2). Memory has to be captured before the isolation state, because Systems Manager can no longer reach the instance through the isolation group; that page adds the capture step to this workflow, alongside the snapshots.

Step 5

Exposed IAM access key

Exposed long-term keys are the top entry point AWS's responders see. When AWS finds a key in a public repository, AWS Health raises AWS_RISK_CREDENTIALS_EXPOSED, and AWS attaches AWSCompromisedKeyQuarantineV3 to the user and opens a support case. The quarantine limits the damage; it doesn't fix it.

IAM is global, so its Health events appear only in us-east-1. With the organizational view delegated to 222222222222, member events arrive on that account's bus and one rule covers the organization.

Rule 5: AWS found one of our access keys in public (EventBridge event pattern, us-east-1, security tooling account) 
{
  "source": ["aws.health"],
  "detail-type": ["AWS Health Event"],
  "detail": {
    "service": ["RISK"],
    "eventTypeCode": ["AWS_RISK_CREDENTIALS_EXPOSED"]
  }
}

The target is a Lambda function, since each action is quick and safe without approval. It reads detail.affectedAccount and detail.affectedEntities, assumes IRAutomationRole in that account, and deactivates the key (reversible, keeps the key ID, and kills presigned URLs it signed). It then denies sessions issued before now, because temporary credentials made with the key outlive it, and posts the key's recent CloudTrail activity to the case.

Deactivate the key and deny older sessions for the user (AWS CLI equivalent, workload account) 
aws iam update-access-key --user-name app-user --access-key-id AKIAIOSFODNN7EXAMPLE --status Inactive

# deny-older-sessions.json denies "*" when aws:TokenIssueTime is before the moment of containment
aws iam put-user-policy \
  --user-name app-user \
  --policy-name ir-revoke-older-sessions \
  --policy-document file://deny-older-sessions.json
deny-older-sessions.json (IAM inline policy; the time is set by the function) 
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Deny",
    "Action": "*",
    "Resource": "*",
    "Condition": {
      "DateLessThan": { "aws:TokenIssueTime": "2026-11-16T09:15:00Z" }
    }
  }
}

The function leaves the quarantine policy alone, as AWS instructs. Eradication in every Region and replacing the key with a role belong to the responders (Task 2.2); for a role, revoke sessions attaches AWSRevokeOlderSessions instead.

Step 6

Crypto-mining on EKS

Runtime Monitoring's agent on prod-eks reports process activity, and a miner starting in a pod raises Impact:Runtime/CryptoMinerExecuted or CryptoCurrency:Runtime/BitcoinTool.B. The finding names the cluster (eksClusterDetails), the workload and its namespace (kubernetesDetails), the container and the process. Related signals may become AttackSequence:EKS/CompromisedCluster, which Rule 2 pages on. Runtime fields can be attacker-controlled, so the notifier encodes them before display.

Rule 6: mining in a container (EventBridge event pattern) 
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "type": ["Impact:Runtime/CryptoMinerExecuted", "CryptoCurrency:Runtime/BitcoinTool.B"]
  }
}

Following AWS's EKS guidance: label the pod so the pre-staged deny-all NetworkPolicy from Task 2.2 isolates it, cordon the node, and keep the pod running for evidence. If one pod of a Deployment is compromised, assume all are. Rule 6 opens a case and pages the on-call responder, who runs these commands once the containment is approved.

Quarantine the pod and the node (kubectl, responder access to prod-eks) 
# the ir-deny-all NetworkPolicy selects pods labelled status=quarantine
kubectl label pod POD_NAME -n shop status=quarantine

# find the node, then stop new pods landing on it
kubectl get pods POD_NAME -n shop -o=jsonpath='{.spec.nodeName}'
kubectl cordon NODE_NAME

A privileged container or node-level identity means the node is compromised and a network policy won't help: the node goes through Step 4 and its role loses its permissions. Fargate pods can't be cordoned. Eradication means rebuilding from a clean image, using Inspector to find how it was exploited, and hunting for new instances, keys or roles in unused Regions.

Design decisions

Rules in the administrator account, not in every member

One set of rules in 222222222222 covers the organization, including future accounts, and member administrators can't change it. The cost is a response role in every workload account: IRAutomationRole, deployed by StackSets, trusting only the security tooling account's automation roles, and protected by an SCP.

Automate by blast radius and reversibility

The company sorts actions into three groups. Fully automatic: reversible, narrow actions (Block Public Access on one bucket, deactivating one key, denying old sessions). Automatic evidence, human approval: anything that affects a running workload (isolating an instance, cordoning a node). Human only: destructive steps (terminating, deleting users, rotating shared secrets). This matches AWS's guidance that playbook steps become automation once they have proved consistent.

Where the approval lives

Step Functions with a task token is the main path: it runs in one account, waits up to a year in a Standard workflow, branches on rejection or timeout, and the approval can come from chat or a ticket. A runbook with aws:approve is the single-account path that responders start from OpsCenter; it is simpler, but approvers are listed as IAM principals and it can't be used in multi-account executions.

Route on Security Hub CSPM for tickets, on GuardDuty for threats

Threat playbooks take GuardDuty events directly: near real time, with the detail they need. Tickets come from Security Hub CSPM, where every source looks the same after the automation rules. GuardDuty alone would miss Inspector, Macie and control findings.

ASR for posture, own code for threats

ASR gives AWS-maintained remediations for many Security Hub CSPM controls, so the company writes none of those. Threat playbooks depend on the company's account layout, forensics process and approval rules, so they are the company's own code, kept small and tested every quarter.

Cost

GuardDuty protection plans are priced separately, and CloudWatch usage metrics for each plan show what they process, so the company reviews them before adding plans in Regions it doesn't use (foundational detection stays on everywhere). Security Hub CSPM charges per check and per finding ingested beyond the free tier, and for automation rule evaluations beyond the first million; the new Security Hub is priced per resource unit.

Alternatives

AWS Security Incident Response

The managed service triages GuardDuty findings and third-party findings that arrive through Security Hub CSPM, opens cases, and gives access to AWS responders 24 hours a day. Its containment runbooks (AWSSupport-ContainEC2Instance, AWSSupport-ContainIAMPrincipal, AWSSupport-ContainS3Resource) are reversible and default to a dry run. It suits a team without round-the-clock cover, and can sit alongside this design; it doesn't do disk or memory forensics or recovery.

An organization event bus

Member accounts could forward GuardDuty events to the security-events bus, but that duplicates the delegated administrator's feed and needs a rule in every account and Region.

A SIEM over Security Lake

Security Lake normalizes logs and Security Hub CSPM findings into OCSF for a SIEM or Athena, which suits correlation with non-AWS sources and long retention. It is analysis, not response; this design's playbooks still start from EventBridge. The security data lake page covers it.

Testing it

  1. Check every pattern against a real eventSave a sample event for each rule (the EventBridge console offers a GuardDuty Finding sample event) and run aws events test-event-pattern --event-pattern file://rule1.json --event file://sample-finding.json; it returns {"Result": true} or false. Check a non-matching event for each rule as well.
  2. Fire sample findings end to endIn the test account 101010101010, aws guardduty create-sample-findings --detector-id DETECTOR_ID --finding-types Backdoor:EC2/C&CActivity.B generates a finding marked [SAMPLE]. It must reach chat, open a ticket and start the workflow, and the workflow must stop at its first state because the finding is a sample. Then run once with the sample check off against a test instance, to prove isolation works.
  3. Generate real findingsThe GuardDuty tester (awslabs/amazon-guardduty-tester) produces real findings in a dedicated non-production account; it may enable protection plans, so only the test account is used.
  4. Check the tuningAfter creating a suppression rule, a matching sample finding must not appear in EventBridge or Security Hub CSPM, and a finding with only one of the two criteria still must. A finding on a env=prod resource must arrive in CSPM as HIGH.
  5. Game dayEvery quarter the team runs the four playbooks against non-production workloads, with an FIS experiment running the isolation runbook while the application is under load (Task 2.1). A tabletop covers who approves at night and when to engage AWS.
  6. MeasureFor each playbook: time from finding creation to containment (from the finding's createdAt and the workflow's end), time to close, and the share of findings closed as false positives (a finding's VerificationState of FALSE_POSITIVE). A rising false positive rate means a suppression rule or trusted list is due; containments that time out waiting for approval mean the on-call process needs work.

"Automatically respond to GuardDuty findings across all accounts with the least operational overhead" is an EventBridge rule in the GuardDuty delegated administrator account with a Lambda, Step Functions or Automation target, not a rule in every member account. "A person must approve before the instance is isolated" is Step Functions with .waitForTaskToken or a runbook with aws:approve. "Remediate Security Hub control findings with AWS-maintained playbooks" is Automated Security Response on AWS. "An access key was published on GitHub" is an EventBridge rule on AWS_RISK_CREDENTIALS_EXPOSED in us-east-1 that deactivates the key. "Stop a scanner's findings without hiding real attacks" is a suppression rule with two criteria or a trusted list, not disabling GuardDuty or a broad filter.
