Reference architecture

Data perimeter across the organization

Only trusted identities, reaching only trusted resources, from only expected networks: three organization-wide guardrails that hold whatever individual teams write in their IAM and resource policies. Resource control policies, service control policies and VPC endpoint policies each enforce one side, and together they cover every direction.

Scenario and requirements

The company (organization o-exampleorgid) runs its web app, EKS containers, S3 data platform and GenAI assistant in production account 111111111111. The data platform bucket shop-data-111111111111 uses a customer managed KMS key; the analytics account 777777777777 reads it with the analytics-etl role, and the vendor 999999999999 collects a daily export. Workload VPCs connect through a transit gateway in the shared network account, with central egress through NAT gateways and Network Firewall.

A review found three ways data could leave despite tidy IAM policies: a wildcard bucket policy, pod credentials stolen through a request forgery bug and replayed from the internet, and an engineer copying objects to a personal bucket.

How it works

Each objective has an identity side and a resource side. SCPs apply to principals in member accounts, RCPs to resources in member accounts, and endpoint policies to company network paths (mapping from the AWS policy examples repository).

ObjectiveApplied onControl on this page
Only trusted identities can access my resourcesResourcesIdentity perimeter RCP (Step 2)
Only trusted identities are allowed from my networkNetworksVPC endpoint policy (Step 5)
My identities can access only trusted resourcesIdentitiesResource perimeter SCP (Step 4)
Only trusted resources can be accessed from my networkNetworksVPC endpoint policy (Step 5)
My identities can access resources only from expected networksIdentitiesNetwork perimeter SCP (Step 4)
My resources can be accessed only from expected networksResourcesNetwork perimeter RCP (Step 3)

Perimeter statements only deny; normal policies still grant. Steps marked AWS are evaluated automatically.

  1. A trusted request: the orders pod reads from the data platform
  2. Pod calls S3WorkloadThe orders-api pod in shop-prod uses its Pod Identity role orders-api-pod-role (tagged dp:include:network=true) to call s3:GetObject on shop-data-111111111111. The route table sends the request to the gateway endpoint vpce-0abc1234def567890 in vpc-0shop1234567890ab.
  3. Endpoint policyAWSPrincipal and bucket are both in o-exampleorgid: the first statement allows it.
  4. SCPs on the caller's accountAWSaws:ResourceOrgID matches, and aws:VpceOrgID matches because the endpoint's owner 111111111111 is a member. No deny.
  5. RCPs on the bucket's accountAWSaws:PrincipalOrgID and aws:VpceOrgID both match. No deny.
  6. Normal evaluation, then KMSAWSIdentity and bucket policies allow the read. S3 calls KMS with a forward access session: aws:ViaAWSService is true, so network statements skip it, and the identity check still sees an organization principal.
  7. Stolen credentials used from outside
  8. Attacker replays the role sessionAttackerAn attacker who stole the pod role's temporary credentials calls s3:GetObject from 198.51.100.77 over the internet. The identity perimeter alone would not stop valid organization credentials.
  9. Network perimeter SCP deniesAWSNo endpoint, so aws:VpceOrgID is absent and StringNotEqualsIfExists matches; the address is outside 192.0.2.0/24 and the role carries dp:include:network. Result: AccessDenied, explicit deny in a service control policy.
  10. The RCP denies as wellAWSThe bucket account's network RCP matches the same conditions, so the resource side holds even if the SCP were detached.
  11. Data pushed out, and outsiders pulling in
  12. Copy to a personal bucketAWSAn engineer calls s3:PutObject on a bucket in another organization. The endpoint policy and the resource perimeter SCP (on every path) deny it.
  13. A wildcard bucket policyAWSWith "Principal": "*" in a bucket policy, an unknown account tries to read. The identity perimeter RCP denies it.
  14. A confused deputyAWSAnother customer points an AWS service at the company's bucket. The call's aws:SourceOrgID is theirs, so the confused deputy statement denies it.

Build it

Step 1

Measure first, enable RCPs and agree the tags

Before any deny goes live, the team measures what crosses the perimeter today. IAM Access Analyzer with the organization as zone of trust lists resources whose policies grant outside access; it is Regional, so it runs in both Regions from the delegated administrator 222222222222. The organization trail in 444444444444, queried with Athena, shows real requests: userIdentity, sourceIPAddress, vpcEndpointId, resources and recipientAccountId (S3 object calls need data events).

Organization-wide external access analyzer, one per Region (AWS CLI, security tooling account 222222222222) 
aws accessanalyzer create-analyzer --region us-east-1 \
  --analyzer-name org-external-access \
  --type ORGANIZATION

aws accessanalyzer create-analyzer --region us-west-2 \
  --analyzer-name org-external-access \
  --type ORGANIZATION

The queries ask which outside accounts reached company resources (only the vendor should), which company principals touched outside resources (expect AWS-owned buckets), and which calls by future dp:include:network roles arrived without a vpcEndpointId from outside the corporate range. Each answer becomes an exception or a fix. CloudTrail doesn't record condition key values, so the queries rebuild them from log fields; AWS's data perimeter helper sample automates this.

Enabling RCPs on the root attaches RCPFullAWSAccess everywhere, so nothing changes until a deny is attached.

Enable RCPs and tag the first principals that the network perimeter will cover (AWS CLI) 
# management account 555555555555
aws organizations enable-policy-type --root-id r-abcd --policy-type RESOURCE_CONTROL_POLICY

# production account 111111111111: the network perimeter applies only to tagged principals
aws iam tag-role --role-name orders-api-pod-role \
  --tags '{"Key": "dp:include:network", "Value": "true"}'

Tags follow the AWS policy examples, all set to true: dp:include:network marks principals the network perimeter targets (workload roles first, since their credentials get replayed); dp:exclude:network, dp:exclude:identity and dp:exclude:resource exempt a principal or resource from one perimeter; dp:exclude exempts from all, for break-glass only.

Step 2

The identity perimeter on resources (RCP)

One RCP caps every team's bucket, key, queue and secret policies. The first statement denies callers outside the organization unless they are the vendor, the resource carries an exception tag, or an AWS service principal calls directly (aws:PrincipalIsAWSService). The second is the confused deputy guard: for service principal calls carrying aws:SourceAccount, aws:SourceOrgID must be the company's organization.

Identity perimeter and confused deputy protection for S3, STS, KMS, SQS and Secrets Manager (RCP, adapted from the aws-samples identity_perimeter_rcp.json) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceOrgIdentities",
      "Effect": "Deny",
      "Principal": "*",
      "Action": [
        "s3:*",
        "sts:AssumeRole",
        "sts:DecodeAuthorizationMessage",
        "sts:GetAccessKeyInfo",
        "sts:GetFederationToken",
        "sts:GetServiceBearerToken",
        "sts:GetSessionToken",
        "sts:SetContext",
        "kms:*",
        "sqs:*",
        "secretsmanager:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:PrincipalOrgID": "o-exampleorgid",
          "aws:PrincipalAccount": ["999999999999"],
          "aws:ResourceTag/dp:exclude:identity": "true"
        },
        "BoolIfExists": {
          "aws:PrincipalIsAWSService": "false"
        }
      }
    },
    {
      "Sid": "EnforceConfusedDeputyProtection",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["s3:*", "sts:*", "kms:*", "sqs:*", "secretsmanager:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:SourceOrgID": "o-exampleorgid",
          "aws:ResourceTag/dp:exclude:identity": "true"
        },
        "Null": {
          "aws:SourceAccount": "false"
        },
        "Bool": {
          "aws:PrincipalIsAWSService": "true"
        }
      }
    }
  ]
}

Keys inside one condition block are ANDed, so with a negated operator the deny applies only when every exception fails. The STS list leaves out sts:AssumeRoleWithSAML and sts:AssumeRoleWithWebIdentity, because federated callers have no aws:PrincipalOrgID; the full sample guards web identity separately.

Create the RCP and attach it to Policy Staging first (AWS CLI, management account) 
aws organizations create-policy \
  --content file://dp-identity-rcp.json \
  --name dp-identity-perimeter \
  --type RESOURCE_CONTROL_POLICY \
  --description "Data perimeter: org identities, vendor, AWS services on our behalf"

# use the policy ID returned above
aws organizations attach-policy --policy-id $RCP_ID --target-id ou-abcd-44444444

RCPs cover only listed services: first S3, STS, KMS, SQS and Secrets Manager, and since a January 2026 expansion many more, such as CloudWatch Logs, DynamoDB, ECR and SNS. Amazon Bedrock wasn't listed when this page was written. For uncovered services, put the same conditions in resource-based policies. RCPs never restrict resources in the management account, service-linked roles, AWS managed KMS keys or kms:RetireGrant. They do apply to delegated administrator accounts and to member root users.

Step 3

The network perimeter on resources (RCP)

Listing every VPC or endpoint with aws:SourceVpc or aws:SourceVpce meant a policy change per new VPC. Since August 2025, aws:VpceOrgID holds the organization ID of the account that owns the VPC endpoint a request came through (with aws:VpceOrgPaths for OUs and aws:VpceAccount for one account). Every company endpoint, including the central ones in 777700007777, is trusted automatically.

Expected networks only, for services that support aws:VpceOrgID (RCP, adapted from the aws-samples network_perimeter_vpceorgid_rcp.json) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceNetworkPerimeterVpceOrgID",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["ecr:*", "kms:*", "s3:*", "sqs:*"],
      "Resource": "*",
      "Condition": {
        "NotIpAddressIfExists": {
          "aws:SourceIp": "192.0.2.0/24"
        },
        "StringNotEqualsIfExists": {
          "aws:VpceOrgID": "o-exampleorgid",
          "aws:PrincipalTag/dp:exclude:network": "true",
          "aws:ResourceTag/dp:exclude:network": "true"
        },
        "BoolIfExists": {
          "aws:PrincipalIsAWSService": "false",
          "aws:ViaAWSService": "false"
        },
        "ArnNotLikeIfExists": {
          "aws:PrincipalArn": ["arn:aws:iam::*:role/aws:ec2-infrastructure"]
        },
        "StringEquals": {
          "aws:PrincipalTag/dp:include:network": "true"
        }
      }
    }
  ]
}

Deny when all are true: not from the office range (aws:SourceIp is absent through an endpoint), not through an organization-owned endpoint, no exception tag, no AWS service calling, not the aws:ec2-infrastructure role the sample excludes, and the caller is tagged dp:include:network. That last test keeps rollout gradual and leaves the vendor, whose roles lack the tag, free to read from its own network.

The aws:ViaAWSService exception is essential: when S3 calls KMS on the caller's behalf, the original endpoint isn't preserved, so without it every SSE-KMS read would fail at the KMS step.

aws:VpceOrgID is supported only by a listed set of services, and AWS warns that using it with others can give unintended results. That's why this statement names only four services. Secrets Manager, STS, CloudWatch Logs and DynamoDB go in a second statement copied from the AWS sample network_perimeter_sourcevpc_rcp.json, which lists VPC IDs with aws:SourceVpc instead. Remember that aws:SourceVpc is the VPC the endpoint is in. For the central interface endpoints that is the network account's endpoint VPC, not the workload VPC.

Step 4

The resource and network perimeters on identities (SCPs)

Exfiltration usually targets someone else's resource, where company RCPs don't apply, so an SCP stops company principals reaching resources outside the organization. AWS-owned resources (managed policies, public SSM documents, service sample buckets) are exempted with NotResource, and Amazon images with ec2:Owner. The list is shortened; service_owned_resources.md in the repository explains the full one.

Company identities reach only company resources, AWS-owned resources and the vendor's export bucket (SCP, shortened from the aws-samples resource_perimeter_scp.json) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceResourcePerimeterAWSResources",
      "Effect": "Deny",
      "Action": "*",
      "NotResource": [
        "arn:aws:iam::aws:policy/*",
        "arn:aws:ssm:*::document/*",
        "arn:aws:ssm:*::parameter/*",
        "arn:aws:ec2:*:aws:prefix-list/*",
        "arn:aws:s3:::athena-examples-us-east-1",
        "arn:aws:s3:::athena-examples-us-east-1/*",
        "arn:aws:s3:::vendor-drop-999999999999/*"
      ],
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:ResourceOrgID": "o-exampleorgid",
          "ec2:Owner": "amazon",
          "aws:PrincipalTag/dp:exclude:resource": "true"
        }
      }
    },
    {
      "Sid": "EnforceResourcePerimeterThirdPartyResources",
      "Effect": "Deny",
      "Action": "*",
      "Resource": ["arn:aws:s3:::vendor-drop-999999999999/*"],
      "Condition": {
        "StringNotEqualsIfExists": {
          "aws:PrincipalTag/dp:exclude:resource": "true",
          "aws:ResourceAccount": ["999999999999"]
        }
      }
    }
  ]
}

The vendor's bucket (named vendor-drop-999999999999, new here) is excluded from the first statement and guarded by the second, so company principals can reach it only while it stays in the vendor's account. A bucket with the same name re-created elsewhere (bucket sniping) is still denied.

The network perimeter SCP is the identity-side twin of Step 3. It stops stolen credentials being used against resources in the attacker's own account, where company RCPs don't reach.

Company identities only from company networks (SCP, Action list shortened from the aws-samples network_perimeter_vpceorgid_scp.json) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceNetworkPerimeterVpceOrgID",
      "Effect": "Deny",
      "Action": ["ecr:*", "ecs:*", "kms:*", "lambda:*", "s3:*", "sqs:*"],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {
          "aws:ViaAWSService": "false"
        },
        "NotIpAddressIfExists": {
          "aws:SourceIp": ["192.0.2.0/24"]
        },
        "StringNotEqualsIfExists": {
          "aws:PrincipalTag/dp:exclude:network": "true",
          "aws:VpceOrgID": "o-exampleorgid"
        },
        "ArnNotLikeIfExists": {
          "aws:PrincipalArn": ["arn:aws:iam::*:role/aws:ec2-infrastructure"]
        },
        "StringEquals": {
          "aws:PrincipalTag/dp:include:network": "true"
        }
      }
    }
  ]
}

SCPs have no Principal element and need no aws:PrincipalIsAWSService test, because they never apply to service principals or service-linked roles. They also never restrict the management account, which is one more reason to run no workloads there.

Step 5

VPC endpoint policies on the company's networks

Every private request leaving a company VPC passes an endpoint policy, so it checks both identity and resource. The default AWS sample has three Allow statements: organization identities to organization resources; AWS service principals; and organization identities tagged dp:exclude:resource to any resource. Anything else through the endpoint is implicitly denied.

Default data perimeter endpoint policy for the production S3 gateway endpoint (VPC endpoint policy, from the aws-samples default_endpoint_policy.json) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowRequestsByOrgsIdentitiesToOrgsResources",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:PrincipalOrgID": "o-exampleorgid",
          "aws:ResourceOrgID": "o-exampleorgid"
        }
      }
    },
    {
      "Sid": "AllowRequestsByAWSServicePrincipals",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "Bool": {
          "aws:PrincipalIsAWSService": "true"
        }
      }
    },
    {
      "Sid": "AllowRequestsByOrgsIdentitiesToAnyResources",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:PrincipalOrgID": "o-exampleorgid",
          "aws:PrincipalTag/dp:exclude:resource": "true"
        }
      }
    }
  ]
}
Replace the default full-access policy on the gateway endpoint (AWS CLI, production account 111111111111) 
aws ec2 modify-vpc-endpoint \
  --vpc-endpoint-id vpce-0abc1234def567890 \
  --policy-document file://dp-endpoint-policy.json

An S3 gateway endpoint serves only its own VPC, not traffic over the transit gateway, VPN or Direct Connect, so every workload VPC gets one (free) with this policy through StackSets. Interface endpoints for STS, KMS, Secrets Manager and Bedrock are central in the network account, so one policy per endpoint covers every VPC. Services such as SSM, EC2 and ECR need the repository's service-specific endpoint policies. An endpoint policy can be up to 20,480 characters, and gateway endpoints require "Principal": "*".

An endpoint policy only filters traffic that uses the endpoint. On its own it can't stop a principal going around it, through the NAT gateway to the public S3 endpoint or from a laptop. The network perimeter SCP and RCP close that gap, and the egress firewall is a further layer, not the perimeter itself.

Step 6

Protect the exception tags, then roll out in stages

Anyone who can tag their own role dp:exclude:network could switch the perimeter off, so the governance SCP lets only platform administrators set dp: tags. The same file blocks sharing paths the main controls don't see, such as sharing snapshots and AMIs, RAM shares that allow outside principals and Lambda function URLs with no authentication. The governance RCP protects session tags, with an exception for tags set by the company's SAML identity provider.

Only platform administrators may set dp: tags (SCP statement, from the aws-samples data_perimeter_governance_scp.json) 
{
  "Sid": "ProtectDataPerimeterTags",
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringNotEqualsIfExists": {
      "aws:PrincipalTag/team": "admin"
    },
    "ForAnyValue:StringLike": {
      "aws:TagKeys": ["dp:*"]
    }
  }
}

An SCP can be up to 10,240 characters with 10 attached per target. An RCP can be up to 5,120 characters with 5 per target, and the undetachable RCPFullAWSAccess counts as one, which leaves four. The pipeline minifies JSON, because whitespace counts. The company uses three: identity, network and governance.

Rollout follows the AWS advice not to attach RCPs to the root untested:

  1. Policy StagingAttach all policies to ou-abcd-44444444, run the pod, analytics, vendor and console journeys against the test account 101010101010, and watch CloudTrail for AccessDenied.
  2. SandboxAttach the identity and resource perimeters to the Sandbox OU, where 333333333333 has real but low-risk users. The network perimeter isn't applied there: sandbox roles aren't tagged dp:include:network, and developers work from home.
  3. Non-prod, then one prod accountAttach to the non-prod workloads OU, then directly to 111111111111, and query the trail daily for denies from the new policies.
  4. Workloads OU, then the rootMove the attachment to ou-abcd-33333333 and finally to r-abcd, removing the account-level attachments. Widen dp:include:network from workload roles to human roles last.

Control Tower users should check the AWS note that roles such as AWSControlTowerExecution may need an exception, or account enrollment breaks.

Design decisions

Deny on the organization ID, not allow lists of accounts

aws:PrincipalOrgID, aws:ResourceOrgID, aws:SourceOrgID and aws:VpceOrgID follow the organization automatically: a new account is inside the perimeter the moment it joins, and a divested one is outside the moment it leaves, with no policy edits. All four are single-valued and sensitive, so they are never used with wildcards. The perimeter is coarse on purpose; who may read which bucket is still the job of identity and resource policies (Task 4.2).

RCPs first, resource policies where RCPs don't reach

An RCP enforces the identity perimeter centrally, and developers keep writing their own resource policies inside it. For services not on the RCP list, the same statements go into resource policies, deployed and checked by AWS Config (Task 6.1).

aws:VpceOrgID over lists of VPC and endpoint IDs

One key replaces dozens of IDs and keeps policies within the RCP size limit. The cost is service coverage: services without aws:VpceOrgID support keep an aws:SourceVpc statement, which the platform team updates when a VPC is added. A tighter variant uses aws:VpceOrgPaths to trust only endpoints owned by accounts in the Workloads and Infrastructure OUs, so a sandbox endpoint doesn't count as an expected network.

Network perimeter by opt-in tag

Applying the network perimeter only to principals tagged dp:include:network lets it start with the highest-value targets, the workload roles whose credentials live on servers and pods, before human roles. The trade-off is that an untagged role is not covered. A custom AWS Config rule therefore flags workload roles without the tag, and the governance SCP stops anyone removing it.

Vendor access by account, not by public resource

Tagging the export bucket dp:exclude:identity would open it to anyone a bucket policy names. Adding 999999999999 to aws:PrincipalAccount keeps the identity perimeter in force for everyone else. The vendor's bucket gets the matching exception on the resource side. Both exceptions are reviewed when the contract is.

Where the perimeter doesn't apply

The management account 555555555555, service-linked roles and AWS managed KMS keys are outside both SCPs and RCPs, so the management account holds no data and the data platform uses customer managed keys (Task 5.2). Encryption in transit is a separate guardrail: the TLS-only RCP on Task 6.1 sits alongside these policies and uses one of the four RCP slots (Task 5.1).

Alternatives

Resource policies only

Adding aws:PrincipalOrgID and aws:SourceVpce conditions to every bucket and key policy was the only option before RCPs. At scale, one missed bucket is a breach.

Control Tower RCP-based controls

Control Tower offers managed RCP-based controls for S3, STS, KMS, SQS and Secrets Manager, with exemption parameters for principals and resources. They are quicker to turn on but less flexible than your own policies, which can add the vendor, tag and AWS-owned resource exceptions this design needs.

Network controls alone

Network Firewall domain filtering and DNS Firewall in the egress VPC block uploads to unknown hosts, but they can't see which bucket or account an S3 request targets, and they do nothing about credentials used from outside. They complement the perimeter as a separate layer (Task 3.3).

Instance credential binding

Comparing aws:SourceVpc with aws:Ec2InstanceSourceVpc in an SCP stops EC2 instance role credentials from being used outside the instance's own VPC. That is narrower and stronger for EC2, but it doesn't cover pod roles or human sessions, and it still relies on VPC endpoints being in use.

Testing it

  1. Validate the policiesRun aws accessanalyzer validate-policy --policy-type RESOURCE_CONTROL_POLICY on each RCP and SERVICE_CONTROL_POLICY on each SCP in the pipeline, and fail the build on errors or on a minified size over the quota.
  2. Trusted paths still workIn the staging account, a pod reads and writes the test bucket through the gateway endpoint, including SSE-KMS objects. The analytics role reads from its own VPC, and the vendor role reads the export prefix. Each must succeed.
  3. Replay credentials from outsideExport a tagged test role's session and call s3:GetObject from a host outside the corporate range: expect AccessDenied with an explicit deny in a service control policy (within the organization, deny messages are gradually gaining the policy ARN). Repeat against a bucket in a separate test organization to prove the SCP, not the RCP, stopped it.
  4. Outsider and exfiltration testsAdd a wildcard bucket policy to a staging bucket and read it from an account outside the organization: expect a deny from the RCP. From inside the VPC, try PutObject to a bucket in the test organization: expect a deny from the endpoint policy and the SCP.
  5. Use the right toolThe IAM policy simulator evaluates SCPs but not RCPs or endpoint policies, so live tests in the staging account are the proof. Access Analyzer doesn't rescan when an RCP changes; trigger a rescan, and treat remaining findings as resource policies to fix at the source.
  6. Keep watchingA saved Athena query over the organization trail lists AccessDenied events that name the data perimeter policies, per account and day. A sudden rise after a deployment is a missed access pattern; a deny from an unknown IP is an incident.

"Ensure that only principals in our organization can access S3 buckets and KMS keys in all accounts, even if a developer misconfigures a bucket policy, with the least operational effort" is a resource control policy with aws:PrincipalOrgID and an aws:PrincipalIsAWSService exception. "Prevent employees from copying data to buckets outside the organization" is an SCP (and endpoint policy) with aws:ResourceOrgID. "Stolen credentials must not work outside our networks" is a network perimeter with aws:VpceOrgID or aws:SourceVpc, aws:SourceIp for corporate ranges and an aws:ViaAWSService exception. Answers that list account IDs in every bucket policy are the high-effort distractor.
