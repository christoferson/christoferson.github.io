Overview

Task 4.1

Design, implement, and troubleshoot authentication strategies.

Domain 4 is the largest on the exam (20%). This task is authentication: which identity system each kind of caller uses, how strong the proof is, and how credentials are kept short-lived; Task 4.2 is what they're allowed to do. The associate-level choice between Identity Center, IAM federation and Cognito, and the root user basics, are in the Solutions Architect guide; revoking sessions and containing users are in Task 2.2.

Running example. The same company. Employees sign in with the corporate identity provider, contractors with accounts in the Identity Center directory; shoppers sign in to the web and mobile apps through Cognito; GitHub Actions deploys to AWS; on-premises warehouse servers send data to S3; a legacy system needs Active Directory in AWS.

Identity for people, applications and systems

Skill 4.1.1Design and establish identity solutions for human, application, and system authentication (for example, AWS IAM Identity Center, Amazon Cognito, multi-factor authentication [MFA], identity provider [IdP] integration).

Workforce users: IAM Identity Center

Instances and identity sources

An organization instance of Identity Center (in the management account, optionally run from a delegated administrator account) is the only kind that gives permission sets for multi-account access, SAML applications, customer managed KMS encryption and multi-Region replication. An account instance serves AWS managed applications in one account only. The identity source is one of three:

  • Identity Center directory: users and groups stored in Identity Center (the contractors in the running example).
  • Active Directory: AWS Managed Microsoft AD, or a self-managed AD through AD Connector, with configurable AD sync.
  • External IdP (Okta, Entra ID and others): SAML 2.0 for sign-in plus SCIM to provision users and groups. Users must exist before they sign in (no just-in-time creation over SAML), and the SAML NameID must match the SCIM username.

SCIM access tokens expire after one year; reminders start 90 days before, and when one expires sync stops silently. A delegated administrator can create SCIM tokens unless an SCP denies sso-directory:CreateBearerToken.

Permission sets

A permission set holds AWS managed policies, customer managed policies (by name), one inline policy and an optional permissions boundary, plus a session duration of 1 to 12 hours. Assigning it to a group in an account creates an AWSReservedSSO_... role there. Those roles are protected: editing them in IAM fails, and changes go through Identity Center. A customer managed policy must already exist with the same name and path in every account the permission set is assigned to; Identity Center doesn't create it, so deploy it first (for example with StackSets). The delegated administrator can't change permission sets provisioned to the management account.

MFA and sessions

For the Identity Center directory and AD sources, MFA is on by default: users register up to 8 devices (2 authenticator apps and 6 FIDO2 passkeys or security keys). Prompting is every sign-in (default) or context-aware (only when device, browser or location changes); users without a device are made to register one, sent an email code, blocked, or let in. With an external IdP, Identity Center's MFA settings don't apply: the IdP enforces MFA. The AWS access portal session lasts 8 hours by default (15 minutes to 90 days); role sessions from permission sets run independently for up to 12 hours, so disabling a user doesn't end sessions already issued.

Multi-Region replication (2026) copies identities, permission sets, assignments and sessions to other Regions so workforce access survives a Regional disruption. It needs an organization instance, a multi-Region customer managed KMS key and an IdP that supports multiple ACS URLs, and isn't available with an Active Directory source.

With context-aware MFA, a user who marks a device as trusted isn't prompted again, even when the policy says to block sign-in for users without MFA. If every sign-in must use MFA, choose every time they sign in.

Command line access

Identity Center users get CLI credentials with aws configure sso and aws sso login; the profile stores the start URL and role, never keys. IAM users, root and directly federated users can now use aws login (CLI 2.32.0 or later, with the SignInLocalDevelopmentAccess policy), which signs in through the browser and gives the CLI credentials for up to 12 hours. It's also the only way to use a passkey or security key MFA for CLI work, because FIDO MFA can't be passed to STS.

A profile that gets credentials from Identity Center (~/.aws/config) 
[profile prod-readonly]
sso_session = corp
sso_account_id = 111111111111
sso_role_name = ReadOnlyAccess
region = us-east-1

[sso-session corp]
sso_region = us-east-1
sso_start_url = https://example-corp.awsapps.com/start
sso_registration_scopes = sso:account:access

Direct IAM federation

SAML 2.0 into IAM roles

Without Identity Center, an IAM SAML provider in each account and a role that trusts it let the corporate IdP sign users in directly. The assertion must carry the Role and RoleSessionName attributes; AWS now recommends the Regional sign-in endpoints as the audience, and supports encrypted assertions.

Trust policy for a role assumed through the corporate IdP (IAM role trust policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "Action": "sts:AssumeRoleWithSAML",
    "Principal": { "Federated": "arn:aws:iam::111111111111:saml-provider/CorpIdP" },
    "Condition": {
      "StringEquals": { "SAML:aud": "https://us-east-1.signin.aws.amazon.com/saml" }
    }
  }
}

If the IdP passes session tags or a source identity, the trust policy also needs sts:TagSession or sts:SetSourceIdentity.

Applications and systems

OIDC for pipelines: GitHub Actions

A pipeline should assume a role with a short-lived OIDC token, never hold access keys. The role trusts the GitHub OIDC provider and must restrict which repository and branch can use it:

Only the main branch of the shop repository can deploy (IAM role trust policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Federated": "arn:aws:iam::111111111111:oidc-provider/token.actions.githubusercontent.com" },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:example-org/shop:ref:refs/heads/main"
        }
      }
    }
  ]
}

Without the sub condition, any repository on GitHub could assume the role. IAM now rejects new or changed trust policies for GitHub and other shared OIDC providers that lack the required claim (sub, or job_workflow_ref for GitHub), with MalformedPolicyDocument. Thumbprints matter less than before: AWS validates the provider against its library of trusted certificate authorities and uses thumbprints only as a fallback.

IAM Roles Anywhere for servers outside AWS

The warehouse servers authenticate with X.509 certificates instead of access keys. A trust anchor (AWS Private CA or your own CA bundle) and a profile (which roles, optional session policy) let a server holding a certificate from that CA get temporary credentials through the credential helper. Restrict each role to its trust anchor and certificate attributes, because any trust anchor in the account could otherwise be used for any role that trusts the service:

Only certificates from the warehouse CA with this common name (IAM role trust policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "rolesanywhere.amazonaws.com" },
      "Action": ["sts:AssumeRole", "sts:TagSession", "sts:SetSourceIdentity"],
      "Condition": {
        "StringEquals": { "aws:PrincipalTag/x509Subject/CN": "warehouse-uploader-01" },
        "ArnEquals": { "aws:SourceArn": "arn:aws:rolesanywhere:us-east-1:111111111111:trust-anchor/ta-0example" }
      }
    }
  ]
}

Revocation uses imported CRLs or CRL distribution point checking; OCSP isn't supported.

Outbound identity federation

The reverse direction: an AWS workload calling an external service can now get a signed JWT from STS (sts:GetWebIdentityToken, after aws iam enable-outbound-web-identity-federation in the account) and present it instead of a stored API key. The token carries claims such as the organization ID and principal tags, lives 60 to 3,600 seconds, and requires a Regional STS endpoint.

Customers: Amazon Cognito

User pools, plans and sign-in options

A user pool is the shoppers' directory and OIDC token issuer. Since November 2024 it has three plans: Lite, Essentials (the default: managed login, email OTP MFA, passkeys and passwordless sign-in) and Plus (adds threat protection, the renamed advanced security features). MFA is off, optional or required, by SMS, email or TOTP; it applies to local users only, and a pool that allows passwordless OTP sign-in can't require MFA (passkeys with user verification can count as MFA).

  • Threat protection (Plus): compromised credential checks (only for username-password flows, not SRP), and adaptive authentication that requires MFA or blocks by risk level (MFA must be optional). Run in audit mode first. It doesn't rate-limit; use AWS WAF on the pool for that.
  • App clients: public clients (no secret) should use authorization code with PKCE; confidential clients have a secret and must send SECRET_HASH. Machine-to-machine access uses the client credentials grant with custom scopes.
  • Tokens: ID and access tokens (5 minutes to 1 day), refresh tokens (default 30 days), optional refresh token rotation. RevokeToken revokes a refresh token and the tokens issued from it. Apps validate tokens against the pool's JWKS, issuer, token_use and audience or client ID.

Identity pools: AWS credentials for app users

An identity pool exchanges a user pool token (or a SAML, OIDC or social token) for temporary AWS credentials, for example so the mobile app can upload a profile photo straight to S3. Use the enhanced flow; the pool chooses the role (default, by rules on token claims, or from the token's cognito:preferred_role). Never map claims users can edit to privileged roles. Guest (unauthenticated) identities need their own minimal role. The role's trust policy must name the pool in the aud condition, which IAM now requires:

Role for signed-in shoppers from one identity pool (IAM role trust policy, JSON) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Federated": "cognito-identity.amazonaws.com" },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": { "cognito-identity.amazonaws.com:aud": "us-east-1:12345678-1234-1234-1234-123456789012" },
        "ForAnyValue:StringLike": { "cognito-identity.amazonaws.com:amr": "authenticated" }
      }
    }
  ]
}

MFA for IAM users and the root user

Requiring MFA

IAM users and the root user can register up to 8 MFA devices: passkeys and security keys (FIDO2), authenticator apps and hardware TOTP tokens. AWS now requires MFA on the root user of every account type, within 14 days of first sign-in. For IAM users that remain, a policy can deny everything except setting up MFA until they've signed in with it:

Deny everything but MFA setup when the user hasn't used MFA (statement of an IAM policy, JSON) 
{
  "Sid": "DenyAllExceptListedIfNoMFA",
  "Effect": "Deny",
  "NotAction": [
    "iam:CreateVirtualMFADevice",
    "iam:EnableMFADevice",
    "iam:GetUser",
    "iam:ListMFADevices",
    "iam:ListVirtualMFADevices",
    "iam:ResyncMFADevice",
    "sts:GetSessionToken"
  ],
  "Resource": "*",
  "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } }
}

BoolIfExists matters: long-term access keys carry no aws:MultiFactorAuthPresent key at all, so a plain Bool check would never match them. A role trust policy can require MFA with "Bool": {"aws:MultiFactorAuthPresent": "true"}, and aws:MultiFactorAuthAge limits how long ago MFA happened.

MFA for API calls works only through GetSessionToken or AssumeRole with a TOTP device's serial number and code. It doesn't work with SAML or web identity federation (the IdP does MFA there), with root user access keys, or with passkeys and security keys. And credentials from AssumeRole don't pass MFA context on to later calls, so a resource policy requiring MFA needs GetSessionToken credentials.

Issuing temporary credentials

Skill 4.1.2Configure mechanisms to issue temporary credentials (for example, AWS STS, Amazon S3 presigned URLs).

AWS STS

The APIs and their lifetimes

  • AssumeRole: an IAM principal assumes a role; MFA and session policies possible; 15 minutes up to the role's maximum session duration (1 to 12 hours, default 1 hour). Role chaining (using role credentials to assume another role) caps the session at 1 hour.
  • AssumeRoleWithSAML and AssumeRoleWithWebIdentity: federated callers with a SAML assertion or OIDC token; no MFA parameter; same duration rules.
  • GetSessionToken: an IAM user's own permissions with MFA; 15 minutes to 36 hours (default 12), 1 hour for root. The result can't call IAM unless MFA was included.
  • GetFederationToken: an IAM user creates credentials for someone else, limited by a session policy; 15 minutes to 36 hours; the result can't call IAM or most of STS.
  • AssumeRoot: centralized root access to member accounts, for 15 minutes (Task 2.2).

Session policies (passed at assume time, up to 2,048 characters combined) can only reduce permissions. Session tags (up to 50, needing sts:TagSession) carry attributes for ABAC, and transitive tags survive role chaining. A third party assuming a role in your account should use an external ID.

Credentials for an IAM user who must use MFA (AWS CLI) 
aws sts get-session-token \
  --serial-number arn:aws:iam::111111111111:mfa/ops-break-glass \
  --token-code 123456 \
  --duration-seconds 3600

Regional endpoints and token versions

Use Regional STS endpoints (sts.us-east-1.amazonaws.com); current SDKs and CLI v2 do by default. Requests to the global endpoint from default Regions are now served in the caller's own Region, but are still logged in us-east-1. Tokens from the global endpoint are version 1 by default and aren't valid in opt-in Regions; either use Regional endpoints or set the account to issue version 2 tokens (aws iam set-security-token-service-preferences). STS can be deactivated per Region for an account, which gives RegionDisabled errors.

S3 presigned URLs

Time-limited access to one object

A presigned URL lets someone without AWS credentials get or put one object, using the signer's permissions. The expiry can be up to 7 days from the CLI or SDK (12 hours in the console), but the URL stops working when the credentials that signed it expire or are deactivated: about 6 hours for instance profile credentials, the session length for a role. A 7-day URL therefore needs an IAM user's long-term key, which is a reason to prefer shorter URLs. A bucket policy can refuse old signatures or require a network:

Refuse presigned requests signed more than 10 minutes ago (S3 bucket policy statement, JSON) 
{
  "Sid": "DenyOldSignatures",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": "arn:aws:s3:::shop-uploads-111111111111/*",
  "Condition": { "NumericGreaterThan": { "s3:signatureAge": "600000" } }
}

S3 checks expiry when a request starts; a download already running continues. For content behind CloudFront, CloudFront signed URLs and cookies (Task 3.1) are independent of IAM credential lifetimes.

Credentials on compute

EC2 instances get role credentials from IMDS (IMDSv2 requires a session token), ECS tasks from the container credential endpoint for the task role, Lambda functions from their execution role, and EKS pods through Pod Identity (Task 3.2). All are temporary and rotated automatically; the application code should never hold an access key.

"A partner must download one report without AWS credentials, for one hour" points to an S3 presigned URL. "A pipeline in GitHub needs to deploy without stored keys" points to OIDC federation. "On-premises servers need AWS access without long-term keys" points to IAM Roles Anywhere.

Troubleshooting authentication

Skill 4.1.3Troubleshooting authentication issues (for example, CloudTrail, Amazon Cognito, IAM Identity Center permission sets, AWS Directory Service).

Reading sign-in events

Console and Identity Center sign-ins in CloudTrail

Console sign-ins are ConsoleLogin events from signin.amazonaws.com. Success or failure is in responseElements, MFA use in additionalEventData; an unknown user name appears as HIDDEN_DUE_TO_SECURITY_REASONS. Root sign-ins can be recorded in us-east-1, us-east-2 or us-west-2, so look in all three. Federated users always show MFAUsed: "No", because AWS can't see the IdP's MFA.

A failed IAM user sign-in (ConsoleLogin event, abridged) 
{
  "eventSource": "signin.amazonaws.com",
  "eventName": "ConsoleLogin",
  "userIdentity": { "type": "IAMUser", "userName": "ops-break-glass" },
  "sourceIPAddress": "198.51.100.23",
  "errorMessage": "Failed authentication",
  "responseElements": { "ConsoleLogin": "Failure" },
  "additionalEventData": { "LoginTo": "https://console.aws.amazon.com/console/home", "MFAUsed": "No" }
}

Identity Center sign-ins produce CredentialChallenge (a factor was requested: password, TOTP, WebAuthn, external IdP), CredentialVerification (it succeeded or failed) and UserAuthentication (all challenges passed), linked by an AuthWorkflowID. External IdP failures show as CredentialVerification with type EXTERNAL_IDP. aws login sessions appear as AuthorizeOAuth2Access and CreateOAuth2Token.

For a cross-account AssumeRole that's denied, CloudTrail doesn't log the failure in the target account; look in the caller's account. Successful cross-account calls appear in both, linked by sharedEventID.

Common failures and their causes

Federation

  • "Your request included an invalid SAML response": the Role attribute is missing or has stray whitespace.
  • "RoleSessionName is required in AuthnResponse": the IdP doesn't send RoleSessionName.
  • "Not authorized to perform sts:AssumeRoleWithSAML": wrong role name, trust policy missing the action, sts:TagSession or sts:SetSourceIdentity, or a condition not met.
  • "Response signature invalid": the IdP's signing certificate changed; update the SAML provider metadata (aws iam update-saml-provider).
  • "Response does not contain the required audience": the relying party identifier doesn't match the audience in the trust policy.
  • "Requested DurationSeconds exceeds MaxSessionDuration set for this role."
  • Web identity: InvalidIdentityToken (token can't be validated, JWKS problem), ExpiredToken, IDPRejectedClaim, or access denied when the token's aud or sub doesn't match the trust policy.

Identity Center

  • Users can't see an account: the permission set isn't assigned, or provisioning failed, often because a referenced customer managed policy doesn't exist with that name and path in the account. Check the provisioning status and re-provision after fixing.
  • "Cannot perform the operation on the protected role": someone tried to edit an AWSReservedSSO_ role in IAM; change the permission set instead.
  • A user deleted and recreated in the IdP gets a new internal ID, so old assignments no longer apply: remove and re-add them.
  • SCIM sync errors: missing first or last name, multivalue attributes, duplicates, or an expired SCIM token.
  • External IdP "unexpected error": NameID format or value doesn't match the Identity Center username, ACS URL mismatch, or encrypted assertions (not supported by Identity Center).

Cognito

  • NotAuthorizedException: wrong password, or a revoked or expired token. "Unable to verify secret hash for client": the app client has a secret and the request lacks a correct SECRET_HASH.
  • UserNotConfirmedException: sign-up not confirmed (ConfirmSignUp or AdminConfirmSignUp). PasswordResetRequiredException: imported users must reset their password.
  • FeatureUnavailableInTierException: the feature (threat protection, passkeys) needs a higher plan.
  • Identity pools: "Basic (classic) flow is not supported with RoleMappings": use the enhanced flow. Access denied when assuming the role: the trust policy's aud doesn't match the pool ID.

Directory Service and STS

  • AD Connector: needs a network path to the domain controllers with at least DNS (53), Kerberos (88) and LDAP (389) open from both subnets, the SRV records for LDAP and Kerberos, a service account that can read users and groups, and Kerberos preauthentication on user accounts. AWS's DirectoryServicePortTest tool checks the ports. RADIUS MFA needs UDP 1812 and matching shared secrets.
  • Trusts: conditional forwarders in both directions, outbound security group rules, and two-way trust for Identity Center and other AWS applications.
  • STS: RegionDisabled (STS deactivated in that Region for the account), ExpiredToken (refresh credentials), and version 1 global-endpoint tokens rejected in opt-in Regions.

"Users can sign in to the portal but don't see the new account" points to permission set assignment and provisioning. "The new pipeline role can't be created" after copying an old GitHub trust policy points to the missing sub condition. "Sign-in to WorkSpaces with on-premises credentials fails" points to the AD Connector network path, DNS or service account.

Key takeaways

  • Identity Center organization instance for multi-account access; identity source is its directory, AD, or an external IdP with SAML plus SCIM (tokens expire after a year). Permission sets create protected AWSReservedSSO_ roles; customer managed policies must exist by name and path in every account.
  • Identity Center MFA (up to 8 devices, every sign-in or context-aware) doesn't apply to external IdP users. Portal sessions 8 hours by default, role sessions up to 12 hours. Multi-Region replication needs a multi-Region KMS key and not an AD source.
  • SAML trust with SAML:aud; GitHub OIDC trust must have sub (IAM rejects it otherwise); Roles Anywhere with trust anchor and certificate conditions; outbound federation with GetWebIdentityToken.
  • Cognito: Lite, Essentials (default; passkeys, passwordless, managed login) and Plus (threat protection); PKCE for public clients, SECRET_HASH for confidential ones; identity pools with the enhanced flow and aud-scoped trust.
  • IAM MFA: root MFA required; deny without MFA using BoolIfExists; API MFA only through GetSessionToken or AssumeRole with TOTP; passkeys for the CLI through aws login.
  • STS: role sessions 1 to 12 hours, chaining 1 hour, GetSessionToken up to 36 hours (root 1 hour); session policies only reduce; Regional endpoints, v2 tokens for opt-in Regions. Presigned URLs end with the signing credentials; s3:signatureAge limits them.
  • Troubleshoot with ConsoleLogin (three Regions for root), Identity Center CredentialChallenge/CredentialVerification/UserAuthentication, SAML and web identity error messages, provisioning status, Cognito exceptions, and AD Connector ports 53, 88 and 389.
