Overview

Task 6.2

Implement a secure and consistent deployment strategy for cloud resources.

Task 6.1 built the accounts and the limits; this task fills them consistently. The exam angle is control: who can deploy into which accounts, what stops an insecure template, what makes a tag trustworthy enough to base access on, and how sharing avoids handing out more access than intended. Control Tower's proactive controls and customization pipelines are in Task 6.1; pipeline vulnerability scanning in Task 3.2.

Running example. The same company. The platform team in the security tooling account (222222222222) deploys baseline roles, Config rules and monitoring to every account with StackSets; application teams deploy with CloudFormation and some with Terraform or CDK; the network account shares subnets and Resolver rules; and the company publishes approved patterns (an encrypted S3 bucket, a hardened web stack) through Service Catalog.

Deploying securely with infrastructure as code

Skill 6.2.1Use infrastructure as code (IaC) to deploy cloud resources consistently and securely across accounts (for example, CloudFormation stack sets, third-party IaC tools, CloudFormation Guard, cfn-lint).

Deploy the security baseline to every workload account, now and as accounts are added (AWS CLI, security tooling account as delegated administrator) 
aws cloudformation create-stack-set --call-as DELEGATED_ADMIN \
  --stack-set-name security-baseline \
  --template-url https://s3.us-east-1.amazonaws.com/platform-templates-222222222222/security-baseline.yaml \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false \
  --managed-execution Active=true \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation create-stack-instances --call-as DELEGATED_ADMIN \
  --stack-set-name security-baseline \
  --deployment-targets OrganizationalUnitIds=ou-abcd-11111111,ou-abcd-22222222 \
  --regions us-east-1 us-west-2 \
  --operation-preferences MaxConcurrentPercentage=25,FailureTolerancePercentage=10,RegionConcurrencyType=PARALLEL
  • Deployment controls: maximum concurrency and failure tolerance (counted per Region), Regions in sequence or parallel. In the default strict mode, concurrency can't exceed the failure tolerance plus one; soft mode keeps concurrency up but can end with more failures than the tolerance.
  • Limits of service-managed StackSets: no nested stacks, macros or transforms (so no SAM), auto-deployment ignores account filters, and parameter overrides don't reach accounts added later.
  • Drift detection on a StackSet reports changed stack instances but doesn't fix them. Scope the execution role down from the administrator access the sample template grants.

Protecting stacks

Stack policies, service roles and termination protection

  • Stack policy: once set, every resource is protected from updates unless the policy allows them; it applies only during updates, can't be deleted (only replaced), and avoid NotResource with Allow, which doesn't reliably protect.
  • Termination protection stops the stack being deleted (it cascades to nested stacks).
  • Service role (--role-arn): CloudFormation deploys with a role trusted by cloudformation.amazonaws.com, so users need only CloudFormation permissions and iam:PassRole. But anyone who can update the stack then acts with that role, even without PassRole, so keep it least privilege; restrict which roles users may pass with the cloudformation:RoleARN condition.
  • Capabilities: templates that create IAM resources need CAPABILITY_IAM, and named IAM resources CAPABILITY_NAMED_IAM; secrets come in through dynamic references, never parameters.
Allow updates to everything except the production database (CloudFormation stack policy, JSON) 
{
  "Statement": [
    { "Effect": "Allow", "Action": "Update:*", "Principal": "*", "Resource": "*" },
    { "Effect": "Deny", "Action": ["Update:Replace", "Update:Delete"], "Principal": "*", "Resource": "LogicalResourceId/OrdersDatabase" }
  ]
}

Checking templates before they deploy

CloudFormation Guard

CloudFormation Guard (cfn-guard, version 3) evaluates JSON or YAML (CloudFormation templates, Terraform plan JSON, Kubernetes manifests) against rules written in its policy language. Queries select values, clauses on separate lines must all hold, and by default every selected value must match (some means at least one). Rules for a resource type that isn't in the template are skipped, not failed. The Guard Rules Registry has ready-made rules mapped to frameworks such as CIS, NIST and PCI DSS, named after the matching Config managed rules.

Every S3 bucket must have default encryption (Guard rule, from AWS's hooks documentation) 
let s3_buckets_s3_default_encryption = Resources.*[ Type == 'AWS::S3::Bucket']

rule S3_DEFAULT_ENCRYPTION_KMS when %s3_buckets_s3_default_encryption !empty {
  %s3_buckets_s3_default_encryption.Properties.BucketEncryption exists
  %s3_buckets_s3_default_encryption.Properties.BucketEncryption.ServerSideEncryptionConfiguration[*].ServerSideEncryptionByDefault.SSEAlgorithm in ["aws:kms","AES256"]
  <<
    Violation: S3 Bucket default encryption must be set.
    Fix: Set BucketEncryption.ServerSideEncryptionConfiguration.ServerSideEncryptionByDefault.SSEAlgorithm to "aws:kms" or "AES256"
  >>
}
Run it in the pipeline, and unit-test the rules (shell) 
cfn-guard validate -d web-stack.yaml -r s3_encryption.guard
cfn-guard test -r s3_encryption.guard -t s3_encryption_tests.yaml

Guard and Lambda hooks

A pipeline check can be skipped by deploying from a laptop. CloudFormation hooks run inside CloudFormation itself, before resources, whole stacks, change sets or Cloud Control API calls are created, updated or deleted, in every deployment in the account and Region. The managed Guard hook runs your Guard rules from S3; the Lambda hook calls your function. Start in WARN mode, then switch to FAIL.

Activate the Guard hook and point it at the company rules (AWS CLI and hook configuration, JSON) 
aws cloudformation activate-type --type HOOK \
  --type-name AWS::Hooks::GuardHook --publisher-id aws-hooks \
  --type-name-alias Private::Guard::CompanyBaseline \
  --execution-role-arn arn:aws:iam::111111111111:role/guard-hook-execution

aws cloudformation set-type-configuration --configuration file://config.json \
  --type-arn arn:aws:cloudformation:us-east-1:111111111111:type/hook/Private-Guard-CompanyBaseline

{
  "CloudFormationConfiguration": {
    "HookConfiguration": {
      "HookInvocationStatus": "ENABLED",
      "TargetOperations": ["STACK", "RESOURCE", "CHANGE_SET"],
      "FailureMode": "FAIL",
      "Properties": {
        "ruleLocation": "s3://platform-guard-rules-222222222222/baseline.guard",
        "logBucket": "platform-guard-reports-222222222222"
      },
      "TargetFilters": { "Actions": ["CREATE", "UPDATE"] }
    }
  }
}

Hooks are activated per account and Region (deploy them with a StackSet), the rules file is downloaded on every invocation (use S3 versioning so it can't be swapped silently), and each invocation has a 30-second timeout. AWS Config custom policy rules also use Guard, but on the guard-2.x.x runtime, for detective checks of deployed resources.

cfn-lint

cfn-lint validates templates against the CloudFormation resource schemas and best practices: E rules for errors, W for warnings (for example W1011, use a dynamic reference instead of a parameter for a secret; W2501, password properties), and I for informational rules that are off by default. Version 1 (2024) renumbered rules, so old ignore lists can stop working. Run it in the editor, as a pre-commit hook and in the pipeline before Guard.

Other IaC tools

CDK, Terraform and registry extensions

  • AWS CDK: cdk bootstrap creates deployment roles in each target account. The CloudFormation execution role defaults to AdministratorAccess; scope it with --cloudformation-execution-policies. --trust lets another account (such as a pipeline account) deploy, and re-running it with a new list replaces the old trusted accounts. cdk-nag checks CDK apps against rule packs (AWS Solutions, NIST 800-53, PCI DSS, HIPAA), with suppressions recorded in metadata.
  • Terraform: state files hold resource details and often secrets in plain text, so AWS's guidance is an S3 backend with SSE-KMS, versioning and a locked-down bucket policy, with locking, and a bucket per account. Cross-account deployments assume a role in each target account.
  • Third-party resource types and hooks from the CloudFormation registry must be activated per account and Region; major versions never update automatically.

Pipeline checks protect only deployments that go through the pipeline. For "no one can deploy an unencrypted bucket, whatever tool they use" the controls are a CloudFormation hook (or Control Tower proactive controls) for CloudFormation deployments, and preventive guardrails such as SCPs, declarative policies and S3 Block Public Access for everything else.

Tags for organizing and governing

Skill 6.2.2Use tags to organize AWS resources into groups for management (for example, by grouping by department, cost center, environment).

A tagging schema

Rules and conventions

Each resource takes up to 50 user tags (keys up to 128 characters, values up to 256); the aws: prefix is reserved, and keys and values are case-sensitive, so CostCenter and costcenter are different tags. AWS's tagging guidance suggests lowercase keys with an organization prefix (example:cost-center, example:environment, example:data-classification) and tags for cost allocation, automation, access control, operations and compliance, each marked mandatory or optional in a published schema. Never put personal or confidential data in tags; many services and billing can read them.

Making tags reliable

Require tags at creation, then audit

  • Proactive: IAM or SCP conditions on the creating action (aws:RequestTag, aws:TagKeys), tag policies that standardize keys and allowed values (Task 6.1), required tags in IaC and Service Catalog TagOptions.
  • Reactive: the Config required-tags rule (up to 6 tags; it reports but doesn't prevent creation), the Security Hub CSPM AWS Resource Tagging Standard (set the required keys, or it only checks that any tag exists), and Tag Editor for bulk fixes.
No EC2 instance or volume without a cost center tag (SCP built from the documented condition keys) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyRunInstancesWithoutCostCenter",
      "Effect": "Deny",
      "Action": "ec2:RunInstances",
      "Resource": ["arn:aws:ec2:*:*:instance/*", "arn:aws:ec2:*:*:volume/*"],
      "Condition": { "Null": { "aws:RequestTag/example:cost-center": "true" } }
    }
  ]
}

Condition key names are case-insensitive while tag values aren't, so enforce the exact key spelling with aws:TagKeys. Tags used for ABAC (Task 4.2) also need protecting from being changed by the people they authorize.

Using tags to group, bill and operate

  • Resource Groups collect resources by tag query or by CloudFormation stack (per Region), and Systems Manager targets commands, patching and maintenance windows by tag or resource group.
  • Cost allocation tags must be activated by the management account (user-defined tags and the AWS-generated aws:createdBy, which applies only to resources created after activation) and can be backfilled up to 12 months.
  • For grouping applications, use tags and Resource Groups rather than AppRegistry, which is closed to new customers.

"Every resource must carry a cost center at creation" points to an SCP or IAM condition on aws:RequestTag (with tag policies for allowed values). "Report resources missing the tag" points to Config required-tags or the Security Hub CSPM tagging standard. "Patch all instances tagged prod" points to Systems Manager tag targets.

Enforcing policies centrally

Skill 6.2.3Deploy and enforce policies and configurations from a central source (for example, AWS Firewall Manager).

AWS Firewall Manager

Prerequisites and policy types

Firewall Manager applies security configurations to every account in scope and keeps them there, including accounts and resources created later. It needs Organizations, a Firewall Manager administrator (default administrator set by the management account, plus up to 9 scoped administrators), and AWS Config enabled with continuous recording in every account and Region it covers. Policy types:

  • AWS WAF (web ACLs with first and last rule groups, now able to retrofit existing web ACLs) and Shield Advanced protections (Task 3.1).
  • Security groups: common (apply baseline groups), content audit (flag or fix rules outside an allowed range), usage audit (remove unused and redundant groups) (Task 3.3).
  • Network ACLs (April 2024): first and last rules managed centrally, with account rules allowed between numbers 5,000 and 32,000.
  • Network Firewall (distributed, centralized or imported firewalls), Route 53 Resolver DNS Firewall rule groups, and third-party firewalls (Palo Alto Networks Cloud NGFW, Fortinet).

Scope and remediation

A policy's scope is accounts or OUs (an include list or an exclude list; if both are given, the include list wins), resource types and resource tags (combinable with AND or OR since January 2025). With auto remediation on, Firewall Manager fixes non-compliant resources; off, it only reports. By default, resources that leave the scope keep their protection unless you enable cleanup. Non-compliance and attack findings go to Security Hub CSPM automatically. Each policy costs $100 per Region per month (WAF and Shield Advanced policies are included for Shield Advanced subscribers), and an organization can have 50 policies per Region.

A baseline web ACL with AWS core rules on every prod ALB and API stage in the workloads OU (Firewall Manager policy, built from the documented put-policy structure) 
{
  "Policy": {
    "PolicyName": "org-baseline-waf",
    "SecurityServicePolicyData": {
      "Type": "WAFV2",
      "ManagedServiceData": "{\"type\":\"WAFV2\",\"preProcessRuleGroups\":[{\"ruleGroupType\":\"ManagedRuleGroup\",\"overrideAction\":{\"type\":\"NONE\"},\"managedRuleGroupIdentifier\":{\"vendorName\":\"AWS\",\"managedRuleGroupName\":\"AWSManagedRulesCommonRuleSet\"},\"excludeRules\":[],\"sampledRequestsEnabled\":true}],\"postProcessRuleGroups\":[],\"defaultAction\":{\"type\":\"ALLOW\"},\"overrideCustomerWebACLAssociation\":false,\"sampledRequestsEnabledForDefaultActions\":true,\"optimizeUnassociatedWebACL\":true}"
    },
    "ResourceType": "ResourceTypeList",
    "ResourceTypeList": ["AWS::ElasticLoadBalancingV2::LoadBalancer", "AWS::ApiGateway::Stage"],
    "ResourceTags": [{ "Key": "example:environment", "Value": "prod" }],
    "ExcludeResourceTags": false,
    "RemediationEnabled": true,
    "DeleteUnusedFMManagedResources": true,
    "IncludeMap": { "ORG_UNIT": ["ou-abcd-11111111"] }
  }
}

Applied with aws fms put-policy --cli-input-json file://policy.json from the Firewall Manager administrator account. ManagedServiceData is itself a JSON string.

Firewall Manager depends on AWS Config: an account or Region without Config recording (continuously) isn't evaluated or remediated, and nothing warns application teams. It also doesn't stop teams adding their own permissive rules between the managed ones unless content audit policies or NACL force remediation are used.

"Make sure every new ALB in the organization gets the company WAF rules automatically" points to a Firewall Manager WAF policy with auto remediation. "Remove security groups that allow SSH from anywhere, everywhere" points to a security group content audit policy.

Sharing resources across accounts

Skill 6.2.4Securely share resources across AWS accounts (for example, AWS Service Catalog, AWS Resource Access Manager [AWS RAM]).

AWS RAM

Sharing without copying

AWS RAM shares supported resources (subnets, transit gateways, Resolver rules and DNS Firewall rule groups, prefix lists, IPAM pools, security groups, Network Firewall policies and firewalls, Private CA, Aurora clusters, Glue catalogs, VPC Lattice service networks and many more) with accounts, OUs or the organization. A managed permission sets the most the recipients can do; their own IAM policies still apply. Customer managed permissions can now include conditions and be shared and parameterized (November 2026).

Turn on organization sharing, then share the central Resolver rules with the workloads OU (AWS CLI, network account and management account) 
# From the management account, through RAM (not through Organizations)
aws ram enable-sharing-with-aws-organization

aws ram create-resource-share --name central-dns-rules \
  --resource-arns arn:aws:route53resolver:us-east-1:777700007777:resolver-rule/rslvr-rr-0123456789abcdef0 \
  --principals arn:aws:organizations::555555555555:ou/o-exampleorgid/ou-abcd-11111111 \
  --no-allow-external-principals
  • Enable organization sharing from RAM; turning on trusted access from Organizations doesn't create RAM's service-linked role. Inside the organization there are no invitations.
  • The console default is "Allow sharing with anyone"; choose organization-only for shares that shouldn't leave it.
  • Sharing with the organization or an OU that contains the owner account gives the owner's own principals access too, because the generated resource policy uses "Principal": "*".
  • You can only share resources you own; a shared resource can't be re-shared.

Shared VPCs

The network account owns the VPC and shares subnets (only within the organization; default VPC subnets can't be shared). Participants create their own instances, databases and security groups in those subnets but can't see or change the owner's or other participants' resources, route tables, NACLs or gateways. Participants can't use the owner's security groups (including the default one) unless a security group is shared with them, and the owner can see but not change participant resources. Network controls stay central while workloads stay separate.

AWS Service Catalog

Approved patterns with launch constraints

Service Catalog publishes approved CloudFormation or Terraform (external engine) products in portfolios. A launch constraint names an IAM role Service Catalog uses to provision the product, so end users need only Service Catalog permissions, not rights to create the underlying resources; that's the key security feature. Template constraints narrow parameters (only certain instance types, only private subnets), and TagOptions add required tags.

Products in the platform portfolio launch with the platform role, not the user's permissions (AWS CLI) 
aws servicecatalog create-constraint \
  --portfolio-id port-y3fnkesxxxxx \
  --product-id prod-cfrfxmraxxxxx \
  --type LAUNCH \
  --parameters '{"LocalRoleName": "SCLaunchRole-EncryptedBucket"}'

LocalRoleName (instead of a role ARN) lets the same constraint work in every account the portfolio is shared with, as long as the role exists in each. A product and portfolio pair can have only one launch constraint, and can't have both a launch and a StackSet constraint; template constraints don't apply to Terraform products.

Sharing portfolios

Share portfolios with accounts (which must import them) or, from the management account or a Service Catalog delegated administrator, with the organization or OUs (no import). Recipients get a reference that stays in sync; they can't change products or remove constraints, and can't re-share it. IAM principals aren't carried over unless you use principal name sharing, and its wildcard form (IAM_PATTERN) is a privilege escalation risk: anyone in a recipient account who can create a role with a matching name gets access. Control Tower's Account Factory is itself a Service Catalog product.

A Service Catalog product without a launch constraint provisions with the end user's own permissions, so users need full rights to every resource in the template, which defeats the point. And sharing a portfolio by name pattern can hand products to roles nobody intended to authorize.

"Developers must be able to deploy only approved, compliant stacks without IAM permissions to create those resources" points to Service Catalog with launch constraints. "Workload accounts need to use the central network's subnets without managing the network" points to a shared VPC through RAM.

Key takeaways

  • StackSets: self-managed (two named roles) or service-managed (Organizations, auto-deployment, never the management account, no nested stacks or macros); delegated admins (unscoped) need --call-as DELEGATED_ADMIN; failure tolerance per Region; drift detection doesn't fix.
  • Stack security: stack policies deny all updates once set and can't be deleted; termination protection; service roles are used by anyone who can update the stack; CAPABILITY_NAMED_IAM for named IAM resources.
  • Guard rules (all values must match by default, SKIP when nothing selected), Guard Rules Registry, Guard and Lambda hooks in WARN then FAIL, per account and Region; Config custom policy rules use Guard 2.x; cfn-lint E, W and I rules.
  • CDK bootstrap execution policy defaults to AdministratorAccess and --trust replaces the list; cdk-nag; Terraform state is sensitive (encrypted, versioned, locked S3 backend).
  • Tags: 50 per resource, case-sensitive, aws: reserved, no secrets; require at creation with aws:RequestTag and tag policies, audit with Config required-tags and the tagging standard; Resource Groups, cost allocation tags (management account activates), SSM tag targets; AppRegistry closed.
  • Firewall Manager: Config everywhere with continuous recording; WAF, Shield Advanced, security group, NACL, Network Firewall, DNS Firewall and third-party policies; scope by OU, type and tag; auto remediation; findings to Security Hub CSPM; $100 per policy per Region.
  • RAM: enable from RAM, default allows external sharing, org shares include the owner's principals, managed permissions cap access; shared VPC participants can't touch the owner's network or each other's resources.
  • Service Catalog: launch constraints so users don't need resource permissions (LocalRoleName for shared portfolios), template constraints, TagOptions; organization sharing without import; avoid wildcard principal name sharing.
