4.1: Complex Failure Diagnosis

When an agent gets something wrong in the fourteenth turn, through the third agent in a chain, one time in ten, the instinct is to blame the model. Often the model reasoned correctly from what it was given. This page separates model, harness, tools and data, and makes intermittent failures measurable.

Overview

Skill 4.1

Complex Failure Diagnosis: "Analyzing evidence from complex production failures, including multi-turn, multi-agent, and non-deterministic failures, to isolate the problem origin among model output, agent harness, tools, and data, including model refusals as a failure class and retrieval-grounding failures."

Exam items give the evidence from one failure (a trace, a replay result, the handoffs between agents) and ask where it originated. Root causes at architecture level are in CCAR-P 4.5; finding a failing slice across many traces is skill 3.3.

Check tools, then data, then the harness, and only then the model

Skill 4.1Check from the outside in.

Take a booking-change agent: an orchestrator calls an availability subagent and a pricing subagent, then a payments tool. A guest extended a three-night stay and was charged for two.

isolate.py (isolate.py) 
"""Isolate where a failed booking-change conversation went wrong: tools, data, harness or model.
Evidence comes from the trace plus a replay of the exact captured request."""


def replay_profile(passes: int, runs: int) -> str:
    """Re-send the captured request several times. Non-determinism is a rate, not a mystery."""
    if passes == 0:
        return "deterministic failure: the request itself produces it"
    if passes == runs:
        return "doesn't reproduce: the live request differed from the captured one, or state has changed"
    return f"intermittent: fails {runs - passes} of {runs}; fix or guard, then measure the rate again"


def isolate(e: dict) -> tuple[str, str]:
    """Check from the outside in; the first origin with evidence is reported."""
    if e["stop_reason"] == "refusal":
        return ("model refusal", f"category {e.get('refusal_category') or 'not given'}: check whether the "
                "request was in scope; retry on a different model, and track the refusal rate as its own signal")
    if e["tool_errors"]:
        return ("tool", f"{e['tool_errors'][0]}: fix the tool or return an actionable error the model can use")
    if e["tool_data"] != e["system_of_record"]:
        return ("data", "the tool returned stale or wrong data; the model reasoned correctly from bad input")
    if e["harness_issues"]:
        return ("agent harness", e["harness_issues"][0])
    if e["grounded_claims"] < e["claims"]:
        return ("model output (grounding)", "claims without support in the retrieved or tool data")
    return ("model output", "inputs and tools were correct; adjust prompt or examples, then re-test on replays")


def harness_checks(request: dict) -> list[str]:
    """Faults in how the application built the request, which look like model mistakes."""
    issues = []
    last = request["messages"][-1]
    if last["role"] == "user" and isinstance(last["content"], list):
        kinds = [b["type"] for b in last["content"]]
        if "tool_result" in kinds and "text" in kinds:
            issues.append("text added beside tool_result blocks: a documented cause of empty end_turn replies")
    if request.get("dropped_turns"):
        issues.append(f"history trimmed: {request['dropped_turns']} turns removed, including the guest's dates")
    if request.get("brief_fields_missing"):
        issues.append(f"subagent brief missing {', '.join(request['brief_fields_missing'])}")
    return issues


def first_divergence(chain: list[dict], field: str, truth) -> str:
    """Multi-agent: walk handoffs in order; the first agent whose output has the wrong value owns it."""
    for step in chain:
        if step["output"].get(field) != truth:
            got = step["input"].get(field)
            return f"{step['agent']}: received {got!r}, produced {step['output'].get(field)!r}"
    return "no divergence on this field"
  • Tools: an error on a tool span, an isError result, a timeout, a schema mismatch. Fix the tool, or make its error actionable so the model can recover.
  • Data: the tool succeeded but returned stale or wrong values; compare with the system of record. The model reasoned correctly from bad input, so a prompt change won’t help.
  • Agent harness: your code built the wrong request: trimmed history, a malformed tool-result turn, a subagent brief missing a field, a compaction that dropped an instruction.
  • Model output: everything going in was right and the output was still wrong. Only now is the prompt, examples, effort or model the lever.
  • Refusals are a class of their own, checked first because they arrive as 200s (below).

Replay the exact request several times to turn "sometimes" into a rate

Skill 4.1Turn "sometimes" into a number.

  • Capture the exact request (system prompt, messages, tools, model ID, effort) on failure, then replay it several times. replay_profile() reads the result.
  • Fails every time: the request itself produces the failure, so it can be fixed and verified deterministically.
  • Never fails on replay: the live request differed from what you captured, or state has moved on (a room now booked, a cache expired). Capture is incomplete; that’s the finding.
  • Fails some of the time: sampling variation on a borderline case. Fix it by making the case less borderline (clearer instruction, a tool that computes instead of the model, structured output) or by adding a deterministic check, then measure the rate again. One passing rerun proves nothing.
  • Sampling controls aren’t the fix: from API version 2026-10-21, temperature, top_p and top_k are rejected, so reliability has to come from the design.

Read the request your code built; many 'model errors' are harness faults

Skill 4.1Read the request, not just the response.

  • Text beside tool results: the stop reasons page names adding text blocks right after tool_result as a cause of empty end_turn replies; send only the tool results. (Sonnet 5.5 and Haiku 5.5 document an exception for user input during a loop.) harness_checks() flags it.
  • Mixed server and client tool calls: a reply with an unanswered server tool call must be sent back unchanged with only your tool results; text in that turn, a missing result or a dropped tool definition returns a 400.
  • History trimming and compaction: a trimming rule or a lossy summary removes the turn where the guest gave their dates, and the model answers from what’s left.
  • Streams that end early: a stream cut off before message_stop may raise nothing, leaving a partial answer that looks complete. Check for a stop reason.
  • Truncation: a tool call cut off at max_tokens becomes a malformed action; retry with more output room.

Walk the handoffs to find the first agent or turn where a value went wrong

Skill 4.1Find the first place the value went wrong.

  • Walk the handoffs: record each agent’s input and output for key fields, then find the first agent whose output disagrees with the truth. Here the availability subagent received three nights and produced two; pricing and payments then did their jobs correctly on wrong input.
  • Briefs are the usual culprit: subagents see only their brief, so a field the orchestrator didn’t pass (dates, loyalty tier) is a harness fault upstream, not a subagent reasoning error.
  • Partial results: a subagent cut off by an API error returns partial output with a note, or "Agent terminated early due to an API error". An orchestrator that treats either as a full answer creates a silent gap.
  • Multi-turn: find the turn where the conversation first went off course (a misread date, a stale tool result reused), not the turn where the guest noticed.
  • Injected text: a subagent’s report can carry instructions from content it read. Claude Code marks instruction-shaped patterns, but check worker reports as data.

Treat refusals and grounding failures as their own classes

Skill 4.1Two failure classes with their own evidence.

  • Refusals: HTTP 200 with stop_reason: "refusal"; stop_details names the policy category when present, but branch on the stop reason, since the category can be missing. Decide whether the request was legitimately in scope (a false positive) or not, retry in-scope ones on a different model, and track the rate separately from errors.
  • Grounding failures: claims in the answer with no support in the retrieved passages or tool data. Check retrieval first (was the right passage there?), then the answer’s citations (skill 2.4).
  • Turn each diagnosis into a regression case, with the captured request and the expected outcome, so the fix stays fixed (skill 4.2).

"The charge was wrong, so the model miscalculated; add 'double-check the number of nights' to the prompt" skips the evidence. The handoff record shows the availability subagent produced the wrong value from a correct input, and the brief tells you why. Isolate first, then change the component that failed.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A tool returns a stale price, and the model correctly computes a wrong total from it. Where is the origin?
  1. A. The model
  2. B. The data
  3. C. The harness
  4. D. The prompt
Answer
B
Why
The model reasoned correctly from bad input, so a prompt change won’t help; fix the data source.
Question 2
Scenario
A failure happens on some runs only. What is the first diagnostic step?
  1. A. Run it once more
  2. B. Capture the exact request and replay it several times to measure the rate
  3. C. Lower the temperature
  4. D. Switch models
Answer
B
Why
Replays turn “sometimes” into a number; temperature is rejected on newer API versions anyway.
Question 3
Scenario
A pricing subagent charged for two nights. Its input said two nights, though the guest asked for three. Which component failed?
  1. A. Pricing
  2. B. The upstream step that produced the two-night value, or the brief that omitted the dates
  3. C. The payments tool
  4. D. The model in general
Answer
B
Why
Walk the handoffs to the first output that disagrees with the truth.
Question 4
Scenario
After returning tool results, a harness adds a text note in the same turn, and replies come back empty. What is the cause?
  1. A. A model refusal
  2. B. A harness fault: text after tool_result can produce empty end_turn replies
  3. C. A data error
  4. D. Rate limiting
Answer
B
Why
The stop reasons page names this pattern; send only the tool results.

Key takeaways

  • Check refusals, then tools, data, harness and model output, in that order; the first with evidence is the origin.
  • Capture the exact request and replay it several times: always failing, never failing and sometimes failing each point somewhere different.
  • Many "model errors" are harness faults: text beside tool results, trimmed history, missing brief fields, early stream ends, truncation.
  • In multi-agent systems, walk the handoffs to the first agent whose output disagrees with the truth.
  • Treat refusals (200s, branch on stop reason) and grounding failures as their own classes, and keep every diagnosis as a regression case.
