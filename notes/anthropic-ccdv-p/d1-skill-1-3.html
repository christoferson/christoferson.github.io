1.3: Architecture Selection at Scale

Once a system is live, its traces say whether the architecture still fits: agents that always take the same path, workflows that push a growing tail to people. This page reads that evidence, then turns to the harness and the shared building blocks a team should standardise on.

Overview

Skill 1.3

Architecture Selection at Scale: "Evaluating production cost, reliability, and quality data to decide whether to evolve a running system between workflow and agentic patterns, and selecting the agent harness, framework, and reusable-pattern standards a team should adopt."

Exam items give production numbers for a running system and ask whether to change its pattern, or describe a team’s needs and ask which harness or standard fits. The first choice of pattern for a new system is CCDV-F 1.1 and CCAR-P 1.3; choosing a deployment surface is CCAR-P 1.6.

Traces show when an agent runs a fixed path or a workflow has a growing tail

Skill 1.3What the traces show.

  • An agent that behaves like a workflow: most runs call the same tools in the same order. You pay for the model to rediscover a fixed path each time, and variance creeps in on the runs where it doesn’t.
  • A workflow with a growing tail: the routes handle the common cases, and a rising share falls through to "other" and a human queue because those inputs are too varied to route.
  • Reliability by step: where failures cluster. Agent errors compound over steps; workflow failures sit on a route that can be fixed in code.
  • Cost per resolved case, not per call: an agent that costs more per run can still be cheaper than the people it replaces on the tail.

Anthropic’s advice runs one way by default: find the simplest solution and add complexity only when it improves results. Evolving toward agents needs evidence; evolving back toward code needs only evidence that quality holds.

Decide per system from agreed thresholds: code for the predictable, an agent for the rest

Skill 1.3Rules agreed before the numbers are read.

Take three systems after a quarter in production: an invoice-matching agent, an order-exceptions workflow with five fixed routes, and a support-queries agent.

evolve.py (evolve.py) 
"""Decide from production data whether a running system should move between workflow and agent.
Thresholds are the team's own, agreed before looking at the numbers."""
import json
import sys

MIN_DOMINANT_PATH = 0.85     # agent runs that follow one tool sequence
MAX_QUALITY_DROP = 0.01      # tolerated drop when replacing agent steps with code
MIN_TAIL_SHARE = 0.10        # workflow inputs that fall through to the human queue
MIN_TAIL_SUCCESS = 0.60      # agent success on that tail, measured on shadow traffic


def recommend(r: dict) -> str:
    if r["pattern"] == "agent":
        if (r["dominant_path_share"] >= MIN_DOMINANT_PATH
                and r["agent_quality"] - r["workflow_replay_quality"] <= MAX_QUALITY_DROP):
            saving = 1 - r["workflow_cost"] / r["agent_cost"]
            return (f"move the dominant path to a workflow ({saving:.0%} cheaper per run, same quality); "
                    "keep the agent for the remaining runs")
        return "keep the agent: runs really do vary, or code loses quality"
    if r["fallthrough_share"] >= MIN_TAIL_SHARE and r["agent_tail_success"] >= MIN_TAIL_SUCCESS:
        if r["agent_cost_per_resolved"] < r["human_cost_per_case"]:
            return ("add an agent for the fall-through cases only; keep the workflow routes, "
                    "which are cheaper and easier to audit")
        return "tail is large but an agent costs more than people: improve routing instead"
    return "keep the workflow"


if __name__ == "__main__":
    for r in json.load(open(sys.argv[1])):
        print(f"{r['system']}: {recommend(r)}")

  • Invoice matching: 93% of runs take one path, and a code replay of that path scores within 0.2 points of the agent, so the dominant path becomes a workflow at about a fifth of the cost. The agent stays for the 7% that vary.
  • Order exceptions: 18% fall through to people. On shadow traffic an agent resolves 71% of those at $0.35 against $6.50 for a person, so the agent is added for the tail only; the five routes stay as code.
  • Support queries: runs vary (the top path covers 41%) and code loses six points, so the agent stays.
  • Hybrids are normal: the answer is rarely "replace everything". It is usually code for what’s predictable and an agent for what isn’t.

Replay, shadow and roll out by share before changing a pattern

Skill 1.3Evidence before, monitoring after.

  • Replay first: run the proposed workflow on recorded inputs and grade it against the agent’s outcomes, case by case (paired, as in CCAR-P 4.4).
  • Shadow the agent: before an agent takes the tail, run it on live fall-through cases without acting, and compare with what people did.
  • Roll out by share, with the old path ready, and watch cost per resolved case, escalation rate and quality by segment.
  • Write down the thresholds first, as the code does, so the decision isn’t argued from whichever number looks best afterwards.

"The agent works, so make every system an agent" or "agents are expensive, so convert them all to workflows" are both decided without the data. The question is per system: does the evidence show the runs are predictable, or the tail is large and solvable, at a cost that beats the alternative?

Pick the harness by how much of the loop and sandbox you want to run

Skill 1.3From least to most that you run yourself.

harness.py (harness.py) 
"""Pick the harness from what the team needs to own (one standard per need, not per team)."""

def choose_harness(n: dict) -> str:
    if n["no_infrastructure"] and n["long_running_async"]:
        return "Managed Agents (Anthropic runs the loop and sandbox; beta; check ZDR and HIPAA needs)"
    if n["coding_or_ci_task"]:
        return "Claude Code headless (claude -p) with the team's plugin and managed settings"
    if n["needs_shell_files_subagents_hooks"]:
        return "Agent SDK, self-hosted (you own the container, sessions and sandbox)"
    if n["approval_or_logging_per_tool_call"]:
        return "Messages API with a manual tool loop"
    return "Messages API with the SDK tool runner (beta): your tools, the loop handled for you"
  • Tool runner (SDK helper, beta): runs the loop over your own tools, wraps tool errors and manages the conversation, with max_iterations and compaction support. It’s available in the Python, TypeScript, Go, Java, C#, PHP and Ruby SDKs, and on every listed platform including Bedrock.
  • Manual tool loop: the documentation’s choice when you need human approval, custom logging or conditional execution on each call.
  • Agent SDK, self-hosted: Claude Code’s loop, built-in file and shell tools, subagents, hooks and sessions, in your container. You own sandboxing, sessions and scaling.
  • Claude Code headless: for coding and CI tasks, carrying the team’s plugins and managed settings.
  • Managed Agents (beta): Anthropic runs the loop and sandbox for long-running, asynchronous work. It isn’t ZDR or HIPAA eligible (except fully self-hosted), and it isn’t on Bedrock’s bedrock-runtime.
  • Third-party frameworks: weigh what they add against what they hide. Anthropic’s agent guidance suggests starting with the API directly and understanding any framework’s underlying code.

Share skills, subagents, MCP servers and contracts across teams

Skill 1.3What a platform team should make shared.

  • Skills for procedures: about 100 tokens of metadata each until triggered, loaded on demand, versioned. Custom Skills don’t sync across surfaces, so publish them where each team runs.
  • Shared subagent definitions (reviewer, test runner, researcher) with fixed tools and models, so every team’s "reviewer" means the same thing.
  • MCP servers for shared systems, one per system, owned and versioned, instead of each team wrapping the same API.
  • Plugins to distribute them together, through a marketplace and managed settings (CCAR-P 7.1).
  • Common contracts: structured output schemas, trace attributes and evaluation harnesses, so data from every system can be compared the way this page compares three.
  • One harness per kind of need, not per team, so operations, security review and on-call knowledge carry across systems.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Traces show that 93% of an agent’s runs call the same tools in the same order, and a code replay of that path scores the same. What change fits?
  1. A. Keep the agent for everything
  2. B. Move the dominant path to a workflow and keep the agent for the runs that vary
  3. C. Replace the agent entirely with code
  4. D. Add more tools to the agent
Answer
B
Why
A fixed path in code is cheaper and steadier; the agent stays for the variable remainder.
Question 2
Scenario
A workflow with fixed routes sends a growing share of cases to people because they don’t fit any route. What should the team test?
  1. A. Adding more routes until none fall through
  2. B. An agent for the fall-through cases only, shadowed first against what people did
  3. C. Turning the whole workflow into an agent
  4. D. Raising the human queue’s capacity
Answer
B
Why
Hybrids are normal: keep the routes as code and evaluate an agent on the varied tail.
Question 3
Scenario
Each call needs a human approval step and custom logging. Which harness does the documentation point to?
  1. A. Tool runner
  2. B. A manual tool loop
  3. C. Managed Agents
  4. D. Claude Code headless
Answer
B
Why
The manual loop gives you control on every call; the tool runner automates the loop for you.
Question 4
Scenario
Every team wraps the same internal API differently and defines its own “reviewer” subagent. What should the platform team standardise?
  1. A. Nothing; teams should choose
  2. B. One owned MCP server per shared system and shared subagent definitions, distributed as plugins
  3. C. A single giant system prompt
  4. D. One harness per team
Answer
B
Why
Shared, versioned components make behaviour and data comparable across systems.

Key takeaways

  • Read the traces: a dominant tool path suggests code; a large, varied fall-through tail suggests an agent for that tail.
  • Decide on cost per resolved case and quality by segment, against thresholds set beforehand; hybrids are the usual answer.
  • Prove the change with replays and shadow traffic, then roll out by share with the old path ready.
  • Harness: tool runner for simple loops, manual loop for per-call control, Agent SDK for files, shell and hooks on your infrastructure, Claude Code for coding and CI, Managed Agents when you don’t want to run the loop.
  • Standardise Skills, subagent definitions, MCP servers, schemas and trace attributes, distributed as plugins.
