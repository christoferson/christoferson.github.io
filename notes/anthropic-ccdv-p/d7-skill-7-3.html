7.3: Identity, Secrets, and Audit at Scale

At scale, "the agent did it" isn’t an answer. Each workload needs its own identity, credentials that expire on their own, tool access that follows the person being served, and a record of every consequential action that can’t be quietly edited afterwards.

Overview

Skill 7.3

Identity, Secrets, and Audit at Scale: "Applying enterprise identity and secrets practice to production Claude deployments, including agent identity, workload identity federation replacing static API keys, credential and secrets management, least-privilege tool permissioning, and audit logging of security-relevant agent actions."

Exam items describe how agents authenticate and what they log, then ask which change removes a credential risk or makes an action attributable. Key handling at Foundations level is CCDV-F 7.3; credential exposure and privilege escalation at architecture level are CCAR-P 3.2.

Sources: the Workload Identity Federation page (read on 21 November 2026), and the authentication, Admin API, MCP security and Agent SDK observability pages used earlier, paraphrased. The rule checks and the audit record design are my own; the carrier, files and code are original, and the code is tested without network calls.

Running example. A parcel carrier runs an intake agent that reads damage claims, a payout agent that proposes compensation, and nightly evaluation jobs in CI. Today all three share one API key stored in CI secrets and container environments.

Agent identity: service accounts

Skill 7.3One non-human identity per workload.

  • Service accounts (svac_...) are named, non-human identities in the organisation: no email, password or Console login. They act in a workspace once added as members, and every one is implicitly in the default workspace.
  • Why it matters: in the documentation’s words, a workspace API key is a credential, whereas a service account has credentials. Usage and rate limits are attributed per workspace, and you can see which workload acted as which account.
  • One per workload and environment: intake, payout and evaluation each get their own; production and staging never share one. A shared key makes a leak impossible to scope and an action impossible to attribute.
  • Agent identity isn’t user identity: the service account says which agent called Claude; the person being served is a separate identity carried into tools (below).

Workload Identity Federation instead of static keys

Skill 7.3Tokens that expire in minutes, minted from an identity you already have.

"""Identity, secrets and audit for a parcel carrier's damage-claims agents (Claude API + MCP tools)."""
import hashlib
import json
import os
from anthropic import Anthropic, IdentityTokenFile, WorkloadIdentityCredentials


def client_for(workload: str) -> Anthropic:
    """Each workload federates as its own service account: no static key to store, rotate or leak."""
    cfg = WORKLOADS[workload]
    if os.environ.get("ANTHROPIC_API_KEY"):
        raise RuntimeError("ANTHROPIC_API_KEY is set and would silently win over federation; remove it")
    return Anthropic(credentials=WorkloadIdentityCredentials(
        identity_token_provider=IdentityTokenFile(cfg["token_file"]),   # projected token, rotated by the platform
        federation_rule_id=cfg["rule"], organization_id=ORG, service_account_id=cfg["svac"],
        workspace_id=cfg["workspace"]))


ORG = "00000000-0000-0000-0000-000000000000"
WORKLOADS = {
    "intake-agent": {"svac": "svac_intake", "rule": "fdrl_intake", "workspace": "wrkspc_prod",
                     "token_file": "/var/run/secrets/anthropic.com/token"},
    "eval-ci":      {"svac": "svac_evalci", "rule": "fdrl_evalci", "workspace": "wrkspc_staging",
                     "token_file": "/var/run/secrets/anthropic.com/token"},
}


def review_rules(rules: list[dict]) -> list[str]:
    """Federation rules: narrow match, minimal scope, short tokens, one service account per workload."""
    issues, seen = [], {}
    for r in rules:
        sub = r.get("subject_prefix", "")
        if not sub or (sub.endswith("*") and not (r.get("claims") or r.get("condition"))):
            issues.append(f"{r['id']}: subject match '{sub}' admits too many workloads; narrow it or add claims")
        if r.get("scope", "workspace:developer") != "workspace:developer":
            issues.append(f"{r['id']}: scope {r['scope']} is broader than model calls need")
        if r.get("token_lifetime_seconds", 3600) > 3600:
            issues.append(f"{r['id']}: tokens live {r['token_lifetime_seconds']} s; keep to an hour or less")
        if r["service_account"] in seen and seen[r["service_account"]] != r["env"]:
            issues.append(f"{r['service_account']}: shared by {seen[r['service_account']]} and {r['env']}")
        seen.setdefault(r["service_account"], r["env"])
    return issues


def audit_event(prev_hash: str, actor: dict, tool: str, args: dict, decision: str, outcome: str) -> dict:
    """Append-only record of a security-relevant action, chained so edits or gaps are detectable."""
    body = {"end_user": actor["user"], "agent": actor["agent"], "service_account": actor["svac"],
            "tool": tool, "args_sha256": hashlib.sha256(json.dumps(args, sort_keys=True).encode()).hexdigest(),
            "decision": decision, "approver": actor.get("approver"), "outcome": outcome,
            "trace_id": actor["trace_id"], "prev": prev_hash}
    body["hash"] = hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()
    return body


def verify_chain(events: list[dict]) -> bool:
    prev = "genesis"
    for e in events:
        body = {k: v for k, v in e.items() if k != "hash"}
        if e["prev"] != prev or hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest() != e["hash"]:
            return False
        prev = e["hash"]
    return True
  • How it works: the workload’s platform (AWS, Google Cloud, Entra ID, GitHub Actions, Kubernetes, SPIFFE, Okta) issues a signed JWT; the SDK exchanges it at POST /v1/oauth/token for a short-lived token acting as the service account, and refreshes it before expiry.
  • Three resources: a federation issuer (which identity provider to trust), a service account, and a federation rule (fdrl_...) saying which JWT claims may act as which account, with what scope and token lifetime (default one hour; 60 seconds to 24 hours).
  • Same image everywhere: inject the rule, organisation, service account, workspace and token-file variables per environment, and construct the client with no key.
  • The migration trap: ANTHROPIC_API_KEY sits above federation in the SDK’s credential order, so a leftover key silently wins. client_for() refuses to start if one is set; the documentation’s steps are to configure federation, confirm which credential wins, unset the key everywhere, then delete it.
  • Only as strong as the identity provider: pair it with the provider’s own controls (workload binding, conditional access, audit logs).

Reviewing federation rules and secrets

Skill 7.3The rule is the new secret: review it like one.

  • Narrow matches: an exact subject such as a specific Kubernetes service account, not a trailing wildcard covering a whole organisation’s repositories, unless claims or a condition narrow it further. review_rules() flags repo:acme/* on its own.
  • Minimal scope: workspace:developer covers model calls; broader scopes are for specific products.
  • Short lifetimes: the Console wizard suggests 600 seconds; a 24-hour token is close to a static key. The minted token also never outlives twice the remaining life of the identity token it came from.
  • Replay protection: identity tokens with a jti are single-use by default; reuse fails as jti_reused on the authentication history page.
  • Where static keys remain (a vendor tool that can’t federate): a service account key, not a personal one, in a secrets manager, with an expiry set at creation, IP allowlisting and usage monitored by api_key_id. Admin keys are for organisation management, never for model calls.
  • Tool credentials: keep the database and payment credentials out of the agent’s context and sandbox entirely; inject them in the MCP server or an egress proxy.

Least-privilege tool permissions

Skill 7.3Tools act for the person, within the agent’s role.

  • On behalf of the user: the claims server authorises each call against the verified identity of the customer or officer in the session, not the agent’s blanket access. An MCP server must reject tokens not issued for it and must not pass tokens downstream.
  • Per-agent tool sets: the intake agent reads claims and attaches photos; only the payout agent can propose a payout, and approving it needs an officer (skill 7.1).
  • Scopes that start small: request the minimum and step up for specific actions, rather than wildcard scopes such as claims:*.
  • Review on change: a new tool, server or scope is a permission change and goes through review like code.

Audit logging of agent actions

Skill 7.3Who, through which agent, did what, approved by whom.

  • What to record for every security-relevant action: the end user, the agent and its service account, the tool, a hash of the arguments, the permission decision (allow, deny, ask) and approver, the outcome, and the trace ID that links to the full trace.
  • Tamper evidence: each record carries the hash of the previous one, so verify_chain() detects an edited or deleted entry. Store the log append-only, outside the agent’s reach.
  • Feed the SIEM: the Agent SDK’s security events (tool_decision, tool_result, mcp_server_connection, permission_mode_changed) and the WIF authentication history, with end-user and tenant attributes.
  • Hash, don’t copy: argument hashes and IDs prove what happened without duplicating claimants’ personal data into the log.
  • Review it: alerts on denied actions, unusual approvals and identity anomalies, and a periodic access review of service accounts and rules.

"Rotate the shared API key every 30 days" shortens a leak’s life but keeps a long-lived secret in CI, shared by three workloads, with every action attributed to the same key. Federation gives each workload its own short-lived identity and removes the secret; rotation is for the few keys that can’t be replaced.

Key takeaways

  • Give each workload and environment its own service account; agent identity and the served user’s identity are separate.
  • Replace static keys with Workload Identity Federation, and remove leftover ANTHROPIC_API_KEY values, which override it silently.
  • Review federation rules: exact subjects or extra claims, minimal scope, short token lifetimes, no sharing across environments.
  • Authorise tool calls on behalf of the verified user, with per-agent tool sets and small scopes; keep tool credentials out of the agent’s reach.
  • Log every security-relevant action with user, agent, tool, decision, approver and trace ID, in a tamper-evident, append-only store fed to the SIEM.
