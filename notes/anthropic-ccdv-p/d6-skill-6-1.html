6.1: Cost Architecture at Scale

With many routes, models and tenants, cost is an architecture question: which model handles which request, how much of each prompt is read from cache, which work waits for a batch, and what happens when one customer spends their budget early. This page models the fleet and the controls.

Overview

Skill 6.1

Cost Architecture at Scale: "Evaluating fleet-level optimization strategies using usage and cost data, including cost modeling and forecasting, model routing and cascades across the Claude model family, caching strategy and cache diagnostics, batch-versus-realtime economics, and per-tenant budget enforcement."

Exam items give usage and cost data for several routes and tenants and ask which strategy brings spend down, or what a forecast or cascade will really cost. Finding the hot spot in one system’s telemetry is CCAR-P 4.6; caching mechanics are in CCAR-P 2.5.

Price each route from its own token mix, then forecast by scenario

Skill 6.1Price each route from its own token mix.

Take a translation platform with 300 customer companies: short UI strings on Haiku 5.5, marketing copy on Sonnet 5.5, and a backlog of documentation re-translations. Spend is about $15,000 a month and growing 10% a month.

cost_model.py (cost_model.py) 
"""Fleet cost model for a localisation platform: forecast, cascade routing and per-tenant budgets.
Prices are $/MTok from the pricing page (input, 5-minute cache write, cache read, output)."""

PRICE = {"opus":   (4.00, 5.00, 0.20, 20.00),
         "sonnet": (2.00, 2.50, 0.10, 10.00),
         "haiku":  (0.10, 0.125, 0.01, 0.50)}           # Haiku 5.5, prompts up to 100k tokens


def request_cost(model, uncached, write, read, out, batch=False) -> float:
    p_in, p_w, p_r, p_out = PRICE[model]
    usd = (uncached * p_in + write * p_w + read * p_r + out * p_out) / 1e6
    return usd / 2 if batch else usd                     # Batch API: half price on every token


def monthly_forecast(routes: list[dict], growth=0.0) -> dict:
    """Cost per route per month from volume and token profile; growth is month-on-month."""
    out = {}
    for r in routes:
        per = request_cost(r["model"], r["uncached"], r["write"], r["read"], r["out"], r.get("batch", False))
        out[r["name"]] = round(per * r["requests_per_month"] * (1 + growth), 2)
    out["total"] = round(sum(out.values()), 2)
    return out


def cascade_cost(first: str, second: str, escalate_share: float, tokens: tuple) -> float:
    """Try the cheap model; escalate a share of requests (both calls are paid for those)."""
    c1, c2 = request_cost(first, *tokens), request_cost(second, *tokens)
    return c1 + escalate_share * c2


def enforce(tenant: dict) -> str:
    """Per-tenant monthly budget, enforced in your gateway (workspace spend limits are coarser)."""
    used = tenant["spent"] / tenant["budget"]
    if used >= 1.0:
        return "block new realtime work; queue to batch for next cycle; notify the account owner"
    if used >= 0.9:
        return "degrade: route this tenant to the cheaper model and move bulk jobs to batch"
    if used >= 0.8:
        return "alert the tenant and the account team"
    return "ok"
  • Per request: uncached input, cache writes, cache reads and output, each at its own price. For Sonnet 5.5 that’s $2, $2.50 (5-minute write), $0.10 and $10 per million tokens; output is usually the largest share.
  • Per route per month: per-request cost times volume. The example gives $880 for 5 million UI strings on Haiku, $7,920 for 400,000 marketing requests on Sonnet and $5,940 for 600,000 backlog requests in batches: $14,740.
  • Forecast: volume growth per route, plus planned changes (a new model, a cache fix, moving a route to batch), each as its own scenario. Reconcile monthly against the Usage and Cost Analytics API, grouped by workspace, key and model.
  • Price the tail: Anthropic advises pricing the long, expensive requests separately; a few long documents can outweigh thousands of short strings.

Route to the cheapest model that meets the floor; cascade only with a cheap check

Skill 6.1The cheapest model that meets the quality floor, per request.

  • Static routing: each route gets a tier from evaluations on its own traffic: Haiku 5.5 for UI strings, Sonnet 5.5 for marketing copy, Opus 5.5 for legal text where errors are costly.
  • Cascades: try the cheaper model, check the result (a validator, a confidence rule, a judge), and escalate the rest. Both calls are paid for escalated requests. At 15% escalation, Haiku then Sonnet costs about a fifth of Sonnet alone; at 100% it costs more than Sonnet alone.
  • The check decides the economics: a cheap, reliable check (glossary terms present, placeholders intact, length within limits) makes a cascade work. If the only check is another expensive model call, the saving shrinks.
  • Anthropic’s order: caching, token hygiene, batching and a prompt audit come before model changes, and tuning one model before adding a second.

Cache shared content first and watch cache read share per tenant

Skill 6.1Usually the largest lever.

  • What to cache: per-customer glossaries, style guides and translation memory that repeat across requests, in a stable prefix ahead of the per-string content.
  • Prices: reads are 0.05x input on Opus and Sonnet 5.5 (0.1x on Haiku 5.5); writes cost 1.25x for 5 minutes or 2x for 1 hour. Bursty customers suit the 5-minute TTL; customers who send work every 20 minutes need the 1-hour TTL, or every request rewrites the cache.
  • Diagnostics: cache read share per route and per tenant. Anthropic’s agent-loop median is 84%; well below 80% means something breaks the prefix (a timestamp, a reordered glossary, a changed tool list) or entries expire between calls.
  • Multi-tenant caches: each customer’s prefix is its own cache entry, so many small customers get little reuse. Put shared content (instructions, the general style guide) before per-customer content so it’s reused across all of them.

Batch work that can wait for half the price

Skill 6.1Half price for work that can wait.

  • The discount: 50% on every token, including cached ones, with most batches finishing within an hour and a 24-hour limit. Anthropic calls batching the second-largest free lever after caching for unattended work.
  • Candidates: the documentation backlog, nightly re-translation after glossary updates, evaluation runs. Interactive editor suggestions stay realtime.
  • Costs of batching: latency, a pipeline to submit and collect, best-effort caching, no streaming or fast mode, and not ZDR eligible. For small volumes the engineering can cost more than the saving.
  • Capacity bonus: batches have their own limits, so moving bulk work frees realtime capacity (skill 2.2).

Enforce per-tenant budgets in graduated steps in your own gateway

Skill 6.1Graduated controls in your own gateway.

  • Attribute first: tag every request with the tenant, or give large tenants their own workspace and key, so spend can be grouped per tenant in the Usage and Cost API.
  • 80%: alert the customer and the account team.
  • 90%: degrade gracefully: the cheaper model for that tenant’s routes, bulk work moved to batch.
  • 100%: stop new realtime work, queue the rest for the next cycle, tell the account owner.
  • Organisation-level backstops: workspace spend limits in the Console (batches can slightly exceed them) and the tier’s monthly cap. Neither knows your tenants, so they protect the company, not individual customers.

"Move every route to Haiku to cut cost" skips the cheaper levers and breaks the quality floor on routes that need a stronger model. "Add a Haiku-first cascade everywhere" can raise cost where most requests escalate. Model the routes, fix caching and batch eligibility first, and cascade only where a cheap check makes escalation rare.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A team adds a Haiku-first cascade that escalates 90% of requests to Sonnet. What happens to cost?
  1. A. It falls sharply
  2. B. It can rise above Sonnet alone, since escalated requests pay for both calls
  3. C. It stays the same
  4. D. It halves
Answer
B
Why
Cascades save money only when escalation is rare and the check is cheap.
Question 2
Scenario
Customers send work every 20 minutes and their cache entries are rewritten each time. What should change?
  1. A. Turn off caching
  2. B. Use the 1-hour cache TTL for their prefixes
  3. C. Shorten the prefix
  4. D. Move them to batches
Answer
B
Why
The 5-minute TTL expires between their requests; the 1-hour TTL keeps the prefix warm.
Question 3
Scenario
Many small tenants each get little cache reuse. How should the prompt be ordered?
  1. A. Per-tenant content first
  2. B. Shared instructions and style guides first, then per-tenant content
  3. C. Random order
  4. D. No caching for small tenants
Answer
B
Why
Shared content ahead of per-tenant content is reused across all tenants.
Question 4
Scenario
A tenant reaches 90% of its monthly budget. What is a graduated response?
  1. A. Block all its traffic
  2. B. Degrade: a cheaper model on its routes and bulk work moved to batch
  3. C. Do nothing until 100%
  4. D. Raise the organisation limit
Answer
B
Why
Graduated controls alert, then degrade, then stop, in your own gateway; workspace limits don’t know your tenants.

Key takeaways

  • Model cost per route from its token profile (uncached, writes, reads, output) and volume; forecast by scenario and reconcile with the Usage and Cost API.
  • Route by evaluated quality floor; cascades save money only when a cheap check keeps escalation rare, since escalated requests pay twice.
  • Cache shared content first, choose TTLs from call gaps, and investigate any route reading well under about 80% from cache.
  • Batch unattended work for half price and its own capacity, accepting latency and pipeline cost.
  • Enforce per-tenant budgets in your gateway with alert, degrade and stop steps; workspace limits and the tier cap are backstops.
