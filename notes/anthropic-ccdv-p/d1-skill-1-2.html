1.2: Durable Execution and State Management

Keeping an agent’s work alive when its worker dies, its container is replaced or its model is retired: which state the SDK keeps for you, which it doesn’t, and the application-side record that lets any worker pick the job up again.

Overview

Skill 1.2

Durable Execution and State Management: "Applying session persistence, checkpointing, resumability, and memory architecture patterns to long-running agents that must survive interruption, restart, and model version change."

Exam items describe a long job that lost work (a restarted pod, a store outage, a retired model) and ask which persistence choice would have kept it. Context policies for runs approaching the window limit are skill 1.4; choosing the lifecycle tools at architecture level is CCAR-P 2.6.

Sources: the Agent SDK pages on sessions, session storage and file checkpointing, read on 21 November 2026, and the model deprecations page used for CCAR-P, all paraphrased. The company, files and code are my own; the code is tested against the Python Agent SDK with an in-memory store.

Running example. A legal-operations team re-tags 60,000 stored contracts against a new clause taxonomy. The agent runs for days on autoscaled workers that can be replaced at any time, and its model, a Sonnet version, is due to retire partway through.

Three kinds of state

Skill 1.2Know which one each mechanism saves.

  • The conversation: the SDK session, written to disk automatically as JSONL: prompt, tool calls, results and replies. "Sessions persist the conversation, not the filesystem."
  • Files the agent changed: covered only by file checkpointing, within limits (below), or by git.
  • Business progress: which contracts are done, which rulings were made. No SDK feature owns this; the application must, in its own database, written after each unit.

Sessions: continue, resume, fork

Skill 1.2Returning to a conversation.

  • Within one process: ClaudeSDKClient keeps the session across query() calls.
  • Continue: continue_conversation=True picks up the most recent session in the working directory; fine for one conversation at a time.
  • Resume: resume=<session_id> returns to a specific session. The ID is on every ResultMessage, including error results, so capture it even when a run fails. Resume is how you recover from error_max_turns or error_max_budget_usd with a higher limit.
  • Fork: fork_session=True with resume starts a new session from a copy of the history and leaves the original alone; it branches the conversation, not the files.
  • Where they live: ~/.claude/projects/<encoded-cwd>/<id>.jsonl, on that machine only.

Resuming on another host

Skill 1.2Ephemeral workers need shared state.

  • Three options, from the documentation: a SessionStore adapter, copying the session file to the new host, or not relying on resume at all and passing captured results into a fresh session, which the documentation calls often more robust.
  • The adapter: append and load are required; list_subkeys is needed to restore subagent transcripts, and delete and the list methods are optional. The SDK ships an InMemorySessionStore for tests, reference S3, Redis and Postgres adapters to copy, and a conformance suite.
  • Keys follow the working directory: resume from the same cwd as the original run.
  • Mirror writes are best-effort: local disk first, then append, retried up to three attempts in total. Retries can re-deliver entries, so deduplicate by uuid. A batch that still fails produces a mirror_error message and is dropped while the run carries on, so alert on mirror_error.
  • The store can be the only copy: a run resumed from the store deletes its local transcript at the end. The SDK never deletes from your store, so retention is yours to set.

File checkpointing

Skill 1.2Undoing file edits, within limits.

  • How: enable_file_checkpointing=True plus extra_args={"replay-user-messages": None}; each prompt that starts a turn is a checkpoint (its user message UUID), and rewind_files(uuid) restores files. The conversation isn’t rewound.
  • Tracked: Write, Edit and NotebookEdit in the main conversation.
  • Not tracked: changes made by Bash (unless the main conversation already edited that file), subagent edits, directory changes, remote files. Checkpoints belong to the session that made them.
  • Doesn’t combine with a session store: the SDK refuses to start with both, because file backups stay on local disk. Multi-host jobs use git (or the system of record) for reversibility instead.

A runner that survives restarts and model change

Skill 1.2The ledger decides how to restart (my design).

durable_runner.py (durable_runner.py) 
"""A long-running re-tagging agent that survives worker restarts and a model change.

Two layers of state: the SDK session (the conversation, mirrored to a shared store) and the
application's own progress ledger (what is done, on which model and prompt). The ledger decides."""
import json
from dataclasses import asdict, dataclass, field
from claude_agent_sdk import ClaudeAgentOptions

MODEL = "claude-sonnet-5-5"        # pinned ID, recorded with every checkpoint
PROMPT_VERSION = "retag-v7"


@dataclass
class Ledger:                      # one row per run in your database, updated after every unit
    run_id: str
    model: str
    prompt_version: str
    session_id: str | None = None
    done: list[str] = field(default_factory=list)       # contract IDs already re-tagged and saved
    decisions: list[str] = field(default_factory=list)  # rulings later units must follow


class DedupStore:
    """SessionStore adapter (in memory here; S3, Redis or Postgres in production).
    The SDK may re-deliver a batch on retry, so drop entries whose uuid is already stored."""
    def __init__(self):
        self.rows: dict[tuple, list] = {}

    async def append(self, key, entries):
        rows = self.rows.setdefault((key["project_key"], key["session_id"], key.get("subpath")), [])
        seen = {e.get("uuid") for e in rows if e.get("uuid")}
        rows.extend(e for e in entries if not e.get("uuid") or e["uuid"] not in seen)

    async def load(self, key):
        return self.rows.get((key["project_key"], key["session_id"], key.get("subpath")))


def plan_resume(ledger: Ledger, session_in_store: bool) -> tuple[str, str]:
    """Resume the conversation only when it's the same model and prompt; otherwise start fresh
    from the ledger, which holds everything a new session needs."""
    todo = "Continue re-tagging. Skip these finished IDs: " + ", ".join(ledger.done or ["none"])
    rules = "Rulings so far: " + ("; ".join(ledger.decisions) or "none")
    if ledger.session_id and session_in_store and (ledger.model, ledger.prompt_version) == (MODEL, PROMPT_VERSION):
        return "resume", todo
    return "fresh", f"{todo}\n{rules}"   # new model or prompt: don't carry the old transcript over


def build_options(ledger: Ledger, store, mode: str) -> ClaudeAgentOptions:
    return ClaudeAgentOptions(
        model=MODEL,
        resume=ledger.session_id if mode == "resume" else None,
        session_store=store,            # any worker can resume; no local file checkpointing with a store
        cwd="/srv/retag",               # the store key derives from the working directory: keep it fixed
        allowed_tools=["Read", "Grep", "mcp__contracts__get", "mcp__contracts__save_tags"],
        max_turns=200,
        max_budget_usd=40.0,
    )


def record_unit(ledger: Ledger, contract_id: str, ruling: str | None = None) -> str:
    """Call after save_tags succeeds; the save itself is keyed by contract ID, so a repeat is harmless."""
    if contract_id not in ledger.done:
        ledger.done.append(contract_id)
    if ruling:
        ledger.decisions.append(ruling)
    return json.dumps(asdict(ledger))   # write to the database before starting the next unit
  • Progress is committed per unit: after save_tags succeeds, the contract ID is written to the ledger. Saves are keyed by contract, so a unit repeated after a crash does no harm.
  • Interruption or restart: a new worker reads the ledger and, if the session is in the store and nothing has changed, resumes it with the list of finished IDs.
  • Store outage or lost transcript: a fresh session from the ledger. Little is lost, because the transcript was never the record of what was done.
  • Model version change: the ledger records the pinned model and prompt version. When either changes (here, the current Sonnet retiring on 30 November 2026), the runner starts fresh with the rulings carried over rather than continuing an old model’s transcript. A new model has its own prompt cache, so resuming a long transcript re-reads it uncached anyway. Run the evaluation set on the new model before the switch.

Memory architecture for long runs

Skill 1.2What to keep where.

  • The context window is working memory: compaction summarises it and loses detail, and it doesn’t survive a restart.
  • The memory tool is durable memory for the agent: files it reads and writes outside the window, kept by your application, so they outlast restarts and model changes.
  • The ledger is durable memory for the system: progress, rulings, the model and prompt in use. It is what operators query and what decides a restart.
  • Subagents: their transcripts are separate (subagents/agent-<id> in a store); without list_subkeys, a resume restores only the main conversation.

"Enable a session store so the job can't lose work" covers the conversation only, and only best-effort. It doesn’t record what was finished, doesn’t revert files, and doesn’t help when the model changes. Durable progress lives in application state written after each unit.

Key takeaways

  • Sessions save the conversation; file checkpointing saves Write and Edit changes in one session; the application must save business progress.
  • Capture session_id from every result; resume after restarts or limit errors, fork to try alternatives.
  • Across hosts: a SessionStore keyed by working directory, deduplicating by uuid and alerting on mirror_error, or a fresh session from captured results.
  • File checkpointing can’t be combined with a store and misses Bash and subagent edits; use git for multi-host reversibility.
  • Record the pinned model and prompt version with progress; on a change, evaluate, then start fresh from the ledger rather than resume an old transcript.
