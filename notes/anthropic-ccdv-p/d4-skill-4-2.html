4.2: Incident Response and Learning Loops

During an incident the first question isn’t the root cause but which kind of incident this is, because a provider outage, a bad deploy, a spent budget and a silent quality drop each need a different first move. Afterwards, the incident should leave the system harder to break the same way.

Overview

Skill 4.2

Incident Response and Learning Loops: "Evaluating incident-response options during an LLM-system outage or quality regression, including triage, mitigation, rollback, and communication, and converting the incident into regression evaluations, monitoring coverage, and postmortem findings."

Exam items describe the first minutes or hours of an incident and ask for the best next action, or describe a resolved incident and ask what should change. Finding the origin of one failure is skill 4.1; the runbooks a handed-over system needs are in CCAR-P 6.3.

Classify the incident first: spend cap, provider, your change, or quality

Skill 4.2Classify the incident from its first signals.

Take a tutoring assistant that gives maths hints and essay feedback. A prompt update shipped on Monday; on Wednesday a teacher reported that essay feedback had become generic.

incident.py (incident.py) 
"""Triage, mitigation and learning loop for a tutoring assistant."""


def triage(s: dict) -> str:
    """Classify from signals available in the first minutes."""
    if s["http_429_no_retry_after"]:
        return "spend cap"                                        # retries won't help until the month resets
    if s["provider_status_degraded"] and s["errors_on_all_versions"]:
        return "provider incident"                                # status.claude.com component degraded
    if s["started_within_min_of_deploy"] is not None and s["started_within_min_of_deploy"] <= 30 \
            and s["only_new_version_affected"]:
        return "our change"
    if s["quality_drop"] and not s["error_rate_up"]:
        return "quality regression"                               # 200s that are wrong: no error alert fires
    return "unclear: widen the search (tools, data, tenants)"


MITIGATE = {
    "spend cap":          ["raise the cap or move to a separately billed platform", "shed batch and bulk work"],
    "provider incident":  ["switch to the fallback model or platform", "turn on degraded mode (labelled answers)",
                           "link the status page in the customer notice"],
    "our change":         ["roll back to the previous prompt, model and server pins", "freeze further deploys"],
    "quality regression": ["roll back the last change on the affected segment", "route that segment to human tutors"],
}


def communicate(kind: str, minutes_in: int) -> str:
    who = "students and teachers" if kind != "our change" or minutes_in > 15 else "internal channel only"
    return f"update {who} every 30 minutes: what is affected, what to do meanwhile, next update time"


def learning_loop(inc: dict) -> list[str]:
    """Turn the incident into lasting changes, each with an owner."""
    items = [f"regression case: {c}" for c in inc["captured_requests"]]          # replayable, with the expected outcome
    if inc["detected_by"] != "monitor" or inc["minutes_to_detect"] > 15:
        items.append(f"monitor: alert on {inc['signal_that_moved_first']} (detection took {inc['minutes_to_detect']} min)")
    if inc["rollback_minutes"] > 10:
        items.append("rollback: make the previous version one routing change away")
    items += [f"postmortem action: {a}" for a in inc["contributing_factors"]]
    return items
  • Spend cap: 429s with no retry-after on every route. Retries and fallback models on the same account won’t help until the month resets.
  • Provider incident: errors or overload on every version and route, matching a degraded component on status.claude.com (claude.ai, Console, Claude API, Claude Code, Claude on Cloud Platforms and others). Subscribe to it by webhook or feed so the signal arrives with your alerts. Platforms such as Bedrock have their own health pages.
  • Your change: the problem started soon after a deploy and affects only traffic on the new version. That points to rollback.
  • Quality regression: 200s that are wrong. No error alert fires; it shows up in graded quality, user feedback or complaints, as here, two days late.
  • Unclear: widen to tools, data and specific tenants with the cohort analysis in skill 3.3.

Restore service first, by rollback or fallback, after capturing evidence

Skill 4.2Restore service first; diagnose afterwards.

  • Rollback is the fastest fix for your own change: route traffic back to the previous prompt, model and server pins. It only works if the previous version is still deployable and one routing change away (skill 2.3).
  • Provider incidents: switch to the fallback model or platform, built and tested in advance with its feature differences (skill 2.1), or turn on labelled degraded answers.
  • Quality regressions can be scoped: roll back only the affected segment (essay feedback), or route it to people, while the rest keeps the update.
  • Freeze other changes so the incident doesn’t pick up a second cause.
  • Keep evidence: capture failing requests and traces before rolling back, because they become the regression cases.

Tell users what is affected, what to do, and when the next update comes

Skill 4.2Regular, specific and honest.

  • Who: internal channel immediately; users once impact is confirmed (here, students and teachers during exam season).
  • What: what is affected, what users should do in the meantime (ask a teacher for essay feedback), and when the next update comes. Avoid promising a cause or a fix time before you have one.
  • Cadence: a fixed interval, such as every 30 minutes, even if nothing has changed.
  • Provider incidents: point to the provider’s status page rather than paraphrasing it, and say what you’re doing on your side.
  • Quality incidents need extra care: users may already have acted on wrong answers, so say which answers in which period might be affected.

Turn every incident into a regression case, a monitor and an owned action

Skill 4.2Every incident adds a test, a monitor or a fix.

  • Regression cases: each captured failing request goes into the evaluation suite with the expected behaviour, so the release gate would have blocked this change (skill 5.1).
  • Monitoring coverage: a teacher, not a monitor, found it two days after the update, so the signal that moved first (graded quality on the essay segment) becomes an alert.
  • Rollback speed: 40 minutes to roll back is an action item in its own right.
  • Postmortem findings: contributing factors, not a culprit. Here the prompt shipped without the essay golden set, so the gate gets the missing segment.
  • Follow through: each item has an owner and a date, and the next incident review checks they were done.

"Find the root cause before changing anything" leaves students with generic feedback for hours when a rollback would restore service in minutes. Mitigate first (after capturing evidence), then diagnose, then make sure the same change can’t reach production untested again.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Two days after a prompt update, users report that one kind of answer has become generic. No error alert fired. What is the best first action?
  1. A. Find the root cause before changing anything
  2. B. Capture failing examples, then roll back the update for the affected segment
  3. C. Switch to a fallback model
  4. D. Wait for more reports
Answer
B
Why
Mitigate first, after saving evidence; a scoped rollback restores service while diagnosis continues.
Question 2
Scenario
Every route returns 429 with no retry-after header, on every model. What is likely, and will a fallback model help?
  1. A. A provider outage; switch models
  2. B. The monthly spend cap; models on the same account won’t help until it resets
  3. C. A bad deploy; roll back
  4. D. A ramp limit; retry faster
Answer
B
Why
The spend cap blocks every route; only a separately billed path or a raised cap helps.
Question 3
Scenario
A quality regression went unnoticed for two days. What should the postmortem add?
  1. A. A culprit
  2. B. An alert on the signal that moved first, regression cases from the captured failures, and the missing segment in the release gate
  3. C. A longer prompt
  4. D. More reviewers
Answer
B
Why
Each incident should add a test, a monitor or a fix, each with an owner and a date.
Question 4
Scenario
Users may already have acted on wrong answers during a quality incident. What must communication include?
  1. A. Only that it is fixed
  2. B. Which answers in which period might be affected, and what to do
  3. C. The root cause in detail
  4. D. Nothing until the postmortem
Answer
B
Why
Quality incidents need users to know what to recheck.

Key takeaways

  • Triage first: spend cap, provider incident, your own change, or a quality regression that returns 200s; each has a different first move.
  • Mitigate before diagnosing: roll back pins for your changes, fall back or degrade for provider incidents, scope quality rollbacks to the affected segment.
  • Capture failing requests and traces before rolling back.
  • Communicate at a fixed cadence with impact, workarounds and the next update time; link the provider’s status page.
  • Turn every incident into regression cases, a monitor on the signal that moved first, faster rollback, and owned postmortem actions.
