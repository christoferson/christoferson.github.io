2.2: Scale and Throughput Management

High-volume Claude workloads hit organisation-wide limits shared by every tenant and route. This page finds which limit binds, keeps one tenant or a bulk job from starving the rest, pushes back instead of queueing forever, and moves unattended work to batches when the numbers say so.

Overview

Skill 2.2

Scale and Throughput Management: "Analyzing rate-limit strategy, queueing and backpressure, batch pipeline design, multi-tenant quota and isolation, and capacity planning for high-volume Claude workloads, and identifying whether rate limits, token throughput, or batch economics is the binding constraint."

Exam items give a workload (requests, tokens per request, a deadline, several tenants) and the limits, and ask what binds or which design holds. Handling a 429 when it arrives is skill 2.1; finding the first component to fail in a whole architecture is CCAR-P 1.2.

Sources: the batch processing page (read on 21 November 2026) and the rate limits and pricing pages used for the CCAR-P notes, paraphrased. Limits shown are one tier’s published values for illustration; use your own Console. The SaaS company, workload and code are my own, and the code is tested.

Running example. A review-insights SaaS serves 40 retailer tenants. Its interactive route answers analysts’ questions on Sonnet 5.5 at up to 3,000 requests a minute; each night it scores 400,000 new reviews on Haiku 5.5, due by 06:00.

How the limits work

Skill 2.2What is counted, and where.

  • Three per-model limits, per organisation: requests (RPM), input tokens (ITPM) and output tokens (OTPM). At the Build tier, Sonnet 5.5 has 10,000 RPM, 5 million ITPM and 1 million OTPM. Every tenant and route shares them, and they’re shared across inference_geo values too.
  • Token bucket: capacity refills continuously, so a short burst can hit a limit that the per-minute figure suggests is far away.
  • Cache-aware ITPM: cache reads don’t count; uncached input and cache writes do. OTPM counts actual output, not max_tokens.
  • Ramp limits: a sharp increase can return 429 (ramp_limit_exceeded) below the limits. Raise traffic step by step and start bulk jobs low.
  • Workspaces can have their own lower limits, but the organisation’s still apply. Response headers report remaining capacity and reset times.

Finding the binding constraint

Skill 2.2Utilisation of each limit at peak.

capacity.py (capacity.py) 
"""Capacity check for a review-insights SaaS: which limit binds, and is batch worth it?
Limits are the Build tier for Sonnet 5.5 from the rate-limits page; check your own Console."""
import math

LIMITS = {"rpm": 10_000, "itpm": 5_000_000, "otpm": 1_000_000}   # organisation-wide, shared by all tenants


def utilisation(rpm, uncached_in, output) -> dict:
    """Cache reads don't count toward ITPM; uncached input and cache writes do. OTPM counts actual output."""
    use = {"rpm": rpm, "itpm": rpm * uncached_in, "otpm": rpm * output}
    return {k: round(use[k] / LIMITS[k], 2) for k in use}


def binding(u: dict) -> str:
    k = max(u, key=u.get)
    return f"{k} at {u[k]:.0%}" + (" (over the limit)" if u[k] > 1 else "")


def batch_plan(requests, in_tok, out_tok, price_in, price_out, deadline_h) -> dict:
    """Batches: half price, up to 100,000 requests per batch, most finish within an hour, expire at 24 h."""
    realtime = requests * (in_tok * price_in + out_tok * price_out) / 1e6
    return {"batches": math.ceil(requests / 100_000),
            "realtime_usd": round(realtime), "batch_usd": round(realtime / 2),
            "fits_deadline": deadline_h >= 24 or "plan a realtime top-up for anything unfinished"}


if __name__ == "__main__":
    print("chat, now:        ", binding(utilisation(3_000, uncached_in=1_800, output=250)))
    print("chat, after cache:", binding(utilisation(3_000, uncached_in=1_200, output=250)))
    print("nightly scoring:  ", batch_plan(400_000, 900, 60, price_in=0.10, price_out=0.50, deadline_h=8))
run_output.txt (Output) 
chat, now:         itpm at 108% (over the limit)
chat, after cache: otpm at 75%
nightly scoring:   {'batches': 4, 'realtime_usd': 48, 'batch_usd': 24, 'fits_deadline': 'plan a realtime top-up for anything unfinished'}
  • Interactive route, now: RPM is at 30%, but 1,800 uncached input tokens per request puts ITPM at 108%. Token throughput binds, not request rate, so more concurrency or an RPM increase wouldn’t help.
  • After caching: moving 600 tokens of tenant context into the cached prefix drops ITPM to 72%, and OTPM (75%) becomes the highest. The next lever is output length, not input.
  • Nightly scoring: four batches (100,000 requests each) at $24 instead of $48. The saving is small; the bigger gain is that batches have their own limits and aren’t ramp-limited, so the bulk job stops competing with analysts’ questions.

Queueing, backpressure and tenants

Skill 2.2Admission control in front of shared limits.

admission.py (admission.py) 
"""Admission control in front of the shared organisation limits: per-tenant fairness, priority,
and backpressure instead of an unbounded queue."""
import time


class Bucket:
    def __init__(self, rate_per_s: float, burst: float, clock=time.monotonic):
        self.rate, self.cap, self.clock = rate_per_s, burst, clock
        self.tokens, self.t = burst, clock()

    def take(self, n=1.0) -> bool:
        now = self.clock()
        self.tokens = min(self.cap, self.tokens + (now - self.t) * self.rate)
        self.t = now
        if self.tokens >= n:
            self.tokens -= n
            return True
        return False


class Gate:
    def __init__(self, tenant_rates: dict, max_queue: int, clock=time.monotonic):
        self.tenants = {t: Bucket(r, r * 2, clock) for t, r in tenant_rates.items()}  # 2 s of burst each
        self.queue, self.max_queue = [], max_queue

    def admit(self, tenant: str, priority: str) -> str:
        if self.tenants[tenant].take():
            return "send"
        if priority == "interactive":
            return "reject: 429 to the caller with Retry-After"      # fail fast; a person is waiting
        if len(self.queue) >= self.max_queue:
            return "reject: queue full, shed bulk load"              # backpressure, not unbounded memory
        self.queue.append(tenant)
        return "queued"
  • Per-tenant buckets: each tenant gets a share of the organisation’s limits in your gateway, so one tenant’s spike can’t take everyone else’s capacity.
  • Priority: interactive requests over bulk. An interactive request over quota fails fast with a 429 and Retry-After, because someone is waiting.
  • Bounded queue: bulk work waits up to a maximum depth, then the gateway sheds load. An unbounded queue turns a short overload into hours of latency and memory pressure.
  • Isolation beyond quotas: separate workspaces and keys for large or regulated tenants give their own limits, spend controls and usage reporting. Per-tenant prompts, caches and data stay separate in your application.

Batch pipeline design

Skill 2.2What the Message Batches API gives and requires.

  • Economics: half price on every token. Up to 100,000 requests or 256 MB per batch; most finish within an hour; anything not processed in 24 hours expires.
  • Results: available for 29 days, in any order, so match by custom_id. Each request ends succeeded, errored, canceled or expired; the last three aren’t billed. Resubmit errored (if retryable) and expired requests.
  • Not allowed in a batch: streaming, fast mode, server-side fallbacks and max_tokens: 0. Tools, server tools, thinking and multi-turn requests are fine.
  • Caching is best-effort, because requests run concurrently in any order. Use the 1-hour cache for shared context.
  • Deadlines: "most within an hour" isn’t a guarantee, and processing can slow with demand. For an 8-hour deadline, submit early, watch request_counts, and have a realtime top-up path for anything unfinished.
  • Constraints: batches aren’t ZDR eligible (29-day retention) and are available on the Claude API, Claude Platform on AWS and Google Cloud (Anthropic managed), not Bedrock’s bedrock-runtime. They can slightly overshoot a workspace spend limit.

Capacity planning

Skill 2.2Plan from peak traffic and tokens per request.

  • Model the peak minute, not the daily average, in all three units, per model. Add the bursts the token bucket will see.
  • Count uncached input, so the cache hit rate is a capacity input. A deploy that breaks the cache can push ITPM over the limit with no change in traffic.
  • Separate realtime and bulk: bulk to batches, or to off-peak hours with a ramp.
  • Headroom and triggers: plan to stay below about 70–80% of each limit, and request a tier or custom limit increase when forecasts cross it, well before launch.
  • Watch the spend cap too: at the monthly cap, the API returns 429s until the month resets, whatever the per-minute headroom.

"Requests are well under RPM, so we have capacity" misses token throughput: long prompts can exhaust ITPM at a third of the request limit. "Move the bulk job to batches to save money" is right, but the stronger reason is often that it frees realtime capacity.

Key takeaways

  • Limits are per organisation and model, in RPM, ITPM and OTPM, refilled continuously; cache reads don’t count toward ITPM, actual output counts toward OTPM.
  • Compute utilisation of all three at peak; the highest binds, and fixing it moves the constraint.
  • Put per-tenant quotas, priority and a bounded queue in front of the shared limits; fail interactive requests fast and shed bulk load.
  • Batches: half price, own limits, no ramp limits, results by custom_id within 24 hours; no streaming, fast mode or fallbacks; plan a top-up for tight deadlines.
  • Plan capacity from the peak minute in tokens, with headroom, cache hit rate and the spend cap included.
