2.1: Reliability Engineering for Claude Services

A production Claude service fails in several distinct ways, and each needs a different response: wait, back off, stop, switch model, switch platform, or give the model more room. This page sorts them, then builds the retry, breaker, fallback and degradation layer around them.

Overview

Skill 2.1

Reliability Engineering for Claude Services: "Evaluating and applying resilience patterns for production Claude integrations, including retry and backoff design, circuit breakers, graceful degradation, and cross-model, cross-region, and cross-platform fallbacks that distinguish rate limits from safety refusals from context-window stops while respecting per-platform feature parity."

Exam items show a resilience design and its symptoms in production and ask which change makes it correct. The error semantics at Foundations level are in CCDV-F 2.4; duplicate side effects and idempotency are in CCAR-P 3.8; throughput limits are skill 2.2.

Sources: the stop reasons page (read on 21 November 2026) and the errors, refusals and fallback, rate limits and Bedrock pages used for the earlier notes, all paraphrased. The decision table, breaker settings and the newsroom are my own; the code is tested with fake responses and a fake clock.

Running example. A newsroom runs an article-summary service with a 99.5% availability objective. It calls the Claude API with Opus 5.5, attaches source documents through the Files API and uses web search; a secondary path runs on Amazon Bedrock.

Errors versus stop reasons

Skill 2.1Two channels that must not be merged.

  • Errors are HTTP 4xx or 5xx: the request wasn’t processed. A 429 is a rate limit, a ramp limit or the tier’s spend cap (no retry-after, keeps failing); 529 is overload; 500 and 504 are server errors (use streaming for long requests); 400, 401 and 403 are your request.
  • Stop reasons come only from successful responses. refusal is a 200 from the safety classifiers, with stop_details naming the category. max_tokens and model_context_window_exceeded mean the output was cut off: treat it as truncated.
  • Why it matters: a refusal or a truncation never reaches an exception handler, so a retry wrapper that only catches errors misses them, and one that retries everything treats them as transient.

One response per failure class

Skill 2.1Classify first, then act.

resilience.py (resilience.py) 
"""Resilience layer for a newsroom's article-summary service.
Primary: Claude API. Secondary: Amazon Bedrock (bedrock-runtime), which lacks some features."""
import random

# Each outcome class gets its own response; one retry loop for everything is the bug to avoid.
ACTIONS = {
    "rate_limit":   "wait retry-after, same target",
    "spend_cap":    "no retry here; alert, move traffic to the other platform",
    "overloaded":   "backoff with jitter, count toward the breaker",
    "server_error": "backoff with jitter, count toward the breaker",
    "bad_request":  "fail fast; fix the request",
    "refusal":      "retry once on a different model; record the refusal",
    "truncated":    "raise max_tokens or continue; never switch model for this",
    "ok":           "return",
}


def classify(status: int, headers: dict, body: dict) -> str:
    if status == 429:
        capped = "retry-after" not in headers or body.get("error_code") == "enforced_spend_limit_reached"
        return "spend_cap" if capped else "rate_limit"
    if status == 529:
        return "overloaded"
    if status >= 500:
        return "server_error"
    if status >= 400:
        return "bad_request"
    if body.get("stop_reason") == "refusal":
        return "refusal"
    if body.get("stop_reason") in ("max_tokens", "model_context_window_exceeded"):
        return "truncated"
    return "ok"


def backoff(attempt: int, base=1.0, cap=30.0) -> float:
    return random.uniform(0, min(cap, base * 2 ** attempt))      # full jitter


class Breaker:
    """Opens after `threshold` overload/server errors in a row; probes again after `cooldown` seconds."""
    def __init__(self, threshold=5, cooldown=60.0, clock=None):
        self.threshold, self.cooldown, self.clock = threshold, cooldown, clock
        self.failures, self.opened_at = 0, None

    def allow(self) -> bool:
        if self.opened_at is None:
            return True
        return self.clock() - self.opened_at >= self.cooldown         # half-open: let one probe through

    def record(self, outcome: str):
        if outcome in ("overloaded", "server_error"):
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = self.clock()
        elif outcome == "ok":
            self.failures, self.opened_at = 0, None


BEDROCK_RUNTIME_LACKS = {"web_search", "files_api", "fallbacks"}     # per the Bedrock page; check yours


def adapt(request: dict, platform: str) -> tuple[dict, list[str]]:
    """Feature parity: degrade deliberately and say so, rather than send a request that fails."""
    if platform != "bedrock-runtime":
        return request, []
    req, notes = dict(request), []
    if "web_search" in req.get("features", []):
        req["features"] = [f for f in req["features"] if f != "web_search"]
        notes.append("summary written without live web sources")
    if req.get("file_id"):
        req["document_text"] = req.pop("file_id_text")               # inline the text we kept for this case
        req.pop("file_id")
        notes.append("document sent inline instead of by Files API reference")
    req.pop("fallbacks", None)                                       # server-side fallback: do it client-side
    return req, notes
  • Rate limit: honour retry-after on the same target. Switching model doesn’t help when the limit is the organisation’s.
  • Spend cap: retries fail until the month resets. Alert, and if a separately billed platform exists, move traffic there (my reasoning).
  • Overload and server errors: back off with jitter and count them toward the circuit breaker.
  • Refusal: the documentation’s answer is to retry on a different Claude model, and to monitor refusals as their own signal.
  • Truncation: raise max_tokens, continue the response, or trim the input. Another model has the same limit problem. If a tool_use block was cut off, retry with more output room.
  • Bad request: fail fast; retrying a malformed request only adds load.

Retries, backoff and circuit breakers

Skill 2.1Bounded retries, and a switch for when they won’t help.

  • The SDK already retries: twice by default, for 408, 409, 429 and 5xx, honouring retry-after and the x-should-retry header. Your own retries multiply on top, so keep the total bounded.
  • Exponential backoff with full jitter and a cap stops a fleet of clients retrying in step.
  • Circuit breaker: after several overload or server errors in a row, stop calling that target for a cooldown, send traffic to the fallback, then let one probe through. Refusals and truncations don’t trip it: they say nothing about the target’s health.
  • Mid-stream errors arrive after the 200, as an error event; a stream cut off before message_stop may raise nothing. Check that a stream completed before treating it as a success.

Fallbacks: model, region, platform

Skill 2.1Three distances to fall back.

  • Cross-model: for refusals, and as a design choice when a model is overloaded (the documentation doesn’t prescribe it for 529). Options are server-side fallback (beta fallbacks, up to three models; Claude API and Google Cloud Anthropic-managed only; not batches), the SDK middleware (any platform), or your own retry with fallback credit. Configure it on every request path, including workers and subagents, and stay on the fallback model for later turns. Haiku 5.5 has no server-side fallback or credit.
  • Cross-region: on Bedrock, global endpoints route across regions, and regional endpoints (us, eu, jp, apac) cost about 10% more but are needed for residency. On the Claude API, inference_geo is global or us, and rate limits are shared across geos, so changing geo isn’t a way round a rate limit.
  • Cross-platform: a second surface protects against a platform-wide outage or a spend cap. Model IDs, lifecycle dates and limits differ by platform; pin each one and test the path regularly, or it fails the day you need it.

Feature parity and graceful degradation

Skill 2.1The fallback must accept the request you send it.

  • Bedrock’s bedrock-runtime lacks the Files API, server tools (web search, web fetch, code execution), Agent Skills, the MCP connector, Batches, server-side fallback and automatic prompt caching. Bedrock’s bedrock-mantle endpoint offers the native Messages API shape with full parity, and Claude Platform on AWS is Anthropic-operated.
  • Degrade deliberately: adapt() drops web search and says the summary has no live sources, inlines the document text the service kept, and moves fallback to the client. A silent failure on the secondary path is worse than a labelled, reduced answer.
  • Other degradations (my list): a cached or extractive summary, a smaller model for non-critical routes, queueing non-urgent work for later, or a clear "try again" to the user, chosen per route before the incident.

"Retry the same request on the fallback platform" sounds like a fallback but fails if the request uses features that platform lacks, and it fails at the worst moment. A fallback path is a different request, built and tested ahead of time, with its degradations stated.

Key takeaways

  • Errors (4xx, 5xx) and stop reasons (200s) are different channels; refusals and truncations never raise.
  • Rate limit: wait as told. Spend cap: stop, alert, move platforms. Overload: back off and trip a breaker. Refusal: a different model. Truncation: more output room.
  • Bound total retries, remembering the SDK’s own two, and use jittered backoff and a breaker with a half-open probe.
  • Fallbacks go cross-model, cross-region or cross-platform; configure them on every path and test them before the incident.
  • Respect feature parity: build the fallback request for what that platform supports, and label the degraded answer.
