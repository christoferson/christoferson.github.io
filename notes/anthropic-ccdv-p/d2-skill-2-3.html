2.3: Production MCP and Change Management

Three things change under a running Claude service: the MCP servers it calls, the model it runs on and the prompts it uses. This page treats all three as releases: versioned, tested against what they might break, checked on every platform, rolled out in stages and reversible.

Overview

Skill 2.3

Production MCP and Change Management: "Applying production MCP operation and change-management practice to MCP server deployments, model version migrations, and prompt updates, including remote MCP deployment and authentication, tool and schema versioning, migration testing against breaking behavior changes, platform-specific configuration parity and gateway/routing architectures, prompt versioning, and progressive rollout with rollback."

Exam items describe a change that went wrong (a renamed tool, a new model that answers differently, a feature missing on one platform) and ask which practice would have caught it. Choosing a migration response at architecture level is CCAR-P 4.7; MCP authentication posture is CCAR-P 3.2.

Run remote MCP servers over Streamable HTTP with tokens issued for them

Skill 2.3Deployment and authentication.

  • Transport: remote servers use Streamable HTTP (SSE is deprecated); stdio is for local processes. The Messages API MCP connector reaches only public HTTPS servers and supports tools only.
  • No sessions in the protocol: state lives behind explicit handles returned by a tool, checked against the caller’s authorisation on every call, with their lifetime stated in the tool description.
  • Authentication: a server must reject tokens not issued for it and must never pass a client’s token downstream. Start with minimal scopes and step up. tools/list may differ by the caller’s scopes, but not by connection.
  • Operations: servers validate inputs, enforce access control, rate-limit calls and sanitise outputs; clients set timeouts and log tool use. Return tools in a deterministic order, which the specification notes improves prompt cache hit rates.
  • Two error channels: JSON-RPC protocol errors (unknown tool, malformed request) and tool execution errors with isError: true, which carry actionable text the model can correct from.

Ship additive changes in place; publish breaking ones under a new tool name

Skill 2.3Know whether a change breaks clients before it ships.

schema_diff.py (schema_diff.py) 
"""Classify a change to an MCP tool catalogue as breaking or additive before it ships."""


def diff(old: list[dict], new: list[dict]) -> dict:
    o, n = {t["name"]: t for t in old}, {t["name"]: t for t in new}
    breaking, additive = [], []
    for name in o.keys() - n.keys():
        breaking.append(f"{name}: removed")
    for name in n.keys() - o.keys():
        additive.append(f"{name}: new tool")
    for name in o.keys() & n.keys():
        oi, ni = o[name]["inputSchema"], n[name]["inputSchema"]
        for p in set(ni.get("required", [])) - set(oi.get("required", [])):
            breaking.append(f"{name}: new required input {p}")
        for p, spec in oi.get("properties", {}).items():
            if p not in ni.get("properties", {}):
                breaking.append(f"{name}: input {p} removed")
            elif spec.get("type") != ni["properties"][p].get("type"):
                breaking.append(f"{name}: input {p} changed type")
        for p in set(ni.get("properties", {})) - set(oi.get("properties", {})) - set(ni.get("required", [])):
            additive.append(f"{name}: optional input {p}")
        oo = o[name].get("outputSchema", {}).get("properties", {})
        for f in oo.keys() - n[name].get("outputSchema", {}).get("properties", {}).keys():
            breaking.append(f"{name}: output field {f} removed")
    return {"breaking": sorted(breaking), "additive": sorted(additive)}


def plan(d: dict, name: str) -> str:
    if not d["breaking"]:
        return "ship in place; clients see it on the next tools/list, and subscribed clients get list_changed"
    return (f"publish the changed tool under a new name (for example {name}_v2) beside the old one, "
            "move clients over, then retire the old name on a stated date")
  • Additive: a new tool, an optional input, a new output field. Ship in place; clients see it on the next tools/list, and subscribed clients get notifications/tools/list_changed.
  • Breaking: a removed or renamed tool, a new required input, a changed type, a removed output field. Prompts, few-shot examples, cached tool lists and agents built against the old shape all depend on it.
  • Versioning by name: publish the changed tool under a new name such as get_fees_v2 beside the old one, move clients, then retire the old name on a stated date. Tool names allow letters, digits, _, - and ..
  • Declare outputs: with an outputSchema, servers must return conforming structuredContent (plus the JSON as text, for older clients), and clients should validate it. A schema change is then visible in review.
  • Collisions: clients that aggregate several servers should prefix tool names with a server identifier, since two servers can both expose search.

Pin model snapshots, version prompts, and gate migrations per segment

Skill 2.3Behaviour changes are breaking changes too.

  • Pin snapshot IDs and record which one each route uses. Models get at least 60 days’ notice before retirement on Anthropic-operated platforms; partner platforms set their own dates.
  • Read the breaking changes for the target model and API version. For example, API version 2026-10-21 rejects temperature, top_p and top_k with a 400, a request-level break that no amount of prompt testing would find.
  • Find every caller: the Console usage export by key and model, aliases, subagent definitions, batch jobs.
  • Prompts are versioned artefacts: stored in source control with an ID, logged on every trace, changed through review, and released through the same gate as code.
  • Migration testing: run the golden set per segment on the candidate, paired against the current version, and gate on no segment regressing beyond tolerance (migration_gate below). A higher average can hide a segment that got worse.

Check every platform supports the release, and route through a gateway

Skill 2.3The same release has to work everywhere it runs.

  • Per-platform configuration: model IDs, available features and lifecycle dates differ. Bedrock’s bedrock-runtime, for example, lacks the MCP connector and server tools, so a release that adds web search must say what routes on that platform do instead.
  • A parity check in the gate: parity() fails the release when any platform lacks the model mapping or a feature the release uses.
  • Gateways: one place for credentials, usage attribution, budgets, audit logs and provider switching. For Claude Code, the documentation notes the gateway becomes infrastructure you operate and must keep up with new features, or they break. Distribute its base URL through managed settings, and pin it with allowedProviders.
  • Routing: a gateway or router can split traffic by version for rollout and send a route back to the old version in one change, which is what makes rollback fast.

Roll out in stages with automatic rollback to the previous pins

Skill 2.3One gate for servers, models and prompts.

rollout.py (rollout.py) 
"""One release gate for MCP servers, model versions and prompts: test, check parity, roll out, roll back."""

STAGES = [0.01, 0.10, 0.50, 1.00]


def migration_gate(candidate: dict, baseline: dict, tolerance=0.01) -> list[str]:
    """Golden-set results per segment for the new version against the current one."""
    problems = []
    for seg, score in baseline.items():
        if candidate.get(seg, 0) < score - tolerance:
            problems.append(f"regression on {seg}: {candidate.get(seg, 0):.2f} vs {score:.2f}")
    return problems


def parity(release: dict, platforms: dict) -> list[str]:
    """Every platform the service runs on must have the model ID and the features the release uses."""
    out = []
    for name, p in platforms.items():
        if release["model"] not in p["models"]:
            out.append(f"{name}: no model ID mapped for {release['model']}")
        for f in set(release["features"]) - set(p["features"]):
            out.append(f"{name}: lacks {f}")
    return out


def next_step(stage: float, live: dict, base: dict) -> str:
    if live["error_rate"] > 2 * base["error_rate"] or live["quality"] < base["quality"] - 0.02:
        return "rollback: route 100% to the previous version (prompt, model and server pins kept)"
    if live["refusal_rate"] > base["refusal_rate"] + 0.005:
        return "hold: refusals up; investigate before widening"
    later = [s for s in STAGES if s > stage]
    return f"advance to {later[0]:.0%}" if later else "complete"
  • Before traffic: the migration gate (golden set per segment) and the parity check.
  • Stages: 1%, 10%, 50%, 100%, each compared with the current version’s live baseline.
  • Rollback triggers: error rate doubling, or quality on sampled grading dropping two points. Rollback routes all traffic to the previous pins, so a release must keep the old prompt, model ID and server version deployable.
  • Hold, don’t widen, on a signal that needs a person, such as a rise in refusals.

"Rename the tool and update the prompt in the same deploy" breaks every client that cached the old list or runs an older prompt version during the rollout. "Switch the model alias to the new version everywhere at once" gives no stage at which to notice a regression and no quick way back.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A server team renames a tool and updates the prompt in the same deploy. Some clients fail during the rollout. What practice would have avoided this?
  1. A. Deploying faster
  2. B. Publishing the changed tool under a new name beside the old one, moving clients, then retiring the old name
  3. C. Asking clients to refresh more often
  4. D. Removing the old tool first
Answer
B
Why
A rename is a breaking change; running both names during migration keeps older clients and prompts working.
Question 2
Scenario
A candidate model scores higher on average than the current one on the golden set. Is that enough to ship?
  1. A. Yes
  2. B. No; gate on no segment regressing beyond tolerance, comparing paired results per segment
  3. C. Yes, if latency is lower
  4. D. Only if the prompt is unchanged
Answer
B
Why
A higher average can hide a segment that got worse.
Question 3
Scenario
A release adds web search, and one deployment runs on a platform without server tools. Where should this be caught?
  1. A. In production
  2. B. In a parity check in the release gate that fails when a platform lacks a feature the release uses
  3. C. By users reporting errors
  4. D. By the model at runtime
Answer
B
Why
Feature support differs by platform; the gate should check before traffic.
Question 4
Scenario
An MCP server receives a client’s access token. Can it pass that token to a downstream API?
  1. A. Yes, to save a login
  2. B. No; it must reject tokens not issued for it and never pass a client’s token downstream
  3. C. Only for read-only calls
  4. D. Only inside a VPC
Answer
B
Why
Token passthrough is forbidden by MCP’s security practices; the server gets its own credentials for downstream calls.

Key takeaways

  • Remote MCP: Streamable HTTP, audience-checked tokens, no passthrough, minimal scopes, explicit state handles, deterministic tool order, actionable isError results.
  • Diff tool catalogues before shipping; ship additive changes in place and breaking ones under a new name beside the old.
  • Pin model IDs and version prompts; test migrations per segment on a golden set and read the API’s breaking changes.
  • Check parity on every platform the release runs on; gateways centralise credentials, budgets and routing but must be kept current.
  • Roll out in stages against a live baseline with rollback triggers, keeping the previous version deployable.
