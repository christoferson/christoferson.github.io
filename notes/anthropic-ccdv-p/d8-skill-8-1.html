8.1: Parallel Agent Orchestration for Engineering Work

A migration across a hundred packages can run as a hundred agents at once, or turn into a hundred conflicting branches. The difference is in the isolation, the way the work is cut up, the order changes come back in, and reading the fleet’s results as a whole.

Overview

Skill 8.1

Parallel Agent Orchestration for Engineering Work: "Evaluating parallel fan-out patterns for large engineering tasks, including parallel agents on isolated worktrees, task decomposition, and merge and conflict strategy, and diagnosing fleet-level failure modes from fleet telemetry."

Exam items describe a fan-out of coding agents and its results (conflicts, failing tests, a few runs that never finish) and ask what to change in the plan. Orchestration patterns in general are skill 1.1; reviewing what the fleet produces is skill 8.2.

Give each agent its own worktree, set up so its tests can run

Skill 8.1Each agent gets its own files and branch.

migrator.md (.claude/agents/http-migrator.md) 
---
name: http-migrator
description: Migrates one package from the old HTTP client to the new one. Use for each task in the migration plan.
isolation: worktree
tools: Read, Edit, Grep, Glob, Bash(npm test *), Bash(git add *), Bash(git commit *)
---

You get one package and an exact file list. Change only those files. Replace calls to the old
client with the new one following MIGRATION.md, run that package's tests, and commit on your
branch. If a change needs a file outside your list, stop and report it instead of editing it.
  • What a worktree is: a separate working directory on its own branch, sharing the repository’s history and remote. claude --worktree <name> creates one under .claude/worktrees/; subagents get one each with isolation: worktree in their definition.
  • Isolation is enforced: an isolated session can’t edit files in the main checkout, run commands there, or redirect git into it. The checks read paths and command text, so a cp or shell redirect into the main checkout is left to permissions and the sandbox.
  • A fresh checkout needs setup: dependencies are installed per worktree, and gitignored files such as .env are copied only if listed in .worktreeinclude. Missing setup is the usual cause of tests failing in every worktree at once.
  • Base branch: by default worktrees branch from the remote default branch; worktree.baseRef: "head" branches from your current work instead.
  • Shared things: the .git directory, project-scope plugins and permission approvals (saved to the main checkout’s local settings) are shared across worktrees.
  • Cleanup: subagent worktrees without changes are removed when the agent finishes; ones with changes stay until a periodic sweep. Headless runs don’t clean up their worktrees, so the pipeline must.

Cut the task into disjoint file sets, and hold shared files for one serial step

Skill 8.1Disjoint file sets, right-sized tasks.

Take a TypeScript monorepo of about 80 packages moving from an old HTTP client to a new one. Packages depend on each other, a lockfile and a shared HTTP wrapper are touched by almost everything, and the team wants it done in a day.

fanout.py (fanout.py) 
"""Fan out a monorepo migration (old HTTP client -> new one across many packages) to parallel
agents in isolated worktrees, then diagnose the fleet from its run records."""
from collections import Counter

SHARED = {"package-lock.json", "tsconfig.base.json", "packages/common/http/index.ts"}   # one owner, done last


def plan(packages: dict[str, set], depends_on: dict[str, set], max_files=40) -> dict:
    """Disjoint file sets per agent; shared files held back; merge order follows dependencies."""
    tasks, held = [], set()
    for pkg, files in packages.items():
        own = files - SHARED
        held |= files & SHARED
        for i in range(0, len(sorted(own)), max_files):          # split oversized packages
            tasks.append({"id": f"{pkg}#{i // max_files}", "package": pkg, "files": set(sorted(own)[i:i + max_files])})
    order, done = [], set()
    while len(done) < len(packages):                             # dependencies merge first
        ready = sorted(p for p in packages if p not in done and depends_on.get(p, set()) <= done)
        if not ready:
            raise ValueError("dependency cycle")
        order += ready
        done |= set(ready)
    return {"tasks": tasks, "serial_last": sorted(held), "merge_order": order}


def overlaps(tasks: list[dict]) -> list[tuple]:
    seen, out = {}, []
    for t in tasks:
        for f in t["files"]:
            if f in seen:
                out.append((seen[f], t["id"], f))
            seen[f] = t["id"]
    return out


def diagnose(runs: list[dict]) -> list[str]:
    """Patterns visible only across the fleet."""
    findings = []
    n = len(runs)
    conflict_files = Counter(f for r in runs for f in r["conflicts"])
    for f, k in conflict_files.items():
        if k >= 3:
            findings.append(f"{k} agents conflicted on {f}: give it one owner or move it to the serial step")
    failing = Counter(r["failed_suite"] for r in runs if r["failed_suite"])
    for suite, k in failing.items():
        if k / n >= 0.2:
            findings.append(f"{suite} failed in {k}/{n} worktrees: likely environment (missing .env or setup), not the code")
    out_of_scope = [r["id"] for r in runs if r["edited_outside_scope"]]
    if out_of_scope:
        findings.append(f"edits outside assigned files: {', '.join(out_of_scope)}: tighten the brief or the hook")
    med = sorted(r["minutes"] for r in runs)[n // 2]
    slow = [r["id"] for r in runs if r["minutes"] > 3 * med]
    if slow:
        findings.append(f"long tail ({', '.join(slow)}): split those tasks further")
    return findings
  • One owner per file: each task gets an exact file list, and no two lists overlap (overlaps() checks). Two agents editing the same file is the agent-teams documentation’s first warning too.
  • Hold back shared files: the lockfile, the base TypeScript config and the shared HTTP wrapper go to one serial step at the end, after the packages that use them.
  • Right-size tasks: split packages over 40 files, so no single agent becomes the long tail; small tasks, though, cost more in coordination than they save.
  • Brief precisely: the package, the files, the migration guide and the test command; tell the agent to stop and report if it needs a file outside its list.
  • Bound the fleet: concurrency and budget caps (20 subagents at once by default), and for runs coordinating hundreds of agents, a scripted workflow rather than turn-by-turn delegation.

Merge in dependency order, one branch per task, shared files last

Skill 8.1How changes come back together.

  • Merge in dependency order: plan() orders packages so dependencies land first; a package that uses common is rebased on the migrated common before it merges.
  • One branch per task, each with its own pull request and green tests, rather than one giant branch that can only succeed or fail as a whole.
  • Rebase, don’t hand-merge: when a task conflicts, rebase it on the latest main and rerun its tests; a recurring conflict on the same file is a planning error, not a merge problem.
  • Serial step last: regenerate the lockfile and update shared files once, after the packages, then run the full test suite.
  • Batch tooling: Claude Code’s /batch runs subagents that each publish their change; the same principles apply to how its tasks are cut.

Read fleet telemetry together to find planning and environment faults

Skill 8.1Patterns no single run reveals.

  • Record per run: task ID, status, minutes, tokens and cost, tests passed, files touched (in and out of scope), conflicts, retries. diagnose() reads them together.
  • Many conflicts on one file: four agents conflicted on the shared HTTP wrapper, so it belongs in the serial step with one owner.
  • The same suite failing everywhere: integration tests failed in a quarter of worktrees, which points at the environment (a missing .env or setup step), not the code changes.
  • Edits outside scope: an agent changed a file it wasn’t given; tighten the brief, or add a hook that denies edits outside the task’s list.
  • Long tail: one run took five times the median; split that task, or check whether it was stuck in a retry loop.
  • Cost per merged change: the fleet’s spend divided by tasks that actually merged, which falls as decomposition improves.

"Add more agents to finish faster" without changing the plan multiplies the conflicts on shared files and the environment failures. Fix the decomposition and the worktree setup first; then parallelism speeds things up.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Four parallel agents keep conflicting on the same shared wrapper file. What should change?
  1. A. Add more agents
  2. B. Take the shared file out of the parallel tasks and give it to one serial step
  3. C. Hand-merge each conflict
  4. D. Use one big branch
Answer
B
Why
Recurring conflicts on one file are a planning error; one owner per file fixes it.
Question 2
Scenario
Integration tests fail in a quarter of the worktrees, on unrelated changes. What is the likely cause?
  1. A. The code changes
  2. B. The worktree environment, such as a missing .env or setup step
  3. C. The model
  4. D. Merge order
Answer
B
Why
The same suite failing everywhere points at setup; list gitignored files in .worktreeinclude.
Question 3
Scenario
How should the migrated packages be merged?
  1. A. All at once
  2. B. In dependency order, one branch and pull request per task, then the shared files and lockfile
  3. C. Alphabetically
  4. D. Shared files first
Answer
B
Why
Dependencies land first, and each task can pass or fail on its own.
Question 4
Scenario
One agent edited a file outside its task list. What is the fix?
  1. A. Ignore it
  2. B. Tighten the brief and add a hook that denies edits outside the task’s files
  3. C. Give every agent every file
  4. D. Remove worktrees
Answer
B
Why
Scope drift is caught by briefs and enforced by hooks.

Key takeaways

  • Isolate each agent in a git worktree (--worktree or isolation: worktree), set up its environment with .worktreeinclude and installs, and clean up headless runs.
  • Give each task a disjoint file list, hold shared files for a final serial step, and right-size tasks to avoid a long tail.
  • Merge in dependency order, one branch and pull request per task, rebasing conflicted tasks and rerunning tests.
  • Diagnose the fleet: repeated conflicts mean a planning error, suite failures everywhere mean environment, out-of-scope edits mean a loose brief.
  • Bound concurrency and spend, and track cost per merged change.
