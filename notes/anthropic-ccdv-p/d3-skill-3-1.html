3.1: Telemetry and Instrumentation

What to record about every model call, tool call and agent turn so that failures can be debugged, cost can be attributed and quality can be traced, without copying sensitive conversations into a monitoring tool that wasn’t meant to hold them.

Overview

Skill 3.1

Telemetry and Instrumentation: "Applying instrumentation practice to production Claude systems under debuggability and privacy requirements, including distributed traces for agent loops and tool calls, token and cost metrics, cache-performance diagnostics, grounding and reasoning traceability, structured log events, and content-capture configuration under privacy constraints such as zero-data-retention."

Exam items describe a system and a privacy rule, then ask which telemetry setup lets the team debug a failure, or why a cost figure or cache rate is wrong. Choosing monitors for a failure that went unseen is CCAR-P 3.4; turning these signals into SLOs and alerts is skill 3.2.

Sources: the Claude API OpenTelemetry pages and span reference (beta; read on 21 November 2026), and the Agent SDK observability page used for CCAR-P, paraphrased. Span names can change during the beta. The insurer, files and code are my own; the code is tested on synthetic spans.

Running example. A health insurer’s member-services assistant answers benefit questions and drafts letters. It runs on Sonnet 5.5 with the Agent SDK for a claims-lookup agent; the organisation has a HIPAA arrangement with Anthropic.

Where traces come from

Skill 3.1Three emitters, one trace.

  • Anthropic SDK tracing (set up in code): a client span per request, the tool runner, client tools you run, tools in a self-hosted sandbox, and other API calls such as file uploads.
  • Claude API tracing (an Admin adds a destination in the Console): server spans for each request, each model run inside it, server tools and MCP connector tools the API runs, and Managed Agents turns. It covers any client, on the Claude API and Claude Platform on AWS.
  • Agent SDK and Claude Code: the CLI exports its own OpenTelemetry metrics, log events and (beta) traces once CLAUDE_CODE_ENABLE_TELEMETRY=1 is set.
  • Join them: the API and SDK use the GenAI semantic conventions, propagate W3C trace context (traceparent), and send OTLP to any platform that accepts it. Wrap each call in your own span carrying route, tenant and user, so model spans sit inside the business request.

Traces for agent loops and tool calls

Skill 3.1One trace per user request, however many turns it takes.

  • Messages API with the tool runner: an anthropic.messages.tool_runner span contains one anthropic.messages.create per request (client and server), model-request spans, server tool spans and anthropic.custom_tool_use spans for your tools.
  • Agent SDK: claude_code.interaction, claude_code.llm_request (model, latency, tokens), claude_code.tool (with time blocked on a user) and claude_code.hook. Subagent spans nest under the parent’s tool span.
  • Managed Agents: turn spans per agent turn; group by gen_ai.conversation.id for one thread or anthropic.session.id for a whole session.
  • Useful attributes: requested and served model, anthropic.request.id, stop reason, error.type, tool name and arguments. Stop reason matters, because refusals and truncations are 200s (skill 2.1).
  • Export errors are silent in the Agent SDK by default; set CLAUDE_CODE_OTEL_DIAG_STDERR=1 and alert when spans stop arriving.

Token, cost and cache metrics

Skill 3.1Count each token once.

span_metrics.py (span_metrics.py) 
"""Token, cost and cache metrics from exported Claude API spans (beta; names from the span reference).
Count each token once: prefer SERVER spans, drop duplicate deliveries, add compaction separately."""
from collections import defaultdict

PRICE = {"claude-sonnet-5-5": {"in": 2.00, "write": 2.50, "read": 0.10, "out": 10.00}}   # $/MTok, 5-minute writes


def counted(spans: list[dict]) -> list[dict]:
    seen, keep = set(), []
    for s in spans:
        key = (s["trace_id"], s["span_id"])
        if key in seen:
            continue                                    # a retried delivery
        seen.add(key)
        if s["name"] == "anthropic.messages.create" and s["kind"] == "SERVER":
            keep.append(s)
    return keep


def metrics(spans: list[dict], route_of: dict) -> dict:
    """route_of: trace ID -> route, taken from your own application span that wraps the call."""
    by_route = defaultdict(lambda: {"usd": 0.0, "input": 0, "cache_read": 0, "truncated": 0, "requests": 0})
    for s in counted(spans):
        a, p = s["attributes"], PRICE[s["attributes"]["gen_ai.response.model"]]
        read, write = a.get("gen_ai.usage.cache_read.input_tokens", 0), a.get("gen_ai.usage.cache_write.input_tokens", 0)
        total_in = a["gen_ai.usage.input_tokens"]        # already includes cache reads and writes
        plain = total_in - read - write
        out = a["gen_ai.usage.output_tokens"] + a.get("anthropic.usage.compaction.output_tokens", 0)
        plain += a.get("anthropic.usage.compaction.input_tokens", 0)
        r = by_route[route_of.get(s["trace_id"], "unknown")]
        r["usd"] += (plain * p["in"] + write * p["write"] + read * p["read"] + out * p["out"]) / 1e6
        r["input"] += total_in
        r["cache_read"] += read
        r["truncated"] += bool(a.get("anthropic.content.truncated"))
        r["requests"] += 1
    return {k: {"usd": round(v["usd"], 4), "cache_read_share": round(v["cache_read"] / v["input"], 2),
                "requests": v["requests"], "flag": "cache below 80%" if v["cache_read"] / v["input"] < 0.8 else ""}
            for k, v in by_route.items()}
  • One source per request: when both exist, sum the API’s SERVER span, not the SDK’s CLIENT span. Sum either request spans or model-request spans, never both.
  • Duplicates happen: a retried delivery repeats a span, so deduplicate by trace ID and span ID.
  • Cache tokens are inside the input count: gen_ai.usage.input_tokens already includes cache reads and writes, so subtract them to price the uncached part, rather than adding them on. Compaction tokens are separate (anthropic.usage.compaction.*).
  • Cache diagnostics: cache read share per route, flagged below about 80% (Anthropic’s agent-loop median is 84%). Here the letters route reads only 20% from cache, so something is breaking its prefix.
  • Spans aren’t the ledger: delivery is best effort, and a caller can switch sampling off. For complete usage by key, use the Usage and Cost Analytics API, which typically updates within about four hours.

Grounding, reasoning and security events

Skill 3.1Trace why an answer said what it said.

  • Grounding: record retrieved document IDs and versions, and the citations in the answer, on your application span. Then a wrong answer can be traced to its source passage or its absence (skill 2.4).
  • Reasoning: spans carry reasoning-token counts (gen_ai.usage.reasoning.output_tokens) and the effort requested. Record the effort, model and prompt version on each request so a behaviour change can be tied to a configuration change.
  • Structured log events: the Agent SDK emits claude_code.tool_decision, tool_result, mcp_server_connection and permission_mode_changed events, which suit a SIEM. Add end-user and tenant IDs as attributes (enduser.id, tenant.id).
  • Log IDs, not text: request IDs, document IDs and citation locations let you rebuild what happened from the system of record without copying the content.

Content capture under privacy rules

Skill 3.1Who may hold the prompts and responses.

telemetry_config.py (telemetry_config.py) 
"""Content-capture settings per environment, decided by data rules rather than convenience."""


def content_mode(env: str, org: dict) -> dict:
    if org["hipaa_or_ferpa"]:
        # API destinations export metadata only for these organisations, whatever you set; match it in the SDK.
        return {"api_destination": "metadata_only", "sdk": "metadata_only"}
    if env == "production":
        # ZDR still allows full content (held in memory until delivered), but your platform then stores
        # members' text under its own retention. Keep production structural by default.
        return {"api_destination": "metadata_only", "sdk": "metadata_only"}
    return {"api_destination": "content", "sdk": "content", "max_content_mb": 0.75}   # staging and eval capture


AGENT_SDK_ENV = {                                   # Agent SDK / Claude Code CLI export (structural by default)
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "CLAUDE_CODE_ENHANCED_TELEMETRY_BETA": "1",     # traces (beta): interaction, llm_request, tool, hook spans
    "OTEL_TRACES_EXPORTER": "otlp", "OTEL_METRICS_EXPORTER": "otlp", "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_SERVICE_NAME": "member-assistant",
    "CLAUDE_CODE_OTEL_DIAG_STDERR": "1",            # export errors are silent by default
    # Not set in production: OTEL_LOG_USER_PROMPTS, OTEL_LOG_TOOL_DETAILS, OTEL_LOG_TOOL_CONTENT, OTEL_LOG_RAW_API_BODIES
}
  • Two content modes: metadata only (the default: IDs, timing, status, token counts, tool and agent names) or full content (prompts and responses in gen_ai.input.messages, gen_ai.output.messages and gen_ai.system_instructions).
  • ZDR doesn’t forbid full content: for Messages API requests the API holds exported content only in memory until delivery. But your observability platform then stores it under its own retention, so ZDR at Anthropic doesn’t mean nothing is kept anywhere. Managed Agents isn’t ZDR eligible.
  • HIPAA, FERPA and K-12 arrangements: API destinations export metadata only, whatever mode is set. SDK spans aren’t affected, so set the SDK to metadata only yourself, as the config does.
  • Size limits: full content is capped at 0.75 MB per span by default; longer content is shortened (system prompt and earliest messages first) and marked anthropic.content.truncated.
  • Agent SDK opt-ins (OTEL_LOG_USER_PROMPTS, OTEL_LOG_TOOL_DETAILS, OTEL_LOG_TOOL_CONTENT, OTEL_LOG_RAW_API_BODIES) stay off in production.

"We have ZDR, so full-content tracing is safe" confuses where data is kept. ZDR covers Anthropic; the traces land in your observability platform with its own access and retention. Decide content capture by where the text ends up, and for HIPAA organisations remember the SDK side isn’t forced to metadata.

Key takeaways

  • Combine SDK spans (client side, your tools), API spans (server side, model runs, server tools, Managed Agents) and Agent SDK telemetry, joined by trace context under your own business span.
  • Count tokens once: server spans over client spans, no double levels, deduplicate by trace and span ID, cache tokens already inside input, compaction separate.
  • Watch cache read share by route; reconcile spend with the Usage and Cost Analytics API, since spans are best effort.
  • Record model, prompt version, effort, retrieved document IDs and citations so answers can be traced; send security events to a SIEM.
  • Default to metadata only in production; ZDR doesn’t cover your platform’s storage, and HIPAA forces metadata on API destinations but not on SDK spans.
