8.4: Organization-Wide Coding Agent Configuration

When thousands of developers run coding agents, defaults become policy. This page sets the organisation-level controls: managed settings developers can’t override, which MCP servers may run, telemetry that every team reports, a gateway for every model call, and the bar a team’s prompt, Skill or server must clear before others depend on it.

Overview

Skill 8.4

Organization-Wide Coding Agent Configuration: "Applying enterprise configuration for organizations adopting coding agents, including managed settings and policies, MCP allowlists, telemetry, gateway routing, and governance with a quality and safety bar for sharing prompts, Skills, and MCP servers across teams."

Exam items describe an organisation’s Claude Code rollout and a gap (an unapproved MCP server in use, spend nobody can attribute, a shared Skill that broke ten teams) and ask which configuration closes it. Packaging and distributing one workflow is CCAR-P 7.1; MCP server security is skill 7.2.

Put organisation policy in managed settings, which users can't override

Skill 8.4The top of the settings stack.

Take an engineering organisation of about 1,500 developers rolling Claude Code out to every team. Security wants control of what agents connect to, finance wants cost by department, and the platform team wants teams to share good Skills without spreading bad ones.

managed-settings.json (managed-settings.json) 
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://llm-gateway.example.com",
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "https://otel.example.com:4317",
    "OTEL_RESOURCE_ATTRIBUTES": "department=engineering,cost_center=eng-100"
  },
  "allowedProviders": ["customEndpoint"],
  "allowManagedMcpServersOnly": true,
  "allowedMcpServers": [
    { "serverUrl": "https://mcp.example.com/*" },
    { "serverUrl": "https://mcp.sentry.dev/*" }
  ],
  "deniedMcpServers": [
    { "serverUrl": "https://*.untrusted.example.net/*" }
  ],
  "managedMcpServers": {
    "code-search": { "type": "http", "url": "https://mcp.example.com/code-search" }
  },
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "example/approved-plugins" },
    { "source": "skills-dir" }
  ],
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)", "Bash(git push --force *)"],
    "disableBypassPermissionsMode": "disable"
  }
}
  • Delivery: server-managed settings from the claude.ai admin console, MDM or registry policies, or a managed-settings.json file. Managed values sit above command-line, local, project and user settings, and users can’t override them; list settings such as deny rules merge across scopes.
  • Typical organisation policy: deny rules for secrets and force-pushes, disableBypassPermissionsMode (and, if wanted, disableAutoMode), a plugin marketplace allowlist, MCP controls, telemetry and the gateway.
  • Some keys only work from managed sources, such as allowManagedMcpServersOnly; repository settings can’t set telemetry exporters or permission defaults like bypassPermissions.
  • Verify on a machine: /status shows which managed source applies, and claude mcp list shows which servers survived the policy.

Allowlist MCP servers by URL or command from a managed source

Skill 8.4From "anything goes" to a fixed set.

  • Why it’s needed: by default anyone can connect any MCP server, and the documentation says Anthropic doesn’t security-audit or manage any MCP server.
  • Patterns, loosest to tightest: a denylist only; a soft allowlist users can widen; an approved catalogue (allowedMcpServers plus allowManagedMcpServersOnly: true); servers provided to everyone (managedMcpServers, HTTPS remote servers only); plugin servers only; a fixed deployment with managed-mcp.json (exclusive control, delivered by device management, not server-managed settings); or MCP disabled with an empty map.
  • Match by URL or command, not name: serverUrl supports wildcards; serverCommand matches the exact command and arguments. A serverName entry "is not a security control", since users choose the label.
  • The denylist always wins and merges from every scope, so users can block a server for themselves. An empty allowlist ([]) allows nothing; an unset one allows everything.
  • No shared secrets in files: any user can read managed-mcp.json; use per-user OAuth, ${VAR} expansion or a headers helper.
  • Tell people: a blocked server just disappears from /mcp, so announce restrictions, and measure actual usage with tool details in telemetry.

Enable telemetry centrally and tag it with team and cost centre

Skill 8.4Set once, centrally, with team attributes.

  • Enable in managed settings: CLAUDE_CODE_ENABLE_TELEMETRY, the metrics and logs exporters and the OTLP endpoint in the managed env block. Set the exporter selectors there too, or a developer can switch a signal off; repository settings can’t set them at all.
  • Metrics: sessions, lines of code changed, pull requests, commits, cost, tokens, edit-tool permission decisions and active time.
  • Events: prompts submitted, tool results, API requests (with cost, duration and tokens), API errors and tool decisions, linked per prompt by prompt.id.
  • Attribution: OTEL_RESOURCE_ATTRIBUTES adds department, team and cost centre to every metric and event, for per-team dashboards, costs and alerts.
  • Content stays out by default: prompt text, responses, tool details and raw bodies are redacted unless explicitly enabled; enable tool names only if you need MCP usage reports.

Route every model call through one pinned gateway

Skill 8.4One path for every model call.

  • What it gives: provider credentials kept server-side, usage attributed by developer or team, budgets and rate limits in one place, audit logs, and switching provider without touching laptops (skill 2.3).
  • Pin it: put ANTHROPIC_BASE_URL in the managed env and set allowedProviders to ["customEndpoint"], so sessions pointed anywhere else, including Anthropic directly, are refused.
  • Give each developer a gateway credential, so offboarding revokes one credential and usage is attributed per person.
  • Keep it current: a gateway that doesn’t forward what new Claude Code releases send breaks those features. Anthropic also offers its own self-hosted Claude apps gateway with SSO and telemetry.

Share prompts, Skills and servers only after an owner, a version, an eval and a review

Skill 8.4Before ten teams depend on it.

sharing_bar.py (sharing_bar.py) 
"""The bar a prompt, Skill or MCP server must clear before it moves from one team to the
organisation catalogue."""
import re

SECRET = re.compile(r"(sk-ant-[a-z0-9-]{8,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----)")


def review(asset: dict) -> list[str]:
    gaps = []
    for field in ("owner", "version", "changelog"):
        if not asset.get(field):
            gaps.append(f"missing {field}")
    ev = asset.get("eval")
    if not ev or ev["cases"] < 20 or ev["pass_rate"] < 0.9:
        gaps.append("needs an evaluation: at least 20 cases at 90% or better, re-run on each version")
    if SECRET.search(asset.get("content", "")):
        gaps.append("contains something that looks like a credential")
    if asset["kind"] == "mcp_server":
        sec = asset.get("security", {})
        for item in ("audience_checked", "no_token_passthrough", "minimal_scopes", "description_hash_pinned"):
            if not sec.get(item):
                gaps.append(f"MCP security review: {item.replace('_', ' ')}")
    if asset["kind"] == "skill" and asset.get("runs_scripts") and not asset.get("scripts_reviewed"):
        gaps.append("Skill runs scripts that nobody has reviewed")
    if asset.get("data_class") == "confidential" and not asset.get("data_owner_approved"):
        gaps.append("touches confidential data without the data owner's approval")
    return gaps
  • Ownership and versioning: a named owning team, a version and a changelog, so a change that breaks others can be traced and rolled back.
  • Quality: an evaluation of at least 20 cases passing at 90% or more, re-run on every version. A shared prompt or Skill is a dependency, and needs the same release discipline as code (skill 5.1).
  • Safety: no embedded credentials; scripts in Skills reviewed; MCP servers that check token audience, don’t pass tokens on, use minimal scopes and have pinned tool descriptions; data-owner approval for anything touching confidential data.
  • Two tiers: team-local assets can move fast; the organisation catalogue (a plugin marketplace on the allowlist) only takes assets that clear the bar.
  • Retire as well as add: telemetry shows which shared assets are used; unused ones are removed so the catalogue stays trusted.

"Block MCP servers by name" blocks nothing a user can rename, and "publish every team’s Skills to everyone" spreads the untested ones. Allowlist by URL or command from a managed source with the lock on, and put shared assets behind an owner, a version, an evaluation and a security review.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Security blocks an MCP server by its name in a denylist, but developers still use it. Why?
  1. A. The denylist is broken
  2. B. Names are labels users choose; match by URL or command instead
  3. C. Denylists only apply to plugins
  4. D. The server is on an allowlist
Answer
B
Why
serverName entries aren’t a security control.
Question 2
Scenario
Finance can’t attribute Claude Code spend to departments. What should be configured?
  1. A. A spreadsheet
  2. B. Telemetry enabled in managed settings with OTEL_RESOURCE_ATTRIBUTES for department and cost centre, or per-developer gateway credentials
  3. C. One shared key per department
  4. D. Higher rate limits
Answer
B
Why
Central telemetry with team attributes, or a gateway, attributes usage.
Question 3
Scenario
Developers point Claude Code directly at Anthropic, bypassing the company gateway. What stops this?
  1. A. A wiki page
  2. B. ANTHROPIC_BASE_URL in managed env plus allowedProviders set to customEndpoint
  3. C. Removing internet access
  4. D. A prompt instruction
Answer
B
Why
Pinning the provider in managed settings refuses sessions pointed elsewhere.
Question 4
Scenario
A shared Skill breaks ten teams after an update. What bar should shared assets meet?
  1. A. None; share freely
  2. B. An owner, a version and changelog, an evaluation rerun on every version, and a security review
  3. C. Only a README
  4. D. Approval by any developer
Answer
B
Why
Shared assets are dependencies and need release discipline.

Key takeaways

  • Managed settings sit at the top of the stack and can’t be overridden; use them for deny rules, disabled modes, marketplaces, MCP, telemetry and the gateway.
  • Control MCP by URL or command with allowManagedMcpServersOnly, provide approved servers centrally, use managed-mcp.json for exclusive control, and remember the denylist always wins.
  • Turn on telemetry from managed settings with team and cost-centre attributes; content stays redacted unless you enable it.
  • Route every call through a gateway pinned with allowedProviders, with per-developer credentials, and keep it current.
  • Share prompts, Skills and servers only past a bar: owner, version, changelog, evaluation, security review and data approval.
