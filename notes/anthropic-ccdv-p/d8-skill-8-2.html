8.2: Verification and AI Code Review Operations

When agents open pull requests faster than people can read them, review becomes the bottleneck and the risk. This page brings AI code review in without letting it decide on its own: run it in shadow, measure it against what people and production found, gate only on what it gets right, and spend human attention where the risk is.

Overview

Skill 8.2

Verification and AI Code Review Operations: "Analyzing verification operations in delivery pipelines where generation outpaces review, including AI code review introduced in shadow mode, calibration against human review before merge gating, and human oversight design."

Exam items describe a team drowning in agent-written pull requests and a proposal for AI review, and ask how to introduce it or whether it may gate merges yet. Who stays accountable for AI-written code is CCAR-P 7.3; calibrating model graders in general is skill 5.2.

Sources: the Claude Code Code Review pages (overview, pull-request findings, customisation), read on 20 November 2026 and paraphrased. The calibration definitions, gate thresholds and review tiers are my own; the company, files and code are original, and the code is tested.

Running example. An online marketplace’s engineering teams run coding agents that open about 300 pull requests a week, triple last quarter’s volume, with the same 40 reviewers. The platform team wants to switch on Claude Code Review and use it to block risky merges.

When generation outpaces review

Skill 8.2The symptoms (my list).

  • Review queues grow and approvals get faster and shallower: large diffs approved in minutes.
  • Escaped defects rise in areas nobody looked at closely, often in code that passed CI.
  • Verification is uneven: tests exist for what agents were asked to change, not for what they changed incidentally.
  • The fix isn’t "review less carefully": it’s more automated verification (tests, static checks, AI review), and targeted human attention.

AI review in shadow mode

Skill 8.2Run it, read it, block nothing yet.

  • What Code Review does: several agents read the change with the surrounding code, a verification step drops false positives, and findings arrive as inline comments ranked Important (fix before merging), Nit or Pre-existing, with a summary and a check run.
  • Shadow by design: a review "never approves or blocks the pull request", and its check run concludes neutral, never failed. Running it on every PR for a few weeks costs reviewer attention but no merges.
  • Choose when and how deep: per repository, review once when a PR opens, after every push, or only on request; level Quick, Standard (default) or Deep, with deeper reviews costing more.
  • Know its blind spots: it reads the diff and surrounding code without building or running it, so tests and CI remain the check that code works; and "a review with no findings doesn’t mean your code is error-free or secure".
  • Record outcomes: for each Important finding, whether it was fixed, confirmed by a reviewer, or dismissed (resolving the thread dismisses it; a reply alone doesn’t).

Calibrating against human review

Skill 8.2Precision and recall on your own PRs (my definitions).

calibrate.py (calibrate.py) 
"""Shadow-mode calibration of AI code review against human review before it gates merges.
Records come from four weeks of pull requests where Code Review ran but blocked nothing (my method)."""


def precision_recall(prs: list[dict]) -> dict:
    """Precision: Important findings that were real (fixed, or confirmed by a reviewer).
    Recall: real defects (found by humans, or escaped to production) that the AI also flagged."""
    flagged = [f for p in prs for f in p["ai_important"]]
    real = [f for f in flagged if f["outcome"] in ("fixed", "confirmed")]
    defects = [d for p in prs for d in p["human_defects"] + p["escaped_defects"]]
    caught = [d for d in defects if d["ai_flagged"]]
    return {"precision": round(len(real) / len(flagged), 2) if flagged else None,
            "recall": round(len(caught) / len(defects), 2) if defects else None,
            "important_per_pr": round(len(flagged) / len(prs), 2)}


def gate_policy(m: dict, min_precision=0.8, max_per_pr=1.0) -> str:
    if m["precision"] is None or m["precision"] < min_precision:
        return "advisory only: too many false Important findings to block merges on"
    if m["important_per_pr"] > max_per_pr:
        return "advisory only: volume would bury reviewers; tune REVIEW.md first"
    return "gate: fail CI when Important findings are open; a person may dismiss one with a reason"


def review_tier(pr: dict) -> str:
    """Human oversight scaled by risk, because generation now outpaces review."""
    risky_paths = ("payments/", "auth/", "migrations/", "infra/")
    if any(f.startswith(risky_paths) for f in pr["files"]) or pr["lines_changed"] > 400:
        return "two human reviewers, one a code owner; AI findings attached"
    if pr["ai_generated"]:
        return "one human code owner reviews; AI review must be clear or dismissed with reasons"
    return "one human reviewer; AI review advisory"
  • Precision: of Important findings, how many were real (fixed or confirmed). A gate with low precision blocks good changes and teaches people to dismiss findings without reading.
  • Recall: of real defects (found by human reviewers, or escaped to production and traced back), how many the AI also flagged. Escaped defects keep recall honest, since humans miss things too.
  • Volume: Important findings per PR. Even accurate findings stop being read when every PR has three.
  • Tune before gating: REVIEW.md (read only from the base branch) recalibrates severity, skips generated files, caps nits and adds repository-specific checks. Re-measure after each change.
  • Per repository: the payments service and the marketing site deserve different levels and thresholds.

Gating merges

Skill 8.2Only on what calibration supports.

  • The decision rule here: gate only when Important precision is at least 0.8 and volume is at most one per PR; otherwise stay advisory. In the example, precision is 0.75, so the review stays advisory and REVIEW.md gets tuned.
  • How to gate: the check run itself never fails, so a CI job reads the severity counts from its Details text and fails when Important findings are open. A missing severity line means no verdict, not zero findings; a "not repeated" title means earlier Important findings are still open.
  • Branch protection can also require conversation resolution, so each finding is fixed or explicitly dismissed.
  • People keep the decision: a person can dismiss a finding with a reason; the gate stops silent merges past known issues, not human judgement.

Human oversight design

Skill 8.2Spend reviewer time by risk (my tiers).

  • High risk (payments, auth, migrations, infrastructure, or over 400 lines): two human reviewers, one a code owner, with AI findings attached.
  • Agent-written, ordinary risk: one human code owner; AI review must be clear or its findings dismissed with reasons.
  • Low risk: one reviewer, AI review advisory.
  • Keep the person accountable: AI review is advisory and agents don’t merge; each change has a named owner and an independent human approval (CCAR-P 7.3).
  • Keep measuring: recalibrate monthly on new PRs and escaped defects, and move repositories between tiers as the numbers change.

"Turn on AI review and make it a required check from day one" gates merges on a reviewer nobody has measured, and the check run doesn’t fail anyway, so a naive required check passes everything. Shadow it, calibrate precision and recall against human review and escaped defects, then gate from CI on Important findings where the numbers support it.

Key takeaways

  • When generation outpaces review, add automated verification and target human attention by risk; don’t just approve faster.
  • Introduce AI review in shadow: it never approves or blocks, its check run is neutral, and it doesn’t run the code, so tests still matter.
  • Calibrate per repository: precision of Important findings, recall against human-found and escaped defects, and findings per PR; tune REVIEW.md.
  • Gate from CI on open Important findings only where calibration supports it; treat a missing severity line as no verdict.
  • Tier human review by risk, keep a named human owner and independent approval, and recalibrate regularly.
