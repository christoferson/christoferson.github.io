5.1: Evaluation System Design

An offline evaluation system decides whether a prompt, model or agent change ships. This page builds one: the kinds of suites it holds, the metrics for retrieval and grounding, the gate CI runs, and the upkeep that stops the suite from quietly measuring the wrong thing.

Overview

Skill 5.1

Evaluation System Design: "Evaluating and designing offline evaluation systems for Claude applications, including golden sets, regression suites, behavioral checks, CI/CD evaluation gates, retrieval precision and groundedness metrics, and release criteria for prompt, model, and agent changes, and maintaining suite validity over time against contamination, saturation, and coverage gaps."

Exam items describe an evaluation setup that let a bad change through, or that stopped telling the team anything, and ask what to change. Building a single evaluation is CCDV-F 4.1; finding the missing dimension after an incident is CCAR-P 4.1; calibrating model graders is skill 5.2.

Keep golden, regression, capability and behavioural suites, each answering its own question

Skill 5.1Different suites answer different questions.

Take a support assistant that answers warranty, parts and recall questions from technical bulletins. Prompts change weekly, the model a few times a year, and a wrong warranty answer costs real money.

  • Golden set: labelled questions with reference answers and the passages that support them, stratified to match production traffic by segment (warranty, parts, recalls), with edge cases on top.
  • Regression suite: "does it still handle what it used to?" It should pass nearly 100%. Every incident adds its captured requests here (skill 4.2).
  • Capability suite: "what can it do well?" It starts with a low pass rate and measures improvement. Tasks that pass consistently graduate to the regression suite.
  • Behavioural checks: must-pass rules: decline out-of-scope requests, say "not found" when the bulletins don’t cover it, never promise a price or a goodwill payment.
  • Where to start: Anthropic suggests 20 to 50 simple tasks drawn from real failures, with a reference solution for each, and warns evals get harder to build the longer you wait.

Grade outcomes over isolated trials, and use pass^k where consistency matters

Skill 5.1Vocabulary from Anthropic’s agent-evals guidance.

  • Task, trial, transcript, outcome: a task is one test; each attempt is a trial; the transcript records everything; the outcome is the final state (a warranty claim actually created, not the agent saying it was).
  • pass@k versus pass^k: pass@k is the chance at least one of k trials succeeds; pass^k that all k do. A 75% task has pass^3 of about 42%. Use pass^k where consistency matters, as for a user who asks once and acts.
  • Graders: code graders are fast, cheap and reproducible but brittle; model graders capture nuance but need calibration against human labels; human grading is the gold standard but slow. "Deterministic graders where possible, LLM graders where necessary."
  • Grade outcomes, not exact paths, with partial credit for multi-part tasks. Insisting on one tool sequence fails valid solutions.
  • Isolate trials: each starts from a clean environment. Anthropic describes Claude gaining an unfair advantage by reading the git history of earlier trials.
  • Read transcripts: failures should look fair. A task at 0% across many trials is usually a broken task, not an incapable agent.

Measure retrieval, groundedness and correctness separately

Skill 5.1Measure retrieval and answers separately.

  • Retrieval precision at k: of the top k passages, how many are relevant. Recall at k: whether the passage holding the answer is among them. Labelled questions record the gold passages, so both are code-graded.
  • Groundedness: the share of claims in the answer supported by a retrieved passage. Citations make this checkable claim by claim (skill 2.4).
  • Correctness: whether the answer matches the reference. A grounded answer can still be wrong if it cited an outdated bulletin, so keep both.
  • Not-found accuracy: questions the library can’t answer, where the right output is "not found".

Write release criteria as code, with a floor for every segment

Skill 5.1Release criteria written as code.

gate.py (gate.py) 
"""CI evaluation gate for a support assistant (warranty rules and parts lookup).
Runs on every prompt, model or agent change; the thresholds are the team's release criteria."""

CRITERIA = {
    "regression_pass_hat_3": 0.98,   # pass^3: all three trials pass; consistency matters when users act on one answer
    "capability_drop": 0.02,         # capability suite may not drop more than 2 points
    "segment_floor": 0.85,           # every segment, not just the average
    "retrieval_precision_at_5": 0.80,
    "groundedness": 0.97,            # share of answer claims supported by a retrieved passage
    "behavioural": 1.00,             # must-pass checks: out-of-scope refusal, "not found", no price promises
}


def pass_at_k(trials: list[bool]) -> bool:
    return any(trials)


def pass_hat_k(trials: list[bool]) -> bool:
    return all(trials)


def gate(results: dict, baseline: dict) -> list[str]:
    fails = []
    reg = [pass_hat_k(t) for t in results["regression"].values()]
    if sum(reg) / len(reg) < CRITERIA["regression_pass_hat_3"]:
        fails.append(f"regression pass^3 {sum(reg) / len(reg):.2f}")
    cap = sum(pass_at_k(t[:1]) for t in results["capability"].values()) / len(results["capability"])
    if baseline["capability"] - cap > CRITERIA["capability_drop"]:
        fails.append(f"capability {cap:.2f} vs {baseline['capability']:.2f}")
    for seg, score in results["segments"].items():
        if score < CRITERIA["segment_floor"]:
            fails.append(f"segment {seg} at {score:.2f}")
    for metric in ("retrieval_precision_at_5", "groundedness", "behavioural"):
        if results[metric] < CRITERIA[metric]:
            fails.append(f"{metric} {results[metric]:.2f} < {CRITERIA[metric]:.2f}")
    return fails
  • Runs on every change type: prompt edits, model version changes, agent and tool changes, retrieval re-indexes.
  • Regression by pass^3: three trials each, all must pass, at least 98% of tasks.
  • Capability can’t fall more than two points against the current release, compared on the same tasks.
  • Every segment has a floor: recalls at 80% fails the release even though the average looks fine.
  • Retrieval, groundedness and behavioural checks have their own thresholds; behavioural checks must all pass.
  • Different changes, different extras: a model change also gets shadow traffic before rollout; a prompt change can rely on replays (CCAR-P 4.2).

Check the suite itself for saturation, coverage gaps, contamination and staleness

Skill 5.1A living artefact with an owner.

health.py (health.py) 
"""Keep the suite valid over time: saturation, coverage gaps and contamination."""
import hashlib
import re


def saturated(history: dict[str, list[float]], ceiling=0.95, releases=3) -> list[str]:
    """Capability tasks passing near 100% for several releases give no signal: graduate them."""
    return [t for t, h in history.items() if len(h) >= releases and min(h[-releases:]) >= ceiling]


def coverage_gaps(production_mix: dict[str, float], tasks_per_segment: dict[str, int], total=400) -> list[str]:
    """Segments with fewer tasks than their share of real traffic warrants (at least 20 each)."""
    out = []
    for seg, share in production_mix.items():
        need = max(20, round(share * total))
        if tasks_per_segment.get(seg, 0) < need:
            out.append(f"{seg}: {tasks_per_segment.get(seg, 0)} tasks, need {need}")
    return out


def _shingles(text: str, n=8) -> set:
    words = re.findall(r"\w+", text.lower())
    return {hashlib.sha1(" ".join(words[i:i + n]).encode()).hexdigest() for i in range(len(words) - n + 1)}


def contaminated(tasks: dict[str, str], exposed: list[str], threshold=0.3) -> list[str]:
    """Tasks whose text largely appears in prompt examples, the retrieval corpus or published docs."""
    pool = set().union(*(_shingles(x) for x in exposed)) if exposed else set()
    return [tid for tid, text in tasks.items() if (s := _shingles(text)) and len(s & pool) / len(s) >= threshold]
  • Saturation: "An eval at 100% tracks regressions but provides no signal for improvement." Tasks at or near the ceiling for several releases graduate to regression, and new harder tasks replace them.
  • Coverage gaps: compare tasks per segment with the production mix. Recalls are 10% of traffic but have 12 tasks, so the suite can’t detect a recall regression.
  • Contamination: a test question that also appears in the prompt’s few-shot examples, the retrieval corpus or published material measures recall of the example, not the skill. Flag tasks with high text overlap and replace them; keep a held-out set that never goes into prompts.
  • Staleness: bulletins change; a reference answer from last year’s warranty terms now fails a correct model. Re-label on a schedule and when the source changes.
  • Ownership: Anthropic suggests an evals team owning the infrastructure while domain experts and product teams contribute tasks, with maintenance as routine as unit tests.

"The suite has been at 99% for months, so quality is stable" may mean the suite is saturated, missing a segment, or contaminated by examples copied into the prompt. A suite that never fails a release isn’t evidence of quality; check its health before trusting its verdict.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A task passes 75% of single trials. Users ask once and act on the answer. Which metric reflects the risk?
  1. A. pass@3
  2. B. pass^3, the chance all three trials pass (about 42%)
  3. C. Average score
  4. D. Best of three
Answer
B
Why
pass^k measures consistency; pass@k only says one attempt usually works.
Question 2
Scenario
A release raises the average score, but one segment that is 10% of traffic drops to 80%. What should the gate do?
  1. A. Ship, since the average rose
  2. B. Fail the release because a segment floor is broken
  3. C. Ignore small segments
  4. D. Re-run until it passes
Answer
B
Why
Every segment needs its own floor; averages hide regressions.
Question 3
Scenario
The suite has scored 99% for months. What should the team check before trusting it?
  1. A. Nothing
  2. B. Saturation, coverage per segment, and contamination from prompt examples or the corpus
  3. C. Only latency
  4. D. Whether the model changed
Answer
B
Why
A suite that never fails may have stopped measuring anything.
Question 4
Scenario
An agent eval grades whether the agent followed one exact tool sequence. What is the problem?
  1. A. None
  2. B. It fails valid solutions; grade the outcome, with partial credit where helpful
  3. C. It is too lenient
  4. D. It needs more trials
Answer
B
Why
Outcome grading accepts every valid path; path grading is brittle.

Key takeaways

  • Keep separate golden, regression (near 100%), capability (starts low) and behavioural (must-pass) suites; start with 20 to 50 tasks from real failures.
  • Run several trials, choose pass@k or pass^k by whether consistency matters, grade outcomes, isolate trials, and read transcripts.
  • Measure retrieval precision and recall, groundedness, correctness and not-found accuracy separately.
  • Gate every prompt, model, agent and index change in CI with per-segment floors, not only an average.
  • Maintain the suite: graduate saturated tasks, fill coverage gaps from the production mix, remove contaminated tasks, refresh stale labels, and give it an owner.
