7.1: Runtime Guardrail Systems

No single control makes a production agent safe. This page stacks layers around one: a screen on what comes in, redaction of what goes out, code that decides which tool calls run, a sandbox around what the agent can reach, people for the irreversible steps, and thresholds tuned on data rather than guessed.

Overview

Skill 7.1

Runtime Guardrail Systems: "Evaluating layered guardrail architectures against a production agent's risk profile, including input/output filtering, PII redactors, hook-based policy enforcement, destructive-action prevention, sandboxing that grants tool and web access without exposing production systems, approval gates, refusal handling and safety fallbacks, deterministic enforcement for irreversible actions, and false-positive/false-negative tuning."

Exam items describe an agent, what it can touch, and a guardrail design, then ask which layer is missing or misplaced, or how to tune one that blocks too much. Deterministic guardrails at Foundations level are CCDV-F 7.2; placing a single control against a misuse path is CCAR-P 5.1; attacks on agents are skill 7.2.

Choose guardrail layers from what the agent can touch

Skill 7.1Start from what the agent can do, not from a list of filters.

Take a public-services agent that answers residents’ questions about local tax, waste collection and housing repairs. It reads a resident’s own case records, can send letters, issue small refunds and search the public web for opening hours and guidance.

  • The risk profile: personal data (case records), external actions (letters, refunds), irreversible changes (deleting or merging records), and untrusted content (web pages, resident messages).
  • Input screening: a lightweight model screen on incoming requests, as Anthropic suggests, with structured output.
  • Redaction: strip personal identifiers before text reaches logs, analytics or third-party tools.
  • Tool policy in code: a PreToolUse hook that denies destructive actions, limits amounts and sends external actions to a person.
  • Containment: least-privilege credentials and a sandbox around anything that executes or browses.
  • Output checks: the reply mentions only the signed-in resident’s own cases.
  • Monitoring: blocks, approvals and refusals as metrics, with repeat offenders throttled. Anthropic’s guidance is to chain safeguards rather than rely on one.

Keep each layer small: screen, redact, enforce actions in a hook, check output

Skill 7.1Each layer is small; together they cover the paths.

guardrails.py (guardrails.py) 
"""Layered runtime guardrails for a public-services agent (Agent SDK).
Each layer catches something the others miss; the irreversible ones are code, not prompt."""
import re

# 1. Input screen: a small model classifies the request first (called via the API; mocked in tests).
def screen(verdict: dict, stop_reason: str) -> str:
    if stop_reason == "refusal":
        return "block"                       # a screening refusal counts as a harmful verdict
    return "block" if verdict["harmful"] and verdict["confidence"] >= THRESHOLD else "allow"

THRESHOLD = 0.7                              # tuned on a labelled set (see tune())

# 2. PII redaction before text leaves the boundary (logs, third-party tools, analytics).
PII = [(re.compile(r"\b[A-CEGHJ-PR-TW-Z]{2}\d{6}[A-D]\b"), "[NI NUMBER]"),
       (re.compile(r"\b(?:\+44\s?7\d{3}|07\d{3})\s?\d{3}\s?\d{3}\b"), "[PHONE]"),
       (re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.]+\b"), "[EMAIL]")]

def redact(text: str) -> str:
    for pattern, label in PII:
        text = pattern.sub(label, text)
    return text

# 3. Hook policy on tool calls: deterministic, runs before permission rules, holds in every mode.
DENY = {"mcp__cases__delete_case", "mcp__cases__merge_records"}                 # never, by any route
ASK = {"mcp__letters__send_external", "mcp__payments__issue_refund"}             # a person approves

async def policy_hook(input_data, tool_use_id, context):
    name, args = input_data["tool_name"], input_data["tool_input"]
    if name in DENY:
        return _decide("deny", "Destructive record changes are done by staff in the case system.")
    if name == "mcp__payments__issue_refund" and args.get("amount_gbp", 0) > 250:
        return _decide("deny", "Refunds over 250 GBP need a finance officer; raise a task instead.")
    if name in ASK:
        return _decide("ask", "Needs officer approval.")
    return {}

def _decide(decision, reason):
    return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": decision,
                                   "permissionDecisionReason": reason}}

# 4. Output check: the reply mentions only the signed-in resident's own case IDs.
def output_ok(reply: str, own_cases: set) -> bool:
    return set(re.findall(r"\bCASE-\d{6}\b", reply)) <= own_cases

# 5. Tuning: choose the screen threshold that keeps misses under a cap with the fewest false blocks.
def tune(scored: list[tuple[float, bool]], max_fn_rate=0.02) -> tuple[float, float, float]:
    best = None
    for t in sorted({s for s, _ in scored}):
        harmful = [s for s, h in scored if h]
        benign = [s for s, h in scored if not h]
        fn = sum(s < t for s in harmful) / len(harmful)
        fp = sum(s >= t for s in benign) / len(benign)
        if fn <= max_fn_rate and (best is None or fp < best[2]):
            best = (t, round(fn, 3), round(fp, 3))
    return best
  • Screen: if the screening model itself refuses, Anthropic’s guidance is to treat that as a harmful verdict, so screen() blocks on stop_reason == "refusal".
  • Redaction is your control: the provider’s data handling doesn’t remove personal data from your own logs. The patterns here are illustrative; production redaction needs a tested library and review.
  • The hook is deterministic: hooks run before permission rules, a hook’s deny holds even in bypassPermissions, and the most restrictive decision wins. Deletes and merges are denied outright, large refunds are denied with a route to a finance officer, and letters and small refunds go to an officer as ask.
  • The reason reaches Claude, so it can tell the resident what happens next instead of retrying.
  • The output check catches a different failure: the agent quoting another resident’s case it should never have seen.

Sandbox execution and browsing, and let scoped credentials set the real limit

Skill 7.1Give access to what’s needed, through boundaries that hold.

  • Claude Code and Agent SDK sandbox: an operating-system boundary around shell commands and their children (Seatbelt on macOS, bubblewrap on Linux and WSL2; not native Windows). Network goes through a proxy whose allowed domains start empty; writes are limited to the working directory unless allowed. Read, Edit, WebFetch, hooks and MCP servers run outside it, so they need permission rules too.
  • Managed Agents: each session gets a fresh cloud container; limited networking with allowed_hosts controls what it can reach. A self-hosted sandbox keeps tool execution inside your network when data can’t leave it.
  • Web access without the intranet: allow the public domains it needs (government guidance, the organisation’s own site), deny internal ranges, and keep the agent’s credentials out of the sandbox.
  • Data access without production writes: a read replica or a narrow API scoped to the resident’s own records, instead of a database credential. The credential’s permissions, not a pattern in a hook, are the real limit.
  • The documentation’s framing: sandboxing, permission rules and permission modes are complementary layers; the sandbox holds even when an allowed command does more than its name suggests.

Gate irreversible effects on a person, and give refusals a safe fallback

Skill 7.1People for the irreversible; a plan for the refused.

  • Gate the effect: approvals sit right before letters leave and money moves, not on reading a case. Show the officer the exact letter and amount.
  • Asynchronous approval: a hook can return defer so the session ends and resumes after the decision, rather than holding a process open (CCAR-P 5.4).
  • Deterministic for the irreversible: deleting a record is denied in code whatever the conversation says; a prompt instruction can be argued with, a hook can’t.
  • Refusal handling: refusals arrive as 200s with stop_reason: "refusal". For an in-scope request, retry on a different model; otherwise give the resident a safe, helpful fallback (contact details, the right form) rather than an empty reply.
  • Safety fallback for the agent itself: when a guardrail blocks, the reply explains what will happen and hands over to staff where needed.

Tune each filter on labelled data by the cost of each kind of error

Skill 7.1Every filter blocks some good requests and misses some bad ones.

  • Measure both on labelled data: a set of harmful attempts (red-team and real) and a larger set of legitimate requests, including awkward but valid ones (a resident angry about a repair, a question mentioning violence in a housing complaint).
  • Choose by the cost of each error: tune() keeps missed harmful requests at or below 2% and then picks the threshold that blocks the fewest legitimate ones. On the synthetic set that’s about 0.62, blocking around 1% of legitimate requests.
  • Different layers, different settings: a lenient input screen is acceptable when deterministic hooks guard the actions; a strict screen in front of a read-only FAQ mostly frustrates residents.
  • Re-tune after changes: a new screening model, a new feature or a new attack pattern moves both rates; re-run the labelled set, and watch live block and appeal rates.

"Tighten the input screen until no attack gets through" blocks legitimate residents and still doesn’t stop an attack that arrives in a web page or tool result. Tune the screen for its job, and put the hard guarantees where they hold: hooks on actions, scoped credentials and the sandbox.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
An agent can delete records. The system prompt says “never delete records”. What is the reliable control?
  1. A. A stronger prompt
  2. B. A PreToolUse hook that denies delete calls, which holds even in bypassPermissions
  3. C. An output filter
  4. D. A screening model
Answer
B
Why
Irreversible actions need deterministic enforcement; a prompt can be argued with, a hook can’t.
Question 2
Scenario
A screening model returns stop_reason refusal on an incoming request. How should the screen treat it?
  1. A. As safe
  2. B. As a harmful verdict, and block
  3. C. Retry until it answers
  4. D. Ignore the screen
Answer
B
Why
Anthropic’s guidance treats a refusing screen as a harmful verdict.
Question 3
Scenario
An agent runs shell commands and browses the web. What stops it reaching internal systems?
  1. A. A prompt instruction
  2. B. A sandbox with a network allowlist, plus credentials that can’t reach production
  3. C. An output check
  4. D. Higher effort
Answer
B
Why
The sandbox and scoped credentials hold even when an allowed command does more than expected.
Question 4
Scenario
A team tightens the input screen until no red-team attack passes. Legitimate users are now blocked often. What is better?
  1. A. Keep it strict
  2. B. Tune the screen on labelled data by error costs, and put hard guarantees in hooks, credentials and the sandbox
  3. C. Remove the screen
  4. D. Block all angry messages
Answer
B
Why
Attacks also arrive in tool results; a screen can’t be the only guarantee.

Key takeaways

  • Derive layers from the agent’s risk profile: what data it reads, which actions are external or irreversible, and which content is untrusted.
  • Screen inputs with a small model (a screening refusal counts as harmful), redact personal data yourself, check outputs against the user’s own scope.
  • Enforce tool policy in hooks: deny destructive actions, cap amounts, send external actions to a person; hook denies hold in every mode.
  • Sandbox execution and browsing, allowlist domains, and use scoped credentials or read replicas so access never reaches production writes.
  • Tune filter thresholds on labelled harmful and legitimate sets by the cost of each error, and re-tune after every change.
