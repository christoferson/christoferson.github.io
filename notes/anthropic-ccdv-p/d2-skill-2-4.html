2.4: Retrieval and Knowledge Grounding at Scale

A knowledge-grounded application is only as good as the passage that reaches the model. This page covers the retrieval pipeline from chunk to rerank, how answers stay tied to their sources, how the system says when it doesn’t know, and how to find the stage that lost the answer when it goes wrong.

Overview

Skill 2.4

Retrieval and Knowledge Grounding at Scale: "Evaluating retrieval architecture for knowledge-grounded production applications, including agentic search versus RAG tradeoffs, chunking and embedding strategy, hybrid search, and reranking, and designing grounding practices such as source citation, uncertainty declaration, and confidence signals, and diagnosing retrieval-quality failures by stage."

Exam items give a retrieval-grounded system with poor answers and its traces, and ask which stage failed or which design change fixes it. Choosing an architecture from corpus and query shape is CCAR-P 3.5; building a single grounded request is CCDV-F 6.4.

At scale, use RAG for the common path and agentic search as the fallback

Skill 2.4The trade-off at scale.

Take an assistant that answers questions from about two million pages of equipment manuals and procedures, updated weekly, with answers used on site.

  • Whole corpus in context: Anthropic’s guidance is that under about 200,000 tokens you can include the knowledge base in the prompt and cache it. Two million pages is far beyond that.
  • Pre-built RAG: indexed retrieval is fast and cheap per query, suits high volume and fairly stable content, and can go stale between re-indexes.
  • Agentic search: the model explores with tools just in time. It’s fresh and handles open questions, but Anthropic notes runtime exploration is slower than pre-computed retrieval, and each query costs several calls.
  • Hybrid (the usual answer at scale): RAG for the common path, agentic search as the fallback when retrieval is weak or the question spans documents. The routing rule is in confidence signals.

Chunk by structure, add context to chunks, combine keyword and vector search, then rerank

Skill 2.4Each stage can lose the answer.

  • Chunking: size, boundaries and overlap matter. A limit stated in a table and qualified in the next paragraph needs both in one chunk; split along the document’s own structure (sections, procedures) rather than fixed lengths alone.
  • Contextual retrieval: prepend 50 to 100 tokens of document context to each chunk ("which manual, which model, which section") before embedding and before building the keyword index. In Anthropic’s tests this cut top-20 retrieval failures by 35% with embeddings, 49% adding contextual BM25, and 67% adding reranking. With prompt caching the one-time cost was about $1.02 per million document tokens.
  • Embeddings: choose and evaluate on your own queries; Voyage and Gemini embeddings did best in Anthropic’s tests. Re-embedding the corpus is a migration, so version the index.
  • Hybrid search: embeddings catch meaning; BM25 catches exact strings such as part numbers and error codes, which technical questions are full of.
  • Reranking: retrieve a wide pool (about 150), rerank to about 20. It adds latency and cost per query and gave the largest single gain.
  • Freshness: re-index as often as the library changes, and record the document version in each chunk so stale answers can be traced.

Ground answers with citations and give Claude a way to say it doesn't know

Skill 2.4Answers tied to passages, and permission not to answer.

grounded_request.py (grounded_request.py) 
"""Build a grounded request: retrieved chunks as search_result blocks with citations, an explicit
way to say 'not found', and a confidence signal the application computes, not the model."""

RERANK_FLOOR = 0.35          # below this, the best chunk is unlikely to answer (tuned on the labelled set)


def build(question: str, chunks: list[dict]) -> dict:
    results = [{"type": "search_result", "source": c["url"], "title": c["title"],
                "content": [{"type": "text", "text": c["text"]}], "citations": {"enabled": True}}
               for c in chunks]
    rules = ("Answer only from the search results. Cite every claim. If they don't contain the answer, "
             "say 'Not found in the engineering library' and name what's missing. If sources disagree, "
             "say so and give both, with their dates.")
    return {"model": "claude-sonnet-5-5", "max_tokens": 2000, "system": rules,
            "messages": [{"role": "user", "content": results + [{"type": "text", "text": question}]}]}


def route(chunks: list[dict]) -> str:
    """Decide before calling the model: weak retrieval goes to agentic search, not to a guess."""
    if not chunks or max(c["rerank_score"] for c in chunks) < RERANK_FLOOR:
        return "agentic_search"
    return "answer"


def confidence(response_blocks: list[dict], chunks: list[dict]) -> str:
    """Share of answer text blocks that carry a citation, combined with retrieval strength."""
    text = [b for b in response_blocks if b["type"] == "text" and b["text"].strip()]
    cited = sum(1 for b in text if b.get("citations"))
    coverage = cited / len(text) if text else 0
    top = max(c["rerank_score"] for c in chunks)
    if coverage >= 0.9 and top >= 0.6:
        return "high"
    return "medium" if coverage >= 0.6 else "low: show sources prominently and suggest an engineer"
  • search_result blocks: each chunk carries a source, title and text content, with citations enabled (they’re off by default, and all results in a request must share the setting). Answers come back with search_result_location citations pointing at the exact block. Inside a tool_result, search results must be the only content.
  • Citations are reliable pointers, not proof: the cited text is guaranteed to exist in the source, but the claim built on it still needs checking. Citations don’t combine with structured outputs (a 400).
  • Uncertainty declaration: the documentation’s first hallucination control is to let Claude say it doesn’t know. Give it an exact phrase, ask it to name what’s missing, and to report conflicting sources with their dates.
  • Restrict to the provided passages for answers used on site, and put the documents before the question.

Compute confidence in code from retrieval scores and citation coverage

Skill 2.4Your code computes it from the evidence.

  • Before the call: if the best reranker score is below a floor tuned on the labelled set, don’t ask the model to answer from weak passages; route to agentic search.
  • After the call: the share of answer text that carries a citation, combined with retrieval strength, gives high, medium or low. Low shows the sources prominently and suggests asking an engineer.
  • Not the model’s own rating: a self-reported "I’m 90% sure" isn’t calibrated. Measured signals can be checked against the labelled set and tuned.
  • Show it to users: a label and the sources, so someone acting on the answer knows when to double-check.

Find the first stage that lost the answer, and fix that stage

Skill 2.4The first stage that lost the answer is the cause.

diagnose.py (diagnose.py) 
"""Find the stage where each failed retrieval-grounded answer went wrong, from traces on a labelled set."""
from collections import Counter

STAGES = ["indexing", "chunking", "retrieval", "reranking", "context", "generation"]


def stage_of(c: dict) -> str:
    """Check stages in pipeline order; the first one that lost the answer is the cause."""
    if c["gold_doc_version"] != c["indexed_version"]:
        return "indexing"                    # stale or missing document in the index
    if not c["gold_chunks"]:
        return "chunking"                    # no single chunk holds the answer (split or truncated)
    if not set(c["gold_chunks"]) & set(c["retrieved_150"]):
        return "retrieval"                   # hybrid search missed it
    if not set(c["gold_chunks"]) & set(c["reranked_20"]):
        return "reranking"                   # found, then ranked out
    if not set(c["gold_chunks"]) & set(c["in_context"]):
        return "context"                     # dropped by the token budget or deduplication
    if not c["answer_correct"] or not c["cited_gold"]:
        return "generation"                  # answer had the evidence and still went wrong or uncited
    return "ok"


def report(cases: list[dict]) -> dict:
    counts = Counter(stage_of(c) for c in cases)
    failed = sum(v for k, v in counts.items() if k != "ok")
    return {s: f"{counts[s]} ({counts[s] / failed:.0%} of failures)" for s in STAGES if counts[s]}
  • What traces must record: document versions indexed, which chunks contain the answer for labelled questions, the top-150 IDs, the reranked 20, what made it into context, and the citations in the answer.
  • Fixes by stage: indexing → re-index cadence and version checks; chunking → structure-aware chunks and context prefixes; retrieval → hybrid search, better embeddings, query rewriting; reranking → a wider pool or a better reranker; context → budget and deduplication; generation → prompt and grounding rules.
  • Aggregate, then fix the biggest stage: the report gives each stage’s share of failures. Measure recall at 20 on your own questions before and after.

"Answers are wrong, so switch to a larger model" fixes only the generation stage. If the right chunk was ranked out or never indexed, no model can cite it; the stage report shows where to spend the effort.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Questions often contain exact part numbers and error codes, and vector search misses them. What should be added?
  1. A. A larger embedding model
  2. B. Keyword (BM25) search alongside embeddings, then reranking
  3. C. Smaller chunks only
  4. D. A longer prompt
Answer
B
Why
Embeddings capture meaning; keyword search matches exact strings. Hybrid search plus reranking covers both.
Question 2
Scenario
A limit is stated in a table and qualified in the next paragraph, and answers keep quoting the limit without the qualification. Which stage is at fault?
  1. A. Generation
  2. B. Chunking, which split the table from its qualification
  3. C. Reranking
  4. D. Citations
Answer
B
Why
Chunking along the document’s structure keeps related content in one chunk.
Question 3
Scenario
Answers are wrong, and the team proposes a larger model. Traces show the right chunk was never in the top 150. What should they fix?
  1. A. The model
  2. B. Retrieval (or indexing), since no model can cite a passage it never received
  3. C. The citation settings
  4. D. The answer format
Answer
B
Why
Diagnose by the first stage that lost the answer; here it is before generation.
Question 4
Scenario
How should the app decide when to label an answer as low confidence?
  1. A. Ask Claude to rate itself
  2. B. Compute it from retrieval scores and the share of the answer backed by citations, tuned on labelled data
  3. C. Use answer length
  4. D. Always label high
Answer
B
Why
Measured signals can be calibrated; a model’s self-rating isn’t.

Key takeaways

  • At scale, RAG for the common path and agentic search for weak or cross-document questions; whole-corpus context only under about 200,000 tokens.
  • Structure-aware chunks with contextual prefixes, hybrid embeddings plus BM25, and reranking a wide pool to about 20; re-index as the library changes.
  • Ground with search_result blocks and citations, an explicit "not found", and conflicting sources reported with dates.
  • Compute confidence from retrieval scores and citation coverage, route weak retrieval away from a guess, and show the label.
  • Diagnose by stage in pipeline order, and fix the stage with the most failures.
