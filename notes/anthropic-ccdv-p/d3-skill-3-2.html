3.2: Production Monitoring and Alerting

An LLM-backed service can be up, fast and wrong. This page defines indicators that capture all three, alerts that wake someone only when the budget is really burning, and the checks that catch quality slipping after a model or prompt change, or a key that has started spending far more than it should.

Overview

Skill 3.2

Production Monitoring and Alerting: "Analyzing production signals from LLM-backed services to define service level indicators (SLIs) and SLOs, design alerting and dashboards (including token and cost telemetry), and detect quality drift, behavioral regressions, and anomalous usage, including drift after model updates."

Exam items give a set of signals and an incident nobody noticed, or an alert that fires constantly, and ask which indicator, threshold or detector is right. The telemetry these signals come from is skill 3.1; measuring quality on live traffic in depth is skill 5.3.

Measure availability, latency, quality, refusals and truncations as separate indicators

Skill 3.2Available, fast and correct, each measured on its own.

slo.py (slo.py) 
"""SLIs, SLOs and burn-rate alerts for a customer-support assistant."""

SLOS = {   # SLI -> (objective, what counts as good)
    "availability":   (0.995, "a usable answer: not a 5xx/529 after retries, not a timeout"),
    "first_token_p95": (1.5,  "seconds to first streamed token, 95th percentile"),
    "quality":        (0.92,  "sampled conversations passing the graded rubric"),
    "refusal_rate":   (0.004, "refusals on in-scope requests (each one is a failed answer)"),
    "truncation_rate": (0.002, "answers ending in max_tokens or model_context_window_exceeded"),
}


def burn_rate(bad: int, total: int, objective: float) -> float:
    """How fast the error budget is being spent: 1.0 spends it exactly over the SLO window."""
    return (bad / total) / (1 - objective) if total else 0.0


def availability_alert(h1: tuple, h6: tuple, objective=0.995) -> str:
    """Two windows (common SRE practice): page only when both the short and long window burn fast."""
    b1, b6 = burn_rate(*h1, objective), burn_rate(*h6, objective)
    if b1 >= 14.4 and b6 >= 14.4:
        return f"page: burning budget at {b1:.0f}x"
    if b6 >= 6:
        return f"ticket: sustained burn at {b6:.0f}x"
    return "ok"
  • Availability: a usable answer after your retries and fallbacks, not just an HTTP 200. Count server errors, overload and timeouts; exclude genuine client errors.
  • Latency: time to first token for streamed chat, and total time for anything a user waits on in full. They respond to different fixes (skill 6.2).
  • Quality: the pass rate of sampled conversations graded against a rubric. Without it, a service that answers quickly and wrongly looks healthy.
  • Refusals and truncations as their own SLIs: both arrive as 200s, so availability never sees them. Track refusals on in-scope requests and answers that stop at max_tokens or the context window.
  • Cost and cache: cost per resolved conversation and cache read share are service-level signals for a Claude workload, even if they don’t carry an SLO.

Page on error-budget burn over two windows, not on every error

Skill 3.2Alert on budget spent, not on every error.

  • Error budget: a 99.5% availability objective allows 0.5% bad answers over the window. Burn rate is how fast that budget is going; 1x spends it exactly over the window.
  • Two windows (common SRE practice): page when both the last hour and the last six hours burn at 14.4x or more, so a brief blip doesn’t page but a real outage does; open a ticket when the six-hour rate stays above about 6x.
  • Page on symptoms users feel (availability, latency, quality falling below objective), and ticket on causes (one tool’s error rate, a cache rate drop) unless they threaten the SLO.
  • Quality alerts need volume: grade enough sampled conversations per hour for a drop to be statistically visible, or alert over longer windows.
  • Alert on missing data too: telemetry export can fail silently, and a quiet dashboard during a peak is a warning, not good news.

Use traces for fast dashboards and the usage API as the ledger

Skill 3.2Two sources with different jobs.

  • Traces and metrics (minutes): tokens, latency, stop reasons and cache read share per route, model and tenant, from the spans in skill 3.1. Fast, but best effort.
  • Usage and Cost Analytics API (the ledger): /v1/organizations/analytics/usage and /cost (beta) with an Admin key, grouped by workspace, API key, model, service tier or the identity behind a request, in 1-minute, 1-hour or 1-day buckets. Usage typically appears within about four hours, so it reconciles and attributes rather than alerts.
  • Per-tenant and per-route views: cost per resolved conversation, tokens per request, cache read share, and rate-limit headroom against the binding limit (skill 2.2).
  • Version on every panel: annotate model ID, prompt version and retrieval index version changes, so a step in a chart can be matched to a deploy.

Compare quality before and after each change, segment by segment

Skill 3.2Compare before and after each change, per segment.

Take a support assistant graded hourly on a sample of conversations about refunds, seating and transfers.

drift.py (drift.py) 
"""Quality drift around a change, and anomalous usage by key or tenant."""
import math
import statistics


def proportion_shift(pass_a: int, n_a: int, pass_b: int, n_b: int) -> float:
    """z for the difference in pass rates (before -> after); |z| > 2 is worth a look."""
    p = (pass_a + pass_b) / (n_a + n_b)
    se = math.sqrt(p * (1 - p) * (1 / n_a + 1 / n_b))
    return (pass_b / n_b - pass_a / n_a) / se


def drift_report(before: dict, after: dict) -> list[str]:
    """Per segment, before and after a model, prompt or retrieval change (graded samples)."""
    out = []
    for seg in before:
        z = proportion_shift(*before[seg], *after[seg])
        if z <= -2:
            out.append(f"{seg}: quality down after the change (z={z:.1f})")
    return out


def usage_anomalies(daily_tokens: dict[str, list[int]], today: dict[str, int]) -> list[str]:
    """Flag keys or tenants whose usage today is far above their own recent history."""
    flags = []
    for key, hist in daily_tokens.items():
        mu = statistics.mean(hist)
        sd = max(statistics.pstdev(hist), 0.1 * mu)        # floor: steady keys still get a tolerance
        if (today.get(key, 0) - mu) / sd > 4:
            flags.append(f"{key}: {today[key]:,} tokens vs a mean of {mu:,.0f}; check for a loop or a leaked key")
    return flags
  • What causes drift: a new model version (an alias that moves, or a migration), a prompt or tool change, a re-index, or a shift in what users ask, such as a new event type. Pinned snapshot IDs don’t change behaviour on their own, so a drop on a pinned model points at your change or your inputs.
  • Segment the comparison: refunds dropped from 92% to 84% after the change (z of about −3.9) while seating held, so the overall rate barely moved. An average hides exactly the regression that matters.
  • After a model update: run the golden set before switching (skill 2.3), then watch live graded samples by segment through the rollout. Refusal and truncation rates are early signs, because a new model may refuse or write at different lengths.
  • Check the grader too: an LLM judge can drift, so re-check it against a fixed set of human-labelled cases on a schedule (skill 5.2).

Compare each key and tenant with its own history, allowing for planned spikes

Skill 3.2Spend that doesn’t match the business.

Take a service whose traffic peaks sharply on planned launch days, called through several API keys.

  • Per key and per tenant: compare today with each one’s own history. A web key at nine times its usual volume suggests a retry loop, an agent stuck in a cycle, or a leaked key; the Usage and Cost API grouped by api_key_id also counts requests that sent no spans.
  • Per session: outliers in turns, tokens or tool calls per conversation catch loops that the daily total hides.
  • Expected spikes: a launch day doubles traffic legitimately; annotate scheduled events so the detector doesn’t page for them, and compare against the same kind of event instead.
  • Spend cap: forecast monthly spend against the tier’s cap; at the cap the API returns 429s until the month resets.

"Alert when the error rate goes above zero" pages on every transient 529 and trains people to ignore the pager, while still missing a quality collapse that returns 200s. Alert on SLO burn across windows, and treat quality, refusals and truncations as indicators in their own right.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A service’s availability dashboard is green, yet users report wrong and cut-off answers. What is missing?
  1. A. A lower error threshold
  2. B. Quality, refusal and truncation indicators, since those failures arrive as 200s
  3. C. More retries
  4. D. Faster time to first token
Answer
B
Why
Availability counts failed requests; quality problems and truncations need their own indicators.
Question 2
Scenario
An alert fires on every transient 529 and the team ignores it. What is better?
  1. A. Alert when errors exceed zero
  2. B. A burn-rate alert over a short and a long window against the SLO
  3. C. Turn off alerting
  4. D. Alert only on daily totals
Answer
B
Why
Two-window burn alerts page on real outages but not brief blips.
Question 3
Scenario
After a prompt change, overall quality barely moves, but one segment fell from 92% to 84%. How should drift be detected?
  1. A. Watch the overall pass rate
  2. B. Compare before and after per segment with a significance test
  3. C. Wait for complaints
  4. D. Re-grade only failures
Answer
B
Why
Averages hide segment regressions.
Question 4
Scenario
One API key suddenly runs at nine times its usual volume on an ordinary day. What should the detector compare against?
  1. A. The organisation’s total
  2. B. That key’s own history, with planned events annotated
  3. C. Another key’s volume
  4. D. A fixed global threshold
Answer
B
Why
Per-key baselines catch retry loops, stuck agents or leaked keys, while planned spikes are expected.

Key takeaways

  • SLIs for availability (usable answers after retries), latency (first token and total), and graded quality, plus refusals and truncations, which return 200s.
  • Page on multi-window burn rate against the SLO, ticket on sustained slower burns and causes, and alert on missing telemetry.
  • Use traces for fast dashboards and the Usage and Cost Analytics API as the ledger; annotate model, prompt and index versions.
  • Detect drift by comparing graded samples before and after each change, per segment; pinned models don’t drift on their own.
  • Flag usage far above a key’s or tenant’s own history, watch per-session outliers, and forecast against the spend cap.
