5.3: Online Quality Measurement

Offline suites say whether a change is safe to ship; live traffic says whether it actually helps. This page samples production for grading, runs A/B tests that can tell a real gain from noise, uses feedback without being misled by it, and picks the metric each kind of task deserves.

Overview

Skill 5.3

Online Quality Measurement: "Analyzing quality on live production traffic using online evaluation techniques, including live-traffic sampling, A/B testing, feedback loops, and metric selection matched to task type (extraction, generation, agentic, retrieval-grounded)."

Exam items describe a live feature and a proposed measure (thumbs-up rate, a judge score, a business metric) and ask whether it measures quality for that kind of task, or whether an A/B result is real. The offline gate is skill 5.1; deciding which evaluation suits a decision is in CCAR-P 4.2.

Measure each feature by the outcome its task exists for

Skill 5.3Each feature fails differently, so it’s measured differently.

Take a listings site that uses Claude four ways: extracting attributes from free-text listings, writing listing descriptions, an agent that books viewings, and question answering grounded in listing documents.

online.py (online.py) 
"""Online quality for a property-listings site with four Claude features."""
import math

METRICS = {   # task type -> primary online metric, plus guard metrics
    "extraction": ("field accuracy on sampled listings, and the rate agents correct extracted fields",
                   ["schema-valid rate", "fields left empty"]),
    "generation": ("rubric score from a calibrated judge on sampled descriptions, and how much agents edit them",
                   ["length", "policy check (no protected-characteristic wording)"]),
    "agentic":    ("viewing bookings that exist in the calendar system and were attended",
                   ["steps per task", "handoffs to staff", "cost per completed booking"]),
    "retrieval":  ("answers judged correct and grounded on sampled questions",
                   ["citation coverage", "'not found' rate", "follow-up question rate"]),
}


def sample_for_grading(traces: list[dict], per_segment=50) -> list[dict]:
    """Stratified live sample: a fixed number per segment, so small segments are graded too."""
    picked, seen = [], {}
    for t in sorted(traces, key=lambda t: t["trace_id"]):          # stable order
        if seen.get(t["segment"], 0) < per_segment and t["consented"]:
            picked.append(t)
            seen[t["segment"]] = seen.get(t["segment"], 0) + 1
    return picked


def ab_result(succ_a: int, n_a: int, succ_b: int, n_b: int) -> dict:
    """Difference in success rate (B - A) with a 95% interval; users, not requests, are the unit."""
    pa, pb = succ_a / n_a, succ_b / n_b
    se = math.sqrt(pa * (1 - pa) / n_a + pb * (1 - pb) / n_b)
    lo, hi = pb - pa - 1.96 * se, pb - pa + 1.96 * se
    call = "B better" if lo > 0 else "B worse" if hi < 0 else "no detectable difference"
    return {"diff": round(pb - pa, 3), "ci": (round(lo, 3), round(hi, 3)), "call": call}


def users_per_arm(base: float, mde: float) -> int:
    """Roughly how many users each arm needs to detect `mde` at 95% confidence and 80% power."""
    p = base + mde / 2
    return math.ceil(2 * (1.96 + 0.84) ** 2 * p * (1 - p) / mde ** 2)


def feedback_rate(thumbs_down: int, thumbs_up: int, sessions: int) -> dict:
    """Explicit feedback is sparse and skewed toward complaints: report coverage alongside the ratio."""
    given = thumbs_down + thumbs_up
    return {"coverage": round(given / sessions, 3), "negative_share": round(thumbs_down / given, 2) if given else None}
  • Extraction: field-level accuracy against a sampled, human-checked set, plus the rate at which listers correct extracted fields after publication, a free implicit label. Schema validity is a guard, not the quality metric.
  • Generation: a calibrated judge’s rubric score on a sample (skill 5.2) and how much listers edit the draft before publishing. No single reference answer exists, so string-match metrics don’t apply.
  • Agentic: the outcome in the system of record (a viewing that exists in the calendar and was attended), not the agent saying it booked one. Steps, handoffs to staff and cost per completed booking are guards.
  • Retrieval-grounded: answers judged correct and grounded on a sample, with citation coverage, the "not found" rate and follow-up questions as signals (skill 2.4).
  • Multidimensional by default: Anthropic’s define-success guidance expects most use cases to need several criteria, such as task fidelity, tone, privacy, latency and price.

Sample live traffic by segment, only where you may keep the content

Skill 5.3Representative, small enough to grade, allowed to keep.

  • Stratify: a fixed number per segment (rentals, sales, commercial) so the small segments are graded at all; random sampling of a skewed mix gives the big segment almost every slot.
  • Respect what you may keep: sample only conversations whose content you’re permitted to retain and grade (consent, contract terms). Full-content tracing makes it possible to build evals from real traffic, but the stored content falls under your observability platform’s retention (skill 3.1).
  • Grade promptly and steadily: a daily sample per segment gives a time series that can show drift (skill 3.2).
  • Feed the offline suite: graded live failures become regression and capability tasks, keeping the offline suite close to real traffic.

Randomise by user, size the test in advance, and report an interval

Skill 5.3Tell a real gain from noise.

  • Randomise by user, not by request, so one person doesn’t see both versions and their many requests aren’t counted as independent. Anthropic’s statistics guidance makes the same point for evals: cluster related cases.
  • Report the difference with an interval: a 2.5-point gain in completed bookings on 10,000 users per arm has an interval clear of zero; 1.5 points on 1,000 users per arm doesn’t, which means "can’t tell", not "no effect".
  • Size the test in advance: detecting a 2-point change from a 41% base needs about 9,500 users per arm at the usual 95% confidence and 80% power. Low-traffic features need longer tests or bigger changes.
  • Fix the metric and duration first, and don’t stop the moment the result looks good; checking repeatedly and stopping early overstates effects.
  • Watch guard metrics: a version that books more viewings but doubles cost per booking or handoffs to staff may not be better.
  • Change one thing: model, prompt or tool in one arm, everything else identical, so the result has one cause.

Prefer implicit signals to sparse, biased ratings, and feed failures back

Skill 5.3Useful, sparse and biased.

  • Explicit feedback (thumbs, ratings) covers a small share of sessions, here 2%, and skews toward complaints. Report coverage next to the ratio, and treat a change in who responds as a possible cause of a change in the ratio.
  • Implicit signals are often better labels: listers correcting extracted fields, editing generated text, users rephrasing a question, a booking cancelled within an hour, escalation to staff.
  • Close the loop: route negative feedback and implicit failures into review queues; reviewed cases become labelled data for the judge and tasks for the offline suite.
  • Business metrics lag and confound: enquiries per listing respond to market conditions as well as descriptions. Use them for direction over months, not to judge a week-long test.

"Thumbs-up rate rose after the change, so quality improved" ignores who gives feedback, how few do, and whether the feature’s actual outcome moved. Measure the outcome the task exists for (field accuracy, edit rate, attended viewings, grounded answers), and compare arms with an interval.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A booking agent’s quality is measured by how often it says “your viewing is booked”. What is a better measure?
  1. A. Its confidence
  2. B. Viewings that exist in the calendar and were attended
  3. C. Response length
  4. D. Thumbs-up rate
Answer
B
Why
For agentic tasks, measure the outcome in the system of record, not the agent’s claim.
Question 2
Scenario
An A/B test shows a 1.5-point gain on 1,000 users per arm, with an interval that includes zero. What does it mean?
  1. A. The change has no effect
  2. B. The test can’t tell; it needs more users or a bigger change
  3. C. The change is better
  4. D. The change is worse
Answer
B
Why
An interval spanning zero means “can’t tell”, not “no effect”.
Question 3
Scenario
An A/B test randomises by request, and heavy users see both versions. What is wrong?
  1. A. Nothing
  2. B. Requests from one user aren’t independent; randomise by user
  3. C. It needs more requests
  4. D. It should randomise by hour
Answer
B
Why
Randomising by user keeps experiences consistent and counts independent units.
Question 4
Scenario
Thumbs-up rate rose after a change. Only 2% of sessions leave feedback. What should the team check?
  1. A. Nothing; quality improved
  2. B. Who responds and whether the task’s actual outcome moved
  3. C. Only the thumbs-down rate
  4. D. Latency
Answer
B
Why
Sparse, self-selected feedback can shift without quality changing.

Key takeaways

  • Pick the metric by task type: field accuracy for extraction, calibrated rubric scores and edit rates for generation, system-of-record outcomes for agents, correct-and-grounded answers for retrieval.
  • Sample live traffic by segment, within what you may retain, and grade steadily; feed failures back into the offline suite.
  • Randomise A/B tests by user, size them in advance, report differences with intervals, and watch guard metrics.
  • Treat explicit feedback as sparse and skewed; prefer implicit signals and route both into review.
  • Business metrics give direction over time; they make poor short-test verdicts.
