3.3: Trace Analysis at Scale

At millions of traces a day, reading traces one by one finds anecdotes, not causes. This page keeps the right traces, aggregates them by the attributes that matter, and ranks the slices of traffic that fail far more than the rest, so a systemic problem shows up with a size attached.

Overview

Skill 3.3

Trace Analysis at Scale: "Analyzing high-volume trace data using sampling strategies, aggregation, and failure-cohort analysis to surface and quantify systemic issues that are not visible in individual traces."

Exam items describe a large trace store and a vague complaint ("it’s worse lately") and ask which analysis would find and size the cause, or why a sampling scheme hid it. Diagnosing one complex failure from its evidence is skill 4.1; the monitors that alert on a problem are skill 3.2.

Sources: Anthropic’s Clio research post (read on 21 November 2026), the multi-agent research system post and the OpenTelemetry pages used earlier, paraphrased. The sampling policy, cohort method and thresholds are my own; the company, files and code are original, and the code is tested on synthetic traces.

Running example. An accounting software company’s in-app assistant handles about two million conversations a day across ledger, invoice and payroll tools in several languages. Support tickets about wrong payroll answers have crept up for a week, and no single trace looks unusual.

Why single traces mislead

Skill 3.3Systemic problems are rates, not events.

  • Every failure looks plausible on its own: a wrong answer, a slow turn, a refusal. Only the rate in one slice of traffic, compared with the rest, shows a pattern.
  • Anecdotes pick themselves: the traces people open are the ones customers complained about, which over-represent loud tenants and dramatic failures.
  • Averages hide slices: a 30% failure rate in one tool path after a prompt change moves the overall rate by a few points.
  • Anthropic’s own practice: for its multi-agent research system, it monitored agent decision patterns and interaction structures without monitoring the contents of individual conversations.

Sampling that keeps the tail

Skill 3.3Decide what to keep after the trace completes.

sampling.py (sampling.py) 
"""Tail-based sampling for an in-app accounting assistant: keep every interesting trace, a small
share of normal ones, and a weight so totals can still be estimated."""
import hashlib

BASE_RATE = 0.01             # normal traces kept
SMALL_TENANT_RATE = 0.10     # so small customers still appear in cohort analysis


def keep(trace: dict, small_tenants: set) -> float | None:
    """Return the sample weight (1/rate) if kept, else None. Decided after the trace completes."""
    if (trace["error"] or trace["stop_reason"] in ("refusal", "max_tokens", "model_context_window_exceeded")
            or trace["latency_s"] > trace["p99_latency_s"] or trace.get("thumbs_down")):
        return 1.0                                                 # always keep the tail
    rate = SMALL_TENANT_RATE if trace["tenant"] in small_tenants else BASE_RATE
    h = int(hashlib.sha256(trace["trace_id"].encode()).hexdigest(), 16) % 10_000
    return 1 / rate if h < rate * 10_000 else None                 # deterministic per trace ID
  • Head sampling (decide at the start) keeps 1% of everything, including 1% of the rare failures you most need. Tail sampling decides after completion, so errors, refusals, truncations, very slow traces and thumbs-down feedback are always kept.
  • Weights: each kept trace carries 1/rate, so totals and rates can still be estimated. Mixing always-kept failures with 1% of successes without weights inflates the apparent failure rate a hundredfold.
  • Stratify: keep a higher share for small tenants, so cohort analysis can see them at all.
  • Deterministic by trace ID, so every service in the request makes the same decision and traces aren’t broken into fragments.
  • Know what’s missing: exported spans are best effort, and a caller can switch sampling off in traceparent. Counts for billing come from the Usage and Cost Analytics API (skill 3.1).

Aggregation: facets first

Skill 3.3The attributes you can slice by decide what you can find.

  • Record facets on every trace: model ID, prompt version, retrieval index version, tool path, tenant, locale, turn count bucket, input length bucket, stop reason, and the outcome (graded pass or fail, user feedback, escalation).
  • Outcome labels make it analysis: a failure definition (graded fail, thumbs-down, a human took over, a refund reversed) has to be on the trace, or aggregation only counts latency and tokens.
  • Bucket continuous values (turns, tokens, latency) so cohorts have enough members.
  • Keep facets low in sensitivity: IDs and categories, not text, so the analysis store can be widely accessible.

Failure-cohort analysis

Skill 3.3Rank slices by how many failures they add.

cohorts.py (cohorts.py) 
"""Failure-cohort analysis over weighted, sampled traces: which slices fail far more than the rest,
and how many failures each accounts for. Individual traces can't show this."""
from collections import defaultdict
from itertools import combinations

DIMENSIONS = ["model", "prompt_version", "tool", "locale", "turns_bucket"]


def cohorts(traces: list[dict], min_weight=200, max_dims=2) -> list[dict]:
    total_w = sum(t["w"] for t in traces)
    base = sum(t["w"] for t in traces if t["failed"]) / total_w
    varying = [d for d in DIMENSIONS if len({t[d] for t in traces}) > 1]   # a constant can't explain anything
    out = []
    for k in range(1, max_dims + 1):
        for dims in combinations(varying, k):
            agg = defaultdict(lambda: [0.0, 0.0])
            for t in traces:
                key = tuple(t[d] for d in dims)
                agg[key][0] += t["w"]
                agg[key][1] += t["w"] * t["failed"]
            for key, (w, f) in agg.items():
                if w < min_weight:
                    continue                           # too small to trust (and to report)
                rate = f / w
                out.append({"cohort": dict(zip(dims, key)), "est_traces": round(w), "fail_rate": round(rate, 3),
                            "lift": round(rate / base, 1), "excess_failures": round(f - base * w)})
    return sorted(out, key=lambda c: -c["excess_failures"])
run_output.txt (Output on a synthetic week) 
{'cohort': {'prompt_version': 'v14', 'tool': 'payroll'}, 'est_traces': 34090, 'fail_rate': 0.307, 'lift': 4.5, 'excess_failures': 8145}
{'cohort': {'tool': 'payroll'}, 'est_traces': 67290, 'fail_rate': 0.163, 'lift': 2.4, 'excess_failures': 6381}
{'cohort': {'prompt_version': 'v14'}, 'est_traces': 100600, 'fail_rate': 0.117, 'lift': 1.7, 'excess_failures': 4889}
{'cohort': {'tool': 'payroll', 'turns_bucket': '1-5'}, 'est_traces': 23030, 'fail_rate': 0.168, 'lift': 2.5, 'excess_failures': 2306}
  • Every slice, one and two facets deep: the failure rate in each, compared with the overall rate (lift), skipping slices too small to trust.
  • Rank by excess failures, not lift alone: failures beyond what the overall rate would predict. A tiny slice with high lift matters less than a large slice with moderate lift.
  • Read the result: prompt v14 combined with the payroll tool fails 31% of the time, about 4.5 times the base rate, and accounts for roughly 8,100 extra failures in the week. The single-facet rows (payroll alone, v14 alone) are the same problem seen less sharply, which is why the interaction matters.
  • Then confirm causally: roll back v14 for payroll or replay those cases on v13, and check the cohort’s rate falls. Cohort analysis points; a controlled comparison proves.
  • Simplification: the demo gives every trace the same weight; with the tail-sampling policy above, use each trace’s own weight.

Clustering content without reading it

Skill 3.3When facets don’t describe the problem.

  • Clio’s approach (Anthropic research, December 2024): Claude extracts facets from each conversation (topic, turn count, language), clusters similar conversations, writes a title and summary for each cluster without private details, and builds a hierarchy. Claude runs every stage, not people.
  • Privacy controls: a minimum number of unique users or conversations per cluster, a check that summaries aren’t identifying, and analysts seeing only higher-level clusters.
  • What it found: a network of automated accounts using similar prompts for SEO spam, safety classifiers missing violations in translation requests, and false positives on job seekers’ CV questions and security coding questions. None of these was visible in a single conversation.
  • Applied to your traffic: cluster failed conversations by what users were trying to do, with the same minimum-size and no-identifying-detail rules, to find failure themes your facets don’t name, such as a new kind of payroll question after a tax-year change.

"Pull the 50 most recent failed traces and read them" finds examples, not the size or the slice. "Sample 1% of all traces" throws away 99% of the rare failures. Keep the tail with weights, aggregate by facets, rank cohorts by excess failures, then confirm with a controlled comparison.

Key takeaways

  • Systemic issues are rates in slices of traffic; individual traces and averages both hide them.
  • Tail-sample: keep every error, refusal, truncation, slow and negatively rated trace, a weighted share of the rest, more for small tenants, decided per trace ID.
  • Record facets and outcome labels on every trace: model, prompt and index versions, tool path, tenant, locale, length buckets, stop reason, graded result.
  • Rank one- and two-facet cohorts by excess failures, then confirm the cause with a rollback or replay.
  • For themes facets can’t express, cluster conversations Clio-style with minimum cluster sizes and non-identifying summaries.
