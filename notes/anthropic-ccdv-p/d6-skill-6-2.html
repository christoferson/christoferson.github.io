6.2: Latency Engineering

"It’s slow" can mean the first word takes too long to appear, or the whole answer takes too long to finish. They have different causes and different fixes. This page splits a turn into its parts and matches each lever to the part it actually moves.

Overview

Skill 6.2

Latency Engineering: "Analyzing the latency profile of a Claude application against a latency target, distinguishing time-to-first-token from total latency, and applying streaming, parallel tool execution, cache checkpointing, and effort-level tuning."

Exam items give a latency breakdown and a target and ask which change meets it, often with options that improve the wrong part. Choosing between latency and accuracy when both constrain a system is CCAR-P 3.3; latency SLIs are in skill 3.2.

Time to first token and total latency have different causes

Skill 6.2Two numbers, two sets of causes.

  • Time to first token (TTFT): network and gateway, plus processing the prompt before generation starts. It grows with uncached input length, and it is what a streaming user feels first.
  • Total latency: TTFT plus every tool round trip plus generation time (thinking and output tokens divided by output speed) plus the next call’s TTFT in an agent loop.
  • Which matters: chat users judge TTFT and a steady stream; an API caller that needs the complete JSON judges total latency, and streaming does nothing for it.
  • Anthropic’s order: get a prompt that works first, measure baseline latency and TTFT, then apply one latency technique at a time and check quality after each.

Profile a turn into its parts before choosing levers

Skill 6.2Attribute the seconds, then choose levers.

Take a grocery app’s order assistant that answers “can I swap the oat milk and still get delivery tomorrow?” by checking stock, delivery slots and the basket. Targets: first token within 1 second, the whole answer within 8 seconds at the 95th percentile.

latency.py (latency.py) 
"""Latency profile of one turn of a grocery app's order assistant, and the levers that move each part.
Rates come from your own traces; the numbers in the demo are illustrative."""
import asyncio


def profile(t: dict) -> dict:
    """Split a turn into what the user waits for before the first token, and after it."""
    ttft = t["gateway_s"] + t["prefill_s"]
    tools = sum(t["tool_s"]) if not t["parallel_tools"] else max(t["tool_s"], default=0)
    generate = (t["thinking_tokens"] + t["output_tokens"]) / t["output_tps"]
    return {"ttft_s": round(ttft, 2), "tools_s": round(tools, 2), "generate_s": round(generate, 2),
            "total_s": round(ttft + tools + generate + t["second_call_ttft_s"], 2)}


def levers(p: dict, target: dict) -> list[str]:
    """Match the lever to the part that misses its target (TTFT and total are separate targets)."""
    out = []
    if p["ttft_s"] > target["ttft_s"]:
        out.append("cache the stable prefix (faster time to first token on long prompts); trim the prompt")
    if p["tools_s"] >= 0.3 * target["total_s"]:
        out.append("run independent tool calls in parallel; return all results in one user message")
    if p["generate_s"] > 0.5 * target["total_s"]:
        out.append("lower effort for this route, ask for shorter answers, or use a faster model / fast mode")
    if not out and p["total_s"] > target["total_s"]:
        out.append("stream so the user sees progress, then attack the largest part")
    return out


async def run_tools(calls: list[dict], impl: dict) -> list[dict]:
    """Run the tool_use blocks of one response concurrently (they are independent reads here)."""
    results = await asyncio.gather(*(impl[c["name"]](**c["input"]) for c in calls))
    return [{"type": "tool_result", "tool_use_id": c["id"], "content": r} for c, r in zip(calls, results)]
  • Before: 2.0 s to first token (a long uncached prompt), 2.4 s of tools run one after another, 10 s generating 1,200 thinking tokens and 300 of answer, and 0.6 s for the follow-up call: 15 s against an 8 s target.
  • The levers the profile points to: cache the prefix (TTFT over target), run the three lookups in parallel (tools over 30% of the budget), and lower effort or shorten the answer (generation over half the budget).
  • After: 0.6 s, 0.9 s and 2.0 s, a 4.1 s turn. Each change was checked against the quality eval before the next.
  • Use percentiles from traces, per route and input size, not a single happy-path run; the slow tail usually comes from long baskets and long conversations.

Streaming shortens the felt wait; caching shortens time to first token

Skill 6.2Faster first token, and progress the user can see.

  • Streaming improves perceived responsiveness: the user reads while the rest is generated. It doesn’t shorten total latency.
  • Cache checkpoints: a breakpoint at the end of the stable prefix (instructions, tools, store policies) means later requests skip processing it. The caching documentation notes improved TTFT for long documents. The 5-minute and 1-hour caches behave the same for latency; use 1 hour when follow-ups can come more than 5 minutes apart.
  • Pre-warming: a request with max_tokens: 0 writes the cache before the user’s first message, lowering the first interaction’s TTFT (not available inside batches).
  • Keep the prefix stable: a timestamp or a reordered tool list at the start forces a full re-read on every call, which shows up as TTFT creeping up with no traffic change.

Run independent tool calls in parallel so a turn waits for the slowest

Skill 6.2Several tool calls in one response, run at once.

  • On by default: Claude can return several tool_use blocks in one response. The API doesn’t set the execution order; run_tools() runs them together with asyncio.gather, so the turn waits for the slowest, not the sum.
  • Safe to parallelise: independent, read-only calls (stock, slots, basket). Calls with side effects, shared state or an order dependency (reserve a slot, then charge) may need to run in sequence.
  • Return format keeps it working: every result in one user message, with no text before the tool results.
  • Encourage it: a system-prompt instruction to call independent tools together; the documentation notes some models issue fewer parallel calls in long agent loops.
  • Turn it off with disable_parallel_tool_use: true inside tool_choice (not a top-level parameter), for tools that mustn’t run together.

Cut generation time with lower effort, shorter output or a faster model

Skill 6.2Generation time is tokens over speed.

  • Effort: higher effort means more thinking tokens, which are output tokens and take time. Set it per request: low for the order assistant’s routine questions, higher for refunds and disputes. A mid-conversation system message can change it without breaking the cache (beta; skill 1.4).
  • Output length: ask for shorter answers (sentence or paragraph limits work better than word counts) and set max_tokens as a hard cap.
  • Model speed: the models overview labels Haiku 5.5 fastest and Sonnet 5.5 fast; Haiku 5.5 is the documentation’s choice for speed-critical work, with effort as its main control.
  • Fast mode: up to about 2.5 times the output speed at a premium price, on the Claude API, for latency-bound routes where a smaller model loses quality.
  • Fewer round trips: one well-specified tool that returns stock and slots together beats two calls; each round trip adds the next call’s TTFT.

"Turn on streaming to meet the 8-second total target" improves how the wait feels, not how long it is. "Switch to a faster model" when the time is spent in sequential tool calls changes little. Profile the turn, then use the lever for the part that misses: caching for TTFT, parallel tools for round trips, effort and length for generation.

Scenario

  1. A. Yes, always
  2. B. No; streaming improves perceived wait, not total latency
  3. C. Only with caching
  4. D. Only on Haiku

B
Why
A caller that needs the whole result judges total latency.

Scenario
Time to first token creeps up with no change in traffic. What is a likely cause?
  1. A. Larger outputs
  2. B. Something at the start of the prompt changes each call, breaking the cache
  3. C. Parallel tools
  4. D. Lower effort
Answer
B

Scenario
A turn spends 2.4 seconds on three independent read-only lookups run one after another. What helps?
  1. A. A faster model
  2. B. Run the tool calls in parallel
  3. C. Streaming
  4. D. More thinking
Answer
B

Parallel execution makes the turn wait for the slowest call, not the sum.
Question 4
Scenario
Generation takes over half the latency budget on routine questions. What lever fits?
  1. A. Disable caching
  2. B. Lower effort for routine requests and ask for shorter answers
  3. C. Add more tools
  4. D. Raise max_tokens
Answer
B
Why
Generation time is tokens over speed; fewer thinking and output tokens shorten it.

Key takeaways

  • Separate TTFT (gateway plus prompt processing) from total latency (plus tools, generation and follow-up calls), and know which one the user or caller feels.
  • Profile real traces by percentile, attribute the seconds, and change one lever at a time with a quality check after each.
  • Cache the stable prefix and pre-warm for TTFT; stream for perceived speed; keep the prefix free of changing values.
  • Run independent tool calls in parallel and return all results in one user message; sequence calls with side effects.
  • Cut generation time with lower effort per route, shorter outputs, a faster model or fast mode, and fewer round trips.
