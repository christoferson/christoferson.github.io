1.4: Context and Memory Architecture

An agent that runs for hours fills its window and its budget. This page sets a context policy: what to clear, when to compact, what to keep outside the window, how to change instructions without losing the cache, and how to keep a 300-tool catalogue from crowding everything else out.

Overview

Skill 1.4

Context and Memory Architecture: "Evaluating context-policy options for long-running agents approaching context limits or cost ceilings, including context compaction and editing, persistent memory, cache-safe instruction changes mid-conversation, and tool-use techniques that keep large tool catalogs out of the context window."

Exam items describe an agent that is slowing, forgetting or overspending deep into a session and ask which policy change fixes it without breaking something else, usually the cache. The Foundations treatment of the same tools is CCDV-F 6.1; persistence across restarts is skill 1.2.

Sources: the mid-conversation system messages page, read on 21 November 2026, and the compaction, context editing, memory tool, tool search and prompt caching pages used for the earlier notes, all paraphrased. The company, files and code are my own; the code is tested by sending each request through the Python SDK to a mocked API.

Running example. A data-platform team runs an agent that migrates warehouse jobs to a new scheduler. Sessions last several hours, it can reach 300 tools from six internal services, and each session has a $30 ceiling.

Where the tokens go

Skill 1.4Measure before choosing a policy.

  • Tool definitions: sent on every request. A multi-server setup can carry tens of thousands of tokens of definitions; the tool search documentation cites about 55,000 as typical, and says tool selection degrades past 30 to 50 tools.
  • Tool results: query output and logs, mostly stale a few turns later.
  • Conversation: reasoning, decisions and instructions that still matter.
  • The cache read share: anything that edits the start of the prompt (tools, then system) forces a re-read of everything after it at full price. A context policy that keeps changing the prefix can cost more than it saves.

Clearing, compaction and memory

Skill 1.4Match the tool to what is growing.

  • Context editing (clear_tool_uses_20250919, beta context-management-2025-06-27): clears old tool results above a trigger (default 100,000 input tokens), keeps the most recent few (default 3), and can exclude tools such as memory. It is exact: the conversation itself is untouched, and your application still holds the full history.
  • Compaction (compact_20260112, beta compact-2026-01-12): summarises the conversation when input reaches a threshold (default 150,000, minimum 50,000). Pass instructions for what must survive verbatim. It loses detail, so don’t let it be the only home for facts the agent must keep exact.
  • The memory tool (memory_20250818): files the agent reads and writes, stored by your application outside the window. It survives clearing, compaction and restarts, and it is ZDR and HIPAA eligible.
  • Order of preference (my reading): clear stale tool output first, keep durable facts in memory, and compact only when the conversation itself is long. The documentation examples show the two edits separately, so this page doesn’t assume they can be combined in one request.
  • Cost ceilings: the same tools lower input tokens per turn. For a hard stop, cap the session in code and tell the agent when it’s close (next section).

Changing instructions without breaking the cache

Skill 1.4Mid-conversation system messages.

  • The problem: the cache hashes tools, then system, then messages. Editing the top-level system, even appending a sentence, misses the cache for the system prompt and every message after it; editing tools invalidates the whole conversation.
  • The fix: append {"role": "system", ...} to messages where the new rule starts. The prefix is unchanged and still read from cache, and the rule carries system weight: it outranks user text, and later system messages win over earlier ones and over the top-level field.
  • Placement: directly after a user turn (a turn of tool results counts), then either the end of messages or an assistant turn. Between a tool_use and its tool_result it returns a 400.
  • Models: current Fable, Opus 5.5, Opus 5, Opus 4.8, Sonnet 5.5 and Haiku 5.5. Not Sonnet 5. On Bedrock’s bedrock-runtime, InvokeModel only.
  • Documented uses: a mid-session policy change, and state your application observes, such as the remaining budget dropping below a threshold. Related betas let the same message add or remove tools and change effort.
  • Not for third-party content: tool output and documents stay in tool_result blocks, where Claude treats them as data.

Keeping a large tool catalogue out of context

Skill 1.4Tool search, deferred loading and code.

  • Tool search with defer_loading: send every definition, mark most as deferred, and add a search tool (tool_search_tool_regex_20251119 or the BM25 variant). Claude finds and loads the few it needs; the documentation reports over 85% fewer definition tokens. Keep the three to five most used tools loaded, keep at least one tool non-deferred, and never defer the search tool. Up to 10,000 tools can be deferred.
  • When it’s worth it: ten or more tools, more than about 10,000 tokens of definitions, falling selection accuracy, or several MCP servers. With a handful of tools used on every turn, plain tool use is better.
  • Programmatic tool calling: Claude writes code that calls tools in the code execution container, so intermediate results don’t enter the context. It isn’t ZDR eligible.
  • Subagents: a worker with its own window and a narrow tool set does the bulky part and returns a summary (skill 1.1).
  • Cache-friendly by design: deferring keeps the tools array stable across turns, while adding and removing tools by editing it would invalidate the cache each time.

The policy in code

Skill 1.4One function builds every request.

context_policy.py (context_policy.py) 
"""Context policy for a long-running data-platform agent: 300 tools across six MCP-backed services,
sessions of several hours, and a per-session spend ceiling. Builds each Messages API request."""

SYSTEM = [{"type": "text", "text": "You migrate warehouse jobs to the new scheduler. ...",
           "cache_control": {"type": "ephemeral", "ttl": "1h"}}]          # stable: never edited mid-session
ALWAYS_LOADED = {"get_job", "run_query", "memory"}                     # the 3-5 tools used on most turns
CEILING_USD = 30.0


def tool_list(catalog: list[dict]) -> list[dict]:
    """Big catalogue: send every definition, but defer all except the few used every turn."""
    tools = [{"type": "tool_search_tool_regex_20251119", "name": "tool_search_tool_regex"},
             {"type": "memory_20250818", "name": "memory"}]
    for t in catalog:
        tools.append(t if t["name"] in ALWAYS_LOADED else {**t, "defer_loading": True})
    return tools


def context_management(tokens: int, tool_result_share: float) -> tuple[dict | None, list[str]]:
    """Clear stale tool output first (cheap, exact); compact only when the conversation itself is long."""
    if tool_result_share >= 0.5 and tokens < 150_000:
        return ({"edits": [{"type": "clear_tool_uses_20250919",
                            "trigger": {"type": "input_tokens", "value": 100_000},
                            "keep": {"type": "tool_uses", "value": 3},
                            "exclude_tools": ["memory"]}]}, ["context-management-2025-06-27"])
    if tokens >= 120_000:
        return ({"edits": [{"type": "compact_20260112",
                            "trigger": {"type": "input_tokens", "value": 150_000},
                            "instructions": "Keep every job ID, its migration status and open errors verbatim."}]},
                ["compact-2026-01-12"])
    return None, []


def notices(spent_usd: float, new_rule: str | None) -> list[dict]:
    """Instruction and state changes go at the end as one system message, so the cached prefix survives.
    It must directly follow a user turn (a tool_result turn counts) and end the messages list."""
    blocks = []
    if new_rule:
        blocks.append({"type": "text", "text": new_rule})
    if spent_usd >= 0.8 * CEILING_USD:
        blocks.append({"type": "text", "text": f"Budget: ${CEILING_USD - spent_usd:.2f} left. Finish the "
                       "current job, write progress to memory, then stop."})
    return [{"role": "system", "content": blocks}] if blocks else []


def request(messages, catalog, tokens, tool_result_share, spent_usd, new_rule=None) -> dict:
    cm, betas = context_management(tokens, tool_result_share)
    req = {"model": "claude-opus-5-5", "max_tokens": 16000, "system": SYSTEM,
           "tools": tool_list(catalog), "messages": messages + notices(spent_usd, new_rule),
           "cache_control": {"type": "ephemeral"}}                      # automatic caching of the growing history
    if cm:
        req["context_management"], req["betas"] = cm, betas
    return req
  • Stable prefix: the system prompt has a 1-hour breakpoint and is never edited; the tool list is the same every turn, with all but the core three deferred.
  • Tool output dominates: clear old results, keeping the last three and the memory tool’s.
  • The conversation itself is long: compact, with instructions to keep job IDs, statuses and errors verbatim.
  • A new rule from the team (dry-run first) and a budget warning at 80% arrive as one system message at the end, so neither breaks the cache.

"Add the new rule to the system prompt" is the natural edit and the expensive one: every cached turn after it is re-read at full price. "Remove unused tools from the tools array as the session goes" has the same effect, for the whole conversation. Append a system message; defer tools instead of removing them.

Key takeaways

  • Find what is growing: tool definitions, tool results or the conversation.
  • Clear stale tool results (exact), keep durable facts in the memory tool, and compact (lossy) only when the conversation itself is long, with instructions for what must survive.
  • Change instructions mid-session with a system message appended after a user turn, not by editing system or tools; not on Sonnet 5.
  • For large catalogues, defer tools behind tool search, keep the core few loaded, and push bulky intermediate work into code or subagents.
  • Enforce cost ceilings in code, and tell the agent its remaining budget as observed state.
