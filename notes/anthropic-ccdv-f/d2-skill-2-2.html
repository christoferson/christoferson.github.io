Overview

Skill 2.2

Systems Life Cycle (2.8% of the exam): "Systems life cycle management concepts and frameworks used to develop, implement, operate, and maintain IT systems."

The description is generic, so this page covers two things: the standard life cycle concepts any developer should know, and how they apply to a Claude application, where models are released, deprecated and retired on a published schedule and API versions change behaviour. Defining requirements is skill 2.1; configuration such as model pinning in files is skill 2.6.

Sources: NIST's glossary and publications (SP 800-160 Vol. 1 Rev. 1, SP 800-218), and Anthropic's documentation on model IDs and versions, API versioning, model deprecations, migration guides and release notes, checked on 8 November 2026. Descriptions of waterfall, iterative and DevOps practice are general knowledge.

Running example. The shop's returns assistant (skill 2.1) has requirements and success criteria. Now it has to be built, launched and kept running for years, through several model generations.

Life cycle concepts

Skill 2.2The general framework for developing and running IT systems.

NIST defines the system development life cycle as the activities associated with a system across its initiation, development and acquisition, implementation, operation and maintenance, and finally its disposal. Textbook versions name more phases (for example concept, requirements analysis, design, construction, acceptance, deployment, maintenance and decommissioning) and stress that they can overlap and repeat.

  • Waterfall: phases run in sequence, each signed off before the next. Predictable, but slow to absorb change.
  • Iterative and agile: short cycles that build, test and get feedback, then repeat.
  • DevOps and CI/CD: automated build, test and deployment, with monitoring feeding back into development; releases are small, staged and reversible.
  • Maintenance includes fixing defects, adapting to a changing environment, improving the system and preventing problems. For an LLM application, "a changing environment" includes the model itself.

Security runs through every phase. NIST's Secure Software Development Framework (SP 800-218, version 1.1) groups practices into preparing the organization, protecting the software, producing well-secured software and responding to vulnerabilities, and has a companion profile for generative AI (SP 800-218A).

Withdrawn NIST guidance. NIST SP 800-64 ("Security Considerations in the System Development Life Cycle") was withdrawn in 2019. NIST now points to SP 800-160 Volume 1, "Engineering Trustworthy Secure Systems" (Revision 1, November 2022).

The life cycle of a Claude feature

Skill 2.2Applying the life cycle to an LLM application.

LLM features fit an iterative model naturally, because quality is measured by evaluations rather than proven by design. Anthropic's own guidance describes the build loop as: define success criteria, write test cases, draft a prompt, test and refine, validate, then ship.

  1. PlanBusiness goal, requirements and measurable success criteria (skill 2.1).
  2. BuildPrompts, tools and the workflow, kept in version control with the rest of the code.
  3. EvaluateRun the evaluation set against the success criteria, fix what fails, and repeat until it passes.
  4. DeployA separate production workspace and key, a pinned model ID, and a staged rollout (for example to 10% of conversations first) with a way back.
  5. Operate and monitorUsage and rate-limit dashboards, error and latency tracking, the request-id of failed calls, a regular sample of conversations re-graded, and customer satisfaction.
  6. MaintainWatch for model deprecations and API changes, re-run evaluations on newer models before switching, update SDKs deliberately, and eventually retire the feature or replace it.

Evaluations are the regression tests. In ordinary software, unit tests protect against regressions. In an LLM feature, the evaluation set plays that role: run it on every prompt change, every model change and every SDK or API-version upgrade.

Model versions

Skill 2.2What a model ID promises, and what an API version controls.

  • Every model ID is a pinned snapshot. The weights behind an ID never change; improvements ship under a new ID. Since the Claude 4.6 generation, IDs have no date (claude-opus-5-5, claude-sonnet-5-5), and the docs warn that these dateless IDs are not evergreen aliases that move to the newest model.
  • Older aliases do move. Before 4.6, IDs carried a date (claude-sonnet-4-5-20250929), and their short aliases (claude-sonnet-4-5) pointed to the latest dated snapshot. The stability promise covers IDs, not those aliases.
  • Pinned isn't frozen. The serving system around a model (routing, safety classifiers, sampling) can change, which may cause small behaviour differences even on an unchanged ID.
  • API versions. Every request sends an anthropic-version header (the SDKs add it). The versions so far are 2023-01-01, 2023-06-01 and 2026-10-21. Within a version, Anthropic may add optional inputs, output fields and event types, so clients must ignore fields they don't recognize.

API version 2026-10-21. The new version, released on 21 October 2026, removes temperature, top_p and top_k for every model (requests that send them get an error) and changes some other request rules. The new major SDK versions (Python 2.0.0, TypeScript 1.0.0) send it by default, so upgrading the SDK can break old code even with the same model. Treat an SDK major upgrade like a model change: re-run the evaluations.

Deprecation and retirement

Skill 2.2Anthropic's model life cycle, from release to retirement.

Each model moves through four statuses:

  • Active: fully supported and recommended.
  • Legacy: no longer updated; may be deprecated later.
  • Deprecated: still works but isn't recommended; it has a named replacement and a retirement date. The docs add that deprecated models are likely to be less reliable than active ones.
  • Retired: requests fail. They aren't redirected to a newer model.

For publicly released models, Anthropic gives at least 60 days' notice before retirement, by email to customers with active deployments and on the deprecations page. Current models list a "not sooner than" retirement commitment, roughly a year after launch (for Claude Opus 5.5, not before 22 September 2027). For example, Claude Sonnet 4.5 was deprecated on 30 September 2026 and retires on 30 November 2026, with Sonnet 5.5 as its replacement. The Console's usage export (by API key and model) shows which applications still call a deprecated model.

Platforms keep their own calendars. The deprecation dates apply to Anthropic-operated platforms (the Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud and Microsoft Foundry). Amazon Bedrock and Google-managed Google Cloud set their own dates: Claude Haiku 3.5, for instance, was retired on the Claude API in February 2026 but stayed available on Bedrock and Google Cloud. Check the dates for the platform you actually use.

Upgrading safely

Skill 2.2Moving to a newer model without surprises.

Swapping the model string isn't a safe upgrade. Anthropic publishes a migration guide for each model because new models often bring breaking changes. Recent examples: Opus 4.6 and later don't accept a prefilled assistant reply; manual extended thinking was replaced by adaptive thinking in the 4.7 generation; Opus 5.5, Sonnet 5.5 and Fable 5.1 reject forced tool_choice; and a new tokenizer from Opus 4.7 changed token counts, and therefore costs.

  1. Read the migration guide and release notesList what the new model changes or rejects.
  2. Run the evaluation set on the new modelIn a development workspace, against the same success criteria, including cost and latency.
  3. Adjust prompts, parameters and codeFor anything the guide lists or the evaluations reveal.
  4. Roll out graduallyChange the pinned ID for a share of traffic, compare production metrics, then switch fully, well before the old model's retirement date.

Ask early, too: the docs recommend testing newer models well before a retirement date rather than at the deadline.

Operating and monitoring

Skill 2.2Keeping a Claude system healthy after launch.

  • Usage and limits: the Console's usage page shows tokens, requests, rate-limit use and cache hit rate; the Usage and Cost Analytics API provides the same data for your own dashboards. Response headers report remaining rate limits.
  • Errors and support: log the request-id of every failed call; check the status page (status.claude.com) during incidents.
  • Quality: re-grade a sample of real conversations against the success criteria on a schedule; quality can drift as customer questions change, even when nothing in the system has.
  • Change awareness: follow the release notes and the deprecations page, and read Anthropic's emails about models you use.
  • Cloud platforms: on Bedrock use CloudWatch and CloudTrail; on Foundry, Azure Monitor. Anthropic's platform pages suggest keeping activity logs for at least a rolling 30 days.

Key takeaways

  • The SDLC runs from initiation through development, implementation, operation and maintenance to disposal; iterative and DevOps practices suit LLM features, with security built in (NIST SSDF). SP 800-64 is withdrawn.
  • A Claude feature's loop: plan, build, evaluate, deploy (pinned model, staged rollout), operate and monitor, maintain. Evaluations are the regression tests.
  • Every model ID is a pinned snapshot; dateless IDs since 4.6 aren't "latest" aliases. API version 2026-10-21 removes sampling parameters, and new SDK majors use it by default.
  • Statuses: active, legacy, deprecated, retired (requests fail). At least 60 days' notice; Bedrock and Google-managed Google Cloud set their own dates.
  • Upgrade by reading the migration guide, re-running evaluations, fixing breaking changes and rolling out gradually, well before retirement.
