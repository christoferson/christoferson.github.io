7.2: Deterministic Guardrails and Least Privilege

Making sure an agent can't do serious damage even if it is fully convinced it should: the narrowest tools and credentials, rules and hooks that refuse in every mode, a person on the writes, and an operating-system boundary around the shell.

Overview

Skill 7.2

Deterministic Guardrails and Least Privilege: "Applying guardrail layering, least privilege, and hooks as deterministic enforcement so that destructive actions cannot execute even under adversarial instruction."

Exam items describe an agent that could delete, overwrite or leak something, and ask which control makes that impossible rather than unlikely. Skill 7.1 lowers the chance that an injection succeeds; this skill limits what a successful one can do. Building hooks in general is skill 1.2.

Sources: the Agent SDK documentation on permissions and hooks, the Claude Code sandboxing documentation and Anthropic's injection guidance, checked on 19 and 20 November 2026 and paraphrased. The hook and approval callback were tested by calling them directly with claude-agent-sdk 0.2.185.

Running example. The shop's operations agent investigates data problems in the orders database and proposes fixes. It reads support tickets, so it will sometimes see text written by attackers.

Assume the model is persuaded

Skill 7.2Design for the case where every prompt-level defence has failed.

"Even under adversarial instruction" is the key phrase. Suppose an injected ticket has convinced the agent that dropping a table is the right thing to do. Instructions in the system prompt are what was just overcome, so they can't be the control. The controls that still hold are the ones that don't consult the model:

  • tools and credentials it was never given;
  • rules and hooks that run before every call;
  • a person who approves writes;
  • an operating-system boundary around the shell.

Layer them so that each one stops the action on its own.

An agent with six layers

Skill 7.2Least privilege, rules, a hook, approval, sandbox and credentials.

ops_guardrails.py (Python, Agent SDK) 
"""An operations agent that can query and fix the shop's database, where destructive actions can't run whatever it is told.
Each layer works on its own; none depends on the model choosing well."""
import json
import re

from claude_agent_sdk import ClaudeAgentOptions, HookMatcher, PermissionResultAllow, PermissionResultDeny

DESTRUCTIVE_SQL = re.compile(r"\b(drop|truncate|alter)\b|\bdelete\s+from\s+\w+\s*(;|$)|\bupdate\s+\w+\s+set\b(?!.*\bwhere\b)", re.I | re.S)
DESTRUCTIVE_SHELL = re.compile(r"\brm\s+-[a-z]*r[a-z]*f|\bgit\s+push\b.*--force|\bpsql\b.*\bprod", re.I)


async def block_destructive(input_data, tool_use_id, context):
    """Layer 3 (hook): runs before the call, in every permission mode, so an injected 'DROP TABLE' never executes."""
    args = input_data["tool_input"]
    text = args.get("sql") or args.get("command") or ""
    if DESTRUCTIVE_SQL.search(text) or DESTRUCTIVE_SHELL.search(text):
        return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny",
                                       "permissionDecisionReason": "Destructive statements are blocked. Propose the change "
                                       "as a migration for review instead."}}
    return {}


def approval(approve):
    """Layer 4 (approval): writes go to a person; the callback runs for calls that would otherwise prompt."""
    async def can_use_tool(tool_name, tool_input, ctx):
        if tool_name == "mcp__db__execute_write":
            ok = await approve(tool_name, tool_input)          # e.g. a Slack button or a ticket
            return PermissionResultAllow() if ok else PermissionResultDeny(message="A reviewer declined this write.")
        return PermissionResultDeny(message=f"{tool_name} isn't allowed for this agent.")
    return can_use_tool


def options(approve) -> ClaudeAgentOptions:
    settings = {"permissions": {"deny": [                         # Layer 2 (rules): checked before the mode
        "Read(./.env)", "Read(./secrets/**)", "Bash(rm -rf *)", "Bash(git push --force *)", "Bash(psql *prod*)"]}}
    return ClaudeAgentOptions(
        allowed_tools=["Read", "Grep", "mcp__db__query"],                 # Layer 1 (least privilege): read freely ...
        disallowed_tools=["WebFetch", "WebSearch", "Write"],              # ... and nothing it doesn't need
        settings=json.dumps(settings),
        hooks={"PreToolUse": [HookMatcher(matcher="Bash|mcp__db__.*", hooks=[block_destructive], on_failure="block")]},
        can_use_tool=approval(approve),
        sandbox={"enabled": True, "allowUnsandboxedCommands": False,      # Layer 5 (OS): Bash can't escape ...
                 "network": {"allowedDomains": ["db.staging.shop.internal"]}},  # ... or reach anything else
        env={"DB_ROLE": "readonly"},                                      # Layer 6 (credentials): the query tool's role
        permission_mode="default",
        max_turns=30,
    )
  1. Least privilege: it reads freely with Read, Grep and a read-only query tool, and the web and file-writing tools are removed.
  2. Deny rules refuse secrets, recursive deletes, force pushes and production psql.
  3. A PreToolUse hook refuses destructive SQL and shell commands, with a reason that redirects to a reviewed migration. on_failure="block" means a crashing hook refuses rather than allows.
  4. Approval: can_use_tool sends database writes to a person and denies anything else that would have prompted.
  5. Sandbox: Bash runs inside the OS sandbox, can't opt out, and can reach only the staging database host.
  6. Credentials: the query tool connects with a read-only database role.

The regexes are a layer, not the wall. Pattern matching on SQL can be evaded with comments, odd spacing or stacked statements. The control an injection can't talk its way past is layer 6: a read-only role cannot drop a table however the statement is written. Put the strongest guarantee where the action happens, in the credentials the tool uses.

The order checks run in

Skill 7.2Why a deny holds in every mode.

For each tool call, the Agent SDK checks, in order:

  1. hooks;
  2. deny rules;
  3. ask rules;
  4. the permission mode;
  5. allow rules;
  6. the canUseTool callback.

Hooks and deny rules come before the mode, so a hook's deny applies even in bypassPermissions. A hook's allow, on the other hand, doesn't skip deny or ask rules. When several hooks disagree, the most restrictive decision wins.

A bypassPermissions value set on a subagent's definition is never applied, though subagents do inherit the main session's mode. So a guardrail written as a hook or deny rule can't be switched off by a mode change, and not by anything the model says either.

Least privilege

Skill 7.2What isn't granted can't be misused.

  • Tools: give the agent only the tools the task needs, and remove the rest with disallowed_tools. Remember that allowed_tools pre-approves rather than restricts. Give subagents their own short tools lists.
  • Tool scope: split read and write into separate tools, so reads can be pre-approved and writes gated. Narrow each tool's parameters too: an email tool that can only send to the verified customer address beats one with a free-text recipient.
  • Credentials: each tool's own access is the final word. That means a read-only database role, a payments key that can refund only up to a limit, and scoped tokens for each environment (skill 7.3).
  • Data: keep secrets out of the agent's context and reach. Deny-read .env and secrets folders, and pass only the records the task needs.

Hooks and rules as hard stops

Skill 7.2Which to use for what.

  • Deny rules (Read(./.env), Bash(rm -rf *)) are simple, declarative and visible in settings. Use them for tools, paths and command patterns.
  • A PreToolUse hook can inspect the full input and apply logic, such as SQL content, a refund amount against a limit, or a path outside the project. Its reason tells Claude what to do instead, so the agent redirects rather than retrying.
  • Approval (the can_use_tool callback, or an ask rule) puts a person in the loop for writes that are legitimate but consequential.
  • In Claude Code, the same layers exist as permissions.deny in settings and hooks in settings.json or a plugin. Managed settings can enforce them across an organisation.

The OS sandbox

Skill 7.2An operating-system boundary around shell commands.

  • What it covers: Claude Code's sandbox puts Bash (and PowerShell and Monitor commands, and every process they start) inside an OS-enforced boundary: Seatbelt on macOS, bubblewrap on Linux and WSL2. Native Windows isn't supported, and commands there run unsandboxed.
  • Filesystem: writes are limited to the working directory, added directories and temp. Reads cover the machine except denied paths, which by default still includes credential files, so add read denials for those.
  • Network: commands have no direct route out. A proxy checks every hostname against the allowed and denied domains, and the allowed list starts empty.
  • Why it's the bottom layer: it holds whatever command the model chose, even when an allowed command does more than its name suggests.
  • What it doesn't cover: Read, Edit, WebFetch, hooks and MCP servers run outside it. Those are governed by permission rules, which merge with the sandbox's paths and domains.
  • Turning it on: /sandbox or sandbox.enabled. Managed settings can require it, with failIfUnavailable and allowUnsandboxedCommands: false so nothing slips out.

Key takeaways

  • Assume prompt-level defences have failed; the guardrails that matter don't consult the model.
  • Layer them: least-privilege tools and credentials, deny rules, a PreToolUse hook (on_failure="block"), approval for writes, the OS sandbox. Each should stop the action alone.
  • Order of checks: hooks, deny, ask, mode, allow, canUseTool. A hook deny holds even in bypassPermissions; a hook allow doesn't override deny or ask rules.
  • The strongest control sits where the action happens: a read-only role can't drop a table, whatever regex a statement slips past.
  • The sandbox confines Bash's filesystem and network at the OS level (not on native Windows); file and web tools, hooks and MCP servers are governed by permission rules instead.
