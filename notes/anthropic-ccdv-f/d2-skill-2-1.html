2.1: Understanding Requirements

Before writing any code, a developer turns "we want Claude to help with returns" into concrete requirements: what the feature must do, how fast, how cheaply and how reliably, where data may go, and how everyone will know it works.

Overview

Skill 2.1

Understanding Requirements (3.4% of the exam): "Functional and infrastructure requirements based on business requirements and solution architecture."

The exam guide gives only that one line. This page takes it to mean what a developer needs to pin down before building a Claude feature: the functional requirements (what it does), the non-functional ones (quality, latency, cost, availability, security), the infrastructure ones (platform, limits, data handling, environments), and measurable success criteria that tie them together. The guide describes its candidates as working "at the intersection of business requirements and technical implementation", which is exactly this skill.

Sources: Anthropic's documentation on defining success criteria, the customer support use-case guide, choosing a model, rate limits, errors, data retention and residency, workspaces and the platform pages, plus "Building effective agents", checked on 8 November 2026 and paraphrased. The shop's requirements below are illustrative.

Running example. The outdoor-gear shop wants a returns assistant on its website: the business goal is to cut the returns desk's workload while keeping decisions consistent with the 60-day returns policy.

From business need to requirements

Skill 2.1Breaking a goal into requirements a developer can build and test.

Anthropic's customer support guide suggests four steps before building, and they generalize well:

  1. Decide whether Claude fitsGood signs include many repetitive requests, the need to pull information together quickly, round-the-clock availability, sudden peaks, and a consistent brand voice.
  2. Describe the ideal interactionWrite out how a good conversation should go, step by step. The guide says this outline is what determines the technical requirements.
  3. Split it into distinct tasksEach task (answer a policy question, look up an order, decide eligibility, hand off to a person) can then be prompted and evaluated on its own.
  4. Agree success criteriaWith the people who own the outcome, here the returns desk (below).

The tasks then point to architecture: questions about the policy need the policy document in context or retrieval; order lookups need a tool that calls the order system; creating a return needs a tool with a confirmation step; staying on topic needs guardrails in the prompt and possibly a check on the output.

Three kinds of requirement

  • Functional: what the feature must do. "Look up an order by number and email, and never invent order details." "Hand off to a person for damaged-on-arrival claims or refunds over US$300."
  • Non-functional: how well it must do it. Latency (time to the first streamed words, time to a full answer), throughput at peak, cost per conversation, availability and behaviour when the API is busy, security and privacy.
  • Infrastructure: what it runs on and under which constraints. Which Claude platform, which model and API version, rate and spend limits, separate development and production environments, how keys are managed, data retention and where processing happens.

Success criteria

Skill 2.1Turning "it should work well" into measurable targets.

Anthropic's guidance is to define success criteria first, then build evaluations that measure against them. Good criteria are:

  • Specific: "accurate eligibility decisions", not "good performance".
  • Measurable: a number or a well-defined scale. Qualitative scores are fine if applied consistently alongside numbers.
  • Achievable: based on benchmarks, earlier experiments or expert knowledge, and within what current models can do.
  • Relevant: tied to the application's purpose; citation accuracy matters more in a medical tool than in a casual chatbot.

Even vague goals can be quantified. The docs' example turns "safe outputs" into "fewer than 0.1% of outputs out of 10,000 trials flagged for toxicity". Most applications need several criteria at once, and Anthropic lists latency and price among them, next to accuracy, consistency, tone and privacy. The customer support guide's example targets include escalation accuracy of at least 95%, deflection of 70 to 80% of conversations, and customer satisfaction of at least 4 out of 5.

returns-assistant success criteria (YAML) 
eval_set: 400 real anonymised return chats + 60 edge cases (expired window, worn boots, gift receipts, angry customer, off-topic)
criteria:
  eligibility_decision_accuracy: ">= 97% match with labels from the returns-desk policy expert"   # code-graded exact match
  policy_answer_accuracy: "100% on the 50 policy FAQ questions"                                 # no invented rules
  escalation_accuracy: ">= 95% of cases that need a person are handed off"
  tool_safety: "0 create_return calls without explicit customer confirmation"
  tone: "average >= 4/5 on a friendliness rubric, graded by a different model"
  deflection: "60-70% of return chats finished without a person, measured over 4 weeks"
  latency: "95% of first tokens within 2 s"
  cost: "average <= $0.03 per conversation"
baseline: current human desk (eligibility accuracy 94%, average handle time 6 min)

Each line can be checked: by code (exact match against expert labels), by another model grading against a rubric, or from production metrics. Building and running those evaluations belongs to Domain 4.

Design choices that follow

Skill 2.1How requirements decide the solution's shape and model.

Workflow or agent

"Building effective agents" defines workflows as LLMs and tools orchestrated "through predefined code paths", and agents as LLMs that "dynamically direct their own processes and tool usage". Its advice is to find the simplest solution that meets the requirements, because "agentic systems often trade latency and cost for better task performance". The returns assistant's steps are predictable (check the order, apply the policy, confirm, create the return), so a workflow with tools fits better than an open-ended agent. For long-running or asynchronous work, Anthropic also offers Claude Managed Agents, a hosted agent harness (in beta since April 2026), as an alternative to building your own loop on the Messages API.

Model and effort

Anthropic's model-selection guide weighs capability, speed and cost, and adds a fourth lever, effort, which it calls "often a better lever than switching models". It describes two ways to start: efficiency-first (start with the fastest, cheapest model, Claude Haiku 5.5, and move up only where evaluations show a gap) and capability-first (start with Claude Opus 5.5, tune the prompts, then lower effort or move down a tier). Its default advice is to start with Opus 5.5 for most workloads. The cost and latency requirements decide which approach suits; the decision itself is covered in Domain 5.

Capacity and cost

Skill 2.1Checking throughput and availability requirements against the API's limits.

  • Two kinds of limit. Spend limits cap monthly cost; rate limits cap requests per minute and input and output tokens per minute, per model class. Both apply at organization level, and you can set lower limits per workspace. The usage tiers are Start, Build and Scale (consolidated in June 2026), plus custom arrangements.
  • Caching raises throughput. Only uncached input tokens and cache writes count toward the input-tokens-per-minute limit, so caching a long system prompt (the returns policy) lets the same tier serve far more traffic. Output limits count tokens actually generated, not max_tokens.
  • Ramp up gradually. A sudden traffic jump can trigger "acceleration" rate limits, so a holiday-sale peak needs planning, not just a higher tier.
  • Plan for errors. The API returns 429 when you're rate limited and 529 when it's overloaded across all customers. The SDKs retry twice by default with backoff; the requirement should say what users see after that (a friendly message and a handoff to a person). Keep the request-id of every call for support.
  • Know the spend cap. When an organization hits its tier's monthly spend cap, the 429 it gets has no retry time, and retries keep failing until the next month. A spend limit you set yourself returns 400 instead.

No more buying capacity. Service tiers are now marked legacy and Priority Tier capacity is no longer sold (existing contracts run to the end), so a new availability requirement can't rely on buying Priority Tier; it isn't offered on the Claude 5 models either. Plan for retries, fallbacks and graceful degradation instead, and contact Anthropic's sales team if you need guaranteed capacity.

Data handling

Skill 2.1Retention, residency and compliance as requirements.

  • Retention. On the commercial API, inputs and outputs are deleted within 30 days by default, with exceptions for features you control (such as uploaded files), usage-policy enforcement and legal requirements. Data isn't used for training without permission.
  • Zero data retention (ZDR). An agreement made with Anthropic's sales team that applies to a whole organization, not a per-request flag. It covers eligible features of the Messages and token-counting APIs; stateful features, the Console and Managed Agents are outside it, and ZDR organizations can't call the API from a browser. Some models, including Fable 5.1, require 30-day retention and so aren't available under ZDR without explicit approval.
  • Health data. For protected health information, use HIPAA readiness with a signed business associate agreement rather than ZDR.
  • Residency. The inference_geo request parameter is "global" (default) or "us"; US-only processing costs 1.1 times as much and needs a Claude 4.6 or later model. There's no EU option on Anthropic's own API. Where data is stored is set per workspace when it's created, and can't be changed.
  • Environments and keys. Workspaces separate projects, environments or teams under one bill, each with its own API keys and optional spend and rate limits. Keep keys out of source code and prompts, give them expiry dates, or use Workload Identity Federation (since May 2026) for short-lived tokens instead of static keys.

Choosing a platform

Skill 2.1Where to run Claude, as an infrastructure requirement.

There are six ways to reach Claude, and the choice usually follows from billing, compliance and feature requirements:

  • Claude API (Anthropic): the newest features first; billed by Anthropic.
  • Claude Platform on AWS (since May 2026): the Claude API operated by Anthropic but bought through AWS Marketplace; features usually arrive the same day; no HIPAA readiness.
  • Claude in Amazon Bedrock: run by AWS, with AWS as the data processor; the docs point here for FedRAMP High, IL4 and IL5 or HIPAA needs. Some Claude API features, such as batches and files, aren't available, and AWS sets its own model retirement dates.
  • Claude models on Google Cloud, in two forms: Google-managed (formerly Vertex AI, with its own retirement dates) and Anthropic-managed (since October 2026, following Anthropic's schedule).
  • Claude in Microsoft Foundry (since November 2025): billed through Azure; the model is addressed by deployment name; no batches.

Feature and lifecycle differences. "Use Bedrock" or "use Google Cloud" isn't a neutral choice: some features (batches, files, server tools, managed agents) are missing on some platforms, Bedrock's regional endpoints cost 10% more than its global one, and Bedrock and Google-managed Google Cloud set their own model retirement dates. Check the platform's page for each feature a requirement depends on.

A requirements file

Skill 2.1Writing it all down where the team can review and test it.

returns-assistant requirements (YAML) 
feature: returns-assistant
business_goal: Cut returns-desk workload while keeping decisions consistent with the 60-day returns policy
functional:
  - FR1: Answer returns-policy questions using only the policy document in context, citing the section
  - FR2: Look up an order by order number and email with the get_order tool; never invent order data
  - FR3: Decide eligibility (within 60 days, item condition, non-returnable categories) and explain why
  - FR4: Create a return with the create_return tool only after the customer confirms
  - FR5: Hand off to a person for damaged-on-arrival claims, refunds over $300, or on request
  - FR6: Stay on topic; politely decline unrelated requests
non_functional:
  latency: first streamed token p95 < 2 s; full answer p95 < 8 s       # stream the response
  throughput: 30 conversations/min at peak after holiday sales          # check tier limits; cache the policy prompt
  cost: <= $0.03 average per conversation                              # model + effort choice, prompt caching
  availability: friendly fallback + human handoff after SDK retries on 429/529/5xx
  privacy: no card numbers in prompts; mask emails in logs; keep request-id per call
infrastructure:
  platform: Claude API (the shop already uses it)
  model: claude-sonnet-5-5, pinned by ID; re-test Haiku 5.5 for cost after evaluations
  environments: workspaces returns-dev and returns-prod, separate keys and spend limits
  data: standard 30-day retention confirmed with legal; inference_geo "us" only if legally required

Kept in the repository, a file like this is reviewed with the code, and each line maps to a test, an evaluation or a configuration setting. How the feature moves from plan to production and maintenance is the next skill.

Key takeaways

  • Go from business goal to the ideal interaction, then distinct tasks, then requirements: functional (what), non-functional (latency, throughput, cost, availability, privacy) and infrastructure (platform, model, limits, environments, data).
  • Success criteria must be specific, measurable, achievable and relevant, and usually several at once; latency and cost are criteria too.
  • Choose the simplest design that meets the requirements: a workflow when the steps are predictable, an agent only when flexibility is worth the extra latency and cost.
  • Check throughput against rate and spend limits; caching raises effective throughput; plan for 429 and 529 errors; Priority Tier is no longer sold.
  • Data: 30-day default retention, organization-level ZDR, HIPAA readiness for health data, inference_geo "us" or "global" only, workspaces for separate environments.
  • Platforms differ in features, compliance options and model retirement dates.
