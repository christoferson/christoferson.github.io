Running example. The shop's applications call Claude in several ways: a support assistant that looks up orders with a tool, a review triage job that extracts fields as JSON, a gear advisor that streams long answers, a catalogue tool that reads product photos, a returns assistant with a long, fixed policy prompt, and a nightly job that writes product descriptions.

Requests and responses

Skill 2.1Message structure: what goes in and what comes back.

A request to POST /v1/messages needs model, max_tokens and messages (alternating user and assistant turns). Common optional fields are system, tools, tool_choice, thinking, output_config (effort and the structured output format), stop_sequences and stream. The API is stateless: each request carries the whole conversation, so your application keeps the history and decides what to resend.

The response is a message with a list of content blocks (text, thinking, tool calls), the model, a stop_reason, stop_details (filled in only for refusals) and usage (input and output tokens, cache reads and writes). A content list can mix block types, so code that reads content[0].text breaks as soon as a thinking block or a tool call comes first: filter by type.

The current models are Claude Fable 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5 (claude-fable-5-2, claude-opus-5-5 and so on), all with a 1M-token context window and up to 128,000 output tokens per synchronous call.

Things that stopped working. A prefilled final assistant turn (the old trick for forcing a format) returns an error on Claude 4.6 and later models; use structured outputs instead. Under API version 2026-10-21, sent by the current SDKs, temperature, top_p and top_k are rejected for every model.

Stop reasons

Skill 2.1Reading stop_reason and doing the right thing next.

There are exactly seven values, and each one asks the calling code for something different:

  • end_turn: Claude finished. Use the answer. An empty end_turn right after tool results usually means the follow-up message had extra text next to the tool_result blocks; send only the results.
  • stop_sequence: one of your stop_sequences appeared; the response's stop_sequence field says which.
  • tool_use: run the client tools it asked for and send one tool_result per call, with nothing else in that user message.
  • pause_turn: a server tool (web search, code execution) reached its step limit, 10 iterations by default. Append the content unchanged as an assistant turn and resend with the same tools and no new user message. It never happens with client tools only.
  • max_tokens: the answer hit your limit and is cut off. If the last block is a tool call, its input is incomplete: retry the original request with a higher max_tokens rather than running it.
  • model_context_window_exceeded: the response filled the context window; treat it like max_tokens.
  • refusal: Claude declined. It arrives with HTTP 200, not as an error, and stop_details.category gives the policy area (for example cyber or reasoning_extraction). The documented recovery is to retry on another model; a field that asks for "step-by-step reasoning" can trigger reasoning_extraction, so ask for a short explanation instead.
run_turn.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()

TOOLS = [{
    "name": "get_order_status",
    "description": "Look up the shipping status of one order by its order number, such as A1042.",
    "input_schema": {
        "type": "object",
        "properties": {"order_id": {"type": "string"}},
        "required": ["order_id"],
        "additionalProperties": False,
    },
    "strict": True,  # tool input always matches the schema
}]


def get_order_status(order_id: str) -> str:
    return f"Order {order_id}: shipped, arriving Thursday."


HANDLERS = {"get_order_status": get_order_status}


def text_of(response) -> str:
    return "".join(b.text for b in response.content if b.type == "text")


def run_turn(messages: list, max_rounds: int = 8) -> str:
    for _ in range(max_rounds):
        response = client.messages.create(
            model="claude-opus-5-5", max_tokens=4096, tools=TOOLS, messages=messages,
        )
        match response.stop_reason:
            case "end_turn" | "stop_sequence":
                return text_of(response)
            case "tool_use":
                messages.append({"role": "assistant", "content": response.content})
                results = [
                    {"type": "tool_result", "tool_use_id": b.id, "content": HANDLERS[b.name](**b.input)}
                    for b in response.content if b.type == "tool_use"
                ]
                messages.append({"role": "user", "content": results})  # only tool_result blocks
            case "pause_turn":
                # A server tool hit its step limit: send the content back, no new user message.
                messages.append({"role": "assistant", "content": response.content})
            case "max_tokens" | "model_context_window_exceeded":
                if response.content and response.content[-1].type == "tool_use":
                    raise RuntimeError("tool call cut off: retry with a higher max_tokens")
                return text_of(response) + "\n[answer truncated]"
            case "refusal":
                # HTTP 200, not an exception; stop_details says why.
                details = response.stop_details
                raise RuntimeError(f"refused: {details.category if details else 'unknown'}")
            case other:
                raise RuntimeError(f"unhandled stop_reason: {other}")  # new values can appear
    raise RuntimeError("too many tool rounds")


if __name__ == "__main__":
    print(run_turn([{"role": "user", "content": "Where is order A1042?"}]))

Code for the unknown case. Loops that only check for tool_use and otherwise read the text treat a refusal or a truncated answer as a success. Match every value, and fail loudly on one you don't recognise, since the list has grown before.

Tools and tool_choice

Skill 2.1Where tool code runs, and how much control you have over calls.

  • Client tools (your own, with a JSON schema, plus Anthropic-defined ones such as bash and the text editor): Claude stops with tool_use, your code runs the tool and returns a tool_result, as above.
  • Server tools (web search, web fetch, code execution, tool search, the MCP connector): Anthropic runs them inside the same request and returns the results in the response; long runs end in pause_turn.
  • tool_choice is auto (the default with tools), any (must call some tool), tool (must call the named one) or none. On Fable 5.2, Opus 5.5, Sonnet 5.5 and Fable 5.1 (and Mythos 5.2 and 5.1), any and tool return a 400 error. Use auto with a clear instruction and "strict": true on the tool, or structured outputs when you need fixed JSON. Where forcing is allowed, a forced call skips thinking.

Tool definitions are sent as input tokens on every call, and changing tool_choice invalidates the cached message part of a prompt.

Structured outputs

Skill 2.1Getting JSON that matches a schema.

There are two forms, and they can be combined in one request:

  • JSON outputs: output_config.format set to {"type": "json_schema", "schema": ...}. Claude's reply, in the text block, is constrained to the schema.
  • Strict tool use: "strict": true on a tool definition, so tool names and inputs always match their schema.
review_fields.py (Python, anthropic SDK and Pydantic) 
from typing import Literal

import anthropic
from pydantic import BaseModel


class ReviewFields(BaseModel):
    sku: str
    rating: int  # 1 to 5; the schema can't hold minimum/maximum, so check in code
    sentiment: Literal["positive", "mixed", "negative"]
    issues: list[str]
    wants_reply: bool


client = anthropic.Anthropic()

review = (
    "The two-person tent (sku-tent-2p) kept us dry for three nights, "
    "but one door zip jammed on day two. 4/5. Can it be repaired?"
)

response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system="Extract review fields for the shop's support team.",
    messages=[{"role": "user", "content": review}],
    # The JSON comes back as the text block, constrained to this schema.
    # transform_schema() adds additionalProperties: false and drops unsupported keywords.
    output_config={"format": {"type": "json_schema", "schema": anthropic.transform_schema(ReviewFields)}},
)

# Refusals and max_tokens cut-offs are the cases where the text can break the schema.
if response.stop_reason in ("refusal", "max_tokens"):
    raise RuntimeError(f"no usable fields: {response.stop_reason}")

text = "".join(b.text for b in response.content if b.type == "text")
fields = ReviewFields.model_validate_json(text)  # still validate before use
if not 1 <= fields.rating <= 5:
    raise ValueError(f"rating out of range: {fields.rating}")
print(fields.sku, fields.rating, fields.sentiment, fields.issues, fields.wants_reply)
  • Schema limits. Objects need additionalProperties: false. Numeric ranges, string lengths, oneOf, not and recursive schemas aren't supported and return 400; the SDK helpers strip such constraints, move them into the field description and validate the reply against your original model. Required properties come out first, then optional ones.
  • When the output can still break the schema: a refusal and a max_tokens cut-off. Enum values may also differ in capitalisation, so compare them case-insensitively.
  • The SDK's messages.parse() (with output_format=YourModel and parsed_output) is the shortcut, but it validates as it parses: a truncated reply raises a Pydantic ValidationError before your code sees the stop reason. The example above sends the format itself so it can check first.
  • Costs and limits. The first request with a new schema is slower while a grammar is compiled; it's then cached for 24 hours. Changing the format invalidates the prompt cache. Structured outputs can't be combined with citations (400) or prefill.

Renamed parameter. The beta output_format request field moved to output_config.format; the old field now works only with the structured-outputs-2025-11-13 beta header and returns 400 without it.

Streaming

Skill 2.1Receiving a response as it's generated.

With "stream": true, the API sends server-sent events in a fixed order: message_start; then, for each content block, content_block_start, one or more content_block_delta events and content_block_stop; then message_delta (carrying the stop_reason and cumulative usage); and finally message_stop. ping events can appear anywhere. Deltas come in types such as text_delta, input_json_delta (tool input as partial JSON) and thinking_delta; new event types may be added, so ignore ones you don't recognise. What to do when a stream fails part-way is in skill 2.4.

gear_advisor.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

# A long answer, so stream it: words reach the customer as they are generated.
# With max_tokens above about 21,333 the Python SDK also refuses a non-streaming call.
with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=64000,
    system="You are the gear advisor for an outdoor-gear shop. Be practical and brief.",
    messages=[{"role": "user", "content": "I'm hiking three days in late autumn hills. What should I pack?"}],
) as stream:
    for text in stream.text_stream:  # only the text deltas, in order
        print(text, end="", flush=True)
    final = stream.get_final_message()  # the complete Message, same shape as messages.create()

print()
print("stop_reason:", final.stop_reason)  # end_turn, max_tokens, refusal, ...
if final.stop_reason == "max_tokens":
    print("Answer was cut off: raise max_tokens or ask Claude to continue.")

"Streaming is required" is an SDK rule. The API itself accepts large non-streaming requests. The SDKs refuse non-streaming calls they estimate could run past 10 minutes; in the Python SDK that means max_tokens above 21,333. Streaming also improves perceived latency, since the first words arrive sooner.

Images and PDFs

Skill 2.1Sending images and documents.

An image block has a source that is base64 data with a media type, a URL, or a file_id from the Files API. Supported formats are JPEG, PNG, GIF (first frame only) and WebP. Put the image before the question about it. Images can be up to 8,000 by 8,000 pixels and 10 MB each (base64, on the Claude API); with more than 20 images in a request, a stricter size applies. Tokens are counted in 28-by-28-pixel patches, so a 1,000 by 1,000 image costs about 1,296 tokens; Claude 4.7 and later models also have a high-resolution tier of up to 4,784 tokens per image.

describe_photo.py (Python, anthropic SDK) 
import base64
from pathlib import Path

import anthropic

client = anthropic.Anthropic()

# Product photo from the shop's catalogue (JPEG, PNG, GIF or WebP).
photo_b64 = base64.standard_b64encode(Path("tent-photo.jpg").read_bytes()).decode("utf-8")

message = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    messages=[{
        "role": "user",
        "content": [
            # Image first, then the question about it.
            {"type": "image", "source": {"type": "base64", "media_type": "image/jpeg", "data": photo_b64}},
            {"type": "text", "text": "List the visible features of this tent (doors, vents, guy-out points) and flag anything a customer would ask about."},
        ],
    }],
)

# With thinking on, thinking blocks can come before the text, so filter by type.
print("".join(block.text for block in message.content if block.type == "text"))
print("input tokens (image + text):", message.usage.input_tokens)

PDFs go in a document block (base64, URL or file ID), up to 600 pages: each page is read as both an image and extracted text, roughly 1,500 to 3,000 text tokens per page plus the image. Plain text can be a document too; Word and Excel files must be converted first. Claude won't identify people in images, and is weaker on very small, rotated or low-quality images and on precise counting. Uploading files once and reusing them is covered in skill 2.4.

Thinking and effort

Skill 2.1Controlling how much Claude reasons before answering.

  • Adaptive thinking (thinking: {"type": "adaptive"}) lets Claude decide whether and how much to think. On the Claude 5 models it's the default: it can't be switched off on Fable 5.2 or Opus 5.5; Sonnet 5.5 allows between_tools (no up-front thinking) but rejects disabled, and Haiku 5.5 allows disabled at effort high or below.
  • Effort (output_config.effort: low, medium, high, xhigh, max) guides how much work Claude puts into the whole answer, thinking, text and tool calls alike. The default is high on Fable 5.2 and Sonnet 5.5 and medium on Opus 5.5 and Haiku 5.5. max_tokens stays the hard cap.
  • What comes back: thinking blocks hold a summary (or nothing, with display: "omitted", the default on the Claude 5 models) and an encrypted signature; the raw reasoning is never returned. You pay for the full thinking as output tokens even when it isn't displayed.
  • With tools, pass thinking blocks back complete and unchanged alongside the tool call they came with; modified blocks cause an error. That's why the loop in the stop reasons example appends response.content as it is.

Manual thinking budgets are legacy. thinking: {"type": "enabled", "budget_tokens": N} is deprecated on Claude 4.6 models and rejected from Claude 4.7 on, including all Claude 5 models. Material that teaches budget_tokens as the main control is out of date; use adaptive thinking and effort.

Prompt caching

Skill 2.1Reusing a long, unchanged prefix to cut cost and latency.

returns_assistant.py (Python, anthropic SDK) 
from pathlib import Path

import anthropic

client = anthropic.Anthropic()

# The full returns policy: long, and identical on every request.
RETURNS_POLICY = Path("returns-policy.md").read_text(encoding="utf-8")

SYSTEM = [
    {"type": "text", "text": "You answer customer questions for an outdoor-gear shop."},
    {
        "type": "text",
        "text": RETURNS_POLICY,
        # Breakpoint: cache everything up to and including this block (tools, then system).
        # Default lifetime is 5 minutes; {"type": "ephemeral", "ttl": "1h"} keeps it an hour.
        "cache_control": {"type": "ephemeral"},
    },
]


def ask(question: str) -> None:
    response = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        system=SYSTEM,  # same bytes every time, or the cache misses
        messages=[{"role": "user", "content": question}],  # the part that changes goes last
    )
    u = response.usage
    print(f"cache write: {u.cache_creation_input_tokens}, cache read: {u.cache_read_input_tokens}, uncached: {u.input_tokens}")


ask("Can I return boots I've worn on one hike?")      # first call writes the cache
ask("How long do refunds take for a sleeping bag?")   # within 5 minutes: read from the cache
  • How matching works. The cache key is the exact prefix in the order tools, system, messages, up to a cache_control breakpoint (up to four per request). Any change before the breakpoint (a timestamp, reordered tools) misses. Changing tool definitions invalidates everything; changing tool_choice, images, the output format, or thinking and effort settings invalidates the message part.
  • Automatic caching: one top-level cache_control on the request, and the API places and moves the breakpoint as the conversation grows.
  • Minimum size. Prompts shorter than the minimum are silently not cached: 512 tokens on the Claude 5 models, more on older ones.
  • Reading the result. usage.cache_creation_input_tokens and cache_read_input_tokens show what was written and read; input_tokens counts only what came after the last breakpoint. A cache read of zero on the second call means the prefix changed.
  • Parallel requests: an entry exists only once the first response starts, so send one request before firing many in parallel.

Prices, lifetimes and where to put several breakpoints are in skill 5.3.

Batch or real time

Skill 2.1The Message Batches API, and when to use it instead of normal calls.

nightly_descriptions.py (Python, anthropic SDK) 
import time

import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()

products = {
    "sku-tent-2p": "Two-person tent, 1.9 kg, two doors, aluminium poles",
    "sku-stove-ti": "Titanium canister stove, 73 g, piezo igniter",
    "sku-pack-45l": "45-litre pack, adjustable back length, rain cover included",
}

# One request per product; custom_id ties each result back to its SKU.
batch = client.messages.batches.create(
    requests=[
        Request(
            custom_id=sku,  # 1-64 characters: letters, digits, - and _
            params=MessageCreateParamsNonStreaming(
                model="claude-opus-5-5",
                max_tokens=1024,
                messages=[{"role": "user", "content": f"Write a 60-word shop description for: {spec}"}],
            ),
        )
        for sku, spec in products.items()
    ]
)
print("batch:", batch.id, batch.processing_status)  # in_progress

# Poll. Most batches end within an hour; requests still waiting after 24 hours expire.
while True:
    batch = client.messages.batches.retrieve(batch.id)
    if batch.processing_status == "ended":
        break
    time.sleep(60)

# Results can arrive in any order: match them by custom_id, never by position.
descriptions = {}
for item in client.messages.batches.results(batch.id):
    match item.result.type:
        case "succeeded":
            msg = item.result.message
            descriptions[item.custom_id] = "".join(b.text for b in msg.content if b.type == "text")
        case "errored":
            print(item.custom_id, "error:", item.result.error.error.type)  # e.g. invalid_request_error
        case "expired" | "canceled":
            print(item.custom_id, item.result.type, "- not billed, submit again")

Batches cost half the normal price, accept up to 100,000 requests or 256 MB per batch, and have their own rate limits. Most finish within an hour; anything not done in 24 hours expires. Results stay downloadable for 29 days, come back in any order, and errored, canceled or expired requests aren't billed. Request errors only show up once the batch has ended, so try one request normally first. Streaming and fast mode aren't allowed in batches; structured outputs are.

Choosing: use real-time calls when a person is waiting (chat, the gear advisor) or you need streaming or the lowest latency (fast mode on Opus 5.5 is real-time only). Use batches for large, non-urgent jobs (the nightly descriptions, evaluations, bulk classification) and for very long outputs: on the Claude 5.5 models a batch request can return up to 300,000 output tokens with a beta header, against 128,000 for a normal call. Batches aren't available on every cloud platform and aren't covered by zero data retention (skill 2.2).

Priority Tier is gone. Service tiers are marked legacy and Priority Tier capacity is no longer sold. The real choice is between standard real-time calls, fast mode for latency, and batches for cost.

Key takeaways

  • The Messages API is stateless: send model, max_tokens and the full messages history; read content blocks by type. No prefill on 4.6+; no sampling parameters under API version 2026-10-21.
  • Seven stop reasons, each with its own next step. refusal comes with HTTP 200 and stop_details; pause_turn means resend without a new user turn; a cut-off tool call must be retried, not run.
  • Forced tool_choice returns 400 on Fable 5.2, Opus 5.5 and Sonnet 5.5: use auto plus strict tools, or output_config.format for JSON.
  • Structured outputs guarantee the schema except on refusal and max_tokens; no numeric or length constraints; no citations or prefill alongside.
  • Streaming events: message_start, content block start/delta/stop, message_delta, message_stop, plus ping. Streaming large max_tokens is an SDK requirement, not an API one.
  • Images: base64, URL or file ID, image before text. Adaptive thinking plus effort replace budget_tokens; return thinking blocks unchanged. Caching needs an identical prefix. Batches: 50% off, up to 24 hours, any order, match by custom_id.
