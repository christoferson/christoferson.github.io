Running example. The shop sorts incoming customer emails into categories with Haiku 5.5, and its gear advisor answers long questions with Opus 5.5. The team wants to know how much text fits, how predictable the answers are, and which settings make them faster or cheaper.

Tokens

Skill 5.1The unit models read, write and bill in.

Anthropic's glossary defines a token as the smallest unit a language model works with: a word, part of a word, a character, or a byte. Text is split into tokens before the model sees it, and everything is measured in them: context limits, rate limits and prices.

  • How much text is a token? On models before Claude Opus 4.7, roughly 3.5 English characters. Claude Opus 4.7 and later models (including all the Claude 5 models) use a newer tokenizer that produces about 30% more tokens for the same text; on it, 1M tokens is about 555,000 words, against about 750,000 before. The figure varies by language.
  • Why it matters: moving a prompt to a newer model can raise its token count, and so its cost, even at the same price per token. Recount on the model you plan to use rather than reuse old counts.
  • Counting before you send. The token counting endpoint returns the input token count for a request on a given model. It's free, has its own rate limits, gives an estimate, ignores prompt caching, and can't count requests that use server tools or images and files sent by URL or ID.
count_email.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

email = "Hi, the sole of my left hiking boot started peeling after two weeks. Can I swap the pair?"
request = {
    "system": "You sort customer emails for an outdoor-gear shop.",
    "messages": [{"role": "user", "content": email}],
}

# Count before you send. Token counting is free and uses the tokenizer of the model you name.
for model in ["claude-haiku-5-5", "claude-sonnet-4-6"]:
    count = client.messages.count_tokens(model=model, **request)
    print(f"{model}: {count.input_tokens} input tokens")

# Claude Opus 4.7 and later models use a newer tokenizer: about 30% more tokens for the same text.

Claude Sonnet 4.6 is an older model still available on the previous tokenizer, so counting the same request on both shows the difference.

Context windows

Skill 5.1How much the model can consider at once, and what counts.

The context window is everything the model can refer to while generating a response, including the response itself: its working memory for that request, not what it learned in training. It holds the system prompt, every message (with tool results, images and documents), the tool definitions, and the output, thinking included. Cached tokens count too; caching changes the price, not the size.

  • Sizes. Fable 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5, and several older models, have a 1M-token window by default at standard prices, except that Haiku 5.5 charges more for prompts over 100,000 tokens. A request can generate up to 128,000 output tokens and include up to 600 images or PDF pages. Some older models have 200,000 tokens.
  • Stateless, and growing. Each turn resends the whole history. On current models, earlier thinking blocks you pass back stay in the context and count as input; older models had them stripped automatically.
  • Overflow. If the input alone is too long, the request fails with 400 "prompt is too long". If the input fits but input plus max_tokens doesn't, Claude 4.5 and later models accept it and stop with model_context_window_exceeded if they run out of room.
  • Bigger isn't automatically better. The docs describe context rot: accuracy and recall fall as the token count grows, so what you put in matters as much as how much fits.

The Models API reports each model's limits and capabilities, so code can predict an outcome before sending a request:

plan_request.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()


def plan(model: str, system: str, messages: list, max_tokens: int) -> dict:
    """Predict how a request will behave before sending it."""
    info = client.models.retrieve(model)  # limits and capabilities, per model
    used = client.messages.count_tokens(model=model, system=system, messages=messages).input_tokens

    if used > info.max_input_tokens:
        outcome = "rejected: 400 prompt is too long"
    elif used + max_tokens > info.max_input_tokens:
        outcome = "accepted, but may stop with model_context_window_exceeded"
    else:
        outcome = "fits"

    # The lowest-thinking setting this model accepts: some reject "disabled" with a 400.
    types = info.capabilities.thinking.types
    if types.disabled.supported:
        thinking = {"type": "disabled"}
    elif types.between_tools.supported:
        thinking = {"type": "between_tools"}
    else:
        thinking = {"type": "adaptive"}  # always on; steer it with effort instead

    return {"input_tokens": used, "outcome": outcome, "max_tokens_cap": info.max_tokens,
            "lowest_thinking": thinking, "low_effort": info.capabilities.effort.low.supported}


if __name__ == "__main__":
    request = {
        "system": "You sort customer emails for an outdoor-gear shop.",
        "messages": [{"role": "user", "content": "Where is order 10482?"}],
    }
    for model in ["claude-haiku-5-5", "claude-opus-5-5"]:
        print(model, plan(model, max_tokens=1024, **request))

Context awareness isn't on every model. Sonnet 5, Sonnet 4.6, Sonnet 4.5 and Haiku 4.5 are told their remaining token budget automatically through injected tags. Opus 4.7 and later, Sonnet 5.5, Haiku 5.5 and the Fable and Mythos models don't get these tags; give them an explicit budget with task budgets (a beta) instead.

Next-token generation and variation

Skill 5.1How text is produced, and why answers vary between runs.

The glossary describes Claude's underlying model as autoregressive: pretrained to predict the next word from the text before it, then fine-tuned (including with reinforcement learning from human feedback) to follow instructions. In general terms, at each step the model produces a probability for every possible next token, one token is sampled from those probabilities and added to the text, and the loop repeats until a stop condition such as the end of the turn or max_tokens. That's why responses stream token by token, and why max_tokens can cut an answer mid-sentence.

Sampling settings. Temperature controls how random that choice is: higher gives more varied output, lower sticks to the most likely wording. Top-p and top-k limit which tokens can be chosen at all. Even at temperature 0, the glossary notes, results were never fully deterministic: the same input can give different outputs across calls, on Anthropic's service and on cloud providers alike.

Sampling can no longer be tuned. Since Claude Opus 4.7 (April 2026), sending a non-default temperature, top_p or top_k returns an error, and API version 2026-10-21 removed the three parameters for every model; the current SDKs don't have them. The migration guide says plainly that no other setting replaces them. Treat sampling as the explanation for why outputs vary, not as a control.

Designing for variation. What still makes output consistent: structured outputs with a JSON schema (which guarantees the shape, not identical content), a precisely specified format, examples in the prompt, grounding in retrieved information, validation and retries in code, and evaluating across many runs rather than one. Effort changes how much work Claude does, not how random it is, and a prefilled assistant reply (an old consistency trick) is rejected on Claude 4.6 and later models.

Thinking and effort

Skill 5.1Reasoning before answering, and how much work to put in.

  • Thinking lets Claude reason in separate thinking blocks before answering: restating the problem, trying approaches, checking results. Thinking tokens are billed as output (even when not shown) and count toward max_tokens and the context window.
  • Adaptive thinking is the current mode: Claude decides for each request whether to think and how much, and may not think at all on a simple question, so don't assume every response starts with a thinking block. Thinking use therefore varies from request to request.
  • Turning it down. Fable 5.2 and Opus 5.5 always think, and reject {"type": "disabled"} with a 400. Sonnet 5.5 rejects disabled but accepts between_tools (no up-front thinking); Haiku 5.5 accepts disabled. With either of those, effort can't be xhigh or max, and can't change mid-conversation.
  • Extended thinking, a fixed budget set with budget_tokens, is legacy: it's rejected on Claude 4.7 and later models. Replace a budget with an effort level.
  • Effort (low, medium, high, xhigh, max) guides how much work goes into the whole answer, including text and tool calls, so it works without thinking too. It's guidance, not a cap (max_tokens is the cap). The default is high on Fable 5.2 and Sonnet 5.5 and medium on Opus 5.5 and Haiku 5.5; Anthropic suggests low for simple, high-volume tasks such as classification.

On the newest top models, a prompt asking Claude to write out its reasoning in tags may be declined (a reasoning_extraction refusal); rely on built-in thinking and ask for a short explanation instead.

Fast mode

Skill 5.1Paying more for faster output from the same model.

Fast mode runs the same model on a faster serving setup: up to 2.5 times more output tokens per second, with no change in quality. It doesn't shorten the time to the first token, so the gain shows most on long, streamed answers. Turn it on with speed: "fast"; usage.speed reports "fast" or "standard".

  • Models and prices: generally available on Fable 5.2 (US$16 and $80 per million input and output tokens), Mythos 5.2 and Opus 5.5 ($8 and $40, double the standard rate). It's a research preview on Opus 5 and deprecated on Opus 4.8, where it stops working on 30 November 2026. Caching and data-residency multipliers apply on top.
  • Limits: its own rate limit, with anthropic-fast-* headers. When fast capacity runs out the request fails (429 or 529); it isn't silently slowed down. Not available with batches.
  • Falling back means resending without speed. The two speeds don't share cached prefixes, so the fallback misses the prompt cache.
fast_advisor.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()


def advise(question: str) -> str:
    params = {
        "model": "claude-opus-5-5",
        "max_tokens": 4096,
        "output_config": {"effort": "medium"},
        "messages": [{"role": "user", "content": question}],
    }
    try:
        # Fail fast instead of waiting out fast mode's own rate limit.
        response = client.with_options(max_retries=0).messages.create(speed="fast", **params)
    except (anthropic.RateLimitError, anthropic.OverloadedError):
        # No fast capacity (429 or 529): same model at standard speed.
        # Speeds don't share cached prefixes, so this call misses the prompt cache.
        response = client.messages.create(**params)
    print("speed used:", response.usage.speed)  # "fast" or "standard"
    return "".join(b.text for b in response.content if b.type == "text")


if __name__ == "__main__":
    print(advise("Compare a 1.2 kg and a 1.9 kg two-person tent for a five-day trek."))

Contrast the options: fast mode spends more for speed on the same model; a smaller model or lower effort saves money instead (skill 5.2).

Explaining what you observe

Skill 5.1Symptoms, the mechanism behind them, and the control that changes them.

  • The same prompt reports about 30% more input tokens after moving from Sonnet 4.6 to Sonnet 5.5. The newer tokenizer produces more tokens for the same text. Recount before budgeting; compare cost per request, not just the price per token (Sonnet 5.5 is cheaper per token, but counts more of them).
  • Two runs of the same classification give different labels. Sampling is random and can't be turned off. Constrain the output (an enum in a schema), add examples, and evaluate across many runs.
  • Code that sends temperature: 0 started failing after an SDK upgrade. API version 2026-10-21 rejects sampling parameters. Remove them; nothing replaces them.
  • Some responses have a thinking block and some don't. Adaptive thinking decides per request. Read blocks by type, and raise effort if hard requests aren't getting enough reasoning.
  • Answers end mid-sentence. stop_reason is max_tokens: thinking and text share the cap. Raise max_tokens or lower effort.
  • Turning thinking off on Opus 5.5 returns 400. It can't be disabled there. Use effort to make it lighter, or a model that allows disabled or between_tools.
  • A long conversation's input tokens keep climbing faster than its visible text. Earlier thinking blocks stay in context on current models. Clear them with context editing or compact the conversation.
  • Fast mode made the answer finish sooner, but the first word appeared no earlier. Fast mode raises output speed, not time to first token.

Key takeaways

  • Tokens are the unit of limits and prices. Claude 4.7 and later models produce about 30% more tokens for the same text; recount on the target model. Token counting is free and an estimate.
  • The context window includes output, thinking, tool definitions and cached tokens; 1M tokens on current models, 128,000 output. Input too long fails with 400; input plus max_tokens too long may stop with model_context_window_exceeded. The Models API reports limits and capabilities.
  • Models sample one token at a time, so outputs vary and were never fully deterministic. Sampling parameters are gone; get consistency from schemas, formats, examples and validation.
  • Adaptive thinking decides per request; it can't be disabled on Fable 5.2 or Opus 5.5; budget_tokens is rejected on 4.7+. Effort steers all output: default high on Fable 5.2 and Sonnet 5.5, medium on Opus 5.5 and Haiku 5.5.
  • Fast mode: same model, up to 2.5 times faster output, on Fable 5.2, Mythos 5.2 and Opus 5.5 at premium prices; fails with 429 or 529 when capacity is out; no batches; falling back misses the cache.
