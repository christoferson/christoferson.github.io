Running example. The shop sorts incoming customer emails into four categories before they reach a person, and wants to know how much text it can send, how predictable the answers are, and whether examples help.

Tokens

Skill 5.1The unit models read, write and bill in.

Anthropic's glossary defines a token as the smallest unit a language model works with: a word, part of a word, a character, or a byte. Text is split into tokens before the model sees it; larger tokens make processing more efficient, smaller ones let the model handle rare words. Everything is measured in tokens: context limits, rate limits and prices.

  • How much text is a token? On models before Claude Opus 4.7, roughly 3.5 English characters. Claude Opus 4.7 and later models (including all the Claude 5 models) use a newer tokenizer that produces about 30% more tokens for the same text; on it, 1M tokens is about 555,000 words, against about 750,000 before. The figure varies by language.
  • Why it matters: moving a prompt to a newer model can raise its token count, and so its cost, even at the same price per token. The docs say to recount on the model you plan to use rather than reuse old counts.
  • Counting before you send. The token counting endpoint returns the input token count for a request on a given model. It's free, has its own rate limits, gives an estimate, ignores prompt caching, and can't count requests that use server tools or images and files sent by URL or ID.
count_email.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

email = "Hi, the sole of my left hiking boot started peeling after two weeks. Can I swap the pair?"
request = {
    "system": "You sort customer emails for an outdoor-gear shop.",
    "messages": [{"role": "user", "content": email}],
}

# Count before you send. Token counting is free and uses the tokenizer of the model you name.
for model in ["claude-haiku-5-5", "claude-sonnet-4-6"]:
    count = client.messages.count_tokens(model=model, **request)
    print(f"{model}: {count.input_tokens} input tokens")

# Claude Opus 4.7 and later models use a newer tokenizer: about 30% more tokens for the same text.

Claude Sonnet 4.6 is an older model still available on the previous tokenizer, so counting the same request on both shows the difference.

Context windows

Skill 5.1How much the model can consider at once, and what counts.

The context window is everything the model can refer to while generating a response, including the response itself: its working memory for that request, not what it learned in training. It holds the system prompt, every message (with tool results, images and documents), the tool definitions, and the output, thinking included. Cached tokens count too; caching changes the price, not the size.

  • Sizes. All current models (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5) have a 1M-token window by default, at standard prices, except that Haiku 5.5 charges more for prompts over 100,000 tokens. Maximum output is 128,000 tokens per request. Some older models have 200,000.
  • Stateless. Each turn of a conversation resends the whole history, so the context grows with every exchange; the API doesn't drop old turns for you.
  • Overflow. If the input alone is too long, the request fails ("prompt is too long"). If the input fits but input plus max_tokens doesn't, newer models accept it and stop with model_context_window_exceeded if they run out of room.
  • Bigger isn't automatically better. The docs describe context rot: accuracy and recall fall as the token count grows, so what you put in matters as much as how much fits.

Context awareness isn't on every model. Some older models (Sonnet 5, Sonnet 4.6 and 4.5, Haiku 4.5) are told their remaining token budget automatically through injected tags. The newest models, including Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1, don't get these tags; they use task budgets (a beta) instead.

Next-token generation and variation

Skill 5.1How text is produced, and why answers vary between runs.

The glossary describes Claude's underlying model as autoregressive: pretrained to predict the next word from the text before it, then fine-tuned (including with reinforcement learning from human feedback) to follow instructions. In general terms, at each step the model produces a probability for every possible next token, one token is sampled from those probabilities and added to the text, and the loop repeats until a stop condition such as the end of the turn or max_tokens. That's why responses stream token by token, and why max_tokens can cut an answer mid-sentence.

Sampling settings. Temperature controls how random that choice is: higher gives more varied output, lower sticks to the most likely wording. Top-p and top-k limit which tokens can be chosen at all. Even at temperature 0, the glossary notes, results were never fully deterministic: the same input can give different outputs across calls, on Anthropic's service and on cloud providers alike.

Sampling can no longer be tuned. Since Claude Opus 4.7 (April 2026), sending a non-default temperature, top_p or top_k returns an error, and API version 2026-10-21 removed the three parameters for every model; the current SDKs don't have them. The migration guide says plainly that no other setting replaces them. Treat sampling as the explanation for why outputs vary, not as a control.

Designing for variation. What still makes output consistent: structured outputs with a JSON schema (which guarantees the shape, not identical content), a precisely specified format, examples in the prompt, grounding in retrieved information, validation and retries in code, and evaluating across many runs rather than one. Some teams also run a prompt several times and compare answers to spot unreliable ones. Effort changes how much work Claude does, not how random it is, and a prefilled assistant reply (an old consistency trick) is rejected on Claude 4.6 and later models.

Fast mode

Skill 5.1Paying more for faster output from the same model.

Fast mode runs the same model on a faster serving setup: up to 2.5 times more output tokens per second, with unchanged quality. It doesn't shorten the time to the first token, so the benefit shows most on long, streamed answers. You turn it on with speed: "fast" on a request, and usage.speed reports which speed was used.

  • Price and availability: double the standard rate; on Claude Opus 5.5 (generally available since 15 October 2026), US$8 per million input tokens and US$40 per million output tokens instead of $4 and $20. Older Opus models only had it as a research preview.
  • Limits: its own rate limits; not available with batches; a fallback to standard speed misses the prompt cache, because the two speeds don't share cached prefixes.
  • Contrast: fast mode spends more for speed on the same model; a smaller model or lower effort saves money instead.

Thinking and effort

Skill 5.1Reasoning before answering, and how much work to put in.

  • Thinking lets Claude reason in separate thinking blocks before answering: restating the problem, trying approaches, checking results. It helps with maths, code, analysis and long agent tasks. Thinking tokens are billed as output (even when not shown) and count toward max_tokens.
  • Adaptive thinking is the current mode: Claude decides for each request whether to think and how much, and may not think at all on a simple question, so don't assume every response starts with a thinking block. It's on by default on the Claude 5 models, and can't be turned off on Opus 5.5 or Fable 5.1.
  • Extended thinking, a fixed budget set with budget_tokens, is now labelled legacy. It's rejected on Claude 4.7 and later models; replace a budget with an effort level.
  • Effort (low, medium, high, xhigh, max) guides how much work goes into the whole answer, including text and tool calls, so it works without thinking too. It's guidance, not a cap (max_tokens is the cap). The default is high on most models and medium on Opus 5.5 and Haiku 5.5. Anthropic suggests low for simple, high-volume tasks such as classification.

The exam guide lists extended and adaptive thinking side by side, which matches how the docs use the terms today: "extended thinking" means only the old manual-budget mode. On the newest top models, a prompt asking Claude to write out its reasoning in tags "may be declined"; rely on built-in thinking instead.

Zero-shot, one-shot and multishot

Skill 5.1Steering output with examples.

In general usage, a zero-shot prompt gives instructions only; a one-shot (single-shot) prompt adds one example; a few-shot or, in Anthropic's word, multishot prompt adds several. Anthropic's prompting guide calls examples one of the most reliable ways to steer format, tone and structure, and gives three rules: make them relevant to the real task, diverse enough to cover edge cases without creating patterns Claude might copy, and structured in <example> tags (inside <examples>). It recommends three to five examples. A single example tends to be copied too literally (its length, wording or label), which is the main weakness of one-shot prompts.

classify_email.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()

LABELS = "order_status, return_or_exchange, product_question, complaint"

# Zero-shot: instructions only, no examples.
ZERO_SHOT = f"""Classify the customer email into exactly one of: {LABELS}.
Reply with the label only."""

# Multishot: the same instructions plus varied examples in <example> tags.
# The gloves example settles an edge case: an angry email that asks for a refund is a return.
FEW_SHOT = f"""Classify the customer email into exactly one of: {LABELS}.
Reply with the label only.

<examples>
<example>
<email>Where is my order 10482? The tracking page hasn't changed since Monday.</email>
<label>order_status</label>
</example>
<example>
<email>These gloves fell apart on the first trip. Poor quality. I want a refund.</email>
<label>return_or_exchange</label>
</example>
<example>
<email>Is the 45-litre pack's rain cover big enough for a sleeping mat strapped on top?</email>
<label>product_question</label>
</example>
<example>
<email>Third time I've called about a broken stove and nobody has called me back.</email>
<label>complaint</label>
</example>
</examples>"""


def classify(system_prompt: str, email: str) -> str:
    response = client.messages.create(
        model="claude-haiku-5-5",           # fast, low-cost model for high-volume classification
        max_tokens=1024,
        output_config={"effort": "low"},    # simple task: less work, faster and cheaper
        system=system_prompt,
        messages=[{"role": "user", "content": f"<email>{email}</email>"}],
    )
    # Thinking can be on by default, so pick the text block by type, not by position.
    return "".join(b.text for b in response.content if b.type == "text").strip()


email = "My boots leak after a month. I want my money back, and I'm not impressed."
print("zero-shot:", classify(ZERO_SHOT, email))
print("few-shot: ", classify(FEW_SHOT, email))

The test email is deliberately ambiguous: angry and asking for a refund. The examples teach the shop's rule that this counts as a return, which a zero-shot prompt leaves to chance. Examples cost input tokens on every request, which prompt caching offsets; and for guaranteed label values, structured outputs with an enum schema are the next step.

Key takeaways

  • Tokens are the unit of limits and prices. Claude 4.7 and later models produce about 30% more tokens for the same text; recount on the target model. Token counting is free and an estimate.
  • The context window includes the output and thinking, tool definitions and cached tokens; 1M tokens on current models, 128,000 output; input too long fails, input plus max_tokens too long may stop with model_context_window_exceeded.
  • Models generate one sampled token at a time, so outputs vary, and were never fully deterministic. Sampling parameters are gone (rejected since Opus 4.7, removed in API 2026-10-21); get consistency from schemas, formats, examples and validation.
  • Fast mode: same model, up to 2.5 times faster output, double the price, Opus 5.5 only, no batches.
  • Adaptive thinking decides per request; extended thinking (budget_tokens) is legacy; effort steers all output and defaults to medium on Opus 5.5 and Haiku 5.5.
  • Zero-shot: no examples; one-shot: one (easily over-copied); multishot: three to five relevant, diverse examples in <example> tags.
