8.1: Tool Design and Response Shaping

Building a tool Claude uses correctly: a schema it can't get wrong, a description that says when to call it, a result with only what matters, errors it can act on, a person in front of anything that moves money, and a tool set small enough to stay fast.

Overview

Skill 8.1

Tool Design and Response Shaping: "Implementing a tool for an integration need: a function schema, a description that drives correct invocation, response shaping so the model receives a minimal and actionable result, error handling, the choice of execution side, and an approval pattern, and assembling the tool set for performance."

This is the implementation skill: exam items show a tool definition and handler, and ask what's wrong or what to change. The design principles are covered in the architect notes (tool interfaces, structured errors, tool distribution). Exposing tools through MCP is skill 8.2, and choosing a tool over a skill or MCP server is skill 8.3.

Sources: Claude's documentation on tool use, defining tools and strict tool use, plus the earlier verified notes on tool descriptions and errors, checked on 19 and 20 November 2026 and paraphrased. The tools were tested by calling the handler directly.

Running example. The support assistant needs to answer "can I return this?" from the order system and start refunds. The order API returns over forty fields per order, and refunds must be approved by staff.

Two tools for one integration

Skill 8.1A read tool and a gated write tool.

returns_tools.py (Python) 
"""Two client tools for the support assistant: a read tool whose result is shaped to what Claude needs,
and a refund tool that queues for human approval instead of paying out on the model's say-so."""
import json

TOOLS = [
    {"name": "check_return",
     "description": ("Check whether one order can be returned and what refund it would get. Use it before promising "
                     "anything about a return. Returns eligible (true/false), the reason, the last return date, the refund "
                     "amount and the next action. It doesn't change anything. Needs the order ID exactly as the customer "
                     "gave it (for example A1042); ask for it if you don't have it."),
     "strict": True,
     "input_schema": {"type": "object", "additionalProperties": False, "required": ["order_id"],
                      "properties": {"order_id": {"type": "string", "description": "Order ID such as A1042"}}}},
    {"name": "request_refund",
     "description": ("Ask for a refund to be paid for an order that check_return said is eligible. A person approves "
                     "every refund, so this returns a ticket, not a payment: tell the customer it is being reviewed. "
                     "Don't call it for ineligible orders."),
     "strict": True,
     "input_schema": {"type": "object", "additionalProperties": False, "required": ["order_id", "amount", "reason"],
                      "properties": {"order_id": {"type": "string"}, "amount": {"type": "number"},
                                     "reason": {"type": "string", "enum": ["damaged", "unused", "late_delivery", "other"]}}}},
]


def shape(order: dict) -> dict:
    """The order API returns 40-odd fields; Claude gets the five that decide a return, already worked out."""
    eligible = order["status"] == "delivered" and order["days_since_delivery"] <= order["return_window_days"]
    return {"eligible": eligible,
            "reason": "within the return window" if eligible else
                      ("not delivered yet" if order["status"] != "delivered" else "return window has passed"),
            "last_return_date": order["return_deadline"],
            "refund_amount": order["amount_paid"] if eligible else 0,
            "next_action": "offer request_refund" if eligible else "explain and offer a person"}


def error(category: str, message: str, retryable: bool) -> tuple[str, bool]:
    return json.dumps({"error": category, "message": message, "retryable": retryable}), True


def run_tool(name: str, args: dict, orders_api, approvals: list) -> tuple[str, bool]:
    """Returns (tool_result content, is_error)."""
    if name == "check_return":
        try:
            order = orders_api(args["order_id"])
        except TimeoutError:
            return error("transient", "Order system timed out; try again once.", True)
        if order is None:
            return error("not_found", f"No order {args['order_id']}. Ask the customer to check the ID.", False)
        return json.dumps(shape(order)), False
    if name == "request_refund":
        order = orders_api(args["order_id"])
        result = shape(order) if order else None
        if not result or not result["eligible"]:
            return error("business_rule", "This order isn't eligible; don't request a refund.", False)
        if args["amount"] > result["refund_amount"]:
            return error("validation", f"Amount exceeds the paid {result['refund_amount']}.", False)
        ticket = f"RF-{len(approvals) + 1}"
        approvals.append({"ticket": ticket, **args})       # a person approves before any money moves
        return json.dumps({"status": "pending_approval", "ticket": ticket}), False
    return error("unknown_tool", name, False)

One integration, two tools, because reading and acting have different risks. check_return can run freely. request_refund changes something, so it is narrower, checks eligibility itself, and queues for approval.

Schema and description

Skill 8.1The schema makes the call valid; the description makes it the right call.

  • Schema:
    • strict: true guarantees the call matches the schema.
    • additionalProperties: false on every object, and required fields marked.
    • An enum for closed sets, such as the refund reason.
    • A description and example format on each parameter.
    Strict mode ensures valid input; it doesn't choose the tool.
  • Description: Claude decides whether to call a tool from its description, so say what it does, what it returns, when to use it, when not to, and what it needs. "Use it before promising anything about a return" and "Don't call it for ineligible orders" steer the behaviour that matters.
  • Missing inputs: say what to do when information is missing ("ask for it if you don't have it"). The docs note that Opus models are more likely to ask for a missing required value, while Sonnet may infer one.
  • Triggering: if Claude under-uses or over-uses a tool, adjust the description or a line in the system prompt, such as "Use the tools to investigate before responding."

Shaping the response

Skill 8.1Minimal and actionable.

  • Minimal: shape returns five fields instead of forty. Every token of a tool result is paid for, stays in the history and is re-sent on every later turn, and irrelevant fields bury the relevant ones.
  • Actionable: the result is already worked out (eligible: true, a reason, a deadline, an amount) and names the next_action. Claude doesn't have to reproduce the return policy's arithmetic from raw dates, which is where mistakes creep in.
  • Meaningful values: plain words and dates rather than internal codes, and IDs only where Claude needs them for a later call.

Errors Claude can act on

Skill 8.1A category, a message with the next step, and retryability.

Each failure returns is_error: true with a JSON body:

  • transient (retry once);
  • not_found (ask the customer to check the ID);
  • business_rule (don't retry: not eligible);
  • validation (fix the amount).

A bare "error" leaves Claude guessing whether to retry, rephrase or give up. The handler also never raises into the loop: every path returns a result. "No such order" is a not_found error the customer can fix, while a search that ran and matched nothing would be a successful empty result (empty results).

Client or server execution

Skill 8.1Where the tool's code runs.

  • Client tools run in your application. That covers your own functions and Anthropic-schema tools such as bash, the text editor and memory. Claude returns stop_reason: "tool_use", your code runs the call and sends a tool_result. Choose client side when the tool needs your systems, your data, your credentials or your approval step. Both shop tools are client tools for exactly that reason.
  • Server tools run on Anthropic's infrastructure: web search, web fetch, code execution, tool search, the advisor tool and the MCP connector. The results come back in the same response with no handler code. Choose them for public web content, sandboxed computation, or remote MCP servers you'd otherwise have to connect yourself. Some add usage charges, such as per search.
  • Mixed: when Claude calls a server tool alongside one of your client tools, your code still has to handle the client call.

An approval pattern

Skill 8.1The model proposes, a person disposes.

  • Queue, don't execute: request_refund validates, records the request and returns pending_approval with a ticket. The description tells Claude to say the refund is being reviewed, so it doesn't promise a payment.
  • Validate in the tool, whatever the model says: eligibility, and an amount no higher than what was paid. A persuaded or confused model can't approve its own request.
  • With the Agent SDK, the same idea is the can_use_tool callback, an ask rule, or a PreToolUse hook returning ask. A defer decision ends the turn so the call can be resumed after review (hooks and rules as hard stops).

Assembling the tool set

Skill 8.1Fewer, clearer tools are faster and chosen more accurately.

  • Every tool costs tokens on every request: its name, description and schema, plus a tool-use system prompt of 286 tokens on the current 5.5 models. Keep the set to what this agent needs, and give subagents their own small sets.
  • No overlap: two tools that sound alike get confused, so merge them or draw a clear boundary in their descriptions. Split a catch-all tool; merge thin wrappers that are always called together.
  • Large catalogues: beyond roughly 30 to 50 tools, use tool search with deferred loading, so definitions load only when needed.
  • Caching: tool definitions sit at the start of the prompt, so a stable tool list is cached with the system prompt. Changing the list invalidates that cache.
  • Parallel calls: independent read tools can run in one turn. Use disable_parallel_tool_use when calls must happen one at a time.

Key takeaways

  • Schema: strict: true, additionalProperties: false, required fields, enums, parameter descriptions. It guarantees valid input, not the right tool.
  • Description: what it does, returns, when to use it, when not to, and what to do about missing inputs. It is the main lever for correct invocation.
  • Shape results to a few worked-out, meaningful fields with a next action; raw API payloads cost tokens on every later turn and bury what matters.
  • Errors as is_error results with a category, a next step and retryability; never raise into the loop.
  • Client tools for your systems, data and approvals; server tools for web, code execution and remote MCP. Queue side-effecting calls for approval and validate in the tool. Keep the tool set small, non-overlapping and stable, with tool search for large catalogues.
