Overview

Skill 2.3

Claude API Mechanics (6.8% of the exam): "Claude API behavior and mechanics, including messages, tools, streaming, vision, thinking, caching, invoking Claude through third-party vendors, Messages API data access patterns, batch API use, and tradeoffs between realtime and batch API selection."

This is the skill that most separates the developer exam from the architect one: the Architect – Foundations guide lists streaming, vision, caching details and cloud-provider setup as out of scope, and here they are the core (Architect or Developer?). Plain HTTP, errors and retries are skill 2.4; tool design in depth belongs to Domain 8.

Sources: Anthropic's documentation on messages, stop reasons, streaming, vision, PDFs, thinking, effort, prompt caching, pricing, the cloud platform pages, the Files API, message threads, data retention and batch processing, plus the release notes and the anthropic Python SDK 2.6.0, checked on 8 November 2026 and paraphrased. The four examples were run against the real SDK with a mocked API, not the live service.

Running example. The shop's applications call Claude in four ways: a gear advisor that streams long answers, a catalogue tool that reads product photos, a returns assistant with a long, fixed policy prompt, and a nightly job that writes product descriptions.

Requests and responses

Skill 2.3The shape of a Messages API call.

A request to POST /v1/messages needs model, max_tokens and messages (a list of user and assistant turns). Common optional fields are system, tools, tool_choice, thinking, output_config (effort and structured output format), stop_sequences and stream. The API is stateless: each request carries the whole conversation, so your application keeps the history.

The response is a message with a list of content blocks (text, thinking, tool calls), the model, a stop_reason and usage. There are exactly seven stop reasons: end_turn, max_tokens, stop_sequence, tool_use, pause_turn (a server tool hit its step limit; send the content back to continue), refusal (returned with HTTP 200, not as an error) and model_context_window_exceeded. usage reports input and output tokens, cache reads and writes, and thinking tokens.

The current models are Claude Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 (claude-opus-5-5 and so on), all with a 1M-token context window and up to 128,000 output tokens.

Things that stopped working. A prefilled final assistant turn (the old trick for forcing a format) returns an error on Claude 4.6 and later models; use structured outputs instead. Under API version 2026-10-21, sent by the current SDKs, temperature, top_p and top_k are rejected for every model. And the Messages API request limit rose from 32 MB to 128 MB in October 2026.

Tools at a glance

Skill 2.3Where tool code runs.

  • Client tools (your own, defined with a JSON schema, plus Anthropic-defined ones such as bash and the text editor): Claude stops with tool_use, your code runs the tool, and you send a tool_result back in the next user message.
  • Server tools (web search, web fetch, code execution, tool search, the MCP connector): Anthropic runs them during the same request and returns the results in the response; some carry their own usage charges.

Tool definitions count as input tokens. On Opus 5.5, Sonnet 5.5 and Fable 5.1, forcing a tool with tool_choice any or a named tool returns an error; use auto with strict tool schemas, or structured outputs.

Streaming

Skill 2.3Receiving a response as it's generated.

With "stream": true, the API sends server-sent events in a fixed order: message_start; then, for each content block, content_block_start, one or more content_block_delta events and content_block_stop; then message_delta (carrying the stop_reason and cumulative usage); and finally message_stop. ping events can appear anywhere, and an error event (for example overloaded_error) can arrive mid-stream after the HTTP 200. Deltas come in types such as text_delta, input_json_delta (tool input as partial JSON) and thinking_delta; new event types may be added, so ignore ones you don't recognize.

gear_advisor.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

# A long answer, so stream it: words reach the customer as they are generated.
# With max_tokens above about 21,333 the Python SDK also refuses a non-streaming call.
with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=64000,
    system="You are the gear advisor for an outdoor-gear shop. Be practical and brief.",
    messages=[{"role": "user", "content": "I'm hiking three days in late autumn hills. What should I pack?"}],
) as stream:
    for text in stream.text_stream:  # only the text deltas, in order
        print(text, end="", flush=True)
    final = stream.get_final_message()  # the complete Message, same shape as messages.create()

print()
print("stop_reason:", final.stop_reason)  # end_turn, max_tokens, refusal, ...
if final.stop_reason == "max_tokens":
    print("Answer was cut off: raise max_tokens or ask Claude to continue.")

"Streaming is required" is an SDK rule. The API itself accepts large non-streaming requests. The SDKs refuse non-streaming calls they estimate could run past 10 minutes; in the Python SDK that means max_tokens above 21,333. Streaming also improves perceived latency, since the first words arrive sooner.

Images and PDFs

Skill 2.3Sending images and documents.

An image block has a source that is base64 data with a media type, a URL, or a file_id from the Files API. Supported formats are JPEG, PNG, GIF (first frame only) and WebP. Put the image before the question about it. Images can be up to 8,000 by 8,000 pixels and 10 MB each (base64, on the Claude API); with more than 20 images in a request, a stricter size applies. Tokens are counted in 28-by-28-pixel patches, so a 1,000 by 1,000 image costs about 1,296 tokens; Claude 4.7 and later models also have a high-resolution tier of up to 4,784 tokens per image.

describe_photo.py (Python, anthropic SDK) 
import base64
from pathlib import Path

import anthropic

client = anthropic.Anthropic()

# Product photo from the shop's catalogue (JPEG, PNG, GIF or WebP).
photo_b64 = base64.standard_b64encode(Path("tent-photo.jpg").read_bytes()).decode("utf-8")

message = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    messages=[{
        "role": "user",
        "content": [
            # Image first, then the question about it.
            {"type": "image", "source": {"type": "base64", "media_type": "image/jpeg", "data": photo_b64}},
            {"type": "text", "text": "List the visible features of this tent (doors, vents, guy-out points) and flag anything a customer would ask about."},
        ],
    }],
)

# With thinking on, thinking blocks can come before the text, so filter by type.
print("".join(block.text for block in message.content if block.type == "text"))
print("input tokens (image + text):", message.usage.input_tokens)

PDFs go in a document block (base64, URL or file ID), up to 600 pages: each page is read as both an image and extracted text, roughly 1,500 to 3,000 text tokens per page plus the image. Plain text can be a document too; Word and Excel files must be converted first. Claude won't identify people in images, and is weaker on very small, rotated or low-quality images and on precise counting. On Bedrock and Google-managed Google Cloud, images must be sent as base64 (no URLs or file IDs).

Thinking and effort

Skill 2.3Controlling how much Claude reasons before answering.

  • Adaptive thinking (thinking: {"type": "adaptive"}) lets Claude decide whether and how much to think. On the Claude 5 models it's the default: thinking can't be switched off on Opus 5.5 or Fable 5.1; Sonnet 5.5 allows between_tools (no up-front thinking) but rejects disabled, and Haiku 5.5 allows disabled at effort high or below.
  • Effort (output_config.effort: low, medium, high, xhigh, max) guides how much work Claude puts into the whole answer, thinking, text and tool calls alike. The default is high on most models and medium on Opus 5.5 and Haiku 5.5. max_tokens stays the hard cap.
  • What comes back: thinking blocks hold a summary (or nothing, with display: "omitted", the default on the Claude 5 models) and an encrypted signature; the raw reasoning is never returned. You pay for the full thinking as output tokens even when it isn't displayed.
  • With tools, pass thinking blocks back complete and unchanged alongside the tool call they came with; modified blocks cause an error.

Manual thinking budgets are legacy. thinking: {"type": "enabled", "budget_tokens": N} is deprecated on Claude 4.6 models and rejected from Claude 4.7 on, including all Claude 5 models. Material that teaches budget_tokens as the main control is out of date; use adaptive thinking and effort.

Prompt caching

Skill 2.3Reusing a long, unchanged prefix to cut cost and latency.

returns_assistant.py (Python, anthropic SDK) 
from pathlib import Path

import anthropic

client = anthropic.Anthropic()

# The full returns policy: long, and identical on every request.
RETURNS_POLICY = Path("returns-policy.md").read_text(encoding="utf-8")

SYSTEM = [
    {"type": "text", "text": "You answer customer questions for an outdoor-gear shop."},
    {
        "type": "text",
        "text": RETURNS_POLICY,
        # Breakpoint: cache everything up to and including this block (tools, then system).
        # Default lifetime is 5 minutes; {"type": "ephemeral", "ttl": "1h"} keeps it an hour.
        "cache_control": {"type": "ephemeral"},
    },
]


def ask(question: str) -> None:
    response = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        system=SYSTEM,  # same bytes every time, or the cache misses
        messages=[{"role": "user", "content": question}],  # the part that changes goes last
    )
    u = response.usage
    print(f"cache write: {u.cache_creation_input_tokens}, cache read: {u.cache_read_input_tokens}, uncached: {u.input_tokens}")


ask("Can I return boots I've worn on one hike?")      # first call writes the cache
ask("How long do refunds take for a sleeping bag?")   # within 5 minutes: read from the cache
  • How matching works. The cache key is the exact prefix in the order tools, system, messages, up to a cache_control breakpoint (up to four per request). Any change before the breakpoint (a timestamp, reordered tools) misses. Changing tool definitions invalidates everything; changing tool_choice, images, or thinking and effort settings invalidates the message part.
  • Automatic caching (since February 2026): one top-level cache_control on the request, and the API places and moves the breakpoint as the conversation grows.
  • Minimum size. Prompts shorter than the minimum are silently not cached: 512 tokens on the Claude 5 models, more on older ones (4,096 on Opus 4.5 and 4.6, for example).
  • Prices. A 5-minute cache write costs 1.25 times the normal input price and a 1-hour write 2 times; reads cost 0.1 times on most models, 0.05 times on Opus 5.5 and Sonnet 5.5, and 0.025 times on Fable 5.1. The 5-minute lifetime is refreshed free on every hit. Cache reads also don't count toward input-tokens-per-minute rate limits.
  • Parallel requests: an entry exists only once the first response starts, so send one request before firing many in parallel.

Claude on cloud platforms

Skill 2.3Calling Claude through Amazon, Google and Microsoft.

The same models are reachable through several vendors, each with its own client class in the SDK:

  • Claude Platform on AWS (Anthropic-operated, AWS billing): AnthropicAWS, the same model IDs and nearly the same features as the Claude API.
  • Claude in Amazon Bedrock (AWS-operated): AnthropicBedrockMantle for the Messages API endpoint (legacy AnthropicBedrock for older models); model IDs prefixed anthropic., such as anthropic.claude-opus-5-5; regional endpoints cost 10% more than the global one.
  • Claude models on Google Cloud, Google-managed (the former Vertex AI): AnthropicVertex, with the model in the URL and its own retirement dates.
  • Claude models on Google Cloud, Anthropic-managed (since October 2026): the Claude API's request format and features, billed through Google Cloud.
  • Claude in Microsoft Foundry: AnthropicFoundry, where the model value is your deployment name.

The Anthropic-operated options get features first. Bedrock and Google-managed Google Cloud lack, among other things, the Files API and URL image sources, several server tools, Agent Skills, the MCP connector and Message Batches; Foundry also has no batches. The docs recommend each platform's own client class rather than pointing the plain client at another base URL.

Getting data in and out

Skill 2.3One reading of "Messages API data access patterns".

No Anthropic page uses the guide's phrase "data access patterns", so this section covers the ways data reaches a request and where it's held, which is the best-supported reading:

  • Inline: text and base64 images and PDFs in each request; nothing is stored between calls.
  • By URL: images and PDFs fetched from a URL (Claude API only).
  • Files API (out of beta since August 2026): upload once, then reference the file_id; up to 500 MB per file. Files belong to the workspace, so any key in it can read them: never accept file IDs from end users, and use separate workspaces per tenant. Uploaded files can't be downloaded again.
  • Retrieval through tools: your tool returns data as a tool result; search_result blocks enable citations for retrieval (RAG); web search and fetch bring in outside content.
  • Server-held state: message threads (a beta since November 2026) let the API keep a conversation for a short time so you send only new messages; Managed Agents sessions keep transcripts until deleted.
  • Retention: the Messages API and prompt caching are eligible for zero data retention; the Files API, Message Batches (results stored 29 days), message threads, code execution and Managed Agents are not.

Batch or real time

Skill 2.3The Message Batches API, and when to use it instead of normal calls.

nightly_descriptions.py (Python, anthropic SDK) 
import time

import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()

products = {
    "sku-tent-2p": "Two-person tent, 1.9 kg, two doors, aluminium poles",
    "sku-stove-ti": "Titanium canister stove, 73 g, piezo igniter",
    "sku-pack-45l": "45-litre pack, adjustable back length, rain cover included",
}

# One request per product; custom_id ties each result back to its SKU.
batch = client.messages.batches.create(
    requests=[
        Request(
            custom_id=sku,  # 1-64 characters: letters, digits, - and _
            params=MessageCreateParamsNonStreaming(
                model="claude-opus-5-5",
                max_tokens=1024,
                messages=[{"role": "user", "content": f"Write a 60-word shop description for: {spec}"}],
            ),
        )
        for sku, spec in products.items()
    ]
)
print("batch:", batch.id, batch.processing_status)  # in_progress

# Poll. Most batches end within an hour; requests still waiting after 24 hours expire.
while True:
    batch = client.messages.batches.retrieve(batch.id)
    if batch.processing_status == "ended":
        break
    time.sleep(60)

# Results can arrive in any order: match them by custom_id, never by position.
descriptions = {}
for item in client.messages.batches.results(batch.id):
    match item.result.type:
        case "succeeded":
            msg = item.result.message
            descriptions[item.custom_id] = "".join(b.text for b in msg.content if b.type == "text")
        case "errored":
            print(item.custom_id, "error:", item.result.error.error.type)  # e.g. invalid_request_error
        case "expired" | "canceled":
            print(item.custom_id, item.result.type, "- not billed, submit again")

Batches cost half the normal price, accept up to 100,000 requests or 256 MB per batch, and have their own rate limits. Most finish within an hour; anything not done in 24 hours expires. Results stay downloadable for 29 days, come back in any order, and errored, canceled or expired requests aren't billed. Request errors only show up once the batch has ended, so try one request normally first. Streaming, fast mode and a few other options aren't allowed in batches.

Choosing: use real-time calls when a person is waiting (chat, the gear advisor) or you need streaming or the lowest latency (fast mode on Opus 5.5 is a real-time-only option). Use batches for large, non-urgent jobs (the nightly descriptions, evaluations, bulk classification), and for very long reasoning that risks timeouts. Remember that batches aren't available on Bedrock, Google-managed Google Cloud or Foundry, and aren't covered by zero data retention.

Priority Tier is gone. Service tiers are now marked legacy and Priority Tier capacity is no longer sold (and isn't offered on the Claude 5 models). The real choice is now between standard real-time calls, fast mode for latency, and batches for cost.

Key takeaways

  • The Messages API is stateless: send model, max_tokens and the full messages history. Seven stop reasons; refusal comes with HTTP 200. No prefill on 4.6+; no sampling parameters under API version 2026-10-21.
  • Streaming events: message_start, content block start/delta/stop, message_delta, message_stop, plus ping and mid-stream error. Streaming large max_tokens is an SDK requirement, not an API one.
  • Images: base64, URL or file ID; image before text; tokens counted in 28-pixel patches. PDFs up to 600 pages as document blocks.
  • Adaptive thinking plus effort replace budget_tokens; pass thinking blocks back unchanged with tool calls; hidden thinking is still billed.
  • Caching: exact prefix (tools, system, messages) up to a breakpoint; 5-minute or 1-hour lifetime; 512-token minimum on Claude 5; reads from 0.025 to 0.1 times the input price.
  • Cloud platforms use their own clients and model IDs; Anthropic-operated ones get features first. Files are workspace-scoped. Batches: 50% off, up to 24 hours, any order, match by custom_id.
