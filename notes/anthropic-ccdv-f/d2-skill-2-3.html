Overview

Skill 2.3

Configuration and SDLC Integration: "Determining the correct configuration for a Claude system from its configuration artifacts and SDLC context, including CLAUDE.md files, settings.json, model version pinning, prompt versioning, plugin dependencies, and CI integration, and assessing how a configuration change affects each environment."

Items show configuration files and a situation ("a teammate says the deny rule doesn't apply", "CI started using a different model") and ask what's in effect or what to change. Each section below is one kind of configuration that can drift between people, machines or releases; the last puts them together. CLAUDE.md is covered in depth in the CCAR-F notes (CLAUDE.md hierarchy); writing and packaging plugins, skills and hooks is the Claude Code domain (Domain 3).

Managed settings win, lists merge, and a deny anywhere beats an allow

Skill 2.3Where Claude Code's settings live, and which wins.

From highest priority to lowest:

  1. Managed settingsSet by the organization (a managed-settings file, device management, or the claude.ai admin console). Nothing below can override a managed key.
  2. Command line--settings <file-or-json>, for one session.
  3. Local project.claude/settings.local.json: yours, for this project, not committed.
  4. Shared project.claude/settings.json: committed, so the whole team gets it.
  5. User~/.claude/settings.json: yours, for every project.
  • Lists merge. permissions.allow rules from every file apply together, and env merges variable by variable, rather than one file replacing another.
  • Deny wins everywhere. Rules are checked deny, then ask, then allow, and a tool denied at any level can't be allowed by another. An allow in your local file doesn't beat an ask rule from the project file.
  • Trust gates some keys. In a committed file, allow rules, extra directories, plugin marketplaces and most env values apply only after each person trusts the folder; deny and ask rules apply immediately. Some settings never apply from a repository at all (for example, auto or bypassPermissions as the default mode).
  • Strict JSON. A comment or trailing comma breaks the file (and in -p mode, a broken file is silently skipped). Add "$schema": "https://json.schemastore.org/claude-code-settings.json" for editor validation.

~/.claude.json is a separate file Claude Code writes itself (account details, MCP servers, per-project trust), not one of these settings files. /config changes a few personal options; there's no claude config command in current versions, so older instructions that use claude config set are out of date.

Commit team settings; keep personal overrides in the local file

Skill 2.3What to commit, and what to keep to yourself.

.claude/settings.json (committed, JSON) 
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(pnpm run lint)", "Bash(pnpm run test *)", "Bash(git diff *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(curl *)"]
  },
  "env": {
    "SHOP_ENV": "dev",
    "SHOP_API_BASE": "http://localhost:8080"
  },
  "extraKnownMarketplaces": {
    "shop-tools": {
      "source": {"source": "github", "repo": "example-shop/claude-plugins", "ref": "stable"},
      "autoUpdate": false
    }
  },
  "enabledPlugins": {
    "catalog-lint@shop-tools": true,
    "order-api-helper@shop-tools": true
  }
}
.claude/settings.local.json (not committed, JSON) 
{
  "model": "claude-opus-5-5",
  "permissions": {
    "allow": ["Bash(docker compose up *)"]
  },
  "env": {
    "SHOP_API_BASE": "http://localhost:9090"
  },
  "enabledPlugins": {
    "order-api-helper@shop-tools": false
  }
}

For this developer, the allow lists combine into four rules; SHOP_API_BASE is 9090 (local beats shared) while SHOP_ENV still comes from the shared file; one plugin is switched off for them alone; and the shared deny rules still beat any local allow. The marketplace is pinned to the stable branch with automatic updates off, so plugin changes arrive only when someone runs an update. Claude Code adds settings.local.json to your global Git excludes when it creates the file; if you create it by hand, add it to .gitignore yourself.

Enforce in settings, guide in CLAUDE.md. CLAUDE.md is instructions Claude reads; settings are configuration Claude Code enforces. "Never read .env" belongs in a deny rule (or, for an organization, a managed deny rule), not only in CLAUDE.md. Bash rules match command text, so they aren't a security boundary on their own; pair them with the sandbox.

Review committed CLAUDE.md files like code

Skill 2.3Instruction files as part of configuration.

CLAUDE.md files exist at managed, user (~/.claude/CLAUDE.md), project (./CLAUDE.md or ./.claude/CLAUDE.md, committed) and local (./CLAUDE.local.md, add it to .gitignore) levels, plus subfolder files loaded when Claude works there. They're combined rather than overriding each other, can import other files with @path, and can be split into .claude/rules/. For configuration management, treat the committed files like code: review changes in pull requests, keep personal preferences out of the shared file, and use claudeMdExcludes in a monorepo to skip other teams' files. In CI, the checked-out project CLAUDE.md is read on every run, so keep it short. The CCAR-F notes cover the hierarchy in depth (task 3.1).

Pin full model IDs and the SDK version; Claude Code aliases move

Skill 2.3Making sure the model that passed testing is the one that runs.

  • On the API, the ID is the pin. Every Claude model ID is a pinned snapshot, including the dateless IDs used from the 4.6 generation on: claude-sonnet-5-5 will always be the same model, and updates ship under new IDs. Only older short aliases (such as claude-sonnet-4-5) move to the newest dated snapshot. A pinned ID still retires eventually; planning for that is skill 5.2.
  • Pin the SDK too. The SDK's major version decides the anthropic-version header it sends; Python SDK 2.x sends 2026-10-21, which rejects temperature. A dependency range such as anthropic>=2,<3 pins the API version as well.
  • In Claude Code, aliases move. opus, sonnet and haiku point to the recommended version for your provider and update over time, and they resolve differently by provider and by Claude Code version. To pin, use a full ID (claude-opus-5-5) or the ANTHROPIC_DEFAULT_OPUS_MODEL style variables. The model is chosen in this order: /model in the session, then --model, then the ANTHROPIC_MODEL variable, then the model setting.
  • Managed control. A managed model is only a starting default; to restrict what people can choose, use availableModels (with enforceAvailableModels).
  • Cloud platforms. Pin model versions before rolling out Claude Code on Bedrock, Google Cloud or Foundry, where the default for an alias may lag or not be enabled; modelOverrides maps Anthropic IDs to provider-specific IDs such as inference profiles.
  • Agent SDK. Set model in ClaudeAgentOptions; otherwise an SDK application inherits whatever model the machine's settings specify, since setting sources load by default.

Version prompts in Git, evaluate each change, and log the version used

Skill 2.3Treating prompts as versioned, tested artefacts.

Anthropic no longer offers a prompt store in the Console, so prompts are versioned the way code is: as files in Git, reviewed in pull requests, with the evaluation suite run on every change (one change at a time: prompt or model), and with the prompt version logged alongside every response.

prompts/order_help/v3.meta.json (JSON) 
{
  "prompt_id": "order_help",
  "version": 3,
  "model": "claude-sonnet-5-5",
  "eval_suite": "evals/order_help/",
  "changed": "2026-11-02",
  "note": "Added sizing guidance; passed 48/50 evaluation cases"
}
shop_config.py (Python) 
"""Model and prompt configuration for the shop's order-help assistant."""

import hashlib
import json
import os
from dataclasses import dataclass
from pathlib import Path

# Pinned model ID: a fixed snapshot. Upgrading is a reviewed code change plus an evaluation run.
MODEL_ID = "claude-sonnet-5-5"

# IDs the evaluation suite has passed on. An environment override must be one of these.
APPROVED_MODELS = {"claude-sonnet-5-5", "claude-haiku-5-5"}

# Bump this in the same pull request that adds prompts/order_help/v4.md.
PROMPT_NAME = "order_help"
PROMPT_VERSION = 3

PROMPT_DIR = Path(__file__).parent / "prompts"


@dataclass(frozen=True)
class PromptConfig:
    model: str
    system: str
    prompt_version: int
    prompt_sha256: str


def load_config() -> PromptConfig:
    # Allow a staging override, but only to a model we have tested.
    model = os.environ.get("SHOP_MODEL", MODEL_ID)
    if model not in APPROVED_MODELS:
        raise ValueError(f"Model {model!r} has not passed the evaluation suite")

    folder = PROMPT_DIR / PROMPT_NAME
    text = (folder / f"v{PROMPT_VERSION}.md").read_text(encoding="utf-8")
    meta = json.loads((folder / f"v{PROMPT_VERSION}.meta.json").read_text(encoding="utf-8"))
    if meta["version"] != PROMPT_VERSION:
        raise ValueError("Prompt file and metadata versions disagree")

    digest = hashlib.sha256(text.encode("utf-8")).hexdigest()
    return PromptConfig(model, text, PROMPT_VERSION, digest)


def request_body(config: PromptConfig, question: str) -> dict:
    # Log prompt_version and prompt_sha256 with every response, so a bad answer
    # can be traced to the exact prompt and model that produced it.
    return {
        "model": config.model,
        "max_tokens": 1024,
        "system": config.system,
        "messages": [{"role": "user", "content": question}],
    }


if __name__ == "__main__":
    cfg = load_config()
    print(cfg.model, f"v{cfg.prompt_version}", cfg.prompt_sha256[:12])

Changing the system prompt also invalidates the prompt cache from the system level onwards, so expect a cache write after each prompt release. Where Anthropic does provide versioning is server-side: Claude Managed Agents store each agent configuration (model, system prompt, tools) as numbered versions, and a session can be pinned to a specific version for a staged rollout; Agent Skills in the API can also be pinned to a version.

Workbench prompts are gone. The legacy Console Workbench closed on 17 August 2026; its saved prompts, variables and evaluations weren't carried over, and the experimental prompt generate, improve and templatize APIs were retired at the same time. Its replacement, the playground, is for trying requests, not storing prompt versions.

Pin plugin versions, dependency ranges and sources

Skill 2.3Controlling which plugin versions a team runs.

  • A plugin's version. If plugin.json sets version, everyone stays on that version until the string changes, however many commits are pushed. With no version anywhere, each commit counts as a new version. Pick one approach and stick to it.
  • Dependencies go in plugin.json as names or objects with a version range in npm style (~2.1.0, ^2.0). Ranges resolve against Git tags named <plugin>--v<version>, which claude plugin tag creates. Without a range, a dependency moves to whatever its marketplace publishes next. Conflicting ranges make the install fail, and dependencies from another marketplace are refused unless that marketplace is explicitly allowed.
  • Pinning the source. A marketplace entry can pin a plugin to a Git ref or a full 40-character sha; an archive source can pin a sha256.
  • Updates. Official marketplaces update automatically; third-party ones don't unless autoUpdate is on. A running session keeps the versions it loaded until /reload-plugins or a restart. claude plugin prune removes dependencies that are no longer needed.
  • Team-required plugins. List the marketplace in extraKnownMarketplaces and the plugins in enabledPlugins, in the committed project settings or, to enforce them across an organization, in managed settings (where true forces a plugin on and false blocks it). They take effect for a teammate only after that person trusts the folder, and a plugin from an external source still has to be installed once on each machine.
plugins/order-api-helper/.claude-plugin/plugin.json (JSON) 
{
  "name": "order-api-helper",
  "version": "1.4.0",
  "description": "Skills and an MCP server for working with the shop's orders API",
  "dependencies": [
    {"name": "catalog-lint", "version": "~2.1.0"}
  ]
}

Give CI runs an explicit model, granted tools and capped turns

Skill 2.3Running Claude Code in a pipeline with a known configuration.

The Claude Code GitHub Action, anthropics/claude-code-action@v1, runs Claude Code on a runner. With no prompt input it waits for an @claude mention in an issue or pull request; with a prompt it runs on any event, and its results go to the run log unless the prompt and tools let it post. GitLab has its own integration, and anywhere else claude -p runs non-interactively.

.github/workflows/claude-pr-check.yml (YAML, GitHub Actions) 
name: Claude PR check
on:
  pull_request:
    types: [opened, synchronize, ready_for_review]

# One run per pull request; a new push cancels the old run.
concurrency:
  group: claude-pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 15  # stop runaway jobs
    permissions:
      contents: read
      pull-requests: read
      id-token: write  # needed for the action's GitHub App authentication
    steps:
      - uses: actions/checkout@v7  # gives Claude the repository, including CLAUDE.md and .claude/settings.json
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}  # a secret, never a value in the file
          settings: .claude/ci-settings.json  # CI-only rules on top of the committed settings
          prompt: "Review this pull request's changes to the payments package against CLAUDE.md and list any problems."
          claude_args: |
            --model claude-sonnet-5-5
            --max-turns 10
            --allowedTools "Bash(git diff *),Read,Grep"
.claude/ci-settings.json (JSON, used only in CI) 
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "deny": ["Bash(git push *)", "Edit", "Write", "WebFetch"]
  },
  "env": {
    "SHOP_ENV": "ci"
  }
}
  • Configuration inputs. claude_args takes any CLI flag (--model, --max-turns, --allowedTools, --mcp-config, --append-system-prompt); settings takes extra settings as JSON or a file path; plugin_marketplaces and plugins install plugins first. Without --model, the run uses Claude Code's default model, which can change with a Claude Code release.
  • Tools must be granted. In automation mode a plain prompt has no shell or GitHub access until you allow tools, with --allowedTools or permissions.allow in the settings input. Nobody is there to approve a prompt.
  • Credentials. An API key or subscription token in a repository or organization secret (prefer an API key for an organization-wide secret, since a token belongs to one person's subscription), or workload identity federation with no stored key. Bedrock, Google Cloud and Foundry use OIDC through use_bedrock, use_vertex or use_foundry.
  • Who can trigger it. The triggering user needs write access, bots are refused unless listed in allowed_bots, and on public repositories fork pull requests get no secrets. Commits made with the default GITHUB_TOKEN don't start other workflows, so let the action use its GitHub App identity if CI must run on Claude's commits.
  • Cost. Cap turns with --max-turns, set a job timeout and a concurrency group, and keep CLAUDE.md short.

Beta inputs are gone. Workflows on @beta used mode, direct_prompt, model and max_turns. In v1, the mode is detected automatically, direct_prompt became prompt, CLI options moved into claude_args, and custom_instructions became --append-system-prompt.

Trace each change to every place that reads it

Skill 2.3Tracing one change to the laptop, the teammate, the runner and production.

Take a team that shares one repository with Claude Code settings and two internal plugins, runs a GitHub workflow where Claude reviews pull requests, and has an order-help assistant in production that must keep the exact model and prompt that passed its evaluations. Its four places read different files:

  • The developer's laptop: managed settings (if the machine is managed), user, shared project and local settings, plus every CLAUDE.md level.
  • A teammate's laptop: the same shared files once they pull, but their own user and local files, and committed allow rules, marketplaces and most env values only after they trust the folder.
  • The CI runner: a fresh checkout, so the shared settings and project CLAUDE.md, plus what the workflow passes in (settings, claude_args, plugins). No user or local file exists there.
  • Production: the order-help assistant calls the API directly, so no Claude Code settings apply at all; only the model ID and prompt version in its own code and files.

Tracing some changes through:

  • A new deny rule in .claude/settings.json applies on every laptop as soon as it's pulled (deny needs no trust) and in CI on the next run. Production is unaffected.
  • "model" in one developer's settings.local.json changes only that developer's sessions. CI keeps the model in claude_args; production keeps MODEL_ID.
  • Setting SHOP_MODEL on the staging server to a model the evaluations haven't covered makes load_config() refuse to start, which is the point of the allow-list.
  • A plugin release with a new version string reaches laptops only when someone updates (auto-update is off for the third-party marketplace); with the version unchanged, nobody gets the new commits. A runner installs plugins fresh each run, so pin the marketplace ref if CI must match the laptops.
  • A Claude Code update that moves the sonnet alias changes the model for anyone using the alias, but not for CI, which names claude-sonnet-5-5, or production, which uses the API.
  • A new prompt v4.md changes nothing until PROMPT_VERSION is bumped in the same pull request, which also runs the evaluations and shows up in the response logs.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A developer adds an allow rule in settings.local.json, but the project’s committed settings deny the same tool. What happens?
  1. A. The local allow wins
  2. B. The deny wins; deny is checked first at every level
  3. C. Whichever file loaded last wins
  4. D. Claude Code asks
Answer
B
Why
A tool denied at any level can’t be allowed by another file.
Question 2
Scenario
CI started using a different model after a Claude Code update. The workflow passes no --model. What fixes it?
  1. A. Pin the SDK
  2. B. Pass a full model ID such as claude-sonnet-5-5 in claude_args
  3. C. Use the sonnet alias
  4. D. Set temperature
Answer
B
Why
Without --model, the run uses Claude Code’s default, which can change with a release.
Question 3
Scenario
A plugin sets version 1.2.0 in plugin.json, and the team pushes ten commits without changing it. What do teammates get?
  1. A. Every commit
  2. B. Nothing new until the version string changes
  3. C. Only the latest commit
  4. D. An error
Answer
B
Why
A set version holds everyone on it until the string changes.
Question 4
Scenario
Production must keep the prompt that passed evaluations. A new v4 prompt file is merged. What should control which prompt runs?
  1. A. The newest file
  2. B. An explicit prompt version bumped in the same pull request that runs the evaluations
  3. C. CLAUDE.md
  4. D. The Console Workbench
Answer
B
Why
Prompts are versioned like code; the version is explicit, evaluated and logged.

Key takeaways

  • Settings precedence: managed, command line, local project, shared project, user. Lists merge, deny wins at every level, and committed allow rules and marketplaces wait for folder trust. Settings files are strict JSON.
  • Commit team permissions, hooks and plugins in .claude/settings.json; keep personal overrides in settings.local.json. Enforce in settings, guide in CLAUDE.md.
  • API model IDs are pinned snapshots; pin the SDK major to pin the API version. Claude Code aliases move, so use full IDs and restrict choices with availableModels.
  • Prompts are versioned as files in Git with evaluations and logged versions; Managed Agents and Skills have server-side versions. Plugin versions: a set version freezes users; dependency ranges resolve against tags; pin sources by ref or sha.
  • CI: claude-code-action@v1 with prompt, claude_args (pin --model, cap --max-turns, grant tools) and settings; credentials in secrets or federation. A runner has only committed files plus what the workflow passes in.
