Overview

Skill 5.2

Model Tier Selection and Release Planning: "Evaluating model tier options across quality, latency, and cost against task requirements and binding constraints, justifying the selection, and planning for behavior change across model releases using regression evaluations."

Items give a task with requirements (volume, a latency target, a budget, a compliance rule) and ask which model and effort fit, or what to do before moving to a new release. The mechanics of effort, thinking and fast mode are in skill 5.1; pinning model IDs in configuration is skill 2.3; cost arithmetic is skill 5.3; building evaluations in depth is Domain 4.

Know what each tier is for; Opus 5.5 is the usual starting point

Skill 5.2What each tier is for, in Anthropic's terms.

  • Claude Fable 5.2 (claude-fable-5-2, US$8 / $40): the highest capability open to all customers, for demanding reasoning and long-horizon agent work such as sessions that run for hours or research carried to a finished document. Thinking is always on; default effort high.
  • Claude Opus 5.5 (claude-opus-5-5, $4 / $20): complex agentic coding and enterprise work, vision-heavy workflows and computer use. Anthropic's starting point for most workloads. Thinking always on; default effort medium.
  • Claude Sonnet 5.5 (claude-sonnet-5-5, $2 / $10): speed plus capability for everyday coding, analysis, content and tool use. Default effort high.
  • Claude Haiku 5.5 (claude-haiku-5-5, from $0.10 / $0.50, dearer above 100,000 prompt tokens): the lowest latency and price, for high-volume classification, extraction, routing, real-time use and subagents. Default effort medium.

Prices are per million input / output tokens. All four have a 1M-token context window, up to 128,000 output tokens and a June 2026 knowledge cutoff. Earlier models (Fable 5.1 and 5, Opus 5 and 4.x, Sonnet 5 and 4.6, Haiku 4.5) remain available, some deprecated. Mythos 5.2 is Fable 5.2's capabilities with different safeguards, offered only to organizations verified through programs such as Anthropic's Cyber Verification Program. Fable is an escalation, not a default: the guidance is to move up only when evaluations on Opus 5.5 at higher effort still fall short.

Rule models out by hard constraints before comparing quality

Skill 5.2Requirements that rule a model in or out before quality is even compared.

  • Data retention. Fable 5.2, 5.1 and 5 and the Mythos models are Covered Models that require 30-day retention, so a zero-data-retention organization can't use them without Anthropic's explicit approval or a separate workspace with retention turned on (skill 2.2). For a zero-data-retention organisation without that approval, Opus 5.5 is the ceiling.
  • Platform. Fable 5.2 runs on Bedrock only through the older bedrock-runtime endpoint; Batches and the Files API aren't on every cloud platform; fast mode is only on some.
  • Forced tool use. If an integration needs tool_choice any or a named tool, Fable 5.2, Opus 5.5 and Sonnet 5.5 are out (400); Haiku 5.5 and Opus 5 still accept it. The alternative is auto with strict tools.
  • Thinking off. Only Haiku 5.5 (disabled) and Sonnet 5.5 (between_tools) can skip up-front thinking; Fable 5.2 and Opus 5.5 always think.
  • Speed. A hard output-speed target may need fast mode, which only Fable 5.2, Mythos 5.2 and Opus 5.5 offer at general availability; a time-to-first-token target points to a smaller model or lower effort instead.
  • Other features. US-only inference needs a Claude 4.6 or later model; with customer-managed encryption keys, Fable 5.2 has no structured outputs or strict tools; very long batch outputs (up to 300,000 tokens) need a model that supports that beta.

Compare cost per completed task, and try effort before switching models

Skill 5.2The levers, where to start, and how to justify a choice.

The levers are the model tier, effort, thinking (where it can be limited), fast mode, the Batch API (half price, slower) and prompt caching. Anthropic's choosing-a-model page says tuning effort is "often a better lever than switching models", and gives two starting approaches:

  • Efficiency-first: start on Haiku 5.5, test, and upgrade only where a specific capability gap shows. Suits prototypes, tight latency, cost-sensitive and high-volume simple tasks.
  • Capability-first: start on Opus 5.5, tune the prompts, then lower effort or move to a cheaper model over time; move to Fable 5.2 only if evaluations at xhigh or max still fall short. Suits complex reasoning, high accuracy needs and autonomous agents.

Justifying with numbers. Compare cost per completed task, not price per token: a cheaper model that fails more often still bills the failed attempt, then the retry. Anthropic's own measurements on a coding benchmark show the shape: Opus 5.5 at its default solved 93.1% at about $0.22 per solved task, at high 95.5% at $0.30, and at xhigh 96.5% at $0.75, level with Fable 5.2 at its default (96.3%) for a little over half the cost. On the same benchmark, Opus 5.5 at low roughly matched Sonnet 5.5 at its default for about 7% more per solved task. Its suggested order: turn on caching and batching first, upgrade if you're a model or two behind, otherwise sweep effort on the current model, and add a second model only if the pair beats the single model's whole curve of score against spend.

Route simple work to small models, but mind per-model caches and thinking blocks

Skill 5.2Using different models for different jobs.

router.py (Python, anthropic SDK) 
"""Pick a Claude model and effort level for each kind of shop task."""
from dataclasses import dataclass

import anthropic


@dataclass(frozen=True)
class Route:
    model: str
    effort: str       # "low", "medium", "high", "xhigh" or "max"
    max_tokens: int   # covers thinking plus the reply


# One entry per task type. Change a route here, then re-run your evaluations.
ROUTES = {
    # Tagging a ticket: high volume, a short label, so the cheapest model at low effort.
    "classify": Route("claude-haiku-5-5", "low", 1024),
    # Replies to customers: good writing, quick turnaround.
    "reply": Route("claude-sonnet-5-5", "medium", 4096),
    # Disputed returns: policy, photos and order history weighed together.
    "dispute": Route("claude-opus-5-5", "high", 16000),
}

client = anthropic.Anthropic()


def run(task_type: str, system: str, user_text: str) -> str:
    route = ROUTES[task_type]
    response = client.messages.create(
        model=route.model,
        max_tokens=route.max_tokens,
        # Effort lives inside output_config. Set it every time: the default is "medium"
        # on Opus 5.5 and Haiku 5.5 but "high" on Sonnet 5.5.
        output_config={"effort": route.effort},
        system=system,
        messages=[{"role": "user", "content": user_text}],
        # No thinking, temperature or prefill here: current models think adaptively
        # by default and reject the rest.
    )
    if response.stop_reason == "refusal":
        raise RuntimeError(f"Declined: {response.stop_details}")
    # Thinking blocks can come first, so pick the text blocks by type.
    return "".join(b.text for b in response.content if b.type == "text")


if __name__ == "__main__":
    print(run("classify",
              "Label the ticket as one of: returns, sizing, shipping, other. Reply with the label only.",
              "My trail shoes are a size too small, can I swap them?"))

These routes follow the docs' guidance (Haiku 5.5 at low effort for simple high-volume work, Sonnet 5.5 for conversation, Opus 5.5 for complex judgement) but are a starting point to tune with evaluations, not an official mapping. Trying a single model at different effort levels first keeps one prompt cache, since caches are per model.

  • Advisor tool (beta): a cheaper executor consults a stronger advisor on hard decisions. It helps only when the executor actually consults, the tool definition adds about 1,000 prompt tokens per request, and Anthropic's results landed about on the executor's own effort curve. A Fable 5.2 executor accepts only a Fable 5.2 or Mythos 5.2 advisor.
  • Orchestrator and workers: a frontier model plans while cheaper models do the pieces. In Anthropic's tests it came out ahead only for routine work with a long cost tail and for work too large for one context window.

Switching models mid-conversation has costs. Each model has its own cache, and thinking blocks are tied to the model that produced them: only Fable 5.2 and Mythos 5.2 can read Fable 5.2's blocks, so a router or fallback that hands a Fable 5.2 conversation to Opus 5.5 drops its reasoning for those turns.

Model IDs are pinned snapshots that still retire, on each platform's calendar

Skill 5.2What a model ID promises, and how long it lasts.

  • Every model ID is a pinned snapshot. The weights behind an ID never change; improvements ship under a new ID. Since the 4.6 generation IDs have no date (claude-opus-5-5), and they aren't evergreen aliases. Before 4.6, short aliases such as claude-sonnet-4-5 pointed to the latest dated snapshot. Pinned isn't frozen, though: the serving system around a model can change slightly.
  • API versions. The anthropic-version header (sent by the SDKs) is separate from the model. Version 2026-10-21 removed sampling parameters for every model, and the new SDK majors send it by default, so an SDK upgrade can break old code with the same model.
  • Statuses: active, legacy (no more updates), deprecated (still works, has a replacement and a retirement date, likely less reliable) and retired (requests fail; they aren't redirected).
  • Notice. At least 60 days before retirement for public models, by email and on the deprecations page. Current models carry a "not sooner than" date: Opus 5.5 not before 22 September 2027, Fable 5.2 not before 9 November 2027. Sonnet 4.5, for example, was deprecated on 30 September 2026 and retires on 30 November 2026, replaced by Sonnet 5.5.
  • Finding stragglers. The Console's usage export breaks usage down by API key and model. In Claude Code, update Claude Code first, then check the model behind aliases and in subagent definitions.

Platforms keep their own calendars. Deprecation dates apply to Anthropic-operated platforms (the Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud and Microsoft Foundry). Amazon Bedrock and Google-managed Google Cloud set their own, so a model retired on the Claude API can still run there, and the reverse.

Each release can break requests or change behaviour silently

Skill 5.2What changed with each generation.

  • Opus 4.6 and Sonnet 4.6 (February 2026): a prefilled assistant reply is rejected on these and every later model; adaptive thinking recommended.
  • Opus 4.7 (April 2026): budget_tokens and non-default sampling parameters rejected; a new tokenizer (about 30% more tokens); thinking hidden by default.
  • Fable 5, Sonnet 5 and Opus 5 (June and July 2026): thinking always on (Fable) or on by default.
  • Opus 5.5, Sonnet 5.5 and Fable 5.1 (September 2026): forced tool_choice rejected; on Opus 5.5 thinking can't be disabled and default effort drops to medium; on Sonnet 5.5 disabled is replaced by between_tools.
  • Haiku 5.5 (October 2026), from Haiku 4.5: budgets, sampling and prefill rejected; thinking on by default; about 30% more tokens; a 512-token caching minimum; a price step above 100,000 tokens.
  • Fable 5.2 (November 2026), from Fable 5.1: editing system, tools or any earlier message now fails the thinking-block prefix check with a 400 ("bound to a different conversation"), so histories must be append-only; its thinking blocks are readable only by Fable 5.2 and Mythos 5.2; the older computer_20251124 tool is rejected outside Bedrock; and a Fable 5.2 executor needs a Fable 5.2 or Mythos 5.2 advisor. It's also cheaper per token than Fable 5.1.

Some changes show up with no error at all. On Fable 5.2, a prompt line such as "answer directly without deliberating" no longer stops thinking at medium effort and above, long tasks sometimes end with a list of remaining work, and style rules are followed more literally. A lower default effort, a leading thinking block that breaks content[0].text, and higher token counts are similar silent changes. Only a regression evaluation catches these.

Switch models only after a regression run, a shadow period and a planned cut-over

Skill 5.2Measuring before moving a route to a new model or effort level.

Anthropic calls a good evaluation set "the most important step" in choosing or changing a model. Its measurement method: pull tasks from production logs weighted like real traffic, write an outcome check for each, record cost per task beside the score, baseline each tier across effort levels, then run the winner in shadow on a slice of traffic before cutting over, and keep the suite running afterwards.

regression_check.py (Python, anthropic SDK) 
"""Regression check before moving a route to another model or effort level."""
import anthropic

client = anthropic.Anthropic()

# USD per million input / output tokens. Check the pricing page; Haiku 5.5 costs more above 100,000 tokens.
PRICES = {
    "claude-haiku-5-5": (0.10, 0.50),
    "claude-sonnet-5-5": (2.00, 10.00),
    "claude-opus-5-5": (4.00, 20.00),
}

SYSTEM = "Label the ticket as one of: returns, sizing, shipping, other. Reply with the label only."

# Real tickets, weighted like production traffic, with the label the support team agreed on.
GOLDEN = [
    ("Where is order 10482? Tracking hasn't moved since Monday.", "shipping"),
    ("My trail shoes are a size too small, can I swap them?", "sizing"),
    ("The stove arrived dented. I want my money back.", "returns"),
    ("Do you sponsor local hiking clubs?", "other"),
]


def score(model: str, effort: str) -> tuple[float, float]:
    passed, cost = 0, 0.0
    for ticket, expected in GOLDEN:
        response = client.messages.create(
            model=model,
            max_tokens=1024,
            output_config={"effort": effort},
            system=SYSTEM,
            messages=[{"role": "user", "content": ticket}],
        )
        label = "".join(b.text for b in response.content if b.type == "text").strip().lower()
        passed += label == expected
        price_in, price_out = PRICES[model]
        # Failed tickets still cost money, so they count in the total.
        cost += (response.usage.input_tokens * price_in + response.usage.output_tokens * price_out) / 1_000_000
    return passed / len(GOLDEN), cost / max(passed, 1)  # pass rate, cost per passed ticket


def safe_to_switch(current: tuple, candidate: tuple, max_drop: float = 0.0) -> bool:
    base_rate, base_cost = score(*current)
    new_rate, new_cost = score(*candidate)
    print(f"current   {current}: {base_rate:.0%} at ${base_cost:.5f} per passed ticket")
    print(f"candidate {candidate}: {new_rate:.0%} at ${new_cost:.5f} per passed ticket")
    return new_rate >= base_rate - max_drop


if __name__ == "__main__":
    ok = safe_to_switch(("claude-sonnet-5-5", "medium"), ("claude-haiku-5-5", "low"))
    print("switch" if ok else "keep the current route")
  1. Read the target's what's-new page and migration guideThey're cumulative, with a section for each starting model.
  2. Change the ID and remove what the target rejectsBudgets, the wrong way of turning thinking off, sampling parameters, prefill, forced tool_choice, old tool versions, history edits on Fable 5.2.
  3. Set effort explicitly and sweep itDefaults and calibration change between releases.
  4. Recount tokens and re-baseline cost and latencyThe tokenizer and thinking both move the numbers.
  5. Run the regression suiteCompare pass rate, edge cases and cost per passed task against the current pinned model; decide the allowed drop in advance.
  6. Shadow, then cut overRun the new model on a share of traffic, compare production metrics, switch fully well before the old model's retirement date, and keep the suite in CI for the next release.

Key takeaways

  • Fable 5.2 (highest capability, $8/$40), Opus 5.5 (the default starting point, $4/$20), Sonnet 5.5 (speed plus capability, $2/$10), Haiku 5.5 (lowest latency and price). Mythos 5.2 is Fable for verified organizations. Escalate to Fable only when Opus at higher effort falls short.
  • Check binding constraints first: zero data retention excludes Fable and Mythos; forced tool use excludes Fable 5.2, Opus 5.5 and Sonnet 5.5; thinking off only on Haiku and Sonnet 5.5; fast mode and features vary by model and platform.
  • Tune effort before switching models; start efficiency-first (Haiku) or capability-first (Opus); justify with cost per completed task and a score-against-spend curve.
  • Model IDs are pinned snapshots; models go active, legacy, deprecated, retired, with at least 60 days' notice; partner platforms keep their own dates.
  • Every release brings breaking and silent changes (prefill, budgets, sampling, tokenizer, forced tool use, thinking defaults, Fable 5.2's append-only history). Plan the move with the migration guide, an effort sweep, a regression suite and shadow traffic.
