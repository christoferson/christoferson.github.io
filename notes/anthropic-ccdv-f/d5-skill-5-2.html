Overview

Skill 5.2

Technical Fundamentals (6.1% of the exam): "Foundational technical concepts supporting AI application development, including basic engineering practices (integrating with SDKs that wrap REST APIs, websockets)."

The REST API itself, status codes, retries, rate limits and async calls are covered in skill 2.4, and streaming events in skill 2.3. This page covers what's left: the SDKs as products, WebSockets, and the basic practices around them.

Sources: Anthropic's client SDK, middleware, migration and OpenAI compatibility documentation, the Claude Code MCP, tools, IDE and Agent SDK documentation, and the release notes, checked on 8 November 2026 and paraphrased; the WebSocket and server-sent events standards (RFC 6455 and the WHATWG HTML standard) for the general comparison. Running example. The shop's backend calls Claude to write product blurbs, and the team wants one well-configured client for the whole service, logs that help support, and unit tests that don't need an API key.

The official SDKs

Skill 5.2Anthropic's client libraries and where they sit.

Anthropic publishes client SDKs in seven languages (Python, TypeScript, C#, Go, Java, PHP and Ruby) plus a command-line tool, ant (since April 2026). As of November 2026 the latest versions are Python 2.6.0, TypeScript 1.6.0, C# 13.6.0, Go 2.7.0, Java 3.6.0, PHP 1.6.0, Ruby 2.6.0 and ant 2.7.1. They cover the Messages API, batches, files, Managed Agents and most of the Admin API, with typed interfaces, streaming, retries, error handling and OpenTelemetry tracing. Two further "libraries", an OpenAI SDK compatibility layer and an Apple Swift package, expose Claude through other frameworks' interfaces but aren't general-purpose clients.

Each SDK major version sends one API version. The October 2026 majors (Python 2.0, TypeScript 1.0 and their counterparts) switched to API version 2026-10-21, send the key as Authorization: Bearer, accept only one credential per client, and moved from the MIT to the Apache 2.0 licence. Above the client SDKs sit higher-level options that run the agent loop for you: the Claude Agent SDK (which runs Claude Code as a subprocess, talking to it over standard input and output), Claude Code itself, and Claude Managed Agents.

What an SDK does for you

Skill 5.2The features you'd otherwise write yourself.

  • Credentials from the environment. Anthropic() reads ANTHROPIC_API_KEY; the docs suggest a .env file so the key stays out of source control. A client holds one credential: passing two is an error.
  • Typed requests and responses. In Python, responses are Pydantic models with .to_json() and .to_dict(); unknown fields are kept rather than dropped.
  • Raw responses. client.messages.with_raw_response.create(...) gives you the HTTP headers (rate-limit counters, request ID) and .parse() returns the normal message. Errors still raise typed exceptions.
  • Request IDs. Every response object has _request_id (public despite the underscore); log it.
  • Pagination, streaming helpers and the tool runner (beta), plus a beta namespace that sends the right beta headers.
  • Middleware. Functions passed as Anthropic(middleware=[...]) run before and after each request, for logging, custom retries or a built-in refusal fallback.
  • Logging and tracing. ANTHROPIC_LOG=debug turns on the SDK's own logs; if your application registers an OpenTelemetry tracer, the SDKs emit a span per request (since October 2026, in beta).
  • Platform clients. Separate classes for each cloud (AnthropicBedrockMantle, AnthropicVertex, AnthropicFoundry, AnthropicAWS, AnthropicGoogleCloud) handle their authentication and URLs (skill 2.3).

Python SDK 2.x uses httpx2. Since Python SDK 1.0 (August 2026), the SDK uses httpx2, a compatible fork of httpx. A custom HTTP client must come from anthropic.DefaultHttpxClient (passing a plain httpx client raises an error, and a raw httpx2 client loses the SDK's default timeouts and limits). Mocking tools that patch httpx, such as respx, don't see the SDK's requests unless you call httpx2.alias_httpx() first.

SSE and WebSockets

Skill 5.2Two ways to push data from server to client.

Server-sent events (defined in the HTML standard) are one-way: the server streams text events over an ordinary HTTP response with the text/event-stream content type, and clients reconnect automatically and can resume from the last event ID. Input travels in separate HTTP requests. Because it's plain HTTP, SSE passes through ordinary proxies and load balancers.

WebSockets (RFC 6455) are two-way: an HTTP request asks to upgrade the connection (101 Switching Protocols), and from then on both sides send text or binary frames over the same connection, using ws:// or, over TLS, wss://. There's no built-in resume, so the application handles reconnecting and heartbeats.

The Claude API uses SSE: a request goes up as a POST and the response streams down. Managed Agents follow the same split, with events streamed down over SSE and new events sent up with POST.

The Claude API has no WebSocket interface. The guide's mention of "websockets" next to SDKs can suggest otherwise, but Anthropic's API documentation has no WebSocket, real-time or voice endpoint: streaming is server-sent events. The Agent SDK's "streaming input mode" isn't a WebSocket either; it's an in-process stream of messages to a local Claude Code subprocess.

Where WebSockets appear

Skill 5.2WebSockets in the tooling around the API.

  • MCP servers in Claude Code can use "type": "ws", which suits a server that pushes events without being asked. They can only be added as JSON (in .mcp.json or with claude mcp add-json; --transport ws is rejected), authenticate with headers only (no OAuth), and drop the connection on a single message over 16 MiB. WebSocket isn't one of MCP's standard transports, which are stdio and Streamable HTTP; for a server that only answers requests, the docs recommend HTTP.
  • The Monitor tool in Claude Code can watch a WebSocket and treat each text frame as an event (opening one needs approval).
  • Internal plumbing: the VS Code and JetBrains integrations talk to the CLI over a local ws:// connection, and voice dictation and some hosted features use WebSockets too. These aren't things you configure.
.mcp.json with a WebSocket and an HTTP server (JSON) 
{
  "mcpServers": {
    "stock-events": {
      "type": "ws",
      "url": "wss://mcp.gear-shop.example.com/stock",
      "headers": {
        "Authorization": "Bearer ${STOCK_MCP_TOKEN}"
      }
    },
    "orders": {
      "type": "http",
      "url": "https://mcp.gear-shop.example.com/orders"
    }
  }
}

The stock server pushes stock-level changes, so it uses a WebSocket; the orders server only answers requests, so it uses HTTP, which also allows OAuth. The token comes from the shop's own variable name: Anthropic credential variables such as ANTHROPIC_API_KEY expand to nothing in a remote server's headers, by design.

A shared client

Skill 5.2Configuring one client well and reusing it.

shop_ai.py (Python, anthropic SDK) 
# shop_ai.py - one shared Claude client for the whole gear-shop backend
import logging

import anthropic
import httpx2

log = logging.getLogger("shop_ai")

MODEL = "claude-haiku-5-5"


def make_client(**overrides) -> anthropic.Anthropic:
    # The key comes from ANTHROPIC_API_KEY in the environment, never from code.
    # Build this once at startup and reuse it: the client keeps a pool of open connections,
    # so creating a new client per request throws that away.
    settings = {
        "timeout": httpx2.Timeout(30.0, connect=5.0),  # the default is 10 minutes
        "max_retries": 3,                              # retries 408, 409, 429 and 5xx with backoff
    }
    settings.update(overrides)  # tests pass a mock http_client here
    return anthropic.Anthropic(**settings)


def describe_product(client: anthropic.Anthropic, product: dict) -> str:
    # with_raw_response gives the HTTP headers as well as the parsed Message.
    raw = client.messages.with_raw_response.create(
        model=MODEL,
        max_tokens=200,
        messages=[{
            "role": "user",
            "content": f"Two-sentence shop blurb for {product['name']} ({product['weight_kg']} kg).",
        }],
    )
    message = raw.parse()  # the same object messages.create() returns

    # Log the request ID: support asks for it when a call misbehaves. Never log the key.
    log.info(
        "sku=%s request_id=%s tokens_left=%s",
        product["sku"],
        raw.headers.get("request-id"),
        raw.headers.get("anthropic-ratelimit-tokens-remaining"),
    )
    return "".join(b.text for b in message.content if b.type == "text")
  • One client, reused. Each SDK client owns its own pool of connections; creating one per request discards it. (The docs don't say "create one client" in so many words; it follows from how the client manages connections.)
  • Shorter timeouts on interactive paths; the default of 10 minutes suits long jobs, not a web request.
  • Idempotent side effects. The SDK retries requests automatically and the API has no idempotency key, so make your own actions safe to repeat, for example by keying them on the order ID or the tool call ID.
  • Keys stay server-side. The TypeScript SDK refuses to run in a browser unless you set dangerouslyAllowBrowser, which would expose the key; call Claude from your backend instead.

Testing without the network

Skill 5.2Unit tests that check what you send, with no key and no cost.

test_shop_ai.py (Python, pytest) 
# test_shop_ai.py - unit test with a fake HTTP layer; no network, no API key
import json

import httpx2
from anthropic import DefaultHttpxClient

import shop_ai

FAKE_REPLY = {
    "id": "msg_test",
    "type": "message",
    "role": "assistant",
    "model": "claude-haiku-5-5",
    "content": [{"type": "text", "text": "Light, roomy and quick to pitch."}],
    "stop_reason": "end_turn",
    "stop_sequence": None,
    "usage": {"input_tokens": 20, "output_tokens": 9},
}


def test_describe_product_sends_expected_body(monkeypatch):
    monkeypatch.setenv("ANTHROPIC_API_KEY", "test-key")
    seen = []

    def handler(request: httpx2.Request) -> httpx2.Response:
        seen.append(request)  # keep it so the test can inspect it
        return httpx2.Response(200, json=FAKE_REPLY, headers={"request-id": "req_test123"})

    client = shop_ai.make_client(
        max_retries=0,  # a test should fail fast, not back off
        http_client=DefaultHttpxClient(transport=httpx2.MockTransport(handler)),
    )
    text = shop_ai.describe_product(client, {"sku": "TENT-2P", "name": "Ridgeline 2-person tent", "weight_kg": 1.9})

    assert text == "Light, roomy and quick to pitch."
    request = seen[0]
    assert request.url.path == "/v1/messages"
    body = json.loads(request.content)
    assert body["model"] == "claude-haiku-5-5"
    assert "Ridgeline 2-person tent (1.9 kg)" in body["messages"][0]["content"]
    # The SDK adds the auth and version headers for you.
    assert request.headers["authorization"] == "Bearer test-key"
    assert request.headers["anthropic-version"] == "2026-10-21"

Injecting a mock transport keeps the SDK's real request building, headers and error handling in the test, which is more faithful than replacing the client with a fake object. Set max_retries=0 in tests so failures surface immediately.

The OpenAI compatibility layer

Skill 5.2Calling Claude through OpenAI's SDK, and its limits.

Since February 2025 you can point an official OpenAI SDK at https://api.anthropic.com/v1/ with a Claude key and model ID. Anthropic describes it as stable but "primarily intended to test and compare model capabilities", not a long-term production solution. It ignores strict on functions, has no prompt caching, returns no thinking, merges system and developer messages into one system prompt, and silently ignores many OpenAI fields. It's only on the Claude API, not the cloud platforms. For full features, use Anthropic's own SDK.

Key takeaways

  • Seven official client SDKs plus the ant CLI; each SDK major sends one API version. The October 2026 majors use 2026-10-21, Bearer auth, one credential per client and Apache 2.0.
  • SDKs add environment credentials, typed models, raw responses with headers, request IDs, pagination, middleware, logging, tracing and per-cloud clients. Python 2.x needs httpx2-based HTTP clients.
  • The Claude API streams over SSE (one-way, over HTTP); it has no WebSocket endpoint. WebSockets appear in Claude Code's ws MCP servers (JSON-only, header auth), the Monitor tool and internal plumbing.
  • Practices: one shared, reused client; shorter timeouts on interactive paths; idempotent side effects; keys only on the server; log request IDs, never keys.
  • Test with a mock transport and max_retries=0. The OpenAI compatibility layer is for testing, not production.
