The current models

Skill 5.3What each model is for, in Anthropic's terms.

ModelBest for (Anthropic's guidance)
Claude Fable 5.1 (claude-fable-5-1), $10 / $50The highest capability: demanding reasoning and long-horizon agent work, such as sessions that run for hours or research carried through to a finished document. Slowest.
Claude Opus 5.5 (claude-opus-5-5), $4 / $20Complex agentic coding and enterprise work: long autonomous coding, large refactors, vision-heavy workflows, computer use. Anthropic's suggested starting point for most workloads.
Claude Sonnet 5.5 (claude-sonnet-5-5), $2 / $10"The best combination of speed and intelligence" for everyday coding, data analysis, content and tool use. Fast.
Claude Haiku 5.5 (claude-haiku-5-5), from $0.10 / $0.50The lowest latency and price: high-volume classification, extraction and routing, real-time applications, subagent tasks. Prompts over 100,000 tokens cost $0.50 / $2.50.

Prices are per million input / output tokens. All four have a 1M-token context window, up to 128,000 output tokens, a June 2026 knowledge cutoff, image input, multilingual support and tool use. Earlier models (Fable 5, Opus 5 and 4.x, Sonnet 5 and 4.6, Haiku 4.5) remain available as legacy models. To check capabilities in code rather than from memory, the Models API reports each model's limits, thinking options and model line.

Fable and Mythos

Skill 5.3The two families the exam guide doesn't mention.

Fable is a tier above Opus and Anthropic's most capable model open to all customers (Fable 5 launched in June 2026, Fable 5.1 in September). Mythos is the same model with different safeguards, available only to organizations verified through Anthropic's programs, such as its Cyber Verification Program; it grew out of the Mythos Preview released for defensive cybersecurity work under Project Glasswing in April 2026. Both require 30-day data retention, so they aren't available under zero data retention without Anthropic's explicit approval, and Fable's thinking is always on.

Fable is an escalation, not a default. On an Anthropic coding benchmark subset, Fable 5.1 at high effort cost about US$1.19 per solved task against $0.21 for Opus 5.5 at medium effort, for a similar score. The guidance is to move up to Fable only when evaluations on Opus 5.5 at higher effort still fall short.

Differences that matter in code

Skill 5.3Thinking and effort behave differently on each model.

The guide lists "adaptive thinking support" as a capability to compare, but every current model now uses adaptive thinking. What actually differs:

  • Turning thinking off: impossible on Opus 5.5 and Fable 5.1; on Sonnet 5.5, send thinking: {"type": "between_tools"} (no up-front thinking, at effort high or below), and disabled is rejected; on Haiku 5.5, disabled works at effort high or below.
  • Default effort: medium on Opus 5.5 and Haiku 5.5, high on Fable 5.1 and Sonnet 5.5. A request that omits effort after moving from Opus 5 to Opus 5.5 silently runs a level lower, so set it explicitly.
  • Forced tool use (tool_choice any or a named tool) is rejected on Fable 5.1, Opus 5.5 and Sonnet 5.5, but still accepted on Haiku 5.5.
  • Fast mode is available only on Opus 5.5 among the current models.
  • Cache-read prices differ: 0.1 times the input price on Haiku 5.5, 0.05 on Opus 5.5 and Sonnet 5.5, 0.025 on Fable 5.1.

Quality, latency and cost

Skill 5.3The levers, and where to start.

The levers are the model tier, effort, thinking (where it can be limited), fast mode (more speed for double the price), the Batch API (half price, slower), and prompt caching. Anthropic's choosing-a-model page says tuning effort is "often a better lever than switching models", and describes two starting approaches:

  • Efficiency-first: start on Haiku 5.5, test, and upgrade only where you find a specific capability gap. Suits prototypes, tight latency, cost-sensitive and high-volume simple tasks.
  • Capability-first: start on Opus 5.5, tune the prompts, then lower effort or move to a cheaper model over time; move to Fable 5.1 only if evaluations at xhigh or max still fall short. Suits complex reasoning, high accuracy needs and autonomous agents.

Anthropic's cost-optimization page shows why effort comes first. On its coding benchmark subset, Opus 5.5 at low effort solved 87.4% at about $0.12 per solved task, roughly matching Sonnet 5.5 at high (87.6% at $0.11); Opus 5.5 at medium reached 92.8% at $0.21. Its suggested order: sweep effort on your current model first (most workloads stop there), then price the stronger model at low effort, and add a second model only if the pair beats the single model's whole cost-versus-score curve. Judge cost per completed task, not per request: a cheap model that needs retries can cost more.

Routing and multi-model patterns

Skill 5.3Using different models for different jobs.

router.py (Python, anthropic SDK) 
"""Pick a Claude model and effort level for each kind of shop task."""
from dataclasses import dataclass

import anthropic


@dataclass(frozen=True)
class Route:
    model: str
    effort: str       # "low", "medium", "high", "xhigh" or "max"
    max_tokens: int   # covers thinking plus the reply


# One entry per task type. Change a route here, then re-run your evaluations.
ROUTES = {
    # Tagging a ticket: high volume, a short label, so the cheapest model at low effort.
    "classify": Route("claude-haiku-5-5", "low", 1024),
    # Replies to customers: good writing, quick turnaround.
    "reply": Route("claude-sonnet-5-5", "medium", 4096),
    # Disputed returns: policy, photos and order history weighed together.
    "dispute": Route("claude-opus-5-5", "high", 16000),
}

client = anthropic.Anthropic()


def run(task_type: str, system: str, user_text: str) -> str:
    route = ROUTES[task_type]
    response = client.messages.create(
        model=route.model,
        max_tokens=route.max_tokens,
        # Effort lives inside output_config. Set it every time: the default is "medium"
        # on Opus 5.5 and Haiku 5.5 but "high" on Sonnet 5.5.
        output_config={"effort": route.effort},
        system=system,
        messages=[{"role": "user", "content": user_text}],
        # No thinking, temperature or prefill here: current models think adaptively
        # by default and reject the rest.
    )
    if response.stop_reason == "refusal":
        raise RuntimeError(f"Declined: {response.stop_details}")
    # Thinking blocks can come first, so pick the text blocks by type.
    return "".join(b.text for b in response.content if b.type == "text")


if __name__ == "__main__":
    print(run("classify",
              "Label the ticket as one of: returns, sizing, shipping, other. Reply with the label only.",
              "My trail shoes are a size too small, can I swap them?"))

These routes follow the docs' guidance (Haiku 5.5 at low effort for simple high-volume work, Sonnet 5.5 at medium or low for conversation, Opus 5.5 for complex judgement) but are a starting point to tune with evaluations, not an official mapping. The docs also suggest trying a single model at different effort levels first, which keeps one prompt cache, since caches are per model.

  • Advisor tool (beta since April 2026): a cheaper "executor" model runs the work and consults a stronger "advisor" model on hard decisions, for work that's difficult only in places. Anthropic's own measurements were mixed (sometimes a small gain for about twice the cost, sometimes worse), so measure on your tasks.
  • Orchestrator and workers: a frontier model plans and combines while cheaper models do the pieces. In Anthropic's tests it paid off mainly for routine work with a long tail of cost, and for work too large for one context window.
  • Refusal fallback: a beta option (fallbacks) reruns a refused request on a recommended model; not available for Haiku 5.5.

Switching models mid-conversation has costs. Each model has its own cache, and thinking blocks produced by one model can't be read by another, so they're dropped when a router or fallback hands a conversation to a different model.

Breaking changes between releases

Skill 5.3What changed with each generation.

  • Claude 4 and 4.1 (2025): a new refusal stop reason; thinking returned as a summary, with the full reasoning encrypted.
  • Opus 4.6 and Sonnet 4.6 (February 2026): a prefilled assistant reply is rejected, on these and every later model; adaptive thinking recommended; effort generally available.
  • Opus 4.7 (April 2026): budget_tokens rejected; non-default temperature, top_p and top_k rejected; a new tokenizer (roughly 30% more tokens for the same text); thinking hidden ("omitted") by default; high-resolution images using up to about three times as many tokens.
  • Opus 4.8 (May 2026): mid-conversation system messages added.
  • Fable 5, Sonnet 5 and Opus 5 (June and July 2026): thinking always on (Fable) or on by default (Sonnet 5, Opus 5).
  • Fable 5.1 (September 2026): forced tool_choice rejected; thinking blocks tied to the model and to an unchanged conversation.
  • Opus 5.5 (September 2026): thinking can't be disabled; default effort drops to medium; forced tool_choice rejected; the older computer-use tool version rejected; text between tool calls moves into thinking blocks, so a progress display can go quiet without an error.
  • Sonnet 5.5 (September 2026): disabled replaced by between_tools; forced tool_choice rejected; effort levels recalibrated.
  • Haiku 5.5 (October 2026), compared with Haiku 4.5: budgets, sampling parameters and prefill rejected; thinking on by default; about 30% more tokens; a 512-token minimum for caching (down from 4,096); a price step above 100,000 tokens.
  • API version 2026-10-21: sampling parameters removed for every model, and new SDK majors send this version by default.

A model swap is never just a string change. Even when nothing errors, the new tokenizer raises token counts, always-on thinking uses more output and needs room in max_tokens, hidden thinking blanks a "show reasoning" display, a leading thinking block breaks code that reads content[0].text, and a lower default effort changes quality.

Switching models safely

Skill 5.3A checklist drawn from Anthropic's migration guides.

  1. Read the target model's what's-new page and migration guideThe guides are cumulative, with a section for each starting model.
  2. Change the model ID and remove what the target rejectsbudget_tokens, the wrong way of disabling thinking, sampling parameters, prefill, forced tool_choice, old tool versions.
  3. Set effort explicitly and run a fresh effort sweepDefaults and calibration change between releases.
  4. Handle thinkingRead content blocks by type, pass thinking blocks back unchanged, leave room in max_tokens, and set a display mode if users see reasoning.
  5. Recount tokens and re-baseline cost and latencyUse token counting on the new model; the tokenizer and thinking both change the numbers.
  6. Handle refusalsCheck stop_reason and stop_details.
  7. Check feature availabilityFast mode, advisor pairings, per-message effort and your platform.
  8. Run the evaluation suite on real prompts and dataCompare accuracy, edge cases and cost per completed task; then run the new model on a slice of traffic before switching over.

The choosing-a-model page calls a good evaluation set "the most important step". And keep watching the deprecations page: models retire with at least 60 days' notice (skill 2.2).

Key takeaways

  • Fable 5.1 (highest capability), Opus 5.5 (complex agentic and enterprise work, the default starting point), Sonnet 5.5 (speed plus intelligence), Haiku 5.5 (lowest latency and price; dearer above 100,000 tokens). Mythos is Fable with different safeguards, for verified organizations.
  • All current models think adaptively; they differ in whether thinking can be turned off, default effort (medium on Opus 5.5 and Haiku 5.5), forced tool use and fast mode.
  • Tune effort before switching models; start efficiency-first (Haiku) or capability-first (Opus); judge cost per completed task.
  • Route by task type and keep each route on one model where possible; advisor and orchestrator patterns pay off only in specific cases.
  • Each release brings breaking changes (prefill, budgets, sampling, tokenizer, forced tool use, thinking defaults). Migrate with the guides, re-sweep effort, recount tokens and re-run evaluations.
