Overview

Skill 2.6

Configuration Management (4.1% of the exam): "Configuration management for Claude system components, including CLAUDE.md files, settings.json, model version pinning, prompt versioning, and plugin dependencies."

Each of the five items is a way configuration can drift between people, machines or releases. This page covers how to control each one. CLAUDE.md is covered in depth in the CCAR-F notes (CLAUDE.md hierarchy), and installing plugins in skill 2.5.

Sources: the Claude Code documentation (settings, settings reference, permissions, managed settings, model configuration, memory, plugin reference, dependencies, marketplaces and loading), the Agent SDK reference, and Anthropic's model IDs, deprecations, versioning, Managed Agents and release-notes pages, checked on 8 November 2026 against Claude Code 2.1.303 and paraphrased. The JSON was validated and the Python module was run.

Running example. The shop's developers share one repository with Claude Code settings and two internal plugins, and the order-help assistant in production must keep running the exact model and prompt that passed its evaluations.

Settings files and precedence

Skill 2.6Where Claude Code's settings live, and which wins.

From highest priority to lowest:

  1. Managed settingsSet by the organization (a managed-settings file, device management, or the claude.ai admin console). Nothing below can override a managed key.
  2. Command line--settings <file-or-json>, for one session.
  3. Local project.claude/settings.local.json: yours, for this project, not committed.
  4. Shared project.claude/settings.json: committed, so the whole team gets it.
  5. User~/.claude/settings.json: yours, for every project.
  • Lists merge. permissions.allow rules from every file apply together, and env merges variable by variable, rather than one file replacing another.
  • Deny wins everywhere. Rules are checked deny, then ask, then allow, and a tool denied at any level can't be allowed by another. An allow in your local file doesn't beat an ask rule from the project file.
  • Trust gates some keys. In a committed file, allow rules, extra directories, plugin marketplaces and most env values apply only after each person trusts the folder; deny and ask rules apply immediately. Some settings never apply from a repository at all (for example, auto or bypassPermissions as the default mode).
  • Strict JSON. A comment or trailing comma breaks the file (and in -p mode, a broken file is silently skipped). Add "$schema": "https://json.schemastore.org/claude-code-settings.json" for editor validation.

~/.claude.json is a separate file Claude Code writes itself (account details, MCP servers, per-project trust), not one of these settings files. /config changes a few personal options; there's no claude config command in current versions, so older instructions that use claude config set are out of date.

A shared and a local file

Skill 2.6What to commit, and what to keep to yourself.

.claude/settings.json (committed, JSON) 
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(pnpm run lint)", "Bash(pnpm run test *)", "Bash(git diff *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(curl *)"]
  },
  "env": {
    "SHOP_ENV": "dev",
    "SHOP_API_BASE": "http://localhost:8080"
  },
  "extraKnownMarketplaces": {
    "shop-tools": {
      "source": {"source": "github", "repo": "example-shop/claude-plugins", "ref": "stable"},
      "autoUpdate": false
    }
  },
  "enabledPlugins": {
    "catalog-lint@shop-tools": true,
    "order-api-helper@shop-tools": true
  }
}
.claude/settings.local.json (not committed, JSON) 
{
  "model": "claude-opus-5-5",
  "permissions": {
    "allow": ["Bash(docker compose up *)"]
  },
  "env": {
    "SHOP_API_BASE": "http://localhost:9090"
  },
  "enabledPlugins": {
    "order-api-helper@shop-tools": false
  }
}

For this developer, the allow lists combine into four rules; SHOP_API_BASE is 9090 (local beats shared) while SHOP_ENV still comes from the shared file; one plugin is switched off for them alone; and the shared deny rules still beat any local allow. The marketplace is pinned to the stable branch with automatic updates off, so plugin changes arrive only when someone runs an update. Claude Code adds settings.local.json to your global Git excludes when it creates the file; if you create it by hand, add it to .gitignore yourself.

Enforce in settings, guide in CLAUDE.md. The docs separate the two: CLAUDE.md is instructions Claude reads, settings are configuration Claude Code enforces. "Never read .env" belongs in a deny rule (or, for an organization, a managed deny rule), not only in CLAUDE.md. Note that Bash rules match command text, so they aren't a security boundary on their own; pair them with the sandbox.

CLAUDE.md in brief

Skill 2.6Instruction files as part of configuration.

CLAUDE.md files exist at managed, user (~/.claude/CLAUDE.md), project (./CLAUDE.md or ./.claude/CLAUDE.md, committed) and local (./CLAUDE.local.md, add it to .gitignore) levels, plus subfolder files loaded when Claude works there. They're combined rather than overriding each other, can import other files with @path, and can be split into .claude/rules/. For configuration management, the point is to treat the committed files like code: review changes in pull requests, keep personal preferences out of the shared file, and use claudeMdExcludes in a monorepo to skip other teams' files. The CCAR-F notes cover the hierarchy in depth (task 3.1).

Pinning the model

Skill 2.6Making sure the model that passed testing is the one that runs.

  • On the API, the ID is the pin. "Every Claude model ID is a pinned snapshot, including the dateless IDs used from the 4.6 generation on": claude-sonnet-5-5 will always be the same model, and updates ship under new IDs. Only older short aliases (such as claude-sonnet-4-5) move to the newest dated snapshot. A pinned ID still retires eventually, with at least 60 days' notice (skill 2.2).
  • Pin the SDK too. The SDK's major version decides the anthropic-version header it sends; Python SDK 2.x sends 2026-10-21, which rejects temperature. A dependency range such as anthropic>=2,<3 pins the API version as well.
  • In Claude Code, aliases move. opus, sonnet and haiku "point to the recommended version for your provider and update over time", and they resolve differently by provider and by Claude Code version. To pin, use a full ID (claude-opus-5-5) or the ANTHROPIC_DEFAULT_OPUS_MODEL style variables. The model is chosen in this order: /model in the session, then --model, then the ANTHROPIC_MODEL variable, then the model setting.
  • Managed control. A managed model is only a starting default; to restrict what people can choose, use availableModels (with enforceAvailableModels).
  • Cloud platforms. The docs say to pin model versions before rolling out Claude Code on Bedrock, Google Cloud or Foundry, where the default for an alias may lag or not be enabled; modelOverrides maps Anthropic IDs to provider-specific IDs such as inference profiles.
  • Agent SDK. Set model in ClaudeAgentOptions; otherwise an SDK application inherits whatever model the machine's settings specify, since setting sources load by default.

Versioning prompts

Skill 2.6Treating prompts as versioned, tested artefacts.

Anthropic no longer offers a prompt store in the Console, so prompts are versioned the way code is: as files in Git, reviewed in pull requests, with the evaluation suite run on every change (one change at a time: prompt or model), and with the prompt version logged alongside every response.

prompts/order_help/v3.meta.json (JSON) 
{
  "prompt_id": "order_help",
  "version": 3,
  "model": "claude-sonnet-5-5",
  "eval_suite": "evals/order_help/",
  "changed": "2026-11-02",
  "note": "Added sizing guidance; passed 48/50 evaluation cases"
}
shop_config.py (Python) 
"""Model and prompt configuration for the shop's order-help assistant."""

import hashlib
import json
import os
from dataclasses import dataclass
from pathlib import Path

# Pinned model ID: a fixed snapshot. Upgrading is a reviewed code change plus an evaluation run.
MODEL_ID = "claude-sonnet-5-5"

# IDs the evaluation suite has passed on. An environment override must be one of these.
APPROVED_MODELS = {"claude-sonnet-5-5", "claude-haiku-5-5"}

# Bump this in the same pull request that adds prompts/order_help/v4.md.
PROMPT_NAME = "order_help"
PROMPT_VERSION = 3

PROMPT_DIR = Path(__file__).parent / "prompts"


@dataclass(frozen=True)
class PromptConfig:
    model: str
    system: str
    prompt_version: int
    prompt_sha256: str


def load_config() -> PromptConfig:
    # Allow a staging override, but only to a model we have tested.
    model = os.environ.get("SHOP_MODEL", MODEL_ID)
    if model not in APPROVED_MODELS:
        raise ValueError(f"Model {model!r} has not passed the evaluation suite")

    folder = PROMPT_DIR / PROMPT_NAME
    text = (folder / f"v{PROMPT_VERSION}.md").read_text(encoding="utf-8")
    meta = json.loads((folder / f"v{PROMPT_VERSION}.meta.json").read_text(encoding="utf-8"))
    if meta["version"] != PROMPT_VERSION:
        raise ValueError("Prompt file and metadata versions disagree")

    digest = hashlib.sha256(text.encode("utf-8")).hexdigest()
    return PromptConfig(model, text, PROMPT_VERSION, digest)


def request_body(config: PromptConfig, question: str) -> dict:
    # Log prompt_version and prompt_sha256 with every response, so a bad answer
    # can be traced to the exact prompt and model that produced it.
    return {
        "model": config.model,
        "max_tokens": 1024,
        "system": config.system,
        "messages": [{"role": "user", "content": question}],
    }


if __name__ == "__main__":
    cfg = load_config()
    print(cfg.model, f"v{cfg.prompt_version}", cfg.prompt_sha256[:12])

Changing the system prompt also invalidates the prompt cache from the system level onwards, so expect a cache write after each prompt release. Where Anthropic does provide versioning is server-side: Claude Managed Agents store each agent configuration (model, system prompt, tools) as numbered versions, and a session can be pinned to a specific version for a staged rollout; Agent Skills in the API can also be pinned to a version.

Workbench prompts are gone. The legacy Console Workbench closed on 17 August 2026; its saved prompts, variables and evaluations weren't carried over, and the experimental prompt generate, improve and templatize APIs were retired at the same time. The Workbench became the "playground" the next day, which is for trying requests, not storing prompt versions. Material that treats the Console as a prompt version store is out of date.

Plugin versions and dependencies

Skill 2.6Controlling which plugin versions a team runs.

  • A plugin's version. If plugin.json sets version, everyone stays on that version until the string changes, however many commits are pushed. With no version anywhere, each commit counts as a new version. Pick one approach and stick to it.
  • Dependencies go in plugin.json as names or objects with a version range in npm style (~2.1.0, ^2.0). Ranges resolve against Git tags named <plugin>--v<version>, which claude plugin tag creates. Without a range, a dependency moves to whatever its marketplace publishes next. Conflicting ranges make the install fail, and dependencies from another marketplace are refused unless that marketplace is explicitly allowed.
  • Pinning the source. A marketplace entry can pin a plugin to a Git ref or a full 40-character sha; an archive source can pin a sha256.
  • Updates. Official marketplaces update automatically; third-party ones don't unless autoUpdate is on. A running session keeps the versions it loaded until /reload-plugins or a restart. claude plugin prune removes dependencies that are no longer needed.
  • Team-required plugins. List the marketplace in extraKnownMarketplaces and the plugins in enabledPlugins, in the committed project settings or, to enforce them across an organization, in managed settings (where true forces a plugin on and false blocks it). A plugin from an external source still has to be installed once on each machine.
plugins/order-api-helper/.claude-plugin/plugin.json (JSON) 
{
  "name": "order-api-helper",
  "version": "1.4.0",
  "description": "Skills and an MCP server for working with the shop's orders API",
  "dependencies": [
    {"name": "catalog-lint", "version": "~2.1.0"}
  ]
}

Key takeaways

  • Settings precedence: managed, command line, local project, shared project, user. Lists merge, deny wins at every level, and committed allow rules and marketplaces wait for folder trust. Settings files are strict JSON.
  • Commit team permissions, hooks and plugins in .claude/settings.json; keep personal overrides in settings.local.json. Enforce in settings, guide in CLAUDE.md.
  • API model IDs are pinned snapshots; pin the SDK major to pin the API version. Claude Code aliases move, so use full IDs or the alias environment variables, and restrict choices with availableModels.
  • Prompts are versioned as files in Git with evaluations and logged versions; the Console Workbench prompt store is gone; Managed Agents and Skills have server-side versions.
  • Plugin versions: a set version freezes users until it changes; dependency ranges resolve against <plugin>--v<version> tags; pin sources by ref or sha; third-party marketplaces don't auto-update.
