2.4: Integration Resilience

Finding the bug in integration code that fails or degrades: error handling that treats every failure the same, streams that break or stop early without anyone noticing, and files sent in the wrong shape. Each fix follows the API's documented error behaviour.

Overview

Skill 2.4

Integration Resilience: "Analyzing failing or degraded integration code and its error output to find the defect and select a correction consistent with documented API error semantics. Defects include mishandled streaming events and terminal-event semantics, retry and fallback logic that does not distinguish Anthropic's error classes (rate limits, overloaded, invalid request, timeout), and faulty multi-format ingestion through the Files API."

Items give code plus an error message or a log excerpt and ask what's wrong and which change fixes it. The three defect families in the guide each get a section, a corrected example and the traps behind the usual wrong answer. The request shapes themselves are in skill 2.1; diagnosing failures in model output (hallucination, format drift) rather than in the integration is Domain 4.

Sources: Anthropic's documentation on API errors, rate limits, streaming, refusals and fallback, fallback credit and the Files API, plus the anthropic Python SDK 2.10.0 source, checked on 8 and 19 November 2026 and paraphrased. The three examples were run against the SDK with a mocked API, including the failure cases; SDK behaviours stated below were observed in those runs.

Running example. The shop's back end calls Claude from a job queue: product descriptions, a gear advisor that streams long answers, and a supplier-document reader that uploads invoices, delivery-note photos and price lists.

Error classes

Skill 2.4What each status and error type means, and what it calls for.

Errors come back as JSON with an error.type, a message and a request_id (also in the request-id header; log it, because support asks for it). New type values can appear, so code must cope with ones it doesn't know.

  • Fix the request, don't retry: 400 invalid_request_error (a malformed request, an unsupported option such as forced tool_choice or prefill on current models, or a spend limit you set), 401 authentication_error, 402 billing_error, 403 permission_error, 404 not_found_error, 413 request_too_large (over 128 MB for Messages; send files separately).
  • Retry with backoff: 429 rate_limit_error (honour retry-after), 500 api_error, 529 overloaded_error (Anthropic's own code: the API as a whole is busy, not just you), and timeout_error, which can come with a 504 or a 500.
  • Retry after fixing the state: 409 conflict_error.

Three 429s that aren't "slow down". A tier's monthly spend cap returns 429 with no retry-after and an error_code of enforced_spend_limit_reached; it keeps failing until access resumes. A sharp jump in traffic can trigger a 429 under your limits (a ramp limit), so increase load gradually. And a 401 that starts "CORS requests are not allowed for this Organization" isn't a key problem: the organization (for example one with zero data retention) can't be called from a browser, so call from your back end.

What the SDK already does

Skill 2.4Retries, timeouts and typed exceptions, so you don't do them twice.

  • Retries. The SDKs retry connection errors, 408, 409, 429 and every 5xx (529 included) twice by default, with exponential backoff and jitter, honouring retry-after; the server can also say yes or no with an x-should-retry header. Change the count with max_retries on the client or per call with client.with_options(max_retries=5). 400, 401, 403, 404 and 413 are never retried.
  • Timeouts. The default is 10 minutes, and the SDK refuses non-streaming requests it expects to run longer: stream those or use batches. A client-side timeout raises APITimeoutError.
  • Typed exceptions, most specific first. In the Python SDK, OverloadedError (529) is a subclass of InternalServerError, and APITimeoutError a subclass of APIConnectionError, so an except InternalServerError placed first swallows every overload. Branch on classes and on e.type or e.error_code, never on message text.
  • Rate limits are per organization and model class (requests, input and output tokens per minute) and refill continuously, so a burst can trip a per-minute limit. A semaphore caps how many requests are open, not how many start per minute.

Don't stack retry loops. Wrapping an SDK call in your own for attempt in range(3) multiplies attempts: three of yours times three of the SDK's is nine calls, and a loop that retries every exception also re-sends 400s that can never succeed. Raise max_retries, or set it to 0 if you want to own the policy. And since POST /v1/messages has no idempotency key, make any side effect based on Claude's answer (creating a refund, say) idempotent yourself.

Retry logic that tells errors apart

Skill 2.4A corrected wrapper for the shop's job queue.

The broken version caught Exception, slept and retried three times on the same model. It re-sent invalid requests, hammered the API during a spend-cap outage, and treated a refusal as success because a refusal isn't an exception. The fix sorts every outcome into "try later" (the queue retries it) or "fix the request" (an alert, no retry):

resilient_call.py (Python, anthropic SDK) 
import logging

import anthropic

log = logging.getLogger("shop.claude")

# The SDK already retries 408, 409, 429, 5xx (529 included) and connection errors, with backoff.
# Raise its retry count here rather than wrapping calls in a second retry loop.
client = anthropic.Anthropic(max_retries=4, timeout=120.0)

PRIMARY = "claude-opus-5-5"
FALLBACK = "claude-opus-4-8"  # for refusals only: a different model, run through the same evaluations


class TryLater(Exception):
    """Transient: put the job back on the queue."""


class FixRequest(Exception):
    """Permanent: sending the same request again can't succeed."""


def ask(messages: list, model: str = PRIMARY):
    try:
        response = client.messages.create(model=model, max_tokens=2048, messages=messages)
    except anthropic.BadRequestError as e:  # 400 invalid_request_error: the request itself is wrong
        raise FixRequest(f"{e.type}: {e.message} ({e.request_id})") from e
    except anthropic.RateLimitError as e:  # still 429 after the SDK's retries
        if e.error_code == "enforced_spend_limit_reached":
            raise FixRequest("monthly spend cap reached; retrying won't help") from e
        raise TryLater("rate limited") from e
    except anthropic.OverloadedError as e:  # 529: the API as a whole is busy (subclass of InternalServerError)
        raise TryLater("overloaded") from e
    except anthropic.InternalServerError as e:  # 500 and 504, including type timeout_error
        raise TryLater(f"{e.status_code} {e.type}") from e
    except anthropic.APITimeoutError as e:  # our own timeout fired (subclass of APIConnectionError)
        raise TryLater("client timeout; stream long answers instead") from e
    except anthropic.APIConnectionError as e:
        raise TryLater("network error") from e

    if response.stop_reason == "refusal":
        # HTTP 200, so none of the handlers above see it. Retrying the same model usually refuses again.
        category = response.stop_details.category if response.stop_details else None
        if model != FALLBACK:
            log.warning("refusal (%s) on %s; retrying on %s", category, model, FALLBACK)
            return ask(messages, model=FALLBACK)
        raise FixRequest(f"refused by both models ({category})")
    return response
  • Order of the except clauses: OverloadedError before InternalServerError, APITimeoutError before APIConnectionError.
  • Overload and rate limits are different signals. A 429 is about your usage, so slow down or spread the load; a 529 is about the service, so back off and try later. Switching models on a 529 is a design choice of yours, not documented guidance; Anthropic's built-in fallback covers refusals only.
  • Timeouts. A server timeout_error or a client timeout on a long generation usually means the request should stream, not that it needs more retries.

Falling back after a refusal

Skill 2.4Retrying a declined request on another model, the documented way.

On Fable 5.x, Opus 5 and 5.5, Sonnet 5.5 and Haiku 5.5, safety classifiers can decline a request: HTTP 200, stop_reason: "refusal", and a stop_details.category. Sending the same request to the same model usually gets another refusal; another model can normally answer. There are three ways to do that:

  • Server-side fallback (beta, Claude API and Anthropic-managed Google Cloud): set fallbacks to "default" (or name up to three models) with the server-side-fallback-2026-07-01 beta header, and the API re-runs a refused request on a recommended model inside the same call. It isn't available for batches.
  • The SDK's client-side fallback middleware, on any platform.
  • A manual retry, as in the example above. Redeem the fallback credit from the refusal so you don't pay for the fallback model's cache write in full. Haiku 5.5 refusals carry no credit and have no server-side fallback.

Fallback pitfalls from the docs. Configure fallback on every request path, including retry handlers, background workers and calls made inside tool execution, which don't inherit fallbacks. Stay on the fallback model for the rest of the conversation. Count refusals and fallback-served responses as their own metrics, since dashboards built on error rates never see a 200. And branch on stop_reason, because stop_details.category can be null. In a batch, a refusal comes back as a succeeded result with stop_reason: "refusal".

Streams that fail or stop early

Skill 2.4Terminal-event semantics and recovering a broken stream.

A healthy stream ends with message_delta (carrying stop_reason and cumulative usage) and then message_stop. Three things go wrong in practice:

  • An error after the 200. An error event (for example overloaded_error) can arrive mid-stream. The status-code handling around the call never sees it, and in the Python SDK it raises a plain APIStatusError with status_code 200, not an OverloadedError: read e.type.
  • A stream that just stops. If the connection closes before message_delta and message_stop, the SDK raises nothing; the final message simply has no stop_reason. Code that treats "the loop finished" or a content_block_stop as the end of the answer ships half an answer.
  • Tool input read too early. input_json_delta events carry fragments of JSON; parse the input only at content_block_stop, or use the SDK's helpers. And ignore event types you don't recognise rather than failing on them.
stream_answer.py (Python, anthropic SDK) 
import anthropic

client = anthropic.Anthropic()

RETRYABLE = {"overloaded_error", "api_error", "timeout_error"}


def stream_answer(question: str, max_attempts: int = 3) -> str:
    received = ""
    request = question
    for _ in range(max_attempts):
        try:
            with client.messages.stream(
                model="claude-opus-5-5",
                max_tokens=8000,
                messages=[{"role": "user", "content": request}],
            ) as stream:
                for text in stream.text_stream:
                    received += text
                final = stream.get_final_message()
        except anthropic.APIStatusError as e:
            # An error event after the HTTP 200 arrives as a plain APIStatusError with status_code 200,
            # not as OverloadedError: read e.type to see which error it was.
            if e.type not in RETRYABLE:
                raise
        except anthropic.APIConnectionError:
            pass  # the connection dropped part-way
        else:
            # A stream that stops before message_delta and message_stop raises nothing:
            # the final message just has no stop_reason. Only a stop_reason means "finished".
            if final.stop_reason is not None:
                return received
        if not received:
            continue  # nothing arrived yet: send the original request again
        # Claude 4.6 and later reject a prefilled assistant turn, so the partial
        # answer goes back in a user message with an instruction to continue.
        request = (
            f"{question}\n\nYour previous response was interrupted and ended with:\n"
            f"{received}\n\nContinue from exactly where you left off."
        )
    raise RuntimeError("stream did not complete")


if __name__ == "__main__":
    print(stream_answer("I'm hiking three days in late autumn hills. What should I pack?"))

Recovery on Claude 4.6 and later keeps what arrived and sends it back in a user message with an instruction to continue; the older trick of putting the partial text in an assistant turn is a prefill, which these models reject. Only text can be resumed: a partly streamed tool call or thinking block can't be recovered, so resume from the last text block or re-run the turn.

Ingesting files

Skill 2.4Getting PDFs, images and other formats through the Files API.

The Files API (generally available, no beta header) stores an upload once and returns a file_id that requests reference. The block type has to match the file type:

  • PDF (application/pdf) and plain text (text/plain): a document block, optionally with a title, context and citations.
  • JPEG, PNG, GIF and WebP: an image block.
  • Anything else (spreadsheets, datasets): a container_upload block for the code execution tool, if Claude should analyse it with code.
  • .docx and .xlsx can't go in a document block: convert them to text, or to PDF to keep images. Files that are already text, such as .csv and .md, can be uploaded with an explicit text/plain type.
ingest_files.py (Python, anthropic SDK) 
import mimetypes
from pathlib import Path

import anthropic

client = anthropic.Anthropic()

# The content block each type needs. A type in the wrong block is a 400 error.
BLOCK_FOR = {
    "application/pdf": "document",
    "text/plain": "document",
    "image/jpeg": "image",
    "image/png": "image",
    "image/gif": "image",
    "image/webp": "image",
}
ALREADY_TEXT = {".csv", ".md", ".txt"}  # upload these with an explicit text/plain type


def upload(path: Path) -> dict:
    mime = "text/plain" if path.suffix.lower() in ALREADY_TEXT else mimetypes.guess_type(path.name)[0]
    if mime not in BLOCK_FOR:
        # .docx and .xlsx can't go in a document block: convert to PDF or text first,
        # or send them to the code execution tool in a container_upload block.
        raise ValueError(f"{path.name}: convert before uploading ({mime})")
    meta = client.files.upload(
        file=(path.name, path.read_bytes(), mime),
        expires_in_seconds=7 * 24 * 3600,  # removed automatically after a week (1 hour to 90 days)
    )
    block = {"type": BLOCK_FOR[mime], "source": {"type": "file", "file_id": meta.id}}
    if block["type"] == "document":
        block["title"] = path.name
    return block


def summarise_supplier_documents(paths: list[Path]) -> str:
    # File IDs are created and kept server-side; never accept one from an end user.
    blocks = [upload(p) for p in paths]
    response = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": blocks + [
            {"type": "text", "text": "For each document give the supplier, invoice number and total."},
        ]}],
    )
    return "".join(b.text for b in response.content if b.type == "text")


if __name__ == "__main__":
    print(summarise_supplier_documents([Path("invoice-0412.pdf"), Path("delivery-note.png"), Path("price-list.csv")]))
  • Errors to recognise: 400 for a file in the wrong block type (an image in a document block), for a file bigger than the context window, for a bad file name, for downloading a file you uploaded, or when the 1 TB organization limit is full; 404 for a file ID that doesn't exist or isn't in this workspace; 413 for a file over 500 MB.
  • Lifecycle. Files can't be edited (upload a new one), persist until deleted unless you set expires_in_seconds (1 hour to 90 days) at upload, and once expired make any request that references them fail before inference. Only files created by skills or code execution can be downloaded.
  • Scope and limits. Files belong to the workspace, so never take a file_id from a user; file operations are free, but the content is billed as input tokens on each request, and file endpoints allow about 500 requests per minute. The Files API isn't on Bedrock or Google-managed Google Cloud, and isn't covered by zero data retention.

From symptom to defect

Skill 2.4Reading the evidence the way exam items present it.

  • Logs show nine identical calls for one failed job. A hand-written retry loop around the SDK's own retries. Remove the loop and set max_retries.
  • The same 400 keeps appearing for hours. The retry policy doesn't separate client errors from transient ones. Stop retrying 4xx (apart from 409 and 429) and surface the message.
  • Every request has failed with 429 for days, with no retry-after header. The tier's monthly spend cap, not a rate limit. Backoff won't help; it clears only when access resumes, so move up a usage tier or wait.
  • An except InternalServerError handler logs "server bug" during a busy period. It's catching 529 overloads first. Put OverloadedError above it and treat overload as "try later".
  • Customers sometimes get answers that stop mid-sentence, with no error logged. The stream dropped and the code never checked stop_reason. Treat a missing stop_reason as an interruption and resume.
  • A resumed stream fails with "This model does not support assistant message prefill". The recovery puts the partial answer in an assistant turn. On 4.6 and later, send it in a user message with a continue instruction.
  • The refusal rate looks like zero, yet support tickets mention "Claude won't answer". Monitoring counts only HTTP errors; refusals are 200s. Track stop_reason: "refusal" and add a fallback.
  • Uploading a price list works, but the request fails with 400 invalid file type. An .xlsx sent in a document block. Convert it to text, or use a container_upload block with code execution.
  • A nightly job that worked last week now fails before inference for some invoices. The files were uploaded with an expiry that has passed. Re-upload them, or set the expiry to cover the job's schedule.

Key takeaways

  • Fix, don't retry: 400, 401, 402, 403, 404, 413. Retry with backoff: 429, 500, 529 and timeout_error; 409 after fixing state. The spend-cap 429 has no retry-after and won't clear by retrying.
  • The SDK retries twice by default with backoff and retry-after; don't add your own loop. Catch OverloadedError before InternalServerError and APITimeoutError before APIConnectionError.
  • Refusals are HTTP 200: retry on a different model (server-side fallbacks in beta, SDK middleware, or a manual retry with fallback credit), on every request path, and monitor them separately.
  • A stream is finished only when it has a stop_reason (from message_delta, then message_stop). Mid-stream errors arrive after the 200; resume on 4.6+ with a user message, never a prefill; tool and thinking blocks can't be resumed.
  • Files API: PDF and text in document, images in image, other data in container_upload; convert .docx and .xlsx; 500 MB per file; workspace-scoped; optional expiry; uploads can't be downloaded.
