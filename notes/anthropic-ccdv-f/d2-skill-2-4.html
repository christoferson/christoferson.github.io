Overview

Skill 2.4

Software Engineering Foundations (7.4% of the exam): "Core software engineering principles and practices, including REST APIs, JSON, asynchronous programming, version control, SDLC integration, code review, and small- and large-scale refactoring."

This is general engineering, applied to Claude: how the API behaves as an HTTP service, how the SDKs handle failures for you, how to make many calls efficiently, and how Claude Code helps with Git, reviews and refactors. The Messages API's own features (streaming, vision, caching, batches) are skill 2.3; diagnosing failures in depth is Domain 4.

The Claude API over HTTP

Skill 2.4What a raw request looks like, and what the SDKs add.

The Claude API is a REST API at https://api.anthropic.com; a message is a POST to /v1/messages with a JSON body. Other endpoints include /v1/messages/batches, /v1/messages/count_tokens, /v1/models and /v1/files.

One request with curl (shell) 
# -i prints the response headers (request-id, anthropic-ratelimit-*) before the body
curl -sS -i https://api.anthropic.com/v1/messages \
  -H "x-api-key: $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -H "content-type: application/json" \
  -d '{
    "model": "claude-haiku-5-5",
    "max_tokens": 300,
    "messages": [
      {"role": "user", "content": "Write a two-sentence shop description for the Ridgeline 2-person tent (1.9 kg)."}
    ]
  }'
  • Headers. Authentication (an API key, or a short-lived token from workload identity federation), anthropic-version and content-type: application/json are required. The API overview now lists Authorization: Bearer as the primary way to send the key and calls x-api-key a legacy fallback, though both work and the docs' own curl samples still use x-api-key.
  • Response. Every response carries a request-id header (also in error bodies as request_id): log it, because support asks for it.
  • Size. A Messages request may be up to 128 MB; larger requests get 413. Batches allow 256 MB and file uploads 500 MB; some cloud platforms set lower limits.
  • The SDKs add the headers, typed requests and responses, retries, timeouts, streaming helpers, pagination and connection management, which is why the docs recommend them over raw HTTP.

New API version, new SDK majors. API version 2026-10-21 (October 2026) removed temperature, top_p and top_k for every model, and the new major SDK versions (Python 2.0.0, TypeScript 1.0.0) send it by default and send the key as Authorization: Bearer. Code or gateways that set those sampling parameters, or that look for an x-api-key header, break on upgrade. The SDKs' licence also changed from MIT to Apache 2.0.

Errors and what to retry

Skill 2.4Reading HTTP status codes and error types.

Errors come back as JSON with a type, a message and the request ID. Roughly, client errors mean fix the request, and server errors and rate limits mean try again later:

  • Don't retry, fix: 400 invalid_request_error (bad request, or a spend limit you set yourself), 401 authentication_error, 402 billing_error, 403 permission_error, 404 not_found_error, 413 request_too_large (make the request smaller, for example by uploading files separately).
  • Retry, with backoff: 429 rate_limit_error (respect retry-after), 500 api_error, 504 timeout_error, and 529 overloaded_error, which means the API as a whole is busy. 529 isn't a standard HTTP code; it's Anthropic's own.
  • Retry after fixing the state: 409 conflict_error.

Not every 429 is worth retrying. When an organization reaches its tier's monthly spend cap, the API returns 429 with no retry-after and an error code of enforced_spend_limit_reached; retries fail until the next month. And errors can also arrive after a 200 response when streaming, as an error event in the stream, so status-code handling alone won't catch them.

Retries, timeouts and rate limits

Skill 2.4What the SDK already does, so you don't do it twice.

  • Retries. The SDKs retry connection errors, 408, 409, 429 and all 5xx (including 529) twice by default, with exponential backoff and jitter (in the Python SDK, starting around half a second and capped at 8 seconds), and they honour retry-after. Change it with max_retries on the client or client.with_options(max_retries=5) per call; 400, 401, 403, 404, 413 and 422 are never retried.
  • Timeouts. The default timeout is 10 minutes, and timeouts are retried too. The SDK refuses non-streaming requests it expects to take longer than about 10 minutes: stream those or use batches.
  • Rate limits are per organization and model class (requests, input tokens and output tokens per minute) and work like a token bucket that refills continuously, so a burst can trip a per-minute limit. Response headers report the state: anthropic-ratelimit-requests-remaining, anthropic-ratelimit-tokens-remaining and their -limit and -reset partners.
  • Idempotency. By HTTP's definition (RFC 9110), POST isn't idempotent, and the Messages API documents no idempotency key. Retrying a generation is harmless apart from cost, but if your code performs a side effect based on Claude's answer (creating a refund, say), make that step idempotent yourself.

Don't stack retry loops. Wrapping an SDK call in your own retry loop multiplies attempts: three of yours times three of the SDK's is nine calls. Raise max_retries instead, or set it to 0 if you want to own the retry policy entirely.

Asynchronous calls

Skill 2.4Running many requests at once without tripping limits.

AsyncAnthropic has the same methods as the regular client, awaited. With asyncio, one process can wait on many requests at the same time; a semaphore caps how many are open at once.

describe_catalogue.py (Python, anthropic SDK) 
# Generate short catalogue descriptions for many products at once.
import asyncio

import anthropic
from anthropic import AsyncAnthropic

# Reads ANTHROPIC_API_KEY from the environment. The SDK retries 408, 409, 429,
# 5xx and connection errors with backoff, and waits for retry-after when sent.
client = AsyncAnthropic(max_retries=4, timeout=60.0)

MAX_IN_FLIGHT = 5  # cap on requests open at the same time

PRODUCTS = [
    {"sku": "TENT-2P", "name": "Ridgeline 2-person tent", "weight_kg": 1.9},
    {"sku": "BAG-0C", "name": "Glacier 0 C sleeping bag", "weight_kg": 1.1},
    {"sku": "PACK-45", "name": "Summit 45 L backpack", "weight_kg": 1.4},
    {"sku": "STOVE-1", "name": "Canister camp stove", "weight_kg": 0.3},
    {"sku": "LAMP-H", "name": "Trail headlamp", "weight_kg": 0.1},
    {"sku": "POLE-C", "name": "Carbon trekking poles", "weight_kg": 0.5},
]


async def describe(product: dict, sem: asyncio.Semaphore) -> str:
    async with sem:  # waits here while MAX_IN_FLIGHT calls are open
        message = await client.messages.create(
            model="claude-haiku-5-5",
            max_tokens=300,
            messages=[{
                "role": "user",
                "content": f"Write a two-sentence shop description for {product['name']} ({product['weight_kg']} kg).",
            }],
        )
    return "".join(b.text for b in message.content if b.type == "text")


async def describe_safely(product: dict, sem: asyncio.Semaphore) -> dict:
    sku = product["sku"]
    try:
        return {"sku": sku, "ok": True, "text": await describe(product, sem)}
    except anthropic.RateLimitError as e:
        # Still 429 after the SDK's own retries. A monthly spend cap is also a 429,
        # with error_code "enforced_spend_limit_reached": retrying won't help.
        return {"sku": sku, "ok": False, "error": f"429 {e.error_code or 'rate_limit'}", "request_id": e.request_id}
    except anthropic.APIStatusError as e:
        # Any other 4xx/5xx, for example 400 bad request or 529 overloaded.
        return {"sku": sku, "ok": False, "error": f"{e.status_code} {e.type}", "request_id": e.request_id}
    except anthropic.APIConnectionError as e:
        # Network failure or timeout (APITimeoutError is a subclass).
        return {"sku": sku, "ok": False, "error": type(e).__name__}


async def main() -> list[dict]:
    sem = asyncio.Semaphore(MAX_IN_FLIGHT)
    results = await asyncio.gather(*(describe_safely(p, sem) for p in PRODUCTS))
    for r in results:  # gather keeps the input order
        print(r["sku"], "OK" if r["ok"] else r["error"])
    return results


if __name__ == "__main__":
    asyncio.run(main())
  • Exception order matters: RateLimitError is a subclass of APIStatusError, so catch it first; catch typed classes rather than matching message text.
  • One failure shouldn't sink the batch. asyncio.gather raises the first exception by default (without cancelling the others); catching inside each task, as here, or passing return_exceptions=True keeps the other results. asyncio.TaskGroup instead cancels the rest on the first failure.
  • A semaphore limits concurrency, not rate. Five open requests can still exceed a requests-per-minute limit if each is fast; ramp up traffic gradually.
  • Async isn't streaming, and isn't batching. Async waits on many requests at once; streaming returns one response bit by bit; for large jobs that aren't urgent, the Message Batches API is half the price (skill 2.3).

The error_code, type and request_id attributes exist on APIStatusError in the current Python SDK (2.6.0) but aren't yet in its documentation's table; on older SDKs, read e.status_code, e.body and the request-id response header.

JSON

Skill 2.4Exchanging and validating JSON safely.

The API speaks JSON in both directions, and its errors are always JSON. JSON exchanged between systems must be UTF-8 (RFC 8259), object keys should be unique, and very large integers can lose precision, since many parsers use double-precision numbers. In Python, json.loads raises json.JSONDecodeError on bad input. When you need Claude's own output as JSON, use structured outputs (output_config.format with a JSON schema) rather than asking nicely in the prompt, and still check stop_reason: a refusal or hitting max_tokens can leave output that doesn't match the schema. Prefilling the reply with { no longer works on Claude 4.6 and later models, which reject a prefilled assistant message.

Version control and CI

Skill 2.4Fitting Claude Code into Git and the delivery pipeline.

  • Branches and pull requests. Ask Claude Code to commit or "create a pr"; it uses git and gh. claude --from-pr 1234 reopens the sessions linked to a pull request.
  • Parallel work. claude --worktree <name> starts a session in its own Git worktree on a new branch, so two tasks never edit the same checkout. A fresh worktree has no installed dependencies and no ignored files; .worktreeinclude copies files such as .env.
  • CI. claude -p runs non-interactively in pipelines and hooks, and the anthropics/claude-code-action@v1 GitHub Action reviews or works on pull requests; GitLab has its own integration.
  • Versioning. Semantic versioning (MAJOR.MINOR.PATCH, a major bump for breaking changes) applies to your own packages. Anthropic's Python SDK "generally follows" it, and its major version also decides the API version it sends, so pin it in your dependencies.
  • Checks. Put the exact test, lint and type-check commands in CLAUDE.md, give Claude a pass-or-fail check, ask for the commands it ran as evidence, and protect the main branch before leaving anything unattended.

Code review

Skill 2.4Reviewing code with people and with Claude.

Good review practice is the same with or without AI: small changes, attention to design, correctness, tests, complexity and naming, and approval once a change improves the code's overall health even if it isn't perfect (Google's engineering practices). Claude Code adds several tools:

  • /code-review reviews the current changes, a branch or a pull request for correctness bugs in a fresh subagent that hasn't seen the conversation, so it isn't swayed by the reasoning that produced the code. Options include an effort level, --fix to apply findings and --comment to post them on the pull request; /review is now an alias.
  • /simplify is a cleanup pass (reuse, simpler code, efficiency); it doesn't hunt for bugs. /security-review checks the branch's changes for issues such as injection and data exposure.
  • Code Review (for Team and Enterprise plans, on GitHub) runs several agents on Anthropic's infrastructure, verifies findings to drop false positives, and posts ranked inline comments. It never approves or blocks a pull request and doesn't run your code, and it reads its REVIEW.md rules from the base branch, so a pull request can't rewrite its own review rules.

Narrow the reviewer's brief. The best-practices page warns that a reviewer asked to find problems will always find something, and fixing every finding adds needless abstraction. Say what matters ("correctness and security; skip style"), and give a read-only reviewer only Read, Grep and Glob so the limit is enforced, not just requested.

Refactoring, small and large

Skill 2.4Changing structure without changing behaviour.

Small refactors

The docs' advice: find the code to change, ask for suggestions, refactor while keeping the same behaviour, and run the tests, working "in small, testable increments". For a bug, have Claude write a failing test that reproduces it first, then fix it.

Large refactors and migrations

  • /batch <instruction> researches the codebase, splits a large mechanical change into 5 to 30 independent units and shows a plan; after approval it runs one background subagent per unit in its own worktree, and each runs the tests and opens a pull request. Example from the docs: /batch migrate src/ from JavaScript to TypeScript.
  • Scripted fan-out: loop over files with claude -p and a tight set of allowed tools, try it on a few files first, fix the prompt, then run the rest.
  • Anthropic's migration practice (its July 2026 post on large code migrations): first build a test harness that passes on the old code and fails on deliberately broken code; write down the rules; run a throwaway trial migration; process units from a resumable queue with implementing and reviewing agents; verify by compiling, smoke-testing and checking behaviour; and when the same error recurs, fix the rule and regenerate rather than hand-patching ("fix the loop, not the code").

/rewind can undo Claude's recent edits within a session, but it doesn't replace Git: commit before a large change.

Key takeaways

  • The Messages API is POST https://api.anthropic.com/v1/messages with auth, anthropic-version (now 2026-10-21) and JSON; log the request-id. New SDK majors send Authorization: Bearer and drop sampling parameters.
  • Don't retry 400, 401, 402, 403, 404 or 413; retry 429, 500, 504 and 529 with backoff; a spend-cap 429 has no retry-after and won't succeed. Streams can fail after a 200.
  • The SDK retries twice by default with backoff and a 10-minute timeout; tune max_retries instead of adding your own loop. POST isn't idempotent, so guard side effects.
  • AsyncAnthropic plus a semaphore for concurrency (not rate); catch typed errors per task; batches for non-urgent bulk work.
  • Claude Code: commits and pull requests, worktrees for parallel work, claude -p and the GitHub Action in CI; /code-review in a fresh context; /batch for large mechanical refactors.
