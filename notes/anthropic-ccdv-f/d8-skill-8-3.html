Overview

Skill 8.3

Capability Mechanism Selection: "Evaluating built-in tools, custom tools, Skills, and MCP servers for a use case, based on where the capability must live, who maintains it, and how Claude discovers and invokes it, and justifying the selection."

Exam items give a use case and ask which mechanism fits and why. The answer must follow from the three criteria the guide names. Building a custom tool is skill 8.1, building an MCP server is skill 8.2, and choosing between Claude Code's extension types (skill, plugin, hook, rule, subagent) is skill 3.2.

Ask where the capability lives, who maintains it, and how Claude finds it

Skill 8.3The guide's criteria, asked in turn.

  • Where must the capability live? Is it on the public web, in a sandbox, inside your systems behind your network and credentials, or on a user's machine? That decides who can run it.
  • Who maintains it? Anthropic, your team, or another team or vendor that owns the system. The owner should be the one who updates it, in one place.
  • How does Claude discover and invoke it?
    • A tool is called with arguments, chosen from its description.
    • A Skill is know-how Claude loads when its description matches the task.
    • An MCP server's tools are listed to Claude by the server itself.

Built-in tools, custom tools, Skills and MCP servers each suit different needs

Skill 8.3What each is, and what it suits.

  • Built-in tools: capabilities Anthropic provides. They include server tools that Anthropic runs (web search, web fetch, code execution, tool search, the MCP connector), Anthropic-schema client tools whose schema Claude is trained on but you execute (bash, the text editor, memory), and Claude Code's own file and shell tools. Nothing to build; use them whenever one fits.
  • Custom tools: a function in your application, defined in the request and executed by your code. Best when one application needs access to your own systems, with your schema, result shaping and approval steps (skill 8.1).
  • Agent Skills: a folder with a SKILL.md of instructions, plus optional reference files and scripts, that Claude loads when relevant. Best for know-how, meaning procedures, house styles and domain rules, and for deterministic helper scripts. A Skill isn't a connection to a live system.
  • MCP servers: a separate service exposing tools (and resources and prompts) over a standard protocol. Best when several clients need the same capability, or when another team owns the system: they maintain one server, and Claude Code, the Agent SDK and the API connector all use it (skill 8.2).

Justify each choice by the three questions

Skill 8.3The questions as code, and the five requests.

Take five requests to a platform team: check competitors’ prices online, let the support app look up an order, give every team’s agents live inventory data, make Claude produce monthly reports in the house style, and have Claude crunch a large sales export.

select_capability.py (Python) 
"""Choose between a built-in tool, a custom tool, a Skill and an MCP server for a use case, and say why."""


def select(u: dict) -> dict:
    """u: {"need": str, "lives": "public_web"|"sandbox"|"our_systems"|"user_machine", "maintainer": "anthropic"|"us"|"other_team",
           "kind": "action"|"know_how", "clients": int, "network": bool}"""
    why = []
    if u["lives"] in ("public_web", "sandbox") and u["maintainer"] == "anthropic":
        mech = "built-in tool"
        why += ["Anthropic already runs it (web search or fetch, code execution) or ships it (Claude Code's file tools)",
                "nothing to build or host; discovery is built in"]
    elif u["kind"] == "know_how":
        mech = "Skill"
        why += ["it is a procedure plus scripts and reference files, not a call into a live system",
                "only ~100 tokens of metadata until Claude decides it's relevant; scripts run without loading their code"]
        if u["network"]:
            why.append("note: API Skills run without network access; use Claude Code, or move the live part to a tool")
    elif u["clients"] > 1 or u["maintainer"] == "other_team":
        mech = "MCP server"
        why += ["one implementation, maintained by its owners, reused by every client (Claude Code, SDK, API connector)",
                "Claude discovers its tools from the server; names arrive as mcp__server__tool"]
    else:
        mech = "custom tool"
        why += ["one application calls one of our systems: a function in that app is the simplest thing",
                "we control the schema, the result shape and the approval step in our own code"]
    return {"need": u["need"], "mechanism": mech, "why": why}
  • Competitor prices: public web, maintained by Anthropic, so the built-in web search tool. Writing your own scraper tool would be redundant.
  • Order lookup in the support app: one app, your system, your team, so a custom tool. An MCP server would add a service to run for a single consumer.
  • Live inventory for every team: many clients, owned by the warehouse team, so an MCP server. Each team writing its own tool would duplicate the integration and drift apart.
  • Reports in the house style: know-how plus a formatting script, so a Skill. It costs about 100 tokens until it's needed, where the same instructions in a system prompt would cost tokens on every request.
  • Crunching a large export: computation in a sandbox, so the built-in code execution tool, with no handler code of yours.

Each choice is justified by the three questions, which is what exam answers have to do.

Skills load progressively, don't sync across surfaces, and have no network on the API

Skill 8.3Progressive disclosure, surfaces and limits.

  • Three levels of loading:
    • The name and description (about 100 tokens) are always in context.
    • The SKILL.md body (guidance is under 5,000 tokens) loads when Claude decides the Skill is relevant.
    • Bundled files load only if read. Scripts run without their code entering context; only their output does.
    Many Skills can be installed at little cost, and a script gives a deterministic result instead of code Claude improvises.
  • Discovery is the description: it must say what the Skill does and when to use it. The rules are 1,024 characters at most, and the name is lowercase with hyphens, up to 64 characters, and can't contain "anthropic" or "claude".
  • Surfaces don't sync:
    • Claude Code Skills are files in .claude/skills/ or ~/.claude/skills/, shareable through plugins.
    • API Skills are uploaded through /v1/skills and shared across the workspace.
    • claude.ai Skills are uploaded separately.
    A Skill made for one surface has to be added to each other surface separately.
  • Runtime: on the API, Skills run in the code execution container with no network access and no package installation. A Skill that needs live data needs a tool or MCP server for that part. In Claude Code they have the user's normal network access.
  • Trust: a Skill can direct Claude to run code and call tools, so use only Skills you wrote or got from Anthropic, and audit others like software you install. Skills aren't eligible for zero data retention.

Use API Skills through container.skills with the code execution tool

Skill 8.3container.skills plus the code execution tool.

skill_request.py (Python, anthropic SDK) 
"""Use the pre-built xlsx Skill and the shop's own custom Skill in one Messages API request, then download the file."""
import anthropic

client = anthropic.Anthropic()


def monthly_report(sales_csv: str) -> list[str]:
    response = client.messages.create(
        model="claude-opus-5-5", max_tokens=8000,
        container={"skills": [
            {"type": "anthropic", "skill_id": "xlsx", "version": "latest"},                       # pre-built
            {"type": "custom", "skill_id": "skill_01ShopReportStyle", "version": "latest"},       # uploaded via /v1/skills
        ]},
        tools=[{"type": "code_execution_20250825", "name": "code_execution"}],                    # Skills run in its container
        messages=[{"role": "user", "content": f"Build this month's sales workbook in our house style.\n<csv>{sales_csv}</csv>"}],
    )
    saved = []
    for item in response.content:                     # generated files come back as file IDs
        if item.type == "bash_code_execution_tool_result" and item.content.type == "bash_code_execution_result":
            for out in item.content.content:
                meta = client.files.retrieve_metadata(file_id=out.file_id)
                client.files.download(file_id=out.file_id).write_to_file(meta.filename)
                saved.append(meta.filename)
    return saved
  • Request: list Skills in container.skills, each with a type (anthropic for the pre-built pptx, xlsx, docx and pdf Skills, or custom), a skill_id and optionally a version, up to 20 per request. Include the code_execution_20250825 tool, because Skills run in its container.
  • Output files: generated documents come back as file_ids inside the code execution results. Download them through the Files API.
  • Multi-turn: to continue a conversation, pass the same container ID, including after a pause_turn.

Combine mechanisms when one feature needs know-how and live data

Skill 8.3Real features often use two.

  • Skill plus tool: the monthly report Skill holds the house style and a formatting script, while a custom tool or MCP server fetches the live sales figures it can't reach from the sandbox.
  • MCP plus approval: the shared inventory server exposes reads freely. Writes stay behind the calling application's approval step or hook, so that one team's server doesn't decide every client's risk.
  • Cost check: every enabled tool, MCP server and Skill adds something to every request (definitions, descriptions, metadata). Enable only what each agent needs (assembling the tool set).

"Make everything an MCP server" or "put the procedure in the system prompt" are the usual wrong answers. A single-app lookup doesn't need a separate service, and a long procedure in the system prompt costs tokens on every request where a Skill would cost about 100.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Several teams’ agents need live inventory data owned by the warehouse team. Which mechanism fits?
  1. A. A custom tool in each app
  2. B. An MCP server maintained by the warehouse team
  3. C. A Skill
  4. D. Web search
Answer
B
Why
Many clients and another team’s system point to one shared server.
Question 2
Scenario
Claude must produce monthly reports in a house style, with a formatting script. Which mechanism fits?
  1. A. The system prompt
  2. B. A Skill with the style guide and script
  3. C. An MCP server
  4. D. A custom tool
Answer
B
Why
A Skill holds know-how and costs about 100 tokens until it’s needed.
Question 3
Scenario
A Skill on the API needs today’s sales figures from an internal system. What is the problem?
  1. A. None
  2. B. API Skills run in a container with no network access; pair the Skill with a tool or MCP server for the data
  3. C. Skills can’t run scripts
  4. D. The Skill is too long
Answer
B
Why
A Skill isn’t a connection to a live system.
Question 4
Scenario
One support app needs to look up orders in the company’s system. Is an MCP server the best fit?
  1. A. Yes, always
  2. B. Not usually; a custom tool in that app avoids running a separate service for one consumer
  3. C. Use web search
  4. D. Use a Skill
Answer
B
Why
MCP pays off when several clients share the capability.

Key takeaways

  • Decide by where the capability must live, who maintains it, and how Claude discovers and invokes it, and state those reasons.
  • Built-in tools when Anthropic already provides it (web, code execution, Claude Code's file tools); custom tools for one app's access to your systems; MCP servers when many clients share it or another team owns it; Skills for know-how and helper scripts.
  • Skills load progressively: about 100 tokens of metadata always, the body when triggered, files and script output only when used. The description drives discovery.
  • Skills don't sync across surfaces; on the API they need the code execution tool (container.skills, up to 20) and have no network access or package installation; output files come back as Files API IDs.
  • Combine mechanisms where it helps (a Skill for the method, a tool for live data), and enable only what each agent needs.
