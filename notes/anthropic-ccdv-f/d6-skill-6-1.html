6.1: Context Management for Long-Running Sessions

When a long session or agent starts to slow, forget or wander: working out what is filling the context, and choosing between clearing old tool output, summarising the conversation, moving work to a subagent, or starting again.

Overview

Skill 6.1

Context Management for Long-Running Sessions: "Analyzing context bloat or drift in a long-running session or agent and selecting the management technique that restores intended behavior, such as compaction, tool-output pruning, subagent isolation, or criteria for starting a fresh session."

Exam items describe a session that has gone wrong and ask which technique fixes it. The answer depends on what is in the context, not just how much. The architect notes cover keeping exact facts through summarisation (task 5.1) and long codebase exploration (task 5.4). This page is about the API and Claude Code mechanics, and how to choose between them.

Sources: Claude's documentation on context windows, context editing and compaction (threshold and on demand), and the Claude Code documentation on the context window, checked on 19 and 20 November 2026 and paraphrased. The example was tested with the anthropic Python SDK 2.10.0 against a mocked API.

Running example. The shop's investigation agent spends a day on refund disputes. It calls an order API dozens of times, the conversation grows past 100,000 tokens, its answers start contradicting earlier findings, and in the afternoon it's asked to switch to planning a CSV export.

Bloat or drift

Skill 6.1Two problems with different fixes.

  • Bloat: the window is filling. Requests get slower and costlier, and accuracy falls as the token count grows (context rot). Ask what the tokens are. Old tool results, conversation turns and file contents each need a different remedy.
  • Drift: behaviour has moved away from what was intended. Early instructions are followed less, earlier findings are contradicted, or the agent keeps working from facts that are no longer true. Drift can happen well before the window is full. The usual causes are instructions buried under hours of other material, stale tool results, or a task change that leaves old context misleading.

Choosing the technique

Skill 6.1Match the technique to what is filling the window.

session_policy.py (Python, anthropic SDK) 
"""Pick the context-management technique for a long session from what is actually filling it, then send the request."""
import anthropic

client = anthropic.Anthropic()

PRUNE = {"edits": [{"type": "clear_tool_uses_20250919",          # drop old tool results, keep the last few
                    "trigger": {"type": "input_tokens", "value": 80_000},
                    "keep": {"type": "tool_uses", "value": 3},
                    "exclude_tools": ["get_case_facts"]}]}          # never clear the facts lookup
COMPACT = {"edits": [{"type": "compact_20260112",                  # summarise older turns on the server
                      "trigger": {"type": "input_tokens", "value": 150_000},
                      "instructions": "Keep order IDs, amounts, dates and every decision verbatim."}]}


def diagnose(s: dict) -> str:
    """s: {"input_tokens", "tool_result_tokens", "task_changed", "stale_reads", "next_step_reads_many_files"}"""
    if s["task_changed"] or s["stale_reads"]:
        return "fresh"        # old context is irrelevant or wrong: carry a short summary, not the history
    if s["next_step_reads_many_files"]:
        return "subagent"     # keep the bulk reading out of this context altogether
    if s["input_tokens"] > 60_000 and s["tool_result_tokens"] / s["input_tokens"] > 0.5:
        return "prune"        # the bloat is tool output: clear it, keep the conversation
    if s["input_tokens"] > 120_000:
        return "compact"      # the conversation itself is long: summarise older turns
    return "none"


def send(messages: list, action: str, summary: str = "") -> tuple[list, object]:
    if action == "fresh":
        messages = [{"role": "user", "content": f"<summary_of_earlier_work>{summary}</summary_of_earlier_work>\n"
                                                f"{messages[-1]['content']}"}]
    extra = {"prune": {"betas": ["context-management-2025-06-27"], "context_management": PRUNE},
             "compact": {"betas": ["compact-2026-01-12"], "context_management": COMPACT}}.get(action, {})
    response = client.beta.messages.create(model="claude-opus-5-5", max_tokens=4000, messages=messages, **extra)
    # Append the whole content: a compaction block must go back as-is, and the API ignores what came before it.
    messages.append({"role": "assistant", "content": [b.to_dict() for b in response.content]})
    return messages, response
  • Old context is wrong or irrelevant (a task change, stale reads): start fresh with a short summary.
  • The next step reads a lot: send it to a subagent so the reading never enters this context.
  • Most of the tokens are tool results: prune them, and keep the conversation.
  • The conversation itself is long: compact it.

The checks run in that order because the earlier problems aren't solved by the later techniques: compacting a stale context just produces a summary of stale facts. After each call, the whole response content goes back into the history, so a compaction block returns unchanged.

Tool-output pruning

Skill 6.1Context editing clears old tool results.

  • Setup: clear_tool_uses_20250919 (beta header context-management-2025-06-27) clears the oldest tool results once input passes a trigger, 100,000 tokens by default. It keeps the most recent few (three by default) and leaves a placeholder so Claude knows something was removed. exclude_tools protects results that must stay; here, the case-facts lookup.
  • Your copy stays whole: the edit happens on the server before the prompt reaches Claude, so your application's history is unchanged. Old thinking blocks can be cleared the same way with clear_thinking_20251015.
  • Prune before it piles up: trimming each result to the fields the task needs before it enters history is cheaper still (trimming tool results).

Compaction

Skill 6.1Summarising older turns, on the server or in Claude Code.

  • At a threshold (beta, compact-2026-01-12): add a compact_20260112 edit. When input passes the trigger (150,000 tokens by default, at least 50,000), the response starts with a compaction block holding the summary. Append the whole response to your history; on later requests the API ignores everything before the block. Use instructions to say what the summary must keep. Billing for that request is the sum of usage.iterations.
  • On demand (beta): send compaction: {"type": "summarize"} to compact now. You get a signed block back, and send it first in messages in place of what it summarises. This lets your application choose when, for example between tasks, rather than mid-request.
  • Pitfall: serialising response blocks with a plain model_dump() adds null fields that make the API reject the next request. Use to_dict(), as the example does, or model_dump(exclude_none=True).
  • In Claude Code: compaction is automatic near the limit, and /compact keep the refund decisions steers it. Project CLAUDE.md and auto memory are re-read afterwards. Path-scoped rules and everything Claude concluded become part of a summary.

A summary is still lossy. Keep must-not-lose facts in a block or file outside it (case facts).

Subagent isolation

Skill 6.1Keeping bulk work out of the main context.

When the next step will read many files, logs or pages, run it in a subagent. Its reads stay in its own context window and only a summary comes back, so the main session stays small without losing anything it needed. It is prevention rather than repair: the cheapest tokens are the ones that never enter the context. Give the subagent a complete brief, since it doesn't see the parent's history.

When to start fresh

Skill 6.1Criteria for a clean session.

  • The task changed: refund disputes are done and the CSV export starts. In Claude Code that's /clear, and the old session stays resumable.
  • Earlier context is stale: the files or data it read have changed, so its old tool results now mislead.
  • Corrections aren't sticking: after a couple of failed corrections, the context is full of wrong attempts. Start again with a better first prompt.
  • Compaction has already run several times and quality keeps falling: a summary of a summary keeps losing detail.

Carry over a short, structured summary of findings, decisions and open questions (the example's <summary_of_earlier_work>), not the old transcript. If most of the earlier context is still valid, resume and say what changed instead (resume or start fresh).

Key takeaways

  • Diagnose first: bloat (what kind of tokens?) or drift (buried instructions, stale facts, a changed task).
  • Tool results dominate: prune with clear_tool_uses_20250919, protecting must-keep tools with exclude_tools, or trim results before they enter history.
  • Long conversation: compact. Threshold compact_20260112 (default 150,000, minimum 50,000) or on-demand compaction: {"type": "summarize"}; send the compaction block back unchanged (to_dict(), not a plain model_dump()); /compact in Claude Code.
  • Bulk reading ahead: a subagent keeps it out of the context altogether.
  • Start fresh, with a structured summary, when the task changes, context is stale, corrections keep failing, or repeated compaction has worn quality down.
