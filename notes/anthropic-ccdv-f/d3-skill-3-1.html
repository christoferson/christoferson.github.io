Overview

Skill 3.1

Claude Code Operation: "Operating Claude Code correctly across the CLI, desktop, IDE, web, and mobile surfaces, including session management, the CLAUDE.md hierarchy and precedence, settings.json, permission modes, headless and streaming modes, and built-in commands."

This is a wide, factual skill: exam items describe a setup and ask which value applies, why a teammate sees different behaviour, or which flag a script needs. The architect notes cover several parts in depth: CLAUDE.md, plan mode and permission modes, sessions and CI. This page puts the operating facts in one place, with settings precedence and headless output in more detail. Extending Claude Code with skills, plugins and hooks is skill 3.2.

CLI, desktop and IDE share local files; web sessions read only committed settings

Skill 3.1One agent, several places to run it.

  • CLI, desktop app and IDE extensions (VS Code, JetBrains) run on your machine and read the same settings files, CLAUDE.md files and sessions. claude --ide connects a terminal session to an open IDE. /config exists only in the terminal; in the IDE panel and desktop app you edit settings files or use the app's own settings.
  • Web (claude.ai/code) runs cloud sessions on a fresh clone of your repository in a cloud environment. claude --cloud "task" starts one from the terminal, and claude --teleport brings one back into your local terminal. A cloud session reads the committed .claude/settings.json (in a single-repository session) and server-managed settings, but not your user or local settings files.
  • Mobile: the Claude app can follow and steer sessions. claude --remote-control (--rc) starts a local session that you can also control from claude.ai or the app.

Managed beats command line beats local beats project beats user, and lists merge

Skill 3.1settings.json: which file, and which value wins.

settings.json (JSON, .claude/settings.json (committed)) 
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "model": "claude-sonnet-5-5",
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  },
  "env": { "SHOP_API": "https://staging.shop.example" },
  "hooks": {
    "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "jq -r .tool_input.file_path | xargs npx prettier --write" }] }]
  }
}
settings.local.json (JSON, .claude/settings.local.json (personal)) 
{
  "model": "claude-opus-5-5",
  "permissions": {
    "allow": ["Bash(docker compose up *)"]
  }
}
  • Four files:
    • user: ~/.claude/settings.json, you in every project;
    • shared project: .claude/settings.json, committed for the team;
    • project local: .claude/settings.local.json, you in this project, kept out of git;
    • managed: deployed by your organization through a file, MDM or the claude.ai console.
  • Precedence, highest first: managed, then --settings on the command line, then project local, shared project and user. So this developer's sessions use Opus (local beats shared), while teammates get Sonnet.
  • Lists merge: permissions.allow entries from both files apply together, so the local file adds docker compose without removing the team's rules.
  • Restrictions on keys: a defaultMode of auto or bypassPermissions doesn't take effect from project or local files. A committed file's allow rules and most env values wait until each teammate trusts the folder, while deny and ask apply at once.
  • Checking: /status lists the setting sources loaded, and claude doctor shows rejected entries. Settings files are strict JSON, so a trailing comma breaks the file. Most edits reload without a restart.

"I set it in my user settings but the project ignores it": the shared project file sets the same key, and project beats user. Override it in .claude/settings.local.json, not in the user file. If managed settings set it, nothing you write overrides it.

CLAUDE.md files are concatenated, not ranked, so fix conflicts

Skill 3.1Which instruction files load, and how they combine.

Instructions come from managed policy, the user file (~/.claude/CLAUDE.md), the project file (./CLAUDE.md or .claude/CLAUDE.md, committed), CLAUDE.local.md (personal) and subdirectory files.

  • Loading: files from the working folder upwards load at launch; files in subfolders load when Claude touches a file there.
  • Combining: unlike settings, the files aren't ranked. They're concatenated, so contradictory instructions are resolved unpredictably. Fix the conflict rather than relying on an order.
  • Checking: /context all shows what loaded. Hard requirements belong in settings or hooks, not prose.

The detail is in the architect notes (how files load and combine).

Choose the permission mode by who can answer a prompt

Skill 3.1What runs without asking.

  • The modes:
    • default, which the interface labels Manual: asks for anything not pre-approved.
    • acceptEdits: file edits and common filesystem commands without asking.
    • plan: explore and propose, no edits until you approve.
    • auto: a classifier reviews actions instead of you.
    • dontAsk: anything that would prompt is denied.
    • bypassPermissions: no checks; isolated environments only.
  • Setting the mode: --permission-mode overrides defaultMode from settings, and Shift+Tab cycles modes during a session.
  • Headless runs: a claude -p run with no mode set starts in Manual. A call that needs approval is then denied, because nobody can answer, unless a PermissionRequest hook or a permission prompt tool approves it. For unattended jobs, pre-approve what's needed with --allowedTools, and consider dontAsk.
  • Rule order: deny beats ask beats allow across all files.

Name, resume and branch sessions, and manage context with built-in commands

Skill 3.1Keeping, resuming and shaping a session.

  • Sessions:
    • name with -n or /rename; resume with --resume <name or ID>; --continue reopens the most recent in this directory;
    • branch with /branch or --fork-session; isolate parallel work in a worktree with -w;
    • start a background session with --bg and watch it in claude agents.
  • Context: /context shows what's using the window, /compact [focus] summarises, /clear starts fresh (the old session stays resumable), and /rewind steps back to a checkpoint.
  • Configuration: /model and /effort change the model and reasoning depth. /config changes personal options, including key=value form. /status shows sources and account, /mcp shows servers, and /plan enters plan mode.

Script Claude Code with -p and --bare, read the JSON result, resume by session ID

Skill 3.1Running Claude Code from a script and reading the result.

headless_review.py (Python, claude CLI) 
"""Drive Claude Code headlessly: stream a review as newline-delimited JSON, then ask a follow-up in the same session."""
import json
import subprocess

BASE = ["claude", "-p", "--bare", "--output-format", "stream-json", "--verbose",
        "--permission-mode", "dontAsk", "--allowedTools", "Read,Grep,Glob", "--max-turns", "20"]


def run(prompt: str, resume: str | None = None, claude: list[str] = BASE) -> dict:
    cmd = claude + ["--resume", resume] if resume else list(claude)
    proc = subprocess.Popen(cmd + [prompt], stdout=subprocess.PIPE, text=True)
    result = None
    for line in proc.stdout:                       # one JSON object per line
        event = json.loads(line)
        if event["type"] == "system" and event.get("subtype") == "init":
            print(f"session {event['session_id']} model {event['model']}")
        elif event["type"] == "assistant":
            for block in event["message"]["content"]:
                if block["type"] == "tool_use":
                    print(f"  tool: {block['name']}")
        elif event["type"] == "result":            # always the last line
            result = event
    if proc.wait() != 0 or result is None or result.get("is_error"):
        raise RuntimeError(f"run failed: {result and result.get('subtype')}")
    if result.get("permission_denials"):           # dontAsk denies anything not pre-approved
        print(f"  denied: {[d.get('tool_name') for d in result['permission_denials']]}")
    return result


if __name__ == "__main__":
    first = run("Review src/refund.ts for unhandled provider errors.")
    print(first["result"], f"(${first['total_cost_usd']:.4f})")
    follow = run("Which of those would lose money?", resume=first["session_id"])
    print(follow["result"])
  • -p runs one prompt non-interactively. It reads piped stdin (up to 10 MB) and exits 0 on success or non-zero on failure.
  • --bare is recommended for scripts. It skips discovered hooks, skills, plugins, MCP servers, auto memory and CLAUDE.md, and needs ANTHROPIC_API_KEY. Without it, -p loads a repository's hooks and .mcp.json even in a folder you never trusted, with no trust prompt.
  • Output formats:
    • text is the default.
    • json gives one object with result, session_id and total_cost_usd, plus structured_output when you pass --json-schema; check it's present.
    • stream-json gives one JSON object per line. It needs --verbose, starts with a system/init event (model, tools, MCP servers, plugin load errors) and always ends with a result message. Add --include-partial-messages for token-by-token deltas.
  • Multi-turn from a script: capture session_id from the result and pass it to --resume, as the follow-up does. --input-format stream-json instead keeps one process open and streams user messages into it.
  • Failures: the result's is_error and subtype (such as error_max_turns) say what went wrong, and denied calls are listed in permission_denials.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
A developer sets model in ~/.claude/settings.json, but the project uses another model. Why?
  1. A. User settings are ignored
  2. B. The shared project file sets the same key, and project beats user; override it in settings.local.json
  3. C. The model is retired
  4. D. CLAUDE.md overrides it
Answer
B
Why
Precedence runs managed, command line, local, project, user.
Question 2
Scenario
A nightly claude -p job needs to run a test command, and it gets denied. Why?
  1. A. -p can’t run commands
  2. B. With no mode set it starts in Manual and nobody can approve; pre-approve with --allowedTools
  3. C. Bash is disabled
  4. D. The job needs --verbose
Answer
B
Why
Unattended runs need tools granted in advance.
Question 3
Scenario
A script runs claude -p in a cloned repository nobody has trusted. What does --bare change?
  1. A. Nothing
  2. B. It skips discovered hooks, plugins, MCP servers and CLAUDE.md, which -p would otherwise load
  3. C. It disables output
  4. D. It forces plan mode
Answer
B
Why
Without --bare, -p loads a repository’s hooks and .mcp.json without a trust prompt.
Question 4
Scenario
A script needs a follow-up question in the same session. How?
  1. A. Run -p again with the same prompt
  2. B. Capture session_id from the JSON result and pass it to --resume
  3. C. Use --continue in another directory
  4. D. Use /branch
Answer
B
Why
The result carries the session ID for resuming.

Key takeaways

  • CLI, desktop and IDE share local settings, CLAUDE.md and sessions; web runs cloud sessions that read only committed and server-managed settings; --cloud, --teleport and --remote-control move work between them.
  • Settings precedence: managed, --settings, project local, shared project, user; lists such as permissions.allow merge; auto and bypassPermissions can't be the default from project files.
  • CLAUDE.md files are concatenated, not ranked; resolve contradictions and check with /context all.
  • Six permission modes; --permission-mode beats defaultMode; claude -p starts in Manual, where unapproved calls are denied, so pre-approve with --allowedTools.
  • Headless: -p with --bare; json for one result object, stream-json plus --verbose for events ending in result; resume by session_id; check is_error, subtype and permission_denials.
