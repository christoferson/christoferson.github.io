4.1: Evaluation Design

Measuring whether a Claude feature is good enough, in a way others will accept: criteria you can count, test cases that look like real traffic, graders matched to each criterion, a judge you've checked against people, and a gate that catches regressions.

Overview

Skill 4.1

Evaluation Design: "Constructing an evaluation that measures a stated quality goal for a Claude application or component, including LLM-as-judge harnesses calibrated against human-labeled data, golden sets, regression tests, and behavioral checks, and selecting defensible metrics."

Exam items state a goal ("replies must be correct and polite") and ask which evaluation would measure it, which grader suits a criterion, or why a reported score can't be trusted. Using an evaluation to find why a specific run failed is skill 4.2. Accuracy broken down by segment, and sampling in production, are covered in the architect notes (human review and calibration).

Sources: Anthropic's guides on defining success criteria and developing tests, checked on 19 and 20 November 2026 and paraphrased. The suite below was tested with the anthropic Python SDK 2.10.0 against a mocked judge; the trust thresholds in it are my own choice, not Anthropic's.

Running example. The shop's assistant sorts each customer email into a category and drafts a reply. Before switching to a cheaper model, the team needs an evaluation that says whether the replies are still good enough.

From goal to criteria

Skill 4.1Measurable, specific, and more than one dimension.

"Good replies" can't be measured. Break the goal into criteria that can each be checked, with a target:

  • the category matches the label;
  • the reply never promises a refund;
  • it quotes the order number;
  • a reviewer would call it polite, helpful and concrete about the next step.

Anthropic's guidance is that most applications need several criteria at once. Its example sets targets for accuracy, toxicity, how bad errors are and latency together, all on a held-out test set. Targets should be ambitious but achievable, based on a baseline or benchmarks.

The golden set

Skill 4.1Inputs with known right answers.

  • Representative: mirror the real mix of traffic, not the easy cases.
  • Edge cases on purpose: sarcasm ("Love waiting 3 weeks. Great."), two topics in one email, irrelevant or empty input, very long input, hostile input, and cases where even people would disagree. Tag them, so results can be read per tag.
  • Volume over polish: Anthropic prefers many cases with slightly noisier automated grading over a few hand-graded ones.
  • Held out: don't tune prompts on the cases you report.

Choosing a grader

Skill 4.1The fastest reliable method for each criterion.

  • Code-based (exact match, string or pattern match, schema checks): fastest, most reliable and endlessly scalable, but rigid. Use it wherever the criterion allows: the category, the forbidden phrase, the order number.
  • Human: the most flexible and highest quality, but slow and expensive. Anthropic says to avoid it where you can, and to use it to create the labels other graders are checked against.
  • LLM-as-judge: fast, flexible and scalable for judgements code can't make, such as tone or helpfulness. In Anthropic's words, "test to ensure reliability first, then scale". The tips:
    • a detailed rubric, possibly several per criterion;
    • a specific output (pass or fail, or a 1 to 5 score), not free-form commentary;
    • reasoning before the verdict;
    • a different model from the one being evaluated.

An evaluation suite

Skill 4.1Golden set, code checks, judge, metrics, regressions.

eval_suite.py (Python, anthropic SDK) 
"""Evaluate the support assistant's email replies against a stated goal: correct category, required behaviours, and
a helpful tone, with an LLM judge that is checked against human labels before its scores are trusted."""
import re

import anthropic

client = anthropic.Anthropic()

GOLDEN = [  # a golden set: real-shaped inputs with known right answers, edge cases tagged
    {"id": "g1", "email": "Order A1042: the footprint tore after one trip.", "category": "return", "tags": ["typical"]},
    {"id": "g2", "email": "Love waiting 3 weeks for a 'next-day' tent. Great.", "category": "delivery", "tags": ["edge:sarcasm"]},
    {"id": "g3", "email": "Do you sell gift cards? Also my stove never came (B77).", "category": "delivery", "tags": ["edge:two-topics"]},
]

RUBRIC = """The reply is acceptable only if ALL of these hold:
1. It answers the customer's actual question or problem.
2. It is polite and does not blame the customer.
3. It gives a concrete next step (what happens, and when).
Output only <result>pass</result> or <result>fail</result> after your reasoning."""


def code_checks(case: dict, out: dict) -> dict:
    """Fast, deterministic checks: exact match against the golden label, plus behavioural rules."""
    order_ids = re.findall(r"\b[A-Z]\d{2,5}\b", case["email"])
    return {
        "category": out["category"] == case["category"],
        "no_refund_promise": not re.search(r"\b(we will|we'll) refund\b", out["reply"], re.I),
        "quotes_order_id": all(o in out["reply"] for o in order_ids),
    }


def judge(case: dict, reply: str) -> bool:
    # A different, stronger model grades; its thinking is always on, so it reasons before the verdict.
    msg = client.messages.create(model="claude-opus-5-5", max_tokens=3000, messages=[{"role": "user", "content":
          f"<rubric>{RUBRIC}</rubric>\n<customer_email>{case['email']}</customer_email>\n<reply>{reply}</reply>"}])
    text = "".join(b.text for b in msg.content if b.type == "text")
    return "<result>pass</result>" in text.lower()


def calibrate(human: dict[str, bool], judged: dict[str, bool]) -> dict:
    """Agreement and Cohen's kappa between the judge and human labels on the same replies."""
    ids = sorted(human)
    n = len(ids)
    agree = sum(human[i] == judged[i] for i in ids) / n
    p_h, p_j = sum(human[i] for i in ids) / n, sum(judged[i] for i in ids) / n
    chance = p_h * p_j + (1 - p_h) * (1 - p_j)
    kappa = (agree - chance) / (1 - chance) if chance < 1 else 1.0
    false_pass = sum(judged[i] and not human[i] for i in ids) / max(1, sum(not human[i] for i in ids))
    return {"n": n, "agreement": round(agree, 3), "kappa": round(kappa, 3), "false_pass_rate": round(false_pass, 3),
            "trusted": n >= 50 and agree >= 0.9 and kappa >= 0.7}


def run(outputs: dict[str, dict], judge_trusted: bool) -> dict:
    results = {}
    for case in GOLDEN:
        checks = code_checks(case, outputs[case["id"]])
        if judge_trusted:                       # an uncalibrated judge doesn't get a vote
            checks["tone_and_help"] = judge(case, outputs[case["id"]]["reply"])
        results[case["id"]] = checks
    metrics = {}
    for criterion in next(iter(results.values())):
        passed = [r[criterion] for r in results.values()]
        metrics[criterion] = f"{sum(passed)}/{len(passed)}"          # report counts, not just percentages
    by_tag = {t: [results[c["id"]]["category"] for c in GOLDEN if t in c["tags"]] for c in GOLDEN for t in c["tags"]}
    return {"results": results, "metrics": metrics, "category_by_tag": {t: f"{sum(v)}/{len(v)}" for t, v in by_tag.items()}}


def regressions(baseline: dict, current: dict) -> list[str]:
    """Cases and criteria that passed on the last accepted version and fail now: block the release on these."""
    return [f"{cid}:{k}" for cid, checks in current["results"].items()
            for k, ok in checks.items() if not ok and baseline["results"].get(cid, {}).get(k)]
  • Code checks first: the category against the golden label, and two behavioural rules as patterns.
  • The judge uses a rubric with all-or-nothing conditions and returns only <result>pass</result> or fail. It runs on Opus 5.5, a different and stronger model than the assistant under test, whose thinking is always on, so it reasons before deciding.
  • An unchecked judge gets no vote: run includes the judge's criterion only when calibration has passed.

Calibrating the judge

Skill 4.1Checking the judge against human labels.

People label a sample of replies pass or fail, the judge labels the same replies, and calibrate compares them:

  • Agreement: how often the two match.
  • Cohen's kappa: agreement corrected for chance. If 90% of replies are good, a judge that always says pass agrees 90% of the time, but its kappa is 0.
  • False-pass rate: how often the judge passes a reply people failed. This is usually the costlier error, because it hides problems.

The example trusts the judge only with at least 50 labels, 90% agreement and a kappa of 0.7. Those thresholds are a reasonable choice, not an Anthropic rule. When the judge falls short, sharpen the rubric, split it into narrower rubrics, or give it examples, then recheck. Re-calibrate whenever the judge's model or rubric changes.

"The judge scored 94%, so quality is 94%" means nothing until the judge has been compared with human labels. An uncalibrated judge measures its own preferences. Anthropic also advises grading with a different model from the one that produced the output.

Behavioural checks and regression tests

Skill 4.1Rules that must always hold, and changes that must not break them.

  • Behavioural checks test properties rather than exact answers: never promises a refund, always quotes the order number, refuses requests outside policy, output always parses as the schema. Each is cheap and deterministic, so it can run on every case.
  • Regression tests compare a candidate (a new prompt, model or setting) with the last accepted version on the same golden set. regressions lists every case and criterion that used to pass and now fails. Gate the release on that list being empty or explained, not only on the overall score staying flat: an average can hold steady while individual cases break.
  • Run them in CI on every change to prompts, models or tools, the same way unit tests guard code (skill 2.3).

Defensible metrics

Skill 4.1Numbers that survive questioning.

  • Tied to the goal: one metric per criterion, not a single blended score.
  • Counts with the rate: "2/3" says how much evidence there is; "67%" hides it.
  • Broken down: per tag or segment. In the example, the overall category score looks fine while the sarcasm case fails (category_by_tag).
  • The right statistic for the task: precision and recall, or F1, for imbalanced classes; agreement and kappa for judges; percentiles for latency.
  • Reproducible: the same golden set version, model ID and prompt version for every run you compare.

Key takeaways

  • Turn the goal into several measurable criteria with targets, on a held-out set.
  • Golden sets mirror real traffic, include tagged edge cases, and favour volume over hand-polish.
  • Grade with code where possible; use an LLM judge (rubric, specific output, reasoning, different model) for judgement calls; use people to label the calibration set.
  • Trust a judge only after comparing it with human labels: agreement, Cohen's kappa and false-pass rate, rechecked when anything about the judge changes.
  • Behavioural checks for must-hold rules, regression gates on case-level changes, and metrics reported per criterion and segment with counts.
