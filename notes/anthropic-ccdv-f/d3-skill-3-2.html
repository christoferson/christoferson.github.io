Overview

Skill 3.2

Claude Code Customization and Extension: "Analyzing a repeatable team workflow to choose the extension mechanism that fits it, whether a Skill, plugin, Rules file, hook, subagent, or slash command, and authoring and packaging that extension for distribution."

There are three verbs, and exam items test each: choose the mechanism for a described workflow, author it (frontmatter, file location, hook output), and package it for others. The architect notes have more on skill frontmatter (task 3.2) and path rules (task 3.3). Plugin version pinning and dependencies are in skill 2.3.

Sources: the Claude Code documentation on plugins, skills, subagents, hooks and memory, checked on 8 and 20 November 2026 and paraphrased. The plugin below passes claude plugin validate, and its hook script was run with real hook input; the chooser is plain Python.

Running example. The shop's developers repeat four things across the API and web repositories: drafting release notes, reviewing database migrations, never touching the production database from a session, and following the testing conventions in every *.test.ts file.

Matching the workflow to a mechanism

Skill 3.2One question per mechanism.

choose_extension.py (Python) 
"""Pick the Claude Code extension mechanism that fits a repeatable team workflow."""


def choose(w: dict) -> tuple[str, str]:
    """w describes the workflow; returns (mechanism, reason). Checked in order: the first match wins."""
    if w.get("must_always_happen"):
        return "hook", "it must run every time, so code runs it, not the model (formatting after edits, blocking prod writes)"
    if w.get("applies_to_paths"):
        return "rules file", "conventions for matching files: .claude/rules/*.md with paths: loads only when those files are touched"
    if w.get("needs_own_context") or w.get("verbose_output"):
        return "subagent", "isolated context and its own tools; returns a summary instead of filling the main conversation"
    if w.get("user_triggers_with_arguments") and not w.get("claude_should_pick_it"):
        return "skill (user-invoked)", "a /command with $ARGUMENTS and disable-model-invocation: true, so only people trigger it"
    if w.get("procedure_used_sometimes"):
        return "skill", "a procedure Claude loads on demand from its description; only the name and description sit in context"
    if w.get("always_relevant"):
        return "CLAUDE.md", "standards every task needs; loaded every session (and after compaction)"
    return "CLAUDE.md", "start simple; promote it to a skill once it is a distinct procedure"


def package(mechanisms: list[str], repos: int, needs_versions: bool) -> str:
    if repos > 1 or needs_versions:
        return "plugin in a marketplace: one install for every repository, namespaced as plugin:component, versioned releases"
    return "commit to the repository's .claude/ folder: the team gets it with the code, no plugin needed"
  • Must it happen every time? Use a hook. Code runs it whatever the model decides, so it suits blocking production database commands or formatting after every edit.
  • Does it apply to certain files? Use a rules file: .claude/rules/testing.md with paths: ["**/*.test.ts"] loads only when such a file is touched.
  • Is it verbose, or does it need its own tools and focus? Use a subagent, such as the migration reviewer. It works in its own context and returns a summary.
  • Do people start it, with arguments? Use a user-invoked skill, which is what a slash command now is, such as /release-notes v2.3.0.
  • Is it a procedure Claude should use when relevant? Use a skill that Claude may invoke itself.
  • Is it needed in every task? Put it in CLAUDE.md.

Packaging is a separate decision. If the work lives in one repository, committing the files under .claude/ is enough. If several repositories need it, or it needs versioned releases, make it a plugin.

Skills and slash commands

Skill 3.2Authoring a SKILL.md.

shop-plugins/plugins/shop-dev/skills/release-notes/SKILL.md (Markdown, skills/release-notes/SKILL.md) 
---
name: release-notes
description: Draft customer-facing release notes from the commits since a tag. Use when someone asks for release notes or a changelog entry.
argument-hint: "<since-tag>"
disable-model-invocation: true
allowed-tools: Bash(git log *), Read
---

Draft release notes for the changes since $ARGUMENTS.

1. Run `git log $ARGUMENTS..HEAD --oneline` and read the commits.
2. Group them under "New", "Fixed" and "Changed". Leave out refactors and test-only commits.
3. Write one plain sentence per item, for customers, not developers.
4. End with the list of commit hashes you used.
  • Commands and skills are one system: .claude/commands/x.md and .claude/skills/x/SKILL.md both give /x, and the skill wins on a name clash. Skills are the current format, and a skill folder can hold supporting files and scripts.
  • Frontmatter:
    • description is how Claude finds the skill.
    • argument-hint shows in autocomplete, and $ARGUMENTS inserts what was typed.
    • disable-model-invocation: true makes the skill user-only; user-invocable: false makes it Claude-only.
    • allowed-tools pre-approves tools for the skill's turn, without restricting them.
    • context: fork runs the skill in a subagent.
  • Where it lives: .claude/skills/ (committed) reaches the team; ~/.claude/skills/ reaches only you. In a plugin, the skill runs as /shop-dev:release-notes.

Subagents

Skill 3.2A specialist with its own context and tools.

shop-plugins/plugins/shop-dev/agents/migration-reviewer.md (Markdown, agents/migration-reviewer.md) 
---
name: migration-reviewer
description: Reviews database migration files for data loss, locking and missing rollbacks. Use whenever a migration is added or changed.
tools: Read, Grep, Glob
model: sonnet
---

You review SQL migrations for the shop's Postgres database. For each migration, report:
- statements that drop or rewrite data, and whether a backup step exists;
- operations that lock large tables (adding a column with a default, creating an index without CONCURRENTLY);
- whether a matching down migration exists.

Report findings as a list with the file, the line and the risk. Don't edit files.

A subagent is a Markdown file with frontmatter: name, a description that says when to delegate to it, the tools it may use and the model, with the system prompt below. It goes in .claude/agents/ in a repository, ~/.claude/agents/ for you, or agents/ in a plugin. The read-only tool list means the reviewer can't change what it reviews.

Hooks and rules files

Skill 3.2The deterministic guard and the scoped convention.

shop-plugins/plugins/shop-dev/hooks/hooks.json (JSON, hooks/hooks.json) 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}/scripts/block-prod-db.sh\"" }]
      }
    ]
  }
}
shop-plugins/plugins/shop-dev/scripts/block-prod-db.sh (Bash, scripts/block-prod-db.sh) 
#!/usr/bin/env bash
# PreToolUse hook: the tool call arrives as JSON on stdin. Exit 2 blocks it and sends stderr to Claude.
cmd=$(jq -r '.tool_input.command // ""')
if printf '%s' "$cmd" | grep -Eq 'psql .*prod|DATABASE_URL=.*prod'; then
  echo "Commands against the production database are blocked. Use the staging database." >&2
  exit 2
fi
exit 0
  • Hook input and output: a command hook receives the event as JSON on stdin. On PreToolUse, exit code 2 blocks the call and sends stderr to Claude as the reason. The script needs jq on the machine.
  • Where hooks live: in settings.json under hooks (user, project or local), or in a plugin's hooks/hooks.json, where ${CLAUDE_PLUGIN_ROOT} points at the installed plugin.
  • Quote the placeholder. claude plugin validate warned that an unquoted ${CLAUDE_PLUGIN_ROOT} breaks if the path contains a space. The example quotes it; the alternative is the exec form, with command plus args.
  • Rules files aren't plugin components. They're committed in each repository's .claude/rules/, scoped with paths:, or always loaded without it.

Packaging a plugin

Skill 3.2One unit for skills, agents, hooks and MCP servers.

shop-plugins/.claude-plugin/marketplace.json (JSON, .claude-plugin/marketplace.json) 
{
  "name": "shop-tools",
  "description": "Internal Claude Code plugins for the outdoor-gear shop",
  "owner": { "name": "Shop dev team", "email": "dev@example.com" },
  "plugins": [
    {
      "name": "shop-dev",
      "source": "./plugins/shop-dev",
      "description": "Release notes, a migration reviewer and a guard against production database commands"
    }
  ]
}
shop-plugins/plugins/shop-dev/.claude-plugin/plugin.json (JSON, plugins/shop-dev/.claude-plugin/plugin.json) 
{
  "name": "shop-dev",
  "version": "1.0.0",
  "description": "The shop's shared Claude Code workflow for the API and web repositories",
  "author": { "name": "Shop dev team", "email": "dev@example.com" }
}
  • Layout: only plugin.json goes inside .claude-plugin/. skills/, agents/, hooks/hooks.json, .mcp.json and scripts sit at the plugin's root. A CLAUDE.md inside a plugin isn't loaded, so put instructions in a skill.
  • Manifest: only name is required. Add version to control what users get (skill 2.3), and userConfig for values asked for at install, with sensitive ones kept in the operating system's credential store.
  • Marketplace: a repository with .claude-plugin/marketplace.json listing plugins and where to fetch each. It's a catalog, not a hosted store.
  • Developing: load the plugin straight from its folder with --plugin-dir, check it with claude plugin validate, and pick up changes with /reload-plugins. Plugins can also be tested with evals.
  • Mods: a plugin can include a hooks module of JavaScript hooks, which can also draw panes and add commands; a plugin with one is called a mod.

Distributing it

Skill 3.2Getting the plugin to the team.

  • Add and install: /plugin marketplace add example-shop/claude-plugins, then /plugin install shop-dev@shop-tools, or claude plugin install ... --scope project from a setup script.
  • Scopes: user (you, every project), project (committed .claude/settings.json, the whole team) or local (you, this repository).
  • Team rollout: commit extraKnownMarketplaces and enabledPlugins in the repository's settings. These apply after each teammate trusts the folder, and each person still installs the plugin on their own machine.
  • Organization: managed settings can allowlist or block marketplaces and force-install plugins.
  • Cloud sessions don't load the plugins in your local settings.

Cost and trust

Skill 3.2What an enabled plugin costs and what it can do.

  • Context on every turn: the name and description of each skill, agent and command that Claude can invoke stays in context in every session, even when nothing from the plugin runs. Full bodies load only when used. Disable plugins you don't need; user-only skills (disable-model-invocation: true) don't need to advertise themselves to Claude.
  • Runs as you: a plugin's hooks and MCP servers run with your user privileges, outside the sandbox and permission rules, and Anthropic doesn't verify plugin contents. Review the hooks, MCP configuration and scripts before installing. Marketplace names: only Anthropic's own repositories may use the official and community names, and every other marketplace is third-party.

Key takeaways

  • Must always happen: hook. File-specific conventions: rules file with paths:. Verbose or specialist work: subagent. Started by people with arguments: user-invoked skill (the slash command). Used when relevant: skill. Always needed: CLAUDE.md.
  • Commands and skills are one system; the frontmatter controls discovery (description), arguments, who can invoke it, pre-approved tools and forking.
  • Hooks get JSON on stdin; exit 2 on PreToolUse blocks with stderr as the reason; quote ${CLAUDE_PLUGIN_ROOT}.
  • Plugins bundle skills, agents, hooks and MCP servers: plugin.json in .claude-plugin/, components at the root, a marketplace to list them, --plugin-dir and claude plugin validate while developing.
  • Distribute by scope (user, project, local) and committed enabledPlugins; an enabled plugin costs context every turn and runs with your privileges.
