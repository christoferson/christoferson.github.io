Overview

Skill 8.2

MCP Server Development and Integration: "Building, deploying, and integrating an MCP server into Claude applications and workflows, including its resources, tools, and prompts, the choice of transport (stdio or HTTP), and authentication."

Exam items describe an integration and ask which primitive, transport or auth setup fits, or why a client can't reach a server. The architect notes cover MCP scopes in Claude Code (task 2.4) and MCP error results (task 2.2). Tool design itself is skill 8.1.

Sources: the MCP Python SDK 2.3 (its classes inspected directly), Claude's MCP connector documentation, and the earlier verified notes on Claude Code's MCP configuration, checked on 8 and 20 November 2026 and paraphrased. The server was tested through a real MCP client, both in-process and as a stdio subprocess, and the connector call against a mocked API.

Running example. The shop wants one orders server that developers run locally in Claude Code, that a hosted support agent reaches over the network, and that the help assistant calls straight from the Messages API.

A server with all three primitives

Skill 8.2One tool, two resources, one prompt, two transports.

orders_server.py (Python, MCP Python SDK 2.x) 
"""The shop's orders MCP server: one tool, two resources and a prompt. stdio for local clients, Streamable HTTP with
OAuth bearer tokens when it is deployed for remote clients."""
import json
import os
import sys

from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from pydantic import BaseModel

ORDERS = {"A1042": {"status": "delivered", "eta": None, "items": ["Ridge 2 footprint"]},
          "B77": {"status": "in_transit", "eta": "2026-11-24", "items": ["Pocket stove"]}}


class OrderStatus(BaseModel):          # a typed return gives the tool an output schema and structured content
    order_id: str
    status: str
    eta: str | None
    items: list[str]


RETURNS_POLICY = "Unused gear can be returned within 60 days. Damaged items: refund or replacement."


class IntrospectionVerifier:
    """Validates bearer tokens for the HTTP deployment. Replace the lookup with your identity provider's introspection."""
    def __init__(self, valid: dict[str, list[str]]):
        self.valid = valid

    async def verify_token(self, token: str) -> AccessToken | None:
        scopes = self.valid.get(token)
        return AccessToken(token=token, client_id="support-assistant", scopes=scopes) if scopes else None


def build(remote: bool) -> MCPServer:
    kwargs = {}
    if remote:   # only the HTTP deployment needs auth; a stdio server runs as the local user who started it
        kwargs = {"token_verifier": IntrospectionVerifier({os.environ.get("ORDERS_TOKEN", ""): ["orders:read"]}),
                  "auth": AuthSettings(issuer_url="https://auth.shop.example",
                                       resource_server_url="https://mcp.shop.example/mcp",
                                       required_scopes=["orders:read"])}
    mcp = MCPServer("shop-orders", instructions="Order status and return policy for the outdoor-gear shop.", **kwargs)

    @mcp.tool()   # tools: actions the model chooses to call
    def get_order_status(order_id: str) -> OrderStatus:
        """Look up one order's delivery status, expected date and items. Read-only. Use the order ID the customer
        gave, such as A1042; if there is no such order, say so and ask them to check it."""
        order = ORDERS.get(order_id.strip().upper())
        if order is None:
            raise ToolError(f"No order {order_id}. Ask the customer to check the ID.")   # reaches the model as an error
        return OrderStatus(order_id=order_id.upper(), **order)

    @mcp.resource("policy://returns")   # resources: context the application chooses to attach
    def returns_policy() -> str:
        return RETURNS_POLICY

    @mcp.resource("order://{order_id}")
    def order_record(order_id: str) -> str:
        return json.dumps(ORDERS.get(order_id, {}))

    @mcp.prompt()   # prompts: templates the user invokes
    def delivery_reply(order_id: str) -> str:
        return f"Look up order {order_id} and write a short, friendly delivery update for the customer."

    return mcp


if __name__ == "__main__":
    remote = "--http" in sys.argv
    build(remote).run(transport="streamable-http" if remote else "stdio")
  • MCPServer is the high-level server class in the MCP Python SDK 2.x, where it replaced FastMCP. Decorators register each primitive, and the docstring becomes the tool's description.
  • A typed return (OrderStatus) gives the tool an output schema and structured content. A plain dict came back only as JSON text when I tested it.
  • ToolError reaches the client as an error result the model can read. In SDK 2.x, a plain exception's message is hidden.

Tools, resources and prompts

Skill 8.2Who decides when each is used.

  • Tools are actions the model chooses to call, such as get_order_status. Use them for anything Claude should decide to do mid-task.
  • Resources are context the application chooses to attach. policy://returns is a fixed resource; order://{order_id} is a template with a parameter. In Claude Code, users reference them with @server:....
  • Prompts are templates the user invokes. delivery_reply appears in Claude Code as /mcp__shop-orders__delivery_reply.
  • Choosing: if Claude must decide when to fetch it, use a tool. If a person or the app attaches it deliberately, use a resource. If it's a reusable instruction a user starts, use a prompt. Not every client supports all three; the Messages API connector, for one, supports only tools.

stdio or HTTP

Skill 8.2Local subprocess or network service.

  • stdio: the client launches the server as a subprocess and talks over stdin and stdout. There's nothing to host and no network exposure. It runs with the permissions and environment of the user who started it, so it suits developer tools on a laptop and local files. One process per client.
  • Streamable HTTP: the server is a web service many clients reach by URL. It suits shared, hosted or remote use, and it's the only option for clients that can't launch processes, such as the Messages API connector or cloud agents. It needs hosting, TLS and authentication. SSE is the older HTTP transport and is deprecated in favour of Streamable HTTP.
  • Same code: the example's server is identical in both modes, and run(transport=...) chooses. Only the remote deployment adds auth.

Authentication

Skill 8.2Bearer tokens on HTTP; the environment on stdio.

  • Remote servers are OAuth resource servers. The SDK's AuthSettings names the authorization server that issues tokens (issuer_url), the server's own URL as the resource identifier (resource_server_url, also where it publishes its protected-resource metadata), and the scopes it requires. A TokenVerifier checks each bearer token and returns its client, scopes and expiry, or None to reject it. In production, verification calls your identity provider rather than the example's lookup.
  • Clients obtain the token: Claude Code can carry it in a header from an environment variable. The Messages API connector expects you to run the OAuth flow yourself and pass the access token, refreshing it as needed.
  • stdio servers typically don't use that flow. They take credentials for the systems behind them from their environment, set by whoever launches them.
  • Scope tokens narrowly (orders:read here). The server's tools can do whatever its own credentials allow, so least privilege applies to the server too (skill 7.2).

In Claude Code and the Agent SDK

Skill 8.2One committed file for the team.

.mcp.json (JSON, .mcp.json (project scope)) 
{
  "mcpServers": {
    "shop-orders": {
      "command": "python",
      "args": ["tools/orders_server.py"]
    },
    "shop-orders-remote": {
      "type": "http",
      "url": "https://mcp.shop.example/mcp",
      "headers": { "Authorization": "Bearer ${ORDERS_TOKEN}" }
    }
  }
}
  • Project scope: .mcp.json is committed, so the whole team gets both servers: the local one launched with command, and the remote one with "type": "http". The token comes from ${ORDERS_TOKEN}, never a literal, and project servers need each person's approval.
  • Other scopes: local (the default, this project only) and user (all your projects) live in ~/.claude.json. Add servers with claude mcp add --scope ....
  • Naming and limits: tools appear as mcp__shop-orders__get_order_status, which is the name to use in permission rules and hook matchers. Output is capped at 25,000 tokens by default.
  • Agent SDK: pass the same server definitions in mcp_servers and pre-approve their tools in allowed_tools. For tools that live in your own process, @tool with create_sdk_mcp_server skips the separate server. A server that fails to start doesn't raise, so check the init message.

From the Messages API

Skill 8.2The MCP connector: no MCP client in your code.

api_connector.py (Python, anthropic SDK) 
"""Use the deployed server straight from the Messages API with the MCP connector (beta): no MCP client in your code."""
import os

import anthropic

client = anthropic.Anthropic()


def ask(question: str) -> str:
    response = client.beta.messages.create(
        model="claude-sonnet-5-5", max_tokens=1000, betas=["mcp-client-2025-11-20"],
        mcp_servers=[{"type": "url", "url": "https://mcp.shop.example/mcp", "name": "shop-orders",
                      "authorization_token": os.environ["ORDERS_TOKEN"]}],   # you run the OAuth flow and refresh it
        tools=[{"type": "mcp_toolset", "mcp_server_name": "shop-orders"}],
        messages=[{"role": "user", "content": question}],
    )
    return "".join(b.text for b in response.content if b.type == "text")
  • Shape: declare the server in mcp_servers (type url, an https:// URL, a name, an optional authorization_token) and enable it with an mcp_toolset entry in tools. The toolset can allowlist, denylist or configure individual tools.
  • What comes back: Anthropic calls the server, and the response contains mcp_tool_use and mcp_tool_result blocks next to the text.
  • Limits: the connector is in beta. It supports only MCP tools, not resources or prompts. The server must be publicly reachable over HTTP (Streamable HTTP or SSE), and a local stdio server can't be connected. It isn't eligible for zero data retention.
  • Managed Agents: MCP servers are declared on the agent, with credentials supplied from a vault for each session.

Testing a server

Skill 8.2Through a real client, before any model sees it.

  • Test through the protocol: the SDK's Client can connect to an MCPServer in-process, launch it as a stdio subprocess, or reach it by URL. My test does the first two: list tools, call one, check a ToolError comes back as an error result, read both resources, render the prompt.
  • Don't stop at the decorated function: calling it directly raises the ToolError instead of producing the error result a client sees, so only a protocol-level test shows what the model will receive.
  • Then test with Claude: check that the model picks the tool from its description (skill 4.1).

Key takeaways

  • MCPServer (Python SDK 2.x, formerly FastMCP): decorators for tools, resources and prompts; typed returns give structured content; raise ToolError for errors the model should see.
  • Tools are model-chosen, resources application-attached, prompts user-invoked; the Messages API connector supports only tools.
  • stdio for local, single-user servers launched by the client; Streamable HTTP for shared or remote ones and any client that can't launch processes; SSE is deprecated.
  • HTTP servers authenticate bearer tokens as OAuth resource servers (AuthSettings plus a TokenVerifier, narrow scopes); clients obtain the token; stdio servers take credentials from their environment.
  • Integrate with a committed .mcp.json (${VAR} for secrets, "type": "http" for remote), Agent SDK mcp_servers, or the MCP connector (beta; public HTTPS, tools only, you supply the token). Test through a real MCP client.
