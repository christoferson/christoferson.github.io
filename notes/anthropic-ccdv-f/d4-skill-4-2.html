4.2: Failure-Mode Diagnosis

When a Claude feature gives a bad result: naming what kind of failure it is, finding out whether your code or the model's output caused it, and fixing the cause rather than adding a patch that hides it.

Overview

Skill 4.2

Failure-Mode Diagnosis: "Analyzing a trace excerpt or reproduction to identify the failure mode, such as hallucination, refusal, under-acting, context loss, format drift, or inconsistent output; isolating whether it originates in the integration layer or in model output; and selecting a recovery that addresses the cause rather than the symptom."

There are three steps, and exam items test each: name the failure, place it (your code or the model's output), and pick the fix aimed at the cause. Diagnosing an agent's design (loop termination, subagent isolation) is skill 1.3. Errors the API returns, such as rate limits and overloads, are skill 2.4. Measuring how often a failure happens is skill 4.1.

Name the failure: hallucination, refusal, under-acting, context loss, format drift or inconsistency

Skill 4.2What each looks like in a trace.

  • Hallucination: a confident claim with no support in what Claude was given, such as an order number or a policy that isn't in the sources.
  • Refusal: Claude declines. Through the API, that's HTTP 200 with stop_reason: "refusal" and stop_details explaining it, not an error.
  • Under-acting: Claude describes, suggests or asks instead of doing. Claude's prompting guide notes that current models follow instructions precisely, so "can you suggest some changes" gets suggestions, not edits.
  • Context loss: Claude forgets what was said or found earlier: missing history, a truncated window, or a summary that dropped the fact.
  • Format drift: the output doesn't have the agreed shape, such as broken JSON, extra prose or missing fields.
  • Inconsistent output: the same input gives different answers across runs.

Compare the raw request and response with what the app showed to find the layer

Skill 4.2Compare what was sent, what came back, and what the app did.

Many failures that look like the model's fault are your code's. To isolate one, log the raw request and the raw response, then compare them with what the application showed:

  • The response was fine, the app mishandled it: it read content[0].text when the first block was thinking, ignored a tool_use stop and showed nothing, or parsed JSON that max_tokens had cut off. That's integration.
  • The request was wrong: the history wasn't resent (the API keeps none), a document wasn't attached, or the system prompt wasn't what you thought. That's also integration, even though the symptom is "Claude forgot".
  • The request was right and the response itself is wrong: that's model output, and the fix is in the prompt, the schema, the grounding or the model choice.

Replaying the logged raw request on its own is the quickest test. If the replay is fine, look at your code.

Check integration causes first, because they can mimic any model failure

Skill 4.2Integration causes first, then model causes.

triage.py (Python) 
"""Classify a failed Claude call from what was sent, what came back, and what the application did with it.
Integration-layer causes are checked first: they look like model failures but are fixed in your code."""
import re


def triage(sent: dict, got: dict, app: dict) -> dict:
    """sent: the request body; got: the raw response; app: what the app showed or parsed, plus context such as
    {"turn": 3, "shown": "...", "parse_error": True, "retried_same": True, "runs": ["...", "..."], "sources": "..."}"""
    blocks, stop = got["content"], got["stop_reason"]
    text = "".join(b.get("text", "") for b in blocks if b["type"] == "text")

    # ---- integration layer: the model's output was fine, the code mishandled it ----
    if app.get("turn", 1) > 1 and len(sent["messages"]) == 1:
        return verdict("context loss", "integration", "earlier turns weren't resent; the API keeps no history",
                       "append each assistant reply and user turn and send the full messages list")
    if blocks and blocks[0]["type"] != "text" and text and not app.get("shown"):
        return verdict("empty answer", "integration", "code read content[0].text but the first block was thinking or tool_use",
                       "select blocks by type instead of position")
    if stop == "max_tokens" and app.get("parse_error"):
        return verdict("format drift (apparent)", "integration", "output was cut off at max_tokens, so the JSON is incomplete",
                       "raise max_tokens or shorten the task, and check stop_reason before parsing")
    if stop == "tool_use" and not app.get("tool_results_sent"):
        return verdict("under-acting (apparent)", "integration", "the loop stopped while Claude was still asking for a tool",
                       "run the requested tools, return tool_result blocks and continue while stop_reason == 'tool_use'")
    if stop == "refusal" and app.get("retried_same"):
        return verdict("refusal", "integration", "the app retried the identical request after a refusal",
                       "read stop_details, don't resend unchanged; rephrase with legitimate context or route to a person")

    # ---- model output: the call worked as designed, the content is wrong ----
    if stop == "refusal":
        return verdict("refusal", "model", "the model declined (HTTP 200, stop_reason 'refusal', stop_details explains)",
                       "if the request is legitimate, give context and purpose; otherwise handle it as a refusal")
    claims = set(re.findall(r"\b[A-Z]\d{3,5}\b", text))
    if app.get("sources") is not None and claims - set(re.findall(r"\b[A-Z]\d{3,5}\b", app["sources"])):
        return verdict("hallucination", "model", f"cites {sorted(claims)} not present in the provided sources",
                       "restrict answers to the sources, allow 'I don't know', ask for quotes first or use citations")
    if app.get("parse_error") and "output_config" not in sent:
        return verdict("format drift", "model", "JSON was requested only in the prompt, so the shape can drift",
                       "use structured outputs (output_config.format) or a strict tool; keep a parser check")
    if len(set(app.get("runs", []))) > 1:
        return verdict("inconsistent output", "model", "the same input gives different answers across runs",
                       "specify the exact format, add examples, ground in retrieved facts, split into chained steps")
    if re.search(r"\b(suggest|could you|can you)\b", sent["messages"][-1]["content"] if isinstance(
            sent["messages"][-1]["content"], str) else "", re.I) and not any(b["type"] == "tool_use" for b in blocks):
        return verdict("under-acting", "model", "the request asked for suggestions, so Claude suggested instead of acting",
                       "ask for the action directly ('Change this function...') or add a default-to-action instruction")
    return verdict("unclassified", "unknown", "no rule matched", "reproduce with the raw request and response")


def verdict(mode, layer, cause, recovery):
    return {"failure_mode": mode, "layer": layer, "cause": cause, "recovery": recovery}

The order matters. Every integration check comes first, because an integration bug can produce any of the model-looking symptoms: a cut-off response reads as format drift, a stopped tool loop reads as under-acting. Each verdict names the layer, the cause and the recovery. Real diagnosis needs judgement, but these are the checks to run, in this order.

Apply the recovery aimed at the cause of each failure mode

Skill 4.2One cause, one fix.

  • Hallucination: ground Claude in sources and say to use only them. Allow "I don't know". For long documents, have it quote the relevant passages first. Use citations, or make it retract any claim it can't support with a quote. In agentic coding, tell it never to speculate about code it hasn't opened.
  • Refusal: read stop_details. If the request is legitimate, give the purpose and context. Don't resend the identical request, and route genuine refusals to a person or another flow.
  • Under-acting: ask for the action ("Change this function to...") rather than suggestions, or add a default-to-action instruction to the system prompt. If the cause is a stopped tool loop, fix the loop.
  • Context loss: resend the full history, keep exact facts in a block that's never summarised, trim bulky tool results, and use memory for what must survive sessions (context in long interactions).
  • Format drift: use structured outputs (output_config.format) or a strict tool, which guarantee the schema except on refusal and truncation. Check stop_reason before parsing. For prose formatting, say what you want rather than what you don't, and match the prompt's own style.
  • Inconsistent output: specify the exact format, add examples, ground answers in retrieved facts, and break a complex task into chained steps.

Reject fixes that only hide the symptom

Skill 4.2The wrong answers exam items like to offer.

  • Retry until it parses: hides a cut-off or a missing schema, and costs a call each time.
  • Regex the JSON out of the prose: works until the prose changes. Structured outputs remove the problem.
  • "Lower the temperature" for inconsistency: under API version 2026-10-21, which the current SDKs send, temperature, top_p and top_k are rejected for every model. The consistency guide's remedies are format, examples, retrieval and chaining.
  • "Tell it harder" in the prompt for a missing-history bug, or for a hallucinated fact that was never in the sources: the cause is the request, not the wording.
  • Switching to a bigger model for an integration bug: the same code mishandles the bigger model's response too.

Hiding a symptom is not recovering from it. Exam options often include a fix that would make the error disappear from the logs. Choose the one that removes the reason the error occurs.

Practice questions

Exam-style questions written for these notes. Decide your answer before reading the explanation.

Question 1
Scenario
Users see blank answers. The logged response has a thinking block first and a text block second. Where is the fault?
  1. A. The model
  2. B. The integration: the app read content[0].text
  3. C. The prompt
  4. D. Rate limiting
Answer
B
Why
The response was fine; the app mishandled it.
Question 2
Scenario
A coding agent describes fixes instead of making them, after being asked “can you suggest some changes?” What is the cause-level fix?
  1. A. A bigger model
  2. B. Ask for the action, or add a default-to-action instruction
  3. C. Lower temperature
  4. D. Retry
Answer
B
Why
Current models follow instructions precisely; suggestions get suggestions.
Question 3
Scenario
JSON output sometimes fails to parse. What fixes the cause?
  1. A. Retry until it parses
  2. B. Structured outputs or a strict tool, and check stop_reason before parsing
  3. C. A regex to extract JSON
  4. D. Ask politely
Answer
B
Why
The schema is guaranteed except on refusal and truncation; retries and regexes hide the problem.
Question 4
Scenario
Answers vary from run to run. Someone proposes lowering temperature. What is wrong?
  1. A. Nothing
  2. B. temperature is rejected under the current API version; use format specs, examples, retrieval and chaining
  3. C. It makes answers longer
  4. D. It only works on Haiku
Answer
B
Why
The consistency remedies are in the design, not sampling settings.

Key takeaways

  • Six modes: hallucination, refusal (HTTP 200, stop_reason: "refusal"), under-acting, context loss, format drift, inconsistent output.
  • Isolate with the raw request and response: if the response was fine, it's integration (block order, tool loop, truncation, missing history); if a correct request got a wrong response, it's model output.
  • Check integration causes first; they masquerade as model failures.
  • Fix the cause: grounding, quotes, citations and "I don't know" for hallucination; explicit action requests for under-acting; full history and fact blocks for context loss; structured outputs and a stop_reason check for format; format, examples, retrieval and chaining for consistency.
  • Retry loops, regex clean-up, temperature tweaks and bigger models hide symptoms; temperature isn't even accepted under the current API version.
