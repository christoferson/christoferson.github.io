Overview

Skill 1.2

Agent SDK Construction and Hooks: "Building and correcting Claude Agent SDK agent definitions, custom agent loops and harnesses, and hook configurations so that required actions execute deterministically rather than at the model's discretion."

The verbs are building and correcting, so exam items show an agent setup, often with a defect, and ask what it does or how to fix it. The thread through all of them is the last clause: anything that must always happen belongs in code that runs regardless of what the model decides. The architect notes cover the same hooks from the design side (prerequisite gates, interception and normalisation); this page focuses on the code and its failure modes.

Sources: the Claude Agent SDK documentation on hooks, subagents, permissions and the agent loop, and the Claude Code hooks reference, checked on 19 and 20 November 2026 and paraphrased. The hooks were tested by calling them with hook inputs using claude-agent-sdk 0.2.185, and the harness against the anthropic Python SDK 2.10.0 with a mocked API.

Running example. The shop lets an agent make small fixes to its refund service. Every edit must be logged, nothing outside the source and test folders may change, and the agent may not report success while the tests fail. A second, hand-written harness issues refunds, and each one must reach the finance ledger.

Discretion or determinism

Skill 1.2Which steps can be left to the model, and which can't.

An instruction such as "always run the tests before finishing" is followed most of the time. A hook or a line in the harness runs every time. That's the distinction the guide asks for:

  • At the model's discretion: anything in the system prompt or a tool description, such as the order of steps, what to check or when to ask.
  • Deterministic: a PreToolUse hook that refuses a call, a PostToolUse hook that records one, a Stop hook that won't let the agent finish, permission rules, and code in your own loop or tool executor.

Use both: the prompt makes the right behaviour likely, and the code makes the required part certain.

An agent with enforced steps

Skill 1.2Agent definition plus three hooks.

release_agent.py (Python, Agent SDK) 
"""A code-change agent whose required steps are enforced by hooks, not left to the model:
every edit is audited, edits outside src/ and tests/ are refused, and it can't finish while the tests fail."""
import json
import subprocess
import time

from claude_agent_sdk import AgentDefinition, ClaudeAgentOptions, HookMatcher

AUDIT = "audit.jsonl"


async def restrict_paths(input_data, tool_use_id, context):            # PreToolUse on Edit|Write
    path = input_data["tool_input"].get("file_path", "")
    if not path.startswith(("src/", "tests/")):
        return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny",
                                       "permissionDecisionReason": f"{path} is outside src/ and tests/; change only those."}}
    return {}


async def audit(input_data, tool_use_id, context):                     # PostToolUse on Edit|Write|Bash
    with open(AUDIT, "a") as f:                                         # runs on every call, whatever the prompt says
        f.write(json.dumps({"t": time.time(), "tool": input_data["tool_name"], "input": input_data["tool_input"]}) + "\n")
    return {}


async def require_passing_tests(input_data, tool_use_id, context):     # Stop
    run = subprocess.run(["npm", "test", "--silent"], capture_output=True, text=True)   # the hook checks, not the model
    if run.returncode == 0:
        return {}
    if input_data.get("stop_hook_active"):
        # Already sent back once and still failing: let it stop, and make the failure visible to the user.
        return {"systemMessage": "Tests still fail; the change was not completed."}
    return {"decision": "block", "reason": "Tests fail. Fix them before finishing:\n" + run.stdout[-2000:]}


options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob", "Edit", "Write", "Bash(npm test *)", "Agent"],   # pre-approved, no prompts
    disallowed_tools=["WebFetch", "WebSearch"],                                            # actually removed
    agents={
        "test-runner": AgentDefinition(
            description="Runs the test suite and summarises failures. Use after every change.",
            prompt="Run npm test. Report each failing test with its file and the assertion that failed.",
            tools=["Bash", "Read"],                 # without this list the subagent inherits every tool
            model="haiku",
        ),
    },
    hooks={
        "PreToolUse": [HookMatcher(matcher="Edit|Write", hooks=[restrict_paths], on_failure="block")],
        "PostToolUse": [HookMatcher(matcher="Edit|Write|Bash", hooks=[audit])],
        "Stop": [HookMatcher(hooks=[require_passing_tests])],   # Stop takes no matcher
    },
    max_turns=40,
)
  • restrict_paths (PreToolUse on Edit|Write) denies changes outside src/ and tests/, and its reason tells Claude what it may change. on_failure="block" means a crashing hook refuses the call rather than letting it through.
  • audit (PostToolUse) appends every edit and command to audit.jsonl. It doesn't depend on the model remembering to log anything.
  • require_passing_tests (Stop) runs the test suite itself and reads the exit code, rather than trusting the model's claim that tests pass or parsing its output.
  • Tool access: allowed_tools pre-approves the tools the agent uses so it isn't stopped by permission prompts, and disallowed_tools removes the web tools altogether. The test-runner subagent gets its own short tools list and a small model.

Agent definitions that go wrong

Skill 1.2Correcting AgentDefinition and option mistakes.

  • Subagent can do too much: its AgentDefinition has no tools list, so it inherits every tool. Give it the few it needs, or use its disallowedTools.
  • "I listed only Read in allowed_tools, but it still ran Bash": allowed_tools pre-approves, it doesn't restrict. Use disallowed_tools or a tools list to remove tools.
  • Subagent never chosen, or chosen for the wrong job: its description is vague. Claude picks subagents by description, so say what it does and when to use it.
  • Subagent lacks information the coordinator had: subagents start without the parent's history. Put what they need in the prompt the coordinator writes, not in the conversation (context is passed, not inherited).
  • Coordinator can't spawn subagents: the Agent tool (formerly Task) has been removed with disallowed_tools or a restrictive tools setting.
  • Run never ends: there's no max_turns or max_budget_usd. Sessions have no timeout of their own.

Hook configurations that go wrong

Skill 1.2Why a hook didn't do what was intended.

  • Hook never fires: the matcher doesn't match the tool name. Matchers are case-sensitive regexes on names such as Bash, Edit|Write or ^mcp__orders__. MCP tools are named mcp__server__tool, so a matcher of process_refund alone may miss.
  • Denial ignored: the output lacks the hookSpecificOutput wrapper with hookEventName, or puts permissionDecision at the top level.
  • Claude retries the blocked action: the deny reason is empty or vague. The reason goes to the model, so name the alternative ("escalate instead").
  • Policy check in PostToolUse: too late, because the tool has already run. Blocking belongs in PreToolUse; PostToolUse is for recording and reshaping results.
  • A crashing hook lets calls through: set on_failure="block" on guards.
  • Several hooks disagree: the most restrictive decision wins (deny over defer over ask over allow), so an allow in one hook can't override another's deny.

Stop hooks

Skill 1.2Not letting the agent finish until a condition holds.

  • When it runs: each time the main agent finishes responding. It doesn't run after a user interrupt, and API errors fire StopFailure instead. In a subagent, the equivalent event is SubagentStop. Stop hooks take no matcher.
  • How to block: return decision: "block" with a reason, which is required and tells Claude what to do. Claude carries on working. additionalContext keeps it going too, but as guidance rather than an error.
  • Avoiding a loop: the input's stop_hook_active is true when Claude is already continuing because of a stop hook. Check it, as the example does, so a condition that can't be met doesn't hold the agent forever. Claude Code also caps continuations at eight in a row, resetting whenever Claude calls a tool.
  • Shortcut: in Claude Code, /goal is a built-in, session-scoped Stop hook driven by a prompt.

Required steps in a custom harness

Skill 1.2When you own the loop, you own the guarantees.

refund_harness.py (Python, anthropic SDK) 
"""A custom harness on the Messages API: the model decides whether to refund; the harness, not the model,
records every refund in the ledger and stops runaway loops."""
import json

import anthropic

client = anthropic.Anthropic()
TOOLS = [{"name": "issue_refund", "description": "Refund an order. Use only after checking the return is eligible.",
          "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}, "amount": {"type": "number"}},
                           "required": ["order_id", "amount"]}, "strict": True}]
ledger: list[dict] = []


def issue_refund(order_id: str, amount: float) -> dict:
    result = {"status": "refunded", "order_id": order_id, "amount": amount}
    ledger.append(result)                    # part of executing the tool: can't be skipped or forgotten by the model
    return result


def run(task: str, max_turns: int = 10) -> str:
    messages = [{"role": "user", "content": task}]
    for _ in range(max_turns):
        response = client.messages.create(model="claude-sonnet-5-5", max_tokens=2000, tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return "".join(b.text for b in response.content if b.type == "text")
        results = []
        for block in (b for b in response.content if b.type == "tool_use"):
            try:
                out, err = issue_refund(**block.input), False
            except Exception as e:                     # report failures to the model instead of crashing the loop
                out, err = {"error": str(e)}, True
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": json.dumps(out), "is_error": err})
        messages.append({"role": "user", "content": results})
    raise RuntimeError(f"no answer after {max_turns} turns")   # a safety net that reports, not a normal exit
  • The must-run step is part of executing the tool: the ledger entry is written inside issue_refund. There's no separate "record in ledger" tool the model might forget to call.
  • Loop on the stop reason: continue only while stop_reason is tool_use, and run every tool call in the response.
  • Failures go back as results: a bad call becomes a tool_result with is_error: true, so the model can correct itself and the loop survives.
  • A turn cap that raises: hitting max_turns is an error to report, not a normal exit. The Agent SDK does the same with error_max_turns.

A classic wrong fix: "add 'always record refunds in the ledger' to the system prompt". It makes the step more likely, not certain. The deterministic fix is in the code that executes the refund, or a hook on it.

Key takeaways

  • Prompts make behaviour likely; hooks, permission rules and harness code make it certain. Put every must-happen step in the second group.
  • PreToolUse denies with a reason Claude can act on (wrapped in hookSpecificOutput, with on_failure="block" for guards); PostToolUse records or reshapes after the tool has run.
  • A Stop hook with decision: "block" and a reason keeps the agent working until a condition holds. Check stop_hook_active to avoid endless loops, and verify the condition in the hook, such as running the tests yourself.
  • Common definition defects: no tools list (inherits all), relying on allowed_tools to restrict, vague descriptions, missing context in the subagent prompt, no turn or budget limit.
  • In a custom harness, do required steps inside tool execution, return failures as is_error results, loop on stop_reason, and make the turn cap raise.
