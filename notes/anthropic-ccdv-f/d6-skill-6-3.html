6.3: Structured Output and Defensive Parsing

Protecting the code that consumes Claude's output: a strict schema for the shape, validation for the rules a schema can't express, explicit handling of refusals and cut-offs, and a careful parser for the cases where you only get text.

Overview

Skill 6.3

Structured Output and Defensive Parsing: "Applying structured outputs with strict schema validation, response validation, and defensive parsing of free-text fallbacks to protect downstream code from malformed or unexpected model output."

Exam items show extraction code that crashes, or silently stores bad data, and ask where it's unprotected. The request side of structured outputs is in skill 2.1. Retry-with-feedback loops and self-checking fields are in the architect notes (task 4.4), and schema design choices such as nullable fields and other enums are in task 4.3.

Sources: Claude's documentation on structured outputs, strict tool use and stop reasons, and the Python SDK, checked on 19 and 20 November 2026 and paraphrased. The pipeline was tested with the anthropic Python SDK 2.10.0 and Pydantic against a mocked API.

Running example. The shop's finance system imports supplier invoices that Claude extracts. A bad total once reached the ledger because the code trusted the JSON it was given.

Three layers of protection

Skill 6.3Shape, meaning, and the cases that escape both.

  • Strict schema: structured outputs make the reply's syntax and shape right. That covers valid JSON, required fields present, no extra fields and enum values only.
  • Response validation: your code checks what the schema can't express: ranges, arithmetic, cross-field rules and formats.
  • Defensive handling: refusals and cut-offs (where the schema isn't guaranteed), and text-only paths that need careful parsing.

Skipping any layer leaves a way for bad data through.

A defensive extraction pipeline

Skill 6.3Every path ends in a validated object or a named error.

safe_extract.py (Python, anthropic SDK + Pydantic) 
"""Extract an invoice so downstream code only ever sees a validated object or an explicit error, never raw model text."""
import json
import re
from dataclasses import dataclass

import anthropic
from pydantic import BaseModel, ValidationError, field_validator, model_validator

client = anthropic.Anthropic()


class Line(BaseModel):
    sku: str
    qty: int
    unit_price: float


class Invoice(BaseModel):
    invoice_no: str
    currency: str
    lines: list[Line]
    total: float

    @field_validator("currency")
    @classmethod
    def upper(cls, v: str) -> str:          # enum casing isn't guaranteed: normalise rather than trust
        return v.upper()

    @model_validator(mode="after")
    def checks(self):                       # rules a JSON schema can't express: ranges and arithmetic
        if any(l.qty <= 0 or l.unit_price < 0 for l in self.lines):
            raise ValueError("quantities must be positive and prices non-negative")
        if abs(sum(l.qty * l.unit_price for l in self.lines) - self.total) > 0.01:
            raise ValueError("lines don't add up to the total")
        return self


SCHEMA = {"type": "object", "additionalProperties": False, "required": ["invoice_no", "currency", "lines", "total"],
          "properties": {"invoice_no": {"type": "string"}, "currency": {"type": "string", "enum": ["EUR", "GBP", "USD"]},
                         "total": {"type": "number"},
                         "lines": {"type": "array", "items": {"type": "object", "additionalProperties": False,
                                   "required": ["sku", "qty", "unit_price"], "properties": {
                                       "sku": {"type": "string"}, "qty": {"type": "integer"}, "unit_price": {"type": "number"}}}}}}


@dataclass
class Result:
    invoice: Invoice | None = None
    error: str | None = None                # "refusal", "truncated", "invalid: ...", "unparseable"


def extract(document: str, max_tokens: int = 2000) -> Result:
    msg = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=max_tokens,
        output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
        messages=[{"role": "user", "content": f"Extract the invoice.\n<document>{document}</document>"}])
    if msg.stop_reason == "refusal":       # the schema isn't guaranteed on a refusal
        return Result(error="refusal")
    if msg.stop_reason == "max_tokens":    # nor when the output was cut off: retry once with more room
        return extract(document, max_tokens * 2) if max_tokens < 8000 else Result(error="truncated")
    return validate("".join(b.text for b in msg.content if b.type == "text"))


def validate(text: str) -> Result:
    try:
        return Result(invoice=Invoice.model_validate_json(text))
    except ValidationError as e:
        return Result(error="invalid: " + "; ".join(err["msg"] for err in e.errors()))


def parse_free_text(text: str) -> Result:
    """Fallback for paths without structured outputs (for example a request that also uses citations):
    find the first complete JSON object in prose or a code fence, then validate it like any other output."""
    text = re.sub(r"```(?:json)?", "", text)
    start = text.find("{")
    depth, in_str, esc = 0, False, False
    for i, ch in enumerate(text[start:] if start >= 0 else "", start):
        if in_str:                         # braces inside strings don't count
            if esc:
                esc = False
            elif ch == "\\":
                esc = True
            elif ch == '"':
                in_str = False
            continue
        if ch == '"':
            in_str = True
        elif ch == "{":
            depth += 1
        elif ch == "}":
            depth -= 1
            if depth == 0:
                return validate(text[start:i + 1])
    return Result(error="unparseable")
  • The schema has additionalProperties: false on every object, required fields, and an enum for the currency.
  • stop_reason is checked before parsing: a refusal becomes an explicit error, and a cut-off gets one retry with more room, then an error.
  • The Pydantic model normalises the currency's case, rejects negative quantities, and checks that the lines add up to the total. That last check is the one that would have stopped the bad ledger entry.
  • Result carries either an Invoice or an error string, never raw text.

What a strict schema guarantees

Skill 6.3Strong on syntax, silent on meaning, and with exceptions.

  • Guaranteed: output that parses and matches the schema. Use output_config.format for a reply, or strict: true for a tool's input; the two can be combined.
  • Not expressible: numeric ranges (minimum, maximum), string lengths, oneOf, not and recursive schemas. The SDK's helpers move such constraints into field descriptions, so the model sees them, but only your validation enforces them.
  • Request limits: every object needs additionalProperties: false. A request can have at most 20 strict tools, 24 optional parameters and 16 parameters with union types, and a nullable type list counts as a union.
  • Not guaranteed when: the model refuses (HTTP 200, stop_reason: "refusal") or output hits max_tokens. Enum casing isn't guaranteed either, so normalise or compare case-insensitively.
  • Not combinable with: citations (a 400 error), and prefilled replies, which current models don't accept anyway.

Validating the response

Skill 6.3Checks that belong in code.

  • Parse into a typed model (Pydantic, a dataclass with checks, or your language's equivalent), not into a loose dictionary that downstream code then indexes blindly.
  • Semantic rules: sums, ranges, dates in order, an ID format, a value that must exist in your database.
  • The SDK route: the Python SDK's messages.parse(output_format=Model) returns parsed_output directly. When I tested it, a truncated response raised a ValidationError rather than returning an error value. Check the stop reason or catch the exception; the example instead calls create and validates itself, so every path returns a Result.
  • When validation fails: retry with the specific error if it's a fixable misreading, or route to review if the information isn't in the document (when a retry can't help).

Parsing free-text fallbacks

Skill 6.3When you only get prose with JSON somewhere in it.

Some paths can't use structured outputs. A request that uses citations can't have a schema. Output can reach you through a chat surface or an older integration, or come from a claude -p run without --json-schema. There, parse_free_text is defensive in specific ways:

  • It strips code fences.
  • It finds the first complete JSON object by tracking depth, ignoring braces inside strings and escaped quotes.
  • It runs the result through the same validation as the structured path.
  • It returns unparseable rather than guessing when no object closes.

A greedy regex such as \{.*\} fails on exactly the cases that matter: two objects in one reply, or a brace inside a string.

Fallback parsing is a fallback. If a path can use structured outputs, switch it rather than hardening the parser. The parser is for the paths that can't.

What downstream code receives

Skill 6.3A contract, not a hope.

  • One return type for every path: a validated object or a named error (refusal, truncated, invalid: ..., unparseable). Downstream code branches on it and never handles raw model text.
  • Named errors route differently: refusals to a person, truncation to a retry or a smaller task, invalid data to review, with the reason attached.
  • Keep the raw response in logs for diagnosis (skill 4.2), but don't let it past the boundary.
  • The same discipline applies to agents: the Agent SDK's output_format returns structured_output, and can end with error_max_structured_output_retries. claude -p --json-schema also returns structured_output. In both cases, check the field exists before using it.

Key takeaways

  • Three layers: a strict schema for shape, code validation for meaning, and explicit handling of refusals, truncation and text-only paths.
  • Schemas need additionalProperties: false; they can't express ranges, lengths, oneOf or recursion; limits are 20 strict tools, 24 optional and 16 union parameters; enum casing isn't guaranteed.
  • Check stop_reason before parsing: refusal and max_tokens break the guarantee; messages.parse raises on truncated output.
  • Validate into a typed model with semantic checks (sums, ranges, formats); retry fixable errors, route missing information.
  • Free-text fallbacks: strip fences, find the first complete object with string-aware depth tracking, validate it, and return unparseable instead of guessing. Downstream code receives only a validated object or a named error.
