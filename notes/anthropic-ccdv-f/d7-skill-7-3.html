7.3: API Key and Credential Handling

Keeping Claude credentials where they belong: on a server, with the narrowest scope that works, separate for each environment, short-lived where possible, and watched so that a leak is caught and shut off quickly.

Overview

Skill 7.3

API Key and Credential Handling: "Handling Anthropic API keys and credentials correctly in development and production, including server-side proxying rather than client embedding, workspace-scoped keys versus admin keys, environment separation, rotation, and access monitoring, without exposing any key beyond its intended scope."

Exam items show where a key lives, what it can reach and who can see it, and ask what's wrong or what to change. Credentials for the tools an agent calls (an egress proxy that injects them, or vaults in Managed Agents) are touched on in skill 1.1; this page is about Claude's own credentials.

Sources: Claude's documentation on authentication, the Admin API and Workload Identity Federation, checked on 20 November 2026 and paraphrased. Both examples were tested with the anthropic Python SDK 2.10.0 against a mocked API.

Running example. The shop's website has a "Ask about this tent" box, a nightly job writes product descriptions, developers try prompts on their laptops, and a two-year-old integration still uses a key nobody remembers creating.

Never in the client

Skill 7.3The browser talks to your back end; the back end holds the key.

backend_proxy.py (Python, anthropic SDK) 
"""The browser never sees a key: the web app calls this back end, which holds the key and makes a constrained call."""
import os
import time

import anthropic

# The key comes from the environment (filled from a secrets manager), never from code or the front end.
# Each environment's deployment gets its own key, scoped to that environment's workspace.
client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
WINDOW, LIMIT = 3600, 30
_calls: dict[str, list[float]] = {}


def handle(session: dict | None, body: dict) -> tuple[int, dict]:
    if not session or not session.get("user_id"):          # your own auth: only signed-in customers
        return 401, {"error": "sign in first"}
    now, uid = time.time(), session["user_id"]
    recent = [t for t in _calls.get(uid, []) if now - t < WINDOW]
    if len(recent) >= LIMIT:                                 # per-user quota, so one account can't run up the bill
        return 429, {"error": "too many questions, try again later"}
    _calls[uid] = recent + [now]
    question = str(body.get("question", ""))[:2000]
    # The client chooses only the question: model, system prompt and limits are fixed here.
    msg = client.messages.create(model="claude-haiku-5-5", max_tokens=600,
                                 system="You answer questions about the shop's gear and policies.",
                                 messages=[{"role": "user", "content": question}],
                                 metadata={"user_id": uid})          # an opaque ID for abuse tracing, no personal data
    return 200, {"answer": "".join(b.text for b in msg.content if b.type == "text")}
  • Why: anyone using a web page can read a key embedded in its code, and the same goes for a mobile app's binary. The API refuses direct browser requests unless they carry a deliberately alarming opt-in header, which the TypeScript SDK's dangerouslyAllowBrowser sets. Organisations with zero data retention or the Compliance API can't make browser calls at all.
  • What the proxy adds besides hiding the key:
    • your own sign-in check;
    • a per-user quota, so one account can't run up the bill;
    • a fixed model, system prompt and max_tokens, so the client chooses only the question;
    • an opaque metadata.user_id for tracing abuse without sending personal data.
  • Forward correctly: the back end should build a new request rather than pass the browser's request through, because the browser's Origin header would come with it.
  • Native apps: for iOS and macOS apps with no back end, App Attest issues each genuine installation a one-hour, workspace-scoped token limited to the Messages API, instead of shipping a key.

Choosing the credential

Skill 7.3The narrowest identity that does the job.

  • Personal key: acts as you, with your roles, for your own development and scripts. It stops working when you leave the organisation, so never share one: a shared personal key breaks when its owner leaves.
  • Service account key: for anything shared or unattended, such as CI and production services. The workload gets its own identity, and the key survives whoever created it.
  • Workspace key (legacy): belongs to a workspace rather than an identity, and keeps working after its creator leaves. Anthropic recommends replacing these with identity-backed keys or federation.
  • Admin API key (sk-ant-admin...): manages the organisation (members, workspaces, invites, existing keys), and only admins can create one. It reaches across the whole organisation, so it belongs in an admin tool or audit job, never in an application making model calls.
  • Workload Identity Federation: the workload exchanges a token from an identity provider you already trust (AWS, Google Cloud, Azure, GitHub Actions, Kubernetes and others) for a short-lived Claude token, and the SDK refreshes it. There's no static key to leak or rotate, and Anthropic prefers it to long-lived keys for production. It's only as strong as the identity provider behind it, so pair it with that provider's controls.

Separate environments

Skill 7.3One workspace and one key per environment.

  • Workspaces: put development, staging and production in separate workspaces, and give each deployment a key scoped to its own workspace. A key scoped to one workspace works only there. A leaked development key can't touch production traffic, and each environment can have its own rate limits.
  • Unscoped keys must name a workspace on every request with the anthropic-workspace-id header, and the API returns a 400 error without it. Prefer scoped keys for applications.
  • Where the key lives: in a secrets manager, injected as ANTHROPIC_API_KEY at run time. Never in code, committed config, logs or error messages.
  • In CI: a repository secret or, better, federation from the CI provider's identity. GitHub Actions is a supported provider.

Expiry, rotation and leaks

Skill 7.3Limit how long a leaked key works, and shut it off fast.

  • Expiry at creation: 3 hours, 1 day, 7 days, 30 days, a custom duration, or Never (only for keys you rotate yourself from a secrets manager). Organisations can set a maximum. Expiry can't be changed later. Anthropic emails a warning before longer-lived keys expire, and an expired key returns 401.
  • Rotation: create the new key, deploy it, confirm requests succeed, then delete the old one. Doing it periodically keeps the procedure practised for the day it's urgent.
  • A suspected leak: disable the key at once. That's reversible: its status becomes inactive. Then rotate and delete it, which is permanent: the key is archived.
  • Limit where a key works: IP allowlisting (in beta) restricts where keys can be used from, so a stolen key fails from elsewhere.

Auditing and monitoring

Skill 7.3A weekly check with the Admin API.

key_audit.py (Python, anthropic SDK (Admin API)) 
"""Weekly key audit with the Admin API: flag keys that could outlive their purpose or reach too far, disable a leaked one.
Runs with an Admin API key from the secrets manager, used for nothing else."""
import os
from datetime import datetime, timedelta, timezone

import anthropic

admin = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_ADMIN_KEY"])   # sk-ant-admin..., admins only
MAX_AGE = timedelta(days=90)
WORKSPACES = {"wrkspc_prod": "prod", "wrkspc_staging": "staging", "wrkspc_dev": "dev"}


def audit(now: datetime | None = None) -> list[dict]:
    now = now or datetime.now(timezone.utc)
    findings = []
    for key in admin.organization.api_keys.list(status="active"):
        issues = []
        if key.principal is None:
            issues.append("legacy workspace key: replace with a service account key or federation")
        if key.expires_at is None and now - key.created_at > MAX_AGE:
            issues.append("never expires and older than 90 days: rotate it")
        if key.scope.type == "organization":
            issues.append("not scoped to one workspace: limit it to the app's environment")
        else:
            env = WORKSPACES.get(key.scope.workspace_id, "unknown")
            if env not in key.name:
                issues.append(f"name doesn't say it belongs to {env}: check where it is deployed")
        if issues:
            findings.append({"id": key.id, "name": key.name, "hint": key.partial_key_hint, "issues": issues})
    return findings


def disable(key_id: str) -> str:
    """Suspected leak: disable at once (reversible), then rotate, then delete the old key."""
    return admin.organization.api_keys.update(key_id, status="inactive").status
  • What it flags:
    • legacy keys with no identity behind them (principal is null);
    • keys that never expire and are older than 90 days;
    • keys not scoped to a single workspace;
    • keys whose name doesn't match their environment.
    The two-year-old integration key trips the first two.
  • What the Admin API can do: list, read, rename and change the status of keys, but not create them; new keys come from the Console. The audit job runs with its own Admin API key, used for nothing else.
  • Watch usage too: a sudden spike on one key or workspace is often the first sign of a leak. The usage and cost analytics API (in beta) and the Console show where usage comes from. Anthropic's own list adds auditing roles, archiving unused workspaces and checking each key's expires_at.

"Use the admin key everywhere so nothing breaks" is the anti-pattern this skill tests. Every key should reach exactly one purpose: one workload, one environment, the lowest role.

Key takeaways

  • Keys never go in browser or app code: a back end holds the key and fixes the model, prompt and limits; App Attest covers native apps with no back end.
  • Personal keys for your own work, service account keys for shared and production workloads, legacy workspace keys replaced, Admin API keys only for administration; Workload Identity Federation removes static keys entirely.
  • One workspace and one scoped key per environment, injected from a secrets manager; unscoped keys need anthropic-workspace-id.
  • Set expiry at creation, rotate on a schedule, disable (reversible) then delete (permanent) a leaked key, and use IP allowlisting.
  • Audit keys with the Admin API (principal, scope, expires_at, status) and watch usage for spikes.
