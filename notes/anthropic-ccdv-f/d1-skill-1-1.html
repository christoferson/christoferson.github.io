1.1: Architecture and Runtime Selection

Overview

Skill 1.1

Architecture and Runtime Selection: "Evaluating whether a workflow or an agentic architecture fits a set of business requirements, error tolerance, and audit constraints. This includes choosing the orchestrator and subagent decomposition and selecting the execution environment: a self-hosted harness or a managed, sandboxed agent runtime."

Exam items describe a business need and its constraints (how costly a mistake is, what must be auditable, where data may go), then ask for the design and the place it runs. The design half overlaps the architect exam, so this page summarises it and links the detail in the CCAR-F notes. The runtime half, and especially Claude Managed Agents, is the developer-specific part. Building the agent itself with the SDK is skill 1.2, and diagnosing a misbehaving one is skill 1.3.

Sources: Anthropic's documentation on Claude Managed Agents (overview, choosing an environment, quickstart) and on hosting the Agent SDK, plus "Building effective agents", checked on 20 November 2026 and paraphrased. Both examples were run against the anthropic Python SDK 2.10.0 with a mocked API, not the live service.

Running example. The shop wants three things automated: refunds under a fixed policy, a weekly audit of supplier contracts that are confidential and must stay on the shop's servers, and open-ended research into what competitors stock.

Workflow or agent

Skill 1.1Fitting the architecture to requirements, error tolerance and audit.

In a workflow, your code fixes the path: Claude is called at defined steps, and the sequence doesn't change. In an agent, Claude decides the next step from each tool result. The choice follows from three things the guide names:

  • Business requirements: if the steps can be written down in advance (check eligibility, calculate, refund, notify), it's a workflow. If they depend on what's found (investigate a contract, then decide what to read next), it's an agent.
  • Error tolerance: where a mistake costs money or breaks a rule, prefer the predictability of a workflow. If an agent is still needed, put the must-hold rules in code around it (approval gates, hooks), not only in the prompt.
  • Audit constraints: a workflow gives the same, reviewable path every time. An agent's path varies, so auditing it means logging every tool call and decision, as the managed example below does.

Anthropic's advice is to start with the simplest design that works and add autonomy only when it pays for itself. The architect notes cover this in more depth (model-driven or predefined).

Splitting into subagents

Skill 1.1Choosing the orchestrator and subagent decomposition.

An orchestrator breaks a task into parts, hands each to a subagent with its own context, and merges what they return. That's worth it when the parts are genuinely independent and broad (research across several competitors, an audit across many contracts): they run in parallel and none fills its context with another's reading. It isn't worth it for a single, sequential task, where one agent is cheaper and simpler. Multi-agent systems use many times the tokens of a single chat.

Decompose by independent subtopic or source so subagents don't duplicate work, and check that the parts together cover the whole question. The details are in the architect notes (partitioning the scope, when one agent is better).

Three runtimes

Skill 1.1Where the agent loop and its tools run.

  • Your own loop on the Messages API. Your code sends requests, runs each tool call and returns the results. It gives full control and nothing is hosted for you. It suits short calls, workflows, and agents whose control flow or tool execution is unusual.
  • The Agent SDK as a self-hosted harness. The SDK provides Claude Code's loop and built-in tools (files, Bash, search), and runs them in your process and your containers. You own isolation, scaling, session storage and network controls.
  • Claude Managed Agents (beta). Anthropic hosts the agent loop. You define an agent once, start sessions, and exchange events with it while it works. Tools run in a sandbox that Anthropic manages, or in one you run yourself. Anthropic positions it for long-running and asynchronous work.

The decision in code

Skill 1.1Requirements in, architecture and runtime out.

choose_architecture.py (Python) 
"""Turn a set of requirements into an architecture and a runtime, with the reason for each choice."""
from dataclasses import dataclass


@dataclass
class Requirements:
    steps_known: bool            # can the sequence of steps be written down in advance?
    error_tolerance: str         # "low" (money, compliance) or "high" (drafts, research)
    audit_every_step: bool       # must each decision be reproducible and reviewable?
    independent_subtasks: int    # how many parts can be worked on separately
    runs_for_minutes: bool       # long, multi-tool tasks or quick request/response
    data_must_stay_on_prem: bool # files and processes must stay on our infrastructure
    needs_custom_loop: bool      # unusual control flow, own tool executor, own UI events
    team_runs_infra: bool        # willing to operate containers, isolation and session storage


def choose(r: Requirements) -> dict:
    why = []
    if r.steps_known or (r.error_tolerance == "low" and r.audit_every_step):
        pattern = "workflow"
        why.append("fixed code path: predictable, testable and auditable step by step")
    else:
        pattern = "agent"
        why.append("the next step depends on what is found, so the model chooses it")
    if pattern == "agent" and r.error_tolerance == "low":
        why.append("keep must-hold rules (approvals, limits) in code or hooks around the agent")
    if r.independent_subtasks >= 3:
        pattern += " with orchestrator and subagents"
        why.append("independent parts run in parallel in isolated contexts; the orchestrator merges them")

    if not r.runs_for_minutes or r.needs_custom_loop:
        runtime = "Messages API, your own loop"
        why.append("short calls or custom control flow: full control, nothing hosted")
    elif r.team_runs_infra:
        runtime = "Agent SDK, self-hosted harness"
        why.append("the agent loop and tools run in your containers; you own isolation and session storage")
    elif r.data_must_stay_on_prem:
        runtime = "Managed Agents, self-hosted sandbox"
        why.append("Anthropic runs the loop; bash and file tools run on your worker, files stay with you")
    else:
        runtime = "Managed Agents, cloud environment"
        why.append("Anthropic runs the loop and an isolated sandbox per session; nothing to operate")
    return {"pattern": pattern, "runtime": runtime, "why": why}
  • Refunds (known steps, low tolerance, every step audited, short calls): a workflow on the Messages API.
  • Contract audit (steps not known in advance, four independent contract groups, runs for minutes, files must stay on site, no appetite to run agent infrastructure): an agent with an orchestrator and subagents, on Managed Agents with a self-hosted sandbox. Approval rules stay in code or hooks.
  • Competitor research (open-ended, mistakes tolerable, no data constraints): an agent on Managed Agents with a cloud environment. A team that wants to run its own containers would choose the self-hosted Agent SDK instead.

The rules are a teaching aid, not a formula: exam items turn on which requirement dominates.

Managed Agents

Skill 1.1A managed, sandboxed agent runtime.

managed_audit_agent.py (Python, anthropic SDK) 
"""A long-running contract-audit agent on Claude Managed Agents (beta), with every tool call logged for audit."""
import json

import anthropic

client = anthropic.Anthropic()          # the SDK adds the managed-agents-2026-04-01 beta header itself


def create(on_prem: bool) -> tuple[str, str]:
    agent = client.beta.agents.create(
        name="Contract auditor",
        model="claude-opus-5-5",
        system="Audit the supplier contracts in /data/contracts. Write findings to /data/out/findings.json.",
        tools=[{"type": "agent_toolset_20260401",          # bash, file tools, web search and fetch
                "configs": [{"name": "web_search", "enabled": False},
                            {"name": "web_fetch", "enabled": False}]}],   # only the tools it needs
    )
    if on_prem:
        # Bash and file tools run on our own worker; contract files never leave our network.
        config = {"type": "self_hosted"}
    else:
        # A fresh Anthropic-managed container per session; no outbound network except the listed host.
        config = {"type": "cloud", "networking": {"type": "limited", "allowed_hosts": ["contracts.internal.example"]}}
    environment = client.beta.environments.create(name="contract-audit", config=config)
    return agent.id, environment.id


def run(agent_id: str, environment_id: str, task: str, audit_log: list) -> str:
    session = client.beta.sessions.create(agent=agent_id, environment_id=environment_id, title="Weekly audit")
    reply = []
    with client.beta.sessions.events.stream(session.id) as stream:
        client.beta.sessions.events.send(session.id, events=[
            {"type": "user.message", "content": [{"type": "text", "text": task}]}])
        for event in stream:
            if event.type == "agent.tool_use":
                audit_log.append({"session": session.id, "tool": event.name, "input": event.input})
            elif event.type == "agent.message":
                reply += [b.text for b in event.content if b.type == "text"]
            elif event.type == "session.status_idle":   # nothing more to do: the task is finished
                break
    # The service keeps the full event history too, so the audit trail can be re-read later.
    return "".join(reply)


if __name__ == "__main__":
    log: list = []
    print(run(*create(on_prem=True), "Audit this week's contracts.", log))
    print(json.dumps(log, indent=1))
  • Four concepts:
    • An agent is the model, system prompt, tools, MCP servers and skills; you create it once and reference it by ID, and it carries a version.
    • An environment says where sessions run.
    • A session is one running task.
    • Events are the messages between your application and the agent.
  • Tools: agent_toolset_20260401 turns on the built-in tools: Bash, file operations, web search and fetch. Disable what the job doesn't need; the docs advise the smallest tool set.
  • Events, not request/response: open the stream, send a user.message, then handle agent.message and agent.tool_use events until session.status_idle says the agent has nothing more to do. You can send more events to steer it, or interrupt it. Logging each agent.tool_use gives the audit trail, and the service keeps the full event history as well.
  • Beta and data handling: every endpoint needs the managed-agents-2026-04-01 beta header, which the SDK adds. Sessions are stateful, and transcripts persist until you delete them. That's why Managed Agents isn't eligible for zero data retention or HIPAA, except when the whole service is self-hosted.
  • Also in the box: prompt caching and compaction built into the harness, persistent session filesystems, and scheduled deployments that run an agent on a cron schedule.

Cloud or self-hosted sandbox

Skill 1.1Where tools and code run, and what you operate.

  • Cloud environment (the default): each session gets a fresh, isolated Linux container on Anthropic's infrastructure, with common languages and tools installed. You set its network rules: limited networking allows only the hosts you list, and that list also restricts web search and fetch. You operate nothing.
  • Self-hosted sandbox ({"type": "self_hosted"}): Claude still runs on Anthropic's side and decides what to call. A worker you run executes the Bash and file tools on your machines and sends the results back. Choose it when files can't leave your network, when tools must reach internal services, or when your own compliance and audit controls must apply. You take on hardening the hosts, controlling egress, rotating the environment key and isolating sessions. Some cloud features, such as preinstalled packages and repository mounting, are lost.
  • What doesn't change: with either option, the conversation history and tool results go to Anthropic, because that's how the model sees what a tool returned. Web search and fetch always run on Anthropic's side.
  • Fully self-hosted Managed Agents: running the whole service yourself, including storing sessions, is available through your Anthropic account team. Model requests still go to Anthropic.

"Self-hosted sandbox, so nothing leaves our network" is wrong. The sandbox's files and processes stay with you, but whatever a tool returns to the model reaches the service. If a tool's output itself must not leave, change what the tool returns.

Self-hosting the Agent SDK

Skill 1.1What running your own harness involves.

Each Agent SDK session is a claude CLI subprocess that owns a shell, a working directory and its transcript files on local disk. Hosting it is not like hosting a stateless API wrapper. The hosting guide's session patterns:

  • Ephemeral: one container per task, destroyed when it ends.
  • Long-running: persistent containers serving many sessions.
  • Hybrid: containers that sleep when idle and restore sessions from a SessionStore, which is then required.
  • Multi-agent container: several agents sharing one environment.

You also own everything around the sessions:

  • Isolation: containers such as Docker, gVisor or Firecracker, and an egress proxy with domain allowlists.
  • Per-tenant settings: in a shared container, give each tenant its own working directory and config, so one tenant's CLAUDE.md and memory can't leak into another's session.
  • Limits: sessions have no timeout of their own, so set max_turns.
  • Sizing: about 1 GiB of RAM, 5 GiB of disk and one CPU per agent to start.

The hosting guide itself suggests Managed Agents when you don’t need to run the loop on your own infrastructure.

Key takeaways

  • Workflow when the steps are known, mistakes are costly or every step must be auditable; agent when the next step depends on what's found. Keep must-hold rules in code around an agent.
  • Use an orchestrator with subagents only for independent, broad parts that benefit from parallel, isolated contexts; one agent is cheaper for sequential work.
  • Runtimes: your own loop on the Messages API (full control), a self-hosted Agent SDK harness (your containers, your isolation and session storage), or Claude Managed Agents (beta; Anthropic hosts the loop, best for long-running, asynchronous work).
  • Managed Agents: agent, environment, session and events; agent_toolset_20260401; stream until session.status_idle; beta header managed-agents-2026-04-01; not ZDR or HIPAA eligible unless fully self-hosted.
  • Cloud environment by default; a self-hosted sandbox when files or tools must stay on your infrastructure. Either way, conversation history and tool results reach Anthropic.
