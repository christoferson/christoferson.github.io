Systems Manager operations

Skill 3.2.1Automate operational processes by using AWS services and features (for example, AWS Systems Manager)

Becoming a managed node

The three prerequisites

The node tools (Run Command, State Manager, Patch Manager, Session Manager, Inventory) work only on managed nodes. When an instance doesn't appear in Fleet Manager, check these three things in order:

  1. SSM AgentInstalled and running. It is preinstalled on Amazon Linux, recent Ubuntu and Windows Server AMIs from AWS.
  2. PermissionsAn instance profile with the AmazonSSMManagedInstanceCore policy, or Default Host Management Configuration (below).
  3. Network pathOutbound HTTPS (443) to the ssm, ssmmessages and ec2messages endpoints, through a NAT gateway or interface VPC endpoints in private subnets. No inbound rules are needed.

Default Host Management Configuration

Turned on per account and Region in Fleet Manager, it makes every EC2 instance a managed node without an instance profile, using the role AWSSystemsManagerDefaultEC2InstanceManagementRole. Instances need IMDSv2 and SSM Agent 3.2.582.0 or later. If an instance does have a profile granting Systems Manager access, the profile wins.

"Instances in a private subnet with no internet access don't show up in Systems Manager": create interface endpoints for ssm, ssmmessages and ec2messages (and an S3 gateway endpoint for patches and agent updates), with a security group allowing 443 from the instances.

Run Command: one-off actions at scale

What it does

Runs a Systems Manager document (such as AWS-RunShellScript or AWS-RunPowerShellScript) on many nodes at once, with no SSH. Choose nodes by tags, resource group or instance ID.

  • Concurrency (--max-concurrency, a number or percentage, default 50): how many nodes run at once.
  • Error threshold (--max-errors, default 0): stop sending to more nodes after this many failures. A value of 2 stops after the third error; commands already running finish.
  • Output to S3 or CloudWatch Logs (the console shows only the first part), and SNS notifications on status changes, which need a service role Systems Manager can pass.
Restart the app on every orders server, a quarter at a time 
# stop if more than 2 servers fail
aws ssm send-command \
  --document-name AWS-RunShellScript \
  --targets Key=tag:App,Values=orders \
  --parameters \
    'commands=["systemctl restart app"]' \
  --max-concurrency 25% \
  --max-errors 2 \
  --output-s3-bucket-name orders-ssm-out

State Manager: keep a configuration applied

Associations

An association applies a document to target nodes on a schedule and reapplies it, so the configuration is enforced continuously rather than set once. Examples: keep the CloudWatch agent installed and configured, join instances to a domain, collect software inventory (AWS-GatherSoftwareInventory). Associations run as soon as they're created, then on their cron or rate schedule, and report to Compliance. New instances with matching tags are picked up automatically. State Manager has no extra charge.

Run Command is a one-off ("do this now"). State Manager is desired state ("keep it like this, and fix new or drifted instances").

Patch Manager

Baselines

A patch baseline defines which patches are approved: by classification and severity, with an auto-approval delay (for example, approve security patches 7 days after release), plus explicitly approved or rejected patches. AWS supplies a default baseline per operating system; create custom ones to change the rules.

Scanning and installing

Patching runs the AWS-RunPatchBaseline document with Operation set to Scan (report missing patches only) or Install (install and, by default, reboot if needed). With RebootOption=NoReboot, patches are reported as installed pending reboot and the node stays non-compliant until it restarts.

Patch policies or maintenance windows

  • Patch policies (through Quick Setup) are the recommended way: one policy sets the baselines and separate scan and install schedules for the whole organization, chosen OUs, accounts and Regions.
  • Maintenance windows with a Run Command task are the older, manual way, still used when patching must happen in an agreed window. Patch groups (the Patch Group tag mapping nodes to baselines) are legacy; patch policies don't need them.

Results appear in Patch Manager's compliance reports, per node: Compliant, or Non-Compliant with the missing patches listed.

Weekly patch scan as a State Manager association 
# 02:00 UTC every Sunday
aws ssm create-association \
  --name AWS-RunPatchBaseline \
  --association-name orders-patch-scan \
  --targets Key=tag:App,Values=orders \
  --parameters 'Operation=["Scan"]' \
  --schedule-expression \
    "cron(0 2 ? * SUN *)"

Maintenance windows

Disruptive work in an agreed slot

A maintenance window has a schedule (cron or rate, with a time zone), a duration and a cutoff (stop starting new tasks this long before the end), targets and tasks. Tasks can be Run Command, Automation, Lambda or Step Functions, each with its own concurrency, error threshold and priority. Use them for anything that interrupts service: patch installs with reboots, AMI creation, restarts.

Access and data

Session Manager

A shell (or PowerShell) on an instance from the console or CLI with no inbound ports, bastion hosts or SSH keys; access is controlled by IAM and every session start is recorded in CloudTrail. Session output can be logged to S3 or CloudWatch Logs and encrypted with KMS. Port forwarding reaches a database or web port through the instance, but those sessions aren't logged. Just-in-time node access, in the unified Systems Manager console, adds approval policies so people get access only when a request is approved, automatically or by a person.

Parameter Store

Configuration values and secrets (SecureString, encrypted with KMS) referenced by scripts, Lambda functions and templates. Standard tier: up to 10,000 parameters per account and Region, 4 KB values, free. Advanced tier: 100,000 parameters, 8 KB values, parameter policies (such as expiration) and cross-account sharing, for a charge. You can upgrade a parameter to advanced but not downgrade it.

Inventory and OpsCenter

Inventory collects installed software, files and settings from nodes; with a resource data sync it can be gathered into one S3 bucket and queried with Athena. OpsCenter collects operational issues as OpsItems, created from CloudWatch alarms or EventBridge rules, with related resources attached and runbooks you can run straight from the OpsItem.

Change Manager and Incident Manager closed to new customers on November 7, 2025, and Application Manager is no longer open to new customers either. The Explorer dashboard leaves the console on December 31, 2026 (its data and APIs remain). Expect the exam to favor the core tools above.

Event-driven automation

Skill 3.2.2Implement event-driven automation by using AWS services and features (for example, Lambda, S3 Event Notifications, Amazon EventBridge, AWS DevOps Agent)

S3 Event Notifications

What they send, and where

  • Events: object created (s3:ObjectCreated:*: Put, Post, Copy, CompleteMultipartUpload), removed, restored from archive, replication failures, lifecycle expiration and transition, tagging and ACL changes.
  • Destinations: a Lambda function, an SNS standard topic, an SQS standard queue (FIFO queues and topics aren't supported), or EventBridge. Each must be in the bucket's Region.
  • Filters: a key prefix and suffix only (invoices/ and .pdf). Two configurations for the same event type can't have overlapping filters.
  • Delivery: at least once and not ordered, so consumers must handle duplicates.

Permissions: the usual failure

S3 must be allowed to deliver to the destination, through the Lambda function's resource-based policy, the SNS topic policy or the SQS queue policy. Without it, saving the notification configuration fails with a validation error. The console adds the Lambda permission for you; the CLI and templates don't.

Let the bucket invoke the function 
aws lambda add-permission \
  --function-name orders-invoices \
  --statement-id s3-invoke \
  --action lambda:InvokeFunction \
  --principal s3.amazonaws.com \
  --source-arn arn:aws:s3:::orders-in \
  --source-account 111111111111

Or send everything to EventBridge

Turn on EventBridge for the bucket and S3 sends all its events to the default event bus. Rules can then filter on more than prefix and suffix (object size, several key patterns), deliver to many targets, and archive or replay events.

Turn on EventBridge delivery for a bucket 
aws s3api \
  put-bucket-notification-configuration \
  --bucket orders-in \
  --notification-configuration \
    '{"EventBridgeConfiguration": {}}'
Rule pattern: new objects under invoices/ 
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": { "name": ["orders-in"] },
    "object": {
      "key": [{ "prefix": "invoices/" }]
    }
  }
}

A function that writes its output back into the bucket that triggers it invokes itself in a loop. Write output to another bucket or a prefix the trigger doesn't match. Lambda's recursive loop detection stops such loops through S3, SQS, SNS and EventBridge after about 16 invocations, but don't rely on it.

Lifecycle deletess3:ObjectRemoved fires for deletes made by requests, not for objects that a lifecycle rule expires. Use the s3:LifecycleExpiration events for those.

Lambda as the automation engine

Asynchronous invocations

S3, SNS and EventBridge invoke Lambda asynchronously: Lambda queues the event and the caller doesn't wait. On a function error, Lambda retries twice by default (configurable 0 to 2); throttled events are retried for up to 6 hours (the maximum event age, which you can lower). Because an event can arrive more than once, make functions idempotent.

Catching failures

Destinations send a record of each invocation, on success or on failure, to SQS, SNS, another Lambda function, an EventBridge bus or (failures only) S3, including the error details. A dead-letter queue (SQS or SNS) is the older option and carries only the original event. Prefer destinations.

Retry once, give up after an hour, record failures 
aws lambda \
  put-function-event-invoke-config \
  --function-name orders-invoices \
  --maximum-retry-attempts 1 \
  --maximum-event-age-in-seconds 3600 \
  --destination-config \
    file://destinations.json

Limits that shape the design

A function runs for at most 15 minutes; longer jobs belong in Step Functions, an Automation runbook or a container task. Its execution role must allow every API it calls. Concurrency is shared across the account's functions (1,000 by default per Region), so reserve concurrency for automation that must never be throttled.

EventBridge as the router

Reacting to AWS events

Most AWS services publish events to the default bus. Rules match them and invoke up to five targets each, including Lambda, Step Functions, SNS, SQS and, for operations, Systems Manager Automation, Run Command and OpsItems. Patterns, retries and troubleshooting are in Task 1.2. Typical operational rules:

  • EC2 Instance State-change Notification with state stopped: start an Automation runbook or notify the team.
  • AWS Health events (scheduled maintenance, retirement of an instance): open an OpsItem or ticket. Health rules are per Region; events for global services such as IAM arrive in us-east-1.
  • Config Rules Compliance Change: notify, or let AWS Config's own automatic remediation run an Automation runbook on the non-compliant resource, with a set number of retries.
  • GuardDuty findings: isolate the instance with a runbook.
Rule pattern: any instance stopping 
{
  "source": ["aws.ec2"],
  "detail-type": [
    "EC2 Instance State-change Notification"
  ],
  "detail": { "state": ["stopped"] }
}

EventBridge Scheduler

Automation on a clock

For jobs that run on a schedule rather than in response to an event (stop development instances every evening, run a nightly report), use EventBridge Scheduler. Scheduled rules on an event bus still work but AWS now calls them a legacy feature. Scheduler adds:

  • One-time schedules (at(...)) as well as rate and cron.
  • Time zones with daylight saving handled, so "08:00 London time" stays 08:00.
  • Flexible time windows to spread invocations rather than firing everything at once.
  • Universal targets: call almost any AWS API directly (for example ec2:StopInstances) without writing a Lambda function.
  • Retries and a dead-letter queue. Completed one-time schedules still count toward the quota until deleted, unless you set them to delete themselves after running.
Stop dev instances at 19:00 London time, weekdays 
# target.json: StopInstances API + role
aws scheduler create-schedule \
  --name stop-dev-evening \
  --schedule-expression \
    "cron(0 19 ? * MON-FRI *)" \
  --schedule-expression-timezone \
    Europe/London \
  --flexible-time-window Mode=OFF \
  --target file://target.json

Investigating events: AWS DevOps Agent

Where it fits

AWS DevOps Agent (generally available since March 31, 2026) starts an investigation automatically when an alert arrives, works out a likely root cause from metrics, logs, recent deployments and code, and proposes mitigation steps. It's advisory: it posts findings and recommendations to tickets and chat, and fixes go to a person or a coding agent rather than being applied directly. Use it for diagnosis, and EventBridge with runbooks and Lambda for automated fixes. Details are in Task 1.2.

"Run this on a schedule" is EventBridge Scheduler. "Run this when something happens in AWS" is an EventBridge rule. "Run this when an object arrives" is an S3 Event Notification (simple, one destination) or S3 to EventBridge (advanced filtering, many targets). "Run this on the instances" is Run Command, State Manager or a maintenance window.

Key takeaways

  • Managed nodes need SSM Agent, permissions (instance profile with AmazonSSMManagedInstanceCore, or Default Host Management Configuration) and outbound 443 to ssm, ssmmessages and ec2messages (VPC endpoints in private subnets).
  • Run Command does one-off work at scale, targeted by tags, with concurrency and error thresholds and output to S3 or CloudWatch Logs. State Manager associations keep configuration applied on a schedule.
  • Patch Manager: baselines with auto-approval delays; AWS-RunPatchBaseline Scan or Install; patch policies through Quick Setup across accounts and Regions; maintenance windows for disruptive work.
  • Session Manager replaces SSH and bastions, with IAM control and session logging; Parameter Store standard (10,000, 4 KB, free) versus advanced (100,000, 8 KB, policies, charged).
  • S3 Event Notifications go to Lambda, standard SNS or SQS, or EventBridge, filtered by prefix and suffix, delivered at least once; the destination's policy must allow S3. Send to EventBridge for richer filtering and many targets. Avoid write-back loops.
  • Async Lambda retries twice and keeps events up to 6 hours; use destinations to capture failures; functions must be idempotent and finish within 15 minutes.
  • EventBridge rules turn AWS events (instance state changes, Health, Config, GuardDuty) into Automation, Run Command or OpsItems; EventBridge Scheduler runs jobs on cron, rate or one-time schedules with time zones and universal targets.
  • AWS DevOps Agent investigates and recommends; automated fixes still run through EventBridge, runbooks and Lambda.
