Overview

Task 2.1

Implement scalability and elasticity.

Scalability is the ability to handle more load by adding resources; elasticity is doing it automatically in both directions, adding capacity when demand rises and removing it when demand falls, so you pay only for what the load needs. Questions describe a load pattern (a daily peak, a sudden spike, a slow-booting application, a database overwhelmed by reads) and ask for the scaling mechanism or the setting that fixes the behaviour.

The examples continue the orders application: an EC2 Auto Scaling group behind an Application Load Balancer, a payments Lambda function, an ECS service, an RDS for PostgreSQL database and a DynamoDB table of shopping carts.

Scaling compute

Skill 2.1.1Configure and manage scaling mechanisms in compute environments

EC2 Auto Scaling: the building blocks

Group, capacity and launch template

An Auto Scaling group keeps a number of instances running between a minimum and maximum, aiming for the desired capacity, spread across the Availability Zones of its subnets. It launches instances from a launch template (AMI, instance type, security groups, instance profile, user data). Launch templates have versions, so a change is a new version the group can adopt.

Launch configurationsThe older alternative. They support no instance types released since January 1, 2023, and accounts created on or after October 1, 2024 can't create them at all. Use launch templates.

Scaling policies

Target tracking (the default choice)

You pick a metric and a target value; Auto Scaling adds and removes instances to keep the metric near the target, like a thermostat. Predefined metrics are average CPU (ASGAverageCPUUtilization), average network in and out, and ALBRequestCountPerTarget, the requests each instance receives from the load balancer. Custom metrics and metric math work too, for example SQS messages per instance. AWS recommends target tracking first.

Keep the orders fleet near 50% average CPU 
aws autoscaling put-scaling-policy \
  --auto-scaling-group-name orders \
  --policy-name cpu-50 \
  --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{
    "PredefinedMetricSpecification": {
      "PredefinedMetricType":
        "ASGAverageCPUUtilization"
    },
    "TargetValue": 50.0
  }'

Target tracking creates and manages its own CloudWatch alarms; don't edit or delete them.

Step scaling

Alarm-driven, with steps that add more capacity the further the metric breaches: add 1 instance at 60–80% CPU, 3 above 80%. Use it when the response must be proportional in a way target tracking can't express.

Simple scaling

One adjustment per alarm, then a cooldown (default 300 seconds) during which no further scaling happens. AWS advises against it: it reacts slowly to large spikes.

Scheduled scaling

Changes minimum, maximum or desired capacity at set times, for known patterns: raise the minimum before the 9 a.m. rush, lower it at night. Combine it with target tracking for the unexpected.

Predictive scaling

Forecasts load from history and launches capacity before the predicted rise, so instances are ready when traffic arrives. It needs at least 24 hours of data and works best with 14 days, forecasts hourly for the next 48 hours, and refreshes the forecast every 6 hours. Start in forecast only mode to check the forecast, then switch to forecast and scale. It only scales out; pair it with target tracking to scale in and to handle anything the forecast missed.

Recurring daily or weekly peaks with slow-starting instances point to predictive scaling (or scheduled scaling for fixed times). Keeping a metric at a level points to target tracking. "Scaling reacts too slowly to a big spike" with simple scaling: switch to target tracking or step scaling.

Settings that change how scaling behaves

Default instance warmup

How long a new instance needs before its metrics count toward scaling decisions. Without it, a booting instance at 100% CPU makes the group launch even more instances. It isn't on by default; AWS strongly recommends setting it, starting at 300 seconds and adjusting to how long the application really takes to start.

Health checks and the grace period

By default the group uses EC2 status checks: an instance is replaced only if the instance itself fails. Turn on ELB health checks so instances that are running but failing the load balancer's health check are also replaced. The health check grace period stops new instances being judged before they have started. Its default is 300 seconds in the console but 0 when the group is created with the CLI or an SDK, a common cause of instances being terminated as soon as they launch.

Warm pools

A pool of pre-initialized instances kept beside the group, Stopped (cheapest: you pay only for EBS), Hibernated (memory preserved) or Running. Scale-out takes an instance from the pool instead of booting a new one, which cuts launch time for applications with long start-ups. An instance reuse policy returns scaled-in instances to the pool instead of terminating them. Warm pools don't work with Spot instances.

Lifecycle hooks

Pause an instance as it launches or terminates so you can do work first: install software or register it with a service when launching, copy logs off it or deregister it when terminating. The instance waits in a Pending:Wait or Terminating:Wait state until your automation (often a Lambda function or runbook triggered through EventBridge) calls CompleteLifecycleAction, or the heartbeat timeout expires (default 3,600 seconds, up to 7,200, extendable with heartbeats). If the timeout expires, the default result is ABANDON.

Mixed instances and Spot

A mixed instances policy lets one group use several instance types and both purchase options: an On-Demand base capacity, a percentage of On-Demand above that, and the rest as Spot. Use the price-capacity-optimized Spot allocation strategy and many instance types (AWS suggests at least 10), so the group can find Spot capacity. Capacity Rebalancing replaces a Spot instance proactively when it receives a rebalance recommendation, before it is interrupted.

Scale-in: which instance goes

Auto Scaling first keeps Availability Zones balanced, then by default terminates instances with the oldest launch template or configuration, then the one closest to its next billing hour. Other termination policies include OldestInstance and NewestInstance. Instance scale-in protection stops an instance being chosen for scale-in (for example, while it finishes a long job), but doesn't stop replacement after a failed health check.

Containers

Amazon ECS

Two layers scale separately:

  • Service auto scaling changes the number of tasks, through Application Auto Scaling, with target tracking (on ECSServiceAverageCPUUtilization, ECSServiceAverageMemoryUtilization or ALBRequestCountPerTarget), step, scheduled or predictive policies.
  • Cluster capacity, when tasks run on EC2: a capacity provider with managed scaling grows and shrinks the Auto Scaling group to fit the tasks, aiming at a target capacity percentage (100% packs instances fully; lower keeps spare room). Managed termination protection stops instances with running tasks being removed.

On Fargate only the first layer exists: there are no instances to scale.

Amazon EKS

Pods scale with the Horizontal Pod Autoscaler (which needs the Kubernetes Metrics Server). Nodes scale with Karpenter, which launches right-sized instances directly in under a minute, or the Cluster Autoscaler, which resizes Auto Scaling groups or managed node groups. EKS Auto Mode runs Karpenter-based node scaling for you.

AWS Lambda

Concurrency

Lambda scales by running more execution environments, one per concurrent request. Each function can add up to 1,000 environments every 10 seconds. The account has a Regional concurrency quota (1,000 by default, raisable). When there's no capacity left, synchronous calls get 429 TooManyRequestsException (throttling) and the Throttles metric rises.

  • Reserved concurrency: guarantees a function a share of the account's concurrency and caps it at that number, so one function can't starve the others (or overwhelm a database). Setting it to 0 stops the function from running.
  • Provisioned concurrency: keeps a number of environments initialized and ready, removing cold starts for latency-sensitive functions. It is set on a version or alias, costs money while configured, and can itself be scaled with Application Auto Scaling, on a schedule or by tracking LambdaProvisionedConcurrencyUtilization.

Reserved concurrency doesn't make a function faster or warm; it guarantees and limits capacity. Cold starts are removed by provisioned concurrency.

Caching

Skill 2.1.2Implement caching by using AWS services to enhance dynamic scalability (for example, Amazon CloudFront, Amazon ElastiCache)

Caching scales a system by not doing work twice. Every request served from a cache is one the application servers and database never see, so the same backend handles far more users, faster.

Amazon CloudFront

How it caches

CloudFront serves content from edge locations near users. On a request it looks up the cache key (by default the URL path); a hit is served from the edge, a miss goes to the origin (an S3 bucket, a load balancer, any HTTP server) and the response is cached for its time to live.

  • Cache policy: defines the cache key (which headers, cookies and query strings make a response different) and the TTLs. Keep the cache key small: every value you add splits the cache and lowers the hit ratio.
  • Origin request policy: sends extra headers, cookies or query strings to the origin without adding them to the cache key.
  • TTLs: minimum, default and maximum. The origin's Cache-Control headers set the TTL within the minimum and maximum; without them the default applies (24 hours in the legacy settings).
  • Origin Shield: an extra caching layer in one Region in front of the origin, so all edge locations' misses are collapsed into fewer origin requests.

Dynamic content

CloudFront helps even with uncacheable content: connections from the edge to the origin are reused and run over the AWS network, and short TTLs (even a few seconds) on popular API responses can absorb huge spikes.

Updating cached content

Prefer versioned file names (app.v42.js) so new content gets a new cache key. Invalidations remove objects from edge caches immediately; the first 1,000 paths each month are free, and a wildcard such as /images/* counts as one path.

Amazon ElastiCache

Engines

  • Valkey (AWS's recommended engine since October 2024, the open-source fork of Redis) and Redis OSS: rich data types, replication, Multi-AZ failover, persistence, pub/sub. Use them when you need high availability or more than simple key-value caching.
  • Memcached: simple, multi-threaded key-value cache, with no replication or failover; losing a node loses its cached data.

ElastiCache Serverless scales capacity automatically with no nodes to choose; node-based clusters give you control of instance types.

Scaling node-based Valkey and Redis OSS clusters

Cluster mode disabled: one shard, a primary plus up to 5 read replicas; scale reads with replicas and writes only by a larger node type. Cluster mode enabled: data is partitioned across up to 500 shards, each with up to 5 replicas, so both reads and writes scale out. ElastiCache auto scaling can add and remove shards or replicas automatically (target tracking or scheduled) on cluster mode enabled clusters.

Caching strategies

  • Lazy loading (cache-aside): the application checks the cache, and on a miss reads the database and writes the result to the cache. Only requested data is cached, but the first request is slow and data can be stale.
  • Write-through: the application writes to the cache whenever it writes to the database. Data is always fresh, but you cache data that may never be read.
  • TTL: an expiry on each key limits staleness and stops the cache filling with dead data. Most designs combine lazy loading with a TTL.

Metrics that matter

Evictions rising means the cache is too small: keys are pushed out before they expire (scale up or out). EngineCPUUtilization (on nodes with four or more vCPUs; CPUUtilization on smaller ones) shows the engine's own load. Also watch CurrConnections, SwapUsage, ReplicationLag and memory usage, and compare cache hits with misses for the hit ratio.

DynamoDB Accelerator (DAX)

A cache made for DynamoDB

An in-memory cache in front of DynamoDB that reduces read latency from milliseconds to microseconds, with no application caching code: the application uses the DAX client with the same DynamoDB API calls. An item cache serves GetItem and a query cache serves Query and Scan; writes go through DAX to the table. DAX serves only eventually consistent reads: strongly consistent reads pass straight through to DynamoDB uncached. A cluster has up to 11 nodes; use at least three, across Availability Zones, in production.

"Microsecond reads for a DynamoDB table with no code changes" points to DAX. "Cache database query results, sessions or leaderboards, with failover" points to ElastiCache for Valkey or Redis OSS. "Cache static and popular content close to users" points to CloudFront.

Scaling managed databases

Skill 2.1.3Configure and manage scaling in AWS managed databases (for example, Amazon RDS, DynamoDB)

Amazon RDS

Scaling up

Change the DB instance class for more CPU and memory. It causes downtime while the instance is replaced; on a Multi-AZ deployment the standby is modified first and then failed over to, which minimizes the outage. Apply it immediately or in the next maintenance window. Storage scales separately, without downtime, including automatically with storage autoscaling (Task 1.3).

Scaling out reads: read replicas

A read replica is a copy kept up to date by asynchronous replication, with its own endpoint. The application sends reads (reports, searches) to replicas and writes to the primary. Each source can have up to 15 read replicas, in the same or another Region. Watch ReplicaLag: replicas can return slightly stale data. A replica can be promoted to a standalone database, for example for disaster recovery. RDS doesn't add replicas automatically.

Not the same as Multi-AZA Multi-AZ standby exists for availability and can't serve reads (in a Multi-AZ instance deployment). Read replicas are for scaling reads (Task 2.2).

Amazon Aurora

Aurora Replicas and Aurora Auto Scaling

An Aurora cluster has one writer and up to 15 Aurora Replicas sharing the same storage, so replica lag is usually under 100 milliseconds. The reader endpoint spreads connections across replicas. Aurora Auto Scaling adds and removes replicas with a target tracking policy on average reader CPU (RDSReaderAverageCPUUtilization) or connections (RDSReaderAverageDatabaseConnections); the cluster needs at least one reader to start. Custom endpoints send particular workloads, such as analytics, to a chosen set of instances.

Aurora Serverless (v2)

Instances whose capacity scales in place, in increments as small as 0.5 Aurora capacity units (ACUs, each about 2 GiB of memory with matching CPU), within a minimum and maximum you set. The range is 0 to 256 ACUs (up to 384 on recent Aurora PostgreSQL versions). With a minimum of 0 ACUs the instance pauses when idle and costs nothing for compute, at the price of a short resume delay. A cluster can mix serverless and provisioned instances. AWS's documentation now calls it simply "Aurora Serverless", since the original version reached end of life in March 2025.

FitsUnpredictable or spiky load, development and test databases, and many small databases.

Amazon DynamoDB

On-demand capacity mode

The default and recommended mode. You pay per request, with no capacity to plan; the table instantly handles up to double its previous peak, and a new table starts able to sustain 4,000 writes and 12,000 reads per second. Growth beyond double the previous peak within 30 minutes can throttle. An optional maximum throughput setting caps a table's cost.

Provisioned capacity mode with auto scaling

You set read and write capacity units, cheaper for steady, predictable traffic. DynamoDB auto scaling (Application Auto Scaling) adjusts them to keep consumed capacity at a target utilization between 20% and 90% (70% in the console by default), for the table and each global secondary index. It reacts over minutes, so a sudden spike can still be throttled.

Switching and throttling

You can switch a table from provisioned to on-demand up to four times in a rolling 24 hours, and from on-demand to provisioned at any time. Throttling shows as ThrottledRequests, ReadThrottleEvents and WriteThrottleEvents, and newer metrics give the cause: a hot key range, the account limit, or the table's maximum on-demand throughput. Burst capacity (up to 300 seconds of unused capacity) and adaptive capacity (shifting capacity to busy partitions) absorb some uneven load, but a single hot partition key still throttles: design keys that spread traffic.

"DynamoDB is throttling during a sudden, unpredictable spike, with auto scaling enabled" is solved by on-demand mode (or DAX for read-heavy spikes), not by raising the auto scaling target: auto scaling responds too slowly for sudden spikes.

Key takeaways

  • Auto Scaling groups use launch templates (launch configurations are effectively retired). Prefer target tracking; add scheduled scaling for known times and predictive scaling for recurring patterns; avoid simple scaling and its cooldown.
  • Set default instance warmup, use ELB health checks, and check the health check grace period (0 seconds by default from the CLI). Warm pools speed up slow boots; lifecycle hooks pause launch or termination for custom work; mixed instances with price-capacity-optimized Spot and Capacity Rebalancing cut cost.
  • ECS scales tasks with service auto scaling and EC2 capacity with capacity providers; EKS scales pods with HPA and nodes with Karpenter, Cluster Autoscaler or Auto Mode. Lambda reserved concurrency guarantees and caps; provisioned concurrency removes cold starts; throttling returns 429.
  • CloudFront caches by cache key with TTLs from the cache policy and origin headers; keep the key small, use Origin Shield to protect the origin, versioned names over invalidations.
  • ElastiCache: Valkey or Redis OSS for replication, failover and rich types (cluster mode enabled to scale writes); Memcached for simple multi-threaded caching. Lazy loading plus TTL is the usual pattern; rising Evictions means the cache is too small. DAX gives DynamoDB microsecond reads, but not for strongly consistent reads.
  • RDS scales up by instance class (brief downtime, minimized with Multi-AZ) and out for reads with up to 15 asynchronous read replicas. Aurora has up to 15 replicas with Aurora Auto Scaling; Aurora Serverless scales in ACUs and can pause at 0.
  • DynamoDB on-demand absorbs sudden spikes; provisioned with auto scaling (target 20–90%) is cheaper for steady load. Hot partition keys throttle in any mode.
