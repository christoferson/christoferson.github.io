Overview

Task 1.3

Implement performance optimization strategies for compute, storage, and database resources.

This task absorbed the old SOA-C02 cost and performance domain, so performance and cost go together throughout: the right answer is usually the one that meets the requirement for the least money. Questions give a symptom (a slow volume, a throttled bucket, a database out of connections) or a goal (cut cost without losing performance) and ask which metric shows the problem and which change fixes it.

The examples continue the orders application: an EC2 Auto Scaling group behind a load balancer, an RDS for PostgreSQL database, a payments Lambda function, and an S3 bucket of order documents and images.

Optimizing compute

Skill 1.3.1Optimize compute resources and remediate performance problems by using performance metrics, resource tags, and AWS tools

Reading the metrics

Over-provisioned or under-provisioned?

Look at utilization over at least two weeks, at peaks as well as averages. An instance averaging 8% CPU with a peak of 20% is over-provisioned: a smaller size or a cheaper family will do. One sitting at 90% CPU with rising latency is under-provisioned: scale up, scale out, or move to a compute-optimized family. Memory needs the CloudWatch agent (Task 1.1), because EC2 doesn't report it.

Burstable instances (T3, T3a, T4g)

Burstable instances earn CPU credits while below their baseline and spend them above it. Watch CPUCreditBalance: a balance draining to zero means the instance is running above baseline most of the time. T3, T3a and T4g launch in unlimited mode by default, so they keep running fast after the credits are gone, and the extra is charged (CPUSurplusCreditBalance and CPUSurplusCreditsCharged). If that happens constantly, a fixed-performance instance such as an M or C family is cheaper. In standard mode the instance is held at its baseline instead, which looks like a sudden slowdown.

Using tags

Finding and grouping what to optimize

Tags (App=orders, Environment=prod, Owner=payments-team) let you act on a whole workload: filter CloudWatch and Compute Optimizer views, build AWS Resource Groups, target Systems Manager automations (Task 1.2), and, once activated as cost allocation tags, break down spend by application in Cost Explorer. Tags also drive savings automation, such as a scheduled runbook that stops every instance tagged Environment=dev at night.

AWS tools

AWS Compute Optimizer

Analyzes CloudWatch metrics with machine learning and recommends better-fitting resources, each marked as over-provisioned, under-provisioned or optimized, with the estimated saving or performance risk. It covers EC2 instances, Auto Scaling groups, EBS volumes, Lambda functions (memory size), ECS services on Fargate, RDS and Aurora databases, commercial software licenses and several other services.

  • History: by default it looks back 14 days, and needs at least 30 hours of metrics for an EC2 instance. Enhanced infrastructure metrics (paid) extends the lookback to 93 days, which captures monthly cycles.
  • Memory: without the CloudWatch agent publishing memory metrics, it can't see memory, so its EC2 recommendations are based on CPU, network and disk alone.
  • Organizations: enable it for all accounts from the management account or a delegated administrator.
  • Cost Optimization Hub: collects Compute Optimizer and other savings recommendations in one place, taking your Reserved Instance and Savings Plans pricing into account.

Other tools

  • AWS Trusted Advisor: checks for idle or low-utilization instances, idle load balancers and unattached Elastic IPs, among many others.
  • Cost Explorer: shows where the money goes, by service, account or tag, and the effect of changes.
  • Savings Plans: once the size is right, commit to a steady level of usage for a lower rate. Right-size first, then commit.

"Recommend instance types based on utilization", "right-size Lambda memory" or "find over-provisioned EBS volumes" all point to AWS Compute Optimizer. If the question says the recommendations ignore memory, the CloudWatch agent isn't installed.

EBS performance

Skill 1.3.2Analyze Amazon EBS performance metrics, troubleshoot issues, and optimize volume types to improve performance and reduce cost

Volume types

TypePerformanceUse it for
gp3 (SSD)3,000 IOPS and 125 MiB/s at any size; provision up to 80,000 IOPS and 2,000 MiB/s, up to 64 TiBThe default for almost everything: boot volumes, applications, most databases
gp2 (SSD)3 IOPS per GiB (100 to 16,000); volumes under 1 TiB burst to 3,000 IOPS on creditsExisting volumes; migrate to gp3
io2 Block Express (SSD)Up to 256,000 IOPS, 4,000 MiB/s and 64 TiB; sub-millisecond latency; 99.999% durabilityThe most demanding databases; Multi-Attach
io1 (SSD)Up to 64,000 IOPS, 1,000 MiB/s and 16 TiB; 50 IOPS per GiBOlder provisioned IOPS volumes; io2 is better
st1 (HDD)Throughput-optimized, up to 500 MiB/s; 125 GiB minimumLarge sequential reads: logs, big data, data warehouses
sc1 (HDD)Cold, up to 250 MiB/s; the cheapest per GiBInfrequently read sequential data
  • HDD volumes (st1, sc1) can't be boot volumes and are poor at small random I/O.
  • gp3 sets IOPS and throughput independently of size, within ratios: up to 500 IOPS per GiB, and up to 0.25 MiB/s of throughput per provisioned IOPS.
  • Since April 2025 every io2 volume is io2 Block Express. On instances not built on Nitro, io1 and io2 top out at 32,000 IOPS.

gp2 to gp3 is the classic optimization: gp3 is cheaper per GiB and gives 3,000 IOPS regardless of size. A 200 GiB gp2 volume has a baseline of only 600 IOPS and depends on burst credits; as gp3 it gets 3,000 IOPS all the time for less money.

Changing a volume: Elastic Volumes

How it works

You can change a volume's type, size, IOPS and throughput while it stays attached and in use. The modification goes through modifying, optimizing and completed; extra space is usable once it reaches optimizing, after you extend the file system inside the instance. You can make up to four modifications in a rolling 24 hours, each finishing before the next starts (until January 2026 the rule was one change every six hours). You can't shrink a volume or cancel a modification.

Convert a gp2 volume to gp3 in place 
aws ec2 modify-volume \
  --volume-id vol-0abc1234def567890 \
  --volume-type gp3 \
  --iops 3000 \
  --throughput 125

# optimizing, then completed
aws ec2 describe-volumes-modifications \
  --volume-ids vol-0abc1234def567890

Metrics and what they mean

Volume metrics (AWS/EBS)

  • VolumeQueueLength: I/O requests waiting. Consistently high with high latency means the volume can't keep up: raise IOPS or move to a faster type.
  • BurstBalance (gp2, st1, sc1): percentage of burst credits left. Falling to zero means performance will drop to baseline; move to gp3.
  • VolumeReadOps, VolumeWriteOps, VolumeReadBytes, VolumeWriteBytes: the workload's IOPS and throughput.
  • VolumeThroughputPercentage (provisioned IOPS volumes): how much of the provisioned IOPS is delivered.
  • VolumeIdleTime: seconds with no I/O. An always-idle volume may not be needed.
  • Nitro instances add VolumeAvgReadLatency, VolumeAvgWriteLatency, VolumeIOPSExceededCheck and VolumeThroughputExceededCheck: the exceeded checks report 1 when the workload is asking for more than the volume is provisioned for.

Instance limits

The instance has its own EBS bandwidth and IOPS limit, and a volume can't go faster than the instance lets it. A 40,000 IOPS volume on a small instance gets only what that instance size supports. In AWS/EC2, InstanceEBSIOPSExceededCheck and InstanceEBSThroughputExceededCheck show the instance limit being hit; on smaller sizes with burstable EBS bandwidth, EBSIOBalance% and EBSByteBalance% show the burst running out. The fix is a larger instance, not a faster volume.

Troubleshooting slow volumes

Slow right after restoring from a snapshot

A volume created from a snapshot loads its blocks from S3 the first time each block is read (lazy loading), so first reads are slow. Options:

  • Pre-warm by reading every block once, with dd or fio.
  • Fast Snapshot Restore on the snapshot, per Availability Zone: volumes are fully initialized at creation (charged per snapshot per AZ per hour).
  • Provisioned rate for volume initialization: request a rate between 100 and 300 MiB/s when creating the volume, so initialization finishes in a predictable time (charged per GiB of snapshot data).

Working through a slow volume

  1. Is the workload asking for more than the volume has?VolumeIOPSExceededCheck or VolumeThroughputExceededCheck at 1, or a high queue length: raise IOPS or throughput, or change type.
  2. Is a burst bucket empty?BurstBalance at zero on gp2, st1 or sc1: move to gp3.
  3. Is the instance the limit?The instance-level exceeded checks: choose a larger instance.
  4. Was the volume just restored?Initialization is still running: pre-warm, or use Fast Snapshot Restore next time.

S3 performance

Skill 1.3.3Implement and optimize S3 performance strategies (for example, AWS DataSync, S3 Transfer Acceleration, multipart uploads, S3 Lifecycle policies) to enhance data transfer, storage efficiency, and access patterns

Request rates and prefixes

Scaling by prefix

S3 supports at least 3,500 PUT, COPY, POST or DELETE and 5,500 GET or HEAD requests per second per partitioned prefix, with no limit on the number of prefixes. Spreading keys across prefixes (orders/2026/11/03/…, or a hash at the start of the key) multiplies the total. S3 scales gradually; while it scales, it may return 503 Slow Down, which SDKs retry with backoff automatically.

Faster uploads and downloads

Multipart upload

Splits an object into parts uploaded in parallel and independently retried, so a failure means resending one part, not the whole file. AWS recommends it for objects over 100 MB, and it is required over 5 GB, the largest single PUT. Parts are 5 MiB to 5 GiB, up to 10,000 of them, and objects can now be up to 50 TB (raised from 5 TB in December 2025). The AWS CLI's aws s3 cp and the SDKs' transfer managers use multipart automatically above a threshold.

Tune the AWS CLI's automatic multipart behaviour 
# switch to multipart above 100 MB
aws configure set \
  default.s3.multipart_threshold 100MB

# 64 MB parts, 20 parts at a time
aws configure set \
  default.s3.multipart_chunksize 64MB
aws configure set \
  default.s3.max_concurrent_requests 20

Byte-range fetches

The download equivalent: request ranges of an object with the HTTP Range header, in parallel, and reassemble them. Aligning ranges with the parts the object was uploaded in is most efficient. It also lets an application read just the part of a file it needs.

S3 Transfer Acceleration

Routes uploads and downloads through the nearest CloudFront edge location and then over the AWS backbone network to the bucket's Region, speeding up long-distance transfers, for example from users on another continent. Turn it on per bucket and use the endpoint bucket-name.s3-accelerate.amazonaws.com. The bucket name must be DNS-compliant with no periods. You pay only for transfers that are actually accelerated, and the Speed Comparison tool shows the gain from each Region before you rely on it.

AWS DataSync

A managed service for moving large amounts of data, once or on a schedule, between on-premises storage (NFS, SMB, HDFS, object storage), other clouds and AWS storage (S3, EFS, all FSx types). It parallelizes the transfer, encrypts it, checks data integrity, and can limit bandwidth so it doesn't swamp a network link.

  • Agent: required for on-premises sources (a VM or EC2 instance near the data); not required for transfers between AWS services or between S3 and other clouds' object storage.
  • Task mode: Enhanced transfers virtually unlimited numbers of files in parallel and has expanded through 2026 to EFS and every FSx type; Basic works sequentially within quotas. The mode is chosen when the task is created and can't be changed.

DataSync or Transfer Acceleration?DataSync moves datasets between storage systems, managed and scheduled. Transfer Acceleration speeds up an application's own uploads and downloads to one bucket from far away.

Storage efficiency: Lifecycle and tiering

S3 Lifecycle rules

Lifecycle rules move objects to cheaper storage classes and delete them on a schedule, per bucket, optionally filtered by prefix, tag or size.

Lifecycle rules for order documents 
{
  "Rules": [{
    "ID": "orders-docs",
    "Status": "Enabled",
    "Filter": { "Prefix": "docs/" },
    "Transitions": [
      { "Days": 30,
        "StorageClass": "STANDARD_IA" },
      { "Days": 180,
        "StorageClass": "GLACIER" }
    ],
    // delete after 7 years
    "Expiration": { "Days": 2555 },
    // old versions: keep 30 days
    "NoncurrentVersionExpiration": {
      "NoncurrentDays": 30
    },
    // clean up failed uploads
    "AbortIncompleteMultipartUpload": {
      "DaysAfterInitiation": 7
    }
  }]
}

The // comments are explanations only; remove them in a real file. Points to know:

  • Minimum storage charges still apply after a transition: 30 days for Standard-IA and One Zone-IA, 90 for Glacier Instant Retrieval and Glacier Flexible Retrieval, 180 for Glacier Deep Archive. Since July 2026 you can transition to Standard-IA or One Zone-IA before day 30, but you are still charged for 30 days.
  • Objects under 128 KB don't transition by default, because the per-object overhead would cost more than it saves.
  • Incomplete multipart uploads are stored and charged but invisible in normal listings; the abort rule is an easy saving.

S3 Intelligent-Tiering

For data whose access pattern is unknown or changes: S3 moves each object between tiers by itself, Frequent Access, then Infrequent Access after 30 days without access, then Archive Instant Access after 90, with optional Archive Access and Deep Archive Access tiers. There are no retrieval fees, only a small monitoring charge per object; objects under 128 KB aren't monitored.

Related Extra

S3 Express One Zone stores data in directory buckets in one Availability Zone you choose, for single-digit millisecond latency on very request-heavy work such as ML training or analytics, placed next to the compute that reads it.

Shared storage

Skill 1.3.4Evaluate and select shared storage solutions (for example, Amazon EFS, Amazon FSx, Amazon S3 Files), and optimize the solutions (for example, EFS lifecycle policies) for specific use cases and requirements

Shared storage means many instances, containers or functions reading and writing the same files at once. EBS can't do this for ordinary workloads (Multi-Attach is only for io1 and io2 with cluster-aware software). The choice depends on the protocol and the workload.

Amazon EFS

What it is

A managed NFS file system for Linux that grows and shrinks automatically, mountable at once from EC2, ECS, EKS and Lambda across Availability Zones (or in one zone with EFS One Zone, which costs less).

Performance settings

  • Throughput mode: Elastic is the default and recommended mode, scaling with demand and charging for what you use, ideal for spiky or unpredictable workloads. Provisioned sets a fixed throughput for steady, high-throughput work. Bursting ties throughput to the amount of data stored (a small file system gets little throughput), which is the usual cause of a slow EFS file system holding little data.
  • Performance mode: use General Purpose. Max I/O is described by AWS as a previous-generation mode, isn't available with Elastic throughput or One Zone, and adds latency.

Storage classes and lifecycle policies

EFS has three storage classes: Standard, Infrequent Access (cheaper storage, charged per access) and Archive (cheapest, for data read a few times a year; needs Elastic throughput, with a 90-day minimum). Lifecycle management moves files automatically based on when they were last accessed: by default to IA after 30 days and to Archive after 90. An optional policy moves a file back to Standard on its first access, which is worth turning on when old files can suddenly become busy again.

Amazon FSx

The family

  • FSx for Windows File Server: SMB shares for Windows applications, integrated with Active Directory and Windows permissions.
  • FSx for Lustre: very high throughput for HPC, ML and media processing, with optional linking to an S3 bucket. Scratch file systems are temporary and unreplicated, cheapest for short jobs; persistent file systems replicate within the AZ for long-running work.
  • FSx for NetApp ONTAP: NFS, SMB and iSCSI from one file system with NetApp features (snapshots, replication, cloning), often for migrating NetApp storage.

Exam scopeFSx for OpenZFS is on the exam guide's out-of-scope list; the other FSx types are in scope as "Amazon FSx".

Amazon S3 Files

What it is

Launched in April 2026: a shared file system on top of an S3 bucket or prefix, mounted over NFS 4.1 or 4.2 from EC2, ECS, EKS or Lambda and built on EFS technology. The bucket stays the authoritative copy and changes sync both ways, so applications that need a file system and applications that use the S3 API work on the same data. The active working set is kept on high-performance storage, while large reads stream directly from S3.

Choosing

Shared Linux files for many instances or containers

EFS.

Windows shares with Active Directory

FSx for Windows File Server.

Hundreds of GB/s for HPC or ML training over data in S3

FSx for Lustre.

Migrating NetApp storage, or multiprotocol access

FSx for NetApp ONTAP.

File access to data that already lives in S3, without copying it

Amazon S3 Files.

An EFS file system that is slow despite low usage is usually in Bursting throughput mode with little data stored. Switch it to Elastic.

RDS performance

Skill 1.3.5Monitor Amazon RDS metrics (for example, Amazon RDS Performance Insights, CloudWatch alarms) and modify configurations to increase performance efficiency (for example, Performance Insights proactive recommendations, RDS Proxy)

Three layers of RDS monitoring

CloudWatch metrics

Published automatically, from the hypervisor: CPUUtilization, FreeableMemory, DatabaseConnections, ReadIOPS and WriteIOPS, ReadLatency and WriteLatency (seconds), DiskQueueDepth, FreeStorageSpace, ReplicaLag and, for gp2 storage, BurstBalance. These are what you alarm on.

Enhanced Monitoring

Operating system metrics from an agent on the database host, as often as every second (1, 5, 10, 15, 30 or 60 seconds), including per-process CPU and memory. Data goes to CloudWatch Logs in the RDSOSMetrics log group, and it needs an IAM monitoring role. Use it when CloudWatch says CPU is high and you need to know what inside the host is using it.

CloudWatch Database Insights (formerly Performance Insights)

Shows database load: active sessions broken down by wait event, SQL statement, host and user, so you can see which query is waiting on what. Performance Insights reached end of life on July 31, 2026, and its users were moved to Database Insights, which has two modes:

  • Standard: 7 days of history free, with paid retention of 1 to 24 months.
  • Advanced: 1 to 24 months included, plus fleet-wide views, execution plans, lock analysis and slow SQL.

Exam questions written before the change still say "Performance Insights"; read it as the same capability.

Proactive recommendations

RDS learns each database's normal behaviour and raises a recommendation when a metric crosses a threshold derived from that baseline, for example too many idle-in-transaction sessions on PostgreSQL, with the cause and a suggested fix. They appear on the Recommendations page of the RDS console and on each database's Recommendations tab, and require detailed metrics with a paid retention period.

"Which SQL statement is causing the load?" is Database Insights (Performance Insights). "Which process on the host is using the CPU?" is Enhanced Monitoring. "Alert when free storage falls below 10 GiB" is a CloudWatch alarm.

Configuration changes that improve performance

RDS Proxy

A managed connection pool between the application and the database. It holds a pool of database connections and shares them among many short-lived client connections, so the database isn't overwhelmed by connection storms, the classic problem with Lambda, where hundreds of concurrent invocations each open a connection. It also keeps client connections open during a Multi-AZ failover and redirects them, cutting failover time by up to 66%.

Clients can be required to use IAM authentication; the proxy reaches the database with credentials from Secrets Manager (or end-to-end IAM authentication). It works with Aurora MySQL and PostgreSQL and RDS for MySQL, PostgreSQL, MariaDB and SQL Server, runs in the database's VPC, and is never publicly accessible.

SymptomDatabaseConnections near the limit, "too many connections" errors, especially from Lambda.

Other levers

  • Read replicas: move read-heavy queries off the primary (Task 2.1).
  • A larger or different instance class: for sustained CPU or memory pressure (Compute Optimizer now recommends RDS sizes too).
  • Storage: gp3 with more IOPS, or io2, when DiskQueueDepth and latency are high. Storage autoscaling grows storage when free space stays at or below 10% for five minutes, by the largest of 10 GiB, 10% or predicted growth, up to a maximum you set, with no more than four storage changes in 24 hours.
  • Caching: ElastiCache in front of the database for repeated reads (Task 2.1).

EC2 storage and networking

Skill 1.3.6Implement, monitor, and optimize EC2 instances and their associated storage and networking capabilities (for example, EC2 placement groups)

Placement groups

StrategyHow instances are placedUse it for
ClusterPacked close together in one Availability Zone; up to 10 Gbps per flow between themLow-latency, high-throughput traffic between instances: HPC, tightly coupled jobs
PartitionSplit into partitions (up to 7 per AZ) that don't share racksLarge distributed systems such as Kafka, Cassandra and HDFS, which spread replicas across partitions
SpreadEach instance on distinct hardware; up to 7 running instances per AZ per groupA few critical instances that must not fail together
  • Cluster placement groups are single-AZ, so they trade resilience for speed, and launching all instances at once with one instance type avoids capacity errors. Burstable instances can't use them.
  • Moving an instance into or out of a placement group requires stopping it first; groups can't be merged.
Create a cluster placement group and launch into it 
aws ec2 create-placement-group \
  --group-name orders-batch \
  --strategy cluster

aws ec2 run-instances \
  --launch-template \
    LaunchTemplateName=orders-batch \
  --count 8 \
  --placement GroupName=orders-batch

Networking performance

Enhanced networking, ENA Express and EFA

  • Elastic Network Adapter (ENA): enhanced networking on current instances, with higher bandwidth and lower latency; the instance's size determines its network bandwidth, and smaller sizes have burstable bandwidth.
  • ENA Express: uses AWS's SRD protocol to raise a single flow from 5 to 25 Gbps and reduce tail latency, now also between Availability Zones in most Regions.
  • Elastic Fabric Adapter (EFA): OS-bypass networking for tightly coupled HPC (MPI) and distributed ML training; EFA traffic can't cross Availability Zones.

Storage attached to the instance

  • EBS-optimized: dedicated bandwidth for EBS, on by default for nearly all current instance types. The instance's EBS limit caps total volume performance (see EBS performance).
  • Instance store: very fast local disks physically attached to the host. Data survives a reboot but is lost on stop, hibernate or terminate, so it suits caches, buffers and scratch data, never the only copy of anything.

"Lowest latency between instances" points to a cluster placement group with enhanced networking. "Instances must not share hardware" points to a spread placement group. "Fastest possible temporary storage" points to instance store.

Key takeaways

  • Right-size from at least two weeks of metrics, including memory from the CloudWatch agent. Compute Optimizer recommends sizes for EC2, Auto Scaling groups, EBS, Lambda, ECS on Fargate and RDS; burstable instances with constantly empty credit balances should move to fixed-performance types. Right-size, then commit with Savings Plans.
  • gp3 is the default EBS type: 3,000 IOPS and 125 MiB/s at any size, up to 80,000 IOPS and 2,000 MiB/s. Migrate gp2 to gp3 in place with Elastic Volumes (up to four changes per 24 hours, no shrinking). io2 Block Express is for the most demanding databases; st1 and sc1 for sequential throughput, never boot.
  • Diagnose slow volumes with VolumeQueueLength, BurstBalance, the volume and instance exceeded checks, and initialization after snapshot restores (pre-warm, Fast Snapshot Restore or a provisioned initialization rate).
  • S3 scales per prefix (3,500 writes and 5,500 reads per second each). Multipart for objects over 100 MB (required over 5 GB, objects up to 50 TB); byte-range fetches for parallel reads; Transfer Acceleration for long-distance transfers via edge locations; DataSync for managed bulk transfers.
  • Lifecycle rules transition and expire objects and abort incomplete multipart uploads; minimum storage charges still apply. Intelligent-Tiering handles unknown access patterns.
  • EFS for shared Linux files (Elastic throughput, General Purpose mode, lifecycle to IA and Archive); FSx for Windows, Lustre and ONTAP; Amazon S3 Files for NFS access to data in S3.
  • RDS: CloudWatch metrics for alarms, Enhanced Monitoring for the OS, Database Insights (Performance Insights ended July 31, 2026) for which SQL is causing load, proactive recommendations from baselines, and RDS Proxy for connection storms and faster failover.
  • Placement groups: cluster for low latency in one AZ, partition for large distributed systems, spread for a few critical instances (7 per AZ). ENA Express and EFA for network-heavy work; instance store for fast, disposable data.
