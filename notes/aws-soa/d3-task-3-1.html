Overview

Task 3.1

Provision and maintain cloud resources.

Infrastructure built by hand drifts, can't be reviewed and can't be rebuilt in a disaster. This task is about defining it in code and images instead, and then operating that code: reading why a stack failed, fixing it, and rolling the same change out to many accounts. Questions are mostly troubleshooting: a stack stuck in a failed state, an AMI that can't be launched in another account, a subnet that has run out of addresses.

The examples continue the orders application, now deployed through CloudFormation from a Git repository. The organization has a tooling account (111111111111), workload accounts and an AWS Organizations management account.

AMIs and container images

Skill 3.1.1Create and manage AMIs and container images (for example, EC2 Image Builder)

AMIs

Golden images

A golden AMI has the operating system patched, agents (SSM Agent, CloudWatch agent) installed and the hardening applied, so instances boot ready instead of configuring themselves for minutes in user data. Faster boots mean faster scaling and more reliable launches.

Copying and sharing

  • AMIs are Regional: to use one elsewhere, copy it with copy-image, which also copies its snapshots.
  • Sharing: grant launch permission to account IDs, an organization or an OU with modify-image-attribute.
  • Encrypted AMIs: can't be shared if their snapshots use the default AWS managed EBS key. Use a customer managed KMS key and grant the other account permission to use it; the target account then launches with that key, or copies the AMI to re-encrypt with its own.
  • Block public access for AMIs: on by default for new accounts, preventing accidental public sharing.
Copy the golden AMI to Ireland and share it with a workload account 
aws ec2 copy-image \
  --source-region us-east-1 \
  --source-image-id ami-0abc1234def567890 \
  --region eu-west-1 \
  --name orders-golden-2026-11

aws ec2 modify-image-attribute \
  --region eu-west-1 \
  --image-id ami-0fed9876cba543210 \
  --launch-permission \
    "Add=[{UserId=222222222222}]"

Retiring AMIs

  • Deprecate: hides the AMI from listings, but it can still be launched by ID, so existing launch templates keep working.
  • Disable: nobody can launch it any more and all its shares are removed; launch templates and Auto Scaling groups that reference it fail to launch.
  • Deregister: deletes the AMI. Its snapshots are kept and keep costing money unless you deregister with --delete-associated-snapshots.

EC2 Image Builder

How a pipeline is built

  • Components: YAML documents of build steps (install packages, apply settings) and test steps (check the service starts, run security tests).
  • Recipe: a base image plus components. An image recipe produces an AMI; a container recipe produces a Docker image.
  • Infrastructure configuration: the instance type, subnet, security group, instance profile and log bucket the build runs with.
  • Distribution settings: which Regions and accounts receive the image, under which KMS key, and optionally update a launch template to the new AMI, or push container images to an Amazon ECR repository.
  • Pipeline: runs the recipe on a schedule. By default a scheduled run builds only when a dependency has changed, such as a newer base image or component version.

Keeping images safe and tidy

Image Builder can scan images with Amazon Inspector and fail the build when findings exceed a severity you set, so a vulnerable image is never distributed. Lifecycle policies deprecate, disable and delete old images and their snapshots automatically. Image Builder itself is free; you pay for the build instances, storage and scans.

"Automatically rebuild the golden AMI when the base image is patched, test it, scan it, copy it to three Regions and update the launch template" is an EC2 Image Builder pipeline with distribution settings.

Container images in Amazon ECR

Operating a registry

  • Scanning: basic scanning (on push or manual) or enhanced scanning through Inspector, which rescans continuously as new vulnerabilities are published and covers language packages too.
  • Lifecycle policies: expire (or archive) old images by count, age or tag, keeping storage costs down.
  • Replication: registry-level rules copy images to other Regions and accounts; the destination account's registry policy must allow it.
  • Tag immutability: stops a tag such as v1.4.2 from being overwritten, so a deployed tag always means the same image.
  • Pull through cache: caches images from public registries such as Docker Hub in your registry, avoiding rate limits and external dependency at launch.

CloudFormation and the CDK

Skill 3.1.2Create and manage AWS resources by using CloudFormation and the AWS CDK

Managing stacks safely

Change sets

A change set previews what an update will do, resource by resource, including which resources will be replaced (deleted and recreated, losing their data and IDs), before anything changes. Review and execute it; never update production blind.

Drift detection

Compares each resource's actual configuration with the template. A stack is IN_SYNC or DRIFTED; drifted resources are MODIFIED or DELETED. Drift usually means someone changed a resource in the console. Fix it by reverting the manual change or by updating the template to match and deploying.

Protecting resources

  • Termination protection: stops a stack from being deleted.
  • Stack policy: stops chosen resources from being updated, replaced or deleted during stack updates. Once set, anything not explicitly allowed is denied; it can be overridden temporarily for a single update.
  • DeletionPolicy: what happens to a resource when it leaves the stack: Delete (default), Retain, RetainExceptOnCreate, or Snapshot for volumes and databases. UpdateReplacePolicy does the same for the old copy when an update replaces a resource.

Passing values in and out

  • Parameters, including SSM parameter types that read the latest value from Parameter Store, such as the newest golden AMI ID.
  • Dynamic references such as {{resolve:secretsmanager:orders-db}} to inject secrets without putting them in the template (not supported in EC2 user data).
  • Outputs and exports: one stack exports a value (the VPC ID) and others import it with Fn::ImportValue. While another stack imports it, the export can't be changed and the exporting stack can't be deleted.
  • Nested stacks: reusable templates included in a parent stack and deployed as one unit.

Configuring instances from a template

Helper scripts and policies

  • cfn-init applies the packages, files and services described in the template's AWS::CloudFormation::Init metadata.
  • cfn-signal tells CloudFormation the instance finished configuring; a CreationPolicy makes the stack wait for that signal (default timeout 5 minutes) and fail if it doesn't arrive.
  • cfn-hup watches the metadata and reapplies it when the stack is updated (checking every 15 minutes by default).
  • UpdatePolicy on an Auto Scaling group: AutoScalingRollingUpdate replaces instances in batches, AutoScalingReplacingUpdate builds a whole new group, and AutoScalingInstanceRefresh runs an Auto Scaling instance refresh.
Rolling update: replace two instances at a time, keep two running 
OrdersAsg:
  Type: AWS::AutoScaling::AutoScalingGroup
  # wait for 3 signals at first launch
  CreationPolicy:
    ResourceSignal:
      Count: 3
      Timeout: PT15M
  UpdatePolicy:
    AutoScalingRollingUpdate:
      MaxBatchSize: 2
      MinInstancesInService: 2
      # each new instance must signal
      WaitOnResourceSignals: true
      PauseTime: PT10M
  Properties:
    MinSize: 3
    MaxSize: 9
    VPCZoneIdentifier: !Ref AppSubnets
    LaunchTemplate:
      LaunchTemplateId: !Ref Lt
      Version: !GetAtt Lt.LatestVersionNumber

The AWS CDK

Infrastructure in a programming language

The CDK (version 2; version 1 ended in June 2023) lets you define infrastructure in TypeScript, JavaScript, Python, Java, C# or Go. Code is built from constructs: L1 constructs map one-to-one to CloudFormation resources; L2 constructs add sensible defaults and helper methods (bucket.grantRead(role) writes the IAM policy for you); L3 constructs, or patterns, build whole architectures, such as a load-balanced Fargate service, in a few lines.

  1. cdk bootstrapOnce per account and Region: creates the CDKToolkit stack with an S3 bucket and ECR repository for assets, and the IAM roles deployments use.
  2. cdk synthGenerates the CloudFormation template from the code.
  3. cdk diffShows what would change, like a change set.
  4. cdk deployDeploys through CloudFormation; the result is an ordinary stack.

Because the CDK deploys CloudFormation stacks, all of the stack troubleshooting below applies. A deployment failing with a missing bucket or bootstrap version message means the account or Region isn't bootstrapped.

Deployment issues

Skill 3.1.3Identify and remediate deployment issues (for example, subnet sizing issues, CloudFormation errors, permissions issues)

CloudFormation stack failures

Start with the stack's Events tab: the first CREATE_FAILED or UPDATE_FAILED event, read from the bottom up, gives the real reason; later failures are usually just the rollback cancelling other resources.

ROLLBACK_COMPLETE

A new stack failed and rolled back. It can only be deleted, not updated; fix the template and create it again. To debug, create it with rollback disabled (--on-failure DO_NOTHING), so the successfully created resources stay and you can inspect the failed one, then retry, update or roll back.

UPDATE_ROLLBACK_FAILED

An update failed and the rollback also failed, often because a resource was changed or deleted outside CloudFormation. Fix the cause if possible, then continue-update-rollback; if a resource can't be rolled back, skip it with --resources-to-skip.

DELETE_FAILED

A resource couldn't be deleted, typically a non-empty S3 bucket or a security group still in use. Empty or detach it and retry, or delete the stack while retaining that resource with --retain-resources.

Common causes

  • Permissions: the identity (or the stack's service role, passed with --role-arn) needs permission for every underlying service action, not just CloudFormation's.
  • Capabilities: templates that create IAM resources need CAPABILITY_IAM, or CAPABILITY_NAMED_IAM if they name them; templates with macros or nested stack transforms need CAPABILITY_AUTO_EXPAND.
  • Name conflicts: a resource with a fixed name that already exists. CloudFormation's pre-deployment validation (on by default) now catches many of these, along with syntax errors, before anything is created.
  • Quotas: replacing a resource creates the new one before deleting the old, which can exceed a quota.
  • Timeouts: an instance with a CreationPolicy that never signals, because user data failed or the instance can't reach the CloudFormation endpoint.

Subnet sizing

Running out of addresses

A subnet can be from /28 (16 addresses) to /16, and AWS reserves 5 addresses in each: the network address, the VPC router (+1), DNS (+2), one for future use (+3) and the last (broadcast). A /28 therefore has only 11 usable addresses. Every instance, load balancer node, Lambda function network interface and EKS pod (with the default VPC CNI) uses an address, so a busy subnet fills up and launches fail.

An existing subnet can't be resized. Add a secondary CIDR block to the VPC, create new, larger subnets, and add them to the Auto Scaling group, EKS node groups or Lambda configuration. Amazon VPC IP Address Manager (IPAM) helps plan and track address use across accounts.

EC2 launch errors

  • InstanceLimitExceeded or a vCPU quota error: request an increase through Service Quotas (On-Demand quotas are counted in vCPUs per instance family group).
  • InsufficientInstanceCapacity: AWS has no capacity of that type in that zone right now. Retry, try other zones, or use several instance types (a mixed instances policy); reserve capacity with a Capacity Reservation for critical launches.
  • Permission errors at launch: passing an instance profile needs iam:PassRole; launching from an encrypted AMI needs permission to use its KMS key.

Across Regions and accounts

Skill 3.1.4Provision and share resources across multiple Regions and accounts (for example, AWS Resource Access Manager [AWS RAM], CloudFormation StackSets)

CloudFormation StackSets

One template, many accounts and Regions

A StackSet deploys the same template as stack instances in chosen accounts and Regions, and keeps them in step when you update it: baseline IAM roles, Config rules, logging, network components.

  • Self-managed permissions: you create AWSCloudFormationStackSetAdministrationRole in the administrator account and AWSCloudFormationStackSetExecutionRole in every target account.
  • Service-managed permissions: uses AWS Organizations; deploy to OUs from the management account or a delegated administrator, with no roles to create, and turn on automatic deployment so new accounts joining the OU get the stack.

Operation options control the rollout: maximum concurrent accounts, failure tolerance (how many accounts may fail before it stops), Region order and whether Regions deploy in sequence (the default) or in parallel.

Deploy a baseline to an OU in two Regions 
aws cloudformation create-stack-set \
  --stack-set-name org-baseline \
  --template-body file://baseline.yaml \
  --permission-model SERVICE_MANAGED \
  --auto-deployment \
    Enabled=true,\
RetainStacksOnAccountRemoval=false \
  --capabilities CAPABILITY_NAMED_IAM

aws cloudformation create-stack-instances \
  --stack-set-name org-baseline \
  --deployment-targets \
    OrganizationalUnitIds=ou-ab12-wkld \
  --regions us-east-1 eu-west-1 \
  --operation-preferences \
    MaxConcurrentPercentage=25,\
FailureTolerancePercentage=10

AWS Resource Access Manager (RAM)

Sharing instead of copying

RAM shares a resource with other accounts, OUs or the whole organization, so they use the one resource rather than each building their own. Commonly shared: VPC subnets, Transit Gateways, Route 53 Resolver rules, prefix lists, IPAM pools, Aurora clusters, Capacity Reservations, License Manager configurations, EventBridge event buses, Systems Manager documents and Image Builder resources.

Turn on sharing with AWS Organizations (enable-sharing-with-aws-organization, from the management account) so shares inside the organization take effect without invitations. Shares with accounts outside it need an invitation to be accepted.

VPC sharing

A networking account owns the VPC and shares subnets with workload accounts (only within the organization, and not subnets of a default VPC). Participants launch their own instances, databases and load balancers into the shared subnets and manage their own security groups, but they can't change the subnets, route tables, network ACLs or gateways. That separation lets a central team run the network while application teams run their workloads.

"Deploy the same resources to every account in an OU, including new accounts automatically" is StackSets with service-managed permissions. "Let other accounts use one existing resource, such as a subnet or Transit Gateway" is AWS RAM.

Deployment strategies

Skill 3.1.5Implement deployment strategies and services

The strategies

All at once

Update everything simultaneously. Fastest and cheapest, but causes downtime and a failure affects every user.

Rolling

Update a batch of instances at a time, keeping the rest in service. No extra capacity needed, but capacity drops during the deployment and old and new versions run side by side.

Immutable and blue/green

Build new instances (or a whole new environment, "green") next to the old ("blue"), test them, then switch traffic. Rollback is switching back. It doubles capacity briefly and needs care with database schema changes.

Canary and linear

Shift a small share of traffic to the new version (canary: 10% for 5 minutes, then the rest; linear: 10% more every minute), watch alarms, and roll back automatically if they fire. The best balance of safety and speed for user-facing services.

Where AWS implements them

EC2 Auto Scaling instance refresh

Replaces the instances in a group after a launch template change, keeping at least a minimum healthy percentage (default 90%) in service. It supports checkpoints (pause after a percentage to verify), skipping instances that already match, CloudWatch alarm-based automatic rollback (off by default) and a bake time. CloudFormation can trigger it through AutoScalingInstanceRefresh.

Amazon ECS

Services deploy with a rolling update by default (controlled by minimum healthy and maximum percent), or with ECS's native blue/green, linear and canary deployments, with bake times, lifecycle hooks and automatic rollback through a deployment circuit breaker or alarms.

AWS Lambda

An alias can split traffic between two published versions by weight (for example 90/10), shifting gradually as confidence grows.

AWS CodeDeploy Extra

Automates these strategies with predefined deployment configurations: for EC2, OneAtATime (the default), HalfAtATime and AllAtOnce; for Lambda and ECS, canary and linear options such as Canary10Percent5Minutes and Linear10PercentEvery1Minute, with automatic rollback on alarms. CodeDeploy, CodePipeline and Elastic Beanstalk appear on neither the exam's in-scope nor out-of-scope list; know the strategies, which the services implement.

"Zero downtime and instant rollback" points to blue/green. "Expose the new version to a small share of users first and roll back automatically on errors" points to canary. "No extra capacity available" points to rolling.

Terraform and Git

Skill 3.1.6Use and manage third-party tools to automate resource deployment (for example, Terraform, Git)

Terraform on AWS

How it differs from CloudFormation

HashiCorp Terraform describes infrastructure in HCL and calls AWS APIs through the AWS provider (or the AWS Cloud Control provider, awscc, generated from CloudFormation's resource schemas). Unlike CloudFormation, which keeps state inside the service, Terraform keeps its own state file recording what it manages. That state has to be stored safely and locked, or two people running Terraform at once can corrupt it.

Remote state in S3 with locking

Store state in a versioned, encrypted S3 bucket. Since Terraform 1.11 the S3 backend can lock state natively with a lock file in the bucket (use_lockfile); the older DynamoDB-table locking is deprecated.

Terraform backend: state in S3 with native locking 
terraform {
  backend "s3" {
    bucket       = "orders-tf-state"
    key          = "prod/network.tfstate"
    region       = "us-east-1"
    encrypt      = true
    # S3 lock file (Terraform 1.11+)
    use_lockfile = true
  }
}

Operations rules: run Terraform from a pipeline with an IAM role rather than personal keys; review terraform plan before apply, like a change set; and don't change Terraform-managed resources in the console, which causes drift that the next plan will try to undo.

Git

Infrastructure from a repository

Keeping templates, CDK code and Terraform in Git gives history, code review through pull requests, and a single source of truth to deploy from. AWS connects to GitHub, GitLab and Bitbucket through AWS CodeConnections. CloudFormation Git sync watches a branch and deploys a stack automatically whenever its template or deployment file changes, and can comment on pull requests.

Key takeaways

  • AMIs are Regional (copy, then share); encrypted AMIs need a customer managed KMS key to share. Deprecate hides, disable blocks launches, deregister deletes (snapshots stay unless you delete them).
  • EC2 Image Builder pipelines build, test, scan and distribute AMIs and container images on a schedule and can update launch templates; ECR adds scanning, lifecycle policies, replication and tag immutability.
  • CloudFormation: review change sets, detect drift, protect with termination protection, stack policies and DeletionPolicy, pass secrets with dynamic references. cfn-init, cfn-signal with CreationPolicy, and cfn-hup configure instances; UpdatePolicy controls Auto Scaling replacement.
  • The CDK synthesizes CloudFormation from code built of L1, L2 and L3 constructs; bootstrap each account and Region first.
  • Fix stacks from the first failure event: ROLLBACK_COMPLETE must be deleted; UPDATE_ROLLBACK_FAILED needs continue-update-rollback (skip resources if needed); DELETE_FAILED can retain resources. Check permissions, capabilities, name conflicts and quotas.
  • Subnets are /28 to /16 with 5 reserved addresses and can't be resized: add a secondary CIDR and new subnets. Capacity errors need other zones or instance types; limit errors need Service Quotas.
  • StackSets deploy one template across accounts and Regions (service-managed with Organizations for automatic deployment); RAM shares single resources such as subnets and Transit Gateways.
  • Strategies: all at once, rolling, immutable or blue/green, canary and linear, implemented by instance refresh, ECS deployments, Lambda aliases and CodeDeploy. Terraform keeps state in S3 with native locking; Git and CodeConnections drive deployments.
