Overview

Task 4.1

Implement and manage security and compliance tools and policies.

Security on this exam is operational: not designing an identity strategy from scratch, but configuring the controls, finding out why someone can't do their job (or can do too much), and fixing findings. The most common question shape is an AccessDenied error and a set of policies, and you must say which one is responsible.

The examples use the orders organization: a management account, a security tooling account, and workload accounts such as 111111111111 in a Workloads OU.

IAM features

Skill 4.1.1Implement IAM features (for example, password policies, MFA, roles, federated identity, resource policies, policy conditions)

Password policy and MFA

Account password policy

Applies to IAM users' console passwords (not the root user, and not access keys). Without a custom policy, passwords need 8 or more characters with three of the four character types, and never expire. A custom policy can set:

  • Minimum length (6 to 128) and each character type separately.
  • Expiry (1 to 1,095 days), optionally requiring an administrator reset after expiry instead of letting the user choose a new one.
  • Preventing reuse of the last 1 to 24 passwords.
  • Whether users may change their own password.

There is no account lockout setting, and a user whose password has expired can still use their access keys.

A stricter password policy for the account 
aws iam update-account-password-policy \
  --minimum-password-length 14 \
  --require-symbols \
  --require-numbers \
  --require-uppercase-characters \
  --require-lowercase-characters \
  --max-password-age 90 \
  --password-reuse-prevention 24 \
  --allow-users-to-change-password

MFA

  • Types: passkeys and FIDO security keys (phishing-resistant, enabled in the console only), virtual authenticator apps, and hardware TOTP tokens. SMS MFA is no longer supported. Up to 8 devices per user and for the root user.
  • Root user: MFA is now required for the root user of every account type, and must be registered within 14 days of first console sign-in.
  • Centralized root access (Organizations): from the management account, remove the root password, keys and MFA of member accounts entirely, and perform the few root-only tasks centrally, such as deleting a bucket policy that locks everyone out. New member accounts are created without root credentials.

Roles and federation

How a role works

A role has two policies: a trust policy (who may assume it) and a permissions policy (what it may do once assumed). Assuming it through sts:AssumeRole returns temporary credentials. Things to remember:

  • Session length: up to the role's maximum session duration (1 to 12 hours). Role chaining (using one role's credentials to assume another) is limited to 1 hour.
  • External ID: a condition in the trust policy for third parties, preventing the "confused deputy" problem where a vendor is tricked into using your role for another customer.
  • Instance profiles deliver a role to EC2; whoever attaches it needs iam:PassRole.
  • Service-linked roles belong to a service; you can view but not edit their permissions.
Trust policy: let a vendor's account assume the role 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "999999999999" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "orders-7f3k9"
      }
    }
  }]
}

Federated identity

  • SAML 2.0: a corporate identity provider (Microsoft Entra ID, Okta, AD FS) signs users in, and they assume roles. For many accounts, prefer IAM Identity Center (below).
  • OIDC: workloads outside AWS, such as GitHub Actions or another cloud, exchange their token for role credentials with AssumeRoleWithWebIdentity, so no long-lived access keys are stored there. The provider must be in the same account as the role; restrict the trust policy to the expected repository or subject.

Resource-based policies

Policies on the resource

S3 bucket policies, KMS key policies, SQS queue and SNS topic policies, Lambda function policies, and role trust policies are attached to the resource and name a principal. Two rules decide most questions:

  • Same account: an allow in either the identity policy or the resource policy is enough, except for KMS key policies and role trust policies, which must allow the principal themselves.
  • Cross-account: both sides must allow: the resource policy in the owning account and an identity policy in the caller's account.

How a request is evaluated

  1. Explicit denyA deny in any policy wins, whatever else allows.
  2. Organization policiesResource control policies and service control policies must allow the action.
  3. Resource and identity policiesAt least one must allow it (both, cross-account).
  4. Boundaries and session policiesA permissions boundary or session policy, if present, must also allow it.

Anything not explicitly allowed is denied by default. A permissions boundary sets the maximum an identity policy can grant, which lets developers create roles without being able to exceed their own permissions.

  "Effect": "Deny",
  "Action": "ec2:TerminateInstances",
  "Resource": "*",

    }
  }
}

Troubleshooting access

Skill 4.1.2Troubleshoot and audit access issues by using AWS tools (for example, CloudTrail, IAM Access Analyzer, IAM policy simulator)

Reading the error

The message names the policy type

Most services now say which kind of policy blocked the request:

  • Explicit deny: "... is not authorized to perform s3:GetObject ... with an explicit deny in a service control policy". The type can be a service control policy, resource control policy, VPC endpoint policy, permissions boundary, session policy, resource-based policy or identity-based policy.
  • Implicit deny: "... because no identity-based policy allows the s3:GetObject action". Add an allow in the policy named.

If several policies deny, only one is reported. EC2 often returns an encoded authorization message instead; decode it (the caller needs sts:DecodeAuthorizationMessage) to see the action, resource and context that failed.

Decode an EC2 authorization failure 
aws sts decode-authorization-message \
  --encoded-message "$MSG" \
  --query DecodedMessage \
  --output text

The tools

AWS CloudTrail

The record of every API call: who (userIdentity: user, role session, federated user), what, when, from where (sourceIPAddress), and whether it failed (errorCode such as AccessDenied, or Client.UnauthorizedOperation for EC2). Search Event history for the last 90 days of management events, or query a trail's logs in S3 with Athena. Use it to answer "who changed this security group?" and "which call is failing?".

IAM policy simulator

Tests whether a user, group or role is allowed an action on a resource, and shows which statement allowed or denied it. It evaluates identity policies, a permissions boundary, SCPs, and resource-based policies you supply; it does not evaluate resource control policies, and results can differ for VPC endpoint policies and role chaining. Supply any condition values (source IP, MFA, tags) the policies depend on.

Can the ops role read this object? 
aws iam simulate-principal-policy \
  --policy-source-arn \
    arn:aws:iam::111111111111:role/ops \
  --action-names s3:GetObject \
  --resource-arns \
    arn:aws:s3:::orders-in/invoices/1.pdf

IAM Access Analyzer

  • External access analyzer: finds resources (S3 buckets, KMS keys, roles, queues, snapshots and more) shared outside the zone of trust, your account or organization. It is Regional: create one in each Region you use.
  • Internal access analyzer (newer, paid): which principals inside your organization can reach critical resources such as S3 buckets, RDS snapshots and DynamoDB tables.
  • Unused access analyzer (paid): roles, users, access keys, passwords and permissions not used within a period you set, for right-sizing.
  • Policy validation: checks policies as you write them, with findings graded as security warnings, errors, warnings and suggestions.
  • Policy generation: builds a least-privilege policy from a role's actual activity in CloudTrail.
  • Custom policy checks: fail a pipeline if a policy change grants new access or public access.
One external access analyzer for the organization 
# run in each Region, from the management
# or delegated administrator account
aws accessanalyzer create-analyzer \
  --analyzer-name org-external \
  --type ORGANIZATION

Auditing credentials

The credential report lists every IAM user with password and access key age, last use and MFA status. Last accessed information (access advisor) shows when a user, role or policy last used each service, so unused permissions can be removed.

"Who did it?" is CloudTrail. "Would this be allowed?" is the policy simulator. "What is shared outside my account or organization?" or "which permissions are unused?" is IAM Access Analyzer.

Multi-account strategy

Skill 4.1.3Implement multi-account strategies (for example, AWS Organizations, SCPs, IAM Identity Center)

AWS Organizations

Structure

One management account creates and pays for member accounts grouped into organizational units (OUs) such as Security, Workloads/Prod, Workloads/Dev and Sandbox. Policies attached to an OU apply to every account below it. Organization policies need all features enabled, not only consolidated billing. Run security services from a delegated administrator account rather than the management account, and keep workloads out of the management account.

Service control policies (SCPs)

SCPs set the maximum permissions for principals in member accounts. They never grant anything: users still need IAM permissions. They apply to everyone in the account, including the root user, but not to the management account or to service-linked roles. Every account starts with the FullAWSAccess SCP; guardrails are added as deny statements.

SCP: protect the security baseline 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ProtectBaseline",
    "Effect": "Deny",
    "Action": [
      "cloudtrail:StopLogging",
      "cloudtrail:DeleteTrail",
      "config:StopConfigurationRecorder",
      "guardduty:DeleteDetector",
      "organizations:LeaveOrganization"
    ],
    "Resource": "*"
  }]
}

Other organization policies

  • Resource control policies (RCPs, since November 2024): the maximum permissions on resources in member accounts, whoever is calling, including external principals. Use them to say "no principal outside our organization can read our S3 buckets or KMS keys".
  • Declarative policies (since December 2024): enforce a service configuration such as blocking public AMI and snapshot sharing, requiring IMDSv2 or turning on VPC Block Public Access. They hold even for new APIs and for service-linked roles.
  • Tag, backup and AI services opt-out policies standardize tags, AWS Backup plans and data use across accounts.

AWS Control Tower Extra

Sets up a governed landing zone (log archive and audit accounts, an organization trail, Config) and applies controls: preventive (SCPs and RCPs), detective (Config rules) and proactive (CloudFormation hooks). Account Factory creates new accounts that already meet the baseline.

IAM Identity Center

One sign-in for every account

The recommended way to give people access to many accounts. Users sign in once to the access portal and pick an account and role.

  • Identity source: the Identity Center directory, Active Directory, or an external IdP (such as Entra ID or Okta) over SAML, with SCIM to sync users and groups automatically.
  • Permission sets: collections of policies that Identity Center provisions as roles in each assigned account. Assign a group a permission set in an account; changing the permission set updates every account.
  • Session duration: 1 hour by default, up to 12 hours, set on the permission set.
  • Use an organization instance (in the management account, with a delegated administrator) for multi-account access; an account instance can't assign access to other accounts.

"Prevent anyone in member accounts, including administrators, from doing X" is an SCP. "Prevent anyone outside the organization from accessing our resources" is an RCP. "Give the workforce single sign-on into all accounts" is IAM Identity Center with permission sets.

Trusted Advisor security

Skill 4.1.4Remediate findings from Trusted Advisor security checks

Which checks you get

Every account gets the core security checks: S3 bucket permissions, security groups with specific ports unrestricted, MFA on the root account, and public EBS and RDS snapshots. The full set, the API, the Security Hub integration and EventBridge events need a higher support plan (Business Support+ and above; the Developer and Business plans are replaced by Business Support+ from January 1, 2027). Trusted Advisor's EventBridge events are published only in us-east-1.

Common findings and their fixes

To act on findings automatically, create an EventBridge rule in us-east-1 for Trusted Advisor check status changes and route it to Lambda, an Automation runbook or a notification. Some fixes have AWS-provided runbooks, such as making an EBS snapshot private.

Compliance and monitoring

Skill 4.1.5Implement compliance and continuous monitoring requirements (for example, Region and service selections, AWS Config conformance packs)

Region and service selection

Keeping data where it must be

Data residency rules ("customer data stays in the EU") are enforced by limiting Regions: an SCP denying actions outside approved Regions with aws:RequestedRegion, or Control Tower's Region deny control. Regions launched after March 2019 are opt-in and disabled until enabled. Before using a service for regulated data, check that it is listed under that compliance program on AWS's "services in scope by compliance program" page, and download the audit reports and agreements (such as a HIPAA BAA) from AWS Artifact.

SCP: deny everything outside two Regions (shortened: the AWS example exempts more global services) 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOtherRegions",
    "Effect": "Deny",
    "NotAction": [
      "cloudfront:*", "iam:*",
      "route53:*", "support:*"
    ],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:RequestedRegion": [
          "eu-west-1", "eu-central-1"
        ]
      }
    }
  }]
}

AWS Config

Recording

The configuration recorder captures the configuration of resources in each Region, either all supported types (with exclusions) or chosen types, continuously or daily. Global IAM resources aren't recorded by default; record them in one Region only to avoid duplicates. An aggregator collects data from many accounts and Regions into one view.

Rules

Managed rules (hundreds, such as s3-bucket-public-read-prohibited or restricted-ssh) or custom rules (Lambda or Guard) evaluate resources on configuration changes, periodically, or both, and mark them COMPLIANT or NON_COMPLIANT. Rules can also run in proactive mode, checking a resource definition before it is deployed. Non-compliant resources can be fixed with automatic remediation through an Automation runbook.

Conformance packs

A conformance pack is a YAML template bundling Config rules and their remediation actions, deployed as one unit to an account and Region, or to the whole organization. AWS supplies more than a hundred sample packs, such as Operational Best Practices for CIS, PCI DSS, NIST 800-53 and HIPAA. Each pack shows a compliance score: the share of rule and resource combinations that are compliant.

Deploy a sample pack from S3 
aws configservice put-conformance-pack \
  --conformance-pack-name cis-baseline \
  --template-s3-uri \
    s3://orders-cfg/cis-1-4.yaml

Use put-organization-conformance-pack from the management or delegated administrator account to deploy it to every member account.

AWS Audit Manager closed to new customers on April 30, 2026; AWS points new users to Config conformance packs. CloudTrail Lake closed to new customers on May 31, 2026. The original Security Hub is now called AWS Security Hub CSPM (it runs the security standards and controls), and a new AWS Security Hub, generally available since December 2025, correlates findings across services. Both are covered in Task 4.2.

Key takeaways

  • Password policies cover IAM users' console passwords only; MFA is passkeys, authenticator apps or hardware tokens (no SMS) and is required for root. Centralized root access removes member accounts' root credentials.
  • Roles: trust policy plus permissions policy, sessions up to 12 hours (role chaining 1 hour), external ID for third parties, OIDC and SAML federation instead of stored keys.
  • Evaluation: explicit deny wins; RCPs, SCPs, boundaries and session policies cap permissions; same-account needs one allow, cross-account needs both sides. Know the condition keys and their pitfalls (SourceIp through endpoints, MFA with BoolIfExists).
  • Troubleshoot with the error message (it names the policy type), CloudTrail for who and what, the policy simulator for "would it be allowed", and Access Analyzer for external, internal and unused access.
  • Organizations: OUs, delegated administrators, SCPs that never grant and don't affect the management account; RCPs for resources; declarative policies for service settings; Identity Center permission sets for workforce access.
  • Trusted Advisor core security checks: open ports, public buckets and snapshots, root MFA; fix them, and automate with EventBridge in us-east-1.
  • Compliance: restrict Regions with SCPs, check service eligibility and use AWS Artifact; record with Config, evaluate with rules, deploy conformance packs (organization-wide) and track compliance scores.
