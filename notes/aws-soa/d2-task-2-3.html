Task 2.3: Implement backup and restore strategies

Overview

Task 2.3

Implement backup and restore strategies.

Task 2.2 kept the application running through infrastructure failure. This task covers the failures high availability can't help with: someone deletes a table, ransomware encrypts a volume, a bad deployment corrupts data, or a whole Region is unavailable. Multi-AZ replicates mistakes instantly; only a backup taken before the mistake can undo them.

Two numbers drive every decision. AWS defines the recovery time objective (RTO) as the maximum acceptable delay between the interruption of service and its restoration, and the recovery point objective (RPO) as the maximum acceptable amount of time since the last data recovery point, which is how much data you can afford to lose. Lower numbers cost more.

The examples continue the orders application: EC2 instances with EBS volumes, an RDS for PostgreSQL database, a DynamoDB cart table and an S3 bucket of order documents, all tagged App=orders.

Automating backups

Skill 2.3.1Automate snapshots and backups for AWS resources (for example, EC2 instances, RDS DB instances, EBS volumes, S3 buckets, DynamoDB tables) by using AWS services (for example, AWS Backup)

AWS Backup

One service to back up most AWS storage and databases on a schedule, with the same retention, copy and audit controls for all of them: EC2 (as AMIs), EBS, RDS, Aurora, DynamoDB, EFS, FSx, S3, Storage Gateway, DocumentDB, Redshift and more.

Backup plans, rules and vaults

  • Backup plan: a set of up to 10 rules. Each rule says how often to back up (as often as every hour, or continuously), the backup window (by default starting at 00:30, starting within 8 hours), how long to keep each recovery point, when to move it to cheaper cold storage (it must then stay there at least 90 days), and copy actions to other Regions or accounts.
  • Resource assignment: which resources the plan covers: by resource type, specific ARNs, or tags such as backup=daily, so new resources are protected the moment they are tagged.
  • Backup vault: where recovery points are stored, encrypted, with a vault access policy controlling who can delete or copy them. Fully managed resources (S3, EFS, DynamoDB with advanced features) are encrypted with the vault's KMS key; others (EBS, EC2, RDS, Aurora, FSx) keep the source resource's encryption.
Backup plan: daily backups, kept 35 days, copied to a second Region 
{
  "BackupPlanName": "orders-daily",
  "Rules": [{
    "RuleName": "daily-35d",
    "TargetBackupVaultName": "orders",
    // 05:00 UTC every day
    "ScheduleExpression":
      "cron(0 5 * * ? *)",
    "Lifecycle": {
      "DeleteAfterDays": 35
    },
    "CopyActions": [{
      "DestinationBackupVaultArn":
        "arn:aws:backup:eu-west-1:111111111111:backup-vault:orders-dr",
      "Lifecycle": {
        "DeleteAfterDays": 35
      }
    }]
  }]
}

Create it with aws backup create-backup-plan --backup-plan file://plan.json, then a selection that assigns resources by tag. The // comments are explanations only; remove them in a real file.

Continuous backups and point-in-time recovery

For RDS, Aurora and S3, a rule can take continuous backups, restorable to any second within up to 35 days (RDS to within about the last 5 minutes, S3 the last 15). A continuous backup copied to another Region or account becomes an ordinary snapshot without point-in-time recovery.

Copying to other Regions and accounts

Copies in another Region protect against a Regional disaster; copies in another account protect against a compromised or deleted account. Cross-account copy requires all accounts to be in the same AWS Organization, with the feature turned on from the management account; the destination vault's access policy must allow backup:CopyIntoBackupVault; and resources not fully managed by AWS Backup need a customer managed KMS key, because AWS managed keys can't be shared with another account.

Making backups tamper-proof

  • Vault Lock: enforces minimum and maximum retention so recovery points can't be deleted early. In governance mode, users with the right IAM permissions can remove the lock; in compliance mode, after a grace period of at least 72 hours, nobody can change or delete it, not even AWS.
  • Logically air-gapped vault: always locked in compliance mode, encrypted with an AWS owned key, and shareable to a recovery account for restores after a ransomware attack.
  • Legal holds: keep specific recovery points beyond their retention while an investigation runs.

Proving backups work

Restore testing restores recovery points on a schedule, records how long the restore took, keeps the restored resource for 1–168 hours so a script can validate it, then deletes it. Backup Audit Manager continuously checks controls such as "every resource is in a backup plan", "backups are copied cross-Region" or "restore time meets the target", and produces daily reports. It needs AWS Config.

AWS Backup for S3 requires S3 Versioning to be enabled on the bucket. A plan that covers an unversioned bucket fails for that bucket.

EBS snapshots and Data Lifecycle Manager

How snapshots work

EBS snapshots are stored in S3, Regionally, and are incremental: the first copies the whole volume, later ones only changed blocks, but each can restore the full volume on its own. Snapshots of the volumes on one instance can be taken together as multi-volume crash-consistent snapshots. For application consistency (databases flushed to disk), use pre and post scripts, or Windows VSS.

Amazon Data Lifecycle Manager (DLM)

Free, EBS-only automation: snapshot policies and AMI policies that target volumes or instances by tag, with up to four schedules each, retention by count or age, cross-Region copy, cross-account sharing, fast snapshot restore, and archiving of monthly snapshots.

AWS Backup or DLM?DLM for EBS snapshots and AMIs alone. AWS Backup when the policy should cover many services the same way, or needs vault locking, cross-account copies and audit reports.

Recycle Bin and the archive tier

  • Recycle Bin: retention rules keep deleted snapshots and EBS-backed AMIs (for 1–365 days) and deleted EBS volumes (1–7 days) recoverable, protecting against accidental or malicious deletion. Rules apply by tag or to the whole Region, and Region-wide rules can be locked.
  • EBS Snapshots Archive: up to 75% cheaper storage for snapshots kept long term but rarely restored, with a 90-day minimum and a restore of up to 72 hours.

Restoring databases

Skill 2.3.2Use various methods to restore databases (for example, point-in-time restore) to meet recovery time objective (RTO), recovery point objective (RPO), and cost requirements

Amazon RDS

Automated backups and point-in-time restore

RDS takes a daily snapshot in the backup window and uploads transaction logs every five minutes, so you can restore to any second within the retention period, up to about the last five minutes. Retention is 0 to 35 days (0 turns automated backups off; the default is 7 days in the console but 1 day from the CLI and API).

A point-in-time restore always creates a new DB instance, with a new endpoint and the default parameter and option groups unless you specify yours. The application then has to be pointed at the new endpoint, or the old instance renamed and the new one given its name.

Restore orders-db to just before a bad delete 
aws rds \
  restore-db-instance-to-point-in-time \
  --source-db-instance-identifier \
    orders-db \
  --target-db-instance-identifier \
    orders-db-restored \
  --restore-time 2026-11-03T09:14:00Z \
  --db-parameter-group-name orders-pg

Manual snapshots

Taken on demand and kept until you delete them, even after the database is deleted, unlike automated backups. Use them before risky changes and for long-term retention. A manual snapshot can be copied to another Region or shared with up to 20 accounts. A snapshot encrypted with the default RDS KMS key can't be shared: use a customer managed key.

Cross-Region automated backups

Replicates snapshots and transaction logs to another Region, so you can do a point-in-time restore there after a Regional outage.

Amazon Aurora

Backups, restore, Backtrack and cloning

  • Continuous backups to S3 can't be turned off (1–35 days, default 1). A point-in-time restore creates a new cluster.
  • Backtrack (Aurora MySQL only): rewinds the existing cluster in place to a point up to 72 hours back, in minutes, with no new cluster or endpoint change. The fastest fix for a bad change, but it must be turned on when the cluster is created or restored.
  • Cloning: a copy-on-write clone in minutes, sharing storage with the source until data changes, ideal for testing a recovery or investigating corrupted data without touching production.

Amazon DynamoDB

Point-in-time recovery and on-demand backups

PITR keeps continuous backups for a recovery period of 1 to 35 days (default 35) and restores to any second in it, typically up to five minutes ago. A restore always creates a new table, and these settings aren't carried over and must be set again: auto scaling, IAM policies, CloudWatch alarms, tags, streams, TTL, deletion protection and PITR itself. On-demand backups are full backups kept until deleted, with no effect on table performance.

Turn on PITR with a 14-day recovery period 
aws dynamodb update-continuous-backups \
  --table-name carts \
  --point-in-time-recovery-specification \
    PointInTimeRecoveryEnabled=true,\
RecoveryPeriodInDays=14

Choosing a method for RTO, RPO and cost

Undo a mistake from 20 minutes ago, as fast as possible

Aurora MySQL with Backtrack (minutes, in place). Otherwise point-in-time restore (RPO about five minutes; RTO the time to create a new instance or table and repoint the application).

Recover from a failed upgrade

A manual snapshot taken just before the change.

Keep yearly backups for seven years cheaply

AWS Backup with transition to cold storage.

Recover after a Regional outage

Cross-Region backup copies or cross-Region automated backups (RTO hours); for minutes, a cross-Region replica or a global database (see Disaster recovery).

Versioning

Skill 2.3.3Implement versioning for storage services (for example, Amazon S3, Amazon FSx)

Amazon S3

S3 Versioning

With versioning on, every overwrite creates a new version and a delete only adds a delete marker, so earlier versions can be restored. A bucket is unversioned (the default), enabled or suspended; once enabled it can never return to unversioned, only be suspended. Every version is stored and charged, so pair versioning with a lifecycle rule that expires noncurrent versions (Task 1.3).

Turn on versioning for the orders bucket 
aws s3api put-bucket-versioning \
  --bucket orders-docs \
  --versioning-configuration \
    Status=Enabled

Protecting versions

  • MFA Delete: requires multi-factor authentication to delete a version or change the versioning state. Only the root user can enable it, through the CLI or API.
  • S3 Object Lock: write-once-read-many protection on versions, for a retention period or with a legal hold. In governance mode, users with s3:BypassGovernanceRetention can override it; in compliance mode, nobody can delete the version until retention ends, not even the root user. It requires versioning and can't be turned off once enabled.

S3 Replication

Copies new objects automatically to another bucket in the same Region (SRR) or another Region (CRR), possibly in another account. It requires versioning on both buckets, doesn't copy objects that existed before the rule (use S3 Batch Replication for those), and doesn't replicate delete markers unless you turn that on. Replication Time Control adds a 15-minute replication SLA and metrics.

Replication isn't a backupReplication copies mistakes too: an overwrite or deletion is replicated. Versioning, Object Lock or AWS Backup protect against that.

Amazon FSx

Versions and backups by file system type

  • FSx for Windows File Server: shadow copies let users restore earlier versions of files themselves through Windows' "Previous Versions" tab; they're off by default and turned on with PowerShell. Automatic daily backups default to 30 days of retention in the console (0–90).
  • FSx for NetApp ONTAP: volume snapshots on a schedule (by default hourly, daily and weekly), browsable in a .snapshot directory, plus daily backups.
  • FSx for Lustre: no user snapshots; backups only for persistent file systems not linked to S3 (data linked to S3 is protected in S3, where you can use S3 Versioning).

AWS Backup can back up all FSx types alongside everything else.

Disaster recovery

Skill 2.3.4Follow disaster recovery procedures and best practices (for example, backup and restore, pilot light, warm standby, active/active)

AWS's whitepaper Disaster Recovery of Workloads on AWS: Recovery in the Cloud describes four strategies, from cheapest and slowest to most expensive and fastest. They differ in how much of the workload already runs in the recovery Region before disaster strikes.

The four strategies

Backup and restore

Data is backed up to the recovery Region (cross-Region backup copies, S3 replication). Nothing runs there. In a disaster you redeploy the infrastructure, ideally from infrastructure as code (CloudFormation, CDK), and restore the data. RPO and RTO are measured in hours. Cheapest; suitable for less critical workloads.

Pilot light

The data is live in the recovery Region, replicating continuously (a cross-Region read replica, an Aurora global database, DynamoDB global tables), but the application servers are switched off or not deployed. Recovery means starting and scaling the application tier and switching traffic. RTO and RPO in tens of minutes. AWS Elastic Disaster Recovery, which replicates servers block by block and launches them on demand, follows this pattern.

Warm standby

A scaled-down but fully functional copy of the whole workload runs in the recovery Region and could serve traffic immediately. Recovery means scaling it up and switching traffic. RTO and RPO in minutes.

Multi-site active/active

The workload runs at full scale in two or more Regions, all serving users, with data replicated between them (DynamoDB global tables, Aurora global databases). Losing a Region means routing everyone to the others. RTO and RPO near zero; the most expensive and complex. The active/passive variant, hot standby, runs at full scale but serves no traffic until failover.

Read the requirement and the budget: "hours acceptable, lowest cost" is backup and restore; "core data must be current, servers can start on demand" is pilot light; "a smaller working copy must take traffic within minutes" is warm standby; "no downtime, users served from multiple Regions" is active/active.

Building blocks

Data replication across Regions

  • Aurora Global Database: replicates to up to 10 secondary Regions with typical lag under a second. A planned switchover loses no data; an unplanned failover loses seconds of data and takes minutes.
  • DynamoDB global tables: multi-Region, multi-active tables, last writer wins, with low or zero RPO.
  • RDS cross-Region read replicas and S3 Cross-Region Replication.

Switching traffic

Route 53 failover routing with health checks, or ARC routing control for a manual, reliable switch (Task 2.2). For pilot light and warm standby, scaling the recovery Region up is part of the runbook.

Procedures and best practices

  1. Set RTO and RPO per workloadAgreed with the business, because they set the strategy and cost.
  2. Automate recoveryInfrastructure as code for the recovery Region and Systems Manager runbooks for the failover steps, so recovery doesn't depend on someone remembering the steps.
  3. Rely on the data plane during recoveryPrefer pre-provisioned capacity and DNS changes over creating resources during an incident, when control plane calls are most likely to be slow.
  4. Test regularlyRestore testing for backups, game days for full failovers, and practice runs for zonal autoshift. An untested plan is an assumption.
  5. Fail back deliberatelyPlan how to return to the primary Region and resynchronize data afterwards.

Key takeaways

  • RTO is how long recovery may take; RPO is how much data may be lost. Multi-AZ and replication copy mistakes; only backups taken before the mistake undo them.
  • AWS Backup plans: rules for frequency, window, retention, cold storage (90-day minimum) and copy actions; resources assigned by tag; vaults with access policies. Cross-account copies need one Organization, a vault policy and customer managed KMS keys. Vault Lock (compliance mode is immutable after 72 hours), logically air-gapped vaults, restore testing and Backup Audit Manager harden and prove backups. S3 backup needs versioning.
  • EBS snapshots are incremental and Regional; DLM automates snapshots and AMIs by tag for free; Recycle Bin recovers deleted snapshots, AMIs and volumes; the archive tier is 75% cheaper for rarely restored snapshots.
  • RDS point-in-time restore (to about five minutes ago, retention 0–35 days) and DynamoDB PITR (1–35 days) always create a new instance or table; manual snapshots persist after deletion. Aurora Backtrack rewinds in place (Aurora MySQL, up to 72 hours); cloning gives a fast copy.
  • S3 Versioning can be suspended but never removed; MFA Delete and Object Lock (governance or compliance) protect versions; replication needs versioning on both buckets and isn't a backup. FSx for Windows has shadow copies, ONTAP snapshots.
  • DR strategies: backup and restore (hours), pilot light (data live, servers off; tens of minutes), warm standby (scaled-down full copy; minutes), multi-site active/active (near zero). Automate, test and plan failback.
