Task 2.2: Implement highly available and resilient environments

Keeping a workload running when parts of it fail: how load balancer and Route 53 health checks decide what is healthy and what to do when nothing is, why they fail and how to fix them, and how to build each tier, from instances to databases to NAT, so that losing an Availability Zone doesn't take the application down.

Overview

Task 2.2

Implement highly available and resilient environments.

High availability means the application keeps serving users when a component fails; resilience means it recovers by itself. On AWS the unit of failure to design for is usually an Availability Zone: every tier should keep working if one zone is lost. Health checks are how the system notices failure and routes around it, which is why the skill pairs them with Multi-AZ design.

The examples continue the orders application: EC2 instances in an Auto Scaling group across three Availability Zones behind an Application Load Balancer, an RDS for PostgreSQL database, and a Route 53 record shop.example.com pointing at the load balancer.

ELB health checks

Skill 2.2.1Configure and troubleshoot Elastic Load Balancing (ELB) and Amazon Route 53 health checks

How a load balancer judges a target

Settings and defaults

Each target group has its own health check. The load balancer sends a request to every target every interval; a target becomes unhealthy after the unhealthy threshold of consecutive failures and healthy again after the healthy threshold of consecutive successes. A response counts as a success if it arrives within the timeout with a code in the matcher (success codes).

SettingApplication LBNetwork LB
ProtocolHTTP or HTTPS (default HTTP)TCP (default), HTTP or HTTPS
Interval30 s (5–300)30 s (5–300)
Timeout5 s6 s for HTTP, 10 s for TCP and HTTPS
Healthy / unhealthy threshold5 / 25 / 2
Success codes200 (any of 200–499)200–399

With the defaults, a failed target is out of service after about a minute (two failures 30 seconds apart) and needs five successes, about two and a half minutes, to come back. Point the health check at a lightweight path such as /health that checks the application can actually serve requests, not just that the web server answers.

Tighten the orders target group's health check 
aws elbv2 modify-target-group \
  --target-group-arn "$TG_ARN" \
  --health-check-path /health \
  --health-check-interval-seconds 10 \
  --healthy-threshold-count 3 \
  --unhealthy-threshold-count 2 \
  --matcher HttpCode=200

When every target is unhealthy: fail open

If all targets in a target group fail their health checks, Application and Network Load Balancers fail open: they send traffic to all targets anyway, on the reasoning that a broken health check is more likely than every server failing at once. Gateway Load Balancers don't fail open; traffic is dropped. For an Application Load Balancer, an HTTP 503 means the target group has no registered targets, not that they are all unhealthy.

Settings around health

  • Deregistration delay (connection draining): how long a deregistering target keeps finishing in-flight requests before removal; default 300 seconds (0–3,600). Shorten it for fast, short requests to speed up deployments and scale-in.
  • Slow start (Application LB): ramps traffic to a newly healthy target over 30–900 seconds, for applications that need to warm caches. Off by default.
  • Target group health thresholds: a minimum number or percentage of healthy targets below which the load balancer fails DNS over to other zones or load balancers, rather than waiting for every target to fail.
  • Automatic target weights (Application LB with the weighted random algorithm): with anomaly mitigation on, sends less traffic to targets returning unusually many errors even before they fail health checks.

Cross-zone load balancing

What it does and the defaults

Without cross-zone load balancing, each load balancer node sends traffic only to targets in its own Availability Zone, so a zone with fewer healthy targets gets the same share of traffic and overloads them. With it, every node spreads traffic across all registered targets in all zones.

  • Application Load Balancer: always on at the load balancer; it can only be turned off per target group.
  • Network and Gateway Load Balancers: off by default; turning it on for a Network Load Balancer incurs inter-AZ data transfer charges.

Troubleshooting unhealthy targets

Read the reason code first

aws elbv2 describe-target-health (or the target group's Targets tab and the load balancer's resource map) gives a reason code for every unhealthy target:

  • Target.Timeout: no response in time. Usually a security group on the instance that doesn't allow the health check port from the load balancer's security group, a network ACL blocking it, or a target too overloaded to answer.
  • Target.ResponseCodeMismatch: the target answered with a code outside the matcher, often a 404 because the health check path doesn't exist, or a 301 redirect to HTTPS.
  • Target.FailedHealthChecks: the connection failed or the application isn't listening on the health check port.
  • Target.NotRegistered, Target.NotInUse: the target isn't registered, or is in an Availability Zone the load balancer isn't enabled in.
  • Elb.InitialHealthChecking: still being checked for the first time; wait.

The network rules that most often cause it

  • The instance security group must allow traffic on the health check port from the load balancer's security group (the simplest rule: allow from the load balancer's security group).
  • The network ACL on the instances' subnets must allow the health check port inbound and ephemeral ports 1024–65535 outbound, because NACLs are stateless; the load balancer's subnets need the mirror image.
  • Some applications only answer requests for a specific host name; the health check's Host header is the target's private IP address, so a virtual host configuration may reject it.

For detail on every check, turn on health check logs, delivered to S3, which record each check's result and a reason such as TimedOut or ResponseCodeMismatch.

Instances behind a load balancer keep getting replaced, even though the application is fine: the Auto Scaling group uses ELB health checks and the health check path or security group is wrong, so healthy instances are judged unhealthy. Fix the health check, and set a health check grace period long enough for the application to start.

Route 53 health checks

Skill 2.2.1(continued) Route 53 health checks and DNS failover

Load balancer health checks route around failed targets inside one deployment. Route 53 health checks work one level up: they decide which DNS answer to give, so traffic can move away from a whole load balancer, Region or site.

Types of health check

Endpoint health checks

Health checkers in several AWS Regions around the world send HTTP, HTTPS or TCP requests to an IP address or domain name. For HTTP and HTTPS, the endpoint must accept a TCP connection within 4 seconds and return a 2xx or 3xx status within 2 seconds; optionally the body must contain a given string within its first 5,120 bytes (string matching). HTTPS checks don't validate the certificate.

  • Request interval: 30 seconds, or 10 seconds (fast, extra cost, and can't be changed later).
  • Failure threshold: consecutive failures before a checker considers the endpoint unhealthy; default 3 (1–10).
  • Verdict: the endpoint is healthy if more than 18% of the health checkers report it healthy.

Calculated health checks

Combine other health checks: healthy if at least a set number of the child checks are healthy, for example "healthy if 2 of the 3 web servers are". Calculated checks can't contain other calculated checks.

CloudWatch alarm health checks

Healthy or unhealthy according to a CloudWatch alarm's state. This is how to health-check private resources: Route 53's checkers are on the internet and can't reach private, local or non-routable IP addresses, but an alarm on, say, a private database's metrics can. You choose what an alarm in INSUFFICIENT_DATA means (healthy, unhealthy or last known status).

Create an HTTPS health check for the shop's endpoint 
aws route53 create-health-check \
  --caller-reference shop-2026-11-03 \
  --health-check-config '{
    "Type": "HTTPS",
    "FullyQualifiedDomainName":
      "shop.example.com",
    "ResourcePath": "/health",
    "RequestInterval": 30,
    "FailureThreshold": 3
  }'

Health checks in routing

Failover routing

A primary record with a health check and a secondary record: Route 53 answers with the primary while it is healthy and the secondary when it isn't, for example a static "we'll be back soon" site in S3, or a standby stack in another Region. The secondary's health check is optional; if both are unhealthy, Route 53 returns the primary.

Evaluate target health on alias records

An alias record pointing at an AWS resource such as a load balancer doesn't need its own health check: turn on Evaluate target health and Route 53 uses the load balancer's target group health. The record is unhealthy if any of its target groups is unhealthy, or all are empty.

Other routing policies

Weighted, latency, geolocation and multivalue records skip unhealthy records when a health check is attached. Two rules surprise people: a record without a health check is always treated as healthy, and if every record in a group is unhealthy, Route 53 treats them all as healthy and keeps answering, rather than returning nothing.

Troubleshooting Route 53 health checks

  • Unhealthy, but the site works: the firewall or security group doesn't allow Route 53's health checkers. Allow their IP ranges, most easily with the managed prefix list com.amazonaws.region.route53-healthchecks.
  • Health check on a private IP: it can't work; use a CloudWatch alarm health check.
  • Can't find the metrics or alarm: Route 53 health check metrics exist only in us-east-1, so alarms on HealthCheckStatus, and their SNS topics, must be created there.
  • Slow to fail over: time to failover is about interval × failure threshold, plus DNS caching for the record's TTL. Give non-alias failover records a short TTL (such as 60 seconds; alias records use the target's TTL), and use the fast interval if needed.

Amazon Application Recovery Controller (ARC)

Zonal shift and zonal autoshift

Health checks catch failures that make targets fail. Some zone problems don't: higher latency or errors in one Availability Zone while health checks still pass. Zonal shift lets you move traffic away from one Availability Zone for a supported resource, for 1 minute up to 3 days (extendable), and then back. It works for Application and Network Load Balancers (enable it on each load balancer first), EC2 Auto Scaling groups and Amazon EKS. With zonal autoshift, AWS shifts traffic itself when its own telemetry shows a zone impairment, and runs weekly practice shifts to prove the application copes with losing a zone, so you must have capacity in the remaining zones.

Routing control

For multi-Region applications: on/off switches, backed by a highly reliable cluster in five Regions, that flip special Route 53 health checks and so move traffic between Regions, with safety rules that stop you switching everything off at once.

ARC's readiness check feature has been in maintenance since March 31, 2026: no new customers. AWS suggests ARC Region switch instead. Zonal shift, zonal autoshift and routing control are unaffected.

Fault-tolerant Multi-AZ systems

Skill 2.2.2Configure fault-tolerant systems (for example, Multi-AZ deployments)

The principle: static stability

Have the capacity before the failure

AWS's Well-Architected Framework calls it static stability: the system keeps working through a failure without having to make changes. Instead of planning to launch replacement instances in another zone when one fails (which depends on control plane calls succeeding during an incident), run enough capacity in each zone beforehand. With three zones, size each to carry the load if one is lost: about 50% of peak each, 150% in total.

Compute and networking

EC2 Auto Scaling across zones

Give the group subnets in at least two, preferably three, Availability Zones. It spreads instances evenly, replaces failed ones in the remaining zones, and rebalances when a zone recovers (launching new instances before terminating old ones). Use ELB health checks so instances that fail the application check are replaced too.

Load balancers

Enable the load balancer in every zone the targets are in; it places a node in each enabled zone. A target in a zone that isn't enabled receives no traffic.

NAT gateways

A standard NAT gateway lives in one Availability Zone. If private subnets in all zones route through one NAT gateway, losing that zone cuts every zone's outbound internet access, and cross-zone traffic costs extra. Create one NAT gateway per zone and route each zone's private subnets to its own. A newer regional NAT gateway mode spans zones automatically and doesn't need a public subnet; zonal gateways are still needed for private NAT.

Databases

RDS Multi-AZ DB instance

A standby in another zone, kept up to date by synchronous replication, so no committed data is lost on failover. The standby can't serve reads. On failure (host, storage or zone failure, or patching), RDS points the database's DNS name at the standby, typically in 60–120 seconds; the application reconnects to the same endpoint. Test it with a reboot with failover:

Force a Multi-AZ failover to test recovery 
aws rds reboot-db-instance \
  --db-instance-identifier orders-db \
  --force-failover

Applications must reconnect after failover and must not cache the database's IP address: a long DNS cache (such as a Java default) keeps them talking to the old primary.

RDS Multi-AZ DB cluster

A writer and two readable standbys in three zones, with semisynchronous replication (at least one reader confirms each write). Failover is typically under 35 seconds, and the standbys serve read traffic through a reader endpoint. Available for RDS for MySQL and RDS for PostgreSQL.

Aurora

Aurora's storage keeps six copies of the data across three Availability Zones, whatever the instances do. For instance failover, add Aurora Replicas in other zones: if the writer fails, a replica is promoted, typically in under 60 seconds and often under 30. Without any replica, Aurora has to recreate the writer, typically in under 10 minutes. Promotion tiers (0 is highest, 15 lowest) decide which replica is promoted.

ElastiCache

For Valkey and Redis OSS, Multi-AZ with automatic failover promotes a replica in another zone when the primary fails; it needs at least one replica in a different zone, and it is always on for cluster mode enabled. Memcached has no replication, so a failed node's cached data is lost and must be refilled from the database.

Storage services that are Multi-AZ by default

  • Amazon S3 Standard, Standard-IA, Intelligent-Tiering and the Glacier classes store data in at least three zones; One Zone-IA and Express One Zone use one.
  • DynamoDB replicates every table across three zones automatically.
  • Amazon EFS Regional file systems span multiple zones; EFS One Zone doesn't survive a zone loss. Create a mount target in each zone the clients run in.
  • EBS volumes are replicated within one zone only: for zone resilience, take snapshots (stored regionally) or replicate at the application level.

"Survive the loss of an Availability Zone with no data loss" for RDS points to Multi-AZ. "Scale reads" points to read replicas (Task 2.1), which are asynchronous and not a failover mechanism by default. "Fastest failover with readable standbys" points to a Multi-AZ DB cluster or Aurora with replicas.

A Multi-AZ RDS deployment protects against zone failure, not against bad data: a mistaken DELETE is replicated to the standby instantly. Protection against that is backups and point-in-time restore (Task 2.3).

Key takeaways

  • Load balancer health checks: interval, timeout, healthy and unhealthy thresholds and success codes per target group. ALB and NLB fail open when every target is unhealthy; GWLB doesn't. Point checks at a real health path.
  • Troubleshoot with reason codes: Target.Timeout is usually a security group or NACL (allow the health check port from the load balancer, and ephemeral ports outbound), Target.ResponseCodeMismatch a wrong path or redirect. Health check logs give per-check detail.
  • Cross-zone load balancing is always on for ALB (off only per target group) and off by default for NLB and GWLB. Deregistration delay defaults to 300 seconds.
  • Route 53 health checks: endpoint (HTTP, HTTPS, TCP, string matching), calculated, or CloudWatch alarm for private resources; healthy if over 18% of checkers agree; allow the checkers through firewalls; metrics only in us-east-1.
  • Failover routing returns the secondary when the primary is unhealthy; alias records can evaluate target health; records without health checks are always healthy, and if all are unhealthy all are treated as healthy.
  • ARC zonal shift moves traffic away from an impaired zone (ALB, NLB, Auto Scaling, EKS); zonal autoshift lets AWS do it. Readiness check is closed to new customers.
  • Design for zone loss with static stability: capacity in every zone beforehand, Auto Scaling across three zones, one NAT gateway per zone (or a regional NAT gateway).
  • RDS Multi-AZ instance: synchronous standby, not readable, 60–120 s failover. Multi-AZ DB cluster: two readable standbys, under 35 s. Aurora: six storage copies; replicas fail over in under 60 s, no replica means up to 10 minutes. S3, DynamoDB and EFS Regional are Multi-AZ by default; EBS is single-zone.
