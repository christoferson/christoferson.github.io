Overview

Task 5.3

Troubleshoot network connectivity issues.

The final task brings Domain 5 together. Questions describe a symptom ("the instance can't reach the internet", "users see stale pages", "the VPN tunnel keeps dropping") and expect the specific misconfiguration. Work through them methodically: the path, then each filter on it, then the logs to confirm.

The examples use the orders VPC from Task 5.1 (10.0.0.0/16, public, private and database subnets), connected to the data center over Site-to-Site VPN and Direct Connect, with CloudFront in front of the application.

VPC configurations

Skill 5.3.1Troubleshoot VPC configurations (for example, subnets, route tables, network ACLs, security groups, transit gateways, NAT gateways)

A method

  1. Read the symptomA timeout usually means something silently dropped the traffic: a route, security group or network ACL. Connection refused means the packet arrived and nothing is listening on that port, so the network is fine and the application isn't.
  2. Check the route both waysSource subnet's route table to the destination, and the destination's route table back.
  3. Check the filtersSecurity groups at both ends (inbound on the destination), and network ACLs on both subnets in both directions, including ephemeral ports.
  4. Check the gatewayDoes the NAT gateway, internet gateway, peering connection or transit gateway attachment exist, and is it available?
  5. Confirm with toolsReachability Analyzer for the configuration, Flow Logs for what actually happened.

Common failures

SymptomUsual causeFix
Instance in a "public" subnet unreachable from the internetNo public IP, or the subnet's route table has no 0.0.0.0/0 route to the internet gatewayAssign a public or Elastic IP; fix the route; allow the port in the security group
Private instance can't reach the internetDefault route missing or pointing at the wrong target; NAT gateway placed in a private subnet; NAT gateway in another zone deletedRoute 0.0.0.0/0 to a NAT gateway in a public subnet, one per zone (or a regional NAT gateway)
Web server reachable on 443 only sometimes, or replies lostNetwork ACL allows inbound 443 but not outbound ephemeral portsAllow outbound 1024-65535 (and inbound for replies to the server's own calls)
Ping fails but TCP worksICMP isn't allowed in the security groupAllow ICMP if needed; don't use ping as the only test
Peered VPCs can't talkRoute missing on one side, security group not allowing the peer CIDR, or overlapping CIDRsRoutes in both VPCs; allow the CIDR or peer security group
Route shows "blackhole"Its target (NAT gateway, instance, interface, peering) was deletedPoint the route at a working target

NAT gateway metrics

  • ErrorPortAllocation above 0: too many simultaneous connections to one destination (55,000 per IP). Add IP addresses or spread across NAT gateways.
  • ConnectionEstablishedCount well below ConnectionAttemptCount: the destination isn't answering.
  • IdleTimeoutCount rising: connections idle for 350 seconds were dropped; clients reusing them see failures. Use TCP keepalives or shorter client timeouts.
  • PacketsDropCount: as a share of packets in, more than a tiny fraction suggests a service issue; check AWS Health.

Transit gateway problems

Association and propagation

Each attachment is associated with one transit gateway route table (which routes its outgoing traffic) and can propagate its routes into any number of tables. "VPC A can't reach VPC B" usually means B's routes aren't propagated (or statically added) to the table A is associated with, or the return path is missing. Then check the VPCs themselves:

  • The VPC route tables need routes for the other VPC's CIDR pointing at the transit gateway.
  • The attachment needs a subnet in every Availability Zone where resources must use it.
  • A VPC whose CIDR overlaps another attachment's doesn't get its routes propagated.
  • Traffic through a stateful firewall in an inspection VPC needs appliance mode on that attachment, so both directions of a flow use the same zone; without it, asymmetric routing drops replies.

VPC Reachability Analyzer

Analyze the configuration, not the traffic

Give it a source and destination (instance, network interface, internet gateway, transit gateway, endpoint, peering connection; IP addresses as destinations). It models the configuration, without sending packets, and either shows the hop-by-hop path or names the blocking component: the security group, network ACL, route table or missing gateway. It works across peering and transit gateways, and across accounts in an organization. Each analysis costs $0.10.

Can the app instance reach the database on 5432? 
aws ec2 create-network-insights-path \
  --source i-0app1234 \
  --destination i-0db5678 \
  --protocol tcp \
  --destination-port 5432

aws ec2 start-network-insights-analysis \
  --network-insights-path-id nip-0abc

Network Access Analyzer answers the opposite question: which paths exist that shouldn't (for example, "anything in the database subnets reachable from an internet gateway"), for security audits.

Networking logs

Skill 5.3.2Collect and interpret networking logs (for example, VPC flow logs, ELB access logs, AWS WAF web ACL logs, CloudFront logs, container logs)

VPC Flow Logs

What they record

Metadata about IP traffic (not packet contents) for a VPC, subnet or network interface, delivered to CloudWatch Logs, S3 or Firehose, aggregated over 10 minutes by default or 1 minute. The default record has: version, account, interface, source and destination address and port, protocol, packets, bytes, start, end, action (ACCEPT or REJECT) and log status. Custom formats add fields such as tcp-flags, pkt-srcaddr (the original source behind a NAT gateway), flow-direction, traffic-path and reject-reason. A flow log can't be edited after creation; delete and recreate it to change the format.

Not recorded: queries to the Amazon DNS server, instance metadata (169.254.169.254), Time Sync, DHCP and Windows license activation traffic.

Flow log for the VPC to S3, 1-minute aggregation 
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0abc1234 \
  --traffic-type ALL \
  --log-destination-type s3 \
  --log-destination \
    arn:aws:s3:::orders-flowlogs \
  --max-aggregation-interval 60

Reading ACCEPT and REJECT

Because security groups are stateful and network ACLs aren't, the pattern of records tells you which one blocked traffic:

Records seenMeaning
Inbound REJECTThe security group or the network ACL denied the request
Inbound ACCEPT, then outbound REJECT for the replyThe network ACL blocked the reply (a security group would have allowed it automatically); add the ephemeral port rule
Inbound ACCEPT and outbound ACCEPT, but the client still failsThe network is fine; look at the application or the return route
No records at allTraffic never reached the interface: routing, DNS, or a filter before it
CloudWatch Logs Insights: top rejected sources 
fields srcAddr, dstAddr, dstPort, action
| filter action = "REJECT"
| stats count(*) as n by srcAddr, dstPort
| sort n desc
| limit 20

Load balancer logs

ALB access logs

Off by default; turn them on to an S3 bucket (written every 5 minutes) or, now, deliver them through CloudWatch to CloudWatch Logs, Firehose or S3. Each request records timings and two status codes, which separate load balancer problems from target problems:

  • elb_status_code is what the client got; target_status_code is what the target returned, or - if it never answered.
  • A processing time of -1 means the load balancer couldn't send the request to a target or the target didn't respond before the idle timeout (typically a 502 or 504).
  • error_reason and actions_executed explain authentication, Lambda and WAF outcomes (WAF blocks show as 403).

ALB connection logs record TLS handshakes and client certificate checks, and health check logs show why targets fail checks. NLB access logs exist only for TLS listeners.

WAF and CloudFront logs

AWS WAF logs

For each request: the action, the terminatingRuleId that decided it (Default_Action if no rule matched), the rule group and its rule, labels, and the request's headers, URI and client IP. Use them to find which rule is blocking legitimate users, then exclude that rule or set it to Count. Sensitive fields can be redacted.

CloudFront logs

Standard logs go to S3, CloudWatch Logs or Firehose, usually within an hour. The x-edge-result-type field shows Hit, RefreshHit, Miss, Error, LimitExceeded or CapacityExceeded; the detailed result type distinguishes origin problems such as OriginConnectError, OriginDnsError and OriginCommError (timeout). Real-time logs go to Kinesis Data Streams within seconds, with a sampling rate, for live dashboards.

Container logs

  • Amazon ECS: the awslogs log driver sends container output to CloudWatch Logs; FireLens (Fluent Bit) routes it to other destinations. Container Insights adds network metrics per task and service.
  • Amazon EKS: control plane logs (API server, audit, authenticator, controller manager, scheduler) are turned on per cluster and go to CloudWatch Logs; node and pod logs need an agent such as Fluent Bit or the CloudWatch Observability add-on.
  • Tasks using the awsvpc network mode have their own network interfaces, so VPC Flow Logs (with the ECS fields) cover their traffic too.

"Which IP is being blocked by the network ACL?" is VPC Flow Logs. "Are the 502s coming from the load balancer or the targets?" is ALB access logs. "Which WAF rule blocked this customer?" is WAF logs. "Is CloudFront serving from cache?" is the CloudFront result type.

CloudFront caching

Skill 5.3.3Identify and remediate CloudFront caching issues

How long CloudFront caches

TTLs and the origin's headers

The cache policy sets a minimum, default and maximum TTL, and the origin's Cache-Control headers decide within that range:

  • With max-age (or s-maxage, which takes precedence for CloudFront), the object is cached that long, clamped between the minimum and maximum TTL.
  • Without caching headers, the default TTL applies (24 hours unless changed).
  • no-cache, no-store and private are honored only if the minimum TTL is 0; otherwise CloudFront caches for the minimum TTL anyway.

Diagnosing

Check the response headers

The X-Cache response header says Hit from cloudfront, RefreshHit from cloudfront or Miss from cloudfront; Age shows how long the object has been cached. The CacheHitRate CloudWatch metric (an additional, paid metric, in us-east-1) shows the trend.

Is this file coming from the cache? 
curl -sI https://www.example.com/app.js \
  | grep -i -E 'x-cache|age|cache-control'
ProblemUsual causeFix
Low cache hit ratioThe cache key includes headers, cookies or query strings that vary per user (all of them, User-Agent, Authorization, session cookies)Use a cache policy keeping only what changes the response (CachingOptimized for static files); pass other values with an origin request policy instead
Nothing is cachedOrigin sends no-cache, private or max-age=0 (or sets cookies) with a minimum TTL of 0; or CachingDisabled is on the behaviorFix the origin's headers, or set a minimum TTL; separate behaviors for static and dynamic paths
Users see old contentLong TTL and the file name didn't changeInvalidate the paths now; use versioned file names in future
An error page persists after the origin recoveredCloudFront caches errors such as 404 and 5xx (10 seconds by default)Lower the error caching minimum TTL in custom error responses
Different users get each other's pagesPersonalized responses cached without the cookie or header that distinguishes themDon't cache personalized paths, or include the distinguishing value in the cache key

Errors from the origin

  • 502 Bad Gateway: CloudFront couldn't complete the connection, commonly because the origin's certificate doesn't match the origin domain name, or it uses an unsupported protocol or cipher.
  • 504 Gateway Timeout: the origin didn't answer in time (by default 3 connection attempts of 10 seconds, then a 30-second response timeout): a security group or firewall not allowing CloudFront, an origin not reachable from the internet, or a slow application. Allow the CloudFront origin-facing prefix list, or raise the timeout.
  • 403 from an S3 origin with OAC: the bucket policy doesn't allow cloudfront.amazonaws.com for this distribution, the objects are encrypted with a KMS key whose policy doesn't allow CloudFront, or the request is for / with no default root object. S3 website endpoints can't use OAC; they are custom origins.

Hybrid and private connectivity

Skill 5.3.4Troubleshoot hybrid and private connectivity issues

Site-to-Site VPN

Tunnels that won't come up or stay up

Each connection has two tunnels in different zones; configure both on the customer gateway so maintenance on one doesn't cause an outage. Check in this order:

  1. IKE phase 1Pre-shared key, IKE version and encryption, hashing and Diffie-Hellman settings must match. The customer gateway firewall must allow UDP 500 and 4500 (NAT traversal).
  2. IPsec phase 2Proposals and traffic selectors must match.
  3. Keeping it upIdle tunnels can drop: generate traffic or configure dead peer detection and its action correctly.
  4. RoutingFor BGP, check ASNs and that TCP 179 is open; for static VPNs, the static routes. In the VPC, turn on route propagation from the virtual private gateway or add routes.

The TunnelState metric is 1 when a tunnel is up and 0 when down (values in between mean one of two tunnels is down). VPN tunnel logs in CloudWatch Logs show IKE and IPsec negotiation, dead peer detection and BGP messages, such as a pre-shared key mismatch or "No proposal chosen".

Tunnel status from the CLI 
aws ec2 describe-vpn-connections \
  --vpn-connection-ids vpn-0abc1234 \
  --query \
    'VpnConnections[].VgwTelemetry'

AWS Direct Connect

Layer by layer

  • Physical: ConnectionState down, ConnectionErrorCount or poor ConnectionLightLevelTx and Rx values point to cabling or optics at the location; work with the provider.
  • BGP: the session stays down if the VLAN, peer IP addresses, ASN or MD5 key don't match. VirtualInterfaceBgpStatus now reports the session state in CloudWatch.
  • Prefix limit: a private or transit virtual interface accepts 100 prefixes from you by default; advertising more puts the BGP session into idle. Summarize routes, or raise the limit where supported.
  • Routing: advertise the on-premises prefixes, propagate routes into the VPC route tables (watch the 100 propagated routes per route table limit), and allow the traffic in security groups and network ACLs.

Direct Connect and VPN together

With a VPN as backup, AWS prefers the most specific prefix first; for the same prefix, Direct Connect BGP routes are preferred over VPN static routes, then VPN BGP routes. If traffic uses the VPN when Direct Connect is up, check whether the VPN advertises a more specific route.

Network monitoring

Skill 5.3.5Monitor networks by using CloudWatch network monitoring services

Three CloudWatch services

Network Synthetic Monitor

AWS-managed probes, with no agents, send ICMP or TCP traffic from your VPC subnets to on-premises destinations over Direct Connect or VPN, and report round-trip time and packet loss. Its network health indicator says whether degradation is on the AWS side, which tells you whether to call AWS or your own network team.

Internet Monitor

Shows how internet problems affect your users: availability and performance from each city and internet provider to your VPCs, Network Load Balancers, CloudFront distributions or WorkSpaces. It raises health events (to EventBridge) when a provider's problem affects your traffic, and suggests which Region or delivery option would serve users better.

Network Flow Monitor

Lightweight agents on EC2 instances and EKS nodes report TCP performance for flows between your workloads and to AWS services (round-trip time, retransmissions, timeouts and data transferred), with top contributors and a network health indicator. For EKS, container network observability builds on it with a service map and flow table.

QuestionService
Is the path to our data center losing packets, and whose fault is it?Network Synthetic Monitor
Are users in one country affected by an ISP outage?Internet Monitor
Which workload's traffic is slow or retransmitting inside AWS?Network Flow Monitor
Why can't A reach B according to the configuration?Reachability Analyzer (a VPC tool, not CloudWatch)

Pair these with service metrics and alarms: NAT gateway errors, VPN TunnelState, Direct Connect ConnectionState and BGP status, load balancer 5xx counts and CloudFront error rates, all alarmed in CloudWatch as in Task 1.1.

Key takeaways

  • Timeouts mean something dropped traffic (route, security group, ACL); refused means nothing is listening. Check routes both ways, then both filters, then the gateway, and confirm with Reachability Analyzer, which names the blocking component.
  • NAT gateway: ErrorPortAllocation (add IPs), IdleTimeoutCount (350-second idle drop). Transit gateway: association versus propagation, VPC routes back, an attachment subnet per zone, appliance mode for stateful firewalls.
  • Flow Logs: inbound ACCEPT with outbound REJECT means a network ACL blocked the reply; Amazon DNS and metadata traffic isn't recorded; recreate to change the format. ALB logs separate elb_status_code from target_status_code; WAF logs name the terminating rule; CloudFront logs show the edge result type.
  • CloudFront caching: TTLs come from the cache policy and origin Cache-Control; trim the cache key for hit ratio; invalidate or version for stale content; errors are cached briefly; 502 is often a certificate mismatch, 504 an unreachable or slow origin, 403 an OAC or KMS policy problem.
  • VPN: two tunnels, matching IKE and IPsec settings, UDP 500 and 4500, route propagation, tunnel logs. Direct Connect: physical metrics, BGP settings, the 100-prefix limit; most specific prefix wins, then DX over VPN. Endpoints: private DNS, security groups, policies, same-Region gateway endpoints.
  • CloudWatch: Network Synthetic Monitor for hybrid paths, Internet Monitor for users' internet experience, Network Flow Monitor for workload TCP performance.
