Task 1.2: Identify and remediate issues by using monitoring and availability metrics

Turning a signal into a fix: reading performance and availability metrics to work out what is wrong, correlating them with what changed, and then automating the response, with Lambda, Systems Manager Automation runbooks, EventBridge rules, and the newer AI-assisted tools, CloudWatch investigations and AWS DevOps Agent.

Overview

Task 1.2

Identify and remediate issues by using monitoring and availability metrics.

Task 1.1 set up the signals. This task is what you do with them: diagnose, then fix, and preferably fix without a person being woken up. Questions describe symptoms ("instances are unhealthy every night at 2 a.m.", "the queue is growing", "an alarm fires but nothing is fixed") and ask which metric identifies the cause or which service automates the response.

Analyze metrics and automate remediation

Skill 1.2.1Analyze performance metrics and automate remediation strategies by using AWS services and functionality (for example, CloudWatch, Lambda, AWS Systems Manager, CloudTrail, Kiro, AWS DevOps Agent)

Every incident follows the same four steps, and each has its own tools:

  1. DetectAn alarm or an event says something is wrong (Task 1.1).
  2. DiagnoseMetrics narrow down which component; logs and traces say why; CloudTrail says what changed.
  3. RemediateLambda or a Systems Manager Automation runbook does the fix, triggered by the alarm or an EventBridge rule.
  4. Verify and learnWatch the metric recover, record the incident, and remove the cause so it doesn't recur.

Availability metrics: which one points where

"Availability metrics" are the ones that say whether users can actually use the system. Knowing which layer each belongs to is how you localize a fault.

MetricWhere it comes fromWhat it tells you
StatusCheckFailed_SystemEC2AWS infrastructure under the instance has failed: recover the instance
StatusCheckFailed_InstanceEC2The instance's own operating system or network config is broken: reboot or replace
UnHealthyHostCountApplication Load Balancer target groupTargets are failing the load balancer's health check, so capacity is shrinking. If every target is unhealthy, the ALB fails open and sends traffic to all of them anyway
HTTPCode_ELB_5XX_CountLoad balancerErrors the load balancer generated itself: 502 (the target refused or reset the connection, or sent a malformed response), 503 (no registered targets), 504 (the target didn't connect or respond in time)
HTTPCode_Target_5XX_CountLoad balancerThe application returned errors: the fault is in your code or its dependencies
TargetResponseTimeLoad balancerHow slow the application is; use p99, not Average
Errors, ThrottlesLambdaFunction failures; throttles mean concurrency limits were hit
ApproximateAgeOfOldestMessageAmazon SQSConsumers can't keep up: the best early warning of a stuck worker fleet
HealthCheckStatusRoute 53 health checkWhether an endpoint answers Route 53's health checkers, which probe from locations around the world

Distinguish the two 5XX metrics. HTTPCode_Target_5XX_Count means the application answered with an error: the fault is in your code or its dependencies. HTTPCode_ELB_5XX_Count means the load balancer couldn't get a usable answer at all: check security groups and network ACLs between the load balancer and targets (502, 504), target keep-alive and idle timeouts (502, 504), and whether any targets are registered (503).

"All targets are unhealthy, so the load balancer must be returning 503" is wrong for an Application Load Balancer. When every target fails its health check, the ALB fails open and routes to all of them. The 503 comes only when the target group has no registered targets, or all of them are in the unused state.

Correlating with what changed

AWS CloudTrail

Most "it broke suddenly" incidents follow a change. CloudTrail's Event history answers it in minutes: filter by event name, user or resource and look at the last 90 days of management events. Classic finds are a security group rule removed, a launch template version changed, a scaling policy edited, or an instance profile detached. Sending a trail to CloudWatch Logs lets a metric filter alarm on changes as they happen, so you learn about a risky change before it causes an incident.

Pairing metrics with deployments

CloudWatch dashboards can overlay annotations, and CloudWatch Application Signals surfaces change events from CloudTrail against a service's latency and error graphs, so a step change in errors lines up visibly with the deployment or configuration change that caused it.

Automating the fix

AWS Lambda

A function invoked straight from an alarm action or an EventBridge rule, for fixes that need custom logic or call several APIs: deregister a failed target, clear a cache, post a formatted message to a chat channel, or tag an instance for investigation. You write and maintain the code, and the function's execution role carries the permissions for whatever it changes.

Systems Manager Automation

A runbook does the same kind of work without you writing a service, and with built-in step logic, approvals, rate control and an execution history that auditors can read. AWS supplies hundreds of ready-made runbooks, so common fixes (restart an instance, resize a volume, remove a public bucket ACL) need no code at all. This is the default answer for operational remediation on this exam; see Systems Manager Automation runbooks.

Choosing between them

  • A predefined runbook exists: use it. Least code, least to maintain.
  • Several ordered AWS API calls, waits, branches or an approval step: a custom runbook.
  • Logic a runbook can't express, or sub-second reaction: Lambda (or a Lambda step inside a runbook).
  • Scaling capacity: neither. Use an Auto Scaling policy (Task 2.1).

Auto remediation that fights the real cause makes incidents worse. A runbook that restarts a service every five minutes hides a memory leak and can mask an outage. Pair remediation with a record (an OpsItem or a ticket) so the underlying fault still gets fixed.

AI-assisted investigation

CloudWatch investigations

Built into CloudWatch at no additional cost. You start an investigation from an alarm action, from a metric widget or from more than eighty service consoles, and it gathers related metrics, logs and changes, suggests probable causes, and proposes Systems Manager Automation runbooks to fix them. Findings collect in an investigation group (one per account) that the team can work through together. It was previously called Amazon Q Developer operational investigations.

AWS DevOps Agent

An agentic service that AWS describes as an always-on, autonomous on-call engineer, generally available since March 31, 2026. An investigation starts from an alert or by hand; the agent discovers the application's topology, correlates telemetry with code and deployment data, and produces a root cause analysis, a mitigation plan and prevention recommendations. It works beyond AWS: observability from Datadog, Dynatrace, New Relic, Splunk and Prometheus, code and CI/CD from GitHub, GitLab and Azure DevOps, and ticketing or chat through ServiceNow, Slack and PagerDuty.

Its scope is an agent space, which defines what the agent may access through IAM roles and tool integrations, per application, per on-call team or one central space. It can write specs for a coding agent such as Kiro to implement, and open a pre-filled support case. It is billed per second of agent task time, and its activity is recorded in CloudTrail.

Investigations or DevOps Agent?CloudWatch investigations is free and stays inside AWS. DevOps Agent goes further: multicloud and on-premises telemetry, code and deployment correlation, and proactive recommendations.

Kiro

AWS's AI development environment, in scope since revision 1.1. Its place in this task is the step after diagnosis: turning a mitigation plan or a prevention recommendation into reviewed code, such as the missing health check, the retry logic or the runbook itself. Its spec-driven approach writes requirements, design and task files before implementing them, and the Kiro CLI (the successor to the Amazon Q Developer CLI) connects to AWS through MCP servers.

Amazon DevOps Guru was the previous ML-based anomaly and insight service. It stopped accepting new customers on October 29, 2026, and support ends September 30, 2027. AWS recommends CloudWatch anomaly detection and alarms for alerting, and AWS DevOps Agent for investigation. Older practice questions may still offer DevOps Guru as the answer for "machine learning detects operational anomalies".

EventBridge: route, enrich, deliver

Skill 1.2.2Use EventBridge to route, enrich, and deliver events, and troubleshoot any issues with event bus rules

EventBridge is the event router that connects "something happened" to "do this about it". Nearly every AWS service emits events to it, which makes it the backbone of automated operations.

The pieces

Event buses

An event bus receives events. Every account has a default bus, which is where AWS services deliver their events. Custom buses carry your own application events, and partner buses receive events from SaaS providers. A bus can be a target of a rule on another bus, including in another account, which is how events are centralized into an operations account. A bus has a resource policy that says which accounts or organizations may put events on it.

Rules

A rule on a bus either matches an event pattern or runs on a schedule (a rate or cron expression, always in UTC). A matching rule sends the event to up to five targets. For new scheduled work, Amazon EventBridge Scheduler is the dedicated service, with more schedule options and higher limits.

Routing: event patterns

Matching events

A pattern matches an event when every field in the pattern is present and matches. Values are given as arrays, which act as "any of these". Content filters allow more than equality: prefix, suffix, anything-but, numeric, exists, cidr and wildcard.

Match ECS tasks that stopped, but not from scaling 
{
  "source": ["aws.ecs"],
  "detail-type": [
    "ECS Task State Change"
  ],
  "detail": {
    "lastStatus": ["STOPPED"],
    // ignore normal scale-in
    "stoppedReason": [{
      "anything-but": {
        "prefix": "Scaling activity"
      }
    }]
  }
}

Fields at the same level are combined with AND, so a pattern naming fields from two different services only matches an event that has both, which no event does. Use a separate rule per service unless the fields really do co-occur.

Enriching: adding context before delivery

Input transformer (on a rule)

A target receives the whole event by default. An input transformer picks values out of the event into variables and builds a new payload from a template, so the target gets exactly what it needs, for example a human-readable message for a chat channel or the parameter shape a runbook expects.

Turn an alarm event into a one-line message 
// 1. pull values out of the event
{
  "alarm": "$.detail.alarmName",
  "state": "$.detail.state.value",
  "why":   "$.detail.state.reason"
}

// 2. build the payload from them
"Alarm <alarm> is <state>: <why>"

EventBridge Pipes

Pipes are for point-to-point integrations, and they add a real enrichment stage. A pipe has a source, optional filtering, optional enrichment and a target. The enrichment step synchronously calls a Lambda function, a Step Functions Express workflow (Standard workflows aren't supported, because they can't be called synchronously), API Gateway or an API destination, and whatever it returns is what the target receives, so an event carrying only an order ID can arrive at the target with the customer's details attached. You are only charged for events that pass the filter.

Pipes or a bus?A bus is for many-to-many routing of events to several targets. A pipe is one source to one target, with filtering and enrichment in between.

Delivering: retries, dead letters and replay

Retry policy and dead-letter queues

EventBridge tries to deliver an event to a target for up to 24 hours, retrying with backoff; you can lower the maximum age and retry attempts per target. When delivery finally fails it publishes the FailedInvocations metric. Attach a dead-letter queue to each important target so failed events are kept instead of lost. It must be an SQS standard queue (not FIFO) in the same Region as the rule, and each message carries attributes that explain the failure, including ERROR_CODE, ERROR_MESSAGE, RULE_ARN and TARGET_ARN.

Not every failure is retried. Missing permissions, a target that no longer exists, or an address that can't be resolved go straight to the DLQ with no retries, because retrying can't succeed until someone fixes the cause. If a target throttles EventBridge for a prolonged period, EventBridge might not retry either.

Archive and replay

An archive stores events delivered to a bus, with an optional filter and retention period. Replay sends archived events back to the bus for a chosen time range, which is how you reprocess events after fixing a broken rule or target.

Troubleshooting event bus rules

Start with the three CloudWatch metrics in AWS/Events: TriggeredRules (did the rule match?), Invocations (did EventBridge call the target?) and FailedInvocations (did the call fail?). They separate a matching problem from a delivery problem immediately.

The rule never matches

  • Test the pattern: the EventBridge Sandbox in the console, or the TestEventPattern API, checks a pattern against a sample event.
  • Exact string matching: most of AWS treats : and / in an ARN as equivalent, but EventBridge does not. The ARN in the pattern must match the event's ARN character for character.
  • Global service events: API call events for global services such as IAM and Route 53 are only delivered in us-east-1. A rule for them in any other Region never fires.
  • CloudTrail-based patterns: some events, including AWS API call events via CloudTrail, have nothing in the resources field, so a pattern matching on it never matches.
  • Wait a moment: a new or changed rule takes a short time to take effect.

The rule matches but the target does nothing

This is almost always permissions, and which kind depends on the target:

  • Lambda, SNS and SQS targets rely on a resource policy on the target itself, unless you give the target an execution role. The Lambda function's policy must allow the events.amazonaws.com principal to call lambda:InvokeFunction, with the rule ARN as the source. The console adds this for you; a rule built with the CLI or a template often doesn't have it. Removing and re-adding the target in the console repairs it.
  • Other targets use an IAM execution role on the target, whose trust policy must allow events.amazonaws.com to assume it and whose permissions must cover the target action.
  • Encrypted SQS queues and SNS topics must use a customer managed KMS key whose key policy lets events.amazonaws.com call kms:Decrypt and kms:GenerateDataKey. With the AWS managed key, delivery silently fails.

Other symptoms

  • Scheduled rule ran at the wrong time: schedule expressions are UTC, and the finest resolution is one minute, not an exact second.
  • The rule ran twice: delivery is at-least-once, so rarely a rule or target runs more than once for one event. Make targets idempotent.
  • Runaway costs: a rule whose own action re-matches the rule creates an infinite loop. Narrow the pattern so the remediation's own events don't match, and set a budget alert.

Alarm on the FailedInvocations metric with statistic Sum: it is the standard way to find out that automation has quietly stopped working.

Systems Manager Automation runbooks

Skill 1.2.3Create or run custom and predefined Systems Manager Automation runbooks (for example, by using AWS SDKs or custom scripts) to automate tasks and streamline processes on AWS

An Automation runbook is an SSM document that performs a sequence of steps against AWS resources or inside instances. It replaces the mix of console clicks, scripts on someone's laptop and tribal knowledge that most operational tasks start as, and every run is recorded with its inputs, outputs and who started it.

Predefined runbooks

What AWS supplies

Systems Manager includes hundreds of predefined runbooks, maintained by AWS, AWS Support and AWS Config, organized by service in the Automation runbook reference. The name tells you the owner and intent:

  • AWS-*: general operations, such as AWS-RestartEC2Instance, AWS-StopEC2Instance, AWS-CreateImage and AWS-ConfigureS3BucketLogging.
  • AWS-*WithApproval: the same work with an aws:approve step that pauses until named approvers agree, such as AWS-StopEC2InstanceWithApproval.
  • AWSSupport-*: troubleshooting runbooks written by AWS Support, mostly diagnostic (collecting evidence about a problem), with some that also apply the fix.
  • AWSConfigRemediation-*: fixes designed to be attached to AWS Config rules as automatic remediation.

Check the reference for a runbook before writing one: for most routine fixes, one already exists.

Custom runbooks

Anatomy

A runbook is YAML or JSON with schemaVersion: '0.3', input parameters, an assumeRole and mainSteps that run in order. Each step runs one action, and later steps use earlier outputs as {{ stepName.outputName }}.

Remediate a full disk: grow the volume, extend the file system 
description: Grow the root volume
schemaVersion: '0.3'
assumeRole: '{{ AutomationAssumeRole }}'
parameters:
  InstanceId:
    type: String
  NewSizeGiB:
    type: Integer
    default: 100
  AutomationAssumeRole:
    type: String
mainSteps:
  - name: findVolume
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: DescribeVolumes
      Filters:
        - Name: attachment.instance-id
          Values:
            - '{{ InstanceId }}'
        - Name: attachment.device
          Values:
            - /dev/xvda
    outputs:
      - Name: id
        Selector: $.Volumes[0].VolumeId
        Type: String

  - name: modifyVolume
    action: aws:executeAwsApi
    inputs:
      Service: ec2
      Api: ModifyVolume
      VolumeId: '{{ findVolume.id }}'
      Size: '{{ NewSizeGiB }}'

  - name: waitForResize
    action: aws:waitForAwsResourceProperty
    timeoutSeconds: 600
    inputs:
      Service: ec2
      Api: DescribeVolumesModifications
      VolumeIds:
        - '{{ findVolume.id }}'
      PropertySelector: $.VolumesModifications[0].ModificationState
      DesiredValues:
        - optimizing
        - completed

  - name: extendFileSystem
    action: aws:runCommand
    inputs:
      DocumentName: AWS-RunShellScript
      InstanceIds:
        - '{{ InstanceId }}'
      Parameters:
        commands:
          # Nitro OS name, not /dev/xvda
          - growpart /dev/nvme0n1 1
          - xfs_growfs -d /
outputs:
  - findVolume.id

The one long line, PropertySelector, has to stay on one line: a YAML folded or quoted string split across lines joins with a space, which would corrupt the JSONPath.

The actions worth knowing

  • aws:executeAwsApi: call any AWS API. Service and Api use the SDK names, and the other inputs are passed straight through.
  • aws:runCommand: run commands inside a managed node, through AWS-RunShellScript or AWS-RunPowerShellScript.
  • aws:executeScript: run a Python or PowerShell script for logic a single API call can't express. This is the "custom scripts" the skill mentions.
  • aws:waitForAwsResourceProperty polls until a property matches; aws:assertAwsResourceProperty checks once and fails the step if it doesn't.
  • aws:approve: pause for human approval before a disruptive step.
  • aws:branch: choose the next step from a value, for conditional paths.
  • aws:invokeLambdaFunction: call an existing Lambda function as a step.

Steps also take timeoutSeconds, maxAttempts, onFailure (Abort, Continue or a step name) and onCancel, which is how a runbook handles failure without a person watching it.

Running a runbook

By hand and from code

From the Systems Manager console (Automation, then Execute automation), from the CLI or an AWS SDK with StartAutomationExecution, or from a CI pipeline. The call returns an AutomationExecutionId; get-automation-execution shows each step's status, inputs and outputs.

Automatically

  • A CloudWatch alarm, through an EventBridge rule on the alarm state change, with the runbook as the target.
  • An EventBridge rule on any event or on a schedule, with a Systems Manager Automation target.
  • An AWS Config rule's remediation action, which runs a runbook (usually an AWSConfigRemediation-* one, but any Automation runbook works) when a resource becomes noncompliant, manually or automatically.
  • A maintenance window, for recurring tasks such as patching.
  • CloudWatch investigations, which suggest the runbook to a person to approve.

Running against many resources: rate control

Choose the Rate Control execution mode, pick the parameter that identifies the resource with --target-parameter-name, and select resources with --targets by tag, by parameter values, by resource group, or all instances. Then limit the blast radius: concurrency is how many run at once, and the error threshold stops the rollout after too many failures. Both accept a number or a percentage. Adaptive concurrency can raise the quota from 100 concurrent automations up to 500.

Restart every tagged instance, 10 at a time 
aws ssm start-automation-execution \
  --document-name AWS-RestartEC2Instance \
  --targets Key=tag:App,Values=orders \
  --target-parameter-name InstanceId \
  --max-concurrency 10 \
  --max-errors 25%

Because the targets come from the tag, you don't pass instance IDs as input parameters. Multi-account and Region mode runs the same automation across accounts and Regions through AWS Organizations, but doesn't support aws:approve.

Stopping an automation that is making things worse

An automation can be attached to a CloudWatch alarm: if the alarm goes into ALARM while the automation runs, the automation is cancelled and its onCancel steps run. CloudTrail records the resulting StopAutomationExecution call.

Permissions: the usual failure

The Automation service role

A runbook acts through the role passed as AutomationAssumeRole. If none is passed, it runs with the permissions of whoever started it, which is fine for a person at the console but fails when the trigger is EventBridge or AWS Config. Two rules cover nearly every permissions failure:

  • The role's trust policy must let ssm.amazonaws.com assume it.
  • The role's permissions must cover every API the runbook calls, including those called by predefined AWS-* runbooks and by aws:executeAwsApi or aws:executeScript steps. AWS calls this out explicitly in the runbook reference: add an inline policy for the services the automation touches.

The person or service starting the automation also needs ssm:StartAutomationExecution and iam:PassRole for that role. For aws:runCommand steps, the instance must be a managed node: SSM Agent running, an instance profile with AmazonSSMManagedInstanceCore, and network access to the Systems Manager endpoints.

An automation that fails immediately on its first aws:executeAwsApi step is usually the assume role missing that API's permission, not a broken runbook. Read the failure message on the step, not just the execution status.

Two Systems Manager tools that older material pairs with remediation have been closed to new customers since November 7, 2025: Incident Manager (response plans, escalation and on-call schedules) and Change Manager (change requests and approvals). Existing customers keep using them. For incident tracking AWS points to OpsCenter, which is unaffected and collects OpsItems from alarms and EventBridge, with runbooks attached for remediation; for change management it points to partner ITSM tools.

Key takeaways

  • Localize faults with availability metrics: system status checks mean AWS hardware (recover), instance status checks mean the OS (reboot or replace), target 5XX means the application, ELB 5XX means the load balancer got no usable answer (502, 504) or has no registered targets (503) — an ALB with all targets unhealthy fails open rather than returning 503, and SQS ApproximateAgeOfOldestMessage is the earliest warning of stuck consumers.
  • CloudTrail Event history answers "what changed" for the last 90 days; a trail to CloudWatch Logs lets metric filters alarm on changes.
  • Remediate with a predefined runbook first, a custom runbook for ordered API calls with waits, branches or approvals, and Lambda for logic a runbook can't express. Always pair remediation with a record so the cause gets fixed.
  • CloudWatch investigations is free, AWS-only AI-assisted troubleshooting that suggests runbooks. AWS DevOps Agent (GA March 31, 2026) investigates autonomously across clouds, code and deployments within an agent space, and replaced DevOps Guru, which ends support September 30, 2027.
  • EventBridge routes with event patterns (exact string matching, fields ANDed), enriches with an input transformer or a Pipes enrichment step (Lambda, Step Functions Express, API Gateway, API destination), and delivers with 24-hour retries, a standard SQS DLQ (permission errors go there without retries), and archive and replay.
  • Troubleshoot rules with TriggeredRules, Invocations and FailedInvocations; test patterns in the Sandbox; remember us-east-1 for global service events, resource policies for Lambda, SNS and SQS targets (unless they have an execution role), execution roles for everything else, and customer managed KMS keys for encrypted targets.
  • Automation runbooks are SSM documents (schemaVersion: '0.3') with ordered steps. Run them from the console, an SDK, an alarm through EventBridge, a Config remediation or a maintenance window, with rate control (--target-parameter-name, --max-concurrency, --max-errors) across a fleet.
  • The AutomationAssumeRole must trust ssm.amazonaws.com and hold permissions for every API the runbook calls; the caller needs iam:PassRole. Incident Manager and Change Manager are closed to new customers; OpsCenter is not.
