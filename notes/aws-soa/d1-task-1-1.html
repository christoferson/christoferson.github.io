Overview

Task 1.1

Implement metrics, alarms, and filters by using AWS monitoring and logging services.

Operations starts with knowing what is happening. This task covers the plumbing: which service collects which signal, how to collect what AWS can't see by default (memory, disk, application logs), how to turn a signal into an alarm that does something, how to show it all on one screen, and how to tell people. Questions are often troubleshooting: an alarm that never fires, a missing metric, a notification that never arrives.

The examples use one setup throughout: an orders application running on an EC2 Auto Scaling group behind an Application Load Balancer, with a Lambda function for payments, a container service on Amazon ECS, and an Amazon Bedrock model that writes order summaries. It runs in a workload account (111111111111) in us-east-1 and eu-west-1; the operations team watches from a monitoring account (222222222222).

Monitoring and logging services

Skill 1.1.1Use AWS services (for example, Amazon CloudWatch, AWS CloudTrail, Amazon Managed Service for Prometheus) to configure monitoring and logging for workloads (for example, serverless, compute, AI)

Three services, three questions. CloudWatch answers "how is it performing?" with metrics and logs. CloudTrail answers "who changed what?" with a record of API calls. Amazon Managed Service for Prometheus answers the CloudWatch question for teams that already use Prometheus, typically on Kubernetes.

CloudWatch metrics

How metrics are organized

A metric is a time-ordered set of data points, identified by a namespace (AWS/EC2, AWS/Lambda, or your own such as Orders/App), a name (CPUUtilization) and up to 30 dimensions (name-value pairs such as InstanceId=i-0abc or AutoScalingGroupName=orders-asg). Each unique combination is a separate metric: CPUUtilization for one instance and for the whole Auto Scaling group are two different metrics, and an alarm must name the exact combination.

When you query a metric you choose a statistic over a period: Average, Sum, Minimum, Maximum, SampleCount, or a percentile such as p99 (often the best measure of latency, because averages hide slow requests).

Resolution, frequency and retention

  • EC2 basic monitoring sends metrics every 5 minutes at no charge; detailed monitoring (paid) sends every 1 minute. Faster Auto Scaling reactions need detailed monitoring.
  • Standard resolution custom metrics have 1-minute granularity; high resolution metrics go down to 1 second, and alarms on them can use 10- or 30-second periods.
  • CloudWatch keeps data points of under 1 minute for 3 hours, 1-minute data for 15 days, 5-minute data for 63 days and 1-hour data for 15 months, aggregating as it ages.

What EC2 doesn't report by itself

The hypervisor sees CPU, network, disk operations on instance store and status checks, but not what happens inside the operating system. Memory use, disk space use, swap and individual processes are not standard EC2 metrics. They need the CloudWatch agent (Skill 1.1.2) or an application publishing custom metrics with PutMetricData or the embedded metric format.

"CloudWatch shows CPUUtilization but not memory for the instance" isn't a permissions problem: memory has never been an EC2 metric. Install the CloudWatch agent.

CloudWatch Logs and metric filters

Log groups, streams and retention

Logs arrive as log events in log streams (usually one per source, such as an instance or Lambda execution environment), grouped into log groups (one per application or component, such as /orders/app). Retention is set per log group, from one day to ten years or never expire; the default is never expire, which quietly grows cost. Log groups can be encrypted with a KMS key.

Metric filters

A metric filter turns matching log events into a CloudWatch metric, so you can graph and alarm on things only the logs know: errors, timeouts, specific status codes, failed logins. It applies only to events that arrive after it is created; it doesn't scan old logs. The filter pattern can match terms ("ERROR"), or fields in JSON logs ({ $.status = 500 }) or space-delimited logs.

Count payment failures in JSON application logs 
# count payment_failed events
aws logs put-metric-filter \
  --log-group-name /orders/app \
  --filter-name payment-failures \
  --filter-pattern \
    '{ $.event = "payment_failed" }' \
  --metric-transformations '[{
    "metricName": "PaymentFailures",
    "metricNamespace": "Orders/App",
    "metricValue": "1",
    "defaultValue": 0
  }]'

metricValue=1 adds one per matching event; defaultValue=0 publishes zero when nothing matches, so an alarm sees "no failures" rather than missing data.

Searching and streaming logs

  • CloudWatch Logs Insights: a query language to search and aggregate logs, for example the top 10 slowest requests in the last hour.
  • Live Tail: watch matching log events in near real time while you troubleshoot.
  • Subscription filters: stream matching events in real time to Lambda, Amazon Data Firehose, Kinesis Data Streams or OpenSearch Service, for example to centralize logs in another account.
  • Log anomaly detection: learns normal log patterns and flags unusual ones.
  • Embedded metric format (EMF): applications write structured JSON logs that CloudWatch automatically extracts into metrics, a cheap way to publish custom metrics from Lambda.

AWS CloudTrail

What CloudTrail records

CloudTrail records API activity: who (IAM identity), what (action and parameters), when, from where (source IP) and the result. Management events (creating, changing or deleting resources, such as TerminateInstances or PutBucketPolicy) are recorded by default and visible in Event history for 90 days at no charge. Data events (high-volume operations on data, such as S3 GetObject or Lambda Invoke) must be enabled explicitly on a trail and cost extra.

Trails

A trail delivers events to an S3 bucket for long-term storage, and optionally to CloudWatch Logs (so metric filters and alarms can react to API calls, such as an alarm whenever someone changes a security group). A trail can cover all Regions, and an organization trail created in the management account covers every account in AWS Organizations. Log file integrity validation adds signed digest files so you can prove logs weren't altered. CloudTrail Insights flags unusual API call rates or error rates.

CloudTrail Lake (a managed event data store queried with SQL) has been in maintenance since March 31, 2026: no new customers. AWS recommends moving its data to Amazon CloudWatch; trails, Event history and Insights are unaffected.

Amazon Managed Service for Prometheus

What it is and when to use it

A managed, Prometheus-compatible service that stores and queries metrics with PromQL, scaling automatically. Workloads (usually Kubernetes on Amazon EKS) send metrics with Prometheus remote write, from a Prometheus server, the AWS Distro for OpenTelemetry collector, or an AWS managed collector that scrapes EKS without running your own agents. Alerting rules and the alert manager run in the workspace; Amazon Managed Grafana is the usual dashboard tool on top.

Choose it whenThe team already uses Prometheus exporters, PromQL and Grafana, or runs Kubernetes and wants open-source-compatible metrics. CloudWatch remains the native home for AWS service metrics.

Monitoring by workload type

Serverless

Lambda publishes Invocations, Errors, Throttles, Duration and ConcurrentExecutions automatically, and sends function output to a log group named /aws/lambda/<function> (the function's role needs permission to write logs). Add Lambda Insights (an extension) for memory and CPU detail, and AWS X-Ray or CloudWatch Application Signals for traces, service maps and latency by dependency. API Gateway, SQS, DynamoDB and Step Functions all publish their own metrics.

Compute

EC2 metrics in AWS/EC2 plus status checks (StatusCheckFailed_System for AWS hardware problems, StatusCheckFailed_Instance for problems inside the instance); the CloudWatch agent for memory, disk and logs; Container Insights for ECS and EKS; load balancer metrics in AWS/ApplicationELB such as TargetResponseTime, HTTPCode_Target_5XX_Count and UnHealthyHostCount.

AI

Amazon Bedrock publishes runtime metrics in the AWS/Bedrock namespace (invocations, latency, input and output token counts, throttles and errors, by model), so you can alarm on throttling or token spend. Model invocation logging, which you turn on in Bedrock settings, sends full prompts, responses and metadata to CloudWatch Logs or S3, where metric filters and Logs Insights work as with any other log. Bedrock Guardrails publishes intervention metrics, and Amazon Bedrock AgentCore sends agent traces to CloudWatch. CloudTrail records Bedrock API calls such as who changed a guardrail.

"Who deleted the security group?" is CloudTrail. "Why are requests slow?" is CloudWatch metrics, logs and traces. "Count error messages in the logs and alarm" is a metric filter. "Team uses PromQL on EKS" is Amazon Managed Service for Prometheus.

The CloudWatch agent

Skill 1.1.2Configure and manage the CloudWatch agent to collect metrics and logs from EC2 instances, Amazon ECS clusters, or Amazon EKS clusters

The CloudWatch agent runs inside the instance or cluster and collects what AWS can't see from outside: operating system metrics (memory, disk, swap, processes), log files, and custom metrics through StatsD and collectd. It runs on Linux and Windows, on EC2 and on premises.

On EC2: install, configure, start

  1. Give the instance a roleAttach an instance profile with CloudWatchAgentServerPolicy (publish metrics and logs) and AmazonSSMManagedInstanceCore (so Systems Manager can manage it).
  2. Install the agentFleet-wide with Systems Manager Run Command and the AWS-ConfigureAWSPackage document (package AmazonCloudWatchAgent), or bake it into the AMI.
  3. Write the configurationA JSON file, created by hand or with the configuration wizard, stored centrally in Systems Manager Parameter Store.
  4. Start the agent with that configurationOn each instance, or fleet-wide with the AmazonCloudWatch-ManageAgent document.

The configuration file

The JSON file has sections for the agent itself, metrics, logs, traces and OpenTelemetry. The metrics go to the CWAgent namespace unless you set another.

CloudWatch agent configuration for the orders instances 
{
  "agent": {
    // seconds; below 60 = high resolution
    "metrics_collection_interval": 60
  },
  "metrics": {
    // tag every metric with these
    "append_dimensions": {
      "InstanceId": "${aws:InstanceId}",
      "AutoScalingGroupName":
        "${aws:AutoScalingGroupName}"
    },
    // also roll up per Auto Scaling group
    "aggregation_dimensions": [
      ["AutoScalingGroupName"]
    ],
    "metrics_collected": {
      "mem": {
        "measurement": [
          "mem_used_percent"
        ]
      },
      "disk": {
        "measurement": ["used_percent"],
        "resources": ["/"]
      }
    }
  },
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [{
          "file_path":
            "/var/log/orders/app.log",
          "log_group_name": "/orders/app",
          "log_stream_name":
            "{instance_id}",
          // log group retention
          "retention_in_days": 30
        }]
      }
    }
  }
}

The // comments are explanations only: JSON doesn't allow comments, so remove them in a real file. append_dimensions accepts only ImageId, InstanceId, InstanceType and AutoScalingGroupName. aggregation_dimensions publishes extra rolled-up copies, here memory and disk per Auto Scaling group, which is what you alarm on for a fleet whose instances come and go.

Storing and loading the configuration

Store the JSON in Parameter Store with a name starting AmazonCloudWatch-, such as AmazonCloudWatch-orders-linux. The managed CloudWatchAgentServerPolicy only allows ssm:GetParameter on parameter/AmazonCloudWatch-*, so any other name fails with access denied unless you write your own policy. Writing the parameter needs CloudWatchAgentAdminPolicy, which should only be on an admin instance.

Load the configuration from Parameter Store and restart the agent 
# -a fetch-config: load the config
# -m ec2: on EC2 (or onPremise)
# -s: restart the agent afterwards
# -c ssm:NAME: from Parameter Store
cd /opt/aws/amazon-cloudwatch-agent/bin
sudo ./amazon-cloudwatch-agent-ctl \
  -a fetch-config -m ec2 -s \
  -c ssm:AmazonCloudWatch-orders-linux

Other actions: -a status shows whether the agent runs and which configuration it loaded; -a append-config adds a second configuration (for example, a team's extra log file) instead of replacing the first. The agent's own log is /opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log, the first place to look when metrics don't appear.

Agent installed but no metrics or logs: check the instance role (missing CloudWatchAgentServerPolicy), the parameter name prefix, network access to CloudWatch endpoints (a private subnet needs a NAT gateway or VPC endpoints for CloudWatch, CloudWatch Logs and Systems Manager), and the agent log.

On Amazon ECS

Container Insights

Container Insights collects CPU, memory, network and storage metrics per cluster, service and task, and ECS turns it on per cluster or as an account default. Container Insights with enhanced observability adds container-level detail and curated dashboards, billed per observation rather than as custom metrics.

Turn on enhanced Container Insights for new ECS clusters 
aws ecs put-account-setting \
  --name containerInsights \
  --value enhanced

For an existing cluster, use aws ecs update-cluster-settings with name=containerInsights,value=enhanced. On ECS with EC2 instances, the CloudWatch agent can also run as a daemon service to collect instance-level metrics; application logs go to CloudWatch Logs through the awslogs log driver or FireLens.

On Amazon EKS

The Amazon CloudWatch Observability add-on

An EKS add-on (also available as a Helm chart) that installs the CloudWatch agent and Fluent Bit as DaemonSets on every node. It turns on Container Insights with enhanced observability (metrics per cluster, node, pod and container) and CloudWatch Application Signals by default, and Fluent Bit ships container logs to CloudWatch Logs. The node role or a Pod Identity association needs CloudWatchAgentServerPolicy.

On EKS, don't install the agent by hand on each node: nodes come and go. Use the add-on, which runs the agent as a DaemonSet on every node automatically.

CloudWatch alarms

Skill 1.1.3Configure, identify, and troubleshoot CloudWatch alarms that can invoke AWS services directly or through Amazon EventBridge (for example, by creating composite alarms and identifying their invokable actions)

How a metric alarm decides

States

OK (within threshold), ALARM (breaching), INSUFFICIENT_DATA (just created, metric not available, or not enough data). Actions run when the state changes, not continuously while it stays the same.

Period, evaluation periods and datapoints to alarm

The alarm aggregates the metric over each period (for example 60 seconds) using a statistic, compares it with a threshold, and looks at the most recent evaluation periods. Datapoints to alarm sets how many of those must breach: "3 out of 5" (an M out of N alarm) tolerates brief spikes better than "1 out of 1".

Alarm when the orders fleet averages over 80% CPU for 3 of 5 minutes 
# the whole group, not one instance
aws cloudwatch put-metric-alarm \
  --alarm-name orders-high-cpu \
  --namespace AWS/EC2 \
  --metric-name CPUUtilization \
  --dimensions \
  Name=AutoScalingGroupName,Value=orders \
  --statistic Average --period 60 \
  --evaluation-periods 5 \
  --datapoints-to-alarm 3 \
  --threshold 80 \
  --comparison-operator \
    GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions \
    arn:aws:sns:us-east-1:111111111111:ops-alerts

Treating missing data

When data points are missing, the alarm treats them as missing (default: ignore, and go to INSUFFICIENT_DATA if all are missing), notBreaching (good), breaching (bad) or ignore (keep the current state). Choose by meaning: for an error-count metric that only reports when errors happen, missing means healthy (notBreaching); for a heartbeat metric, missing means the sender is down (breaching).

Other alarm types

  • Anomaly detection alarms: compare a metric with a band learned from its history, for metrics with daily or weekly patterns where a fixed threshold doesn't fit.
  • Metric math alarms: alarm on an expression, such as error rate = errors ÷ requests × 100.
  • Metrics Insights query alarms: alarm on a SQL-style query across many resources, such as the highest CPU of any instance with a tag.
  • Log-based alarms: alarm on a metric created by a metric filter.

ActionNotes

Anything else: through EventBridge

Every alarm state change is also sent to Amazon EventBridge as a CloudWatch Alarm State Change event. An EventBridge rule can route it to targets alarms can't call directly: Step Functions, a Systems Manager Automation runbook, an SQS queue, an ECS task, an API destination such as a chat or ticketing tool, or an event bus in another account.

EventBridge pattern: any orders alarm entering ALARM 
{
  "source": ["aws.cloudwatch"],
  "detail-type": [
    "CloudWatch Alarm State Change"
  ],
  "detail": {
    // alarms named orders-...
    "alarmName": [{"prefix": "orders-"}],
    "state": { "value": ["ALARM"] }
  }
}

"Recover the instance automatically when the underlying hardware fails" is an EC2 recover action on a StatusCheckFailed_System alarm. "Run a multi-step remediation workflow" is EventBridge to Step Functions or a Systems Manager Automation runbook.

Composite alarms

What they are for

A composite alarm watches other alarms and goes into ALARM when a rule over their states is true. It reduces noise: instead of five pages when the database slows down (high latency, 5XX errors, queue backlog, CPU, connections), one composite alarm pages when the symptoms that matter coincide. The child alarms can have no actions at all.

Composite alarm rule for the orders service 
// page only when users are affected
ALARM("orders-5xx-high")
  AND (ALARM("orders-latency-p99")
       OR ALARM("orders-queue-backlog"))
  AND NOT ALARM("maint-window")

Rules use ALARM(), OK() and INSUFFICIENT_DATA() with AND, OR and NOT, and AT_LEAST(2, ALARM, (...)) for "at least two of these". A composite alarm can have up to 100 child alarms. Actions suppression can silence a composite's actions while a named suppressor alarm (for example, a deployment-in-progress alarm) is in ALARM.

What composite alarms can invoke

Only SNS notifications, Lambda functions, Systems Manager OpsItems and Incident Manager incidents (plus starting an investigation). They can't run EC2 actions or Auto Scaling actions; put those on the child metric alarm. Child alarms must be in the same account and Region, except when the composite alarm is in a CloudWatch cross-account observability monitoring account.

"Use a composite alarm to scale out the Auto Scaling group" is wrong: composite alarms can't trigger Auto Scaling. Scaling belongs on a metric alarm (or better, a target tracking policy).

Troubleshooting alarms

Alarm stuck in INSUFFICIENT_DATA

The metric doesn't exist with those exact dimensions (a typo, or alarming per instance on a metric only published per Auto Scaling group), the metric isn't being published (agent stopped, basic monitoring's 5-minute data with a 1-minute period), or the alarm is in a different Region from the metric.

Alarm in ALARM but nothing happened

Alarm actions are disabled (ActionsEnabled false, or a mute rule or actions suppression is active); the action is only set for a different state; the SNS topic's subscription isn't confirmed; the SNS topic is encrypted with a KMS key whose key policy doesn't allow CloudWatch (cloudwatch.amazonaws.com) to use it; the Lambda function's resource policy doesn't allow CloudWatch to invoke it.

Alarm flapping

Too sensitive: increase evaluation periods, use M out of N datapoints, a longer period, or an anomaly detection band.

Dashboards across accounts and Regions

Skill 1.1.4Create, implement, and manage customizable and shareable CloudWatch dashboards that display metrics and alarms for AWS resources across multiple accounts and AWS Regions

Building dashboards

A dashboard is a page of widgets: line, stacked area, number, gauge and bar graphs of metrics; alarm status widgets; Logs Insights query results; text (Markdown) for runbook links. Dashboards are global: one dashboard can show widgets from several Regions. Automatic dashboards exist for most services, and dashboard variables let one dashboard switch between, for example, environments or instance IDs from a drop-down.

Dashboards as code

A dashboard is a JSON document: create it with aws cloudwatch put-dashboard, or as an AWS::CloudWatch::Dashboard resource in CloudFormation, so every environment gets the same dashboard and changes are reviewed like code.

Seeing other accounts

CloudWatch cross-account observability

The recommended approach, set up with the Observability Access Manager. In the monitoring account (222222222222) you create a sink; each source account (such as 111111111111) creates a link to it, choosing what to share: metrics, log groups, X-Ray traces, Application Signals data, Application Insights applications and Internet Monitor monitors. With AWS Organizations, new accounts can be linked automatically. In the monitoring account, people search, graph, query and alarm on source-account data as if it were local, with no extra charge for sharing metrics and logs.

It works within one Region: set up a sink and links in each Region you use. A monitoring account can have up to 100,000 source accounts; a source account can share with up to five monitoring accounts.

Cross-account cross-Region dashboards (the older console method)

Each sharing account creates the CloudWatch-CrossAccountSharingRole IAM role, trusting the monitoring account; the monitoring account enables cross-account viewing. Dashboards in the monitoring account can then show metrics and alarms from many accounts and many Regions in one view. It shows metrics and alarms, not logs, and doesn't let you create alarms on the other accounts' metrics, which is why AWS recommends cross-account observability for new setups.

Sharing a dashboard with people outside the account

A dashboard can be shared publicly (anyone with the link), with specific email addresses (they sign in with a password, managed by Amazon Cognito), or through a single sign-on provider. Viewers don't need AWS accounts; CloudWatch creates an IAM role to read the dashboard's data.

"One dashboard for the operations team showing metrics, logs and traces from all workload accounts, with alarms in the central account" points to cross-account observability (sink and links). "Executives without AWS accounts need to see a dashboard" points to dashboard sharing.

Notifications with Amazon SNS

Skill 1.1.5Configure AWS services to send notifications to Amazon SNS and to invoke alarms that send notifications to Amazon SNS

Amazon SNS is publish-subscribe messaging: a service publishes a message to a topic, and SNS delivers a copy to every subscription: email, SMS, HTTP(S) endpoints, SQS queues, Lambda functions, mobile push, Amazon Data Firehose, and chat channels through Amazon Q Developer in chat applications (formerly AWS Chatbot). Email and HTTP subscriptions must be confirmed before they receive anything.

Services that publish to SNS

Directly

  • CloudWatch alarms: an SNS action per state (ALARM, OK, INSUFFICIENT_DATA).
  • EC2 Auto Scaling: notifications when instances launch, terminate or fail to launch.
  • Amazon RDS event subscriptions: failovers, reboots, backups, configuration changes.
  • S3 Event Notifications: object created or deleted, to a topic.
  • AWS CloudFormation: stack event notifications.
  • AWS Backup, AWS Config, AWS Budgets and many others.

Through EventBridge

Most AWS services emit events to EventBridge (AWS Health events, GuardDuty findings, EC2 state changes, Systems Manager changes). A rule matching the event, with the SNS topic as its target, notifies people about anything that has an event even if the service has no SNS option of its own.

Permissions: the most common failure

Topic access policy

When a service (rather than an IAM identity) publishes, the topic's access policy must allow that service principal to call sns:Publish. Without it, S3 refuses to save the event notification configuration, and EventBridge rules fail to deliver.

Topic policy statement: let S3 publish events from one bucket 
{
  "Effect": "Allow",
  "Principal": {
    "Service": "s3.amazonaws.com"
  },
  "Action": "sns:Publish",
  "Resource":
    "arn:aws:sns:us-east-1:111111111111:ops-alerts",
  "Condition": {
    // only this bucket, in this account
    "ArnLike": {
      "aws:SourceArn":
        "arn:aws:s3:::orders-uploads"
    },
    "StringEquals": {
      "aws:SourceAccount": "111111111111"
    }
  }
}

Encrypted topics

A topic encrypted with a customer managed KMS key only works if the key policy lets the publishing service use the key (kms:GenerateDataKey* and kms:Decrypt). The AWS managed key for SNS can't be used by other services, so an alarm or S3 notification to a topic encrypted with aws/sns silently fails. Use a customer managed key with the service principal allowed.

An alarm goes into ALARM, the alarm history shows the action ran, but no email arrives: check that the email subscription was confirmed, then whether the topic is encrypted with a key the publisher can't use.

Related service Extra

AWS User Notifications centralizes notification setup in the console (for example, for AWS Health and CloudWatch alarm events) and delivers to email, chat channels and the AWS Console Mobile Application. Revision 1.1 of the exam guide removed it from the skill examples, but it may still appear as an answer option.

Key takeaways

  • CloudWatch metrics are identified by namespace, name and dimensions; alarms must name the exact combination. EC2 basic monitoring is 5-minute, detailed 1-minute; memory and disk space are never EC2 metrics.
  • Logs live in log groups with per-group retention (default never expire). Metric filters turn new matching log events into metrics; subscription filters stream logs out; Logs Insights queries them.
  • CloudTrail records management events by default (90-day Event history); trails store events in S3 and optionally CloudWatch Logs, across Regions and organizations; data events cost extra. CloudTrail Lake takes no new customers.
  • Amazon Managed Service for Prometheus is for Prometheus and PromQL users, typically on EKS, with Managed Grafana.
  • The CloudWatch agent collects memory, disk, processes and log files. It needs CloudWatchAgentServerPolicy, a configuration in Parameter Store named AmazonCloudWatch-*, and fetch-config. ECS uses Container Insights (enhanced observability); EKS uses the CloudWatch Observability add-on.
  • Alarms act on state changes: SNS, Lambda, EC2 actions, Auto Scaling, OpsItems, Incident Manager, investigations; everything else through EventBridge. Composite alarms combine alarms to cut noise and can only notify (SNS, Lambda, OpsItems, incidents), never scale or stop instances.
  • Cross-account observability (sink in the monitoring account, links in source accounts, per Region) is the recommended way to see and alarm on other accounts; the older cross-account role shows metrics across Regions on dashboards.
  • SNS delivers to confirmed subscriptions. Service publishers need a topic policy allowing their service principal and, for encrypted topics, a customer managed KMS key that allows them.
